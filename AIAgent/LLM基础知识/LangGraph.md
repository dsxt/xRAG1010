# LangGraph

> 来源：尚硅谷《大模型技术之 LangGraph》V1.1.0。阅读稿。`create_agent`、消息类型、工具定义见 `LangChain.md`，这里只写图运行时自己的部分。第 8 节是对照面试题补的恢复、停机、网关边界、评测门禁和选型，课件机制仍在前面。

LangGraph 是低级编排框架和运行时，用来构建、管理和部署长期运行的有状态智能体。工作流被建成一张图：

| 概念 | 是什么 |
|---|---|
| 节点 | 一次计算。可以是模型调用、工具，或任意函数 |
| 边 | 节点之间怎么转移 |
| 状态 | 整次执行共享、沿图传递的数据 |

它把这些做成生产能力：执行可以持久化，故障后接着跑；任意点可以停下来让人看、改状态；短期工作记忆和跨会话长期记忆；为流式工作流设计；有状态、长时间运行的流程能部署。

- 仓库：https://github.com/langchain-ai/langgraph
- 文档：https://docs.langchain.com/oss/python/langgraph/overview

和 LangChain 的分界用一句话就够：应用需要有状态、可循环、可分支、还能回溯的多步控制流时，链不好写，要用图。

| | LangGraph | LangChain |
|---|---|---|
| 抽象 | 低，控制到每一步 | 高，开箱即用 |
| 状态 | 自带状态机和检查点 | 要自己管 |
| 执行 | 按图，同一步里可以并行 | 线性的链 |
| 持久化 | 原生 | 要另做 |
| 适合 | 复杂、有状态的智能体 | 简单的链式调用 |

因此它用在：多智能体、要长期记忆、要人工审核、后台任务和实时交互混在一起、编排逻辑必须精细控制的场合。

课程环境：`conda create --name=langgraph_venv python=3.12`，`pip install langgraph==1.0.5`，用 `pip show langgraph` 确认。看图结构需要 `grandalf`，然后 `compiled_graph.get_graph().draw_ascii()`。

## 1. 一次最小的图

五步：定义状态，写节点函数，用状态构造 `StateGraph` 并添加节点和边，`compile()` 得到可调用的图，`invoke`。

课程的例子是问答：拿到问题后，知识库检索和联网搜索同时做，两边都到了再汇总成最终回答。状态是一个 `TypedDict`：`query`、`rag_result`、`web_search_result`、`final_answer`。两个搜索节点都从 `START` 拉边，都再连到汇总节点，汇总连到 `END`。从 `START` 分出两条边，就是同一步并行。节点返回的是自己改过的那几项，例如 `{"rag_result": ...}`。

```python
graph = StateGraph(state_schema=MyState)
graph.add_node(rag_search_node)
graph.add_node(web_search_node)
graph.add_node(final_answer_node)
graph.add_edge(START, "rag_search_node")
graph.add_edge(START, "web_search_node")
graph.add_edge("rag_search_node", "final_answer_node")
graph.add_edge("web_search_node", "final_answer_node")
graph.add_edge("final_answer_node", END)
compiled = graph.compile()
compiled.invoke({"query": "如何使用LangGraph"})
```

`add_node` 不另起名字时，节点名就是函数名。

## 2. 状态

状态是整张图的目标，也是节点允许改的数据。先定状态，再写节点。

### 2.1 三种写法

| 写法 | 特点 | 课程建议 |
|---|---|---|
| `TypedDict` | 给字典的键标类型，reducer 也标在键上 | 推荐 |
| Pydantic `BaseModel` | 运行时校验，静态检查也能推类型 | 可以用 |
| `@dataclass` | 标准库数据容器，自动生成 `__init__` 等 | 可以用 |

键的类型后面可以再挂 reducer，见 2.3。

### 2.2 输入、内部、输出可以不是同一份

`StateGraph` 有三个 schema：

| 参数 | 作用 |
|---|---|
| `state_schema` | 图内部的完整状态。节点能读能写的字段都在这里。必填 |
| `input_schema` | 调用方允许传入的键，是内部状态的子集。省略时等于 `state_schema` |
| `output_schema` | 调用返回的键，也是子集。省略时等于 `state_schema` |

这样对外只暴露 `query` 进、`final_answer` 出，中间的检索结果留在图里。多传了 schema 里没有约定的输入键，不会变成合法输入。

节点函数的注解还可以写成另一份更窄的类型，表示这个节点只声明自己关心的字段。课程把这叫做节点间的数据隔离：搜索节点和汇总节点不必在签名里共享同一份「可见字段」清单。真正写回图的，仍然是返回字典里的增量，并且这些键要能和 `state_schema` 合并。

### 2.3 Reducer：增量怎么并进全局状态

每个节点返回的是增量，不是新的完整状态。某个键怎么从旧值变成新值，由这个键自己的 reducer 决定。reducer 接收两个参数：左边是当前全局值，右边是节点刚写出的值，返回合并结果。

| 种类 | 行为 |
|---|---|
| 不写 reducer | 覆盖。节点返回 `{"foo": 2}`，`foo` 变成 2，没返回的键保持原样 |
| `operator.add` | 由类型决定。`list` 是追加，`str` 是拼接，`int` 是相加。并行节点写同一个键时靠它汇总，而不是互相覆盖 |
| 自定义函数 | `(left, right) -> merged`。课程用它把消息列表接起来 |
| `add_messages` | 课程点名的内置 reducer，位于 `langgraph.graph.messages`，专门合并消息列表 |

挂法是 `Annotated`：

```python
class ListAddState(TypedDict):
    data: Annotated[list[int], operator.add]
```

并行时两个节点都从 `START` 出发、都连到 `END`，各自返回一段列表。`operator.add` 会把两段都接在初始值后面。字符串、整数同样：初始 `"Say: "` 接上 `"Hello "` 和 `"World!"`；初始 `10` 加上 `5` 和 `3`。

默认覆盖的例子：初始 `{"foo": 1, "bar": ["hi"]}`，第一个节点只写 `foo=2`，第二个节点只写 `bar=["bye"]`，结果是 `foo` 被换成 2，`bar` 被换成 `["bye"]`，不是在 `["hi"]` 后面追加。

自定义 reducer 和 `operator.add` 的差别在于合并策略可以自己写。消息场景里，左边是已有消息，右边是这个节点新产生的消息。

### 2.4 不存状态时，每次调用都是一张白纸

`invoke` 的默认行为：先做一个空状态，再把这次传入的初始值合并进去，然后跑图。一次性任务没问题。两类场景会坏：

- 同一会话要多次调用。第一次写入的 `messages` 在第二次调用时不存在，因为又从一个空列表开始。
- 跑到中间某个节点抛错。已经成功的节点不想重算，修复后要从断点继续。

两边都靠把状态存下来，下次按同一个 id 取回来，而不是重新初始化。同一个 Agent 会有多用户、单用户多会话，所以存储必须带 id。这个 id 叫 `thread_id`，只是状态空间的隔离键，和线程无关。

存状态的组件是 Checkpointer，类都在 `langgraph.checkpoint` 下。可以放内存，也可以放数据库。接法三步：

1. 创建 checkpointer。
2. `compile(checkpointer=...)`。
3. 调用时传入 `config={"configurable": {"thread_id": "..."}}`。

同一个 `thread_id` 就是同一段短期记忆；新会话用新 id。`create_agent` 底层就是一张 LangGraph 图，所以把 `InMemorySaver` 传给 `create_agent(..., checkpointer=...)`，效果和自己 `compile` 一样。两次 `invoke` 用同一个 `user_1_session_1`，第二次问题「适合出去玩吗」能看见第一次查过的天气。

`InMemorySaver` 解决不了进程退出。生产用数据库。课程用 SQLite：`pip install langgraph-checkpoint-sqlite`，`sqlite3.connect(path, check_same_thread=False)`，再 `SqliteSaver(conn)`。

断点续跑的约定：节点修好之后，`invoke(None, config=原来的 config)`。`None` 表示不要新的初始状态，用这个 `thread_id` 上一次留下的检查点继续。第一次失败前，已经成功的节点写进库；恢复时那些节点不会被当作全新输入再跑一遍。

### 2.5 历史状态长什么样

有检查点之后，才能回答「状态是什么时候写下的」。这要先看运行时怎么推进，见第 3 节。这里先记读取接口，它们都要 `thread_id`：

| 方法 | 返回 |
|---|---|
| `get_state(config)` | 最近一个时间步的快照 |
| `get_state_history(config)` | 全部时间步的迭代器，按时间倒序 |

每条是 `StateSnapshot`：

| 字段 | 含义 |
|---|---|
| `values` | 这一步的状态值 |
| `next` | 下一步超步要执行的节点名。恢复时靠它知道从哪继续 |
| `config` | 取到这条快照所用的配置 |
| `metadata` | 这条快照的元数据 |
| `parent_config` | 父快照的配置，没有则为空 |
| `interrupts` | 这一步尚未处理的中断 |

## 3. 底层是 Pregel，不是普通 DAG

`compile()` 把逻辑图变成一个 Pregel 实例。Pregel 管从开始到结束的整次运行。两个部件：

| 部件 | 对应什么 |
|---|---|
| Actor | 节点。类是 `PregelNode`，实现 LangChain 的 Runnable。每个 Actor 订阅一些通道、写入一些通道 |
| Channel | Actor 之间的通信。每个通道有值类型、更新类型、更新函数。更新函数收下一批更新，改掉通道里存的值 |

边的本质就是在声明：这个节点订阅哪些通道，跑完写哪些通道。因此它不是传统 DAG。传统 DAG 里，一个节点要等所有上游边都完成才启动。LangGraph 里，节点是因为自己订阅的通道在上一步被写过，才在这一步被选中。

执行单位叫超步（Superstep）。一个超步三阶段：

1. Plan。决定这一步跑哪些 Actor。第一步选订阅了特殊输入通道的 Actor；之后选订阅了「上一步被更新的通道」的 Actor。
2. Execute。选中的 Actor 并行跑，直到全部完成、有一个失败，或超时。
3. Update。用这一步写出的值更新通道。

超步反复做，直到没有 Actor 被选中，或步数到达上限。

课程用一张五节点的图说明通道和步。`START` 在 step -1 把输入写进通往 `a` 的通道。step 0 跑 `a`，写通往 `b` 和 `c` 的通道。step 1 并行跑 `b` 和 `c`。step 2 跑 `b_2` 和 `d`。`b_2` 又写了通往 `d` 的通道，所以 step 3 再跑一次 `d`。没有新的通道更新后结束。`d` 会执行两次，不是因为边上写了两次调用，而是因为它的通道被写了两次。

编译后的图上能直接看这些对象：`graph.channels`、`graph.nodes`，以及某个节点的 `triggers`（订阅）和 `writers`（写入）。`START` 这个特殊节点跑完也会落一个检查点。

`START` 和 `END` 本身是字符串：`START` 是 `"__start__"`，`END` 是 `"__end__"`。`START` 表示把用户输入送进图，用来指定谁先跑。`END` 表示这条边走完就停。

## 4. 节点

### 4.1 输入由运行时注入

节点一般是普通 Python 函数，同步或异步都可以。参数：

| 参数 | 内容 |
|---|---|
| `state` | 业务状态 |
| `config` | `RunnableConfig`。里面有 `thread_id`，也可以放调用时带上的其它配置，例如 `user_id` |
| `runtime` | `Runtime`。`context` 是调用时传入的依赖（模型、数据库），另外还有 `store`、`stream_writer` |

这三个由运行时注入。`config` 和 `runtime` 用关键字传入，所以它们在签名里的顺序可以调换。

依赖不要写死在节点里。`invoke(..., context={"llm": ..., "db": ...})`，节点里用 `runtime.context["llm"]` 取。和某次调用相关、但不是业务状态的配置放 `config["configurable"]`，例如用户 id。进度不必写进状态：`runtime.stream_writer({"status": "thinking", ...})` 把自定义数据送到图外，只有流式模式 `custom` 收得到。

### 4.2 输出只能是增量

返回字典里只放这个节点改过的键。运行时把所有节点的输出当作增量，和当前全局状态合并。

把整个 `state` 改完再返回，会出两种问题：

- 没有 reducer 的键无法合并，直接抛异常。
- 有 reducer 的键会被算进这次更新。节点如果顺手把不属于自己的键也带了出去，数据会被多合并一次。

并行的搜索节点各自只返回自己的结果键；汇总节点只返回 `final_answer`。

### 4.3 缓存

同一个节点、同一份输入、缓存没过期，就不再计算。两处配置：

- 编译时给存储：`langgraph.cache` 里有内存、Redis、SQLite。`compile(cache=InMemoryCache())`。
- 节点上给策略：`add_node(..., cache_policy=CachePolicy(ttl=10))`。`ttl` 单位秒，不写则永不过期。`key_func` 默认用 pickle 对输入做哈希，可以换成自己的键。

课程的演示是一个睡 5 秒的节点。第一次 `x=5` 真的算；第二次换了 `thread_id` 但输入仍是 `x=5`，10 秒内直接拿缓存。缓存键看的是节点输入，不是线程 id。

### 4.4 重试

调 API、查库、调模型时，节点会不稳定。`add_node(..., retry_policy=RetryPolicy(...))`。

| 字段 | 含义 |
|---|---|
| `max_attempts` | 总共最多尝试几次 |
| `retry_on` | 哪些异常才重试 |

默认策略会重试一般异常，但下面这些不重试：`ValueError`、`TypeError`、`ArithmeticError`、`ImportError`、`LookupError`、`NameError`、`SyntaxError`、`RuntimeError`、`ReferenceError`、`StopIteration`、`StopAsyncIteration`、`OSError`。所以一个故意抛 `ValueError` 的节点，即使写了 `max_attempts=3`，也不会被默认策略再试。

## 5. 图执行过程中把数据送出来

`invoke` 要等整张图结束才返回最终状态。前端要逐 token 显示，或者长流程要显示「现在在哪一步」，用 `stream` / `astream`。图实现了 Runnable，所以有这组方法。

| `stream_mode` | 每次给出什么 |
|---|---|
| `values` | 某个节点结束后的完整状态 |
| `updates` | 该步的增量。同一步有多份增量就分多次吐。元素是 `{节点名: 该节点返回值}` |
| `custom` | 节点里 `stream_writer` / `writer` 推出来的自定义数据，不进状态 |
| `messages` | 任何调用了 LLM 的节点里，模型的流式片段。元素是 `(token chunk, metadata)`，`metadata` 里有 `langgraph_node` |
| `debug` | 调度、输入输出等全部调试事件 |
| 多种模式的列表 | 例如 `["updates", "custom"]`。元素变成 `(mode, data)` |

`custom` 用来报「正在分析意图」「正在检索」，又不污染状态。`messages` 用来把模型生成的 token 直接推到图外。

## 6. 人工审核：interrupt

有些步骤要人拍板。在节点任意位置调用 `interrupt(payload)`，执行停在这里，payload 会随着结果离开图。人处理完，用同一次配置再 `invoke`，图继续。必须有 checkpointer，否则停住的状态无处可放。

课程的例子是转账前审核：

1. `compile(checkpointer=InMemorySaver())`，调用带固定 `thread_id`。
2. 第一次 `invoke` 停在 `interrupt`。返回值里 `result["__interrupt__"][0].value` 就是给用户看的审核数据。
3. 第二次 `invoke(Command(resume=用户的决定), config=同一个 config)`。`resume` 的值回到 `interrupt(...)` 的返回值。课程里它可以是 `bool`，也可以是带 `approved`、以及改过的收款人、金额、备注的字典。
4. 节点根据这个返回值写 `approved` 等字段，后面的执行节点再决定真转还是取消。

恢复时的坑：有 `interrupt` 的函数会从头再执行一遍，而不是从 `interrupt` 的下一行接着执行。`interrupt` 前面的写库、调外部 API 会再跑一次。这些操作要做成幂等的，或者挪到单独的节点里，让恢复时不会再次执行。

## 7. 边、循环、递归上限

普通边 `add_edge(源, 目标)`，直接指定下一个节点。

条件边是一个路由函数，看当前状态决定下一步去哪。`add_conditional_edges(源节点, 路由函数, 路径映射)`。路由函数的返回值如果是别名，映射表把它变成真实节点名；也可以直接返回节点名或 `END`。课程的例子：`value` 为偶数去 B，奇数去 C。

```python
builder.add_conditional_edges(
    "node_a",
    route_condition,
    {"node_b_alias": "node_b", "node_c_alias": "node_c"},
)
```

条件边可以指回前面的节点，图就有了环。典型的 ReAct 就是这样：模型节点和工具节点互相指，直到模型决定不再调工具。

环可能停不下来。`recursion_limit` 放在 `invoke` 的 config 里，限制的是超步数量，默认 25。超过仍没自然结束，抛 `GraphRecursionError`。这是安全阀，业务上的停止条件仍应写在路由函数里（例如计数达到 `max_count` 就返回 `END`）。限制设得很小、而循环次数设得很大时，会先撞上这个异常，而不是走完业务条件。

## 8. 运行时怎么收

图能循环、暂停和恢复，只说明机制在。面试要的是：状态里放什么、失败后续跑还是重跑、怎样真的停下来、什么任务根本不该画成图。

### 8.1 一次请求在运行时里经过哪几站

入口先鉴权。然后组装这一次的提示：系统指令、工具说明书、历史和检索结果。模型路由选定模型，解析 `tool_calls`，按权限执行，把状态和 trace 写下来，再决定继续循环、挂起等人，还是结束。对用户的出口是 SSE。短对话走同步 loop；要等外部系统很久的，改成队列里的异步任务，用同一份会话状态接上。

硬限制、检查点、取消令牌和工具的副作用标记都要在这条链上，不能只写在提示词里。人审是挂起，恢复后从挂起点继续。权威状态在服务端。前端只持有会话 id，停止按钮只停界面不算停完。

模型进出和任务循环分成两层。网关管鉴权、选模型、流式、限流、计量和缓存。Harness 管循环、工具执行、人审和恢复。只转发云厂商接口、没有计量和追踪的，仍是反向代理。自建推理还要管调度、KV Cache 和批大小。只接云 API 时，把这层讲成网关。

缓存分精确键和语义键。两边的键都带上租户、权限范围和模型。命中之后仍做 ACL。用户私有数据、价格库存、写意图默认不进缓存，或 TTL 极短。带工具的对话只缓存没有副作用的答案。错答要能按条剔除。命中率和错答率一起看。

费用在入口按模型单价预留，上游返回 usage 之后实扣，失败和取消退回预留。流式在 `done` 时结算，记下供应商请求号用来对账。并发扣减用预留、提交、回滚。按租户和项目出成本，和成功率放在同一张报表里。路由、半截 JSON 和多维限流的细节在 `agent.md` 第 10 节和第 18 节。

### 8.2 检查点、续跑和重跑

每步之后把续跑必需的状态序列化：消息、目标、还没写回的工具结果、步数、token 或费用预算、挂起点。trace 用来排障，要脱敏，不能拿它当恢复源。恢复时校验图的版本，版本不兼容就不要硬接着跑。

中断之后先看副作用有没有发生。已经写成功、并且带了幂等键，走续跑。搞不清写没写成功，先查执行凭证再决定，不要整段重跑。用户取消之后算不算失败，要产品先定义。

等人补充信息时进入 wait：检查点留着，下一轮消息或回调来了再醒，同时设 TTL 和提醒。前端展示待填的槽位。`interrupt` 所在函数恢复时会从头再执行，所以挂起前的写操作要么幂等，要么挪到单独节点。

### 8.3 死循环和取消

`recursion_limit` 只限制超步数量，默认 25，超过抛 `GraphRecursionError`。生产上的停止条件要更多：

| 条件 | 怎么判 |
|---|---|
| 步数 | 常见上限 8 到 20，按任务单独定 |
| token、费用、墙钟 | 按租户配额，超了就停 |
| 重复调用 | 同一工具加同一组参数，连续 2 到 3 次就停 |
| 无进展 | 对规范化后的工具签名、检索 query，或订单号、金额这类目标字段做指纹。连续几步没变化就判空转，然后换工具、追问或停止 |

分页翻页要用目标字段的变化来判断。页码在涨、目标没变，这是正常翻页，不能当成空转。超限之后转人工，或回一句固定话术。看板上要有强制终止率和无进展触发率。

用户点停止，或立刻再发一条，要作废当前请求代号、发起下一个。界面只采纳代号等于当前值的片段。服务端不能只靠连接断开：前面有反向代理时，断开常常到不了推理。取消令牌从入口下传到占着 GPU 的那一层，按 token 或调度步检查，命中就把请求移出批次并释放 KV Cache。沙箱里还要杀掉进程组或微虚拟机、摘掉网络。已经发生的外部写靠幂等或补偿。

### 8.4 边、并行和事务

条件边可以让模型决定下一跳，但下一跳必须落在白名单里。非法输出就重试，或进入兜底节点。边表放进配置，每种 observation 到边的映射都有单测。退款、支付这类关键边仍用确定性条件，不交给模型现编。

没有数据依赖的只读工具可以并行，有依赖的必须串行。汇合时用「全部落定」：成功的子集和失败的错误码一起交回模型，独立工具可以单独重试。每个调用有自己的超时和取消，外面再加一个总超时。关键路径可以短路。子任务各自有预算，一个烧光不能拖垮整单，回传用摘要。

模型节点不做业务提交。写库和支付放在确定性节点里，可回滚或带幂等键。模型输出先经过校验，再进入写路径。失败时的补偿要事先写明。

### 8.5 什么时候用图，什么时候拆成多个 Agent

LangChain 是模型、提示、解析器、检索器和工具的组件层，适合固定的线性 RAG。LangGraph 把同一次任务收成可持久化的状态图，才能循环、暂停和恢复。分支事先写死的流程，用配置或低代码就够。自研状态机最可控，成本也最高。Temporal 适合长事务和重试，选工具的语义仍要自己做。简单链路不必上图；上了图就要有第 8.3 节的停止条件。

任务切不开，就一个 Agent 加工具。能切开，再拆规划、执行、审核。共享状态用受限的黑板或消息，冲突用监督者或投票，汇总用摘要，不要把全轨迹塞回去。循环讨论要有轮次上限和重复论点检测。子 Agent 另加深度上限和子预算，只回摘要。超预算就收束，或升级到人。

低延迟对话用同步 loop。多段等待、长任务用事件和队列。可以同步开场、异步收尾，中间用会话状态接上。

图本身要版本化。两套编排同时在线时，按租户或用户哈希分流，看板上对比成功率、成本和延迟。放量前用影子流量比指标，保留一键回到上一版图的能力。

平台题只记到这里：工具执行前后要有拦截点（跑权限检查、跑测试）；评测要能拿到每步的 action 和 observation；Worker 按任务隔离，脏任务不要和在线对话挤在同一组进程里。这三件是运行时的钩子，不是再画一张业务图。评测怎么挡发布，见第 8.6 节。

### 8.6 评测门禁

单次模型评测看的是一段文本好不好。Agent 评测看三层：工具选得对不对、轨迹里的关键步骤在不在、任务有没有做完。业务以任务完成为准。工具选择准确率用来查描述和路由。两者冲突时先保任务完成，持续选错再改工具说明。

黄金轨迹是标好的工具序列和关键断言，带版本。产品改了就修订这条轨迹并重跑。离线评测用模拟器：订单这类对象做成有限状态，非法操作返回和线上一致的错误码。真打第三方又贵又飘。模拟器把鉴权放宽，线上才会露出越权。

提示词、模型、工具变更走同一条：版本化，评测不过不发布，灰度或影子流量对照成功率、成本和安全拒答，保留一键回到上一版。PR 跑冒烟、契约和一小套轨迹；夜间跑全量。上线前的集合至少有主路径、该拒答的边界、注入和越权、工具失败。

线上坏例子的闭环是：采样，按检索、路由、工具、生成、产品预期归类，修对应模块，看复发率。P0 进每次发布的冒烟，其余进夜间全量。每步有主人和时间。只改提示词、不改工具契约，同类坏例还会回来。

离线金标很好、换模型掉点，按这个顺序查：评测样本和线上分布是不是一批人；工具 JSON 和对话模板是否还兼容，不兼容就先降成只读或转人工；解码是否把参数截断，tokenizer 是不是这只模型自己的。先有归因，再决定要不要换回去。

人工介入率要和风险等级一起看。外发、支付、改价、删除必须确认，这一档的介入率下降要能对上策略变更。自动放行的单子按比例抽检。介入率单独下降、自动路径的错误率上升，视为指标被刷。

运行时交给评测的是每步的 action、observation、当时的提示词版本、模型版本、工具版本，以及能按同一条轨迹重放的入口。CI 用同一组钩子跑冒烟。
