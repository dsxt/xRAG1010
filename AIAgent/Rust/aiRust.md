# 0 系统全貌

## 0.1 在造什么

五层，依赖只能向下。接入层查询调度结果，不改调度器内部队列；调度层查询显存余量，不自己调 CUDA kernel。

```
客户端
  │  HTTP / SSE / gRPC
  ▼
1 接入层          鉴权、限流、协议、流式输出、取消
  ▼
2 调度核心        队列、组批、prefill/decode、抢占、公平
  ▼
3 资源层          显存池、KV 页表、权重加载
  ▼
4 沙箱层          namespace / cgroup / seccomp，或 Wasm，或 microVM
  ▼
5 推理后端        CUDA kernel / llama.cpp / vLLM 的执行引擎
```

集群在这五层之上再加：**全局调度器 → 节点 Agent → 上面这套单机运行时**。

一条请求的生命周期是后面所有埋点的骨架：

```
接入 → 鉴权/限流/token 计数 → 入队 → 准入（KV 还放得下吗）
→ 组批 → prefill（建 KV）→ decode 循环 → 采样/detokenize
→ SSE 推出 → 结束或取消 → 释放 KV
```

Rust 负责决策和隔离：网关、队列、页表元数据、沙箱、配额。矩阵乘、Attention、集合通信留在 CUDA / C++。热路径上逐个 kernel 从 Rust 发起，FFI 往返会吃掉调度收益；一个调度周期组装好整批计划，少量调用下发。

## 0.2 三条主线

后面每个设计都可以回到这三条：

1. **用户感知的是尾延迟。** TTFT（首 token 时间）和 TPOT / ITL（后续每个 token 的间隔）的 p99，比平均吞吐更接近体验。GPU 打满往往让排队时间爆炸。
2. **显存是新的内存，KV 是新的页。** 分页、共享、写时复制、换出、淘汰，就是把虚拟内存搬到 GPU 上。
3. **计算和 IO 分开线程。** tokio 跑网络和协议；组批和页表可以放专用线程；CUDA 提交放拥有 context 的线程。三套线程用 channel 交数据。

## 0.3 知识在哪一阶段用

| 虚拟内存、mmap、NUMA | 中 | 低 | 高 | 中 |

## 0.4 术语

| 词 | 含义 |
|---|---|
| Prefill | 一次前向吃完 prompt，并行建 KV。偏计算。决定 TTFT 里的计算部分 |
| Decode | 自回归，每步一个新 token，要重读权重和已有 KV。偏访存。决定 TPOT |
| KV Cache | 每层历史 token 的 K 和 V。不缓存就要每步重算历史 |
| PagedAttention | KV 按固定页分配，请求持有逻辑页到物理页的表 |
| Continuous batching | 每个 decode step 都能插入新请求、移除已完成请求 |
| TTFT | 请求到达 → 第一个 token 可见 |
| TPOT / ITL | 相邻两个输出 token 的间隔 |
| Goodput | 真正交付给用户、且落在延迟目标内的 token 速率。取消之后还在生成的 token、推测解码被拒绝的 token，不算 |
| SLO | 对 TTFT / TPOT / 错误率的目标，例如「TTFT p99 ≤ 500 ms」 |

# 1 操作系统

这一章恢复大学里的进程、内存、调度和 IO，并接到推理服务上。不讲文件系统实现、不讲所有调度算法的历史。

## 1.1 进程、线程、协程（L1）

**进程**是资源容器：独立地址空间、打开的文件、用户身份。进程切换要换页表，TLB 大量失效。

**线程**是调度单位，同一进程内的线程共享地址空间。切换要保存寄存器并陷入内核，量级大约 1–10 μs，真正贵的是回来之后 cache 是冷的。

**协程**（tokio 里的 task）由用户态运行时调度。挂起只保存少量寄存器和状态机位置，大约几十到几百纳秒。协程不是线程：`async fn` 返回一个 `Future`，`.await` 挂起时不占用内核线程，除非你在里面做了阻塞调用。

三种映射：

| 模型 | 谁调度 | 阻塞时 |
|---|---|---|
| 1:1 内核线程 | 内核 | 只堵住这个线程 |
| N:1 用户线程 | 用户态 | 一次阻塞，整组都停。已淘汰 |
| M:N | 运行时把 M 个协程放到 N 个内核线程上 | tokio 的模型。协程里若直接阻塞，会堵住当前 worker 上的所有协程 |

推理网关同时握着成千上万条 SSE 长连接。一条连接一个线程，文件描述符和栈内存先爆。正确的承载是协程。GPU 上的计算则用少量专用内核线程，见 [5.3](#s5-3)。

## 1.2 用户态、内核态、系统调用（L1）

CPU 有特权级。用户态不能碰设备、不能任意改页表。系统调用是主动陷入内核的入口，一次大约几百纳秒，还不算后面真正的工作。

缺页、中断、异常也会陷入内核。高并发下「每个 IO 一次陷入」会成为固定税，所以才有批量提交（io_uring）和「一次组批、一次下发 GPU」。

## 1.3 五种 IO 模型（L1）

大学课的五级，用在这里的结论很短：

| 模型 | 行为 | 在本系统中 |
|---|---|---|
| 阻塞 | 线程睡到数据到 | 只用于专用线程上的 CUDA 等待、少量管理操作 |
| 非阻塞 + 轮询 | 反复看到 `EAGAIN` | 空转烧 CPU，不用 |
| IO 多路复用 | `select` / `poll` / `epoll` / `kqueue`：一个线程等很多 fd 就绪 | **网关网络面的默认** |
| 信号驱动 | `SIGIO` | 生产不用 |
| 异步 IO | 提交后内核做完再通知。Linux 上可用的形态是 **io_uring** | **存储面**：权重预读、日志、KV 落盘 |

`select` / `poll` 每次要把整个 fd 集合拷进内核，关注的 fd 越多越慢。`epoll` 把注册和等待拆开：fd 存在内核红黑树里，就绪的放进一条链表，`epoll_wait` 只返回已就绪的。这是 C10K 之后 Linux 网关的基础。

普通文件的 fd 在 epoll 看来永远就绪，随后的 `read` 仍可能堵在页缓存锁或磁盘队列上。所以 **tokio 的文件 IO 不走 epoll**，而是丢进阻塞线程池（默认上限大约 512）。权重加载、KV 换出到磁盘，不能把这个池当主力。

## 1.4 epoll：水平触发与边缘触发（L1）

- **LT（水平）**：缓冲区里还有数据，就会再次通知。编程简单，可能多余唤醒。
- **ET（边缘）**：只在状态变化时通知一次。必须把 fd 设成非阻塞，循环读到 `EAGAIN`。漏读一次，这个 fd 就再也不会被通知。

mio / tokio 对 socket 使用边缘触发。所以异步读的契约是：这次唤醒要把当前可读数据取完。

相关套接字选项：

- `EPOLLONESHOT`：一次事件处理完再重新注册，避免多线程同时读同一个 fd。
- `SO_REUSEPORT`：多个线程或进程监听同一端口，内核按连接分配。多 worker 网关的监听端用它，避免一把 accept 锁。

epoll 只告诉你「可以读了」。数据仍要通过 `read` / `write` 系统调用进出。把这一步也异步化，才是 io_uring。

## 1.5 io_uring 用在哪里（L2）

Linux 5.1 之后，用户态和内核共享两个环：

- **SQ（提交队列）**：应用写入 IO 请求。
- **CQ（完成队列）**：内核写入结果。

环本身是 `mmap` 出来的共享内存。批量提交时用 `io_uring_enter` 进入内核一次（SQPOLL 模式下连这次都可以省掉）。这和更早的 Linux AIO（`io_submit` / `io_getevents`）不是同一套接口。

有用的能力：预注册文件描述符、预注册缓冲区（避免每次 pin 内存）、请求链接、`IORING_OP_SEND_ZC` 这类零拷贝发送。`IORING_SETUP_SQPOLL` 让内核线程忙等 SQ，延迟更低，但这个内核线程会占核。已经用 `isolcpus` 划给推理的核上，不要再跑 SQPOLL。

**分工：**

| 路径 | 选择 | 原因 |
|---|---|---|
| 网关长连接、SSE | epoll / tokio | 每条连接有自己的状态机，要低延迟单次唤醒。io_uring 倾向批量收割，SQPOLL 还抢核 |
| 权重异步加载、tracing 落盘、KV 换出到盘 | io_uring 或专用加载线程 | 普通文件 IO 会堵，tokio 阻塞池会先耗尽 |

两边用 channel 对接，不必把整个运行时换成一种 IO 模型。Rust 侧存储可选 `tokio-uring` 或 thread-per-core 的 `monoio`。沙箱里默认不要放行 io_uring：它和内核共享内存，历史上扩大过攻击面，见 [6.3](#s6-3)。

## 1.6 虚拟内存、页表、缺页（L1）

进程看到的是虚拟地址。MMU 经页表翻译成物理页。页表缓存叫 **TLB**。默认页 4 KiB，几十 GB 的权重会让 TLB 覆盖范围不够，miss 后要走内存里的多级页表。

**缺页**分两种：

- **minor fault**：页已在页缓存或只是还没建页表项，不读盘。
- **major fault**：要从磁盘读。慢，而且会卡住当时的线程。`/proc/vmstat` 的 `pgmajfault`、`perf stat -e page-faults` 用来确认。

**mmap** 把文件映射进地址空间，访问到某一页才装入（demand paging）。模型权重用它，是因为：

- 映射建立很快，不必启动时把文件全部拷进用户缓冲。
- 多个进程映射同一份只读文件时，物理页在页缓存里只有一份。
- 少一次「页缓存 → 用户缓冲」的拷贝。

第一次真正碰到的页如果还不在页缓存，就是 major fault，首个请求的 TTFT 会差几个数量级。加载之后要预热：顺序扫一遍，或 `madvise(MADV_WILLNEED)`，或 `mmap` 时带 `MAP_POPULATE`。节点启动时做，不要等第一个用户。

`madvise(MADV_DONTNEED)` / `posix_fadvise(POSIX_FADV_DONTNEED)` 用来丢掉不再需要的缓存，避免旧 checkpoint 占着页缓存。

## 1.7 大页、锁定、换页、OOM（L2）

**大页**（2 MiB、1 GiB）让一条 TLB 覆盖更多地址。两条路：

- **透明大页 THP**：内核自动合并。对大数组有利，但后台 `khugepaged` 和同步压缩会制造毫秒级停顿。推理机器设成 `madvise`，不要 `always`。
- **显式大页 hugetlbfs**：启动时预留，`mmap` 带 `MAP_HUGETLB`。KV 换出区和权重用这条，停顿可预期。

**mlock** 把页钉在物理内存里，禁止换出。权重和热 KV 需要它。代价是占物理内存，而且锁定额度受 `RLIMIT_MEMLOCK` 和 `CAP_IPC_LOCK` 限制。沙箱里必须把这个额度算进配额，否则租户可以把物理内存锁满。

**swap**：推理机通常关掉。权重或 KV 被换到磁盘，延迟从微秒变成毫秒以上。cgroup 内存超限时的回收行为仍要懂：回收本身抢 CPU 和 IO，空闲内存贴着水位线时 p99 会毛。

**OOM Killer** 在全局内存耗尽时按 `oom_score` 选进程杀掉。cgroup v2 下更常用的是组内上限：`memory.max` 触顶会杀组内进程；`memory.oom.group` 可以整组一起杀，避免沙箱里只死一个子进程。监听 `memory.events` 的 `oom` / `oom_kill` 计数，在被杀之前做清理。

`memory.high` 是软上限：超过后该组被强制回收并限速，进程还活着，但会变慢。`memory.max` 是硬上限。沙箱用 high 做预警、max 做最后一刀。

## 1.8 CPU 调度：公平和低延迟是两件事（L1）

Linux 默认 **CFS**。它用 `vruntime`（加权后的虚拟运行时间）选最小的任务来跑，目标是公平分时间，不是让某一个线程的唤醒延迟最小。

空载时唤醒大约微秒级。推理进程和编译、日志、网卡软中断挤在同一组核上时，runqueue 等待可以到毫秒甚至十几毫秒。一次十几毫秒的抢占直接写进 TTFT 或 TPOT。CFS 还可能为了负载均衡把线程迁到另一个 NUMA 节点，见 [1.13](#s1-13)。

把推理核从这种公平里摘出来，按这个顺序做：

1. **`isolcpus` + `nohz_full` + `rcu_nocbs`**：这些核不再参与普通 CFS 负载均衡，减少时钟中断和 RCU 回调。
2. **中断亲和性**：`/proc/irq/*/smp_affinity` 把网卡、NVMe、GPU 的中断放到非推理核。停掉对这些核的 `irqbalance`。
3. **绑核**：`sched_setaffinity` 或 cgroup `cpuset`。tokio worker、GPU 提交线程、权重所在内存，绑到 GPU 对应的 NUMA 节点。
4. **`SCHED_FIFO`（可选）**：实时优先级。线程一旦忙等就会永远占核，必须有看门狗。推理服务多数情况用隔离核就够，不必上完整的 `PREEMPT_RT`。`PREEMPT_RT` 把更多内核临界区变成可睡眠锁，最坏延迟下降，吞吐也下降，它服务的是硬实时控制，不是 LLM 的默认选择。

cgroup 的 `cpu.weight` 只是组间份额，组内仍然是 CFS。满载时推理进程照样被节流。硬隔离用 `cpuset` 划核，再用 `cpu.max` 限制带宽。

`cpu.max` 写成 `配额 周期`，单位微秒。`200000 100000` 表示每 100 ms 最多跑 200 ms，也就是 2 个核的算力。`cpu.stat` 里的 `nr_throttled` 和 `throttled_usec` 上升，说明配额在切你的时间片，p99 会跟着抖。

## 1.9 cgroup v2（L1）

v1 是每类资源一棵树，控制器互相打架。v2 是一棵统一树，一个进程只在一个节点。新沙箱用 v2。

进程要能在子节点里启用控制器，父节点得先把控制器写进 `cgroup.subtree_control`。自己节点上有进程时，不能再把控制器下放（no internal process），所以中间节点只做结构，叶子节点放进程。

| 文件 | 作用 |
|---|---|
| `cpu.max` / `cpu.weight` | 带宽上限 / 相对权重 |
| `cpuset.cpus` / `cpuset.mems` | 允许的 CPU 和 NUMA 节点 |
| `memory.max` / `memory.high` / `memory.low` | 硬顶 / 软顶 / 保护线 |
| `memory.peak` / `memory.events` | 峰值；low/high/max/oom/oom_kill 计数 |
| `memory.swap.max` | swap 上限。推理沙箱通常写成 0 |
| `io.max` | 某块设备的带宽和 IOPS |
| `pids.max` | 进程数。防 fork 炸弹，沙箱必设 |
| `cgroup.freeze` | 整组冻结 |
| `cgroup.kill` | 整组杀掉 |

**cgroup 不管理 GPU 显存。** 显存隔离见 [6.4](#s6-4)。

## 1.10 Namespace（L1）

Namespace 改变的是「进程能看见什么」，不改变机器上真实有多少资源。资源多少由 cgroup 管。

| Namespace | 隔离什么 | 沙箱里为什么要 |
|---|---|---|
| user | uid/gid 映射 | 非 root 也能在沙箱里当 root，映射回宿主机上的普通用户。现代轻量沙箱的起点 |
| pid | 进程号 | 沙箱里的 PID 1 负责收割子进程；看不到宿主机进程表 |
| mount | 挂载点 | 自己的 rootfs，不看见宿主机目录 |
| net | 网络栈 | 没有默认路由，或只有允许的 veth |
| uts | 主机名 | 次要 |
| ipc | System V / POSIX 共享内存 | 堵住跨沙箱 IPC |
| cgroup | cgroup 根在哪 | 防止沙箱里再逃出自己的资源限制 |
| time | 时钟偏移 | 一般推理用不上；要骗程序的时间才用 |

`/proc` 和 `/sys` 如果 bind 的是宿主机的，沙箱里就能读进程列表、甚至写内核参数。要在新的 pid namespace 里重新挂一份精简的 procfs。

user namespace 的映射：先写 `/proc/self/setgroups` 为 `deny`，再写 `uid_map` / `gid_map`。顺序反了会失败。

## 1.11 seccomp、capabilities、Landlock（L1）

root 的能力在 Linux 里被拆成 capabilities。`CAP_SYS_ADMIN` 几乎等于 root（能挂载、能摆弄 namespace）。沙箱的 capability 集清到最小，需要的再加回来。`CAP_SYS_PTRACE` 去掉，避免调试接口被拿来改内存。

**seccomp-bpf** 在系统调用入口跑一段 BPF，可以看调用号，也可以看参数。典型动作：

- `SECCOMP_RET_ALLOW`：放行
- `SECCOMP_RET_ERRNO`：返回 `EPERM` 等错误，进程还活着。白名单策略用这个，误杀时好排查
- `SECCOMP_RET_KILL_PROCESS`：直接杀
- `SECCOMP_RET_USER_NOTIF`：挂起调用，交给用户态监督进程决定。可以用来代理个别 ioctl。CUDA 的 ioctl 又多又必须，靠 seccomp 逐个审查不现实，GPU 的硬边界在 MIG，不在 BPF

启用过滤器之前必须 `PR_SET_NO_NEW_PRIVS`，否则非特权进程不能安装过滤器，也防止过滤之后通过 setuid 重新拿权。默认拒绝，再开白名单。危险且容易漏的包括 `ptrace`、`bpf`、`userfaultfd`、`keyctl`、`perf_event_open`。

**Landlock**（Linux 5.13+）让进程自己声明只能访问哪些路径，不需要写一套系统级 SELinux 策略。它适合「只能读 `/models/某模型` 和自己的临时目录」。

Landlock 和 seccomp 一旦装上就不能撤销。构建顺序：

```
先把配置校验完
→ namespace（之后仍可用 setns 调整）
→ cgroup（可改）
→ Landlock（不可逆，文件系统边界）
→ seccomp（不可逆，系统调用边界，放最后）
→ exec 目标程序
```

seccomp 之后还要做的初始化，会因为缺系统调用而失败。

DAC 是传统的 rwx。MAC（AppArmor、SELinux）是强制策略，root 也绕不过。自研轻量沙箱先把 namespace + cgroup + Landlock + seccomp 做对；MAC 是宿主机上的第二层，不是第一版的阻塞项。

## 1.12 进程的生和死（L1）

- **僵尸**：子进程已退出，父进程还没 `wait`。进程表项还在。沙箱父进程要收 `SIGCHLD`，或用 pidfd。
- **孤儿**：父进程先死，子进程被 init 或 subreaper 收养。沙箱最怕这个：管理进程崩溃后，推理子进程继续占着 GPU。
- **`PR_SET_PDEATHSIG`**：父进程死时，内核给子进程发指定信号（沙箱里用 `SIGKILL`）。要在父进程还活着时设置，并处理「设置之前父进程已经死了」的竞态（设置后再检查 `getppid`）。
- **进程组**：`setpgid` 之后 `kill(-pgid, SIGKILL)` 能整组杀。只杀直接子进程会留下孙进程。
- **pidfd**（Linux 5.3+）：用文件描述符指一个进程，避免 PID 被复用后杀错人。
- **subreaper**：沙箱里再 fork 的树，由沙箱 PID 1 收割，而不是漏给宿主机 init。

信号：`SIGTERM` 可捕获，用来优雅退出；`SIGKILL` 不可捕获，用来超时强杀；`SIGPIPE` 在对端关闭后写 socket 时出现，网关要处理，避免进程因此退出。

<a id="s1-13"></a>

## 1.13 NUMA（L2）

多路服务器上，每个 CPU 插座有自己的内存控制器。访问本地内存大约 80 ns，跨插座大约 150–220 ns，带宽往往差一倍以上。差的不是常数，decode 和权重预取是带宽活，跨节点流量会把互联总线打满。

两条规则：

1. **执行线程、它分配的内存、它使用的 GPU，在同一个 NUMA 节点。** GPU 插在哪棵 PCIe 树上，用 `lscpu` 和 `/sys/devices/system/node/` 对出来。
2. **绑核不等于绑内存。** 物理页落在哪个节点，由第一次写入该页的 CPU 决定（first touch）。先 `sched_setaffinity`，再分配大块内存；或者显式 `mbind` / `numa_alloc_onnode`。`numactl --cpunodebind=N --membind=N` 是进程级的做法。

`numa_balancing` 会让内核自动迁移页，推理机器关掉，自己管。cgroup 的 `memory.numa_stat` 用来核对一个沙箱的页到底在哪个节点。

权重如果被所有插座均匀读，偶尔会用 `interleave`。推理线程的 KV 和任务结构不要 interleave。

<a id="2-计算机网络"></a>

# 2 计算机网络

推理服务是长连接流式服务。这一章只讲会写进 TTFT / TPOT 的机制，不讲路由协议和全部 TCP 状态机。

## 2.1 TCP 里真正要记住的（L1）

三次握手之后，数据才走得通。服务端有两个队列：半连接（SYN 已到、还没 accept）和已完成连接（accept 队列）。突发连接时它们会溢，`netstat -s` 里能看到。`somaxconn` 和 listen backlog 要按连接速率设，不是按一个魔法数。

**滑动窗口**是对方还能收多少。**拥塞窗口**是发送方自己估计的网络容量。有效发送量取两者较小者。

- **CUBIC** 是 Linux 常见默认，靠丢包判断拥塞。缓冲区很大时，它会把缓冲填满再丢包，延迟上去（bufferbloat）。
- **BBR** 用带宽和 RTT 的模型，不等丢包。跨机房拉权重、公网接入，值得试。RoCE 不用这两套，见 [10.3](#s10-3)。

**TIME_WAIT** 在主动关闭方停留大约 2MSL（常见 60 秒），占用本地端口。短连接网关会把端口打光。推理网关用长连接、连接池、HTTP/2 多路复用。`tcp_tw_reuse` 只影响本机作为客户端的出站连接。`tcp_tw_recycle` 已删除，不要写进配置。

**Keepalive** 用来发现中间设备已经悄悄拆掉的空闲连接。应用层心跳（SSE 注释行）比只靠 TCP keepalive 更可控，两层都开。

<a id="s2-2"></a>

## 2.2 Nagle、延迟确认、SSE（L1）

Nagle 算法把小包攒一攒再发，减少报头开销。SSE 每个 token 就是一个小包。攒包的时间直接加进 TPOT。流式连接设置 `TCP_NODELAY`，关掉 Nagle。

路径上任何一层缓冲都会造成同样的问题：反向代理的 `proxy_buffering`、语言运行时的块缓冲、没刷新的 `BufWriter`。SSE 要求：

- `Content-Type: text/event-stream`
- 响应头里禁止中间层缓冲（如 `X-Accel-Buffering: no`）
- 每条事件写完就 flush
- 周期性注释行，避免中间设备按空闲超时掐连接

客户端读得慢时，TCP 发送窗口和用户态缓冲会满。这是反压的起点，必须一路传到 decode 循环，见 [8.6](#s8-6)。只在网关把 token 堆进内存，GPU 会继续为已经没人看的请求生成。

**取消**是同一条链的另一半：HTTP 断开 → tokio 任务结束 → 调度器的取消集合里出现这个请求 id → 下一步组批不再包含它 → KV 页归还。生成循环每个 step 都要看这个集合。

## 2.3 零拷贝，以及 GPU 真正在乎的拷贝（L2）

磁盘到网卡的经典路径是：磁盘 DMA 到页缓存，CPU 拷到用户缓冲，CPU 再拷到 socket 缓冲，网卡 DMA 走。零拷贝去掉中间的 CPU 拷贝：

| 接口 | 做什么 |
|---|---|
| `sendfile` | 内核里从文件 fd 到 socket |
| `splice` | 两个 fd 之间经管道移动页 |
| `mmap` + `write` | 少一次从页缓存到用户缓冲的拷贝，写 socket 时通常还要拷一次 |
| `MSG_ZEROCOPY` | 发送时页先被网卡引用，完成后再通知可复用 |
| io_uring 的 send_zc | 同上，走 uring |

这些对「把已有文件转发出去」有效。LLM 的响应是 GPU 现算出来、CPU 再编成 SSE 文本的，零拷贝窗口很窄。

GPU 路径上真正贵的是另一件事：可分页的主机内存做 `cudaMemcpy` 时，驱动会先拷到一块临时的锁页缓冲，再 DMA。**锁页内存（pinned memory，`cudaHostAlloc` / `cudaHostRegister`）** 允许设备直接 DMA。权重预热、KV 换出、输入输出张量，走锁页池。这是 FFI 层的默认，不是微优化。

<a id="s2-4"></a>

## 2.4 限流、熔断、负载均衡（L1）

| 算法 | 行为 | 用在哪 |
|---|---|---|
| 固定窗口计数 | 窗口边界会有两倍突发 | 粗配额 |
| 滑动窗口 | 平滑些，要存时间桶 | 租户 QPS |
| 令牌桶 | 平均速率固定，允许一定突发 | 网关入口 |
| 漏桶 | 输出速率恒定 | 需要严格整形时 |

过载时**拒绝**（429，带上重试等待时间），而不是无界排队。队列变长，每个请求的等待都变长，然后客户端超时重试，负载再翻倍。这就是雪崩。

熔断器三态：关闭（正常放行）→ 打开（直接失败）→ 半开（放少量探测）。下游节点 p99 或错误率越线就打开。内容安全类的 4xx 不要当成「换一个模型再试一次」，那会绕过安全策略。

负载均衡：

- 四层看连接，七层看模型和请求。
- 轮询会把共享同一前缀的请求打散，前缀缓存命中率掉下去。
- 推理用**两段路由**：先按负载（队列深度、剩余 KV 页、p99）选出候选，再在候选里偏好前缀能命中的节点。只按前缀会把热点打在一台机器上。

重试：指数退避加抖动。固定间隔会让所有客户端同一毫秒回来。重试的前提是幂等键，见 [10.2](#s10-2)。

## 2.5 应用协议（L2）

对外保持 OpenAI 兼容的 HTTP API，调用方不用改。对内节点之间用 gRPC（Rust 侧 tonic）：HTTP/2 多路复用、流式、明确的超时。

序列化：

- 控制面 Protobuf 足够。
- 高频小消息若 profiler 显示序列化占比高，再看 FlatBuffers / Cap'n Proto（解码不先拷成一棵对象树）。
- KV 页的正文不要序列化成 Protobuf。那是一大块字节，走 RDMA 或共享内存，旁边只带页 id 和长度。

QUIC / HTTP3 对公网接入有 0-RTT 和没有 TCP 队头阻塞的好处。集群内部短 RTT 网络上，先把 gRPC 和 RDMA 做对。

## 2.6 TLS（L2）

握手有计算和一次额外往返。公网用会话复用。集群内部 mTLS：调度器和 Agent、节点之间的 KV 控制通道都要双向证书。租户凭证只授权它自己的模型和配额。

证书轮转要能在不重启推理线程的情况下换掉配置。读多写少的配置用 `arc-swap` 这一类结构，见 [4.3](#s4-3)。

<a id="3-组成原理与-gpu"></a>

# 3 组成原理与 GPU

## 3.1 延迟数量级（L1）

先有比例尺，再谈优化。数量级比精确值重要，不同代际会变，但台阶不变。

| 位置 | 大约 |
|---|---|
| L1 命中 | ~1 ns |
| L2 | 数 ns |
| L3 | ~10–40 ns |
| 本地内存 | ~80 ns |
| 跨 NUMA 内存 | ~150–220 ns |
| 同机 NVMe 随机读 | 数十 μs 起 |
| H100 HBM 读满带宽时，140 GB 权重量级 | ~40 ms |
| 同机房 RDMA | 数 μs 起 |
| 跨机房 TCP RTT | 毫秒到几十毫秒 |

一个错误的优化是去抠 100 ns 的锁，同时允许 10 ms 的调度抢占或 40 ms 的额外排队。

## 3.2 缓存行、伪共享、MESI（L1）

CPU 以 **缓存行** 为单位搬内存，常见 64 字节。两个核各自更新两个逻辑上无关的变量，只要这两个变量落在同一行，就会互相失效。这叫**伪共享**。调度器里典型的样子：一个结构体里紧挨着 `enqueue_time`、`state`、`assigned_worker` 三个 `AtomicU64`，不同核写不同字段。

MESI 是缓存一致性的四态：修改、独占、共享、无效。写一条别的核还持有的行，要把对方的行废掉再独占。伪共享的代价就是这条线在核之间来回作废。

查：`perf c2c`。改：按**写入者**拆开字段，中间垫到不同的缓存行（`#[repr(align(64))]` 或 `crossbeam` 的 `CachePadded`）。把整个结构体对齐到 64 字节并不够，相邻字段仍会在同一行。

数据布局：同一线程顺序扫的字段放一起（SoA 或按热度分组）。为了「看起来整齐」把冷热字段交错，预取会把用不到的字节一起拖进缓存。

## 3.3 内存序（L2）

编译器和 CPU 都可以重排读写。原子变量的内存序就是在约定哪些重排被禁止。

| 序 | 保证 | 用在哪 |
|---|---|---|
| `Relaxed` | 只有原子性 | 统计计数。只关心最终加总 |
| `Release` 写 | 这次写之前的写，对后来的 Acquire 读可见 | 发布「数据已经准备好」 |
| `Acquire` 读 | 读到之后的读写，不会跑到这次读前面 | 看到标志后再读数据 |
| `AcqRel` | 一次读改写上两者都有 | CAS |
| `SeqCst` | 所有 SeqCst 操作有一个全局顺序 | 拿不准、且不在热路径上的时候 |

发布页表的正确配对是：把页表内容写完，再 `Release` 存储一个状态；消费者 `Acquire` 读到状态，再读页表。`SeqCst` 在 x86 上因为 TSO 往往和 Acquire/Release 代价接近，在 ARM 服务器（Grace、Ampere）上会多出屏障。热路径不要用 SeqCst 求安心。

## 3.4 SIMD 用在哪（L2）

AVX2 / AVX-512 用在 CPU 上的 tokenize 后处理、小规模量化反量化、采样前的掩码。矩阵乘在 GPU 上。Rust 用 `std::arch`，并用 `is_x86_feature_detected!` 做运行时分发，避免二进制在旧 CPU 上非法指令。

## 3.5 GPU 上程序怎么跑（L1）

一块 GPU 有很多 **SM**。调度单位是 **warp**，NVIDIA 上 32 个线程锁步执行。warp 里的线程走到不同分支，硬件会把两条路串行做，这是 **warp divergence**。自己写 kernel 时避免按数据值分叉；用现成的 Attention 实现时，知道这件事即可，不必先写 kernel。

内存从快到慢：寄存器 → shared memory（SM 内）→ L2 → **HBM 显存** → 经 PCIe 或 NVLink 到别的设备。

带宽的台阶（规格峰值，实际 kernel 会打折）：

| 路径 | 大约 |
|---|---|
| H100 SXM HBM3 | 3.35 TB/s |
| H200 HBM3e | 约 4.8 TB/s |
| A100 80GB HBM2e | 约 2 TB/s |
| PCIe 4.0 x16 | 单向约 32 GB/s |
| NVLink（代际不同） | 数百 GB/s 量级，远高于 PCIe |

H100 是 HBM3。HBM3e 是 H200 这一代。算账时不要混用。

**Decode 慢，是因为每生成一个 token 都要把权重从 HBM 读出来，算力吃不满。** batch 把这一次读取摊给多个请求。这是第 7 章算账的硬件原因。

<a id="s3-6"></a>

## 3.6 CUDA 执行：stream、event、graph、分配（L2）

**Stream** 里的操作按提交顺序执行。不同 stream 可以并行。KV 换出和计算重叠、预取下一块权重，靠多 stream 加 event 同步，而不是 CPU 上睡一觉。

**Event** 记录 stream 上的一个点。`cudaStreamWaitEvent` 让另一条 stream 等它；主机侧 `cudaEventQuery` 用来不阻塞地问完成了没有。完成通知回到调度线程，不要在 tokio worker 里 `cudaEventSynchronize`。

**Kernel 启动**本身有固定开销。Decode 每步有很多小 kernel 时，启动开销会占掉 TPOT 的一块。**CUDA Graph** 把一串已经定下来的启动录成一张图，之后整图重放。限制是：录制时形状要固定。实践里按 batch 大小分桶，每桶一张图。图捕获之后再改指针和形状，是一类难查的错误。

**分配：**

- `cudaMalloc` / `cudaFree` 会同步整个设备，热路径上一次几十到几百微秒，还会把显存切碎。
- `cudaMallocAsync`（CUDA 11.2+）按 stream 排序，命中池时只是几微秒。跨 stream 复用要等 event。
- 自研页分配器建立在池之上：按页大小分若干子池，而不是回到裸的 `cudaMalloc`。
- `cudaMemPoolTrimTo` 放在低峰，把池里多余的空闲还回去，避免进程占着已释放的显存。

**Context** 绑在线程上。一个 GPU 一个提交线程（或明确用 primary context 并规定谁 `cuCtxSetCurrent`）。MIG 实例之间的 context 不能混用。

**fork 与 CUDA 不能并存。** 已经初始化 CUDA 的进程再 fork，子进程里的 context 是坏的。GPU 工作放独立进程，用 `clone` 进新 namespace，而不是在持有 context 的进程里 fork 任务。

<a id="s3-7"></a>

## 3.7 Roofline：先判断算力还是带宽（L2）

算术强度 = 做了多少 FLOPs / 搬了多少字节。

屋顶的两条边：

- 斜边：性能 = 带宽 × 算术强度（搬得不够快）
- 平边：性能 = 峰值算力（算得不够快）

拐点 = 峰值算力 / 峰值带宽。H100 的 FP16 Tensor Core 峰值大约 10^15 FLOP/s 量级，带宽 3.35 TB/s，拐点在几百 FLOP/字节。

Decode 每 token 的线性层大约做 `2 × 参数量` 次浮点运算，同时至少读一遍权重。FP16 下算术强度大约 `2 / 2 字节 = 1` FLOP/字节，远在拐点左边，所以是**带宽瓶颈**。把 SM 占用率优化到更高，吞吐不会按比例涨。

Prefill 一次处理很多 token，大矩阵乘的算术强度高，落在算力一边。超长序列的 Attention 若物化完整的 `n×n` 矩阵，显存先爆；FlashAttention 分块计算、不落下整块矩阵，把 Attention 变成 IO 友好的算法。

优化方向由此决定：decode 去减读取的字节（量化、GQA、更大的有效 batch），prefill 去提高算力利用（融合、FlashAttention、不要被一个超长 prompt 独占太久）。

**MFU**（模型 FLOPs 利用率）= 实际每秒 FLOPs / 峰值 FLOPs。Decode 的 MFU 天然低，因为它在等带宽。用 MFU 评价 decode 服务会得出「GPU 很闲，再塞点别的任务」的错误结论。Decode 看 HBM 带宽利用率和 goodput。

## 3.8 数值格式（L2）

| 格式 | 构成 | 特点 |
|---|---|---|
| FP32 | 1+8+23 | 范围和精度都宽，推理权重很少全用它 |
| FP16 | 1+5+10 | 范围大约到 6 万，容易溢出 |
| BF16 | 1+8+7 | 范围接近 FP32，精度低。训练和不少推理的默认 |
| FP8 | E4M3 / E5M2 | H100 有硬件通路。E4M3 偏精度，E5M2 偏范围 |
| INT8 / INT4 | 整数 + 缩放因子 | 权重量化的主流落点 |

量化误差来自舍入，也来自激活里的离群值。所以不是均匀地砍比特就行：GPTQ 用二阶信息逐层量化，AWQ 保护对激活影响大的通道，SmoothQuant 把激活的难度转移到权重上以便 W8A8。这些方法的校准数据和缩放因子是模型的一部分，加载器和校验和都要覆盖它们。

KV Cache 也可以用 FP8 存。显存大约减半，从而并发大约翻倍，代价是长上下文的数值误差。要单独做效果回归，不要只看显存。

<a id="4-数据结构与并发"></a>

# 4 数据结构与并发

## 4.1 队列（L1）

| 结构 | 适用 | 不适用 |
|---|---|---|
| 有界 MPSC / MPMC | 请求从多个 IO 线程进入一个调度线程 | 无界版本。过载时内存先被队列吃掉 |
| 优先级堆 | 租户等级、截止时间 | 不处理饥饿就会让低优先级永远不出队。要老化 |
| 按长度分桶的队列 | 避免一个超长 prompt 堵住短请求 | 桶太多会让每桶凑不齐 batch |
| SPSC 环形缓冲 | 单生产者单消费者的指标、batch 缓冲 | 多生产者。别硬改成 MPMC |
| 时间轮 | 大量超时 | 需要按优先级精确排序的场景。那是堆 |

调度队列的实用形态是**分片**：按模型或按 GPU 把队列拆开，每片一把锁或一个消费者。它躲开全局锁，也不必先写对一个无锁队列。

## 4.2 无锁的边界（L2）

CAS 是无锁结构的基本操作：只有内存里的值仍等于期望值才写入。ABA 是指值从 A 变成 B 又变回 A，CAS 以为没人动过。带版本号的指针，或索引加世代，用来打破 ABA。

更难的是**回收**。别的线程可能还拿着即将被释放的节点。做法包括 epoch（`crossbeam-epoch`）、hazard pointer、RCU 风格的宽限期。Michael & Scott 队列是教科书上的 MPMC，把回收做对之前不要自己换上它。

低竞争时 `parking_lot::Mutex` 往往又快又好读。无锁在高竞争下减少睡眠，同时增加缓存行乒乓。先测量再换。推理调度的竞争热点用分片解决，比用无锁解决更常见。

<a id="s4-3"></a>

## 4.3 锁怎么选（L1）

| 场景 | 选择 |
|---|---|
| 同步代码里的短临界区 | `parking_lot::Mutex`。比标准库小，快路径不进内核，没有中毒状态 |
| 临界区跨过 `.await` | `tokio::sync::Mutex`。标准库锁跨 await 会把 worker 堵住 |
| 读多写少的配置 | `arc_swap`：读者无锁拿一个 `Arc`，写者换整份快照 |
| 一次性回传结果 | `oneshot` |
| 调度线程之间的高吞吐管道 | `crossbeam-channel`，有界 |
| IO 任务之间 | `tokio::sync::mpsc`，有界 |

锁的顺序全进程统一，避免 AB-BA 死锁。锁内不做 IO、不做 FFI、不做内存分配。异步锁不要去包一层同步锁再反过来等。

## 4.4 内存池（L1）

全局分配器在高并发小对象上会有锁和碎片。网关每请求要解析 JSON、切 token、写 SSE。生产把全局分配器换成 mimalloc 或 jemalloc，热路径再用对象池和 `bytes::Bytes` 复用缓冲。

主机侧 pinned 内存单独成池。显存侧用 [3.6](#s3-6) 的池。请求生命周期内的临时对象可以用 arena，请求结束整块丢掉。

## 4.5 这一章和调度器的对应

第 8 章的调度器直接使用这里的选择：有界分片队列、优先级加老化、令牌桶在接入层、页分配器在资源层。不要在调度器那一章再换一套结构。

## 4.6 本章自检

- 说明有界 channel 怎样把反压变成阻塞或拒绝，而无界 channel 怎样变成 OOM。
- 说出 ABA 和「节点何时能释放」是两个问题。
- 判断一个锁会不会跨 await，并选出对应类型。

# 5 Rust 工程

假定所有权、借用、生命周期已经会用。这里只讲把第 1–4 章落成进程的部分。

## 5.1 Future、Waker、Pin（L2）

`Future::poll` 要么返回就绪，要么返回挂起。挂起时运行时留下 `Waker`。IO 完成、定时器到期或 channel 有数据时，waker 把这个任务放回运行队列。

`async fn` 被编译成状态机。状态机里可能有指向自己字段的引用，所以 Future 被移动就会悬空。`Pin` 保证它不再被移动。用 `.await` 时编译器处理 Pin；手写 `Future` 或自引用结构时用 `pin-project`。

持有 CUDA 句柄、fd、KV 页的类型要有 `Drop`。取消任务时 Drop 必须归还这些资源。这就是取消安全：`await` 点被取消后，不能只归还了一半。

## 5.2 tokio 能做什么、不能做什么（L1）

多线程运行时是 work-stealing：每个 worker 一条本地队列，空了去偷别人的。默认 worker 数等于核数。它还有协作式预算，长时间不让出的任务会被强行让出，避免一个任务饿死同线程的其他任务。

阻塞调用放在 worker 上时，这个 worker 不能再 poll 任何任务。文件 IO、CPU 密集的 JSON，用 `spawn_blocking`（独立的阻塞池）。`block_in_place` 会把当前 worker 交出去并迁移任务，只在多线程运行时可用，不适合「每个请求都阻塞一下」的设计。

**GPU 提交不进 `spawn_blocking`。** 阻塞池有上限、没有绑核、也不拥有稳定的 CUDA context。GPU 用自己的 `std::thread`。

`tokio::spawn` 的任务如果 panic，错误留在 `JoinHandle` 里。不 await 这个 handle，请求就静默消失。统一用 `JoinSet` 或包装函数记录 panic，并安装 panic hook 打点。

`select!` 在多个分支都就绪时不保证公平，取消的分支要能承受 Drop。无界 `mpsc` 在消费者变慢时把内存吃完。定时器很密时，`sleep` 的唤醒本身有开销，大量超时用时间轮，而不是每个请求一个 `sleep`。

<a id="s5-3"></a>

## 5.3 三套线程（L1）

```
tokio workers          网络、解析、鉴权、SSE 写出、取消检测
        │ 有界 channel
调度线程（每 GPU 1 个，可绑核）
        组批、页表、准入、抢占决策。同步代码
        │ 任务描述
GPU 线程（每 GPU 1 个，持有 CUDA context）
        录/放 CUDA Graph，提交 stream，用 event 等完成
        │ oneshot / 结果队列
tokio                   把 token 写回对应连接
```

采样和 detokenize 若在 profiler 里占了 IO 线程，再拆一个小的 CPU 池。默认先放在调度线程或 GPU 线程的完成回调里，确认是热点再拆。

这是整份文档的落地骨架。后面的沙箱、调度循环、取消传播都接在这三套线程上。

## 5.4 取消、背压、Send（L1）

- 每个请求一个 id。连接断开时把 id 放进取消集合（`Atomic` 标志或调度线程上的集合）。
- KV 页的引用计数和取消在同一个所有者里更新，避免「任务已取消、页还被 batch 使用」或「页已释放、kernel 还在读」。
- 跨线程的任务类型必须是 `Send`。`Rc`、没加 `Sync` 的裸指针、某些 CUDA 句柄不是 `Send`。把 `!Send` 的资源留在拥有它的那一个线程里，channel 里只传 id。

## 5.5 FFI（L2）

- `bindgen` 生成 C 绑定。C++ 引擎用 `cxx`，让异常和模板停在边界外。
- 边界上的结构体 `#[repr(C)]`。谁分配谁释放，写在类型的注释里，并用 RAII 封装句柄。
- panic 不能穿过 FFI。边界上 `catch_unwind`，变成错误码。
- `unsafe` 块缩到最小，每个块上面写安全不变量。`Send` / `Sync` 的手工实现同样写不变量。
- 权重文件用 `memmap2`，再 `cudaHostRegister` 把需要 DMA 的区间登记为锁页。

## 5.6 构建与测试（L2）

发布配置：`opt-level = 3`、`lto = "thin"`、`codegen-units = 1`。要采火焰图时保留 frame pointer 和调试符号，不要在还没看过火焰图之前就 `strip`。

| 工具 | 查什么 |
|---|---|
| `loom` | 原子和锁的交错。状态空间小的队列和状态机放进 CI |
| `miri` | unsafe 的未定义行为 |
| `criterion` | 微基准 |
| `tokio-console` | 哪个任务一直不让出 |
| `proptest` | 页分配、组批这种「性质比例子好写」的逻辑 |

loom 枚举不开整个服务器。用它保护页表状态机和 SPSC 环，用压测看 p99。

# 6 沙箱

## 6.1 先写威胁模型（L1）

沙箱防的是不同的人，强度就不该一样。

| 威胁 | 例子 | 合适的边界 |
|---|---|---|
| 自己的推理进程有 bug，会把内存或 fd 打爆 | 泄漏、死循环、fork 风暴 | 进程沙箱：cgroup + seccomp |
| 租户提交的代码不可信，但不碰 GPU | 预处理、后处理、工具调用 | Wasm |
| 租户代码不可信，且必须直访 GPU | 多租户上跑任意推理进程 | microVM + VFIO 透传，或 MIG 把卡切开再加进程沙箱 |
| 模型文件本身有毒 | pickle 反序列化执行代码 | 格式白名单，见 [6.6](#s6-6) |
| 用户用提示词套系统指令 | prompt injection | 这是业务策略层的事。进程沙箱防不住自然语言 |

没有一种沙箱同时满足强隔离、GPU 直访、毫秒级启动。先选定威胁，再选技术。

## 6.2 三条路线（L1）

| | 进程沙箱 | Wasm（Wasmtime） | microVM（Kata / Cloud Hypervisor） |
|---|---|---|---|
| 边界 | 共享宿主内核 | 用户态，没有直接系统调用 | 独立内核 |
| 启动 | 约 10 ms 量级 | 亚毫秒到数毫秒 | 约 100 ms 量级，还要更多内存 |
| GPU | 可以透传设备节点。隔离强度等于你给了哪张卡 | 不能直接 CUDA。经 hostcall 把计算交给外面的引擎 | VFIO 透传 PCIe 设备。需要 IOMMU |
| 适合 | 信任度中等、要密度、要直访 GPU 的推理进程 | 插件和用户脚本 | 不可信代码还要 GPU |

补充几个容易选错的点：

- **Firecracker** 为了缩小攻击面，不做 GPU 透传。要 GPU 的 microVM 用 Kata 配 Cloud Hypervisor 或 QEMU，并处理 NVLink 的隔离。
- **gVisor** 用用户态内核拦截系统调用，隔离强于普通容器，GPU 支持有限。它不是第一版的默认。
- Wasm 里可以跑 CPU 上的小模型（有的运行时接了 GGML）。那是另一条产品线，不是这条 CUDA 服务的推理进程。

Wasmtime 要打开的能力：线性内存上限、fuel（按指令计费，相当于 CPU 配额）、epoch interruption（到点打断）。Host 只导入明确的函数，例如「提交一段文本、取回 token」。不导入文件系统和任意网络。大块张量用共享内存传递，避免每个 token 都序列化穿越边界。

<a id="s6-3"></a>

## 6.3 进程沙箱的启动顺序（L1）

下面每一步都依赖前一步。Rust 里系统调用用 `nix` 或 `rustix`，seccomp 用 `seccompiler` 或 libseccomp，路径策略用 `landlock`，capabilities 用 `caps`。这些 crate 各自独立，组合顺序要自己保证。

```
1. clone / unshare：先 user namespace，再 pid、mount、net、ipc、uts
2. 写 setgroups=deny，再写 uid_map / gid_map
3. 准备 rootfs：pivot_root 到最小目录；只读 bind 模型目录；tmpfs 做 /tmp
4. 在新 pid namespace 里挂精简 procfs；不要露出宿主机的 /proc 和 /sys
5. 把进程放进新建的 cgroup：pids.max、memory.high、memory.max、memory.swap.max=0、
   cpu.max、cpuset、io.max
6. PR_SET_PDEATHSIG = SIGKILL；进入独立进程组
7. close_range 关掉继承下来的 fd；所有打开都带 O_CLOEXEC
8. 清空 capabilities
9. PR_SET_NO_NEW_PRIVS
10. Landlock：只允许读模型目录和自己的临时目录
11. seccomp 白名单（最后一步）。默认不要放行 `io_uring_setup` / `io_uring_enter`，存储面确需使用时再单独评估
12. exec 目标程序
```

父进程是监督者：等 pidfd、读 `memory.events`、超时则 `cgroup.kill`。退出后读 `cpu.stat` 和 `memory.peak` 做计量，确认 GPU 进程已经消失。

fd 泄漏是最常见的逃逸面之一。父进程打开的套接字、日志、甚至 `/proc/self/mem` 会继承给子进程。`Command` 默认行为随平台变化，沙箱路径上显式关闭。

<a id="s6-4"></a>

## 6.4 GPU 隔离（L2）

设备节点 `/dev/nvidia*`、`nvidiactl`、`nvidia-uvm` 一旦出现在沙箱里，沙箱就拿到了这张卡的控制面。cgroup 的 devices 控制器能限制看得见哪些设备节点，不能限制进程能 `cudaMalloc` 多少显存。所谓「cgroup 显存上限」通常是 DCGM 看到超额之后再发信号，窗口里已经分配出去了。

| 手段 | 隔离 | 限制 |
|---|---|---|
| MIG（Ampere 及以后，A100 / H100 等） | 硬件切开 L2、内存控制器和显存地址。最多 7 个实例，profile 固定，不是任意 MB | 老卡没有。实例大小要能放下模型 |
| 时间片 / MPS | 共享一张卡，利用率和隔离都弱 | 能互相看见对方造成的抖动 |
| 只透传指定设备节点 + DCGM 杀进程 | 软限制 | 做不到「不可能超额」 |
| vGPU | 虚拟化切分 | 许可和虚拟化栈 |

MIG 解决隔离，不解决碎片。实例内部仍然要分页 KV。

计量用 NVML 把显存算到 PID 上。CUDA 上下文最好跟沙箱进程同生共死：进程被杀，上下文随之释放。长命进程里反复 fork 任务，显存会留下来。

GPU 故障：ECC 双位错误、Xid（`nvidia-smi -q` 或 DCGM）表示卡或驱动出了问题。这种节点打污点，排空之后再考虑 reset。reset 是节点级动作，不是请求级动作。

## 6.5 生命周期（L1）

```
创建 → 运行 →（冻结 / 超限 / 超时）→ 杀死进程组 → 收割，避免僵尸
→ 删除 cgroup → 确认显存已归还 → 记账
```

超时至少分开：整段墙钟超时、多久没有新 token、TTFT 超时。时间用单调时钟。墙钟会被 NTP 拨动。

监督者自己崩溃时，靠 `PDEATHSIG` 和 pid namespace 的 init，而不是靠「希望子进程听话」。

<a id="s6-6"></a>

## 6.6 权重与供应链（L1）

`torch.load` 走 pickle，反序列化时可以执行任意代码。加载一个来历不明的 `.pt` 等于在服务器上跑对方的程序。

接受的格式：safetensors（头部是 JSON，正文是原始张量，不执行代码）、GGUF。校验哈希，白名单之外的仓库不拉取。`trust_remote_code=True` 会在加载时执行仓库里的 Python，生产关闭。

分片权重（张量并行的每一份）和量化缩放因子一起校验。只校验主文件会让一份错误的分片在启动后很久才爆。

<a id="7-推理原理与显存账"></a>

# 7 推理原理与显存账

## 7.1 两个阶段（L1）

```
prompt: t0 … t(n-1)

Prefill：n 个 token 一起做前向
  Q、K、V 由这一整段并行算出
  Attention 的计算随 n 增长（标准实现是平方，FlashAttention 仍然要读完相关的 KV）
  结束时：长度为 n 的 KV，以及最后一个位置的 logits

Decode：每次只多一个 token
  读全部权重 + 这条请求已有的 KV
  写出 1 个新 token 的 logits → 采样 → 把新的 K、V 追加进缓存
```

Prefill 是大矩阵乘，算术强度高，受算力限制。Decode 是带宽限制，见 [3.7](#s3-7)。两者抢同一块 GPU 时，一个很长的 prefill 会把所有正在 decode 的请求卡住一个 prefill 的时间，TPOT 出现尖刺。所以调度上把它们分开对待，见 [7.7](#s7-7) 和 [第 8 章](#s8)。

## 7.2 显存公式（L1）

每个 token 的 KV：

```
字节 = 2 × 层数 × KV头数 × 头维 × 每元素字节
```

前面的 2 是 K 和 V 各一份。

Llama 3 70B 的常用配置：80 层，GQA 的 KV 头数是 8，头维 128，FP16 每元素 2 字节。

```
2 × 80 × 8 × 128 × 2 = 327680 字节 = 320 KiB / token
8192 token × 320 KiB = 2560 MiB = 2.5 GiB / 请求
```

权重按 70×10^9 参数 × 2 字节 ≈ 140 GB（十进制，和显卡规格同一套单位）。一张 80 GB 的卡放不下 FP16 的 70B 权重，要么量化，要么张量并行。下面的带宽账用「权重已经放得下」的抽象机器来说明 batch，不表示单卡 80 GB 能装下 140 GB。

单卡账本：

```
显存 = 权重
     + KV 池
     + 激活和 workspace（Attention 临时区、CUDA Graph 捕获的静态缓冲）
     + CUDA context 与通信缓冲（每进程数百 MB 起）
     + 碎片
```

容量规划把后三项算进去。只减「权重 + KV」会在上线后 OOM。

GQA / MQA 把 KV 头数从「等于查询头数」降到 8 或 1，KV 字节线性下降。MLA（DeepSeek 一类模型）再把 KV 压成低秩向量。选型时 KV 头数和上下文长度一起算，否则 128K 上下文的并发会先被 KV 打光。

## 7.3 Decode 的带宽账（L1）

这是下限：假设 kernel 吃满 HBM 峰值，并且每步把全部权重读一遍。实际会更慢。H100 SXM 的 HBM3 峰值是 3.35 TB/s。

上面的 2.5 GiB 换成和显卡规格同一套的十进制，是 2.68 GB。H100 SXM 的 3.35 TB/s 即 3350 GB/s。

**batch = 1，上下文 8K，FP16：**

```
读取 ≈ 140 GB 权重 + 2.68 GB KV ≈ 143 GB
时间 ≈ 143 / 3350 秒 ≈ 43 ms
这条请求 ≈ 23 token/s
整卡合计也是 ≈ 23 token/s
```

**batch = 32，每条都是 8K：**

```
读取 ≈ 140 GB + 32 × 2.68 GB ≈ 226 GB
一步的时间 ≈ 226 / 3350 秒 ≈ 67 ms
```

这一步为 32 条请求各生成 1 个 token：

- 每条请求的间隔仍是 67 ms，大约 **15 token/s**。单请求变慢了。
- 整卡合计 32 / 0.067 ≈ **480 token/s**。总吞吐变高了。

把 67 ms 除以 32 得到「每个 token 摊到约 2 ms」，那是整卡的平均字节成本，不是某一条请求看到的间隔。请求要等这一整步结束才拿到自己的那一个 token。

这就是 batch 的交换：**总吞吐上升，单请求 TPOT 变差，KV 显存线性上涨。** 调度器在 SLO 里找平衡，而不是把 batch 开到最大。

量化把权重字节砍下去，这个下限会跟着变。INT4 权重约 35 GB 时，batch=1 的读取时间大约是 FP16 的四分之一，前提是计算和缩放没有变成新的瓶颈。

Prefill 不要套这个公式。长 prompt 的时间主要由算力、Attention 的 IO 和有没有被别的请求堵住决定。

## 7.4 PagedAttention（L1）

按最大长度连续预分配 KV，内部碎片很大：请求只用了 200 token，却占着 8K 的坑。vLLM 论文里，这种做法的显存浪费是服务吞吐上不去的主因；分页之后同样的卡能服务更多并发。

做法和虚拟内存相同：

- 物理显存切成固定块（常见 16 个 token 一块）。
- 每个请求一张块表：逻辑块 → 物理块。
- 需要新 token 时从空闲列表取一块，结束时归还。
- Attention kernel 按块表读取。kernel 在 CUDA 里，Rust 管表和空闲列表。

块尾部仍有碎片（最后一块没用满）。块越小碎片越少，块表越大、kernel 的索引开销越高。16 是常见起点，用自己的长度分布再调。

物理块可以被多个请求的块表指向。相同前缀（系统提示、few-shot）只算一次，引用计数加一。某个请求在前缀之后开始不同，再拷贝出私有块（写时复制）。引用计数和「这个请求被抢占时，共享块还能不能释放」要在同一处决定。

淘汰：空闲块不够时，按优先级或 LRU 选牺牲者。牺牲者的 KV 可以换到主机锁页内存，也可以丢掉、下次重算。序列还很短时，经 PCIe 换出再换入，往往比重算更贵。策略要比较「剩余生成长度 × 重算成本」和「换出字节 / PCIe 带宽」。

## 7.5 前缀缓存（L2）

前缀缓存是分页的一种用法：用前缀的 token 哈希（或一棵 radix 树，SGLang 的 RadixAttention）找到已经算好的块。命中则跳过相应的 prefill，TTFT 下降。

命中率取决于路由。共享系统提示的请求若被轮询打散，每台机器都要各自算一遍。集群里的前缀亲和见 [2.4](#s2-4) 和 [11.2](#s11-2)。

缓存块也占显存。全是唯一前缀的流量里，强行留很多缓存块会挤掉并发。用命中率和因此拒绝的请求数一起看。

## 7.6 Batch 的三种形态（L1）

| 形态 | 行为 | 结果 |
|---|---|---|
| 静态批 | 凑满 N 个、一起开始、一起结束 | 短请求等长请求，GPU 在批内末尾空转 |
| 动态批 | 等一个时间窗或凑满 N 再启动 | 仍要等整批结束才能插入新请求 |
| Continuous / iteration-level（Orca） | 每个 decode step 移除已完成的，插入在等的 | 现代引擎的默认。调度器必须实现这个，而不是只做动态批 |

插入时检查：批大小上限、这一步的 token 预算、剩余 KV 块够不够这一步的 prefill 加 decode。

<a id="s7-7"></a>

## 7.7 Chunked prefill 与 prefill/decode 分离（L1）

**Chunked prefill** 把长 prompt 切成若干块，每一步只 prefill 一块，并和正在 decode 的请求放在同一次迭代里。长 prompt 的 TTFT 变长一点，其他请求的 TPOT 不再被一次几百毫秒的 prefill 打穿。

**分离（disaggregation）** 把 prefill 和 decode 放到不同的 GPU 池，中间传送 KV。单机上如果只有一张卡，先做 chunked prefill。多卡或多机、而且 KV 搬得够快时，分离才划算。搬得慢，分离只是把排队从 GPU 换成了网络。代价模型在 [11.3](#s11-3)。

## 7.8 算子、采样、推测解码（L2）

**FlashAttention**：分块、在片上做 softmax 的在线更新，不写下 `n×n` 的注意力矩阵。长上下文的 prefill 依赖它或同级实现。

**算子融合**把多次启动合成一次，减少往返 HBM 的次数。推理引擎和 CUDA Graph 已经做了一部分。自研 kernel 不是这条学习路线的前半。

**采样**在 logits 之后：温度、top-k、top-p、重复惩罚。它在 CPU 或一颗小 kernel 上，batch 很大时会变成 TPOT 的可见部分。结构化输出（JSON schema、正则）要在每步掩掉不合法的 token，掩码来自一个有限状态机（xgrammar、Outlines 一类）。grammar 的编译时间算进 TTFT。`n > 1` 的并行采样共享同一次 prefill 的 KV，分叉之后才复制。

**推测解码**：小模型一次起草 γ 个 token，大模型并行验证，接受最长的正确前缀。期望加速大约 1.5–2 倍这一量级，取决于接受率。变体包括多头草稿（Medusa）、在特征上草稿（EAGLE）、无草稿模型而利用提示里的重复（检索场景）。调度器要处理：两个模型的 KV、验证失败时的回滚、同一批里每条请求接受的长度不同。接受率低时，草稿的开销会让 goodput 下降。

## 7.9 权重怎样进显存（L2）

| 方式 | 行为 |
|---|---|
| 整文件读入再 `cudaMemcpy` | 简单，启动慢，多一份主机拷贝 |
| mmap + 预热 + 按需 H2D | 多进程共享页缓存。预热时机过早会挤掉别的缓存，过晚会让第一个请求缺页 |
| 后台线程读、锁页缓冲、另一条 stream 拷贝，与计算重叠 | 多模型切换时用 |

多进程映射同一份只读权重，页缓存只有一份，这是 mmap 的价值。`mlock` 防止它被换出，同时计入 cgroup 的内存上限。

多模型同卡：权重大，换入换出很慢，能常驻就常驻。KV 才是按请求调度的对象。适配器（LoRA）若共享底座，底座一份，适配器按需。

# 8 调度器

调度器是第 5.3 节里的那一个同步线程（每 GPU 一个）。它不做 CUDA，只决定这一步跑谁。

## 8.1 目标（L1）

同时看三件事，而不是只看 token/s：

- **TTFT** 落在目标内（排队 + prefill + 调度空隙）。
- **TPOT** 落在目标内（decode 的步长时间）。
- **Goodput**：交付出去且达标的 token。客户端已经断开还在生成、推测解码被拒的草稿、为了刷吞吐而严重超时的 token，都不计入。

一个可用的表述：在 TTFT 和 TPOT 的约束下，最大化 goodput。批大小、排队时间、抢占都从这个约束推回来。

## 8.2 排队论给的边界（L2）

**Little 定律**：系统里的平均请求数 L = 到达率 λ × 平均停留时间 W。每秒 10 个请求、每个停留 2 秒，则平均 20 个并发。它用来核对监控：三个数对不上，就是埋点或排队模型错了。

**Kingman 近似**（M/G/1 的等待时间）说明等待随利用率上升：

```
等待 ≈ (ρ / (1-ρ)) × ((到达变异² + 服务变异²) / 2) × 平均服务时间
```

ρ 接近 1 时，`ρ/(1-ρ)` 趋向无穷。LLM 的服务时间变异很大（提示长度差几十倍），所以同样的利用率，尾部比指数分布更差。给 GPU 留余量，常见是让它不要长期贴着 100% 跑；具体余量用自己的 p99 曲线标定，而不是背一个固定的 80%。

批的等待窗也一样：窗越长，批越大，吞吐越好，队里每条请求的 TTFT 越差。窗的长度由「再等下去，队首的 TTFT 会不会破目标」决定，而不是写死 5 ms。

## 8.3 一步迭代（L1）

```
loop:
  从取消集合去掉已死请求，归还它们的 KV
  若有请求的 KV 需要抢占或换出，先做
  组这一步的 batch：
      正在 decode 的请求（continuous）
      若干 prefill 块（chunked，受 token 预算限制）
      受 max_seqs、剩余块数、TPOT 预算约束
  把计划交给 GPU 线程
  等这一步完成（在 GPU 线程上等，调度线程可以选择等结果或被 event 唤醒）
  完成的请求出队；采样；需要继续的留在 decode 集合
  把新的 token 交给对应连接
```

队头阻塞：一个 32K 的 prefill 和一堆 32 token 的请求在同一个不可抢占的批里，短请求的 TTFT 等于长请求的 prefill。用长度分桶和 chunked prefill 把这个绑定拆开。

## 8.4 抢占（L2）

高优先级到来且显存不够时，选低优先级的牺牲者：

- **重算**：丢掉 KV，之后重新 prefill。短序列、PCIe 慢时更合适。
- **换出**：KV 到锁页主机内存，之后换回。长序列、换出带宽够时更合适。

抢占本身增加牺牲者的尾延迟。触发条件写清楚：显存水位、队列里高优先级等待超过多久、而不是「只要来了高优先级就换出」。

## 8.5 公平（L2）

只有优先级时，低等级会被饿死。给等待时间加权（老化），或按租户做赤字轮转（DRR）：每个租户一个份额，份额用完排到后面。多资源（GPU 时间、KV 字节、并发数）同时公平时，用主导资源公平（DRF）的思想：看每个租户在自己占用比例最高的那种资源上有多满。

优先级反转：低优先级拿着共享前缀的块，高优先级在等这些块。共享块的引用要能区分「可抢占的独占」和「还有别人在用」。

<a id="s8-6"></a>

## 8.6 反压与准入（L1）

三层，每一层都有上限：

1. **接入**：租户令牌桶 + 全局并发上限。满了返回 429。
2. **队列**：有界。入队前用 `提示长度 + max_tokens` 估算 KV 块。不够就拒绝或稍后再试，不要先入队再在一小时后 OOM。
3. **输出**：SSE 写不动时停止从 decode 取 token，调度器下一步把这个请求留出 batch 或降速。

p99 持续破目标时主动减载，保护已经在跑的请求。过载时所有人都变慢，比一部分人立刻失败更难恢复。

## 8.7 多模型（L2）

同卡多模型时，调度维度是「哪个模型的权重已经在显存里」加上「这个模型的队列有多深」。权重换入是秒级，KV 换出是毫秒到几十毫秒级。尽量让权重稳定，用 KV 吸收波动。

每个模型一个队列分片，避免一个热模型的锁拖住其他模型。

<a id="9-可观测与排障"></a>

# 9 可观测与排障

## 9.1 三种信号（L1）

| 信号 | 回答 | 不要拿来做 |
|---|---|---|
| 指标 | 这个服务现在是否健康 | 把 request_id、user_id、完整错误字符串做成标签 |
| 追踪 | 这一次请求的时间花在哪一段 | 每个 token 一个 span。用一个 span 加 step 计数 |
| 日志 | 某一件事的现场 | 每 token 一行 info |

指标标签的基数爆炸会把 Prometheus 打满。标签只用模型名、租户等级、状态码这一类有限集合。高基数的 id 放进追踪的 exemplar 或日志。

延迟用直方图，不用 summary 做跨进程分位（summary 不能正确相加）。TTFT 和 TPOT 分开两套桶：一个是百毫秒到数秒，一个是几毫秒到几十毫秒。

**USE**：每个资源看利用率、饱和度（排队）、错误。GPU 的利用率看 SM，也看显存带宽；饱和度看队列深度和 `throttled_usec`；错误看 ECC / Xid。

**RED**：每个服务看速率、错误、耗时。

指标、追踪、日志用同一个 trace id 串起来。

## 9.2 推理服务最少要有的指标（L1）

- TTFT、TPOT 的直方图
- 在跑请求数、排队时间、拒绝数
- 批大小分布、每步 token 数
- KV 已用块、前缀命中率、换出次数、抢占次数
- GPU 显存、SM 利用率、显存带宽活跃（DCGM 的相关字段，具体名以当前 DCGM 版本为准）
- `nr_throttled`、major fault、runqueue 等待

Goodput 单独一条：成功写到客户端且未超 SLO 的 token 速率。

## 9.3 工具（L2）

| 现象 | 工具 |
|---|---|
| CPU 时间花在哪 | `perf record` 火焰图 |
| 线程在睡觉等什么 | off-CPU 火焰图、`offcputime` |
| 被调度器耽误了多久 | `runqlat`、`perf sched` |
| 伪共享 | `perf c2c` |
| 缺页 | `perf stat -e page-faults`、`pgmajfault` |
| 系统调用和 seccomp 误杀 | `bpftrace` 的 syscall 跟踪点、审计日志 |
| 磁盘 | `biolatency` |
| GPU kernel | Nsight Systems / Compute；日常看 DCGM、`nvidia-smi dmon` |
| 跨服务的一次请求 | OpenTelemetry：网关 → 调度 → Agent → GPU 步 |

eBPF 用来确认机制，不作为架构本身。先有第 5.3 节的线程模型，再用 `runqlat` 验证推理线程没有在队列里等 10 ms。

## 9.4 毛刺从哪来（L2）

按这个顺序拆，不要一上来改 kernel：

```
p99 变差
→ 看 TTFT 和 TPOT 哪一个变了
→ TTFT：排队变长，还是 prefill 变长，还是冷权重缺页
→ TPOT：步长变长（batch 变大 / 带宽），还是步与步之间有空隙（调度、启动开销、锁）
→ 空隙：runqlat、off-CPU、cudaMalloc 是否出现在热路径、THP 压缩、代理缓冲
```

常见来源：THP 压缩、权重没预热、推理线程被中断抢走、跨 NUMA、热路径 `cudaMalloc`、tokio worker 被阻塞、SSE 被代理缓冲、无界队列、一个长 prefill 没切开。

# 10 分布式基础

单机的队列和页表先做对。这一章只加「多了一台机器之后，哪些单机假设会坏」。

## 10.1 一致性放在哪（L1）

CAP 说的是：网络分区时，不能同时保证所有节点看到的数据完全一致、并且每个请求都得到成功响应。PACELC 补了一句：没有分区时，也要在延迟和一致性之间选。推理对延迟敏感，请求路径上不做跨节点的强一致提交。

| 数据 | 一致性 | 原因 |
|---|---|---|
| 集群成员、模型注册、租户配额、拓扑 | 强一致，Raft（etcd 即可） | 量小，写得少，错了会超售或把请求送到不存在的节点 |
| 节点当前显存、队列深度 | 允许过期几秒的心跳 | 写得频繁。用租约限制过期窗口 |
| KV 页在哪台机器 | 负责它的调度器内存里为准；目录可以批量汇报 | 每分配一块就写一次 etcd，写延迟是毫秒级，页分配会停 |
| KV 的字节 | 随传输到达，不走共识 | 共识复制 2 GB 的 KV 没有意义 |

Raft 用在元数据。任务队列和 KV 正文不进 Raft。

<a id="s10-2"></a>

## 10.2 租约、时钟、幂等与重试（L1）

**租约**：调度器把「这张卡接下来 T 秒归你」交给 Agent。到期没续约，资源回到池里。这比「相信最近一次心跳永远正确」更能限制超售。

**Fencing token**：每次决策带一个递增的代号。旧主脑裂之后回来发调度，Agent 拒绝代号更小的指令。

**时钟**：超时和租约用单调时钟。不要用两台机器的墙钟比先后。NTP 会把钟拨回去，任务会提前超时或永远不过期。跨机器的顺序用调度器发的版本号。

**幂等**：客户端带 `request_id`。重试到达时，如果还在生成，接上原来的流或者明确告诉客户端「已经在跑」；不要再 prefill 一次再收一份钱。流式场景下，断线重连要约定是接着 token 序号继续，还是整段重来。两种都能做，不能混。

**重试**：指数退避加抖动；区分可重试（超时、503）和不可重试（400、鉴权失败、内容安全拒绝）。限制重试预算，防止故障时重试流量大于原始流量。

**故障模型**：崩溃、丢包、分区、慢节点。慢节点比死节点更常见：一张降频的卡把整组张量并行拖住。拜占庭故障（节点恶意伪造结果）不在这套系统的第一版范围内。

**分区时的本地自治**：Agent 和全局调度器失联，继续跑已经开始的请求，停止接新的。恢复后再对账。把失联当成「立刻杀掉本机所有推理」会在一次网络抖动里清空集群。

<a id="s10-3"></a>

## 10.3 RDMA / RoCE / InfiniBand（L2）

多机推理的瓶颈经常是机器之间的带宽，不是某一张卡的算力。张量并行每一层都要集合通信；PD 分离要把 KV 搬到另一台机器。

RDMA 让网卡直接读写对端内存，数据面不经过对端 CPU 和内核协议栈。延迟从 TCP 的几十微秒降到数微秒这一量级，带宽靠硬件而不是靠主机拷贝。

| | InfiniBand | RoCE v2 |
|---|---|---|
| 网络 | 专用 | 以太网 |
| 丢包 | 网络本身按无损来建 | 要自己做成无损：PFC、ECN、拥塞控制 DCQCN |
| 代价 | 贵，独立布线 | 能复用以太网，配置错了会丢包，RDMA 重传，延迟塌掉 |

RoCE 的 PFC 若配错，会暂停过多的流量甚至形成暂停帧风暴。上线前用交换机计数器看 pause 和重传，而不是只看「ping 得通」。

**GPUDirect RDMA** 让网卡 DMA 直接碰到 GPU 显存，少一次主机中转。它依赖拓扑：网卡和 GPU 要足够近（同一 PCIe switch 一类的接法）。拓扑不满足时会退回锁页主机内存，性能掉一个台阶。调度器要知道哪两块设备是近的。

**Spine-Leaf** 是常见的机房拓扑：服务器接 Leaf，Leaf 之间经 Spine 全连接，任意两台服务器跳数相同。张量并行这种每层都通信的任务，放在同一台 Leaf 下面。跨 Spine 的 KV 搬运即使带宽数字够，也更容易碰到拥塞。

控制面继续走 gRPC。数据面的 KV 走 RDMA 或厂商的传输库（NIXL、Mooncake Transfer Engine 这类），不要把 KV 放进 Redis 或 etcd。

<a id="11-集群"></a>

# 11 集群

## 11.1 形状（L1）

```
客户端
  → 接入网关（鉴权、限流、兼容 API）
  → 全局调度器（路由；元数据在 Raft）
  → 节点 Agent（每台 GPU 机器一个）
  → 第 0 章的单机五层
```

全局调度器回答「去哪一台」。单机调度器回答「这一步批里有谁」。不要把 continuous batching 写进 K8s scheduler。

<a id="s11-2"></a>

## 11.2 全局调度器与节点 Agent（L1）

调度器看到的资源：GPU / MIG 实例、剩余 KV 容量、哪个模型已加载、NUMA 和网卡拓扑、租户标签。

策略按这个顺序收紧，而不是互相覆盖：

1. 硬约束：模型放得下、租户还有配额、TP/PP 需要的节点组能同时满足。
2. 拓扑：要集合通信的组落在同一 Leaf。
3. 负载：队列深度、剩余 KV、近期 p99。留出 Kingman 那一节说的余量。
4. 亲和：在已经合格的候选里，偏好前缀缓存能命中的节点。

中心调度器会成为瓶颈。按模型或租户分片，元数据仍由 Raft 复制。Gossip 适合超大规模的粗粒度状态，不适合作为第一版。

Agent 的职责：按心跳和事件上报、创建沙箱、拉起 worker、执行本地的第 8 章调度、发现 GPU hung / ECC、失联时按 [10.2](#s10-2) 自治。

过期视图会造成超售：调度器以为卡是空的，两份请求同时进去，一起 OOM。租约加上 Agent 侧的硬拒绝（本地账本不够就拒绝这次放置）比「调度器单方面相信自己」安全。

<a id="s11-3"></a>

## 11.3 分布式 KV 与 PD 分离（L2）

KV 迁移的路径：

```
源 GPU 显存 →（必要时）源主机锁页内存 → RDMA → 目的主机 → 目的 GPU
```

能 GPUDirect 则跳过主机那一跳。

一次迁移值不值，把时间和收益放在一起算。第 7.2 节那条 8K、70B、FP16 的 KV 是 2.68 GB，在 100 Gbps 线上：

```
2.68 × 8 ≈ 21.4 Gbit
21.4 / 100 秒 ≈ 210 ms
```

400 Gbps 大约 54 ms。这还是线速下限，不含排队和拷进 GPU。短回答若只生成十几个 token，210 ms 的搬运会计入 TTFT，分离可能更慢。长回答把 prefill 和 decode 的资源错开，搬运可以被后面的几百个 token 摊掉。按预测的生成长度决定走不走分离，而不是所有请求都拆。

页的位置信息由源端调度器在迁移完成后更新。传输过程中不需要全球同步每一块的字节。etcd 只存目录级信息，而且批量写。

**缓存孤岛**：四台机器各有 10 GB 本地 KV 缓存，一个请求只能命中它被分到的那一台，有效缓存仍是 10 GB。跨节点只读共享（LMCache 一类的做法）把命中域扩大。共享带来一致性和失效：块被淘汰时，目录要作废。

PD 池可以配不同的并行度和显存水位。Prefill 池要吃得下突发的长 prompt；Decode 池把显存尽量留给 KV。两套负载指标不要合成一个「GPU 利用率」。

vLLM 的 connector、SGLang 的分离实现、Mooncake 的传输层都是这个结构的现成参考。自研时先用 TCP 把「页 id、块表、迁移状态机」跑通，再换 RDMA。逻辑没通之前换网卡，排障会混在一起。

## 11.4 并行（L1）

| 方式 | 切什么 | 通信 | 调度单位 |
|---|---|---|---|
| 数据并行 DP | 整份模型的多个副本 | 请求之间没有模型通信 | 单节点。集群服务的默认 |
| 张量并行 TP | 一层切到多卡 | 每层都有集合通信，要 NVLink 或同 Leaf 的 RDMA | 一组绑死的卡。坏一张，整组失效 |
| 流水线并行 PP | 按层切开 | 阶段之间传激活 | 一组节点，还要处理流水气泡 |
| 专家并行 EP | MoE 的专家放在不同卡 | all-to-all | 和 TP 一样按组放置 |

组的失败要有降级：缩小 TP，或拒绝并让客户端重试到 DP 副本。没有降级时，一张卡的 ECC 等于整组模型下线。

## 11.5 多租户、分发、编排（L2）

租户配额是集群级的：GPU 时间、并发请求、KV 字节、token 速率。Agent 本地再设硬顶，防止全局计数延迟期间被打穿。

网络：调度通道 mTLS。沙箱默认没有出网。租户之间不共享 Unix socket 和 IPC namespace。

计费至少分开：token、GPU 时间、前缀缓存命中（命中的请求成本更低，账单若仍按全价 prefill 会和实际资源不符）。

模型分发：对象存储是源头，节点后台拉取并预热。70B 的 FP16 权重量级是一百多 GB，一百台一起拉要规划仓库的出口。灰度是路由比例，回滚是把比例拨回去，而不是在请求过程中替换已经映射的文件。

**K8s** 适合管节点、容器生命周期、基础网络和存储。它的默认调度器没有 KV 页、没有 continuous batching，调度延迟也对 TTFT 不友好。形态是：K8s 运行 Agent 和进程，Rust 调度器做推理放置。完全裸机则节点生命周期、磁盘、发布都要自己做。团队小的时候用 K8s 管机器。

<a id="12-端到端设计"></a>

# 12 端到端设计

## 12.1 延迟预算（L1）

把目标拆开，否则优化会花在占比很小的一段上。

```
TTFT ≈ 接入与排队 + tokenize + 等待组批 + prefill + 第一次采样 + 第一次 SSE
TPOT ≈ 一步 decode（含 kernel 与启动）+ 采样 + 写出
      步与步之间的空隙另计
```

举例：TTFT 目标 500 ms。若排队已经 400 ms，把 kernel 从 80 ms 优化到 60 ms 几乎不改变用户体验。先看直方图里每一段的 p99，再选工具。冷启动缺页、跨机下载权重，会让这一段变成秒级，预算表里单独列「未预热」。

## 12.2 容量（L2）

从流量反推，而不是从卡的数量正推。

1. 峰值请求率 λ、平均提示长度、平均生成长度、TTFT / TPOT 目标。
2. 用第 7.2 节算每请求 KV，用第 7.3 节算单卡 decode 的合计 token/s 下限，再打折（带宽利用率常常远低于峰值，先用测量值；没有测量时不要假设 100%）。
3. 并发上限 = 可用于 KV 的显存 / 每请求 KV。它和算力上限取更小的那个。
4. 用 Little 定律检查并发是否等于 λ × 停留时间。停留时间 ≈ TTFT + 生成长度 × TPOT。
5. Prefill 和 decode 若分离，两池分开做 2–4 步。

成本按 GPU 时间计。量化用显存换效果，分离用网络换两池的利用率。两者都要有延迟和效果的回归，不只看单卡 token/s。

## 12.3 协议（L1）

对外：OpenAI 兼容的 chat / completions，流式用 SSE。请求体在网关做 token 计数（HuggingFace `tokenizers` 这一类库），计费、限流、KV 估算都用这个数，不要相信客户端自报的 token 数。

错误要能让调用方决定要不要重试：

| 情况 | 行为 |
|---|---|
| 配额、队列满 | 429，带等待时间 |
| 请求不合法、超长 | 400，不重试 |
| 鉴权失败 | 401 / 403，不重试 |
| 内容安全拒绝 | 明确的 4xx，不换模型重试 |
| 本机失败、可换副本 | 503，可重试，且带幂等键 |
| 超时 | 网关超时小于客户端超时，留出重试的时间 |

取消和幂等见 [2.2](#s2-2) 和 [10.2](#s10-2)。

## 12.4 可靠性和停机（L1）

超时分层：连接建立、排队等待、TTFT、整段生成、单步无进展。外层预算大于内层之和，避免内层还在正常工作、外层已经断开。

降级顺序：拒绝新请求 → 关掉推测解码和可选的长上下文 → 只保留核心模型的 DP 副本 → 返回静态错误。不要在故障时同时打开更多重试。

**优雅停机**：从负载均衡摘掉 → 停止接新请求 → 等存量完成或迁移 KV → 释放页和 context → 卸权重 → 退出。K8s 的 `preStop` 要留够这个时间。杀掉进程再让客户端重试，等于把停机变成一次全量 prefill。

## 12.5 安全清单（L2）

| 面 | 做法 |
|---|---|
| 不可信插件 | Wasm，不给 GPU，不给任意网络 |
| 推理进程资源 | 第 6.3 节的进程沙箱 |
| 不可信且要 GPU | MIG 或 microVM |
| 模型文件 | safetensors / GGUF，校验哈希，关闭远程代码 |
| 提示词注入 | 网关做策略钩子；沙箱不解释自然语言 |
| 租户越权 | 身份以令牌为准，覆盖客户端自己填的租户字段 |
| 节点之间 | mTLS，fencing token |
| 密钥和 fd | 不继承进沙箱 |

<a id="14-项目阶段与学习顺序"></a>

# 14 项目阶段与学习顺序

每一阶段都有可以失败的验收。没过验收不进入下一阶段。

## 14.1 阶段

**阶段 1：沙箱能关住一个不听话的进程**

user namespace、cgroup v2、seccomp 白名单、`PDEATHSIG`、`close_range`。跑一个会 fork 炸弹、会写爆内存、会死循环的程序。

验收：三种滥用都被限额或杀掉；父进程退出后没有孤儿；`memory.events` 能看到 oom；没有继承来的额外 fd。

**阶段 2：纯 CPU 的调度器**

有界队列、优先级和老化、按时间窗组批、用 sleep 模拟 prefill 和 decode 两种服务时间。不碰 GPU。

验收：压测曲线上能看见利用率升高后 p99 翘起（Kingman）；Little 定律的三个数对得上；队列满时拒绝而不是内存增长。

**阶段 3：接上 GPU**

独立 GPU 线程，显存池，主机侧块表，continuous batching，SSE 把 token 推出去。后端可以是 llama.cpp 或引擎的 C API。

验收：客户端断开后 GPU 在下一步停止该请求；热路径没有 `cudaMalloc`；TTFT / TPOT 分成两套直方图。

**阶段 4：沙箱包住推理进程**

阶段 3 的 worker 跑在阶段 1 的沙箱里。GPU 只看见指定设备。超时、强杀、显存回收串起来。

验收：`kill -9` 监督路径上的故障注入之后，没有泄漏的进程和显存；fd 审计通过。

**阶段 5：把 p99 里最大的那一段打下去**

绑核、中断、NUMA、权重预热、chunked prefill、前缀缓存、必要的 CUDA Graph。用第 9.4 节的顺序，一次只改一个因素。

验收：有一份前后对照，写明改的是排队、prefill、步长还是空隙。

**阶段 6：两台机器的数据并行**

Agent、心跳、租约、fencing、全局路由只做 DP。etcd 只放注册和配额。

验收：拔掉调度器与 Agent 之间的网络，已在跑的请求继续；恢复后不会超售；重复的 `request_id` 不会生成两份。

**阶段 7：分离与搬运**

先用 TCP 搬运 KV，状态机正确后再换 RDMA。按生成长度决定是否分离。

验收：手算的搬运时间和测量值在同一量级；短请求不会被强制分离；元数据写不在每页的热路径上。

**阶段 8：租户和故障**

配额、mTLS、污点与排空、一种混沌情况（杀 Agent 或给 RoCE 制造丢包，二者择一，把现象记录清楚）。

Wasm 插件如果产品需要，作为阶段 4 之后的分支：host 只暴露推理调用，不进阶段 7 的关键路径。

## 公式

```
KV 每 token  = 2 × 层数 × KV头数 × 头维 × 字节数
70B FP16 例  = 2 × 80 × 8 × 128 × 2 = 327680 字节 = 320 KiB/token
8K 上下文    = 8192 × 327680 = 2.68 GB = 2.5 GiB

带宽下限     = 读取字节 / HBM 峰值带宽
H100 SXM     = 3.35 TB/s = 3350 GB/s（HBM3，不是 H200 的 HBM3e）
batch=1      ≈ (140 + 2.68) / 3350 ≈ 43 ms     → 单请求 = 合计 ≈ 23 token/s
batch=32     ≈ (140 + 32×2.68) / 3350 ≈ 67 ms  → 单请求 ≈ 15 token/s
                                                 合计 ≈ 480 token/s
               单请求速率 = 1 / 一步时间
               合计速率   = B / 一步时间

100 Gbps 搬 2.68 GB ≈ 210 ms（线速下限）

Little       L = λ × W
Kingman 等待 ≈ [ρ/(1-ρ)] × [(Ca²+Cs²)/2] × 平均服务时间

算术强度     = FLOPs / 字节
屋顶         性能 ≤ min(峰值算力, 带宽 × 算术强度)
```

- 核心问题一：把 Rust FFI 调用与 CUDA 驱动/kernel-launch 开销混为一谈。普通 FFI 调用本身通常不是文中所暗示的主要成本，批量执行计划和 CUDA Graph 也有价值，但论证起点不准确，见  
C:\cxProject\ODN_TestCraft\document\agent\rust\deepseek.md:26-28、  
C:\cxProject\ODN_TestCraft\document\agent\rust\deepseek.md:221-225。
- 核心问题二：建议用 [u8; 0] 隔离不同写入者的 cache line；零长度数组本身不提供有效填充，应使用实际 padding 或 CachePadded，见  
C:\cxProject\ODN_TestCraft\document\agent\rust\deepseek.md:64-68。
- 可信度问题：多处给出非常具体的碎片率、吞吐和锁延迟数字，却没有可复现环境或来源，例如自定义分区池把碎片率压到 5%、吞吐从 210 提到 245 的算例，见  
C:\cxProject\ODN_TestCraft\document\agent\rust\deepseek.md:128-134。
- 适合读者：已读主教材后，用来挑战“io_uring 一定更快”“Firecracker 可透传 GPU”等简单结论；不适合作为唯一学习材料。
四、跨七篇需要特别警惕的共同问题
1. seccomp 路径过滤是跨文档反复出现的共同盲区。  
腾讯、千问、豆包、智普、Kimi、minimax、deepseek 都以不同方式暗示可直接匹配路径。学习时应统一纠正为：BPF 可直接检查数值参数，不能直接把用户态字符串当普通内存读取并安全地做路径授权。
2. “代码多”没有转化为可靠性。  
minimax 的代码量最大，但错误代码和错误算例也最多；智普、deepseek 虽然短，严重错误密度反而更高。评价时应看“每千行有多少会改变设计结果的错误”，而非总页数。
3. 性能数字普遍缺少测试条件。  
吞吐量、启动时间、锁延迟、RDMA 倍数、量化“几乎无损”等结论，如果没有模型、硬件、batch、输入输出长度、精度和软件版本，就只能当线索，不能直接做容量承诺。
4. 若两篇内容互相重复，不能把它们当成相互核验。  
多篇显然共享了同一套提纲和部分错误，选择两篇是为了覆盖与学习体验，不代表获得两个独立事实来源。
最终选择
如果只选一篇：腾讯
理由是它在七篇中提供了最高的净可靠信息量：没有 minimax 的阅读与核验负担，学习结构又足够完整，生产补项比豆包、智普、deepseek 更均衡。  
若目标被明确限定为“从零开始、按课程自学并做项目”，则学习体验上可改选 Kimi，但综合首选仍是腾讯。
如果选两篇组合：Kimi＋腾讯
- Kimi 作主线：按章节、项目、月份和验收标准学习。
- 腾讯作压缩复习与生产补全：用于回顾优先级，并补 tokenizer、取消、故障、发布、计量等工程环节。
这不是互补性最强的“正反方组合”，而是七篇中综合收益最高、整体风险最低的两篇组合。使用时仍需共同纠正 seccomp、GPU 隔离和未经验证的性能数字，不能拿两篇互相证明同一断言。

## 谁更适合学习

**Kimi 最适合当主线。** 它按「OS → Rust 并发 → 推理账本 → batching 谱系 → 沙箱配方 → 线程模型 → 集群 → 带验收标准的项目阶段」往下走，附录里有 KV 公式、Little / Kingman、内存序和一份自查清单。阶段任务写了「做完怎样算过」，例如沙箱要挡住 fork 炸弹、调度要用 Little 定律对一下压测曲线。长上下文、MoE、约束解码、推测解码变体也放在该出现的位置，而不是名词堆砌。

**豆包最适合当第一遍导读。** 每节都回答四件事：这是什么、推理服务里为什么在乎、Rust 落在哪个 API、错了会怎样。OS、epoll、NUMA、无锁和有锁的取舍讲得稳。集群后半变成提纲，深度不如 Kimi。

**千问适合建立整体图像。** 开篇把系统收成三条线：尾延迟、把虚拟内存那套搬到 KV 上、Rust 只做编排。OS、沙箱步骤、调度指标、集群坑都在。篇幅更短，展开不如 Kimi，而且有一处会教错：把 `io_submit` / `io_getevents` 说成 io_uring。那是旧的 Linux AIO，io_uring 的提交接口是 `io_uring_enter`。

**腾讯适合当复习笔记。** 覆盖面和千问、豆包接近，另外补了 tokenizer、safetensors、取消传播、优雅停机、GPU XID，这些是做服务时真会碰到、大纲里容易漏的点。解释偏短，不适合零基础第一遍。

**智谱是同一份大纲的压缩版。** KV 公式、沙箱 8 步、三池线程模型、租约和 fencing、Stage 1–7 都在，300 多行能扫完全图。它不解释「为什么这样设计」，不能代替教材。

**DeepSeek 不适合当第一份教材，适合当第二份。** 它几乎不系统讲 TCP、内存序、cgroup 文件，而是专门改常见选型：

- 推理网关的网络面继续用 epoll；io_uring 放在权重加载和 KV 落盘。
- 没有一种沙箱同时做到强隔离、GPU 直访、低开销。Wasm 跑插件，进程沙箱加 MIG 跑推理，要强隔离再上 microVM 透传。Firecracker 不做 GPU 透传。
- cgroup 限制不了显存，超额只能事后杀掉；硬隔离靠 MIG。
- PD 分离把瓶颈从算力调度挪到 KV 传输；元数据要强一致，KV 内容本身不要走 Raft。

这些判断比另外六份更尖。文中的吞吐数字（例如碎片率、tokens/s）和个别项目名要自己核对，不要当论文数据背。

## 谁的知识点更全

**MiniMax 全得多一个数量级。** 同一份提纲在它这里被铺成十多章：OS 调优参数、seccomp、Roofline、MFU、goodput、前缀缓存、chunked prefill、采样与受限解码、推测解码、排队论、eBPF、分离式推理、容量规划、威胁模型和错误码，后面还有按严重程度排的坑和配置样例。做实现时按章查它。

它不适合线性学。八千行里正确的细节和需要复核的数字混在一起。最显眼的一处在第 7 章的 batch 算例：70B、FP16、H100，batch=1 时大约 42 ms/token、约 23 token/s，这个量级是对的。batch=32 时它写成「单请求约 480 token/s、总吞吐 15360 token/s」。这里把「权重被 32 路摊薄后的平均字节成本」当成了每个请求的延迟。一次前向仍然要大约 66 ms，每个请求这一步只拿到 1 个 token，所以单请求大约 15 token/s，整批合计大约 480 token/s。batch 提高的是总吞吐，单请求的 token 间隔通常变差。另外 H100 是 HBM3，HBM3e 是 H200。这种地方它写得很像教材，错了也不容易看出来。

Kimi 的 70B KV 账和 MiniMax 一致，而且没把这个吞吐算反：80 层、8 个 KV 头、FP16，大约 0.33 MB/token，8K 上下文大约 2.6 GB。可读文档里，Kimi 的覆盖最全。

千问、豆包、腾讯、智谱的知识地图高度重合，因为都按同一份「单机 → 内核 → 集群」清单在写：沙箱三件套、continuous batching、PagedAttention、CUDA 不要进 tokio、NUMA、RDMA、PD 分离、Raft 只放元数据、K8s 管机器不管推理调度。差别在展开程度，不在有没有这个主题。

## 建议的读法

1. 先读豆包或千问，只建立五层架构和 TTFT / TPOT / KV / batch 这几个词。
2. 以 Kimi 为主教材，按它的 Stage 做，做完用附录清单自测。
3. 读 DeepSeek，专门看沙箱三条路线、io_uring 的边界、PD 分离之后瓶颈在传输。
4. 写代码时按章节翻 MiniMax，公式和「实测吞吐」先手算再信。
5. 智谱和腾讯留到每一阶段结束时当对照表，看有没有漏掉 tokenizer、停机、取消传播、租约。
