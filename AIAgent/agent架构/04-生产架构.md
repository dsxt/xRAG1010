# Agent 系统生产级架构方案

> 版本：v3.0（深度整理版）  
> 口径：2026-11-20。这是行为与降级的架构正文。逐步顺序以《Agent 应用开发全流程》为准；长 Schema 与检查清单以契约文档（原 v2）为准，双方冲突时改契约，不另写一套行为。  
> 适用范围：企业级 RAG / LLM Wiki / 多 Agent 编排 / MCP 工具系统  
> 文档目标：从请求进入到答案交付、写操作审批、审计回流，定义可实现、可观测、可治理的系统边界。

## 1. 摘要与设计目标

系统由网关、策略与身份层、Agent Runtime、知识层、工具执行层、审批层、观测评估层组成。Agent 负责理解与生成，确定性服务负责授权、预算、状态迁移、写操作提交和审计。

核心目标：

- **正确路由**：识别领域、任务、风险、实体和缺失槽位。
- **受控执行**：计划是有约束的 DAG；工具权限按任务授予。
- **证据回答**：答案可追溯到文档、Wiki 词条、工具结果及其版本。
- **安全写入**：写操作使用预览、确认、幂等提交及审计边界。
- **故障可控**：超时、取消、预算耗尽、依赖故障时能停止或降级。
- **租户隔离**：身份、检索、缓存、工具、日志和知识全链路带租户与权限范围。

> 阈值、评分权重和超时均为初始建议值，必须用业务黄金集、压测和风险评审校准，不能当作通用常数。

## 2. 总体架构与请求路径

```text
客户端
  → API Gateway（鉴权、限流、请求校验）
  → Policy / Safety（权限、风险、审批要求）
  → Agent Runtime（状态机、预算、取消、编排）
  → 意图识别 → 规划器（受约束 DAG）
  → Context / Memory（最小上下文、Just-in-Time 注入）
  → Knowledge Plane（LLM Wiki、RAG、Ontology、知识图谱）
  → Task Scheduler（并行调度、子 Agent 隔离）
  → Tool Gateway（MCP、参数校验、权限、幂等、超时）
  → Result Validator / Merger
  → Approval Gate（需要时）
  → Output Guard → 客户端
  → Trace / Metrics / Audit / Evaluation / Knowledge Governance
```

一次请求的稳定标识建议包括 `tenantId`、`userId`、`conversationId`、`traceId`、`runId`；每个子任务另有 `taskId`、`subRunId`。所有跨服务调用传播 trace 上下文，但不得把完整会话或不必要的个人数据写进日志。

## 3. 身份、租户与策略边界

身份和权限必须由可信网关/身份服务签发，模型输出不能授予自己权限。统一 `RequestContext` 至少包括：主体、租户、角色/属性、允许的数据域、语言/时区、风险标签、策略版本、请求追踪 ID。

- 在入口验证用户、租户、会话和资源授权。
- 检索前按租户及 ACL 过滤，检索后再次验证返回项权限。
- 工具调用时重新授权，不能只依赖早期检查结果。
- 缓存键绑定租户、权限范围指纹、数据版本、模型/提示版本及查询指纹。
- 日志、队列、Redis key、对象存储路径和指标标签遵循租户隔离；避免高基数标签泄露敏感标识。
- 跨租户管理和紧急访问应有独立审批、短期授权及审计记录。

策略服务对每个动作返回明确决定：`ALLOW`、`DENY`、`REQUIRE_APPROVAL`、`DEGRADE`。拒绝原因使用稳定错误码，避免把内部策略细节泄漏给终端用户。

## 4. Agent Runtime 状态机

持久化并返回给调用方的任务状态，与《Agent 应用开发全流程》第 4.1 节同一套：

`queued`、`running`、`waiting_approval`、`waiting_tool`、`succeeded`、`failed`、`cancelled`、`timed_out`、`handed_off`。

`cancelled` 表示用户或系统明确取消。`timed_out` 表示 deadline 到期。两者分开记录。预算耗尽记 `failed`，原因码 `budget_exceeded`。`waiting_approval` 期间不执行写操作。批准绑定预览摘要、操作者和有效期。

阶段只写入 Trace，不作为任务状态返回：

```text
received → authorized → classifying → planning → executing
        → validating → merging → responding
```

高风险写操作在 `planning` 或 `merging` 之后把任务状态改为 `waiting_approval`，阶段停在进入审批前的那一个。`executing` 是阶段名。任务状态里对应的值是 `running` 或 `waiting_tool`。

每次任务状态迁移由 Runtime 持久化，并记录 `fromState`、`toState`、原因、时间、策略/配置版本。迁移要具备幂等性；重复事件不重复执行副作用。每个阶段开始前及工具调用前检查：取消标记、deadline、剩余预算、Kill Switch、审批状态、策略版本有效性。

外部工具已经成功但响应丢失时，进入结果核对和幂等查询，见《Agent 应用开发全流程》第 4.6 节。终态不被普通重试改写。新尝试创建新的 attempt 或 run，并关联原 trace。

## 5. 记忆与上下文管理

| 类型 | 典型内容 | 建议载体 | 生命周期/边界 |
|---|---|---|---|
| 工作记忆 | 当前轮、计划、子任务状态、工具结果 | KV/工作流状态库 | run 级，按保留策略清理 |
| 会话记忆 | 近期对话、用户确认事项 | 会话库/摘要 | 受用户/租户权限控制 |
| 长期偏好 | 经用户允许保存的偏好 | Profile KV/文档库 | 可查看、修正、删除 |
| 业务知识 | 文档、记录、事实 | RAG、图谱、Wiki | 来源、ACL、版本、有效期 |
| 策略记忆 | 风险阈值、允许工具、预算 | 策略/配置中心 | 版本化，运行时快照 |

采用 Just-in-Time 投递：先给子任务最小必要输入，执行过程中按需补充检索片段。历史长对话优先摘要并保留来源引用；摘要不能替代原始证据。明确区分用户声明、系统事实、模型推断和待确认内容，减少记忆污染。

## 6. 意图识别与路由

识别结果应是结构化数据，不是自由文本。建议分层：规则和确定性校验 → 轻量分类/抽取 → 低置信或多义时调用 LLM 复核 → Schema 校验 → 路由策略。

需识别：领域、任务类型、一个或多个意图、风险等级、实体、槽位、缺失参数、所需知识域/工具、是否需追问/审批。高风险动作即使分类置信度很高仍须走策略与审批。

示例（置信度由校准后的分类器输出）：

```json
{
  "domain": "customer_service",
  "taskType": "multi_step",
  "riskLevel": "medium",
  "intents": [{"name": "refund_eligibility", "confidence": 0.91}],
  "entities": {"orderId": "123"},
  "slots": {"orderId": "123", "policyScope": null},
  "missingSlots": ["policyScope"],
  "route": "refund_readonly",
  "needClarification": true,
  "needApproval": false
}
```

初始路由可用双阈值：高于校准阈值自动进入规划；中间区间用澄清或低风险路径；低于下限时追问/转人工。具体阈值按领域分别校准。缓存意图时需绑定租户、权限与分类器版本，避免把上下文不同的请求误命中。

## 7. 规划、任务契约与并行调度

规划器输出可校验的 DAG，不输出未经校验即可执行的自然语言指令。Runtime 对计划做静态检查：任务数、依赖环、工具白名单、权限、风险、超时、预算、并行度、输出 Schema 和人工门。

### 7.1 TaskSpec 契约

```json
{
  "taskId": "task-02",
  "type": "knowledge_lookup",
  "dependsOn": [],
  "parallelGroup": "read-1",
  "inputRefs": ["intent.orderId"],
  "contextRefs": ["wiki:refund-policy"],
  "allowedTools": ["wiki.search", "order.read"],
  "timeoutMs": 8000,
  "tokenBudget": 1200,
  "costBudget": 0.02,
  "riskLevel": "low",
  "sideEffect": "none",
  "needApproval": false,
  "idempotencyKey": null,
  "retryPolicy": {"maxAttempts": 2, "retryableCodes": ["UPSTREAM_TIMEOUT"]},
  "outputSchema": "RefundLookupResult/v1"
}
```

预算单位应在平台统一（例如 USD 等值或内部 cost unit），并明确汇率/模型价格版本。任务只能访问列明的工具和上下文引用。DAG 可并行的独立读取任务并行执行；依赖任务等待上游结果通过验证。

### 7.2 子 Agent 隔离与通信

主编排器派发任务，子 Agent 不直接互相调用。通信通过任务队列/工作流引擎/状态库；事件至少含 `tenantId`、`runId`、`taskId`、attempt、schemaVersion、deadline、trace context。队列消费需幂等，死信队列需有告警和人工处理路径。

每个子 Agent 使用独立 `subRunId`，只获得经授权的最小上下文和工具集合。共享事实以有来源的结构化对象传递，不共享整段对话。子任务输出在校验、权限复核和可用性判断前不得直接展示给用户。

## 8. 知识层：RAG、Ontology、图谱与 LLM Wiki

### 8.1 RAG 流程

Query 规范化/改写 → ACL 与租户过滤 → 混合召回（关键词/向量）→ 去重 → Rerank → 新鲜度与来源检查 → 片段组装 → 带引用注入。过滤条件应尽可能在召回前应用，召回后再次检查。缓存绑定 ACL、租户、知识快照和索引版本。

### 8.2 Ontology 与知识图谱

Ontology 定义实体类型、属性、关系、约束；图谱保存可追溯的实体关系和来源。图谱推断必须保留推理路径和来源，不能把推断边伪装成原始事实。它们用于实体消歧、关系查询、约束校验和冲突检测，与文本检索互补。

### 8.3 LLM Wiki

LLM Wiki 是经过治理的模型可消费知识层，强调原子化、适用范围、权威来源、版本与时效，不等同于把文档摘要堆在一起。

词条建议字段：`wikiId`、类型、标题、定义/规则、适用范围、租户/ACL、owner、版本、状态、有效期、来源引用、关联实体、置信/审核状态、创建/更新记录。发布状态采用 `draft → review → published → deprecated/archived`。冲突规则应声明权威级别和有效期，无法消解时显式返回冲突，不让模型自行猜测。

候选知识可从工单、文档、代码注释等提取，但发布前需来源校验、去重、权限检查和审核。线上坏例先进入候选队列，不自动覆盖正式规则。检索返回 Wiki 条目时附带版本、适用范围和 sourceRefs。

## 9. Tools / MCP 执行与写操作事务

工具通过 Tool Gateway 注册，声明输入/输出 Schema、所需权限、风险等级、副作用、超时、幂等能力、重试语义和数据分类。执行顺序：生成调用提案 → Schema 校验 → 授权/策略判定 → 参数脱敏检查 → 幂等检查 → 调用 → 响应校验 → 记录审计与结果。

### 9.1 写操作生命周期

```text
DRAFT → PREVIEW → PENDING_APPROVAL → APPROVED → COMMITTING → COMMITTED
                                      ↘ REJECTED / EXPIRED
```

预览绑定目标资源、变更内容摘要、策略版本和有效期；确认后再次验证权限、对象版本和预算。提交使用服务端生成的幂等键并保存外部系统回执。关键动作采用事务 Outbox / Saga 等适合业务系统的模式；跨系统操作通常不是单一 ACID 事务。

- 对可补偿操作定义补偿步骤；对不可补偿操作明确标注并提高审批级别。
- 超时后先查询幂等键/外部结果，再决定重试，避免重复扣款、重复发信或重复建单。
- 已提交操作不可因用户取消而宣称已回滚；取消只阻止尚未提交的动作。
- 审计保存操作者、审批者、预览摘要、参数摘要、幂等键、外部回执和时间。

## 10. 结果契约、可用性判定与合并

### 10.1 SubAgentResult

```json
{
  "taskId": "task-02",
  "status": "succeeded",
  "schemaVersion": "1",
  "structuredData": {"eligible": true},
  "confidence": 0.88,
  "citations": [{"sourceId": "wiki:refund-policy@3.2", "span": "section-4"}],
  "warnings": [],
  "errorCode": null,
  "latencyMs": 412,
  "cost": 0.004,
  "usableScore": 0.82
}
```

评分仅用于排序/路由，不能代替硬性校验。建议由任务匹配、Schema 完整度、来源权威性、时效性、权限合规分别评分；权限失败、无来源的强事实、Schema 不合法、过期政策等属于硬拒绝条件，不应被高总分抵消。

建议动作区间（需业务校准）：高分且通过硬校验则使用；中间分数补证/降级并标注；低分重试、换源、追问或转人工。重试必须有上限和可重试错误码。

### 10.2 合并策略

- 权威来源优先：已发布且适用的策略/Wiki、业务系统事实、一般文档、模型推断按业务定义的来源等级排序。
- 事实冲突时保留来源、版本、时间和适用范围；不能用简单多数票覆盖权威系统。
- 部分成功只陈述已验证部分，并指出缺失部分，不暗示任务整体成功。
- 汇总器输入仅限通过校验的结果；输出再次执行引用完整性、权限和安全检查。
- 引用必须能定位到实际来源片段或工具回执，不生成虚构引用。

## 11. 错误处理、重试、取消与降级

对外错误码只有《Agent 应用开发全流程》第 0.2 节那一组，常量源在《Agent 开发语言》6.11。内部原因可以更细，映射到对外码：鉴权失败 → `unauthorized`；策略拒绝 → `policy_denied`；限流 → `rate_limited`；预算耗尽 → 任务状态 `failed` 且错误码 `budget_exceeded`；用户取消 → 任务状态 `cancelled`；run 的 deadline 到期 → 任务状态 `timed_out`。子任务内部码见契约文档附录 B.5，不原样返回给调用方。

| 情况 | 处理原则 |
|---|---|
| 网络/限流 | 有界指数退避+抖动，遵守 deadline 和重试预算 |
| 参数/Schema 错误 | 可让模型修正一次；仍失败则终止，不无限循环 |
| 权限拒绝 | 不重试，不绕过；按用户可理解方式说明 |
| 工具不可用 | 备用只读源或部分答案；禁止默默伪造结果 |
| 子任务超时 | 取消未启动依赖，保留其他已验证结果 |
| 证据冲突 | 提示冲突/追问/转人工，不强行拼成单一事实 |
| 预算耗尽 | 停止新增调用，按策略输出已验证部分或失败 |

取消流程：写取消事件 → Runtime 传播至队列和可取消工具 → 阻止后续副作用 → 记录哪些步骤已完成/不可取消 → run 标记终态。每个工具应声明取消能力。

## 12. 成本、延迟与容量治理

在 run 级预算内预留各阶段额度，再向 task 分配 `tokenBudget`、`costBudget`、deadline。设软阈值触发模型降级、减少并行/检索量；硬阈值停止非必要调用并禁止新写操作。百分比（如 80% 软阈值）仅为初值，按延迟和任务成功率校准。

治理项：模型分层路由、上下文压缩、工具调用上限、检索缓存、并发池隔离、租户配额、供应商限流、超预算熔断。成本账单按 trace 归集模型输入/输出 token、检索、工具和重试开销；价格与模型版本留档。异常告警不得只按平均值，应观察高分位和租户异常。

## 13. 审批与风险分级

风险策略应明确动作类别和责任主体，而非只依赖模型给出的风险标签。

- 只读低风险：可自动执行，保留来源和访问审计。
- 可逆低影响写：按租户策略允许自动化，必须幂等并记录审计。
- 中高影响写：展示预览，用户或授权审批者确认后执行。
- 高危/不可逆动作：强制人工审批；关键生产变更可要求双人审批。

审批绑定内容摘要和版本；预览改变、对象版本变化、审批过期或策略更新时必须重新审批。

## 14. 安全、隐私与合规

按输入、检索、规划、工具、输出、知识治理各阶段防御提示注入、数据外泄、越权代理、敏感信息、供应链风险。外部文档内容视为不可信数据，不能升级为系统指令。工具使用最小权限、短期凭证和明确网络边界；密钥不进入模型上下文或普通日志。

配套控制包括 IAM/ABAC、数据分类与脱敏、审计、密钥轮换、工具清单与签名/来源审查、红队测试、回归测试、紧急 Kill Switch。将适用的 OWASP LLM 风险分类映射到具体控制与测试用例，持续更新版本，不只把安全要求写入 Prompt。

## 15. 可观测性、审计与版本治理

### 15.1 追踪

每个 trace 记录阶段耗时、状态迁移、模型/提示版本、知识快照、检索引用 ID、子任务、工具名/版本、策略决策、预算消耗、审批记录和最终合并来源。敏感输入/输出采用最小化、脱敏、访问控制和保留期限策略。

### 15.2 版本快照

trace 必须可还原：模型及参数、Prompt、Agent/Skill、MCP 工具契约、知识索引/Wiki 快照、策略、分类器、合并器版本。部署按版本灰度；回滚时保留历史 run 的原始版本记录。

### 15.3 指标与 SLO

监控任务成功率、意图误路由率、引用可用率、工具成功率、重试率、人工接管率、越权拦截、成本、P50/P95/P99 延迟。按租户和任务类型拆分，但防止高基数和敏感标签。为关键链路定义 SLO、错误预算和告警责任人。

## 16. 评估与知识治理闭环

- **离线**：黄金集覆盖意图、槽位、检索、引用、工具参数、写操作边界、冲突合并和安全攻击。
- **影子/灰度**：先影子评估，再小流量只读能力，逐步扩大；写能力单独放量。
- **在线**：规则和人工抽样评估正确性、引用、风险、延迟、成本、满意度；LLM Judge 仅作辅助信号。
- **回流**：用户负反馈和失败 trace 进入脱敏、去重、审核后的候选队列；更新评测集/Wiki/Prompt 需版本化审批。

任何指标优化都要同时观察安全、成本与用户体验，避免用单一“答案正确率”驱动系统行为。

## 17. 部署、弹性与故障演练

支持云端、私有化或混合部署时，逐项标明数据驻留、模型边界、工具网络边界、日志落点、租户隔离方式和灾备目标。Redis/队列/向量库/模型服务需定义容量、备份、恢复和降级行为。

定期演练模型限流、工具超时、队列积压、Redis 不可用、知识索引落后、审批系统故障、取消风暴、成本突增。验证告警、隔离、降级和恢复，而不只验证正常路径。

## 18. 灰度发布与 Kill Switch

按模型、Prompt、工具、知识版本分别灰度。建议阶段：离线回归 → 影子流量 → 内部/白名单 → 低比例只读 → 扩量 → 受控写操作。每阶段设成功率、延迟、成本、安全事件回退门槛。Kill Switch 可按租户、工具、模型或写操作类型禁用，并保留只读安全路径（若策略允许）。

## 19. 推荐初始阈值与调参方法

| 项目 | 初始建议 | 校准方法 |
|---|---|---|
| 意图置信度 | 高/中/低三段，不跨领域共用单阈值 | 各领域黄金集、置信度校准、误路由成本 |
| 子任务重试 | 仅可重试错误，最多少量尝试 | 成功率、重复副作用风险、尾延迟 |
| 结果可用性 | 评分辅助；权限/Schema/引用设硬门槛 | 人工标注集与业务损失函数 |
| 预算软阈值 | 预算消耗接近上限时降级 | 质量-成本曲线、租户配额 |
| 预算硬阈值 | 达上限停止新增调用/写操作 | 预算账单一致性与熔断演练 |
| deadline | 按交互式/后台任务分层配置 | P95/P99 延迟及依赖 SLA |

上线前对阈值做离线回放和影子流量校准；上线后按版本记录变化，禁止无审计地在线自调高风险阈值。

## 20. MVP 到生产的实施顺序

1. **MVP**：单租户/清晰 ACL、只读 RAG、单 Agent、结构化工具契约、trace 与基础限流。
2. **受控多任务**：DAG、子任务状态、超时/取消、预算上限、结果 Schema 与引用校验。
3. **知识治理**：LLM Wiki 生命周期、版本快照、冲突/过期处理、坏例候选审核。
4. **受控写操作**：预览审批、幂等提交、结果核对、补偿策略、完整审计。
5. **生产韧性**：多租户隔离、灰度/回滚、SLO、压测和故障演练、红队回归。

## 21. 运行排障顺序

从 `traceId` 检查：入口鉴权/限流 → 策略决策 → 意图与槽位 → DAG 合法性 → 预算/deadline → 上下文来源 → RAG/Wiki ACL、版本、召回 → 子任务队列/重试 → 工具参数、权限、幂等和回执 → 结果 Schema/证据 → 合并冲突 → 审批 → 输出过滤 → 审计/评估回流。
