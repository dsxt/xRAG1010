# 一次用户请求从前端进来，到最终返回、再到上线治理和排查
### 1. 请求进入：网关与上下文组装

用户在前端输入消息后，请求先到达 **AI Gateway / Agent API**。这一层负责：

- **鉴权**：校验 `userId`、`tenantId`、角色权限。
- **限流熔断**：控制 QPM/TPM，防止模型、工具、RAG 被打爆。
- **安全前置拦截**：对输入做违禁词、提示词注入、恶意指令检测。
- **路由**：决定走哪个 Agent、哪个模型、哪个知识库、哪套工具集。
- **生成 traceId / runId**：后续所有日志、指标、评估都挂在这个 ID 上。

同时会拉取当前会话的历史消息、用户偏好、任务状态，组装成 `AgentContext`。这里通常不会只靠内存，而是用外部存储承载会话状态，方便断点续跑、横向扩展和异常恢复。

### 2. 记忆加载：短期记忆 + 长期记忆 + 用户画像

进入 Agent Runtime 后，先补上下文。

| 记忆类型 | 典型内容 | 存储方式 |
|---|---|---|
| 短期工作记忆 | 当前轮次对话、已执行步骤、工具返回 | Redis / 会话存储 |
| 长期记忆 | 用户偏好、历史任务结论、常用模板 | 向量库 / KV / 文档库 |
| 业务记忆 | 订单、工单、文档、知识库片段 | RAG / 知识图谱 / 本体库 |
| 策略记忆 | 权限、黑白名单、风险阈值 | 配置中心 / 策略服务 |

Redis 在这里通常承担：会话缓存、运行状态锁、取消信号、分布式限流、工具执行状态、重试计数器、幂等键、Pub/Sub 取消广播。

### 3. 安全与策略校验

在真正调用模型之前，先做一次“能不能答、能不能做”的判断：

- 用户是否有权访问该知识库或工具；
- 请求是否包含敏感词、越权指令、注入攻击；
- 当前场景是否允许自动执行写操作；
- 是否需要人工确认，比如删除数据、发送邮件、调用支付接口；
- 是否命中成本控制策略，例如高成本任务需要先降级为规划模式。

这一步很关键：**模型负责生成，策略层负责边界**。不能把权限、合规、业务规则完全交给模型判断。

### 4. Agent Runtime 启动 ReAct / Plan-Execute 循环

Agent 拿到上下文后，进入主循环：

1. **Think**：模型根据目标、历史、工具列表，决定下一步做什么。
2. **Act**：执行工具调用、RAG 检索、代码执行、MCP 调用等。
3. **Observe**：把执行结果写回上下文，判断是否继续、重试、降级或结束。
4. **Reflect**：检查结果是否可信，是否需要修正计划。

循环必须有保护：

- 最大迭代次数；
- 最大 Token 预算；
- 最大工具调用次数；
- 超时控制；
- 重复动作检测；
- 死循环熔断；
- 用户取消信号检查。

### 5. RAG / 知识库：语义检索 + 知识图谱 + Ontology

如果任务需要查资料，Agent 会触发 RAG 链路。

#### 5.1 语义检索

用户 Query 先经过改写、分词、向量化，再进入向量库检索。这里会做：

- Query 扩展；
- 同义词补全；
- 时间范围过滤；
- 权限过滤；
- Top-K 召回；
- Rerank 精排。

#### 5.2 知识图谱 / Ontology

语义检索解决“哪些片段相似”，本体和知识图谱解决“这些实体之间是什么关系”。

- **Ontology**：定义实体类型、属性、关系、约束，比如“用户—订单—商品—售后单”的关系。
- **知识图谱**：存储实体关系，支持路径查询、依赖推断、冲突检测。
- **语义圈**：可以理解为围绕某个实体或意图形成的相关实体、文档、事件、工具能力的集合。

更成熟的系统会把三者结合起来：先用语义检索召回候选片段，再用图谱/本体做实体对齐、权限校验、关系推理，最后把结构化事实和非结构化片段一起注入上下文。

#### 5.3 知识库持续治理

RAG 不是一次性接入，治理重点包括：

- 文档去重、版本管理、过期清理；
- Chunk 策略评估，避免切得太碎或太长；
- Embedding 模型版本管理；
- 召回率、命中率、Rerank 效果监控；
- 坏例回流：线上错误问题自动进入评测集；
- 权限隔离：不同租户、部门、角色看到不同知识；
- 数据血缘：知道答案来自哪篇文档、哪个版本。

### 6. MCP / Tools / Skills 调用

当模型决定调用外部能力时，会经过 MCP 或工具注册中心。

- **MCP**：统一管理工具发现、参数 Schema、权限、调用协议和错误返回。
- **Tools**：具体能力，比如查数据库、调 API、搜索、发邮件。
- **Skills**：更高层的复合能力，比如“生成周报”“排查告警”“同步多端配置”。

调用流程通常是：

1. Agent 输出结构化调用提案；
2. Runtime 校验参数 Schema；
3. 策略层检查权限和风险等级；
4. 真正执行工具；
5. 捕获超时、权限不足、格式错误；
6. 把结果结构化写回上下文；
7. 如果失败，进入重试或兜底。

这里要避免模型直接访问生产系统。所有写操作最好经过适配器层，并且对高危动作加人工确认。

### 7. Redis 在 Agent 里的具体用法

Redis 不只是缓存，它在 Agent 运行时里承担很多工程职责：

- **会话状态**：保存当前 run 的上下文、已执行步骤、工具结果。
- **取消信号**：用户取消或输入新消息时，写入 `stop_flag`，循环每步检查。
- **幂等控制**：防止同一次工具调用被重复执行。
- **重试计数**：记录某个工具或模型调用失败次数。
- **分布式锁**：避免多个实例同时修改同一会话。
- **限流**：按用户、租户、工具维度做 QPM 控制。
- **事件广播**：用 Pub/Sub / Stream 通知前端、子 Agent、任务调度器。

### 8. 失败重试、兜底与降级

Agent 的失败不能简单抛异常，需要分类处理。

| 失败类型 | 处理方式 |
|---|---|
| 网络超时 | 指数退避重试，限制最大次数 |
| 参数错误 | 把错误信息返回给模型，让它修正参数 |
| 权限不足 | 不重试，直接提示需要授权 |
| 工具不可用 | 切换到备用工具或降级回答 |
| 模型输出格式错误 | 触发格式校验重试 |
| 死循环 | 达到最大步数后强制终止 |
| 成本超限 | 停止继续调用，返回部分结果或摘要 |

兜底策略包括：

- 返回更保守的答案；
- 只给出可验证的事实和来源；
- 转人工；
- 关闭自动执行，只保留建议模式；
- 触发 Kill Switch，直接阻断高风险 Agent。

### 9. 用户取消、立即输入新消息

用户取消或输入新消息时，系统不能只在前端“清屏”。后端需要：

1. 前端发送取消事件；
2. 写入 Redis 取消标记；
3. Runtime 在每次循环开始前检查标记；
4. 立即停止未开始的工具调用；
5. 对正在执行的工具尝试中断或标记为可丢弃；
6. 对已完成的写操作记录审计日志，不能自动回滚业务数据；
7. 把新消息作为新 run 的起点，同时保留旧 run 的 trace，方便复盘。

这里有一个重要边界：**已落库的写操作不能随意撤销**。系统只能停止后续动作，并把状态标记为“用户中断”。

### 10. 违禁词与安全拦截

安全拦截通常放在三层：

- **输入层**：检测敏感词、越权指令、提示词注入、恶意代码。
- **执行层**：限制工具权限、沙箱执行、禁止访问未授权资源。
- **输出层**：检测泄露、违规内容、幻觉高风险表达。

对于企业系统，还要区分：

- 硬拦截：明确违规，直接拒绝；
- 软拦截：风险较高，需要人工确认；
- 审计拦截：允许执行，但必须留痕。

### 11. 可观测：Trace、Metrics、Logs、Eval

Agent 的问题往往不在最后那句回答，而在中间某一步决策偏了。所以需要把一次请求拆成多层可观测数据。

- **Trace**：一次请求对应一个 traceId，内部每个 LLM 调用、RAG 检索、工具调用都是一个 span。
- **Metrics**：延迟、成功率、重试率、Token 消耗、工具失败率、幻觉率、用户负反馈率。
- **Logs**：记录 Prompt、工具入参出参、RAG 召回片段、权限决策、错误堆栈。
- **Eval**：离线黄金集回归测试，线上采样打分，坏例回流到测试集。

排查线上问题时，通常按这条链看：

`用户输入 → 安全拦截 → 记忆加载 → RAG 召回 → 模型规划 → 工具调用 → 结果校验 → 最终回答`

如果回答错了，先看 RAG 是否召回了错误材料；如果工具调用失败，看是参数问题、权限问题还是下游故障；如果模型反复调用同一工具，看是否缺少终止条件。

### 12. 上线灰度、回退与 Kill Switch

Agent 上线不能直接全量。常见灰度方式：

- **影子模式**：用线上流量跑，但不返回给用户，只对比效果。
- **白名单灰度**：先给内部用户或小比例用户开放。
- **流量灰度**：按 1%、5%、20% 逐步放量。
- **能力灰度**：先开放只读能力，再开放写操作。
- **模型灰度**：同一 Agent 切换不同基座模型或 Prompt 版本。

回退方案包括：

- 一键回滚到上一个稳定 Prompt / 工具集 / 模型版本；
- 一键降级为纯问答模式，关闭自动工具调用；
- Kill Switch 直接阻断 Agent 路由；
- 对写操作关闭自动执行，改为人工审批。

### 13. 线上问题排查清单

遇到线上问题时，可以按这个顺序查：

1. 看 traceId，确认完整链路是否完整；
2. 看用户输入是否被安全策略误拦；
3. 看历史记忆是否被污染或缺失；
4. 看 RAG 召回内容是否正确、是否过期；
5. 看知识图谱/本体是否缺少关键实体关系；
6. 看模型是否生成了错误工具调用；
7. 看 MCP/Tool 是否返回异常或超时；
8. 看 Redis 中是否有取消信号、重试风暴或锁竞争；
9. 看成本是否触发降级；
10. 看评估系统里是否有类似坏例回归失败。

### 14. 一条完整请求的典型路径

综合起来，一条请求大致这样走：

`前端输入 → API 网关鉴权/限流/安全拦截 → 生成 traceId/runId → 加载短期会话记忆和长期用户记忆 → 查询 RAG / 知识图谱 / Ontology → 模型规划下一步 → 通过 MCP 调用 Tools/Skills → Redis 记录状态、重试、取消信号 → 校验工具结果 → 继续循环或直接生成回答 → 输出层安全过滤 → 返回前端 → 写入 Trace/Metrics/Logs → 采样进入评估集 → 坏例回流治理知识库和 Prompt`

如果要把这套链路落到 Python 工程里，可以按 `gateway / policy / context_builder / rag_adapter / mcp_tool_adapter / agent_runtime / session_store / eval_pipeline` 分层实现，面试或简历里也更容易讲清楚边界。
