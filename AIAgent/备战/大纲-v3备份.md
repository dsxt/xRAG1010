## 2. Tier 1｜准入硬核基础

### 2.1 LLM 推理底层基础（CUDA 主线）

#### 核心知识点

**基础概念层**
- token、BPE 分词、上下文窗口、RoPE / ALiBi 位置编码、位置外推（NTK / YaRN）
- 特殊 token、chat template、system prompt 拼接对指令跟随的影响

**KV Cache（重中之重）**
- prefill 阶段（并行计算全 prompt，计算密集）vs decode 阶段（逐 token 生成，访存密集）
- KV 布局：`[layer][kv_head][seq_len][head_dim]`
- 显存占用估算公式：
  ```
  KV 显存 ≈ 2 × num_layers × num_kv_heads × head_dim × seq_len × batch × dtype_bytes
  （GQA 场景 num_kv_heads < num_attention_heads，这是省显存的关键）
  ```
- KV 失效场景：换模型、换 system prompt 前缀、上下文被裁剪、swap 回收
- 连续批处理（continuous batching）本质：以 **iteration** 为调度粒度而非以 request 为粒度

**采样策略**
| 参数 | 作用 | Agent 场景建议 |
| --- | --- | --- |
| temperature | 分布锐化/平滑 | 规划、工具选择用 0~0.3；创意生成 0.7~0.9 |
| top_p | 核采样截断 | 与 temperature 二选一调，不要同时激进 |
| top_k | 硬截断候选 | 结构化输出场景可收紧 |
| repetition penalty | 抑制重复 | 过高会破坏 JSON / 代码结构 |
| stop sequences | 提前终止 | 工具调用场景必须精确配置，否则解析错乱 |

**流式**
- SSE 协议格式、`data: [DONE]` 终止、chunk 边界不完整问题
- partial tool call 流式解析：`function.arguments` 是逐字符拼接的 JSON 字符串，必须等 `finish_reason=tool_calls` 后整体解析
- SSE 背压：客户端消费慢导致服务端缓冲区堆积；需用有界队列 + 丢弃策略

**量化**
| 格式 | 精度损失 | Agent 适用性 |
| --- | --- | --- |
| BF16 / FP16 | 基线 | 全场景可用 |
| FP8（E4M3/E5M2） | 小 | Hopper/Ada 原生支持，性价比最佳 |
| AWQ / GPTQ INT4 | 中 | 工具调用格式错误率上升，需回归测试 |
| INT4 激进量化 | 大 | 长上下文、复杂推理明显退化，不建议做规划 Agent |

- 量化损伤的观测点：JSON schema 遵循率、工具参数幻觉率、长上下文中间信息遗忘率

**推理引擎**
- vLLM：PagedAttention（分页 KV 管理，消除显存碎片）、Block Manager、prefix caching、chunked prefill
- SGLang：RadixAttention（前缀树共享 KV）、多轮对话天然复用、结构化输出约束解码（基于正则/JSON schema 的 logit 掩码）
- 关键参数：`gpu_memory_utilization`、`max_model_len`、`max_num_seqs`、`swap_space`、`block_size`、`enable_prefix_caching`
- 排障工具：`nvidia-smi`（显存与利用率）、`nsys` / `ncu`（kernel 耗时）、vLLM metrics（TTFT、TPOT、队列深度）

#### 高频面试题
1. PagedAttention 解决了什么问题？和传统连续 KV 分配的区别？
2. 同一会话多轮工具调用，KV Cache 何时复用、何时失效？prefix caching 命中条件是什么？
3. prefill 和 decode 的瓶颈分别在算力还是带宽？为什么？
4. 7B / 13B / 70B 在 Agent 系统里如何分配角色（路由 / 执行 / 规划）？
5. 量化后工具调用成功率下降，你怎么定位是量化导致还是 prompt 导致？

#### 差异化输出点
- CUDA 上部署 vLLM / SGLang 的实操参数、压测方法（并发梯度下的 TTFT / TPOT 曲线）
- FP8 在 Ada 与 Hopper 上的性能差异实测
- 显存碎片化成因与 `expandable_segments` 等缓解手段

### 2.2 Agent 基础范式与编排

#### 核心范式
| 范式 | 机制 | 适用 | 风险 |
| --- | --- | --- | --- |
| ReAct | Thought → Action → Observation 循环 | 通用工具型任务 | 无限循环、动作漂移 |
| CoT | 单轮长推理链 | 数学、逻辑 | 无外部反馈 |
| Self-Consistency | 多次采样投票 | 高准确率要求的单点判断 | 成本 ×N |
| Plan-and-Execute | 先出完整计划再执行 | 步骤可预判的结构化任务 | 计划不可动态修正 |
| Reflexion | 执行后自我反思再重试 | 有明确成功判据的任务 | 反思幻觉，越改越错 |
| Self-Ask | 自问自答拆解子问题 | 多跳问答 | 子问题发散 |

#### LangGraph 核心
- **State**：TypedDict / Pydantic 定义，支持 reducer（如 `add_messages`）实现增量合并
- **节点与边**：普通边、条件边（`add_conditional_edges`）、`Send` 实现 map-reduce 并发分发
- **Checkpoint**：每个 super-step 落盘；`thread_id` 隔离会话；支持 `get_state` / `update_state` 人工干预
- **中断**：`interrupt()` 实现 human-in-the-loop，恢复时重放节点
- **子图**：能力复用与命名空间隔离
- **常见坑**：
  - State 过大 → checkpoint 序列化开销爆炸（尤其存了全量文档）
  - 条件边无终止条件 → 死循环
  - `interrupt` 前后的非幂等副作用会被重复执行

#### LangChain
- Runnable 协议（`invoke` / `batch` / `stream`）、LCEL 组合、Callback 事件
- 痛点：抽象层过厚、调试困难、版本破坏性变更频繁
- 判断标准：快速原型用 LangChain；生产核心链路手写编排更可控

#### 高频面试题
1. 怎么防止 ReAct 无限循环调用工具？至少给出三种终止策略（轮次上限、状态重复检测、目标达成校验、成本预算熔断）
2. LangGraph checkpoint 存 Redis，State 很大怎么办？（分离冷热状态、只存引用、大对象外置对象存储）
3. human-in-the-loop 在生产中怎么设计权限、超时、重试、审计？

### 2.3 Function Calling / Tool System

#### 核心知识点
- **Structured Output**：OpenAI `response_format` / JSON Schema、约束解码、失败重试策略
- **Schema 描述词工程**：
  - 工具名用动词短语，参数名用业务语义而非技术缩写
  - `description` 写清「何时用、何时不用」，比写「是什么」更能降低误调用
  - enum 优先于自由文本，减少参数幻觉
- **工具层架构**：
  - 工具注册中心（name → handler + schema + 权限标签 + 版本）
  - Pydantic 强校验（类型、范围、正则、跨字段约束）
  - 工具版本管理（schema 变更必须版本化，否则旧 prompt 全部失效）
- **执行治理**：
  - 超时（分级：快工具 5s / 慢工具 60s / 长任务异步化）
  - 重试（仅幂等工具可自动重试，且需指数退避）
  - 熔断（连续失败 N 次摘除工具，避免拖垮整轮）
  - 结果裁剪：截断、摘要、结构化提取
  - **Observation Masking**：可重新执行的输出（文件内容、目录列表、重复查询）直接丢弃，成本最低且不引入摘要幻觉
- **并行与依赖**：并行工具调用、工具依赖 DAG、结果冲突校验（同一实体被两个工具改写）
- **高危工具防护**：
  - SQL Agent：禁止 DDL/DML、白名单表、行数上限、只读账号、结果脱敏、注入检测
  - 代码沙箱：e2b / Modal / Firecracker 隔离，禁网或白名单出网，资源限额

#### 高频面试题
1. 模型频繁输出不符合 schema 的工具调用，分层解法？（约束解码 → schema 简化 → few-shot 示例 → 服务端校验回灌错误信息 → 降级到文本解析）
2. 工具返回超大文本撑爆上下文，有哪些方案、各自代价？
3. 并行工具调用时，两个工具改同一资源怎么处理？

### 2.4 RAG 全链路工程

#### 链路拆解
| 阶段 | 关键技术与坑 |
| --- | --- |
| 解析 | PyMuPDF、MarkItDown、布局分析（标题层级）、表格结构化抽取、扫描件 OCR、公式与图片处理 |
| 清洗 | 页眉页脚去重、乱码修复、跨页段落合并、编码统一 |
| 分块 | 固定块、滑动窗口重叠、语义分块（embedding 相似度断点）、分层分块（父块检索子块召回）、摘要先行分块 |
| 元数据 | 来源、页码、权限标签、更新时间、版本号（缺了这些后面全链路都做不了） |
| Embedding | BGE / E5 / Jina；归一化；cosine vs dot；模型版本变更必须全量重建 + 双写灰度 |
| 索引 | HNSW（`M` / `ef_construction` / `ef_search` 权衡）、IVF（`nlist` / `nprobe`）、量化 PQ |
| 检索 | BM25 + 向量 Hybrid、RRF 融合（`k=60`）、metadata 过滤、多路召回 |
| 重排 | BGE-Reranker / Jina Reranker；TopN 召回 → 精排 TopK；延迟敏感场景用轻量 cross-encoder |
| 上下文组装 | 去重、按相关度排序、token 预算分配、引用标注 |
| 生成 | 强制引用、拒答策略（检索为空时不许编） |

#### 高级策略
- Query 改写：多轮对话中的指代消解、口语转检索语言
- Query 分解：多跳问题拆子查询，分别检索再融合
- 多轮 RAG：对话历史感知检索（不是简单拼接历史）
- 图 RAG：实体/关系抽取 → 图谱查询 → 子图序列化进上下文
- 自适应检索：先判断是否需要检索（避免闲聊也走检索）

#### 高频面试题
1. RAG 召回差，完整排查链路？（分块 → embedding 模型匹配度 → 索引参数 → 过滤条件 → query 改写 → 是否该用 hybrid）
2. Hybrid Search 什么时候收益明显，什么时候没必要？
3. 文档持续更新，向量库一致性怎么保证？（版本号 + 增量 upsert + 软删除 + 定期全量重建）

### 2.5 后端、中间件、容器 + React 前端

#### 后端
- **FastAPI**：`async/await` 陷阱（同步阻塞调用会卡住事件循环）、依赖注入、BackgroundTasks、SSE（`StreamingResponse`）、中间件、连接池
- **Redis**：String/Hash/List/ZSet/Stream、TTL、`SETNX PX` 分布式锁、Lua 原子脚本、Redis Stack HNSW
- **MQ**：Kafka（分区顺序、消费组、幂等）、RabbitMQ（ACK、死信、延迟队列）；异步长任务必用
- **DB**：PostgreSQL（PGVector、行级权限）、MySQL；事务隔离、索引、慢查询
- **容器**：Docker 多阶段构建、K8s Pod/Deployment/Service/HPA/ConfigMap、GPU 资源声明（`nvidia.com/gpu`）

#### React 前端（差异化标签）
**用途**：Agent 调试控制台、会话回放、Langfuse Trace 可视化、工具调用链路、评估用例管理

**技术要点**
- SSE 流式渲染：`EventSource` / `fetch` + `ReadableStream`；断线重连、`Last-Event-ID` 续传
- 状态管理：Zustand（轻）或 Redux Toolkit（复杂）；流式增量更新避免全量重渲染
- 长列表：虚拟滚动（`react-window` / `@tanstack/virtual`）
- Trace 树：虚拟化 + 按需展开 + 懒加载节点详情
- 组件化：`MessageBubble` / `ToolCallCard` / `SpanTree` / `EvalCaseTable`

## 3. Tier 2｜深度工程层

### 3.1 单 Agent Harness 深度拆解：Pi 与 DSH

> **上位概念**：Harness（智能体外壳 / 运行时）= 模型之外的一切——循环、工具、环境、状态、会话、权限、观测。
> **通用定义**（DSH 官方表述）：**Agent = Model + Environment + Tools + State**

面试谈单 Agent，不能只会调 `ChatCompletion`，必须能讲清一个 Harness 内部怎么组织、有哪些扩展点、代价在哪。

---

#### 3.1.1 Pi（`earendil-works/pi`）——极简、可塑的终端 Agent Harness

**定位**
开源、极简的终端编码 Agent Harness，TypeScript 生态。官方口号："a minimal agent harness, adapt Pi to your workflows"。核心是一个小而可重塑的内核，而非预装固定权限体系和流程的封闭助手。

**包结构（源码级认知）**

| 包 | 职责 |
| --- | --- |
| `@earendil-works/pi-ai` | LLM provider 抽象、模型类型、transcript 工具、枚举 |
| `@earendil-works/pi-agent-core` | 有状态 Agent 循环、消息类型、工具执行、事件流 |
| `@earendil-works/pi-schema` | JSON Schema 构建器，工具参数类型推导 |
| `@earendil-works/pi-mcp` | 接入 MCP Server，把每个 MCP 工具包成 `AgentTool` |
| `@earendil-works/pi-codemode` | 运行模型写出的 JS 脚本，脚本通过 `runToolCall()` 回调 Agent 工具 |
| `@earendil-works/pi-tui` | 终端 UI 组件 |
| `pi-coding-agent` | CLI / 交互模式入口 |

**核心工程设计点**

1. **Session 以树（tree）而非扁平 transcript 存储**
   - 可从历史任意节点分叉（branch），无需复制整段对话
   - 这是断点恢复、试错回退的底层支撑
   - **工程代价**：分支数量爆炸需冷热分离（活跃分支 Redis，历史分支归档对象存储）+ 分支 TTL

2. **四种运行形态**
   - 交互式 TUI、print/JSON 脚本输出、RPC 进程、可嵌入 SDK
   - 同一内核面向不同宿主，体现「Harness 与宿主解耦」

3. **工具定义机制**
   - `AgentTool` + JSON Schema 参数（`pi-schema` 构建器带类型推导）
   - `beforeToolCall` / `afterToolCall` 钩子对普通工具与 codemode 内部调用**统一生效**
   - 这是权限、审计、埋点的天然切面

4. **1.0 关键能力**
   - Codemode（原生 MCP 支持、非 LLM 模型如图像模型接入）
   - 虚拟模型扩展、工具延迟加载（deferred tool loading）
   - Anthropic 缓存预热（cache warming）
   - 会话中途系统消息（transcript 感知的 prompt / 工具变更）

5. **刻意取舍**
   - 官方明确**不内置 sub-agents、plan mode** 等重型能力，留给用户用扩展 / 包自行组装
   - 理念：等能力被验证后再纳入，抵制短命复杂度

**面试判断**
- Pi 代表「**单 Agent 内核极简主义**」：核心循环小、扩展靠包和扩展点
- 适合：需要深度定制 Harness 行为、把 Agent 嵌进自有产品的场景
- 不适合：开箱即用的固定多角色流水线
- 与 Claude Code / Codex 同属「围绕一个具体 Agent 优化 Harness」路线；DSH 走的是另一条路

#### 3.1.2 DSH（`deepseek-ai/deepseek-harness`）——一切皆插件的模型无关 Agent 运行时

**定位**
DeepSeek 开源（MIT，Developer Preview v0.1，2026 年 8 月）的 Agent Harness。基于 **Cordis** 插件系统，把模型、工具、技能、会话、沙箱、存储、循环、调度、UI 全部做成可替换插件。
Harness 内核只负责加载 / 卸载插件、依赖管理、事件机制，**不含任何特定 Agent 能力**——官方表述：「There is no privileged core to patch」。

**三层架构（plugin → bundle → profile）**

| 层 | 含义 |
| --- | --- |
| **Plugin（实现层）** | 一个 Cordis 插件：`name / inject / Config / apply(ctx, cfg)`，提供 Service、注册 Tool/Command、贡献 Prompt 段 |
| **Bundle（打包层）** | 一个 npm 包，`package.json` 声明 `dsh.bundle.patch`，内含 `cordis.patch.yml` 的一组插件行 |
| **Profile（组合层）** | 有序 bundle 列表 + 用户 `cordis.patch.yml` patch 层 + `--patch` 覆盖层 |

**内核三大设计**

**① Capability Seam（可替换能力缝）**

三层结构：**Service Definition（接口定义）→ Service Provider（实现）→ Consumer（通常是暴露给模型的工具）**

- 例：FS Service 下挂 Local FS / E2B FS / Remote FS 多个 Provider，向上呈现统一的 file tools
- Shell、Subprocess、Sandbox、Web、LLM、SubAgent 同构
- **工程含义**：Agent 依赖「能力接口」而非「具体工具实现」；换 Provider 时模型看到的工具形态不变，底层环境整体替换

**② 事件流水线（Event Pipeline）**

内部不是简单的「LLM → 工具 → LLM」，而是每条 Turn 拆成可被插件监听的事件节点：

```
turn/start → claim input → assemble(system prompt / context / tools)
→ agent/pre-step → step/start → LLM request(agent/request) → llm/stream
→ assistant/message → tool/call → tools/pre-execute(permission / guard / policy / hook)
→ tools/execute → tools/post-execute → tool/result → step/end → next turn
```

- `turn/*` `step/*` `user/message` `assistant/*` `tool/*` 是**持久化会话事件**
- `agent/pre-step` `agent/request` `llm/stream` `tools/*` 是**扩展点**
- 安全校验、记忆注入、行为记录、请求改写、停止判断都以 **listener** 形式挂到事件上，**不改 Agent 循环源码**
- 典型挂载：安全校验挂 `tools/pre-execute`；记忆挂 `agent/pre-step`；观测挂 session 事件；请求改写挂 `agent/request`；停止判断挂 `agent/turn-stopping`

**③ Session Event Log：Model-visible means logged**

- 仅追加（append-only）会话日志
- 凡进入模型请求的内容（系统提示、思维链、工具调用与结果、子 Agent 调度、每次上下文注入）都必须可从日志重建
- 由运行时不变量强制
- 恢复、分叉、检索、回放共用同一份事件流
- **可观测性不是事后加的日志，而是 Harness 的一级约束**

**面试判断**
- DSH 把 Harness 当成**模型无关的操作系统**，Agent 本身是跑在上面的可替换应用
- 自由度极高，代价是配置 / 上手成本高，且仍是 Developer Preview
- 可迁移到自研系统的四条：
  1. 循环每一步事件化（权限 / 记忆 / 策略 / 日志做 listener）
  2. 能力按接口标准化、环境可插拔
  3. 「模型可见即留痕」
  4. append-only 日志支撑回放与 handoff

| --- | --- | --- |
| 设计哲学 | 极简内核，可塑 substrate，功能按需用包组装 | 一切皆插件，Harness 模型无关、像 OS |
| 内核定位 | 围绕单编码 Agent 的精简循环 | 内核只管插件加载 / 依赖 / 事件，无特定能力 |

#### 3.1.4 DSH 与 LangGraph 的互补关系（秒杀级加分点）

很多面试官会问：既然 DSH 事件驱动这么灵活，为什么还要 LangGraph？

| 维度 | DSH | LangGraph |
| --- | --- | --- |
| 擅长 | **把 Agent 能力做成可插拔平台**：统一事件观测、统一工具抽象、横向扩展能力插件 | **强控制流**：复杂分支、人工介入、长状态机、纵向编排业务流程 |
| 类比 | Agent 操作系统 | 业务流程状态机 |
| 短板 | 复杂业务 DAG 编排需要自己搭 | 底层工具 / 沙箱 / 埋点要自己集成 |

**落地组合方案**：
> DSH 作为底层 Harness 运行时（统一工具、沙箱、事件、埋点）；LangGraph 作为上层业务编排层，挂载在 DSH 的 subagent 插件上。二者是「OS + 应用框架」的分层关系，不是竞争关系。

### 3.2 长上下文治理 & 分层记忆

#### 分层存储架构

| 层 | 介质 | 内容 | 特性 |
| --- | --- | --- | --- |
| 工作记忆（短期） | Redis / 内存 | 当前会话 State、最近 N 轮原文 | TTL 自动清理，<5ms 读写 |
| 情节记忆 | PG / MongoDB | 全量对话审计、时间戳、token 消耗、元数据 | 用于回溯与审计 |
| 语义记忆 | 向量库（Milvus / PGVector） | 跨会话事实、用户画像 embedding | 相似度召回 |
| 实体关系记忆 | Neo4j / 结构化 JSON | (Subject, Predicate, Object) 三元组 | 语义级压缩、关系推理 |

#### 写入策略
- **Write-Through**：主链路同步写 Redis，保证当前对话连贯
- **Write-Behind**：通过 MQ 异步刷入 MongoDB / 向量库 / 图库，不阻塞主请求
- **一致性处理**：主库为准，异步落盘失败进死信队列重试；向量库与主库不一致时以主库回补

#### 上下文压缩四方案对比

| 方案 | 机制 | 成本 | 风险 |
| --- | --- | --- | --- |
| 滚动摘要 | 保留近 N 轮原文，更早交 LLM 摘要 | 中（要额外调用） | **摘要幻觉、事实丢失**（如「要求退款但未付运费」被压成「要求退款」→ 错误全额退款） |
| 结构化抽取 | 订单 / 客户 / 权限抽成强 schema 字段 | 低 | 只能覆盖已知字段，非结构化信息丢失 |
| 按需检索重放 | 历史向量化，按 query 召回相关片段 | 低 | 召回不准导致上下文缺关键信息 |
| **Observation Masking** | 可重算的工具输出直接丢弃 | **最低** | 需要工具可重复执行 |

> **优先级结论**：Observation Masking > 结构化抽取 > 按需检索 > 摘要压缩。
> 摘要压缩是**有损**的、会引入幻觉的；前三种是索引 / 裁剪，不引入新的错误事实。

#### 压缩触发策略
- token 占用达上下文窗口 60%~70%
- 固定轮次间隔（如每 5 轮）
- **最佳时机：工具调用结束后立刻裁剪冗余工具返回**（此时信息价值已消费完）
- 压缩本身也要算成本预算，不能每轮都压

#### 遗忘策略
TTL 时效、访问热度衰减、用户主动遗忘接口、合规删除（GDPR / 个保法）

#### 高频面试题
1. 三种压缩方案对比、适用业务、失败模式？
2. 跨会话记忆如何防止记忆污染？（写入校验、来源标记、置信度、冲突检测）
3. Write-Behind 异步落盘，向量库和主库不一致怎么处理？

### 3.3 AI Gateway / 模型中转站

**定位**：AI 系统的**控制平面**，不是简单转发。

#### 能力集

| 能力 | 说明 |
| --- | --- |
| 协议适配 | 统一 OpenAI 兼容格式，对接 OpenAI / Anthropic / vLLM / SGLang / Gemini |
| 鉴权隔离 | 统一 Token 管理，业务侧不持有上游 key |
| 智能路由 | 按任务复杂度、输入长度、成本预算路由大小模型；静态标签路由 + LLM 动态路由 |
| 流量治理 | 指数退避重试、熔断、限流、**单任务 / 单租户 Token 硬上限** |
| 成本审计 | 租户 / 用户 / Agent 实例级 token 统计、成本看板、预算告警 |
| 流式转发 | SSE、partial tool call 字段完整性 |

#### 三大隐形杀手与解法

| 问题 | 成因 | 解法 |
| --- | --- | --- |
| **重试风暴** | 客户端超时立刻重试，打爆上游 | 客户端指数退避；网关侧 `Max Retries = 1` 或直接关闭重试 |
| **连接池枯竭** | 高并发 TCP 连接耗尽 | 反向代理（Caddy/Nginx）开 keepalive；调大 `ulimit -n` |
| **SQLite 锁死** | New-API 默认 SQLite，高并发日志写入卡顿假死 | 生产迁移 MySQL / PostgreSQL，或关闭非必要日志 |

#### Agent 场景的特殊要求
- **Function Call 协议完整性**：部分中转站只模拟 OpenAI 格式，工具调用字段缺失，直接导致 Agent 逻辑错乱。上线前必须完整测试工具调用链路
- **硬额度上限**：Agent 容易循环调用，网关必须配置单任务 / 单账号 Token 上限，防止逻辑 Bug 带来巨额账单
- **模型版本固定**：Agent 行为对模型版本敏感，网关必须支持指定版本，禁止静默切 latest

#### 高频面试题
1. 网关为什么不能无脑开重试？重试风暴防护方案？
2. 自研网关，模型路由策略怎么设计？
3. Agent 循环调用工具，网关层、Agent 层两层防护分别做什么？（网关：token 硬上限；Agent：循环终止条件 + 成本预算）

#### 差异化
Go 自研轻量网关：SSE 流式转发、令牌桶限流、路由调度，对比 LiteLLM 的性能短板与扩展限制。

### 3.4 业务建模：Ontology 本体 + 动作约束

#### LLM Wiki vs Ontology

| | LLM Wiki（文档 RAG） | Ontology（业务本体） |
| --- | --- | --- |
| 解决问题 | 资料分散 | 业务执行 |
| 告诉 Agent | 规则是什么 | 业务怎么运转、能做什么、谁有权做 |
| 产出 | 回答 | 合法动作 |

#### 四步建模法
1. **定义对象**：客户、订单、库存、仓库、工单
2. **定义关系**：订单属于哪个客户、库存对应哪个仓库
3. **定义动作**：修改工单、发起退款、调整排产
4. **定义规则**：金额超 10 万必须人工审批、涉及隐私需权限校验

#### 落地形式
- JSON Schema / OWL / 图结构
- 作为 Agent 的**约束上下文**，而不是纯 prompt 文本
- **运行时校验**：Agent 输出动作 → 先过本体规则引擎 → 再交给工具执行；越权、不合规动作**在 LLM 之外拦截**

#### 适用边界
- 需要：强流程、强权限、实体密集业务（工单、订单、供应链、金融）
- 不需要：简单问答、单轮查询

#### 高频面试题
1. 售后退款 Agent，本体怎么设计？（列出对象 / 关系 / 动作 / 规则四层）
2. Ontology 放在 Prompt 内，还是独立规则引擎？各自优缺点？（Prompt 内灵活但不可靠；规则引擎可靠但需维护）
3. 本体迭代更新，存量 Agent 状态怎么兼容？（版本化 + 旧会话锁定旧本体版本）

### 3.6 多 Agent 框架深度：AutoGen / CrewAI / Super-agent

#### 3.6.1 CrewAI

**抽象**：Agent（角色 + 能力 + LLM）、Task（描述 / 依赖 / 输出格式）、Process

| Process | 机制 |
| --- | --- |
| Sequential | 任务串行，前一任务输出作为后一任务上下文 |
| Hierarchical | Manager Agent 分派任务给 Worker，汇总结果 |

**优势**：声明式、低代码，面向业务任务编排，适合固定流水线型多 Agent

**短板**：
- 细粒度状态流转、中断、自定义重试弱
- 灵活度低于 LangGraph
- Hierarchical 的 Manager Agent 可能误分派、重复分派

---

#### 3.6.2 AutoGen

**抽象**：Agent、Conversation、GroupChat、Orchestrator、CodeExecutor

**模式**：
- 一对一对话
- GroupChat 群组协商（轮次发言 / 自动选择发言者）
- 带管理者仲裁（Manager 决定下一个发言者）
- CodeExecutor 代码协同

**优势**：对等对话、辩论、动态协商，适合开放式协作、方案评审、代码协同

**短板**：
- 状态持久化、可观测、大规模调度原生薄弱
- 容易无限闲聊、话题跑偏、重复观点
- 成本不可控（多 Agent 轮流调用 LLM）

---

#### 3.6.3 DeepSeek Super-agent（重点）

**定位**
DSH 之上的**长期运行多任务系统**。不是围绕单个复杂任务拆分子 Agent，而是把「跨任务协调」独立成一个系统层。
解决痛点：人只能同时跟进 3~5 个活跃 Session，需手动切换上下文。
四大目标：**连续性（continuity）、高效（efficiency）、主动（proactivity）、持久（persistence）**

**Router / Worker 双层架构**

| 组件 | 职责 |
| --- | --- |
| **Router** | 维护全局上下文、任务关系、事件接收、识别分派、对外统一沟通；**不做耗时执行** |
| **Worker** | 独立 Session + 独立工具环境 / 工作目录，并发执行具体任务，结果回报 Router；内部可再用 Subagent / Agent Team |
| **Trigger** | 外部环境事件（GitHub Issue / PR 评论、CI 失败、群聊、邮件、日程） |
| **Thread** | 组织同一讨论 / 事项的相关事件流 |
| **Ticket** | 持久化跟踪的工作任务 |
| **Assignment** | 某次具体执行安排 |
| **Session** | 保存执行上下文与历史 |

**关键机制**

**① Fast Path / Slow Path 路由**
- Fast Path：确定性规则按来源 / 用户 / 群组 / 事件类型 / 授权范围过滤大部分噪声
- Slow Path：才交模型做语义判断（建任务、关联现有任务或忽略）
- 原则：**能规则判断的不交模型**

**② Thread Subscription**
- Worker 承接任务后订阅对应 Thread，后续相关事件直达该 Worker Session
- 不必每次重走 Router 模型判断 → 降路由负载、避免上下文重建
- **生命周期风险**：Worker 完成 / 崩溃 / 取消后订阅必须清理，否则事件持续推给闲置 Worker，浪费 token 并产生幻觉关联

**③ Inline & Spill**
- Inline：当前所需信息（任务摘要、相关 Thread、近期反馈）放进上下文
- Spill：完整历史 / 低频信息留外部存储，上下文只存摘要 + 引用标识
- Context Window 被当作**容量有限的高速缓存**，而非无限增长的历史记录

**④ Chain of Recall**
- 为 Trigger / Thread / Ticket / Session 建关联引用，模型沿引用链逐步恢复历史
- 例：PR 评论问某修改背景 → Thread → Ticket → 原始 Issue → Worker Session

**和相近技术区分**

| 技术 | 解决的问题 |
| --- | --- |
| Context Engineering | 当前模型请求应该看到什么 |
| RAG | 从外部知识中检索相关信息 |
| Long-term Memory | 从历史中沉淀长期有价值的信息 |
| **Chain of Recall** | 按任务与事件关系恢复历史上下文 |

**⑤ Watchdog**
- 主系统之外的独立监控
- 既查基础设施存活 / 超时，也判断 Worker 是否陷入无效循环、反复调工具、目标偏移
- 必要时触发恢复或人工介入
- **核心洞察**：长期运行 Agent 不仅要监控「是否在执行」，还要判断「执行是否仍然有效」

**⑥ 主动性约束**
- 推断式任务接纳模式：`off` / `observe` / `auto`
- `observe`（默认）只评估不接活
- `auto` 也只有命中启用规则的事件才能自动触发
- 主动性建立在**确定性授权与规则**之上，不交模型自由裁量

**与传统 Multi-Agent 的本质区别**

| | 传统 Multi-Agent（CrewAI / AutoGen / LangGraph） | Super-agent |
| --- | --- | --- |
| 组织对象 | 单个复杂任务拆分协作 | 多个持续存在的任务并发推进 |
| 调度中心 | 框架内编排 / 对话 | Router 独立成层，统一交互与协调 |
| Session 归属 | 常共享或按任务临时建 | Worker 独立 Session / 目录，隔离并发 |
| 触发方式 | 用户主动 Prompt | 事件驱动，可主动响应外部 Trigger |
| 核心难点 | 角色分工、对话收敛 | 任务持久化、事件路由、订阅、上下文召回、Watchdog |

**代价与边界**

| 设计 | 优势 | 代价 |
| --- | --- | --- |
| Router / Worker | 多任务并发、统一交互 | Router 可能成为调度瓶颈 |
| 独立 Session | 减少上下文干扰 | Token 与资源消耗增加 |
| 事件驱动 | 减少人工发起任务 | 误触发、重复事件、消息噪声 |
| Thread Subscription | 降低重复路由成本 | 关联错误、订阅生命周期管理 |
| Inline & Spill | 减少上下文冗余 | 可能遗漏需恢复的信息 |
| 异步执行 | 避免长任务阻塞前台 | 并发、取消、结果顺序更复杂 |
| Watchdog | 改善长任务异常恢复 | 监控本身也可能误判 |
| 存算分离 | 支持长期在线与多环境 | 远程授权、凭据、安全成本 |

### 3.7 安全、权限、合规

#### Prompt 注入防御
- 输入校验与分隔符隔离（用户内容用明确边界包裹）
- 最小权限原则：Agent 只拿到完成当前任务的最小工具集
- 沙箱执行：代码 / 命令不下宿主机
- 输出过滤：拦截越权指令、敏感信息
- **独立校验 Agent**：用小模型或规则校验主 Agent 的动作合法性

#### 数据权限
- RAG 行级权限隔离：检索时带 `metadata` 权限过滤，而非检索后过滤（避免信息泄露）
- 向量库按租户 / 部门分区

#### 隐私与合规
- PII 脱敏（入库前 / 上下文注入前）
- 记忆删除接口、数据不出域、模型水印
- 审计日志留存

## 4. Tier 3｜架构与前沿协议层

> Rust：后期进修，面试不主动主推，被问到再说明自学计划。

### 4.1 Agent 互联协议：MCP + A2A

#### MCP（Model Context Protocol）
- **作用**：标准化大模型与外部工具、数据源的连接方式；解决每个 Agent 单独写工具适配代码的问题
- **与 Function Calling 的关系**：
  - Function Calling 是**模型层面能力**（模型决定调用哪个函数）
  - MCP 是**应用层面协议**（标准化函数的暴露与调用方式）
  - MCP ≈ Function Calling 的「USB-C 接口」
- **架构**：MCP Host / MCP Client / MCP Server
- **取舍**：生态尚不成熟，增加运维负担；平台化、大量异构工具才值得引入；单一业务小团队优先直接封装工具

#### A2A（Agent to Agent）
- **作用**：多 Agent 系统之间的通信协作；能力发现、任务协商、状态同步、结果回执
- **与编排框架的区别**：LangGraph / CrewAI / AutoGen 是**编排框架**；A2A 是**跨系统 Agent 通信标准**，不在同一层
- **适用**：跨团队、跨系统异构 Agent 组网；同业务内部子 Agent，中心化编排通常更稳更好调试

### 4.2 多 Agent 高级架构

| 架构 | 机制 | 优劣 |
| --- | --- | --- |
| Orchestrator 中心化调度 | 主规划 Agent 拆分任务分派子 Agent | 易调试、可控；企业首选；中心可能瓶颈 |
| 评审式 | 生成 Agent + 校验 / 评审 Agent | 自纠错闭环；成本翻倍 |
| 分布式对等（A2A 路线） | 无中心，自主协商 | 扩展性好；调试难、观测成本高 |

- **通信方案**：共享状态、消息队列、事件总线
- **并发冲突**：同一实体被多 Agent 修改 → 锁、版本号、冲突仲裁策略

**演进方向**（结合 Super-agent 开放问题）：
- Router 专用化（规则 / 轻量模型分流）
- 跨任务 Memory（长期运行的记忆提取、更新、遗忘、检索）
- 分布式任务协调（分层 Router、任务分片、跨 Worker 通信、资源冲突控制）
- 执行环境安全（权限继承、沙箱隔离、凭据保护、审计）
- 任务进展监控（从存活检查扩展到目标偏移与死循环识别）
- 交互方式变化（从 Session 列表转向任务 / 进度 / 待确认事项 / 交付结果）

### 4.3 CUDA 推理侧高级调度

- 多模型混部、GPU 共享、K8s DevicePlugin、调度队列优先级
- 动态批处理、预热、模型热加载、模型池化
- KV Cache 共享池、Prefix Cache（长会话降本核心）
- 多模态推理链路与图文混合 Agent 坑点

### 4.4 平台化：单 Agent → Agent PaaS

| 能力 | 要点 |
| --- | --- |
| 租户隔离 | 状态、记忆、向量库、网关配额全隔离 |
| 版本管理 | Prompt、工具、本体、评估基线绑定（Langfuse 天然适配） |
| 模板市场 | Agent 模板、MCP 服务注册中心 |
| 生命周期 | 灰度、发布、回滚 |

### 4.5 成本治理全景（独立大题，优先级从高到低）

| 优先级 | 手段 | 预期收益 |
| --- | --- | --- |
| 1 | 网关路由：简单任务下沉小模型 | 高 |
| 2 | 语义缓存：query 向量相似度命中直接返回 | 高（30%~70%） |
| 3 | 上下文治理：Observation Masking > 结构化抽取 > 摘要压缩 | 高 |
| 4 | 推理侧：Prefix Cache、KV 复用、连续批处理、合理量化 | 中高 |
| 5 | 检索侧：控制召回 TopN，避免过度检索 | 中 |
| 6 | Agent 层：严格终止校验，减少无效工具轮次 | 中 |

## 5. 补充卷 A｜Harness 工程深水区

> 这一卷是 Pi / DSH 的**生产落地坑**，面试被追问「那你实际搭过吗」时的弹药。

### 5.1 Pi 的工程坑

#### ① 分叉（branch）≠ 环境分叉（最容易踩的认知坑）

- Pi 的树状 Session 只分叉**对话记录**，不自动快照沙箱 / 文件系统
- MCP 工具调用有外部副作用（写文件、调 API），会话分叉后**环境状态不会回滚**
- 要做环境级回滚，需外接 e2b / 容器快照层

| 使用分叉 | 不要用分叉 |
| --- | --- |
| prompt 变体试错 | 需要环境状态原子回滚的操作 |
| 同一步骤不同模型版本对比 | 已产生外部副作用的链路 |
| 工具参数 A/B | — |

**追问话术**：「Pi 的 branch 是 transcript 分支，不是 state 分支。做 prompt 实验很合适；但涉及写文件、发消息这类副作用，我会叠一层沙箱快照，否则分叉会产生环境与对话不一致。」

#### ② Codemode 安全边界

- Codemode 允许模型生成 JS 脚本并在 Harness 内执行，但**执行隔离是轻量隔离，不是强沙箱**
- 生产必须：拦截原生 `fs` / `network`，或把 codemode 执行代理到 e2b 容器
- 脚本与主循环共享工具上下文，脚本内 `runToolCall()` 会混进同一 turn 事件流 → 埋点、Langfuse span 必须区分，否则 trace 混乱

#### ③ 与 MCP 的绑定细节

- Pi 自带 `pi-mcp`，MCP Server 是子进程
- 需管理：子进程生命周期、僵死检测、重连、多 MCP Server 并发的端口 / stdio 管理
- MCP 工具报错要向上翻译成 Pi 的 ToolError 事件，否则模型收到的是无结构异常

### 5.2 DSH 的工程坑

#### ① Cordis 插件依赖冲突（生产最大痛点）

- 插件间通过 `inject` 做依赖注入
- 同一 Service 被多个插件提供 → **provider 冲突、覆盖顺序问题**
- Profile 的 bundle 有序性不是装饰，是**核心约束**——它本质是依赖解析的声明文件
- 线上变更 bundle 必须**版本锁定**，禁止直接拉 latest

**追问话术**：「DSH 的 profile 是依赖解析清单，不是插件列表。bundle 顺序决定 provider 覆盖优先级，线上必须锁版本，否则一次 npm update 就可能换掉 LLM provider 实现。」

#### ② 事件流水线的阻塞与顺序

- `turn/start`、`tools/pre-execute` 等 listener 是**同步执行**
- 长时间校验、大模型策略判断写在同步 listener 里会卡住整个 turn
- 复杂策略应走异步事件 + 状态机，或放到独立 Worker
- **回放一致性**：回放时插件版本必须与当时完全一致；插件逻辑变更后旧事件流可能回放失败
  - 这是「Model-visible means logged」的代价：日志是对的，但插件版本漂移会导致行为不一致
  - 解法：事件日志记录插件版本快照，回放时按当时 profile 重建

#### ③ Capability Seam 的接口契约版本管理

- 替换 FS / Shell / LLM provider 时，接口 schema 要版本化
- 否则换 provider 后模型看到的工具描述没变，但返回字段变了 → 大量 tool call 失败
- 类比：这是 Harness 层的「API 兼容性治理」

### 5.3 Harness 层通用工程原则（可直接迁移到自研）

1. **循环每一步事件化**：权限、记忆、策略、日志做 listener，而不是硬编码进循环
2. **能力按接口标准化**：依赖「能力接口」而非「具体工具」
3. **模型可见即留痕**：所有进入模型上下文的内容必须可重建
4. **append-only 日志**：支撑回放、分叉、审计、handoff
5. **环境与对话分离治理**：对话状态与环境状态是两个独立生命周期

## 6. 补充卷 B｜Super-agent 深挖

### 6.1 Fast Path 规则引擎选型

- 原型是简单条件匹配
- 生产方案：可配置规则引擎（CEL / JsonLogic）、规则版本管理、规则灰度
- 规则也可做成 DSH 插件，统一纳管
- **风险**：规则膨胀、规则冲突 → 需规则优先级 + 冲突检测 + 规则覆盖率监控（多少事件被 Fast Path 拦掉、多少漏到 Slow Path）

**追问话术**：「Fast Path 不是写 if-else，是要做成可配置规则引擎 + 版本管理 + 冲突检测，否则规则一多就变成不可维护的硬编码。同时要监控 Fast Path 的拦截率和误拦率。」

### 6.2 Thread Subscription 生命周期与泄漏

- Worker 完成后订阅必须清理
- 未清理的后果：无关事件持续推给闲置 Worker → 浪费 token、产生幻觉关联、上下文被污染
- 治理：订阅与 Worker 生命周期绑定；心跳检测；过期订阅回收；订阅关系可观测（谁订阅了哪个 Thread）
- **关联错误**：Thread 归属判断错误会导致事件推给错误 Worker

### 6.3 Inline & Spill 与「摘要压缩」的本质区别（高频混淆点）

| | 摘要压缩 | Inline & Spill |
| --- | --- | --- |
| 机制 | 主动把历史浓缩成自然语言 | 引用 + 摘要索引，原文完整存在外部存储 |
| 信息 | **有损**，可能丢事实、产生幻觉 | **无损**索引，需要时可按引用拉回原文 |
| 恢复能力 | 原文已丢失，无法恢复 | Chain of Recall 可按需拉回 |
| 成本 | 每次压缩要额外 LLM 调用 | 一次写入，多次按需读 |

> **一句话**：摘要压缩是「把历史改写成短文」；Inline&Spill 是「历史原样存着，上下文里只放目录」。

### 6.4 Watchdog 的两种模式与误判风险

| 模式 | 判断内容 | 难度 |
| --- | --- | --- |
| 存活 Watchdog | 超时、进程挂、无输出 | 低（规则可判） |
| 目标对齐 Watchdog | 当前动作是否还在推进 Ticket 目标 | 高（本质是 LLM 判断） |

- Watchdog **不能自动强干预**，默认走告警 + 人工接管
- 自动恢复（重置 Worker、新建 session）是高危动作，必须开关 + 审计日志
- **误判风险**：把长耗时但有效的任务判为卡死；把探索性动作判为目标偏移

**追问话术**：「Watchdog 我分两层：存活检测走规则，目标对齐走模型判断但只告警不干预。自动恢复一定是高危动作，要有开关和审计，否则 Watchdog 自己会成为新的故障源。」

### 6.5 Worker 资源隔离

- Worker 是独立 Session、独立沙箱目录，但 **GPU 资源共享**
- 需要：Worker 池、并发配额、每 Worker token 硬上限、GPU 显存配额
- 防止一个卡死 Worker 占满全部资源

### 6.6 已知短板：跨 Ticket 依赖

- Ticket 之间存在依赖（B 任务等 A 任务输出）
- 原型依赖能力弱
- 生产要在 Router 层增加 **DAG 依赖调度**：Ticket 状态机、依赖等待、就绪队列、失败传播

| WebSocket | 双向实时 | 连接状态管理复杂 |

### 7.2 权限模型
- **MCP 协议本身没有权限模型**
- 权限控制必须在 Harness 层做：DSH 的 `tools/pre-execute` listener / Pi 的 tool 钩子
- 按工具、按参数、按调用方身份做细粒度授权

### 7.3 缓存与会话隔离
- MCP Server 可能持有自己的会话状态
- 多个 Agent 共享同一 MCP Server → **状态串扰**
- 解法：每个 Agent 独立 MCP 实例，或 MCP 侧做 session 隔离（按 client_id 分区）

### 7.4 MCP vs 原生 Function Calling 运维成本对比

| | 原生 FC | MCP |
| --- | --- | --- |
| 实现成本 | 低，直接封装 | 中，需 Server + 协议 |
| 复用性 | 单一 Agent | 一次开发多框架复用 |
| 故障面 | 小 | 大（多一层进程 / 服务） |
| 可观测 | 直接 | 需跨进程埋点 |

**选型一句话**：内部少量工具直接 FC；异构大量工具、跨团队共享工具，才上 MCP。

## 8. 补充卷 D｜Langfuse 观测与评测量化

### 8.1 Span 分层规范（可直接写进项目文档）

| 层级 | 对应对象 | 说明 |
| --- | --- | --- |
| trace | 一次用户请求 / 一个 Ticket | 最外层 |
| span | turn、llm_call、tool_call、retrieval、agent_planner、watchdog_check | 按语义阶段分组 |
| generation | 单次 LLM 调用 | 含 model、prompt、token、cost |

**自定义属性（metadata）**：
`harness_type=pi/dsh`、`worker_id`、`ticket_id`、`thread_id`、`mcp_server_name`、`agent_version`、`prompt_version`

### 8.2 失败 Case 分类体系（不能只看成功率）

| 类别 | 具体失败 |
| --- | --- |
| LLM 侧 | 输出格式错误、幻觉、拒绝回答、截断 |
| 工具侧 | 参数错误、权限拒绝、第三方超时、MCP 服务挂 |
| Agent 循环 | 无限 tool call、目标漂移、上下文溢出、重复动作 |
| 编排层 | Router 路由错误、Worker 订阅泄漏、事件乱序、Ticket 依赖死锁 |

> 每类失败配独立指标与告警阈值，才能定位「成功率下降」到底降在哪。

### 8.3 LLM-as-judge 偏差治理

- **双 Judge 交叉校验**（不同模型 / 不同 prompt）
- **固定 judge 版本**，judge prompt 纳入 Langfuse 管理
- **规则校验器做硬基线**（schema、关键词、权限、引用存在性），**规则优先，LLM judge 只做软评估**
- 已知偏差：偏好长回答、偏好格式规整、对专业性错误不敏感、位置偏好（偏好第一个候选）

### 8.4 Langfuse 自托管部署坑

- 依赖：ClickHouse、Postgres、Redis
- **高写入场景 ClickHouse 是瓶颈**（Agent 大量 turn 事件）
- trace 采样策略：小流量全量；生产按用户 / 按 trace_id 采样；错误 trace 强制全采样
- 埋点不能阻塞主链路：本地缓冲队列 + 异步重试

## 9. 补充卷 E｜CUDA 推理的 Agent 场景专属坑

### 9.1 Agent 多轮 turn 的 prefill / decode 开销

- Agent 是多轮 turn，每轮都要 prefill（系统提示 + 工具定义 + 历史）
- **KV 复用 / Prefix Cache 对 Agent 收益远大于普通问答**
- 对比：问答一次 prefill；Agent N 轮 N 次 prefill，prefix cache 命中可省掉大比例重复计算
- 关键前提：**前缀稳定**（system prompt、工具 schema 顺序固定），否则缓存失效

### 9.2 工具返回超长文本的推理侧配合

- Agent 层策略：Observation Masking / 截断 / 结构化
- 推理侧配合：长 observation 不进 KV 常驻，或单独缓存；避免一轮超长 observation 把整个对话 KV 撑爆触发 swap

### 9.3 模型热加载与会话冲突

- 正在跑的 Worker Session，背后模型版本切换会导致行为突变
- 策略：**Worker 绑定模型版本**，Ticket 完成后才回收、切换模型；不要热切正在运行的 Worker

### 9.4 nsys 针对 Agent 场景的观测点

不只看单 token latency，重点看：
- **prefill 扎堆**（多会话同时进入新 turn）
- **GPU idle**（等待工具返回时空转，此时可考虑让出资源）
- **KV swap 风暴**（多轮工具调用 + 长上下文容易触发）

> 这三个指标在 Agent 场景比「平均 TTFT」更有诊断价值。

## 10. 补充卷 F｜React 前端工程难点

### 10.1 SSE 长连接 + 多 Agent 并发流

- 一个页面同时看多个 Worker、多个 Trace 流
- 需要：连接池管理、自动重连、`Last-Event-ID` 断线续传、流数据本地缓存、背压控制
- 浏览器对同域并发连接有限制（HTTP/1.1 下 6 个），多流场景需复用或走 WebSocket

### 10.2 Trace 树组件性能

- 一条 Super-agent Ticket 可能上百 turn、上千 span
- 必须：虚拟滚动、按需展开、懒加载 span 详情、避免一次性渲染全部节点
- 数据结构用扁平 map + parentId，而非深层嵌套对象（便于增量更新）

### 10.3 与 Langfuse 的两种集成模式

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| A. OpenAPI 拉取自研渲染 | 完全可控，可定制 | 内部调试台 |
| B. iframe / 官方 UI 嵌入 | 快速上线，自定义弱 | 早期验证 |

### 10.4 本地回放能力（项目亮点）

- 基于 DSH append-only 事件日志 / Pi 树状 transcript，前端做**本地回放**，不依赖 Langfuse
- 支持：逐 turn 播放、span 时间轴、工具调用参数对比、prompt 版本切换对比
- 这是很多 Agent 候选人没有的端到端能力，面试主动讲

## 11. 补充卷 G｜生产运维与稳定性

> 这一卷区分 Demo 选手与工程选手，架构面必问。

### 11.1 全链路降级

| 依赖 | 不可用时 | 降级策略 |
| --- | --- | --- |
| LLM | 限流 / 宕机 | 静态提示、排队、结果缓存兜底、降级小模型 |
| 工具 / MCP | 超时 / 挂 | 工具熔断、返回预设提示，Agent 不崩溃 |
| 向量库 | 挂 | 降级关键词检索 |
| Langfuse | 挂 | 本地缓冲队列，异步重试，**不阻塞主链路** |
| 网关 | 挂 | 直连备用通道（需协议兼容） |

### 11.2 分层限流

| 层 | 限流对象 |
| --- | --- |
| 网关 | 租户 / 用户 / 模型维度 QPS、token 速率 |
| Agent | 单 Worker token 配额、单 Ticket 总预算 |
| 推理 | GPU 队列深度、并发 seq 上限 |
| MCP | 单 Server 并发、单工具 QPS |

### 11.3 审计链路

所有副作用操作（写文件、调业务 API、发消息）必须记录：
`user_id`、`ticket_id`、`turn_id`、`tool_name`、入参快照、返回结果、操作时间
→ 不可篡改审计日志（append-only，哈希链）

### 11.4 幂等性

- Agent 天然容易重试、重复调用工具
- 所有带副作用工具必须支持幂等，用 `turn_id` 或 `tool_call_id` 作为幂等 key
- 非幂等操作要人工确认（human-in-the-loop）

### 11.5 可观测三件套
- 指标（Metrics）：成功率、延迟、成本、队列深度
- 日志（Logs）：结构化、trace_id 贯穿
- 链路（Traces）：Langfuse span 树

## 12. 补充卷 H｜项目包装与面试落地

### 12.3 风险清单（系统设计收尾必说，显得成熟）

| 组件 | 风险 |
| --- | --- |
| Pi | 会话树膨胀、MCP 子进程管理、codemode 沙箱风险 |

### 12.4 差异化加分包（简历 & 面试主动输出）

### 12.5 可选延伸（Tier 3 有余力再啃，不做主线）

- 分布式 DSH：多进程 / 多机插件调度（官方原型是单机）

- 成本细粒度分摊：按 Ticket / Worker / 用户 / 工具类型统计，而非只看模型 token

## 13. 系统设计答题范式（统一模板）

### 五步结构

**Step 1｜给基线（Tier 1 稳定方案）**
> 「我会先用单 Agent Harness + ReAct 循环，RAG 查政策，SQL 工具查订单，Redis 存 checkpoint，vLLM CUDA 推理，Langfuse 全链路埋点。」

**Step 2｜自曝瓶颈**
> 「这套基线在长会话、多轮工具调用、业务规则复杂、多任务并发下会出问题：上下文膨胀、状态漂移、动作越权、成本失控。」

**Step 3｜分层优化（Tier 2）**
> 「引入 Ontology 约束动作与权限；分层记忆 + Observation Masking 控制上下文；Gateway 做模型路由和 token 上限；Langfuse 搭 Eval 闭环持续验证任务成功率。」

**Step 4｜平台演进（Tier 3）**
> 「工具异构之后接 MCP 标准化；跨系统协作考虑 A2A；如果要长期并发多任务，借鉴 Super-agent 的 Router/Worker + Thread Subscription + Watchdog。」

**Step 5｜收尾**
> 「评估指标：任务成功率、P99 延迟、单任务成本；风险：Router 瓶颈、订阅泄漏、Watchdog 误判、成本失控；降级方案：LLM 不可用走缓存兜底，工具不可用走熔断。」

### 完整示例：设计售后工单 Agent

| 阶段 | 内容 |
| --- | --- |
| 基线 | 单 Agent Harness + ReAct；RAG 查售后政策；SQL 查订单；Redis checkpoint；CUDA vLLM；Langfuse 埋点 |
| 瓶颈 | 退款规则复杂、工具轮次多、上下文膨胀；后续多业务线工单并发、事件驱动跟进 |
| 优化 | Ontology 约束退款动作与权限；分层记忆 + Observation Masking；Go 网关路由 + Token 上限；Langfuse 评估成功率 |
| 多任务演进 | 固定流水线用 CrewAI；多方评审用 AutoGen；长期并发工单借鉴 Super-agent 的 Router/Worker + Thread Subscription + Watchdog |
| 收尾 | 指标：任务成功率 / P99 / 单任务成本；风险：越权、成本失控、Watchdog 误判；降级：工具熔断 + 缓存兜底 |
