# 一次请求：前端、后端、数据库

用两笔请求把三层走完。写请求是用户在页面上提交一笔普通订单。读请求是打开这笔订单的详情。业务数字以 MySQL 为准，Redis 做扣减前的原子判断和详情缓存。

这条路径与 `面试/传统后端-Python.md` 开头一致。模型和工具调用的长链路在 `Agent架构/01-请求全流程.md`，文末只标边界。

## 三层各管一段

| 层 | 跑在哪 | 这次请求里做的事 |
| --- | --- | --- |
| 前端 | 浏览器里的 React / TypeScript | 收集表单，带登录态发出 HTTP，按错误码改界面 |
| 后端 | 网关进程和 FastAPI 进程 | 鉴权、限流、生成请求 id，按顺序调用 Redis 和 MySQL |
| 数据库 | MySQL、Redis | MySQL 留下订单、库存和发件箱；Redis 留下可重建的计数和缓存 |

一次点击在浏览器里开始，在数据库里结束。中间每一跳带着同一个请求 id，日志才能对上。浏览器不打开 MySQL，也不打开 Redis。连接池留在后端进程里。

## 写：提交订单

用户点「提交」。页面上已有商品、数量和收货地址。页面上的库存只是展示，提交时再问一次后端。

```text
浏览器
  → 网关：验令牌、限流、盖上用户 id、传请求 id
  → FastAPI：校验这张单属于这个用户
  → Redis：Lua 原子判断并扣减
  → MySQL：一个事务里写订单、条件扣库存、发件箱
  → 返回订单号
  → 后台循环把发件箱推到队列
  → 消费者更新搜索或创建下游单据
```

### 前端

点击之后按钮进入提交中。同一笔订单的第二次点击不再发新请求。

请求体是 JSON：商品、数量、地址、一把幂等键。幂等键在这次点击时生成。超时后的重试用同一把。用户明确要再下一笔，才换新的。

请求头带登录得到的令牌。上游已经给出追踪 id 就放进头里。响应里把请求 id 拿回来，失败时显示在页面上，方便对日志。

浏览器自己的超时比网关略长，网关的错误码才能回到页面。页面展示码和一句说明：未登录、被限流、库存不足、重复提交。堆栈留在服务端日志。

成功响应里是订单号和状态，页面跳到详情。超时之后用这把幂等键查一次订单在不在：在，就按成功展示；不在，再让用户重试。这次查询仍走后端。

### 后端

请求先到网关。网关校验令牌，从令牌取出用户 id，写进往下传的身份。请求体里客户端自己填的用户 id 被盖掉。限流按用户；没有登录态的接口按 IP。请求体超过上限直接拒绝。通过之后把请求 id 往下传。头里没有，FastAPI 自己生成，放进 `contextvars`。日志、Redis 和数据库操作都带上它。

FastAPI 处理这张单本身：参数是否齐全、数量是否为正、地址是否属于这个用户。网关不知道订单属主。

扣库存前，Redis 用一段 Lua 做原子判断。键还在、数量够，就减掉。Lua 在 Redis 里一次执行完，两个并发请求不会都读到「还剩 1」再都减成功。Redis 说不够，这里返回库存不足，MySQL 不打开事务。

Redis 说够了，才进 MySQL。一个事务里写三样：订单行、库存的条件更新、发件箱里的一条消息。库存更新写成：

```sql
UPDATE inventory
SET stock = stock - :n
WHERE id = :id AND stock >= :n
```

`rowcount` 为 0，整个事务回滚，并把 Redis 里刚减掉的数量加回去。三样一起提交，或一起没有。

事务提交之后，接口返回「已下单」。搜索索引、通知、下游单据留在事务外面。另一个循环扫发件箱里未发送的行，推到队列，成功再标成已发送。进程在推送前停了，重启会再推，消费者按订单号做幂等。

HTTP 调用和 Redis 调用放在这个事务外面。行锁占到提交为止，中间夹一次外部调用，会挡住别人改同一行库存。

秒杀是这条路径的变体，请求里不建单。活动库存预先写进 Redis，限购和扣减放在同一段 Lua 里，成功后把用户、SKU、请求 id 放进队列，消费者按数据库能承受的速度建单。订单表用用户加活动加 SKU，或用请求 id 做唯一键。普通下单仍在请求里把订单和发件箱一起提交。

### 数据库

MySQL 存必须对的数：订单、库存、发件箱。连接从进程级连接池取，请求结束归还。每个 worker 一份池。池的连接总数乘以副本数，要小于 MySQL 的 `max_connections`。

Redis 存可以重建的数：预扣的库存计数，以及后面会写上的详情缓存。Redis 丢了，用 MySQL 重新灌。MySQL 里没有的订单，就是没有这张单。

提交成功后删掉这张订单详情的 Redis 键。下一次读从 MySQL 回填。删失败就记一条待删，后台再删。键上的 TTL 是最后一道。

队列里的消费者晚于事务。用户已经看到订单号时，搜索里可能还没有这条。详情页读 MySQL，或读刚从 MySQL 回填的缓存。

## 读：打开订单详情

```text
浏览器 GET /orders/{id}
  → 网关：验令牌、限流
  → FastAPI：这张单属于这个用户
  → 本进程短缓存 → Redis → MySQL
  → 回填缓存，返回 JSON
```

### 前端

详情页用订单号发 GET。登录态和请求 id 与写请求同一套头。GET 可以安全重试。页面先保留上一份已经拿到的数据，新的响应到了再替换。未登录去登录页。订单不存在，停在说明页。

### 后端

网关同样验令牌和限流。FastAPI 确认这张订单属于头里的用户。订单号被猜中，属主不对，仍然拒绝。

读的顺序固定。先看本进程的短缓存，秒级 TTL。没有再看 Redis，分钟级 TTL。都没有再查 MySQL，查到后回填两级缓存。同一个订单号同时过期时，进程内按这个键加锁，只放一个协程去查库。这把锁只挡住本进程。多个进程同时过期，靠 Redis 锁。

查无此单也缓存一小段，避免别人用猜出来的订单号反复打到 MySQL。

### 数据库

这次读到的行来自 InnoDB 已提交的版本。普通 `SELECT` 不加锁。缓存键带业务版本，例如 `order:v3:{id}`。字段结构变了就换前缀，旧键等 TTL 自己消失。

每个 worker 有自己的一份短缓存。订单在别的进程里更新之后，本进程要等本地 TTL 结束才去看 Redis。所以本地用秒，Redis 用分钟。

## 时间与失败

超时从外往里变短。浏览器 3 秒，网关 2.5 秒，服务查库 2 秒。外层更长，内层的错误码才能回到页面。

网关先断开时，事务可能已经提交。超时之后前端用幂等键查结果。后端用同一把幂等键认出这是同一笔，不插第二张订单。

限流发生在网关，数据库还没被碰到。库存不足发生在 Redis 的 Lua，或 MySQL 的条件更新。页面对这两处用同一句「库存不足」。重复点击带着同一把幂等键，第二次看到的是已经写下的那张订单。

## 和模型请求的边界

上面是一笔业务读写。这次请求还要调用模型时，网关在鉴权之后把短请求转给 Python 编排，流式结果用 SSE 写回浏览器。长任务立刻返回 `task_id`，页面改为轮询或订阅进度。顺序、错误码和取消见 `Agent架构/01-请求全流程.md`。

订单和库存的落库方式不变。模型只提出下一步。扣库存仍由这段确定性代码执行。
