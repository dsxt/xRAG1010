## 2. P0｜LLM 推理基础

### 2.1 Token 与输入

- BPE / SentencePiece 分词；中文 token 数与字数的关系；token 计数决定成本和窗口
- chat template：system / user / assistant / tool 角色如何拼接成一段文本；模板不一致会导致指令跟随变差、工具调用格式错乱
- 位置编码 RoPE；长度外推 NTK / YaRN 的思路；「支持 128k」不等于 128k 内效果均匀，中间信息容易被忽略

### 2.2 Prefill 与 Decode

| 阶段 | 做什么 | 瓶颈 | 对应指标 |
| --- | --- | --- | --- |
| Prefill | 一次性计算整段 prompt，生成 KV | 计算密集 | TTFT（首 token 延迟） |
| Decode | 每步生成一个 token，读全部 KV | 访存密集 | TPOT / ITL（每 token 间隔） |

- Agent 每一轮都要 prefill：系统提示 + 工具定义 + 历史 + 新的工具结果。轮数越多，prefill 占比越高，这是 prefix caching 对 Agent 特别重要的原因

### 2.3 KV Cache

```
KV 显存 ≈ 2 × 层数 × KV 头数 × 头维度 × 序列长度 × 批大小 × 每元素字节数
```

- GQA / MQA：KV 头数少于注意力头数，直接按比例省显存
- 失效场景：前缀任何一处变化（system prompt、工具列表顺序、时间戳插在前面），之后的缓存全部作废
- **会话内稳定前缀是第一优化手段**：把会变的内容放到后面

### 2.4 vLLM 核心机制

| 机制 | 解决的问题 | 要点 |
| --- | --- | --- |
| PagedAttention | 连续分配 KV 导致碎片和预留浪费 | KV 按固定大小块分配，块表做逻辑到物理映射；相同前缀可以共享块 |
| Continuous batching | 按请求组批，短请求等长请求 | 按迭代调度，每步都可以加入或移出请求 |
| Prefix caching | 重复前缀重复计算 | 按块哈希命中；只能命中完整的前缀块 |
| Chunked prefill | 长 prompt 的 prefill 阻塞 decode | 把 prefill 切块与 decode 混合调度，平滑 ITL |
| 抢占 | KV 不够时 | **V1 引擎只做重算（recompute），GPU↔CPU KV 交换已移除，`swap_space` 参数已删除**；重算时靠 prefix caching 跳过已缓存部分 |

- 常用参数：`gpu_memory_utilization`、`max_model_len`、`max_num_seqs`、`max_num_batched_tokens`、`enable_prefix_caching`、`tensor_parallel_size`
- 频繁抢占的处理：降低 `max_num_seqs` / `max_num_batched_tokens`，提高显存占比，或加张量并行
- SGLang：RadixAttention 用前缀树管理 KV，多轮对话复用更自然；对结构化输出和多次调用编排友好

### 2.5 采样与结构化输出

| 参数 | Agent 场景 |
| --- | --- |
| temperature | 规划、工具选择用 0~0.3；创作类调高 |
| top_p / top_k | 与 temperature 不要同时激进 |
| repetition penalty | 过高会破坏 JSON 和代码 |
| stop | 工具调用场景要精确配置 |

- **约束解码**：按 JSON Schema 或语法在每步屏蔽非法 token。vLLM 支持 xgrammar、outlines、guidance 等后端
- 代价：复杂 schema 会拖慢首 token；约束只保证格式合法，不保证字段值正确
- 流式工具调用：`arguments` 是分片到达的 JSON 字符串，要拼接完整、`finish_reason` 表明结束后再解析

### 2.6 量化

| 格式 | 影响 | 建议 |
| --- | --- | --- |
| BF16 / FP16 | 基线 | 默认 |
| FP8 | 小 | Hopper / Ada 原生支持，性价比高 |
| AWQ / GPTQ INT4 | 中 | 工具调用格式错误率可能上升，上线前跑回归 |
| 更激进的低比特 | 大 | 不建议用于规划型 Agent |

- 量化回归要看的不是困惑度，而是：schema 遵循率、工具参数错误率、长上下文关键信息召回

### 2.7 指标与压测

- TTFT、TPOT / ITL、端到端延迟、吞吐（tokens/s、req/s）、排队深度、KV 使用率、抢占次数
- 压测要做并发梯度，画「并发数 → P50/P99 TTFT」曲线，找拐点
- 区分「单请求快」和「系统吞吐高」：continuous batching 提高吞吐但会拉长单请求 ITL

## 3. P0｜Agent 循环与工具调用

### 3.1 循环结构

```
准备上下文（系统提示、工具列表、历史、记忆）
→ 调模型（流式）
→ 解析：文本 / 工具调用
→ 校验参数 → 权限与策略检查 → 执行工具
→ 结果写回上下文（裁剪后）
→ 判断：继续 / 结束 / 要人确认 / 压缩
```

**手写一遍再用框架**。面试官区分候选人的方式，往往是问「框架帮你做了什么，出问题时你怎么定位」。

### 3.2 终止条件

| 策略 | 说明 |
| --- | --- |
| 轮次上限 | 最基本的兜底 |
| 预算上限 | token、费用、时间三种预算 |
| 重复检测 | 同一工具同一参数连续出现 |
| 完成判定 | 由编排器按状态和判据决定。模型不再调用工具只是信号，不能单独当成做完 |
| 无进展检测 | 连续 N 轮状态没有变化 |

### 3.3 推理范式

| 范式 | 机制 | 适用 | 风险 |
| --- | --- | --- | --- |
| ReAct | 思考 → 行动 → 观察 循环 | 通用工具任务 | 循环、动作漂移 |
| Plan-and-Execute | 先计划再执行，可重规划 | 步骤可预判的任务 | 计划过时 |
| Reflexion / 自我修正 | 失败后反思再试 | 有明确判据（测试、校验器） | 没有外部判据时越改越错 |
| Self-Consistency | 多次采样投票 | 高准确率的单点判断 | 成本 ×N |

推理模型普及后，显式写 CoT 的价值下降，关键变成「给什么工具、给什么判据、何时停」（见第 9 章）。

### 3.4 工具设计

- 工具名用动词短语；参数用业务语义；`description` 写清「何时用、何时不用」
- 能用 enum 就别用自由文本
- 工具数量：几十个以上时选择准确率下降。做法是按场景分组、动态加载（先给工具搜索，再把选中的工具加入当前上下文）
- 返回值：结构化、带编号和摘要；大结果给引用，让模型按需再取
- 错误作为结果返回模型：参数错误、权限拒绝、未找到，都写成模型能据此修正的信息，而不是抛异常中断循环
- 完成与否由编排器按状态和判据决定，不能只听模型说「做完了」
- 生产审计记输入版本、检索证据、计划摘要、工具请求与结果、策略判定、最终结果。隐藏思维链不展示给用户，也不写入长期记忆。供应商若要求把思考块原样带回下一轮，只放在当次请求里（第 9 章）
- 工具注册至少声明：版本与 Owner、Schema、风险等级、只读或写入、幂等键、超时重试限流、补偿动作、是否要确认、弃用日期。禁止模型自行拼任意 HTTP、SQL 或 Shell

### 3.5 执行治理

| 维度 | 做法 |
| --- | --- |
| 校验 | Pydantic 校验类型、范围、跨字段约束；失败把错误回灌给模型 |
| 超时 | 按工具分级；长任务异步化，返回任务号 |
| 重试 | 只有幂等工具自动重试，指数退避加抖动；写操作不自动重试 |
| 并发 | 只读工具并行；写同一资源的操作串行；外部状态变更整批串行 |
| 熔断 | 连续失败摘除工具，并告诉模型这个工具暂不可用 |
| 幂等 | 以 `tool_call_id` 或业务键做幂等键，存在数据库唯一约束上，不只靠 Redis 锁 |
| 截断 | 响应被截断导致参数不完整时，整批不执行 |

### 3.6 高危工具

- SQL：只读账号、表白名单、禁止 DDL/DML、行数上限、超时、结果脱敏
- 代码与命令：容器或微虚拟机隔离、禁网或出网白名单、CPU/内存/时间限额、文件系统只挂工作目录
- 发消息、付款、删除：必须人确认，或限定额度和对象

### 3.7 框架内的实现参照

- LangGraph：状态图 + 检查点；`interrupt()` 实现人在回路，恢复时会**重放整个节点**，节点里的副作用必须幂等
- OpenAI Agents SDK / Claude Agent SDK：把循环、工具、交接（handoff）、护栏封装好，适合快速起步；要深度控制时仍会回到手写循环

## 4. P0｜上下文工程与记忆

### 4.1 上下文预算

把窗口当成有容量的缓存，按优先级分配：

| 区块 | 特点 | 策略 |
| --- | --- | --- |
| 系统提示 + 工具定义 | 稳定 | 放最前面，保证前缀缓存命中 |
| 任务状态 / 结构化记忆 | 小而关键 | 每轮都带 |
| 近期对话原文 | 中 | 保留最近 N 轮 |
| 工具结果 | 大而易过期 | 消费后裁剪或替换成引用 |
| 检索片段 | 按需 | 控制条数与长度 |

### 4.2 压缩方案（按场景选，不存在固定排序）

| 方案 | 机制 | 适合 | 风险 |
| --- | --- | --- | --- |
| Observation Masking | 可重新获取的工具输出直接丢弃或换成引用 | 文件内容、列表、查询结果 | 依赖工具可重放、结果不变 |
| 结构化抽取 | 关键状态写成字段（订单号、已改文件、待办） | 业务字段明确 | 只覆盖已知字段 |
| 按需检索 | 历史存外部，用时检索 | 长期会话 | 检索不准就缺信息 |
| 滚动摘要 | 早期内容让模型摘要 | 其余手段不够时 | 有损，可能丢关键条件或编造 |

**组合用法**：上表没有放之四海的排序。组合时工具结果先 mask，关键状态结构化，摘要只压更早的对话，并且摘要里只放「索引」。当前状态用工具重新查，不信摘要里的数值。

### 4.3 压缩时机与细节

- 触发：窗口占用达到阈值（例如 60%~80%，按模型实测调）；工具结果被消费之后立即裁剪
- 切分点要保证工具调用和工具结果成对，不能切在中间
- 摘要请求本身不要污染主会话的前缀缓存
- 上下文溢出时：压缩一次后重试；仍溢出则报错，不要无限压

### 4.4 Prompt Caching（API 侧）

- 这是厂商按前缀计费的缓存，和第 2.3 节的 KV 块缓存不是同一个实现。缓存部分更便宜，TTFT 更短
- 失效条件与 2.3 相同：前缀要逐字节一致。稳定内容在前，工具定义不随轮次变化

### 4.5 记忆分层

| 层 | 内容 | 存储 | 关键问题 |
| --- | --- | --- | --- |
| 工作记忆 | 当前任务状态、近期消息 | 内存 / Redis | 过期清理 |
| 会话日志 | 全量事件，审计与回放 | 数据库，仅追加 | 体量、留存期 |
| 语义记忆 | 跨会话事实、用户偏好 | 向量库 | 检索不准、过时 |
| 结构化记忆 | 实体与关系 | 关系库 / 图 | 写入校验、冲突 |

- 写入：先校验来源与置信度，带来源标记；冲突时以新的、来源可信的为准，并保留旧值
- 遗忘：TTL、热度衰减、用户主动删除、合规删除
- 防污染：模型从网页、邮件读到的内容，不能直接写进长期记忆

## 5. P0｜RAG 全链路

### 5.1 链路

| 阶段 | 要点 |
| --- | --- |
| 解析 | PDF 版面、表格、扫描件 OCR、标题层级；解析质量决定上限 |
| 分块 | 固定长度 + 重叠；按结构（标题、段落）；父子块（子块召回、父块补上下文） |
| 元数据 | 来源、页码、版本、更新时间、权限标签——缺了后面都做不了 |
| 向量化 | bge-m3 / E5 / Jina 等；换模型必须全量重建索引，灰度双写 |
| 索引 | HNSW（`M`、`ef_construction`、`ef_search`）；IVF（`nlist`、`nprobe`）；PQ 量化省内存 |
| 检索 | 向量 + BM25 混合；RRF 融合（常用 k=60）；元数据过滤 |
| 重排 | Cross-encoder 重排，召回 TopN → 精排 TopK |
| 组装 | 去重、按相关度排序、token 预算、标注出处 |
| 生成 | 强制引用。检索为空时不编造：能澄清就澄清，没有可补信息再拒答。空召回和拒答分开统计（第 41 题） |

### 5.2 进阶

- 查询改写：多轮指代消解；口语改成检索语言；HyDE
- 查询分解：多跳问题拆子查询
- 自适应检索：先判断要不要检索
- Agentic RAG：把检索做成工具，让模型决定检索几次、检索什么。检索是否发生会改变权限、成本和评测归因时，由编排器写死，不交给模型。本仓库项目 P1 采用写死（第 29.3 节）
- 图 RAG：实体关系抽取，适合关系密集的问题；成本高，先证明普通 RAG 不够。本仓库不把它当主线（第 29.7 节）

### 5.3 评测（必须会算）

| 层 | 指标 |
| --- | --- |
| 检索 | Recall@k、MRR、nDCG |
| 生成 | 忠实度（答案能否被检索内容支持）、答案相关性、引用正确率 |
| 端到端 | 问题解决率、拒答准确率 |

- 数据集：从真实问题采样，人工标注标准答案和应命中的文档。学习实验 100 条起步（第 23 章实验 4）；本仓库闸门先用 30 题（第 29.6 节），分层和留出盲测的要求相同
- 排查顺序（后文都引用这一条）：知识是否存在且有效 → 解析 → 分块是否切断关键句 → ACL 是否滤错 → 正确块是否召回 → 融合或重排是否丢掉 → 是否因 token 截断没进上下文 → 提示是否要求依据证据 → 模型是否忠实使用证据。不要一错就换大模型

### 5.4 一致性

- 文档版本号 + 增量 upsert + 软删除 + 定期全量重建；原文删除要联动切片、向量、缓存和引用。先删后插不是事务，插入失败会空窗。切换用别名或双集合，查不到时回退旧版本（第 49 题）。本仓库目前仍是按 `file_title` 先删后插，这是现状，见第 29.3 节坏例 4
- 权限条件下推到检索请求里，召回前就过滤。先召回再在应用层丢掉无权结果，无权内容会进日志，也浪费配额
- 每个切片保存：`chunk_id`、`doc_id`、版本、原文位置、父级路径、租户与 ACL、生效时间、解析器 / 切片器 / Embedding 版本、内容哈希
- 可疑指令不要直接删掉改原文。隔离、标信任等级、禁止当系统指令，并留原始证据
- 向量值本身做普通加密会破坏近邻检索。保护靠访问控制、租户隔离、传输和磁盘加密
- 实时价格、库存、订单状态走数据库或 API，不用静态向量快照代替

## 6. P0｜评测与可观测

### 6.1 Agent 评测的层次

| 层 | 问题 | 方法 |
| --- | --- | --- |
| 结果评测 | 任务完成了吗 | 规则判据（测试通过、字段正确）优先；必要时 LLM 评审 |
| 轨迹评测 | 过程合理吗 | 工具选择是否正确、参数是否正确、多余步骤数、是否越权 |
| 组件评测 | 哪一环出问题 | 检索 Recall、工具调用准确率、单步决策 |
| 线上指标 | 用户是否满意 | 成功率、人工接管率、重试率、成本、延迟 |

- **pass@k 与 pass^k**：前者是 k 次里至少成功一次；后者是 k 次全部成功，更能反映稳定性，生产更该看后者
- 公开基准可以参考：函数调用（BFCL）、工具交互（τ-bench）、编码（SWE-bench Verified）、浏览器与 GUI（WebArena、OSWorld）。面试用来说明你知道怎么衡量，不必背分数

### 6.2 数据集

- 来源：线上真实请求抽样 + 人工确认的坏例 + 必守的固定用例（权限、格式、危险操作）
- 数据集分层：金标、回归、难例、对抗、新鲜流量。评分器、标注规范和数据集一起版本化
- 发布硬门槛：任务成功率不低于基线；高风险错误和 ACL 泄露为 0；延迟、错误率、单任务成本不越线；对抗集通过；人工接管和降级可用
- 一次发布绑定的是版本集合：代码、工作流、Prompt、模型与路由、工具契约、策略、Embedding / Reranker、知识快照与索引、Schema、Feature Flag。Trace 里要能反查这套集合
- 每条用例写清输入、期望结果或判据、允许的工具
- 防过拟合：留一部分盲测集，不参与调 prompt

### 6.3 LLM 评审

- 已知偏差：偏好长答案、偏好格式规整、位置偏好、偏好与自己同源的输出、对专业错误不敏感
- 治理：规则校验做硬基线；评审 prompt 和模型版本固定并纳入版本管理；成对比较时交换位置；定期抽样人工校准一致率

### 6.4 回归门禁

```
改动（prompt / 工具描述 / 模型 / 检索参数）
→ 跑数据集 → 与上一版对比
→ 低于基线不发布 → 通过后灰度 → 线上抽样评分写回 Trace
→ 确认的坏例补回数据集
```

### 6.5 可观测（以 Langfuse 为例）

| 层 | 对象 |
| --- | --- |
| trace | 一次用户请求或一个任务 |
| span | 一轮循环、一次工具调用、一次检索 |
| generation | 一次模型调用：模型名、输入输出、token、费用、延迟 |

- 关联字段：session、user、prompt 版本、工具版本、任务编号
- 失败分类（每类单独计数和告警）：模型侧（格式错、幻觉、截断）、工具侧（参数错、超时、权限拒绝）、循环侧（死循环、目标漂移、上下文溢出）、编排侧（路由错、交接失败）
- 自托管注意：Langfuse 依赖 ClickHouse、Postgres、Redis；高写入时 ClickHouse 是压力点；埋点必须异步，不能阻塞主链路；错误请求全采样，正常请求按比例采样

## 7. P0｜Python 异步与服务工程

### 7.1 asyncio（Agent 运行时最容易出错的地方）

- 同步阻塞调用（requests、同步数据库驱动、CPU 重活）会卡住整个事件循环；用异步库，或放进线程池 / 进程池
- **取消**：`task.cancel()` 在下一个 await 点抛 `CancelledError`；捕获后要清理并重新抛出，不能吞掉
- **超时**：`asyncio.timeout()` / `wait_for`；超时本质也是取消
- **结构化并发**：`asyncio.TaskGroup`，一个子任务失败，其余被取消，异常聚合抛出
- 背压：有界 `asyncio.Queue`；生产者在队列满时等待
- 并发上限：`asyncio.Semaphore` 限制同时调用模型或工具的数量
- GIL：IO 密集用异步或线程；CPU 密集用多进程

### 7.2 流式

- SSE 格式：`data:` 行、空行分隔、`[DONE]` 结束；网关和 Nginx 要关闭缓冲
- 一次生成：客户端断开要取消这次上游模型请求，否则继续烧 token
- 多步任务：连接断开不会自动停掉后续工具。要停，就置取消标记，并在每次模型调用和工具调用前检查（第 47 题）。项目 P1 目前做不到，见第 29.3 节坏例 11
- 断线续传：事件带序号，客户端用 `Last-Event-ID` 续接
- WebSocket：需要双向（打断、追加输入）时用

### 7.3 FastAPI

- 依赖注入、生命周期（startup 初始化连接池）、`StreamingResponse`
- `async def` 里不能放阻塞调用；`def` 路由会在线程池执行
- 部署：gunicorn + UvicornWorker；worker 数与连接池大小匹配

### 7.4 中间件

- Redis：缓存、分布式锁（`SET NX PX` + 唯一值 + Lua 校验释放）、限流、Stream 做轻量队列
- 锁的边界：锁会过期，持锁进程可能在提交前死掉——资金类操作的最终保障是数据库唯一约束和幂等表
- 消息队列：Kafka（分区内有序、消费组、至少一次投递需消费端幂等）；RabbitMQ（ACK、死信、延迟队列）
- 数据库：事务隔离级别、索引、慢查询；PostgreSQL + pgvector 适合中小规模向量检索

## 8. P0｜生产稳定性与成本

### 8.1 降级

| 依赖不可用 | 降级 |
| --- | --- |
| 主模型 | 切备用模型或小模型；排队；明确告知用户 |
| 工具 / MCP | 熔断并告诉模型该工具不可用；Agent 不崩 |
| 向量库 | 退化为关键词检索 |
| 观测平台 | 本地缓冲，异步重试，不阻塞主链路 |

### 8.2 分层限流

| 层 | 对象 |
| --- | --- |
| 网关 | 租户 / 用户 / 模型的请求数与 token 速率 |
| Agent | 单任务 token 与费用预算、轮次上限 |
| 推理服务 | 排队深度、并发序列数 |
| 工具 | 单工具并发与 QPS |

### 8.3 审计与幂等

- 副作用操作在第 3.4 节的 Trace 字段之外，再记用户、任务、轮次和时间；日志仅追加
- 带副作用的工具都要有幂等键；不可幂等的操作走人确认。模型调用的重试规则在第 8.5 节，不自动套到写工具上

### 8.4 成本治理

| 手段 | 说明 |
| --- | --- |
| 模型路由 | 简单任务用小模型；路由本身要评测 |
| 前缀缓存 | 稳定前缀，提高缓存命中 |
| 上下文治理 | 工具结果裁剪、摘要、按需检索 |
| 减少无效轮次 | 终止条件、更好的工具描述 |
| 语义缓存 | 相似问题直接返回；只适合答案不随人和时间变化的场景，需要设阈值和失效策略 |
| 批处理 | 离线任务走批量接口 |

成本要按任务、用户、工具类型分摊，而不是只看模型账单总额。

### 8.5 容量、容灾与灰度

- 在途请求 ≈ 到达率 × 平均处理时长；模型 token 吞吐 ≈ QPS × 每请求平均 token；工具峰值 ≈ 请求量 × 平均工具次数；所需 Worker ≈ 到达率 × 平均任务时长 ÷ 单 Worker 并发。按峰值持续时间和故障后的 N+1 算，不按日均 QPS
- 队列积压时先看到达率是否已经高于消费率。下游已饱和时，先限流和降优先级，不要盲目加 Worker
- 模型错误分类：429 / 超时 / 5xx 可以受控重试或切备用；400 修调用，不切换；内容安全拒绝不换模型绕过；上下文超限则压缩或拒绝。这只覆盖模型调用。写工具仍按第 3.5 节，没有幂等键不自动重试。备用模型要提前验证工具 Schema、JSON、上下文长度和安全策略。接口能调通不等于业务容灾成功
- 放量顺序：离线评测 → Shadow → 内部用户 → 白名单 → 低风险辅助 → 小流量执行 → 分阶段扩量。观察窗口内看成功率、接管、越权、重复执行、P99、429、单任务成本和安全事件。不可逆错误、泄露、越权立即停写并回滚
- 回滚包含代码、数据库、索引、Prompt、策略和模型路由，不只回滚镜像

## 9. P1｜推理模型与规划

- 推理模型在回答前生成思考内容，按 token 计费，延迟更高
- 何时用：规划、复杂多步决策、代码与数学；何时不用：简单分类、格式转换、高频低延迟路由
- 思考预算：控制思考长度或强度，按任务难度分档
- 思考与工具交错：多轮工具调用时，部分 API 要求把上一轮的思考内容原样回传，否则影响后续推理或缓存，接入时按各家文档处理
- 组合模式：推理模型做规划和检查，普通模型做执行；或反过来，普通模型执行、失败时升级到推理模型
- 显式 CoT 提示对推理模型收益有限，重点放在：清晰目标、可验证判据、合适的工具

## 12. P1｜多 Agent 与框架选型

### 12.1 先问要不要多 Agent

多 Agent 带来：上下文隔离、并行、专业化分工。代价：token 成倍增长、交接时信息丢失、调试困难。
**单 Agent + 好工具能做的，先不用多 Agent。**

### 12.2 常见架构

| 架构 | 机制 | 适合 | 风险 |
| --- | --- | --- | --- |
| Orchestrator-Worker | 主 Agent 拆任务、分派、汇总 | 可并行的调研、批量处理 | 主 Agent 成为瓶颈；子任务描述不清 |
| 交接（handoff） | 按意图把对话交给专门 Agent | 客服分流 | 交接时上下文丢失 |
| 生成 + 评审 | 一个生成、一个按判据检查 | 有明确标准的产出 | 成本翻倍；评审标准模糊时无效 |
| 对等协商 | 多 Agent 自由对话 | 研究、头脑风暴 | 跑题、无限对话、难收敛 |

### 12.3 框架

| 框架 | 定位 | 适合 |
| --- | --- | --- |
| LangGraph | 图状态机 + 检查点 + 人在回路 | 需要精确控制流程、可恢复的生产流程 |
| OpenAI Agents SDK | 轻量：Agent、工具、handoff、护栏、tracing | 快速搭建，OpenAI 生态 |
| Claude Agent SDK | 基于 Claude Code 的运行时：文件、命令、子 Agent、MCP | 编码与操作类 Agent |
| Google ADK | 多 Agent 编排，与 Google 生态集成 | Gemini / GCP 场景 |
| CrewAI | 角色 + 任务 + 流程（顺序 / 层级） | 固定流水线、快速原型 |
| Microsoft Agent Framework | AutoGen 与 Semantic Kernel 合并后的继任者，图工作流 + 多 Agent | 微软生态、企业场景 |

- **AutoGen 已归档，不再维护**，微软建议迁移到 Microsoft Agent Framework。面试被问到 AutoGen，讲它的思想（对话式多 Agent、群聊选发言人），同时说明现状
- 选型讲法：控制力需求、可恢复性、可观测、团队生态、厂商锁定

### 12.4 多 Agent 的工程问题

- 交接时传什么：任务目标、约束、已完成内容、产物引用；不要整段历史
- 共享状态冲突：版本号、乐观锁、按资源串行
- 可观测：每个 Agent 一个 span，交接关系可追踪
- 预算：整个任务一个总预算，子 Agent 分配额度

## 13. P1｜MCP 与 A2A

### 13.1 MCP（以 2026-07-28 版规范为准）

- 作用：标准化应用向模型暴露工具、资源、提示模板的方式
- 与 Function Calling 的关系：Function Calling 是模型决定调用什么；MCP 是工具如何被发现、描述和调用的协议，两者在不同层
- 角色：Host（应用）/ Client / Server
- **标准传输只有两种**：

| 传输 | 适用 | 要点 |
| --- | --- | --- |
| stdio | 本地子进程 | 凭据从环境变量取；要管子进程生命周期、超时、日志 |
| Streamable HTTP | 远程服务 | 单一端点，每条消息一个 POST；响应为 JSON 或该请求范围内的 SSE 流；必须校验 `Origin` 防 DNS rebinding；本地运行只绑定 127.0.0.1 |

- 早期的 HTTP+SSE 传输已被 Streamable HTTP 取代；WebSocket 不是标准传输
- 2026-07-28 版本移除了 GET 流端点和协议层会话，服务端向客户端的交互改为嵌在结果里的多轮请求；接入不同版本时要处理兼容
- **授权**：HTTP 传输下按 OAuth 2.1，客户端每个请求带 Bearer token，服务端校验 token 的签发方和受众，通过 Protected Resource Metadata 发现授权服务器
- 协议管「客户端能否访问这个 Server」；**按工具、按参数、按调用人的细粒度策略仍要在 Host / Harness 层做**

### 13.2 MCP 工程问题

- 工具描述来自第三方 Server，可能被投毒（描述里藏指令），接入前要审查并固定版本
- 多 Agent 共用一个 Server 时注意状态串扰
- 工具报错要翻译成模型可理解的结构化错误
- 什么时候不值得上 MCP：进程内、要低延迟、只有一个调用方，直接调函数。MCP 解决发现、传输和能力协商，不提高智能，也不代替服务端鉴权。本仓库仍用它包两个只读工具，用来练协议（第 29.4 节）

### 13.3 A2A

- 作用：跨系统、跨团队的 Agent 之间互相发现能力、委派任务、同步状态
- 与编排框架不在一层：框架管一个系统内部怎么编排；A2A 管系统之间怎么通信
- 同一业务内部的子 Agent，中心化编排更好调试

## 14. P1｜AI 网关

| 能力 | 说明 |
| --- | --- |
| 协议统一 | 对外统一 OpenAI 兼容格式，对接各家与自建推理服务 |
| 密钥隔离 | 业务不持有上游密钥 |
| 路由 | 按任务类型、长度、成本、可用性路由；主备切换 |
| 流量治理 | 限流、熔断、退避重试、单任务 / 单租户 token 硬上限 |
| 成本审计 | 按租户、用户、应用统计 |

- 接入网关和模型网关不是一层。接入网关管身份、签名、防重放、租户限流、请求大小、Trace、一键只读。模型网关管厂商差异、能力标签、路由、配额、熔断和 token 账单

- **工具调用完整性**：部分中转只兼容文本，工具调用字段、流式分片处理不完整，上线前必须完整测试工具调用链路

## 15. P1｜安全与权限

### 15.1 提示注入

- **直接注入**：用户输入里要求模型忽略指令
- **间接注入**：网页、邮件、文档、工具返回、MCP 工具描述中藏指令——Agent 场景的主要威胁
- 高危组合：Agent 同时具备「读取私有数据」「接触不可信内容」「能向外发送数据」三者时，注入可以导致数据外泄。设计时至少切断其一

### 15.2 防御分层

| 层 | 做法 |
| --- | --- |
| 权限 | 最小工具集；工具按用户身份执行，而不是用 Agent 的超级权限 |
| 隔离 | 不可信内容明确标记为数据；读不可信内容的子 Agent 不给高危工具 |
| 动作 | 高危动作人确认；出站请求白名单；金额与范围上限 |
| 检测 | 输入输出过滤、规则或小模型校验动作合法性 |
| 沙箱 | 代码和命令不在宿主机执行 |
| 审计 | 所有副作用可追溯 |

没有一层能单独防住注入，**原则是假设模型会被说服，靠权限和动作约束兜底**。

### 15.3 数据

- RAG 按第 5.4 节在召回前过滤；向量库按租户分区
- PII 在入库前、注入上下文前脱敏
- 记忆删除接口、数据不出域、审计留存

## 16. P1｜长任务与持久执行

- 问题：任务跑几分钟到几小时，进程会重启，调用会超时，人会晚回复
- 持久执行：每一步结果落盘，崩溃后从最后完成的步骤继续（Temporal 一类工作流引擎；LangGraph 检查点）
- 要求：步骤幂等或可去重；不可重复的副作用要记录已执行
- 补偿：多步操作中途失败时，按逆序执行补偿动作（Saga 思路）
- 人在回路：任务挂起等待确认，有超时和提醒；恢复时状态完整
- 长任务先落库再执行；中断后只自动恢复声明可重复执行的步骤

## 19. P2｜Harness 设计模式（Pi / DSH / Super-agent）

> 这三个项目都处于开发者预览或研究原型阶段，**面试谈设计模式，不吹生产落地**。版本变化快，具体细节以官方文档为准。

### 19.1 Harness 的定义

Harness = 模型之外的一切：循环、工具、环境、状态、会话、权限、观测。

### 19.2 五个可迁移的设计模式

| 模式 | 含义 | 例子 |
| --- | --- | --- |
| 循环事件化 | 每一步发出事件，权限、记忆、日志作为监听器挂上去，不改循环源码 | DSH 的事件流水线：`agent/pre-step`、`agent/request`、`tools/pre-execute` 等扩展点 |
| 能力接口化 | 依赖「能力接口」而非具体实现，换环境时模型看到的工具不变 | DSH 的 Capability Seam：FS 服务可以是本地、远程或沙箱实现 |
| 模型可见即留痕 | 进入模型请求的内容都能从日志重建 | DSH 的仅追加会话事件日志 |
| 会话树 | 会话可从任意节点分叉，支持回退与试错 | Pi 的树状会话 |
| 极简内核 | 内核小，能力靠扩展包组合 | Pi 不内置子 Agent 和计划模式 |

### 19.3 Pi（`earendil-works/pi`）

- 极简终端编码 Agent Harness，TypeScript
- 包分层：provider 抽象（`pi-ai`）、Agent 循环（`pi-agent-core`）、MCP 接入（`pi-mcp`）、脚本执行（`pi-codemode`）、终端 UI（`pi-tui`）
- 工具前后钩子 `beforeToolCall` / `afterToolCall`，是权限、审计、埋点的切面
- **会话分叉只分叉对话，不回滚环境**：已写的文件、已发的请求不会撤销，要做环境回滚需外接沙箱快照
- codemode 让模型写脚本调用工具，执行隔离较轻，生产要放进沙箱

### 19.4 DSH（`deepseek-ai/deepseek-harness`）

- 基于 Cordis 插件系统，模型、工具、会话、沙箱、存储、循环都是插件；内核只管加载、依赖和事件
- 组合层次：plugin → bundle → profile
- 风险 `[推演]`：同一服务多个提供方时的覆盖顺序问题，需要锁版本；在同步监听器里做重活会拖慢整轮；插件版本变化后旧日志回放可能不一致
- 与 LangGraph 的关系：DSH 偏运行时底座（工具、沙箱、事件），LangGraph 偏业务流程编排，可以分层组合

### 19.5 Super-agent（DSH 之上的长期多任务系统）

| 机制 | 解决的问题 |
| --- | --- |
| Router / Worker | Router 负责接收事件、分派、对外沟通，不做耗时执行；Worker 独立会话并发执行 |
| Fast / Slow Path | 能用规则过滤的事件不交给模型 |
| Thread Subscription | Worker 订阅相关事件流，后续事件直达，不重复路由；要管理订阅生命周期，防止泄漏 |
| Inline & Spill | 当前需要的放进上下文，其余存外部只留引用 |
| Chain of Recall | 沿 事件 → 线程 → 任务 → 会话 的引用链恢复历史 |
| Watchdog | 不只查进程活着，还判断执行是否仍在推进目标；默认告警，自动干预要有开关 |

- 公开实验结论：双层结构缩短完成时间、改善长尾，代价是多个独立会话带来更多缓存读取 token，即用计算换并发与稳定性
- 官方原型声明仅供研究，非生产就绪

### 24.2 例：售后工单 Agent

## 25. 题库（带答案要点）

> 标 `[推演]` 的是基于工程经验的判断，不是官方结论；面试时说「我的判断是」。

### 推理基础

1. **PagedAttention 解决什么？**
   连续分配 KV 要按最大长度预留，造成碎片与浪费。改为固定大小的块按需分配，块表映射逻辑位置；同前缀的请求可共享块。代价是注意力计算要按块表间接寻址。

2. **prefill 和 decode 瓶颈分别是什么？**
   prefill 一次算整段 prompt，矩阵乘为主，计算密集；decode 每步一个 token，却要读全部权重和 KV，访存密集。所以 decode 靠批量提高利用率，prefill 靠缓存避免重复。

3. **prefix caching 何时命中？**
   请求前缀与已缓存的块逐 token 一致，且只能命中完整的块。系统提示里插入时间、工具顺序变化都会导致失效。

4. **KV 不够时 vLLM 怎么办？**
   V1 引擎抢占部分请求，释放其 KV，之后重算；不再做 CPU 交换。频繁抢占时降低并发序列数或每批 token 数、提高显存占比、加张量并行。

5. **量化后工具调用变差，怎么判断是量化导致的？**
   固定 prompt 和数据集，只换量化版本，对比 schema 遵循率与参数错误率；再看错误集中在长上下文还是复杂 schema。

### Agent 循环与工具

6. **怎么防 Agent 无限循环？**
   轮次上限、token / 费用 / 时间预算、同工具同参数重复检测、无进展检测、明确的完成判据，至少组合三种。

7. **模型总是输出不合法的工具调用？**
   约束解码保证格式；简化 schema、用 enum；描述写清何时用；校验失败把错误回灌让模型修正；仍失败则降级或转人工。

8. **工具返回超大文本？**
   截断加提示；提取结构化字段；存外部只返回引用和摘要；可重取的结果消费后从上下文移除。

9. **两个并行工具改同一资源？**
   读可以并行，写同一资源串行；用版本号或乐观锁检测冲突；外部状态变更整批串行执行。

10. **为什么写操作不自动重试？**
    无法确定上次是否已经生效，重试可能造成重复扣款、重复发送。要么有幂等键，要么查询状态后再决定，要么交给人。

11. **工具很多（上百个）怎么办？**
    分组、按场景动态加载；先提供工具搜索，选中后再加入上下文；评测工具选择准确率。

12. **LangGraph 的 interrupt 有什么坑？**
    恢复时整个节点重新执行，interrupt 之前的副作用会再做一遍。副作用放到 interrupt 之后，或做成幂等。

### 上下文与记忆

13. **压缩方案怎么选？**
    看工具结果能否重取（能则 mask）、关键状态能否结构化（能则字段化）、历史是否需要语义检索；摘要放最后，只压早期内容，摘要里放索引，当前状态重新查询。

14. **摘要压缩有什么风险，怎么缓解？**
    丢条件、编造细节。缓解：关键状态不放摘要而放结构化字段；摘要附引用编号；用到的状态用工具重新查询；压缩前后在数据集上对比成功率。

15. **跨会话记忆怎么防污染？**
    写入校验和来源标记；不可信来源不直接写长期记忆；冲突检测；定期过期；用户可查看和删除。

16. **为什么 Agent 更需要前缀缓存？**
    每轮都要重新 prefill 系统提示、工具定义和历史，前缀高度重复；保持前缀稳定可大幅降低 TTFT 与费用。

### RAG

17. **召回差怎么排查？**
    按第 5.3 节的顺序走完，每步用对应指标，不要一错就换模型。检索层再单独看：向量模型是否适合领域、索引参数、查询改写、混合检索是否补上了精确匹配。

18. **什么时候混合检索收益明显？**
    专有名词、编号、代码、型号多的场景，向量检索容易漏精确匹配，BM25 能补上；纯语义问题收益较小。

19. **文档更新如何保证一致？**
    版本号、增量 upsert、软删除、定期全量重建；换向量模型必须全量重建并灰度切换。

### 评测与可观测

20. **怎么搭 Agent 评测体系？**
    结果评测（规则判据优先）+ 轨迹评测（工具选择与参数）+ 组件评测（检索、单步）+ 线上指标；数据集来自真实请求和坏例；改动必须过回归门禁。

21. **pass@k 和 pass^k 的区别？**
    pass@k 是 k 次里至少一次成功，衡量能力上限；pass^k 是 k 次都成功，衡量稳定性。生产关心后者。

22. **LLM 评审的偏差与治理？**
    偏好长答案、偏好格式、位置偏好、同源偏好。治理：规则硬校验优先、固定评审版本、交换位置、定期人工校准一致率。

23. **线上成功率下降，怎么排查？**
    先按失败分类看哪一类上升；对照最近的改动（prompt、模型、工具、数据）；抽 Trace 看具体轨迹；在数据集上复现后回滚或修复。

### Python 与服务

24. **asyncio 里取消要注意什么？**
    `CancelledError` 要在清理后重新抛出；超时本质是取消；用 TaskGroup 让子任务一起失败一起取消；客户端断开时要取消上游模型请求。

25. **FastAPI 接口突然整体变慢？**
    先查 `async def` 里是否有同步阻塞调用卡住事件循环；再看连接池耗尽、上游延迟、GIL 竞争的 CPU 重活。

26. **Redis 分布式锁能防重复放款吗？**
    不能单独保证：锁会过期，进程可能在提交前死掉。最终保障是数据库唯一约束或幂等表，锁只用来减少并发冲突。

### 多 Agent 与框架

27. **什么时候该用多 Agent？**
    任务可以并行、子任务需要上下文隔离、或需要独立的评审角色时。否则单 Agent 更便宜、更好调试。

28. **LangGraph、OpenAI Agents SDK、CrewAI 怎么选？**
    要精确控制流程和可恢复：LangGraph；快速搭建、OpenAI 生态：Agents SDK；固定角色流水线原型：CrewAI。还要看可观测、团队熟悉度和锁定风险。

29. **AutoGen 现在还能用吗？**
    已归档、不再维护，微软建议迁移到 Microsoft Agent Framework。可以讲它的群聊式多 Agent 思想，新项目不用它。

30. **多 Agent 交接时信息丢失怎么办？**
    交接内容结构化：目标、约束、已完成、产物引用；子 Agent 的结果有固定格式；交接关系在 Trace 中可见。

### MCP 与安全

31. **MCP 有权限控制吗？**
    HTTP 传输下有基于 OAuth 2.1 的授权，控制客户端能否访问 Server；按工具、参数和调用人的细粒度策略仍需在应用层做。

32. **MCP 有哪些传输？**
    stdio 和 Streamable HTTP。旧的 HTTP+SSE 已被取代；Streamable HTTP 要校验 `Origin`，本地只绑 127.0.0.1。

33. **间接提示注入怎么防？**
    假设模型会被说服：不可信内容标记为数据；读不可信内容的环节不给高危工具；出站白名单；高危动作人确认；避免同时具备私有数据、不可信输入、外发能力三者。

34. **SQL Agent 怎么防删库？**
    只读账号、表白名单、禁止 DDL/DML、行数和超时上限、结果脱敏。

### 进阶

35. **推理模型什么时候用？**
    规划、复杂决策、代码；简单路由和格式转换不用。可以推理模型规划、普通模型执行，或失败时升级。

36. **什么时候该微调？**
    格式和工具调用不稳且 prompt 解决不了、需要用小模型降成本降延迟时；缺知识用 RAG，不用微调。

37. **编码 Agent 常见失败？**
    改错文件、编辑格式不匹配、没跑测试就宣布完成、为通过测试改测试。对策：仓库地图、可校验的编辑格式、强制跑测试、禁止修改测试或单独审查。

38. **Pi 的会话分叉能回滚环境吗？**
    不能。分叉的是对话记录，文件和外部调用不会撤销；要回滚需外接沙箱快照。

39. **Super-agent 的 Router 和普通协调者有什么不同？**
    Router 只做接收、分派和沟通，不做耗时执行；Worker 独立会话并发；事件驱动、订阅直达，适合多个长期任务并行。

40. **DSH 的监听器里做重活会怎样？** `[推演]`
    如果监听器在关键路径上同步执行，会拖慢整轮；复杂判断应异步化或放到独立 Worker。以官方实现为准。

41. **拒答和空召回为什么不是一个指标？**
    空召回是检索结果，拒答是决策。有召回但证据不足也该拒答；空召回也可能该澄清。合成一个「没答出来」，会把检索故障和谨慎拒答混在一起。

42. **RAGAS 四项够不够？**
    faithfulness、answer relevancy、context precision、context recall 只说明「像不像被证据支持、像不像切题、相关片段排得前不前、该有的信息召回没有」。它们依赖评审模型，对数字和引用格式不敏感，也分不开检索错和生成错。另外看 citation precision、拒答正确率和任务成功率。

43. **检索错和生成错怎么分开？**
    gold chunk 不在 top-k 是检索失败；在 top-k 里但答案错是生成失败。只把 gold 片段喂给生成器：这时答对，问题在检索；仍错，问题在提示、生成或校验。

44. **幂等键为什么不能带时间窗？**
    重试可能落在窗外，变成第二条记录。键用业务唯一键加客户端请求 ID，时间窗只用于展示或清理。

45. **什么时候不必上 MCP？**
    进程内、要低延迟、只有一个调用方时直接调函数。MCP 解决发现、传输和能力协商，不提高智能，也不代替服务端鉴权。

46. **会话历史能代替 Checkpoint 吗？**
    不能。历史只有文本，没有节点位置、未完成的中断和结构化状态。停在澄清或确认时，要靠 Checkpoint 回到断点。

47. **断开连接和取消任务差在哪？**
    一次生成的流：断开后要取消这次上游请求，否则继续烧 token。多步任务：断开本身不会停掉后续工具；取消要另置标记，并在每次模型调用和工具调用前检查。

48. **存活探针和就绪探针各探什么？**
    存活失败就重启进程。就绪失败摘掉流量但不重启，用来表示数据库、向量库、模型依赖不可用。依赖全挂时，摘流量比反复重启安全。

49. **索引更新出现空窗怎么办？**
    先删后插不是事务。用别名或双集合切换，查不到时回退旧版本，并监控该文档条数掉到 0。

50. **过滤表达式注入怎么防？**
    表达式由代码拼，用户输入只当值。转义或参数化，并用 allowlist。不把整段表达式交给模型。补一条「不转义会扩大命中范围」的对照。

## 28. 企业落地生命周期

这一章只保留第 3–16 章没有展开的落地动作。循环、RAG、评测、网关、安全和多 Agent 的机制仍看前面。

### 28.1 三条主线

- 业务：目标 → 基线 → 场景 → 验收指标 → 试点 → 收益兑现
- 技术：数据 → 检索 → 模型 → Agent → 工具 → 工作流 → 接口 → 基础设施
- 治理：身份 → 权限 → 策略 → 安全 → 审计 → 监控 → 应急 → 退役

落地时多出来的四条，机制本身看前面：

- 模型不负责最终授权。权限、金额、数据范围由确定性系统控制（动作规则见第 20 章）
- 不可信输入的范围见第 15.1 节；落地时把其他 Agent 的输出也算进去
- 高风险动作在第 3.6 节的确认之外，还要能暂停和补偿
- 发布物是第 6.2 节的版本集合。没有上线前的同口径基线，就不能把之后的变化算成 Agent 的功劳

### 28.2 阶段门

`行业发现 → 立项 → 流程拆解 → 场景选型 → 方案 → 数据/RAG → Agent 与工具 → 评测与安全 → 部署 → 灰度 → 运营 → 退役`

每个阶段写清输入、活动、产物、放行条件和指标。下面的表是放行检查，不是另一套阶段名：拆解含流程拆解和场景选型；架构含方案；开发含数据、Agent 与工具；验收含评测与安全；放量含部署和灰度。行业发现并进立项，退役并进运营。

| 阶段 | 放行条件 |
| --- | --- |
| 立项 | 痛点有量化证据；有业务 Owner；和其他方案比过；PoC 成败能客观判断 |
| 拆解 | 每个任务有触发、输入、输出、成功标准、异常、责任人和证据 |
| 架构 | 业务、数据、安全、测试、运维联评通过；能部署、观测、降级、回滚 |
| 开发 | 可重复构建、可测试、可追踪。本地能跑不算过门 |
| 验收 | 功能、RAG、工具、性能、故障恢复、注入与越权、UAT、运维可接管，一起过 |
| 放量 | 安全、不可逆错误或数据一致性越线，立刻停 |
| 运营 | SLO、坏例、漂移、成本、漏洞、灾备、供应商退出、退役都有人 |

立项时先比较规则引擎、搜索、工作流、RPA 和普通程序。条件和动作固定用规则；流程固定用工作流；精确查询用搜索或数据库；没有接口的重复页面操作才考虑受控 RPA；金额和权限用程序。Agent 适合非结构化输入、路径有限可变、工具受控、结果可验证、错误能被发现。

形态按写权限递增：知识助手（只读加引用）→ 草稿 Copilot（人提交）→ 工作流里的模型节点 → 工具型 Agent → 审批型 Agent → 多 Agent。多步骤不等于多 Agent。

### 28.3 策略层和数据准入

策略层独立于模型，决定谁能用哪个 Agent、能看哪些知识、能调哪些工具和参数、哪些内容要阻断或转人工、哪些模型和处理地域可用。单任务的 token、时间、步骤和费用上限沿用第 3.2 节。策略要版本化、可灰度和可回滚。

数据进系统前先回答：所有者是谁、能否给第三方模型、敏感等级、谁可见、保留多久、原文删除后切片和向量怎么联动删、争议时能否回到原版本。

知识流水线：`采集 → 格式与病毒检查 → 解析 → 清洗 → 分级 → 脱敏 → 信任标记 → 切片 → Embedding → 索引 → 抽检 → 发布`。

固定长度切片只是实验起点（通用文本可从 512–1024 token、overlap 10%–20% 试），必须用金标集调，不是标准答案。本仓库项目 P1 用标题切分，父子块要等题集证明缺它再加（第 29.2 节）。

存储按问题选：专有名词用全文检索；中小规模可 PostgreSQL + pgvector；极小数据才用应用内计算；对象存储做离线构建，不直接扛在线查询；图数据库补关系，不替代向量和全文；本地文件索引要另做多副本。生产常见组合是全文 + 向量 + 结构化查询 + 重排。

### 28.4 故障处理

十步：确认影响 → 定级 → 先止损 → 指定指挥、操作、记录三人 → 收指标、日志、Trace 和变更时间线 → 分层定界 → 每条假设写支持、反证和下一步 → 固定版本做最小复现 → 技术恢复后再跑业务旅程和对账 → 复盘触发因素、根因、放大因素和哪道控制失效。一次只改一个变量。恢复优先于追根。

| 现象 | 先做什么 |
| --- | --- |
| 回答变差 | 排查顺序同第 5.3 节，再核对是否换了模型或路由；临时回退；案例进回归集 |
| 延迟突增 | 拆成入口排队、策略、检索、模型排队、首 token、生成、工具、落库。对照流量、饱和、慢依赖、长 Prompt、缓存失效、重试放大 |
| 队列积压 | 口径同第 8.5 节：先比到达率和消费率，下游饱和先限流。再查毒消息 |
| 模型 429 | 看配额和并发；重试有总预算、退避和抖动，只在一层做（第 14 章）；熔断后切已验证的备用模型 |
| 重复写入 | 先关自动重试或写能力；用幂等键对账；再补状态查询和回归 |
| 泄露或越权 | 关工具、知识库或租户；轮换凭证；保全审计；走通报。不能只改 Prompt |

证据包在第 3.4、8.3 节的审计字段上，再加：`trace_id`、`request_id`、`session_id`、`task_id`、租户、各阶段耗时、版本集合、召回文档和 ACL、token 与首 token、工具幂等键和审批、降级或拒绝原因。

复盘要有永久修复、新增测试或告警、Owner 和期限。不接受「加强关注」当作整改。

### 28.5 看懂一条陌生业务流程

路径：`行业事实 → 价值链 → L1–L5 → 任务/规则/数据/系统/角色/控制 → 四方取证 → 基线 → 瓶颈 → 评分 → 试点`。

- L1 价值流，L2 流程域，L3 端到端，L4 场景，L5 可执行步骤。L5 再拆任务、规则、数据、系统、角色、控制
- 制度、口述、系统和实际做法通常不是同一条。访谈是线索，单据、日志和跟岗才是证据
- 四方：访谈、跟岗、文档核验、事件日志。人数和条数是自定抽样（关键岗位 2–3 人，手工回放 30–50 个实例），见第 27 章。跟岗要覆盖普通日、高峰日和异常日
- 先去掉无价值步骤并写成稳定规则，再自动化

硬门槛，命中则不做全自动，最多做辅助或影子运行：法律要求自然人判断、人身或资金风险且控制不足、数据或接口不可靠、规则一直在变、无法定义正确结果、不可逆且无补偿、没有接管和审计。

评分只用于比较假设，不替代安全和合规决定：

`候选优先级 = 业务价值（满分 50）+ Agent 适配（满分 50）- 风险扣分（0–30）`

分档和下面的 30/60/90 天是自定读法，不是行业及格线：75 以上优先试点；60–74 先补数据或接口；40–59 做辅助；40 以下暂不用 Agent。

30 / 60 / 90 天：前 30 天交流程资产包和基线，结论至少两类证据；31–60 天影子运行，不影响生产决策；61–90 天先建议、后低风险执行，用对照组或历史同期看收益。过不了门就停止扩张。

基线窗口自定，建议至少看 4–8 周，季节性业务覆盖一个周期。报中位数、P75、P95，不只报平均。总周期拆成处理、等待、返工、系统延迟。时间主要耗在审批等待时，加快生成不会缩短总周期。

净节省工时要扣掉复核和运维。理论节省不等于财务收益，只有减少加班、外包、招聘，或释放产能并带来新价值，才算兑现。同一份收益不能同时算进人工节省和收入增长。

### 28.6 交付时带上的卡片

- 场景卡：Owner、触发和结束、基线、正常/异常/拒绝路径、形态、接管点、最大损失、成功指标、停止条件
- 工具卡：字段同第 3.4 节，另写出站范围
- 发布单：版本集合、评测和安全报告、灰度范围、停止阈值、回滚方案、值班决策人
- 故障单：级别、影响、时间线、止损、假设和反证、根因、新增用例和告警
- 架构决策：约束、候选、比较维度、放弃了什么、何时重估

### 28.7 教学闭环里要记住的边界

一个最小闭环是「企业知识问答 + 确认后创建工单」：模型只输出结构化计划；服务端做权限、预算、审批和幂等。可运行源码不放进这份大纲。

生产替换时逐项换成：网关校验过的身份、召回前 ACL 的真实检索、数据库唯一约束、带补偿的真实写入、可暂停的持久化工作流、真实 tokenizer 计费、OpenTelemetry、以及 Prompt / 策略 / 模型 / 工具 / 索引的联合版本。前端不能自己声明角色。流一旦开始，中途错误用事件返回，不能再改 HTTP 状态码。

## 29. 个人项目推进（本仓库）

知识学习按第 1 章的 12 周。本章的 P1–P4 是四个项目，不是学习优先级。本仓库不按日历，按闸门。市场要的是能把 Agent 放进业务，并用数字证明它没变差。

### 29.1 怎么读招聘数字

样本含外包、重复发布和城市差异，只看趋势。

| 信号 | 怎么用 |
| --- | --- |
| 2026 秋招口径里，AI 相关岗位放量，智能体是缺口方向之一 | 先有能讲的作品，不追求功能清单 |
| 猎聘大模型应用开发样本月均约 1.8 万；3–5 年约 2.3 万。Agent/RAG 的 JD 常见 25–60K，50–80K 是上沿 | 档位靠落地和数字，不靠框架数量 |
| Gartner 预测到 2027 年底超过 40% 的 Agentic AI 项目会取消，原因是成本、价值不清、风控不足 | 评估和治理是差异化，不是收尾工作 |
| MCP 已跨厂商标准化 | 项目 P2 要做 Server 和客户端，不只「了解」 |

主投 Agent 应用和 RAG 知识库。平台 / 交付岗等 P4 有部署数字再投。多 Agent 研究、训练和推理内核不主投。

项目原则：默认单 Agent，项目 P3 只做对照，不达标就退回；这条 RAG 用拒答、引用和评估证明价值；一次失败复盘优先于再加一个框架；Python、接口、数据库、部署优先于多学一个 SDK；项目 P2 必须写到确认后落库。

每项能力要有三段证据：能指到的代码、改前改后的数字（写明模型、温度、题集版本）、一次失败的现象到修复。没有证据就说「读过，没在这条链路上用过」。

### 29.3 P1：现在这条链路

导入：PDF（MinerU）或 Markdown → 图片摘要进 MinIO → 标题切分 → 商品名抽取 → BGE-M3 稠密加稀疏 → Milvus 按 `file_title` 先删后插。先删后插是现状，插入失败会空窗（坏例 4）。目标做法见第 49 题，不把现状当成推荐架构。

查询：商品名确认（0.85 高置信 / 0.6 候选；中置信反问；库中无商品拒答）→ 有现成答案则透传，否则混合检索、HyDE、MCP 联网三路并行 → RRF（k=60，只融合前两路）→ 重排后按证据生成。SSE 事件有 `ready`、`progress`、`delta`、`final`、`error`。

写死的边界：模型不能决定要不要检索，这是相对第 5.2 节的收窄，方便把检索失败和生成失败分开。反问靠历史等下一轮；任务表和 SSE 队列在进程内存里，重启即丢。这替代不了 Checkpoint（第 46 题），项目 P2 的澄清和确认再落检查点。

五件收尾：30 题 jsonl、检索和生成分开统计的评估脚本、关键结论强制 `[chunk_id]` 或 `[url]`、空证据或全部无关时不调用模型、高置信度每个提取名最多确认一个标准名。另外两个小修：没有商品名就不要全库打；图片只从 `source == local` 的切片来。

| # | 坏例 | 处理 |
| --- | --- | --- |
| 1 | 高于 0.85 的名字全部进过滤，带入无关手册 | 修，留前后数字 |
| 2 | 没有商品名就全库检索 | 修：停检索或沿用已确认的历史名 |
| 3 | 重排失败把分数写成空，断崖被跳过 | 讲。失败要显式状态，不要装成低分 |
| 4 | 先删后插，插入失败时该文档检索为空 | 讲。监控条数掉到 0 |
| 5 | HyDE 编造步骤，召回去找像编造的切片 | 讲。做一次关闭对照 |
| 6 | 网页和本地在重排里同分 | 讲。操作步骤以本地为准 |
| 7 | 历史从旧到新装，预算不够时丢掉较新的否定和数字 | 讲。P2 改成从新到旧，旧的做摘要 |
| 8 | 空证据仍调用模型 | 修，并进 G1 |
| 9 | 网页图片也能进最终结果 | 修，按来源过滤 |
| 10 | 生成失败被写成正常回答 | 讲。固定错误码，堆栈只进日志 |
| 11 | 页面断开，后台图还在跑 | 讲。P4 做取消 |
| 12 | 健康检查只探进程 | 讲。就绪检查要探依赖 |

入库侧另记四个数：解析成功率、空切片率、图片 404 率、重复切片率。没有跑出来的数字就讲机制，不编。

三分钟讲法：导入链路 → 查询链路 → 一个坏例的前后数字 → 评估脚本在 `eval/`，检索和生成分开。

### 29.4 P2：设备维修助手

用户描述故障 → 识别型号 → 检索手册 → 必要时澄清 → 步骤加引用 → 确认后写一条维修记录。不做多租户、不计费、不接真实工单、不让模型拼 Milvus 表达式、不自动写。

图：`intake → clarify → plan → act → draft → confirm → write → final`。澄清和确认是中断点。计划不超过 5 步，循环不超过 6 轮。写工具在确认前不出现在模型可见列表里。

五个工具：`search_manual`、`get_item`、`check_evidence`、`web_search`、`create_repair_record`。前四个只读。写工具的幂等键用 `session_id + item + fault + 客户端请求 ID`，不把时间窗放进键。

P2 只调 P1 的 `POST /v1/retrieve`。请求给 query、可选型号、top_k、是否含网页。响应给切片和 trace；过滤表达式只进日志，不进模型上下文。空列表是合法结果。`503/504` 最多重试 2 次，`4xx` 不重试。检索失败和空召回用不同的 `error_type`。

状态只放结构化字段。`item_name`、证据 ID、确认令牌、幂等键由服务端写，模型不能改。恢复时先校验确认令牌再写。

30 条任务：20 条复用 P1，10 条覆盖确认、拒绝、重复提交、超时、坏参数、注入、指代丢型号、网页冲突、空召回、多轮。成功要四项都为 1：答案对、引用有效、没有未确认的写、没有编造；写任务还要业务库有且仅有一条记录。每次改动记下模型、温度、提示词、集合、题集、commit、embedding / reranker、索引构建时间、切片版本。

MCP 只包 `search_manual` 和 `get_item`，用来讲发现、传输和权限，不替换主检索。

### 29.5 P4 和 P3 的边界

P4 从 P2 第一天记 Trace：标识、九项版本、原问题和改写、三路条数、工具参数和幂等键、token、`ttft_ms`、`error_type`。错误类型分开：空召回、检索失败、工具失败、规划失败、生成失败、校验失败。

取消标记在每次模型调用和工具调用前检查。SSE 跨副本用 Redis 做广播和最近事件，带 `event_id`，重连用 `Last-Event-ID` 补发。Checkpoint、会话、幂等键进 Postgres。2 副本能续会话。20 并发只说明排队、超时和 429，不说明容量上限。

P3 四个角色：编排者不检索不写；检索专员只有检索；校验专员只判断引用是否支持结论，不引入新事实；工单专员凭确认令牌写。共享状态只传 chunk id、任务状态、已确认型号、幂等键和确认令牌。

自定退出线（不是行业标准）：完成率没有比 P2 高过 5 个百分点，或 token 高 30% 以上，或重复调用超过 1.5 倍，或定位超过 10 分钟，就退回单 Agent。主实现用 LangGraph；另一个框架只做最小对照。

### 29.6 题集、指标和失败模式

30 题按失败模式分，不按文档分：单商品步骤 8、指代 4、口语 3、多候选 3、库中无商品 3、有商品但手册没写 3、索引过期 2、切片拆开步骤 2、网页冲突 1、片段内指令 1。其中 20 条 `dev`、10 条 `holdout`。holdout 不参与调参。

简历里可以写的项目指标：拒答正确率、误拒率、无关切片比例、Recall@k、citation precision、任务成功率、确认后写入率、每成功任务成本、P95、退回率、索引空窗发现率。P95 要写样本量，成功率要写谁判定，成本要写模型版本和缓存策略。分母不同的百分比不能比。

| 现象 | 先看 | 改哪里 |
| --- | --- | --- |
| 答非所问 | gold 是否召回、过滤表达式、改写 | 收窄过滤、换查询、重排 |
| 编造参数 | 证据是否为空 | 空证据拒答，强制引用 |
| 反复查同一句 | query 哈希、步数 | 去重、轮次上限、只重排剩余步骤 |
| 澄清后丢型号 | state 里的型号、Checkpoint | 长期事实加确认令牌 |
| 写重复或页面失败但库里已有 | 幂等键、业务库 | 先查状态再重试 |
| 断开仍在跑 | 任务状态、模型日志 | 取消标记 |
| 成本上涨 | 分段 token、缓存命中 | 压缩、减少轮次、路由 |
| 多副本随机坏 | session 能否在另一个副本恢复 | 外置 Checkpoint 和事件 |
| 集群更差 | token、重复调用、P95 | 退回单 Agent 并记录原因 |

### 29.7 作品集和禁写

四件套：README（启动命令、题集怎么跑、数字表）、3 分钟视频（含一次拒答）、1 页架构图、1 页失败复盘。30 分钟讲述按业务边界、架构、一次失败、取舍、重做会改什么。

简历数字用真实结果替换。P1 写链路和一条坏例的前后变化。P2 写五个工具、确认后写入比例、三类失败。P4 写取消后的新调用次数、2 副本、20 并发的 P95 和 429。P3 只有对照数字支持时才写，并且写明默认单 Agent。

不要写：精通全部框架、自研评估平台、K8s 生产调优、高并发、显著提升、已上线生产、P3 优于单 Agent。没数字就不要写「构建了评估集」。

不立项：自研评估平台、Computer Use、微调主线、GraphRAG 主线、六个框架都做、为了对照去迁移 Pinecone、多租户和计费系统。选型差异用一页笔记。

通用机制题看第 25 章。项目追问用本节的坏例、`/retrieve` 契约和失败模式回答，并指到对应文件。
