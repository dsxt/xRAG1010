### 视频原文（纯中文）
今天想按模块把Agent Harness的架构给你拆明白了，拆完你对Agent到底是怎么跑起来的，会有更深一层的理解。

现在大家都知道大模型，但大模型底下是怎么被调起来的——怎么调工具、怎么联网搜数据、上下文怎么攒、一轮一轮对话时这段历史怎么维护、跨会话的memory又是怎么存怎么取的——这些大部分人没概念。

你要是想做Agent插件，这些模块之间怎么交接、各家Agent开放给插件的接口能力差多少，你不摸清楚，插件就是在瞎猜着写。理解了，才谈得上二次开发；不理解，它就是个黑盒子，你是在想象它内部怎么跑，很多地方会做错。它的hooks怎么接、Function Call怎么做，这些弄明白了，你做二次开发才顺手。

而且你拿Agent去服务客户或者自己公司业务，真出了bad case，你才知道从哪下手查——不懂机制，出了问题你是真的没法弄。拆完DeepSeek、Codex、Pi三家开源Harness，我有个结论：它们的骨架在趋同。这意味着两件事：从零自研一个Agent越来越不划算，复用成熟的Harness做二次开发才是主流；而只有读懂一套Harness，你才知道该复用什么、改哪里。今天先拆DeepSeek——三家里只有它，把agent loop本身也做成了插件，改配置就能换，适合想把每个模块都换成自己的团队。想要这张架构图的HTML，评论区说一声，我发你。

先看地图，五个模块，正好对上刚才那几个问题。谁去调模型：驱动核心。Function Call怎么落地：工具系统。上下文怎么维护、记忆怎么存：Session和历史与存储。插件从哪接进来：最外面这圈Cordis骨架。每个模块我只讲四件事：管什么，跟谁交接，为什么这么切，代价是什么。

先看谁去调模型。驱动核心分两层：对外一个公共接口，里面一个默认实现，真正推着Agent一步一步干活。插件只认公共接口，所以整套驱动换掉，生态不用跟着改。驱动每次调模型，要过两道锁。第一道，这一步开始时，把用哪个模型、谁用哪些工具拍个快照；第二道，把请求绑到当前这一版的模型适配器上。为什么要锁？准备请求是异步的，中途工具可能被卸掉，适配器可能被热替换，不锁的话，模型看到的工具清单和真正发出去的请求可能对不上。好处是重试不会把用户的话再吃一遍；代价是插件在请求阶段能改的东西变少了。

模型说要调工具，接下来就是工具系统，Function Call真正落地的地方。它拆成三层，对应三种会变的东西。一层管有哪些工具、谁能看见、谁不准用；一层管怎么把工具交给模型，可以一个一个声明，也可以让模型直接写一段代码把几个工具组合起来；最后一层管执行规矩：审批、安全检查、结果整理。协议变了只动中间那层，规矩变了只动最后一层。声明和执行由同一层负责，就不会出现告诉模型一套、实际执行另一套。模型一次常常要调好几个工具，DeepSeek的做法是：标了可以并发的，放进一个有上限的池子一起跑，其余的一个一个来。跑可以一起跑，写进历史必须按模型发起的顺序：二号、三号先跑完了，也得等一号，一号一到，一二三一起提交。全串行最容易排查，但慢；谁先跑完谁先写最快，但模型每次看到的顺序都不一样。它取中间，代价是队头等待，行话叫head-of-line blocking。

工具结果、模型回复，最后都写进同一个地方：Session。它是一本只追加、不改写的账，行话叫single source of truth。为什么这么死板？模型、界面、存储、各个业务模块都想知道发生了什么，各记一份迟早对不上；只认一本账，审计和恢复都从这里来。官方还定了一条硬规矩，做插件的一定要记住：模型能看到的东西，必须先记进这本账。你想给模型塞一段额外的上下文，也得先写成Session里的一条记录。流式输出的中间片段是过路的，不进账，结算完才记一条。靠这一层，它把一本账分成两条路。一条给模型：每一步都从账里挑出该给模型看的部分，现生成一份历史，驱动自己不攒历史。中间还有一层，各个业务模块各自整理出自己的视图。另一条给磁盘：按会话排队写文件，刷盘成功才算真存住，所以告诉用户“已保存”，必须等刷盘成功。再说记忆，在我读的这版源码里，没有一个单独的长期记忆模块。它能做的是resume和fork：把存下来的会话重新打开接着聊，跨对话的长期记忆，得你自己写插件，而且按刚才那条规矩，召回的记忆要喂给模型，也得先进Session。

最后看插件从哪接进来：最外面这圈Cordis，行话叫IoC容器，你可以理解成所有插件的底座。官方原话：模型适配器、工具注册表、会话日志，连agent loop都是插件，没有一块特权核心可以打补丁。Cordis自己不碰业务，只管三件事：装配、依赖、退出。管住这三件，换模块靠改配置，不靠改代码。装配就是config as code。先选一套预设，里面是一组插件包；再按插件包、预设、用户目录、命令行四层覆盖配置，后写的赢；最后合成一棵插件树，照着树把系统搭起来。网页、无界面模式、SDK三个入口，就是三种配置组合，不是三套代码。代价是行为散在四层配置里，排障得能追到这一行是哪层写的。

依赖，是Cordis最值钱的部分，就是标准的依赖注入：驱动只声明我要六种能力，谁来提供由配置决定。厉害在运行时：工具服务下线，驱动自动卸载；工具回来，驱动自动装回，没人攥着一个已经失效的引用。有个坑官方文档没写，我在源码里核过：组件自己出错进了失败状态，依赖回来它也不会自己好，得手动恢复。也别神化插件化，契约定得松，复杂度就摊给每个实现方；它买到的是可维护性，目前没有证据说它能让编码任务跑分更高。插件一多，谁来收拾？靠作用域。三层嵌套：全局、预设、每个Agent自己一层。工具和提示词从外往里继承，同名就近覆盖，所以不同Agent能看到不同的工具。在作用域里注册的东西都记着撤销办法，Agent一退出，它注册过的一次撤干净，全局不受影响。退出也讲顺序：先停驱动，再放资源；已经对外做出去的操作，撤不回来。

做插件最关心的：能在哪儿插手？DeepSeek留的是一串钩子，像Web框架的中间件，一层套一层，每层处理完交给下一层。每一步开始前，你能放行、改写，或者直接拒掉这一轮的输入；工具执行前、执行中、执行后，各有一道。工具执行后那道，可以把结果改成一条带纠正意见的错误回给模型，但已经对外发生的操作撤不回。另外还有一个钩子，能叫停整轮。别忘了那条规矩：你插进去想让模型看到的东西，都得先进Session。

讲完模块，给你一张出了bad case能直接用的表：每份状态归谁管。骨架管服务绑定和依赖；驱动管活跃的Agent和每一步的推进；待处理的输入单独排队；工具层管定义和准入；Session管已经提交的事实；存储层管写入和刷盘。客户那边出了问题，先问一句：这段状态归谁？再看右边这列最常见的坑：调度不等于外部事务，原始日志不等于给模型的历史，写进内存不等于已经落盘。owner画清楚，排查就有了起点。

五个模块串起来，跟着编号走一圈。一，驱动拿提示词组装请求，工具清单这时由工具系统提供。二，调模型，回复流回来，结算后写进Session。三，有工具调用，就过工具系统三层。四，结果写回Session。五，从Session重新生成下一步的历史，交回驱动。关键在最后一步：驱动自己不攒历史，每一步都从同一本账重新生成，这才是single source of truth真正的用法。所有连线打开，其实只有三类。蓝色调用线，驱动去找提示词、模型和工具；橙色事实线，所有人往Session写，Session再落盘；绿色读取线，从Session生成模型历史和业务视图。三类线都要经过的只有Session，所有模块又都挂在Cordis上。一个管发生了什么，一个管谁能跑，整套系统靠这两根柱子撑着。

如果你在搭自己的Agent平台，最值得带走的是一个判断：什么东西该单独拆成模块？看三点：有没有自己的生命周期，有没有自己的失败方式，有没有自己的使用方，占得越多越该拆。Session活过整个运行，工具调用只活一瞬，所以拆；模型要看的和系统要留的保真度不同，所以拆。反过来，同生共死的两样东西硬拆，只会多一层转发。落到实操，基于DeepSeek Harness做二次开发有三档。最轻松改配置：换预设、四层覆盖，不碰代码就能换组合。往上是换插件：按它的依赖契约写一个插件包，把工具集、模型适配或者持久化换成你自己的。最重是换驱动：实现公共的Agent接口，替换默认的循环，只认公共接口的插件照样能用。几个提醒：它还在早期，上生产先评估成熟度；契约要定严；组件出错不会自己恢复；退出顺序自己写清楚。




拆开Pi的Agent内核，小到能从头读到尾。
上一期拆了DeepSeek，它把包括agent loop在内的每一块都做成插件，所有发生过的事记在一本只追加的账上。这期拆Pi，思路几乎反过来：不追求什么都能换，追求小到你能从头读到尾。就一条原则：用不到的就不做。
我的观点也是context engineering is paramount，模型读到什么，你得精确控制，输出才会好；而很多现成的Harness会在背后往上下文里塞东西，界面上还看不到。所以Pi把每份状态归谁管、什么时候进模型上下文，都做成显式的。拿来学习、做原型，或者把一个小内核嵌进自己的工具，Pi很合适；
要上企业生产，权限、持久化、多人治理得自己补。六个模块，各答一个问题。先看地图，六个模块，对上几个问题。
  · 谁去调模型：执行核心，一个管状态，一个管推进。Function Call怎么落地：工具。上下文怎么维护、记忆怎么接上：记录与投影。插件从哪接：应用层和扩展。换模型走哪：模型接入。最上面是宿主，终端界面和SDK都在这。同一份会话，内存里一份、文件里一份、发给模型的又是一份，Pi把这三份各归谁管，拆得很清楚。
  · 谁去调模型：Agent管状态，先看谁去调模型。执行核心拆成两个角色。Agent是状态的主人：消息、模型、工具、正在流式输出的内容、还没完成的工具调用、中断控制，都在它手里。驱动循环只管推进：拿着这一轮的上下文快照，发模型请求、跑工具批次、决定要不要接着来，它不认识终端，也不认识会话文件。
事件回到Agent，先更新状态，再挨个等核心监听者处理完，慢的那个会把整条事件卡住，行话叫back-pressure。拆开的代价是，状态、这一轮的上下文和会话记录，得在明确的时点同步。模型要调工具，就进工具管线。有个事件最容易被误读：开始。调用先发一个开始通知，然后才去找工具、预处理参数、校验格式、跑前置钩子，全部通过才真正执行。
所以看到开始，只代表进了管线，不代表外部动作已经发生。默认一起跑，但一批里只要有一个工具要求按顺序，整批都改成顺序执行。还有一条保护：模型输出因为长度被截断，这一组调用直接报错，不去执行可能残缺的参数。完成先后，和进历史的顺序，两个顺序放一起看就清楚了。
三个调用一起跑，完成通知是二号、三号、一号，写进历史的结果仍然是一二三。研究时我们用一个假的模型在本地验证过：完成通知里，后发起的先到；写进历史，先发起的在前。好处是界面能实时看到进度，模型下一轮拿到稳定的顺序；代价是慢工具拖住整批提交。所以看到工具完成，推不出模型已经看到了结果。
工具结果这件事，Pi做得很直接：一开始就拆成三份。一份给模型，一份给界面和日志，一份给程序，而且写明给程序的那份不发给模型。作者的动机很实在：如果只有一份给模型的文本，界面想展示结构化数据，就得反过来解析自然语言。代价是三份要保持一致，所以扩展改了给模型的那份、没同步给程序的那份，旧的会被直接清掉。
字段拆开也不等于隐私保证，最终要看什么被真正发了出去。上下文怎么维护？靠记录与投影。会话文件存的是一棵树，每条记录指向上一条，每次准备请求，沿当前位置取出这条路径，套上压缩摘要，合入编辑记录，生成一份投影，每条消息都能追回原记录，再转成模型认识的格式交出去。
好处是存储和模型接口能各自演进；代价是一条消息有三种形态：原记录、投影、真正发出去的请求，排障得追到最后一层。这里有个坑，专门提醒做插件的人。Pi分两步：先挑这一轮给模型看哪些消息，再把这些消息翻译成模型认识的格式。几条规则要记住：压缩摘要会变成用户消息；应用自定义的消息也会变成用户消息，哪怕它在界面上设成不显示，照样发给模型。
界面隐藏、存储保留、模型可见，是三个独立的开关。另外，请求阶段做的变换不会写回会话文件，想留痕得走专门的编辑记录。再说记忆，Pi没有一个单独的长期记忆模块，跨会话靠三样东西。
  · 一是会话能接着用，可以接上最近一次，也可以挑一次接着聊。
  · 二是聊长了有压缩摘要，旧内容压成摘要继续带着。
  · 三是项目说明文件，全局放一份，再从当前目录往上每层找一份，启动时拼进系统提示词。所以想让它记住团队规矩，最省事的是写进这份文件；要真正的长期记忆，得自己写扩展。
换模型走模型接入这一层，原则是统一契约、差异留在边界。核心只认一个统一的流式接口：进去的是整理好的对话，出来的是统一格式的事件流；出错不许直接抛异常，必须编码成流里的事件。底下是模型路由，再往下是各家模型的适配。
跨厂商切换时，当前实现会丢掉旧的思考内容、去掉不兼容的签名，必要时改写调用编号。作者自己也说，这只能尽力而为。能切模型，不等于上下文能无损搬过去。插件从哪接？先看应用层。最上面的宿主很薄：命令行三种模式，SDK可以直接装配，界面只管显示，不控制循环，也不持有历史。
应用层把所有策略收在一处：资源和工具注册、扩展运行、压缩、重试、模型路由。它给执行核心发请求，在工具调用前后挂拦截，再把事件通知给界面，而且不等界面刷新完。为什么单独一层？执行核心要能被别的应用复用，压缩和路由是产品自己的策略，不该污染核心。
一条事件，这一镜是Pi写得最严谨的地方：一条消息结束的事件，要过六站。先进Agent状态，再等核心监听者，再等扩展，然后通知界面但不等待，最后写进会话记录，同步追加到文件。由此得出两条：不能说界面渲染完才落盘，写入失败时，只回滚会话记录自己，不回滚Agent状态，更不撤销工具已经做过的事。
插件能在哪儿插手：钩子与扩展。做插件最关心的：能在哪儿插手？先分清：扩展是可执行的代码，Skill是一份指令文件，默认只把名称和描述放进提示词，正文用到再读。钩子不是旁观者：上下文钩子能改这一轮的请求，工具钩子能在调用前拦下、调用后改写结果，回合钩子能参与要不要接着跑。
重载要按顺序来：旧会话关掉、旧运行器作废，再重建，旧的上下文引用不能跨重载用。还有，项目信任默认先问你，它管扩展加不加载，不是逐个工具的权限系统。注册了不等于模型看得见。MCP这件事，Pi的立场变过。作者早先说不做：两个常用的浏览器MCP，光工具说明就各占一万多token，还没干活，7%到9%的上下文就没了。
后来团队改了口，因为Pi需要的和MCP需要的很像，都是一个能跑脚本的解释器沙箱，也就是Codemode。现在工具注册了不等于模型看得见，分三档：直接给模型；只给脚本调用，不占工具列表，这是MCP的默认档；先藏着，模型搜到再加载。注意，脚本沙箱受限，不代表它调的命令也被隔离，Pi默认继承启动进程的权限。
讲完模块，给你一张出了bad case能直接用的表：每份状态归谁管。Agent管消息、模型、工具和流式状态；驱动循环只管这一轮；应用层管策略、扩展和压缩；扩展运行器管扩展的上下文；会话记录管文件、分支和压缩；模型路由管各家模型；界面只管显示。
出了问题，先问这段状态归谁，再看右边这列常见的坑：流式临时状态不是持久记录，会话文件不是模型上下文，接口统一不代表语义无损。截图保存这张表。
连起来：一次run走一圈。六个模块串起来，跟着编号走一圈。一，宿主提交请求，经应用层到Agent。二，会话记录投影出这一轮的上下文，转成模型格式，交给模型接口。三，模型路由到具体厂商，事件流回来。四，工具调用进管线，一起跑，按原顺序交回。五，结果回到Agent，过核心监听者和扩展，追加进会话文件，同时通知界面。
贯穿全程的是同一个调用编号：完成通知、Agent状态里的结果、会话里的那条记录，是三个不同的完成条件。四类线：调用、事实、读取、事件。所有连线打开，一共四类：蓝色调用、橙色事实、绿色投影读取，再加一条紫色事件线，把状态变化通知出去。
和上期的DeepSeek比，Pi没有一个通用的插件容器，核心靠显式的类型和函数组合，扩展靠自己的生命周期钩子。下期的Codex，又会把产品协议单独做成一层，而在Pi里，RPC只是一种运行模式。
从Pi带走三条，给搭Agent平台的人三条判断。先给每份状态定主人，再定谁能投影、谁能改、谁能订阅；有事件总线，不等于有所有权。应用消息保留表达力，到模型边界再收窄，投影要能追回原记录。工具结果按使用方拆开，同时定好对不上时怎么办。如果你做的只是短会话的纯文本工具，这些都可以先不做。
基于Pi二次开发：三档。落到实操，基于Pi做二次开发有三档。最轻是写Skill，一份指令文件，零代码。往上是写扩展：用钩子拦截工具、改写结果、参与续跑，加自己的工具，配MCP的曝光档位。最重是用SDK，把Pi的内核嵌进你自己的产品，入口和界面都自己做。
上生产前补三块：权限，它默认继承启动进程的权限，没有逐个工具的权限系统；持久化，写失败只回滚自己的记录，不保证崩溃恢复；多人会话和集中治理，也得自己设计。
这是Agent Harness拆解系列的第二期。下期拆Codex：OpenAI说过，它的网页版、命令行、IDE插件和桌面App，背后是同一套Harness，我们看一个内核怎么同时撑起这么多产品。最后一期横评，把三家放在一起看：工具一起跑、按模型顺序交回，这件事三家都做了，为什么会撞到一起。




拆开Codex Harness架构，一个内核撑起多种产品。
Agent Harness拆解03/04。
前两期拆了DeepSeek和Pi，一个把每一块都做成插件，一个小到能从头读到尾。这期拆Codex，它要解决的问题大得多。OpenAI官方说过，Codex的网页版、命令行、IDE插件、桌面App背后是同一套Harness。所以学Codex学的是一件事：一个Agent内核怎么同时撑起好几种产品。
还要分清一点，Codex好用有相当一部分来自模型。OpenAI公开说过，GPT-5-Codex是针对Codex里的agentic coding进一步优化过的版本，也更守AGENTS.md里的规矩。模型和Harness是一起调出来的。你的团队要把成熟的coding agent嵌进自己的产品，这期最用得上。
先看地图，六个模块对上几个问题。怎么接到不同的产品界面？左边这列App Server，产品协议层。谁去调模型、一段工作怎么推进？Core会话。Function Call怎么落地、能不能执行？工具系统。上下文怎么维护？上下文与模型。会话怎么存、怎么恢复、记忆放哪？存储与恢复。插件从哪接？扩展。
Agent出问题常常出在交接上：模型说完了，工具还在跑；工具返回了，结果却没进下一轮。Codex最值得看的，就是它怎么把每一次交接接住。
先看它怎么接到不同的产品。命令行、SDK、IDE、第三方客户端，最后都汇到App Server这一层。它不执行，只做三件事：校验和转发请求，把内部事件翻译成客户端能懂的通知，需要审批时反过来问客户端。
看这张时序：发起一段工作，马上回一个进行中，接着是一条条进度通知；中途要审批，客户端回复之后才继续，最后才是这段工作结束。所以拿到响应，不等于活干完了。
协议把会话建成三层：Thread是整个会话，Turn是一段工作，Item是其中一条消息或一次命令，界面照着状态渲染，不用从文本里猜。这一层是被需求一步步逼出来的。
OpenAI工程博客讲过：最早只有终端界面；做VS Code插件时，试过直接暴露成MCP server，语义对不上；于是先上一套模仿终端循环的协议应急；等JetBrains、Xcode、桌面端多Agent编排都来了，才规范成要求向后兼容的正式协议。
我的判断看宿主数量：只有一个宿主，直接调库就行；多个宿主各自演进，又要共享审批和取消的语义，才值得付这层协议的维护成本。
再看谁去调模型：Core会话管一个Agent会话的长期服务：模型连接、MCP、进程管理、存储和扩展。对外只开两个口：一个进输入，一个出事件。为什么拆成两个口？模型调用可能很长，这期间系统得照样收得到新输入、审批回复和中断。提交输入可以只等到系统决定怎么处理就返回，调用方不等了，已经排上队的输入也不会撤回。代价是调用方得清楚自己到底等到了哪一步。
顺便说一句，这里的Thread指一次Agent会话，跟操作系统的线程没关系。这一镜纠正一个常见误解：模型说完了，这段工作未必结束。一段工作里，每次调模型前先拍一张请求快照，调用时顺手收集工具结果；返回后再判断要不要续跑：模型还有后续，或者队列里来了新输入，就再来一轮。
都没有了，才进停止钩子，钩子还能带着追加内容要求继续。停下来，也不代表结果被验收过。只盯着模型那一次回答，会误判整个系统的行为。
我认为Codex里最值得借鉴的是两层上下文。外层管整段工作的身份、配置和授权；内层是每次请求前拍的快照，冻结这一次用的设置、环境和工具目录。一段工作中途，工具目录从一版升到二版，新请求用二版；但第一次请求发起、晚一点才执行的那个调用，手里仍是一版的快照，照旧找一版的执行器。
文件授权走另一条路：回到这段工作实时去查。一句话：工具目录跟请求走，授权跟这段工作走。更简单的做法是整段冻结目录，代价是更新要等下一轮。这套机制官方没写过，是源码里读出来的。
Function Call在Codex里分三层，各答一个问题。
  · 第一层答看不看得见：内置工具、MCP、扩展、客户端的动态工具，在这里组成这一次的计划，给模型的声明和执行用的注册表，出自同一份计划。
  · 第二层答能不能一起跑：调用先落记录，再拿着请求快照找执行器，处理取消和结果转换。
  · 第三层答该不该批准：管本机命令的审批、沙箱和重试。注册了、看得见、允许执行，是三个不同的集合。
并发上，Codex把两件事交给两个机制。
  · 谁能同时跑，靠读写锁：能并行的拿读锁，要独占的拿写锁，所以四号要等前面的读锁都放掉。
  · 谁先进历史，靠一个有序队列：按发起的顺序收结果，二号、三号早跑完也得等一号。
比全串行保住了吞吐，比按完成顺序提交多了确定性，代价是队头等待，行话叫head-of-line blocking。
还有个细节：调用先记录再执行，取消时没派发的也补一条中止结果，历史里不留没有回音的调用。安全这条线要看清分工。
策略层先算出要不要审批；协调层管审批、沙箱选择和重试；审批可以来自策略、人工，或者自动审查；沙箱管理再选本机用哪种约束。
  · MCP和客户端的动态工具有各自的处理器，本机沙箱的结论管不到它们。最容易踩的坑：自动审查批准了原来的动作，不等于批准了提权之后的重试。别给所有调用贴同一张安全标签。
  · 上下文怎么维护：Codex把内部历史和模型输入分开。工具结果带着这段工作和模型的信息，记进内部历史；下次请求前再投影一份给模型：规范格式，模型读不了的图片和文件变成文字占位，再拼上快照里的指令和工具计划。模型连接管厂商、认证和备用，每段工作开一个连接做增量请求，认证换了人就清缓存。
为什么拆开？审查和恢复要的信息，跟推理要的不一样。后台压缩也一样，装回去之前先核对版本、模型和认证，对不上就丢掉。
  · 存储这层，Codex把四个动作分开：追加、检查点、刷盘、关闭。部分写入可以在后台推进，刷盘和关闭时必须等它们完成，失败要报出来。所以产品上说已保存，要等刷盘到可读的边界，收到界面事件不算。
恢复会话时，先拿到写入权，再返回权威历史，避免基于旧快照接着跑。中断要先核对是哪一段工作，等核心确认中止。恢复能重建会话，已经对外做出去的操作回不去，得另外设计补偿。
  · 再说记忆。前两期的DeepSeek和Pi，都没有单独的长期记忆模块；这版Codex源码里有一套。能看到的是：生成记忆和使用记忆是两个开关，可以分开开；有一条规则决定哪些记录能拿去生成记忆，对话、工具调用和结果可以，开发者指令、推理过程、压缩记录不行；还有一个开关叫遇到外部内容就停用记忆，打开以后会话里一混进联网搜索这类外部内容，这段会话就被标成被污染；记忆存在本地一个数据库里，命令行有清空的命令。
具体怎么生成、怎么召回，在单独的包里，这次没有展开读。另外，每次请求的快照里都会记下当时的AGENTS.md。插件从哪接？Codex的扩展按阶段接入：上下文、工具、模型请求、这段工作的输入、生命周期，各有各的入口；扩展的数据按session、thread、turn三个范围存。
工具的结局有四种：完成、被拦、失败、中止，取消甚至可能早于开始的回调。再加上前面说的停止钩子，能在收尾时要求继续。这意味着扩展作者要按阶段契约写代码，平台方要承担接口演进的成本。MCP、Skills、动态工具和内部扩展，接入点各不相同，别混成一类。

拆开DeepSeek·Pi·Codex三家Harness横评
Agent Harness拆解·04/04。
这是Agent Harness拆解系列的最后一期。前三期，DeepSeek、Pi、Codex分开拆完：Agent能力≈模型×Harness。一个把每一块都做成插件，一个小到能从头读到尾，一个用同一套内核撑起好几种产品。这期把三张地图并排放。
先抛一个判断：Agent的能力，约等于模型乘以Harness。有粉丝留言我：一聊Agent又扯回模型，那Harness还聊什么？拆完三家，我的回答是：恰恰因为Harness在趋同，模型的差距才重新变成主变量；而Harness决定的是，模型的能力能兑现多少。这期先看三家在哪几处撞到了一起、哪几处各走各的。
最后回答一个更实际的问题：Harness趋同之后，企业的钱该花在哪？
三个团队，两种语言，彼此没有协作。三份源码分开读完，有六处设计几乎一样。这期按七种角色逐行对照：入口和协议、驱动、请求和长期状态、工具并发、结果怎么表示、事实和存储、生命周期。
看完你会知道，搭Agent平台时，哪些决定是绕不过去的。先定标准，免得变成找相似点。算收敛，要同时满足三条：解决同一个工程问题，实现手法完全不同，付出的代价和换来的收益是同一种。下面每一条，都来自前三期分别核实过的源码，这里只做横向对照。
  · 第一处，三家都给核心留了可替换的余地，只是路径不同。DeepSeek是一开始就设计好，连agent loop都做成插件，代价是接口契约必须定得很严，否则复杂度会摊给每个实现方。
Codex和Pi是被需求推着走：Codex的App Server从给VS Code插件应急的协议，演进成多宿主的正式协议；Pi从早先不做MCP，到后来借Codemode的解释器沙箱一起接入。两条路都能走到可替换：提前做就提前付契约成本；等需求来就先用够用的方案。
  · 第二处，这一次请求看到的和系统长期记住的，三家都分开管。DeepSeek给每次请求上两道锁：先把模型和准用的工具拍成快照，再绑定当前这一版模型适配器，长期的事实留在Session。Codex用两层上下文：请求快照冻结这一次的能力，整段上下文管身份和授权，授权实时查。
Pi在交给模型之前先挑这一轮看哪些消息，这一步不写回会话文件，长期记录留在会话记录里。
  · 三套实现，回答同一个问题：这次请求看到的保持多久不变，长期记住的怎么不被一次请求弄脏。代价也一样：多一层转换，多一套生命周期。
  · 第三处，工具结果服务的不只是模型。DeepSeek把调用和结果记进Session，再分别生成模型历史、业务视图和磁盘记录。Codex把结果记进内部历史，投影一份给模型，交一份给存储层，事件再翻译给客户端。Pi最直接，结果一开始就拆成三份：给模型、给界面、给程序。Pi还多一条兜底：给模型的那份被改了、给程序的没同步，旧的直接清掉。多种表示并存，就必须有一条对不上时怎么办的规则。
  · 第四处，手法差别最大，结论最一致：工具一起跑，进历史必须按模型发起的顺序。DeepSeek是前面连续跑完的一段先提交；Codex用读写锁管谁能同时跑，用有序队列按发起顺序收；Pi等整批收齐，再按原位置写回。细节有差别，DeepSeek前缀一就绪就提交，Pi要等整批；但代价都是队头等待，收益都是模型看到的顺序，始终等于它自己发起的顺序。
为什么都这么选？三家官方都没专门解释，这是我的推论：工具调用是模型自己生成的，调用顺序本身就是上下文的一部分。按完成先后塞回去，等于往下文里塞进一个模型从没生成过的顺序，后果很难预测。保序真正保护的，是上下文的一致性。但它只管结果怎么排，外部操作谁先谁后，还得靠工具自己声明能不能一起跑。也有两行，三家各走各的。
  · 第一行是生命周期怎么管。DeepSeek靠Cordis这个容器统一管，依赖没了自动下线，回来了自动装回，连agent loop都住在容器里。Codex不用通用容器，状态分层靠显式的上下文结构，加上Rust的所有权规则手写。Pi在中间：核心靠显式的类型和函数组合，扩展有自己的生命周期钩子。
三家连要不要一个通用容器都没达成一致，却在前面几处给出了相同的答案，说明那几处收敛来自这类系统本身的约束，跟用哪个框架关系不大。
  · 第二行是记忆。DeepSeek和Pi都没有单独的长期记忆模块：DeepSeek能把存下的会话重新打开、或者分叉，跨对话的记忆要自己写插件，而且按它的规矩，想让模型看到的都得先进Session；Pi靠接着聊、压缩摘要，加上启动时拼进提示词的AGENTS.md。
Codex这版源码里有一套单独的记忆功能：生成和使用分开开关，有规则筛哪些记录能进记忆，打开对应开关后，混进联网搜索这类外部内容的会话会被标成被污染。对企业来说，这一行最该自己拿主意：记忆是交给Harness，还是放在你自己的业务层里。
  · 第五处，退出和重载都有严格顺序。DeepSeek：组件清理按注册的逆序启动，默认循环先停驱动、等手头工作收完，再放资源、确保落盘。Codex：中断先核对是哪段工作，等核心确认中止，没派发的调用补一条中止结果。Pi：重载先等旧会话关闭，旧的运行器作废，再重建、重新绑定。
三家都不承诺自动撤回已经发生的外部操作，清理从来不是免费的。
  · 第六处，已保存要对齐真正的存储边界。DeepSeek：先进内存，排队写文件，刷盘过了耐久屏障才算。Codex：追加和刷盘分开，刷到可读的边界才算，收到界面事件不算。Pi：同步追加文件，但通知界面早于追加，写失败只回滚自己的记录，同步写也不等于断电不丢。
三家都把界面看到了和真正存住了，当成两件事。落成一张搭平台用的判断清单。给核心留余地：先用够用的方案，出现第二个独立需求再抽象；要一开始就做成可替换，就把契约定严。分开两种状态：这次请求看到的和长期记住的，别共用一个对象的生命周期。
结果按使用方拆：至少模型、界面、程序三类，并配一条一致性规则。并发先问依赖：工具之间有没有隐式依赖，模型对顺序敏不敏感。已保存要对齐存储边界。清理写清顺序，取消不等于回滚。回到开头：巧合还是必然？我的判断是必然。一个持续运行、接收用户输入、调外部工具、再把结果喂回模型的系统，只给工程师留了几个关键决策：驱动逻辑锁不锁死，状态按什么粒度分层，结果给几种读者，并发和顺序怎么取舍。
答案本来就不多，三家撞在一起不奇怪。这是我的判断，不代表任何一家的官方立场。回到开头那个公式，拆完三家，我想把它说得更准。这个乘法里有配对：前沿厂商会把模型和自家Harness一起调。
OpenAI公开说过，GPT-5-Codex是针对Codex里的agentic coding进一步优化的版本，所以用哪家的模型往往配它原生的Harness最顺手。它还有门槛：低于门槛，模型能力会大量漏掉。OpenAI举过例子，同一个模型只改两项Harness设置，分数差了将近三倍；过了门槛，收益开始递减，Pi的作者就观察到，只给一个终端会话的极简agent，在Terminal-Bench上照样排得不错。
更重要的是，Harness分两层：通用那层，循环、工具、状态，三家已经趋同，复用就好；业务那层，你的工具、知识、规矩和评测，模型再强也不会自己知道，这才是企业自己的护城河。
我的判断是：日常任务换哪家Agent差别越来越小，长链路的复杂任务，比如大型coding，差距主要来自模型和它跟Harness的配合。钱怎么花：模型选，不造；通用Harness用，不重写；业务层自己建。落到选型，基于谁做二次开发，看你要什么。
要把成熟的coding agent嵌进自己的产品，而且要协议稳定，选Codex，Apache协议，按官方给的三层接入：一次性任务用exec，应用代码里用SDK，Agent就是产品本身才上App Server；
要轻、读得完，想深度定制上下文和交互，选Pi，MIT协议，Skill、扩展、SDK三档；代价是上生产得自己补权限、持久化和多人治理。
有平台团队、想把每个模块都换成自己的，选DeepSeek Harness，也是MIT协议，三家里只有它连agent loop都是插件；代价是它还在早期，契约要定得很严。
Agent Harness拆解系列到这里就完整了，一共四期：DeepSeek看插件内核和一本账，Pi看三种表示和结果三分，Codex看产品协议和两层上下文，这期看三家撞在哪、钱该花在哪。细节回到各自那期，这期的结论要看完三家才成立。





### 视频内容
1. **Agent 协作的三个进化方向**
   - **Harness**：让模型能动手，是单个 Agent 本身的架构，模型作为大脑，通过工具、上下文、运行循环来执行任务，DeepSeek Harness、Pi、Codex 都属于这类。
   - **Proactive Agent**：主动式 Agent，自己盯着邮件、日程、群消息，有事儿才来找你，个人助手只是一种用法，xAI、Meta、OpenAI、Anthropic 都推出了自己的相关产品，国内有 Today AI。
   - **Multi-agent**：一群 Agent 的分工，关键看谁来派活，包含 Subagent（主 Agent 临时派）、Agent Team（从共享任务表领）、Router + Worker（专职调度，自己不干活）、Agent Swarm（派活训练进模型）。

2. **DeepSeek Super-agent 相关内容**
   - **三种能力合流**：底座是 DeepSeek Harness，能盯着 GitHub、飞书，采用 Router + Worker 的分工模式。
   - **设计总览**：一个入口，背后自己分工，事件入口包含群消息、PR 评论、CI 结果，经过代码筛选与权限后，由 Router 调度层派活给 Worker，背后开多少个 Session 由它自己管。
   - **双层：Router + Worker**：Router 是前台调度，接话、派活、记住全局，自己不干活，用轻一点的模型就够；Worker 一件事儿一个，上下文隔离，配最强的模型，干完只向 Router 汇报，由 Router 统一回复。
   - **派活相关实验**：派不派活不能只靠自觉，DeepSeek 做了合成负载对照实验，提示词写“合适的时候用”时，五次一次没派，全自己扛；改成“优先派出去”时，五次派了四次，剩下那次它嫌活小，又自己干了。且分工要写进架构，别只靠提示词。

3. **其他 Agent 设计要点**
   - **事件驱动**：唤醒 Agent 的是群消息、代码评论、CI 结果这些业务里发生的事，不是等你敲提示词，先由代码筛选事件，权限由代码执行，再交给模型判断。
   - **上下文管理**：同一个 PR，后续评论直达原来的 Worker，不用再经过一次 Router 派活；当前用得上的给完整内容，其余给可检索的目录，要用再取，浪费上下文窗口就是浪费模型的智能。
   - **交互设计**：耗时命令异步执行，发出命令先回一句“已启动”，结果回来算一条新消息，你随时能插话；在哪说话就怎么交代，群里只在让你拍板或验收时开口，GitHub 上才写完整说明。
   - **运行与监控**：Agent 不跟电脑一起睡觉，大脑和记忆放在云上，电脑只负责动手执行，电脑合上它照样在线；看 Agent 要看进展，别只看它是否活着，用 Watchdog 定时查每个 Worker 有没有真进展，发现异常就介入。
   - **成本与边界**：并行和全局协调都有成本，读缓存的 Token 是单 Session 方案的两到四倍；原型能试，但边界要看清，只能在小范围、可信环境里用，开源不等于装上就能用，命令执行要用独立系统账号。
