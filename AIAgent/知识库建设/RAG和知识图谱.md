# RAG 与知识图谱：检索层、增量更新和权限

检索截止：2026-11-23。本篇讲派生索引和多跳检索。已经编译的结论见 [LLMwiki.md](LLMwiki.md)，术语谁说了算见 [本体Ontology.md](本体Ontology.md)，总的生命周期见 [知识体系建设.md](知识体系建设.md)。

## 检索层回答什么问题

RAG 在提问时把相关原文交给模型。它擅长：原文很长、刚更新、需要引用原句、问题落在长尾、不值得为每份材料写一页综述。

它不擅长单独承担：口径冲突以谁为准、页面过期了怎么办、调用者能不能看这段、删掉源文档后旧切块是否还在。这些要写在规范知识和治理控制面上。索引可以整库重建，规范页不能只活在向量库里。

2026 年比较清楚的分工是：

| 问法 | 先用 | 原因 |
| --- | --- | --- |
| 错误码、制度编号、专有名词 | 关键词 | 向量容易把相邻概念混在一起 |
| 自然语言、表述和原文不一致 | 向量或混合检索 | 覆盖改写 |
| 「全部合同里的主要风险是什么」 | 图上的社区摘要或 wiki 综述 | 不能靠顶 k 切块代表全集 |
| 「这个里程碑延期会碰到哪些义务」 | 图上的实体和关系 | 多跳在切块里不稳定 |
| 「净收入按哪一版定义」 | 已确认本体，再按需取证据 | 排序不能代替确认 |

没有一种检索在所有问题上更好。Wavect 的写法是：用还能保住含义和证据的最便宜方法。Google Cloud 对 Agent 发现的研究把企业检索看成大海捞针，测试集要包含缩写、旧名称、不完整问题和冲突来源。

来源：[AI-Ready Company Wiki](https://wavect.io/blog/ai-ready-company-wiki/)。

## 一条可以治理的 RAG 链路

```text
来源（带来 ACL 和版本）
  → 解析（版式、表格、图片、标题树）
  → 切块（保留文档 ID、位置、权限、内容哈希）
  → 关键词索引 + 向量索引 + 可选的实体关系图
  → 检索时按调用者过滤
  → 重排
  → 模型作答并引用
  → 反馈、坏例、黄金问题
```

切块是实现细节。能进审计的是证据指针：哪一篇、哪一页或哪一个单元格、内容哈希、抽取时间。模型引用这些指针。只引用「片段 17」无法复核。

权限放在过滤之前。把受限文档拷进一个共享向量库，生成后再滤掉，调用者已经可能在提示词里看到不该看的内容。每个搜索和读取都用本次身份与来源 ACL 求交。MCP 同样如此：上一次结果里的 ID 不是下一次的读许可。

## 增量、删除、回滚

知识库腐烂有一半来自更新路径：只会全量重建，不会删除；源改了，旧切块还在；wiki 页改了，向量还是上一版。

选型时直接问实现，不看介绍页：

- 同一文档再次同步，是按哈希跳过，还是再插一份？
- 源侧删除后，切块、向量和图节点是否在同一次任务里去掉？
- 替换文档时，引用旧版本的 wiki 页会不会被标成待复核？
- 人工改过的切块，重新解析会不会覆盖？需要保留修订。
- 重建索引是否从规范文本和原文出发，而不是从旧索引出发？

公开实现里的差异，截至 2026 年 10 月的版本比较：

| | Microsoft GraphRAG 3.3.0 | LightRAG 1.5.7 |
| --- | --- | --- |
| 许可 | MIT | MIT |
| 该比较采用的发布日 | 2026-10-08 | 2026-09-02 |
| 项目状态 | 官方仓库写明研究项目，基本处于维护模式，不接受新功能 PR，做缺陷和 CVE 修复 | 持续开发。默认的文件库只适合小规模试验，生产推荐 PostgreSQL 等 |
| 索引时的模型工作 | 抽实体关系、社区摘要；全局问题主要读摘要 | 按块抽实体和关系，对合并很多的实体做摘要 |
| 提问路径 | local / global / drift / basic | local / global / hybrid / naive / mix |
| 增量 | `graphrag update`，面向新标题 | 按内容或文件哈希插入 |
| 删除或改写一篇 | 比较文章写明不支持按文档删除，需要全量重建 | `adelete_by_doc_id`，可利用抽取缓存重建 |
| 本地模型 | 比较文章称未见明确的本地模型下限，大量测试在 OpenAI gpt-4 系列 | 文章给出的参考下限是非思考模式的 Qwen3-30B-A3B-Instruct |

来源：GraphRAG 仓库警告，<https://github.com/microsoft/graphrag>；LightRAG 仓库，<https://github.com/HKUDS/LightRAG>；Particula，[LightRAG vs GraphRAG (2026)](https://particula.tech/blog/lightrag-vs-graphrag)，2026-10-09。表内行为对应这两个版本，升级后要重读发布说明。

GraphRAG 的论文路径（arXiv:2404.16130）是把贵的推理放在索引时：抽取图，用 Leiden 做社区，给社区写摘要。全局问题在摘要上做 map-reduce，局部问题从实体向外走。代价是索引贵，而且摘要会过时。LightRAG 的论文路径（arXiv:2410.05779）把索引做轻，提问时同时用低层关键词找实体、高层关键词找关系。频繁变更的企业材料更适合能删除、能增量的一边；几乎不变、又要回答「全集主题是什么」的语料，才值得付 GraphRAG 那种索引成本。官方维护模式意味着后者不宜再当成会前进的产品内核。

AWS 在 2026-09-14 发了 `unified-kg-rag-on-aws`（Apache-2.0）：在 Bedrock、Neptune、OpenSearch 上同时提供两种方法的清洁室实现，按查询选择策略，摄取和缓存共用。这适合作为「一种存储、多种检索」的参考，而不是把某一篇论文绑死。

<https://aws.amazon.com/blogs/opensource/unified-knowledge-graph-rag-on-aws-graphrag-and-lightrag-on-one-stack/>

## 图里放什么，不放什么

图适合所有权、依赖、例外和多跳。它不适合替代普通的文档查找，也不适合充当唯一事实来源。

实用的节点是：文档、章节、实体、主张、已确认术语。边要有类型，例如 `cites`、`defines`、`contradicts`、`supersedes`、`owned_by`。无类型的「相关」边很难治理。

社区摘要、自动抽出来的关系和模型写的实体描述，都是派生数据。源文档删除或术语被废弃时，它们要能重算。把模型抽出来的边直接当成已批准的本体，会把「图上有这条边」误写成「公司承认这条关系」。批准过的关系放在本体里，并带负责人和版本。

## 平台里已经能看到的治理功能

以下均为 2026-11-23 仓库或文档页上的公开描述。

**RAGFlow 1.0.0（2026-11-06，Apache-2.0，约 94547 star）。** 从深度文档解析引擎长成面向 Agent 的上下文基础设施。2026-08-19 加入知识编译：在文档和数据集级别生成 Wiki、图、树、PageIndex、思维导图、时间线和 Skills。同日加入分档的 Agentic RAG。2026-07-02 起有 BigQuery 摄取和增量同步，2026-09-10 起能按 sitemap 摄入网站。它把「原文检索」和「编译结果」放在同一产品里，接近总纲的派生索引加规范投影。编译结果仍要有自己的负责人和过期时间。<https://github.com/infiniflow/ragflow>

**WeKnora（约 38004 star，许可证页为 Other，使用前读 LICENSE）。** 同一知识库上有 RAG、Agent 和 wiki。检索是关键词加向量、重排、父子切块，并可选 Neo4j 上的 GraphRAG；评测含召回和 BLEU / ROUGE。切块可编辑、可看修订、可回滚；wiki 页同样有修订。数据源包括飞书、Confluence、GitLab、Notion、语雀、钉钉文档、Seafile、RSS 等。权限是多工作区 RBAC、资源所有权、审计日志、范围 API key。v0.9.0（2026-10-29）把 Agent 执行分成只读、变更前确认、自动写入。v0.5.2 称 wiki 摄取可扩展到约 4 万篇文档。<https://github.com/Tencent/WeKnora>

**Dify（约 161652 star，许可证页为 Other）。** 知识库分成 Agent 知识库和经典知识库。Agent 知识库对网站、在线文档和网盘按计划刷新，变更后重跑关键问题，并跟踪检索没覆盖的坏例。经典知识库把切块、索引和检索方式交给配置，Notion 和网站要手动同步。两边都能做检索测试。文档更新会重新索引。权限粒度是仅自己、全团队或部分成员。它强在应用编排和刷新，弱在「定义是否已批准」——那一层不要指望应用平台顺便完成。<https://github.com/langgenius/dify>，文档 <https://docs.dify.ai/en/cloud/use-dify/knowledge/overview>

这三个都可以做企业知识库的检索和更新骨架。它们都没有替你回答：没经负责人确认的口径能不能进财务答案。那道关卡在本体和查询策略里。

## 评测

上线时就固定一组问题，之后每次改切块、嵌入模型、重排或图抽取都重跑。

| 集合 | 内容 | 通过标准 |
| --- | --- | --- |
| 能答 | 答案在当前语料里 | 引用到正确文档和位置 |
| 不该答 | 语料没有，或调用者无权 | 拒答或只返回有权的部分，不编造 |
| 冲突 | 两份来源数字不同 | 答案点出冲突和各自版本，不取平均 |
| 过期 | 旧称呼、已废弃制度 | 命中替换页或标明过期 |
| 权限 | 同一问题，两个身份 | 低权限身份看不到高权限片段 |
| 删除 | 删掉源文档后再问 | 旧切块和图节点不再被引用 |

BLEU、ROUGE 可以看生成文本像不像参考答案，不能代替引用是否正确、权限是否守住。WeKnora 同时报召回和这些生成指标，阅读时把召回和引用放在前面。

Dify 文档里的做法值得抄：变更后重跑黄金问题，并单独收集检索失败的坏例。坏例进入下一次切块或 schema 调整，而不是只调 top k。

## 和 wiki、本体一起用

推荐的运行形态：

1. 连接器把来源同步进对象存储，记录 ACL、版本和哈希。
2. 混合检索索引这些原文，供引用。
3. 对稳定主题，由 LLM Wiki 或 RAGFlow / WeKnora 的编译功能写综述页。综述页的 frontmatter 指向源文档哈希。
4. 图只保留有类型的关系，并可以从原文重抽。
5. 高风险术语不从检索得分里「选一个最像的」。查询服务先读本体；没有当前人工确认，就拒绝用任何检索片段充当该术语的定义。检索片段仍可当证据，附在定义下面。
6. 用户指出错误时，改规范页或标记切块，写修订记录，再重建受影响索引。不在聊天窗口里改完就算修完。

Snowflake 2026 年的一组内部基准（生物医学问句，满分 2 分）把语义视图、知识图谱、GraphRAG 和术语映射叠在一起：仅语义视图成功率 50.0%（均分 0.93），加上知识图谱 60.0%（1.14），换成 GraphRAG 70.0%（1.38），再加上术语映射 78.2%（1.55）。样本和领域都窄，只能说明在那次评测里结构上下文比多加一轮推理更相关。不要把 78% 当成企业上线指标。

来源：<https://www.snowflake.com/en/blog/engineering/ontology-grounded-cortex-agents/>

## 常见失败

- 全公司一个索引，权限靠提示词约定。
- 只增不删。过期制度在向量空间里和现行制度得分一样高。
- 嵌入模型一换，没有保留原文哈希，无法证明新索引覆盖了旧文档。
- 图抽取一次成功就冻结，源系统改了外键或制度，图仍在回答旧关系。
- 用社区摘要回答需要精确数字的问题。摘要适合主题，不适合口径。
- 评测集只有编写者的问法，上线后全是缩写和半句话。
