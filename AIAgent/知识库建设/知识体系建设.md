# 企业知识体系建设、更新迭代与持续治理

检索截止：2026-11-23。数字、版本和产品状态都来自当日能打开的公开页面，会随发布变化。厂商基准和宣传口径单独标明，不当作本企业的准确率。

本篇是总纲。三种具体手段分别见 [LLMwiki.md](LLMwiki.md)、[RAG和知识图谱.md](RAG和知识图谱.md)、[本体Ontology.md](本体Ontology.md)。

## 要解决的问题

企业知识会在上线后腐烂，原因通常不是缺一个向量库。文档还在，口径已经变了；检索还能命中，权限和出处已经对不上；Agent 每次都从原文重新拼答案，上次发现的矛盾没有留下。

2026 年能站住的知识体系，同时满足人和 Agent 的五个条件：找得到、被授权、能追溯、还有效、能回归测试。只加语义搜索，解决的是「找得到」。所有权、冲突、权限和过期，要在知识对象上单独建。

来源：[AI-Ready Company Wiki](https://wavect.io/blog/ai-ready-company-wiki/)；[Open Knowledge Format v0.3](https://github.com/open-knowledge-format/open-knowledge-format/blob/main/SPEC.md)。

## 六层，各管一件事

换模型、换向量库、换图数据库时，不能把「什么算数」一起换掉。

| 层 | 职责 | 允许重建 | 不能丢 |
| --- | --- | --- | --- |
| 来源系统 | 制度、工单、仓库、数仓、会议纪要、已确认对话 | 否，原文只追加或版本化 | 原始权限和修改时间 |
| 规范知识 | 概念、指标、剧本、实体页，稳定 ID | 内容可修订，ID 保持 | 负责人、来源、状态、确认记录 |
| 治理控制面 | 密级、可见范围、复核日、审批、保留期、审计 | 否 | 谁在何时放行了哪一版 |
| 派生索引 | 关键词、向量、图、社区摘要 | 是，索引是投影 | 无。索引不是唯一副本 |
| 交付 | 带身份的检索 API 或 MCP，返回最小上下文并指回来源 | 接口可替换 | 调用身份、命中的知识 ID、策略决定 |
| 使用面 | 人浏览 wiki；助手问答；Agent 为有界任务装载上下文 | 是 | 高风险写操作仍走审批 |

Google Cloud 的 Open Knowledge Format（OKF）v0.3 适合放在「规范知识」这一层：Markdown 加 YAML 头，人能读，Git 能 diff，Agent 能改。它明确不管检索、权限和运行时交付，所以另外五层仍然要自己建。OKF 自己也写明：信任等级是建议信号，不是访问控制。

## 三种知识形态，分工而不是互相替代

| 形态 | 适合放什么 | 更新方式 | 详细文档 |
| --- | --- | --- | --- |
| 编译型 wiki | 已经综合过的结论、实体、概念、对照、已标出的矛盾 | 新来源触发一次重构，而不是追加一页 | LLMwiki |
| 检索与图谱 | 长原文、刚入库的材料、需要原句和多跳关系的问题 | 增量写入、按文档删除、索引重建 | RAG和知识图谱 |
| 本体 / 语义层 | 术语含义、负责人、口径、计算所在资产、允许的动作 | 长尾可从工作痕迹学习；关键口径必须有人确认后才能进答案 | 本体Ontology |

查询时的顺序可以固定下来：

1. 关键术语先查已确认定义。未确认的草稿不能回答财务、合规、安全和对外口径。
2. 稳定结论查 wiki。答案带回页面、版本和来源。
3. 原文证据、新近材料和多跳关系走混合检索或图。
4. 把这次问答里真正新的、且有来源的结论写成草稿，进入复核队列，而不是留在聊天记录里。

## 一条知识的生命周期

Polyvia 在 2026 年把「可操作本体」写成五类对象：事物、关系、主张（claim）、证据、动作。主张是可核对的原子陈述，带时间和置信度，状态可以是 proposed、verified、disputed、retracted。证据指向页、表单元格或图，而不是只留一段切块。状态变化记成事件，才能审计、回滚、回答「上个月我们相信的是什么」。

来源：[From RAG to Reality](https://polyvia.ai/blog/from-rag-to-reality)。这是一家产品博客里的设计，不是行业标准；可用的是对象和状态，不是它的实现。

落到本企业，每条规范知识至少带这些字段：

```yaml
id: finance.net-revenue          # 稳定 ID，改名不改 ID
status: draft                    # draft | stable | deprecated
owner: human:finance-steward
domain: Finance
generated:
  by: agent:wiki-maintainer
  at: "2026-11-20T02:00:00Z"
verified:                        # 与 generated 分开。改写后，旧的人工确认不再算当前
  - { by: "human:finance-steward", at: "2026-11-18T09:00:00Z" }
stale_after: "2027-02-20T00:00:00Z"   # 绝对时间，不用相对 TTL
superseded_by:                   # 仅在 deprecated 时有意义
sources:
  - policy/rev-rec-2026.md#3
sensitivity: internal
```

OKF v0.3 的信任分层只看「不早于最近一次实质修改」的确认：

- 没有当前确认：unverified
- 只有机器或流程确认：machine-confirmed
- 有人的当前确认：human-reviewed

Agent 在人审之后又改了一稿，这条知识回到未人工确认，直到人再签一次。旧签收留在文件里当历史。

## 更新迭代：按风险分流，而不是一律人工或一律自动

| 风险 | 例子 | 写入 | 复核 | 过期 |
| --- | --- | --- | --- | --- |
| 高 | 收入、客户、违约、权限、安全生产、对外承诺 | Agent 只出 diff 和依据 | 具名负责人通过后才是 stable，查询路径强制检查 | 短，如 30–90 天，或随制度版本 |
| 中 | 运行手册、领域综述、事故复盘 | Agent 可合并到草稿分支 | 负责人抽检；自动扫矛盾和断链 | 按主题，如季度 |
| 低 | 会议纪要、长尾操作说明、阅读笔记 | 带来源即可入库 | 周期 lint；被高风险页引用时升级 | 随来源失效 |

一次合格的变更闭环：

1. 来源变更（连接器、Git、工单、仪表盘、人工投喂）。
2. 解析并保留原文指针；权限从原系统继承，不在索引里重新发明一套。
3. 生成补丁：更新实体页、标出与旧主张的冲突、写日志。
4. 按风险进入队列。驳回的草稿不得进入可信检索。
5. 发布后重建受影响的关键词、向量和图投影。能按文档删除的系统，删除和替换必须落到切块和图节点。
6. 用固定问题集做回归。变了的召回、引用和关键口径要失败可见。
7. 周期 lint：矛盾、断链、孤儿页、过期主张、该有专页却没有的概念。

Karpathy 在 2026-04-04 的 LLM Wiki 里把维护成本讲清楚了：人放弃知识库，是因为簿记比阅读更累。LLM 适合做簿记。企业场景要补上的是：簿记结果里，关键口径仍要有人负责。见 LLMwiki。

## 持续治理：避免上线即腐烂

每周看队列，每月看健康，每季看价值。指标尽量能从系统里算出来。

**所有权**

- 每条可被高风险回答引用的知识有一个负责人。共同编辑可以， accountable owner 只有一个。
- 同名不同义用域分开，例如 `Finance.Net Revenue` 和 `Sales.Net Revenue`。Snowflake 2026-11 的 Business Ontology 用这种限定名。见本体篇。
- 含义和计算公式分开拥有。定义回答「活跃客户是什么」；指标回答「在这张表上怎么数」。表结构变化不应该伪装成口径变化。

**新鲜度**

- `stale_after` 用绝对时间。到期后高风险检索降权或排除，并指向替换页。
- 「最后编辑时间」不算治理。没有复核策略的页面，默认会过期。
- 来源侧能增量同步。网站、网盘、Notion、飞书、Confluence 至少要有周期刷新；删除必须传播。

**权限**

- 在检索时用调用者身份和来源 ACL 求交。生成之后再过滤，已经太晚。
- 共享向量库加上事后过滤，是常见的串库路径。OWASP 对向量和嵌入的风险清单把跨上下文泄漏、知识投毒和弱访问控制列在一起。
- MCP 入口自己做认证和授权。一次检索返回的 ID，不能当成下一次读取原文的许可。
- 答案、深度链接和引用都要服从同一权限。看不见那份仪表盘的人，Agent 也不用它来回答。

**审计与评测**

- 日志保留：问题、命中的知识 ID 和版本、策略判定、答案、反馈。秘密和连接串不进日志。
- 评测集用真实问法：缩写、旧名称、问一半、互相冲突的来源。只跑编写者写的漂亮问题，测不出上线后的失败。
- 任务结果和引用正确率一起看。答得顺、引错来源，记为失败。
- 高风险答案要能还原「用了哪一版定义」。银行、保险和对外财务场景把这一点当成上线条件，而不是体验优化。

**组织**

- 数据团队的高价值工作从「替业务写完全部定义」变成「经营确认队列、权限、评测和例外」。
- 业务负责人确认关键口径。Agent 从 SQL、仪表盘、笔记和工单里整理长尾。
- 写和确认分离。生成者不是确认者。OKF 把 `generated` 和 `verified` 分成两个字段，就是这个原因。

## 2026 年的参考实现，按层挑选

没有一个开源项目同时把六层做完。选型时按缺口补，不按星数选「平台」。

| 缺口 | 可看的公开实现 | 检索日页面 | 注意 |
| --- | --- | --- | --- |
| 个人或小团队的编译型 wiki | Karpathy 模式；[lucasastorian/llmwiki](https://github.com/lucasastorian/llmwiki/) | Apache-2.0，约 1783 star，2026-04-04 创建 | 自主维护要加确认关卡才能进企业关键口径 |
| 本地优先的 ingest / query / lint | [ddsyasas/llm-wiki](https://github.com/ddsyasas/llm-wiki) | MIT，v1.2.3，约 75 star | 规模小，模式完整 |
| 从编码会话沉淀 wiki | [Pratiyush/llm-wiki](https://github.com/pratiyush/llm-wiki) | MIT，约 402 star | 材料是会话，不是制度原文 |
| 文档 RAG + Agent + 自动 wiki | [Tencent/WeKnora](https://github.com/Tencent/WeKnora) | 约 38004 star；v0.9.0 发布于 2026-10-29 | 许可证页为 Other，使用前读 LICENSE。有工作区 RBAC、审计、切块和 wiki 回滚 |
| 深度文档解析和知识编译 | [infiniflow/ragflow](https://github.com/infiniflow/ragflow) | Apache-2.0，约 94547 star；1.0.0 发布于 2026-11-06 | 2026-08-19 起能把数据集编译成 Wiki、图、树、PageIndex 等 |
| 应用侧知识库和定时同步 | [langgenius/dify](https://github.com/langgenius/dify) | 约 161652 star；许可证页为 Other | Agent 知识库支持按计划刷新网站、在线文档和网盘，并保留坏例 |
| 图检索 | [HKUDS/LightRAG](https://github.com/HKUDS/LightRAG)、[microsoft/graphrag](https://github.com/microsoft/graphrag) | 均为 MIT | GraphRAG 官方已进入维护模式；增量删除见 RAG 篇 |
| 从元数据起草本体 | [NVIDIA/auto-ontology](https://github.com/NVIDIA/auto-ontology) | Apache-2.0，约 14180 star，2026-04-27 创建 | 认证字段还不是原子发布流程，见本体篇 |
| 规范知识交换格式 | [open-knowledge-format](https://github.com/open-knowledge-format/open-knowledge-format) | SPEC v0.3 | 信任、新鲜度、生命周期；不管权限 |

星数为检索当日仓库页显示值，只用于判断社区体量。

## 90 天落地，不先上全公司平台

**第 1–2 周，定边界。** 选一个会反复被问、答错有代价的域，例如结算口径、事故升级或权限申请。列出来源系统和它们现在的 ACL。点名 15–30 个关键术语的负责人。写下：未确认定义不得进入这类回答。

**第 3–6 周，先有规范层和检索层。** 关键术语用 OKF 或等价 frontmatter 入库。长文档走混合检索，权限在检索时生效。准备 30–50 道来自真实工单的问题，含冲突来源和过期叫法。索引从规范文本重建，规范文本不从索引回写。

**第 7–10 周，把确认做成关卡。** 关键术语只有 `human-reviewed` 且未过期的版本可被高风险工具引用。Agent 的修改进草稿队列，界面上能看 diff、来源和驳回理由。图或向量侧证明：删除一篇文档后，旧切块不再被命中。

**第 11–12 周，把腐烂变成队列。** 打开 `stale_after` 扫描、矛盾 lint、断链检查和评测回归。给负责人一个每周队列，而不是一个新的文档站点。用四周的数据决定要不要扩展到第二个域：队列是否有人清、黄金问题是否稳定、有没有未确认口径漏进高风险答案。

扩展时复用同一套对象和日志。不要为第二个域再抄一份向量库，也不要让每个 Agent 私藏一份口径。

## 上线前的七个检查

1. 未经过负责人确认的口径，能否被 Agent 用来回答财务、合规或安全问题？期望是不能。
2. 答案是否记下定义 ID、版本和来源？期望是能还原。
3. 定义能否带负责人和审批历史导出？期望是能，避免锁死在一家平台里。
4. 检索是否按调用者身份过滤，并继承原系统权限？期望是生成前过滤。
5. 删除或替换一篇来源后，切块、图节点和 wiki 引用是否一起失效？期望是能证明。
6. 同一个词在两个部门含义不同时，系统是否保留两个概念？期望是按域并存。
7. Agent 改写已确认页面后，旧的人工签收是否自动失效？期望是失效，直到人再确认。
