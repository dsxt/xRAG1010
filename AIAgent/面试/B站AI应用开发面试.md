### 3. 为什么用Python又碰Golang，两边在你项目里分别干什么

- **Python**：LLM应用业务层。快速迭代Agent逻辑、LangGraph状态机、RAG检索链路、Embedding、prompt编排、模型调用、评测脚本。生态完善，适合快速实验和业务逻辑开发。缺点：并发弱、启动慢、资源开销大，不适合高并发网关。
- **Golang**：底层调度网关/harness底座。Agent任务队列、并发调度、限流熔断、超时控制、鉴权、多请求路由、结果缓存。优势：轻量协程，高并发、低内存占用，适合承载大量Agent请求，隔离模型调用的异常，保护Python业务服务。
  一句话总结：Python负责**智能逻辑**，Golang负责**高可用工程底座**。

### 4. 意图识别是怎么做的，规则、分类模型、LLM路由还是混合

生产环境**混合方案最优**：

1. 前置硬规则：高频明确query直接匹配，低成本拦截；
2. 轻量小分类模型：处理大部分标准意图（速度快、token成本低）；
3. LLM路由：只留给歧义、长尾、复杂query。
   优点：平衡成本、延迟、准确率。纯LLM路由太贵，纯规则覆盖不了长尾，纯小模型对模糊query泛化差。

### 5. 意图识别错了怎么兜底，用户一句话既像查视频又像发弹幕你怎么处理

1. **置信度阈值**：模型输出置信度低于阈值，不直接判定单一意图，走歧义分支；
2. **多候选并行预检索**：同时走两条分支的轻量检索，根据检索结果相关性二次判断；
3. **人机澄清兜底**：无法判定时，反问用户确认意图，而不是强行猜测；
4. **事后回写badcase**：把歧义样本回流到数据集，迭代分类模型/规则；
5. 安全兜底：禁止在意图不确定时执行写操作（发弹幕），只读查询优先放行。

### 6. RAG里召回和生成谁更容易翻车，举你踩过的坑

**召回更容易翻车。生成的幻觉根源大多来自召回错误**
踩坑举例：

1. 短文本噪声（弹幕）embedding召回语义漂移，把无关视频chunk捞出来；
2. chunk切分破坏语义，一段内容被截断，导致上下文残缺；
3. 向量库距离偏差，相近语义但是完全无关事实；
4. 时间/作者metadata没过滤，召回其他UP主内容；

> 生成侧问题：召回内容正确时，LLM偶尔编造细节；召回错了，生成一定会错。
> 优化手段：混合检索（关键词+向量）、rerank重排、metadata过滤。

### 7. Embedding模型怎么选，中文弹幕/标题/评论这种短噪声文本怎么处理

**选型思路**：优先中文领域微调Embedding，优先测试业务真实样本，不是看排行榜。
评估维度：中文语义能力、短文本效果、推理速度、向量维度、显存开销。
**短噪声文本（弹幕）处理**

1. 预处理：清洗emoji、无意义重复字符、停用词；
2. 语义补全：短query拼接上下文，做句子扩展；
3. 混合检索：向量检索 + BM25关键词检索互补，弥补短文本embedding质量差；
4. 负样本训练/微调：用弹幕业务数据微调embedding，降低噪声干扰；
5. rerank二次过滤，剔除语义匹配但事实无关结果。

### 8. LangChain 和 LangGraph 你更喜欢哪个，别背官网话

LangChain适合简单链式RAG，但是复杂Agent状态流转、多轮分支、断点恢复很难写，状态管理混乱，不适合生产级多Agent。
LangGraph核心价值是**状态机**，支持分支、循环、条件跳转、持久化状态，适合Agent多轮工具调用、人机协同。
缺点：学习成本更高，需要自己维护state结构，框架封装会带来一定黑盒问题，简单场景用它会过度设计。
我的选择：简单问答RAG用LangChain；需要循环工具调用、多Agent、断点恢复的复杂工作流，用LangGraph。

### 9. LangGraph 里 state、node、edge、conditional edge 你实际怎么用

- `state`：全局状态，存储对话历史、工具返回结果、错误信息、当前任务、用户query，**所有节点共享，不可直接原地修改，每次节点返回新state**
- `node`：执行单元，比如意图识别节点、检索节点、工具调用节点、LLM生成节点。接收state，执行业务逻辑，返回更新后的state。
- `edge`：固定跳转，A节点执行完固定走到B节点
- `conditional edge`：条件分支，根据state里面字段判断下一跳节点。例：判断是否需要调用工具，需要→工具节点，不需要→回答节点。

> 实战：state尽量精简，不要无限累积历史；conditional edge用来终止循环，防止Agent死循环调用工具。

### 10. 多Agent什么时候该拆，什么时候纯属装复杂

✅ **适合拆多Agent**

1. 任务天然解耦，职责边界清晰（检索Agent、工具执行Agent、规划Agent、校验Agent）；
2. 不同Agent需要独立模型/权限/内存；
3. 任务长链路，可以并行执行子任务；
   ❌ **不该拆，过度设计**
4. 简单任务，单轮LLM就能完成；
5. 子任务强耦合，大量上下文互相拷贝，信息传递损耗大；
6. 拆分后调度成本、错误排查成本远大于收益。

> 原则：优先单Agent，职责边界清晰、收益明确再拆多Agent。

### 11. Agent调工具失败、超时、返回脏数据，harness层怎么兜

harness层=工具调用的**容错与校验层**

1. 超时控制：Golang网关设置超时，超时直接熔断，重试策略（有限次数、退避重试，幂等工具才重试）；
2. 返回schema校验：对工具返回结果做JSON schema校验，脏数据直接拦截；
3. 结果合法性校验：校验字段范围、业务规则，过滤无效/越界数据；
4. 错误分类：区分网络错误、业务错误，不同错误给不同提示词回传给LLM；
5. 降级兜底：工具不可用时，返回预设兜底信息，不直接崩溃；
6. 日志埋点：记录调用入参、出参、错误类型，用于badcase分析。

### 12. Python 里异步和同步在 Agent 调用链里你怎么选

- **同步**：开发简单，调试方便。适合单条链路、开发调试、低QPS场景。缺点：IO阻塞，并发差，大量LLM/工具请求时吞吐量低。
- **async异步**：LLM、向量库、工具调用都是IO密集型，异步可以并发等待多个IO，提升吞吐，节省资源。适合线上高并发Agent服务。

> 工程取舍：生产环境主链路用async；复杂业务逻辑如果同步代码可读性高，局部可以同步。注意异步代码异常更难调试，要做好异常捕获。

### 13. Golang 写 Agent 网关/调度层相比Python有什么优势

1. 轻量协程，高并发，内存占用低，大量并发Agent请求资源开销远小于Python；
2. 编译型，性能稳定，无GIL锁问题；
3. 适合做流量控制：限流、熔断、队列、超时、鉴权；
4. 服务稳定性好，不容易因为单个请求异常拖垮整个进程；
5. 可以做请求隔离，保护上游Python LLM业务服务。

> 短板：LLM生态弱，不适合写prompt、RAG、模型推理业务。

### 14. 手撕算法：给一堆用户query，按意图类别分组并去重，输出每类出现次数Top K

思路：

1. 字典`key=意图类别，value=query集合（去重）`；
2. 遍历所有query，分类后加入对应集合自动去重；
3. 统计每个意图集合长度；
4. 对意图按数量降序排序，取Top K。
   Python伪代码：

```python
from collections import defaultdict

def top_k_intent(queries, intent_list, k):
    intent_map = defaultdict(set)
    for q, intent in zip(queries, intent_list):
        intent_map[intent].add(q)
    cnt = [(intent, len(qs)) for intent, qs in intent_map.items()]
    cnt.sort(key=lambda x:x[1], reverse=True)
    return cnt[:k]
```

## 二面

### 1. 自我介绍（同一面）

### 2. 挑一个最复杂的AI工作流讲清楚：输入、路由、工具、记忆、输出、回写

推荐Agent问答工作流

1. **输入**：用户query + 会话历史
2. **路由**：意图识别，歧义校验，判断是否需要检索/调用工具
3. **工具**：向量库检索、业务API（视频信息查询）
4. **记忆**：短期会话记忆state；长期用户记忆存入数据库，每次读取；区分对话历史和业务数据
5. **输出**：LLM生成回答，harness校验输出，过滤幻觉；
6. **回写**：把本次query、结果、是否失败写入日志；badcase自动入库，定期回流训练集。

### 3. 多Agent协作时上下文怎么传，会不会越传越傻

上下文传递方案：**不要全量复制全部历史**

1. 主Agent维护全局精简上下文，子Agent只拿到**任务相关子集**；
2. 子Agent返回结果只返回结论，不返回完整内部对话，减少token膨胀；
3. 设置上下文窗口截断、摘要压缩；
4. 增加校验Agent，校验子Agent返回结果真实性。

> 越传越傻根源：上下文无限膨胀、无关噪声信息传递、错误信息层层传递。对策：摘要、过滤、结果校验。

### 4. 共享 memory 和私有 memory 你怎么设计

- **私有memory**：单个Agent私有，比如规划Agent的中间思考，工具执行Agent临时参数，其他Agent不可见；减少全局state体积，隔离内部细节。
- **共享memory**：全局公共信息，用户原始query、最终结论、用户基础信息，所有Agent可读，只有主节点可以修改。

> 存储：短期放LangGraph state；长期持久化到数据库，区分会话级记忆 & 用户长期记忆。

### 5. RAG 里 chunk size、overlap、metadata、rerank 你是怎么调出来的

**chunk size**：看文本类型。视频字幕：200~500token；长文稿800-1000。太小语义破碎，太大向量丢失细节。靠离线召回评测集调参。
**overlap重叠**：一般chunk的10%~20%。用来避免语义在chunk边界被切断；太高会重复检索，增加成本。
**metadata**：存储UP主、视频ID、时间戳、发布时间；检索时做过滤，限定视频范围，防止跨视频信息污染。
**rerank**：向量召回Top50，rerank压缩到Top3~Top5。解决向量召回语义匹配但事实不匹配的问题。

> 调参方式：构造业务离线测试集，用召回准确率、答案正确率作为指标，网格搜索参数，不是凭感觉。

### 6. 用户问B站某个UP主视频里的内容，RAG怎么避免答成全网泛知识

核心：**强限定检索范围，强制优先使用知识库内容**

1. 检索metadata强制过滤：只取该UP主+指定视频ID的chunk；
2. Prompt强约束：优先使用检索片段，检索不到时禁止编造外部知识，直接告知没有相关信息；
3. 增加事实校验Agent，检查回答内容是否在检索片段内；
4. 召回兜底：检索结果为空时，禁止调用模型外部知识。

### 7. LangGraph人机协同、断点恢复、回滚你做过没

- **人机协同**：在conditional edge判断，当需要人工确认时，中断图执行，state持久化，等待人工输入，人工确认后继续跑图。
- **断点恢复**：每次node执行完成，持久化完整state到数据库；服务重启后，可以读取state，从上次中断节点继续执行。
- **回滚**：保存state快照。如果后面节点校验失败，恢复到之前快照，撤销已经执行的副作用操作（比如写数据库）。

> 注意：有副作用的工具（写数据），要做事务补偿，不能只回滚state。

### 8. Agent循环调用工具停不下来怎么治，max step之外还有啥招

max step只是兜底。更多方案：

1. **循环检测**：记录工具调用序列，如果出现重复入参+重复工具，判定死循环，强制终止；
2. 状态校验：判断当前state是否收敛，连续多次没有新增有效信息就停止；
3. 工具权限隔离：区分只读工具和写工具，循环只出现在只读查询；
4. prompt约束：告诉模型，多次查询得不到信息要直接回答，不要反复重试；
5. harness层校验：统计连续调用相同工具次数，超过阈值直接熔断。

### 9. 工具定义混乱导致模型乱填参数，harness层怎么校验和收敛

1. 强JSON Schema：严格定义工具参数类型、枚举、范围；模型输出不满足schema，直接拒绝；
2. 参数业务校验：比如视频ID格式校验、数值范围校验；
3. 错误反馈：校验失败，返回结构化错误信息给LLM，让模型修正参数，有限重试次数；
4. 工具描述优化：精简tool definition，不要冗余描述，减少模型混淆；
5. 预过滤：harness提前清洗参数，过滤非法字符。

### 10. Golang侧怎么做Agent任务队列、限流、降级

1. **任务队列**：使用Redis/RabbitMQ做任务队列；Goroutine worker池消费；任务持久化，支持重试。
2. **限流**：令牌桶/漏桶；按用户、接口、模型维度限流；区分普通用户、高优请求。
3. **熔断降级**：模型/工具错误率超过阈值，熔断；降级策略：返回静态兜底回答，切到轻量模型，关闭非核心Agent能力。

### 11. 高并发下 LLM 调用成本炸了，你怎么控token 和钱

1. 缓存：相同query缓存LLM结果，命中缓存直接返回；
2. 精简prompt：压缩system prompt，截断冗余历史；用摘要代替完整对话历史；
3. 路由策略：简单query用小模型，复杂问题才调用大模型；
4. RAG优化：减少召回chunk数量，rerank压缩上下文；
5. 预校验：意图识别前置过滤无效请求；
6. 配额+限流：用户侧token配额，防止恶意调用；
7. 批量推理，复用embedding结果。

### 12. 评测怎么做，别只说人工，自动评测指标和坏case回归怎么说

**自动评测指标**

- RAG：召回率、精确率、上下文相关性、事实一致性；
- Agent：任务完成率、工具调用成功率、幻觉率、步骤步数、token消耗、延迟。
  自动评测方案：LLM-as-judge，构造测试集，自动打分。
  **坏case回归**

1. 线上收集badcase入库；
2. 每次版本迭代，自动跑全部历史badcase，回归测试；
3. 指标下跌阻断上线；
4. badcase定期回流到prompt、检索、意图模型的迭代数据集。
   人工评测做抽样复核，用来校准自动评测。

### 13. 线上Agent答错了，怎么定位是召回烂、prompt烂、模型烂还是工具烂

分层定位：

1. 看完整链路日志：用户query → 意图结果 → 召回文档 → prompt → 模型输出 → 工具返回；
2. **召回烂**：检索出来的原文本身就是错的/无关；
3. **prompt烂**：召回内容正确，但prompt约束不足，模型无视参考信息；
4. **模型烂**：参考信息充足、prompt没问题，模型编造事实；
5. **工具烂**：工具API返回脏数据/错误结果。
   验证方法：隔离变量，固定其他部分，单独替换模块复测。

### 14. 手撕算法：实现简易拓扑排序，用来跑DAG工作流节点依赖

原理：Kahn算法，入度表+队列

```python
from collections import deque
def topo_sort(graph):
    # graph: key节点，value依赖列表
    in_degree = {u:0 for u in graph}
    for u in graph:
        for v in graph[u]:
            in_degree[v] +=1
    q = deque([u for u in in_degree if in_degree[u]==0])
    res = []
    while q:
        n = q.popleft()
        res.append(n)
        for neighbor in graph[n]:
            in_degree[neighbor]-=1
            if in_degree[neighbor]==0:
                q.append(neighbor)
    # 环判断：结果长度小于总节点数
    if len(res) != len(graph):
        return None # 存在环
    return res
```

### 14. 手撕算法：给定一个工具调用序列，检测是否存在环/死循环调用，并输出环路径

DFS + 递归栈方法。
思路：遍历调用序列，记录当前路径；访问到已经在当前路径里的节点，找到环。

```python
def find_cycle(adj):
    visited = set()
    rec_stack = []
    cycle = None
    def dfs(u):
        nonlocal cycle
        visited.add(u)
        rec_stack.append(u)
        for v in adj[u]:
            if v not in visited:
                if dfs(v):
                    return True
            elif v in rec_stack:
                idx = rec_stack.index(v)
                cycle = rec_stack[idx:] + [v]
                return True
        rec_stack.pop()
        return False
    for node in adj:
        if node not in visited:
            if dfs(node):
                return cycle
    return None
```
