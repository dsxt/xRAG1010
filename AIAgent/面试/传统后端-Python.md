# 传统后端学习笔记（Python）

一份 Python 服务从请求进入到数据落地的知识体系。业务数据以 MySQL 为准，Redis 承担缓存、计数和原子扣减，Elasticsearch 承担搜索，消息队列承担异步和削峰，网关承担入口的鉴权和限流，容器和 Kubernetes 负责交付。进程里用 FastAPI 接请求，用 SQLAlchemy 2.0 访问数据库。

库以仍在维护的为准：`redis`（redis-py）、`elasticsearch` 8 的 DSL、`nacos-sdk-python` v2、`rocketmq-python-client` 5.x、SQLAlchemy 2.0、`asyncmy`、`mysql-replication`、`aio-pika`、`aiokafka` 或 `confluent-kafka`、`httpx`、OpenTelemetry 的 Python SDK。

一条写请求穿过这些层：

1. 连接在 Linux 上完成 TCP 握手，TLS 和 HTTP/2 在 Ingress 结束，Uvicorn 收到 HTTP/1.1。
2. 网关校验令牌、写入请求 id、按用户限流，再转到 Service。
3. FastAPI 把请求 id 放进 `contextvars`，参数由 Pydantic 校验。
4. 库存、限购这类读改写在 Redis 里用 Lua 一次做完。
5. 订单行和发件箱行在同一个 MySQL 事务里提交。提交同时落 redo 和 binlog。
6. 后台循环把发件箱推到队列。消费者建下游单据或更新搜索索引，按业务键幂等。
7. 日志、指标、trace 带同一个请求 id。副本挂了由 kubelet 拉起，扩容看饱和度。

读请求先看进程内短缓存，再看 Redis，最后查库并回填。强一致的读打主库。

下面先走完一次提交和一次读详情。开发流程放在这些机制之后：分支怎么收拢、同一份镜像怎么从预发进生产、出了问题怎么退回上一份。随后十三节对应这条路径上要能讲清的机制：MySQL、Redis 与缓存、计算机网络、Linux、开发框架、消息队列、Docker 与 Kubernetes、微服务、分布式理论、系统设计、可观测性、云平台、安全底线。网络一节里有 gRPC 和 WebSocket/SSE，Kubernetes 一节里有持久卷，分布式理论一节里有 Paxos。

## 一次请求

用两笔请求把浏览器、网关、应用和数据库走完。写请求是用户在页面上提交一笔普通订单。读请求是打开这笔订单的详情。业务数字以 MySQL 为准，Redis 做扣减前的原子判断和详情缓存。这一节定顺序、每一层的责任，以及提交在中途断开时浏览器、Redis、MySQL 各剩什么。锁、复制、连接池和发件箱的机制在后面各节。

### 三层各管一段

| 层 | 跑在哪 | 这次请求里做的事 |
| --- | --- | --- |
| 前端 | 浏览器里的 React / TypeScript | 收集表单，带登录态发出 HTTP，按错误码改界面 |
| 后端 | 网关进程和 FastAPI 进程 | 鉴权、限流、生成请求 id，按顺序调用 Redis 和 MySQL |
| 数据库 | MySQL、Redis | MySQL 留下订单、库存和发件箱；Redis 留下可重建的计数和缓存 |

一次点击在浏览器里开始，在数据库里结束。中间每一跳带着同一个请求 id，日志才能对上。浏览器只发 HTTP。MySQL 和 Redis 的连接留在后端进程里。

### 写：提交订单

页面上已有商品、数量和收货地址。页面上的库存只是展示，提交时再问一次后端。

```text
浏览器
  → 网关：验令牌、限流、盖上用户 id、传请求 id
  → FastAPI：校验这张单属于这个用户
  → 主库：幂等行已在就直接返回
  → Redis：Lua 认幂等键并扣减
  → MySQL：同一事务写订单、条件扣库存、发件箱、幂等行
  → 返回订单号
  → 后台循环把发件箱推到队列
  → 消费者更新搜索或创建下游单据
```

#### 前端

点击之后按钮进入提交中。同一笔订单的第二次点击不再发新请求。

请求体是 JSON：商品、数量、地址、一把幂等键。幂等键在这次点击时生成，放进 `sessionStorage`，键名带上这次提交。刷新页面还能用它查结果。只放在按钮组件的内存里，超时之后页面一重建，就只剩再试一次，于是换成新键，变成第二张订单。超时后的重试用同一把。用户明确要再下一笔，才换新的。

请求头带登录得到的令牌。上游已经给出追踪 id 就放进头里。响应里把请求 id 拿回来，失败时显示在页面上，方便对日志。

浏览器自己的超时比网关略长，网关的错误码才能回到页面。页面展示码和一句说明：未登录、被限流、库存不足、重复提交。堆栈留在服务端日志。

成功响应里是订单号和状态，页面跳到详情。超时之后用这把幂等键查一次订单在不在：在，就按成功展示；不在，再让用户重试。这次查询仍走后端。

#### 后端

请求先到网关。网关校验令牌，从令牌取出用户 id，写进往下传的身份。请求体里客户端自己填的用户 id 被盖掉。限流按用户；没有登录态的接口按 IP。请求体超过上限直接拒绝。通过之后把请求 id 往下传。头里没有，FastAPI 自己生成，放进 `contextvars`。日志、Redis 和数据库操作都带上它。

FastAPI 处理这张单本身：参数是否齐全、数量是否为正、地址是否属于这个用户。网关不知道订单属主。

重试先查主库里的幂等行。行已经在，返回那张订单，不再碰 Redis。行不在，才执行 Lua。Lua 认的是这把幂等键，不只是库存数字。

```lua
local held = redis.call('GET', KEYS[2])
if held then
  return held
end
local left = tonumber(redis.call('GET', KEYS[1]) or '-1')
local n = tonumber(ARGV[1])
if left < n then
  return '-1'
end
redis.call('DECRBY', KEYS[1], n)
redis.call('SET', KEYS[2], 'held', 'EX', ARGV[2])
return 'held'
```

`KEYS[1]` 是库存，`KEYS[2]` 是幂等键。已经是 `held`，直接返回，不再减。库存不够返回 `-1`，不占这把键，稍后库存回来还能再试。够了就把「记下这把键」和「减库存」放在同一次执行里。两个并发请求不会都读到「还剩 1」再都减成功。`ARGV[2]` 是占住的秒数，要长于网关超时，盖住服务超时和一次重试。键先于事务结束而消失，下一次重试会再减一截。

返回 `-1` 就报库存不足，MySQL 不打开事务。返回 `held` 才进 MySQL。同一事务里写订单行、库存的条件更新、发件箱和幂等行。库存更新写成：

```sql
UPDATE inventory
SET stock = stock - :n
WHERE id = :id AND stock >= :n
```

`rowcount` 为 0，事务回滚。加回用另一段 Lua：键仍是 `held` 才 `INCRBY`，并删掉这把键，避免两次加回。加回放在请求任务外面，单独起一个有上限的任务。请求协程被取消，加回还在跑。加回失败，或进程在加回之前停了，Redis 就少一截；键过期之后的重试会在这个偏少的值上再减。对账用 MySQL 里的库存覆盖 Redis，不在偏少的值上累加。不确定提交成功没有，先查主库幂等行，不先加回。这些行一起提交，或一起没有。

事务提交之后，接口返回「已下单」。搜索索引、通知、下游单据留在事务外面。另一个循环扫发件箱里未发送的行，推到队列，成功再标成已发送。进程在推送前停了，重启会再推，消费者按订单号做幂等。幂等表、发件箱和确认时机在消息队列那一节。

HTTP 调用和 Redis 调用放在这个事务外面。行锁占到提交为止，中间夹一次外部调用，会挡住别人改同一行库存。

秒杀是这条路径的变体，请求里不建单。活动库存预先写进 Redis，限购和扣减放在同一段 Lua 里，成功后把用户、SKU、请求 id 放进队列，消费者按数据库能承受的速度建单。订单表用用户加活动加 SKU，或用请求 id 做唯一键。脚本和拆段在系统设计的秒杀一节。普通下单仍在请求里把订单和发件箱一起提交。

#### 数据库

MySQL 存必须对的数：订单、库存、发件箱。连接从进程级连接池取，请求结束归还。每个 worker 一份池。总数是副本数 × worker 数 ×（`pool_size` + `max_overflow`），要小于 `max_connections` 的八成，式子和 `pool_recycle` 在 SQLAlchemy 那一节。

Redis 存可以重建的数：预扣的库存计数，以及后面会写上的详情缓存。Redis 丢了，用 MySQL 重新灌。MySQL 里没有的订单，就是没有这张单。

提交成功后删掉这张订单详情的 Redis 键。下一次读从 MySQL 回填。删失败就记一条待删，后台再删。键上的 TTL 是最后一道。先删缓存再被旧值回填的竞态，在缓存那一节。

队列里的消费者晚于事务。用户已经看到订单号时，搜索里可能还没有这条。详情页读 MySQL，或读刚从 MySQL 回填的缓存。

### 读：打开订单详情

```text
浏览器 GET /orders/{id}
  → 网关：验令牌、限流
  → FastAPI：短缓存 → Redis → 主库
  → 用行里的用户 id 对请求头，再返回 JSON
```

#### 前端

详情页用订单号发 GET。登录态和请求 id 与写请求同一套头。GET 可以安全重试。页面先保留上一份已经拿到的数据，新的响应到了再替换。未登录去登录页。订单不存在，停在说明页。

#### 后端

网关同样验令牌和限流。FastAPI 先取出这一行，再用行里的用户 id 对请求头里的用户。对不上就拒绝。订单号被猜中也一样。

读的顺序固定。先看本进程的短缓存，秒级 TTL，用 `cachetools.TTLCache`。没有再看 Redis，分钟级 TTL。都没有再查主库，查到后回填两级缓存。缓存里放的是行，鉴权在读出之后。同一个订单号同时过期时，这个 worker 里按键加锁，只放一个协程去查库。这把锁只挡住本进程。多个 worker 同时过期，靠 Redis 锁。

查无此单可以短缓存。这把键只表示这个 id 没有行。不属于这个用户的拒绝不写进这把共享键，下一个用户不会因此看到别人的拒绝。

#### 数据库

这次读到的行来自 InnoDB 已提交的版本。普通 `SELECT` 不加锁。缓存键带业务版本，例如 `order:v3:{id}`。字段结构变了就换前缀，旧键等 TTL 自己消失。

刚提交完跳到详情的这次 GET 打主库。从库还没追上时，读副本会把刚写下的订单说成不存在。之后的普通详情可以接受秒级旧缓存。

每个 worker 有自己的一份短缓存。订单在别的进程里更新之后，本进程要等本地 TTL 结束才去看 Redis。所以本地用秒，Redis 用分钟。

### 时间与失败

超时从外往里变短。浏览器 3 秒，网关 2.5 秒，服务 2 秒。外层更长，内层的错误码才能回到页面。这两秒里要装下 Lua、借连接和条件更新。加回 Redis 另计一个几百毫秒，不占这 2 秒里已经用完的剩余。数字和重试预算在网络那一节，这里把每一刀切断时三边各剩什么列出来。

| 断在哪 | 用户看见 | Redis | MySQL | 同一把幂等键再来 |
| --- | --- | --- | --- | --- |
| Lua 之前 | 超时或失败 | 未动 | 未动 | 重新扣 |
| Lua 返回 `held`，事务未提交 | 超时 | 已减，键是 `held` | 未提交 | 不再减，事务再做一遍 |
| 事务已提交，响应没回到浏览器 | 超时 | 已减，键仍是 `held` | 订单、库存、发件箱、幂等行都在 | 主库查出这张订单，当成功 |
| 条件更新行数为 0，加回成功 | 库存不足 | 数量加回，键删掉 | 已回滚 | 可以再扣 |
| 行数为 0，加回失败，或进程在加回前停了 | 库存不足或超时 | 少了一截 | 已回滚 | 键还在就不再减；键过期后会再减。对账用 MySQL 的库存覆盖 Redis |
| 提交成功，详情键还没删掉 | 已下单 | 详情可能是旧的 | 已是新行 | 详情读主库 |

限流发生在网关，数据库还没被碰到。库存不足发生在 Redis 的 Lua，或 MySQL 的条件更新。页面对这两处用同一句「库存不足」。重复点击带着同一把幂等键，第二次看到的是已经写下的那张订单。

### 和模型请求的边界

上面是一笔业务读写。这次请求还要调用模型时，网关在鉴权之后把短请求转给 Python 编排，流式结果用 SSE 写回浏览器。长任务立刻返回 `task_id`，页面改为轮询或订阅进度。顺序、错误码和取消见 [请求全流程](../agent架构/01-请求全流程.md)。

订单和库存的落库方式不变。模型只提出下一步。扣库存仍由这段确定性代码执行。

## 1. MySQL

业务行存在 InnoDB 里。驱动负责连接、事务和 SQL。SQLAlchemy 2.0 是应用侧的入口，异步驱动用 `asyncmy`，连接串形如 `mysql+asyncmy://user:pass@host/db?charset=utf8mb4`。MySQL 8 的库、表、连接都用 `utf8mb4`。名为 `utf8` 的字符集最多三字节，生僻字和 emoji 会在写入时失败。

### 一条写入落在哪

InnoDB 的数据页默认 16KB。Buffer Pool 按页缓存数据和索引。专用机器上缓冲池可以占物理内存的一半到七成；容器里按 memory limit 算，给连接、临时表和操作系统留余量。`innodb_buffer_pool_size` 按宿主机内存去设，容器一限制内存就会被 OOM 杀掉。

缓冲池用变种 LRU。新读入的页先放在 old 区，只有再次被访问才进 young 区。全表扫描因此不会把热点页都挤出去。页被改过就成脏页，由后台刷盘。刷盘跟不上时，用户线程会被迫参与刷页，语句延迟抬高。

改一行时 InnoDB 做三件事。把旧版本推进 undo，形成版本链，供 MVCC 和回滚使用。把页的修改记进 redo，按 WAL 先写日志再刷脏页。把这次变更记进 server 层的 binlog，供复制和恢复使用。redo 是物理逻辑日志，崩溃恢复用它把页补到提交后的状态。undo 是逻辑上的旧版本，恢复一致性读和回滚用它。binlog 是 server 层的逻辑日志，主从复制和增量恢复看它。

redo 先写 Log Buffer，再按 `innodb_flush_log_at_trx_commit` 刷盘。`1` 是每次提交都 fsync，提交返回后崩溃不丢这批事务。`2` 是每次提交写到操作系统缓存、大约每秒 fsync，操作系统还没刷盘时崩溃会丢。`0` 是大约每秒才写日志，丢得更多。生产用 `1`。这个参数只管 redo，不管 binlog。

binlog 刷盘由 `sync_binlog` 控制。`1` 是每次提交都 fsync。和 redo 的 `1` 一起用，一台机器上的已提交事务在进程崩溃后还在。组提交把多个事务的 fsync 合并，用来把这个组合的吞吐做上去。

事务提交在引擎和 binlog 之间是内部两阶段提交：

1. InnoDB 把事务标成 prepare，对应的 redo 落盘。
2. 写 binlog 并 fsync。
3. InnoDB 把事务标成 commit。

崩溃发生在 binlog 落盘之前，恢复时回滚这笔事务，从库也不会看到它。崩溃发生在 binlog 已经落盘、引擎 commit 标记还没写完时，恢复时根据 binlog 把引擎提交完成。这样主库的数据和即将复制出去的日志是同一批事务。只开 redo、不开 binlog，主从会分叉。只靠 binlog 做崩溃恢复，页的修复没有 redo 那么直接。两边都要，并用这个顺序对齐。

binlog 格式用 `ROW`，`binlog_row_image=FULL`。ROW 记的是行的前后像，复制和 binlog 订阅都依赖它。STATEMENT 记 SQL 文本，带不确定函数时主从会算出不同结果。`binlog_expire_logs_seconds` 控制保留时长，保留太短会让断线的从库补不上增量，只能重做全量。

脏页刷回数据文件时，一页是 16KB，磁盘不一定把这一页一次写完。写到一半掉电，页就撕开了。redo 记录的是在一页完整内容上的修改，应用到半页上会得到坏页。doublewrite 在写数据文件之前，先把这批脏页顺序写到一块专门的区域并 fsync，然后再写各自的数据页。恢复时数据页校验通不过，就从 doublewrite 区域把整页拷回来，再应用 redo。这块区域是刷盘用的缓冲区，不是每页永久存两份。`innodb_doublewrite` 默认开着。只有磁盘保证整页原子写入时才关掉，普通云盘保持打开。

二级索引页不在缓冲池里时，修改它要先随机读入这一页。change buffer 把非唯一二级索引上的插入、删除标记先记在缓冲池里的一块变更缓冲，等这页因为别的查询被读入，或者后台合并，再合进真正的索引页。唯一二级索引要先读页才能判断键是否重复，走不了这条路径。缓冲池已经装得下工作集时，change buffer 帮不上忙，合并还会在读的时候突然变慢。写入远大于内存、二级索引又多时，它才划算。`innodb_change_buffer_max_size` 是它在缓冲池里的比例上限，默认 25。

### 一条语句怎么走

一条 SQL 先过服务器层，再进 InnoDB。

1. 连接器做 TCP 握手和认证。MySQL 8 默认认证插件是 `caching_sha2_password`。连接空闲超过 `wait_timeout` 就被断开。密码和全局权限在连接时确定，改密码对已经连着的会话要重连才生效。库级权限在下一次 `USE` 生效，表和列权限在下一条语句生效。
2. 解析器做词法和语法分析，语法错在这里返回。预处理展开视图、确认表和列存在，把 `*` 展开成列。
3. 优化器按代价选索引、连接顺序和是否用覆盖索引。代价来自索引基数和直方图，统计信息过时就会选错。`EXPLAIN` 看的是这一步的结果。MySQL 8.0 起没有查询缓存，相同的语句不会在服务器里直接交回上一次的结果。结果缓存放在应用和 Redis。
4. 执行器按优化器的计划调用存储引擎。能下推的条件下推到引擎，其余在服务器层过滤。引擎在缓冲池里找页，没有再读盘。这一段就是上一节的页、redo 和锁。

SQLAlchemy 的 `text()` 配绑定参数，值不进 SQL 文本。把用户输入拼进字符串再交给 `text()`，解析器看到的就是攻击者写的语句。

### 索引

InnoDB 用 B+ 树。非叶子节点只存键，叶子才有记录，相邻叶子串成链表，范围扫描沿着链表走。一棵树通常三到四层。二叉树在有序插入时会退化，红黑树对磁盘页不友好，哈希等值快但做不了范围。

主键索引的叶子是整行，这是聚簇索引。二级索引的叶子是索引列加主键。查完整行要拿主键再查一次聚簇树，这是回表。不建主键时，InnoDB 会找一个非空唯一列，找不到就生成隐藏的行 id。隐藏行 id 是全局分配的，并发插入会争用。主键用自增整数：插入多发生在最右边，页满了分裂出新页。随机主键（例如 UUID v4）往页中间插，造成页分裂和碎片。需要在应用里生成、又希望按时间局部有序时，用雪花 id 或 UUID v7。

联合索引按定义顺序排序。第一列相同才比较第二列。查询从左往右用，中间断了，右边的列不能再用来缩小查找范围，但可以留在索引里做过滤。`(name, age, position)` 上，`name = ? AND position = ?` 只用到 `name` 做查找，`position` 在 5.6 之后可以索引下推：存储引擎在索引里顺手把 `position` 比掉，再回表。`Extra` 里是 `Using index condition`。范围条件的右边列同样不能做查找，`name > ? AND age = ?` 往往只用 `name` 定位。

覆盖索引是查询的列都在这棵索引里，`Extra` 出现 `Using index`，不再回表。`SELECT *` 加大范围时，优化器经常放弃二级索引，因为每一行都要回表，代价超过全表扫描。这时只改 SQL 把列收窄，计划就会回到索引上。`FORCE INDEX` 能逼它走，代价不一定更低。

最左前缀包括三种用法：从第一列开始的等值或范围；第一列的最左字符串前缀，`LIKE 'LiLei%'` 能用，`LIKE '%LiLei'` 不能用这棵索引做查找；第一列等值时，后面的列接着用。索引列上包函数、做计算、隐式类型转换，这列的查找能力就没了。

`EXPLAIN` 看 `type`、`key`、`key_len`、`rows`、`Extra`。`type` 从好到差大致是 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL`。`const` 是主键或唯一键等值命中一行。`eq_ref` 是连接时被驱动表按唯一键最多一行。`ref` 是非唯一索引等值，可能多行。`range` 是索引上的范围。`index` 是扫整棵索引的叶子。`ALL` 是全表。`key_len` 看出联合索引用了前几列，计算时把字符集字节数、变长长度和 NULL 标记算进去。`rows` 是估算。`Using filesort` 表示排序没沿索引顺序走，排序缓冲区不够会落到磁盘，名字里的 file 不代表一定在磁盘上。`Using temporary` 表示去重或分组用了临时表。MySQL 8 可以用 `EXPLAIN ANALYZE` 看实际行数和耗时。

`id` 相同的是同一层，数字更大的子查询先执行。`select_type` 里 `SIMPLE` 是单表或简单连接，`PRIMARY` 是最外层，`SUBQUERY` 是标量子查询，`DERIVED` 是 `FROM` 里的子查询，会先落成临时表。`filtered` 是估算里还能留下的百分比，和别的表连接时用 `rows * filtered / 100` 估这一侧的行数。

`key_len` 按字符集算。`utf8mb4` 下一个字符最多 4 字节。`varchar(n)` 还要加长度前缀：这一列的最大字节数不超过 255 时是 1 字节，否则是 2 字节。列允许 NULL 再加 1 字节。8.0 默认 DYNAMIC 行格式，单列索引前缀上限是 3072 字节，更长的字符串只能索引前缀。更早的资料里 768 字节、一个汉字 3 字节，对应的是 COMPACT 和名为 `utf8` 的 `utf8mb3`。

范围很大又必须回表时，优化器会放弃二级索引。`SELECT *` 加一个宽范围经常是这种计划。改成只取索引里的列，变成覆盖索引，计划会回到索引上。要看它比较了哪些代价，打开这一会话的 `optimizer_trace`，执行语句，再查 `information_schema.OPTIMIZER_TRACE`。里面先是把语句展开，再是选索引和算代价。

分页用上一页的游标：`WHERE id > ? ORDER BY id LIMIT 10`。`LIMIT 100000, 10` 会先扫过前面的行再丢掉。按非主键排序时，先在子查询里只取出排序后的主键，再按主键回表拿整行。

连接：有索引的等值连接多是嵌套循环，被驱动表走索引，小表做驱动，循环次数才小。`INNER JOIN` 里谁驱动看 `EXPLAIN`，不看 SQL 里谁写在左边。没索引的大表连接在 8.0 里经常走哈希连接，用较小的一侧建哈希表。更早的块嵌套循环是把驱动表按 `join_buffer` 分块，每块和被驱动表全表比。关联表多、连接列没索引时，行数是相乘的。`STRAIGHT_JOIN` 固定左边驱动右边。

`IN` 适合外表大、子查询结果小。`EXISTS` 适合外表小，对外表每一行去内表探一下。两边连接列都有索引时，优化器常常把它们改写成连接。

`count(*)` 和 `count(1)` 都是数行，InnoDB 会选一棵最窄的索引来扫。`count(列)` 要跳过 NULL，不能用这列不在里面的索引。`count(主键)` 往往扫聚簇索引，行更宽。引擎不保存一张表的精确总行数。MyISAM 对不带 WHERE 的 `count(*)` 直接读自己维护的计数，但没有事务和行锁，业务表用 InnoDB。`SHOW TABLE STATUS` 的 `Rows` 是估算。精确总数如果很贵，就维护在别的存储里，并接受延迟。事务回滚不会自动改那份计数。慢查询打开 `slow_query_log`，阈值从 1 秒收到几百毫秒，再配合 `EXPLAIN` 看计划。

### 事务、隔离与锁

ACID 落在不同的机制上。原子性靠 undo：未提交的修改可以沿版本链撤销。持久性靠 redo 和 binlog 的刷盘：提交返回之后，重启还能找回来。隔离性靠锁和 MVCC。一致性是业务约束，由事务边界、约束和外键一起保住，例如扣款和加款在同一个事务里。

并发现象有四种。脏写是两个事务都按自己读到的旧值去写，后写的覆盖先写的，更新丢了。脏读是读到别人还没提交的修改。不可重复读是别人提交之后，本事务再读同一行，值变了。幻读是同一范围再读，行集合变了，多出来或少掉的行是别的事务插入或删除后提交的。

四个隔离级别：读未提交、读已提交、可重复读、串行化。InnoDB 默认可重复读。读未提交几乎不用于业务。读已提交解决脏读。可重复读在快照读上再解决不可重复读，当前读配合临键锁把幻读也挡住。串行化把普通 `SELECT` 变成加共享锁的当前读。

MVCC 用 undo 版本链和 Read View。行上有隐藏的 `trx_id` 和 `roll_pointer`。每次更新把旧行推进 undo，新版本指回旧版本。普通 `SELECT` 是快照读，不加锁。可重复读在事务第一次一致性读时生成 Read View，记下当时活跃的事务 id，之后普通 `SELECT` 都用这一份，所以别人后来的提交对这个事务不可见。读已提交每次一致性读都生成新的 Read View，能看见最新已提交的版本。

`SELECT ... FOR UPDATE`、`FOR SHARE`、`UPDATE`、`DELETE` 是当前读。它们读最新已提交版本并加锁。可重复读下，当前读对索引记录加临键锁：记录锁加这条索引记录前面的间隙锁。间隙锁挡住别人往这个范围里插行，当前读因此看不到幻影，也改不到别人刚插入的行。快照读靠 Read View 本来就看不到事务开始之后提交的新行。

锁加在索引上。没有合适的索引时，当前读会锁住扫过的大量记录，甚至接近锁整张表。条件更新一定要有能定位到行的索引。

几种锁要分开：

| 锁 | 作用 |
| --- | --- |
| 记录锁 | 锁住一条已有的索引记录 |
| 间隙锁 | 锁住两条记录之间的空隙，挡住插入。间隙锁之间不互斥，和插入意向锁互斥 |
| 临键锁 | 记录锁加它前面的间隙，左开右闭。可重复读下范围当前读的默认锁 |
| 插入意向锁 | `INSERT` 在真正插入前加的间隙锁，用来和已有的间隙锁冲突并等待 |
| 意向锁 | 表级的 IS / IX。事务在加行锁之前先加意向锁，表锁才能知道表上已经有行锁 |

唯一索引上等值当前读，记录存在时退化为记录锁，不再锁前面的间隙。记录不存在时加间隙锁，挡住别人把这个键插进来。非唯一索引的等值仍会锁住这一串等值记录和它们两侧的间隙。

读已提交不加间隙锁。`UPDATE` 和 `DELETE` 还会做半一致读：先看最新提交版本是否符合 `WHERE`，不符合就不锁这行。锁范围小，高并发更新更不容易死锁。代价是同一事务里两次快照读可能看到不同的值。互联网业务里很多写多的库用读已提交，库存和余额用单条条件更新保证正确，需要稳定范围的语句再显式 `FOR UPDATE`。可重复读适合不能接受幻读、又会做范围当前读的事务，例如批量按条件改状态。隔离级别是连接上的选择，在事务开始前设好：

```python
engine = create_async_engine(url, isolation_level="READ COMMITTED")
```

单个连接可以用 `execution_options(isolation_level="REPEATABLE READ")`。`AUTOCOMMIT` 在 SQLAlchemy 里也是一种 isolation 选项，语句自己提交。

死锁是两笔事务按相反顺序锁住对方已经持有的行，InnoDB 检测到环之后回滚代价较小的那一笔。锁等待超时是 `innodb_lock_wait_timeout`（默认 50 秒）到了还没拿到锁，和死锁不是一条路径。驱动抛出 `OperationalError`，MySQL 错误码 1213 是死锁，1205 是锁等待超时。应用把整笔事务重试，设次数上限和抖动。锁的顺序按主键固定，能减少死锁。事务里只留必须原子的 SQL。HTTP 和 Redis 放在事务外面。行锁会一直占到提交，外部调用一慢，就挡住别人。

扣库存用一条带条件的更新，用 `rowcount` 判断有没有更新到：

```python
async with session.begin():
    result = await session.execute(
        text("UPDATE inventory SET stock = stock - 1 WHERE id = :id AND stock > 0"),
        {"id": sku_id},
    )
```

`rowcount == 0` 就是没扣成。这一条语句本身是原子的，不依赖先 `SELECT` 再在应用里减。乐观锁是另一种做法：读出 `version`，更新时带 `WHERE version = ?`，同时把版本加一，`rowcount == 0` 就重读重试。适合冲突少的行。冲突很高的热点行，重试会打满数据库，热点要移到前面的 Redis 或队列里。

### 复制与高可用

主库把 binlog 发给从库，从库有 IO 线程接收、SQL 线程重放。异步复制是主库写完自己的日志就返回，从库还没收到。主库在这一瞬间宕机，已提交的事务可能不在从库上。

半同步要求至少一个从库确认收到日志，主库才给客户端返回。等待点是 `rpl_semi_sync_source_wait_point`，8.0 里的名字是 `rpl_semi_sync_master_wait_point`。默认 `AFTER_SYNC`：binlog 已经 fsync，从库确认写进 relay log 之后，主库才在存储引擎里提交并响应客户端。客户端拿到成功时，这笔事务已经在从库上，切换不会丢。`AFTER_COMMIT` 先在主库引擎提交再等从库，提交之后、确认之前，别的会话已经能读到这行，从库可能还没有。`rpl_semi_sync_source_timeout` 默认 10 秒，超时后退回异步。生产保持 `AFTER_SYNC`。故障转移之后按新主重建旧主，不把旧主原样拉起来继续写。

GTID 用 `source_id:transaction_id` 标识每一笔已提交事务。从库按 GTID 集合续传，换主时不用手工对文件名和位点。复制过滤和多源复制会让 GTID 集合变复杂，过滤要在设计时固定下来。

从库可以承担读。写之后立刻读自己的写入，要打主库，或者在从库上 `WAIT_FOR_EXECUTED_GTID_SET` 等到这笔 GTID 重放完再读。从库延迟时，所有读都打过去会读到旧数据。延迟的常见来源是从库单线程重放、大事务、从库机器更弱、锁等待。并行复制按库或按 writeset 并行，能把延迟降下来。大事务拆开，提交更频繁，复制和锁的颗粒度都更小。

组复制（MGR）用 Paxos 在多数节点上提交事务，单主模式下写仍进主节点，多数派确认后才提交。它解决的是复制本身的高可用。代理或编排负责把写流量切到新的主。切换期间会有一小段不可写，客户端要重试幂等的语句，非幂等的语句先按唯一键查有没有写成。

只读实例把 `read_only` 和 `super_read_only` 打开，避免应用用高权限账号误写从库。备份用 `xtrabackup` 这类物理备份加 binlog 位点或 GTID，逻辑备份 `mysqldump` 适合小库和单表。恢复演练按固定周期做，没演练过的备份不算备份。

### SQLAlchemy 与连接

一个请求一个 `AsyncSession`，请求结束就关。会话放进全局或缓存，会把连接和对象身份串到下一次请求。

```python
async with session.begin():
    await session.execute(...)
```

`Session` 有身份映射，同一个事务里同一主键只有一份对象。提交后默认过期，下次访问会再查。异步代码里访问过期属性会触发隐式 IO，这在异步会话里会直接报错。查询侧用 `expire_on_commit=False`，要新数据就显式再查。

连接池是进程级的。四个 worker 就是四份池。`pool_size` 是常驻连接，`max_overflow` 是突发时多出来的连接。总数是副本数 × worker 数 × (`pool_size` + `max_overflow`)，要小于 `max_connections` 的八成左右，给管理连接、从库复制和在线变更留位置。每个连接在服务器上是一个线程，内存按连接数预留。`pool_recycle` 小于数据库、代理或负载均衡的空闲断开时间。`pool_pre_ping` 在取出连接时先探活，多一次往返，只在空闲连接经常被中间设备掐掉时开。`wait_timeout` 太短时，池里的连接会在服务器侧先被关掉，下一次使用才发现断开。

列表接口避免 N+1。主查询之后按关联键一次 `IN` 查回来，SQLAlchemy 里用 `selectinload`。`joinedload` 用外连接，一对多时主表行会被乘开。循环里对每行 `await session.get` 会把一次列表变成几百次查询。

迁移用 Alembic，放在滚动更新之前的一次性 Job 里跑。多个副本同时 `upgrade` 会抢同一张表的元数据锁。8.0 里不少加列、删列可以用 `ALGORITHM=INSTANT`，做不到就让语句失败，而不是悄悄改成拷表。改列类型、加二级索引仍可能重建或长时间占用。大表的阻塞变更用影子表工具（gh-ost、pt-online-schema-change）在线做，做完再切换。变更期间的 binlog 量会上升，从库延迟要一起看。

### 分库分表

先确认单机的索引、SQL、连接数、缓冲池和磁盘已经用尽，再拆。垂直拆按业务分库，订单和用户各自的库，连接和故障域分开。水平拆按用户 id 或订单 id 取模或按范围。

两条接入方式：

- 代理（ShardingProxy、Vitess、ProxySQL）对外说 MySQL 协议。应用拿普通连接串连代理，分片规则在代理上。跨分片事务和跨分片查询受代理能力限制。
- 应用内分片：SQLAlchemy 的 `ShardedSession` 按键选择引擎。异步会话通过 `sync_session_class=ShardedSession` 接进去。分片键必须出现在查询里，否则要扇出到所有库。

分片键选查询一定会带上的列。按用户 id 拆之后，按订单 id 查就要有一张订单 id 到用户 id 的映射，或者订单 id 里就编进用户 id。范围查询和时间排序会扇出到所有分片，这种查询改走搜索引擎或汇总库。扩容用成倍的分片数，例如 8 扩到 16，数据只需要搬一半。迁移期间双写或按 id 段搬，对完数再切路由。跨分片的写入用消息做最终一致，不跨库做两阶段提交。

全局唯一约束在单表里由唯一索引保证。分片之后，唯一键必须包含分片键，否则要单独建一张以这个键为分片键的索引表。

## 2. Redis 与缓存

Redis 在这条体系里做四件事：缓存、计数、分布式锁、原子脚本。异步服务用 `redis.asyncio`，同步客户端会占住调用线程。应用关闭时 `aclose`。Redis 7 起，小哈希、小有序集合和列表 quicklist 的节点用 listpack。Stream 可以做进程内或单机的轻量日志，保留和堆积受内存限制，跨服务的事件总线仍用后面的消息队列。

### 命令执行

一条命令的执行在主线程上排队。快是因为数据在内存里，数据结构把操作控制在可预期的复杂度，加上 epoll 把「连接可读」变成事件。慢命令会堵住后面所有命令：`KEYS`、对大 key 的 `SMEMBERS` 或 `HGETALL`、对大集合的 `SUNION`、复杂度随元素数上升的聚合。`io-threads` 默认是 1，也就是只有主线程。把它设成大于 1 之后，多出来的线程默认只写响应，`io-threads-do-reads yes` 才让它们也读。`io-threads 4` 表示 1 个主线程加 3 个 IO 线程。命令本身仍在主线程执行。`UNLINK` 和过期删除可以丢给后台线程释放内存，避免主线程一次回收一个大对象。

key 在服务器里是 SDS，可以存二进制，长度单独存放，不因为里面有 `\0` 就截断。`decode_responses=True` 时响应是 `str`，适合 JSON 和数字。存压缩包或原始字节时设为 `False`。值用 JSON 或纯数字，键名带业务和版本：`order:stock:v1:{sku}`。过期时间在写入时一起设上，`SET key value EX 秒`。先 `SET` 再 `EXPIRE` 的话，两条命令之间进程挂了，键就没有过期时间。

### 结构

按过期粒度和内存选类型：

| 类型 | 用法 | 编码 |
| --- | --- | --- |
| 字符串 | 计数用 `INCR`，对象用 JSON。每个 key 都能单独过期 | int、embstr、raw |
| 哈希 | 一个对象的多个字段。7.4 起 `HEXPIRE` 可以让单个字段过期，更早只能设在整个 key 上 | 字段少用 listpack，多了转哈希表 |
| 列表 | 队列、时间线 | quicklist，节点是 listpack |
| 集合 | 去重 | 全是整数且数量不大时用 intset，否则哈希表 |
| 有序集合 | 排行榜、延迟任务 | 成员到分数用哈希表，按分数有序用跳表。量很小用 listpack |
| Stream | 带 id 的追加日志，消费组、待确认列表 | listpack 组成的 radix tree |
| 地理位置 | `GEOADD` / `GEOSEARCH` | 分数是 geohash，底层是有序集合 |

每个数据库是一张哈希表。存一个 key，先算哈希，再对桶的个数取模，落到一个桶。两个 key 进同一个桶，用链表串起来。设了过期时间的 key 再在另一张过期表里登记，过期扫描只看这张表。桶上的链太长就扩容。一次性把全部 key 搬到新表，主线程会停住。渐进式 rehash 让新旧两张表同时存在：查找先查旧表，没有再查新表；新写入只进新表；每次增删改查顺手搬一个桶；空闲时定时任务再搬一点。旧表空了，两张表交换，扩容结束。客户端无感知。

哈希表里的值包着一个 redisObject。`type` 是对外的类型，`encoding` 是当前真正用的结构。数据少用紧凑结构省内存，数据多了换成能保住复杂度的结构。`OBJECT ENCODING` 能看到现在用的是哪一种。

字符串有三种编码。能放进整数的用 int，数字放在对象里，不再单独申请一块字符串。Redis 7 起，不超过 44 字节的短字符串用 embstr：redisObject 和 SDS 一次分配在连续内存里，改一次就会转成 raw。更长的一开始就是 raw，对象和字符串分两次申请。SDS 在头部记下长度，取长度不用扫描，中间有 `\0` 也不会被截断。追加时预留空间：需要的新长度不到 1MB 就按这个长度翻倍，达到 1MB 之后每次多留 1MB。一个字符串最大 512MB。Bitmap 就是按位使用的字符串：签到用一个用户一年一条，一位一天；在线状态用用户 id 当位的下标，一亿个用户大约 12MB。`BITCOUNT` 数置位的个数，`BITOP AND` 得到连续几天都出现过的用户。

哈希、小集合、小有序集合用 listpack：一块连续内存，头部记下总字节数和元素个数，每个格子记下自己的编码、数据和自己的长度，末尾一个结束标记。它的前任 ziplist 记的是前一个格子的长度。前一个格子变长，后一个用来记长度的字段也可能从 1 字节涨到 5 字节，后面的格子跟着改，这是连锁更新。listpack 只记自己，倒着走时读末尾的长度就能跳过。哈希的字段个数或单个值超过 `hash-max-listpack-entries`、`hash-max-listpack-value`（默认 128 和 64）就转成哈希表。7.4 起 `HEXPIRE` 可以给单个字段设过期，更早的过期只能挂在整个 key 上。

列表用 quicklist：双向链表的每个节点是一个 listpack。`list-max-listpack-size` 默认 -2，一个节点大约 8KB。纯链表每个元素都要前后指针，纯数组在中间插入要搬移后面的元素。quicklist 把元素分进一节节节点，两头进出只动端点上的节点。元素很少时可以只有一个 listpack。

集合里全是整数、个数不超过 `set-max-intset-entries`（默认 512）时用 intset：从小到大排好的整数数组，查找用二分。塞进一个当前编码放不下的数，整个数组从 16 位升到 32 位或 64 位，不再降回去。有非整数但元素不多，用 listpack。再多就换成哈希表，只用键，值空着。

有序集合元素少时仍是 listpack，成员和分数按分数挨着放。超过 `zset-max-listpack-entries` 或 `zset-max-listpack-value`（默认同样是 128 和 64）就换成跳表加哈希表。哈希表按成员查分数。跳表在有序链表上按概率往上加层，每往上一层的概率是 1/4，最高 32 层。查找从最高层往右，走过头就下一层。每一层记着这一跳跨过多少个节点，所以查排名也是对数复杂度。按分数取一段时，先找到起点，再沿着最底层往后走。插入和删除只改几根相邻指针。红黑树做范围扫描要中序走树，插入删除还要旋转和变色，跳表把这两件事都留在链表上。

HyperLogLog 只估不重复的个数，不存元素本身，固定大约 12KB，标准误差大约 0.81%。它能给出「有多少个不同的人」，给不出成员名单。地理位置把经纬度编成 geohash，当作分数放进有序集合。同一片网格里的点分数接近；贴着网格边界的近邻，分数不一定挨在一起，`GEOSEARCH` 会把相邻网格一起算进去。Stream 比把列表当队列多了消费组和待确认列表：消息被取走但没确认，就留在这个列表里，消费者停了可以由别人认领。它仍然受这台 Redis 的内存限制，跨服务、要落盘的事件走消息队列。布隆过滤器是一条很长的位数组加上几个哈希函数。写入时把算出的几位置成 1。查询时只要有一位还是 0，这个元素一定不存在；全是 1 只说明可能存在，这几位也可能是别的元素置上的。元素只能加，不能单独删。Redis 8 起开源发行版内置 `BF.ADD` 和 `BF.EXISTS`，更早用 RedisBloom 模块，或者用 Bitmap 自己做。redis-py 直接发这些命令。

管道把多条命令一次写出：`pipeline(transaction=False)`，`execute()` 拿列表。`transaction=True` 会包 `MULTI`/`EXEC`。管道里某一条失败，其他命令仍然执行，返回值里夹着异常。管道和事务都做不到「先读再按结果写」的原子，读到的值在写之前可能变了。这种读改写用 Lua。`WATCH` 加上 `MULTI` 是乐观锁，写之前键变了就整事务失败，由客户端重试。Lua 在主线程上原子执行，脚本里不要写循环去扫大集合，执行期间别的命令都在等。

Redis 7 的 Function 把脚本登记在服务器上，随复制持久化。客户端 `EVAL` 的脚本每次要带上正文，适合随版本发布的短逻辑。无论哪一种，脚本要短，参数从 `KEYS` 和 `ARGV` 传入。

### 连接、内存与超时

`max_connections` 按这个进程的并发算。四个 worker 就是四份池，总和要小于 Redis 的 `maxclients`。`socket_connect_timeout` 管握手，`socket_timeout` 管一条命令最多等多久。超时后这条命令的结果不确定，服务器可能已经执行了 `INCR`。扣库存靠 Lua 的返回值判断，超时就用请求 id 再查一次，而不是盲目再执行。

大键用 `MEMORY USAGE` 或 `redis-cli --bigkeys` 找。删除大键用 `UNLINK`。线上扫键用 `SCAN`，游标由服务端保持，中间有写入时不保证不重复、不遗漏，调用方自己去重。`maxmemory` 设了之后要选淘汰策略：

| 策略 | 行为 |
| --- | --- |
| `allkeys-lru` | 在所有键里淘汰最近最少使用的 |
| `allkeys-lfu` | 在所有键里淘汰使用频率最低的，计数会随时间衰减，历史热点不会永远占着 |
| `volatile-ttl` | 只在设了过期时间的键里淘汰更快过期的 |
| `volatile-lru` / `volatile-lfu` | 只淘汰设了过期的键 |
| `noeviction` | 写满后拒绝写入 |

缓存用 `allkeys-lfu` 或 `allkeys-lru`。访问分布很斜时 LFU 更合适。`volatile-*` 只在带 TTL 的键里挑，如果这些键的内存远小于 `maxmemory`，内存仍会顶满，然后写失败。`noeviction` 适合把 Redis 当数据库用、不能丢键的场景。拒绝写入时，应用要把 Redis 故障和「键不存在」区分开，否则会把一次内存满当成缓存未命中，全部打到数据库。

`--hotkeys` 依赖 LFU 的频率统计，策略是 `allkeys-lfu` 或 `volatile-lfu` 时才有意义。`MONITOR` 会把每条命令打出来，生产上会把主线程拖慢。热 key 更稳妥的是在代理或业务侧对 key 打点。

### 持久化、复制、哨兵、集群

RDB 是某一时刻的全量二进制，恢复快，生成慢。`bgsave` 用 fork 和写时复制，父进程继续服务。写得多时，拷贝被改过的页，父进程内存会涨上去。AOF 追加命令，`everysec` 大约每秒 fsync，最多丢一秒。`always` 每条命令都 fsync。重写把一串 `INCR` 收成一条 `SET`。4.0 起混合持久化在重写时写成 RDB 头，之后的新命令仍追加 AOF。Redis 7 的 AOF 可以拆成多个文件，重写和增量分开。缓存可以只开 RDB，甚至不持久化，数据能从数据库重建。锁和限购如果只活在 Redis 里，就要开 AOF，并接受最多大约一秒的丢失窗口。

主从第一次同步是全量 RDB，加上复制缓冲区里的增量。断线后用 backlog 里的 offset 续传，offset 已经被覆盖就退回全量。所有从节点同时找主做全量，会把主打满。从节点下面再挂从节点，全量的压力就分散了。Redis 的复制是异步的。

哨兵监视主节点。`sentinel monitor` 里的 quorum 是多少个哨兵同意才算主失效，一般是哨兵数的一半加一。真正执行故障转移还要有多数哨兵可达，避免网络切开时两边各选一个主。客户端用 `redis.Sentinel`，`master_for` 拿当前主，`slave_for` 拿从节点。地址写死成某一台，切换之后会一直打到已经下线的主。故障切换有几秒到十几秒不可写，调用方要重试。从节点复制有延迟。扣减、锁、限购走主节点。

Cluster 把数据分成 16384 个槽，`CRC16(key) % 16384`。`RedisCluster` 收到 `MOVED` 会更新槽表并跳到持有该槽的节点。迁移过程中键还在源节点时，目标节点返回 `ASK`，这次请求临时去源节点，槽表先不改。跨槽的多 key 命令会被拒绝，除非用哈希标签 `{sku}` 让相关 key 落在同一槽。事务、管道和 Lua 里的多个 key 也受这个限制。节点用 gossip 交换状态。集群规模控制在官方建议的范围内。某个槽的主从都不可用时，这个槽上的键不可用；`cluster-require-full-coverage` 为 yes 时，整个集群拒绝写入。

### 锁

单机上加锁是一条命令：`SET key token NX PX 毫秒`。token 是随机值。释放时只有值仍是自己的 token 才删除。`redis-py` 的 `Lock` 就是这样做的：获取用 `SET NX PX`，释放用 Lua 比较 token 再 `DEL`。token 放在 `threading.local`，避免线程 A 读到线程 B 后来写入的 token，把别人的锁删掉。

```python
with client.lock("sku:1001", timeout=10, blocking_timeout=2):
    ...
```

`timeout` 是锁的寿命，业务必须在这之前结束。`extend` 用 Lua 续期，同样要先对上 token。超时仍未释放，锁会消失，下一个人能拿到。这是为了进程崩溃后不会一直占着锁。业务耗时和锁超时重叠时，两个人可能都以为自己持有锁，所以超时要大于业务耗时，业务再检查一次资源状态。续期任务和业务要在同一把锁的 token 上，进程被杀死后续期也停了，锁会在 TTL 后释放。

主从切换时锁可能丢：写在主上，还没复制到从，主挂了，新主没有这把锁。多主投票的 Redlock 要求多个独立主节点、时钟偏差有上界、实例会在超时后放锁。网络延迟和时钟跳变会破坏这些假设。库存扣减用 Lua 直接改数字。锁只包住「从数据库装载库存进缓存」这种重建过程。真正不能丢的互斥，用数据库唯一键或行锁。

### 缓存

详情页拆成能缓存的部分和必须实时的部分。标题、图、属性、规格可以缓存。价格、库存、促销单独接口，缓存时间短，或者直接读 Redis。扣库存和支付结果以数据库事务为准。

整页静态化用 Jinja2 在发布时渲染成 HTML，放到对象存储或 Nginx 能直接读的目录。模板一改要重渲染全部商品。商品一多就改成 Nginx 缓存 HTML 片段，实时数据走接口。`proxy_cache` 按 URL 缓存匿名流量。带登录态的页面按用户片段缓存，避免把一个人的页面交给下一个人。

本地缓存挡在 Redis 前面。进程内用 `cachetools.TTLCache`，设最大条数和 TTL。`functools.lru_cache` 没有 TTL，只适合启动后不变的配置。每个 worker 有自己的一份，失效不会自动广播。本地 TTL 用秒级，Redis TTL 用分钟级。Redis 6 的客户端缓存可以在键变更时收到失效通知，本地副本因此能主动丢掉。没接这套通知时，就靠短 TTL。

三类失效：

- 击穿：热点 key 过期，大量请求同时打到数据库。用锁只放一个请求去加载，其他请求短暂等待或返回旧值。
- 穿透：查不存在的 key。固定的空值可以缓存，TTL 更短。每次都换 key 时，用布隆过滤器先挡。Redis 8 起用内置的 `BF.ADD` / `BF.EXISTS`，更早用 RedisBloom 模块。redis-py 直接发这些命令。位数组在结构那一节。过滤器说不存在就一定不存在；说存在仍可能是误判，那时再查库。元素只能加不能删，删数据要换一个新过滤器再灌一遍主键。
- 雪崩：一批 key 同时过期，或 Redis 本身不可用。TTL 加随机抖动。热点 key 用锁重建。Redis 不可用时要有限流和降级，而不是无限穿透到数据库。

强一致的数据留在数据库里。缓存这条链路做到最终一致：先写库，事务提交成功后再删 Redis。删失败就记一条待删记录，后台再删，TTL 是最后一道。直接改缓存里的对象要处理局部更新和并发写，容易和数据库岔开。

有一个固定的竞态：请求 A 读到旧值，请求 B 写库并删掉缓存，A 再把旧值写回去。处理是写路径只删不改，读路径回填时带短 TTL；写完隔一小段再删一次，间隔要盖住正在回填的读。更稳的是订阅 binlog，提交已经发生之后再删缓存，应用漏删也会被补上。

读：先看 `TTLCache`，再看 Redis，都没有再查库，然后回填。回填用按 key 的 `asyncio.Lock`，同一个 key 同时过期时只有一个协程去查库。这把锁只挡住本进程。多个进程仍靠 Redis 锁。不要用一把全局锁。

空值也缓存。布隆过滤器放在缓存之前，元素是已经存在的主键。误判率大约是 `(1 - e^{-kn/m})^k`：`m` 是位数，`k` 是哈希次数，`n` 是预计元素个数。位数按预计数据量一次算好。超过预计容量，误判率会很快变高，查询又会漏到数据库。

缓存键带上业务版本，例如 `detail:v3:{id}`。结构变了就换前缀，旧键等 TTL 自己消失。展示用的总库存、总条数可以短暂不准，放 Redis 并加随机 TTL。

## 3. 计算机网络

应用看到的是一条 HTTP 请求。它实际穿过网卡、IP 路由、TCP 连接、TLS、HTTP，再进入进程。Python 服务把 TLS 和 HTTP/2 放在 Ingress 或 Nginx，Uvicorn 对内用 HTTP/1.1。超时、连接池和幂等要按这几层分开设。

### 分层和一次请求

链路层把帧送到同一二层网络里的下一跳。IP 层按路由表选下一跳，不保证到达。TCP 在 IP 之上提供字节流：可靠、有序、有拥塞控制。UDP 只提供报文，不重传、不排序。HTTP 是请求响应的应用协议，跑在 TCP 上；HTTP/3 跑在 QUIC 上，QUIC 跑在 UDP 上。

一次跨机器调用的时间大致是这些量级：同机房内存访问约 100 纳秒，同可用区网络往返约 0.5 毫秒，跨可用区约 1 毫秒，固态盘读约 100 微秒，机械盘寻道约 10 毫秒。应用超时如果设成和同机房 RTT 一样短，正常抖动就会失败；如果设成几十秒，故障时线程和连接会被占满。

DNS 把名字解析成地址。浏览器和操作系统有缓存，权威服务器上的 TTL 决定缓存能放多久。Kubernetes 里 Pod 的 `resolv.conf` 常见 `ndots:5`：名字里的点少于 5 个时，先拼上搜索域再问绝对名字。`order` 会先变成 `order.ns.svc.cluster.local`，这是集群内服务发现要的行为。`mysql.xxx.com` 这种外部名字也会先走一遍搜索域，多几次 NXDOMAIN，延迟就加在每次新建连接上。集群内服务用服务名，集群外地址用完整域名，或者把这个 Pod 的 `ndots` 降下来。

CPython 的 `loop.getaddrinfo` 把解析放在默认线程池里执行。解析卡住时占的是线程池，事件循环还能跑别的协程，但池子被占满之后，`asyncio.to_thread` 和同步路由都要排队。连接池把「解析加握手」摊到很多请求上，长连接一直复用，解析次数就下来了。

### TCP

三次握手：客户端发 SYN，服务端回 SYN+ACK 并进入 SYN_RCVD，客户端再发 ACK，两边进入 ESTABLISHED。服务端在握手完成前把连接放在 SYN 队列，完成之后放进 accept 队列，等 `accept` 取走。SYN 队列满了，新的握手会被丢掉或触发 SYN Cookie。accept 队列满了，已完成的连接会被丢掉，客户端看到超时。队列长度受 `somaxconn` 和监听 backlog 里较小的那个限制。`ss -lnt` 里，监听套接字的 Recv-Q 是还没被 accept 的连接数，Send-Q 是 backlog。Recv-Q 顶满就是应用取取得不够快。

四次挥手：主动关闭的一方发 FIN，对方回 ACK，之后对方发 FIN，主动方再回 ACK。主动关闭的一方进入 TIME_WAIT，等待 2MSL，用来让最后的 ACK 有机会重传，并让老的报文从网络里消失。TIME_WAIT 在主动关闭的那一端。HTTP 保活超时由服务端发起关闭时，TIME_WAIT 堆在服务端。由客户端关闭时，堆在客户端。它占的是四元组，数量很大时要看是不是在频繁建连又立刻断开。`tcp_tw_recycle` 已经从内核里去掉，它在 NAT 后面会把合法的新连接丢掉。`tcp_tw_reuse` 只影响本机作为客户端向外发起的连接。

保活用来发现对方已经消失、但本机还以为连接在的情况。中间设备也会按空闲时间掐连接。应用的空闲超时、负载均衡的空闲超时、数据库的 `wait_timeout`、内核的 keepalive 要放在同一套数上：越靠近调用方，空闲断开越晚，池里的连接才不会被对端先关掉。

Nagle 把小包攒一攒再发，延迟 ACK 让接收方等一等再确认。两个同时开着，小请求会多等一个延迟 ACK 的定时器。内网 RPC 关 Nagle（`TCP_NODELAY`），HTTP 客户端一般已经关了。

拥塞控制避免把网络打满。慢启动把窗口按指数放大，超过阈值后进入拥塞避免。丢包时 CUBIC 把窗口降下来再爬。BBR 按估算的带宽和 RTT 发，对有缓冲的链路更不容易把缓冲区填满。丢包重传和拥塞窗口下降都会变成应用看到的长尾。同一可用区里的超时要能盖住偶发重传，跨地域调用要把超时和重试次数一起降下来。

半开连接是一端已经重启，另一端还拿着旧连接去写。写才会发现 RST，只读的连接要靠超时或 keepalive。所以读超时是必须的，不能只设连接超时。

### HTTP

HTTP/1.1 在一条 TCP 上串行请求和响应，靠 `Connection: keep-alive` 复用连接。管道化把多个请求一起写出，但服务器必须按顺序响应，中间一个慢响应会挡住后面的，实践里很少开。队头阻塞发生在这一层，也发生在 TCP 丢包时：一个包丢失，这条连接上后面的字节都要等重传。

HTTP/2 在一条 TCP 上多路复用多个流，头部用 HPACK 压缩。TCP 丢包时，这条连接上所有流仍然一起停。HTTP/3 把流放到 QUIC 上，一个流丢包只挡住这个流。QUIC 的 0-RTT 能在恢复连接时提前发数据，这段数据可以被重放，非幂等的 POST 不能放进 0-RTT。

方法按幂等来记。GET、HEAD、PUT、DELETE 在协议语义上是幂等的，相同请求执行多次和执行一次的效果相同。POST 不是。实际接口里 PUT 和 DELETE 仍然可能有副作用，能不能重试看服务有没有按幂等实现。状态码按谁的责任分：

| 状态码 | 含义 |
| --- | --- |
| 200 / 201 / 202 / 204 | 成功、已创建、已接受但还没做完、成功且没有正文 |
| 400 / 422 | 请求不合法。FastAPI 的校验失败是 422 |
| 401 / 403 | 没有身份、有身份但没有权限 |
| 404 | 资源不存在 |
| 409 | 和当前状态冲突，例如唯一键、幂等键对应了另一份请求体 |
| 429 | 被限流 |
| 500 | 服务自己没处理好 |
| 502 / 503 / 504 | 网关连不上上游、上游不可用、网关等上游超时 |

超时从外往里缩短。客户端 3 秒，网关 2.5 秒，服务调下游 2 秒。外层更长，内层的错误才能返回。网关先断开时，服务可能还在写数据库，调用方重试就会重复下单。所以写请求带幂等键，超时之后先查结果。

`httpx.AsyncClient` 按进程创建一份，关闭时 `aclose`。每次请求新建客户端会反复握手，连接池也攒不起来。超时拆开：连接超时短，读超时按这个接口的正常耗时加余量，池等待超时避免在取连接时无限等。

```python
timeout = httpx.Timeout(connect=0.2, read=2.0, write=2.0, pool=0.2)
limits = httpx.Limits(max_connections=100, max_keepalive_connections=20)
client = httpx.AsyncClient(timeout=timeout, limits=limits)
```

重试只针对幂等的 GET，以及带了幂等键的 POST。没有幂等键的下单，超时后先查结果，再决定要不要重发。重试要有次数上限和抖动，否则一个慢下游会让所有调用方同步放大流量。

入口在 TLS 终止后把 `X-Forwarded-For` 和 `X-Forwarded-Proto` 传进来。这两个头只信任直接相连的代理写进来的值。应用看到的对端地址是网关的地址，真实客户端地址在代理追加的头里。应用如果直接听公网，就不能用客户端自己带的转发头做访问控制。

### TLS

TLS 1.3 握手是 1-RTT：客户端发支持的参数和密钥份额，服务端回证书和自己的密钥份额，两边算出会话密钥，应用数据可以接着发。1.2 通常要 2-RTT。恢复会话时 1.3 可以 0-RTT，重放风险和 HTTP/3 的 0-RTT 一样。证书在入口上，进程里不再做握手。轮换证书是入口的配置，不用重新发布应用镜像。

### 负载均衡

四层负载均衡按 IP 和端口转发，不看 HTTP。云上的网络型负载均衡、Kubernetes 的 Service 和 kube-proxy 都是这一层。一条连接被转到某个后端之后就留在那里，直到连接结束。

七层负载均衡看 Host、路径和头。Ingress、Nginx、API 网关是这一层。它可以按请求做路由、限流和 TLS。HTTP 长连接上的多个请求可以到不同后端，前提是代理在请求边界上转发。WebSocket 和 gRPC 流是一条长连接，会被钉在选中的那个后端上。

均衡算法：轮询适合实例能力相近的无状态服务。最少连接适合请求耗时差很多的场景。一致性哈希把节点和键映到同一个环上，键顺时针遇到的第一台负责它。一台离开，只有它和前一台之间那段弧上的键改道。每台物理节点在环上放很多虚拟节点，弧被切碎，数据不会整段堆到下一台。分库和缓存用同一套环，算法放在系统设计里。权重用来把新版本慢慢放进来。

健康检查失败才摘除。检查要打应用的就绪接口，只探 TCP 端口会把还没加载完的进程放进轮询。检查间隔、失败阈值和成功阈值决定摘除有多快、恢复有多稳。阈值太低，一次抖动就把实例摘掉，流量堆到剩下的实例上。

### gRPC

gRPC 跑在 HTTP/2 上。接口和字段写在 protobuf 里，生成 Python 的请求类和 stub。一条 RPC 是 HTTP/2 上的一个流，消息按长度前缀放进 DATA 帧。和 JSON 相比，字段号是合同的一部分：加字段用新的号，旧客户端忽略不认识的号；已经发出去的号不改含义、不复用。

四种调用。一元是一个请求一个响应，对应普通的内部接口。服务端流是一个请求之后持续回多条，用来推进度。客户端流是连续上传再收一个汇总。双向流是两边随时写，用来做需要同一条连接上对讲的内部通道。对外的 HTTP API 仍用 JSON。内部、字段稳定、或者要流式的调用用 gRPC。

Python 用 `grpcio`。通道按进程建一条，stub 从通道生成。同步 stub 在自己的线程里等，放进 `async def` 会堵住事件循环。异步服务用 `grpc.aio`。

```python
channel = grpc.aio.insecure_channel("order.prod.svc:50051")
stub = OrderStub(channel)
response = await stub.CreateOrder(request, timeout=1.0)
```

`timeout` 是从现在起的截止时间，写进 `grpc-timeout`，沿调用链往下传。每一跳用剩余时间，不再用自己原来的一整段。剩余时间不够就返回 `DEADLINE_EXCEEDED`，不再往下调用。调用方没设截止时间时，服务端给一个自己的上限。

状态码和 HTTP 的不是同一套。`OK` 成功。`CANCELLED` 是调用方取消。`DEADLINE_EXCEEDED` 是截止时间到了。`NOT_FOUND`、`ALREADY_EXISTS`、`FAILED_PRECONDITION` 是业务前置条件。`RESOURCE_EXHAUSTED` 是配额或限流。`UNAVAILABLE` 是连接不上或服务端暂时不能接，可以对幂等的方法重试。`INTERNAL` 是服务端没处理好。非幂等的方法不因为 `UNAVAILABLE` 就自动重试。

元数据用来传认证和 `traceparent`，不把它们塞进业务消息。默认单条消息大约 4MB，大文件走对象存储，RPC 里只传地址。

负载均衡要按 RPC 而不是按连接。一条 HTTP/2 连接上可以跑很多 RPC。四层负载均衡选定后端之后，这条连接上的全部 RPC 都进同一个 Pod。副本扩了也用不上。两种接法：无头 Service 把 Pod 地址交给客户端，客户端用 `round_robin`；或者用能识别 HTTP/2 流的代理，按 RPC 转发。默认的 `pick_first` 只会盯住解析结果里的第一台。

空闲连接会被中间设备掐掉。心跳要比这条空闲时间更勤，同时不要短于服务端允许的最小 ping 间隔，过勤会被 `GOAWAY`。通道在进程退出时关闭。

### WebSocket 与 SSE

这两条都是服务器持续往浏览器推数据。差别在方向和连接怎么活。

WebSocket 从一条 HTTP 请求升级，成功是 101，之后双方都可以发帧：文本、二进制、ping、pong、关闭。它适合聊天、协同编辑这种两边都要主动写的场景。帧上没有 HTTP 头，认证放在升级请求的 Cookie 或 `Authorization` 里。令牌放在查询串里会进访问日志。

```python
@router.websocket("/ws")
async def ws(socket: WebSocket):
    await socket.accept()
    try:
        while True:
            data = await socket.receive_text()
            await socket.send_text(data)
    except WebSocketDisconnect:
        return
```

SSE 仍是一条 HTTP 响应，`Content-Type` 是 `text/event-stream`。服务器往下写事件，浏览器或调用方不能在这条响应上反向写业务数据。客户端要发命令就另开 POST。它适合通知、任务进度、模型逐字输出。

一条事件以空行结束。`id` 是续传位置，`event` 是类型，`data` 是正文，多行 `data` 会拼起来。

```python
async def events(last_id: str | None):
    cursor = last_id
    while True:
        item = await next_item(cursor)
        cursor = item.id
        yield f"id: {item.id}\ndata: {item.body}\n\n"

@router.get("/events")
async def stream(request: Request):
    return StreamingResponse(
        events(request.headers.get("last-event-id")),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

浏览器的 `EventSource` 只会发 GET，会带 Cookie，不会带 `Authorization`。断线后它自动重连，并带上最后一次的 `Last-Event-ID`。自己用 `fetch` 读流时，这些要自己做。Nginx 默认会缓冲响应，`X-Accel-Buffering: no` 加上代理侧关掉缓冲，事件才能立刻到客户端。

一条 SSE 在 HTTP/1.1 上占住浏览器到这个域名的一个连接名额，大约六个里的一个。HTTP/2 上它只是一个流。WebSocket 升级之后不再受这个名额限制，但代理和网关要允许升级。

多副本时，连接落在哪一台，消息就要能送到那一台。每台进程把自己接住的连接放在内存里。要广播时，先发到 Redis，各进程再写自己的套接字。Pub/Sub 不留消息，断线期间的内容要靠 Redis Stream 或数据库按 id 补。重连带上最后的 id，服务器从那之后接着发。

心跳间隔短于负载均衡和网关的空闲断开时间。只靠 TCP keepalive，应用层的代理仍可能按 HTTP 空闲把连接拆掉。WebSocket 用 ping，SSE 用注释行（以冒号开头）或一条心跳事件。

四层和七层负载均衡都会把这条长连接钉在第一次选中的后端上。发布时这个后端被摘掉，连接断开，客户端重连到新后端。滚动更新因此会看到一波重连，而不是每个请求平稳地切过去。

## 4. 操作系统（Linux）

Python 进程跑在这套机制上：虚拟内存、页缓存、调度、epoll、信号、cgroup。容器是同一套机制划出来的视图，不是另一台虚拟机。

### 进程、线程与协程

进程有独立的地址空间、文件描述符表和 PID。线程共享地址空间，各自有栈和寄存器。协程是用户态的切换，操作系统看不到它，一次只在一个线程上往下执行。创建成本从高到低是进程、线程、协程。隔离性反过来。

CPython 默认有 GIL：同一时刻只有一个线程在执行 Python 字节码。线程在等网络、磁盘、Redis 时会放开 GIL，所以 IO 密集用线程或协程都有效。纯计算（压缩、加密、大循环）拿不到第二个核，要开进程。

3.13 起有 free-threaded 构建（`python3.13t`，编译选项 `--disable-gil`）。`sys._is_gil_enabled()` 看当前是否真的关掉了 GIL。没标成支持 free-threading 的 C 扩展一导入，GIL 会被重新打开。默认发布版仍然开着 GIL。上线按「默认有 GIL」设计，free-threaded 只作为可选加速，多进程仍然是 CPU 并行的办法。

三层并发，各管一件事：

- `asyncio` 在一个线程里切换协程。适合大量同时在等的连接：HTTP、Redis、数据库。一个事件循环卡住（同步的 `requests`、`time.sleep`、没释放的锁）会拖住这个循环上的所有请求。阻塞函数用 `asyncio.to_thread` 丢出去。
- `threading` 适合少量阻塞库，或者和协程混用。`threading.Lock` 保护复合操作。`RLock` 允许同一线程重复获取。标准库没有读写锁；free-threaded 下读多写少再用 `readerwriterlock` 这类包才有意义。GIL 还在时，一把普通锁通常够用。
- `multiprocessing` 或 `concurrent.futures.ProcessPoolExecutor` 做 CPU 密集。每个进程一份解释器和内存，传参走 pickle，大对象和连接池不能直接塞进子进程。进程数按核数的 1 到 2 倍，再多只是上下文切换。

可见性的实际规则：GIL 让单个字节码看起来原子，`i += 1` 这种复合操作仍然会丢更新。共享状态放进 `queue.Queue`，或者用锁包住一小段。

进程内同步：

| 要做的事 | 用法 |
| --- | --- |
| 互斥 | `threading.Lock`。协程之间用 `asyncio.Lock`，它只挡住同一个事件循环上的其他协程，线程仍然可以跑别的任务 |
| 限流，同时 n 个 | `threading.Semaphore(n)` 或 `asyncio.Semaphore(n)` |
| 等一组任务都完成 | `asyncio.gather`，或 `asyncio.Event` 加计数。3.11 起优先用 `TaskGroup` |
| 一组任务到齐再一起走，并且能重复用 | `threading.Barrier` |
| 有界队列，满了堵住 | `queue.Queue(maxsize=n)`，`n` 是正整数。协程用 `asyncio.Queue(maxsize=n)` |
| 不限制长度 | `maxsize=0`。这是不设上限，队列会一直堆积 |
| 带返回值的后台任务 | `concurrent.futures.Future`，或 `asyncio.create_task` |
| 停机 | 线程用 `threading.Event`，阻塞点用带超时的 `wait`，或往队列里放哨兵。协程取消 `Task`，在 `finally` 里清理 |

线程没有安全打断点。别的线程只能 `event.set()`，干活的线程在循环和每次阻塞返回后看这个标志，自己走完清理再退出。只设标志不够，因为线程可能正堵在 `queue.get()` 上，所以 get 要带超时，或者往队列里丢一个哨兵值。

请求进程不做大计算。计算丢给 `ProcessPoolExecutor`，或者丢进队列让独立 worker 做。请求进程只负责收下任务、返回「处理中」。

`fork` 用写时复制共享父进程的页，子进程一写才复制那一页。Linux 上进程启动方式默认仍可能是 `fork`。应用已经开了线程（Uvicorn、gRPC、客户端后台线程）之后再 fork，子进程只剩发起 fork 的那条线程，锁可能永远停在被占住的状态，子进程卡死。池子用 `multiprocessing.get_context("spawn")` 创建。spawn 会重新导入模块，启动更慢，没有继承来的锁。

生产上一个容器里跑一个服务进程，水平扩展交给副本数。一个 Pod 里要开多个 worker 时，用 Uvicorn 自带的 `--workers`（子进程是 spawn，Windows 也能用），或者 Gunicorn 预派生加上 `uvicorn-worker` 包里的 worker 类。`uvicorn.workers` 模块已标记为后续会删。每个 worker 是完整的一份应用：导入、连接池、本地缓存各有一份。副本数乘以 worker 数才是总进程数，内存按这个乘。CPU 密集的服务把 worker 数压到接近核数。纯异步 IO 常见做法是一个 Pod 一个 worker，靠副本数扩。

Gunicorn 的 master 是 arbiter，worker 挂了由它拉起。Uvicorn 多进程下，`SIGHUP` 逐个重启 worker 以便加载新代码，`SIGTTIN` / `SIGTTOU` 加减 worker 数量（Windows 上没有这组信号）。收到 `SIGTERM` 要停接收新请求、等在途请求结束再退出。`terminationGracePeriodSeconds` 要大于这段等待。

glibc 会按线程数开多个 malloc arena。多线程 worker 的虚拟内存和 RSS 会因此上去。容器里把 `MALLOC_ARENA_MAX` 设成 2，可以压住这份开销。Python 的分配器也不会把每块闲内存立刻还给操作系统，RSS 上去之后往往不下来。按内存做自动扩容时，阈值要按稳定后的 RSS 设，否则副本只会加不会减。

调度上，进程状态里 R 是可运行，S 是可中断睡眠（等网络、等锁），D 是不可中断睡眠（通常在等磁盘），Z 是僵尸。僵尸是子进程已经退出、父进程还没 `wait`，只剩进程表里的一条记录。Gunicorn 的 master 要回收 worker，避免僵尸堆积。load average 是可运行和不可中断睡眠的进程数的滑动平均，不等于 CPU 使用率。IO 堵住时 load 很高，CPU 可以很低。

### 事件循环

协程函数调用后只得到协程对象，要到 `await`、`asyncio.run` 或 `create_task` 才排进循环。`create_task` 把协程包成 `Task`（`Task` 是 `Future` 的一种），循环下一轮才开始执行，执行到第一个 `await` 把控制权交回去。同一时刻这个线程上只有一个协程在往下走，其余都停在某个 `await` 上。

循环背后是操作系统的多路复用（Linux 上是 epoll）。socket 还没可读就登记进去，线程去做别的就绪协程。所以等 Redis、等 MySQL、等 HTTP 能叠很多。`time.sleep`、`requests.get`、同步的 `redis.Redis`、大段纯 Python 计算不会登记，循环就停在那里。

`TaskGroup` 把一组任务收成一个作用域：其中一个抛错，其余被取消，退出 `async with` 时全部结束。`gather` 要自己传 `return_exceptions` 才不会漏掉失败任务。超时用 `asyncio.wait_for` 或 `asyncio.timeout`，超时之后任务会被取消。

`CancelledError` 继承 `BaseException`，`except Exception` 接不住。清理写在 `finally`，或者捕获之后再重新抛出。吞掉取消会让关闭过程停不下来。`asyncio.shield` 只保护内层任务不被外层取消带走，内层自己该停还是要停。

`contextvars` 会拷进新的 `Task`。请求 id、当前用户放这里。线程池里的函数拿不到这份上下文，除非用 `contextvars.copy_context().run`。

`asyncio.to_thread` 使用循环上的默认线程池，给偶尔的阻塞调用。压缩、加密、批量算特征进 `ProcessPoolExecutor`。

跨线程碰循环上的对象，用 `loop.call_soon_threadsafe`。`asyncio.Queue` 不是线程安全的。线程和协程之间用 `janus`，或者 `loop.call_soon_threadsafe(queue.put_nowait, item)`。

停机顺序固定为四步：先拒绝新请求，再等待已经进来的请求（带超时），然后关闭 Redis、数据库、搜索客户端，最后取消还挂着的任务。关连接放在取消之前，避免任务在 `finally` 里还去用一个已经关掉的客户端。

### 内存

每个进程有自己的虚拟地址空间。页表把虚拟页映射到物理页。缺页时内核分配物理页或从磁盘把文件页读进来。匿名页是堆和栈，文件页是映射进来的文件。`free` 里的 available 才是还能给应用用的内存，buff/cache 里的页缓存可以回收。看到 used 很高、available 也很高，是页缓存在干活。

页缓存是文件读写的中间层。`write` 返回只说明进了页缓存，`fsync` 才把脏页交给磁盘。数据库的提交要 fsync 日志。应用自己写文件，写完不 fsync 就报告成功，掉电会丢。容器的可写层更不适合放要保留的数据，文件放在卷上。

脏页由 `dirty_ratio`、`dirty_background_ratio` 和相关字节阈值控制。写得太猛时，进程会在 `balance_dirty_pages` 里停住，延迟突然变高。这和缓冲池刷脏页是同一类现象，一层在内核，一层在 InnoDB。

内存不够时触发 OOM Killer。它按 oom_score 挑进程，分值高的先被杀。容器里由 cgroup 的 memory.max 触发，杀的是这个 cgroup 里的进程，`dmesg` 或事件里能看到 `OOMKilled`。Kubernetes 的 memory limit 就是这个上限。Python 进程被杀掉之前往往没有 Python 异常，退出码是 137。

交换分区会把匿名页换出内存。数据库和 Redis 的机器关掉交换，避免一次换页把延迟打到毫秒以上。内核参数 `vm.swappiness` 调低只是减少换出倾向，要彻底没有交换就 `swapoff` 并确认 `free` 里 swap 为 0。容器节点同样关掉交换，否则内存限制和驱逐的判断会被交换搅乱。

### 磁盘和 IO 模型

一次 IO 有五种历史模型。阻塞 IO：进程停在 read 上直到数据到。非阻塞 IO：没有数据就立刻返回，由应用自己轮询。IO 复用：用 select、poll 或 epoll 先等「哪些 fd 就绪」，再去读。信号驱动：就绪时发信号。异步 IO：内核完成后通知应用，Linux 上现在用的是 io_uring。

epoll 在 fd 很多时用事件回调，不用像 select 那样每次拷贝整张 fd 集合。水平触发是只要缓冲区里还有数据，下次 epoll_wait 仍会返回。边沿触发是状态从无到有时通知一次，应用必须一直读到 `EAGAIN`，否则剩下的数据没有下一次通知。asyncio 使用的是能把「可读」持续交付的方式，应用代码只在 `await` 上等待，不用自己写边沿触发的循环。

磁盘上的文件描述符也可以放进 epoll，但默认的磁盘 read 在数据进页缓存之前，进程仍可能进入不可中断睡眠。真正不挡住线程的磁盘 IO 用 io_uring，或者把读写丢进线程池。请求路径上的大文件下载交给 Nginx 的 `sendfile`，由内核在页缓存和套接字之间拷贝，应用进程不碰文件内容。

inode 是文件的元数据，目录项把名字指到 inode。硬链接是另一个名字指向同一个 inode，只能在同一个文件系统里。软链接是一个单独的文件，里面存目标路径，可以跨文件系统，目标消失后就悬空。删除打开着的文件只是拿掉目录项，进程还握着 fd 时空间不会释放。日志切割之后，进程如果继续写已经删除的 fd，磁盘还在涨，`ls` 却看不到文件。切日志要让进程重新打开文件，或者直接把日志打到 stdout，由容器运行时收集。

文件描述符上限在 `/proc/<pid>/limits` 里。每个连接、每个打开的文件各占一个。`Too many open files` 先看是连接泄漏还是上限太低。容器里还要看 cgroup 的 pids 和节点的 fs.file-max。

### 信号和停机

`SIGTERM` 是请进程退出，处理函数里可以做清理。`SIGKILL` 不能捕获，内核直接回收。`SIGSTOP` 也不能捕获。容器停止先发 `SIGTERM`，宽限时间到了再 `SIGKILL`。PID 1 负责收这个信号。shell 形式的启动命令会让 shell 成为 PID 1，信号打在 shell 上，Uvicorn 收不到，最后被强杀，在途请求被掐断。

信号处理函数里只能调用异步信号安全的函数。Python 的信号在主线程下一次字节码边界上执行。循环被一个不释放 GIL 的 C 扩展占住时，信号处理会推迟。停机逻辑放在信号里只做一件事：设一个标志，或者往事件循环丢一个回调。清理放在正常的协程路径上。

### 看一台机器

| 现象 | 看什么 |
| --- | --- |
| CPU 打满还是在等 | `vmstat 1` 的 us、sy、id、wa、st。st 是被宿主机抢走的时间 |
| 哪个进程在用 | `pidstat -u -r 1`，`top` 里按 CPU 或内存排 |
| 磁盘是否饱和 | `iostat -x 1` 的 await 和 `%util` |
| 连接堆在哪 | `ss -s`，`ss -tan` 按状态数。TIME-WAIT、ESTAB、SYN-SENT 分开看 |
| 是不是被 OOM | `dmesg` 里的 Out of memory，或容器的 OOMKilled |
| 文件描述符 | `/proc/<pid>/limits` 和 `/proc/<pid>/fd` |

`st` 持续大于 0，是 CPU 限额或邻居把时间抢走了。`wa` 高是在等磁盘。us 高且是 Python 进程，先看是不是把计算放进了请求进程。

### cgroup

cgroup 限制和统计一组进程的 CPU、内存、IO 和进程数。cgroup v2 是一棵统一的树。Kubernetes 的 requests 用来调度，limits 写成 cgroup 上限。CPU limit 是 `cpu.max` 里的配额，用完这个周期的配额，进程被节流，延迟变高，平均 CPU 可以看起来不高。被节流的时间在 `container_cpu_cfs_throttled_seconds_total` 里。内存 limit 是 `memory.max`，超了就 OOM。超内存是杀进程，超 CPU 是变慢。

namespace 划出进程能看见的资源：PID、挂载点、网络栈、主机名、用户、IPC。容器里的 PID 1 在宿主机上只是一个普通进程。网络 namespace 有自己的网卡、路由和端口。Service 的 ClusterIP 是集群网络里的地址，由 kube-proxy 或 eBPF 转成 Pod IP。这些机制的用法放在容器那一节。

## 5. 开发框架

框架负责把 HTTP 变成一次函数调用，并管好参数、依赖和生命周期。业务规则留在服务自己的模块里。Python 服务这里以 FastAPI 为准，Django 和 Flask 只说明它们适合的边界。

### WSGI 和 ASGI

WSGI 是同步的调用约定：服务器调用一个函数，传入环境字典和开始响应的回调，函数返回响应体。一个请求占住一个线程，直到函数返回。Flask 和 Django 的传统视图是这条路径。并发靠进程数或线程数。

ASGI 是异步的调用约定：服务器把连接和消息传给一个异步可调用对象。HTTP 和 WebSocket 都走它。FastAPI 建在 Starlette 上，Starlette 是 ASGI 框架。Uvicorn 和 Hypercorn 是 ASGI 服务器。Gunicorn 是进程管理器，用 Uvicorn 的 worker 类去跑 ASGI 应用。

一条请求在 FastAPI 里的路径是：Uvicorn 读完 HTTP，Starlette 依次穿过中间件，路由匹配路径和方法，依赖的 `Depends` 按依赖图执行，Pydantic 校验路径、查询和正文，路由函数运行，响应模型再校验出去的对象，然后按相反顺序走出中间件。

同步的 `def` 路由会丢进线程池执行，池子默认大约四十个线程。池子被慢的同步调用占满时，后面的同步路由排队，异步路由仍然可以跑。真正要并发的 IO 写成 `async def`，并使用异步客户端。`async def` 里调用 `requests`、`time.sleep` 或同步的数据库驱动，会把整个事件循环停住，这个 worker 上的所有请求一起等。

### 应用怎么组织

进程级的客户端在生命周期里创建和关闭。`on_event` 已经过时，用 lifespan：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.redis = redis.asyncio.from_url(settings.redis_url)
    app.state.http = httpx.AsyncClient(timeout=timeout, limits=limits)
    yield
    await app.state.http.aclose()
    await app.state.redis.aclose()

app = FastAPI(lifespan=lifespan)
```

路由按资源拆成 `APIRouter`，每个路由文件只引用自己的服务。服务函数接收已经建好的会话和客户端，不在函数里新建连接。配置用 `pydantic-settings` 从环境变量读，启动时校验一次，缺字段就起不来：

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="APP_")
    mysql_dsn: str
    redis_url: str
```

依赖注入用 `Depends`。一次请求里同一个依赖默认只算一次。需要清理的依赖用 `yield`，响应发出之后执行 `yield` 后面的代码，用来关会话、释放锁：

```python
async def get_session():
    async with Session() as session:
        yield session
```

`yield` 之后的清理在异常时也会走到，清理里自己的异常会盖住原来的业务异常，清理要接住并记日志。依赖可以挂在路由、路由器或整个应用上。鉴权这种每个接口都要的检查挂在路由器上。只跟某一个资源有关的检查留在这个路由上。

中间件包住所有请求，适合请求 id 和访问日志。后添加的中间件在更外层，请求先进入它。CORS 放在最外层，里面的错误响应才带得上跨域头。中间件要接住异常并仍然打出访问日志，否则 500 没有统一格式，也没有耗时。纯 ASGI 中间件可以直接处理流式响应。`BaseHTTPMiddleware` 会先把请求体读完，流式上传和一些后台任务的行为会变，访问日志用它足够，改写正文时用 ASGI 中间件。

请求 id 从网关的头读进来，没有就自己生成，放进 `contextvars`，日志和下游调用都带上。下游的头里继续传这个 id，trace 的 `traceparent` 由 OpenTelemetry 的注入器写。

参数和响应用 Pydantic v2 的模型。`model_validate` 从字典或对象构建，`model_dump` 再变回字典。字段约束写在模型上，路由函数里拿到的已经是合法对象。对外响应用 `response_model` 收口，多出来的字段不会漏出去。校验失败是 422，正文里带字段位置。业务上的「这笔订单不属于这个用户」在函数里显式返回 403 或 404，不借校验异常来表达。

后台任务 `BackgroundTasks` 在响应发送之后、仍在这个进程里执行。进程在任务跑完前被杀掉，任务就丢了。发邮件、写搜索索引这种必须做完的事放进消息队列。`BackgroundTasks` 只用来做丢了也能接受的收尾，例如打一条统计。

异常处理按类型注册。业务异常带稳定的错误码，未捕获的异常统一成 500，日志里留栈，响应里不留栈。把内部异常的消息原样返回，会把 SQL 和路径暴露给调用方。

### 和其他框架的边界

Django 适合管理后台、服务端渲染和一张业务库上的完整应用。ORM、迁移、权限和 Admin 是一套。它的传统视图是同步的，并发靠 Gunicorn 的进程和线程。WebSocket 和长连接走 Channels，那是另一条进程模型。一个内部系统、一个团队、数据模型还在一张库里时，Django 把交付速度做上去。

Flask 是薄的 WSGI 工具包。路由和请求对象是核心，数据库、迁移和结构由项目自己选。适合很小的同步服务。新的 IO 密集服务用 FastAPI，少维护一套线程池尺寸。

选择看阻塞点和团队边界。大量同时在等的外部调用用 ASGI。CPU 密集不靠框架解决，靠进程池或队列。服务要拆开时，每个服务一个小的 FastAPI 应用，共用的只有日志格式、错误码和追踪上下文这些内部包。

### 测试和运行

接口测试用 `httpx.ASGITransport` 直接打应用，不先起端口。依赖用 `app.dependency_overrides` 换成测试里的假实现，测完清掉。数据库测试用事务回滚，每个用例结束回到起点。迁移和真实 SQL 的差异在单独的集成测试里打测试库。

本地用 Uvicorn 的 reload。生产用前面写的多进程或单 worker 加副本，关闭 reload。访问日志打到 stdout，格式在日志那一节统一。健康检查拆成存活和就绪，路径和 Kubernetes 探针那一节对上。

## 6. 消息队列

队列用来解耦、异步和削峰。生产者写入后即可返回，消费者按自己的速度处理。下游停了，消息还在；队列自己停了，这条链路停。队列要单独做高可用，否则它就变成新的单点。

本系统稍后执行的任务用 Celery 或 RQ。要和别的服务交换业务事件，用 RabbitMQ、RocketMQ 或 Kafka，正文用 JSON。消息体里放业务键和版本，大文件放对象存储，消息里只放地址。

### 投递和幂等

默认是至少投递一次。超时后生产者会重发，消费者处理完却没确认，消息也会再来。消费逻辑按唯一业务键做成幂等。恰好一次的范围很窄：Kafka 可以把「写出下游消息」和「提交消费位点」放进同一个事务，这覆盖的是消费再转发。消费者写自己的数据库时，数据库事务和 Broker 的确认仍然是两步，业务侧按幂等来写。

幂等表和业务写在同一个事务里：

```sql
CREATE TABLE idempotency (
  idem_key VARCHAR(64) PRIMARY KEY,
  request_hash CHAR(64) NOT NULL,
  response_body JSON NULL,
  created_at DATETIME(3) NOT NULL
);
```

先插入幂等键，唯一键冲突就读出上一次的结果返回。同一个键配了不同的请求体，返回 409，避免把一次重试打成另一笔业务。订单表上的「用户 + 活动 + SKU」或请求 id 唯一键是同一件事的另一种落点。Redis `SET NX` 只能挡住短时间的重复，进程在写库前停了，键还在，请求会被挡住；键过期之后重复消息又会进来。持久的去重放在数据库。

本地事务和发消息放不到同一个数据库事务里。发件箱把这件事留在自己的库里：业务事务同时写入订单和一张 `outbox` 表，提交之后，另一个循环把未发送的行推到队列，成功再标成已发送。

```sql
CREATE TABLE outbox (
  id BIGINT PRIMARY KEY,
  aggregate_id BIGINT NOT NULL,
  topic VARCHAR(128) NOT NULL,
  payload JSON NOT NULL,
  status TINYINT NOT NULL,
  created_at DATETIME(3) NOT NULL,
  KEY idx_status_id (status, id)
);
```

进程在推送前停了，重启后会再推，所以消费者仍要幂等。轮询按 `status, id` 取一批，发送成功再更新状态。发送超时的行保持未发送，下一轮会再发。RocketMQ 的事务消息是 Broker 先收下一条消费者看不见的 half 消息，等本地事务结果再提交或回滚。发件箱不依赖某一种 Broker 的事务能力，换队列时业务事务不用改。

积压时先看是消费变慢还是生产变快。消费变慢就加消费者，或者先把非关键订阅停掉，把积压转到可以水平扩的通道上。毒消息是处理逻辑对这条正文永远失败。它会占住重试。失败次数到顶后进死信，死信要有告警和人工或补偿消费，不能只堆着。

三种队列的差别：

| | RabbitMQ | RocketMQ | Kafka |
| --- | --- | --- | --- |
| 模型 | 交换机把消息推进队列，消费后从队列移除 | topic 下多个队列，Broker 存消息 | topic 下多个分区，追加日志，按保留时间删除 |
| 顺序 | 单个队列里、单个消费者时 | 同一个消息组进同一个队列 | 同一个 key 进同一个分区 |
| 堆积 | 队列变长，堆积很大时更适合让 Kafka 来接 | 可以堆积，受磁盘限制 | 按磁盘保留，适合大流量和回放 |
| 消费语义 | ack 之前可以重投 | 不可见时间之后重新可见 | 位点没提交就会再投 |

Celery 适合发邮件、生成报表、可以重试的第三方调用。`task_acks_late=True` 让任务做完再确认，worker 中途被杀会重跑。broker 用 Redis 时，堆积体现在列表长度上，没有交换机和死信这套路由。跨服务事件用队列的 topic，不用 Celery 的任务名。

### RabbitMQ

生产者只对交换机发，消费者只对队列收。队列没绑定交换机就收不到消息。异步服务用 `aio-pika`，`connect_robust` 负责断线重连。处理完再 ack。失败则 nack，并决定要不要重新入队。

四种交换机。扇出复制到每一个绑定的队列。直连按完整的 routing key 匹配。主题用 `*` 匹配一个词、`#` 匹配零个或多个词。头交换机按消息头匹配。

publisher confirm 打开之后，Broker 落盘（或按策略写入）才给回执。没开 confirm 时，`publish` 返回只说明写进了客户端缓冲区。队列不存在且设置了 mandatory 时，走 return 回调，发件箱那一行保持未发送。

死信有三条来源：队列满了并且拒绝新消息、消费者拒绝且 `requeue=False`、消息超过 TTL。队列参数 `x-dead-letter-exchange` 和 `x-dead-letter-routing-key` 指向下一跳。仲裁队列还可以设 `x-delivery-limit`，同一条消息被投递到这个次数就进死信，避免一条坏消息无限重入队。用「每条消息一个 TTL + 死信」做延迟时，队列按队头检查过期，队头没到期，后面已经到期的消息也出不去。延迟各不相同就用延迟插件，或按延迟档位拆队列。

队列用仲裁队列（quorum queue）。副本按 Raft 多数派确认，镜像队列是旧的做法。prefetch 是每个消费者一次拿多少条未 ack 的消息。设得太大，消息堆在一个慢进程里，别的进程空闲。积压时先加消费者。消费者数量和队列本身的并行度要一起看：一个队列上如果要求严格顺序，就只能有一个活跃消费者。

### RocketMQ

5.x 的 Python 客户端是 `rocketmq-python-client`，走 gRPC，仓库是 `apache/rocketmq-clients`。客户端连 Proxy 端点，由 Proxy 找 Broker。NameServer 在 5.x 部署里仍然保存 Broker 信息。

Producer 往 topic 发，Consumer 按组拉。组里的消费者分摊消息。广播是组里每个消费者都收到全量。消息上有 topic、tag、keys、body。tag 用来在订阅时过滤，keys 用来按业务 id 查。

`SimpleConsumer.receive(max_num, invisible_seconds)` 拉到的消息在不可见时间内不会再给别人。处理完必须 `ack`。超过不可见时间还没 ack，消息重新可见。失败让它超时再投，多次失败进重试 topic，超过次数进死信 topic。死信要有人消费或告警。消费后的消息按 Broker 上的保留时间删除，例如每天固定时刻删掉超过保留小时数的文件。

同一笔订单的创建、支付、取消用同一个消息组，Broker 把它们放进同一个队列，消费者按队列顺序处理。顺序只在一个队列里成立。扩容之后，新的组才会落到新队列。

事务消息：先发 half 消息，消费者看不见；执行本地事务；再提交或回滚。进程在提交前停了，由回查决定。回查做成无副作用的查询：本地事务表里有记录就提交，没有就回滚。

### Kafka

消息按 topic 再按 partition 追加，消费后不删，靠保留时间或大小清理。消费者属于一个组。同组一条消息只给一个消费者。另一组可以再消费全量。offset 提交了，同组就不会再投这条。分区可以回放，只要数据还在保留范围里。

客户端用 `confluent-kafka`（librdkafka）或 `aiokafka`。处理成功再提交位点。自动提交等于拉到就算消费完，处理到一半进程停了就会跳过这条。两次 poll 的间隔有上限，处理太慢会被踢出组，分区分给别人。一次 poll 的条数按处理速度设。

新组从哪开始由 `auto.offset.reset` 决定。`latest` 只消费启动之后的新消息。`earliest` 从保留范围内最早的一条开始，之后仍接上次提交的位点。这和每次手动 seek 到开头不同。换 `group.id` 等于换一组新进度。

Rebalance 在组成员变化或分区数变化时发生。Range 按分区段切，Round-robin 轮询，Sticky 尽量保住上次的分配，只挪走挂掉成员的分区。Cooperative Sticky 是增量再均衡：只收回要挪走的分区，其余分区继续消费。Range 和 Round-robin 会让全组先停下来再分配。协调器是该组 offset 所在 `__consumer_offsets` 分区的 leader。消费者先找到它，发 JoinGroup。协调器选第一个连上来的当组长，把成员列表交给它算分配方案，再通过 SyncGroup 把每人的分区发回去。再均衡期间这组成员暂停拉取。

消息 key 决定分区。同一订单号进同一分区，这个分区里才有顺序。key 太集中时，流量堆在一个分区上，加消费者也没用，因为一个分区同时只被组里的一个消费者读取。消费者数量超过分区数时，多出来的一直空闲。要提高并行度就先增加分区。分区数可以增加，减少会破坏 key 到分区的映射，一般不减。

副本按分区组织，通常三个，落在三台 Broker 上。leader 负责读写。follower 用和消费者一样的 fetch 去拉，请求里带着下一条从哪个 offset 开始。同步复制要等副本写完，最慢的那台拖住写入。异步复制是 leader 写完就返回，没复制出去的在 leader 宕机时丢掉。Raft 和 ZooKeeper 用多数派，容忍 f 台故障要 2f+1 个副本。Kafka 维护的是 ISR。follower 超过 `replica.lag.time.max.ms`（默认 30 秒）还没追上，就移出 ISR，补齐后再加回来。一条消息进入当前全部 ISR，才算已提交。三副本、只从 ISR 接班时，坏两台仍不丢已提交的数据。`min.insync.replicas=2` 时，坏一台还可以继续写；再坏一台，写入失败。

每个副本有自己的 LEO（log end offset），指向下一条要写入的位置。HW（high watermark）是 leader 认为已经复制到全部 ISR 的位置。消费者只能读到 HW 之前的消息。leader 刚把一条消息写在 offset 500，LEO 变成 501，follower 还没拉走时 HW 仍停在 500，消费者最多读到 499。ISR 都发来「从 501 开始拉」，HW 才推进到 501。

`acks=0` 发出去就算成功。`acks=1` 只等 leader。`confluent-kafka` 和 `aiokafka` 的默认各自不同，生产配置里写上 `acks=all` 和 `enable.idempotence`。Java 客户端从 Kafka 3.0 起这两项已经是默认，Python 这两条客户端不要靠那个默认。幂等生产者去掉同一次会话里的重试重复。消费者处理成功但提交位点失败，仍会再投一次。

`acks=all` 等的是当时的 ISR。ISR 缩到只剩 leader 时，也只写了一份。主题的 `min.insync.replicas` 至少为 2，副本因子至少 3。这项的默认是 1。数量不够时生产者收到失败。`unclean.leader.election.enable` 保持关闭。

每一任 leader 有递增的 leader epoch。旧 leader 回来后，先问新 leader 自己这一任到哪结束，截掉分叉点之后的日志，再把正确的数据拉回来。Kafka 4.0 起可以启用 ELR（合格主副本，KIP-966），只在 KRaft 上：不在 ISR、但至少持有到高水位的副本也能接班。4.0 默认关闭，要设 `eligible.leader.replicas.version=1`。4.1 起新建集群默认开启，升级上来的旧集群不会自动打开。选举先看非空的 ISR，再看未被隔离的 ELR。unclean 选举会让没有已提交数据的副本接班。

扣款、借书这种主题用三副本、`acks=all`、`min.insync.replicas=2`、关闭 unclean 选举。任意一台宕机，已确认的消息还在，其余副本仍能写入。`acks=all` 的延迟取决于 ISR 里最慢的副本。三副本大约是三倍的磁盘和复制带宽。一个分区的写入只打 leader。

积压看 lag：分区末端位点减去已提交位点。先分辨是处理变慢还是生产变快，再决定加分区还是改处理函数。扩容消费者之前先确认还有空闲分区。按 lag 扩容可以用后面云和 Kubernetes 一节里的 KEDA，HPA 的 CPU 反映不出堆积。

## 7. Docker 与 Kubernetes

容器把进程放进独立的 namespace，用 cgroup 限制资源，用镜像里的根文件系统启动。Kubernetes 在多台机器上调度这些容器，做自愈、滚动升级和服务发现。Python 服务要额外处理启动慢、多进程内存和信号。

### 镜像

镜像是只读层叠起来的。容器的写入落在最上面的可写层，容器删了可写层就没了。要留的数据用卷。层是按 Dockerfile 的每一条生成文件的指令缓存的。依赖很少变，代码经常变，所以先安装锁文件，最后才 `COPY` 源码。改一行业务代码不会重新下载依赖。

基础镜像用 `python:3.12-slim`，标签钉死版本。多阶段构建：第一阶段安装依赖，第二阶段只保留虚拟环境和代码。`PYTHONDONTWRITEBYTECODE=1` 不写 `.pyc`，`PYTHONUNBUFFERED=1` 让日志立刻进入 Docker 的日志驱动。锁文件放进构建上下文，镜像里按锁安装。

用非 root 用户运行。`USER` 放在 `ENTRYPOINT` 前面。拷文件用 `COPY`。`ADD` 还会拉 URL、解压缩包，构建结果会跟着网络变，镜像里不用它。`CMD` 和 `ENTRYPOINT` 都可以写多次，生效的是最后一条。`EXPOSE` 只是文档，映射靠 `-p` 或 Compose 的 `ports`。

启动命令用 exec 形式，让 Uvicorn 成为 PID 1，才能收到 SIGTERM：

```dockerfile
ENTRYPOINT ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

shell 形式会多一层 shell，停容器时信号打在 shell 上，worker 收不到，最后被强杀。需要在 PID 1 上收割僵尸进程时，用 `tini` 或 `dumb-init` 作为入口，再由它拉起 Uvicorn。

```dockerfile
FROM python:3.12-slim AS build
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
COPY src ./src
RUN uv sync --frozen --no-dev

FROM python:3.12-slim
WORKDIR /app
RUN useradd --create-home --shell /usr/sbin/nologin app
COPY --from=build /app/.venv /app/.venv
COPY --from=build /app/src /app/src
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1
USER app
EXPOSE 8000
ENTRYPOINT ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`.dockerignore` 去掉 `.git`、`.venv`、`__pycache__`、测试数据和本地 `.env`。上下文里带了 `.venv`，会把宿主机的二进制打进去。镜像标签用 git 提交号。`docker build -t 账号/app:版本 .` 之后 `docker push`。回滚时指回旧标签。生产不用 `latest` 作为唯一标识，滚动更新分不清现在跑的是哪一次构建。

日志打到 stdout。需要留存的上传文件用命名 volume，目录对用户 `app` 可写。只读配置挂 `:ro`。

Compose 把应用、MySQL、Redis、队列写在一份 YAML 里，给本地和测试用。服务之间用服务名当主机名，例如 `redis:6379`。`depends_on` 只保证启动顺序。数据库和 Redis 写 `healthcheck`，应用用 `condition: service_healthy`。健康检查通过只说明端口开了，迁移是否跑完由应用自己重试。`expose` 只在 Compose 网络里可见，`ports` 才映射到宿主机。`links` 是遗留字段。本地 Compose 和生产清单共用镜像名、端口、环境变量名。副本数和资源限制各自写。生产不用 `network_mode: host`，否则绕开 Service 的负载均衡。

### 集群里有什么

控制面有四个组件。API Server 是唯一入口，所有写操作经过它。etcd 存集群状态。调度器给还没有节点的 Pod 选一台机器，依据是资源请求、亲和、污点和拓扑。Controller Manager 里跑各种控制器，它们把当前状态往 spec 上推：副本少了就建，节点没了就把 Pod 排走。

节点上有 kubelet 和容器运行时。kubelet 按 Pod 清单拉镜像、起容器、执行探针，停机时先跑 preStop，再发 SIGTERM。kube-proxy 监听 Service 和 EndpointSlice，用 iptables、IPVS 或 eBPF 把 ClusterIP 转成 Pod IP。CoreDNS 把服务名解析成 ClusterIP。

Pod 是调度的最小单位。同一个 Pod 里的容器共享网络 namespace 和存储卷，用 localhost 加端口互相访问。一个 Pod 里放主进程和必须跟它同生共死的边车。可以分开扩缩的进程分成不同的 Deployment。

工作负载按状态来选：

| 对象 | 用途 |
| --- | --- |
| Deployment | 无状态服务。Pod 可替换，用滚动更新 |
| StatefulSet | 稳定的网络名和每副本一块盘。有序滚动。消息队列和数据库用它，业务服务通常不用 |
| DaemonSet | 每个节点一份。日志采集和网络代理 |
| Job / CronJob | 跑完就结束的任务。迁移和对账 |
| ReplicaSet | 维持副本数。一般由 Deployment 管，不单独写 |

Service 按标签选 Pod，提供一个稳定的虚拟 IP。四种类型：`ClusterIP` 只在集群内；`NodePort` 在每个节点上开一个高位端口；`LoadBalancer` 让云创建外部负载均衡；`ExternalName` 返回一条 CNAME。应用只连服务的 DNS 名。Endpoints 为空时，Service 有 IP 但转不走，调用方看到连接失败，先查标签和就绪探针，而不是先改代码。

Ingress 是七层入口，按 Host 和路径转到 Service。证书放在 Ingress 上。Gateway API 是后出现的模型，把网关的部署和路由规则拆开，集群已经用 Ingress 时不必为了名字去换。NetworkPolicy 限制哪些 Pod 可以互相访问。默认经常是全通，生产按命名空间收成「入口来自网关，数据层只接受应用命名空间」。

配置进 ConfigMap，密钥进 Secret。密钥不写进镜像层，也不进 Git。只改 ConfigMap 不会重启容器，进程已经读进 `os.environ` 的值也不会变。需要整进程重载时，给 Pod 模板加一个配置摘要注解，摘要变了就滚动。密钥的轮换同样靠滚动，或者应用自己监听文件变化后重建客户端。

### 持久卷

容器的可写层和 `emptyDir` 随 Pod 一起消失。`emptyDir` 适合解压临时文件和多进程 Prometheus 的目录。`hostPath` 把节点上的目录露进容器，Pod 换一台机器就找不到原来的文件，也把节点文件系统暴露给进程。业务数据不放这两种。

要活过 Pod 重建的磁盘分成三层。PersistentVolume 是集群里的一块存储。PersistentVolumeClaim 是 Pod 发出的申请，写容量、访问模式和 StorageClass。StorageClass 上的供给器看到申请后，去云盘或存储系统里把 PV 造出来并绑上。应用清单里只写 PVC，不写某块盘的 id。

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: order-data
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: ssd
  resources:
    requests:
      storage: 20Gi
```

访问模式是约束，不是性能提示。`ReadWriteOnce` 表示同一时刻只能挂到一个节点上读写。两个副本的 Deployment 共用一块这样的盘，后调度到别的节点的那个 Pod 会一直 Pending。`ReadOnlyMany` 可以多节点只读。`ReadWriteMany` 可以多节点读写，底层得是 NFS、CephFS 这种共享文件系统，云厂商的普通云盘做不到。数据库和队列用一副本一块 `ReadWriteOnce` 盘，由 StatefulSet 的 `volumeClaimTemplates` 按序号各申请一块，Pod 重建后还挂原来那块。

供给时机用 `volumeBindingMode: WaitForFirstConsumer`。立刻供给会在申请创建时就把盘造在某个可用区，调度器随后可能把 Pod 放到另一个区，盘和 Pod 永远碰不到。等 Pod 选好节点再造盘，盘和 Pod 在同一个区。

回收策略：`Delete` 在 PVC 删除时连带删掉云盘。`Retain` 留下云盘和数据，需要人去清。生产数据盘用 `Retain`，确认备份之后再手工删。删 Deployment 不会删 StatefulSet 管的 PVC，缩容留下的 PVC 还占着盘，要单独处理。

磁盘快照是崩溃一致性：快照那一刻磁盘上有什么就有什么，MySQL 可能正写着一页。库的备份仍用 `xtrabackup` 或带 GTID 的逻辑备份。快照用来加快整盘恢复，不代替 binlog。

非 root 的 `app` 用户要能写挂载点。Pod 的 `securityContext.fsGroup` 设成这个用户的组，kubelet 才会把卷的属主改过来。不设的话，进程能启动，第一笔写文件才报权限错误。

Python 服务自己无状态。上传文件进对象存储。PVC 留给自建的数据库、队列和必须落在磁盘上的大文件。托管的 RDS 和 Redis 不需要在业务 Pod 上挂盘。

### 探针、资源和发布

导入 FastAPI、ORM 和搜索客户端要几秒。`startupProbe` 给足失败次数，过了启动阶段才开始存活探针。就绪探针失败只是从 Service 摘掉，不重启。存活探针打 `/healthz`，只判断进程还能不能回答。就绪探针打 `/readyz`，确认连得上 Redis 和数据库。存活探针不去查数据库。数据库一抖动，kubelet 会把 Pod 全部重启。

```yaml
startupProbe:
  httpGet: { path: /healthz, port: 8000 }
  periodSeconds: 5
  failureThreshold: 30
readinessProbe:
  httpGet: { path: /readyz, port: 8000 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /healthz, port: 8000 }
  periodSeconds: 10
```

内存按副本数乘以每个 Pod 里的 worker 数估算，写进 `resources.requests` 和 `limits`。CPU 的 limit 会触发节流。IO 型服务把 CPU limit 设得明显高于 request，或者只设 request、用命名空间的 LimitRange 兜住上限。内存 limit 仍然要设。QoS 按 requests 和 limits 的关系分：两者相等是 Guaranteed，只设了 requests 或两者不等是 Burstable，都没设是 BestEffort。节点内存紧张时，BestEffort 先被杀，然后是超出 requests 的 Burstable。

HPA 看 CPU 时，进程经常在等 IO，CPU 很低但连接已经满了。更有用的是正在处理的请求数、事件循环滞后、连接池占用。这些做成自定义指标再交给 HPA。队列堆积用 KEDA 按 lag 扩消费者。没有这些指标时，先按内存和固定副本数扩。

滚动更新用 `maxUnavailable: 0`、`maxSurge: 1`：先起一个新 Pod，就绪之后再停一个旧的。`minReadySeconds` 设几秒，避免刚通过探针就接全量流量。`PodDisruptionBudget` 的 `minAvailable` 保证腾挪节点时至少留一个能服务的 Pod。副本数是 1 时，PDB 和自愿驱逐会互相卡住，至少两个副本再加 PDB。

`preStop` 里先等几秒，让端点从 Service 摘掉，再让进程处理 SIGTERM。`terminationGracePeriodSeconds` 从 preStop 开始算，到点还没退出就 SIGKILL。preStop 的等待加上处理在途请求的时间要小于这个值。

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]
terminationGracePeriodSeconds: 30
```

镜像拉取用 `imagePullPolicy: IfNotPresent` 配合不可变标签。标签每次构建都变，节点上不会误用旧层。拉取密钥放在 ServiceAccount 上，不写进业务环境变量。

清单的一级字段是 `apiVersion`、`kind`、`metadata`、`spec`、`status`。Deployment 的 `selector` 和 Pod 模板标签一致，副本数写在 `replicas`。`kubectl create deployment ... --dry-run=client -o yaml` 可以先打出一份再改。状态字段由控制面写，提交清单时不去填。

## 8. 微服务

微服务是按业务能力拆开的一组进程：各自部署，各自拥有数据，通过网络调用或消息协作。拆开之后，故障面变小，发布可以分开。代价是一次业务操作跨过网络，事务、超时和观测都要单独设计。系统不够大时，一个仓库里的模块边界就够了，抽成独立进程的协调成本更高。

### 边界

代码上对应三种边界：

- 一个进程里的包：`accounts`、`orders` 只是目录，调用是函数调用。事务还是本地的。
- 独立进程：各自的镜像、Deployment、数据库。调用走 HTTP 或消息。一个进程停了，另一个进程还在。
- 内部包：发到内部索引，各服务钉死主版本。包里放日志格式、追踪上下文、错误码。创建订单这种业务留在订单服务里。

按业务能力拆，不按技术层拆。把「所有数据库访问」放进一个服务、把「所有校验」放进另一个服务，一次请求仍然要穿过所有层，发布还得一起发。订单服务拥有订单表，商品服务拥有商品表。需要别人的数据时，要么同步调用拿一次，要么订阅对方的事件在本地留一份只读副本。两个服务写同一张表，就回到了共享数据库，只是进程分成了两个。

中台是把各业务线里重复的能力抽出来。业务中台是用户、会员、支付、权限这种各条线都要的服务。数据中台是统一的存储、建模和计算。技术中台是日志、配置、鉴权、任务这些共用平台。烟囱是每条产品线各做一份权限和订单，共性抽不出来。落地顺序是：先按业务拆开，再把共有能力收成平台，最后调整编制和投入。调用方拿用户 id 就能完成登录态校验，用户服务把存储细节留在自己这边。

拆分的信号是：这个模块要独立扩容，发布节奏和别人不同，故障时不想拖垮主路径，数据所有权已经清楚。反向的信号是：每次改需求都要改三个服务，同步调用链超过三跳，为了一次查询做分布式事务。这种情况下先把边界收回到一个进程里。

### 同步调用上的保护

服务之间用一个进程级的 `httpx.AsyncClient`。超时拆开，重试只打在幂等请求上。超时从外往里缩短，理由在网络那一节。

五个保护要一起用：

- 超时：每次下游调用都有上限，连接、读、池等待分开。
- 重试：有次数、有抖动，只打幂等接口。重试会放大流量，下游已经超时的时候，重试往往还在打它。
- 熔断：连续失败后暂时不再调用，给对方恢复的时间，也避免自己的连接全堵在一个已经坏的下游上。半开时放少量探测。打开期间返回缓存里的旧数据，或一个明确的稍后再试。
- 舱壁：每个下游一把 `asyncio.Semaphore` 和一份连接限额。支付慢只占满支付的额度，查询还剩自己的连接。
- 限流：在入口按用户和接口收住，在服务里按自己的容量再收一层。

熔断计数在进程内时，每个 worker 各算各的。副本很多时，单个进程的失败样本变少，打开得更慢。入口限流放在网关，效果对所有副本同时生效。降级路径里不再同步调用同一个下游。

幂等键由调用方生成，放在头里，服务端用前面的幂等表记住结果。超时之后调用方用同一个键再请求，拿到的是第一次的响应。键要跟着业务单走，用户每点一次「提交」是一个新键，同一次提交的自动重试是同一个键。

```python
pay_limit = asyncio.Semaphore(20)

async def call_pay(body: dict, idem_key: str):
    async with pay_limit:
        return await client.post(
            "/pay",
            json=body,
            headers={"Idempotency-Key": idem_key},
        )
```

服务网格把 mTLS、部分重试和指标下沉到边车。应用仍然要设自己的超时和幂等。边车的重试和代码里的重试叠在一起，总次数是相乘的。开了网格之后，重试只留一处。

### 跨服务的数据

一次下单要改订单、库存和优惠券。这三个库没有同一个本地事务。做法按一致性要求选：

- 能放在一个库里的，就还是一个库、一个事务。拆服务不强制拆库。
- 发件箱加事件。订单事务提交后，库存服务消费事件再扣。中间有一段时间两边不一致，用对账补。
- Saga 是一串本地事务加补偿。编排式由一个协调者按步骤调用，失败了按相反顺序执行补偿。编舞式由每个服务发出事件，下一个服务自己接着做。补偿要做成幂等，因为补偿消息也会重投。Saga 没有隔离性：步骤之间别人能看见中间状态，业务上要用状态机把「支付中」「已取消」显式写出来。
- TCC 把每个资源分成 Try、Confirm、Cancel。Try 预留，Confirm 确认，Cancel 释放。隔离性比 Saga 好，业务代码要按这三个阶段改。冲突高、又要预留资源的场景才用，例如库存预占。

两阶段提交让所有参与者先准备再提交。协调者在准备之后宕机，参与者会一直占着锁等它。跨服务的业务事务不用这条路径。数据库内部的 redo 和 binlog 是另一回事，那是一个进程里的两阶段。

读自己的写入：写完去从库或去别人的只读副本，可能还没有这笔数据。用户刚提交的订单，查询打主库或打本地已提交的结果。列表和搜索可以接受秒级延迟。

接口演进用加字段、不改旧字段含义的方式。先让调用方能忽略新字段，再让调用方开始写新字段，最后才停用旧字段。同时在线的两个版本要都能处理对方的消息。消息体里带 schema 版本。破坏性变更用新的路径或新的 topic，旧的留到调用方都迁走。

### 网关、配置与发现

鉴权、限流、黑名单放在入口，每个服务就不用各写一份。APISIX 或 Kong 放在 Pod 前面：

- 路由：按路径或 Host 转到哪个上游。上游是一组 Pod 的 Service。
- 匹配：路径前缀、Header、方法。不满足就不转发。
- 插件：JWT、限流、改写路径、请求 id、访问日志。

只有一个服务、流量也不大时，用 FastAPI 的 `Depends` 在进程内做鉴权。服务多了之后，令牌校验放到网关，后面的服务信任网关注入的用户 id。这个头在最外层入口清掉再由网关写入，调用方自己带的同名头进不了内网。网关做所有服务都要的事：TLS、限流、鉴权、请求 id、访问日志、转发。进程里留和这个资源有关的事：参数校验、这笔订单是不是这个用户的、幂等。网关不知道订单属主。

### 登录态

浏览器应用用服务端会话。登录成功后在 Redis 里写一份会话，Cookie 里只放会话 id。Cookie 设 `HttpOnly`、`Secure`，`SameSite=Lax`。`HttpOnly` 让页面脚本读不到它。注销就是删掉 Redis 里的这份会话，所有副本立刻失效。改权限也是改这一份，下一次请求就生效。

Cookie 会由浏览器自动带上。`SameSite=Lax` 挡住别的站点发起的 POST，顶层链接进来的 GET 仍会带上。会改数据的接口再对一份 CSRF 令牌，不把「带了 Cookie」当成唯一的授权依据。

JWT 把声明和签名放在令牌里，网关用密钥验签，不必每次去 Redis。令牌是三段 base64url：头、载荷、签名。载荷里放 `sub`（用户 id）、`exp`、`iat`、`iss`、`aud`、`jti`。角色可以放，但权限一改，旧令牌里的角色还要等到过期。密码、手机号、完整资料不放进去，令牌会进日志和浏览器。

签名算法在服务端固定。验签时不采用令牌头里临时指定的算法，避免被换成 `none` 或换成攻击者自己的密钥。对称的 HS256 要求所有验签的服务共享密钥。非对称的 RS256 或 EdDSA 由认证服务用私钥签，网关只用公钥验，私钥不进业务服务。

访问令牌的有效期用几分钟到一刻钟。刷新令牌有效期长，只交给认证服务，在 Redis 或数据库里存它的哈希。换发时作废旧的刷新令牌、发新的一对。旧的刷新令牌再次出现，就把这一族都作废，当成已经泄露。注销时删掉刷新令牌，并把访问令牌的 `jti` 放进拒绝列表，放到它的 `exp` 为止。访问令牌越短，拒绝列表越小。

浏览器里，访问令牌放内存，刷新令牌放 `HttpOnly` Cookie。放进 `localStorage` 的令牌，页面上任何一段脚本都能读走。手机和别的服务用 `Authorization: Bearer`。网关验完签，把用户 id 写进内部头。业务服务查订单时用这个 id 做条件，不信任路径或正文里自带的用户 id。

时钟有偏差，`exp` 的校验留几十秒余量。余量只盖住时钟误差，不拿它延长令牌寿命。

限流按路由配。秒杀和普通查询分开。固定窗口会在窗口边界放进两倍流量。漏桶按固定速率漏出。令牌桶允许短时间的突发，桶空了就拒绝。限流键用用户 id，没有登录态时用 IP。只按 IP 会误伤出口地址相同的一群人。分布式限流的计数放在 Redis，用一段 Lua 做令牌桶或滑动窗口，单机内存里的计数每个副本各算各的。

Nacos 同时做注册和配置。纯 Kubernetes 用 Service 和 CoreDNS 发现，配置用 ConfigMap。虚拟机或混部再用 Nacos。两套发现会给出不同的地址，选一套。

Python 用 `nacos-sdk-python` v2，走 gRPC，端口是 HTTP 端口加 1000。`ClientConfigBuilder` 里写地址、命名空间、账号。

```python
config_client = await NacosConfigService.create_config_service(client_config)
raw = await config_client.get_config(
    ConfigParam(data_id="order-dev.yaml", group="DEFAULT_GROUP")
)
```

Data Id 用「应用名-环境.后缀」。共享配置和扩展配置分成不同 Data Id，后读到的覆盖先读到的。命名空间或分组写错时读到空内容。`add_listener` 在变更时回调。回调里替换进程内的配置对象。已经建立的数据库连接池不会因为配置文本变了就自动换主机，换地址要重建引擎。

回调不一定跑在事件循环线程上。回调里只解析文本、换上一个不可变配置对象。要通知协程就 `call_soon_threadsafe`。解析失败保持旧配置。

本地缓存目录在连不上服务器时用来启动。容器根文件系统只读时，把这个目录指到可写的 emptyDir。

```python
naming = await NacosNamingService.create_naming_service(client_config)
await naming.register_instance(RegisterInstanceParam(
    service_name="order",

```

调用方 `list_instances(..., healthy_only=True)`，在健康实例里按权重选。SDK 负责心跳和本地缓存。进程退出要反注册。注册用临时实例：心跳在，实例就在；心跳没了，服务器超时后摘掉。持久实例没有心跳，崩溃后会一直留在列表里。调用方使用订阅来的列表。在 Kubernetes 里，就绪探针已经在做摘除，再注册一份 Nacos 就会有两套实例列表。

## 9. 分布式理论

一个进程里用锁和事务就能排好的事，拆到多台机器上之后要面对三件事：消息会丢、会重复、会延迟；机器会停；网络会把集群切成几块。下面这些名词都是在给这三件事选规则。

### CAP、PACELC、BASE

CAP 说的是发生网络分区的时候：分区的两侧不能同时做到「每次读都看到最新写入」和「两侧都继续对外服务」。选一致性，少数派就停止写入，甚至停止服务，这是 CP。选可用性，两侧都继续读写，等分区恢复再合并，读到的可能是旧的，这是 AP。没有分区的时候，延迟和一致性还可以同时往前做。把 CAP 理解成平时也只能三选二，会漏掉「分区才迫使你选」这个条件。

PACELC 把没有分区的情况补上：有分区（P）时在可用性（A）和一致性（C）之间选；没有分区时在延迟（L）和一致性（C）之间选。同步复制更一致，提交要等另一台确认，延迟更高。异步复制返回快，另一台还没收到。MySQL 半同步和 Redis 异步复制就是这个选择的两个点。

BASE 是另一端的工程说法：基本可用、软状态、最终一致。软状态是允许中间有一段时间读到旧值或中间步骤。最终一致是在没有新的写入、消息也都送达之后，副本会相同。它不是「可以一直不一致」。要有一个时刻用对账把两边对齐，并给这个延迟一个上限。

### 一致性怎么分级

强一致是读到的是上一次成功写入。主从都确认之后再返回，读也打到主，接近这个效果。线性一致还要求所有客户端看到的顺序和真实时间一致，通常要共识算法在多数派上提交。

顺序一致是所有客户端看到同一个操作顺序，这个顺序可以和真实时间略有偏差。因果一致保证有因果关系的操作不被看反，没有因果关系的可以不同顺序。读己之写是一个客户端至少能读到自己刚写的。会话一致把这个保证放在一次会话里。最终一致只保证收敛。

业务上按数据来选。余额和库存的扣减要强一致，用数据库条件更新或单主上的原子操作。时间线、搜索索引、统计可以最终一致，用消息把变更送过去。一个接口里混着两种数据时，把强一致的那部分单独读主库，其余走缓存。

### 多数派和副本

N 个副本，写入要 W 个确认，读取要 R 个确认。W + R > N 时，读集合和写集合一定有交集，能读到最近一次满足 W 的写入。常见是 N = 3，W = 2，R = 2，可以坏一台。W = N 是每写都要全部确认，一台慢就写不进去。W = 1 是最快的写，读必须接触全部副本才能确认自己看到的是最新的。

这是无主副本的算法。MySQL 和 Redis 主从是有主的：写进主，读主就看到这次写入；读从就要接受复制延迟。Kafka 的 `acks=all` 等的是当时的 ISR，不是超过半数。`min.insync.replicas` 设成 2、副本因子 3 时，确认只需要两份；ISR 缩到只剩 leader 时，这项保证也跟着缩掉。细节在消息队列的 Kafka 那一节。

法定人数也用来选主。三个节点可以坏一个，五个可以坏两个。两个节点没有多数派，网络一切开就无法决定谁是主，所以哨兵、etcd、ZooKeeper 都用奇数。

### Paxos

Paxos 要一组进程对一个值做出唯一的决定。进程会停，消息会丢、会重复、会延迟，发送方不会伪造消息。决定做出来之后，后面学到结果的进程都学到这同一个值。

三个角色可以叠在同一台机器上。提议者提出值，接受者投票，学习者得知结果。

每个提议有一个编号，所有编号能比大小，并且不重复。轮次放在高位、机器号放在低位，两台机器就不会拿出同一个号。

第一阶段是准备。提议者选一个比自己用过的都大的编号 n，向一个多数派发送准备请求。接受者如果还没有答应过更大的编号，就承诺不再接受编号比 n 小的提议，并把自己已经接受过的、编号最大的那条提议（编号和值）回给提议者。没有接受过任何提议，就只回承诺。

第二阶段是接受。提议者集齐一个多数派的承诺之后才能发接受请求。值按回包决定：有人已经接受过提议，就用这些回包里编号最大的那个值；谁都没接受过，才用提议者自己原来想提的值。请求是 (n, v)。接受者只要还没有答应过比 n 更大的编号，就接受它。

一个值被选定，是指一个多数派接受了同一个 (n, v)。学习者从接受者那里得知这件事。Basic Paxos 只决定一个值。一条日志是一串这样的决定，每个槽位跑一轮。

安全性来自多数派一定相交，再加上「有旧值就必须沿用」。假设编号 n 的值 v 已经被一个多数派接受。任何编号更大的提议者要进入第二阶段，都得再拿到一个多数派的承诺。这两个多数派至少有一个接受者是同一个人。这个人已经接受过 (n, v)，回包里会带上它；如果他后来又接受了更新的提议，那条更新的提议也是按同一规则从 v 沿用下来的。新提议者必须采用回包里编号最大的值，所以发出去的仍然是 v。对编号做归纳：凡是编号大于 n、并且真能完成的提议，值都是 v。两个不同的值不能同时被各自的多数派选定。

这套规则不保证某一次提议一定完成。两个提议者可以轮流用更大的编号打断对方，两边都过不了第二阶段。已经选定的值不会因此变成别的值，只是新的决定暂时做不出来。

工程上先固定一个稳定的提议者。它做一次准备，承诺覆盖后面的一段槽位；每条新命令只跑第二阶段，把一条日志复制到多数派。这是 Multi-Paxos。提议者宕了再重选，新提议者的准备阶段会把多数派上见过的旧值收集回来，按上面的规则补全。

Raft 把这套做法收成固定角色：强领导者、任期、日志必须连续，选举时就要求候选人的日志足够新。Paxos 允许槽位上暂时有空洞，实现者自己补。ZooKeeper 用的 Zab、etcd 用的 Raft，都是「稳定领导者加上多数派复制」。Chubby 用的是 Multi-Paxos。讲 Raft 的选举和日志匹配时，对应的就是这里的准备阶段和「旧值必须沿用」。

### Raft

Raft 是一种共识算法，etcd、Kubernetes 的一些组件、RabbitMQ 仲裁队列都用它或它的变体。一个任期里最多一个领导者。领导者把日志复制到跟随者，多数派写下之后，这条日志才算提交，然后应用到状态机。

选举：跟随者在选举超时内没收到心跳，就变成候选人，任期加一，向其他节点要票。每个节点在一个任期里只投一票，并且只投给日志至少和自己一样新的候选人。超时时间加随机抖动，避免所有人同时发起选举。少数派凑不齐多数票，选不出领导者。已经提交的日志只会由拿到多数派的那一个领导者继续复制。

日志匹配：同一索引、同一任期的日志在所有节点上是同一条。领导者只追加，冲突时用自己的日志覆盖跟随者。已经提交的日志在以后的领导者里仍然存在。这些规则保证提交过的操作不会因为选主被丢掉。

客户端只向领导者写。领导者还没复制到多数派就宕机时，客户端超时重试。操作本身要幂等，或者用一个客户端 id 和序号，让新领导者认出这是同一笔。Raft 保证的是日志的一致，不代替业务幂等。

### 时钟

物理时钟会漂移，NTP 校正时还可能往回跳。用本机时间做超时和证书判断可以，用两台机器的时间戳决定事件顺序不可以。Redis 锁的 TTL 用的是 Redis 服务器的时间，客户端时钟跳了不会直接让锁提前过期；主从切换仍会把还没复制的锁丢掉，那是复制的问题，不是客户端时钟的问题。

Lamport 时钟是一个整数，事件发生或收到消息时取最大值再加一。它可以给出一个全序，但看不出两件事是不是因果相关。向量时钟每个进程一维，能判断因果，维度随进程数增长。混合逻辑时钟把物理时间和逻辑计数放在一起，既接近真实时间，又在时钟回拨时靠逻辑位继续递增。订单号和日志的时间用单点生成的雪花 id，或者数据库的自增，不拿各台应用机器的 `time.time()` 拼顺序。

租约是带期限的所有权。持有者在期限前续约，到期没续，别人就可以拿走。Kubernetes 的选主、Kafka 的组成员、Redis 的锁都是租约。期限必须大于时钟误差和处理时间，续约失败要当成已经失去所有权，停下手上的独占操作。

### 失败的样子

宕机是进程停了，内存里的状态没了。恢复靠磁盘上的日志和启动时的重放。网络分区是两边都活着但不通。这时候最容易出现两个写入点。防护是少数派没有法定人数就不写。

脑裂是分区两侧各有一个主。Redis 哨兵要求多数派才故障转移，降低两侧同时选主的可能。旧主如果还在对外服务，客户端可能继续往旧主写。哨兵把旧主改成从、并要求从只读，是为了让它重新连上之后丢掉分叉的写入、向新主对齐。应用在切换窗口会写失败，按幂等重试到新主。

重复和乱序一起出现。消息至少一次，所以会重复。不同分区之间没有顺序。消费者按业务键去重，用状态机接受「取消先到、支付后到」这种乱序：状态只能沿允许的边走，走不通的消息先放着或进死信，不能把状态从已支付改回未创建。

幂等是这些失败模型的落点。同一笔请求执行多次，系统状态和执行一次相同。数据库唯一键、条件更新、幂等表、带 token 的锁释放，都是在实现这句话。

## 10. 系统设计

设计题先把约束问清楚，再估容量，再画主路径，最后把失败和一致性补上。组件从前面几节里选，不从名词表里堆。

### 怎么拆一道题

先问清楚这几件事：读多还是写多，峰值 QPS 和平均差多少，数据要留多久，能不能接受旧数据，有没有热点，用户在一个地域还是多个。问完才能决定要不要缓存、要不要分片、要不要异步。

然后做数量级估算。每秒请求数乘以单次读写的大小得到带宽。每天的新增行数乘以保留天数得到存储。峰值按平均的几倍到几十倍留余量，秒杀这种脉冲要单独算。连接数按副本数乘以每进程的池大小，对到数据库的 `max_connections`。估算是为了选出瓶颈在 CPU、网络、磁盘还是锁，不是为了算到个位数。

接口和数据模型接着写。谁是聚合根，哪些查询要同时返回，哪些可以延迟。能用一张表和一个事务完成的，不拆成三个服务。

主路径画一条写、一条读。写路径标出事务边界和发件箱。读路径标出缓存层级和回源。然后单独写失败：下游超时怎么办，消息重复怎么办，缓存和库不一致怎么收口，扩容时数据怎么搬。观测放在最后：这条路径的延迟、错误率和积压看哪几个数。

延迟的预算按层扣。入口 3 秒的时候，里面每一跳都是几十到几百毫秒，数据库一次查询控制在几毫秒到几十毫秒。某一跳占掉大部分预算，就把它变成异步，或者加缓存。

### 几个反复出现的构件

id 在单库里用自增主键，插入落在索引的右边。要在应用里生成时用雪花 id：1 位符号，41 位毫秒时间，10 位机器，12 位序列，趋势递增，单毫秒单机能发 4096 个。机器号从库或 Redis 租，租约到期才能给别人。时钟回拨时拒绝发号或等到时间追上，不能把时间往回倒着发。UUID v7 也按时间排序，16 字节，做主键比 v4 友好。UUID v4 是随机的，会把 B+ 树写散。

限流算法按窗口的毛病来选。固定窗口在边界两侧各放进一整窗的量。滑动窗口把当前时间附近的计数加起来，边界平滑。令牌桶按速率补充令牌，允许短突发。漏桶按固定速率放行，出口更平。分布式计数用 Redis Lua，本地突发用进程内令牌桶先挡一层。

一致性哈希用来把键分配到一批节点上，并且在节点增减时只搬一小段数据。把哈希空间收成一个环。每台物理节点用多个不同的种子算出很多位置，这些是虚拟节点。一个键哈希之后，沿环顺时针遇到的第一个虚拟节点就是它的归属，这个虚拟节点再映射回物理节点。

三台机器 A、B、C，每台在环上有很多点。键 k 顺时针先碰到 A 的某个虚拟节点，就由 A 负责。A 下线时，原先落在 A 那些点上的键，继续顺时针走到 B 或 C 的点，其他键不动。没有虚拟节点时，A、B、C 各占环上的一个点，A 离开会把自己那一整段弧都交给下一家，下一家的内存和流量突然翻倍。虚拟节点把这段弧切成很多小段，小段分别落到剩下的机器上。虚拟节点的个数按机器数取，每台一两百个就足够把倾斜压下去。机器权重不同时，权重大的放更多虚拟节点。

缓存节点用这套环，键是缓存 key。分库也可以用它：键是用户 id，节点是分片。和取模相比，取模在分片从 8 扩到 9 时几乎每行都要搬；扩到 16 这种两倍才只搬一半。一致性哈希在任意增减一台时只搬这一台名下的键。代价是实现要维护环，并且要处理节点抖动：一台缓存时好时坏，键会来回搬，打穿数据库。节点离开前先把流量摘干净，或者用带副本的一致性哈希，每个键沿环再找下一台做备份。

负载均衡把同一类请求送到同一台时用的是同一个环。请求没有本地状态时不必用它，轮询更均匀。

对账是最终一致的闭环。每隔一段时间用源表的聚合和目标对一下：订单数和库存扣减数、发件箱已发送和消费者处理数、缓存里的库存和数据库的库存。偏差超过阈值再告警，而不是每次有消息就人工看。

### 秒杀

普通购买是查商品、建单、扣库存、付款、发货。秒杀是活动页、详情、立即抢、去付款。特点是价格低、瞬时并发高、限时限量、要预热（今天的页面上放明天的商品）。

读和写分开。详情走缓存或静态页。写的本质是并发扣减，要保证不超卖。秒杀接口单独路由、单独副本，限流放在网关上，超过的返回排队页。验证码和答题放在真正扣库存之前，把脚本流量挡在外面。

活动开始前把库存写进 Redis。扣减是一段 Lua，多条命令之间不会被别的客户端插进来。售罄标记如果只放在某个 worker 的内存里，别的进程看不到。标记的来源是 Redis：Lua 返回售罄，或者订阅一个售罄频道。Pub/Sub 不留存，进程刚启动时本地标记是空的，第一批请求打到 Redis，再把标记树起来。

```python
DECR_IF_POSITIVE = """
local left = tonumber(redis.call('GET', KEYS[1]) or '-1')
if left <= 0 then
  return -1
end
return redis.call('DECR', KEYS[1])
"""
```

限购和扣减放进同一段 Lua，避免扣完又发现这个用户已经买过，还得把库存加回去：

1. 请求 id 已有结果，直接返回上次的结果。
2. `SET 用户限购键 1 NX EX 活动时长`。设不上就是已经买过。
3. 库存大于 0 才 `DECR`，否则删掉限购键并返回售罄。
4. 把用户、SKU、请求 id 放进队列。队列满了就 `INCR` 还库存、删限购键，接口返回稍后再试。

消费者按数据库能承受的速度建单。订单表的唯一键是用户 id + 活动 id + SKU，或请求 id。插入成功再写扣减流水。碰到唯一键就是重复投递，确认消息即可。数据库故障则不确认，稍后再消费。多次仍失败就把库存还回 Redis，并记入失败表。

定时任务用「预热库存 − 成功订单数」和 Redis 当前值比较，偏差超过阈值再告警。活动结束后以订单表为准做一次对账。

热点 SKU 的一个 key 会打在集群的一个槽上。库存拆成 `stock:{sku}:0` 到 `stock:{sku}:9`，请求随机选一段，这一段空了再试别的段。哈希标签 `{sku}` 让这些键落在同一个槽，一段 Lua 里可以连续尝试。拆段之后总库存是各段之和，展示用短缓存。

有人绕过接口直接改库时，缓存不会跟着变。订阅 binlog，而不是轮询表。`mysql-replication` 的 `BinLogStreamReader` 扮成 slave。MySQL 8 要 `binlog_format=ROW`、`binlog_row_image=FULL`、`binlog_row_metadata=FULL`，账号有复制权限，`server_id` 不和现有副本冲突。位点要自己存，断线从位点续上。也可以让独立进程拉 binlog 再推进 Kafka，应用只做消费者。解析到库存或价格变更后删缓存，或发消息更新搜索索引。这件事放在订阅进程里，不放在下单请求里。

### 搜索

搜索走 Elasticsearch，下单和库存走 MySQL。倒排索引按词指向文档 id。中文用 IK：`ik_max_word` 切得细，`ik_smart` 切得粗。7.x 起类型固定为 `_doc`。

商品索引：标题、关键词、副标题用 `text` 加 IK；品牌名、类目名、图片 URL 用 `keyword`；价格、销量、上架时间、是否有货用数值、日期、布尔。属性是一对多，映射成 `nested`（`attrId`、`attrName`、`attrValue`）。普通 object 数组会被拍扁，`颜色=黑` 和 `尺寸=L` 会错配成交叉组合。

异步服务用 `AsyncElasticsearch`，进程退出时 `await client.close()`。条件多时用 DSL：`AsyncSearch(using=client, index="product_db")`，`s.query(...)`，`to_dict()` 看最终 JSON。已经有查询字典时，直接 `client.search`。

筛选放进 `bool.filter`：品牌、价格区间、有货、类目。`filter` 不参与打分，可以被缓存。关键词放进 `bool.must` 的 `multi_match`，字段用 `name^3`、`keywords^2`、`subTitle`。`should` 用来加分，例如品牌名刚好等于输入词。用户选了价格或销量，就按那个字段排。默认排序用相关性，也可以用 `function_score` 把销量、上架时间折进分数。分页用 `search_after`：排序字段里带一个唯一值，下一页把上一页最后一条的 `sort` 传回去。`from + size` 超过 `index.max_result_window`（默认 10000）会被拒绝。

品牌和属性筛选项是聚合。bucket 是分组，metric 是组上的统计。nested 属性要先进入 nested 文档再 terms。高亮用 `highlight`，`fragment_size` 控制片段长度，`number_of_fragments` 控制返回几段。

商品保存成功后发消息，消费者写 ES，失败可重试。搜索允许秒级延迟。写入用 `helpers.async_bulk`。429 和 503 退避重试，映射错误进失败队列。更新用 `if_seq_no` 和 `if_primary_term`：序号不一致就重新读再写。

默认 `refresh_interval` 是 1 秒，写完立刻搜可能还看不到。主分片数在索引建好后要改，就建新索引再切别名。查询可以打在副本上，写入打在主分片再同步。别名指到当前索引，对完数再原子拨过去。改分词器或已有字段的类型都要重建索引。

Master 管元数据和分片分配，Data 节点存分片并承担读写。应用连接超时设短，搜索读超时按慢查询上限设。聚合限制 `size` 和 `timeout`。客户端超时取消不了已经在节点上跑的查询。

### 容量不够时的顺序

先做单机能做的：索引、连接池、慢查询、缓存、无用的同步调用。然后加副本，应用无状态，数据库加读副本。写仍打在主库上，写成为瓶颈时再分库分表。异步把不是主路径的写移出请求。每一步都要能说出现在的瓶颈数字，再选下一步。

## 11. 可观测性

可观测性是从系统外面发出的信号还原里面发生了什么。日志、指标、追踪是三种信号。只有日志时，要靠人去翻一次请求。只有平均值时，看不到慢的那百分之一。三者用同一个请求 id 串起来。

服务看四个信号：流量、延迟、错误、饱和度。延迟用直方图的分位，不用平均值。错误看 5xx 和业务错误码，不只看进程还在不在。饱和度看连接池占用、队列 lag、事件循环滞后、CPU 节流。资源看使用率、饱和度和错误：磁盘 `%util` 和 await，内存 available，文件描述符。

RED 是给服务的：Rate、Errors、Duration。USE 是给资源的：Utilization、Saturation、Errors。两边一起看，才能分清是自己慢还是依赖慢。

### 日志

日志打到 stdout，一行一个 JSON。字段固定：时间、级别、服务名、请求 id、trace_id、span_id、路径、状态码、耗时、错误码。正文是消息，不把整份请求体打进去。手机号、令牌、密码不进日志。

请求 id 放在 `contextvars` 里，日志过滤器每次从上下文取。OpenTelemetry 的当前 span 里有 trace_id，过滤器和它对齐，日志平台才能从一条错误跳到整条追踪。异常用 `logger.exception` 留下栈，栈在日志系统里，不在 HTTP 响应里。

访问日志每个请求一条，在中间件里打，包含状态码和耗时。业务日志只在状态变化和外部调用失败时打。循环里逐条打，流量一上来就会把磁盘和采集管道打满。级别在生产用 INFO，排查时对单个服务临时开 DEBUG，用完收回。

### 指标

指标是可聚合的数字。Prometheus 的客户端库里三种类型就够用：

- Counter 只增。请求数、错误数。看速率用 `rate()`，看增长用 `increase()`。
- Gauge 可升可降。正在处理的请求数、连接池占用、队列长度。
- Histogram 观察值的分布。请求耗时。分位用 `histogram_quantile`，桶的边界按自己的 SLO 设，例如 50 毫秒、100 毫秒、300 毫秒、1 秒。

标签是有限集合：服务、路由模板、状态码、下游名字。用户 id、订单 id 放进标签，基数会把 Prometheus 打满。路由用模板 `/orders/{id}`，不用真实路径。

进程里用 `prometheus_client` 暴露 `/metrics`，由采集器拉取。多进程的 Gunicorn 要使用它的多进程目录，否则每个 worker 一份计数，拉到的只是其中一个。异步服务注意采集不能堵住事件循环，官方客户端的生成是同步的，单独放在线程里或者接受它很短。

应用自己的指标补上框架没有的：Redis 命令超时次数、数据库连接池在用数量、发件箱堆积行数、Lua 返回的售罄次数。框架的 HTTP 直方图只知道路由慢，不知道慢在下游还是慢在锁。

### 追踪

一条追踪是一次请求穿过所有服务的树。span 是树上的一个节点：一次 HTTP 调用、一次 SQL、一次 Redis。span 上有开始时间、结束时间、状态和几个属性。父 span 的 id 放在 `traceparent` 头里往下游传，W3C 的格式是标准的那一个。

Python 用 OpenTelemetry SDK。`TracerProvider` 加上 `BatchSpanProcessor`，导出到 OTLP 收集器。收集器再送到后端。导出放在进程外的收集器上，应用不直接对后端的地址负责。FastAPI、httpx、SQLAlchemy、Redis 有对应的 instrumentation，进来的头会被读成父 span，出去的调用会把头注入。

```python
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))
trace.set_tracer_provider(provider)
```

采样在流量大时按比例，错误和慢请求要能留下。头部采样在请求进来时就决定，实现简单，可能把一次慢请求丢了。尾部采样等整条追踪结束再决定，能保住错误，代价是收集器要先把追踪攒住。入口先用按比例加「错误一定采样」，就够定位大部分问题。

span 上只放定位需要的属性：订单 id、下游地址、重试次数。SQL 可以记语句模板，不记绑定进去的隐私参数。

### SLO 和告警

SLI 是测量出来的比例，例如 30 天里耗时小于 300 毫秒且不是 5xx 的请求占比。SLO 是这个比例的目标，例如 99.9%。错误预算是 1 减去 SLO，预算烧完就停止普通发布，先处理可靠性。

告警打在症状上：错误率、延迟分位、预算燃烧速度、队列 lag、探针失败。CPU 高本身不叫醒人，它引起的延迟才叫醒人。燃烧速度用两个窗口一起看，短窗口抓突发，长窗口抓慢性消耗，避免一次抖动就响。

每个告警带一个下一步：看哪张仪表盘，先查哪个下游。没有下一步的告警会在几次之后被关掉。就绪失败和存活重启分开告，前者是依赖，后者是进程自己。

### 接口变慢怎么查

先分清范围。看入口的流量、延迟分位和错误率：是全站一起变慢，还是一条路由、一个用户。时间和最近一次发布对齐。全站的 5xx 先看网关到 Pod 的连接失败和就绪探针，再看应用。

然后看饱和，而不是先重启。正在处理的请求数、事件循环滞后、连接池里正在用的连接、池等待时间。池等待升高，请求堆在应用里，原因在池子后面的数据库、Redis 或下游。事件循环滞后升高，进程里有同步阻塞或一段纯计算。

用这一条慢请求的 trace 看时间花在哪个 span。SQL 长，就去数据库上看锁和扫描行数：`sys.innodb_lock_waits`、慢查询、`EXPLAIN` 里的 `rows`。行锁等待和死锁对应 MySQL 那一节的 1205 和 1213。Redis 长，看 `slowlog`、是不是在 `bgsave`、是不是一个大 key。下游 HTTP 长，看对方的错误率和超时，本进程的熔断有没有打开。

机器放在最后。`container_cpu_cfs_throttled_seconds_total` 在涨，同时延迟升高，是 CPU limit 在节流，平均 CPU 可以仍然不高。退出码 137 且原因是 OOMKilled，是内存上限。`dmesg` 里的 Out of memory 是节点自己在杀进程。CPU 高但延迟和错误率都正常时，先记下，不把它当成这次故障的原因。

依赖都正常、只有新版本变慢，就回滚镜像，再对这条路由做剖析。回滚解决不了数据库里已经变差的执行计划，那种要单独处理 SQL。

## 12. 云平台

云把机器、网络、负载均衡和托管数据服务按 API 提供出来。区域是地理位置上的一组数据中心，可用区是区域内电力和网络独立的一块。同可用区延迟低，一台可用区的故障不会直接拆掉另一台。跨区域延迟高一个数量级，用来做容灾，不用来做同步调用。

应用无状态，可以放在任一可用区。状态放在托管的数据库、缓存和对象存储里，由这些服务自己做多可用区复制。Python 进程里不保存要跨请求保留的数据，上传的文件进对象存储，会话进 Redis 或做成签名令牌。

### 网络和入口

VPC 是一块隔离的私有网络。子网按可用区放，应用子网和数据子网分开。安全组是有状态的防火墙，最小权限打开：入口只接受负载均衡的流量，数据库只接受应用安全组，管理端口不对公网开放。出网走 NAT，实例不必带公网地址。

负载均衡放在至少两个可用区。健康检查打就绪接口，失败阈值和 Kubernetes 的探针错开一点，避免同一瞬间两边一起摘除。TLS 在负载均衡上终止。静态资源和上传文件走对象存储加 CDN，应用只签发上传地址或回源，不在 Pod 的磁盘上存用户文件。

域名解析到负载均衡。内部服务用云的内网 DNS 或 Kubernetes 的 Service，不把内部地址写死成 IP。IP 在扩缩容和故障转移时会变。

### 托管数据服务

关系库用多可用区的主备。应用写主、读可以走只读实例，读己之写的查询留在主上。备份自动做，恢复时间要试过。参数和前面 MySQL 那一节一致：`utf8mb4`、`ROW`、提交时刷 redo 和 binlog。连接数按所有应用副本的池子加起来设，托管实例的最大连接数是选规格时的一个上限。

缓存用托管 Redis，持久化和淘汰策略按用途设。主从切换会有短暂停写，客户端用哨兵或集群协议重新发现主，地址不写死。内存打满会触发淘汰或拒绝写，监控 `maxmemory` 的使用率。

对象存储按桶划分权限。应用用角色拿到临时凭证，不把长期密钥放进镜像或环境变量文件。私有桶通过短时签名 URL 给浏览器上传或下载。桶可以跨区域复制，用来做备份，复制有延迟。

消息队列如果用云上的托管 Kafka 或 RocketMQ，投递语义和自建相同。换的是磁盘、副本和扩分区由平台做。积压、幂等和死信仍是应用的责任。

### 计算和发布

容器服务跑在 Kubernetes 上。节点组分布在多个可用区，Pod 的拓扑约束让同一 Deployment 的副本不要全挤在一个可用区。`topologySpreadConstraints` 按可用区打散。一个可用区不可用时，另一个区的副本还在，配合 PDB 和至少两个副本。

发布用不可变镜像。构建在流水线里完成，集群只拉取。回滚是把 Deployment 的镜像标签指回上一个提交。数据库迁移作为发布前的 Job，并且向后兼容：先加列和双写，再切读，再停旧列。先做不兼容的 DDL 再滚动应用，滚动的中途旧代码会写失败。

配置和密钥放在平台的密钥管理或 Kubernetes Secret 里，由卷挂进容器。环境变量适合非机密的开关。密钥进了环境变量就会出现在崩溃转储和 `/proc` 里，挂成文件、只给进程读，范围更小。

自动扩缩看饱和度，不看时刻。定时扩容用在知道脉冲何时到来的场景，例如活动开始前把秒杀的副本拉起来，HPA 在脉冲已经打进来之后才反应。缩容设稳定窗口，避免 RSS 还没下来就再扩一轮。

成本按三个数看：副本是不是远高于实际 QPS，日志和追踪是不是全量采集，跨可用区流量是不是因为把数据库和所有应用放在了不同的区。同可用区优先放同一组会互相调用的服务。规格从能撑住连接数和内存的最小档开始，Python 进程吃内存的方式在操作系统那一节已经说过。

### 权限和故障

人和服务都用角色，不用共享的长期密钥。流水线发布用的角色只能推指定仓库和滚动指定命名空间。应用的角色只能访问自己的桶和自己的库账号。人的排障角色默认可读，写生产要单独提升，并留下审计。

可用区故障时，负载均衡把流量送到剩下的区，数据库切到备用区。应用要能在写失败时重试幂等请求，并在连接被重置后重建池里的连接。`pool_pre_ping` 在这种切换后用得上。区域级故障靠另一个区域的数据和只读或降级后的入口，切换是事先演练过的运行手册，不是故障发生时再想。

多租户如果跑在同一个集群里，用命名空间、NetworkPolicy 和资源配额分开。一个租户的请求打满节点，会让同节点的其他 Pod 被节流或驱逐。重要服务用独立的节点组。

## 13. 安全底线

鉴权放在网关，授权放在资源上。网关证明「你是谁」。订单服务证明「这行是你的」。两件事都做，只做前面那件，换一个订单 id 就能读到别人的数据。

### 查询和越权

SQL 的值走绑定参数。SQLAlchemy 的 `text()` 配 `:id` 这种占位符，驱动负责转义。用 f-string 把路径参数拼进 SQL，解析器会把用户的引号当成语法。`IN` 列表用 SQLAlchemy 的展开绑定，不把一串 id 连成一段文本。

ORM 挡不住越权。`session.get(Order, order_id)` 只要主键存在就返回。查询条件里带上当前用户，用户 id 来自网关写入的头，不来自正文或查询串：

```python
stmt = select(Order).where(Order.id == order_id, Order.user_id == user_id)
order = (await session.execute(stmt)).scalar_one_or_none()
if order is None:
    raise HTTPException(status_code=404)
```

不存在和不属于当前用户都返回 404，避免用 403 告诉对方这个 id 是有主的。管理接口走单独的角色和路由，不在普通接口上多接一个 `user_id` 参数。列表接口同样按用户过滤，分页游标里也不要信任客户端传来的别人的主键范围。

改状态的接口带上登录态里的用户，再校验这条资源当前允许这个动作。只校验「登录过」等于水平越权。

### 密码和令牌

密码只存单向哈希。用 argon2id 或 bcrypt，把一次校验调到几十毫秒，成本参数随机器更新。SHA256、MD5 可以穷举，不能当密码哈希。每个密码自己的盐由算法生成，存在哈希结果里。校验用库提供的函数，它按固定时间比较，避免用耗时差异试出正确密码。

登录失败和账号不存在返回同一句话。日志里不写密码、验证码和完整令牌。令牌的签发、刷新和注销按微服务那一节的做法。内部服务之间用单独的身份，不把用户的访问令牌转发到和这次请求无关的下游。

### 上传和向外的请求

上传限制大小，先看 `Content-Length`，再限制实际读到的字节数，避免只改头就传进一个大文件。文件名由服务端生成，用户提供的文件名只做下载时的展示，并且去掉路径和换行，避免盖掉别的对象或注入响应头。类型用文件内容判断，不信客户端声明的 `Content-Type`。对象放在私有桶，下载用短时签名 URL。桶不允许当网站执行。业务 Pod 的磁盘不留用户文件。

服务如果要按用户给的地址去拉取，就有 SSRF。地址先解析成 IP，再判断是不是回环、链路本地、私网和云元数据地址 `169.254.169.254`。不在允许的域名里就拒绝。重定向要逐跳重新做这个检查，攻击者会用一个公网地址 302 到内网。`httpx` 的超时和重定向次数都设上。能用固定的上游就不要接收任意 URL。

调试路由、交互式文档和默认管理端口在生产关掉，或者只对内网和单独的身份开放。错误响应不带栈和 SQL。密钥按云平台那一节，用角色的临时凭证，不进镜像。

## 开发流程

前面各节讲一条请求怎么走完。这一节讲这份代码怎么从几个人的笔记本变成线上还能退回去的版本。例子是图书馆：登录、查书、借书、还书，书目和借阅记录在 MySQL。缓存、会话、主从、队列、网关和编排的机制已经写在对应的节里。这里定它们出现的顺序，以及哪一步会把别人的工作盖掉、哪一步会让全校一起借不了书。

### 版本控制

几个人同时改登录、查书、借书、还书。把文件发到群里，后传到的那份会盖掉先传到的，也看不出借期是谁从 14 改成了 30。Git 管的是整个工作树。一次提交是这一刻全部文件的快照，再加上指向父提交的指针。分支是一个可以移动的名字，指着某一次提交。`git diff` 看工作区和当前提交差了哪几行。`git log -p`，或者两次提交之间的 diff，看历史里具体改了什么。把分支指回从前某一次提交，工作树回到那时的快照。

远程仓库是大家共用的那一份。改完在本地提交，再推上去，别人从远程拉。三个人用的是同一条历史。

`main` 上只放能编译、测试能过、可以拿去部署的快照。借书和还书各自从 `main` 拉出分支。功能要写几天，当天只写了一半，就留在自己的分支上。半成品推进 `main`，别人一拉，整个程序跑不起来。Git 把每条分支上的提交按父指针串起来。两条分支从同一次提交分出去，之后各自追加。

写完用 merge 收回 `main`。Git 从当初分叉的那次提交起，把两边末端的快照合成一次新的合并提交。两边改的是不同文件，自动合成。两边改了同一处，例如借期一边写成 14 天、一边写成 30 天，合并停住，冲突标在文件里。人改完、重新提交，这次合并才算完成。

rebase 把当前分支上分叉之后的提交摘下来，接到目标分支现在的末端后面重放。历史看起来是一条直线，分叉点不再出现在图上。个人分支还没被别人拿去接着做时，用 rebase 跟上 `main`，冲突先在自己这边解决。已经推送到公共分支、队友拉过的提交不再 rebase。重放会改掉提交编号，队友本地的历史对不上，下一步就是强制推送。`main` 上已经存在的提交同样不再变基。收进 `main` 用 merge，冲突留在这一次合并里。仓库规则写明这一点。有人用 rebase 收、有人用 merge 收，历史会变成两种形状。

### 评审和持续集成

`main` 设成保护分支，不能直接推。借书的判断写反了，直接推进去，下一次发布全校都借不了。改动从自己的分支提起 Pull Request。自建的 GitLab 上这一步叫 Merge Request。至少一名队友看过才能合并。人看的是库存不足、重复提交、还书时这本书根本没借出，这些边界会不会漏。

每次推送和每次提起评审，流水线跑同一套检查，没过就不能合并。`pytest` 用 `httpx.ASGITransport` 打应用，依赖用 `dependency_overrides` 换成假实现。迁移和真实 SQL 放在单独的集成测试里打测试库。镜像按锁文件安装，标签用这次提交的 git 编号，不把 `latest` 当唯一标识。

预发和生产用同一份镜像，只换配置和连接的库。在预发重新编译，两边就不是同一次提交，评审看过的代码和生产跑的代码会岔开。预发用测试数据，或只放隔离的流量。在预发把借书、还书、库存不足和重复提交走一遍，再允许进入生产。

### 从一台机器到多份实例

笔记本上的地址，别的同学连不到。先放到一台常年开着的云服务器上。校园内网里专门对外响应的那台机器，是同一种角色。一台的 CPU 满了，或者这台宕了整个馆都停，就再跑几份相同的程序。一台物理机上可以跑多份，各自有自己的 CPU 和内存限额。口头说的加机器，和在同一台上加实例，都是水平扩展：用更多份相同的程序分担请求。

前面加一层反向代理。对外一个地址，按算法把请求分到后面的实例，实例健康检查失败就从名单里摘掉，拿不到正常回复就停止把新请求打过去。它把后端实例的真实地址藏在后面。正向代理站在客户端这一侧，替客户端去访问外面。反向代理站在服务这一侧，替服务接收外面进来的请求。四层和七层怎么转发，在负载均衡那一节。

实例一多，登录态不能放在某一台的内存里。学生在第一台登录，下一跳被分到第二台，第二台的内存里没有这个会话，学生就被当成没登录。会话编号和学号放进 Redis，每台都按同一个编号去取。Cookie、过期和注销在登录态那一节。

查书远多于借书和还书。读可以打从库，写只打主库。主库把日志送到从库需要时间。学生刚还完最后一本，立刻查从库，仍可能看到未还。这种读打主库。热门教材的书目放进 Redis，没命中再查 MySQL，并设过期时间。不存在的书号、同一批 key 同时过期、更新之后删缓存，按缓存那一节做。借书和还书改的是库存和借阅记录，走主库事务。Redis 里的数字只是加速用的副本。对不上时以 MySQL 为准，由对账把缓存盖回去。

全网每一份从库和每一份缓存都要立刻看到这次还书，就要等复制和缓存失效都完成再返回，延迟会抬上去。允许从库和缓存有短暂延迟，查书才能留在低时延这一侧。借还这种要强一致的写，走主库事务。这个选择就是 CAP 和 PACELC 在这条业务上的落点，名词在分布式理论那一节。

### 同一份镜像上线

评审和检查都过了，还不能在生产机器上手工拷文件。各台机器的运行时、依赖和配置会漂：一台的语言版本和另一台不一样，同一份代码在这边能跑、在那边启动失败。镜像把程序、依赖和运行时打在一起。容器共享宿主机的内核，不自带一整套操作系统，所以比虚拟机轻，启动是秒级。虚拟机是在一台物理机上用虚拟化切出的一整台机器，自己有内核。依赖和虚拟环境怎么进镜像，在 Docker 那一节。

持续交付是：`main` 上每一份通过检查的提交都能打成镜像，放到预发，差一次人工确认就能进生产。持续部署是确认这一步也交给流水线。借还会改库存，生产由人点。点下去之后，十几个实例同时换成新镜像，一次错误判断会让全校一起失败。先让负载均衡把一小部分请求切过去，看借书失败率和延迟。稳了再一批一批放大。不对就把流量指回上一份镜像。回滚改的是流量指向的镜像标签。线上机器上不改判断条件。滚动更新先起一个新副本、就绪后再停一个旧的，`maxUnavailable: 0`、`maxSurge: 1`，在探针、资源和发布那一节。灰度决定切多少流量，滚动决定怎么换副本。新副本先接一小部分，确认后再按滚动把其余副本换掉。

### 什么时候拆服务

一个进程里，还书的错误发布会把查书一起换掉，借书忙的时候电子书也得跟着扩容。一个有问题的依赖把进程打满，登录和借书一起停。边界清楚、发布和扩容的节奏已经不同，再拆成各自拥有数据的服务。用户、账号和登录会话收成所有学校共用的一块。每个团队发自己的版本。

对外给浏览器和手机的接口继续用 HTTP 和 JSON。对内字段稳定、调用密的，用 IDL 和 gRPC：先加字段，旧客户端按字段号跳过不认识的字段。连接、序列化和超时由框架处理。契约、超时、重试、熔断和舱壁在微服务那一节。拆开之后一次借书要跨网络。网络会丢、会慢、会重复，这些保护跟着拆分一起做。

### 编排、入口和故障

几十个服务、每个多份实例之后，人已经算不清新容器该放哪台还有空闲的机器上。Kubernetes 要的是期望状态：借阅服务要 50 个副本。控制面把容器补到这个数。半夜有容器停了，或者某台机器坏了，它把副本再拉回来。开学前把副本数调高，闲下来再调低。声明式的对象、探针和滚动更新在 Docker 与 Kubernetes 那一节。

实例的地址会变。借阅服务把用户服务的 IP 写进配置文件，扩容或重启之后这份配置立刻过期。服务发现给出一份还能连的地址：实例带着心跳或健康检查登记，调用方查这份名单，并在本地缓存一小段时间。Kubernetes 里这份工作由 Service 和 CoreDNS 做。虚拟机或混部再用 etcd、Nacos 或 Consul。注册中心和 Redis 一样，是业务旁边的基础设施。注册中心自己停了，发现就停。选一套。Service 和 Nacos 各维护一份名单时，调用方会拿到两套地址。

调用链上的保护按这个顺序看：先从名单里挑一个实例，连接放进连接池，请求设超时，只有可以重复执行的操作才重试，失败比例高了就熔断，慢调用放进单独的并发额度里。推荐服务卡死时，主页面先不展示推荐，借书仍然能做完。熔断过一段时间进入半开，放少量请求试探，成功再合上，失败继续断开。这些细节在同步调用上的保护那一节。

外面进来的不再只是浏览器。后端已经是几十个服务。调用方记不住每个服务的内部地址，脚本也不能直接打到借阅服务上刷座位。网关是外部请求进集群的统一入口：按路径把借书转到借阅服务，把查书转到书目服务；TLS 在这里结束；登录态在这里验一次，再把用户 id 传给后面。限流也放在这里，把多余的流量挡在业务进程之外。网关自己要有多份，单份网关停了，整个入口就停。进来之后，服务之间的调用走集群内部的发现，不再绕回网关。路由、鉴权和限流在网关、配置与发现那一节。

### 异步、观测，以及网格要不要上

借书在用户服务确认没欠费、库存也扣完之后，这件事本身已经做完。通知、统计、推荐可以晚几秒。把它们留在同一次请求里，通知服务一停，借书接口就报错。请求一多，当场拉起的任务会把下游打满。进程重启，还在内存里的任务就没了。以后再加积分，借阅服务还得再改一次。

消息队列放在借阅服务外面。借阅服务往队列里写一条借书成功的事件，写成功就可以返回。通知、统计各自订阅。队列把一瞬间的高峰先接住，消费端按自己的速度处理。Kafka 和 RocketMQ 把这条消息复制到多台机器上。坏掉一台，已经确认的消息还在。投递是至少一次，同一条提醒可能再来，消费端按借阅记录的主键做成幂等。可靠、削峰和这条解耦在消息队列那一节。副本怎么确认，在 Kafka 那一节。

组件多了之后，学生借书偶尔失败，已经不能在一台机器上打断点。三份信号一起留。指标看流量、耗时和错误率，灰度时盯的就是借书失败率。日志记扣库存失败、推送异常，并且集中收集，不留在容器被删掉就消失的本地盘上。追踪给一次请求一个编号，从网关穿过借阅、数据库，进消息队列再出来，都带着它。拿这个编号才能看出死在哪一环。三份信号在可观测性那一节。

服务网格是再往后的一步。Java、Go、Python 混在一起，超时、重试、熔断和链路加密若都写在各自的框架里，改一个超时就要每种语言发一版。网格在每个业务容器旁边放一个代理，进出的流量先经过它。这些代理是数据面。另一套控制面不碰具体请求，把超时和限流的规则推给全部代理。接口生成和语言内部的序列化仍然留在业务进程里。每一次调用多一跳，延迟、CPU 和内存都会上去。几十个服务、语言还没混到框架管不过来时，框架里的保护就够。网格换来的是治理逻辑可以单独发版。边车的重试和应用自己的重试叠在一起会相乘，这一点在同步调用上的保护那一节。

| 阶段 | 图书馆里先碰到的事 | 往下看 |
| --- | --- | --- |
| 几个人改同一份代码 | 借书、还书分分支，`main` 只留能运行的快照 | 本节的版本控制和评审 |
| 一台机器顶不住 | 多实例、反向代理，会话放进 Redis | 负载均衡、登录态 |
| 数据库顶不住 | 读可以从库，热门书目进缓存，借还走主库 | MySQL 复制、缓存 |
| 上线一次换光 | 同一份镜像，先切一小部分流量 | Docker，探针、资源和发布 |
| 一个程序互相拖累 | 按业务拆开，各自发布和扩容 | 微服务 |
| 容器该放哪台机器 | 声明副本数，地址用服务发现 | Kubernetes，网关、配置与发现 |
| 借书成功后还要通知 | 事件进队列，消费端按主键幂等 | 消息队列 |
| 偶尔失败查不到死在哪 | 同一个请求编号穿过日志、指标和追踪 | 可观测性 |

这一节用图书馆把顺序串起来。前面各节的例子仍是订单。两条业务用的是同一套规则：保护分支、同一份镜像、写走主库、允许读有短暂延迟、跨服务的通知走队列。
