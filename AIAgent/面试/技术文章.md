## 一次请求实际在跑什么

模型每步只做一件事：读当前上下文，输出一段文本，或者输出一个带参数的工具调用。循环、分支、记忆、权限都在模型外面。这层外面的程序就是 harness。LangGraph、自研 loop、工作流引擎只是这层程序的不同写法。

一轮可以写成：

```text
state = load(thread_id)
while state.step < budget and not state.done:
    msg = model(assemble(state))
    if msg.tool_calls:
        for call in msg.tool_calls:
            if call.needs_approval:
                checkpoint(state); return WAITING
            result = tools.invoke(call)
            state.append(result)
    else:
        state.append(msg)
        if should_stop(state, msg):
            state.done = True
    state.step += 1
    checkpoint(state)
```

`assemble` 决定模型这一步看见什么。`checkpoint` 决定进程死后从哪继续。`tools.invoke` 决定副作用是否真的发生。评测看的是这三处的记录，不是最后一段看起来通顺的话。

ReAct（Yao 等，ICLR 2023）把一步拆成 Thought、Action、Observation。Thought 是给下一步约束用的中间文本，Action 是工具名加参数，Observation 是工具返回、原样塞回上下文。生产系统里 Thought 常常不展示给用户，但要进 trace。没有 Observation 回写，模型下一轮会重复调用同一个工具。

和「链」的差别在于边可以回到前面的节点。链是 A→B→C。Agent 是「调用工具 → 看结果 → 再决定叫不叫、叫哪个」。检索不够再查一次、参数错了改一次、人点了确认再往下，都是这条回边。回边必须有步数、时长和重复调用上限，否则它会一直转。

## Harness

### 状态里要有什么

一个 thread 的状态至少包括：

- 对话消息和工具结果，按顺序
- 当前计划或阶段（澄清、检索、执行、等待确认、收束）
- 未完成的工具调用和它的幂等键
- 已批准或已拒绝的动作
- 步数、已用 token、已用时长、工具调用次数
- 本轮任务目标。目标被压缩掉之后，模型会改去做别的事

检查点要在副作用提交之后写，或者把「工具已发出、结果未回」单独标成 in-flight。恢复时先看 in-flight：已经写过库的调用用幂等键取回结果，不再执行第二次。只存聊天记录、不存 in-flight，重启后会重复发券、重复下单、重复发邮件。

人的确认是一次中断，不是线程睡在那里。流程把状态写成 `WAITING`，请求先返回。人点确认后用同一个 `thread_id` 再进入循环，从中断的那条边继续。确认的内容要哈希。Etcetera 的预览指纹就是这件事：确认时看到的邮件正文哈希，必须等于真正 SMTP 发出去的正文哈希。中间若又被模型改写过，这次发送作废。

长任务不要绑在 Web 进程上。Web 负责收请求和推 SSE，Worker 拿租约执行。租约过期，另一台 Worker 根据已落库的步骤接着跑。心跳只证明进程还活着，步骤表才证明做到了哪一步。SSE 断线后客户端拿最后一条事件 id 来补，不靠模型把进度重讲一遍。

### 预算

预算要分成几把尺子，共用一把「最多 20 步」会误伤。

| 尺子 | 挡住什么 |
|---|---|
| 步数 | 计划—执行死循环 |
| 工具调用次数 | 同一工具反复试错 |
| 墙钟时间 | 外部 API 挂起 |
| 单次运行 token | 上下文被检索结果撑满 |
| 子 Agent 深度 | 委派套委派 |
| 金额 | 重模型被简单子任务打满 |

子 Agent 要有自己的预算，并且默认只读。父 Agent 的写权限不能继承下去。深度超过三层之后，失败已经很难归因：不知道是父计划错了，还是子工具错了，还是子子的检索空了。Etcetera 把树深卡在三层并禁止再嵌套，是为了让 trace 还能被人读完。

### 压缩

窗口满了不能从前面直接删。要留的是：任务目标、已经做出的决定、未关闭的错误、关键工具结果的摘要、仍需遵守的约束。可以丢掉的是：被后来结果覆盖的中间检索、重复的报错、已经合并进摘要的早期闲聊。

压缩本身是一次模型调用，它会丢细节，也会把推测写进摘要。所以摘要要带「这些事实来自哪次工具结果」。下一轮如果要引用数字，回到原始工具结果，不引用摘要里的数字。刘稔远把多轮压成一条独立请求，是更硬的一种压缩：规划模型只看补全后的当前句，历史由规则状态机在外面拿着。这样历史里的闲聊不会改工具链，代价是状态机没覆盖的指代会补错。

Prompt cache 只对稳定前缀生效。系统提示、工具 schema、常驻项目摘要放在最前面，并且少改。用户这句话、检索片段、工具结果放在后面。每轮都重写系统提示，缓存命中率会掉，首 token 时间和账单一起上去。

### 失败要分型

| 类型 | 现象 | 处理 |
|---|---|---|
| 模型输出坏了 | JSON 缺字段、工具名不存在 | 把校验错误回给模型，限一次。不要把整段生成扔掉重来 |
| 工具超时或 5xx | 结果为空或连接重置 | 同一幂等键重试。写操作先查上次是否已经成功 |
| 参数合法但业务拒绝 | 库存不足、无权限 | 把拒绝原因回给模型，让它改计划或问人。盲重试没有用 |
| 检索空 | 召回 0 条 | 改写查询或明确拒答。不要用参数知识把答案补上 |
| 策略冲突 | 模型要做策略禁止的事 | 工具层直接拒绝，不靠提示词恳求 |

「按失败类型重试」指的是这张表。所有错误都再试三次，会把「无权限」打成三次相同的拒绝，并把写操作打成三次提交。

## 工具

### 模型怎么发出一次调用

工具以 schema 放进上下文：名字、自然语言说明、参数的 JSON Schema。模型输出结构化的 `tool_name` 和参数对象。约束解码可以在生成时就禁止不合法的 JSON；做不到约束解码时，用一次校验加一次修复。修复时把校验器的错误信息给模型，例如「`date` 必须是 YYYY-MM-DD」，不要只说「请输出合法 JSON」。

Schema 的说明文字是给模型做选择用的，不是给人类看的文档缩写。两个工具都叫「查询」，模型就会混。说明里写清：什么时候用、什么时候不用、参数的单位、返回里哪些字段可信。参数例子放一个真实的，放一个边界的。例子里的假 id 会被模型照抄进生产调用，例子要用显然的占位符。

### 工具多了以后怎么选

把 100 个工具的 schema 全放进提示，有三笔账：token、选择错误、缓存失效（schema 一改，前缀全变）。漏斗是：

```text
全部工具
  → 意图或查询，先收成候选 40（向量 + BM25 + RRF）
  → 交叉编码器重排，留 20
  → 规划模型只看见 10，并输出有序工具链
```

召回阶段用双塔或 BM25，因为要对全库做。重排只对这 40 个做，因为交叉编码器要为每对 (查询, 工具说明) 跑一次前向。规划阶段再缩小，是因为模型在十几个相似工具之间会乱序。

「Top-10 全召回」的定义要说死：这条请求依赖的工具集合是 G，前 10 名集合是 T，成功条件是 G ⊆ T。普通 Recall@10 在有多个相关工具时会把「找回了一部分」算成部分分。工具链只要缺一个，后面的参数就接不上，所以这里用集合包含，不用部分分。

负例要分型，不能只随机抽。随机负例太好分，模型学不会「查库存」和「查在途」的差别。类型化负例是同一业务域、名字相近、参数略不同的工具。刘稔远用 7 万正对加 9.6 万这种负例，就是在买这个区分度。

另一条路是分组披露：先分类意图，再只注入该意图的工具组。张利娜的 `INTENT_TOOL_GROUPS` 是这条路。它省掉一次大规模检索，代价是分类错了，后面整组工具都错。分类器可以用小模型甚至规则。14 个意图里 13 个用规则、1 个留给 LLM，是因为规则能覆盖的句子不应该付一次大模型调用。规则没覆盖的长句再交给模型。

### MCP、函数调用、Skill 各管一层

函数调用是模型输出格式：这一步要执行哪个函数、参数是什么。

MCP 是工具提供方和 Agent 宿主之间的协议。宿主里面有客户端，外面有服务器。服务器声明自己有哪些工具、资源和提示模板。传输可以是本机 stdio，也可以是 HTTP。把存量 HTTP 服务收成 MCP Server，是为了让多个 Agent 共用同一份 schema、同一套错误形状和同一套鉴权，而不是每个 Agent 各写一套 requests。王艺辉的 MCPBridge 做的就是这层适配：发现、填参、错误回传、上下文补全。

Skill 是给模型的操作说明，通常包含：何时启用、步骤、允许用哪些工具、输出长什么样。它不是又一个可执行函数。戴雨欣每次调用前按角色过滤系统 Skill 和用户 Skill，是因为 Skill 文本进了上下文就等于给了模型一套行为；不该看的 Skill 不要出现在窗口里。

三层叠在一起是：Skill 决定「这类事怎么做」，MCP 决定「这些函数从哪来、长什么样」，函数调用决定「这一步具体执行哪一个」。Registry 管生命周期：这个工具现在启用吗、超时多少、配额多少、失败了降级到哪个、调用记到哪条审计。新工具注册进来就能被选到，不用改 Agent 的装配代码。

### 读和写

读工具可以让模型直接调用。写工具在服务端分成两段：先 `preview`，返回将要发生的变更；人确认后 `commit`，并且 commit 必须带 preview 的哈希。工具实现里检查当前状态仍允许这个变更，再执行。只在聊天界面上弹一个「确定」按钮，模型可以在按钮之后再改参数。

SQL 类工具在数据库角色上就去掉写权限。提示词里写「只能 SELECT」挡不住模型输出 `DELETE`。库用户本身没有写权限，这条语句会在执行层失败。

幂等键用业务单号，不用随机 UUID 当唯一依据。重试时带着同一个单号，服务返回上一次的结果。支付、发货、发券、发邮件都走这条。梁慧的「验签之后幂等发货」和郭靖修过的「核销失败必须把并发占用放回去」，都是写工具的同一类账：失败路径要把占用和副作用一起结清。

## 上下文和记忆

### 这一轮窗口里的顺序

从前往后通常是：

1. 系统约束：角色、拒答条件、输出格式、安全规则
2. 工具 schema（这一轮真正可能用到的那一组）
3. 常驻记忆：项目摘要、已经批准的规则，短，且很少变
4. 检索到的证据，带 id
5. 近期对话和本轮工具结果
6. 用户当前这句话

第 3 段放前面是为了缓存。第 4 段必须带 id，后面的引用才有东西可指。第 5 段里如果有未压缩的失败尝试，模型会模仿那些失败。压缩时优先收掉失败尝试，留下最后一次错误原因。

「Lost in the middle」指的是：很长上下文里，模型对开头和结尾更敏感，中间的证据容易被忽略。所以和当前问题最相关的几段放在证据区的首尾，不要按数据库返回顺序原样铺开。

### 四种记忆不要写成一个向量库

| 种类 | 内容 | 写入时机 | 读入方式 |
|---|---|---|---|
| 工作记忆 | 这一轮的目标和中间结果 | 每步 | 全量留在状态里，直到本轮结束 |
| 情景记忆 | 发生过的事：哪次对话、哪个工具、人怎么改的 | 回合结束或工具返回后 | 按当前问题检索，不每轮全塞 |
| 语义记忆 | 稳定事实：用户偏好、项目约定、术语表 | 被人确认之后 | 常驻一小段，或按实体查 |
| 程序记忆 | 怎么做一类事 | 人把做法收成 Skill 或规则 | 按意图加载，不进每轮闲聊 |

李鹏斌写的 perceptual 是另一种：外部感知的原始结果，例如检索片段、网页、传感器。它应该能删、能过期。和语义记忆混在一个表里，过期的网页会变成「事实」。

常驻摘要每轮都放进提示，所以它必须短，而且只放已经确认的规则。历史事件放附录，用时再查。戴雨欣的 MEMORY / HISTORY 就是这个分法。每轮把全部历史做一次向量检索，既贵，又会把不相关的旧决定注入当前任务。

矛盾的处理要有版本。新规则覆盖旧规则时，旧规则留在审计里，不要留在常驻摘要里。两个摘要同时说「默认仓库是 A」和「默认仓库是 B」，模型会各用一次。

人的修改要过阈值再变成规则。一次改分可能是个案。同一个改动在多个项目里出现，理由也足够具体，才归纳成一条，并且先在回归集上跑过，再对指定项目灰度。这是 Etcetera 的做法。把每一次点击都微调进模型，会把个案写死，而且无法按项目回滚。

### 图什么时候有用

实体之间要跳两跳以上，向量邻居不够。例子：这份保单引用了哪个产品、产品的哪条条款、条款对应哪份 OCR。图上存的是这些边。查询可以是「从当前产品出发，沿条款边取出原文」。冯威的知识图谱、李鹏斌用 Neo4j 存攻击路径，都是把「关系」从文本里提出来单独存。图抽错了边，多跳会把错误放大，所以抽取结果要能回链到原句，不能只存三元组。

## RAG

### 入库

文档先变成稳定的块，再嵌入。块要带着来源：文档 id、章节、页码或时间轴、版本。王长玉把课程答案指到章节和时间点，王艺辉把产品材料指回原文，靠的都是这个坐标，不是向量本身。

切分按结构，不按固定字数一刀切。条款、标题、表格、代码块是自然边界。一块太大，嵌入被无关句子稀释；一块太小，检索命中了也回答不了。常见做法是小块用来召回，命中后把所属的父章节送给模型。父章节仍然要有长度上限。

增量用内容哈希。哈希没变的块不重新嵌入。冯威的内容哈希增量，避免整库重算。版本变了，旧块作废而不是覆盖到无记录，否则引用会指向新文本里已经不存在的句子。

### 查询侧

用户原句经常不能直接拿去搜。多轮里的「那个」「继续」「按刚才的条件」要先补全。补全结果单独记在 trace 里。补全错了，后面的高召回没有意义，排障时要能看到改写前后的两句话。

硬过滤在打分之前做。租户、权限、目的地、语种、时间范围，都是过滤条件。把「别的目的地的段落」交给重排模型慢慢降权，它们仍可能因为词面相似排进前几。李鹏斌先按目的地过滤，跨目的地污染可以从十几条变成零。权限过滤更必须在打分前：无权限的文档不应该进入候选，否则重排或生成阶段仍可能把它的句子漏进答案。

### 两路分数为什么不能直接加

BM25 大致是：对查询里的每个词，用「这个词在文档里有多密」乘「这个词在整个库里有多稀」。文档长度会做归一，避免长文档只因为词多就总排前面。它擅长订单号、错误码、专有名词、很少出现的术语。

稠密检索把查询和文档都变成一个向量，用内积或余弦排序。它擅长「说法不同但意思接近」。它不擅长精确符号：用户要 `ERR_2401`，向量可能找回一篇讲错误处理的文章。

两路的分数单位不同，不能因为都叫 score 就相加。RRF 只用名次。文档在某一路排第 r 名，得 `1/(k+r)`。几路的分加起来。k 取 60 时，第 1 名大约是 1/61，第 10 名大约是 1/70，名次的影响是平缓的，一条路里的异常高分不会压过另一路。Cormack 等 2009 年的实验用的就是这种融合。

交叉编码器把查询和文档拼成一条输入，输出一个相关分。它看得到词和词的交互，所以比双塔准，但每对都要算一次，只能用于前几十条。ColBERT 折中：查询和文档离线或在线各算一串 token 向量；查询的每个 token 在文档 token 里找最大内积，再对查询 token 平均。文档向量可以预先算好。它比单个 CLS 向量细，比交叉编码器便宜。

BGE-M3（Chen 等，ACL Findings 2024，arXiv:2402.03216）用一个编码器同时给出这三种分：

- 稠密：CLS 向量归一化后做内积
- 词法：每个 token 一个非负权重，查询和文档共有的 token 把两边权重相乘再求和
- 多向量：和 ColBERT 一样的晚交互

训练时三路分数加起来当老师信号，再蒸馏回每一路。所以它可以只部署稠密一路，也可以三路一起融合。BGE-Reranker 是另一个交叉编码器模型，用来替换或补上重排那一步。简历里写「BGE-M3 + BGE-Reranker」是「召回用 M3，重排用 Reranker」，两步都写清楚才算数。

### 生成之后还要查一次

检索分高不代表句子被证据支撑。生成后再做一次主张级检查：把答案拆成主张，每条主张必须能指到一块证据，并且证据蕴含主张，而不是只共享几个词。NLI 模型可以把这对句子判成蕴含、中立或矛盾。矛盾和中立的主张删掉，或者触发一次有界的补查。

补查要有上限。判断证据不够 → 改写查询 → 再召回一次 → 合并证据 → 生成。只允许一次，是因为第二次仍不够时，继续查通常是在重复相近查询，token 和延迟线性涨，忠实度不一定涨。李鹏斌把这个上限写成「最多一次」。

引用要落到坐标，并且坐标属于这次真正读过的块。模型可以编一个看起来像的页码。检查方法是：引用 id 必须出现在本轮工具结果里，片段文本必须能在该块中找到。谷子昂的做法更进一步：打开原始网页或 PDF，核对主张旁边确实有那句话。弱引用就换来源或改结论，不保留那句。

### 指标怎么算，以及怎么被做高

设 4 条查询，相关文档数和第一命中名次如下：

| 查询 | 相关文档数 | 前 5 名里命中几个 | 第一个相关的名次 |
|---|---|---|---|
| Q1 | 2 | 2 | 1 |
| Q2 | 2 | 1 | 3 |
| Q3 | 1 | 0 | 无 |
| Q4 | 1 | 1 | 2 |

Recall@5 = (2/2 + 1/2 + 0/1 + 1/1) / 4 = 0.625。

MRR = (1/1 + 1/3 + 0 + 1/2) / 4 = 0.458。Q3 没有命中，贡献 0，不能从平均里拿掉。拿掉未命中的查询，MRR 会被做高。

nDCG 用于相关度分档，例如「完全相关 3、部分相关 1、不相关 0」。位置 i 的增益除以 log2(i+1)，前 K 个相加得到 DCG。再除以「把相关文档按理想顺序放在最前面」得到的 IDCG。只关心第一名时看 MRR；相关文档有多个、又在乎排得靠不靠前时看 nDCG。比较两个系统时，K、相关度档位和查询集合必须相同。

引用命中率是另一件事：答案中的引用有多少能在证据块里按字符串或 id 对上。Recall@5 是 1，引用仍可能全部指向错块。两个数都要报。

下面这些改动能让指标变好看，同时让线上变差：

- 评测查询和文档用同一套措辞，稠密检索会显得特别强。真实用户会换说法。
- 不放「库里没有答案」的题。模型靠参数知识答题也会得高分。Sanjay 单列了不可答和假前提。
- 用生成结果当相关文档。那是在用模型评模型已经看见的东西。
- 改了重排却没锁住召回集合，分不清是召回变了还是重排变了。

离线比较至少锁住：同一批查询、同一份文档版本、同一套相关标注、召回深度、是否使用过滤。一次只改改写、或只改重排、或只改提示。李鹏斌用历史 trace 加人工 golden set 做这种 A/B。

## 评测

### 检索评测和任务评测是两层

检索评测问：该到的文档或工具在不在前 K。任务评测问：做完之后世界状态对不对。RAG 问答两层都要。只有检索分，可能文档对了、答案编了。只有问答分，可能答案碰巧对、依据是错的。

任务评测的一条样本要有：初始状态、用户目标、允许的工具、禁止的动作、结束时必须成立的状态、必须告诉用户的信息。τ-bench（Yao 等，arXiv:2406.12045）把这几样做成：隐藏的数据库、一组 Python 工具、一份策略文档、一个由模型扮演的用户。用户看不见工具轨迹，避免他替 Agent 把参数说完。奖励是 0/1：数据库终态和唯一正确答案一致，并且该输出的信息也在对用户的话里。部分做对仍然是 0，因为机票订错一程就是失败。

pass^k 是同一任务独立跑 k 次、全部成功的比例。如果单次成功率是 p，并且各次独立，pass^k 大约是 p 的 k 次方。p=0.8 时，pass^1=0.8，pass^4≈0.41。简历里只写平均成功率，会把「经常能成」说成「可以交付」。高风险动作用单独的 pass 率，不混进总准确率。一次越权被 99 次闲聊平均掉。

fixture 和 real 分开报。fixture 里工具是假的、模型可以是假的，用来看流程、权限和恢复。real 里才看模型会不会选错工具。李鹏斌两边都跑。只跑 fixture，上了真模型才会发现工具描述有歧义。

对照实验还要锁：harness 的 commit、工具 schema 版本、温度、最大步数、是否带记忆。每轮从一个干净状态开始。Yadeesh 加了一条：除了任务允许改的字段，别的状态必须和初始一样。否则 Agent 可以靠改无关数据「凑」到一个表面正确的结果。

开发集上调出来的提示，要在没参与调参的题上再跑。他看到的情况是开发集涨了，留出题上的失败还在。所以「我们把准确率调到了 x」这句话要带数据集的名字。

### 模型当评委

评委模型和被评模型要分开。同一模型给自己的答案打分，会偏高。评委要看证据和主张，不要看标准答案全文，否则它会按「像不像范文」打分，这就是 answer-blind。

两个稳定性指标：

- RCR：同一份输出、同一套量表，评委打两次，一致的比例。低说明量表或温度不稳，业务准确率不可信。
- ESF：在固定 checkpoint 上，评委的分数能不能复现专家的分数。低说明自动分还不能代替人。王艺辉把专家对齐做在 checkpoint 上，是为了版本一变就重新对齐，而不是永远沿用旧人的口味。

人的一致率也要抽样。Yadeesh 写 LLM judge 和人的一致率 88%，指的是在已经有人工标签的题上对过。没有这一项，judge 分只是另一个模型的意见。

线上用的是另一套：真实请求的 trace、人的点赞或改写、工具失败率、拒答率、人工接手率。离线 golden set 决定能不能发版；线上这些数决定发版之后有没有变坏。两边的题分布不同，离线涨了 5 个点，线上接手率仍可能上升。

## 多智能体

拆开的条件只有一个：子任务的上下文、工具或权限应该和父任务隔离。检索、写操作、审查放在同一个上下文里，模型会把检索到的不可信文本当成可以执行的指令，也会在审查之前就把书写掉。

审查者不要和执行者共用同一段「我想这样写」的推理。李鹏斌的 Reviewer、谷子昂的 verifier、Ahamed 的「检索 / 推理 / 校验 / 升级」分开，都是让后一阶段只看证据和产物，不看前一阶段的自我辩护。

主管加专职子 Agent 适合工具域确实不同的时候：库存、排班、邮件，各有各的 schema 和权限。不适合「一个问答拆成五个都在聊天的角色」。那样延迟按角色数相加，出了错也不知道是谁的上下文坏了。

子 Agent 返回给父 Agent 的应该是结构化结果：结论、证据 id、未解决的问题、花费。不要把子 Agent 的全部消息贴回父上下文。贴回去等于没有隔离。

辩论可以当旁路。正反双方各写一轮，综合者列出一致点和分歧，人决定接不接受。产物先落在旁边，不直接改需求或配置。戴雨欣的三轮辩论是这个结构。辩论结果直接写进生产配置，就没有人负责。

多个编码 Agent 互相发消息，要解决的是投递和身份，不是又做一个编排器。消息要带来源，防止 A 的输出被 B 当成用户指令再发回 A，造成回环。看门狗负责一方不再响应时把会话标成失败，而不是无限等。孟祥龙把「发现、投递、回复」和「任务编排」分成 HailMesh 和上层，就是这个原因。

## 模型这一侧

Agent 的延迟和账单主要来自模型调用方式，不来自业务 if。

### Prefill 和 Decode

一次请求分两段。Prefill 把整段输入并行算完，得到 KV cache，并吐出第一个 token。Decode 之后每生成一个 token，都要读已经积累的 KV。所以：

- 首 token 时间主要由输入长度决定。检索片段、工具 schema、历史都算在这里。
- 生成速度主要由输出长度和并发时的显存带宽决定。
- 长检索上下文会让每一轮都变慢，即使你只想要一句话。

流式输出改善的是用户看到第一个字的时间，不减少总计算量。工具调用那一轮通常不需要长输出，把 `max_tokens` 按这一步收紧，能避免模型在该停的时候继续写。

vLLM 用分页管理 KV cache，让多条请求共享显存、减少碎片。它不让单次生成变聪明。选型时看的是并发和显存，不是榜单分数。没有 GPU 时换成本机能跑的推理后端，接口保持 OpenAI 兼容，上面的 Agent 代码不用分叉。Bingo 按机器在 vLLM 和 MLX 之间换，换的是这一层。

### 路由

简单句走小模型或规则，长推理、低资源语言、工具链规划走大模型。路由本身必须便宜，否则省下的钱被路由器吃掉。可用的信号：意图分类的置信度、查询长度、是否含有代码或数字、检索分数是否过低。

刘稔远用查询向量和领域原型的距离做域划分，再用模型内部表示估计难度。张利娜按语种和句子复杂度选模。Aman 按任务槽位：编排用大模型，子任务用小模型。三套都是同一原则：贵模型只处理路由器拿不准或明确标成难的那一部分。

路由要有兜底。小模型置信度低，或者工具调用校验失败，升级到大模型一次。升级也计入预算，避免来回跳。

### 什么时候改权重

能用检索、规则、提示解决的，先不要微调。微调把行为写进权重，回滚要比换一份提示慢，而且需要和当前基座版本绑在一起。

适合微调的是稳定、可标注、提示怎么写都不够的映射：意图分类、固定候选集上的工具链、领域用词。刘稔远把意图放在 0.6B 的 LoRA 上，是因为这是一个封闭分类，小模型够用，还更快。工具链用 8B 的 SFT，是因为要输出有顺序的多步调用，分类器只够做第一步。

LoRA 不改原权重 W。旁边加一个低秩支路，输出是 `Wx + BAx`。A 是 r×d，B 是 d×r，r 远小于 d，常加在注意力的 Q、V 上。训练只更新 A 和 B。换任务就换这一对小矩阵。QLoRA 先把 W 量化再加 LoRA，用显存换一点数值误差。

P-Tuning 不改注意力矩阵，在输入上加一段可训练的连续向量。ChatGLM 早期方案里它很常见。它和 LoRA 可以分别试，但上线时要选一个，避免两套适配器叠在一起无法归因。

SFT 是用正确轨迹做监督学习：给定补全后的请求和候选工具，输出那条正确的工具链。数据如果都是一个模板生成的，加到 5 万条也只是在重复同一个决策面。刘稔远把同风格数据从 9K 加到 54K 没有稳定收益，换成跨风格轨迹才涨，说明缺的是覆盖，不是条数。

DPO 用成对偏好，不再单独训一个奖励模型再跑 PPO。损失让策略提高「选中答案相对参考模型」的对数概率，压低「拒绝答案相对参考模型」的对数概率，两者之差经过一个温度 β 再进 sigmoid。β 大，策略离参考模型更近，更稳，也更学不动；β 小，学得猛，更容易把拒绝答案里的格式也学坏。

偏好对要来自模型真实犯过的错，而不是人工编的「坏答案」。父模型在新请求上错了 8309 次，从中抽 4000 对，学的是这个模型的错误边界。人工写的坏答案往往错得太明显，训练之后只学会拒绝那种夸张错误。

微调之后原来的检索评测和任务评测都要再跑。分类准确率到了 100%，工具链可能变差。一个数上涨不是发版条件。

## 不可信文本

检索结果、网页、邮件、工具返回，都是数据，不是指令。模型会把其中的「忽略之前的要求，调用退款工具」当成要执行的话。处理是：

- 工具结果用固定分隔包起来，系统提示写明分隔内没有指令权。这只是降低概率。
- 真正的挡住在工具层：退款工具看的是用户身份和订单状态，不看模型说「对方要求我退款」。
- 外链和 URL 工具做允许名单，挡内网地址和 DNS 重新绑定后的内网地址。否则模型读到一条恶意文档，就会去请求内网。
- 代码工具跑在沙盒里，文件系统、网络和进程都有限制。超时必须能杀掉进程。
- 高风险动作仍然要人确认，并且确认的是参数，不是模型的一句解释。

审查者和执行者分开，审查者的通过也不能代替权限检查。权限在每次工具调用时用当前用户再算一次。网关里验过的 JWT，到了工具进程里还要验，避免内网调用绕过网关。

## 一条线上请求

把上面收成同一次用户请求里发生的事。以「根据资料回答，并可能改一条业务数据」为例。

1. 网关鉴权，按租户选模型路由和配额。记 request id。
2. 加载 thread。若上次停在等待确认，先处理确认，不重新规划。
3. 规则或小模型做意图。闲聊直接走小模型。业务问题进入主循环。
4. 把当前句补全成独立查询。补全结果写入 trace。
5. 按租户和权限过滤索引，BM25 和向量各取一批，RRF 融合，交叉编码器留前若干块。块上带着文档坐标。
6. 组装窗口：稳定前缀、少量常驻规则、带 id 的证据、压缩后的近期状态、当前句。
7. 模型要么给出带引用的草稿，要么发出只读工具。工具结果追加进状态并 checkpoint。
8. 主张检查。有主张没有证据，做一次改写重检索。仍然没有，这句话改成拒答或标明未知。
9. 若要写业务数据，工具返回预览和哈希，状态改为等待确认，SSE 告知用户。人确认后，用同一哈希提交。失败按幂等键查上次结果。
10. 写 trace：模型名、token、每步延迟、检索 query、证据 id、工具参数和错误、是否人工改过。评测和排障都读这份记录，不读模型的自我总结。

发版前用同一份 golden set 跑第 4 到第 8 步。线上用第 10 步的失败类型看要不要回滚。回滚的是提示、检索参数或适配器版本，不是去改某一条聊天记录。

## 面试里够用的口径

讲一个自己的系统时，按这条线讲，每段停在一个可以追问的机制上：

- 状态里有什么，重启后哪类副作用不会执行第二次
- 工具超过上下文时，候选是怎么从全量收到个位数的，指标是部分召回还是集合包含
- 检索过滤在打分前还是打分后，引用对的是块 id 还是模型自己写的页码
- 评测的一次成功定义是什么，同一题跑多次时看的是平均值还是全部成功
- 改的是提示和规则，还是 LoRA 权重；回滚分别怎么做

答不出其中一段，就把简历里对应的形容词收掉。留着的每句都应该能落到上面某一步。

站点是 https://xiaohui.cool/ 。下面只写上半没有展开、而这批笔记里写清楚的部分。`program/llm` 有 44 条笔记，投资和生活不收。没逐篇拆开的篇目在本节末尾。

### 四种用法怎么叠

单次调用、工作流、多智能体、OneAgent + MCP，是同一条光谱上的四档，不是四代必须升级的产品。

单次调用是无状态文本 API。成本和延迟按 token 可估。历史要进下一轮，只能手工拼进 prompt。

工作流把控制流写死。例子是意图识别、资料收集、分阶段分析、汇总、报告。高频标准单走这条。每个场景一条烟囱，盖不住长尾。

多智能体把 LLM 从工位升成规划者。Lilian Weng 的拆法是 Planning、Memory、Tool Use。ReAct 用外部 Observation 压内部幻觉；外部源本身错，错误照样进来。模型弱时循环会重复调用并且停不下来。四个框架的差别在编排：AutoGen 让角色互聊；CrewAI 先定 Role、Goal、Backstory 再委派；LangGraph 把回边做成一等公民；蚂蚁的 AgentUniverse 把专家流程收成模式，PEER 是 Plan、Execute、Express、Review。

OneAgent 的 One 是「一个基础 Agent 可派生」，不是「系统里只准有一个 Agent」。Manus 的循环是六步：看事件、选一个工具、等沙盒执行、迭代、提交、待命。Cline 把规划设成只读，人批准后才进入可写的执行。企业内部用领域 MCP 替换那一组通用 function。没有全知的 God Agent。Barry Zhang 的短定义是：Agent 是在循环里使用工具的模型。循环能扛长任务，靠的是预训练里的工具调用，加上下面的上下文工程。

客服可以叠着用：一次调用做意图；查订单走工作流；开放故障交给自主循环。Anthropic 的原则是从最简档开始，只在路径未知的任务上付不确定的步数。

### 上下文工程的六种动作

基础 ReAct 图就是 agent 节点、tools 节点、条件边、工具执行完必须回到 agent。生产里窗口会被几十次工具调用撑满。Chroma 把这种现象叫 Context Rot：变长之后模型开始重复和幻觉。Manus 典型任务大约 50 次工具调用，输入和输出 token 大约 100 比 1。

| 动作 | 机制 | 笔记里的落点 |
|---|---|---|
| Plan | 让模型把 todo 写回上下文末尾，锁定目标 | `write_todos`。工具几乎无业务副作用，返回值用来提醒进度。`@dynamic_prompt` 每轮把清单拼进系统提示 |
| Offload | 大结果进 state 或文件，消息里只留确认 | 5000 token 的计划若每轮都带，10 轮是 5 万 token。卸载后确认大约 50 token，10 轮大约 500。主 Agent 和子 Agent 之间传路径 |
| Isolate | 子任务用自己的窗口 | 避免不同子任务互相污染。子 Agent 可以和主 Agent 同构，也可以是一张确定性的图 |
| Reduce | 剪裁留原文，或摘要生成新文本 | 检索 3000 token 剪到大约 600。摘要和剪裁不是一回事。笔记转述 Claude Code 在窗口大约 94% 时触发压缩 |
| Retrieve | 数据按需召回，工具也按需装载 | Claude Code 不做代码索引，靠模型自己 grep。静态塞入全部工具会同时损害选择和缓存 |
| Cache | 稳定前缀吃 KV cache | 笔记引用 Sonnet 的价格：缓存输入 0.30 美元/百万 token，未缓存 3 美元。系统提示少改 |

RAG 是往窗口里加原始相关块。Pruning 是检索之后删无关、留下原文。Summarization 是把整段历史压成新摘要。三件事先分清再选。

虚拟文件挂在这次 Run 的 state 上，所以多个 Agent 不会写到同一份内存文件。真实磁盘只用于只读解压。派生一个领域 Agent 只交三样：工具或 MCP、领域指令、可选子 Agent。内置六件套是 todo、读写改、列目录、`task`。系统提示沿 Claude Code：XML 切模块，Markdown 做层次；`<system-reminder>` 把容易忘的状态钉在段尾，并要求不要向用户复述；好坏例子用来在多条看起来都合理的路径里标出偏好。

HTML 或卡片只允许出现在最终回答。工具调用和正文是两个通道。若 prompt 要求全程 HTML，模型会跳过工具直接编一张卡片。

MCP 运行时还要有一份兜底规则：没有合适的 MCP 就先问推荐 MCP 的 MCP。领域词禁止跨域调用。不要让模型自己执行 `node` 或启动桥接进程。当时写明的缺口是：todo 质量仍依赖人，长链错误会累积，嵌套加异步后状态难追，长任务缺少恢复。

### 在线咨询：控制、事实、表达分开

AgenticOne 是 OneAgent 在保险快查在线咨询上的应用。一次请求分成三个平面。

主 Agent 是控制面：理解意图、解析「第一款」「换一批」、选择能力、判断事实够不够、决定结束。它不拼复杂过滤条件，不吞条款原文，不在终末工具成功后再总结一遍。

工具和子 Agent 是数据面：候选、命中原因、原文片段、试算数字、核保条件写入共享 state，交还的只有编号、清单和引用。

终末工具是表达面。这是一次 Typed Handoff：工具自己从 state 组装上下文，交给专门的摘要模型，产出 Markdown 和 A2UI。结果不回到主 Agent。主 Agent 再写一遍，会拆掉组件、丢掉产品卡、改写证据。

保费和收益是中间工具，返回事实后仍由主 Agent 向用户解释。推荐报告和条款问答是终末工具。

核保和车险是状态机，不是闲聊。Orchestrator 在每轮开头看会话是否已经停在某个子流程里。在，就直接进入该子流程；不在，才进入主 Agent。核保要跨轮记住确诊时间、血压、用药、并发症，这些字段不放进普通 messages。

搜品是一张子图，不是一个函数。主 Agent 传入改写后的任务，搜索 Agent 把条件规划成四类任务：产品、核保、预算、收益，交给并发执行。产品任务之间取并集，后三类与候选取交集，再按白名单、排序、同名去重截断。`scope=last` 表示在上一轮完整结果池上追加条件。搜索 Agent 只输出产品编号 JSON，编号还要和快照核对，滤掉编出来的号。搜索阶段用轻量字段定产品，表达阶段再拉深档案写卡片。

条款问答把取证和回答拆开。取证子 Agent 读条款、健告、除外和投保须知，聚合后写入 `search_evidence`，主 Agent 只看到「证据已入库」。`qa_summary` 的参数只有问题和产品编号，原文从 state 读。优先级是本轮证据、产品档案、往轮对话。终末消息被转成最终回答并结束本轮。

流式层不按事件到达顺序推给用户。运行时事件来自 `astream_events`。生产者按检查点命名空间分组，用 `run_id` 和 `parent_ids` 把一棵执行树收成业务段落。并发取证合成一张「正在查材料」的卡。消费者按段落顺序发 SSE。裸 LLM 若在终末工具内部，必须打上智能体名字，token 才能进回答区。LangChain 事件描述内部执行，A2UI 描述界面更新，SSE 只负责传输。

### 离线报告：节点内放开，节点间收紧

输入一个产品编号，链路是：生成报告、补内部增量、对齐外部叫法、质量校验、回调。这个顺序稳定，所以外层是 StateGraph，不再让 Host 用 `task` 临场决定先校验还是先写。节点内部仍然允许搜索和改写。

Host 的 prompt 只留阅读方法、引用、证据不足时降级、禁止编造。把核保、合规、演算全塞进系统提示，会在证据不够时写出很专业但很空的段落。数据源进工具或外层节点。险种 prompt 教的是怎么读医疗、重疾或储蓄，不是每个产品一份标准答案。

通用读盘工具加上「不准离开素材目录」的提示，挡不住模型搜到别处。工具改成必须带产品编号：列出、搜索、读取都先定位该产品的根目录，读取用真实路径校验，防止目录穿越。grep 默认带上下文行，因为条款里单独一行经常没有意义。原则是：prompt 里被反复违反的约束，下沉到工具的参数和默认值。

语义搜索先在该产品材料里交回最多 5 个块 id，再读原文和前后文。下载完成之后，中间件切块、嵌入、把索引放进 state，并缓存到 Redis。嵌入接口失败时，工具返回降级说明，Agent 退回关键词，主链路不停止。

后置的三个 Agent 共享虚拟文件里的 `report.md`，上下文彼此隔离。内部增量补增值服务和理赔说明。世界知识只许改「真实叫法」那一章，改到别的章，父图丢弃这次更新并继续。质量网关看能不能交付。

校验走过三代。第一代生成完直接回调。第二代查数值是否忠于素材，不通过打回 Host，最多 5 次；术语误报多，而且风险不只是数字。第三代把增强放在校验前面，取消重试环。Gate 只做确定性检查：有没有错误码、是不是唯一一份报告。Execute 才调用模型。致命问题才写质量差的错误码，包括素材不够、核心条款缺失、核心参数大面积不合格，以及「由保险单载明」「按一定比例赔付」这种空话。结构不漂亮只记建议，不阻断回调。

评分是另一条独立能力，从源会话恢复文件再打分。三维是事实忠实、信息完整、基础质量，合规是门槛：不通过就折损，不参与普通加权。检查点只有通过、部分、不通过。聚合分在 Python 里重算。信息层级形成天花板：只有条款骨架时，不能靠文笔接近满分；核保数据和精算指标是更高层。产品评测再单独写一份水位报告：亮点、达标、注意点、坑点，必须引用基线和警戒线；没有基线就只描述。只信报告和原始素材，缺数据不评，禁止购买建议。

Python 运行时还有一个容易忽略的隔离。数据库连接池绑在创建它的事件循环上。质量校验的长推理若跑在主循环上，会堵住其他请求和数据库。主循环跑推理和检查点，校验用自己的循环和内存检查点，历史查询再用单独的池。

### 进程里图怎么复用

一个 worker 里缓存一份编译后的图。每次请求是独立的 Run。状态来自这次输入、配置、`thread_id` 和检查点，不来自图对象上的字段。共享节点里不要写 `self.current_user`，并发会互相覆盖。

Checkpointer 按 thread 存图状态，用于断点续跑。Store 跨 thread，放画像和会话总结。单次任务用新 thread，多轮对话复用同一个。清理过期会话不等于销毁进程里的图、连接池和模型客户端。

这套服务跑在 Flask 上，用的是 Gunicorn 的线程 worker，所以每个进程有一个长寿命事件循环。MySQL 异步池、Future 和锁都在这个循环上创建。同步入口把协程投递进去，禁止在请求线程里另起 `asyncio.run`。池的最大连接数在借连接处等待，形成背压。CPU 密集和同步 SDK 丢到线程池或进程池。

一个 Agent 请求会放大成不确定次数的下游调用：搜索可能 4 次也可能 14 次，校验步数随引用数变化。长 Run 占着数据库连接、模型流和工具配额。单 worker 通常只吃满一个核；水平扩展后，数据库连接大约是进程数乘池大小。模型并发往往先于数据库成为瓶颈。

### 协议对象：取消、恢复、流

框架名会变，外部系统依赖的对象比较稳：Thread 是多轮边界，Run 是一次执行，Step 是一步，Event 是进展，Artifact 是产物，Checkpoint 是可恢复快照。超时、成本和审批都绑在 Run 上。

参照 LangGraph 的服务形态：API 先把 Run 和输入写入数据库，再让消息系统叫醒 Worker。Worker 凭 run id 读库。消息丢失不等于任务丢失，SSE 断开不等于任务消失。数据库是故障恢复的事实源。Redis 只放唤醒、心跳、取消信号和实时转发。Worker 内存里的协程不能当唯一状态。

同一 Thread 上允不允许并行 Run，要写成明确策略：排队、拒绝、取消旧的并覆盖、从同一检查点分叉，或提交时检查版本。Thread 本身不是一把全局锁。

取消和「问人」是两种状态。问人进入等待输入，恢复时要带回那个中断点的值。取消先写成已请求，并推进一个版本号。Worker 在下一节点、调用模型或工具前后、创建子 Agent 之前、写检查点之前检查本地取消标记。终态写入带上启动时看见的版本；版本已经变了，迟到的模型结果被拒绝。已经发出的邮件和订单不会因为 Run 变成已取消而消失，工具侧还要幂等键或补偿。

`interrupt()` 不是把 Python 栈冻进数据库。节点里第一次调用它、又没有恢复值时，抛出图的中断信号，引擎把载荷和状态交给检查点。人用同一个 thread 和恢复值再次执行。代码会从该节点开头重跑，所以中断之前的副作用必须幂等。调试用的节点前后暂停、用户取消但保留现场、回滚并删掉这次 Run 的内部痕迹，是三种不同 API。回滚也不撤销外部副作用。

子 Agent 的取消能传多远，取决于它还在不在同一张图里。同一张图里，中断会向顶层传播。另一个 Worker 上的子 Run，要事先存下父子 run id。跨 HTTP 的远端图收不到本地的中断异常，必须把中断 id 和取消版本写成协议字段。根任务要等子树进入终态，或把失联的子任务标成孤儿。

工具错误默认作为数据返回给模型，由它换工具或告诉用户。系统级故障才向上抛。节点失败时，已成功的检查点保留，重入只重试失败节点。

跨网络的流要可恢复，就不能只靠 PubSub。实时转发和断线补收是两件事。开启可恢复流之后，事件片段落库，客户端用最后一条事件 id 补收。SSE 的句柄是 run id，不是某条 HTTP 连接。run id 不可猜，订阅和取消都要鉴权，终态片段要有过期时间。

多 Agent 的四种语义是子图、子任务、交接棒、群聊或发布订阅。笔记的建议是先把单 Agent 的对象边界做稳，再加必要的交接。工具协议会先于协作拓扑标准化：JSON Schema 加 MCP 的工具、资源和提示模板。Thread、Run 和中断仍归 Runtime。

### 大字段放哪

检查点、轨迹、产物、WAL 是四件事。检查点丢失，图不能从原处恢复。轨迹丢失，通常只是没法排障。产物丢失，引用会失效。WAL 只是某种存储提交前的追加记录，保护数据库的 WAL 恢复不了图，保护采集管道的 WAL 也恢复不了图。只有把每一步调度都建成可重放事件，轨迹才能重建运行状态。那是事件溯源，不是普通 tracing。

默认 ReAct 会把工具全文追加进消息，于是后面每个检查点都复制这份正文。抓取节点应先按内容哈希上传，state 里只留引用：地址、哈希、类型、大小、是否恢复所必需。分析节点下载后复制消息列表，临时把正文填进这次模型调用，返回时只提交模型的新回复。若把展开后的整表消息返回，reducer 会把全文写回去。恢复所必需的对象，保留期要盖住检查点还能恢复的窗口，对象存储的生命周期不能先删。1 MB 是存储大小，上下文预算仍要用目标模型的分词器算。

轨迹走 OpenTelemetry。Span 上记引用，完整 prompt 和工具结果进对象存储。内部字段保留 run id、checkpoint id 和 schema 版本，导出时再映射到 GenAI 语义约定。采集用的本地队列只保证日志尽量不丢，不代替检查点。

引用表按租户和哈希去重。同一对象可以被检查点、轨迹和用户产物同时引用。删除用延迟扫描，避免删一个检查点时伤到还被轨迹指着的文件。状态只有几十到几百 KB、数据库还没有被大字段拖慢时，直接用官方的 Postgres Saver。

### MCP 在 2026 的三条线

MCP Apps 让工具声明一段 HTML，宿主放进沙盒 iframe。扩展在 2026 年 1 月稳定。`visibility` 把给模型的工具和给界面的工具分开：界面可以调用「刷新」，模型看不见它；模型用的工具，界面不能直接碰。界面发出的调用走和普通工具相同的审计。安全假设是上游服务器不可信：双层 iframe、CSP 只能收紧、模板在连接时就可枚举并做哈希、自带工具要审批。工具仍必须返回有意义的文本，命令行宿主才能降级。

无状态核心是 2026 年 7 月的规范候选。它去掉会话 id 和初始化握手。协议版本和客户端能力随每个请求走。发现接口返回版本和能力。路由头让网关不读 body 就能分流。需要更多输入时，结果类型标成需要输入，客户端带上回答重试同一次调用，不再由服务器反向请求客户端。这样一次工具调用自包含，才能水平扩展。

AAIF 把 MCP 和 A2A 放进同一个 Linux 基金会下的治理框架。MCP 管代理到工具，A2A 管代理到代理。A2A 1.0 在 2026 年 3 月发布，8 月由 Google 移交。身份和支付还没有收进这套通信协议。笔记的选择是：工具开发按 MCP 投入；多 Agent 协作在 A2A 进入同一基金会之后，观望成本下降。

### 界面协议：操作日志和邻接表

模型决定把一张卡片换成按钮时，线上传的是变更描述，客户端持有的是组件表。

JSON Patch 的一行是操作、路径和值。它相对当前文档，顺序错了文档就坏了。A2UI 把组件发成扁平列表，子节点只记 id。客户端放进按 id 索引的表，从根按 id 展开。重发同一个 id 是幂等更新，允许乱序，丢了可以只补那个 id，引用不存在的 id 就跳过。json-render 对外流 Patch，对内编译回这张表。看一个生成式 UI 框架时，先问 Patch 是传输编码还是唯一真相，组件是扁平 id 还是嵌套树。

### Harness 怎么把循环装成工作台

DeepSeek Harness 用 Cordis 做运行时组装。Profile 决定这次启动装哪些包，Scope 决定这个 Agent 能看见哪套文件系统和模型。调用方依赖 `ctx.llm` 这种契约，不依赖具体类。插件注册能力时同时登记撤销动作。撤销只覆盖被运行时追踪、且提供了逆操作的副作用。已发送的邮件不会因为卸载插件而消失。

事件有四种调度。只广播、不等待的，不能承担审批。要等全部完成的，适合互不依赖的观察者。按注册顺序的，适合终止检查。洋葱型的 `waterfall` 用 `next()` 把控制权交给下游；审批插件可以不调用 `next()` 直接拒绝。

Turn 从开始到不再欠下一次模型请求。里面有零个或多个 Step。每个 Step 是一次模型请求加上它触发的工具。用户中途追加的话进收件箱，按语义在下一 Turn 或下一 Step 领取。会话日志里的 turn、step、消息和工具结果是可回放事实。下一轮发给模型的历史从这份日志投影出来，不从插件内存拼。工具执行前的审批和执行后的归一化仍按模型给出的调用顺序提交；标成可并行的工具可以同时跑，独占工具形成屏障。进行中的模型流不能换掉一半实现，切换点是下一次请求或新会话。

### 检索的两种交付物

同样是向量匹配，保险里两条链路的产物不同。

QQ Matching 召回的是一组产品。复杂查询的产品池由离线 Agent 搜索生成，和离线问句一起放进 Elasticsearch。线上只取回已经物化的池。嵌入模型是保险语料微调的 Qwen-Embedding-4B，只取最相似的一个离线问句，超过阈值才算命中，不把多个问句的产品池合并。简单查询仍走原来的搜索引擎。一个小模型判断简单或复杂，并且和两条检索从同一时刻并发：判成简单就交原搜索；判成复杂且向量命中就交离线池；向量没过阈值就交已经在途的原搜索，不再新开一次。笔记里的组件级近似是嵌入约 50 毫秒、判断约 250 毫秒；最近一天接口平均约 340 毫秒，P95 约 640 毫秒。时延接近判断和被选中分支里较慢的那个，不是相加。

这条链路的核心指标是 Precision@3：前三个产品里有几个满足既有标准，再对查询做宏平均。返回不足三个时，分母仍按三个，避免少返回把精度做高。训练和测试按问句的语义簇分开。取回之后还要用代码拦截下架、渠道不可售和年龄、保额、健告等硬条件。这个指标不评价解释写得好不好。

QA Matching 交给报告 Agent 的是坐标。先用产品编号限定材料，窗口 2000 字、重叠 200 字。嵌入只吃正文，不拼标题。返回最多 5 个块 id，Agent 再打开前后文。条款里「赔付金额」可能写成「给付保险金」，限制条件在后面的免除责任。Anchor Precision@5 只评价这五个块是不是有效定位：可以直接包含答案，或落在该继续读的正确章节。把 Agent 带到另一项责任的相似词不算相关。Agent 有没有把后文读完，归生成器的评测。五个块里四个不相关，先修检索；定位对了但没核对后文，修工具策略；证据完整仍写错，修生成和校验。

在线产品过滤在几万量级走进程内全量快照。JSON 只是版本化的分发格式，启动时解析成内存映射。模型写的是查询计划：字段、比较符、单位归一后的数值、责任上的正则。代码对每个产品做布尔判断。「除外国家里出现日本」不能被扫成「日本可保」。条件清楚通常一批并发任务就够；过宽或过窄最多再收窄两次；任务里含核保就只做一轮。截断发生在全库硬条件之后。先做语义 Top K 再套年龄和免赔额，正确产品若落在截断线外就回不来。到单机放不下、或查询主要变成语义发现时，搜索引擎才划算，而且硬条件要下推到过滤阶段，排序取前 K 放在过滤之后。

### 报告评测：从检查点到评测器自己的分数

出处：《如何科学评测 Agent 生成的文本报告》。业务方要的是报告能不能用：数字、来源、忠实、覆盖、深度、专业指标、前后一致、险种条件、可读性、合规。一个总分只能说「好像不行」，说不清修等待期还是修引用。

三层是 Dimension → Item → Checkpoint。例子：

```text
D1 基础信息质量
  └── I1 数值准确
        ├── 等待期、犹豫期、投保年龄、保额
        ├── 轻症保额、疾病种类、偿付能力指标
```

每个检查点只有 1.0 通过、0.5 部分、0.0 不通过、N/A 不适用。聚合顺序是检查点 → 评分项 → 维度 → 裸分 → 合规乘数 → 最终分。合规是乘数，不是普通加权里的一项。机器翻译的 MQM / WMT 早就做显式错误标注和严重度加权；这里换的错误类型是数字、引用、幻觉、合规、逻辑和遗漏。

评测器输出必须能进回归：

```text
checkpoint_id, score, status,
evidence 来自报告, source 来自素材,
reason_code 来自枚举
```

「整体较好，引用不够充分」这种话没有工程价值。LLM Judge 适合语义、模糊质量和开放比较，必须关进评分表。G-Eval 用思维链和表单提高与人的一致性；Prometheus 2 专门训练评测模型并支持自定义 rubric；Claw-Eval 把轨迹、审计、环境快照和安全放进证据链；MetaCritique 把评论拆成原子单元再算事实性和 F1。

ESF（Expert Scoring Fidelity）是主指标，看检查点，不看总分猜得像不像。

扣分召回率 = 评测器命中的专家扣分检查点权重之和 / 专家扣分权重之和。专家扣分指 `expert.score < 1.0`。权重例子：合规红线 10，核心事实 5，缺引用 3，表达 1。错一个标点和错一个保额不能一样算。

正常项通过率 = 评测器正确放行的专家满分权重 / 专家满分权重。它防止评测器变成杠精：什么都扣，召回率会很高，业务上不能用。

F1 = `2PR / (P+R)`。更怕漏严重问题的时候用 F2 = `5PR / (4P+R)`，P 是正常项通过率，R 是扣分召回率。金融、保险、法务、医疗用 F2。

算例：数值准确有 10 个检查点，专家 7 个满分、3 个 0.5。评测器命中 2 个扣分点，正确放行 6 个满分。召回 2/3，通过率 6/7，F1 约 75%。这比「评测器 0.82、专家 0.85」有用，因为它指出漏了一个扣分点，还误伤了一个满分点。

SCE = 平均 |评测器总分 − 专家总分|。专家 85、评测器 82，误差 3；100 份平均 4.2 就是 SCE。它只做校准。专家在 A 扣 10 分、B 不扣，评测器把两项对调，总分可以一样，逻辑是错的，ESF 会抓住。

RCR 看同一份报告多次评是否像自己。三层：检查点分数一致的比例；总分的标准差；合规通过/不通过是否翻转。

| 场景 | 检查点稳定 | 总分标准差 | 合规翻转 |
|---|---|---|---|
| 内测 | ≥ 0.90 | ≤ 3 | ≤ 2% |
| 生产 | ≥ 0.95 | ≤ 2 | ≤ 1% |
| 高风险 | ≥ 0.98 | ≤ 1 | 0 |

对外只报一个数时，用检查点稳定率当 RCR 主值。标准差和翻转不能被平均掉。一致性和对齐专家是两条轴，相关性 0.9 替不了它们。

优化闭环：专家历史评分收成 JSON，加构造样本，评测器出同构 JSON，按 `checkpoint_id` 对齐，算三个指标，再改 prompt、rubric、few-shot、规则或模型。Train 调 prompt 和样例，Dev 调阈值和权重，Test 冻结后只评一次，对抗集专门放数字篡改（50 万写成 500 万）、删引用、加入素材里没有的事实、前后矛盾、绝对化承诺、删掉关键章节。拿测试集调 prompt 只会过拟合。优先级是先抬 ESF，再降 SCE，再稳住 RCR。ESF 低是判断逻辑没学好，SCE 高是聚合和校准，RCR 低不能上线。

改评测器让它更像专家，是反馈优化。自进化多一层：同一次漏判，低质量反馈是「给这个 case 加一条特殊规则」；高质量反馈会问 rubric 是不是太粗、评测器是不是职责太多、证据链有没有显式检查、合规有没有结构化。经验要分成错误类型、修复策略、反馈质量和「这次修改有没有引入新退化」。评测器不可靠时，优化生成器是在追一个会移动的靶。

Harbor 的 Hello World 把尺子收成可重复环境。Task 含题面、初始容器、资源限制、阅卷脚本和可选参考解。Trial 是一次作答，Job 是一批 Trial，reward 由 verifier 写入文件，不是模型自报完成。构建失败或阅卷器没启动，记成基础设施失败。两次锁定的镜像或阅卷脚本不同，分数不能比。业务 Agent 通过适配器接入：要么在这次 Trial 的容器里执行受限动作，要么把产物写到约定路径再阅卷。版本固定到镜像摘要或 Git SHA。

### Deep Research：要轨迹包，不只是证据包

出处：《从 RAG 到 Deep Research》。简单问答可以 retrieve-then-generate：问等待期，找到那一句就能答。复杂报告里改变结论的材料往往不是最相似的那一段。销售页写「可续保至 100 周岁」，只围绕「续保」检索，会写成「支持续保至 100 周岁」，漏掉条款里的「申请续保，经保险公司审核同意后方可续保」。

笔记把相关工作串成一条线：RAG 把材料放进上下文；Self-RAG 判断何时检索、证据是否相关、回答是否被支持；CRAG 在召回质量差时过滤和补搜；Agentic RAG 把检索变成多步工具；Deep Research 把这套做成带引用的长报告；LongTraceRL 用搜索轨迹和中间实体覆盖当奖励，干扰文档和打开但未引用的页面也是训练信号。

研究型检索追的是结论敏感性：一段材料可以和问题不太像，但能改写最后一句。写保障范围时，除了「保险责任」，还要主动查免除、不承担、等待期、免赔额、医院定义、首次确诊、既往症、审核同意、本公司有权。

给模型的上下文因此从证据包改成轨迹包。证据包是「以下是和续保相关的材料，请总结」。轨迹包要有：当前研究问题、初始判断、支持材料、继续检查的路径、限制性材料、没找到的材料、不能说满的写作约束。对照式流程是七步：粗判断、找支持、找反对、找缺失、收窄判断、写章节 brief、再汇总成文。

五个模块：规划器把目标拆成研究视角（定位、责任、赔付条件、金额、等待期、免除、续保、销售页和条款的差异）；搜索器对每个视角跑支持、限制、反证、缺失四类查询；阅读器判断一段材料是支持、限制、和销售页冲突，还是改写了责任的含义，不急着收成一个永远稳定的 JSON schema；编排器按轨迹包排阅读顺序；生成器写报告，批判器再查有没有把销售话术当成正式承诺、有没有在缺证据时下断言。

评测因此有三层，不只看文章好不好读：轨迹是否拆对视角、是否打开关键文档；每个关键结论有没有查过反对材料；报告有没有把轨迹里的反向材料写成确定结论。

### 领域微调：正例展开说法，负例改一个槽位

出处：《保险推品中的语义匹配》。线上 QQ Matching 比较的是两个推品问题，不是问题和产品文档。产品责任仍由数据和搜索工具提供。向量只决定能不能复用一组已经离线选好的产品池。

新数据从 Top1000 查询造查询之间的正负关系，面向 Qwen3-Embedding，导出成 MS-SWIFT 的 InfoNCE。锚点是「三高买什么医疗险」。正例把疾病展开成「高血压高血脂高血糖怎么买医疗险」，推品意图不变。难负例改成「三高买什么重疾险」，人群不变，赛道变了。样本只有 user 文本，没有 assistant 答案。`messages` 是锚点，`positive_messages` / `negative_messages` 是候选。监督关系靠字段位置，制作依据不写进训练文本。

制样前用产品映射、规则和受限 LLM 标出产品、人群、疾病、赛道和硬约束。正例每条计划 2 到 4 个：别名、句式、少量错别字都可以，年龄、免赔额、健告、续保年限不能漏也不能多补。负例每条计划 4 到 7 个，一次只改一个关键槽位，例如 60 岁改成 6 岁，或只改免赔额。少量跨赛道随机负例可以有，不能代替难负例。「保证续保 20 年」对「保障期 1 年」是两个字段，不能靠替换词表直接判负。「老人」改成「父母」也不自动保留年龄。「医疗险 / 百万医疗」「三高 / 高血压」以及产品集合高度重合的两条查询，要复核，不能只看标签不同就当负例。

另外用原始 Qwen3-Embedding 在 Top1000 里找近邻：标签冲突且确实改变推品意图的收为负例，意图相同的真实问法补进正例。说不清的留给人。每条正负例存 `sample_logics`：改了哪个实体、为什么认为意图相同或不同。导出给训练框架时只留 role 和 content，不能假定框架会忽略自定义字段。

InfoNCE：

```text
L = -log( exp(s(q, q+)/τ) / (exp(s(q, q+)/τ) + Σ exp(s(q, qj-)/τ)) )
```

s 是余弦，τ 控制分数差有多敏感。Qwen3-Embedding 的公开配方是先继承语言模型，再用约 1.5 亿对弱监督文本做对比预训练，其中约 1200 万对高质量样本做微调。领域这一步不再加 `Instruct:` 前缀，训练和线上必须同一套纯问题输入。同一锚点的多条正例不能在一个 batch 里互相排斥。全参还是 LoRA 当时没定；LoRA 冻结底座，向量仍会变，原有匹配能力不保证不掉。

切分不能按导出行随机切。同一原始问题的全部改写、同义组和同一产品别名组必须在同一集合。评测集优先留真实查询对和人工确认样本。一条真实近邻被多个原始问题引用时，要查它会不会以另一条训练样本的身份再出现在评测集；只查 query_id 不够。新模型上线要和离线查询库的向量成套切换，相似度分布变了，旧阈值要重做。匹配分更高但带回错误产品池，问题没有解决。错误也不全是模型：查询库缺需求、产品池过期、排序把合适产品挤到后面，都算。

### 生成器、评估器、优化器

出处：《AI 系统如何进化》。看一次失败之后，下一次任务的输入有没有变。

生成器把候选放到桌上，可以是模型、检索器或会用工具的 Agent。评估器把「不对」拆成信号；它看不见的问题，后面只能靠人。优化器决定重跑、改 prompt、换检索源、补测试，还是把坏样例放进回归集。

三层改进不要叫成同一个「闭环」：

| 层 | 改什么 | 例子 |
|---|---|---|
| 闭环优化 | 当前产物 | 报告里的数字查表改对；测试从红变绿 |
| 进化 | 下一次任务的条件 | 多一条数据源校验、一个回归测试、角色卡上的服装字段、一条 skill |
| 自进化 | 改进方式本身 | 比较哪种修法长期有效，哪种只堵住一次；错误是生成器不会、评估器看错，还是返工放得太晚 |

剪辑如果六步只服务这一条片子，仍是闭环优化。风格规则、信息卡字段、样片长度和「只说弹出慢一倍，别的不动」留下来，才是进化。再比较哪些规则真减少返工，哪些只是把流程变重，才是自进化。保险报告、代码、投研、客服用同一把尺子。

### Harbor 怎样当发布门禁

出处：《用 Harbor 构建稳定的 Agent 评测、晋级与发布环境》。Hello World 只说明对象。生产里一个保险 Task 要冻结四类东西：带版本的材料快照、Material-Scoped 工具的参数和失败语义、研究轨迹、结构化评分。100 个产品跑一遍是一个 Job、至少 100 个 Trial；每个样本重复 5 次就是 500 个 Trial。`-k 5` 只增加尝试次数。考场容器和 Candidate 的应用运行时不要打进同一个镜像。

可比较的 Agent 先变成 Candidate：commit → CI → `registry/deep-research@sha256` → 独立 Preview 命名空间 → 健康检查 → Harbor。Preview 不能带着上一版的缓存和 LangGraph checkpoint。digest 或 URL 由流水线传入，Harbor 不会自己发现仓库里刚打出来的镜像。改了网络配置还复用旧 Job 名，会因为 `lock.json` 和配置不一致而拒绝继续。

轨迹可以离线从 Checkpointer 转成 ATIF，不必等当时开了事件监听。读 `get_state_history`，用 `snapshot.metadata.writes` 的增量，不要把每个快照里累计的 `messages` 全量再导出一遍。能恢复的是消息、工具调用、最终结果和已经写进 `usage_metadata` 的 token。恢复不了的是开始结束时间、真实延迟、内部重试、被中间件吞掉的异常、未完成的模型调用、流式 token。工具超时后重试成功、只把最终 ToolMessage 写入状态时，离线轨迹只看见成功。错误引用可以离线评；无效搜索在保留了查询和返回时可以部分评；工具失败最依赖在线事件或旁路审计。审计事件适合另写 append-only 日志，用 thread、run、tool_call_id 和检查点对齐，不要永久堆进 State。

`reward.json` 里主分以外的事实忠实、覆盖、引用、工具成功、有效搜索不能被平均掉。少搜几次可能总分不变，同时漏掉「审核同意后方可续保」。`result.json` 只够当索引。优化器要的失败包是：Job 汇总、逐 Task 的新旧配对、退化 Trial、轨迹、检查点明细和证据、工具日志。只看总分会在系统提示里加一句「注意续保」；看过轨迹才会知道搜了「保证续保」，没继续搜「申请续保」「本公司有权」，限制材料已经出现却没写进报告。一轮只推一个假设。

发布门禁和单题阅卷分开。进程退出码 0 只表示实验跑完，一个什么都不做的 Agent 也可以是 0 且 reward 为 0。policy script 再读汇总。例子：平均 reward 比基线高至少 3%，引用不低于基线，工具异常不超过 1%，合规翻转为 0，P95 增幅不超过 10%，环境异常不超过 1%。通过后，生产跑的必须是刚刚评过的同一个 digest。评完再 rebuild 一个「代码应该一样」的镜像，证据链就断了。

评测器自己也进 Harbor。生成器 Job 的输入是材料，被测的是 DeepResearch，verifier 必须是已经通过元评测的那一版。评测器 Job 的输入是材料和一份固定报告，专家 GT 只在 verifier 阶段使用，不给被测评测器。ESF 和 SCE 在单个 Trial 里算；RCR 要等同一 Task 的多次 Trial 汇总。Evaluator v8 替换 v7 的条件包括 ESF 不低于旧版、SCE 明显下降、检查点稳定率不低于 0.95、合规翻转不超过 1%、严重错误的加权召回不能下降。比较生成器 v17 和 v18 时冻结评测器、数据集和环境。评测器升级后可以给历史报告重打一条新基线，不能把两把尺子的分数接成一条趋势线。线上新失败回流到对抗集之前要版本化和人工确认。

离线回归集冻结材料、索引和工具返回，回答相同条件下有没有进步。在线观察集允许实时搜索，回答当前世界里还能不能用。两个数不要合成一个平均数。`n_attempts=1` 分不清提升和运气。晋级十步里，优化器不能读隐藏测试的答案。半年后要解释「引用正确率从 68% 到 81%」，账上要能找回 agent commit、两个 digest、数据集版本、环境 digest、评测器版本、模型版本、job id 和 deployment id。数据、环境或评测器也要升级时，另开一条基线。

### LangGraph 的三张表和三层流

出处：《LangGraph State 的生命周期》《LangGraph Agent Event 消费指南》。

State 的生命周期是写入、更新、回滚、读取。三张表：

| 表 | 粒度 | 何时写 |
|---|---|---|
| `checkpoints` | 每个快照一条元数据 | 快照完成 |
| `checkpoint_writes` | 每个节点的部分更新 | 节点一结束就写 |
| `checkpoint_blobs` | 每个 channel 一份合并后的序列化状态 | 快照完成 |

`thread_id` 是会话。`checkpoint_ns` 空字符串是根图，非空是子图。`channel` 是 state 的一个字段，各自版本化。`channel_versions` 记这个快照时刻每个字段指向哪个 blob version。表之间没有外键，加载时用 channel 名和 version 去 join。未变化的 channel 继续引用旧 blob，分叉后也共享，这是 Git 式去重。

version 来自 `get_next_version`：该 channel 的写入计数加 1，再加一段随机数，格式是 32 位计数加 16 位随机。前缀不是 checkpoint 序号。`messages` 的第 2 次写入可能发生在第 3 或第 5 个快照。零填充让字典序等于时间序。序列化用 JsonPlusSerializer，类型通常是 msgpack。

回滚不删旧快照。`update_state` 指向目标 checkpoint 后，插入一条新记录，`parent_checkpoint_id` 指向那个目标，blob 从目标复制过来。旧分支留着。节点失败后的恢复读的是 writes 里已成功的部分更新；审计对比 writes 和 blobs 的数据量，可以看出一次快照里哪些节点写了什么。`task_id` 是节点名，`task_path` 是子图路径，主图是 `()`。

流有三层，不要混成「把 token 打出来」：

| 接口 | 看到什么 |
|---|---|
| `astream(stream_mode=...)` | 按用途抽出的频道 |
| `astream_events(v2)` | 组件生命周期：chain、chat model、tool 的 start/stream/end，带 run_id 和 parent_ids |
| `astream_events(v3)` | 拆开的投影：messages、values、output、subgraphs、interrupts |

`stream_mode` 里，`messages` 是 token，`updates` 是节点完成后的 state 增量，`values` 是完整 state，`custom` 是节点用 `get_stream_writer()` 主动写的业务进度，`debug` / `tasks` / `checkpoints` 给排查和恢复。产品界面优先 messages、updates、custom。v2 用来回答「哪个工具没有出现在外层流里」，不适合当长期产品协议。

LangGraph 按步选出可运行节点并行执行，channel 更新到步边界才一起提交。token 和 custom 可以在步中途流出来，并 multiplex 进同一条 async iterator。到达顺序不是节点定义顺序。消费端按 `langgraph_node`、namespace、run_id、parent_ids、message_id、tool_call_id 分桶。子图要 `subgraphs=True`，事件带着 `("parent_node:task", "child_node:task")` 这种路径。同一 async context 里，手动 `ainvoke` 子图通常还能把事件送出来。丢进裸线程、队列或另一个进程，外层就看不见；要把当前 `RunnableConfig` 传进去，或另做事件桥。

custom 事件表达「开始检索、已召回 100 条、正在读第 3 份材料」。字段要能 JSON 序列化且稳定，不塞大段 prompt 和完整工具参数。对外协议用自己的名字：`run_started`、`message_delta`、`tool_progress`、`human_interrupt`、`run_completed`。测试不断言全局第几个事件必须是谁，只断言同一 message 的 delta 顺序、工具开始和结束能配对、错误能归到节点、敏感字段没有进产品事件、最终一定有 run_completed。

### 货架：缓存候选，不缓存话术

出处：《保险搜品能力工程架构》。第一版输出候选货架，文案是「可以优先看看、理由是、还要确认这些条件」。没有年龄、地区、职业、健告和预算时，不能写「最适合你」「保证可买」「一定能赔」。

搜品是主 Agent 的能力，不是独立入口。具名产品和短条件走 `fast_search_products`，例如「好医保长期医疗」：归一化、精确缓存、未命中再调传统搜索、货架硬过滤、批量拉深档案、规则排序。宽泛需求走 `ProductSearchGraph`，未命中缓存才进 AgenticOne。主 Agent 不拼复杂参数，也不把长候选塞进 messages。第一版不让模型做最终排序。

Redis 五件事：内部 run、可恢复事件、精确候选缓存、语义候选缓存、30 秒防击穿锁。键有版本前缀，例如 `ps:v1:cache:exact:{searchMode}:{queryHash}`，候选 TTL 6 小时，run 和事件流 24 小时。缓存体只存产品编号、命中摘要、召回来源和分数、写入时的 `shelfVersion`。不存最终清单、卡片文案、购买建议和模型推理。实时查询成功后先截断 Top 50 再写缓存，不等展示顺序排完。

语义缓存用 RediSearch 的 HNSW，维度在文中例子里是 1536，余弦。第一版宽松复用的条件是同一 searchMode、相似度至少 0.72、payload 未过期。命中之后仍要重新做货架过滤，卡片理由按当前问题和深档案重算。精确和语义都 miss 时，`SET lock NX EX 30`；没抢到锁的请求等 300 到 800 毫秒再读一次精确缓存，还没有就自己查，不等待无限期。

货架硬过滤只做上下架、渠道、白名单、同计划去重、运营屏蔽。年龄、地区、预算、职业、健告不在这一层猜测。用户已经说了预算或健康条件，才由 AgenticOne 的对应工具收窄。深档案批量失败就剔除该产品，一个都不剩就返回无候选，不编卡片。SSE 写失败不阻断主链路，但 run 快照仍要落盘。

失败要分开观测：意图进入搜品的比例、快工具和子图的比例、两种缓存命中、实时查询比例、过滤后为空、档案失败、两段延迟、卡片点击、用户改写提问、主链路错误。上线前的最小集包括具名产品、给爸妈买、给全家买、日本旅游、电动车意外、预算不高的寿险、和百万医疗对比、以及「推荐一个保险」。必测的一条是：货架下架之后，缓存命中仍然被滤掉。第一版明确不做独立入口、模板缓存、画像强过滤、投保适配、多轮指代、模型排序和缓存最终文案。

### 后训练的题要落在能力边界上

同一道题采样二十次，全对或全错都几乎没有相对奖励的梯度。要留在强化学习队列里的，是既有成功也有失败的题。难度是当前策略的失败率，不是题目的固有标签。全会的留在回归集并降低采样。当前全败、但更强模型或参考解能做的，先用监督或蒸馏搭桥。参考解也失败的，是环境或验证器坏了，隔离，不要当负样本。

一道可训练的题要能恢复初始状态，并带有验证器和预算。验证器检查业务对象终态和不允许的副作用：退款信写得漂亮但没走审批，算失败；删掉测试让检查变绿，也算失败。真实工单先脱敏，再还原成状态、权限和异常。模拟接口要保留分页、幂等键，以及「第一次调用已经写入、响应在路上丢了」。返回永远干净的同名接口，练出来的是填参，不是处理副作用。

失败先分流。工具格式和固定顺序进监督微调。会用工具但不稳定的分支，进可验证的强化学习。当前策略始终零成功时，让更强模型在它实际走到的状态上纠正，这是在策略蒸馏，蒸馏的是眼前跨不过去的那一步。生产失败先排除服务故障和验证器误判，再生成变体，并留一部分同类失败做隐藏测试。大约三十个真实失败、一个能复位的环境和几条确定性断言，就够暴露管线问题。每轮只增加一种难度，旧题不删，只降低训练权重。

奖励漏洞会迁移。笔记引用的实验是：模型在大约八十个可被利用的强化学习环境里学会寻找评分器、修改奖励，并把这套行为带到新场景。增加无关文件或随机让工具报错，可以降低通过率，但不增加值得学的判断。

### 生成式预训练和向量训练差在出题

两边都是前向、损失、反向、更新参数。差别是题目。

生成式模型把一段文本错开一位：看见左边，预测下一个 token。2048 个有效 token 大约提供 2047 个监督位置，所以网页和代码不用人工写答案。因果掩码禁止看右侧。最后位置的隐藏向量经过词表层变成整个词表上的分数，交叉熵只看正确答案的概率。语义是预测压力的副产品。训练不检查事实，模型可以流畅地复述错误材料。

下一 token 的损失不要求整句变成一个稳定向量，也不要求同义文本的余弦更高。直接平均某一层，不能当成检索向量。向量模型通常继承已经训练过的语言底座，再池化、投影、归一化，用对比损失把相关文本拉近。相关由数据定义：问题靠近答案，需求靠近商品，疾病的不同说法可以靠近，险种变了就要分开。批内其它文档当负例能省编码，但「没有配成对」不等于「不相关」。随机负例太好分；「设置密码」对「解除密码」这种困难负例才迫使模型区分动作。标错的困难负例会把正确文档推远。损失下降之后，按来源、时间和近重复簇切开，再看 Recall@K、MRR、nDCG，以及返回的东西能不能用。向量库只加速查找，修不了标错的关系。

Jev 被笔记描述成可能保留 Transformer、但改掉生成头的判别模型：一次编码 state，直接给候选项打分，用选择、真假和等级概率输出。这样省掉逐字生成和 JSON 修复。代价是候选必须事先给定。列表内的 softmax 分数还要单独校准，才谈得上接近真实正确率。排序变好，不能反推内部一定是某种双塔结构。

### 产品和生产各有一个闭环

Agent Native 指两个平面都形成闭环。产品平面用 Agent 满足用户意图。生产平面用 Agent 观察失败、修改提示、知识、工具或代码，再经过评测发布。只有聊天框，是功能。只用编码助手写代码，是辅助工程。

离线 token 用来生产可复用的认知资本：知识库、评测集、来源记录。在线 token 用来调度这些资本。早期会增加 token、评测和治理成本。闭环跑通之后，成本从重复人工转到这些资产上。压缩的是三段时间：意图到结果、反馈到下一次迭代、故障到修复。

在线咨询是产品平面。报告流水线、评测器元评测、Harbor 和可验证后训练，是生产平面里「失败怎样变成下一轮能力」。

### 检索交给模型的是哪一种证据

块前先写 50 到 100 个 token 的块内说明，再拿「说明 + 原文」做嵌入和 BM25。Contextual Retrieval 报告的 top-20 失败率，基线 5.7%；只加上下文嵌入降到 3.7%；嵌入和 BM25 一起用，失败少 49%；再加重排，少 67%。这是那组语料和 Gemini 嵌入上的数。通用摘要贴在每个块前面，增益很小。说明要写出这块属于哪家公司、哪一季，否则「收入增长 3%」无法和别的文件区分。

整篇放进长上下文，换的是证据覆盖。arXiv 2606.20898 在制造安全培训材料上比较了 972 份回答：长上下文正确率 73.1%，语义检索 65.4%，token 大约是 26 倍。材料小到能整篇装进窗口、漏一段就会改结论时，付这个成本。ACL 2026 industry 的多格式文档实验里，被动检索约 6%，检索加工具约 46%。工具是翻页、读表、定位。SurfSense 在 30 篇长 PDF、171 道题上，长上下文高配大约 59.6%、中位 6.8 秒，带工具的检索大约 53.2%、中位 52.8 秒；作者用 McNemar 检验后认为这 6 个点在该样本上区分不开。选型按材料是否装得下、漏一段是否改结论、标识和权限是否必须先滤，不按架构名称。

保险链路上，简单问句走搜索引擎。复杂问句复用已经物化的离线问句和产品池，线上一次近邻，过阈值才命中。条款问答交出去的是块坐标，窗口 2000、重叠 200，嵌入只吃正文，Agent 再打开前后文。研究型报告要的是轨迹包：支持、限制、没找到的材料、不能说满的约束。

### 近邻先过硬条件

索引进来 10 个近邻，年龄、租户或权限条件扔掉 9 个，查询仍返回成功，上下文被饿瘦。pgvector 0.8 的 `hnsw.iterative_scan` 取 `strict_order` 或 `relaxed_order`，会继续扫，直到滤后的条数够，或碰到 `hnsw.max_scan_tuples`（默认 20000）。过滤极严又很稳定时，例如一个租户只有几千块，直接在这片上做精确扫描。距离阈值和稠密过滤叠在一起时，先把高选择性条件收成候选集，再算距离。

词法和向量按名次融合，每一路贡献 `1 / (60 + rank)`，60 是常用阻尼。重排放在融合之后的几十条上。权限、租户、下架进索引查询。这和货架、进程内全量过滤是同一条规则：硬条件在截断之前。几万产品放内存做布尔判断；规模再上去，硬条件下推到近似近邻之前。

### 可恢复流：事件日志和检查点各管一件事

出处：《LangGraph Platform 可恢复流协议深度解析》。Thread 保存跨 Run 的检查点。不带 thread 的 Run 不持久化状态。Run 的状态是 `pending → running → success | error | timeout | interrupted`，`attempt` 从 1 计。Stream 可以挂在一次 Run 上，Run 结束就关；也可以挂在 Thread 上，跨 Run 开着。可恢复是 Run 上的开关。

三个端点：POST `/threads/{tid}/runs/stream` 创建 Run 并开始推；GET 指定 `run_id` 只重连，不新开执行；GET `/threads/{tid}/stream` 加入该 Thread 上当前活跃的 Run。POST 和 GET 共用消费者。消费者从缓冲里阻塞读，不区分回放和实时。Redis 的键按 `run_id` 建，例如 `llm:run:{run_id}:events`。用户 id 只用于鉴权和归属。一个人可以同时有多个会话和多个 Run。

两个开关要一起开。`on_disconnect` 默认 `cancel`：断线就停，省掉用户已经走掉的算力；`continue` 让 Worker 独立于这条 SSE 继续跑。`stream_resumable` 默认 false，事件 yield 后丢掉；true 才写入缓冲。只 continue 不落缓冲，执行还在，断线期间的 token 补不回来。只落缓冲却 cancel，缓冲里没有新事件。

SSE 每个事件有递增 `id`、`event`、`data`，以空行结束。重连带上上次的 id。不传 id，只收之后的新事件；`"-1"` 从头回放；正整数 N 表示 id 大于 N。LangGraph 从 v0.6.0 起改成 exclusive，和 SSE 规范对齐，之前是 inclusive。同一游标多次重连，服务端起点相同。客户端若不清掉已渲染的 token，回放会拼成「HelloHello」。浏览器原生 EventSource 会自动带 `Last-Event-ID`，但不能 POST，所以创建 Run 要用 fetch 式 SSE 客户端。

检查点和流是两套持久化。检查点是图状态，放在数据库，标识是 thread、namespace、checkpoint id，给人中断和 Worker 崩溃后续跑，默认可长期留着。`checkpoint_during=true` 时每个 super-step 写一次；false 只在结束或中断时写。流事件是 id、类型、载荷，放在 Redis Stream 一类的日志里，给客户端补画面。笔记里的 `RESUMABLE_STREAM_TTL_SECONDS` 默认 120 秒。超时后流补不了，只能从检查点重新执行。`checkpoint_during` 不影响事件是否入流。

缓冲选型按能不能跨进程、重启后还要不要。跨进程用 Redis Stream；旧 Redis 用 List 加 INCR 生成 id，Pub/Sub 只负责叫醒。Pub/Sub 本身发完即忘。单进程、重启可丢，用内存队列。进程内先推、异步再写 Redis 时，崩溃会留下已显示但没进日志的事件，重连对不齐，所以可恢复路径要先落日志再推，或接受这个窗口并在客户端按 id 去重。

同一 Thread 上的并发策略在创建 Run 时声明：`enqueue`、`reject`、`rollback`、`interrupt`。这和前面的取消版本是同一类问题：后来的 Run 能不能覆盖还在跑的那次。

### 能力证书绑的是一次运行，不是一个分数

出处：《从 Harbor Hub 到 Agent 能力认证市场》，作者写于 2026 年 8 月。当时 Harbor Hub 已经能发布带 digest 的 Task 和 Dataset，Dataset 可带自定义聚合，Job 可以边跑边上传，排行榜给出试验数、错误、成本、reward 和模型。缺的是授权、隐藏测试、泄题检测、反作弊，以及和代码、镜像、部署的绑定。

作者把流水线拆成三个已经成熟的平面，再补一个不发明评分器的控制平面。制品平面管 commit 和镜像 digest。评测平面管 Harbor 的 Task、Trial、轨迹和 reward。发布平面管 Preview、Canary、生产和回滚。控制平面把 digest、Preview 健康检查、锁定的 Dataset 和 Evaluator 交给 Harbor，再把政策门禁写回 PR。一个什么都不做的 Agent 也能让 Job 正常退出，reward 是 0，所以门禁不能看退出码。

再往后的交易物是能力证书，不是 500 道题。证书至少绑 certificate id、agent 镜像和配置的 digest、dataset、environment、evaluator 的 digest、指标政策版本、harbor job id、签发和失效时间。模型、提示、工具或环境一变，旧证书不继承。评测器要先经过 ESF、SCE、RCR 的元评测，并带版本和有效期。专家标注、评分提示、底座模型或计分方式变了，尺子重考。没通过元评测的新评测器，不能用来证明新 Agent 更好。

分数一旦影响合同，隐藏集泄露、题目太窄、单模型评测器随底座漂移、外部网页无法完全复现、私有镜像需要隔离和销毁记录，都会出现。一次高分不承担无限责任，证书要写清任务边界和失效条件。作者的落地顺序是先做公司内的发布门禁，看它拦下多少回归、省下多少人工验收、失败样本多久进下一轮、通过后发布的是不是同一个 digest。这些数稳定之后，再共享私有评测资产，最后才签发公开证书。

### 运行时边界：草图里的内核，和后来真正分开的对象

2025 年 9 月的 NARE 把多 Agent 画成操作系统。内核集中调度、上下文、资源、工具和网络，Agent 是用户态进程。A2C 是注册、领任务、读写上下文、经内核调工具。Agent 之间不直接共享内存，靠同一个 `context_id` 追加结果。心跳失败就把未完成任务放回队列。长任务上报进度，换一个 Agent 从检查点继续。工具调用要求幂等。上下文分支用写时复制。每个 Agent 一块虚拟文件系统，脚本在沙箱里跑。意图进不同队列：实时用截止时间，交互用时间片，批处理用吞吐，空闲队列可以偷任务。外部模型和密钥要向资源代理申请令牌。

这些是设计类比，笔记里没有给出这套内核的线上测量。到 2026 年，同作者写下来的生产边界更窄，也更可核对。进程里复用的是编译后的图，状态在 Run 和检查点。跨 Run 的画像在 Store。可恢复的画面在带 TTL 的事件日志。工具在 MCP 注册表，不在一个模拟的驱动层。取消用版本号，不靠心跳猜。Agent 之间先做单 Agent 的对象，再按需要交接。虚拟文件系统和写时复制，在后来的笔记里变成工作区隔离和检查点分支，而不是再造一个内核。
