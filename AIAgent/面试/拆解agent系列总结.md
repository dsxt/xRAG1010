# Agent Harness 拆解系列总结

> 来源：`拆解agent系列.md`（系列共 4 期：01 DeepSeek / 02 Pi / 03 Codex / 04 三家横评，外加一篇 DeepSeek Super-agent 视频笔记）。

---

## 0. 一页速览

**核心公式**：Agent 能力 ≈ 模型 × Harness

- **Harness**：模型以外的运行框架，包括驱动循环（agent loop）、工具、上下文、状态、存储、扩展和对外协议。
- 三家 Harness 越来越像，所以模型差距又成了主要变量；Harness 决定模型的能力能兑现多少。
- Harness 分两层：
  - **通用层**（循环、工具、状态）：三家已经趋同，直接复用。
  - **业务层**（你的工具、知识、规矩、评测）：模型再强也不会自己知道，这才是企业的护城河。
- 钱怎么花：**模型选，不自己造；通用 Harness 用，不重写；业务层自己建。**

**三家一句话定位**

| 项目 | 设计取向 | 一句话 | 协议 |
|---|---|---|---|
| DeepSeek Harness | 一切皆插件 | 连 agent loop 都是插件，所有事件记在一本只追加的账（Session）上 | MIT |
| Pi | 极简、可读完 | “用不到的就不做”，状态归属与上下文进入时机全部显式 | MIT |
| Codex | 一个内核撑多产品 | 网页版 / CLI / IDE 插件 / 桌面 App 共用一套 Harness，靠 App Server 协议层对接 | Apache 2.0 |

**排查 bad case 的通用方法**：先问“这段状态归谁管”，再对照常见误区排查。

## 1. 第 02 期：Pi —— 小到能从头读到尾

### 1.1 设计理念

- 理念：**context engineering is paramount**。模型读到什么必须精确控制，输出才会好。
- 批评点：很多现成的 Harness 会在背后往上下文里塞东西，而且界面上看不到。
- Pi 的做法：每份状态归谁管、什么时候进入模型上下文，全部显式化。
- 适用：学习、做原型、把小内核嵌进自己的工具。
- 不足：上企业生产要自己补**权限、持久化、多人治理**。

### 1.2 六个模块与对应问题

| 问题 | 模块 |
|---|---|
| 谁去调模型 | 执行核心（Agent 管状态 + 驱动循环管推进） |
| Function Call 怎么落地 | 工具管线 |
| 上下文怎么维护、记忆怎么接上 | 记录与投影 |
| 插件从哪接 | 应用层 + 扩展 |
| 换模型走哪 | 模型接入 |
| 最上层 | 宿主（终端界面、SDK） |

> 同一份会话有三份副本：**内存里一份、文件里一份、发给模型的一份**。Pi 把这三份分别归属清楚。

### 1.3 执行核心：Agent 与驱动循环分离

- **Agent 是状态的主人**：消息、模型、工具、正在流式输出的内容、未完成的工具调用、中断控制。
- **驱动循环只管推进**：拿本轮上下文快照，发起模型请求、跑工具批次、决定是否续跑。它不认识终端，也不认识会话文件。
- 事件回到 Agent 后先更新状态，再**逐个等待核心监听者处理完**。慢的监听者会卡住整条事件，这就是 **back-pressure（背压）**。
- 代价：Agent 状态、本轮上下文、会话记录三者要在明确的时点同步。

### 1.4 工具管线

**“开始”事件最容易误读**：

```
发出"开始"通知 → 查找工具 → 预处理参数 → 校验格式 → 前置钩子 → 全部通过 → 真正执行
```

所以看到“开始”，只说明调用进了管线，**不代表外部动作已经发生**。

**并发规则**：
- 默认整批并行；批内只要有一个工具要求顺序执行，**整批改为顺序执行**。
- 如果模型输出因长度被截断，这一组调用**直接报错**，不执行可能残缺的参数。

**完成顺序和入历史顺序是两回事**：
- 三个调用并行时，完成通知可能是 2、3、1，但写进历史的结果仍是 1、2、3（作者用假模型在本地验证过）。
- 好处：界面实时看进度，模型下一轮拿到稳定的顺序。
- 代价：慢工具拖住整批提交。
- 推论：**看到工具完成，推不出模型已经看到了结果。**

### 1.5 工具结果拆成三份（Pi 最有特色的设计）

| 份 | 给谁 | 说明 |
|---|---|---|
| 1 | 模型 | 文本 |
| 2 | 界面 / 日志 | 展示用 |
| 3 | 程序 | 结构化数据，**明确不发给模型** |

- 动机：如果只有一份给模型的文本，界面要展示结构化数据就得反过来解析自然语言。
- 一致性规则：扩展改了给模型的那份、却没同步给程序的那份时，**旧的程序数据直接清掉**。
- 注意：字段拆开**不等于隐私保证**，最终要看实际发出去的内容。

### 1.6 记录与投影（上下文维护）

- 会话文件是一棵**树**，每条记录指向父记录（支持分支）。
- 每次请求前：沿当前位置取路径，套上压缩摘要，合入编辑记录，生成**投影**（每条消息都能追回原记录），再转成模型格式发出。
- 好处：存储格式和模型接口可以各自演进。
- 代价：一条消息有三种形态（**原记录 → 投影 → 真正发出的请求**），排障要追到最后一层。

**插件开发者要注意的坑**（两步：先选消息，再翻译格式）：
- 压缩摘要会变成**用户消息**。
- 应用自定义消息也会变成用户消息，**即使界面上设成隐藏，照样发给模型**。
- **界面隐藏、存储保留、模型可见是三个独立的开关。**
- 请求阶段的变换**不写回会话文件**，想留痕要走专门的编辑记录。

### 1.7 记忆

Pi **没有独立的长期记忆模块**，跨会话靠三样：
1. **会话续接**：接上最近一次，或挑一次接着聊。
2. **压缩摘要**：聊长了，旧内容压成摘要继续带着。
3. **项目说明文件（AGENTS.md）**：全局一份，再从当前目录逐层向上各找一份，启动时拼进系统提示词。

想让它记住团队规矩，写进项目说明文件最省事；要真正的长期记忆，得自己写扩展。

### 1.8 模型接入

- 原则：**统一契约，差异留在边界。**
- 核心只认一个统一的流式接口：输入整理好的对话，输出统一格式的事件流；**出错不许抛异常，必须编码成流里的事件**。
- 分层：统一接口 → 模型路由 → 各厂商适配。
- 跨厂商切换时会丢掉旧的思考内容、去掉不兼容的签名，必要时改写调用编号。作者自己也说只能“尽力而为”。
- 结论：**能切模型 ≠ 上下文能无损迁移。**

### 1.9 应用层与宿主

- **宿主很薄**：CLI 三种模式，SDK 可直接装配；界面只管显示，不控制循环，也不持有历史。
- **应用层收拢所有策略**：资源与工具注册、扩展运行、压缩、重试、模型路由。它在工具调用前后挂拦截，把事件通知给界面（不等界面刷新完）。
- 单独成层的原因：执行核心要能被别的应用复用；压缩、路由是产品自己的策略，不该污染核心。

**一条“消息结束”事件要过六站**（Pi 写得最严谨的地方）：

```
Agent 状态 → 等核心监听者 → 等扩展 → 通知界面（不等待） → 写会话记录 → 同步追加到文件
```

推论：
- 不能说“界面渲染完才落盘”。
- 写入失败只回滚会话记录本身，**不回滚 Agent 状态，更不撤销工具已做的事。**

### 1.10 钩子与扩展

- **扩展** = 可执行代码；**Skill** = 指令文件，默认只把名称和描述放进提示词，正文用到时再读（渐进加载）。
- 钩子能直接改行为，不只是旁观：
  - 上下文钩子：改本轮请求。
  - 工具钩子：调用前拦截，调用后改写结果。
  - 回合钩子：参与决定是否续跑。
- 重载顺序：关闭旧会话 → 作废旧运行器 → 重建。旧的上下文引用不能跨重载使用。
- 项目信任：默认先问用户，它管的是**扩展加不加载**，**不是逐个工具的权限系统**。

### 1.11 MCP 立场的变化

- 早期不做 MCP：两个常用浏览器 MCP 光工具说明就各占一万多 token，还没干活就吃掉 **7%~9%** 的上下文。
- 后来改口：Pi 需要的和 MCP 需要的很像，都是一个能跑脚本的解释器沙箱，也就是 **Codemode**。
- 现在“注册了 ≠ 模型看得见”，工具曝光分三档：
  1. 直接给模型；
  2. 只给脚本调用，不占工具列表（**MCP 的默认档**）；
  3. 先隐藏，模型搜索到再加载。
- 注意：脚本沙箱受限，不代表它调用的命令也被隔离。Pi 默认**继承启动进程的权限**。

### 1.12 状态归属表（Pi）

| 状态 | 归属 |
|---|---|
| 消息、模型、工具、流式状态 | Agent |
| 本轮推进 | 驱动循环 |
| 策略、扩展、压缩 | 应用层 |
| 扩展上下文 | 扩展运行器 |
| 文件、分支、压缩记录 | 会话记录 |
| 各家模型 | 模型路由 |
| 显示 | 界面 |

常见误区：**流式临时状态 ≠ 持久记录；会话文件 ≠ 模型上下文；接口统一 ≠ 语义无损。**

### 1.13 一次 run 走一圈

1. 宿主提交请求，经应用层到 Agent。
2. 会话记录投影出本轮上下文，转成模型格式，交给模型接口。
3. 模型路由到具体厂商，事件流返回。
4. 工具调用进管线，并行执行，按原顺序交回。
5. 结果回到 Agent，过核心监听者和扩展，追加进会话文件，同时通知界面。

- 贯穿全程的是**同一个调用编号**：完成通知、Agent 状态里的结果、会话里的记录，是**三个不同的完成条件**。
- 四类连线：调用（蓝）、事实（橙）、投影读取（绿）、事件（紫）。

### 1.14 Pi 的三条启示与二次开发

**三条判断**：
1. 先给每份状态定主人，再定谁能投影、谁能改、谁能订阅。**有事件总线不等于有所有权。**
2. 应用消息保留表达力，到模型边界再收窄；投影要能追回原记录。
3. 工具结果按使用方拆开，同时定好对不上时怎么办。

> 如果只是做短会话的纯文本工具，以上都可以先不做。

**二次开发三档**：

| 档位 | 方式 | 说明 |
|---|---|---|
| 轻 | Skill | 指令文件，零代码 |
| 中 | 扩展 | 钩子拦截工具、改写结果、参与续跑；加自定义工具；配置 MCP 曝光档位 |
| 重 | SDK | 把内核嵌进自己的产品，入口和界面自己做 |

**上生产前要补三块**：
- 权限：默认继承启动进程权限，没有逐工具权限系统。
- 持久化：写失败只回滚自己的记录，不保证崩溃恢复。
- 多人会话与集中治理。

## 2. 第 03 期：Codex —— 一个内核撑起多种产品

### 2.1 背景

- OpenAI 官方说明：网页版、CLI、IDE 插件、桌面 App 背后是**同一套 Harness**。
- Codex 好用有相当一部分来自模型：**GPT-5-Codex** 针对 Codex 里的 agentic coding 进一步优化过，也更遵守 AGENTS.md 的规矩。**模型和 Harness 是一起调出来的。**
- 适用场景：团队要把成熟的 coding agent 嵌进自己的产品。
- 看点：Agent 出问题常常出在**交接**上（模型说完了、工具还在跑；工具返回了、结果没进下一轮）。Codex 最值得看的，就是它怎么接住每一次交接。

### 2.2 六个模块与对应问题

| 问题 | 模块 |
|---|---|
| 怎么接到不同的产品界面 | App Server（产品协议层） |
| 谁调模型、一段工作怎么推进 | Core 会话 |
| Function Call 怎么落地、能不能执行 | 工具系统 |
| 上下文怎么维护 | 上下文与模型 |
| 会话怎么存、怎么恢复、记忆放哪 | 存储与恢复 |
| 插件从哪接 | 扩展 |

### 2.3 App Server：产品协议层

- CLI、SDK、IDE、第三方客户端最终都汇到 App Server。
- 它**不执行**，只做三件事：
  1. 校验和转发请求；
  2. 把内部事件翻译成客户端能懂的通知；
  3. 需要审批时反过来问客户端。
- 时序：发起工作 → 立即回“进行中” → 一条条进度通知 →（中途审批，客户端回复后才继续）→ 工作结束。所以**拿到响应 ≠ 活干完了**。
- 会话三层模型：
  - **Thread**：整个会话（与操作系统线程无关）；
  - **Turn**：一段工作；
  - **Item**：其中一条消息或一次命令。
  - 界面按状态渲染，不用从文本里猜。

**演进过程（被需求逼出来的）**：
只有终端界面 → 做 VS Code 插件时试过直接暴露成 MCP server，语义对不上 → 先上一套模仿终端循环的应急协议 → JetBrains、Xcode、桌面端多 Agent 编排陆续接入 → 规范成**要求向后兼容的正式协议**。

**判断标准**：只有一个宿主，直接调库；多个宿主各自演进、又要共享审批和取消语义，才值得付这层协议的维护成本。

### 2.4 Core 会话

- 负责一个 Agent 会话的长期服务：模型连接、MCP、进程管理、存储、扩展。
- 对外**只开两个口：一个进输入，一个出事件。**
- 原因：模型调用可能很长，这期间系统必须照样能收新输入、审批回复和中断。
- 提交输入可以只等到“系统决定怎么处理”就返回；调用方不再等了，已排队的输入也不会撤回。
- 代价：调用方必须清楚自己到底等到了哪一步。

**常见误解：模型说完了 ≠ 这段工作结束**

```
每次调模型前拍请求快照 → 调用中收集工具结果 → 返回后判断：
  模型还有后续 或 队列里有新输入 → 再来一轮
  都没有 → 进停止钩子（钩子还能带追加内容要求继续）
```

停下来也不代表结果被验收过。只盯模型那一次回答，会误判整个系统的行为。

### 2.5 两层上下文（作者认为最值得借鉴）

| 层 | 管什么 | 生命周期 |
|---|---|---|
| 外层（整段工作上下文） | 身份、配置、授权 | 整个 Turn |
| 内层（请求快照） | 这一次用的设置、环境、工具目录 | 单次请求，冻结 |

示例：工作中途工具目录从 v1 升到 v2，新请求用 v2；但第一次请求发起、晚一点才执行的调用，手里仍是 v1 快照，照旧找 v1 的执行器。而**文件授权实时回到这段工作去查**。

一句话：**工具目录跟请求走，授权跟这段工作走。**
- 更简单的替代方案：整段冻结目录，代价是更新要等下一轮。
- 这套机制官方没写过，是作者从源码里读出来的。

### 2.6 工具系统：Function Call 三层

| 层 | 回答的问题 | 内容 |
|---|---|---|
| 第一层 | 看不看得见 | 内置工具、MCP、扩展、客户端动态工具组成本次计划；给模型的声明和执行用的注册表出自**同一份计划** |
| 第二层 | 能不能一起跑 | 调用先落记录，再拿请求快照找执行器，处理取消和结果转换 |
| 第三层 | 该不该批准 | 本机命令的审批、沙箱、重试 |

**注册了、看得见、允许执行，是三个不同的集合。**

**并发由两个机制分工**：
- **谁能同时跑 → 读写锁**：能并行的拿读锁，要独占的拿写锁（写锁要等前面的读锁全部释放）。
- **谁先进历史 → 有序队列**：按发起顺序收结果，2、3 早跑完也要等 1。
- 比全串行保住了吞吐，比按完成顺序提交多了确定性；代价是队头等待（**head-of-line blocking**）。

**细节**：调用**先记录再执行**；取消时没派发的调用也补一条“中止”结果，**历史里不留没有回音的调用**。

### 2.7 安全分工

```
策略层：算出要不要审批
协调层：管审批、沙箱选择、重试
审批来源：策略 / 人工 / 自动审查
沙箱管理：选本机用哪种约束
```

- MCP 和客户端动态工具有各自的处理器，**本机沙箱的结论管不到它们**。
- 最容易踩的坑：**自动审查批准了原动作，不等于批准了提权之后的重试。**
- 别给所有调用贴同一张安全标签。

### 2.8 上下文与模型

- **内部历史和模型输入分开**：工具结果带着 Turn 和模型信息记进内部历史；请求前再投影一份给模型：
  - 规范格式；
  - 模型读不了的图片和文件变成文字占位；
  - 拼上快照里的指令和工具计划。
- 模型连接：管厂商、认证、备用；每段工作开一个连接做增量请求；**认证换人就清缓存**。
- 拆开的原因：审查和恢复要的信息，跟推理要的不一样。
- 后台压缩：装回去之前先核对**版本、模型、认证**，对不上就丢掉。

### 2.9 存储与恢复

- 四个动作分开：**追加、检查点、刷盘、关闭**。
  - 部分写入可在后台推进；刷盘和关闭时必须等它们完成，失败要报出来。
  - 产品上说“已保存”，要等刷盘到可读的边界；**收到界面事件不算。**
- 恢复会话：先拿到**写入权**，再返回**权威历史**，避免基于旧快照接着跑。
- 中断：先核对是哪段工作，等核心确认中止。
- 恢复能重建会话，但**已对外执行的操作回不去**，得另外设计补偿。

### 2.10 记忆（三家中唯一有独立记忆模块）

- **生成记忆**和**使用记忆**是两个独立开关。
- 有规则筛选哪些记录能拿去生成记忆：
  - 可以：对话、工具调用及结果；
  - 不可以：开发者指令、推理过程、压缩记录。
- “遇到外部内容就停用记忆”开关：打开后，会话里一混进联网搜索这类外部内容，这段会话就被标记为**被污染**。
- 记忆存在本地数据库，CLI 有清空命令。
- 具体怎么生成、怎么召回在单独的包里，作者没有展开。
- 每次请求的快照里都会记下当时的 AGENTS.md。

### 2.11 扩展

- **按阶段接入**：上下文、工具、模型请求、Turn 输入、生命周期，各有各的入口。
- 扩展数据按 **session / thread / turn** 三个范围存储。
- 工具结局四种：**完成、被拦、失败、中止**；取消甚至可能早于“开始”回调。
- 停止钩子能在收尾时要求继续。
- 扩展作者要按阶段契约写代码，平台方要承担接口演进成本。
- MCP、Skills、动态工具、内部扩展的接入点各不相同，**别混成一类**。

### 2.12 状态归属表（Codex）

| 状态 | 归属 |
|---|---|
| 翻译（不推进执行） | 协议层 App Server |
| 活跃会话 | 会话管理 |
| 长期服务 | Core 会话 |
| 身份和授权 | 整段上下文 |
| 仅这一次 | 请求快照 |
| 内部历史 | 历史管理 |
| 连接 | 模型连接 |
| 能不能执行 | 调用调度 |
| 审批 | 审批协调 |
| 权威历史、刷盘 | 存储层 |

常见误区：**长期服务 ≠ 这一次的能力；能并发 ≠ 按完成顺序进历史；追加 ≠ 刷盘。**

### 2.13 一次 Turn 走一圈

1. 输入经 App Server 交给 Core 会话。
2. 拍下请求快照，与投影好的历史拼成请求，经模型连接流式发给模型。
3. 工具调用交给调度，按准入执行，按发起顺序收回。
4. 结果记进历史，再交给存储层。
5. 内部事件翻译成通知，回到客户端。

- 每一步都说得清依据的是哪份状态、结果交给了谁，这就是这套设计的价值。
- 与前两期最大的不同是**紫色事件线**：内部事件被翻译成一套**稳定、向后兼容的客户端协议**。
- 没有 DeepSeek 式的通用插件容器，分层靠显式上下文结构加 **Rust 所有权规则**。

### 2.14 Codex 的三条启示与二次开发

**三条判断**：
1. 宿主多、各自演进，才值得单独一层产品协议；否则直接调库。
2. 只要支持运行中更新，就把“这次请求看到的能力”和“执行时找谁要授权”分开存。
3. 工具可以并行，进历史要有确定顺序；**普通错误转成工具结果让模型自己处理，致命错误往上抛。**

> 底层逻辑：**先定允许什么变化，再定状态归谁、边界多厚。**

**二次开发三档**：

| 档位 | 方式 |
|---|---|
| 轻（零代码） | AGENTS.md 写清项目规矩 + 接 MCP 和 Skills |
| 中（写代码调用） | 一次性脚本任务用 `exec`；要启动、恢复、流式控制，在应用里用 SDK |
| 重（Agent 即产品） | 接 App Server，或直接改内核 |

- 官方选法：**Agent 本身就是产品，才上 App Server。**
- Apache 协议，允许商用；代价是改内核要动 Rust，代码量也大。

## 3. 第 04 期：三家横评

### 3.1 收敛的判定标准

要同时满足三条才算“收敛”，避免沦为找相似点：
1. 解决**同一个工程问题**；
2. 实现手法**完全不同**；
3. 付出的代价和换来的收益是**同一种**。

三个团队、两种语言、彼此没有协作，却有**六处设计几乎一样**。对照维度：入口和协议、驱动、请求和长期状态、工具并发、结果表示、事实和存储、生命周期。

### 3.2 六处收敛

**① 核心留可替换余地（路径不同）**

| 家 | 路径 |
|---|---|
| DeepSeek | 一开始就设计好，连 agent loop 都是插件；代价是接口契约必须很严，否则复杂度摊给每个实现方 |
| Codex | 需求驱动：App Server 从 VS Code 插件的应急协议演进成多宿主正式协议 |
| Pi | 需求驱动：从不做 MCP，到借 Codemode 解释器沙箱接入 |

结论：提前做就提前付契约成本；等需求来就先用够用的方案。

**② “这次请求看到的”与“长期记住的”分开管**

| 家 | 做法 |
|---|---|
| DeepSeek | 每次请求两道锁：先把模型和准用工具拍成快照，再绑定当前版本的模型适配器；长期事实留在 Session |
| Codex | 两层上下文：请求快照冻结能力，整段上下文管身份和授权，授权实时查 |
| Pi | 先挑本轮看哪些消息，不写回会话文件；长期记录留在会话记录 |

共同问题：这次请求看到的保持多久不变？长期记住的怎么不被一次请求弄脏？
共同代价：多一层转换，多一套生命周期。

**③ 工具结果服务的不只是模型**

| 家 | 做法 |
|---|---|
| DeepSeek | 调用和结果记进 Session，分别生成模型历史、业务视图、磁盘记录 |
| Codex | 记进内部历史 → 投影给模型 + 交给存储层 + 事件翻译给客户端 |
| Pi | 一开始就拆三份：模型 / 界面 / 程序；不一致时清掉旧的程序数据 |

结论：多种表示并存，就必须有一条“对不上时怎么办”的规则。

**④ 工具并行执行，进历史按模型发起顺序（手法差别最大，结论最一致）**

| 家 | 做法 |
|---|---|
| DeepSeek | 前缀一就绪就提交（连续跑完的一段先提交） |
| Codex | 读写锁管谁能同时跑 + 有序队列按发起顺序收 |
| Pi | 等整批收齐，再按原位置写回 |

- 共同代价：队头等待。共同收益：模型看到的顺序始终等于它自己发起的顺序。
- **作者的推论**（三家官方都没专门解释）：工具调用是模型自己生成的，**调用顺序本身就是上下文的一部分**。按完成先后塞回去，等于往上下文里塞进一个模型从没生成过的顺序，后果难以预测。保序真正保护的是**上下文一致性**。
- 但保序只管结果怎么排；外部操作谁先谁后，还得靠工具自己声明能不能并行。

**⑤ 退出和重载有严格顺序**

| 家 | 做法 |
|---|---|
| DeepSeek | 组件按注册逆序清理；默认循环先停驱动、等手头工作收完，再释放资源、确保落盘 |
| Codex | 中断先核对是哪段工作，等核心确认中止；未派发的调用补中止结果 |
| Pi | 重载先等旧会话关闭、作废旧运行器，再重建、重新绑定 |

结论：三家都**不承诺自动撤回已发生的外部操作**，清理从来不是免费的。

**⑥ “已保存”要对齐真正的存储边界**

| 家 | 做法 |
|---|---|
| DeepSeek | 先进内存 → 排队写文件 → 刷盘过了耐久屏障才算 |
| Codex | 追加与刷盘分开，刷到可读边界才算，收到界面事件不算 |
| Pi | 同步追加文件，但通知界面早于追加；写失败只回滚自己的记录；同步写也不等于断电不丢 |

结论：三家都把“界面看到了”和“真正存住了”当成两件事。

### 3.3 两处分歧

**① 生命周期怎么管**

| 家 | 做法 |
|---|---|
| DeepSeek | **Cordis** 容器统一管理：依赖没了自动下线、回来了自动装回，agent loop 也住在容器里 |
| Codex | 不用通用容器，靠显式上下文结构 + Rust 所有权手写 |
| Pi | 居中：核心靠显式类型和函数组合，扩展有自己的生命周期钩子 |

三家连要不要通用容器都没达成一致，却在前六处给出相同答案。这说明那几处收敛来自**这类系统本身的约束**，与框架无关。

**② 记忆**

| 家 | 做法 |
|---|---|
| DeepSeek | 无独立长期记忆；会话可重新打开或分叉；跨对话记忆要自己写插件，想让模型看到的都必须先进 Session |
| Pi | 无独立长期记忆；靠续接、压缩摘要、启动时拼进提示词的 AGENTS.md |
| Codex | 有独立记忆功能：生成与使用分开开关、筛选规则、外部内容污染标记 |

对企业来说这一项最该自己拿主意：**记忆交给 Harness，还是放进自己的业务层。**

### 3.4 搭 Agent 平台的判断清单

1. **给核心留余地**：先用够用的方案，出现第二个独立需求再抽象；要一开始就可替换，就把契约定严。
2. **分开两种状态**：这次请求看到的和长期记住的，别共用一个对象的生命周期。
3. **结果按使用方拆**：至少模型、界面、程序三类，并配一条一致性规则。
4. **并发先问依赖**：工具之间有没有隐式依赖？模型对顺序敏不敏感？
5. **“已保存”对齐存储边界。**
6. **清理写清顺序**：取消不等于回滚。

### 3.5 巧合还是必然？—— 必然（作者观点）

一个持续运行、接收用户输入、调外部工具、再把结果喂回模型的系统，只给工程师留了几个关键决策：
- 驱动逻辑锁不锁死；
- 状态按什么粒度分层；
- 结果给几种读者；
- 并发和顺序怎么取舍。

答案本来就不多，三家撞在一起不奇怪。

### 3.6 再看“模型 × Harness”

- **乘法里有配对**：前沿厂商会把模型和自家 Harness 一起调（如 GPT-5-Codex）。用哪家的模型，往往配它原生的 Harness 最顺手。
- **有门槛**：低于门槛，模型能力会大量漏掉。OpenAI 举过例子，同一个模型只改两项 Harness 设置，分数差了**将近三倍**。
- **过门槛后收益递减**：Pi 作者观察到，只给一个终端会话的极简 agent 在 Terminal-Bench 上照样排得不错。
- 日常任务换哪家 Agent 差别越来越小；长链路复杂任务（如大型 coding）的差距主要来自**模型以及它与 Harness 的配合**。

### 3.7 选型

| 需求 | 选 | 协议 | 接入档位 | 代价 |
|---|---|---|---|---|
| 把成熟 coding agent 嵌进产品，要协议稳定 | **Codex** | Apache | exec / SDK / App Server | 改内核要动 Rust，代码量大 |
| 轻量、读得完，深度定制上下文和交互 | **Pi** | MIT | Skill / 扩展 / SDK | 生产要自补权限、持久化、多人治理 |
| 有平台团队，想把每个模块都换成自己的 | **DeepSeek Harness** | MIT | 全插件（含 agent loop） | 还在早期，契约要定得很严 |

**系列各期看点**：DeepSeek 看插件内核和一本账；Pi 看三种表示和结果三分；Codex 看产品协议和两层上下文；横评看三家撞在哪、钱该花在哪。

## 4. 补充：DeepSeek Super-agent（视频笔记）

### 4.1 Agent 协作的三个进化方向

| 方向 | 含义 | 代表 |
|---|---|---|
| **Harness** | 让模型能动手：单个 Agent 的架构，模型是大脑，靠工具、上下文、运行循环执行任务 | DeepSeek Harness、Pi、Codex |
| **Proactive Agent** | 主动式 Agent：自己盯着邮件、日程、群消息，有事才来找你（个人助手只是其中一种用法） | xAI、Meta、OpenAI、Anthropic；国内 Today AI |
| **Multi-agent** | 一群 Agent 分工，**关键看谁来派活** | 见下表 |

**Multi-agent 四种派活模式**：

| 模式 | 谁派活 |
|---|---|
| Subagent | 主 Agent 临时派 |
| Agent Team | 各 Agent 从共享任务表领 |
| Router + Worker | 专职调度者派活，自己不干活 |
| Agent Swarm | 派活能力训练进模型 |

### 4.2 Super-agent 设计

- **三种能力合流**：底座是 DeepSeek Harness（Harness），能盯着 GitHub、飞书（Proactive），采用 Router + Worker 分工（Multi-agent）。
- **整体流程**：

```
事件入口（群消息 / PR 评论 / CI 结果）
  → 代码筛选 + 权限校验
  → Router 调度层派活
  → Worker（开多少个 Session 由 Router 自己管）
```

- **双层分工**：

| 角色 | 职责 | 模型 |
|---|---|---|
| Router | 前台调度：接话、派活、记住全局，自己不干活；统一对外回复 | 轻量模型即可 |
| Worker | 一件事一个，上下文隔离；干完只向 Router 汇报 | 最强模型 |

- **派活实验**（合成负载对照）：
  - 提示词写“合适的时候用” → 5 次 0 次派活，全自己扛；
  - 改成“优先派出去” → 5 次派了 4 次，剩下 1 次嫌活小又自己干了。
  - 结论：**派不派活不能只靠模型自觉，分工要写进架构，别只靠提示词。**

### 4.3 其他设计要点

- **事件驱动**：唤醒 Agent 的是业务里发生的事（群消息、代码评论、CI 结果），不是等你敲提示词。先用代码筛选事件，**权限由代码执行**，再交给模型判断。
- **上下文管理**：
  - 同一个 PR 的后续评论直达原 Worker，不再经过 Router 重新派活；
  - 当前用得上的给完整内容，其余给**可检索的目录**，要用再取；
  - **浪费上下文窗口就是浪费模型的智能。**
- **交互设计**：
  - 耗时命令异步执行：先回一句“已启动”，结果回来算一条新消息，用户随时能插话；
  - 在哪说话就怎么交代：群里只在需要拍板或验收时开口，GitHub 上才写完整说明。
- **运行与监控**：
  - 大脑和记忆放云上，电脑只负责动手执行，电脑合上 Agent 照样在线；
  - 看 Agent 要看**进展**，别只看是否还活着：用 **Watchdog** 定时检查每个 Worker 有没有真进展，发现异常就介入。
- **成本与边界**：
  - 并行和全局协调都有成本，读缓存的 Token 是单 Session 方案的 **2~4 倍**；
  - 原型能试，但只能在小范围、可信环境里用；开源不等于装上就能用；
  - 命令执行要用**独立系统账号**。

## 5. 高频“不等于”清单（排障与面试速记）

| 看到的现象 | 不能推出 |
|---|---|
| 工具“开始”事件 | 外部动作已发生 |
| 工具“完成”通知 | 模型已看到结果 |
| 完成顺序 2、3、1 | 历史顺序也是 2、3、1（实际按发起顺序 1、2、3） |
| 界面隐藏 | 模型看不到 |
| 字段拆开 | 隐私有保证 |
| 能切换模型 | 上下文能无损迁移 |
| 接口统一 | 语义无损 |
| 会话文件 | 模型上下文 |
| 流式临时状态 | 持久记录 |
| 有事件总线 | 有所有权 |
| 工具已注册 | 模型看得见 / 允许执行 |
| 拿到响应 | 活干完了 |
| 模型说完了 | 这段工作结束 |
| 停下来了 | 结果被验收过 |
| 自动审查批准原动作 | 批准了提权后的重试 |
| 追加 | 刷盘 |
| 收到界面事件 | 已保存 |
| 取消 / 恢复 | 回滚已做的外部操作 |
| 项目信任 | 逐工具权限系统 |
| 脚本沙箱受限 | 被调用的命令也被隔离 |
| 长期服务 | 这一次请求的能力 |

## 6. 面试问答提纲

**Q1：什么是 Agent Harness？它和模型是什么关系？**
Harness 是模型以外的运行框架：驱动循环、工具系统、上下文管理、状态与存储、扩展、对外协议。Agent 能力 ≈ 模型 × Harness：低于门槛时模型能力大量漏掉（同一模型改两项 Harness 设置，分数可差近 3 倍）；过门槛后收益递减。通用层趋同可复用，业务层（工具、知识、规矩、评测）才是护城河。

**Q2：多个工具并行调用，结果怎么写回历史？为什么？**
并行执行，但按模型发起的顺序写回。DeepSeek 前缀就绪先提交，Codex 用读写锁加有序队列，Pi 等整批收齐再按位置写回。原因：调用顺序是模型生成的，属于上下文的一部分，乱序写回会引入模型从未生成过的顺序。代价是队头阻塞。保序不负责外部副作用的先后，那要靠工具声明能否并行。

**Q3：怎么避免运行中更新（工具升级、配置变更）把一次请求搞乱？**
分两层：请求快照冻结本次能力（工具目录、设置、环境），整段工作上下文管身份和授权、实时查询。也就是工具目录跟请求走、授权跟这段工作走。更简单的方案是整段冻结，代价是更新要等下一轮。

**Q4：为什么工具结果要拆成多份？**
模型、界面、程序三类读者需求不同。只有一份文本时，界面要展示结构化数据就得反解析自然语言。拆分后必须有一致性规则，例如 Pi 在模型那份被改、程序那份未同步时直接清掉旧数据。拆分也不等于隐私保证。

**Q5：Agent 的上下文怎么管理？**
存储与模型输入分离：会话记录（Pi 是树结构）→ 投影（套压缩摘要、合编辑记录）→ 转成模型格式。投影要能追回原记录。界面隐藏、存储保留、模型可见是三个独立开关。按需加载：Skill 只放名称和描述，MCP 工具可以分档曝光（直接给、只给脚本调用、搜索后加载）。浪费上下文窗口就是浪费模型智能。

**Q6：Agent 记忆怎么做？**
DeepSeek 和 Pi 没有独立长期记忆，靠会话续接 / 分叉、压缩摘要、AGENTS.md。Codex 有独立记忆：生成和使用分开开关，筛选可入记忆的记录（排除开发者指令、推理过程、压缩记录），外部内容进入会话即标记污染。企业要先决定记忆放 Harness 还是业务层。

**Q7：什么时候需要单独做一层产品协议（如 Codex App Server）？**
只有一个宿主时直接调库；多个宿主各自演进、又要共享审批和取消语义时才值得。协议层只翻译、不执行；会话分 Thread / Turn / Item 三层，界面按状态渲染。Agent 本身就是产品，才上 App Server。

**Q8：Agent 的“已保存”怎么定义？取消和恢复要注意什么？**
已保存要对齐真正的存储边界（刷盘或过耐久屏障），界面事件不算；追加和刷盘要分开。取消时未派发的调用补中止结果，历史里不留无回音的调用。恢复会话先拿写入权、再取权威历史。已发生的外部操作回不去，需要额外设计补偿。

**Q9：Agent 的安全怎么做？**
注册、可见、允许执行是三个集合。策略层判定是否审批，协调层管审批、沙箱和重试，审批可来自策略、人工或自动审查。MCP 和动态工具不受本机沙箱结论约束。提权后的重试要重新审批。生产环境里命令执行用独立系统账号，权限由代码执行，不交给模型自觉。

**Q10：Multi-agent 怎么设计派活？**
四种模式：Subagent、Agent Team、Router + Worker、Agent Swarm。Router + Worker：Router 用轻量模型负责调度和全局记忆、不干活；Worker 用强模型、上下文隔离、只向 Router 汇报。DeepSeek 实验说明提示词约束不可靠（“合适时用”5 次 0 派），分工要写进架构。配套设计：事件驱动、同一任务后续消息直达原 Worker、异步执行、Watchdog 监控进展。成本上读缓存 Token 是单 Session 的 2~4 倍。

**Q11：模型的普通错误和致命错误怎么处理？**
普通错误转成工具结果，让模型自己处理；致命错误往上抛。Pi 的模型接入层要求出错不抛异常，而是编码成流里的事件。

**Q12：如果让你基于开源 Harness 做二次开发，怎么选？**
- Codex（Apache）：嵌入成熟 coding agent、要协议稳定；按 exec、SDK、App Server 三档接入。
- Pi（MIT）：轻量可读、深度定制上下文；Skill、扩展、SDK 三档；需自补权限、持久化、多人治理。
- DeepSeek Harness（MIT）：有平台团队、要全模块可替换；还在早期，契约要定严。
- 原则：模型选，不自己造；通用 Harness 用，不重写；业务层自己建。
