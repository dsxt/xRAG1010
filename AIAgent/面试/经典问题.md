# 问题01
agent领域RAG检索中：用户问了小细胞癌，检索出来的答案是细胞癌，你怎么定位排查并修复问题

“小细胞癌”被检索成“细胞癌”，本质是**检索粒度失配**：在稠密向量空间里，“小”作为限定修饰词的判别力被“细胞癌”这个核心概念的语义引力淹没，系统退化为对上级概念（“细胞癌”）的匹配。这不是单一环节的 bug，需要沿 Agentic RAG 的链路逐层定位。

---

## 第一步：定位——用 Trace 拆开链路，确认“丢在哪一层”

Agentic RAG 的检索不是一个黑盒调用，而是一条包含多个可观测 Span 的链路。按以下顺序逐层核对，就能把“检索错了”拆成具体问题：

**① Query 改写 Span：关键修饰词是否在改写中被丢弃？**
Agentic RAG 通常默认包含查询改写或分解步骤。检查改写后的 query 是否仍然完整包含“小细胞癌”这个短语，还是被 LLM“概括”成了“细胞癌相关”或“细胞癌治疗”。LLM 驱动的查询分解有时会偏离原始临床意图，引入噪声。如果改写后的 query 已经丢了“小”，后续检索再准也回天乏术。

**② 检索 Span：稠密向量是否把“小细胞癌”和“细胞癌”拉到了同一邻域？**
这是最可能的故障点。通用 Embedding 模型对“小细胞癌”和“细胞癌”的余弦相似度往往很高，因为二者共享“细胞癌”这个强语义核，而“小”在通用语料中的判别权重不足以在向量空间中拉开距离。医疗领域有完全平行的案例：**“小细胞肺癌”与“非小细胞肺癌”在向量空间中相似度常常在 0.85 以上**，仅靠纯稠密检索无法可靠区分这两种临床意义截然不同的亚型。你的 case 同理：稠密检索擅长“意思相近”，不擅长“必须逐字命中的修饰限定”。

**③ 重排 Span：如果正确文档被召回了，重排是否把它踢出了 top-K？**
检查召回集合中是否**存在**同时讨论“小细胞癌”与“细胞癌”区分的文档，但重排器因为整体语义相似而把它排到了后面。重排器如果只看 query 与 chunk 的整体语义相似度，同样可能放大“细胞癌”而非“小细胞癌”的权重。

**④ 上下文构建 / 生成 Span：截断或拼接是否进一步稀释了关键约束？**
即使检索召回了正确文档，如果上下文构建时“小细胞癌”的关键段落被截断，或者被大量“细胞癌”泛化内容包围，生成阶段仍然会输出错误答案。

**⑤ 最终校验：是否有针对“实体完整性”的检查？**
如果链路末端没有校验检索结果或草稿答案是否保留了“小细胞癌”这个完整实体，系统就无法自动发现并触发修复。


## 第二步：修复——按环节分层干预，稠密检索打底，精确匹配兜底

### 修复层 1：Query 改写环节——强制保留“约束短语”

不要让改写模型自由压缩医学术语。在改写 Prompt 中明确要求：**从原问题中逐字复制疾病/实体名称作为检索约束短语，不得改写、缩写或省略修饰词**。MedHopper 在 biomedical 多跳 QA 中的做法可以直接借鉴：让模型从问题中 verbatim 抽取短约束短语，并用这些短语作为额外的检索 query，且强制过滤确保抽取的短语确实出现在原问题文本中。对于“小细胞癌”，这意味着改写输出中必须同时保留原始短语“小细胞癌”，并可以将其作为独立检索通道的 query，而不是只依赖改写后的“细胞癌治疗”。

### 修复层 2：检索环节——混合检索，让 BM25 负责“小”的精确命中

这是解决该问题的**核心工程手段**。BM25 对**必须逐字命中的字符串**具有稠密检索无法替代的优势：只要语料中出现了“小细胞癌”这个短语，BM25 的词项匹配就会给它高分，而不管“细胞癌”在语义上多么邻近。具体落地：

- **双路召回**：稠密向量负责语义泛化（确保相关文献不被漏掉），BM25（或中文适配的字符级/词级稀疏检索）负责精确短语命中（确保“小细胞癌”不被降级为“细胞癌”）。两路各自召回、融合去重，谁漏了另一路兜底。
- **BM25 的中文医学适配**：医疗 RAG 中建议使用**字符级分词**结合 BM25，针对药品名、诊断标准、疾病亚型等专有名词做精准锁底，避免跨病症泛化。“小细胞癌”与“细胞癌”仅差一字，字符级匹配能直接命中“小”这个关键修饰。
- **融合权重按 query 类型调**：纯稠密检索在“必须逐字命中”场景下会系统性漏召回。对于包含明确疾病亚型术语的 query，可以适当提高 BM25 路的融合权重，或在使用 RRF 融合时给稀疏路更高的先验。

### 修复层 3：重排与上下文环节——把“实体完整性”作为排序信号

- 重排器不应只看整体语义相似度。可以引入一个轻量的**实体完整性检查**作为重排特征：候选 chunk 是否包含查询中的**完整核心实体短语**（逐字或近似匹配“小细胞癌”）。包含完整实体的 chunk 获得加权，仅包含上级“细胞癌”的 chunk 降权。
- 上下文构建时，优先保留**同时出现“小细胞癌”并对其做出限定/区分的段落**，避免被泛化“细胞癌”内容挤占 Token 预算。

### 修复层 4：Agent 自省循环——让检索失败可被发现和重试

Agentic RAG 相对于经典 RAG 的关键优势，在于它可以**对检索结果打分，不合格就重写 query 再检索**。在你的场景中，可以在检索后加一个轻量评分节点：

- **检查检索结果是否覆盖了查询中的约束短语**（例如，“小细胞癌”是否在至少一个召回 chunk 中逐字或近似出现）。
- 如果**没有任何召回 chunk 包含完整约束短语**，说明检索很可能发生了粒度降级，触发**查询修复**：用原始约束短语（或“小细胞癌”+核心意图）重新构造检索 query，而不是继续使用可能已经丢失修饰词的改写 query。
- 修复后重新检索，直到约束短语被覆盖，或达到重试预算后走降级路径（如返回“未找到针对小细胞癌的精确信息”而非用“细胞癌”内容强行作答）。

MedHopper 在答案验证失败后也有类似的 **query repair** 机制：收到原始问题、当前策略和最近验证过的实体，重新生成针对特定实体的短检索 query。这说明在医疗 RAG 中，**检索失败后的定向修复**是已经被验证有效的工程模式。


## 一个最小可落地的修复组合

如果只能做一件事，**先加 BM25 混合检索**，它对“小细胞癌→细胞癌”这类修饰词丢失的修复效果最直接、确定性最高。然后在 Query 改写 Prompt 中加入 **verbatim 约束短语保留规则**，防止 Agent 在改写阶段主动丢掉“小”。这两步覆盖了绝大多数粒度降级 case。如果 Agent 框架支持自省循环，再叠加**约束短语覆盖率检查 + 重试**，作为兜底防护网。

**排查顺序上**，先用 Trace 看改写后的 query 是否完整：如果“小”在改写阶段就没了，优先修改写；如果改写保留了完整短语但稠密检索仍然返回“细胞癌”内容，优先上混合检索。两者都修完后，用同一批包含“小细胞癌”“非小细胞癌”“小细胞肺癌”等细粒度医学实体的 query 做回归，确认 top-K 中精确亚型文档的召回率不再被上级概念文档碾压。






三道题都按「先止血、再保证状态一致、最后把延后的事写成有主人的下一步」来答。

## 1. 停止后立刻再发：只展示最后一次，并真正停掉上一次推理

前端和后端各守一层，两层用同一个请求代号对齐。

**前端：用递增代号把「当前这次」钉死。** 每次发送（点停止也算一次作废）把代号加一，界面只采纳代号等于当前值的片段。点停止或立刻再发时做三件事：作废上一次连接（浏览器侧中断读取）、代号加一、输入区切到新一轮。旧连接上晚到的字、报错、收尾包，因为代号对不上，直接丢掉，不会写进新气泡。这样即使停止和新消息几乎同时发生，也不会把上一轮的尾巴画进下一轮。

**后端：连接断开不够，要有一条能传到推理引擎的取消。** 网关或服务在客户端断开，或收到显式取消时，把这个请求标成已取消，并把取消标记顺着调用链传到真正占着 GPU 的那一层。推理按 token（或一个调度步）检查这个标记，命中就不再算下一个 token，并把这条序列从批处理里拿掉，释放它占用的 KV cache。只在请求入口判断一次是不够的，模型会把已经在跑的步算完。

显式取消要和断开连接一起做。前面有反向代理或缓冲时，连接断开常常传不到推理进程，显式取消才靠得住。取消按请求代号做成幂等：重复取消、取消一个已经结束的请求，都当成功。服务端不再往这条流上写；万一还有残留包，前端仍用代号丢掉。

停止后再发新消息，是「作废 N、发起 N+1」两件事。N 的取消和 N+1 的生成互不覆盖：N 停算，N+1 作为新请求进队列。

1.前端记录每轮次对话递增id，点击停止更改当前轮次对话状态并发送后端，后端接受消息取消流式输出并通知大模型侧停止，前端创建新的对话轮次并把新消息发送给后端，开启新一轮次对话

## 2. Embedding 换型导致答非所问，负责人联系不上

先恢复检索，再补流程。这类故障的典型原因是：查询向量换成了新模型，库里仍是旧模型的向量，两个空间对不上，召回的文档是错的，生成只能在错上下文上作答。

**当晚：**

1. 核对影响面：从模型切换的时间点起，哪些租户、哪条检索链路、错答是否集中在「检索命中差」而不是生成参数。
2. 立刻回切到上一版「模型 + 索引」这一对。只把查询模型退回去、索引仍是新向量，或者只退索引、查询仍用新模型，都会继续错。若新索引还在建、旧索引还在，就把流量指回旧索引，这是分钟级的止血。等重新向量化再修，会让故障继续到天亮。
3. 用一小套固定问题看召回是否回到切换前的水平，确认后再对客户群说：原因是检索模型版本不一致，已切回稳定版本，并给出你验证过的范围。先有结论再展开，避免群里持续空等。
4. 把证据留下：切换时间、版本号、回切动作、召回对比。负责人回来接手的是一份已止血的记录，不是一条「好像是 embedding」的猜测。

**根上避免再发：**

- 查询编码器和索引是一个版本单元。上线时校验维度、归一化方式、模型标识一致，不一致就拒绝启动，而不是带着错空间对外服务。
- 新模型先双索引或小流量对照，用固定评测集看召回，退步就不放全量。回切是改一个流量指针，不是临时重算全库。
- 模型版本写死在配置里，变更走和生产发布一样的窗口：有值班代理人、有回切步骤。负责人休假时，换型要么已具备可回切的旧索引，要么不做。
- 线上看检索分数分布、空召回比例、点踩率。这些在客户投诉之前就会偏离，告警打到值班通道，而不是只打给休假中的个人。

## 3. 一个人同时面对 P99、CI、30 分钟后的 demo

先用几分钟看清三件事会不会互相卡住，再按这个顺序处理。

**顺序：线上 P99 → demo → CI。** 用户已经在受慢请求影响，这是正在发生的损失。demo 有硬截止时间，拖过 30 分钟就补不回来。CI 挡住的是内部发布，同事还在，可以用替代办法先解开。

若那条紧急修复就是用来压这笔 P99 的，CI 就并进故障处理，排到 demo 前面。否则 CI 保持第三。

**时间怎么切：**

- P99 只做止血：回切最近的变更、扩容、关掉最慢的那条路径，把延迟压回可接受。把根因分析放到 demo 之后，不在这 15 分钟里追完整调用链。
- 止血一有结果，就转向 demo。demo 走一条你刚确认过的路径；若演示依赖的正是出问题的环境，就改到仍健康的环境，并让产品经理按收窄后的脚本讲。你留在故障沟通里，不必亲自操作每一页。
- CI 用一两句话交给同事一个能立刻执行的办法：用上一份成功产物发紧急修复，或先重跑已知会绿的任务。你写明自己回来看流水线的时间。同事这时是在执行，不是在等你排上队。

**被延后的事不丢掉：** 切走之前在值班频道写下一行：现象、你已做的动作、下一步、回来的时间、谁在跟。P99 没查完的根因、CI 的正式修复、demo 若改了脚本，各有一条。给自己定一个回到队列的时间点。高峰过去后同一天收口：延迟恢复并补上原因，流水线重新变绿，和产品经理对一下演示实际走了哪条路径。

三方各收到一句当前状态：用户侧是「慢请求已压住，还在看原因」；产品经理是「演示走哪条路径、你负责哪几步」；同事是「紧急修复怎么先发出去、流水线何时修」。延后的是深挖和正式修复，线上影响和那场 demo 都有着落。

### 4. AWS：ECS、Lambda、API Gateway

- **Lambda**：事件驱动、冷启动、超时 15 分钟、内存配置、容器镜像部署、与 API Gateway/DynamoDB/S3/SNS/SQS 集成。
- **ECS**：Task Definition、Service、Cluster、ALB、Auto Scaling；Fargate 与 EC2 启动类型差异。
- **API Gateway**：REST/WebSocket、限流、鉴权、Lambda Authorizer、Cognito、IAM。
- **选型能力**：短事件任务用 Lambda，长运行/复杂服务用 ECS Fargate，需要底层控制或成本优化时用 ECS on EC2。
- **基础运维**：CloudWatch Logs/Metrics、Secrets Manager、VPC、IAM 最小权限。

### 5. 容器化与微服务

- **Docker**：镜像分层、多阶段构建、环境变量、健康检查、本地 Debug。
- **微服务拆分**：单一职责、独立部署、无状态化、API 版本化。
- **服务通信**：REST/gRPC 同步调用；SQS/Kafka 等异步解耦。
- **弹性与容错**：超时、重试、熔断、降级、幂等。
- **数据一致性**：Database per Service、Saga、事件驱动、最终一致性。

### 6. 平台重构与 Python 升级

- **向后兼容**：API 版本化、字段弃用策略、双写/灰度、迁移窗口、回滚方案。
- **依赖扫描**：检查第三方库对目标 Python 版本的支持、ABI 兼容、C 扩展兼容性。
- **升级路径**：pyenv/uv/python 多版本管理；生产环境优先用容器镜像切换运行时。
- **测试矩阵**：单元测试、集成测试、类型检查、CI 并行跑多 Python 版本。
- **发布策略**：蓝绿/金丝雀、Feature Flag、监控告警、指标验收。

### 7. Linux / 运维 / 可观测性

- **Linux**：进程、端口、日志、文件权限、网络排查、systemd、cron。
- **调试**：容器内日志、远程调试、pdb、性能剖析。
- **可观测性**：日志聚合、Metrics、Trace、慢查询定位、错误率与延迟监控。
- **CI/CD**：构建镜像、运行测试、部署 ECS/Lambda、回滚机制。

### 8. 系统设计高频题

- 设计高并发 Django API。
- REST 迁移到 GraphQL 的方案与风险。
- 单体拆分为微服务，如何保证兼容和一致性。
- Python 小版本/大版本升级落地流程。
- ECS 与 Lambda 如何混合使用。
- 如何治理 N+1、缓存穿透、限流、幂等。

如果继续细化，建议优先把 **Django ORM 优化、graphene-django Resolver 设计、ECS/Lambda 选型、Python 升级迁移流程** 这四块整理成可复述的面试答案。
