# 项目演进

用一套图书管理系统，把后端从几个人的课设走到几百所学校共用的平台。业务始终是登录、查书、借书、还书。书目和借阅记录以 MySQL 为准。

顺序按痛点出现的先后，每一步只引入当时挡不住的那一层：

1. 几个人同时改同一份代码，靠版本控制和分支收拢。
2. 一台机器扛不住访问，也不扛机器宕机，靠多实例、反向代理，再把数据库的读和热点拆出去。
3. 错误代码和不一致的运行环境会让全校一起失败，靠评审、持续集成、同一份镜像、灰度和回滚。
4. 一个大进程里的发布、故障和扩容互相拖累，按业务边界拆成服务。
5. 容器多到人摆不下，用编排维持期望副本数，用服务发现维持地址。
6. 一次下游变慢会沿调用链放大，在每次调用上加超时、受控重试、熔断和隔离。
7. 外部调用方不该看见内部地址，用网关收口路由、鉴权和限流。
8. 借书成功之后的通知和统计不该挡住借书，用消息队列做异步、削峰和解耦。
9. 组件多了之后，偶尔失败已经无法在一台机器上打断点，留指标、日志和链路追踪。
10. 语言混到每种框架各维护一套治理时，再把通信治理挪到服务网格。网格是最后一步，几十个服务、语言还没混开时，框架里的保护就够。

每一节先讲图书馆里为什么会走到这一层，再写这一层用到的技术、框架和必会知识点，然后是 Go、Python、Java 的落地，最后分两句：这一项目现在该怎么做，以及国内公司里这一层的主流组合。版本基线和三份后端笔记对齐：Go 1.27、Python 3.12、Java 21、Spring Boot 3.5、MySQL 8.4、Redis 7。库用仍在维护的线：Gin、GORM、`go-redis` v9、FastAPI、SQLAlchemy 2、`redis-py`、MyBatis、HikariCP、Lettuce。国内存量里 MySQL 8.0、Spring Boot 2 和 Java 8/11 仍然很多，下面把新项目和存量分开写。

| 阶段 | 图书馆里先碰到的事 | 这一步留下的能力 | 还没解决的事 |
| --- | --- | --- | --- |
| 版本控制 | 借书、还书分头改，群里传文件互相覆盖 | `main` 只留能运行的快照，并行工作能收回来 | 程序还在笔记本上 |
| 部署和扩容 | 同学连不上；CPU 打满；MySQL 打满；换一台就掉线 | 多实例、读写分离、热点缓存、共享会话 | 谁都能往生产推代码；机器环境会漂 |
| 代码上线 | 借书判断写反，十几个实例一起换掉 | 评审、自动检查、同一份镜像、先切一小部分流量 | 所有功能仍在一个进程里 |
| 微服务 | 还书的发布把查书一起换掉；借书忙，电子书也得扩 | 按业务独立发布、独立扩容、各自拥有数据 | 容器该放哪台机器，地址一变配置就过期 |
| 容器编排 | 几十个服务、每个几十份，半夜容器停了没人拉 | 声明副本数，服务发现给出还能连的地址 | 下游一慢，调用方一起堵住 |
| 容错 | 用户服务变慢，借书和它的调用方线程被占满 | 超时、重试、熔断、降级、舱壁 | 外部还在记每个服务的内部地址 |
| 网关 | 小程序、App、脚本都要进集群 | 一个入口做路由、TLS、鉴权、限流 | 通知失败会让借书接口报错 |
| 消息队列 | 借书办完还要通知、统计、推荐 | 事件先落队列，消费端按自己的速度处理 | 偶尔失败，看不出死在哪一跳 |
| 可观测性 | 一次借书穿过网关、服务、数据库和队列 | 同一个请求编号串起指标、日志和追踪 | 治理逻辑散在每种语言的框架里 |
| 服务网格 | Java、Go、Python 各写一套超时和重试 | 改超时和限流不必每种语言发一版 | 多一跳，延迟和资源开销上升 |

## 01 版本控制

三个人分工写登录、查书、借书、还书。文件发到群里互相传，后传到的那份盖住先传到的。借期一边是 14 天、一边是 30 天时，翻历史也看不出是谁改的、从哪一版改的。版本控制管的是整个项目目录，并且能把工作树退回到过去某一次提交时的样子。

### 仓库、提交和分支

Git 管的是整个工作树，这份工作树就是一个仓库。一次提交是这一刻全部被跟踪文件的快照，再加上指向父提交的指针。两次提交之间的差异可以算出来，所以能查看某两次提交具体改了哪几行。`git diff` 看的是工作区和当前提交差了哪几行。分支是一个可以移动的名字，指着某一次提交。把分支指回从前某一次提交，工作树回到那时的快照。

远程仓库是大家共用的那一份，放在 GitHub，或者后面公司私有部署的 GitLab 上。改完在本地提交，再推送回远程，别人从远程拉。三个人用的是同一条历史。

`main` 上只放能编译、测试能过、可以拿去部署的快照。借书和还书各自从 `main` 拉出分支。功能要写几天，当天只写了一半，半成品留在自己的分支上。半成品推进 `main`，别人一拉，整个程序跑不起来。Git 把每条分支上的提交按父指针串成一条时间线。两条分支从同一次提交分出去，之后各自追加。

### 合并

写完用 merge 收回 `main`。Git 从当初分叉的那次提交起，把两个分支末端的最新快照合成一次新的合并提交，这次合并提交有两个父提交。两边改的是不同文件，自动合成。两边改了同一处，例如借期一边写成 14 天、一边写成 30 天，合并停住，冲突标在文件里。人改完、重新提交，这次合并才算完成。冲突留在这一次合并里，看历史能看出两边曾经并行过。

### 变基

rebase，中文常叫变基。它把当前分支上分叉之后的提交摘下来，接到目标分支现在的末端后面重放。每条提交会得到新的编号。历史看起来是一条直线，分叉点不再出现在图上。

个人分支还没被别人拿去接着做时，用 rebase 跟上 `main`，冲突先在自己这边解决，分支保持整洁。已经推送到公共分支、队友拉取过的提交不再变基。重放会改掉提交编号，队友本地的历史对不上，下一步就是强制推送。`main` 上已经存在的提交同样不再变基。收进 `main` 用 merge。仓库规则写明这一点。有人用 rebase 收、有人用 merge 收，同一条主线上会出现两种历史形状。

### Go、Python、Java

Git 的对象模型三种语言相同。这一步真正要进仓库的，是各语言用来锁定依赖的文件，以及会让别人一拉就编译失败的生成物。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 依赖怎么锁定 | `go.mod` 写模块路径和 Go 版本，`go.sum` 记下每个模块的校验和。私有模块放进 `GOPRIVATE`，`GOSUMDB` 保持开启 | `pyproject.toml` 写直接依赖，`uv.lock` 锁住整棵解析树。虚拟环境 `.venv` 留在本机 | Maven 的 `pom.xml`，或 Gradle 的 `libs.versions.toml`。`mvnw`、`gradlew` 和对应的 wrapper 文件一起提交，构建不依赖各人机器上装的发行版 |
| 半成品放哪 | 功能分支上可以暂时 `go test` 失败。`main` 上 `go test ./...` 必须过 | 功能分支上可以暂时有失败的 `pytest`。`main` 上必须过 | 功能分支上可以暂时有失败的测试。`main` 上 `mvn verify` 或 `gradle test` 必须过 |
| 格式化 | `gofmt` 是工具链的一部分，提交前格式是确定的 | 格式化工具的版本写进开发依赖，CI 用同一版本检查 | 格式化插件的版本写进构建脚本，CI 用同一版本检查 |
| 容易冲突的文件 | `go.sum`、protobuf 生成的 `*.pb.go` | `uv.lock`、生成的 `*_pb2.py` | `pom.xml` 的版本段、生成的 Java 源文件 |

锁文件冲突时，先保留两边的业务改动，再由一个人按锁文件的工具重新解析并提交。`go.sum` 和 `uv.lock` 里的哈希行不手改。生成代码要么连同生成器版本一起提交，要么放在 CI 里重新生成并和仓库比对。两种做法选一种，同一个文件不能有时提交、有时忽略。

目录在这一步就按业务切开，调用仍是进程内的函数。Go 用 `cmd/library` 放入口，`internal/borrow`、`internal/catalog` 放业务。Python 用 `src/library` 下的包。Java 用一个 Spring Boot 模块里的包，启动类放在足够靠外的包上，让子包都能被扫到。用户、书目、借阅分成包，表仍然在同一个 MySQL 库里。

### 技术和必会点

这一层没有业务框架。大家共用的是 Git 本身，再加上一个放远程仓库、做评审的平台。语言相关的只是锁文件和目录习惯。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| Git | 记录每次快照、分支、合并和回退 | Git |
| 远程托管和评审 | 保护 `main`，用评审才能合并 | GitLab、极狐 GitLab、阿里云效 Codeup、腾讯工蜂、Gitee、GitHub |
| 依赖锁定 | 别人拉下来得到同一套库 | Go Modules、uv、Maven、Gradle |

#### 四层目录

工作区是正在改的文件。暂存区是这次准备提交的内容，`git add` 把选中的改动做成对象放进去。`git commit` 用暂存区生成一次提交，写进本地仓库。`git push` 把本地还没出现在远程的提交送上去。`git fetch` 只把远程历史取回，本地分支的指针不动。`git pull` 是取回再合并。合并方式要和仓库规则一致，否则同一个人有时拉出合并提交，有时把历史重写成直线。

`HEAD` 是当前检出的位置，通常指着分支名，分支再指着某次提交。直接检出某一次提交时，`HEAD` 不再指着任何分支，之后的新提交不会推进 `main`。功能做完要回到自己的分支上再提交。

#### 对象和内容寻址

blob 是文件内容，相同内容只存一份。tree 是目录，里面是名字到 blob 或其他 tree 的引用。commit 是根 tree、父提交、作者和说明。分支和标签只是指向 commit 的名字。

编号是内容的哈希，默认 SHA-1，新仓库可以是 SHA-256。借期从 14 改成 30，文件的 blob 变了，它所在的 tree 变了，这次 commit 的编号也变了。改一个字节，从这一文件到这次提交的编号整条都变。编号对得上，内容就对得上。两次提交之间的差异是用两棵 tree 算出来的，仓库里存的是快照。`git diff` 看工作区和当前提交，`git diff --cached` 看暂存区和当前提交，`git log -p` 看历史上某一次提交改了哪几行。

暂存区是一张路径表：路径、文件模式、blob 编号。平时每条路径一个阶段。冲突时同一路径会并排三份：阶段 1 是共同祖先，阶段 2 是当前分支，阶段 3 是要合进来的那边。人改完执行 `git add`，三份收成阶段 0 的一份，这次合并才能继续提交。

#### 合并和变基

收回 `main` 时，两边如果已经从同一次提交分头前进，Git 做三方合并：共同祖先、`main` 的末端、功能分支的末端。两边改的是不同文件，合成一次有两个父提交的合并提交。`main` 上没有新提交、功能分支只是往前接时，可以快进，`main` 的指针直接移到功能分支末端，不产生合并提交。保护分支上通常要求留下合并提交，历史才能看出借书和还书曾经并行过。

rebase 把分叉之后的提交按顺序在新的基点上重放，每条得到新编号。旧编号还留在本地的 reflog 里，过期之前可以找回来。已经推送并且别人拉过的提交不再变基。编号一变，普通推送会被远程拒绝，下一步就是强制推送，队友本地的父指针对不上。`main` 上已经存在的提交同样不再变基。个人分支跟上 `main` 用 rebase，收进 `main` 用 merge。

已经发布出去的错误用 revert：新增一次提交，把那次改动反过来，历史继续往前。reset 是把分支指针挪到另一次提交。`--soft` 只挪指针，暂存区和工作区还留着。默认的 `--mixed` 把指针和暂存区一起挪回去，工作区的改动还在。`--hard` 连工作区一起盖成目标那次快照。已经推送的 `main` 用 revert。

#### 冲突

同一处两边都改了，Git 停住，文件里标出两侧的内容和共同祖先。人改完，`git add` 再提交，这次合并才完成。冲突留在这一次合并提交里，以后能看出借期曾经有过 14 和 30 两个版本。锁文件冲突时先保留两边的业务改动，再由一个人用对应工具重新解析。`go.sum` 和 `uv.lock` 里的哈希行不手改。

#### 保护分支

`main` 不能直接推。至少一人评审通过、流水线通过才能进。半成品留在功能分支。评审看库存不足、重复提交、还的书根本没借出这些边界。流水线看编译、测试和漏洞。两边都过，这次快照才配拿去部署。

国内主流是私有部署的 GitLab，评审叫 Merge Request。互联网公司用自己的工蜂、云效 Codeup，或者 GitHub Enterprise。高校和一部分企业用 Gitee。新项目都用 Git。SVN 只留在还没迁走的旧仓库里。

### 当前最优解

一个远程仓库，`main` 设成保护分支。功能用短分支，个人分支用 rebase 跟上 `main`，收进 `main` 用 merge。锁文件、wrapper 和生成器版本全部提交。登录、查书、借书、还书先放在这一个仓库里。按业务拆成多个仓库，留到发布节奏已经不同的那一步。

这一步结束时，三个人能在同一份代码上并行干活，`main` 上的每次快照都能运行。程序还只在各自的笔记本上。

## 02 部署和扩容

学校图书馆开始用这套系统。别的同学在自己电脑上输入写代码那台机器的地址，连不上。程序要放到一台常年开着、同学们都能连上的机器上。这种常年通电联网、专门持续对外响应请求的主机就是服务器。学校可以把它放在校园内网。多数团队不去自己买机器建机房，而是向云厂商租一台云服务器。云服务器是云厂商用虚拟化软件在一台大物理机上模拟出硬件、切分出来的一台机器，自己带一整套操作系统。

### 多实例和反向代理

图书馆正式用起来之后，这一台的 CPU 会跑满。这台宕了，整个馆都停。下一步是再跑几份相同的后端程序，一起分担请求。一台物理机上可以同时跑多份，各自有 CPU 和内存限额。口头说的加机器，和在同一台上加实例，都是水平扩展：用更多份相同的程序处理请求。垂直扩展是把这一台的 CPU 和内存加大，单机有上限，机器更换时服务仍会停。

实例多于一份之后，外面仍是一个地址。这个地址后面加一层反向代理：它接收外部请求，按算法转给后面某一个实例，并把实例的真实地址藏在后面。正向代理站在客户端这一侧，替客户端去访问外面。反向代理站在服务这一侧，替一组服务接收外面进来的请求。

分发要做两件事。一是选择实例，常见的是轮询、最少连接，或者按某个键做一致性哈希。二是健康检查。实例探针失败，或者反向代理从它那里拿不到正常回复，就把它从可用名单里摘掉，新请求不再打过去。恢复之后再加回来。

四层转发看的是连接，七层转发能看 HTTP 的路径和头部。这时候后面还是同一份程序，两种都能把流量摊开。等后面按路径把借书和查书分到不同服务，就要看 HTTP，那是网关的事。

### 数据库先拆读写

后端的并发撑住之后，MySQL 会被打满。一条 SQL 在库里要走完连接、解析、优化、执行，再交给存储引擎去读写数据。借书和还书改的是库存和借阅记录，还要靠事务和行锁把并发的修改隔开。这些开销在单机上有上限。

查书远多于借书和还书。扩展的第一步是主从复制加读写分离，和后端多实例是同一类做法：把压力分到多份上。主库把变更日志送给从库，从库重放。写只打主库。可以接受稍微旧一点的读打从库。

复制有延迟。主库把日志送到从库、从库应用完，都需要时间。学生刚在主库还完最后一本书，立刻查从库，仍可能看到未还。这种“读自己刚写的结果”打主库。列表和检索可以接受秒级延迟，留在从库。

异步复制是主库提交并返回，从库稍后才跟上。半同步要等到至少一台从库收到日志才返回，从库应用日志仍可能落在返回之后。强一致的读还是打主库。

### 热点放进缓存

读写分离摊开的是读请求的数量。开学季成千上万个学生反复点同一批热门教材，这些读打到从库上仍然是同一批行，而且每次都要做磁盘寻址和关系表解析。反复读、允许短暂旧一点的数据，搬到内存里。

Redis 是独立运行的内存存储。常用数据放在内存里，用快照（RDB）或操作日志（AOF）定期把数据落到磁盘。缓存场景下的数据可以从 MySQL 重建，持久化丢一小段可以接受。锁和限购如果只活在 Redis 里，才需要更紧的刷盘。

查书走缓存旁路，分成两步：

1. 先按书号查 Redis。命中就直接返回。
2. 没命中就查 MySQL，把结果写回 Redis，并带上过期时间。过期时间避免旧副本一直占着内存。

库存和“现在能不能借”仍以主库事务为准。Redis 里的书目是加速用的副本。对不上时以 MySQL 为准，由下一次回填或对账把缓存盖回去。

三类会把数据库打穿的情况要分开处理：

| 现象 | 图书馆里的样子 | 挡住的办法 |
| --- | --- | --- |
| 击穿 | 一本考研教材的缓存刚好过期，几千个学生同时来查，请求一起回源 | 本进程里同一书号只放一个请求去加载，其余等这一个结果；多个进程再靠一把短锁，只让一个回源 |
| 穿透 | 有人拿根本不存在的书号反复请求，每次都到 MySQL | 短时间缓存空值。书号每次都变时，前面加布隆过滤器。过滤器说不存在就一定不存在；说存在仍可能误判，那时再查库。元素只能加，删数据要换一个新过滤器再灌一遍主键 |
| 雪崩 | 一大批书目同时过期，或者 Redis 本身挂了，流量全部打到 MySQL | 过期时间加随机抖动。Redis 不可用时限流、返回稍旧的本地副本或明确的稍后再试，停止无限回源 |

本地缓存还可以挡在 Redis 前面。进程内的过期时间用秒级，Redis 用分钟级。每个进程有自己的一份，失效不会自动广播到别的进程，所以本地这份要短。这就是多级缓存：本地、Redis、MySQL。限流和熔断留在 Redis 或数据库已经被打满的时候，把多余请求挡在外面。

### 允许短暂延迟，借还仍走主库

学生刚还了一本书，缓存里可能还是借出。做法是先提交 MySQL，事务成功之后再删掉对应的缓存。下一次查询未命中，打到 MySQL，再把新值填回去。提交前删除会让并发的读把旧行又装回缓存。删缓存失败就记一条待删记录，后台再删，过期时间是最后一道。

还有一个固定的窗口：一个读请求已经拿到旧值，还书事务提交并删了缓存，这个读请求再把旧值写回去。写路径只删、不改缓存里的对象。读路径回填时带短的过期时间。写完隔一小段再删一次，间隔盖住正在回填的读。更稳的是订阅主库的 binlog，确认提交已经发生之后再删缓存。

这些延迟来自同一件事：数据拆到多台机器上之后，副本之间要传消息。CAP 说的是发生分区的时候：分区两侧不能同时做到“每次读都看到最新写入”和“两侧都继续服务”。平时没有分区，PACELC 把另一头补上：要在延迟和一致性之间选。全网每一台从库、每一份缓存都在返回前和主库对齐，提交就要等复制和失效都完成，延迟会抬上去。查书允许从库和缓存有短暂延迟，换低时延。借书和还书改库存，走主库事务。最终一致要有一个时刻用对账把两边对齐，并给这个延迟一个上限。

### 会话放进共享存储

后端扩成多份之后，登录态不能放在某一台的内存里。学生输入学号和密码，校验通过，服务生成一个随机的会话编号，放进 Cookie。浏览器之后的请求会自动带上这个编号。Cookie 里只放编号，学号和权限留在服务端。

负载均衡把登录打到第一台，会话如果写在这台的内存里，下一次请求落到第二台，第二台翻自己的内存，找不到这个编号，学生就被当成没登录。把同一个学生钉在登录的那一台，这台还活着时能对上。这台一停，学生就要重新登录。

会话编号和学号写进 Redis。每一台都按同一个编号去取。实例自己不再保存用户状态。注销就是删掉 Redis 里的这一份，所有实例立刻失效。编号用密码学安全的随机数生成。Cookie 设成脚本读不到、只在 HTTPS 下发送。

这一步的进程还是一个，三种语言都要解决同一组数字：连接池有多大、超时写在哪、缓存什么时候删、会话放进哪一种客户端。

连接数按这个式子留余量：副本数 × 每副本进程数 × 每进程池大小，小于 MySQL `max_connections` 的八成。Go 一个容器一个进程，不再乘 worker。Python 如果用 Gunicorn 开 4 个 worker，池要按 4 倍算。Java 一个容器一个 JVM，虚拟线程不乘连接数，池仍然按 Hikari 的上限算。

缓存删除放在事务提交成功之后。Go 放在 `Transaction` 返回 `nil` 之后。Python 放在 `begin()` 块正常退出之后。Java 放在 `TransactionSynchronization.afterCommit` 或 `@TransactionalEventListener(phase = AFTER_COMMIT)`。提交前删除，并发的读会把旧行装回缓存。

SQL 参数用占位符。Go 和 Python 用驱动的参数绑定。Java 的 MyBatis 用 `#{}`。`${}` 是字符串拼接，只留给白名单里的列名和表名。

密码只存单向哈希。Go、Python、Java 都用 argon2id 或 bcrypt，校验函数按固定时间比较。SHA-256 和 MD5 可以穷举，不拿来存密码。

#### 扩展方式和负载均衡

垂直扩展是把一台机器的 CPU 和内存加大。单机有上限，换机器时服务会停。水平扩展是再跑几份相同程序。口头说的加机器，和在同一台上加进程，都是水平扩展。

四层转发看的是连接：源地址、目的地址、端口。它看不见 URL，一条连接上的后续请求会跟着进同一台。七层能看 HTTP 的路径和头部，才能按 `/loans` 和 `/books` 分到不同程序。这一步后面还是同一份程序，轮询或最少连接就够。一致性哈希按学号把同一个人钉在一台机器上，会话放进 Redis 之后，登录不再靠这根钉子维持，哈希还会把热门操作堆在同一台。健康检查失败，或者反向代理拿不到正常响应，就把这台从名单摘掉，恢复后再加回来。

#### SQL 执行路径和索引

连接器做 TCP 握手和认证。空闲超过 `wait_timeout` 就被断开。分析器做语法和名字解析。优化器按代价选索引、连接顺序。`EXPLAIN` 看的是计划，`EXPLAIN ANALYZE` 能看到实际行数。执行器再调用 InnoDB。MySQL 8 起没有查询缓存，反复读的书目放在应用和 Redis。

InnoDB 用 B+ 树。非叶子只存键，叶子才有记录，相邻叶子串成链表，范围扫描沿着链表走。主键索引的叶子是整行，这是聚簇索引。二级索引的叶子是索引列加主键，要整行就拿主键再查一次聚簇树，这是回表。查询的列都在这棵索引里时是覆盖索引，`Extra` 里出现 `Using index`。`SELECT *` 加大范围时，优化器经常放弃二级索引，因为每一行都要回表。

联合索引按定义顺序排。第一列相同才比较第二列。`(isbn, campus)` 上，`WHERE campus = ?` 用不上这棵索引做查找。`WHERE isbn = ? AND campus = ?` 两列都能用来查找。索引列上包函数、做计算、把字符串和数字比，这列的查找能力就没了。`type` 从好到差大致是 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL`。`ALL` 是全表扫。深分页 `LIMIT 100000, 20` 会先扫过前面的行再丢掉，改成上一页的游标：`WHERE id < ? ORDER BY id DESC LIMIT 20`。

主键用自增整数，插入多发生在最右边。随机的 UUID v4 往页中间插，造成页分裂。要在应用里生成、又希望按时间局部有序时，用雪花 id 或 UUID v7。雪花 id 把毫秒时间、机器号和这一毫秒里的序列放进一个整数，单毫秒单机的序列有上限。机器号要租约，时钟回拨时停止发号，等到时间追上再发。

数据页默认 16KB。Buffer Pool 按页缓存数据和索引。页被改过就是脏页，由后台刷回数据文件；刷盘跟不上时，用户线程会被迫参与刷页，语句变慢。新读入的页先放在 LRU 的 old 区，停留超过一小段时间再被访问才进 young 区，一次扫全表不会把热门书目挤出内存。一页 16KB 在磁盘上不一定一次写完，写到一半掉电，页就撕开了。doublewrite 先把这批脏页顺序写到单独区域并 fsync，再写各自的数据页。恢复时页校验失败，从这块区域把整页拷回来，再应用 redo。

#### 事务、MVCC 和锁

ACID 落在不同机制上。原子性靠 undo，回滚时把旧版本找回来。持久性靠 redo 按 WAL 先写日志再刷脏页，以及 binlog 的刷盘。隔离性靠锁和 MVCC。一致性是业务约束：库存不能减成负数，由条件更新和约束保住。

改一行时 InnoDB 做三件事。旧版本推进 undo，形成版本链。页的修改记进 redo。这次变更再记进 server 层的 binlog，供复制和恢复。提交在引擎和 binlog 之间是内部两阶段：redo 先落到 prepare，再写 binlog 并 fsync，然后引擎标成 commit。崩溃发生在 binlog 落盘之前，恢复时回滚，从库也看不到这笔。崩溃发生在 binlog 已经落盘、引擎 commit 标记还没写完时，恢复时按 binlog 把引擎提交补完。生产上 redo 和 binlog 都每次提交 fsync。binlog 用 `ROW`，记的是行的前后像。

并发现象有四种。脏写是两个事务都按自己读到的旧值去写，后写覆盖先写。脏读是读到别人还没提交的修改。不可重复读是别人提交之后，本事务再读同一行，值变了。幻读是同一范围再读，行集合变了。InnoDB 默认隔离级别是可重复读。

普通 `SELECT` 是快照读，不加锁。行上有隐藏的事务 id 和回滚指针。可重复读在事务里第一次一致性读时生成 Read View，之后的普通 `SELECT` 都用这一份。读已提交则每次一致性读都生成新的 Read View。`BEGIN` 本身不生成视图。

Read View 记下生成那一刻还没结束的事务，以及当时系统即将分配的下一个事务 id。拿一行的事务 id 做判断：是自己写的，可见；小于当时已经结束的那些，可见；大于等于视图生成后才分配的 id，不可见；落在中间的，还在活跃名单里就不可见。不可见就顺着回滚指针找更老的版本，直到看见一个已提交的，或者链走到头。

`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读。它们读最新已提交的版本并加锁。可重复读下，范围上的当前读加临键锁：记录锁加这条索引记录前面的间隙，区间左开右闭。间隙锁挡住别人往这个范围里插行。间隙锁之间不互斥，和插入意向锁互斥。两个事务都对「不存在的副本 id」做 `FOR UPDATE`，两边的间隙锁都能加上，真正 `INSERT` 时互相等待，InnoDB 检出环之后回滚代价较小的那一笔，错误码 1213。等锁超过 `innodb_lock_wait_timeout` 是 1205。

同一个事务里先快照读再当前读，当前读仍可能看见别人刚刚提交的新行。库存和「能不能借」用单条条件更新，不在应用里先查再减：

```sql
UPDATE copy SET status = 'lent'
WHERE id = ? AND status = 'available';
```

`RowsAffected = 0` 就是没借成。锁加在索引上。条件列没有索引时，当前读会锁住扫过的大量记录。事务里只留必须原子的 SQL。HTTP、Redis 和发消息放在事务外面，行锁会占到提交，外部调用一慢就挡住别人，也占着池里的一条连接。长事务还占着元数据锁和 undo。后面的加列要等它，查询也要沿着变长的版本链找自己的快照。

读已提交不加间隙锁，锁范围更小。互联网里写多的库常用这一级，库存仍靠上面这条条件更新。需要稳定范围时再显式 `FOR UPDATE`。

#### 主从

主库把 binlog 发给从库。从库的 IO 线程把日志收进 relay log，SQL 线程重放。异步复制是主库写完自己的日志就返回。主库在这一瞬间宕机，已提交的还书可能不在从库上。

半同步要至少一台从库确认收到日志，主库才给客户端返回。等待点用 `AFTER_SYNC`：binlog 已经 fsync，从库确认写进 relay log 之后，主库才在引擎里提交并响应。从库应用完仍可能更晚，所以「从库收到了」不等于「从库已经能查到」。超时后退回异步。`AFTER_COMMIT` 是先在主库引擎提交再等从库，确认之前别的会话已经能读到这行。

GTID 用 `source_id:transaction_id` 标识每一笔已提交事务。从库按 GTID 集合续传，换主时不用手工对文件名和位点。延迟常见来自单线程重放、大事务、从库更弱、锁等待。学生刚还完书再查，打主库，或者在从库上等到这笔 GTID 重放完再读。书目列表可以打从库。

#### 故障切换

复制延迟是从库还没跟上。故障切换是主库已经不能写，要换一台继续写。两件事前后脚发生，处理方式不同。

云上的 RDS 把切换做在代理后面。应用连的是读写地址，地址不变，背后的主库换掉。自建时由 Orchestrator 这一类工具选新主：在还活着的从库里挑 GTID 最全的一台，把它的 `read_only` 关掉。旧主如果还活着，设成 `super_read_only`，让它拒绝写入。两边同时能写，借出会分叉成两套库存。

异步复制有一个真实的窗口：主库已经向客户端返回成功，binlog 还没到任何从库，主库随即宕机。这几笔还书在新主上不存在。半同步的 `AFTER_SYNC` 把窗口缩到「至少一台从库收到日志之后才返回」。从库收到仍然不等于已经能查到。

旧主恢复之后，按新主重新做成从库。只在旧主上提交过、任何从库都没有的事务，不能再写回新主，那些借还以丢失告警，由对账找出来。切换那几秒到几十秒不可写。池里指向旧主的连接会断开，或者在只读库上执行更新失败。驱动丢掉已经变成只读的连接，下一笔再向新地址要连接。这一笔借书用同一把幂等键再试。幂等键的记法在容错那一节：切换前已经借成、响应丢了，重试读到第一笔；切换前没写上，重试才真正去扣。

#### 备份

从库重放的是主库的 binlog。错误的更新、误删、删表都会跟着到从库。从库用来分担读和接替主库，留不住「误操作之前」的数据。

备份是某一时刻的副本，加上从那之后连续的 binlog，才能恢复到误删之前的一秒。物理备份和云上的磁盘快照恢复快，适合整库。逻辑备份适合小库和单表。全量按天做。binlog 的保留时间要长于两次全量的间隔，还要盖住恢复本身花的时间，否则断点对不上。备份放在另一套存储上，和数据库磁盘分开。

云 RDS 的自动备份加上日志备份，可以按时间点恢复。自建要把 binlog 持续送到对象存储。备份任务显示成功，只说明文件写完了。隔一段时间把备份恢复到一台隔离的实例上，核对借阅行数和最近的 GTID，确认这套备份打得开。

#### 连接

一次借书先是一条 TCP 连接：客户端发 SYN，服务端回 SYN-ACK，客户端再 ACK，之后才有字节流。TLS 在入口做握手，协商出会话密钥，HTTP 跑在这条已经加密的连接上。HTTP/1.1 的长连接让后面的请求继续用同一条 TCP，省掉重复握手。每个请求仍然有自己的响应。负载均衡若按连接转发，这条长连接上的后续请求会进同一台实例。

应用进程到 MySQL、到 Redis，又是各自的 TCP。池子把这些连接建好留着，借书时只借用，用完归还。每次查询都新建连接，时间会花在握手和认证上。池子放大有三道硬上限：数据库的 `max_connections`、进程能打开的文件描述符、机器的临时端口。短连接由主动关闭的一方进入 TIME_WAIT，大约两个报文最大生存时间里，这个端口不能再用来建新连接。突发把短连接打满时，先耗尽的是临时端口，而不是 CPU。

负载均衡和防火墙会掐掉空闲连接。应用这边的空闲寿命要短于那一侧，否则下一笔请求打在一条已经被拆掉的连接上，客户端看到的是连接重置。这条规则对到数据库的池子、到 Redis 的池子、浏览器到网关的长连接都适用。

#### 连接池

池子借光后，后来的请求堵在借连接上，直到有连接归还，或者这次调用的截止时间到了。没有截止时间的调用会一直等。总数按副本数 × 每副本进程数 × 每进程池大小估算，留在 `max_connections` 的八成以下。Go 一个容器一个进程。Python 开了多个 worker 要按 worker 数乘。Java 虚拟线程不乘连接数，池仍按 Hikari 的上限算。

空闲连接的寿命要短于数据库 `wait_timeout`、云负载均衡和防火墙掐掉空闲连接的时间，并留几分钟。池子不会在借出前主动探测每一条连接。空闲连接被对端掐掉之后，下一次使用才发现。已经发出去的语句超时，结果不确定，不能靠换一条连接把同一条借书再执行一遍。

#### Redis 的执行、持久化和复制

数据在内存里。结构把单次操作的复杂度控住：字符串计数是 `INCR`，对象的多个字段用哈希，排行用有序集合（跳表加哈希表），去重用集合。网络用多路复用，很多连接的可读事件进同一条循环。命令在主线程上排队执行。`KEYS`、对大键的 `HGETALL` 或 `SMEMBERS`、一段很长的 Lua，会堵住后面所有命令。删大键用 `UNLINK`，让后台线程去释放。线上扫键用 `SCAN`，调用方自己去重。

键名带业务和版本，例如 `book:v3:{isbn}`。过期时间在写入时一起设，`SET key value EX 秒`。先 `SET` 再 `EXPIRE`，两条命令之间进程挂了，键就没有过期时间。到期有两条清理路径：访问到已到期的键时顺手删，后台再随机抽一批带过期时间的键来删。内存上限是另一套机制，靠 `maxmemory` 和淘汰策略。缓存用 `allkeys-lru` 或 `allkeys-lfu`。`noeviction` 写满后拒绝写入。拒绝写入要和「键不存在」分开，否则会把内存满当成缓存未命中，全部打到 MySQL。

RDB 是某一时刻的全量快照，`bgsave` 用 fork。AOF 追加命令，`everysec` 大约每秒 fsync，最多丢大约一秒。书目缓存可以从 MySQL 重建，只开 RDB 甚至不持久化都可以。锁和限购如果只活在 Redis 里，才需要更紧的 AOF。

主从复制是异步的。哨兵要多数派同意才做故障转移，客户端连哨兵给出的当前主，地址不写死某一台。切换有几秒到十几秒不可写。Cluster 把键分成 16384 个槽。跨槽的多键命令会被拒绝，相关的键用 `{isbn}` 这种哈希标签落到同一槽。某个槽的主从都不可用时，这个槽上的键不可用。

多进程击穿用的短锁是一条命令：`SET key token NX PX 毫秒`。token 是随机值。释放时用 Lua 先比对 token 再删，两条命令拆开做会把别人刚拿到的锁删掉。业务要在 TTL 之前结束。锁过期之后原持有者还在往下写时，资源侧再认一个只增的序号，序号更小的写入拒绝。库存扣减本身用数据库条件更新。这把锁只包住「缓存失效后只有一个请求去回源」。

#### 三种缓存故障，以及和库怎么对齐

击穿是热点键刚好过期，几千个请求同时回源。本进程里同一书号只放一个请求去加载，其余等这一个结果。多个进程再靠上面的短锁，拿到锁之后先再读一次 Redis，没有再查 MySQL。

穿透是查根本不存在的书号，每次都到 MySQL。固定的空书号缓存一个更短的空值。书号每次都变时，前面加布隆过滤器：几位里有一位是 0，就一定不存在；全是 1 仍可能是别的书号置上的，那时再查库。元素只能加，删数据要换一个新过滤器再灌一遍主键。误判率随元素个数上升，超过预计容量就很快变高。

雪崩是一大批书目同时过期，或者 Redis 本身挂了。过期时间加随机抖动。Redis 不可用时限流、返回稍旧的本地副本或明确的稍后再试，停止无限回源。

对齐的顺序是先提交 MySQL，成功后再删 Redis。下一次未命中再把新值填回去，并带上过期时间。提交前删除，并发的读会把旧行装回缓存。写路径只删、不改缓存里的对象。还有一个固定窗口：一个读已经拿到旧值，还书事务提交并删了缓存，这个读再把旧值写回去。写完隔一小段再删一次，间隔盖住正在回填的读。更稳的是订阅主库 binlog，确认提交已经发生之后再删。删缓存失败就记一条待删记录，后台再删，过期时间是最后一道。

#### 会话和这一步的一致性

Cookie 里只放密码学安全的随机编号，学号和权限在 Redis。`HttpOnly` 让页面脚本读不到。`Secure` 只在 HTTPS 下发送。`SameSite=Lax` 挡住别的站点发起的 POST，顶层链接进来的 GET 仍会带上。注销就是删掉 Redis 里的这一份，所有实例立刻失效。密码只存 argon2id 或 bcrypt，校验按固定时间比较。SHA-256 和 MD5 可以穷举，不拿来存密码。

一致性按数据来选。借还的库存要读到自己刚写的结果，写和刚写完的查询都打主库。书目列表和缓存允许秒级旧数据。发生分区时，分区两侧不能同时做到「每次读都看到最新写入」和「两侧都继续服务」。没有分区时，要在延迟和一致性之间选：提交前和从库、缓存对齐，延迟更高；提交后异步复制和失效，返回更快，读到的可能旧一点。单机的索引、SQL、连接数、缓冲池和磁盘都用尽之后，才按业务分库、按借阅键做水平拆分。

#### 对账

允许短暂不一致的每一处，都要有一个时刻把两边比完，并且给这个延迟一个上限。权威是 MySQL 里已经提交的借阅和副本状态。缓存、从库展示、Redis 里的可借本数、通知记录，都是从它派生的。

比的是成对的数，按同一把业务键：

| 左边 | 右边 | 偏差持续超过上限时 |
| --- | --- | --- |
| 副本行的状态 | Redis 里的书目 | 删掉这一个缓存键，下一笔读从主库回填 |
| 可借本数的计数 | `COUNT` 出来的在架副本 | 用计数覆盖 Redis，不在 Redis 上把差额加回去 |
| 发件箱里已发送的借阅 id | 消费者幂等表里的同一批 id | 缺的按发件箱再投一次。多出来的通知不反写一笔借阅 |
| 借阅行 | 通知记录 | 有借阅、没有通知，补投。有通知、没有借阅，告警，人来看 |

上限按链路的正常延迟来定。缓存覆盖热门书用秒级。通知覆盖队列堆积，用一分钟这一档。窗口之内的偏差是复制和消费还在飞，不告警。超过窗口仍然对不上，才修。

修的方向只有一个：以主库已提交的行为准，让派生侧向它对齐。发现差额就在 Redis 上加一减一，会把一次延迟修成第二次写错。旧主上多出来、新主没有的事务，也不自动合并回去。对账任务本身按批做，用上一页的主键当游标，避免一次扫全表。热门书可以更勤，全库每天一遍。

国内主流是云负载均衡加云 RDS MySQL 主从，缓存用云 Redis 或自建哨兵。业务框架在国内后端岗位里默认是 Spring Boot，本地缓存用 Caffeine，浏览器登录用 Spring Session 配 Redis。App 和小程序大量签发 JWT。Go 的新服务用 Gin，或公司统一的 Kratos、go-zero。Python 的数据接口用 FastAPI，带页面的管理端用 Django。读写分离在 Java 项目里常见动态数据源或 ShardingSphere-JDBC 只做读从库。分库分表和 TiDB 是单机主从已经不够以后的事，这一层先不引入。

### 当前最优解

入口用云负载均衡，校园内网没有云负载均衡时用 Nginx。后面是多份相同进程。负载均衡用轮询或最少连接。会话已经在 Redis 里，不需要按学号做一致性哈希，哈希会把热门操作钉在同一台机器上。

数据用 MySQL 8.4 一主多从。写和“刚写完就要读到”的查询打主库，书目列表打从库。复制用异步或半同步。主库地址走 RDS 的读写地址或一层代理，切换时应用不改连接串。全量备份按天，binlog 连续归档，保留长于全量间隔。隔一段时间把备份恢复到隔离实例上核对。热点书目用 Redis 7 做缓存旁路：先写库，提交成功后删除缓存，读路径回填并带过期时间。空书号先缓存短 TTL 的空值。布隆过滤器留到书号空间大、空值缓存压不住的时候。进程内缓存只挡极热的几十本书，TTL 用秒级。Caffeine、`singleflight`、按 key 的锁都是这一层。缓存、计数和后面的通知都按主库对账，窗口之内的延迟不告警。

会话用 Redis 里的服务端会话。Cookie 带 `HttpOnly`、`Secure`、`SameSite=Lax`。

语言按团队已有的运行时选，库按上面这张表，不在这一步混用两套数据访问：

- 新的 IO 密集服务、希望镜像是一个静态二进制：Go，Gin 加 GORM 加 `go-redis`。
- 算法、检索和要快速交付的接口：Python，FastAPI 加 SQLAlchemy 2 加 `redis.asyncio`。管理后台、一张库上的完整页面用 Django。
- 已有 Java 资产、事务和连接池要靠成熟默认值：Java，Spring Boot 3.5 加 MyBatis 加 HikariCP 加 Lettuce。业务服务保持 MVC。WebFlux 留到网关。

这一步结束时，入口是一个地址，后面是多份无状态实例。读可以走从库和缓存，借还走主库。Redis 同时做两件事：热点书目的副本，以及所有实例共享的会话。

## 03 代码上线

有人改借书逻辑，把判断条件写反，直接推进 `main`。下一次发布，全校都借不了。`main` 设成保护分支，不能直接推。改动从自己的分支提起 Pull Request。自建的 GitLab 上这一步叫 Merge Request。作者不能自己合并，至少一名队友看过才能进 `main`。人看的是边界：库存不足、重复提交、还的这本书根本没借出、借期非法。

人眼会漏。每次推送和每次提起评审，流水线跑同一套检查，没过就不能合并。这是持续集成：把合入主线之前的编译、测试和漏洞检查变成自动的、每次都跑的门。测试用固定的测试数据，碰到共享状态的测试要能重复跑出同一个结果。

大多数团队实际把验收分成两套环境。预发和生产用同一份构建产物，只换配置和连接的库。在预发重新编译，两边就不是同一次提交，评审看过的代码和生产跑的代码会岔开。预发用测试数据，或只放隔离的流量。在预发把借书、还书、库存不足和重复提交走一遍，再允许进入生产。

### 同一份镜像

评审和检查都过了，还不能在生产机器上手工拷文件。各台机器的运行时、依赖和配置会漂：一台的语言版本和另一台不一样，同一份代码在这边能跑、在那边启动失败。镜像把程序、语言运行时、依赖库和启动方式打在一起。拿到同一份镜像，启动结果就一样。配置，例如数据库地址，留在镜像外面，部署时注入。

容器是跑这份镜像的进程隔离环境。它共享宿主机的内核，用内核的隔离和资源控制切出独立的文件系统视图、进程空间和 CPU、内存上限。虚拟机自带一整套操作系统。容器少了这套内核，所以轻，通常一两秒就能启动。上限先写在容器上，后面编排调度才知道这台机器还剩多少。

### 灰度发布和回滚

持续交付是：`main` 上每一份通过检查的提交都能打成镜像，放到预发，差一次人工确认就能进生产。持续部署是确认这一步也交给流水线。借还会改库存，生产由人点。点下去之后如果十几个实例同时换成新镜像，一次写反的判断会让全校一起失败。

发布分成两件独立的事。灰度决定切多少流量：负载均衡先把一小部分请求指到新版本，看借书失败率和延迟，稳了再一批一批放大。滚动决定怎么换副本：先起一个新副本，就绪之后再停一个旧的，过程中保持能服务的副本数。新副本先接这一小部分流量，确认后再按滚动把其余副本换掉。

回滚改的是流量指向的镜像标签，把实例换回上一份已经发布过的镜像。线上机器上不改判断条件，也不在生产里重新编译。镜像标签用这次提交的编号。`latest` 会移动，回滚时指不清上一份是哪一次提交。

### Go、Python、Java

流水线对三种语言做同一类门：测试、竞态或并发检查、漏洞扫描、打出带提交号的镜像。镜像里的运行时和本机可以不同，所以构建在 CI 里完成，开发机只负责把源码推上去。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 合入前的检查 | `go test ./...`。会碰共享状态的包加 `-race`。`govulncheck` 看已经编进二进制的漏洞，不只看 `go.mod` 里写的版本 | `pytest`。接口用 `httpx.ASGITransport` 打应用，不先起端口。数据库用例结束时回滚事务 | `mvn verify` 或 `gradle test`。控制器用 `MockMvc`。数据库用 Testcontainers 起 MySQL。H2 的方言和 MySQL 对不齐的地方会漏 |
| 镜像 | 多阶段。构建阶段 `golang:1.27`，`CGO_ENABLED=0` 打出静态二进制，放进 `distroless/static`。进程以非 root 运行，入口用 exec 形式，才能成为 PID 1 并收到 `SIGTERM` | 多阶段。`python:3.12-slim`，`uv sync --frozen` 按锁文件安装。`PYTHONUNBUFFERED=1` 让日志立刻出来。入口是 `uvicorn`，同样用 exec 形式 | 多阶段。构建出分层 jar，运行阶段用 `eclipse-temurin:21-jre`。`-XX:MaxRAMPercentage=70.0` 让堆跟着容器内存上限走，`-XX:+ExitOnOutOfMemoryError` 让堆耗尽时进程退出，交给后面的探针拉起 |
| 停机 | `http.Server.Shutdown` 停止接收，等在途请求结束，再关 Redis 和数据库 | Uvicorn 在 PID 1 上收到 `SIGTERM` 后停止接收。前面多一层 shell 时，信号打在 shell 上，worker 要等到强杀 | `server.shutdown=graceful`，再配 `spring.lifecycle.timeout-per-shutdown-phase`。宽限时间要盖住这段等待 |
| 本地依赖 | `docker compose` 起 MySQL 和 Redis。`depends_on` 只保证启动顺序，数据库加上 `healthcheck`，应用用 `service_healthy` | 同一份 Compose。主机名用服务名，例如 `redis:6379` | 同一份 Compose。生产清单和本地清单共用镜像名、端口和环境变量名 |

`distroless` 里没有 shell，也没有 `curl`。健康检查由后面的编排直接打 HTTP，不在镜像里装一个 shell 专门用来探活。Python 和 Java 的基础镜像带有包管理器，仍然用非 root 用户运行，密钥不写进镜像层。`.dockerignore` 去掉 `.git`、本地 `.env` 和本机的虚拟环境，避免把宿主机的二进制打进镜像。

数据库结构变更用迁移工具，放在发新版本之前的一次性任务里：Go 用 golang-migrate 或 goose，Python 用 Alembic，Java 用 Flyway。多个副本同时改同一张表会抢元数据锁。大表加列优先走 MySQL 的 `ALGORITHM=INSTANT`，做不到就让语句失败，再改用 gh-ost 或 pt-online-schema-change。

| 编排的前身 | 本地把应用、MySQL、Redis 一起拉起 | Docker Compose |
| 结构变更 | 发版前改表，且不和滚动副本抢锁 | Flyway、Alembic、golang-migrate、goose、gh-ost |
| 发布 | 先小流量，失败指回旧镜像 | Nginx 权重、云负载均衡权重、后面的 Kubernetes 滚动 |

#### 持续集成和制品

持续集成是合入前自动检查：每次推送、每次提起评审，都跑编译、测试和漏洞扫描，没过就不能进 `main`。持续交付是 `main` 上每一份通过检查的提交都能打成镜像放到预发，差一次人工确认就能进生产。持续部署是连确认也交给流水线。借还会改库存，生产留人工确认。

预发和生产拉取同一份镜像，只换配置和连哪一个库。在预发重新编译，评审看过的提交和生产跑的二进制就不是同一份。配置，例如数据库地址，留在镜像外面，部署时注入。密钥不写进镜像层，也不进 Git。

#### 镜像、容器和虚拟机

虚拟机自带一整套内核。容器共享宿主机内核，用 namespace 切出独立的进程、文件系统、网络和用户视图，用 cgroup 给 CPU 和内存封顶，所以少了一层内核，启动是秒级。上限先写在容器上，后面编排才知道这台机器还剩多少。

镜像是只读层叠起来的。容器写入落在最上面的可写层，容器删了可写层就没了。要留下的借阅数据放 MySQL，上传的封面放对象存储，都不放容器磁盘。层按 Dockerfile 里会改文件系统的指令缓存。依赖变化少、源码变化多，所以先拷锁文件、安装依赖，最后才拷源码。改一行借书判断不会重新下载依赖。

入口用 exec 形式，进程成为 PID 1，才能直接收到 `SIGTERM`。前面多一层 shell 时，停止信号打在 shell 上，业务进程要等到强杀才退出，事务可能停在提交之前。`distroless` 里没有 shell，也没有 `curl`。健康检查由后面的编排直接打 HTTP。`.dockerignore` 去掉 `.git`、本地 `.env` 和本机虚拟环境，避免把宿主机的文件打进镜像。

隔离用六类 namespace：进程、挂载点、网络、主机名、进程间通信、用户。容器里的 PID 1 就是入口进程，它看不见宿主机上的其他进程。网络 namespace 给它自己的网卡和端口。cgroup 把 CPU 时间和内存封在这个容器上。CPU 用时间片配额，配额用完就等到下一个周期，进程还在，延迟会上去。内存超过上限，进程被杀掉。镜像按 OCI 来做：每一层是一组文件变更，用内容哈希标识，启动命令写在镜像元数据里。多阶段构建把编译器和构建缓存留在前面的阶段，最终镜像只留运行所需的文件。

#### 标签、灰度和滚动

标签用这次提交的编号。`latest` 会移动，回滚时指不清上一份是哪一次构建。回滚改的是流量指向的镜像标签，把实例换回上一份已经发布过的镜像。线上不改判断条件，也不在生产里重新编译。

灰度决定百分之多少的请求进新版本，并且按阶梯放大：先 1% 或一所学校，观察一个窗口（例如 5 分钟），再放到 10%、50%、100%。每一档拿这一窗口和发布前的基线比。借书的系统错误只计 5xx 和数据库报错，库存不足单列。错误率比基线高出 1 个百分点，或者绝对值超过 1%，持续这一个窗口，就停止放量，把流量指回旧标签。借书延迟的 p99 超过发布前的两倍，或者超过这一跳的时间预算，同样停止。就绪探针失败、发件箱未发送行数在这个窗口里抬升，也停止。错误率和分位怎么计，在可观测性那一节。

滚动决定副本怎么替换：先起一个新的，就绪之后再停一个旧的，过程中保持能服务的副本数。两件事拆开。新副本先接这一小部分流量，确认后再按滚动把其余副本换掉。蓝绿是两套完整环境切换，成本高。借还这种核心链路用分批滚动加观察。

停机的顺序是：先停止接收新请求，等在途的借书走完，再关 Redis 和数据库。宽限时间要盖住这段等待。到点还没退出，就会被强杀。

#### 结构变更

多个副本同时改同一张表会抢元数据锁。DML 持有共享的元数据锁，DDL 要排他。长事务不提交，加列就排队，排在后面的查询也会被堵住。加列优先走 MySQL 的 `ALGORITHM=INSTANT`。做不到就让语句失败，再改用 gh-ost 或 pt-online-schema-change：建一张新结构的影子表，用触发器或 binlog 把变更追过去，对完再换名。变更期间 binlog 量会上升，从库延迟要一起看。

迁移放在发新版本之前的一次性任务里，不放进每个副本的启动。应用和表要能同时在线两个版本。先加可空列或新表，旧代码照常写；再发会写新列的应用；最后才停用旧列。先发不兼容的表结构、再滚动应用，滚动中途旧代码会写失败。删列放在确认没有旧副本之后。

国内主流里，存量流水线大量是 Jenkins，镜像仓库是 Harbor。新项目更多用 GitLab CI 或阿里云效、腾讯云 CODING 的流水线，镜像放 Harbor 或云厂商的 ACR/TCR。容器运行时就是 Docker 这一套，生产机器上不再手工拷 jar 或二进制。核心交易和借还由人点发布，灰度用负载均衡权重或发布系统的分批。蓝绿是两套完整环境切换，成本高，国内更多用分批滚动加观察，而不是长期维持两套生产。

### 当前最优解

CI 在每次推送和每次评审上跑测试和漏洞扫描。通过之后打镜像，标签用 git 提交号，同时推到仓库。预发和生产拉取同一份镜像，只换配置。借书、还书会改库存，生产由人确认。确认之后按 1%、10%、50%、100% 放大。每一档看 5 分钟：借书的 5xx 和数据库报错比基线高出 1 个百分点或绝对值超过 1%，或者 p99 超过发布前的两倍，就停止放量，把流量指回上一份提交号。库存不足不放进这个错误率。不在线上重新构建。

三种语言都用多阶段构建、非 root、exec 形式的入口。Go 用静态二进制加 distroless。Python 用锁文件安装。Java 用分层 jar 加按容器内存百分比设置的堆。

这一步结束时，进生产的代码经过评审和自动检查，各台机器跑同一份镜像，上线可以只切一小部分，失败能指回上一份。所有功能仍在同一个进程里。

## 04 微服务

平台变成几百所学校共用。跨校借书、自习室座位、电子书、推荐都加进同一个程序。规模小的时候，一个进程结构简单，一次本地事务就能改完库存和借阅记录。再往下会碰到三件事：

- 一次错误发布要回滚时，所有人的改动跟着一起回去。
- 一个依赖把进程撑满或打崩溃，查书和借书一起停。
- 开学借书忙，想扩容就得把平时并不忙的电子书和推荐一起扩。

这三个信号同时出现，再拆。拆分的单位是业务能力，各自拥有数据，可以独立开发、部署和扩容。用户信息、账号权限和登录会话收成独立的用户服务，往往成为所有学校、所有业务共同依赖的一块。借阅服务拥有借阅记录和库存，书目服务拥有书目，座位服务拥有座位。每个团队发自己的版本。开学只加借阅服务的实例。

按技术层拆会拆错。把“所有数据库访问”放进一个服务、把“所有校验”放进另一个服务，一次借书仍要穿过所有层，发布还得一起发。两个服务写同一张表，就回到了共享数据库。需要别人的数据时，同步调用拿一次，或者订阅对方的事件，在本地留一份只读副本。

反向的信号也同样具体：每次改需求都要改三个服务，同步调用链超过三跳，为了一次查询做分布式事务。这时先把边界收回到一个进程里的包。包之间的调用是函数调用，事务还是本地的。

### 跨网络之后要有契约

一次借书要问用户服务：没欠费、还能再借。查库存可能再问书目或馆藏。各服务跑在不同机器上。网络会丢、会慢、会重复。这些失败从拆分的这一天起就存在，保护放在后面的容错一节，拆的时候就要把调用当成会失败的远程调用。

进程之间要先把内存里的对象变成一串能传输的字节，这是序列化。对面再把字节还原成对象。JSON 是文本序列化，人能直接读。面向浏览器、小程序和手机 App 的接口继续用 HTTP 和 JSON。

内部调用密、字段稳定、团队和语言都不同时，文本和口头约定会碎。有人改了字段名或类型，对面就解析失败，或者悄悄把借期读成别的含义。远程过程调用把一次跨网络的调用收成“按契约调用某个方法”。契约用接口描述语言写下来：哪个字段是借阅天数，每个字段是什么类型，字段编号是多少。描述语言独立于具体编程语言，各端从同一份描述生成代码。

兼容按字段编号来。借阅服务新加一个字段并先上线，旧的调用方按编号跳过不认识的字段，调用不会因此失败。只加字段、不改旧字段的含义、不复用废弃的编号。破坏性变更用新的方法或新的路径。

这种契约通常搭配二进制序列化：线上传的是字段编号和紧凑的字节，比同样内容的 JSON 小。生成出来的客户端把建连接、序列化、发请求、收响应、反序列化收进框架。gRPC 是这一套的常见实现，底层用 HTTP/2。对外的 API 仍留在 HTTP 和 JSON。内部把跨服务调用收回到一份可以生成、可以兼容演进的契约上。

### Go、Python、Java

拆分之前，三种语言先把包边界划清。包之间的调用还是函数调用，库存和借阅记录仍在一个本地事务里。独立进程、独立库是下一刀，两刀不在同一次发布里一起切。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 还没拆时的边界 | `internal/borrow` 不能去改书目的表。需要书目时调书目包的函数 | `borrow`、`catalog`、`accounts` 是包。服务函数接收已经建好的会话，不在函数里新建连接 | 一个 Boot 应用里的包。事务仍是一个 `@Transactional`。启动类的包要盖住这些子包 |
| 对外 HTTP | Gin 的结构体做 JSON。`encoding/json` 默认忽略未知字段。1.27 起另有 `encoding/json/v2`，重复字段名的处理以绑定层的显式配置为准 | Pydantic v2。`response_model` 收口，多出来的字段不出去。校验失败是 422 | Jackson。保持未知字段可忽略。`@Valid` 校验形状，借阅记录是不是这个学生的留在服务里，校验失败是 400 |
| 对内 RPC | `grpc-go`。`grpc.NewClient` 按进程建通道，截止时间放在 `context` 里。负载均衡用 `round_robin`。默认的 `pick_first` 会把一条 HTTP/2 连接上的全部 RPC 打进解析结果里的第一台 | `grpc.aio`，和 FastAPI 共用事件循环。同步的 `grpc` 调用会堵住循环。对外的 HTTP 用进程级的 `httpx.AsyncClient` | 跨语言用 `grpc-java`，契约仍是同一份 protobuf。全是 Java、而且已经在 Dubbo 上时，用 Dubbo 3 的 Triple，它也跑在 HTTP/2 上。对 HTTP JSON 的下游，新代码用 `RestClient`，已有大量声明式接口用 OpenFeign |
| 错误码 | gRPC 的 `NOT_FOUND`、`FAILED_PRECONDITION`、`UNAVAILABLE` 用 `status.FromError` 取出，不比较错误字符串 | 业务异常带稳定错误码。未捕获的异常变成 500，响应里不带栈 | `@ControllerAdvice` 按异常类型收口。受检异常要写 `rollbackFor`，否则事务会提交 |

一次借书要改借阅库，通知库在另一个服务里。两个库没有同一个本地事务。这一步的写法是：借阅事务里同时写下借阅记录和发件箱。库存如果还和借阅在同一个库，就留在这个事务里，不为了“微服务”把库存再拆出去。用户服务只同步问一次“能不能借”。

### 技术和必会点

这一层的技术是进程边界、序列化和远程调用。框架开始分成两截：对外的 HTTP 框架还在，对内多了一套 RPC 框架和接口描述。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| 模块化单体 | 还没拆进程时的边界 | Go 的 `internal` 包、Python 包、Spring 的模块 |
| 序列化 | 把内存对象变成可传输的字节 | JSON、Jackson、Pydantic、protobuf |
| HTTP API | 给浏览器、小程序、App | Spring MVC、Gin、FastAPI |
| RPC | 服务之间按契约调用 | Dubbo 3、gRPC、Kitex、tRPC |
| 接口描述 | 字段号、类型、兼容规则 | protobuf、Dubbo IDL |
| 对象存储 | 封面和电子书只留地址 | 阿里云 OSS、腾讯云 COS、MinIO |
| 跨库写入 | 没有同一个本地事务之后怎么对齐 | 发件箱、Seata、本地消息表 |

#### 拆分单位和数据所有权

三个信号同时出现再拆：要独立扩容，发布节奏已经不同，故障不想拖垮主路径。数据所有权是拆分单位的前提，各自拥有自己的表。按技术层拆成「一个库服务、一个校验服务」，一次借书仍要穿过所有层，发布还得一起发。反向的信号也同样具体：每次改需求都要改三个服务，同步调用链超过三跳，为了一次查询做分布式事务。这时先把边界收回到一个进程里的包。包之间是函数调用，事务还是本地的。

拆分之前先在一个仓库里把包边界划清，独立进程和独立库是下一刀，两刀不在同一次发布里一起切。每个服务拥有自己的表。需要别人的数据时，同步调用拿一次，或者订阅对方的事件，在本地留一份只读副本。两个服务写同一张表，就回到了共享数据库。用户服务拥有账号和会话，借阅服务拥有借阅记录。库存如果和借阅是同一次提交里必须一起成功的，就留在借阅这一个库里，不为了「微服务」再拆出去。

#### 远程调用的失败

一次借书要问用户服务：没欠费、还能再借。各服务跑在不同机器上。网络会丢、会慢、会把同一次请求送两次。调用方看到超时，只说明自己没在截止时间前拿到响应，对面可能已经把「还能再借」算完了，也可能根本没收到。所以超时从拆分的这一天就要有，保护的细节在容错那一节。同步调用链上每一跳都吃掉一段延迟预算。入口剩下 300 毫秒时，里面不能再各拿完整的 300 毫秒。

#### 序列化和字段号

进程之间先把内存里的对象变成一串字节，对面再还原。JSON 是文本，人能直接读，字段靠名字对齐。有人把 `loanDays` 改成 `days`，或者把数字写成字符串，对面就解析失败，或者悄悄读成别的含义。面向浏览器、小程序和 App 的接口继续用 HTTP 和 JSON，多出来的字段不返回给调用方，进来的未知字段忽略。

内部调用密、字段稳定、语言不同时，契约用 protobuf 写下来：哪个字段是借阅天数，类型是什么，字段编号是多少。描述语言独立于编程语言，各端从同一份 `.proto` 生成代码。线上传的是字段编号和紧凑的字节。一条字段由 tag 和值组成，tag 把字段编号和线类型编在一起：编号越小，tag 越短。旧代码遇到不认识的编号，按线类型跳过这段字节。proto3 会把不认识的字段留着，中间服务再转发出去时不会丢掉。改字段名不影响线上字节，因为线上没有名字。改类型、改编号、复用已经废弃的编号，调用方就会读错。

兼容按编号来。服务端新加一个字段并先上线，旧调用方按编号跳过不认识的字段。只加字段、不改旧字段的含义、不复用废弃的编号。废弃的号标成 reserved。破坏性变更用新的方法或新的路径。CI 对 `.proto` 做破坏性变更检查。单条消息保持在几兆以内。封面和电子书不进这条消息。

#### 对象存储

封面和电子书的字节放在对象存储里。书目表存桶名、对象键、大小、内容类型和校验和。RPC 和缓存里只出现这个键。把文件放进 MySQL 的大字段，备份、复制和缓冲池都会被几兆的封面撑大。

上传由浏览器或小程序直传。书目服务先核对这是管理员、类型和大小在限额内，再签发一个短时的上传地址。文件不经过业务进程。上传完成后，客户端把对象键交回来，书目服务核对存储上的大小和校验和，再把键写进书目表。没写进表的对象由对账任务清理。下载私有的电子书同样签发短时地址，过期自己失效。封面若对所有学生公开，走 CDN，桶策略只公开封面这个前缀。

长期密钥留在书目服务或云上的角色里，不放进浏览器，也不写进镜像。删书时先把书目行标记掉，对象异步删。对账看两方向：书目行指向的键在桶里是否还在，桶里超过保留期、没有任何书目行指向的对象删掉。国内把这类文件放在阿里云 OSS 或腾讯云 COS，自建用 MinIO，三套都按对象键访问。

#### HTTP 和 RPC

对外是 HTTP 加 JSON。对内的远程过程调用把「调某个方法」收成生成代码：建连接、序列化、发请求、收响应、反序列化都在框架里。gRPC 跑在 HTTP/2 上。一条连接里可以同时有很多请求，每个请求有自己的流。四层负载均衡若把整条连接钉在解析结果里的第一台，扩容对这条连接上的后续 RPC 无效。客户端要按单次 RPC 做轮询，或者由认识 HTTP/2 的代理按请求转发。`grpc-go` 的默认策略是 `pick_first`，内部调用要显式改成 `round_robin`。

截止时间放在这次调用的上下文里，框架把它写进 `grpc-timeout`。业务错误用稳定的状态码取出来：找不到是 `NOT_FOUND`，库存或资格不满足是 `FAILED_PRECONDITION`，下游暂时不可用是 `UNAVAILABLE`。不比较错误字符串。全是 Java、而且已经在 Dubbo 上时，用 Dubbo 3 的 Triple，它也跑在 HTTP/2 上，契约仍然落到同一份 protobuf。

#### 两个库没有同一个事务

一次借书要改借阅库，通知记录在另一个服务里。XA 让所有参与者先准备再提交。协调者在准备之后宕机，参与者会一直占着锁等它。InnoDB 内部 redo 和 binlog 的两阶段是一个进程里的事，和跨服务的 XA 不是同一件事。Seata 的 AT 模式靠前后镜像回滚，全局锁加在热点行上时，并发会被打下来。

借书主链路用发件箱：借阅记录和待发送事件写在同一个本地事务里。提交之后另一个循环把未发送的行推到队列，通知服务再消费。中间有一段时间通知还没发出去，用对账补。Saga 是一串本地事务加补偿：编排式由一个协调者按步骤调用，失败了按相反顺序补偿；编舞式由每个服务发出事件，下一个服务自己接着做。补偿要幂等。Saga 没有隔离，步骤之间别人能看见中间状态，业务上把「借阅中」「已取消」写进状态机。TCC 把资源分成 Try、Confirm、Cancel。Try 先预留，Confirm 再确认，Cancel 释放预留，步骤之间别人拿不走已经预留的库存。三个阶段都要写，并且按事务号幂等。空回滚是 Cancel 比 Try 先到，Cancel 要能当成无事发生。悬挂是 Cancel 之后迟到的 Try，Try 要拒绝。借书这种主链路不使用数据库 XA 去包 HTTP。库存若和借阅同库，就留在这个事务里。

国内主流分两条线。Java 业务团队的默认组合是 Spring Cloud Alibaba：注册和配置用 Nacos，服务之间用 OpenFeign 或 Dubbo 3，后面的限流熔断用 Sentinel。Spring Cloud Netflix 那一套（Eureka、Hystrix、Zuul）已经停止更新，只留在旧系统里。阿里系和很多互联网公司内部 RPC 仍是 Dubbo，新版本的 Triple 跑在 HTTP/2 上。Go 侧字节系用 Kitex、tRPC，B 站用 Kratos，很多中小团队用 go-zero 或 Gin 加 gRPC。跨 Go、Java、Python 的新契约，国内新项目收成 protobuf。只在一个 Java 团队内部时，国内默认答案仍然是 Dubbo 或 HTTP JSON，不会为了单一语言先上 gRPC。分布式事务在 Java 简历和项目里常见 Seata，落地时热点写更多改成本地消息表。

### 当前最优解

三个信号还没同时出现时，保持一个进程、一个库、按包分边界。三个信号到了再拆成用户、书目、借阅、座位。每个服务拥有自己的表。

对外继续 HTTP 和 JSON。对内跨 Go、Python、Java 的调用用一份 protobuf，gRPC 作为运行时。Java 服务之间如果整条链路都在 Dubbo 上，可以继续用 Triple，契约仍然落到 protobuf，避免再维护一套只在 Java 里存在的接口定义。

跨服务的写用发件箱，后面的消息队列一节把投递补完。借书这种主链路不使用数据库 XA 去包 HTTP。封面和电子书放对象存储，书目表只存桶、对象键、大小和校验和。桶保持私有，上传和下载走短时地址，长期密钥留在书目服务。

这一步结束时，每个业务有自己的发布节奏和数据。一次借书已经是跨网络的多次调用。

## 05 容器编排

几十个服务，每个跑几十份副本。新容器该放哪台还有空闲 CPU 和内存的机器，人已经算不清。开学前借阅服务要加实例，闲下来要减。半夜某个容器停了，或者某台物理机坏了，要有人把它拉起来。容器编排系统把这三件事自动化。Kubernetes 是这一层的常见实现。

### 声明期望状态

人写的是期望状态：借阅服务要 50 个副本，用哪一份镜像，每个副本要多少 CPU 和内存，就绪之后才接流量。控制面拿期望和现状比较，少了就补，多了就收，把容器安排到还有余量的机器上。半夜容器退出，或者机器失联，控制面把副本再补到 50。开学前把副本数调高，闲下来调低。也可以按 CPU 或每秒请求数自动改这个数字。忙时加上去、闲时缩回来，改的仍是同一份期望。

这和把程序固定装在几台虚拟机上不同。以前扩容是人登上去装一份。现在机器是可以被替换的，副本死了就在别的机器上再起一份。滚动更新也写在期望里：先多起一个新副本，就绪探针通过后再停一个旧的，避免更新过程中一份能服务的副本都没有。

探针分成两件。存活探针失败，说明进程自己已经不正常，把它杀掉再拉起。就绪探针失败，说明它暂时不该接流量，从转发名单里摘掉，容器还在。前面反向代理做的“拿不到正常回复就摘掉”，在这里变成集群自己的名单。

### 服务发现

借阅服务把用户服务的 IP 写进配置文件，在地址不变的时候能连上。扩容、发新版本、崩溃重启都会换 IP，甚至换机器。旧配置立刻过期。

服务发现维护一份还能连的地址，分三步：

1. 注册。实例启动时把自己的地址登记上去。
2. 健康。实例每隔几秒发一次心跳，或者接受健康探针。心跳没了、探针失败，就把这份地址摘掉。临时实例随心跳存在；没有心跳的持久实例，崩溃后会一直留在名单里。
3. 查询。调用方来取当前名单，并在本地缓存一小段时间。缓存避免每次调用都问一遍注册中心。缓存要有过期，否则摘掉的实例还会被继续调用。

常见的注册中心有 etcd、Nacos 和 Consul。Kubernetes 里这份工作由 Service 和集群 DNS 做：调用方连的是服务名，名字解析到当前的一组地址。虚拟机或和虚拟机混部时再用 Nacos 这一类。两套发现各维护一份名单，调用方会拿到两套地址。选一套。

注册中心和 Redis 是同一类角色。它们不实现借书还书，站在业务进程旁边，给所有服务提供通用能力。注册中心自己停了，新的发现就停。已经缓存在本地的名单还能用一小段时间，所以注册中心也要多副本。

### Go、Python、Java

编排清单三种语言共用。差别在容器里的进程怎么理解 CPU、内存上限，以及探针该打哪一个路径。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 内存上限 | 设 `resources.limits.memory`。`GOMEMLIMIT` 设在这个上限的八到九成，把 GC 目标放在 cgroup 杀掉进程之前 | 一个 Uvicorn worker 一份内存。容器里再开多个 worker，内存和数据库连接按 worker 数乘 | `-XX:MaxRAMPercentage=70` 把堆限制在容器内存的七成。堆外、元空间、线程栈留在剩下的三成。`/tmp` 用 emptyDir，只读根文件系统上 Tomcat 才能解压 |
| CPU | Go 1.25 起 `GOMAXPROCS` 跟着 CPU limit 走。limit 仍是吞吐量上限，IO 型服务可以把 limit 设得高于 request | CPU 密集的段落不靠把异步路由改成 `async def` 解决。那种工作丢进进程池，或者丢进后面的队列 | 虚拟线程减少的是占用平台线程的时间。CPU 密集的代码仍占着载体线程。容器的 CPU limit 会节流，和堆的大小是两套设置 |
| 探针 | 存活打 `/healthz`，只判断进程还能不能回答。就绪打 `/readyz`，这里才查数据库和 Redis。镜像里没有 curl，探针用 HTTP | 启动比 Go 慢，`startupProbe` 把失败次数留够，启动完成后再开始存活探针。存活里不查 Redis | 启动更慢，启动探针的窗口按一次冷启动的耗时留。Spring Boot 3.3 起可以用 CDS 把类数据归档打进镜像，窗口能短一截。归档和 classpath 必须一致 |
| 发现 | 集群内直接连 `user.namespace.svc`。需要注册中心时用 `nacos-sdk-go` v2，gRPC 端口是 HTTP 端口加 1000 | 同样连服务名。混部时用 `nacos-sdk-python` v2 | Spring Cloud 的 Nacos 客户端。临时实例靠心跳。进程退出要反注册，杀进程时靠心跳超时兜底，所以调用方自己的超时仍要设 |
| 配置 | 环境变量和启动时读完的配置。缺字段就退出。业务开关进配置中心，改数据库地址仍要重建连接池，跟着滚动更稳 | `pydantic-settings` 在启动时校验。热更新只换进程内的不可变配置对象，不在请求中途换掉正在用的连接池 | `@ConfigurationProperties` 启动时校验。`@RefreshScope` 能重建一部分 Bean。已经建立的 Hikari 池不会因为配置文本变了就自动换主机 |

滚动更新三种语言同一份策略：`maxUnavailable: 0`、`maxSurge: 1`，先起一个新 Pod，就绪之后再停旧的。`preStop` 先等几秒，让端点从转发名单里摘掉，再处理 `SIGTERM`。镜像里没有 shell 时，用生命周期自带的 `sleep`，不写 `sh -c`。`terminationGracePeriodSeconds` 要盖住这段等待加上进程自己的优雅退出。

扩容看饱和，不单看 CPU。Go 看正在处理的请求数、`database/sql` 的 `WaitDuration`、goroutine 数。Python 看事件循环滞后和连接池占用。Java 看 Tomcat 或虚拟线程的在途请求、Hikari 的等待。这些做成指标再交给 HPA。队列堆积的消费者用 KEDA 按 lag 扩，放在消息队列那一节。

### 技术和必会点

这一层的技术是容器编排、服务发现和配置。应用框架不再负责「进程该落在哪台机器」，集群负责。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| 编排 | 维持副本数、滚动、自愈 | Kubernetes，云上是 ACK、TKE、CCE |
| 工作负载 | 无状态服务、有状态中间件、每节点一份的代理 | Deployment、StatefulSet、DaemonSet、Job |
| 发现 | 用名字找到还活着的 Pod | Service、CoreDNS、kube-proxy |
| 注册和配置 | 虚机混部，或业务开关热更新 | Nacos、Apollo、etcd、Consul |
| 弹性 | 按饱和度加减副本 | HPA、KEDA |
| 发布细节 | 探针、优雅停机、不可用预算 | startup/readiness/liveness、preStop、PDB |
| 网络边界 | 业务端口只接受指定来源 | NetworkPolicy、安全组 |

#### 控制面和节点

人写的是期望：借阅服务 50 个副本、哪份镜像、每个副本要多少 CPU 和内存。控制面拿期望和现状比较，少了就补，多了就收。半夜容器退出或机器失联，副本会被补到 50。再跑一遍如果已经对齐，就什么都不做。以前扩容是人登上去装一份。现在机器可以被替换，副本死了就在还有余量的机器上再起一份。

API Server 是唯一入口，所有写操作经过它。etcd 存集群状态，至少三节点、奇数个，靠多数派提交。调度器给还没有节点的 Pod 选机器，依据是资源请求、亲和和污点。控制器把副本数维持住。节点上的 kubelet 拉镜像、起容器、做探针，停机时先跑 preStop，再发 `SIGTERM`。名字解析和把虚拟 IP 转到 Pod 的部分写在 Service 里。

Pod 是调度的最小单位。同一个 Pod 里的容器共享网络和卷，用 localhost 加端口互相访问。可以分开扩缩的借阅和书目分成不同的 Deployment。

#### 工作负载和 Service

无状态的借阅服务用 Deployment，Pod 可以替换。要稳定网络名和每副本一块盘的数据库、队列用 StatefulSet，盘用 `volumeClaimTemplates` 按序号各申请一块，访问模式是同一时刻只挂到一个节点。日志采集这种每个节点一份用 DaemonSet。迁移用跑完就结束的 Job，不放进每个副本的启动。

Service 按标签选 Pod，提供一个稳定的虚拟 IP。`ClusterIP` 只在集群内，应用只连这个 DNS 名，例如 `user.namespace.svc`。`NodePort` 在每个节点上开一个高位端口。`LoadBalancer` 让云创建外部负载均衡。就绪 Pod 的地址放在 EndpointSlice 里，按协议和端口分组。切片为空时，Service 有地址但转不走，调用方看到连接失败，先查标签和就绪探针。CoreDNS 只把名字解析成这个虚拟 IP。kube-proxy 用 iptables、IPVS，或由 eBPF 监听切片，把发往虚拟 IP 的包改写到某个 Pod。DNS 不负责在 Pod 之间挑一个。

Nacos 的临时实例靠心跳，心跳没了就摘掉。持久实例没有心跳，进程崩溃后会一直留在名单里。两套发现各维护一份名单时，调用方会拿到两套地址。纯 Kubernetes 的新服务只连 Service。已经在用 Nacos 做业务开关时，Nacos 只做配置，实例名单仍交给 Service。只改 ConfigMap 不会重启容器，进程已经读进内存的数据库地址也不会自动换池。换地址跟着滚动，给 Pod 模板加一个配置摘要，摘要变了就重建。

集群的默认常常是同一集群里的 Pod 都能互相访问。NetworkPolicy 按标签选定一组 Pod，再写明入站允许哪些命名空间、哪些端口。借阅、书目、用户的业务端口只允许网关所在的命名空间。MySQL 和 Redis 只允许应用命名空间，网关也不直接连库。没有策略的虚拟机部署用安全组做同一件事：应用端口只对负载均衡开放，不对公网开放。头上的用户 id 仍按网关那一节校验。网络放行和头的信任是两道，少一道，脚本就能绕过入口。

#### 三种探针

启动探针给足失败次数。Java 冷启动比 Go 慢，窗口按一次冷启动的耗时留，过了启动阶段才开始存活探针。存活探针打 `/healthz`，只判断进程还能不能回答。失败说明进程自己不正常，杀掉再拉起。就绪探针打 `/readyz`，这里才查数据库和 Redis。失败只是从转发名单摘掉，容器还在。数据库和 Redis 放进存活，依赖一抖，kubelet 会把借阅的副本全部重启，故障被放大成重启风暴。镜像里没有 curl，探针用 HTTP。

探针有自己的周期、超时和连续失败次数。一次探测超时算一次失败。存活的连续失败次数设得太小，一次 GC 停顿就会把进程杀掉。启动探针允许的失败次数乘上周期，要盖住一次冷启动。就绪可以失败得更勤，摘掉流量比杀掉进程便宜。

#### 资源、滚动和停机

requests 给调度看，调度器按它判断这台机器还剩多少。limits 是上限。两者相等是 Guaranteed。只设了 requests，或两者不等，是 Burstable。都没设是 BestEffort，节点内存紧张时最先被杀。CPU 的 limit 会节流：进程还能跑，但被掐住时间片，延迟上去。IO 型的借阅服务可以把 CPU limit 设得高于 request。内存 limit 仍然要设。Go 把 `GOMEMLIMIT` 放在内存上限的八到九成，GC 目标在 cgroup 杀掉进程之前。Java 用 `-XX:MaxRAMPercentage=70` 把堆限制在容器内存的七成，堆外、元空间和线程栈留在剩下的三成。

滚动用 `maxUnavailable: 0`、`maxSurge: 1`：先多起一个新 Pod，就绪之后再停旧的。`minReadySeconds` 设几秒，避免刚通过探针就接全量。副本数至少 2，再加 `PodDisruptionBudget`，腾挪节点时至少留一个能服务的 Pod。副本数是 1 时，这条预算和自愿驱逐会互相卡住。

Pod 进入 Terminating 之后，端点摘除和 `preStop` 并行发生。摘除要等转发规则刷新，这段时间新请求还会进来。`preStop` 里先等几秒，再让进程处理 `SIGTERM`。镜像里没有 shell，用生命周期自带的 `sleep`，不写 `sh -c`。`terminationGracePeriodSeconds` 从停机流程开始算，要盖住这段等待加上进程自己的优雅退出。默认 30 秒，preStop 睡 10 秒、优雅停机再要 30 秒，事务还没提交就会被 `SIGKILL`。

#### 扩容看饱和

CPU 低不代表还能接请求。借阅经常堵在等数据库，CPU 不高，连接池和在途请求已经满了。扩容看正在处理的请求数、连接池等待、goroutine 数或事件循环滞后、Hikari 的等待。这些做成指标再交给 HPA。堆使用率不拿来扩容，GC 之后 RSS 也不会立刻回到零。队列堆积按 lag 扩消费者，用 KEDA。goroutine 或在途请求涨，往往是下游变慢，扩容之前先确认下游还能接。

国内主流分两档。互联网和上云的团队，编排就是 Kubernetes，阿里云 ACK、腾讯云 TKE、华为云 CCE。传统行业仍有一批虚拟机加 Nginx 加发布脚本。业务注册和配置在国内默认是 Nacos。Apollo 是另一大配置中心存量，尤其在携程系和一部分金融系统。Consul 更多出现在早期运维和 Go 项目。etcd 是 Kubernetes 自己的存储，也用来做选主和租约，一般不拿来给所有业务服务当注册中心。纯 Kubernetes 的新服务只连 Service，Nacos 若已经在用，就只做配置和开关。

### 当前最优解

业务服务用 Deployment。副本数至少 2，再加 `PodDisruptionBudget`。数据库和消息队列这种要稳定名字和独立磁盘的，用 StatefulSet，不和业务服务放在同一种工作负载里。

服务发现只用 Kubernetes Service 和 CoreDNS。调用方连服务名。配置用 ConfigMap 和 Secret，变更靠滚动。已经在用 Nacos 做业务开关时，Nacos 只做配置，实例名单仍交给 Service。两套名单一起用，调用方会拿到两套地址。

探针分成启动、就绪、存活。依赖失败只让 Pod 从 Service 摘掉，不重启。进程自己不回答了才重启。业务端口用 NetworkPolicy 只接受网关所在的命名空间。MySQL 和 Redis 只接受应用命名空间。虚拟机部署用安全组做同一件事。

这一步结束时，副本数和放置由控制面维持，调用方靠服务名找到活着的实例。一次调用本身还没有超时和熔断。

## 06 容错

用户服务变慢或无响应时，借阅服务发过去的请求都挂在那里等。借阅服务里等待的并发被占满，它自己也开始变慢。调用借阅服务的上层跟着堵住。局部故障沿调用链逐级放大，最后整段核心链路都停，这是雪崩。

一次正常的远程调用按这个顺序保护：

1. 从服务发现的名单里挑一个实例。挑的时候跳过刚失败的，避免把流量继续打进已知不健康的副本。
2. 连接放进连接池。建立连接要握手，开销大，每次调用都新建连接会把时间花在握手上。池有上限，连接数不会跟着请求数一起涨。每个下游单独一份池，慢的下游只占满自己的那一份。
3. 发出去之后设超时。拨号、等待响应、整次调用分开计时。超时从入口的剩余时间往下缩短，下游拿到的时间比上游更短，上游才有机会在自己超时前返回。
4. 重试只打在可以重复执行的操作上。查询可以重试。借书这种会扣库存的，带上幂等键再重试：同一次提交用同一个键，服务端认出是同一笔，返回第一次的结果。重试有次数、有间隔，间隔加随机抖动，避免所有调用方在同一时刻一起重试。下游已经慢的时候，重试会把请求量成倍放大。
5. 失败比例或慢调用比例超过阈值，熔断器打开，这条链路暂时不再发起真实调用，立刻失败，或者走降级。推荐服务被熔断时，主页面先不展示推荐列表，借书仍能做完。过一段时间进入半开，放少量请求试探。成功再合上，失败就继续断开。
6. 每个下游单独一份并发额度。推荐慢，只占满推荐的额度。借书还有自己的连接和并发。这是舱壁：一个下游把额度用完，别的下游还能走。

入口还要有限流和过载拒绝。正在处理的请求已经到了容量，就直接拒绝，并告诉调用方过多久再试。继续排队会让在途请求按“到达率乘以停留时间”继续涨，把后面的请求一起拖死。上限按连接池和能接受的等待时间来定。

这些能力由微服务框架做进进程。框架是编译进程序的代码：找地址、负载均衡、连接池、超时、重试、熔断、隔离都在这次调用的路径上。课设留下的 Java 服务用 Java 生态里的这套组件。新服务用 Go 时，腾讯的 tRPC-Go、B 站的 Kratos 把同一组能力装进 Go 进程。中小团队用现成框架。后面的推荐、检索和各种算法服务，只要它会调用别的服务或被别人调用，就套同一组保护。

原则是一条：上下游都会失败。超时、受控重试、熔断降级和隔离把故障留在局部。调用方要能在下游无响应时自己结束等待。

### Go、Python、Java

保护写在调用方进程里。三种语言的差别是这些上限落在哪种类型上，以及哪一种运行时会被同步调用拖住整个进程。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 超时 | `context.WithTimeout`。gRPC 把它写进 `grpc-timeout`。HTTP 客户端把拨号、TLS、响应头分开。没带截止时间的 `context.Background()` 会在池空时一直等 | `httpx.Timeout` 把 connect、read、write、pool 分开。`async def` 里调用 `requests` 或 `time.sleep` 会停住这个 worker 上的全部请求 | Feign 的 `connectTimeout` 和 `readTimeout` 按客户端设，默认往往比网关还长，要写短于入口剩余时间。`RestClient` 同样在客户端上设 |
| 舱壁 | 每个下游一把 `semaphore.Weighted`，再加一份独立的 HTTP 连接池。推荐的额度用完，借书的信号量还在 | 每个下游一把 `asyncio.Semaphore`，再加一份 `httpx.Limits`。信号量在进连接池之前获取 | 每个下游一份连接限额。Sentinel 还可以按并发线程数限。虚拟线程开了之后，舱壁仍然要设，否则慢下游会拉出大量虚拟线程堵在 IO 上 |
| 重试 | 只包幂等的方法。次数少，间隔加抖动。`go-redis` 的写把 `MaxRetries` 设为 -1。gRPC 对 `UNAVAILABLE` 的幂等方法才重试 | 同一份 `httpx` 客户端上包一层有限重试。写接口带 `Idempotency-Key`。重试前先看这次调用的截止时间还剩多少 | Spring Cloud OpenFeign 的默认重试器是 `NEVER_RETRY`。幂等的读要换实例再试时，显式打开，并限制次数。LoadBalancer 的重试和 Feign 的重试会乘在一起 |
| 熔断 | 进程内熔断器，按下游记失败率和慢调用。半开只放少量请求。团队已经用 Kratos 时，熔断放在它的 middleware 里，不另写一套 | 进程内熔断。Gunicorn 多 worker 时每个 worker 各算各的，样本少，打开得更慢。入口的全局限流不靠这个计数 | Sentinel 按慢调用比例、错误比例熔断，`blockHandler` 处理限流，`fallback` 处理业务降级，两条分开。Resilience4j 是另一套实现。同一个下游只留一套计数 |
| 过载 | 在途 goroutine 到上限就返回 503，带 `Retry-After`。上限按连接池和能接受的等待时间定，不按机器还能再开多少 goroutine 定 | 在途请求到上限就拒绝。异步服务的上限看事件循环能否继续调度，不看线程数 | 在途请求到上限就拒绝。Servlet 容器的队列长度写明。队列太长时，延迟已经变高的请求还在排队 |

幂等键由调用方生成，放在头里。同一次提交的自动重试用同一个键，用户明确再点一次才换新键。服务端用数据库唯一键记住结果。超时之后用同一个键再请求，拿到的是第一次的响应。

降级按业务写。推荐服务打开熔断时，Go、Python、Java 都返回空的推荐列表和明确的状态，借书接口不调用推荐。缓存里的旧书目可以用来展示，库存仍以主库为准。

### 技术和必会点

这一层没有新的业务系统，是给每一次远程调用加上的保护。框架把这些保护做成调用链上的拦截器。国内 Java 项目里，这套框架几乎就是 Sentinel。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| 超时 | 下游不回时调用方自己结束等待 | `context`、httpx、Feign、gRPC deadline |
| 重试 | 失败后再试，只试幂等的 | 框架重试器，必须限次数和抖动 |
| 熔断 | 下游已经坏了就暂时不再打 | Sentinel、Resilience4j、Kratos middleware |
| 舱壁 | 一个慢下游只占自己的并发额度 | 信号量、独立连接池、Sentinel 线程数限流 |
| 限流 | 整站按路由，热点按书号 | 令牌桶、漏桶、滑动窗口；Sentinel 热点参数 |
| 降级 | 熔断之后返回还能用的结果 | 空推荐、旧书目、明确的稍后再试 |
| 幂等 | 同一次提交重试不会借出两本 | 幂等键、数据库唯一索引 |

#### 超时和截止时间

入口剩下 300 毫秒，下游就不能再拿完整的 300 毫秒。拨号、TLS、等待响应头、整次调用分开计时。整次调用的截止时间从入口的剩余时间往下缩短，上游才有机会在自己超时前返回一个明确的失败。gRPC 把截止时间写进 `grpc-timeout`。池子借光时，没有截止时间的调用会一直等，把后面的请求一起拖住。超时只说明调用方不再等，对面可能已经把借书做完了，所以超时之后的重试必须能认出是同一笔。

#### 重试

下游已经慢，每个调用方再试三次，到达下游的流量变成四倍。只重试查询，以及带幂等键的写。间隔加随机抖动，避免所有调用方在同一毫秒一起重试。次数要少，重试前先看这次调用的截止时间还剩多少，不够就不再试。两层框架都开重试时，次数相乘：Feign 的重试和负载均衡的换实例重试是这样，边车的重试和应用的重试也是这样。下游返回「库存不足」是业务结果，再试也是同一个结果。`UNAVAILABLE` 这种暂时连不上，才值得换一个实例再试。

#### 熔断三态

关闭时正常调用，并统计失败比例和慢调用比例。过了阈值就打开，打开期间立刻失败或走降级，不再把请求打进已经坏了的下游。过一段时间进入半开，放少量请求试探。成功再关闭，失败继续打开。推荐服务打开熔断时，主页面返回空的推荐列表和明确的状态，借书接口不调用推荐。缓存里的旧书目可以用来展示，库存仍以主库为准。

计数按下游分开。同一个下游只留一套计数。Sentinel 和另一套熔断同时统计，阈值会对不上。Gunicorn 多 worker、或者每个副本各算各的时候，样本少，打开得更慢。全站是否已经坏了，要看入口的错误率，不靠某一个 worker 的窗口。

#### 舱壁和过载

舱壁隔离的是资源。推荐的连接池和并发额度用完，借书还有自己的那一份。推荐慢，只占满推荐的信号量。虚拟线程开了之后，舱壁仍然要设，否则慢下游会拉出大量虚拟线程堵在 IO 上。

过载是自己这一侧已经满了。在途请求到了连接池和能接受的等待时间，就直接返回 503，带 `Retry-After`。继续排队会让停留时间变长。在途数量大约等于到达率乘以停留时间：延迟已经变高时还继续收，在途请求按这个乘积涨上去，把后面的请求一起拖死。上限按池子能承受的量来定。Go 不按机器还能再开多少 goroutine 来定。Java 的容器队列写明长度，队列太长时，延迟已经变高的请求还在排队。

#### 限流算法

固定窗口在边界两侧各放进一整窗的量，窗口一交界就会放进大约两倍流量。滑动窗口看最近一段时间，边界平滑，实现上把这段时间切成小格，过期的格子丢掉。漏桶按固定速率放行，出口更平，桶满就拒绝或排队。令牌桶有两个数：每秒补充多少令牌，桶里最多攒多少。桶满之后多出来的令牌丢掉，突发停在这个容量上，桶空了就拒绝。刷座位用令牌桶或滑动窗口。进程内的计数每个副本各算各的，十个副本各放 100，全站就是 1000。全站配额放在网关或 Redis，用一段 Lua 做完取令牌。进程内的桶只挡住这一副本的突发。

熔断的统计也是一个时间窗。窗口里的请求数没到最小样本，不打开，避免两三笔失败就把下游判死。慢调用先定一个耗时阈值，超过的算慢。错误比例和慢调用比例各有一条线。打开之后有一段休眠，休眠结束才进入半开。半开放行的请求数是单独的额度，这几笔都成功才回到关闭。

#### 热点参数

全站令牌桶按路由计数。开学季某一本教材被几千人同时点，整条借书路由的配额被这一本书吃光，别的书也借不出去。热点参数把限流的维度落到书号上。这一本被拒绝时，其他书号继续走。

Sentinel 按参数值统计，规则写明看第几个参数、阈值多少。Go 没有这套组件时，用一张有上限的本地令牌桶表，键是书号。冷门书号从这张表里过期删掉。把每一个书号都做成指标标签，时间序列会按书的数量涨，和可观测性里的高基数是同一件事，书号留在日志里。

进程内的计数每个副本各算各的。十个副本各自放行 100，这一本书全站仍是 1000。要全站按书号限，计数放在网关或单独的令牌服务。缓存击穿是键过期之后大家一起回源。热点限流发生在回源之前，超出的请求直接拒绝。同一本书上两件事可以同时存在，处理的位置不同。

#### 幂等键

同一次点击的自动重试用同一把键。用户明确再借一次，才换新键。键由调用方生成，放在头里。服务端用数据库唯一键记住第一笔的结果：先插入这把键，冲突就读出上一次的响应。同一个键配了不同的请求体，返回冲突，不把另一本书借出去。超时之后用同一个键再请求，拿到的是第一次的结果。只在 Redis 里用一个会过期的键挡住重复，键过期之后，再来的请求会再借一本。持久的去重放在 MySQL。

幂等是指同一操作执行一次和执行多次，系统状态相同。查询天然可以重试。扣库存的条件更新配上这把唯一键，重试也不会借出两本。代理和框架不知道这一次借书能不能安全地发第二次，这个判断留在业务里。

国内主流是 Sentinel。它覆盖流量控制、熔断、热点参数和系统负载，规则可以推到每台机器。Hystrix 已经停止维护，新项目不再用。Resilience4j 出现在跟着 Spring 官方生态走的团队，和 Sentinel 二选一，两套同时计数会对不上。Go 侧用 Kratos、go-zero 自带的中间件，也有 Sentinel 的 Go 版本。限流的全站部分国内放在网关，进程里的 Sentinel 挡这一台的突发和热点书号。

### 当前最优解

每次出站调用都带截止时间，并且比入口的剩余时间更短。每个下游单独的连接池和并发额度。重试只打在查询和带幂等键的写上，次数少，带抖动。熔断按下游统计，半开再探测。

Java 侧熔断和热点参数用 Sentinel 这一套。Go 侧放在调用封装或 Kratos 的 middleware 里，热点书号用一张有上限的本地令牌桶表。Python 侧放在 `httpx` 客户端的封装里。三种语言不把熔断再叠加到网关上的另一套计数。全局限流放在下一节的网关。某一本书的突发按书号单独限，进程内的桶只挡住这一副本。全站按书号的配额放在网关或令牌服务。

这一步结束时，推荐卡死不再拖垮借书。外部调用方仍然要知道每个服务的地址，登录校验也还散在各个服务里。

## 07 网关

访问方不再只有浏览器。微信小程序、手机 App、学校的开放接口都要进平台。后端已经是几十个服务。调用方记不住每个服务的内部地址，也不该连进内网。脚本如果能直接打到座位服务上，就可以绕过页面刷自习室座位。

网关站在外网和集群之间，角色像家里的路由器站在家庭网络和外面之间。最早那层反向代理已经在做“一个地址后面藏着多台机器”。服务多了之后，它独立成所有外部请求进入集群的统一入口，并且按请求内容转发。

路由按路径或主机名把请求转到服务。借书转到借阅服务，查书转到书目服务，预约座位转到座位服务。网关可以把外部的 HTTP 转成内部的 RPC，这是协议转换。过滤是另一块职能，和业务服务分工不同：网关做所有服务都要的事，业务服务做和这笔资源有关的事。

所有服务都要的事放在网关：

- TLS 在这里结束。证书集中在入口，业务进程处理已经解密的请求。
- 登录态在这里验一次。前面每个实例自己拿会话编号去查 Redis。现在由网关查，查完把用户 id 写进往下传的内部头。几十个业务服务不再各自写登录校验。调用方自己带的同名头在入口清掉，再由网关写入，外面伪造的用户 id 进不了内网。
- 限流按用户和接口挡在边界。刷座位的脚本在进座位服务之前就被拒绝。没有登录态的接口按 IP 限流。只按 IP 会误伤出口地址相同的一群人，有用户 id 时用用户 id。
- 入口生成请求编号，写进访问日志，再往下传。后面的追踪用的就是这个编号。

业务进程里留下和资源有关的事：参数是否合法、这本书是不是这个学生借的、这一次提交是不是重复的。网关不知道借阅记录的属主。

网关自己要有多份，前面再有一层把流量分给这些网关。单份网关停了，整个入口就停。真正进入集群以后，服务之间的调用走内部的服务发现，不再绕回网关。绕回去会让东西向的流量都挤在入口上，网关的发布也会变成全部内部调用的发布。

### Go、Python、Java

网关一旦独立成进程，业务服务里就只留下和这笔借阅有关的检查。三种语言的写法差在“用户 id 从哪读”和“哪一层还要再验一次属主”。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 入口还只有一个服务时 | Gin 中间件读会话、写请求 id、按用户限流。可信代理设成网关网段，`ClientIP` 才不会采信调用方自己带的 `X-Forwarded-For` | 鉴权做成 `Depends`，挂在路由器上。请求 id 放进 `contextvars` | 过滤器比拦截器更靠外，可以挡住没进控制器的请求。请求 id 放进 MDC |
| 服务变多之后 | 业务进程只读网关写好的用户 id。客户端自己带的同名头在网关清掉。资源属主在处理函数里查：这本借阅是不是这个学号的 | 路由函数从依赖里拿学号，不从 JSON 正文里的学号字段做授权。Pydantic 只证明形状合法 | 控制器从网关写入的头拿学号。`@Valid` 只证明形状。订单属主在服务里查。网关如果用 Spring Cloud Gateway，它跑在 WebFlux 上，过滤器里用 WebClient 和响应式 Lettuce，阻塞的 `RestTemplate` 会占住事件循环 |
| 限流键 | 进程内 `golang.org/x/time/rate` 只挡这一副本的突发。全站配额用 Redis Lua | 进程内计数同样只代表这一 worker。全站配额放在网关的 Redis 令牌桶 | Sentinel 的进程内计数也是各副本各算各的。入口用网关的 Redis 限流，按用户 id；没有登录态时用 IP |

浏览器继续用上一节的 Redis 会话。小程序、App 和开放接口用访问令牌：认证服务用私钥签名，网关用公钥验，业务服务不持有私钥。载荷里放用户 id、过期时间、签发方、受众和 `jti`。密码和手机号不放进去。访问令牌的有效期用几分钟到一刻钟。刷新令牌只交给认证服务，注销时作废刷新令牌，并把还没过期的 `jti` 放进拒绝列表，直到它自己的过期时间。验签时算法在服务端固定，不采用令牌头里临时指定的算法。

改数据的浏览器接口再对一份 CSRF 令牌。带了 Cookie 只说明浏览器自动附上了会话，还不能单独当作授权依据。

### 技术和必会点

这一层是集群的南北向入口。反向代理只做「一个地址后面多台机器」。网关在这之上按路径转发，并统一做 TLS、鉴权、限流和请求编号。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| 网关 | 外部请求的唯一入口 | Apache APISIX、Spring Cloud Gateway、Kong、Nginx |
| 云上网关 | 不想自建控制面时 | 阿里云 MSE 云原生网关、API 网关，腾讯云 API 网关 |
| TLS | 证书和加解密收在入口 | 网关或 Ingress 终止 HTTPS |
| 身份 | 浏览器会话或访问令牌 | Redis 会话、JWT、OAuth2 的访问令牌和刷新令牌 |
| 安全框架 | Java 进程里的认证授权 | Spring Security、Sa-Token |
| 限流 | 按用户挡住刷座位 | 网关的 Redis 令牌桶、APISIX limit-count |
| 网络边界 | 业务端口只接受网关来的流量 | NetworkPolicy、安全组 |

#### 网关、反向代理、南北向

最早那层反向代理做的是「一个地址后面多份相同进程」：轮询或最少连接，不健康的摘掉。服务变成几十个之后，入口还要按路径或主机名把借书转到借阅服务、把查书转到书目服务，并在边界做所有服务都要的事。资源是不是这个学生的，网关不知道，仍留在业务进程里。

浏览器和 App 进网关，这是南北向。进了集群之后，借阅调用户服务走内部的服务发现，这是东西向。东西向再绕回网关，入口会变成全部内部调用的瓶颈，网关的发布也会变成全部服务的发布。网关自己至少两副本，前面再有一层把流量分给这些网关。单份网关停了，整个入口就停。

TLS 在网关结束。握手时客户端验证证书链，双方用证书上的公钥协商出会话密钥，之后的 HTTP 用这个密钥加密。私钥只放在网关，业务进程处理已经解密的请求。证书要在过期前续上，续期只换入口的证书和私钥。集群内部如果到这里就不再加密，借阅服务之间的调用在机房网络上是明文，服务之间的身份和加密留到网格。网关可以把外部的 HTTP 转成内部的 RPC，这是协议转换。过滤是另一块职能：鉴权、限流、请求编号、访问日志。

#### 两种登录态

浏览器把随机编号放 Cookie，学号和权限放 Redis。注销就是删掉这一份，所有实例立刻失效，改权限下一次请求就生效。代价是每个请求读一次 Redis。Cookie 会由浏览器自动带上。`SameSite=Lax` 挡住别的站点发起的 POST，顶层链接进来的 GET 仍会带上。会改数据的浏览器接口再对一份 CSRF 令牌。带了 Cookie 只说明浏览器自动附上了会话，还不能单独当作授权依据。

小程序、App 和开放接口用访问令牌。令牌是三段 base64url：头、载荷、签名。载荷里放用户 id（`sub`）、过期时间（`exp`）、签发时间、签发方、受众和 `jti`。角色可以放，权限一改，旧令牌里的角色要等到过期。密码、手机号和完整资料不放进去，令牌会进日志和浏览器。

认证服务用私钥签名，网关用公钥验，业务服务不持有私钥。对称算法要求所有验签的服务共享密钥。验签按固定顺序做：把头里的算法收成服务端允许的那一种，用对应公钥验第三段，再查过期时间、签发方和受众，最后查 `jti` 是否在拒绝列表。任何一步失败都拒绝。不采用令牌头里临时指定的算法，否则调用方可以把算法换成 `none`，或换成自己的密钥。载荷是 base64url，谁拿到令牌都能读出用户 id，所以里面不放密码和手机号。访问令牌的有效期用几分钟到一刻钟。刷新令牌只交给认证服务，库里存它的哈希。换发时作废旧的刷新令牌、发新的一对。旧的刷新令牌再次出现，就把这一族都作废。注销时作废刷新令牌，并把还没过期的 `jti` 放进拒绝列表，直到它自己的过期时间。访问令牌越短，拒绝列表越小。时钟有偏差，`exp` 的校验留几十秒余量，余量只盖住时钟误差。

浏览器里，访问令牌放内存，刷新令牌放 `HttpOnly` Cookie。放进 `localStorage` 的令牌，页面上任何一段脚本都能读走。手机用 `Authorization: Bearer`。

#### 头的信任边界和限流键

调用方自己带的用户 id 头在网关清掉，再由网关写入。业务服务只接受来自网关网段的这个头。这本书是不是这个学号借的，用这个头去查借阅记录。JSON 正文里的学号只说明调用方声称自己是谁。Pydantic 和 `@Valid` 只证明形状合法，不证明属主。

头校验挡的是伪造的用户 id。Pod 地址或 NodePort 还能被集群里别的进程直接打到时，调用方可以自己写下这个头，校验等于没做。Kubernetes 用 NetworkPolicy：借阅、书目、用户的业务端口只接受网关所在的命名空间。MySQL 和 Redis 只接受应用命名空间。虚拟机用安全组，应用端口只对负载均衡开放。编排那一节写的是同一条边界。头和网络两道都留。

有登录态按用户限流，没有登录态按 IP。只按 IP 会误伤出口地址相同的一群人，例如同一个校园网。固定窗口有边界突刺，入口用令牌桶或滑动窗口，计数放在 Redis。进程内的计数只代表这一副本或这一个 worker。

Spring Cloud Gateway 跑在 WebFlux 上。过滤器里用阻塞的 `RestTemplate` 会占住事件循环，查会话和下游用 WebClient 和响应式的 Redis 客户端。APISIX 基于 Nginx 和 etcd，插件做鉴权、限流和日志。多语言的集群用一个与语言无关的网关，避免每种语言各写一个门户。

国内主流按技术栈分。Java 微服务项目里最常见的自建网关是 Spring Cloud Gateway。Zuul 1 只剩旧系统。多语言、要性能、要插件的新项目，国内开源里最常见的是 APISIX。Kong 有部署，新项目的声量小于 APISIX。简单转发仍然到处是 Nginx。不想自己运维控制面时，用阿里云 MSE 或云 API 网关。登录在管理端常用 Redis 会话加 Spring Security 或 Sa-Token，App 常用 JWT。

### 当前最优解

多语言的集群用一个与语言无关的网关，APISIX 或 Kong，放在 Ingress 后面，至少两副本。它做 TLS、路由、鉴权、按用户的 Redis 限流、请求 id 和访问日志。纯 Java 且整条链路都在 Spring Cloud 里时，可以用 Spring Cloud Gateway，过滤器保持非阻塞。已经有 Go 和 Python 的服务时，入口收成 APISIX 这一套，避免每种语言各写一个门户。

浏览器会话留在 Redis。App 和开放接口用短时访问令牌，非对称签名，网关只放公钥。业务服务信任网关写入的用户 id，再做资源属主和幂等。业务端口只从网关命名空间进来，头校验和网络放行两道都留。内部调用走 Service，不绕回网关。

这一步结束时，外部只有一个入口。借书接口里如果同步调用通知服务，通知一停，借书仍会失败。

## 08 消息队列

服务了几百所学校之后，一次借书不再只是改一行记录。学生在小程序上点借书。借阅服务先调用用户服务，确认没欠费、还能再借，再在主库事务里扣库存、写下借阅记录。到这一步，借书本身已经办完。后面还有微信通知、借阅统计、推荐更新。这些事可以晚几秒。把它们留在同一次请求里，通知服务一停，借书接口就报错。

在借书进程里当场起一个异步任务，能让用户不必等通知发完。这样仍有三个缺口：

1. 任务留在容器自己的内存里。进程一重启，这批通知和统计当场丢失。
2. 开学瞬间如果为每个请求拉起不受限的并发，下游的通知和统计会被打垮。高峰是尖刺，下游的容量是平稳的。
3. 以后再加积分或打卡，借阅服务还得改一次，把新的调用加进主链路。

消息队列放在业务容器外面，模型是生产者和消费者。借阅服务是生产者，往队列里写一条借书成功的事件，写入被确认就可以返回。通知、统计、推荐各自订阅这一类事件，按自己的速度处理。队列把一瞬间的高峰先接住，消费端一批一批拉。原本的尖刺被拉平，这是削峰。

容器重启不影响已经写入队列的消息。消费端停了，消息还在，恢复之后接着处理。再加积分，或者数据团队要拿记录做分析，就新加一个订阅。借阅服务不再为每个下游改代码。这是解耦：生产者不知道后面有几个消费者。

队列自己也要多副本。Kafka 和 RocketMQ 把一条已确认的消息复制到多台机器上。坏掉一台，已经确认的消息还在。队列整体停了，这条异步链路停，所以队列的可用性要单独做，不能当成永远可用的内存。

### 至少一次，消费端幂等

跨服务很难把“恰好送到一次”当成默认。业务写在自己的数据库里，消息确认发生在队列上，这是两次写入。进程可以停在两次写入之间。默认按至少一次：超时就再送，消费者处理完却没确认，消息也会再来。宁可再送一遍，也不漏掉。同一条借书成功或抢座成功的提醒可能到两次。

幂等是指同一操作执行一次和执行多次，系统状态相同。消费端用借阅记录的主键做唯一键。处理时先插入这把键，再写通知记录，放在同一个本地事务里。键已经在，就读出上一次的结果，不再发第二遍。只在 Redis 里用一个会过期的键挡住重复，键过期之后，再来的消息会再发一遍。持久的去重放在数据库。

生产者这边也有一个窗口：借阅事务已经提交，进程在把消息写出之前停了。消息队列在容器外面也接不住这条还没写出的消息。发件箱把事件和借阅记录写在同一个数据库事务里。提交之后，另一个循环把未发送的行推到队列，得到确认再标成已发送。进程在推送前停了，重启会再推，所以消费者仍按主键幂等。

积压时先分清是消费变慢还是生产变快。消费变慢就加消费者，或者先停掉非关键的订阅，把容量留给通知。某一条消息的正文让处理逻辑永远失败，失败次数到顶后进入死信，死信要有告警，由人看或由补偿任务处理。同一笔借阅的“借出、续借、归还”用同一个业务键，让它们进同一个分区，这个分区上的顺序才有意义。

### Go、Python、Java

队列在业务进程外面，三种语言差在客户端怎么确认、发件箱怎么扫、以及哪些“看起来异步”的 API 其实还活在本进程里。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 还留在进程里的异步 | `go` 启动的函数随进程退出消失。`context.WithoutCancel` 只能躲开请求取消，躲不开进程退出。必须完成的通知不放这里 | `BackgroundTasks` 在响应发出后仍于这个进程执行。进程先停，任务就没了 | `@Async` 提交到另一个执行器，同样随进程退出消失。默认执行器要有界 |
| 本系统的任务 | 用数据库任务表，多个实例用 `FOR UPDATE SKIP LOCKED` 把行分走 | Celery 或 RQ 跑本系统稍后执行的任务。跨服务的借书事件不走它 | 本系统任务用数据库任务表或 Spring 调度加锁。跨服务事件不走 `@Scheduled` |
| Kafka 客户端 | `franz-go`。生产者等 `acks=all`。消费者处理完并提交数据库之后再交位点 | `aiokafka` 挂在异步循环上。同步的客户端放进异步路由会堵住 worker。也可用 `confluent-kafka`，调用放在线程里并设超时 | `spring-kafka`。监听器在业务事务提交成功之后再 ack。自动提交会在处理失败时把位点往前移 |
| RocketMQ 客户端 | 5.x 用 `rocketmq-clients/golang`，走 gRPC。4.x 的 Remoting 客户端不和这套混在同一个调用栈里 | `rocketmq-python-client` 5.x | RocketMQ 5 的 gRPC 客户端，或仍在 4.x 上的 `rocketmq-spring`。两套协议不混用 |
| 发件箱 | 借阅插入和 `outbox` 插入放进同一个 `Transaction`。后台循环按 `status, id` 取未发送的行 | 同一个 `session.begin()` 里写两张表。SQLAlchemy 用 `skip_locked` 让多个副本分行走 | 同一个 `@Transactional` 里写两张表。MyBatis 用 `FOR UPDATE SKIP LOCKED`。`afterCommit` 只负责唤醒发送循环，发送失败的行保持未发送 |

幂等表和业务写入放在消费者自己的同一个数据库事务里。先插入幂等键，唯一键冲突就读出上一次的结果。Redis 的 `SET NX` 会过期，过期之后重复消息会再执行一次，持久去重放在 MySQL。

确认的顺序是：数据库事务提交成功，再向队列确认。先确认再提交，进程停在中间，这条消息不会再来，库里也没有结果。Kafka 把位点提交放在这之后。RocketMQ 和 RabbitMQ 的 ack 也放在这之后。

分区键用借阅记录主键。通知、统计、推荐是三个消费组，各自有自己的位点，某一方积压不挡住另外两方。死信用独立的告警。消费者按 lag 扩容，用 KEDA，而不是按 CPU。

### 技术和必会点

这一层是进程外面的消息系统。模型是生产者和消费者。国内业务消息和日志管道用的是两种不同的队列。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| 业务消息 | 借书成功后通知、积分、延迟关单 | RocketMQ |
| 日志和回放 | 多消费组、按时间保留、数据团队重放 | Kafka |
| 传统任务队列 | 路由复杂、流量不大 | RabbitMQ |
| 进程内异步 | 只适合丢了也没关系的收尾 | goroutine、`BackgroundTasks`、`@Async`、Celery |
| 可靠投递 | 数据库事务和发消息对齐 | 发件箱、RocketMQ 事务消息 |
| 消费语义 | 重复投递时不产生第二笔副作用 | 幂等表、唯一索引、死信队列 |

#### 异步、削峰和解耦

异步是借书接口不必等微信发完。削峰是开学瞬间的尖刺先堆在队列里，通知服务按自己的速度拉，高峰是尖刺，下游的容量是平稳的。解耦是再加积分或打卡时，借阅服务不用改代码，新消费者自己订阅。生产者不知道后面有几个消费者。

在借书进程里当场起一个 goroutine、`BackgroundTasks` 或 `@Async`，用户可以不必等通知发完。任务仍活在这个进程的内存里。容器一重启，这批通知当场丢失。不受限地为每个请求拉起并发，还会把通知服务打垮。本系统稍后执行、丢了可以再扫的任务，用数据库任务表，多个实例用 `FOR UPDATE SKIP LOCKED` 把行分走。跨服务、必须留下的借书事件走队列。

队列自己也要多副本。Kafka 和 RocketMQ 把一条已确认的消息复制到多台机器上。坏掉一台，已经确认的消息还在。队列整体停了，这条异步链路停。队列的可用性要单独做。

#### 至少一次和确认顺序

业务写在自己的数据库里，消息确认发生在队列上，这是两次写入。进程可以停在两次写入之间。默认按至少一次：生产者超时会重发，消费者处理完却没确认，消息也会再来。宁可再送一遍，也不漏掉。同一条借书成功的提醒可能到两次。

恰好一次的范围很窄。Kafka 可以把「写出下游消息」和「提交消费位点」放进同一个事务，这覆盖的是消费再转发。消费者写自己的 MySQL 时，数据库事务和 Broker 的确认仍然是两步。跨库把「恰好一次」当成默认，会在进程停在中间时丢消息或者重复。

确认的顺序是：先提交自己的数据库事务，再向队列确认。先确认再提交，进程停在中间，这条消息不会再来，库里也没有通知记录。Kafka 把位点提交放在这之后，自动提交会在处理失败时把位点往前移。RocketMQ 超过不可见时间还没 ack，消息重新可见。RabbitMQ 的 ack 同样放在事务提交之后。

消费端用借阅记录的主键做唯一键。处理时先插入这把键，再写通知记录，放在同一个本地事务里。键已经在，就读出上一次的结果，不再发第二遍。同一个键配了不同的正文，返回冲突。只在 Redis 里用一个会过期的键挡住重复，键过期之后，再来的消息会再发一遍。持久的去重放在 MySQL。

#### 发件箱和事务消息

借阅事务已经提交，进程在把消息写出之前停了。队列在容器外面也接不住这条还没写出的消息。发件箱把借阅记录和待发送事件写在同一个本地事务里。提交之后，另一个循环按 `status, id` 取未发送的行，推到队列，得到确认再标成已发送。发送超时的行保持未发送。多个实例一起扫时，用 `FOR UPDATE SKIP LOCKED` 把行分走。进程在推送前停了，重启会再推，所以消费者仍按主键幂等。发件箱不依赖某一种队列的事务能力，换 Kafka 或 RocketMQ 时，借阅事务不用改。

对账按部署那一节的规则做，权威在已经提交的借阅行。这一层要对的是两对：发件箱里标成已发送的借阅 id，对消费者幂等表里的同一批 id；借阅行对通知记录。缺的通知按发件箱再投一次。幂等表里多出来的记录不反写一笔借阅。有通知、没有借阅行，告警，人来看。窗口按这条队列的正常消费延迟定，大约一分钟。窗口之内还在飞的消息不告警。

RocketMQ 事务消息是另一条路。先发一条消费者看不见的半消息，执行本地事务，再提交或回滚。进程在提交前停了，Broker 回查。回查做成无副作用的查询：本地事务表里有记录就提交，没有就回滚。回查可能发生多次。

#### 顺序、堆积和死信

同一笔借阅的借出、续借、归还用同一个业务键，才会进同一个队列或分区。顺序只在这一条里成立，分区之间没有顺序。这个分区上同时只跑一个处理流程。键太集中时，流量堆在一个分区上，加消费者也没用，因为一个分区同时只被组里的一个消费者读取。消费者数量超过分区数时，多出来的一直空闲。要提高并行度就先增加分区。分区数可以增加，减少会改掉键到分区的映射。

消费组再均衡发生在成员变化或分区数变化时。Range 和 RoundRobin 会让整组先停下来再重新分配。Cooperative Sticky 只收回要挪走的分区，其余分区继续消费。被收回的分区在交出去之前，这一任消费者要把已经拉下来的消息处理完并提交位点，否则下一任会把同一条再处理一遍。

RocketMQ 里一条消息被取走之后有一段不可见时间，同组的其他消费者在这段时间里看不到它。处理完要 ack。超过不可见时间还没 ack，消息重新可见。不可见时间要盖住本地的数据库事务。事务比这段时间长，提交之前另一个消费者会把同一条再取走。

堆积先分清是消费变慢还是生产变快。消费变慢就加消费者，或者先停掉非关键的订阅，把容量留给通知。Kafka 的 lag 是分区末端位点减去已提交位点。扩容之前先确认还有空闲分区。按 lag 扩用 KEDA，CPU 反映不出堆积。

某一条消息的正文让处理逻辑永远失败，失败次数到顶后进入死信。死信要有告警，由人看或由补偿任务处理。位点不要向前跳过失败的那条，否则这条借书成功的通知就静默丢了。

#### 三种队列的模型

RocketMQ 按主题和消费组。集群消费是同一组里一条消息给一个消费者，组内订阅必须一致。广播是组里每个消费者都收到。消息可以堆在磁盘上。刷盘和复制可以同步或异步，同步刷盘加同步复制才接近「响应返回时消息已经在多台机器上」。4.x 的延迟消息是固定的十几个档位，5.x 可以指定任意延迟。延迟关闭未签到的座位，档位对得上就用它，对不上就用数据库按时间扫描。4.x 的 Remoting 客户端和 5.x 的 gRPC 客户端不混在同一个调用栈里。

Kafka 是按分区追加的日志。消费后不立刻删，靠保留时间或大小清理，另一个消费组可以在保留范围内再读全量。副本通常三个。leader 负责这个分区的读写，follower 拉取复制。一条消息进入当前全部 ISR 才算已提交。`acks=all` 等的是当时的 ISR，不是主题上配置的全部副本。ISR 可以缩到只剩 leader，这时 `acks=all` 也只写了一份。主题把 `min.insync.replicas` 设成 2、副本因子设成 3，ISR 数量不够时写入失败。`unclean.leader.election.enable` 保持关闭，不让没有这份数据的副本接班，否则已确认的消息会被截掉。消费者只能读到高水位之前的消息，高水位是 leader 认为已经复制到全部 ISR 的位置。借书这种丢一条就要对账的主题用这组配置。埋点可以放松。

RabbitMQ 里生产者对交换机发，消费者对队列收。扇出复制到每一个绑定的队列，直连按完整的 routing key 匹配。消费确认后从队列移除。队列用仲裁队列，副本按 Raft 多数派确认。prefetch 是每个消费者一次拿多少条未确认的消息，设得太大，消息堆在一个慢进程里。

Redis 的列表和 Stream 受这台内存限制。Stream 有消费组和待确认列表，仍然不是跨服务、要落盘的事件总线。新的业务中台不把 Redis 当借书事件的队列。

国内主流里，交易、通知、积分、延迟关单用 RocketMQ。集群消费是同一组里一条消息给一个消费者，广播是组里每个消费者都收到。刷盘和复制可以同步或异步，同步刷盘加同步复制才接近「响应返回时消息已经在多台机器上」。失败会进重试，次数到了进死信。日志、埋点、大数据链路用 Kafka，重点是分区、消费组、位点、`acks` 和保留时间。RabbitMQ 在传统企业和流量不大的任务系统里仍然很多。新的业务中台不会把 Redis 当跨服务的事件总线。

### 当前最优解

通知、统计、推荐要各自订阅、各自积压，数据团队还要按保留时间回放时，用 Kafka。副本因子 3，`min.insync.replicas=2`，生产者 `acks=all`。消息键用借阅 id。

国内业务团队的默认队列是 RocketMQ。团队已经有 RocketMQ 的运维、延迟消息和消费排查习惯时，借书事件放 RocketMQ，不为此再单独建一套 Kafka。两种队列都用数据库发件箱把本地事务和投递对齐，消费者都用借阅主键做唯一键，确认都放在本地事务提交之后。发件箱已发送的借阅 id 对消费者幂等表，借阅行对通知记录，按主库对账。缺的再投。幂等表里多出来的不反写借阅。有通知、没有借阅行，告警。

延迟关闭未签到的座位，已经有 RocketMQ 时用它的延迟消息。没有这套集群时，用数据库按时间扫描。Redis Stream 和列表留在单机任务里。

这一步结束时，借书主链路只做必须当场完成的事。通知、统计、推荐晚几秒，并且可以各自失败、各自重试。

## 09 可观测性

组件多了之后，有学校反馈学生借书偶尔失败。一次请求穿过网关、借阅服务、用户服务、主库，再进消息队列，由通知服务消费。它可能慢在任何一跳，也可能慢在两次跳之间的排队。已经不能在一台机器上打断点。

留三份信号，回答三个不同的问题：

| 信号 | 回答的问题 | 图书馆里怎么用 |
| --- | --- | --- |
| 指标 | 现在整体是否健康 | 流量、耗时、错误率。灰度时看借书失败率和延迟。超过阈值就停止放量或回滚 |
| 日志 | 当时执行过什么、抛出了什么 | 扣减库存失败、微信推送异常、幂等键冲突。人能读的一条记录，带上请求编号 |
| 追踪 | 这一次请求死在哪一跳 | 从网关到借阅、用户服务、数据库，进队列再出来，每一跳的耗时串在同一个编号下 |

指标看的是聚合。它能说明借书错误率在升高，不能单独指出是哪一个学生的哪一次点击。日志能还原某一次执行，散落在几十台机器上时要对得上同一次请求。追踪给一次请求一个编号，常叫 Trace ID。网关在入口生成，微服务框架把它放进请求头往下透传。跨进消息队列时，编号写进消息；消费者取出来，接在同一条链上。拿着这个编号在追踪平台上查，能看到时间花在哪一跳、错误出自哪一个服务。

框架和系统会自动上报请求量、耗时和错误率。业务上的失败要人在关键点打日志：库存不足是业务结果，扣库存时数据库报错是故障，两条要分开。日志集中收集。留在容器本地盘上，容器一删就没了。

三份信号用同一个请求编号。灰度发布盯指标。学生投诉某一次借书失败时，用编号去对日志和追踪。没有这个编号，几十个服务的日志对不上同一次点击。

### Go、Python、Java

三份信号的字段对齐之后，语言只决定它们从哪个 API 里取出来。采集端看的是同一套名字：服务、路由模板、状态码、下游、trace_id。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 日志 | `slog` 的 JSONHandler 打到 stdout。请求 id 放在 `context` 里，用 `InfoContext` 取出。生产不用默认的文本格式 | `contextvars` 里的请求 id 由日志过滤器写入每一条。异常用 `logger.exception` 留栈。栈留在日志里，不进 HTTP 响应 | Logback 打 JSON 到 stdout。请求 id 和 trace id 放在 MDC，格式里留出来。异常栈同样只进日志 |
| 指标 | Prometheus 的 `client_golang`。Counter、Gauge、Histogram 三种就够。`/metrics` 绑在管理端口。一个进程一份计数，没有多 worker 各算各的问题 | `prometheus_client`。Gunicorn 多 worker 时要用它的多进程目录，否则拉取只能看见一个 worker。生成指标的过程是同步的，不要放在事件循环正中间长时间占着 | Micrometer 暴露 Prometheus。直方图按自己的延迟目标设桶，例如 50 毫秒、100 毫秒、300 毫秒、1 秒。标签用路由模板，不用带真实书号的路径 |
| 追踪 | OpenTelemetry SDK，`BatchSpanProcessor` 导出 OTLP。`otelhttp`、Gin、数据库和 Redis 的包装负责读写 `traceparent`。进程退出时 `Shutdown`，把还没导出的 span 刷出去 | OpenTelemetry SDK，FastAPI、httpx、SQLAlchemy、Redis 有对应的 instrumentation。导出同样走 OTLP | OpenTelemetry Java Agent 自动给 HTTP、JDBC 建 span，业务代码少改。已经在用 Micrometer Tracing 时，导出目标仍是 OTLP，不另建一套采样规则 |
| 饱和度该看的数 | goroutine 数、`database/sql` 的 `InUse` 和 `WaitDuration`、Redis 池占用、发件箱未发送行数 | 事件循环滞后、数据库池占用、发件箱堆积 | Hikari 活跃连接和等待、在途请求、发件箱堆积。堆使用率不拿来扩容，GC 之后 RSS 也不会立刻回到零 |

告警打在症状上：借书错误率、延迟分位、队列 lag、就绪探针失败。CPU 高本身不作为叫醒人的条件，它引起的延迟才是。每个告警写下一步先看哪张图、哪一个下游。

### 技术和必会点

这一层是日志、指标、追踪，以及把它们收走的采集系统。应用只负责把信号打出来，存储和查询在集群外面。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |

| 指标 | 看整体错误率和延迟 | Prometheus、Grafana、Micrometer、夜莺 |

| 采集 | 三种信号统一出口 | OpenTelemetry Collector、Filebeat、Promtail |
| 关联 | 把一次点击串起来 | W3C `traceparent`、MDC、`context` |
| 告警 | 错误率和延迟越线时叫醒人 | Alertmanager、云监控、Grafana |

#### 三份信号

指标是聚合，能说明借书错误率在升高、延迟的分位变了，指不出是哪个学生的哪一次点击。日志能还原某一次执行：扣减库存失败、微信推送异常、幂等键冲突。追踪给一次请求一棵树，能看出时间花在网关、借阅、用户服务、数据库还是队列。三份用同一个编号才能对上。灰度盯指标。学生投诉某一次失败时，用编号去对日志和追踪。

服务看 RED：速率、错误、耗时。机器和池子看 USE：使用率、饱和、错误。两边一起看，才能分清是自己慢还是下游慢。CPU 高但错误率和延迟正常时，先记下来，不把它当成这次故障的原因。

#### 指标类型和高基数

Counter 只增，用来计请求数和错误数。看速率用一段时间内的增量。进程重启后 Counter 从零开始，查询时用增量，不用原始值当「总共处理了多少」。Gauge 可升可降，用来看在途请求、连接池占用、发件箱未发送行数、队列 lag。Histogram 看延迟分布。桶按自己的目标设，例如 50 毫秒、100 毫秒、300 毫秒、1 秒。告警看分位，不看平均值。平均值会被大量很快的查询拉平，把那百分之一的慢借书藏住。

标签是有限集合：服务、路由模板、状态码、下游名字。用户 id、借阅 id、书号放进标签，每本新书或每个学生都会生出一个新的时间序列，把 Prometheus 打满。它们进日志和 span 的属性。路由记成 `/loans/{id}`。SQL 记语句模板，不记绑进去的学号和密码。`/metrics` 放在管理端口，由采集器拉取，不和业务端口一起对公网。

Python 用 Gunicorn 开多个 worker 时，每个 worker 有自己的计数，拉取要走多进程目录，否则只能看见一个 worker。Go 一个进程一份计数。

#### 追踪

一次请求是一棵树。span 是树上的一个节点：一次 HTTP、一次 SQL、一次 Redis、一次发消息。span 上有开始、结束、状态和几个属性。父 span 的标识放在 W3C 的 `traceparent` 里往下传，格式是 `版本-traceid-spanid-标志`。trace id 是 32 个十六进制字符，span id 是 16 个。标志的最低位表示这一跳是否采样。下游生成自己的 span id，父 id 填上游传来的 span id，trace id 保持不变。网关在入口生成。微服务框架读进来的头，给出去的调用再写上头。进消息队列时把整段头放进消息属性，消费者用它当父 span，通知处理就挂在同一次借书下面。

采样在入口按比例。错误和超过延迟目标的请求要能留下。头部采样在请求进来时就决定，实现简单，可能把一次慢请求丢了。尾部采样等整条追踪结束再决定，能保住错误，收集器要先把追踪攒住。入口先用按比例，再加上错误一定留下。进程退出时把还没导出的 span 刷出去，宽限时间要留这一步。

采集器分成接收、处理和导出。应用只对集群里的 Collector 发 OTLP。批量、重试和尾部采样放在 Collector 里。后面换成另一套存储，改的是 Collector 的导出，应用里的地址不动。

#### 日志

打成 JSON 到标准输出，一行一条，由节点上的采集器收走。留在容器本地盘，容器一删就没了。字段固定：时间、级别、服务名、请求 id、trace id、span id、路由模板、状态码、耗时、错误码。手机号、令牌和密码不进日志。栈留在日志里，不进给用户的响应。访问日志每个请求一条。业务日志打在状态变化和外部调用失败上。循环里逐条打，流量一上来会把采集管道打满。

库存不足是业务结果，扣库存时数据库报错才是故障。两条分开计数。灰度盯的是后者和延迟。把库存不足算进错误率，开学季每次放量都会被「错误率升高」挡住。

#### SLI 和错误预算

借书这一跳的 SLI，是一段时间内同时满足三件事的请求占比：不是 5xx，不是数据库报错，延迟落在这一跳的目标里。库存不足留在另一条计数里。30 天的 SLO 按 99.9% 记。错误预算是 1 减这个数，大约千分之一的请求可以失败。预算在月初就烧完，后面的普通发布停下来，先把错误率压回去。

灰度用的窗口是几分钟，和发布前的基线比，比这 30 天的数字更严。错误率比基线高出 1 个百分点，或者绝对值超过 1%，或者借书 p99 超过发布前的两倍，这一档就停止。分位从 Histogram 的桶里算。平均值会被大量很快的查询拉平。

#### 变慢时的定位顺序

先分清范围：全站一起变慢，还是一条路由、一所学校。时间和最近一次发布对齐。全站的 5xx 先看网关到 Pod 的连接失败和就绪探针，再看应用。

然后看饱和，而不是先重启。正在处理的请求数、goroutine 或事件循环、连接池正在用的连接和等待时间。池等待升高，请求堆在应用里，原因在池子后面的数据库、Redis 或下游。goroutine 升高、CPU 不高，多半是都堵在 IO 上。

再用这一条慢请求的 trace 看时间花在哪个 span。SQL 长，就去库上看锁等待和扫描行数，1213 是死锁，1205 是等锁超时。Redis 长，看慢日志和是不是一个大键。下游 HTTP 长，看对方的错误率和本进程的熔断有没有打开。队列 span 长，看的是发出去之前的等待还是消费者里的处理，lag 能把这两件事分开。

机器放在最后。CPU 被 limit 节流时，节流时间和延迟一起涨。退出原因是内存上限，和「GC 把 CPU 打满但进程还在」分开看。依赖都正常、只有新版本变慢，就回滚镜像。回滚解决不了数据库里已经变差的执行计划，那种要单独处理 SQL。

告警打在症状上：借书错误率、延迟分位、队列 lag、就绪探针失败。CPU 高本身不作为叫醒人的条件。每个告警写下一步先看哪张图、哪一个下游。就绪失败和存活重启分开告，前者是依赖，后者是进程自己。

国内现状分存量和新项目。Java 链路追踪最常见的是 Apache SkyWalking，用字节码探针，日志里打上它的 TraceId。指标自建是 Prometheus 加 Grafana，夜莺在国内运维团队里也很常见。日志自建大量仍是 Elasticsearch、Filebeat、Kibana。云上对应阿里云 ARMS、SLS，腾讯云 APM、CLS。Zipkin、Jaeger 有存量。新项目把探针收成 OpenTelemetry，导出到 Collector，后面接 Prometheus、日志系统和追踪系统，避免每种语言各接一套后端地址。

### 当前最优解

三种语言都把日志打成 JSON 到 stdout，由节点上的采集器收走。指标用 Prometheus 的格式，追踪用 W3C `traceparent`。进程里的 SDK 把 OTLP 发给集群里的 OpenTelemetry Collector，再由 Collector 分给指标、日志和追踪的存储。应用不直接写死某一种后端的地址。

Java 用 OpenTelemetry Java Agent 覆盖框架和 JDBC。Go 和 Python 用各自 SDK 的 instrumentation。库存不足记成业务结果，不进借书的 SLI。30 天 SLO 按 99.9%。灰度的 5 分钟窗口相对基线，比月度数字更严，分位从 Histogram 算。

这一步结束时，故障能定位到某一跳。超时、重试、熔断这些规则如果写在 Java、Go、Python 各自的框架里，改一条规则就要每种语言发一版。

## 10 服务网格

服务数量还有限、语言也集中时，微服务框架里的服务发现、负载均衡、重试、熔断和指标就管得过来。平台再往后，Java、Go、Python、C++ 会混在一起。同一套通信治理散落在每种语言的框架里。框架里修一个安全漏洞，或者把超时从 300 毫秒改成 200 毫秒，每种语言都要发一版。业务代码并没有改。

服务网格把通信治理从业务进程里拆出去。每个业务容器旁边配一个独立的代理容器，紧贴着业务容器，叫边车。业务进程只和本机的这个代理说话。所有进出的网络流量先经过代理转发。代理负责找地址、负载均衡、超时、重试、熔断、链路加密和指标。成千上万个业务容器各自挂上代理，这些代理彼此连成一张网，这是 Mesh 这个名字所指的那张网。

这张网分成两面：

- 数据面是紧贴业务容器、经手每次真实请求的那些代理。转发、重试、采集这一次调用的指标，都在这里发生。
- 控制面不碰具体请求。它保存超时、限流和代理策略，并把规则推给全集群的边车。改一条超时，改的是控制面的配置，边车收到后执行。业务镜像不用为此重新构建。

和编程语言绑在一起的事留在业务进程里：从接口描述生成代码、把语言里的对象序列化成字节。网格接管的是机房内部、服务之间的通信调度和容错。外部请求仍从网关进。网关是南北向的入口，网格是东西向的服务之间。

代价是每一次调用多两跳：先经过自己的边车，再经过对方的边车。延迟、全集群的 CPU 和内存都会上升。边车里的重试和业务代码里的重试叠在一起，总次数是相乘的。网格接管重试之后，重试只留在这一处。应用仍要设置自己的超时，并保证被重试的操作是幂等的。代理不知道这一次借书能不能安全地发第二次。

### Go、Python、Java

网格把流量从业务进程旁边接走之后，三种语言里和网络有关的那一层要让出重试，和语言绑在一起的那一层留着。

| | Go | Python | Java |
| --- | --- | --- | --- |
| 留在进程里 | protobuf 生成的类型、`context` 里的截止时间、幂等键、业务错误码。gRPC 通道仍由进程建立，边车在外面把连接转走 | Pydantic 或 protobuf、`httpx` 的调用、幂等键。截止时间仍由应用设置，边车不知道这一次借书能不能发第二次 | Dubbo 或 gRPC 的存根、`@Transactional`、幂等键。Feign 的重试保持 `NEVER_RETRY`，避免和边车的重试相乘 |
| 交给边车 | 服务发现、按请求的负载均衡、mTLS、部分重试、网格侧的指标 | 同样这一组。应用里的重试关掉 | 同样这一组。Sentinel 如果还在进程里统计熔断，就和边车的熔断分成了两套数，只留一处 |
| 仍会踩的坑 | HTTP/2 的一条连接上有很多 RPC。边车要按 RPC 转发，四层把整条连接钉死时，扩容用不上 | 同步客户端堵住事件循环这件事，边车看不出来，进程还是会停 | WebFlux 网关里的阻塞调用，边车也看不出来。南北向仍走上一节的网关 |

经典边车是每个 Pod 一个 Envoy，出站进自己的边车，入站再进对方的边车。Istio 这一类实现里，控制面把超时、重试和认证策略推下去。改策略是改控制面的配置，业务镜像不用重建。

### 技术和必会点

这一层把通信治理从业务进程搬到旁边的代理。国内大多数业务团队还停在框架和网关，网格是语言已经混开、策略要统一下发之后才考虑的。

| 技术 | 在这一步做什么 | 常见产品 |
| --- | --- | --- |
| 数据面 | 经手每次真实请求 | Envoy、Istio 的 ztunnel、蚂蚁 MOSN |
| 控制面 | 下发超时、重试、认证，不碰具体请求 | Istiod |
| 边车 | 每个业务容器旁边一个代理 | Istio sidecar、Linkerd |
| 无边车网格 | 节点上做加密，少数服务再做七层 | Istio ambient、waypoint |
| 仍留在进程里的部分 | 序列化、截止时间、幂等 | protobuf、gRPC、Dubbo、Sentinel |

#### 治理放在代理里

超时、重试、熔断、服务间的双向 TLS 若写在 Java、Go、Python 各自的框架里，改一个超时或修一个代理漏洞，每种语言都要发一版。业务代码并没有改。网格把通信治理从业务镜像里拆出去。和语言绑在一起的事留在进程里：从 protobuf 生成代码、把对象序列化成字节、这次调用的截止时间、幂等键、业务错误码。代理不知道这一次借书能不能安全地发第二次。

几十个服务、语言还没混开时，框架里的保护就够。网格是语言已经混杂，而且策略要统一下发、不能跟着每种语言发版时才上。

#### 数据面和控制面

数据面是经手每次真实请求的代理。找地址、负载均衡、转发、重试、采集这一次调用的指标，都在这里发生。控制面不碰具体请求。它保存超时、重试和认证策略，并把规则推给全集群的代理。改一条超时，改的是控制面的配置，边车收到后执行，业务镜像不用重建。

经典边车是每个 Pod 一个 Envoy。Pod 的网络命名空间里把出站和入站的 TCP 重定向到本机代理端口。应用仍然拨服务名，它发出的包先到旁边的 Envoy，Envoy 再按控制面下发的集群和端点转出去。一次调用因此多两跳：出站先过自己的边车，入站再过对方的边车。延迟、全集群的 CPU 和内存都会上升。控制面用 xDS 把监听、路由、集群和端点推给每个代理。代理连不上控制面时，用上一份已经拿到的配置继续转发。HTTP/2 的一条连接上有很多 RPC。边车要按 RPC 转发。四层把整条连接钉死时，扩容仍然用不上。同步客户端堵住事件循环、WebFlux 里的阻塞调用，边车看不出来，进程还是会停。

#### 重试只留一处

边车里的重试和应用里的重试叠在一起，总次数是相乘的。网格接管重试之后，应用侧重试关掉。Feign 保持不重试，Go 和 Python 的客户端封装里也不再包一层。熔断同样只留一处。Sentinel 如果还在进程里统计，就和边车的熔断分成了两套数。应用仍要设置自己的截止时间，并保证被重试的操作是幂等的。查询可以重试。扣库存的写要带幂等键。

mTLS 由网格在服务之间做：每个工作负载一张证书，调用双方互相验。外部用户的登录仍在网关。网关是南北向，网格是东西向。两套都做重试和鉴权时，写清各自的范围。南北向的 TLS、用户鉴权和按用户的限流留在网关。东西向的服务身份、超时和重试留在网格。

#### ambient

每个业务容器都坐一个完整的 Envoy，资源开销和排障成本是大多数团队不上网格的原因。ambient 把原来边车里的事拆开。节点上的 ztunnel 做认证和加密，流量在节点这一层就完成双向 TLS，业务 Pod 里不必再放一个代理。需要按请求做七层策略的服务，例如按路径设超时和重试，再挂 waypoint。只需要加密的服务不必为七层策略付一个完整代理。应用侧的重试仍然关掉，截止时间和幂等键留在 Go、Python、Java 的代码里。

国内主流是不上服务网格。Java 的治理在 Dubbo、Sentinel 和 Spring Cloud Gateway 里，Go 的治理在 Kratos、go-zero、Kitex 里。中小团队把网格的资源开销和排障成本算进去之后，继续用框架。大厂有自研数据面，蚂蚁的 MOSN 是公开的代表。Istio 在云原生平台团队有落地，通常由平台团队维护，业务项目不把它当默认依赖。新做网格时，国内云厂商也提供托管的 Istio。重试只留在网格一处，超时和幂等仍在业务代码里。

### 当前最优解

几十个服务、Go 和 Java 的框架还能各自把超时和熔断维护住时，不上网格。保护留在第 06 节的进程里，入口留在 APISIX。

语言已经混杂，而且超时、mTLS、重试策略要统一下发、不能跟着每种语言发版时，再上网格。优先用 Istio 的 ambient：节点上的 ztunnel 做认证和加密，需要按请求做七层策略的服务再挂 waypoint。这样不必每个业务容器都坐一个完整的 Envoy。应用侧的重试关掉，截止时间和幂等键留在 Go、Python、Java 的代码里。

## 怎么把这条线讲完

每一层都是用当时承受得起的复杂度，换当时真正挡住业务的那件事。组件站在业务代码外面，对付的是四类麻烦：多人改同一份代码会互相覆盖，机器会宕，流量会突然上来，故障会沿调用链放大。

讲某一个组件时，先说它出现之前图书馆已经有什么，再说它接住的那一次故障。反向代理出现在实例变成多份之后，网关出现在服务变成多个之后。两者都是入口，管的范围不同。Redis 先做热点书目和共享会话。跨服务、要留下来的借书事件走消息队列，不走 Redis 的内存列表。注册中心和 Redis 都是旁边的基础设施，一个给地址，一个给数据副本和会话。

本地开发时，笔记本装不下后面几十个服务和中间件。能在本地跑的是当前这个服务，加上它直接依赖的数据库和缓存。其余依赖用测试替身，或者连一套共享的预发。上线走的是分支、评审和持续集成，产物是带提交编号的镜像。出了问题，先看借书错误率和延迟，再用请求编号对日志和追踪，回滚时把流量指回上一份镜像。

同一套规则可以收成几句：`main` 只留能运行的快照；各台机器跑同一份镜像；写走主库，读允许短暂延迟；会话放在所有实例都能读到的地方；跨服务的通知走队列，消费端按业务主键幂等；调用都有超时，只有幂等的操作才重试。Go、Python、Java 换的是客户端和运行时，这一句的顺序不变。

## 接到 Agent 岗时，这条线怎么用

图书借还仍按上面十层讲。Agent 面试另要一段自己做过的智能体：用户是谁、任务成功率或人工介入率、一次回滚、一次工具误写或检索串权怎么收住。下面只把已经讲过的机制对上那一段。

| 图书馆里已经有的 | Agent 里对上的 |
|---|---|
| 借书按业务主键幂等 | 写操作的幂等键，例如订单、动作和请求号 |
| 灰度，出问题把流量指回上一份镜像 | 提示词、模型、工具先过评测，再放量，保留一键回到上一版 |
| 请求编号串起日志和追踪 | 同一次任务的 trace。续跑读检查点，不把日志全文当恢复源 |
| 只有幂等的操作才重试 | 读可以重试。写先查执行凭证，不清楚就不要整段重放 |
| 网关收口鉴权和限流 | 模型网关管鉴权、选模型、计量和缓存。循环、工具和人审在运行时 |

口述先用三十秒讲图书馆里的一次故障，例如借书判断写反，灰度把流量指回去。再讲 Agent 里同构的一次事故，数字换成自己的。没有跟过的坏例，就停在这张对照上。
