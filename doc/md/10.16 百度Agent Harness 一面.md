# 10.16 百度Agent Harness 一面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 一面

### 1. 自我介绍

**答题思路**

一两分钟，按「你做哪一段 → 一个代码修复项目 → 和 Harness 岗位的关系」讲完。

1. 一句话说明你做的是模型改代码、以及怎样判断改对了的那一层。年限用你自己的，不补充职级和公司。
2. 只展开这一个修复项目：输入是报错日志、失败测试还是缺陷描述；你负责定位、补丁、验证里的哪一段；结果用你拿得出来的证据。没有指标就讲评测集或一类坏例。
3. 收到 Harness 岗位时，点出你关心循环外面的上下文、工具权限、沙箱和失败后如何恢复。停在这个项目上，让对方顺着往下问。

### 2. 怎么理解 Harness？

**参考答案**

Harness 是包住模型的运行时，把一次次生成收成可重复、可停止、可追查的任务。

一次循环是：组装上下文，调用模型；若返回工具调用就执行，并把观察写回，直到模型结束、步数或费用到顶，或外部检查判定完成。Harness 负责循环外面的部分：工具参数校验、超时、权限和沙箱；哪些历史、文件和日志进入窗口，过长时如何压缩；中断后从哪一步恢复；测试和 lint 这类由外部给出的停止条件；每一步留下的轨迹。

模型决定下一步。参数能不能执行、窗口里还剩什么、失败后能不能回到现场，都在 Harness 里。更强的模型补不上「从不跑测试」，也补不上压缩时把报错栈丢掉。

### 3. Agent 修复代码的效果是怎么评判的？修复正确的评判维度有哪些？

**参考答案**

修复正确，指原来失败的行为现在成功，相关的原有行为也还在。模型说已经修好，不能当作结论。

先固定一条修之前就失败的证据：失败测试、最小复现或稳定报错。补丁打在干净工作区之后，这条证据变为通过。再跑修复前已经通过的相关测试，确认没有回归。构建、类型检查和 lint 只能排除另一类错误。

补丁要单独看：测试和断言保持原样，没有为了变绿写死输出；改动限于和缺陷相关的代码。换一组等价输入仍然通过，避免只拟合看见的用例。

SWE-bench 这一类评测就是这个结构：目标测试从失败变为通过，回归测试保持通过。测试本身不稳定时，要把测试抖动和错误补丁分开计。

### 4. 项目里面除了修复 Agent 以外还有其他的 Agent 吗，这是一个多 Agent 架构的项目吗？

**答题思路**

先回答有还是没有。一个循环里调用多个工具，仍然是一个 Agent。

有多个角色，就按真实名单讲。每个角色只说输入、允许使用的工具、产出交给谁。定位、改代码、跑验证可以拆开，只有项目里真的拆开了才这样讲。

只有一个修复 Agent 时，说明任务是一条回路：下一步依赖上一步的报错原文，拆开以后栈和文件内容容易丢。角色的提示、权限或可以并行的子任务确实不同，再拆开。

最后说清谁对最终补丁负责。几个角色都会改代码时，说清冲突交给谁。

### 5. 各个 Agent 之间是怎么协作的，项目中是否支持用户自定义 Agent？

**答题思路**

按一次缺陷的路径讲协作。

1. 交接物：传给下一个角色的是结构化字段还是整段对话。字段里至少有目标、相关文件、已尝试的补丁、最新测试输出。
2. 控制权：固定流水线，还是一个主 Agent 按需要调用子 Agent。主 Agent 负责时，子 Agent 要用到的上下文写进任务本身。
3. 结束：子 Agent 返回补丁、结论还是工具轨迹。失败时重试、换角色，或交给人。
4. 自定义：支持就讲用户能改提示、工具白名单，还是能新增角色，以及权限和评测怎样跟着角色走。不支持就说明角色写在代码里，以及当时没有做成可配置的原因。

项目若是单 Agent，就说协作发生在工具调用之间，没有自定义 Agent 的入口。框架名字代替不了上面四步。

### 6. 项目上线的时候有没有出现什么修复失败的问题？

**答题思路**

承认有失败。只讲你见过的一类，按「现象 → 怎么发现 → Harness 改了哪一处」说，不补充次数。

常见类型可以用来对照，只选真实出现过的：

1. 目标测试变绿，但测试被改掉，或输出被写死。
2. 日志裁短之后，栈或第一条异常不在上下文里，模型修到了错误的一层。
3. 补丁和仓库当前内容对不上，应用失败仍被记成成功。
4. 同一类报错反复重试，中间没有新证据。

发现手段用你真实的那一个：评测集、上线后人工打回，或验证命令的退出码。改动落在门禁上，例如成功必须同时满足目标证据变绿、原有测试仍绿。还没处理的失败说成已知限制。

### 7. 有没有考虑过使用工程方式来解决这一类代码规范问题？

**参考答案**

代码规范是确定性规则，用工具执行。格式交给仓库已选定的格式化工具，例如 Python 的 Ruff 或 Black、前端的 Prettier、Go 的 gofmt。命名、未使用符号和危险写法交给 linter，规则放在仓库配置里。提交前用钩子跑格式化和 lint，合并前在 CI 再跑一次。工具能自动改的用它的 fix，剩下的报错退回。

存量代码可以用语法树做一次性改写，改完仍过同一套 lint 和测试。模型处理规范说不清、需要理解意图的部分。缩进、引号和导入顺序交给工具之后，修复 Agent 只需要遵守仓库里这套工具，手改格式会和工具打架。

当时若全部交给模型，就照实说，并补上要加的门禁：编辑之后跑格式化，格式化失败不能算修复成功。

### 8. Claude Code 里面是怎么解决这一类代码规范问题的，项目中有从中得到什么启发？

**参考答案**

Claude Code 把约定写进仓库说明，把能执行的检查做成钩子，模型再按周围代码修改。

`CLAUDE.md` 记录本仓库的命令和约定，会话会把它放进上下文。锁住格式的是钩子：`PostToolUse` 可以在 `Edit` 或 `Write` 成功之后，对刚改的文件跑 Prettier、Ruff、gofmt。`Stop` 钩子可以在它准备结束时跑 lint 或测试，失败就喂回去继续改。只写在提示里的风格，下一次生成仍会漂。

通过 Bash 改文件，不会命中只匹配 `Edit|Write` 的 `PostToolUse`。这种写入用 `FileChanged`，或在 `Stop` 时检查工作区。

讲启发时连到你的项目即可：规范从修复 Agent 里拿出去，编辑后跑仓库自己的格式化和 lint，失败不算完成。Claude Code 的配置不要说成你已经上线的功能。

### 9. 假如对系统进行扩展，使用多 Agent 并行来修复代码缺陷，多个 Agent 同时修改一个文件可能会产生冲突，这种情况该怎么办？Claude Code 中是怎么实现的，文件锁这些机制了解吗？

**参考答案**

多个 Agent 各自使用独立的 git worktree 和分支，避免共用一个工作区改同一个文件。任务按文件划分所有权，同一文件只有一个写者。必须一起改时，各自产出补丁，由单个写者按顺序应用；应用前核对基线内容，文件已经变化就重新读取再生成。语义上重叠的部分成为合并冲突，交给协调者或人。各分支先通过自己的测试，集成并解决冲突后再跑同一道门禁。

Claude Code 用 worktree 做这层隔离：`claude --worktree`，或子 Agent 设置 `isolation: worktree`。会话留在 worktree 里时，打到主工作区的 `Edit`、`Write` 会被拒绝，把 git 重定向回主工作区的命令也会被拒绝。`Edit` 按当前文件做精确替换，`old_string` 必须唯一匹配。它已经不在文件里时，这次编辑失败并要求重读，不会按过期内容覆盖。它仍能唯一匹配时，编辑会进行，并提示文件里还有其他改动。这里没有把源文件上的 `flock` 当作隔离手段。

`flock` 和 `fcntl` 记录锁都是建议性锁，只约束遵守协议的进程。`fcntl` 可以锁字节范围；同一进程里只要再关闭该文件的任意一个文件描述符，这个进程在该文件上的记录锁会全部释放。锁文件用独占创建，进程被杀死后文件还在，需要另做失效判断。模型的读取、生成、写回跨得很长，持锁会互相堵住，也区分不了同一文件里两处改动是否冲突。锁适合读完立刻写的短临界区，不适合作为并行修缺陷的主方案。

### 10. 你了解过 Claude Code 里面的沙箱机制吗？

**参考答案**

Claude Code 的这层沙箱包住 shell 命令，以及命令再启动的子进程。`Read`、`Edit`、`Write`、MCP 和钩子在沙箱外面，走单独的权限规则。

Linux 和 WSL2 用 bubblewrap 做隔离，并用 socat 把网络接到宿主机上的代理；macOS 用 Seatbelt。原生 Windows 上命令不受这层沙箱约束，要隔离就放到 WSL2 里跑。

写入默认给当前工作目录、一块按用户划分的临时目录，以及配置里额外允许的路径。读取默认能碰到机器上的大部分文件，包括常见的凭证文件，要用拒绝读取的规则收紧。网络没有直连出口。Linux 把命令放进独立的网络命名空间，连接经过宿主机代理，按域名允许列表过滤，列表初始为空。不读取代理环境变量的客户端，域名在列表里也连不出去。

文件边界和网络边界一起用。命令能读到密钥时，没有网络限制就可以把密钥送出去；只有网络限制时，命令仍可能改到沙箱外的文件。沙箱减少的是 shell 的逐次确认，路径允不允许改仍看权限配置。进程环境变量会进入命令，放在环境里的密钥要另外清掉。

### 11. 如果让你优化这个系统，你会从什么方面进行优化？

**参考答案**

先让结果可判定，再增加并行，然后收紧上下文。

并行的前提是写路径已经隔开：一个任务一个 worktree，同一文件不并发写。成功条件写成门禁：目标失败变为通过，原有测试仍然通过，格式化和 lint 由工具执行。模型结束会话不算成功。

上下文只留和缺陷相关的证据。日志按必须保留的字段压缩，并保留回到原文的指针。系统提示和工具定义保持稳定，便于前缀缓存；每轮变化的报错放在后面。

Shell 放进沙箱，改文件的路径使用允许列表。同一种失败没有新证据时停止重试，并把轨迹留下。比较时用同一批已修复和修失败的样本，分开看解决率、误报成功、回归、token 和步数。

### 12. 对日志的预处理、减少 token 这个操作是怎么做的，会不会有关键信息缺失，这是怎么解决的？

**参考答案**

压缩发生在送进模型之前，丢掉重复和无关体积，留下还能定位的因果链。

去掉 ANSI 颜色、明显的二进制和超长 Base64。重复行合并成一条并保留次数；合并前确认差异只在时间戳或重复计数上，载荷不同的行保持原样。紧挨异常的前几行即使是 INFO 也留下，那里常是出错前的状态。栈保留异常类型、消息，以及业务帧的文件、函数和行号。第一条异常和最外层异常都留着，过长的库帧可以收起。单行超长时保留键和报错字段，截断值。路径改成仓库相对路径。结果里放原始日志的位置或 trace id，证据不够时再按指针取一截。

信息会在三处丢掉：级联异常只留了最后一条，根因在第一条；去重把唯一不同的那一行也删了；trace id 和时间序被去掉之后，跨服务的日志拼不起来。

把必须保留的内容写成固定字段，用已经定位过的历史故障检查：压缩结果里还能否找到当时的异常类型、文件和行。找不到就放宽规则。检查通过只说明这些字段还在，验证阶段仍然要能回到原文。讲项目时按你真实的规则说，没做的检查不要说成已经上线。

### 13. 怎么保证多个模型输出的无缝衔接？

**参考答案**

衔接放在任务边界上，用同一份结构化状态，两个模型的生成文本直接拼在一起接不上。

上游结束时写出交接：目标、已确认的结论、相关文件和版本、已尝试的修改、最新测试或报错、下一步允许做的事。下游读取这份交接和仓库里的当前文件。字段用固定模式校验，缺了就退回上游，空缺留在那里，由下游补成事实会把错误写进代码。

两个模型的工具调用格式不同时，在 Harness 里转成同一套内部表示再执行。切换点选在一个步骤完成之后，函数或代码块写到一半时换模型续写，前后语法对不上。

下游修改前先核对交接里的版本和仓库是否一致，不一致就重新读取。不能改测试、必须复现的报错，写在交接字段里。换模型只换推理，任务状态仍是同一份。

### 14. 有没有做内部的 QA 模型，专门回答已有的一类问题？

**答题思路**

先回答有没有专门的模块处理已经见过的那一类问题。没有就讲当时重复问题怎么处理，再说最小的补法。不编模型名和准确率。

1. 先看这类问题是否封闭：同一错误码、同一栈，对应已知修复。封闭时用规则或检索历史工单。检索结果带上代码版本，代码已经改过的答案失效。
2. 如果做了模型：数据来自已确认的历史问题和结论。回答要能指回条目或当前代码，对不上就弃权，交给修复 Agent。评测用留出的历史问题，同时看命中和答错仍坚持的比例。
3. 分工：QA 只回答库里有证据的问题。库里没有的，进入修复流程，由 QA 编一条修复会绕过证据。人工改过的答案写回库，并带上版本。

### 15. 除了含错误信息的日志，有些错误在程序中没有打出日志，这一类问题有解决吗？

**答题思路**

有日志的缺陷和完全没有输出的缺陷分开讲。

1. 先找日志以外的失败信号：测试断言、进程退出码、stderr、崩溃转储、类型检查。测试框架抛出的断言，应用里可以一条业务日志都没有。
2. 仍然没有可复现信号时，完成条件缺少失败证据，就停下来要复现，或先补观测再修。让模型直接改代码，修完无法判断对错。
3. 项目里做过哪一种，就讲信号是测试、静态检查还是线上追踪，以及修完之后这个信号如何从失败变为成功。范围当时只覆盖「日志里有异常」的缺陷，就把无日志说成已知缺口。
4. 空的 `except`、被忽略的返回值，是代码里就没有日志的原因。可以用静态检查把它们找出来。这和给修复模型多喂日志是两件工作。

### 16. 如果让你优化这个项目，你会从什么方面进行优化？

**参考答案**

这一问接在日志、无日志错误和多模型后面，优化点放在证据链上。

日志压缩改成可核对的：保留异常类型、第一条和最外层栈、trace id，并用旧故障检查压缩结果还能否定位。没有日志的失败另开入口，用测试或退出码作为证据；没有证据就不进入「已修复」。

重复出现、库里已有结论的问题走检索或规则，条目上写版本。对不上当前代码就弃权。多模型之间使用交接字段，下游核对仓库版本再改代码。

门禁保持一条：目标证据变为成功，原有测试仍然成功，格式化由工具执行。修失败的样本分开看，是证据丢了、交接丢了，还是补丁本身错了。

### 17. 说说 Python 的装饰器、生成器、上下文管理器的应用场景。

**参考答案**

三者把不同的重复控制从业务函数里拿出来。

装饰器接收函数并返回函数。`@deco` 等于定义后执行 `fn = deco(fn)`：套上发生在定义时，额外逻辑在调用时。用来加日志、耗时、重试、权限和缓存。`functools.wraps` 保留原函数的名字和签名。多个装饰器从下往上套。

生成器函数含有 `yield`。调用它得到生成器，执行停在 `yield`，下次 `next` 从那里继续。用来逐行读大文件、分页拉接口，不用先做成完整列表。一条生成器只能向前消费一遍。

上下文管理器给 `with` 使用。`__enter__` 获取资源，离开 `with` 时无论是否异常都调用 `__exit__`。适合文件、锁、事务和临时目录。`@contextmanager` 把 `yield` 前面写成获取，把 `finally` 里写成释放。`__exit__` 返回真值会吞掉异常，释放资源时让异常继续抛出。

### 18. Python 生成器中使用了 yield，还想拿到其中的 return 信息，要怎么获取？

**参考答案**

生成器里的 `return 值` 由解释器变成交给消费者的 `StopIteration`，值在 `StopIteration.value` 上。`for` 会接住这个异常，值就被丢掉。给 `next` 传默认值也会接住异常，同样拿不到返回值。

调用方自己驱动生成器，在 `StopIteration` 里取：

```python
def gen():
    yield 1
    return "done"

g = gen()
try:
    while True:
        item = next(g)
except StopIteration as exc:
    result = exc.value  # "done"
```

另一个生成器使用 `yield from` 委托时，子生成器 `return` 的值就是 `yield from` 表达式的结果：

```python
def outer():
    result = yield from gen()
    # result == "done"
```

在生成器内部写 `raise StopIteration` 不可靠。从 Python 3.7 起，按 PEP 479，生成器内部冒出来的 `StopIteration` 会变成 `RuntimeError`。返回值用 `return` 写出，由解释器在生成器边界上抛出。

### 19. Python 的 asyncio 有了解吗，什么场景下适合用？

**参考答案**

`asyncio` 是单线程上的协作式并发，用来同时等待大量 I/O。协程执行到 `await` 一个真正的异步操作时，事件循环可以去跑其他协程，例如异步 HTTP、异步数据库驱动、异步子进程。适合同时发出很多请求、维持长连接，以及 Agent 里并行等待多个模型或工具的网络返回。程序入口一般是 `asyncio.run`。

CPU 密集计算、`time.sleep`、同步的 `requests` 和普通的阻塞式文件读写会占住这个线程，其他协程都停着。这类调用放到 `asyncio.to_thread`，或改成异步实现；纯计算放到进程里。协程在 `await` 处才会交错，先检查再更新如果中间有 `await`，共享的可变状态仍会互相覆盖。每个外部调用加上超时，取消要传到子任务，只取消外层会留下还在进行的请求。

### 20. 有三道代码题：看程序找出当前程序中存在的问题，然后进行修改。

**参考答案**

原帖只记录了有三道看程序找问题并修改的题，没有贴出程序，具体补丁无法还原。现场按这个顺序做，改完要能指出每一处原来的错误行为。

1. 先顺着调用走通正常路径，再看空输入、边界、异常和重复调用。题面给了输入输出，就以那个为准。
2. 优先检查：差一、可变默认参数、浅拷贝共享了内部列表、边界条件写反、空的 `except` 吃掉异常、异常路径上没有释放资源、协程没有 `await`。
3. 改动只动出错的那一处，保持原来的函数签名。用原来的例子，再加上能触发这个错误的例子，确认行为。
4. 先说错误行为，再说原因，最后给修改。同时改风格会把缺陷淹没。
