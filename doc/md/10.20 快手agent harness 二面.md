# 10.20 快手agent harness 二面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 二面

### 1. 自我介绍

**答题思路**

控制在一两分钟，把话题交到你真正做过的 Agent 运行时上。

1. 先说你实际负责的方向和年限，例如工具执行、任务状态或评测。职级和薪资不用报。
2. 只讲一个你能展开的项目：用户要完成什么，你负责的是编排、状态、工具还是评测。用真实项目的叫法，细节留到下一问。
3. 对齐这轮会追问的运行时：任务状态放在哪，中断后从哪一步继续，写操作怎样只生效一次。
4. 讲完停在这个项目上，等对方往下追。

### 2. 你们项目里 Agent 的任务状态存在哪，中断后怎么恢复

**答题思路**

按你真实系统里的存储和恢复过程讲。当时如果只放在内存里，就说明进程一停会丢掉什么，不要改口说成有持久化。

1. 先分开工作副本和可恢复状态。模型上下文和进程内存是工作副本。能恢复的是任务库里已经提交的那一版：任务状态、当前步骤、已提交的工具结果、下一步游标。聊天记录可以另存，恢复靠游标。
2. 把中断前已经写成功的边界说清楚。步骤至少分开未开始、执行中、已拿到结果、失败。工具已经返回、状态还没提交时崩溃，恢复要能分辨这一步可能已经执行。
3. 再讲接手过程。领取时带租约和版本，租约过期才允许另一个 worker 接手。已有结果的步骤跳过，从下一步执行。写操作沿用原来的幂等键，先向下游查询，再决定要不要重放。
4. 最后说你怎么确认恢复是对的：进程被杀掉或调用超时之后，同一次任务只有一份副作用，轨迹上能看出从哪一步接上。没有这组记录，就讲你当时凭什么日志判断，不编成功率。

### 3. 多 Agent 协作时，Planner、Executor、Verifier 各自负责什么

**参考答案**

三个角色看不同产物：Planner 产出计划，Executor 产出观察，Verifier 产出是否过关的判定。

Planner 把目标拆成带顺序和依赖的步骤。每步写明意图、允许的工具范围、输入来自哪一步、怎样算做完。它不调用有副作用的工具。计划作为数据落库，中断后可以沿步骤继续。

Executor 领取当前步骤，校验参数后执行工具，把脱敏后的结果、错误码和耗时写回该步。它不修改任务目标，也不宣布整个任务成功。写操作带幂等键。失败时标明可重试还是不可重试。

Verifier 对照完成标准和用户约束检查结果。能用规则或回读业务状态判断的，就不用模型的自述代替。判定只有三种：通过、带着原因重试、转人工。Verifier 只用只读工具，不和执行者共用写权限。

计划、执行、判定分成三次独立记录。执行者把输出标成成功时，判定仍然看业务状态。

### 4. 多 Agent 之间怎么通信，共享状态和私有状态怎么划分

**参考答案**

通信走显式交接。交接物是一条结构化消息，或任务表上的一行：目标、约束、上游步骤号、已提交事实的引用、截止时间。接收方只消费已经提交的版本。

共享状态只放必须对齐的内容：任务目标、全局约束、已确认的实体标识、每步终态、证据编号、剩余预算。写入带 `task_id`、`step_id`、角色和单调版本，过了 schema 才对其他 Agent 可见。

私有状态留在各自运行里：候选计划、被否决的参数、检索到但未引用的片段、局部重试计数。需要别人知道的，先收成一条事实再提交。推理草稿不进入共享区。

任务表或消息队列都可以送达，分区键用 `task_id`，同一任务的交接保持有序。队列负责送到，权威状态在任务库。未校验的输出不能成为另一个 Agent 的前提。

### 5. 多个 Agent 拿到不同时间的数据怎么办，怎么避免状态不一致

**参考答案**

一次协作绑定一个数据版本，后续读取都带这个版本。

任务开始时记下 as-of：业务版本号、知识库快照号，或两者都记。共享状态里的每条事实带来源、版本和观察时间。后到的旧版本直接丢弃。先后用数据库里的单调版本比较，不用各机器的本地时钟。

写操作带期望版本做条件更新。版本不匹配，说明前提已经变了：这一步失败，回到规划，作废依赖旧事实且尚未执行的步骤，再按新版本重读。已经成功的写步骤不重做。

价格、库存、是否在售以业务库为准。向量检索只返回候选标识，索引可以短暂落后于业务库。同一实体同时只有一个写者，其他 Agent 只读。

各自取当前最新时，后启动的 Agent 会读到尚未提交的中间结果，或读到任务开始之后才出现的新值，步骤之间的前提就对不上。

### 6. Agent 的 Trace 要记哪些字段，Replay 为什么冻结工具结果而不是重新调用

**参考答案**

Trace 要能还原当时模型看见了什么、决定了什么、工具实际返回了什么。一次运行一条 trace，每个步骤一个 span，用 `trace_id`、`span_id`、`parent_span_id` 串起来。

步骤上留下：`task_id`、会话、租户和用户标识、角色、步骤号、模型名、提示模板版本、工具名、schema 版本、脱敏后的参数、结果存放位置、结果哈希、状态码、耗时、token 用量，以及继续、重试、停止或转人工。成功和失败的工具结果都留下。密钥和完整证件号不进 trace。

Replay 复盘的是同一次决策，工具结果按当时的记录回放。检索索引、库存和时钟都会变，重新调用会得到另一份观察，无法区分是模型变了还是世界变了。写工具再调用一次还会产生第二次副作用。

要比较的是新策略面对同一串观察会不会换选择。重新驱动线上任务必须另开模式，并沿用原来的幂等键。只冻结果、不记 schema 和模板版本，回放仍然对不齐。

### 7. Agent 评测体系怎么搭，离线评测、线上观测、人工抽检分别看什么指标

**参考答案**

三层回答三个问题。离线看这一版有没有变差，线上看真实流量是否健康，人工看自动指标认为做完的事，人是否也认为做完了。

离线用版本固定的用例集和评分器。看任务有没有到达终态、工具是否选对、参数是否合法、轨迹里有没有空转和提前停止、有没有违反约束。费用和延迟按同一套预算一起记。线上失败样本回灌进用例集。

线上不以模型自评为准。看业务终态是否成立、工具错误率、超时率、重试率、人工接管率、单任务延迟和 token。安全拦截、写操作确认按工具和场景拆开，避免一个总成功率把检索失败和越权混在一起。

人工抽检按风险和低置信抽样，高风险写操作提高比例。评分表分开记事实是否正确、有没有证据、目标是否完成、有没有越权。双人标注看一致性，分歧样本进入离线集，用来校准自动评分器。

### 8. RAG 幻觉怎么降，召回质量、排序质量、最终答案质量怎么分别评测

**参考答案**

降幻觉靠证据约束。检索先做元数据过滤，再用关键词和向量混合召回，然后重排，只把靠前的少量片段送进上下文。没有过阈值或结果为空就拒答。数字、价格、规则必须能指回片段或工具结果。引用对不上原文就丢掉这句。否定词和数字不放进过度压缩的摘要。

三层分开评。召回看标注片段在不在前 k 个里，用 recall@k。证据没取回就是召回失败；最终答案碰巧正确，也不能算召回合格。

排序看相关片段是否靠前，用 MRR 或 nDCG@k。相关片段排在上下文窗口之外，生成时等于没召回。

最终答案看忠实度和完整性：每个论断是否被所引片段支持、该答的点是否答到、引用有没有张冠李戴。检索完整而答案仍然编造，记在这一层。答案正确但引用错，仍然是幻觉。

### 9. Spring AI 或 LangChain 里 Tool、Memory、Chain、Graph 分别解决什么问题

**参考答案**

四个名字对应四件不同的事。

Tool 是带 schema 的外部能力。模型只产出工具名和参数，框架校验后执行，再把观察送回去。Spring AI 里是 `ToolCallback` 或 `@Tool`，LangChain 里是 Tool。它把「模型想调用」和「系统真的执行」分开。

Memory 管跨轮内容。短期是窗口内的消息，长期是抽出来、可检索的少量事实。Spring AI 用 `ChatMemory` 和对应 Advisor，LangChain 用 memory 组件。它解决的是窗口装不下全部历史。订单和余额仍以业务库为准。

Chain 是代码里写死的管道：提示、检索、模型、解析按固定顺序执行。LangChain 里是 LCEL。Spring AI 用 `ChatClient` 加 Advisor，把记忆、检索和日志套在一次调用上。下一步由代码决定，适合路径已知的 RAG。

Graph 是带类型化状态的节点和条件边，允许循环。LangGraph 用它表达观察之后再选择，停止、分支和人工节点落在边上。Spring AI 核心没有与之对等的图运行时，循环要自己写，或使用带图的扩展。Advisor 的顺序是固定增强，不会由模型选择下一个节点。

### 10. MCP 和 Function Calling 是什么关系，生产级 MCP Server 要做哪些安全治理

**参考答案**

Function Calling 是模型能力：请求里带上工具 schema，模型返回结构化的工具名和参数。MCP 是宿主和工具服务器之间的协议：`tools/list` 发现工具，`tools/call` 执行，另外还有资源和提示。两者解决的环节不同。

生产里的接法是：MCP Server 提供目录和执行；宿主把 MCP 的 `inputSchema` 转成模型的 function schema；模型用 function calling 选出调用；宿主再发 `tools/call`，把结果作为工具观察送回。进程内工具可以只有 function calling，没有 MCP。

生产级 MCP Server 按外部入口治理。每个租户单独鉴权，列目录和执行时再做一次授权，不共用一把高权限凭据。参数按 schema 校验，并拦截路径穿越、命令注入和任意出网。只读与写入分开授权，不可逆动作在模型之外确认。

工具描述、资源和返回内容都按不可信数据处理，避免说明文字里的指令反过来指挥宿主。工具定义固定版本或哈希，避免上线后静默改描述。再加超时、入参大小、限流和审计，密钥不进返回值和日志。本地 stdio 服务继承启动用户的权限，不能把它当成可以任意执行 shell 的入口。

### 11. Skill 机制是什么，工具/技能很多时怎么路由，为什么要延迟加载

**参考答案**

Skill 是一套可复用的做法：何时使用、步骤、配套工具，以及用到时才读的参考材料。Tool 是其中一次可调用的操作。

技能多时分三层加载。第一层常驻名称和一两句描述，用来判断归哪个技能。第二层命中后再加载该技能的说明。第三层才暴露它声明的工具 schema；参考文件和脚本在真正用到时再读。规则能确定的意图直接选中，不确定的再用描述检索出少数候选。描述写不清，路由不会把正文加载出来。

延迟加载把 token 留给当前任务。几十份完整说明同时放进上下文，模型会跟错流程，也会在相近工具里选错。未选中的技能不进入上下文，内部步骤和参数也不会提前暴露。加载成功之后，执行前仍然做权限校验。

### 12. 线程池核心参数和任务提交流程，Agent 并发执行子任务时线程池怎么配

**参考答案**

`ThreadPoolExecutor` 的参数是核心线程数、最大线程数、空闲回收时间及单位、工作队列、线程工厂和拒绝策略。超过核心数的线程，空闲超过 `keepAliveTime` 后回收。任务超时不是构造参数。默认拒绝策略是 `AbortPolicy`，另外还有 `CallerRunsPolicy`、`DiscardPolicy`、`DiscardOldestPolicy`。

`execute` 在线程池处于运行状态时按这个顺序处理。工作线程数小于核心线程数，就新建核心线程直接执行。否则尝试入队。入队成功后如果线程池已经关闭，把任务移除并拒绝；如果这时一个工作线程都没有，再补一个线程消化队列。入队失败，才把线程数扩到最大线程数。仍然失败就拒绝。队列无界时，线程数不会超过核心线程数，最大线程数和饱和拒绝都不会生效。

Agent 子任务大多阻塞在模型和工具的网络调用上。池大小按下游承受得住的在途数来定。模型调用、读工具、写工具分池；也可以用虚拟线程承接阻塞，再用按依赖划分的信号量限制在途数。核心线程数等于最大线程数，加上较短的有界队列，就是一组固定舱壁。队列很长且核心数小于最大数时，要等队列塞满才扩容，尾延迟会先变坏。

彼此无关的只读子任务可以并行，有依赖的串行，写操作不并行。连接超时和读超时设在 HTTP 客户端上，等待方再设定截止时间并 `cancel(true)`。父任务不要在同一个有界池里等待子任务，否则工作线程会全部堵在等待上。队列满了用 `AbortPolicy`，把这一步记成过载，不要让模型无间隔重试。`CallerRunsPolicy` 会把任务退回提交线程；提交线程若属于这个池，退回的任务会和等待叠在一起。

### 13. 分布式令牌桶限流怎么实现，多实例下怎么保证不超放

**参考答案**

多实例共用一个桶，额度只在 Redis 主节点上扣。每个实例如果各自按全量速率补充，突发和平均速率都会乘上实例数。

桶有两个数：容量是突发上限，补充速率是平均速率。单次消耗不能大于容量。请求到达时先按经过的时间补充，再看余量够不够。补充和扣减放在同一段 Lua 里，时间用脚本内的 Redis `TIME`。客户端时钟向前跳，会把桶瞬间补满。

Redis 单线程执行这段脚本，实例之间不会交错。键只放余量和上次补充时间。拒绝时也写回补充后的余量和时间，同一次时间差不会被下次请求再加一遍。键的过期时间要长于从空补满所需的时间；过期后若直接重置为满，空闲一小段就会多出一次突发。

实例可以一次预扣一小段额度再在本地花。这段额度已经从全局桶里减掉，实例宕机只会少放。Redis 不可用时，要保证不超放就拒绝请求。扣减打在主节点，副本上的余量是旧的。

```lua
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2]) -- 每毫秒补充的令牌数
local cost = tonumber(ARGV[3])
local ttl = tonumber(ARGV[4])

local time = redis.call('TIME')
local now = tonumber(time[1]) * 1000 + math.floor(tonumber(time[2]) / 1000)
local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts = tonumber(data[2])
if tokens == nil then
  tokens = capacity
  ts = now
end
local elapsed = math.max(0, now - ts)
tokens = math.min(capacity, tokens + elapsed * rate)
local allowed = 0
if cost <= capacity and tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end
redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, ttl)
return allowed
```

### 14. 百万级商品知识库动态更新场景怎么设计，增量更新和向量库同步怎么做

**参考答案**

业务库是权威数据，向量库是由它派生的索引。商品编辑只提交业务事务和发件箱，向量化不占用编辑请求的线程。

发件箱按 `sku_id` 分区消费，同一商品的变更按版本顺序处理。事件带单调版本、上下架状态和用于召回的文本。消费端先做条件更新：索引版本小于事件版本才记下进度，更新成功才改向量。旧事件重试时条件失败，直接跳过。

一个商品可能分成多段。文本变化后，在同一个版本判断里先按 `sku_id` 删除旧点，再写入新点。下架写成可过滤状态或删点；查询同时过滤下架，避免删除延迟期间仍被召回。

价格、库存、是否在售不从向量正文里取。召回只返回候选 sku，回答前回业务库读这些字段。嵌入模型更换后，新旧向量不能放进同一个空间，全量写入新集合，核对完成后再切换别名。稳态走增量。对账任务比较业务版本和索引版本，补上漏掉的事件。

百万商品、每件若干段，点数在百万到千万，常见的近似最近邻索引放得下。难的是版本顺序、重新分段和模型升级。

### 15. 手撕算法：二叉树的层序遍历，并要求按层输出结果

**参考答案**

按层输出用广度优先。进入每一层时先记下队列长度，这个长度就是本层节点数。循环只弹出这么多个，子节点放进队尾，留到下一层。不先记下长度，新入队的子节点会和本层节点混在一起。

空树返回空列表。每个节点入队、出队一次，时间复杂度 O(n)。队列最多容纳最宽的一层，最宽可以到约 n/2，结果本身也要 O(n) 空间，所以空间复杂度 O(n)。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.Queue;

public final class LevelOrder {
    public static final class TreeNode {
        public final int val;
        public TreeNode left;
        public TreeNode right;

        public TreeNode(int val) {
            this.val = val;
        }
    }

    public static List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> result = new ArrayList<>();
        if (root == null) {
            return result;
        }
        Queue<TreeNode> queue = new ArrayDeque<>();
        queue.offer(root);
        while (!queue.isEmpty()) {
            int size = queue.size();
            List<Integer> level = new ArrayList<>(size);
            for (int i = 0; i < size; i++) {
                TreeNode node = queue.poll();
                level.add(node.val);
                if (node.left != null) {
                    queue.offer(node.left);
                }
                if (node.right != null) {
                    queue.offer(node.right);
                }
            }
            result.add(level);
        }
        return result;
    }
}
```

深度优先也可以按深度放进对应层，但要先处理根再处理子节点，同一层的顺序才和从左到右一致。题目要求按层输出时，广度优先直接对应层的边界。
