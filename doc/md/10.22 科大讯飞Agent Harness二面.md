# 10.22 科大讯飞Agent Harness二面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 二面

### 1. 自我介绍

**答题思路**

一两分钟，按「你在 Agent 运行时里负责哪一段 → 一个能讲透的闭环 → 和这个岗位的关系」收住。

1. 先说你实际做的部分：编排、工具执行、状态恢复、权限或评测。年限按真实情况说，不报职级。
2. 只留一个你能往下拆的系统：一次任务怎样被拆开、谁派发、写操作落在哪、失败后从哪一步继续。没有把握的调用量和成本数字不说。
3. 最后一句落到运行时：断点、幂等、工具权限或检索质量。讲完停，把多 Agent 拆分和线上故障留给后面的题。

### 2. 你们多 Agent 是怎么拆的：按角色、按业务、按工具权限，还是按任务粒度

**参考答案**

四条轴一起用，职责不同。任务粒度是执行单位，工具权限是硬边界，业务域负责路由，角色只描述节点在做什么。

每个子任务带上输入、输出结构、允许的工具和完成条件，做完把产物交回。上下文和失败限制在这一段里，编排层才能单独重试。读操作、发消息、扣费、改配置分属不同允许集，由服务端按调用方身份下发。普通用户路径和内部运营路径各自拿自己的允许集。

知识库和下游系统不同时，编排层先选定业务域，再进入该域的任务图。域之间用产物编号交接。规划、执行、反思共用状态和工具时，放在同一张图的不同节点上。上下文必须隔开、模型不同或权限不同时，才提升成独立 Agent。

拆得比任务边界更碎，交接会丢掉上下文，同一次写操作也可能落到两个执行者身上。先写清权限和完成条件，再决定要不要新的 Agent。

### 3. Supervisor / Orchestrator Agent 怎么派活，子 Agent 结果怎么汇合，失败子任务怎么处理

**参考答案**

Supervisor 负责把任务图派出去并验收，子 Agent 之间不直接传话。失败按子任务重试或跳过，已经成功的分支保留。

派活时写成结构化子任务：编号、依赖、输入产物编号、输出结构、工具允许集、步数和费用上限、完成条件。没有依赖的并行发出，有依赖的等上游产物。

汇合看输出有没有满足完成条件。结果写进按本次运行隔离的产物库，状态里留摘要和编号。事实以工具回执为准。同一业务对象只留一个写入者，两个子任务都要改它时，合成一个带版本条件的写动作。

超时和明确可重试的错误，在预算内用同一幂等键再派一次。参数错误、权限失败和业务拒绝标为失败，依赖它的下游改为跳过或改派。目标因此走不完，就停在当前检查点并转人工。

子 Agent 回复“已完成”而没有回执，验收不能通过。完成条件要能在状态里判定。

### 4. LangGraph 的 State、Node、Edge、Checkpointer 你们生产里怎么用，断点恢复具体怎么落

**参考答案**

State 保存这次运行，Node 是两次检查点之间的执行单元，Edge 决定下一步，Checkpointer 把每步提交后的状态落到进程外。

State 用类型化结构。消息列表按追加归约，当前步骤和游标按覆盖归约。大块结果放对象存储，状态里只留编号和摘要。模型调用、工具执行、路由各占一个节点；条件边按状态选择下一节点，需要并行时再派出多个节点。

生产检查点放在数据库，常见是 Postgres，`thread_id` 用任务编号。节点成功后写入通道值、版本和下一节点。用同一个 `thread_id` 恢复时，尚未落检查点的节点会重入。同一步里已经成功的并行节点记在 pending writes 里，恢复时直接沿用。

`interrupt` 恢复后，该节点从头再执行，调用前的代码会再跑一遍。写操作放在已提交的前一个节点，或按幂等键去重。检查点只表示图走到哪，短信和工单记在效果表里。

### 5. Agent 跑到第 7 步崩溃，前面已经发了短信、建了工单，怎么保证恢复时不重复发、不重复建

**参考答案**

用同一个任务编号恢复到最后一份检查点，已经提交的步骤不再调度。写操作另外按幂等键记账，挡住“下游已经成功、检查点还没写下”的那一段缝隙。

每个写步骤的幂等键在调用前生成，由任务、步骤、动作和规范化参数决定，重试不换新键。先把效果写成“已开始”，唯一约束挡住并发的第二次插入；再带着这把键调用短信或工单；拿到回执后写成“已提交”，然后才推进检查点。

恢复时先读效果表。状态已是“已提交”：跳过调用，把回执放回状态。状态是“已开始”：按这把键向下游查询，查到就补记提交，确认没有受理才用原键再调用。查询也拿不准，步骤标成不确定并转人工。

任务队列再投递整次运行时，仍然落到同一个 `thread_id` 和同一批幂等键。下游没有幂等能力、也没有按外部单号查询的接口时，这个写步骤停止自动重试，交给人工核对。

### 6. 工具调用幂等怎么做：创建订单、扣费、发消息这种有副作用操作和只读查询怎么分开

**参考答案**

工具按只读和有副作用两类注册，重试策略跟着类别走。副作用工具把幂等键交给下游，下游保存第一次的请求和响应。

只读工具在超时和短暂 5xx 时按预算退避重试。同一步里相同参数的成功结果可以复用。只读结果不进效果表。

创建订单、扣费、发消息在第一次尝试前就定下幂等键。下游用唯一约束保存“键 → 请求摘要 → 第一次的响应”。同一把键且请求一致，返回第一次的响应；同一把键但请求体变了，直接拒绝。订单用调用方单号做唯一索引，扣费超时先按键查单，消息用调用方消息号去重。

模型重试、队列重投和 HTTP 客户端重试共用这一把键。图层面“节点失败再跑一遍”对只读节点成立；写节点要靠这把键，重复进入才会拿到第一次的结果。

### 7. Tool 超时、返回空、返回部分成功、返回 500，这四种情况 Agent 分别怎么处理

**参考答案**

先判断结果是否已知，再决定重试、继续还是停。四种返回的已知程度不同。

超时表示结果未知。只读按预算退避重试。写操作先按幂等键查询：有回执就沿用，确认没受理才用原键再提交，仍然未知就停住并转人工。

返回空要拆开看。状态码成功、结构完整的空列表，表示“没有数据”，模型可以据此继续。响应体缺失或字段类型不对，算工具失败，这份空白不作为观察写进上下文。

部分成功按条目记账。每一条有自己的键和状态，成功的留下回执，只继续失败的条目。交给模型的是成功、失败和未知三组结果。条目没有全部有结论之前，这一步不算完成。

500 表示服务端返回了错误，写操作仍可能已经提交。只读和对方明确声明可重试的 500 按预算重试；写操作走和超时相同的查询。参数错误和权限错误停止重试。同一工具的 500 持续升高就熔断，这一轮不再继续打。

### 8. 你们怎么防止 Agent 死循环，最大步数、反思节点、人工介入、状态不变终止这些机制怎么组合

**参考答案**

每一步先看有没有新进展。没有进展就进入一次反思；反思仍拿不出新动作，就转人工或判失败。最大步数始终垫在下面。

进展看动作签名：工具名、规范化参数、观察结果的摘要。连续两步签名相同，或者在一个很短的动作环里打转，就判定状态没变。模型换了说法、调用不变，仍然算没有进展。

反思节点的输入是最近的动作和错误，输出限定为换一个具体动作、结束或转人工。反思自己只有一轮额度。

写操作结果不确定、反思要求升级、或继续执行会碰到费用上限时，图在检查点暂停，人的决定写回状态后再继续。

最大步数、最大模型回合和墙钟时间是硬上限，触顶记为失败，任务保持未完成。Supervisor 和子 Agent 的委托深度单独计数。

只放最大步数时，步数用尽之前同样的副作用可能已经发生多轮。动作签名能更早停下来。

### 9. Prompt Injection 怎么防：用户上传的文档、网页抓取内容、工具返回文本都可能投毒

**参考答案**

上传文档、网页和工具返回都按数据处理。工具权限和参数校验决定正文里的指令会不会变成真实调用。

不可信文本用固定边界包起来，并标明其中的命令无效。系统指令、工具名单和这段数据分通道进入模型。边界只能降低误跟从的概率，模型仍可能听正文。

读取不可信内容的执行者不携带发消息、扣费、导出和改配置的工具。一侧只把正文抽成结构化字段；持有工具的一侧只接受校验过的字段，不再看到原文。网页里的链接不自动继续抓，避免第二跳再投毒。

收件人、金额和地址取自用户本轮请求和会话身份。工具参数在进程内校验，高风险动作把结构化摘要交给用户确认。下游使用终端用户的受限凭证。检索结果同样不能写回系统提示或工具名单。

用户输入框只是其中一面。生产里更常见的注入来自工具返回和抓取到的网页。

### 10. 工具权限怎么做，普通用户、内部运营、管理员能调的 Tool 集合一样吗

**参考答案**

三套身份的工具集不同。允许集在服务端按已认证身份裁剪，模型只能看到下发的工具，执行器会拒绝允许集之外的调用。

普通用户保留自己的查询、自己的单据和低风险申请。内部运营可以做职责范围内的运营写操作，没有全局配置和跨租户工具。管理员的集合可以更大，破坏性动作单独审计，必要时二次确认。

工具允许和对象允许分两层。角色可以“查订单”，执行前仍用会话里的租户和用户核对这张订单的归属。身份只取网关已经认证的会话。

下游再校验一次凭证。Agent 服务若拿超级账号代调，提示词里的权限要求挡不住伪造参数。模型从文档里抄出一个管理工具名时，执行器因为本轮没有下发而拒绝。

### 11. RAG 答非所问，你怎么判断是召回错了、Rerank 排歪了、上下文截断了，还是模型没用检索结果

**参考答案**

顺着证据从后往前看：模型有没有用到已经送进提示的内容，这段内容有没有被截断，金标段落有没有在重排时掉出去，最后才看它有没有被召回。

正确段落已经在提示里，回答却和它矛盾或不引用它，就是模型没有使用检索结果。要求按引用作答，没有依据就明确说不知道，并看这段是不是落在上下文中部。

提示里的段落比检索日志短，或金标名次落在被截掉的尾部，就是截断，调整预算和送入顺序。金标还在重排前的候选里、重排后掉出送入模型的前几名，就是 Rerank 排歪了。对照前后名次，并核对送进重排的段落有没有被截短。

候选集里没有金标段落，才是召回问题：说法和原文差得远、切块把答案切开、过滤过严，或精确编号只在词法索引里。每次失败留下查询、重排前后的编号和分数、真正送进模型的文本。用已知正例归类后，再决定动召回、重排、预算还是生成约束。

### 12. Hybrid Search 里 BM25 和向量怎么融合，RRF 和 Cross-Encoder Rerank 你们用哪种，成本怎么样

**参考答案**

BM25 和向量各召回一列，再用 RRF 按名次合成；Cross-Encoder 只重排合成后的短名单。两段都做，成本大头在重排候选数。

BM25 覆盖精确词、编号和少见术语，向量覆盖换了说法的语义。两边原始分数尺度不同，直接加权要先按查询归一。RRF 只用名次，文档分数是各列表中 `1/(k+rank)` 之和，k 常用 60。这一步只做排序合并，得到一个短名单。

Cross-Encoder 把查询和段落放在一起打分，计算量随候选条数和段落长度增长。它跑在 RRF 的短名单上，再把最前面几条送进上下文。时延紧时按查询跳过重排，或换更小的重排模型。重排之后再混回 BM25 原始分，尺度又会漂。

### 13. Embedding 模型要换，五千万向量怎么迁移，不停机、不降召回、能回滚，说具体

**参考答案**

新模型写入新索引，旧索引继续接查询。评测过关后切换读别名；回滚把别名切回去，所以切换后一段时间旧索引仍接收新写入。

不同模型的向量不能互相换算。从原文按切块编号重新嵌入，旧向量只服务当前查询。离线回灌五千万条，按编号断点续跑。回灌期间的新增和修改双写两套索引，冲突按文档版本取舍，嵌入吞吐和在线查询分开限流。

切换前用同一批标注查询打两边，比较召回和尾延迟。新索引召回不低于旧索引，且索引构建已经完成，才切换读别名。切块规则和模型分开变更，评测才能分清是哪一项造成的。

出问题把别名切回旧索引。切换后的双写保留一段观察期，旧索引里才有这段增量。查询带上索引版本，新模型的查询向量只打新索引。

### 14. Kafka 在 Agent 系统里用来干什么，工具异步执行、任务排队、Trace 上报还是多 Agent 通信

**参考答案**

Kafka 负责任务排队、慢工具的异步完成和 Trace 投递。多 Agent 之间用它投递工作单，协作状态放在数据库和检查点里。这几类流量分成不同 topic。

长任务先写成待执行，再投到任务 topic，分区键用任务编号。消费端把任务标成执行中并写入任务表，然后提交位点；图的执行和这次提交分开，避免长任务触发再均衡。执行中崩溃靠租约过期重新领取。失败按次数上限重试，超过进入死信。

慢工具发到工具 topic 后，图在检查点暂停。结果 topic 按任务和步骤编号送回回执，再恢复图，回执按幂等键去重。Trace、token 和工具耗时走单独 topic，埋点堆积不堵住任务 topic。

多 Agent 用任务 topic 派子任务、用结果 topic 交回产物。中间状态和工具回执以存储为准。Kafka 位点是消息消费到哪，步骤游标是执行到哪，恢复时两份都要读。

### 15. Agent 单次任务成本突然涨 3 倍，你从 Token、工具调用次数、重试、Rerank、上下文膨胀哪几个点查

**参考答案**

先比一次变贵的任务和同类型正常任务的分步账单。token 没涨就查模型和缓存；token 涨了再拆是上下文变厚、步数变多、重试放大，还是重排变多。

每一步留下模型名、输入和输出 token、命中缓存的 token、工具名、第几次尝试、检索条数和重排条数，用同类型任务的中位数对照。

输入 token 随步数陡增，是上下文膨胀：工具原文逐步累加，检索片段没有裁剪，反思又把整段历史贴回去。步数变多时看动作签名，重复调用会同时抬高 token 和工具费用。

一次超时把整段图重跑，检索、重排和模型调用会一起乘上去。重排再看候选条数、是不是每步都在重排、模型有没有换档。token 总量接近而费用接近三倍时，核对是否路由到更贵的模型，以及前缀缓存命中有没有掉下去。

### 16. 说一个你们最难的 Agent 线上 bad case，根因、止血、长期修复分别是什么

**答题思路**

选你真正处理过、而且影响已经落到用户或写操作上的那一件。按「现象 → 根因 → 止血 → 长期修复」讲。不借别人的事故，也不编指标。

1. 现象用一次具体任务讲：用户期望的终态是什么，系统实际留下了什么。说清是重复副作用、错误调用、答非所问，还是任务停不住。
2. 根因讲一条因果链。触发点可以是检索、工具结果或重试；缺口是运行时缺的那一层，例如没有幂等键、失败被当成成功、权限只写在提示词里。停在“模型幻觉”上，对方会继续追问是哪一层没挡住。
3. 止血讲当时能做的开关：关掉该工具、收紧允许集、停止自动重试、把这类任务转人工。没有把握的恢复时长不说。
4. 长期修复对着根因：效果表或参数校验、一条回归样本、追踪里补上的字段、对应告警。说明修复之后下一次会走哪条不同的分支。
5. 你做的和同事做的分开。讲完停，对方追问时再展开那一层。
