## 二面

### 1. 自我介绍

**答题思路**

控制在一两分钟，按「方向 → 一个项目 → 和这个岗位的关系」讲完就停。

1. 第一句说明你做 Java 后端里哪一段：工具执行、会话状态，还是模型循环外面的运行时。年限用你自己的，不报职级和薪资。
2. 只展开一个你真正写完主干的项目：用户要完成的任务、你负责的链路、结果用你拿得出来的证据。没有数字就讲约束和坏例，不临时编调用量或项目名称。
3. 收到 Harness 岗位上：你准备展开的是调度、超时、鉴权、上下文，以及失败后怎么停。话停在这里，把追问留给项目。

### 2. 项目介绍

**答题思路**

按一次任务怎么跑完来讲，不要按框架名单讲。只使用你做过的系统。

1. 场景：谁在用、输入是什么、怎样算做完。范围停在你确实负责的那一段。
2. 主路径：谁组装上下文，模型返回工具调用后谁校验、执行、写回，什么条件结束。点出你写过的模块。
3. 准备三件你真实处理过的事：轮次怎么被上限拦住，工具超时后调用怎么停，删数据或发消息前谁确认。每件讲到代码和记录，不讲团队规模。
4. 观测收住：一次会话能串起模型输出、工具名、耗时、成功或失败。对方往下追时用这条记录展开。

### 3. 你理解的 AI Agent Harness 是什么，和单纯调大模型 API、固定 Workflow 有什么区别

**参考答案**

Agent Harness 是包在模型外面的运行时。它准备这一轮的上下文，接收模型给出的工具调用，执行后把结果写回，并用轮次、权限、超时和调用轨迹把整段任务卡住。

单纯调大模型 API，是一次请求对应一次生成。提示词怎么拼、要不要再请求、结果怎么落地，都在调用方自己的代码里。这种调用没有工具注册表，也没有跨轮会话状态。

固定 Workflow 的分支由人预先画好，模型通常只生成某一步的文本。步骤稳定时路径清楚，排查也直接。模型这一轮临时要多查一个数据源时，图上如果没有这条边，流程不会走出去。

Harness 把「下一步调哪个工具」交给模型，把「能不能调、最多跑多久、失败后停不停」留在 Java 代码里。面试里把你卡住的那几处讲具体，比报一个框架名字有用。

### 4. Agent 执行链路里，Java 后端负责哪一层（工具注册、调度、上下文、记忆、观测）

**参考答案**

这五层都在 Java。模型服务只负责在给定工具集里做选择，由调度层发起调用。

1. 工具注册：启动时把名称、说明、参数 Schema、超时、是否有副作用放进注册表。每次请求只下发这个用户、这个会话允许看见的子集。
2. 调度：解析工具调用，校验参数，提交执行，处理超时、取消和重试，再把统一结构的结果写回。业务 SQL 和外部接口留在具体工具里。
3. 上下文：按会话拼系统说明、目标和最近若干轮。接近窗口上限时先压缩更早的工具原文，并记下截断位置。
4. 记忆：进行中的对话留在会话里。跨会话只保存带来源、用户和时间的事实，检索时按当前问题取少数几条。
5. 观测：每次模型调用和工具调用带同一个 traceId、会话 id、耗时和状态。指标按工具名和状态聚合，会话 id 放日志和链路，避免标签基数被打爆。

### 5. Function Calling 在你项目里怎么落地：工具元数据、参数 Schema、分发器、结果回写怎么设计

**参考答案**

四段都由后端约束，模型只在已注册工具里做选择。

1. 工具元数据：名称用稳定的动词短语。描述写清适用情况和不适用情况，以及只读还是有副作用。权限、超时放在元数据字段里，供调度器读取。
2. 参数 Schema：类型、必填、枚举、范围写进 JSON Schema，并拒绝未声明字段。日期、金额、资源 id 使用明确格式。参数对象和数据库实体分开，避免模型多传的字段被直接写进表。
3. 分发器：工具名只在注册表里查找，不按模型给出的字符串反射任意类。先过 Schema，再进入对应执行器。未知工具把错误写回模型，不执行。
4. 结果回写：统一成是否成功、业务数据、错误码。用本次 `tool_call_id` 把结果挂回对应调用。结果很大时落对象存储，回写摘要和引用。

同一参数的读操作可以按幂等键复用结果。写操作没有幂等键时，失败后不自动再执行一遍。

### 6. Agent 多轮推理怎么防止死循环：最大轮次、重复调用检测、连续失败降级怎么实现

**参考答案**

三道限制都写在运行时里，每轮结束时更新，模型不能自己改这些计数。

1. 最大轮次：按任务类型配置模型回合上限和工具调用上限，另外加一个墙上时钟预算。到达任一上限就停止，返回已经拿到的依据，并把任务标成未完成。只数轮次不够，一轮超大的工具结果一样会把上下文撑满。
2. 重复调用检测：对工具名和规范化参数做哈希，保留本会话最近若干次。参数字段顺序不影响比较。已经成功过的相同调用直接把上次结果写回，不再执行。连续相同的失败达到阈值，就停止这一支。
3. 连续失败降级：同一工具连续超时或返回可重试错误时，先把它从本回合可用工具里拿掉，或换成只读的替代工具，并在上下文里写明原因。全部路径都失败，就结束回合并告警。

模型反复给出同一计划、又没有新的工具调用，也按停滞处理，避免空转把额度打满。

### 7. 大模型返回的工具调用 JSON 解析失败或参数非法，后端怎么兜底和重试

**参考答案**

解析失败和参数非法要分开处理。两种重试都计入第 6 题的轮次和时钟预算。

工具协议已经返回结构化的 `tool_calls` 时，直接读这个结构。模型只给了一段自由文本时，按约定的 JSON 解析一次。解析失败就把原始输出截断后记入日志，向模型回一条固定错误：请只返回已注册工具的调用。这种修正最多一到两次。仍然失败就结束本回合，把能够展示的文本答复交给用户，这期间不执行任何工具。

参数非法由 Schema 校验指出字段和原因，例如缺少订单号、枚举越界。错误作为这条工具调用的结果写回，让模型修改参数。资源 id、金额和删除范围不替模型填默认值。同一个字段错误连续出现，就停止再问模型要参数。

工具已经开始执行之后的失败，走业务重试或补偿，不再当作「重新解析 JSON」。

### 8. Agent 上下文和记忆怎么管理：短期上下文截断、长期记忆存储、并发会话隔离怎么做

**参考答案**

短期上下文是这一轮模型看得到的消息。长期记忆是跨会话检索出来的少量事实。两者分开存储。

截断按固定顺序做。保留系统说明和用户目标；先把更早的工具原文换成摘要和存储引用；仍超窗口，就把旧轮压成一条带序号水位的摘要，最近几轮保持原文。摘要调用失败时，退回为直接删掉最旧的消息。最后一条用户消息和最近一次工具错误留在窗口里，便于排错。被换掉的原文留在消息表里。

长期记忆只写确认过的偏好、实体和结论，并带用户、来源和时间。同一事实有新结论时，检索只取最新的一条，旧记录留作审计。每轮按当前问题取少数几条注入。写入放在回合提交之后异步做，避免挡住用户响应。

隔离以会话 id 为主键。进行中的状态和数据库追加都带会话 id；同一会话同时只跑一个回合，用版本号或会话锁拦住交错写入。记忆检索始终加上用户 id。

### 9. Spring 里工具执行器怎么注册和生命周期管理，AOP 怎么埋点统计每次 Agent 调用

**参考答案**

注册和统计都放在执行入口，工具 Bean 本身保持无状态。

每个工具是一个 `ToolCallback`，或是带 `@Tool` 的 Spring Bean，元数据包含名称、Schema、超时和是否有副作用。容器启动时收集进线程安全的注册表，同名直接让启动失败。流量进来之前注册表必须已经完整。下线某个工具用开关过滤新调用，已经在执行的调用允许跑完。

执行器使用单例，会话数据放在方法参数里，不放进 Bean 字段。连接和线程池在初始化时建好。下线时先停止接收新回合，等待在途调用到达上限，再关闭线程池。

埋点切在调度器调用执行器的入口，一次模型调用和一次工具执行各打一个切点。环绕通知记录 traceId、会话 id、工具名、耗时、状态和错误码，异常统计完继续抛出，由调度层决定重试。参数和结果脱敏后再进日志。指标标签只留工具名和状态。

Spring AOP 走的是代理，入口必须调用注入的 Bean。同一个类内部的自调用不会进入切面，所以统计不能只注解在内部私有方法上。

### 10. 线程池在 Agent 并发调用工具场景怎么设计：核心参数、异步编排、超时与拒绝策略

**参考答案**

模型调用、阻塞型工具和 CPU 型解析分成独立的池，避免慢工具把正在等模型的线程占满。

阻塞型工具使用有界队列、有限的最大线程和有名字的线程。最大在途数取「希望承接的并发」和「下游允许的在途」里更小的那个，再用压测调整。Java 21 及以上也可以把阻塞调用放在虚拟线程上，同时用信号量限制在途数。线程形态不改变下游容量。队列不设成无界。

同一轮模型返回的多个只读工具，用 `CompletableFuture` 并行，全部完成或到达这一轮的总超时后再请求下一次模型。有依赖的调用保持串行。写操作不和其他写操作并行。

超时分成三层：客户端读写超时短于 `Future` 的等待，`Future` 的等待短于整回合预算。超时后 `cancel(true)`，并让 HTTP 或 SQL 客户端真正中止请求。只设置中断标志时，堵在不可中断 IO 上的调用还会继续。

队列和线程都满时拒绝本次提交，记一条失败，把「系统忙」写回给模型。拒绝不在原调用线程里同步把任务跑掉，否则会堵住正在推进回合的线程。

### 11. Redis 在 Agent 系统里能承担什么角色：会话状态、限流、工具结果缓存、分布式锁

**参考答案**

四个角色可以同时存在，完整对话历史仍以 MySQL 为准。Redis 里放的是会过期、可以重建的状态。

1. 会话状态：进行中的回合、轮次和工具计数放在带会话 id 的键里，每轮结束刷新 TTL。进程重启或键过期后，按会话从数据库恢复。计数和状态用一段 Lua 一起更新。
2. 限流：按用户、工具和模型额度做计数。超限的新回合直接拒绝，不再请求模型。固定窗口在两个窗口交界处会放进大约两倍流量，要用滑动窗口或令牌桶。
3. 工具结果缓存：只缓存只读、参数可以规范化、允许短暂过期的结果。键包含工具名、参数哈希，以及用户或租户。写操作和订单一类个性化结果不进这个缓存。
4. 分布式锁：锁住「同一会话只有一个回合」或「同一个幂等键的写工具」。用 `SET key token NX PX` 加租约，释放时用 Lua 核对 token 再删除，避免删掉别人续上的锁。执行时间可能超过租约时要续期。锁负责互斥，数据库里的状态条件才是最终提交依据，业务侧仍然做幂等。

### 12. Kafka 或 RocketMQ 在 Agent 任务里怎么用：异步化、事件驱动、失败重试和削峰

**参考答案**

消息队列承接可以稍后完成的长任务。模型这一轮正在等待的工具结果仍走同步调用，避免回合被堆积的消息拖住。

异步化：请求先写任务表，状态为待执行，再发消息并返回任务 id。消费者执行工具或整段 Agent，进度写回同一行。发送和落库对不齐时，用事务消息或发件表，避免出现「库里有任务但没有消息」。

事件驱动：上传完成、工具完成、人工确认分开处理。分区键用会话 id，保证同一会话的事件按顺序被消费。Agent 在「可以进入下一步」的事件上被唤醒。

失败重试：消费方按任务状态做条件更新，重复投递不会把发送、扣款或删除执行两次。可重试的错误按有上限的退避重新投递，超过次数进入死信并告警。Kafka 由应用或死信主题完成重试；RocketMQ 可以使用其延时重试，再进入死信。两种中间件的状态机和幂等是同一套。

削峰：突发的批量任务先入队，消费者并发对齐下游额度。队列积压和消费延迟要告警，否则任务会一直排着而没有人发现。

### 13. MySQL 里 Agent 对话、任务、工具调用记录怎么建表，怎么设计索引和分区

**参考答案**

按会话顺序、任务状态和工具排查三条查询来建。超长工具结果放对象存储，表里留引用。

```sql
CREATE TABLE agent_session (
  id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  status VARCHAR(16) NOT NULL,
  msg_seq INT NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_time (user_id, created_at)
);

CREATE TABLE agent_message (
  id BIGINT PRIMARY KEY,
  session_id BIGINT NOT NULL,
  seq INT NOT NULL,
  role VARCHAR(16) NOT NULL,
  content TEXT NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_session_seq (session_id, seq)
);

CREATE TABLE agent_task (
  id BIGINT PRIMARY KEY,
  session_id BIGINT NOT NULL,
  status VARCHAR(16) NOT NULL,
  idempotency_key VARCHAR(64) NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_idem (idempotency_key),
  KEY idx_session_status (session_id, status)
);

CREATE TABLE agent_tool_call (
  id BIGINT NOT NULL,
  created_at DATETIME NOT NULL,
  session_id BIGINT NOT NULL,
  task_id BIGINT NULL,
  tool_name VARCHAR(64) NOT NULL,
  status VARCHAR(16) NOT NULL,
  args_json JSON NULL,
  result_ref VARCHAR(255) NULL,
  latency_ms INT NULL,
  PRIMARY KEY (id, created_at),
  KEY idx_session_time (session_id, created_at),
  KEY idx_tool_status_time (tool_name, status, created_at)
) PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p202611 VALUES LESS THAN ('2026-12-01'),
  PARTITION pmax VALUES LESS THAN (MAXVALUE)
);
```

消息序号在会话行上加锁递增，`(session_id, seq)` 唯一约束兜底。任务用 `WHERE id=? AND status=?` 做条件更新。调用记录按月做范围分区，便于丢掉过期明细；MySQL 要求主键和唯一键都包含分区列，所以主键是 `(id, created_at)`，id 本身仍用全局唯一号。分区表上不建外键。按会话查调用记录时带上时间范围，否则会逐个分区查索引。会话表和任务表在单表还能承受时先不分区。

### 14. 大文件喂给 Agent 时，上传、切片、解析、向量化链路怎么用 Java 工程化落地

**参考答案**

整条链路做成可续跑的状态机：已上传、解析中、已切块、向量化中、就绪、失败。每个阶段用文档 id 做幂等，崩溃后从当前阶段重新执行。在线对话和这条链路使用不同的线程池或消费者。

上传时文件分片直接进入对象存储，Java 只签发凭证并记录大小、类型和哈希。相同哈希的文件复用已有文档。服务端不把整个文件读进堆；解析器需要随机访问时落到临时文件，`finally` 里删除。

解析按格式走流式解析器。扫描件和表格走单独的解析器，某一块失败就标记这一块并继续其余块。一条坏文件把文档标成失败并提交消息位点，避免卡死整个分区。

切块按标题或段落进行，相邻块保留重叠，避免一句话刚好被切断。块记录文档 id 和序号。

向量化按嵌入服务的批量上限分批调用，失败从失败的块继续。向量带上文档 id、用户 id、嵌入模型名称和版本。更换嵌入模型时新建一份索引，建完再把检索切过去。检索时只查这个用户有权限的文档，并把命中的块和页码一起交给模型。

### 15. Agent 调用敏感工具（删数据、发消息、查订单）怎么鉴权、审计和回滚

**参考答案**

模型选中了工具，只说明它提出了调用。执行前由后端按当前登录用户重新鉴权。

鉴权同时检查功能权限和资源范围。参数里的订单号、用户号逐个核对是否属于这个用户，或属于他被授权的范围。服务端账号不能绕过这层范围。删除和发送不进入直接执行：工具先返回影响范围的摘要和一次性确认令牌，令牌短时有效，并绑住参数哈希。确认由用户在已登录的界面上完成，确认接口不放进模型的工具列表。

审计记录谁、何时、工具名、规范化参数、结果和 traceId。提案和真正执行各记一条，模型不能改这些记录。查订单同样审计，避免被用来批量套数据。

回滚只针对已经发生的写。删除优先用软删除，撤销时清除删除标记；物理删除前保留前镜像。发消息若通道支持撤回就撤回，不支持就把记录标成需要人工处理。查订单没有数据可回滚，防护在鉴权和审计。写工具带幂等键，超时或重复请求不会删第二次，也不会发第二次。

### 16. 手撕算法：实现一个简化版 Agent 工具调度器，支持注册工具、按名称执行、超时中断、失败重试和调用记录

**参考答案**

调度器只做五件事：同名拒绝的注册、按名称查找、在线程池里执行、超时后取消、按失败类型决定是否重试，并把每一次尝试记下来。

查找是哈希表的平均 O(1)。一次执行最多尝试 R 次，R 等于重试次数加一；每次最多等待该工具配置的超时，调度开销是 O(R)，墙钟时间由工具本身和超时决定。调用记录随尝试次数线性增长，下面用内存列表演示，生产环境应落到调用记录表并做脱敏和保留期限。

超时后要 `cancel(true)`，同时依赖客户端自己的读写超时，调用才会从不可中断的 IO 里返回。只读工具超时可以重试；有副作用又没有幂等键的工具，超时后把失败交回去，不在调度器里自动再执行。参数错误和未预期异常不重试。线程池拒绝时记一条失败并立即返回，不在原地空转。

```java
import java.time.Duration;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Future;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;

public class AgentToolScheduler {

    public record ToolResult(boolean success, boolean retryable, String payload) {}

    public interface Tool {
        String name();
        Duration timeout();
        int maxRetries();
        boolean retryOnTimeout();
        ToolResult invoke(String arguments) throws Exception;
    }

    public record CallRecord(
            String name, int attempt, String status, long costMs, String detail) {}

    private final ConcurrentMap<String, Tool> registry = new ConcurrentHashMap<>();
    private final ExecutorService workers;
    private final List<CallRecord> records =
            Collections.synchronizedList(new ArrayList<>());

    public AgentToolScheduler(ExecutorService workers) {
        this.workers = Objects.requireNonNull(workers, "workers");
    }

    public void register(Tool tool) {
        if (tool == null || tool.name() == null || tool.name().isBlank()) {
            throw new IllegalArgumentException("tool name required");
        }
        if (tool.timeout() == null || tool.timeout().toMillis() <= 0) {
            throw new IllegalArgumentException("timeout must be at least 1ms");
        }
        if (tool.maxRetries() < 0) {
            throw new IllegalArgumentException("maxRetries must be >= 0");
        }
        Tool previous = registry.putIfAbsent(tool.name(), tool);
        if (previous != null) {
            throw new IllegalStateException("duplicate tool: " + tool.name());
        }
    }

    public ToolResult execute(String name, String arguments) {
        Tool tool = registry.get(name);
        if (tool == null) {
            add(name, 1, "NOT_FOUND", 0, "unknown tool");
            return new ToolResult(false, false, "unknown tool");
        }
        int attempts = tool.maxRetries() + 1;
        ToolResult last = new ToolResult(false, false, "not run");
        for (int attempt = 1; attempt <= attempts; attempt++) {
            long start = System.nanoTime();
            Future<ToolResult> future;
            try {
                future = workers.submit(() -> tool.invoke(arguments));
            } catch (RejectedExecutionException ex) {
                add(name, attempt, "REJECTED", elapsed(start), "pool full");
                return new ToolResult(false, true, "pool full");
            }
            try {
                last = future.get(tool.timeout().toMillis(), TimeUnit.MILLISECONDS);
                long cost = elapsed(start);
                if (last == null) {
                    add(name, attempt, "EMPTY", cost, "null result");
                    return new ToolResult(false, false, "empty result");
                }
                if (last.success()) {
                    add(name, attempt, "OK", cost, null);
                    return last;
                }
                add(name, attempt, "FAIL", cost, last.payload());
                if (!last.retryable()) {
                    return last;
                }
            } catch (TimeoutException ex) {
                future.cancel(true);
                add(name, attempt, "TIMEOUT", elapsed(start), "timeout");
                last = new ToolResult(false, tool.retryOnTimeout(), "timeout");
                if (!tool.retryOnTimeout()) {
                    return last;
                }
            } catch (ExecutionException ex) {
                future.cancel(true);
                String message = rootMessage(ex);
                add(name, attempt, "ERROR", elapsed(start), message);
                return new ToolResult(false, false, message);
            } catch (InterruptedException ex) {
                future.cancel(true);
                Thread.currentThread().interrupt();
                add(name, attempt, "INTERRUPTED", elapsed(start), "interrupted");
                return new ToolResult(false, false, "interrupted");
            }
        }
        return last;
    }

    public List<CallRecord> records() {
        synchronized (records) {
            return List.copyOf(records);
        }
    }

    private void add(String name, int attempt, String status, long costMs, String detail) {
        records.add(new CallRecord(name, attempt, status, costMs, detail));
    }

    private static long elapsed(long startNanos) {
        return TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNanos);
    }

    private static String rootMessage(Throwable throwable) {
        Throwable current = throwable;
        while (current.getCause() != null) {
            current = current.getCause();
        }
        String message = current.getMessage();
        return message == null ? current.getClass().getSimpleName() : message;
    }
}
```
