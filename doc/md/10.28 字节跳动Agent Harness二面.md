# 10.28 字节跳动Agent Harness二面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 二面

### 1. 自我介绍

**答题思路**

一两分钟，按「你负责哪一段 → 一个闭环项目 → 和这个岗位的关系」讲完就停。

1. 先说你在 Agent 系统里实际负责的部分，例如编排、工具执行、状态恢复或评测。年限按真实情况说，不报职级。
2. 只留一个你能讲透的项目：用户要完成的动作、你负责的链路、你怎样确认这件事已经生效。没有把握的数字不说，改讲你用来判断对错的终态。
3. 最后一句落到运行时：长任务失败后从哪一步接着做，写操作怎样避免做两次。讲完停住，把深挖留给下一问。

### 2. 挑一个最难的项目讲：Agent 在你们业务里到底替用户完成了什么动作，不是调模型，是闭环

**答题思路**

选你真正负责过、而且链路里有写操作或长步骤的那一个。围绕用户的事有没有做完来讲，模型调用只是其中一步。

1. 用一句话定义闭环：什么事件进来，用户最终得到哪个已经生效的结果。这个结果要能在业务状态里查到，例如消息已发出、订单已变更、支付单已落定。
2. 按一次真实执行讲：拿到目标，用工具读现状，决定下一步，执行有副作用的动作，再读回来核对。核对不上就停住或转人工。
3. 难点放在闭环会断的地方：做到一半超时、同一任务被投递两次、工具已经成功但回复失败。说明状态放在哪里，恢复时从哪一步继续，已经成功的写操作不会再做一遍。
4. 你的职责和协作边界分开。指标只用你能复述口径的那些；没有就讲坏例怎样进入回归集。
5. 讲完停。对方追问幂等、轨迹或评测时再展开。

### 3. Agent 长任务用 Kafka 异步化，怎么保证任务状态、重试、断点恢复，不丢不重

**参考答案**

长任务只把 Kafka 当作可靠触发，执行状态放在数据库。消费线程接住任务就返回，避免占住分区直到整个 Agent 跑完。

不丢靠事务性发件箱：同一事务写入 `PENDING` 任务和待投递记录，再异步发到 Kafka，分区键用 `task_id`。消费者把任务条件更新为 `RUNNING` 并写上租约后，才手动提交位点。提交之前崩溃会重新投递；提交之后崩溃，靠租约过期被别的 worker 领取。

不重靠状态机和步骤幂等键。重复消息发现任务已终态就直接跳过；发现某一步已有结果，就从下一步继续。Kafka 的事务能力覆盖不了外部工具，外部副作用要靠幂等键。

断点是每一步成功后写下的游标：步骤号、工具结果位置、下一步。恢复时沿着游标往后执行。重试进延迟队列，带次数上限，超过就进死信并把任务标为失败。

容易漏的是 `max.poll.interval`：处理时间超过它会触发再均衡，同一条消息被另一个消费者拿走。数据库条件更新要挡住租约还没到期的 `RUNNING` 任务。

### 4. 工具有一百个，怎么路由：分层分类、语义检索、参数补槽、非法调用拦截

**参考答案**

一百个工具不要一次塞进上下文。路由分成四层，模型只在最后一层看到少量候选。

分层先按业务域和风险把工具归到目录里，用规则或一次轻量分类选定当前子目标所属的域，候选从一百降到一个域。语义检索只对这个域里的工具卡片做，卡片包含名称、做什么、什么时候不该用、关键参数。用当前子目标检索出 top-k，只把这 k 个 schema 交给模型。

参数补槽按 JSON Schema 检查必填项。上下文、实体记忆和上一步工具结果里能确定的值就填上；确定不了再问用户。标识符一类的参数对不上就停，留空调用会被拦截。

非法调用在进程内拒绝：工具名必须属于本轮下发的名单，参数必须过 schema，再过租户、权限、金额和对象校验。写工具和读工具分开授权。未下发的工具名、越权对象和超额金额都记为一次失败，不进入真实调用。

工具描述写得分不开时，检索会把相近工具一起送进模型，这是路由质量的主要来源。

### 5. 工具调用偶发 5xx/超时，为什么不能无脑重试三次；幂等键、重试预算、熔断、降级怎么设计

**参考答案**

5xx 和超时只说明结果不确定。超时发生时，下游可能已经完成写操作。固定重试三次会叠加超时、打满故障中的依赖，也会把同一次逻辑调用变成多次副作用。

幂等键在发起调用前生成，由任务、步骤、工具名和规范化参数组成，同一次逻辑调用的各次尝试共用这一把键。下游按键保存结果；超时后先按键查询，确认没有受理过再重新提交。查询本身也使用同一把键。

重试预算分三层：单次调用、单个任务、单个下游。只对连接失败、429、明确可重试的 503 做退避加抖动。参数错误、鉴权失败和业务拒绝直接结束。写操作的超时走查询，不直接重发。

熔断按下游统计错误率和慢调用，打开后快速失败，半开时放少量探测。降级要按工具语义分开：查询可以返回缓存或明确说暂时查不到；支付、改单和发消息失败就停在待确认或转人工，保留已查询到的下游状态。

### 6. Agent 有写操作（发消息、改单、调支付），怎么防止重试导致重复副作用

**参考答案**

写操作的去重放在业务侧，锁到期不能代替去重。每个写步骤先生成幂等键，再用唯一约束记下「键 → 受理结果」。重复请求返回第一次的结果。

执行顺序是：先把步骤写成 `INTENT`，再调用下游，最后把下游回执和步骤状态写成成功。崩溃后重试先读这张记录。没有记录才调用；有回执就跳过；只有意向、没有回执时，先按幂等键查询下游。

三类写操作的落点不同。发消息使用调用方生成的消息号，接收方按消息号去重。改单使用期望版本或期望状态的条件更新，目标状态已经成立就当作成功。支付以渠道的幂等窗口为准，超时后先查单，只有明确未受理才再次提交。

模型重试、队列重试和 HTTP 客户端重试共用同一把幂等键。用户确认也绑定这次动作的摘要，确认之后动作参数发生变化就重新确认。分布式锁只用来缩短并发窗口，锁释放之后仍然靠唯一约束挡住第二次提交。

### 7. 多 Agent 协作时，Supervisor 怎么分发子任务，中间结果放哪，冲突谁仲裁

**参考答案**

Supervisor 负责拆开、分发和验收，子 Agent 之间不直接互相对话。每个子任务写清输入引用、输出结构、允许使用的工具和完成条件。没有依赖的子任务并行；有依赖的子任务等待上游产物。

中间结果放在按 `run_id` 隔离的产物库里，正文进对象存储或表，上下文只放摘要和产物编号。大段日志、检索原文和工具响应通过引用传递。子 Agent 需要上游结果时，由 Supervisor 把对应摘要写进它的输入。

冲突由 Supervisor 裁决，规则事先写死。事实不一致时采用带来源和时间的工具结果，本轮观察优先于记忆。同一业务对象只保留一个写入者，两个子任务都要修改时，合并成一个带版本号的写动作。目标互相矛盾时，对照用户最初的目标取舍；仍然决定不了就转人工。

子任务有步数、深度和费用上限。验收看输出结构有没有满足完成条件，子 Agent 自报完成不算结束。

### 8. 记忆怎么存：短期上下文、长期用户画像、实体记忆，怎么避免历史污染当前决策

**参考答案**

三类记忆分开存，当前决策先看本轮工具结果。

短期上下文只保留这次任务的对话、步骤摘要和未完成目标。窗口放不下时，把更早的步骤收成摘要，摘要里留下实体编号、已经成功的写操作和还没完成的目标。

长期画像保存稳定偏好，由单独的抽取任务写入，并带置信度和证据。敏感偏好只在用户明确表达后写入。实体记忆保存订单、地址、账号这类结构化记录，带有效期和来源工具；编号类字段按精确值查找。

避免历史污染靠写入和读出两条边界。失败尝试、被用户否决的计划和工具里的指令性文字不写成事实。读记忆时按当前子目标检索少量条目，并过滤过期项。用户本轮的新指令覆盖旧画像在这一轮的作用，一句情绪化表达不会直接改写长期偏好。画像和本轮工具结果冲突时，以本轮工具结果为准。

### 9. RAG 在 Agent 里不是一次检索到底：选工具前、执行中、反思阶段分别检什么

**参考答案**

三个阶段查的材料不同，过滤条件也不同，避免用同一次宽检索走完全程。

选工具前查规程和工具适用条件：这类请求该用哪个工具、哪些工具被禁止、完成标准是什么。这时还没有可靠的实体细节，先不把业务单据全文召回进来。

执行中的查询已经带上实体编号、字段和错误码。这一阶段查接口约束、字段含义和错误处理说明，用来补参数、解释工具结果。工具结果很大时先抽取，发现缺口再做下一次更窄的检索。

反思阶段查验收条件和合规限制，对照本轮已经拿到的证据核对结论有没有超出依据、要不要转人工。反思使用的材料限定为政策、清单和本轮证据，不再换一个宽查询引入新的业务文档。

文档类型、版本和权限要能过滤。选工具看 `sop`，执行看 `api`，反思看 `policy`。检索漏了就明确缺证据，而不是用上一次的片段把结论补满。

### 10. 向量检索用 Milvus 还是 ES？亿级向量 + 高 QPS 怎么选，标量过滤怎么下推

**参考答案**

按主查询形态选。亿级向量、以近似最近邻为主并且 QPS 高，用 Milvus 这类向量引擎：按集合和分区拆开，用副本承住查询，索引按内存和磁盘取舍。过滤很重、关键词和向量要一起查、规模还没把专用引擎的运维成本赚回来时，用 Elasticsearch 做混合检索更合适。两边都要过滤时，也可以向量走 Milvus、关键词走 ES，应用层按相同主键合并。

标量过滤要发生在检索引擎内部。租户这类几乎每次都带的条件做成分区键，查询先裁掉无关分片。其余过滤字段建标量索引。选择率高时先按标量找出候选再在候选上检索；选择率低时在近邻搜索里持续扩大候选，直到凑够 k 条通过过滤的结果。应用层拿回 top-k 再过滤，会把命中数滤空，看起来像召回变差。

ES 里过滤条件写进 kNN 查询自身。放在返回后的 `post_filter` 也会把已经召回的结果滤掉，补不满 k。过滤字段的基数、选择率和 QPS 要用真实查询估，再决定分区和副本，不靠一个固定配置。

### 11. Redis 在 Agent 系统里承担什么：会话状态、限流、分布式锁、语义缓存，分别怎么用

**参考答案**

Redis 放短期、可丢失后能重建的数据。运行轨迹和业务结果仍然以数据库为准。

会话状态用 `session_id` 做键，保存当前步骤、已填槽位和滚动摘要，活动时续期。只留这一轮需要的状态，完整轨迹写到数据库；值要设大小上限。

限流按用户、工具和模型分键，用带衰减的令牌桶或滑动窗口。固定窗口计数在窗口边界会放进两倍流量。模型调用超限就拒绝或排队，避免故障时继续放大费用。

分布式锁用 `SET key token NX PX`，释放时用 Lua 比较 token 再删除，只保护很短的领取临界区。任务有没有被领走，以数据库条件更新为准。锁不替代支付和发消息的幂等记录，过期之后要允许别人接手，同时靠幂等键挡住重复执行。

语义缓存的键至少包含规范化问题、模型、提示词版本、工具版本、权限范围和知识版本。精确命中用哈希；近义命中要有向量索引，并用评测集标定相似度。写操作、个性化结果和已过期证据不进入可复用缓存。

### 12. MySQL 存 Agent 运行轨迹和业务结果，表怎么设计，trace_id 怎么贯穿全链路

**参考答案**

轨迹和业务结果分表，大文本不进主行。`agent_run` 记录一次运行：`run_id`、`trace_id`、`session_id`、`user_id`、状态、父子运行、起止时间、token 统计和失败类别。`agent_step` 记录有序步骤：步骤号、类型（模型、工具、检索、反思）、状态、耗时、幂等键、错误类别，以及输入输出在对象存储中的位置。幂等键加唯一约束。业务表保留自己的主模型，只增加 `trace_id`、`run_id` 和幂等键，订单和支付的状态不塞进轨迹表。

`trace_id` 在请求进入网关时生成，或沿用上游的 `traceparent`。它写入运行表、Kafka 消息头、日志和每个工具调用的请求头；子 Agent 使用同一个 trace 下的新 span。Langfuse 的 trace 使用同一个标识，排障时一次查询能对上日志、数据库和模型轨迹。

索引围绕 `trace_id`、`session_id` 加时间、`user_id` 加时间。提示词和工具原文按保留期清理，主表只留可检索的状态和引用。

### 13. Agent 线上延迟变高：怎么拆模型耗时、工具耗时、排队、上下文膨胀

**参考答案**

先给一次运行拉出分段耗时，再看变化落在哪一段。入口受理时间到 worker 开始执行是排队，对应 Kafka 积压、线程池队列和租约等待。模型段记录每次调用的首 token 时间和总时间，同时记下输入、输出 token。工具段按工具名记录下游耗时和重试等待。

上下文膨胀表现为同一次任务里输入 token 随步骤上升，模型首 token 变慢，工具耗时却没有同步上升。常见来源是完整历史、原始工具 JSON 和多 Agent 记录被原样拼进下一次提示。步数上升但 token 不明显上升，则是本可并行的工具被串行调用，多次模型耗时叠在一起。

定位之后分别处理：排队看消费能力和池大小；工具看该依赖的超时、重试和熔断；上下文按步骤摘要、截断工具输出；无依赖的工具并行。比较时看同一提示词版本和模型版本，避免把一次发布造成的变慢混进容量问题。

### 14. 可观测性：Langfuse/Trace 打点打哪些字段，token 成本、步骤数、失败分类怎么看

**参考答案**

一条用户请求对应一条 trace，标识与链路上的 `trace_id` 相同。trace 上放会话、用户哈希、Agent 名称、环境、提示词版本和最终结局。每次模型调用记模型名、输入和输出 token、首 token 时间、总耗时。每次工具调用记工具名、状态码、耗时、幂等键和错误类别。参数和结果默认脱敏，密钥、证件和支付信息不进观测系统。

token 成本按模型调用的 usage 汇总，价格表单独版本化，并按 Agent、模型和步骤类型拆开。看「每个成功任务的成本」，失败请求看起来便宜，却会把成本问题掩盖掉。

步骤数同时看模型步、工具步和重试步。失败分类使用固定枚举，例如模型超时、工具 5xx、参数不合法、策略拒绝、超过步数、注入拦截、转人工和用户取消，标在 trace 上，并指向第一次出错的步骤。提示词版本要能筛选，否则一次提示词改动造成的 token 上涨无法和流量上涨分开。

### 15. Agent 评测：任务成功率、轨迹合理性、幻觉率、转人工率，bad case 怎么回流成评测集

**参考答案**

四个指标都要先定义分母，并且用可复核的终态，不用模型的自报完成。

任务成功率看业务终态或标准答案是否满足，例如订单状态、消息回执、答案里的必要事实。轨迹合理性用规则比对：该调用的工具有没有调用、禁止的工具有没有出现、顺序和步数是否在预算内。幻觉率的分子是无法从本轮工具结果或检索证据推出的断言，分母要说明是按断言计还是按任务计；编号、金额和状态先做确定性核对。转人工率要拆开政策要求的正确升级，以及无法完成才移交的失败。

坏例来自失败、差评、人工接管和抽检。回流时脱敏，标失败类别，写成稳定用例：输入、允许的工具、可用证据、期望轨迹和期望终态。去重后进入发版前的回归集。线上比例用来发现新问题，固定集合用来防止旧问题回来。

### 16. 安全：prompt injection 从工具返回里进来怎么办，危险操作怎么加确认和人审

**参考答案**

工具结果、检索文档和网页都按不可信数据对待。系统指令与这些内容分层，工具正文放进明确的数据字段；其中出现的「忽略之前的指令、改调用某个工具」不会改变工具名单、权限和策略。

不可信文本不能直接流进有副作用的参数。金额、收款对象、消息接收人和外部 URL 只接受策略允许的值，来源要能追溯到用户原话或已授权的业务数据。读工具和写工具使用不同的最小权限凭证。

危险操作由模型之外的策略引擎判定。确认页展示规范化后的动作：对谁、金额、对象、效果。用户确认生成一次性凭证，凭证绑定这个动作的摘要；确认后参数发生变化，凭证失效。超过金额、新的支付对象或批量外发进入人审队列。人审通过后仍然走幂等执行，审核记录和 `trace_id` 一起留下。

拦截发生在执行前，并记入失败分类。只在系统提示里要求模型小心，挡不住来自工具返回的间接注入。

### 17. Spring Cloud 服务里接 Agent，超时、熔断、降级怎么和传统 RPC 调用共存

**参考答案**

Agent 运行和普通 RPC 分开治理。提交任务的接口按普通接口的短超时返回 `run_id`，后续用查询或流式输出看进度。多步执行放在独立 worker 和独立线程池，不占 Servlet 容器里等 RPC 的线程。

超时分成三层：单次模型调用、单次工具调用、整次运行的截止时间。打到原有微服务的工具继续用原来的客户端超时，因为下游容量没变。整次 Agent 不复用这个超时。

熔断按下游服务共用同一套资源。Agent 的工具客户端接入已有熔断器，支付服务已经打开时，Agent 不再从另一条没有熔断的连接打进去。重试只留在 Agent 步骤这一层，写操作客户端关掉自动重试，避免客户端重试和步骤重试相乘。

降级结果按调用方分开。普通查询可以回退缓存或默认值；Agent 完不成时返回待处理或转人工，并保留已经查询到的下游状态。两类流量的舱壁分开，Agent 的慢调用不会把查询接口的线程池占满。`trace_id` 继续通过原有客户端拦截器传到下游。

### 18. 手撕算法：给一个异步任务依赖图，实现拓扑排序并输出可执行批次（Java 或 Go 任选）

**参考答案**

用 Kahn 算法按层输出。边 `from → to` 表示 `from` 完成后才能开始 `to`。某一刻入度为 0 的任务互不依赖，组成一个可并行批次；本批结束后才释放它们的后继。同一批内部的顺序不影响正确性。深度优先搜索得到的是一条线性顺序，不能直接当作并行批次。

时间复杂度 O(V+E)，空间复杂度 O(V+E)。自环和去重后仍然无法清空的环都判为不可执行。重复边只计一次，否则入度被抬高，无环图也会被误判成有环。

波次实现简单，但同批里的慢任务会挡住只依赖快任务的后继。线上执行可以把「前驱计数归零就投递」作为真正的调度；题目要求输出批次时，返回下面这种同步波次即可。

```java
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

public final class TaskBatches {
    /** edges 中 [from, to] 表示 from 完成后才能开始 to。有环时抛出异常。 */
    public static List<List<Integer>> executableBatches(int n, int[][] edges) {
        if (n < 0) {
            throw new IllegalArgumentException("n < 0");
        }
        List<List<Integer>> next = new ArrayList<>(n);
        int[] indegree = new int[n];
        for (int i = 0; i < n; i++) {
            next.add(new ArrayList<>());
        }
        Set<Long> seenEdges = new HashSet<>();
        for (int[] edge : edges) {
            int from = edge[0];
            int to = edge[1];
            if (from < 0 || from >= n || to < 0 || to >= n) {
                throw new IllegalArgumentException("edge out of range");
            }
            if (from == to) {
                throw new IllegalArgumentException("cycle");
            }
            long key = (((long) from) << 32) | (to & 0xffffffffL);
            if (!seenEdges.add(key)) {
                continue;
            }
            next.get(from).add(to);
            indegree[to]++;
        }

        List<Integer> ready = new ArrayList<>();
        for (int i = 0; i < n; i++) {
            if (indegree[i] == 0) {
                ready.add(i);
            }
        }

        List<List<Integer>> batches = new ArrayList<>();
        int seen = 0;
        while (!ready.isEmpty()) {
            batches.add(List.copyOf(ready));
            List<Integer> nextReady = new ArrayList<>();
            for (int task : ready) {
                seen++;
                for (int downstream : next.get(task)) {
                    indegree[downstream]--;
                    if (indegree[downstream] == 0) {
                        nextReady.add(downstream);
                    }
                }
            }
            ready = nextReady;
        }
        if (seen != n) {
            throw new IllegalArgumentException("cycle");
        }
        return batches;
    }
}
```
