# 10.29 科大讯飞Agent Harness三面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 三面

### 1. 自我介绍

**答题思路**

一两分钟，按「你负责的层 → 一个项目 → 和这轮问题的关系」讲完就停。

1. 先说你做 Agent 的哪一段：编排、工具执行、评测或运行时。年限按简历上的事实说，职级和薪资不报。
2. 只展开一个你最熟的项目：用户要完成的任务、你负责的链路、你能拿出来的证据。没有线上数字，就讲评测集或一类坏例。
3. 收到三面会追问的点上：角色边界、怎样验收、循环外面的步数、权限和失败后怎么停。话停在这个项目上，方便对方接着问。

### 2. 你带人做 Agent 项目时，算法同学、后端同学、Prompt 工程同学、测试同学谁和谁最容易扯皮，你怎么切责任边界

**参考答案**

最容易扯皮的是算法和 Prompt 工程。同一次答错两边都能改，归因又叠在一起。

按失败层切责任。算法负责模型选型、索引、检索和重排，看约定延迟内该出现的证据有没有被召回。Prompt 工程负责系统指令、工具的自然语言描述、示例和输出说明，负责证据已经在上下文里、模型却没用上或说错。后端负责循环、工具网关、参数校验、超时、幂等、状态和日志，负责越权、重复执行和工具失败。测试负责用例、判定细则、回归门禁和抽检，负责这条算不算失败，不负责把提示词改到通过。

端到端只看四方认可的同一套样例。召回分、提示词版本、接口成功率都不能单独宣布上线。坏例先标层：没召回、召回了没用上、工具选错、工具失败、不该答仍答了。工具描述单独算契约：Prompt 起草说法，后端锁定 schema，算法不改工具语义。

### 3. 老板说“下周就要上多 Agent 客服”，但 RAG 召回才 60 分，你敢不敢上，怎么排期

**参考答案**

不敢按全量多 Agent 客服上。召回大约六十分，说明该进上下文的证据有相当一部分没有进来。规划器会在缺证据时继续分派，答错会被多轮放大，事后也分不清是检索错了还是某个专家错了。

下周可以上能当天关掉的窄切片：召回已经按意图分开、并且写了门禁的类目，才允许自动发送；其余只生成草稿，由人工点发送。实现用单循环、工具白名单和低置信转人工。同时把这 60 分拆开，看是没召回、召回了排不上去，还是文档里本来没有答案。

多 Agent 放到这条单循环跑出轨迹之后。轨迹里步骤类型确实分叉、一个提示装不下时，再拆一个专家，用同一套样例比完成率、接手率、严重错误和成本。自动发送按意图开关，出问题就回到人工。

### 4. Agent 项目没有标准需求文档，需求方只会说“要聪明一点”，你怎么做目标拆解和验收

**参考答案**

先把「聪明」写成可观察的任务结果。写不出判定细则，就还没有需求。

收成一个任务：输入是什么，交付物是什么，哪些话不能出现，例如没有依据的承诺。结果分成做成、做错、交给人。做错里单列编造政策和该停没停。每一类配少量锚定样例，需求和测试一起认定，里面要有必须转人工的反例。

验收看任务完成率、严重错误率、转人工率，以及回答能否被本轮证据支持。语气只作观察。离线样例过门禁再灰度，灰度看人工改了什么。对方若说还不够聪明，就要求指出一条样例，归进某一类再改。只有好答案、没有「必须不答」的样例时，乱答会混进验收。

### 5. LangChain 和 LangGraph 都不是银弹，什么场景你宁愿自研 Agent Loop 也不用框架

**参考答案**

工具执行、停止条件和崩溃恢复都收得进框架、团队也接受它的状态模型时，用框架。对不上时自研薄循环，集成库仍用现成的。

LangChain 适合留下模型适配、文档加载和检索组件。LangGraph 把循环做成带状态的图，checkpoint 和中断能覆盖人审，以及崩溃后从断点继续。工具节点若必须调用自己的网关，就在图里写这个节点，接受它的 checkpoint。

仍自研循环的情况有三类。工具在网关之外被框架直接执行，权限和幂等会落空。工具上若开了自动重试，非幂等副作用会做两次。checkpoint 表达不了「已发出、尚未回执」，进程死掉就不知道外部动作有没有发生。预算检查可以写成节点；要改框架才能控制重试和未回执状态时，薄循环更清楚：读状态、组上下文、调模型、校验、网关执行、写观察、按版本更新 checkpoint，直到完成或预算用尽。

稳定的单循环没有产品意义上的分支时，图主要增加升级时的行为变化。自研范围停在循环、状态和闸门。

### 6. Harness 工程你怎么做：最大步数、工具白名单、输出 schema 校验、人工确认、回滚点、审计日志这套外围骨架怎么搭

**参考答案**

这六件都做在模型循环外面，由同一条状态机串起来。写进提示词的限制，模型自己可以绕开。

最大步数存在任务状态里，每次模型调用和工具执行前检查，并跟 checkpoint 一起恢复，避免重跑把计数清零。同时记账 token 和墙钟，防止步数很少但单步极贵。工具按阶段给白名单，咨询阶段不出现退款。下发给模型的列表先过滤，网关执行前再查一次，并记下白名单版本。

模型输出先解析，再用该版本的 schema 校验工具参数；任务要求结构化结果时，最终答案也校验。拒绝未声明字段。非法输出不执行，错误写回观察，少量修正后再校验。高危动作把状态改为暂停，确认绑定参数的规范形式，通过后用同一个幂等键执行，过期或改过参数都要重新确认。

每个已提交步骤有一个不可变 checkpoint，用版本号条件更新。已经发出的邮件或退款不会因为回到旧 checkpoint 而撤销，外部补偿要另做。审计是追加的事件：模型输入输出的引用、工具名、参数摘要、策略版本、审批人和 trace。密钥不入库。快照用来恢复，事件用来追责，两份都要留。

### 7. AI 工作流和 Agent 的边界在哪，为什么有些业务用 DAG 工作流比多 Agent 更稳

**参考答案**

工作流的下一跳由程序按边上的条件选择。Agent 的下一跳由模型在循环里选择。多 Agent 是多个循环再加移交。节点内部调了模型，控制流仍可以是工作流。

审批、对账、固定话术客服，步骤事先画得出来：核身、检索、槽位、规则、生成、人审。每个节点最多调一次模型、节点内不再套循环时，轮次有上限。失败停在确定的节点上，重试和补偿有固定位置。「检索低于门槛就转人工」写成一条边。规则节点可以单测，回归集盖得住这些边。

多 Agent 把这条边变成一次移交。召回差、路由错、移交时丢掉上下文，都会表现为客服答错，定位时要先猜是哪个专家。路径和轮次都随模型变化，图本身不封顶。

下一步确实无法枚举、而且各专家的工具必须分开时，再用多 Agent。能画成图的业务把受步数限制的 Agent 放在单个节点里，整单仍由工作流收口。

### 8. 你们怎么做 Agent Eval：Golden Set、轨迹级评估、工具调用准确率、最终答案 Faithfulness 怎么量化

**参考答案**

四层分开打分。最终答对，不能抵消中间的乱调用。

Golden Set 冻结输入、文档版本、期望要点和禁止项，按意图分层，并留出不参与调参的一份。集合和索引一起编号，否则两次召回不能比。样例里包含必须拒答的题。

轨迹看约束满不满足：该调的工具调了，不该调的没调，顺序成立，例如先核身再退款，并且没有无进展的重复。和某条标准轨迹逐字对比会过严。代码能判的用代码；用评审模型时，拿人工抽过的样本校准。

工具调用拆开报。选择对不对用两个分母：应调用的步里选对了多少，以及实际发出的调用里选对了多少。参数是否正确只在工具选对时计算，标识和枚举规范化后精确匹配。Schema 非法单独成率。下游超时另记为执行失败。

Faithfulness 把最终答案拆成原子陈述，对照本轮检索和工具证据，标成支持、矛盾或证据中没有。分数是支持条数占全部陈述的比例。带了文档编号，还要核对原文能否推出这句话。字面重合和世界知识另设指标。

四个数都要写清分母和证据版本，否则可以被调参调上去。

### 9. A/B 测两个 Agent 版本，用户满意度差不多但成本高 40%，你砍哪个，依据是什么

**参考答案**

默认砍贵的那一版，把便宜的留作默认。满意度差不多，说明多花的大约四成成本没有换成用户能感知的收益。

下线前先看满意度有没有盖住事故。严重错误、越权、投诉、人工接手率，以及高价值意图的完成率，有一项明显更好，就保留贵的版本在那一段，其余流量走便宜版本。各段都没有差别，就整版下线贵的。实验分得清成本、分不清满意度时，以成本为准；样本太小、区间很宽时，先补样本，不凭一次「差不多」做永久决定。

四成成本要拆开来源：步数、上下文长度、模型单价还是工具调用。来源是空转步数时，先给贵的版本加上步数和预算上限再比一次。限制之后仍然差不多，再砍。满意度是滞后指标，规模上来以后这四成会直接变成账单。

### 10. 多 Agent 并发改同一份知识库、同一行任务状态、同一个文件，冲突怎么避免

**参考答案**

能切开的先切开：每个 Agent 只写自己的草稿和自己的路径。仍然重叠的写入，用版本条件更新挡住后写覆盖。模型推理放在临界区外面。

知识库不让 Agent 直接改线上索引。修改针对文档的基线版本提交，由唯一的发布者做条件更新，成功后再重建该版本的索引。检索绑定快照，一次查询不会混进半更新的段落。按 chunk 直接覆盖看起来互不相干，后写的会把别人的段落换掉。两份修改都基于同一版本时，交给人或这个发布者合并，不把两段自动拼进索引。

任务状态那一行只由编排器写。Agent 交回事件。提交时带上读到的版本，版本不符就重读再合并。同一事件带幂等键，重试不会记两次。

文件默认各写各的副本。必须改同一个文件时，补丁带上基线内容的哈希，哈希一致才应用，否则返回冲突。日志类写入改成追加。上下文里的旧副本没有版本，发现不了这些冲突。

### 11. Agent 系统可观测性你埋哪些点：每次 LLM 输入输出、Tool 入参出参、State 快照、Token、耗时、错误码

**参考答案**

这些点挂在同一次运行的同一条 trace 上，用步骤序号串起来。散落的日志对不回「哪一步把任务带偏了」。

每次模型调用是一个 span：模型名、提示词版本、结束原因，输入输出存引用，正文另存并脱敏。每次工具调用记下名字、schema 版本、脱敏后的参数、结果摘要和幂等键。State 在步骤边界记 checkpoint 编号和版本，暂停或失败时留可恢复的快照，不把整份状态每步塞进日志索引。Token 分开记输入、输出和供应商返回的缓存命中，先归到步骤再汇总到任务。耗时分开记排队、模型、工具和人审等待，人审不计入「模型变慢」。错误码用稳定枚举：Schema 非法、策略拒绝、工具超时、工具 5xx、预算用尽、厂商限流或 5xx。模型没选对和下游故障要能分开。

子 Agent 的 span 挂在父 trace 下。失败请求的正文保留；成功请求的大字段可以只留摘要。采样若把失败丢掉，事故来了会没有现场。

### 12. 如果大模型厂商接口半夜降级，你们 Agent 怎么从“全量智能”切到“规则兜底+人工台”

**参考答案**

开关放在编排入口，每回合开始时读熔断状态。全量循环、备用模型、本地规则、人工台四档事先接好。规则和模板放在本地，兜底路径不再请求已经熔断的厂商接口。

模型客户端统计超时和错误。连续失败或错误率越过按该供应商日常水平事先定好的线，熔断打开，新回合不再进入自由选工具的循环。另留一个人工开关。已经发出的工具等回执写入 checkpoint；退款或发送这类动作不确定有没有成功时，靠幂等键核对，人工台不凭猜测再做一次。然后停止循环。

规则只覆盖能枚举的高置信问法，用本地意图表和模板回复。对不上的进入人工队列，附上用户目标、最后一轮原话、已提交的工具结果和 checkpoint 编号。降级期间，规则没有写明允许的写操作一律不做。

供应商恢复后，先用一小部分只读流量探测，稳定再放开全量。探测不走对外发送和转账。熔断未恢复时，队列里的重试也要先读这个状态，否则旧请求会继续打满接口。

### 13. 你最近在跟的 Agent 方向新技术是什么，MCP、A2A、GraphRAG、Deep Research、Computer Use 里你最看好哪个

**答题思路**

五个里只押一个你能讲到数据流的。工具接入做过，就讲 MCP；没做过就改讲你真读过的那一个，其余只答它们坐落在哪一层。

1. MCP 讲三句：宿主侧的客户端发现工具、资源和提示词，服务器提供 schema；真正执行仍经过自己的网关；协议里的身份声明不能代替网关的权限、幂等和审计。
2. 准备好为什么不把另外四个当主答案。A2A 管的是跨系统把任务委托给另一个 Agent，边界还在同一个编排器里时，用事件回传即可。GraphRAG 是索引结构：抽实体关系、做社区摘要，用来回答要通读全库的问题，索引成本高；客服召回差时先查分块、过滤和混合检索。Deep Research 是多步检索、阅读、带引用写作的产品形态，步数和引用都要靠 Harness 收住。Computer Use 是没有接口时的截图到界面动作循环，点错就是副作用，有接口时直接调接口。
3. 收在一个你真看过的细节上，例如一次工具调用怎样和 trace 对齐。没读过的协议不要编字段名。

### 14. 你是怎么把一个完全没碰过的框架，比如 LangGraph 或某向量库，在一周内变成能上线方案的

**答题思路**

一周的交付是一条窄路径和它的失败行为，加上能回到旧链路的方法。教程跑通不算上线方案。按你真的学过的那个框架讲，没做到的步骤就直接说停在那里。

1. 先读执行模型：状态放在哪、一步怎样推进、工具在哪执行、重试是框架发起的还是你发起的、有没有 checkpoint。用官方最小例子跑通一次调用。
2. 换成你自己的一个工具，并强制走现有网关。框架能绕过校验，这周就没有可上线的方案。
3. 写一小批坏例：重复调用、非法参数、工具超时、中途取消。看默认会不会偷偷重试或吞掉错误。
4. 接上已有的 trace、步数上限和密钥管理。密钥不进 checkpoint。
5. 向量库换同一套问法：先核对过滤条件、删除、版本和权限字段，用一小份数据看过滤会不会漏，再谈召回分。
6. 灰度只放这条路径，写明谁值守、怎样切回旧实现。没有回退，就还是演示。面试时讲一个你读过的机制；当时没上线，就说停在哪条门禁。

### 15. 你带团队做 AI 项目时，怎么判断一个人是“真做过生产 Agent”还是“跑过 Notebook Demo”

**参考答案**

看他能不能讲清失败和副作用。演示流畅，说明不了系统进过生产。

做过生产的人，能从一次坏例走到 trace：模型输入、工具参数、工具结果，以及当时的提示词和 schema 版本。他说得清进程在工具返回前挂了会怎样，幂等键放在哪。他有冻结的评测集和失败分层，知道一次任务的步数和 token 大致在哪一档，也知道什么条件会停。写操作经过网关，密钥不在脚本里。

停在演示的人，成功标准是某次运行看起来对。工具函数和模型调用写在同一段脚本里，执行前没有校验。重跑同一输入会再发一次外部请求。他说不出状态存在哪，也说不出状态里有哪些字段，只记得框架名字。

现场可以给一个场景：退款工具超时，不确定钱扣了没有。顺着幂等键和回执查的，是生产路径；说再跑一遍的，是演示路径。已经有用户、却没有停止条件、权限和回放的服务，仍按演示算。
