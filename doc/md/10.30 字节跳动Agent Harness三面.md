# 10.30 字节跳动Agent Harness三面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

三面不怎么抠细节了，主要看你有没有自己的技术判断和体系化思考。Agent 这块大家都在摸索，所以面试官更在意你的选型逻辑和学习路径是不是靠谱。别装懂，不会就说不会，但给出你的思考方向，反而比硬编加分。技术选型那题很关键，能看出你是不是真的在生产里做过决策。

## 三面

### 1. 自我介绍

**答题思路**

三面时间短，这段用来交代你做过判断的那一段，项目细节留给下一问。

1. 用一句说你在 Agent 链路里负责的部分，例如编排、工具执行、评测或运行时。年限按事实说。
2. 只留一个取舍：当时有哪两条路，你选了哪条，用什么现象确认它成立。数字只说你能复述口径的。
3. 最后一句落到这个岗位：状态恢复、工具边界、成本，你能负责哪一件。说完停。

### 2. 介绍一个你最满意的项目，为什么满意，你在里面的角色和最大贡献是什么

**答题思路**

选一个你真负责过、现在还愿意维护的。满意要有标准，贡献要和别人的工作分开。

1. 两句框定范围：用户要完成的事，系统最后落到哪个可以核对的状态。角色用职责说，例如状态、工具或发布。
2. 满意只留一条，讲你守住的那个约束。例如写操作有幂等、失败后能从上次成功的步骤继续、费用能按任务对上账。
3. 最大贡献讲一个你拍板的设计，以及换一种做法会坏在哪。协作方的工作单独一句带过。
4. 规模和收益只说你能复述的口径。对方追问再往下拆，介绍本身停在这个决定上。

### 3. 如果让你从零搭建一个 Agent 平台，你会选哪些核心组件，画一下架构图，讲清楚每一层的职责和选型理由

**参考答案**

控制面自己做，模型和工具做成可替换的。同步请求只负责受理，长任务进队列。

```text
接入层：鉴权、租户、配额，受理后返回 run_id
        |
Harness：步骤、预算、人审、checkpoint
   |                 |                |
模型网关          工具网关         队列与 worker（租约）
                    |
                 注册中心
                 |      |
              内部工具  MCP 适配
        |
轨迹、费用、回归集
```

- 接入层做鉴权、租户和配额，通过后落任务并返回 `run_id`。长任务不占请求线程；配额不够就在入队前拒绝。
- Harness 独占状态写入，保存目标、已完成步骤、预算和暂停原因。每次调用模型和工具之前检查步数、墙钟和费用。停止条件放在运行时，模型改不了任务状态。
- 模型网关按这一步的难度选模型，统一超时和 token 计量。系统提示和工具定义保持稳定前缀，便于服务商做前缀缓存。业务代码不绑某家 SDK。
- 注册中心记录 schema、风险、超时和是否幂等。内部工具和 MCP 服务都先登记，再走工具网关，凭证由网关注入。未登记的工具不会进模型可见列表。
- worker 用租约领取队列里的任务，checkpoint 放数据库。进程重启后从最后一次成功的步骤继续；已经成功的写操作靠幂等键跳过。
- 轨迹把同一次运行的模型、工具和费用串起来，失败样本进回归集。发布时一起钉住 prompt、schema 和策略的版本。

在途任务绑定启动时的 schema。人审和去重在工具网关完成，模型拿不到能绕过网关的凭证。

### 4. 技术选型：MCP 协议和自研工具注册中心，你选哪个，为什么；社区方案成熟度和业务定制灵活性怎么平衡

**参考答案**

两层叠在一起用：注册中心做控制面，MCP 做接入协议。

MCP 负责发现和调用，例如拉取工具列表、按 schema 传参、读取资源，本地进程和远程服务都能接到主机上。它的鉴权解决的是客户端能不能连上这个服务，不负责这次任务能不能执行这只工具、有没有超预算、要不要人审，也不提供你们自己的幂等和错误码。这些放在注册中心：负责人、风险、超时、可否重试、schema 版本。模型只能看见已登记、并且当前步骤允许的工具。

社区服务成熟，就用适配器登记进同一张表，运行时仍走同一条策略。扣款、改数据和对外发消息，要等幂等和确认做进适配器之后再登记；在此之前用内部实现。只读、或者失败了可以安全重做的动作，可以直接登记维护良好的社区服务。服务自报的只读或危险标记只当提示，执行与否以注册中心的策略为准。

规范版本钉在适配器上。注册表用契约测试挡住不兼容变更。质量不稳定的社区服务换成一层薄的内部工具，模型不直连该服务。这样成熟度体现在可选的适配器上，各业务团队仍共用一套调用协议。工具说明和工具返回都按不可信文本处理，接上 MCP 也不会消掉间接注入。

### 5. Agent 框架迭代很快，你怎么判断一个新框架值不值得引入，评估维度有哪些

**参考答案**

值得引入，是指它替掉一块你正在维护的运行时，并且工具执行前的策略钩子还留在你手里。只换一套更短的调用写法，不值得动已经在跑的任务。

- 失败模型：进程在工具返回前退出，能不能从最后一次成功的步骤再跑；等人审批时不占着工作线程。
- 控制点：每次工具调用之前都能做权限、预算和轨迹。这一层做不到，框架只留在原型里。
- 在途任务：框架升级之后，暂停中和执行中的 checkpoint 还能否跑完。
- 依赖面：许可证、维护者、破坏性变更的频率。值班的人要能沿着一条轨迹看到工具参数。
- 迁移成本：现有工具要改多少。业务代码依赖自己的运行时接口，类型不从框架里直接漏出去。

用已经有的坏例试，不用演示项目：超时、同一步执行两次、等待审批、进程在工具返回前重启。过不了就留在主路径外面。引入后钉住版本，原来那套循环真的删掉，避免两套状态并存。

图或状态结构一升级，旧的暂停任务还会留在旧代码上。发布说明里要写这些任务怎么迁完。

### 6. 团队里有人坚持用旧的稳定方案，你觉得应该推新技术吗，怎么推，举一个你推动过的实际案例

**答题思路**

先算旧方案正在付的成本，再决定推不推。故障、交付速度或值班负担说不清，就先别换。

1. 值得推的条件：现方案已经挡路，新方案能用一组坏例验证，并且能退回。已经跑起来的任务在退回之后仍走旧路径。
2. 用小范围、默认关闭的试点来推。试点期间值班的人是你。成功标准和谁可以叫停，事先写下来。成功可以是失败可恢复、调用方无感，按你这次改动真实能观察的现象来定。
3. 案例按「痛在哪、范围划到哪、怎样算成、怎样退回」讲你真正推动过的一次。公司、人数和收益按事实说。没有这么完整的一次，就讲你推动过的最小变更，一次依赖升级不要讲成平台迁移。
4. 对方守着旧方案时，先复述他在防的风险。试点过不了你自己写下的标准，就继续用旧的。

### 7. 最近半年在学什么新技术，怎么学的，学到什么程度算掌握了

**答题思路**

只讲一门你最近半年真在学、并且和这个岗位有关的技术。

1. 先说场景：用在哪条链路上，原来哪一件事做不到。
2. 学的顺序：先看规范或源码里和状态、失败有关的部分，再做一个贴近你系统的小切片，最后用一次真实失败来检验。只看教程，到这里还没学完。
3. 掌握看三条：能独立接到现有系统里；能说清崩溃或超时之后状态落在哪；能举出一种不该用它的情况。缺一条就说卡在哪一条。
4. 学到一半也可以讲。把已经验证过的和只看过文档的分开。

### 8. 你对 Agent 未来一年的趋势判断是什么，Multi-Agent 是噱头还是真解法

**参考答案**

未来一年更值得投入的是运行时：长任务可恢复、工具侧有约束、按成功任务记账、上线前有回归。模型会换，这层换得少。带外部裁判的场景会继续快于开放域办事，测试、编译和策略都能判定产物对不对。

Multi-Agent 在几种结构里是解法。子任务互不依赖，可以并行；两边权限不该相同，例如一边能改、一边只读；或者需要一个靠测试和策略下结论的检查器。交接用结构化结果，共享状态由父节点写入。

一个顺序流程拆成规划、执行、反思三个角色，上下文仍是同一份，通常是把 token 和故障面乘上去。检查器把整段轨迹再读一遍，费用会超过干活的那一个。单循环的预算、停止条件和轨迹先做硬，再在确实要并行或隔离权限的地方加 worker。

问责要落到一次具体的工具调用上，角色名字不能代替这次调用的记录。

### 9. 你平时看哪些技术博客、论文、开源项目，怎么筛选阅读优先级

**答题思路**

报你这周真的打开过的来源，三个就够。

1. 优先级只看一件事：它会不会改变你这个月已经在做的设计或排障。对不上的先放着。
2. 先读规范、论文，以及仓库里的 issue 和发布说明，再读别人的解读。解读用来找入口，结论以一手材料为准。
3. 开源项目先看维护者、测试和最近的破坏性变更，再看演示。没有发布节奏的仓库不拿来做生产评估。
4. 读完用一句话记下它改了你的哪个决定。写不出这句，就从队列里拿掉。固定一个短名单，比存一堆没读的标题有用。

### 10. 跨团队协作时，Agent 系统的接口规范、数据格式、错误码怎么对齐，谁说了算

**参考答案**

对齐一份带版本的契约。跨团队共用的信封，由运行这套系统、要对在途任务负责的团队定：任务状态、幂等键、追踪字段、错误结构、超时语义。业务字段和业务错误的含义，由提供工具的团队定，放在信封里并带自己的前缀。

数据用带 schema 版本的 JSON。标识和时间用字符串，金额用最小货币单位的整数或十进制字符串。大段原文进对象存储，上下文里放引用和摘要。一次运行钉住启动时的版本，新版本不改已经在跑的任务。

错误分成平台码和业务码。平台码覆盖超时、鉴权、限流、schema 不合法和幂等冲突，并带上是否可重试、是否已经受理。业务码不占用这些语义。运行时根据这两个字段决定重试、停住或转人工。

变更走兼容性检查和双边契约测试，留弃用窗口。增加可选字段可以兼容；改一个错误码的含义就要换版本。意见冲突时，先让旧版本把在途任务跑完。

可重试由被调用方在结构里声明。调用方看见 5xx 就重试，会把已经受理的写操作做成两次。

### 11. 线上有一个 Agent 长期任务跑了很久没结束，你怎么排查，从入口到出口说清楚每一步

**参考答案**

用 `run_id` 把网关、队列、worker、模型和工具对齐到同一次运行，再按状态往下看。

1. 入口：网关是否受理成功。没有任务记录，就是没进系统。停在待执行，就看队列是否堆积、消费者是否还在、前面有没有堵住的消息。
2. 领取：执行中要对上 worker 和租约到期时间。租约过了状态仍是执行中，说明恢复逻辑没有把这单重新领走。
3. 步骤：看 checkpoint 里最后一次成功的步骤、尚未回执的工具调用、最近一次模型请求的时间。卡在模型，查这一步的总截止时间；只设单次读超时，会被持续吐字拖住。卡在工具，查请求是否发出、下游耗时、结果写回是否失败。等人审批却标成执行中，说明暂停状态没有单独分出来。
4. 进展：步数在涨，目标和参数摘要不变，就是空转。接着看步数上限为什么没有触发。
5. 出口：结束条件是目标状态已经成立，还是只等模型说完成。没有步数、墙钟或预算的硬上限时，循环可以一直规划下去。

处理时先停止新的模型调用。已经发出的工具按幂等键查询回执，再决定从 checkpoint 继续，还是标失败。先杀进程会留下说不清的外部副作用。

### 12. 一个 Agent 系统每天消耗大量 token，老板问能不能降本，你怎么分析、怎么提方案

**参考答案**

先按任务类型、模型、输入、输出、缓存命中、重试和失败运行把费用拆开，找到占大头的那一类，再谈全局限流。很多供应商的输出单价更高，倍数以账单为准。

常见的大头是每一步重发全部工具定义和历史、失败步骤无差别重试、用大模型做抽取和路由，以及多个 Agent 各读一遍相同上下文。

方案按风险排。先加上步数、墙钟和重复调用的上限，参数错误不重试。稳定的系统提示和工具定义放在前缀里，用户标识和任务标识不要插到前缀前面，否则前缀缓存对不上。这一步用不到的工具定义不要下发；旧的工具原文改成摘要加引用。意图判断和抽槽走小模型，拿不准的步骤再用大模型。同一次任务里，参数相同的读工具复用结果。模型回复不要按问题文本做全局缓存，工具状态变了，答案会变。

用每个成功任务的费用，连同成功率和人工接管率一起看。单次请求的 token 下来了，重试变多，总账会更高。限制输出长度时要让工具参数仍是完整 JSON，截断的参数会引发重试。压缩上下文时留下后续决策依赖的错误信息和已确认槽位。

### 13. 你带过新人吗，怎么帮他们理解 Agent 和传统后端的区别，踩过什么坑

**答题思路**

先按事实说带没带过。带过就讲你真带过的人；没带过就讲你准备怎么带。

1. 用一次真实调用把区别讲具体。传统接口是一次请求、一个返回码，重试由调用方决定。Agent 是一个循环：下一步取决于模型，工具可能已经改了外部状态，成功要看业务状态有没有成立。
2. 带的时候一起读一条失败轨迹，让对方指出下一步状态应该是什么，再补一条回归。不从框架教程开头。
3. 坑只讲你确实见过的。常见的是把模型当成可重试的 RPC、重试写操作、只记录最终文案、没有步数和墙钟上限、提示词改了却不进发布记录。没见过的不要说成自己的事故。
4. 新人先改一条只读链路。他能说清幂等键和停止条件之后，再开放写操作。

### 14. 团队里有人写代码不考虑边界和异常，你怎么跟他沟通，有没有具体例子

**答题思路**

对着一次具体的失败路径谈。

1. 在评审里写清输入、缺掉的判断和你期望的终态。例如工具超时之后，任务应停在可恢复的状态；重复请求应返回第一次的结果。
2. 例子用你真评审过或自己写过的代码。没有现成故事，就讲你会盯住的不变量：超时、空结果、重复提交。同事的事故和损失数字都按事实说。
3. 约定一条测试：没有这个判断时测试失败。人改完之后，测试留在仓库里。
4. 同一类问题再出现，就把检查放进共享的运行时或测试模板。第二次还只靠当面提醒，会变成两个人的分歧。

### 15. 手撕算法：设计一个带超时控制的 Agent 任务调度器，支持并发执行、结果收集、超时取消

**参考答案**

用固定大小的线程池并发跑任务。提交的那一刻就挂上截止计时，到点 `cancel(true)`，不等收集线程走到这道任务。收集时再按剩余时间等待，计时器迟到也不会多等。结果先写上的就保留，到点还没完成记超时。返回顺序与提交顺序一致。

`cancel(true)` 只是中断工作线程。Agent 循环要在下一步之前看中断标记并退出，模型流和工具请求要用可关闭的客户端。超时之后不再发新的工具调用；已经发出的写操作按幂等键查询，不因为超时再提交一次。

线程池的核心线程数和最大线程数设成同一个值，队列有界。`ThreadPoolExecutor` 在核心线程满了之后会先入队，队列满了才扩到最大线程数，所以最大线程数大于核心线程数时，并发限制会晚于队列堆积。队列容量按能接受的等待任务数来定。装不下就拒绝这一次提交，调用方稍后重试。队列不设上限时，慢任务会把内存堆满。

每道任务用自己的截止时间。还要整批截止时，提交瞬间把该任务的超时收成单任务超时和批剩余时间里更短的那个。任务自己抛出的超时和业务异常记为失败。调度器的超时只来自提交时挂上的计时，以及 `Future.get` 等到截止。计时还没到就被取消或中断，记为取消。

整理结果是 O(n) 时间和 O(n) 空间。墙钟由并发度和最慢任务决定。模型和工具自己的耗时不算进调度开销。若要先完成的先返回，用 `CompletionService` 取结果；截止计时仍然在提交时挂上，不改成取出时才开始。

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.Callable;
import java.util.concurrent.CancellationException;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.concurrent.atomic.AtomicBoolean;

public final class AgentTaskScheduler implements AutoCloseable {
    private final ExecutorService pool;
    private final ScheduledExecutorService timers;

    public AgentTaskScheduler(int concurrency, int queueCapacity) {
        if (concurrency < 1 || queueCapacity < 1) {
            throw new IllegalArgumentException("capacity < 1");
        }
        this.pool = new ThreadPoolExecutor(
                concurrency,
                concurrency,
                0L,
                TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<Runnable>(queueCapacity),
                new ThreadPoolExecutor.AbortPolicy());
        this.timers = Executors.newSingleThreadScheduledExecutor();
    }

    /** timeoutMillis 从每道任务提交时起算，队列里的等待也算在内。 */
    public <T> List<TaskOutcome<T>> runAll(List<? extends AgentTask<T>> tasks, long timeoutMillis)
            throws InterruptedException {
        if (tasks == null || timeoutMillis <= 0) {
            throw new IllegalArgumentException("bad arguments");
        }
        int n = tasks.size();
        List<Slot<T>> slots = new ArrayList<Slot<T>>(n);
        boolean done = false;
        try {
            for (int i = 0; i < n; i++) {
                AgentTask<T> task = tasks.get(i);
                if (task == null || task.id() == null || task.id().trim().isEmpty()) {
                    throw new IllegalArgumentException("task id required");
                }
                slots.add(submitOne(task, timeoutMillis));
            }
            List<TaskOutcome<T>> outcomes = new ArrayList<TaskOutcome<T>>(n);
            for (int i = 0; i < n; i++) {
                outcomes.add(awaitOne(tasks.get(i).id(), slots.get(i), timeoutMillis));
            }
            done = true;
            return outcomes;
        } finally {
            if (!done) {
                for (int i = 0; i < slots.size(); i++) {
                    slots.get(i).cancel();
                }
            }
        }
    }

    private <T> Slot<T> submitOne(AgentTask<T> task, long timeoutMillis) {
        long startNanos = System.nanoTime();
        final Future<T> worker;
        try {
            worker = pool.submit(task);
        } catch (RejectedExecutionException rejected) {
            return new Slot<T>(null, rejected, startNanos);
        }
        final Slot<T> slot = new Slot<T>(worker, null, startNanos);
        try {
            // 到点就取消，不依赖收集线程是否已经走到这道任务。
            slot.alarm = timers.schedule(new Runnable() {
                @Override
                public void run() {
                    slot.timedOut.set(true);
                    worker.cancel(true);
                }
            }, timeoutMillis, TimeUnit.MILLISECONDS);
        } catch (RejectedExecutionException rejected) {
            worker.cancel(true);
            return new Slot<T>(null, rejected, startNanos);
        }
        return slot;
    }

    private static <T> TaskOutcome<T> awaitOne(String id, Slot<T> slot, long timeoutMillis)
            throws InterruptedException {
        if (slot.submitError != null) {
            return TaskOutcome.failed(id, slot.submitError);
        }
        long remainingNanos = TimeUnit.MILLISECONDS.toNanos(timeoutMillis)
                - (System.nanoTime() - slot.startNanos);
        if (slot.worker.isDone()) {
            return readDone(id, slot);
        }
        if (remainingNanos <= 0) {
            return finishLate(id, slot);
        }
        try {
            T value = slot.worker.get(remainingNanos, TimeUnit.NANOSECONDS);
            cancelAlarm(slot);
            return TaskOutcome.ok(id, value);
        } catch (TimeoutException timeout) {
            return finishLate(id, slot);
        } catch (CancellationException cancelled) {
            cancelAlarm(slot);
            return slot.timedOut.get() ? TaskOutcome.timedOut(id) : TaskOutcome.cancelled(id);
        } catch (ExecutionException failed) {
            cancelAlarm(slot);
            return failedOutcome(id, failed.getCause() == null ? failed : failed.getCause(), slot);
        }
    }

    /** 截止时间已到。结果刚好写上就保留，否则取消并记超时。 */
    private static <T> TaskOutcome<T> finishLate(String id, Slot<T> slot) throws InterruptedException {
        slot.timedOut.set(true);
        slot.worker.cancel(true);
        if (slot.worker.isDone() && !slot.worker.isCancelled()) {
            return readDone(id, slot);
        }
        cancelAlarm(slot);
        return TaskOutcome.timedOut(id);
    }

    private static <T> TaskOutcome<T> readDone(String id, Slot<T> slot) throws InterruptedException {
        cancelAlarm(slot);
        if (slot.worker.isCancelled()) {
            return slot.timedOut.get() ? TaskOutcome.timedOut(id) : TaskOutcome.cancelled(id);
        }
        try {
            return TaskOutcome.ok(id, slot.worker.get());
        } catch (CancellationException cancelled) {
            return slot.timedOut.get() ? TaskOutcome.timedOut(id) : TaskOutcome.cancelled(id);
        } catch (ExecutionException failed) {
            return failedOutcome(id, failed.getCause() == null ? failed : failed.getCause(), slot);
        }
    }

    private static <T> TaskOutcome<T> failedOutcome(String id, Throwable cause, Slot<T> slot) {
        if (cause instanceof InterruptedException || cause instanceof CancellationException) {
            return slot.timedOut.get() ? TaskOutcome.timedOut(id) : TaskOutcome.cancelled(id);
        }
        return TaskOutcome.failed(id, cause);
    }

    private static void cancelAlarm(Slot<?> slot) {
        if (slot.alarm != null) {
            slot.alarm.cancel(false);
        }
    }

    @Override
    public void close() {
        timers.shutdownNow();
        pool.shutdownNow();
    }

    private static final class Slot<T> {
        final Future<T> worker;
        final AtomicBoolean timedOut = new AtomicBoolean();
        final Throwable submitError;
        final long startNanos;
        Future<?> alarm;

        Slot(Future<T> worker, Throwable submitError, long startNanos) {
            this.worker = worker;
            this.submitError = submitError;
            this.startNanos = startNanos;
        }

        void cancel() {
            cancelAlarm(this);
            if (worker != null) {
                worker.cancel(true);
            }
        }
    }

    public interface AgentTask<T> extends Callable<T> {
        String id();
    }

    public static final class TaskOutcome<T> {
        public enum Status { OK, TIMED_OUT, CANCELLED, FAILED }

        public final Status status;
        public final String id;
        public final T value;
        public final Throwable error;

        private TaskOutcome(Status status, String id, T value, Throwable error) {
            this.status = status;
            this.id = id;
            this.value = value;
            this.error = error;
        }

        public static <T> TaskOutcome<T> ok(String id, T value) {
            return new TaskOutcome<T>(Status.OK, id, value, null);
        }

        public static <T> TaskOutcome<T> timedOut(String id) {
            return new TaskOutcome<T>(Status.TIMED_OUT, id, null, null);
        }

        public static <T> TaskOutcome<T> cancelled(String id) {
            return new TaskOutcome<T>(Status.CANCELLED, id, null, null);
        }

        public static <T> TaskOutcome<T> failed(String id, Throwable error) {
            return new TaskOutcome<T>(Status.FAILED, id, null, error);
        }
    }
}
```

调用方线程在收集过程中被中断时，尚未正常返回的任务会取消计时并 `cancel(true)`。不响应中断的任务仍可能占着线程，后面的任务会在队列里耗尽自己的截止时间。`close` 先停计时线程，再 `shutdownNow` 工作线程。
