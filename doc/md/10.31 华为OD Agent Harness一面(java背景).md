# 10.31 华为OD Agent Harness一面(java背景)

## 一面

### 1. 自我介绍

**答题思路**

控制在一两分钟。一面先让对方知道你做哪一段、准备往下讲哪个项目，项目细节留到下一问。

1. 第一句说明 Java 后端年限和你实际写过的那段：会话状态、工具执行，或模型循环外面的运行时。年限用你自己的，不报职级和薪资。
2. 只点一个你写完主干的 Agent 或 AI 项目：谁在用、输入是什么、你负责哪一段。效果用你拿得出来的事实；没有数字就讲约束，例如超时后调用怎么停。不临时编项目名和调用量。
3. 最后一句收到这个岗位上：你准备展开的是编排、参数校验和上下文。说完就停。

### 2. 介绍一个你做过的智能 Agent 或 AI 相关项目，讲清楚架构、你负责的模块和落地效果

**答题思路**

按一次请求怎么走完来讲，对方才好往下追。只讲你真正做过的系统。

1. 场景：用户是谁，输入是什么，怎样算做完。范围停在你确实负责的模块。
2. 架构按这条线说：请求进入，组装上下文，模型给出工具调用，校验后执行，结果写回，满足什么条件结束。点明你写的那段，其余一句话带过。
3. 落地准备两件你真实处理过的事，例如相同调用被拦住、参数不合法没有执行，或删除、发送前必须人确认。每件讲到代码位置和你看到的结果。没有监控数字就不要编成功率。
4. 收在一处你确实想过的改进上，例如状态没有落库，或工具超时后调用还在跑。

### 3. Agent 和普通 Chatbot、固定 Workflow 的区别是什么，什么场景不适合上 Agent

**参考答案**

Agent 在循环里自己决定下一步：看上一次观察，选择工具，再把结果写回，直到目标完成或被运行时拦住。普通 Chatbot 的主路径是按对话生成文本，检索和模板由程序在生成前插好，模型不负责规划多步行动。固定 Workflow 的顺序和分支由人预先写死，模型通常只填某一步的文案或字段。

路径能穷举、结果必须每次一致的流程，例如对账、出账、权限变更，用 Workflow。单次问答加明确检索就能完成的，用普通问答。工具只有一两个且顺序不变时，Workflow 更便宜，也更好回归。高危写操作如果没有独立的人工确认，不让模型把闭环自己跑完。

模型外面套了循环，但工具和顺序其实写死，排查和费用仍按 Workflow 评估。Agent 适合步骤随观察变化、事先画不全分支的任务。

### 4. Agent 的 Harness 层你怎么理解，编排、状态、工具调用、可观测分别负责什么

**参考答案**

Harness 是模型循环外面的运行时，把一次任务约束到可结束、可审计。模型只负责在给定工具集里做选择。

1. 编排：组装本轮上下文，发起模型调用，解析工具调用，执行后写回，并决定继续、结束还是转人工。轮次、墙上时钟和重复签名都在这里计数，模型改不了这些计数。
2. 状态：保存目标、消息、工具结果和任务阶段。进程重启后按会话恢复。同一会话同时只推进一个回合。
3. 工具调用：维护注册表、参数 Schema、权限、超时和统一的结果结构。分发只按名称查表。未注册的名字直接拒绝。
4. 可观测：同一次任务共用 traceId，记录模型回合、工具名、参数摘要、耗时、状态和停止原因。指标按工具名和状态聚合，会话 id 放日志，避免标签基数被打爆。

这四层都在应用代码里。模型服务不知道轮次上限，也不替你做鉴权。

### 5. ReAct 循环里 Agent 反复调用同一个工具停不下来，怎么检测并强制退出

**参考答案**

ReAct 是推理、行动、观察的循环。停不停由 Harness 判定。

签名用工具名加上规范化参数。参数先过 Schema，只保留声明过的字段，再按键排序序列化。模型多塞的随机字段过不了校验，也进不了签名。同一工具、参数不同，可能是正常翻页，不能只按工具名熔断。

本回合里同一签名已经成功过，再次出现就回放上次结果，不再执行。同一签名的执行或回放次数达到本任务的上限，或者总步数、墙上时钟任一到达上限，就强制结束。两个工具交替着重复，会被签名计数抓住；参数每次都在合法范围内变一点，则靠总步数和截止时间挡住。

退出时不再发起工具调用。任务标成未完成，写明停止原因，把已经拿到的观察返回给调用方。超时且结果不明的写操作不回放成成功，也不自动再执行。

### 6. 工具调用链路怎么设计，Function Calling 参数校验失败、类型不对怎么兜底

**参考答案**

链路分注册、下发、校验、执行回写。模型只能在本轮下发的工具子集里选择。

注册表保存名称、描述、JSON Schema、超时和是否有副作用。分发用名称查表，不按模型给的字符串反射任意类。执行前校验类型、必填、枚举、范围，并拒绝未声明字段。未知工具把错误写回，执行次数为零。

校验失败不执行。把字段路径、期望类型和实际类型作为这条 `tool_call_id` 的结果写回，让模型在下一轮改正。金额、资源 id、删除范围不填默认值，也不做隐式类型转换，避免 `"012"` 和 `12` 变成同一次调用，把幂等键和审计对乱。同一字段连续错到任务允许的次数，就停止再要参数，把失败交给用户。

协议已经给出结构化 `tool_calls` 时直接读。若只收到一段坏 JSON，回一条固定纠错，仍失败就结束本回合，期间不执行工具。工具开始执行之后的失败走业务重试或补偿，不再当成解析问题。

### 7. RAG 流程里文本分块策略怎么定，召回不准时从哪些环节排查

**参考答案**

分块按文档结构来。标题、段落、列表各自成块，表格单独成块。块仍然过大，就按段落再切，相邻块保留一段重叠，让跨在边界上的句子至少在一块里完整。每块记下文档 id、序号、标题路径和权限标签。块长跟着嵌入模型的输入上限和召回实验调，不写死一个所有文档通用的字数。更换嵌入模型或改切法时新建索引，建完再把检索切过去。

召回不准从数据查到生成，先分清没有召回到，还是召回到了没有用上。

1. 目标文档是否入库，权限和状态过滤是否把正确块去掉，查的是不是旧版本索引。
2. 抽出那一块看切分：答案是否被切碎，或一块里混了多个主题。
3. 查询侧看指代有没有消解，向量一路和关键词一路各自命中了什么。
4. 正确块在列表里但名次靠后，查重排和 topK 截断。
5. 块已经放进上下文仍答非所问，查原文是否被截断，以及回答有没有引用这些块。

权限过滤过严常常表现为召回为空。这种情况下先改过滤和索引，而不是先改生成提示词。

### 8. 短期记忆和长期记忆怎么存，跨会话上下文如何用 Redis 和 MySQL 落地

**参考答案**

短期记忆是这一轮要送进模型的消息窗口。长期记忆是跨会话保留的少量用户事实。全量消息和事实以 MySQL 为准，Redis 放会过期、可以重建的热数据。

消息表按 `session_id` 加序号存储角色、内容和时间，`(session_id, seq)` 唯一。进行中的回合、轮次和未完成的工具调用放在 Redis，键带会话 id，并设 TTL，每推进一次就刷新。Redis 丢失或淘汰后，按序号从 MySQL 把最近窗口装回来。超长工具原文落对象存储，表里留摘要和指针。

长期记忆另表保存用户 id、事实、来源消息和更新时间。只在回合正常结束后写入确认过的偏好和结论，工具原文和报错不写进去。同一事实有新结论时，检索只取最新一条。

新会话不复制旧消息。按当前问题从长期记忆里取少数几条注入，查询条件必须带用户 id。同一会话同时只跑一个回合，用带 token 的 Redis 锁或版本号拦住交错写入。不同会话的消息序号互不影响。

### 9. 提示词注入和工具越权怎么在 Harness 层拦截，高危操作怎么加审批和降级策略

**参考答案**

拦截做在调度和执行入口。提示词只能降低被带偏的概率，挡不住用户内容或工具结果里的指令。

系统说明、用户输入、检索文档、工具结果分开放。文档和工具结果标成数据。结果里出现「改调删除」这类文字，不会被执行器解析成新调用。只有下一轮正式的工具调用结构才进入调度，并且再过一遍权限。

每次调用按当前登录用户重新鉴权，核对资源是否属于他的范围。本轮没有下发的工具直接拒绝。参数里的用户 id 以服务端会话为准，忽略模型自填的身份。

删除、发送、改权限、付款标成高危，不直接执行。先落一条审批：影响范围摘要、一次性令牌、会话、用户、工具名和参数哈希，短时有效。用户在已登录界面确认。确认接口不放进模型的工具列表。执行时用库存的参数。拒绝或超时都告诉模型这次没有执行，不自动重试。

审批或鉴权依赖失败时，高危工具直接拒绝，只读查询可以继续。连续失败就结束回合并转人工。提案和真正执行各记一条审计，模型改不了这些记录。

### 10. Java 线程池核心参数，Agent 并发调多个工具时怎么隔离上下文和限流

**参考答案**

`ThreadPoolExecutor` 的关键参数是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、工作队列、线程工厂和拒绝策略。当前工作线程数少于 `corePoolSize` 时新建线程；达到核心线程数后任务先入队；队列满了才扩到最大线程数；再满就拒绝。无界队列会让任务堆在内存里，最大线程数也不会生效。希望队列几乎不堆积、先扩容再拒绝时，用没有容量的 `SynchronousQueue`。

模型调用、阻塞型工具和 CPU 解析分成独立的池，线程带名字。阻塞型工具使用有界队列。拒绝时把「系统忙」写成这条工具调用的结果，记入轮次预算。不用 `CallerRunsPolicy` 在推进回合的线程里把任务跑掉。

上下文放进提交的任务对象：用户、会话、traceId、允许的工具集，在提交时拷贝。工作线程不读线程池上残留的 `ThreadLocal`，线程复用不会把上一个会话带过来。`InheritableThreadLocal` 只在创建线程时继承，挡不住已经建好的池线程。多个只读工具并行，结果回到会话线程后按 `tool_call_id` 合并。写工具不和其他写并行。工具 Bean 本身无状态。

限流分三层：单个用户能同时发出的工具数、单个工具的在途信号量、进程池的队列容量。多实例再加 Redis 计数或令牌桶，本地信号量仍然保留。超时后 `cancel(true)`，并让 HTTP 或 SQL 客户端自己的读写超时先到，调用才会从不可中断的 IO 里返回。

### 11. synchronized 和 ReentrantLock 区别，锁升级过程说一下

**参考答案**

`synchronized` 由 JVM 实现，进入和退出由编译器配对，异常路径也会释放。线程堵在进入同步块时不响应中断。`ReentrantLock` 用 AQS 的 `state` 计重入次数，必须在 `finally` 里 `unlock`。它支持公平策略、`tryLock`、带超时的尝试、`lockInterruptibly` 和多个 `Condition`。两者都可重入。`ReentrantLock` 默认非公平；公平锁上的无参 `tryLock()` 仍会直接抢占，带等待时间的 `tryLock` 才遵守队列。

锁升级说的是 `synchronized` 的对象头，`ReentrantLock` 没有这条路径。经典 HotSpot 的顺序是无锁、偏向锁、轻量级锁、重量级锁。无锁时低位锁标志是 `01`、偏向位为 0。偏向锁的锁标志仍是 `01`，偏向位为 1，高位是线程 ID；同一线程再次进入只比对线程，不再 CAS。别的线程来抢时在安全点撤销偏向：原线程还在同步块里，就补成它持有的轻量级锁；已经退出，对象回到无锁，再按轻量级锁竞争。轻量级锁在当前栈帧放 Lock Record，用 CAS 让对象头指向它，标志是 `00`，重入再压一条记录。竞争持续，就膨胀成 `ObjectMonitor`，标志变为 `10`，抢不到的线程进入队列阻塞。

JDK 15 起偏向锁默认关闭，JDK 18 移除了实现和相关参数。现行主路径是无锁经轻量级锁膨胀到重量级监视器。空闲监视器可以被异步撤销，下次再从轻量级开始。锁正被持有时不会降级。锁消除和锁粗化是 JIT 的优化，不属于升级。

### 12. Spring 的 AOP 实现方式，JDK 动态代理和 CGLIB 区别，事务为什么失效

**参考答案**

Spring 里常见的 AOP 是运行时代理。`@EnableAspectJAutoProxy` 默认 `mode` 是代理，用的是 `@Aspect` 的写法，不会把通知织进业务类的字节码。真正的 AspectJ 编译期或加载期织入可以拦到自调用，需要单独的织入配置。事务注解在绝大多数项目里走的是代理。

有接口时，Spring Framework 默认用 JDK 动态代理，代理对象实现这些接口，只能拦接口上的方法。没有接口，或 `proxyTargetClass=true` 时，用 CGLIB 生成子类并覆盖方法。`final` 类和 `final` 方法无法被 CGLIB 覆盖。Spring Boot 2 及以后默认 `spring.aop.proxy-target-class=true`，Boot 3、4 仍是这个默认值，所以有接口的 Bean 也常常是类代理。

事务失效，是因为调用没有进入代理，或代理没有找到事务属性。同类里的 `this.xxx()` 自调用不会进代理。代理模式默认只处理 `public` 方法。`@Transactional` 只标在接口上时，JDK 代理能看到，CGLIB 看不到接口注解，Boot 默认类代理就会静默没有事务。异常在方法里被吃掉、没有再抛出，代理不知道失败。默认只对 `RuntimeException` 和 `Error` 回滚，受检异常要写 `rollbackFor`。对象是自己 `new` 出来的，上面没有代理。

统计和事务都要标在被注入的 Bean 的对外方法上。自调用要拆到另一个 Bean，或改走注入进来的代理对象。

### 13. MySQL 联合索引最左匹配原则，范围查询为什么会导致后面字段失效

**参考答案**

联合索引 `(a, b, c)` 先按 `a` 排序，`a` 相同再按 `b`，再按 `c`。最左匹配是从最左列开始连续使用，中间断了，右边的列就不能用来定位。`a = 1 AND b = 2 AND c = 3` 能用三列；`a = 1 AND c = 3` 只用到 `a`；只有 `b = 2` 用不上这个索引。等值条件在 SQL 里的书写顺序不影响，优化器会重排。

`b` 变成范围（`>`、`<`、`BETWEEN`、`LIKE 'abc%'`）时，`b` 自己仍能划定扫描区间，但这个区间里 `c` 不再整体有序，优化器不能继续用 `c` 缩小查找范围。`a` 上的等值不受影响。`a > 1 AND b = 2` 同样只能用 `a`。`c` 可以留在索引叶子里做覆盖扫描，也可以靠索引条件下推在引擎层过滤，那是过滤，不是按 `c` 定位。`LIKE '%abc'` 连它所在的这一列也用不上。

`IN` 常被拆成多个等值，和 `>` 这种范围不同，后面的列仍可能用上。看执行计划时看 `key_len` 和范围访问类型，确认实际用到了第几列。

### 14. Redis 缓存穿透、击穿、雪崩分别怎么解决

**参考答案**

三种故障的数据状态不同，处理也不同。

穿透是查询的数据根本不存在，缓存里永远没有，请求每次都打到数据库。先做参数校验，明显非法的 id 直接拒绝。仍然可能不存在的键，缓存一个短 TTL 的空值，并在真实数据写入时删掉这个空值。布隆过滤器判定不存在就直接返回；判定可能存在才查缓存和数据库。它可能把少量不存在的键放进去，不会把存在的键拦掉。同一个不存在的键在空值写入前的并发，用单飞合并成一次数据库查询。

击穿是一个热点键刚好过期，大量请求同时打到数据库。互斥重建只放一个请求去加载，其他请求等待这次结果或短暂重试，锁和等待都要有超时。热点也可以用逻辑过期：读到旧值先返回，只让一个线程去刷新。

雪崩是大量键在同一时间过期，或 Redis 自身不可用，流量一起打到数据库。过期时间加随机偏移，热点提前预热。缓存前面做限流，数据库前面再留一层兜底限流。应用内可以保留一份短时的本地缓存。Redis 使用带故障转移的部署，同时假定缓存会空，数据库必须扛得住被限流之后的那部分流量。

### 15. 分布式锁用 Redis 怎么保证安全

**参考答案**

加锁用 `SET key token NX PX ttl`。`token` 是持有者独有的随机值，不能写成固定的 `1`。释放时用 Lua 先 `GET`，值等于自己的 `token` 才 `DEL`，避免删掉别人刚拿到的锁。续期同样先比对 `token`。进程停了，续期就停，锁会在租约到期后释放。获取失败要有等待上限，不能空转。

锁过期时原来的持有者可能还在写，新的持有者已经开始写。Redis 锁挡不住这个窗口。拿到锁时对序号键 `INCR`，把这个递增序号带到写请求里；数据库用版本号或唯一约束拒绝过期持有者的提交。主从异步复制时，锁还没同步到新主，故障转移会再把同一把锁发出去。资金和库存以数据库里的条件更新为准，Redis 只负责减少并发冲突。

### 16. Kafka 在 Agent 系统里能承担什么角色，工具回调重复消费怎么保证幂等

**参考答案**

Kafka 承接可以稍后完成的工作：长工具的任务队列、工具完成和人工审批的事件、审计日志，以及突发流量下按消费者能力削峰。对话线程负责把任务落库并投递，记下任务 id。模型这一轮正在等待的短调用仍走同步，不把关键路径放进可能堆积的主题。分区键用会话 id，同一会话的事件按顺序消费。一个会话过热时，热点会落在单个分区上，需要单独看积压。

工具回调按至少一次投递设计，同一条会来多次。以 `tool_call_id` 做幂等键。会话只有处于「等待这个调用」时才接受结果：条件更新成功，才把观察写入上下文并推进回合。第二次投递看到状态已经变了，提交位点后返回，不再请求模型，也不再执行副作用。位点放在数据库更新成功之后。处理前就自动提交，进程崩溃时消息会丢。

生产者幂等只保证单次生产会话里、分区内的写入不重复，约束不了消费端再次处理。有副作用的回调先占住幂等键再执行外部动作。上次超时且结果不明时，先查下游状态或转人工，不盲目再执行一次。超过重试次数进入死信并告警，避免一条坏消息卡住分区。

### 17. 手撕算法：给一段字符串，提取括号内容并判断括号是否合法，LeetCode 1021 变种

**参考答案**

一次扫描做完两件事：深度从未为负且结束时为 0，括号就合法；每个平衡原语去掉最外层那一对圆括号，其余字符原样拼接。这是 1021 的输出，并补上原题假定输入合法、没有做的校验。非法时返回空串，不把扫到一半的结果交给调用方。

只统计 `(` 和 `)`。深度从 0 变为 1 的左括号，以及回到 0 的右括号，是最外层，不写入结果。内层括号和字母保留。`(()())(())` 得到 `()()()`；`a(b(c)d)e(f)` 得到 `ab(c)def`；`()()` 得到空串；`())` 和 `(()` 非法。没有括号的字符串视为合法，结果就是它本身。只剥每个原语的最外层一对，不会把内层括号一起剥掉，`((a))` 的结果是 `(a)`。

字母不需要入栈，计数器够用。时间 O(n)，额外空间 O(1)，输出 O(n)。若改成 `()[]{}` 同时要合法，再用栈核对种类，提取规则保持不变。

```java
final class BracketExtract {
    private BracketExtract() {}

    static final class Result {
        final boolean valid;
        final String content;

        Result(boolean valid, String content) {
            this.valid = valid;
            this.content = content;
        }
    }

    static Result parse(String text) {
        if (text == null) {
            throw new IllegalArgumentException("text is null");
        }
        StringBuilder out = new StringBuilder(text.length());
        int depth = 0;
        for (int i = 0; i < text.length(); i++) {
            char ch = text.charAt(i);
            if (ch == '(') {
                if (depth > 0) {
                    out.append(ch);
                }
                depth++;
            } else if (ch == ')') {
                if (depth == 0) {
                    return new Result(false, "");
                }
                depth--;
                if (depth > 0) {
                    out.append(ch);
                }
            } else {
                out.append(ch);
            }
        }
        if (depth != 0) {
            return new Result(false, "");
        }
        return new Result(true, out.toString());
    }
}
```
