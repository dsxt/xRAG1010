# 11.02 美团Agent Harness二面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 二面

### 1. 自我介绍

**答题思路**

控制在一分钟内，把话题交到你真正写过的那条 Agent 链路上。

1. 先说方向和你实际做过的年限，例如后端、工具执行或运行时。职级、薪资和编制不用报。
2. 只点一个项目：用户要完成什么，你负责编排、工具、上下文还是评测。细节留到下一问。
3. 对齐这个岗位：你处理的是模型循环外面的约束，包括工具能不能调、超时怎么停、失败怎么留下痕迹。
4. 话停在这个项目上，等对方挑一层往下问。

### 2. 挑一个 Agent 项目讲：你负责哪层，Harness 做了什么，线上跑没跑，QPS 和失败率大概多少

**答题思路**

用你真实做过的一个项目，按「边界、你的层、Harness、是否线上、指标口径」讲。没有的数就说没有。

1. 一句话说明谁在用，以及为什么一次问答不够。讲你自己的业务，不换成听起来更大的场景。
2. 链路分成入口、模型循环、工具执行、状态和观测。你写的那层讲到接口和失败行为；别人写的只说边界。
3. Harness 讲循环外的部分：工具契约、参数校验、超时和取消、停止条件、trace。模型负责选择下一步。当时如果没有这层，就说调用散落在业务代码里，以及因此遇到的具体问题。
4. 有真实流量就说入口、服务对象和跑了多久。只在本地或评测集上跑过，就说是评测或演示。
5. QPS 和失败率先定义口径。QPS 是新会话、模型请求还是工具调用；失败是超时、工具报错、被策略拒绝，还是最终答错。有监控就说明时间窗口和量级；没有就说明当时没打这组指标，再讲你怎么从日志里区分这几类。不临时编一个精确数字。

### 3. Agent Harness 和单纯调大模型 API、固定工作流有什么区别，什么场景不该上 Agent

**参考答案**

Harness 是包在模型外面的运行时。直接调 API 没有循环，固定工作流的分支写在代码里，Agent 则由模型根据上一步的观察选择下一步。

直接调 API 是一次请求、一次完成。控制流在调用方，适合分类、抽取、改写和有固定提示的生成。延迟和费用有明确上限。

固定工作流把步骤和分支写成代码，其中几步可以调模型，但模型不决定跳到哪一步。路径已知时它好测试，失败也可以落在确定的步骤上。

Agent 在循环里选择工具或结束。Harness 负责把这个选择变成受约束的执行：拼上下文、校验参数、执行工具、写入观察、按预算停止，并留下 trace。模型不持有权限，也停不掉自己。

路径会随中间结果变化、又没法事先枚举时，才用 Agent。步骤固定的校验、对账和格式转换用工作流。一次调用就能结束的请求直接调 API。延迟或费用不能接受多轮工具调用时，也不要上循环。不可逆动作如果没有独立于模型的审批，同样不该让 Agent 直接执行。

停止条件、权限和预算写在 Harness 里。写进提示词，模型自己可以绕开。

### 4. ReAct 循环里 Agent 一直重复调同一个工具停不下来，怎么检测、拦截、降级

**参考答案**

空转要在执行前由 Harness 发现并拒绝。模型自己「再想一次」停不住。

同一次运行里记录工具名，以及参数规范化之后的哈希。JSON 先按键排序、去掉无意义空白再哈希，否则键顺序不同会绕过检测。连续两次参数相同就拦截。结果哈希也相同，说明观察没有变化。两个工具交替出现，单工具计数看不出来，再对最近若干步的工具名序列做重复检测。

分页和轮询可以合法地重复调用。放行条件是游标、offset 或时间窗口确实在变，并且结果里出现了新的标识。另外设最大步数、总时间和费用上限，用来拦住「每次把查询改一个字」的空转。

拦截时这一次不执行。把上次的参数和结果摘要写回观察，要求换工具或结束。

降级分两步。先从本轮可用工具里拿掉它，再给模型一次机会。仍然空转，就用已经拿到的观察做一次直接回答，并标明没有做完，或者交给人。已经成功的写操作在降级路径上不能再执行一遍。

### 5. 大模型返回的工具调用 JSON 解析失败或参数非法，后端怎么校验、重试、兜底

**参考答案**

解析失败和参数非法都发生在执行之前。这两种情况都不会打到下游。

工具参数常常是字符串里的一段 JSON，要先解出这一层，再解析对象。外面若包了一层 Markdown 代码围栏，只剥一次。解析用严格的 JSON 解析器，拒绝尾部多余内容。解析之后用该工具该版本的 JSON Schema 校验类型、必填、枚举和范围，并拒绝未声明的字段。Schema 通过后做业务校验：订单是否属于当前用户、金额是否在额度内。缺了用户或金额时直接失败，服务端不补默认用户，也不补默认金额。

重试的是模型，不是同一次非法调用。把解析错误或字段错误写回观察，最多再给一到两次修正机会。参数错误再试不会变好，所以业务校验失败通常直接结束这一步。修正后的参数要重新走 Schema 和业务校验。

可选工具失败时，用已经拿到的上下文继续。必选工具失败时，这一步返回明确错误，任务停在可见的失败状态。提供商若支持结构化输出或工具调用协议，可以减少语法错误，但不能代替服务端校验。

### 6. Function Calling 工具注册中心怎么设计：Schema、权限、超时、幂等、审计日志

**参考答案**

注册中心存的是可执行契约。模型只能看见自己有权调用的那一部分，校验和审计在执行闸门完成。

每条工具包含名字、版本、描述、参数 JSON Schema、读写级别、超时、能否重试、幂等键取哪些字段、所需权限、负责人和是否启用。Schema 拒绝未声明字段。契约变更新增一个版本，旧的 trace 仍对得上当时的 Schema。启动时从 Bean 或配置装载，名字加版本必须唯一，Schema 不合法就拒绝启动。

权限用登录态里的用户和租户判断。下发给模型的工具列表先按权限过滤，执行前再查一次。模型在参数或正文里声称自己有权限，闸门不采信。

超时写在契约上，由调度器取消，并回一条超时观察。读工具可以按策略重试。写工具必须能算出幂等键；执行前用这个键占用一条记录，重复调用返回第一次的结果。

审计每次追加一条：traceId、用户、工具版本、脱敏后的参数、允许或拒绝、耗时和错误码。密钥和完整证件号不进日志。这条日志不提供更新和删除。

### 7. 多轮对话上下文怎么管：短期上下文截断压缩、长期记忆存储、并发会话隔离

**参考答案**

短期上下文是这一次任务的工作记忆，受 token 预算约束。长期记忆是跨会话抽出的少量事实。并发上，不同会话互不可写，同一会话同时只进一轮。

短期上下文留下系统提示、当前目标和最近几轮原文。更早的对话收成结构化摘要：目标、约束、已确认的事实、未完成的步骤。按 token 预算触发，不按固定轮数一刀切。数字、否定词和还要用的工具结果放在单独槽位里，摘要盖不住它们。摘要增量更新，避免每轮把全部历史再送去总结一次。

一轮结束后，异步抽取可以跨会话使用的偏好和实体，按用户和租户写入数据库；需要语义召回的再进向量库。下一轮只取回和当前问题相关的几条。订单、余额、库存以业务库为准。用户可以删除自己的记忆，敏感内容默认不写进去。

所有键带 tenantId 和 sessionId。同一会话的并发请求用版本号或一把短锁串行，第二个请求等待，或被告知这一轮还在进行。这把锁只包状态的读写，不包模型调用。

### 8. Java 线程池在 Agent 并发调工具场景怎么配：核心参数、异步编排、超时与拒绝策略

**参考答案**

线程池限制的是同时打出去多少调用。任务超时不是 `ThreadPoolExecutor` 的构造参数，取消也不是。队列必须有界。

工具调用主要阻塞在网络上。池大小按下游承受得住的在途数来定，不按 CPU 核数套一个固定倍数。JDK 21 起可以用虚拟线程承接阻塞调用，再用按工具划分的信号量卡住下游并发。核心线程数等于最大线程数，再加一个较短的有界队列，就是一组固定舱壁。核心数小于最大数且队列无界时，队列不会满，最大线程数不会生效。模型和工具分池，读工具和写工具也分开，慢的一侧占不满另一侧的线程。

彼此无关的只读工具用 `CompletableFuture` 并行，有依赖的串行，写操作不并行。每个调用有自己的截止时间。`Future.get` 超时和 `orTimeout` 都只结束等待；要停掉任务，还要 `cancel(true)`，并且 HTTP 客户端设置连接超时和读超时。中断停不掉不可中断的阻塞。

队列满了用 `AbortPolicy`，把拒绝记成这一步失败。`CallerRunsPolicy` 会把工具丢回提交线程；提交线程如果正在等这个池，工作会堵在自己身上。池满是过载，Harness 不要立刻让模型再调一次同一个工具，否则重试会把池打得更满。

### 9. synchronized 和 ReentrantLock 区别，锁升级过程，高并发工具执行怎么避免锁竞争

**参考答案**

两者都可重入。`synchronized` 锁的是对象监视器，由 JVM 成对进入和退出，方法抛异常也会释放。`ReentrantLock` 锁的是 AQS 上的 state，必须在 `finally` 里 `unlock`。

`synchronized` 竞争失败时只能一直等。`ReentrantLock` 默认的 `lock` 也要等到拿到，但另外提供 `tryLock(超时)` 和 `lockInterruptibly`，等待可以放弃。它可以做成公平锁，也能挂多个 `Condition`。默认是非公平锁。即便锁是公平的，无参 `tryLock()` 仍会在锁空闲时直接拿到。

锁升级指的是 HotSpot 里 `synchronized` 的 Mark Word，不是 `ReentrantLock`。当前 JDK 无竞争时，线程用 CAS 把 Mark Word 指到自己栈上的锁记录，这是轻量级锁；同一线程重入只增加锁记录里的计数。CAS 失败表示有竞争，锁膨胀成 `ObjectMonitor`，线程进入队列并 park，这是重量级锁。`wait` 和 `notify` 也会膨胀。JDK 15 之前，第一次加锁会先写成偏向锁，出现竞争再撤销偏向并升到轻量级。偏向锁从 JDK 15 起默认关闭，JDK 18 已移除。空闲的重量级监视器可以被虚拟机异步撤销，业务不能假设解锁后下一次仍是轻量级。

高并发的工具执行不用互斥锁包住远程调用。在途数由有界线程池和按工具划分的信号量限制。需要互斥的是会话状态那几行内存，按 session 分段加锁，或用 `ConcurrentHashMap` 做局部更新。计数用 `LongAdder`。JDK 21 到 23 里，虚拟线程在 `synchronized` 中阻塞会钉住载体线程，等待 `ReentrantLock` 时可以卸下；JDK 24 起这种钉住已经消除。工具调用要超时和取消时，仍用可超时的锁或信号量。

### 10. Spring 里工具执行器怎么注册和生命周期管理，AOP 怎么埋点统计每次 Agent 调用耗时与成功率

**参考答案**

工具执行器做成接口，声明名字、版本、Schema 和 `execute`。实现类是单例 Bean。注册中心用构造器注入 `List<ToolExecutor>`，启动时检查重名和 Schema，有问题就让应用起不来。HTTP 客户端跟 Bean 一起创建，随 Bean 销毁而关闭。请求级的上下文放在方法参数里，不放进单例字段。

停机用 `SmartLifecycle`。`stop` 时先拒绝新调用，再等待在途调用结束，到点之后无论如何都要执行停机回调，否则 Spring 关闭会停在这里。`@PreDestroy` 只适合关闭客户端，它不会等在途的 Agent 步骤。

每次 Agent 调用的耗时和成功率切在运行时入口上，用 Micrometer 的 `Timer` 包住入口方法。正常返回且业务状态是完成，记 success；返回失败状态记 failure；未捕获异常记 error，记录之后把异常抛回去。技术成功率是这三档里 success 的比例。用户觉得答错了，那是评测，不进这组指标。

工具名可以做第二组 Timer 的标签，因为工具集合有界。用户 id、会话 id 放进日志和 trace，不放进指标标签。同一个类内部自己调用自己的方法不经过代理，切面不会生效，所以统计放在对外的入口 Bean 上。入口把异常吃成失败对象时，切面要读返回值里的状态，否则成功率会一直是百分之百。

### 11. Redis 在 Agent 系统里能承担什么：会话状态、限流、工具结果缓存、分布式锁，缓存击穿怎么防

**参考答案**

Redis 放热数据。对话原文、审计和任务流水以 MySQL 为准，Redis 丢失后要能从数据库恢复最近状态。

会话状态放当前窗口的指针、滚动摘要和这一轮是否还在进行，键里带租户和会话，并设置 TTL。消息很多时一条 String 会变成大 key，窗口用 List 或 Stream 按条存放，并只保留最近一段。

限流按用户、租户和工具做。固定窗口是 `INCR` 加过期时间，实现简单，窗口边界会叠成两倍流量。滑动窗口或令牌桶用一段 Lua 把读取和扣减做成原子操作。

工具结果只缓存成功的、可重试的读。键包含租户、工具版本和规范化参数，TTL 要短。写操作和带权限的个性化数据不进这层缓存。

分布式锁用 `SET key token NX PX` 占用，释放时用 Lua 比较 token 再删除，避免删掉别人的锁。锁只包「同一会话同时只进一轮」这种短临界区，不包整次模型调用。锁过期而业务还在跑时，第二个请求会进来。看门狗只在持有进程还活着时续期。资金这类写入要让下游拒绝过期的 fencing token，单靠 Redis 锁不够。

热点 key 过期的那一刻，并发请求一起打到数据库上，这是击穿。一个请求用单独的互斥键去回源，其他请求短等后再读缓存。也可以不设硬过期，值里写逻辑过期时间，由一个请求异步刷新，其余请求继续用旧值。查询的数据根本不存在，每次都穿过缓存，那是穿透，用空结果的短 TTL 或布隆过滤器挡住。大量 key 同时失效是雪崩，过期时间要错开。

### 12. Kafka 在 Agent 任务里怎么用：异步化、事件驱动、失败重试、削峰，重复消费怎么保证幂等

**参考答案**

耗时的 Agent 运行从请求线程里拿掉：接口收下任务并返回任务 id，循环放到消费者里跑。一步完成、人审批通过、工具结束，都写成事件，由下一阶段接着处理。数据库和消息要同时成功时，用事务外盒，避免库回滚了消息已经发出去。

分区键用 sessionId，同一会话按顺序处理。消费线程拿到消息后交给工作池，处理完再提交 offset。整段循环若占着 poll 线程，处理时间超过 `max.poll.interval.ms` 会触发再均衡，这条消息会被另一个消费者再执行。

失败进带退避的重试主题，超过次数进死信。在原分区里 sleep 再试，会堵住后面的会话。

突发流量堆在 topic 里。消费者的并发对齐模型和下游配额，而不是对齐分区数。

至少一次投递下，重复消费是正常现象。生产者开启幂等，只收紧生产者重试造成的重复写入。消费者可能已经执行了副作用，offset 还没提交。写工具使用 taskId 加 step 作为幂等键，数据库用这个键做主键；重复消息直接返回上一次的结果。Kafka 事务保证不了外部 HTTP 只发生一次。

### 13. MySQL 怎么存对话、任务、工具调用 trace，怎么建表、建索引、做分区和审计查询

**参考答案**

按会话读的表和按时间归档的表分开。字符集用 `utf8mb4`。要过滤的字段做成普通列，参数正文不拿来做索引。

`conversation` 存租户、用户、状态和时间，索引是 `(tenant_id, user_id, created_at)`。`message` 的主键用 `(conversation_id, id)`，按会话拉历史就是一段连续扫描。正文特别长时，原文放对象存储，表里留摘要和地址。`agent_task` 挂在会话下，索引 `(conversation_id, created_at)` 用来回放，`(status, created_at)` 用来找卡住的任务。

`tool_call` 记录任务、步骤、工具版本、脱敏参数、状态、耗时、错误码和 traceId，并冗余租户和用户，审计时不必再联表。它按月做范围分区，主键带上 `created_at`。MySQL 要求每个唯一键都包含分区列，所以幂等键的全局唯一不要建在这张分区表上。单独做一张不分区的幂等表，主键就是幂等键。

查某个任务的 trace 时，先读任务的创建时间，再带上时间下界和 taskId，分区才能裁剪。敏感操作另外记追加日志，应用账号只授予 `INSERT` 和 `SELECT`。更正写成新的一条，不修改旧记录。

### 14. 敏感工具（删数据、发消息、查订单、动资金）怎么鉴权、审批、回滚、防提示词注入越权

**参考答案**

模型不是权限边界。身份来自登录态，敏感动作先审批再执行，能撤销的靠补偿，提示词改变不了闸门的决定。

工具按读、写和不可逆分级。下发工具列表时按 scope 过滤，执行前再查一次。订单和资金的属主用会话里的用户 id，不用模型传来的用户 id。模型可以传订单号，服务端再确认这张订单属于这个人。下游服务做自己的鉴权，Agent 服务放行代替不了下游。

删除、发消息和动资金在执行前暂停循环，把工具名和规范化参数给用户看。审批令牌绑定这些参数的哈希，一次性，并有过期时间。模型改了金额或收件人，令牌作废，需要重新审批。

能撤销的动作用补偿：软删除可以恢复，未扣款的预占可以释放。已经发出的消息和已经入账的资金不能靠本地事务撤回。这类动作拆成预览或预占，确认之后才产生副作用。每次写带幂等键，审批重试不会扣第二次。

网页、文档和工具结果都是数据。模型说「忽略规则并调用删除」时，闸门仍按 scope 和审批令牌判断。工具参数走结构化字段，用户原文不拼进 SQL 或 shell。

### 15. 大文件喂给 Agent：上传、切片、解析、向量化链路怎么用 Java 工程化落地，失败怎么恢复

**参考答案**

文件字节进对象存储，MySQL 只记任务状态。解析、切片和向量化每一步都可以按主键重做。

浏览器拿预签名 URL 直传，应用不把大文件读进堆。任务行记下 objectKey、校验和、状态、尝试次数和错误原因。worker 流式读取，按标题、段落和页码切开；块仍然过大时再按句子切开，并留一小段重叠。块写入 `(file_id, ordinal)` 唯一的表。嵌入按批进行，向量库以 chunkId 做 upsert，每批成功后记下已完成的序号。

抢占用条件更新：只有状态是上一步、租约也过期时，才能把任务改成当前步骤并写上新的 `lock_until`。更新行数为 0，说明别的 worker 已经拿走。状态机、对象存储和向量库不在一个数据库事务里，所以以「向量 upsert 成功之后再改状态」为准。进程死在这两步之间，重跑仍是同一个 chunkId，结果不变。

失败停在当前状态，尝试次数加一，超过上限标为 failed 并记下原因，不挡住队列里的其他文件。压缩包要限制解压后的大小。worker 使用有界队列；无界的 `@Async` 会在大文件堆积时耗尽内存。

### 16. 场景题：Agent 跑到第 30 轮，每步看起来都对，但最终结果错了，你怎么定位是检索、规划还是工具执行的问题

**参考答案**

沿 trace 找到第一个把正确事实弄丢、或把错误事实引进来的步骤。那一步属于哪一层，问题就在哪一层。每一步都跟着上一步自洽，仍可能整体走错。

先固定这一次运行的记录：每步的目标、工具名、参数、下游原始结果，以及写回上下文的文本。从最终错误的事实往回找它第一次出现的位置。

正确段落从未出现在召回列表里，或出现后被过滤条件和截断丢掉，问题在检索。列表里已经有这段证据，就先不改检索。

证据已经在上下文里，下一步却换了目标、漏了约束，或在中途摘要里弄丢了数字和否定词，问题在规划或上下文压缩。30 轮任务的摘要是常见断点。对照的是最初目标和当前观察，不是模型对上一步的解释是否通顺。

工具选对了，但参数错、下游报错被当成正文、缓存是旧的、租户串了，或者 Harness 改写了结果，问题在执行。把模型给出的参数、下游原始响应和写回模型的文本三份对齐。

在出错前的那一步做单步重放。把正确证据放回上下文后，下一步变了，问题在检索或上下文；下一步不变，问题在规划；下一步的计划是对的，但下游结果和写回文本不一致，问题在执行。

### 17. 场景题：Agent 调用链突然 RT 升高，线程池打满，怎么及时止损和排查

**参考答案**

先减少新的在途调用，再区分线程是在排队，还是卡在某一次工具调用里。

入口拒绝新的 Agent 运行，让调用方稍后重试，不再往已满的池里塞。已经超过截止时间的在途调用执行取消；取消不了的，靠客户端读超时把线程还回来。已经变慢的工具打开熔断，只读工具可以这一次不用。后台任务和在线循环使用不同的池，先停后台。下游超时时，把并发降到它还能承受的数量；此时加机器，只会多打开连接。

然后看池的 active、queue、rejected，以及任务从入队到开始执行的等待时间。等待时间上涨，是池满了；执行时间上涨，是工具本身变慢。线程 dump 先分清是工具池、Web 容器还是数据库连接池，再看线程停在 HTTP、锁还是数据库。按工具名对照耗时、错误率和最近的发布，并看重试次数有没有放大。缓存同时失效也会让读工具突然全部回源。

过载错误不能再自动重试。Agent 如果跑在 Kafka 的 poll 线程里，先停消费，避免再均衡之后把同一批任务再跑一遍。

### 18. 手撕算法：实现一个简化版 Agent 工具调度器，支持注册工具、按名执行、超时中断、失败重试、调用记录（可先朴素实现，再优化为线程池异步版）

**参考答案**

调度器做五件事：按名字注册，按名字执行，到点中断，只有暂时失败才重试，每次尝试留下记录。

朴素版每次新开一条线程，调用方 `join` 到超时，超时就 `interrupt`。它能把语义跑通，但线程数随重叠调用增长。超时后的那条线程可能还没停，下一次重试已经发出。

线程池版把执行放进固定大小、队列有界的池，调用方用 `Future.get(超时)` 等待，超时后 `cancel(true)`。`submit` 把等待和重试放到另一组线程上，Agent 循环就可以同时发出几个只读工具。等待如果也提交进同一个有界池，工作线程会全堵在 `get` 上，真正的工具任务进不去。

`cancel(true)` 只是给执行线程一个中断。工具卡在不可中断的 IO 上时，池线程仍然占着。HTTP 客户端要有自己的读超时。超时后的重试可能和尚未退出的那一次重叠，写操作要使用同一个幂等键。参数错误不重试。同一个工具可能被并发执行，工具实现自己要能并发；调度器不用一把全局锁把所有会话串起来。

注册平均 O(1)。一次调用最多尝试 `maxAttempts` 次，调度开销 O(次数)，墙钟时间不超过次数乘以超时，再加上工具还没响应中断的那段。空间是工具表加上每条调用记录。池化之后，工作线程数是池大小。

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.Callable;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentLinkedQueue;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Future;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ThreadFactory;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.concurrent.atomic.AtomicInteger;

public final class AgentToolScheduler implements AutoCloseable {

    public interface Tool {
        String name();

        String execute(String args) throws Exception;
    }

    /** 下游暂时不可用。参数非法抛 IllegalArgumentException，不重试。 */
    public static final class RetryableException extends Exception {
        public RetryableException(String message) {
            super(message);
        }
    }

    public record CallRecord(
            String tool,
            String args,
            boolean success,
            String result,
            long costMs,
            int attempts,
            String error) {
    }

    private final ConcurrentHashMap<String, Tool> tools = new ConcurrentHashMap<>();
    private final ConcurrentLinkedQueue<CallRecord> records = new ConcurrentLinkedQueue<>();
    private final ExecutorService workers;
    private final ExecutorService waiters;

    public AgentToolScheduler(int poolSize, int queueCapacity) {
        if (poolSize < 1 || queueCapacity < 1) {
            throw new IllegalArgumentException("poolSize and queueCapacity must be positive");
        }
        this.workers = newPool(poolSize, queueCapacity, "agent-tool");
        this.waiters = newPool(poolSize, queueCapacity, "agent-tool-wait");
    }

    public void register(Tool tool) {
        Tool previous = tools.putIfAbsent(tool.name(), tool);
        if (previous != null) {
            throw new IllegalStateException("duplicate tool: " + tool.name());
        }
    }

    /** 朴素版：每次新建线程，join 超时后 interrupt。 */
    public CallRecord executeNaive(String name, String args, long timeoutMs, int maxAttempts) {
        requirePositive(timeoutMs, maxAttempts);
        Tool tool = tools.get(name);
        if (tool == null) {
            return finish(name, args, false, null, 0, 0, "tool not found");
        }
        long start = System.nanoTime();
        CallRecord last = null;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            NaiveAttempt running = new NaiveAttempt(tool, args);
            Thread thread = new Thread(running, "agent-tool-naive");
            thread.start();
            try {
                thread.join(timeoutMs);
            } catch (InterruptedException interrupted) {
                thread.interrupt();
                Thread.currentThread().interrupt();
                return finish(name, args, false, null, millis(start), attempt, "caller interrupted");
            }
            if (thread.isAlive()) {
                thread.interrupt();
                last = finish(name, args, false, null, millis(start), attempt, "timeout");
                continue;
            }
            if (!running.finished || running.error != null) {
                Throwable cause = running.error == null
                        ? new IllegalStateException("tool crashed")
                        : running.error;
                last = finish(name, args, false, null, millis(start), attempt, messageOf(cause));
                if (!retryable(cause)) {
                    return last;
                }
                continue;
            }
            return finish(name, args, true, running.result, millis(start), attempt, null);
        }
        if (last == null) {
            throw new IllegalStateException("no attempt");
        }
        return last;
    }

    /** 线程池版：工具在 workers 中执行，当前线程只等待到超时。 */
    public CallRecord execute(String name, String args, long timeoutMs, int maxAttempts) {
        requirePositive(timeoutMs, maxAttempts);
        Tool tool = tools.get(name);
        if (tool == null) {
            return finish(name, args, false, null, 0, 0, "tool not found");
        }
        long start = System.nanoTime();
        CallRecord last = null;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            Future<String> future;
            try {
                future = workers.submit((Callable<String>) (() -> tool.execute(args)));
            } catch (RejectedExecutionException rejected) {
                return finish(name, args, false, null, millis(start), attempt, "pool rejected");
            }
            try {
                String value = future.get(timeoutMs, TimeUnit.MILLISECONDS);
                return finish(name, args, true, value, millis(start), attempt, null);
            } catch (TimeoutException timeout) {
                future.cancel(true);
                last = finish(name, args, false, null, millis(start), attempt, "timeout");
            } catch (ExecutionException execution) {
                Throwable cause = execution.getCause() == null ? execution : execution.getCause();
                last = finish(name, args, false, null, millis(start), attempt, messageOf(cause));
                if (!retryable(cause)) {
                    return last;
                }
            } catch (InterruptedException interrupted) {
                future.cancel(true);
                Thread.currentThread().interrupt();
                return finish(name, args, false, null, millis(start), attempt, "caller interrupted");
            }
        }
        if (last == null) {
            throw new IllegalStateException("no attempt");
        }
        return last;
    }

    /**
     * 异步版。等待和重试占用 waiters，不占用 workers。
     * 工具失败写进 CallRecord，Future 正常完成。
     */
    public CompletableFuture<CallRecord> submit(String name, String args, long timeoutMs, int maxAttempts) {
        try {
            return CompletableFuture.supplyAsync(
                    () -> execute(name, args, timeoutMs, maxAttempts), waiters);
        } catch (RejectedExecutionException rejected) {
            CallRecord record = finish(name, args, false, null, 0, 0, "waiter rejected");
            return CompletableFuture.completedFuture(record);
        }
    }

    public List<CallRecord> records() {
        return new ArrayList<>(records);
    }

    @Override
    public void close() {
        waiters.shutdown();
        workers.shutdown();
    }

    private static ExecutorService newPool(int poolSize, int queueCapacity, String prefix) {
        return new ThreadPoolExecutor(
                poolSize,
                poolSize,
                0L,
                TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(queueCapacity),
                named(prefix),
                new ThreadPoolExecutor.AbortPolicy());
    }

    private CallRecord finish(
            String name,
            String args,
            boolean success,
            String result,
            long costMs,
            int attempts,
            String error) {
        CallRecord record = new CallRecord(name, args, success, result, costMs, attempts, error);
        records.add(record);
        return record;
    }

    private static void requirePositive(long timeoutMs, int maxAttempts) {
        if (timeoutMs <= 0 || maxAttempts < 1) {
            throw new IllegalArgumentException("timeoutMs and maxAttempts must be positive");
        }
    }

    private static boolean retryable(Throwable error) {
        return error instanceof RetryableException
                || error instanceof TimeoutException
                || error instanceof InterruptedException;
    }

    private static String messageOf(Throwable error) {
        return error.getMessage() == null ? error.getClass().getSimpleName() : error.getMessage();
    }

    private static long millis(long startNano) {
        return TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startNano);
    }

    private static ThreadFactory named(String prefix) {
        AtomicInteger sequence = new AtomicInteger();
        return runnable -> {
            Thread thread = new Thread(runnable, prefix + "-" + sequence.incrementAndGet());
            thread.setDaemon(false);
            return thread;
        };
    }

    private static final class NaiveAttempt implements Runnable {
        private final Tool tool;
        private final String args;
        private volatile String result;
        private volatile Exception error;
        private volatile boolean finished;

        private NaiveAttempt(Tool tool, String args) {
            this.tool = tool;
            this.args = args;
        }

        @Override
        public void run() {
            try {
                result = tool.execute(args);
                finished = true;
            } catch (Exception failure) {
                error = failure;
                finished = true;
            }
        }
    }
}
```
