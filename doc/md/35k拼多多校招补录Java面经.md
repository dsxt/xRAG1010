### 3. 高并发下单系统如何防止超卖？

**参考答案**

超卖是两个订单都通过了「还有库存」的检查，最后卖出的数量大于库存。要防的是检查和扣减之间的空档，不是再加一把大锁。

数据库用一条条件更新做最后裁决。库存行以 SKU 为主键或唯一索引，否则可能锁住大范围：

```sql
UPDATE stock
SET available = available - #{qty}
WHERE sku_id = #{skuId}
  AND available >= #{qty};
```

影响行数是 1 才算扣到。InnoDB 会锁住这行，后到的更新等锁释放后重新判断条件。先 `SELECT` 再在应用里扣，两次都会读到有货。

同一订单因超时重试被扣两次，减的是库存、不是超卖。扣减流水对订单号加 SKU 建唯一约束，和库存更新放在同一个本地事务里。冲突时返回上一次的结果。

热点商品不要让所有请求都打到这一行。Redis 用 Lua 一次做完判断和扣减，失败立刻返回；成功后再走数据库。数据库失败要把预扣补回，补回必须认这同一笔订单的状态，不能无条件 `INCR`。Redis 里的数字只是闸门，不能代替上面的条件更新。

分布式锁把所有请求串到一把锁上，吞吐更差。锁过期时前一个请求还在扣，仍可能超卖。未支付占用库存是另一件事，用延迟消息释放，释放也要幂等。

### 4. Redis 在你们系统中主要解决了什么问题？

**答题思路**

只讲你项目里真实用过的一两处，不要把 Redis 的功能表背完。

1. 先说业务问题：读放大、重复提交、计数还是限流。
2. 再说为什么不是数据库硬抗，也不是进程内 Map：多实例、要过期，或者要原子操作。
3. 落到结构和 key：详情用 String 或 Hash，排名用 ZSet。说明过期时间由谁设置。
4. 补一致性：数据以数据库还是 Redis 为准，更新时删缓存还是改缓存，Redis 挂了是失败还是回源。没做的就说没做。

如果只用过缓存，不要再编一把分布式锁。面试官会问锁过期和误删。

### 5. Redis 缓存穿透和缓存雪崩的解决方案

**参考答案**

穿透是在查一个本来就不存在的数据。缓存没有，每次都打到数据库。先校验明显非法的参数；再把空值缓存一小段时间；也可以用布隆过滤器，它说不存在就可以直接返回，说存在仍要查缓存和数据库。空值缓存要在数据真正插入时删掉，否则短时间内还会查到空。

雪崩是大量 key 同时失效，或者 Redis 本身不可用，流量一起打到数据库。过期时间加随机值，只解决「一起过期」。Redis 宕机要靠限流、降级和热点的本地缓存，而不是把所有接口都放行去回源。

另一个容易混进去的是击穿：一个热点 key 过期的瞬间被并发打穿。处理是互斥重建，或逻辑过期后由单个线程刷新。它不是穿透，也不是雪崩。

### 6. 如果 Redis 集群某个节点挂了，数据如何恢复？

**参考答案**

先看挂的是主还是从，以及这份数据是缓存还是事实来源。故障转移恢复的是服务，不是每一笔还没复制出去的写。

从节点挂了，主节点继续服务，集群再补一个副本。主节点挂了，复制偏移更靠前的从节点优先发起选举，得到多数主节点同意后，接管它负责的槽。客户端收到 `MOVED` 后更新槽位表。默认情况下，和主节点失联太久的从节点不会被提升。旧节点带着磁盘回来，不会把旧数据合并回去，而是同步新主：积压还在就部分同步，追不上就全量同步。

复制是异步的。已经返回成功但还没到从节点的写，转移后会丢。没有从节点就不会自动转移，只能靠这块盘上的 AOF 或 RDB 重启；盘也没了，这个分片就没了。

缓存丢了可以从数据库回源，同时限流，避免所有请求一起重建。库存、锁这类状态不能指望缓存自己变热，要从扣减流水或订单对账重放。

### 7. MySQL 索引失效的常见场景

**参考答案**

多数失效是索引列没有按原样参与查找。还有一种是索引可用，但优化器认为全表扫描更便宜。

1. 对索引列做函数、运算，或把转换放在列上。字符串列和数字比较时，转换发生在列上，索引用不上。数字列和数字字符串比较，通常转的是常量，索引仍可以用。
2. `LIKE '%xx'` 不能用普通索引定位。`LIKE 'xx%'` 可以。
3. 联合索引没有带上最左列。出现范围条件后，它右边的列不能再缩小扫描范围。
4. `OR` 一边没有可用索引时，经常整句都不走索引；有时会走 index merge，不能说成绝对不走。
5. 要回表的行太多时，优化器会选全表扫描。索引还在，只是这次没被选中。

`IS NULL` 和 `!=` 不是必然失效。用执行计划确认，不要背口诀。

### 8. 为什么使用 B+ 树而不是 B 树做索引？

**参考答案**

这里的 B 树是经典 B-tree：数据可以放在任意节点。B+ 树只在叶子放数据，非叶节点只有键和子页指针，叶子之间再用链表连起来。

InnoDB 按页读，常见页是 16KB。非叶节点越瘦，一页能装的键越多，树越矮，定位一行的随机读越少。范围查询沿着叶子链表顺序读。经典 B 树的内部节点也放数据，同样的页能装的键更少，范围查询还要在树里上下跳。

InnoDB 的聚簇索引把整行放在叶子里，二级索引的叶子放主键，再回表。这是 B+ 树叶子存数据的用法。

二叉树按单个键分支，树太高，也不按页装数据。哈希索引只能等值查找，不能做范围和排序。

### 9. 订单表数据量过大如何分库分表？

**参考答案**

先确认单表已经过了归档、按时间分区、补索引和读写分离能解决的程度。分库解决的是容量和写热点，同时会失去跨分片事务和普通分页。

用户查自己的订单是主路径，分片键用 `user_id`。订单号里带上分片位，详情查询就能定位到一个库；做不到改号时，再用一张订单号到用户的路由，不要按订单号广播。订单明细使用同一个分片键，避免跨库连接。

订单号必须全局唯一，不能拿各库的自增主键对外。逻辑分片数一开始留够，再映射到较少的物理库。扩容时搬一部分逻辑分片。按 `user_id % 当前库数` 取模，一扩容就要搬几乎所有数据。

单笔订单的写入停在一个分片里，不做跨分片事务。运营按状态、时间的查询走搜索或离线库。用户自己的分页在单分片内完成，禁止对所有分片做深分页再合并。

### 10. Kafka 如何保证消息不丢失？

**参考答案**

这里的不丢是至少送达一次。生产者、Broker、消费者都要确认成功，消费者还要能接受重复。

生产者使用 `acks=all`，失败要重试，并处理回调里的最终失败。Kafka 3.0 起官方客户端默认就是 `acks=all` 且开启幂等；更早的客户端默认 `acks=1`，领导者还没复制出去就可能返回成功，随后宕机会丢。幂等消除的是重试带来的重复，不是丢失。没开幂等时，重试加上多个未完成请求，还会打乱分区内顺序。

副本数至少 3，`min.insync.replicas` 设为 2。`acks=all` 只等当前同步副本集合（ISR）；里面如果只剩领导者，仍然只写了一份。不满足最小同步副本时，生产者应该得到失败。不要让明显落后的副本当选领导者，否则已确认的数据会被截断。

消费者关掉自动提交，处理成功后再提交位移。先提交再处理，崩溃后这条消息不会再来。重复投递用业务唯一键挡住。这不是精确一次；精确一次还要生产者事务，并且消费者只读已提交的消息，不是把 `acks` 调大就有。进程退出前没发完的缓冲区也会丢，发送后要等待回调或关闭生产者。

### 11. RocketMQ 和 Kafka 的区别

**参考答案**

Kafka 是可以回放的提交日志，适合大流量流水。RocketMQ 面向业务消息，事务、延迟和失败重试是现成能力。

两边都按分区或队列保存顺序，消费组各自记进度，消费完也不删消息，客户端都是拉取。RocketMQ 的推模式底层仍是长轮询。

差别在语义。RocketMQ 事务消息先放半消息，本地事务成功后再提交，Broker 会回查本地事务，用来避免「数据库写了，消息没发出去」。Kafka 的事务是把多次发送和消费位移一起提交，不是这个模型。延迟消息在 RocketMQ 4 是固定档位，RocketMQ 5 可以指定投递时间；Kafka 没有内置延迟，要自己做定时或延迟主题。消费失败时 RocketMQ 会重试并进入死信队列，Kafka 要应用自己做重试主题。

Kafka 用批量、页缓存和顺序写承担日志更常见。RocketMQ 可以在服务端按 Tag 过滤，Kafka 一般在消费端过滤。按要不要事务消息和延迟消息来选。

### 12. 手写算法：实现一个 LRU 缓存

**参考答案**

用哈希表定位节点，用双向链表维护使用顺序。刚访问的放在表头一侧，淘汰表尾。`get` 和 `put` 都是均摊 O(1)，空间 O(容量)。

已有的 key 只更新值和位置，不增加容量。超过容量时，先从链表摘掉最久未使用的节点，再按节点里保存的 key 删哈希表。哨兵头尾可以少写空指针。下面按常见题意，不存在时 `get` 返回 -1。它不是线程安全的。

```java
import java.util.HashMap;
import java.util.Map;

public class LruCache {
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LruCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addToHead(created);
        if (map.size() > capacity) {
            Node removed = tail.prev;
            unlink(removed);
            map.remove(removed.key);
        }
    }

    private void moveToHead(Node node) {
        unlink(node);
        addToHead(node);
    }

    private void addToHead(Node node) {
        node.next = head.next;
        node.prev = head;
        head.next.prev = node;
        head.next = node;
    }

    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private static final class Node {
        private final int key;
        private int value;
        private Node prev;
        private Node next;

        private Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }
}
```

JDK 里可以用 `LinkedHashMap`：打开访问顺序，并在超过容量时删掉最老的元素。默认是插入顺序，也不会自动淘汰，那不是 LRU。生产缓存很少用纯 LRU，扫描一遍就会把热点冲掉；Caffeine 这类实现会同时看访问频率。

### 13. 谈谈你对微服务架构的理解

**参考答案**

微服务按业务能力拆成能独立部署的服务。每个服务只写自己的数据，通过接口或消息协作，不共享一个数据库。

换来的是单独发布和扩容，付出的是网络失败、跨服务一致性、链路排查和测试成本。边界看业务是否一起变化，不要按控制器、服务类、数据访问层拆成三个服务。

没有超时、监控和追踪时，拆开只会让故障更难查。流量和团队都还小的时候，把模块边界划清的单体更合适。校招项目不必为了架构名词拆成很多个服务。

### 14. 服务发现和负载均衡的实现原理

**参考答案**

服务发现解决「现在有哪些实例」，负载均衡解决「这次选哪一个」。注册中心本身不是负载均衡器。

实例启动时把地址、端口和元数据注册上去，用心跳或租约续期，停止心跳后被摘掉。调用方把实例列表缓存在本地，注册中心用推送或定时拉取更新。注册中心短时间不可用时，还可以用上次的列表发起调用。

选实例有两种位置。调用方自己选，是客户端负载均衡，例如注册中心加 Spring Cloud LoadBalancer，Dubbo 也是这种。调用方只访问一个固定地址，由网关、Nginx 或 Kubernetes Service 转发，是服务端负载均衡。

策略上，Dubbo 默认加权随机，Spring Cloud LoadBalancer 默认轮询。还有最少连接、一致性哈希。轮询不管实例已经多慢。连续失败的实例要先在本地摘掉，等注册中心过期通常更慢。列表变化后，旧的 DNS 缓存仍可能打到已经下线的地址。

### 3. 为什么选择 Spring Cloud 而不是 Dubbo？

**参考答案**

两者不是同一层。Dubbo 是 RPC 和调用治理，Spring Cloud 是一套微服务配套，常见形态是 HTTP。按调用方式和语言边界选，不要按名字站队。

Dubbo 按接口调用。经典协议是 TCP 长连接和二进制序列化，Dubbo 3 又有基于 HTTP/2 的 Triple。超时、重试、负载均衡和分组路由做在 RPC 里，Java 服务之间通常比 HTTP JSON 省。Spring Cloud 常见的是 Gateway、OpenFeign 和 LoadBalancer，契约是 HTTP，浏览器、网关和其他语言更好接，序列化和连接开销更大。

网关和配置中心不是 Dubbo 包办的；Spring Cloud 也不是一个 RPC 框架。Spring Cloud Netflix 里的 Eureka、Hystrix、Ribbon 已经停在维护状态，新项目不要拿它们当主体。Nacos、Sentinel 或 Resilience4j 更常见，Dubbo 也可以注册到 Nacos。

内部 Java 调用量大、要接口级治理时，用 Dubbo 更合适。对外 HTTP、调用方语言不统一时，用 Spring Cloud。也可以对外走 Gateway，对内走 Dubbo。回答时补你项目里的真实约束；没用过就按这个边界说，不要编一段没做过的迁移。

### 4. 服务熔断和降级的实现方案

**参考答案**

熔断是停止调用已经异常的下游，降级是停掉之后返回什么。两件事要一起设计。

熔断器有关闭、打开、半开三态。关闭时统计窗口内的超时、连接失败和 5xx。错误率或慢调用比例超过阈值，并且达到最少样本，就打开。打开期间直接失败，不再占用调用方线程。等待结束后进入半开，放进少量探测：成功就关闭，失败就重新打开。Resilience4j 和 Sentinel 都是这个模型。Hystrix 只用来理解原理。

降级要事先写好：返回缓存、默认值，或关掉非核心功能。降级逻辑不能再调用同一个下游。库存不足这种业务结果不是故障，不能拿来打开熔断器。

只有熔断、没有超时，线程会在熔断打开之前被慢调用占满。超时要短于调用方自己的超时。熔断被打开时要有监控，否则等于把功能静默关掉。限流防的是入口流量太多，和熔断不是一回事。

### 5. 分布式事务的解决方案

**参考答案**

先把必须原子的写入收进一个本地事务。跨服务默认最终一致，不要一上来做分布式事务。

订单库里的业务写入，和一条待发送消息，放在同一个本地事务。后台再把消息发出去，失败就重试。RocketMQ 事务消息是另一条路：先发半消息，本地事务成功后提交，Broker 回查事务状态，避免事务成功但消息丢了。Kafka 没有半消息，用本地消息表。

下游必须幂等。超时重试和重复投递都会把同一笔再送一次。

不能接受一段不一致时，再用 TCC 或 Saga。TCC 分成尝试、确认、取消。取消可能比尝试先到，所以要能空回滚，也要防止取消之后尝试又成功。Saga 用补偿处理长流程，通知已经发出去这类动作补偿不回来。

XA 能做强一致，代价是协调者。Seata AT 侵入小，靠 undo 日志和全局锁，默认允许脏读，热点行冲突时会堵住。这两种都不要用在热点库存上。最终一致还要有对账，失败的消息不会自己变正确。

### 6. 如何设计一个秒杀系统？

**参考答案**

秒杀要挡住两件事：读流量把主站打垮，以及最后几件库存被并发扣穿。入口收窄，扣减做成原子操作，建单异步化。依赖不可用时直接拒绝，不要把流量放进数据库。

页面静态化走 CDN，应用、缓存和主站分开。入口按用户限流，并只发和库存同一数量级的令牌，没有令牌就失败。可售库存用 Redis Lua 在一次调用里判断并扣减；页面上的库存只用于展示，不能拿来决定能不能卖。

Lua 成功后发消息异步建单，接口先返回排队中，等数据库结果再告诉用户成功。数据库仍用库存条件更新做最后检查。用户加活动做唯一约束，消费端按它幂等。数据库失败，就按这张订单把 Redis 预扣补回，不能无条件加。超时未支付用延迟消息释放。

热点会集中在一个库存 key、一行记录和一个消息分区上。用分布式锁把所有人串起来，只会使吞吐更差。

### 7. Elasticsearch 的倒排索引原理

**参考答案**

倒排索引把「词项到文档」记下来，用来按词找文档。正排是文档到内容，对应 `_source`，用来取回原文，不负责检索。

文本先经过分析器切成词项。倒排表记录词项出现在哪些文档，通常还有词频和位置。词项字典按顺序组织，Lucene 用 FST 把字典前缀放进内存，倒排表放在磁盘。布尔查询对几条倒排表做交集或并集，里面的跳表用来跳过文档号。相关度从 Elasticsearch 5 起默认是 BM25，不是更早的 TF-IDF。

排序和聚合一般走列式的 doc values，不走倒排。默认分析器会把中文切得很碎，生产要换中文分析器，而且索引和查询要用同一套切词，否则词项对不上。

索引按不可变的段存放。新文档写入新段，段随后再合并。所以刚写进去的文档不会立刻出现在搜索结果里。

### 8. ES 集群节点故障如何处理？

**参考答案**

先看挂的是主节点还是数据节点。副本用来保持可用，不是备份。

有资格参选的主节点通常至少三台，并分开故障域。主节点挂了，要凑够投票配置里的多数才能选出新主。一次丢掉超过半数，集群状态不能更新，分片也不会被重新分配。

数据节点挂了，它上面的主分片如果还有被集群认为同步过的副本，副本会被提升成主分片，再在其他节点补副本。只有副本缺失时集群是黄色，读写还在。主分片没有同步副本时索引变红，这部分数据从快照恢复。不要手动指定一个空的主分片，集群会变绿，数据却没了。节点只是重启时，延迟再复制，避免大分片来回搬。

删除和错误写入也会复制到副本。快照要放在独立存储。旧节点带着磁盘回来，是从现任主分片同步，不会把旧副本合并回去。

### 9. 如何保证 ES 数据的实时性？

**参考答案**

搜索是近实时的。按文档 id 读取，和按条件搜索，不是一条路径。

写入先进入内存缓冲和 translog。默认每 1 秒 refresh 一次，生成可搜索的新段，所以搜索通常最多等一个刷新间隔。把间隔调得更短，段会变多，合并压力变大。`refresh_interval` 设为 `-1` 是关掉自动刷新，适合批量灌入，不是为了更快被搜到。

要求这次写入后的搜索一定能看见，对这次请求使用 `refresh=wait_for`，让它等到下一次刷新。不要每次写入都强制刷新。按 id 的 GET 默认会读 translog，可以立刻读到，这不代表搜索也能立刻读到。

从数据库同步到 ES，还要加上采集和消费的延迟。刚写完必须正确的数据查数据库，ES 负责搜索和列表。

refresh 决定能不能搜到，translog 刷盘决定进程崩溃丢多少，flush 才是 Lucene 提交。三件事不要合成一个「刷盘」。

### 10. 海量日志数据如何快速查询？

**参考答案**

慢通常是因为全文检索和长时间聚合堆在一起，还允许不带时间范围的扫描。日志不要进 MySQL。

采集端先打上服务名、级别和 traceId，前面放 Kafka 削峰，避免检索集群抖动时把业务机器上的采集进程堵住。近线检索用 Elasticsearch，按时间滚动索引。查询必须带时间范围，只打开对应索引。traceId 和服务名用 keyword 精确匹配，正文才用 text。

热数据只留一段较短的窗口，更早的索引用生命周期转到便宜磁盘或删除。必须长期保留的原文放对象存储。错误数、耗时分位这类统计走列式存储，不要对原文做大范围聚合。

写入用 bulk，高峰可以把 refresh 间隔调大。查询禁止很深的 `from/size`，改用 `search_after`，并加查询超时。时间范围已经能剪掉大部分索引后，分片不是越多越快，过多小分片只会增加扇出和集群状态。

### 11. 手写算法：二叉树层序遍历

**参考答案**

用队列做广度优先。每层开始时记下队列长度，把这一层正好出队完，再处理下一层。空树返回空列表。每个节点入队出队一次，时间 O(n)；队列最宽时接近 n/2，空间 O(n)。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.Queue;

class TreeNode {
    int val;
    TreeNode left;
    TreeNode right;

    TreeNode(int val) {
        this.val = val;
    }
}

public class LevelOrder {
    public List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> result = new ArrayList<>();
        if (root == null) {
            return result;
        }
        Queue<TreeNode> queue = new ArrayDeque<>();
        queue.offer(root);
        while (!queue.isEmpty()) {
            int size = queue.size();
            List<Integer> level = new ArrayList<>(size);
            for (int i = 0; i < size; i++) {
                TreeNode node = queue.poll();
                level.add(node.val);
                if (node.left != null) {
                    queue.offer(node.left);
                }
                if (node.right != null) {
                    queue.offer(node.right);
                }
            }
            result.add(level);
        }
        return result;
    }
}
```

如果只要访问顺序、不按层分组，可以不记录 `size`。用递归时要额外传入深度，空间取决于树高，不是这题最直接的写法。

### 12. 线上问题排查思路

**参考答案**

先确认影响面和最近一次变更，再把问题收窄到一层。止血和找根因分开。

1. 看哪个接口、从什么时候开始、是报错、变慢还是结果错，影响多少用户。先对发布、配置和流量。很多故障跟着变更走。
2. 用错误率、延迟、流量和饱和度判断在网关、应用、数据库、Redis 还是下游。不要先重启，重启会丢掉线程栈和堆。
3. 报错看异常栈和 trace。变慢就把时间拆开：CPU、GC、锁、连接池等待、SQL、外部调用。数据库看慢查询和锁，Redis 看慢日志和大 key。
4. 先止血：回滚、限流、降级或摘掉坏实例。然后再改根因。
5. 用当初报警的那张图确认恢复，把缺的监控或回归测试补上。

没把握的参数不要直接在线上试。工具名不熟时，先说要看的证据是日志、链路、GC 日志还是线程栈。

### 13. JVM 调优经验分享

**答题思路**

讲一次你真的看过 GC 日志或处理过内存问题的经历。没有线上案例，就讲本地压测或一次 OOM，不要编停顿时间和堆大小。

1. 现象先分类：停顿变长、Full GC 变多、OOM，还是 CPU 被 GC 占满。说明影响的是延迟还是吞吐。
2. 证据用 GC 日志、堆转储或线程栈。OOM 要分清堆、Metaspace、直接内存还是创建不起本地线程，不能一律加大 `-Xmx`。
3. 堆里对象一直涨，先找谁在持有，不要先改收集器参数。确认存活对象确实超过堆，再谈加大堆。
4. 收集器讲对版本：JDK 8 默认是 Parallel GC，JDK 9 起 HotSpot 默认改为 G1。ZGC 要显式打开，而且先证明停顿来自收集器，不是泄漏。CMS 在 JDK 14 移除，JDK 8 里也已过时，不要当现成方案。
5. 一次只改一个变量，用同一类日志对比停顿和吞吐。`MaxGCPauseMillis` 只是目标，不是保证。

说不清的参数不要报。面试官要听你怎么判断，不是听一长串启动参数。

### 4. 系统性能瓶颈如何定位？

**参考答案**

先量出时间花在哪一层，再决定加机器、改 SQL 还是减少调用。瓶颈经常不在感觉慢的那段代码里。

1. 分清是吞吐到顶，还是同样流量下 P99 变长。对照变更、数据量和流量。
2. 拆开网关、应用、数据库、Redis 和下游。连接池排队要单独看，它表现成应用慢，线程其实在等连接。
3. 应用里再分 CPU 在计算、GC 在停，还是堵在锁和 IO。CPU 高再看热点方法；CPU 低但线程多，看栈停在哪个调用。
4. 数据库看扫描行数和锁，不只看语句耗时。Redis 看大 key 和慢查询。下游超时后的重试会把一次延迟乘上去。
5. 对着证据改一处。单行热点上加应用实例没有用。缓存如果没有处理失效后的回源，流量上来仍会打穿。

平均耗时会掩盖尾巴，定位时看 P99 和慢调用的分布。

### 9. 手写算法：找出数组中第 K 大的数

**参考答案**

第 K 大是从大到小的第 K 个，等于升序排列后下标 `n - K` 的元素。K 从 1 开始。先全量排序再取这个下标是对的，时间 O(n log n)。下面用快速选择，平均 O(n)，额外空间 O(1)，最坏 O(n^2)。随机选枢轴，是为了避开已经有序时每次都切得很偏。

分区把小于枢轴的放在左边，枢轴落到它在升序里的最终位置。这个位置正好是 `n - K` 就返回；否则只进包含目标的那一侧。

```java
import java.util.concurrent.ThreadLocalRandom;

public class KthLargest {
    public int findKthLargest(int[] nums, int k) {
        int target = nums.length - k;
        int left = 0;
        int right = nums.length - 1;
        while (left <= right) {
            int pivotIndex = partition(nums, left, right);
            if (pivotIndex == target) {
                return nums[pivotIndex];
            }
            if (pivotIndex < target) {
                left = pivotIndex + 1;
            } else {
                right = pivotIndex - 1;
            }
        }
        throw new IllegalArgumentException("k out of range");
    }

    private int partition(int[] nums, int left, int right) {
        int chosen = left + ThreadLocalRandom.current().nextInt(right - left + 1);
        swap(nums, chosen, right);
        int pivot = nums[right];
        int store = left;
        for (int i = left; i < right; i++) {
            if (nums[i] < pivot) {
                swap(nums, store, i);
                store++;
            }
        }
        swap(nums, store, right);
        return store;
    }

    private void swap(int[] nums, int i, int j) {
        int tmp = nums[i];
        nums[i] = nums[j];
        nums[j] = tmp;
    }
}
```

有重复值时，小于枢轴的放左边，相等的先留在右边，枢轴的位置仍然是一个合法的升序位置。如果更在意最坏时间，用大小为 K 的最小堆保存当前最大的 K 个，堆顶就是第 K 大，时间 O(n log K)，空间 O(K)。数组不能被改掉时也用堆。

### 10. 技术选型时的考虑因素

**参考答案**

先写约束和现有技术栈，再在两三个成熟选项里选，并记下放弃了什么。

1. 问题本身：数据量、延迟、一致性，以及流量是短峰值还是一直这么高。
2. 团队是不是已经在运行同类组件。第二套消息队列的运维成本，经常大于功能上的差别。
3. 失败和容量：副本、备份、扩容和升级有没有在生产里验证过。
4. 迁移成本：协议、数据和人员。冷门组件在人离开之后，可能没有人能修。
5. 风险最大的那一点用压测或故障演练验证，不靠对比文章下结论。

选型结果要能说出不选另一个的原因。说不出约束，就还没到选组件的时候。

### 11. 如何保证代码质量？

**参考答案**

质量是变更能被看懂、关键路径有测试、出了问题能收回。格式化分数不能代替这些。

1. 写之前定失败行为：重复请求、空值和超时各返回什么。
2. 改动尽量小。评审看事务、索引、幂等和超时，不把时间花在格式上。
3. 分支逻辑用单测，SQL 和事务用集成测试。修过的缺陷补一条回归。
4. CI 要真的跑这些测试。静态检查用来抓空指针和没关闭的资源，替代不了测试。
5. 上线留回滚和指标。本地正确、灰度之后指标歪了，同样是质量问题。

合进去的代码要能自己讲清。讲不清的生成代码，先不要进主干。
