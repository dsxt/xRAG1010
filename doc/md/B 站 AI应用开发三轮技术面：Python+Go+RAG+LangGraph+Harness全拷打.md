> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这岗位确实不水，背 LangChain 文档混不过去。一面就开始扒意图识别和 RAG 的坑，二面把 Agent 架构拆开问，三面更像在找能扛系统的人，只会调 API 不够。最烦「LangGraph 很强大、多 Agent 很灵活」这种空话，真做过的人一开口就能听出来。整体偏难，问得痛快。能面到这里，说明不是纯 CRUD 的 AI 岗。要是被挂，大概率是 harness 的工程深度和线上评测体系讲不透，模型名字倒在其次。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「定位 → 一条链路 → 和岗位的交点」讲。

1. 一句话：年限，Python 和 Go 各自放在哪一层。Agent 编排和网关分开说。
2. 只展开一个你真实做过的 Agent：用户的哪句话要变成哪个结果，请求经过路由、检索或工具、再回到回复。指标只用你手上有的数。
3. 点出和这个岗位的交点：内容是视频、弹幕、评论这种又短又吵的语料，系统要能检索、能控工具，还要能停。
4. 收在你最熟的那一层，把话筒交给面试官。

### 2. 最近做的 AI Agent 项目介绍

**答题思路**

用真实项目套。没做的模块直接说明边界。

1. 业务目标：用户想完成的事，例如查某个视频里讲过的点、解释一条弹幕、或办理一个只读的客服问题。
2. 你的边界：意图、编排、检索、工具、评测、网关，你写的是哪几层，谁评审上线。
3. 按时间讲一条请求：接入与身份 → 会话上下文 → 意图和槽位（视频号、UP）→ 图里的节点 → 工具（超时、校验、幂等）→ 带出处的回复。只读和写操作分开。
4. 准备一次你亲手处理过的失败：现象、你断定坏在哪一层、改了什么、用哪条坏例确认。没有的召回率不要编。
5. 主动留三个能接住的追问：状态存在哪、写操作谁有权执行、模型超时以后任务怎么续。

### 3. 为什么用 Python 又碰 Golang，两边在你项目里分别干什么

**答题思路**

面试官要的是边界，不是「两个都会」这句话。

1. 先画分工。Python 放迭代快的部分：图、提示词、检索、评测脚本、模型 SDK。Go 放要长期挂着的部分：鉴权、限流、队列、SSE、任务租约。按你的真实仓库讲，只调用过另一边的接口就说是调用。
2. 讲一件跨语言的交接物：任务号、会话键、幂等键、截止时间、工具结果的结构。说明这份结构谁定义、谁校验。
3. 讲一个因此少出事的例子：Python worker 重启时，Go 侧任务还在；或者评测脚本用 Python 重放一条失败轨迹。
4. 收一句你个人写过的代码落在哪一边，避免听成团队简介。

### 4. 意图识别是怎么做的，规则、分类模型、LLM 路由还是混合

**参考答案**

结论：生产用混合路由。规则守住高频和有副作用的意图，小分类模型吃头部说法，大模型只接长尾、多意图和抽槽位。

规则适合「我要发弹幕」「投诉」这种必须稳的说法，延迟低、可以单测，说法一变就要改。小模型适合已经有标注的常规说法，便宜、输出稳定，标签体系一改就要重训。大模型适合一句里夹了两件事、还要抽出视频号或 UP 的情况，表达力好，输出会漂，不适合当唯一的回归手段。

落地时三层都输出同一份结构：意图、槽位、置信度。规则命中高置信度就采用；否则看小模型；剩下的交给大模型，结果仍过 schema。资损或社区副作用类意图即使分对了，也只表示用户想做这件事，能不能执行由后面的策略节点决定。

### 5. 意图识别错了怎么兜底，用户一句话既像查视频又像发弹幕你怎么处理

**参考答案**

结论：读和写不对称。含糊时可以澄清或先做只读；发弹幕这种写操作不靠分类置信度自动执行。

一句话同时像查视频又像发弹幕，按多意图处理，并标出缺的槽位：哪一个视频、弹幕正文是什么。视频已经能唯一确定时，查询可以继续。发弹幕默认进入确认节点，把将要发送的视频、时间点和正文给用户看，同意之后再调工具。分类器把写意图打得很高，也改变不了这条策略。

兜底分三档。置信度不够，路由到澄清节点，问一个具体问题，而不是再自由生成一轮。工具执行前再用槽位校验挡一次，没有视频号就不发。写操作如果已经发出，幂等键撤回不了弹幕，只能走补偿和事后复盘，所以确认要放在执行前。

每次决策记下主意图、次意图和有没有进入确认。这批日志就是后面评测「查视频 / 发弹幕」混淆的样本。

### 6. RAG 里召回和生成谁更容易翻车，举你踩过的坑

**参考答案**

结论：线上答错，根因更多出在召回。生成只能根据送进上下文的证据组织句子；证据错了，模型会把错的说圆。生成自己的失败是另一类：证据在却不用，证据没有却用参数知识补，该拒答时硬答。

一刀能切开：把这道题的金标片段和最终 prompt 对一下。金标不在 prompt 里，查过滤条件、切分和召回。金标在 prompt 里答案仍错，查提示词约束和模型。先改生成提示词，经常只是让错误证据说得更顺。

讲自己踩过的坑时，用能回放的那一次，按「过滤条件 → 召回 id → 进 prompt 的片段 → 改了哪一层 → 哪条坏例不再犯」说。常见的三类可以直接套结构：

- 没把视频号放进硬过滤，同名话题召回到了别的 UP。
- 知识库用的是标题或单条弹幕，用户问的是「视频里讲了什么」，正文根本没进库。
- 字幕按字数切断，结论和它的时间范围拆在两块里，召回只拿到一半。

没有日志可以回放的事故，不要编成自己的线上案例。把上面某一类讲成你准备怎么防，并说明你还没在生产里验证过。

### 7. Embedding 模型怎么选，中文弹幕、标题、评论这种短噪声文本怎么处理

**参考答案**

结论：用你自己的问句集选模型，知识库以字幕、简介、标题为主。单条弹幕又短又吵，不适合当成「UP 说过什么」的事实来源。

基线选一个当前仍维护、能处理中文短查询的向量模型，例如 bge-m3 这一类同时给出稠密和稀疏权重的模型，或更新的中文向量模型。和 BM25 比召回，看的是你标过金标片段的问句，而不是公开榜单的总分。模型如果要求 query 和 passage 使用不同前缀，索引和线上必须同一套。

短文本先清洗：去刷屏、纯表情、重复字符，繁简和大小写按业务收成同一个键。标题和 UP 名、黑话要留一条关键词通道，向量会把专名抹平。弹幕如果要用，按视频和时间窗聚合，并带上视频号和时间；聚合是为了做高能或争议这类信号，回答里要和字幕里的原话分开标注。

有真实的难负例再考虑微调。没有难负例时，换模型不如先补过滤和混合检索。

### 8. LangChain 和 LangGraph 你更喜欢哪个，别背官网话

**参考答案**

结论：路径会分叉、要停下来等人或要从中间恢复时，用 LangGraph。检索然后生成这种直线，用普通函数就够，不必为了图而上图。

Chain 的下一步是代码里写死的，适合固定流水线，延迟和回归都好控。Graph 把状态、节点和条件边摊开，循环在运行时里，不藏在一次「Agent 自己决定」的黑盒里。我更在意的是坏例能不能按节点重放，而不是框架名字新不新。

LangChain 里真正好用的是模型适配、文档加载和检索器这些库。预先封装好的 Agent 循环把停止条件、重试和工具错误卷进框架，线上出了问题要先猜它做了什么。图稳定以后，库可以留着，循环要能在日志里逐跳看完。

### 9. LangGraph 里 state、node、edge、conditional edge 你实际怎么用

**参考答案**

结论：state 是这份任务的结构化事实，node 是纯函数式的一步，edge 是写死的跳转，conditional edge 只读 state 决定下一步。模型不能在运行时造出新节点。

state 用类型约束。消息列表配追加用的 reducer，按消息 id 更新；视频号、意图、证据这些键默认是覆盖。谁有权写哪个键要固定，避免后一个节点把过滤条件写成空。node 接收整份 state，只返回自己改动的部分。有副作用的节点和纯计算节点分开，副作用节点前面才能插人机确认。

普通边用于「分类之后一定去检索」这种不需要判断的跳转。条件边的路由函数不做 IO，返回已经注册的节点名；要并行扇出时，用框架提供的扇出机制指向已有节点。回路可以存在，例如工具结果回到模型节点，所以它不等于后面手撕题里的 DAG。

```python
from typing import Annotated, Literal, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list, add_messages]
    intent: str
    bvid: str


def route(state: State) -> Literal["video_qa", "clarify"]:
    if state["intent"] == "video_qa" and state.get("bvid"):
        return "video_qa"
    return "clarify"


builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("video_qa", video_qa)
builder.add_node("clarify", clarify)
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route)
builder.add_edge("video_qa", END)
builder.add_edge("clarify", END)
```

持久化时给每次会话一个 `thread_id`，检查点才知道往哪份状态上追加。

### 10. 多 Agent 什么时候该拆，什么时候纯属装复杂

**参考答案**

结论：工具权限、模型或可独立评测的职责确实不同，再拆。一条直线流水线拆成多个 Agent，增加的是交接损耗。

该拆的情况：一个角色只能检索，另一个角色才能发弹幕；两路检索语料互不依赖，可以并行；某个专家的输入输出能单独做回归。拆开以后，每个角色看到的工具列表不一样，这是拆的意义。

该留在同一张图里的情况：分类、检索、生成共用一份状态，下一步并不需要另一套目标和人设。把这三个函数叫成三个 Agent，上下文要互相转述，约束（视频号、只读）很容易在转述里丢掉。判断方法：把旁边那个 Agent 收成一个函数之后，权限和结果都不变，它就应该是节点。

多 Agent 的成本在交接、追踪和评测份数。业务路径还没稳定时，先把一张图跑通。

### 11. Agent 调工具失败、超时、返回脏数据，harness 层怎么兜

**参考答案**

结论：harness 是模型外面的运行时，负责校验、权限、超时、执行和停止。这些不写进提示词里指望模型自觉。

每个工具调用单独设超时，用户取消或截止时间到了，下游 HTTP 一起停。错误分成超时、下游 5xx、schema 不符、空结果、业务拒绝。只有幂等的读可以有限次退避重试；写操作只允许带着同一个幂等键重放，避免超时以后再发一条弹幕。

脏数据按不可信输入处理。回包先过响应 schema，对不上的视频号丢掉；正文截断，并把弹幕、评论当数据圈起来，避免里面的指令进入下一轮系统提示。结构化错误可以回给模型一次。第二次仍失败，图走到澄清、缓存答案或人工，由代码决定，不由模型决定要不要再试一次写操作。

容易漏的一点：工具结果进模型之前和进日志是两条路。日志留原文便于回放，prompt 里只留裁剪后的视图。

### 12. Python 里异步和同步在 Agent 调用链里你怎么选

**参考答案**

结论：这一步主要在等模型、等检索、等 HTTP，并且一个进程要挂很多请求，用 asyncio。本地重计算和低并发脚本用同步，或干脆放到独立进程。

同一次请求里，互不依赖的只读检索用 `TaskGroup` 并发；后一步依赖前一步结果，就串行。发弹幕这类写操作按会话键串行，异步不构成乱序执行的理由。每个外部调用单独超时；客户端断开时取消上游请求，避免人走了 token 还在烧。

同步 SDK 若躲不开，放进 `asyncio.to_thread`，并限制线程数。线程可以并发等待网络。默认 CPython 仍有 GIL，纯 Python 的重排不会因为开了线程就用满多核，这种计算放到推理服务或进程池。供应商并发用信号量对齐配额，协程开得比配额多，结果是一起堵在 429 上重试。

QPS 很低、库只有同步版本、一条任务一个进程时，同步写法更清楚。不必为了形式把整条链改成异步。

### 13. Golang 写 Agent 网关或调度层相比 Python 有什么优势

**参考答案**

结论：优势在大量空等连接、取消传递、发布隔离和协议稳定。模型那一次推理的耗时在供应商侧，网关的语言改变不了模型速度。

goroutine 适合挂很多 SSE 和慢客户端。`context` 把超时和客户端断开传进每一次下游 HTTP，任务截止以后 worker 能停下来。任务协议（会话键、幂等键、截止时间、重试次数）用类型固定住，Python worker 只消费已经校验过的任务。网关是单二进制，可以和 Python 的图、提示词分开发布，worker 滚动时接入层还在。

策略只放一处。用户能不能发弹幕，由 Go 在执行前强制检查；Python 里不要再相信模型声明的权限。两套语言各写一份判断，就会出现网关禁了、编排层又放行的缝。

### 14. 手撕算法：给一堆用户 query，按意图类别分组并去重，输出每类出现次数 Top K

**参考答案**

结论：先定口径再写。下面按这个实现：每条记录是 `(query, intent)`，query 规范化后，在各自意图里用哈希计数（相同 query 合成一个键，次数保留），每个意图输出出现次数最高的 K 条。若面试官要的是「意图榜的 Top K」，对意图总数做同样的排序即可，结构不变。

规范化在计数前做完：去首尾空白、合并中间空白、英文小写。空 query 和空意图丢弃。同一句在两个意图下各算各的；如果业务要求一句只归属一个意图，先把标签定下来再计数。次数相同按 query 字典序，结果稳定。`k <= 0` 返回空；K 大于该类条数时返回全部。

时间是 O(N·L + Σ uᵢ log uᵢ)，N 为记录数，L 为字符串长度，uᵢ 为该意图下去重后的 query 数。空间 O(U)，U 是全部 `(意图, query)` 键的数量。单个意图基数很大而 K 很小时，把排序换成大小为 K 的堆，时间可以降到 O(U log K)。全角半角和繁简不会被 `lower()` 收掉，业务敏感就放进 `normalize`。

```python
from collections import defaultdict


def normalize(query: str) -> str:
    return " ".join(query.strip().lower().split())


def topk_by_intent(
    records: list[tuple[str, str]], k: int
) -> dict[str, list[tuple[str, int]]]:
    """返回 {意图: [(query, 次数), ...]}，每类最多 k 条。"""
    if k <= 0:
        return {}
    counts: dict[str, dict[str, int]] = defaultdict(lambda: defaultdict(int))
    for query, intent in records:
        text = normalize(query)
        label = intent.strip()
        if not text or not label:
            continue
        counts[label][text] += 1
    ranked: dict[str, list[tuple[str, int]]] = {}
    for label, freq in counts.items():
        ordered = sorted(freq.items(), key=lambda item: (-item[1], item[0]))
        ranked[label] = ordered[:k]
    return ranked
```

## 二面

### 1. 自我介绍

**答题思路**

四五句就够，落到你马上要讲的那条工作流。

1. 你负责的系统是什么，用户侧的结果是什么。
2. 点名这条链路里最难的一段：分支、人机确认、恢复，或评测。
3. 说明 Python 和 Go 在这条链路里各守一段。

### 2. 挑一个最复杂的 AI 工作流讲清楚：输入、路由、工具、记忆、输出、回写

**答题思路**

只讲一条你能画出来的流程，严格按照这六段，不要并行介绍两个项目。

1. 输入：用户原文、身份、会话 id，以及已经绑定的视频号或 UP。说清哪几个字段是接入层注入的，模型改不了。
2. 路由：规则、分类模型和长尾模型谁先走，写操作在哪一个节点被掰开。
3. 工具：列出真正调用过的几个，每个的超时、是否幂等、失败以后进哪一个节点。
4. 记忆：这一轮 state 里有什么；跨轮只留摘要和已确认槽位；工具原文留在日志，不整段塞回提示词。
5. 输出：用户看到的句子必须能对上证据或工具回包；没有证据时的拒答长什么样。
6. 回写：写回会话存储、指标和坏例库的分别是什么。发弹幕这类外部副作用放在确认之后，并带幂等键。
7. 准备一个断点：进程重启之后从哪份检查点续，已经执行过的写操作为什么不会再执行一次。

### 3. 多 Agent 协作时上下文怎么传，会不会越传越傻

**参考答案**

结论：传结构化交接，不传另一个 Agent 的草稿。约束用代码在每跳重新套上，转述变傻的时候视频号和只读限制还在。

交接对象只留：目标、硬约束（视频号、用户、是否允许写）、证据 id、未填槽位、上一次工具的状态。下一家要事实时按 id 回读原文，不相信上一家用散文复述的「视频里大概说了」。跳数设上限，超过就澄清或结束。

变傻通常来自三处：摘要丢掉过滤条件，人设把未确认的猜测写成事实，工具回包里的弹幕文本被下一家当成指令。对策是过滤条件放在 state 字段里，由检索节点强制使用；猜测和已确认事实分字段；工具文本以数据身份进入提示词。

若两个角色总是一前一后、交接字段和一份函数参数一样多，它们就该是同一张图上的两个节点。

### 4. 共享 memory 和私有 memory 你怎么设计

**参考答案**

结论：共享区只放已经确认、别人也能用的事实；私有区放草稿和原始回包。私有区默认不进入下一个角色的提示词。

共享、按会话：用户 id、当前视频号、已确认槽位、采纳的证据 id、任务状态。每个字段有固定的写入者，用 reducer 规定是覆盖还是追加，避免两个角色同时写意图。共享、按用户、跨会话：偏好这一类长期事实，单独存储，带有效期，用的时候再取，不在每轮自动铺开。

私有、按角色：候选计划、尚未过滤的检索结果、工具原始 JSON。角色结束时只把 schema 校验过的结果映射回父状态。LangGraph 里可以用父图状态加子图：子图有自己的 schema，回到父图的只有显式映射的键。

原始弹幕和评论留在私有回包或日志里。它们又吵，又可能夹着指令，放进共享记忆后会被后续所有角色读到。

### 5. RAG 里 chunk size、overlap、metadata、rerank 你是怎么调出来的

**参考答案**

结论：用一组标了金标片段的问句调，一次只动一个因素。没有放之四海的切片字数。

先按结构切。字幕按时间段或话题段，一块里尽量一个主题，并且能对应起止时间；简介和标题按自然段。固定字数只是兜底。块太大，会掺进别的分钟，向量被平均掉。块太小，条件和结论拆开，每块单独看都像对的。

overlap 只为被切断的句子服务，常见是把块尾的一两句放到下一块开头。加还是减，看「答案刚好跨在切点上」的那些问句还能不能召回到完整事实。重叠补不了一块里混了两个视频。

metadata 至少有：视频号、UP 的 mid、分 P、起止时间、来源（字幕、简介、评论）、入库版本。过滤在向量搜索之前做。先过滤再搜，才不会被别的视频的高分片段占满候选。

召回先取一批候选，再用交叉编码重排留少数几条进 prompt。重排能压掉「向量近但不回答这句问」的片段，救不了金标根本没进候选。所以先看召回有没有把金标带上来，再调重排。混合检索如果用 RRF，融合的是名次，常量 k 沿用论文里的 60 作为起点，再按你的问句集改。

### 6. 用户问 B 站某个 UP 主视频里的内容，RAG 怎么避免答成全网泛知识

**参考答案**

结论：视频身份是硬过滤，回答只能引用这个视频的证据。库里没有就拒答或先去拉这期的字幕，不能退回模型自己的常识。

先把 UP、视频号解析出来。解析不确定就问是哪一期，不先答。检索前按视频号过滤；重排之后再丢弃视频号对不上的块。查询改写可以改措辞，不能把视频号从过滤条件里拿掉。

提示词要求每句论断对得上字幕片段和时间点。证据不足以支撑时，回复字幕里没有这段，不补充「一般来说」。温度用偏低的设定。标题、弹幕和字幕分来源展示，弹幕上的观点不能写成 UP 的原话。

这期还没入库时，用工具只拉这一期的字幕或 ASR，写进带视频号的临时证据再答。工具失败就说明现在答不了。缓存键里必须有视频号和索引版本，否则上一期的答案会被复用到下一期。

### 7. LangGraph 人机协同、断点恢复、回滚你做过没有

**参考答案**

结论：人机确认和断点都依赖检查点；回滚状态不等于撤回已经发生的外部副作用。没做过就说没做过，把这个边界讲清楚。

图在编译时挂上检查点存储，每次调用带同一个 `thread_id`。发弹幕这类节点用 `interrupt_before` 停在执行前，或在节点里调用 `interrupt()` 把待确认的参数抛给调用方。进程重启之后，用同一个 `thread_id` 读回状态。`interrupt_before` 的续跑是对这份配置再次 `invoke`；节点内 `interrupt()` 则用 `Command(resume=...)` 把人的决定送回去。确认节点前面停，才能避免「先发完再等人点头」。

状态历史可以按检查点查看。从旧检查点分叉，或 `update_state` 改一个槽位再继续，得到的是另一条状态分支。已经发出的弹幕不会因为状态回到上一跳就消失。写工具要有幂等键，续跑时同一个键返回上一次的结果，而不是再写一次。读工具可以重跑。

真上过线，就讲存储用的是库还是 Redis、确认超时怎么处理、用户拒绝以后进入哪个节点。没上过线，就讲你会把确认放在哪一个节点前面，以及为什么状态回滚和业务补偿是两件事。

### 8. Agent 循环调用工具停不下来怎么治，max step 之外还有什么办法

**参考答案**

结论：步数上限必须有，它只负责兜底。真正要停的是「没有进展」和「同一调用重复出现」。

harness 为每一步记状态键：工具名加上规范化参数（排序后的 JSON，去掉 trace id 这类每次都变的字段）。同一状态再次出现，判定进入环，跳出循环，把环路径记进轨迹。参数在变、但观察结果的哈希连续几轮不变，同样算没有进展，例如翻页页码变了、返回却一模一样。

再加预算：token、墙钟时间和费用。触到预算就走到固定的收尾节点，向用户说明做到哪一步，而不是把半截工具 JSON 吐出去。模型侧要求显式的结束动作，代码侧同时检查目标是否已经满足，例如证据 id 已齐或槽位已填。只在提示词里写「不要重复调用」挡不住。

步数上限的值按任务类型分。只读问答的上限和多步办理不一样。触顶比例要进监控，长期靠触顶收场说明停条件设错了。

### 9. 工具定义混乱导致模型乱填参数，harness 层怎么校验和收敛

**参考答案**

结论：执行前用 schema 校验，信任字段由 harness 注入，模型填错就修一次，再错就停止。同时把当前节点能看见的工具收窄。

参数用 JSON Schema 或等价的模型，关掉额外字段，枚举和必填写死。用户 id、视频号这类已经由会话确定的值，从会话写入请求，模型即使填了也以会话为准。校验失败不执行。把校验错误回给模型，只允许再填一次；第二次仍失败，进入澄清节点，让用户补槽位。

收敛还靠工具列表。一个节点只挂这一步用得着的工具，描述里写清什么情况不要调。几十个工具一起给模型，参数会串。被拒绝的原始参数存下来，补进回归集，下一版 schema 或描述用这批样本验收。

### 10. Golang 侧怎么做 Agent 任务队列、限流、降级

**参考答案**

结论：用带确认和死信的队列按会话分区；限流按用户、按模型和按工具分层；降级阶梯事先写好。队列满了就快速失败。

任务至少投递一次，所以写操作带幂等键。同一会话键进同一分区，保证一个对话里的写操作不会并发。worker 拿租约，超时未确认可以重新投递；超过重试次数进死信，留给人工或补偿，不在主队列里无限转。

限流：进程内令牌桶只保护本进程；多实例的用户配额和模型并发用 Redis 一类集中计数，保证原子扣减。模型配额和工具配额分开，检索打满不应该把发弹幕的额度一起耗尽。`context` 的截止时间传进下游 HTTP。

降级按顺序：命中缓存、换更小的模型、跳过重排、对已知意图返回固定说明、最后 429 或排队。排队必须有上限，否则延迟无限变长，客户端重试会把系统打穿。写任务失败要明确失败，不能降级成「看起来发送成功」。供应商 429 和连续超时时熔断一段时间，恢复用少量探测流量。

### 11. 高并发下 LLM 调用成本炸了，你怎么控 token 和钱

**参考答案**

结论：先按节点量 token，再砍调用次数和上下文。流式只改善体验，不减少总 token。

稳定的系统提示和工具定义放在前缀，用户原文和字幕放在后面，这样供应商的前缀缓存才有机会命中。具体起扣门槛随供应商变化，面试里讲清楚摆放顺序即可。输出设上限。意图能用规则或小模型解决的，不要进大模型；大模型留给「对着证据写答案」那一步。小模型如果路由更差、导致工具调用变多，总费用可能更高，所以路由要和端到端费用一起看。

工具原文按 id 落库，下一轮只带短视图和 id。两小时视频的字幕不能整段重放，只取命中的时间段。缓存键包含视频号、模型名和提示词版本。重试是费用策略：读可以有限重试，写和已经收到内容的生成不要盲目重试。

用户级和全局预算在调用前检查，超预算走降级或拒绝。离线评测和在线对话分账号或分队列，避免回归跑批打满在线配额。

### 12. 评测怎么做，别只说人工，自动评测指标和坏例回归怎么说

**参考答案**

结论：离线用分环节的自动指标卡住回归，在线看任务有没有办成。人工用来审计抽样和给坏例定性，不承担每次发布的全量检查。

离线按环节：意图看准确率和「查视频 / 发弹幕」的混淆；槽位看视频号是否精确命中；检索看金标片段的 recall@k，以及过滤后视频号是否正确；生成看论断是否被引用片段支持，以及该拒答时是否拒了。工具看选对没有、参数是否精确匹配。有副作用的工具在坏例集上的误执行数应为 0。轨迹看关键节点是否走到，独立的只读步骤允许顺序不同。

自动评判若用模型当裁判，要有评分细则，并定期用人审过的样本检查裁判自己漂了没有。裁判分不能单独当上线标准。

每条线上事故收成一条冻结轨迹：输入、当时的过滤条件、工具回包、期望行为。提示词、模型、索引或图有改动，CI 里重放。回归集里要有「应该拒答」和「不应该调用写工具」的题，不能只有答对的好例子。在线看任务完成、空召回、工具错误、人工接手率和单次成功的费用，按意图拆开。点赞能做参考，覆盖不了沉默的失败。

### 13. 线上 Agent 答错了，怎么定位是召回烂、prompt 烂、模型烂还是工具烂

**参考答案**

结论：拿一个 trace id，按「实体 → 召回 → 进 prompt 的证据 → 工具回包 → 最终句子」往下对。金标证据塞进上下文之后答案就对了，问题在召回；塞进去仍错，问题在生成。

先看解析出的视频号。视频号错了，停在意图和实体链接，后面的召回分数没有意义。视频号对了，看过滤之后的候选里有没有金标片段。没有，查切分、混合检索和过滤是不是把这期排除了。候选里有、最终 prompt 里没有，查重排或上下文预算把对的挤掉了。prompt 里有、句子和证据矛盾，或出现了任何片段里都没有的事实，查提示词约束和这次用的模型。工具回包和最终句子对不上，例如接口是空的、回复却给了播放量，问题在工具结果的使用，生成不该补数。

日志里留的必须是渲染之后真正发出的 prompt，以及过滤前、过滤后两份检索结果。只存模板无法判断线上到底看见了什么。定位以后把这整条轨迹收进上一题的回归集。

### 14. 手撕算法：实现简易拓扑排序，用来跑 DAG 工作流节点依赖

**参考答案**

结论：用 Kahn 算法。入度为 0 的节点可以执行，执行完就把它指向的后继入度减一。所有节点都能进入结果，就得到一种合法顺序；入度降不到 0 的节点处在环上，或必须穿过环才能到达。

时间 O(V+E)，空间 O(V+E)。V 是节点数，E 是去重后的依赖边数。初始入度为 0 的节点互相不依赖，可以并行。若要输出并行分层，每一轮只处理本轮开始时已经在队列里的节点，新解锁的放进下一层。下面的代码用一个队列连续弹出，得到的是合法的串行顺序，本身不是并行调度表。队列按输入顺序放入，结果稳定。业务要优先级时把队列换成堆，复杂度变为 O((V+E) log V)。

输入约定：边是 `(前置, 后置)`。若调用方给的是「A 依赖 B」（B 先做），建图时反过来。重边只计一次，否则入度会偏大。自环使该节点入度永远大于 0，从而留在阻塞列表里。未声明的节点直接报错。有环时仍返回已经能跑的前缀：前缀里每个节点的前置都在前缀中。Agent 里那种「工具结果回到模型」的回路不是 DAG，不要用拓扑序去跑那段循环；拓扑序适用于建索引、特征回填这种无环依赖。

```python
from collections import defaultdict, deque


def workflow_topo(
    nodes: list[str], edges: list[tuple[str, str]]
) -> tuple[list[str], list[str]]:
    """返回 (合法顺序, 因环而跑不了的节点)。边为 (前置, 后置)。"""
    if len(nodes) != len(set(nodes)):
        raise ValueError("duplicate node")
    known = set(nodes)
    indegree = {node: 0 for node in nodes}
    downstream: dict[str, list[str]] = defaultdict(list)
    seen: set[tuple[str, str]] = set()
    for before, after in edges:
        if before not in known or after not in known:
            raise KeyError("unknown node: %s -> %s" % (before, after))
        if (before, after) in seen:
            continue
        seen.add((before, after))
        downstream[before].append(after)
        indegree[after] += 1
    ready = deque(node for node in nodes if indegree[node] == 0)
    order: list[str] = []
    while ready:
        current = ready.popleft()
        order.append(current)
        for nxt in downstream[current]:
            indegree[nxt] -= 1
            if indegree[nxt] == 0:
                ready.append(nxt)
    done = set(order)
    blocked = [node for node in nodes if node not in done]
    return order, blocked
```

深度优先的三色标记能找出一条具体回边。调度更关心「现在谁能跑」，Kahn 和这个语义一致。

### 15. 你要是来面我，我会先问你哪个最狠的问题

**答题思路**

这题是角色对调：你当面试官，第一问就问到必须做过才答得出来的取舍。

1. 问一个带约束的设计，例如：写操作超时之后，幂等键放在哪一层，模型自己重试和 harness 重试怎样保证只写一次。或者：视频号过滤在召回的哪一步，错了怎样用一条轨迹证明。
2. 说明你为什么先问这个：这个岗位坏就坏在副作用和答非所问，框架名词可以后补。
3. 准备两层追问。对方只回答「有 max step」或「我们用了向量库」，你继续问状态存在哪、失败进死信还是进模型。
4. 也准备你自己的答法。你问出口的题，面试官经常会请你先答一版。

### 3. B 站场景里 Agent 做视频理解、弹幕理解、搜索问答，优先级你怎么排

**参考答案**

结论：先做能核对出处的只读搜索问答；视频理解作为给这条链路供数的管道；弹幕理解先做离线信号，不作为第一期对话 Agent 的事实来源。

搜索问答直接对应「这期视频里讲了没有」。对错可以用字幕核对，动作是只读，延迟和费用都能按单次问答衡量。它依赖视频理解产出的字幕、时间轴和片段索引，所以视频理解要做，但是做成入库流水线：抽字幕、按时间切、带视频号入库。不先做开放式的「帮我看完所有视频再聊天」，那会把成本花在用不到的全量理解上。

弹幕是站点特色，也是最吵的一路：反话、刷屏、和 UP 观点相反的句子都有。第一期把弹幕按视频和时间窗聚合成高能或争议信号，展示时和字幕分来源。等只读问答的拒答和引用稳定了，再考虑让对话引用弹幕。发弹幕、自动回复排在最后，因为发错是社区副作用，确认和幂等的成本高于再做一个理解模型。

这个顺序的取舍是：覆盖面让位于可核对。先把一个视频问准，再扩语料。

### 4. 多 Agent 系统上线后监控看哪些指标，别背可观测性名词

**参考答案**

结论：看任务有没有办成、在哪一步空转、有没有误触发写操作、办成一次花了多少钱。追踪字段是为了把这些数拆开，不是指标本身。

按意图看任务完成率：用户是否拿到带出处的答案，或是否在确认后完成了那一次写操作。空召回率、过滤后证据条数，用来发现检索是不是在空转。工具超时率、schema 拒绝率、同一参数重复调用率、触达步数上限的比例，用来发现循环和脏工具。人工接手率要带原因码，否则看不出是政策要求接手，还是系统答不上来。

写操作被拦截的次数单独看。这笔数突然掉到零，往往是确认被绕过，而不是突然变安全。费用看「每次成功任务的 token」，不看总 token；总 token 上升可能只是流量变了。延迟看端到端 p95，并落到节点，知道是模型、检索还是某个工具。人机确认还要看待处理多久没人接。

上线第一周按意图拆这几项就够。平均响应时间一张图，看不出是哪一个 Agent 在重复调工具。

### 5. RAG、多 Agent、工作流都有了，技术选型你为什么不直接全用大模型一把梭

**参考答案**

结论：新视频不在权重里，写操作需要确定的策略，而一整段自由循环无法做回归。大模型用在「语言是问题」的那几步。

B 站的视频每天在增加，模型参数里的常识回答不了「这期第几分钟说了什么」。检索加上视频号过滤，才能把证据限制在这一期。分类、配额、能不能发弹幕，用代码更稳定，也更便宜。工作流把确认、超时和回写固定下来，同一次输入才能重放。

多 Agent 只在权限或语料真的要隔离时使用。都交给一个大模型循环，工具列表会变长，交接约束没有落点，费用随步数放大。小模型或规则负责路由，大模型只对着已经过滤的证据写答案，失败时也能看出是哪一段坏了。

一把梭的吸引力在原型快。上线之后要付的是不可复现的轨迹和无法单测的副作用。

### 6. LangChain / LangGraph 用久了，你觉得哪部分是真价值，哪部分是包装

**参考答案**

结论：真价值是可恢复的状态机：显式状态、条件边、检查点、人机中断。包装是把一个普通循环换了名字，控制流却仍然看不清。

用久了会把库和编排拆开。模型适配、加载器、检索器省的是接入时间，升级时钉住版本，用你的回归集跑一遍。编排留在 LangGraph 里的理由，是你需要暂停、续跑和按节点回放。若图已经退化为「检索然后生成」，收成自己的函数更直白，工具定义和评测不用跟着重写。

预先封装的 Agent、把消息列表改名成记忆、在版本之间频繁更换的调用写法，都要能回答：它多给了哪一种你原来做不到的控制。回答不上来，就把它当包装。框架升级的验收标准是坏例轨迹仍通过，而不是示例笔记本能跑。

### 7. 新人来了看不懂你的 Agent 状态机和 harness 代码，你怎么带

**答题思路**

目标是让对方能安全地改一个节点，并说清写操作为什么会停。

1. 第一天只给一张图：state 有哪些字段，每个字段谁可以写，哪条边会走到写工具。
2. 一起重放一条真实轨迹，从路由走到工具回包，对照日志里的 `thread_id`。
3. 第一个改动做成「加一条回归」或「给某个工具补超时」，代码评审时对照 harness 的校验清单。先改提示词很容易把约束改丢。
4. 阅读顺序固定：状态结构 → 条件边 → 参数校验和权限注入 → 工具实现。
5. 对方能独立讲清：续跑为什么不会把同一条弹幕发两次。讲清之后再让他改路由。

### 8. 跨团队推 AI 工作流，算法、后端、产品、运营谁最难搞，怎么推

**答题思路**

没有固定的「最难的部门」。最难的是掌握否决权、又不和你一起值班的那一方。内容产品里这常常是运营或安全，因为错推荐、错引导落在社区上，不落在错误率报表上。

1. 先承认各自守的东西：算法守答案质量，后端守延迟、权限和副作用，产品守范围，运营守用户可见的说法和坏例子。
2. 推一个很小的只读试点，写明不做什么。例如只回答白名单视频的字幕问题，不发弹幕，不改推荐。
3. 共用一份坏例表。每周只看失败，不看框架选型。每方认领一个数：算法认领引用是否支持论断，后端认领误调用写工具的次数，运营认领哪类说法不能出现。
4. 上线标准写成他们能行使的否决：坏例没过、或没有关闭开关，就不上。这样阻力变成门禁，而不是会议里的态度。

### 9. 老板说接个大模型就能提效，你敢不敢怼，怎么怼

**答题思路**

敢反对这句判断，同时给出一个两周能验证的做法。反对的是「接上就会提效」，接受的是「量完再决定扩到哪」。

1. 复述你听到的目标：想省掉的是哪一步人工，例如客服重复问、或给视频做摘要。
2. 摆出现状：这一步现在耗在哪，哪一部分是模型做不了的，例如没有字幕、必须人工才能退款。
3. 给一个只读试点：语料范围、不允许自动执行的动作、费用上限、怎样算提效、谁可以关掉。两周用同一批真实问句对比「现在的做法」和「检索加引用」。
4. 把结果说死：试点达不到约定的完成率或费用，就停在检索，不扩写操作。语气保持在对事。

### 10. Agent 出线上事故，用户被错误引导或错误推荐，责任怎么定

**参考答案**

结论：先停止继续伤害，再按控制点分责。结案原因写成缺失的那道控制，不写成「模型幻觉」。

错误推荐或错误引导一旦确认，先用开关关掉对应的写工具或推荐位，能撤回的动作做补偿，用户侧给出更正。然后看控制点。该不该允许自动执行，是发布前的产品决定；已经规定必须确认、确认却被绕过，是 harness 和发布审查；视频号过滤失败导致串视频，是检索链路；证据在上下文里、回复仍编出未出现的事实，是生成策略和拒答条件。没有人规定过高风险动作不能自动执行，就把责任记在这次上线的决策上，而不是记在值班的人身上。

复盘要留下两样东西：一条可重放的回归，以及默认关闭的权限。处罚不代替这两样。用户已经被引导去发弹幕、去投诉或去相信一条不存在的视频内容时，对外说明和内部根因分开写，避免把未证实的模型解释发到外面。

### 11. 你最近在学什么，LangGraph 之后下一步啃什么

**答题思路**

讲一个和你短板对齐的主题，带一个已经做出的小产物。避免报一串框架名单。

1. 若这轮暴露的是评测：你在做坏例集和轨迹重放，下一步把「该拒答」和「不该写」也放进自动回归。
2. 若暴露的是检索：你在用真实问句对比混合检索和纯向量，下一步把视频号过滤做成召回前的硬条件。
3. 若暴露的是线上循环：你在把工具状态键和停条件写进 harness，下一步看触顶率和重复调用率。
4. 学习方式说具体：读的是哪段运行时行为，用哪条自己的轨迹验证。还没验证的部分直接说还在读。

### 12. 你是怎么判断一个 AI 框架值得长期投入还是跟风

**参考答案**

结论：值得投入的框架，解决的是你已经碰到的运行时问题，并且可以钉版本、可以回归、可以退出。只是把循环换了个名字，就当跟风。

先写出你现在的痛：坏例不能重放、人机确认没有落点、或工具错误进不了统一的停止逻辑。框架若刚好提供检查点、中断和可查看的状态，它就有候选资格。接着看三件事。运行时你能不能读懂，出了问题能不能自己定位。升级能不能在你的坏例集上跑过再上生产。退出时，状态结构和工具能不能留在你这边，图换成普通代码仍能跑。

LangGraph 这一类图运行时，在你需要暂停和恢复时值得留下。每隔一个季度换一个「更自主」的 Agent 框架，评测和工具权限都要重接，这是跟风。决定之前用同一批轨迹做一次对照：延迟、费用、坏例通过率、一次事故的定位时间。这四项没有改善，就维持现在的写法。

### 13. 如果只给你两个人一个月，做一个 B 站客服加视频问答 Agent，你怎么做

**参考答案**

结论：一个月只做两件只读的事：帮助中心客服问答，以及白名单视频的字幕问答。一个人守接入和配额，一个人守索引、图和评测。不发弹幕，不做多 Agent，不微调，不做全站视频理解。

范围先写死。客服只回答已有帮助文档能支撑的问题，账号处罚、退款一类走人工。视频问答必须解析出视频号，只引用这一期的字幕，没有字幕就说答不了。两路共用一张图：分类 → 按文档源或视频号检索 → 带引用的回答或拒答 → 需要写操作时转人工。

大致四周。第一周定范围，收集几十到一百条真实问句并标金标，打通字幕拉取和帮助文档入库。第二周把图、硬过滤、引用和 trace 跑通。第三周加上限流、费用上限、人工转接和坏例回归。第四周小流量旁路，看空召回、错误引用和单次费用，开关可以一次关掉模型调用。

难点是视频身份解析错、帮助文档互相过时、以及模型在没有证据时补常识。对应的取舍：解析不确定就反问；文档按版本过滤；没有引用就拒答。全站理解和自动回复留到这套只读链路的回归稳定之后。

### 14. 手撕算法：给定一个工具调用序列，检测是否存在环或死循环调用，并输出环路径

**参考答案**

结论：把序列看成一条有向路径，相邻两次调用各是一条边。某个状态第二次出现，就是回到该状态的回边，两次出现之间（含两端）就是环路径。

状态不要只用工具名。`search` 翻页时参数变了，那是进展；工具名和规范化参数都相同，才是死循环。规范化时把 JSON 键排序，去掉每次都变的 `trace_id`、`request_id`。检测范围限定在同一次任务里，不要把一整天的调用拼成一条序列。

时间 O(N·L)，空间 O(N·L)，N 是调用次数，L 是状态串长度。下面的函数在第一次发现重复时返回路径；空序列、单次调用、全程无重复都返回 `None`。路径两端是同一个状态，用来标明在哪里闭合。`["search", "detail", "search"]` 得到 `["search", "detail", "search"]`；`["a", "b", "c", "b"]` 得到 `["b", "c", "b"]`，报的是最早的环。

若输入不是一条轨迹，而是显式的「谁调用谁」依赖边，这道题变成在有向图里找环：深度优先，灰节点表示还在栈上，邻接到灰节点就是回边，环路径取栈上从该节点到栈顶再加回它自己。那是图的问题。题目给的是序列，用状态再次出现即可。

```python
import json


def call_state(name: str, args: dict) -> str:
    stable = {
        key: value
        for key, value in args.items()
        if key not in {"request_id", "trace_id"}
    }
    payload = json.dumps(
        stable, ensure_ascii=False, sort_keys=True, separators=(",", ":")
    )
    return name + "\n" + payload


def find_cycle(states: list[str]) -> list[str] | None:
    """状态再次出现时，返回含两端的环路径；没有环返回 None。"""
    first_index: dict[str, int] = {}
    for index, state in enumerate(states):
        previous = first_index.get(state)
        if previous is not None:
            return states[previous : index + 1]
        first_index[state] = index
    return None
```

线上除了这条结构环，还可以对「连续若干次观察结果哈希不变」另设停条件。页码在变、内容却不变，状态串不一定相同，单靠本函数抓不到。

### 15. 你相比会写 Agent 的算法岗和会写微服务的后端岗，凭什么要你

**答题思路**

两边都要尊重。这个位子要的是把模型放进能上线的系统，用你真实守过的那一层证明。

1. 算法岗强在模型、数据和效果。后端岗强在服务、权限和故障。你不要贬低任何一边。
2. 讲一条你负责过的交叉链路：编排或工具约束是你写的，接入、限流或队列也是你写的或你对接的。只真正写过其中一层，就说另一层是协作，避免装成全栈。
3. 补一个你确实处理过、两边都容易漏的点。例如写操作的幂等和确认，或答错之后用轨迹分清是召回还是工具。讲你加上的那道控制，以及它挡住过什么。
4. 收在这个业务：只读的视频问答可以自动答，发弹幕和错误推荐必须能停。你守的是这条边界，而不只是会调一个模型或会写一个接口。
