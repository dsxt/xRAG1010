### 3. Goroutine 和线程的区别是什么？Goroutine 的调度原理是怎样的？

**参考答案**

结论：goroutine 是 Go 运行时调度的用户态协程，线程是内核线程。能并行执行 Go 代码的线程数由 `GOMAXPROCS` 决定，goroutine 数量可以远大于它。

goroutine 起始栈大约 2KB，不够就整段拷贝扩容，空闲再收缩。创建和切换都在用户态，切换只保存少量寄存器。线程栈通常是数 MB，创建和切换要进内核。一个进程里可以同时存在大量 goroutine。

调度用 GMP。G 是 goroutine，M 是操作系统线程，P 是逻辑处理器，个数等于 `GOMAXPROCS`。M 必须绑上 P 才能执行 Go 代码。每个 P 有本地运行队列，另有一个全局队列；本地空了会去别的 P 偷一批，也会隔一段时间从全局队列拿，避免全局队列里的 G 饿死。Go 1.25 起，Linux 上的默认 `GOMAXPROCS` 会考虑 cgroup 的 CPU limit。容器里把它设得比限额还高，只会增加抢占。

网络阻塞把 G 挂到 netpoller，M 继续跑别的 G。G 进入阻塞系统调用时，M 和 P 分离，P 可以交给别的 M。sysmon 会抢占运行过久的 G，也会把卡在系统调用里的 P 夺走。Go 1.14 起，长时间不主动让出的循环也会被信号异步抢占。

goroutine 之间优先用 channel 交接数据。goroutine 泄漏会留下栈，栈还是 GC 的根，所以数量本身要监控。

### 4. Go 的 GC 是如何工作的？三色标记法的过程能详细说一下吗？

**参考答案**

结论：Go 的 GC 是并发、不移动对象、不分代的三色标记清除。业务大部分时间和标记、清扫并行，停顿集中在两个很短的停止一切（STW）窗口。

白色是还没访问到的对象，灰色是已经可达、指针还没扫完的对象，黑色是指针已经扫完的对象。标记开始时先做一次短 STW：收尾上一轮还没扫完的 span，打开写屏障。然后从根把对象标灰。根包括全局变量、各 goroutine 的栈和寄存器。之后反复取出灰色对象，把它指向的白色对象标灰，自己变黑。没有灰色对象时，剩下的白色不可达，交给清扫。

并发标记要保住一条不变量：黑色对象不能独自指向一个仍是白色的对象。堆上的指针写入走混合写屏障，旧目标和新目标都会被标灰。栈上写指针不走这道屏障；每个 goroutine 的栈在标记期间被一致地扫一次。标记过程中新分配的对象直接标黑，本轮不回收。因此不必在标记结束前把全部栈再 STW 重扫一遍。第二段 STW 用来确认标记真的结束、关掉写屏障并准备清扫。

清扫是懒的。分配需要 span 时顺手扫，后台也有清扫。`GOGC` 默认 100，意思是堆相对上一轮存活数据大约再涨一倍时触发。`GOMEMLIMIT` 是软上限，靠近它时 GC 会更积极。分配比标记快时，分配的 goroutine 会被拉去协助标记，延迟就会抖。

Go 1.26 起默认用 Green Tea 做标记：仍是三色和同一套写屏障，但把同一 span 里的小对象攒起来扫，提高局部性。它没有把 GC 改成分代或压缩。

### 5. 讲一下 Go 的 Channel 底层实现，发送和接收的具体流程是怎样的？

**参考答案**

结论：channel 在运行时是一把锁保护的 `hchan`：环形缓冲区、发送下标、接收下标、发送等待队列、接收等待队列和关闭标志。等待者用 sudog 挂在队列上。

发送时先锁住 channel。接收队列里已经有人，就直接把数据拷到接收方并唤醒它，有缓冲时这条路径说明缓冲区是空的。没有接收者但缓冲区还有空位，数据拷进 `buf[sendx]`。缓冲区也满了，发送方做成 sudog 挂到发送队列，然后 `gopark`。被唤醒后如果发现 channel 已关闭，发送会 panic。

接收时也先加锁。缓冲区有数据就取 `buf[recvx]`。如果这时发送队列还有人，说明缓冲区是满的：接收方拿走最老的元素，等待发送者的值补进缓冲区，顺序仍然是先进先出。缓冲区是空的但有发送者在等，那就是无缓冲或等价的直接交接，数据从发送方拷到接收方。队列和缓冲区都空、channel 已关闭，返回零值和 `false`；缓冲里的剩余元素会先被取完，然后才是零值。都没有就挂到接收队列上。

关闭只能由发送方做一次。关闭 nil channel、重复关闭、向已关闭 channel 发送，都会 panic。对 nil channel 发送或接收会永远阻塞。

无缓冲 channel 没有队列，发送和接收必须碰上，数据直接在两边的栈之间拷贝。有缓冲 channel 解耦两边，容量满则发送阻塞，空则接收阻塞。

### 6. Go 里面的 Map 是线程安全的吗？如何实现一个线程安全的 Map？

**参考答案**

结论：普通 `map` 不是线程安全的。并发读写、并发写会直接把进程打崩。只有「大家一起读、没有人写」才是安全的。

要并发访问，有几条正路。

- 所有读写，包括遍历，都用同一把 `sync.Mutex` 包住。需要一次看到稳定视图时，这是最好解释的做法。临界区里只做这一次 map 操作。
- 读远多于写、临界区又确实有一点工作，可以用 `sync.RWMutex`。临界区只有一两次寻址时，读者计数的原子操作未必比一把互斥锁便宜。
- 多个 goroutine 按 key 分摊访问，用 `sync.Map`。Go 1.24 起它的实现换成哈希字典树，Go 1.26 起旧的 read/dirty 双表已经移除。`Load` 沿原子指针走，不加锁；`Store` 锁的是 key 落到的那个内部节点，不同 key 有机会并行写。key 和 value 都是 `any`。`Range` 不是一个完整快照，遍历过程中别的 goroutine 仍可能改到别的 key。它也不提供跨多个 key 的事务。
- 热点很集中时，把 key 分片到多把锁和多张 map 上，降低同一把锁的争抢。分片数按热点测，不是越多越好。
- 订单簿这种要看全量、还要保持价格时间优先的结构，用「一个 goroutine 独占这张表」更合适。channel 把命令串行送进去，表本身不必再加锁。

`sync.Map` 的零值可以直接用，复制会出问题。旧说法「必须先把 key 预热进只读层」描述的是 1.24 之前的实现。

### 7. sync.Mutex 和 sync.RWMutex 的区别是什么？RWMutex 在读多写少的场景下是如何工作的？

**参考答案**

结论：`sync.Mutex` 同时只允许一个持有者。`sync.RWMutex` 允许多个读者并行，或者一个写者独占。两者的零值都可用，第一次使用之后都不能复制。

`Mutex` 的快路径是一次原子操作。争抢时先在用户态短暂自旋，自旋转不成就把当前 goroutine 挂起。正常模式下，新来的 goroutine 因为已经在 CPU 上，可能插到刚被唤醒的等待者前面。等待超过 1ms 会进入饥饿模式：所有权直接交给队头，新来的排到队尾，避免尾延迟被无限插队。

`RWMutex` 用读者计数区分状态。没有写者时，`RLock` 只是把计数加一，读者之间不互斥。写者到来时先拿内部的写互斥，再把读者计数减去一个很大的数，使它变成负数。已经在里面的读者继续读完；新的 `RLock` 看到负数就等待。现存读者都 `RUnlock` 之后，写者进入。写者释放时再把等待的读者叫醒。这样连续到来的新读者不会把写者永远挡在外面。

官方约束要一起记住：持有读锁时不能再 `RLock`，否则写者在等、自己又等写者，会自己死锁。读锁不能升级成写锁，写锁也不能降级成读锁。

读多写少时，多个读者可以同时进临界区，适合临界区里真有一段共享只读工作的情况。临界区若只是读一个指针或一个整数，`RWMutex` 每次都要改共享的读者计数，缓存行会在核之间跳。这种短读用 `Mutex` 或原子操作往往更合适。

### 8. Go 的并发内存模型（happens-before）了解吗？讲一个你使用它的实际场景

**参考答案**

结论：没有数据竞争时，Go 程序表现得像所有 goroutine 被放到一个处理器上轮流执行。跨 goroutine 要让一次写被另一次读一定看见，中间必须有 happens-before 关系，编译器和 CPU 才不能把这两次访问拆开。

同一 goroutine 里，happens-before 跟语言规定的求值顺序走。跨 goroutine 的边来自同步操作：

- channel 上的一次发送，同步于对应接收的完成。
- 无缓冲 channel 上，接收还同步于对应发送的完成，两边是一次握手。
- 关闭 channel，同步于一次因为关闭而返回零值的接收。
- 容量为 C 时，第 k 次接收同步于第 k+C 次发送的完成。
- 对同一把 `Mutex` 或 `RWMutex`，第 n 次 `Unlock` 同步于第 m 次 `Lock` 返回，n < m。
- `go` 语句同步于新 goroutine 的开始。`sync.Once` 里 `f` 的返回同步于任一 `Do` 的返回。
- `sync/atomic` 的操作按顺序一致性排。一次原子读如果观察到某次原子写，这次写就同步于这次读。

goroutine 函数返回本身不和任何操作建立 happens-before。用普通 `bool` 自旋等另一个 goroutine 做完，既是数据竞争，也可能永远看不见那次写入。

可以拿这段真实结构去讲，换成你代码里的一次跨协程发布即可：撮合协程先把成交写进结构体，再向 channel 发送或关闭；下游收到之后再读这组成交。发送之前的写，都 happens-before 接收完成之后的读。

```go
ready := make(chan struct{})
go func() {
    book = build(snapshot) // 这些写发生在发送之前
    close(ready)
}()
<-ready
use(book)
```

### 9. 在撮合引擎这种低延迟场景下，如何减少 GC 带来的停顿影响？

**参考答案**

结论：撮合路径上的尾延迟主要来自分配、标记协助和扫指针，不是那两段已经很短的 STW。先让热路径几乎不分配，再给进程一个明确的内存上限。

订单簿用只含整数的结构，链表指针改成切片下标。不含指针的数组位于 noscan span，GC 不用逐个字去扫。订单 ID、价格、交易对都用整数。热路径上不要拼字符串、装箱成 interface、打带分配的日志。

订单对象用撮合协程私有的空闲链表或预先分配的槽位回收。`sync.Pool` 会在 GC 时被清掉，空池之后的突发又会回到堆分配，不适合当作延迟上界。实验性的 arena 没有成为稳定方案，不要当成生产依赖。

活集稳定之后，再设 `GOMEMLIMIT`，留出栈、系统和 cgroup 之外的余量，不要顶满容器限额。`GOGC` 用来在内存和 GC 频率之间取舍。旧的「分配一块大 ballast 减少 GC」是 `GOMEMLIMIT` 之前的做法。`GOGC=off` 又没有内存上限时，堆会一直涨到 OOM。

撮合协程不要碰网络和磁盘，避免把系统调用、分配和 GC 协助叠在同一段关键路径上。用分配 profile 确认热路径的 allocs 接近零，用 GC 暂停和标记协助的时间确认尾延迟，而不是只看平均停顿。

### 10. Redis 在你们的系统中扮演什么角色？如何保证缓存与数据库的一致性？

**答题思路**

先按真实系统说 Redis 在不在链路上、承担哪几类数据。常见且站得住的是行情读模型、会话、限流计数、幂等键、很少改的配置。资金余额和订单是否成交以账本和撮合日志为准。没用过就直接说没有，不要为了题目补一个缓存层。

一致性按下面的机制讲，键名换成你自己的：

1. 写路径先提交数据库，成功后再删除缓存。下一次读未命中，再读库并回填。并发写如果直接改缓存，后到的旧值会覆盖新值。
2. 回填仍有窗口：请求 A 读到旧值，请求 B 写库并删掉缓存，A 再把旧值写回去。能接受短暂旧值，就给键一个不长的 TTL。不能接受的数据不要走这层缓存，读路径回到主库或撮合结果。
3. 更及时的失效用数据库变更日志异步删键。删失败靠 TTL 兜底，而不是在业务线程里 sleep 再删第二次。
4. 热点键同时未命中时，用 singleflight 合并回源，避免打穿数据库。
5. 缓存和数据库之间没有原子事务。下单、冻结、成交都不以缓存写入成功作为确认。

### 11. 如果让你用 Go 的 Channel 实现一个最简单的订单撮合逻辑，你会怎么设计？

**参考答案**

结论：一个交易对的订单簿只由一个 goroutine 写。其他协程把订单送进同一条 channel，时间优先就是这条 channel 上发送成功的顺序。

撮合循环里只做内存匹配，向外扔成交事件。网络、刷盘和行情放到出站 channel 的消费者里。出站队列有界；满了就反压到入口并明确拒单，不能在撮合中间丢掉已经产生的成交。停机命令也放进同一条输入 channel，这样它和最后一笔订单的先后是确定的。

下面只演示限价单。价格用整数 tick。买盘从高到低，卖盘从低到高，同一价位先来先成交。成交价用簿上对手单的价格。切片从头部摘订单只适合讲清楚流程；生产里价位索引用固定 tick 数组或平衡树，价位内部用环形队列或下标链表。

```go
type Order struct {
    ID, Price, Qty int64
    Side           int // 1 买，2 卖
}

type Trade struct {
    TakerID, MakerID int64
    Price, Qty       int64
}

type Engine struct {
    bids [][]Order // 下标 0 是最高买价
    asks [][]Order // 下标 0 是最低卖价
}

func (e *Engine) Loop(in <-chan Order, out chan<- []Trade) {
    for o := range in { // 只能在这个 goroutine 里碰订单簿
        out <- e.match(o)
    }
}

func (e *Engine) match(taker Order) []Trade {
    var trades []Trade
    levels := &e.asks
    if taker.Side == 2 {
        levels = &e.bids
    }
    for taker.Qty > 0 && len(*levels) > 0 {
        lvl := &(*levels)[0]
        if !crosses(taker, (*lvl)[0].Price) {
            break
        }
        maker := &(*lvl)[0]
        q := taker.Qty
        if maker.Qty < q {
            q = maker.Qty
        }
        trades = append(trades, Trade{
            TakerID: taker.ID, MakerID: maker.ID,
            Price: maker.Price, Qty: q,
        })
        taker.Qty -= q
        maker.Qty -= q
        if maker.Qty == 0 {
            *lvl = (*lvl)[1:]
        }
        if len(*lvl) == 0 {
            *levels = (*levels)[1:]
        }
    }
    if taker.Qty > 0 {
        e.rest(taker)
    }
    return trades
}

func crosses(taker Order, makerPrice int64) bool {
    if taker.Side == 1 {
        return taker.Price >= makerPrice
    }
    return taker.Price <= makerPrice
}

func (e *Engine) rest(o Order) {
    levels := &e.bids
    if o.Side == 2 {
        levels = &e.asks
    }
    for i := range *levels {
        p := (*levels)[i][0].Price
        if p == o.Price {
            (*levels)[i] = append((*levels)[i], o)
            return
        }
        // 买盘价格高的在前，卖盘价格低的在前
        if (o.Side == 1 && o.Price > p) || (o.Side == 2 && o.Price < p) {
            *levels = append(*levels, nil)
            copy((*levels)[i+1:], (*levels)[i:])
            (*levels)[i] = []Order{o}
            return
        }
    }
    *levels = append(*levels, []Order{o})
}
```

市价单不进簿，并要有保护价。撤单是同一条命令流里的另一种命令，用订单号找到槽位再从价位队列摘掉。多个发送者只保证「发送成功」的顺序，不保证它们调用发送语句的顺序。

### 12. Kafka 在交易系统中常用来做什么？如何保证消息不丢失？

**参考答案**

结论：Kafka 用来留下可回放的命令和事件，把撮合与落库、清算、行情解开。生产者等到的是副本确认，不是消费者已经处理完。

交易里常见三类用途。订单命令日志按进入撮合的顺序持久化，恢复时先加载快照再重放。成交、冻结、解冻事件送给清算和账户。行情是另一条可以落后一点的消费路径。撮合线程不要同步等下游业务处理完。

不丢失要三段一起看。

- 生产者：`acks=all`，开幂等生产者，发送失败就重试或向上游返回失败，不能把未确认的订单告诉用户已接受。幂等生产者解决的是同一次发送重试造成的副本重复，应用自己发两次仍然会有两条消息。
- Broker：`acks=all` 等的是 ISR，不是所有副本。订单 topic 的副本数至少 3，`min.insync.replicas` 至少 2，并禁止 unclean leader election。否则只剩一个副本时仍可能确认，或者让落后副本当领袖，已确认的消息会丢。
- 消费者：处理并持久化之后再提交位移。自动提交或处理前提交，进程死在中间就会丢。这是至少一次，重复不可避免。成交和订单用业务 ID 做数据库唯一约束，重复投递变成空操作。

批次和 linger 能提高吞吐，也会抬高单条发送延迟。延迟预算紧时少攒一些；这个选择要测，没有统一的毫秒数。跨主题的恰好一次才需要事务生产者和 `read_committed`。进数据库的恰好一次靠幂等写入或发件箱，不是只打开生产者幂等。

### 13. 在微服务架构下，如何设计一个高性能的订单号生成服务？

**参考答案**

结论：订单号在接入侧本地生成，热路径上不为每个号打一次远程调用。号要全局唯一、大致按时间有序，允许有空洞，不能有重复。

号段方案：数据库里每个业务一行，`max_id` 按步长原子增加，实例拿到一段区间后在内存里递增。当前段快用完时异步取下一段，避免用尽时卡住下单。步长越大，数据库越轻，进程崩溃留下的空洞也越大。时钟无关，单调性只在单个实例的一段内严格成立。

雪花方案：时间戳、机器号、毫秒内序列拼成一个 64 位整数。机器号用带租约的租借，同一时刻不能借给两个实例；租约过期后还要有防护，避免旧进程继续发号。序列在同一毫秒内用完就等到下一毫秒。时钟回拨时等到时间超过上次发号的时间戳，或者直接失败。进程重启会把序列清零，所以启动时要把本地或租约里记下的最后时间戳推过去，避免同一毫秒重复。

多个发号器之间只是大致按时间有序，不是一把全局锁发出的连续号。路由如果依赖号里的分片位，位布局要先定好。

UUID v4 会把聚集索引写散。UUID v7 按时间有序，适合做外部 ID。撮合日志若要短整数和紧凑索引，号段或雪花更合适。生成服务自己挂掉时，已借出的号段和机器号仍能发号；恢复依赖的是租约和号段记录，不是每笔订单回源。

### 3. 你在处理线上 Go 服务的内存泄漏或 Goroutine 泄漏问题时，一般有哪些排查思路和工具？

**参考答案**

结论：先分清是 goroutine 堆着不退，还是堆内存退不下来。两者都看 pprof 的两份快照差分，而不是只看进程 RSS 的一个瞬时值。

goroutine 泄漏看数量是否在没有流量增长时一直上升。`/debug/pprof/goroutine?debug=1` 按栈聚合，能看出卡在哪里。常见栈是：永久阻塞在 channel 收发、`WaitGroup` 少了 `Done`、持锁的一方已经走死、出站请求没有超时也没有取消、HTTP 响应体没有关闭。`time.After` 在忙循环里制造的是大量短命定时器；真正把 goroutine 留住的，是函数退出后仍有人堵在永远不会来的 channel 上。

Go 1.27 起可以用 `/debug/pprof/goroutineleak`（1.26 里还是实验项）。它在 GC 标记时判断：一个 G 堵在 channel、`Mutex` 这类同步点上，而这个同步点从任何还能运行的 goroutine 都到不了，那么这个 G 不会再被叫醒。挂在全局变量、或仍可运行的 goroutine 的局部变量上的阻塞，它发现不了，栈差分还是要看。

内存泄漏在 Go 里多数是对象仍被引用。安静一段时间后连采两份 heap，用 `pprof -base` 看 `inuse_space` 哪些对象还在涨。优先检查只增不删的 map、从大数组切下来仍被引用的小切片、全局缓存、被堵住的 goroutine 栈，以及 cgo 分配了但没释放的内存。子串会共享原来的底层数组，一个短字符串可以按住一大块缓冲。

`inuse_space` 看还活着的，`alloc_space` 看累计分配。只是分配频繁、GC 能收回，是压力问题，不是泄漏。`GOMEMLIMIT` 改变的是回收节奏，不会修好被引用住的对象。

pprof 端口不要暴露到公网。线上保留最近的 profile，事故时才有基线。

### 4. 如何对一个 Go 的撮合服务进行性能剖析（Profiling）和优化？你常用哪些工具和指标？

**参考答案**

结论：先定尾延迟和正确性，再决定看哪一种 profile。CPU profile 看不到堵在 channel、锁和磁盘上的时间。

常用几份 profile，都从 `net/http/pprof` 或测试的 `-cpuprofile`、`-memprofile` 来。

- CPU profile 看撮合循环里的热点函数。
- heap 的 `alloc_space` 看热路径还在分配什么；`inuse_space` 看活集。
- `runtime.SetMutexProfileFraction` 和 `SetBlockProfileRate` 打开锁竞争和阻塞 profile。撮合突然变慢但 CPU 不高时，先看这两份。
- `runtime/trace` 看调度延迟、GC 和系统调用是不是叠在同一段时间。
- `go test -bench -benchmem` 看每次操作的分配次数和字节数。`-gcflags=all=-m` 看不该逃逸的订单对象有没有逃到堆上。

指标用服务自己的直方图：从命令进入撮合循环到产出成交的 p99、p999，加上拒绝率和原因、队列深度、goroutine 数。运行时看 GC 暂停、标记占用的 CPU、`GOMEMLIMIT` 离得还有多远、调度延迟。平均值会把尖刺藏掉。

优化顺序是：确认热路径分配，再看订单簿是不是按订单而不是按价位在抖动，然后才是 GC 和刷盘的组提交。每改一处就用同一段行情回放对比延迟和成交结果。没有基线的参数调整，不算优化。

### 5. 在订单撮合过程中，核心的匹配逻辑（比如价格优先、时间优先）你是如何实现和保证其高效性的？底层数据结构是如何选型的？

**参考答案**

结论：价格优先、时间优先放在单写者里做。买盘最高价、卖盘最低价先成交；同一价位按进入这个写者的先后排成 FIFO。成交价用簿上那张挂单的价格。

高效实现按价位组织，不按每一张订单堆一个堆。

- 订单本体放在连续槽位里，字段用整数和后继下标，避免 `*Order` 链表。
- 订单号到槽位的索引，让撤单先 O(1) 找到单。
- 每个价位保存总量和一条 FIFO。新单接到队尾；部分成交的挂单留在队头，时间优先不变。减量通常留在原位；改价视为从原价位删除再插入新价位，排到新价位队尾。这是常见交易所规则，回答时要说你实现的是哪一种。
- 价位本身要能快速找到最优价，也能在价位变空时删掉。价格带宽、tick 固定时，用数组下标 `(price - min) / tick`，最优价用一个游标维护，进出都是 O(1)。价格范围很宽、价位稀疏时，数组太浪费，改用按价格排序的平衡树或跳表，最优价和增删价位是 O(log P)，P 是价位数量。哈希表只能 O(1) 按价格找到价位，不能代替有序索引。
- 以订单为元素的堆，取最优是 O(log N)，任意撤单要么 O(N)，要么要懒删除，堆里会堆满过期节点。同一价格的时间顺序还得把序列号编进键。它适合讲复杂度，不适合作为完整订单簿。

匹配循环只看对手盘最优价位的队头。买单价大于等于卖一、卖单价小于等于买一就成交，数量取两边较小值，挂单量为零再出队，价位为空再从有序索引删除。市价单不挂簿，并要有保护价。若规则是按比例分配而不是时间优先，价位内就不能用纯队列。

高效来自三件事：单线程所以没有锁；热路径不分配；撤单和找最优价都不扫描全簿。正确性用回放做回归：数量守恒、不能交叉盘口、同一价位不能后单先成。

### 6. 如何保证撮合引擎在处理极端行情（瞬间大量订单）时的高可用性和可靠性？有哪些容错和降级机制？

**参考答案**

结论：同一个订单簿不能多点同时写。高可用是「单写者 + 命令日志 + 带防护的主备切换」，极端行情靠有界队列和明确拒绝，而不是把 goroutine 开到无限。

可靠性沿命令顺序做。命令先进入日志，快照只在两条命令之间拍，并记下日志位点。恢复时加载快照，重放位点之后的命令。撮合过程不读墙钟来决定谁先谁后，也不遍历 map 来取下一个订单，这样同一条日志在备机上会得到同一组成交。确认给用户「已接受」之前，这条命令要已经落在你选定的持久点上：本地日志组提交，或者 Kafka 副本确认。组提交用很短的批次换磁盘吞吐，批次边界就是延迟地板。

主备切换要有纪元。旧主在网络分区后不能继续追加日志。备机只从已经确认的位点提升。切换期间这个交易对短暂停写，比两个主同时成交便宜。

极端行情时入口队列有界。满了就拒绝新的增风险订单，并返回明确错误。撤单和只减风险的请求单独留容量，不能和新建单抢同一个已满队列然后一起被丢。按账户和连接限流，避免一个做市商占满单写者。触发类、冰山这类更重的订单可以暂时停掉，限价和撤单继续。该拒绝就拒绝，不要为了「都接着」静默改变成交顺序。

下游清算变慢时，撮合可以继续，只要成交事件有持久日志，清算按幂等追赶。资金校验若依赖的本地额度已经不可信，就拒绝新的增风险订单。行情消费者落后只影响推送，不回写订单簿。

热点交易对放到独立的核上。扩容单位是交易对或交易对分组，不是把一个订单簿拆给多个写者。

### 7. 你如何理解分布式系统中的最终一致性？在交易场景下，哪些环节可以接受最终一致性，哪些必须强一致？

**参考答案**

结论：最终一致性是说，更新停止之后各副本会收敛到同一结果，读请求在此之前可以看见旧值。它不保证刚写完的下一笔读就看见新值。

必须按撮合序列立即成立的：

- 一笔挂单的数量不能被两笔吃单同时用掉。这由单写者的顺序保证，不靠事后合并。
- 一笔订单在受理前，对应资金或仓位的冻结要在该账户自己的账上先成功。两个接入同时拿一份过期余额做校验，会双花。
- 用户看到的接受、成交、撤单，要和这条命令日志一致。同一订单号的重试必须幂等。

可以最终一致的：

- 对外行情、K 线和最新成交推送。它们可以略晚于撮合，但不能被当成成交确认。
- 历史查询、账单索引、通知、监控。读模型由事件异步投喂，失败就重放。
- 跨服务的订单列表，只要「我刚下的单」这种读己之写走主路径或带上已确认的日志位点。

余额展示可以略旧，下单校验不行。强一致的范围是「这条命令及其资金冻结」，不是让所有服务共享一个分布式锁之后再撮合。冲突以命令日志的顺序为准，不能对余额做后写覆盖先写。

### 8. Kafka 的 Consumer Group 的再平衡（Rebalance）机制了解吗？在交易系统消费订单消息时，如何避免 Rebalance 带来的处理暂停或重复消费？

**参考答案**

结论：再平衡是消费组成员或分区数变化时，重新决定谁读哪些分区。经典协议里处理会停一下；重复来自「至少一次」的位移提交，要靠业务幂等吸收。

经典客户端协议里，成员加入、离开、心跳超时、处理时间超过 `max.poll.interval.ms`、分区数变化，都会触发再平衡。eager 协议先把大家的分区全部收回，再统一分配，整组在这一段不能消费。cooperative sticky 只收回必须搬走的分区，其余分区继续读，通常要两轮才能稳定。分配器不要在同一组里混用两种协议。

减少暂停：

- 每个实例配置稳定的 `group.instance.id`，并且全组唯一。进程在会话超时内重启，不会因为短暂离开就全组再平衡。超时仍会发生。
- 消费循环里尽快 poll。单次处理时间留在 `max.poll.interval.ms` 以内。重活放到有界队列时，位移只能在这些活真正做完后提交，否则提交点和处理点会错开。
- 发布时用静态成员，避免每次滚动都打散分区。分区数按交易对的并行度规划，不要为了扩容频繁改分区。

Kafka 4 的新消费者组协议把分配放到协调者上增量下发，用来避免客户端主导的全体停顿。回答时先说清线上是经典协议还是这套新协议。

重复消费：关闭自动提交，在分区被收回的回调里把已经持久化的位移提交掉，处理成功后再提交。崩溃恢复会从上次提交重放。订单号、成交号在库里唯一，重复消息变成空操作。这才能既不丢已确认的消息，又不怕再平衡重放。恰好一次只存在于「消费、处理、再写出 Kafka」并且使用事务和 `read_committed` 的链路；写数据库仍以幂等为准。

### 9. 订单和交易数据最终要持久化，在数据库（如 MySQL）层面，你们是如何做分库分表设计的？如何应对热点账户问题？

**答题思路**

先讲你真实的分片键和哪张表最热，再落到热点账户。没有分库就说没有，补一句什么样的量才会拆。下面是交易库里站得住的讲法，用来和你的方案对照。

1. 订单、冻结和余额按账户分片，让同一用户的「冻结资金 + 写订单」落在一个库的本地事务里。订单号里带上分片位，按订单号查询才不必广播。
2. 成交至少按参与者各写一份，分别落在买方和卖方的分片，用成交号幂等。若再按交易对加时间做行情查询表，那是读模型，和账户分片分开。
3. 只按交易对分片时，活跃交易对会把一个库打满。撮合内存可以按交易对分片，MySQL 上的账户数据不要跟着交易对走。
4. 历史订单按时间再拆，热表只留未完成订单和近期成交。

热点账户，例如做市和手续费账户，更新会打到同一行，行锁把这些更新串行化，连接在锁上排队。可以讲你真实用过的一种：

- 把热点账户拆成多个子账户分摊扣减，后台合并展示。
- 一个账户一个队列，把多笔成交的增量合成一次 `balance = balance + ?`。
- 热点账户单独放到一台实例，避免拖垮同库的普通用户。这不能提高这一行本身的更新速度。
- 实时风险用撮合侧已经确认的日志，数据库按同一条日志追账。

Redis 可以缓存读，不能当余额权威。跨分片查询靠分片位或汇总读模型，不在下单路径上对所有库广播。

### 10. 假设让你设计一个支持多种订单类型（如限价单、市价单、冰山订单）的扩展性更强的撮合引擎，你会从架构上如何考虑？

**参考答案**

结论：订单簿只认识「可见数量 + 价位 FIFO」。多种订单类型在进入簿之前变成少数几种命令，由同一条单线程序列执行。

命令保持很少：新单、撤单、改单、触发后转成的普通单。限价单校验价格和数量后，吃得掉的部分成交，剩余挂簿。市价单只吃对手盘，不挂簿，必须带保护价或最大滑点，否则一次扫穿整个簿。冰山单把显示量和隐藏量分开，簿上只有显示量；显示量吃完再补一截。常见规则是补出来的这一截排到该价位队尾，隐藏量不出现在行情里。止损、止损限价先放在按触发价组织的结构里，不进主簿；成交价穿过触发价时，在同一条命令序列里把它变成市价或限价。触发若另开线程读行情，回放结果会不稳定。

扩展点放在簿外：风控、自成交策略、价格带、不同订单类型的预处理。热路径里用有限的类型分支，而不是为每种订单做一次堆分配和接口调用。新类型先证明它能翻译成现有命令，再考虑改簿的数据结构。

改单的规则写进命令定义：改价格通常失去时间优先，只减量通常保留。自成交策略（撤旧、撤新、两边都撤、递减）也是簿外策略，决定之后仍由单写者执行。

正确性靠命令日志回放：同一输入得到同一组成交，冰山的可见量不超过剩余隐藏量，任何类型都不能让盘口交叉。这样做的代价是新类型必须适配命令模型，换来的是撮合循环仍然可解释、可重放。

### 11. 在团队协作中，你是如何保证核心交易模块的代码质量和可维护性的？有哪些实践（如 Code Review，单元测试等）？

**答题思路**

只讲团队里真实在做的实践。没有回放测试就不要说有。可以按这个顺序组织。

1. 核心撮合有明确的所有者。改订单簿、命令顺序和持久化语义的合并请求必须经过评审，评审人数少而固定。
2. 评审单不看排版，看不变量：单写者有没有被新的锁或新的 goroutine 打破，热路径有没有新的分配，撤单和重试是否幂等，成交价是否仍用挂单价格，数量是否守恒。
3. 测试用表驱动覆盖部分成交、全部成交、价格不交叉、时间优先、撤单。若有黄金回放文件，说明它是从哪段真实或脱敏流量来的，断言的是成交序列而不只是「不报错」。
4. `go test -race` 和热点基准进持续集成。基准看分配次数和字节数，不只看纳秒。
5. 线上差错补一条能复现的回归，再修。核心路径上的顺手重构单独开变更，不和行为变更混在一起。

### 12. 目前 AI 在量化交易和策略生成方面有一些应用，你有关注过吗？你认为 AI 技术有可能在撮合引擎的哪些环节带来革新？

**参考答案**

结论：模型适合放在撮合外侧做监视、容量和参数。谁先成交、以什么价格成交，必须仍由确定的价格时间规则决定，否则无法回放，也无法向监管和用户解释。

策略生成是策略团队的上游。引擎把这些订单当成普通订单。模型单通常撤单更多、突发更陡，引擎要准备的是撤单吞吐、队列公平和入口拒绝，而不是在撮合循环里调用模型。

旁边值得做的是：离线或旁路识别幌骗、分层挂单这类异常行为；用历史流量做容量规划，估计热点交易对该留多少核、日志磁盘的尾延迟够不够；盯拒单率、撮合尾延迟和 GC 协助的异常检测。这些输出是告警和建议，不回写订单簿。

手续费、最小变动价位、限仓阈值可以用数据辅助选择，上线前仍用回放验证有没有改变成交顺序。把模型放进撮合循环会引入不确定延迟和不确定结果，和单写者可重放的目标相反。

回答这题时承认边界即可。没有把握的准确率、收益数字不要报。

### 2. 如果你作为这个撮合引擎项目的技术负责人，你会如何规划它的技术演进路线？（考虑性能、功能、可维护性）

**参考答案**

结论：路线按「先能回归，再削热路径，然后加订单类型，最后做切换演练」推进。没有回放的重写，性能和功能都无法证明。

第一步把命令日志、快照和回放对账变成日常工具。断言数量守恒、不交叉盘口、时间优先。之后每一项优化都用同一段流量对比。

性能只改测量点名的地方。典型顺序是：热路径去掉分配，订单簿改成整数下标，撮合线程不碰网络和磁盘，日志组提交，再按机器预算设 `GOMEMLIMIT`。热点交易对独占核心。内核旁路、换语言重写撮合内核，放到回放证明 Go 热路径已经不是瓶颈之后。

功能演进保持命令模型。新订单类型先翻译成新单、撤单、触发，触发和成交走同一条序列。自成交、价格带、拍卖放在簿外策略里。每加一种类型，就加一组回放，而不是加一条只有作者能看懂的分支。

可用性单独排期：主备纪元、旧主不能继续写、定期真的做切换。演练和功能开发错开，避免同一周既改成交规则又改选主。

可维护性靠收窄接口和评审不变量，而不是提前拆成很多微服务。拆分只发生在扩展维度不同的地方：接入可以水平扩展，一个订单簿仍是单写者，清算按事件追。

延迟、可解释和交付速度要同时留在路线图上。一个别人不敢改的极致内核，不算演进成功。

### 3. 在追求极致低延迟的场景下，除了语言和算法优化，还可以从哪些层面（操作系统、网络、硬件）去考虑和优化？

**参考答案**

结论：先去掉调度、中断和电源管理带来的抖动，再考虑少一次网络跳转。这些优化都用同一段回放的尾延迟验收。

操作系统上，撮合线程绑到专用核，IRQ 和别的进程挪走。关掉这颗核的降频和深度睡眠，避免唤醒时的频率抖动。内存和线程放在同一 NUMA 节点。热路径需要的页提前触达并锁在内存里，避免缺页。`SCHED_FIFO` 这类实时优先级要非常小心：撮合线程若占住不让出，GC 和其他系统线程会饿死，尾延迟会以另一种方式爆掉。Go 里更稳的做法是普通优先级、独占核、运行队列保持很瘦，并给 GC 和网络留下别的核。

网络上，接入和撮合同机时，用共享内存或本机队列交接，少一次 TCP。还在用 TCP 时打开 `TCP_NODELAY`，避免小包被攒住。协议用定长或二进制帧。网卡中断合并偏小可以降低延迟，但会增加中断；忙轮询能再降一截，代价是一颗核。Go 的标准网络轮询是 epoll、kqueue 或 IOCP，不是把运行时切到 io_uring 就结束。DPDK 或厂商内核旁路要离开 `net` 包或依赖特定网卡，只有测量表明内核协议栈才是瓶颈时才做。

硬件上，撮合更吃单核主频和稳定的频率，不只是核数。网卡和日志盘尽量走同一颗 CPU 的 PCIe 路径。日志盘看的是 fsync 的尾延迟，用组提交摊薄，而不是每笔都同步刷。BIOS 里关掉省电。超线程对抖动的影响要用实验看，不作为默认信条。

时间同步用 PTP 可以做好审计时间戳。谁先成交仍以进入单写者的序列为准，不用各机墙钟比大小。

### 4. Go 的 sync 包里的锁，在底层与操作系统调度是如何交互的？在协程频繁争抢锁导致性能下降时，除了优化临界区，还有什么高级的应对思路？

**参考答案**

结论：`sync.Mutex` 的快路径只是用户态原子操作，不进内核。争抢失败时挂起的是 goroutine；操作系统线程只有在这个 P 上没有别的 G 可跑时才去休眠。

慢路径先看能不能自旋。大致条件是多核、自旋次数还不多、本地运行队列是空的。自旋是在等持有者马上释放，避免一次调度。自旋不到，就把等待计数加上，当前 G 通过运行时信号量 `gopark`。M 回到调度器执行其他 G。解锁的一方如果发现有等待者，就 `goready` 一个 G，把它放回运行队列。从被叫醒到真正跑起来，中间还有排队，这段延迟通常比临界区本身更显眼。

正常模式允许正在 CPU 上的新 goroutine 插队。等待大约超过 1ms 后进入饥饿模式，锁直接交给队头，新来的到队尾排队。`RWMutex` 的读者和写者最终也走同一类挂起和唤醒。所以「锁住了操作系统互斥量」这个说法不准确：绝大多数争抢停在 Go 调度器，只有 M 无事可做时才进入 futex 一类的内核等待。

争抢已经把尾延迟打高时，缩短临界区只是第一步，接着换结构：

1. 取消共享。订单簿改成单写者，其他协程用 channel 或单生产者环形队列送命令，锁消失。
2. 按交易对或账户分片，让不同键不要抢同一把锁。热计数和锁之间垫开，避免落在同一条缓存行上互相失效。
3. 只读快照用 `atomic.Value` 发布不可变副本，读者不加锁。这适合配置和行情副本，不适合要原地改的订单簿。
4. 单个标志或序号用 `sync/atomic`，并保留 happens-before。不要用原子操作拼一个自己的锁。
5. 把多次唤醒合成一批：一次取出一批命令再处理，减少 park 和 ready 的次数。
6. 临界区里不做网络、不刷盘、不向可能阻塞的 channel 发送、不触发会协助 GC 的分配。
7. 减少争抢者。一百个 goroutine 抢一把锁，换成一个消费者，通常比换锁的实现更有效。

手写无锁订单簿很容易把内存模型写错。没有 profile 证明锁是瓶颈时，清晰的单写者优于一套自研无锁结构。

### 5. 如何设计有效的压测方案来评估撮合引擎的容量和瓶颈？如何模拟真实的市场行情和订单流？

**参考答案**

结论：容量是「在声明过的订单构成下，p99 仍满足目标且成交结果正确」时的吞吐，不是把均匀随机订单打到 CPU 打满。

先写下目标：撮合段的 p99 和 p999、拒绝率上限、以及不变量。然后准备流量。最好回放脱敏后的真实命令；没有录像时，按真实统计去合成，而不是每笔订单独立均匀抽样。至少包含这些倾斜：少数交易对占大部分流量，少数账户是做市商，撤单远多于成交，价格集中在买一卖一附近，爆发段比平稳段高一个数量级并持续数秒。订单类型比例按生产来，包含撤单和改单。

客户端走和线上相同的接入协议，跑在别的机器上，避免压测进程偷撮合的核。同时记录两端时间：客户端往返包含网络，服务端在进入撮合和离开撮合处打点，用来把协议栈和撮合分开。开环按固定速率发送，用来找饱和点；闭环按返回再发，更接近用户等待。两套都要，并写明曲线是哪一种。

阶梯：单交易对、多交易对、一个热点加一组长尾、平稳段后接爆发、满载时做一次主备切换。每级同时看 CPU、分配、锁和阻塞 profile、GC 协助、日志 fsync、入口队列深度和拒绝原因。

正确性用影子回放：把压测期间的命令日志再跑一遍，对比成交。检查数量守恒、盘口不交叉、时间优先。性能达标但成交对不上，这级容量无效。

环境要接近生产的核数、电源策略、`GOMAXPROCS` 和内存上限。容量数字必须连同订单构成一起报。只说一个 QPS，没有意义。

### 6. 在分布式交易系统中，如何保证资金、仓位等核心账务数据的强一致性？是否了解 TCC、Saga 等分布式事务方案，以及它们在交易场景下的适用性。

**参考答案**

结论：强一致落在两处：账户分片上的本地事务，以及撮合命令日志的顺序。跨库的原子提交不放在撮合热路径上。

下单时，在该账户所在的库里用本地事务冻结：可用减少、冻结增加，订单号唯一，余额不足就失败。冻结成功，命令才进入撮合。撮合按单写者产生成交。成交事件带着成交号，买方分片和卖方分片各自入账：冻结转成实际交割，对手资产增加。同一成交号重复到达则空操作。未成交部分在撤单时解冻。任一侧暂时失败就按同一成交号重试，不另造一笔交易。

这要求订单和余额按同一账户分片，冻结才不必跨库。两侧分片都入账之前，用「成交已确认、入账进行中」这样的状态表达，而不是让撮合等两边数据库一起提交。发件箱把「本地入账」和「发出下游消息」放在同一个本地事务里，避免账写了消息没了。

TCC 可以用来描述这条资金边界。Try 是冻结，Confirm 是按成交把冻结转成交割，Cancel 是解冻。Confirm 只允许技术性重试，不能在 Try 已成功后再做一次可能失败的业务校验。Cancel 可能先于 Try 到达，要用事务状态表做成空回滚；迟到的 Try 必须拒绝，避免挂起后再把钱冻上。TCC 的代价是每个资源都要写三个操作。它适合账户冻结，不适合在撮合循环里同步调用双方数据库。

Saga 用一串本地事务加补偿处理长流程，例如出金、法币或上币。成交不适合靠补偿「撤销」：价格已经变了，用户可能已经基于这笔成交做了下一笔。账务上只能追加调整分录，不能删掉原成交。Saga 的中间状态对外可见，隔离性弱。

XA/两阶段提交能提供更强的原子性，但锁和协调者会跨服务持有，协调者故障时还要恢复。它可以出现在低频清算批处理的讨论里，不放在逐笔撮合上。

周期性对账：冻结金额等于未完成订单，两侧成交之和相等，账户合计能对上出入金。对账发现的差异走调整流程，不回改已经发布的成交顺序。

### 7. 当团队在引入一项新技术（例如，尝试用 Rust 重写部分性能关键模块，或引入新的流处理框架）时，作为技术核心，你会从哪些维度来评估和决策？

**参考答案**

结论：先用现有系统的 profile 和回放证明瓶颈，再做有退出条件的试验。换语言或换框架本身不是目标。

看这些维度。

1. 证据。热点是分配、锁、fsync 还是下游。说不清瓶颈时不启动重写。
2. 正确性。新撮合内核必须吃同一条命令日志，成交差分是零。内存安全并不自动保证价格时间优先。
3. 延迟。用生产形态的回放比 p99 和 p999，同时看资源占用。Rust 没有 GC 停顿；若结果要穿过 FFI 或进程边界再拷贝回来，收益可能被边界吃掉。只重写已经证明热的那一段，编排和外围仍可以留在 Go。
4. 失败方式。流处理框架要看背压、检查点、重复投递和操作方式。它提供的语义如果团队不会在故障时用，就只是新的运行负担。
5. 运维。上线、观测、回滚和值班技能是否够。凌晨没人能看懂的栈，算可靠性风险。
6. 迁移。并排跑、对比输出、按交易对切换、能退回旧实现。不做一次性切流。
7. 成本。同样的人月若用来去掉热路径分配就能达标，就不必引入第二门语言。

试验开始前写退出条件：回放差分为零，尾延迟达到事先定的目标，值班能独立排障。做不到就停，并留下记录。避免只因为技术新而扩大范围。

### 8. 在带领或指导新人时，你会如何帮助他快速理解并上手像撮合引擎这样复杂的系统？

**答题思路**

按「一条路径、一组不变量、一个小改动」带，不要先讲完所有目录。

1. 一起走一笔限价单：从接入、冻结、进入单写者、成交、出站到入账。让他能在白板上画出这条路径，并指出哪一段是单写者。
2. 给不变量，不给实现细节清单：成交价用挂单价格、同一价位 FIFO、数量守恒、热路径不分配。让他用一笔部分成交把这四条对上。
3. 第一周的改动选有测试或回放罩着的小行为，例如一种拒绝原因或一条日志。核心循环里的顺手重构明确先不做。
4. 拿一笔异常单一起看命令日志和回放差异，演示「先重放，再改代码」。
5. 说清提问方式：卡住超过一段时间就带着他的假设来问，而不是自己在撮合循环里试。

人选、周期和你们仓库里的真实模块名，用实际情况填。没有导师制度就讲你实际会怎么做，不要编一套没运行过的培养体系。

### 9. 当你与业务方（如策略团队）或跨部门（如清算团队）对技术方案或排期有分歧时，你通常如何处理以达成共识并推进项目？

**答题思路**

用一次真实分歧来讲。没有现成故事就按这个骨架准备，不编排期和损失金额。

1. 把分歧写成可核对的约束：撮合尾延迟、资金入账的截止、回放必须通过的不变量。先确认双方争的是不是同一段链路。
2. 策略侧关心的是成交公平和可预期，清算侧关心的是账能平。很多方案可以把「撮合序列」和「清算追账」拆开，不必绑成一个同步调用。
3. 给出两个可选方案，每个写明代价：谁变慢、谁承担不一致窗口、回滚怎么做。能用一段回放或一笔对账差异说明的，不用形容词。
4. 决定权跟着风险走。资金正确性给清算和风控否决权；排期用范围切开，先上主路径，把触发类订单或新协议留到下一档。
5. 把决定、放弃的方案和回滚条件记下来，避免下次会议从头争。

语气保持在事实和选项上。不要把对方讲成不讲理来突出自己。

### 10. 最近半年，你在技术领域（不限于 Go）重点学习和研究的是什么？是什么驱动你去学习它？你是通过什么方式系统学习的？

**答题思路**

只讲一件真在学的东西，不要报一串名词。

1. 它是什么，用两三句讲到能让面试官追问的深度。例如你真的读过的调度、存储或一致性主题。没把握讲源码级细节的，就不要选。
2. 驱动来自具体缺口：线上某类尾延迟讲不清、下一次设计要用、或者面试和评审里自己答虚过。不要说「为了保持竞争力」这种空话。
3. 学习方式按真实路径：先官方文档或规范，再读对应实现，然后做一个能失败的小实验，或者在自己的项目里改一处并用测试验证。文章用来找地图，不能代替实验。
4. 收尾讲一个你因此改变的做法或一个你现在能讲清的取舍。学完没有产出，就承认还在中途，说清下一步验证什么。

没有最近半年的主题就诚实缩小范围，讲你为这次撮合面试重新核对过的一个机制，以及你怎么核对的。不要临时编一个研究方向。
