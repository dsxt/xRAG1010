# KuCoin 半远程 AI Agent

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这场面试偏工程落地，不是背八股的场子。面试官不想听 RAG 流程图复述，三层记忆、Harness、多 Agent、GraphRAG 一上来就往生产问题上问。答得扎实时像在聊架构，答得虚就会被追问成本、评测、权限和回放。半远程不是福利，而是要自己把交付扛住。只会用 Spring Boot 加 ChatClient 调模型的话，进去会被问得很吃力。真做过 Agent 落地的人会越聊越顺，没做过的人到第三轮就容易露怯。

## 一面

### 1. 请做一个自我介绍

**答题思路**

控制在 1.5 到 2 分钟，按"身份 → 主线经历 → AI 相关亮点 → 为什么匹配这个岗位"来讲：

1. 一句话定位：几年 Java 后端经验，近期转向 AI Agent 工程落地。
2. 后端底子：讲你真正做过的高并发、稳定性、数据一致性方面的经验，这是 Agent 上生产的基础。
3. AI 项目：用一两句话说明做过的 Agent / RAG 项目、你负责的模块（意图路由、检索、记忆、工具调用、评测等）和可量化的结果。数字必须是你自己的真实数据。
4. 匹配点：交易所类业务对稳定性、合规、权限、幂等要求高，而这些正是你的强项；半远程也要求自驱和异步沟通。
5. 收尾：把话题引到下面要展开的项目上。

### 2. 最近做的 AI Agent 项目介绍

**答题思路**

用 STAR 加架构图的方式，建议 3 到 4 分钟：

1. 背景与目标：解决什么业务问题，用户是谁，为什么要用 Agent 而不是普通接口或规则。
2. 整体架构：入口 → 意图识别 → 路由 → RAG / 工具 / 工作流 → 生成 → 安全与审核 → 输出，另有记忆、日志、评测几条旁路。
3. 你的职责：讲清你亲自设计和落地的部分，不要把团队成果都说成自己的。
4. 关键难点与取舍：例如检索不准、工具调用不稳、上下文膨胀、成本控制，每个难点说明方案和效果。
5. 结果与复盘：任务成功率、响应耗时、成本等指标用真实数据，再补一句下一步优化方向。

准备好被追问：为什么这样选型、哪里最难、线上出过什么问题、怎么评测。

### 3. 你们这套 Agent 是面向交易/行情/客服/运营哪种业务，整体链路怎么画

**答题思路**

先回答业务场景（选你真实做过的那类），再讲链路。链路可以按下面的顺序组织：

1. 入口层：网关、鉴权、限流、用户身份与权限上下文透传。
2. 前置治理：输入安全检测、敏感信息脱敏、风控与合规规则。
3. 意图识别与路由：规则 → 小模型 → LLM 分层，输出意图、置信度和槽位。
4. 能力层：按意图进入 RAG 问答、工具调用（只读查询或写操作）或固定工作流。
5. 编排与 Harness：上下文装配、工具调度、重试和降级、步数与预算限制。
6. 生成与后置审核：答案依据校验、合规话术、敏感信息过滤。
7. 旁路：记忆读写、trace 与日志（Kafka 异步落库）、评测与反馈回流。

画图时强调两点：读写权限分离（写操作必须经审批或确认），以及每一层都有降级路径。

### 4. 意图识别怎么做，规则、分类模型、LLM 路由分别用在哪一层

**参考答案**

意图识别用"规则 → 小分类模型 → LLM 路由"逐层兜底，层层升级，既控成本又保准确。

- **规则层**：处理确定性强的输入，例如固定指令、菜单点击、关键词和正则（订单号、币对）、敏感词和黑白名单。延迟接近零、可解释、零成本，适合做安全前置拦截。
- **分类模型层**：针对高频、边界清晰的意图，用小模型（微调的 BERT 类模型或 embedding 加分类头）。延迟低、可离线评测，输出意图和置信度。
- **LLM 路由层**：处理长尾、模糊、多意图和强依赖上下文的请求，要求输出结构化 JSON，并用枚举约束意图集合。

升级条件是置信度低于阈值、多个意图分数接近或规则未命中。LLM 的输出还要经过合法性校验，不在意图表内的归为未知并兜底。容易漏掉的点是：意图集要版本化，并配回归集，否则新增意图会让旧意图的准确率悄悄下降。

### 5. 用户说"帮我看看我账户是不是有点不对"，这种模糊输入怎么判别意图

**参考答案**

不要硬猜单一意图，而是输出候选意图集合，结合上下文取证，再决定澄清还是走安全的只读路径。

1. **候选展开**：这句话可能对应余额或资产异常、订单异常、登录与安全异常、风控冻结、费率疑问等多个意图，LLM 或分类模型输出 top-k 及置信度。
2. **上下文取证**：用已鉴权的用户身份，调用只读工具拉取近期登录记录、资产变动、订单状态、风控状态，结合最近对话判断偏向哪类。
3. **决策**：某一意图置信度明显领先时直接进入对应流程。分数接近时给出有限选项让用户选择，或追问一个关键问题，例如"是资产数字不对，还是有陌生登录或操作"。
4. **安全优先**：只要候选中包含账户被盗这类高风险意图，就先走只读诊断和风险提示，绝不默认执行任何写操作。
5. **反馈**：记录用户最终选择，作为意图集的训练和评测样本。

### 6. 意图识别和下游工具路由怎么解耦，避免改一个意图全链路炸

**参考答案**

核心是在"意图"和"工具"之间加一层稳定的能力（capability）契约，用配置驱动路由，而不是在代码里硬编码 if-else。

- **意图注册表**：每个意图声明名称、版本、所需槽位、对应的 capability 或 workflow，配置化管理，可灰度。
- **路由表**：intent → capability → tool 是多对多映射，工具通过 JSON Schema 注册，上游不感知工具实现细节。
- **契约稳定**：意图识别只输出标准结构（intent、confidence、slots），下游只依赖这个结构。改意图内部逻辑不影响接口。
- **版本与灰度**：意图集和路由表版本化，新增或修改先灰度，旧版本可回滚。
- **回归保障**：维护意图回归集和工具契约测试，任何意图改动自动跑一遍，提前发现影响面。
- **兜底**：未知意图和路由失败统一走默认处理，避免一个节点失败拖垮整条链路。

### 7. RAG 多路召回你们做了几路，向量、BM25、图谱、元数据过滤各自解决什么问题

**参考答案**

多路召回是为了让不同检索方式互补，路数以实际项目为准，常见是这四类。

- **向量召回**：解决语义相近但字面不同的问题，例如同义改写、口语化提问。弱点是对编号、专名、错误码不敏感。
- **BM25 / 关键词召回**：解决精确匹配，例如订单号、币对、合约代码、错误码、专有名词。弱点是不懂语义。
- **图谱召回**：解决实体间关系和多跳问题，例如"某规则影响哪些产品"或"这个账户关联了哪些设备"。依赖实体抽取和图谱质量。
- **元数据过滤**：不是召回而是约束，作为硬条件在检索时做 pre-filter，包括权限、租户、时间、文档版本、语种和业务线。它既保证安全合规，也能显著缩小搜索空间。

回答时可以说明：你实际做了几路，为什么这样取舍，每路对召回率的增量是多少（用自己的评测数据）。容易漏的点是权限过滤必须在召回阶段完成，不能等生成后再过滤。

### 8. 多路召回结果分数不可比，怎么融合、去重、再 Rerank

**参考答案**

不同召回路的分数量纲不同（余弦相似度、BM25 分、图跳数），不能直接相加，应该用基于排名的融合。

1. **融合**：常用 RRF（Reciprocal Rank Fusion），每路按排名贡献 `1/(k+rank)`，累加后排序，k 常取 60。优点是无需归一化分数，对异常分数不敏感。也可以做 min-max 或 z-score 归一化后加权，但权重需要用评测集调。
2. **去重**：先按 chunk_id 或文档版本去重，再用内容哈希去完全重复，必要时用 simhash 或向量相似度去近似重复，并保留来源较新的版本。
3. **Rerank**：对融合后的前 50 到 100 条用 cross-encoder 类重排模型精排，取前 5 到 10 条进入上下文。可结合 MMR 提升多样性。
4. **注意点**：rerank 会增加延迟，要控制候选数量并设置超时降级（超时就用融合结果）。最终保留引用来源，便于溯源和评测。

### 9. 三层记忆怎么分：短期、工作记忆、长期记忆分别放哪、怎么写回、怎么淘汰

**参考答案**

三层记忆按生命周期和用途区分。

| 层 | 内容 | 存放 | 写回 | 淘汰 |
|---|---|---|---|---|
| 短期记忆 | 当前会话最近若干轮消息 | 上下文窗口，Redis 持久化会话 | 每轮追加 | 滑动窗口，会话 TTL |
| 工作记忆 | 当前任务的计划、已完成步骤、槽位、工具中间结果 | Agent State，checkpoint 到 Redis 或数据库 | 每个节点执行后更新 | 任务结束即归档或清理 |
| 长期记忆 | 跨会话的用户偏好、稳定事实、历史结论 | 向量库加 KV 或 MySQL | 会话结束或关键事件后异步抽取 | TTL、重要性打分、时间衰减、容量上限 |

长期记忆的写回要点：异步抽取、与已有记忆去重合并、冲突时以新信息覆盖并保留来源和时间、带置信度。不要把原始对话全量写入。容易说漏的是隐私合规（可查询、可删除）和防止被注入的内容污染长期记忆。

### 10. 上下文快爆了的时候，摘要压缩、滑动窗口、关键事实抽取怎么配合

**参考答案**

三者按"原文、摘要、事实"分层配合，目标是在 token 预算内尽量不丢关键信息。

1. **滑动窗口**：保留 system prompt 和最近 N 轮原文，保证当前对话的连贯性。
2. **摘要压缩**：窗口之外的较早对话做滚动摘要，每次只摘要新滑出的部分并并入已有摘要，避免反复重写。
3. **关键事实抽取**：用户约束、ID、金额、币对、偏好、已确认的决定这类不能丢的信息，抽取为结构化字段单独存储，每轮固定注入。摘要是有损的，所以关键事实不能只依赖摘要。
4. **其他手段**：工具的大输出做截断或只放引用 ID，检索结果按预算分配 token。
5. **触发**：按 token 占用比例设置阈值触发压缩，并给 system、事实、摘要、近期原文、检索结果各自设定预算。

压缩本身要评测，对比压缩前后的任务成功率，避免摘要引入错误。

### 11. 图数据库在 Agent 里存什么，和向量库的职责边界在哪

**参考答案**

图数据库存"实体与关系"，向量库存"文本内容的语义表示"，两者互补，通过 ID 关联。

- **图数据库**：存实体和关系，例如用户、账户、订单、设备、产品、规则和政策之间的关联。擅长多跳查询、路径、关联分析，结果是结构化且可解释的。
- **向量库**：存非结构化文本块的 embedding，擅长按语义相似度找内容，不擅长表达精确关系和多跳推理。

边界可以概括为：回答"谁和谁有什么关系、经过几跳到达"用图，回答"哪段内容语义上最相关"用向量。实践中图节点可以保存关联的 chunk_id，向量库的 chunk 元数据里保存 entity_id，让两边可以互相跳转。注意两边数据的一致性维护，以及图扩展时要限制跳数，避免爆炸。

### 12. LangChain 和 LangGraph 在你项目里分别承担什么角色，为什么不是只用 Chain

**参考答案**

LangChain 提供组件，LangGraph 负责有状态的流程编排。

- **LangChain**：提供模型封装、Prompt 模板、工具抽象、Retriever、输出解析等基础组件，以及线性的链式组合，适合"检索 → 生成"这类单向流程。
- **LangGraph**：把流程建模为带共享状态的图，节点是函数，边可以带条件。它原生支持循环、条件分支、并行、checkpoint 持久化、中断恢复和人工介入。

只用 Chain 不够的原因：Agent 的本质是"思考 → 调用工具 → 观察 → 再思考"的循环，还要处理失败重试、条件分支、多 Agent 协作、审批断点和故障恢复。纯线性的 Chain 表达这些会写成一堆嵌套逻辑，状态难以持久化，也很难回放。所以通常是 LangChain 组件加 LangGraph 编排。

### 13. Redis 在 Agent 系统里除了缓存，还能做会话状态、限流、锁、任务队列吗，怎么用

**参考答案**

都可以，但要清楚各自的边界。

- **会话状态**：用 Hash 或 String 存会话消息和工作状态，设置 TTL，也可作为 LangGraph checkpointer 的后端。
- **限流**：按用户或租户做令牌桶或滑动窗口，可用 Lua 脚本保证原子性，也可以对 token 消耗做配额限流。
- **分布式锁**：`SET key value NX PX` 加唯一 value，释放时用 Lua 校验 value 再删除。要考虑锁过期与业务耗时，必要时用 Redisson 的看门狗续期。对强一致场景还要配合 fencing token 或数据库唯一约束。
- **任务队列**：List 实现简单但可靠性弱。Stream 加消费组支持 ACK、pending 重试，更适合轻量任务队列。高可靠、大吞吐、需要回放的场景更适合 Kafka 或专业 MQ。
- **其他**：幂等键快速拦截（`SET NX`）、语义缓存、热点数据缓存。

容易漏的点是 Redis 数据可能丢失（主从异步复制、持久化策略），资金类的最终一致性不能只靠 Redis。

### 14. MySQL 存 Agent 执行日志和会话记录，表怎么设计，热点表怎么治

**参考答案**

按"会话 → 运行 → 步骤"三级建模，大字段外置。

- **会话表 session**：session_id、user_id、渠道、状态、创建和更新时间。
- **消息表 message**：session_id、seq、role、内容、token 数、created_at。索引 `(session_id, seq)`。
- **运行表 agent_run**：run_id、session_id、trace_id、状态、模型和 prompt 版本、总 token、总耗时、错误码。
- **步骤表 step**：run_id、step_no、类型（llm 或 tool 或 retrieval）、工具名、参数和结果摘要、耗时、状态、错误码。

大段的 prompt、response 和检索原文放对象存储或 ES，表里存引用，避免行过大拖慢查询。主键用自增或雪花 ID，避免随机 UUID 造成页分裂。

热点治理：

- 日志写入走 Kafka，消费端批量插入，削峰。
- 按时间分区或分表，冷热分离，历史数据归档到 ClickHouse 或 ES 做分析。
- 热点行（如计数、累计 token）用 Redis 聚合后定时回写，避免单行争用。
- 查询统一带 `user_id` 或时间范围，避免全表扫描。
- 必要时读写分离。

### 15. 手撕算法：给定一个意图标签列表和用户输入，实现一个最简意图路由函数，支持关键词命中、兜底未知意图、返回路由结果对象

**参考答案**

思路：对每个意图遍历其关键词，统计命中的关键词，以命中关键词长度之和作为得分（更长的关键词更具体）。取得分最高的意图，没有命中则返回兜底的 `unknown`。得分相同时保留先声明的意图，保证结果确定。

```python
from dataclasses import dataclass, field


@dataclass
class RouteResult:
    intent: str
    score: int = 0
    matched: list[str] = field(default_factory=list)
    is_fallback: bool = False


def route(text: str, intents: dict[str, list[str]], min_score: int = 1) -> RouteResult:
    t = text.lower()
    best = None
    for name, keywords in intents.items():
        hits = [k for k in keywords if k.lower() in t]
        if not hits:
            continue
        score = sum(len(k) for k in hits)
        if best is None or score > best.score:   # 严格大于：平局取先声明的
            best = RouteResult(name, score, hits)
    if best is None or best.score < min_score:
        return RouteResult("unknown", 0, [], True)
    return best


if __name__ == "__main__":
    intents = {
        "query_balance": ["余额", "资产"],
        "query_order": ["订单", "委托"],
        "withdraw": ["提币", "提现"],
    }
    print(route("帮我查一下订单状态", intents))
    print(route("今天天气怎么样", intents))
```

复杂度：设意图数为 K、关键词总数为 M、文本长度为 L，时间约 O(M·L)，空间 O(K)。关键词很多时可以改用 Aho-Corasick 自动机，一次扫描完成多模式匹配。可以补充说明：真实系统里这只是规则层，未命中会继续走分类模型和 LLM 路由，并且要处理否定、多意图并列等情况。

### 1. 请做一个自我介绍

**答题思路**

二面更偏技术深度，自我介绍要比一面更聚焦：

1. 开头一句话交代年限和方向。
2. 直接切到最相关的 Agent 项目，用三句话讲清架构、你的职责和最难的点，把话题引向工作流、状态管理、工具调用、RAG 和评测这些二面常问的内容。
3. 补充工程底子：并发、幂等、一致性、稳定性方面的实战经验，说明它们如何用在 Agent 落地中。
4. 以匹配度收尾，说明为什么适合这个岗位，包括对半远程协作的适应。

不要重复一面的完整版本，注意节奏，留出让面试官追问的空间。

### 2. 继续深挖项目：你们 Agent 工作流是哪几类节点，条件分支和循环怎么落

**答题思路**

先讲节点分类，再讲分支和循环，最后讲踩坑。按你的真实项目回答，可参考以下结构：

1. 节点类型：意图和路由节点、检索节点、LLM 推理或生成节点、工具调用节点、条件判断节点、人工审批节点、子 Agent 或子图节点、汇总和结束节点。
2. 条件分支：用条件边加路由函数，依据 State 里的字段（意图、置信度、校验结果、风险等级）决定下一个节点。强调分支条件尽量基于可校验的结构化字段，而不是让模型自由文本决定。
3. 循环：典型是"推理 → 工具 → 观察 → 再推理"的回边，必须配套最大步数、总 token 预算、总超时和重复调用检测，超限后走兜底节点。
4. 失败路径：每个关键节点都设计失败边（重试、降级、转人工）。
5. 状态与恢复：每个节点后做 checkpoint，支持断点恢复和回放。
6. 复盘：讲一个因为分支或循环设计不当出过的问题和修复，指标用真实数据。

### 3. LangGraph 的 State、Node、Edge、Condition、Checkpointer 怎么映射到你们业务

**参考答案**

这五个概念对应一个有状态工作流的全部要素：

- **State**：整个图共享的状态，通常是 TypedDict 或 Pydantic 模型，包含消息、意图、槽位、检索结果、工具结果、步数等。每个字段可以指定 reducer，例如消息列表用追加的方式合并。映射到业务就是"一次任务的完整上下文"。
- **Node**：接收 State 并返回对 State 的更新的函数，例如意图识别、检索、调用工具、生成回答、审批。
- **Edge**：节点之间固定的流转，例如检索完成后进入生成。
- **Condition（条件边）**：路由函数读取 State 返回下一个节点名，例如置信度低去澄清，需要工具则去工具节点，已完成则结束。也是实现循环的方式。
- **Checkpointer**：每个执行步骤后保存 State 快照，按 `thread_id` 区分会话。它支撑故障恢复、`interrupt` 暂停加人工审批后恢复、历史回溯与回放。开发用内存实现，生产要用持久化后端（如 Postgres 或 Redis）。

举例映射：客服类任务中，State 存会话与槽位，意图节点后用条件边分流到知识问答或工单查询，高危操作前设置 interrupt 等待审批，Checkpointer 让审批可以隔天再继续。

### 4. 如果不用 LangGraph，用 Java 自己写一套 Agent 状态机，你怎么设计

**参考答案**

核心是"显式状态加节点加迁移规则加持久化的执行引擎"。

1. **模型**：`State` 是可序列化的上下文对象，包含运行 ID、当前节点、业务数据、步数和版本。`Node` 是接口，输入 State，返回 `NodeResult`（状态更新加建议的下一个节点或状态码）。
2. **迁移**：用迁移表或条件函数 `(state) -> nextNode`，把路由逻辑和节点逻辑分开。
3. **引擎循环**：取当前节点 → 执行（带超时）→ 合并结果 → 持久化 checkpoint → 计算下一个节点，直到结束、步数超限、预算耗尽或超时。
4. **异常**：节点声明重试策略和失败节点，失败迁移到降级或人工节点。
5. **中断恢复**：节点返回 `WAITING`，引擎保存状态并退出，外部审批后调用 `resume(runId, input)` 继续。
6. **并行**：fork 节点并行执行多个分支，join 节点按 reducer 合并结果。
7. **幂等和可观测**：每个节点执行带 step_id，副作用节点要幂等，每步产生事件用于 trace 和回放。

```java
public interface Node {
    NodeResult execute(AgentState state) throws Exception;
}

public record NodeResult(Map<String, Object> updates, String next, Status status) {}

public class Engine {
    public AgentState run(AgentState s, Map<String, Node> nodes,
                          Router router, CheckpointStore store, int maxSteps) {
        while (s.step() < maxSteps && !s.isFinished()) {
            Node node = nodes.get(s.current());
            NodeResult r = node.execute(s);
            s = s.merge(r.updates()).nextStep();
            store.save(s);                            // 每步落 checkpoint
            if (r.status() == Status.WAITING) return s;   // 等待审批后 resume
            s = s.moveTo(r.next() != null ? r.next() : router.route(s));
        }
        return s;
    }
}
```

权衡：自研可控、与 Java 微服务集成方便，但要自己实现可视化、回放和生态集成。

### 5. Harness 工程你是怎么理解的，上下文装配、工具调度、异常兜底、回放评测分别在哪一层

**参考答案**

Harness 指围绕模型的整套工程运行时：模型负责推理，Harness 负责让它在受控环境里可靠地完成任务。可以分成四层。

- **上下文装配（输入层）**：组装 system prompt、历史、记忆、检索结果和工具描述，做 token 预算和裁剪，决定模型"看到什么"。
- **工具调度（执行层）**：工具注册和 Schema 校验、权限检查、超时、重试、并发控制、结果清洗，决定模型"能做什么、怎么做"。
- **异常兜底（控制层）**：最大步数、预算、重复调用检测、失败降级、熔断、转人工，保证出错时系统可控。
- **回放评测（观测与评测层）**：完整记录每步的输入、输出和工具结果，支持用记录的数据确定性回放，配合评测集做回归和对比。

关键认识：Agent 的可靠性大部分来自 Harness，而不是 prompt。容易漏掉的是，回放要求工具调用结果可以被 mock 或录制，否则无法复现问题。

### 6. 工具调用失败有哪些类型：参数错、超时、返回脏数据、模型乱调用怎么分别处理

**参考答案**

不同类型的失败，处理策略不同。

- **参数错误**：调用前用 JSON Schema 校验（类型、必填、枚举、范围）。校验失败就把结构化错误信息返回给模型让其修正，限制修正次数（例如两到三次），仍失败则向用户澄清或降级。
- **超时**：每个工具设置独立超时。只读和幂等工具可以指数退避加抖动重试，配合熔断和降级。写操作超时不能盲目重试，应先用幂等键查询操作状态再决定。
- **返回脏数据**：对返回做 Schema 校验和字段清洗，截断过长内容，异常数据标记为不可用而不是交给模型猜测。外部来源的内容视为不可信数据，不能当作指令。
- **模型乱调用**：按意图和权限限制可见工具集（白名单），参数做业务范围校验，检测重复调用和死循环，设置步数上限，高危工具加审批。权限校验放在代码层，不能只依赖 prompt。

所有失败都要有明确的错误码和 trace 记录，便于统计和回放。

### 7. Agent 调创建订单/转账/提币类工具，幂等键怎么设计，重试怎么不重复下单

**参考答案**

原则是幂等键由业务意图确定，在重试之间保持不变，并由服务端用唯一约束保证。

1. **键的生成**：键不能由模型每次调用时随意生成，也不能每次重试都重新生成。可以在 Agent 平台层针对"某次运行中的某一步操作"生成稳定的 `request_id`，例如基于 `run_id + step_id + 操作类型` 生成，并在执行前随 checkpoint 持久化。重试和恢复都复用同一个键。
2. **服务端去重**：在订单或交易表建立 `(user_id, idempotency_key)` 唯一索引。处理流程是先插入"处理中"记录，成功后执行业务，再写入结果。重复请求命中唯一键时直接返回原结果。
3. **参数一致性**：同一个键但请求参数不同，应返回冲突错误，而不是执行。
4. **Redis 的作用**：`SET NX` 只做快速拦截，最终正确性依赖数据库唯一约束。
5. **超时未知结果**：不要直接重试，先按幂等键或业务单号查询真实状态，再决定是否重放。
6. **下游透传**：对接下游交易系统或链上提币时，把幂等键作为 client_order_id 一并传递。
7. **额外保护**：这类操作还要叠加风控、限额和人工审批，幂等只解决"不重复"，不解决"该不该做"。

### 8. 多 Agent 协作有哪些拓扑：Supervisor、Handoff、Debate、DAG 你选哪种

**参考答案**

四种拓扑适用场景不同，没有绝对优劣。

- **Supervisor（主管模式）**：一个主管 Agent 负责拆解任务、分派给子 Agent 并汇总。优点是集中控制、易于审计和限权，缺点是主管成为瓶颈和单点，且多一次模型调用。
- **Handoff（交接）**：当前 Agent 把控制权和上下文转交给更专业的 Agent，例如通用客服转交专业的风控 Agent。结构简单，适合按领域分流，但容易出现来回交接。
- **Debate（辩论）**：多个 Agent 互相质疑后给出结论，适合高价值、需要提升判断可靠性的场景，成本高、延迟大。
- **DAG（有向无环图）**：预先定义任务依赖，可并行，确定性强、易测试，适合流程相对固定的场景，灵活性差一些。

选择：默认以 Supervisor 为主，子流程里流程固定的部分用 DAG 并行，领域分流用 Handoff，Debate 仅用于少数关键判断。更重要的原则是，能用单 Agent 加工具解决的就不上多 Agent，因为多 Agent 会显著增加成本、延迟和调试难度。

### 9. 多 Agent 之间上下文怎么传，怎么防止消息膨胀和角色越权

**参考答案**

**上下文传递**：不要把完整历史转发给每个 Agent，而是传结构化的任务单，包含目标、约束、必要输入和期望输出 Schema。共享状态可以用"黑板"（共享 State），每个 Agent 只读取和写入各自负责的字段。子 Agent 只返回结果和简短摘要，必要时返回引用 ID，主 Agent 再按需取详情。

**防止消息膨胀**：对历史做滚动摘要，大块内容用引用而不是内联，为每个 Agent 设定 token 预算，Agent 之间的消息用结构化格式而不是自由对话，同时限制交互轮数。

**防止越权**：

- 每个 Agent 有独立的工具白名单和身份，权限由执行层代码校验，不依赖 prompt 约束。
- 遵循最小权限原则，只传递完成任务所必需的数据和凭证。
- 高危工具集中在少数受控 Agent，并要求审批。
- 一个 Agent 的输出对下游而言是不可信输入，不能直接作为指令执行。
- 所有跨 Agent 调用都要审计记录。

### 10. RAG 切片策略怎么定，固定长度、语义切、标题层级、表格/PDF 分别怎么处理

**参考答案**

切片没有银弹，从简单基线开始，再用检索评测数据驱动调整。

- **固定长度**：按 token 或字符数切，加一定比例的重叠，实现简单，是基线方案。缺点是可能切断语义。
- **语义切分**：按段落或句子边界，或基于相邻句 embedding 相似度的断点切分，让每块语义完整。
- **标题层级**：对 Markdown、HTML 和规章类文档，按章节结构切，并把标题路径作为前缀放进 chunk，保留上下文。也可以做父子分块：用小块检索，命中后返回所属的大块给模型。
- **表格**：不要从中间切开。小表整体作为一块，大表按行分组并在每块重复表头，转成 Markdown 或结构化文本，并可附带简短的自然语言描述以提升召回。
- **PDF**：先做版面解析，去除页眉页脚，处理多栏和跨页表格，扫描件先 OCR，保留页码和章节作为元数据。

所有 chunk 都要带上元数据（文档 ID、版本、章节、页码、权限），便于过滤和溯源。chunk 大小、重叠比例用评测集上的召回率和答案质量来定，而不是凭感觉。

### 11. 文档更新后向量库怎么增量同步，旧 chunk 怎么删，冲突版本怎么优先用新的

**参考答案**

核心是用稳定的文档标识加内容哈希做变更检测，以文档为单位原子替换。

1. **变更检测**：每个文档有 `doc_id` 和版本号，记录内容哈希。更新事件到来时（可用 CDC 或 Kafka 事件驱动）对比哈希，没变化则跳过。
2. **增量重建**：重新切片，对每个 chunk 计算哈希，只对新增或变化的 chunk 重新 embedding，复用未变化的向量，节省成本。
3. **写入与切换**：新版本 chunk 先以待生效状态写入，全部成功后切换为生效，再删除旧版本，避免出现"旧的已删、新的未写完"的空窗期。
4. **删除旧 chunk**：按 `doc_id` 加旧版本号批量删除，或按哈希差集删除。先软删除，延迟物理清理，便于回滚。
5. **冲突版本**：元数据记录 `version`、`updated_at`、`effective_time`。检索时默认只检索生效的最新版本，必要时把版本新旧作为排序因素，来源冲突时按来源可信度处理。
6. **幂等**：消费事件按"至少一次"设计，用文档 ID 加版本去重。
7. **模型变更**：更换 embedding 模型需要全量重建，用新旧双索引并行切换，不能混用不同模型的向量。

### 12. Kafka 在 Agent 系统里能干什么：任务队列、日志回流、评测数据、异步 embedding 写入

**参考答案**

Kafka 适合"异步、解耦、削峰和可回放"的场景。

- **任务队列**：长耗时 Agent 任务异步执行，用会话或任务 ID 作分区键保证同一会话内的顺序。Kafka 没有单条消息的 ACK 重试，需要自己设计重试 topic 和死信队列。
- **日志回流**：trace、工具调用、模型调用事件异步写入 Kafka，再落到 ES、ClickHouse 或数仓，避免日志写入拖慢主链路。
- **评测数据**：线上的 badcase、用户反馈和接管记录采样后流入评测数据管道，离线构建评测集和回归集。
- **异步 embedding 写入**：文档变更事件 → 切片 → embedding → 写向量库，削峰并控制对 embedding 接口的调用速率。

注意事项：消费语义通常是至少一次，消费端必须幂等；注意分区键的选择和消费积压监控；消息不要携带过大的全文，放引用即可；对需要强事务或严格顺序的资金类写操作，不要只依赖消息队列。

### 13. Elasticsearch 和向量库混合检索时，分词、同义词、编号、专名这些坑怎么处理

**参考答案**

向量擅长语义，ES 擅长精确和词法，各自的坑要分别处理。

- **分词**：中文使用 IK 等分词器，并加载领域词典（币种名、产品名、行业术语），否则专名会被错误切开。常见做法是索引时用细粒度、搜索时用粗粒度，具体以评测为准。
- **同义词**：通过同义词过滤器配置，优先放在搜索时分析阶段，修改词表时不必重建索引。词表要持续维护并审核，避免过度扩展带来噪声。
- **编号和专名**：订单号、合约代码、错误码这类标识用 `keyword` 字段精确匹配，不要分词，必要时辅以 ngram 做前缀或模糊匹配。检测到查询中含有编号，直接走精确过滤。向量模型对编号不敏感，所以必须保留词法通道。
- **归一化**：统一大小写、全半角和符号，避免因格式不同而漏召回。
- **融合**：BM25 和向量的分数不可比，用 RRF 按排名融合，再接 rerank。
- **过滤**：权限、版本、时间等元数据作为过滤条件同时作用于两路检索。

调优以评测集为准，分别观察编号类、专名类和口语类查询的召回率。

### 14. 手撕算法：实现一个带最大步数限制的 ReAct 循环骨架，每轮输出 thought、tool、observation，死循环要能强制退出

**参考答案**

思路：循环最多执行 `max_steps` 轮。每轮让模型返回 thought 和动作，若返回最终答案则结束；否则执行工具得到 observation，追加到轨迹中。强制退出有三道保险：步数上限、相同调用重复超过阈值（检测死循环）、工具异常转成 observation 而不是崩溃。超限后返回已有轨迹和明确的状态，由上层兜底。

```python
import json
from typing import Any, Callable


def react(question: str,
          llm: Callable[[str, list], dict],
          tools: dict[str, Callable[..., Any]],
          max_steps: int = 8,
          max_repeat: int = 2) -> dict:
    """llm 返回: {"thought": str, "action": {"tool": str, "args": dict}} 或 {"thought": str, "final": str}"""
    trace: list[dict] = []
    seen: dict[str, int] = {}

    for step in range(1, max_steps + 1):
        out = llm(question, trace)
        thought = out.get("thought", "")

        if out.get("final") is not None:
            return {"status": "done", "answer": out["final"], "trace": trace}

        action = out.get("action") or {}
        tool, args = action.get("tool"), action.get("args", {})

        key = f"{tool}:{json.dumps(args, sort_keys=True, ensure_ascii=False)}"
        seen[key] = seen.get(key, 0) + 1
        if seen[key] > max_repeat:                      # 重复调用，判定为死循环
            trace.append({"step": step, "thought": thought, "tool": tool,
                          "observation": "ERROR: repeated call, abort"})
            return {"status": "loop_detected", "answer": None, "trace": trace}

        if tool not in tools:
            obs = f"ERROR: unknown tool {tool}"
        else:
            try:
                obs = tools[tool](**args)
            except Exception as e:                      # 工具异常转成观察结果
                obs = f"ERROR: {type(e).__name__}: {e}"

        trace.append({"step": step, "thought": thought, "tool": tool, "observation": obs})

    return {"status": "max_steps", "answer": None, "trace": trace}
```

复杂度：时间取决于步数上限和每步的模型与工具耗时，最多 `max_steps` 次模型调用，空间 O(max_steps)。生产里还应加总超时、token 预算和单工具超时，并在 `max_steps` 或 `loop_detected` 时走降级回复或转人工。

### 1. 请做一个自我介绍

**答题思路**

三面通常是技术负责人或更高层级，关注综合判断和落地能力。自我介绍建议：

1. 简短交代背景，重点放在"我如何把 Agent 做到可上线、可评测、可运维"。
2. 用一个项目讲完整闭环：架构、关键取舍、评测与回流、线上问题与治理。
3. 体现工程判断：成本、稳定性、安全和权限、可观测等方面的思考。
4. 说明对这个岗位的理解，尤其是交易所业务对资金安全、合规的要求和半远程协作方式。
5. 控制时间，把评测、安全、多 Agent 等细节留给后面的追问。

### 2. 项目里最难的一个 Agent 坑是什么，怎么定位、怎么救、救完指标变没变

**答题思路**

选一个你真实遇到过的问题，按"现象 → 定位 → 方案 → 结果 → 复盘"讲，不要编造数据。

1. 现象：描述可观察的症状，例如循环调用、检索召回偏差、工具参数错误率高、上下文污染导致答非所问或成本突增。
2. 定位：怎么发现和排查的。先靠 trace 找到具体 run 和出问题的步骤，再区分是检索、意图、prompt、工具还是模型的问题，通过回放和对照实验验证假设。
3. 解决：说明改动内容，例如加 Schema 校验、调整检索策略、拆分 prompt、引入步数和预算限制、调整上下文裁剪。强调每次只改一个变量。
4. 结果：改动前后用同一份评测集对比，给出真实的指标变化，同时说明有没有副作用（例如延迟或成本上升）。
5. 复盘：沉淀了什么机制，例如把该问题加入回归集、加告警、写入规范，避免再次发生。

### 3. Agent 效果怎么证明，评测集怎么造，任务成功率、工具调用成功率、幻觉率、人工接管率怎么算

**参考答案**

效果证明靠"有代表性的评测集加明确的指标定义加稳定的评测流程"。

**评测集构造**：来源包括脱敏后的线上真实请求、业务专家构造的典型任务、历史 badcase、边界与对抗样本（注入、越权、模糊输入）。按意图、难度分层采样，每条标注期望结果：答案要点、期望的工具和参数、应否拒答或转人工。评测集要版本化，并避免与调优数据泄漏。

**指标定义**：

- **任务成功率** = 满足验收标准的任务数 ÷ 总任务数，是端到端指标，可用规则校验加 LLM 评审，再由人工抽检校准。
- **工具调用成功率**：可拆为格式合法率（Schema 校验通过）、选择正确率（选对工具）、执行成功率（返回无错误），分别统计更有诊断价值。
- **幻觉率** = 含无依据陈述的回答数 ÷ 总回答数。把回答拆成若干断言，逐条与检索证据或工具结果核对。
- **人工接管率** = 转人工或需要人工介入的会话数 ÷ 总会话数，同时分析接管原因。注意这个指标并非越低越好，高危场景该转人工就应该转。

**其他要点**：LLM 评审要用人工标注校准一致性；因为模型输出有随机性，需要多次采样看方差；样本量要足够并给出置信区间；线上指标和离线指标要对照验证。

### 4. Badcase 怎么回流，Prompt 改一版怎么防止把老问题改坏

**参考答案**

回流是一条闭环流水线，Prompt 变更要走和代码一样的回归流程。

**回流流程**：

1. 收集：用户点踩、人工接管、工具失败、LLM 评审低分和客诉，都通过 `run_id` 关联到完整 trace。
2. 归因：分类为检索、意图、prompt、工具、模型或数据问题。
3. 处理：脱敏后人工确认标注，进入评测集和回归集，同时驱动对应的修复。
4. 验证：修复后用该样本和全量回归集验证。

**Prompt 变更防护**：

- Prompt 版本化管理（Git 或配置中心），每次变更记录原因。
- 改动前后在同一份评测集上跑对比，包含历史 badcase、核心场景和通用集，设置准入门槛，核心指标不得下降。
- 每次只改一个变量，便于归因。
- 灰度发布或 A/B，必要时用影子流量对比，保留一键回滚。
- 把每个已修复的 badcase 永久留在回归集，防止同类问题复发。

### 5. GraphRAG 场景题：实体关系存 Neo4j，原文块存向量库，查询时先图后向量还是先向量后图

**参考答案**

取决于查询类型，没有固定答案，生产里通常按查询路由，或并行检索后融合。

**先图后向量**：适合实体明确、关系型或多跳问题，例如"A 公司的关联方有哪些，涉及什么规则"。流程是实体链接 → 在图中扩展邻居或路径 → 得到相关实体及其关联的 chunk_id → 用这些 chunk_id 限定向量检索范围或补充语义检索 → rerank → 生成。优点是精准、可解释、缩小范围。

**先向量后图**：适合问题开放、实体不明确。流程是先向量召回相关 chunk，从中抽取实体，到图中扩展一到两跳补充关联上下文，再融合排序。优点是对模糊提问更鲁棒。

**关键难点**：

- 实体链接的准确率，决定"先图"能不能走通。
- 图扩展会爆炸，需要限制跳数、边类型和 top-k。
- 图节点和 chunk 的映射维护，以及两边数据的一致性。
- 权限过滤要同时作用于图和向量两侧。

实践建议：用一个轻量路由器判断查询类型，实体明确走先图，否则先向量，同时对效果做评测对比。

### 6. 多 Agent 生产环境最怕什么：成本突增、循环调用、权限越权、状态不一致，你排优先级

**参考答案**

我的排序是：权限越权 > 状态不一致 > 循环调用 > 成本突增。依据是后果的不可逆程度和资金风险，交易所场景尤其如此。

1. **权限越权**：可能造成资金损失、数据泄露和合规事故，且不可逆，优先级最高。对策是最小权限、代码层鉴权、高危审批、工具白名单、审计。
2. **状态不一致**：多 Agent 并发读写、重试导致重复下单或状态错乱，同样会造成资金和数据问题。对策是幂等键、唯一约束、乐观锁或版本号、单一状态源、checkpoint。
3. **循环调用**：会拖垮可用性并放大成本，但可以通过步数上限、重复调用检测、总超时快速止损，属于可控风险。
4. **成本突增**：多数时候是循环调用或异常流量的后果。用预算熔断、按用户和租户限额、成本告警兜底，损失有上限，可以事后治理。

这个排序依据业务而变：如果是不涉及写操作的内容型场景，成本和循环调用的优先级会上升。无论怎么排，都要有统一的熔断开关，必要时能整体降级到单 Agent 或规则兜底。

### 7. 高危操作比如退款、提币、删数据，怎么接 Human-in-the-loop 和审批断点

**参考答案**

做法是风险分级加执行前断点加绑定参数的审批。

1. **风险分级**：只读操作自动执行；低风险写操作自动执行并事后审计；退款、提币、删数据等高危操作必须审批，按金额和影响范围设置阈值。
2. **断点**：在编排中把高危工具节点前设为中断点（例如 LangGraph 的 `interrupt`）。执行到此处保存 checkpoint 并暂停，线程资源释放，不阻塞等待。
3. **审批单**：生成审批请求，包含操作类型、参数、风险评分、依据的证据和过期时间，推送到审批系统。
4. **审批动作**：审批人可通过、驳回或修改参数。
5. **恢复**：审批结果通过 `resume` 回写，从 checkpoint 继续执行。
6. **防篡改**：审批绑定的是操作参数的哈希，批准后模型不能再改参数，执行时校验哈希一致。
7. **执行保障**：审批通过后仍然走幂等键、风控和限额校验，审批有过期时间，过期需重新发起。
8. **安全**：审批动作不能由 Agent 自己或被注入的内容触发，提币类可要求多人复核，所有环节留审计记录。

### 8. Agent 被提示词注入攻击了会怎样，外部网页/邮件/用户输入怎么隔离出高权限路径

**参考答案**

**后果**：Agent 可能被劫持去调用高权限工具（转账、发邮件、删数据），泄露 system prompt 或用户数据（例如通过拼接链接或图片 URL 外传），污染长期记忆，或输出恶意内容。网页、邮件和文档里的间接注入尤其隐蔽。

**防御的关键是架构隔离，而不是依赖 prompt 里的"请忽略恶意指令"**：

- **数据与指令分离**：外部内容明确标记为不可信数据，用分隔符隔离，并告知模型其不具备指令效力。这只是辅助手段。
- **权限隔离**：处理不可信内容的 Agent（读取和摘要）不挂载任何敏感工具，只输出受约束的结构化结果给高权限 Agent，高权限 Agent 不直接接触原始不可信内容（隔离式双 LLM 模式）。
- **污点追踪**：上下文一旦包含不可信来源，就禁止调用敏感工具，或强制触发人工审批。
- **最小权限**：工具权限按当前用户的身份和授权范围，而不是 Agent 的全局身份。
- **高危操作**：通过 HITL 审批，并校验参数。
- **出站控制**：限制可访问的域名，不渲染外部链接和图片，防止数据外泄。
- **记忆保护**：写入长期记忆前做审核，避免被污染。
- **检测与演练**：输入检测只作为补充，并定期做红队测试。

### 9. 你们有没有做模型路由，强模型、小模型、规则引擎分别在什么环节用

**参考答案**

模型路由的目标是在质量、延迟和成本间取平衡，常见做法是按任务复杂度分层。

- **规则引擎**：确定性强、可枚举、需要合规保证的环节，例如固定话术、敏感词拦截、权限与金额阈值判断、简单的状态查询。零成本、可解释、延迟最低。
- **小模型**：意图分类、查询改写、槽位抽取、简单摘要、安全分类、embedding 和 rerank 等，量大且要求低延迟的环节。
- **强模型**：复杂规划、多步推理、多工具编排、需要高质量的最终生成，以及小模型置信度低时的升级处理。

**路由方式**：先规则后小模型，再按置信度升级到强模型的级联；也可以训练一个路由器按问题难度分流。要点包括：

- 用评测集验证路由后的质量不低于全量强模型，并量化成本节省。
- 设置降级和备用模型，应对服务商故障或限流。
- 配合缓存（语义缓存、结果缓存）进一步降本。
- 路由决策本身要被记录到 trace，便于分析。

### 10. 可观测性怎么做：trace、token 消耗、工具耗时、召回结果、成本、用户反馈怎么串起来

**参考答案**

核心是用统一的 `trace_id` 和 `run_id` 把一次请求全链路的数据串起来。

1. **Trace 结构**：入口 → 意图 → 检索 → LLM 调用 → 工具调用 → 输出，每一步是一个 span，基于 OpenTelemetry 规范，跨服务透传 trace_id。
2. **每个 span 记录**：模型名与版本、prompt 版本、输入输出 token 数、耗时、工具名、参数摘要、状态与错误码、召回的 chunk ID 与分数、rerank 后的顺序。
3. **成本**：成本等于 token 数乘以单价，按用户、租户、场景和意图聚合，并设置预算告警。
4. **用户反馈**：点赞点踩、人工接管、追问等都以 `run_id` 关联到 trace，方便定位 badcase。
5. **存储**：事件通过 Kafka 异步落地，热数据放 ES 或 ClickHouse 用于查询和聚合，原文采样保存并做脱敏，设置保留期限。
6. **工具**：可以用 Langfuse、LangSmith、Phoenix 等专用平台，或 OpenTelemetry 加 Grafana 自建，按团队情况选择。
7. **告警与回放**：针对错误率、P99 延迟、成本、循环调用设置告警，并支持基于 trace 的回放。

### 11. 如果让你从零搭一套 Java + Spring AI / LangChain4j + LangGraph 的 Agent 平台，技术选型怎么拍板

**参考答案**

选型的依据是团队技术栈、生态成熟度、可控性、可观测和与现有系统的集成成本，而不是追热点。

1. **模型接入层**：Spring AI 与 LangChain4j 二选一为主，不要混用。团队本身是 Spring 体系，Spring AI 与 Spring Boot、配置、观测和 MCP 等集成自然；LangChain4j 在 AI Services、RAG 和工具抽象上更丰富。用同一个业务场景做小规模 PoC 对比后拍板。
2. **编排层**：LangGraph 官方是 Python 和 JS 生态，Java 侧有社区的 LangGraph4j。简单流程用代码加状态机即可，复杂的有状态循环和审批断点用 LangGraph4j 或自研引擎。若算法团队主要用 Python，也可以让 Python 的 LangGraph 服务和 Java 网关配合。需评估社区的活跃度和与官方版本的差距。
3. **抽象与解耦**：自己定义模型、工具、记忆的接口，隔离框架，避免被锁定。
4. **存储**：Postgres 或 MySQL 存业务数据，Redis 做会话和缓存，向量库和 ES 做检索，Kafka 做异步。
5. **基础设施**：Checkpointer 持久化、OpenTelemetry 观测、评测与回放平台、权限与审批体系，这些要在平台层统一提供。
6. **落地策略**：先 PoC，再选一个业务场景做 MVP，边做边沉淀平台能力。

### 12. 最近在学什么 AI 工程方向，MCP、A2A、Agent Skills、Eval、Harness 里你最熟哪个

**答题思路**

选一个你真正熟的方向讲透，其余的能说清定位即可，不要贪多。先做到每个都能准确说出一句话定义：

- **MCP（Model Context Protocol）**：由 Anthropic 提出的开放协议，用统一的方式让模型应用连接外部工具、资源和提示，基于 client–server 架构。
- **A2A（Agent2Agent）**：由 Google 提出的 Agent 之间互操作的协议，用 Agent Card 描述能力，解决跨框架、跨厂商 Agent 之间的协作。它和 MCP 互补：MCP 连工具，A2A 连 Agent。
- **Agent Skills**：以文件夹形式封装的能力包（说明文件加脚本和资源），按需渐进加载，避免一次性塞满上下文。
- **Eval**：评测体系，包括评测集、指标、LLM 评审和回归流程，是 Agent 迭代的基础。
- **Harness**：模型之外的运行时工程，涵盖上下文装配、工具调度、兜底和回放。

回答结构：先说自己最熟的是哪个，再讲你的实践（用它解决了什么问题）、遇到的坑和个人理解，最后简要说明其他几项的认知和下一步学习计划。结合所学如何服务这个岗位。

### 13. 你是怎么把一个新 AI 框架从 demo 用到生产的，看过源码还是只调 API

**答题思路**

重点体现"从能跑到可靠"的工程方法，如实回答是否读过源码，不要夸大。建议按以下顺序：

1. 选型调研：为什么选这个框架，对比过什么，评估标准是什么（成熟度、可控性、生态、可观测性）。
2. Demo 到 PoC：用真实业务数据而不是玩具数据验证，列出风险点。
3. 读源码：说明你读了哪些关键部分以及目的，例如工具调用流程、状态与重试机制、token 与上下文处理、异常处理，读源码是为了弄清行为边界和排查问题。如果没通读，就讲清读过哪些关键路径，以及遇到问题时怎么按需深入。
4. 生产化加固：封装抽象层避免锁定、固定版本、补充超时重试限流、可观测、评测回归、灰度回滚、安全与权限。
5. 踩坑案例：举一个框架行为与预期不符的例子，如何定位并解决。
6. 总结：沉淀成规范或模板，让团队复用。

### 14. 手撕算法：给一组工具定义和一句用户请求，实现工具候选召回 + 参数提取 + Schema 校验 + 校验失败降级的简化版 Tool Dispatcher

**参考答案**

思路分四步：

1. **候选召回**：按关键词命中计分，取 top-k 候选工具。生产中可以换成 embedding 检索加规则。
2. **参数提取**：按每个参数声明的正则从请求中提取并转型，真实系统里可以用 LLM 的结构化输出。
3. **Schema 校验**：检查必填、类型、枚举、数值范围。
4. **降级**：没有候选则转兜底（普通对话或知识问答）。有候选但校验失败，则返回缺失或错误信息，让上层向用户澄清，而不是带着错误参数去调用工具。

```python
import re
from dataclasses import dataclass, field
from typing import Any, Callable, Optional

TYPES = {"string": str, "integer": int, "number": (int, float)}
CASTERS = {"string": str, "integer": int, "number": float}


@dataclass
class Tool:
    name: str
    keywords: list[str]
    # 参数名 -> {type, required, regex, enum, minimum, default}
    params: dict[str, dict] = field(default_factory=dict)
    handler: Optional[Callable[..., Any]] = None


def recall(tools: list[Tool], text: str, top_k: int = 3) -> list[Tool]:
    t = text.lower()
    scored = []
    for tool in tools:
        score = sum(len(k) for k in tool.keywords if k.lower() in t)
        if score:
            scored.append((score, tool))
    scored.sort(key=lambda x: -x[0])
    return [tool for _, tool in scored[:top_k]]


def extract(tool: Tool, text: str) -> dict:
    args = {}
    for name, spec in tool.params.items():
        m = re.search(spec["regex"], text) if "regex" in spec else None
        if m:
            raw = m.group(1) if m.groups() else m.group(0)
            try:
                args[name] = CASTERS[spec["type"]](raw)
            except ValueError:
                args[name] = raw            # 留给校验阶段报类型错误
        elif "default" in spec:
            args[name] = spec["default"]
    return args


def validate(tool: Tool, args: dict) -> list[str]:
    errors = []
    for name, spec in tool.params.items():
        if name not in args:
            if spec.get("required"):
                errors.append(f"missing:{name}")
            continue
        v = args[name]
        if not isinstance(v, TYPES[spec["type"]]):
            errors.append(f"type:{name}")
            continue
        if "enum" in spec and v not in spec["enum"]:
            errors.append(f"enum:{name}")
        if "minimum" in spec and v < spec["minimum"]:
            errors.append(f"minimum:{name}")
    return errors


def dispatch(tools: list[Tool], text: str) -> dict:
    candidates = recall(tools, text)
    if not candidates:
        return {"status": "fallback", "reason": "no_tool_matched"}

    first_failure = None
    for tool in candidates:
        args = extract(tool, text)
        errors = validate(tool, args)
        if not errors:
            return {"status": "ok", "tool": tool.name, "args": args}
        if first_failure is None:
            first_failure = {"tool": tool.name, "args": args, "errors": errors}

    # 校验失败降级：不调用工具，返回需要澄清的信息
    return {"status": "need_clarification", **first_failure}


if __name__ == "__main__":
    tools = [
        Tool("get_price", ["价格", "行情"], {
            "symbol": {"type": "string", "required": True, "regex": r"\b([A-Z]{2,10}-[A-Z]{2,10})\b"},
        }),
        Tool("list_orders", ["订单", "委托"], {
            "limit": {"type": "integer", "regex": r"(\d+)\s*条", "default": 10, "minimum": 1},
        }),
    ]
    print(dispatch(tools, "看下 BTC-USDT 的价格"))
    print(dispatch(tools, "看下价格"))          # 缺少 symbol，降级为澄清
    print(dispatch(tools, "你好"))              # 无候选，兜底
```

复杂度：召回 O(T·K)（工具数乘关键词数），每个候选的提取和校验 O(P·L)（参数数乘文本长度）。补充说明：校验通过后才能调用 handler；写操作类工具还要叠加确认、审批和幂等键；校验失败的结构化错误也可以回传给 LLM 让它修正一次，仍失败再向用户澄清。

## HR 面

### 1. 自我介绍，顺便说下你为什么看 KuCoin 这种交易所 AI 岗

**答题思路**

自我介绍简短，重点回答"为什么是交易所 AI 岗"：

1. 简要背景：年限、技术栈、AI 方向的积累。
2. 对行业的理解：交易所业务对稳定性、实时性、安全合规要求高，AI 落地价值（客服、风控辅助、运营、数据分析）和难度并存，是能把工程能力用上的场景。
3. 能力匹配：Java 工程功底加 Agent 落地经验，特别是对幂等、权限、可观测的重视。
4. 个人动机：想做有真实业务约束的 AI 系统，而不是只做 demo。
5. 态度：如实说明对加密行业波动和监管环境有了解，并能接受相应的工作节奏。避免只谈薪资和行业热度。

### 2. 半远程办公你能不能扛住，时区、自律、沟通同步怎么解决

**答题思路**

先给明确态度，再用具体做法证明，不空谈"我很自律"：

1. 态度：能适应，并说明是否有远程或跨团队协作的经历。
2. 时区：主动对齐团队的核心重叠时段，重要会议和同步提前约定，其余时间异步推进。
3. 自律：用任务拆解、每日计划、里程碑和可见的产出来管理自己，而不是靠被盯。
4. 沟通同步：书面优先，文档和 issue 记录决策，每日或每周同步进度和风险，遇到阻塞及时抛出而不是等待，关键事项当面或视频对齐。
5. 交付意识：以结果为导向，对线上问题有明确的响应方式和值班预期，并确认公司对半远程的具体要求（到岗频次、值班安排）。

### 3. 上家为什么走，是被业务拖死还是自己想冲 AI

**答题思路**

原则：真实、正面、不抱怨前公司，把原因落到"成长方向"上。

1. 先说客观原因：业务方向或团队阶段与自己的发展规划不再匹配，不要说前公司或同事的坏话。
2. 再说主动选择：对 AI 工程落地有持续投入，希望把精力放在更能发挥价值的方向。
3. 用事实佐证：做过哪些 AI 相关的实践、自学和项目，说明不是一时冲动。
4. 说明对新岗位的期待：和现有积累衔接，而不是单纯逃离现状。
5. 保持前后一致，因为面试官可能会和背调、前面几轮的说法交叉比对。

### 4. 薪资预期，加密行业波动大、期权/代币激励怎么看

**答题思路**

不要编造具体数字，按以下框架回答：

1. 先表达更看重岗位匹配和成长，薪资希望和能力、市场水平匹配。
2. 给范围和依据：基于现有薪资结构和市场行情给一个区间，说明有协商空间，也可以反问岗位的薪资带宽。
3. 对激励的看法：现金薪酬作为基本保障，期权或代币作为额外激励，更关注归属周期、兑现条件、折算方式和税务合规，不把波动较大的激励当成固定收入。
4. 对行业波动的态度：了解行业周期波动和监管风险，更关注公司的合规状况和业务稳定性。
5. 表示愿意在了解完整的薪酬结构（固定、绩效、激励）后综合判断。

### 5. 如果业务方明天要你接一个完全没做过的 Agent 场景，你先干啥

**答题思路**

体现结构化推进，而不是上来就写 prompt：

1. 先对齐目标：和业务方明确要解决的问题、成功标准、可接受的错误范围、涉及的数据和权限、上线时间。
2. 判断是否适合 Agent：能用规则或固定流程解决的就不要用 Agent，明确哪些环节需要模型决策。
3. 梳理现状：现有的人工流程、数据源、工具接口、合规与风险点（尤其是写操作和资金相关）。
4. 快速建立评测：先收集一批真实样例，定义验收指标，哪怕几十条，有基线才能判断好坏。
5. 做最小可行方案：先只读场景、单 Agent 加少量工具，跑通后再迭代。
6. 风险控制：权限最小化、高危操作审批、可观测和降级方案先设计好。
7. 同步节奏：约定迭代和演示节奏，持续对齐预期，及时暴露风险。

### 6. 和算法同学、前端、风控、合规吵架了怎么收场

**答题思路**

重点体现就事论事、对齐目标和推动落地：

1. 态度：冲突多数来自目标和约束不同，先弄清对方的诉求和顾虑，例如风控关心风险敞口，合规关心监管要求，算法关心指标，前端关心体验和接口稳定。
2. 方式：把争论从观点转到数据和事实，用评测结果、线上数据或原型说话。
3. 找共同目标：回到业务目标和用户价值，一起列出方案的收益、风险和成本。
4. 决策与升级：分歧无法解决时，把选项和利弊整理清楚，交给负责人拍板，拍板后无条件执行。
5. 对合规和风控：把它们当作约束和伙伴，主动提前沟通，而不是事后补救。
6. 收尾：事后复盘，把达成的共识写成文档，避免重复争论，关系上保持尊重。

可以用一个真实案例，按"分歧点 → 沟通方式 → 结果 → 学到什么"来讲。

### 7. 你觉得自己最值钱的能力是 Java 工程底子，还是 AI 系统嗅觉

**答题思路**

不要二选一，而是说明二者的组合才是竞争力：

1. 给出观点：Agent 上生产，模型能力只是一部分，更多是工程问题，包括稳定性、幂等、权限、可观测、成本，这些正是 Java 工程底子的价值。
2. AI 系统的判断：知道哪里该用模型、哪里该用规则，能设计评测和回流闭环，能判断方案在成本、延迟和质量间的取舍。
3. 用案例证明：举例说明你如何用工程手段让一个不稳定的 AI 能力变得可靠、可评测。
4. 成长方向：工程底子是基础，AI 判断力是持续迭代的部分，两者结合在交易所这种高要求场景里更有价值。
5. 保持谦虚，说明仍在学习新的方向。

### 8. 入职前如果有空窗期，你会拿来刷题还是真做一个 Agent 项目

**答题思路**

建议回答"以做项目为主，辅以少量刷题保持手感"，并说明原因和计划：

1. 观点：做一个能跑通的 Agent 项目更能积累真实经验，也更贴近岗位要求。
2. 计划：围绕岗位相关场景（例如带工具调用、检索、评测和可观测的小型 Agent），先定义评测集，再迭代，记录踩坑和指标变化。
3. 重点打磨的点：Harness、幂等和权限、HITL 审批、评测与回放，这些是面试中被追问的部分。
4. 刷题：每天安排少量时间保持算法手感，尤其是限步循环、路由、调度这类和 Agent 相关的手写题。
5. 其他：整理总结成文档，也方便入职后快速上手，同时适当休息，保持入职状态。
