## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「身份 → 一件最相关的事 → 技术栈 → 为什么是基础设施」讲。

1. 说明年限和方向，训练系统、推理服务或集群平台，说你真实的那一个。
2. 只展开一段做过的事：规模、你负责的边界、瓶颈在算力、显存、通信、调度还是成本。指标用自己量过的。
3. 点出你亲手碰过的栈，例如分布式训练、推理运行时、调度或 GPU 排障。文档里的名词不要说成线上经验。
4. 收尾落到还想解决的问题，把话头交给下一题的项目。

### 2. 介绍一个你负责的 AI 基础设施项目

**答题思路**

按系统讲，业务一句带过。

1. 背景：训练还是推理，规模在什么量级，慢或贵在哪里。
2. 边界：你负责运行时、调度、通信、存储还是平台，上下游是谁。
3. 做法：关键路径上的一个机制，以及你放弃的做法。
4. 定位：用 profiler、指标或日志，把瓶颈钉在计算、显存、通信、数据或排队中的一类。
5. 结果只报真实对比。
6. 留下的问题：重做会改哪一个决定。

提前准备三个追问：显存大头是参数、优化器还是激活或 KV；通信在机内还是跨机；故障后从哪一份 checkpoint 或哪一个版本恢复。

### 3. 大规模 AI 推理服务如何做性能优化和成本控制？

**参考答案**

**结论**：目标是在 TTFT 和 token 间隔的约束下降低单位 token 成本。常见并发下，prefill 吃算力，decode 吃显存带宽和 KV Cache。

运行时按迭代重新组 batch：做完的请求马上离开，新请求马上进入。KV 用分页，按块分配，避免按最大长度预留。相同前缀复用已有 KV。长 prefill 切成小块，插入 decode 之间，避免一次预填充把后面每个 token 的间隔拉高。decode 用 CUDA Graph 去掉逐 kernel 启动的开销，batch 落到固定档位。

模型侧把 Attention、RMSNorm、SwiGLU 融成少数 kernel。decode 每步都要读权重，权重量化直接减少带宽；激活量化单独看精度。GQA 减少 KV 头数，显存和带宽一起降。投机解码只有在草稿模型便宜、接受率够高时才划算。

并行放在机内做张量并行。MoE 再加专家并行。流量大了以后，prefill 池和 decode 池可以拆开，KV 经 RDMA 传过去，两种卡可以按算力和带宽分开采购。拆开之后多一段传输和两级排队，小流量不一定划算。

服务侧按模型、LoRA 和前缀亲和路由，多个适配器共享底座。准入看 KV 空闲块和单步 token 预算，扩缩容看队列等待，单看 QPS 会在 KV 已经打满时继续加请求。离线流量用可抢占资源。长尾模型在常驻和冷启动之间按调用量算账。

线性注意力的状态不按 KV 随序列增长；多模态还要单独算视觉或音频编码器的激活。套用「瓶颈一定在 KV」会优化错地方。分配率很高但时延被打穿、请求反复重试，单位成本是上升的。

### 4. 模型服务部署时，如何做版本管理和灰度发布？

**参考答案**

**结论**：一次可回滚的发布是一份不可变制品，加上已经预热好的旧副本。灰度切的是流量，不是在同一张卡上硬塞两份大模型。

制品把这些绑在一起：权重哈希、tokenizer、对话模板、默认采样参数、量化格式、张量并行度、引擎所针对的 GPU 架构和软件版本。少一项，就会出现权重正确、行为错误。引擎和权重用同一个版本号。

新版本单独起副本，加载并预热完成才进就绪。大模型加载常常要数十秒到数分钟，回滚要切回仍在服务的旧副本，临时再拉一次权重来不及。网关按用户或比例把流量分到新版本，响应里带上版本号。

会话粘在某个副本的 KV 上时，切走就要重算 prefill。做成无状态、靠前缀缓存，副本可以随时替换。按用户粘住版本时，长会话会一直留在旧版本，灰度比例和真实体验会偏。

看门禁时，错误率和时延不够。用固定评测集看质量，线上再看格式失败和反馈。tokenizer 或模板不兼容是破坏性变更，和权重更新分开发布。LoRA 可以热加载；换底座权重或 CUDA 引擎用蓝绿副本。

### 5. 在 AI Infra 场景下，遇到过哪些棘手的内存或显存问题，如何解决的？

**答题思路**

选一个你真实处理过的，按「现象 → 怎么量的 → 属于哪一类 → 改了什么 → 如何确认没有挪到别处」讲。下面的分类用来对号入座。

1. 训练峰值。混合精度 Adam、梯度也是半精度时，参数、梯度和优化器大约每参数 16 字节，再加激活。ZeRO 或 FSDP 切的是这份状态，激活靠重计算、减小 micro-batch 或序列并行。重计算通常大约多三成计算。
2. 碎片。`reserved` 远大于 `allocated` 时，是缓存分配器的空洞。`expandable_segments` 一类选项缓解碎片，堵不住泄漏。
3. 泄漏。列表或日志持有没有 `detach` 的张量，计算图会越攒越大。
4. 推理 KV。占用随并发和序列增长；请求取消后块没还回去，或者权重和 KV 池互相割裂。
5. 主机内存。rank 0 收集全量 checkpoint，或 DataLoader 的每个 worker 拷一份数据，CPU 内存先爆。
6. 通信缓冲。集合通信的临时张量让峰值高于参数公式。

度量用分配器摘要和分配栈，看峰值出现在反传、通信还是保存。只展开你真修过的一类，不报没量过的容量数字。

### 6. 谈谈你对模型并行、流水线并行、数据并行的理解，各自适用场景是什么？

**参考答案**

**结论**：数据并行切批次，模型并行在这里指把同一层矩阵切开的张量并行，流水线并行切层。通信发生在多近的地方，决定并行度放在哪。

数据并行是每卡一份模型、不同的 micro-batch，反向后同步梯度。DDP 把梯度分桶，和反传重叠。模型放得下、全局批次还能加大时用它。混合精度 Adam 且梯度为半精度时，每个参数约 16 字节：半精度参数和梯度各 2 字节，FP32 主权重、动量、方差共 12 字节。放不下就只在数据并行组里切状态。设数据并行度为 \(N\)，参数量为 \(\Psi\)：ZeRO-1 约 \(4\Psi+12\Psi/N\)，ZeRO-2 约 \(2\Psi+14\Psi/N\)，ZeRO-3（FSDP 的 `FULL_SHARD`）约 \(16\Psi/N\)。\(N\) 不是总卡数，张量并行和流水线占掉的卡不进这个分母。前两阶段通信量可以做到与普通数据并行同一量级，阶段 3 前向和反向都要 all-gather 参数，大约 1.5 倍，靠按层预取和计算重叠盖住。ZeRO 不切激活。

张量并行把 QKV 和 MLP 第一层按列切，输出投影和 MLP 第二层按行切，中间的逐元素运算不用通信。每个 Transformer 层前向两次 AllReduce，反向再两次，所以放在机内 NVLink 上，度数一般就是单机卡数。序列并行把 LayerNorm 和 Dropout 沿序列切开，用 all-gather 和 reduce-scatter 换激活显存，通信量仍是同一量级。

流水线只在 stage 边界传递激活，可以跨机。GPipe 和 1F1B 的气泡大约都是 \((P-1)/M\) 倍理想计算时间；GPipe 要留下全部 micro-batch 的激活，1F1B 把激活降到和 stage 数同级。交错流水线让每张卡放多个模型块，气泡大约再降到 \((P-1)/(V \cdot M)\)。\(M\) 不够大时气泡会吃掉并行收益。边界张量的体积是 batch × seq × hidden，序列很长时流水线并不省通信。

常见摆法是机内张量并行、跨机流水线、最外层数据并行。序列极长要加上下文并行，MoE 要加专家并行，这是另外两根切分轴。

### 7. 如何设计和实现一个高可用、可扩展的模型训练任务调度系统？

**参考答案**

**结论**：训练调度要让一组 GPU 同时开工，并按 NVLink 域和机架拓扑放置。按单个 Pod 公平摆放，满足不了这个约束。

作业写成期望状态：卡数、是否整机、拓扑、队列、优先级、镜像和启动命令。状态放在 API 里。调度器选主，重启后按对象和节点现状重建队列，避免进程内存里的账和集群实际占用分叉。

放置分三步。滤掉不健康、驱动不对、已经隔离的节点。整组预留，全部满足才占用，避免两个大作业各拿一半后都启动不了。打分时把同一个作业塞进同一台机器、同一个 leaf，并按 rail 对齐，减少集合通信跨过脊交换机。小作业可以回填碎片，前提是不推迟已经承诺的大作业。

队列做层级配额：保证量之内的资源不被抢走，空闲可以借用，借用的部分按整组抢占。配额若只是一个 GPU 整数，不绑定整机或拓扑，就会出现配额够、拼不出作业。

NCCL 在整组放置完成后再初始化。节点出现掉卡或不可恢复的 ECC，就隔离节点。非弹性作业整组从 checkpoint 拉起；只补一个 rank，旧进程组对不上。弹性重入要重新建组，并保证优化器分片和采样器还对齐。

规模变大时，镜像用 DaemonSet 预拉，状态更新合并，一次决策提交整组，而不是逐卡抢锁。训练为了通信会挤在同一故障域里；在线推理的副本则要散开。两类作业分队列。

### 8. 在分布式训练中，如何监控和定位节点性能瓶颈或故障？

**参考答案**

**结论**：先分清是所有 rank 一起慢，还是一个 rank 拖住了集合通信。快的 rank 堵在通信里，慢的那个才是根因。

把一步拆开：数据加载、主机到设备拷贝、前向、反向、集合通信、优化器。所有 rank 的数据时间都高，查存储和 DataLoader。只有一个 rank 高，查那台机器的磁盘、CPU 或样本长度不均。通信时间在快的 rank 上高、在某一个 rank 上低，顺着低的那个看它的计算或数据。

GPU 看 SM 占用、显存带宽、时钟、温度、功耗、NVLink、ECC 和 Xid。时钟掉下去时，卡看起来一直忙，实际在降频。Xid 79 这类掉卡、Xid 48 这类双比特 ECC，直接隔离节点。网络看丢包、PFC 和各 rail 是否均衡。存储打满同一张计算网卡时，集合通信会超时，现象像 NCCL 故障。

卡住时看谁没有进入通信。用进程组超时和 NCCL flight recorder 留栈，生产上用采样指标。全量的 nsys 只在复现时开，观测本身会改变步时。

处理上，非弹性作业整组回到最近一次已提交的 checkpoint。和一份正常 step 的轨迹比，能看出是回归还是单点故障。只看到作业失败率，会漏掉没崩溃、但被慢节点拖着走的情况。

### 9. 如何保证大规模训练任务中 Checkpoint 存储的可靠性与高效读写？

**参考答案**

**结论**：每个 rank 写自己的分片，全部刷稳之后再用一份清单发布。读者只认清单。优化器状态远大于半精度权重，体积和耗时都按这份状态估。

可靠性按这个顺序做。各 rank 把参数分片、优化器分片、随机数和采样器状态写到临时路径，刷盘并带上校验和。所有 rank 成功之后，一次发布清单，里面有步数、并行度、世界大小、文件列表和校验和。同一文件系统上用临时文件改名发布；对象存储则等分片可读后再写清单对象。写到一半失败，训练仍读上一版。新清单落稳前不删旧版。定期做恢复演练，写入成功不算恢复成功。

所有 rank 必须快照同一步。异步保存时，先把这一步拷进独立的主机缓冲，拷贝完成前下一步不能覆写那块显存，所以至少要双缓冲。主机内存要装得下这份分片。只把 GPU 上的引用交给后台线程，会存出被下一步改坏的状态。

性能上让各 rank 并行写，文件少而大，避免海量小文件打垮文件系统元数据。保存会有突发带宽，先落本地 NVMe 再传到远端可以削峰，本地盘会随节点一起消失，不能当唯一副本。存储流量和集合通信分开，或至少降低保存的网络优先级。同步保存把间隔拉长，失败就多丢步；异步把尖峰削掉之后间隔可以缩短。世界大小变化时按清单里的分片计划重切，不能假定卡数永远不变。

### 10. 在 AI Infra 中，你如何看待和使用 Kubernetes？

**参考答案**

**结论**：Kubernetes 适合做节点生命周期、多租户控制和推理服务的声明式部署。大任务训练还要整组调度、拓扑和 RDMA，默认调度器不够。

它擅长把期望状态放进 API、失败后调谐、用配额和 RBAC 分租户，以及用 GPU Operator 把驱动、设备插件和监控对齐。推理服务可以用 Deployment 做多副本，按队列等待和 KV 占用扩缩容。坏卡通过 cordon、drain 和污点退出。

训练的缺口在这几处。默认调度器逐个放 Pod，不会整组预留，也不认识 NVLink 域和 rail。数千 Pod 的对象和状态会压 API 和 etcd，镜像拉取会形成风暴。高性能集合通信通常要 RDMA，现场常常开 hostNetwork，网络策略和多租户隔离会变弱。设备插件历史上把一张卡记成一个扩展资源，更细的切分可以看 DRA，两种都替代不了拓扑感知。Pod 重启也不等于从 checkpoint 恢复。

用法是把 Kubernetes 当控制面：训练用带整组调度的 Job 或 Operator，进程内仍用框架自己的分布式运行时；推理用部署和网关。镜像预热，驱动版本全池一致。调度策略、队列和 checkpoint 放在 Kubernetes 旁边的控制器里，不把高频指标写进 etcd。

有的团队训练继续用 Slurm 一类批调度，推理和平台用 Kubernetes。要合成一套时，补的是调度插件，而不是再造一个控制面。

### 11. 为了提升 GPU 集群的整体利用率，你们做了哪些工作？

**答题思路**

先定义指标，再讲你动过的杠杆。分配率表示卡被占着；MFU 或有效步时表示卡在做能推进训练、或在 SLO 内吐出 token 的工作。两个都报。

只讲你真落地过的，建议按这个顺序：

1. 度量一步里计算、通信、数据各占多少，加上失败后重算掉的时间。
2. 调度上做小任务回填、整组预留、空闲配额借用和可抢占队列。占着大部分卡等最后几张，浪费大于空闲。
3. 缩短空转：镜像预热、入组前做 GPU 和通信自检、失败后从已提交 checkpoint 拉起。
4. 把单个作业变快：数据预取重叠、通信和计算重叠、压流水线气泡。作业结束得早，卡就释放得早。
5. 推理按 KV 和队列缩容。训练和在线推理分池，空闲时段再借用。
6. 按占用计量到团队，占着不用的配额会露出头来。

训练共享一张卡的 MIG 或时间片会让集合通信抖动，不适合拿来当利用率手段。百分比用自己量过的。

### 12. 你认为当前 AI Infra 领域最大的技术挑战是什么？你们团队是如何应对的？

**答题思路**

第一问收成一个能讲机制的判断。规模上来之后，有效算力上不去：峰值 FLOPs 被故障、通信和显存搬运吃掉。买不到卡是约束，机制问题是卡加上去之后，有多少时间在推进训练或在时延内生成 token。

可以展开的机制有三条，挑和你经历一致的讲。卡一多，单点故障在一次长作业里几乎一定会碰到，非弹性的集合通信通常整组停。跨机之后 AllReduce，或者 MoE 的 AllToAll，占满步时。优化器状态、激活或 KV 的搬运让算力闲着。分配率可以同时很高。

如果你的主战场是在线服务，就改成这句：在时延约束下，单位 token 成本降不下来。prefill 和 decode 的瓶颈不同，塞在一池里会互相拖。

第二问只讲团队真实做过的一件事：动了哪个机制，用哪条指标验收，留下什么代价。规模没到万卡，就讲你那个规模下的瓶颈。

## 二面

### 1. 自我介绍

**答题思路**

这一轮听架构判断。两分钟内，把「做过什么」收成「你拍过的一个板」。

1. 一句话说明系统边界。
2. 用一个决定代替项目清单：约束、选中的方案、放弃的方案、用哪条指标验证。
3. 技术栈只留和这个决定有关的部分。
4. 结尾停在权衡上，方便对方追问。背景细节留给下一题。

### 2. 详细描述你设计或优化的一个 AI 系统架构（如推理/训练平台），重点讲权衡与决策

**答题思路**

和一面的项目题分开。可以是同一个系统，这里只讲决定，不复述背景。

1. 约束最多三条：时延或步时、故障恢复、成本、人力。
2. 画清控制面和数据面。一次请求或一步训练经过哪些组件。
3. 至少两个认真考虑过又放弃的做法，用机制说明原因。
4. 上线后哪条假设错了，设计改了哪一处。
5. 这个决定今天还在付的代价：利用率、复杂度或被锁定的硬件。

真选过才往下讲的对照包括：同步还是异步 checkpoint，训练节点独占还是共享，推理用现成引擎还是自研路由和调度。数字用自己的。

### 3. 如何为超大规模模型（如千亿参数）设计训练基础设施？需要考虑哪些关键因素？

**参考答案**

**结论**：先分清稠密千亿还是 MoE 的总参数，再按显存、网络、故障和存储设计。卡的型号服从这四件事。

显存上，混合精度 Adam、梯度也是半精度时，参数、梯度和优化器约每参数 16 字节。1000 亿参数仅这份状态就约 1.6 TB（按 \(10^{12}\) 字节计），激活和通信缓冲另算。机内用张量并行，跨机用流水线，数据并行组上用 ZeRO 或 FSDP，激活用重计算。MoE 的总参数和单步激活参数不是同一个数，还要专家并行；专家不均衡会让某些卡先打满。只拿 1.6 TB 除以单卡显存，会把卡数低估很多，因为步时目标、激活和冗余都要额外的卡。

网络上，张量并行留在 NVLink 域内。跨机的 RoCE 或 InfiniBand 按 rail 对齐，让集合通信少跨脊。MoE 的大头是 AllToAll，为 AllReduce 优化的拓扑要重新量。全局批次受到收敛效率限制，不能只为摊平通信往上加。

故障上，入组前做 GPU 和通信自检，失败从已提交 checkpoint 整组恢复，并留热备。恢复时间算进有效算力。存储上，样本打成大分片并预取；checkpoint 按 rank 写、用清单提交。保存流量和计算网分开或降优先级。

一次运行绑定代码、数据版本和随机数。支持 BF16 的 GPU 上，训练常用 BF16，少为溢出去调 loss scale。FP8 要单独做缩放和收敛验证。机柜电力、散热和布线决定拓扑能不能按图纸落地，并行度要反过来迁就真实机柜。

### 4. 在多租户的 GPU 集群中，如何实现高效的资源隔离、调度与配额管理？

**参考答案**

**结论**：隔离要同时做配额、整组调度和性能，三层缺一层都会要么超卖，要么互相拖慢。

配额用层级队列。保证量之内不抢，空闲允许借用，借用部分可以按整组抢占。计量按分配出去的 GPU 时，占着不用也会入账。配额只记卡数、不记整机和拓扑时，64 卡配额散落在几十台机器上，仍然跑不了一组 64 卡作业。

调度上，训练作业整组预留、按节点和 rail 挤在一起。小作业回填以不推迟保证作业为前提。在线副本要散开，和训练分队列。抢占时整组进、整组出，抽走一个 Pod 会把一次集合通信打崩。

性能隔离比 Namespace 难。训练独占 GPU 和节点，避免时间片或 MIG 让 NCCL 抖动，也避免邻居抢 PCIe、CPU 和页缓存。推理的小模型可以用 MIG 或同卡多副本，但要限制显存和 CPU。网络上，一个作业的 AllReduce 可以打满 leaf，重的作业要么独占一条轨，要么分优先级。

安全上，RDMA 和 hostNetwork 往往伴随高权限，命名空间隔离不等于不可信租户隔离。外部用户用独立池或更强的沙箱，并接受通信变慢。数据路径、checkpoint 目录和镜像仓库按租户授权，避免只隔离了计算、没隔离数据。

### 5. 如何设计一个支持多框架（PyTorch、TensorFlow、JAX）的统一训练平台？

**参考答案**

**结论**：统一控制面和节点上的驱动，不统一自动求导。框架自己跑训练循环，平台负责把作业可靠地送上一组 GPU。

作业描述与框架无关：镜像、命令、资源、数据挂载、世界大小。平台注入各框架都能消费的约定，例如 rank、world size、master 地址或 hostfile。PyTorch 用这套环境做 rendezvous，JAX 用来初始化分布式，TensorFlow 的 `TF_CONFIG` 由同一份分配结果生成。节点上的 GPU 驱动是硬约束，镜像里的 CUDA 和集合通信版本必须跟驱动匹配，所以按框架和版本提供不同镜像，不做一个万能大镜像。

数据用分片格式放在共享存储上，各框架自己写 DataLoader。指标约定成步时、loss 和吞吐，带作业号和 rank 推到同一条管道，不靠解析日志当接口。

checkpoint 的元数据和保留策略可以统一，完整恢复状态不能。推理用的权重可以经 safetensors 交换；优化器状态跟框架绑定。为了「一份快照随便换框架接着训」去做转换层，投入大、收益小。

XLA 和 eager 的编译缓存、卡死形态、显存峰值都不同，排障手册按框架分。平台若再包一层统一 Trainer，会把三个框架的最低公共部分变成所有人的上限。调度、配额、日志、权限和制品保留做深，运行时留给框架。

### 6. 在模型服务中，如何实现动态批处理（Dynamic Batching）以优化吞吐和延迟？

**参考答案**

**结论**：分类、向量或奖励模型可以用「等一小段时间凑成一批」。自回归生成要按迭代重新组 batch，不能等这一批里最长的序列生成完。

经典动态批处理维护一个队列，达到最大 batch 或队首等待超过上限就取出，垫成相同长度后执行。这段等待直接加进延迟，用来换吞吐。按长度分桶能减少填充。不同模型和不同 LoRA 分开组 batch。

大模型服务里，每个解码步之后都重新组一次：结束的请求归还 KV，新请求在 token 预算和空闲 KV 块之内进入。预填充按块切开，和一步解码穿插，这样一条长提示不会把所有请求的 token 间隔打高。变长 kernel 配合分页 KV，按真实 token 计算，不必垫到批内最长序列。

```python
def iteration(running, waiting, kv, token_budget):
    for req in list(running):
        if req.finished:
            kv.free(req)
            running.remove(req)
    budget = token_budget
    for req in running:
        budget -= req.next_chunk  # 已在批内：prefill 的下一块，或 1 个 decode token
    while waiting and budget > 0:
        req = waiting[0]
        cost = req.next_chunk
        if cost > budget or not kv.try_alloc(req):
            break
        waiting.pop(0)
        running.append(req)
        budget -= cost
    run_varlen_kernels(running)
```

已在跑的请求持有自己的 KV，`try_alloc` 只申请增量。队首一条放不进的请求会挡住后面的短请求，所以单请求还要有占用上限，预算不够时允许跳过。CUDA Graph 要求地址和档位稳定，KV 放在分页池里，batch 大小对齐到捕获过的档。交互请求和离线请求分队列，离线只用剩下的预算。真要抢占，就要重算或换出 KV，这不是免费操作。

### 7. 如何构建一个高效的模型编译与优化流水线，以提升推理性能？

**参考答案**

**结论**：流水线产出的是可复现的制品，加上精度和时延门禁。构建放在离线，请求路径上不做编译。

导出时保留动态形状的范围，自定义算子单独登记。图上做常量折叠、融合、量化和布局转换。Attention、MoE 路由这类热算子允许手写 kernel，其余走融合。通用 ONNX 路径经常覆盖不了分页 KV 和自定义注意力，所以运行时可以是按架构预先构建的引擎，也可以是带 CUDA Graph 和分页 KV 的 LLM 运行时。两种都要进入同一条制品和门禁流程。

调优结果按 GPU 架构、精度和形状桶缓存。制品键包括架构、软件版本、量化格式和张量并行度。在一种卡上构建的引擎不能拿到另一代卡上用。

校验用同一批输入对比 eager，浮点按容差，不按逐比特。性能在目标并发下看 TTFT、token 间隔和吞吐，不看单 kernel 的峰值。形状超出配置要告警，并落到明确的慢路径。上线前预热，把分配和捕获算进就绪，避免第一笔请求付编译成本。模型或运行时版本一变就重建制品，构建缓存跨机构共享，避免每个副本各编一次。

### 8. 谈谈你对存算分离架构在 AI 训练中应用的理解，其挑战和收益是什么？

**参考答案**

**结论**：存算分离是 GPU 节点和数据集、checkpoint 分开扩展。节点本地盘只做缓存和削峰，不是可靠性的来源。

收益有四方面。数据集变大时不用重做 GPU 服务器，多个作业共享一份远端数据。节点替换后按版本把分片拉回来，作业不绑死在某台盘上。GPU 机柜可以把电力留给卡和网络。预处理放在 CPU 集群，和训练分开扩。

挑战主要是带宽和语义。每步读样本、保存时突发写出优化器状态，远端存储跟不上，GPU 就空等。小文件随机读最伤，样本要打成大分片，由预取线程顺序读，和计算重叠。本地 NVMe 缓存热分片，并有明确的版本号；数据集一更新，旧缓存不能再被读到。

对象存储没有训练脚本假设的那套本地文件系统语义。随机写、文件锁、靠列目录判断成功，都会出错。提交 checkpoint 用清单，不用目录扫描。

计算网和存储网叠在同一张卡上时，保存会触发拥塞，集合通信超时。两条网分开，或给存储流量更低的优先级。新节点的缓存是冷的，替换之后第一步会慢，调度上要算进这段预热。

把优化器卸到 CPU 或 NVMe 是单作业用 PCIe 换显存，步时通常变长。那是显存扩展，和集群层面的存算分离不是一回事。

### 9. 如何监控和保障整个 AI 平台（从数据、训练到推理）的 SLA？

**参考答案**

**结论**：数据、训练和推理各有各的 SLI。平台内部先定 SLO，再决定对外能承诺什么。训练的承诺是有效步时和恢复时间，不是 loss 降到某个值。

数据看快照是否按时完成、校验是否通过、版本是否不可变。训练读到一半数据集被覆盖，是平台事故。流水线延迟和坏样本比例分开告警。

训练看队列等待、入组后真正在步进的时间比例、故障后回到下一步的时间。心跳停在某一步超过阈值就判停滞。成功率之外还要看慢节点，否则作业没失败、有效算力已经掉了。

推理看成功率、TTFT 和 token 间隔的尾部，以及容量。质量用发布前的评测集卡住，不把「回答好不好」塞进实时可用性。尾部不能用平均值代替。

保障手段是准入控制、离线流量降级、故障容量、变更灰度和恢复演练。推理的错误预算烧快了，就冻结高风险发布。探测用固定请求打在线服务，用小的通信检查打 GPU 池。依赖项包括对象存储、镜像仓库和控制面，它们掉了，模型进程还活着也达不到 SLO。

每段链路有负责人。数据问题不会出现在推理的 5xx 里，但会在下一个模型版本里变成质量事故。

### 10. 在技术选型上，何时会考虑自研核心组件，而不是使用开源方案？请举例说明

**参考答案**

**结论**：开源方案已经盖住关键路径时就扩展它。自研只发生在缺口正好卡在你的瓶颈上，补丁等不到，而且后续版本你养得起。

先写清 SLO 和量出来的差距，再估计接入成本和两到三年的维护。能上游或能薄薄包一层，就不要 fork 成另一套。

适合自研或深改的例子：调度策略要懂自己的 rail、配额和抢占，用 Kueue 或 Volcano 做队列，自己写放置策略。模型结构偏离通用运行时，例如一种新的注意力或专家路由，上游还没有可用 kernel，就补这层 kernel 和并行，不重写整个训练框架。开源 checkpoint 盖不住「异步拷贝 + 对象存储清单 + 改变并行度后重切」时，自研这个提交协议，权重加载仍用现成格式。

不适合自研的例子：再写一个集合通信库，应调现成库的拓扑和缓冲。再写一个通用推理服务器，分页 KV 和连续批处理已经有 vLLM、SGLang、TensorRT-LLM 这类运行时，自己的价值在路由、准入和缺失的算子。包一个同时屏蔽 PyTorch、TensorFlow、JAX 的统一训练循环，会把三个框架的限制叠加给用户。

时间盒也要有。模型结构几个月就变，为单个算子做的大编译器可能收不回成本；稳定的调度、网络和 checkpoint 可以跨模型使用。

### 11. 你如何评估和引入新的硬件（如新型 AI 加速卡）到现有基础设施中？

**参考答案**

**结论**：用真实模型的端到端步时和单位 token 成本评估，软件栈不成熟就停在试验池。宣传册上的峰值算力不作为准入条件。

选定代表性负载：一段稠密训练、一段 MoE 或长序列、在线的 prefill 加 decode。固定精度、序列和并发。指标用达成的 FLOPs 比例或每卡 token、时延尾部、功耗和单位成本。

软件门槛包括框架后端、集合通信、推理运行时、profiler、容器和驱动，以及掉卡、ECC 之后怎么隔离。缺通信或算子会悄悄退回 CPU 时，吞吐数字没有意义。

先量模型里真实出现的 GEMM、带宽和集合通信消息大小，再跑完整一步，并用同一小段数据对比 loss。数值阈值事先写好。一个作业里不混用不同厂商的卡，集合通信库不同，进程组建不起来。新卡单独资源池，用调度标签隔开。

机柜电力、散热和网卡能不能接进现有 fabric，先于采购规模。接不进就形成孤岛，平台要多养一套拓扑。试点放非关键作业，保留退回原集群的路径。采纳时指定角色，例如离线推理或一片训练分区，不做整池替换。软件栈一个版本周期后再复核，驱动和算子覆盖会改变结论。

### 12. 从 AI Infra 的角度，如何看待和应对大模型带来的变革？

**参考答案**

**结论**：大模型把基础设施从「把单个作业跑起来」变成「让一组紧耦合的 GPU 在故障和带宽限制下仍然产出 token」。峰值算力退到第二位。

调度单位变成必须同时启动的整组卡。瓶颈转到显存带宽、互联和 KV。训练是同步的集合通信，推理是变长、多租户、有时延目标的在线服务。模型结构几个月一变，把某种注意力或某种并行写死的平台会跟着过时。模型一旦对外服务，生命周期里的推理开销往往会超过那一次训练，单位 token 成本变成平台指标。卡数增加后，两次 checkpoint 之间碰到故障变成常态。

应对是把稳定面和易变面分开。集群、配额、作业 API、清单式 checkpoint 和指标少变。kernel、并行配置和单模型运行时可以换。预填充和解码、计算和存储、研究作业和生产服务，扩展方式不同的就拆开。并行策略放进配置，而不是写进一次性脚本。容量按 token 和有效 GPU 时规划，并带上 SLO。

模型不能被当成一个黑盒函数调用。并行、KV 和 checkpoint 就是系统本身。每来一篇新结构就重做整套平台，同样站不住，接口要能接住替换。

### 3. 在领导一个 AI Infra 项目时，如何定义技术愿景、设定优先级并推动落地？

**答题思路**

### 4. 当团队在核心技术方案上产生重大分歧时，你如何处理并做出最终决策？

1. 写明约束：步时或时延、显存、恢复时间、人力、能不能回滚。口味上的偏好不进列表。
2. 两套方案各写成本、风险，以及什么证据会让自己改主意。
3. 能回滚的，用同一段模型和同一套指标做有时间盒的试验，例如两种并行或两种 checkpoint。
4. 不能回滚的，由承担后果的人决定，决定里保留反对意见。
5. 记下复核日期。没有新证据，不反复重开。

例子用你真经历过的分歧。没有管理职权时，讲你如何把试验设计出来、把结果交给拍板的人。

### 5. 如何构建和培养一支高效的 AI 基础设施团队？你看重成员的哪些特质？

**答题思路**

先讲特质，再讲分工和培养，最后才是组织形式。人数和汇报线用真实的。

特质可以收成三条。能从一份 trace 讲到机制，不停留在组件名。出了事故写得清检测缺口和系统修复，肯值守自己负责的子系统。能和做模型的人把数值问题、系统问题分开谈。

分工上，调度、训练运行时、推理运行时、网络存储至少要有人能独立负责到底。全员只会调同一个框架，关键路径会没有备份。

培养用三件具体的事：事故复盘轮着写、设计文档记录放弃过的方案、研究侧的需求走同一套作业 API。讲你真用过的做法。没带过人，就讲你如何带一个同事把子系统交接到能独立值守。

### 6. 在快速发展的 AI 领域，如何确保技术架构的前瞻性与长期可维护性？

**参考答案**

**结论**：会变的部分放在接口后面，每个自研组件有主人和退役条件。前瞻性来自跟着瓶颈迁移，不来自预先做完所有抽象。

集群、配额、作业 API、checkpoint 清单和指标保持稳定。并行策略、kernel 和单模型运行时默认会随模型结构更换。并行配置和制品版本用数据描述，平台代码里不写死某一种张量并行或流水线。

新硬件和新的通信库先放进独立资源池，仍走同一套作业 API，不复制一整套平台。第二种真实需求出现之后再提取接口。为想象中的第五个框架做的抽象，会变成所有人的限制。

每个自研组件有负责人、升级方式和退役条件。只能前进、不能回滚的发布，不可维护。灰度、恢复演练和版本兼容与功能一起排期。

每季度用真实瓶颈复核假设。瓶颈从 AllReduce 变成 MoE 的 AllToAll，或从训练步时变成推理的单位 token 成本时，架构跟着这件事变。论文名单本身不构成路线图。

### 7. 你如何评估一项基础设施投资（如自研系统、采购硬件）的长期 ROI？

**参考答案**

**结论**：比较「未来一个硬件周期里，不做这件事会多花什么、少交付什么」。算不出来的回报率百分比不写进决策。

成本用全成本：机器、电力、网络、存储、空闲时间、维护的人。采购单价或云上标价，都不是一小时 GPU 的真实成本。

收益分成三列，不揉成一个数。省下的 GPU 时，来自吞吐或有效时间占比。省下的人工和故障损失。以及没有它就做不成的能力，例如目标规模训不起来。第三列单独说，不折进一个看起来精确的净现值。

对照方案必须存在：继续用开源、买云，或维持现状。自研加上两到三年维护。硬件常见按一代、大约两到三年看窗口，软件投资最好能带到下一代机器。换一种模型结构就作废的 kernel，和换代仍然有用的网络、调度、checkpoint，分开评估。

试点写停掉条件：精度不达标、软件栈缺口还在、单位 token 成本没有下降。利用率上升的同时重试和 SLO 失败变多，这笔投资的收益是负的。只有原作者能改的系统，人一离开，收益就归零。

### 8. 在跨部门协作中，如何向非技术背景的团队（如业务方、研究院）阐述 AI Infra 工作的价值与挑战？

**答题思路**

先问他们这一次要拍什么板：加机器、改排期，还是砍范围。材料只服务这个决定。

研究院关心实验多久能排上、配额公不公平、失败后能不能从 checkpoint 接上。业务关心单位 token 成本、时延、可用性，以及一个需求多久能上线。用这三个量级翻译：一次训练要多少卡时，挂一次丢掉多少进度，接口变慢用户会碰到什么。集合通信的细节等对方追问再讲。

挑战放在同一页：规模上去，故障会变多；模型结构一变，上季度的优化可能失效。这不是把进度表压紧就能消化的。

准备一张路径图：请求或训练作业从进入队列到产出 token 或下一步，时间和钱花在哪一段。数字用你系统里的真实数量级。没有的成本不要配。

### 9. 你认为一个优秀的 AI 基础设施负责人，最重要的三项能力是什么？

**参考答案**

**结论**：系统判断、在不完整信息下做可逆决策、把接口和负责人定清楚。这三项对应「做对的瓶颈、肯收口、别人能并行干活」。

系统判断是把问题钉在有效算力、时延或恢复时间上，并说清是计算、显存、通信、数据还是排队。组件名单和分配率替代不了这个判断。证据是能讲一次自己改过的瓶颈，以及用哪条指标确认。

决策能力是约束写得清、放弃的方案还记得、有复核时间。可逆的用试验收口，不可逆的由承担后果的人拍板。证据是一个真实分歧，不是原则表述。

组织能力是让调度、训练、推理、网络有人负责到底，并把研究侧和业务侧的需求收成同一套作业或服务接口。负责人自己要能读 trace，否则判断会被名词带走。这不是要求亲手写每一个 kernel。

讲的时候每项配一段自己的经历。缺管理样本，就用技术决定和跨团队推动代替编制故事。

### 10. 分享一个你经历过的最有挑战性的系统故障或架构缺陷，以及后续的复盘与改进

**答题思路**

选你真实扛过的一次，按时间线讲。优先用这几类里你碰到过的：checkpoint 读不到或读错、集合通信卡死、没有崩溃但整组变慢、调度重复占卡、显存泄漏把节点打满。

1. 影响：哪段时间、哪些作业或多少流量。数字用真实的。
2. 检测：告警当时响了，还是人先发现。没响就是事故的一部分。
3. 止血：隔离节点、切流量或回到上一份清单。先讲怎么止住。
4. 根因落到一个机制。人的操作只作为触发。
5. 修复是改协议、补检测或补演练，并说清如何确认下一次会抓住。

如果案例是 checkpoint，对方会追问一致性点在哪、失败后读到哪一版、异步拷贝有没有和下一步重叠。按当时的实现回答。没有这种事故，就换一个你真处理过的，不借用别人的故障。

### 11. 面对业界日新月异的技术（如新硬件、新框架、新范式），你的学习方法论是什么？

**答题思路**

方法论要能落到一个最近的例子，不报阅读清单。

1. 以当前瓶颈选题，一次只挖一个机制。
2. 读原始论文和你正在用的版本说明。和这条链路直接相关的是 Megatron 的并行、ZeRO、FlashAttention、分页 KV，再加上运行时的发行说明。
3. 用小规模把机制量出来，例如一步里的通信占比，或一条请求的 KV 占用。
4. 新组件进来时，把一次训练 step 或一次请求画到已有路径上，看哪一层假设失效。
5. 和值班的人核对。博客替代不了故障记录。

输出是一篇短笔记：适用边界、你决定不引入的原因。面试时讲最近一次你这样处理过的技术。

### 12. 未来 1-2 年，你最关注 AI 基础设施的哪个技术方向？为什么？

**答题思路**

只选一个方向。用机制说明它为什么会决定成本和可行性，再扣到你自己的经历。

和经历对得上的话，可以从这三条里选：

1. 推理成本。预填充和解码分开、KV 的传输和复用、在时延约束下的单位 token 成本。模型要对外服务时，生命周期里的推理开销往往会超过一次训练；你的经历如果在训练侧，就不要用这句。
2. 训练有效算力。故障恢复、checkpoint、慢节点。卡数上去之后，挂一次和慢慢等会吃掉峰值算力。
3. MoE 或长上下文带来的通信和显存层次。AllToAll、专家不均衡、KV 或线性注意力的状态，和稠密模型那套 AllReduce 假设不同。

硬件要进现有软件栈才有价值，方向落在你能改的系统层。收尾用你已经看到的瓶颈、你判断它还会存在的原因，以及你明确不押的东西。
