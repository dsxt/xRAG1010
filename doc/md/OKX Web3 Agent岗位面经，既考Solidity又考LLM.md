**答题思路**

3. Agent 能力：业务目标、你负责的模块（意图、工具、签名、评测里真实做过的），以及模型碰不到私钥这个边界。
4. 匹配：这个团队要的是能把自然语言收成一笔可模拟、可确认的交易的人。把话停在你最熟的那个项目上。

### 2. 项目介绍，重点说你做过的 Agent 相关的工作，链上还是链下

**答题思路**

选一个真实项目，讲 3 分钟。先说用户和资金在哪，再把链路拆开。

1. **链上**：合约保管什么状态，资产在用户钱包、合约还是托管。你写过的模块点到权限、升级和记账即可。
2. **链下**：模型、工具、索引、报价、签名分别在哪个服务。说明哪一段会等待 RPC，哪一段只是编排。
3. **边界**：模型产出结构化意图；金额、合约地址和 calldata 由链下服务按链上数据重算；签名在用户钱包或限额会话密钥里。
4. **你的职责**：哪几段是你设计和上线的。留一个你愿意被追问的难点，例如错误代币、nonce 或模拟通过但上链失败。

链上和链下都做过，就各给一个例子。只做过一边，直接说另一边你接到了哪一层，以及你准备怎么补。

### 3. EVM 执行模型里，opcode 层面 SLOAD 和 SSTORE 的 gas 消耗为什么差这么多

**参考答案**

SLOAD 是读存储，SSTORE 是写存储。差出一个数量级，是因为新增状态要被所有全节点长期保存，而同一次交易里的重复读取只是访问列表里的缓存。

现行计价（柏林 EIP-2929 的冷热访问，加上 EIP-2200、伦敦 EIP-3529）可以记这几档：

- 冷 SLOAD 2100，同一笔交易里再次读取变成热 SLOAD，100。
- 把 0 写成非 0 收 20000；这个槽若还是冷的，再加 2100，合计 22100。
- 已有的非 0 值改成另一个值：热槽 2900，冷槽 5000。写成和当前值一样，热槽只收 100。
- 非 0 清成 0 会记一笔 4800 的退款，整笔交易的退款不超过已消耗 gas 的五分之一。

第一次把空槽写成有值，状态树和后续见证都会变大，所以最贵。热读几乎只是内存查找。SSTORE 还有一道 2300 gas 的门槛，剩余 gas 不超过 2300 会直接失败，因此普通转账附带的 2300 stipend 写不进存储。

### 4. Solidity 里 delegatecall 和 call 的区别是什么，delegatecall 会改变哪个地址的 storage

**参考答案**

`call` 在被调用地址自己的上下文里执行：storage、余额和 `address(this)` 都属于被调用合约，`msg.sender` 变成发起这次 call 的合约。`delegatecall` 只借用被调用地址的代码，storage、余额和 `address(this)` 仍属于发起 delegatecall 的合约，`msg.sender` 和 `msg.value` 保持外层那次调用的值。它也没有单独的 value 参数。

所以 delegatecall 改的是**调用方地址**的 storage。代理合约 delegatecall 实现合约时，槽位写在代理上，实现合约自己的 storage 不动。

低级 `delegatecall` 在对方 revert 时只返回 false，调用方必须检查返回值。目标地址没有代码时，这种低级调用也会返回成功，因此升级前要确认实现地址真有代码。两边的存储布局必须一致，否则调用方的关键槽会被实现合约的变量写掉。

### 5. 可升级合约里，Proxy 和 Implementation 的 storage slot 碰撞问题怎么解决

**参考答案**

碰撞是因为 delegatecall 让实现合约的变量直接写进代理的存储。代理若把管理员或实现地址放在 slot 0，实现合约的第一个状态变量也会用 slot 0，一次业务写入就会覆盖代理的控制位。

标准做法是 EIP-1967：把这些控制位放进编译器不会顺序分配到的槽。实现地址槽是

`bytes32(uint256(keccak256("eip1967.proxy.implementation")) - 1)`

admin、beacon 用各自的固定字符串，同样减 1。业务变量从 slot 0 正常排列，两边碰不到。

实现合约侧再守住三条：已有变量只追加、不改顺序和类型；继承链末端留 storage gap，给以后的父合约加变量用；初始化用 initializer，因为构造函数只在实现合约部署时运行，写不进代理的状态。模块增多时，用 ERC-7201 的命名空间槽，让每个模块有独立基址。

透明代理把升级函数留在管理员路径，UUPS 把升级函数放在实现合约里，并在升级时检查新实现仍带升级入口。这解决的是函数选择器冲突和「升级逻辑丢了」，槽位本身仍然靠 EIP-1967。

### 6. Uniswap V3 和 V2 相比，集中流动性和恒定乘积的本质区别是什么，tick 是什么

**参考答案**

V2 用 \(x \cdot y = k\) 把流动性铺在从 0 到无穷的整个价格轴上，手续费默认 0.3%，LP 凭证是可互换的 ERC-20。大部分资金停在几乎不会成交的价格上。

V3 的 LP 自己选一个价格区间。价格落在区间内时，局部仍是恒定乘积，用的是虚拟储备：真实储备加上区间端点贡献的虚拟数量，乘积等于 \(L^2\)。价格走出区间后，该头寸变成单一资产，不再赚手续费。同样的手续费收入可以只用更少的资金，代价是要管理区间。手续费分成多档，头寸因区间不同而是 NFT。

tick 是离散价格刻度，价格为 \(1.0001^{tick}\)，池子里存的是 Q64.96 的平方根价格。相邻可用 tick 的间距由手续费档决定，例如 0.3% 档的间距是 60。一笔兑换沿刻度移动，只有穿过已初始化的 tick 才增减活跃流动性；两格之间流动性不变，按恒定乘积连续成交。

### 7. MEV 是什么，sandwich attack 的原理是什么，有没有做过相关开发

**参考答案**

MEV 是区块提议者及其合作的搜索者，通过决定交易的包含、排除和顺序，从用户交易里额外拿到的价值。早期叫矿工可提取价值，现在主要出现在 searcher 和 block builder 的拍卖里。常见形态有套利、清算和三明治。

三明治针对的是公开内存池里、滑点留有余地的兑换。受害者要用 ETH 买 USDC 时，搜索者先在同一笔 bundle 里买入 USDC，把价格推高；受害者仍能成交，但拿到的 USDC 更少；搜索者立刻卖回 USDC。差价扣掉 gas 和付给 builder 的出价后就是利润。搜索者的合约在无利可图时回滚，所以库存不会裸露到下一个区块。

防守放在订单参数上：更紧的 `amountOutMinimum`、短 deadline、私有通道或批量拍卖。Agent 的滑点上限由策略写死，模拟失败后不能自动放宽再发。

做过的话，按真实范围讲：你是在交易里加了最小到手量和私有提交，还是接过现成的保护 RPC。只调用过聚合器，就说明单是聚合器发出的，以及你在 Agent 里卡住滑点的位置。

### 8. RAG 和 Fine-tuning 的区别是什么，你们的 Agent 用的哪种，为什么

**参考答案**

RAG 在推理时把外部资料检索进上下文，权重不变。文档更新后重新索引即可，适合协议说明、风险规则和操作手册。它依赖检索是否命中，也占上下文长度。

Fine-tuning 改的是权重，适合稳定的输出格式、工具调用习惯和内部术语。知识写进权重后会过时，事实型语料用它记住既贵又不可靠。它不能跟着每个区块更新。

余额、授权、池子价格和 nonce 两边都不该记，应该用工具去读指定区块的 RPC 或索引。DeFi Agent 常见的组合是：工具负责链上状态，RAG 负责文档，微调只在格式和工具选择有评测收益时再上。价格和合约地址放进权重，错了就是错误交易。

回答「你们用哪种」时，按实际上线的链路说。理由落在状态会变、知识要能撤回、以及评测里工具和检索各自抬了哪一项成功率。

### 9. LangChain 的 Agent 执行框架里，ReAct 模式下 Thought、Action、Observation 的循环是怎么工作的

**参考答案**

ReAct 把推理和行动交错进行。模型先看到系统提示、工具说明、对话和草稿本，产出 Thought，再产出 Action（工具名和参数）。框架解析并真正执行工具，模型自己不执行。工具的返回或错误作为 Observation 追加进草稿本，然后再调用模型。直到模型给出最终回答，或步数、token、时间预算用完。

经典 LangChain 用 AgentExecutor 加 ReAct 文本格式：`Action`、`Action Input`、`Final Answer`。解析失败时，把解析错误当作 Observation 交回去，并设最大重试。现在更多用模型原生的 tool calling，循环一样：模型消息里带 `tool_calls`，工具节点执行，结果以 tool message 回到模型。LangGraph 把这个循环做成显式的边，状态用消息列表累加。

容易漏掉的是：有副作用的工具要能幂等，因为模型可能调用两次；Observation 是不可信数据；写链上的 Action 在这里只能产出意图，签名在循环外面的策略层。

### 10. 你们的 Agent 怎么和链上合约交互，是直接 RPC 还是有中间层

**参考答案**

写操作要有中间层。模型直连 RPC 并自己签名时，幻觉的 `to`、calldata 和 chainId 会直接进区块。

比较稳的分法是：

1. 模型只输出类型化意图：链、卖出资产、买入资产、数量、滑点上限、收款人。
2. 交易服务用白名单解析合约，按固定 ABI 组 calldata，在同一个区块上报价和 `eth_call` 模拟，再核对余额变化。
3. 签名放在用户钱包、MPC 或带额度的会话密钥里。Agent 进程不保存主密钥。
4. 广播走自己的 RPC 池，由 nonce 管理器排队。同一 nonce 可以提高费用替换。收据回来后核对日志。
5. 读操作可以更直接，仍通过工具，并带上区块号、超时和 chainId。

面试时按你的真实进程画这五步，标出签名发生在哪一个进程。若当时是脚本直接发交易，说明你现在会把模拟和白名单补在哪一层。

### 11. 用户用自然语言说「帮我把钱包里的 ETH 换成 USDC」，Agent 要怎么安全地完成这个操作

**参考答案**

模型只把这句话变成意图，数量、合约和签名都由交易服务决定。

「我的钱包」以本次登录会话里的地址为准，换到的 USDC 也回到这个地址。链必须明确。ETH 默认是该链原生币，USDC 用该链白名单里的合约，小数位以合约为准。原生币卖出不需要 approve。余额和 gas 用工具读。

报价只问白名单路由或聚合器，固定一个区块，记下到手量、价格影响和路径。策略检查滑点、单笔和当日额度、收款人必须是用户本人、deadline 要短。`eth_call` 要成功，并且 USDC 的增加和 ETH 的减少与报价一致。

展示给用户的是解码后的内容：卖出多少 ETH、最少收到多少 USDC、路由合约、截止时间。主钱包由用户签名；会话密钥只有落在预授权里才能代签。服务端组好的交易再广播。失败就停，不自动放宽滑点。意图 ID 用来挡住重复提交。

难在三处：报价到上链之间区块会前进；同一个符号对应多个合约；提示注入会改收款人。三处都由白名单、模拟和用户看到的解码结果卡住。

### 12. Ethereum 的 EIP-4337 账户抽象是什么，UserOperation 的执行流程是怎样的

**参考答案**

EIP-4337 让智能合约账户自己发起操作。用户签的是 UserOperation，由 bundler 收进另类内存池，再打包进一笔普通交易，共识层看到的就是这笔普通交易。

一笔 UserOp 里有 sender、nonce、callData、gas 和费用上限、签名；新账户可以带 factory 数据，也可以带 paymaster 代付。流程是：

1. 账户或钱包构造 UserOp，对包含 chainId 和 EntryPoint 的哈希签名，发给 bundler。
2. bundler 先模拟 validation。这一段不读取会在模拟和打包之间变化的区块环境，存储也限制在账户和 paymaster 的关联槽，模拟才和上链一致。
3. bundler 调用单例 EntryPoint 的 `handleOps`。EntryPoint 先对整批做 validation：按需用 factory 部署账户，调用 `validateUserOp`，有 paymaster 就检查代付押金。
4. 整批验证完成后才逐笔执行 callData。某一笔执行失败，同批其余操作继续，这笔仍按已用 gas 从账户或 paymaster 的押金结算给 bundler。验证失败的操作要在提交前剔除，否则整批 validation 会回滚。

nonce 是二维的：高 192 位是 key，低 64 位是序号，不同 key 可以并行。代付和会话密钥都要限制目标合约和额度。EIP-7702 让 EOA 临时委托一段代码，那是另一类账户能力。UserOperation 的打包流程属于 4337。

### 13. 实现一个带超时的 Promise.race，要求在最快响应或超时后返回结果

**参考答案**

哪个 promise 先结算，就把它的成功或失败原样交出去；到点还没有结果，就 reject 一个带 `TIMEOUT` 的错误。调用方因此分得清超时和业务失败。空数组没有响应，只会等到超时。

订阅 n 个 promise 是 O(n) 时间，额外空间 O(1) 再加一个定时器。超时不会取消已经发出的请求；要取消得另传 AbortSignal，在结算时 abort。已经完成的值会排在微任务里，比 0 毫秒的定时器更早，这和「最快响应」一致。

```javascript
function raceWithTimeout(promises, timeoutMs) {
  if (!Array.isArray(promises)) {
    return Promise.reject(new TypeError("promises must be an array"));
  }
  if (!Number.isFinite(timeoutMs) || timeoutMs < 0) {
    return Promise.reject(new TypeError("invalid timeout"));
  }

  return new Promise((resolve, reject) => {
    let settled = false;
    const finish = (settle, value) => {
      if (settled) return;
      settled = true;
      clearTimeout(timer);
      settle(value);
    };

    const timer = setTimeout(() => {
      const error = new Error("timeout");
      error.code = "TIMEOUT";
      finish(reject, error);
    }, timeoutMs);

    for (const item of promises) {
      Promise.resolve(item).then(
        (value) => finish(resolve, value),
        (error) => finish(reject, error)
      );
    }
  });
}
```

`Promise.resolve` 的回调至少排到微任务，所以 `timer` 赋值之后才会被调用。`settled` 保证只结算一次，慢回来的失败也不会变成未处理拒绝。

### 2. 你最有深度的一个 Web3 项目，从合约设计到 Agent 集成，说说整体架构

### 3. 合约的重入攻击是什么，Checks-Effects-Interactions 模式怎么用，OpenZeppelin 的 ReentrancyGuard 原理是什么

**参考答案**

重入是外部调用还没结束，对方又调回本合约。余额等状态若还没改完，同一次取款可以成功多次。转 ETH 和带回调的代币都会触发。

Checks-Effects-Interactions 把顺序固定下来：先检查权限和余额，再写状态，最后才做外部调用。先把余额减掉再转账，回调里看到的就是新余额。

OpenZeppelin 的 `ReentrancyGuard` 用一个状态字：未进入是 1，已进入是 2。进入时若已经是 2 就回滚，否则写成 2，退出写回 1。共用同一份资产状态的函数加同一把锁。两个加了锁的入口互相调用会回滚，共用逻辑放在未加锁的私有函数里。

1 和 2 都是非 0。部署时写成 1，之后每次都是非 0 之间互改，避免每次从 0 写成非 0 的 20000 gas。写回 1 的退款也不大，更不容易被「退款不超过交易 gas 的五分之一」截掉。

这把锁挡的是再次进入。外部协议仍可能在回调期间读到中间状态，这是只读重入。新版本对 view 也可以在锁着时直接回滚。Cancun 之后可以用 EIP-1153 的瞬态存储做同样的锁，交易结束即消失；OpenZeppelin 的 `ReentrancyGuardTransient` 就是这条路，基于存储的守卫已被标为后续替换。可升级合约里，这把锁要放在命名空间槽里。

### 4. 你们 Agent 的 tool calling 是怎么设计的，工具描述怎么写能让模型更好地理解意图

**参考答案**

每个工具是一份 JSON Schema：稳定的名字、何时使用、参数类型、枚举、必填项和单位。描述里同时写触发条件和排除条件。例如 `swap` 写明「用户要把资产 A 换成资产 B 时使用；只问余额时不用」。`amount` 用十进制字符串，decimals 以链上为准；`slippageBps` 写明上限。

链和代币符号在服务端用白名单解成地址，模型传来的地址也要再对一遍白名单。读工具和写工具分开。写工具先返回解码后的预览，确认之后的广播是另一步，不放在同一次模型调用里自动完成。

Schema 通过后，服务端仍要校验范围、收款人和额度。工具失败时返回结构化错误，让模型可以改槽位；策略同时禁止它用更大的滑点或新的收款人自行重试。工具少、边界清楚，模型更容易选对。重叠的「转账」和「兑换」要在描述里写清资产变化的方向。

面试时拿出你真实的一个工具定义，讲一条它曾经选错、你后来改了描述或加了服务端校验的例子。

### 5. 大模型的 context window 有限，处理长链上历史的 Agent 怎么做 memory 管理

**参考答案**

链上历史留在索引器里，按地址、时间和事件去查。上下文里只放本轮决策需要的摘要和原文级的关键字段。

- **工作记忆**：当前意图、已确认的数量、报价、待签名交易。每轮都带。
- **会话摘要**：更早的对话压短。地址、金额、交易哈希按原文保留，不让摘要改写数字。
- **长期记忆**：默认滑点、常用链、地址备注。结构化存储，带时间和来源。用户改口就覆盖，并留版本。
- **检索**：文档和过去的对话可以用向量；余额、授权和报价用精确查询，以最新区块为准。

超出预算时先丢掉原文，留下已确认槽位和未完成交易。记忆里的旧余额不能覆盖刚刚读到的链上余额。索引结果要带区块高度，落后于执行区块时只用于解释，不用于签名。

### 6. 你们有没有做过 Agent 评估，怎么量化准确率，有没有用 LangSmith 或类似工具

**参考答案**

链上 Agent 把准确率拆开报。准备一组固定用例：用户原话、夹具状态、应该调用的工具和参数、应该拒绝的请求。分开统计意图、工具选择、参数、越权比例和模拟通过率。地址和数量做确定性比对，滑点只允许你规定的容差。话术可以由模型打分，收款地址用规则核对。

改 prompt、工具描述或模型之前重跑这组用例。线上再抽检 trace，看人工接管、模拟失败和确认后失败。温度设为 0，同一用例跑多次，看是否波动。

LangSmith 以及 Langfuse 一类产品用来存 trace、数据集和评分。没有它们，就把同一次任务的工具入参、模拟结果和收据串进自己的日志。评测集里至少包括错误代币、超额滑点和提示注入。

做过就讲用例大概的规模和你盯住的那一个失败指标。没做过，就说最小集就是这三类拒绝样本。

### 7. 多个 Agent 协作完成复杂任务，你用的是哪种框架，AutoGPT、CrewAI 还是自己实现，为什么

**参考答案**

涉及资金时，用状态机把报价、风控、确认和签名连成固定的边。LangGraph 或自己写的图都能表达这件事：每个节点有自己的工具和权限，共享一份类型化状态，签名节点只接受已经通过策略的交易草稿。

AutoGPT 那种开放循环适合探索，不适合每一步都可能转走资产的流程。CrewAI 的角色分工适合做原型；重试、权限和回放要自己补上，才能放到真实交易里。多个模型来回讨论还会放大费用，并且没有一个节点对最终 calldata 负责。

很多 DeFi 任务用一个 Agent 加工具就够了。研究、解释和监控可以分给别的节点，那些节点没有签名工具。

回答时说你真实用过的框架。没用过多 Agent，就讲单 Agent 加工具，以及你为什么把签名留在图的固定节点上。

### 8. 链上数据的实时索引，你用过 The Graph 或类似协议吗，有什么局限性

**参考答案**

The Graph 用子图把合约事件映射成实体，对外提供 GraphQL，适合历史流水、持仓和榜单。映射用 AssemblyScript 写。官方托管服务已在 2024 年 6 月停止，查询现在走去中心化网络或自建 graph-node。去中心化网络按查询收费，延迟和可用性取决于服务该子图的 indexer。

局限有四条。索引有滞后，最近的区块还会重组，所以下单前的余额、储备和授权要用指定区块的 `eth_call`。mapping 没写进去的事件，接口照样返回成功，数据却是缺的。它不看内存池，也做不好跨链的实时汇总。改 schema 往往要从头同步。

生产上用索引器解释历史，用 RPC 做执行前的最新状态，两边都带区块高度。同类选择有 Ponder、SQD，或自己消费日志并处理重组。用过就讲你索引了哪些事件、滞后多少个区块、重组时怎么回滚。没用过就讲你用日志加数据库做到了哪一步。

### 9. 你们的 DeFi Agent 有没有遇到过模型幻觉导致的链上操作错误，风险控制怎么做

**参考答案**

模型会编造代币地址、池子、链和收款人，也会在失败后建议把滑点放得很大。控制点放在模型外面，模型的句子没有最终决定权。

- 模型只输出意图。calldata 由服务端用固定 ABI 和白名单合约组装。
- 每个写操作先模拟，核对余额变化、收款地址和最小到手量。模拟失败就停止。
- 滑点、额度、approve 数量和 deadline 有硬上限。approve 用本次金额。
- 用户确认的是解码后的交易。主密钥不进 Agent 进程。会话密钥带支出限额，并且可以撤销。
- 工具返回、代币名称和网页都当数据。和系统策略冲突的指令不执行。
- 失败后不自动放宽限制重试。有按用户和全局的熔断。

面试时举一个真实案例或评测样本，例如代币名称里夹带转账指令。没遇到过线上事故，就讲这句样本会在哪一层被挡住：白名单、模拟，还是用户看到的解码预览。

### 10. Python 的 asyncio 和多线程有什么区别，你们的 Agent 服务是用 async 写的吗，遇到过哪些坑

**参考答案**

asyncio 是单线程上的协作式并发，任务在 `await` 处让出事件循环，适合同时等模型接口和 RPC。多线程由操作系统调度。等待 I/O 时线程能并行；纯 Python 的 CPU 计算受 GIL 限制，多线程不会因此用满多个核。会释放 GIL 的阻塞式 C 扩展，放在线程池更合适。

Agent 服务的时间大多花在等待上，主体通常用 async。坑集中在让出点：

- 在协程里调用同步的 web3、`requests` 或 `time.sleep`，整个循环停住。同步 SDK 放进 `asyncio.to_thread`，HTTP 用异步客户端。
- 忘记 `await`，或者 `create_task` 的结果没有保存，任务可能被回收，异常也无人领取。
- RPC 和模型调用要有超时。`wait_for` 取消任务时，`CancelledError` 继续往外抛，并释放 nonce 锁。
- `await` 前后协程会交错。nonce 的占用要在一次让出之前完成，或者用 `asyncio.Lock`。同一把 nonce 若交给线程池，再加线程锁。
- 无界 `gather` 会打满供应商限额，用 `Semaphore` 封顶。
- 已有事件循环时再 `asyncio.run`，会报循环已在运行。

是不是 async，按仓库里的实际入口说。常见形态是接口层 async，少数同步 SDK 丢进线程池。

### 11. 你怎么看 AI Agent 在 DeFi 里的未来，完全自主的链上 Agent 最大的风险是什么

**参考答案**

比较现实的下一步是带授权的执行层：Agent 做研究、监控、报价和解释，在白名单、额度和模拟之内起草交易，由用户钱包或会话密钥签名。交易所和钱包已经有用户和风控，Agent 降低的是操作门槛，并把每一步留下可审计的意图和收据。

完全自主、还能动用资金的 Agent，最大的风险是错误或被注入的调用不可逆。链上没有回滚，密钥或会话权限一旦被绕过，损失直接发生。它还会变成可预测的对手盘：按过期报价成交、被三明治，或者在目标只写成「提高收益」时去签无限授权和有毒池子。

能落地的自主发生在授权盒子内部。超出盒子的动作停下来等人。责任要能追溯到哪一条策略、哪一次签名、哪一个模型版本。

### 12. 实现一个 Trie（前缀树）的插入和搜索，要求支持通配符匹配

**参考答案**

词按字面插入。搜索模式里 `?` 匹配一个字符，`*` 匹配任意长度，包括空串，规则与 shell 通配一致。面试官若要 LeetCode 211 那种单字符通配，把 `?` 换成 `.`，只保留那条分支。

插入是沿字符往下建节点，时间 O(L)，L 为词长。搜索用回溯：字面量走对应子节点，`?` 枚举全部子节点，`*` 既可以匹配空串而前进到下一个模式字符，也可以消耗一个字符后继续匹配 `*`。用 `(模式下标, 节点)` 做记忆化，避免同一状态重复算。设节点数为 N、模式长度为 P、分支系数为 Σ，时间大约 O(P·N·Σ)，记忆化空间 O(P·N)。Trie 本身没有环，递归会顺着树高或模式前进。

```python
class TrieNode:
    def __init__(self):
        self.children = {}
        self.is_end = False


class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word: str) -> None:
        node = self.root
        for ch in word:
            node = self.children_of(node, ch)
        node.is_end = True

    def children_of(self, node: TrieNode, ch: str) -> TrieNode:
        nxt = node.children.get(ch)
        if nxt is None:
            nxt = TrieNode()
            node.children[ch] = nxt
        return nxt

    def search(self, pattern: str) -> bool:
        memo = {}

        def dfs(index: int, node: TrieNode) -> bool:
            key = (index, id(node))
            if key in memo:
                return memo[key]
            if index == len(pattern):
                memo[key] = node.is_end
                return node.is_end

            ch = pattern[index]
            if ch == "*":
                ok = dfs(index + 1, node) or any(
                    dfs(index, child) for child in node.children.values()
                )
            elif ch == "?":
                ok = any(dfs(index + 1, child) for child in node.children.values())
            else:
                nxt = node.children.get(ch)
                ok = nxt is not None and dfs(index + 1, nxt)
            memo[key] = ok
            return ok

        return dfs(0, self.root)
```

`*` 先尝试匹配空串，再尝试多消耗一个字符，所以 `c*t` 能命中 `cat`，`*` 单独也能命中任意已插入的词。模式比词更长、或中途没有对应子节点时返回 false。

### 4. 设计一个链上资产管理的 AI Agent 平台，支持多链、多钱包、自然语言交互

**参考答案**

平台分成身份、钱包、链适配和执行四层。

用户用钱包签名登录。一个账户挂多条链、多个地址，地址分可签名和只读。「我的 ETH」对应多个地址时先确认。每笔意图都带 chainId。

主密钥留在用户钱包。代发用会话密钥或 MPC，权限写成额度、代币白名单和到期时间，并可以撤销。模型进程碰不到主密钥。

EVM 先做成一套适配器，管 RPC、nonce、模拟和回执。历史和持仓走索引器，下单前的余额和报价用指定区块的 RPC，并标出区块高度。索引落后时只用于展示。

执行是固定工作流：话术变成查询、转账、兑换或存取，服务端补全合约和精度，策略检查收款人、滑点、单笔和每日额度，再展示解码预览。用户确认后签名、广播，并核对收据。意图 ID 防止重复提交。trace 留下工具参数和交易哈希。

新链先作为只读适配器接入，跑稳再开放写。签名不交给自由多 Agent。提示注入和错误合约由白名单、模拟和用户确认的解码结果挡住。

### 5. 你有没有读过 EIP 或者 Ethereum 黄皮书，说一个你觉得最有价值的 EIP 以及原因

**答题思路**

黄皮书是状态转换和操作码的形式化规格，适合当工具书查。没通读就直接说你查过哪些章节。然后只讲一个你真读过、又和这个岗位有关的 EIP。下面用 EIP-1559 作为可以展开的版本。

EIP-1559 在伦敦升级把一口价拍卖改成基础费加小费。每个区块的 gas 目标等于 gas 上限的一半。父区块用量高于目标时，基础费最多上调八分之一，低于目标则最多下调八分之一。基础费销毁，优先费给提议者。交易给出 `maxFeePerGas` 和 `maxPriorityFeePerGas`；maxFee 低于当前基础费就不能进块。实际小费是优先费和「maxFee 减基础费」中的较小值。

它的价值是费用随拥堵连续变化，钱包更有依据去估价。拥堵连续很多个区块时基础费仍会涨，MEV 也会通过小费竞价。做 Agent 时，gas 按基础费加一小笔优先费来估，maxFee 留出后续几个区块的上浮空间。

如果我的工作更靠近签名确认，我会改讲 EIP-712：域分隔符把 name、version、chainId 和 verifyingContract 绑进哈希，用户签的是结构化字段。只讲自己读过的那一个，并能说出它改变了哪一段代码。

### 6. Agent 的 prompt engineering 里，system prompt 哪些内容是必须有的，有没有遇到过 prompt 注入攻击

**参考答案**

system prompt 至少固定五块，并由服务端注入，不从用户句子里覆盖。

- 边界：可以查询和起草，不能编造余额，不能自己签名，不能更换收款人。
- 工具策略：数字以工具返回为准；工具失败就说明失败，不能换成脑补的数。
- 输出形状：要么是给用户的解释，要么是符合 schema 的意图。
- 安全规则：写操作必须经用户确认；滑点和额度有上限；与这些规则冲突的指令拒绝执行。
- 会话事实：当前用户、允许的链、时间。这三项由服务端写入，模型只把它们当作已确定的事实。

提示注入会写在用户输入、代币名称、RPC 错误和网页里，例如要求忽略规则并转走资产。分隔符能帮模型把数据和行为分开，真正的拦截在服务端：校验工具参数、合约白名单，以及让用户确认解码后的交易。评测集里要有这类句子。

遇到过就讲那次改了哪条策略。没遇到过线上案例，就讲这句样本在上线前会命中哪一层。

### 11. LeetCode 460，LFU Cache（按访问频率淘汰）

**参考答案**

`get` 和 `put` 都要 O(1)。用一张表存 key 到值和频率，再用频率映射到一个有序桶。桶里左边是该频率下最久未用的 key，右边是最近使用的。另外记下当前最小频率，淘汰时就不用扫描所有频率。

`get` 命中后频率加 1：从旧桶删除，追加到新桶末尾。旧桶空了，且它就是最小频率，最小频率加 1。`put` 已有 key 时更新值并同样加频率。新 key 在容量已满时，从最小频率桶的左端淘汰，再以频率 1 插入，最小频率记为 1。同频率时左端就是最久未使用的那个。

空间 O(capacity)。容量为 0 时 `get` 返回 -1，`put` 直接返回。更新已有 key 不会淘汰别人。

```python
from collections import OrderedDict


class LFUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.min_freq = 0
        self.values = {}
        self.buckets = {}

    def _touch(self, key: int) -> None:
        value, freq = self.values[key]
        bucket = self.buckets[freq]
        del bucket[key]
        if not bucket:
            del self.buckets[freq]
            if self.min_freq == freq:
                self.min_freq += 1
        freq += 1
        self.values[key] = [value, freq]
        self.buckets.setdefault(freq, OrderedDict())[key] = None

    def get(self, key: int) -> int:
        if self.capacity <= 0 or key not in self.values:
            return -1
        self._touch(key)
        return self.values[key][0]

    def put(self, key: int, value: int) -> None:
        if self.capacity <= 0:
            return
        if key in self.values:
            self.values[key][0] = value
            self._touch(key)
            return
        if len(self.values) >= self.capacity:
            oldest = self.buckets[self.min_freq]
            evict, _ = oldest.popitem(last=False)
            del self.values[evict]
            if not oldest:
                del self.buckets[self.min_freq]
        self.values[key] = [value, 1]
        self.buckets.setdefault(1, OrderedDict())[key] = None
        self.min_freq = 1
```

`OrderedDict` 的头尾删除是均摊 O(1)。官方例子里容量为 2，`put(1,1)`、`put(2,2)`、`get(1)` 之后，key 1 的频率是 2；`put(3,3)` 淘汰频率为 1 的 key 2。再 `get(3)` 后，key 1 和 key 3 频率相同，key 1 更久未用，`put(4,4)` 淘汰 key 1。
