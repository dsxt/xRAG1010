## 面试感受

基础背得再顺，场景题一深就露馅。Redis 有哪些数据结构这种话，面试官懒得问；他更想听你大促当天在干嘛、超卖了怎么补、老板问系统撑不撑得住，你敢不敢拍个数。

三轮下来，OPPO 想要的是：能落地、能背锅、能跟产品拍桌子，也能跟 DBA 把慢 SQL 聊明白的人。纯八股选手别来凑热闹。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「做什么的、做成过什么、为什么匹配」讲。

1. 一句话：年限、Java 后端、交易或商品这条链路。不要从教育经历讲起。
2. 只留一个生产系统：用户是谁、你负责哪一段、量级用你记得住的数量级（QPS、订单量、大促倍数）。记不清的百分比不要编。
3. 埋两个可以被追问的点，例如幂等、库存、慢 SQL、大促当天你值过班。面试官会顺着这两个点往下问。
4. 收尾对准岗位：能独立把一条写链路讲清楚，也能在出问题时定位。

不要堆框架名单。学习项目、Demo 不要放进这段。

### 2. 讲一个你最近做的项目里最像生产问题的场景，不要讲学习项目

**答题思路**

选最近半年里真正出过故障、对过账或扛过大促的一件事。没有线上事故，就选一次你改过失败路径的发布，不要改用课程项目。

按这个顺序讲，大约 3 分钟：

1. 场景：哪天、什么业务动作、影响面。先给数量级，再画链路。
2. 链路：请求从哪进来，经过哪些服务，写到 MySQL、Redis 还是消息队列。你负责哪一截。
3. 异常点：超时、重复请求、脏数据、慢 SQL，四选一讲透。当时的第一判断是什么，后来证据证明是什么。
4. 你做的改动：改的是超时、唯一约束、补偿任务还是索引。为什么没选另一个做法。
5. 结果：错误率、耗时或资损停在什么程度。没有监控数字就说你后来补了哪张图。

主动留下能展开的口：状态怎么迁、失败了谁重试、怎么确认没有重复写。被问到没做过的细节就说没做到，接着讲你当时的边界。

### 3. 有个接口平时 20ms，某天大促突然 P99 到 2s，你先查什么，再查什么，最后怎么定位到慢 SQL 还是外部调用

**参考答案**

先看是整体变慢还是只有尾巴变慢，再把这 2 秒拆到排队、数据库、Redis 和下游调用上。P99 到 2 秒，经常就是某个超时或重试，不是代码突然算了 2 秒。

1. 先对齐时间线。看 QPS、P50、P99、错误率和有没有发布或配置变更。P50 也从 20ms 抬上去，多半是容量或必经依赖变了；只有 P99 变坏，优先看锁、队列、GC、个别慢请求和重试。
2. 再看饱和。应用活跃线程、队列长度、GC 停顿、数据库连接池等待、Redis 连接等待。线程堵在借连接上，这 2 秒是等出来的。
3. 然后拆时间。有链路追踪就按 span 排序；没有就看访问日志里的分段耗时。同一分钟拿慢请求的 trace 去对 MySQL 慢日志和 Redis slowlog。
4. SQL 执行时间接近 2 秒，就是慢 SQL，接着看锁等待和执行计划。SQL 只有几毫秒、HTTP span 接近 2 秒，就是外部调用，看下游耗时、连接池排队和客户端超时。两边都短，回到线程排队和 GC。
5. 大促优先怀疑库存行锁、连接池打满、缓存失效后打到数据库、下游没设超时。有重试时，一次 400ms 的失败会被乘成接近 2 秒。

先加一张分段耗时，再决定是加索引、收超时，还是限流。不要一上来扩容。

### 4. 用户重复点提交订单，前端没拦住，后端怎么保证不会下两单，从网关、接口、数据库、消息消费几个层面说

**参考答案**

前端禁用按钮挡不住超时重试。后端要保证同一个业务动作只有一笔订单，每一层都用同一个幂等键。

1. 网关按用户和接口限流，挡掉连点造成的突发。可以要求带上幂等键，但网关没有订单数据，不能当作不会下两单的证据。
2. 接口用稳定的幂等键，例如用户加客户端令牌，或者预下单时发的令牌。Redis `SETNX` 只能挡掉短时间的重复包，键过期或 Redis 故障之后仍然可能重入。抢到锁之后还要把结果写进数据库。
3. 数据库做最终裁决。订单表对幂等键建唯一索引，插入和订单写入放在同一个事务里。冲突时查出已有订单，把原来的订单号返回去，不要再插入一笔，也不要返回一个让客户端继续重试的错误。禁止先查再插，两次请求会同时查到没有。
4. 消息至少会投递一次。消费者按订单号做唯一约束或去重表，重复消息直接当成功。位点在处理成功之后再提交，见下面 Kafka 那题。

返回结果也要幂等：第二次请求返回第一次的订单，页面才能停住。

### 5. Redis 里存了商品详情，数据库更新后缓存还是旧的，你会怎么设计更新策略，延迟双删和监听 binlog 你选哪个，为什么

**参考答案**

商品详情以监听 binlog 删缓存为主，更新接口在数据库提交成功后再删一次，并给缓存一个 TTL。延迟双删只适合还没有 binlog 的过渡，不作为主方案。

延迟双删要防的是这段窗口：线程 A 删了缓存，线程 B 读到旧库并写回缓存，线程 A 才提交新数据。第二次删除放在一段延迟之后，指望把 B 写回的旧值清掉。延迟只能估计，请求里睡眠也不合适，第二次删除失败就没有人再试。

binlog 记的是已经提交的变更，后台、脚本和其他服务的写入都能覆盖到。消费失败可以重试，积压能看见。代价是缓存会落后一个消费延迟，详情页通常可以接受。价格和库存在下单时不能读这份缓存，要走扣减自己的数据。

详情是多表拼出来的，更新时不要把一份半成品写进缓存，只删除。读请求回填时带上版本号，用 Lua 保证版本更旧的值不能覆盖新值。删除失败靠 TTL 和 binlog 重试兜住。

### 6. 一个热点商品被大量请求打爆，Redis 单 key 成为热点，你怎么拆，怎么预热，怎么防止缓存击穿

**参考答案**

一个 key 在集群里只落在一个分片，读再多也打在同一个主线程上。详情是读多写少，要在 Redis 前面把量吃掉，再把 key 拆开。

1. 拆：应用内用短 TTL 的本地缓存挡住大部分读。仍然打到 Redis 的，把详情复制成多份 key，客户端按请求散列到其中一份，让多个分片一起扛。份数不用很多，够把单核从打满降下来即可。库存不能这么复制后各写各的，库存要分段扣减，每段一个 key，下单时选一段。
2. 预热：开售前把热点详情写入 Redis，并提前打进各实例的本地缓存。开售瞬间如果全部未命中，会一起回源数据库。
3. 防击穿：击穿是热点 key 过期的那一下，大量请求同时打到数据库。大促期间热点 key 不要刚好在峰值过期。值里放逻辑过期时间，过期后仍返回旧值，只允许一个请求回源刷新。没有旧值时，用互斥锁让一个请求查库，其他请求短暂等待或直接返回售罄，不要全部穿透。

本地缓存会有几秒不一致。库存和是否售罄以扣减结果为准，不以详情页缓存为准。

### 7. Kafka 消费者消费订单消息时宕机了，重启后消息会不会丢，offset 怎么提交才靠谱

**参考答案**

消费者宕机不会把消息从日志里删掉。会不会丢，取决于位点是在处理之前提交，还是处理成功之后提交。同一消费组重启，一般是重复，不是丢失。

自动提交并没有和业务成功绑在一起。它会在后面某次 `poll` 时，把上一批已经拉下来的位点提交掉。处理完成再去 `poll`，宕在处理中途通常会再投一次。如果把消息丢进线程池就立刻 `poll`，库还没写完位点已经提交，这时宕机，这批订单消息就不会再来。

靠谱的做法是关掉自动提交，按分区顺序处理，成功之后再提交。位点表示「这个位置之前的都处理完了」，所以前面一条失败时，不能把后面已经成功的位置提交上去。提交当前批次的全部位点，只在这一批都成功时做。

订单入库以订单号唯一约束做幂等，重复投递直接当成功。再均衡之前把已经完成的位点提交掉，否则换一个消费者会整段重放。处理时间也不能超过消费组认定存活的间隔，否则分区会被抢走，和本地还在执行的任务撞在一起。

发送侧要等副本确认再认为发送成功。那是进队列之前的可靠性，和这次宕机不是同一段，但面试里应该补上。

### 8. 线上报大量 Redis timeout，但 CPU 和内存都没满，你会往哪几个方向猜，怎么验证

**参考答案**

机器平均 CPU 和内存都不满，只能说明整机没被占满。Redis 命令跑在一个线程上，一个核打满时整机仍然看起来很空。先把超时拆成「命令慢」「借连接慢」还是「网络慢」。

1. 单核打满。看 Redis 进程自己的 CPU，不要看整机平均值。再看是不是只有集群里某一个分片超时。
2. 慢命令或大 key。`KEYS`、大 hash 的整表读取、直接删除大 key，都会堵住后面的命令。用 slowlog、延迟事件和 key 的内存占用对上时间点。
3. 持久化卡住主线程。备份或 AOF 重写时的 fork，以及磁盘慢导致 fsync 拖住主线程，CPU 可以不高。看最近一次 fork 耗时、AOF 延迟计数，再看磁盘是否忙碌。
4. 客户端在等连接。池子借不出来，超时报在应用里，Redis 本身可能很闲。看连接池的等待数。使用独立连接池的客户端更容易这样；多路复用的客户端则看事件循环是不是被少数慢命令堵住。
5. 网络。在应用所在的机器上测到 Redis 的延迟，不要只在 Redis 本机看。丢包、跨机房、带宽打满都会表现为超时。
6. 内存没满也可能是看错了对象。主机还有空闲，但 Redis 已经到了自己的内存上限，正在淘汰键，延迟会抖动。看淘汰计数。

先用同一分钟的超时、slowlog 和连接池指标对齐，再改池大小或超时时间。

### 9. MySQL 一条 SQL 明明有索引却走了全表扫描，你见过哪些诡异原因

**参考答案**

索引存在，只说明优化器可以选它。先看执行计划里类型是不是全表扫描、候选索引里有没有你想的那个，再用 `SHOW WARNINGS` 看语句有没有被改写。

常见原因：

1. 字符串列和数字比较，优化器会把这一列转换成数字，列上的索引用不上。数字列和纯数字字符串比较，一般仍然能用索引。
2. 关联两边的字符集或排序规则不同，条件被改写成转换函数。
3. 对索引列套函数或做计算，例如对时间列取日期再比较。
4. 联合索引没有从最左列开始连续使用。
5. `LIKE '%关键字'` 这种前导模糊匹配。
6. 统计信息过期、数据倾斜，或者超长的 `IN` 列表让行数估歪。优化器认为回表更贵，候选索引有值，实际却不选。大批量导入后很容易遇到。
7. 表很小，直接扫描更便宜。
8. MySQL 8 的隐形索引还在，但优化器不会用。
9. `OR` 的一侧没有可用索引，或者不等于覆盖了大部分行，优化器放弃索引。

```sql
-- phone 是 varchar 时，这个比较用不上 phone 的索引
SELECT * FROM user WHERE phone = 13800138000;
```

先把改写和行数估计看懂，再考虑强制索引。强制索引会在数据分布变化后变成另一个事故。

### 10. 用线程池处理批量推送，任务数远大于线程数，如果某个任务执行特别慢，会把整个池拖死吗，怎么设计才稳

**参考答案**

一个慢任务只占一个工作线程，其他线程还能继续做。真正把池拖死的是慢任务把所有线程都占满；队列如果没有上界，没排上的任务会堆在内存里，延迟越来越大，最后把堆撑满。

单线程的池子，一个慢任务就会挡住后面的全部任务。慢任务如果拿着大家共用的锁，也会把别的线程卡住。拒绝策略如果选择由提交者自己执行，慢任务会跑到 Tomcat 或定时任务的线程上，影响就溢出这个池子。`Executors.newFixedThreadPool` 用的是无界队列，生产上不要这么建池。

批量推送可以这样隔离：

1. 推送单独用池，不和改订单、扣库存混在一起。
2. 队列有界。满了就记录并退回消息队列稍后重试，不要无界堆积，也不要占用请求线程现做。
3. 每次外部调用都有超时。超时的任务计为失败，进入有次数上限的延迟重试。
4. 线程数按下游推送接口能承受的并发来定，不按积压条数来定。
5. 看住活跃线程、队列长度、拒绝次数和任务耗时。队列持续变长，就是下游已经慢了，要降速而不是再提交。

### 11. 现在要做一个接口限流，网关层和服务层分别能做什么，令牌桶和漏桶在你这个场景里怎么选

**参考答案**

网关挡的是入口流量，服务挡的是业务额度和它自己的下游。两层都要有，因为服务之间的调用不经过网关。

网关适合按 IP、用户、接口做粗限流，在请求占用应用线程之前拒绝，并给统一的错误码。它看不到「这个商品还剩多少库存」这类规则。服务上按用户的下单频率、按商品保护库存那一行、按调用方保护某个下游。限额要放在资源旁边。

令牌桶按固定速率补令牌，桶里有存量时允许一次短突发，适合提交订单这种接口：用户连点和页面并发请求不该被一刀切死，但平均速率要被按住。漏桶按固定速率往外漏，突发被排平或直接拒绝，适合后面那一下数据库写入和扛不住尖刺的下游。

提交订单在网关用令牌桶；库存和数据库入口用突发容量很小的令牌桶，或者漏桶。拿不到额度立刻失败并返回明确结果，不要让请求线程堵在那里等令牌。集群内的总额度用 Redis 加 Lua 计算，单机限额只作为它前面的一道快速过滤。

### 12. 手撕算法：给定一个数组和 target，返回所有和为 target 的不重复二元组

**参考答案**

先定口径：二元组按值去重，`(1, 4)` 和 `(4, 1)` 是同一个；同一个下标不能用两次，数组里两个相等的值可以组成一对；空数组、长度小于 2、没有符合的组合，都返回空。下面按这个口径写。

排序后用双指针从两端往中间收。和偏小就移动左指针，和偏大就移动右指针，相等就收下这一对，并跳过两侧所有相同的值。和要用更宽的整数类型相加，避免两个大整数溢出后比较错。

时间复杂度 O(n log n)，额外空间是排序的栈空间；如果不能改原数组，先复制一份，空间 O(n)。散列也能做到平均 O(n)：扫到 `x` 时看 `target - x` 是否已经出现过，再用集合挡住重复的一对。重复值多的时候，双指针更好讲清楚。

```java
public static List<int[]> uniquePairs(int[] nums, int target) {
    List<int[]> ans = new ArrayList<int[]>();
    if (nums == null || nums.length < 2) {
        return ans;
    }
    Arrays.sort(nums);
    int i = 0;
    int j = nums.length - 1;
    while (i < j) {
        long sum = (long) nums[i] + nums[j];
        if (sum == target) {
            ans.add(new int[]{nums[i], nums[j]});
            int left = nums[i];
            int right = nums[j];
            while (i < j && nums[i] == left) {
                i++;
            }
            while (i < j && nums[j] == right) {
                j--;
            }
        } else if (sum < target) {
            i++;
        } else {
            j--;
        }
    }
    return ans;
}
```

### 2. 挑你做过的一个核心模块，讲清楚当时业务痛点、你拍板的方案、上线后踩的坑

**答题思路**

选一个你能画出失败路径的模块，不要选听起来最大、但你只写过边缘接口的系统。按痛点、方案、坑的顺序讲。

1. 痛点用一件具体的事开头：重复下单、超时关单把已支付的单关掉、对账对不平、大促时某一行库存锁死。说出影响的是用户、库存还是财务。
2. 方案讲你真正拍过的板：什么放进同步链路，什么改成消息；一致性靠唯一约束、状态机还是补偿。接着说你放弃的做法，以及放弃的原因，例如分布式锁会把热点串行化，或者分布式事务把所有下游的耗时算进了下单。
3. 坑要是上线之后的：回补不幂等把库存加了两次、延迟消息丢了没有扫表兜底、索引在生产数据量下没被选中。讲你怎么发现的，后来加了什么约束或任务。
4. 结果用你记得住的现象收尾。数字记不清就说现象和数量级。

不要编项目名和没发生过的故障。被问到同事负责的部分，说清楚边界即可。

### 3. 下单成功后要发短信、加积分、扣库存、写流水，其中扣库存必须成功，其他失败可以补偿，你怎么设计链路

**参考答案**

扣库存没确认之前，订单不能叫成功，只能是创建中。短信、积分、流水都听「订单已成功」这件事实，失败了重试，不把订单打回去。

同库时，创建订单和条件扣库存放在一个本地事务里：更新库存时带上 `stock >= 数量`，影响行数为 0 就整笔回滚。跨服务时，订单先落成创建中，再用幂等键去扣库存；扣减成功才把订单改成成功。技术失败按幂等键重试，明确没有库存就把订单失败掉。不要先给用户成功，再指望库存以后一定扣到。

成功之后写一条待发送记录，和订单状态放在同一个事务里，再由消息通知三个下游：

1. 短信按订单号去重，失败就重发。短信送不走不能回滚订单。
2. 积分按订单号入账，重复消息不能加两次。冲正用一笔反向积分，不删原记录。
3. 流水同样追加，失败重试，定期和订单对账。少了一笔就补记，不在下单请求里同步等财务库。

四个动作不要放进一个大事务。短信的耗时和失败会把库存锁拖住。库存是成功的前提，另外三件是成功之后的最终一致。

### 4. RocketMQ 事务消息和本地消息表，你在什么场景下会选哪个，别背概念，说你项目里真用得上的情况

**参考答案**

两种都是「数据库已经提交」和「消息一定能被消费」对齐，消费都要幂等。差别在消息的凭据放在哪。

本地消息表：业务数据和一条待发送记录在同一个库事务里提交。单独的任务扫描待发送记录，发出去再改状态。发送超时会再发，所以消费者要按业务键去重。它不绑定某一种消息队列，库里能查出哪些还没发出去，对账直接查这张表。代价是扫表有延迟，发送后的记录要归档，不然这张表会变成新的大表。支付成功后写流水、而且财务要在库里核对每一笔有没有发出去，用这张表更合适。

RocketMQ 事务消息：先写一条消费方看不见的半消息，本地事务提交后再提交这条消息。生产者如果没来得及确认，broker 会回查。回查必须查数据库里的订单或支付状态，不能看内存；回查里也不要重做一笔不幂等的操作。回查一直给不出结论，这条消息最终不会进入消费。订单支付成功后通知积分，团队已经在用 RocketMQ，本地结果又能按主键查到，用事务消息可以少一次扫表。

生产者实例全部挂掉时，半消息没有人回答回查。团队还没有把回查做成只查库之前，继续用本地消息表。

### 5. 订单创建后 30 分钟未支付要自动关单并回补库存，延迟队列、时间轮、定时扫表、Redis 过期事件，你选哪套，为什么

**参考答案**

用延迟消息做准时关单，用扫表兜住没发出去或没消费到的订单。不把 Redis 过期通知和进程内时间轮当凭据。

下单事务提交时，同时记下一条 30 分钟后触发的消息。RocketMQ 4 的延迟级别里有 30 分钟这一档，5 可以指定任意延迟。消费时只处理仍然是待支付的订单：`where status = 待支付` 更新成功，才回补库存。更新行数为 0，说明已经支付或已经关过，什么都不要做。回补按订单号幂等。

延迟消息可能没发出去，消费者也可能积压。再跑一个低频任务，按「待支付 + 创建时间」的索引去找超过 30 分钟的订单，走同一套关单。有索引时扫的是这一小段待支付订单，不是全表。多个实例要用调度锁，避免同时关同一批。

Redis 过期通知是发布订阅，订阅者挂了事件就没了，过期时间在实例忙的时候也不准，不能用来关单。进程内时间轮重启即丢，只适合进程内的短延时。

关单和支付回调会撞在一起。已经支付成功的不能关。关单之后才收到支付成功，走退款，不要把已关闭订单直接改回已支付，除非业务写明允许。

### 6. 库存服务和订单服务是两个库，扣库存成功但订单落库失败，怎么回滚，能不能接受最终一致，补偿任务怎么写才不死循环

**参考答案**

结果未知时先查，不要直接回补。确认订单可以按同一幂等键补写，就补写订单；确认订单没有落上，再回补库存。这个方向短时间最终一致可以接受，窗口里是少卖，不是超卖。不能接受的是回补做了两次，库存被加多。

同步调用里只做一次查询和一次决定。补偿不要在 `catch` 里递归调用原方法。真正的重试写成任务：

1. 任务表按业务键唯一，状态只有待处理、成功、死信。每次重试更新同一行，不要再插入一条。
2. 先按幂等键查订单。订单已经在，任务标成功，不回补。
3. 订单确认不存在，调用回补。回补接口以订单令牌、SKU 和「回补」这个操作做唯一约束，超时重试返回的仍是成功，库存只加一次。
4. 网络超时和 5xx 才增加重试次数，按退避拉开间隔。超过次数改为死信并告警。参数错误、找不到原扣减记录，直接停，找不到说明没有扣成，不需要回补。
5. 再加一个对账：扣减流水在，订单不在，而且超过几分钟还没有任务，就补插一条。唯一键挡住重复。这样能盖住「库存已扣、任务还没写上进程就宕了」的窗口。

对外始终返回同一个幂等结果。用户已经看到失败时，不要在后台又把订单补出来，除非用同一个键让用户的重试拿到这一笔。

### 7. ES 里商品搜索突然变慢，数据量没怎么涨，你会先怀疑索引、分片、查询语句还是集群状态

**参考答案**

数据量没涨，却在某个时间点突然变慢，先看集群状态，再看是所有查询都慢还是某一条语句变慢。索引体积和分片数量不会在数据几乎不变时突然恶化，除非刚做过映射变更、重建索引或分片迁移。

全部查询都慢，看节点是否掉线、是否正在迁移分片、JVM 老年代是否在频繁回收、搜索线程池是否排队甚至拒绝、磁盘水位是否让索引只读。一个分片慢，整次搜索都会等它。客户端超时不一定是查询本身执行了那么久，可能是线程池队列里等的。

只有某一个搜索变慢，对发布时间。常见是深分页、脚本查询、前导通配、大聚合，或者把不分词字段换成了分词字段。用 profile 看时间耗在哪个分片的哪一段，而不是先改分片数。

映射字段突然暴涨会把集群状态撑大，这仍然是集群问题，不是「索引不够」。分片过多是长期问题；这次如果刚发生过节点重启或重平衡，慢是迁移带来的，等迁移结束再判断要不要调整分片。

### 8. 微服务里 A 调 B，B 超时，A 这边线程被占满，怎么从熔断、隔离、超时、降级四件事上改

**参考答案**

先给调用加上短于上游的超时，线程才还得回来。熔断不会打断一个已经堵在 IO 上的线程，它只能阻止新的调用再堵进去。

1. 超时：连接超时和读取超时分开设，都要比 A 自己的调用方超时短。只对幂等的查询做有限次重试，下单、扣库存这种写操作不要超时后盲目重试。没有超时的时候，其余三件事都等不及。
2. 隔离：B 使用单独的并发上限，信号量或独立的一小段连接池都行。上限按 B 还能承受的在途请求来定，不按 A 的最大线程数来定。B 变慢时，多出来的请求在 A 里马上失败，A 处理别的接口的线程还在。
3. 熔断：错误率和慢调用比例一起算，超时也要计入。熔断打开后直接走失败，过一段时间放少量请求探测。探测也要有并发上限，避免半开的一瞬间又把线程打满。
4. 降级：失败时的返回值按业务写死。查询页可以返回缓存或隐藏一块；下单必须返回失败，不能假装成功。降级逻辑里不能再调用 B。

落地顺序是超时、隔离、熔断、降级。先把线程占用时间封顶，再限制并发，然后在 B 明显不健康时快速失败，最后才是产品能接受的兜底结果。

### 9. 大促前要做全链路压测，老板只问你一句话：系统能扛多少，你会怎么估 QPS、连接数、DB 压力

**参考答案**

先把「扛得住」定义成某一条链路，在约定的错误率和 P99 之内，并且没有超卖和重复下单。不带这个前提的一个 QPS 没有意义。

QPS 从业务峰值倒推，不从机器数正推。用预计峰值订单和漏斗算：详情浏览、提交、支付不是同一个量级。小时均值要换成峰值那一分钟的每秒值，大促的尖刺远高于把一小时平均到每秒。读和写分开报。

连接数用并发而不是用实例数去乘一个很大的池。同一时刻需要的数据库连接大约是「每秒请求数 × 单次数据库耗时（秒）」。例如 1000 QPS、每次占用连接 5ms，同时大约只要 5 个连接。池子远大于这个数，只会把数据库的连接内存占满。应用实例数乘每实例池大小，必须小于数据库允许的连接，并给管理连接和备份留余量。Redis 和 HTTP 客户端同样用这个算法看在途数。

数据库压力看最热的那一行和最慢的那条 SQL，不看平均 CPU。库存单行更新会被行锁串成一队；每多一个二级索引，写入就多一份维护。缓存命中之后，真正进库的读是总读量乘以未命中比例。还要看复制延迟和磁盘。

对老板的说法来自一次包含网关、应用、缓存、消息和数据库的全链路压测：在这个标准内稳定的 QPS、拐点在哪、先打满的是库存行锁还是某条 SQL。线上目标取拐点以下的一截，留出故障和流量估计误差。没有压到拐点之前，不报一个整数。

### 10. 配置中心推送配置变了，某些 Bean 不想重启就要生效，你项目里怎么做的，踩过坑吗

**参考答案**

面试时只讲你真实用过的配置中心。下面是 Spring Cloud（Nacos 走这套）和 Apollo 的差别，以及哪些对象推送之后不会变。

开关和阈值放在一个配置对象里，业务每次从这对象读，不在启动时把值抄进自己的字段。Spring Cloud 刷新环境时会重新绑定 `@ConfigurationProperties`，标了 `@RefreshScope` 的 Bean 会销毁并在下次使用时重建。普通单例里的 `@Value` 不会变。Apollo 会回写它记录过的 `@Value` 字段；你在初始化时自己 `new` 出来的线程池、缓存，两种配置中心都不会替你改。

日志级别、线程池核心线程数这种，要在变更监听里按 key 做增量调整，例如调用线程池现成的调整方法。不要为了一个数字把整个池子换掉。

常见的坑：

1. `@PostConstruct` 里按旧配置拉起了后台线程。刷新作用域的 Bean 重建时，没有销毁方法就会把旧线程留下。
2. 给数据源加上刷新作用域，一次推送会拆掉连接池，正在执行的请求失败。
3. `@ConditionalOnProperty` 只在启动时决定 Bean 是否存在，推送不会把 Bean 变出来或卸掉。
4. 一部分实例没拉到新配置。要能看到每个实例当前的值，不能只看配置中心页面显示已发布。
5. 监听器抛了异常，系统里会一半是新值、一半是旧值。

连接地址、账号这种仍然走发布重启。动态生效只留给开关、阈值和日志级别。

### 11. AI 编码工具你们团队用没用，自动生成的 Java 代码你敢直接合进生产吗，你会怎么 review

**参考答案**

可以用，不能未经评审就合进生产。生成代码的责任在合入的人，线上事故不会算到工具头上。

团队如果在用，就说实际用在哪：补测试草稿、写转换代码、起草 SQL。没有用过就直接说没有，再讲你准备怎么审查，不要编一个使用率。

审查和看一个不熟悉的同事的合并请求一样，而且默认它会编出一个能编译、但语义是错的实现：

1. 你讲不清这段为什么这样写，就不能合。尤其是事务边界、幂等键、状态迁移和钱。
2. 看空指针、并发、资源有没有关、异常是不是被吃掉后返回成功、SQL 是不是把参数拼进了语句。
3. 对一下当前仓库的 Spring 和 JDK 版本。生成代码经常调用不存在的方法，或用了这项目已经封掉的写法。
4. 测试如果只验证模拟对象被调用过，不算数。涉及超卖、重复下单的分支，要有断言最终数据的测试。
5. 不接受顺手改来的大重构。生成内容分小段合入，SQL 在接近生产的数据量上看执行计划。
6. 密钥和内部代码能不能送到外部模型，按公司规定来。工具写进文件的口令不能提交。

它适合产生草稿，不降低合并的标准。

### 12. 手撕算法：手写一个简易的滑动窗口限流器，给定窗口大小和最大请求数，判断某个请求是否放行

**参考答案**

先定口径。窗口是 `(当前时间 - 窗口大小, 当前时间]`，刚好落在左边界上的旧请求不再计数。只有放行的请求占名额，被拒绝的不记入窗口，否则一串拒绝会把窗口一直堵死。时间由调用方传入，方便测试。窗口或上限不是正数，构造时直接失败。时间回拨则拒绝这一次，避免队列里的时间倒序。这是单机限流器，多实例的总额度要放到共享存储里。

用一个双端队列保存窗口内已放行的时间。每次先从队头丢掉过期时间，队列长度达到上限就拒绝，否则把当前时间加到队尾。每个时间最多入队出队一次，平摊下来每次调用是常数时间，最坏要清掉整个窗口，空间是窗口内的放行数，不超过最大请求数。方法要同步，判断长度和入队必须是一件事。

```java
public final class SlidingWindowLimiter {
    private final long windowMs;
    private final int maxRequests;
    private final ArrayDeque<Long> hits = new ArrayDeque<Long>();

    public SlidingWindowLimiter(long windowMs, int maxRequests) {
        if (windowMs <= 0 || maxRequests <= 0) {
            throw new IllegalArgumentException("windowMs and maxRequests must be positive");
        }
        this.windowMs = windowMs;
        this.maxRequests = maxRequests;
    }

    public synchronized boolean allow(long nowMs) {
        if (!hits.isEmpty() && nowMs < hits.peekLast()) {
            return false;
        }
        long expireAt = nowMs - windowMs;
        while (!hits.isEmpty() && hits.peekFirst() <= expireAt) {
            hits.pollFirst();
        }
        if (hits.size() >= maxRequests) {
            return false;
        }
        hits.addLast(nowMs);
        return true;
    }
}
```

### 2. 你做过最复杂的一个业务域是什么，如果现在让你重做一遍，架构上你会改哪三处

**答题思路**

选一个你能从状态、数据归属和失败路径三条线画出来的域。复杂指分支和一致性，不是指微服务个数。

三处必须是结构上的改动。每一处都说清现在哪里痛、改成什么、放弃什么。可以对照下面这类方向，换成你自己的系统来讲，不要现编一个项目：

1. 成功条件：例如把「订单成功」收成库存已经确认之后，而不是先成功再补扣。
2. 数据归属：谁能写订单状态，谁只能发命令。报表从在线库拿开，避免运营查询打到交易库。
3. 故障隔离：大促的写链路缩短，非核心下游异步；预扣留下可重放的名单，而不是只留一个库存数字。

讲完说你会先做哪一处，以及为什么它的收益最大、风险可控。升级框架、补注释不算架构改动。没把握的性能数字不要报。

### 3. OPPO 商城场景里，新品手机开售，百万请求抢几万台机器，你会怎么分层：前端、网关、秒杀服务、库存、订单、MQ 各自干什么

**参考答案**

能买到的只有几万单，一百万请求里的绝大多数应该在写库之前失败。Redis 负责把人挡住，数据库只接那几万个胜出的请求。

1. 前端：页面和图片走 CDN。开售前按钮不可用，开售后每次点击带上一次发放的令牌，超时拿同一个令牌查询，不要连着重试。
2. 网关：鉴权、风控、按用户和全局限流。售罄标记打到网关或本地内存后，后面的请求直接返回售罄。
3. 秒杀服务：校验资格，用 Lua 原子地判断并扣减 Redis 库存，同时写入「谁抢到了」的名单，再发消息。这里只返回「确认中」和令牌，不返回「已经抢到」。
4. 库存：Redis 是闸门，数据库的条件更新是最后一道。开售前把可售数量预热进 Redis。扣到 0 之后马上让各实例知道售罄，停止继续打 Redis。
5. 订单：消费这几万条消息，按用户加活动做唯一约束创建订单，并在同一个事务里做数据库扣减。重复消息不会产生第二单。
6. 消息队列：只承载已经在 Redis 扣成的请求，所以堆积上限就是库存量级，不是一百万。按用户分区，死信要能重放。

数据库扣减失败时，对用户的查询结果改为失败，并按幂等规则处理 Redis 名额。不要在应答「确认中」之前只做一个减一，却没有留下可重放的名单。

### 4. 秒杀里 Redis 预扣减成功，但写订单数据库时主库挂了，用户看到抢到了，后台没单，这种资损风险怎么兜

**参考答案**

根上不要在订单落稳之前显示「抢到了」。已经显示出去的，用一份可重放的抢到名单把订单补上。数据库超时是结果未知，不是失败，不能因为超时就把 Redis 库存加回去。

应答用户之前，这个用户、商品和令牌必须已经写进多副本的消息队列，或者写进有持久化和副本的 Redis 结构。只做一个减一的计数，主库一挂就不知道该给谁补单。

消息还在，消费者就按令牌幂等重试，主库恢复后订单会补出来，用户查询从「确认中」变成成功。异步复制切换时，最后一批已经返回成功的提交也可能丢，所以补单以抢到名单为准，不假设主库的提交都还在。

如果当时已经跟用户说了成功，查询接口按名单返回「订单生成中」，不要返回一个新的失败让他再抢一次。支付渠道已经扣款但订单不存在时，要么按支付记录把这笔订单补上，要么发起退款。钱和订单之间不能有一边落下。

库存在订单确认失败之前保持扣着。只有确认这条名单作废，才回补 Redis 和数据库，而且回补要幂等。超时就回补、同时消息又把订单写上，就会超卖。名单和订单表做对账，缺单就重放，多扣就告警后人工看，不自动加库存。

### 5. 多个团队对库存、营销、订单状态机理解不一致，接口联调天天扯皮，你作为核心开发怎么把边界定下来

**参考答案**

边界是「谁能写这份数据」和「状态只能怎么迁」，不是再开一次对齐会。订单服务写订单状态，库存服务写库存数量，营销服务写券和活动的冻结、确认、释放。其他团队发命令，不改对方的表。

先把三张状态图写成代码里的迁移表，并用测试把非法迁移固定住：待支付才能到已支付，已关闭不能因为补通知被打开，券的冻结必须能按订单号释放。命令使用幂等键和固定的错误码，例如库存不足、重复确认、状态不允许。联调时对照错误码，不再争论一个词在两个团队里的意思。

下单时间线也写成一张表：冻结优惠、扣库存、创建订单、支付、确认优惠和库存。每一步写明失败由谁补偿。营销的「已锁定」不进订单的状态枚举，在接口边界上翻译。

推进时拿已经发生的重复扣减或券用了但订单取消来说明，不拿架构原则压人。先选一条新链路按这个契约做，旧接口定一个下线时间。文档要和测试在同一个变更里，只写在文档里的状态机挡不住联调扯皮。

### 6. 现在要引入 AI 客服摘要、工单自动归类这类能力，Java 后端怎么把大模型能力接进现有系统，上下文、鉴权、超时、降级怎么处理

**参考答案**

模型放在旁路，不进下单和支付的主事务。业务服务只调用内部的模型网关，厂商的地址和密钥集中在网关，不要散落在各个服务里。

1. 上下文：按工单号拉取已有对话，只带标题、描述、渠道和最近一段消息，并限制长度。电话、地址、证件号在出域前打码。分类结果必须是你自己的枚举加置信度，枚举对不上就当未分类。第一版不要让模型直接查生产库。
2. 鉴权：沿用现在客服看这张工单的权限，模型网关不再单独放宽。调用厂商的密钥放在密钥管理里。提示词和摘要按用户数据来保存和授权，并规定保留多久。
3. 超时：创建工单的请求不等模型。后台任务去摘要和归类，连接超时和读取超时都要有上限。限流和 5xx 做有限次退避，调用用工单号当幂等键，避免超时后重试造成多次计费还互相覆盖。
4. 降级：超时、熔断或置信度不够时，工单留在原来的人工队列，页面说明摘要暂时没有。创建工单、转人工、退款都不能被模型拖住。自动归类只能影响排队，低置信度不直接派到错误的组。模型调用有单独的并发上限和每日额度。

模型输出记成一条可修正的建议，人改过的结果留下来，用来看准确率。不根据摘要自动做退款这种不可逆操作。

### 7. 分库分表后运营要查跨月订单报表，开发说不好查，产品说必须查，你怎么折中

**参考答案**

先问清报表的维度，很多「必须跨月」其实是查一个用户自己的订单。分片键是用户时，这查询本来就落在一个分片上，加上时间条件即可，不必做一套分析库。

真正难的是所有用户、跨月、还要随意筛选。在线库的分片键是为下单准备的，不要为了报表改掉，也不要让运营的查询扫每一个分片。折中是加一条旁路：用数据库变更日志把订单同步到按时间组织的查询库，按月分区，常用的日报先汇总好。跨月报表查的是这条旁路，不是交易主库。

和产品把延迟写进需求。运营看盘可以接受分钟级延迟；财务对账用第二天的核对结果，不和实时搜索共用一条不准的链路。能支持的筛选条件列出来，例如时间、状态、店铺。临时想加的任意关联，另算成本。

旁路还没建好时，用夜间任务导出限定时间范围的数据，禁止把报表 SQL 打到主库。查询库和主库对总数，延迟和缺数要有告警。这样交易的分片不用拆开，产品也能查，只是不再要求和刚提交的订单同一秒可见。

### 8. 系统里用了 Redis、MySQL、Kafka、ES，老板问你：明年流量翻 3 倍，先扩哪个，不花钱能先优化什么

**参考答案**

先扩已经接近瓶颈的那个，不按组件名字轮流扩。交易系统里先核对 MySQL，因为热点行锁、慢 SQL 和连接数翻三倍时最容易先到顶。应用无状态，扩起来便宜，但解决不了一行库存被写爆。

用现有峰值判断，不要凭印象：

1. MySQL 看慢查询、锁等待、连接、复制延迟和磁盘。Kafka 有堆积但 broker 很闲，通常是消费者后面的数据库慢，加 broker 没有用，先提高消费后的写入效率。一个热点 key 的分区，加分区也散不掉。
2. Redis 看单个进程的 CPU、是不是到了自己的内存上限、是不是某一个 key 热。内存和单核都有空闲就先不扩。
3. ES 看搜索线程池有没有拒绝、堆和磁盘水位。搜索不是这次业务峰值的话，可以排在后面。

不花钱能先做的：改慢 SQL、归档冷数据、减少不必要的二级索引；热点读用本地缓存挡住；库存热点行拆开；短信和积分继续异步；连接池按在途请求重算，拆掉过大的池；ES 去掉用不到的字段和深分页，旧索引按策略删掉。这些做完再压一次，剩下的倍数才是该买的机器。

对老板只报两句：瓶颈在哪，不花钱的优化预计能吃掉多少，其余加在哪个组件上。估计不了的部分用压测补，不报一个拍出来的三倍配置。

### 9. 你带过人吗，或者说你是怎么把踩过的坑变成团队规范的，举一个真事

**答题思路**

没有正式带过人就直接说没有，改讲你怎么影响过同一条链路的写法。不要把参与过一次发布说成带团队。

用一件真事，按这个骨架讲：

1. 发生了什么：重复写、超时把线程打满、或者一次配置推送把连接池拆了。讲你自己的责任，不把责任推给某一个同事。
2. 根因是什么习惯，而不是谁粗心。
3. 规范写成能检查的条目。例如「写接口必须带幂等键，表上有唯一约束，代码评审不通过」。只写「注意幂等」不算规范。
4. 落地在评审清单、公共客户端或数据库变更检查里，让以后不靠记忆。
5. 后来怎么确认别人真的按此做了：拦截了一次有问题的合并，或同类故障没有再生。

没有把握讲完整的事故，就讲一个较小的线上问题。不要编一条团队规范。

### 10. 有个老开发坚持用存储过程写核心逻辑，你坚持放应用层，意见不合你怎么推进，不是吵，是说清楚落地动作

**参考答案**

先把边界划开，不要主张「存储过程全部搬走」。集合式的条件更新、唯一约束和对账用的批量 SQL 留在数据库；分支很多、还要调用其他服务的流程放在应用里。存储过程难做代码评审和单测，也进不了链路追踪，发布还绑在数据库权限上。它的好处是一次往返完成一套数据修改，这个好处要用应用里的一条条件 SQL 保留下来，而不是改成逐行查询。

落地按这个顺序，不在走廊里争：

1. 把正在争的那一个过程写下来：输入、状态变化、失败时留下什么。两边先同意行为，再谈放在哪。
2. 只拿一个新需求试。应用里实现同一条条件更新，用一份接近生产的数据对结果，记录耗时和锁等待。请他和 DBA 一起看 SQL。
3. 用开关切流量，旧过程先留着。指标稳定后再删，不在第一次发布时两套一起改。
4. 评审标准写成一句：跨服务和业务分支进应用，单库里的原子更新可以留在 SQL。以后按这条判，不按资历判。

他仍然不认可时，把对比结果交给这条链路的负责人决定。会很短，因为行为和数据已经摆在那里。

### 11. 最后一轮了，说一个你这两年技术上最痛的教训，以及你后来怎么长记性的

**答题思路**

讲一个你做错过决定的技术问题，不讲心情故事，也不讲「沟通不够」这种没有工程动作的结论。

1. 你当时的判断：例如觉得超时就是失败、觉得数据库唯一约束可以以后再加、觉得先发消息再提交事务没问题。
2. 实际代价：脏数据、多出来的库存、还是对了一夜账。只说你记得住的范围。
3. 后来变成的习惯：哪一项写进了你自己的清单，哪一个公共写法被你改掉，哪类测试你现在会先补。习惯要具体到下一次能执行。
4. 收在你现在会怎么做，不要收在自责。

没有特别痛的事故，就讲一次返工最大的错误设计。不要为了显得深刻编一个 P0。

### 12. 手撕算法：给定一个订单列表，每个订单有金额和时间，返回金额 Top K 且时间最新的订单，边界情况自己说清楚

**参考答案**

口径先说死：按金额从高到低取 K 笔；金额相同，时间更新的在前；金额和时间都相同，用订单号大的在前，保证结果稳定。这就是 `ORDER BY amount DESC, time DESC, id DESC LIMIT k`。如果面试官要的是「先限定最近一段时间，再取金额前 K」，那是另一个过滤条件，先问时间范围再写。

边界：

1. 列表为空，或者 K 小于等于 0，返回空。
2. 有效订单不足 K 笔，全部返回，仍然按上面的顺序排好。
3. 空对象跳过。金额用分，用整数，不用浮点。
4. 同一订单号出现多次，先去重，留下更优的那条，再参与排名。
5. 不修改调用方的列表。

用大小为 K 的堆。堆顶始终是当前这 K 笔里最差的一笔：金额更低，或金额相同但时间更旧。新订单比堆顶更优才替换。去重之后时间复杂度 O(n log k)，堆的空间是 O(k)；去重的表是 O(n)。订单号已经唯一时可以把表拿掉。最后把堆里的结果按排名排一次再返回，堆的遍历顺序不是名次。

```java
static final class Order {
    final long id;
    final long amount;
    final long timeMs;

    Order(long id, long amount, long timeMs) {
        this.id = id;
        this.amount = amount;
        this.timeMs = timeMs;
    }
}

/** 大于 0 表示 a 更优：金额高，其次时间新，再次订单号大。 */
static int rank(Order a, Order b) {
    if (a.amount != b.amount) {
        return a.amount > b.amount ? 1 : -1;
    }
    if (a.timeMs != b.timeMs) {
        return a.timeMs > b.timeMs ? 1 : -1;
    }
    return a.id == b.id ? 0 : (a.id > b.id ? 1 : -1);
}

static List<Order> topK(List<Order> orders, int k) {
    if (orders == null || k <= 0) {
        return Collections.emptyList();
    }
    Map<Long, Order> byId = new HashMap<Long, Order>();
    for (Order order : orders) {
        if (order == null) {
            continue;
        }
        Order prev = byId.get(order.id);
        if (prev == null || rank(order, prev) > 0) {
            byId.put(order.id, order);
        }
    }
    PriorityQueue<Order> heap = new PriorityQueue<Order>(new Comparator<Order>() {
        @Override
        public int compare(Order a, Order b) {
            return rank(a, b);
        }
    });
    for (Order order : byId.values()) {
        if (heap.size() < k) {
            heap.offer(order);
        } else if (rank(order, heap.peek()) > 0) {
            heap.poll();
            heap.offer(order);
        }
    }
    List<Order> ans = new ArrayList<Order>(heap);
    Collections.sort(ans, new Comparator<Order>() {
        @Override
        public int compare(Order a, Order b) {
            return rank(b, a);
        }
    });
    return ans;
}
```

## HR面

### 1. 自我介绍

**答题思路**

HR 这一轮用一分钟，少讲框架，多讲你稳定在做什么、为什么来。

1. 年限、业务方向、最近一段负责的模块，用业务语言而不是组件名单。
2. 一件能说明你靠谱的事：大促值守、线上问题你跟到恢复、或者一个需求你从方案跟到上线。
3. 为什么看这个机会，用一句事实收住，细节留给下一题。

不报期望薪资，也不评价上一家公司。

### 2. 为什么看 OPPO，是真喜欢还是海投

**答题思路**

不要说「一直的梦想」，也不要说「只投了这一家」如果事实不是这样。海投本身不是问题，说不出为什么是这一家才会减分。

1. 你在看的是消费电子或交易后端里的少数几个机会，OPPO 是其中你主动了解过的一个。
2. 给出一个你核实过的理由：新品开售的峰值、商城和硬件的关系、你想深入的交易链路。理由要能对上这三轮问过的事。
3. 你能马上贡献的点：库存和订单、大促容量、慢 SQL，选你真做过的那一项。
4. 如果城市、业务阶段也是原因，直接说。避免空泛的「平台大、发展好」。

喜欢品牌可以说，但要落在你想做的工作上。没有把握的内部信息不要讲。

### 3. 你现在薪资多少，期望多少，别绕

**答题思路**

直接报数，数用你自己的，不要用别人的包去套。

1. 先说现在的结构：月薪、一年发几个月、奖金大致比例、股票一年实际能拿到多少。只说总包容易和对方的月薪口径错位。
2. 再说期望：给一个区间。下限是你能接受并入职的数，上限是同级别、同等职责你了解到的市场水平。区间不要宽到像没想过。
3. 说明这个数对应的职责：例如独立负责一条交易链路，而不是只接需求。
4. 对方追问底线时，重复你的下限和结构，不要现场再降一截。还没拿到级别和职责就先记下，可以说等职级明确后按这个区间谈。

不评价现在公司给得低。没有官方 offer 口头数字时，不要把口头承诺说成已经到手。

### 4. 如果给你字节和 OPPO 两个 offer，你分别会因为什么选、因为什么拒

**答题思路**

按工作内容选，不按公司名次排。每一家都准备一个你会去的理由和一个你会拒的理由，理由都要能落到团队，而不是口号。

1. 先列你的排序标准：第一年实际做的业务、你能负责的范围、城市或出差、强度、薪酬结构。标准按你的真实取舍排，现场不要改口。
2. OPPO：新品和商城的峰值、软硬件相关的交易链路，是你会选的理由。如果岗位前几个月只有历史缺陷、城市或薪酬对不上，这是你会拒的理由，用事实说，不要贬低业务。
3. 字节：业务迭代快、同方向的工程要求高，是你会选的理由。团队方向和你想深入的交易不一致，或者强度和你的安排冲突，是你会拒的理由。
4. 收尾：两家都给到你要的业务和职责，你就按上面的排序标准选；现在信息不够的部分，你会在 offer 里看团队和具体工作，而不是先站队。

这轮是 OPPO 的面试，也不要把答案说成一定会拒掉 OPPO。还没有两个 offer 时，就说这是你的判断标准。

### 5. 你觉得自己最适合做业务后端、基础架构、还是稳定性/中间件方向

**答题思路**

选一个，再用你已经做过的事说明。三个都说「可以」，等于没答。

1. 业务后端：自己守一块状态和数据，直接面对产品和峰值。交易、订单、库存属于这里。
2. 基础架构：做别人复用的平台，反馈更慢，问题更通用。
3. 稳定性或中间件：容量、消息、缓存、数据库和故障响应是本职，业务需求不是主线。

这场面试如果和你的经历一致，就明确说业务后端，并补一句你会把超时、容量和补偿做进业务里，而不是只接需求。你更想做中间件的话也直接说，同时承认你还需要补哪一段生产经验。不要为了迎合临时改方向。

### 6. 遇到过最烦的线上事故是什么，你心态崩没崩

**答题思路**

讲一件真事，重点在你前一小时做了什么。没有特别大的事故，就说最大的一次是什么级别，不要升格成全站故障。

1. 现象和影响：谁不能下单、错了多少、持续多久。只讲你知道的范围。
2. 你的动作按顺序：先止血，再定位，再修数据，再复盘。止血是限流、回滚、降级或关掉入口，选你当时真正做的。
3. 心态：说紧张是正常的，接着说明你怎么让动作保持有顺序，例如先在群里同步现象和临时措施，再查原因。不要说自己完全没有波动，也不要把慌张当作成长故事来渲染。
4. 结束后你留下的那一项改动。和前面技术轮讲过的如果是同一件，就承认是同一件，把视角换成协作和节奏。

不指责同事，不讲还在保密范围内的用户数据。

### 7. 如果入职后前三个月做的全是修历史 bug 和接老接口，你能不能顶住

**答题思路**

可以顶，同时把这三个月怎么干活说具体。不要说「我很喜欢修 bug」。

1. 承认老接口和历史缺陷就是这个系统的真实行为，先看懂再改，比空降一个新设计有用。
2. 你的做法：先补一个能锁住旧行为的测试，再改；不趁修一个缺陷重构整个模块；搞不清的规则问清谁拍板，并把结论写在接口旁边。
3. 你能接受的范围是三个月以熟悉和止血为主。你希望在这期间拿到一块明确的责任，而不是永远只接临时单。这句话用来对齐期望，不要说成条件威胁。
4. 如果完全不能接受纯维护，就诚实说你希望维护和一个小的业务目标同时存在，让对方判断岗位是不是这样。

### 8. 未来三年你想成哪种 Java 工程师，别背简历话术

**答题思路**

不要说「成为架构师」或「持续学习」。描述你能负责的问题和证据。

1. 一种工程师：能独立守住一条业务链路，从方案、上线到故障；关键取舍讲得清；MySQL 或消息队列里有一块深到能和专职的人对话。选你真正想加深的那一块。
2. 三年怎么走到：第一年把一块模块和它的值班接稳；第二年做成一次比较难的改造，例如一致性、热点或容量；第三年能审查别人的方案，并把踩过的坑写成团队能执行的约定。
3. 每一步都对着你已经有的经历说缺口。没有带过人，就说先把链路守好，再谈带人，不要把管理岗写成三年目标来凑。

说完可以问对方这个岗位第一年实际守的是哪条链路，用来验证你的目标和岗位是不是一回事。
