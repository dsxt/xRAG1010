### 3. MySQL 事务隔离级别有哪些，分别解决什么问题

**参考答案**

SQL 标准定义四个隔离级别，隔离性逐级增强、并发性能逐级下降：

- **读未提交（READ UNCOMMITTED）**：能读到其他事务未提交的数据，存在脏读、不可重复读、幻读。
- **读已提交（READ COMMITTED）**：只读已提交数据，解决脏读，仍有不可重复读和幻读。
- **可重复读（REPEATABLE READ）**：同一事务内多次读结果一致，解决脏读和不可重复读。标准下仍可能幻读，但 InnoDB 通过 MVCC（快照读）加 next-key lock（当前读）在很大程度上避免了幻读。这是 MySQL 默认级别。
- **串行化（SERIALIZABLE）**：读也加锁，事务串行执行，彻底避免上述问题，但并发最差。

容易说漏：InnoDB 的可重复读并不是完全没有幻读，快照读之后再做当前读（如 `UPDATE`、`SELECT ... FOR UPDATE`）仍可能看到别的事务新提交的行。很多互联网公司会把级别调成读已提交，减少间隙锁带来的死锁和锁范围。

### 4. 可重复读级别下 MVCC 怎么工作的，快照什么时候生成

**参考答案**

MVCC 通过 **undo log 版本链 + ReadView** 实现非锁定的一致性读。

- 每行有隐藏列：`DB_TRX_ID`（最近修改它的事务 ID）和 `DB_ROLL_PTR`（指向 undo log 中的上一版本），修改记录形成版本链。
- ReadView 包含：`m_ids`（生成时活跃的事务 ID 列表）、`min_trx_id`、`max_trx_id`（下一个待分配的事务 ID）、`creator_trx_id`。
- 判断某个版本是否可见：版本的事务 ID 等于自己，可见；小于 `min_trx_id`，已提交，可见；大于等于 `max_trx_id`，不可见；介于两者之间时，在 `m_ids` 中则不可见，不在则可见。不可见就沿版本链找上一个版本。

**快照时机**：可重复读下，事务里**第一次执行快照读（普通 SELECT）时**生成 ReadView，之后复用，所以多次读一致。不是 `BEGIN` 的时候生成（除非用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`）。读已提交则是**每次** SELECT 都重新生成。

注意：`UPDATE`、`SELECT ... FOR UPDATE` 是当前读，读最新已提交版本并加锁，不走 ReadView。

### 5. 联合索引最左匹配原则，举一个会失效的 SQL 例子

**参考答案**

联合索引 `(a, b, c)` 按 a、b、c 依次排序存储，查询必须从最左列开始、连续地使用，才能利用索引定位。

会失效或只能部分生效的例子（索引 `idx(a, b, c)`）：

```sql
-- 跳过最左列 a，无法使用索引定位
SELECT * FROM t WHERE b = 1 AND c = 2;

-- 中间列断开，只有 a 能用来定位，c 用不上
SELECT * FROM t WHERE a = 1 AND c = 2;

-- 范围查询之后的列无法继续用于索引定位
SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 3;  -- a、b 用上，c 不能用来定位

-- 对索引列做函数或隐式类型转换
SELECT * FROM t WHERE a + 1 = 2;
SELECT * FROM t WHERE LEFT(a, 3) = 'abc';

-- 左模糊
SELECT * FROM t WHERE a LIKE '%abc';
```

容易说漏的点：

- `WHERE` 里条件书写顺序无所谓，优化器会重排，`b=1 AND a=1` 一样能用到 a、b。
- 以 `a, b` 做等值再按 `c` 排序，也能利用索引有序性避免 filesort。
- 部分情况下 MySQL 会用索引条件下推（ICP）在索引内过滤，MySQL 8.0.13 起还有 Index Skip Scan，但它依赖前导列区分度很低，不要依赖。

### 6. Redis 常用数据结构，支付场景里用 Redis 一般存什么

**参考答案**

常用结构：String、Hash、List、Set、ZSet，以及 Bitmap、HyperLogLog、Geo、Stream。

支付场景里常见用法：

- **幂等与防重**：`SET key value NX EX` 存请求号、幂等 token，拦截短时间内的重复请求。
- **分布式锁**：按商户号加订单号加锁，控制并发处理同一笔订单。
- **限流与风控计数**：String 计数器、ZSet 滑动窗口，统计商户或卡号在窗口内的交易次数、失败次数。
- **缓存**：汇率、商户配置、渠道路由配置、费率，Hash 存对象。
- **会话与验证码**：登录态、支付验证码、短期 token。
- **排行榜、延迟任务**：ZSet 做延迟队列或超时订单扫描。

重要原则：**Redis 只做缓存、辅助判断和短期状态，不做资金账务的权威数据源**。余额、流水、订单状态以 MySQL 为准，Redis 数据丢失或不一致时应能从数据库恢复，并且要有大 key、热 key 的治理。

### 7. Redis 持久化 RDB 和 AOF 区别，跨境支付对账场景选哪个

**参考答案**

- **RDB**：按条件或手动 fork 子进程，生成某一时刻的全量快照文件。文件小、恢复快，适合备份；缺点是两次快照之间的数据宕机会丢，fork 在大内存下可能有短暂卡顿。
- **AOF**：记录每条写命令，按 `appendfsync` 策略刷盘：`always`（每次写都刷，最安全最慢）、`everysec`（每秒一次，最多丢约 1 秒，常用）、`no`（交给操作系统）。文件会增长，通过 AOF rewrite 压缩；恢复比 RDB 慢。
- **混合持久化**：Redis 4.0 起支持，AOF 重写时前半段写 RDB 格式、后半段追加增量命令，兼顾恢复速度和数据完整性（`aof-use-rdb-preamble`，5.0 起默认开启）。

**对账场景的选择**：对账的数据依据应该是 MySQL 里的本地流水和渠道账单文件，不应依赖 Redis 持久化保证不丢。如果 Redis 里存了对账进度、批次状态之类的中间数据，建议 AOF `everysec` 加 RDB（或混合持久化），并且设计成可以从数据库重建、批次可重跑。真正不能丢的数据直接落库，而不是依赖更强的 Redis 持久化。

### 8. 线程池七个参数分别说什么，支付回调处理用哪种队列合适

**参考答案**

`ThreadPoolExecutor` 七个参数：

1. `corePoolSize`：核心线程数。
2. `maximumPoolSize`：最大线程数。
3. `keepAliveTime`：非核心线程空闲存活时间。
4. `unit`：时间单位。
5. `workQueue`：任务队列。
6. `threadFactory`：线程工厂，用来命名线程、设置守护属性。
7. `handler`：拒绝策略（Abort、CallerRuns、Discard、DiscardOldest 或自定义）。

执行流程：线程数小于核心数就新建线程；否则入队；队列满且线程数小于最大数才创建非核心线程；都满了触发拒绝策略。注意是"先队列后扩容"，所以用无界队列时最大线程数永远不生效。

**支付回调的队列选择**：使用**有界队列**（`ArrayBlockingQueue` 或指定容量的 `LinkedBlockingQueue`），不用无界队列（`Executors.newFixedThreadPool` 默认无界，积压会导致 OOM），也不用 `SynchronousQueue`（突发流量下容易直接触发拒绝）。拒绝策略不要直接丢弃，可用 `CallerRunsPolicy` 形成反压，或自定义策略把任务落库。

更重要的是回调的处理方式：**先验签、落库记录回调（幂等）、立即返回成功应答，再异步处理业务**。线程池队列里的任务是内存态，进程重启会丢，所以不能依赖它保证回调不丢，丢失的部分靠主动查询和对账补偿。

### 9. synchronized 和 ReentrantLock 区别，锁升级过程说一下

**参考答案**

**区别**：

- `synchronized` 是 JVM 层面的关键字，自动加锁释放（异常也会释放）；`ReentrantLock` 是 JDK 提供的 API，需要在 `finally` 里手动 `unlock`。
- 两者都可重入，都保证可见性和互斥。
- `ReentrantLock` 额外支持：可中断获取（`lockInterruptibly`）、带超时的 `tryLock`、公平锁（构造参数）、多个 `Condition`。
- `synchronized` 只有非公平，通过 `wait/notify` 实现单一条件队列。
- 现代 JDK 下 `synchronized` 经过大量优化，性能与 `ReentrantLock` 相近，简单场景优先用它。

**锁升级**（针对 `synchronized`，对象头 Mark Word 记录锁状态）：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。

- 偏向锁：同一线程反复获取，只在 Mark Word 记录线程 ID。
- 轻量级锁：出现竞争时撤销偏向，线程通过 CAS 把 Mark Word 指向栈上的 Lock Record，竞争线程自旋等待。
- 重量级锁：自旋失败或竞争激烈时膨胀为 `ObjectMonitor`，未获取线程阻塞挂起，涉及内核态切换。

升级不可逆（一般不降级）。容易说漏：**偏向锁在 JDK 15 起默认关闭并标记废弃，后续版本逐步移除**，所以新版本里实际是无锁 → 轻量级 → 重量级。

### 10. Spring 事务传播行为，嵌套调用时事务怎么算

**参考答案**

七种传播行为：

- `REQUIRED`（默认）：有事务就加入，没有就新建。
- `REQUIRES_NEW`：挂起当前事务，新建独立事务。
- `NESTED`：有事务就在其中创建保存点（savepoint），没有就新建。
- `SUPPORTS`：有就加入，没有就以非事务执行。
- `NOT_SUPPORTED`：挂起当前事务，以非事务执行。
- `MANDATORY`：必须已有事务，否则抛异常。
- `NEVER`：必须没有事务，否则抛异常。

**嵌套调用的计算**：

- `REQUIRED` 套 `REQUIRED`：共用同一个物理事务，内层抛异常会把事务标记为 rollback-only；即使外层捕获了异常，最终提交时会抛 `UnexpectedRollbackException`。
- `REQUIRES_NEW`：内层独立提交或回滚，不受外层回滚影响，外层回滚也不会撤销已提交的内层。代价是占用两个数据库连接，连接池紧张时可能互相等待；如果内外层操作同一行数据还可能死锁。典型用途：写操作日志、记录失败流水。
- `NESTED`：内层回滚只回滚到保存点，外层可以继续；外层回滚则连内层一起回滚。需要数据库和事务管理器支持保存点（`DataSourceTransactionManager` 支持，`JpaTransactionManager` 默认不支持）。

最常见的坑：**同类内部方法调用（`this.xxx()`）不走代理，事务注解不生效**；另外默认只对 `RuntimeException` 和 `Error` 回滚，受检异常要配置 `rollbackFor`。

### 11. 你们项目里怎么处理接口幂等，数据库唯一索引和 Redis 防重怎么配合

**参考答案**

幂等的核心是：**同一个业务请求无论执行多少次，结果相同**。做法是由业务给每个请求一个唯一的幂等标识（如商户号加商户订单号，或客户端生成的请求号），然后分层保证：

1. **Redis 防重（前置，快速拦截）**：请求进来先 `SET idem_key value NX EX ttl`，成功才继续处理，失败说明在处理或已处理，直接返回处理中，或查询已有结果返回。作用是挡住并发重复请求，减轻数据库压力。
2. **数据库唯一索引（最终保证）**：订单表或幂等表对幂等标识建唯一索引，插入时如果触发 duplicate key，就查出已有记录返回原结果。
3. **状态机条件更新**：`UPDATE ... SET status = 'PAID' WHERE order_no = ? AND status = 'PAYING'`，根据影响行数判断，避免重复流转。

配合关系：Redis 是性能层、可以失效；数据库唯一索引是正确性层、不可绕过。即使 Redis 宕机或 key 过期，唯一索引也能兜住。

容易说漏的点：

- 业务明确失败时可以释放 Redis key 允许重试；结果未知（如超时）时不能随便删，防止重复提交。
- 调用下游渠道时要用**同一个渠道请求流水号**，让渠道侧也具备幂等。
- 幂等记录要保存首次处理结果，重复请求返回的是同一个结果。

### 12. 场景题：用户点支付连点三次，渠道侧只扣一次，你们后端怎么挡

**参考答案**

结论：**前端防抖只是体验优化，真正的拦截要靠后端多层幂等**。

1. **前端**：点击后按钮置灰、防抖，减少无效请求。
2. **请求标识**：下单时生成支付单号，三次点击携带同一个支付请求号或幂等 token。
3. **Redis 防重**：`SET NX EX` 抢占，只有第一个请求进入后续流程，其余返回"处理中"或直接返回已有结果。
4. **状态机 CAS**：`UPDATE ... SET status='PAYING' WHERE order_no=? AND status='INIT'`，只有一个请求能更新成功，其余影响行数为 0。
5. **唯一索引**：支付流水表对 `(订单号 + 支付尝试序号)` 或支付单号建唯一索引，兜住并发插入。
6. **渠道侧幂等**：调用渠道时使用固定的渠道请求流水号，即使我方重复调用，渠道也只处理一次。

关键点：渠道调用超时属于**结果未知**，不能当成失败再换一个新流水号重发，应该保持处理中，通过查询接口或回调确认结果。重复请求统一返回同一个支付结果或支付页面信息。

### 13. 场景题：支付成功渠道回调丢了，用户订单卡在支付中，怎么兜底

**参考答案**

结论：**不能只依赖回调，必须有主动查询补偿加对账两层兜底**。

1. **主动查询补偿**：对处于"支付中"超过阈值的订单，通过定时任务、延迟消息或时间轮，按递增间隔（例如 30 秒、1 分钟、5 分钟……具体间隔按渠道特性定）调用渠道的订单查询接口。
2. **统一状态处理入口**：查询结果和回调使用同一套处理逻辑，按状态机和幂等规则更新订单，避免重复入账或重复通知。
3. **渠道重试**：多数渠道会在我方未返回成功应答时重复回调，我方接口要保证验签、幂等并正确应答。
4. **对账兜底**：T+1 对账发现"渠道成功、本地处理中"的差异，进入差错处理自动补单或人工处理。
5. **超时关单**：到达最大等待时间仍未知时，不要直接关单。应先调用渠道关单或查询，确认终态后再关闭，防止"用户已被扣款但订单被关"。
6. **监控告警**：统计支付中订单的停留时长、数量，超限告警，必要时人工介入。

### 14. Kafka 和 RocketMQ 在支付系统里怎么选，事务消息用过没

**参考答案**

结论：**交易核心链路优先 RocketMQ，日志、埋点、风控数据流、数据同步等大吞吐场景用 Kafka**。

- **Kafka**：吞吐极高，生态完善（流处理、日志采集、数据管道），适合大数据量、允许少量延迟的场景。它的事务是针对"读取 → 处理 → 写入 Kafka"的 exactly-once 语义，不能直接和业务数据库的本地事务做一致性绑定；也没有原生的任意延迟消息、消息重试队列和死信队列的完整支持。
- **RocketMQ**：原生支持事务消息（半消息加回查）、延迟消息（4.x 为固定延迟等级，5.x 支持任意时间）、顺序消息、消费重试和死信队列、消息轨迹，更贴合订单、支付、通知这类强业务语义的场景。

事务消息要点：先发半消息，执行本地事务，再根据结果提交或回滚；未确认时 Broker 回查生产者的本地事务状态。它只保证"本地事务和消息发送"的一致，消费端仍需幂等和重试。

如果没有实际用过，应如实说明，并讲清原理和适用场景，不要编造线上经历。

### 15. 手撕算法：给一个数组和一个 target，返回两数之和的下标

**参考答案**

思路：用 `HashMap` 记录"值 → 下标"，遍历时检查 `target - nums[i]` 是否已在表里；在则返回，不在则把当前值放入。一遍扫描。时间 O(n)，空间 O(n)。

```java
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> idx = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = idx.get(target - nums[i]);
        if (j != null) {
            return new int[]{j, i};
        }
        idx.put(nums[i], i);
    }
    return new int[0]; // 题目保证有解时不会走到这里
}
```

边界要说清楚：先查再放，可以避免同一个元素被用两次，同时能正确处理重复值（如 `[3,3]`、target 为 6）；数组为空或无解的返回约定；金额类题目换成 `long` 避免 `int` 溢出。暴力双循环是 O(n²)、O(1) 空间，可作为对比。

### 3. 跨境 B2B 支付里清算和结算区别，系统里怎么拆

**参考答案**

结论：**清算是"算清楚谁欠谁多少"（信息流和账务计算），结算是"把钱真正划过去"（资金流）**。

- **清算（Clearing）**：交易发生后，对交易数据进行核对、计费、汇率换算、轧差，得出各方的应收应付金额，生成清算结果。
- **结算（Settlement）**：根据清算结果实际划转资金，完成债权债务的最终转移，如向收款方或渠道出款、与银行资金头寸调拨。

跨境场景下还涉及多币种、不同时区和不同国家的清算体系，清算和结算往往不在同一时间点，结算周期（如 T+0、T+1）也不同。

**系统拆分**：

1. 交易层：订单、支付单，只记录业务事实。
2. 账务层：账户、复式记账分录，保证借贷平衡，流水只追加不修改。
3. 清算模块：计费、汇率、轧差，产出不可变的清算单或批次。
4. 结算模块：根据清算单生成出款指令，调用渠道出款，跟踪结果，管理头寸。
5. 对账与差错：和渠道、银行核对，处理长短款。

各模块之间通过事件或消息异步解耦，每一步都有独立状态和幂等保护，清算结果和账务分录一旦生成不允许直接修改，只能通过冲正或调账追加。

### 4. 一笔付款从下单到渠道出款到入账，状态机怎么设计，有哪些核心状态

**参考答案**

结论：状态机的目标是**每一笔资金的位置和进度都可以被明确描述，并且不会重复或倒退**。

核心状态（可按业务裁剪）：

- 已创建（待处理）
- 风控审核中（可能再细分通过、拒绝、人工审核）
- 资金已冻结或已收款
- 已提交渠道（处理中）
- 渠道已受理
- 出款成功
- 入账成功（完成）
- 失败（含失败原因）、已关闭、退汇或已冲正

设计原则：

1. **合法流转表**：明确"从哪个状态可以到哪个状态"，不允许跳转和倒退，终态不可逆。
2. **条件更新**：`UPDATE ... WHERE status = 旧状态`，用影响行数做 CAS，配合幂等。
3. **状态流水**：每次流转写一条状态变更日志，保留时间、原因、操作来源，便于审计和排查。
4. **未知态不当失败**：渠道超时属于"处理中/未知"，通过查询或回调确认，不能随便置失败重发，否则会重复出款。
5. **多维度拆分**：主订单状态、资金状态、渠道指令状态分开管理，避免一个字段承载太多含义。
6. **异常路径**：退汇、冲正、人工介入作为独立分支设计，提前定义。

### 5. 渠道网关怎么设计，多通道路由怎么做，主通道失败怎么切换

**参考答案**

**网关设计**：

- **统一接入**：对内提供统一的请求、应答模型和错误码；对外每个渠道一个适配器（协议、报文格式、签名加密、通信方式各不相同），新增渠道只需实现适配器接口。
- **通用能力**：签名验签、重试、超时控制、限流、熔断、日志与链路追踪、渠道流水号生成。
- **配置化**：渠道、产品、费率、限额、可用时间都通过配置管理，支持动态调整。

**路由策略**：按币种、国家或地区、金额、时效要求、成本、渠道能力筛选候选渠道，再按优先级、权重或实时成功率排序，同时支持商户级白名单、灰度开关。

**主通道失败切换**：

1. 通过滑动窗口统计渠道成功率、超时率，达到阈值时熔断，路由层自动降权或摘除。
2. **区分失败类型**：明确失败（如参数错误之外的渠道拒绝、渠道明确返回失败）可以换通道重发；**超时等结果未知必须先查询确认，不能直接换通道**，否则可能同一笔款项通过两个渠道出款。
3. 切换时使用新的渠道流水号，记录完整的路由轨迹，方便对账和排查。
4. 隔离：不同渠道用独立线程池或信号量隔离，避免某个渠道变慢拖垮整个网关。
5. 恢复：通过半开探测小流量，确认恢复后逐步放量。

### 6. 分布式事务在跨境汇款里怎么选，TCC 还是可靠消息最终一致，为什么

**参考答案**

结论：**整体链路以"可靠消息最终一致加状态机加补偿对账"为主，内部强资源预留的部分（账户冻结和扣减）可以用 TCC 或"冻结 → 确认 → 解冻"模式**。

原因：

- 跨境汇款涉及外部渠道、银行，**外部系统通常不提供 Try/Confirm/Cancel 接口**，也不受我方事务协调，无法使用 TCC 或 2PC。只能靠本地事务加消息、查询、冲正来保证最终一致。
- 链路长、耗时长（可能分钟到天级），不适合长时间持有锁的强一致方案。
- TCC 对业务侵入大，要自己实现幂等、空回滚、防悬挂，开发和维护成本高。

适用划分：

- **TCC 或冻结确认模式**：内部账户、额度、优惠等需要先预留资源的场景，Try 冻结，Confirm 扣减，Cancel 解冻。
- **可靠消息（本地消息表或 RocketMQ 事务消息）**：订单状态变更后通知账务、通知商户、触发下游清算等异步步骤，消费端幂等加重试。
- **兜底**：状态机加主动查询加日终对账，处理消息之外的不一致。

取舍：最终一致意味着中间态对外可见，需要在产品和状态设计上明确"处理中"的含义。

### 7. TCC 的空回滚和防悬挂怎么处理

**参考答案**

- **空回滚**：Try 还没执行（请求超时或丢失）但协调者已经触发了 Cancel。此时 Cancel 要**识别出没有 Try 记录，直接返回成功，并记录"已回滚"标记**，不能报错也不能去解冻不存在的资源。
- **防悬挂**：Cancel 先于 Try 执行（比如 Try 请求网络延迟后才到达）。如果此时 Try 仍然执行，就会冻结资源却再也没有人来 Confirm 或 Cancel，资源永久被占用。要求 **Try 执行前先检查是否已有 Cancel 记录，有则拒绝执行**。

常用实现：建一张事务控制表（或 Seata 的 `tcc_fence_log`），以全局事务 ID 加分支 ID 为唯一键，记录状态（已 Try、已 Confirm、已 Cancel）。

- Try：在本地事务内先插入控制记录，若唯一键冲突或已存在 Cancel 记录则拒绝，再执行资源冻结。
- Cancel：在本地事务内查控制记录。没有记录，说明 Try 没执行，插入一条已 Cancel 记录并返回成功（空回滚加防悬挂标记）；状态为已 Try，则解冻资源并更新为已 Cancel；已是 Cancel，直接返回成功（幂等）。
- Confirm：只处理状态为已 Try 的记录，已 Confirm 直接返回成功。

三个接口都必须幂等，控制记录与业务资源变更放在同一个本地事务内。

### 8. 对账系统怎么设计，本地流水和渠道流水怎么匹配，差错怎么处理

**参考答案**

结论：对账是资金安全的最后一道防线，要做到**批次可重跑、结果可追溯、差错有闭环**。

**流程**：

1. **获取渠道账单**：按约定时间通过 SFTP 或 API 拉取，校验文件完整性（笔数、总金额）。
2. **标准化解析**：统一字段、币种、金额精度、时区，写入对账明细表。
3. **匹配**：以渠道流水号或我方订单号为主键关联，再核对金额、币种、状态、手续费。
4. **分类**：平账；我方有而渠道无；渠道有而我方无（"长款"和"短款"的叫法各家定义不同，建议按字段含义描述）；金额不一致；状态不一致。
5. **差错处理**。

**差错处理**：

- 可自动处理的（如渠道成功、我方处理中）：调用查询确认后，通过统一状态机补单或更新状态。
- 不能自动处理的：生成差错工单，人工核实，调账需复核（制单与审核分离），**通过冲正或调账分录追加记录，不直接修改历史流水**。
- 在途交易、跨日交易按截止时间和时区处理，次日再核。

**工程要点**：对账批次有唯一标识、幂等，可重跑；大数据量按日期或商户分片、排序后归并比较；除明细核对外增加汇总核对（笔数、总额）；对账结果和差错处理全程留痕，并有监控与告警。

### 9. 多币种场景下汇率什么时候锁，锁定后渠道失败怎么回退

**参考答案**

**锁汇时机**取决于业务模式，常见做法：

- **报价阶段**：生成报价单（含报价 ID、汇率、有效期），用户确认下单时校验报价有效并**绑定到订单**，这时汇率即被锁定。B2B 场景用得最多，用户看到的金额与实际一致。
- **成交阶段**：资金到账或换汇真正成交时才锁，更贴近真实成本，但用户侧金额存在不确定性。

锁汇意味着平台承担从锁定到实际换汇之间的汇率敞口，需要结合对冲或风控规则（报价有效期要短、设置点差、单笔限额）。

**渠道失败后的回退**：

- 换汇或出款还没发生：释放报价、解冻已冻结资金，订单置失败，无汇兑损益。
- 已换汇、出款失败：按产品规则处理，一般为按原汇率快照退回原币种（汇差由平台承担，或按协议规定），或保留目标币种重新出款。
- 无论哪种，**订单上保存汇率快照**，退款和冲正基于快照和原账务分录计算，不重新取实时汇率；需要产品和财务提前明确政策。
- 金额使用 `BigDecimal` 或最小货币单位整数，明确舍入规则和币种精度（如日元没有小数位），回退操作做好幂等并写入账务分录。

### 10. RocketMQ 事务消息半消息机制，本地消息表方案对比

**参考答案**

**RocketMQ 事务消息流程**：

1. 生产者发送**半消息**到 Broker，半消息已持久化，但对消费者**不可见**。
2. Broker 确认写入成功后，生产者执行**本地事务**（如更新订单状态）。
3. 根据本地事务结果向 Broker 发送二次确认：提交（消息变为可消费）或回滚（丢弃）。
4. 如果 Broker 迟迟没收到二次确认（生产者宕机、网络问题），会定时**回查**生产者的本地事务状态（回查有次数上限，超过后按回滚处理，具体次数和间隔可配置）。回查逻辑必须基于业务数据判断，比如根据订单表里的记录判断事务是否已成功。

**与本地消息表对比**：

| 维度 | RocketMQ 事务消息 | 本地消息表 |
| --- | --- | --- |
| 原理 | 半消息加回查 | 业务数据和消息记录在同一本地事务，定时任务扫描后发送 |
| 依赖 | 依赖 RocketMQ 特性 | 只依赖数据库，可对接任意 MQ |
| 实时性 | 提交后立即投递 | 取决于扫描频率，有轮询延迟 |
| 开发成本 | 实现回查接口 | 建表、扫描任务、清理历史数据 |
| 额外代价 | 回查逻辑要正确 | 占用数据库，消息表膨胀，扫描有压力 |

两者共同点：只保证"本地事务和消息发送"一致，**消费端必须幂等**，并配合重试和死信处理。实际选择：用 RocketMQ 且追求实时性，选事务消息；MQ 不支持事务消息或希望解耦中间件，选本地消息表。

### 11. Redis 分布式锁在支付幂等里怎么用，锁过期但业务没跑完怎么办

**参考答案**

**基本用法**：加锁 `SET lock:{商户号}:{订单号} 随机UUID NX PX 过期时间`；释放时用 **Lua 脚本**先比较 value 再删除，防止误删别人的锁：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

锁粒度细化到订单级别，持有锁期间完成"查询订单状态 → 校验 → 状态流转"。

**锁过期但业务没跑完**：

1. **看门狗续期**：Redisson 在没有显式指定 leaseTime 时，默认锁时间为 30 秒，并且每隔约三分之一时间续期。注意：**显式指定 leaseTime 后不会自动续期**。
2. 设置合理的过期时间，并给业务加超时控制，保证业务耗时小于锁过期时间；尽量缩小临界区，不要在锁内做耗时的远程调用。
3. **锁不能作为正确性的唯一保证**。GC 停顿、网络分区、主从切换（异步复制导致锁丢失）都可能让两个客户端同时持锁。所以必须有兜底：数据库唯一索引、状态机条件更新（CAS）、乐观锁版本号，必要时使用 fencing token（单调递增令牌，下游拒绝旧令牌）。

结论：Redis 锁用来减少并发冲突和保护性能，**最终的幂等和一致性由数据库约束保证**。

### 12. 场景题：发现某商户突然多笔高风险国家小额测试交易，系统侧怎么联动风控

**参考答案**

这类行为通常是试探性交易（探测卡或账户有效性、试探风控阈值）或拆分规避限额，需要实时发现、分级处置、可追溯。

1. **事件采集**：交易事件实时发送到 MQ，风控引擎（规则引擎加流式计算，如 Flink）消费。
2. **特征与规则**：用滑动窗口统计商户在短时间内的笔数、金额分布、失败率、目的国家、新增收款人数；规则示例："短窗口内向高风险国家发起多笔小额交易"；结合历史画像判断是否偏离正常行为。
3. **同步与异步结合**：交易前置链路同步调用风控获取决策（要低延迟，并约定超时降级策略）；异步分析产生告警和画像更新。
4. **分级处置**：放行、加强验证、转人工审核（订单进入风控审核中状态）、拦截、临时限额、暂停该商户的出款；严重情况冻结账户并通知合规团队。
5. **名单与合规**：对接制裁名单、黑灰名单、国家风险等级配置，支持动态更新。
6. **联动与闭环**：风控决策、命中规则、处置结果全部留痕，便于审计；人工审核结果反哺规则调优；新规则先在影子模式或灰度验证，避免误伤正常商户。

### 13. ES 在支付系统里用不用，查交易流水为什么不直接走 MySQL

**参考答案**

结论：**用，但只作为查询副本，交易主数据和强一致查询仍以 MySQL 为准**。

为什么不全走 MySQL：

- 查询条件多变（商户、时间范围、状态、金额区间、币种、关键字等任意组合），MySQL 难以为所有组合建合适的索引，索引过多又拖累写入。
- 大表深分页、模糊搜索、聚合统计，MySQL 代价高，容易拖慢交易库影响核心链路。
- 运营后台、商户对账查询属于读多且允许秒级延迟，放到 ES 可以隔离读压力。

实现与注意点：

- 数据同步：通过 binlog（Canal、Flink CDC 等）或消息异步同步到 ES，存在延迟，是**最终一致**。
- 对**强一致**场景（支付结果确认、对账、资金操作）仍查 MySQL，不用 ES 做判断依据。
- ES 不支持事务，数据丢失或错乱时能从 MySQL 重新回灌。
- 深分页使用 `search_after` 而不是 `from + size`；按时间做索引分片，冷热分离。
- 如果数据量和查询复杂度都不高，合理建好 MySQL 索引就够了，不必为了用而引入 ES。

### 14. AI 相关：有没有用大模型做过日志分析或风控规则提取，怎么落地的

**参考答案**

这是方案类问题。没有实际做过就如实说明，再讲清楚你会怎么落地；做过则按真实经历补充。一个稳妥的落地思路：

**日志分析**：

1. 先**脱敏**（卡号、账号、姓名、证件号等敏感信息），数据不出境并遵守合规要求，优先使用私有化或合规的模型服务。
2. 先用传统方法降噪（日志模板聚类、异常关键字过滤），再把聚合后的异常样本、上下游调用链交给模型总结根因。
3. 结合 RAG 检索历史故障案例和运维手册，输出结构化结果（可能原因、影响范围、排查建议），并附上引用的日志原文，减少幻觉。

**风控规则提取**：

1. 从历史案件、调单报告、拒付记录中让模型抽取特征和阈值，生成候选规则（规则 DSL）。
2. **必须人工评审，用历史数据回测，再在影子模式灰度验证**，评估误杀率和召回率，不直接上线。

**边界**：大模型不放进实时交易的同步决策链路（延迟高、结果不确定、可解释性差），只做离线分析、辅助和建议；评估指标看准确率、人工采纳率、节省的排查时间。

### 15. 手撕算法：按支付状态分组并统计金额

**参考答案**

题目：入参是交易记录列表，输出 `Map<状态, 金额汇总>`。

思路：一次遍历，用 `Map.merge` 把同一状态的金额累加。金额使用 `BigDecimal`，避免浮点误差。时间 O(n)，空间 O(k)（k 为状态种类数）。

```java
public class Trade {
    private String status;
    private BigDecimal amount;
    // getter 省略
}

public static Map<String, BigDecimal> sumByStatus(List<Trade> trades) {
    Map<String, BigDecimal> result = new HashMap<>();
    if (trades == null) {
        return result;
    }
    for (Trade t : trades) {
        if (t == null || t.getStatus() == null || t.getAmount() == null) {
            continue; // 脏数据按约定跳过，或抛异常，要和面试官确认
        }
        result.merge(t.getStatus(), t.getAmount(), BigDecimal::add);
    }
    return result;
}
```

需要主动说明的边界：

- 空列表、空元素、状态或金额为 null 的处理约定。
- 金额不能用 `double`；比较金额用 `compareTo` 而不是 `equals`（`equals` 会比较精度）。
- **多币种时不能直接相加**，应按"币种加状态"分组，或先按汇率折算。
- 数据量很大时可以分片并行汇总，再合并结果。

### 3. 支付系统灰度发布怎么做，渠道切换怎么保证不资损

**参考答案**

结论：**小流量、可观测、可回滚、资金可核对**。

**灰度发布**：

- 代码层面：金丝雀或分批发布，先发少量实例，观察指标后逐步扩大。
- 流量层面：按商户白名单、商户尺度、金额上限、百分比逐步放量，先内部测试商户和小额。
- 数据库变更遵循向前兼容（先加字段或表再发代码，最后清理），保证新旧版本可共存、可回滚。
- 发布避开业务高峰，配套监控大盘、告警和回滚预案，用开关控制新逻辑。

**渠道切换防资损**：

1. 路由配置化，按商户或比例灰度切换，随时可以一键切回。
2. **在途订单不迁移**：已提交给旧渠道的订单仍按旧渠道完成和查询，新订单走新渠道。
3. 幂等：渠道流水号唯一，切换不会导致同一笔被两个渠道处理。
4. 事前验证：沙箱或小额真实交易验证，核对费率、币种、限额、回调和对账文件格式。
5. 事中监控：成功率、超时率、金额一致性实时监控，异常自动熔断回退。
6. 事后核对：切换后尽快做对账，发现差异及时处理；设置单笔和日累计限额，限制最坏损失。

### 4. 你们怎么做支付链路监控，单边账怎么自动发现

**参考答案**

**链路监控**分几层：

- **技术指标**：QPS、耗时（P95、P99）、错误率、线程池和连接池、MQ 积压。
- **业务指标**：支付成功率（按渠道、币种、商户维度）、各状态订单数量及停留时长、渠道超时率、回调延迟、退款率。
- **链路追踪**：全链路 traceId，串起交易、网关、渠道和账务的日志（如 SkyWalking 等）。
- **告警分级**：核心指标异常（成功率骤降、支付中订单堆积）高优先级通知，设置值班和升级流程。

**单边账**指的是一边已处理、另一边没有对应记录（例如渠道已扣款而我方未入账，或我方已记账而渠道没有）。自动发现的手段：

1. **准实时**：扫描"处理中"超时的订单，主动查询渠道最终状态，与本地状态比对，不一致即告警或自动补单。
2. **日终对账**：与渠道账单逐笔核对，输出差异清单进入差错流程。
3. **内部账务校验**：借贷是否平衡、账户余额是否等于流水汇总、订单状态与账务分录是否一一对应，定时校验。
4. **处置闭环**：能自动修复的走统一状态机补单或冲正，不能的生成工单人工处理，并记录原因，统计单边账数量作为稳定性指标。

### 5. 技术选型时新技术和稳定旧技术冲突，你怎么拍板，举个例子

1. **先问需求**：现有技术到底有没有解决不了的问题，新技术带来的收益是否可量化。
2. **多维评估**：成熟度、社区与资料、团队熟悉度、运维与监控能力、故障时的行为、迁移和回滚成本、合规要求。

4. **决策方式**：用数据和对比表说话，充分听取反对意见，记录决策依据（ADR），明确回退条件。

### 6. 如果让你带 3 到 5 个人做清结算模块，怎么拆任务保进度

**答题思路**

结构建议：

1. **先对齐目标与范围**：明确核心交付（MVP）、上线时间、验收标准，和产品、财务、运营确认清结算规则。
2. **模块拆分**：按领域切分，例如账务、清算计费、结算出款、对账、差错处理，再按人员能力和意愿分配，确保每个模块有明确负责人。
3. **接口先行**：先定模块之间的接口、事件和状态机，之后可以并行开发和 mock 联调。
4. **关键路径与里程碑**：识别依赖链（账务模型 → 清算 → 结算 → 对账），把风险最高的部分（渠道对接、资金一致性）放在最前面。
5. **质量保障**：设计评审、代码评审、资损用例测试、灰度计划和回滚方案；清结算对正确性要求高，不为进度牺牲。
6. **过程管理**：每日短同步、每周复盘，用看板追踪，风险早暴露；自己也承担核心设计和最难的部分，同时关注团队成员成长。

### 7. 跟产品意见不一致，比如产品要实时入账你要异步对账，怎么沟通

**答题思路**

先点明一个概念：**实时入账和异步对账并不矛盾**。入账可以基于渠道的成功确认（回调或查询）实时完成，对账是事后核对的兜底，两者是不同阶段。

沟通思路：

1. **先理解诉求**：产品要实时入账是为了用户体验和资金周转，先确认背后的目标，而不是对立。
2. **讲清风险**：用具体场景说明——渠道回调伪造、渠道状态后续变化、重复入账，如果没有对账兜底可能造成资损；最好用数据或真实事故案例。
3. **提出折中方案**：基于渠道确认结果实时入账；风险较高的场景设置入账限额、延迟可用或先入待结算户；异步对账发现差异后自动冲正或走差错流程；高风险商户保守处理。
4. **分阶段**：先上线核心场景，观察数据后再放宽。
5. **达成共识并留痕**：风险、限额、责任边界书面确认，必要时拉上风控、财务一起评审。

态度上以"共同解决问题"为主，不要简单说"做不了"。

### 8. MySQL 深分页在交易流水查询里怎么优化

**参考答案**

问题根源：`LIMIT 1000000, 20` 需要扫描并丢弃前一百万行，如果还要回表，代价更大，页数越深越慢。

优化方案：

1. **游标（键集）分页**：记住上一页最后一条的排序键，下一页直接从该位置往后查，不需要跳过 offset，性能与页数无关。排序字段要有唯一性，通常用（时间, 主键）。

```sql
SELECT * FROM trade_flow
WHERE merchant_id = ?
  AND (create_time < ? OR (create_time = ? AND id < ?))
ORDER BY create_time DESC, id DESC
LIMIT 20;
```

2. **延迟关联**：子查询只走覆盖索引取主键，再回表取目标页的数据。

```sql
SELECT t.*
FROM trade_flow t
JOIN (
    SELECT id FROM trade_flow
    WHERE merchant_id = ?
    ORDER BY create_time DESC, id DESC
    LIMIT 1000000, 20
) x ON t.id = x.id
ORDER BY t.create_time DESC, t.id DESC;
```

索引建议 `(merchant_id, create_time)`，InnoDB 二级索引自带主键，便于覆盖。

3. **业务限制**：限制最大翻页数，必须带时间范围条件，不提供"跳到第 N 页"，改成上一页、下一页。
4. **搜索引擎**：复杂条件查询走 ES，深分页使用 `search_after`。
5. **冷热分离与分库分表**：历史数据归档，按时间路由缩小扫描范围；`COUNT` 总数可缓存或使用近似值。

### 9. RocketMQ 消息积压了，支付通知延迟，怎么快速消积

**参考答案**

先**定位原因**，再处理：是生产突增、消费者变慢或卡死（下游慢、死锁、异常反复重试）、还是消费者数量不足。

**快速消积措施**：

1. **止血与降级**：如果是下游故障（如商户通知接口超时），先熔断或降级，避免消费线程被拖住；暂时限流生产端或非关键消息。
2. **提升消费能力**：增加消费者实例，调大消费线程数（`consumeThreadMax`），开启批量消费并让逻辑批处理（如批量写库）。
3. **注意并行度上限**：同一消费组内，**消费者实例数超过队列数后，多出来的实例是空闲的**。队列数不足时，临时新建一个队列数更多的 Topic，让一批临时消费者把积压消息快速转发过去，再由更多消费者并行处理。
4. **优化消费逻辑**：去掉同步慢调用、重复查询，把耗时操作异步化。
5. **分级处理**：支付结果通知属于高优先级，应隔离到独立的 Topic 和消费组，不与低优先级消息抢资源；对非关键且可丢弃的消息可以跳过。
6. **保证幂等**：积压处理过程中重试、重复消费概率上升，消费逻辑必须幂等；失败消息进入死信队列后单独处理。
7. **兜底**：积压期间用户侧可以通过主动查询接口获得结果，不依赖通知。

**事后治理**：配置积压量告警、容量评估和压测、消费耗时监控。

### 10. 最近在学什么，AI 编码工具在支付业务代码里你信到什么程度

**答题思路**

1. **最近在学什么**：如实说，最好与岗位相关，例如分布式一致性、支付与清结算领域知识、云原生、AI 应用开发；讲一件具体学到并用起来的东西，说明怎么学（读源码、做小项目、复盘线上问题）。
2. **AI 编码工具的使用立场**：不要全盘信任，也不要全盘否定，给出分级原则：
   - 信任度较高：样板代码、单元测试用例、日志和 SQL 排查辅助、文档与代码解释、重构建议。
   - 谨慎对待：金额计算、幂等、事务边界、状态机、并发和资金相关逻辑。AI 生成后必须**人工审查、补测试用例（含异常和边界）、走正常评审流程**，当作"能干的实习生草稿"。
3. **安全与合规**：不把真实用户数据、密钥、未脱敏的业务代码发到外部模型，遵守公司的使用规范。
4. **总结**：AI 提升效率，但对结果的正确性和资金安全仍由工程师负责。

### 11. 怎么判断一门新技术值不值得引进支付核心链路

**参考答案**

结论：**支付核心链路的原则是稳定、可控、可回退，新技术必须证明"解决了现有方案解决不了的问题，并且风险可承受"**。

判断维度：

1. **必要性**：要解决的具体问题是什么，收益能否量化（性能、成本、可用性），现有方案能否通过优化达成。
2. **成熟度**：版本是否稳定，社区和文档，有没有金融或同等级别场景的生产案例，已知缺陷。
3. **可靠性与一致性**：故障时的行为（数据是否可能丢失、重复、乱序），与现有事务和幂等机制是否兼容。
4. **可运维性**：监控、告警、排障工具，团队是否有人能处理线上故障，是否有厂商或社区支持。
5. **合规与安全**：数据安全、审计、许可证、监管要求。
6. **迁移与回滚成本**：能否并行运行、灰度、随时切回。

落地方式：先做 PoC、压测和故障演练；从非核心或边缘链路试点；核心链路小流量灰度，配套对账和监控；形成决策记录，并设定明确的回退条件。

### 12. 手撕算法：括号合法性判断，并改成生成 n 对括号的所有组合

**参考答案**

**第一问：判断括号字符串是否合法**（假设只含 `()[]{}`）

思路：用栈。遇到左括号就把对应的右括号入栈；遇到右括号就检查是否和栈顶匹配；结束时栈必须为空。时间 O(n)，空间 O(n)。

```java
public boolean isValid(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        switch (c) {
            case '(': stack.push(')'); break;
            case '[': stack.push(']'); break;
            case '{': stack.push('}'); break;
            default:
                if (stack.isEmpty() || stack.pop() != c) {
                    return false;
                }
        }
    }
    return stack.isEmpty();
}
```

边界：空串视为合法；奇数长度可以直接返回 false；若字符串里还有其它字符，需要先和面试官约定是忽略还是非法。

**第二问：生成 n 对括号的所有合法组合**

思路：回溯。每一步可以放左括号（已放左括号数小于 n），或放右括号（已放右括号数小于已放左括号数），保证任何前缀都合法。结果数量是卡特兰数 \(C_n = \frac{1}{n+1}\binom{2n}{n}\)，时间复杂度约为 \(O\!\left(\frac{4^n}{\sqrt{n}}\right)\)，递归深度和额外空间 O(n)。

```java
public List<String> generateParenthesis(int n) {
    List<String> res = new ArrayList<>();
    backtrack(res, new StringBuilder(), 0, 0, n);
    return res;
}

private void backtrack(List<String> res, StringBuilder sb, int open, int close, int n) {
    if (sb.length() == 2 * n) {
        res.add(sb.toString());
        return;
    }
    if (open < n) {
        sb.append('(');
        backtrack(res, sb, open + 1, close, n);
        sb.deleteCharAt(sb.length() - 1);
    }
    if (close < open) {
        sb.append(')');
        backtrack(res, sb, open, close + 1, n);
        sb.deleteCharAt(sb.length() - 1);
    }
}
```

回溯时别忘了撤销选择（`deleteCharAt`）；`n = 0` 时返回包含一个空串的列表，是否符合预期要和面试官确认。

HR 面的自我介绍更偏"人"，1 到 2 分钟：

1. 基本信息：年限、技术方向、最近的工作内容。
2. 一两个最能代表你的成果，用一句话讲清楚做了什么、产生了什么价值。
3. 性格与协作方式：责任心、沟通、对稳定性的重视（支付岗位很看重）。
4. 加入意愿：为什么对这家公司和这个方向有兴趣。

语速平稳，不要重复技术面已经讲过的细节。

### 2. 为什么看 XTransfer，对跨境支付业务怎么看

**答题思路**

1. **为什么看这家公司**：基于你真实了解到的信息，例如公司做跨境 B2B 支付和外贸金融服务，业务贴近真实的企业客户场景；技术上涉及多币种、多渠道、合规与风控，有深度。不要编造你不了解的细节，事前读官网和公开资料。
2. **对业务的理解**：跨境支付的价值在于解决跨境收付款的效率、成本和合规问题；难点在于链路长、对接渠道多、各国监管差异、汇率风险、对账与资金安全。
3. **与自己的匹配**：你的支付、对账、幂等、资损防控经验如何对应；你希望在这里深入的方向。
4. **收尾**：表达愿意在复杂业务中长期成长的态度。

### 3. 上家为什么走

**答题思路**

1. 原则：**真实、正向、不抱怨前公司或前同事**。
2. 结构：先说客观原因（业务调整、团队变化、成长到瓶颈等，只说真实的），再说你的思考——想在什么方向有更大空间，这家公司恰好能提供。
3. 表达要把"离开"转成"选择"：因为想做更深入的支付业务，所以选择新的机会。
4. 如果有空档期或被动离职，如实简要说明，并讲清这段时间的收获，不要回避。
5. 避免：薪资不满、与领导不合、说前公司坏话。

### 4. 你觉得自己做支付后端最拿得出手的一点是什么

**答题思路**

1. 先给**一个**核心优势，不要罗列一堆，例如：对资金安全和一致性的敏感（幂等、状态机、对账、资损防控）。
2. 用一个真实案例证明：遇到什么问题、你怎么设计和推动、结果如何（指标或事故减少）。
3. 点出这个能力和岗位的关联：在跨境支付里，渠道多、链路长，这种能力能直接降低风险。
4. 补一句持续改进的态度，显得踏实而不自夸。

### 5. 期望薪资和底线

**答题思路**

1. 先了解自己：市场行情、当前薪资结构、对总包的预期，提前做功课。
2. 回答方式：给出一个**合理范围**而不是死数字，并表达看重综合因素（业务、成长、团队、总包结构）；底线按你自己的真实情况说，不要夸大当前薪资。
3. 可以先反问岗位级别和薪资结构，再给出范围。
4. 表达灵活但有原则：愿意根据面试表现和岗位职责沟通，不要一上来就说"没有底线"或报一个过高的数字。
5. 注意：具体数字按你自己的实际情况定，这里不预设。

### 6. 能接受加班和偶发资损应急复盘吗

**答题思路**

1. **态度明确**：支付业务对稳定性要求高，偶发的线上问题需要及时响应，这是岗位性质，能够理解并接受。
2. **区分常态与应急**：日常通过合理排期、自动化和监控减少不必要的加班；突发故障时愿意优先处理。
3. **复盘的价值**：把资损应急看作改进机会，重点是还原时间线、找根因、补监控和预案，而不是追责，也愿意主动推动复盘落地。
4. **展示经验**（如有真实经历）：处理过的线上问题、响应流程、事后改进。
5. 可以顺势了解团队的值班机制、补偿方式，体现成熟度，但不要显得在讨价还价。

### 7. 后面职业规划是往架构走还是往小团队负责人走

**答题思路**

1. **先给方向**：基于你真实的倾向，选一个主方向，也说明另一方向的基础（技术深度和影响力是两者共同的根基）。
2. **短期（1 到 2 年）**：先把支付核心领域做深，成为清结算、渠道、风控或稳定性某一块的骨干，具备独立主导复杂需求的能力。
3. **中期**：如果偏架构，负责跨系统方案设计和技术选型、稳定性体系；如果偏管理，带小团队、做任务拆解与进度质量把控，培养新人。
4. **与公司结合**：说明这个方向在这家公司能得到什么机会，愿意按团队需要承担责任。
5. 避免：说得太空、频繁变化的目标，或与岗位完全无关的规划。
