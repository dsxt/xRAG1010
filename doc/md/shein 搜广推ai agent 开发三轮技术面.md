## 一面

### 1. 请做一个自我介绍

**答题思路**

控制在 1.5 到 2 分钟，按"身份 → 核心经历 → 与岗位的匹配点 → 求职动机"来讲：

1. 一句话说明年限、技术栈和主要方向（后端、搜推或 Agent）。
2. 挑 1 到 2 个最相关的项目，每个按"业务问题、你负责的部分、关键技术手段、结果"讲，结果用你真实的指标。
3. 点明与搜广推加 Agent 的交集：既碰过搜索、推荐、广告链路或高并发中间件，也做过 LLM 应用、工具调用、RAG 之类的落地。
4. 收尾说想来做这个方向的原因，并把话题引向你最想被追问的项目。

不要背简历，也不要罗列所有技术名词。

### 2. 讲一个你最近做的搜广推或 AI Agent 相关项目，你在里面负责哪块

**答题思路**

用 STAR 结构，控制在 3 分钟内，并预留被深挖的点：

1. **背景与目标**：解决什么业务问题，核心指标是什么（转化、点击、成功率、延迟、成本）。
2. **整体架构**：用一两句话画出链路，例如"请求 → 路由 → 召回/工具 → 排序/生成 → 返回"，说明数据流和依赖的中间件。
3. **你的职责边界**：明确哪些是你独立设计和实现的，哪些是协作的，不要把团队成果都说成自己的。
4. **难点与取舍**：挑 1 到 2 个最难的点（如延迟、一致性、效果评估、工具稳定性），讲备选方案、为什么选当前方案、结果如何。
5. **结果与复盘**：用真实数据说明收益，再说一个遗留问题或下一步优化。

准备好后续追问：为什么这样选型、线上出过什么问题、怎么评估效果。没有的数字宁可不说，也不要编造。

### 3. Redis 在搜广推场景里一般放什么数据，比如热门商品榜、用户短期兴趣特征怎么存

**参考答案**

Redis 适合放"读多、时效性强、可重建"的数据，按访问模式选数据结构。

- **热门商品榜**：用 ZSET，`ZINCRBY` 累加热度，`ZREVRANGE` 取 Top N。按时间窗口（如分钟或小时）分桶，查询时用 `ZUNIONSTORE` 合并最近几个桶，实现滑动窗口；也可以由 Flink 离线算好后整体覆盖写入，避免在线热点写。
- **用户短期兴趣特征**：key 形如 `feat:{uid}`。字段较多时用 Hash，整体读取时用序列化后的 String；最近点击序列用 List 配合 `LTRIM` 保留固定长度，或用 ZSET（score 为时间戳）按时间截断。统一设置 TTL。
- **其他**：召回结果缓存、曝光去重（Set 或 Bloom Filter）、频控计数器。

注意点：

- TTL 加随机抖动，防止同一时间大批 key 过期造成雪崩。
- 控制 value 大小，避免大 key。
- 热榜这种热 key 可加本地缓存（如 Caffeine），或做 key 分片。
- Redis 只是特征的缓存层，源数据在特征平台或存储里，要有回源与重建能力。

### 4. Redis 缓存和 MySQL 主数据不一致怎么处理，先删缓存还是先更新库，为什么

**参考答案**

推荐 Cache Aside：**先更新数据库，再删除缓存**，并加上删除失败的重试兜底。

原因：

- **先删缓存再更新库**：删完缓存后，若有并发读请求读到库里的旧值并回填缓存，随后写请求才更新库，缓存就会长期保留旧值，且没有后续动作去修正，脏数据窗口大。
- **先更新库再删缓存**：只有"读请求在写库前读到旧值，并在写请求删缓存之后才回填"这种较罕见的时序才会出现脏数据，因为读通常比写快得多，概率很低。

兜底手段：

1. 删除缓存失败时，通过 MQ 重试，或订阅 binlog（如 Canal）异步删除缓存，保证最终删除成功。
2. 所有缓存设置 TTL，作为最后的自愈手段。
3. 对强一致要求高的场景，可用延迟双删（更新库后，延迟一段时间再删一次），或直接读主库、不走缓存。

要强调：这个方案保证的是最终一致，不是强一致。搜广推特征大多能接受秒级不一致，而资金、库存扣减这类数据，应以数据库为准。

### 5. Kafka 在用户行为埋点到实时特征更新这条链路里怎么用，怎么保证不丢不重

**参考答案**

链路：客户端埋点 → 采集网关 → Kafka → Flink 或消费服务计算实时特征 → 写入 Redis 或特征存储。

**用法**：

- 以 `user_id` 作为消息 key，同一用户的行为进入同一分区，保证用户维度有序，便于做序列和窗口特征。
- 分区数按目标吞吐和消费者并行度规划。

**不丢**：

- 生产端：`acks=all`、`retries` 开启、`enable.idempotence=true`。
- Broker 端：副本数不少于 3，`min.insync.replicas>=2`，关闭 `unclean.leader.election`。
- 消费端：关闭自动提交，**处理成功后再提交 offset**。

**不重**：

Kafka 端到端的 exactly-once 代价较高，工程上通常是"至少一次 + 幂等处理"：

- 每条事件带全局唯一 `event_id`，下游用它去重（如 Redis `SETNX` 加过期时间）。
- 特征更新尽量设计成幂等：用"覆盖写、带版本号或时间戳的 CAS"，而不是无条件的累加。
- 如果链路是"读 Kafka → 处理 → 写 Kafka"，可用 Kafka 事务；Flink 则用 checkpoint 配合支持两阶段提交的 sink。

### 6. Elasticsearch 做商品搜索时，倒排索引怎么建，中文分词和拼音搜索怎么搞

**参考答案**

**倒排索引**：文本字段（`text` 类型）写入时先经过分析器：char filter → tokenizer → token filter，切成词项（term）。倒排表记录 `term → posting list`（文档 ID，可含词频、位置），查询时对 query 做同样的分词，再按 term 找文档并算分（默认 BM25）。`keyword` 字段不分词，用于过滤、聚合、排序。

**中文分词**：

- 使用 IK 分词器：索引时用 `ik_max_word`（切得细，提高召回），搜索时用 `ik_smart`（粗粒度，提高精度）。
- 维护自定义词典：品牌词、款式词、新词热词，以及同义词（如"连衣裙/裙子"）和停用词。

**拼音搜索**：

- 使用 pinyin 插件，用 multi-fields 给标题再建一个子字段，如 `title.pinyin`，配置全拼和首字母。
- 查询时用 `multi_match` 同时查 `title`、`title.pinyin`，并给原字段更高权重。
- 输入联想可用 `completion suggester`，或 `edge_ngram`。

注意：

- 修改分词词典或分析器后，已有数据不会自动重新分词，需要 reindex 或 `update_by_query`。
- 索引分词器与搜索分词器要有明确的设计，避免召回不到。

### 7. MySQL 联合索引最左匹配原则，举个搜广推里按用户 id + 时间范围查行为的例子

**参考答案**

联合索引 `(a, b, c)` 的 B+ 树按 a、b、c 依次排序，所以查询要能"从最左列开始连续使用"索引，才能充分利用它。

例子：行为表建联合索引 `idx_user_time (user_id, event_time)`。

```sql
-- 走索引：user_id 等值定位，再在其内部按 event_time 范围扫描
SELECT * FROM user_behavior
WHERE user_id = 1001
  AND event_time BETWEEN '2026-11-01' AND '2026-11-07'
ORDER BY event_time DESC
LIMIT 20;

-- 不能高效使用该索引：缺少最左列 user_id
SELECT * FROM user_behavior WHERE event_time BETWEEN '2026-11-01' AND '2026-11-07';
```

要点：

- **等值列放前，范围列放后**。遇到范围条件后，其后的列不能再用来继续定位（如 `(user_id, event_time, event_type)`，`event_type` 在时间范围之后只能靠索引条件下推过滤，不能缩小扫描区间）。
- `ORDER BY event_time` 与索引顺序一致时，可以避免 filesort。
- `WHERE` 里条件的书写顺序无关紧要，优化器会重排，关键是索引列是否被用到。
- 用 `EXPLAIN` 验证实际使用的索引和扫描行数。

### 8. 线程池核心参数，IO 密集型的 Agent 服务里你一般怎么配，为什么这么配

**参考答案**

`ThreadPoolExecutor` 七个参数：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`。

执行流程：线程数小于核心数则新建线程；达到核心数后任务进队列；**队列满了**才扩到最大线程数；仍然满则触发拒绝策略。

IO 密集型的配法：线程大部分时间在等待网络（调 LLM、调工具、查库），所以线程数应明显大于 CPU 核数。经验公式：`N_cpu × (1 + 等待时间 / 计算时间)`，起步可取 `2×N_cpu` 左右，之后压测并结合下游承载能力调整。

实践要点：

- **使用有界队列**，不用 `Executors` 默认的无界队列，否则会堆积任务造成 OOM，且 `maximumPoolSize` 永远不会生效。
- 拒绝策略不要简单丢弃，可用 `CallerRunsPolicy` 形成背压，或自定义为"快速失败 + 降级返回"。
- 按下游隔离线程池（舱壁模式）：LLM 调用、各类工具各用独立线程池，避免某个慢下游拖垮全部请求。
- 线程命名并监控活跃线程数、队列长度、拒绝次数。
- 也可以考虑异步非阻塞或 JDK 21 的虚拟线程来承载大量 IO 等待。

### 9. Spring 的 Bean 生命周期和循环依赖解决思路

**参考答案**

**Bean 生命周期（单例）**：

1. 实例化（反射创建对象）
2. 属性填充（依赖注入）
3. Aware 回调（`BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware`）
4. `BeanPostProcessor.postProcessBeforeInitialization`（`@PostConstruct` 在此阶段处理）
5. 初始化：`InitializingBean.afterPropertiesSet`，再执行自定义 `init-method`
6. `BeanPostProcessor.postProcessAfterInitialization`（AOP 代理通常在此生成）
7. 使用
8. 销毁：`@PreDestroy`、`DisposableBean.destroy`、自定义 `destroy-method`

**循环依赖**：Spring 通过**三级缓存**解决单例 Bean 的 setter 或字段注入的循环依赖：

- 一级 `singletonObjects`：成品 Bean。
- 二级 `earlySingletonObjects`：提前暴露的早期引用。
- 三级 `singletonFactories`：`ObjectFactory`，用于在需要时生成早期引用。

流程：A 实例化后先把工厂放入三级缓存，再填充属性时去创建 B；B 需要 A 时，从三级缓存拿到工厂得到 A 的早期引用（需要 AOP 时这里会提前创建代理），放入二级缓存，B 完成后 A 继续完成。

三级缓存的关键价值：在存在 AOP 时，保证注入的是代理对象，且不用在实例化阶段就创建代理。

局限：

- **构造器注入**的循环依赖无法解决（对象还没创建出来），可用 `@Lazy` 打破。
- 原型作用域不支持。
- Spring Boot 2.6 起默认禁止循环依赖，应优先通过重构设计来消除。

### 10. 用户搜连衣裙，Agent 要调搜索召回、库存校验、个性化排序三个工具，怎么设计超时、降级和重试

**参考答案**

核心思路：**整体给一个延迟预算，每个工具有独立的超时、熔断和降级方案，重试只用于幂等的读请求。**

1. **超时**：请求入口设置总 deadline（如搜索场景的整体时限），向下传递并扣除已用时间；每个工具再设自己的超时，且不超过剩余预算。能并行的并行（例如库存校验可以和一部分排序特征获取并行）。
2. **重试**：仅对幂等读操作，且只重试超时、连接失败、5xx 这类可恢复错误。最多 1 到 2 次，使用指数退避加抖动，并受总预算约束；设置"重试预算"（重试占总请求比例上限），防止重试风暴。4xx 参数错误不重试。
3. **熔断与隔离**：用 Resilience4j 或 Sentinel，按错误率和慢调用比例熔断；每个工具使用独立线程池或信号量隔离。
4. **降级**：
   - 搜索召回失败：退回缓存的热门或类目召回，或最基础的关键词检索。
   - 库存校验超时：用缓存库存做弱过滤，把"强校验"推迟到加购或下单环节。
   - 个性化排序失败：回退到默认排序（销量、热度、召回分）。
5. **Agent 层配合**：工具返回结构化结果（含 `retryable`、`degraded` 标记），由编排层而不是让 LLM 自己无限重试；降级时在回答里不做过度承诺（如"库存紧张"）。
6. 全链路带 trace，记录各工具耗时、降级率，便于调参。

### 11. 你用 LLM 做过的 Agent 里，Prompt 怎么写，CoT 和 ReAct 分别在什么场景用

**参考答案**

**Prompt 的写法**：结构化、可测试、可版本化。通常包含：

- 角色与目标；
- 约束与边界（不能做什么、不确定时怎么办）；
- 可用工具及其说明（名称、用途、参数 schema）；
- 输出格式（尽量用 JSON schema 约束）；
- 少量示例（few-shot），覆盖典型和边界情况。

system 与 user 内容分离；Prompt 放进版本管理，每次修改用评测集做回归。

**CoT**（Chain-of-Thought）：让模型逐步推理再给答案，适合**不需要外部信息、靠推理即可完成**的任务，如规则判断、多步计算、意图拆解。

**ReAct**：Thought → Action → Observation 循环，边推理边调用工具，适合**需要外部信息或实时数据、路径不确定**的任务，如查库存、搜索、多步检索。

取舍：

- ReAct 多轮调用，延迟和成本较高，要限制最大步数。
- 流程固定的任务，更适合 workflow 或 Plan-and-Execute，稳定且便宜。
- 现在的推理模型已内置推理能力，不一定要在 prompt 里写"一步步思考"；也不要把完整思维链直接暴露给用户。

### 12. 大模型返回的工具调用参数偶尔不合法，怎么在工程层兜底

**参考答案**

不信任模型输出，分层防御：

1. **事前约束**：用 JSON Schema 描述参数，使用厂商的 strict 或结构化输出模式（受约束解码）；schema 里写清类型、枚举、范围、必填项；参数说明写具体并给示例。
2. **事中校验**：服务端用 Pydantic 或 JSON Schema 校验器严格校验类型、必填、枚举、取值范围。
3. **自动修复**：对确定性问题做轻量修复，比如去掉 markdown 代码围栏、补全尾逗号、字符串转数字。
4. **反馈重试**：把校验错误作为 observation 回传模型，让它修正后重新调用，限制最多 N 次，避免死循环。
5. **兜底降级**：多次失败后使用规则或默认参数，或追问用户补充缺失信息，或走无工具的保守回答。
6. **安全**：参数一律当不可信输入，做白名单、权限校验、注入防护（SQL、路径、SSRF）；写操作和高危工具要二次确认。
7. **监控**：统计非法参数率，按工具和模型版本聚合，反向优化 schema、prompt 和模型选择。

### 13. Linux 线上 Agent 服务 CPU 飙到 90% 你怎么排查

**参考答案**

先止血再定位：

1. `top` 找到高 CPU 进程；`top -Hp <pid>` 找到最耗 CPU 的线程。
2. 把线程 ID 转成 16 进制（`printf '%x'`），用 `jstack <pid>` 找到对应 `nid` 的栈，看它在做什么。也可用 Arthas 的 `thread -n 3`，或用 async-profiler 生成火焰图。
3. 判断是业务线程还是 GC 线程：`jstat -gcutil <pid>` 看 GC 频率。频繁 Full GC 多半是内存问题（大对象、泄漏），CPU 高只是表象。
4. 用 `vmstat`、`pidstat -w` 看上下文切换是否过多（线程数太大或锁竞争）。
5. 结合监控看是否有流量突增、最近是否发布过变更。

Agent 服务常见原因：

- 死循环或无限工具调用循环（没有步数上限）；
- 正则回溯；
- 大 JSON 的序列化与反序列化、超长上下文拼接和 token 计算；
- 日志输出过多；
- 线程池配置过大造成频繁切换。

处置：限流、回滚、扩容先稳住，再修复根因（加最大步数、拆大对象、优化序列化），并补上告警和压测。

### 14. 手撕环节取消，改为讲一个你写过的最复杂的 SQL 或 ES DSL

**答题思路**

选真实写过、能讲出取舍的一个，按以下顺序讲：

1. **业务背景**：这条查询服务于什么功能，数据量级和延迟要求。
2. **复杂在哪**：多表关联、窗口函数、分组聚合、多条件过滤，或 ES 里 `bool` 查询、`function_score`、聚合的组合。
3. **关键写法**：讲核心结构，不要照念整段代码。
4. **调优过程**：用 `EXPLAIN` 或 `profile` 看瓶颈，如何改索引、改写查询（如延迟关联、拆分子查询、把过滤放进 `filter` 以利用缓存且不参与算分）。
5. **结果**：优化前后的耗时变化，用真实数据。

ES DSL 的常见结构（示意，用来组织思路，不是标准答案）：

```json
{
  "query": {
    "function_score": {
      "query": {
```

## 二面

### 1. 请做一个自我介绍

**答题思路**

二面面试官通常已看过一面反馈，自我介绍要更偏"技术深度"：

1. 开场一句话：年限、方向、擅长的技术。
2. 重点放在与 Agent 架构、搜广推链路相关的 1 到 2 个项目，说明你的决策点（选型、取舍、踩坑），而不是只讲做了什么。
3. 突出可量化的成果和线上问题处理经验。
4. 最后把话题引到你想深聊的部分，如 Agent 编排、工具层或评测体系。

控制在 2 分钟左右，避免重复一面已经讲过的内容。

### 2. 深挖你项目里的 Agent 架构：Router、Planner、Tool Executor 怎么拆，状态怎么流转

**答题思路**

先画出整体链路，再按模块讲职责、接口和你的取舍，用自己项目的真实情况回答。可组织成下面的框架：

1. **Router**：做意图识别与分流，决定走哪条链路、哪个子 Agent，或直接回答。实现可以是规则、小模型分类，或 LLM 分类，通常"规则兜底 + 模型"。讲清为什么要拆，以及误路由怎么兜底（置信度低时走通用链路或追问）。
2. **Planner**：把任务拆成步骤，输出结构化计划（步骤、依赖、所需工具）。可以是 ReAct 式即时规划，也可以是 Plan-and-Execute。说明何时允许重规划，计划如何校验。
3. **Tool Executor**：只负责执行，不做决策。包含参数校验、鉴权、超时重试熔断、并发执行、幂等、结果标准化与裁剪、审计日志。
4. **状态流转**：把状态抽象成一个 State 对象（session_id、消息历史、当前计划、已完成步骤、工具结果、剩余预算），用状态机或图来驱动；每一步落盘 checkpoint（Redis 或 MySQL），支持失败恢复和断点续跑。
   - 流转：Router → Planner → Executor → Observation → 判断（继续、重规划、结束、转人工）→ 生成回答。
5. **护栏**：最大步数、token 预算、总超时、重复调用检测、终止条件。

准备好回答：为什么这样拆、状态存在哪里、失败如何恢复、哪个环节最不稳定。不要编造没做过的模块，没做过的就说明是设计思路。

### 3. Multi-Agent 协作时，子 Agent 之间结果怎么汇合，冲突怎么解

**参考答案**

常见模式是 **Orchestrator-Worker**：主 Agent 拆任务并分发，子 Agent 在**独立上下文**中执行，只回传结构化结果（结论、证据来源、置信度、状态），由主 Agent 或专门的 Aggregator 汇合。

**汇合方式**按任务而定：

- 并集去重（如多路检索结果）；
- 投票或加权（多个判断类子 Agent）；
- 交给 LLM 综合生成最终答案，要求其基于子结果、不得臆造。

**冲突处理**：

1. **权威来源优先**：事实类以权威系统为准，例如库存以库存服务为准，价格以价格中心为准，而不是模型的推断。
2. **时间戳优先**：同一事实取最新的数据。
3. **证据打分**：根据证据来源、置信度排序。
4. **二次核实**：无法裁决时，再调工具验证一次。
5. **如实披露**：仍不确定时，在回答里说明不确定性，或转人工。

工程上还要注意：子 Agent 设置超时，超时就用部分结果降级；子 Agent 之间不共享完整上下文，避免互相污染和 token 膨胀；全链路用同一个 trace_id，便于定位是哪个子 Agent 出错。

### 4. RAG 在搜广推里怎么落：商品知识库、规则文档、运营话术分别怎么切分和检索

**参考答案**

三类数据特点不同，切分与检索策略也要不同。通用方案是：**混合检索（BM25 + 向量）+ 元数据过滤 + rerank**。

1. **商品知识库**：商品多是结构化属性（类目、材质、尺码、价格、库存）加描述文本。
   - 以商品或 SKU 为基本单位，把属性转为自然语言描述，并把类目、价格、库存状态等放进元数据，用于过滤。
   - 价格、库存这类强时效字段不要靠向量检索，应通过结构化查询或实时接口获取。
   - 长描述按段落或语义切分。
2. **规则文档**（退换货、活动规则、合规条款）：
   - 按标题层级或条款结构切分，保证每个 chunk 语义完整；chunk 大小一般几百 token，可保留少量重叠。
   - 元数据带上章节标题、版本、生效与失效时间、适用地区。
   - 检索命中子块后可带出父级章节（parent-child），保证上下文完整。
3. **运营话术**：
   - 本身短，按条目独立成 chunk，不要拼接。
   - 打标签：场景、品类、语气、是否有禁用词，检索时按标签过滤再向量匹配。

通用要点：增量更新与版本管理，过期内容及时下线；回答要带引用来源；用评测集（召回率、答案正确率）持续调整 chunk 策略，而不是凭感觉定数字。

### 5. 为什么向量检索之外还要接 BM25，混排分数怎么融合

**参考答案**

两者互补：

- **向量检索**擅长语义相似（"显瘦的裙子"能找到"A 字收腰连衣裙"），但对精确匹配较弱，例如型号、SKU、品牌名、专有名词、数字。
- **BM25** 擅长词项精确匹配，可解释，对长尾和精确词表现稳定，但不理解同义和语义。

所以混合检索通常比单一路径召回更全。

**分数融合**：两种分数尺度不同，不能直接相加。

1. **RRF（Reciprocal Rank Fusion）**：只用排名，`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60。不依赖分数分布，实现简单，鲁棒性好。
2. **归一化加权**：先对两路分数做 min-max 或 z-score 归一化，再 `α·dense + (1-α)·bm25`，α 用离线评测集调。
3. **重排**：融合后取 Top-N，再用 cross-encoder 或 rerank 模型精排，这通常是提升效果最明显的一步。

权重和 k 值要在评测集上用 Recall@K、nDCG 等指标验证，不同业务最优值不同。ES 新版本也原生支持 kNN 与关键词混合检索及 RRF。

### 6. Agent 调用 ES、Redis、推荐 API 这些工具时，鉴权、限流、审计日志怎么统一收口

**参考答案**

做一个**统一的工具网关**（可基于 MCP 或自建），Agent 不直连任何后端，所有调用都经过它。

- **鉴权**：
  - 同时校验"Agent 身份"和"终端用户身份"（身份透传，on-behalf-of），按最小权限原则给每个工具分配 scope。
  - 使用短期令牌；写操作、删除等高危操作走白名单，必要时需要二次确认。
  - 工具的数据范围按用户权限过滤，防止越权查询。
- **限流**：
  - 多维度：用户、租户、Agent、工具、下游服务，使用令牌桶或滑动窗口（如 Sentinel）。
  - 并发隔离、超时、熔断也在网关统一配置，保护 ES、Redis 等下游。
- **审计日志**：
  - 每次调用记录 trace_id、session_id、用户、工具名、参数（敏感字段脱敏）、结果摘要、耗时、状态码，异步写 Kafka 再落存储。
  - 支持按会话回放，用于问题排查和合规审计。
- **其他**：统一做参数校验、结果裁剪（防止返回过大撑爆上下文）、错误码标准化。

好处是策略集中、改动一处全局生效，也方便做评测和成本统计。

### 7. MySQL 深分页在用户行为查询里慢怎么优化，覆盖索引和游标分页讲一下

**参考答案**

`LIMIT 100000, 20` 慢，是因为 MySQL 要扫描并丢弃前 100000 行，且每行可能还要回表。

**优化一：覆盖索引 + 延迟关联**。先在二级索引上只查主键（索引覆盖，不回表），再按主键回表取需要的 20 行：

```sql
SELECT t.*
FROM user_behavior t
JOIN (
    SELECT id FROM user_behavior
    WHERE user_id = 1001
    ORDER BY event_time DESC, id DESC
    LIMIT 100000, 20
) x ON t.id = x.id;
```

**优化二：游标分页（keyset）**。记住上一页最后一条的排序键，下一页直接从该位置往后查，不扫描前面的行：

```sql
SELECT id, event_time, item_id
FROM user_behavior
WHERE user_id = 1001
  AND (event_time < :last_time OR (event_time = :last_time AND id < :last_id))
ORDER BY event_time DESC, id DESC
LIMIT 20;
```

配合索引 `(user_id, event_time, id)`，复杂度不再随页数增长。注意排序键必须唯一（加上主键），否则会重复或漏数据。

局限：游标分页不能随机跳页，适合"下一页、无限滚动"。

其他手段：产品上限制最大翻页深度；历史冷数据归档，或迁到 ES 等更适合检索的存储。

### 8. Kafka 消息积压了，消费者扩容有哪些坑，分区数能随便加吗

**参考答案**

**先定位原因**：是消费逻辑变慢（下游慢、GC）、流量突增，还是频繁 rebalance 导致消费停滞。

**扩容的坑**：

- **并行度上限是分区数**。同一消费组内，一个分区只会被一个消费者消费，消费者数量超过分区数，多出来的是空闲的。
- 扩容消费者会触发 **rebalance**，期间消费暂停；可使用 cooperative sticky 分配策略降低影响。
- 消费者增多会增加下游（数据库、外部接口）压力，瓶颈可能只是转移。
- 并行消费要保证**幂等**，同时顺序性要求高的业务要注意分区内有序。
- 处理时间超过 `max.poll.interval.ms` 会被踢出组，造成 rebalance 风暴；`max.poll.records` 不宜过大。

**分区数不能随便加**：

- 分区只能增加，不能减少。
- 增加分区后，按 key 哈希取模的映射会变化，**同一个 key 的新老消息可能落在不同分区**，破坏 key 维度的顺序性。
- 已有数据不会重新分布。

**应急做法**：新建一个分区数更多的临时 topic，写一个转发程序把积压消息搬过去，再用大量消费者并行消费；同时优化单条处理逻辑（批量处理、异步化、减少远程调用）。事后复盘容量规划，设置积压告警。

### 9. RocketMQ 事务消息在广告投放扣费场景里怎么用

**参考答案**

目标：保证"本地扣费事务"与"通知下游的消息"**最终一致**，避免出现"扣了费但消息没发"或"消息发了但没扣费"。

流程：

1. 生产者先发送**半消息**（half message）到 Broker，此时对消费者不可见。
2. 执行本地事务：例如扣减广告主预算并写入扣费流水（同一个数据库事务）。
3. 根据本地事务结果向 Broker 提交 `COMMIT`（消息变为可消费）或 `ROLLBACK`（丢弃）。
4. 若 Broker 迟迟没收到结果（如服务宕机），会**回查**生产者的 `checkLocalTransaction`，此时根据扣费流水表判断事务状态并返回。
5. 下游消费者收到消息后，更新报表、结算、预算统计等。

关键点：

- **消费端必须幂等**：以扣费流水号做唯一键去重，因为消息至少投递一次。消费失败有重试，最终进入死信队列并告警。
- **回查要可行**：本地事务状态必须能被查询（流水表加唯一约束）。
- 它保证的是最终一致，不是强一致，也不是传统意义的两阶段提交；扣费核心数据仍以数据库流水为准，并配合对账兜底。
- 预算扣减要防止并发超扣（条件更新 `WHERE balance >= ?` 或乐观锁）。

### 10. 广告主说自动投放 Agent 把预算花在转化差的词上，你怎么定位是召回问题、排序问题还是 Agent 决策问题

**参考答案**

思路：**先用数据拆漏斗，再分层控制变量，逐段排除。**

1. **确认现象**：按词、时间、出价、匹配类型拆分花费、点击、转化和 CVR，与历史版本或人工投放基线对比，确认是个别词还是普遍现象。
2. **召回问题**：看这些词的流量是否来自过宽的匹配或扩词，query 与广告相关性是否低；抽样 query → 广告对，评估相关性。如果流量本身不精准，后面排序再好也救不了。
3. **排序问题**：检查 pCTR、pCVR 预估的**校准性**（预测均值 vs 实际均值、分桶校准曲线、AUC），冷启动词是否预估偏高；转化回传延迟可能造成近期转化被低估或高估；看出价与 eCPM 的计算是否合理。
4. **Agent 决策问题**：回放 Agent 的 trace，看它依据哪些数据调了预算或出价：
   - 是否把小样本噪声当成趋势；
   - 优化目标是点击还是转化；
   - 是否没考虑转化延迟；
   - 是否越过了预算护栏。
5. **控制变量验证**：固定召回和排序，只把 Agent 决策替换为规则策略，对比结果；反过来固定决策，替换召回或排序版本，看差异落在哪一层。离线回放加小流量 A/B 验证。
6. **止血**：给词级预算上限、CPA 约束，转化差的词降价或暂停，把这些护栏做成硬规则，Agent 不可突破。

### 11. Agent 的 Memory 怎么设计，短期上下文和长期用户画像分别存哪，怎么避免上下文污染

**参考答案**

**短期记忆**：当前会话的消息、工作状态（计划、中间结果）。存在 Redis（带 TTL）或会话存储中；受上下文窗口限制，用"滑动窗口 + 历史摘要压缩"控制长度，关键信息固定放在 system 或状态里。

**长期记忆**：
- 结构化画像（尺码、风格偏好、预算区间等）存 MySQL 或特征平台；
- 非结构化的经历与语义记忆（偏好描述、历史对话要点）存向量库；
- 每条记忆带来源、时间戳、置信度。

**写入与读取**：
- 写入走异步管道：由模型抽取候选记忆，经过校验、去重、冲突合并后再入库，不在对话热路径同步写。
- 读取按当前问题检索 Top-K，注入 prompt 时标明来源和时效，不要整库塞入。

**避免污染**：
1. 按 user_id 与 session 严格隔离命名空间，子 Agent 使用独立上下文。
2. 区分"用户明确声明的事实"和"模型推断"，推断低置信、可过期，冲突时以最新的显式声明为准。
3. 工具结果和外部文本视为**不可信数据**，不能未经校验写入长期记忆，防止提示注入被持久化。
4. 记忆有过期与衰减机制；任务切换时清理无关上下文。
5. 提供用户查看与删除的能力，满足合规。

### 12. 评估 Agent 效果你怎么埋点，任务成功率、工具调用准确率、人工抽检怎么结合

**参考答案**

**埋点**：以 trace_id 串起一次请求的完整链路，记录：

- 用户意图与路由结果；
- 计划及每一步；
- 每次工具调用（工具名、参数、返回摘要、耗时、成败）；
- 每次模型调用（模型与 prompt 版本、token、延迟）；
- 最终回答；
- 用户反馈（点赞点踩、追问、转人工）与业务结果（点击、加购、成交）。

**指标**：

- **任务成功率**：端到端是否完成用户目标。可用规则判定、LLM-as-judge、用户行为信号综合。
- **工具调用准确率**：是否选对工具、参数是否正确。对照标注的标准调用轨迹（golden trace）可以自动评测，也可看参数校验失败率、重试率。
- **效率与成本**：步数、延迟（P50、P99）、单次 token 成本。

**三者结合**，分层漏斗：

1. 自动指标覆盖全量流量，做实时监控和告警。
2. LLM judge 评估中等规模样本，评估回答质量和事实一致性。
3. 人工抽检小规模分层抽样（按意图、失败样本、低置信度、新版本），同时用来校准 LLM judge，检查两者一致性。
4. 失败和人工发现的 bad case 回流到离线评测集，每次改 prompt 或模型都跑回归，再配合线上 A/B。

### 13. 模型选型：GPT、Claude、Gemini、开源模型在中文电商场景里你怎么选，成本和延迟怎么权衡、如何切换

**参考答案**

说明：原题末尾 OCR 不清，这里按"成本和延迟怎么权衡、怎么切换"理解。

不凭印象选模型，而是**用自己的评测集说话**：把中文电商的典型任务（商品理解、工具调用、多轮对话、风格话术）在候选模型上跑一遍，对比质量、延迟（首 token 延迟和总耗时）、成本（单价 × 实际 token 用量）、稳定性与限流、合规要求。

**分层路由**：
- 意图分类、改写、信息抽取等简单任务，用小模型或微调后的开源模型，便宜且快。
- 复杂规划、多步推理、关键的工具调用，用能力更强的模型。

**取舍**：
- GPT、Claude、Gemini 等闭源模型通用能力和工具调用通常较稳，但成本高，且要考虑用户数据出境与合规。
- 开源模型（如 Qwen、DeepSeek 等中文表现较好的系列）可私有化、可微调、成本可控，但需要自己做推理部署与运维。

**切换与容灾**：
- 在应用与模型之间加统一的模型网关，屏蔽各家接口差异。
- 配置主备模型，根据超时、错误率、限流触发熔断并自动切换；不同模型的 prompt 要单独适配和评测。
- 新模型走灰度和 A/B；对高频相似请求可做缓存，进一步控制成本。

### 14. 让 Agent 解释为什么这件贵价外套排在搜索第一位，它要调哪些数据，怎么保证回答可溯源、不出现 hallucination

**参考答案**

原则：**解释必须基于排序系统的真实证据，LLM 只负责组织语言，不负责猜测原因。**

**要调用的数据**：
- 当前 query 与用户意图；
- 该商品的召回通道，以及各阶段的分数：文本相关性、pCTR、pCVR、价格带匹配度；
- 业务规则：是否有加权、置顶、活动、广告位；
- 商品属性、库存状态；
- 个性化特征的主要贡献。

这需要排序系统提供 **explain 接口或日志**，并保存请求当时的特征快照（特征会随时间变化，事后重算可能与当时不一致）。

**保证可溯源、不幻觉**：
1. 输出结构化的 `{claim, evidence_id}`，每个结论绑定一条工具返回的证据。
2. 增加校验层：检查每个结论里的因素和数字是否出现在证据中，没有证据就删除。
3. 证据不足时明确回答"无法确定"，而不是编造。
4. 用模板约束解释的结构，LLM 只润色措辞，温度设低。
5. 记录 trace，支持审计回放。

**合规与披露**：如果该商品排第一是因为广告或人工置顶，要如实标注为"推广"；内部策略、模型权重等敏感信息要脱敏，并按权限控制展示的内容。

### 1. 请做一个自我介绍

**答题思路**

三面通常是业务负责人或高级面试官，关注"能不能扛事、判断力、成长性"，自我介绍要偏全局：

1. 一句话概括职业主线和擅长领域。

4. 以对该岗位的期望和能带来的价值收尾。

### 2. 你带过搜广推或 Agent 方向的小团队吗，怎么拆任务和下指标

**答题思路**

用真实经历回答；如果没有正式带过团队，就讲你作为模块负责人协调他人的经历，并如实说明角色，不要夸大。建议结构：

1. **背景与规模**：团队几个人、分工、你的角色。
2. **目标与指标**：业务指标（转化、GMV、点击率）和技术指标（任务成功率、工具调用准确率、P99、单次成本），分层下放到个人或小组。
3. **任务拆解**：按链路或领域拆，例如召回与工具层、编排层、评测与数据、平台与稳定性；明确接口和负责人。
4. **节奏**：先定 MVP 和里程碑，周更同步，设置评审点。
5. **质量与机制**：Code Review、线上值班、复盘、评测门禁。
6. **反思**：做得不好的一次，以及后续如何改进。

### 3. 和算法同学对不齐：他觉得 Agent 该全自主，你觉得得加硬规则兜底，怎么推方案

**答题思路**

先对齐目标，再用数据说话，而不是争论立场。可以按下面的顺序回答：

1. **先确认共同目标**：双方都想要效果和稳定，分歧在于风险控制，理解对方担心的是"规则太死限制泛化"。
2. **按风险分级**：低风险的开放式任务（话术、推荐理由）可以放开让模型自主；涉及资金、价格、库存、预算调整、合规的高风险动作，必须有硬规则、预算上限、人工确认等护栏。这是工程底线。
3. **用实验验证**：离线回放或小流量 A/B，对比"全自主"与"加护栏"的任务成功率、违规率、成本，让数据决定。
4. **让规则可演进**：规则做成可配置、可观测的，记录拦截率；如果某条规则长期拦截很少、模型已能稳定做对，就逐步放松。
5. **明确责任与指标**：共同关注业务效果和事故率，出现线上问题时有清晰的回滚机制。

重点是体现"尊重对方、有原则、用数据推进"。

### 4. 项目排期紧，Agent 评测流水线还没写完，你先上线上实验还是先补评测，为什么

**参考答案**

结论：**先补最小可用的评测，再灰度小流量上线**，而不是完整流水线写完才上线，也不是没有评测就直接上。

理由：Agent 输出是非确定性的，没有评测就没法判断一次改动是变好还是变坏；线上实验结果会难以解释，出问题时回滚也没有依据。

折中做法：

1. 用 1 到 2 天构建**最小评测集**（几十到上百条核心场景用例，含 golden trace）和最关键的几个自动指标（任务成功率、工具调用准确率、违规率），先跑通回归。
2. 同时做好护栏：最大步数、预算上限、降级到传统链路、快速回滚开关。
3. 上线采用影子流量或小比例灰度，配合人工抽检，监控成功率、延迟、成本。
4. 评测流水线的其余部分（自动化 judge、看板、大规模回归）在灰度期间补齐。

例外：涉及资金、合规等高风险动作的功能，评测和护栏不能省，宁可延期。

同时要主动和业务方沟通风险与范围，必要时缩小首版功能范围来保住质量，而不是压缩验证。

### 5. Elasticsearch 索引 mapping 变更、MySQL 加列、Redis 热 key 迁移，这三件在搜广推系统里分别怎么平滑做

**参考答案**

总原则：**兼容性优先、先双写或双读再切换、可回滚、避开高峰。**

**ES mapping 变更**：
- 已存在字段的类型不能直接修改，新增字段可以直接 `PUT _mapping`。
- 需要改类型或分词器时：新建索引 v2（新 mapping），应用侧始终通过**别名（alias）**访问；用 `_reindex` 全量迁移，同时通过双写或消费 Kafka、binlog 追平增量；校验文档数和抽样结果后，原子地切换别名；保留旧索引一段时间以便回滚。

**MySQL 加列**：
- 先确认版本和算法：MySQL 8.0 支持 `ALGORITHM=INSTANT` 加列，几乎不拷贝数据；5.7 用 Online DDL，超大表或需要更强控制时用 gh-ost、pt-online-schema-change 这类影子表方案。
- 留意**元数据锁**：长事务会阻塞 DDL，而 DDL 又会阻塞后续所有查询，执行前先检查并清理长事务，设置锁等待超时。
- 发布顺序：先加列（可空或带默认值）→ 上线兼容新列的代码 → 回填数据 → 再加约束或切换读写。

**Redis 热 key 迁移**：
- 先治理热点：本地缓存（Caffeine）、把 key 拆成多个副本（`key#0..n`）分散读、读写分离。
- 迁移（扩容或迁到独立实例）：Redis Cluster 按 slot 在线迁移，期间通过 `ASK/MOVED` 重定向；先拆分大 key，因为迁移大 key 会阻塞。
- 对热 key 采用双写加灰度切读，旧 key 靠 TTL 自然过期；切换前预热，避免缓存击穿。
- 全程监控 QPS、延迟、命中率。

### 6. 大规模 Agent 服务平台怎么设计，模型推理、工具网关、会话状态、限流分别放哪层

**参考答案**

分层设计，核心原则：**编排层无状态、状态外置、模型和工具各自网关化。**

1. **接入层（API 网关）**：鉴权、租户识别、入口限流，支持 SSE 或 WebSocket 做流式输出。
2. **Agent 编排层**：Router、Planner、执行引擎，无状态，可水平扩展，所有状态从状态层读取。
3. **会话状态层**：Redis 存热状态与会话上下文，MySQL 或对象存储做持久化和 checkpoint，按 session_id 分片；支持中断恢复。
4. **模型网关层**：统一接入第三方 API 和自建推理服务（如 vLLM 这类推理引擎，使用 continuous batching）；负责路由、fallback、重试、缓存、按模型和租户的 RPM/TPM 与并发限流、成本统计。
5. **工具网关层**：工具注册与发现（schema）、鉴权、限流、熔断、超时、审计、结果裁剪；可采用 MCP 协议接入。
6. **知识与记忆层**：向量库、ES、特征存储。
7. **可观测与评测**：trace、指标、日志、评测平台、成本看板。
8. **异步任务**：长任务走消息队列，结果通过轮询或回调返回。

**限流分层放置**：入口按用户或租户限 QPS；模型网关限 token 速率和并发；工具网关按下游承载能力限流。长连接的资源（连接数）要单独评估和限制。

### 7. Function Calling 和 MCP 的区别，什么时候该自己写 MCP Server

**参考答案**

**区别**：两者不在同一层，是互补关系。

- **Function Calling** 是**模型能力和 API 约定**：你把工具的 schema 告诉模型，模型输出"要调用哪个函数、参数是什么"，真正的执行由你的应用完成。不同厂商格式略有差异。
- **MCP（Model Context Protocol）** 是**开放的应用层协议**，标准化了 Host/Client 与 Server 之间如何暴露和发现 tools、resources、prompts（基于 JSON-RPC，支持 stdio、HTTP 等传输）。它解决的是工具集成的 M×N 问题：工具实现一次，可被不同 Agent 框架和客户端复用。

实际流程中，MCP Client 先从 Server 获取工具列表，再通过模型的 Function Calling 让模型选择工具，调用结果通过 MCP 返回。

**什么时候自己写 MCP Server**：
- 工具要被多个 Agent、应用或客户端复用；
- 需要统一的鉴权、审计、限流等治理；
- 希望工具独立部署、独立迭代，与 Agent 解耦；
- 对内部系统（搜索、库存、推荐）提供标准化能力。

**不必写的情况**：只是单个应用内的简单函数，直接用本地 Function Calling 就够，引入 MCP 会增加网络开销和运维成本。

另外要关注安全：使用第三方 MCP Server 要警惕提示注入和过大权限，坚持最小权限与审计。

### 8. Agent 生产环境最怕什么：循环调用、工具副作用、上下文溢出，你分别怎么防

**参考答案**

**循环调用**：
- 设置最大步数、总耗时和 token 或成本预算，超限强制终止并降级。
- 重复检测：连续 N 次相同工具加相同参数，则中止或强制换策略。
- 判断是否有"进展"（新增信息），无进展则退出。

**工具副作用**：
- 读写分离，写操作单独管理，默认最小权限。
- 写操作带**幂等键**，避免重试造成重复执行。
- 采用"预览 / dry-run → 用户或规则确认 → 执行"的流程，高危动作必须人工确认。
- 多步写操作用 Saga 补偿，保留审计日志；禁止模型直接调用不可逆的高危工具。

**上下文溢出**：
- 实时 token 计数，设置阈值。
- 滑窗保留近期消息，对旧消息做摘要压缩。
- 工具结果截断、分页、只返回必要字段；超大结果落到外部存储，上下文里只放引用，需要时再按需读取。
- 关键信息放在 system 或结构化状态中，其他内容通过检索按需注入，而不是全部塞入。

此外要配套监控和告警：步数分布、重复调用率、截断率，并用评测集持续回归这些边界场景。

### 9. 最近半年你学的新东西里，哪一个最可能改搜广推的工程形态，比如 RLHF、多模态、端侧模型随便挑一个讲

**答题思路**

这是开放题，考察学习力和判断力。只讲你真正学过或试过的，不要硬凑名词。建议结构：

1. **选一个方向**，一句话说明它是什么。
2. **它改变了什么**：说明对现有搜广推工程形态的影响。可参考的角度：
   - 多模态：用视觉语言模型理解商品图，和文本统一向量化，支持拍照找同款、图文混合搜索，改变召回和排序的特征来源；
   - 端侧模型：用户短期兴趣在设备上实时推理，降低延迟、保护隐私，减少上传；
   - RLHF 或偏好优化：用用户反馈对齐排序和对话目标，而不仅仅是点击率。
3. **如何落地**：你设想或试过的最小实验、需要的数据与评测方式。
4. **局限与风险**：成本、延迟、数据质量、可解释性。
5. **你自己的实践程度**：如实说明是看论文、跑过 demo，还是在项目里试过。

### 10. 你怎么判断一个 AI 新技术是真有用还是 demo 玩具，举一个你踩过坑的例子

**答题思路**

先给判断框架，再用真实经历举例。

**判断框架**：
1. **有没有明确的业务问题和可量化指标**，而不是为了用技术而用技术。
2. **在真实数据和分布上验证**：用自己的评测集和长尾样本，而不是演示用的精选 case；demo 通常只展示成功案例，要看失败率。
3. **工程可行性**：延迟、成本、稳定性、可观测、可回滚。
4. **和简单基线对比**：规则、传统模型是否已经够用，新技术是否有显著且稳定的提升。
5. **小流量实验**：先 A/B，再扩大。

**踩坑例子**：用你自己的真实经历，按"当时为什么觉得有用 → 上线或试用后暴露的问题 → 如何发现 → 如何止损或改进 → 学到什么"来讲。没有真实案例时，就如实说明你的评估方法，不要编造事故。

### 11. 如果让你从 0 搭 SHEIN 的购物助手 Agent，搜索、推荐、广告三个域的工具怎么编排，首版 MVP 你先做什么

**参考答案**

**架构**：Router 识别意图后走对应链路，三个域各提供标准化工具，由统一工具网关管理。

- **搜索域**：商品搜索与筛选、商品详情、尺码与材质知识库（RAG）、价格库存查询。
- **推荐域**：相似商品、搭配推荐、个性化推荐。
- **广告域**：原则上 Agent **不自主决定投放**，广告仍由现有的广告竞价与排序系统产出，Agent 只负责在结果中融合展示，并清晰标注"广告"、遵守合规。

**典型编排**：
- 找商品："意图与参数抽取 → 搜索召回 → 库存与价格校验 → 个性化重排 → 生成回答（必要时穿插合规的广告位）"。
- 搭配或发现类："推荐工具 → 商品详情补全 → 生成"。
- 确定性高的部分使用固定 workflow，LLM 只负责意图理解、参数抽取和回答生成，复杂场景再引入 ReAct。

**MVP 先做**：
1. 选一个高频、价值明确的场景："自然语言找商品"（搜索 + 筛选 + 库存价格校验）。
2. 工具少而稳（3 到 4 个），先不做多 Agent。
3. 同步搭好**评测集、埋点和降级**：失败时回退到传统搜索，保证不比现状差。
4. 小流量灰度，关注任务成功率、点击与转化、延迟、成本。
5. 稳定后再扩展到推荐与搭配，最后才接入广告域。

### 12. 聊点硬的：你们现在 Agent 链路 P99 多少，成本高在哪，有没有做过 KV cache、批处理或模型蒸馏的优化

**答题思路**

数字必须用你自己系统的真实数据，不能编；没有测过就如实说，并讲你会怎么测。回答可按下面组织：

1. **先拆 P99**：把链路拆成接入、路由、模型首 token、生成时长、各工具调用、重试几段，说明最长的是哪一段，用 trace 数据支撑。
2. **成本高在哪**：
   - 输入 token：冗长的 system prompt、历史对话、检索内容、工具返回冗余；
   - 输出长度；
   - ReAct 循环的轮数；
   - 简单任务也用了强模型；
   - 重试和失败的浪费。
3. **优化手段**（说明你做过哪些、了解到什么程度）：
   - **KV cache 与前缀缓存**：自回归解码里缓存历史 token 的 K、V，避免重复计算，占用显存随序列长度增长；固定的 system prompt 前缀可复用（API 的 prompt caching，自建推理引擎的 prefix caching），降低首 token 延迟和成本。
   - **批处理**：推理引擎的 continuous batching 提高 GPU 吞吐；离线任务用批量接口。
   - **模型蒸馏与小模型**：用强模型产出数据，蒸馏意图分类、改写、抽取等窄任务的小模型；配合模型路由。
   - 其他：上下文压缩、工具结果裁剪、并行工具调用、流式输出改善体感、语义缓存与结果缓存，以及量化、投机解码等推理侧优化。
4. **效果与代价**：优化前后的指标变化，以及对质量的影响如何验证。

**答题思路**

### 2. 为什么看 SHEIN 这边搜广推加 Agent 的岗

**答题思路**

回答要体现"有调研、有匹配、有长期考虑"：

1. **行业与业务**：SHEIN 是出海电商，业务规模大、流量和数据丰富，搜广推与 AI 应用结合的场景真实。
2. **技术匹配**：你的经验正好覆盖搜广推链路的工程能力以及 LLM 或 Agent 的落地，这个岗位能把两者结合起来。
3. **成长空间**：希望在真实的大规模业务中，把 Agent 从 demo 做到可评测、可上线的系统。
4. **个人规划**：与自己的长期方向一致。

不要贬低现公司，不要只说"薪资高"或"公司大"。

### 3. 你现在团队规模和对自己下一步的定位

**答题思路**

1. **团队规模**：如实说明团队人数、分工，以及你负责的部分和汇报关系，不夸大。
2. **当前定位**：你现在在团队中承担什么角色（核心开发、模块负责人等）。
3. **下一步定位**：说明你想往哪个方向发展（如更深入 Agent 工程化与评测、搜广推系统架构），并与这个岗位的职责对应起来。
4. **落点**：说明你期望在新岗位上承担更大范围的技术决策或业务影响，并愿意持续学习。

保持真实、方向清晰，避免"什么都想做"。

### 4. 项目里最尬的一次背锅或返工是什么

**答题思路**

这是考察心态、复盘和责任感，**选一件真实且不致命的事**，不要说"没有"，也不要编造。结构：

1. **事件**：简述背景，客观说明问题所在，不甩锅给他人。
2. **你的责任**：明确自己哪里判断失误或沟通不足。
3. **补救**：怎么止损、推动返工、和相关方沟通。
4. **复盘与改进**：之后建立了什么机制（评审、评测、灰度、检查清单）。
5. **结果**：后来类似问题是否减少。

核心是展现"承认问题 → 快速修复 → 机制化改进"。

### 5. 能接受的业务节奏和出海多时区支持程度

**答题思路**

坦诚、有边界、有方法：

1. **态度**：理解出海业务有时区差，线上问题和跨区域协作需要一定的灵活性，可以接受合理范围内的错峰沟通和值班。
2. **具体说明**：说清你能接受的程度，比如固定的 on-call 轮值、重要发布期间的配合，而不是承诺"随时在线"。
3. **方法**：通过异步文档、清晰的值班和告警机制、自动化减少人为盯守。
4. **确认信息**：反问团队实际的值班安排和协作时段，了解真实情况。

不要夸口"完全没问题"，也不要一上来就拒绝。

### 6. 期望薪资和目前手头 offer 情况

**答题思路**

不要编造具体数字或虚构 offer，按真实情况回答：

1. **期望**：先表达更看重岗位匹配度和成长，再给出基于市场行情和自己能力的合理范围，可以说"希望和岗位级别、市场水平匹配"。如果对方明牌，可以给一个有弹性的区间，而不是单一数字。
2. **offer 情况**：如实说明是否在流程中、各自阶段，不用透露具体公司和金额细节；可以表明这家的优先级和你的决策时间点。
3. **态度**：表达对这个机会的诚意，薪资可根据整体包（薪资结构、绩效、福利）综合沟通。

不要为了压价或抬价虚构信息，诚信比一时的筹码重要。

### 7. 下班不回消息这事儿你怎么看

**答题思路**

要体现边界感和责任心的平衡：

1. **原则**：工作时间内及时响应；下班后有合理的边界，不是所有消息都需要立刻回复。
2. **分级**：线上故障、紧急事故会及时响应并处理，这是工程师的责任；普通事务可以次日处理。
3. **方法**：用 on-call 轮值、告警分级、清晰的升级流程减少无效打扰，让"紧急"的定义明确。
4. **沟通**：提前对齐团队的约定，既保护个人时间，也保证团队的稳定性。

不要说"随时回复"显得没有边界，也不要说"下班一律不回"显得不负责任。

### 8. 有什么反向问我的

**答题思路**

准备 3 到 4 个有质量的问题，围绕岗位和团队，不要问已经公开的信息，也不要一开始就问薪资和加班：

1. **岗位与目标**：这个岗位前半年最重要的目标是什么，怎么衡量成功？
2. **团队与业务**：团队目前的规模和分工，搜广推与 Agent 方向的业务落地到什么阶段？
3. **技术环境**：Agent 的评测、灰度、成本控制目前是怎么做的，最大的技术挑战是什么？
4. **成长与协作**：团队的培养方式、跨时区协作和值班的安排。
5. **流程**：后续的流程和时间安排。

问题要体现你对业务和落地的关注。
