### 1. 自我介绍

**答题思路**

控制在 1～2 分钟，按「现在做什么 → 一个 Agent 项目里你负责的那段 → 和岗位的重合点」讲。

1. 第一句只说年限和现在做的系统类型。年限用自己的，不要顺口改成岗位喜欢的年数。
2. 技术栈按这条链路排：服务端框架、存储和消息队列，然后是你真写过的编排、检索或工具。只调过聊天接口，就说到接口为止。
3. 留一个钩子：谁在用这个 Agent，请求进来后你负责哪一段。架构和难点留给下一问。
4. 收在匹配点：能把模型放进现有服务，并把超时、权限和失败收住。

讲完停住。不要铺框架名词，也不要主动提离职和薪资。

### 2. 项目介绍，重点说你在 AI Agent 项目中承担的角色和技术难点

**答题思路**

用你真实负责的项目，2～3 分钟，按「业务 → 角色 → 一条请求 → 一个难点」讲。

1. 先说谁在用、怎样算做成。用户要的是查对、办成，还是生成一段能用的结果，用一句业务话说完。
2. 角色和同事分开：编排、工具、检索、评测，你占哪一段。没做的部分不要说成自己设计的。
3. 用一条请求把组件串起来：接入、意图或计划、工具或检索、模型、落库。只讲这条链上存在的组件。
4. 难点只留一个你能画出来的取舍，例如状态写在哪、检索怎么更新、写操作失败后会不会做第二次。数字用你能对上的；没有监控就讲现象。
5. 讲完停在这个取舍上，等面试官往下挖。

### 3. Python 和 Java 在 AI Agent 开发中的优劣对比，你们项目为什么这么选

**参考答案**

结论：Agent 的时间主要花在模型、检索和工具这些 IO 上，不花在语言跑分上。Python 的编排和评测生态更靠前；Java 更适合把工具接进已有的企业服务。

Python 改图、改提示、做评测的周转短，LangGraph 以及数据处理、评测脚本都集中在这边。类型约束弱，工具一多，参数 schema 容易悄悄对不上，要靠测试补。GIL 限制的是同一进程里的 CPU 并行；等待模型返回用异步 IO 即可。解析和批量向量如果真吃 CPU，放到独立进程或别的服务，不要指望多线程绕过 GIL。

Java 适合工具本身就是订单、权限、事务这些存量服务的情况。超时、熔断、发布和已有监控可以直接接上。Spring AI、LangChain4j 能做模型调用、工具和检索，但新的编排能力通常比 Python 晚一截。Java 21 的虚拟线程适合阻塞式的模型 HTTP，并发上限仍要用信号量按供应商配额卡住，否则只是把线程换成了打满的连接。

两边不要各存一份权威状态。业务工具和团队在 Java，可以由 Java 做网关和有副作用的工具，编排放在同一侧，或单独一个运行时通过内部接口调工具。提示和评测变化快、又依赖 Python 的图，就把无副作用的编排放在 Python，副作用留在 Java。

容易漏的是用「Python 慢、Java 快」收尾。同步链路上的耗时主要在模型和检索。

**答题思路**

1. 先说项目实际用的语言，主链路在哪一侧。
2. 理由只讲当时的约束：工具和存量服务在哪、谁维护、图和提示改得勤不勤。
3. 说因此放弃的一面：Java 侧实验慢在哪里，或 Python 侧的权限、发布和类型约束是怎么补的。
4. 两边都有时，说清进程边界：谁持有状态，谁执行有副作用的工具，超时在哪一层。

不要编性能倍数，也不要编一个没上线的语言迁移。

### 4. 意图识别的常用方案，规则匹配和基于模型的各有什么优缺点

**参考答案**

结论：规则负责边界清楚、必须稳定的意图；模型负责说法多变的长尾。线上通常规则先拦，模型接剩下的，置信度不够就澄清，而不是二选一。

规则是关键词、正则和模板。它便宜、可解释、改完立刻生效，适合转人工、投诉、敏感操作这类不能分错的入口。说法一变就失效，规则之间会抢同一句话，意图一多就难维护。

基于模型，常见是分类器，或让生成模型在给定名单里选一个意图。它能接住改写和口语，新增说法不一定要写规则。代价是要标注或示例，有延迟和费用，输出必须约束在名单内，同一句话也可能前后不一致。分类器新增意图通常要重新训练；生成模型改名单就能试，但更不容易做回归。

高优先级规则先执行，命中且没有歧义就直接走。否则交给模型，只允许返回注册过的意图名。前两名分差太小，或落在「其他」，就反问，不调用有副作用的工具。一句话里有两件事时，不要硬压成一个标签。

容易漏的是只比整体准确率。规则看关键意图的精确率，模型看长尾召回，两套指标分开。

### 5. LangChain 的核心组件有哪些，Chain、Agent、Tool 之间的关系

**参考答案**

结论：Tool 是动作，Agent 是选择动作的策略，Chain 是事先定好的步骤。真正执行工具、把观察写回去的是运行时，不是模型。

常用组件还有：聊天模型、提示模板、输出解析器、检索器，以及文档加载和切分。记忆不是一个神秘模块，就是放进状态里的消息。追踪用回调接到外面。

Chain（现在多用 LCEL 的 Runnable 组合）由代码决定数据怎么流，例如检索、填提示、生成、解析。每次走哪些步骤是写死的，条件分支也是代码里的分支。

Agent 每一步把工具名单和当前消息交给模型，模型返回某个工具调用，或宣布结束。工具带名称、描述和参数 schema，描述会进入模型看见的上下文。运行时按注册表执行，把结果作为观察追加回去，再进入下一步。

三者的关系：Chain 可以无条件调用某一个工具；Agent 在多个工具之间选择。一条 Chain 可以包住一次模型调用，Agent 的循环也可以成为更大 Chain 里的一步。旧版本里执行器像一条链，现在这个循环多半跑在 LangGraph 上。包名不能说明控制流是直线还是循环。

容易漏的是工具报错直接把请求打崩，模型就没有机会改参数。可恢复的工具错误应作为观察返回，并占用一步重试预算。名称不在注册表里，同样按错误观察处理，不能反射着去调任意函数。

### 6. LangGraph 和 LangChain 的区别，什么时候需要用 Graph 来编排 Agent

**参考答案**

结论：LangChain 的链适合事先定好的直线或少量代码分支。LangGraph 把应用做成有共享状态的图，允许有界的环、人工暂停和按步恢复。出现这些需求再用图。

链上的中间值活在这一次调用里。进程停了，已经走到哪一步没有对应的检查点，只能整段重来。旧的 Agent 执行器内部有循环，但暂停下来等人、再从同一步继续，要另外补。

LangGraph 的节点读一份状态，返回自己负责的那一部分；字段用合并函数合上去。普通边表示做完去哪。条件边读状态，返回下一个节点名，也可以走回前面的节点，工具循环就是这种环。编译时接上 checkpointer，每个调度步之后可以落盘。

只是「检索然后生成」、失败了可以整段重跑的流程，一条链就够。需要分支、失败后换路、循环修订、等人审批，或进程重启后接着跑，再用带检查点的图。图也解决不了权限和预算，这些仍放在图外的运行时里。

容易漏的是为了用上框架，把直线流程也画成图。没有环、也不需要恢复时，检查点只增加存储和理解成本。

### 7. 你理解的 AI 工作流是什么，如何用 DAG 或者状态机来设计一个复杂任务

**参考答案**

结论：工作流是把目标拆成有状态的步骤，每一步谁来做、失败走向哪，由代码决定。DAG 表达依赖和并行，状态机表达分支、回退和循环。复杂任务通常外面是状态机，里面某几步是 DAG。

DAG 的边表示「必须先完成」，没有环，每个节点在一次运行里只做一次。适合互不依赖的只读检索并行，再汇合生成。它表达不了「审查不通过就退回去改」，除非把每一轮手工展开成不同节点，轮数还得事先定死。

状态机用状态和事件决定迁移，草稿、待审、待人工、完成、失败都可以是状态。守卫条件写在迁移上，例如工具成功、校验失败、超时。环是允许的，所以必须有退出：通过、放弃，或步数用尽。

设计时先列状态字段，再定每个节点只改哪些字段，然后画迁移。有副作用的节点和纯判断分开。并行的只读步骤收成一张 DAG，挂到状态机的一个状态上。持久化的是状态，不是图上的坐标。进程挂了从最后一次提交的状态继续，已经成功的副作用不要自动再做一遍。

容易漏的是把示意图当成工作流。图上没有超时、幂等和退出条件，它就只是一张图。LangGraph 可以有环，不要把它叫成严格的 DAG。

### 8. RAG 检索增强生成的完整流程，embedding 模型怎么选，chunk 策略怎么定

**参考答案**

结论：离线把文档变成带元数据、可过滤的块，并同时建向量和关键词索引；在线先召回再重排，只把少量有依据的块交给模型。

离线解析时保留标题、表格和来源。按结构切块，超长的再按嵌入模型能接受的长度切开。块上带文档 id、章节、更新时间和权限。文档更新按文档 id 替换旧块，而不是只往索引里追加。

在线可以对问句做改写，但关键词检索要留着用户原话里的专有名词。带过滤条件做两路召回，融合、去重、重排，再取前几块，上下文里带上章节路径。没有够格的依据就说明知识库里没有，不要让模型补。

嵌入模型用自己的问句和文档做召回评测，公共榜只作初筛。查询和文档必须是同一模型、同一套归一化和同一套指令；模型规定查询侧和文档侧指令不同时，两侧都按说明做。维度、延迟、能否私有化，按数据和流量定。换模型或换距离度量，就新建索引整库重嵌，新旧向量不能混在一起比距离。

切块先按标题和自然段，表格和代码不要从中间切断。块太大，向量会被无关内容冲淡；块太小，命中了也缺主语。检索用较小的块，送给模型时带上父级章节。重叠只能补一点边界，补不了切错结构。长度按 token 算，并小于嵌入模型的最大长度。

容易漏的是选一个榜单模型、按固定字数切完就上线。没有按「这条问句应该命中哪一块」看过召回，选型和切块都只是猜测。

**答题思路**

1. 说出真实的模型名，以及查询和文档是否用了同一套指令，换模型时索引有没有重建。
2. 切块说出按什么边界切、表格有没有单独处理。长度记不清就讲原则，不要编一个 token 数。
3. 当时如果是固定长度硬切、也没有评测，就照实说，再补你现在会改的一点。

### 9. 多个 Agent 之间如何通信和协调，有没有遇到过死锁或者循环调用

**参考答案**

结论：用一份结构化共享状态，或由调度者做明确交接。不要让多个 Agent 在同一段对话里自由互相呼唤。

步骤相对固定时，每个角色是图上的节点，读状态并返回自己那几个字段。同一步里并行的节点，看到的是这一步开始时的状态，写同一个没有合并函数的字段会冲突。需要限制谁能调用谁时，由调度者把子任务交给专家，专家只返回结果，不直接再调用另一个专家。交接带上任务 id、目标和剩余步数。和用户这次等待无关的积压，再走消息队列。

角色的写入范围事先分开。有副作用的动作只放在一个节点，并带幂等键。每次交接都减少剩余深度。

Agent 里更常见的是循环调用，不是数据库那种互斥锁死锁：A 把任务交回 B，B 又交回 A，状态没有新信息；或者两边互相等对方的结果。只有另外用了分布式锁、并且加锁顺序不一致时，才会出现经典死锁。

同一任务不要重复进入同一个角色。用状态指纹判断这一步有没有新信息，没有就停止并说明卡在哪。每跳都有超时，超时写成失败观察。锁按固定顺序获取，并设租约。图的步数上限是最后一道保险，不是正常业务分支。

容易漏的是只限制对话句数。要限制的是调用图上的重复边，以及谁可以写有副作用的状态。

**答题思路**

有过就讲一次真实情况：两个角色如何互相等待或反复交接，你靠哪个字段发现状态没变，最后是超时、步数上限还是人工把它停住。线上没遇到过，就说设计里有哪些限制，不要编事故。用脚本让模型一直返回同一个工具调用，证明循环能被停住，这比编故事有用。

### 10. Harness 工程具体指什么，你们怎么对 Agent 做测试和监控

**参考答案**

结论：Harness 是模型外面的运行时，负责循环能不能停、工具能不能安全执行、一次运行能不能被追踪和复现。它不是提示词，也不是模型权重。

它通常管这些事：组装上下文并在超长时压缩、工具注册表、执行前的参数校验和权限、步数与费用预算、失败后把观察交回模型、检查点、取消、以及需要人确认时暂停。LangGraph 提供图和检查点这类原语；哪些工具能执行、超限后怎么收口，是 Harness 上的策略。

测试分层。路由函数和状态合并用固定输入做单测，不打模型。模型用脚本替身，断言工具名、参数和停止条件。轨迹评测看工具序列和必须出现的依据，不只看最终文案像不像。提示词或模型版本变更时，用同一套任务回归。检索内容里夹带「忽略以上指令」时，工具权限仍然在网关生效。有副作用的工具在测试里走假实现。

监控上，一次用户请求是一条 trace，每次模型调用、检索和工具调用是子 span。指标看任务有没有按业务定义完成、工具失败率、超时率、步数打满的次数、token 和费用、转人工比例。告警打在熔断打开、检索为空和费用突变上。模型给自己打的分不能当唯一监控。

容易漏的是只监控聊天接口的 HTTP 200。接口成功了，检索仍可能为空，用户拿到的是没有依据的回答。

**答题思路**

按上面的清单对你自己的系统：哪些已经有，哪些只有日志。没做轨迹回归就不要说成有评测平台。准备一段你能打开的 trace，指出同一次请求里的模型调用和工具调用；没有追踪系统，就讲你当时靠什么日志排过一次故障。

### 11. Redis 在 Agent 系统中一般用来做什么，缓存还是会话存储

**参考答案**

结论：两类都会用，键的生命周期不同。会话是这条对话的热状态；缓存是可丢弃的计算结果。有副作用的任务不能只活在 Redis 里。

会话按会话 id 存最近消息、已确认槽位和运行到哪一步的指针，并设置过期。进程重启还要继续的检查点写到数据库，Redis 最多做这份状态的热缓存。只放 Redis、又没有可靠的持久化时，宕机会把做到一半的任务清掉。

缓存用来放查询向量、检索结果和只读工具的结果。键里带知识库版本和嵌入模型名，否则索引更新后仍会命中旧片段。用相似问句直接复用旧回答要很严：问法接近，但用户、日期或单号不同，就会答错。

限流计数、幂等键和短租约也常用 Redis。发布订阅不留底，不适合当 Agent 之间的可靠通道；要可靠事件用消息队列。

容易漏的是答完「用 Redis 存对话」就停。要补一句权威状态在哪，以及缓存键里有没有版本。

### 12. MySQL 索引结构，B+ 树为什么适合范围查询

**参考答案**

结论：InnoDB 的索引是 B+ 树。范围查询可以先落到起始键所在的叶子页，再顺着叶子页的链表顺序扫，不用每个后续键都从根查一遍。

非叶子节点只放键和子页指针，扇出大，树通常很矮。聚簇索引的叶子是整行，一张表只有一棵，一般建在主键上。二级索引的叶子是索引列加主键，要整行还得回表。没有主键时，InnoDB 选用第一个全列非空的唯一索引；再没有，就生成隐藏行号。页内记录有序，同一层的页用双向链表相连。

范围扫描从根找到起始键，然后沿叶子页向后读，直到越过结束键。相邻页按键有序，对缓存友好。经典 B 树把记录也放在内部节点，范围要做中序遍历，内部节点更宽，扇出更小。哈希只能做等值。InnoDB 的自适应哈希是对热点等值查询的内存加速，不是范围索引。

容易漏的是只答「树高低所以快」。树高低对点查也成立。范围的关键是叶子有序，并且页和页相连。

### 13. 手写算法：实现一个简单的 LRU 缓存，要求 get 和 put 都是 O(1)

**参考答案**

用哈希表按键找到节点，用双向链表维护使用顺序。最近使用的放在头哨兵后面，淘汰时删掉尾哨兵前面那个。查找、移动、插入、删除都是常数时间。空间和容量成正比。

约定按常见题面：容量是正整数，键和值是整数，键不存在时 `get` 返回 -1。`get` 命中要刷新为最近使用。`put` 已有的键时只更新值并刷新顺序，容量不变；键是新的且超出容量，才淘汰最久未使用的那个。这份实现不是线程安全的。

标准库可以用 `LinkedHashMap`：`accessOrder` 设为 true，并在 `removeEldestEntry` 里按容量淘汰，底层同样是哈希表加双向链表。`accessOrder` 忘了打开时，淘汰的是最早插入的，不是最久未使用的。

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    private static class Node {
        int key, value;
        Node prev, next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node lru = tail.prev;
            remove(lru);
            map.remove(lru.key);
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}
```

### 3. 意图识别准确率怎么提升的，样本不均衡怎么处理，有没有用主动学习

**参考答案**

结论：先别看整体准确率。多数类会把准确率撑得很高，少数类可能几乎没被识别。补数据和改决策阈值，通常先于换一个更大的模型。

评测看每个意图的召回，以及最容易混的那几对，另外单独看「不确定就澄清」的比例。测试集固定下来，不从后面的抽样里再挑题，否则每轮难度都在变，准确率没法比。训练和测试里出现同一句话，分数也会虚高。

**答题思路**

只讲你真做过的一两项，按「原来错在哪一对意图 → 改了数据、权重、阈值还是澄清 → 在哪份固定测试集上看的」说。没留测试集，就讲错例，不要编前后百分比。没用过主动学习就说没用，再补你会抽哪类说法给人标。

### 4. LangGraph 的状态管理机制，State 是怎么更新的，分支和循环怎么控制

**参考答案**

结论：State 是一份可序列化的共享数据。节点返回局部更新，由字段上的合并函数在这一步结束时写回去。分支靠路由读状态，循环必须有退出条件。

没有声明合并函数的字段会被整份覆盖，不是按键深合并。消息列表常用 `add_messages`：新消息追加，id 相同则替换那一条，所以它不是无脑拼接。同一步里并行的节点看到的是这一步开始时的快照，彼此看不见刚写的值；它们若写同一个不能合并的字段，这一步会失败。

```python
def route(state: State) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return END
```

条件边的返回值是节点名，不会写进 State。`END` 表示这一步之后结束，它不是一个业务节点。返回多个节点名时，这些节点在同一步并行。节点也可以返回 `Command`，同时带上局部更新和下一跳；路由只放一处，避免条件边和 `Command` 各写一套去向。

工具循环是一条回到模型节点的边：有工具调用就去执行，没有就到结束。模型如果总返回同一个调用，状态指纹不变，应主动停。图还有步数上限，到了会中断；这是保护，不要当成正常分支。每个调度步结束后可以用 checkpointer 按线程 id 落盘，恢复时从上次提交的状态继续。

容易漏的是节点把截至目前的全部消息又返回一遍。用列表拼接做合并时，旧消息会被再接一次；`add_messages` 只按 id 替换已有消息，没有 id 的仍会追加。节点只返回这一步新产生的消息。

### 5. 你们 RAG 系统里，如果检索到的文档质量差，怎么降噪或者重新排序

**参考答案**

结论：先分清是不相关的块进了候选，还是相关的块排在后面。前者靠过滤和召回，后者才靠重排。重排救不回根本没召回到的文档。

召回前就按权限、文档类型和生效时间过滤，过期制度和现行制度不要一起进候选。向量和关键词两路召回，按名次融合，并去掉同一文档挤占名额的重复块。再用交叉编码器这类重排模型，对「查询，块」成对打分，从几十条里留少数几条。重排模型和嵌入模型分开评。

「低于多少分就当没检索到」要在标注集上定。余弦相似度的绝对阈值不能换一个嵌入模型继续沿用。不够格就明确说知识库里没有依据。块仍然太长时，可以抽取和问题有关的句子，但引用要回到原块。送进模型时，把更相关的块放在上下文的前部和后部，中间位置更容易被忽略。

不要靠提示词写「请忽略不相关内容」来降噪。不相关的块就不放进去。生成模型也变不出没召回到的条款。另一个容易漏的是 Top-K 全来自同一篇的重复片段，看起来分数很高，依据仍然偏。

### 6. 一个用户请求进来，经过多个 Agent 流转，超时和熔断怎么设计

**参考答案**

结论：整次请求只有一个截止时间。每个 Agent、每次模型和工具调用只能使用剩余预算。熔断按依赖单独计算，打开后快速失败并降级，而不是继续重试把工作线程打满。

入口记下截止时间，下游拿到的超时是「自己的上限」和「剩余时间」里更短的那个。超时后要取消正在进行的 HTTP 调用，把这一步记为超时。只停止等待、连接还挂着，配额和线程仍被占住。取消一个 Future 也不等于对方的 HTTP 客户端一定会断开，要以客户端真正支持取消为准。单次调用允许的时间如果长于剩余预算，预算就没有意义。排队等待也算进截止时间，不能等出队之后才开始计时。

重试只给可重复的读，次数少，带退避和抖动，并且剩余预算还够才重试。会改数据的调用用幂等键；结果未知时先查询下游，不盲目再做一次。

熔断按模型入口、某个工具或某个专家 Agent 分开。关闭、打开、半开三种状态：连续失败或窗口内错误比例过高就打开，打开期间直接走降级，半开只放探测请求。降级可以跳过可选 Agent、返回已经完成的部分，或转人工。必选步骤没有结果时，要在回答里写明缺了什么，不能让模型把缺的部分补成事实。每个依赖还有自己的并发上限，避免一个慢专家占满全部工人。

重试会让熔断看得更多次失败。要定好哪一层负责重试，避免同一次用户请求把熔断器提前打开。

容易漏的是所有 Agent 共用一个很长的超时。前面的专家把预算用完，后面的专家已经没有时间，用户却要等满整个超时。

### 7. Elasticsearch 在你们项目里用了没，倒排索引和向量检索怎么结合

**参考答案**

结论：倒排索引负责词项精确匹配，向量负责语义相近。两路对同一批文档召回，按名次融合，不要把 BM25 分和余弦相似度直接相加。

倒排索引是词项到文档列表，列表里有文档、词频和位置。文档和查询要走同一套分析器，否则入库做了小写或分词、查询却用原样，就会对不上。BM25 用词频、逆文档频率和长度做打分，适合单号、错误码、专有名词和必须原样命中的短语。

向量是同一文档上的稠密向量字段，查询必须用同一个嵌入模型。近邻搜索常用 HNSW 这类近似算法，速度快，但可能漏掉真正更近的文档，评测时不能把它当成精确搜索。权限、租户和时间要写进检索条件，在近似搜索时就生效。先取一个全局前 K 再过滤，过滤完可能一条不剩。

两路都返回文档 id，再用倒数排名融合合成名次。两套原始分不是一个量纲，直接加权会让某一路一直压过另一路。融合后的前几十条再交给重排。两路索引同一批块，更新时一起替换。嵌入模型一换，就重建向量，不能和旧向量混在一个字段里比距离。关键词检索和 kNN 可以放在一次查询里完成。

容易漏的是只建向量、用 Elasticsearch 当普通向量库。单号和错误码这类精确词，倒排一路往往更稳。

**答题思路**

用过就说文档上哪两个字段、过滤条件是什么、两路结果在哪里汇合。没用过就直接说没用，再讲你实际用的检索组件，以及如果要结合会按上面的方式做。不要编集群规模或版本号。

### 8. Kafka 消息队列在 Agent 间异步通信中的作用，如何保证消息不丢失

**参考答案**

结论：Kafka 用来承载和这次用户等待脱开的任务与事件，例如建索引、通知、审计和可以稍后完成的子任务。用户还在连接上等待的调度，不要先绕一圈消息队列。不丢的保证是至少一次送达；重复要靠业务幂等消化。

生产者要等当前 ISR 都确认（`acks=all`），并开启幂等，这样超时后的重试不会在分区日志里留下重复记录。`acks=all` 等的是 ISR，不是所有副本。ISR 里如果只剩一个，确认过的消息仍可能随这一份数据一起丢掉，所以副本数至少 3、`min.insync.replicas` 至少 2。不要允许 ISR 之外的副本成为首领，否则落后副本当选会截掉已经确认的消息。调用发送接口不算成功，要等 broker 确认之后，才能对上游说任务已接收。

消费者在处理成功后再提交位移。按时间自动提交会在处理前就提交，这时进程挂了，消息不会再投递，这才是丢。处理完、提交前挂了，消息会再来一次，所以外部工具按消息 id 做幂等。Kafka 事务能覆盖「消费、处理、再写入 Kafka」这一种链路，覆盖不了事务外面的发信、扣款或调用另一个 Agent。

同一任务要用同一个分区键，保证这个任务内部有序。消费者数超过分区数时，多出来的消费者分不到分区。

容易漏的是把「不丢」说成「恰好一次」。至少一次加上幂等，业务上才不会丢，也不会因为重投做第二次。

### 9. Java 多线程方面，线程池核心参数怎么设，你们 Agent 并发量多大

**参考答案**

结论：Agent 的线程大多在等模型和工具返回，池的大小按允许的在途请求算，不按 CPU 核数乘二。队列必须有界，否则最大线程数不会生效。

`ThreadPoolExecutor` 的七个参数是核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂和拒绝策略。执行顺序是：未到核心线程数就建线程；否则入队；队列满了再扩到最大线程数；仍然不行就拒绝。`Executors.newFixedThreadPool` 用无界队列，任务会一直堆着，最大线程数基本不参与。`newCachedThreadPool` 会无界建线程。生产里不要用这两个来打模型。

稳定时，在途请求大约等于每秒请求数乘以单次调用占用的秒数，再被供应商允许的并发和自己的截止时间封顶。对这种要等外部响应的负载，核心线程数可以接近这个在途上限，最大线程数不要比核心数大很多。队列只留还能在截止时间前开始执行的那些任务，来不及的直接拒绝，并给用户一个明确的降级，而不是默默丢掉。`CallerRunsPolicy` 会让提交线程自己去等模型，HTTP 线程会被拖死。存活时间只影响超过核心数的那些线程，除非另外允许核心线程超时退出。

Java 21 可以用虚拟线程承担阻塞式 HTTP，但仍然要用信号量限制打向模型的在途数，否则限制只是从线程数换成了连接数。模型和本地快任务分开限制。连接超时、响应超时都要小于剩余预算。线程工厂把线程命名，转储时才分得清是哪一个池。

容易漏的是把池配得很大，却不限制单个慢工具。一个专家卡住，整个池都被占满，健康检查和其他 Agent 一起超时。

**答题思路**

先定义口径：同时在飞的模型请求，还是每秒进来的用户请求，两个数不要混。有监控就说峰值在途、当时的超时比例，以及供应商允许的并发，并说清统计窗口。没有监控就说你按「每秒请求数 × 单次耗时」估算、再用配额封顶，并承认这是估算。不要报一个整数充数。最后只讲一个你因此改过的参数：队列长度、信号量或超时。没改过就停在估算方法上。

### 10. Spring Boot 里的 AOP 在 Agent 日志和监控中怎么用的

**参考答案**

结论：AOP 适合放在所有工具调用都会经过的那一个网关上，用来记耗时、成功与否和 trace。它不适合散落在每个工具方法上，更不能把工具异常吃掉。

Spring Boot 默认的 AOP 是运行时代理，不是编译期织入。调用必须打到 Spring 代理上，切面才生效。类内部的自调用不经过代理。Agent 循环如果执行的是注册表里的函数对象，而不是某个 Bean 的方法，打在工具类上的切面不会运行。可靠的做法是只留一个工具网关，循环只调这个网关；切面或装饰器包在网关上。

环绕通知里先记开始时间，再 `proceed()`。成功和失败都记一条指标，失败后把原异常抛出去，模型才看得到工具错误。日志里放工具名、耗时、trace id 和结果是成功还是失败，不放完整提示词、用户原文和工具返回。这些内容既有隐私，也会把日志打满。指标标签用工具名和结果，不要用用户 id 或原始问句，否则标签基数会爆。

工具如果返回异步对象，切面默认只量到提交那一下。计时要挂到完成之后，才是真正的工具耗时。权限校验和日志如果是两个切面，校验失败也要能被日志看见，不能被外层吃掉。

容易漏的是用切面代替工具网关的权限和超时。切面绕得过，网关是唯一入口才绕不过。

### 11. 你们 AI 工作流的可视化编排是自己做的还是基于开源框架，说说设计思路

**参考答案**

结论：画布保存的是带版本的流程定义，超时、幂等和恢复都在运行时。自研还是开源，差在定义能不能编译成你可控的运行时。

节点类型先收口：模型、工具、检索、条件、人工。状态字段先定义，节点只写自己那几项。定义用结构化文档落库，一次运行绑定启动时的版本，中途发布新版本不改变已经在跑的实例。

运行时把定义编译成有检查点的图或自己的状态机。条件只读结构化字段。循环必须有结束条件。画布要么能表达环，要么把循环标成节点属性再由编译器展开；只能画 DAG 的编辑器表达不了工具来回调用。调试读 trace：当前节点、状态快照、模型输入输出和工具参数，而不是只放一张箭头动画。

Dify、LangFlow 这类开源编排适合把「检索然后生成」先跑起来。企业内部往往还要私有化模型、统一身份、工具级权限、审计、评测门禁和检查点。这些如果补在产品外面，升级时容易碎。自研的成本在编译器、版本和权限，不在拖拽组件；运行时仍要单独做，不能认为有了画布就有了引擎。

容易漏的是把编辑器里的试运行当成生产运行时。试运行没有租户隔离、检查点和幂等，不能直接拿去接有副作用的工具。

**答题思路**

说清你们实际用的是哪一个，它负责到哪一层。用开源就说明权限、检查点和审计是产品自带的，还是你们补的。自研就说定义存在哪、运行时是不是另一套代码。线上如果没有可视化编排，就直接说没有，再讲你会把定义和运行时分开。不要把调研过的产品说成已经上线。

### 12. 如果让你从零搭建一个企业级 AI Agent 平台，技术栈你会怎么选

**参考答案**

结论：先做扎实一条请求的运行时：身份和配额、模型网关、工具网关、知识库、检查点、评测和追踪。模型可以换，工具契约和轨迹换不了。多 Agent 等单 Agent 的回归稳定后再拆。

接入层做统一身份、租户和配额，入口就定好这次请求的截止时间。编排上，有分支、循环和人工插入点时用有检查点的图；只是检索然后生成，一条链就够。权威状态放数据库，缓存只做加速。

模型网关屏蔽厂商差异，集中做超时、限流、失败切换和 token 记账，业务代码里不散落密钥。工具用注册表和 schema，只读和会改数据分开；会改数据的带幂等键和权限，不把数据库账号交给模型。知识库做解析、按结构切块、向量加关键词、重排，索引带版本，更新用切换而不是半截覆盖。

建索引、评测和审计走消息队列。用户还在等的那一段保持同步调用。上线前有固定任务集；线上抽样看工具失败、检索为空和回答有没有依据。一次请求的 trace 要能对上每次模型和工具调用。

团队主力如果是 Java，工具和网关放在 Java。编排和评测变化快，可以独立一个运行时，但状态只能有一处是权威。先做一个负责调度的循环加上明确工具，失败边界比多个 Agent 自由对话清楚。

容易漏的是把平台做成模型代理加一个聊天窗口。没有评测集和轨迹，换提示词只能靠感觉。

### 13. 手写算法：给定一个字符串，找出最长的不含重复字符的子串长度

**参考答案**

结论：滑动窗口。右端逐个纳入，窗口里出现重复就把左端挪到这个字符上一次出现位置的下一位。题目要的是长度，子串必须连续；不连续的最长子序列是另一题。

用哈希表记录每个字符最近一次的下标。右指针从左扫到右。只有上一次下标还落在当前窗口里，左指针才跳到它的下一位；窗口外面的同名字符不构成重复。左指针只往右，不会回头。每步用右减左再加一更新答案。

每个下标最多被右指针和左指针各处理一次，时间是 O(n)。额外空间是窗口里不同字符的数量，上界是字符集大小。空串答案是 0。例如 `abcabcbb` 的答案是 3，对应 `abc`。

容易漏的是左指针见到历史下标就跳，不判断它是否还在窗口内。`abba` 里最后的 `a` 不能把左指针拉回已经越过的位置。

```java
import java.util.HashMap;
import java.util.Map;

public class LongestSubstring {
    public int lengthOfLongestSubstring(String s) {
        Map<Character, Integer> last = new HashMap<>();
        int left = 0;
        int best = 0;
        for (int right = 0; right < s.length(); right++) {
            char c = s.charAt(right);
            Integer prev = last.get(c);
            if (prev != null && prev >= left) {
                left = prev + 1;
            }
            last.put(c, right);
            best = Math.max(best, right - left + 1);
        }
        return best;
    }
}
```
