### 3. Java 内存模型包含哪些区域？垃圾回收机制是怎样的？

**参考答案**

结论：题目问的是区域，按 JVM 运行时数据区回答。并发里的 JMM 是另一套概念，讲的是主内存、工作内存和 happens-before。

线程私有的是程序计数器、Java 虚拟机栈、本地方法栈。程序计数器只记当前字节码位置，是规范里唯一不会溢出的区域。栈里每个方法一帧，保存局部变量、操作数栈和返回地址；栈深超限是 `StackOverflowError`，线程要的栈扩不出来是 `OutOfMemoryError`。

线程共享的是堆和方法区。对象和数组在堆上。JDK 8 起 HotSpot 用本地内存里的元空间实现方法区，类元数据放这里，字符串常量池在堆中。直接内存给 NIO 用，不在这五块里，靠 Cleaner 回收，堆还空着时机器内存也可能先被打满。

垃圾回收从 GC Roots 做可达性分析，根包括栈上引用、静态变量、JNI 引用和同步监视器等。不可达对象才会被收。HotSpot 按分代处理：新生代里朝生夕灭的对象用复制算法，在 Eden 和两块 Survivor 之间搬；熬过几次年轻代回收的对象晋升老年代。老年代用标记整理，或像 G1 那样按 Region 挑垃圾多的区域复制。到达安全点才会停顿。JDK 8 默认是 Parallel，JDK 9 起默认是 G1。年轻代回收不等于整堆 Full GC；元空间满了会触发类卸载，表现为 `OutOfMemoryError: Metaspace`。

### 4. 线程池的核心参数有哪些？请解释每个参数的含义

**参考答案**

结论：`ThreadPoolExecutor` 有七个构造参数。队列有没有界，决定最大线程数会不会生效。

1. `corePoolSize`：核心线程数。默认一直保留，空闲也不退出。
2. `maximumPoolSize`：线程数上限，含核心线程。
3. `keepAliveTime`：超过核心数量的线程，空闲超过这段时间就退出。
4. `unit`：上一项的时间单位。
5. `workQueue`：核心线程都在忙时，任务进入的队列。
6. `threadFactory`：创建线程，用来指定名字、是否守护，以及未捕获异常处理器。
7. `handler`：拒绝策略。默认 `AbortPolicy` 抛 `RejectedExecutionException`。`CallerRunsPolicy` 在池还在运行时让提交线程自己执行。`DiscardPolicy` 丢掉新任务。`DiscardOldestPolicy` 丢掉队列头再尝试提交当前任务。

`allowCoreThreadTimeOut(true)` 且存活时间大于 0 时，核心线程空闲也会退出。`Executors.newFixedThreadPool` 使用无界队列，任务会一直入队，`maximumPoolSize` 基本不会参与。生产里用有界队列，并规定拒绝之后是失败还是退回调用方。

### 5. 线程池执行任务的完整流程是怎样的？

**参考答案**

结论：先补核心线程，再入队，队列满了再扩到最大线程，仍然不行才拒绝。入队成功之后还有一次复核。

`execute` 的顺序是：

1. 工作线程数小于核心线程数：`addWorker(task, true)` 创建核心线程执行这个任务。创建失败就继续往下，例如线程池正在关闭。
2. 池处于 `RUNNING` 并且 `offer` 成功：再读一次状态。此时若已关闭，把任务从队列移除并拒绝。若工作线程数变成 0，再补一个空任务的线程去消化队列，避免任务卡在队列里。
3. 入队失败：队列满了，或者池已经不接收新任务。此时 `addWorker(task, false)`，把线程扩到 `maximumPoolSize`。
4. 扩容也失败：交给拒绝策略。

工作线程执行完手里的第一个任务后，从队列取下一个。核心线程默认 `take` 阻塞等待；非核心线程 `poll` 超时后退出。`execute` 抛出的运行时异常进线程的未捕获处理器；`submit` 同样走 `execute`，异常放在 `Future` 里，不调用 `get` 就看不见。

### 6. Spring AOP 有哪些实现方式？动态代理的实现方式和区别是什么？

**参考答案**

结论：Spring 自己的 AOP 是运行时代理，要么 JDK 动态代理，要么 CGLIB。`@Aspect` 用的是 AspectJ 的切点语法，默认并不是 AspectJ 织入。

创建代理的规则：目标类实现了接口、并且 `proxyTargetClass=false` 时，用 JDK 动态代理，`InvocationHandler` 在调用时转发到目标对象。没有接口，或者 `proxy-target-class=true` 时，用 CGLIB 生成子类。Spring Boot 2 起这个属性默认是 `true`，即使有接口也走 CGLIB。编译期、编译后和加载期织入属于 AspectJ，能拦构造器和字段访问，需要单独的编译器或 agent。

JDK 代理对象只实现接口，按具体类注入会失败。CGLIB 代理是目标类的子类，可以按具体类注入，但不能代理 `final` 类和 `final` 方法。两种代理都只拦从外部打到代理上的调用。类内部的 `this.method()` 不经过代理，事务和切面都不会生效。需要生效时，把方法放到另一个 Bean，或通过已注入的代理对象调用。`private` 方法不能被子类覆盖，也不会被增强。

### 7. MySQL 索引的原理是什么？非聚簇索引和聚簇索引有什么区别？

**参考答案**

结论：InnoDB 用 B+ 树。聚簇索引的叶子是整行，一个表只有一棵；二级索引的叶子是索引列加主键，查完整行要回表。

非叶子节点只放键和子页指针，扇出大，树通常很矮。叶子之间有链表，范围扫描可以沿着叶子走。页大小 16KB，高度和数据量、行宽有关，不要背死成固定层数。

聚簇索引就是主键那棵树，数据和索引在一起。没有主键时，InnoDB 用第一个全列非空的唯一索引；再没有，就生成 6 字节隐藏行号。主键顺序和数据页顺序一致，所以主键宜短、宜递增，随机主键会把插入打散到多个页。

二级索引是非聚簇的：叶子不放整行，放主键值。`SELECT *` 要拿主键再查一次聚簇索引，这就是回表。查询列都被这棵二级索引覆盖时，不必回表。MyISAM 的主键和二级索引叶子都是数据文件地址，数据另存，两棵都是非聚簇。

### 8. 联合索引的最左匹配原则是如何实现的？

**参考答案**

结论：联合索引在 B+ 树里按列从左到右组成有序元组。查找必须先确定左边的列，右边的列才有序，所以能用的是左前缀。

索引 `(a, b, c)` 先比 `a`，再比 `b`，再比 `c`。`a = 1 AND b = 2` 可以从根往下定位；只有 `b = 2` 时，同一棵树并不按 `b` 整体有序，无法从根上直接定位。优化器会把等值条件重排成索引顺序，`b = 2 AND a = 1` 仍然用得到 `(a, b)`。

范围列会截断后面的定位：`a = 1 AND b > 2 AND c = 3` 用 `a` 和 `b` 确定扫描范围，`c` 不能再缩小起点，但可以做索引条件下推，在存储引擎里过滤。`LIKE 'ab%'` 能用前缀；`LIKE '%ab'` 不能。对列做函数或类型转换，比较的就不再是索引里的原始值。

MySQL 8.0 的索引跳跃扫描是例外：前导列区分度很低时，优化器可能按前导列的少数取值分段，再用后面的列查找。日常建索引仍按这个顺序：等值列放左边，范围列放它右边。

### 9. Redis 的持久化方式有哪些？各自的原理是什么？

**参考答案**

结论：RDB 是某一时刻的二进制快照，AOF 是追加写命令。可以同时开。进程重启时，只要 AOF 开着，就优先用 AOF 恢复。

RDB：`SAVE` 在主线程里同步写，会堵住命令。`BGSAVE` 先 `fork` 子进程写临时文件，写完再原子替换。父子进程用写时复制共享内存，期间写得多，父进程就会复制出额外脏页，内存会涨。快照之间的写入在宕机时丢掉。适合备份和较快的冷启动。

AOF：把写命令追加到文件。`appendfsync` 为 `always` 时每条命令都刷盘；`everysec` 是常见配置，大约每秒刷一次，宕机可能丢一秒；`no` 则交给操作系统决定何时刷。文件变大后 `BGREWRITEAOF` 同样 `fork`，按当前数据重写成重建数据集所需的最短命令，父进程把重写期间的新命令放进重写缓冲区，最后拼到新文件再替换。Redis 4.0 起可以混合：文件头是 RDB，后面接增量 AOF，加载比纯命令回放快。Redis 7 起 AOF 可以拆成基础文件加增量文件。

持久化保留的是这块磁盘上的数据。磁盘一起损坏时，要靠主从或多副本来恢复。

### 10. 了解 Redis 集群吗？说说它的工作原理

**参考答案**

结论：Redis Cluster 把数据分成 16384 个槽，由多个主节点分片持有，副本负责顶上故障的主节点。分片和高可用都在集群内部完成。哨兵管的是不分片主从的切换。

键先算 CRC16，再对 16384 取模得到槽。`{...}` 里的内容才参与计算，花括号相同的键落在同一槽，才能一起做多键操作。普通多键命令跨槽会被拒绝。

节点之间走集群总线，端口是客户端端口加 10000，用 Gossip 交换节点状态和故障怀疑。某个槽的主节点被多数主节点判定下线后，它的副本发起选举，得到多数主节点投票才能升主。所以主节点数通常取奇数，至少 3 个。某个槽的主节点和副本全不可用时，默认 `cluster-require-full-coverage yes`，整个集群都会拒绝访问，而不只是这个槽。

客户端缓存槽位映射。请求打错节点会收到 `MOVED`，客户端更新映射再重试。槽正在迁移时收到的是 `ASK`，只对这一次重定向，不改本地映射。

### 11. Kafka 和 RocketMQ 在架构设计上有什么主要区别？

**参考答案**

结论：Kafka 以分区日志为中心，擅长高吞吐和按位点回放。RocketMQ 把所有主题顺序写进一份 CommitLog，再用队列索引对外提供消费，并把延迟、事务和重试做进 Broker。

存储上，Kafka 每个分区是一组独立的段文件，消息在分区内追加，消费者按 offset 拉。分区多、主题多时，文件也多。RocketMQ 的 Broker 先把消息追加到 CommitLog，每个逻辑队列一份 ConsumeQueue，里面是消息在 CommitLog 中的位置、长度和 Tag 哈希。主题再多，写盘仍然主要是一份顺序日志。

协调上，Kafka 旧集群用 ZooKeeper，新集群用 KRaft，控制器在 Broker 里选举。RocketMQ 用无状态的 NameServer，Broker 注册路由，客户端定期拉取。NameServer 之间不选主，路由是最终一致的。

消费上，两者的并行和顺序单位都是分区或队列，都是拉模式。RocketMQ 的推模式是长轮询封装出来的。位点上，Kafka 消费组把 offset 记在内部主题；RocketMQ 传统模式把消费进度放在 Broker。业务消息上，RocketMQ 有半消息事务、固定等级或任意时间的延迟消息、重试队列和死信队列。Kafka 有幂等生产者和事务生产者，延迟和死信一般要自己用重试主题来做。

### 12. 什么是 AI Agent？其核心组成部分有哪些？

**参考答案**

结论：Agent 用模型做决策，根据目标和环境的观察反复行动，直到完成或触发停止条件。一次补全没有这个闭环。

核心部分有五块：

1. 模型：负责理解、选择下一步和生成结果。
2. 规划：把目标拆成步骤，或在 ReAct 循环里边做边定下一步。
3. 记忆：短期是当前对话和中间观察，长期是向量库、业务库或用户资料。上下文窗口装不下的状态要放到外面。
4. 工具：模型只产出符合 schema 的调用，由运行时执行搜索、接口或计算。
5. 约束和运行时：系统提示、工具白名单、步数上限、超时和日志。没有停止条件，循环会一直打同一个工具。

模型、工具和可恢复的状态都在，才谈得上可上线的 Agent。只包一层聊天接口，缺的是行动和观察这条回路。

### 13. Agent 中的 Tool 是什么？常见的工具类型有哪些？

**参考答案**

结论：Tool 是暴露给模型的一项能力，包含名字、用途说明和参数 schema。模型发出调用请求，运行时校验并执行，再把结果送回模型。

常见类型：

1. 检索：搜索、知识库、只读数据库。用来补模型没有的事实。
2. 业务接口：订单、账户、工单这类 HTTP 或 RPC。
3. 计算：计算器、代码执行、SQL。执行环境要有资源限制。
4. 写操作：发消息、改数据、付款。要有权限、幂等键，以及必要的人工确认。
5. 移交：转给人或另一个 Agent，并交还当前任务状态。

描述要写清何时该用、何时不该用，参数用结构化 schema 约束。运行时做类型、范围和权限校验，超时和业务错误要原样返回给模型，让它换参数或停下来问用户。密钥放在服务端，不进提示词。

### 14. 在 Agent 开发中，如何通过 Prompt 实现高效的意图识别？

**参考答案**

结论：意图收成闭集，模型只输出结构化结果；置信度不够就追问，不进入工具。

做法是：

1. 给每个意图写定义、反例和要抽的槽位。「未知」和闲聊单独成类，避免硬塞进业务意图。
2. 输出固定成 `intent`、`slots`、`confidence`、`missing_slots`。能用结构化输出或函数调用就不要让模型自由写一段再去解析。
3. 每类放两三条容易混的例子，例子放边界。
4. 路由提示词和执行提示词分开。路由只分类，不带大段业务说明。
5. 意图很多时分两段：先大类，再在大类里分小类。
6. 低于阈值就生成澄清问题。缺槽位时追问槽位，不猜测。
7. 用真实话术做混淆集，看哪两类互相抢，再改定义或例子。

路由结果要能回归。只改提示词、不看识错的句子，上线后同类说法会漂。

### 15. 如果让你设计一个高可用的 Agent 服务，你会考虑哪些方面？

**参考答案**

结论：计算节点无状态，会话和步骤放外面；模型和工具都要超时、限流和降级。长任务不占着请求线程。

1. 接入层水平扩展。对话、计划步骤放 Redis 或数据库，实例挂了可以从最后一步继续。
2. 模型调用有超时、有限次重试和熔断。主模型不可用时切备用模型或备用供应商，响应里能区分这次是否降级。流式中断要结束本次调用，避免连接一直占着。
3. 工具单独超时，和模型的线程池隔开。写操作带幂等键，重试不能重复下单或扣款。失败把错误返回给模型，或直接结束，不无限重试。
4. 分钟级任务进队列，接口只负责提交和查状态。队列满了拒绝新任务。
5. 向量库或下游故障时，降级成依据当前对话回答，或返回明确失败。
6. 按租户限制 QPS、并发和 token，避免一个调用方打满额度。
7. 同一个 trace 串起模型、检索和工具，看成功率、超时、工具错误和费用。
8. 会改数据的工具默认不自动执行，服务端再验一次权限。提示词和工具 schema 带版本，灰度发布。

### 1. 自我介绍

**答题思路**

二面可以比一面更短，大约一分钟，落点放在接下来要被深挖的 Agent 项目上。

1. 一句定位：年限、Java 方向、现在做的是业务系统还是智能体服务。
2. 只点名一个你负责的项目，说清用户和你负责的那一段，不要把一面已经讲过的技术栈再背一遍。
3. 用一句取舍结尾，例如为什么编排留在 Java 服务里、知识库怎么更新。等面试官选这一点往下问。
4. 一面已经报过的年限和职责保持一致。

### 2. 请详细介绍一下你负责的 Agent 项目，包括业务场景和技术架构

**答题思路**

按「场景 → 请求链路 → 你的边界 → 一个设计取舍」讲 4 分钟左右。用真实项目，没有多 Agent 就按实际架构讲。

1. 场景：谁在用，成功的标准是查对、办成一件事，还是生成可复核的结果。说出输入和产出。
2. 链路按层讲：接入（身份、租户、限流）→ 编排（意图或计划、状态）→ 模型 → 工具和检索 → 存储（业务库、向量、日志）。只讲你系统里有的层。
3. 每层点一个你拍过板的选择：同步还是异步、检索放在哪、写操作谁来执行。框架名跟着选择走，不要先堆名词。
4. 职责说清楚：哪些是你设计的，哪些是接现成组件。
5. 结尾留挑战：延迟、检索更新、工具副作用或循环调用，选你真处理过的一个，交给下一问。

没有线上数据就讲现象和约束，不编 QPS、准确率或节省的人数。

### 3. 在 Agent 项目中遇到的最大技术挑战是什么？你是如何解决的？

**答题思路**

只讲一件你亲自处理的事，按「现象 → 怎么定位 → 选项 → 为什么选这个 → 怎么确认好了」讲。

1. 现象用用户能感知的话：答非所问、重复下单、超时，或同一步工具被调用很多次。
2. 定位到一层：提示词、检索数据、工具参数、编排状态，还是模型超时。说出你凭什么判断是这一层。
3. 至少对比过一条别的路。例如先限制工具和步数，还是先换模型；先清洗文档，还是先加澄清问题。

### 4. 当项目成员对技术方案有不同意见时，你会如何沟通并达成一致？

**答题思路**

按「对齐目标 → 把分歧写成可验证的差异 → 用证据取舍 → 定责并执行」讲。用你真实经历过的一次分歧，不现场编一套架构争论。

5. 若问到你让过步的例子，讲你放弃的点和你坚持的底线，例如可以换组件，但不能让模型直接决定写哪些数据。

### 5. 在 Agent 项目中，为什么选择 Spring AI 而不是直接使用 LangChain？

**答题思路**

先讲你项目当时的约束，再讲两个栈的差别，最后落到你真实放弃的那部分能力。下面这些差别按你的实际情况取用。

1. 约束通常是：团队写 Java、服务已经在 Spring Boot 里、鉴权和事务不能再拆一个进程。是这些就明说；不是就说真实原因。
2. Spring AI 的 `ChatClient`、Advisor、`VectorStore` 和工具回调，与 Spring 的配置、Micrometer 和安全模型在同一个进程里。模型厂商包在 `ChatModel` 后面，业务代码少绑死一家 API。
3. 直接用 LangChain，指的是 Python 运行时：要单独部署，身份、租户和超时得跨进程传。Java 里接近的是 LangChain4j，工具和 RAG 很全，也可以进 Spring Boot，但它的中心抽象是 AI Service，不是 Spring 这一套 Bean 和 Advisor。
4. 主动说出 Spring AI 薄的地方：有状态的多 Agent、检查点和人工中断，LangGraph 更完整。复杂循环要自己做状态机，或只把那一段放到 LangGraph。
5. 结论收在部署和权限边界，不收在「谁更新更勤」。准备一个你后来觉得别扭的点，例如编排是手写的，避免答成全是优点。

### 6. 请描述你项目中的 Multi-Agent 架构设计逻辑

**答题思路**

按「角色怎么分 → 谁调度 → 状态放哪 → 怎么停」讲你真实的系统。没有多 Agent，就说明是单 Agent 加工具，并解释为什么不再拆。

1. 角色：每个 Agent 只有自己的目标和工具白名单。规划者负责拆任务和收口，专家不互相无限转发。
2. 调度：谁决定下一步交给谁。常见是一个总控看当前步骤；也可以是固定流水线。讲清你用的是哪一种。
3. 状态：共享的是任务单、步骤状态和产物引用。每个 Agent 只拿本步需要的上下文，不把全部历史复制给所有人。
4. 交接：上一棒的输出要有结构，下一棒缺字段就失败返回，不靠自然语言硬接。
5. 停止：最大步数、重复调用检测、超时，以及写操作回到服务端鉴权。总控挂了要能从步骤状态恢复。
6. 准备一个不拆的反例：两个角色总是一起出现、工具也相同，拆开只是多一次模型调用。

### 7. RAG 系统如何实现知识库的增量更新和数据删除？

**参考答案**

结论：用稳定的文档主键和内容哈希做增量。文档变更时先按文档删掉全部旧切片再写入。只 upsert 新切片，变短的文档会留下尾部旧切片。

更新按这个顺序：

1. 每篇文档有 `doc_id`，每个切片有 `chunk_id`。哈希没变就跳过，不重新做向量。
2. 解析、切分、向量化之后，先按 `doc_id` 删除旧切片，再写新切片。任务以文档加版本做幂等，重复消息不会插出两套。
3. 向量、关键词索引和对象存储里的原文走同一条流水线。查询可以接受短暂延迟，但三处版本要能对上。
4. 元数据记下 embedding 模型版本。换模型就按版本整库重算，旧向量不能和新查询向量混在一个空间里检索。

删除要一次删全：该 `doc_id` 的所有切片、父子切片或摘要切片、原文、关键词文档。需要审计时先打删除标记，检索条件排除它，再异步物理删除。权限缓存和查询缓存按文档或租户失效。只删向量时，关键词检索仍会把这篇文档搜出来。

### 8. 海量文档场景下，RAG 的文档入库和向量检索如何做性能优化？

**参考答案**

结论：入库避免重复计算并批量写；检索先按权限缩小范围，再做近似搜索，最后只对少量候选重排。

入库：

1. 内容哈希没变的文档不解析、不做向量。
2. 解析、切分、向量化、写入拆成队列。向量化按接口允许的批量调用，并用并发和背压保护下游。
3. 向量库批量写入。按租户或时间分片，避免所有租户挤在一次全量扫描里。
4. 原文放文档库。向量侧保留主键、向量和过滤字段。

检索：

1. 租户、权限、有效期在搜索时就过滤。引擎若先取全局 TopK 再过滤，名额会被别的租户占满。
2. 用近似最近邻，把搜索宽度当作召回和延迟的旋钮，不默认精确 KNN。
3. 关键词和向量一起查，融合后取一小段做重排，再送进模型。
4. 重复问题缓存查询向量。用小切片检索，命中后回拿父块，避免整篇进上下文。
5. 内存紧时再考虑量化。量化会损失召回，要用你的查询集看过再开。

专有名词和编号仍要靠关键词。只加机器、不改过滤位置，延迟下来了，结果仍会错。

### 9. Elasticsearch 在 Agent 系统中可以应用于哪些场景？

**参考答案**

结论：Elasticsearch 适合又要关键词、又要过滤和原文的检索，也适合查日志。事务和任务状态放在数据库。

1. 混合检索：错误码、保单号、产品名走 BM25，语义走 `dense_vector` 的 kNN，再做融合排序。纯向量容易把精确编号检丢。
2. 检索前过滤租户、权限和有效期，并返回高亮和原文位置，用来做引用。
3. 工具说明、接口文档和运维手册的关键词检索，供路由或人工排障。
4. 对话、工具调用和用户反馈的检索与聚合，用来回放失败案例。

团队已经在运维 ES，并且需要过滤和高亮时，向量可以放在 ES，少一个组件。数据主体是向量、还要细调图索引参数时，用专门的向量库，ES 留关键词和原文。索引近实时刷新，刚写入的切片要等下一次 refresh 才能被搜到；写入路径上频繁 refresh 会拖慢入库。

### 10. MySQL 的事务隔离级别有哪些？它们分别解决了哪些并发问题？

**参考答案**

结论：InnoDB 默认是可重复读。四个级别逐级减少能看见的别人的修改。InnoDB 的可重复读对普通查询使用事务级快照，对当前读使用 next-key lock，已经挡住大部分幻读。

1. 读未提交：可能读到其他事务还没提交的修改。脏读、不可重复读、幻读都可能发生。
2. 读已提交：每条普通查询单独看一份已提交快照，没有脏读。同一事务里两次读同一行，可能因别人已提交而不同；范围查询也可能多出行。加锁读主要锁记录，不锁间隙，外键和唯一键检查仍会用间隙锁。
3. 可重复读：事务里第一次普通查询建立快照，后面的普通查询都看它，读不到之后才提交的修改。`SELECT FOR UPDATE`、`UPDATE`、`DELETE` 走当前读，加记录锁和间隙锁，其他事务插不进已锁住的间隙。SQL 标准里的可重复读并不要求消除幻读；InnoDB 更进一步。先普通查询、再当前读，当前读仍可能看见快照之后提交的新行。
4. 可串行化：在可重复读之上，把普通 `SELECT` 变成共享 next-key lock。`autocommit` 开启时，单条查询仍是一致性读。

脏读是看见未提交的值，不可重复读是同一行前后值不同，幻读是同一条件前后行集合不同。应用先读出余额再写回计算结果时，丢失更新在可重复读下仍会发生。`UPDATE ... SET balance = balance - ?` 或带版本条件的更新，才是在锁内基于当前行计算。

### 11. Java 中如何避免死锁？请举例说明

**参考答案**

结论：死锁要同时有互斥、占有且等待、不可抢占、循环等待。工程里最有效的是所有线程按同一个总序加锁，循环等待就不会出现。

转账是典型场景：一个线程先锁账户 A 再锁 B，另一个先锁 B 再锁 A，就会互相等待。修复是按不变的账户主键排序，先锁编号小的。

```java
public void transfer(Account from, Account to, long amount) {
    long fromId = from.getId();
    long toId = to.getId();
    if (fromId == toId) {
        throw new IllegalArgumentException("same account");
    }
    Account first = fromId < toId ? from : to;
    Account second = first == from ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

所有会同时拿两把账户锁的路径都要遵守这个顺序，包括解冻、冲正。`synchronized` 不能超时，等待可能一直挂着。需要放弃时用 `ReentrantLock.tryLock`：第二把锁超时就放开第一把，回到无锁状态再重试，并在 `finally` 里解锁。锁内不要调外部接口。已经发生的死锁可以用 `jstack` 或 `ThreadMXBean.findDeadlockedThreads` 看谁在等谁。

### 12. 如何设计一个支持多租户的 Agent 平台？

**参考答案**

结论：租户身份来自鉴权结果，并贯穿检索、工具、缓存和日志。模型生成的参数不能决定访问哪个租户。

1. 隔离按规模选。小租户可以共享库，每张表和每个向量都带 `tenant_id`；要求更强时用独立 schema 或独立库。控制面可以共享，大租户的模型额度和向量索引放到单独资源池。
2. 知识库按租户分集合，或在每次检索强制过滤。缓存键、分布式锁键都带租户。漏一个条件就会串数据。
3. 工具执行前，用服务端上下文覆盖租户和资源所属人。模型即便传了另一个租户的 ID，也覆盖掉。
4. 配额按租户计：QPS、并发任务、token、存储。一个租户打满时只限它自己。
5. 文档和密钥按租户加密。提示词、模型、工具白名单做成租户配置，不要写死在全局提示词里。
6. 日志、trace 和账单带租户，排障和计费才能分开。

共享表方案成本最低，前提是代码评审能挡住不带租户条件的查询。独立库隔离更强，迁移和连接池的运维成本也更高。

### 13. Agent 的 Planning 能力指的是什么？在系统中如何实现？

**参考答案**

结论：Planning 是把目标拆成可执行步骤，按观察决定继续、重试或改计划。提示词里写「一步步思考」只影响单次生成，步骤状态要在系统里单独保存。

常见做法：

1. ReAct：思考、行动、观察交替，计划是隐式的。实现成本低，适合步骤数少的任务。必须有最大步数；同一工具、同一参数反复出现就停止。
2. 先计划后执行：先让模型产出结构化步骤，执行器逐步调用工具，失败时只重规划未完成的部分。每步有待执行、执行中、完成、失败。状态落库，进程重启后从失败步继续。
3. 多 Agent：规划者只拆分和收口，执行者只拿本步工具和必要上下文。交接用结构化字段。
4. 会改数据或花钱的步骤先停，等人确认后再执行。

树搜索一类做法调用次数高，适合离线难题，不作为在线默认路径。计划本身也要校验：步骤是否越出工具白名单，输入输出能否接上。
