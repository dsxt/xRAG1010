### 3. Python的GIL是什么，对多线程有什么影响，你写AI服务时怎么处理的

**参考答案**

GIL 是 CPython 里的一把解释器锁。默认构建下，同一进程里同一时刻只有一个线程在执行 Python 字节码。它存在，是因为 CPython 用引用计数管理对象，计数器本身不是线程安全的。

它卡住的是字节码并行，不是 IO。纯 Python 的 CPU 计算开多线程跑不满多核，切换和抢锁还有开销。线程进入阻塞 IO（等网络、等数据库）时会放开 GIL，所以多线程可以重叠等待。`asyncio` 用单线程搅动大量等待，也适合这种负载。NumPy、PyTorch 的重计算多在 C/C++ 里进行，计算期间通常会释放 GIL，和纯 Python 循环不是一回事。

AI 服务可以按这个边界拆：

- 对外 API 保持薄。用异步框架并发等模型接口，事件循环上不做重的纯 Python 计算。
- 按核起多个进程，用进程绕开 GIL。
- PDF 解析、清洗等 CPU 活放进程池。模型推理单独部署，Web 进程只发请求，不把权重加载进来。
- GIL 不保证 `x += 1` 这类复合操作原子。多进程之后，配额和任务状态要落到 Redis 或数据库，而不是进程内变量。

无 GIL 的 CPython 是另一套可选构建，C 扩展要逐个验证。容量方案按「线上默认解释器仍有 GIL」来设计。

### 4. Python里深拷贝和浅拷贝的区别，哪些场景容易踩坑

**参考答案**

浅拷贝只新建最外层容器，里面的子对象仍和原来共享；深拷贝会递归复制子对象。`b = a` 连外层都是同一个对象，并不产生副本。

`list.copy()`、切片、`dict.copy()`、`copy.copy` 都是浅拷贝。`copy.deepcopy` 才会递归，并用备忘录处理循环引用。子对象若都不可变（数字、字符串、不含可变对象的元组），两种拷贝在使用上看不出差别。

容易踩坑的地方：

- 会话消息是「列表套字典」。`history2 = history[:]` 之后改 `history2[0]["content"]`，原始会话一起变。请求模板、多轮历史最常中招。
- 函数默认参数写成 `{}` 或 `[]`，所有调用共享同一对象。
- 配置字典里再嵌一层模型参数，浅拷贝后改温度会污染全局配置。
- 对 Session、数据库连接、Tokenizer、模型做深拷贝，要么报错，要么慢到不能用。该复制的是你拥有的数据。
- NumPy 切片默认是视图，改切片会改原数组；要独立数据就显式 `.copy()`。

跨请求复用的提示模板，每次请求新组装消息列表，不在模板对象上 `append`。

### 5. 讲一下你对LLM的理解，Decoder-only架构的核心流程是什么

**参考答案**

现在工程上说的大语言模型，主体是在大量文本上做下一个 token 预测的 Decoder-only Transformer。它本身不检索、不执行工具，那些是外面的系统。

文本先被分词器切成 token，变成词向量，并带上位置信息（主流是 RoPE），再送入一叠相同的解码层。每层是带因果掩码的自注意力加上前馈网络，外面裹着残差和归一化。因果掩码让位置 i 只能看见 i 以及它左边的 token。训练时，给定前文去拟合下一个 token，损失是词表上的交叉熵。

推理是自回归的：模型给出下一个 token 的分布，按温度、top-p 等策略取出一个，接到末尾，直到结束符或长度上限。工程上用 KV cache 留下已经算过的 Key 和 Value，每一步只算新 token 的 Query，再和缓存做注意力，避免整段重算。

和带编码器的序列模型比，它没有单独的编码器，提示和已生成内容都在同一条因果序列里。面试里补一句：窗口、采样和缓存决定延迟与费用，但决定「说得准不准」的通常是外面的资料、工具和校验。

### 6. RAG的完整流程讲一下，你在项目里怎么做的向量检索

**参考答案**

RAG 是「先取资料，再让模型只根据资料组织回答」。模型的权重不承担客户知识的更新。

1. **入库**：解析文档，去掉页眉页脚和重复，按标题、段落、表格切块，每块带文档名、章节、权限和版本。
2. **索引**：用固定的嵌入模型把块变成向量，连同块 id 和过滤字段写入向量库。原文和状态放在数据库，向量是可重建的派生数据。
3. **查询**：必要时先做查询改写，再用同一个嵌入模型把问题变成向量。模型和归一化方式必须和入库时一致，换模型就要重建索引。
4. **召回**：按租户、权限、知识库版本过滤，取 top-k。过滤要进检索条件；先取 k 条再过滤，结果容易被滤空。
5. **增强**：关键词一路互补，必要时对短名单做重排，再把命中的原文和出处放进提示。
6. **生成与拒答**：要求回答能对上引用；资料不够就拒答。记录问题、命中的块和回答，供以后回归。

讲项目时按这六步说你真实负责的几步：文档从哪来、块大约多长、索引用什么、过滤字段是什么、k 是多少、你怎么发现召回错了。数字和组件名只用你做过的。

### 7. 向量检索为什么比传统关键词搜索更适合语义匹配，有什么短板

**参考答案**

关键词检索（BM25 一类）看词出现了没有、出现得珍不罕见。用户换一种说法、用了同义词或口语，词对不上就召不回。向量检索把问题和文档块映射到同一空间，用距离表示语义远近，所以「退款什么时候到账」可以命中「提现时效说明」这种词面不同的段落。

短板也很明确：

- 编号、错误码、专名、必须原样匹配的短语，语义近邻会把精确命中挤出去。
- 近似最近邻不保证真的找回最近的块。
- 切块把否定、前提和表头切开后，向量表示的是残片。
- 嵌入模型没覆盖客户领域时，距离不能代表业务上的相关。
- 命中原因难解释；权限若在召回之后才过滤，top-k 会被滤空。

所以语义检索适合「说法很多、意思接近」的问题，精确符号仍要关键词。线上一般两路一起召回，再融合。

### 8. Redis在你的AI服务里起什么作用，比如大模型接口的限流和缓存怎么做

**参考答案**

在 AI 服务里 Redis 适合放短寿命、要跨进程共享的状态：限流计数、并发租约、检索缓存、任务心跳。它不替代会话原文和账单。

**限流**：模型接口又慢又贵，要按用户、密钥、模型分别限制。固定窗口用 `INCR` 加过期，实现简单，但窗口交界会放进将近两倍流量。正式环境用一段 Lua 做滑动窗口或令牌桶，把计数、过期和判断放在一次原子执行里。另外对「正在跑的请求数」做租约：占坑时写入带过期时间的标记，请求结束就删；进程崩溃靠过期释放，避免信号量只减不加。超限就快速失败或入队，不把线程堵在模型调用上。

**缓存**分三种，键都要带知识库版本和模型名：

- 嵌入缓存：相同文本不重复算向量。
- 检索缓存：相同问题直接复用块 id，文档一更新版本就变，旧键失效。
- 回答缓存：只缓存温度低、不含个人数据、不触发写操作的重复问题。语义相近就复用答案，只适合容忍近似的 FAQ，阈值要用坏例调，不能拍一个相似度就上线。

缓存和限流、分布式锁不要挤在一个开了淘汰策略的实例里，否则计数器会被当成缓存删掉。

### 9. MySQL的索引你了解多少，如果让你存对话历史表，你会怎么设计

**参考答案**

InnoDB 的默认索引是 B+ 树。主键索引的叶子就是行数据（聚簇）。二级索引的叶子存主键，查到主键后再回表。联合索引遵守最左前缀：范围条件右边的列不能再用于定位，只能在已经定位的范围内做过滤。区分度太低、在列上套函数、隐式类型转换，都会让索引用不上。`EXPLAIN` 看访问类型和扫描行数，小表全表扫描不一定更差。

对话历史拆成两张表，不要把整段会话塞进一个 JSON。

- `conversation`：主键用递增的 bigint 或按时间有序的 id，另有 `user_id`、标题、状态、`updated_at`。列表页用 `(user_id, updated_at)`。随机 UUID 做聚簇主键会让页分裂很厉害。
- `message`：主键、`conversation_id`、角色、正文、token 数、模型名、创建时间、请求 id。联合索引 `(conversation_id, id)`，翻页用 `id` 做键集（`id < 上一页最后一条`），不用大 OFFSET。请求 id 在会话内唯一，用来挡住客户端超时重试插进来的重复消息。

正文用 `utf8mb4`。图片和附件存对象存储，表里留地址。向量不进这张表。历史很长时，热消息留在这张表，冷消息归档。权限以会话行为准，取消息时先确认会话属于当前用户。

### 10. 你用过哪个向量数据库，和Elasticsearch的区别是什么

**参考答案**

先说你真实用过的那一个，以及你用到的能力：过滤、混合检索、按集合隔离，还是只做了单机演示。常见选项有 Milvus、Qdrant、pgvector，也有团队直接用 Elasticsearch 的 `dense_vector`。

专用向量库把近似最近邻当主路径，标量过滤和向量距离是一起设计的，适合向量量大、过滤条件多、还要保住召回的场景。pgvector 的好处是和业务表在同一个事务里，规模上去之后索引和资源要单独评估。Elasticsearch 的本行是倒排、BM25、聚合和现成的运维；向量检索是后加的能力，关键词加语义放在一次查询里比较方便。

差异可以收成三点：

- 向量库的全文和聚合弱；ES 做高维检索时，内存、过滤方式要单独压测，召回不够就两路各自召回再融合。
- 两边都不是事实来源。原文、权限、发布状态放 MySQL，向量库只存能重建的索引。
- 换嵌入模型、换距离定义（归一化之后内积才等价于余弦）都要重建，不能和旧向量混查。

选型时，团队已经长期运维 ES、又强依赖关键词，就不必为了向量再引进一套集群；向量规模和过滤复杂度已经压过 ES，再拆专用库。

### 11. Prompt工程你一般怎么调，有没有一套自己的方法论

**参考答案**

把 Prompt 当成有版本的接口，而不是一段越写越长的说明。可以按这个顺序调：

1. 先写任务、输入、输出和什么样算失败，再写提示词。
2. 系统约束、检索到的资料、用户原话分成三段。资料是数据，不拼进系统提示。
3. 输出定契约：字段、枚举、JSON Schema。能用结构化输出或工具调用，就少靠「请严格按格式」。
4. few-shot 只补格式和少数边界。例子要短，里面的实体会被模型抄进正式回答。
5. 提示词、模型、温度、知识库版本绑在一起留档。比较两次修改时只改一个变量。
6. 用固定坏例集看效果。失败样例补进集子，再改下一版。
7. 分类、抽取、生成拆开。一个提示同时做意图识别、检索和最终文案，坏了无法定位。

温度只在比较提示词时固定住。抽取类放低，需要多样表达时再升高。面试里补上你真实踩过的一次：指令互相打架、例子泄漏、或者提示长到模型忽略中间的约束。方法论的落点是评测集，不是文采。

### 12. 大模型输出不稳定怎么兜底，你在驻场项目里遇到过什么坑

**参考答案**

不稳定分两类：格式飘，和内容飘。格式靠机器兜，内容靠资料和校验兜，不能靠多跑几次碰运气。

格式上，能用 JSON Schema 或工具参数约束就用约束；生成后再用 schema 校验。失败就把校验错误塞回下一次调用，重试一到两次，仍失败就走模板或人工，不再空转。抽取类把温度降到 0。温度和种子只能减少抖动，提供商升级、批处理并行之后仍可能变，所以幂等要做在校验和业务键上。

有副作用的动作（建工单、改数据）必须等完整输出校验通过，并且带上请求 id。流式场景先拼完整、校验，再执行。

驻场里可以讲的坑，用你遇到过的真实那件；没有就讲你准备怎么防：

- 模型把 JSON 包进 markdown 代码块，或混进中文弯引号，解析器直接失败。
- 流在半截 JSON 处断开，下游已经拿半截结果去调了业务接口。
- 现场网络不稳，客户端超时重试，没有幂等键就建出两张单。
- 客户直接改线上提示词，没有版本，第二天效果变了无法对回哪一版。
- 更换模型后，同一套提示的字段开始漂移。

讲的时候点明你加的那一层是校验、幂等还是版本，不要停在「后来稳定了」。

### 13. 手撕算法：LeetCode 最长回文子串。给定一个字符串，找出其中最长的回文子串并返回

**参考答案**

中心扩展：回文都有一个中心，奇数长度的中心是一个字符，偶数长度的中心是两个字符之间。从每个中心向两边扩，记下看到的最长区间。

时间 O(n²)，额外空间 O(1)（结果串另计）。动态规划也是 O(n²) 时间，还要 O(n²) 空间。若面试官要线性时间，再提 Manacher，O(n) 时间、O(n) 空间，手撕优先写中心扩展。存在多个最长时返回任意一个即可。

```python
def longest_palindrome(s: str) -> str:
    if not s:
        return ""
    start = end = 0

    def expand(left: int, right: int) -> tuple[int, int]:
        while left >= 0 and right < len(s) and s[left] == s[right]:
            left -= 1
            right += 1
        return left + 1, right - 1  # 循环多走了一步，缩回来

    for i in range(len(s)):
        for left, right in (expand(i, i), expand(i, i + 1)):
            if right - left > end - start:
                start, end = left, right
    return s[start:end + 1]
```

空串返回空串，单字符返回它自己。偶数中心在末尾时 `right` 越界，循环不会进入，长度比较为负，不会覆盖已有答案。

### 2. 讲一个你做的AI应用项目，从需求到上线的完整链路

**答题思路**

按时间讲一条你真正跟到上线的需求，每一步都说「谁决定的、你交付了什么」。

1. **需求**：客户原话是什么，你把它收成哪一个动作和哪条验收标准。模型做不了的部分当时有没有划出去。
2. **方案**：同步还是异步，知识从哪来，要不要工具，人在哪一步确认。
3. **实现**：接口、任务状态、检索或工具、提示词版本、日志。只深讲你写的那段。
4. **上线**：灰度、失败时用户看到什么、怎么回滚提示词或索引。
5. **上线之后**：一个真实指标或一桩故障，以及你改动的那一层。

链路里主动点出权限、超时和幂等。驻场项目还要说明网络和数据能不能出客户环境，这会决定模型部署在哪。

### 3. Agent 和普通RAG有什么区别，什么场景适合用Agent

**参考答案**

普通 RAG 的路径是写死的：检索，拼上下文，生成，结束。Agent 把「下一步做什么」交给模型：它可以选择检索、调用业务接口、观察结果，再决定继续还是回答。RAG 常常只是 Agent 手里的一个工具。

适合 Agent 的情况：步骤多少取决于中间结果，例如先查工单、发现缺字段、再去另一个系统补、最后才总结；或者需要写操作，而且写之前的参数要靠前一步的查询。适合停在 RAG 的情况：问题能由一批文档直接支撑，路径固定，延迟和费用要稳。

Agent 的代价是延迟、token、不可重复。循环必须有最大步数，写操作必须有服务端鉴权和人工确认。能用一个固定流程写清楚的，就不要为了「更智能」改成自由循环。

### 4. 你用过哪个Agent框架，讲一下它的核心抽象和你觉得哪些设计不好

**参考答案**

先报你真实用过的框架和版本。下面用 LangGraph 这一类「显式状态图」做参照；如果你用的是别的，把名词换成你系统里的对应物。

核心抽象就四件：一份可序列化的状态，一组节点函数，按状态决定下一步的边，以及把状态存下来的检查点。工具调用通常是一个独立节点：模型只产生调用参数，运行时执行后再把结果写回状态。检查点用来恢复、人工插入确认、从某一步重放。

用起来别扭的地方，面试里挑你真实遇到的两件讲：

- 状态里一旦塞了连接、模型对象或巨大的原文，检查点要么序列化失败，要么把存储打满。状态里应该是 id 和短字段。
- 条件边变多以后，业务不变量散落在提示词里，图看起来灵活，回归时不知道哪条边坏了。
- 框架升级改状态字段时，旧检查点对不上新代码。
- 把本可以用代码判断的分支也塞进模型循环，延迟和费用都上去，还更难单测。

可视化编排（各类工作流产品）搭得快，但缺少 diff、单测和代码评审，复杂分支一样难维护。评价设计时，落到「状态清不清、失败能不能重放、确定性步骤有没有被模型包办」。

### 5. Function Calling的原理和流程讲一下，怎么让大模型稳定调用工具

**参考答案**

工具调用不是模型自己去执行函数。应用把工具的名字、用途和参数 schema 发给模型；模型要么给出最终回答，要么给出要调用的工具名和一份参数。应用校验并执行，把结果作为工具消息追加回去，再让模型继续，直到它给出回答或达到步数上限。

以常见的对话接口为例，顺序是：带 `tools` 的请求 → 助手消息里出现 `tool_calls` → 应用执行 → 先原样保留这条助手消息，再追加带同一个调用 id 的工具结果 → 再次请求。助手消息和工具结果必须成对，缺一边接口会直接拒绝，模型也会失去「刚才调用过什么」的上下文。

要稳，约束加在模型和代码两边：

- 工具少而界限清楚，描述里写明什么情况不该用。参数用枚举、必填和类型，少用自由字符串传 id。
- 参数在服务端再校验一遍。模型会编造不存在的单号。错误以工具结果的形式返回，让模型修正，而不是抛成一段无结构的 500。
- 有副作用的工具要幂等，并按当前用户鉴权。模型没有权限这个概念。
- 彼此有依赖的工具不要并行；并行适合互不相干的只读查询。
- 温度放低，限制最大步数和总超时。

稳定来自评测：准备「该调、不该调、参数缺字段、工具报错」四类样例，改提示词或换模型时重放。

### 6. 多轮对话里上下文怎么管理，token超了怎么裁剪，你怎么保证不丢关键信息

**参考答案**

先用这个模型真实的分词器算预算：上下文窗口减去预留的输出，再减去系统提示和工具 schema。后两者每一轮都占位置，历史只能用剩下的那一段。不同库算出来的 token 会有偏差，上线前用实际请求对一下。

裁剪按优先级保留，而不是从最旧的消息机械地砍：

1. 系统提示始终保留。
2. 关键约束另存成结构化槽位：用户明确说过的「不要发邮件」、当前单号、已确认的城市。槽位可以更新，不靠摘要碰运气。
3. 最近几轮原文保留，指代和未完成的追问都在这里。
4. 更早的对话压成滚动摘要。
5. 单条工具结果过长时，状态里留结论和可回查的 id，原文放库。

工具调用和它的结果要么一起留，要么一起删，拆开会让下一轮请求不合法。

边界情况要主动说，这些是追问的高发点：

- 摘要会弄丢否定和限定条件。所以「不能做什么」放槽位，摘要只负责叙事，用户更正后先改槽位。
- 从中间切断代码块或 JSON，模型会把残片当成完整输入。按消息边界切，必要时整段换成「已折叠，id 是多少」。
- 一条工具结果就超过剩余窗口。必须在进模型前截断，并告诉模型这是截断后的结果。
- 用户中途改口，旧摘要还写着旧事实。槽位以最新确认为准，摘要在当次重写。
- 重新生成某一轮时，分清哪一条历史是主干，避免两条互相矛盾的助手回答都留在窗口里。

### 7. Kafka在你的系统里扮演什么角色，比如异步推理任务你怎么用消息队列解耦的

**参考答案**

模型调用经常是几十秒，还可能超时重试。让用户请求堵在这上面，接口线程和上游配额都会被拖死。Kafka 在这里做缓冲：接入层尽快返回，推理在消费者上横向扩展。

一条能落地的链路：

1. 鉴权、校验参数，在数据库插入任务，状态 `pending`，返回 `task_id`。
2. 消息里只放 `task_id`。提示词和附件放数据库或对象存储。Kafka 单条消息通常在 1MB 量级，放大提示词会顶到上限，也会让分区副本变贵。
3. 消费者用条件更新把 `pending` 改成 `running`，更新成功才调模型。成功写结果并改为 `succeeded`；失败按次数重试，超过进入死信，状态 `failed`。
4. 投递是至少一次，消费必须幂等。同一个 `task_id` 不能建两次单、扣两次费。
5. 只有同一会话必须保序时，才用 `conversation_id` 做分区键，并接受一个慢任务堵住这个键后面的消息。没有顺序要求就不要用用户 id 当键，否则热点用户占满一个分区。

先发消息、后写库，崩溃时会出现没有主记录的幽灵消息，或者任务永远停在 `pending`。稳妥的做法是同一事务里写任务和发件箱，再由发件箱投递，投成功才标记已发送。消费者的处理超时要大于模型耗时，否则还在跑就被认为失败，消息重投，同一任务会并发两份。

### 8. RocketMQ延迟消息你用过吗，AI任务超时兜底怎么设计

**参考答案**

用过就说版本和你用它解决的超时；没用过就直接讲状态机，说明延迟消息、定时扫描或 Redis 有序集合都能当闹钟，不把「用过」说满。

RocketMQ 4.x 只有 18 个固定延迟档，从 1 秒到 2 小时。超时时间对不上档位时，投到不短于目标的那一档，消费时再核对任务自己的 deadline。5.x 可以指定投递时间。

超时兜底是一个状态机，不是把 HTTP 超时调大：

1. 提交任务时写 `running` 和 deadline，并投递一条到期检查消息。
2. 正常完成用条件更新 `running → succeeded`。
3. 检查消息到达时，若仍是 `running` 且已过 deadline，条件更新为 `timeout`，通知用户，能取消上游调用就取消，减少空转费用。
4. 迟到的成功结果再次条件更新时会失败，结果丢弃或记到旁路日志，不能覆盖 `timeout`。

重复的检查消息靠条件更新变成空操作。时钟以数据库时间为准。只依赖消费者进程的超时会和「消息重投」缠在一起，业务超时必须是任务上的一个字段。

### 9. Elasticsearch和向量库混合检索你做过吗，怎么把BM25和向量得分融合

**参考答案**

做过就按你的参数讲；没做过就讲这套可以落地的做法，并说明融合权重必须用标注集调，不能现场编一个比例。

BM25 的分和向量相似度不在一个尺度上，也不能跨查询比较，直接加权相加不稳定。优先用倒数排名融合（RRF）：两路各自排序，文档得分是 `Σ 1 / (k + rank)`，`k` 常用 60。只出现在一路里的文档仍然有分。`k` 越大，名次差异被压得越平。

流程：

1. 关键词一路、向量一路各自取几十条，过滤条件（权限、知识库、版本）两路都带上。
2. 用 RRF 合成短名单。若用归一化后的加权和，也是在这一批候选里做 min-max，再按评测集定权重；精确编号类问题提高关键词那一路的话语权。
3. 名单仍偏长、延迟允许时，用交叉编码器重排前几十条，再把前几条放进提示。重排模型看的是原文对，不是融合分本身。
4. 同一文档的多个块要去重或按父文档聚合，避免提示里四条都来自同一段。

融合解决的是「两路谁更靠前」，解决不了两路都没召回到。评测时分着看：编号类、改写类、两路都该中的类。ES 新版本可以在服务端做 RRF，应用层自己融合也一样，关键是候选集和过滤，不是接口长在哪。

### 10. 大模型幻觉问题你在项目里怎么处理的，光靠Prompt够不够

**参考答案**

光靠 Prompt 不够。提示词可以提高「只根据资料回答、没有就说不知道」的比例，模型仍然可以无视，而且说得很确定。

按层处理：

1. **检索**：多数胡编是资料没取到，模型用先验补上。先看切块、混合召回和重排，而不是先把提示词写得更凶。
2. **拒答**：放进提示的资料里没有依据，就返回固定的「不知道」，不要让它用常识补客户的制度、价格和日期。
3. **工具**：库存、金额、时间计算走数据库和代码。模型负责组织工具返回的结果。
4. **校验**：回答里的数字、单号、专名要能在引用块里找到原文。对不上就重试一次或拒答。
5. **评测**：集子里同时放「有答案」和「应该拒答」。只看有答案的题，系统会靠编造拿高分。

Prompt 管态度和格式，事实靠检索、工具和校验。高风险动作即使回答看起来有引用，也要人确认后再执行。

### 11. 流式输出你怎么实现的，SSE 还是 WebSocket，后端怎么和前端配合

**参考答案**

普通对话用 SSE 就够：服务端按 token 往下推，浏览器走 HTTP，认证、网关和重试都成熟。WebSocket 是双向的，适合生成过程中客户端还要持续上传的场景，例如语音帧、协作编辑，或者你需要一条自己设计的中断通道。只为了「停止生成」不必上 WebSocket，HTTP 请求用取消信号就能中断。

后端以异步生成器读取模型的流，按 SSE 写出：

```text
data: {"delta": "你"}

: ping
```

空行才是事件边界。心跳用注释行，避免中间代理把空闲连接掐掉。响应头关掉缓存，并告诉反向代理不要缓冲（例如 `X-Accel-Buffering: no`）。应用自己的访问日志中间件也不要先把 body 读完再转发。

结束时给一个明确的完成事件，流中途失败给错误事件，不要把半截内容标成成功。前端用 `fetch` 读流并增量渲染。`EventSource` 只支持 GET，带不了常见的 JSON 请求体，所以对话接口多用 `fetch`。用户点停止就 abort，服务端收到断开后取消上游模型请求，否则人走了还在计费。

持久化放在流正常结束之后：库里的助手消息是完整正文。断开时界面保留已显示的半截，并标明未完成，不把半截写成成功记录。

### 12. 你在驻场时客户要一个AI功能但模型能力不够，你怎么应对

**参考答案**

先把「不够」变成一批样本上的失败，再决定收范围、换架构，还是明确不做。

1. 让客户拿出真实例子，而不是一句「要能智能处理」。几十条就够看出失败集中在抽取、计算、还是根本没有资料。
2. 拆开哪些步骤是规则、查询、检索、模型草稿、人工确认。精确计算和权限判断留在代码里。
3. 当场用这批例子跑一版，把错例分类给客户看：缺数据、模型不会、还是需求本身有两种正确答案。
4. 能力差距来自「没有可靠资料或工具」时，先补资料或接口。差距来自模型做不到的确定性，就把产品收成草稿加人工确认，或者本期不做自动办理。
5. 验收写下来：覆盖哪些例子、哪些情况必须拒答、谁对最终结果负责。驻场最容易在口头承诺里把演示说成全自动。

面试里用你的真实例子讲到第 4 步的决定。对方要听的是你敢不敢在现场把做不到说清楚，以及说完你给了什么替代。

### 13. 手撕算法：LeetCode 全排列。给定一个没有重复数字的集合，返回其所有可能的全排列

**参考答案**

回溯：路径里一位一位地选还没用过的数，选满就收集一份副本，然后撤销选择。题目保证元素互不相同，不需要排序去重。如果以后出现重复元素，要先排序，并在同一层跳过相同的值。

时间 O(n × n!)，因为一共 n! 个排列，每个复制进结果要 O(n)。递归栈和 `used` 是 O(n)，结果本身是 O(n × n!)。

```python
def permute(nums: list[int]) -> list[list[int]]:
    result: list[list[int]] = []
    path: list[int] = []
    used = [False] * len(nums)

    def dfs() -> None:
        if len(path) == len(nums):
            result.append(path.copy())
            return
        for i, value in enumerate(nums):
            if used[i]:
                continue
            used[i] = True
            path.append(value)
            dfs()
            path.pop()
            used[i] = False

    dfs()
    return result
```

`used` 按下标标记，不按值标记，这样和「有重复元素」的变体是同一套结构。空数组得到 `[[]]`，与「零个位置的一种排法」一致；这道题的常规输入长度至少为 1。

### 2. 讲一下你对大模型应用落地的整体判断，哪些场景是真需求哪些是伪需求

**参考答案**

真需求是已经在发生的语言劳动：频率高，错了的代价说得清，而且有资料或工具能撑住。伪需求是没有样本、没有验收，或者用查询和规则就能做完，却想加一个「什么都能问」的入口。

用客户最近的真实记录来判，几十条就够，不用等一个完整平台：

1. 这件事现在是不是人在做，做一条要多久，一天有多少条。
2. 错一次会发生什么。文案可以改，账、权限、生产配置不能让模型直接改。
3. 输入是不是不稳定的自然语言。字段齐全的查询、对账和计算，放在数据库和代码里。
4. 知识和规则有没有来源。没有文档、没有接口，模型只能靠先验猜客户制度。
5. 使用者能不能接受草稿加确认。既不能出错、又没有校验器，就先不要承诺自动办理。

常见的真需求：对着客户自己的文档问答、从长文本里抽字段、生成必须由人再改的草稿、调用已有系统查数再总结。常见的伪需求：替代审批流、替代权限、举不出十个真实问题的「智能助手」。

落地时把范围收成一条链，写上拒答条件和人工节点，用这批样本做上线门槛。

### 3. 你做过AI应用的效果评测吗，怎么量化一个RAG系统的好坏

**参考答案**

检索和生成分开量。只看最终回答对不对，就不知道该改切块、索引还是提示词。

离线固定一份标注集，至少覆盖：事实问答、要拼多段才答得上的问题、应该拒答的问题、客户的编号和黑话。

- 检索看两件事：前 k 条里是否至少命中一条相关切片，以及相关切片被找回的比例（Recall@k）。k 用你真正放进提示词的条数。排序再看 MRR 或 nDCG。
- 生成：有标准答案的看正确率；还要看论断是否都能在引用切片里找到（忠实度），以及该拒答时有没有拒答。
- 引用：数字和专名要和切片原文一致，不是同义改写就算过。

抽一部分人工标注，用来看「让另一个模型当裁判」偏在哪里。改切分、嵌入、提示词或模型，跑同一套集子再上线。

在线看采纳或点踩、重新生成率、空检索率、人工接管率，并按知识库版本拆开。坏例分成检索错、不忠实、该拒答没拒、格式错，回流进集子。集子里如果没有「不该答」的题，系统靠编造也能显得分数很高。

**参考答案**

用数据能不能出域，加上你们自己的评测集来选。公开榜单只用来把候选缩到两三个，不作为上线依据。

1. **边界**：驻场数据经常不能出客户网络。不能出域，公有云 API 就排除，改成可私有化部署或客户已经买进内网的模型。开源权重的协议要逐个核对能不能商用、能不能改，不看宣传页。
2. **能力**：在自己的集子上看中文、工具调用是否稳定、结构化输出、长上下文的实际利用率。参数量不进入结论。
3. **费用**：按「一次成功任务」算，把重试和多步调用算进去，不按标价的每百万 token 单独比。
4. **运维**：开源要算 GPU、量化之后的效果损失、推理服务和值班。vLLM、SGLang 这一类是服务方式，不是选型理由。商用 API 省运维，同时带来限流、调价和模型下线。
5. **组合**：数据允许的前提下，难回答走效果更好的模型，分流、改写、抽取走更便宜的模型。路由写在代码里，两个模型都进同一套评测。

换模型是一次发布：提示词版本、评测结果和回滚方式一起走，不在驻场环境里临时改个模型名。

### 5. 你在项目里怎么控制大模型调用成本，有没有做过token优化

**参考答案**

按完成一次有效任务的成本来看，不按单次调用的 token 自嗨。先打点，再动刀：每个功能记下模型、输入和输出 token、重试次数、是否被用户采纳。没有这张表，就不知道该砍提示词还是砍重试。

有效的手段：

- **分流**：分类、改写、抽取用小模型；只有开放式生成或分流判不准的才走大模型。
- **上下文**：知识走检索，不把整本手册贴进提示。提供商若按稳定前缀缓存计费，前缀就要逐字节稳定，把变化的日期和用户问题放在后面。
- **输出**：限制 `max_tokens`；下游是程序就返回 JSON，不返回散文。
- **历史**：按窗口裁剪，工具结果留 id。
- **缓存**：温度低、不含个人信息、不触发写操作的重复问题可以精确缓存。语义缓存只用于低风险 FAQ，键里带知识库版本。
- **停损**：检索为空就不要再付一次大模型；重试有上限。嵌入请求能批量就批量。

换更便宜的模型之前，用同一评测集看成功率。token 降了、人工返工涨了，任务成本可能更高。Agent 的步数上限通常比提示词措辞更影响账单。

### 6. Prompt注入攻击你了解吗，你的系统里怎么防护

**参考答案**

提示注入是把「指令」混进模型本来当作「数据」的文本里，诱导它改目标、泄露系统提示或调用不该调用的工具。一种来自用户输入，一种来自检索到的网页和文档。RAG 系统更要防第二种，因为恶意句子是你自己取回来交给模型的。

防护放在权限边界上。提示词里写「不要听从用户」只能降低概率。

1. 系统提示只来自你的模板。用户文本和检索片段放在单独的数据区，不拼接进系统角色。
2. 模型没有权限。发邮件、改数据、跑命令由服务端按当前用户鉴权；工具参数做类型和白名单校验；SQL 和 shell 不拼接模型输出。
3. 敏感动作给人确认。确认页上展示的是服务端解析后的参数。
4. 工具结果和网页同样不可信，下一轮会把里面的指令再带回来。对模型来说它们仍是数据。
5. 系统提示和工具描述里不放密钥、连接串和别人的隐私。
6. 评测集里放一组注入样本，断言没有越权工具调用、没有把系统提示原样吐出。

对检索文本做关键词过滤，只能减少一些直白样本，不能当成安全边界。

### 7. Redis的缓存淘汰策略你了解哪些，AI场景下你一般选哪个

**参考答案**

内存达到 `maxmemory` 后，Redis 按 `maxmemory-policy` 决定怎么办。默认是 `noeviction`：需要新内存的写命令失败，读仍然可以。其余策略分两类：只淘汰设了过期时间的键（`volatile-lru`、`volatile-lfu`、`volatile-ttl`、`volatile-random`），或在全部键里淘汰（`allkeys-lru`、`allkeys-lfu`、`allkeys-random`）。LRU 看最近使用，LFU 看使用频率；Redis 的 LRU/LFU 是采样近似，不是全量精确排序。`volatile-ttl` 优先淘汰更快过期的键。过期删除和内存淘汰是两套机制。

AI 场景把实例拆开用：

- 嵌入缓存、检索缓存、FAQ 缓存：独立实例，`allkeys-lru` 或 `allkeys-lfu`，键上再带 TTL。热点问题很集中时 LFU 更合适；访问比较平均就用 LRU。
- 限流计数、分布式锁、任务租约：`noeviction`。这些键被删掉，表现为超卖、锁丢失或任务状态错乱，而不是「缓存没命中」。

如果缓存选用 `volatile-lru`，却有键忘了设 TTL，那些键永不淘汰，内存会被它们撑满，然后写入失败。缓存实例上的键一律带过期时间，或者直接用 `allkeys-*`。

### 8. MySQL和向量库的数据一致性怎么保证，比如知识库更新了向量怎么同步

**参考答案**

向量是派生索引，原文、切片和发布状态以 MySQL 为准。不要两边同时当主库，也不要在请求线程里同步写完就算完成。

更新一个文档时：

1. 事务里写入新版本切片，状态为待索引；旧版本保持可检索。同一事务写发件箱。
2. 异步任务按切片算嵌入，按 `chunk_id` 写入向量库。载荷带上版本号和嵌入模型名。
3. 写入成功后，把 MySQL 里的已发布版本切到新版本。检索条件带「当前已发布版本 + 当前嵌入模型」，旧向量还在也不会被查到。
4. 再按 `chunk_id` 删除旧向量。顺序反过来会出现一段空窗。

进程死在中途就重试发件箱。条件写保证同一文档的旧任务不会把新版本盖回去。定期对账：MySQL 里已发布的切片，向量库必须有同一模型的向量；向量库里多出来的 id 删掉。

更换嵌入模型时新建一份索引，全量重建，评测通过后再切读取用的别名。在旧索引上覆盖，查询会在一段时间内混到两种空间的向量，距离没有意义。

### 9. 你做过的AI功能里，哪个上线后效果最差，你怎么复盘和改进的

**答题思路**

讲一件能对上时间线的真事。效果差，是指上线后的指标，不是你最不喜欢的技术。

1. 功能上线前怎么验收的。如果只看了演示，就直接说当时没有集子。
2. 哪个数不好：使用率、采纳率、人工接管、投诉、延迟或费用。给数量级，用你记得住的口径。
3. 原因落到一层：需求本不该自动做、资料质量、检索、提示词、模型、界面让用户以为它一定对。
4. 你改的是哪一层，用同一批坏例怎么回归。改完仍差，就说你最后怎么收的范围。
5. 收在「下次上线前会先补上的那一项」。

原因里留你自己的决定，例如当时没做拒答、没看检索命中。只说模型和客户的问题，这题就结束了。

### 10. 最近在学什么新技术，你是怎么判断一个AI新框架值不值得跟的

**答题思路**

先说你最近真在用的那一块，最好和你的项目痛点连着：评测、检索、推理服务、编排，选一个能讲出「读了什么、做了什么小试验」的。

判断一个新框架值不值得跟，按这个顺序：

1. 它解决的是不是你现在的痛：状态难恢复、回归跑不起来、检索不稳、账单看不懂。只是换了一层 API 名字，就停在观望。
2. 抽象里有没有状态、失败、观测和测试的位置。只有「一句话生成一个 Agent」，先放一放。
3. 用一两天接到你的一条真实链路上看。比通读发布演示有用。
4. 看维护和锁定：破坏性变更多不多、许可证、是不是必须绑一家云、出了问题能不能在本地把一次调用重放出来。
5. 给出采用、观望或不跟，并说出你因此少做的那件事。

学习节奏也顺手讲清：跟着线上问题读对应文档和源码，保留一个能重复跑的小样本。框架会很多，样本和评测集可以留很久。

### 11. 你平时用什么AI工具辅助编码，Copilot还是Cursor,真实体验怎么样

**答题思路**

说你真正常开的那个，以及客户网络允不允许它出域。很多驻场环境不能把仓库发到公有云，这时答案就是「现场不用」或「只用内网允许的」，这个回答是加分，不是落后。

可以按这个结构讲体验：

1. **补全类**（Copilot 这一类）适合当前文件里的样板、测试草稿、熟悉的框架用法，打断少，也容易在你没注意时把一个相近但不对的 API 补进去。
2. **带仓库上下文的对话和多文件修改**（Cursor 这一类）适合跨文件改动和陌生代码，改动面大。真实体验要包括：你怎么看 diff、怎么跑测试、哪些目录不让它动。
3. 讲一个它帮你省时间的例子，再讲一个它写得很自信但错了的例子：边界、并发、权限、和业务语义有关的条件。关键逻辑是你自己写的。
4. 工具生成的代码同样走评审。密钥和客户数据不进提示。

不要把工具讲成产能数字。面试官要听你有没有复核习惯。

### 12. 手撕算法：LeetCode 零钱兑换。给定不同面额的硬币和一个总金额，求凑成总金额所需的最少硬币个数

**参考答案**

完全背包。`dp[x]` 表示凑出金额 x 的最少硬币数。`dp[0] = 0`。枚举硬币，内层金额从小到大，保证一枚硬币可以重复使用：`dp[x] = min(dp[x], dp[x - coin] + 1)`。凑不出时保持不可达。

时间 O(金额 × 硬币种类)，空间 O(金额)。贪心（每次拿不超过剩余金额的最大面额）不正确，例如面额 1、3、4，金额 6：贪心先拿 4，共 3 枚；最优是两枚 3。

LeetCode 这题在凑不出时返回 -1，金额为 0 时返回 0。

```python
def coin_change(coins: list[int], amount: int) -> int:
    if amount < 0:
        return -1
    inf = amount + 1  # 面额至少为 1 时，可行解不会超过 amount 枚
    dp = [inf] * (amount + 1)
    dp[0] = 0
    for coin in coins:
        if coin <= 0:
            continue
        for x in range(coin, amount + 1):
            if dp[x - coin] + 1 < dp[x]:
                dp[x] = dp[x - coin] + 1
    return dp[amount] if dp[amount] <= amount else -1
```

也可以看成从 0 出发、每次加上一种面额的无权图，求到 `amount` 的最短路，复杂度同阶。手撕用上面的一维 DP 更直接。

## HR面

### 1. 自我介绍

**答题思路**

一分钟，少用框架名。对方要判断沟通和稳定性，不是再面一道 RAG。

1. 年限、现在做的方向、驻场或项目制经历（有就说）。
2. 一段业务结果：你帮客户把哪件重复的事做成了可上线的功能，人在流程里的哪一步。
3. 为什么看中软这种岗位：你想继续做 AI 应用交付，并且接受客户现场的工作方式。

口语化，讲完留一个对方好接的点，例如「我最近两年主要在客户现场做这块」。

### 2. 你为什么从之前的工作看AI方向，是怎么转过来的

**答题思路**

讲一条真实的转折，不讲风口。

1. 原来的工作给你留下了什么：接口、数据、排障、和业务对需求。这些就是应用开发要的底子。
2. 转折点：哪一次需求让你开始做模型调用、检索或评测，你负责的是哪一段，做成了没有。
3. 为什么是应用而不是算法研究：你关心的是把能力嵌进现有系统、对上验收。
4. 为什么现在看机会：原环境能做的 AI 工作到了头，或你希望这条链路归你负责。对前公司只讲事实。

薪资可以后面再说，这一题不拿涨薪当主要动机。

### 3. 对中软这种驻场外包模式，你怎么看

**答题思路**

先表明你知道这个模式是什么：人在客户现场，需求和数据规则以甲方为主，考核常常同时看公司和客户。

然后分两面讲，都用你的真实偏好：

- 你认的部分：业务近，方案能不能用很快见分晓，沟通和边界会被迫练出来。
- 你在意的部分：项目切换时技术上下文会断；你希望仍然对方案和代码负责，而不是只按人天填位置。

接着问清楚：这个岗位是长期跟一个客户，还是短周期轮转；离场时代码和文档留在哪。态度落在「接受驻场，同时看重交付的完整度」，不评价这个行业高不高。

### 4. 现在薪资什么情况，期望多少

**答题思路**

数字只用你自己的真实情况，现场不编竞争对手的 offer。

1. 先确认职级、驻场城市、驻场补贴、项目奖金、加班怎么计算、社保公积金在哪个城市缴。这些会改变总包，先问再报价。
2. 按总包说现状：月薪区间、浮动或年终大概占多少，不报一个含糊的「综合」。
3. 期望给一个范围，并说明可以随职责和驻场强度调整。底线和目标自己事先算好，只在对方进入具体讨论时说。
4. 对方先给范围，就对着范围谈差距来自哪里（城市、值班、补贴），不在 HR 面临时改口加码。

还没问清驻场补贴之前，不把一个裸月薪当成结论。

### 5. AI这个方向变化很快，你压力大吗，怎么保持学习的

**答题思路**

承认变化快，同时给出你已经在用的节奏，不说「我很热爱学习」。

1. 压力来自哪：你在意的是线上效果和客户验收，不是每一个新框架的名字。
2. 固定动作：每周留一段不被会议吃掉的时间，只跟当前项目的一个问题，读对应文档或源码，留一个能重跑的样本。
3. 取舍：和现在的检索、评测、成本无关的发布，先记下来，不占用当周。判断标准可以和三面那题一致，这里用大白话再说一遍。
4. 怎么知道自己没掉队：你能把新东西放进现有评测里比较，而不是演示能跑。

补一句可持续的做法：工作日有截止时间，证书和课程只在它们直接服务当前项目时才上。长期靠熬夜追更新，讲出来不可信。

### 6. 驻场如果客户那边节奏很紧、经常加班赶AI功能，你能接受吗

**答题思路**

接受阶段性的上线和故障支持，同时把「经常」问清楚。

1. 态度：交付节点你会在，驻场本身就包含配合客户节奏。
2. 你想了解的事实：近两个月加班多不多、是否有调休或补贴、紧是因为上线窗口还是需求没有收口。
3. 你的做法：模型做不到或资料没到的功能，会先拿出样本和客户对齐，从这一期拿掉或改成人工确认，而不是只靠加时间硬赶。
4. 边界：可以讲你能接受的强度（例如上线前两周），这个数字按你的真实底线说。长期没有补偿、也没有范围的赶工，你会在当期就提出来，而不是离职时才说。

不要回答「加班越多越好」，也不要把「完全不加班」说成原则。HR 要的是可靠，加上你不会用加班掩盖做不到的需求。

### 7. 有什么想问我们的

**答题思路**

问 3 个左右，技术面已经结束，就问交付方式和考核。从下面挑和你决定有关的：

1. 这个组的 AI 需求是客户已有项目，还是从传统开发往过迁？验收是客户的业务负责人说了算吗？
2. 这个级别进场后，是负责一条功能从方案到上线，还是按人天补进现有组？
3. 代码、评测集和线上日志的权限在公司还是在客户？人离场之后沉淀留在哪？
4. 绩效更看客户评价、交付节点，还是线上指标？
5. 驻场城市、补贴和近期加班的实际情况，如果前面没谈清，放在最后问。

先听回答再决定要不要追一句。不问「你们公司好不好」，也不把这一题变成第二轮技术面。
