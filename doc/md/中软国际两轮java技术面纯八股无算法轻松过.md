### 3. ArrayList 和 LinkedList 的区别及各自适用场景

**参考答案**

列表的默认选择是 ArrayList。LinkedList 是双向链表，按下标访问要沿链表走，适合已经在遍历中改结点，或只在头尾当双端队列用。

ArrayList 把元素放在 `Object[]` 里。无参构造起初是空数组，第一次加入才扩到 10，之后大约按 1.5 倍增长并拷贝。按下标读和改是 O(1)，尾部追加均摊 O(1)。中间插入或删除要搬移后面的元素，是 O(n)。内存连续，顺序遍历对缓存友好。它不是线程安全的，迭代时结构被改会快速失败。

LinkedList 的结点保存元素、前驱和后继，并实现了 Deque。头尾增删在已有首尾指针时是 O(1)。`get(i)` 会从离下标更近的一端数过去，按下标插入也要先走到那里，都是 O(n)。每个元素多一个结点对象和两根指针。

查询和尾部追加用 ArrayList。只在头尾增删、又要当队列或栈时，用 ArrayDeque 通常更合适。LinkedList 适合遍历过程中按迭代器删除当前结点。读多写少、又要线程安全的列表，用 CopyOnWriteArrayList，那是拷贝数组，和链表无关。

### 4. ConcurrentHashMap 在 JDK 1.8 中如何保证线程安全，与 Hashtable 的区别

**参考答案**

JDK 1.8 的 ConcurrentHashMap 把锁粒度放在单个桶上：空桶用 CAS 放入头结点，桶里已有结点时用 `synchronized` 锁住头结点再写入。Hashtable 则给每个公开方法加同一把对象锁，读写都锁整张表。

JDK 1.8 取消了 1.7 的分段锁。结构是数组加链表，链表长度达到 8 且数组长度达到 64 时，该桶树化成红黑树。数组更小时只扩容，不树化。扩容拆分时，桶里结点数不超过 6 会退回链表。`get` 不加锁，靠数组和结点引用的 volatile 读到已经发布的写。扩容时多个线程可以协助迁移，读会顺着转发结点找到新表。计数用类似 LongAdder 的分段计数，并发更新时 `size` 是近似值，避免一把全局计数锁。

两者都不允许 null 键或 null 值。ConcurrentHashMap 的迭代器是弱一致的，遍历时遇到并发写入也不会抛 ConcurrentModificationException。它的锁只挡住同一个桶上的写，不同桶可以并行。Hashtable 一次只允许一个线程进入整张表，迭代过程中表结构被改掉会快速失败。

### 5. synchronized 和 ReentrantLock 的区别，什么场景下用哪个

**参考答案**

两者都是可重入的互斥锁，默认都是非公平的。临界区就是一个代码块、希望异常时自动放开时用 `synchronized`；需要超时、可中断、公平策略或多个等待条件时用 ReentrantLock。

`synchronized` 由 JVM 实现，锁状态在对象头。竞争轻时用轻量级锁，靠 CAS 把 Mark Word 指向当前栈上的锁记录；竞争加剧时膨胀成重量级锁，线程进入监视器队列。偏向锁在 JDK 15 默认关闭，后续版本已移除。它锁的是代码块或方法，退出或抛异常都会释放。等待和唤醒用 `wait` / `notify`，一个对象上的等待线程共用这一套队列。正在等这把锁的线程不能被中断打断。

ReentrantLock 基于 AQS，用 state 记重入次数。`lock()` 默认非公平，构造参数可以要公平锁。`tryLock` 能立刻返回或带超时，`lockInterruptibly` 在等待时响应中断。一把锁可以建多个 Condition，按条件分组唤醒。必须在 `finally` 里 `unlock`，漏掉就不会随异常自动释放。

读多写少再考虑读写锁。公平锁会降低吞吐，只在确实要避免饿死时打开。

### 6. 线程池的核心参数有哪些，工作流程是什么

**参考答案**

`ThreadPoolExecutor` 的七个参数是核心线程数、最大线程数、空闲存活时间及单位、工作队列、线程工厂、拒绝策略。提交顺序是先补核心线程，再进队列，队列满了才把线程扩到最大数。

工作线程数小于核心数时，即使已有核心线程空闲，也会新建核心线程执行。核心数已满，任务进入队列。队列放不下，且线程数还小于最大数，再创建非核心线程。线程数已经到最大、队列也满，才走拒绝策略。默认 AbortPolicy 抛 `RejectedExecutionException`。CallerRunsPolicy 交给提交任务的线程跑，DiscardPolicy 直接丢弃，DiscardOldestPolicy 丢掉队列头部再尝试提交一次。

空闲时间默认只回收超出核心数的线程。`allowCoreThreadTimeOut` 打开后，核心线程空闲也可以回收。

无界队列时最大线程数基本用不上，任务会一直堆在内存里。`SynchronousQueue` 不保存任务，没有线程正在取的时候入队会失败，线程数就会往最大数扩。缓存线程池是这种配法，而且最大数很大。固定大小的池如果配了无界队列，拒绝策略也几乎不会触发。

### 7. JVM 内存区域划分，堆里新生代和老年代的区别

**参考答案**

HotSpot 从 JDK 8 起，线程私有的是程序计数器、虚拟机栈和本地方法栈；线程共享的是堆，以及用本地内存实现的元空间。程序计数器是规范里唯一不会抛 OutOfMemoryError 的区域。

虚拟机栈的每个栈帧放局部变量表、操作数栈、动态链接和返回地址。栈深超过线程栈大小会 StackOverflowError，栈扩展失败会 OutOfMemoryError。堆上放对象实例和数组，字符串常量池也在堆里。类的元数据在元空间，元空间默认不设上限，类加载过多会占满本地内存。NIO 的直接内存同样在堆外。

新生代放新分配的对象，收集频繁，单次通常较短，用复制算法。分代布局是一块 Eden 和两块 Survivor，Minor GC 把存活对象复制到另一块 Survivor，年龄加一。老年代放活得久的对象，收集次数少，单次停顿可能更长。年龄上限通常是 15，G1 会在这个上限里动态决定何时晋升；Survivor 空间不够时也会提前晋升。

G1 不再把堆切成固定的两块物理区域，而是等大的 Region，年轻代和老年代各是一组 Region。超过 Region 一半的对象进入 Humongous Region，算在老年代一侧。

### 8. GC 算法有哪些，你了解 CMS 和 G1 吗

**参考答案**

常见算法有三种。标记-清除先标出存活对象再清掉死亡对象，会留下碎片。标记-复制把存活对象拷到空闲区，没有碎片，要留出一块空区域，新生代常用。标记-整理把存活对象挪到一端，没有碎片，移动对象时要停顿，老年代常用。判断存活从 GC Roots 出发，包括栈上引用、静态变量、JNI 引用和同步监视器等。

CMS 是面向低停顿的老年代收集器，JDK 9 废弃，JDK 14 移除。过程是初始标记（停顿，只标 Roots 直接引用）、并发标记、重新标记（停顿，补上并发期间的变化）、并发清除。它走标记-清除，碎片多了会出现并发模式失败，再退化成整堆压缩，停顿会很长。并发阶段还和业务抢 CPU，清除时产生的浮动垃圾要等下一次回收。

G1 从 JDK 9 起在服务端机器上是默认收集器。堆分成 Region，优先回收垃圾比例高的 Region。年轻代收集复制存活对象；并发标记之后的混合收集，会挑一部分老年代 Region 一起收。停顿主要发生在复制存活对象时，默认停顿目标是 200 毫秒，用来限制单次回收量。复制能避免 CMS 那种碎片。腾不出空间时会 Full GC，JDK 10 之后这次 Full GC 是并行的。要更低停顿可以显式开 ZGC，它不是默认收集器。

### 9. MySQL 事务的 ACID 指什么，InnoDB 默认隔离级别是什么

**参考答案**

ACID 是事务要同时满足的四项。InnoDB 的默认隔离级别是可重复读（REPEATABLE READ）。

原子性指同一事务里的修改要么全部提交，要么全部撤销，InnoDB 用 undo 做回滚。一致性指提交之后主键、外键和业务不变量仍然成立；数据库负责约束，转账两边平衡这类业务等式要靠事务里的语句一起写对。隔离性指并发事务按隔离级别决定彼此能看见什么，靠锁和 MVCC。持久性指提交成功之后崩溃也不丢，InnoDB 用 redo 做预写日志，提交时按刷盘策略把日志写下去。

可重复读下，同一事务里的普通查询看到同一份快照，读不到别的事务尚未提交的修改，也读不到快照建立之后才提交的新版本。Oracle、SQL Server、PostgreSQL 常见默认是读已提交，不要把别的库的默认级别说成 MySQL 的。当前读怎样抑制幻读，放在 MVCC 和行锁里讲。

### 10. 索引底层为什么用 B+ 树不用 B 树，什么情况下索引失效

**参考答案**

InnoDB 用 B+ 树，是为了让同样大小的页装下更多键，树更矮，磁盘读更少，同时让范围扫描只沿着叶子走。

B+ 树的非叶子结点只存键和子页指针，整行数据都在叶子。叶子按顺序串成链表，范围查询顺着叶子扫。B 树的内结点也存数据，范围扫描要在不同层之间跳。聚簇索引的叶子是整行，二级索引的叶子是主键，走二级索引后往往再按主键回表。

所谓索引失效，多数是优化器认为全表或另一条路径更便宜。常见情况有：对索引列做函数、计算，或把字符串列和数字比较，导致转换发生在列上；`like '%xx'` 这种前导模糊；联合索引没用上最左前缀；列区分度很低；`or` 两侧不能各自用上索引。不等于和 `not in` 经常扫掉很大一段，优化器可能放弃索引。`is null` 在列上有索引时是可以用索引的。MySQL 8.0 可以对表达式建函数索引，让原来套函数的条件重新走索引。

最终以 EXPLAIN 的 `type`、`key` 和 `rows` 为准，不要凭写法直接认定一定没走索引。

### 11. Redis 支持哪些数据类型，分别用在什么场景

**参考答案**

基础类型有五种，另外几种是在它们之上的专门结构。选型看要不要按字段改、要不要去重、要不要顺序。

String 用来做缓存对象、计数（`INCR`）、分布式锁的占位和简单的会话。单个字符串最大 512MB。Hash 用来存对象的多个字段，可以只改一个字段，适合用户资料这类结构。List 用来保留最新的一段记录，或做简单的一侧进一侧出；它没有确认和重试，不能代替消息队列。Set 用来去重、求交并差，例如标签和共同关注。ZSet 用分数排序，适合排行榜，也可以把分数当成时间做延迟队列。

Bitmap 适合签到和按位统计，HyperLogLog 适合允许误差的 UV 估算，Geo 适合附近的人。Stream 带消费组，比 List 更接近日志型队列。小对象会用紧凑编码，元素变多或变大后转成哈希表或跳表，具体阈值随版本变化，面试时讲清会变即可。

### 12. Redis 持久化 RDB 和 AOF 的区别，你们生产用哪种

**参考答案**

RDB 是某一时刻的数据快照，文件小、恢复快，两次快照之间宕机会丢掉这一段写入。AOF 记录写命令，丢数据的窗口更小，文件更大，重放恢复更慢。

RDB 一般用 `BGSAVE`：主进程 fork 出子进程写临时文件，利用写时复制，再替换旧文件。fork 本身有开销，快照期间的新写入不会进这个文件。AOF 把命令追加到日志。`appendfsync` 为 `always` 时每次写都刷盘，最慢也最稳；默认是 `everysec`，大约最多丢一秒；`no` 则交给操作系统决定何时刷。AOF 会重写来压缩体积。Redis 4.0 起可以混合持久化：AOF 文件前半是 RDB 快照，后半是快照之后的增量命令，恢复时先加载快照再重放。

被问到生产用哪种，按自己环境说。缓存允许回源重建时，有的只开 RDB，甚至不持久化。写入不能多丢时，常见是 AOF 的 everysec，或打开混合持久化。没亲手配过就讲这个取舍，不报一套没见过的参数。

### 13. 缓存穿透、击穿、雪崩是什么，怎么解决

**参考答案**

三者都是请求打穿缓存落到数据库，差别在 key 的状态。穿透是查的数据根本不存在，击穿是一个热点 key 刚好过期，雪崩是大批 key 同时失效，或者 Redis 自身不可用。

穿透时缓存和数据库都没有这份数据，每次都会打到库，随机不存在的 key 还可以被拿来打。处理是先校验参数；对确定不存在的 key 缓存一个短 TTL 的空值；再用布隆过滤器挡住「一定不存在」的 key。布隆说不存在就可以直接返回，说存在仍可能误判，所以还是要查。空值的 TTL 要短，数据后来被写进库时要把空值删掉或覆盖。

击穿是热点过期的瞬间，很多请求同时回源。可以让一个请求拿互斥锁去加载，其他请求等待；也可以逻辑过期，读到旧值先返回，由异步任务刷新。特别热的 key 可以不设 TTL，改由更新数据时主动改缓存。

雪崩是大量 key 一起过期，或缓存进程挂了，流量同时到数据库。TTL 加随机偏移，避免同一秒过期；缓存做主从或集群；入口限流、降级。Redis 宕机和 key 过期要分开说，高可用解决的是进程挂掉，抖动的 TTL 解决的是同时过期。

### 14. Spring IoC 和 AOP 的理解，AOP 用哪几种方式实现

**参考答案**

IoC 是把对象的创建和依赖交给容器。业务类依赖接口，由容器注入实现，同时管作用域和生命周期。注入用构造器、setter 或字段，构造器注入能在创建时就把依赖定下来。

AOP 把日志、事务、权限这类横切逻辑从业务方法里拆出来。Spring 在运行时用代理包住 Bean，外部调用先进入代理，再按通知做前置、后置、环绕或异常处理。

实现方式有三种。JDK 动态代理要求目标实现接口，按接口生成代理。CGLIB 生成目标类的子类来拦截方法，final 类和 final 方法无法代理。Spring Boot 2 起 `spring.aop.proxy-target-class` 默认为 true，即使有接口也用 CGLIB。第三种是 AspectJ 的编译期或类加载期织入，能切到自调用和 private 方法。Spring 默认的 `@Aspect` 仍是运行时代理，不是这种织入。

代理只拦从外部进来的调用。同一个类里用 `this` 调用自己的方法，不会走到切面，加在那个方法上的事务也不会生效。

### 15. Spring Boot 自动配置原理简单说一下

**参考答案**

自动配置是按类路径和配置项，有条件地注册一批默认 Bean。用户自己声明了同类型 Bean 时，默认的那份就让开。

`@SpringBootApplication` 里包含 `@EnableAutoConfiguration`。启动时 `AutoConfigurationImportSelector` 读出候选配置类。Boot 2.7 之前写在 `META-INF/spring.factories` 的 `EnableAutoConfiguration` 键下。2.7 增加了 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，这段时间两处都能用。Boot 3 的自动配置只读这个新文件。

每个自动配置类上有条件注解。`@ConditionalOnClass` 表示类路径里有对应依赖才生效，`@ConditionalOnMissingBean` 表示用户还没声明同类型 Bean 才装配默认实现，`@ConditionalOnProperty` 看配置项开没开。starter 本身多半是一组依赖描述，把第三方库和自动配置类一起带进来。不想要某项时，用注解的 `exclude`，或配置 `spring.autoconfigure.exclude`。

条件不满足时，只引入 starter 也不会创建那些 Bean。

### 3. 数据库慢查询你一般怎么排查，EXPLAIN 重点关注哪些字段

**参考答案**

先分清慢在 SQL 本身、锁等待，还是连接池排队。应用超时不等于缺索引。

从慢查询日志或 `performance_schema` 取出完整语句和真实参数，看 IN 列表有多长、分页有多深。然后看执行计划。`EXPLAIN` 不真正改数据；MySQL 8.0.18 起的 `EXPLAIN ANALYZE` 会执行语句，写操作要在只读或备份环境看。同时看锁等待。计划正常但请求很慢时，经常是在等行锁，而不是没走索引。

重点看这几列。`type` 是访问方式，从好到差大致是 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL`。`ALL` 是全表扫描，`index` 是把整棵索引扫一遍，不等于按键查找。`key` 是实际选用的索引，`possible_keys` 里有而 `key` 为空，就是优化器没选它。`key_len` 用来看联合索引用了左起多少字节，再对照列类型和字符集换算成列数，不能把字节数直接当成列数。`rows` 是估算要扫描的行，不是精确返回行数，可以搭配 `filtered` 看条件还能滤掉多少。`Extra` 里重点看 `Using filesort`、`Using temporary`、`Using index`（覆盖索引，不用回表）和 `Using join buffer`。

处理按证据来：补合适的索引、改掉列上的函数和隐式转换、深分页改成按上次最大主键往后取，或者处理锁和数据量。不要先在高峰对大表执行统计信息收集。

### 4. 什么情况下需要建联合索引，最左前缀匹配原则是什么

**参考答案**

多列经常一起出现在过滤、连接、排序或分组里，就建联合索引。等值列放左边，范围列放右边。查询要返回的列都能放进索引时，做成覆盖索引，避免回表。优化器已经在对多个单列索引做 index merge、而且查询稳定时，可以收成一个联合索引。写入很频繁时只给真实查询建，索引多了会拖慢插入和更新。

最左前缀指的是索引列的顺序，不是 SQL 里条件写的先后。索引是 `(a, b, c)` 时，`a` 的等值、`a` 加 `b`、以及三列等值，都能用来查找。只有 `b` 和 `c`、没有 `a` 时，一般用不上这棵索引。`a` 等值且 `c` 等值、但缺了 `b`，查找只能用到 `a`。`a` 已经是范围条件时，它右边的列不能再用于查找，最多参与过滤。`order by a, b` 在左边没有范围条件时，可以顺着索引的顺序，少一次额外排序。

MySQL 8.0.13 起有索引跳跃扫描：被跳过的最左列区分度很低时，优化器可能仍用这棵索引。这是补充路径，不要据此说最左前缀可以不讲。列的区分度要服从查询的等值前缀，不能只把区分度最高的列无条件放在最左。

### 5. MySQL 行锁是基于什么实现的，什么情况下 InnoDB 会用表锁

**参考答案**

InnoDB 的行锁加在索引记录上。有主键时锁聚簇索引，走二级索引时会同时锁二级索引记录和对应的主键记录。没有可用索引时，它仍按聚簇索引逐段加锁，扫过的记录和间隙都会被锁上，并发效果接近锁住整张表。InnoDB 没有「行锁太多就升级成表锁」这一步。

可重复读下，普通的锁定读和更新使用 next-key lock，也就是记录锁加上这条记录前面的间隙，用来挡住别的事务往间隙里插入。唯一索引上等值查到了记录时，常常只留记录锁；记录不存在时仍然锁间隙。读已提交默认不加间隙锁，外键和唯一键检查除外，所以幻读更明显，间隙带来的死锁更少。

会碰到真正表级锁的情况分开看。显式 `LOCK TABLES` 锁的是整张表。自增列在 `innodb_autoinc_lock_mode` 为 0 或 1 时，`INSERT ... SELECT` 这类语句会把表级 AUTO-INC 锁持有到语句结束。MySQL 8.0 默认是 2（交错），为自增分配不再加这把表锁，自增值可以不连续。服务器层还有元数据锁：DML 持有表的共享元数据锁，DDL 要排他元数据锁，所以改表会等长事务结束。这和 InnoDB 的行锁不是同一层。

### 6. MVCC 是什么，在 RR 隔离级别下怎么解决幻读

**参考答案**

MVCC 让普通查询去读旧版本，读写不必互相阻塞。InnoDB 在每行上保留最近修改它的事务 id 和指向 undo 的回滚指针，旧版本串成一条链。表没有主键、也没有非空唯一索引时，还会生成隐藏的行 id，所以表要自己建主键。

一致性读开始时生成 Read View。本事务自己的修改总是可见。其他事务的 id 小于创建视图时的最小活跃 id，视为已经提交，可见；大于等于当时尚未分配的 id，不可见；落在当时活跃列表里的也不可见。介于最小活跃 id 和尚未分配的 id 之间、又不在活跃列表里的，说明创建视图前已经提交，可见。看不见当前版本时，顺着 undo 找更老的版本。可重复读在本事务第一次普通查询时生成 Read View，之后复用，所以多次快照读结果一致。读已提交则每条语句新建一个 Read View。

幻读是同一次范围查询里，后一次多出了别的事务新插入的行。可重复读下要分开看。普通 `SELECT` 用固定快照，看不见视图建立之后才提交的新行。`SELECT FOR UPDATE`、`UPDATE`、`DELETE` 这些当前读会加 next-key lock，锁住记录和间隙，别的事务插不进来。

先做快照读、再做当前读时，当前读能看见这中间已经提交的新行，和快照不一致。所以要说清：快照读靠 Read View，当前读靠间隙锁，两种读混在一个事务里仍可能对不上。

### 7. Redis 集群模式了解吗，槽位是怎么分配的，扩缩容怎么处理

**参考答案**

Redis Cluster 是无中心的分片。数据按 16384 个槽划分，每个槽归属一个主节点，主节点可以带从节点。节点之间用 Gossip 交换状态。客户端缓存槽和节点的对应关系。

槽位由 `CRC16(key) % 16384` 决定，不是一致性哈希环。键里用大括号标出哈希标签时，只对括号内的内容做哈希，相关键就能进同一个槽。跨槽的多键操作会被拒绝，除非这些键落在同一槽。16384 这个数量也能放进心跳的位图里传播，集群不适合把节点数扩到很大。

扩容是把一部分槽迁到新主节点，缩容是先把下线节点上的槽迁空。迁移以槽为单位：目标节点标记为导入，源节点标记为迁出，再把槽里的 key 迁走。迁移过程中，key 还在源上就由源处理；已经迁走时，源返回 ASK，客户端只对这一次去问目标，不改本地的槽缓存。整个槽迁完，归属更新，之后客户端拿到的是 MOVED，才会改缓存。只改槽的映射、不迁移 key，数据就丢了。缩容确认节点上已经没有槽，再把它移出集群。

### 8. Redis 分布式锁怎么实现，Redisson 看门狗机制是什么

**参考答案**

单机上的互斥用 `SET key 唯一请求号 NX PX 过期时间`：键不存在才设置，并带上过期时间，避免持有者宕机后锁永远不释放。释放时必须先核对请求号再删除，而且这两步要原子执行，否则会删掉别人刚加上的锁。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

只做 `SET NX` 时锁不可重入。过期时间到了业务还没做完，别的客户端可以进入，互斥已经被打破；原来的客户端此时再删锁，就要靠请求号核对挡住。主从异步复制还有一个窗口：锁写在主上，主宕机，从提升后锁可能还没复制过去。关键的资金或库存链路，更稳妥的是数据库唯一约束，或用共识组件做锁。Redis Cluster 和红锁不是一回事，一个 key 的锁只落在一个槽上。

Redisson 的 `lock()` 不传租期时会开看门狗。默认锁约 30 秒，持有期间大约每 10 秒把过期时间续回 30 秒，所以进程还活着、又没解锁时，锁会一直续。解锁或客户端宕机后，续期停止，锁在剩余时间内过期。加锁时如果显式传了租期，看门狗不启动，到期就释放，不管业务是否结束。看门狗是客户端在续，客户端如果长时间停顿，仍然可能先过期。

### 9. 消息队列你用过吗（RabbitMQ / Kafka / RocketMQ），为什么引入 MQ，怎么保证消息不丢失

**参考答案**

先按真实经历说用过哪一种、放在链路的哪一段。三种都没上过生产，就说明了解定位，后面按原理讲，不编集群台数和参数。

引入消息队列通常是为了三件事：把下单和发通知、记流水拆开，调用方不用一起成功；把慢操作移出主链路；把突发流量先堆在队列里，消费者按能力拉。代价是最终一致、重复投递、堆积和额外运维。强一致、又要立刻读到结果的写，不适合先丢进队列。

不丢失要三段一起做。生产者必须等到确认再认为发送成功：Kafka 用 `acks=all`，并让 `min.insync.replicas` 至少为 2，避免只写到一个副本；RocketMQ 同步发送并检查发送结果；RabbitMQ 开发布者确认，同时把队列和消息都标成持久化。Broker 侧要落到足够的副本或按需要刷盘，Kafka 还要避免选举一个没有追上的副本当首领。消费者处理成功再提交位点或 ack。Kafka 关掉自动提交，RocketMQ 失败就返回稍后重试，RabbitMQ 用手动确认。

这套做完是至少一次，消费者要用业务键做成幂等。数据库事务和发消息也要放在一起考虑：事务消息或本地消息表，避免「消息已发出去、本地事务回滚」或「事务提交了、进程在发出去之前崩溃」。

### 10. Spring Bean 的生命周期说一下，单例 Bean 是否线程安全

**参考答案**

单例 Bean 从创建到销毁，主路径是：实例化、填充依赖、回调、初始化、投入使用、容器关闭时销毁。

构造器完成实例化后，容器注入依赖。接着回调 `BeanNameAware`、`BeanFactoryAware`，并在前置处理里设置 `ApplicationContextAware` 等。初始化的顺序是 `@PostConstruct`，然后 `InitializingBean.afterPropertiesSet`，再然后自定义的 init-method。这些初始化跑在目标对象上。BeanPostProcessor 的后置处理紧跟在后面，AOP 代理多半在这里包上去。之后业务拿到的才是代理。容器关闭时销毁单例，顺序是 `@PreDestroy`、`DisposableBean.destroy`、自定义 destroy-method。原型 Bean 创建之后不再归容器销毁。

单例指一个容器里这份 Bean 只有一个实例，创建过程由容器加锁保证只建一次。这不保证业务状态线程安全。无状态的 Service，成员只有依赖，方法里只用局部变量，可以并发调用。可变成员会被所有请求共享，计数、缓存 Map、把本次请求的数据放进字段，都会串。请求级数据放进方法参数或请求作用域，需要共享可变状态时再加锁或用并发容器。

### 11. Spring 事务的传播机制和常见失效场景

**参考答案**

传播行为决定当前方法怎样对待已经存在的事务。默认是 REQUIRED：有就加入，没有就新建。

REQUIRES_NEW 把外层挂起，自己新建事务并独立提交，外层之后回滚也不会撤掉内层已经提交的修改。NESTED 在已有事务里建保存点，内层失败只回到保存点，外层仍可提交；外层如果回滚，内层的修改一起回滚。没有外层事务时，NESTED 和 REQUIRED 一样新建事务。SUPPORTS 是有事务就加入，没有就以非事务运行。NOT_SUPPORTED 挂起已有事务，以非事务运行。MANDATORY 要求外面必须已经有事务，否则抛异常。NEVER 要求外面一定没有事务。

常见失效有这些。方法不是 public，默认的事务代理不拦截。同一个类内部自己调用自己，调用不经过代理。异常被 catch 住没有再抛出。抛出的是受检异常，而默认只在 `RuntimeException` 和 `Error` 时回滚，受检异常要写 `rollbackFor`。对象不是容器管理的，或库引擎不支持事务。传播理解错了：内层用了 REQUIRES_NEW 并且已经提交，外层失败带不回来。事务绑在线程上，新开的线程不会自动带上外层事务。

### 12. 接口幂等性怎么设计，举一个你项目中的实际做法

**参考答案**

幂等是同一请求执行一次和执行多次，业务状态的结果相同。目标是让重试安全，不是禁止客户端重试。

幂等键要由调用方生成，超时重试时复用同一个键。服务端每次自己生成新键，重试会被当成新请求。落地有几种做法，按场景选。

创建类请求用业务单号做唯一索引，和业务写入放在同一个事务里。并发下两个插入只有一个成功，另一个撞上唯一约束，再查出现有结果返回。先查再插，中间仍有窗口，约束必须留在数据库上。状态变更用带条件的更新，例如 `WHERE status = 待处理`，影响行数为 0 就说明已经处理过。提交按钮可以用一次性令牌：先把令牌放进 Redis，处理时原子取走，取不到就拒绝。令牌删掉之后业务又失败时，要放回令牌或改成「处理中 / 已完成」状态，否则客户端无法重试。消息消费用消息键或业务键做去重记录，和业务更新放在一起。

对外要分清两种结果：已经成功过，返回和第一次成功相同的业务结果；这次失败了，返回可重试的错误。调用方才能判断要不要再用同一个键重试。

**答题思路**

讲自己的项目时，按真实接口说，不要临时编一个支付或下单系统。

1. 重复从哪来：用户连点、超时重试，还是消息至少投递一次。
2. 键是什么：调用方传入的请求号，还是业务单号。存在哪张表或哪个缓存里。
3. 冲突时怎么返回：把已有结果交回去，还是提示正在处理。
4. 处理到一半失败，重试会不会做第二遍。没做过完整方案，就讲你系统里真实存在的唯一约束或条件更新，并说明它盖不住的窗口。

### 13. 如果线上服务 CPU 飙高你怎么排查

**参考答案**

先确认是哪台机器、哪个进程、哪类线程在耗 CPU，保留现场，再决定要不要重启或扩容。

用监控或 `top` 看是不是这台、是不是 Java 进程，并区分用户态、内核态和 IO 等待。IO 等待高，方向是磁盘而不是死循环。确认是 Java 进程后，用 `top -Hp <pid>` 找出最忙的线程，把线程号转成十六进制，到 `jstack <pid>` 里对 `nid`。机器上有 Arthas 时，`thread -n` 可以直接给出最忙线程的栈，原理一样。

栈是 `RUNNABLE` 且停在同一段业务代码，查死循环、忙等、正则回溯或热点计算。大量线程在 `BLOCKED`，去查锁。CPU 高也可能是 GC：用 `jstat -gcutil` 看老年代是不是在涨、Full GC 是不是在连着发生。是的话先看堆是否过小、有没有明显泄漏，再考虑在低峰 dump。dump 会暂停进程，不要一上来就做。

先留线程栈和 GC 日志，再限流、摘流量或重启。容器里看到的 CPU 百分比要对照限额，避免把配额打满误判成机器还有空闲。

### 14. 你平时怎么学新技术，最近在看什么

**答题思路**

这题看学习是不是能落到工作里。讲一个真实在看的点，讲清你怎么验证自己学会了。

1. 从一个具体问题带出来，例如一条慢查询、一次重复消费、一个线程池打满。不要从书单或名词清单开场。
2. 顺序是：官方文档把核心模型看懂，本地用最小例子跑通，再对上自己项目里能用的一个点，最后主动看一种失败，比如超时、重复、丢数据或内存涨。

5. 收尾用自己的例子讲一遍。讲不清机制，就还没到可以当项目经验说的程度。
