### 3. String、StringBuilder和StringBuffer的区别是什么

**参考答案**

String 不可变，适合当常量、Map 的键和跨方法传递的文本。StringBuilder 用来在单线程里拼接。StringBuffer 只比 Builder 多了方法级同步，实际很少需要。

String 是 final 类。JDK 9 起内部用 `byte[]` 加编码标记，字符都能放进 Latin-1 时按单字节存，否则用 UTF-16；更早的版本是 `char[]`。拼接、截取、替换都返回新对象。不可变让字面量和 `intern()` 可以放进常量池，池从 Java 7 起位于堆中。判断内容用 `equals`，`==` 比的是引用。

StringBuilder 和 StringBuffer 都是可变序列，容量不够时大约按两倍扩容。Buffer 的公开方法带 `synchronized`，Builder 没有，所以单线程拼接用 Builder。Buffer 的锁只包住一次方法调用，先看长度再追加这种组合动作仍会交错。

一条表达式里的 `+` 会收成一次构建。循环里写 `s = s + x`，每一轮都产生新的 String，应改成在循环外持有一个 StringBuilder。多个线程各自拼接，就各自持有 Builder，不必共享一个 Buffer。

### 4. ArrayList和LinkedList在底层结构和适用场景上有何不同

**参考答案**

列表的默认选择是 ArrayList。LinkedList 是双向链表，按下标访问要遍历，并不适合作为「中间插入很多」的通用容器。

ArrayList 的元素放在 `Object[]` 里。新建时空数组被共享，第一次加入元素才扩到默认容量 10，之后按约 1.5 倍增长并拷贝。按下标读和改是 O(1)，尾部追加均摊 O(1)。在中间插入或删除要搬移后面的元素，是 O(n)。内存连续，遍历缓存友好。它不是线程安全的，迭代过程中结构被改会快速失败。

LinkedList 的结点保存元素以及前驱和后继，并实现了 Deque。已经拿到结点时，改指针是 O(1)。`get(i)` 会从离下标更近的一端数过去，按下标插入也要先走到那里，都是 O(n)。每个元素多一个结点对象和两根指针，跳跃访问对缓存不友好。

只在头尾增删、又要当队列或栈时，用 ArrayDeque，一般比 LinkedList 更合适。LinkedList 适合遍历过程中按迭代器删除当前结点。需要线程安全的读多写少列表，另选 CopyOnWriteArrayList，那是拷贝整个数组的策略，和链表无关。

### 5. Java中创建线程有哪几种方式

**参考答案**

任务和线程分开看。向操作系统申请平台线程的是 `Thread.start()`。业务代码把任务提交给有界线程池，而不是随请求 `new Thread`。

常见写法有四种：

1. 继承 Thread，重写 `run`，再 `start`。类已经有父类时不方便，任务也被绑死在线程上。
2. 实现 Runnable，交给 `new Thread(runnable)` 或线程池。没有返回值，受检异常要在 `run` 里处理。
3. 实现 Callable，用 FutureTask 包起来再启动，或交给 `ExecutorService.submit`。可以返回结果，异常会在 `get()` 时包成 ExecutionException。
4. 线程池复用平台线程。用 `ThreadPoolExecutor` 明确核心数、最大数、队列和拒绝策略。`newFixedThreadPool`、`newSingleThreadExecutor` 的队列无界，`newCachedThreadPool` 的线程数无界，任务涌进来会把内存或线程打满。

直接调用 `run()` 只是在当前线程执行方法。CompletableFuture 也不是新的建线程方式，它使用已有的池；不传执行器时走公共 ForkJoinPool，业务任务应使用自己的池。

Java 21 起可以用 `Thread.ofVirtual().start(...)` 为阻塞在 IO 上的任务启动虚拟线程。CPU 密集计算仍用数量有限的平台线程。

### 6. synchronized和ReentrantLock的区别

**参考答案**

两者都可重入。只需要互斥时用 synchronized；需要超时、可中断、公平或分开的条件队列时用 ReentrantLock。

synchronized 是 JVM 的监视器，可以写在实例方法、静态方法或代码块上。退出代码块时会释放，抛异常也一样。同一个监视器只有一个等待集合，配合 `wait` / `notify`。线程在争这把锁时不能被中断，也没有超时返回。实现上先用 CAS 把对象头指到当前栈帧里的锁记录，竞争激烈再膨胀成重量级监视器，线程进入操作系统队列。JDK 15 起偏向锁默认关闭，JDK 18 起实现已删除。编译器还能对它做锁消除和锁粗化。它锁的是对象，不要锁在会被到处复用的包装对象或字符串常量上，否则不相干的代码会共用同一把锁。

ReentrantLock 基于 AQS，`lock` 必须写在 `try` / `finally` 里 `unlock`，否则异常后锁不会还。它可以 `tryLock`、限时等待，也可以 `lockInterruptibly`。默认非公平，新线程可以插队，吞吐更好；构造参数传 `true` 则按队列公平获取，饥饿更少，切换更多。`newCondition()` 能建多个条件队列。它还能查看是不是当前线程持有、队列有多长。

`tryLock` 没拿到锁就不能解锁：

```java
if (lock.tryLock()) {
    try {
        // 临界区
    } finally {
        lock.unlock();
    }
}
```

等待和唤醒要跟所持的锁配套：进了 synchronized 用 `wait` / `notify`，持有 ReentrantLock 用 Condition。

### 7. JVM内存模型中堆和栈分别存放什么，有什么区别

**参考答案**

堆和栈是 JVM 运行时数据区里的两块。题目说的「内存模型」按存放位置来答。可见性和重排序属于 JMM，用 happens-before 说明，不在这两块区域的划分里。

堆被所有线程共享，存放对象实例和数组，对象的实例字段也在这里。它是垃圾回收的主要区域，空间由堆参数控制。分配失败、回收后仍放不下，抛出堆空间不足。逃逸分析之后，没有逃出方法的对象可能被标量替换，不一定真的在堆上留一个对象；语言层面仍按「对象在堆上」来理解。

这里的栈指每个线程私有的 Java 虚拟机栈。每次方法调用压入一个栈帧，里面有局部变量表、操作数栈、动态链接和返回地址。局部变量表保存基本类型的值和对象引用，引用指向的对象在堆上。方法返回，栈帧弹出，不靠垃圾回收来释放。栈太深会 `StackOverflowError`。每个线程都要一块栈，线程过多、栈总内存申请不到时会 `OutOfMemoryError`。

因此：堆共享、容量大、靠回收；栈私有、随调用自动伸缩、放的是帧和局部变量。本地方法还有单独的本地方法栈，不要和 Java 虚拟机栈混成一块。

### 8. 描述Spring Bean的生命周期

**参考答案**

单例 Bean 从创建到可替换销毁，顺序是固定的。初始化和 AOP 代理的先后最容易说乱。

1. 实例化。构造器注入发生在这一步。
2. 填充属性，完成字段和 setter 注入。
3. 回调 BeanNameAware、BeanClassLoaderAware、BeanFactoryAware。
4. BeanPostProcessor 的前置处理。ApplicationContextAware 等其余 Aware 在这里回调，`@PostConstruct` 也在这里执行。
5. 若实现了 InitializingBean，调用 `afterPropertiesSet`。
6. 调用自定义的 init-method。
7. BeanPostProcessor 的后置处理。声明式事务和 AOP 的代理通常在这里包到目标对象外面。
8. Bean 投入使用。
9. 容器关闭时销毁单例：先 `@PreDestroy`，再 `DisposableBean.destroy()`，最后自定义 destroy-method。

`@PostConstruct` 早于 `afterPropertiesSet`，二者都早于代理生成。所以在初始化回调里调用本类的事务方法，调用的是目标对象，事务拦截器不会生效。同类内部的自调用同样不走代理。

原型 Bean 每次获取都新建，容器创建后不再跟踪，默认也不会调它的销毁回调。构造器上的循环依赖在实例化阶段就会失败。单例的 setter 或字段注入，才可能通过三级缓存拿到提前引用；Spring Boot 2.6 起默认禁止循环依赖，要显式打开才走得到这套引用。

### 9. 简述Spring MVC处理一个HTTP请求的完整流程

**参考答案**

一次请求先过 Servlet 容器和 Filter，再由 DispatcherServlet 找到控制器、执行、写回结果。

1. Tomcat 收到连接后进入 Filter 链，例如编码、跨域和安全过滤，然后到达 DispatcherServlet。
2. DispatcherServlet 按 HandlerMapping 匹配路径，得到控制器方法以及拦截器链。
3. 拦截器按顺序执行 `preHandle`。有一个返回 false，后面的控制器就不再执行。
4. HandlerAdapter 解析参数、做校验，再调用控制器方法。控制器默认是单例，请求数据放在参数和局部变量里，不要写进字段。
5. 返回值分成两条路。`@ResponseBody` 或 `@RestController` 由 HttpMessageConverter 直接写响应，不再找视图。返回视图名时，ViewResolver 解析出视图再渲染。
6. 控制器正常返回后，拦截器执行 `postHandle`，然后渲染视图。无论成功还是失败，已通过 `preHandle` 的拦截器都会走到 `afterCompletion`。控制器抛异常时不会走 `postHandle`，异常交给 HandlerExceptionResolver，例如 `@ControllerAdvice` 里的 `@ExceptionHandler`。

Filter 属于 Servlet 规范，包在 DispatcherServlet 外面，能拦住所有进入容器的请求。拦截器是 Spring 的机制，只能看到已经交给 DispatcherServlet 的请求。

### 10. MySQL索引有哪些类型，各自特点是什么

**参考答案**

InnoDB 里和业务直接相关的是 B+Tree 索引。先分清数据结构，再分清它是聚簇索引还是二级索引。

按数据结构：

- B+Tree 是 InnoDB 和 MyISAM 的普通索引形态。非叶子结点只放键，叶子结点形成有序链表，适合等值和范围。树通常很矮。
- 哈希索引用于 Memory 引擎，等值查找很快，不支持范围和排序。InnoDB 不提供让用户建的哈希索引；它对热点页可能自动维护自适应哈希。
- 全文索引是倒排索引，用 `MATCH ... AGAINST` 做分词检索，不能替代普通的范围查询。
- 空间索引用 R-Tree，服务地理类型的范围判断。

按和数据的关系：InnoDB 的聚簇索引就是主键，叶子放整行。没有主键时，用第一个全非空唯一索引，再没有就生成隐藏行号。二级索引的叶子放索引列和主键，查其他列要回表。查询列都在这棵索引里时成为覆盖索引，不必回表。

按约束还有主键、唯一、普通、联合和前缀索引。联合索引服从最左前缀，范围条件后面的列不能再用于查找。前缀索引只取列的前若干字符，区分度不够时过滤效果差，唯一性也只覆盖到这个前缀。`LIKE '%关键字'` 无法使用普通 B+Tree。

### 11. 数据库事务的隔离级别有哪几种，分别解决了什么问题

**参考答案**

标准隔离级别有四种，用来逐级消除脏读、不可重复读和幻读。InnoDB 默认是可重复读。

三种现象先分开。脏读是读到了别的事务尚未提交的修改。不可重复读是同一行读两次，中间被别的已提交事务改了值。幻读是同一个范围条件查两次，行集合因为别的事务插入或删除而变了。

1. 读未提交：三种现象都可能出现，线上基本不用。
2. 读已提交：不再脏读。本事务只能看见已提交的数据，但同一行两次读取仍可能不同，范围查询也可能看见新行。Oracle 这一类数据库通常默认这一级。InnoDB 在这一级按语句建立新的读视图。
3. 可重复读：不再脏读，普通的一致性读也不会因为别的事务提交而改变同一行的结果。这是 MySQL 的默认级别。InnoDB 在事务第一次一致性读时建立读视图并一直沿用。`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 属于当前读，读的是最新已提交版本并加锁；这一级使用临键锁，也就是记录锁加间隙锁，用来挡住范围里的插入。
4. 串行化：普通查询也会变成加共享锁的当前读，读写互相阻塞，三种现象都按加锁来避免，并发最差。

标准 SQL 里，幻读要到串行化才要求消除。InnoDB 的可重复读额外做了两件事：一致性读沿用同一张快照，加锁读使用临键锁。快照读不加锁，当前读仍会加锁，两者看到的版本可以不同。

### 12. Redis支持哪些数据类型，请举例说明其使用场景

**参考答案**

常用的是字符串、哈希、列表、集合、有序集合。位图、HyperLogLog、地理位置和 Stream 是在这些结构上的专门能力。Redis 适合缓存、计数和短临界区，订单是否支付仍以数据库为准。

- 字符串：缓存一个对象或页面片段，用 `INCR` 做计数，用 `SET key value NX EX` 做带过期时间的互斥。会话令牌也常放这里。单个字符串最大 512MB。
- 哈希：缓存一个对象的若干字段，只更新变化的字段，例如商品的价格和库存展示。购物车可以用用户做键、商品做字段。
- 列表：保留最新的 N 条动态，一头推进去、另一头按长度裁剪。阻塞弹出能做简单队列，它没有 Kafka 那种积压、重放和消费者组能力。
- 集合：标签、点赞用户这类去重。交集可以算共同好友，随机弹出可以做抽奖。
- 有序集合：成员带分数。排行榜按分数取前 N 名。把执行时间戳当分数，可以做时间范围的延迟任务；弹出要用 `ZPOPMIN` 或 Lua，把「取出」和「删除」做成一次操作。

延伸类型：位图统计签到，HyperLogLog 估算很大基数的独立访客，地理位置按经纬度查附近的人。Stream 带消费者组和待确认列表，适合同一业务进程里的轻量事件流。跨系统、要长期保留和回放的日志仍交给专门的消息队列。

### 13. 如果让你设计一个秒杀系统，你会考虑哪些核心环节

**参考答案**

秒杀要先把打到数据库的请求减下来，再用条件更新守住最终库存。只靠数据库最一致，热点行会在开场被锁住；只靠 Redis 最快，宕机可能把剩余数量弄丢。所以 Redis 负责挡流量，数据库负责最终数量。

1. 入口：页面静态化和 CDN 只减轻读页面的压力。网关按用户和活动限流。库存已经是 0 时，在应用本地记住售罄标记，短时间内不要再访问 Redis。
2. 预扣：活动前把可售数量预热到 Redis。扣减放进 Lua，判断和减少一次完成。键不存在就失败，不要把空值当成还有货。

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if (not stock) or (stock < tonumber(ARGV[1])) then
  return -1
end
return redis.call('DECRBY', KEYS[1], ARGV[1])
```

3. 削峰：预扣成功才把下单消息放进队列，消费者按数据库写得动的速度创建订单。队列堆积超过阈值，就在入口直接拒绝，而不是无限塞。
4. 落库：库存用条件更新做最后核对。订单对用户和活动做唯一约束，重复点击插不进第二单。预扣和入队之间进程若退出，库存会暂时少一件，用预扣流水对账加回去。

```sql
UPDATE seckill_stock
SET available = available - 1
WHERE sku_id = ? AND available >= 1;
```

5. 回补：创建订单失败，或超时仍未支付，按同一业务单号把 Redis 和数据库的库存加回。回补本身也要幂等。关单前先核对支付结果，已经付成功的走退款。Redis 故障时停止开卖，按数据库剩余量重建，不继续裸卖。

### 14. 你在之前的项目或学习中接触过哪些AI工具或框架

**答题思路**

按自己真实到过的深度讲，分三层，只讲到过的那一层。这场如果对方不追问，两分钟内收住。

1. 开发辅助：编辑器补全或对话工具。准备一个真实片段，说明它生成了什么、你改了哪一处、你怎么确认它是对的。事务边界、锁和幂等不要交给生成结果直接合并。
2. 查资料：用对话看报错、对 API。说明你会回到官方文档或源码核对，不把模型的回答当结论。
3. 业务调用：只有真的调用过模型 API，才讲请求是同步还是流式、超时和失败时业务状态怎么处理、密钥放在哪。看过文档或跑过一次示例，就说是学习和试用。

### 4. 设计一个高并发订单系统，你会如何考虑架构和存储

**参考答案**

同步路径只留必要的几步：认证和限流、服务端重新算价、用客户端令牌做幂等、预留库存、写入待支付订单和明细。优惠通知、搜索索引和履约都异步做。订单、库存、支付回调分成明确边界。库存如果在另一个库，用按订单号幂等的预留和回补，不用两阶段提交把两个库套在一起。

存储上，订单和明细放在同一个本地事务里。面向买家的查询多，就用买家 id 做分片键，让这两张表落在同一片。订单号里带上分片基因，按订单号也能找到分片。状态迁移用条件更新，影响行数为 0 就是状态已经变过：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_id = ?
  AND status = 'UNPAID'
  AND pay_amount = ?;
```

金额用整数分或 DECIMAL，不使用浮点。用户刚写下的单，返回写入结果或读主库，避免从库还没追上就显示订单不存在。订单状态变化频繁，缓存要么在状态变更时删掉，要么只缓存商品和地址这类读多写少的数据。后台多条件检索可以异步进 Elasticsearch，那里允许短暂延迟。

普通商品直接用数据库条件更新扣库存。少数热点商品再前置 Redis 原子预扣，失败回补。超时关单和支付回调会碰到一起：关单前向渠道核对，已经支付的走退款，不能改成已取消。同步路径短，代价是要接受「待支付已创建、履约还没开始」这个中间状态，靠状态机、幂等和对账收口。

### 5. Redis的持久化机制RDB和AOF分别是如何工作的，各有什么优缺点

**参考答案**

RDB 是某一时刻的紧凑快照，恢复快，两次快照之间的写入会丢。AOF 追加写命令，丢数据的窗口更小，文件更大。开启 AOF 时，重启用 AOF 恢复，因为它通常比最近一次 RDB 更完整。两者都代替不了另一台机器上的副本。

RDB 常用 `BGSAVE`。父进程 fork 出子进程，子进程把 fork 那一刻的数据写成二进制文件，写完再原子替换。写时复制让父进程继续处理命令；父进程改过的内存页会被复制一份，所以大实例 fork 时可能出现明显的内存放大。`SAVE` 会堵住主线程，一般只在维护时使用。触发靠手动命令，或按时间窗口里的写次数自动触发，常见配置是 3600 秒内至少 1 次写、300 秒内至少 100 次、60 秒内至少 10000 次。优点是文件小、加载快，适合备份和作为从节点的全量基础。缺点是备份点之后的写入会丢，fork 也有成本。

AOF 把写命令追加到文件末尾。刷盘有三档：`always` 每条命令都刷，最不容易丢也最慢；`everysec` 大约每秒刷一次，是常见默认，宕机大约丢一秒；`no` 交给操作系统，窗口更大。文件变大后用重写压缩：fork 子进程按当前内存生成能重建数据的命令，重写期间的新命令先放在缓冲区，结束后接回去。Redis 4.0 起这段内容可以先是 RDB 格式、后面再跟增量命令；Redis 7 起可以分成基础文件和增量文件。优点是耐久性更好。缺点是文件更大，纯命令回放较慢，`everysec` 仍可能丢一秒。

### 6. Kafka如何保证消息不丢失，从生产者到消费者的全流程角度说明

**参考答案**

Kafka 这条链做到的是至少一次。生产者、Broker、消费者三段都确认之后，消息才不会因为单点重启而丢；重复要靠业务键消化。恰好一次还要幂等或事务。

生产者要把「收到应答」定义成发送成功。`send` 返回时消息可能还在内存缓冲区，进程退出就没了。生产环境确认这三项：`acks=all`、开启幂等、失败会重试。旧客户端的默认曾经是 `acks=1` 且不幂等，升级后不要想当然。幂等生产者为分区分配序列号，重试不会在同一个分区里写出重复记录，也不会打乱这个分区内的顺序。

```properties
acks=all
enable.idempotence=true
```

Broker 侧，副本因子至少 3，`min.insync.replicas` 设为 2。`acks=all` 只等待当前 ISR，而 `min.insync.replicas` 的常见默认是 1，只剩 leader 时也会应答成功。落后副本不能当选 leader，否则会截断已经确认过的消息。应答表示 ISR 中的副本已经把消息写入各自日志。刷盘仍由操作系统页缓存决定，所有副本同时掉电时，尾部仍可能丢。消息若来自一次数据库修改，要在同一个本地事务里写业务表和发件箱，再异步投递，避免库已经提交、进程退出、消息却没发出。

消费者处理成功后再提交位移。自动按间隔提交时，提交的是已经 poll 到的位移，处理还没完成重启后就不会再投递。处理完再提交会在崩溃时重复投递，所以消费端按订单号或消息键做幂等。写入数据库和提交位移不是一个事务；要在 Kafka 内部做消费后再生产，才使用 Kafka 事务并让下游按已提交读。落到业务库时，仍然靠幂等和对账。

### 7. 简述Elasticsearch倒排索引的基本原理

**参考答案**

倒排索引把「文档里有哪些词」换成「一个词出现在哪些文档里」，查询时先找词，再拿文档列表做交并和算分。

写入时，分析器处理文本字段：字符过滤、分词、小写或去停用词等词项过滤。`text` 会分成词项，`keyword` 不分词，整段值就是一个词项。索引和查询必须使用同一套分析器，否则写进去的词和查的词对不上。

每个分片是一个 Lucene 索引，由若干不可变 segment 组成。segment 里词项字典按序组织，Lucene 用 FST 把词项映射到倒排表。倒排表记录文档 id，也可以记录词频、位置和偏移。有位置才能做短语查询，有偏移才能做高亮。新文档先进入内存缓冲并写入 translog，refresh 之后形成新 segment 才能被搜到。默认大约 1 秒 refresh 一次，所以这是近实时，不是写完立刻能搜。更新和删除是追加新文档并标记旧文档删除，后台合并 segment 时才真正清掉。

查询把条件改写成词项查找，用倒排表做与或非，再用 BM25 算相关度。排序、聚合使用的是列式的 doc values。`text` 默认没有 doc values，需要排序或聚合时另建 `keyword` 字段。一次搜索会在各分片上执行，再把结果合并。

### 8. 解释MySQL的MVCC机制是如何实现可重复读隔离级别的

**参考答案**

InnoDB 的可重复读，靠事务内复用同一个读视图，沿撤销日志里的版本链找到创建视图时已经提交的那一版。这保证的是一致性读。当前读走另一条路。

聚簇索引的每行记录带有最后修改它的事务 id，以及指向撤销日志的回滚指针。更新不是原地覆盖旧内容，旧版本挂在版本链上。一次一致性读会创建读视图，里面有当时尚未结束的事务 id、这些事务里的最小 id（低水位），以及创建视图时即将分配的事务 id（高水位）。

判断一个版本可不可见时：是本事务自己改的，可见；事务 id 小于低水位，说明那时已经提交，可见；大于等于高水位，是视图创建之后才开始的，不可见；落在活跃事务列表里，创建视图时还没提交，不可见；其余情况是创建视图前已提交，可见。不可见就顺着回滚指针找更老的版本。

可重复读在这个事务第一次一致性读时建立读视图，后面的普通 `SELECT` 都用它，所以别的事务后来的提交不会改变你再读同一行的结果。读已提交则每条语句新建一个读视图。可重复读下，`START TRANSACTION WITH CONSISTENT SNAPSHOT` 在事务开始时建立视图，普通的 `START TRANSACTION` 等到第一次一致性读。读已提交下，这个修饰不会把同一张快照延长到整段事务。

`UPDATE`、`DELETE` 和 `SELECT ... FOR UPDATE` 是当前读，读最新已提交版本并加锁，不沿用这张快照。可重复读下，范围条件使用临键锁挡住间隙插入，这才是 InnoDB 抑制幻读的另一半。先做普通查询，再在本事务里更新同一行，更新会作用在最新版本上，之后的查询能看见自己的修改。可重复读挡住的是其他事务的提交，不是自己的当前读。

### 9. 当单表数据量过大时，分库分表有哪些常见的拆分思路

**参考答案**

先确认大在哪里。行太宽、业务耦合，用垂直拆分。行数让索引、备份和变更都很难做，或单库写入到顶，再水平拆。没有统一的行数阈值，先看慢查询、缓冲池命中、备份和 DDL 时间。历史数据能归档时，先归档。

垂直分库按业务边界拆，例如用户、订单、商品各自一个库，库之间用服务调用，不在数据库里做跨库连接。垂直分表把低频大字段拆到扩展表，主表留热字段，按主键一对一关联。

水平拆分有两种常见路由：

- 按时间或主键区间划分。新数据进新的分片，旧分片可以归档，但写入会集中在最新一片。
- 按分片键哈希取模。写入更均匀。分片数取 2 的幂时，数量翻倍只需把大约一半数据迁到新分片。跨分片的范围查询要扇出。

分片键要出现在绝大多数查询里，基数高、分布均匀，并且让必须同一事务的表落在同一片。面向买家的订单和明细可以用买家 id。订单号里放入这个键的一部分，这样只拿订单号也能算出分片，不必先查一张全局映射。主键在应用侧用号段或雪花算法生成，不依赖单库自增。

后台的多条件分页和跨片统计放到异构索引或搜索里，接受一点延迟。拆分之后，跨片连接、分布式事务和扩容迁移都变成常态成本，所以单库还能承载时不先拆。

### 10. 在微服务架构中，服务注册与发现的基本原理是什么

**参考答案**

服务不把对方的 IP 写死。提供者把实例登记到注册中心，调用方按服务名拿到当前实例列表，再自己或由入口选择一台。

提供者启动时注册服务名、地址、端口，以及版本、环境这类元数据，之后用心跳或租约续期。到期没有续约就被摘除。进程退出时主动注销，比等租约过期更快。临时实例随心跳消失；需要长期保留的实例另做持久登记，避免进程一停就被删掉。

调用方订阅这个服务名，把列表缓存在本地，变更时更新。发起调用前按随机、轮询或权重选一个实例，失败就换实例，并配合超时和熔断。注册中心短时间不可用时，用本地缓存继续调用，不把所有请求都停在发现这一步。缓存也会变旧，所以不健康实例仍要靠调用失败来摘除。

这是客户端发现，Nacos、Eureka、Consul 都是这个模型。Eureka 一类在分区时更偏向继续提供旧列表；Consul、etcd、ZooKeeper 更偏向强一致，选主期间可能暂时不能登记。Nacos 的临时实例和持久实例分别走这两种取舍。

另一类是服务端发现。调用方只访问一个稳定地址，由 Kubernetes Service、网关或负载均衡器根据端点列表转发。原理仍是「健康实例集合加选择一台」，只是选择发生在调用方进程外面。

### 11. 分布式场景下，如何保证跨服务的事务一致性，有哪些常见方案

**参考答案**

能拆开的业务用本地事务加上最终一致。外部支付和长流程不放进一个全局事务。所有最终一致方案都要幂等，并有对账把重试仍补不上的单找出来。

1. 本地消息表，也叫发件箱。业务修改和一条待发送记录提交在同一个数据库事务里，后台再投到消息队列。消费者按业务单号幂等处理。窗口期内会出现订单已创建、下游还没完成。实现落在自己手里，不依赖特定消息中间件。
2. 事务消息。以 RocketMQ 为例，先发送半消息，再执行本地事务；提交成功才让消息可投递，失败则丢弃半消息。状态不明时由 Broker 回查本地事务。它和发件箱是一类思路，少维护一张投递表，但消息中间件要支持这套协议。
3. TCC。Try 预留库存或余额，Confirm 确认占用，Cancel 释放。三个接口都按业务单号幂等，还要处理取消先到的空回滚，以及取消之后才到的预留。适合必须先占住资源的场景，业务代码要写三套。
4. Saga。每个服务提交自己的本地事务，失败时按相反顺序补偿。适合步骤多、时间长的流程。没有全局隔离，中间状态能被看见。
5. XA 两阶段提交。协调者先让所有参与者准备，再统一提交或回滚。能提供强一致，参与者和协调者的故障都会把锁持有时间拉长。适合短、冲突少、全在内部数据库的操作。Seata 的 AT 记录 SQL 前后镜像和 undo log，提交后删除日志，回滚时按镜像补偿，并用全局锁挡住脏写。它和数据库 XA 的准备协议不同。热点行上的全局锁会限制并发。

方案按隔离要求和持续时间选。下单扣库存若只是两个内部库，可以评估 TCC 或 AT；一旦带上外部支付，就回到本地事务、幂等回调和对账。

### 12. 你认为当前AI技术的发展对Java后端开发会产生哪些具体影响

**参考答案**

模型会变成 Java 服务要调用的一个不稳定、高延迟的下游。原有的事务、幂等和容量规划仍然决定系统是否正确。

写代码时，样板、测试和普通 SQL 会更快。锁的范围、事务包含哪些写、消息是否先于数据库提交，仍要人来判断，生成结果要当成未经审查的补丁。

业务上会多出一类调用。同步接口里直接等待模型几十秒，会占住容器线程并放大超时。调用要单独设超时、限流和降级，能流式返回就不要攒成一个大响应。模型失败或返回无法解析时，不能把订单写成成功。提示词和模型版本要能追踪，否则线上结果无法复现。

系统组件也会多出来：向量检索、调用工具前的权限校验、输入输出的敏感信息处理。密钥和用户数据不能直接拼进发往第三方的提示词。测试不能只靠一条固定断言，非确定性输出要准备抽样评估和人工复核。

对后端岗位，增删改查的差异变小，把模型接进现有链路并在失败时保持数据正确，变成新的基本功。没有实际调用经验时，按这个边界讲影响即可，不必描述一个没做过的智能体平台。

### 13. 当你和团队成员在技术方案上产生分歧时，通常会如何沟通推进

**答题思路**

按事实和约束推进，不编一个具体的争吵故事。有真实例子时，把下面五步填进去。

1. 先复述目标和限制：延迟、一致性、能不能停机、必须什么时候交付。确认双方争的是同一件事。
2. 把方案收成几行对比：正确性、故障时的行为、实现成本、团队熟不熟、怎么回滚。
3. 分歧若来自事实不清，就约定一个小范围验证，并事先写好看哪个结果。验证代替来回讲感觉。
4. 明确谁在什么时间拍板。决定之后按决定做，把当时的前提记下来；前提变了再重开，不在实现途中各写各的。
5. 表述停在方案上。不把分歧说成对方不配合，也不用职级代替理由。

对方问「你遇到过吗」，就讲一次你真正参与的技术选择：你主张什么、最后采用了什么、上线后哪一个判断被验证了。没参与拍板就说自己提供了哪部分依据。

### 14. 你对自己未来三年的技术成长有什么规划

**答题思路**

按能力和能负责的场景讲，不报职级、头衔和薪资数字。规划要和 Java 后端对得上。

1. 近一年：把现在这条业务链路上的数据库、缓存、消息和故障定位讲透，目标是能独立看住一个模块的线上问题。
2. 第二年：能给这个模块出方案，包括容量大概落在哪、哪些地方最终一致、依赖挂了怎么降级。
3. 第三年：在现有业务之外补一块相邻能力。高并发存储，或把模型调用稳妥接进现有服务，选一个和你真实兴趣一致的，不要两个都说成已经在做。
4. 学习方式：一次只跟一个生产问题或一个小示例，能讲清原理和失败场景，再换下一个。

若目前还没有线上模块，就把第一年说成补齐项目里真实用到的中间件，不把规划说成已经负责过整个系统。

### 15. 你有什么问题想问我或者了解我们团队的

**答题思路**

准备两个问题，技术面先问工作本身。用面试里已经出现的方向往下问，表示你在想怎么落地。

可以选：

1. 团队现在的业务是什么，这个岗位上手后大概负责哪一段服务。
2. 线上的技术栈、发布方式和值班是怎么安排的。
3. 前三个月怎样算做得好，是独立接需求，还是先熟悉现有链路。
4. 方案评审和故障复盘平时怎么做。

问法要具体。对方刚才若追问了订单或消息，可以问这条链路更在意延迟还是一致、峰值大概是什么量级。薪资、加班和编制留到 HR，或等对方先开这个话题。没有问题时不要用「没有了」直接结束，至少问清接下来的流程。
