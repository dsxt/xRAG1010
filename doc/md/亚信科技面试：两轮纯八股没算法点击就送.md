### 3. Java中==和equals的区别

**参考答案**

`==` 比较的是值或引用是否相同，`equals` 比较的是对象在业务上是否相等。

基本类型用 `==` 比的是数值。引用类型用 `==` 比的是两个变量是否指向同一个对象。`Object.equals` 的默认实现就是 `==`。`String`、包装类和业务实体通常重写 `equals`，按内容比较。重写 `equals` 必须同时重写 `hashCode`：相等的对象哈希必须相同，否则放进 `HashMap` 时，`equals` 为真也可能找不到。哈希相同并不要求对象相等。

包装类不要用 `==`。`Integer.valueOf` 默认缓存 -128 到 127，自动装箱的小整数 `==` 可能为真，超出范围就是两个对象。比较内容用 `equals`。`null` 不能当调用方，写成 `"常量".equals(变量)` 或 `Objects.equals`。

字符串字面量进常量池，同一段字面量 `==` 为真。`new String("a")` 是堆上的新对象，和字面量 `==` 为假、`equals` 为真。

### 4. String、StringBuilder、StringBuffer的区别

**参考答案**

`String` 不可变，适合常量、Map 的键和跨方法传递。单线程拼接用 `StringBuilder`。`StringBuffer` 只比 Builder 多了方法级同步，新代码很少需要。

`String` 是 final 类。JDK 9 起内部是 `byte[]` 加编码标记，字符都能放进 Latin-1 时按单字节存，否则用 UTF-16；更早是 `char[]`。拼接、替换、截取都返回新对象。不可变才让字面量可以放进常量池，池从 Java 7 起在堆里。

`StringBuilder` 和 `StringBuffer` 都是可变字符序列，默认容量 16，不够时大约按旧容量的两倍再加 2 扩容。Buffer 的公开方法带 `synchronized`，锁只包住一次调用；先看长度再追加这种组合动作仍会交错。多线程各自拼接时，各自持有一个 Builder。

一条表达式里的 `+` 会收成一次构建。JDK 9 起单次拼接走 `invokedynamic`，不一定是源码里的 `StringBuilder`。循环里写 `s = s + x`，每一轮仍然得到新的 `String`，应在循环外持有一个 `StringBuilder`。

### 5. 讲一下Java的垃圾回收机制

**参考答案**

垃圾回收从 GC Roots 做可达性分析，不可达的对象才会被收。HotSpot 按分代处理，JDK 8 默认是 Parallel，JDK 9 起默认是 G1。

根包括虚拟机栈里的引用、静态字段、JNI 引用和同步监视器等。循环引用只要整体不可达就能收，不靠引用计数。软引用在内存紧张时回收，弱引用挡不住回收，虚引用用来做回收后的清理。对象还被静态集合、线程池里的 ThreadLocal 或未关闭的资源指着，回收不了，这是泄漏，不是 GC 失效。

对象一般在 Eden 分配。年轻代回收把 Eden 和一块 Survivor 里的存活对象复制到另一块 Survivor，年龄加一。年龄到阈值（默认 15），或 Survivor 放不下，或触发动态年龄，就晋升老年代。复制没有碎片，代价是要留出空间。

老年代由收集器决定。标记-清除会留碎片，标记-整理能把活对象挤到一端。G1 把堆切成 Region，日常做年轻代回收；并发标记之后用 Mixed GC 连同一部分垃圾多的老年代 Region 一起复制。`MaxGCPauseMillis` 默认目标 200 毫秒，是目标，不是上限。复制失败会退化成整堆 Full GC。ZGC 把停顿压得很短，CPU 和内存开销更高，停顿并不是零。

`System.gc()` 只是建议，可以用参数关掉。`finalize` 已废弃，不要拿它做释放。到达安全点才会停下来回收，对象变成不可达后也不会立刻消失。

### 6. 什么是双亲委派模型

**参考答案**

类加载请求先交给 parent，parent 加载不了，当前加载器再自己找。每个加载器只有一个 parent，并不是两个父加载器。

层次是启动类加载器、平台类加载器、应用类加载器，再到自定义加载器。JDK 8 的扩展类加载器，在 JDK 9 起换成平台类加载器。`ClassLoader.loadClass` 先看自己是否已经加载过，再交给 parent，parent 抛出找不到，才调用 `findClass`。自定义加载器一般只覆盖 `findClass`。

好处是 `java.lang.String` 由启动类加载器加载，应用 classpath 上的同名类不会被用上。类的身份是「全限定名 + 定义它的加载器」，核心类只加载一次。两个应用之间的隔离来自不同的加载器，不是来自这套委派顺序。

打破它的场景要单独记。JDBC 这类 SPI 用线程上下文类加载器，让上层加载器找得到应用里的驱动。Tomcat 的 Web 应用类加载器默认先查自己的类，再交给 parent，避免应用和容器的类混在一起。

### 7. Spring Bean的生命周期

**参考答案**

单例 Bean 的路径是实例化、填充依赖、初始化、使用、销毁。AOP 代理包在初始化之后。

1. 实例化。构造器注入发生在这一步。
2. 填充属性。字段和 setter 上的 `@Autowired` 在这里完成，早于 `@PostConstruct`。
3. 回调 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。
4. `BeanPostProcessor` 的前置处理。`ApplicationContextAware` 等其余 Aware 在这里注入，`@PostConstruct` 也在这里执行。
5. `InitializingBean.afterPropertiesSet()`，然后是自定义 init-method。
6. `BeanPostProcessor` 的后置处理。声明式事务和 AOP 的代理通常在这里包到目标对象外面。
7. 投入使用。
8. 容器关闭时销毁单例：先 `@PreDestroy`，再 `DisposableBean.destroy()`，最后自定义 destroy-method。

`@PostConstruct` 早于 `afterPropertiesSet`，二者都早于代理生成。在初始化回调里调用本类的事务方法，调用的是目标对象，拦截器不会生效。原型 Bean 容器创建后不再跟踪，默认也不会调销毁回调。构造器循环依赖在实例化阶段就会失败；单例的属性循环依赖才可能靠提前引用，Spring Boot 2.6 起默认还禁止循环依赖。

### 8. Spring AOP的实现原理

**参考答案**

Spring AOP 默认是运行时代理，只拦截方法执行，不是编译期织入。

`@EnableAspectJAutoProxy` 注册 `AnnotationAwareAspectJAutoProxyCreator`。它作为 `BeanPostProcessor`，在 Bean 初始化之后按切点决定要不要包一层代理。目标有接口、且没有强制按类代理时，用 JDK 动态代理，代理对象实现那些接口，不能强转成目标类。否则用 CGLIB 生成子类。Spring Boot 默认按类代理，有接口也常用 CGLIB。`final` 类和 `final` 方法无法被 CGLIB 覆盖，private 方法也不会被增强。

调用进入代理后，命中的通知排成一条链，沿 `proceed` 前进。Around 包住整次调用，Before 在业务之前，After 无论成败都执行，AfterReturning 和 AfterThrowing 看结果。多个切面用 `@Order`，数值小的包在外层。

对象内部自己调自己的方法不经过代理，切面和声明式事务都不会生效。要生效就把调用改到注入进来的代理上，或打开 `exposeProxy` 再取当前代理。`new` 出来的对象不在容器的代理里。需要拦截构造器、字段或自调用时，才用 AspectJ 编译期或加载期织入。

### 9. MySQL索引有哪些类型

**参考答案**

InnoDB 里和业务直接相关的是 B+ 树索引。先分数据结构，再分它是聚簇索引还是二级索引。

按数据结构：B+ 树是 InnoDB 和 MyISAM 普通索引的形态，非叶子只放键，叶子连成有序链表，适合等值和范围。哈希索引用于 Memory 引擎，等值很快，做不了范围和排序。InnoDB 不提供让用户建的哈希索引，只对热点页自动维护自适应哈希。全文索引是倒排，用 `MATCH ... AGAINST`，不能替代范围查询。空间索引用 R 树，服务地理类型。

按和数据的关系：InnoDB 的聚簇索引就是主键，叶子放整行。没有主键时用第一个全非空的唯一索引，再没有就生成隐藏行号。一张表只有一个聚簇索引。二级索引的叶子放索引列和主键，查其他列要回表。查询列都在这棵二级索引里，就是覆盖索引，不必回表。主键很长时，每棵二级索引都会变大。

按约束还有主键、唯一、普通、联合、前缀索引。MySQL 8.0 还可以给表达式建索引。联合索引服从最左前缀，范围条件后面的列不能再用于查找。前缀索引只取列的前若干字符，区分度不够时过滤差，也不能靠它覆盖这一列的完整值。`LIKE '%关键字'` 用不上普通 B+ 树。

### 10. 什么是事务的隔离级别

**参考答案**

标准隔离级别有四种，用来逐级约束脏读、不可重复读和幻读。InnoDB 默认是可重复读。

脏读是读到了别的事务尚未提交的修改。不可重复读是同一行读两次，中间被别的已提交事务改了值。幻读是同一个范围条件查两次，行集合因为别的事务插入或删除而变了。

1. 读未提交：三种现象都可能出现，线上基本不用。
2. 读已提交：不再脏读。同一行两次读取仍可能不同，范围查询也可能看见新行。Oracle 通常默认这一级。InnoDB 在这一级按语句建立新的读视图。
3. 可重复读：普通的一致性读沿用事务里第一次建立的读视图，别的事务后来的提交不会改变你再读同一行的结果。这是 MySQL 的默认级别。`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，读最新已提交版本并加锁；这一级用临键锁，也就是记录锁加间隙锁，挡住范围里的插入。
4. 串行化：关闭自动提交时，普通 `SELECT` 会被改成加共享锁的当前读，读写互相阻塞，并发最差。

标准 SQL 里，幻读要到串行化才要求消除。InnoDB 的可重复读多做了两件事：一致性读复用同一张快照，加锁读使用临键锁。快照读不加锁，当前读仍会加锁，两者看到的版本可以不同。隔离级别替代不了更新丢失所需的版本号或 `SELECT FOR UPDATE`。

### 11. Redis有哪些数据结构

**参考答案**

常用的是字符串、哈希、列表、集合、有序集合。位图、HyperLogLog、地理位置和 Stream 是在这些能力上的专门类型。Redis 适合缓存、计数和短临界区，订单是否支付仍以数据库为准。

- 字符串：缓存一个对象，用 `INCR` 做计数，用 `SET key value NX EX` 做带过期的互斥。单个字符串最大 512MB。内部按长度走整数、embstr 或 raw。
- 哈希：缓存对象的若干字段，只更新变化的字段。元素少时用紧凑编码，变大后转成哈希表，具体阈值随版本变化，不必背数字。
- 列表：一头推进、另一头弹出，可以留最近 N 条。阻塞弹出能做简单队列，没有消费者组和长期回放。
- 集合：去重、交集、随机弹出。成员都是整数且数量少时用整数集合，否则用哈希表。
- 有序集合：成员带分数，用来做排行榜。把执行时间当分数，可以做按时间弹出的延迟任务；弹出要用 `ZPOPMIN` 或 Lua，把取出和删除做成一次操作。小对象用紧凑编码，变大后是跳表加哈希表。

位图按位统计签到，偏移特别大时字符串会被撑开。HyperLogLog 估算很大的独立访客，结果有误差，内存有上限。地理位置把 geohash 放进有序集合。Stream 带消费者组和待确认列表，适合同一业务进程里的事件流；要长期保留和回放的日志仍交给专门的消息队列。

### 12. 如何保证缓存与数据库的一致性

**参考答案**

旁路缓存做的是最终一致：读的时候先读缓存，未命中再读库并回填；写的时候先提交数据库，成功后再删除缓存。要读到强一致结果的请求直接读库，不走这套缓存。

写路径去更新缓存时，两个写并发，后完成的那个旧请求会把缓存写成旧值，库里已经是新值。删除缓存则下一次读会回源，窗口更小。先删缓存再更新库，中间的读会把旧行装进缓存，库更新之后，这份旧值会一直留到下一次写或 TTL 到期。删除要放在事务提交成功之后；提交前就删，别的请求仍会读到旧的已提交行并回填。

先更新库再删除，仍有一个窄窗口：一个读已经拿到旧行，写提交并删了缓存，然后这个读把旧行写回去。缓存值带上版本或更新时间，回填时发现已有更新的版本就放弃。同一个 key 用单飞，只放一个请求回源。删除失败要重试，或订阅 binlog 再删一次。TTL 是兜底，这次没删掉，旧值也会过期。延迟双删是提交后再删第二次，用来盖住回填旧值的窗口，延迟时间不好估，binlog 更稳。

写完立刻读从库再回填，会把还没跟上的旧行写进缓存。回源读主库。缓存击穿、穿透和雪崩是另一组问题：热点失效用单飞和逻辑过期，不存在的 key 缓存短 TTL 的空值，大批 key 同时过期就把 TTL 打散。

### 13. 了解AI在Java开发中的应用吗

**参考答案**

Java 里的 AI 应用分两层：写代码时用辅助工具，以及业务服务去调用模型。模型是一个高延迟、会失败、输出不稳定的下游，事务和幂等仍由 Java 负责。

开发辅助是补全、起草测试和解释报错。生成结果按未经审查的补丁处理，锁、事务边界和权限要人来定。

业务调用常见有四类。一是同步问答或工单分类，Java 用 Spring AI、LangChain4j 或直接 HTTP 调模型。二是检索增强：文档切段、向量化，放进 pgvector、Elasticsearch 或专用向量库，检索后再拼进提示词。三是让模型按给定工具查内部接口，工具的权限和参数校验在 Java 侧。四是异步摘要、归类，用消息把耗时调用挪出下单这类主链路。

工程上要单独设超时、限流和降级，解析不了的输出不能把业务写成成功。提示词模板和模型版本要能追踪。密钥和用户原文不要打进日志，也不要无约束地发给第三方。面试时只展开自己真正用过的那一层；看过文档就说是了解，不说成已经上线。

### 14. 如果让你设计一个简单的AI服务接口，你会考虑哪些方面

**参考答案**

接口只做一件事：把一次生成变成可超时、可追踪、失败时不污染业务数据的调用。短请求同步返回，长生成用流式或任务号，不要让调用方一直占着一条无超时的连接。

同步接口接收业务字段、模型名和输出格式，由服务端套上版本化的提示词模板。客户端直接传整段系统提示词时，线上结果无法复盘，也容易被注入改掉规则。需要逐字返回时用 SSE，客户端断开要取消上游，避免白烧 token。预计要跑几十秒的，返回任务号，调用方轮询或等回调，任务状态持久化。

保护放在模型调用外面。按用户限流和配额，限制输入长度和 `max_tokens`。客户端重试用幂等键，生成本身不要无脑重试。超时预算从网关到模型客户端逐段变短。失败时返回明确错误，或降级到规则结果；解析不成约定的 JSON，就不要写入订单或工单状态。

模型供应商藏在适配器后面，业务代码只看见自己的请求和响应。日志记请求号、模型版本、耗时、token 和错误类别，不记密钥和完整的用户隐私。同一个接口要能按版本对比效果，否则换了模型却说不清是变好还是变差。

### 2. 详细介绍一下你最熟悉的项目

**答题思路**

按一次请求的路径讲，大约 5 分钟，让对方能画出框。模块名称和边界用真实项目。

1. 入口在哪，鉴权和限流放在网关还是服务里。
2. 服务怎么分。哪些调用是同步的，哪些已经改成消息。
3. 数据：哪份库是准据，缓存放什么、失效后以谁为准，每个主题谁生产、谁消费。
4. 正常路径选一条请求，从入口讲到落库。标出哪里是本地事务。
5. 失败路径：重复提交、下游超时、消息至少投递一次，这三件里挑你真实处理过的讲。幂等键放在哪要说清。
6. 你的边界：哪些接口和表是你的。没参与的部分不要讲成自己的设计，没做过的容量数字不要补。

### 3. 项目中遇到的最大挑战是什么

**答题思路**

只讲一件你亲手处理过的事。想不起「最大」时，就讲一次线上故障或一次把数据改正确的改造，不要编一个宏大架构。

1. 先说约束：慢在哪里、错在哪里、能不能停机、数据能不能重放。
2. 至少两个可选做法和各自的代价，例如先加索引还是先加缓存，同步调用还是消息。
3. 你选了哪一个，放弃另一个的原因落在一致性、延迟、复杂度和当时的人力上。
4. 怎么验证：看哪条日志、哪个指标或哪一种对账。记得住数量级就说数量级，记不清就不说精确百分比。
5. 上线后还剩什么风险。一个人完成和跟别人一起完成，按真实情况说。

### 4. 如何设计一个高并发的秒杀系统

**参考答案**

秒杀先把打到数据库的请求减下来，再用条件更新守住最终库存。Redis 负责挡流量，数据库负责最终数量。只靠数据库时热点行会在开场被锁住；只靠 Redis 时，持久化窗口里的宕机会把剩余数量弄丢。

1. 入口把页面静态化放到 CDN。网关按用户和活动限流。库存已经是 0 时，在应用本地记住售罄标记，短时间内不要再访问 Redis。
2. 活动前把可售数量预热到 Redis。判断和扣减放进 Lua，一次做完。键不存在就失败，不能把空值当成还有货。集群里这个操作只碰一个库存键，避免跨槽。

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if (not stock) or (stock < tonumber(ARGV[1])) then
  return -1
end
return redis.call('DECRBY', KEYS[1], ARGV[1])
```

3. 预扣成功才把下单消息放进队列，消费者按数据库写得动的速度创建订单。队列堆积超过阈值就在入口拒绝。
4. 落库用条件更新做最后核对。同一用户和活动加唯一约束，重复点击插不进第二单。预扣成功但进程在入队前退出，库存会暂时少一件，用预扣流水对账加回去。

```sql
UPDATE seckill_stock
SET available = available - 1
WHERE sku_id = ? AND available >= 1;
```

5. 创建订单失败，或超时仍未支付，按同一业务单号把 Redis 和数据库的库存加回，回补本身也要幂等。关单前先核对支付结果，已经付成功的走退款。单行热点仍顶不住时，把库存拆成多段，分段带来对账成本。Redis 故障时停止开卖，按数据库剩余量重建。

### 5. 如何保证分布式系统的一致性

**参考答案**

先说清要的是哪一种一致。线性一致是读到最新已提交的写；事务隔离是一个库里并发事务能看见什么；缓存和库通常只做最终一致。网络分区发生时，不能同时保证线性一致和完全可用。分区是故障，不是一个可以事先丢掉的选项。

能放进同一个库的写入，用本地事务。跨服务的默认做法是每个服务提交自己的本地事务，再用可靠消息把结果送出去，消费按业务键幂等。

1. 发件箱：业务修改和一条待发送记录在同一个本地事务里提交，后台再投递。投递是至少一次。窗口期内会出现上游已提交、下游还没完成。
2. 事务消息：以 RocketMQ 为例，先发半消息，本地事务成功后再让消息可投递，状态不明时由 Broker 回查。少维护一张投递表，但中间件要支持这套协议。
3. TCC：Try 预留，Confirm 确认，Cancel 释放。三个接口都按业务单号幂等，还要处理取消先到。适合必须先占住库存或余额的场景。
4. Saga：每步提交本地事务，失败按相反方向补偿。步骤多、时间长时用它。没有全局隔离，中间状态能被看见。
5. XA：协调者先准备再统一提交，能做强一致，故障时锁会持得很久。适合参与方少、可以同步等待的内部库。Seata AT 靠 undo log 回滚，并有全局锁，和数据库 XA 的准备协议不同。

外部支付不要放进全局事务。消息会重复，也会乱序，对账扫未投递的发件箱和未完成的补偿。要读到自己刚写的结果，就读负责写入的那个库。

### 6. 消息队列如何保证消息不丢失

**参考答案**

生产、存储、消费三段都确认成功，才不会因为单点重启把消息丢掉。实际做到的是至少一次，重复靠业务键消化。不要口头保证恰好一次。

生产者要把「收到确认」定义成发送成功。调用返回时，消息可能还在客户端缓冲区，进程退出就没了。失败要重试，重试会带来重复。Kafka 生产环境显式确认 `acks=all` 并开启幂等；旧客户端的默认曾经是 `acks=1` 且不幂等。幂等生产者用分区内序列号去掉同一次会话里的重试重复。RabbitMQ 要打开发布确认，队列持久，消息本身也标成持久。RocketMQ 用同步发送，并按耐久要求选择同步刷盘和同步复制。

Broker 侧，Kafka 副本因子至少 3，`min.insync.replicas` 设为 2。`acks=all` 只等待当前 ISR，而 `min.insync.replicas` 的常见默认是 1，只剩 leader 时也会应答成功。落后副本不能当选 leader，否则会截断已经确认的消息。应答表示 ISR 已经写入各自日志，数据多半还在操作系统页缓存里；所有副本同时掉电时，尾部仍可能丢。业务写和发消息若来自同一次修改，要在同一个本地事务里写业务表和发件箱，再异步投递。

消费者处理成功后再提交位移或确认。按间隔自动提交时，提交的是已经拉到的位移，处理还没完成就重启，这条不会再来。处理完再确认会在崩溃时重复投递，所以按订单号或消息键做幂等。写入业务库和提交位移不是一个事务。

### 7. 如何优化数据库查询性能

**参考答案**

先证明时间花在执行计划、锁等待还是返回的数据量上，再改索引或 SQL。还没看计划就加一堆索引，写入变慢，优化器也可能选错。

从慢查询日志拿出语句，看 `EXPLAIN` 的 `type`、`key`、`rows` 和 Extra。`ALL` 是全表扫，`Using filesort`、`Using temporary` 说明还要额外排序或落临时表，`Using index` 才是覆盖索引。MySQL 8 可以用 `EXPLAIN ANALYZE` 看实际耗时。扫描行数不大、时钟时间很长，先查行锁和元数据锁，这不是加索引能解决的。

索引对准 WHERE、JOIN、ORDER BY 里真正用来过滤的列，联合索引从左连续用起。对列套函数、隐式类型转换、前导通配的 `LIKE`，都会让这列上的索引用不上。查询列都在索引里就不必回表。不要 `SELECT *`。深分页的 `LIMIT 100000, 20` 会先扫过再丢掉，改成按主键或排序列记住上次位置再向后取。统计信息过期时用 `ANALYZE TABLE` 更新，不要凭表大小口头判断谁驱动谁。

单条 SQL 已经合理，再看架构：热点读放缓存，历史数据归档，只读请求才走从库。刚写完要读到自己的更新时仍读主库。事务里不要包远程调用，锁持有时间会表现为别的查询变慢。

### 8. 如何排查线上CPU飙高的问题

**参考答案**

先分开两件事：业务线程在烧 CPU，还是 GC 线程在烧 CPU。

`top` 确认是这个 Java 进程，再看用户态、内核态和 IO 等待。等磁盘高，就去看 IO，不是去改计算。然后 `top -Hp <pid>` 找出最忙的线程，线程号转成十六进制，到 `jstack` 或 `jcmd <pid> Thread.print` 的 nid 里对上。Arthas 的 `thread -n` 可以少做换算。

一个业务线程高，看死循环、正则回溯、大对象序列化、加密和热路径上的空转。一排 GC 线程高，转去 `jstat -gcutil` 和 GC 日志：回收之后老年代掉得下去又很快涨满，是分配太快或晋升太多；掉不下去，是存活集太大或泄漏。很多业务线程都高而且 QPS 也高，先确认是不是流量本身上来了。

`jstack` 只是一个瞬时快照，偶发尖刺用 JFR 或 async-profiler 采一段时间，火焰图里才能看见业务函数、GC 和本地代码各占多少。容器里还要看 cgroup 配额是不是把进程限流了。先留线程栈和 GC 日志，不要一上来就重启，现场会消失。

### 9. 微服务架构有哪些优缺点

**参考答案**

微服务按业务边界拆成能独立部署的服务。边界和团队都清楚时，它换来的是独立发布和扩容；边界不清楚时，它只是把一次进程内调用换成网络调用。

好处是每个服务可以按自己的流量扩容，小团队各自发布，故障有机会留在一个服务里。技术栈可以不同，但运维和排障的成本也会上去。故障隔离要靠超时、舱壁和熔断，拆开本身并不会自动隔离。

代价是网络会失败、会变慢。跨服务没有一个本地事务，一致性要改成发件箱、补偿和对账。一次请求横跨很多同步调用时，延迟和故障面会叠在一起。数据被拆开之后，原来的表连接变成了服务调用或冗余数据。日志、指标和链路追踪变成必选项。测试要补契约，否则各自发布会把对方的接口改坏。

拆得过细、又同步串成一条链、甚至还共用一个库，就是分布式单体：发布独立了，故障和事务仍然绑在一起。领域和团队都还没稳定时，模块化单体更合适。已经拆开的，同步调用要有明确超时，跨库写入按最终一致来设计。

### 10. Redis持久化方式有哪些

**参考答案**

有两种：RDB 是某一时刻的快照，AOF 是追加写命令。两边可以同时开，AOF 还可以在重写时把 RDB 格式放在前面。它们保的是这台机器重启后还在的数据，替代不了另一台机器上的副本。

RDB 常用 `BGSAVE`。父进程 fork 出子进程，子进程把 fork 那一刻的数据写成二进制文件，写完再原子替换。父进程继续处理命令，改过的内存页会被复制一份，所以大实例 fork 时可能卡住，内存也会升高。`SAVE` 会堵住主线程，只在维护时用。触发靠手动命令，或按时间窗口里的写次数自动触发。常见配置是三条规则满足任意一条即保存：3600 秒内至少 1 次写、300 秒内至少 100 次、60 秒内至少 10000 次。文件小、恢复快，适合备份和从节点的全量基础。两次快照之间的写入会丢。

AOF 把写命令追加到文件末尾。`always` 每条都刷，最不容易丢也最慢；`everysec` 大约每秒刷一次，是开启 AOF 后的常见默认，宕机大约丢一秒；`no` 交给操作系统。文件变大后 fork 子进程重写。Redis 4.0 起重写结果可以先是 RDB、后面再跟增量命令；Redis 7 起可以分成基础文件和增量文件，用清单管理。开启 AOF 时，重启优先用 AOF 恢复，因为它通常比最近一次 RDB 更完整。

只当缓存、丢了可以从数据库装回来，可以关掉持久化。要秒级以内少丢数据，用 AOF 的 `everysec`。Redis 的持久化替代不了数据库事务。

### 11. Kafka如何保证消息顺序

**参考答案**

Kafka 只保证单个分区里的追加顺序，不保证整个 Topic 的全局顺序。需要顺序的消息用同一个 key，让它们进同一个分区。

默认分区器按 key 哈希选分区。没有 key 时，新版本的粘性分区器会把一批消息写进同一个分区，换一批可能换分区，跨批没有顺序。两个生产者写同一个 key，记录仍会在分区里交错，顺序只存在于各自的发送序列里。

重试会打乱顺序的前提是：没开幂等，并且同一个连接上有多条请求在途。幂等生产者给分区分配序列号，Broker 按序列号接日志，同一次生产者会话里的重试不会插到后面的消息之前。开启幂等时，在途请求数不能超过 5。旧客户端若关闭幂等又允许多个在途请求，就要把在途数降到 1，用吞吐换顺序。

一个分区在同一个消费组里只会分给一个消费者。这个消费者若把拉到的一批再并发处理，业务顺序就没了。要顺序就在该分区上单线程处理，成功后再提交位移。失败消息丢进重试主题、本分区继续往后消费，也会把后面的消息先处理掉。严格按 key 有序时，这个 key 要停在原地，直到当前消息成功。全局有序只能用一个分区，吞吐受这一分区限制。扩分区之后，同一个 key 的新消息可能进新分区，旧分区里还没消费完的记录仍可能晚到。

### 12. 在项目中如何应用AI技术

**答题思路**

按自己真实到过的深度讲，把「产品里调用模型」和「自己写代码时用辅助工具」分开。这场如果对方不追问，两分钟内收住。

1. 先说场景：要解决的是分类、检索、摘要，还是只是写代码更快。没有业务调用，就直接说辅助编程用到什么程度，不另编一个智能体项目。
2. 真的接过模型时，按这条线讲：调用放在主链路里还是异步、超时和失败时业务状态停在哪、输出解析失败怎么办、密钥放在哪。
3. 只跑过示例或看过文档，就说是学习和试用。检索增强、工具调用、多智能体这些名词，没做过就不要说成项目经验。
4. 效果只用记得住的现象。没有评测数据，就说当时怎么人工核对，不编准确率。

### 13. 对AI辅助编程的看法

**参考答案**

辅助编程适合当草稿和阅读工具，合并进仓库的每一行仍然要由人负责。

它适合生成样板、起草测试、解释不熟的 API、把一段报错和调用栈对照起来。这些输出能缩短起步时间。事务里包含哪些写、锁的范围、SQL 会不会走索引、权限有没有放宽，生成结果经常看起来能跑，边界是错的。大段接受之后，如果没人能讲清失败时的数据状态，这段代码就不能进核心链路。

使用时把密钥、生产数据和用户隐私留在工具外面。外部模型的回答要回到官方文档或源码核对。团队里，辅助生成的 diff 和手写的 diff 走同一套评审，不因为是生成的就降低标准，也不用它代替设计评审。

对自己的要求是：用它加快阅读和第一稿，对并发、一致性和安全相关的改动逐行看完再提交。没有在项目里形成流程，就说是个人在用，不说成团队已经靠它改生产。

### 14. 未来的职业规划是什么

**答题思路**

按能力和能负责的场景讲，不报职级、头衔和薪资数字。规划对着 Java 后端，以及这场里已经聊到的中间件和 AI 应用。

1. 近一年：把现在这条链路上的 MySQL、Redis、消息队列和故障定位讲透，目标是能独立看住一个模块的线上问题。
2. 接下来：能给这个模块出方案，包括哪些地方最终一致、依赖挂了怎么降级、一次 CPU 或慢查询怎么查。
3. 再往后补一块相邻能力。高并发下的存储和一致性，或把模型调用稳妥接进现有服务，只选一个和你真实兴趣一致的，不要两个都说成已经在做。
4. 学习方式：一次只跟一个生产问题或一个小示例，能讲清原理和失败场景，再换下一个。

若目前还没有线上模块，就把第一年说成补齐项目里真实用到的中间件，不把规划说成已经负责过整个系统。
