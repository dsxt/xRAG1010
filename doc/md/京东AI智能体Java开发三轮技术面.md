### 3. Redis 在高并发场景下用作缓存，常见的缓存问题有哪些（如击穿、穿透、雪崩）？你的解决思路是什么？

**参考答案**

结论：三个名字对应三种流量形态。穿透是在查一定不存在的数据，击穿是一个热点 key 失效后并发打到数据库，雪崩是一大批 key 同时失效，或者 Redis 自身不可用。

穿透：业务先写库再删缓存的正常路径挡不住「库里从来没有」的 key。可以短暂缓存空值，写入真实数据时覆盖它，TTL 要短，避免空值把刚写进库的数据挡住。布隆过滤器适合挡海量不存在的 key：它说没有就直接返回，说可能有才查库。误判会放进少量请求。删除数据后普通布隆不能摘掉成员，要换计数布隆或定期重建，否则会把已删除的 key 放行，或者把新 key 错挡在外面。

击穿：热点过期的瞬间，很多请求同时发现缓存没有，一起回源。重建要互斥，用带过期时间的锁让一个请求回源，其余等待或短暂返回旧值。更稳的是逻辑过期：缓存值里带失效时间，数据可以先返回，由单独的线程刷新。互斥锁要有 TTL，拿锁的请求挂了不能把热点永久锁死。

雪崩：给 TTL 加随机抖动，避免同一批数据在同一秒过期。Redis 用主从或集群，并设置内存淘汰策略，避免打满后大面积写失败。应用侧对回源限流，数据库顶不住时熔断，非核心读返回旧值或默认值。本地缓存只能接极热的一小部分，并要有上限和失效途径。

缓存和数据库谁更新谁，是一致性问题，和上面三种故障分开讲。

### 4. Redis 的分布式锁如何实现？在极端情况下（如主从切换）可能有什么问题？有更好的替代方案吗（可提及 Redlock 或基于 ZooKeeper、etcd 的实现）？

**参考答案**

结论：Redis 锁适合「重复做一次只是浪费」的互斥。主从切换会丢锁；红锁有争议，也不能靠它保护资金和库存。正确性要求高时，用 etcd 或 ZooKeeper 拿到单调的租约令牌，并由存储拒绝过期令牌。

实现用一条命令完成「不存在才设置，并带过期时间」，避免 `SETNX` 成功后进程崩溃、还没执行 `EXPIRE`：

```lua
-- 解锁：只删除自己持有的锁，比较和删除必须原子
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

value 用每次加锁独有的令牌。过期时间必须大于业务正常耗时；客户端还活着就定期续期，进程死了就停止续期，锁自己到期。进程若卡顿超过租约，锁会被别人拿走，原持有者醒来仍会往下执行。所以租约只能保证「大概互斥」。

主从切换的洞在异步复制：主节点已经向客户端确认加锁，复制还没到从节点，主节点宕机，从节点升主，第二个人也能加锁。Redlock 要求的是多套独立主节点，过半加锁成功，并且花费的时间必须明显小于租约。把它部署成一主两从，解决不了上面的复制窗口。它仍依赖时钟和「进程不会停顿超过租约」，也没有一个存储能识别的围栏令牌。进程暂停、租约到期、另一个客户端加锁成功后，暂停的那个客户端继续写，Redlock 挡不住。

etcd 用租约加事务比较创建：key 不存在才写入，租约到期或会话断了锁就释放，ModRevision 作为围栏令牌交给数据库。ZooKeeper 用临时顺序节点，序号最小的持有锁，只监听前一个节点，避免惊群；会话超时会删掉临时节点。两者都基于共识，锁的归属是线性一致的。真正防止旧持有者晚到写入的，是资源侧拒绝更小的令牌，例如数据库里记录已接受的最大令牌，过期写入更新 0 行。只有协调服务、存储不校验令牌，暂停的客户端仍能写脏。

库存和支付以数据库唯一约束或版本号为准。Redis 锁用来减少冲突，不能当作唯一的正确性保证。

### 5. Kafka 如何保证消息的有序性？在 Consumer 端扩容时，如何避免有序性被破坏？

**参考答案**

结论：Kafka 的顺序只存在于同一个分区内部。需要按订单、用户或会话有序时，用这个业务键做消息键，让同一个键始终进同一个分区，再由一个消费者按位移顺序处理该分区。

生产者侧，默认分区器按 key 的哈希对分区数取模。幂等开启时，broker 按分区序列号接受写入，同一分区的在途请求不能超过 5，重试也不会把后写成功的批次排到先发批次前面；超过这个在途上限时，生产者会在配置阶段拒绝启动。幂等关掉且允许多个在途请求时，失败重试才会打乱同一分区的顺序。没有 key 的消息会轮询分区，谈不上业务顺序。

消费者组里，一个分区同一时刻只分给一个消费者，这是顺序的前提。处理必须沿位移往前：这一条成功并提交位移，再处理下一条。把一个分区的消息扔进无序线程池，分区内的顺序就没了。要并行，就按键分条，同一个键进同一条队列。

扩容要分开看。只增加消费者、不增加分区时，重平衡会把分区从旧消费者挪走。旧消费者必须在撤销时停掉该分区的处理，按顺序提交已经完成的位移；新消费者从已提交位移接着读，顺序还在。协作式粘性分配可以只挪必须挪的分区，减少全部分区停下来的时间。自动提交、或者撤销后旧消费者还在处理，会出现重复、跳跃，看起来像乱序。

增加分区才能提高并行度，但默认取模会把同一个 key 映到新分区。旧分区里还有这个 key 的历史消息，新消息已经进了另一个分区，两个消费者会并行处理同一个键，顺序被破坏。已经按 key 有序的主题，不能靠直接加分区来扩容。可行的做法是：分区数按峰值一次规划够；或者自定义分区器，把旧 key 钉在原分区，只让新 key 使用新分区。全局严格有序意味着单分区，吞吐上不去，一般不是目标。

### 6. 如果使用 Kafka，如何设计才能实现「精确一次」（Exactly-Once）的语义处理？需要考虑哪些方面？

**参考答案**

结论：先界定边界。Kafka 事务能做到「从 Kafka 读、处理、再写回 Kafka」这一段只生效一次。写数据库或调用外部 HTTP，要靠同一本地事务，或者靠幂等键，事务本身覆盖不到这些副作用。

Kafka 内部用事务把输出消息和消费位移绑在一起。生产者开启幂等并配置稳定的 `transactional.id`，同一个任务重启后仍用这个 id，新实例会把旧实例围栏掉。消费端关掉自动提交，隔离级别用 `read_committed`，这样未提交和已回滚的事务消息不会被读到。

```java
producer.beginTransaction();
producer.send(new ProducerRecord<>("out-topic", key, result));
producer.sendOffsetsToTransaction(
        Map.of(tp, new OffsetAndMetadata(record.offset() + 1)),
        consumer.groupMetadata());
producer.commitTransaction();
```

位移要提交「下一条要读的位置」，并带上消费者组这一代的元数据。只传组名的旧接口，重平衡后可能把过期的位移写进去。`ProducerFencedException` 表示这个事务 id 已经有新实例，旧进程必须退出，不能再 `abort` 后继续用同一个生产者。一批拉取放进一个事务：太大占着事务协调器，后面的已提交消息也要等未完成事务结束才能被 `read_committed` 的消费者看见；太小则提交过于频繁。

broker 侧要让已确认的消息真的落在多数副本上：`acks=all`，同步副本数留有余量，关闭不干净的领导者选举。否则已确认的数据会丢，精确一次没有基础。

落到 MySQL 时，用另一种边界：业务写入和「主题、分区、位移」放进同一个数据库事务，重启后按库里的位移 seek，不再向 Kafka 提交。Kafka 至少投递一次，数据库用唯一约束把重复事件挡掉，效果上只应用一次。调用支付、发消息这类外部接口时，带上事件 id 作为幂等键，对方按这个键去重。没有幂等键的外部调用，重复消费就会重复生效。

处理逻辑本身要能重放：事务回滚后这批消息会再次到来。用外部调用的结果决定事务能否提交时，要先确认那次调用有没有成功，避免回滚了事务、副作用却已经发生。

### 7. MySQL 的 InnoDB 存储引擎下，事务的隔离级别「可重复读」（RR）是如何通过 MVCC 机制实现的？「幻读」在 RR 级别下真的完全解决了吗？

**参考答案**

结论：RR 下，普通 `SELECT` 用第一次快照读建立的 Read View，两次读同一范围看不到别的事务新插入的行。这只覆盖快照读。当前读要靠 next-key 和间隙锁；快照读和当前读混在同一个事务里时，后面仍可能看见新行。不能说幻读在任何读写组合下都消失了。

一行上有最近一次修改它的事务 id，以及指向 undo 的回滚指针。快照读不沿当前最新版本硬读，而是顺着 undo 找「对自己可见」的那一版。Read View 记下创建时还没提交的事务、其中最小的事务 id，以及当时下一个将分配的事务 id。某个版本可见的规则是：自己写的可见；事务 id 比当时所有活跃事务都小，说明早已提交，可见；大于等于下一个将分配的 id，说明是快照之后的修改，不可见；落在中间的，创建快照时还活跃就不可见，当时已经提交就可见。不可见就沿 undo 找更老的版本。

RR 在事务里第一次快照读时建立这个视图，之后的普通查询都用它，所以同一行的旧版本稳定，别的事务提交的新插入也不进入这个视图。读已提交则是每条语句一个新视图。undo 里没人需要的老版本才会被清理。事务一直开着，Read View 就一直握着，undo 膨胀，版本链变长。

幻读指的是同一范围的行集合变了，和「同一行的值变了」不是一回事。InnoDB 在 RR 下对加锁读和 `UPDATE`、`DELETE` 使用 next-key 锁，也就是索引记录上的记录锁加上记录前面的间隙。别的事务要往这个间隙插入，会和间隙锁冲突。唯一索引上等值命中已有记录时，只锁这条记录，因为不可能再插入同一个键。普通 `SELECT` 不加这些锁，它只是「看不见」，并没有阻止别人插入。

混用时幻读会露出来。表 `t` 有主键 `id` 和整数列 `c`：

```sql
-- 会话 A（RR）
BEGIN;
SELECT * FROM t WHERE id = 1;           -- 快照读，没有这行

-- 会话 B：INSERT INTO t (id, c) VALUES (1, 1); COMMIT;

SELECT * FROM t WHERE id = 1;           -- 仍然没有，Read View 未变
UPDATE t SET c = c + 1 WHERE id = 1;    -- 当前读看到已提交的新行并更新
SELECT * FROM t WHERE id = 1;           -- 看得到，这是自己写出的新版本
```

如果 A 一开始就是 `SELECT ... FOR UPDATE`，记录不存在时会锁住间隙，B 的插入会被堵住。锁加在索引上，没有合适的索引时，锁的范围会扩得很大，幻读被堵住的同时并发也会掉下去。

MVCC 让读可以不阻塞写，它不防止两个事务按各自读到的值去覆盖同一行。这种丢失更新要用当前读、行锁或版本号。

### 8. 线上遇到一个慢 SQL，你的排查思路和优化步骤是怎样的（可以从执行计划、索引、表结构、业务逻辑层面展开）？

**参考答案**

结论：先分清是语句本身慢，还是在等锁、等 IO；再看执行计划和扫描行数，最后才改索引、改表或改调用方式。一次只改一处，用同一条语句的耗时和扫描行数对比。

1. 定位。从慢日志或 `events_statements_summary_by_digest` 拿到完整 SQL、发生频率、`Query_time` 和 `Lock_time`，以及扫描行数和返回行数。`Lock_time` 高，先查未提交事务和锁等待，而不是先加缓存。扫描行数远大于返回行数，说明大部分行白扫了。确认是某一个参数慢，还是整表都慢，以及是不是从某次发布开始。
2. 执行计划。`EXPLAIN` 看 `type`、实际用到的 `key`、估算行数和 `Extra`。`Using filesort`、`Using temporary` 说明还有排序或临时表。MySQL 8.0 可以用 `EXPLAIN ANALYZE` 看实际耗时花在哪一段。优化器没用某个索引，可能是统计信息过时，也可能是这个索引帮不上这个谓词。
3. 索引和 SQL。联合索引满足最左列；查询列都被索引盖住时可以不回表。列上套函数、和列的类型不一致的比较，会让索引用不上。区分度很差的列不单独建索引。深分页改成「主键大于上一页最后一条，再限制条数」。`SELECT *` 只留需要的列。
4. 表结构。SQL 已经贴着索引走、仍然慢，再看行是不是太宽、冷数据能不能归档、主键是不是随机写入导致页分裂。改结构成本高，放在改写 SQL 之后。大表收集统计信息或直方图放在低峰，先确认优化器是因为估计错才没选对索引。
5. 业务。每次打开页面都查几年明细、循环里逐条查，加索引也解决不了。能缓存的读、能进汇总表的统计、能异步的导出，从调用次数上拿掉。
6. 验证。对比扫描行数、耗时和写放大。新索引会拖慢写入，确认写路径还能接受。

### 9. Spring Cloud 或 Dubbo 这类微服务框架，在服务间调用时，如何设计一个健壮的熔断与降级策略？你用过哪些具体组件（如 Sentinel、Hystrix）？

**参考答案**

结论：熔断按依赖分开，只统计真正代表下游不健康的失败；降级结果必须对业务安全。非核心读可以返回缓存或空，下单和支付失败就告诉用户失败，不能降级成「当作成功」。

调用方给每个下游设置短于自己上游期限的超时。隔离用有界并发或独立线程池，避免一个慢依赖占满本服务的请求线程。滚动窗口里的错误率或慢调用比例超过阈值，并且样本数够，才打开熔断；打开后快速失败，经过一段恢复时间只放少量探测，成功再关上。样本不够就打开，流量一小就会误熔断。

业务校验失败、调用方参数错误，不能算进失败率。重试只给幂等的读，次数少，并且只在熔断关闭时做。超时再重试，会把一次慢调用放大成多次，把下游打得更慢。Dubbo 一类框架自带的失败转移重试，要和熔断、超时放在一起算。

降级函数不能再调用同一个依赖，否则熔断没有意义。核心写路径的降级是明确失败，必要时记一笔待补偿，而不是用旧数据冒充新结果。推荐、摘要、非关键查询可以回退到缓存或直接跳过。

组件按你线上用过的讲，没用过的不要说用过。Hystrix 以每个依赖一个线程池或信号量做隔离，用滚动窗口的错误比例决定开关，处于维护状态，新的 Spring Cloud 版本不再把它作为默认选择。Sentinel 按资源统计 QPS、并发、慢调用和异常比例，规则可以推到配置中心，改阈值不用发版；资源名要落到接口或方法，一个热点方法熔断不应带走同一服务的全部方法。Spring 现在更常见的是 Resilience4j，用装饰器组合熔断、限时、舱壁和重试。无论哪一个，都要有打开次数、降级次数和下游耗时，否则熔断已经打开了也没人知道。

### 10. 在容器化（如 Docker + K8s）部署环境下，Java 应用在监控、日志收集、配置管理方面，相比传统部署需要注意什么？有什么好的实践？

**参考答案**

结论：容器会被调度、替换，IP 和本地盘都不稳定。监控靠指标和追踪，日志走标准输出，配置和镜像分开，内存必须按容器限制来算。

监控不能靠登录机器跑 `jstat`。进程用 Micrometer 暴露堆、GC、线程、连接池和接口延迟，由 Prometheus 抓取。存活探针失败会重启容器，不要用它去探下游，否则依赖一抖，Pod 会被成片杀掉。就绪探针失败只是从 Service 摘掉流量。启动慢的 JVM 用启动探针，避免还在预热就被杀掉。追踪用 OpenTelemetry，trace 要穿过 HTTP 头和 Kafka 消息头。

内存方面，容器的 limit 是硬上限。堆使用认 cgroup 的比例来设，并给元空间、线程栈和直接内存留余量。早期不认 cgroup 的 JDK 8 会按宿主机内存估算堆，容易把容器打到 OOMKilled。OOM 时的堆转储写到卷上，容器消失后还在。CPU limit 会触发配额节流，现象是延迟尖刺，CPU 利用率看起来却不高。请求量决定调度，限制要单独看。

日志打到标准输出，一行一条 JSON，带上 traceId。节点上的采集器负责收集和滚动。只写容器本地文件，重建后日志就没了。密钥、证件号和完整提示词不进日志，提示词需要排查时按比例采样并脱敏。

配置不打进镜像。环境差异放 ConfigMap、Secret 或配置中心。密钥用权限收紧的挂载文件。`@RefreshScope` 盖不住全部 Bean，不能假设改完配置所有客户端立刻生效；不能热更新的项就滚动重启。发布时先从 Service 摘除，再让已接进来的请求在优雅停机时限内处理完，然后才收到终止信号。摘除端点到各节点生效需要时间，`preStop` 留出的等待要按集群测，不靠一个拍脑袋的秒数。

### 11. 设计一个短链接生成服务，你会如何考虑存储、缓存、发号器（唯一 ID 生成）和高并发访问？

**参考答案**

结论：短链是读多写少。生成可以慢一点，但必须全局唯一；跳转路径只做缓存读取和 302，点击统计异步化，不堵在跳转上。

发号不要把数据库自增主键直接当短码，否则容易被遍历。号段模式更适合高并发：数据库里一行记录某个业务已经分配到的最大 id，实例用事务把最大 id 加上一个步长，拿到一段连续号码后在内存里发放。步长大，实例重启丢掉的号就多；步长小，数据库会被频繁更新。雪花算法不依赖每次访问数据库，但依赖时钟，回拨时要等待或拒绝发号，同一毫秒序列用尽也要等到下一毫秒。64 位雪花 id 转 Base62 大约 11 个字符。若产品要求 6 到 8 位，用号段发出的整数做可逆打乱，再 Base62。随机短码则靠唯一索引冲突后重试。同一个长链接要不要永远对应同一个短码，是产品决定：要分活动统计就每次新发，要省空间才按长链哈希去重。

存储用短码做主键，行里放长链接、过期时间、状态和所属用户。跳转是按主键点查。长链如果要去重，再给长链的摘要一个唯一约束。过期和人工禁用都改状态，不物理依赖「缓存碰巧失效」。

读路径是本地缓存、Redis、再数据库。热点短码用单飞，避免失效瞬间打穿。缓存里对不存在的短码放短暂空值。跳转返回 302，目标变更和点击统计仍经过服务端。301 会被浏览器长期缓存，之后改目标、统计点击都会失效。写路径只在生成时落库。点击用消息或计数器异步累加，跳转成功不依赖这次写入。

生成接口按用户限流，并拒绝内网地址和脚本协议，避免短链被当成跳板。多实例只共享号段表和短码唯一约束，不在应用内存里各自从 1 开始数。

### 12. 你如何看待向量数据库在 AI 应用中的作用？它与传统关系型数据库（如 MySQL）和搜索数据库（如 Elasticsearch）的核心区别是什么？

**参考答案**

结论：向量库解决的是「按语义找相近的内容」。MySQL 负责事务和精确条件，Elasticsearch 的本行是词项检索。检索增强生成通常是向量召回加上关键词召回，再用业务库做权限和原文的准据。

向量索引把文本、图片经嵌入模型变成高维向量，查询时找距离最近的一批。数据量大时用近似最近邻，例如 HNSW、IVF，用召回率换延迟和内存。距离要和模型训练时的度量一致，余弦和内积不能混用。索引和查询必须用同一个嵌入模型，换模型就要整库重算。它不提供 MySQL 那种事务、关联和精确更新语义，文档的权威副本仍应在对象存储或关系数据库，向量库存的是可重建的索引。

MySQL 的主路径是 B+Tree：等值、范围、事务和约束。新版本可以存向量并计算距离，这不等于它能替代面向大规模近似检索的索引。权限、订单状态、文档是否下线，用关系库判断，不要只靠向量相似度。

Elasticsearch 的核心是倒排索引和 BM25，适合错误码、专有名词、SKU 这类必须词面命中的查询，也适合过滤和聚合。它现在也能做稠密向量的 kNN。和专用向量库的差别在于重心：一边是词项加过滤，一边是向量的存储布局、量化和大规模近邻检索。语义检索会把「退款失败」和「退款没成功」拉近，也会把精确代号抹平，所以两类召回常常一起用，再交重排模型。

过滤条件要在检索时生效。先取全局最相近的 K 条再按租户扔掉，结果可能为空，权限也会漏。向量检索是近似的，评测看召回率和引用是否支撑答案，不看某一次演示。

### 3. 在实现 AI 智能体（例如基于 LangChain、Dify 或自研框架）时，你是如何管理「对话历史」（Context）的？如何平衡上下文长度、效果与成本？

**参考答案**

结论：不要把历史原文每轮都塞进提示词。用「最近几轮原文 + 更早对话的摘要 + 必须遵守的结构化槽位」，并给这三块单独的 token 预算。

原文全量重放会线性增加输入费用，还会把系统提示、工具定义和检索片段挤出窗口。最近几轮保持原文，是因为指代和刚确认的事实经不起摘要。更早的内容压成一段滚动摘要，摘要本身也要占预算，并且会丢掉否定和数字。用户说过的「不要退款」「必须人工」以及订单号、已选商品，写成单独字段，拼装提示词时固定带上，不依赖摘要还记不记得。

预算按这个顺序扣：系统提示和工具定义、本轮必须的检索结果、结构化槽位、最近原文，最后才是更早的摘要。超了就先截断工具返回的长文本，再丢掉最早的原文。多模态不要每轮重传图片字节，保存文件 id，这一轮确实要用再取。

效果和成本的平衡点是「这一轮决策用得上的信息还在」。闲聊可以多裁；正在办理中的任务，槽位不能裁。历史很长时，按当前问题检索相关的旧轮次，比无脑保留最后 N 轮更不容易丢掉早先的约束。系统提示和工具定义保持稳定并放在前缀，服务商的前缀缓存才能命中；每轮改写系统提示，缓存会失效，输入费用降不下来。

框架只负责存放消息的话，裁剪策略仍要写在你的组装层。消息落库，进程重启后按会话重放，内存里的列表不是历史的来源。

### 4. 当智能体的响应速度成为瓶颈时，可以从哪些层面进行优化（提示：模型选择、Prompt 优化、缓存、异步、流式响应等）？

**参考答案**

结论：先看慢在首 token，还是慢在整次做完。流式输出改善的是用户看到第一个字的时间，总 token 和费用还在。

模型按任务拆开。分类、抽槽位用小模型或规则，只有生成和复杂规划才用大模型。路由错了的代价是答非所问，所以路由本身要有评测，不能只看平均延迟。

提示词变短：少放互相重复的说明和例子，把稳定前缀留住以便缓存。每轮重写一大段系统提示，延迟和费用会一起上升。

缓存分两种。完全相同、答案不随人和时间变化的问句，用精确缓存。语义相近就复用答案时，阈值要用历史问句标定，过高几乎不命中，过低会答错。价格、库存、订单状态、个性化结果不进这种缓存。

和回复无关的工作移出关键路径：记忆写入、标题、埋点在回复发出后做。检索的嵌入在入库时算好。用户断开就取消上游生成，避免人走了还在出 token。

检索限制候选数量，重排只排前面一小批，多路召回并行，并设超时。智能体侧减少来回：能同时调用的只读工具并行，步数和总时长设上限。连接池复用到底，不要每个请求新建客户端。

排队要有等待上限。只把请求放进队列，平均耗时看起来变「可接受」，排在后面的请求会一直堆着。优化前后分别看首 token、总耗时和单次费用，避免只把时间从模型转移到无人看见的队列里。

### 5. 如果让你设计一个支持多模态（文本、图片、文件）的 AI 智能体接入网关，你会考虑哪些核心模块？如何设计 API 和鉴权？

**参考答案**

结论：网关统一做身份、配额、文件和模型路由。业务服务不持有供应商密钥，模型服务不相信客户端传来的用户 id。大文件先上传拿 fileId，对话请求只引用 fileId。

模块有六块。认证和租户配额，按应用、用户和模型限流，并限制单次 token。文件接入：白名单类型、大小、病毒扫描，原件进对象存储。内容规范化：文档抽文本，图片只保留模型接受的引用，输出统一的内部消息。会话组装和路由：没有图片就不走视觉模型。流式生成，客户端断开则取消上游。审计记录租户、文件摘要、模型、token 和 traceId，不把所有原件永久留在日志里。

API 保持普通 HTTP。`POST /v1/files` 用 multipart 上传，返回 fileId。`POST /v1/conversations/{id}/messages` 的正文是消息数组，每段内容是文本或 fileId，并声明是否流式。流式响应用 SSE。提交消息带 Idempotency-Key，同一次重试返回同一次生成，不另开一轮费用。长文档的解析和嵌入走异步任务，对话接口只接受已经处理完的 fileId。

鉴权在网关完成：外部用 OAuth2 或 JWT，验签后把租户和用户注入内部调用。文件 id 绑定租户，送给模型前再查一次归属，避免知道 fileId 就能读到别人的文件。对象存储使用短时签名，桶不公开。供应商密钥只放在网关的密钥存储里。管理接口和用户接口的凭证分开。内部服务之间可以用 mTLS。

预处理没通过的文件不能进入模型。网关对每个供应商单独超时和熔断，某个视觉模型不可用时，文本对话仍可走备用模型，并在响应里标明降级。

### 6. RAG（检索增强生成）是解决大模型幻觉和知识更新的重要手段。请描述一个你实现或了解的 RAG 系统流程。其中，文档分块（Chunking）和向量化检索的策略有哪些考量和优化点？

**参考答案**

结论：RAG 是「先检索到可引用的片段，再让模型基于片段回答」。它能减少胡编并跟上文档更新，但不能单靠提示词保证不幻觉，权限和评测要做在检索里。

入库：解析文档，去掉页眉页脚等噪声，按结构分块，用固定的嵌入模型向量化，向量和元数据进检索库，原文放对象存储或数据库。元数据至少有文档 id、章节、更新时间和租户，方便删除、重建和过滤。查询：用当前问题改写指代，嵌入查询，按租户和权限过滤后取近邻，需要时和关键词检索合并，再用重排模型留下几段，连同出处交给模型。回答里带引用。文档更新走同一条入库链路，按文档 id 删掉旧块再写入，避免新旧版本同时被召回。

分块没有万能长度。太长，一块里塞进多个主题，嵌入被稀释，也占提示词；太短，步骤和条件被切开。按标题、段落、表格来切，表格带上表头，代码按函数切，不要在句子中间硬截。块之间少量重叠，用来保住跨在边界上的句子。更稳的是小块用于召回、返回时带上父级段落，既找得准，又给模型足够上下文。语义上哪里跳变就在哪里切，入库成本更高，适合长文档，不适合作为第一版。具体长度用召回评测比较，不超过嵌入模型的输入上限。

检索侧，索引和查询必须是同一个模型和同一种距离。换模型就全量重嵌入。错误码、药名、SKU 同时走关键词检索，语义向量单独容易把精确符号抹掉。重排只处理召回的前几十条。先按租户过滤再取近邻，避免取完全局 Top K 才发现全是别的租户。多轮对话先把「这个」还原成具体对象，再去检索。

上线前看召回率和「引用是否真支持答案」。检索为空就明确说没有依据，不要让模型用参数知识把空检索填上。

### 7. 在微服务架构中，如何保证调用第三方 AI 服务（如 OpenAI、文心一言、通义千问）的稳定性、可观测性和成本控制？

**参考答案**

结论：把供应商调用收口到一个网关，按供应商做超时、熔断和配额。稳定性靠失败隔离和可取消，可观测靠分段延迟和 token，成本靠预算和路由，而不是月底对账才发现。

稳定性：连接超时、首 token 超时和总超时分开。只对幂等请求在 429 和 5xx 上重试，遵守 `Retry-After`，加上抖动，次数少。流式生成重试前先确认客户端没有收到半截内容，否则用户会看到两段拼在一起。每个供应商独立熔断和连接池，一个供应商慢，不占满整个网关。备用模型可以接文本流量，响应里标明降级，因为备用模型的答案质量不一样。异步场景进队列，队列有长度和等待上限。

可观测：trace 从业务请求连到供应商的 request id。分开记录排队、首 token 和总时间，以及输入输出 token、结束原因、是否走了缓存或备用模型。提示词默认不落全量日志，采样并脱敏。告警看 429、5xx、熔断打开和费用突增，不只看进程还在不在。

成本：每个租户有月度配额和单次 token 上限，调用前按上下文估算，超限直接拒绝。能用小模型的意图不要默认打到最大的模型。相同问答走精确缓存，稳定前缀利用服务商的前缀缓存。客户端断开就取消上游。输出 token 通常更贵，限制最大生成长度。费用按应用 id 记账，才能把某一条业务的提示词膨胀找出来。

密钥放在网关，业务服务只有内部权限。供应商的单价和区域会变，模型名做成配置，避免换一个模型就要改每个调用方。

### 8. 你如何理解「Agent」（智能体）与传统的「API 调用」在架构设计思想上的根本不同？这对后端服务的设计提出了哪些新挑战？

**参考答案**

结论：传统 API 的控制流写在调用方代码里，契约是固定的输入输出。智能体把「下一步调用哪个工具」交给模型，服务端提供的是一组受约束的工具，加上这个循环的预算和状态，而不是一条写死的流程。

同一次用户请求里，模型可能不调用工具、调用一次，或根据观察结果再调用。同样的话可能走出不同的工具序列。因此后端不能假设「这个接口背后就是一次查询」。路径事先能画完的，仍应做成普通工作流，不必套一层智能体。

新的约束有这些。循环必须有步数、墙钟时间和费用上限，否则一次请求会一直调用工具。工具参数是模型生成的 JSON，要按 schema 校验，非法就把错误交回模型，不能直接执行。会改数据的工具，权限和幂等写在服务端：模型说自己有权不算数。支付、发消息这类操作要能识别同一次尝试，做了一半失败时，重试从最后一次成功的工具继续，不能把已成功的支付再做一遍。会话、工具结果和「等待人工确认」的状态要落库，进程重启后能恢复。

一条请求包含多步，追踪要记下每一步的工具名、参数摘要、结果和 token。只给整次请求一个耗时，无法排障。测试也不能只比对最终一句话，要检查轨迹：该查的数据源查了，不该出现的写操作没有出现。

工具应能承受重复调用和顺序变化。把「先扣款再查库存」的正确性寄托在模型会按这个顺序调用，这个设计站不住。顺序和事务仍由后端的业务接口保证，模型只决定要不要进入这个接口。

### 9. 场景题：设计一个「智能客服工单自动分类与路由系统」，需求是能根据用户描述的文本，自动判断问题类型、紧急程度并分配给相应处理组。你会如何设计技术方案（涉及 NLP 模型、分类算法、规则引擎、工作流等）？

**参考答案**

结论：分类和路由拆开。类型可以交给模型，路由必须是配置好的确定性规则。模型不直接退款、不直接改订单。

请求进来先做规范化：去掉无效字符，抽出订单号和错误码，标上用户等级和渠道。这些用规则就能稳定抽取。支付失败码、安全投诉、监管关键词走规则直接定类型和紧急度，结果可审计，不交给模型自由发挥。

剩下的文本再分类。标签稳定、标注够，用训练过的文本分类模型，延迟和费用都可控。标签经常变、说法很散，用大模型按 schema 输出类型、紧急度、置信度和依据原文，校验失败就进人工。紧急度不要只靠分类模型的一个分数。资金、VIP、已经超时的工单，用业务规则抬高优先级，可以覆盖模型。

置信度高则自动分派；低则进入人工队列，并附上建议标签。类型加紧急度映射到处理组，映射、班次和队列长度放在工作流配置里。同一用户还有未关闭工单时，尽量回到原组。人工改掉的标签写回样本，用来补规则和重新训练。

全走大模型，上线快，但费用、抖动和审计都差。主干用规则加分类模型，长尾交给大模型，是更稳的组合。评价时紧急类的召回优先于总体准确率：把支付故障分到普通咨询，比多转一次人工严重。上线初期可以只建议、不自动分派，人工采纳率上来再放开自动路由。

### 10. 如何评估一个 AI 功能或智能体上线的效果？除了准确率、成功率，你会关注哪些业务和技术指标？

**参考答案**

结论：上线看三件事：任务有没有办成、付出的延迟和费用是多少、有没有越权。离线准确率只说明固定样本上的拟合，不能代替这三件。

质量按意图拆开。办理类看是否在允许的步骤内做完；问答类看引用是否支撑回答；工具类看有没有选对工具、参数对不对。类别不均衡时看每一类的召回。一个总准确率会把样本量小的紧急类淹没。

业务指标看解决率、转人工率、重复进线、满意度和处理时长。转人工下降但短时间重复进线上升，说明没有真解决，只是把人拦住了。客服场景里这组指标要一起看。

技术和成本看首 token、完整耗时的尾延迟、错误率和超时、平均步数、每成功一次的 token 和金额、缓存命中、降级比例。只优化平均耗时，尾部和费用可能同时变差。

安全看不该调用的工具有没有被调用、隐私有没有进日志、提示注入能不能把内部指令套出来。这些要有单独样本，不能指望准确率反映它们。

方法上，固定评测集用来挡回归，线上用对照流量看真实变化。评测集持续加入新的失败案例，否则分数会和用户体验脱节。用模型给回答打分，只能观察趋势，要抽一部分人工复核。报告任何比例时都说清分母是全部会话，还是只包括自动处理的那部分。

### 1. 自我介绍

**答题思路**

这一面技术追问少，介绍侧重你怎么做决定、怎么和人一起交付。一分钟。

1. 一句身份和现在负责的范围：哪些是你独立做的，哪些是你推动别人一起做的。
2. 一个结果，用你能解释的口径：延迟、故障、人工成本或交付周期。不展开架构。
3. 一个你会复盘的点，例如某个取舍如果重来会改。自然接到下一问。
4. 不要在这里谈薪资、职级或离职原因。对方没问，就停在工作方式上。

### 2. 在你刚才提到的项目中，如果现在有资源让你重做一遍，你会在架构、技术选型或团队协作上做出哪些不同的改进？

**答题思路**

就着上一问那个项目说，不要换一个没讲过的系统。准备三处改动，每处都是「当时的痛 → 现在会怎么做 → 代价」。痛必须是你遇到过的。

1. 架构一处。例如当时把模型调用嵌在业务线程里，重做会收口到独立网关，换取统一的超时、取消和费用记账，代价是多一次内部调用。
2. 选型一处。例如当时直接上大模型做全部分类，重做会把稳定标签交给小模型或规则。说清你用什么现象判断原来的选择不合适。
3. 协作一处。例如提示词和接口各改各的，重做会让工具 schema、评测样本和发布说明放在一起评审。
4. 收一句当时不这么做的原因：工期、没有样本，或依赖方还没准备好。这样是复盘，不是全盘否定。
5. 没做过的「平台化」「多 Agent」不要借来当改进项。说不上代价的改进，面试官会继续追。

### 3. 在 AI 技术日新月异的背景下，作为一名后端开发者，你是如何保持技术敏感度和学习节奏的？主要通过哪些渠道？

**答题思路**

讲一个你真的在执行的节奏，渠道只留你打开过、也能现场复述的。

1. 节奏绑在当前系统的问题上：例如这段时间补检索评测，或把工具调用的超时和取消做完。固定一段不受发布会影响的时间，而不是每个新模型都追。
2. 渠道按信号强度排：你依赖的框架和供应商的发行说明、相关源码、线上失败样本、自己写的小实验。短视频和资讯只用来发现题目，结论回到文档和实验。
3. 敏感度用三条筛选：费用变了没有，延迟变了没有，失败时的行为变了没有。和这三件无关的新名词先放着。
4. 准备一个五分钟能讲完的例子：你看了哪份文档，改了哪段代码或哪组样本，得出什么取舍。讲不出例子，方法就是空的。
5. 不要罗列一串社区名字来证明自己关注行业。对方会抽一个问你上次学到的具体限制。

### 4. 请分享一个你近期学习并实践过的、非 Java 的、与 AI 或效率相关的新技术、工具或框架，并谈谈它给你带来的启发或价值

**答题思路**

只讲你真的跑通过、最好能打开笔记或仓库的东西，而且不是 Java。教程看完但没跑，就说做到哪一步，不要讲成上线项目。

1. 它解决的具体问题：例如评测脚本、一次向量检索、一个工作流编排，选你实际碰过的那一个。
2. 你怎么把它跑起来，卡在哪：数据格式、状态没有持久化、还是本地能跑但一重启就丢。
3. 带回 Java 服务的一条启发，落在工程上：工具要幂等、状态要落库、评测要先于改提示词、或者某种编排不该拿来包住支付。
4. 明确边界：身份、事务和审计仍放在现有 Java 服务里。这个工具替换的是哪一段，没有替换哪一段。
5. 不要以「它比较先进」收尾。对方要听的是你把它用在一个问题上之后，改了自己哪一个设计。

### 5. 你认为未来 1-2 年，AI（特别是 Agent）技术的发展，会对传统的企业级 Java 后端开发带来哪些具体的冲击和机遇？我们的工作重心可能会发生什么转移？

**参考答案**

结论：样板接口和重复的胶水代码会被生成式工具分担，溢价下降。企业里真正难的仍是正确性、权限和故障时的行为。Java 后端的机会是成为模型的工具层和事务边界，而不是把提交订单交给模型自己决定。

冲击很具体。CRUD、转换代码、测试骨架的编写时间会变短，只靠「写得快」区分候选人会变难。同时模型的输出不稳定，不能作为库存扣减、支付和权限判断的最终执行者。若把这些写进提示词，出了事故无法复现，也无法审计。

机遇同样具体。原有领域服务会更值钱，因为智能体需要一批幂等、权限清楚、错误码稳定的 API 当工具。缺少这些 API 的系统，模型只能聊天。新的后端工作是：工具契约、调用配额、轨迹日志、评测集，以及「做到一半失败」的补偿。零售、物流、客服里，大量系统已经有订单和工单，缺的是把模型安全地接进去。

工作重心会从实现每一个分支，转到划定哪些步骤允许模型选择、哪些必须由代码走完。评审生成的代码、看失败样本和单次费用，会占比现在更多的时间。值班时除了数据库和消息队列，还要看供应商故障、配额和突然变长的提示词。

分布式事务、索引、并发这些基本功不会因此过时。工具最终都要落到这些系统上。转移的是时间分配：少写重复控制器，多保证一次智能体调用在失败、重试和越权时仍然可收场。

### 6. 在技术方案评审中，如果与同事或 Leader 在核心实现路径上产生分歧，你会如何处理？请结合一个具体实例说明

**答题思路**

用你自己的一次评审。没有「你说服了所有人」的结局也可以，关键是怎么把分歧变成可判定的事实。不要现编一个没发生过的事故。

1. 先把对方的方案复述到对方认可，包括它想保住的点：工期、延迟、简单或可回滚。
2. 写下共同的标准：正确性、尾延迟、费用、交付时间、失败后能不能收回。标准没对齐，后面都是在争偏好。
3. 用一小份对照说话。例如同步等待模型，对照先落任务再回调，各看十条失败样本或一次限时压测。拿数据，不拿资历。
4. 限时。到期仍有分歧，把两个方案、证据和你的建议一起交给负责拍板的人。
5. 决定之后按决定做。没被采纳的风险记下来，用线上数据再看，不在评审之外反复翻同一件事。
6. 实例按这个顺序讲完即可。避免两句空话：「我会坚持正确的一方」，以及「领导说了算我就听」。

### 7. 假设你现在是某个 AI 项目模块的技术负责人，你会如何制定开发规范、代码审查策略，并保证项目的交付质量和进度？

**参考答案**

结论：规范写成评审时能检查的约定，质量用固定样本和副作用审查守住，进度按一条用户意图端到端交付。时间不够就减场景和减工具，不减鉴权、审计和超时。

规范只留会出事故的几条：工具的入参出参 schema、错误码、超时、幂等键；日志里固定有 traceId、会话 id、工具名和 token；供应商密钥不进仓库；会改数据的操作必须能靠幂等键重放。提示词和工具契约一起版本化，禁止线上直接改提示词而不留记录。

审查看小的变更。有副作用的工具要看到权限校验和幂等，SQL 和用户输入进提示词的位置要看一遍。模型生成的代码和手写代码同一标准。两个人都看过才能合并涉及支付或删除的改动。

质量门禁是自动化测试加上一组固定对话：该调用的工具调用了，不该写的没写，成功率掉了就拦住合并。线上新的失败案例补进这组样本。没有这组样本时，不靠感觉宣布提示词「优化过了」。

进度按垂直切片排：一个意图从接入、工具到失败补偿先走通，再复制到下一个意图。每周看失败样本、尾延迟和费用，阻塞写在明处，例如标注不够或供应商配额不够。范围要削时，先削长尾场景。用故事点堆一层「平台」而没有一条跑通的用户路径，不算有进度。

### 8. 你对自己的职业规划是什么？希望在未来三年内，在技术或业务上成长为什么样的角色？

**答题思路**

用能力描述三年后能负什么责，不报职级，不报薪资，不说空泛的「成为架构师」。

1. 第一年：独立交付一条业务链。模型调用、工具、失败补偿和单次费用，你都能对上日志讲清楚。
2. 第二年：把这条链收成别人可以接入的服务，补上评测、配额和追踪。订单、库存、支付仍走原来的事务接口。
3. 第三年：负责一个业务模块的交付质量和线上效果，能在评审里讲清取舍，并带一两个人把规范执行下去。
4. 说明基本功还在：JVM、MySQL、缓存和消息仍是工具落地的地方，不会改成只写提示词。
5. 和你面试的业务对齐一句，用你真有经历能接上的场景，例如交易、物流或客服。没有做过的业务不要硬贴。
6. 如果对方追问「管人还是做深」，按上面的第三条答：先能对一条线上链路负责，再扩大到一个模块。
