# 京东 Agent 开发一面面经

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 一面

### 1. 实习经历提问

**答题思路**

按「任务 → 你写的那段 → 一个取舍 → 结果」讲，讲完就停。

1. 两三句说明实习要完成的事和你的角色。公司、职级、薪资不要主动展开。只讲你亲手做过的部分，没核对过的数字不说。
2. 时间放在一条链路上：请求从哪进来，模型决定什么，哪些步骤是代码固定的，哪个写操作必须停下来等规则或人。
3. 准备一个取舍。例如查询可以让模型选工具，出账、改库却收回到确定性服务。备选方案和放弃原因各一句。
4. 结果讲你观察到的变化：误调用、人工复核或某段耗时。被追问时能说清状态存在哪，失败后从哪一步恢复。
5. 锁、Redis、SQL 后面会单问。这里只点出用过的组件，不在这段把原理讲完。

### 2. 如果是一个金融系统，不能让 agent 自己去真实操作（钱放出去就是大问题），你会选择怎么做？

**参考答案**

模型只提交提案，资金变动由确定性服务在校验和确认之后执行。Agent 不保存支付凭证，能调的工具里也没有真实转账。

余额、限额、收款账户是否在白名单，做成只读工具。模型按固定字段交出付款方、收款方、金额、币种、用途和幂等号。类型、范围和账户格式由代码校验，失败就拒绝，不把原话拼进资金接口。

记账服务只认落库的单据：核权限、限额和幂等键，通过后停在待确认。是否放行由规则看这些字段，不看模型的自由文本；超额、新收款人或字段不完整必须人工确认。确认和扣款分成两步，扣款只认确认后的单据。

超时当成结果未知，先按幂等号查询，没有成功记录才重试。进程重启从单据状态恢复，不让模型重新决定这笔钱。提案、参数、确认人和入账结果都留痕。出款路径用工作流写死，模型只填单和解释。

### 3. Java 常用数据结构包含哪些

**参考答案**

按接口来选：要不要顺序、操作复杂度、是否线程安全。

List 里，按下标读和在尾部追加用 ArrayList，随机读是 O(1)，中间插入要搬移元素。LinkedList 头尾增删是 O(1)，按下标访问是 O(n)。去重用 Set：HashSet 无序、平均 O(1)，LinkedHashSet 保留插入顺序，TreeSet 按键排序、O(log n)。Map 对应 HashMap、LinkedHashMap、TreeMap。HashSet 底层就是 HashMap。

栈和队列优先用 ArrayDeque，要优先级用 PriorityQueue。上面这些集合都不是线程安全的。并发下换 ConcurrentHashMap、ConcurrentLinkedQueue 或阻塞队列。Vector、Hashtable、Stack 是遗留类，新代码不用。

HashMap 允许一个 null 键；TreeMap 用自然序时不允许 null 键；ConcurrentHashMap 的键和值都不能是 null。

### 4. 如果是一个并发量比较高的系统，你在写代码的时候会考虑哪些问题？

**参考答案**

先少放共享的可变状态，再给锁、线程池和外部调用加上限。先改 JVM 参数解决不了写错的临界区。

多个请求之间不要共用可变对象。必须共享时用并发容器，或把写收进同一个线程。锁只包住内存里的修改，里面不访问数据库和远程接口。线程池有界，慢的下游单独隔开，队列满了要拒绝或降级，避免把入口线程一起堵住。

写接口先有幂等键。超时先查询再决定重试，只重试明确的网络失败和限流，并做退避。热点行、没有索引的更新、拖得很长的事务，会比 CPU 更早顶住。缓存要写明过期后谁回源；缓存不可用时限流或降级，而不是无上限地打到数据库。

每个外部调用都有超时，并且短于整次请求的截止时间。连接池按下游容量来定。同一次请求的追踪号要穿过异步线程传下去。

### 5. 锁这块你用过吗？ReentrantLock 的底层实现了解过吗？

**参考答案**

ReentrantLock 建在 AQS 上。state 为 0 表示空闲，大于 0 是重入层数，持有线程记在 exclusiveOwnerThread。加锁用 CAS 把 state 从 0 改成 1；同一线程再进入就把 state 加上去，所以可重入。

CAS 失败的线程进入 AQS 的双向等待队列（CLH 的变体），用 LockSupport.park 挂起。解锁由持有线程把 state 减一，这一步不再 CAS；减到 0 才清掉持有者并唤醒后继。默认是非公平锁，新线程会先抢一次 CAS。公平锁在抢之前先看队列里有没有排在前面的节点。建成公平锁之后，无参的 tryLock() 仍然不排队。

相对 synchronized，它能中断、限时、选择公平，一把锁也可以挂多个 Condition。await 会一次放掉全部重入层数；signal 把节点移回 AQS 队列并唤醒，线程重新抢到锁之后，state 才恢复成原来的层数。加锁和解锁次数要成对，解锁放在 finally 里。

用过就用一句说临界区在保护什么；没在业务里用过，就直接讲实现，不要编一个场景。

### 6. 在并发场景下用 HashMap 会有什么问题？

**参考答案**

HashMap 不能用在多线程写的场景里。两个线程同时 put，可能覆盖同一个桶上的节点，更新丢失；size 和链表、红黑树也会写到一半，读到 null 或对不上的结构。

JDK 7 扩容时头插，并发迁移可能把链表收成环，遍历死循环。JDK 8 改为尾插，链表过长再树化，那种成环不再是典型故障；并发 put 仍会丢更新，扩容时仍可能把桶写乱。fail-fast 只看 modCount，用来发现本线程遍历时又改了结构，管不住别的线程同时去写。

共享映射用 ConcurrentHashMap。JDK 8 没有分段锁：空桶用 CAS，已经有节点的桶锁桶头，get 不加锁。它不允许 null 键和值。先 containsKey 再 put 不是原子的，要用 putIfAbsent、compute，或放到同一把锁里。Collections.synchronizedMap 锁整张表，只适合写很少的时候。

### 7. 分布式这块有什么了解吗？比如一些常用框架？

**参考答案**

按调用、协调、数据和失败之后怎么处理来讲，每个框架只说它解决的那一个问题。

服务之间同步调用常用 Dubbo、gRPC 或 OpenFeign，入口用网关做认证和限流。注册和配置常见 Nacos，旧系统里也有 ZooKeeper。异步解耦用 Kafka 或 RocketMQ，消费端单独做幂等。缓存、限流和一些互斥用 Redis。跨服务写数据，优先用本地消息表或事务性发件箱，把业务提交和消息发出绑在一起。Seata 能做全局事务，但会带来锁和协调开销；资金类更常见的是单据状态加对账。

超时、熔断、限流可以用 Sentinel 或 Resilience4j，慢依赖要隔开。定时任务放进调度平台，避免每台机器同时扫同一张表。一次请求用追踪把网关、服务和消息串起来。

这些组件负责发现、传输和重试。重复扣款、超卖要靠幂等键和数据库约束，不靠框架默认行为。

### 8. Redis 你用在什么场景下了？

**答题思路**

问的是你用过的地方，不是把数据结构背全。只讲实习里真实的一到两个。

1. 先说当时的问题：读被放大、重复提交、限流，还是多台机器抢同一段工作。没做过的不要凑。用过分布式锁就点出业务互斥点，实现留到下一题。
2. 缓存要能讲完：键由什么组成、过期怎么定、改完数据是先更新库还是先失效缓存、缓存没有时谁去加载。更新顺序说不清，就不要把缓存当主例子。
3. 结构一句即可：计数是带过期的键，去重是集合，排名是有序集合。说明为什么不是一个把所有用户塞进去的大 Hash。
4. Redis 慢或挂了时，请求是限流后回源、直接失败，还是读旧数据。没有压测就不要报 QPS 和命中率。

### 9. 分布式锁用过吗？用 SETNX 实现分布式锁的底层是怎么做的？会有什么问题吗？

**参考答案**

可以用 Redis 做互斥，但单独一条 SETNX 还不构成锁。加锁、过期和释放要原子，并且只允许持有者释放。

正确的加锁是一条命令：`SET key token NX PX ttl`。NX 表示不存在才写入，过期时间和写入一起生效。token 要能区分持有者，不能写成固定的 `1`。释放在服务端用 Lua：值等于自己的 token 才删除。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

只发 SETNX 会有这些问题。没有过期时间时，客户端宕了锁就不放开。补一条 EXPIRE 又和 SETNX 不是原子的，进程可以死在两条命令中间。不比较 token 就 DEL，会删掉别人刚拿到的锁。业务超过租约还没做完，锁会先过期，互斥已经没了。这种写法也不能重入，同一线程再申请一次会把自己堵住。

主从异步复制还有缺口：锁写到主节点、还没复制到从节点时主节点宕机，新主上没有这把锁。Redis 也不提供让数据库核对的递增租约号，过期后的旧持有者仍可能去写。库存和资金用唯一键或版本号兜底，Redis 只减少冲突。用过就说互斥的是哪段工作；没上过生产就讲这个实现，不要把客户端库说成自己做的。

### 10. 如果有一个 MySQL 需要调优，你会基于哪些角度去考虑？执行计划（EXPLAIN）里你会看哪些列？

**参考答案**

先分清慢在语句、锁还是实例。大表上的全表扫描和长事务，改缓冲池解决不了。

顺序是：慢查询里的 SQL 和索引，事务是否太长、有没有锁等待，然后才是缓冲池、连接数和日志。读写分离、归档、分库，是访问路径已经合理、单机容量不够以后的事。

EXPLAIN 优先看 type、key、key_len、rows、filtered 和 Extra。type 从好到差，重点区分 const、eq_ref、ref、range、index、ALL。ALL 是扫整张表，index 是把一棵索引从头扫到尾。key 是实际选中的索引；possible_keys 有值但 key 为空，就是没采用。key_len 看联合索引用了最左几列。rows 是估计要检查的行，不是结果行数；filtered 是这些行里再被条件留下的比例。Extra 里 Using index 表示覆盖、不用回表；Using index condition 是把条件下推到引擎，和覆盖不是一回事。Using filesort、Using temporary 表示还要排序或临时表。

MySQL 8 可以用 EXPLAIN ANALYZE 看实际耗时。准备一条你能把 type、key_len、Extra 对上索引定义的语句。

### 11. 如果有一张 5000 万的表，让你做分页查询，你会怎么查？

**参考答案**

`LIMIT 25000000, 10` 会按排序顺序走过前面两千五百万行再丢掉，页越深越慢。分页要有唯一排序键，两次查询才能对上同一页。

连续翻页用游标。id 是主键时写成 `id > #{lastId} ORDER BY id LIMIT 10`，每次只做一小段范围查找。这种写法不能跳到任意页。

必须跳页、又要带出很多列时，内层只扫窄索引取出 10 个主键，外层再读完整行。按创建时间排序就要有 (created_at, id)，内层被这棵索引覆盖，扫过偏移时不必去读 50 个字段：

```sql
SELECT t.*
FROM t
JOIN (
  SELECT id
  FROM t
  ORDER BY created_at, id
  LIMIT 25000000, 10
) x ON x.id = t.id;
```

排序键就是聚簇主键时，叶子页上已经是整行，先取 id 再 join，省不掉扫描这两千五百万行叶子的 IO。子查询中的 LIMIT 会让派生表先物化，避免被合并成原来的大偏移语句。历史数据按时间或主键归档后，在线查询才碰不到这么深的页。

### 12. 回表听说过吗？

**参考答案**

InnoDB 的聚簇索引叶子存整行，二级索引叶子存索引列和主键。用二级索引找到记录后，SELECT 的列如果不全在这棵索引里，就要拿主键再查一次聚簇索引，这次查找叫回表。

要的列都在二级索引里就不回表，EXPLAIN 的 Extra 会出现 Using index，这是覆盖索引。主键本来就附在二级索引叶子上，只查主键和索引列也能覆盖。

回表是按主键的随机查找。命中很少时合适；命中很多时，优化器可能改扫聚簇索引。索引条件下推用索引里已有的列先过滤，减少回表次数，过滤后剩下的行还是要回表。一次回表很多行时可以走 MRR，先把主键排好再查，让 IO 更接近顺序读。

### 13. 用非聚簇索引查，5000 万那张表有 A、B、C 三列的组合索引，条件只有 A、B，要查 ID 大约在 2500 万位置的 10 条数据，这个 SQL 会怎么执行？逻辑是什么？如果这张表有 50 个字段，要把 50 列全查出来，你会从哪些角度去优化？

**参考答案**

主键若是 id，二级索引 (a, b, c) 的叶子顺序是 (a, b, c, id)：InnoDB 会把主键接在索引列后面。c 夹在中间，a、b 相等时后面先按 c 排，不能按 id 取一段。

「2500 万位置」先看成跳过约两千五百万条再取 10 条：

```sql
SELECT *
FROM t
WHERE a = ? AND b = ?
ORDER BY id
LIMIT 25000000, 10;
```

a、b 等值用得上最左前缀，c 继续缩不了范围，这棵索引也给不了 id 序。优化器或者在二级索引里找出匹配主键再排序，50 列另回表去取；或者沿主键从前往后扫，边扫边过滤 a、b，这样不用排序，但至少要检查两千五百万行。(a, b) 匹配不到这么多行时，大偏移是空的。另一种问法是主键落在两千五百万附近：`a`、`b` 等值且 `id >= 25000000 ORDER BY id LIMIT 10`。没有大偏移，但 (a, b, c, id) 仍然不能直接定位到那个 id。

50 列不要塞进索引。这条语句用 (a, b) 即可，主键会自己接在后面，叶子按 id 有序。翻页写成 a、b 等值加 `id > 上一页的 id`，范围大约只碰 10 个索引项，再回表取 50 列。必须保留大偏移时，子查询只查 id，靠 (a, b) 覆盖着走过前面的项，外层只回表 10 次。c 要留给别的查询，就单独做索引，不要放在 id 前面。

### 14. AI 自带幻觉，它在工程层面能不能落地？

**参考答案**

能落地。事实和有副作用的动作都不依赖模型自己记得对不对。幻觉还会生成出来，但不能出账，也不能冒充查询结果。

事实问题只采用检索或查询工具返回的内容，回答要能对上记录。没查到或对不上，就说明没有依据，不让模型补一段。抽取把温度压低，输出收成固定结构；解析失败就是失败，不把半截文本当成功。

会改数据的操作分成提案和执行。模型填写提案，金额、账户和状态迁移由代码校验。这道校验不看模型再生成的「我检查过了」。对不上白名单、超过限额或没有工具返回作证据，就拒绝执行。金融场景里不把转账工具交给模型，是同一条边界。

上线前用固定题目看事实错误，以及不该调工具却调了的比例；改了提示词或检索，用同一批题再跑。线上留下检索片段和工具参数，反复出错的说法收成规则。高风险步骤保持写死的流程，模型只做填写和说明。
