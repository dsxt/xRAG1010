## 一面

### 1. 请先做一个简单的自我介绍

**答题思路**

按「我是谁、我做成过什么、我为什么适合这个岗位」来讲，控制在 1 到 2 分钟。

1. 年限和方向：例如 Java 后端，做过交易或订单相关系统。
2. 只讲一个最熟的项目：业务是什么、你负责哪块、规模（QPS、数据量）和结果。
3. 补一句技术栈：Spring Boot、MySQL、Redis、消息队列，点到和岗位匹配的部分。
4. 收尾对准岗位：外包岗位更看重能不能独立接手需求、把链路讲清楚，不要展开职业规划。

不要从大学流水账讲起，也不要堆框架名词。

### 2. 简要介绍一下你之前最熟悉的项目

**答题思路**

用 STAR，但把重点放在你亲手做的技术决策上。

1. 业务：这个系统解决什么问题，上下游是谁。
2. 架构：入口、核心服务、存储、缓存、消息队列，用 4 到 5 句话画出来。
3. 你的角色：挑一个难点，讲清约束、你的方案、为什么没选另一个方案。
4. 结果：延迟、错误率、超卖或资损有没有压下来。数字记不清就说数量级，不要编一个很精确的百分比。

准备被追问：表怎么设计、缓存怎么更新、失败了怎么补偿。介绍时主动埋这几个点。

### 3. 你在项目中如何处理过电商场景下的高并发下单请求？

**参考答案**

下单的热点不在「把请求打进数据库」，而在「用更少的同步工作扛住峰值，再保证不超卖、不丢单」。

常见做法是分层：

1. 接入层限流和排队。网关按用户、商品或接口限流，超过容量直接快速失败，避免把数据库打满。秒杀场景可以先用验证码或令牌把请求打散。
2. 读和写分开。商品详情、库存展示走缓存；下单只做必要校验，然后落一笔状态明确的订单。
3. 库存扣减尽量原子化。Redis 里用 Lua 判断库存并扣减，成功后再异步创建订单、写数据库。数据库侧用 `update stock set available = available - ? where sku_id = ? and available >= ?`，靠行锁和条件更新兜底。
4. 下单主链路要短。扣库存、创建订单、发「订单已创建」消息可以在一个本地事务里完成，支付、通知、积分放到消息后面。
5. 水平拆分只在单库确实扛不住时再做，按用户或订单号分片，避免一上来就分库。

面试里把「限流保护数据库、原子扣库存、主链路变短」这三句说清楚，再补你真正做过的那一层。

### 4. 在电商业务中，如何设计一个库存扣减服务，防止超卖？

**参考答案**

超卖的根因是「读到还有库存」和「真正扣减」不是原子的，并发下两个人都读到最后一件。

可靠的扣减要满足三点：原子判断并扣减、扣减可回滚、重复请求不会扣两次。

1. 数据库条件更新是最后一道防线。`where available >= ?` 更新成功才算扣到，影响行数为 0 就返回库存不足。InnoDB 行锁保证同一行的更新串行。
2. 高并发时不要让所有请求都打到这行。先在 Redis 用 Lua 做预扣：库存足够才 `DECRBY`，失败立刻返回。预扣成功再写扣减流水，异步或同步落到数据库。数据库扣失败要把 Redis 加回去。
3. 每次扣减带业务单号。扣减流水对 `(sku_id, order_id)` 做唯一约束，重复请求直接返回上一次的结果，避免网络重试扣两次。
4. 预扣库存要有超时。用户取消或超时未支付，用延迟消息或定时任务释放。释放同样要幂等。
5. 热点 SKU 可以把库存分段，分到多个 key 上减少单 key 争用，下单时随机打到一段。段内仍然用原子扣减。

不要只说「加分布式锁」。锁能串行化，但热点商品会把所有请求堵在一把锁上，吞吐更差。

### 5. 如果用户在支付完成后，订单状态更新失败，你会怎么设计补偿或重试机制？

**参考答案**

支付成功和订单状态更新是两个系统，中间一定会有失败。原则是：支付渠道是事实来源，订单服务要能安全地追上这个事实，并且重复通知不能把订单改乱。

1. 支付回调先落库，再改订单。回调接口验签后，把通知写成一条支付消息（带支付单号、订单号、金额、渠道流水），唯一索引挡住重复通知。接口尽快返回成功，避免渠道不停重试。
2. 改订单做成幂等状态机。只有「待支付」能到「已支付」。已经是已支付、已关闭，再次收到成功通知直接返回成功。金额和订单号不一致则拒绝并告警，不能为了成功把状态改过去。
3. 本地更新失败要可重试。更新数据库和「已支付」后续动作（通知库存、发货）放在事务消息或本地消息表里。失败按退避重试，例如 1 分钟、5 分钟、30 分钟，超过次数进死信，人工或对账任务处理。
4. 定时对账兜底。拉渠道账单或按未完成支付单主动查询渠道。渠道已成功、订单仍待支付的，补一次状态推进。查询也要幂等。
5. 关单和对账会赛跑。超时关单前再查一次渠道；已经支付成功的不允许关成取消。若已经关单又收到支付成功，走退款，不要把已关闭订单硬改回已支付，除非业务明确允许。

### 6. 简述一下你了解的 Spring Cloud 核心组件及其在微服务中的作用

**参考答案**

Spring Cloud 是一套微服务配套，不是某一个框架。面试里按「服务怎么被找到、请求怎么进来、配置从哪来、挂了怎么办」讲即可。

1. 注册与发现：Nacos、Eureka 或 Consul。实例启动时注册，调用方按服务名拿到实例列表，不用写死 IP。
2. 配置中心：Spring Cloud Config 或 Nacos Config。配置和包分开，改配置可以动态刷新，环境之间不会把配置打进 jar。
3. 服务调用：OpenFeign 把 HTTP 调用写成接口；负载均衡（现在常用 Spring Cloud LoadBalancer）从实例列表里选一个。
4. 网关：Spring Cloud Gateway 做统一入口，负责鉴权、限流、路由和灰度。
5. 容错：Resilience4j 或旧的 Sentinel、Hystrix 思路，做超时、重试、熔断、隔离。调用方不能因为下游慢把自己的线程打满。
6. 链路追踪：Micrometer Tracing 配合 Zipkin 或 SkyWalking，一次请求跨了哪些服务能串起来。

现在新项目更常见的是 Spring Boot 加 Nacos、Gateway、OpenFeign，不一定把每个 Spring Cloud 子项目都用上。说清楚每个组件解决的问题，比背版本号重要。

### 7. 在分布式系统中，如何保证服务之间调用的幂等性？

**参考答案**

幂等是指同一个请求执行一次和执行多次，对业务状态的影响相同。超时重试、消息重复投递都会把请求送多次，所以写接口默认要当成「至少一次」来设计。

1. 给请求一个稳定的幂等键。下单用订单号，支付用支付单号，扣库存用订单号加 SKU。不要用每次重试都变的随机 ID。
2. 用唯一约束挡住重复写入。处理前先插入幂等表，唯一键冲突就查出上一次的结果直接返回。这比先查询再插入更安全，查询和插入之间仍有并发窗口。
3. 更新做成条件转移。`where status = '待支付'` 这样的更新，重复执行不会把状态再推进一步。
4. 数据库唯一键和事务要包住「记幂等」和「改业务数据」。只在 Redis 里 `SETNX` 可以挡一层，但 Redis 失败或过期后仍可能重复，核心资金和库存要以数据库约束为准。
5. 查询、删除某一条确定的数据，天然比较容易做成幂等。扣减、创建、发消息必须专门设计。

对外返回也要一致：重复请求返回第一次的成功结果，而不是报「重复」让上游继续重试。

### 8. 假设一个商品详情页需要聚合多个服务的数据（如库存、价格、促销），如何优化其响应速度？

**参考答案**

详情页慢，通常是因为串行调用了库存、价格、促销、评价好几个服务，总耗时等于它们相加。

1. 没有依赖关系的调用并行发出去。用异步 HTTP 或一组超时受控的并发调用，总耗时接近最慢的那个，而不是总和。每个下游都要单独超时，一个服务慢不能拖死整页。
2. 能缓存的不要每次现查。商品基础信息和价格按商品 ID 缓存，促销按活动维度缓存。库存展示可以短缓存，下单时再查实时库存，避免详情页缓存导致超卖。
3. 页面分清首屏。价格、标题、主图同步返回；评价、推荐可以异步加载。接口不要为了「一次给全」把所有下游都串进主请求。
4. 对热点商品做预聚合。变更时提前把详情组装进缓存，请求只读一次缓存。注意失效：价格或促销变了要删掉或更新对应缓存。
5. 下游失败要降级。促销服务挂了，详情仍返回商品和价格，促销区块提示稍后再试，不要整页 500。

### 9. 你了解哪些消息中间件？在订单系统中，消息队列通常用于解耦哪些流程？

**参考答案**

Java 电商里常见 RocketMQ、Kafka，也有用 RabbitMQ 的。订单系统里，Kafka 更偏高吞吐日志和流水，RocketMQ 更常被选来做业务消息，因为它有事务消息、延迟消息和比较明确的投递语义。

订单链路里适合异步的，是那些不需要堵在用户点击上的步骤：

1. 创建订单后通知库存预占、清除购物车。
2. 支付成功后通知履约、发货、开发票、加积分、发短信。
3. 超时未支付的关单，用延迟消息，到点再查一次状态。
4. 订单状态变更写成事件，给搜索、数据仓库和风控各自消费。

不适合丢进队列再祈福的，是「这次下单有没有成功」。用户需要同步知道结果。队列负责主流程成功之后的扩散。

使用时要讲清：生产者确认、消费者手动提交、失败重试和死信、消费幂等。订单消息重复是常态，消费者要用订单号做幂等。

### 10. Redis 在电商系统里一般用来缓存什么数据？缓存穿透和缓存雪崩是什么，如何应对？

**参考答案**

电商里 Redis 通常缓存读多写少、可以容忍短暂不一致的数据：商品详情、类目、价格、促销、用户会话、购物车，以及计数类的库存预扣和限流计数。资金流水和订单状态以数据库为准，Redis 至多是加速层。

缓存穿透是在查一个本来就不存在的数据，缓存没有，请求每次都打到数据库。应对是缓存空值并设较短过期时间，或者用布隆过滤器先判断 key 是否可能存在。还要校验入参，拦掉明显非法的 ID。

缓存雪崩是大量 key 同一时间失效，或者 Redis 本身不可用，流量一起打到数据库。应对是过期时间加随机值，避免同时失效；热点 key 逻辑过期，后台单线程刷新；做多级缓存和限流。Redis 故障时要有降级，例如只保下单、暂时关闭推荐，而不是所有接口一起打数据库。

另外两个容易被一起问到：击穿是某个热点 key 过期瞬间有大量并发回源，用互斥锁或逻辑过期，保证只有一个请求去加载。

### 11. 谈谈你对数据库事务的理解，在分布式场景下如何保证数据一致性？

**参考答案**

单库事务用 ACID。原子性靠 undo 回滚，持久性靠 redo，隔离性靠锁和 MVCC。InnoDB 默认隔离级别是可重复读，用 MVCC 解决普通读的不可重复读，用间隙锁补幻读。事务要短，不要在事务里调远程接口。

跨服务以后没有一个单机事务能包住所有库。先按业务决定能不能接受最终一致：

1. 订单服务自己的「创建订单、写本地消息」必须强一致，放在同一个本地事务里。
2. 库存、积分、通知可以最终一致。用本地消息表或事务消息，保证「业务写成功则消息一定发出」。消费者幂等更新自己的库。
3. 对账补洞。定时比较订单和支付、订单和库存，发现不一致再补偿。
4. 真的要求跨库同时成功或同时失败，才考虑 TCC、Saga。TCC 要写 Try、Confirm、Cancel，成本高，适合支付、账务这种不能靠事后补偿糊弄的场景。普通电商下单用消息加幂等就够。

一致性还包括一个容易漏的点：重试和补偿本身要幂等，否则补救过程会制造新的不一致。

### 12. 你之前是如何排查和定位线上问题的？可以举一个具体例子吗？

**答题思路**

讲一个你真的处理过的故障，按时间线，不要先背工具名。

1. 现象：哪个接口、从什么时候、影响多少用户，错误是超时、5xx 还是结果错。
2. 缩小范围：看监控把问题定到应用、数据库、缓存还是下游。黄金指标看延迟、流量、错误率、饱和度。
3. 定位：应用看日志和 trace，慢接口看线程和 CPU；数据库看慢查询和锁；缓存看命中率和连接数。
4. 处理：先止血（限流、降级、回滚、扩容），再改根因。
5. 复盘：补监控或测试，避免下次靠人肉看日志。

例子可以是一次慢 SQL、一次缓存击穿，或一次消息堆积。把「怎么判断是它、做了什么、结果如何」讲具体。没把握的命令行参数不要编。

### 13. 你怎么看待 AI 辅助编程工具（如 Copilot、Cursor）在当前开发工作流中的作用？

**参考答案**

这些工具适合加速已经会做的事：补样板代码、写测试草稿、解释一段不熟的代码、根据报错给出排查方向。它们不替你对需求、边界和线上后果负责。

比较稳的用法是人来定接口、数据模型和失败策略，让工具写第一版实现，然后自己审查 diff。重点看事务边界、空值、并发、权限和是否把不可信输入拼进 SQL 或命令。生成的代码要能在本地跑过测试，不能因为「看起来对」就提交。

不适合直接交给它的，是你自己讲不清的设计。库存怎么扣、消息会不会重复，这些如果自己没有判断，工具给出的方案往往是常见模板，不一定符合这个系统的一致性要求。

面试里可以收成一句：AI 编程提高的是产出速度，代码审查、测试和线上责任仍然在工程师身上。
