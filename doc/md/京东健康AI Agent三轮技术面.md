# 京东健康 AI Agent 三轮技术面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

面完了，整体感觉挺硬的，没问那些八股文，上来就直接问场景和架构，是正经做事的面试。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「我是谁 → 做过什么 → 为什么和这个岗位有关」讲完就停。

1. 一句话交代年限和方向，点出你真实写过的检索、工具调用或对话状态，别先铺模型名词。
2. 只展开一个最相关的项目：用户要完成什么事、你负责哪一层、结果用你拿得出来的证据。没有数字就讲评测样本或坏例，不要临时编指标。
3. 收到京东健康这个岗位上：症状、用药和挂号都会碰到真实用户和真实接口，回答必须能停、能转人工、能审计。把话停在你准备被追问的那个项目上。

### 2. 请介绍一下你参与的项目，以及你在其中的角色和核心贡献

**答题思路**

用真实项目套这个顺序。团队项目里先划清边界，没做的层直接说没做。

1. 用户是谁，任务是查询、办理，还是只生成一段说明。为什么一次问答不够。
2. 按一条请求讲：入口与鉴权、会话状态、检索或工具、校验、回复或转人工。每一步说清输入和输出。
3. 你的贡献落在编排、工具、检索、评测或线上排障中的具体一层，并说明谁对医疗内容或业务规则负责。
4. 准备一个难点：现象、落在哪一层、改了什么、用什么确认修好。常见真问题包括检索命中了但生成改写了事实、写接口超时后被重复执行、多轮把已采集的槽位盖错。
5. 主动留三个追问口：状态存在哪、失败时用户看到什么、剂量或号源从哪个接口来。

简历里没有智能体项目时，讲最接近的检索、规则或工作流，并说明它还缺工具观察和任务是否完成的判定。

### 3. AI Agent 与传统的自动化脚本或 RPA 机器人最主要的区别是什么？你是如何理解「智能」这个维度的？

**参考答案**

AI Agent 按目标决定下一步，可以调用工具，并根据观察继续、澄清或停止。自动化脚本和 RPA 按预先写好的步骤操作界面或接口，分支和异常也要事先枚举。

「智能」指两件事：脚本没覆盖的说法仍能接住；看到工具结果或用户补充后，下一步可以改变。它不表示模型有权下医疗结论。模型的选择是概率性的，所以系统还要有真实工具观察、步数上限，以及必须停下来转人工的条件。

只有一段自然回复、没有行动和停止条件，仍然是对话补全。界面或接口契约一变，RPA 会停；Agent 则要靠契约校验和评测，避免它在契约外面自由发挥。

### 4. 在设计和实现一个与健康咨询相关的 AI Agent 时，你会从哪些方面考虑其系统架构？（可涉及模块划分、数据处理流程）

**参考答案**

按接入审计、对话状态、安全策略、知识检索、业务工具和人工升级拆开。模型负责理解说法和组织语言；急症分流、药品事实和号源由规则和工具给出。

模块上，接入层做鉴权、同意、限流和审计。对话层保存槽位，而不是只堆积历史消息。安全层在模型之外识别急症和越界请求。知识库带来源、版本和生效时间。工具层访问药品、号源和档案，参数先校验。低置信度和高风险进入人工。

处理顺序是：输入先过急症和提示注入检查；更新槽位；缺关键信息就只问一个问题；信息够了再检索或调工具；回答要对上检索片段或工具结果；输出策略再拦一遍禁止项，然后才发给用户。失败时明确说不知道，并给出转人工或就医入口。

漏掉急症比多问一句严重，规则宁可误报。用户档案和共享知识库分开，标识信息默认不出已评审的部署。

### 5. Agent 的核心循环通常包括感知、规划、执行、学习。在 Spring AI 或 LangChain 的框架实践中，你是如何对应实现这几个环节的？能结合一个具体场景（如用药提醒、报告解读）说明吗？

**参考答案**

感知、规划、执行放在同一次带工具的模型循环里。生产环境的「学习」不是当场更新权重，而是记下确认过的事实和失败样本。

感知：Spring AI 用 ChatClient 把用户这句话、窗口记忆和检索 Advisor 拼进同一次请求。LangChain 现在更适合用 LangGraph 的状态读入等价信息，而不是把循环藏在不可回放的执行器里。规划：模型在直接回答和调用哪个工具之间选择；路径固定时用 Chain，需要分支时才进入 Agent 循环。执行：Spring AI 的 `@Tool` 方法，或 LangChain 的 Tool，真正访问数据库和接口，观察写回状态。学习：槽位、依从性事件和被人工改过的回答进入记忆与评测集。这两个框架的默认循环都不做在线梯度更新。

用药提醒里，用户说忘了，规划只允许先取该药说明书的漏服条款。条款不存在就回答不知道，并建议联系药师，不能生成一条对所有药都成立的补服规则。报告解读同样先把指标结构化，再查参考范围，解释引用这份结果，不下诊断。

### 6. 在 Java 技术栈中集成大模型能力，你通常会采用哪种方式？比较直接调用 API、使用 Spring AI 框架、或集成 LangChain4j 的优劣和适用场景。

**参考答案**

已有 Spring 服务、需要统一模型和工具时，用 Spring AI 做运行时。编排和检索实验很重时可以用 LangChain4j，但只留一个编排入口。框架还没封装的厂商私有参数，才直接调用 API。

直接调 API 能立刻用流式、新参数和厂商特有的工具格式，记忆、路由、审计和供应商差异都要自己写。Spring AI 的 ChatModel、ChatClient、Advisor 和 `@Tool` 嵌进现有鉴权、配置和监控；短板是抽象会落后于厂商最新字段，合规也不会被框架代劳。LangChain4j 用 AiServices 把工具、记忆和 RAG 收进一个接口，复杂检索链起步快。它和 Spring AI 各写一套循环，会出现两套状态。

健康业务服务以 Spring AI 接模型，工具边界写在业务 Bean 里。私有部署只要提供 OpenAI 兼容接口，就仍然走这层抽象。引入 LangChain4j 之前，先确认它替换的是编排，而不是又包一层聊天接口。

### 7. AI Agent 在处理多轮对话时，如何有效管理和维护对话状态（Dialog State）与上下文（Context）？你在项目中是如何实现的？

**参考答案**

上下文是这一轮放进窗口的文本；对话状态是结构化槽位，窗口被截断后仍然在。只靠历史消息，多轮问诊会丢掉已采集的症状，或者把旧值覆盖错。

状态至少包括当前意图、已填槽位、已经问过的问题、待执行工具、紧急程度和是否已转人工。槽位要带来源，区分用户原话、系统推断和工具结果。它按会话编号放在 Redis 或数据库里，和长期健康档案分开。每轮先读状态，用结构化输出或规则做增量更新，再把状态摘要注入系统提示。历史只留最近若干轮加一段摘要。矛盾的新值先追问，不直接覆盖。同一会话用版本号或锁，避免两条并发消息互写。

讲项目时按「存在哪、谁可以改、重启后还在不在、工具失败会不会写成猜测」说。当时如果只有消息窗口，就承认这一点，并说明会丢哪类槽位。

### 8. 使用 Spring AI 时，如何对不同的模型提供商（如 OpenAI、通义千问、本地部署模型）进行抽象和统一管理，以实现灵活的模型切换和降级策略？

**参考答案**

业务依赖 ChatModel 这个接口，每个供应商一个实现。切换放在路由和配置里。Spring AI 自带的重试打在同一个端点上，跨供应商降级要自己包一层。

OpenAI 兼容接口用对应 Starter。通义千问用 Spring AI Alibaba 的 DashScope ChatModel，或把兼容模式地址配进 OpenAI Starter。本地模型用 Ollama，或把 vLLM 的 OpenAI 兼容地址配进去。多个 Bean 用限定符区分。每个模型登记是否支持工具调用、JSON 模式和上下文长度，不能只换模型名。

只有超时、429 和 5xx 才降到备用模型。参数校验失败不换一个模型碰运气。两个都不可用时，急症走固定话术，其余明确失败并转人工。含身份信息的健康对话默认进已评审部署，不因为降级打到未评审的公网模型。换模型按发版处理：同一评测集通过再生效。追踪里带上供应商、模型名和是否降级。

### 9. 场景题：假设要为京东健康设计一个「智能分诊」Agent，用户通过文字或语音描述症状，Agent 需要引导问询并初步判断可能的科室或紧急程度。请描述这个 Agent 的关键技术模块和核心处理流程。

**参考答案**

这是分诊辅助，用来建议就诊方向和紧急程度，不产出诊断。急症规则和指南检索在模型之外。

模块包括语音转写、急症规则、槽位状态、指南检索、受结构约束的判断、人工升级和审计。流程是：

1. 文字直接进入，语音先转写并保留原文。否定词和部位要向用户确认，避免把「没有胸痛」听成「胸痛」。
2. 胸痛、呼吸困难、大出血、意识障碍、自伤等命中急症规则后，停止追问，给出急救提示并转人工。
3. 未命中时，每轮只补一个缺失槽位：主要症状、时长、程度、年龄、性别、孕期、慢病和用药。
4. 槽位足够后，按人群过滤指南片段。模型只能在给定枚举里输出可能科室、紧急程度、依据和置信度。
5. 低置信、自相矛盾或用户明显痛苦时，改为转医师。科室名使用医院真实号源。

急症召回优先于少问两句。对外话术是「可能适合就诊的方向」，并留下医师入口。

### 10. Agent 在调用外部工具（Tool Calling）或 API（如查询药品信息、预约挂号接口）时，如何保证调用的可靠性、处理超时与异常？

**参考答案**

工具按普通远程调用来设计：校验、超时、幂等和熔断都在模型之外。模型只看见结构化的成功或失败；失败后不允许改用参数记忆编造药品信息或号源。

调用前用 schema 校验参数，用户身份从登录上下文取。连接超时和读超时分开，并在本轮剩余时间用尽时取消。药品查询这类读接口可以有限次重试。挂号这类写接口不盲目重试，用幂等键把重复请求收成同一次业务结果，执行前让用户确认。

超时、4xx、5xx 和熔断写成工具观察，例如未找到说明书或上游超时。堆栈和上游原文不要塞回模型，既避免间接提示注入，也避免模型把错误圆成正常回答。工具循环有最大步数。写操作用发件箱或本地消息，避免接口已成功但本地没有记录。查不到药品时回答不知道，不估算剂量。

### 11. 在 Agent 的开发中，如何进行效果评估和持续优化？你关注哪些核心指标？

**参考答案**

离线看任务有没有做对、危险请求有没有拦住；线上看有没有办完、是否转人工、延迟和成本。用户满意度不能代替医疗正确性。

离线固定对话集至少包括：任务是否成功、槽位是否填对、工具名和关键参数是否正确、回答是否被引用支持、该拒答的是否拒了。分诊把急症召回单列，漏检不能被总分平均掉。用药核对说明书事实，不用模糊的文本相似度代替。

线上关注一次会话是否办完、转人工率、不安全输出、工具成功率、平均步数、时延、输入和输出 Token、费用。高风险意图人工抽检。提示词、模型或索引变更都回归同一套样本，安全样本退步就不得发布。

优化时按错误类型改对应层：检索错改索引，事实错改工具，话术错才改提示词。模型自己生成、未经复核的回答不进入训练集。

### 12. 你如何看待 AI Agent 在医疗健康领域的应用边界与伦理风险？在技术实现上如何设置必要的「护栏」（Guardrail）？

**参考答案**

Agent 可以做导诊、说明书解释和流程办理。诊断和处方留给有资质的医师。护栏是模型外面的规则、权限和发布门禁；一段「请不要胡说」的提示词挡不住错误剂量。

主要风险是错误用药、虚假安慰、隐私泄露，以及用户把助手当成医生。检索文档和工具结果都可能携带注入指令。孕期、儿童和用药变更默认更保守。

输入层识别急症和越界请求。决策层把剂量、号源和医嘱只交给工具，检索不到就拒答。输出层禁止确定性诊断用语和自行计算剂量，关键事实带上来源。权限层按服务端身份鉴权，高风险动作二次确认，全链路审计。提示词和模型变更先过安全样本。这些措施降低风险，不能证明已经没有幻觉。被问效果时，讲拦截和转人工是否按预期触发。

## 二面

### 1. 自我介绍

**答题思路**

一面面试官还在场时，用 20 秒收住：年限、项目和你的角色各一句，然后把话交给最大的技术挑战，不把一面的架构再讲一遍。

换了面试官，就用 1 分钟补齐三件事：用户要完成的任务、请求经过的关键层、你亲自写的那一层。仍然只留一个项目。数字和案例用你自己的；没有统计就说当时靠哪类坏例判断做对了。结尾停在挑战上，方便对方追问分析和验证。

### 2. 深入聊聊你做过的项目。遇到的最大技术挑战是什么？你是如何分析并解决的？

**答题思路**

选一个你能从轨迹里讲清楚的问题。优先选「模型说得很顺，但事实或副作用错了」，而不是一个只靠调参解决的故事。

1. 情境：用户任务、哪一类请求失败、影响是错答、重复写入还是无法收场。
2. 分析：用同一次请求的提示词、检索片段、工具参数和工具结果把层次拆开。先分清是检索错、工具错、状态被盖错，还是生成改写了证据。
3. 动作：改拥有事实的那一层。剂量和号源回到工具；协议内的分支收成规则；提示词只改话术。给这个坏例补一条回归样本。
4. 结果：用现象说明，例如同类坏例不再出现、写接口不再重复成功。没有对照数据就不编百分比。
5. 收束：你现在会在上线前固定哪类样本。没做过的环节不要说成你的方案。

### 3. Agent 的规划（Planning）能力至关重要。在复杂的健康管理场景中（如慢性病管理涉及用药、运动、饮食、监测），Agent 如何进行任务分解和步骤规划？有没有研究或应用过 ReAct、ToT 等进阶框架思路？

**参考答案**

慢性病管理维持一份护理计划：用药、监测、饮食、运动和复诊各自有时间、前置条件和状态。协议里已经确定的步骤用状态机推进，模型用来理解例外和生成解释，不每次从零写一份长计划。

每轮只处理当前事件。漏服或监测值异常时，选出相关任务，规划接下来一到三步，而不是把一周的生活一次生成完。事件发生就重规划，过期计划不继续执行。

ReAct 适合当前这一问：思考、调用工具、读观察、再决定。它看得近，也可能循环，所以要有步数上限，并且思考过程不直接当作用户可见的医疗建议。先规划再执行适合跨天任务，但计划必须能因新事件作废。Tree of Thoughts 只在高不确定、允许变慢的问题上做少量分支，由规则或医师策略打分；不用模型投票做医疗决定。

LangGraph 把这些步骤收成有检查点的状态图，进程重启后从上次事件继续。用药时间表这类确定性流程，不交给无约束的 ReAct。

### 4. RAG 是增强 Agent 知识准确性的关键。在健康领域，如何构建高质量的医学知识库（数据来源、清洗、结构化）？在检索阶段，如何提升查询与文档的匹配精度，并处理可能的冲突或过期信息？

**参考答案**

知识库只用有来源、有版本的材料，例如现行诊疗指南、药品说明书和医院已生效的内部规范。论坛和未标注出处的文章不进索引。用户个人档案也不进共享知识库。

清洗时去掉页眉页脚，按药品、疾病和章节结构化，表格整表保留。每段带上来源、版本、生效时间、适用人群和科室。切分按章节做，小块负责命中，生成时带回所属小节，避免剂量表和药名拆开。嵌入模型一换就要重建索引。

检索用混合召回：药名、剂量单位走关键词，症状描述走向量，再按人群、科室和生效时间过滤，并用交叉编码器重排。多轮对话先把指代补成可以独立检索的查询。低分或空结果就拒答。

冲突时按权威和时间排序：现行说明书和指南优先。排序后仍冲突，就并列引用，不擅自选边；涉及剂量则不回答，转药师。失效文档在查询时滤掉。用户问的是旧版本时，明确说现在依据的是哪一版。

### 5. 多模态能力整合：如果 Agent 需要处理用户的皮肤照片、体检报告图片等，并结合文字描述进行判断，在架构上如何设计？涉及哪些关键组件和技术选型？

**参考答案**

图片先归类，再走不同解析器，最后和用户文字一起进入同一份会话状态。一份报告或一张皮肤照都不能直接变成诊断或治疗方案。

组件包括对象存储、同意与审计、类型路由、报告解析、皮肤照片处理和文本推理。报告优先做版面分析和 OCR，把指标、单位和参考范围收成结构，再由工具核对、由文本模型解释。这条链路可以指出每个数字从图片的哪一处来。整页交给视觉模型更省事，但表格错一位数时很难审计。皮肤照片先做清晰度检查；视觉模型只描述可见特征。专用分类模型如果使用，也只给医师做参考，输出需要鉴别的方向，不直接给用户病名。

用户文字用来补充部位、时长和既往情况，不能代替图片里缺失的信息。两条结果都写进状态，并标记来源。含身份信息的图片留在已评审环境。看不清、类型不符或用户要求治疗方案时转人工。

### 6. Agent 的「记忆」机制。如何设计长期记忆和短期记忆，以支持对用户个性化健康习惯的学习和持续服务？在实现上，如何与向量数据库、传统数据库结合？

**参考答案**

短期记忆管这一次会话，长期记忆管跨会话仍然有效的事实。个性化不能覆盖医嘱：提醒时间可以学习，剂量不能从聊天里学出来。

短期记忆放 Redis 或带过期时间的会话库，内容是最近消息、滚动摘要、当前槽位和这一轮工具结果。超长就摘要，槽位单独保存。

长期记忆分成三份。关系数据库保存确认过的档案：过敏、慢病、偏好，字段带时间、来源和是否用户自述。向量库只保存交互摘要，检索时必须按用户过滤，用来想起「上次说过头晕」，不作为过敏史的权威数据源。医嘱和提醒计划只由医嘱服务写入。对话里新提到的过敏记成用户自述，不覆盖就诊档案；两者冲突时告诉用户，并建议人工确认。

每轮先读档案，再用当前问题检索少量相关摘要。检索到的记忆当数据，不当指令。用户可以删除对话记忆。工具原文默认不写入长期记忆。

### 7. 场景题：设计一个「智能用药依从性管理 Agent」。它需要提醒用户服药，并能响应用户关于「忘吃了怎么办」「有副作用如何处理」等复杂咨询。请详细阐述其系统设计、核心交互逻辑以及可能用到的 AI 模型/工具。

**参考答案**

权威数据是医嘱和说明书，模型只负责理解用户的话和解释工具结果。提醒本身用调度和模板完成，不每次让大模型自由发挥。

系统包括医嘱服务、提醒调度、会话状态、说明书检索、升级工单和依从性日志。咨询这一轮才调用较强的模型。工具至少有：按用户取当前医嘱、把口语药名解析成药品主数据 ID、读取说明书指定小节、记录服药事件、创建人工单。

用户说忘了时，先确认是哪一种药，再只读取该药的漏服条款并按条款回答。没有条款就说不知道，建议联系药师。不生成「所有药都下次加倍」或「把两次合成一次」。

用户说有副作用时，先收集严重程度，再对照说明书里的立即就医条目。命中这些条目，或出现呼吸困难、严重皮疹、呕血、黑便等表现，就停止自我处理并转人工。不要建议自行停药，除非说明书或医嘱写了停药条件；其他情况请联系开方医师。

药名有歧义、同时服用多种药，或工具查不到时，先澄清或拒答。提醒时间可以按用户习惯调整，剂量和时间表的医学内容只跟医嘱走。

### 8. Spring AI 的 Function Calling 支持是如何工作的？在项目中，你是如何定义和管理这些可供 Agent 调用的函数的？如何保证函数调用的安全性和权限控制？

**参考答案**

模型只产生工具名和参数，Java 方法由框架执行。Spring AI 把 `@Tool` 方法的 schema 发给模型；模型返回调用请求后，框架反序列化参数、执行方法，再把结果作为工具消息发起下一次请求，直到模型给出文本，或达到工具调用上限。

工具按业务能力定义在 Spring Bean 上，描述写清何时调用、何时不要调用。单次请求需要的工具通过 ChatClient 注册。返回内容只给该小节或结构化结果，不把整本说明书塞回窗口。行为变化时给工具加版本，并用录好的调用和非法参数做测试。

身份不放进模型能填的参数。`ToolContext` 由服务端传入，不会进工具 schema，方法里只读取，这个 Map 本身不可变：

```java
@Tool(description = "按药品主数据 ID 读取说明书的漏服条款；没有该条款时返回未知")
public String getMissedDose(
        @ToolParam(description = "药品主数据 ID") String drugId,
        ToolContext toolContext) {
    access.check(toolContext.getContext().get("userId"));
    return leafletService.missedDose(drugId);
}
```

```java
chatClient.prompt()
        .user(userText)
        .tools(leafletTools)
        .toolContext(Map.of("userId", currentUserId))
        .call()
        .content();
```

方法内再做参数校验、数据权限和限流。每个场景一份工具白名单，不把仓库方法直接暴露成工具。写操作二次确认并带幂等键。工具结果当数据，不当新的系统指令。参数、结果码和耗时进审计，敏感内容脱敏。

### 9. 在微服务架构下，如何将 AI Agent 能力以服务的形式提供？如何设计 API 接口、如何处理高并发下的 Agent 实例管理与资源隔离？

**参考答案**

编排服务保持无状态，会话状态放在外部存储。请求到来才装载状态，不在 JVM 里为一个用户常驻一个 Agent 对象。医嘱、药品和号源继续由各自的服务拥有。

接口按会话和事件设计。创建会话；发送消息时带幂等键，并用 SSE 返回文本增量、工具调用、引用和转人工等事件。长任务做成带检查点的作业，客户端用同一会话重连。同一会话同时只有一个写入者，用锁或单写队列避免两条消息改同一份槽位。第二个请求排队，或直接告知用户稍候。

模型调用按供应商设信号量、超时和 Token 预算。扩容看在途请求和延迟，不看 CPU，因为等待模型时 CPU 可以很低。扩容前先看供应商配额，否则实例变多只会放大 429。工具服务独立超时、权限和降级，编排服务故障不丢医嘱主数据。

隔离做到场景配额、独立线程池，以及请求绑定提示词和模型版本，避免同一次发布里一个用户碰到两种行为。

### 10. 谈谈你对 LangChain（或 LangChain4j）中 Chain、Agent、Tool 这些核心抽象的理解。它的设计哲学对你在构建 Agent 系统时有什么启发或影响？

**参考答案**

Tool 是带 schema 的能力：输入校验后执行，输出是观察。副作用只发生在这里。Chain 是代码里预先排好的步骤，适合「先检索、再按证据回答」这种路径已知的流程。Agent 把下一步交给模型，在工具和结束之间循环，灵活，也更不容易预测。

LangChain 的设计是把模型、提示词、解析和工具都变成可组合的组件。早期 AgentExecutor 把循环藏起来，排障困难；LangGraph 把循环变成看得见的状态图，这个方向更适合要审计的系统。LangChain4j 不照搬这条管道语法，而是用 AiServices、`@Tool` 和 ChatMemory 把同一类概念装进 Java 接口。控制流仍然应该留在你能测试的代码里。

启发是：固定路径用 Chain，只有分支真的依赖观察时才用 Agent；Tool 成为权限和副作用的边界；提示词和模型可以替换，但任务状态不放进任何一个框架的隐藏对象里。

### 11. 如何对 AI Agent 系统进行监控和可观测性建设？除了常规的 QPS、耗时，你会特别关注哪些与 AI 相关的指标（如 Token 消耗、提示词命中率、工具调用成功率等）？

**参考答案**

一次用户请求做成一条追踪，下面挂模型调用、检索和每个工具。常规的 QPS、错误率和延迟仍然要有，但它们看不出回答是否有依据。

Token 把输入、输出和工具结果分开记。工具观察经常是费用的大头。同时记录首 Token 时间和场景级费用。工具成功率按工具名拆开：参数不合法、超时、业务上不存在和 5xx 是四类问题，查无此药不是服务故障。

「提示词命中率」没有单一行业定义，要先说明口径。一个是场景路由是否选中了预定模板，它影响行为是否一致；另一个是供应商前缀缓存是否命中，它影响延迟和费用。两个数不要合成一个。

另外看每轮步数、空检索率、拒答率、安全规则触发率和转人工率。线上指标发现不了「说得流畅但剂量是编的」，所以高风险场景保留抽检，并和离线评测集一起看。日志默认脱敏，安全事件保留足够的轨迹供复核。

### 1. 自我介绍

**答题思路**

控制在 30 到 45 秒，讲判断力，不再讲模块清单。

1. 你现在做的是面向用户的任务系统，还是内部效率工具。一句话说清用户最后要拿到什么。
2. 举一个你坚持不交给模型的决定，例如剂量、支付、删除或对外承诺。说明你把事实放回了哪一层。
3. 为什么愿意做健康场景：约束硬，做错有明确代价，系统必须能停、能追溯。
4. 停在这个取舍上，方便对方接着问愿景、选型和团队协作。

### 2. 抛开具体技术，从产品和技术愿景角度，你认为一个理想的「京东健康 AI 健康助手」应该具备哪些核心能力和特征？它与当前常见的客服机器人或知识库搜索有何本质不同？

**参考答案**

理想的助手能把一件健康事务推进到安全的结果：记住任务进行到哪一步，调用真实的购药、挂号和档案能力，不确定时转给医师，并且每条关键事实都能追溯。它可以主动提醒，但不能主动改医嘱。

核心特征是责任边界清楚。用户知道下一步是自我处理、线上问诊还是急诊。个性化只体现在习惯和表达，不体现在剂量和诊断。跨天之后还要接得上一次的任务。

客服机器人把一句话映射到话术或一篇文章，知识库搜索返回文档。二者优化的是「有没有一条回复」。助手优化的是任务有没有在安全状态下结束：该办的办完，该停的停下，并留下可以复核的记录。

### 3. 在技术决策层面，当面对一个全新的、快速演进的 AI Agent 技术栈（如不断更新的 LangChain、各种新框架）和一个你们团队已经熟悉但可能并非最优的旧方案时，你会如何主导技术选型？决策过程中会重点评估哪些维度？

**参考答案**

先用同一批真实任务对比，不凭框架热度替换。旧方案没有碰到安全、排障或交付效率上的硬伤时，不因为新框架重写核心循环。

评估这些维度：健康数据能不能留在已评审环境；控制流能不能单测和回放；框架 API 稳定不稳定，核心循环被私有接口绑死后退出成本有多高；团队能不能在故障时自己定位；延迟、费用和供应商配额；现有鉴权、审计和发布流程能不能接上。

做法是把编排和模型客户端分开。模型接入、向量库可以用成熟组件；任务状态和工具权限留在自己的代码里。给新旧方案同一个时间盒和同一套评测，用任务成功、定位一条故障所需的步骤、安全样本是否退步来量化差距。只迁移差距已经出现的那一层，旧场景继续服务，直到新路径在评测上胜出。

### 4. 如何带领或协调一个团队从 0 到 1 开发一个 AI Agent 项目？在人员能力构建、开发流程、协同方式上，你认为有哪些需要特别注意的地方？

**参考答案**

从一个窄场景的端到端竖切开始，不先做平台。上线标准在写功能之前定好：什么叫这件事情办完，哪些话绝对不能说，什么情况必须转人工。

人员上同时要有后端、评测和业务或临床复核。只会写提示词覆盖不了工具、审计和坏例。每个人都要能读一条完整轨迹。临床或业务方从第一周参加，而不是上线前再看话术。

流程上，评测样本和安全红线先于功能清单。提示词、模型和索引按代码版本管理。每周按错误类型复盘，而不是只看演示。高风险回答有明确的否决权。

协同上，产品负责场景边界和验收，工程负责工具、状态和审计，算法负责检索和模型指标。医疗内容的分歧取更保守的方案，同时写清转人工带来的等待成本。特别注意演示和线上的差距：没有轨迹回放和回归样本，团队无法判断一次修改是变好了还是只变流畅了。

### 5. AI Agent 的幻觉问题是落地中的一大挑战。在健康这种高严谨性领域，你们在项目中采用了哪些工程和技术手段来尽量缓解或控制幻觉？效果如何？

**参考答案**

幻觉要按事实类型拆开处理。剂量、号源、档案和医嘱只从工具读取。医学解释走带来源的检索，检索为空或分数不够就拒答。急症和越界由模型外的规则决定。模型负责把这些结果说清楚。

工程上，回答使用结构化输出，关键事实要求引用。高风险回复做一次主张和证据的核对；剂量这种字段用精确匹配，不靠另一个模型的感觉。事实类调用把温度调低。检索文本和工具结果当数据隔离，避免里面的指令改变策略。未经复核的模型回答不回灌训练。提示词、模型和索引变更都要过同一套安全样本。

这些手段减少无依据的事实，不能消灭所有错误表述。讲效果时只比较同一批标注样本在改动前后的差异，例如不该出现的用药建议有没有减少、该转人工的有没有转。没有这份对照，就说明当时还没能量化，不补一个百分比。

### 6. 从系统架构角度看，你认为构建一个企业级、可运维、可迭代的 AI Agent 平台，需要哪些核心的中间件或平台组件支持？（可涉及提示词管理、评估平台、A/B 测试、数据回流等）

**参考答案**

平台要让一次行为变化能定位、能回滚，而不是只把模型调用包装成接口。

核心组件包括：模型网关，负责路由、配额、密钥和降级；提示词注册表，保存版本、适用模型和回滚；工具注册表，保存 schema、权限和超时；会话与记忆存储；带生效时间的检索流水线；独立的护栏服务；人工工单。

迭代组件包括评测平台、实验平台和数据回流。评测平台用固定数据集出分数，安全样本一票否决。A/B 测试的单位是用户或会话，避免同一个人一轮一个版本；实验可以改话术和模型，不把安全策略放进实验组，并设置能自动停的保护指标。数据回流先脱敏、抽样和人工复核，复核后的坏例进入评测集或提示词，不自动变成训练标签。

观测、成本和权限贯穿这些组件。没有评测和版本，提示词管理只是一张可编辑的表。

### 7. Agent 的持续学习（Continual Learning）能力：如何设计系统，使得 Agent 能够从与用户的真实交互中安全地学习并优化自身行为，而不需要频繁的全量重训？

**参考答案**

交互数据不能直接改线上权重。安全的持续学习是：审计过的数据用来更新提示词、检索库、工具和记忆；模型权重只在离线、小步、可回滚地变。

每条轨迹记录输入、状态、检索、工具、输出、用户是否纠正、是否转人工，脱敏后入库。抽样由人和业务复核。模型自己的回答不能直接当标签，否则会把幻觉学进去。用户说「以后所有药都加倍」这类话也不能写成规则。

大多数改进不需要训练：坏例进评测集，修正提示词和路由，新指南重新入库，工具修缺陷。用户偏好放在已确认的长期记忆里，立即生效且可删除。剂量和诊断不在可学习字段里。

确需改模型时，用小规模的监督微调或偏好优化，并回放旧的安全样本，避免灾难性遗忘。先走影子流量，再小流量。评测退步就回滚。不做按对话步的在线梯度更新，否则既容易被投毒，也无法解释某一天行为为什么变了。

### 8. 谈谈你对「多 Agent 协同」在复杂健康场景（例如，一个负责解读报告，一个负责生成膳食建议，一个负责协调日程）中应用前景的看法。这会带来哪些新的技术挑战？

**参考答案**

多 Agent 适合职责已经冲突的场景：报告解释、膳食建议和日程安排如果塞进同一个提示词，规则会互相污染。对用户只暴露一个协调者，专家返回结构化结果，由协调者决定说什么、办什么。

前景在于每个专家可以单独评测，日程和检索也可以并行。前提是共享同一份任务状态，而不是三个 Agent 各记各的记忆。

新的挑战是建议冲突、延迟和费用叠加、责任不清。膳食建议若和药品饮食禁忌冲突，以禁忌和医嘱为准，并提示咨询医师或药师，不能让两个 Agent 各说各的。任何一个专家都不应该直接给用户发消息，也不应该各自拥有写医嘱的权限。

评测要看整条链路，而不是每个 Agent 的演示。简单问答不要拆成多个自由对话的 Agent。从一个 Agent 加多个工具开始，只有提示词和评测已经互相干扰时再拆。

### 9. 你个人如何保持对 LLM、AI Agent 领域快速发展的技术敏感度和学习节奏？最近半年，最让你感到兴奋或认为有颠覆性潜力的相关技术、论文或开源项目是什么？

**答题思路**

把节奏说成固定动作，而不是「经常关注」。例如每周看你真能调用的模型的发布说明，读一篇工程文章或论文，并用自己的一个小任务验证它有没有改变工具成功率、延迟或排障方式。自己留一份记录：试了什么、留下什么、放弃什么。框架发布很多，只深跟你系统里会用到的那一层。

最近半年只讲一件你读过或跑过的东西。按「它解决的旧问题 → 你验证了什么 → 用到健康场景有什么限制」讲。没看过的论文名不要背。

如果需要备选方向，选你能讲清机制的：用统一工具协议把业务接口和模型解耦，用推理模型以更多测试时计算换规划质量，或者用轨迹评测代替演示判断。把名字换成你自己的阅读记录。兴奋点落到京东健康能用的地方，同时主动说明成本和不确定输出。

### 10. 在资源（算力、数据、人力）有限的情况下，你会优先投资于 AI Agent 系统的哪个环节以最大化用户体验和业务价值的提升？为什么？

**参考答案**

优先投资一条高频、高风险、已经能接上真实系统的任务链路，把权威工具和安全闸门做对，并配一套小的复核评测集。模型保持够用。

用户能感到的是这件事有没有办完、答案有没有依据、危险情况有没有被拦住。药品、号源和医嘱放在数据库里，比换一个更大的模型便宜，也更可核对。没有评测集，后面的提示词和模型花费无法判断有没有变好。算力用在这条链路的在线推理和检索上。

先不投全量微调、多 Agent 平台和新框架迁移。这条链路的任务成功和安全拦截稳定之后，下一笔再投到知识更新和转人工质量。

## HR面

### 1. 请做一个简单的自我介绍。

**答题思路**

用 45 到 60 秒，少讲架构，多讲你做什么、和谁一起做成、为什么来这里。

1. 现在的方向和年限，一句即可。
2. 一件和 Agent 或相近系统有关的事：你负责的部分、和产品或算法怎么配合、最后用户能完成什么。不报记不住的指标。
3. 为什么和京东健康的 AI Agent 岗位有关：你想把高约束场景做成能上线、能追溯的系统。
4. 技术面已经讲过的细节不重复。收住，把时间留给动机和协作。

### 2. 为什么选择京东健康，以及这个 AI Agent 开发的职位？

**答题思路**

回答落在业务约束和岗位匹配上，不贬低现在的团队，也不空泛地说平台大。

1. 京东健康把健康咨询、购药和就医服务放在同一套业务里，Agent 有真实接口可以接，不是只做聊天演示。
2. 这个职位看重的是把想法做成稳定系统：要处理安全、可靠和医疗边界。这和你想深入的问题一致。
3. 用你真实经历里最接近的一段说明：你处理过工具副作用、错误答案或跨角色标准不一致。没用过京东健康的服务就不要编就诊经历，改讲你为什么选择高风险场景。
4. 最后一句收在你能贡献的层：编排、工具、评测或线上质量，选你真做过的。

### 3. 在过往的 AI 或 Agent 项目中，你遇到最大的困难（不限于技术）是什么？如何克服的？你从中学到了什么？

**答题思路**

选一件真发生过、能看出判断力的事。优先选「正确性和上线速度冲突」，或「产品、算法对什么叫答对了标准不一致」。不抱怨具体的人。

1. 当时要交付什么，难在标准不统一或风险看不清。
2. 你做了什么：把不能说错的案例写成样本，缩小首发范围，高风险改走人工，并让相关角色一起看同一批例子。
3. 结果用现象说明，例如可以发布、同类坏例减少。没有统计就不编百分比。
4. 学到的一点：高风险系统先写禁止项和验收样本，再写功能。这个做法放到健康场景同样适用。

### 4. 你如何看待 AI 技术，特别是 Agent，在医疗健康行业未来的发展和可能带来的挑战？

**答题思路**

先肯定能落地的价值，再把挑战说具体，最后表明你的工作方式。

1. 价值在重复、可核对的事情：导诊引导、用药提醒、报告里的名词解释、挂号和购药流程。医师的时间留在决策上。
2. 挑战包括幻觉和过度确信、诊断与处方的责任主体、隐私和数据出境、用户把助手当成医生，以及模型更新带来的行为漂移。
3. 你的看法：这个方向会继续发展，落地顺序应该是低风险、能追溯的任务先上。诊断和处方留在有资质的医师那里。
4. 收到岗位上：你关心的是这些边界能不能被规则、工具和发布门禁执行，而不只是写在产品说明里。

### 5. 你未来的职业发展规划是什么？希望在这个岗位上获得哪些成长？

**答题思路**

规划跟这个岗位对齐，不报职级和薪资，也不把目标说成离开技术去做纯管理。

1. 近一到两年：把一条健康 Agent 链路的效果、安全和成本守住，能独立定位线上问题并完成可回滚的迭代。
2. 再往后：能负责编排、评测和发布标准，让团队改提示词或模型时知道有没有变好。
3. 希望获得的成长：医疗场景里什么不能交给模型、大规模线上治理，以及和产品、算法、医学角色一起定义质量。
4. 说明你仍然会写核心链路，管理范围变大是因为你要为质量和边界负责。

### 6. 你一般如何与产品经理、算法工程师等其他角色协作？有意见分歧时通常怎么处理？

**答题思路**

先讲日常分工，再讲一次分歧怎么收场。用你自己的例子替换，不要编一个没发生过的冲突。

1. 产品定场景、边界和验收，算法定检索与模型质量，工程定状态、工具、权限和审计。你主动把轨迹和坏例分享给两边，避免只在评审会上看演示。
2. 分歧出现时，先写成一个可验证的问题，例如「这类回答能不能直接给用户」。用同一批样本讨论，不用角色压人。
3. 医疗内容上取更保守的方案，同时说明代价，例如转人工会增加等待。能小流量验证的，先验证再推广。
4. 仍不一致时，把选项、风险和你的建议交给有否决权的人，并执行决定。事后把结果写回样本，避免下次重复争同一句话。

### 7. 你对工作环境和团队氛围有什么样的期待？

**答题思路**

期待说三件和工作质量有关的事，不把福利清单放在前面。

1. 坏例可以拿出来复盘，改错和问问题不会被当成不懂。
2. 质量和演示分开。发布看安全样本和任务有没有完成，不看一场演示顺不顺。
3. 职责清楚，工程、算法、产品和医学反馈有固定的协作方式。讨论可以激烈，但决定和记录要留下。
4. 补一句你的工作方式：你习惯把取舍讲清楚，也能接受开放设计题里的来回讨论。

### 8. 你还有什么问题想问我的吗？

**答题思路**

准备两个问题，都用来判断岗位真实在做什么。薪酬和加班等对方先谈到条件时再问；期望薪资给范围，不编一个精确数字。

1. 这个岗位半年内最要交付的场景是什么？现在主要卡在医疗标准、业务工具，还是模型效果？
2. 线上回答的安全责任怎么划分？发布前谁有否决权，医学或业务角色如何参加？

如果还有时间，再问团队里工程、算法和医学怎么协作，以及这个 Agent 已经在线上，还是仍在从 0 到 1。对方回答后用一句复述确认，不再连续追问待遇。
