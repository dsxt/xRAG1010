### 3. Java 中线程池的核心参数有哪些？分别解释其作用

**参考答案**

结论：`ThreadPoolExecutor` 里决定任务去向的是核心线程数、最大线程数、空闲存活时间、工作队列和拒绝策略。时间单位跟着存活时间，线程工厂负责创建线程。

运行中的线程还少于核心线程数时，即使已有线程空闲，也会新建核心线程执行。达到核心线程数之后，任务先进入工作队列。队列再放不下，并且线程数还没到最大，才创建非核心线程。线程数已经到最大且队列已满，才走拒绝策略。

四种常见策略：`AbortPolicy` 是默认实现，抛出 `RejectedExecutionException`；`CallerRunsPolicy` 由提交任务的线程自己执行；`DiscardPolicy` 直接丢掉；`DiscardOldestPolicy` 丢掉队列里最老的任务后再尝试提交。非核心线程空闲超过 `keepAliveTime` 会回收。`allowCoreThreadTimeOut` 打开后，核心线程同样按这个时间回收。

`Executors.newFixedThreadPool` 使用无界队列，队列不会满，最大线程数不会参与扩容，任务堆积时先把内存撑上去。`newCachedThreadPool` 的核心线程数是 0，队列是不保存任务的 `SynchronousQueue`，最大线程数是 `Integer.MAX_VALUE`，来一个任务就可能新建线程，线程过多同样会把内存打满。

容易漏的是顺序：先入队，队列满了再扩到最大线程数。`submit` 的异常在 `Future` 里，不取结果就看不见；`execute` 的未捕获异常会让该工作线程退出，并交给未捕获异常处理器。任务内部要自己记录失败。

### 4. Python 的 GIL 全局解释器锁是什么？它对多线程编程有什么影响

**参考答案**

结论：CPython 的 GIL 是解释器上的一把互斥锁，同一时刻只有一个线程执行 Python 字节码。它保护引用计数这套内存管理。共享数据的业务不变量，仍然要自己加锁。

CPU 密集的纯 Python 多线程不会因此用满多个核，线程按时间片轮流持有这把锁，间隔可以用 `sys.getswitchinterval` 查看和修改。阻塞 I/O、`time.sleep`，以及主动释放 GIL 的 C 扩展，在等待期间允许别的线程运行，所以 I/O 密集的多线程仍然有收益。`x += 1` 是多条字节码，锁可以在中间切换，它不是原子操作。

CPU 上要并行，用多进程，每个进程有自己的解释器，代价是进程间通信和序列化。大量并发连接用异步 I/O，它提高的是单线程上的等待重叠，不是字节码的并行。3.13 起另有去掉 GIL 的自由线程构建，需要单独安装；默认解释器仍然带 GIL。没声明支持自由线程的 C 扩展，导入时还可能把 GIL 重新打开。

容易漏的是把 GIL 理解成「有了它，多线程就不用加锁」。字节码被串行化了，你自己的复合操作仍然会交错。

### 5. 什么是 RAG？相比纯生成模型，RAG 有哪些优势

**参考答案**

结论：RAG 先检索外部资料，再让模型基于检索结果生成。知识和参数分开，更新资料不必重新训练。

相对只靠参数生成，文档可以单独更新，回答能指回片段，私有和长尾事实不必写进权重。权限可以在检索时过滤。较小的模型也能回答刚入库的内容。纯生成在改写、格式转换、不依赖外部事实的推理上更直接，不必为每句话查一次库。

检索为空、检索错了，或材料互相矛盾时，模型仍会编造。多出来的检索和重排会增加延迟，索引也要跟着文档更新和删除。生成阶段如果允许脱离上下文自由发挥，检索结果就只是一段参考，约束并没有落上。

容易漏的是把「接了向量库」说成已经消除幻觉。要补充的是：没证据时允许回答不知道，关键句要能回到片段。

### 6. 请描述 RAG 的完整工作流程，从文档处理到生成答案

**参考答案**

结论：离线把文档变成带权限和版本的索引，在线先查再生成，答案要能回到片段。

离线先解析，去掉页眉页脚，保留标题、表格和来源。按文档结构分块，块上带文档 id、章节、权限和更新时间。同一套嵌入模型做向量，专有名词再做关键词索引。写入的幂等键用文档、分块和模型版本，源端删除要同步到索引。

在线先补全指代，一问里有多件事就拆开。租户和权限在打分前过滤。向量和关键词各自召回，融合后只对一小段候选重排。把父块或完整条款连同引用 id 放进提示，要求依据这些内容回答；证据不够就说明不知道。金额和状态这一类，能用工具查到的以工具原文为准。

容易漏的是只讲用户提问之后的检索。旧版本留在索引里，回答会一直引用过期条款。

### 7. 文本分块有哪些常见策略？如何根据业务场景选择分块大小和重叠窗口

**参考答案**

结论：按「这一块单独拿出来还能不能答对」来切。长度和重叠用带正确片段的查询集调节，没有跨业务通用的数字。

固定长度最好实现，也最容易从句子中间切开。递归分隔会尽量在段落、句子边界断开。制度、手册和代码按条款、标题或函数切。语义分块看相邻句子的嵌入在哪里突然变远，嵌入成本更高。小块负责检索，父块或整条条款送给模型，避免片段太碎又丢了主语。

问答对通常一问一块。制度带上标题路径。表格不从一行中间截断；超大表按表头加若干行一组，每组重复表头。重叠用来保住卡在边界上的那句话，加在句子边界，宽度明显小于块本身。块太大，无关句子会稀释相似度并挤占上下文；块太小，代词和条件从句会掉在另一块。

容易漏的是全库共用一个长度，或者只加大重叠、不改切开的位置。事实被切成两半时，两块都会缺条件。

### 8. 主流向量数据库如 Faiss、Pinecone、Milvus 各有什么特点？如何选型

**参考答案**

结论：Faiss 是进程内的相似检索库，Pinecone 和 Milvus 才是向量数据库。按数据能不能出域、规模、过滤复杂度和谁来运维来选。

Faiss 提供精确检索，以及 IVF、乘积量化和 HNSW 这类近似索引，可以跑在 CPU 或 GPU 上。它适合嵌进自己的进程或离线实验。索引可以落成文件，副本、权限、服务发现和完整的标量过滤要应用自己做。

Pinecone 把命名空间、元数据过滤和扩容交给托管服务，适合不想自建的团队。数据在服务商一侧，有不出域要求时，先确认部署方式是否满足。

Milvus 可以自建，也有商业云。集合、分区、副本和标量过滤是数据库能力。规模上去之后要运维查询节点、数据节点、元数据和对象存储。小规模可以用单机或嵌入式模式。

一个索引里只用一套嵌入模型和同一种距离，模型一换就换集合。过滤很严时，把过滤下推到检索里。先取出 topK 再在应用层滤掉无权文档，名额会被占满。

容易漏的是脱离数据量、召回率和过滤比例，给三者排一个固定的速度名次。

### 9. AI Agent 的三层记忆系统指的是哪三层？每层分别解决什么问题

**参考答案**

结论：按数据能活多久分成三层。短期记忆管这一次会话，工作记忆管当前任务的中间状态，长期记忆管跨会话仍然有效的事实。

短期记忆是还要接着引用的对话：最近若干轮原文、滚动摘要、已经确认的槽位。它解决「那个」「继续」这种指代。放在上下文里，并用会话 id 落到带过期的存储里，请求落到另一台机器时还能读到。超长就摘要，槽位单独保存，不要只留在摘要句子里。

工作记忆是这一轮的计划、工具参数和工具返回。它解决多步任务做到一半把中间结果弄丢。放在编排状态里，和展示给用户的回复分开，避免模型把工具 JSON 复述出来。长任务随检查点保存，任务结束可以丢。

长期记忆是偏好、稳定事实，以及需要时再召回的经历。能覆盖更新的放数据库，要按语义找的放向量索引，键里带用户。订单和余额会变，用的时候查业务系统，不写进长期记忆。

容易漏的是三层塞进同一段提示，也不写失效时间。过期偏好会一直被当成当前事实。

### 10. 大模型幻觉有哪些常见类型？请举例说明

**参考答案**

结论：先看它和哪一份原文冲突。和用户输入冲突、和给定材料冲突、和既定事实冲突，是三类；Agent 里还要加上编造没有发生的动作。

和用户输入冲突：用户要查 A 订单的物流，回答按 B 订单解释。摘要漏掉用户强调的限制，也属于这一类。

和给定材料冲突：制度片段没写报销上限，回答写成「上限是 5000」；或者片段写的是未开通，回答说已经开通。检索增强里最常遇到的是这一种。和来源相反，是内在幻觉；材料里没有却添上去，是外在幻觉。

和既定事实冲突：编造不存在的论文、接口参数、法条编号或链接。参数知识过期时，也会把旧版本的行为说成当前版本。

动作幻觉是：工具没被调用，回答却说已经提交成功；工具返回失败，回答改写成成功。

容易漏的是只准备「世界知识背错了」这一种。材料内添油加醋同样过不了验收，而且换一个更大的模型也消不掉。

### 11. 在工程层面，可以采取哪些措施来缓解大模型幻觉

**参考答案**

结论：把「没有证据就不要说死」做成检索、生成和校验三道闸门，提示词里的禁止编造只是其中一句。

进上下文之前过滤权限和时效，相关性不够就少放片段。提示词要求关键句对应片段 id，并允许回答不知道。金额、状态、是否成功以工具原文为准。事实类降低温度，减少同义改写；该用枚举和结构的字段不用自由文本。生成后核对引用是否存在、句子是否被对应片段支持，不支持就删掉或改成不确定。写操作、花钱和对外发送在执行前等人确认。

留一组应拒绝和应引用的题。提示词或索引一变就跑一遍，看不忠实的比例，而不是只看回答通不通顺。

容易漏的是把温度调到 0 当成已经解决。温度降低的是随机性。检索错了，低温度会把错误内容说得更确定。

### 12. 如果让你设计一个支持多源知识库的 RAG 系统，你会考虑哪些核心组件和架构设计

**参考答案**

结论：多源的关键是权限、更新时间和权威来源在检索前就分开，生成时还能回到原来那份文档。

每种来源一个连接器，负责增量拉取和删除同步。文档 id 全局唯一，并带上源、租户、权限、更新时间和版本。解析和分块按源的结构来，条款、表格和工单评论不用同一个长度。向量索引用同一套嵌入模型，专有名词再配关键词索引。换了嵌入模型就换集合。

查询先决定查哪些源。权限过滤下推到两路检索。融合、重排之后，上下文保留片段 id 和来源。同一事实冲突时，展示权威源和更新时间，并列差异，不捏成一句确定的话。

写入按文档版本幂等，删除必须到达索引。缓存键带上权限范围和索引版本。评测查询按源标注正确片段，看引用对不对。

容易漏的是在应用层才滤权限。前面的名额会被无权文档占满，该看的片段进不了重排。

### 13. 手写算法：给定一个字符串，请你找出其中不含有重复字符的最长子串的长度

**参考答案**

结论：滑动窗口。右端点一路向右，左端点只在重复字符落在窗口内时，跳到它上次出现位置的下一位。时间 O(n)，空间是字符集大小。

窗口是 `[left, right]`。每个字符只记录最近一次下标。当前字符的上次出现位置大于等于 `left`，说明它还在窗口里，把 `left` 设为那个下标加一。上次出现在窗口左边时，左端点保持不动。然后更新下标，并用 `right - left + 1` 刷新答案。

`abba` 走到最后一个 `a` 时，它的上一次下标已经在窗口外。左端点若被无条件拨回去，窗口会重新包进中间的重复字符。

```python
def length_of_longest_substring(s: str) -> int:
    last = {}
    left = 0
    best = 0
    for right, ch in enumerate(s):
        prev = last.get(ch, -1)
        if prev >= left:
            left = prev + 1
        last[ch] = right
        best = max(best, right - left + 1)
    return best
```

空串得到 0。用集合、左端点每次走一步也能做，均摊同样是 O(n)。下标表把左端点一次跳到位。

### 15. 你最近在学习哪些 AI 相关的新技术？通常通过什么途径来学习和掌握新技术

**答题思路**

只讲一项你最近真的用过或读过、追问得住的东西。渠道按你的真实顺序说。

1. 它解决的具体问题：上下文太长、工具调用不稳、检索引用对不上，或评测对不了齐。先说现有做法哪里不够。
2. 你怎么学的：先做一个接到自己系统上的最小闭环，记下第一个跑不通的点；再看官方文档、发行说明或论文里对应的那几节。博客用来找入口，结论回到原文核对。

4. 和当前工作的关系：现在能接到哪一层；还缺数据、评测或权限时，就说缺的是哪一个条件。

只看过标题的模型、框架和论文不要放进名单。面试官会追问实验设置和你不同意的点。

### 2. 请深入介绍你负责的 Agent 项目，包括架构设计、技术选型和核心难点

**答题思路**

用你自己的项目填这三块。没做的组件直接说没做，不要把框架的默认能力讲成设计。

1. 架构按一次请求讲：入口和身份、编排、模型、记忆、检索、工具运行时、校验和轨迹。说明同步走到哪里，哪一段是异步。写操作停在确认之前还是可以直接执行。

4. 收在责任边界：你写的代码、你看的评测、出了问题谁能回滚。

### 3. 一个典型的 Agent 架构包含哪些核心组件？请说明各组件的作用和交互流程

**参考答案**

结论：模型负责选择下一步。记忆、工具执行、权限和停止条件都在运行时，不在权重里。

接入层保存会话、身份和原始输入。记忆模块读取这次会话的状态，以及这条请求允许使用的长期记忆。策略模型在系统提示、工具 schema 和当前状态下，产出工具调用或最终回答。工具运行时校验参数、做鉴权、超时和幂等，执行后把观察写回状态；只读和有副作用分开。控制循环限制步数、token 和重复调用，需要人确认时暂停。输出校验核对格式和引用，轨迹留下模型提议和工具原文。

流程是：加载状态，模型做一次决策。若是工具调用，运行时执行并把结果追加为观察，再进入下一次决策。直到给出回答、超出预算，或转人工。然后写回检查点，并按写入策略更新长期记忆。

容易漏的是让模型自己叙述「工具已经成功」。观察只能由运行时写入，失败和超时要原样进入下一步。

### 4. 在多 Agent 协同系统中，可能遇到哪些挑战？如何解决 Agent 之间的冲突或循环依赖

**参考答案**

结论：协作收成有界的调用图。每份共享状态只有一个写入者，每次委托带深度上限。

常见问题是目标不一致，两个 Agent 改同一份状态；A 委托 B、B 又委托 A，或者互相等对方的结果；把全部历史转发给所有角色，上下文和费用一起涨；下游失败被上游当成事实继续推理。

调用关系用主管，或事先声明的有向图，未声明的回头边不执行。其他人只提交提案，由写入者落地。委托带上任务 id 和剩余深度，同一对任务和角色不重复进入。角色之间传递约定好的结构，不传递整段聊天。有副作用的工具带幂等键；超时后把结果记为未知，由原任务决定重试还是停止。规则能够裁决的冲突由主管选一个结果，规则盖不住就停下来问人。

容易漏的是只比较相邻两句话像不像。要限制的是调用图的深度和重复边。自由对话式的多 Agent 还会把责任散掉，最终回答要有一个角色对引用和工具结果负责。

### 5. LangGraph 相比 LangChain 的传统链在状态管理和记忆方面有哪些优势

**参考答案**

结论：优势在于状态是显式的、每一步可持久，并且允许有界的循环。记忆质量不会因为换成图就自动变好。

传统链把步骤排成一条调用，LCEL 管道也是这样。状态是这次调用的输入和返回值。历史通常在链外拼进提示词，一次运行的中途停掉，已经走到哪一步没有对应的检查点。条件分支可以表达，循环不是这种链的基本能力；旧的 Agent 执行器虽然会循环，暂停下来等人、再从同一步恢复，要另外补。

LangGraph 里每个节点返回自己负责的那一部分状态，用合并函数合到一起，消息列表按追加合并，后一个节点不会覆盖整段历史。条件边可以走回前面的节点，工具循环就是这种环。检查点按会话在每一轮节点调度之后保存，进程重启、人工打断、从某一步重放，都读这份状态。会话里的短期记忆和工作记忆放在检查点里。跨会话的长期记忆用另一套按用户划分的存储：删掉某个会话的检查点，不会把用户事实一起删掉；这些事实要靠检索或明确读取才会进入下一次提示。

容易漏的是把检查点当成长期记忆。检查点跟着会话走；记什么、摘要怎么写、哪条事实会过期，仍然是应用自己的策略。

### 6. 在 Agent 开发中，如何对底层大模型进行调优？微调、Prompt 工程和 RAG 如何结合使用

**参考答案**

结论：先用评测分清缺口在知识、格式还是检索，再决定改提示词、改索引还是改权重。三者补的不是同一类问题。

准备一组带标准依据的题。失败若是没检索到，或检索到了却没用上，就改分块、过滤、召回和提示里的引用要求。上下文已经正确，格式或工具参数仍不稳，再收紧输出约束；仍然不稳，并且有足够的正确轨迹，再做小规模监督微调。常见做法是 LoRA 这一类参数高效微调。全量微调成本高，事实一变，权重里的说法就过期。温度和最大长度只影响这一次采样。

提示词放角色、步骤、输出格式、何时调用工具、何时拒绝，改动可以当天生效，也装不下会变化的长尾事实。RAG 放必须引用、会更新的内容，索引更新不必动权重。微调只承接稳定的格式、领域说法和工具调用习惯，上线后仍然走 RAG。检索错了，微调不会把错误片段救回来。

容易漏的是用微调去背规章和价格。库更新之后，权重还是旧的，而且比一条写错的提示更难发现。

### 7. 除了多路召回和重排序，还有哪些高级技术可以提升 RAG 的召回率和答案准确性

**参考答案**

结论：多路召回和重排解决的是候选里谁更靠前。召回率和答对与否，还取决于问法、切块、该不该查，以及答案有没有被证据支持。

问法上，先把指代补全；一句话里有多件事就拆成子问题再查。问法和正文差得很远时，可以用假设性答案去贴近文档的写法，这会多一次生成，假设本身跑偏时，召回会跟着偏。切块上，用小块检索，把父块或章节送给模型；写入前给块补上标题路径，片段离开章节也知道在说谁。路由上，闲聊和上下文里已经有的问题不必查库，该查哪个源由问题类型决定。

关系稳定、需要多跳的事实，用图补向量找不到的那一跳，边上的结论要能回到文档。生成后丢掉没有引用的句子；证据互相矛盾时并列来源。模型也可以先判断要不要检索，片段不相关就改写查询再查一次。

这些步骤都放在同一套标注查询上看召回和忠实度。只增加环节，延迟会上去，答案不会自动更对。

### 8. 请系统性地阐述你会从哪些层面构建一个完整的幻觉抑制方案

**参考答案**

结论：按数据、检索、生成、校验和评测分层设闸门，并允许系统回答不知道。任何一层都不能单独消除幻觉。

数据层给每份文档来源、权威级别和更新时间，过期和重复内容不进索引。检索层把权限和时效过滤放在打分之前；证据不够就减少片段，甚至不生成肯定句。生成层要求关键论断对应片段 id，数字和状态以工具返回为准，事实类使用低温度。校验层在生成后检查引用是否存在、论断是否被片段支持，不支持就删除或改成不确定。写操作、付款和对外发送由人确认，不靠模型自检通过。

评测层固定一组应拒绝和应引用的题，索引或提示一变就回归，线上再抽检不忠实的比例。用另一个模型当裁判时，把原文一起给它。只看回答通不通顺，裁判会把流畅当成正确。

容易漏的是闸门都做在提示词里。检索为空时，模型仍然会用参数知识把空缺补上。空证据要在进模型之前就走拒绝或追问。

### 9. 当 Agent 系统响应延迟明显升高时，你的排查思路和优化手段有哪些

**参考答案**

结论：先把变慢定位到某一段耗时，再决定动模型、检索、工具还是循环步数。没有分段时间，就先补轨迹。

划定范围：哪个接口、从什么时候开始、看的是尾部延迟还是平均、是不是某个租户或某个工具。轨迹至少分开排队、嵌入、检索、重排、首 token、生成、每一次工具调用和步数，并和变慢前的基线比较。

常见原因对得上这些段：历史没有裁剪，提示变长；反思停不下来，步数变多；有依赖关系的工具被串成一长串，下游超时后再重试；检索参数被调大；请求被路由到更慢的模型；线程池或连接池打满，时间花在排队。用户看到的时间包含队列时，服务自己的处理时间可能仍然正常。

优化对着那一段：限制步数和上下文，独立的只读工具并行，热查询的嵌入和检索结果按索引版本缓存，路由用小模型，拿不准的请求再用大模型。重试要有次数上限和抖动。先保住可观察，再改提示词。

### 10. 设计一个支持长期记忆、工具调用和人类反馈的 Agent 系统，需要考虑哪些关键模块和数据处理流程

**参考答案**

结论：三条能力走三条数据路径。长期记忆按用户持久化，工具调用走带权限的运行时，人类反馈分成执行前批准和执行后纠正。纠正先落成可追溯的记录。

编排图的每一步都能暂停和恢复。会话状态放短期存储。长期记忆只收明确的偏好和已确认的事实，带用户、来源和时间；用户可以删除。订单和额度仍查业务系统，用户不能把权限写进记忆。工具注册表包含 schema、鉴权、超时、幂等键，以及是否有副作用。只读可以自动执行。写操作、花钱和对外发送进入人工节点。

人的批准或拒绝写回状态。拒绝时记下原因，再换路径或停止。事后的点赞和改正进入评测集；如果要改记忆，覆盖的是某一条，并保留旧值。人和工具结果冲突时，以工具和业务系统为准。一次反馈不直接改模型权重。

流程是：加载会话和相关长期记忆，模型给出下一步；只读工具立即执行，写操作暂停等人；观察进入工作记忆；本轮结束再按策略抽取长期记忆。模型提议、工具原文和人的决定都留在轨迹里。

容易漏的是人还没确认，副作用已经发出去。暂停点要在工具执行之前。

### 11. 手写算法：给定一个包含非负整数的 m x n 网格，请找出一条从左上角到右下角的路径，使得路径上的数字总和为最小

**参考答案**

结论：按每次只能向右或向下走一格来做，起点和终点都算进总和。用动态规划。时间 O(mn)，下面的二维表额外空间 O(mn)，可以压成 O(n)。

到达 `(i, j)` 只能来自上边或左边，所以该格的最小路径和等于本格的值，加上上边、左边两个最小和中较小的一个。第一行只能从左边来，第一列只能从上边来。非负在这个走法里不是必须条件；只能向右或向下，才保证没有环，递推不会用到还没算完的格子。

例如 `[[1,3,1],[1,5,1],[4,2,1]]`，最小和是 7，一条路径是 `1 → 3 → 1 → 1 → 1`。

```python
def min_path_sum(grid: list[list[int]]) -> int:
    m, n = len(grid), len(grid[0])
    dp = [[0] * n for _ in range(m)]
    dp[0][0] = grid[0][0]
    for j in range(1, n):
        dp[0][j] = dp[0][j - 1] + grid[0][j]
    for i in range(1, m):
        dp[i][0] = dp[i - 1][0] + grid[i][0]
    for i in range(1, m):
        for j in range(1, n):
            dp[i][j] = grid[i][j] + min(dp[i - 1][j], dp[i][j - 1])
    return dp[m - 1][n - 1]
```

若还允许向上或向左，非负边权改用 Dijkstra，并且不要重复进入同一个格子。那是另一道题。一行滚动数组从左向右更新时，`dp[j]` 仍是上一行的值，`dp[j - 1]` 已经是这一行左边的值。

### 12. 在 Agent 系统中，如何使用 Redis 缓存频繁访问的提示模板或中间结果？需要注意哪些问题

**参考答案**

结论：模板按版本缓存。中间结果只缓存纯读、可以重建的那一部分。键里带上版本、模型和权限，避免把一个用户的结果发给另一个用户。

模板正文用名称加版本做键，发布新版本就换键。线上提示写错时，等原来的键过期才替换，这段时间还会继续用错模板。已经填入用户内容的提示，和模板正文分开；要缓存就落到该用户，并设置较短的过期时间。

适合缓存的中间结果包括查询向量、同一索引版本下的检索结果、幂等只读工具的返回。键包含模型名、模板版本、索引版本、规范化后的查询，以及租户和权限范围。个性化生成不要放进共享键。有副作用的工具结果不能当成缓存重放。

值要有大小上限，超长上下文不要整段放进去。热点键失效时用单次回源，避免同时打到模型和数据库。含有用户原文的键要过期，并按租户隔离。序列化用明确的文本或二进制格式，避免语言自带的不安全反序列化。

容易漏的是检索缓存不带权限。前一个用户的命中会被下一个用户读到。

### 13. 如果使用 Kafka 来处理多个 Agent 之间的异步消息，如何保证消息的顺序性和可靠性

**参考答案**

结论：顺序只在同一个分区内成立。可靠投递按至少一次设计，业务侧用幂等挡住重复。多个 Agent 调用外部工具时，不能假设每条消息只被处理一次。

同一个会话或工作流的事件使用同一个键，使它们进入同一分区。该分区由一个消费者按顺序处理，处理成功后再提交位移。消费者内部再并发执行这个分区的消息，分区内的顺序就散了，除非按键串行。不同工作流使用不同的键，才能并行。增加吞吐靠分区数和消费者数量，不是靠全局有序。

多个 Agent 若在同一个消费组里，一条消息只会被组内一个成员处理，这是分活，不是广播。若每个 Agent 一个消费组，各组都看得到消息，组与组之间没有共同顺序。有先后关系时，让上游成功之后再产生下一条，由下游消费下一条，而不是两个组同时读同一条流再靠到达时间配合。

生产者开启幂等，确认数使用 all。幂等要求同一连接上未完成的请求不超过 5，超出时客户端会拒绝启动。应答时除了 leader 还要有跟随副本，常见做法是 `min.insync.replicas` 至少为 2，副本数比它再多，这样坏掉一台机器仍能写入。不要允许 ISR 之外的副本当选 leader，否则已经确认的消息可能在换主时被截掉。消费者关闭自动提交；失败按上限重试，之后进入死信，并告警。写到外部工具时用事件 id 挡住重复。事务能包住的是消费后再写回 Kafka 这一段，HTTP 工具不在这个事务里。

容易漏两件事：把分区内有序说成所有 Agent 看到的全局顺序；处理成功前就提交位移，失败后这条消息不会再来。

### 14. 作为项目负责人，你如何评估技术风险并保证 Agent 项目的进度和质量

**答题思路**

讲你真正常用的拆法和门槛。例子用自己的项目，不编进度百分比。

1. 先把不确定的点列出来：效果达不达标、工具副作用、依赖的模型和外部接口、权限和数据。每一项写清影响、用什么验证、最晚哪天必须有结论。
2. 排期按用户能走通的垂直切片，每一片包含失败处理和验收。效果不确定的部分放进时间盒，到期就换方案或缩小范围。
3. 质量门槛和「做完」绑在一起：工具契约、检索回归、轨迹抽检、可以回滚。门槛没过，这一片不算完成。
4. 向上同步用证据：评测差在哪、卡在哪个依赖。用「还在优化」代替结论，风险会拖到上线前。
5. 延期时先砍并行场景，保住主路径、评测和回滚。主路径的验收标准不跟着范围一起降。

收尾补一个你做过的取舍：当时砍了什么，上线后看哪个现象确认这个判断。

### 15. 你如何持续跟踪 AI 领域的最新进展？通常会关注哪些会议、论文或开源项目

**答题思路**

讲你的过滤方法，再举一两项你真的跟过的工作。名单要经得起「你不同意它哪一点」的追问。

1. 固定一个和当前系统有关的问题，例如引用对不上、工具超时后状态不明、上下文太长。只收集能碰到这个问题的材料。
2. 来源按你的真实习惯说。会议可以是你真的看过论文的那些，例如 ICLR、NeurIPS、ACL 里和检索或工具使用有关的一篇。工程侧看你在用的框架的发行说明和迁移文档。开源就提你读过代码或改过配置的仓库。
