### 3. JVM 内存结构是怎样的？哪些区域是线程私有的，哪些是共享的？

**参考答案**

线程私有的是程序计数器、虚拟机栈和本地方法栈。堆和方法区由线程共享。

程序计数器保存下一条字节码地址，执行本地方法时为空，这块不会溢出。虚拟机栈按方法存放栈帧，里面是局部变量表、操作数栈、动态链接和返回地址。栈太深抛 `StackOverflowError`，线程栈扩不开抛 OOM。本地方法栈给 native 方法用。规范里它和虚拟机栈分开，HotSpot 通常把它们放在同一块由 `-Xss` 控制的线程栈里。

堆存放对象和数组，是垃圾回收的主区域，装不下会抛出堆空间 OOM。规范把类元数据和运行时常量池放在方法区。HotSpot 从 JDK 8 起用元空间存放类元数据，占用本地内存，类过多会 `Metaspace` OOM。`java.lang.Class` 对象和静态字段在堆上，静态字段指向的实例也在堆上。字符串常量池从 JDK 7 起位于堆中。

直接内存不属于上述分区，NIO 的堆外缓冲由各线程共享，泄漏时进程一样会耗尽内存。TLAB 只是堆内部按线程划分的分配缓冲区。逃逸分析可能把未逃逸的对象拆到栈上，那是编译优化，不是另一块规范中的区域。

### 4. 谈谈 CMS 收集器和 G1 收集器的区别，以及各自的应用场景

**参考答案**

CMS 只回收老年代，算法是标记-清除，追求短停顿，但会留下碎片。G1 把整个堆分成 Region 来收集，用复制换可预期的停顿。JDK 9 起默认收集器是 G1。

CMS 通常和 ParNew 搭配。初始标记、重新标记需要停顿，并发标记和并发清除与业务并行。它不整理存活对象，碎片多了会导致晋升失败。并发周期还没结束、老年代已经满时，会退化为单线程的整堆收集，停顿很长。重新标记还要处理并发期间改过的引用，停顿不稳定。CMS 在 JDK 9 废弃，JDK 14 移除，只适合还停在旧 JDK、暂时不能更换收集器的服务。

G1 的年轻代和老年代都是一组 Region，超过 Region 一半的对象进入 Humongous 区。它优先收集垃圾比例高的 Region，被收走的区域得到整理。停顿目标的常见默认值是 200 毫秒，这是期望，回收仍可能超过它。正常路径是年轻代回收和带一部分老年代的混合回收。跨 Region 引用靠记忆集维护，记忆集会占用额外内存。分配持续快过回收时会整堆收集，那不是 G1 的正常路径。

新服务用 G1。停顿要求更低、堆特别大时，再单独评估 ZGC。两个收集器都有并发标记，也都有停顿。

### 5. Java 中 synchronized 和 ReentrantLock 的实现原理与区别是什么？

**参考答案**

`synchronized` 是 JVM 内置监视器，`ReentrantLock` 是基于 AQS 的库实现。两者都可重入。低竞争时性能接近，差别在公平性、超时、可中断和条件队列。

`synchronized` 的锁状态在对象头。无竞争时走轻量级锁：CAS 把 mark word 换成指向当前栈帧中锁记录的指针，同一线程重入则增加计数。竞争加剧后膨胀为 `ObjectMonitor`，等待线程被 park。偏向锁从 JDK 15 起默认关闭，后续版本不再把它当作优化路径。编译器会在正常返回和异常路径都补上退出，所以调用方不用写 `finally`。每个监视器只有一个等待集合，`wait` / `notify` 作用于这一集合。它不能试锁、不能超时，阻塞在进入锁时也不能响应中断。锁对象不逃逸时，JIT 可以消除这把锁。

`ReentrantLock` 用 AQS 的 `state`。0 表示未锁定，持有线程重入时加一，并记录拥有者。默认非公平：入队前先 CAS 抢一次，吞吐更好。公平模式会先看队列里有没有前驱。它提供 `tryLock`、带超时的获取和 `lockInterruptibly`。一个锁可以有多把 `Condition`，`signal` 只唤醒对应条件上的线程，`await` 会先释放锁。`unlock` 必须放在 `finally` 中。

选择看需不需要超时、多条件队列和可中断等待。两者在默认使用方式下都允许新来的线程插队，不能靠其中任何一个天然避免饥饿。

### 6. Spring Bean 的生命周期是怎样的？可以详细说说吗？

**参考答案**

单例 Bean 的主线是实例化、注入、初始化、使用和销毁。初始化回调有固定顺序，AOP 代理在初始化之后生成。

1. 实例化。构造器注入发生在这一步。
2. 填充属性，完成字段注入和 setter 注入。
3. 回调 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。
4. 执行 `BeanPostProcessor.postProcessBeforeInitialization`。`@PostConstruct` 由处理公共注解的后处理器在这里调用。`ApplicationContextAware` 等上下文回调也发生在这个阶段。
5. 调用 `InitializingBean.afterPropertiesSet`。
6. 调用自定义 `init-method`。
7. 执行 `postProcessAfterInitialization`。声明式事务和 AOP 代理通常在这里包上去。
8. 放入容器并对外提供。
9. 容器关闭时销毁单例：先 `@PreDestroy`，再 `DisposableBean.destroy`，最后自定义销毁方法。原型 Bean 的销毁不由容器负责。

因此 `@PostConstruct` 早于 `afterPropertiesSet`，再早于 `init-method`。`BeanFactoryPostProcessor` 改的是 Bean 定义，发生在实例化之前；`BeanPostProcessor` 改的是对象。懒加载单例不会在启动时走完这条链。循环依赖提前暴露的是尚未初始化完成的对象，协作者若在自己的初始化期间调用它，`@PostConstruct` 可能还没执行。

### 7. Spring 如何处理循环依赖问题？三级缓存具体是如何工作的？

**参考答案**

三级缓存解决的是单例、并且通过属性注入形成的循环。构造器循环和原型循环不走这套缓存。Spring Boot 从 2.6 起默认禁止循环依赖，需要显式打开才会用到它。

一级 `singletonObjects` 存放初始化完成的单例。二级 `earlySingletonObjects` 存放已经生成的早期引用。三级 `singletonFactories` 存放工厂，只有真正需要早期引用时才调用。

A 依赖 B、B 又依赖 A 时，A 先构造完成，把工厂放入三级，再注入 B。创建 B 时回头获取 A：一级和二级都没有，于是调用三级工厂。工厂通过 `getEarlyBeanReference` 拿出早期引用；如果 A 需要 AOP，这里会提前生成代理，放进二级并删除三级工厂。B 完成初始化后进入一级。A 继续做完初始化。早期已经生成过代理时，初始化之后复用同一个代理，不再包第二层，然后 A 进入一级。

三级存放工厂，是为了没有循环时仍在初始化之后才生成代理。如果一构造完就把原始对象放进二级，B 拿到的是原始对象，容器里后来发布的是代理，两者不是同一个实例。二级用来记住这次提前生成的引用，保证工厂只调用一次。

构造器循环在对象还不存在时就要对方，提前暴露帮不上。可以改成属性注入，或在一侧使用 `@Lazy`，先注入一个延迟解析的代理。

### 8. 在使用 Redis 作为缓存时，如何保证缓存与数据库的数据一致性？有哪些方案？

**参考答案**

默认用旁路缓存：数据库提交成功后再删除缓存。Redis 和 MySQL 不在同一个本地事务里，目标是失败后能够恢复的最终一致。

读请求先查缓存，未命中再查库并回填。写请求先提交数据库，再删除缓存。删除比修改缓存合适，因为两次写并发时，后写入缓存的可能是较早的值，而删除是幂等的。先删缓存再更新库时，中间的读会把旧行重新放回缓存。

还有一个较窄的窗口：读请求已经取出旧行，更新提交并删掉缓存之后，这个读才回填，缓存又变回旧值。短 TTL、删除失败后的重试，以及按 key 把回填和更新串行起来，都能把窗口收住。延迟双删是隔一小段时间再删一次，延迟要盖住那次回填，这个时间并不稳定，只能作补充。

删除请求本身失败时，没有 TTL 的缓存会一直脏。可以用消息重试，或订阅 binlog 后再删，TTL 做最后的兜底。存在主从延迟时，删缓存之后的读可能从从库读到旧行并回填，写之后的短时间内应读主库。

写穿是应用只写缓存、由缓存组件同步写库，Redis 本身不提供这层能力。写回是先写缓存再异步落库，吞吐高，最近的写可能丢失。要求读到自己刚写的值时，这次读绕过缓存，或在值上带版本，旧版本不能覆盖新版本。

### 9. MySQL 的 InnoDB 存储引擎，事务的四大特性是如何通过日志和锁机制实现的？

**参考答案**

原子性靠 undo log，持久性靠 redo log 和 binlog，隔离性靠 MVCC 加锁。一致性是约束，加上这三项把库从一个有效状态带到下一个有效状态。

改数据页之前先写 undo，内容是如何撤销这次修改。事务回滚时按 undo 做反向操作。MVCC 也沿这条版本链构造旧快照，所以同一份 undo 同时服务于回滚和一致性读。

提交按 WAL 进行，先让 redo 按策略落盘。`innodb_flush_log_at_trx_commit` 为 1 时，每次提交都刷 redo，已向客户端确认的事务在进程或机器崩溃后还在。为 2 时每次写到操作系统缓存、大约每秒才 fsync，机器掉电可能丢。为 0 时大约每秒才写入日志，进程崩溃也可能丢。需要复制时还要 binlog。InnoDB 使用两阶段：redo 进入 prepare，写 binlog，再写 redo 的 commit。崩溃恢复时 binlog 已经完整就提交，否则回滚，存储引擎和从库因此看到同一批事务。`sync_binlog` 为 1 时，binlog 也在每次提交时刷盘。doublewrite 用来防止数据页写到一半，不负责事务回滚。

普通 `SELECT` 走 MVCC。RC 每条语句建立一个 Read View，RR 在事务第一次一致性读时建立并后续复用。`SELECT ... FOR UPDATE`、`UPDATE` 和 `DELETE` 这些当前读会加锁。RR 使用记录锁、间隙锁和 Next-Key Lock，挡住锁定范围内的插入。快照读不加间隙锁。

主键、唯一约束和外键在写入时检查。崩溃后用 redo 重做已提交的页，用 undo 撤掉未完成的事务，页才能回到这些约束仍然成立的状态。

### 10. 你了解 Spring AI 吗？它的主要目标是解决什么问题？

**参考答案**

Spring AI 要让 Spring 应用用统一的方式调用模型，并接上自己的数据和接口。更换模型厂商时，业务代码继续依赖这些端口，而不改写成另一家 SDK。

各家 SDK 的报文、流式格式和工具调用都不一样。Spring AI 用 starter 和自动配置把它们收成可替换的能力：对话、嵌入、图像、语音、向量库、文档切分、结构化输出和工具调用。模型名称和地址放在配置里。Advisor 把记忆、检索和日志插进调用链，不必写进每个业务接口。

它解决的是接入和替换。智能体如何规划、在哪一步暂停、失败后如何恢复，仍由应用规定。权限、超时和人工确认也留在业务代码里。

### 11. Spring AI 的核心接口，比如 ChatClient、EmbeddingClient 的设计理念是什么？

**参考答案**

`ChatClient` 是给业务用的流式门面。题目里的 `EmbeddingClient` 是早期名字，1.0 起改为 `EmbeddingModel`。按厂商实现对话协议的端口是 `ChatModel`，不是现在的 `ChatClient`。

`ChatClient` 由 Builder 创建。一次调用里可以放系统提示、用户消息、Advisor、工具和输出转换。`call().content()` 返回完整字符串，`stream().content()` 返回增量。`call` 或 `stream` 只选定模式：同步请求在 `content()` 这一步发出；流式则要等返回的 `Flux` 被订阅。自动配置提供的 Builder 是原型作用域，不同场景可以各自带默认提示和默认工具。更换模型时替换底层 `ChatModel` 和配置，这条调用链保持不动。一个应用可以有多个 `ChatClient`，也可以接入多个 `ChatModel`。

`EmbeddingModel` 的核心是 `call(EmbeddingRequest)`。`embed` 接受一条或一批文本，返回 `float` 向量。建索引和查询必须使用同一个实现，维度和归一化方式也要一致。向量库是另一个端口，嵌入模型和库可以分开替换。

这和数据访问的拆法相同：门面保持稳定，驱动可以更换。早期的 `ChatClient` 本身就是模型接口；现在它负责组织一次调用，具体协议由 `ChatModel` 实现。

### 12. 什么是 AI Agent？你如何理解它在应用开发中的角色？

**参考答案**

AI Agent 是把模型放进循环里的应用结构。模型根据目标和已有观察，决定直接回答还是调用工具；应用执行工具，把结果放回上下文，直到得出答案或达到步数上限。

它位于编排层，不替代订单、库存这类业务服务。用户意图开放、步骤事先写不完时，用它选择下一步。规则已经清楚的退款和审批，用固定流程更可测，模型只负责理解说法和解释结果。模型是策略，工具契约、权限、超时和副作用属于应用。模型碰不到数据库和支付接口，只能提出调用。

和一次问答相比，Agent 有状态，并且会根据工具结果改变下一步。路径因此不固定，必须有步数上限、工具白名单，以及会改数据的人工确认。没有这些边界，它只是一次更长的聊天。

### 13. 场景题：如果让你设计一个基于大模型的智能客服系统，你会考虑哪些模块和技术选型？

**参考答案**

业务系统做事实来源，模型负责理解意图和组织语言。查政策走检索，查订单走工具，涉及资金的动作由代码中的确认步骤放行。

接入层处理渠道、登录身份、会话和限流，用户身份以登录态为准。退款、改地址这类规则清楚的流程用状态机；开放问题再进入带工具的对话，并限制步数。政策、FAQ 切片后做向量检索，回答带出来源和版本。价格和库存调用现有接口，不写进长文档。

查订单和查物流是读工具。创建退款是写工具，要校验订单属于当前用户，并且等用户确认后才允许这次调用。模型通过统一客户端流式输出，并设置超时。模型不可用时转人工，或返回固定指引。Redis 保留最近几轮，更早的内容压成摘要。工具返回的大报文只留结论和单号。

投诉、资金操作、检索为空，或同一问题反复失败时转人工，并把已查到的订单和文档片段交给坐席。知识经常变化，所以用检索，而不是把政策训进模型。完全自由的工具循环容易被话术绕过，资金操作放在外层状态机。流式输出能提前看到首字；工具还没返回时，不能先向用户承诺已经办理。

编排放在现有 Spring 服务里，模型和向量检索可以单独扩容。向量库可以沿用已有搜索集群，也可以单独部署，关键是能按渠道和文档版本过滤。效果看解决率、转人工率和抽检到的错误类型。

### 2. 请详细介绍一下你简历中提到的那个涉及 AI 能力的项目，你遇到了哪些技术难点，又是如何解决的？

**答题思路**

按边界、一个难点、取舍和验证来讲。只讲你写过的那段，不编公司、职级、项目名和调用量。

1. 需求用一句话说明：客服、搜索还是内部助手。你写的代码和框架代劳的部分分开。
2. 只深挖一个难点，而且要有日志或坏例子：检索不准、工具被误调用、超时与重试、流式中断，或答案对不上业务数据。
3. 按怎么发现、改了哪一层、为什么不用另一个方案来讲。例如写操作从模型自由调用改成确认后再生效，原因是提示词禁止不住误下单。
4. 结果用现象说明：坏例子还能不能复现，投诉或转人工有没有变化。没有监控数字就讲你怎么抽查。
5. 准备被追问替代方案，事先想好一个你拒绝过的做法。当时没有权限校验或没有超时，就直接说，不要补成一套完整平台。

### 3. 在分布式系统中，如何设计一个高性能、高可用的服务？需要考虑哪些方面？

**参考答案**

计算层保持无状态，以便水平扩展；状态放在有副本的存储里。性能来自缩短同步链路，可用性来自超时、隔离和可以降级的路径。

服务部署多个实例，前面做健康检查，滚动发布时先摘掉流量。会话不放在进程内存里，允许丢失的状态放缓存。读多的数据走缓存，数据库提交仍是事实来源。不必留在用户请求里的工作放进消息队列。

每个下游都有超时、有限次重试和熔断。重试要加抖动，并且只覆盖幂等操作，避免故障期间把下游打满。入口做限流。不同依赖拆开线程池或并发额度，一个慢接口不应占满公共池。热点 key 单独处理。

数据库要有副本和明确的主从切换。缓存和搜索索引都应该能够重建，不能当作唯一副本。

超时太短会误熔断，太长会占住线程，应按用户能够等待的总时间向下分配。异步和副本提高吞吐，读到的数据可能稍旧。库存和资金走同步事务，通知和统计走异步。多个实例之后，同一条请求要能在日志里串起来，否则扩容只是把故障复制到更多进程。

### 4. 谈一下你对微服务治理的理解，比如服务发现、熔断降级、配置中心等

**参考答案**

治理是把「调用谁、失败怎么办、配置怎么变」从业务分支里抽出来，让故障停在依赖的边界上。

服务发现负责实例启动时注册、用心跳维持、下线时注销。调用方缓存实例列表，注册中心抖动时按缓存继续转发，并把连续失败的实例摘掉。负载均衡可以放在客户端或网关。健康检查看服务是否就绪，而不是进程是否还在。

熔断在一个时间窗口里统计错误率和慢调用，达到最小请求量才打开，避免几次失败就把链路切断。打开后快速失败，半开时放少量请求探测。降级应返回说得清的结果，或转入排队，不能返回一个会被当成成功的空值。只对幂等读做重试。超时设在调用方，并且短于用户侧的总预算。舱壁把不同依赖的并发隔开。Hystrix 已经停止维护，现役实现用 Sentinel 或 Resilience4j。

配置中心集中管理开关、超时和阈值，变更要能审计和回滚。数据源和线程池不一定能热替换，这类变更需要显式重建或重启。配置中心不可用时，用本地快照启动。密钥不要以明文进仓库。

还要有跨服务的 trace id 和入口限流。熔断打开之后，没有调用链就看不出慢在哪一跳。

### 5. Elasticsearch 的倒排索引原理是什么？它相比传统数据库的 B+ 树索引，在全文搜索上的优势在哪？

**参考答案**

倒排索引是从词指向文档列表。全文检索的优势在于按词命中，不依赖这个词出现在字段的哪个位置，并且可以直接做相关度排序。

写入时由分析器分词和归一化。索引和查询必须使用同一套分析器，否则两边的词对不上。每个词对应一份倒排表，里面是文档 id，通常还有词频；短语查询再保存词的位置。Lucene 用 FST 把词映射到倒排表，文档 id 做差量压缩，跳表用来加快多个词求交。相关度默认使用 BM25，综合考虑词频、逆文档频率和字段长度。

索引按段写入。段生成后不能就地修改，新文档进入新段，刷新之后才能被搜到，常见的刷新间隔是一秒，后台再合并段。所以它是近实时的，写入之后不能当成立刻可搜。

B+ 树按列值整体有序，适合等值、范围和排序。词出现在句子中间时，`LIKE '%词%'` 用不上普通 B+ 树。倒排对词在文本中的位置不敏感，多词与或、短语和打分都是它的正常查询。关系库里的全文索引本身也是倒排，这里的优势是相对 B+ 树而言。

代价是更新要写新段再合并，比原地修改一行重。它也不提供 InnoDB 那种事务和崩溃恢复。结构化字段的等值和范围仍交给数据库，倒排索引不替代主键查找。

### 6. Kafka 如何保证消息的顺序性和可靠性（不丢失、不重复）？

**参考答案**

顺序只保证到分区。不丢失靠副本确认和消费位移的提交时机，不重复靠生产者幂等加上消费侧的业务幂等。没有一个开关能让包含数据库副作用的整条链路恰好一次。

同一个键进入同一个分区，分区内按偏移有序。消费者组里，一个分区同时只分配给一个消费者。这个分区内若再开多线程处理，顺序就会被打乱，除非按键重新排队。未开启幂等时，重试加上多个在途请求会打乱分区内顺序，需要把在途数限制为 1。开启幂等后，生产者用分区内序列号，把协议允许的有限个在途请求排回原来的顺序。全局有序意味着主题只能有一个分区，吞吐也会跟着下降。

生产者使用 `acks=all` 时，确认的是当时的全部 ISR，不是全部副本。因此还要把 `min.insync.replicas` 设到 2，副本数的常见做法是 3。关闭不干净的领导者选举，避免落后副本成为领导者后丢掉已确认的消息。消费者在处理成功后再提交位移，这是至少一次。先提交再处理，进程崩溃会丢消息。自动提交看的是拉取位置，不是业务是否成功。

Kafka 3.0 起，生产者幂等默认开启。它能去掉同一次生产者会话中的重试重复；进程重启后换了生产者标识，就不再用旧序列号去重。至少一次的消费仍可能重复执行业务，要用业务唯一键挡住。事务配合 `read_committed`，可以让「从 Kafka 读、处理、再写回 Kafka」在日志内部恰好一次。写到数据库的副作用不在这个事务里，仍然需要发件箱或幂等键。

### 7. RocketMQ 的事务消息机制是如何实现的？它解决了什么场景下的问题？

**参考答案**

事务消息解决本地事务和发送消息要一起成功或一起失败的问题，例如订单入库的同时通知下游。它提供的是最终一致，不是数据库和 Broker 之间的 XA。

生产者先发送半消息。Broker 把它持久化，但不放进消费者能够拉取的队列。发送成功后，生产者才执行本地事务。本地事务提交，就请求 Broker 提交半消息，之后消费者可见；本地事务失败，就回滚半消息。

提交或回滚的请求可能丢失。Broker 过一段时间会回查生产者。回查必须能根据持久化的本地事务状态返回提交、回滚或未知；未知就稍后再查。状态只放在内存里时，进程重启后无法判断，消息会一直悬着，直到按策略结束。

消费者仍可能重复收到已经提交的消息，下游处理要幂等。和本地消息表相比，待发送状态放在 Broker，而不是业务库。回查这一步仍然依赖业务库里查得到事务结果。没有这份可查询的记录，事务消息的后半段就接不上。

### 8. 你了解哪些主流的 AI Agent 框架（如 LangChain、Semantic Kernel）？与直接用 Spring AI 相比，它们的设计思想有何不同？

**参考答案**

LangChain 和 Semantic Kernel 着重管理智能体的编排。Spring AI 管理的是 Spring 应用如何以可替换的方式调用模型、向量库和工具。

LangChain 以链和可组合的调用单元为中心，把模型、检索和工具串成管道，主要生态在 Python 和 JavaScript。循环、分支以及需要暂停后恢复的流程，在 LangGraph 里变成显式状态图，每一步可以做检查点。控制力强，状态和边需要自己定义。Java 里常见的是独立项目 LangChain4j，它不是 LangChain 的官方移植。

Semantic Kernel 以 Kernel 为中心登记插件，插件可以是本地函数、提示词模板或远程接口。调用顺序可以由应用代码显式编排，也可以交给规划器。过滤器放在调用前后，用来做鉴权和重试。它覆盖 .NET、Python 和 Java，和微软的模型及依赖注入贴得紧。它的重点是给已有应用增加一组可由模型选择的能力。

Spring AI 把 `ChatModel`、`EmbeddingModel`、`VectorStore` 做成端口。`ChatClient` 把一次调用的提示、Advisor 和工具收在一起。2.0 的工具循环放在 `ChatClient` 的 `ToolCallingAdvisor` 上，它不是一个带检查点的流程引擎。事务、鉴权和线程模型沿用 Spring。步骤必须持久化、崩溃后续跑，或需要多人审批时，状态图更合适。模型只是现有服务里的一项能力时，Spring AI 的端口更合适。

两边可以一起用：对话和工具协议走 Spring AI，复杂流转用自己的状态机。框架不拥有副作用，订票这类写操作的确认仍要写在业务代码里。

### 9. 数据库索引建立的原则是什么？如何判断一个 SQL 语句是否使用了索引？

**参考答案**

索引服务于已经出现的查询，而不是给每一列都建一个。以 InnoDB 来说，判断有没有用上，要看执行计划实际选择的索引。

列出现在 `WHERE`、`JOIN`、`ORDER BY` 或 `GROUP BY` 中，并且能明显减少扫描时，才值得建索引。联合索引把等值列放在前面、范围列放在最后，顺序跟着真实查询走，不是简单地把区分度最高的列放在最左。取值很少的列通常只作为联合索引中的一列。热查询可以建覆盖索引，需要的列已经在叶子上，就不必回表。

写多的表要控制索引数量，每个二级索引都会随写入维护。主键会进入聚簇索引，也会出现在每个二级索引里，因此主键宜短，并尽量按插入顺序增长。长字符串可以只索引有区分度的前缀；前缀索引不能像整列那样支持排序和覆盖。对列套函数或发生隐式类型转换时，普通索引用不上，除非另建表达式索引。已经有 `(a, b)` 时，单独的 `(a)` 通常多余，单独的 `(b)` 并不多余。

MySQL 用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 查看。`key` 为空表示没有选中索引，`possible_keys` 有值只说明它是候选。`type` 为 `ALL` 是全表扫描；`index` 是沿着整棵索引扫描，不等于很快定位到少数行。`key_len` 可以看出联合索引用了左侧多少字节。`Extra` 中的 `Using index` 表示覆盖索引，不必回表；`Using index condition` 表示索引条件下推。`Using filesort` 说明排序没有被这个索引吃掉，它本身不代表完全没走索引。

`EXPLAIN` 里的 `rows` 是估算。要看实际扫描，用 `EXPLAIN ANALYZE`。索引即使被选中，范围太大或回表太多时仍然会慢。

### 10. MySQL 的 RR（可重复读）隔离级别是如何解决幻读问题的？Next-Key Lock 是如何工作的？

**参考答案**

RR 下，普通 `SELECT` 用快照避免看到新提交的行；当前读用 Next-Key Lock 堵住锁定范围内的插入。两种读使用的机制不同。

幻读指同一事务里两次查询的行集合发生了变化，多出或少了行。同一行的内容变化是不可重复读。

InnoDB 的普通 `SELECT` 是一致性读。RR 在事务第一次这种读时建立 Read View，之后复用，其他事务新提交的插入不会出现在这个视图里。这条路径不加间隙锁。RC 每次语句新建 Read View，因此能看到语句开始前已经提交的新行。

`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`，以及 `UPDATE`、`DELETE`，属于当前读。它们读取最新已提交版本并加锁。Next-Key Lock 等于记录锁加上这条索引记录之前的间隙，区间是前一条记录到当前记录，左开右闭。其他事务向这个间隙插入时，插入意向锁会和它冲突，于是下一次当前读不会在范围内冒出新行。间隙锁本身只锁开区间；插入意向锁加在插入点所在的间隙上，彼此兼容，但和已有间隙锁冲突。

唯一索引上等值查找并且记录存在时，退化为只锁这一行，因为这个键不能再插入另一条。记录不存在时，仍然锁住它应该落入的间隙。非唯一索引上等值查找，除了命中记录前面的间隙，还会锁到后一条不同取值之前，避免再插入一个相同的键。例如索引值是 10、20、30，对非唯一的 `age = 20` 做当前读，会锁住 `(10, 20]` 和 `(20, 30]`。条件没有走索引时，可能锁住扫描到的大范围。

RC 的普通当前读一般不加间隙锁，所以锁住现有行也挡不住新插入。RR 里如果先做快照读，别的事务插入并提交，再做 `FOR UPDATE`，当前读仍看最新版本，可能读到快照中没有的行。RR 保证的是同一条快照不变，以及当前读已经锁定的范围不被插入。

### 11. 在 Spring AI 中，如何处理大模型返回的流式响应（Streaming Response）？

**参考答案**

用 `ChatClient.stream().content()` 取得逐段文本，再以响应式流推给前端。流式依赖响应式栈；命令式应用也要引入 `spring-boot-starter-webflux`。

```java
@GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> chat(@RequestParam String message) {
    return chatClient.prompt()
            .user(message)
            .stream()
            .content();
}
```

同步的 `call().content()` 会在这一步发出请求并返回完整文本。`stream().content()` 返回的是 `Flux`，订阅之后才向模型逐段要增量。控制器把 `Flux` 直接返回给客户端，写出响应时才订阅。每一段都是增量，由前端拼接，空段要过滤。客户端断开时取消订阅，让上游的模型请求停下来。若先把 `Flux` 收成一个字符串再返回，首字延迟就消失了。

同步调用走 Servlet 栈。纯 WebFlux 应用如果还使用阻塞的 `call()`，需要同时引入 `spring-boot-starter-web`，并且这些调用会阻塞。定制模型的 HTTP 客户端时，`RestClient` 和 `WebClient` 都要配置。

对话记忆不要按 token 写入。默认的记忆 Advisor 位于工具循环外侧，流结束后保存完整的用户消息和助手回答。自己收集时也等整段结束后再存。中途失败时，用户可能已经看到半截回答，重试要说明是续写还是重新开始。

带工具时，参数可能分成多段到达，收齐并校验后再执行。工具执行是阻塞的，要有独立的超时，不能无期限占用业务线程。工具还没返回时，不能把已经流出的半截文本说成查询成功或办理完成。

### 12. Spring AI 的 Function Calling 功能是如何实现的？它如何帮助大模型与外部工具/API 交互？

**参考答案**

模型根据工具的名字、说明和参数 schema 决定是否调用，并生成参数。真正的执行发生在应用里，模型接触不到工具背后的 API。

Spring AI 2.0 把循环放在 `ChatClient` 自动注册的 `ToolCallingAdvisor` 上。`ChatModel` 只返回工具调用请求，自己不执行。1.x 则是各家 `ChatModel` 内部自带这个循环。

工具可以用 `@Tool` 标在方法上，也可以用 `FunctionToolCallback` 包装一个函数。说明要写清何时使用。参数默认必填，可选参数用 `@ToolParam` 标出。调用时把工具对象交给 `ChatClient`：

```java
String answer = ChatClient.create(chatModel)
        .prompt()
        .user(userText)
        .tools(new OrderTools())
        .call()
        .content();
```

`ChatClient` 上的 `.tools()` 会追加到该客户端的默认工具之后，不是替换。会修改数据的工具按请求注册，不放进所有请求共享的默认工具。同名工具在 `ChatClient` 合并列表时会直接拒绝这次请求。直接放进 `ChatModel` 请求选项的工具列表则是替换模型上的默认工具。

Advisor 先把工具定义随请求发给模型。模型若返回 tool call，`ToolCallingManager` 按名字找到回调，把参数反序列化后执行，再按调用 id 把结果追加到历史并重新请求模型。这个过程持续到模型不再要工具；工具如果标记为直接返回，循环就此结束并把工具结果交给调用方。直接使用 `ChatModel` 时没有这层 Advisor，需要自己判断 `hasToolCalls()`，执行工具后再构造下一次提示。

模型生成的参数经常不是合法 JSON，枚举值也会编错。校验失败时把错误作为工具结果退回，并限制修正次数。`@Tool` 方法就是普通 Java 方法，不会自动带上当前用户的权限。方法里要根据登录身份重新检查参数。这样，大模型就能用业务语言触发查订单、查天气等已有接口，而鉴权、事务和幂等仍留在这些接口里。

### 13. 设计一个能够使用工具（如查天气、订机票）的 AI Agent，你会如何设计它的决策和执行流程？

**参考答案**

查天气和查航班可以放进模型驱动的循环。订机票会改变订单，由外层状态机决定这次请求能不能看见订票工具；模型负责补齐条件并解释结果。

读工具包括查天气和查航班，schema 写清城市、日期、出发地和到达地。订票工具只接受上一次查询发出的报价 id，不接受模型自己编写的航班号和价格。用户还没确认时，这次请求不注册订票工具。

决策循环交给带工具的 `ChatClient`。模型要么给出最终回复，要么给出工具调用。运行时校验工具名和参数，按当前用户做权限检查，并设置超时。结果按调用 id 回到上下文。循环要有步数上限，避免来回查询。工具失败要作为结构化结果返回，让模型向用户说明原因，而不是变成空字符串后继续编造。

会话状态放在应用里，至少区分收集条件、已报价、待确认和已下单。确认文案由查询结果生成，不用模型复述出来的价格。下单携带幂等键，支付仍走原来的订单服务。天气查询失败不阻断已经开始的订票。

这样会多一次确认，换到的是模型不能绕过状态直接下单。全程交给模型更灵活，但误订和编造价格没有第二道门。每一步留下工具名、参数、耗时和结果码，出了错才能区分是模型选错了工具，还是下游超时。

### 14. 你平时通过哪些渠道学习和跟进 AI 领域的新技术？最近有看到什么让你印象深刻的技术或方案吗？

**答题思路**

这题看你是不是真的在跟进，不看能报出多少名词。按渠道、跟进方式、一个最近的例子来讲。

1. 渠道只留能够落实到自己代码的来源：所用框架和模型的官方说明、迁移文档，以及你跑通的一个小例子。社区讨论用来发现线索，结论回到文档或这次复现。
2. 跟进时盯一个和你的系统有关的点，例如流式输出、工具调用或检索效果。讲清它解决什么问题、你会改哪一层。讲不出要改的代码，就还没有跟上。
3. 最近的例子只选一个你读过或写过的。按以前怎么做、新做法动了哪一步、还有什么没有验证来讲。没有合适的例子，就说正在补哪一块。
4. 不要编论文、公司或调用量。这轮如果已经聊过 Function Calling 或框架差异，例子就用刚才那个对比的来源，例如官方文档和一次自己写的工具循环。
