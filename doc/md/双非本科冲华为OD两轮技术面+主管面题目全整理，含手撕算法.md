### 3. Java 中面向对象的三大特征是什么

**参考答案**

三大特征是封装、继承和多态。

封装把数据和对数据的操作收进对象，外部只通过公开方法访问。调用方依赖行为，类内部的字段和存储方式可以改。继承表达「是一种」，子类复用父类的字段和方法，父类一改，所有子类都跟着变。能用组合表达的复用，优先用组合。多态是同一类型的引用在运行时落到不同实现，Java 里靠父类或接口加重写：编译期看引用类型，运行期看实际对象。

重载在编译期就选定了方法，不属于这里说的运行时多态。父类引用去读字段时，读到的是父类字段，字段不参与多态。

### 4. JVM 内存区域划分，哪些区域会发生 OOM

**参考答案**

按 HotSpot、JDK 8 及以后来讲。线程私有的是程序计数器、Java 虚拟机栈、本地方法栈。线程共享的是堆和方法区，方法区的实现是元空间，占用本地内存。直接内存不属于规范里的这几块运行时数据区，NIO 的堆外缓冲会用到，问 OOM 时要一起说。

会发生 OutOfMemoryError 的主要是堆（`Java heap space`）、元空间（`Metaspace`）和直接内存（`Direct buffer memory`）。虚拟机栈帧太深，先抛 `StackOverflowError`；只有在给新线程分配栈失败，或栈扩展时没有内存，才是 `OutOfMemoryError`。程序计数器不会 OOM。

堆溢出先区分是对象活着释放不掉，还是流量超过了堆容量。元空间溢出常见于类被反复加载。直接内存不在普通堆转储的对象图里。字符串常量池在堆上，大量 `intern` 撑满的是堆。

### 5. MySQL 的 InnoDB 引擎中，B+ 树索引相比 B 树的优势是什么

**参考答案**

InnoDB 的索引是 B+ 树。优势在扇出、范围扫描和单次查询代价稳定。建表语句里有时写成 `BTREE`，实现仍是 B+ 树。

非叶子节点只放键和指向子页的指针，不放整行。一页里能放下更多键，树更矮，点查经过的磁盘页更少。记录都在叶子上，从根到叶子的路径长度相同，单次查询的代价稳定。同一层的页用双向链表串起来，范围查询定位到左端点后，顺着叶子链表往下扫。B 树的非叶子节点也存记录，范围扫描要在树里做中序遍历，随机读更多；节点里夹着记录，同样大小的页能容纳的键更少。

聚簇索引的叶子是整行，二级索引的叶子是主键，查完整行还要回表。这个结构和「为什么用 B+ 树」是两件事，被追问再讲。

### 6. Redis 常用的数据类型有哪些，各自适用什么场景

**参考答案**

基础类型是字符串、哈希、列表、集合、有序集合。Redis 5.0 起 Stream 也是独立类型。Bitmap、HyperLogLog 建在字符串上，GEO 建在有序集合上。

字符串适合缓存一整份结果、计数和锁的持有者标识，`INCR` 是原子的。哈希适合一个对象的多个字段、按字段读写；过期粒度是整键。列表适合最新 N 条和时间线。它没有确认和重试，可靠投递用 Stream 的消费组，或用专业消息队列。集合适合去重、标签和交集，例如共同关注。有序集合里成员唯一，分数决定顺序，适合排行榜，也可以用时间戳当分数做延迟队列。Bitmap 适合签到和状态位。HyperLogLog 适合允许误差的 UV。GEO 适合附近的人、附近的点。

选型时说明要不要排序、要不要去重、是整存整取还是按字段更新。一个 value 特别大，或集合里元素特别多，删除和迁移都会堵住 Redis，这是使用这些类型时要守的边界。

### 7. 场景题：线上接口响应突然变慢，你的排查思路和具体步骤是什么

**参考答案**

先把「变慢」收成可核对的范围，再往下拆。没有监控数据时，先补范围，再进入具体一层。

1. 划定范围。哪一个接口，从哪个时间点开始，所有实例还是一台，错误率有没有一起升高，当时有没有发布、改配置或流量尖峰。只变慢，和大量超时失败，下一步不同。
2. 看应用自己。把耗时分位、CPU、GC 停顿、线程池队列、数据库连接池的等待时间分开看。线程栈里大量堵在同一把锁、同一次 RPC 或同一条 SQL，瓶颈就在那里。
3. 看依赖。数据库看慢查询、行锁和连接数。Redis 看慢日志和大 key。下游超时后的重试会把请求放大。同步接口如果在等一条异步链路，消息堆积也会表现为接口变慢。
4. 对一下变更。索引被删、缓存成批失效、调用方突然加重试，都会在同一分钟把耗时打高。
5. 先止血再保留现场。限流、降级或回滚用来保住错误率。线程栈和 GC 日志先留。堆转储会让进程停顿，确认和堆有关再做。

变慢经常是在排队。线程池或连接池打满时，单次执行不一定变长，等待变长。执行时间和等待时间要分开看。

### 8. 场景题：如何使用 Redis 设计一个简单的分布式锁，需要考虑哪些边界问题

**参考答案**

单机 Redis 上的互斥，用一条 `SET` 把「不存在才写入」和「过期时间」一起做完，解锁用 Lua 核对持有者再删除。过期、主从切换和旧持有者回写，是三道要单独说的边界。

```redis
SET lock:order:1001 7c3a9e NX PX 30000
```

`NX` 保证只有一个客户端能拿到锁，`PX` 让持有者崩溃后锁会自己消失。value 用本次请求的唯一标识，不能用固定的 `1`。

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

比对失败就不动 key，避免把别人刚拿到的锁删掉。`SET` 和 `DEL` 分成两条命令、或者 `SETNX` 成功后再单独 `EXPIRE`，中间崩溃会留下一把没有期限的锁。

边界有四件。第一，业务时间可能超过 TTL。续期也用 Lua，只有 value 还是自己才延长，不能无条件 `PEXPIRE`。第二，Redis 主从异步复制时，锁写在主上、还没复制到从，主宕机后新主没有这把锁，第二个客户端会再拿到。单实例锁保不住故障切换下的互斥。真正怕两个写一起发生时，存储层要认一个单调递增的 fencing token，过期前的旧持有者拿旧 token 写不进去。第三，同一调用链需要重入时，用「持有者 + 计数」，再次 `SET` 会把 TTL 和持有者弄乱。第四，集群里一段 Lua 涉及的 key 必须在同一个槽，多 key 用 hash tag。

生产上这三件事（唯一 value、Lua 解锁、到期前续期）常常交给现成客户端做。面试里要把这三件事本身讲清楚。多主的 Redlock 依赖时钟和停顿假设，讲完单实例锁的边界即可，把它当成默认正确答案会讲偏。

### 10. Elasticsearch 的倒排索引原理大概讲一下

**参考答案**

倒排索引记的是「词 → 出现过这个词的文档」。按词查找时走这条映射，按文档扫描的是正向内容。

写入时分析器做分词，并把大小写、词干收成统一的 term。每个 term 对应一条倒排链，链上是文档号，短语查询还要位置，高亮还要偏移。文档号有序，用差分编码压缩，链上建跳表，方便做交集和并集。Lucene 里词项按字典序存放，词项索引常用 FST，按前缀定位到对应的块。

段写成之后不可变。新文档进入新段，查询逐段做再合并结果。删除先打标记，段合并时才物理清掉，所以删除后空间不会立刻还回来。

排序和聚合主要走 doc values 这种按列存放的结构。分词后的文本字段拿来做精确聚合会失真，精确值用 keyword 字段。

### 11. Kafka 和 RocketMQ 在消息可靠性方面分别怎么保证的

**参考答案**

两边的投递语义都是至少一次。副本和刷盘解决的是不丢，业务幂等解决的是重复。写成恰好一次，需要把范围说清楚。

Kafka 靠副本，不靠每条消息都 `fsync`。生产者使用 `acks=all`，并让 `min.insync.replicas` 至少为 2，应答时 ISR 里要有 leader 以外的副本，否则副本数不够时写入会失败。关闭 unclean leader election，落后副本不能被选成 leader，已确认的消息不会因为换主被截断。幂等生产者去掉同一会话里重试造成的重复。消费成功后再提交位移；处理外部数据库时，用业务唯一键挡住重复消息。事务配合 `read_committed`，保证的是「消费 Kafka 再写回 Kafka」这一段，写到 Kafka 以外的副作用仍然要幂等。

RocketMQ 要同时看刷盘和主从。同步发送失败会重试。`SYNC_FLUSH` 是落盘之后才应答，异步刷盘只保证进了页缓存，机器掉电可能丢。`SYNC_MASTER` 是从节点确认后才应答，异步复制是主节点先应答。同步刷盘加同步复制最稳，延迟也最高。本地事务和发消息要绑在一起时用事务消息：半消息对消费者不可见，本地事务提交后再提交消息，提交结果丢失时 Broker 回查本地事务。消费端处理成功再返回成功；失败按延迟级别重试，超过 `maxReconsumeTimes`（默认 16 次）进入该消费组的死信队列。顺序消费遇到失败要卡住当前队列，跳过会把顺序打乱。

### 12. 手撕算法：LeetCode 141 环形链表，判断是否有环并找出环的入口节点

**参考答案**

判断有环是 141，找入口是 142。题目两步都要，用 Floyd 快慢指针一次做完。有环时返回入口节点，无环返回 `null`。时间 O(n)，空间 O(1)。

慢指针每次一步，快指针每次两步。快指针先到 `null` 就是无环。两者相遇说明有环。然后另起一个指针从头节点出发，留在相遇点的那个指针原地开始，两者都改成每次一步，再次相遇的节点就是入口。头到入口的距离，等于相遇点顺着环走到入口的距离，多出来的整圈会在走的过程里抵消。

例如 `1 → 2 → 3 → 2`，入口是 2。用哈希集合记录走过的节点也能做：第一次重复访问的节点就是入口，空间 O(n)。面试里先写 O(1) 空间这版。

```java
public class Solution {
    public ListNode detectCycle(ListNode head) {
        ListNode slow = head;
        ListNode fast = head;
        while (fast != null && fast.next != null) {
            slow = slow.next;
            fast = fast.next.next;
            if (slow == fast) {
                ListNode entry = head;
                while (entry != slow) {
                    entry = entry.next;
                    slow = slow.next;
                }
                return entry;
            }
        }
        return null;
    }
}
```

`ListNode` 按常规定义，含 `val` 和 `next`。两个指针都从头开始，先走再比较，单节点自成环时入口就是它自己。

### 4. 数据库层面你们怎么做慢 SQL 优化，联合索引的最左匹配原则底层原理是什么

**参考答案**

慢 SQL 先定位再改，联合索引的最左匹配来自 B+ 树叶子的排序方式。落到项目时只讲一条你改过的语句：优化前 `EXPLAIN` 是什么样，你加了或调整了什么，扫描行数怎么变。

定位看慢查询日志或性能库里的语句、耗时和扫描行数。`EXPLAIN` 重点看 `type`、`key`、`rows` 和 `Extra`。`rows` 是估算。`Using filesort`、`Using temporary` 说明排序或去重没靠索引完成，`Using index` 说明覆盖了查询、不用回表。

常见改法有这些。索引列上套函数、或者字符串列和数字做比较，优化器用不上这个索引，把比较改成和列的存储方式一致的范围条件。联合索引把等值列放在前面，范围列放在后面，顺序按你这条查询的等值前缀来，而不是机械地把区分度最高的列放最左。深分页的 `LIMIT 100000, 20` 会先扫过再丢掉，改成按主键或有序列记住上一页的终点往下取。还要看锁等待、统计信息过期和缓冲池，慢的原因也可能在锁和 IO，加索引之前确认写进去的代价。

最左匹配的底层是：联合索引 `(a, b, c)` 的叶子按 a、再按 b、再按 c 有序。要定位到一段连续叶子，得从左边给出等值前缀。`a = ?`、`a = ? AND b = ?`、`a = ? AND b = ? AND c = ?` 都能顺着这棵树缩小范围。只有 `b = ?` 时，叶子不是按 b 整体有序的，常规路径用不上这个索引。`a = ? AND c = ?` 只用 a 定位，c 是过滤；索引条件下推可以把 c 的判断放到引擎里，减少回表，c 仍然不参与这段范围的定位。`b` 一旦变成范围，它右边的 `c` 也不再用于定位。优化器会重排条件，所以和 `WHERE` 里列的书写顺序无关。

MySQL 8.0.13 起有索引跳跃扫描：最左列区分度很低时，优化器可能分成几段去用右边的列，执行计划里能看到。这是少数计划上的例外，建索引仍然按真实查询的等值前缀来。

### 5. 项目里 Redis 缓存和数据库不一致怎么处理的，缓存穿透怎么防

**参考答案**

常规写路径是 Cache Aside：先更新数据库，成功后再删除缓存。穿透要同时做参数校验、布隆过滤器和短 TTL 的空值，单靠空值挡不住随机 key。如果项目里用的是别的顺序，把当时的并发窗口讲出来。

删除缓存而不是更新缓存，是因为两次并发写会交错：后写完缓存的那次，可能把较旧的值留在缓存里。先删缓存再更新数据库也有窗口，中间的读会把旧行装回缓存，脏数据会留到过期。先更新数据库再删缓存，窗口窄得多，仍然存在一种交错：读请求在更新前读到旧值，又在删缓存之后把旧值写回去。短 TTL 用来兜底。要把这个窗口收紧，用 binlog 订阅在提交后再删一次，或者缓存值带版本，旧版本不能覆盖新版本。延迟双删依赖一个猜出来的等待时间，binlog 的顺序和数据库提交一致。删缓存失败要重试，否则数据库已是新值，缓存仍是旧值。

穿透是请求的 key 在数据库里不存在，缓存永远不会被正常回填，流量一次次打到数据库。先做参数合法性，非法 id 直接拒绝。布隆过滤器说不存在就返回；说存在仍可能误判，再查缓存和数据库。数据库确认没有之后，写入一个短 TTL 的空值，同一 key 在这段时间里不再打穿。攻击流量用大量不同的随机 key 时，空值会把内存占满，所以空值缓存前面要有限流，布隆过滤器放在缓存查询之前。

和另外两个词分开讲。击穿是热点 key 过期的瞬间，大量请求一起重建。雪崩是大批 key 同时过期，或缓存进程不可用。

### 6. 场景题：设计一个支持高并发的秒杀系统，你会从哪几层做限流和削峰

**参考答案**

限流和削峰从外往里做，越早拒绝越便宜。库存以数据库的条件更新为准，Redis 负责把绝大多数请求挡在数据库外面。

1. 页面。活动页静态化，放在 CDN。按钮防重复点击。展示用的库存允许延迟，页面刷新打到缓存或静态资源，不打到下单接口。
2. 接入层。网关按用户、IP 和活动总 QPS 限流，超过直接返回繁忙。非法参数和明显的脚本流量在这里丢掉。
3. 应用。单机限流挡住瞬时突发，Redis 限流做全局限额。过了这一层，才进入资格校验。
4. Redis 预减。用一段 Lua 判断库存大于 0 再扣减，失败立刻返回售罄。这一步是准入，最终以数据库为准。

```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if not stock or stock <= 0 then
    return 0
end
redis.call('decr', KEYS[1])
return 1
```

5. 队列。拿到资格的请求写入消息队列，消费者按数据库能承受的速度创建订单。队列设上限，满了就拒绝，堆积本身会变成故障。
6. 数据库。用 `UPDATE stock SET remain = remain - 1 WHERE id = ? AND remain > 0`，影响行数为 0 就是卖完。用户和活动上的唯一约束挡住重复下单。

预减成功但消息没发出去，或者下单失败，都要回补 Redis 库存，回补按订单号幂等。只扣 Redis 不落这条条件更新，会超卖。同步在请求线程里扣数据库，峰值会把连接池打满。队列把结果变成异步查询，要给出查询入口，超时未支付的订单把库存还回去。

库存 key 会打在一个分片上。要拆 key 时，扣减仍然需要一个原子的总量，拆开之后各凭感觉扣，会超卖。

### 7. Spring 的 IOC 容器初始化过程大概说一下，AOP 在项目中具体用在哪些地方

**参考答案**

以 `AnnotationConfigApplicationContext` 的 `refresh` 为准，容器初始化是一条固定顺序，单例创建放在后段。

先准备环境和内部状态，再拿到 `BeanFactory`。接着执行 `BeanFactoryPostProcessor`。注解配置下，`ConfigurationClassPostProcessor` 在这一步解析 `@Configuration`、`@ComponentScan` 和 `@Bean`，把 `BeanDefinition` 注册进去。然后注册 `BeanPostProcessor`，初始化事件多播器，`onRefresh` 留给子类做自己的事，例如 Web 容器在这里启动。随后注册监听器，在 `finishBeanFactoryInitialization` 里实例化所有非懒加载单例，最后发布 `ContextRefreshedEvent`。

单个单例的创建是：实例化、填充依赖、初始化。初始化完成后，对象放进单例池。AOP 代理一般在初始化之后的 `BeanPostProcessor` 里生成，容器外面拿到的往往已经是代理。提前暴露给循环依赖的那个早期引用，也会在取出时走代理的创建逻辑。构造器注入的循环依赖，三级缓存接不住。

**答题思路**

AOP 用在哪，只讲你仓库里真实存在的一个切面，再提一句事务。

1. 先点名切面：操作日志、权限校验、接口耗时，或一个自己写的加锁注解。说出切点是哪类方法。
2. `@Transactional` 也是 AOP。如果它和你的切面叠在同一个方法上，说明两者的顺序是怎么定的。
3. 补上失效场景：同类内部自己调用方法，调用的是原始对象，代理上的事务和切面都不会执行。你如果遇到过，就把那个方法怎么拆开讲一下。
4. 全局异常处理多用 `@ControllerAdvice`，它是组件回调。你的项目里如果是切面做的，再说它是切面。

### 8. 线程池的拒绝策略有哪几种，你们项目里怎么配置线程池参数的

**参考答案**

`ThreadPoolExecutor` 自带四种拒绝策略，也可以自己实现 `RejectedExecutionHandler`。默认是 `AbortPolicy`。

任务进来时的顺序是：运行中的线程少于核心线程数，就新建线程；否则尝试入队；队列满了，且线程数还没到最大线程数，就再新建线程；最大线程数也满了，才走拒绝策略。队列如果无界，请求会一直入队，最大线程数和拒绝策略都不会生效，内存先被队列吃掉。

`AbortPolicy` 抛 `RejectedExecutionException`，调用方知道这次没提交成功。`CallerRunsPolicy` 让提交任务的线程自己跑，形成反压；拿来跑它的如果是接入线程，接入能力会下降，这是有意用慢换不丢。`DiscardPolicy` 把任务丢掉，没有异常。`DiscardOldestPolicy` 丢掉队列里最旧的任务再提交一次，新任务更有价值时才用，被丢掉的那个调用方收不到通知。线程池已经关闭时，`CallerRunsPolicy` 也会丢弃任务。

`Executors.newFixedThreadPool` 的队列无界，`newCachedThreadPool` 的线程数无界。生产上的池子用有界队列，并写上线程名。`keepAliveTime` 默认只回收超过核心线程数的那些线程，除非打开 `allowCoreThreadTimeOut`。CPU 密集的任务，核心线程数从核数附近开始压。IO 密集可以更大，上限看下游连接池，线程数超过连接数之后只是在排队。队列长度、活跃线程、拒绝次数要进监控。

**答题思路**

配置按你项目里那个池子讲，记不清的 `core` 和队列容量就讲口径。

1. 这个池子跑的是哪类任务，调用方是在线请求还是后台作业。
2. 队列为什么有界，满了用的是哪一种拒绝，用户或调用方能不能感知。
3. 你看过哪张图或哪条日志：队列长度、拒绝次数，还是下游超时。
4. 如果当时用了无界队列，说明你现在会怎么改，以及改完拒绝发生时调用方做什么。

### 9. 中间件场景题：如果用 Kafka 消费消息时频繁 Rebalance，你会怎么排查

**参考答案**

频繁 Rebalance 说明消费组在反复收回分区再分配，这段时间消费是停的，表现为 lag 一阵阵升高。先从日志里的原因下手，再决定是处理太慢、成员在抖动，还是分配协议本身停顿太长。

日志里看成员加入、离开、掉线和分区变化。常见原因有四类。第一，一次 `poll` 拿回去的消息，处理时间超过 `max.poll.interval.ms`（常见默认 5 分钟），客户端被判定为没能力继续消费，踢出组。心跳在独立线程里发送，把消费线程堵住，心跳仍可能正常，这条处理时限照样会触发。第二，进程崩溃、长时间 GC、网络断开，心跳超过 `session.timeout.ms`，成员被移除。第三，发布时消费者一起退出再加入，或者主题分区数变化，都会重新分配。第四，默认一类 eager 协议会先把分区全部收回，再整批分回去，组里每次成员变化都是全员停顿。

排查按这个顺序。先对一下 Rebalance 的时间点和发布、扩容、GC、处理耗时。处理慢就减小 `max.poll.records`，把单次处理时间压进 `max.poll.interval.ms`，慢的业务移出消费线程。把这个超时调得很大，只会让卡死的消费者更晚被发现。发布抖动可以给消费者配置 `group.instance.id`，同一实例在会话超时前回来，组里不做一次 Rebalance。全员停顿用 `CooperativeStickyAssignor` 改成增量分配，只挪走要变更的分区，组内消费者都要支持这种协议。

分区数远大于或远小于消费者数，会让每次分配的变化更多。先把「为什么触发」和「分配时停多久」分开，再改参数。

### 11. 手撕算法：LeetCode 146 LRU 缓存，实现 get 和 put 方法

**参考答案**

`get` 和 `put` 都要 O(1)。用哈希表定位节点，用双向链表维护使用顺序。链表靠近头的是刚用过的，靠近尾的是最久没用的。`get` 命中也要把节点挪到头部，读过的数据同样算最近使用。

`get` 找不到返回 -1，找到则挪到头部并返回值。`put` 已有这个 key 时更新值并挪到头部，个数不变。没有这个 key 时插到头部；插入后超过容量，删掉链表尾部那个真实节点，并把它的 key 从哈希表里去掉。漏删哈希表，后面会拿到一个已经不在链表里的节点。

容量为 2 时：`put(1,1)`、`put(2,2)`、`get(1)`、`put(3,3)` 会淘汰 2，`get(2)` 返回 -1。LeetCode 146 的容量至少为 1。时间平均 O(1)，空间 O(capacity)。这套结构本身不加锁，并发要另加互斥或分段。

允许用标准库时，`LinkedHashMap` 把 `accessOrder` 设为 true，并在 `removeEldestEntry` 里按容量淘汰。访问顺序会在 `get` 和 `put` 时更新。面试要求手写完整版时，写下面这套指针。

```java
import java.util.HashMap;
import java.util.Map;

class LRUCache {
    private static class Node {
        final int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addToHead(created);
        if (map.size() > capacity) {
            Node lru = tail.prev;
            remove(lru);
            map.remove(lru.key);
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addToHead(node);
    }

    private void addToHead(Node node) {
        node.next = head.next;
        node.prev = head;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}
```

头尾使用哨兵节点，删除和插入时不用再判断空指针。淘汰的是 `tail.prev`，它才是最久未使用的数据节点。

1. 背景用两句：做什么需求，分歧的双方各自要保什么。
2. 分歧点说成一个技术选择，并摆出约束：一致性、延迟、工期、出了问题谁值守。
3. 决定靠一次可以看的证据：对账、压测、灰度，或把两种方案的失败路径写在同一页上比较。
4. 定了之后按结论做。如果后来证明是你漏了约束，直接说你漏了哪一条，以及你怎么补的。
5. 收尾落在结果：方案上线后哪条风险被接住了。避免评价对方的态度。

### 6. 近 1 到 2 年的职业规划大概是什么样的

**答题思路**

规划落在能力，不写目标职级、管理幅度或薪资。和前面项目里你真实的短板接上。

1. 近一年：独立把一块业务从需求、上线走到故障处理。短板就说你已经遇到的那一类，例如慢 SQL、缓存一致性或消息重复，选你真的要补的一项。
2. 到两年：能做小模块的方案，把容量、失败和回滚讲清楚，评审时把风险写下来。
3. 和这次机会的关系：这些能力放在当前这类项目里练。发展看项目和考核，计划里不写转正编的时间表。
4. 如果对方问管理还是技术，按你的真实意向答。想继续做技术，就说先把一个系统做深。

### 7. 平时怎么保持技术学习，最近在学什么新技术或关注哪些方向

**答题思路**

方法讲你真实的习惯。最近在学的只说一个你能展开几分钟的，没在学的方向不要临时改口。

1. 材料以官方文档和源码为准，文章用来找入口。学一个点，就落到一段你跑过的代码，或项目里的一个改动。
2. 顺序是工作里已经遇到的问题优先，然后才是岗位相关的存储、消息和并发。
3. 最近这一项要能讲下去：例如缓存和数据库怎么配合、消费消息怎么提交位移，或者你怎么用编码工具并自己核对结果。和前面技术面答过的内容保持一致。
4. 笔记或代码放在你当场打得开的地方。对方追问细节时，按你读过的那一截讲。

### 8. 你觉得自己哪方面的特质比较适合我们这边

**答题思路**

只讲两个特质，每个都用前面说过的同一段经历当证据。特质要和派驻开发对得上：能进项目、能和人对齐、能把分到的模块交付完。

1. 第一个建议讲把问题追到具体一层：线上变慢或数据不对时，你怎么收到某一层，而不是把整个链路重讲一遍。用你项目里那件真事。
2. 第二个建议讲协作或工期：方案里你会把失败和回滚写上，时间紧时先保住数据和能回退的路径。
3. 两句之内说完每个特质，把时间留给对方追问那件证据。
4. 「学习能力强」「抗压」这类说法，如果要用，后面立刻跟上那件具体的事。没有事例就换一个你能证明的特质。
