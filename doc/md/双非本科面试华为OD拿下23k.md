### 2. 请介绍一个你做过的最有挑战性的项目，并说明你承担的核心工作

**答题思路**

### 3. synchronized 和 ReentrantLock 的区别是什么？分别适用于什么场景？

**参考答案**

两者都是可重入的互斥锁。synchronized 由 JVM 实现，进出代码块自动加解锁；ReentrantLock 基于 AQS，必须自己 lock，并在 finally 里 unlock。

1. 释放方式不同。synchronized 在代码块结束或抛出异常时都会释放。ReentrantLock 少写一次 unlock，锁会一直被占着；重入几次就要解锁几次。
2. 控制能力不同。ReentrantLock 可以 tryLock 超时放弃、lockInterruptibly 在等待时响应中断、构造公平锁，也可以建多个 Condition，把等待队列分开。线程堵在 synchronized 的监视器入口上时，中断只会留下标记，不会立刻放弃等待；它也没有超时和公平模式。
3. 实现不同。ReentrantLock 用 CAS 修改 AQS 的 state，抢不到就进入队列，默认允许插队，所以是非公平锁。synchronized 现在走轻量级锁，竞争激烈再膨胀成重量级监视器。偏向锁从 JDK 15 起默认关闭，后续版本已移除，不要再按「偏向、轻量、重量」三步来讲。
4. 场景。小范围、逻辑简单的互斥用 synchronized，JVM 还能对未逃逸对象做锁消除。需要超时、可中断、公平或分组唤醒时用 ReentrantLock。读写比例差很多时用 ReentrantReadWriteLock，那是另一把锁。

公平锁会降低吞吐。先说默认非公平，再说明为什么这个场景必须排队。

### 4. Java 的垃圾回收机制中，G1 收集器的工作原理和特点是什么？

**参考答案**

G1 把堆划成大小相等的 Region，年轻代和老年代都是一组 Region，回收时优先处理垃圾比例高的 Region，用来把停顿压在目标时间内。JDK 9 起它是默认收集器。

年轻代回收仍是停顿复制：Eden 里的存活对象复制到 Survivor，年龄够了再复制到老年代 Region。老年代先做并发标记，找出每个 Region 还有多少存活对象；标记之后的 Mixed GC 会在同一次停顿里收掉全部年轻 Region，再加一批垃圾多的老年代 Region。正常路径是把存活对象复制到空 Region，靠 Remembered Set 处理跨 Region 的引用。

停顿主要花在复制和重新标记上，并发标记阶段应用线程仍在跑。目标停顿时间是努力方向，垃圾产生速度超过回收速度、或者复制时空间不够，仍会退化为 Full GC。超过 Region 一半的大对象独占连续 Region，回收不及时会把连续空间占满。

面试里要补上两句：G1 的常规回收是复制，Mixed GC 只挑一部分老年代 Region；它降低的是停顿，整堆标记和跨 Region 引用都有成本。

### 5. Spring 框架中，Bean 的生命周期是怎样的？

**参考答案**

单例 Bean 从定义到销毁，主路径是实例化、填充依赖、初始化、放入容器、关闭时销毁。

1. 实例化。按 BeanDefinition 调用构造器或工厂方法。构造器注入发生在这一步，此时对象还不能被别人使用。
2. 填充属性。处理字段和方法上的 @Autowired、@Value。填充过程中如果依赖别的 Bean，会触发那个 Bean 的创建。
3. 初始化。先回调 BeanNameAware、BeanFactoryAware；再走 BeanPostProcessor 的前置方法，ApplicationContextAware 和 @PostConstruct 都在这里；然后是 InitializingBean.afterPropertiesSet 和自定义 init-method；最后走后置方法。AOP 代理一般在后置方法里生成，容器外面拿到的往往是代理。
4. 使用。完成初始化的单例放进单例池。
5. 销毁。容器关闭时先调 @PreDestroy，再调 DisposableBean.destroy，最后调自定义 destroy-method。原型 Bean 容器不负责销毁。

@PostConstruct 早于 afterPropertiesSet。事务和切面作用在代理上，同类内部自己调用方法不会走到代理。

### 6. 如何解决循环依赖问题？Spring 是如何处理的？

**参考答案**

先拆依赖，这是正法：把互相调用的逻辑收进第三个类，或者只在一侧用事件。Spring 的三级缓存只兜住一种情况，单例并且用属性或 setter 注入。

构造器循环依赖解决不了，对象还没构造完，没有引用可以提前交出去。原型 Bean 不进缓存，循环创建会直接失败。

单例属性循环的做法：

1. 创建 A 时，实例化之后就把一个工厂放进三级缓存，再去填充 A 的属性。
2. 填充时发现需要 B，转去创建 B。B 又要 A 时，通过这个工厂拿到 A 的早期引用。如果 A 需要 AOP，代理就在这一刻创建，然后放进二级缓存。
3. B 完成后回到 A，A 走完初始化，放进一级缓存，并清掉二、三级里的记录。提前暴露过代理时，容器里登记的就是那个代理，避免有人拿到原始对象、有人拿到代理。

三级缓存放工厂，是为了真的发生循环时才创建早期引用。没有循环的 Bean 不会提前做代理。

Spring Boot 2.6 起默认禁止循环依赖。构造器上的 @Lazy 可以注入一个延迟代理来打断循环，但这只是把问题推迟，依赖关系仍然是环。

### 7. MySQL 索引的底层数据结构是什么？为什么选择 B+ 树而不是 B 树或哈希表？

**参考答案**

InnoDB 的索引是 B+ 树。主键索引的叶子存整行，数据和主键放在一起，称为聚簇索引；二级索引的叶子存索引列和主键。没有合适的主键时，会选用唯一非空索引，再没有就生成隐藏行号。

选 B+ 树，是因为数据库索引要同时支持等值、范围和排序，而且节点要按页落在磁盘上。

1. 对比 B 树。B 树的内部节点也存数据，一页能放下的键更少，树更高。范围查询还要在树的上下层来回跳。B+ 树只有叶子存行，内部节点全是键，扇出更大，高度常常只有三到四层；叶子之间有链表，范围扫描可以顺着链表走。
2. 对比哈希。哈希等值很快，但不支持范围、排序和最左前缀，也不适合按页组织。Memory 引擎可以把哈希当索引，InnoDB 的普通索引不是哈希。自适应哈希是 InnoDB 对热点页建的内存结构，用来加速重复等值查找，不是建表时选的索引类型。

二级索引每次叶子都带着主键，主键太长会把所有二级索引都撑大。

### 8. 什么是回表查询？如何避免？

**参考答案**

回表是先用二级索引找到主键，再拿主键到聚簇索引里读整行。二级索引叶子没有完整的行，查询需要的列不在这棵索引里，就得再查一次。

避免的办法是覆盖索引：where、order by、select 用到的列都在同一棵索引里，优化器不用回表。例如经常按 user_id 和 status 查 created_at，可以建 (user_id, status, created_at)。只为覆盖把大量很少用的列塞进索引，写入和页分裂都会变贵。

explain 里 Extra 出现 Using index，表示这次用了覆盖索引。Using index condition 是索引条件下推，能在存储引擎里先过滤、减少回表行数，并不等于没有回表。

主键尽量短。每个二级索引都保存主键，主键长，回表读到的键也更重。返回很多行时，就算有覆盖索引，也要先收窄查询范围。

### 9. Redis 为什么快？除了内存存储，还有哪些关键设计？

**参考答案**

数据在内存里只是第一层原因。Redis 能把单机 QPS 做得很高，还因为命令路径短、等待连接的方式便宜。

1. 命令由一个线程顺序执行。没有锁去抢同一份键空间，也没有线程切换。Redis 6.0 起可以用额外线程分担网络读写和解析，命令本身仍然串行。慢命令会堵住后面所有客户端，所以避免 KEYS、对大集合做聚合，以及一次删除巨大的 key；删除可以用 UNLINK 交给后台。
2. I/O 多路复用。一个线程用 epoll 这类机制盯住大量连接，连接可读可写时才处理，不为每个连接建一个线程。
3. 数据结构按内存访问来设计。SDS、哈希表、跳表、listpack 尽量紧凑，常见命令是 O(1) 或 O(log N)。
4. 协议简单。RESP 的解析成本低，一次往返往往就是一次内存操作。

持久化和主从复制不放在命令线程里同步做完。RDB 靠子进程，AOF 刷盘有单独线程。fork 时的页复制、AOF 重写和过大的 key，才会把延迟打上去。单线程也意味着一个实例吃不满多核，容量再往上走要分片。

### 10. Redis 的缓存击穿、穿透、雪崩分别是什么？如何预防和解决？

**参考答案**

三者都是请求穿过缓存打到数据库，但原因不同，不能用同一个办法。

1. 穿透：这个 key 在数据库里也不存在，缓存永远建不起来，每次查询都落到库。处理是先校验参数；对空结果做短 TTL 的缓存；再用布隆过滤器挡住肯定不存在的 key。布隆过滤器只会把不存在误判成可能存在，不会把存在误判成不存在，所以它只能挡穿透，不能代替数据库。空结果的 TTL 要短，否则数据后来写入了，缓存仍说没有。
2. 击穿：某个热点 key 到期的那一下，并发请求同时去加载数据库。处理是逻辑过期，由单个后台任务刷新；或者用互斥锁，只放一个请求回源，其余等待或快速失败。几乎不变的配置可以不设 TTL，更新时主动删除。
3. 雪崩：大量 key 在同一时刻过期，或者 Redis 整机不可用，流量一起打到数据库。处理是 TTL 加随机值；缓存做副本或分片；入口限流，Redis 不可用时降级，不把数据库打满。

击穿是一个热 key，雪崩是一批 key 或整个缓存层。重建缓存时要防止把异常结果写进去。

### 11. 谈谈你对分布式系统中 CAP 理论的理解，在实践中的取舍是怎样的？

**参考答案**

CAP 讨论的是网络分区时的选择。C 是读到最新写入，A 是未故障的节点在有限时间内给出响应，P 是分区仍然发生时系统还能按设计运行。分区无法靠设计消灭，所以真正要取舍的是分区期间偏向一致还是偏向继续服务。

偏向一致时，写不进多数派就拒绝写入，调用方看到失败，分区恢复前不提供可能过期的成功。etcd、ZooKeeper 的选主属于这一类。偏向可用时，各侧继续读写，允许读到旧值，分区愈合后再收敛。没有分区时，一致和可用可以同时满足。CAP 不讨论正常情况下的延迟，延迟和一致的取舍要用别的框架看。

一个系统里可以按数据分开选。库存扣减、支付记账分区时宁可失败；商品详情、时间线可以读旧。最终一致要有版本或日志把副本追平，还要有对账把追不平的数据找出来。

服务发现常常偏向继续提供名单，再用健康检查把坏实例摘掉；配置下发和选主更偏向读到同一份最新值。

### 12. 你了解 RESTful API 设计规范吗？一个好的 API 设计应该注意哪些方面？

**参考答案**

REST 用 URL 表示资源，用 HTTP 方法表示对资源的操作，用状态码表示结果。它是接口风格，不是某个框架。

1. 路径用名词，动作放在方法上。GET /orders/1 查询，POST /orders 创建，PUT 整体替换，PATCH 局部修改，DELETE 删除。查询不要做成 POST /getOrder。
2. 幂等要事先定好。GET、PUT、DELETE 重复执行，结果应和执行一次相同。POST 创建默认不幂等，超时重试可能出两笔单，需要客户端带幂等键，服务端用唯一约束挡住。
3. 状态码要和语义一致。200 成功，201 已创建，400 参数错误，401 未认证，403 已认证但无权限，404 资源不存在，409 状态冲突，429 被限流，5xx 是服务端故障。团队若统一用 200 加业务码，就要写进文档并坚持，不能两种风格混用。
4. 过滤、排序、分页放在查询参数里。分页要有稳定排序，避免翻页时重复或漏数据。大偏移量改为按上一次的主键继续取。
5. 破坏兼容的改动要有版本。错误响应给出稳定的错误码和可阅读的说明，不把内部堆栈返回给调用方。

搜索、导出、长时间批处理不必硬套一个资源动词，可以提供明确的动作地址，并说明能不能安全重试。

### 13. Linux 系统中，如何排查一个 CPU 使用率过高的 Java 进程？

**参考答案**

先确认是哪一个进程、哪一个线程，再决定是业务死循环、GC 还是启动期的编译。

1. top 按 CPU 排序，确认是目标 Java 进程，并看用户态和内核态各占多少。top -Hp 加上进程号，找到最忙的线程。把线程号转成十六进制，到 jstack 输出里对 nid。
2. 栈停在业务方法里，就看是不是死循环、灾难性回溯的正则、反复序列化或忙等。连续打两次栈，都停在同一行，基本就是这个热点。
3. 栈很浅、CPU 主要在 GC 线程上，用 jstat -gcutil 看回收频率和各代占用。年轻代回收过密，或者对象晋升后反复 Full GC，都会表现为 CPU 高、请求变慢。
4. 有条件用 async-profiler、JFR 或 Arthas 的 profiler 采样几分钟，比肉眼看栈更适合定位热点方法。进程刚启动时，JIT 编译线程会短时间占 CPU，先对一下启动时间，避免误判成死循环。
5. 流量没有增加、CPU 却缓慢爬升，同时看 GC 是否越来越勤。那更像缓存被击穿后的重复计算，或对象攒多了不停回收。

CPU 问题先留线程栈和 GC 日志。堆转储会让进程停顿，等栈证明和堆有关再做。现场不要先重启。

### 14. 手写算法：给定一个字符串，请你找出其中不含有重复字符的最长子串的长度。

**参考答案**

用滑动窗口。右端从左到右扫每个字符，哈希表记录这个字符上一次出现的下标。窗口里出现重复时，左端移到「该字符上次位置的下一位」。左端只能往右：上次位置如果已经在窗口外面，就忽略。窗口长度的最大值就是答案。

例如 abba。遇到第二个 b 时，左端移到这个 b；后面的 a 虽然在开头出现过，但那次位置已经落在窗口外，左端不能退回去。最长长度是 2。

每个字符最多进入窗口一次、被左端跨过一次，时间 O(n)。空间是字符集大小；字符没有范围限制时，最坏是 O(n)。空串返回 0。

```java
public int lengthOfLongestSubstring(String s) {
    java.util.Map<Character, Integer> last = new java.util.HashMap<>();
    int left = 0;
    int best = 0;
    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        Integer prev = last.get(c);
        if (prev != null && prev >= left) {
            left = prev + 1;
        }
        last.put(c, right);
        best = Math.max(best, right - left + 1);
    }
    return best;
}
```

字符只含 ASCII 时，可以把哈希表换成长度 128 的下标数组。这里按码元滑动，面试里默认字符落在基本多文种平面。

### 2. 详细描述你项目中的技术架构，以及在性能优化或高可用方面做了哪些工作？

**答题思路**

先画架构，再只深挖一件你亲自做过的优化。两件都点到，往往两件都讲不透。

1. 架构按请求路径讲：客户端、网关、哪几个服务、各自的库，读走缓存还是走从库，写完是否发消息。说明同步链路到哪里为止。
2. 性能挑一个有前后对比的点：慢 SQL、缓存、批处理或无用的远程调用。讲清优化前时间花在哪，你改了什么，为什么没选另一个改法。
3. 高可用讲一条失败路径：下游超时怎么断路、消息失败怎么重试、数据库或缓存不可用时是拒绝还是降级。给出你实际用过的那个。
4. 数字只用你能解释的数量级。被追问到没做的部分，直接说当时没做，并说明现有方案的边界。

主动准备一张失败时序：请求超时了，状态停在哪，谁来补偿，怎么保证补偿执行两次也没问题。

### 3. 在微服务架构下，服务之间如何保证数据的一致性？（可谈谈分布式事务）

**参考答案**

每个服务有自己的数据库时，本地事务跨不过服务边界。先确认业务能不能接受最终一致。允许中间态的，用消息加幂等；必须同时成功或同时取消的，再用 TCC、Saga 或 XA。

1. 本地消息表适合大多数链路。下单服务在同一个本地事务里写业务数据和一条待发送记录，后台再把记录投到消息队列。下游按业务单号做唯一约束，重复消息直接当成功。定时任务把长期没确认的记录对出来。
2. RocketMQ 事务消息是同一思路。先发半消息，本地事务成功后再提交；提交结果丢失时，Broker 会回查本地事务状态。回查必须查本地事务记录，不能只看内存。
3. TCC 把每个操作拆成尝试、确认、取消。尝试阶段预留资源，确认才真正生效。要处理空回滚和悬挂：取消先到而尝试还没执行时，取消应空成功，后到的尝试要拒绝。语义清楚，代码量也大。
4. Saga 用一串本地事务推进，失败就按相反顺序补偿。步骤多、又允许短时间中间态时可以用，隔离性要靠业务状态自己保证。
5. Seata 的 AT 模式靠前后镜像自动补偿，对业务代码侵入小。冲突高时全局锁会拖住热点行，不适合当作热点库存的唯一手段。XA 两阶段提交能做强一致，协调者故障时参与者会阻塞，高并发链路上很少用。

无论哪种，下游都要能幂等、能查询。没有查询接口，超时后无法判断应该重试还是补偿。

### 4. 你了解哪些服务注册与发现组件？对比一下 Nacos 和 Eureka

**参考答案**

常见的有 Eureka、Nacos、Consul 和 ZooKeeper。ZooKeeper 用临时节点做注册，偏一致；Consul 用 Raft 和健康检查，注册与发现、配置都能做。Java 面试里重点对比 Eureka 和 Nacos。

Eureka 偏向可用。客户端定时心跳续约，服务端互相复制注册表，调用方在本地缓存实例列表。心跳大量丢失时会进入自我保护，暂停按过期剔除，避免网络抖动把实例都删掉，代价是已经死掉的实例还会留在名单里。Eureka 2.x 没有继续，1.x 只保持维护，本身也不管配置。

Nacos 同时做注册和配置。临时实例走心跳和 AP 模型，适合会扩缩容的服务；持久实例可以走 CP，并由服务端做 TCP 或 HTTP 探测。它还有命名空间、权重和保护阈值：健康实例比例过低时，不再把流量只压到剩下的少数实例上。

新的 Java 项目更常选 Nacos，因为注册、配置和健康检查在一处，实例还可以按 AP 或 CP 分开。调用方都不能只相信名单，还要有超时、重试和熔断。Eureka 的自我保护、Nacos 的保护阈值，都说明注册表会在故障时故意保留旧数据。

### 5. RocketMQ 或 Kafka 如何保证消息的可靠投递？（不丢失、不重复）

**参考答案**

不丢失要生产者、Broker、消费者三段一起做，结果是至少一次。不重复靠业务幂等。消息队列单独做不到业务意义上的恰好一次。

不丢失：

1. 生产者确认成功后再继续。Kafka 把 acks 设为 all，表示当前同步副本都写下才返回；同时把 min.insync.replicas 设到 2 以上。这个值默认是 1，acks=all 仍可能只有领袖一份。副本因子至少 3，才能在一台宕机后仍满足两项。RocketMQ 用同步发送，并按可靠性要求开启同步刷盘和同步复制。
2. Broker 不要让明显落后的副本升为领袖，否则会把未复制的消息丢掉。Kafka 应保持 unclean leader election 关闭。
3. 消费者处理成功后再提交位点。Kafka 关掉自动提交，处理完再 commitSync。先提交再处理，进程一崩就丢消息；处理完但提交失败，就会再投一次。RocketMQ 成功返回成功状态，失败进入重试，超过次数进死信，不要在消费者里无限卡住。

不重复：

Kafka 生产者幂等只能去掉同一次生产者会话内的重试重复，Kafka 3.0 起默认开启。应用因为超时又发了一次业务消息，或者生产者换了会话，仍然会重复。RocketMQ 的重试同样会重复。消费者按业务键建唯一约束或去重表，重复消息返回第一次的结果。

本地事务和发消息要绑在一起，用事务消息或本地消息表。只在事务提交后裸发一次，进程正好在中间退出，消息还是会丢。

### 6. 如何使用 Redis 实现一个分布式锁？需要注意哪些问题？（超时、续期、可重入）

**参考答案**

加锁用一条命令完成：SET key value NX PX ttl。NX 保证不存在才写入，过期时间必须和写入原子完成。先 SETNX 再 EXPIRE，进程死在两条命令之间，锁就没有过期时间。value 用全局唯一的持有者标识。

释放用 Lua：值等于自己的标识才删除。直接 DEL 会把刚被别人加上的锁删掉。

三个必考问题：

1. 超时。业务执行时间超过 TTL，锁会先过期，第二个请求进得来。TTL 要盖住正常执行时间，同时假设它仍可能提前失效。
2. 续期。持有者在后台查看锁是否还属于自己，属于自己才延长 TTL。Redisson 的看门狗默认大约 30 秒过期，并按大约三分之一的间隔续期。业务结束要停止续期并解锁。进程挂了，续期一起停，锁靠 TTL 释放。
3. 可重入。同一线程再次进入不能把自己堵死。可用 Hash 记录持有者标识和重入次数，解锁时减一，减到 0 才删除。普通 SET 实现不可重入。

主从切换还有一个洞：锁写到主节点、还没复制到从节点时主节点宕机，新主节点上这把锁不存在。单 Redis 锁保不住这个故障。更强的互斥用 etcd 或 ZooKeeper；Redlock 依赖多台独立主节点和严格超时，对时钟敏感，不拿来保护资金。

锁过期后，旧持有者可能还在写。存储侧要校验单调递增的 fencing token，或者用数据库唯一约束和状态条件做最终裁决。Redis 锁用来减少冲突，正确性放在数据库约束上。

### 7. MySQL 的主从复制原理是什么？延时问题如何监控和优化？

**参考答案**

主库提交事务时把变更写进 binlog。主库的 dump 线程把 binlog 发给从库；从库的 IO 线程把它写到 relay log，再由 SQL 线程重放。现在默认多用 row 格式，记录的是行变更。

异步复制时，主库写完 binlog 并提交就返回，从库稍后才拉。主库在日志传走前宕机，已返回成功的事务可能丢。半同步要等至少一台从库收下日志，主库才向客户端返回成功；从库可能还没执行，所以读从库仍会看到旧数据。等太久会退回异步。

延迟先不要只看 Seconds_Behind_Source。IO 线程已经停了、SQL 线程却把现有 relay log 放完时，这个值可以是 0。更稳的是比较主从 GTID 的差距，或写一张心跳表，看从库读到的时间和主库写入时间差多少。

优化针对回放慢的原因：

1. 拆开大事务。一个事务改几十万行，从库要等它整段回放完。
2. 打开并行回放。同一组在主库提交的事务之间没有写冲突，从库可以并行执行；按写入集合还能再提高并行度。
3. row 格式靠主键或唯一键定位行。表没有主键时，从库回放可能变成全表扫描，延迟会非常明显。
4. 从库的磁盘和索引不能比主库差。延迟超过阈值的从库要暂时移出读流量。

无写入时仍在落后，先看从库是不是正在做备份，或某一条更新因为缺索引在从库特别慢。

### 8. 线上遇到一个慢查询，你的排查思路是怎样的？

**参考答案**

先拿到完整语句和当时的耗时，再区分是执行慢、等锁，还是在等连接和磁盘。

1. 从慢查询日志或性能平台取出 SQL、参数、扫描行数和发生频率。默认的慢查询阈值常常是 10 秒，更短的回归问题要临时降低阈值，或直接看性能视图。把真实参数代回去。
2. 用 explain 看访问类型、用到的索引、估计行数和 Extra。全表扫描、Using filesort、Using temporary 要继续追。估计行数和真实耗时差很多时，再用 explain analyze 看实际执行，它会把语句跑一遍，只能对安全的查询使用。
3. 核对索引是否匹配条件。联合索引看最左前缀，列上套函数、发生隐式类型转换、前置模糊匹配，都会让索引用不上。选出大量行再回表，也会慢。
4. 执行计划正常但时间很长，就查锁和资源。看是否有未提交事务占着行，缓冲池命中是否异常，磁盘是否打满，统计信息过旧是否让优化器选错索引。
5. 改动按收益排。先收窄扫描范围或补上匹配的索引，再改写深分页，把大偏移量换成按主键续取。确认不是锁等待之后，才考虑拆表。

改完用同一组参数对比扫描行数和耗时。新索引对写入的影响要一起评估。

### 9. JVM 调优你有哪些实践经验？常用的监控和诊断工具有哪些？

**参考答案**

调优先有证据。先分清是停顿尖刺、回收太频繁，还是内存持续上涨，再改一个因素，用同一段流量对比。

工具按场景选：

1. 看趋势用 jstat -gcutil，观察各代占用、回收次数和耗时。线上长期看 GC 日志，JDK 9 以后用 -Xlog:gc*，配合进程的 CPU、堆和停顿指标。
2. 看线程用 jcmd Thread.print 或 jstack。低开销地看热点，优先 JFR、async-profiler 或 Arthas。
3. 看谁占着堆，用 jcmd 做堆转储，再用 MAT 看支配树。堆转储会停顿，不作为第一步。
4. 元空间上涨查动态类生成；直接内存上涨查 NIO、Netty 是否释放。这两部分都不在普通堆里，只加大 -Xmx 看不到。

常见处理：

1. 年轻代回收过密，先看分配速率和对象是不是本可以短命。把停顿目标交给 G1 之前，先去掉无意义的大对象分配。MaxGCPauseMillis 是目标，不是保证。
2. 内存一直涨，从堆转储里找仍被引用的缓存、监听器和未关闭的资源。先加堆只会把宕机推迟。
3. 容器里显式设置堆上限，给线程栈、元空间和堆外内存留余量。JDK 能识别容器内存限制，也不能把堆设成容器上限。

没有基线时，不同时改堆大小、收集器和代的比例。

### 10. 在云原生和容器化趋势下，你对 K8s 有哪些了解？它解决了什么问题？

**参考答案**

Kubernetes 解决的是容器跨很多机器之后，怎样部署、恢复、扩容和找到彼此。镜像怎么打包是容器运行时的事，K8s 负责让声明的副本数和实际运行的 Pod 一致。

1. 自愈和调度。Deployment 写明要几个副本，节点故障或 Pod 退出后，控制器会在仍有资源的节点上再拉起。调度按 CPU、内存的 request 来放，不按程序自己的线程数。
2. 稳定入口。Pod 地址会变，Service 给一组 Pod 固定的访问方式。就绪探针没通过的 Pod 不接流量；存活探针失败才会重启。JVM 启动慢时还要单独的启动探针，避免还没起来就被重启。
3. 发布。滚动更新按批次换镜像，失败可以回到上一版。配置放在 ConfigMap 和 Secret 里，和环境镜像分开。
4. 伸缩。HPA 按 CPU 或自定义指标增减 Pod 数。它扩的是副本，不会把单个 JVM 的堆自动调大。有状态服务用 StatefulSet 保持稳定标识，数据放在独立的卷里。

K8s 不负责事务、索引和缓存一致性。Java 进程还要处理 SIGTERM：收到信号后停止接新请求，把已经接住的请求做完再退出。探针要打真实的健康检查，进程还在不代表依赖可用。

### 11. 如何设计一个高并发、高可用的秒杀系统？请简述核心思路。

**参考答案**

秒杀要让真正进入下单的请求接近库存量，并把超卖挡在数据库条件更新上。页面 QPS 不能拿来当数据库的容量。

1. 页面静态化，走 CDN。活动开始前不发下单资格；开始时发放数量受控的令牌，没拿到的请求直接失败。
2. 网关按用户和活动限流，并限制单用户购买次数。验证码用来提高脚本成本，代替不了限流。
3. Redis 用 Lua 判断库存并预扣，成功才写入订单消息。Lua 保证判断和扣减是原子的。Redis 是削峰，不是最终账本。
4. 订单服务按自己的能力消费消息。数据库更新写成 stock = stock - 1 且 stock >= 1，影响行数为 0 就失败。用户和活动的唯一约束挡住重复下单。
5. 预扣成功但进程在发出消息前退出，会造成少卖。用对账把 Redis 和数据库的差额补回来。支付超时用延迟消息归还库存，归还按订单号幂等。
6. 热点 key 可以把库存分到多段，降低单 key 争用。段与段之间不必完全均匀，总数仍由数据库兜住。

Redis 或消息队列异常时，直接拒绝新的秒杀，不要同步打到数据库。容量按库存写入能承受的速度计算，上线前做一次包含下游的压测。

### 13. 你认为 AI 大模型（如你正在使用的技术）会对未来的软件开发模式产生什么影响？

**参考答案**

大模型会把从零写样板代码，变成先写清约束、再生成、然后验证。责任仍然在工程师，模型不能当资金和库存的最终裁决。

1. 写代码的重心会移动。增删改查、测试骨架、SQL 草稿和重构建议可以由助手出第一版。人更该花时间在接口契约、并发、事务和失败路径上。
2. 评审标准会变。生成的代码默认不可信，评审要看它是否满足约束、有没有越权访问和注入，不能只看格式。没有测试和日志的生成结果，不能因为「能跑」就进主干。
3. 系统里会多出检索、工具调用和异步任务。模型输出不稳定，所以要有超时、降级和人工入口。下单、扣款、改权限仍然走原来的确定性代码，模型至多帮助整理信息和草稿。
4. 对人的要求更偏判断。能把问题拆开、能看出答案错在哪，比记住更多 API 重要。不理解事务和一致性的人，用助手会更快地写出错误系统。

可以结合自己正在用的助手举一个例子：它帮你节省了哪一步，你又在哪一步抓住过它的错误。没有这种例子，就不要声称它已经能独立交付。

### 14. 手写算法：实现一个 LRU 缓存机制。

**参考答案**

用哈希表加双向链表。哈希表按 key 找到节点，做到 O(1) 查找；链表维护使用顺序，表头是最近使用的，表尾是最久未使用的。

get 找不到返回 -1，找到就把节点移到表头并返回值。put 时 key 已存在，就更新值并移到表头；不存在就插入表头。容量超出时删除表尾节点，并同时删掉哈希表中的项。只改一边会留下悬空数据。

get 和 put 都是 O(1)，空间 O(capacity)。容量按正整数处理。下面的实现不是线程安全的；要并发使用，需要在外面加锁，或者确认面试官允许使用现成结构。

Java 里也可以用 LinkedHashMap，把 accessOrder 设为 true，并在 removeEldestEntry 里按容量淘汰。手写的意义是把「查找」和「顺序」两套结构的更新说清楚。

```java
public class LRUCache {
    private final int capacity;
    private final java.util.Map<Integer, Node> map = new java.util.HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node eldest = tail.prev;
            remove(eldest);
            map.remove(eldest.key);
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private static class Node {
        final int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }
}
```

## 三面

### 1. 请做一个全面的自我介绍，包括你的技术成长路径。

**答题思路**

主管面听的是成长和协作，控制在 3 分钟。少报参数，多讲负责范围怎么变大。

1. 现在是谁：年限、方向、目前能独立负责的模块。
2. 成长路径按阶段，不要按学期。入门时你靠什么把第一块功能做上线；后来开始负责哪条链路；现在别人会把什么问题交给你。
3. 每个阶段只留一个证据，例如一次你独立定位的故障，或一个你做出取舍的方案。
4. 补一句目前的短板，以及你正在怎么补。短板要具体，例如对容量评估还缺少线上数字，不要说「我追求完美」。
5. 收尾对到岗位：你能接手需求、按规范交付，也能在出问题时把链路讲清楚。

学校只作为起点一句带过。不要编公司、职级和项目名；用你真实经历里的阶段替换上面的空位。

### 2. 在你过往的经历中，遇到的最大的技术挑战是什么？是如何解决的？

**答题思路**

只讲一件事，用「情况、任务、行动、结果」的顺序，重点放在行动里的取舍。

1. 情况：什么业务、影响面、当时的限制，例如不能停机、不能错账、时间只有一个发布窗口。
2. 任务：你个人负责哪一段。团队的成绩不要说成自己一个人做的。
3. 行动：你先查了什么，第一个判断是什么，后来哪个证据改变了判断。方案至少对比过一个替代做法，说明为什么没选它。
4. 结果：用你记得住的数量级说明恢复到了什么程度。补一句如果重来会提前做什么，例如补报警、补幂等或补压测。
5. 停在可追问的点上：数据怎么核对、回滚怎么做、怎么避免下次再出现。

挑战必须是技术问题。排期变化、沟通不畅留给后面的协作题。没有把握的数字换成「大约一个数量级」。

### 3. 如何看待加班？当项目进度紧张时，你会如何安排自己和团队的工作？

**答题思路**

先承认发布窗口和故障会占用正常下班时间，再讲你怎样避免把加班当成默认排期。

1. 态度：关键路径上的事，你会留下来把能发布的范围做完并验证。用加班掩盖估计失误，不能当计划。
2. 紧张时先重排范围。列出必须上线、可以降级、可以推迟的三列，和负责人确认日期和砍掉的部分。先加时间、不减范围，后面还会再超时。
3. 自己的安排：先做阻塞别人的接口和数据变更，留下可回滚的步骤，不在深夜上没验证过的大改。
4. 团队的安排：只有关键路径上的人留下，其他人为第二天的验证做准备。进度每天对齐风险，不等到最后一天一起熬。
5. 质量底线：资金、权限、数据迁移没有验证就不进当夜发布。这个边界提前说，比临时拒绝更站得住。

不要回答「绝不加班」，也不要回答「加班代表态度」。主管要听的是你能不能在紧的时候仍然按优先级交付。

### 4. 在团队协作中，如果你和同事（或上级）的技术方案有分歧，你会如何处理？

**答题思路**

按「对齐目标、对比证据、留下决策、执行到底」讲。分歧题最怕只说「我会沟通」。

1. 先复述对方要达成的目标，确认两边是目标不同，还是目标相同、路径不同。目标不同就先让负责人定目标。
2. 把两个方案写成同一张对比：复杂度、失败时的影响、上线步骤、能不能回滚。用一次故障场景说明，少用「业界都这么做」。
3. 听取同事的信息差。对方更熟存量数据或发布窗口时，把这个约束放进方案，而不是只坚持自己更优雅的设计。
4. 决策权在上级时，把风险写清楚后接受拍板。拍板之后按选定方案做完，不在实现时偷偷改回自己的做法。
5. 涉及丢数据、权限放大或无法回滚时，要求把风险和回滚步骤留在评审记录里再动手。这是对结果负责，不是固执。

举一个真实的小分歧最好。没有例子，就讲你会如何组织这场对比，不要编一个没发生过的争吵。

### 5. 你对自己的职业规划是怎样的？未来 3 年希望达到什么样的目标？

**答题思路**

规划要能和这个岗位接上，讲能力，不讲职级和薪资。

1. 近一年：独立负责一个模块，从需求、设计、上线到线上排障都能闭环。目标是别人交给你的问题，你能定位到具体一层。
2. 三年：在一条业务链路上能做方案，覆盖数据模型、缓存、消息和失败补偿，并能带一个新人把需求做完。深度放在你已经接触过的领域，不要同时说想成为架构师、算法专家和管理者。
3. 和当前机会的关系：先把交付质量做稳，在真实项目里把上面的能力练出来。这个岗位能接触到规范的研发流程和较大的业务系统，所以它是路径的一段，而不是过渡。
4. 补短板的方式要可检查，例如每季度把一次线上问题写成复盘，或把一个模块的容量和依赖画清楚。

不要报具体职级、头衔和薪酬数字。面试官追问「做到什么算达到」，用能独立设计的范围来回答。

### 6. 为什么选择华为 / 这个岗位？你对我们有什么了解？

**答题思路**

讲你能对上的事实和你的工作方式。只讲你真的了解的部分，不要背介绍页。

1. 对公司和业务：选择一条你说得出来的公开业务，例如云、终端或企业通信。讲你知道它的工程问题是规模、稳定和长期维护，不要罗列口号。说不出产品细节，就不要展开产品判断。
2. 对岗位：这个岗位要在既定流程里把需求交付到线上，看重设计能被评审、问题能被定位、结果能被交接。这和你想把一条后端链路做扎实的目标一致。
3. 对你自己：用前面项目里的一个证据说明，你适应规范、评审和值班，而不是只适合一个人写完就算结束。
4. 收尾：你希望在较大的系统和明确的质量要求下积累交付经验。不要贬低现有工作来抬高这次选择，也不要把原因说成只有城市或待遇。待遇留给人力资源环节。

了解程度被追问时，答得出就讲一个具体系统或公开技术实践；答不出就承认目前只了解到岗位职责，并说明你入职后打算先熟悉哪一层。

### 7. 你有什么问题想问我的？

**答题思路**

准备三个问题，按面试里还没讲清的信息挑两个。问工作怎么做、怎么算做好，用来判断岗位，也让主管看到你关心交付。

可以问：

1. 入职后前三个月主要交付哪类需求？我会先接触哪一段系统？
2. 团队现在的技术栈、发布方式和线上值守是怎样分工的？
3. 您觉得这个岗位最容易在什么地方出问题？做到什么程度，您会认为一个人已经独立？

避开三类问题：官网上一搜就有的公司介绍；只问加班和福利；把面试官的评价再问一遍来求认可。薪酬、合同和职级如果这次没有人力资源环节，留到对应环节，不在技术判断已经结束后展开。

主管回答之后，用一句复述确认，例如「所以前期主要是接现有服务的需求，发布由组里统一窗口做」。不要连着抛出一张问题清单。
