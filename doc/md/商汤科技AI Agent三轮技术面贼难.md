# 商汤科技AI Agent三轮技术面贼难

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

一面的面试官很抠细节，意图识别和 Chunk 切分都追着问边界，不像有些公司问完 ReAct 的定义就结束。这场面试不是靠背八股能过的，HashMap 这类题基本不问，直接围绕 Harness 循环和 State Reducer 深挖。算法题比较常规，但二面要求手写 Agent Loop 伪代码，不是背 LangGraph 文档能应付的。三面负责人很在意“你敢不敢拆 LangChain”：回答线上 LangChain 黑盒重试改不动、团队自己做了轻量 Harness 之后，对方明显感兴趣。HR 面正常聊，没有画饼。商汤这个 AI Agent 岗位是真正做工程的地方，不是套壳 Prompt 工程师的岗位。整体感觉：能扛过二面就算合格，三面比的是有没有在生产环境里踩过坑。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1.5 到 2 分钟，按“身份 → 经验 → 代表项目 → 岗位匹配”四段讲：

1. 一句话说明年限、方向和技术栈（后端 / AI 应用工程）。
2. 挑与 Agent 相关的 1 到 2 段经历，说清你负责的模块，例如 Harness 循环、RAG、工具层、评测。
3. 给出可验证的结果：稳定性、准确率、时延、成本等。数据要真实，没有就讲方法和取舍。
4. 最后收到“为什么适合这个岗位”，并留一个钩子（比如生产环境里的踩坑经历），引导面试官往你熟悉的方向追问。

### 2. 讲一个你落地过的 AI Agent 项目，你在里面负责哪一块（Harness / RAG / 工具层 / 评测等）

**答题思路**

用 STAR 加技术深度的结构，建议 3 到 4 分钟：

1. **背景和目标**：解决什么业务问题，为什么用 Agent 而不是固定流程。
2. **整体架构**：用户请求 → 意图识别 → 规划 / 循环 → 工具调用 → 检索 → 输出，画出主链路。
3. **你负责的部分**：明确边界，只讲自己做过的，比如循环控制与终止条件、上下文管理、工具 Schema 与参数校验、检索与重排、评测与埋点。
4. **难点与取舍**：挑 1 到 2 个具体问题，说明现象 → 定位 → 方案 → 结果，例如工具调用失败重试、检索不准、循环不收敛。
5. **结果与反思**：指标变化、上线后的问题、下一步改进。

准备好被追问：为什么这样选型、哪里出过事故、怎么评测。不要编造没做过的内容。

### 3. Agent 和传统 LLM 工作流（Workflow）本质区别是什么，什么场景不该用 Agent

**参考答案**

本质区别是控制流由谁决定：Workflow 的步骤和分支由代码预先写死，LLM 只是其中的一个节点；Agent 由 LLM 在运行时根据观察结果动态决定下一步做什么、调用哪个工具、何时结束。

- Workflow：确定性高、可预测、易测试、时延和成本稳定，但灵活性差。
- Agent：能处理开放任务和长尾情况，但是非确定性、步骤数不可控、成本和时延波动大、调试难。

不该用 Agent 的场景：

1. 流程固定、步骤可枚举（审批流、固定 ETL、固定模板问答）。
2. 对时延、成本、SLA 有严格上限的在线链路。
3. 合规或资金类操作，要求行为严格可审计、可复现。
4. 单次 LLM 调用加一点检索就能解决的问题。

实践上通常是“Workflow 为骨架，在不确定的局部嵌入 Agent”，并用步数上限、超时和人工确认兜底。

### 4. 意图识别在你项目里是怎么做的，规则路由、小模型分类、还是 LLM 路由，各自边界在哪

**参考答案**

三种方式各有适用范围，常见做法是分层组合。

- **规则路由**（关键词、正则、命令前缀）：零成本、微秒级、完全可控，适合固定指令和高精度场景；缺点是泛化差，维护成本随规则数增长。
- **小模型分类**（fastText、BERT 类、Embedding 加线性分类器）：延迟低、成本低、输出带置信度，适合意图集合固定且有标注数据的场景；缺点是新增意图要重新标注训练，遇到集合外（OOD）的输入容易误判。
- **LLM 路由**：零样本或少样本就能覆盖长尾和复杂表达，还能同时抽取槽位；缺点是延迟高、成本高、输出有随机性，需要约束输出格式。

推荐流程：规则命中直接走 → 未命中走小模型 → 置信度低于阈值或判为“其他”时交给 LLM，仍不确定就反问用户。需要强调：设置“未知 / 其他”类别、阈值要用验证集标定，并且线上持续抽样标注，监控误路由。

### 5. 多轮对话里用户说“刚才那个改成 MySQL”，你怎么把指代消歧到前一轮的具体实体

**参考答案**

核心是维护结构化的对话状态，而不是只靠把历史原文塞给模型。

1. **实体记录**：每轮把抽取到的实体写入对话状态，包含类型、ID、名称、所在轮次、关键属性（如“订单库配置”“某张表”）。
2. **候选筛选**：“改成 MySQL”意味着被改对象应该是“数据库类型 / 存储选型”类实体，先按类型过滤，再按时间近邻优先排序。
3. **查询改写**：让 LLM 结合近几轮对话和实体表，把当前输入改写成自包含的指令，例如“把【订单服务的存储】从 PostgreSQL 改成 MySQL”，输出带实体 ID 的结构化 JSON，而不是自由文本。
4. **歧义处理**：候选多于一个且得分接近时，反问并给出选项；单一候选但属于高风险修改时，回显确认。
5. **校验**：改写结果要校验实体 ID 真实存在、类型与操作匹配，再进入工具调用。

容易漏的点：指代消解要放在意图识别和槽位抽取之前或同时做，并且要处理“它”“那个”“上一个”“第二个”这类不同形式。

### 6. ReAct 和 Plan-and-Execute 的取舍，长任务里你为啥选其中一个

**参考答案**

ReAct 是“思考 → 行动 → 观察”逐步循环，Plan-and-Execute 是先生成完整计划，再按步骤执行，必要时重规划。

- **ReAct**：每一步都能根据最新观察调整，适应性强，适合探索性、环境不确定的任务；缺点是每步都调用大模型，历史越长 token 越多，容易目标漂移、陷入循环，难以并行。
- **Plan-and-Execute**：规划只调一次强模型，执行步骤可以用更小的模型或直接调用工具，步骤间可并行，整体可控、易于展示进度；缺点是计划在开始时基于不完整信息，环境变化会让计划失效，需要重规划机制。

长任务的常见选择：外层用 Plan-and-Execute 保证方向和进度，每个子步骤内部用短的 ReAct 处理局部不确定性，步骤失败或观察与预期不符时触发重规划，并设置重规划次数上限。选择依据要落到具体指标：任务完成率、平均步数、token 成本和失败类型。

### 7. Function Calling 参数错了（类型不对 / 枚举越界 / 必填写空）你们怎么拦截和回流给模型重试

**参考答案**

原则：模型输出一律不可信，执行前必须校验，校验失败不执行，把结构化错误返回给模型重试，且有次数上限。

1. **校验层**：用 JSON Schema 或 Pydantic 校验类型、枚举、必填、范围、长度、格式；必填值为空字符串也要视为缺失。
2. **语义校验**：schema 之外再检查实体是否存在、当前用户是否有权限、参数之间是否冲突。
3. **回流**：把错误作为 tool 消息（带对应的 `tool_call_id`）返回，内容要具体且结构化，例如 `{"error":"invalid_argument","field":"status","reason":"值不在枚举内","allowed":["open","closed"]}`，让模型知道怎么改。
4. **重试上限**：通常 2 到 3 次，超过后降级：向用户反问缺失信息，或终止并返回可读错误。
5. **预防**：开启支持的严格结构化输出（strict / 约束解码），Schema 描述写清约束，枚举尽量用 `enum`；对确定性的小问题（如 `"5"` 转 `5`）可以做保守的自动规范化，但不要猜测业务语义。

要记录每次校验失败的字段和模型，用于分析哪个工具的 Schema 描述需要优化。

### 8. RAG 切片（Chunk）切多大，语义切分和固定窗口怎么选，重叠窗口有什么用

**参考答案**

没有通用最优值，常见起点是几百 token 一段（例如 200 到 800 token），再用召回率、答案质量等评测集调参。文本类型不同差异很大：FAQ 适合小块，长文档、技术文档适合稍大块或按章节切。

- **固定窗口**：实现简单、大小可控，但可能把一句话或一段代码从中间切断。
- **语义 / 结构切分**：按标题、段落、句子边界，或 Markdown / 代码的语法结构切分（递归切分器是常见折中），语义完整，但块大小不均，需要设置上下限。

**重叠窗口**的作用是缓解边界处信息被截断：相邻块共享一小段（常见做法是块大小的 10% 到 20%），使跨边界的信息至少在一个块里完整出现。代价是索引变大、检索结果出现冗余，需要去重。

进阶做法：小块检索、大块（父块）送入模型，也就是 parent-child 检索；每个块带上文档标题、章节路径等元数据，提高检索准确度。

### 9. 向量检索召回了但不相关，你们怎么接 BM25 做混合检索，RRF 怎么融合

**参考答案**

向量检索擅长语义相似，但对专有名词、错误码、型号、人名等精确词匹配较弱；BM25 正好互补。做法：同一个查询并行走向量和 BM25 两路，各取 top N（比如 50），再融合。

**RRF（Reciprocal Rank Fusion）** 只使用排名，不使用原始分数：

\[
\text{score}(d)=\sum_{i}\frac{1}{k+\text{rank}_i(d)}
\]

其中 \(\text{rank}_i(d)\) 是文档在第 \(i\) 路结果中的名次，未出现在该路则不计入；\(k\) 是平滑常数，常见取 60。好处是不同路的分数量纲不同（BM25 分数和余弦相似度不可直接比较），用名次就不用做归一化。也可以对各路加权，或者先归一化再加权求和，但需要调参。

融合之后不要直接送给模型：再接 Rerank、元数据过滤和相关性阈值，把“召回了但不相关”的内容去掉。中文场景要注意分词器质量，会直接影响 BM25 效果。

### 10. Rerank 模型放在哪一层，为什么不能只靠 Embedding 余弦

**参考答案**

Rerank 放在召回之后、送入 LLM 之前：多路召回和融合先取 top 50 到 100 个候选，Rerank 精排后留下 top 3 到 10 个。

为什么不能只靠 Embedding 余弦：

1. Embedding 是双塔结构，查询和文档各自独立编码成向量，再算相似度，查询与文档之间没有 token 级交互，只能表达“主题相近”，难以判断“是否回答了这个问题”。
2. 否定、条件、数字等细节容易丢失，比如“不支持 X”和“支持 X”的向量很接近。
3. 余弦分数在不同查询之间没有统一的校准，难以设置通用阈值。

Rerank 常用 cross-encoder：把查询和文档拼在一起输入模型，输出相关度，精度更高，但每个候选都要完整推理一次，成本随候选数线性增长，所以只能用在小候选集上。这也是“召回求全、精排求准”的两阶段设计的原因。

### 11. Redis 在 Agent 系统里你拿它存过什么（会话状态 / 工具结果缓存 / 限流），用哪种结构

**参考答案**

常见用途与结构：

- **会话状态**：Hash 或 String（JSON）存当前对话状态、槽位；最近若干轮消息可用 List 或 Stream；设置 TTL 自动过期，大对象控制体积。
- **工具结果缓存**：String，key 由“工具名 + 规范化后的参数哈希”组成，TTL 按数据新鲜度设置；只缓存幂等的只读工具，并且 key 中要带上用户或租户维度，避免越权读到别人的结果。
- **限流**：固定窗口用 `INCR` + `EXPIRE`；滑动窗口用 ZSet；令牌桶用 Lua 保证原子性。可以按用户、工具、模型分别限流。
- **分布式锁和幂等**：`SET key token NX PX` 做锁，请求幂等键也可以放这里。
- **异步任务事件**：Stream 配合消费者组。

注意点：缓存要考虑击穿和一致性；会话状态如果需要持久恢复，不能只放 Redis，要有持久化落库方案；设置过期时间，避免 key 无限增长。

### 12. MySQL 存 Agent 执行轨迹（trace）怎么建表，中间步骤要审计怎么落

**参考答案**

按“一次运行 + 多个步骤”两层建模，类似 trace / span。

```sql
CREATE TABLE agent_run (
  run_id       VARCHAR(64) PRIMARY KEY,
  session_id   VARCHAR(64) NOT NULL,
  user_id      VARCHAR(64) NOT NULL,
  status       VARCHAR(16) NOT NULL,      -- running/success/failed/timeout
  model        VARCHAR(64),
  total_tokens INT,
  started_at   DATETIME(3) NOT NULL,
  finished_at  DATETIME(3),
  error_code   VARCHAR(64),
  KEY idx_user_time (user_id, started_at),
  KEY idx_session (session_id)
);

CREATE TABLE agent_step (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  run_id       VARCHAR(64) NOT NULL,
  step_no      INT NOT NULL,
  step_type    VARCHAR(16) NOT NULL,      -- llm/tool/retrieval/human
  name         VARCHAR(128),              -- 工具名或模型名
  input_json   JSON,
  output_json  JSON,
  status       VARCHAR(16) NOT NULL,
  latency_ms   INT,
  tokens       INT,
  error_msg    VARCHAR(512),
  created_at   DATETIME(3) NOT NULL,
  UNIQUE KEY uk_run_step (run_id, step_no)
);
```

审计要点：

1. **只追加**：步骤写入后不更新、不删除，业务账号不授予 UPDATE / DELETE 权限；需要更强的防篡改时可以加哈希链。
2. **脱敏**：手机号、密钥、令牌等落库前脱敏。
3. **大字段外置**：长文本或工具返回的大内容放对象存储，表里只存引用和摘要。
4. **容量**：按时间分区，冷数据归档；高频写入可以先写队列再批量落库，避免拖慢主链路。
5. 记录完整的 `tool_call_id`、参数、调用者身份和审批人，满足“谁在什么时候让 Agent 做了什么”的追溯。

### 13. AI Coding 场景里，让 Agent 改一个跨文件 Bug，上下文怎么裁剪，不会把整个仓库塞进 prompt 吧

**参考答案**

不会塞整个仓库。原则是“先定位，再按需读取，渐进式扩展”。

1. **入口定位**：从报错堆栈、失败的测试、用户描述里的符号和路径出发，用 ripgrep、符号索引、LSP（定义 / 引用查询）或 AST 找到相关函数。
2. **关系扩展**：沿调用链和依赖关系（调用者、被调用者、类型定义、相关测试）逐层扩展，每次只读需要的文件片段（按行范围），而不是整个文件。
3. **仓库地图**：提供精简的目录结构、模块签名摘要，让模型先“看地图”再决定读什么。
4. **语义检索**：对代码块做 embedding 检索作为补充，用于找不到明确符号时。
5. **预算管理**：给上下文设 token 预算，工具返回过长时截断并提示“可继续读取”；历史对话和旧的工具结果压缩或丢弃。
6. **验证闭环**：修改后运行相关测试或类型检查，把失败信息的关键部分回传，再迭代。

容易漏的点：要让模型知道哪些内容被截断了，否则它会误以为已经看全了；修改前先读取最新文件内容，避免基于过期上下文改动。

### 14. 手撕算法：给一段括号字符串，判断是否是合法括号序列（顺手问：顺带输出最长合法子串长度）

**参考答案**

**思路**：

- 合法性判断：用栈。遇到左括号入栈，遇到右括号时栈顶必须是对应的左括号，否则非法；遍历结束栈必须为空。时间 O(n)，空间 O(n)。
- 最长合法子串（仅 `(` 和 `)`）：栈中存下标，并先放入哨兵 `-1`。遇到 `(` 就压入下标；遇到 `)` 先弹栈，若栈空则把当前下标作为新的哨兵压入，否则用当前下标减去栈顶下标更新最大长度。时间 O(n)，空间 O(n)。

```python
def is_valid(s: str) -> bool:
    pairs = {')': '(', ']': '[', '}': '{'}
    stack = []
    for ch in s:
        if ch in '([{':
            stack.append(ch)
        elif ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
    return not stack


def longest_valid(s: str) -> int:
    """只含 '(' 和 ')' 时的最长合法括号子串长度"""
    stack = [-1]          # 哨兵：最近一个无法匹配的位置
    best = 0
    for i, ch in enumerate(s):
        if ch == '(':
            stack.append(i)
        else:
            stack.pop()
            if not stack:
                stack.append(i)
            else:
                best = max(best, i - stack[-1])
    return best


# is_valid("{[()]}") -> True；is_valid("([)]") -> False
# longest_valid(")()())") -> 4；longest_valid("(()") -> 2
```

边界：空串视为合法，长度为 0；字符串中出现非括号字符时要先和面试官确认是忽略还是判非法。

## 二面

### 1. 自我介绍

**答题思路**

二面的自我介绍要比一面更偏技术、更短（约 1 分钟），因为面试官已经看过一面的记录：

1. 一句话背景和年限。
2. 直接点出与岗位最相关的项目和你的核心职责（循环设计、状态管理、工具层、评测）。
3. 说一个能体现工程深度的点，例如线上稳定性、成本优化、框架取舍。
4. 把话题引向你最擅长的部分，方便后面被深挖时发挥。

### 2. 把你一面那个 Agent 项目再讲细点，哪一段是你自己设计的 Harness 循环

**答题思路**

重点是讲清“循环是怎么控制的”，建议按下面的顺序讲，只讲你实际做过的：

1. **循环结构**：输入（消息、工具列表、状态）→ 调用模型 → 解析输出（工具调用或最终答案）→ 执行工具 → 把观察写回上下文 → 判断是否终止。
2. **终止条件**：最大步数、总超时、模型给出最终答案、重复调用检测、预算（token / 费用）耗尽。
3. **异常处理**：模型输出格式错误、工具超时或报错、参数校验失败的重试和降级策略。
4. **上下文管理**：历史压缩、工具结果裁剪、状态怎么持久化。
5. **可观测性**：每一步的 trace、日志、指标，以及怎么用它定位线上问题。
6. **取舍**：为什么这样设计，遇到过哪些线上问题，后来怎么改。

准备好回答“如果让你重做会改什么”，这个问题能体现反思能力。不要编造细节，没做过的部分直接说明是方案设想。

### 3. LangChain 和 LangGraph 在你项目里分别承担什么，为什么后期要切到 LangGraph

**参考答案**

两者定位不同：

- **LangChain**：偏组件和集成层，提供模型接口、Prompt 模板、工具抽象、检索器、输出解析以及大量第三方集成，早期的 Chain 偏线性的“串联”。
- **LangGraph**：偏编排运行时，把流程建模成有状态的图（节点、边、共享状态），原生支持循环、条件分支、并行、检查点持久化、中断恢复（人工介入）和流式输出。

后期切到 LangGraph 的典型原因：

1. 需要循环和条件跳转（检索失败后重规划、反思重试），线性链难以表达。
2. 需要显式的、可检查的状态，而不是隐式地在各步之间传参。
3. 需要断点恢复、人工审批、长任务失败后从检查点继续。
4. 需要更细粒度的可观测和可控性（每个节点的超时、重试）。

补充：两者不是互斥关系，LangGraph 里的节点内部仍然可以使用 LangChain 的模型和工具组件。回答时结合自己项目里遇到的具体问题。

### 4. StateGraph 里 Node / Edge / State 三件套，你们 State 是 TypedDict 还是 Pydantic，Reducer 怎么写

**参考答案**

- **State**：图的共享数据结构，节点读取它并返回对状态的更新（部分字段）。
- **Node**：普通函数（或可调用对象），入参是当前 State，返回要更新的字段字典。
- **Edge**：节点之间的连接，分普通边和条件边（由函数根据 State 返回下一个节点名）。

**TypedDict 和 Pydantic 的选择**：TypedDict 轻量、无运行时校验开销，也是最常见的写法；Pydantic 在入口可以做类型校验和默认值，适合对数据质量要求高的场景，但有额外开销，并且要注意各节点返回的更新是否经过校验。两者都可以，重点是选择的理由。

**Reducer**：用 `Annotated` 给字段绑定合并函数，决定节点返回的更新如何和旧值合并。没有 Reducer 的字段默认是覆盖；列表类字段（如消息）要用追加或按 ID 合并，否则并行节点写同一个字段会互相覆盖或报冲突。

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph
from langgraph.graph.message import add_messages
import operator


def merge_docs(old: list, new: list) -> list:
    """按 id 去重合并检索结果"""
    seen = {d["id"]: d for d in old}
    for d in new:
        seen[d["id"]] = d
    return list(seen.values())


class AgentState(TypedDict):
    messages: Annotated[list, add_messages]       # 按消息 id 追加或更新
    docs: Annotated[list, merge_docs]             # 自定义合并
    steps: Annotated[int, operator.add]           # 每个节点返回 1，自动累加
    final_answer: str                             # 无 Reducer：覆盖
```

Reducer 应该是纯函数、结果不依赖执行顺序（并行节点的写入顺序不固定），并且要考虑幂等和去重。

### 5. Conditional Edge 怎么避免 Agent 在“检索-重规划”之间死循环，最大步数和外层 timeout 谁兜底

**参考答案**

死循环要靠多层防护，而不是只靠一个全局上限。

1. **State 内的计数器**：记录 `retrieve_count`、`replan_count`，条件边函数中先判断，超限则直接路由到“用已有信息作答或承认信息不足”的节点。
2. **进展检测**：如果本轮检索的查询和上一轮相同，或没有产生新的文档、结果相似度没有提升，就认为没有进展，直接退出循环。
3. **查询改写要有变化**：重规划时要求换角度（扩展、拆分、换数据源），并记录已尝试过的查询，避免重复。
4. **图级别的递归上限**：LangGraph 有 `recursion_limit` 配置，超过会抛出 `GraphRecursionError`，要显式设置并捕获，返回友好的降级结果。
5. **时间上限**：节点内部调用工具和模型设置各自的超时；整次请求有总截止时间（例如在外层用 `asyncio.wait_for` 或网关的 deadline）。

**谁兜底**：两者防护的对象不同，不能互相替代。最大步数限制的是“次数”，但单步可能卡住很久；超时限制的是“时间”，但不能阻止在时间内高频空转。最底层兜底应该是外层总超时（保证一定会返回），步数上限负责防止成本失控；两者都要有，并且单步超时 < 整体超时。

### 6. 多 Agent 编排：Orchestrator-Worker、Supervisor、Pipeline 三种你用过哪种，商汤这种多模态场景你会怎么分角色

**参考答案**

三种模式的区别：

- **Pipeline**：固定顺序的阶段（例如解析 → 检索 → 生成 → 校验），确定性强、易测试，适合步骤固定的任务。
- **Orchestrator-Worker**：中心节点动态拆分任务并分派给 Worker，再汇总结果；子任务数量和内容事先不确定时适合。
- **Supervisor**：主管 Agent 在多个专长 Agent 之间反复路由，每轮根据当前状态决定下一个由谁处理，适合需要来回协作的任务。

回答“用过哪种”时，要说清自己实际用过的，并给出选择理由和遇到的问题（比如主管路由出错、上下文在 Agent 之间传递丢失）。

多模态场景的角色划分示例：

1. **路由 / 规划**：判断任务类型，拆解子任务。
2. **感知类 Worker**：图像或视频理解、OCR、语音转写，各自封装成工具或子 Agent。
3. **检索 Worker**：知识库、文档检索。
4. **推理与汇总**：融合多模态结果生成答案。
5. **校验 / Critic**：核对事实一致性、格式、安全。

权衡：Agent 数量越多，通信、延迟和成本越高，调试越难。能用一个 Agent 加多个工具解决的，就不要拆成多 Agent；拆分的依据应该是上下文隔离、权限隔离或并行加速。

### 7. Agent 之间通信走共享 State 还是消息总线，Kafka 在这里能不能用，什么时候该用 RocketMQ

**参考答案**

**选择依据是 Agent 是否在同一个进程或同一次编排内。**

- **共享 State**：同一次编排内的 Agent 通过共享状态传递，简单、类型清晰、方便做检查点和回放。缺点是状态会膨胀，所有 Agent 都能看到全部内容，需要控制可见范围。
- **消息总线**：Agent 作为独立服务、需要异步、跨团队部署、长耗时任务或需要削峰时，通过消息队列通信，解耦但引入最终一致性、幂等和排序问题。

**Kafka 能不能用**：能。适合高吞吐的事件流、需要回放和保留历史的场景；同一个 key（如 session_id）进入同一分区可以保证局部有序；消费者组便于水平扩展。局限：没有原生的单条消息延迟投递、没有内置的重试队列和死信队列（需要用重试 topic 自己实现）、同一分区内一条消息处理慢会阻塞后面的消息。

**RocketMQ 更适合**：需要延迟消息（例如定时重试、超时检查）、事务消息、内置重试和死信队列、按 tag 过滤、顺序消息的业务型异步任务。

没有这些特殊需求，团队已有 Kafka 基础设施时优先复用；无论选哪个，都要做消费端幂等。

### 8. 意图识别模块线上 badcase：用户说“把上周报表发我”但没说发哪、发给谁，Agent 该堵住还是反问还是默认

**参考答案**

结论：按风险和信息可恢复性决定，不能一刀切。

1. **先尝试从上下文和记忆补全**：“发我”里的“我”可以由登录身份确定接收人；“上周报表”可以在报表系统中按时间检索。能唯一确定的就不需要问。
2. **有多个候选时给选项**：例如检索到多份上周报表，列出让用户选，而不是随便挑一份。
3. **有副作用的操作（发送、删除、付款）**：关键参数缺失或不确定时必须反问或回显确认，不允许静默默认。发送到外部地址、发送敏感内容尤其要确认。
4. **只读、低风险的操作**：置信度高时可以采用合理默认，并在回复里明确说明“已按 X 处理，如需修改请告知”。
5. **不要直接拒绝（堵住）**：直接报错体验差，除非缺失的信息无法通过任何方式获得或涉及权限问题。

实现上用槽位定义：每个工具有必填槽位、可选槽位、默认值策略和风险等级，对话管理按槽位状态决定“执行 / 反问 / 确认”。反问要具体（“请问发给谁？”），一次尽量问清缺失的所有槽位，避免多轮追问。

### 9. RAG 知识库有权限隔离（普通员工不能查高管薪酬），检索层怎么把 ACL 带进向量召回

**参考答案**

核心原则：权限必须在检索阶段强制执行，并且用户身份来自认证系统，不能由 LLM 或用户输入决定。

1. **入库时打标**：每个 chunk 带上文档 ID 和权限元数据（可见的用户 / 组 / 角色、密级、租户）。
2. **检索时前置过滤（pre-filter）**：把当前用户的身份和所属组转成过滤条件，随查询一起下推给向量库（元数据过滤）。不要先召回 top K 再过滤，否则无权限内容占满名额会导致有权限的结果被挤掉，召回量不足，而且存在泄漏风险。
3. **过滤与近似检索的兼容**：过滤命中比例很低时 HNSW 之类的索引召回会下降，可以按租户或密级分区（collection / partition）、选择支持过滤检索的实现，并评估召回率。
4. **权限变更同步**：文档权限变化后要更新对应 chunk 的元数据；权限复杂、变更频繁时，可以在 chunk 里只存文档 ID，查询时向权限服务查可见文档集合（可加短 TTL 缓存）。
5. **二次校验**：最终进入 prompt 前，再按文档 ID 校验一次权限，作为兜底。
6. **其他泄漏面**：缓存的 key 要包含权限维度；日志、引用来源、重排结果、摘要里都不能暴露无权限内容；Agent 的工具调用同样要用用户身份而不是服务账号。

### 10. Agentic RAG 和普通 RAG 差异，检索失败要不要触发重新规划，举你项目里的例子

**参考答案**

**差异**：普通 RAG 是固定的“检索一次 → 拼上下文 → 生成”；Agentic RAG 由 Agent 控制检索过程：决定要不要检索、检索什么、用哪个数据源或工具、对结果进行相关性评估，不满意就改写查询、拆分子问题或换数据源再检索，最后再生成。

- 优点：能处理多跳问题、复杂问题和检索不准的情况，质量上限更高。
- 缺点：延迟和成本更高，行为更难预测，需要步数和超时的约束。

**检索失败要不要重新规划**：要，但要有条件和上限。判断“失败”的方式：相关性评分低于阈值、检索结果为空、Rerank 最高分很低、LLM 评估无法回答。触发后的动作：查询改写（同义词、拆分子问题）、放宽过滤条件、换数据源或检索方式（向量 / BM25 / 结构化查询）。重规划次数要限制，仍然失败就明确回答“知识库中没有找到相关信息”，不要硬编。

举例时用你自己项目里的真实场景；如果没有，可以用通用例子说明：用户问“A 产品 3.2 版本的限流配置”，首次检索只召回 3.0 版本文档，评估发现版本不匹配，于是加上版本过滤条件重新检索。

### 11. AI 工作流里“人工确认节点”怎么嵌进 LangGraph，HITL 断点恢复状态存哪

**参考答案**

做法：在需要确认的位置暂停图的执行，把待确认内容展示给人，人给出结果后从断点继续。

1. **暂停**：在节点内调用 `interrupt(payload)`，或在编译时用 `interrupt_before` / `interrupt_after` 指定节点。必须配置 checkpointer，否则无法保存和恢复。
2. **标识会话**：调用图时通过 `config={"configurable": {"thread_id": ...}}` 区分不同的执行实例。
3. **恢复**：人工确认后，用 `Command(resume=人工输入)` 以同一个 `thread_id` 再次调用，图从暂停点继续，`interrupt()` 返回的就是人工提供的值。

```python
from langgraph.types import interrupt, Command

def approve_node(state):
    decision = interrupt({"action": state["pending_action"], "tip": "是否批准？"})
    return {"approved": decision == "yes"}

# 首次调用会在 interrupt 处暂停；之后用同一个 thread_id 恢复：
# graph.invoke(Command(resume="yes"), config={"configurable": {"thread_id": "t1"}})
```

**状态存哪**：开发环境可以用内存 checkpointer；生产环境要用持久化存储（常见是 PostgreSQL，也有 Redis、SQLite 等实现），保证服务重启、多实例部署下仍然能恢复。

注意点：恢复时包含 `interrupt` 的节点会从头重新执行，所以 `interrupt` 之前的副作用必须幂等或放到暂停之后；要设置等待超时和过期策略；审批人的身份和审批记录要落库审计；审批人需要有相应权限。

### 12. 工具层接内部 RPC/HTTP，工具超时、502、限流分别怎么处理，会不会把错误原文全喂回 LLM

**参考答案**

分情况处理：

- **超时**：每个工具设置合理的超时（连接和读取分开）。只读或幂等的调用可以有限次重试（指数退避加抖动）；有副作用的调用重试前必须有幂等键，否则不要自动重试，因为超时不代表没有执行成功。
- **502 / 503 等上游暂时性错误**：有限次重试，配合熔断器避免持续冲击故障服务，必要时降级（使用缓存、备用服务）。
- **限流（429）**：遵守 `Retry-After`，客户端侧也做限流和排队，不要立刻重试；多个 Agent 并发时需要做全局的限流或令牌桶。

**不要把错误原文全部喂回 LLM**，原因：

1. 浪费 token，干扰模型判断。
2. 可能泄露内部地址、堆栈、凭据等敏感信息。
3. 错误内容中可能夹带不可信文本，存在提示注入风险。

正确做法：把错误归一化成结构化信息再返回，例如 `{"error":"tool_timeout","retryable":true,"hint":"可稍后重试或换用其他方式"}`；完整的原始错误只写入日志和 trace 用于排查。对模型明确“哪些错误可重试，哪些应该告知用户”，同时限制模型层面的重试次数。

### 13. Elasticsearch 在 Agent 里除了 BM25 还能干啥，你们用 ES 做混合检索时向量字段怎么存

**参考答案**

ES 在 Agent 系统中除了 BM25 全文检索，还能做：

1. **结构化过滤和聚合**：按时间、类型、租户、权限等元数据过滤，统计聚合。
2. **向量检索**：`dense_vector` 字段配合 kNN 搜索（基于 HNSW），和全文检索组合成混合检索。
3. **文本分析**：自定义分词、同义词、拼音、模糊匹配、短语匹配、高亮。
4. **日志和 trace 检索**：存储并检索 Agent 的执行日志和审计数据。
5. **权限过滤**：在查询里带上 ACL 条件，与向量检索一起执行。

**向量字段存储**：在 mapping 中定义 `dense_vector`，指定维度，开启索引并设置相似度，同一个文档里同时保留文本字段（用于 BM25）和元数据字段。

```json
{
  "mappings": {
    "properties": {
      "content":   { "type": "text", "analyzer": "ik_max_word" },
      "title":     { "type": "text" },
      "doc_id":    { "type": "keyword" },
      "acl_groups":{ "type": "keyword" },
      "created_at":{ "type": "date" },
      "embedding": {
        "type": "dense_vector",
        "dims": 1024,
        "index": true,
        "similarity": "cosine"
      }
    }
  }
}
```

说明：中文分词用 `ik` 等插件需要单独安装；`dims` 要和 Embedding 模型的输出维度一致，各版本对最大维度、索引类型（如量化）的支持不同，使用前核对对应版本文档；混合检索的融合可以用 ES 提供的 RRF 能力（受版本和许可约束），或在应用层自己做 RRF；换 Embedding 模型后需要重建向量索引。

### 14. 手撕算法：实现一个最小可用 Agent Loop（伪代码也行）——输入 messages+tools，循环输出 thought/action/observation，直到 final_answer，要体现步数上限和异常退出

**参考答案**

**思路**：循环中每轮调用模型，若返回 `final_answer` 就结束；否则解析 `action`，执行工具，把观察结果追加到消息里继续。需要体现的点：

1. 步数上限和总超时。
2. 模型调用异常、未知工具、工具执行异常都要处理，并且转成观察结果反馈给模型，而不是让整个循环崩溃。
3. 重复调用检测，避免空转。
4. 退出时返回明确的状态（成功 / 达到步数上限 / 超时 / 模型异常）。

时间复杂度与步数成正比，最坏 O(max_steps) 次模型调用；每步上下文增长，实际要做压缩。

```python
import json
import time


def agent_loop(llm, tools, messages, max_steps=8, deadline_s=60.0):
    """
    llm(messages, tool_names) -> {
        "thought": str,
        "action": {"name": str, "args": dict} | None,
        "final_answer": str | None,
    }
    tools: {name: callable}
    """
    start = time.monotonic()
    seen = set()  # 已执行过的 (工具名, 参数)

    for step in range(1, max_steps + 1):
        if time.monotonic() - start > deadline_s:
            return {"status": "timeout", "steps": step - 1}

        try:
            out = llm(messages, list(tools))
        except Exception as e:  # 模型调用失败：真实系统里可先做有限重试
            return {"status": "llm_error", "error": type(e).__name__, "steps": step - 1}

        if out.get("final_answer") is not None:
            return {"status": "ok", "answer": out["final_answer"], "steps": step}

        action = out.get("action") or {}
        name, args = action.get("name"), action.get("args", {})
        messages.append({"role": "assistant",
                         "thought": out.get("thought", ""),
                         "action": action})

        key = (name, json.dumps(args, sort_keys=True, ensure_ascii=False))
        if key in seen:
            obs = {"error": "重复调用相同工具和参数，请换一种方式或给出最终答案"}
        elif name not in tools:
            obs = {"error": f"未知工具 {name}", "available": list(tools)}
        else:
            seen.add(key)
            try:
                obs = {"result": tools[name](**args)}
            except Exception as e:  # 工具异常转成观察结果，不让循环崩溃
                obs = {"error": type(e).__name__, "message": str(e)[:200]}

        messages.append({"role": "tool", "name": name, "observation": obs})

    return {"status": "max_steps", "steps": max_steps}
```

补充：生产版本还要加单步工具超时、工具参数校验、上下文压缩、token 预算、trace 记录，以及达到上限时让模型基于已有信息给出尽力而为的答案。

## 三面

### 1. 自我介绍

**答题思路**

三面面对的是技术负责人，自我介绍要突出“决策和影响力”：

1. 简述背景和年限（30 秒）。
2. 重点讲你主导或深度参与的 Agent 项目：为什么做、怎么选型、团队怎么分工。
3. 突出技术判断和生产经验：做过哪些取舍、线上出过什么问题、怎么复盘改进。
4. 简要提及协作和带人的经历。
5. 收尾说明你对这个岗位的理解和想解决的问题。

### 2. 你带队或主导的 Agent 项目，技术选型时 LangChain 生态 vs 自研 Harness 你怎么拍板的

**答题思路**

重点展示决策方法，而不是“站队”。可以按下面的顺序讲，内容必须基于你的真实经历：

1. **先讲决策维度**：业务复杂度、对稳定性和可控性的要求、团队能力、迭代速度、可观测性、框架升级和维护成本、锁定风险。
2. **用验证代替争论**：做过 PoC，用同一批评测集对比效果、延迟、成本、调试难度，而不是凭感觉。
3. **说明取舍**：框架在原型阶段上手快、生态丰富；但在生产环境里，重试策略、超时、状态管理、日志追踪等行为如果是黑盒，就难以定位和定制。自研 Harness 可控，但要承担开发和维护成本。
4. **折中方案**：只自研核心的循环和状态控制，模型、检索器、工具等通用组件仍使用成熟库；通过薄的抽象层隔离，保证可以替换。
5. **拍板和复盘**：谁参与决策、如何记录决策依据、上线后的验证结果，以及如果重新选择会怎么调整。

避免绝对化表述（“框架都不能用”），体现你对成本和风险的权衡。

### 3. Harness 工程里“上下文压缩”你们做了几层：滑窗、摘要、关键帧保留、工具结果裁剪，各自 token 节省多少

**参考答案**

这是分层的组合策略，先做便宜、确定性的，再做昂贵、有损的。

1. **工具结果裁剪**（通常收益最大）：对工具返回按字段白名单提取、截断长文本、表格只保留相关行、大内容存外部引用（仅保留摘要和读取句柄）。无损或低损，应当最先做。
2. **滑动窗口**：保留最近 N 轮完整消息，更早的内容移出；简单但会丢失早期关键信息，所以要和下面的手段配合。
3. **关键帧 / 关键信息保留**：始终保留系统提示、用户目标、约束条件、已确认的事实、待办清单等不能丢的内容（可以放在结构化状态里，而不是靠历史消息）。
4. **摘要**：把较早的对话和执行过程用模型压缩成摘要，有损且额外消耗一次模型调用，要防止摘要把关键细节（ID、数值、否定条件）丢掉，也要防止摘要累积失真。
5. **触发策略**：按 token 占用比例（例如接近上限的某个比例）触发，而不是每轮都压缩；注意压缩会破坏提示词缓存的前缀，需要权衡。

关于“各自节省多少 token”：这取决于任务和数据，没有通用数值，不应编造数字。正确的做法是做消融：在同一批任务上逐层开关，记录每层的平均 token、成本和任务完成率，并评估压缩前后的质量差异，用数据说明每层的收益和代价。

### 4. 多 Agent 系统评测怎么搞，单 Agent 准确率、工具调用准确率、端到端任务完成率分别怎么埋点

**参考答案**

评测要分层，才能定位问题出在哪一层。基础是完整的 trace：每次请求有 `run_id`，每个 Agent、每次模型调用、每次工具调用都是带父子关系的 span，记录输入、输出、耗时、token、状态。

- **单 Agent 准确率**：对每个 Agent 准备独立的黄金测试集（输入 → 期望输出或判定规则）。能规则判定的用规则（精确匹配、结构校验），开放文本用 LLM 评审加人工抽检校准。在 span 中记录该 Agent 的输入输出，离线回放评测。
- **工具调用准确率**：拆成几个指标：工具选择是否正确、参数是否正确（和标注的期望参数对比）、调用是否成功、是否有冗余或遗漏的调用。埋点位置在工具调用 span，记录工具名、参数、参数校验结果、返回状态。
- **端到端任务完成率**：定义明确的成功标准，最好是可自动验证的结果（目标状态是否达成，例如数据库里的记录、生成的代码是否通过测试），而不是只看最后一句回复。记录最终状态和失败归因。
- **辅助指标**：平均步数、总延迟、token 成本、人工介入率、重试次数、Agent 之间交接（handoff）的正确率。

方法上：离线用固定数据集做回归，线上对流量抽样打标并监控指标变化；按失败类型归因（规划错误、工具错误、检索错误、模型错误），才能知道优化哪一层。

### 5. 模型升级（Qwen 切 GLM 切自研）时 Agent 提示词和工具 Schema 要动哪些，回归测试怎么跑

**参考答案**

不同模型在指令遵循、工具调用格式、上下文长度等方面有差异，不能只换模型名。

**需要检查和调整的内容**：

1. **提示词**：系统提示的风格和长度、few-shot 示例、输出格式约束、角色标记和聊天模板（不同模型的 chat template 不同）。
2. **工具 Schema**：不同模型对 JSON Schema 的支持程度不同（嵌套对象、`enum`、`anyOf`、严格模式、并行工具调用、`tool_choice` 选项），工具描述的措辞也会影响选择准确率。
3. **推理参数**：temperature、top_p、停止词、最大输出长度、是否有“思考模式”及其输出格式。
4. **上下文和分词器**：窗口长度、token 计数方式变化会影响上下文压缩阈值和成本估算。
5. **输出解析**：工具调用返回格式、结构化输出的解析容错。

**回归测试**：

1. 用固定的黄金评测集在新旧模型上分别回放，对比单步指标（工具选择、参数准确率、格式合规率）和端到端任务完成率，设置通过门槛。
2. 针对历史线上 badcase 建立专项用例集。
3. 影子流量或灰度发布，对比线上指标（成功率、延迟、成本、人工介入率），并保留一键回滚。
4. 模型版本要固定（pin），避免供应商静默更新。
5. 提示词和 Schema 的修改走版本管理，每次变更都跑评测。

### 6. 意图识别模块从 LLM 路由回退到轻量分类模型，你们怎么定阈值，误路由率多少能接受

**参考答案**

阈值不是拍脑袋，要用带标注的数据和业务代价来定。

1. **准备标注集**：覆盖线上真实分布，包含集合外（OOD）和边界样本；LLM 路由的历史输出可以作为辅助标注，但需要人工抽检校准。
2. **选指标**：按意图分别看精确率、召回率，画 PR 曲线；分类器的置信度要先校准（比如温度缩放），否则分数不可信。
3. **按错误代价设阈值**：高风险意图（涉及写操作、付费、外发）使用更高的阈值，误路由代价低的意图可以较低。低于阈值的请求不直接执行，而是回落到 LLM 路由或向用户澄清。
4. **分层兜底**：轻量模型高置信直接路由，低置信交给 LLM，这样既保证成本，也限制误路由。
5. **线上监控**：持续抽样人工标注，监控各意图的路由分布、回落比例、用户纠正率，数据漂移时重训。

**误路由率能接受多少**：没有通用数字，取决于业务代价。关键是区分“错误能否被后续步骤发现和纠正”以及“是否有副作用”：只读、能纠错的场景可以容忍更高；涉及不可逆操作的意图应追求极低的误路由，并在执行前加确认步骤。回答时给出你们真实的数据和标准，不要编造。

### 7. RAG 召回冲突（两篇文档结论打架）Agent 怎么决断，接不接知识图谱做证据链

**参考答案**

先判断是不是真的冲突，再决定怎么处理。

1. **识别冲突**：很多“冲突”其实是适用条件不同（版本、地区、时间、对象不同），把条件对齐后并不矛盾。
2. **依据元数据裁决**：看来源权威性（官方文档 > 个人笔记）、时效性（新版本覆盖旧版本）、适用范围（版本号、地域）、是否已被废弃。这些元数据要在入库时就保存。
3. **无法裁决时如实呈现**：给出两种说法及其出处，说明存在分歧，必要时向用户追问关键条件（例如具体版本）；不要随机选择一个，也不要“平均”出一个折中结论。
4. **Agent 可以补充检索**：针对冲突点再查更权威的来源，或调用能直接验证的工具（查询真实配置、执行测试）。
5. **回答带引用**：每条结论都能追溯到文档，方便人工核实。

**要不要接知识图谱做证据链**：取决于场景。实体关系密集、需要多跳推理、需要可解释证据链的领域（合规、医疗、企业知识）有价值；但构建和维护图谱成本高，抽取质量会成为瓶颈。多数场景先用元数据加引用就够了，确有多跳和溯源需求再引入图谱，并先做小范围验证收益。

### 8. AI Coding Agent 跑 CI 前怎么防它把密钥写进代码提交，沙箱和权限边界怎么画

**参考答案**

核心思路是：让 Agent 根本拿不到长期密钥，并在提交链路上多重拦截。

**沙箱边界**：

1. 在隔离环境（容器，更强的用 gVisor 或 Firecracker 之类的轻量虚拟机）里运行，一次任务一个临时环境，用完销毁。
2. 以非 root 运行，文件系统只读，只有工作目录可写，限制 CPU、内存、磁盘和运行时间。
3. 网络默认禁用，或只允许访问白名单域名（包管理镜像、必要的 API），防止外传数据。
4. 不把宿主机的凭据、`~/.ssh`、云厂商凭据挂载进去。

**权限和密钥**：

1. 不把真实密钥放进环境变量或仓库。需要的凭据由工具代理注入，使用短期、最小权限、可吊销的令牌。
2. Agent 使用的 Git 令牌只能推送到特性分支和创建 PR，不能直接推送主干，主干开启分支保护，合并必须经过人工评审。
3. 对高危操作（删除、发布、改动权限、改 CI 配置）加人工确认。

**提交链路拦截**：

1. 提交前本地钩子和 CI 里做密钥扫描（如 gitleaks、trufflehog），再加上平台的推送保护。
2. 禁止或忽略 `.env`、密钥文件，Agent 读取这些文件的权限直接拒绝。
3. 对 diff 做检查，模型输出里匹配到密钥特征的内容拦截。
4. 一旦泄露：立即吊销并轮换密钥，清理历史，不能只靠删除提交。

### 9. Kafka 在 Agent 异步任务（长耗时代码生成 / 批量文档解析）里怎么解耦，消费幂等怎么做

**参考答案**

**解耦流程**：

1. 接口收到请求后，先在数据库创建任务记录（状态 PENDING，有唯一 `task_id`），再向 Kafka 发消息（key 用 `task_id` 或会话 ID），立刻返回 `task_id`。为避免“写库成功但发消息失败”，可以用事务发件箱（outbox）模式。
2. Worker 以消费者组消费，处理长任务，状态变化更新到数据库（RUNNING / SUCCESS / FAILED），进度和结果写入存储。
3. 客户端通过轮询、SSE、WebSocket 或回调获取结果。
4. 失败的消息进入重试 topic，多次失败进入死信 topic，人工或定时处理。

**长耗时消费的注意点**：处理时间超过 `max.poll.interval.ms` 会被判定消费者掉线触发再平衡，导致重复消费。常见做法是调大该参数，或消费线程只拉取消息，把任务交给工作线程池并配合暂停、提交 offset 的控制；任务特别长时，消息里只放任务 ID，由 Worker 自己管理租约和心跳。

**消费幂等**：Kafka 常见的投递语义是至少一次，所以消费者必须幂等。

1. **业务唯一键 + 状态机**：用条件更新，例如 `UPDATE task SET status='RUNNING' WHERE task_id=? AND status='PENDING'`，影响行数为 0 就说明已被处理，直接跳过。
2. **唯一索引去重**：把消息 ID 或任务 ID 写入去重表，唯一约束保证只处理一次。
3. **外部副作用带幂等键**：调用下游或第三方时传幂等键。
4. 先处理成功再提交 offset；Redis 的 `SETNX` 去重只能作为辅助，不能作为强保证（有过期和故障问题）。
5. Kafka 自身的事务和 exactly-once 只覆盖 Kafka 内部的读写，对外部系统的副作用仍然要自己保证幂等。

### 10. Redis 分布式锁在 Agent 并发占工具（比如只占一个浏览器实例）时够不够，Redlock 你信不信

**参考答案**

**单实例锁的做法**：`SET lock_key token NX PX ttl` 加锁，释放时用 Lua 脚本先比较 token 再删除，避免误删别人的锁。

**不够的地方**：

1. **锁过期但任务没结束**：浏览器任务耗时不确定，TTL 到了锁被释放，另一个 Agent 进来，就会同时操作同一个实例。需要看门狗续期（如 Redisson 的 watchdog），但进程卡顿（GC、网络暂停）时续期也可能失败。
2. **主从切换丢锁**：Redis 主从复制是异步的，主节点宕机前锁还没同步到从节点，故障转移后另一个客户端就能拿到同一把锁。
3. **没有 fencing token**：持锁者因为暂停而“以为自己还持有锁”，仍然去操作资源。

**Redlock**：在多个独立 Redis 节点上取得多数节点的锁来提高可用性。它在争议中的关键点是：依赖时钟和时间假设，没有 fencing token，在极端时序下仍可能出现两个持有者。因此：

- 如果锁只是为了“效率”（避免重复劳动，偶尔重复无大碍），单实例加续期或 Redlock 通常够用。
- 如果锁关系“正确性”（重复占用会造成严重后果），不应只信任 Redis 锁，需要 fencing token 配合资源侧校验，或使用强一致的协调服务（如 etcd、ZooKeeper）或数据库行锁。

**浏览器实例这个场景**：更合适的设计是“实例池 + 租约”：用数据库或协调服务记录实例的当前持有者、租约到期时间和单调递增的版本号；持有者定期心跳续约；实例侧（浏览器服务）在每次操作时校验令牌和版本号，过期的持有者会被拒绝；崩溃的持有者靠租约到期被回收。必要时用信号量限制并发数，而不是只用一把互斥锁。

### 11. 最近半年你学的最离谱或最有用的一项 Agent 相关技术是什么，怎么上手验证的

**答题思路**

这是考察学习能力和落地意识的问题，必须讲真实经历，不要编造。建议结构：

1. **选一个具体的技术点**：例如某种上下文管理方法、评测方法、工具协议、检索改进、沙箱方案。选一个你真的动手验证过的。
2. **为什么关注**：它解决了你遇到的什么具体问题。
3. **怎么验证**：写了最小可运行的 demo，设定对比基线和评测集，记录指标变化（准确率、成本、延迟），而不是只看官方示例。
4. **结论和边界**：哪些场景有效，哪些场景不适用，发现了什么坑。
5. **是否落地**：有没有引入项目，没有的话原因是什么。能说出局限和不适用场景，比一味夸赞更可信。

### 12. 给你一个完全没接触过的框架（比如新出的 harness runtime），你一周内怎么判断能不能上生产

**参考答案**

用“先评估风险，再做验证，最后给出结论”的方式，一周的节奏大致如下：

1. **第 1 天：了解和筛选**：看文档、示例、版本发布频率、维护者和社区活跃度、许可证、已知问题、有没有生产案例；读核心源码，弄清状态管理、重试、超时、并发模型。
2. **第 2 到 3 天：用真实场景做 PoC**：不要只跑官方示例，拿项目里最有代表性的一个流程完整实现，对比现有方案的效果、延迟、成本，同时记录开发体验和调试难度。
3. **第 4 天：故障和压力测试**：模型超时、工具报错、进程重启、并发压测，观察是否能恢复、有无资源泄漏、行为是否可预期。
4. **第 5 天：生产适配性**：可观测性（日志、trace、指标能否接入现有体系）、配置和密钥管理、多实例部署、状态持久化、版本升级的兼容性。
5. **第 6 天：安全和合规**：依赖审计、权限边界、数据是否外传、提示注入的防护能力。
6. **第 7 天：结论**：输出评估报告，包含收益、风险、迁移成本和退出方案（如何替换），给出“不上 / 小范围灰度 / 全量”的建议。

判断标准：能否定位问题、能否控制行为、有没有退出路径。通过后也先在非核心流程灰度，并设置回滚方案。

### 13. 你怎么带比你还懂 Prompt 的应届生，Agent 项目里代码权和提示词权怎么分

**答题思路**

体现的是技术管理和协作能力，要真诚、不贬低任何一方：

1. **态度**：承认对方在提示词上的专长，把它当成团队资源；我的价值在工程化、稳定性和线上经验，双方互补。
2. **带人方式**：明确目标和验收标准，先给小而完整的任务，及时反馈，通过代码评审和复盘传递生产环境的经验（超时、幂等、可观测、安全）。
3. **代码权和提示词权的划分**：
    - 控制流、状态管理、工具接口、Schema、校验、权限、重试等由工程代码负责，走正常的代码评审。
    - 提示词作为受版本管理的配置或资源，可以由熟悉的人负责迭代，但每次修改必须经过评测集回归（有门槛指标）才能合入，修改要可追溯、可回滚。
    - 以评测数据而不是个人判断来决定提示词好坏，减少争论。
4. **边界**：安全和权限相关的约束不能只写在提示词里，必须用代码强制执行；提示词不能绕过代码里的校验。
5. **成长**：给对方参与工程设计和线上排查的机会，也向对方学习提示词技巧，形成互相促进的关系。

### 14. 手撕算法：多轮对话状态机给定意图序列和槽位填充规则，输出最终可调用工具的参数 JSON（带缺槽反问逻辑）

**参考答案**

**思路**：

1. 为每个工具定义必填槽位、反问话术和校验函数。
2. 维护对话状态：当前工具、已填槽位。
3. 逐轮处理输入（意图加本轮抽取的槽位）：
    - 取消意图：清空状态；
    - 出现新的工具意图且与当前不同：切换工具并清空槽位；
    - 其他意图（如补充槽位）：合并本轮槽位，校验不通过的不写入，并标记要重新询问。
4. 每轮结束后检查缺失槽位：有缺失就输出反问（优先问第一个缺失的槽位，也可以一次问多个）；全部满足就输出工具名和参数 JSON，并重置状态。

时间复杂度：每轮 O(槽位数)，空间 O(槽位数)。

```python
import json

TOOLS = {
    "send_report": {
        "required": ["report_name", "recipient"],
        "ask": {
            "report_name": "请问要发送哪一份报表？",
            "recipient": "请问发给谁？",
        },
        "validators": {"recipient": lambda v: "@" in v},
    },
    "book_meeting": {
        "required": ["time", "attendees"],
        "ask": {
            "time": "请问会议什么时间开始？",
            "attendees": "请问有哪些参会人？",
        },
        "validators": {},
    },
}


def run_dialog(turns, tools=TOOLS):
    """turns: [{"intent": str, "slots": {...}}, ...]，返回每一轮的系统回复"""
    tool, slots, replies = None, {}, []

    for turn in turns:
        intent, new = turn.get("intent"), turn.get("slots") or {}

        if intent == "cancel":
            tool, slots = None, {}
            replies.append({"status": "cancelled"})
            continue

        if intent in tools and intent != tool:     # 切换到新的工具意图
            tool, slots = intent, {}

        if tool is None:                           # 还没有进入任何工具流程
            replies.append({"status": "no_tool"})
            continue

        spec, bad = tools[tool], []
        for k, v in new.items():
            if k not in spec["required"] or v in (None, "", []):
                continue
            check = spec["validators"].get(k)
            if check and not check(v):             # 校验失败：不写入，重新询问
                bad.append(k)
            else:
                slots[k] = v

        missing = [k for k in spec["required"] if k not in slots]
        if missing:
            k = missing[0]
            tip = ("格式不正确，" if k in bad else "") + spec["ask"][k]
            replies.append({"status": "need_slot", "missing": missing, "ask": tip})
        else:
            replies.append({
                "status": "ready",
                "tool": tool,
                "arguments": {k: slots[k] for k in spec["required"]},
            })
            tool, slots = None, {}                 # 完成后重置状态
    return replies


turns = [
    {"intent": "send_report", "slots": {"report_name": "上周周报"}},
    {"intent": "slot_fill", "slots": {"recipient": "zhang"}},
    {"intent": "slot_fill", "slots": {"recipient": "zhang@a.com"}},
]
for r in run_dialog(turns):
    print(json.dumps(r, ensure_ascii=False))
# 1) need_slot：请问发给谁？
# 2) need_slot：格式不正确，请问发给谁？
# 3) ready：{"tool":"send_report","arguments":{"report_name":"上周周报","recipient":"zhang@a.com"}}
```

可以继续扩展的点：默认值和可选槽位、槽位被用户修改（覆盖）、多个工具并存时的优先级、高风险工具在输出前增加确认状态、槽位值的类型转换。

## HR面

### 1. 自我介绍

**答题思路**

HR 面的自我介绍重点是匹配度和稳定性，不需要讲太多技术细节，约 1 到 2 分钟：

1. 基本背景、工作年限和主要方向。
2. 1 到 2 个代表性经历，用结果和个人贡献体现价值，语言通俗，避免大量术语。
3. 你的特点：责任心、沟通协作、解决问题的方式。
4. 求职动机，与这个岗位的匹配点。

### 2. 为什么看商汤 AI Agent 岗，不去大模型厂或创业公司

**答题思路**

重点是动机真实、有依据，并且不贬低其他类型的公司。按下面的顺序组织：

1. **岗位匹配**：你做 Agent 工程的经历和这个岗位的工作内容对得上，想把它做深。
2. **业务和场景**：强调企业内部系统复杂、业务场景和数据丰富，能把 Agent 落到真实生产环境里，这正是你想积累的经验。回答前要查公司公开的信息，只讲你确认过的内容，不要编造。
3. **和其他选择的比较**：大模型厂偏模型研发，创业公司偏速度和不确定性；你自己更偏好工程落地和系统稳定性，所以这个岗位更合适。
4. **长期发展**：希望在稳定的平台上持续做出可量化的成果。
5. 表明你已经做过功课，并且是主动选择而不是随便投递。

### 3. 你觉得自己做 Agent 工程最不可替代的一点是什么

**答题思路**

“不可替代”不是自夸，而是找出你最强且可举证的一点，用事实支撑：

1. **选一个核心优势**：例如“把原型变成稳定的生产系统”的能力（循环控制、超时重试、可观测、评测体系），或者后端工程加 AI 应用的复合背景。
2. **用具体经历证明**：一件你做过的事，包含问题、动作和结果。
3. **说明对团队的价值**：这项能力如何降低线上事故、提高迭代效率、控制成本。
4. **保持谦虚**：承认其他方面还在成长，也说明你的学习计划。

不要说“我什么都会”，也不要编造数据。

### 4. 项目里和算法同学（调模型 / Prompt）吵架过吗，怎么收尾

**答题思路**

这是在考察沟通和冲突处理，不要说“从来没有分歧”，也不要抱怨对方。建议用 STAR 讲一个真实的分歧：

1. **背景**：分歧点是什么，例如效果优先还是稳定性和成本优先，提示词改动影响线上行为。
2. **立场**：双方的出发点各自合理，你理解对方关注的是效果，你关注的是稳定性、延迟、成本。
3. **解决方式**：用数据说话，建立共同的评测集和指标；约定变更流程（提示词变更先回归评测再上线）；必要时做小流量对比。
4. **结果**：达成了什么共识，后续协作如何改善。
5. **反思**：你从中学到的沟通方式，比如先对齐目标、用事实而不是观点讨论。

### 5. 商汤这种大体量内部系统，Agent 上线要过哪些关，你愿意做脏活吗

**答题思路**

分两部分回答：先展示你对上线流程的理解，再表明态度。

1. **上线关卡**（按你真实理解讲）：评测门槛（离线评测集通过）、安全和权限（数据隔离、工具权限、提示注入防护）、成本和延迟预算、稳定性（超时、重试、限流、降级方案）、可观测性（trace、监控、告警）、灰度发布和回滚、审计和合规、与已有内部系统的对接和评审。
2. **关于“脏活”**：坦诚地表示愿意做，并举例说明它们的价值，比如梳理历史接口、补评测数据、处理线上 badcase、写迁移脚本、对接多个团队。可以结合自己做过的类似事情，说明自己能把繁琐的工作系统化、自动化，而不是单纯忍受。
3. 说明你的原则：优先做影响稳定性和用户体验的事，也会推动重复性工作的工具化。

### 6. 薪资预期和职级对标，手上几个 offer

**答题思路**

不要编造具体数字和 offer 情况，只按真实情况回答：

1. **薪资**：先说明你更看重岗位、成长和团队，薪资希望与市场水平和你的能力相匹配；然后基于你的现状和市场调研，给出一个合理区间（说真实期望，不夸大），并表示有沟通空间。也可以先了解公司的职级和薪酬体系再讨论。
2. **职级**：说明你对自己能力层级的判断和依据（承担的职责范围、项目影响力），希望对标与之相符的职级，具体听公司的评估。
3. **offer 情况**：如实说明目前的面试和 offer 状态；有 offer 可以说明在比较，但强调对这个岗位的兴趣和明确的决策时间点；没有就如实说正在推进流程，不要虚构。
4. 保持礼貌和诚信，不用其他 offer 施压。

### 7. 未来三年你想成为 Agent 架构师还是带人做业务落地

**答题思路**

重点是方向清晰，与岗位路径一致，并且不把两者对立：

1. **说明方向**：基于你的兴趣和优势选择主方向，例如先把技术深度做扎实，成为能设计和评估 Agent 系统的人，同时逐步承担更大范围的责任。
2. **分阶段规划**：第一年快速融入并在业务上交付可衡量的成果；第二年在系统设计、评测体系、稳定性方面形成可复用的方案；第三年扩大影响力，视团队需要承担技术方案负责人或带小团队的角色。
3. **两者的关系**：架构能力和落地能力互相依赖，好的架构需要在业务落地中验证，带人也需要技术判断力。
4. **和公司需求对齐**：表示愿意根据团队的需要灵活调整，关注能创造的价值，而不只是头衔。

### 8. 反向提问：你问 HR 的两个问题是什么

**答题思路**

向 HR 提问要围绕流程、团队和成长，避免问太细的技术问题，也不要一开口就问薪资福利细节。可以准备两个：

1. **关于团队和岗位**：“这个岗位所在团队目前的规模和分工大致是怎样的？入职前三个月对新人有什么期望和考核方式？”
2. **关于成长和流程**：“公司对这个方向的新人有怎样的培养和轮岗机制？后续面试或录用流程的时间安排是怎样的？”

备选：“团队近期最重要的目标是什么，这个岗位在其中承担什么角色？”

不要问网上一搜就能查到的信息，也不要问和你无关的内容。提问要体现你对岗位的认真考虑。
