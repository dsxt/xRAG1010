### 3. AI Agent 与普通 LLM Chat 的本质区别是什么，核心组件有哪些

**参考答案**

本质区别：普通 Chat 是"一问一答"的文本生成，Agent 是以 LLM 为决策核心、能感知环境、自主规划并通过工具行动、直到完成目标的闭环系统。Chat 只产出文本，Agent 产出的是对外部世界的动作和结果。

核心组件：

- **LLM（大脑）**：理解目标、推理、决定下一步。
- **规划（Planning）**：任务拆解、反思、重规划（ReAct、Plan-and-Execute 等）。
- **工具（Tools）**：API、数据库、代码执行、检索等，通过 Function Calling 调用。
- **记忆（Memory）**：短期（对话上下文、滑动窗口）和长期（向量化摘要、知识库）。
- **运行时/控制循环**：循环调度、终止条件、最大步数、错误处理。
- **护栏与观测**：权限、安全校验、Trace、评估。

容易漏的点：Agent 的关键是"循环 + 工具反馈"，而不是"多调几次模型"；还要有终止条件和安全约束。

### 4. 讲一下 ReAct（Reasoning + Acting）范式的工作流程，Thought → Action → Observation 如何循环

**参考答案**

ReAct 让模型交替输出推理和行动，用外部观测纠正推理，减少纯思维链的幻觉。

流程：

1. 输入用户问题和可用工具描述。
2. **Thought**：模型分析当前状态，决定下一步要做什么。
3. **Action**：输出要调用的工具和参数（现在多用原生 Function Calling 的 tool_call，而不是解析文本）。
4. 运行时执行工具，把结果作为 **Observation** 追加到上下文。
5. 回到 Thought，基于新观测继续推理，直到模型给出 Final Answer，或触发终止条件。

工程要点：

- 必须设置最大迭代次数、总 token 和超时预算，防止死循环。
- 工具报错要以 Observation 形式回传，让模型有机会自我修正。
- 上下文会随循环膨胀，需要裁剪或压缩历史 Observation。
- 缺点：串行、步数多则延迟和成本高，复杂任务可结合 Plan-and-Execute 先规划再执行。

### 5. 意图识别在 Agent 系统里怎么做——用 LLM Router、规则分类还是微调分类器，各有什么优劣

**参考答案**

三种方式各有取舍，生产里通常分层组合。

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| 规则/关键词/正则 | 极快、零成本、可解释、确定 | 泛化差、维护成本随规则增长 | 高频固定指令、安全拦截 |
| 微调小分类器（BERT 等） | 低延迟、便宜、稳定，可离线评估 | 需要标注数据，新增意图要重训 | 意图集稳定、流量大 |
| LLM Router（Prompt + few-shot/结构化输出） | 零样本泛化强，新增意图只改 Prompt | 延迟和成本高，输出有波动 | 意图多变、冷启动 |

推荐做法：规则兜底 + 小模型/向量相似度快速路由 + 低置信度时交给 LLM 判断。输出用结构化格式（JSON schema），并带置信度和"其他/澄清"类别。

容易漏的点：要有"无法识别/需要澄清"的出口；评估要用混淆矩阵看易混意图；线上记录误分样例回流成训练/few-shot 数据。

### 6. LangChain 中 Chain、Agent、Tool、Memory 各自职责，LCEL 的基本链路是怎样的

**参考答案**

- **Chain**：把多个步骤（Prompt → Model → Parser 等）按固定顺序串起来，流程由开发者写死。
- **Agent**：由 LLM 动态决定调用哪个工具、调几次，流程由模型在运行时决定。
- **Tool**：被封装成统一接口的可调用能力（名称、描述、参数 schema、函数），供模型选择。
- **Memory**：保存并注入历史对话/状态。新版本中更推荐用 LangGraph 的 State 和 Checkpointer 管理，旧的 `ConversationBufferMemory` 之类已逐步弃用。

**LCEL**（LangChain Expression Language）用 `|` 管道符组合 `Runnable`，基本链路：

```python
chain = prompt | llm | StrOutputParser()
result = chain.invoke({"question": "..."})
```

所有组件都实现统一的 Runnable 接口，天然支持 `invoke / batch / stream / ainvoke`，并可用 `RunnableParallel`、`RunnablePassthrough`、`RunnableLambda` 做并行和数据传递，便于流式输出和追踪。

补充：LangChain 官方现在推荐用 LangGraph 构建复杂 Agent，旧的 `AgentExecutor` 属于遗留方案。

### 7. RAG 的完整流程——Query 改写、Chunk 切分策略、Embedding、向量检索、Rerank、Context 注入，说说你优化过哪些点

**参考答案**

流程：离线阶段是文档解析 → 清洗 → 切分 → Embedding → 入库（向量 + 元数据 + 关键词索引）；在线阶段是 Query 改写 → 检索 → 融合 → Rerank → 拼装 Context → LLM 生成（带引用）。

常见优化点：

- **Query 改写**：多轮对话中做指代消解；Multi-Query 扩展；HyDE；复杂问题拆成子问题。
- **切分**：按文档结构（标题、段落）语义切分，加适度 overlap；保留标题路径作为元数据；表格、代码单独处理；可用 small-to-big（检索小块、返回父块）。
- **Embedding**：选对中文或多语言模型；query/doc 前缀要符合模型要求；必要时领域微调。
- **检索**：向量 + BM25 混合，加元数据过滤，适当调大 top-k 召回。
- **Rerank**：用 cross-encoder 对粗召回的候选精排，再截取 top-n。
- **Context 注入**：去重、按相关性排序、控制 token 预算，注意"lost in the middle"，要求模型基于资料回答并给出处，没有依据就说不知道。

回答"你优化过哪些"时，只说你真做过的，并讲清"发现什么问题 → 用什么指标衡量 → 提升多少"。

### 8. 向量数据库选型（FAISS/Milvus/Qdrant/Chroma），你们为什么选这个，召回率怎么评估

**参考答案**

选型对比：

- **FAISS**：库而非数据库，单机内存检索，性能强、灵活，但没有持久化、过滤、分布式等服务能力，适合原型或嵌入式场景。
- **Chroma**：轻量易上手，适合本地开发和小规模。
- **Qdrant**：Rust 实现，部署简单，payload 过滤能力好，中等规模生产常用。
- **Milvus**：分布式、云原生，支持海量数据、多种索引和混合检索，运维较重，适合大规模。

选型依据：数据规模、QPS 和延迟、是否需要元数据过滤和权限、是否要混合检索、运维能力、是否已有基础设施（如已有 ES/PG 可考虑 ES 或 pgvector）。回答"为什么选这个"要结合你们的规模和约束讲，不要空泛。

**召回率评估**：

1. 构建评测集：Query 与应命中的文档/Chunk 标注（人工标注，或用 LLM 合成问题再抽检）。
2. 检索指标：Recall@k、MRR、nDCG、Hit Rate。
3. ANN 近似误差：以暴力检索（Flat）结果为基准，计算 ANN 的 Recall@k，用来调索引参数（如 HNSW 的 `ef`、`M`）。
4. 端到端：再评估答案正确性、忠实度（如 RAGAS 类指标）。

注意区分"ANN 召回"和"业务召回"，两者要分别看。

### 9. Agent 调工具时参数解析失败或 JSON 格式不对怎么处理，如何防止无限循环调用

**参考答案**

**参数解析失败**：

1. 优先用模型原生的 Function Calling / 结构化输出（JSON schema，部分服务支持 strict 模式），从源头减少格式错误。
2. 解析后用 Pydantic / JSON Schema 做校验。
3. 失败时把具体错误信息（缺哪个字段、类型错在哪）作为 Observation 回传，让模型重试，限制重试次数（如 2 到 3 次）。
4. 可做轻量修复（去掉 markdown 代码块围栏、补全括号、`json-repair` 之类的库），但修复后仍要校验。
5. 仍失败则降级：换更强的模型、走兜底话术或转人工，不要静默继续。

**防止无限循环**：

- 设置最大步数、总 token、总时长三类预算。
- 检测重复调用：对（工具名 + 规范化参数）做哈希，连续相同调用超过阈值就中断或提示换策略。
- 工具结果为空或报错时给明确的终止/换路提示。
- 有副作用的工具加幂等键。
- 超限后返回已有的部分结果和原因，而不是硬抛异常，并记录 Trace 用于排查。

### 10. Redis 在你 Agent 系统里的用途——缓存、分布式锁、Session 存储、消息队列，各举一例

**参考答案**

- **缓存**：缓存确定性强的工具结果（如天气、设备状态快照）、Embedding 结果、检索结果，或语义缓存（相似问题命中），设置合理 TTL 来降低延迟和 LLM 成本。
- **分布式锁**：同一会话/同一设备同时只允许一个 Agent 任务执行，避免并发写状态或重复下发指令。用 `SET key value NX PX ttl` 加锁，value 用唯一标识，解锁用 Lua 脚本校验后删除，并考虑锁续期（如 Redisson 的看门狗）。
- **Session 存储**：保存短期对话历史、Agent 中间状态，用 Hash/List，按 `session_id` 设 TTL。LangGraph 的 Checkpointer 也有 Redis 实现。
- **消息队列**：Redis Stream（带消费者组和 ACK）可做轻量异步任务队列。List 方案没有 ACK，可靠性弱；严格可靠、高吞吐场景建议用 Kafka/RocketMQ。

回答时要提 TTL、一致性（缓存与源数据）和故障场景（锁过期、Redis 宕机）。

### 11. MySQL 事务 ACID 简单说一下，隔离级别有哪些

**参考答案**

**ACID**：

- **原子性（A）**：事务要么全做要么全不做，靠 undo log 回滚实现。
- **一致性（C）**：事务前后数据满足约束和业务规则，是目的，由 A、I、D 加应用逻辑共同保证。
- **隔离性（I）**：并发事务互不干扰，靠锁和 MVCC 实现。
- **持久性（D）**：提交后数据不丢，靠 redo log（WAL）实现。

**四种隔离级别**：读未提交（RU）、读已提交（RC）、可重复读（RR）、串行化。

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 否 | 可能 | 可能 |
| 可重复读 | 否 | 否 | 标准下可能 |
| 串行化 | 否 | 否 | 否 |

InnoDB 默认是 RR：快照读靠 MVCC（ReadView 在事务首次读时生成），当前读靠 next-key lock（记录锁 + 间隙锁），在很大程度上避免了幻读。RC 下每次读都生成新的 ReadView。

### 12. Python 中 GIL 是什么，对多线程和多进程的影响

**参考答案**

GIL（全局解释器锁）是 CPython 解释器里的一把互斥锁，同一时刻只允许一个线程执行 Python 字节码，原因是 CPython 的引用计数内存管理不是线程安全的。

影响：

- **多线程**：CPU 密集型任务无法利用多核，多线程甚至可能因切换变慢；**I/O 密集型**任务在等待 I/O 时会释放 GIL，多线程仍然有效。NumPy 等 C 扩展在计算时也常会释放 GIL。
- **多进程**：每个进程有独立解释器和独立 GIL，可以真正并行利用多核，代价是内存占用和进程间通信（序列化）开销。

实践选择：Agent 里大量是调用 LLM/工具的网络 I/O，用 `asyncio` 或多线程即可；CPU 密集用 `multiprocessing` / `ProcessPoolExecutor` 或 C 扩展。

补充：GIL 不保证复合操作的原子性，共享数据仍要加锁。Python 3.13 起提供了可选的 free-threaded（无 GIL）构建，目前仍是实验性质，默认构建依旧有 GIL。

### 14. 你对 LangGraph 或 Agent Harness 有了解么，简单说下认知

**参考答案**

**LangGraph**：基于图的有状态 Agent 编排框架。用 State（共享状态）、Node（执行单元）、Edge（含条件边）描述流程，支持循环、分支、并行、人工介入（interrupt）、Checkpointer 持久化和断点恢复、流式输出。相比线性 Chain，它让流程可控、可调试。

**Agent Harness**：围绕模型的运行时"外壳"，负责模型本身之外让 Agent 可靠运转的一切，包括：循环控制、工具注册与调用、上下文管理（压缩、裁剪）、记忆、权限与沙箱、钩子（hooks）、可观测、评估与重试降级。通俗地说：模型是引擎，Harness 是让引擎在真实环境里安全、稳定跑起来的整车。

两者关系：LangGraph 偏"流程编排"的底层框架，Harness 偏"工程化运行时"的整体方案，Harness 可以构建在 LangGraph 之上，也可以自研。认知上的重点是：模型能力趋同后，Agent 的可靠性越来越取决于 Harness 的设计。

### 15. 手撕算法：LeetCode 46——全排列（Permutations），给定一个不含重复数字的数组，返回所有可能的排列

**参考答案**

思路：回溯。用 `path` 记录当前排列，用 `used` 标记已选元素，路径长度等于 `n` 时收集结果，然后回退（撤销选择）继续尝试其他分支。

复杂度：时间 O(n × n!)（共 n! 个排列，每个拷贝 O(n)），空间 O(n)（递归深度和 `used`，不计输出）。

```python
from typing import List


def permute(nums: List[int]) -> List[List[int]]:
    res: List[List[int]] = []
    path: List[int] = []
    used = [False] * len(nums)

    def backtrack() -> None:
        if len(path) == len(nums):
            res.append(path[:])  # 必须拷贝
            return
        for i, x in enumerate(nums):
            if used[i]:
                continue
            used[i] = True
            path.append(x)
            backtrack()
            path.pop()
            used[i] = False

    backtrack()
    return res
```

易漏点：收集结果时要拷贝 `path`；回溯要完整撤销状态。本题元素不重复，若含重复数字（LeetCode 47）需要先排序并剪枝。

### 2. 详细讲你最复杂的 Agent 项目架构——入口、意图路由、规划层、执行层、工具层、记忆层、可观测

**答题思路**

不要编造具体项目名和数字，用你真实项目填充。可以画一张分层图，按请求流向讲：

1. **入口层**：协议（HTTP/SSE/WebSocket）、鉴权、限流、会话 ID、流式输出。
2. **意图路由**：规则 + 小模型 + LLM 分层，输出意图、置信度、是否需要澄清。
3. **规划层**：简单任务直接 ReAct，复杂任务先拆解成步骤（Plan-and-Execute），失败可重规划。
4. **执行层**：循环调度、最大步数与预算、并行工具调用、重试与降级、人工确认节点。
5. **工具层**：统一注册和 schema、参数校验、超时与熔断、权限分级、有副作用的操作带幂等键。
6. **记忆层**：短期（滑动窗口 + 摘要）、长期（向量化摘要、用户画像）、知识库（RAG）。
7. **可观测**：Trace/Span、token 成本、工具耗时、评估回流。

每层都准备一个"为什么这么设计、放弃了什么"的取舍。结尾讲你负责的部分和遇到的最大难点。

### 3. 什么是 Agent Harness，它与直接使用 LangChain AgentExecutor 或 LangGraph 比有什么优劣势，你们为啥选这个方案

**参考答案**

**Agent Harness** 是包裹模型的运行时框架：管理 Agent 循环、工具注册与调用、上下文与记忆、权限与沙箱、钩子、可观测、评估和容错，目标是让 Agent 在生产环境可靠、可控、可复用。

对比：

| 方案 | 优势 | 劣势 |
| --- | --- | --- |
| `AgentExecutor` | 上手最快，几行代码跑通 ReAct | 流程是黑盒，难控制中间步骤，难做持久化和人工介入；官方已将其视为遗留，推荐迁移到 LangGraph |
| LangGraph | 显式状态图，流程可控，支持分支、循环、Checkpointer、interrupt、流式 | 需要自己设计状态和节点，图复杂后维护成本高；通用能力（上下文压缩、权限、沙箱）仍要自己补 |
| Harness（自研或成熟方案） | 把工程化能力（上下文管理、权限、钩子、观测、评估）沉淀成统一底座，多个 Agent 复用，贴合业务 | 开发和维护成本高，有"重复造轮子"风险，需要团队长期投入 |

选型要看：流程是固定还是模型自主决定、是否需要持久化和人工介入、团队规模和维护能力、与现有基础设施的整合、可观测与合规要求。回答"为啥选这个"时必须落到你们的真实约束上，并说清放弃了什么。若是 Harness 方案，强调它是把共性能力抽成底座，而不是替代 LangGraph（可以在其上构建）。

### 4. LangGraph 中 StateGraph 的三要素 State、Node、Edge，Conditional Edge 怎么根据 LLM 输出做分支路由，Checkpointer 做什么用

**参考答案**

**三要素**：

- **State**：整个图共享的状态（`TypedDict` 或 Pydantic），每个字段可定义 reducer（如 `add_messages`）来决定节点更新如何合并。
- **Node**：函数，接收 State，返回对 State 的增量更新（可以是 LLM 调用、工具执行、检索等）。
- **Edge**：节点间的连接，分普通边、条件边，以及 `START`、`END` 特殊节点。

**Conditional Edge**：`add_conditional_edges(source, router_fn, mapping)`。`router_fn` 读取当前 State 并返回下一个节点名（或节点名列表，用于并行）。典型做法是看 LLM 最后一条消息是否带 `tool_calls`：

```python
def route(state):
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

graph.add_conditional_edges("agent", route, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")   # 形成 ReAct 循环
```

也可以让 LLM 输出结构化的意图字段，再按字段映射到节点。

**Checkpointer**：在每个 super-step 后保存 State 快照（按 `thread_id` 区分）。作用：多轮对话的短期记忆、故障后断点恢复、`interrupt` 人工审批后继续、时间回溯和调试（time travel）。生产环境用持久化实现（SQLite/Postgres/Redis），不要用内存版。注意：它保存的是线程内状态，跨线程的长期记忆要用 Store。

### 5. 多 Agent 协作常见模式 Orchestrator-SubAgent（Supervisor）、Swarm、Pipeline、Debate/Voting，分别适合什么场景

**参考答案**

- **Orchestrator-SubAgent（Supervisor）**：中心 Agent 拆任务、分派、汇总。适合任务可拆分、需要统一控制的场景（如客服总控分发到订单、物流、知识问答子 Agent）。优点是可控、易观测；缺点是中心节点成为瓶颈，上下文压力大。
- **Swarm（去中心化/Handoff）**：Agent 之间根据情况直接移交控制权。适合对话式、按阶段切换角色的场景（如售前转售后）。灵活、延迟低，但全局流程难追踪，容易出现来回踢皮球。
- **Pipeline（流水线）**：固定顺序，前一个的输出是后一个的输入（如检索 → 起草 → 审校）。适合流程确定的内容生产和数据处理，可预测、易测试，但缺少灵活性。
- **Debate/Voting**：多个 Agent 独立给出答案，再投票或辩论评审。适合高风险、需要提高准确性的决策（代码审查、事实核验、推理题）。代价是成本成倍增加，且若各 Agent 来自同一模型，错误可能相关。

选择原则：能用单 Agent 或固定流程解决就不要上多 Agent，多 Agent 带来协调成本、token 成本和调试难度。

### 6. 多 Agent 系统怎么避免子 Agent 重复执行、任务丢失（任务队列、状态追踪、幂等性设计）

**参考答案**

核心思路：把每个子任务建模成有状态的、可持久化的、幂等的工作单元。

- **任务队列**：任务写入持久化队列（Kafka/RocketMQ/Redis Stream/DB 任务表），消费者用 ACK 确认，处理失败可重试，超过次数进死信队列。这样任务不会因进程崩溃而丢失，语义是至少一次（at-least-once）。
- **状态追踪**：每个任务有 `task_id`、状态机（PENDING → RUNNING → SUCCEEDED/FAILED）、重试次数、租约（lease）和心跳；超时未心跳的任务可被回收重新调度。状态用 DB 或 LangGraph Checkpointer 持久化，并通过 Trace 串联父子任务。
- **防重复执行**：领取任务时用乐观锁/CAS（`UPDATE ... WHERE status='PENDING'`）或分布式锁，保证同一时刻只有一个执行者。
- **幂等性**：至少一次投递必然带来重复，所以消费端必须幂等。给每个任务或每次工具调用生成幂等键，执行前查"已完成记录"，有副作用的操作（下单、控制设备）下游要支持幂等键或去重表。

容易漏的点：锁过期后的"双执行"、重试导致副作用重复、父任务汇总时对缺失子结果的超时处理。

### 7. Agentic RAG 与 Naive RAG 区别，Agent 如何决策何时调 RAG、何时直接回答、何时调搜索工具

**参考答案**

**区别**：Naive RAG 是固定的"检索一次 → 生成"流水线，每个问题都检索，无论是否需要。Agentic RAG 让 Agent 自主决策：是否检索、检索什么（改写、拆分子问题）、用哪个数据源、结果不够时是否再检索或换工具、是否需要自我校验，是一个多步循环。

**路由决策**：

- 直接回答：闲聊、通用常识、已在上下文里有答案的问题。
- 调 RAG：涉及企业内部、私有、需要时效可控的知识库。
- 调搜索工具：需要最新的公开信息，知识库没有覆盖。
- 调业务 API：需要实时的业务数据（订单、设备状态）。

**实现方式**：把"知识库检索""联网搜索"等做成带清晰描述的工具，让模型通过 Function Calling 自主选择；用 Prompt 写清各工具的适用边界；对关键场景可在前面加一个路由器；检索结果加相关性评估（grader），不相关时改写重试或降级（Self-RAG / CRAG 的思路）。

**代价和护栏**：延迟和成本更高，要限制最大检索轮数，检索为空时要明确告知而不是编造。

### 8. Hybrid Search（向量 + BM25/关键词）怎么实现，多路召回后如何 Rerank 和融合

**参考答案**

**实现**：同一个 Query 同时走两路：稠密向量检索（语义匹配，对同义表达好）和 BM25/关键词检索（精确匹配，对专有名词、型号、编码好）。可在一个系统里完成（ES、OpenSearch、Milvus、Qdrant 等均支持混合检索），也可以分别查询后在应用层合并。

**融合**：两路分数量纲不同（BM25 无界，余弦在固定区间），不能直接相加。

- **RRF（Reciprocal Rank Fusion）**：只用排名，`score = Σ 1 / (k + rank_i)`，`k` 常取 60，简单且稳健，是最常见的做法。
- **加权求和**：先对各路分数归一化（min-max 或 z-score），再按权重相加，权重要在评测集上调。

```python
def rrf(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:
        for r, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + r)
    return sorted(scores, key=scores.get, reverse=True)
```

**Rerank**：融合后取前 N（如几十条）候选，用 cross-encoder 重排模型对（query, doc）逐一打分，再取 top-k 给 LLM。Rerank 精度高但慢，所以只用在候选集上。最后按评测集的 Recall/nDCG 来调各路 top-k 和权重。

### 9. 知识库有权限隔离（不同用户可见不同文档）怎么做——ACL 元数据过滤、行列级权限在检索阶段注入

**参考答案**

原则：权限必须在检索阶段强制过滤，而不是检索后再让 LLM"别说"，更不能靠 Prompt 约束。

做法：

1. **入库时打标**：每个 Chunk 带元数据，如 `tenant_id`、`owner`、`allowed_groups/allowed_users`、密级、部门。文档权限变化时要同步更新（或存文档 ID，查询时再关联权限）。
2. **查询时注入过滤**：服务端从可信的身份凭证（JWT/SSO，不是用户传的参数）解析出用户的组和角色，把 ACL 条件作为 filter 拼进向量检索和关键词检索（如 ES 的 `filter`、Milvus/Qdrant 的 filter 表达式）。这样两路召回都被限制在可见范围内。
3. **预过滤 vs 后过滤**：预过滤（先过滤再 ANN）结果正确；后过滤可能把 top-k 过滤光导致结果不足，且有信息泄漏风险。过滤选择性很高时要注意 ANN 的性能，必要时按租户分 collection/分区。
4. **行列级权限**：结构化数据通过 SQL 层的行过滤、列脱敏实现，Agent 用受限账号或按用户身份执行查询，不要共用高权限账号。
5. **其他细节**：缓存（语义缓存、检索缓存）的 key 必须包含权限维度，否则会越权命中；日志和 Trace 也要脱敏；审计谁检索了什么。

### 10. Agent 长期记忆怎么实现——向量化存摘要、检索注入、与短期滑动窗口的配合策略

**参考答案**

**分层设计**：

- **短期记忆**：当前会话最近 N 轮原文（滑动窗口），保证连贯，放在上下文里，由 Checkpointer/Redis 保存。
- **长期记忆**：跨会话的用户偏好、事实、历史经验，存到向量库 + 结构化存储。

**写入**：会话结束或每隔若干轮，用 LLM 抽取"值得记住的内容"（偏好、事实、决策），生成摘要或事实条目，附带元数据（用户 ID、时间、类型、重要度），向量化后写入。写入前要去重、合并冲突（新事实覆盖旧事实），并过滤敏感信息。

**读取与注入**：新一轮到来时，用当前问题（可结合近期上下文）检索 top-k 相关记忆，按相关性、时间衰减、重要度打分，放进 Prompt 的单独段落（如"用户背景"），注意 token 预算。

**配合**：滑动窗口负责"刚刚说了什么"，长期记忆负责"以前知道什么"；窗口外的内容被淘汰前先摘要沉淀。

**要注意的问题**：记忆污染和错误记忆（可追溯、可删除）、隐私与用户可控（可查看和删除）、遗忘策略（TTL、衰减）。

### 11. 上下文窗口超限怎么处理——摘要压缩、滑动窗口、关键实体提取、向量检索历史注入，各说适用场景

**参考答案**

| 方案 | 做法 | 适用场景 | 注意点 |
| --- | --- | --- | --- |
| 滑动窗口 | 只保留最近 N 轮或 N 个 token | 闲聊、短任务，近期上下文最重要 | 早期关键信息会丢失 |
| 摘要压缩 | 把旧对话用 LLM 压成摘要，保留近期原文 | 长对话、需要保留大致脉络 | 摘要有损，多次迭代摘要会累积失真，本身耗 token 和延迟 |
| 关键实体/状态提取 | 抽取槽位、实体、待办、已确认决策等结构化信息持续维护 | 任务型对话（订票、工单、设备控制） | 需要设计 schema，抽取错误会持续影响 |
| 向量检索历史注入 | 历史切片向量化，按当前问题检索相关片段 | 超长会话、跨会话回忆 | 可能漏召回，丢失时序和指代 |

另有针对 Agent 的做法：清理旧的工具 Observation（只保留结论或引用）、大结果落盘只保留摘要和句柄、子 Agent 隔离上下文只回传结论。

实践中通常组合：近期原文窗口 + 滚动摘要 + 结构化状态 + 按需检索。触发时机用 token 阈值（如接近窗口一定比例时）。

### 12. Function Calling 与 MCP（Model Context Protocol）的区别，MCP 解决什么问题

**参考答案**

**Function Calling** 是模型能力：开发者把函数的名称、描述、参数 schema 传给模型，模型输出结构化的调用请求（函数名 + 参数），由应用自己执行并回传结果。它解决"模型如何表达要调什么工具"，但工具的定义、调用方式、传输都是各应用、各厂商自己实现。

**MCP** 是 Anthropic 提出的开放协议，标准化 AI 应用（Client/Host）与外部工具和数据源（Server）之间的连接。它定义了工具（Tools）、资源（Resources）、提示模板（Prompts）等原语，以及基于 JSON-RPC 的通信，传输方式有 stdio 和 Streamable HTTP（早期为 HTTP + SSE）。

**MCP 解决的问题**：N 个应用 × M 个工具的重复集成（N×M 变成 N+M）；工具可以被不同客户端复用；支持动态发现工具；便于统一鉴权和治理。

**关系**：两者不是替代关系，是不同层。MCP 客户端从 Server 拉取工具列表，转成模型的 Function Calling 格式，模型发出调用后，客户端再通过 MCP 去执行。

要补充的风险：MCP Server 的权限和供应链安全、工具描述注入（prompt injection）、工具过多导致上下文膨胀和选择困难。

### 13. Agent 效果怎么评估——任务完成率、工具调用准确率、平均步数、人工评分、LLM-as-Judge 怎么用

**参考答案**

**指标分层**：

- **结果指标**：任务完成率/成功率（有明确判定标准）、答案正确性、忠实度（RAG 里是否有依据）。
- **过程指标**：工具选择准确率、参数正确率、平均步数、无效或重复调用比例、是否触发死循环。
- **成本与性能**：延迟（P50/P95）、token 成本、失败率、重试率。
- **体验指标**：人工评分、用户满意度、线上点赞点踩、转人工率。

**评估集**：从线上真实日志中抽样并标注，覆盖常见、边界和已知 Bad Case，每次改 Prompt/模型/工具都做回归。工具调用准确率可以对比"标准调用序列"自动判断。

**LLM-as-Judge**：用强模型按明确的评分标准（rubric）给输出打分或做两两比较。要点：

- 评分标准写具体，输出结构化分数加理由。
- 两两比较时交换顺序以消除位置偏差，注意长度偏好和自我偏好（评委和被评对象用同一模型时偏高）。
- 先用人工标注样本校准，计算评委与人工的一致率。
- 能规则判定的（格式、工具调用是否正确）不要用 LLM 判。

最终组合：自动指标做回归，LLM Judge 做规模化，人工抽检做校准。

### 14. 你们 Agent 服务的部署方式（FastAPI/容器化/异步任务），如何做限流和熔断

**参考答案**

**部署**：

- **服务层**：FastAPI + `uvicorn`/`gunicorn` 多 worker，接口全异步（`async`），流式输出用 SSE 或 WebSocket。
- **容器化**：Docker 打包，Kubernetes 部署，配健康检查（liveness/readiness），按 CPU、QPS 或队列长度做 HPA 弹性伸缩，配置和密钥用 ConfigMap/Secret 管理。
- **异步任务**：长耗时的 Agent 任务不要占着 HTTP 连接，改为"提交任务 → 返回 `task_id` → 轮询/回调/推送"，后端用 Celery/Kafka/RocketMQ/Redis Stream 等队列加 worker 消费，任务状态持久化。
- **状态**：服务本身无状态，会话状态放 Redis/DB/Checkpointer，这样可以水平扩展。

**限流**：

- 多维度：按用户、租户、接口、全局，同时限制 QPS 和 token 用量/并发数。
- 算法：令牌桶或滑动窗口；多实例用 Redis（Lua 保证原子）做分布式限流，或在网关层（Nginx/Kong/Envoy）实现。
- 超限返回 429，并告知重试时间；对下游 LLM 的并发用信号量或队列做背压。

**熔断与降级**：对 LLM 或工具下游统计失败率/超时率，超过阈值进入"打开"状态快速失败，经过冷却期进入"半开"小流量探测，成功再恢复（可用 `pybreaker` 或网关/服务网格能力）。熔断后降级：换备用模型、返回缓存或兜底话术。再配合超时、指数退避加抖动的重试，避免雪崩。

### 15. 手撕算法：实现一个简单的 Tool Call Parser——输入 LLM 返回的 tool_call JSON（name + arguments 字符串），解析成 Python dict，校验 arguments 是否为合法 JSON，非法返回 None

**参考答案**

思路：模型返回的 `arguments` 是**字符串**形式的 JSON（OpenAI 风格），需要二次解析。步骤：外层解析（输入也可能是字符串）→ 校验是 dict 且有非空字符串 `name` → 取 `arguments`，若是字符串则 `json.loads`，若已是 dict 则直接用 → 解析结果必须是对象（dict）→ 任一步失败返回 `None`。

复杂度：时间 O(L)（L 为输入长度，主要是 JSON 解析），空间 O(L)。

```python
import json
from typing import Any, Optional


def parse_tool_call(tool_call: Any) -> Optional[dict]:
    """返回 {"name": str, "arguments": dict}；任何非法情况返回 None。"""
    try:
        if isinstance(tool_call, (str, bytes)):
            tool_call = json.loads(tool_call)
        if not isinstance(tool_call, dict):
            return None

        # 兼容 {"function": {"name":..., "arguments":...}} 形式
        fn = tool_call.get("function", tool_call)
        if not isinstance(fn, dict):
            return None

        name = fn.get("name")
        if not isinstance(name, str) or not name.strip():
            return None

        args = fn.get("arguments", "{}")
        if isinstance(args, (str, bytes)):
            args = json.loads(args) if args.strip() else {}
        if not isinstance(args, dict):  # 参数必须是 JSON 对象
            return None

        return {"name": name, "arguments": args}
    except (json.JSONDecodeError, TypeError, ValueError):
        return None


# 示例
print(parse_tool_call({"name": "get_weather", "arguments": '{"city": "Shenzhen"}'}))
# {'name': 'get_weather', 'arguments': {'city': 'Shenzhen'}}
print(parse_tool_call({"name": "get_weather", "arguments": '{"city": '}))  # None
```

易漏点：`arguments` 空串的处理要事先约定；解析结果不是对象（如数组、数字）也应判非法；`json.loads` 可能抛 `TypeError`；生产里还要用 JSON Schema/Pydantic 校验字段，失败时把错误信息回传给模型重试。

### 3. 如果让你从零设计一个无人机操控/工业场景的多意图 AI Agent（含设备控制、知识问答、工单创建），整体架构怎么画，模块怎么拆

**参考答案**

整体思路：分层架构，意图路由分发到三类能力域，其中**设备控制是高风险操作，必须由确定性代码和安全层兜底，不能让 LLM 直接决定安全相关动作**。

**模块**：

1. **接入层**：多端入口（App/语音/Web）、鉴权、会话管理、流式输出、限流。
2. **意图路由**：规则 + 小模型 + LLM 分层，输出意图（控制/问答/工单/闲聊/未知）、槽位和置信度；低置信度或槽位缺失时发起澄清。
3. **三个子 Agent/能力域**：
    - **设备控制**：把自然语言解析成结构化指令（目标设备、动作、参数），经**参数校验 → 权限校验 → 安全规则校验**（如禁飞区、电量、风速、高度限制）→ 高风险动作要用户**二次确认** → 下发；指令要幂等、可撤销、有超时，执行结果回读确认。
    - **知识问答**：RAG（混合检索 + Rerank + 引用），带权限过滤，检索为空时拒答或转人工。
    - **工单创建**：槽位填充（设备、故障描述、优先级），先让用户确认再调用工单系统，用幂等键防重复创建。
4. **编排与状态**：LangGraph 或自研循环，状态持久化（Checkpointer），支持中断恢复和人工介入。
5. **工具层**：统一注册、schema 校验、超时和熔断、权限分级（只读/低风险/高风险）。
6. **记忆**：短期窗口 + 摘要、用户和设备偏好的长期记忆。
7. **安全与护栏**：输入/输出过滤、Prompt 注入防护、操作审计、紧急停止（不经过 LLM 的硬通道）。
8. **可观测与评估**：Trace、成本、工具耗时、离线评测集、线上回流。
9. **基础设施**：消息队列用于异步任务和设备事件，设备状态通过实时通道订阅。

**关键难点和权衡**：控制类意图要高准确率、低延迟，宁可多一次确认；实时指令走确定性通道，LLM 只做理解和解析；意图切换（比如问到一半要下指令）需要状态隔离。

### 4. Harness 工程化——Agent 的可观测性（Trace / Span / Token 成本 / 工具耗时）怎么做，用 LangSmith / LangFuse 还是自研，采集哪些关键指标

**参考答案**

**数据模型**：一次用户请求对应一个 **Trace**，其中每次 LLM 调用、工具调用、检索、子 Agent 执行是一个 **Span**，形成树状结构，记录输入输出、耗时、状态、错误、模型名、token 用量、版本信息（Prompt 版本、模型版本）。通过 `trace_id` 和 `session_id` 串联多轮对话。

**关键指标**：

- 延迟：端到端、首 token（TTFT）、各步骤耗时（P50/P95/P99）。
- 成本：输入/输出 token、按用户/租户/功能归集的费用。
- 质量：任务成功率、工具调用成功率与参数错误率、平均步数、重试和降级次数、检索命中情况、用户反馈（点赞点踩）。
- 稳定性：超时率、错误率、限流次数、熔断次数。

**选型**：

- **LangSmith**：与 LangChain/LangGraph 集成最好，功能完整（Trace、评测、Prompt 管理），为 SaaS（也有企业自托管版本）；数据合规要考虑。
- **Langfuse**：开源，可自托管，支持 Trace、评估、Prompt 管理，对数据不出域的场景友好。
- **自研**：基于 OpenTelemetry 采集，接入已有的 Prometheus/Grafana/ELK/Jaeger，好处是与公司监控体系统一、可定制；代价是要自己做 LLM 专用的界面和评测。

实践建议：用 OpenTelemetry 做统一埋点（避免被单一厂商绑定），LLM 专用分析用 Langfuse 之类的工具，或自研补充。要注意**脱敏**（用户隐私、密钥）、采样策略（全量存错误，正常请求采样）和异步上报，避免影响主链路性能。

### 5. Agent 在生产环境运行时的容错与降级策略——LLM 超时重试（指数退避）、工具不可用 fallback、RAG 检索空结果怎么处理

**参考答案**

**LLM 超时与错误**：

- 设置超时（连接超时和总超时）。
- 只对可重试错误（超时、429、5xx）重试，用**指数退避加随机抖动**，限制次数；4xx（参数错误）不重试。
- 遵守 429 响应里的 `Retry-After`。
- 重试耗尽后降级：切换备用模型/备用供应商，或换小模型，或返回兜底话术。
- 配合熔断，避免对已故障的服务持续打请求。

```python
import random, time

def call_with_retry(fn, retries=3, base=0.5, cap=8.0):
    for i in range(retries + 1):
        try:
            return fn()
        except RetryableError:
            if i == retries:
                raise
            time.sleep(min(cap, base * 2 ** i) * random.uniform(0.5, 1.0))
```

**工具不可用**：

- 超时、熔断，下游故障时快速失败。
- Fallback：备用工具/备用数据源、缓存的旧数据（并告知可能过期）、降级为只读或提示稍后重试。
- 把失败原因作为 Observation 回传，让 Agent 选择替代方案，而不是死循环重试。
- 有副作用的工具重试要有幂等保证。

**RAG 检索空结果**：

- 先区分"真的没有"与"没检出"：放宽条件重试（改写 Query、降低阈值、增加 top-k、切换为关键词检索）。
- 仍为空：明确告知"知识库中没有相关信息"，或者转联网搜索（如果允许），或转人工；**不要让模型无依据地编造**。
- 记录空结果的 Query，用于补充知识库和优化检索。

整体原则：快速失败、有限重试、逐级降级、全程可观测，并保证降级后的结果对用户是诚实的。

### 6. 如何做 Prompt 版本管理、A/B 测试及线上灰度发布

**参考答案**

**版本管理**：

- Prompt 当作代码资产管理：存放在 Git 或 Prompt 管理平台（Langfuse/LangSmith 等），有版本号、变更说明、评审流程，与代码、模型版本、工具 schema 一起记录。
- 运行时从配置中心加载，支持指定版本和快速回滚，不需要重新发布服务。
- 每次调用的 Trace 中记录 Prompt 版本，方便问题归因。

**发布前评估**：改动先跑离线评测集（含历史 Bad Case 的回归集），对比关键指标，通过后才进入线上流程。

**A/B 测试**：

- 流量按用户 ID（或会话 ID）哈希分桶，保证同一用户体验一致，避免同一会话中途切换版本。
- 明确指标：任务成功率、用户反馈、转人工率、成本、延迟；样本量足够再下结论，注意统计显著性。
- 单次实验只改一个变量。

**灰度发布**：从小比例（如 1% → 5% → 20% → 100%）逐步放量，每一档观察核心指标和告警；设置自动回滚阈值（错误率、延迟、负反馈异常）；高风险场景（设备控制）可以先从内部用户开始，或先用影子流量（shadow）对比输出而不对外生效。

LLM 输出有随机性，不能靠少量样例判断好坏，要靠评测集和统计指标。

### 7. 多轮对话里用户突然改意图（如问完产品参数突然让下单），你的系统怎么检测和处理

**参考答案**

**检测**：每一轮都重新做意图识别，而不是沿用上一轮意图。输入包括当前问题 + 最近几轮上下文 + 当前任务状态（是否有未完成的流程）。发现与当前流程的意图不一致且置信度足够时，判定为意图切换。可用规则（如"下单""取消""算了"）加模型判断组合。

**处理**：

1. **状态管理**：为每个任务维护独立的状态（槽位、进度），把对话栈化：新意图入栈，处理完再决定是否回到旧任务。
2. **上下文继承**：新意图要能引用之前的信息，如"这款"指代刚才聊的产品，通过指代消解和实体槽位（商品 ID）自动带入下单流程。
3. **未完成任务的处理**：旧流程（如半填的工单）可挂起保留，必要时询问用户"需要继续刚才的吗"，超时清理。
4. **低置信度或有歧义**：发起澄清问题，而不是猜测。
5. **高风险动作**（下单、控制设备）：先向用户确认关键信息再执行。

**实现层面**：在 LangGraph 中让路由节点每轮都执行，根据意图跳转到对应子图，状态存入 Checkpointer。评估时专门构造"意图切换"的测试用例，关注误切换（用户只是在补充信息，却被判为新意图）和漏切换两类错误。

### 8. Elasticsearch 做全文检索与向量检索混合查询了解么，如何写 Bool Query + KNN 查询

**参考答案**

了解。ES 8.x 支持 `dense_vector` 字段（需 `index: true` 并指定相似度，底层为 HNSW）和 `knn` 搜索，与 `query` 同时使用即为混合检索：两路得分相加后排序（可用 `boost` 调权重）。

映射示例：

```json
PUT docs
{
  "mappings": {
    "properties": {
      "content":   { "type": "text" },
      "tenant_id": { "type": "keyword" },
      "embedding": { "type": "dense_vector", "dims": 768, "index": true, "similarity": "cosine" }
    }
  }
}
```

混合查询（Bool 全文检索 + KNN）：

```json
GET docs/_search
{
  "size": 10,
  "query": {
    "bool": {
      "must":   [ { "match": { "content": { "query": "无人机 返航 电量", "boost": 0.4 } } } ],
      "filter": [ { "term": { "tenant_id": "t1" } } ]
    }
  },
  "knn": {
    "field": "embedding",
    "query_vector": [0.12, -0.03, "..."],
    "k": 10,
    "num_candidates": 100,
    "boost": 0.6,
    "filter": { "term": { "tenant_id": "t1" } }
  }
}
```

要点：

- `knn.filter` 是在 kNN 搜索时的**预过滤**，保证返回 k 个满足条件的结果；而 `query` 里的 `filter` 只作用于全文部分，两处都要写，权限过滤才完整。
- `num_candidates` 越大召回越准但越慢，需大于等于 `k`。
- 分数融合：默认是各路分数加权相加，两路分数量纲不同时，可以调 `boost`。更稳的方式是使用 **RRF**（`retriever` 中的 `rrf`，ES 8.14+，该功能依赖订阅级别许可），或者取回两路结果后在应用层自行做 RRF。
- 版本差异：不同 ES 版本的语法有差异（如较新版本支持在 `query` 中使用 `knn` 子句、`retriever` 语法），使用前请核对所用版本的文档。

### 9. Kafka / RocketMQ 在 Agent 系统里的使用场景——异步工具执行、日志采集、事件驱动多 Agent 通信

**参考答案**

- **异步工具执行**：耗时工具（报表生成、设备巡检、批量处理）通过消息解耦：Agent 发布任务消息 → worker 消费执行 → 结果写回状态存储并通知。优点是削峰、可重试、不占用请求线程。需要消费端幂等（至少一次投递）、失败重试、死信队列、任务状态可查询。
- **日志与 Trace 采集**：Agent 的 Trace、token 用量、用户反馈等异步写入 MQ，再由消费者落到 ES/ClickHouse/数据湖，用于分析、评测集构建、计费。不阻塞主链路，且可承受突发流量，Kafka 的高吞吐适合这个场景。
- **事件驱动多 Agent 通信**：Agent 之间通过 topic 发布和订阅事件（如"工单已创建""设备告警"），实现解耦和异步协作；可以按 key（会话 ID、设备 ID）分区，保证同一对象的消息有序。
- **设备/业务事件接入**：设备告警等事件触发 Agent 主动处理。

选型提示：

- Kafka：吞吐高、生态强、适合日志流和事件流；单分区内有序。
- RocketMQ：天然支持延迟消息、事务消息、重试和死信，适合业务消息和订单类可靠场景。

注意点：消息顺序（按 key 分区）、重复消费（幂等）、消息积压监控、消息体大小（大对象存对象存储，消息只放引用）。

### 12. 假如团队对是否引入一个新 Agent 框架（如 CrewAI / AutoGen / 自研 Harness）有分歧，你怎么推动决策

**答题思路**

重点体现"用事实和流程推动共识"，而不是个人偏好：

1. **对齐问题**：先明确要解决的问题和约束（业务场景、可控性、团队技能、交付周期、可观测与合规要求），把"框架之争"转化为"需求之争"。
2. **定义评估维度**：可控性与调试性、功能匹配度、社区活跃度和稳定性（版本变动是否频繁）、学习成本、与现有基础设施集成、性能与成本、锁定风险、维护成本（自研的长期投入）。
3. **用数据决策**：选一个有代表性的真实场景，限时做 PoC（如 1 到 2 周），按统一评测集对比效果、开发效率、可观测性，而不是靠争论。
4. **降低风险**：用适配层/抽象接口隔离框架，保证后续可替换；可以先在非核心业务试点，设定退出条件。
5. **决策与记录**：召开评审，写决策文档（ADR），记录选择理由、放弃的选项和复盘时间点；少数意见保留，实施后按指标复盘。
6. **沟通方式**：倾听异议，承认各方案优点，决策后全员对齐执行。

### 13. 你觉得自己相比其他 AI 应用工程师最核心的竞争力在哪

**答题思路**

不要空喊"学习能力强"，要给出 1 到 2 个可被证据支撑的差异点：

1. **选定定位**：例如"把 Agent 从 Demo 做到可上线的工程化能力"，或"后端基础扎实加 LLM 应用经验"（Redis、MQ、数据库、高并发经验迁移到 Agent 系统的容错、幂等、可观测）。
2. **举证**：每个点配一个真实案例，用"问题 → 我的做法 → 结果"说明，例如评估体系、降级策略、Bad Case 处理。
3. **与岗位匹配**：说明为什么这些能力正是大疆这类设备控制、工业场景需要的（可靠性、安全、可控）。
4. **保持谦逊**：补一句自己仍在提升的方向，不贬低他人。

### 14. 手撕算法：LeetCode 139 单词拆分（Word Break），给定字符串 s 和单词字典 wordDict，判断 s 是否可由字典中单词拼接而成

**参考答案**

思路：动态规划。`dp[i]` 表示 `s[:i]` 能否被拆分。`dp[0] = True`；对每个 `i`，若存在 `j < i` 使得 `dp[j]` 为真且 `s[j:i]` 在字典中，则 `dp[i] = True`。答案是 `dp[n]`。字典用集合以 O(1) 查询；可以用最大单词长度限制 `j` 的范围来剪枝。

复杂度：加最大单词长度 L 剪枝后，共 O(n × L) 次判断，每次切片和哈希 O(L)，时间约 O(n × L²)；不剪枝最坏 O(n³)。空间 O(n)（不计字典）。

```python
from typing import List


def word_break(s: str, word_dict: List[str]) -> bool:
    words = set(word_dict)
    if not words:
        return False
    max_len = max(map(len, words))

    n = len(s)
    dp = [False] * (n + 1)
    dp[0] = True

    for i in range(1, n + 1):
        # 只需要检查长度不超过最长单词的片段
        for j in range(max(0, i - max_len), i):
            if dp[j] and s[j:i] in words:
                dp[i] = True
                break
    return dp[n]
```

易漏点：`dp[0] = True` 作为空串的初始状态；字典中的单词可以重复使用；用 DFS 需要记忆化，否则会指数级超时。

## HR面

### 1. 自我介绍

**答题思路**

HR 面的自我介绍侧重"稳定性、动机和与岗位的匹配"，不用太深入技术细节：

1. 基本情况：学历、年限、方向。
2. 一两个代表性经历：职责和成果，用通俗的语言讲。
3. 个人特质：沟通协作、责任心、学习能力，配一个简短的例子。
4. 求职动机：为什么做 AI Agent，为什么对大疆感兴趣。

控制在 1 分钟左右，语速平稳。

### 2. 为什么想来大疆，对 DJI 的 AI Agent 方向有什么了解

**答题思路**

答案要真诚，建立在你真实了解的信息上，不要编造内部信息：

1. **对公司的认知**：从公开信息出发，如在无人机、影像、手持设备、机器人等领域的产品和技术积累，软硬件结合、重视工程和产品质量。
2. **对 AI Agent 方向的理解**：设备控制与智能交互、行业应用（巡检、测绘等）中的知识问答和工单流程，强调**可靠性、安全性和实时性**，这和一般的聊天机器人有区别。
3. **个人匹配**：你的项目经验中哪部分能直接迁移（工具调用、RAG、容错与可观测）。
4. **成长诉求**：想在软硬件结合的真实场景中做可落地的 Agent。

避免只说"公司大、待遇好"。

### 3. 讲一个你最自豪的项目经历，你在里面承担的角色和贡献

**答题思路**

用 STAR 结构，重点放在"你个人的贡献"：

1. **背景（S）**：项目要解决什么问题，难度在哪里。
2. **任务与角色（T）**：你的职责边界，是负责人还是核心成员。
3. **行动（A）**：讲 2 到 3 个关键动作，包括遇到的困难和你的决策。
4. **结果（R）**：业务或技术上的真实成果（只说真实数据），以及团队或他人的评价。
5. **反思**：学到了什么，以后怎么做得更好。

HR 面不需要过多技术细节，讲清楚"自豪点"（解决难题、推动协作、带来价值）。

### 4. 遇到和产品/算法/后端意见不合时你怎么沟通协调，举个具体例子

**答题思路**

用一个真实例子，按以下顺序：

1. **场景**：分歧点是什么（如产品要求的效果与实现成本冲突）。
2. **先理解对方**：了解对方的目标和约束，而不是争对错。
3. **用事实和数据沟通**：做小实验、拿评测数据或线上数据，把争论变成对比。
4. **提供选项和折中**：给出备选方案与各自代价，让决策人能权衡。
5. **结论与落地**：达成一致后推进，必要时请上级或负责人拍板，事后复盘。

要体现的态度：对事不对人、尊重分工、结果导向。避免把他人说成"不懂技术"。

### 5. 同时接多个需求或 Bug 时你怎么排优先级

**答题思路**

1. **先澄清信息**：影响范围、紧急程度、截止时间、业务价值。
2. **分级标准**：线上故障和安全问题最高（先止损、再根治），然后看"重要且紧急"的需求，再看重要但不紧急的，低价值的协商推迟或拒绝。可用"影响面 × 紧急度 × 成本"的方式评估。
3. **沟通对齐**：与产品、负责人确认优先级，不自行默默决定；资源不足时明确说明取舍和风险。
4. **执行方式**：拆分成小任务，先做快速见效的，预留机动时间处理突发问题，及时同步进度。
5. **复盘**：减少反复救火，推动监控告警和自动化测试，从源头降低 Bug。

### 6. 你期望的工作氛围和团队风格是什么样的

**答题思路**

回答要真诚，同时与团队特点相匹配：

1. **关键词**：开放坦诚、技术驱动、结果导向、乐于分享、鼓励试错且重视复盘。
2. **理由**：说明这样的环境如何让你发挥（如 Agent 方向变化快，需要快速验证和共同讨论）。
3. **你的贡献**：你也愿意参与分享、写文档、帮助他人，而不是只"索取"环境。
4. **适应性**：表明你能适应不同的节奏和风格，不要给出过于苛刻或负面的条件，也不要贬低以前的团队。

### 7. 你的职业规划三年想做到什么程度

**答题思路**

不要编造夸张目标，突出"方向清晰、可落地、与公司一致"：

1. **第一阶段（约半年到一年）**：快速熟悉业务和技术栈，独立承担模块，做出可衡量的成果。

3. **第三阶段（三年左右）**：在技术深度上成为该领域的骨干，并带动团队（指导新人、技术分享），能对业务结果负责。
4. 说明规划与公司业务绑定，愿意随业务需要调整，避免过早定死管理或纯技术的单一路径。
