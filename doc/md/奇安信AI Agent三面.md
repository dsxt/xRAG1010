# 奇安信 AI Agent 三面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这岗不像招 Agent 工程师，像招能跟攻防人员对线、又能把 Golang/C++ 落地的人。一面就别想背八股了，Prompt Injection、SSRF、工具调用越权这些不问虚的。二面开始拼实战，没真做过多 Agent、RAG、沙箱隔离，基本聊两句就露馅。三轮不考你写代码，考你脑子清不清：Agent 安全不是加个围栏就完事，得懂攻击面，也得懂工程边界。整体很硬，但爽，比那些「说说 Transformer 原理」的面试尊重人。

## 一面

### 1. 自我介绍

**答题思路**

控制在一分半到两分钟，按「我是谁 → 和这个岗相关的两段经历 → 把话口留给边界问题」。

1. 年限和主语言。后端为主，Golang 能独立写服务，C++ 说过检测、插件或沙箱里你真写过的那一层。没写过的语言不要报。
2. 安全相关的工程挑一件：权限、审计、不可信输入、隔离或高并发网关。说清你负责的模块和线上约束（延迟、误报、故障时怎么停）。
3. Agent 挑一个能产生真实动作的项目，两句说完：谁在用、链路、你守住的那道闸门。调用量、延迟、成本只用你能解释的数。
4. 收尾点到这个岗：既能把工具调用落到 Go 服务里，也能说清攻击面。主动把下一步引到权限或隔离，方便面试官往下挖。

不要从 Transformer 结构讲起，也不要把简历上的中间件名单念完。

### 2. 讲一下你做过的 AI Agent 项目，整体架构和调用链路

**答题思路**

用你真实做过的项目讲 3 到 4 分钟。项目名用真的，没有把握的数字就说口径，不要临时编。

1. **动作边界**：用户是谁，Agent 可以读什么、可以改什么。先说明哪些步骤是固定流程，哪些才需要模型现选工具。
2. **链路**：接入鉴权 → 按身份裁剪可用工具 → 规划 → 工具代理执行 → 把工具结果当不可信数据回灌 → 校验或一次反思 → 回复、草稿或人工。旁边标记忆、审计和沙箱。
3. **你的职责**：网关、工具代理、检索过滤、运行时、评测，点明哪一段是你设计和上线的。
4. **闸门放在哪**：模型提议，服务端决定能不能执行。举一个你真实拦住过的调用（越权参数、重复提交、超时后的重试）。
5. **结果**：完成率、人工接管率、工具失败率，口径要和日志对得上。
6. 收尾留一个你愿意展开的难点，例如委托身份、沙箱或轨迹。不要把所有优化点平铺完。

### 3. Agent 里 Planning、Memory、Tool Calling、Reflection 分别怎么落地

**参考答案**

结论：四段都落在运行时里，模型只提议；安全场景默认「显式计划 + 有写入策略的记忆 + 网关执行工具 + 无副作用的校验」。

- **Planning**：规划器输出结构化步骤（目标、工具名、参数、停止条件），运行时先对照工具白名单和步数预算，再执行。只读、三步以内的任务可以用 ReAct；会改状态的任务用计划加执行，失败才重规划，并设重规划次数。计划文本本身不能扩大权限。
- **Memory**：按生命周期拆开。当前运行用检查点，会话用带过期时间的摘要，长期记忆按租户和用户做访问控制。写入要带来源：用户原话和工具返回分开存。工具返回和网页正文不能写进系统指令槽。检索时带过滤条件，过期和无权的记录不进上下文。
- **Tool Calling**：工具目录是代码或签名后的注册表，包含名字、JSON Schema、是否有副作用、超时和幂等要求。模型输出只是候选；网关做模式校验、参数策略和鉴权，再去调下游。
- **Reflection**：优先用确定性检查（模式、证据编号、策略）。需要模型再看一眼时，批评者只读，不能调用会改状态的工具，并且最多一轮。它发现的问题写进轨迹，决定权仍在策略。

面试里容易把 Reflection 讲成再挂一个什么都能调的 Agent。那样只是把循环变长，信任边界没有变化。

### 4. Agent 调用外部工具时，怎么做权限控制和审计

**参考答案**

结论：一次调用要同时满足三层权限——用户本来就能做、这个 Agent 被允许做、这次参数落在策略里——并且判决和参数要留下不可改的审计。

身份使用用户委托后再收窄的令牌，受众、范围和有效期都限制住。下游系统用这枚令牌自己鉴权，这样工单和仓库的访问控制仍然有效。有副作用的工具和只读工具分开注册。策略看具体参数：收件人、仓库、库表、金额、批量大小，只看工具名不够。不可逆动作加人确认，确认记录和这次运行绑在一起。

审计至少记下：租户、用户、Agent、模型版本、工具目录哈希、策略版本、工具名、参数、结果码、耗时、拒绝原因、追踪号。密钥和令牌打码。日志写到 Agent 改不到的存储，追加写。

重试前先查这枚幂等键有没有已经成功，避免超时后再发一次信、再改一次单。面试里要补一句：模型输出「允许执行」不算鉴权，鉴权发生在模型外面。

### 5. 如果 Agent 能执行 shell 命令，怎么防止它被执行恶意命令

**参考答案**

结论：默认不要通用 shell。必须执行时，二进制和参数来自白名单，用 argv 直接执行，进程放在没有内部网络、没有宿主凭证的沙箱里。

运行时不把模型给出的字符串交给 `sh -c`。分号、管道、命令替换的黑名单挡不住引号和编码。先把候选解析成程序路径加参数数组，程序和子命令必须在白名单里，路径限制在这次任务的工作目录内。环境变量改成最小集合，避免把云凭证和 `LD_PRELOAD` 继承进去。

进程用独立用户、只读根文件系统、丢掉 capabilities，并用 seccomp 收紧系统调用。网络默认拒绝。`CommandContext` 绑定这次运行的上下文，取消时杀掉整个进程组，然后 `Wait`，避免留下子进程和僵尸进程。标准输出限制长度。高危命令即使在白名单里，也要人工确认。

审计保存实际 argv，保存模型说自己「已经检查过」没有意义。工具返回同样当成不可信数据，不能因为它来自你的沙箱就写进系统提示。

```go
cmd := exec.CommandContext(ctx, bin, args...)
cmd.Env = []string{"PATH=/usr/bin", "LANG=C"}
cmd.Dir = workspace
if err := cmd.Run(); err != nil {
    return err
}
```

`bin` 和 `args` 来自白名单解析结果。`Env` 设了之后不会继承父进程环境；`Env == nil` 才会继承。

### 6. Prompt Injection 在 Agent 场景下比普通大模型更严重，为什么

**参考答案**

结论：普通对话被注入，坏掉的通常是这一段回复；Agent 被注入，坏掉的是它有权做的那些动作，而且指令可以来自它正在读的数据。

严重在四处：

1. **有副作用**。模型后面接着邮件、数据库、工单、shell 和消息队列，输出会变成外部状态。
2. **权限更集中**。助手往往同时拿着读邮件、查知识和发消息的委托，攻击者借的是这把聚合后的权限。
3. **间接注入**。网页、邮件、工单和检索片段都会进上下文。攻击者不需要和机器人对话，只要把指令写进它一定会读的内容。审计里看起来像正常的「阅读邮件」。
4. **会留下来**。如果运行时把工具返回写进长期记忆或知识库，后面的会话会继续吃到这段指令。多 Agent 还会把被污染的文本当成下一个任务。

分隔符和提高警惕的系统提示能降低概率，成不了边界。边界是：不可信文本没有调用工具的权力，工具参数由网关按策略检查。

### 7. 用户给 Agent 发一段网页内容，Agent 自动抓取并总结，怎么防 SSRF

**参考答案**

结论：抓取发生在模型外面、没有内网路由的出网代理上。模型只能提交 URL，能不能连由代理决定。

代理只允许 `https`。用严格的 URL 解析器去掉用户信息段，拒绝 `file`、`gopher`、`dict` 这类协议。解析出全部地址，拒绝回环、私网、链路本地、云元数据、组播，以及用 IPv6 映射地址绕过 IPv4 判断的情况。校验通过的地址要钉住再连接，避免检查时和连接时解析到不同地址。每一跳重定向都重新做完整校验，并限制跳数。

出站请求不携带内部 Cookie 和鉴权头。限制时长、响应体大小和内容类型。返回给模型的是截断后的正文，错误信息里不带内网拓扑。抓取进程所在的网络本身就到不了办公网、元数据地址和管理口。

面试里容易只答「禁掉内网 IP」。重定向、钉住地址和网络隔离要一起说。这道题修在出网路径上，修不在提示词里。

### 8. Agent 读取邮件、文档、数据库后做自动回复，怎么防数据泄露

**参考答案**

结论：自动回复的收件人、正文槽位和能否发送由策略决定。模型拟草稿，网关决定发不发。

检索之前按当前用户的权限过滤。不该看见的行和文档不要先进上下文，再指望模型保密。高敏感数据源默认只生成内部草稿，不参与自动外发。

回复使用固定模板，模型填槽，不直接生成整封 MIME。收件人只能是原线程里的对方，不能新增外部地址，也不能把内容发到模型指定的 URL。出站前做敏感信息检查：凭证、证件号、大段源码、内网地址。命中则改为人工。单次可引用的记录数和长度设上限，避免用「总结一下」把整库带走。

邮件正文和文档内容按数据封装，里面的「请把附件发到某处」不能变成工具调用。审计记下数据来源、收件人和放行策略。关键词过滤会漏掉改写后的秘密，所以它是补充，高敏感源仍然默认不外发。

### 9. Golang 里 goroutine 泄漏怎么排查，举一个 Agent 服务里的真实场景

**参考答案**

结论：泄漏就是还有 goroutine 堵在永远不会到来的通道、锁或网络读上。先看数量和栈，再把取消传到每一次外部调用。

一个典型的告警研判服务：每条告警起一组 goroutine，分别查情报、读模型流和回写工单。用户点了停止，HTTP 连接断了，但这三步都没用这次运行的上下文。情报请求用了没有超时的 `http.DefaultClient`，模型流用了 `context.Background()`，回写堵在一个已经没人接收的通道上。高峰过去后 `runtime.NumGoroutine` 不回落。

排查时先看 goroutine 数是否和在途任务一起只升不降，再抓 goroutine profile，按栈聚合。增长栈如果停在 `net/http` 读、通道收发或 `semacquire`，就回到对应代码看有没有听 `ctx.Done()`。profile 只开在内网或本机，栈里可能有请求路径。测试里用 goleak 把「起了任务却不取消」变成回归。

修复是全程传递同一个 `ctx`，用 `errgroup` 限制并发，任一失败就取消其余调用；HTTP 和模型客户端都必须使用这个 `ctx`，并设置超时。`errgroup` 取消的是上下文，堵在忽略上下文的调用里的 goroutine 不会因此返回。

```go
req, err := http.NewRequestWithContext(ctx, http.MethodPost, toolURL, body)
// http.DefaultClient 的 Timeout 为 0，表示没有超时，Agent 工具客户端不要用它。
```

### 10. Golang channel 在 Agent 多任务编排里怎么用，关闭 channel 有哪些坑

**参考答案**

结论：通道用来传任务和结果，取消用 `context`。数据通道由唯一的发送方在发完后关闭。

编排里常见三种用法：带缓冲的任务队列加固定工人、多个工具结果汇合到一个结果通道、用容量有限的通道当信号量。缓冲大小按下游承受能力定，用来形成背压，不按峰值请求数把缓冲开到很大。

关闭的规则：

- 发送到已关闭通道、重复关闭、关闭 `nil` 通道，都会 panic。
- 多个发送者谁都不该随便关闭。取消改由 `ctx` 广播，或者只留一个聚合方在 `WaitGroup` 结束后关闭输出通道。
- 对已关闭通道接收会立刻得到零值。`for range` 会在关闭后退出；`case v := <-ch` 如果不看 `ok`，会空转把 CPU 打满，goroutine 也退不掉。
- 关闭带缓冲的通道不会丢掉还没取走的值，接收方还能排空。
- 数据和取消不要共用一个通道。接收方把通道设成 `nil` 可以在 `select` 里关掉这个分支，这和 `close(nil)` 完全是两件事。

```go
func fanIn(ctx context.Context, workers ...<-chan Event) <-chan Event {
    out := make(chan Event)
    var wg sync.WaitGroup
    for _, ch := range workers {
        wg.Add(1)
        go func(ch <-chan Event) {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case ev, ok := <-ch:
                    if !ok {
                        return
                    }
                    select {
                    case <-ctx.Done():
                        return
                    case out <- ev:
                    }
                }
            }
        }(ch)
    }
    go func() {
        wg.Wait()
        close(out) // 只有聚合方关闭 out
    }()
    return out
}
```

调用方停止读取时要取消 `ctx`，否则工人会堵在发送上。父流程不要再关闭一次 `out`。

### 11. Golang 上下文取消 context.Context 在 Agent 超时、中断、人工介入时怎么设计

**参考答案**

结论：一次运行一棵上下文树。超时、用户停止和人工接管都要留下原因；等人审批时把状态落盘，脱离网关这次 HTTP 请求的寿命。

入口用 `context.WithoutCancel` 保留追踪号这类 value，同时避开客户端断开或网关超时把整次运行提前取消。在这之上用 `WithCancelCause` 记录原因，再用 `AfterFunc` 在预算耗尽时取消。工具和模型调用都使用这棵树的子上下文，子超时短于整次运行的预算。`CommandContext` 和 HTTP 请求必须带上它，取消才真的停得下来。

原因要能区分超时、用户停止、被新消息取代、人工接管。业务结果另记；`cancel(nil)` 只负责释放，第一次写入的 cause 不会被后面的 `cancel` 覆盖。正常结束也要 `Stop` 定时器并调用 `cancel`，避免定时器和子上下文泄漏。

人工确认可能要几分钟到几小时。把运行检查点写下来：运行号、步号、已成功的幂等键、等的是哪一次确认。进程可以结束。确认到达后用同一个运行号新建上下文继续。干等在一个 goroutine 里，既占着工人，也会在发布时把运行丢掉。

```go
base := context.WithoutCancel(reqCtx)
ctx, cancel := context.WithCancelCause(base)
defer cancel(nil)
timer := time.AfterFunc(budget, func() { cancel(errTimeout) })
defer timer.Stop()
// 用户停止或人工接管：cancel(errUserStop) / cancel(errHandoff)
// 结束后用 context.Cause(ctx) 写入轨迹
```

### 12. C++ 侧如果做 Agent 插件或沙箱模块，智能指针怎么管理生命周期

**参考答案**

结论：宿主独占插件和沙箱进程，用 `unique_ptr`；会话被多个回调共享时用 `shared_ptr`，工作线程只留 `weak_ptr`。跨动态库不要用智能指针传递所有权。

插件对象、沙箱 pid 和管道描述符由宿主用 `unique_ptr` 持有，自定义删除器里做终止进程、`wait` 和关闭描述符，避免析构漏杀或留下僵尸。卸载顺序固定：停止接收新任务，取消并 `join` 工作线程，确认没有调用栈还在插件代码里，再 `reset`，最后才 `dlclose`。删早了就是工作线程执行到已卸载的代码。

会话需要共享时，对象先放进 `shared_ptr`，再使用 `enable_shared_from_this`。构造函数里调用 `shared_from_this` 会抛 `bad_weak_ptr`。工作线程锁 `weak_ptr`，锁不到就退出。插件不要再用 `shared_ptr` 指回宿主，否则环会让两边都析构不了。

`shared_ptr` 的控制块拷贝是线程安全的，对象本体不是。同一个裸指针不能交给两个智能指针。动态库和宿主如果不是同一套运行时，`shared_ptr` 不能穿过 ABI；导出 `create` / `destroy` 的 C 接口，各自在自己的堆上释放。

关闭时不要握着会话锁去 `join` 还要抢这把锁的线程。

### 13. C++ 里多线程访问 Agent 共享状态，怎么避免竞态和数据污染

**参考答案**

结论：会话状态尽量归一个执行流改；必须共享的配置用不可变快照发布。锁的临界区里不做模型调用和工具 I/O。

每个会话的记忆、预算和步骤都交给同一条执行流串行修改，这一块就不必再加锁。策略、工具目录这类读多写少的数据，整体换成 `shared_ptr<const Policy>`。读者拷贝指针后放开锁，写者构造一份新对象再替换指针。C++17 可以用 `shared_mutex` 保护这枚指针，C++20 也可以用 `atomic<shared_ptr<const Policy>>`。指针替换是线程安全的，`Policy` 里面没有锁，所以旧快照不能再改。

计数器可以用 `std::atomic`，统计用 `memory_order_relaxed` 即可。不要用 relaxed 的原子裸指针发布一块还会被改的状态。多把锁用固定顺序或 `std::scoped_lock`。持锁期间不能调用插件回调，回调可能重入。

数据污染还来自复用：线程池里的 `thread_local` 缓冲、对象池和全局「当前提示」如果没清空，会把上一个租户的正文带进下一次运行。放过程密钥或提示词的缓冲用完即弃，或者在归还前清掉。不可信工具输出先校验，再写入会话状态，不能直接追加到全局记忆。

数据竞争是未定义行为，靠「测试没踩中」证明不了。数据竞争用 ThreadSanitizer 抓，析构和越界用 AddressSanitizer。

### 14. Agent 调用 LLM 超时、返回脏数据、工具失败，整体怎么兜底

**参考答案**

结论：每一段有自己的超时和失败类型，整次运行有预算；失败时降到「说清做了什么、不确定的标未知」，不要编造成功。

超时分成模型、单个工具和整次运行三层，子超时之和不能靠重试把总预算撑破。只对幂等读做有限次退避重试。写操作必须带幂等键，超时后先查结果再决定要不要重试。模型供应商连续失败时熔断，切换备用模型或直接转人工。

脏数据包括不合模式的 JSON、表外工具名、过大的参数，以及夹在自然语言里的命令。用模式校验和大小限制，非法就带错误信息做一次修复。修复仍失败，就返回固定的失败说明。不要从散文里正则提取命令再执行。工具结果里的文本不能覆盖系统策略。

工具失败分成可重试（超时、429、503）和不可重试（鉴权、参数、找不到）。把已完成步骤放在检查点里，回复里列出已完成和未完成。降级顺序：收紧工具集到只读、换小模型、规则引擎给出确定性结论、转人工。安全场景的降级结果是未知或拒绝，默认放行会把故障变成误处置。

### 15. 红队视角：如果你要攻击一个企业里的 AI Agent 助手，你会先打哪几个点

**参考答案**

结论：先看它的身份和数据通道。提示词只是把已经存在的权限用起来，权限上限由工具和令牌决定。

按杠杆从高到低看这几处，每一处都对应一道闸门：

1. **工具和身份**。它能读哪些系统、能写哪些系统，用的是不是一把覆盖全员数据的服务账号。闸门是按用户委托并且再收窄的令牌。
2. **它一定会读的内容**。邮件、网页、工单、知识库都可以携带间接指令，审计里仍像一次正常阅读。闸门是这些文本不能触发工具，参数策略不看正文怎么说。
3. **出网和抓取**。总结链接、webhook 和「帮我请求这个地址」既可能碰到内网，也可能把数据带出去。闸门是出网代理和目的地白名单。
4. **记忆和知识库的写入口**。一次写入会留到后续会话。闸门是写入审核、来源标记，以及指令槽不接收外部正文。
5. **人的确认**。助手可以把敏感内容写进看起来正常的回复，或引导同事点批准。闸门是确认界面展示真实动作和参数，审批按运行号绑定。

面试时按「入口、能碰到的权限、留下的痕迹」讲。只说会做提示词注入，深度不够。

### 1. 自我介绍

**答题思路**

1. 一句话：年限、Golang 为主或 Go/C++ 双栈、最近做的是能执行动作的 Agent。

### 2. 讲一个你最复杂的 Agent 项目，哪里最难，你怎么啃下来的

**答题思路**

只讲一个项目，按「难在哪 → 怎么拆 → 怎么验证 → 留下什么限制」讲 4 分钟左右。公司和指标用真实的。

1. 用两句重建背景：动作有副作用，还是只读分析；用户和攻击者可能控制哪些输入。
2. 难点选一个真正卡过你的，例如工具权限和业务 ACL 对不齐、沙箱逃不出但性能不够、检索把无权文档带进了上下文、重试导致重复处置。先说错误现象。
3. 拆法：你把哪部分从模型里拿出来做成确定性代码，留了哪些状态（检查点、幂等键、策略版本）。备选方案是什么，为什么没选。
4. 验证：回归集、影子模式、线上的哪条指标告诉你修好了。没有指标就说你看的日志口径。
5. 收尾讲残留风险和你现在仍会加的限制。面试官接着会问失败模式，不要把结果说成永久消灭了注入或幻觉。

### 3. 多 Agent 协作时，任务怎么拆分，消息怎么路由，状态怎么同步

**参考答案**

结论：按权限和职责拆，由编排器持有状态机。处理过不可信内容的工人不能直接指挥有副作用的 Agent。

拆分看边界：编排器负责计划和授权内的下一步；检索、告警解释这类工人只有只读工具；批评者没有工具。不要为了「多 Agent」把同一份权限复制给每一个角色。

路由使用类型化消息。`TaskAssignment` 只能由编排器发出，`Observation` 是工人的观察，按不可信数据处理。消息里带租户、任务号、因果号和输入哈希。模型可以建议下一个角色，真正把有副作用的任务发出去的是策略检查之后的编排器。

状态以编排器的检查点为唯一事实来源，按步号版本化。工人拿到的是快照加本步输入，不共享一块可写内存。传递至少一次，工具侧用幂等键挡住重复。失败就停在当前步，记录原因，可以改派；补偿动作也走同一套鉴权。

同步延迟是显式的：下一步只能读已经落盘的观察，不能读工人进程里还没提交的草稿。

### 4. Agent 在企业内网里接 OA、工单、知识库、代码仓库，认证和鉴权怎么设计

**参考答案**

结论：下游系统自己的访问控制仍然生效。Agent 使用当前用户委托下来、再被工具策略收窄的身份。

用户登录走企业身份源。网关做令牌交换，换成受众分别是 OA、工单或 Git 的短期令牌，范围是「用户原本拥有」和「这个工具允许」的交集。下游用这枚令牌再鉴权一次，仓库和工单不用在 Agent 里复制一套权限表。知识库在检索时就按用户可见范围过滤，无权片段不能先进入提示词。

写操作使用单独的范围，默认人工确认。服务之间用双向 TLS。令牌放在密钥管理系统，不进提示词，日志里打码。老系统如果没有令牌交换，就按用户保存可吊销的刷新凭证，仍然不要合成一个能看所有人数据的服务账号。

面试里把这句说完整：在系统提示里写「只访问该用户的数据」，同时工具使用超级账号，等于没有鉴权。

### 5. Agent 执行代码或运行沙箱，怎么做到隔离：进程、容器、seccomp、eBPF 随便展开

**参考答案**

结论：隔离分层做。能用结构化工具就不要执行代码；必须执行时，每次任务一只新沙箱，默认没有内部网络，也没有宿主凭证。

进程层：独立用户，`NO_NEW_PRIVS`，丢掉全部 capabilities，只读根文件系统，工作目录单独挂入。`rlimit` 限制进程数、文件数和地址空间。使用独立的 mount、pid、network namespace。seccomp-bpf 在系统调用入口用白名单，只留这次运行需要的调用。容器运行时自带的默认配置通常是裁掉一批高危调用，不是按任务收紧的白名单。新内核上还可以用 Landlock 让进程自己收紧可访问路径；支持网络规则的版本还可以限制 TCP bind 和 connect。

容器层：非 root、只读根、丢 capabilities、自定义 seccomp，不挂宿主网络和容器套接字。容器仍共享内核。不可信代码再用 gVisor 这种用户态内核，或 Kata 这类跑在 Firecracker 等微虚拟机上的运行时，把内核隔开。

eBPF 适合观测和补充拦截：非预期的 connect、exec、写敏感路径，可以告警或配合策略拒绝。它是运行时防线的一层，代替不了 namespace、seccomp 和虚拟机边界。

超时后杀整个进程组，限制输出大小。沙箱的标准输出回到模型时仍按不可信数据封装。策略在运行时外，不由提示词开关。

### 6. 如果 Agent 能调 Kafka/RocketMQ 发消息，怎么防止被滥用成投毒或刷消息

**参考答案**

结论：Agent 不能往任意主题发任意正文。命令类主题不接受模型起草的消息，下游只承认网关身份发出的、符合模式的消息。

工具参数里的主题来自白名单，系统使用的重试、死信和控制主题不在其中。消息体用登记过的模式校验，限制大小和批量。速率和配额按租户、Agent、主题三层计，多实例用共享计数。幂等生产者解决的是同一条消息重试造成的重复，拦不住模型发出一万条内容不同的消息，刷消息要靠配额。

网关以自己的身份发送，并给消息签名或写入下游能核验的来源标记。模型不能指定被下游当成命令的头部、标签或分区键。下游把正文当数据；如果另一个 Agent 会消费它，这段正文仍然是不可信输入，不能进入对方的指令槽。

「关闭告警」「下发封禁」「改情报」这类主题只接受经过人工或确定性流程发布的消息。审计记下主题、键、模式版本和策略判决。配额组件故障时，能改状态的发送直接拒绝。

### 7. RAG 场景里知识库被植入恶意文档，Agent 怎么被影响，怎么检测

**参考答案**

结论：恶意文档会改变回答，也会在运行时把工具调用带偏；检测做不到闭合，摄入权限和「检索文本不能发号施令」才是边界。

影响有三条。检索命中后，文档里的指令和隐藏文本进入上下文，模型可能按它改口或去调工具。如果回答会写回知识库或长期记忆，这段内容会留下来。引用看起来像正规制度，用户和下游流程会更相信它。

摄入侧：知识库写入走审核和来源签名，Agent 的输出不能直接成为高信任文档。按租户和权限建索引，检索时先过滤。入库时做大小、类型和隐藏文本检查（极小字号、注释、零宽字符），这是卫生措施，绕过它并不意外。

运行侧：检索片段以数据字段进入提示，工具调用仍走网关白名单。策略比较「用户原来请求的动作」和「实际工具参数」，由正文突然提出的外发、改库和执行默认拒绝。轨迹里留下文档版本和哈希，便于回放是哪一篇带偏的。

检测用固定问题集和金丝雀文档看索引有没有被投喂，再用「有害动作是否只在命中某篇之后出现」做关联。发现后下线文档版本、清掉由此写入的记忆，并复跑回归集。不要把检测模型当成唯一闸门。

### 8. Golang 写高并发 Agent 网关，百万级任务事件怎么削峰、限流、降级

**参考答案**

结论：入口快速鉴权、去重、入队；模型的并发按配额封顶。百万级事件里，大部分应被规则和聚合吃掉，而不是各打一次模型。

削峰：网关把事件写入 Kafka 或已有的 RocketMQ 后尽快确认。分区键用租户，配合配额，避免一个租户占满所有分区。消费端是固定工人池，空闲工人数按模型时延和配额反推。进程内再用有界信号量保护客户端。队列深度超过水位，就拒绝新的低优先级请求，并告诉调用方稍后重试。

限流分三层：全局保护模型供应商，按租户避免互相饿死，按工具保护 OA 或扫描器。单机令牌桶只管本进程的突发；多实例的配额放在共享存储。令牌桶适合允许少量突发，窗口计数适合按租户做硬配额。限额组件故障时，有副作用的工具拒绝，只读分析可以排队。

降级顺序写进策略：去掉反思和长上下文，换更小的模型，改走规则引擎，最后只保留入队。告警场景降级后的结论是未知并转人工。去重和聚合放在调用模型之前，相同指纹的事件在时间窗里合并。

舱壁要加在模型客户端和每个下游上。只在入口限流时，一个慢依赖仍会占满工人池。goroutine 数量、在途数、队列深度和拒绝率要有指标。

### 9. C++ 侧做安全检测模块，怎么处理不可信输入，防溢出、防格式化字符串、防反序列化漏洞

**参考答案**

结论：检测模块解析的文件、流量和规则都是攻击者控制的。先限制大小和复杂度，再用内存安全的写法解析；模块跑在低权限的独立进程里，崩溃不能变成宿主的代码执行。

溢出：使用 `std::vector`、`std::string` 和带长度的视图，去掉 `strcpy`、`sprintf`、`gets`。分配前检查长度，加法或乘法用能发现回绕的检查，避免 `n + 1` 回绕成很小的缓冲区。嵌套层数和循环次数设上限，用来挡住压缩炸弹和深层结构。能用模糊测试打这个解析器就加上，AddressSanitizer 进 CI。

格式化字符串：不可信字节只作为数据。`printf`、`syslog` 和任何把外部字符串当格式串的接口，格式都用字面量，例如 `printf("%s", s)`。影响是越界读，部分转换符还会写内存。编译打开格式串告警。

反序列化：用带模式的 protobuf 或 JSON，显式限制总字节数和嵌套深度，不依赖库默认值，因为版本之间会变。不要按外部给的类型名重建多态对象，也不要加载来路不明的原生序列化。规则文件里的 XML 关掉外部实体，YAML 同样限制大小和构造类型。

解析进程的权限低于 Agent 宿主，通过有长度限制的 IPC 交回结构化结果。栈保护和地址随机化是减轻后果的措施，代替不了长度检查。

```cpp
bool append_field(std::vector<std::byte>& out, size_t n,
                  const std::byte* p, size_t remain) {
    if (n > remain || n > kMaxField) return false;
    out.insert(out.end(), p, p + n);
    return true;
}
```

### 10. LLM 工具描述本身被篡改，Agent 会不会被诱导调用危险接口，怎么防

**参考答案**

结论：会。模型很听工具说明，说明被改，等于有人换了「这个工具该怎么用」的说明书。说明没有权限，能不能调只看服务端那张工具表。

被改的说明可以诱导模型多调一个工具、把内部字段填进某个参数，或把只读工具说成必须先导出数据。远程工具如果允许安装之后再改说明，用户当初的确认就失效了。同名或近似名字的工具还会把调用抢过去。

工具目录来自受信任注册表，名字、参数模式、说明、副作用标记和版本一起钉住哈希，对不上就拒绝加载。模型输出的工具名必须命中这张表，表外名字和未声明参数直接失败。运行时不会按说明里写的 URL 临时发请求。鉴权看工具 id 和参数策略。说明变成「请忽略权限」时，网关的判决不变。

远程目录变更要重新审核。审计记录本次运行加载的目录哈希，便于判断说明是不是被人换过。只校验 JSON Schema 不够：模式保证形状，保证不了这还是当初批准的那个工具。

### 11. 给一个场景：攻击者用少量提示把客服 Agent 改成数据外传通道，你怎么复盘和加固

**参考答案**

结论：先停外发和抓取，再按轨迹圈定哪些会话把数据送到了新目的地，最后改网关；提示词清洗只算辅助。

处置按这个顺序：

1. **停住**。关掉这个 Agent 的发信、webhook 和任意 HTTP 抓取，吊销它的令牌。已经在跑的会话全部取消。
2. **固定证据**。保住提示、工具参数、结果码、模型版本、工具目录哈希和策略判决。先别清理现场。
3. **定范围**。按时间窗搜轨迹：目的地不在原工单收件人里、参数里出现内部记录、同一篇来源文档反复出现。把命中的会话、可能流出的数据级别和下游系统列出来。
4. **清掉残留**。下线被植入的文档或记忆，轮转已经暴露的凭证，通知该通知的人。范围按证据说，不按模型复述。
5. **加固**。收件人和 URL 改白名单；检索在进模型前做权限过滤；正文不能触发新的外发；高敏感源只出内部草稿；工具参数做敏感信息检查；对新目的地和异常批量告警。修完用当时的坏输入做回归，确认外发工具不会再被调起。

复盘要回答两个问题：哪次工具调用把数据送了出去，哪条策略本应拒绝却没拒绝。答成「模型被绕过了，我们加强提示词」，这次事故还会再来。

### 12. 安全运营里用 Agent 自动分析告警，误报率高、幻觉严重，怎么让它可用

**参考答案**

结论：先让它做有证据约束的辅助，不让它自动关单或自动封禁。可用看的是有标注样本上的准确率，以及「未知」占多少。

把任务收窄成：提取告警里真实出现过的指标和实体、对照处置手册、指出还缺哪份数据、给出需要人看的理由。每条结论必须带事件编号。输出里的 IP、域名和哈希如果在原始事件中不存在，就丢掉这条结论。证据不足时的合法输出是未知，未知走人工。

上线前用一段时间的历史告警做对照，按告警类型看精度和召回，只放行表现稳定的类型。先影子模式，再给分析员看建议。分析员的采纳和驳回写回评测集，确认过的模式沉淀成规则，规则能判的下次不再问模型。

自动封禁、自动关单不放在第一阶段。幻觉的危害在安全运营里是误处置和漏处置，所以失败方向要写成未知，默认无害同样危险。

### 13. Agent 产生的安全事件要不要可回溯，日志、轨迹、工具调用、模型输入输出怎么存

**参考答案**

结论：要可回溯。没有动作轨迹，就无法区分是用户要求、检索文本诱导，还是工具目录被人换过。

一次运行用同一个追踪号串起来，至少留下：

- 身份：租户、用户、Agent、委托范围
- 版本：模型、系统提示哈希、工具目录哈希、策略版本
- 输入：用户消息。检索内容留文档版本和哈希；正文如果敏感，放在更严格的库里，轨迹里留指针
- 动作：工具名、参数、结果码、耗时、错误、幂等键、人工确认
- 输出：给用户的最终回复，以及策略是放行还是拒绝

令牌、密码和密钥打码。存储追加写，和 Agent 的运行身份隔离，Agent 不能删除或修改自己的轨迹。保留期按合规要求定，日志本身的访问再审计一次，因为轨迹里会有敏感正文。时钟用统一授时。

模型内部推理过程按合规要求处理；安全复盘最低限度要有动作序列和输入来源。只有最终回答、没有工具参数的日志，不够用来复盘外传或越权。

### 14. 蓝队视角：你们公司上了 AI Agent，你作为防守方第一周会补哪些短板

**参考答案**

结论：第一周做资产、权限和停机开关，把已经能改状态的路径收紧。不在这一周重写一套检测模型。

1. 列出每个 Agent 的工具、身份、能读的数据和能改的系统。对不上主人的，先下线。
2. 去掉覆盖全员数据的共享账号，改成用户委托；暂时改不了的，把写工具关掉。
3. 确认有一键停掉全部动作的开关，并真的演练一次，记下生效时间。
4. 补齐动作审计，确认运行身份写不了这批日志。
5. 抓取和 webhook 收到出网代理上，目的地没有白名单的先禁用。
6. 检查知识库谁可以写、检索有没有按权限过滤，Agent 能不能把回复写回高信任文档。
7. 核对工具目录和系统提示谁能改，改动有没有哈希和回滚。
8. 给外发、批量读取和异常工具组合加上告警。抽查过去一周的工具参数。
9. 写一页应急步骤：谁有权停 Agent、谁吊销令牌、轨迹存在哪。

第一周结束时应该说得清：它能碰什么、出了事谁能在几分钟内让它停下来。

## 三面

### 1. 自我介绍

**答题思路**

三面的自我介绍突出判断，不重复项目细节。一分钟到一分半。

1. 一句话说明你做过多久后端或安全工程，Agent 是接在这些约束上面的。
2. 用一个决定说明你怎么取舍：哪些动作你拒绝交给模型，哪些你允许在影子模式里试。
3. 补一句协作：你和检测、安服或值班怎么对齐风险，谁对残留风险签字。
4. 收尾说明你想深入的是这个岗的上线边界，把反问留到最后。

这个开场是为了让后面的「压谁、怎么推进、怎么选技术」有抓手。具体项目等对方问再展开。

### 2. 你怎么看 AI Agent 在网络安全里的位置，是辅助、武器还是基础设施

**参考答案**

结论：现在能稳定承担的是辅助。它一旦能调用工具，就要按基础设施来提要求。在身份、停机和审计做完之前，把它当武器，失守时代价最大。

辅助是解释告警、对照手册、起草规则和整理时间线，决定和阻断仍在确定性系统里。这条路径可测，也容许未知。

基础设施指的是平台义务：身份可委托可收窄、策略在模型外、动作可审计、故障时拒绝、分钟级停机。Agent 平台要按这个标准建。单个分析助手还没满足这些义务时，不要说它已经是安全基础设施。

武器指的是它会自动完成攻击或处置。攻击者用 Agent 做自动化，是你的新攻击面；自己的 Agent 被带偏时，也会变成对着内部系统的武器。自动渗透和自动封禁必须有授权范围、闭合的动作空间和人工确认。

所以三个词对应三件不同的事：用法上先做辅助，工程上按基础设施约束，效果上警惕它变成武器。用「会不会取代 IDS」来回答这道题，等于没分清检测和编排。

### 3. 如果让你从 0 搭一个安全场景的 Agent 平台，技术栈怎么选，Golang、C++、Python 各放哪

**参考答案**

结论：信任边界放在 Golang 网关，不可信文件解析放在 C++ 独立进程，Python 负责评估和快速试验。三种语言都能碰到模型，但只有网关能放行工具。

- **Golang**：对外 API、身份和令牌交换、工具代理、队列消费、审计投递。它和模型运行时分成两个进程，Python 里的 Agent 循环不能绕过它去拿 OA 凭证。Go 适合这里的原因是高并发 I/O、单二进制和比较直白的部署，不因为它能防止提示词注入。
- **C++**：已有的检测引擎、YARA 集成、文件和协议解析、沙箱启动器。解析器单独进程、低权限，通过有模式的 IPC 把结构化结果交回来。新解析器如果没有历史包袱，可以用更不易出错的语言；已经用 C++ 写的检测代码，把输入约束和进程隔离做完再谈重写。
- **Python**：评测集、离线对照、提示和模型试验、与模型 SDK 的原型。适合快速改循环，不适合作为唯一的鉴权进程。原型里跑通的工具调用，上线时要迁到网关后面。

旁边的组件按职责选：策略用独立策略引擎，队列用 Kafka 或已有 RocketMQ，检查点用事务数据库，密钥用 KMS，沙箱按风险用容器、gVisor 或微虚拟机。

小团队的取舍是少一种语言就少一分值班成本。人不够时，C++ 只留在已经存在的解析和检测上，Python 只留在离线评估，在线路径收敛到 Go。不要为了语言纯洁把成熟的检测引擎重写一遍。

### 4. Agent 自动渗透测试平台和传统扫描器本质区别是什么，边界在哪

**参考答案**

结论：扫描器在人写好的检查集合里做覆盖；Agent 在运行时选择下一步。差别在动作空间是否闭合、同样的输入能否复现。

扫描器的目标、检查项和速率事先确定，漏报和误报可以回归。它不理解业务上下文，也不会临时发明一个脚本里没有的动作。

Agent 能根据页面、认证状态和上一步结果决定再看什么，适合做优先级、参数推断和结果解释。代价是不稳定、成本高，授权范围也更容易被一步步走宽，还可能给生产带来意外负载。

边界写成运行时能执行的字段：目标、时间窗、允许的检查类别、是否允许有副作用的验证、速率和并发。超出就拒绝。危险和不可逆的验证使用预置的安全检查，模型负责挑选和解释，新检查沉淀回扫描器，而不是永远留在对话里。扫描器继续当覆盖基线。全过程留下轨迹，并且能停。

没有闭合的动作空间和授权对象时，它就是一个能发请求的机器人。智能程度代替不了扫描器的可回归性。

### 5. 安全规则、YARA、Suricata、IDS/IPS 这些能力和 Agent 怎么结合

**参考答案**

结论：规则引擎负责确定性检测和阻断，Agent 负责解释、关联和起草。Agent 不站到数据包的阻断路径上。

YARA 扫文件和内存。Agent 可以根据已确认样本起草规则，上线前用恶意样本和正常样本做回归，检测工程师审核后再交给引擎。Agent 也可以解释某次命中对应哪段特征。

Suricata 和 IDS 产出告警与协议元数据。Agent 按告警编号和时间窗做受限查询，把事件串成时间线，指出缺了什么证据。这个查询接口有身份和范围，避免变成任意下载流量。

IPS 的丢弃和封禁由规则与策略执行。Agent 可以提交变更草案，生产规则的发布走原有变更。确认过的事件再回流成新规则，这条闭环比让模型对每个包重新判断更可测。

延迟、可用性和误封禁的代价都要求阻断留在规则引擎。规则已经能判的，不要再问一次模型。

### 6. 甲方上了 Agent 后最怕什么，乙方卖 Agent 安全方案最容易吹什么

**参考答案**

结论：甲方怕的是它拿着权限做错事还说不清；乙方容易把辅助能力说成已经能替代检测和处置。

甲方最怕的几件事：

- 助手读到不该读的数据，或把内部内容发到外面
- 误封禁、误回信、误改规则，而且停不下来
- 出事之后只有一段模型总结，没有工具参数和策略判决
- 分析员默认相信它的结论，规则和人工复核被绕开
- 提示词、知识和日志里的敏感数据说不清存在哪、谁能看

乙方容易吹的几件事：

- 「自主 SOC」或「替代一批分析员」，却没有标注集上的精度，也没有未知这个输出
- 用一段系统提示宣称已经解决提示词注入
- 把一只普通容器说成隔离边界
- 把接上知识库说成权限已经对齐，检索前并没有做访问控制
- 给出一个检测率，却不说样本、基线和误报怎么算

谈方案时让对方指出：哪次调用能改生产，谁能在几分钟内停掉，轨迹里有没有工具目录哈希。这三件事对得上，再谈模型效果。

### 7. 你最近在学什么，Agent、安全、底层、模型、攻防各学到哪了

**答题思路**

挑一条主线讲深，其余每项最多一句。这个岗更想听学习方式和证据，不想听书单。

1. 先说最近一两个月只挖一条线，例如工具鉴权，或不可信内容进入工具参数的路径。
2. 每条都用同一模板：看了什么一手材料，动手做了什么，卡在哪，对应岗位上的哪道闸门。
3. Agent 讲一个你真的跑起来的运行时：步数预算、工具白名单、轨迹打在哪。框架名字一句带过。
4. 安全讲一个你能画出来的数据流：输入从哪进，动作从哪出，哪次校验不依赖模型。
5. 底层讲到你读过或写过的代码为止。Go 就讲上下文取消和泄漏，C++ 就讲插件生命周期或解析器的长度检查。
6. 模型讲你怎么用同一套坏输入对比过两个模型会不会更听话地执行检索文本。攻防讲你在自己的环境里怎么验证防线，讲到授权边界为止。
7. 收尾留一个还没做完的实验，并说明你准备用什么现象判断学会了。

材料名和结论用你自己的。临时编论文、CVE 或线上事故，追问两句就会露。

### 8. 一个新技术又新又酷但没经过生产验证，一个老技术稳但笨，你咋选

**答题思路**

先问它坐不坐在信任边界上，再问选错了能不能撤。

1. 坐在边界上的用老技术：鉴权、不可信文件解析、沙箱、审计、默认拒绝。这里要的是见过的失败模式，以及出问题时权限不会放大。
2. 可替换、可灰度、不掌握凭证的用新技术：摘要模型、离线评估器、内部效率工具。新旧接在同一个接口后面，先影子对比，再切流量。切不回去就不算准备好。
3. 你要的「生产验证」说具体：失败时会不会扩大权限、能不能关掉、有没有对照数据。博客里的架构图不算验证。
4. 两种都不满足任务时，缩小任务。例如先做只读建议，把没验证过的自动处置留在范围外。
5. 用你自己的一次选择收尾：你选了哪个，观察期看哪条指标，什么信号会让你退回。

判断句可以落在：新东西用来发现问题和提高效率，已经验证过的东西用来守住权限和隔离。

### 9. 你是怎么快速吃透一个安全方向或者一个新模型的，举具体动作

**答题思路**

讲一周内能做完的动作，按顺序说，并配一个你真的这么做过的方向。没有就讲你下一次会怎么做，不要编一个没读过的漏洞。

1. 半天画出数据流：输入、身份、动作、日志。先标信任边界，再看产品名词。
2. 只读一手材料：官方文档、这个方向被引用最多的两三段原始说明、公开事故通告。先把术语和真实行为对齐。
3. 在你有权使用的环境里做最小实验。安全方向验证「哪道闸门生效」；模型方向用同一批坏输入对比两个模型或两个运行时，记录动作差异，而不只记录回答好不好看。
4. 写一页纸：不变量是什么、什么输入会让它失效、你怎么检测失效。
5. 加上限制条件再看一遍：权限、延迟、误报、能不能停。很多演示过不了这四问。
6. 给同事讲十分钟，并回答「换一个入口还成不成立」。讲不清的那一处就是还没吃透的地方。

收尾说你怎么判断自己学会了：能独立把闸门画对，并能指出一个还没验证的失败模式。

### 10. 带人做 Agent 安全项目时，开发和安服意见不一致，你压谁，依据是什么

**答题思路**

不按嗓门和职级站队。把分歧收成一个具体动作，再看失败代价和能不能撤。

1. 先写清动作：例如沙箱要不要出网、工具能不能发信、检索要不要先过权限。写成「做成会怎样，不做会怎样」。
2. 信任边界上的分歧，默认取更保守的一边。越权、外发和代码执行，安服指出的失败模式如果成立，就不要用进度把它压过去。
3. 体验和成本上的分歧，如果动作只读、可回滚、先跑影子模式，由负责交付的人拍板，同时把反对意见和残留风险写进记录。
4. 拍板人是风险归属方。能改生产或造成出域的决定，安全负责人不点头，就先缩小范围。
5. 留下四件事：决定、依据、补测时间、回滚办法。会后不靠聊天记录里的口头妥协。

面试里给一个你真实遇到的分歧。没有就用上面的发信或出网举例，并说明你会要求谁签字。

### 11. 老板要求 Agent 一周上线自动研判告警，安全负责人说没对齐风险，你怎么推进

**答题思路**

一周可以交付的是可关、可审计、可对照的影子研判。自动处置不放在这一周。

1. 当天把范围写成三行：哪些告警类型、只读哪些数据、禁止哪些动作。封禁、回信、改规则明确排除。
2. 把安全负责人的反对逐条变成验收条件：结论必须引用原始事件，未知不能写成无害，没有轨迹不能打开，人可以一键停。
3. 用一小份历史告警做对照，记录 Agent 和人的差异。对外只给分析员看建议，不改生产防护。
4. 向老板换承诺：时间表保持一周，交付物从「自动闭环」改成「影子模式加对照结果」。风险没对齐的部分写上不做，以及这个切割是谁同意的。
5. 一周结束用对照数据决定扩不扩大。没有数据就维持只读，不用「已经上线」结束讨论。

这样既推进了老板要的可见进展，也没有绕过安全负责人。如果老板坚持自动封禁，把残留风险写成需要他和安全负责人共同签字的决定，你不口头承担。

### 12. 你觉得自己和只会写 CRUD Agent 的人最大区别在哪

**答题思路**

区别在你把模型放在哪，不在你用没用某个框架。语气保持具体，不要贬低别人。

1. 先承认 CRUD 式 Agent 能解决查询和填表。然后说安全场景多出来的是：调用方可能是模型，输入里混着不可信内容，动作会改外部状态。
2. 用你做过的三件事说明：
   - 身份：动作用谁的权限，用户看不见的数据会不会进上下文
   - 副作用：超时重试会不会把消息发两次，失败时停在哪一步
   - 证据：一次运行能不能把提示来源、工具参数和策略判决串起来
3. 补一个你拒绝交给模型的决定，以及你用什么确定性代码接住了它。
4. 收尾落到岗位：答对一句，不如少做一次不该做的动作。

没有现成项目时，就用这三件套讲你会怎么改一个「收到文本就查库并回复」的机器人，仍不要编公司名。

### 13. 如果面试我这种岗位，你会问什么狠问题

**答题思路**

准备三个你真要用来做决定的问题，按「动作、身份、事故」问。对方答完再追一句「这周只能补一个，会补哪个」。

1. 生产里的 Agent 现在有哪些工具能改状态，哪些必须人工确认？一键停掉全部动作的开关在哪，生效大概多久？有没有演练过？
2. 工具目录和系统提示谁能改，变更怎么审核和回滚？有没有固定回归集，覆盖间接提示词注入和越权工具参数？
3. Agent 的身份如果泄漏，最远能读到什么、能改什么？轨迹里有没有工具参数、策略判决和工具目录哈希？这个 Agent 自己能不能改日志？
4. 检测规则和 Agent 怎么衔接：它能不能把规则直接推进 IPS 或封禁？
5. 上一次和 Agent 有关的误操作或注入是怎么发现的，复盘后改的是提示词，还是网关上的一道闸门？

这些问题用来判断闸门在不在，不用来表现强硬。如果动作范围、停机和审计都没有负责人，这个信息比岗位介绍更重要。
