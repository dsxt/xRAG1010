### 3. Golang 的 goroutine 调度模型(GMP)，与线程的区别，什么情况下会发造成goroutine 泄漏

**参考答案**

GMP 是 Go 运行时的 M:N 调度模型：G 是 goroutine，M 是操作系统线程，P 是逻辑处理器（持有本地运行队列和调度所需的资源）。M 必须绑定 P 才能执行 G。

- **调度流程**：新建的 G 优先放入当前 P 的本地队列（容量 256），满了就把一部分转移到全局队列。M 先从本地队列取 G，其次取全局队列（每隔一定次数会检查全局队列，避免饿死），再从网络轮询器获取，最后从其他 P 偷一半（work stealing）。
- **系统调用阻塞**：M 陷入阻塞的系统调用时，P 会被解绑并交给其他 M，保证其他 G 继续运行。网络 IO 走 netpoller，不会阻塞 M。
- **抢占**：sysmon 监控长时间运行的 G。Go 1.14 之后支持基于信号的异步抢占。
- **与线程的区别**：goroutine 初始栈很小（约 2KB 起，可动态伸缩），线程栈通常是 MB 级；goroutine 的创建和切换在用户态完成，成本低；由 Go 运行时调度，不是内核调度；数量可以到几十万。

**goroutine 泄漏的常见场景**：

1. channel 发送或接收永远阻塞（无人接收、无人发送，或 channel 从未关闭）。
2. `select` 没有 `ctx.Done()` 或超时分支。
3. `WaitGroup` 的 `Add` 和 `Done` 不匹配导致 `Wait` 永久阻塞。
4. 锁没有释放，或死锁。
5. 请求超时返回后，下游 goroutine 仍在等待结果。典型修复是用带缓冲 channel 或 `context` 取消。
6. `time.Ticker` 没有 `Stop`，或 for 循环里没有退出条件。

排查可以用 `pprof` 的 goroutine profile，或对比 `runtime.NumGoroutine()` 的趋势。

### 4. Golang 的 channel 有无缓冲区别，close之后再发送会 panic吗，如何优雅退出goroutine

**参考答案**

**无缓冲 channel**：发送和接收必须同时就绪，同步交接，有 happens-before 保证。**有缓冲 channel**：缓冲未满时发送不阻塞，缓冲为空时接收才阻塞，发送方和接收方被解耦。

**close 之后再发送会 panic**（`send on closed channel`）。相关规则：

- 对已关闭的 channel 再次 `close` 也会 panic，对 nil channel 执行 `close` 同样 panic。
- 从已关闭的 channel 接收：先取完缓冲里的剩余数据，之后立刻返回零值，`v, ok := <-ch` 中 `ok == false`。
- 向 nil channel 发送或从 nil channel 接收会永久阻塞。
- 原则：**由发送方关闭**，多个发送方时不要直接 close，可以用额外的 done channel 或 `sync.Once`。

**优雅退出 goroutine**：

1. 用 `context.WithCancel` 或 `WithTimeout`，工作 goroutine 在 `select` 里监听 `ctx.Done()`。
2. 用 `sync.WaitGroup` 或 `errgroup` 等待所有 goroutine 退出。
3. 对生产者，先停止生产并 close 数据 channel，消费者用 `for range` 把数据消费完再退出。
4. 服务层面配合 `signal.NotifyContext` 和 `http.Server.Shutdown`。

```go
func worker(ctx context.Context, jobs <-chan int) {
    for {
        select {
        case <-ctx.Done():
            return
        case j, ok := <-jobs:
            if !ok {
                return
            }
            _ = j // 处理任务
        }
    }
}
```

### 5. 用户说"我想找个附近人均50左右好吃的川菜馆，最好能订座"——本地生活场景下怎么做意图识别与槽位填充(Slot Filling)，NER+分类还是微调还是LLM，说方案

**参考答案**

推荐**分层混合方案**：LLM 负责理解和结构化抽取，规则和词典负责归一化与兜底，高 QPS 场景再用小模型蒸馏。

1. **意图**：这句话是"找餐厅"，并带有"订座"的后续意图。可以定义主意图（`search_poi`）加可选动作（`book`），或者做成多意图。
2. **槽位**：`category=川菜`；`price_per_person≈50`（归一成区间，如 40~60）；`location=附近`（依赖用户定位，不是文本能得到的槽位，需要从端上上下文注入）；`sort=好评/口碑`（"好吃"映射为评分偏好）；`need_reservation=true`。缺失的必填槽位（时间、人数）通过追问补齐。
3. **方案对比**：
   - NER + 分类：延迟低、可控，但新说法泛化差，标注成本高。
   - 微调小模型：线上成本低、稳定，适合流量大且意图集合稳定的场景，需要数据闭环。
   - LLM（few-shot + function calling / 结构化输出）：冷启动快、泛化好，但延迟和成本高，需要约束输出。
4. **落地**：先用 LLM 冷启动并积累线上数据；高频意图用微调小模型或规则快速路径；LLM 做兜底和长尾。抽取后做**归一化**（菜系词典、价格区间、商圈 / 地理编码），并校验槽位合法性。
5. 评估用意图准确率、槽位 F1 和联合准确率，并监控线上追问率。

### 6. 如果用LLM做意图识别，怎么设计System Prompt 保证输出稳定 JSON，如何处理模型乱返回格式的问题

**参考答案**

最可靠的方式是**不只靠 Prompt，用"约束生成 + 校验 + 重试"的组合**。

**System Prompt 设计**：

1. 明确角色和任务，给出完整的 JSON Schema（字段名、类型、枚举值、是否必填）。
2. 明确"只输出 JSON，不要解释，不要 Markdown 代码块"。
3. 对枚举字段列出全部可选值，并说明"无法判断时输出 `unknown`"，而不是让模型自由发挥。
4. 给 2 到 3 个覆盖边界情况的 few-shot 样例。
5. 温度设为 0 或较低值。

**工程保障**：

1. 优先使用模型原生能力：JSON mode、Structured Outputs（Schema 约束解码）或 function calling。
2. 解析前做清洗：去掉代码块围栏，截取第一个完整 JSON 对象。
3. 用 JSON Schema 或结构体做**校验**（字段、类型、枚举）。
4. 校验失败时把**错误信息回喂给模型重试**，限制重试次数（如 1 到 2 次）。
5. 最终失败走降级：规则兜底、默认意图，或追问用户。
6. 监控解析失败率，把失败样本沉淀进评测集，迭代 Prompt。

### 7. RAG的全链路流程说一下，文档切片策略怎么选（重叠、大小），为什么不能用过大或过小的 chunk

**参考答案**

**全链路**分离线和在线两段：

- **离线**：文档解析与清洗 → 切片（chunking）→ 向量化（embedding）→ 写入向量库，并保存元数据（来源、城市、时间等），必要时同时建立关键词索引。
- **在线**：Query 理解与改写 → 检索（向量 + BM25 混合）→ 元数据过滤 → 重排（rerank）→ 上下文组装 → LLM 生成（带引用）→ 后处理与评估。

**切片策略**：常见做法是按语义或结构切分（标题、段落、句子边界），再用 token 数限制长度，块大小常见在几百 token 量级，重叠取块大小的 10%~20% 左右。具体数值没有通用最优，要用自己的评测集做对比。重叠是为了避免语义在边界被切断。

**为什么不能过大或过小**：

- **过大**：一个向量要表达的内容太杂，语义被稀释，检索精度下降；塞进 Prompt 的无关内容多，噪声大、token 成本高，还有"中间丢失"（lost in the middle）的问题。
- **过小**：上下文不完整，指代和前提信息丢失，单块信息量不足以回答问题，检索结果碎片化，需要更大的 top-k。

进阶做法：父子块（小块检索，返回大块）、按文档结构切分、给 chunk 附加标题或摘要上下文。

### 8. 向量数据库用的是什么(Milvus/Chroma/Faiss)，相似度度量用余弦还是内积，什么场景用哪种

**参考答案**

选型要说清各自定位（具体用了哪个以你的真实经历为准）：

- **Faiss**：Meta 开源的向量检索库，不是数据库，没有分布式、持久化和元数据过滤，适合单机、离线或嵌入到服务内部使用。
- **Chroma**：轻量、开箱即用，适合原型和小规模场景。
- **Milvus**：分布式向量数据库，支持多种索引（HNSW、IVF 系列等）、标量过滤、混合检索和水平扩展，适合生产和大规模数据。

**度量方式**：

- **余弦相似度**只看方向，不受向量长度影响，文本语义检索最常用。
- **内积（IP）**同时受方向和模长影响。**向量归一化之后，内积和余弦等价**，而且内积计算更快，所以通常的做法是"归一化 + 内积"。
- **L2（欧氏距离）**常用于图像等特征向量。
- 关键原则：**度量要和 embedding 模型的训练目标一致**，查模型文档。需要把"模长"当作权重信号时（如推荐里的热度），才有意义使用未归一化的内积。

### 9. LangChain 和 LangGraph 的核心区别，为什么说 LangGraph 更适合多步 ReAct Agent

**参考答案**

**LangChain** 提供模型、提示词、检索器、工具等**组件抽象**，以及用 LCEL 把组件串成链（偏线性或 DAG）。**LangGraph** 是面向**有状态、可循环的工作流**的编排框架，把流程建模为图：节点是函数，边是控制流，共享一个状态对象。

LangGraph 更适合多步 ReAct Agent 的原因：

1. **支持循环**：ReAct 是"思考 → 调工具 → 观察 → 再思考"的循环，线性链表达不了，图里加一条回边即可。
2. **显式状态管理**：消息、中间结果和计划都在 State 里，并可通过 reducer 控制合并方式。
3. **条件路由**：由 Conditional Edge 决定"继续调用工具还是结束"。
4. **持久化与可恢复**：Checkpointer 保存每一步的状态，支持断点续跑、人工介入、时间回溯。
5. **流式与可观测**：天然支持节点级的流式输出和 tracing。
6. 可控性强：可以限制最大步数，在关键节点插入校验或审批。

补充：新版 LangChain 的预置 Agent 底层也是基于 LangGraph 实现的，两者不是对立关系。

### 10. LangGraph 中 State / Node / Edge /Conditional Edge 分别解决什么问题，Checkpointer 是干嘛的

**参考答案**

- **State**：整个图共享的状态（通常是 `TypedDict` 或 Pydantic 模型），解决"各步骤之间怎么传递数据"。每个字段可以绑定 **reducer**，决定新值怎么合并（例如消息列表用追加，而不是覆盖）。
- **Node**：一个函数，接收当前 State，返回对 State 的**更新**，封装一步具体工作（调用 LLM、调用工具、检索等）。
- **Edge**：固定的流转关系，A 执行完必然到 B，解决"流程顺序"。
- **Conditional Edge**：由路由函数读取 State 后决定下一个节点，解决"分支和循环"，例如 ReAct 里判断模型是否发出了 tool call，是则去工具节点，否则结束。
- **Checkpointer**：在每个超步（super-step）之后把 State 快照持久化，以 `thread_id` 区分会话。作用：
  1. 多轮对话的短期记忆。
  2. 故障后从最近的检查点恢复。
  3. Human-in-the-loop 的中断和恢复。
  4. 时间回溯和调试（查看或回放历史状态，从某个检查点分叉）。

生产中常用 Postgres 之类的持久化实现，开发时可以用内存实现。

### 11. Redis 在你 Agent 系统里可以用来做什么(缓存、分布式锁、会话状态、限流举例)

**参考答案**

1. **缓存**：缓存 POI 详情、热门查询结果、工具调用结果、embedding 结果，设置 TTL，并注意缓存穿透、雪崩的防护。也可以做 LLM 语义缓存（需要向量检索能力的 Redis 模块或配套组件）。
2. **分布式锁**：保证同一会话或同一订单同一时刻只有一个 Agent 在执行。用 `SET key value NX PX` 加唯一 value，释放时用 Lua 脚本校验 value 再删除；长任务需要续期（看门狗）。要说明锁可能因过期而失效，关键业务仍需要幂等或乐观锁兜底。
3. **会话状态**：用 Hash 或 JSON 存多轮对话的槽位、最近消息和摘要，设置过期时间；配合 DB 做长期持久化。
4. **限流**：基于 `INCR + EXPIRE` 的固定窗口，或 Lua 实现滑动窗口 / 令牌桶，按用户、租户、模型维度限制 QPS 和 token 用量，实现多实例的全局限流。
5. **幂等去重**：用 `SET NX` 记录请求 ID 或工具调用 ID。
6. **队列与广播**：Stream 做轻量任务队列，Pub/Sub 做取消信号或流式事件分发。

### 12. MySQL 事务四大特性 ACID，MVCC 是怎么实现的

**参考答案**

**ACID**（InnoDB 的实现）：

- **原子性（A）**：由 undo log 保证，事务失败时回滚。
- **一致性（C）**：事务前后数据满足约束，是 A、I、D 加应用逻辑共同保证的结果。
- **隔离性（I）**：由锁和 MVCC 保证。
- **持久性（D）**：由 redo log（WAL，先写日志后刷脏页）保证，崩溃后可恢复。

**MVCC 实现**（用于一致性非锁定读，即普通 SELECT）：

1. 每行有隐藏列：`DB_TRX_ID`（最近修改它的事务 ID）和 `DB_ROLL_PTR`（指向 undo log 里的上一个版本），多个版本串成**版本链**。
2. 事务读取时生成 **ReadView**，包含：活跃事务 ID 列表、最小活跃事务 ID、下一个将分配的事务 ID、创建者事务 ID。
3. 沿版本链找到第一个对当前 ReadView **可见**的版本：事务 ID 小于最小活跃 ID 的可见；大于等于下一个分配 ID 的不可见；在活跃列表里的不可见（自己修改的除外）。
4. **隔离级别差异**：读已提交（RC）每次查询都生成新的 ReadView；可重复读（RR）在事务第一次读时生成，之后复用，所以能重复读。

容易漏的点：`SELECT ... FOR UPDATE` 等**当前读**读取最新版本并加锁，不走 MVCC；RR 下当前读的幻读靠间隙锁和临键锁解决。

### 13. Agentic RAG 和普通 Naive RAG 的区别，什么时候需要 Agentic RAG

**参考答案**

**Naive RAG** 是固定的单次流程：Query → 检索 top-k → 拼接上下文 → 生成。它不判断检索质量，也不会调整策略。

**Agentic RAG** 把检索变成 Agent 可以自主决策的行为：

- 判断是否需要检索，以及检索哪个数据源（路由到向量库、SQL、搜索引擎或 API）。
- 改写或拆分 Query，做多跳检索。
- 对检索结果做相关性评估，不够好就换策略重新检索。
- 生成后做自检（是否有依据、是否完整），不通过则补充检索。

**需要 Agentic RAG 的场景**：问题复杂、需要多跳推理（"人均 50 以内、离地铁近、适合带老人的川菜"）；有多个异构数据源；Query 模糊需要追问或改写；对准确性要求高，需要自检闭环。

**代价**：延迟更高、成本更高、可控性更差，所以简单的 FAQ 类问题仍然用 Naive RAG 更合适，可以先用路由把简单问题分流。

### 14. 说一下 ReAct 范式(Thought-Action-Observation)，和Plan-and-Execute 的区别及适用场景

**参考答案**

**ReAct** 把推理和行动交替进行：模型先输出 **Thought**（当前该做什么），再输出 **Action**（调用哪个工具、什么参数），拿到工具返回的 **Observation** 后继续下一轮，直到给出最终答案。它根据环境反馈动态调整，不依赖一开始的完整计划。

**Plan-and-Execute** 先由规划器生成完整的步骤计划，再由执行器逐步执行，必要时重新规划（replan）。

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 决策方式 | 走一步看一步 | 先全局规划再执行 |
| 灵活性 | 高，适应环境变化 | 较低，需要 replan |
| 成本 / 延迟 | 每步都要调用大模型 | 执行步骤可以用小模型，更省 |
| 风险 | 容易陷入循环、目光短浅 | 计划可能一开始就错 |

**适用场景**：任务不确定、需要根据中间结果探索时用 ReAct；任务结构清晰、步骤较多、希望降本和可预测时用 Plan-and-Execute。实际常常混合使用：Plan 定框架，每个步骤内部用 ReAct。

### 15. 手撕算法：LeetCode 中等——给一个字符串数组，找出字符串能拼接成的最长前缀(实现 Trie 或用横向扫描均可，口述思路+写代码)

**参考答案**

题意应该是 LeetCode 14「最长公共前缀」：求字符串数组所有字符串共有的最长前缀。

**横向扫描**：以第一个字符串为初始前缀，依次与后面每个字符串比较，不断缩短前缀；前缀为空时可以提前返回。时间复杂度 O(S)（S 为所有字符总长度），空间复杂度 O(1)。

**Trie 解法**：把所有字符串插入 Trie，从根开始往下走，直到出现分叉（子节点数大于 1）或某个字符串结束。适合需要反复查询前缀的场景，空间 O(S)。

```go
func longestCommonPrefix(strs []string) string {
    if len(strs) == 0 {
        return ""
    }
    prefix := strs[0]
    for _, s := range strs[1:] {
        i := 0
        for i < len(prefix) && i < len(s) && prefix[i] == s[i] {
            i++
        }
        prefix = prefix[:i]
        if prefix == "" {
            return ""
        }
    }
    return prefix
}
```

边界：空数组、含空串、只有一个字符串。

### 2. 详细讲你项目中多Agent 协作的架构是 Supervisor/Orchestrator-SubAgent、Pipeline还是 Swarm，为什么选这个模式

**答题思路**

这是项目深挖题，按下面的顺序回答，内容以你的真实项目为准：

1. **先说明选了哪种模式**，并画出架构：有哪些 Agent，各自职责，谁负责路由。

   - Pipeline：步骤固定、可预测，适合流程确定的任务，缺点是不灵活。

3. **结合业务约束**：延迟要求、任务是否固定、是否涉及下单等高风险动作、是否需要强一致和审计。
4. **通信与状态**：子 Agent 之间怎么传递上下文（共享 State 还是消息），结果如何汇总。
5. **踩过的坑和改进**：路由误判、子 Agent 重复执行、上下文膨胀、某个子 Agent 超时拖垮整体，以及你的解决方案。
6. 不编造具体项目名、指标，没有的就说"如果重做我会……"。

### 3. 多 Agent 系统中如何避免子 Agent 重复执行同任务，如何保证最终一致性，幂等怎么设计

**参考答案**

核心思路：**任务唯一标识 + 状态机 + 幂等工具调用 + 单一写者**，在"至少一次投递"的前提下做到"效果上只执行一次"。

1. **避免重复执行**：
   - 为每个子任务生成**确定性的任务 ID**（如 `hash(run_id, step, 规范化后的输入)`）。
   - 在任务表上建唯一索引，执行前用 `INSERT ... ON CONFLICT` 或 `SET NX` 抢占；状态流转 `PENDING → RUNNING → DONE/FAILED`。
   - 抢占使用带 TTL 和心跳的租约，执行者崩溃后租约过期，任务可被重新接管。
   - Orchestrator 在派发前检查已完成的结果，直接复用。
2. **幂等设计**：
   - 有副作用的工具调用（下单、扣券、发消息）带**幂等键**（由任务 ID 派生），下游据此去重。
   - 查询类工具天然幂等。
   - 重试前先查询下游真实状态，不盲目重发。
   - 消费端对消息做去重，处理逻辑本身可重入。
3. **最终一致性**：
   - Orchestrator 作为**唯一写入全局状态**的角色，子 Agent 只返回结果，避免并发写冲突。
   - 状态变更和事件发布用**事务性发件箱（Outbox）**，避免状态更新了但消息没发出。
   - 跨系统的多步操作用 **Saga**：每步配补偿动作，失败时反向补偿。
   - 对账任务定期扫描"卡住"的任务，补偿或重试。

### 4. Harness Engineering 是什么，Agent Harness 层一般包含哪些职责（调度、超时/熔断、上下文注入、可观测性、错误隔离）

**参考答案**

**Harness Engineering** 指围绕模型搭建的运行时脚手架的工程化：模型只是"大脑"，Harness 是让它能稳定、安全、可控地完成任务的外围系统。常见的说法是 Agent = 模型 + Harness。它关注的不是 Prompt 本身，而是把不确定的模型放进一个**可控、可验证、可恢复**的系统里。

典型职责：

1. **调度与循环控制**：驱动"推理 → 工具 → 观察"的循环，控制最大步数、并发和任务队列。
2. **超时 / 重试 / 熔断**：给模型调用和每个工具设置超时，对幂等调用做带退避的重试，对不稳定的下游熔断并降级。
3. **上下文管理与注入**：组装系统提示、工具描述、记忆和检索结果；做裁剪、压缩和摘要，控制 token 预算。
4. **工具层**：工具注册、参数校验、权限控制、沙箱隔离。
5. **错误隔离**：单个工具或子 Agent 失败不拖垮整体，把错误以结构化形式反馈给模型自我修正。
6. **状态与恢复**：checkpoint、断点续跑、人工审批。
7. **可观测性**：全链路 trace、记录每一步的输入输出、token、耗时和成本，支持回放和评测。
8. **验证与护栏**：输出校验、安全过滤、完成度检查。

### 5. LangGraph 中怎么实现 Human-in-the-loop（中断恢复 checkpoint），序列化状态存在哪

**参考答案**

实现需要三要素：**Checkpointer + thread_id + 中断点**。

1. 编译图时传入 checkpointer：`graph = builder.compile(checkpointer=saver)`，调用时在 `config` 里指定 `thread_id`。
2. 在需要人工介入的节点里调用 `interrupt(payload)`（也可以用编译时的 `interrupt_before` / `interrupt_after` 做静态中断）。图会暂停，把状态存入 checkpointer，并把 payload 返回给调用方展示给人。
3. 人工给出决定后，用 `graph.invoke(Command(resume=人工输入), config)` 恢复，`interrupt()` 会返回这个值，图从断点继续。还可以在恢复前修改状态（如更新参数）。

```python
from langgraph.types import interrupt, Command

def approve_order(state):
    ok = interrupt({"question": "是否确认下单？", "order": state["order"]})
    return {"approved": ok}

# 恢复
graph.invoke(Command(resume=True), config={"configurable": {"thread_id": "t1"}})
```

**注意点**：恢复时被中断的节点会**从头重新执行**，所以 `interrupt` 之前的副作用必须幂等，或者放在中断之后。

**状态存哪**：由 Checkpointer 决定，开发用内存实现，本地可用 SQLite，生产常用 Postgres 或 Redis 的实现。状态通过序列化器（默认是基于 JSON / msgpack 的序列化）存储，每个超步一个 checkpoint，按 `thread_id` 组织。注意状态里不要放不可序列化的对象（连接、文件句柄），也要考虑敏感信息的存储合规。

### 6. 意图识别在多轮对话中怎么维护上下文，怎么处理意图切换(比如中途改需求说"算了我要找日料")

**参考答案**

核心是维护**结构化的对话状态（DST）**，而不是只依赖拼接历史文本。

1. **上下文维护**：
   - 保存结构化状态：当前意图、已填槽位、待确认槽位、上轮展示的结果。
   - 保留最近几轮原文，更早的对话压缩成摘要。
   - 每轮识别时把"状态 + 最近对话 + 当前输入"一起输入，让模型输出**增量更新**，并做指代消解和省略补全（如"换个便宜点的" → 继承品类，修改价格）。
2. **意图切换处理**：
   - 识别切换信号："算了""换成""不要了"，或新的品类 / 意图与当前槽位冲突。
   - 区分**修正**（同一意图下替换槽位：川菜 → 日料）和**新意图**（从找餐厅变成查订单）。
   - 修正时只覆盖冲突槽位（品类）；**保留可继承的槽位**（位置、人数、预算），但与旧品类强相关的槽位（如旧菜系的偏好）要清除。
   - 新意图时可以用意图栈保存旧任务，允许"回到刚才的话题"。
3. **不确定时反问**：置信度低或槽位冲突时，用一句话确认，不要静默猜测。
4. 状态变更要有版本，便于回溯和调试，对话状态按会话存储，设置过期。

### 7. RAG 检索结果不理想怎么优化——Query Rewriting / HyDE / Multi-Query / Rerank(Cross-Encoder)，说你用过的

**参考答案**

先**定位问题在检索还是生成**：用评测集看 Recall@k，召回里没有答案就优化检索，召回有但答错就优化重排、上下文和生成。

**优化手段**：

1. **Query Rewriting**：用 LLM 把口语、省略、多轮指代的问题改写成完整、独立、适合检索的查询，也可以拆分子问题。
2. **HyDE**：先让 LLM 生成一个"假设性答案"，用它的向量去检索，缓解 query 与文档的表达形式不一致，对短 query 效果好；缺点是多一次 LLM 调用，且假设答案出错会带偏检索。
3. **Multi-Query**：生成多个改写 query 分别检索，再合并去重，常用 RRF（倒数排名融合）融合排序，提高召回。
4. **Rerank**：先召回较多候选（如几十条），再用 **Cross-Encoder** 对 query 和文档联合打分重排，取 top-n。精度高于双塔向量，代价是延迟，所以只对候选集做。
5. **混合检索**：向量 + BM25，应对关键词、专有名词（店名、菜名）。
6. **元数据过滤**：城市、品类、时间。
7. **切片和索引优化**：调整 chunk 策略、父子块、补充标题上下文。

回答时只讲你真实用过的，并给出对比数据来源：用同一评测集做 A/B，对比 Recall@k、MRR 和最终答案质量。

### 8. GraphRAG 和普通向量 RAG 的区别，适合本地生活知识库吗，为什么

**参考答案**

**普通向量 RAG** 把文档切块、向量化，按语义相似度检索片段，擅长局部事实问答，但对跨文档的多跳关系和"全局性总结"类问题较弱。

**GraphRAG**（以微软的方案为代表）在索引阶段用 LLM 从文本中抽取实体和关系，构建知识图谱，再做社区发现并生成社区摘要。查询时可以做**局部搜索**（围绕实体沿关系扩展）和**全局搜索**（基于社区摘要回答整体性问题）。

| 维度 | 向量 RAG | GraphRAG |
| --- | --- | --- |
| 擅长 | 单点事实、语义相似 | 多跳关系、全局总结 |
| 索引成本 | 低 | 高（大量 LLM 抽取调用） |
| 更新 | 增量简单 | 图和摘要更新复杂 |

**对本地生活的适用性：部分适合，不应该整体替换。**

- 适合：商户、商圈、菜系、菜品、优惠、地铁站之间天然是图结构，多跳问题（"地铁站附近、适合带老人、有包间的川菜"）和 UGC 评论的整体洞察可以受益。
- 不适合：价格、库存、营业时间、距离等**强时效、结构化**数据变化很快，应该走结构化查询（ES / DB / 实时 API），用图抽取再摘要会过时且成本高。
- 建议：结构化数据 + 向量检索作为主路径，知识图谱（可以不依赖 LLM 抽取，直接用已有的商户关系数据）作为补充，用于多跳场景。

### 9. Golang 高并发下调用 LLM API 怎么做限流(令牌桶/滑动窗口)，怎么做熔断防止下游拖垮服务

**参考答案**

**限流**：

1. LLM 供应商通常同时限制请求数（RPM）和 token 数（TPM），所以要做**两个维度**的限流，token 用量按预估值预扣、完成后按实际值修正。
2. 单机用令牌桶：`golang.org/x/time/rate`，允许一定突发，平均速率可控。滑动窗口精度更高，更适合严格配额。
3. 多实例要做**全局限流**：用 Redis + Lua 实现，或按实例数分配配额。
4. 按用户、租户、模型分层限流，并设置优先级队列，保证核心流量。
5. 遇到 429 时遵循 `Retry-After`，用指数退避加抖动，不要立刻重试，避免放大流量。

```go
limiter := rate.NewLimiter(rate.Limit(50), 100) // 每秒 50，突发 100

func callLLM(ctx context.Context, req Req) (Resp, error) {
    if err := limiter.Wait(ctx); err != nil {
        return Resp{}, err
    }
    ctx, cancel := context.WithTimeout(ctx, 30*time.Second)
    defer cancel()
    return client.Do(ctx, req)
}
```

**熔断**：

1. 使用熔断器（如 `sony/gobreaker`），三态：**关闭 → 打开 → 半开**。统计一段时间内的失败率或超时率，超过阈值就打开，快速失败；一段时间后进入半开，放少量探测请求，成功则恢复。
2. 配合**超时**（每次调用必须有 deadline）、**舱壁隔离**（限制并发数，不同模型或下游使用独立的 goroutine 池或信号量）。
3. 熔断后降级：切换备用模型 / 供应商，使用缓存或规则兜底，或返回友好提示。
4. 监控熔断状态和错误率，及时告警。

### 10. gRPC 和 HTTP 在你 Agent 服务间通信怎么选，protobuf 相比 JSON 优劣

**参考答案**

**选择原则**：内部服务之间优先 gRPC，对外和浏览器场景用 HTTP/REST（或 SSE / WebSocket）。

- **gRPC**：基于 HTTP/2，多路复用、长连接，支持**双向流**，适合 Agent 内部服务调用，以及 LLM 的 token 流式返回；有强类型接口定义（IDL）、代码生成、内置超时（deadline）传播、拦截器；性能和带宽更好。
- **HTTP/REST**：通用、调试简单、对浏览器和第三方友好，网关、缓存等生态成熟。对外开放的接口、Webhook、需要被前端直接调用的场景更合适。浏览器直连 gRPC 需要 grpc-web 或网关转换。

**protobuf vs JSON**：

- 优势：二进制编码，体积小、序列化 / 反序列化快；有 schema，强类型，通过字段编号支持向前向后兼容的演进；配合 gRPC 自动生成客户端。
- 劣势：不可直接阅读，调试需要工具；需要维护 `.proto` 和代码生成流程；动态结构（如 Agent 工具的任意 JSON 参数）表达不方便，需要用 `Struct` / `Any` 或把 JSON 当字符串字段；对外部生态的兼容性不如 JSON。
- 注意：字段编号不能复用，删除字段时要 `reserved`。

### 11. Elasticsearch 在本地生活搜索中怎么用，分词器IK还是自定义，如何做拼音/同义词搜索

**参考答案**

**用法**：商户、商品和团购的倒排索引做关键词检索，结合**地理查询**（`geo_distance` 过滤和排序）、结构化过滤（品类、价格、营业状态）和 `function_score`（评分、销量、距离等综合排序）。在 Agent 场景里，ES 常作为 RAG 的关键词召回通道，与向量检索做混合检索。

**分词器**：

- 中文使用 IK：**索引时 `ik_max_word`**（切得细，提高召回），**查询时 `ik_smart`**（切得粗，提高精度）。
- 本地生活里有大量店名、菜名、商圈等专有词，必须**自定义扩展词典**，并支持热更新（远程词典）。通用词典切不对"海底捞""小龙虾"这类词会明显影响效果。
- 需要更精细的控制时，可以自定义 analyzer（char_filter + tokenizer + token filter）。

**拼音搜索**：使用 pinyin 分词插件，给字段建多个子字段（multi-field）：原文字段（IK）、全拼字段、首字母字段，查询时多字段 `multi_match` 并设置权重，让原文匹配的权重更高，避免拼音召回噪声压过正文匹配。

**同义词**：用 `synonym` / `synonym_graph` 过滤器。更推荐放在**查询阶段**（search_analyzer）使用，这样改同义词词典不需要重建索引；放在索引阶段则需要重建。词典要维护（如"火锅 / 涮锅""麦当劳 / 金拱门"），并注意多词同义词和分词器的顺序，避免与 IK 切词冲突。

### 12. Kafka 或 RocketMQ 在 Agent 系统里的使用场景异步任务、审计日志、工具调用事件流，如何保证消息不丢失

**参考答案**

**使用场景**：

1. **异步任务**：耗时的 Agent 任务（长流程、批量处理）放入队列，由 worker 消费，削峰填谷。
2. **审计与日志**：记录每次模型调用、工具调用的输入输出，用于审计、回放和评测。
3. **事件流**：工具调用事件、状态变化推送给下游（监控、计费、数据分析）。
4. 服务解耦，比如订单、通知和 Agent 状态之间的异步通知。

**不丢消息要从三个环节保证（以 Kafka 为例）**：

1. **生产端**：`acks=all`，配合 `min.insync.replicas ≥ 2` 和副本数 ≥ 3；开启重试和幂等生产者（`enable.idempotence=true`）；必须检查发送结果（回调），不要"发了就不管"。
2. **Broker 端**：多副本，关闭 unclean leader 选举，合理的刷盘和复制配置。
3. **消费端**：**关闭自动提交，处理成功后再手动提交位点**。这是"至少一次"语义，可能重复消费，所以消费逻辑必须**幂等**。
4. 业务写库与发消息要保持一致时，用**事务消息或 Outbox 模式**。

RocketMQ 对应的手段：同步发送、同步刷盘 / 同步复制、事务消息，消费失败自动重试并进入死信队列。无论使用哪种 MQ，都需要对死信和堆积做监控。

### 13. 说下你做过的 Prompt 工程优化Few-shot / CoT /输出格式约束，遇到过模型忽视指令怎么处理

**参考答案**

**常用优化手段**：

- **Few-shot**：给 2 到 5 个有代表性的样例，覆盖边界和易错情况；样例要多样，顺序和标签分布要均衡，避免模型被样例带偏。
- **CoT**：让模型分步推理，提升复杂任务的准确率。对推理类模型不需要强制写"一步步思考"；生产里如果不想暴露推理，可以让它在内部推理，只输出结果，或使用模型自带的推理能力。
- **输出格式约束**：给出 Schema、枚举值，使用结构化输出或函数调用，并在代码里校验。
- **结构化 Prompt**：角色、任务、约束、示例、输出格式分段，用分隔符标出输入数据。

**模型忽视指令时的处理**：

1. 精简 Prompt，去掉冲突和重复的指令，把最关键的约束放在开头或末尾，并用明确、正向的表述（说"必须做什么"，而不是只说"不要做什么"）。
2. 加入针对性的 few-shot 示例，展示正确的行为。
3. 拆分任务，把一个复杂 Prompt 拆成多步，每步只做一件事。
4. 把能用代码保证的约束放到代码里：输出校验、后处理、重试。
5. 降低温度，必要时换更强的模型。
6. 用评测集回归，每次改 Prompt 对比指标，记录版本，避免"改好一个坏了另一个"。

### 14. Agent出现无限循环或规划混乱怎么防最大步数、循环检测、反思节点(Reflection)

**参考答案**

**预防和兜底要多层叠加**：

1. **硬限制**：最大步数、最大 token 预算和总超时。LangGraph 里可以通过 `recursion_limit` 限制；触达上限后强制结束并返回已有结果或兜底回答，不是抛异常。
2. **循环检测**：记录最近的"工具名 + 规范化参数"的哈希，连续重复（或在窗口内出现多次）就判定为循环，打断并注入提示，或直接切换策略。也可以对状态做哈希，判断状态是否没有进展。
3. **进展检查**：每几步让一个轻量判断节点评估"离目标更近了吗"，没有进展就终止或重新规划。
4. **反思节点（Reflection）**：让模型（或另一个 critic 模型）评审上一步的结果和计划是否合理，指出错误并修正；注意反思本身也会增加成本，要限制次数。
5. **规划约束**：Plan 阶段输出结构化、可校验的步骤，限制可用工具集；工具失败时返回**清晰的结构化错误**，避免模型反复重试同一个错误动作。
6. **降级**：多次失败后转人工、追问用户，或走固定流程兜底。
7. 记录 trace 并统计触发循环的 case，用于回归评测。

### 15. 手撕算法：LeetCode中等用栈实现括号匹配有效性判断，并扩展写出最长有效括号长度(32题)

**参考答案**

**有效括号（LeetCode 20）**：遇到左括号入栈，遇到右括号检查栈顶是否匹配，最后栈为空才有效。时间 O(n)，空间 O(n)。

```go
func isValid(s string) bool {
    pair := map[byte]byte{')': '(', ']': '[', '}': '{'}
    stack := []byte{}
    for i := 0; i < len(s); i++ {
        c := s[i]
        if m, ok := pair[c]; ok {
            if len(stack) == 0 || stack[len(stack)-1] != m {
                return false
            }
            stack = stack[:len(stack)-1]
        } else {
            stack = append(stack, c)
        }
    }
    return len(stack) == 0
}
```

**最长有效括号（LeetCode 32）**：栈里存**下标**，并用 `-1` 作为"最后一个没匹配的位置"的哨兵。遇到 `(` 入栈下标；遇到 `)` 先出栈，如果栈空了，说明这个 `)` 无法匹配，把它的下标作为新的哨兵入栈；否则当前有效长度是 `i - 栈顶`。时间 O(n)，空间 O(n)。

```go
func longestValidParentheses(s string) int {
    best := 0
    stack := []int{-1}
    for i := 0; i < len(s); i++ {
        if s[i] == '(' {
            stack = append(stack, i)
            continue
        }
        stack = stack[:len(stack)-1]
        if len(stack) == 0 {
            stack = append(stack, i)
        } else if l := i - stack[len(stack)-1]; l > best {
            best = l
        }
    }
    return best
}
```

另一种解法是动态规划，也是 O(n) 时间；还有正反两次扫描、O(1) 空间的做法，可以作为追问时的备选。

### 2. 项目中最难的一个 Agent 技术难点是什么，怎么解决的，如果重新设计会改哪

**答题思路**

选一个**真实、能展开 3 层追问**的难点，按下面的结构讲：

1. **问题与影响**：现象、出现频率、对业务指标的影响（如工具选错率高、长任务不稳定、RAG 答非所问、延迟或成本过高）。
2. **定位过程**：用 trace、评测集和 bad case 分类，如何把问题归因到某个环节，而不是凭感觉。
3. **方案与取舍**：试过哪几种方案，为什么选最终这个，代价是什么。
4. **结果**：用对比的指标说明，没有精确数字就说方向和量级，不要编造。
5. **如果重新设计**：例如把状态模型做得更显式、更早建立评测集和 trace、对工具做契约测试、把关键流程做成确定性步骤、模型路由和缓存提前设计。
6. 坦承局限，展示复盘能力，比讲得完美更有说服力。

### 3. 本地生活场景下 Agent 调第三方 POI/团购/订单接口，工具调用失败或返回异常数据怎么处理，降级策略说一下

**参考答案**

按"调用前、调用中、调用后"分层治理：

1. **调用前**：校验参数（Schema、范围），限流和熔断，设置超时和预算。
2. **调用中**：
   - 区分错误类型：超时和 5xx 可重试；4xx 参数错误不应重试，而应把错误反馈给模型修正参数。
   - 重试要**指数退避加抖动**，限制次数；只对**幂等操作**自动重试。
   - **下单、支付等非幂等操作**必须带幂等键，超时后先查询真实状态，再决定是否重试，避免重复下单。
3. **调用后（异常数据）**：校验返回值：字段缺失、价格为负、坐标超出城市范围、营业状态与时间矛盾、数据过期等。异常数据不要直接交给模型生成，应该丢弃、修复，或标记为不可信。
4. **降级策略**（按优先级）：
   - 备用数据源或备用供应商。
   - 使用缓存的旧数据，并标注更新时间（价格、库存类要谨慎）。
   - 使用自建的 POI 索引（ES）提供基础信息。
   - 功能降级：只返回推荐，不提供实时库存或下单。
   - 如实告诉用户"暂时无法获取"，不要编造；必要时引导人工或稍后重试。
5. **结构化错误回传**：把错误类型和建议动作以结构化形式给模型，让它决定换工具、改参数或结束，同时限制最大重试步数。
6. 全链路埋点、监控各工具的成功率和延迟，设置告警，保留现场用于复盘。

### 4. 如何评测一个本地生活意图识别模块或RAG问答效果——离线指标(Precision/Recall/EM/BLEU)和线上 AB 实验怎么设计

**参考答案**

**离线评测**要先有高质量的**评测集**：从线上真实流量采样，覆盖各意图、长尾和边界样本，由人工标注，并持续用 bad case 补充。

**意图识别**：

- 整体准确率；每类的 Precision / Recall / F1，以及 Macro / Micro F1（类别不均衡时看 Macro）。
- 槽位的 F1，以及联合准确率（意图和所有槽位都对才算对）。
- 拒识和 OOD 样本的识别能力，混淆矩阵用于分析易混类。

**RAG 问答**：

- **检索环节**：Recall@k、Hit Rate、MRR、nDCG。
- **生成环节**：答案正确性、忠实度（是否有依据、有无幻觉）、答案相关性、引用正确性。短答案可以用 EM / F1；**BLEU / ROUGE 对开放式生成相关性较弱**，只能做参考。
- 常用 **LLM-as-Judge**，但要用人工标注样本校准评判模型的一致性，避免偏差。

**线上 AB 实验**：

1. 假设和指标：核心指标（任务成功率、点击率、下单或预订转化）、过程指标（追问率、人工转接率）、**护栏指标**（延迟、成本、投诉率、幻觉率）。
2. 分流：按用户 ID 哈希随机分桶，保证同一用户体验一致；检查样本比例是否偏离预期（SRM）。
3. 样本量和时长：事先估算样本量和效应量，覆盖至少一个完整业务周期（工作日和周末的差异）。
4. 上线节奏：先离线评测通过，再影子流量（shadow），小流量灰度，再逐步扩量，保留一键回滚。
5. 事后分析：按城市、用户群、意图拆分结果，并回收 bad case 回流评测集。

### 5. 多 Agent 系统成本怎么控制模型路由(小模型做路由大模做规划)、Cache Semantic Cache、提前终止策略

**参考答案**

成本主要来自 token 数量、模型单价和调用次数，所以从这三方面同时优化：

1. **模型路由**：简单任务（意图分类、路由、抽取、格式化）交给小模型或微调模型；复杂规划和推理才用大模型。可以用规则、分类器或"先小模型，不自信再升级"的级联方式。要用评测集验证降级不掉质量。
2. **缓存**：
   - **精确缓存**：相同请求直接命中。
   - **语义缓存**：用 embedding 找相似问题，复用答案。阈值要保守，并带上**作用域**（城市、用户群、时间）；对时效性强（库存、价格）、个性化和有副作用的请求不要缓存。
   - **Prompt / 前缀缓存**：把稳定的系统提示、工具描述放在前面，利用模型服务的前缀缓存降低成本和延迟。
   - 工具结果缓存。
3. **提前终止**：设置最大步数、token 预算和时间预算；已满足完成条件就停止；检测到无进展或循环就终止；置信度足够时跳过反思和重排等可选步骤。
4. **减少上下文**：裁剪历史、摘要压缩、只注入相关工具描述（工具很多时先做工具检索）、控制检索的 top-k。
5. **并行与批处理**：独立的工具调用并行执行以降低延迟，离线任务批处理。
6. **治理**：按租户或业务线设置配额，监控每个请求的成本和 token 分布，找出成本异常的流程重点优化。

### 6. 说下你了解的字节内部 Go AI 框架（如 Eino/CloudWeGo），如果让你用 Go 封装一个 LangGraph 类似的 Graph 编排引擎核心结构怎么设计

**参考答案**

**Eino 与 CloudWeGo**：CloudWeGo 是字节开源的微服务中间件体系（如 Kitex RPC、Hertz HTTP 框架、Netpoll 网络库），Eino 是其中面向 Go 的大模型应用开发框架。大致特点：提供标准化的**组件抽象**（ChatModel、Tool、Retriever、Embedding、Prompt 模板等），提供 **Chain / Graph / Workflow 编排**，支持**流式处理**（对流的拼接、合并、复制等由框架处理）、**回调切面**（用于日志、trace 和监控），并提供 ReAct 等 Agent 的现成实现。我的了解停留在公开资料层面，具体 API 以官方文档为准。

**自己设计一个类似 LangGraph 的 Go 编排引擎，核心结构**：

1. **State**：共享状态，每个字段可配置 reducer（追加或覆盖），并发节点的更新通过 reducer 合并。
2. **Node**：`func(ctx, State) (Update, error)`，统一接口，便于包装成可观测、可重试的节点。
3. **Edge / Branch**：静态边和条件边（路由函数返回下一个节点名）。
4. **Compile 阶段**：校验图（入口、可达性、孤立节点、环是否合法），生成不可变的 `Runnable`。
5. **Runtime 调度**：按超步（super-step）执行，每步并行执行当前就绪的节点（goroutine + errgroup），等全部完成后合并更新，再计算下一批节点；支持最大步数、`context` 超时和取消。
6. **Checkpointer 接口**：每个超步后存储状态，支持恢复、中断（interrupt）和人工介入，后端可以接 Redis / MySQL。
7. **流式**：用 channel 输出节点事件和 token 流。
8. **中间件 / 回调**：统一处理 trace、超时、重试、限流和日志。

```go
type State map[string]any
type Node func(ctx context.Context, s State) (State, error)
type Router func(s State) []string // 返回下一批节点，空表示结束

type Graph struct {
    nodes    map[string]Node
    edges    map[string][]string
    branches map[string]Router
    entry    string
    reducers map[string]func(old, new any) any
    saver    Checkpointer
    maxSteps int
}

type Checkpointer interface {
    Save(ctx context.Context, threadID string, step int, s State, next []string) error
    Load(ctx context.Context, threadID string) (State, []string, int, error)
}
```

运行循环：取出当前节点集合 → 并行执行 → 用 reducer 合并 → 存 checkpoint → 通过边和路由函数计算下一批节点 → 直到结束或超过 `maxSteps`。

### 7. 说下 MCP(Model Context Protocol)或Tool/Skill注册与版本管理机制，怎么防止 Skill描述漂移导致工具选择错误

**参考答案**

**MCP** 是由 Anthropic 提出的开放协议，用于标准化大模型应用与外部工具和数据源的连接，基于 JSON-RPC 2.0。采用 **Client-Server** 架构，Server 暴露三类能力：**Tools**（可调用的函数）、**Resources**（可读取的数据）、**Prompts**（提示模板）。传输方式有 stdio 和 Streamable HTTP。Client 通过 `tools/list` 发现工具，通过 `tools/call` 调用，Server 能力变化时可以发送 list changed 通知。

**注册与版本管理**：

1. 建立**工具注册中心**，每个工具包含：名称、描述、入参 Schema、版本号（语义化版本）、负责人、权限等级、超时和限流配置。
2. 兼容性规则：新增可选参数属于小版本；改变参数含义或删除字段属于大版本，需要并行保留旧版本，并灰度切换。
3. 按名称空间隔离，避免重名冲突；Agent 配置里**固定（pin）工具版本**，而不是默认拉最新。

**防止描述漂移导致选错工具**：

1. 描述被当作代码管理：版本控制、变更评审，并为**描述计算哈希**，描述或 Schema 变化时触发告警。
2. 建立**工具选择评测集**（query → 期望工具和参数），描述变更必须通过回归，才允许发布。
3. 描述写清楚"何时使用、何时不使用"、输入输出示例，并避免相似工具描述重叠；工具数量多时先做**工具检索**，只给模型相关的少量工具。
4. 线上监控工具选择分布、参数校验失败率和调用成功率，漂移时可以快速回滚。
5. 对第三方 MCP Server，要锁定版本、审查描述变化，因为描述中可能被注入恶意指令，需要权限控制和最小授权。

### 8. Golang interface 的底层结构(itab +data)，nil interface 和含 nil 指针的interface相等吗，为什么

**参考答案**

**底层结构**：Go 的 interface 有两种：

- 非空接口（有方法）：`iface{ tab *itab, data unsafe.Pointer }`。`itab` 包含接口类型、具体类型、类型哈希和方法表（`fun` 数组，保存具体类型实现的接口方法地址）。方法调用通过 itab 的方法表动态派发。
- 空接口 `interface{}` / `any`：`eface{ _type *_type, data unsafe.Pointer }`，只有类型和数据指针。

`data` 指向实际的值（值较大时会发生堆分配和拷贝，指针类型则直接存指针）。itab 在运行时按（接口类型，具体类型）缓存。

**nil interface 和含 nil 指针的 interface 不相等**：接口值只有在**类型字段和数据字段都为 nil** 时才等于 `nil`。把一个值为 nil 的 `*MyErr` 赋给 `error` 接口，接口的类型字段是 `*MyErr`（非 nil），数据为 nil，所以 `err != nil` 为 true。

```go
type MyErr struct{}
func (*MyErr) Error() string { return "err" }

func f() error {
    var p *MyErr = nil
    return p // 返回的 error 不是 nil
}

func main() {
    fmt.Println(f() == nil) // false
}
```

这是常见的坑：函数返回 `error` 时，不要返回一个具体类型的 nil 指针，应直接 `return nil`。

### 9. GC 调优经验，Golang 大对象频繁分配对Agent 服务(高并发 LLM 调用)有什么影响，怎么缓解

**参考答案**

**Go GC 基础**：并发三色标记清除，带写屏障，STW 很短。GC 触发由 `GOGC`（默认 100，堆增长到上次存活堆的 2 倍时触发）和 Go 1.19 之后的 `GOMEMLIMIT`（软内存上限）控制。

**大对象频繁分配的影响**：

1. 堆增长快，GC 触发更频繁，占用更多 CPU。
2. GC 期间的 **mutator assist**（分配压力大的 goroutine 被拉去帮助标记）会增加请求延迟，造成 P99 抖动。
3. 大对象（超过 32KB）直接从堆上分配，不走线程缓存，分配成本更高，也容易造成内存碎片。
4. 容器内存限制下可能被 OOM。
5. LLM 服务里典型的大对象：长 Prompt、大 JSON 请求和响应体、流式响应缓冲、向量和检索结果。

**缓解手段**：

1. 先用 `pprof`（heap、allocs、CPU）和 `GODEBUG=gctrace=1` 找出分配热点，别凭感觉优化。
2. 复用对象：`sync.Pool` 复用 `bytes.Buffer` 和切片；预分配切片容量，减少扩容。
3. 流式处理：用 `json.Decoder`、`bufio` 流式读写，不要一次性读入整个响应；避免不必要的 `[]byte` 和 `string` 转换拷贝。
4. 减少指针和小对象数量（降低标记成本），注意逃逸分析（`go build -gcflags=-m`）。
5. 调参：根据延迟与内存的权衡调大 `GOGC`，并设置 `GOMEMLIMIT` 防止 OOM（它替代了过去的内存"压舱石"技巧）。
6. 通过限流和限制并发数控制同时存活的大对象数量，必要时拆分上下文大小。

### 10. 说下你跟进过的新技术或论文—比如ReAct / Tree of Thoughts / Self-RAG /AutoGen 你看过哪个，核心收获

**答题思路**

选**真正读过**的 1 到 2 个来讲，用"核心思想 → 对我工程的启发 → 局限"的结构，不要硬背。参考要点：

- **ReAct**：把推理（Thought）和行动（Action）交替进行，用工具的观察结果修正推理，减少幻觉。启发：工具调用循环、结构化 trace；局限：容易循环，步数和成本不可控。
- **Tree of Thoughts**：把推理过程组织为树，对多个候选思路展开、评估、回溯（搜索）。启发：复杂规划可以做多方案评估；局限：调用次数多，成本高，适合高价值任务。
- **Self-RAG**：让模型学会按需检索，并生成反思标记，对检索内容的相关性、生成内容的依据和质量进行自我评估。启发：检索的"是否需要"和"结果好不好"需要显式判断；局限：需要专门训练，工程里更常用 Agentic RAG 加评估节点来近似。
- **AutoGen**：多 Agent 对话式协作框架，通过 Agent 之间的消息交互完成任务。启发：角色分工、对话式协作；局限：可控性弱，需要边界和终止条件。

最后落到"我在项目里借鉴了哪一点，效果如何"，没有实际用过就明说"了解原理，尚未落地"。

### 11. 你是怎么学习一个新框架（LangGraph/Eino）并从 demo 推到生产落地的，学习路径说一下

**答题思路**

按"学 → 做 → 落地 → 沉淀"四步讲：

1. **学**：先读官方文档的核心概念和 Quickstart，再读源码或关键模块（状态、调度、checkpoint），理解设计取舍，并和同类框架对比。
2. **做 Demo**：用一个真实的小场景做最小可运行版本，验证关键能力是否满足需求（流式、中断恢复、并发、可观测）。
3. **评估风险**：框架的成熟度、版本稳定性、社区活跃度、与现有技术栈（Go / Python）的集成成本、是否有可替代的退路。
4. **走向生产**：补齐工程化能力，包括超时、重试、限流、熔断、持久化 checkpoint、trace 和指标、评测集、灰度发布和回滚、压测、依赖版本锁定。
5. **沉淀**：封装公司内部的通用组件和最佳实践，写文档和分享，建立代码模板。
6. 强调"demo 与生产的差距主要在稳定性、评测和成本"，并举一两个你真实踩过的坑。

### 12. 如果团队要推 AI Agent 改造现有搜索/推荐链路，你如何说服TL和业务方，关键风险点说什么

**答题思路**

框架是"**用数据说话，小步验证，风险可控**"：

1. **先讲价值，对齐业务目标**：现有链路的痛点（如长尾 query 无结果、复杂需求无法表达、转化路径长），Agent 能带来的增量（多条件理解、对话式推荐、任务闭环）。用业务指标，而不是技术指标来说服。
2. **提出渐进方案**：不要一次替换主链路。先在细分场景或小流量试点，Agent 作为旁路或增强（例如 Query 理解、复杂 query 的补充入口），用影子流量和 AB 实验验证。
3. **准备证据**：离线评测集上的对比、小范围试点的数据、竞品或行业案例，以及一份成本测算。
4. **主动讲风险和对策**：
   - **延迟**：搜索对时延敏感，需要异步化、流式输出、小模型和缓存。
   - **成本**：模型路由、缓存、预算限制。
   - **效果与幻觉**：评测体系、引用来源、护栏和人工兜底。
   - **稳定性**：降级到原有链路，随时可以回滚。
   - **可控性与合规**：内容安全、数据隐私、可解释和审计。
   - **与现有排序策略的冲突**，以及团队的维护成本。
5. 明确**止损标准**和里程碑，让 TL 看到可控的投入和退出机制。
6. 不要夸大收益，也不要编造数字。

### 13. 手撕算法：写一个 LRU Cache（Golang 实现，Get/Put O(1)，带容量淘汰）

**参考答案**

**思路**：**哈希表 + 双向链表**。哈希表通过 key 在 O(1) 时间找到链表节点；双向链表按使用时间排序，头部是最近使用，尾部是最久未使用。`Get` 命中后把节点移到头部；`Put` 时如果 key 存在则更新并移到头部，不存在则插入头部，超过容量就删除尾部节点（同时从 map 里删除）。用**哨兵头尾节点**简化边界处理。`Get` 和 `Put` 都是 O(1)，空间 O(capacity)。

```go
type node struct {
    key, val   int
    prev, next *node
}

type LRUCache struct {
    cap        int
    m          map[int]*node
    head, tail *node // 哨兵
}

func Constructor(capacity int) LRUCache {
    h, t := &node{}, &node{}
    h.next, t.prev = t, h
    return LRUCache{cap: capacity, m: make(map[int]*node), head: h, tail: t}
}

func (c *LRUCache) remove(n *node) {
    n.prev.next = n.next
    n.next.prev = n.prev
}

func (c *LRUCache) addToFront(n *node) {
    n.next = c.head.next
    n.prev = c.head
    c.head.next.prev = n
    c.head.next = n
}

func (c *LRUCache) Get(key int) int {
    n, ok := c.m[key]
    if !ok {
        return -1
    }
    c.remove(n)
    c.addToFront(n)
    return n.val
}

func (c *LRUCache) Put(key, value int) {
    if n, ok := c.m[key]; ok {
        n.val = value
        c.remove(n)
        c.addToFront(n)
        return
    }
    if len(c.m) == c.cap {
        last := c.tail.prev
        c.remove(last)
        delete(c.m, last.key)
    }
    n := &node{key: key, val: value}
    c.m[key] = n
    c.addToFront(n)
}
```

追问点：并发安全需要加锁，且由于 `Get` 也会修改链表，应使用 `sync.Mutex`，而不是 `RWMutex`；也可以用标准库 `container/list` 实现；高并发下可以分片（shard）降低锁竞争。`capacity <= 0` 要单独处理。

### 1. 自我介绍

**答题思路**

HR 面的自我介绍要简短、清晰，突出稳定性和匹配度：

1. 基本背景：学历、年限、技术方向。

4. 个人特点：沟通协作、责任心、学习能力，配一个简短的事例。

### 2. 为什么想跳来字节做本地生活 AI Agent，对这个方向怎么看

**答题思路**

分"我的动机"和"对方向的判断"两部分：

1. **动机**：想在更大规模、更真实的业务场景里做 AI Agent 的落地；本地生活有丰富的数据、工具（POI、团购、订单）和闭环（从意图到交易），适合验证 Agent 的价值；看重团队的工程氛围和技术成长空间。动机里要有积极的追求，不要只讲对现状的不满。
2. **对方向的看法**：
   - 机会：本地生活的需求高频、场景明确，用户意图常常是多条件的复杂表达，Agent 能提升效率和转化。
   - 挑战：实时性、数据准确性、成本和延迟、可靠性（尤其涉及下单），以及效果评测。
   - 判断：短期内是"增强现有链路"，逐步走向任务闭环。
3. 说明你能带来的价值：把 Agent 做成可上线、可评测、可控成本的系统。
4. 回答要体现你做过的功课，但不要编造对公司业务的具体细节。

### 3. 你最不能接受的公司或团队文化是什么

**答题思路**

这道题考察价值观是否匹配，同时避免踩雷：

1. 选**真实的价值观**，表述为"我更看重什么"，而不是抱怨：例如缺少坦诚沟通、推诿责任、不讲数据只凭主观判断、不允许试错。
2. 用一句话解释原因，并给出你自己的做法（"所以我习惯……"），体现你是积极的，不是挑剔的。
3. 避免极端或会被理解为"不能加班""不能被安排任务"的说法，也不要批评前公司。
4. 可以补充"我也理解不同团队有差异，会先沟通和适应"，体现成熟度。

### 4. 你期望的薪资范围，目前base和期权情况

**答题思路**

不要编造数字，按你真实的情况回答，思路如下：

1. **如实说明目前的构成**：base、奖金、期权或股票分开讲，期权按真实的兑现或可兑现部分说，不夸大。

3. 表达灵活性："具体想听听公司对这个岗位的定级和薪酬结构，我也愿意在合理范围内沟通。"

### 5. 讲一个你和PM或上游撕逼后怎么推进的事例

**答题思路**

这是考察冲突处理和协作能力，用 STAR 讲一个**真实**的例子（不要编造），重点放在"如何解决"，不是"谁对谁错"：

1. **背景**：双方目标是什么，分歧点在哪（需求范围、排期、技术可行性、效果预期）。
2. **你的做法**：先搞清楚对方真正的诉求和约束；用数据或原型说话（评测结果、成本测算、排期风险）；提出备选方案并说明取舍；必要时拉上 TL 或相关方对齐优先级。

### 6. 如果 Agent 项目上线后效果不达预期被老板质疑，你怎么应对

**答题思路**

先稳住心态，用"**数据拆解 → 对齐预期 → 改进计划 → 同步进展**"的结构回答：

1. **先对齐"不达预期"的定义**：是对比什么基线，哪个指标，哪类用户或场景。避免在口径上纠缠。
2. **用数据定位**：分层拆解 bad case（意图识别、检索、工具调用、生成、延迟），按影响量级排序，找出最大的几个问题，而不是笼统地说"模型不够好"。
3. **立即止血**：必要时缩小流量、降级到原链路、关闭效果差的场景，控制风险。
4. **制定改进计划**：短期（Prompt、规则、数据修复）、中期（评测集、检索与路由优化、微调）、长期（架构调整），每项有预期收益、负责人和时间点。
5. **坦诚沟通**：定期同步进展和结论，说明哪些是确定的，哪些还不确定；可以重新对齐预期和成功标准。
6. **复盘**：上线前评测集不足、预期管理不到位等，下次提前做好。
7. 态度上不甩锅、不辩解，让老板看到你可控、有计划。

### 7. 你未来 2-3 年想往哪个方向 deep dive
