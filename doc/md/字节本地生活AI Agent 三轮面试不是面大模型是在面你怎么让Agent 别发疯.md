# 字节本地生活AI Agent 三轮面试不是面大模型是在面你怎么让Agent 别发疯

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这轮不是背八股能混过去的。一面就开始追项目、追数据、追为什么，不是问你知不知道 Agent，是问你有没有真上线过。二面更阴，专挑死循环、Token 炸、子 Agent 失控、工具超时不兜底这些 Demo 里永远不写的坑。三面直接把你按在架构师位置上锤：多 Agent、GraphRAG、Harness、Codex、权限、审计、故障降级全来。

字节本地生活这岗确实难，但说白了就一句话：会调 Prompt 的人一大把，能把 Agent 做成高并发、可观测、可回滚、能背业务指标的没几个。面试官要是只听到 ReAct、多 Agent、RAG 这些名词，基本没戏；你能聊死循环、降级、图库和向量库同步、Codex 生成代码怎么审，才算进门。

别怕被怼。这种面就是在筛只会做 Demo 的人。答不上来正常，但别装，装一眼就会被看穿。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「我是谁 → 做过什么 → 为什么和这个岗位有关」讲完就停。

1. 一句话交代年限和方向，点出你真实写过的检索、工具调用或对话链路。
2. 只展开一个最相关的项目：用户要完成什么事、你负责哪一段、结果用你拿得出来的证据。没有数字就讲评测集或坏例。
3. 收到本地生活上：查门店、用券、下单会碰到真实库存和金额，工具要有超时、幂等和确认。
4. 把话停在你准备被追问的那个项目上，方便面试官顺着往下挖。

### 2. 最近做的 AI Agent 项目介绍，你在里面负责哪一块

**答题思路**

面试官要听见边界，不是听见一个全栈形容词。用真实项目套这个顺序：

1. 一句话说明用户是谁、任务是什么、为什么一次问答不够。
2. 用三五句画出请求路径：入口、意图和槽位、检索或工具、校验、回复。标明哪几步是你写的，哪几步是现成服务。
3. 只讲一个你负责的难点，按「现象 → 怎么定位 → 改了什么 → 怎么验证」说。常见的真问题有：槽位被下一句盖掉、工具超时被重复执行、检索命中了但生成改了价格。
4. 补一句线上约束：步数或超时上限、失败时用户看到什么、金额从哪个接口来。
5. 团队项目不要把整条链路都说成自己的。简历里没有 Agent 时，讲最接近的检索、规则或工作流，并说明它还缺观察和完成判定。

### 3. 本地生活场景里，用户一句话下单、查门店、退券、问活动，怎么做意图识别

**参考答案**

先把一句话拆成意图列表，再填槽位。本地生活里一句经常叠了多件事，「附近火锅，再用掉那张券」是查门店加用券，压成一个标签会丢动作。

多轮先补全省略和指代，把「那张」「这家」还原成券和门店，再分类。意图至少分开：下单、查门店、退券、问活动、查订单、闲聊。槽位包括门店、菜品、时间、地点、人数、券码。高置信且槽位齐就进入对应流程；缺的只追问缺的那一项。下单和退券即使意图对了，也要用户确认对象和金额。

「再加两个人」多半是当前订单的人数，不是新意图。判别标准是：它有没有换任务。换了任务才新开一条意图，否则只更新槽位。

### 4. 意图识别用规则、分类模型还是 LLM 路由，各自什么时候用

**参考答案**

三种按代价和失误代价叠在一起用。

规则适合封闭、必须稳定命中的说法：订单号、券码、明确指令「取消订单」。时延低、可解释，换种说法就失效。分类模型适合意图表已经稳定、有标注、流量大的入口，用置信度做阈值；新意图和一句多意图要补标注。LLM 路由适合长尾说法、类别还没枚举完、需要同时出槽位的请求，输出必须落成结构化结果，并单独设超时。

线上常见顺序是规则先接精确串和高风险指令，分类模型接大部分流量，低置信或明显多意图再升级到 LLM。升级之后仍然低，就向用户澄清。资金是否可退、库存够不够，由后续规则和接口判定，路由只决定进哪条流程。

### 5. Python 里 asyncio 跑批量 Agent 任务，为什么不能无脑并发，怎么限流

**参考答案**

协程创建很便宜，模型和工具的额度并不便宜。无上限并发会打满 RPM、TPM、工具 QPS 和连接池；每个任务还握着提示词和响应。默认事件循环是单线程的，循环里混进阻塞 IO 或大段 JSON、分词，所有任务的尾延迟一起变差。失败后全体立刻重试，会把限流打成雪崩。

限流按依赖拆开：模型、检索、写工具各有各的并发上限和速率上限。批量任务用固定数量的 worker 消费有界队列，队列满了就停止拉取，这就是背压。散落的调用点用 Semaphore。每次调用带超时，超时要取消底层 HTTP，连接才不会继续占着。重试只覆盖超时和 429 这类错误，带次数和抖动；写操作带幂等键。

`asyncio.gather` 一次创建全部任务时，Semaphore 只能限制在途请求，限制不了任务对象本身。任务量很大时用 worker，而不是先把几十万个协程建出来。

### 6. Golang 里用 goroutine 调 LLM 工具，context 超时和 cancel 怎么设计，怎么避免 goroutine 泄漏

**参考答案**

取消不会自动停掉 goroutine。每个阻塞点都要观察 `ctx.Done()`，调用返回之后 goroutine 才算退出。

入口使用请求自带的 context。单次模型或工具调用用 `context.WithTimeout` 派生子 context，并且 `defer cancel()`，调用提前结束时把定时器释放掉。HTTP 使用 `NewRequestWithContext`，超时后连接才会中断。父 context 已经快到期时，子调用不会重新获得一段完整超时。

泄漏通常来自阻塞发送没有人接收：接收方已因超时返回，发送方仍卡在无缓冲 channel 上。另起 goroutine 时，调用本身要认 context；结果写入容量为 1 的 channel，发送方在取消后也能返回。循环里用 `time.After` 会留下定时器直到触发。一组工具调用可以用带 context 的 errgroup，其中一个失败就取消其余调用，已经取消的路径不再写共享状态。

### 7. RAG 里 Chunk 怎么切，代码、门店公告、活动规则、用户对话分别怎么处理

**参考答案**

切分要保住一块里的事实是完整的，统一字数做不到这一点。

代码按语法边界切，函数、类、配置项整段保留，签名和注释跟实现在一起。元数据写上路径和符号名。从函数中间切开，召回的是半截逻辑。

门店公告多数一条一块。较长的按营业时间、地址、暂停营业这类标题切，每块带上门店、城市和生效时间。检索按当前时间过滤，过期停业通知不能因为向量相近被召回。

活动规则按条款切，每块都带上活动名、人群、时间和门槛。「满 100 减 20」必须留在同一块，互斥和叠加规则跟对应条款放在一起。重叠窗口补不回被切断的数字条件。

用户对话单独索引，按一次任务切段，更早的轮次收成摘要，电话和地址先脱敏。检索带用户过滤。公告、规则和对话混进同一个无权限索引，会把别人的订单内容召回来。

### 8. BM25 和向量召回有什么区别，为什么本地生活搜索经常要混合召回

**参考答案**

BM25 按词频和逆文档频率打分，店名、菜名、券码、地址和门槛数字要原样出现才能命中。说法换了就召不回，它也不理解「便宜」「适合约会」。

向量召回把查询和文档映到同一空间，改写和模糊描述能对上，精确 ID、数字和否定容易弱，近似最近邻还可能把名额占满，过滤之后所剩无几。

本地生活两种问法都有。「海底捞」要词面命中；「安静、适合两个人的火锅」靠语义。两路并行召回，用倒数排名融合合并名次，再用城市、营业时间和库存过滤。查询改写要留下品牌名。只走向量时，精确店名会被语义近邻挤掉。

### 9. 向量数据库选 Milvus、Qdrant、Weaviate 还是 VikingDB，重点看哪些点

**参考答案**

先看过滤能不能和向量一起做。本地生活的查询几乎都带城市、租户、营业时间和地理范围。近似最近邻做完再后过滤，前 k 条可能全部被滤掉。选型时看过滤能否下推，或者库是否支持带过滤的迭代检索。

再看按主键的更新和删除。营业时间和库存会变，要能按门店删改，而不是整库重建才生效。混合检索若需要自己在库外维护 BM25，就要算上这一份链路。多租户隔离、HNSW 的内存、量化之后召回怎么验、备份和监控，都比公开榜单有用。

Milvus 适合大规模分布式和分区；Qdrant 的过滤和运维面比较直接；Weaviate 自带关键词和向量的混合检索；VikingDB 是火山引擎上的托管向量库，模型和业务已经在这朵云上时，合规、网络和嵌入接入比自建功能清单更要紧。用同一份带过滤的业务查询对比，再决定。

### 10. 图数据库在本地生活里能干什么，门店、菜品、用户、订单、POI 怎么建模

**参考答案**

图用来回答多跳关系。地理范围和全文检索各自有索引，不必塞进图里。

点用用户、门店、菜品、订单、POI、券、活动、品牌。边表示用户下了订单、订单包含菜品、订单发生在门店、门店属于品牌、门店落在某个 POI、活动适用于门店或品牌、用户持有券、券适用于品牌或门店。商场这类 POI 下面可以挂多家门店，火锅店和影院是附近的两个点，路程用地理索引算完再连回图。不要给每对门店建一条距离边。

这样能回答「这张券能不能用在这家店的这个套餐上，加盟店是否排除」「上一单那家的同品牌，周六还有没有位」。环境安不安静仍走标签或向量。价格和库存以下单时的业务库为准，图可以略滞后。

### 11. Agent 调工具时参数写错、返回脏数据、接口超时，怎么兜底

**参考答案**

三类失败分开接，不要都丢回模型自由重试。

参数在调用前用 JSON Schema 检查类型、枚举和必填项。校验失败把错误交回模型改一次，并限制次数。写操作先有幂等键，重试不会变成第二单。

返回同样按契约检查。价格为负、门店和请求对不上、缺少订单号，都算工具失败，这段 JSON 不能写进后续上下文当事实。

超时、429、503 可以有限重试并加抖动；参数非法和业务拒绝直接停止。只有读操作，或带幂等键的写操作，才能自动重试。熔断打开后，读可以退回标明时效的缓存；下单和退券失败要明确告诉用户还没完成。模型不能在没有成功结果时口头确认订单。

### 12. 说一下 ReAct 和固定 Workflow 的区别，什么场景不该上 Agent

**参考答案**

ReAct 每一步根据工具的真实返回决定下一次调用，步骤事先列不全时用得上。步数、时延和结果都不稳定，要有步数上限和停止条件。

固定工作流把分支写在状态机里，模型填槽，或只判断其中一个节点。同一输入的路径可以复现，时延和审计都更好测。

支付确认、退券资格、库存扣减、高频且一步能完成的查询，用规则或工作流。这些路径的失败模式清楚，自由循环只增加重复下单和说不清失败的概率。开放式多约束，例如先找能用券的火锅再看附近场次，可以让模型在检索节点里决策；真正下单仍回到确认节点。

外壳用工作流、个别节点用模型，通常比整段对话都交给 ReAct 好测。

### 13. 手撕算法：最长无重复字符子串

**参考答案**

用滑动窗口。右指针逐个扫字符，哈希表记录每个字符上次出现的下标。这个下标落在当前窗口里，就把左指针移到它的下一位。窗口 `[left, right]` 始终没有重复字符，过程中保留最长的那一段。

时间 O(n)，空间 O(min(n, 字符集大小))。

```python
def longest_unique_substring(s: str) -> str:
    last = {}
    left = 0
    best_l, best_r = 0, 0  # 半开区间 [best_l, best_r)
    for right, ch in enumerate(s):
        prev = last.get(ch)
        if prev is not None and prev >= left:
            left = prev + 1
        last[ch] = right
        if right + 1 - left > best_r - best_l:
            best_l, best_r = left, right + 1
    return s[best_l:best_r]
```

窗口外面的旧下标不能把 `left` 往回拉，所以要判断 `prev >= left`。`abba` 会踩中这一点。空串返回空串。存在多段同样长的答案时，上面的写法保留最先出现的那段。题目如果只问长度，返回 `best_r - best_l` 即可。

## 二面

### 1. 自我介绍

**答题思路**

二面官多半看过简历，自我介绍压到 45 秒左右，用来把后面的深挖引出来。

1. 一句话说明年限和方向。
2. 直接点你准备讲透的那条 Agent 链路：用户请求进来之后，经过哪几个状态，最后哪一步算执行完成。
3. 补一个你亲自处理过的失败，例如超时、重复执行或检索和生成不一致，只点名字，细节留给追问。
4. 结束在这条链路上。公司背景和完整履历简历上已经有，不必再铺一遍。

### 2. 把你的 Agent 项目完整讲一遍，从用户请求到最终执行结果

**答题思路**

按一次真实请求的时间顺序讲，每一步说清输入和输出。用你自己的项目填空，没有的环节就明说当时没有。

1. 请求进入：身份、会话、城市和渠道从哪里来。这些字段由网关注入，不由模型填写。
2. 理解：查询改写、意图列表、槽位、还缺什么。
3. 决策：这一跳走固定流程、检索，还是工具。给出当时的停止条件。
4. 执行：工具名、参数校验、超时、幂等。读和写分开讲。
5. 观察：返回怎么校验，失败时用户看到什么，状态写到哪里。
6. 结束：什么叫成功，部分成功怎么表示，有没有确认步骤。
7. 最后留三个可以追问的点：状态存在哪、钱和库存以哪个接口为准、怎样从一次请求追到全部工具调用。

### 3. Supervisor / Planner / Worker / Reviewer 的边界怎么划，工具集能不能共用

**参考答案**

Supervisor 掌握用户目标、步数和费用预算，决定把哪一段交给谁，只看结构化摘要。Planner 产出带依赖和完成条件的任务，不调用有副作用的工具。Worker 只拿一个域的工具，例如门店或券，按任务卡执行，不能改全局目标，也不能无限再派子任务。Reviewer 对照模式和业务约束检查计划与观察，金额、对象、是否真有工具结果都在这里看；它可以打回，不能替用户改需求。

工具注册表可以共用，权限按角色发允许列表。写工具只给指定的 Worker，并且经过确认。Supervisor 如果握着全部写权限，前面的分工就失去约束力。Worker 之间不共享原始轨迹，只接收父级显式传下来的字段，例如已经选定的门店。

### 4. 多 Agent 协作用中心化调度还是去中心化，字节本地生活这种高并发业务为什么通常选中心化

**参考答案**

中心化是一个调度器分配任务、合并结果，并统一卡住步数、费用和截止时间。去中心化是 Agent 互相发消息，组合灵活，时延、重复调用，以及谁有权下单，都更难封顶。

本地生活的在线流量高，而且下单、用券、占库存都有副作用。一条用户请求需要对齐到同一份任务状态、全局限流、幂等键，以及一条能追到每次工具调用的 trace。尖峰时调度器可以排队，先丢掉离线索引重建，保住还在等待的那条请求。Agent 彼此自由调用，会在尖峰把模型次数乘上去。

线上形态一般是中心调度加无状态 Worker。没有写权限、深度有上限的子任务，可以在调度器划定的范围内互相配合。

### 5. Agent 死循环怎么防，最大步数、重复动作检测、结果校验怎么落地

**参考答案**

提示词里写「不要循环」挡不住循环，运行时要有三道硬限制。

第一道是预算：最大步数、最大工具次数、token 和墙钟时间。到点就停止，向用户说明没完成或转人工，避免停在含糊的「正在处理」。

第二道是重复动作。工具名加上规范化之后的参数做哈希，同样的签名连续出现几次，槽位却没有变化，就停止或强制重新规划。A、B 两个调用来回振荡也算没有进展。

第三道是结果校验。观察要符合模式，并且带来新证据，例如少了一个未填槽位，或出现了新的门店。同一参数的返回若和上次相同，就不再调用。

停下来之后，已经预占的库存要释放，或标成待确认。只把对话状态删掉，业务侧的预占还在。

### 6. 子 Agent 再调子 Agent，上下文和 Token 怎么炸，怎么隔离状态

**参考答案**

子 Agent 若继承父会话全文，每一层都会把历史再复制一份，token 随深度和扇出一起涨。工具原文再贴进上下文，会把窗口占满，真正的任务约束反而被挤掉。

子任务只接收任务卡：目标、约束、允许的工具、预算。它返回结构化结果和引用。父级按引用保存，放进上下文的是摘要。工具原文放在对象存储或 Redis。

再加三道限额：深度通常限制在两层，限制扇出数量，子预算小于父级剩余。每个 Agent 使用单独的 checkpoint 命名空间。共享的只有显式字段，例如选定的门店，而不是同一条聊天记录。子任务看不到的历史，就调用不了不该调用的工具。

### 7. Agentic RAG 和普通 RAG 区别，什么时候要让 Agent 自己决定再检索一次

**参考答案**

普通 RAG 的检索次数是写死的：改写、召回、重排、生成。Agentic RAG 由模型决定要不要检索、查向量、关键词还是图，以及看完证据后要不要再查。

再查要有具体缺口：某个必填槽位没有证据，几条证据互相冲突，改写把品牌或时间弄丢了，或者命中的活动已经过期。思考过程里写了「我不太确定」，本身不构成再检索的理由。

再检索设一个很小的上限，常见是额外一两轮，并且要换查询或换数据源。用同一句话重复打同一个索引，不算进展。到了上限仍缺证据，就说明缺什么，或改问用户。

### 8. 检索结果来了以后为什么要加 Rerank，Rerank 模型和向量库各自解决什么问题

**参考答案**

向量库负责在大量文档里召回。查询和文档分开编码，才能做近似最近邻；两者没有细粒度交互，否定、门槛数字和是否营业容易排错。

Rerank 负责短名单的顺序。交叉编码器把查询和文档放在一起打分，计算贵，所以只打融合之后的几十到一两百条。它调整的是已经召回到的候选。金标文档没有进候选，换重排模型也出不来，要回到召回。

本地生活的混合召回会给出一堆相似门店和活动。重排阅读标题、规则全文和当前约束，把正在营业、有这道菜、门槛对得上的排到前面。向量分和重排分解决的是两段不同的问题。

### 9. 图数据库做 GraphRAG，和纯向量检索比，适合回答哪类本地生活问题

**参考答案**

纯向量适合一段文本就能答的模糊描述，例如环境、口味。它覆盖不了散落在多条记录里的关系：券适用于品牌但排除加盟店，上一单的店同一品牌附近周六还能订，套餐和券能不能叠加。

图检索从实体出发走有限跳，把路径上的条款交给模型，回答里保留边的类型。本地生活用维护好的业务图，点是门店、菜品、券、POI、订单。把评论做社区发现再生成社区摘要，适合开放域的主题问答，不能当作能不能用券的依据。

跳数和超时要有上限。图里没有的偏好回到向量。金额和适用关系在下单前用业务库对一次版本。

### 10. Go 写 Agent 后端，为什么有时候比 Python 更适合做网关、调度、并发执行

**参考答案**

这里比的是控制面。模型推理在独立的模型服务里，网关进程比的是大量在途连接、取消和尾延迟。

Go 用 goroutine 配 netpoller，可以用同步写法承接很多流式上游；`context` 是标准库约定，客户端会跟着取消；静态类型适合卡住工具的请求和响应；部署是单个二进制。Python 的 asyncio 同样能并发等待网络，GIL 在等待 socket 时会放开。线上容易出问题的是同步 SDK 把事件循环堵死，以及分词、大段 JSON 和校验占住循环。

Go 更适合做成统一的超时、连接池和限流。提示词实验、评测和依赖 PyTorch 的重排，仍放在 Python。两边谁调用模型 API，取决于契约和中间件放在哪一层，不取决于语言能不能发 HTTP。

### 11. Python 和 Golang 在 Agent 系统里怎么分工，模型调用、编排、工具执行、在线服务怎么切

**参考答案**

Go 承担在线控制面：鉴权、配额、编排状态机、工具网关，以及需要严格超时的执行。有副作用的工具都经过这层，重试、幂等和审计才有同一套规则。

Python 承担迭代快的部分：提示词实验、评测、离线切片和嵌入，以及必须用 Python 模型栈的重排或小模型。仅仅是 HTTP 调用模型 API 时，Go 网关可以直接调用。

两边共享同一份 JSON Schema 或 protobuf。Python 服务写订单时，也要经过租户检查和幂等中间件，不能因为在做实验就直连交易库。在线路径的进程和离线重建的进程分开，重建挤占不了用户正在等待的配额。

### 12. Kafka 或 RocketMQ 在 Agent 系统里用来干什么，工具执行异步化、消息积压怎么排

**参考答案**

消息队列承接不必占着请求线程的工作：订座回执、退券审核、文档变更之后的切片和嵌入，也可以作为工具调用的事件日志，供审计和回放。用户正在等待的短读取仍走同步调用。

同一任务用会话或实体做分区键，既保证这条任务有序，又避免所有流量进一个分区。用户态工具和离线重建分主题、分优先级。看消费延迟。失败先进入重试队列，再进入死信；一条毒消息不能无限重试，把分区堵住。消费者按工具调用 ID 做幂等。

延迟升高时，编排器少生产低优先级任务，先保住用户正在等的那条。RocketMQ 的延时消息适合退避重试，Kafka 适合高吞吐日志。集群用团队已经在运维的那一种，积压时的取舍不变。

### 13. Redis 在 Agent 里存什么，会话状态、意图缓存、工具结果缓存、分布式锁怎么用

**参考答案**

会话热状态按 session 存一份 JSON，带版本号做乐观锁，并设置 TTL。需要追责的最终状态写入数据库。Redis 丢失后可以重建进行中的会话，订单账本以数据库为准。

意图缓存的键包含规范化查询和意图体系版本；结果因人而异时，键里还要有用户分桶。只缓存高置信结果，TTL 短。

工具缓存只覆盖幂等的读，键包含参数哈希和数据版本。下单、退券的成功响应不能拿来复用。

锁用 `SET key token NX PX`，解锁时比对 token。它只包住状态合并这种短临界区。等模型的十几秒不放在锁里面。写操作去重用幂等键；锁的过期时间到了，请求仍可能还在执行。

### 14. Harness 层是什么，和 Agent 提示词、模型、工具调用之间的关系是什么

**参考答案**

Harness 是模型外面的运行时。它解析模型给出的动作，做鉴权，执行工具，把观察写回，保存状态，限制步数和费用，并留下 trace。

提示词表达任务、格式和约束。模型根据当前上下文提出下一步。工具描述是契约，说明参数和返回。这一步能不能执行、超时之后怎么停止、失败算不算完成，由 Harness 决定。模型宣布成功，代替不了工具的成功结果。

没有这层，系统就只是在循环里拼接消息。死循环、越权和重复副作用都要靠运行时截住，改提示词解决不了执行权的问题。

### 15. 手撕算法：合并多个有序链表，并说下在多路召回结果归并里的类比

**参考答案**

k 路有序链表用大小为 k 的小根堆归并。每条链表的当前头节点入堆，每次弹出最小节点接到结果上，再把它的后继入堆。堆里放入链表下标，相等值比较下标，避免去比较节点对象。

时间 O(N log k)，空间 O(k)，N 是节点总数。

多路召回里，每一路是一个有序列表，堆可以做 k 路归并。前提是比较键属于同一尺度。BM25 分、向量距离和图上的跳数不能直接入堆。先变成同一尺度的重排分，或按名次做倒数排名融合，再归并。

```python
import heapq

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def merge_k_lists(lists):
    heap = []
    for i, node in enumerate(lists):
        if node is not None:
            heapq.heappush(heap, (node.val, i, node))
    dummy = ListNode(0)
    tail = dummy
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node
        tail = node
        if node.next is not None:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next
```

全部为空时返回 `None`。节点值相等时，下标保证堆比较的是元组前两项，不会落到 `ListNode` 上。

### 1. 自我介绍

**答题思路**

三面听的是架构判断。控制在 1 分钟，把一个你真做过的取舍摆到台面上。

1. 一句话说明你做 Agent 的年限和主要场景。
2. 讲一个架构决定：例如写操作收口到工具网关、调度用中心化、检索和图以业务库为源。说明当时的约束是什么。
3. 讲这个决定挡住了哪类事故，例如重复下单、说不清的失败或索引和交易不一致。用你能展开的证据。
4. 停在这个决定上，让面试官来挑战。完整项目时间线留给下一问。

### 2. 讲一个你做过的复杂 Agent 项目，最难的一版架构是怎么演化的

**答题思路**

讲演化，不要讲成一次设计就定稿。用真实项目，按版本说。

1. 第一版解决什么：通常是一条能跑通的只读链路。当时的状态存在哪，失败怎么返回。
2. 哪次上线把这版打穿：挑一个真问题，例如工具超时被重试成多次执行、多轮把槽位盖错、检索和生成各说各的价格。
3. 下一版改了哪一层：状态机、幂等、checkpoint、评测集或权限。说明为什么没改提示词了事。
4. 怎么知道新版本更好：同一批坏例、影子流量或灰度。没有数字就讲对比口径。
5. 如果重做，哪一层会先于多 Agent 框架做出来。主动承认第一版缺的东西，比把每版都说成最优更可信。

### 3. 本地生活业务里，用户说「帮我安排周六下午和女朋友吃火锅顺便看电影」，多 Agent 怎么拆任务

**参考答案**

先把约束列出来：周六下午、两人、火锅、还要看电影，两件事有先后，中间有路程。地点没说，就用用户默认商圈；没有默认就问。随便选一个区，后面的店和场次都会错。

Planner 产出一张有向无环图：解析地点之后，火锅检索和排片并行，再按用餐、路程和场次拼起来，最后给出一到两个方案。用餐和路程用可配置的假设，并且让用户看见。门店 Worker 只查火锅、营业时间和两人桌；电影 Worker 只查附近场次。拼接用 POI 路程，两家各自评分高，不代表赶得上。

Reviewer 核对时间有没有重叠、店是否仍在营业、场次是不是工具返回的。订座和购票等用户确认具体方案之后才执行。一边失败，就释放另一边的预占。

跨域约束和部分有货是难点。用户没同意的晚场，不能为了有票擅自换上。也不必再派一个没有明确输出的 Agent。

### 4. 意图识别不准时，是先改分类、改 Prompt、改检索还是加人工兜底，怎么用数据定位

**参考答案**

先定位再改。抽坏例，标上金标意图和槽位，看混淆对，例如退券和查券、下单和问活动，再按渠道、是否多意图、句子长短切片。

标注彼此矛盾，就先改标签体系和标注说明。规则在精确词上误伤，就收规则。分类器在已经稳定的类上大面积错，补这批评测数据再训练，同时看置信度还能不能当阈值。意图若靠检索回来的示例，错例来自错误示例，就改检索。提示词只有在类别定义本身含糊，而且同一评测集能复现时才改。每次改动都跑同一套集。

人工兜底用来接低置信和资金类请求，控制失误代价。兜底率要单独看，它变成主路径，说明前面的系统性错误还在。

### 5. 多 Agent 系统上线后 Bad Case 怎么归类，意图、检索、规划、工具、生成分别怎么判责

**参考答案**

沿 trace 找到第一次偏离金标的阶段，那一阶段记主责。一条 case 可以有次因。

工具还没调用，路由或槽位就错了，记意图。用户已经说了人数，槽位里却没有，仍算理解。意图对，证据缺失、店错或活动过期，记检索，对照候选里有没有金标文档。证据够，步骤顺序错了或约束丢了，例如把看电影丢掉，记规划，看计划产物。计划里的工具名和参数符合策略，但超时、5xx 或返回缺字段，记工具，看状态码和校验结果。观察是对的，最终话术和观察矛盾，例如接口没有下单却说订好了，记生成。

券服务返回 500，主责在工具。把它记成模型幻觉，后面的修复会改错地方。

### 6. Codex / Claude Code 这类编码 Agent 做需求，你怎么把模糊需求写成 Spec

**参考答案**

规格要把产品决定写死，让编码 Agent 按契约实现。里面包括：目标、明确不做的事、用户可见行为、验收例子（成功、失败和边界）、接口和数据契约、不变量（幂等、权限、金额以哪张表为准）、允许修改的目录、禁止碰的模块、用什么命令验证。

还没决定的问题写成阻塞项。「按最佳实践处理」会让模型自己选一套方案。例如「优化下单」要写成触发条件、输入输出、超时和重复点击怎么处理、怎样算完成。

规格和当时的提示词版本一起留在仓库里。回放一次生成时，才知道它被要求做什么，验收命令也才能原样再跑。

### 7. AI 生成代码能跑但架构烂，你怎么审，哪些模块绝不让 AI 直接定方案

**参考答案**

现有测试通过，只说明这些测试覆盖到的路径是绿的。测试若也是模型生成的，并且只走成功路径，评审还没开始。

看依赖方向和状态放在哪里：领域规则是收在领域模块里，还是散在控制器和提示词里；副作用有没有经过工具网关。逐项看超时、重试上限、写操作的幂等键、密钥有没有进仓库、事务边界对不对。捕获全部异常再返回成功，这种代码会把失败伪装成完成。

方案由人先写约束的模块是：支付和退款、库存扣减、租户隔离和鉴权、隐私数据、对外 API 兼容、作为事实来源的数据迁移。模型在已经定好的接口内实现。评审结论写在变更上：接受、要改，或这一版结构推倒。CI 通过代替不了这个结论。

### 8. Harness 工程里 checkpoint、replay、trace、回滚、人工介入点怎么设计

**参考答案**

Checkpoint 写在每个可恢复步骤之后：Agent、步骤号、计划、工具调用 ID、输入哈希、观察的引用、状态，以及提示词和工具 schema 的版本。能按版本重建的全文不必整段存下。

Replay 用当时的 checkpoint 和录下来的工具输出，复现模型当时看到的观察，用来查错。继续执行是另一件事。有副作用的工具不能因为回放再打一次；接着跑靠幂等键，读可以使用录制结果。

Trace 以用户请求为 trace id。模型、检索和每个工具各有 span，带上 token、缓存是否命中和工具错误码。

上下文可以回到上一个 checkpoint。业务动作不会跟着回去。步骤标成只读、预占或已提交；只有工具提供补偿，例如释放占座、撤销未支付单，才能做业务回滚。已支付的订单要走补偿，恢复图状态取消不了它。

人工介入放在低置信、超过金额阈值、策略拒绝、重复失败和证据冲突。图暂停为待处理，人的决定作为一条新观察写回，再从该 checkpoint 继续。待处理状态本身有超时。

### 9. 向量库和图库一起用时，数据一致性怎么保，文档更新后向量和图谱怎么同步

**参考答案**

业务库是事实来源，向量库和图都是派生物。

变更通过发件箱或 binlog 发出，事件带实体 ID、内容哈希和版本，并按实体分区，旧事件不会覆盖新版本。切片嵌入和图更新是两个消费者，写入同一个版本号。失败就重试这条事件。请求线程里同时写两边，一边成功一边失败时，没有一张待重试的事件可以补齐。

读路径可以接受短暂滞后，结果上带版本。券、价格和库存在下单前用业务库再查一次。删除写墓碑，两个索引都删。再加对账，按更新时间扫描源和索引的版本差。

检索略旧，影响的是推荐文案；提交路径用旧索引扣库存，影响的是订单。两条路径的一致性要求不同。

### 10. Agent 平台要做多租户、权限隔离、工具鉴权、审计日志，核心模块怎么画

**参考答案**

租户 ID 来自鉴权结果，由网关注入。模型填进参数里的租户 ID 不作数。

模块分成这些：网关负责身份和配额；控制面保存每个租户的 Agent 配置、工具注册和提示词版本；鉴权决定谁能调用哪个 Agent 和哪个工具；数据面把索引分成命名空间或强制加上租户过滤，缓存键带租户前缀，记忆按租户隔开；凭证放在保险库，按租户取用，不进提示词；审计日志追加写入，字段包括租户、操作者、工具、参数哈希、结果码和 trace id。

模型到工具之间再过一次工具网关，鉴权和审计在这里做。模型自称已经获准，网关仍要再查一次。提示词里可能有个人信息，普通日志脱敏，审计日志的访问单独授权。

### 11. 模型故障、工具故障、检索故障同时发生，降级策略怎么排优先级

**参考答案**

三路一起出故障时，先保证有副作用的动作不会被做错，再保证事务读的真实性，最后才是回答完整。

写入：工具不可用，或返回经不起校验，就拒绝下单和退券。回复里不能出现「已经订好」。

事务读：订单和券的状态以接口为准。检索不可用时，这条读仍走接口。接口也不可用，就明确失败。向量里的旧文案不能冒充实时状态。

模型不可用：高频只读意图走规则和模板，多 Agent 规划关掉。备用模型若守不住工具契约，就只生成说明，不提交订单。

检索不可用：活动和推荐改成暂时查不了；精确店名还可以走结构化查询。

三路都不可用时，返回系统繁忙并给出转人工的入口，停掉自动重试，避免把剩余依赖打穿。丢弃顺序是离线重建和重排、开放式规划，最后才是核心只读。

### 12. 最近在学什么 AI 工程化东西，怎么判断一个新技术是真能上线还是玩具

**答题思路**

挑一件你最近真在看或真在做的事，讲深，不要报一串名词。

1. 说清对象：例如评测集、工具运行时、索引同步或追踪。你读到了哪一层，自己动手复现了哪一小段。
2. 用下面的问题判断它能不能上线，而不是用发布会的形容词：
   - 超时、脏输出、部分成功时，状态停在哪里。
   - 有没有来自真实流量的评测，而不只是几十条手挑样例。
   - 事实以哪个库为准，索引滞后时提交路径怎么处理。
   - 目标 QPS 下的时延和单次任务成本能不能说清，包括尾延迟。
   - 失败能不能回滚或补偿，谁会收到告警。
   - 工具权限边界在运行时的哪里。
3. 笔记本里能跑、没有预算和 trace、说不出工具 500 时用户看到什么，就还是演示。
4. 承认你还没验证的部分。面试官会顺着你声称看过的那一项往下问。

### 13. 你是怎么读论文、看源码、踩生产坑来建立 Agent 工程认知的

**答题思路**

讲方法，不背一篇你没读过的论文。三样材料各解决不同的问题。

1. 论文用来看问题定义、假设和消融：作者假定工具一定成功了吗，检索是一次还是循环。记下假设，不记口号。
2. 源码用来对运行时：checkpoint 写在调用前还是调用后，取消有没有传到 HTTP，工具失败是抛错还是被收成一段文本。选一个你真的打开过的框架或服务，按一次请求把这条路径走完。
3. 生产事故用来补前两者不会写的部分：超时之后的重试、脏 JSON、索引版本和交易版本不一致。每个坑记四列：现象、根因、改动、怎么防止再发。
4. 输出一份自己的笔记：主张、它依赖的假设、在你的链路上哪一条不成立。面试时主动邀请对方挑其中一条深问。

### 14. 如果让你从 0 搭字节本地生活 Agent 中台，先搭哪一层，半年里程碑怎么排

**参考答案**

先搭工具网关，再谈多 Agent 框架。网关里有 schema、超时、幂等、鉴权和审计。本地生活的工具会碰库存和金额，没有这一层，上面的规划无从约束。

然后只做一条只读竖切，例如查门店或查订单，带上 trace、黄金评测集和失败时的明确返回。第三条才是活动和规则的混合检索，解决时效与引用。这条路径的坏例能闭环之后，再做跨域规划和人工确认，并加上 checkpoint。多租户和配置平台放在已经有一条能看指标的链路之后。

半年可以这样排：第一个月交付网关和一条只读意图；第二到三个月做活动检索、坏例闭环、限流和缓存；第四个月做带确认和步数上限的多步骤；第五到六个月接入第二个域，补上租户隔离，并做故障降级演练。看任务成功率、工具错误率和单次任务成本。

### 15. 手撕算法：给定一个任务依赖关系，用拓扑排序判断 Agent DAG 是否能无环执行，并输出执行顺序

**参考答案**

用 Kahn 算法。边 `(pre, post)` 表示 `pre` 完成后才能执行 `post`。统计入度，入度为 0 的节点入队；弹出时写入结果，并把后继入度减一。结束时处理过的节点数小于 n，图里有环，拒绝执行。有环时不要删掉一条边硬跑。

时间 O(V+E)，空间 O(V+E)。节点编号需要落在 `0` 到 `n-1`。

同时入度为 0 的节点谁先执行，可以用优先级决定，偏序保持不变。拓扑顺序只说明没有循环依赖。下单这种节点即使排到了，仍要等用户确认，到点不等于自动提交。

```python
from collections import defaultdict, deque

def agent_execution_order(n, edges):
    indeg = [0] * n
    graph = defaultdict(list)
    for pre, post in edges:
        graph[pre].append(post)
        indeg[post] += 1
    ready = deque(i for i in range(n) if indeg[i] == 0)
    order = []
    while ready:
        node = ready.popleft()
        order.append(node)
        for nxt in graph[node]:
            indeg[nxt] -= 1
            if indeg[nxt] == 0:
                ready.append(nxt)
    if len(order) != n:
        return None
    return order
```

自环和互相等待都会让部分节点入度降不到 0，函数返回 `None`。模型生成的图要先检查端点是否存在，再排序。
