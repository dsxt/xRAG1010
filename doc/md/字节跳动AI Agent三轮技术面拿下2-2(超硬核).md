### 2. 项目介绍，重点介绍与 AI Agent 相关的项目经验

**答题思路**

### 3. 多模态大模型的具体结构是什么样的？请详细描述视觉编码器和语言模型的衔接方式

**参考答案**

主流结构是视觉编码器产出一串 patch 向量，连接层把它们对齐到语言模型的隐藏维度，再替换文本里的图像占位符，和文本 embedding 拼成同一条序列，由解码器做自注意力。

视觉侧多用 ViT。图像切成 patch 编码；要看清文字或细节时，会做动态切块或保留更高分辨率，而不是先压成一张小图。衔接常见三条路：线性层或两层 MLP 只改维度，token 数不变，细节好、占上下文多；Q-Former、Perceiver 用少量可学习 query 做交叉注意力，压成固定长度，省 token、会丢细节；也有把跨模态注意力插进语言模型各层的做法，按层注入视觉特征。

视觉向量直接处于 embedding 空间，不再过词表。它们占用语言模型的位置编码，后面文本的位置随图像 token 数后移。损失一般只算在文本回答上。训练通常先冻住编码器和语言模型、只训连接层，指令微调时再解冻语言模型，视觉侧用更小的学习率。

容易漏的是预算：一张图会变成几十到上千个 token，延迟和上下文要按这个数算。

### 4. ReAct 框架的工程实现细节，消息格式如何设计？tool_response 应该用什么角色传回？为什么？

**参考答案**

ReAct 在工程上是一个有预算的循环：模型只产生思考和工具调用，运行时执行工具，再把结果写回消息列表，直到给出最终答案或触发步数、时间、费用上限。

消息按调用成对出现。assistant 消息带 `tool_calls`：调用 id、工具名、JSON 参数字符串。参数先做 schema 校验再执行。紧跟着一条工具结果，用同一个 id 关联；并行调用就跟多条结果。结果要裁剪，失败写成错误码、原因和是否可重试，不把原始堆栈塞进上下文。

工具结果用独立的 tool 结果，不能写成 assistant。OpenAI 兼容协议里角色就是 `tool`，并带 `tool_call_id`。Anthropic 的接口要求 user 和 assistant 交替，因此把 `tool_result` 放在 user 消息的内容块里，块类型仍然是工具结果并绑定 `tool_use_id`，不是用户又说了一句话。

这样可以同时对上是哪一次调用，训练时只给动作算损失，也避免把工具输出当成用户的新指令。

### 5. Agentic CPT、SFT、RL 三阶段训练流程分别是什么？为什么 SFT 时要 mask observation tokens？

**参考答案**

三阶段是先让模型适应智能体语料，再克隆高质量策略，最后按任务结果优化。三阶段里，环境返回都不是模型要生成的动作。

CPT 在基座上继续做因果语言建模，语料是工具轨迹、API 文档、代码和执行记录。目标是熟悉工具文本和领域写法。observation 又长又噪时就降权，避免模型把主力用在续写环境原文上。

SFT 用「指令、轨迹、最终答案」做行为克隆。标签只留在思考、工具调用和最终回答上；system、user 和 observation 的 label 设为忽略。这些 token 仍留在输入里，模型必须根据真实工具返回往下决策，只是不为它们计算损失。不 mask 的话，长观察会淹没决策 token，模型还会学会编造工具结果。

RL 让策略在环境里采样动作，观察由环境给出。奖励看任务是否完成、格式是否合法，并可惩罚多余调用。PPO、GRPO 或拒绝采样后再训都可以。logprob 同样只落在采样出的动作上。SFT 先把格式和基本策略稳住，RL 的探索才有意义。

### 6. Redis 在 AI Agent 系统中可能有哪些应用场景？如何设计缓存策略？

**参考答案**

Redis 适合放低延迟、可重建、带过期时间的状态，不代替审计库，也不代替大流量的持久事件流。

常见用途：会话和当前轮的运行状态，供崩溃后续跑；`SET key token NX PX` 做同一会话的互斥，释放时用 Lua 校验 token 再删除；令牌桶或滑动窗口做限流和费用预算；工具幂等键缓存「这个副作用已经执行过」的结果；检索、嵌入和用户画像的热缓存。发布取消信号可以用 Pub/Sub，短任务队列可以用 Stream；量大且要回放的事件交给消息队列。

缓存策略按数据分开。会话写 Redis 并设 TTL，异步落库，丢了能从库恢复最近会话。检索缓存的 key 要带上查询、知识库版本、过滤条件、top-k 和模型或提示词版本，知识库更新就升版本。空结果给短 TTL，热点 key 的并发回源合并成一次，TTL 加抖动。实时状态、未确认的写操作，以及权限会变化的内容，不按裸查询去缓存；权限必须进 key。

### 7. MySQL 索引在什么情况下会失效？使用 LIKE 进行模糊查询时索引什么情况下会失效？

**参考答案**

B+Tree 能用，前提是条件能落成对索引列的有序查找。下面这些情况会让优化器放弃范围查找，或直接全表扫描。

在索引列上套函数或计算，例如 `DATE(create_time)`、`amount + 1`，索引用不上。字符串列和数字比较时，MySQL 会转换列上的值，例如 `varchar_col = 123`，索引失效；数字列和数字字符串比较，通常转换的是常量，索引仍可用。联合索引没满足最左前缀时不能按这个索引查找。MySQL 8.0 的 index skip scan 只在最左列取值很少时偶尔出现，不能当成通用能力。`OR` 的一侧没有可用索引时，经常退回全表扫描。`!=`、`NOT IN` 不是语法上一定失效，选择性差时优化器会认为全表扫描更便宜。列和比较值的字符集或排序规则不一致，也会触发转换。

`LIKE` 要看前缀是否是常量。`col LIKE 'abc%'` 可以走范围扫描；`'%abc'`、`'%abc%'` 前缀不固定，不能做范围查找。`'_abc%'` 的首字符也不是常量，同样不行。覆盖索引下，前导模糊仍可能显示 `Using index`，那是扫整段索引，不是定位到少量记录。`LIKE '%词%'` 也不会自动改走全文索引，全文检索要用 `MATCH ... AGAINST`。

### 8. 消息队列在 AI Agent 系统中的作用是什么？为什么不直接通过数据库通信？

**参考答案**

消息队列用来把「接住请求」和「跑完 Agent」拆开。模型调用和工具执行经常是秒级甚至更长，队列负责削峰、异步执行、失败重试和死信，以及把同一次运行的事件扇出给记忆、计费和评测。需要按会话有序时，用会话 id 做分区键。

数据库适合保存任务状态和业务数据。用任务表轮询来通信，会占用连接，延迟取决于轮询间隔，多个消费者还会抢同一批行。Agent 运行时和每个订阅方都打在同一套 OLTP 上，源数据的稳定性会被拖垮。队列提供推送、消费位点、积压指标和按保留期回放，这些不是数据库的长处。

两边要一起用时，采用发件箱：业务写入和待发送事件放在同一个本地事务里，再由投递程序发到队列。这样数据库仍然是状态的来源，队列才是通道，也不会出现业务已经提交、消息却没发出去的裂缝。

### 9. RAG 流程中为什么要引入父子索引？BM25 和向量检索如何融合？

**参考答案**

父子索引解决的是「小块才点得准，大块才答得全」。子块按句或小段做索引和嵌入，命中更集中；父块是所在的段落或页面，保留上下文。检索先拿 top-k 子块，再按 parent id 取回父块，去重后送给模型。同一父块的多个子块会占满名额，所以合并父块后再排序。关联用 parent id 做一次批量读取即可。

BM25 擅长专名、错误码、编号和罕见词，对改写不敏感。向量擅长语义相近的说法，对精确符号弱。两边的分数不在一个量纲上，直接加权需要先归一，权重还要靠评测集调。更稳的基线是倒数排名融合：每个文档的分数是各路排名的 `1 / (k + rank)` 之和，k 常用 60。融合后再用交叉编码器重排前几十条。查询明显是精确符号时，可以提高词项这一路的候选数量。

权限过滤要放在检索条件里。只在提示词里要求模型不要泄露，挡不住召回阶段已经把别人的文档取出来。

### 10. Agent 的记忆机制怎么设计？短期记忆和长期记忆分别如何实现？

**参考答案**

短期记忆保真，服务当前任务；长期记忆压缩后跨会话复用，并且必须能改、能删。两者分开存。

短期记忆是当前会话的原始消息、这一轮的计划和工具结果，再加运行检查点。消息放在带 TTL 的缓存和数据库里，上下文放不下时保留系统提示、未完成计划和最近若干轮，更早的内容交给摘要。检查点记录当前步和尚未完成的工具调用，进程挂了可以续跑。工具原文和展示给用户的话分开，避免把大段观察直接当成对话。

长期记忆分几种：稳定偏好用结构化字段，历史任务用情节摘要，可检索事实用带 embedding 的记录。写入放在回合之后异步做：抽取候选，按用户去重，新事实覆盖旧事实，并记下时间、来源和置信度。读取时按当前问题检索少量记录，连同权限范围一起放进提示词，设长度上限。能从业务库查到的订单和状态，重新查询，不写进记忆。

隔离按用户和租户做。记忆要提供删除和覆盖，模型推断出来的内容和用户明确说过的内容要能区分。

### 11. 上下文超出限制时如何处理？滑动窗口和动态摘要的区别是什么？

**参考答案**

先用与线上模型一致的分词器算预算：留出系统提示、工具定义和回答的位置，剩下的才给历史。超限时先压缩工具输出，再动对话；未闭合的工具调用和结果必须成对保留。

滑动窗口保留系统提示和最近 N 轮或 N 个 token，更早的原始消息直接丢掉。它没有额外的模型调用，保留下来的部分是原文；早期约定、名字和约束会一起消失。

动态摘要在历史超过阈值时，把较老的回合收成一份滚动摘要，上下文里是「摘要 + 最近原文」。早期决策还在，但多一次模型调用，摘要会丢细节，也会写错，所以要增量更新，并允许用业务库或原始日志纠偏。

线上通常把两者合在一起：钉住的规则和结构化任务状态每轮都在，最近几轮用原文，更早的用摘要。单条工具结果本身就超预算时，库里存全文，上下文里只留预览和 id。

### 12. 手写算法：实现反转链表

**参考答案**

用三个指针迭代。`prev` 起初为空，`curr` 从头结点开始。每一步先记下 `curr.next`，再把 `curr.next` 指回 `prev`，然后两个指针前移。结束时 `prev` 就是新头。空链表和单节点不用特殊分支。

时间 O(n)，额外空间 O(1)。递归也能做，栈深 O(n)。题目默认无环；先改 `next` 再保存后继会把链断开。

```python
class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def reverse_list(head: ListNode | None) -> ListNode | None:
    prev = None
    curr = head
    while curr is not None:
        nxt = curr.next
        curr.next = prev
        prev = curr
        curr = nxt
    return prev
```

### 3. 你的 Agent 如果出现死循环怎么办？异常处理机制如何设计？

**参考答案**

循环要靠运行时打断，不能指望模型自己喊停。全局先设最大步数、最大模型调用次数、墙钟时间和费用上限，到了就带着已完成的部分结果结束，并写明停在哪一步。

再检测局部循环。把工具名、规范化后的参数和结果摘要做成哈希，同一调用重复出现若干次就停止；A、B 两种工具来回震荡同样算循环。连续若干步之后，任务状态哈希没有变化，也视为没有进展。

异常按类处理。格式不合法：把校验错误还给模型，限制它自行修正的次数。暂时性的超时、429 和 5xx：指数退避加重试上限，写操作先查状态再决定是否重试。权限不足或对象不存在：停止这一条路，换工具或告诉用户。所有失败都进 trace，回归集收这些坏例。

熔断之后的对外行为要事先定好：返回部分结果、转人工，或明确说这次没有做完。静默再跑一轮会把费用和副作用放大。

### 4. 工具库有上百个工具时，如何让模型快速准确地选择工具？

**参考答案**

把上百个 schema 全塞进提示词，上下文和延迟都扛不住，相似工具也更容易选错。每次调用前只给一小撮候选。

用工具说明做嵌入，按当前用户目标和最新观察检索 top-k，k 一般是个位数到十几个。任务中途目标会变，所以每一步都可以重新检索，而不是第一轮定死。工具很多且领域分明时，先路由到工具组，组内再检索。模型还可以有一个 `search_tools`，第一次没召回到时再查，避免候选集是空的。

检索之前先按用户权限过滤，没有权限的工具不进入候选。工具说明要写清适用和不适用的情况，职责重叠的工具合并。参数仍由 schema 约束，工具名可以用合法集合做约束解码。

评测看两个数：检索的 recall@k，以及最终选对工具并且参数正确的比例。只看对话「看起来完成了」会漏掉选错工具。

### 5. Agent 执行过程中遇到工具调用失败（如支付接口超时）如何处理？

**参考答案**

支付超时的结果是未知：可能已经扣款，也可能对方没收到。这种调用先查状态，确认没有受理之后再重试。

每个付费动作在发起前生成幂等键，支付网关按这个键去重。超时或网络断开时，用幂等键或订单号查询。查到成功就按成功继续；查到明确失败，把错误码、原因和可否重试写成工具结果还给模型；查不到就标记为处理中，延迟再查，并对用户说正在确认。自动重试只用于网关明确表示可以重试的错误，次数和退避要有上限。

同一笔业务如果已经占了库存、却没完成支付，按补偿把库存释放掉。熔断用于网关大面积超时，避免每次都打满超时时间。用户侧只有在拿到成功状态之后才说支付完成。模型自己说「已经付好了」不能当作状态。

### 6. 长上下文对话中，如何让 Agent 不忘记关键信息？除了向量检索还有什么方法？

**参考答案**

关键信息不要和普通闲聊抢同一个窗口。每轮固定注入一块很小的结构化状态：目标、约束、已做决定、待补的槽位、关键实体。这块状态由程序更新，不靠模型在长文里自己翻到。

最近几轮保留原文，更早的对话收成滚动摘要。系统规则、未完成计划和这笔任务的约束钉住，不参与淘汰。人名、单号、地址这类精确字段放进实体表，按字面查找；它们不适合只靠语义相似度。

订单状态、库存、日程以业务库为准，用到时重新查询。向量检索适合跨会话的偏好和旧任务摘要，补的是「库里没有、对话里又太早」的内容。上下文里可以用分隔把检索结果、摘要和用户原话分开，模型改写过的摘要不能覆盖用户刚刚说的话。

### 7. Tree of Thoughts 在线上系统中能用吗？如何平衡成本和效果？

**参考答案**

可以上线，但只能走在少数高价值、难决策的请求上。树搜索会按分支数和深度倍增模型调用，默认路径用它，延迟和费用都会先爆。

请求先经过便宜的路由：简单问答和单次查询走普通的一次生成或 ReAct；规划、有中间评价标准的复杂决策才进入搜索。分支数和深度设小，例如宽度 2 到 3、深度 2 到 3，某一支评分已经够格就停止。能用规则、测试或程序打分的，就不用模型当评委。各支可以并行，这样降的是时延，费用仍然按调用次数涨，所以每个请求还有费用帽，超过就退回单路径。

更划算的用法常常是离线搜索，把好轨迹留成训练或评测数据，线上用单次推理。若只是想要多样结果里挑一个，对若干条独立采样做选择，通常比维护一整棵树更容易控成本。

### 8. 如果 Agent 的决策出错导致数据误删，系统设计上如何防范？

**参考答案**

默认认为模型迟早会发出危险动作，所以删除权限不放在模型侧。生产环境的删除不进默认工具列表；Agent 使用的凭证没有物理删除能力，删除一律是软删除，保留可恢复窗口。

工具按读、写、不可逆分级。不可逆动作先返回影响范围预览，例如将删除哪些对象。用户在界面上确认后，系统签发一次性、短时有效的确认令牌，令牌绑定参数的规范化哈希。模型在确认之后若改了条件，令牌对不上，网关拒绝执行。

网关再检查策略：必须带范围条件、影响行数有上限、租户与当前用户一致。审计记下操作者、参数、确认 id 和时间。备份和恢复流程要能在保留窗口内找回数据。评测集里放诱导删除的用例，看的是网关是否拒绝，而不是模型是否口头答应谨慎。

### 9. 用户提出模糊需求如「按老样子帮我订一下」，Agent 如何处理？

**参考答案**

「老样子」要解析成一次具体的历史订单，再向用户确认，然后才下单。下单和支付是不可逆动作，习惯不能直接当成授权。

优先查业务库里的最近订单和常用订单，其次才用对话记忆。只命中一笔且时间、地址、商品都齐，就把它复述出来：店、内容、时间、数量，问用户是不是这一笔。命中多笔就问一个能区分的问题，或者展示最近的一笔作为默认选项。槽位仍缺时间或人数时，只在置信度高的字段上预填，缺的继续问。

没有历史时，直接说没有可参照的上一笔，并询问要订什么。模型记忆里的「上次好像是」若和订单库冲突，以订单库为准。确认文案里的内容和即将提交的参数必须是同一份，避免用户点头之后又换了一单。

### 10. 如何量化评估一个上线的 Agent 好坏？除了准确率还有哪些指标？

**参考答案**

先按场景定义「做完」：该发生的副作用确实发生，例如订单创建成功，而不是最终回复里出现了「已帮你订好」。准确率只覆盖有标准答案的子集。

线上同时看这些指标。任务成功率按意图切片；工具选对率和参数正确率；多余调用比例。时延看首 token 和端到端的 p50、p95，以及步数。费用看每次成功任务的 token 和外部 API 成本。稳定性看超时、重试、中途放弃和触发循环熔断的比例。安全看越权工具尝试、策略拦截和敏感信息外泄。用户侧看差评、重试同一需求、转人工和任务中途离开。RAG 场景另加引用是否支持回答。

没有自动标签的部分，用抽样人工评测或固定评委模型，并保留一套离线回归集做发布门槛。指标变好要能对应到场景，而不是只看一个总准确率。

### 11. Kafka 在 AI Agent 系统中可能用于哪些场景？如何保证消息顺序性？

**参考答案**

Kafka 适合做可回放的事件流：每一步模型输出、工具调用和工具结果；把在线链路和评测、计费、会话索引拆开；慢工具的任务分发；RAG 文档的入库流；以及「订单已创建」这类再触发后续 Agent 的领域事件。短生命周期的会话锁和热点缓存仍放 Redis。

顺序只在同一个分区内成立。需要按会话或单次运行有序时，用 session id 或 run id 做消息键，同一键会进同一分区。未开启生产者幂等时，同一连接上允许多个未确认请求，重试可能让后发的消息先写入；开启幂等后，分区内有序列号，重试不会把顺序打乱。

消费组里一个分区同时只给一个消费者。要保住顺序，就按拿到的顺序处理完再提交位移；在分区内再并发执行，顺序就没了。跨键可以并行。处理失败若要跳过当前消息继续向后，后面的消息会先生效，严格顺序就按键阻塞或把这个键单独重试。消费侧按至少一次来设计，处理函数用幂等键挡住重复投递。全局只设一个分区能得到全主题顺序，吞吐也会被这个分区封顶，一般只保证需要顺序的那个键。

### 12. Elasticsearch 在 RAG 系统中的作用是什么？如何优化检索性能？

**参考答案**

Elasticsearch 在 RAG 里承担词项检索和过滤：BM25 倒排索引负责关键词，`keyword` 字段负责租户、权限、时间和文档类型，`dense_vector` 可以同时做向量近邻。这样混合检索和权限过滤能在一次查询里完成。返回内容要带上片段和来源，供引用。

优化从映射开始。过滤字段用 keyword，全文按语言选分析器，中文不要直接靠默认分词。查询侧先按权限和业务条件过滤，再做 BM25 与 knn，两路候选用 RRF 合并，前几十条交给交叉编码器。knn 的 `num_candidates` 要大于 k，过滤很严时再加大，否则近似近邻的候选被滤掉后会不够。

索引侧用批量写入。初始化灌库时可以把刷新间隔调大，默认大约 1 秒的刷新会让写入放大。分片按数据量规划，常见量级是数十 GB 一个分片，分片过多会增加集群开销。按租户路由可以让查询打到更少的分片。返回时只取正文和引用所需字段。深分页用 `search_after`。权限条件必须在查询里，不能只依赖模型。

### 13. 手写算法：计算二叉树最大宽度

**参考答案**

宽度按 LeetCode 662 的定义：同一层最左、最右非空节点的下标差加 1，中间空位算进去。只统计节点个数会把空位漏掉。

根下标为 0，父节点 i 的左子是 `2i`，右子是 `2i+1`。层序遍历时记录每个节点的下标，该层宽度是最右减最左再加 1。偏树的原始下标会到 `2^n`，所以传给子节点之前先减去本层最左下标。时间 O(n)，队列空间 O(n)。空树宽度是 0。

```python
from collections import deque

class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

def max_width(root: TreeNode | None) -> int:
    if root is None:
        return 0
    queue = deque([(root, 0)])
    best = 0
    while queue:
        left = queue[0][1]
        right = left
        for _ in range(len(queue)):
            node, idx = queue.popleft()
            right = idx
            base = idx - left
            if node.left is not None:
                queue.append((node.left, base * 2))
            if node.right is not None:
                queue.append((node.right, base * 2 + 1))
        best = max(best, right - left + 1)
    return best
```

### 2. 从架构角度分析 Tools、Workflow 和 Agent 三者的本质区别

**参考答案**

三者的差别在于控制流由谁决定，以及失败了能不能复现。

Tool 是一个带 schema 的能力，搜索、下单或查库都算。它本身不决定下一步，调用方传入参数，它返回结果或副作用。Workflow 的步骤和分支是开发时写好的，模型可以是其中某个节点，负责分类、抽取或生成，路径仍由程序控制，容易测试和回放。Agent 在运行时根据当前观察选择下一个工具或是否结束，路径枚举不全，能覆盖开放任务，也带来步数、费用和结果的不确定性。

架构上三者是组合关系：Tool 是叶子，Workflow 把模型和工具编排成确定过程，Agent 是「下一步由模型选择」的那种编排。线上常见的做法是骨架用 Workflow，只有无法穷举的那一段用 Agent，并且 Agent 能调用的工具是收过权限的。

确定性、可测试性从 Tool 到 Workflow 再到 Agent 递减，长尾任务的覆盖则递增。能写死的流程，就把控制流留在程序里。

### 3. Multi-Agent 系统如何设计三层架构？Agent 之间如何通信？

**参考答案**

可以分成编排层、专职 Agent 层和共享能力层。

编排层面对用户，负责鉴权、会话、全局步数和费用、最终回复。它持有任务状态，决定把哪一段交给哪个专职 Agent。专职 Agent 各有各的提示词、工具子集和停止条件，例如检索、执行、校验，互不继承对方的权限。共享能力层提供模型网关、工具、RAG、记忆、沙箱和策略引擎，不在这一层做业务决策。

通信默认用「把另一个 Agent 当成工具」：编排者传入目标、约束和必要材料，对方返回约定好的结构。上下文传任务简报，不把全部思考过程转发给所有人。步骤之间要交接明确状态时，用类型化的共享状态，每个字段只有一个写入者。长任务走队列，消息带 task id 和 correlation id，按任务键保证顺序。

群聊式的自由发言很难限制轮数。终止条件、预算和冲突以编排层为准，专职 Agent 不互相覆盖对方的结论。整条链路共用一个 trace id。

### 4. 当前阻碍 Agent 大规模落地的最大挑战是什么？如何解决可控性和能力的平衡问题？

**参考答案**

最大的障碍是长程任务的可靠性：每一步的小错误会叠到最终副作用上，同时费用、延迟和权限都有硬约束。模型分数上去了，也不等于可以在生产里连续做完一百步。

可控性和能力是权限边界的问题，不是把自主性开关打开或关上。能力放在边界内增长：更好的检索、更清楚的工具 schema、对可验证结果做强化学习，都让决策变好，同时工具集合不变。边界本身用机制卡住：工具白名单和类型约束、已知路径走工作流、高风险动作由人确认、步数和费用有上限、写操作先预览再执行。

什么时候扩大权限，由这个场景的成功率和事故率决定。没有回归集和拦截指标之前，扩大工具权限只会让演示更好看、事故更难查。企业侧还要面对接口不稳定和缺少过程标签，这些会限制能自动判定对错的范围。

### 5. MCP、A2A、Skills 和 Function Call 分别是什么？它们之间有什么区别？

**参考答案**

四者处在不同层，可以叠在一起用。

Function Call 是模型的输出协议：模型给出工具名和 JSON 参数，应用执行后把结果送回。schema 随这次请求传入，它不负责跨进程的发现和鉴权。

MCP 是模型和工具服务器之间的协议。宿主通过它发现并调用远端的 tools，也可以读 resources、取 prompts。本地常用 stdio，远程用 HTTP。模型仍然通过 Function Call 表达「我要调某个工具」，宿主再把这次调用路由到 MCP server。

A2A 是 Agent 和 Agent 之间的协议。Agent 用 Agent Card 公布能力、地址和鉴权，然后交换任务、消息和产物，适合跨框架或跨团队委托。它不替代 MCP：一个 Agent 用 MCP 访问工具，用 A2A 把子任务交给另一个 Agent。

Skills 是按需加载的能力包，常见形式是一份带触发描述的说明，加上脚本和材料。宿主先看描述决定是否启用，启用时才把正文放进上下文。它教的是一套做法，不是一次远程函数调用，也不是传输协议。

### 6. Agent 的上下文工程有哪些主流技术？如何设计有效的上下文管理策略？

**参考答案**

上下文工程管的是这一次模型调用能看见什么。常用手段有：稳定的系统说明和工具定义；按问题挑选记忆、文档和工具，而不是全量塞入；把旧对话做成摘要，把工具结果裁到后续步骤真正用到的字段；用子任务或专职 Agent 隔离上下文，避免一份巨大历史服务所有步骤；把任务状态放在程序里，每轮小块注入。

策略上先分预算。系统说明和工具定义保持稳定，放在前缀，便于提示词缓存；其后是结构化状态、检索证据，最近的用户目标靠后。无信任的网页和工具输出用明确边界包起来，和系统说明分开。历史超限时先裁工具输出，再摘要旧对话，工具调用和结果成对保留。

有效性用消融来判断：拿掉某一块之后，场景成功率没有变化，这块就是噪音。提示词和裁剪规则要有版本，跟回归集一起发布。只增加「请仔细阅读以上全部内容」这类句子，不会让过长的上下文变得可用。

### 7. 在团队中如何推动 AI Agent 项目的技术选型和架构演进？

**答题思路**

按「先对齐约束，再用同一套证据做决定」来讲，选择一个你真实参与过的选型：

1. 把场景、延迟、费用、权限和可回滚写成共同约束，同时写清怎样算上线成功。
2. 选型标准事先说好：可控性、可观测、团队能否维护、替换成本。演示效果只是其中一项。
3. 用同一评测集做小范围对比，必要时加影子流量。你负责把结果整理成可复核的记录，包括放弃某个方案的原因。
4. 演进时新链路灰度，旧流程保留回退。用垂直切片替换，避免停下来重写。
5. 决策和复盘点记下来，三个月后按当时的指标检查，而不是重新争论一遍。

强调你自己承担的那一段落地，以及你如何把反对意见写进风险和兜底。

### 8. 当团队成员对技术方案有分歧时，你如何沟通并达成共识？

**答题思路**

用一次真实分歧来讲，按下面的顺序，不把对方说成「不懂」：

1. 先分开三类分歧：目标不同、事实不同，还是风险偏好不同。三种的处理不一样。
2. 把非协商项摆出来，例如安全要求、工期和必须保住的指标。
3. 事实问题用一次最小实验或同一套评测解决，并约定看哪个数、什么时候停。
4. 实验做不完又必须推进时，由负责人在期限前拍板，同时写明反对意见对应的监控和回退。
5. 结论同步到文档里，接口和责任跟着改，避免会上统一、会下各做各的。

最后补一句你后来的验证：当时的担心有没有发生，指标说明了什么。

### 9. 如何保证复杂 AI Agent 项目的开发进度和质量？

**答题思路**

讲你真正用过的拆法和门槛，数字用你项目里的：

1. 按用户能走通的垂直切片排期，每一片包含工具、失败处理和验收，而不是先做完一个空平台。
2. 模型能力不确定的部分先做时间盒内的验证，再放进关键路径。
3. 质量门槛放在发布前：工具契约测试、离线回归集、trace 抽检、可回滚。回归集没过就留在这一片。
4. 进度看「通过的场景数」和线上事故，同时看剩余风险，而不是只看人天。
5. 延期时先砍并发场景，保住主路径、评测和回滚。主路径的验收标准不跟着范围一起降。

补一个你做过的取舍：哪次你砍了范围，结果如何。

### 10. 最近在学习和研究哪些 AI 相关的新技术或论文？

**答题思路**

只讲一篇你真读过、能回答追问的论文或一个你真用过的系统。按四段说：

1. 它要解决的具体问题，以及现有做法哪里不够。
2. 方法里真正起作用的机制，用你自己的话讲清楚，能写到关键步骤。
3. 实验或实现的限制：数据、成本和失败情况。
4. 它和你正在做的系统哪里接得上；现在接不上的话，缺的是哪一个条件。

方向可以是上下文压缩、工具使用的强化学习、Agent 评测或工具协议，选你读过原文或读过代码的那个。面试官会追问实验设置和你不同意的点。只看过标题的工作不要放进名单。

### 11. 你是如何系统性地学习一门新技术的？会关注哪些资源？

**答题思路**

用一门你最近学过的技术当例子，按实际顺序讲：

1. 先做一个最小闭环，把它接到你熟悉的系统上，记下第一个跑不通的点。
2. 再回头补原理，对着官方文档、发行说明和原始论文看，博客用来找线索，结论回到原文核对。
3. 沿着源码看一条关键路径，例如一次工具调用从协议到执行的过程。
4. 用输出检验：一段能运行的代码，或一页写给同事的说明，里面包括失败模式和你不会采用它的情况。
5. 资源按这个优先级：官方文档和变更说明、论文、可运行的源码、自己的坏例。榜单数字要看到评测设置再引用。

最后说你如何保持更新：固定少量来源，并用一个小实验判断它是否影响你现在的系统。

### 12. 对于 AI Agent 领域的未来发展，你有什么看法和规划？

**答题思路**

看法和规划分开讲，看法要有边界，规划要落到你自己的工作。

看法可以组织成三句。近一两年先规模化的是窄场景：工具可靠、结果可评测、高风险动作有人确认。瓶颈会更多出现在接口、上下文、评测和权限，而不是单次对话的流畅度。架构上，确定流程会继续兜住主路径，模型负责长尾，模型本身应能替换。

规划按时间说，职级数字不必报：

1. 近一两年把一个真实场景的成功率和成本做稳，包括评测、故障和回滚。
2. 接下来能负责一条链路的编排和评测，判断哪些步骤不该交给模型。
3. 学习上跟一个你真会用到的方向，例如工具协议或可验证奖励，并说它如何服务于上面的场景。

用「这个判断基于你做过的哪件事」收尾，避免只背趋势。

### 13. 手写算法：LeetCode 22 题，生成括号组合

**参考答案**

给定 n 对括号，生成所有合法组合。合法指任意前缀里右括号不多于左括号，且最终两者都是 n。

回溯时记录已经放入的左右括号数。左括号少于 n 就可以放左括号；右括号少于左括号就可以放右括号。长度到 `2n` 时收集一个答案。这个剪枝只生成合法序列，数量是第 n 个卡特兰数。时间与 `4^n / sqrt(n)` 同阶，若计入把路径拷贝成字符串，还要再乘 O(n)。递归栈空间 O(n)，不计输出。

先生成全部左右排列再过滤也能得到答案，中间状态会多很多。

```python
def generate_parenthesis(n: int) -> list[str]:
    ans: list[str] = []
    path: list[str] = []

    def dfs(opened: int, closed: int) -> None:
        if len(path) == 2 * n:
            ans.append("".join(path))
            return
        if opened < n:
            path.append("(")
            dfs(opened + 1, closed)
            path.pop()
        if closed < opened:
            path.append(")")
            dfs(opened, closed + 1)
            path.pop()

    dfs(0, 0)
    return ans
```

## HR面

### 1. 自我介绍

**答题思路**

HR 这轮用 1 分钟，少用框架名词：

1. 你是谁：年限和目前做的业务问题。
2. 一件做成过的事：用业务语言说清问题、你的作用和结果。
3. 为什么这次看机会：想在真实用户场景里把 Agent 做稳。
4. 停住，把时间留给对方。

项目名和数字只用真实的。技术架构留给技术面，这里证明你能把事情讲清楚。

### 2. 为什么选择字节跳动？为什么对 AI Agent 方向感兴趣？

**答题思路**

分成两问，每一问都落到你的经历，大约各 30 秒：

1. **为什么是这家**：你看重的是有真实用户、工具和约束的场景，以及工程标准。选一个你确实了解的产品或问题，说明你想验证什么。避免只说平台大、发展好。
2. **为什么是这个方向**：你已有的后端或业务经验用在工具、状态和稳定性上；模型会换，这条工程能力还能积累。用你已经做过的一个模块作为证据。
3. 两句之间要接得上：这家有场景，你有对应的准备，所以是现在这轮机会。

动机讲完即可，把薪资和职级留到对方问的时候。

### 3. 你对自己未来 3-5 年的职业规划是什么？

**答题思路**

规划沿技术主线说，和你应聘的工作接上：

1. 前一两年：独立把一个 Agent 场景从能跑做到可运营，含评测、成本和故障处理。
2. 中期：能对一条业务链路的方案负责，带小范围的技术决定，并说清哪些流程不该交给模型。
3. 再往后：在这个方向上判断优先级，继续写关键路径上的设计和代码。
4. 补一句你希望团队提供的条件，例如真实流量和明确的质量标准。

把规划说成「升到某级」或「转去纯管理」都和这轮岗位对不上。还没想清的部分，说你准备用哪类项目来验证。

### 4. 在之前的工作中遇到最大的挑战是什么？如何解决的？

**答题思路**

选一个真实的、有不确定性和取舍的难题，用 STAR 讲完控制在 2 分钟：

1. **背景**：一句说清业务约束，例如结果不能错、时间紧、接口不可靠。
2. **责任**：你个人要交付什么，和团队目标分开。
3. **行动**：两到三个你自己做的动作，包括你放弃的办法。
4. **结果**：用真实数字；没有数字就说行为变化，例如事故是否复发、发布是否可回滚。
5. **反思**：如果再来一次，你会更早做哪一步。

挑战本身体现判断。把「加班很多」或「和别人意见不合」当成挑战时，要能讲出你改变了哪一个机制。

### 5. 你期望的团队氛围和工作方式是怎样的？

**答题思路**

先说你能适应并愿意维护的协作方式，再举一个短例子：

1. 目标和方法可以争论，争论时对着约束和指标。
2. 决定有记录，接口有约定，线上问题追到具体链路。
3. 你习惯把方案、风险和回退写出来再评审，评审后按结论执行。
4. 例子用一次你在这种协作里提前暴露风险、最后按约定交付的经历。

期望说完，补一句你也会配合关键发布的集中投入。对前公司的评价停在事实，不用来对比衬托。

### 6. 如何看待工作与生活的平衡？

**答题思路**

给出你真实的节奏，以及你如何保证交付：

1. 你认可上线和故障期间集中投入，也认为长期产出依赖可维持的节奏。
2. 具体做法：需求前期把风险和评测做在前面，减少上线后救火；工作时有完整的深度工作时间。
3. 如果有固定的个人时间约束，直接说边界，同时说明你怎么补齐协作，例如核心时段在线、紧急事故有响应方式。
4. 用一次发布说明你能扛住高峰，也能在高峰之后恢复节奏。

把「随时都可以」和「完全不加班」都说满，后面的工作安排会对不上。按你的真实边界讲。

### 7. 你目前的薪资期望是多少？

**答题思路**

谈总包，并留出确认职级的空间：

1. 先确认职级、城市和职责。总包包含月薪、奖金或年终、股票，单独报一个月薪会对不齐。
2. 给出一个区间。下限是你经过考虑能接受的总包，上限参考这个级别的市场位置和你现在的总包。具体数字只用你自己核算过的。
3. 若对方还没说明带宽，可以先问带宽和结构，再把区间落进去。
4. 说明你看重事情和职级是否匹配，同时把期望说清楚，方便对方判断。

还没想好具体数字时，不要在现场编一个。可以说你按总包结构核算后再确认，并给出你已经确定的原则。

### 8. 有什么问题想问我吗？

**答题思路**

准备两个你确实关心、对方也答得了的问题，听完再追问一句：

1. 这个岗位前半年做成的标志是什么？Agent 目前落在哪类业务场景？
2. 团队怎样划分模型、编排和业务工具的责任？现在质量上最大的缺口是什么？

若职级或总包结构还没谈清，可以单独问评估方式和总包构成。把加班、假期放在前面，信息量比上面两个问题少；如果这是你的硬约束，放在业务问题之后诚实地问。对方已经讲过的内容不要再问一遍。
