### 3. Go 里 slice 和 array 的区别，slice 扩容规则是什么

**参考答案**

结论：array 的长度属于类型，是一整块值；slice 是指向底层数组的描述符。`append` 之后的长度超过 cap，才会换一块新数组并把旧元素拷过去。

`[3]int` 和 `[4]int` 是不同类型。数组赋值、传参会拷贝全部元素，元素类型可比较时数组也可以比较。slice 的头是指针、len、cap，传参拷贝的是头。没换底层数组时，改元素对所有共享它的 slice 都可见。slice 可以为 nil，len 和 cap 都是 0，`append` 仍可用。子切片 `s[i:j]` 共享数组；`s[i:j:k]` 把 cap 限到 `k-i`，避免 `append` 写进原数组后面的元素。调用方要接住 `append` 的返回值，否则自己的头仍指向旧数组。

扩容时先算一个新容量。新的 len 已经大于旧 cap 的两倍时，新 cap 至少取到这个 len。否则从 Go 1.18 起：旧 cap 小于 256 时翻倍；达到 256 后用 `newcap += (newcap + 3*256) / 4`，从 2 倍平滑过渡到大约 1.25 倍。1.18 之前的门槛是 1024，达到后大约按 1.25 倍涨。算出的字节数还会按内存分配器的 size class 向上取整，所以看到的 cap 经常更大，并且和元素大小有关。

### 4. Go 的 GMP 调度模型讲一下，P 的作用是什么

**参考答案**

结论：G 是 goroutine，M 是操作系统线程，P 是逻辑处理器。M 必须持有 P 才能执行 Go 代码。P 的数量等于 `GOMAXPROCS`，用来限制并行度。

P 上有本地运行队列和分配小对象用的 mcache，调度和大部分堆分配因此不用抢全局锁。新建或唤醒的 G 优先放本地队列，放不下再批量挪到全局队列。本地空了，就从全局队列取，或从别的 P 偷一批。大约每 61 个时间片会先看一眼全局队列，避免堆在那里的 G 饿死。

网络等待只把这个 G 挂到 netpoller，M 继续跑别的 G。G 进入阻塞系统调用时，M 和 P 拆开，P 交给别的 M，这次调用就不会占住一个并行名额。运行大约超过 10ms 的 G 会被抢占。容器里如果按宿主机核数取 `GOMAXPROCS`，会超过 cgroup 限额，应按限额来设。

### 5. channel 有缓冲和无缓冲区别，select 搭配 channel 做超时控制怎么写

**参考答案**

结论：无缓冲 channel 的发送和接收必须碰面，数据从发送方直接拷到接收方。有缓冲 channel 在缓冲没满时发送不阻塞，缓冲不空时接收不阻塞。

超时要让发送方在对方已经离开后仍能退出，所以结果 channel 用容量 1。`select` 同时等结果和定时器。超时后工作函数如果还在跑，要靠 `context` 通知它停，`select` 只是停止等待。

```go
type result struct {
    v   string
    err error
}

func call(parent context.Context, d time.Duration) (string, error) {
    ctx, cancel := context.WithTimeout(parent, d)
    defer cancel()

    ch := make(chan result, 1)
    go func() {
        v, err := work(ctx)
        ch <- result{v, err} // 容量为 1，调用方离开后也不会堵在发送上
    }()

    select {
    case r := <-ch:
        return r.v, r.err
    case <-ctx.Done():
        return "", ctx.Err()
    }
}
```

无缓冲时，超时之后发送会永远堵着，这个 goroutine 就泄漏了。循环里少用 `time.After`：Go 1.23 之前，定时器要等到触发才能回收；1.23 起没有人引用的定时器可以被 GC。仍建议 `time.NewTimer` 配合 `Stop`，并把取消传进 `work`。`work` 不看 `ctx` 的话，协程要等它自己返回才结束。

### 6. Go 里 defer 的执行顺序，defer 修改返回值要注意什么

**参考答案**

结论：多个 defer 按注册的逆序执行，发生在 `return` 把结果写好之后、函数真正回到调用方之前。defer 后面的参数在注册时就求值，函数体延后执行。

```go
func inc() (n int) {
    defer func() { n++ }()
    return 1 // 先把 n 设为 1，再执行 defer，调用方得到 2
}
```

返回值有名字时，defer 改的就是这份结果。返回值没有名字时，`return x` 已经把值拷进临时结果，defer 里再改局部变量，调用方看不到。

循环里的 defer 要等整个函数结束才跑，文件和锁会攒下来。每一轮包进一个内层函数，defer 就在这一轮结束时执行。发生 panic 时，已经注册的 defer 仍会跑；`recover` 要直接写在 defer 函数里才接得住这次 panic。

### 7. Go 的 GC 用的三色标记法，简单说下流程，STW 出现在哪

**参考答案**

结论：Go 的 GC 是并发、精确、不分代、不整理的三色标记清除。白色没访问过，灰色已经可达但子指针还没扫完，黑色的子指针已经扫完。标记结束仍是白色的对象会被回收。

流程是：从栈、全局变量这些根把可达对象涂灰，再把灰色对象的指针扫完并涂黑。标记期间混合写屏障会把被覆盖的旧指针和新写入的指针都标灰，新分配的对象直接标黑。栈扫过一次就当黑色，收尾时不用再全量扫栈。分配太快、后台标记跟不上时，业务 goroutine 会协助标记。清扫是并发的，分配时也会顺手扫。

STW 有两处，都短。第一次在标记开始：打开写屏障，准备根扫描；上一轮清扫如果没做完，也在这次停顿里收尾。第二次在标记收尾：确认没有灰色对象，关闭写屏障，再进入并发清扫。Go 1.26 起默认的 Green Tea 仍是这套三色和这两次停顿，变化是把同一页上待扫的小对象攒在一起扫。

### 8. 内存逃逸是什么，什么情况变量会逃到堆

**参考答案**

结论：逃逸是编译器无法证明变量在函数返回后就没有引用，于是把它分配在堆上，交给 GC。能留在栈上的对象随函数返回释放。

常见情况：

- 返回局部变量的指针，或把它存进堆上的结构、slice、map、全局变量。
- 把指针发进 channel，别的 goroutine 可能在函数返回后继续用。
- 闭包在函数返回后仍会执行，它捕获的变量一起逃。
- 传给 interface 参数，编译器看不到对方会不会保存。`fmt.Println` 经常让参数逃逸。
- `make` 的长度要运行时才知道，底层数组通常在堆上。编译期能确定、足够小、又没有逃出函数的，可以留在栈上。

用 `go build -gcflags=-m` 看判断。编译器拿不准就放堆。热路径上意外逃逸会抬高分配次数和 GC 时间。

### 9. TCP 三次握手四次挥手，TIME_WAIT 状态存在的意义

**参考答案**

结论：三次握手是双方交换并确认初始序号。四次挥手是双方分别关闭自己的发送方向。TIME_WAIT 在主动关闭的一方停留 2MSL，Linux 上常见是 60 秒。

握手：客户端发 SYN（seq=x）进入 SYN_SENT；服务端回 SYN+ACK（seq=y，ack=x+1）进入 SYN_RCVD；客户端再 ACK（ack=y+1），双方进入 ESTABLISHED。服务端要收到第三次 ACK，才知道自己的序号被对方收下。旧的重复 SYN 也不会仅凭一次往返就把服务端带进已建立连接。

挥手：主动方发 FIN 进入 FIN_WAIT_1；被动方 ACK 后进入 CLOSE_WAIT，主动方进入 FIN_WAIT_2，被动方这时还可以把剩余数据发完；被动方再发 FIN 进入 LAST_ACK；主动方 ACK 后进入 TIME_WAIT，被动方收到 ACK 进入 CLOSED。被动方没有剩余数据时，ACK 和 FIN 可以合在一个报文里，抓包有时是三包，状态仍是这一套。

TIME_WAIT 做两件事。最后的 ACK 丢了，被动方会重发 FIN，主动方还能再回 ACK。同时等旧连接的迟到报文从网络里消失，新的同四元组连接不会把它们当成新数据。服务端如果先关连接，TIME_WAIT 就堆在服务端。

### 10. HTTP 和 HTTPS 区别，HTTPS 握手过程

**参考答案**

结论：HTTP 的报文直接放在连接上。HTTPS 是 HTTP 跑在 TLS 里，多了机密性、完整性和服务端身份。常见端口是 80 和 443。身份靠证书，不是靠“流量被加密”本身。

TCP 连上之后做 TLS。现在默认的 TLS 1.3 是一轮往返：

1. ClientHello 带上支持的版本、密码套件、SNI、ALPN，以及 key_share 里的 ECDHE 公钥。
2. ServerHello 选定版本、套件和自己的 key_share。随后的证书、CertificateVerify 和 Finished 已经加密。CertificateVerify 证明服务端持有证书私钥。
3. 客户端校验证书链、有效期和域名（对 SAN），再回 Finished。之后用派生出的应用层密钥传 HTTP。

会话恢复可以用 PSK。0-RTT 的 early data 可能被重放，只适合幂等请求。TLS 1.2 是两轮：证书和密钥交换参数先明文协商，客户端再发密钥交换和 Finished。浏览器里的 HTTP/2 通过 ALPN 谈在 TLS 上。握手成本靠连接复用摊薄。

### 11. Redis 常用数据结构，zset 底层跳表大概讲一下

**参考答案**

结论：常用的是 String、List、Hash、Set、ZSet，分别适合缓存或计数、队列、对象、去重、按分值排序。ZSet 小时用紧凑编码，大了用跳表加哈希表。

String 可以是整数或字符串。List、Hash、Set、ZSet 在元素少、成员短时用 listpack 一类紧凑结构，超过阈值再转成哈希表或跳表。Redis 7 之前 ZSet 的小编码是 ziplist。官方默认是成员数 128、单个成员 64 字节，超过就升级。

大 ZSet 同时有两份结构。跳表按分值排序，节点带成员、分值和多层前进指针；层高以 1/4 的概率往上加，最高 32 层，查找和插入是 O(log N)。最底层双向链接，可以倒序扫。指针上的 span 用来 O(log N) 计算排名。哈希表是成员到分值，`ZSCORE` 为 O(1)。分值相同再按成员字典序排。范围查询先定位起点，再沿底层链表取。

### 12. Redis 持久化 RDB 和 AOF 区别，生产怎么选

**参考答案**

结论：RDB 是某个时间点的快照，AOF 是追加写命令。能从数据库重建的缓存可以只留 RDB 甚至关掉持久化；要少丢数据就用 AOF 的 everysec，并用 RDB 或带 RDB 头的 AOF 做备份。

RDB 由子进程写出，文件小、加载快。两次快照之间的写入会丢。实例大、写入多时，fork 的写时复制会抬高内存和延迟。

AOF 记录写命令。`always` 每次都 fsync，最不容易丢，也最慢；`everysec` 崩溃时大约丢掉一秒内的写入，是常见选择；`no` 交给操作系统决定何时刷盘。文件大了会重写。Redis 4.0 起，重写文件可以前面放 RDB、后面接增量命令，加载更快。

主从复制是异步的，新主未必有旧主最后那些写，所以复制代替不了本机持久化。缓存和数据库的关系如果本来就是可重建的，持久化级别按能接受的丢失窗口来定。

### 13. MySQL 为什么用 B+ 树不用 B 树，聚簇和非聚簇索引区别

**参考答案**

结论：InnoDB 用 B+ 树。数据都在叶子，内部节点只放键，一页里能放更多键，树更矮；叶子之间有链表，范围扫描顺着叶子走。经典 B 树的内部节点也放数据，同样大的页能放的键更少，范围查询要在树里来回。InnoDB 页默认 16KB。

聚簇索引的叶子是整行，表按这个索引组织。二级索引的叶子存的是主键，要整行时再按主键回表。查询列都在二级索引里时是覆盖索引，不用回表。回表是按主键再查一次，行很散时优化器可能放弃这个索引。

没有主键时，InnoDB 选第一个全列非空的唯一索引做聚簇索引；再没有就生成隐藏的 row_id。MyISAM 的索引叶子是数据文件里的位置，数据和索引分开，属于非聚簇。说聚簇、回表时默认指 InnoDB。

### 14. 联合索引最左匹配原则，什么情况索引会失效

**参考答案**

结论：联合索引 `(a, b, c)` 按从左到右的顺序组织。等值前缀能用来定位：`a`、`a+b`、`a+b+c`。范围条件右边的列不再缩小扫描起点。

`a = 1 AND b > 2 AND c = 3` 能用 `a` 和 `b` 定位，`c` 只在扫描时过滤。没有 `a` 时，普通查找不能从 `b` 开始。MySQL 8.0 的 Index Skip Scan 是例外：被跳过的前缀列基数很低时，优化器可能仍走这棵索引。

“失效”指这棵索引不能用来定位，或优化器放弃它。列上套函数、做计算，会对列转换，例如 `DATE(t) = '2024-01-01'`。字符串列和数字比较，也会转换列。`LIKE '%abc'` 不能用索引定位，`abc%` 可以。`OR` 里有一侧没有可用索引时，常常退回扫描；两侧各自有索引时，可能走 index merge。选择性很差或统计信息过期时，优化器会改选全表扫描，索引本身还在。`!=`、`IS NULL` 并不一律不能用索引。

### 15. 用 AI 辅助写 Go 代码时你怎么用，会不会 review 它生成的并发代码

**答题思路**

先给结论：会 review，并发结构和退出条件自己定，再让 AI 填实现。

1. 说清真实用法：样板、表驱动测试、不熟悉的标准库可以让它起草。锁、channel 归谁、goroutine 如何退出，由自己写进约束。
2. 按生成结果核对：每个 goroutine 在 ctx 取消后，发送和接收都能返回；channel 由谁关闭，关闭后还会不会发送。
3. 持锁期间不做 channel 收发和 RPC。多把锁在所有路径上的顺序一致。共享变量要么在锁内，要么用原子操作。
4. 看 `go.mod` 的 Go 版本。1.22 起每次迭代有自己的循环变量；更早的版本里，闭包捕获的是同一个变量。
5. 错误要处理。外面 `select` 到了超时，下游调用也要带同一个 ctx。
6. 用 `go test -race` 和能失败的用例验证。生成结果先当待审核补丁，跑过再提交。

### 16. 给定 n 对括号，生成所有合法括号组合（力扣 22）

**参考答案**

结论：用回溯。任意前缀里右括号不超过左括号，最终两者都等于 n。合法组合的个数是第 n 个卡塔兰数，时间复杂度约为 O(4^n / √n)。递归深度 O(n)，输出要存下全部字符串。

长度为 2n 时收下当前串。左括号少于 n 就可以再放左括号；右括号少于左括号才放右括号。路径用一块长度上限 2n 的缓冲，返回时 `string` 会拷贝一份，回溯不影响已经收下的答案。题目范围一般是 1 到 8，可以全部生成。

```go
func generateParenthesis(n int) []string {
    res := make([]string, 0)
    path := make([]byte, 0, 2*n)
    var dfs func(open, close int)
    dfs = func(open, close int) {
        if open == n && close == n {
            res = append(res, string(path))
            return
        }
        if open < n {
            path = append(path, '(')
            dfs(open+1, close)
            path = path[:len(path)-1]
        }
        if close < open {
            path = append(path, ')')
            dfs(open, close+1)
            path = path[:len(path)-1]
        }
    }
    dfs(0, 0)
    return res
}
```

### 3. 项目里用 Redis 做缓存，缓存和数据库一致性怎么保证，延迟双删和 binlog 监听方案说下

**参考答案**

结论：旁路缓存的写路径是先提交数据库，再删缓存。延迟双删和 binlog 监听都是在补“旧值又被填回缓存”的窗口，窗口还在，所以要有 TTL，读自己的写要有单独办法。

读的时候先看缓存，没有再查库并回填。写的时候更新库再删缓存。两个写并发时，后完成的“更新缓存”可能把旧值写回去；删除则让下一次读回填新值。仍有一个小窗口：读请求已经拿到旧行，写请求提交并删了缓存，读请求再把旧值 set 回去。

延迟双删的经典步骤是先删缓存、更新数据库、等待一段时间、再删一次。它想清掉等待期间被填回去的旧值。等待要盖住这次回填，有主从延迟时还要盖住复制。慢请求落在第二次删除之后，旧值仍会留下。这个等待没有稳妥的固定值。

binlog 方案用 Canal 一类组件订阅行格式 binlog，事务提交后按主键删缓存。消费是幂等的，失败要重试。不一致窗口变成消费延迟。回填时带上版本（更新时间或位点），旧版本不能覆盖新版本，晚到的旧值就写不进去。删失败和没消费到的情况靠 TTL 兜底。

面试时按自己项目里真实在跑的路径讲，另一条作为对比。需要本请求立刻读到刚写的值时，读主库或直接返回这次写入的结果。binlog 删缓存是异步的，这段时间里缓存可能还是旧值。

### 4. 缓存穿透、击穿、雪崩分别是什么，你们项目怎么防

**参考答案**

结论：穿透是查一定不在缓存里的 key，击穿是一个热点 key 失效的瞬间，雪崩是大批 key 一起失效或缓存整体不可用。

穿透时 key 在数据库里也不存在，缓存不命中，请求都打到库。入口先校验参数。布隆过滤器挡住确定不存在的 key，它有误判，放行的再查库；删除数据后普通布隆不能删成员，所以仍要缓存空值并给较短 TTL。

击穿是热点 key 过期，大量请求同时回源。用 `singleflight` 或互斥锁把重建合成一次。也可以逻辑过期：值里放过期时间，过期后先返回旧值，只放一个请求去刷新。

雪崩是很多 key 在同一时刻过期，或者 Redis 宕机，数据库被打满。TTL 加随机抖动，缓存做主从或集群，应用侧可以有小容量本地缓存。数据库前面要有限流和降级，冷启动时先预热热点。

落到项目上，只讲真正做过的那几层，以及缓存挂了请求会怎样。

### 5. 用 Go 写个限流，令牌桶或者基于 channel 的限流思路

**参考答案**

结论：令牌桶按固定速率补充令牌，桶满就不再加，所以允许不超过 burst 的突发。容量固定的 channel 如果只做“申请和归还”，限制的是同时执行数，不是每秒请求数。

下面用 channel 当桶。容量是 burst，启动时放满。后台按 `time.Second/qps` 投一枚，桶满就丢掉。`Allow` 非阻塞地取一枚。这个协程要用 `Stop` 退出。qps 必须使间隔大于 0，整数除法也会让速率有偏差。`Allow` 是 O(1)，空间是 O(burst)。这是单机限额。

```go
type Limiter struct {
    tokens chan struct{}
    stop   chan struct{}
    once   sync.Once
}

func NewLimiter(qps, burst int) *Limiter {
    if qps < 1 || burst < 1 || time.Second/time.Duration(qps) <= 0 {
        panic("invalid qps or burst")
    }
    l := &Limiter{
        tokens: make(chan struct{}, burst),
        stop:   make(chan struct{}),
    }
    for i := 0; i < burst; i++ {
        l.tokens <- struct{}{}
    }
    go l.loop(time.Second / time.Duration(qps))
    return l
}

func (l *Limiter) loop(interval time.Duration) {
    ticker := time.NewTicker(interval)
    defer ticker.Stop()
    for {
        select {
        case <-l.stop:
            return
        case <-ticker.C:
            select {
            case l.tokens <- struct{}{}:
            default:
            }
        }
    }
}

func (l *Limiter) Allow() bool {
    select {
    case <-l.tokens:
        return true
    default:
        return false
    }
}

func (l *Limiter) Stop() { l.once.Do(func() { close(l.stop) }) }
```

`golang.org/x/time/rate` 用经过的时间乘速率来补令牌，有互斥锁，没有后台协程，还提供带 `context` 的 `Wait`。多实例的总 QPS 要放在网关或 Redis，单机桶只保护本进程。

### 6. context 包干嘛用，Done 信号怎么传递，怎么避免 goroutine 泄露

**参考答案**

结论：`context` 沿调用链传递取消、截止时间和请求范围的数据。取消是协作的，父 ctx 取消后派生出去的子 ctx 也会取消，已经在跑的函数必须自己看 `Done()`。

`Done()` 返回的 channel 在取消或超时后被关闭。`WithCancel`、`WithTimeout`、`WithDeadline` 都返回 cancel，函数退出时要调用。子 ctx 取消不影响父 ctx。`WithValue` 只放请求级数据，例如 trace id，key 用未导出类型。

```go
ctx, cancel := context.WithTimeout(parent, 200*time.Millisecond)
defer cancel()

ch := make(chan string, 1)
go func() {
    v := doWork(ctx) // doWork 内部要看 ctx，取消后才能返回
    select {
    case ch <- v:
    case <-ctx.Done():
    }
}()
```

入口使用 `r.Context()`，数据库、Redis 和出站 HTTP 带同一个 ctx 或更短的超时。只在外面 `select`、下游不看 ctx，工作仍会跑完。父请求结束、子任务还要单独做完时，用 Go 1.21 的 `context.WithoutCancel` 切断取消，并给这个子任务自己的超时。长期存活的对象里不要藏一个请求的 ctx。泄漏常见于：无人接收的发送、停不掉的 ticker、没有 cancel 的派生 ctx。

### 7. Kafka 和 RocketMQ 区别，你们为啥选这个，怎么保证消息不丢不重复消费

**参考答案**

结论：两者都是消费端拉取、按消费组分担。Kafka 是可回放的分区日志，吞吐和留存强。RocketMQ 把延迟消息、事务消息、重试队列和死信做成了现成能力。选型按项目当时的真实约束讲。

Kafka 的顺序单位是分区，位点由消费者提交。生态上适合接入、留存和回放。RocketMQ 按 topic 下的队列组织，业务消息的定时、半消息和失败重试不用自己再造一套 topic。

不丢要生产、存储、消费三段一起看。Kafka 生产者用 `acks=all` 和 `enable.idempotence=true`，`min.insync.replicas` 至少为 2，副本数比它大，并避免未同步副本当选 leader。消费者先处理成功再提交位点；先提交再处理，崩溃就会丢。RocketMQ 用同步发送，并按需要等待刷盘或从副本应答；消费成功后再 ACK，失败进重试，超过次数进死信。数据库和消息要一起成功时，用事务消息或本地消息表。

重复还会发生：处理完、提交位点或 ACK 之前崩溃，消息会再来。消费端用业务唯一键做幂等，数据库唯一约束或幂等表都可以。Kafka 事务能保证“消费再写回 Kafka”这一段，写到外部数据库仍是至少一次。没在项目里用过的那个，讲差异即可。

### 8. 分布式锁用 Redis 怎么实现，锁过期但业务没跑完怎么办

**参考答案**

结论：用一条 `SET key token NX PX ttl` 加锁。token 每次随机生成。解锁和续期都先比较 token，避免动到别人刚拿到的锁。业务时间可能超过 TTL 时要续期；续期也失败时工作要停，并用 fencing token 挡住旧持有者的晚到写入。

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

续期把 DEL 换成 `PEXPIRE`。后台大约按 TTL 的三分之一执行，业务结束就停掉这个协程再解锁。`SETNX` 和 `EXPIRE` 拆成两次时，中间崩溃会留下没有过期时间的锁。

进程暂停超过 TTL 时，锁会过期，另一个客户端能拿到锁。旧客户端醒来后续期会失败，因为它的 token 已经对不上。存储层再记一个单调的 fencing token，拒绝更小的 token 写入。Redis 主从复制是异步的，主节点挂了且这条锁还没到新主，锁也会丢。续期填不上这个窗口。

### 9. MySQL 事务 ACID，MVCC 讲下，可重复读怎么解决幻读

**参考答案**

结论：原子性靠 undo 回滚，持久性靠 redo，隔离性在 InnoDB 里靠锁和 MVCC，一致性是事务把库从一个满足约束的状态带到下一个。可重复读下，快照读靠同一份 Read View，当前读靠 next-key lock，两边合起来才处理幻读。

InnoDB 默认可重复读。崩溃恢复用 redo，回滚和旧版本用 undo，主从和按时间点恢复用 binlog。开了 binlog 时，提交要协调 redo 和 binlog。刷盘策略决定宕机时能丢多少最近的事务。

MVCC：行上有最后修改它的事务 ID 和指向 undo 的指针。快照读生成 Read View。可见的是“生成这份视图之前已经提交的版本”，加上本事务自己的修改；当时还没提交的、以及之后才开始的事务都不可见，就顺着 undo 找更老的版本。可重复读在事务里第一次快照读时生成 Read View 并一直用；读已提交则每条语句新建一份。

普通 `SELECT` 是快照读，可重复读里看不到别的事务后来插入并提交的行。`SELECT FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，读最新已提交版本并加锁。可重复读使用 next-key lock，也就是记录锁加前面的间隙锁，堵住这个间隙里的插入。唯一索引等值命中已有行时可以只锁记录；行不存在时仍要锁间隙，避免别人把这个键插进来。当前读和快照读看到的结果可以不同。

### 10. 线上 Go 服务 CPU 飙到 100% 怎么排查，用哪些工具（pprof、top、火焰图）

**参考答案**

结论：先确认是不是这个进程在烧 CPU，再用 30 秒 CPU profile 看栈。火焰图里业务函数、GC 和锁会落在不同的位置。

`top` 看进程的 us、sy、wa。wa 高是在等 IO。`top -H -p <pid>` 看线程。然后对 pprof 端口采样。服务要在排查端口挂上 `net/http/pprof`，这个端口不要裸露到公网。

```bash
top -H -p 1234
curl -o cpu.out "http://127.0.0.1:6060/debug/pprof/profile?seconds=30"
go tool pprof -http=127.0.0.1:8081 cpu.out
curl -o heap.out "http://127.0.0.1:6060/debug/pprof/heap"
```

pprof 网页里的火焰图按栈宽看 CPU 时间。栈集中在业务函数，就是热循环、序列化、正则或加密。集中在 `runtime.gcBgMarkWorker`、扫描和 `mallocgc`，就是分配太勤，再用 heap profile 看分配点。锁竞争看 mutex 和 block profile，这两类要先打开才有样本。栈在 cgo 或内核里时，用 `perf top -p <pid>` 补 Go profile 看不到的部分。

容器里同时看 cgroup 的 CPU throttling。`GOMAXPROCS` 高于限额时，进程会一直被限流，看起来也像 CPU 打满。

### 12. 设计一个短链系统，海量映射怎么存，ID 怎么生成，热点 URL 怎么处理

**参考答案**

结论：短链是 code 到长 URL 的映射。写路径发唯一 ID 再编码，读路径按 code 查一次。读远多于写，热点靠缓存挡住，不靠数据库硬抗。

ID 用雪花或号段，再 base62，6 到 8 位够用。雪花遇到时钟回拨就等待或拒绝，避免重复。号段是每个节点向存储领取一段，在内存里往下发。不把裸自增主键当 code，连续数字容易被遍历。

映射按 code 分片，字段有 code、长链、过期时间和状态。跳转只打一个分片。同一长链可以对应多个 code，去重不放在跳转路径上。MySQL 做持久化，Redis 做缓存。写路径用 code 的唯一约束让重试幂等。

读路径是本地缓存、Redis、数据库，然后返回 302。302 不会被浏览器长期记住，改目标和过期才能生效。热点 code 用本地缓存和 Redis 吸收重复读，回源用 singleflight 合成一次，过期时间加随机抖动。需要马上失效的链接，不做 CDN 长缓存。跳转前校验目标协议和域名，统计放到异步链路，不挡重定向。

### 13. 最近在学什么，怎么接触一门新中间件，AI 工具在你学习新东西时起到啥作用

**答题思路**

1. 先说最近在看的那一个，它和现在做的系统哪一块有关。没有就说最近补的那块基础，讲真实在看的。
2. 接触顺序：官方文档里的核心模型和交付保证，跑通一个最小读写，再确认失败时数据还在不在、调用会不会堵住、结果会不会重复。
3. 和已经用过的组件对一下：位点提交、ACK、重试分别是谁的责任，避免用错原来的心智模型。
4. 生产配置放在最后看：持久化、副本、超时、消费失败后的去向。默认值以当前版本文档为准。
5. AI 用来解释概念、整理术语和生成最小示例。持久化语义、默认值和版本差异回到官方文档或源码。生成的客户端要把超时、重试和重复处理自己跑一遍。

### 14. 删除链表倒数第 N 个节点（力扣 19）

**参考答案**

结论：快慢指针一轮扫描。快指针先走 n 步，然后一起走；快指针到尾时，慢指针停在待删节点的前一个。时间 O(n)，空间 O(1)。题目保证 n 有效。

从 dummy 出发，是为了删除头节点时仍有前驱。先数长度再走第二遍也是 O(n)，快慢指针把两次合成一次。

```go
type ListNode struct {
    Val  int
    Next *ListNode
}

func removeNthFromEnd(head *ListNode, n int) *ListNode {
    dummy := &ListNode{Next: head}
    fast, slow := dummy, dummy
    for i := 0; i < n; i++ {
        fast = fast.Next
    }
    for fast.Next != nil {
        fast = fast.Next
        slow = slow.Next
    }
    slow.Next = slow.Next.Next
    return dummy.Next
}
```
