### 3. Golang 中 goroutine 和线程的区别是什么？

**参考答案**

结论：goroutine 是 Go 运行时调度的用户态协程，初始栈大约 2KB，按需扩缩；线程是内核调度的执行单元，栈通常是 MB 级。同等内存下，goroutine 能创建的数量高得多，用户态切换也不必每次陷入内核。

调度模型是 GMP。G 是 goroutine，M 是操作系统线程，P 是逻辑处理器，数量默认等于 `GOMAXPROCS`。可运行的 G 放在 P 的本地队列，空闲的 P 会从别的 P 偷任务。网络读写走 netpoller：G 在等待时挂起，M 去跑别的 G。G 如果卡在会阻塞线程的系统调用上，运行时把 P 交给另一个 M，这个进程的并行度还在。

容易说漏三点。第一，阻塞系统调用、很多文件 IO 和 cgo 仍会占住一条 M，只有网络轮询不会。第二，G 没有语言规范里的稳定 ID，业务里不要依赖 `goid`。第三，goroutine 泄漏时栈和它引用的对象都回收不掉，线程数看起来可以仍然很少。

### 4. Golang 的 channel 有缓冲和无缓冲的区别？

**参考答案**

结论：无缓冲 channel 的发送和接收必须碰上面才完成，是同步交接；有缓冲 channel 的缓冲区没满就能把发送做完，用来削峰，容量用尽以后发送照样阻塞。

无缓冲的容量是 0。发送方会等到某个接收方拿走这份数据，接收完成先于发送完成，所以它自带 happens-before，能用来交接所有权、做通知。有缓冲用 `make(chan T, n)`，里面是一个环状队列：发送只在长度为 n 时阻塞，接收只在队列空时阻塞。缓冲把生产者和消费者拆开，也把背压推迟到队列满的那一刻。

关闭之后两边都不能再发送，再发送会 panic；缓冲里已经写下的元素仍可以读完，读尽后再读得到零值和 `ok == false`。`nil` channel 上发送和接收都会一直堵着，`select` 里常用这个特性关掉一条分支。

容量不是越大越快。缓冲区会藏住消费端变慢，延迟和内存一起涨。需要强同步就用无缓冲；需要少量削峰就按下游处理速度估一个有界容量。`len(ch)` 有竞态，不要拿它做逻辑判断。

### 5. 大模型 Transformer 架构的核心组件有哪些？

**参考答案**

结论：核心是自注意力、位置信息、前馈网络，以及残差和归一化。编码器-解码器结构和现在常见的纯解码器大模型，差在有没有交叉注意力。

自注意力把每个 token 线性投影成 Q、K、V，权重是 `softmax(QK^T / sqrt(d_k))`，再去加权 V。除以 `sqrt(d_k)` 是为了避免点积随维度变大后 softmax 饱和。多头是把 `d_model` 拆成多组独立的 QKV，最后拼接再投影，让不同头看不同的关系。注意力本身对顺序不敏感，所以要加位置信息：原论文用正弦位置编码，现在的大模型多用 RoPE，把相对位置揉进 Q、K 的旋转里。

每个子层外面是残差加 LayerNorm（新模型常用 Pre-Norm，归一化也常换成 RMSNorm）。前馈网络对每个位置单独做两层线性变换，中间是激活；现在常用 GELU 或 SwiGLU，而不是最初的 ReLU。

原版 Transformer 还有编码器，解码器用掩码自注意力看自己的过去，再用交叉注意力看编码器输出。GPT 这类模型只有解码器：因果掩码保证位置 i 看不到 i 之后的 token，最上面接一个词表上的线性层。面试里先说明你讲的是哪一种，再往下拆组件。

### 6. Redis 的持久化机制 RDB 和 AOF 的区别？

**参考答案**

结论：RDB 是某一时刻的全量快照，文件小、恢复快，两次快照之间的写入会丢；AOF 按写命令追加日志，丢数据的窗口更小，文件更大，重放也更慢。

RDB 一般用 `BGSAVE`。父进程 `fork` 出子进程写 `dump.rdb`，靠写时复制继续对外服务。内存越大，`fork` 时的停顿和之后的缺页越明显。它适合做备份和跨机拷贝，不适合当作「最多丢一秒」的承诺。

AOF 把写命令追加到文件。`appendfsync` 有三种常见策略：`always` 每次写都刷盘，最稳也最慢；`everysec` 大约每秒刷一次，是常用的折中，宕机时大约丢一秒；`no` 交给操作系统，宕机时丢的窗口不确定。文件会越来越大，所以要 `BGREWRITEAOF`：重写期间的新写入进增量缓冲，重写结束后再合并。重写同样要 `fork`。

Redis 4 之后的混合持久化在重写 AOF 时先写入 RDB 格式的全量，后面再接增量命令。加载时先吃快照，再重放一小段日志。两者可以同时打开。副本做全量同步时，主库也会生成一份类似 RDB 的快照发给副本，这和 AOF 的刷盘策略是两条线。

### 7. MySQL 的索引为什么使用 B+ 树？

**参考答案**

结论：InnoDB 的索引要匹配 16KB 的页和磁盘顺序读。B+ 树让内节点只放键和指针，扇出大、树矮；叶子之间有链表，范围扫描可以顺着叶子走。

二叉树和红黑树的高度是对数级，但底数小，一次查询要很多次随机 IO，不适合放在磁盘页上。B 树的内节点也存数据，同样大小的页能放下的键更少，树更高，范围查询还要在内节点和叶子之间来回跳。B+ 树的数据都在叶子上，内节点更瘦，三到四层就能覆盖很大的表。一次页读进来，里面有很多有序的键，局部性好。

InnoDB 的主键索引是聚簇索引，叶子放整行。二级索引的叶子放主键，查到主键后再回表读聚簇索引。所以二级索引覆盖了查询所需的列时，可以不再回表。

哈希索引等值查询很快，但做不了范围、排序和最左前缀。Memory 引擎可以用哈希；InnoDB 的自适应哈希是在 B+ 树之上对热点页建的缓存，不是你建索引时选的结构。

### 8. Kafka 如何保证消息不丢失？

**参考答案**

结论：不丢要三段一起做。生产者等 ISR 全部确认，Broker 禁止落后副本当选，消费者处理成功之后再提交位移。只开其中一段，消息仍会在另外两段丢掉。

生产者用 `acks=all`，并且 `retries` 足够。`acks=all` 等的是当前 ISR，不是主题上配置的全部副本。`min.insync.replicas` 保持默认 1 时，ISR 里只剩 leader 也会确认成功。常见配法是副本因子 3、`min.insync.replicas=2`，这样至少两个副本落盘确认后才返回。重试会制造重复，所以同时打开幂等生产者：每个分区有序列号，Broker 对重试去重。发送失败要看回调，不能发完就当成功。

Broker 侧关掉 unclean leader election，避免一个落后副本升主之后，把已经确认过的日志截掉。

消费者关掉自动提交，业务处理成功再提交位移。先提交再处理，进程在处理中途挂掉，这条消息不会再投递。处理后提交是至少一次，消费逻辑要能扛重复。位移提交的是「下一条要读的位置」，提交偏移 5 表示 0 到 4 都已处理。

### 9. 场景题：设计一个短链接生成系统，如何保证高并发？

**参考答案**

结论：读多写少。生成短码要无状态、可水平扩展；跳转路径用缓存吃掉读流量，点击统计异步化，不堵在跳转上。

短码用全局唯一整数再做 Base62，6 位大约有 568 亿种组合。发号有两种常见做法。号段模式每次从数据库领一段区间，发号在内存里完成，数据库只在领号时写一次。雪花算法把时间、机器号和序列拼进一个 64 位整数，发号不访问数据库，机器号要统一分配，时钟回拨要能拒绝发号或等待。对长链接做哈希会碰撞，同一条长链接也可能需要多条短链，所以哈希只能作为可选的去重手段，唯一性以发号为准。

存储上，`short_code` 做主键，长链接和过期时间做字段。创建走主库。跳转是主路径：先查本地缓存，再查 Redis，未命中再查库，并用缓存回写。过期时间和短链本身对齐。不存在的短码缓存一个短 TTL 的空值，避免被人用随机码把数据库打穿。特别热的短链放进程内缓存，并加上限流。

跳转返回 302。301 会被浏览器长期记住，目标改了也到不了服务端，点击次数也统计不全。点击量写 Kafka，异步落库，跳转接口不写事务。

创建接口按用户限流。服务本身无状态，多实例部署。Redis 用集群，短码的槽位随 key 散开。数据库只承担创建和缓存未命中，读副本用来恢复缓存，不承担跳转的主流量。

### 10. 算法题：手写快速排序

**参考答案**

选一个枢轴，把小于它的放左边、大于它的放右边，再递归两边。平均时间 `O(n log n)`，额外空间主要是递归栈，平均 `O(log n)`。枢轴每次都选到最值时退化为 `O(n^2)` 时间和 `O(n)` 栈空间。它不稳定。

随机选枢轴，是为了避开已经有序的输入。重复元素很多时，两边仍然会偏，三路划分（小于、等于、大于）才划算。下面用 Lomuto 划分，等于枢轴的元素会落到右边。

```go
func QuickSort(a []int) {
	quickSort(a, 0, len(a)-1)
}

func quickSort(a []int, lo, hi int) {
	if lo >= hi {
		return
	}
	p := partition(a, lo, hi)
	quickSort(a, lo, p-1)
	quickSort(a, p+1, hi)
}

func partition(a []int, lo, hi int) int {
	pivotAt := lo + rand.Intn(hi-lo+1)
	a[pivotAt], a[hi] = a[hi], a[pivotAt]
	pivot := a[hi]
	i := lo
	for j := lo; j < hi; j++ {
		if a[j] < pivot {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[hi] = a[hi], a[i]
	return i
}
```

`rand.Intn` 来自 `math/rand`。Go 1.20 起全局随机源会自动播种。面试里如果被追问栈深度，可以先递归较短的一侧，另一侧用循环，把最坏栈空间压到 `O(log n)`。

### 11. 在你的项目中，如何利用 Redis 缓存提升性能？

**答题思路**

这题要讲你自己的项目，按「慢在哪 → 缓存了什么 → 一致性 → 结果」讲，两分钟。数字和 key 都用真实的。

1. 先点明慢的接口和原因：慢查询、重复计算，还是下游超时。说出优化前的延迟大概在哪个量级，口径是 P99 还是平均值。
2. 缓存的内容：key 怎么组成，value 是整行还是算好的结果，TTL 多长。说明为什么这个 TTL 能接受短暂脏读。对象很大时，讲你怎么拆 value，避免一个 key 把单线程的 Redis 堵住。
3. 更新方式用你真实采用的那种。旁路缓存是读时回填、写时先更新数据库再删缓存。你如果用了延迟双删或订阅 binlog，就把失败时谁负责重试讲清楚。
4. 主动补两个你处理过的问题：热点 key、缓存击穿，或者批量 key 同时过期。没处理过就说实话，并给出你现在会加的保护，例如互斥回源、TTL 加随机抖动。
5. 用命中率和该接口延迟的变化收尾。命中率说不清统计窗口，就不要报百分比。

### 12. 大模型在推荐系统中的应用有哪些挑战？

**参考答案**

结论：推荐链路吃的是几十毫秒内的排序和亿级候选，大模型吃的是长文本和慢推理。能落地的用法是离线产特征、在线只碰精排之后的一小截，而不是让大模型代替召回。

延迟和成本是第一道坎。召回、粗排、精排往往要在几十毫秒内打完，一次大模型生成是百毫秒到秒级，每个候选都跑一遍，GPU 成本按流量线性涨。候选集是百万到亿，模型也看不到完整集合，让它直接「生成商品 ID」会编出不存在的物品。

信号也对不上。大模型强在文本语义，弱在刚刚发生的点击、库存和价格。这些仍在特征平台和序列模型里，得把语义向量和 ID 特征一起喂给排序模型，不能只靠提示词。

训练和评估也不同。推荐日志是有偏的隐式反馈，曝光位置本身会影响点击。监督微调用的示范数据、对齐用的偏好数据，都不能直接当成点击率标签。离线困惑度升高或下降，说明不了 GMV。要看约束候选之后的在线实验。

比较稳的切法：离线用大模型抽取标签和文本向量，建进向量索引；在线仍用双塔或序列模型召回和排序；只对 Top K 生成推荐理由，或者做一次小模型重排。物品 ID 必须从候选集里选。

### 13. Golang 中如何避免内存泄漏？

**参考答案**

结论：Go 有 GC，泄漏几乎都是对象从根上仍然可达。最常见的根是停不下来的 goroutine、只增不删的 map，以及切片和底层数组的牵连。

goroutine 卡在无人接收的 channel、没有超时的下游调用，或者退出时没有 `cancel` 的 `context` 上，它的栈以及栈上引用的整棵对象都会留着。`pprof` 的 goroutine 剖面能直接看到它们堵在哪一行。任务要用 `context` 带上超时，启动之后要有人负责退出。

第二种是容器没有淘汰。全局 map、没有上限的连接表、把请求放进 `sync.Pool` 以外的自建池，都会随流量涨。`sync.Pool` 本身会在 GC 时被清掉，不适合当会话缓存。

第三种是小切片牵着大数组。`buf[:n]` 仍引用整块 `buf`。只想留下一小段时要 `copy` 到新切片。字符串切片同样共享底层字节。`http` 的响应体不 `Close`，连接和缓冲也回不了池。

`time.Ticker` 不用了就要 `Stop`。Go 1.23 起，已经没有引用的 Timer 可以被 GC 回收；在此之前，循环里反复 `time.After` 会把还没触发的 Timer 留到触发为止。排查看 heap 的 `inuse_space`，对比分配点和存活对象，而不是先调用 `debug.FreeOSMemory`。

### 14. 如何监控 MySQL 的慢查询？

**参考答案**

结论：慢日志负责已经执行完的语句，`performance_schema` 负责聚合和正在跑的语句。先按摘要聚合，再对出现次数多、总耗时长的那几条做 `EXPLAIN`。

打开 `slow_query_log`，把 `long_query_time` 从默认的 10 秒下调到你的接口预算附近，例如零点几秒。需要时再打开未走索引的语句，这条日志量会很大，只在排查时开。日志可以用 `pt-query-digest` 或 `mysqldumpslow` 按指纹汇总。慢日志是语句结束后才写的，一个正在等锁的会话不会出现在里面。

正在执行的语句看 `performance_schema.events_statements_current` 和 `SHOW PROCESSLIST`。历史汇总看 `events_statements_summary_by_digest`，里面有执行次数、总耗时、扫描行数和返回行数。锁等待看 `data_lock_waits`。总耗时里包含等锁，所以一条「慢 SQL」可能是锁，不是没索引。

应用侧用 trace 把接口耗时拆开，确认时间是在数据库，而不是在应用自己的序列化或锁上。改完索引之后看同一条 digest 的扫描行数和耗时有没有下降，而不是只看一次手工查询。

### 15. Kafka 的消费者组如何工作？

**参考答案**

结论：同一个 `group.id` 里的消费者共同消费主题，每个分区在组内只会分给一个消费者。并行度的上限是分区数，消费者比分区多时，多出来的成员分不到分区。

组由一个 Broker 担任协调者，位移存在内部主题 `__consumer_offsets`。成员启动时先找到协调者，再加入组。协调者选定一个 leader，leader 按策略把分区分配方案交回去（新协议里也可以由 Broker 侧分配）。常见策略有 Range、RoundRobin、Sticky 和 CooperativeSticky。前几种是全量再均衡：一成员进出，所有人都停下并归还分区。CooperativeSticky 是增量再均衡，只挪必须挪的分区。

成员用心跳保活，处理时间过长、迟迟不 `poll`，也会被当成失联。再均衡的触发包括成员加入、退出、崩溃、订阅变化和分区数变化。重启造成的不必要再均衡，可以用静态成员（固定 `group.instance.id`）减轻。

位移可以自动提交，也可以处理完再提交。再均衡期间没提交的分区会由新消费者重读，所以处理逻辑要幂等。消费者数量的规划按分区和单分区处理速度来，而不是按机器数。

### 4. Golang 中如何实现高性能的并发编程？

**参考答案**

结论：先用剖面找到热点，再限制并发、减少分配、缩短持锁时间。无界地 `go` 出去不能提高吞吐，只会把下游打满，并把延迟堆在内存里。

并发度按最慢的下游来封顶。可以用固定大小的 worker 池，也可以用带上限的 `errgroup`。每个请求再开一堆 goroutine 去扇出时，总任务数也要有上限。出口用 `context` 取消，调用方超时之后，里面的工作要能停下来。

共享状态优先看访问模式。保护 map 或连接表用 `sync.Mutex`，读远多于写再用 `RWMutex`。锁里面不要做 IO、RPC 和 channel 操作。计数和标志用原子操作。channel 适合交接所有权和通知；在热路径上用 channel 传递每个请求，往往比加锁的对象池更慢。Go 的那句「通过通信共享内存」是并发安全的建议，不是性能建议。

分配会把 CPU 花在 GC 上。热点路径上复用 `[]byte`，短命且同质的对象可以放 `sync.Pool`，注意池会把对象留到下一轮 GC，不要把请求级的大对象无界放进去。内存上限用 `GOMEMLIMIT` 配合容器配额，避免 GC 和业务互相踩。

上线前对热点函数做 benchmark，用 race 检测器跑测试。上线后看 CPU 剖面、goroutine 数、GC 暂停和调度延迟，再决定要不要改。

### 5. 大模型微调有哪些常见方法？各自优缺点？

**参考答案**

结论：先分清两条轴。一条是更新哪些参数，一条是用什么目标训练。全量微调和 LoRA 解决第一条，SFT 和 DPO 解决第二条。

全量微调更新全部权重，效果上限最高，也最吃显存和数据。每个任务一份完整模型，部署成本高，还容易把预训练里的能力覆盖掉。

LoRA 冻结原权重 W，只训练低秩分支 `BA`（秩为 r，远小于隐藏维度），输出相当于 `W + (alpha/r) BA`。可训练参数少，一张消费级显卡也能跑小模型，多个任务各存一份适配器。推理前可以把 `BA` 合并进 W，几乎不增加延迟。秩太小、或者任务要大幅改写知识时，表达能力不够。它不包含量化。

QLoRA 在 LoRA 的基础上把冻结的基座量化到 4 bit（常用 NF4），适配器仍用 16 bit 训练，再用分页优化器控制显存峰值。同样的显存能上更大的基座，代价是量化误差和更慢的反量化计算。

Prefix Tuning、P-Tuning 只训练插在各层或输入端的连续向量，参数更少，适合分类和简单风格，生成任务上通常弱于 LoRA。

目标函数上，SFT 用标准答案做监督，负责学会格式和基本行为。DPO 用偏好对直接优化，不需要在线采样和奖励模型。PPO 一类的强化学习更灵活，训练更不稳，也更贵。参数高效方法决定改多少权重，SFT 或 DPO 决定拿什么损失去改，两者是叠加关系。

### 6. 设计一个支持亿级用户的大模型推理服务，需要考虑哪些方面？

**参考答案**

结论：亿级用户不能理解成每次打开应用都跑一次大模型。先把请求分级、把相同前缀缓存掉，再按 token 而不是按请求数去调度 GPU。模型分片、负载均衡和成本是一件事的三面。

模型放得下是前提。单卡放不下时，张量并行按层把矩阵切到同一台机器的多张卡上，依赖 NVLink 这类高速互联；流水线并行按层切到不同机器，会有流水线气泡。这是模型分片。副本数才是吞吐的横向扩展，一张逻辑上的「完整模型」对外是一个副本，副本之间互相独立。MoE 还要单独考虑专家并行，别和张量并行混为一谈。

请求调度看 token，不看 QPS。预填充吃算力，逐 token 解码吃显存带宽，两者拆到不同的 GPU 池，避免长提示把解码的间隔拉高。连续批处理让新请求填上已经结束的空位；KV cache 按页管理，减少碎片。负载均衡按前缀亲和来路由：系统提示相同的请求尽量打到已经缓存了这段 KV 的副本上，同时看每个副本的排队 token 数，而不是轮询。队列超过延迟预算就拒绝或降级，而不是无限排队。

成本靠少打大模型。完全相同的请求走结果缓存；简单请求走小模型；只有困难请求升级到大模型。权重和 KV 能用 FP8 等低精度的地方就量化，并给每个用户限制生成长度。GPU 扩容慢，要有常驻的暖副本，自动扩缩容只处理持续的水位变化。

稳定性上，流式输出把首 token 延迟和后续每 token 延迟分开监控。超时、单用户公平队列、小模型降级都要在接入层做好。重试对流式接口不透明，幂等键要按请求而不是按连接。

### 7. 场景题：Redis 缓存穿透如何预防和解决？

**参考答案**

结论：穿透是查询的 key 在缓存和数据库里都不存在，请求每次都落到数据库。和它挨着的两个问题要分开：击穿是热点 key 过期，雪崩是大量 key 同时失效或缓存集群不可用。

先在入口挡住明显非法的 key：格式、长度、签名。对确认不存在的 key，缓存一个短 TTL 的空值，让后续请求停在 Redis。攻击者如果每次换一个随机 key，空值会占满内存，所以还要限流，并且在缓存前加布隆过滤器。

布隆过滤器建的是「可能存在的 key」的集合。它说不存在，就可以直接返回，不会有漏报（前提是集合只增不删，删除要换成计数布隆过滤器）。它说可能存在，才去查缓存和数据库。误判只会多一次后端读取。

误判率由位数 m、哈希函数个数 k、已插入元素 n 决定。某一位在插入后仍为 0 的概率约为 `e^{-kn/m}`，查询时 k 位全为 1 的概率约为：

`ε ≈ (1 - e^{-kn/m})^k`

k 取 `(m/n) ln 2` 时误判率最低，大约是 `2^{-k}`。想把误判率放在 1% 附近，每个元素大约 10 bit、7 个哈希函数，因为 `2^{-7} ≈ 0.8%`。过滤器要按数据全集构建，数据库删除了 key 而过滤器没重建时，被删的 key 仍会穿过过滤器打到后端。

互斥锁和 singleflight 解决的是同一个热点 key 的并发回源，也就是击穿，挡不住永远不存在的随机 key。

### 8. 算法题：手写二叉树层序遍历

**参考答案**

用队列做广度优先。根入队后，每一层开始时记下当前队列长度，只处理这么多个节点，把它们的值记为一层，再把它们的孩子排到队尾。时间 `O(n)`，队列最宽处是最底层，空间 `O(n)`。

```go
type TreeNode struct {
	Val   int
	Left  *TreeNode
	Right *TreeNode
}

func LevelOrder(root *TreeNode) [][]int {
	if root == nil {
		return nil
	}
	res := make([][]int, 0)
	q := []*TreeNode{root}
	for head := 0; head < len(q); {
		n := len(q) - head
		level := make([]int, 0, n)
		for i := 0; i < n; i++ {
			node := q[head]
			head++
			level = append(level, node.Val)
			if node.Left != nil {
				q = append(q, node.Left)
			}
			if node.Right != nil {
				q = append(q, node.Right)
			}
		}
		res = append(res, level)
	}
	return res
}
```

用下标 `head` 前进，是避免 `q = q[1:]` 在长时间存活的队列里把已出队节点留在底层数组上。这道题函数返回后整段队列都会释放，用切片头弹出也对。空树要单独返回。如果题目要的是自底向上的层序，得到 `res` 后反转即可，不必改遍历顺序。

### 10. Redis 集群模式下，数据分片和故障转移如何实现？

**参考答案**

结论：Redis Cluster 把数据切成 16384 个哈希槽，每个槽有一个主节点和若干副本。分片是槽到主节点的映射；故障转移是某个主节点的副本通过选举接过这些槽。

key 先算 CRC16，再对 16384 取模得到槽号。客户端缓存槽位表，请求直接发到对应节点。节点发现 key 不属于自己，返回 `MOVED`，客户端据此永久更新映射。槽正在迁移时返回 `ASK`，这次请求改道，映射先不改。相关的 key 要落在同一个槽时，用花括号标出参与哈希的那段，例如 `{userId}.a` 和 `{userId}.b`。不在同一槽的多 key 命令会被拒绝。

节点之间用 gossip 交换状态。主节点失联后，它的副本发起选举，需要多数主节点同意，配置纪元递增，复制偏移更大的副本优先当选。选上之后，新主广播自己接管的槽，客户端通过 `MOVED` 或刷新槽位表找到它。

复制是异步的。没同步到副本的最后一段写入，在切换后会丢。要求写入必须跟上至少 N 个副本，可以缩小这个窗口，副本不够时写入会失败。选举期间，这些槽不可用。哨兵模式只做一主多从的故障转移，不负责分片，和 Cluster 不是同一套机制。

### 11. MySQL 事务隔离级别有哪些？分别解决什么问题？

**参考答案**

结论：SQL 标准有四级。InnoDB 默认是可重复读，并用 MVCC 加间隙锁处理快照和幻读。隔离级别对应的是脏读、不可重复读和幻读，替代不了更新丢失所需的版本号或 `SELECT FOR UPDATE`。

读未提交：能读到别的事务还没提交的修改，脏读就发生在这里。基本不用。

读已提交：语句只能读到已经提交的数据，脏读被挡住。同一事务里两次读同一行，中间有人提交了修改，两次结果可以不同，这是不可重复读。范围查询同样可能看到新插入的行。InnoDB 在这个级别上每次一致性读都会生成新的 Read View。

可重复读：事务里第一次一致性读建立 Read View，之后的普通 `SELECT` 都看这同一份快照，不可重复读被挡住。InnoDB 对 `UPDATE`、`DELETE`、`SELECT FOR UPDATE` 这类当前读加临键锁（记录锁加间隙锁），别的事务不能在间隙里插入，用来挡幻读。普通快照读看不到新行，但当前读看得到最新已提交版本，所以「先查没有，再插入」仍可能撞上唯一键。

串行化：普通 `SELECT` 也变成加锁读，隔离最高，并发最差。

间隙锁在可重复读下更容易死锁，有的业务会改用读已提交来换更高的并发。两种级别都挡不住两个事务都先读再写回造成的丢失更新，这种要用原子更新、乐观版本号或显式加锁。

### 12. Kafka 如何实现 Exactly-Once 语义？

**参考答案**

结论：Kafka 的精确一次指的是「写进 Kafka」以及「消费-处理-再写回 Kafka」这条链路，不是包括数据库在内的整个业务副作用。它由幂等生产者和事务两部分组成。

幂等生产者给每个分区维护生产序号。开启后，重试不会在同一个分区里写出重复记录，单分区内的顺序也能在有限的在途请求下保住。它不保证多个分区一起成功或一起失败。

跨分区、以及和消费位移绑在一起，要用事务。生产者固定 `transactional.id`，初始化时拿到纪元，旧进程再提交会被隔离掉。一次处理的顺序是：开始事务，把结果写到下游主题，用 `sendOffsetsToTransaction` 把输入位移和这批写入放进同一事务，然后提交。事务协调者写提交或中止标记。崩溃时这批输出和位移要么都可见，要么都不可见。

下游消费者要把 `isolation.level` 设为 `read_committed`，未提交和已中止的事务记录不会被交出去。仍用 `read_uncommitted` 的消费者，会看到后来被中止的消息。

写 MySQL 这类外部系统不在这个语义里。要和数据库一起做到端到端只生效一次，输出侧还得做幂等写，或者用发件箱，让数据库提交和发消息放在同一个本地事务里。事务会增加一次提交往返，吞吐会低于只开幂等的生产者。

### 13. 大模型推理阶段如何优化延迟和吞吐？

**参考答案**

结论：延迟看首 token 时间（TTFT）和后续每个 token 的间隔（TPOT），吞吐看每张 GPU 每秒打出的 token。批越大吞吐越高，排队也越久，两个目标要分开设预算。

预填充是一次把整段提示算完，受算力限制；解码是每个 token 去读越来越大的 KV cache，受显存带宽限制。静态组批会让短请求等长请求。连续批处理允许解码中的请求和新来的预填充拼在同一批里。长预填充要切成块，插进解码的间隙，避免一个长提示把别人的 TPOT 顶高。

KV cache 是显存的大头。按页分配减少碎片，相同的系统提示命中前缀缓存，不必重算。KV 量化到 FP8 能多塞一些并发序列，用质量换容量。缓存满了要有淘汰，不能无限保留会话。

解码的 kernel 启动开销占比高，可以用 CUDA Graph 把一步解码的内核调用录下来重放。注意力用 FlashAttention 这类融合实现，少读写中间矩阵。投机解码用小模型先猜若干 token，大模型一次验证，接受率高时能降低延迟；接受率低就白算。

权重量化（FP8、INT4）提高能同时放的批大小，也会掉效果，要看任务是否扛得住。应用侧能做的是限制生成长度、缓存相同请求、把短请求交给小模型。批大小和并行度最后都对着 TTFT、TPOT 和每 GPU 的 token 吞吐来调，不单独追求某一个。

### 14. 在团队中，如何推动技术方案落地？

**答题思路**

讲一次你真实推动过的改动。没有这样的经历，就讲你准备怎么做，并说明它还停在方案阶段。不要编一个你没参与的跨团队项目。

1. 把问题量化：谁在痛，频率多高，现在的延迟、错误率或人工成本是多少。对方不承认这个问题，方案不会往下走。
2. 写一页就能看完的说明：目标、做法、你比较过的另一个做法、迁移步骤、怎么回滚。回滚要具体到开关或兼容旧数据。
3. 找一个最小试点：一个接口、一个租户或一台灰度机器。约定几天内看哪两个指标，指标变差就退回。
4. 用试点的数据同步给受影响的人，包括值班和上下游。扩大范围时写清谁负责兼容旧路径。
5. 收尾落到默认路径：脚手架、评审清单、文档和告警。人走了方案还在，才算落地。

你在其中的角色说清楚：是你写的方案，还是你负责灰度。别人做的决策不要说成自己推动的。

### 15. 你的职业规划是什么？未来想深入哪个技术方向？

**答题思路**

按「这一年能独立负责什么 → 接下来想深入的方向 → 和 Golang / 大模型工程的关系」讲，控制在两分钟。不报职级，不报薪资数字，公司只用简历上真实的那家。

1. 这一年：把 Go 服务的并发、延迟和故障处理讲到你能独立负责一条链路。材料用你已经有的项目，指标用你解释得了的那种。
2. 方向落在模型工程，而不是改口做训练算法。可选的点要和你的经历接上，例如推理服务的延迟和 GPU 成本、检索增强，或者推荐链路里大模型只处理精排之后的一小段。选一个就讲透，不要三个都要。
3. 证明你已经在这条路上：你正在读的实现或论文，你写过的最小服务，以及你用来判断自己学会了的那个问题。学习方法要和前面「最近在学什么」一致。
4. 收尾：你希望在真实流量里做取舍，能同时看延迟、成本和效果。对方如果介绍的是纯业务后端，就把同一套能力说成高并发和服务稳定性，模型经验作为补充，不要当场否掉对方的业务。
