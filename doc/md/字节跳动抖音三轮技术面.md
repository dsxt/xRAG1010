### 1. 先做个自我介绍吧，说说你最近在做的项目和技术栈

**答题思路**

控制在两分钟内，按「我是谁 → 最近在做什么 → 和岗位的关系」来讲。

1. 一句背景：工作年限、主要用 Go 做后端，业务落在交易、内容或高并发链路上。用你的真实方向。
2. 最近一个项目：你负责的模块、峰值口径（哪个接口、秒级还是分钟级）、用到的存储和消息队列。只报你能对着监控解释的数字。
3. 留两个可以深挖的点，例如容量是怎么估的、库存或订单怎么保证不写错。后面的题会从这里追。
4. 收尾：你为什么想做抖音电商这种有突发流量、又要求数据正确的业务。

技术栈报你真的在线上用过的，版本和组件名都要经得起追问。

### 2. 你说你做过高并发系统，那你说说 QPS 怎么评估？你们系统峰值多少？

**参考答案**

结论：峰值 QPS 先用业务量估算，再用监控核对口径，最后用压测找到拐点。报数字时要说清是哪个接口、什么时间窗口、包不包括重试。

估算公式是：峰值 QPS ≈ 峰值时段请求数 / 该时段秒数。请求数 ≈ 峰值在线人数 × 人均操作次数 × 每个操作扇出的接口数。日活除以 86400 只是全天平均，直播和秒杀的峰值会集中在很短的窗口里，要用峰值时段，不能用全天平均代替。重试、网关到下游的扇出都会把后面的 QPS 放大，所以入口 QPS 和数据库 QPS 要分开报。

监控核对：看网关或服务的秒级曲线，取大促或直播的历史峰值，并区分成功、失败和限流。没有这条曲线，就明确说出估算里哪些是假设。

压测用来验证估算，分两层。单机压到 P99 和错误率的拐点，看 CPU、goroutine、GC、连接池谁先满。全链路压测给流量染色：写请求进影子表和影子 Topic，支付、短信走 mock，按线上接口比例梯度加压。提前写好停止条件，例如错误率、P99、数据库连接、消息堆积。染色一旦丢失，压测写进真实库，所以要有全局开关，能立刻停压、停写。

集群容量要在单机结果上打折，折扣取决于负载是否均匀、以及下游是不是先被打满，这个折扣用压测测，不拍一个固定比例。

### 3. 场景题：一个接口突然变慢，从哪些维度排查？

**参考答案**

结论：先圈定「哪个接口、从什么时刻、一台还是全部」，再把时间拆到服务内和下游，最后对上那一次发布、配置或流量变化。

1. 范围。是这一个接口还是整机都慢；P99 变长还是错误率上升；QPS 是升高、持平还是下降。QPS 掉了同时变慢，常见是锁、连接池或下游超时把请求堆住。
2. 变更。对齐发布时间、配置、扩缩容、数据倾斜和依赖方的故障。先看变更，能少走很多弯路。
3. 时间花在哪。用 trace 看网关、本服务、数据库、Redis、下游 RPC 各占多少。本服务占比高，再看 CPU profile、锁和 GC；下游占比高，就去看慢查询、锁等待、Redis 慢日志和下游自己的延迟。
4. Go 进程内。goroutine 数是否上涨，block、mutex profile 里等在哪里，GC 标记是否把用户协程拉去 assist。`database/sql` 的等待次数上升，说明连接池不够或 SQL 变慢。
5. 数据与热点。是不是出现了热 key、大事务、突然的全表扫描。一台机器慢，多半是实例或它连的分片；全部机器慢，多半是共享依赖。

现场先留 profile、慢日志和一台机器的 goroutine 栈，再考虑重启。重启能恢复，但会把栈弄丢。

### 4. MySQL 索引失效的场景有哪些？举几个实际例子

**参考答案**

结论：B+Tree 索引要求查找键是连续、可比较的前缀。对列做函数或类型转换、左模糊、跳过联合索引最左列，都会让这棵索引用不上。优化器因为选择性差而选择全表扫描，是另一回事，要用 `EXPLAIN` 分开看。

```sql
-- 列上套函数，created_at 上的普通索引用不上
SELECT * FROM orders WHERE DATE(created_at) = '2026-11-08';

-- 改成范围，才能沿 created_at 定位
SELECT * FROM orders WHERE created_at >= '2026-11-08'
                       AND created_at <  '2026-11-09';

-- phone 是 varchar，和数字比较时转换发生在列上，索引失效
SELECT * FROM users WHERE phone = 13800138000;
-- 列是整数、常量是字符串时，转换发生在常量上，索引仍然可用

-- 左模糊不能做范围定位；'手机%' 可以
SELECT * FROM products WHERE name LIKE '%手机';

-- 联合索引 (user_id, status, created_at)，跳过了 user_id
SELECT * FROM orders WHERE status = 1 AND created_at > '2026-11-01';
```

还有几种实际里常见：

- 两张表 join 的列字符集或 collation 不一致，驱动列上的索引用不上。
- `OR` 连着不同列的条件时，经常无法稳定地只用一棵索引。可以拆成两条各自走索引的查询，再用 `UNION` 合并，避免同一行同时满足两个条件时重复出现。
- 命中行太多，回表成本高于全表扫描，优化器会放弃索引。这时索引本身还能用，只是这次不划算。
- MySQL 8.0 可以给表达式单独建函数索引，那是另一棵索引，不能据此认为给列套了函数还能用原来的索引。

`EXPLAIN` 里看 `type`、`key` 和 `rows`。`type=ALL` 且 `key` 为空，才是这次没走索引。

### 5. 分布式锁，Redis 和 etcd 你怎么选？为什么？

**参考答案**

结论：临界区短、QPS 高、数据库唯一约束还能兜底时用 Redis。互斥必须严格成立、冲突不剧烈、可以接受毫秒到几十毫秒的协调延迟时用 etcd。库存和资金的最终互斥以数据库条件更新或唯一键为准，锁只是缩小并发窗口。

Redis 的做法是 `SET key token NX PX ttl`，token 用随机值。解锁必须用 Lua 先比对 token 再删除，避免把别人续上的锁删掉。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

持有时间可能超过 TTL 时，业务还在跑就续期，业务结束就停掉续期。进程如果停顿超过 TTL，锁已经到期，续期救不了这次停顿。主从异步复制还有另一个窗口：锁写在主库，主库宕机时副本还没收到，新主会再发一次锁。Redlock 需要多套独立的 Redis 主节点；Cluster 的主从副本不是独立的一份锁。更稳的做法是加一把单调递增的 fencing token，数据库只接受比已见过的 token 更新的写入。

etcd 用 Raft 保证授权线性一致，主从切换不会把同一把锁发给两个客户端。常见用法是租约加 revision：`concurrency.Mutex` 按创建 revision 排队，前者释放（删除 key）后者才能拿到。进程挂了，租约到期锁会释放。停顿超过租约时，旧客户端仍然可能以为自己持有锁，所以写存储时带上这个 revision，存储层拒绝过期的 revision。

选择时看三点：冲突频率、临界区长短、锁失效时业务能不能靠数据库约束收住。每请求一次的热点互斥不要放在 etcd 上。低频的选主、调度和配置用 etcd。Redis 锁的过期时间按临界区来设，没有普遍适用的默认值。

### 6. 手写一个线程安全的 LRU Cache

**参考答案**

结论：用 map 做 O(1) 查找，双向链表维护使用顺序，最近使用的放在头哨兵后面，淘汰链表尾部。Get 会改顺序，所以和 Put 共用一把互斥锁，不能用读锁包住 Get。时间每次 O(1)，空间 O(容量)。

map 和链表要在同一把锁里改。锁只包住指针操作，不要在锁里做 RPC。结构体含 `sync.Mutex`，只能按指针传递，按值复制会把锁拷走。

```go
package lru

import "sync"

type entry struct {
	key, val   int
	prev, next *entry
}

type LRUCache struct {
	cap        int
	mu         sync.Mutex
	items      map[int]*entry
	head, tail *entry
}

func NewLRUCache(capacity int) *LRUCache {
	head, tail := &entry{}, &entry{}
	head.next = tail
	tail.prev = head
	return &LRUCache{
		cap:   capacity,
		items: make(map[int]*entry),
		head:  head,
		tail:  tail,
	}
}

func (c *LRUCache) Get(key int) (int, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	e, ok := c.items[key]
	if !ok {
		return 0, false
	}
	c.moveFront(e)
	return e.val, true
}

func (c *LRUCache) Put(key, val int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if e, ok := c.items[key]; ok {
		e.val = val
		c.moveFront(e)
		return
	}
	if c.cap <= 0 {
		return
	}
	if len(c.items) >= c.cap {
		old := c.tail.prev
		c.detach(old)
		delete(c.items, old.key)
	}
	e := &entry{key: key, val: val}
	c.items[key] = e
	c.attachFront(e)
}

func (c *LRUCache) moveFront(e *entry) {
	c.detach(e)
	c.attachFront(e)
}

func (c *LRUCache) detach(e *entry) {
	e.prev.next = e.next
	e.next.prev = e.prev
}

func (c *LRUCache) attachFront(e *entry) {
	e.prev = c.head
	e.next = c.head.next
	c.head.next.prev = e
	c.head.next = e
}
```

容量为 2 时，依次 `Put(1)`、`Put(2)`、`Get(1)`、`Put(3)`，应该淘汰 2。更新已存在的 key 只改值并移到表头，不增加长度。键值类型换成别的，或者改成泛型，数据结构不变。

### 7. 消息队列重复消费怎么处理？幂等性设计

**参考答案**

结论：主流队列给消费者的保证是至少一次，重复来自生产者超时重试、消费者处理完但提交位点前崩溃、以及再均衡。业务侧用稳定的幂等键，把重复变成空操作。

幂等键用业务主键，例如 `订单号 + 事件类型`。生产者重试必须沿用同一个键。如果每次重试都生成新的消息 ID，消费方无法去重。

落地放在和业务写同一个本地事务里：

- 业务表本身能表达状态时，用条件更新：`UPDATE orders SET status='paid' WHERE order_id=? AND status='paying'`。影响行数为 0，说明已经处理过或状态不合法，再读一次状态区分这两种情况。
- 没有状态机时，建一张去重表，幂等键做主键，和业务写同一事务插入。主键冲突就提交一个空事务并确认消息。
- Redis `SET NX` 只能当过滤器。Redis 丢了会放行重复请求，钱和库存以数据库唯一约束为准。

外部副作用（扣款、发短信）使用同一个幂等键，并且放在本地事务提交之后，由出站任务发起。顺序是：先提交本地状态，再确认消息。确认失败导致的再次投递，会被唯一键或状态机吸收。

Kafka 的幂等生产者只保证单次生产者会话里，重试不会把同一条写进日志两遍。消费方对数据库和 HTTP 的副作用，仍然要自己做幂等。

### 8. 场景题：秒杀系统，库存超卖了怎么解决？

**参考答案**

结论：超卖是因为「先读库存再写入」不是原子的。热门 SKU 用队列把突发流量削平，数据库条件更新保证不超卖，Redis 只负责提前拦住明显没库存的请求。用户看到的成功，以数据库更新成功为准。

数据库侧一条语句完成判断和扣减：

```sql
UPDATE sku SET remain = remain - ? WHERE id = ? AND remain >= ?;
```

影响行数为 1 才算扣成。这是行锁下的条件更新。版本号乐观锁适合更复杂的读改写；纯扣库存如果用版本号，高并发下会把「还有库存但版本对不上」的请求也打失败，所以这里用 `remain >= ?`。

Redis 预减用 Lua 把比较和扣减放在一起，键不存在按无库存处理，避免对空键 `DECR` 得到负数：

```lua
local n = tonumber(ARGV[1])
local left = tonumber(redis.call("GET", KEYS[1]) or "-1")
if left < n then
    return -1
end
redis.call("DECRBY", KEYS[1], n)
return left - n
```

活动开始时用数据库库存初始化这个键，不要给它一个会提前消失的 TTL。Redis 重启后在重新装载完成前保持拒绝，避免空窗里继续放行。

队列按 `sku_id` 分区，同一个 SKU 的扣减落在可控的消费并发上，数据库的写入速度就被挡住了。消费者里仍然做条件更新。更新失败就把 Redis 加回去，订单失败。接口可以先返回「排队中」，结果由消费者写完再通知。队列解决的是峰值，原子性仍然在 SQL。

同一用户同一活动加唯一键，挡住重复下单。已经超卖时：先停售，按订单创建顺序保留不超过真实库存的已支付订单，其余取消并退款，再用数据库库存重灌 Redis。取消规则要确定，不能随机挑订单。

### 9. gRPC 和 HTTP/2 了解吗？对比一下

**参考答案**

结论：HTTP/2 是传输协议，gRPC 是默认跑在 HTTP/2 之上的 RPC 框架。对比的是「裸的 HTTP 接口」和「带 IDL 的 RPC」，两层叠在一起，不是二选一的同一层协议。

HTTP/2 把连接拆成二进制帧和多条流，一条 TCP 连接上可以同时跑多个请求，头部用 HPACK 压缩，流有自己的流量控制。它仍然是方法、路径、头和正文，不规定序列化，也不规定服务定义。

gRPC 在这个传输上规定了 protobuf IDL、四种调用（一元、服务端流、客户端流、双向流）、deadline、metadata，并用 trailer 里的 `grpc-status` 返回业务状态。拦截器用来做超时、重试和监控。多路复用、头部压缩和流式都来自 HTTP/2，契约和代码生成来自 gRPC。

选型可以按调用方来。内部服务、接口要强约束、需要流式时用 gRPC。给浏览器或外部合作方、希望用 curl 就能看的接口，用 HTTP JSON；浏览器里要走 gRPC 时，一般用 gRPC-Web 或网关，因为页面脚本拿不到完整的 trailer 语义。

有两个容易漏的点。第一，HTTP/2 的多条流共享一条 TCP，一个丢包会让这条连接上的流一起等重传；要按流隔离丢包，得换到 QUIC 上的 HTTP/3，gRPC 也有对应实现。第二，gRPC 习惯长连接，四层负载均衡只在建立连接时分配一次，之后这条连接上的请求都进同一个后端。要按请求均衡，用客户端负载均衡，或者用能识别 HTTP/2 的代理。字节开源的 Kitex 常见路径是自有 RPC 协议配合 Thrift 或 Protobuf，同时可以接入 gRPC。内部服务怎么选，把协议、IDL 和负载均衡这三件事对齐即可。

### 10. 你说你做过服务治理，熔断降级怎么实现的？

**参考答案**

结论：熔断是调用方保护自己的状态机；降级是熔断或开关打开之后，用一个事先定义好的退路。读请求可以退回缓存或空结果，下单和扣库存没有安全的假成功，只能快速失败或进队列。

状态机有三态。关闭时请求正常发出，滑动窗口统计系统错误和超时，业务错误（参数不对、没库存）不计入。窗口内请求数达到最小样本量，且错误率或连续失败达到阈值，进入打开。打开期间直接走退路，经过一段冷却再进入半开。半开只放少量探测，成功则关闭，失败则回到打开。最小样本量用来避免流量很低时，一两次失败就把电路断开。

和熔断绑在一起的还有超时和舱壁。超时要短于用户侧的总预算，否则熔断还没打开，goroutine 已经堆在下游。舱壁用信号量限制同时在途的调用，慢调用占不满整个进程。重试只发生在关闭状态，并且要有次数和预算；打开之后重试会把下游按住。

降级开关放在配置里，大促可以手动关掉评价、推荐、优惠试算这些非核心依赖。自动熔断和手动开关走同一套退路，避免两套逻辑。

字节开源的 Kitex 在治理中间件里提供熔断，哨兵和自研滑动窗口也是同一套状态机。面试时讲你实际上用的那一个：统计口径、阈值怎么定的、半开放过多少探测、退路返回什么。阈值没有统一默认值，按这个依赖的 SLO 来定。

### 11. 场景题：数据一致性要求高，本地事务和分布式事务怎么选？

**参考答案**

结论：不变式能放进一个数据库分片，就用本地事务。跨服务时，电商链路上常用「本地事务写出站消息」，再加消费端幂等和对账。XA 只适合参与者少、事务短、吞吐要求不高的场景。一致性要求高，指的是不丢单、不超卖、账能平，不是必须上两阶段提交。

本地事务是 InnoDB 的单库 ACID，回滚是真的回滚。订单和订单明细如果按同一个 `user_id` 分片，可以放在一个本地事务里。库存按 SKU 分片、订单按用户分片时，扣库存和建单天然不在一个库，这才需要跨库方案。

跨库按不变式来选：

- 出站表：业务写入和待发消息在同一个本地事务里提交，转发进程再投递消息。消费端按幂等键处理。消息丢了会重试，重复了会被状态机吸收。适合下单后通知库存、积分、搜索索引。
- TCC：Try 预留资源，Confirm 确认，Cancel 释放。预留和确认都要幂等，还要处理空回滚（Cancel 先于 Try）。适合余额、库存这种必须先占住的资源，业务改造成本高。
- Saga：每步一个本地事务，失败按相反顺序补偿。适合步骤长、允许中间状态被看到的流程，补偿本身要可重入。
- XA：准备阶段持有锁，协调者故障会堵住参与者。核心下单链路的峰值上很少用它。

用户可见的状态要落在状态机上，例如「已下单、库存确认中、已支付」。中间状态允许被读到，但钱和库存的最终数字要有对账任务，发现出站消息和下游结果不一致就补单或冲正。

### 12. Go 的 goroutine 调度模型了解吗？

**参考答案**

结论：Go 用 GMP 在用户态调度。G 是 goroutine，M 是操作系统线程，P 是逻辑处理器。执行 Go 代码时 M 必须绑定一个 P，P 的数量由 `GOMAXPROCS` 决定，默认等于机器的 CPU 数。

每个 P 有自己的本地运行队列，另外有一条全局队列。M 在当前 P 上循环取 G：先看本地，也会周期性地看全局，避免全局队列里的 G 饿死；本地没有可运行的 G 时，从别的 P 偷走大约一半本地队列，这就是 work stealing。

阻塞分两种。网络 IO 把 G 挂到 netpoller（Linux 上是 epoll）上，M 不进入阻塞，可以继续跑别的 G，fd 就绪后再把 G 放回队列。系统调用会把当前 M 一起堵住，这时 P 可以解绑，交给别的 M 继续跑这条 P 上的队列；系统调用返回后，G 再去抢一个 P，抢不到就进全局队列。所以 M 的数量可以多于 P。

sysmon 是一个不需要 P 的监控线程。它把卡在系统调用里太久的 P 夺走，也负责抢占运行过久的 G。Go 1.14 之后抢占是基于信号的异步抢占，没有函数调用的死循环也能被打断。goroutine 初始栈大约 2KB，按需扩缩。

容易说漏的一点：GMP 管的是谁在跑，不管对象怎么回收。goroutine 泄漏是 G 一直停在等待态，例如 channel 没有人收、context 没有取消，调度器不会把这种 G 自动清掉。

**追问：三色标记**

Go 的 GC 是并发的三色标记清除，不分代，也不移动对象。白色是没访问过，灰色是访问过但子对象还没扫完，黑色是子对象已经扫完。从根（全局变量和各 G 的栈）把对象标灰，再把灰色扫成黑色。

标记和用户代码并发进行。Go 1.8 起在堆上写指针时使用混合写屏障：新指向的对象要标灰，被覆盖掉的旧对象也要标灰。这样收尾时不必把所有栈再扫一遍。标记开始和标记结束仍有很短的 STW，清扫和分配并发。分配比标记快时，用户 G 会被拉去帮忙标记，延迟会出现抖动。碎片靠分配器的 size class 缓解，因为对象不移动。

### 13. 有看过 Go 源码吗？印象最深的是哪个部分？

**答题思路**

只讲一处你真的读过、对方追问还能往下走的代码。按「它解决什么 → 核心数据结构 → 一条路径 → 一个坑」来说，控制在三分钟。

如果读的是调度器，可以讲 `schedule` / `findrunnable`：本地队列、全局队列、netpoller 和 work stealing 怎么串起来，以及系统调用为什么要把 P 让出去。

如果读的是 channel，可以讲 `hchan`：环形缓冲、`sendq`/`recvq` 上的 sudog、一把运行时锁。发送时如果已有接收者在等，直接拷贝过去；缓冲有空位就入队；否则挂起。关闭会唤醒等待者。再补一条语义：向已关闭的 channel 发送会 panic，从已关闭的 channel 接收会得到零值。nil channel 上的收发会一直等。

如果读的是 map：经典实现是 bucket、tophash 和溢出桶，装载因子大约 6.5 时渐进式扩容。Go 1.24 起运行时改成了 Swiss table。你按自己读的版本讲，并主动说明版本。map 本身不是并发安全的。

没读过源码就说最近在看哪一块、看到了哪一层，不要把调用栈背成「我读过 runtime」。

### 14. 平时怎么学习？最近在看什么技术？

**答题思路**

用「一个和工作相关的主题，加上一次验证」来回答，不要报一串名词。

1. 主题从线上问题来，例如超时、调度、索引或一致性。
2. 材料的顺序：官方文档和源码，然后是设计说明和故障复盘，最后才是文章。
3. 学完用一次：在项目里验证，或者写一个很小的实验把行为跑出来。
4. 「最近在看」准备三分钟：为什么看、机制是什么、哪个点你还没想清。举例的形状是「最近把 Go 调度和线上超时对上号」，换成你真实在看的内容。

和这个岗位同向的主题包括 Go 运行时、MySQL/Redis、消息幂等和容量。选你能讲到细节的那一个。

### 1. 先自我介绍一下，说说你做过最有挑战的项目

**答题思路**

开场十五秒带过年限和技术栈，剩下的时间只讲一个项目。按下面的顺序，数字和组件都用真实的：

1. 业务目标和你的角色，说清哪些是你做的。
2. 约束：峰值口径、数据量、一致性要求、当时不能改的遗留系统。
3. 难点只留一个，例如热点写入、跨库一致、或延迟突然变长。
4. 方案和你放弃的备选，各用一句话说明取舍。
5. 结果：错误率、延迟、成本或人力，用你能打开监控对上的数。
6. 如果重做，会改哪一个决定。

这个项目要和后面的架构演进是同一个，避免讲着讲着换成另一个系统。

### 2. 那个高并发项目，技术架构是怎么演进的？

**答题思路**

按时间讲三段就够，每一段只有一个瓶颈、一个动作、一个结果。不要一口气把缓存、分片、网格全报上来。

可以套这个形状，但只保留你真的做过的阶段：

1. 早期单库，慢查询或连接数先到顶。动作是索引、读写分离、把热读放进缓存。
2. 主流程被非核心写或扇出堵住。动作是把通知、计数或 Feed 扩散放进消息队列，核心事务留在本地。
3. 单库写入或单机房成为上限。动作是按访问维度分片，按领域把服务拆开，并做同城多可用区。容灾要讲到：应用无状态多实例、数据库怎么切换、缓存冷了之后如何限制回源。没做过多机房，就说清当前的故障域，以及你已经看到的下一个瓶颈。

服务拆分的时机是发布耦合或容量模型已经不同，不是用户数到了某个整数就拆。每段都准备一个你当时拒绝过的方案，例如过早拆服务、或用分布式事务硬把两个库绑在一起。

### 3. 场景题：如果让你设计一个 Feed 流系统，核心挑战是什么？

**参考答案**

结论：关注流的核心矛盾是粉丝规模差几个数量级，单独写扩散或单独读扩散都会在某一端爆掉。先确认面试官说的是关注流还是推荐流。抖音首页推荐的主路径是召回和排序；下面按关注流来讲。

挑战集中在这几件事：

- 写放大和读放大。普通人发帖如果写进每个粉丝的收件箱，大 V 一次发布会变成百万级写入。如果改成读的时候现拉，关注了很多大 V 的用户会在一次打开里打满下游。
- 分页要稳定。用 `(时间, 帖子 ID)` 做游标。用偏移量翻页，新帖插入时会重复或漏掉。
- 删除、取消关注、可见性变更之后，时间线上不能继续露出。这是异步扇出下的一致性问题。
- 存储成本。每个人一份收件箱，活跃用户和长历史会把 Redis 和磁盘都抬上去，所以收件箱里只存 ID，正文单独放。
- 热点。一条突然被打开的内容，读路径会打到同一个 key。

推荐流如果被追问，挑战换成候选召回、排序特征、样本和展示去重，推拉模型覆盖不了那条链路。

### 4. 推拉结合模式，具体怎么实现？

**参考答案**

结论：粉丝数低于阈值的作者，发帖后异步写进粉丝的收件箱；超过阈值的作者只写自己的发件箱，读者打开时再拉最近的几条，和收件箱按时间归并。阈值按粉丝数和单次扇出预算来定，不设一个放之四海的固定人数。

存储拆开：

- 正文按 `post_id` 放在数据库或 KV，时间线里只放 ID。
- 收件箱是每个用户一个 ZSET，member 是 `post_id`，score 是时间戳。
- 发件箱是每个作者一个 ZSET，保留最近一批帖子，同样只存 ID。
- 关注关系里，普通作者保留粉丝列表供扇出；用户侧保留「我关注的大 V」这份小名单，读的时候只拉这份名单。

写路径：帖子先落库。普通作者发一条消息，扇出任务按页读取粉丝，批量写入收件箱，不在发布接口里同步写完。大 V 只写发件箱，不进入扇出。粉丝数异步更新，越过阈值后新帖不再扇出，旧收件箱可以懒清理。

读路径：从收件箱取一页，再对每个关注的大 V 取最近若干条，在应用内按 `(score, post_id)` 做多路归并，用这个二元组当游标。单次拉取的大 V 人数和每人条数要有上限。

删除和取关：帖子加墓碑，读的时候过滤；收件箱里的 ID 异步删。取关后懒删除，避免一次取关扫描整个收件箱。只给最近活跃的粉丝推、不活跃的用户下次打开时重建，是进一步省扇出的做法，活跃的定义用最近打开时间。

发布接口返回成功时，粉丝时间线是最终一致的。这个延迟要在方案里说清楚。

### 5. 场景题：用户量从 100 万涨到 1 亿，架构怎么演进？

**参考答案**

结论：先把用户数换成日活、峰值 QPS、数据量和读写比，再决定要不要引入新组件。演进的顺序是：把单库做稳，再按领域拆服务，最后才水平分片，并补上同城容灾。

100 万用户、日活只是其中一部分时，一个模块化的单体或很少的几个服务就够：MySQL 一主一从，热读用 Redis，应用无状态，图片和视频走对象存储和 CDN。这一阶段把慢 SQL、索引和连接池做对，收益最大。

到千万级，垂直拆库，把发布节奏和容量模型不同的域分开，例如用户关系、内容和交易。非核心写进消息队列。限流、超时和基础监控在这个阶段进框架。Feed 如果还是纯写扩散，大 V 会在这个量级先出问题，开始改成推拉。

到亿级，按 `user_id` 这类稳定且高基数的键水平分片，订单号里带上分片位。关注流用推拉，计数和库存这种热行单独治理，不跟普通帖子表抢一行锁。服务按数据所有权拆开，每个服务自己的库。

容灾至少做到同城多可用区：应用多副本，数据库有切换演练，缓存失效时限制回源，避免击穿把主库打满。异地是冷备还是多活，看 RPO/RTO。多活要解决写入路由和冲突，不是多部署一套就完成了。

直播和爆款按峰值准备容量，不按日均。推荐系统如果有，和关注流的读路径分开，避免排序把时间线接口拖死。

### 6. 缓存一致性怎么保证？Cache-Aside 和 Write-Through 选哪个？

**参考答案**

结论：商品详情、用户资料、Feed 这种读多写少，用 Cache-Aside：更新数据库，再删除缓存。Write-Through 适合数据放得进缓存、写完要立刻被别人读到、而且写入口只有缓存这一条的数据。库存和余额的正确性放在数据库，缓存只做展示。

Cache-Aside 的读路径是先读缓存，未命中再读库并回填。写路径是先提交数据库，成功后再删缓存。并发更新如果都回写缓存，后完成的旧值会覆盖新值；删除让下一次读从数据库重建，这个窗口更小。

还剩下两种不一致：

- 数据库已提交，删除缓存失败。缓存继续吐旧值。删除要有重试；更稳的是订阅 binlog，提交之后由消息再删一次。TTL 用来兜住消息也丢了的情况。
- 一个读请求未命中并读到旧行，同时写请求已提交并删了缓存，读请求再把旧行回填。窗口很窄。binlog 删除若发生在回填之后，能再清掉；回填更晚时，用 Lua 比较版本，旧版本不能覆盖新版本，TTL 继续兜底。

延迟双删是在更新前后各删一次，中间睡一会儿，用来盖住回填。睡眠时间是估计的，第二次删除失败就不起作用。它可以当补充，可靠的失效来自 binlog 加版本比较。

Write-Through 是写缓存时同步写数据库，两边都成功才返回，读都走缓存。写延迟等于两边之和。应用若绕过缓存直接改库，这套一致性就没了，所以写入口要唯一。热点 key 被删除后会有击穿，重建时用 singleflight 把并发回源合成一次。

### 7. 场景题：热点 key 问题，怎么发现和解决？

**参考答案**

结论：在代理或 SDK 上统计访问，产出热 key 名单再下发；治理时把读热、写热、大 key 分开。线上不要用 `MONITOR` 做常态采集，它会把全部命令打出来，本身就能打满 Redis。

发现可以放在三处。接入层或 Redis 代理对 key 做本地 top-K 或 Count-Min Sketch，每秒汇总，超过阈值就进名单。同时看单个分片的 CPU、网卡和慢日志是否倾斜，确认热点落在哪台。`redis-cli --hotkeys` 依赖 LFU 淘汰策略，而且是抽样，只适合短时间排查。大 key 用 `MEMORY USAGE` 或 `--bigkeys` 来找，拆值和限长，跟热 key 不是同一件事。

解决按读写来：

- 读热：进程内很短的 TTL 缓存，加上 singleflight，同一个 key 的并发回源并成一次。名单之外的 key 不进本地缓存，避免把内存占满。
- 仍然热：把 key 拆成多份，读随机一份，写时更新全部，或者写一份再同步到其他份。份数按读 QPS 和单分片能力来算。
- 写热的计数：本地聚合后批量刷，或拆成多个计数键再求和。
- 隔离：热 key 所在分片加副本或迁到独立节点，避免拖垮同节点的其他键。

名单、阈值和本地缓存的 TTL 都要能动态改。面试时把这条链路讲完即可，不必猜某个组内部系统的名字。

### 8. 分库分表，sharding key 怎么选？数据迁移怎么做？

**参考答案**

结论：分片键选大多数查询和事务里都会带上、取值稳定、基数高的字段。电商里「我的订单」用 `user_id`，并让订单号能反推出分片，避免查一单先广播所有库。

选择时看四件事：

- 查询要带得上。订单和订单明细用同一个 `user_id`，才能在一个分片里做本地事务。
- 取值不变。手机号、昵称会改，改一次就要跨分片搬数据。
- 分布均匀。对 `user_id` 做哈希，避免按注册时间范围分片，把新用户都打进最新的库。
- 超级商家、超级主播这种单个取值本身就是热点时，单独拆走或加盐，加盐之后的查询要能把盐枚举出来再聚合。

按订单号查询：把分片位编进订单号。商家维度的列表是另一条访问路径，冗余一张按 `merchant_id` 分片的索引，用消息异步维护。全局订单号不要用各个库的自增。

迁移用增量追平，而不是停机拷贝：

1. 新库表和路由准备好。扩容尽量按 2 的幂增加分片，一个键只迁到一个确定的新位置。
2. 存量按主键范围分批拷贝，增量订阅 binlog 追平。
3. 按分片对行数和关键字段做校验，再灰度读新库做比对。
4. 先切读，稳定后切写。旧库保留一段可回滚的时间。
5. 应用双写也能做增量，但失败组合更多，要用对账把两边补齐。

切流前，跨分片 join 和跨分片事务要先改掉：要么改成单分片能完成，要么改成异步加对账。

### 9. 你说你做过监控告警，指标体系怎么设计的？

**参考答案**

结论：先定用户能感知的 SLI，再往下拆服务、依赖和资源。告警打在症状上，每个告警有负责人。标签的基数要可控，用户 ID、订单号不能放进指标标签。

电商链路可以按四层来设计，名字换成你系统里真实的：

- 业务：下单成功率、支付成功率、库存扣减失败率。这是要叫人的指标。
- 服务：核心接口的 QPS、错误率（按错误码拆开）、P99。对应 RED：速率、错误、耗时。
- 依赖：数据库慢查询和锁等待、Redis 延迟和命中率、消息堆积和消费失败。
- 资源：CPU、内存、goroutine 数、GC、连接池占用。对应 USE：利用率、饱和度、错误。饱和度看的是队列和等待，不只是 CPU 百分比。

告警分成叫醒和工单。成功率下降、P99 越过 SLO、消息堆积持续变长，这些叫醒；CPU 偏高进工单。核心 SLI 看燃烧率和持续时间，毛刺不会立刻叫人。阈值来自错误预算和历史峰值，不拍一个整数。

每条叫醒告警挂到一张可以下钻的面板：从业务指标到接口，再到依赖和实例。日志负责单次错误的现场，trace 负责一次请求的时间分布，指标负责趋势。三者用同一个请求 ID 串起来。

面试时拿一条你真实加过的告警讲：它原来漏了什么、你改了哪条 SLI、之后误报是少了还是故障更快被发现。

### 10. 场景题：线上出现内存泄漏，怎么定位？

**参考答案**

结论：先看 `HeapInuse` 和 goroutine 数是不是在流量平稳时仍然单调上涨。RSS 单独升高，可能是运行时还留着空闲页，先不要当成泄漏。

定位按这个顺序：

1. 用监控把曲线和发布时间、配置、流量对齐。一台涨还是全部涨，决定是实例问题还是代码路径问题。
2. goroutine 数上涨时，先看栈。`/debug/pprof/goroutine?debug=1` 能看出大量 G 停在同一个 channel、锁或 RPC。这种泄漏不在堆的业务对象上，而在停不下来的 G 和它的栈。
3. 堆上的活对象上涨时，抓两份相隔一段时间的 heap profile，用 `-base` 看增量，关注 `inuse_space`。`alloc_space` 高但 `inuse` 稳定，是分配得勤，不是泄漏。

```bash
go tool pprof -inuse_space http://127.0.0.1:6060/debug/pprof/heap
go tool pprof -base heap.old heap.new
```

服务如果没用 `DefaultServeMux`，要自己把 `net/http/pprof` 的路由挂到内部端口。

Go 里常见的根因有：全局 map 或 `sync.Map` 只增不删；把大切片切出的小切片长期存下来，底层数组被拖住；`time.Tick` 或没有 `Stop` 的 `Ticker`；`context` 没取消导致 goroutine 退出不了；响应体没关闭。堆曲线是平的、RSS 仍在涨时，再看 cgo、线程数和 `StackSys`，堆分析看不到堆外内存。

一次 profile 用来定位调用栈，连续曲线用来证明它在漏。修完用同一条 `HeapInuse` 曲线验收。

### 11. 微服务拆分，边界怎么划？遇到过什么坑？

**参考答案**

结论：按业务能力和数据所有权划边界。一个服务独占自己的表，服务之间走 API 或事件。两个功能如果每次请求都要在同一个事务里改同一批表，就先留在一起。

划分时看三点。它们是不是一起变更；发布节奏和容量是不是相同；故障时能不能单独降级。Feed 扇出、通知这种容量模型和交易完全不同的模块，适合先拆出去。按技术层拆成「接口服务」和「数据服务」，两边仍然绑在一起，只是多了一次网络。

常见的坑，选你真正遇到的一个展开，没拆过就讲单体里已经看到的耦合：

- 拆了进程，仍共用一个库，两边直接改同一张表，发布还是绑死。
- 同步调用链太长，尾延迟和故障会级联。超时预算要沿调用链递减，下游的超时要短于上游。
- 为了保住原来的本地事务，引入 XA，把峰值路径堵住。
- 循环依赖，一个需求要同时发布两个服务。
- 没有统一的 trace，出了问题只能对日志时间。

拆分的时机是单体的发布和容量已经互相拖累，不是一开始就拆成很多个仓库。

### 12. 对字节的技术栈有了解吗？

**答题思路**

只讲你能对上公开资料、并且和你经验接得上的部分，再反问这个组实际用什么。

公开资料里比较稳的是：业务后端大量用 Go；RPC 框架是 Kitex，IDL 常见 Thrift，也支持 Protobuf；HTTP 框架是 Hertz；网络库是 netpoll。服务治理里的超时、重试、熔断、负载均衡做在 RPC 框架里。存储侧 MySQL 和 Redis 很常见，公开分享里还有 Abase 这类自研分布式 KV。消息队列公开场合能看到 Kafka、RocketMQ，以及各团队自己的平台。

把你用过的 Go、MySQL、Redis、消息队列接到这些对应物上，说明迁移的是模型（超时预算、幂等、分片），不是包名。没把握的内部代号不要背。问清楚对方组的 RPC、主存储和消息队列，后面的项目例子就按那一套来对齐。

### 13. 如果入职，你希望负责哪块业务？

**答题思路**

选一条和你经历接得上的，并说明你能扛的问题是什么。两条都站得住的例子：

- 交易链路：下单、库存、支付回调。你能讲条件更新、幂等和消息。
- 高并发读：Feed、商品详情、直播间峰值。你能讲缓存、热 key 和容量。

然后说你希望先把这条链路的数据模型和故障案例补齐，再独立负责其中一段。不要回答「都可以」。如果面试官介绍的是基础设施，就把你的选择说成「把业务里做过的稳定性，做到这条核心链路上」，和你的真实意向保持一致。

### 14. 你觉得自己和字节的匹配度在哪里？

**答题思路**

用前面已经讲过的项目当证据，分成匹配和差距。

匹配点挑两个就够：Go 做过高并发服务；在库存、订单或缓存上处理过正确性和峰值。每个点用一句结果收住。

差距直接说。例如没做过直播或推荐，就说明你准备怎么补：先读核心链路的表结构和 oncall 记录，第一个月能独立排查一条慢请求。匹配度是「经验对得上、缺口说得清」，不是把岗位描述重读一遍。

## 三面

### 1. 简单介绍一下自己，说说你的职业规划

**答题思路**

介绍只用三句：年限、Go 和业务方向、一个代表项目的结果。然后把时间留给规划，规划要和这个介绍是一条线。

1. 过去几年你实际在解决什么问题，例如峰值、一致性或稳定性。
2. 未来一到两年：把哪项能力补到能独立负责一段链路。说一个具体缺口，例如多可用区容灾、或服务治理，不要说「继续学习」。
3. 三到五年：能对一条链路的容量和故障域做决定，并能带一个很小的小组把设计落地。
4. 为什么是这个组：抖音电商有突发流量和强一致的交易数据。如果对方组做基础设施，就把规划接到「把业务里验证过的稳定性做成平台能力」。这必须是你的真实方向；你更想深耕交易，就明确说交易。

不要报职级号码，也不要编一个和简历对不上的方向。

### 2. 为什么想离开现在的公司？

**答题思路**

用拉力来讲：你想要的规模、技术深度或业务，当前环境给不到。结构可以是：

1. 现在的工作你已经负责到哪一步，哪些能力已经练过。
2. 触达不到的部分是什么，例如流量规模、分布式复杂度、或更完整的工程体系。说事实，不评价具体的人。
3. 字节电商的哪一段正好补上这个缺口。
4. 为什么是现在，而不是再等一年。

薪资留到专门的问题里。离职原因和职业规划要能对上，避免这边说想做分布式，那边说因为加班才走。

### 3. 你觉得自己最大的技术优势是什么？

**答题思路**

只选一个，并用一个项目片段证明。两个比较贴这个岗位的选择：

- 线上问题能从现象追到一层机制，再改掉。结构是：症状、你看的第一张图、定位到的原因、改完的结果。
- 高并发下把数据写对。结构是：哪条不变式、你用的条件更新或幂等、放过什么方案。

第二个优点用一句话带过即可。避免「学习能力强」「沟通好」这种没有证据的说法。优势要和简历上的项目是同一个，方便对方追问。

### 4. 场景题：给你一个模糊的需求，怎么拆解和推进？

**参考答案**

结论：先把「做成什么样」写成可以验收的标准，再切一条能上线的主路径，依赖和风险写在明面上。

1. 复述目标、用户、明确不做的事、截止时间和成功指标，直到产品和你的说法一致。
2. 未知拆成两类：现在不定就会走错的，以及可以在第一版之后再定的。
3. 画出主路径和失败路径。交易类至少包括超时、重复请求、库存不足。
4. 垂直切一个最小版本，里面包含表、接口和验收方式，而不是先做完所有底层。
5. 每个外部依赖有负责人。数据口径、容量和兼容性是最常见的风险。
6. 里程碑按能演示的增量来排。范围变化时改书面的成功标准。

推进时你自己盯关键路径和阻塞，每天用很短的时间同步，不把进度隐藏在「正在做」里。

### 5. 你做过最有成就感的项目是什么？

**答题思路**

选一个你能讲清个人贡献、并且有业务结果的项目。从 0 到 1 可以讲，但第二句就要落到业务价值，不要停在「搭了一个平台」。

1. 当时的业务问题是什么，谁在痛。
2. 你负责的边界，协作者做了什么，分开说。
3. 最难的决定是什么，你放弃了什么。
4. 结果用业务语言收：人效、耗时、错误率、成本或故障次数。数字用真实的，对方追问口径时说得清统计方式。
5. 如果重做会改哪里。这一句用来表现判断，不是自我否定。

没有量化数据时，讲一个可核对的前后对比，例如原来要人工对账、后来哪一类差错消失了，不要临时编一个百分比。

### 6. 如果让你带一个 3 人小组，你怎么安排工作？

**答题思路**

三个人的小组用轻量的做法，目标对齐比流程重要。

1. 和上级确认目标、截止时间和验收标准，写成几条可检查的结果。
2. 按可以独立交付的纵切来分，每个人包含自己那块的接口、数据和失败处理。避免一个人只写接口、另一个人只写 SQL。
3. 你自己留下集成和最不确定的那块，例如一致性和容量。
4. 先定接口和数据口径，再并行写。每天十五分钟同步阻塞，代码评审看正确性、幂等和边界。
5. 风险出现时你去拆依赖，进度看的是能否验收，不是看谁留下得晚。

技术分享只分享刚遇到的坑。三个人不需要重的项目管理工具，一块看板就够。

### 7. 对字节的业务有了解吗？

**答题思路**

先讲你作为用户能确认的链路，再问这个组负责哪一段，最后把你的经验接上去。

抖音电商是内容把人带到商品：短视频和直播里出现商品卡片，用户提单、支付，然后是履约和售后。和传统货架相比，流量更随内容突发，一个直播间的爆品会把库存、订单和下游同时打热。技术上要同时守住两件事：峰值容量，以及库存、订单、资金不能写错。

本地生活是另一条业务，履约方式和电商实物不同，不要合成一个系统来讲，除非你确实做过。

讲完问对方负责的是交易、库存、营销价格、直播间还是商家侧。然后用一句你的项目对齐，例如你处理过热点库存或高并发读。不了解的内部产品不要猜名字。

### 8. 你期望的工作节奏是什么样的？

**答题思路**

给出一个你能接受的真实节奏，并和后面的加班问题保持一致。

可以这样说：大促、发布和故障时可以集中投入；日常希望需求有优先级，oncall 有轮换，做完有复盘。你在意的是结果和故障处理的效率，希望节奏是可预期的。

然后反问一句对方组的发布窗口和 oncall 频率，用对方的回答判断，而不是在面试里把节奏谈成口号。

### 9. 你觉得后端工程师的核心竞争力是什么？

**参考答案**

结论：核心竞争力是在约束下把不变式写对，并把延迟和故障控制在业务能接受的范围内。语言和框架会换，这项判断可以带走。

具体是四件事。第一，不变式进了存储和状态机：库存不为负、订单状态只按允许的方向转移、账能够对平。第二，知道瓶颈在 CPU、锁、网络还是下游，并且能量化、能用压测验证。第三，部分失败时的行为是定义过的：超时、重试预算、幂等和降级。第四，出了问题能从一张业务曲线走到一次请求。

在电商里，这表现为大促前说得清容量，大促中订单和库存不写错，出问题能定位到某一层，而不是先重启试试。

### 10. 五年后你想成为什么样的人？

**答题思路**

和开场的职业规划是同一条线，只是把「能做什么决定」说得更具体。

一个站得住的说法是：五年后能够负责一条核心链路，对它的容量、一致性和故障域做出决定，并且带着一个很小的小组把设计落到线上。评价自己的标准是这条链路的错误率、延迟和故障处理时间，不是职级号码。

补一句你已经在做的事，证明这条线不是现场想的。例如你现在已经在负责某个服务的容量和故障，接下来要补的是多机房或平台化。方向如果是基础设施，就说你希望别人在你的平台上少踩你踩过的坑。

### 11. 手里有其他 offer 吗？

**答题思路**

如实说，不编造，也不贬低其他公司。

有 offer：说阶段（口头还是书面）和业务方向，以及你为什么把字节放在前面比较。具体薪酬数字等对方问到薪资时再对齐口径，避免两道题的数字互相矛盾。

没有 offer：说你还在看哪些方向，字节是你当前更想去的原因。不要用虚构的 offer 抬价，HR 核对起来会伤可信度。

### 12. 期望薪资是多少？

**答题思路**

先确认对方问的是月薪还是年包，年包里是否包含奖金和股票。然后给一个区间，而不是一个没有解释的单点。

区间的依据是你现在的总包、城市和这个级别的市场，面试前自己算清楚。复习时不写死数字，现场用你核算过的范围。下限也要提前想好，那是你真的可以接受的数。

如果前面说了其他 offer，这里的口径要和那个 offer 的结构一致。细项可以留给 HR，但区间本身在这轮要说得出口。

### 13. 对加班怎么看？

**答题思路**

和「期望的工作节奏」同一套说法。大促、发布窗口和线上故障，你可以一起扛，这是电商峰值的一部分。长期没有目标、只靠拉长工时的情况，你会先问清原因，把重复的人工和对不齐的需求收掉。

表态用你的真实边界。可以接受紧急投入，就明确说出来；不能接受长期通宵，也在这里说，避免入职后预期不同。问一句对方组最近一次峰值是怎么排班和复盘的，比抽象地讨论加班有用。

### 14. 有什么想问我的？

**答题思路**

准备四件你真的想知道的事，按这个顺序问：

1. 这个组负责抖音哪一段链路，这一年最大的稳定性或一致性问题是什么。
2. 线上实际用的 RPC、主存储和消息队列是什么。
3. 新人三个月，你希望他独立承担哪一块。
4. 团队大概多少人，oncall 和发布节奏是怎样的。

薪资和加班如果前面没问清，可以放在最后补一句。第一问不要只用待遇开场。对方回答之后，用你的项目接一句，表示你听进去了，而不是在念问题清单。
