> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

一面还行，问得不算装。召回、粗排、精排、重排能聊明白就过半。

二面开始抠项目和落地。别拿八股糊弄。没真做过特征一致性、多目标融合、AB 实验，容易被追到哑火。

三面明显看中台视野和 Agent 落地边界。要讲清谁来兜底、谁来拍板、怎么不把线上搞炸，而不是吹 Agent 取代算法。整体偏工程，算法深度也有，但更看重你懂不懂推荐系统怎么赚钱、怎么跑稳、怎么扩到多条业务线。

## 一面

### 1. 自我介绍

**答题思路**

控制在两分钟，按「做什么的 → 最近一条推荐链路 → 和中台岗位的关系」来讲。

1. 一句背景：工作年限，以及你实际负责的是召回、特征、排序还是平台。只报线上用过的组件。
2. 一个项目：服务的场景、你个人改过的那一段、候选规模和延迟大概在什么量级。数字要能指回监控或实验报告。
3. 留两个可深挖的点，例如多路召回怎么融合，或训练用的特征和服务用的是不是同一份。
4. 收尾说明你为什么看推荐中台：要同时对效果、稳定性和多业务复用负责。

不要报没做过的模型名，也不要编职级和薪资。

### 2. 项目介绍

**答题思路**

三分钟内讲完一个你能防守的项目，顺序固定。

1. 业务问题：优化的是时长、留存、转化里的哪一个，约束是延迟、候选规模还是审核。
2. 你的边界：模型、特征、链路、平台里你真正拍板的那一块。其余说成协作，不要讲成全部由你设计。
3. 方案：输入输出、上线前后差在哪、你放弃过的备选。
4. 结果：指标口径、实验怎么开的、相对变化。没有把握的百分比就讲指标定义和变化方向。
5. 留一个线上问题，例如特征对不齐或实验不显著，等面试官往下追。

### 3. 推荐系统中台是干什么的，你理解里它和业务的推荐系统有什么区别

**参考答案**

结论：中台提供多条业务线共用的召回、特征、排序服务、实验和样本能力。业务推荐系统决定自己的目标、内容和规则，并通过扩展点接入。

中台要稳定、可复用：统一的检索框架、特征注册和在线读取、模型发布、分流实验、曝光点击日志。业务系统变化快：类目和审核、优化时长还是转化、活动期的排序规则，都跟着业务走。

中台的成功看接入成本、复用和故障隔离，同时不能把各业务的效果做差。业务系统的成功就是该场景的指标。只被一个业务使用、还跟着活动改的逻辑留在业务侧。收进中台之后，其他业务线会一起承担它的发布和故障。

### 4. 召回、粗排、精排、重排各自解决什么问题

**参考答案**

结论：四段是在候选规模和打分成本之间逐级缩小范围。前一段把后一段打不起的候选去掉，重排再对一整刷负责。

召回从全库里用多路方法取出几千量级的候选，目标是少漏，各路分数不能互比。粗排用轻模型把合并后的候选收到几百，把算力留给精排；它和精排的目标不一致时，精排喜欢的物品会在截断时被丢掉，可以用精排分蒸馏粗排来减轻。精排对这几百个物品用重模型打准，输出点击、时长、转化等分数。重排处理的是一刷列表：去重、打散、频控、冷启动名额。精排逐条打分看不到这些列表约束。

各段的具体数量随场景变化，面试时用你自己系统的监控数字。

### 5. 多路召回一般有哪些路，向量召回和协同过滤召回怎么配合

**参考答案**

结论：多路召回用不同信号覆盖不同人群和物品，合并时按路保留名额。向量和协同过滤互补，分数不能直接相加。

常见的路有：按近期点击查相似物品的 ItemCF 或 Swing；双塔向量加 ANN；关注关系；热门和新品；类目、地域、人口属性；用内容向量补冷启动。线上协同过滤一般是物品到物品，用用户刚点过的物品查相似表。UserCF 要在线上找相似用户，规模大时更重。

协同过滤在有共现时更准，稀疏和冷启动会空。向量召回能泛化到长尾，但近邻可能只是语义像，训练数据又热门时，头部会占满近邻，需要对流行度打压。ANN 是近似检索，索引本身有召回损失，调的是召回率和延迟，没有普遍适用的一套索引参数。配合方式是每路配额，避免一路霸榜，再交给粗排统一打分。

### 6. 实时特征怎么从用户行为流里算出来，延迟要求大概多少

**参考答案**

结论：行为日志按用户分区进入流任务，用事件时间做窗口和最近行为序列，覆盖写到在线存储。端到端按秒级要求，近线计数可以到分钟级。没有统一的毫秒级默认值。

链路是埋点、消息队列、流计算、在线键值存储、排序读取。同一用户的事件进同一分区，才能保持顺序。用事件时间加水印处理乱序，用事件 ID 去重。计数和最近 K 次行为是两类状态，序列要截断。写出带事件时间，旧事件后到时不能覆盖更新的值。

刚发生在本次会话里的点击，可以由请求直接带上，不跟流的延迟绑定。训练要用请求时刻已经可见的值。流还没算完就用未来的计数，离线会虚高。

### 7. Redis 在推荐系统里一般放什么，热点物品特征还是用户画像

**参考答案**

结论：两边都放，形态不同。Redis 是热数据层。全量向量和全量历史用专门的索引和特征库，不把 Redis 当主存。

热点物品特征读多写少，而且倾斜严重，适合 Redis 加机器本地缓存，并对同一个 key 的并发回源做合并。用户实时画像、短窗口计数、短行为序列也放 Redis，按用户做 key，序列必须截断，避免大 key。

本地缓存适合允许短暂不一致的物品静态特征。频控要用的曝光次数是硬状态，各台机器各缓一份会对不齐，重排时读在线存储。热 key 来自爆款物品，大 key 来自不截断的行为列表，两类问题分开处理。

### 8. Redis 缓存和特征存储的一致性怎么处理，特征更新后缓存什么时候失效

**参考答案**

结论：实时特征覆盖写，并用事件时间拒绝旧写。批量特征按版本整体切换。TTL 只防止写入停止后永远留着旧值，不负责定义新鲜度。

在线排序读的是特征服务。Redis 里是一份热副本。更新直接写新值，避免先删再读时拿到空。批量特征发布新分区后切换版本指针，旧版本延迟淘汰，不要按单个 key 猜测该什么时候过期。

物品下架、不可推荐这种状态走物料服务，要求马上生效。统计类特征允许秒级延迟。两边不要共用一个失效时间。缓存更新只影响之后的请求。训练样本用的是请求当时打进日志的快照，不能因为缓存后来变了就回改历史样本。

### 9. MySQL 里推荐物料表怎么设计，为什么不适合把所有特征都放 MySQL

**参考答案**

结论：MySQL 存物料主数据和可推荐状态。统计特征、序列和向量放特征库与向量索引。排序链路上百物品的批量点查不要打到 MySQL。

```sql
CREATE TABLE item (
  item_id       BIGINT PRIMARY KEY,
  author_id     BIGINT NOT NULL,
  category_id   INT    NOT NULL,
  status        TINYINT NOT NULL, -- 审核中、可推荐、下架
  publish_time  DATETIME NOT NULL,
  updated_at    DATETIME NOT NULL,
  KEY idx_status_cat_time (status, category_id, publish_time)
);
```

这张表负责审核、上下架和运营查询。下架要立刻反映到可推荐集合，由物料变更通知在线过滤，不等天级特征作业。

特征列又宽又常改，实时计数更新频繁，向量和序列也不适合行存。一次排序要查几百个物品，MySQL 的连接和缓冲池扛不住这个扇出。主数据要事务，特征要高并发点查，存在一起会互相拖累。

### 10. Kafka 在推荐链路里承担什么角色，样本流和特征流怎么走

**参考答案**

结论：Kafka 传行为日志、样本和近线特征变更。在线排序是 RPC，不经过 Kafka。样本和特征分 topic、分消费组，分别看堆积。

行为 topic 按用户分区，供流任务算实时特征。请求日志里带上特征快照、实验桶、召回路和模型版本，再按 request_id 和后续的点击、播放拼接，写入样本 topic。近线特征写在线存储，可以有自己的变更 topic，不进样本 topic。

全局没有顺序，只能保证同一 key 在同一分区内有序。样本要等归因窗口，窗口没结束就标成未点击，晚到的正样本会被学成负的。堆积告警也分开：特征消费落后影响的是新请求，样本消费落后影响的是训练。

### 11. 如果线上推荐效果突然掉，你怎么分层排查，是先看召回还是先看精排

**参考答案**

结论：不固定先看召回或精排。先确认口径、埋点和变更，再看漏斗从哪一层开始断。候选数量掉了查召回和过滤；数量正常而分数或点击掉了，再查特征、精排和重排。

1. 看范围：大盘还是一个实验桶，哪一个指标，是不是只掉了某个场景。实验桶单独掉，先看实验配置。
2. 看点击和曝光的日志量。埋点丢了会表现为点击率掉，模型和召回可以是正常的。
3. 对齐模型版本、特征版本、索引版本和过滤配置。
4. 看各路召回条数、空结果率、超时和过滤丢掉的比例。这里空了，精排无法把物品变出来。
5. 候选数量正常时，看特征缺失率、精排分分布、重排规则命中率，以及最终曝光序和模型序还像不像。

同一小时的昨天作为对照。先留日志和版本，再考虑回滚。

### 12. AI Agent 能不能用来辅助推荐策略迭代，比如自动分析 BadCase、生成实验假设

**参考答案**

结论：可以辅助分析 BadCase 和起草实验假设，不能自己改线上策略。

适合的用法是：给定时间范围和场景，Agent 查曝光、召回和特征日志，把失败案例分成召回为空、特征缺失、重排打掉、重复曝光几类，每条结论附上 query 和样例 request_id。实验假设写成：改哪个已注册参数、预期哪个指标变化、哪个护栏不能坏、什么条件回滚。

假设要由负责的算法同学确认，再进小流量。一次改一个因子，否则有效了也不知道是谁起的作用。Agent 不在排序 RPC 里，也不根据线上奖励直接改全量权重。

### 13. 手撕算法：给一个候选分数列表，按多目标权重融合后返回 TopK，要求说明稳定性和边界处理

**参考答案**

结论：融合分用加权和，按分数降序取 K 个。分数相同则保留输入中更靠前的候选。缺失和无穷大不参与，不能当成 0。各目标先校准到可加的尺度，再乘权重。

稳定性靠第二关键字，用原始下标，不依赖排序算法本身稳不稳定。边界是：K 小于等于 0 或列表为空返回空；K 大于候选数则全部返回；某一行的分数个数和权重不一致、出现 None、NaN、Inf，就跳过该行；权重本身不是有限数就拒绝计算。权重允许为负，用来做抑制，因此不能再把权重归一化，和为 0 时还会除零。

尺度不一致时加权和没有意义。点击率 0.2 和观看秒数 40 直接相加，时长会主导结果。先变成校准后的概率、期望时长或路内可比分。去重是另一道题，这里相同 id 的两行都保留。时间 O(n log n)，空间 O(n)。n 很大时可以换成大小为 K 的堆，时间 O(n log K)。精排之后 n 通常不大，全排更直接。

候选 A 的分数是 0.2 和 0.9，B 是 0.8 和 0.1，权重各 0.5，则 A 为 0.55，B 为 0.45。把权重改成明显偏向第一项目标，顺序会反过来。换权重是业务取舍，要走实验。

```python
import math


def _finite(x):
    return isinstance(x, (int, float)) and not isinstance(x, bool) and math.isfinite(x)


def fuse_topk(items, weights, k):
    """加权和后取 TopK。缺失和 NaN 不当成 0，负权重不做归一化。"""
    if isinstance(k, bool) or not isinstance(k, int) or k <= 0 or not items:
        return []
    if not weights or any(not _finite(w) for w in weights):
        raise ValueError("weights must be non-empty and finite")

    ranked = []
    width = len(weights)
    for idx, item in enumerate(items):
        scores = item.get("scores")
        if item.get("id") is None or not scores or len(scores) != width:
            continue
        if any(not _finite(s) for s in scores):
            continue
        total = sum(w * s for w, s in zip(weights, scores))
        if not math.isfinite(total):
            continue
        ranked.append((-total, idx, item["id"], total))

    ranked.sort()
    return [{"id": i, "score": s} for _, _, i, s in ranked[:k]]
```

### 1. 自我介绍

**答题思路**

二面时间留给项目。背景压缩到三十秒，然后明确说今天展开哪一个项目。

1. 年限和方向一句带过，点明你做的是推荐链路还是中台。
2. 直接说出项目的业务目标和你负责的层：模型、特征、链路或平台。
3. 预告两个能往下钻的决定，例如特征为什么以请求日志为准，多目标权重为什么这么定。
4. 不要重复一面已经讲完的技术栈清单，面试官接的是项目细节。

### 2. 挑一个推荐/中台项目讲，你负责哪块，模型、特征、链路还是平台

**答题思路**

只认定一块主责，其余讲接口和协作。按下面的顺序讲，每段都能被追问。

1. 目标：主指标、护栏、延迟和候选规模。
2. 边界：你写的是模型、特征定义、在线链路还是平台能力。把团队的工作说成自己的，一追就会断。
3. 方案和放弃的备选：为什么用这条链路，另一条差在延迟、口径还是迭代速度。
4. 上线：离线看什么，小流量看什么，护栏是什么。
5. 一个真实故障或一次不显著的实验：你怎么定位，最后改的是特征、数据还是重排。

百分比只讲实验报告里能指出来的相对变化和口径。没有就讲判断标准，不要编一个提升数字。

### 3. 特征平台里离线特征和在线特征怎么保证口径一致，训练和服务不一致会有什么后果

**参考答案**

结论：同一份特征定义，训练优先用服务时打进请求日志的快照。离线重算只用于对账，而且只能取请求时刻之前的值。

口径包括窗口、过滤、去重、默认值和类型。离线 SQL 与在线作业有任何一项不同，模型学到的就不是线上能拿到的数。常见的错法是训练时回连最新特征，把点击之后才产生的计数学进去。上线后这个未来信息消失，离线指标就不成立。

默认值也算口径。训练填 0、在线填均值，或者在线突然缺失而训练没见过缺失，分数都会漂。做法是特征平台登记定义和负责人；排序请求落特征快照；训练直接读快照；另跑对账，比较同一批 request_id 的重算值和日志值，不一致就告警。

后果是离线 AUC 上升、线上效果不动甚至变差。严重时模型依赖一个服务阶段根本没有的特征。

### 4. 用户行为序列特征怎么建，短期兴趣和长期兴趣怎么分开

**参考答案**

结论：短期序列供应当下意图，实时更新并截断；长期兴趣用搜索或聚合，按天或近线更新。不要把几个月的行为原样送进同一个注意力模块。

短期可以是最近一段时间的点击和播放，带上类目、时间差和播放时长，连续重复的事件去掉，长度截到模型能承受的范围。排序时用候选物品对这段历史做目标注意力，不同候选看到的权重不同。这次会话里刚发生的行为可以由请求带上。

长期兴趣如果全量做注意力，计算和噪声都过大，当前意图会被冲掉。常见做法是先按类目或向量从长序列里取出相关的一段，再做注意力；也可以沉淀成兴趣向量，按天更新。

两边分开存。短期放在线存储，长期放特征库。更新频率、截断长度和模型结构都不同，混成一个特征就无法单独改。

### 5. DeepFM、DIN、DCN 这类模型你用过哪个，为什么选它，交叉特征怎么来

**参考答案**

结论：有强行为序列就用 DIN 处理序列，其余稀疏特征用 DeepFM 或 DCN 做交叉。没有序列时不要为了名字上 DIN。

DeepFM 用因子向量的内积做二阶交叉，再叠 DNN，两边共用同一套 embedding。适合 ID 很多、人工交叉不全的场景。DCN 每一层用当前层算出一个标量，去缩放原始输入再加回当前层，交叉阶数随层数增加，参数比把交叉全展开省。DCN-V2 把这个标量换成矩阵变换后再与原始输入按元素相乘，表达更强。DIN 用候选物品对行为序列做注意力，同一个用户面对不同候选时，历史行为的权重不同。这和先做自注意力再池化是两种结构。

交叉有三个来源：FM 或 Cross 这样的显式交叉、DNN 的隐式交叉、少量人工强交叉，例如用户类目和物品类目。序列交互交给目标注意力。不要把高基数 ID 做笛卡尔积。选模型之前先看序列强不强、要不要可控的显式交叉，再用消融确认增益。面试时只讲你真的训练过、能说出输入和上线约束的那一个。

### 6. 多目标排序里点击率、完播、转化、时长怎么融合，主目标和护栏指标怎么定

**参考答案**

结论：每个头先单独校准，再按业务选定的主目标融合。完播率不能代替时长。护栏在开实验前登记，护栏变差就停。

点击率、完播、转化都是概率，时长是期望观看时间。期望时长可以拆成播放概率乘条件时长，也可以直接回归。另一种做法是正样本按观看时长加权、负样本权重为 1，用逻辑回归的 odds 近似期望观看时长。完播率偏爱短内容，时长偏爱长内容，只优化完播会把大盘时长做短。

转化如果只在点击样本上训练，再和点击率相乘，选择偏差还在。要在全部曝光上同时学习点击和转化，用 pCTR × pCVR 把转化约束到曝光空间。融合可以用加权和，也可以用带指数的乘积。乘积适合有漏斗的场景，某一项为 0 会直接淘汰该物品；加权和允许补偿，但尺度必须先对齐。

内容场景的主目标常见是时长或留存，交易场景常见是转化。护栏看负反馈、低质占比、多样性和不能牺牲的另一个目标。权重是业务选择，不是网络结构，改权重就要做实验。

### 7. 重排阶段除了模型分数，还要考虑多样性、频控、去重、冷启动，你怎么设计重排策略

**参考答案**

结论：先做硬过滤，再按融合分生成列表，用规则兜住多样性、频控和冷启动名额。重排对一刷负责，精排的逐条分数做不到这一点。

硬过滤包括下架、不安全、业务规定必须去掉的已看内容。去重看物品、作者，以及封面或内容向量过于接近的条目。多样性用滑动窗口：一刷之内，同一类目或作者不能超过上限。窗口和上限按这一刷的长度定。频控读取用户最近的曝光记录，在列表阶段执行；只在精排里加一个曝光次数字段，仍然可能在同一刷里扎堆。

冷启动给固定名额，用内容向量作先验，不能把整刷都换成探索。没有行为的物品不要指望协同过滤召回它。生成时可以用融合分减去与已选物品的最大相似度，在相关性和多样性之间取平衡。多样性过强会伤点击，频控过严会伤供给。实验同时看主指标、类目分布和连续重复率。

### 8. Agent 接进推荐系统，用来做哪些事：日志分析、策略生成、自动调参、还是人工审核辅助

**参考答案**

结论：接日志分析、策略草案和人工审核辅助。自动调参可以产出建议，不能直接写生产参数。

日志分析看 BadCase、特征缺失和各路召回是否为空，输出必须带 request_id 和查询。策略生成限于已经注册的参数和取值范围，并写成实验单。审核辅助是把证据和候选改动交给负责人，由人决定开不开流量。

在线打分、无审核的自动调参、自动全量，都不交给 Agent。排序延迟是毫秒级，Agent 的多步调用既不稳定也不必要。调参建议进入实验平台的草案状态，人确认后才有流量。

### 9. 如果让 Agent 根据线上指标自动提出 AB 实验方案，你怎么约束它不乱改线上策略

**参考答案**

结论：Agent 只能创建实验草案，不能改默认策略、不能分配流量、不能发布。可改参数用白名单和上下界封死。

每份草案要写出改动、主指标、护栏、计划看的流量和回滚条件。一次只改一个因子。召回和重排同时改，有效也无法归因。流量从最小桶开始，错误率或护栏破了就停。开实验前检查分组比例是否异常。

草案绑定当时的提示、工具调用和数据快照，方便复盘。负责的人确认后才能开始。不允许根据线上奖励直接更新全量参数，那会绕过实验。

### 10. Elasticsearch 在推荐里适合做什么，和向量检索怎么配合做混合召回

**参考答案**

结论：Elasticsearch 负责文本倒排和结构化过滤，向量索引负责语义近邻。两路分数不可比，按名次融合；过滤很严时要避免后过滤把结果滤空。

倒排适合标题、标签、查询词，以及类目、地域、状态、时间这些过滤。向量适合「和这个物品或这段兴趣语义接近」。规模上来之后，不要对全库向量逐条算相似度，要用近似最近邻。

配合有两种。一是文本一路、向量一路，各自取回结果，用倒数排名融合：物品在某一路的名次是 r，这一路就贡献 1/(平滑常数 + r)。平滑常数用来压住第一名的权重，取值按各路质量调。二是先过滤再检索。若先做近似最近邻再过滤，过滤条件严时会凑不满 K 个，需要放大召回量，或者按主要过滤条件分开建索引。文本和过滤可以继续留在 Elasticsearch，向量规模和过滤复杂度高时独立部署向量索引。

### 11. RocketMQ 或 Kafka 消息积压了，推荐样本延迟变大，怎么降级保证模型不被脏数据带偏

**参考答案**

结论：样本延迟超过归因窗口时，暂停在线增量训练，继续用上一版稳定模型。积压的数据可以离线补，不能当成新鲜样本把模型追平。

曝光之后点击会晚到。窗口没结束就当成未点击，晚到的正样本会变成假负样本，点击率被系统性压低。消费重复又没有幂等时，标签会被算多次。用事件时间判断是否还在窗口内，太晚的进离线补数。

排序侧如果实时特征跟着落后，就退回上一份近线特征，并带上缺失标记。模型在训练时要见过缺失，否则线上一缺失分数就偏。特征消费的限流、扩容是另一件事，先保证训练输入是成熟样本。RocketMQ 和 Kafka 在这里的处理原则相同：看堆积时长和事件时间，而不是把积压一次性灌进在线训练。

### 12. 模型上线后离线 AUC 涨但线上 CTR 不涨，你怎么定位是特征、重排、曝光偏差还是用户疲劳

**参考答案**

结论：AUC 只说明曝光样本上的排序变好，不保证融合分尺度、重排后的顺序和用户看到的重复程度。先排除埋点，再把特征、重排、位置偏差和疲劳拆开看。

用同一批 request_id 比较训练特征和服务日志。对不上，或重要特征缺失率突然上升，就是特征问题，包含训练时用到了请求之后才有的值。

看精排顺序和最终曝光顺序的重合度，以及规则命中率。重合度明显下降，说明重排或规则把模型序改掉了，离线 AUC 反映不到这一刷。

位置偏差和疲劳用切片分开。同一物品在不同坑位点击率差很多，是位置效应；模型会把「经常出现在前面」学成物品本身的质量。打分时最终坑位还没确定。训练时把位置当普通特征、服务时填一个常数，只是去掉了这个输入，物品表示里已经吸收的位置偏差还在。常见做法是用该位置被看到的概率做逆概率加权，或在随机流量上估计位置效应。同一坑位上，曝光次数越高点击率越低，才是疲劳，要靠频控处理。

最后看校准：预测点击率和实际点击率是否还贴着。AUC 不受分数尺度影响，加权融合会受尺度影响。

### 13. 手撕算法：多路召回结果合并去重，并按来源权重和分数做融合排序

**参考答案**

结论：同一路里同一物品只留最高分，再用来源权重做加权和，按融合分降序取 TopK。未配置的来源整路丢弃。各路分数先变成可比尺度，否则权重没有意义。

协同过滤的共现分和向量内积不能直接相加。可以先在路内校准，或改成倒数排名融合，只使用名次。多路都召回到同一物品时，加权和会提高它的名次，这是在奖励多路一致；若业务想只信最强的一路，应该取最大值。这个函数实现的是加权和。

边界：K 小于等于 0 返回空；分数为 None、NaN、Inf 的条目丢掉；权重不是有限数的来源丢掉；同一路重复出现取最高分，避免重复计数。并列时，数值 id 按数值排，其他 id 按字符串排，保证可复现。时间 O(N + M log M)，空间 O(M)。N 是合并前的条目数，M 是去重后的物品数。

```python
import math


def _finite(x):
    return isinstance(x, (int, float)) and not isinstance(x, bool) and math.isfinite(x)


def _id_key(i):
    if isinstance(i, bool) or not isinstance(i, (int, float)):
        return (1, str(i))
    return (0, i)


def merge_recalls(paths, source_weights, k):
    """路内取最高分，再按来源权重加权求和。"""
    if isinstance(k, bool) or not isinstance(k, int) or k <= 0:
        return []

    best = {}
    for path in paths:
        source = path.get("source")
        weight = source_weights.get(source)
        if not _finite(weight):
            continue
        for item in path.get("items") or []:
            score = item.get("score")
            iid = item.get("id")
            if iid is None or not _finite(score):
                continue
            by_source = best.setdefault(iid, {})
            prev = by_source.get(source)
            if prev is None or score > prev:
                by_source[source] = score

    fused = []
    for iid, by_source in best.items():
        total = sum(source_weights[src] * score for src, score in by_source.items())
        if not math.isfinite(total):
            continue
        fused.append((-total, _id_key(iid), iid, total, sorted(by_source, key=str)))

    fused.sort()
    return [
        {"id": iid, "score": total, "sources": sources}
        for _, _, iid, total, sources in fused[:k]
    ]
```

## 三面

### 1. 自我介绍

**答题思路**

三面先讲平台判断，少讲模型结构。一分钟到两分钟。

1. 说明你做的是单业务还是多业务共用的能力，服务了几条线只说真实数量。
2. 举一条你划过的边界：什么收进平台，什么留在业务插件里，依据是复用还是变更频率。
3. 讲一个稳定性或效果上的结果，口径说清楚。没有跨业务数字就讲接入方式和故障时怎么隔离。
4. 收在你为什么适合中台：能把效果、发布风险和复用放在一起做取舍。

### 2. 你做推荐中台时，怎么让多个业务线都接你的平台，接入成本和迁移成本怎么压

**参考答案**

结论：先统一主键、行为日志和特征定义，再提供一条只靠配置就能跑的默认链路。迁移用适配和双跑，按场景切，不要求业务第一天就改掉自己的策略。

接入成本大部分耗在日志含义和特征口径，不在 RPC 桩。请求上下文、物品 ID、曝光和点击的字段先定死，并提供实验分流 SDK。默认链路包含通用召回、通用特征和一个可配置的排序，业务先配类目、过滤和目标。只有默认链路不够时才写扩展。

旧系统用适配层做字段映射，影子流量对比召回差和最终列表差。按场景灰度，指标对齐再下掉旧链路。第一条业务的踩坑写进模板，第二条才快。平台如果要求每个业务都改核心排序才能上线，接入成本会回到各写各的。

### 3. 中台能力抽象时，通用召回、通用特征、通用实验平台和垂类业务规则怎么边界划分

**参考答案**

结论：跨业务稳定的执行能力放中台，跟着某一个业务的目标和活动变的规则留在垂类。

通用召回指检索框架、配额和索引管理，具体召回路可以配置。通用特征指注册、计算、存储、对账和在线读取。实验平台指分流、指标和回滚，不规定每个业务的主指标内容。这些能力接口稳定，被多条线共用。

垂类保留类目细节、审核、优化的是时长还是转化，以及活动期的排序规则。划分标准是：至少两条业务用同一语义，并且接口能稳住，再进中台。只有一家使用、下周可能就改的逻辑留在业务侧。把某一家的分支写进通用排序，其他业务会一起承担发布风险。

### 4. 如果业务方要求加一个很定制化的排序逻辑，你会做成中台能力还是业务侧插件

**参考答案**

结论：默认做成业务侧插件，挂在重排扩展点上。超时或失败就退回中台给出的顺序。

扩展点的输入是候选和上下文，输出是过滤或调序，运行有超时。中台保证没有插件时链路仍然完整。满足两个条件再收进中台：已经有第二个业务要同一语义，并且能参数化，例如作者打散、类目窗口，而不是在代码里判断业务名。

活动加权、只服务一次的特殊公式留在插件里，过期能卸掉。判断时看三件事：失败能不能回退、会不会有第二条业务、能不能变成参数。三条都偏向一次性需求，就不要改通用服务。

### 5. Agent 在推荐中台里能不能做智能运维：自动看监控、定位召回异常、生成修复建议

**参考答案**

结论：可以看监控、做定位草稿和修复建议。自动执行只限于事先写好的降级开关，并且要有熔断和人的确认。

召回异常先对变更，再对计数。Agent 读取各路召回条数、空结果率、超时、过滤比例、索引版本和特征缺失率。很多故障是索引没切成功或过滤配错，要先把发布单和曲线对齐，而不是直接断定模型坏了。

建议写成可执行的一条：切回上一版索引，或降级到热门召回，并说明证据和影响面。重启服务、切换模型、修改召回配额，不作为 Agent 的自由动作。人确认后执行，或者只允许打开已经存在的降级开关。

### 6. 多 Agent 协作做推荐策略研发时，规划 Agent、实验 Agent、复盘 Agent 之间怎么通信，状态放哪

**参考答案**

结论：用外部任务单通信。对话上下文只做临时推理，不作为共享状态。

规划 Agent 写入目标指标、允许改的参数、禁止事项和完成标准，没有生产写权限。实验 Agent 只能调用实验平台的草案接口，把实验 ID 写回任务单，不能自己放量。复盘 Agent 只读实验结果和日志，写结论和下一步，不能开实验。

任务状态放数据库，例如待分析、待确认、实验中、已复盘。SQL、日志片段和报告放对象存储，消息里只传任务 ID 和结构化字段：假设、改动、护栏、实验 ID、结论。自然语言只作说明。每个 Agent 的工具权限按角色切开。上下文会被截断，长任务要从任务单恢复，写操作带幂等键。

### 7. Agent 给出策略建议但和资深算法同学判断冲突，你信人还是信 Agent，怎么设计人工兜底

**参考答案**

结论：数字以核对过的查询为准，发不发布由负责的人决定。Agent 没有生产环境的写权限。

两边报的指标不一致时，用同一段时间和同一个口径重跑查询，不靠投票。数字一致但判断不同时，例如主指标上升、负反馈也上升，按开实验前登记的护栏执行。护栏没覆盖到的品牌或合规风险，由人决定不发。

兜底是权限而不是口号：生产变更必须人确认，高风险动作由负责人执行。每次分歧记下预测和最终选择，用来看 Agent 是不是系统性地偏向某一个指标。人的判断若没有数据，也要补上同一套查询再决定。

### 8. 推荐系统里的数据闭环怎么建，日志、样本、特征、模型、实验、监控怎么串起来

**参考答案**

结论：用 request_id 把一次请求的日志、特征快照、实验桶和模型版本串起来。本轮训练只用已经成熟的分区，新日志进入下一轮。

曝光、点击、播放日志带上位置、实验桶、模型版本和召回路。样本由这份日志加上请求时的特征快照和成熟后的标签组成。特征定义只有一份，在线读取和离线对账都指向它。训练产出进入模型注册，实验平台按桶放量，监控看效果、延迟和特征缺失，再决定保留、回滚或进入下一轮。

缺 request_id，样本就拼不回那一次排序。缺特征快照，训练只能事后重算，容易用到当时还没有的值。缺实验桶，效果无法归因。监控如果不能按模型版本和召回路拆开，闭环在定位时会断。

### 9. 生成式推荐或 LLM 重排现在能不能上生产，和传统精排相比工程风险在哪

**参考答案**

结论：可以在小流量里对精排给出的少量候选做重排。不能无约束替换精排，也不能让模型自由生成物品 ID。

传统精排的特征契约固定，分数可以校准，延迟稳定在毫秒级，出了问题能对到特征和版本。LLM 重排的延迟和单次成本都明显高于它，而且随 QPS 上升。输出必须是给定候选的一个排列。解析失败、出现候选之外的 ID、或者超时，都退回精排原序。安全、合规和去重仍在模型后面做硬检查。

生成式召回若是逐 token 生成下一个物品，还要处理词表约束、重复和召回为空。离线生成指标和线上点击、时长的关系弱，是否保留只看小流量和护栏。prompt 与模型版本都要能回滚。

### 10. 中台要支撑搜索、广告、内容推荐，模型服务和特征服务怎么避免互相拖垮

**参考答案**

结论：模型服务按业务拆部署、拆限流。特征定义可以共用，在线读取按可用性要求分池，离线回灌不进入在线读池。

搜索有查询尖峰，广告在意计费链路的延迟和正确性，内容推荐是很高的打分 QPS。峰值和失败代价不同，不能放在一个没有优先级的共享池里互相抢。

舱壁包括各自的连接池、超时和熔断。每个业务有自己的兜底，例如热门结果或上一份缓存。容量按各自峰值估计。典型的连带故障是某一业务的特征回刷打满共用集群，三条线一起变慢。回刷走单独副本或严格限流，在线读取只访问服务池。

### 13. 手撕算法：给定一个依赖关系，多个推荐任务（特征更新、模型训练、样本拼接、上线）之间有先后依赖，输出合法执行顺序，并检测环

**参考答案**

结论：用入度做拓扑排序。全部任务都进入顺序才算可执行；否则有环，不返回残缺顺序，并给出一条环。本轮「上线产生的新日志」属于下一轮输入，不要画回本轮的特征更新，否则会得到假环。

依赖由样本怎么用特征来决定。样本在拼接时就要写入这批特征，顺序是特征更新、样本拼接、模型训练、上线。线上请求已经把特征快照打进日志时，样本拼接只依赖日志和归因窗口，可以和离线特征更新并行，训练依赖样本，上线依赖训练。两种都合法，不能混用。拼接时写入，就要等特征作业完成；训练时再查特征，只能查请求时刻之前的版本。

重复边只计一次，否则入度会被算大，没有环也会被判成环。自环是环。并列可执行的任务按名字排序，只为了同一次输入得到同一个顺序，不代表业务优先级。要优先级就把堆元素换成优先级加名字。时间 O(E + V log V)，空间 O(V + E)。任务链很长时，找环的递归会碰到解释器递归上限，可以改成显式栈。下面的任务数量用递归足够。

```python
import heapq
from collections import defaultdict


def schedule(tasks, deps):
    """有合法的全序就返回顺序；有环则顺序为空，并给出一条环。"""
    names = list(tasks)
    if len(names) != len(set(names)):
        raise ValueError("duplicate task")

    graph = defaultdict(list)
    indeg = {t: 0 for t in names}
    seen = set()
    for pre, post in deps:
        if pre not in indeg or post not in indeg:
            raise ValueError("unknown task")
        if (pre, post) in seen:
            continue
        seen.add((pre, post))
        graph[pre].append(post)
        indeg[post] += 1

    ready = [t for t, d in indeg.items() if d == 0]
    heapq.heapify(ready)
    order = []
    while ready:
        cur = heapq.heappop(ready)
        order.append(cur)
        for nxt in graph[cur]:
            indeg[nxt] -= 1
            if indeg[nxt] == 0:
                heapq.heappush(ready, nxt)

    if len(order) == len(names):
        return {"ok": True, "order": order, "cycle": []}
    return {"ok": False, "order": [], "cycle": _one_cycle(names, graph)}


def _one_cycle(tasks, graph):
    white, gray = 0, 1
    color = {t: white for t in tasks}
    stack = []
    onstack = set()

    def dfs(node):
        color[node] = gray
        stack.append(node)
        onstack.add(node)
        for nxt in graph[node]:
            if color[nxt] == white:
                found = dfs(nxt)
                if found:
                    return found
            elif nxt in onstack:
                i = stack.index(nxt)
                return stack[i:] + [nxt]
        stack.pop()
        onstack.remove(node)
        color[node] = 2
        return None

    for task in tasks:
        if color[task] == white:
            found = dfs(task)
            if found:
                return found
    return []
```
