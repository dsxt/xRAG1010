## 一面

### 1. 自我介绍

**答题思路**

控制在 1 分半到 2 分钟，按「我是谁 → 做过什么 → 为什么匹配」讲：

1. 年限、语言和当前方向，落到办公协同或开放平台上的 Agent，点明你写过机器人、回调或工具调用。
2. 只展开一个最相关的项目：用户是谁、你负责的一段链路、一个你能复述的结果。接口细节留给后面两题。
3. 补一个工程证据，例如鉴权、幂等、失败重试或延迟，说明你碰过线上。
4. 收束到岗位：希望在日历、消息和权限都是真实约束的环境里把 Agent 做稳。

项目名和数字只用你自己的。一面会顺着这里往下问。

### 2. 项目介绍

**答题思路**

挑一个你亲自落地、最好和机器人或开放平台相关的项目，3 分钟以内按这个顺序讲：

1. **场景**：谁在用，原来怎么完成，怎样算成功。
2. **链路**：从事件入口到鉴权、处理、调用外部 API、再回到会话。用一次真实请求走完。
3. **你的部分**：具体到模块、状态和失败处理。补一句选型时放弃了什么，例如为什么没有让模型直接发原始 HTTP。
4. **两个难点**：各用「现象 → 原因 → 做法 → 结果」。优先选令牌失效、回调重复、权限或工具选错。
5. **上线**：日志、失败兜底、权限范围。记不清的接口直接说边界，只讲你写过的部分。

换票和请求头的细节下一题会单独问，这里把业务链路讲清楚。

### 3. 飞书开放平台 API 调用流程（获取 tenant_access_token 等）

**参考答案**

企业自建应用调飞书接口，先用应用凭证换租户令牌，再在请求头里带上它访问业务 API。这个令牌代表「应用在该租户下的身份」。

在开放平台创建应用，拿到 `app_id` 和 `app_secret`，开通消息、日历等权限，发布后由管理员授权。服务端请求 `POST /open-apis/auth/v3/tenant_access_token/internal`，body 带这两个凭证，返回 `tenant_access_token` 和 `expire`。之后的请求头写 `Authorization: Bearer <token>`。国内域名是 `open.feishu.cn`。

读某个员工的日历、以该员工身份改日程，要另走用户授权：引导用户拿到授权码，再用应用身份把授权码换成 `user_access_token` 和 `refresh_token`，按响应里的过期时间续期。商店应用还要先处理 `app_ticket` 和 `tenant_key`，不能直接套 internal 这一个接口。

令牌集中缓存，在 `expire` 前提前刷新；发现令牌失效时清缓存，并用互斥保证只有一个请求回源。事件回调先验签，立刻返回，耗时逻辑异步做。租户令牌只能访问已经授给应用的数据。

### 4. 飞书机器人开发中，消息卡片（Card）与普通文本消息的区别及适用场景

**参考答案**

文本消息负责把一句话说完，卡片负责把状态展示出来并收回用户的一次明确操作。

文本（含富文本）发出后就是一段内容，适合解释、闲聊和边生成边出字。卡片是结构化 JSON，由标题、字段、按钮等组件组成，消息类型是 interactive。按钮会把 `value` 随卡片回传事件交给服务端；服务端还能按 `message_id` 更新同一张卡片，让「待确认」变成「已预订」，不用再刷一条新消息。批量通知可以用模板加变量。

订会议室、审批、告警确认用卡片。原因说明和开放式问答用文本。Agent 里由服务端拿结构化状态渲染卡片，模型负责文案和槽位；未校验的卡片 JSON 不要直接发给飞书。

容易漏的是时限和幂等：卡片回调要在短时限内返回（文档要求 3 秒内），超时用户会看到失败；同一动作可能重试，用动作唯一键去重。发普通消息也可以带 `uuid`，避免重试发出两段一样的文本。

### 5. Agent 架构中，感知层、推理层、执行层的职责划分

**参考答案**

感知层把外部世界变成观察，推理层决定下一步，执行层才真正调用工具并把结果交回来。

感知层接收飞书事件、消息、卡片回调和日历数据，整理成谁在说话、会话是哪一段、当前有什么权限、抽出来的时间和参会人。它做归一化和脱敏，不决定要不要订会议室。推理层在目标和约束下选择下一步，可以是一次模型调用，也可以先被规则截住；它只产出计划或工具调用。执行层按 schema 校验参数、检查权限、处理超时和幂等，再调用 API，把成功结果或错误码写回观察。

三层通过同一份状态交接。执行失败就写成错误观察，供下一轮推理改参数或向用户追问。飞书里的权限放在执行层强制检查。

容易漏的是预算：推理层要有步数、时间和费用上限，新消息不断进来时循环也要能停。

### 6. 大模型在 Agent 中扮演什么角色？除了生成文本，还有哪些作用？

**参考答案**

大模型是策略和语言接口。说给用户听的那段文字，只是它的一种输出。

它还负责：从原话里抽取意图和槽位（时间、会议室、参会人）；在给定工具里选择工具并填写参数；把多步目标拆成有顺序的子任务；看到工具报错后决定重试、改参数还是追问；筛选检索片段，判断证据够不够。带图片或语音转写时，它负责理解这些观察。有的系统也让模型做路由，把简单请求交给更小的模型。

鉴权、写日历、改库存这类要一致性和审计的动作，由工具和规则执行。模型提出调用，参数先过 schema 和业务校验，失败信息再喂回去。

容易漏的是把模型输出当成提案。提案和真正发出的 API 请求中间要有一道校验。

### 7. 什么是 Tool Calling？Agent 如何决定调用哪个工具？

**参考答案**

Tool Calling 是模型按约定产出「工具名 + 参数」，运行时执行后，把结果写回上下文。外部系统由运行时访问。

工具以名字、用途和 JSON Schema 放进本次上下文。模型这一轮要么给出最终回复，要么发起调用；运行时先校验参数，再执行，并用同一个调用 id 把结果接回去。模型看到结果后，再决定继续调用还是回复用户。选哪个工具，来自工具描述和当前观察是否对得上。工具很多时，先按意图缩小候选，再让模型在小集合里选。

描述要能互相区分，参数用枚举和必填项收紧。并行调用只用于互不依赖的只读工具；会写数据的工具保持串行。

容易漏的是失败回传。错误要写成错误码、原因和能否重试，空字符串会让下一轮失去修改依据。

### 8. 如何解决 Agent 在长对话中“遗忘”上下文的问题？

**参考答案**

模型不会跨请求保存对话。窗口被截断，或早期约束没单独存放，看起来就是遗忘。

分三层留信息。当前任务保留系统提示、最近几轮原文和还没完成的工具状态；更早的对话做成滚动摘要，摘要里强制留下时间、会议室、参会人和已经同意的决定。正在收集的会议字段放进结构化状态，每轮重新注入，不靠模型自己记得。跨会话仍有用的偏好写入可检索记忆，按用户和租户隔离，用到时再召回。

摘要在窗口还没顶满时就做，并允许用户纠正。工具返回往往比对话更长，写回前先裁剪。

容易漏的是否定条件。「不要订晚上 9 点以后」要进状态，不能只留在摘要的一个从句里。

### 9. 如果线上 Agent 延迟明显变高，你会如何排查？

**参考答案**

先分清是全体变慢，还是某一个意图、租户或实例变慢，再按链路拆时间。

给每次请求打点：排队、组装上下文、模型首 token、模型生成、每一次工具调用、检索和后处理。对比变慢前后的耗时分布和超时率。各段对得上不同原因：供应商限流或降级、上下文变长导致预填充变慢、工具超时后的重试被放大、检索数据变多、下游错误把重试打满，或新版本把工具数和提示变长了。

处理跟着证据走：先裁剪上下文和工具原文；只读工具并行，写操作仍串行；给飞书调用加超时、熔断和有限次重试；模型超时就降级成规则或更小模型，先回一张可操作的卡片。先保证可用，再修根因。

容易漏的是把排队时间和模型生成时间看混。队列堆积时调整并发，生成变慢时减少 token 或改路由。

### 10. 简述 RAG 在 Agent 中的应用，与普通问答 RAG 有何不同？

**参考答案**

普通问答 RAG 是检索片段之后一次生成。Agent 里的 RAG 是工具：模型决定何时查、查哪类资料、证据够不够，以及要不要再查或改口问用户。

飞书场景把制度、会议室说明和项目文档切块入库，先按租户和用户可见范围过滤，再做相似度排序。结果回到推理层，可能触发一次更具体的查询，也可能变成订会议室前的约束。查询经常是模型改写过的，保留文档版本和引用，方便核对。写日程仍走专用工具。

评测除了答案是否忠实，还要看该不该调用检索、参数对不对。没查到和没权限要分成两种结果。

容易漏的是过滤顺序。先按权限去掉看不见的块，再排序；模型的保密提示替代不了这道过滤。

### 11. 手写算法：会议室预订问题（线段树/树状数组实现）

**参考答案**

按在线预订来写：多次调用 `book(start, end)`，时间是整数，区间用半开区间 `[start, end)`，每次都记下这次预订，并返回当前最大并发。端点相接不算冲突，`[10, 20)` 和 `[20, 30)` 的最大并发是 1。

基准做法是有序差分：起点 +1、终点 -1，插入后扫一遍前缀和。单次 O(n)，q 次总共 O(q²)。动态线段树把时间轴当成值域 `[0, U]`，U 要盖住最大时间，Unix 秒放到 10^18 量级即可。`book` 对闭区间 `[start, end - 1]` 做区间加 1，根上的最大值就是答案。整段被覆盖时只累加懒标记，这段的最大值同步加同一个数；继续往下之前把标记下推给左右孩子。单次 O(log U)，q 次时间 O(q log U)，空间 O(q log U)，不用把整条时间轴建出来。

例如 `book(10, 20) → 1`，`book(50, 60) → 1`，`book(10, 40) → 2`，`book(5, 15) → 3`。

树状数组适合离线：端点离散化后，起点 +1、终点 -1，所有前缀和里的最大值就是最大并发，总时间 O(n log n)，空间 O(n)。它负责点更新和前缀和。区间加完再问区间最大时，加法标记没有逆运算，标准树状数组维护不了，在线版本用线段树。

若题目改成同一时刻只能有一场，更新前先查询该段最大值，大于 0 就拒绝，否则再区间加 1，复杂度和上面相同。移植到 Java 或 C++ 时，中点写成 `left + (right - left) / 2`，避免 `left + right` 溢出。

```python
class Node:
    def __init__(self):
        self.left = None
        self.right = None
        self.lazy = 0
        self.mx = 0


class MeetingBook:
    def __init__(self, upper=10**18):
        self.root = Node()
        self.upper = upper

    def book(self, start: int, end: int) -> int:
        if not (0 <= start < end <= self.upper + 1):
            raise ValueError("invalid interval")
        self._add(self.root, 0, self.upper, start, end - 1, 1)
        return self.root.mx

    def _push(self, node: Node) -> None:
        if node.left is None:
            node.left = Node()
        if node.right is None:
            node.right = Node()
        if node.lazy:
            for child in (node.left, node.right):
                child.lazy += node.lazy
                child.mx += node.lazy
            node.lazy = 0

    def _add(self, node, left, right, ql, qr, delta) -> None:
        if ql <= left and right <= qr:
            node.lazy += delta
            node.mx += delta
            return
        self._push(node)
        mid = left + (right - left) // 2
        if ql <= mid:
            self._add(node.left, left, mid, ql, qr, delta)
        if qr > mid:
            self._add(node.right, mid + 1, right, ql, qr, delta)
        node.mx = max(node.left.mx, node.right.mx)
```

```python
class Fenwick:
    def __init__(self, n: int):
        self.tree = [0] * (n + 1)

    def add(self, index: int, delta: int) -> None:
        while index < len(self.tree):
            self.tree[index] += delta
            index += index & -index

    def prefix(self, index: int) -> int:
        total = 0
        while index > 0:
            total += self.tree[index]
            index -= index & -index
        return total


def max_concurrent(intervals: list[tuple[int, int]]) -> int:
    """离线计算半开区间的最大并发。"""
    points = sorted({t for start, end in intervals for t in (start, end)})
    rank = {point: i + 1 for i, point in enumerate(points)}
    bit = Fenwick(len(points))
    for start, end in intervals:
        bit.add(rank[start], 1)
        bit.add(rank[end], -1)
    return max((bit.prefix(i) for i in range(1, len(points) + 1)), default=0)
```

### 1. 自我介绍

**答题思路**

同样 1 分半到 2 分钟，重心放在结构，功能清单一句带过：

后面的框架设计题会接着用你这里的词，前后保持同一套分层。

### 2. 项目介绍

**答题思路**

选一个你能讲清取舍的 Agent 项目，按「约束 → 结构 → 你的决定 → 后果」讲：

1. 业务约束：哪些步骤必须对人确认，哪些错误不能发生第二次。
2. 运行时怎么转：状态存在哪里，模型产出什么，工具谁来执行，崩溃后从哪条记录继续。

二面要听的是这套东西能不能交给别人改，不听功能演示。

### 3. 如果让你设计一个通用 Agent 框架，你会怎么设计？（分层架构、标准化协议）

**参考答案**

框架提供一条可恢复的循环和一套稳定协议。业务差异放在工具包、系统提示和策略插件里。

循环是：装载状态，组装上下文，模型产出动作，校验并执行工具，把事件写回，直到结束或预算用尽。接入层只做飞书事件、HTTP 的鉴权和协议转换。运行时管会话、步数、超时、取消和幂等。模型适配层把各家接口收成统一的消息和工具调用。工具层登记名字、JSON Schema、所需权限和是否有副作用。观测层记录每一步的输入输出和耗时。

协议至少固定三件事：消息角色和调用 id、工具的 schema 与错误结构、状态事件的日志格式。换模型或增加工具时，循环本身不动。状态按会话持久化；恢复时沿事件继续，有副作用的工具只执行一次，并记下当时的结果。

默认是单 Agent 循环。多 Agent 做成可选编排。规则可以在进模型前短路。容易漏的是副作用标记：框架不知道哪些工具会写数据，重试和恢复就会双写。

### 4. 如何设计 Agent 的记忆机制？短期记忆和长期记忆如何区分？

**参考答案**

短期记忆服务这一次任务，长期记忆服务跨会话仍然成立的事实。两者的寿命、谁能写、怎么注入都不一样。

短期记忆放在会话里：最近原文、滚动摘要、正在填写的字段（时间、会议室、待确认项）和还没消化的工具结果。它随会话过期，可以整段重写，每轮都注入，但有长度预算。长期记忆是跨会话条目，例如偏好、常订的会议室。写入要有门槛，用户明确说「以后都这样」，或一次成功任务后抽取，并带来源和更新时间。读取走检索，按用户和租户过滤，注入时标成用户可以纠正的内容。

离开这次对话还成不成立，用这个标准区分。会议已经创建，是日历和业务库里的事实，随业务接口变更，不放进记忆。新旧偏好冲突时保留时间和来源，检索到互相矛盾的两条就追问。

容易漏的是敏感字段。证件号、密钥和私人联系方式默认不进长期记忆。

### 5. 在飞书场景下，如何设计一个智能会议安排 Agent？（涉及日历 API、冲突检测、多轮交互）

**参考答案**

目标是在权限允许的范围内订下一场会。槽位和状态机负责主路径，模型负责听懂用户想怎么改。

先补齐标题、时间或时长、参会人、线下会议室或视频会议、是否允许冲突。缺了就发追问卡片。然后用该用户的 `user_access_token` 查忙闲。忙闲接口给出的是忙碌时段，空闲要用搜索窗口去减，再对参会人求交集。重叠按半开区间判断，端点相接可以连着开。全天日程、重复日程要先展开，跨时区先归一成绝对时间。某人的日历没权限时标成未知，并追问，不能当成全天空闲。

候选用卡片给两三个，用户点选后再创建日程并邀请。创建带业务幂等键，避免回调重试订出两场。模型把「改到明天下午」翻译成槽位更新，交集和冲突由接口和规则计算。写之前用确认卡片列出即将提交的字段。失败分成没权限、没有共同空闲、会议室被占，每种给不同的下一步。

办公场景默认确认后再写。只持有租户令牌时，读不到未授权的个人日程。

### 6. 如何评估一个 Agent 的好坏？除了准确率，还看哪些指标？

**参考答案**

准确率只回答「最终那句话像不像」。Agent 还要看任务有没有真的完成、路径对不对、花了多少、有没有误伤。

任务成功率以业务结果为准：槽位正确，而且日历里确实有这场会。工具侧看该调用时有没有叫到、选错率、参数合法率，以及多余调用次数。过程看平均步数、端到端延迟、token 和费用、重试次数。体验看追问是否过多、用户是否中途放弃、人工接管率。安全看越权调用、没有依据的写操作、敏感信息出域。同一用例要重复跑，看成功率波动。

评测集来自真实 Bad Case，加上跨天、没权限、重名同事这类边界。能结构化的工具参数和业务结果用规则判分。上线前固定回归集，线上按版本对比。

容易漏的是副作用用例：订错以后有没有撤销，重复回调会不会订两次。文本相似度过不了这类检查。

### 7. 如何做上下文压缩？为什么有些 Agent 在多轮对话后效果变差？

**参考答案**

上下文压缩是在超过窗口之前，把旧内容换成更短、仍然能决策的表示。

系统提示和工具 schema 保持原文。已经确认的槽位和当前计划用结构化状态保留。较早的对话换成摘要，并写明不能丢掉的约束。工具结果只留状态码、关键字段和错误，原始 JSON 去掉。按 token 阈值触发，不要等溢出再截。

多轮变差，通常是信息在压缩和堆叠里坏了。摘要丢掉否定条件；过期的工具结果和新结果矛盾，模型仍照旧结果预订；无关历史变长后，工具参数开始缺字段；之前的错误格式留在历史里，后面的轮次照着学。摘要模型还可能改写时间和数字。摘要本身也占上下文，触发太勤会把一次错误写进摘要，后面再压也回不来。

压缩前后用同一批多轮用例回归，工具参数要保持一致。关键事实放状态，时间、人数和否定条件不放进自然语言摘要。

### 8. 如何解决工具路由（Tool Routing）问题？当工具很多时，如何避免模型选错？

**参考答案**

工具一多，描述会开始相像，模型就会选错或填错参数。路由要在进模型之前把候选收小。

先用规则或小模型把请求分到域，例如日历、消息、文档，本次提示只放该域的 schema。工具说明写清做什么、不做什么、和旁边那个工具差在哪里。参数用枚举、必填和示例收紧。只读且互不依赖的可以并行；会写数据的拆开，并在用户确认前不暴露「创建日程」这类工具。失败信息要写明该改哪个字段。

还可以按查询对工具说明做召回，只把 Top-K 交给模型。K 太大等于没有路由。分类置信度低时先澄清，每个域留一个追问工具。

容易漏的是评测口径。要统计正确工具是否出现在候选集里。正确工具没放进提示，模型无法选中。

### 9. 在混合决策（规则引擎 + 大模型）中，如何平衡效率与准确性？

**参考答案**

规则处理边界清楚、要稳定、要低延迟的决定；模型处理开放说法和抽取。顺序是规则先短路，模型处理规则覆盖不了的部分，规则再校验模型的输出。

会议场景里，没登录、没日历权限、时间缺失，规则直接返回追问或错误。 「明天下午三点」交给模型或专用时间解析器抽槽。抽出来的时间是否重叠、是否落在允许的工作时间，再用规则算。创建日程前，规则检查必填项和幂等。高置信度的分类可以缓存，能由规则定下来的请求不进模型。

分界看三点：错了是否难撤回、输入能否枚举、延迟预算是否盖得住一次模型调用。这几条越齐，越该把决定放在规则里。规则表达不了的长尾再交给模型。

每个字段指定一个权威来源。规则校验失败时，把错误喂回模型修改，两边不要各执行一次。

### 10. 手写算法：实现一个简单的 RAG 检索系统（向量相似度计算）

**参考答案**

检索段做的是：每个文档块有一个向量，查询向量和它们逐个算余弦相似度，取得分最高的 k 块。余弦是点积除以两个 L2 范数；任一范数为 0，相似度记 0。入库前已经单位化的向量，余弦等于点积。

暴力扫描的时间是 O(n·d)，空间是 O(n·d)，n 是块数，d 是维度。用排序取 Top-K 时，排序是 O(n log n)。块数很大以后再换近似最近邻，并单独看召回，参数不在这道题里展开。生成不写进这个函数；低分要能表示没检索到，调用方不要把最不相关的一块也送去生成。

维度必须相同，不一致就报错。截断后会算出一个看起来正常、实际没有意义的分数。不同模型、不同归一化方式的向量不能放进同一个库比阈值。权限过滤在打分前做完。

```python
import math


def cosine(a: list[float], b: list[float]) -> float:
    if len(a) != len(b):
        raise ValueError("dimension mismatch")
    dot = norm_a = norm_b = 0.0
    for x, y in zip(a, b):
        dot += x * y
        norm_a += x * x
        norm_b += y * y
    if norm_a == 0.0 or norm_b == 0.0:
        return 0.0
    return dot / math.sqrt(norm_a * norm_b)


class VectorRetriever:
    def __init__(self, chunks: list[dict]):
        self.chunks = chunks  # {"text": str, "vector": list[float]}

    def search(self, query: list[float], k: int = 3, min_score: float | None = None) -> list[dict]:
        if k <= 0 or not self.chunks:
            return []
        scored = [
            (cosine(query, chunk["vector"]), idx)
            for idx, chunk in enumerate(self.chunks)
        ]
        scored.sort(key=lambda item: item[0], reverse=True)
        hits = []
        for score, idx in scored[:k]:
            if min_score is not None and score < min_score:
                break
            hits.append({"text": self.chunks[idx]["text"], "score": score})
        return hits
```

### 3. Agent 开发中，如何保证数据安全与合规？（敏感信息处理、权限控制）

**参考答案**

Agent 多了几条数据出去的路：工具结果会进模型上下文，也可能进记忆和日志。安全按数据流做。

权限沿用飞书现有模型。每次工具调用带当前用户的令牌，由开放平台判断能不能读这本日历、这份文档。检索先按租户、部门和文档权限过滤，再做相似度。会话状态按用户隔离。

证件号、密钥、私人手机号默认不进上下文；必须用时先脱敏，并且不写进长期记忆和普通日志。日志记 trace id、工具名和状态码。排障要用原文时，走有权限的短时抽样。回复发出前再扫一遍，避免模型把工具返回里的隐藏字段复述出来。

工具按最小权限开通，写操作有确认和审计。用户能查看和删除自己的记忆。企业文档不拿去训练，除非有明确授权。文档和消息里的「忽略权限」改变不了工具白名单。发给模型供应商的内容同样算出域，高密场景用约定的部署方式，并限制外发的工具结果长度。

### 4. 如何设计一个支持多模态（文本、语音、图像）的飞书 Agent？

**参考答案**

多模态扩展的是感知和展示。推理和执行仍走同一套工具循环，避免每种输入各写一个 Agent。

文本直接进入会话。语音先转写，并带上置信度，置信度低就让用户确认文字。图片消息先用 `image_key` 把文件取下来，再做 OCR 或视觉理解，产出描述和结构化字段，例如截图里的会议时间。资源接口同样受会话权限约束，拿不到文件就明确失败。这些观察收成同一条：用户说了什么、看到了什么、哪里不确定。

纯文本用对话模型，带图时才换视觉模型，用来控制费用和 token。订日历、发消息的工具与模态无关。短确认回文本，需要点选的会议候选回卡片。

一张图会变成大量 token，要限制张数和分辨率。语音识别错误会污染槽位，关键字段以用户确认为准。图片里出现别人的信息，不因此扩大日历或文档权限。办公场景优先「转成文本再进原来的 Agent」，路径更好回归。

### 5. 在电商场景下，如何设计一个库存监控 Agent？（实时数据感知、预警机制）

**参考答案**

库存数字由事件和规则盯着，Agent 负责解释异常和起草动作。

感知订阅下单、入库、调拨、预占这些变更，用事件更新可售库存。每条事件带 SKU、仓、变更量和版本。规则产生告警：可售低于安全库存、下降速度异常、预占长时间不释放、渠道库存和主库存对不上。告警写明 SKU、当前量、阈值和最近变更，按仓和负责人去重，并抑制抖动。通知可以落到飞书卡片。

Agent 收到告警后，检索该 SKU 的补货策略，汇总原因，给出补货、调拨或忽略并填写原因。改库存走交易或仓储接口，带幂等键和权限。用户在卡片上确认后才执行。

可售的定义（现货减预占、是否含在途）要和交易系统一致。事件要能按版本重放。大促时合并同类告警。全自动补货只留给规则已经很稳的 SKU，默认由人确认。模型用于归类和文案，库存还剩多少以事件计算的结果为准。

### 6. 如何解决 Agent 的“幻觉”问题？在飞书办公场景中，如何确保生成内容的准确性？

**参考答案**

办公场景里更危险的幻觉，是编出一个不存在的会议、人或文档结论。事实从工具和文档来，模型负责组织语言。

时间、会议室占用、员工姓名和 open_id 都以 API 结果为准。模型提到工具结果里没有的时间或人名，回复前丢掉或改成追问。制度、纪要、说明走 RAG，答案要能指回片段；检索为空就说没有找到。写操作使用确认卡片，列出即将创建的字段，确认后按这份结构化状态调用 API。用户看见的字段和提交的字段用同一份状态渲染。

工具参数做 schema 和业务校验，例如结束时间早于开始时间。线上把「没有调用工具却给出确定事实」记成 Bad Case。缓存的忙闲带查询时间，过期就重查。权限不足时说明看不到。

容易漏的是卡片文案。正文若由模型自由发挥，会和按钮上的真实参数不一致，所以文案也从结构化状态生成。

### 7. 如何做 Agent 的持续优化？线上遇到 Bad Case 如何处理？

**参考答案**

持续优化是一条闭环：线上留得下轨迹，Bad Case 进集合，改动能回归，再灰度。

每轮记下意图、候选工具、实际调用、参数校验、用户是否改口或取消，以及最终业务结果。Bad Case 来自失败任务、人工接管、差评和抽检。先分类：理解错、路由错、参数错、工具失败、检索错，或在不该写的时候写了。理解问题改提示和槽位，路由问题改候选和工具描述，检索问题改切块和过滤，超时问题改下游。不要把所有修改都堆进系统提示。

每条 case 写成可回放用例：输入事件、允许的工具、期望的状态或 API 参数。改完先跑这批，再跑全量，同时看成功率和费用。按租户或部门灰度，保留回滚，包括把写操作降成只给建议。

影响写操作正确性的 case，先加规则短路止损，再改模型行为。进评测集前去掉个人内容和他人日历详情。这个坑要留在用例库里，下个版本才会被拦住。

### 8. 你如何看待 Agent 与 Workflow 的边界？在什么场景下应该用 Workflow 替代 Agent？

**参考答案**

Workflow 是人预先写好的分支和顺序。Agent 是运行时由模型在工具和约束里选择下一步。看路径稳不稳定、错一步的代价，以及输入还有没有开放说法。

步骤和异常都枚举得清时用 Workflow。例如审批通过、订会议室、发邀请、落纪要模板，每步的 API 和失败补偿都明确，流程引擎更好审计，延迟也稳。输入是自然语言、步骤随情况变化时用 Agent，例如要躲开若干人的特殊时间限制来排会。

常见做法是外层 Workflow、内层 Agent。流程规定先查权限、再抽取、再确认、最后创建；「改到周四下午」这句话交给模型。一进写日历，就回到流程节点。

必须证明每一步做过、失败要补偿、同一输入要同一路径，或模型在两步之间反复摇摆时，把这段收成 Workflow。长尾说法仍留在 Agent 里，避免流程图把所有例外都画进去。

### 9. 在团队协作中，如何管理 Agent 的开发流程？（需求分析、模型选型、测试上线）

**参考答案**

把 Agent 按产品功能管，分成需求、方案、评测、上线，每段都可以停。

需求写清谁用、怎样算做成、哪些动作可以自动、哪些必须确认、错了怎么撤回，同时写明不做什么。方案里一起定模型、工具和规则的分工，并准备一个小评测集，覆盖主路径、权限、冲突和提示注入。模型选型用这批评测比较任务成功率、工具选对率、延迟和单次费用。简单请求用小模型路由，难例再用大模型。

测试分三层：工具和规则的单测、评测集回放、沙箱租户里的端到端。写操作先打到测试日历。上线按租户或部门灰度，监控成功率、人工接管和越权拦截。回滚开关要能把写操作降成只出建议。提示、工具 schema、模型和规则一起版本化，只回滚代码可能回不到当时的行为。

产品和业务定成功标准，工程拥有工具和权限，应用侧负责提示和评测。提示词和工具描述的改动走评审和回归。Bad Case 进同一套用例库。

### 10. 手写算法：实现一个简单的任务规划算法（多步任务分解）

**参考答案**

用层次分解：复合任务有若干种拆法，按优先级排列，每种拆法是一组有序子任务。子任务还可以再拆，直到变成可以直接执行的原语工具。按深度优先尝试拆法，第一条能完全拆开的就采用。用栈检查环，并限制深度，避免方法互相引用时停不下来。

返回的是一条原语序列，顺序就是执行顺序。成功的那条拆法按子任务个数线性展开；排在它前面、最终失败的拆法都会白走一遍。最坏情况和尝试的拆法数成正比，空间是递归栈加上结果。这是把目标展开成步骤，不包含执行失败后的重规划。要重规划，就把失败的原语标成不可用再跑一次。拆不开就向用户追问。

「安排会议」可以拆成查忙闲、确认、创建日程；查忙闲再拆成查参会人和求交集。四个都是原语时，结果就是这个顺序。创建日程排在确认后面，确认要写成显式步骤。同一个原语在序列里出现两次就会执行两次，只读步骤若要去重，在拆法里不要重复写。参数来自槽位，不在分解时现编。

```python
def decompose(goal, methods, primitives, max_depth=6):
    """methods: 任务名 -> 若干拆法，每种拆法是子任务列表。成功返回原语步骤，否则 None。"""

    def expand(task, depth, stack):
        if task in primitives:
            return [task]
        if depth == max_depth or task in stack or task not in methods:
            return None
        stack.add(task)
        for recipe in methods[task]:
            plan = []
            failed = False
            for sub in recipe:
                sub_plan = expand(sub, depth + 1, stack)
                if sub_plan is None:
                    failed = True
                    break
                plan.extend(sub_plan)
            if not failed:
                stack.remove(task)
                return plan
        stack.remove(task)
        return None

    return expand(goal, 0, set())
```
