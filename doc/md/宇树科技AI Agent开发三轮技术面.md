### 2. 请用通俗的语言解释一下什么是 AI Agent，它的核心组成部分有哪些？

**参考答案**

**结论：** AI Agent 是围绕一个目标反复“决定下一步、动手、看结果”的系统。大模型负责判断，程序负责执行和停止。

普通对话把话说完就结束。Agent 会改外部状态：查数据、调接口、写文件，再根据返回决定继续还是收工。

核心部分：

- **模型**：读目标和当前状态，决定下一步。
- **规划**：拆步骤，某一步失败就换路。
- **工具**：搜索、数据库、业务接口、代码。没有工具，就还是聊天。
- **记忆**：这场对话的上下文，以及跨会话留下的信息。
- **循环和停止条件**：步数、超时、完成信号。没有这一层，模型会一直调工具。
- **约束**：哪些工具能用，什么动作必须先问人。

容易漏的是停止条件和权限。只讲“大模型加提示词”，还不是 Agent。

### 3. 你了解的 AI Agent 开发主要技术栈是什么？（如 LangChain、LlamaIndex 等）

**参考答案**

**结论：** 按模型、编排、工具、知识、运行时、评测六层来记。框架只占编排层。

- **模型**：商用 API，或开源模型加 vLLM、SGLang 这类推理服务。
- **编排**：LangChain 提供模型、提示、工具等组件；有状态的循环、分支和断点续跑常用 LangGraph。LlamaIndex 强项是数据接入和检索。AutoGen、CrewAI 多见于多智能体分工。步骤固定时，自研一个循环就够。
- **工具**：函数调用，或 MCP 这种统一的工具接入协议。每个工具要有名称、参数和副作用说明。
- **知识**：切块、嵌入、向量索引、关键词索引、重排。
- **运行时**：会话状态、队列、超时、轨迹。
- **评测**：离线题集加上线轨迹。LangSmith、Langfuse 用来追踪，不是 Agent 本身。

容易漏：框架不负责检索准不准，也不负责工具是否幂等。早期的 `AgentExecutor` 只是一个固定循环，分支和暂停一多就会不够用。

### 4. 什么是 LLM 的“幻觉”问题？在 Agent 开发中，我们可以通过哪些技术手段来缓解或消除幻觉？

**参考答案**

**结论：** 幻觉是模型说得通顺，但内容没有根据，或和工具结果矛盾。不能消除，只能把高风险结论绑到可检查的证据上。

根子是它按概率续写，训练数据里又没有这个事实。Agent 里还会多两种：检索塞进了无关或过期文档，以及工具报错后模型自己把结果圆回去。

可用的手段：

1. **能查的就去查**：数据库、检索、计算，不让模型口算事实。
2. **回答带出处**：结论对应到某条观察或某段原文；没有出处就说不知道。
3. **独立校验**：规则、程序执行，或另一个只判断“证据是否支持结论”的步骤。同一个模型说“我再检查一遍”不算数。
4. **失败要可见**：检索为空、工具超时，都原样写回，不允许编一个成功结果。
5. **不可逆动作先确认**：发消息、改数据、驱动设备，闸门在程序里，不在提示词里。

调低温度只减少随机，不去掉胡编。思维链也可以先写错结论再补理由。

### 5. 请谈谈你对“提示词工程”的理解。在构建一个任务型 Agent 时，设计提示词有哪些关键原则？

**参考答案**

**结论：** 提示词工程是把目标、约束、工具和输出格式写成稳定可执行的说明，并用同一批题反复改。它不是文案润色。

任务型 Agent 的提示词等于一份岗位说明。原则：

1. **目标单一**，写清怎样算做完，怎样算做不了。
2. **工具写清楚**：用途、参数、副作用、失败时怎么办。模型靠这段文字选工具。
3. **输出固定结构**，方便程序解析，不要靠从散文里抠字段。
4. **指令和外部数据分开**。用户原文、网页、检索片段不能覆盖系统规则。
5. **例子只覆盖易错分支**，例如该追问却直接调用、该拒绝却照做。
6. **每次修改都回放同一批题**，不要只看一条演示。

容易漏：工具描述也是提示词，写得含糊就会选错工具。提示词也不能代替鉴权，写“不要删除数据”挡不住一个真有删除权限的工具。

### 6. 在 Agent 的上下文中，“上下文窗口”指的是什么？当任务对话超过上下文长度限制时，有哪些主流的处理方案？

**参考答案**

**结论：** 上下文窗口是模型这一次前向能够读入并生成的 token 上限。系统提示、工具描述、历史、检索片段和这次要写出的内容都占里面。

常见接口把读和写算在同一个窗口里，所以不能把额度全填成输入。超限时的主流做法：

1. **滑动窗口**：丢掉最早的轮次。实现简单，早期约束会一起丢。
2. **滚动摘要**：把旧对话压成摘要再放回去。摘要可能漏掉用户强调过的限制，关键约束要单独存放。
3. **外部记忆**：历史放进存储，这一轮只检索相关片段。
4. **结构化状态**：目标、已确认的事实、待办放进状态对象，不要回放全部原话。
5. **裁剪工具结果**：观察先抽出结论和证据编号，原始长文不整段塞回。
6. **换更长窗口的模型**：费用和延迟会上去，而且放在中部的证据仍可能被用得很少。

没有一种做法能无损保留全部历史。要保留的是约束和未完成的目标，不是每一句闲聊。

### 7. 为什么在 RAG 架构中需要使用向量数据库？它相比传统数据库在检索上有什么优势？

**参考答案**

**结论：** RAG 要按语义找相近文本。向量库提供的是高维向量的近似最近邻，这是传统等值和关键词索引不擅长的。

文档和问题先变成同一套嵌入模型的向量。检索变成“找距离最近的向量”，度量要和模型训练时一致，常见是余弦或内积，向量是否归一化也要一致。数据量大时不能逐条扫描，所以用 HNSW、IVF 这类近似索引。

传统关系数据库擅长等值、范围和事务；全文索引擅长关键词和 BM25。两边词面不同但意思接近时，关键词索引会漏。“退货”和“怎么把东西寄回来”就是这种例子。

向量检索的优势是语义召回，不是所有查询都更快、更准。型号、错误码、人名仍要靠关键词。线上常见做法是两路一起召回，再用元数据过滤租户、时间和权限。pgvector 这类扩展说明能力在索引，不在是不是独立产品。数据量大时常用的近邻索引是近似的；即使精确找到了最相近的段落，那段文字本身也还要再核对，不能直接当成事实。

### 8. 请简述 RAG 的基本工作原理。它如何帮助 Agent 获取更准确、更实时的信息？

**参考答案**

**结论：** RAG 是先检索、再把检索到的材料交给模型生成。模型不把知识背在权重里，回答受这次查到的内容约束。

离线：解析文档、清洗、按结构切块、嵌入，写入向量索引，同时保留原文、关键词和元数据。在线：先处理问题（补全指代、必要时改写），召回一小批候选，可选重排，再把内容和来源放进提示词，要求按材料回答。

对 Agent 的帮助有两层。准确性：事实有出处，材料里没有就可以拒绝，而不是靠参数记忆硬答。实时性：制度、价格、库存变了，更新索引即可，不用重新训练；模型权重本身并不因此变成实时的，新鲜程度等于入库有多快。

检索错了，模型会顺着错误材料说得很确定。所以 RAG 降低的是“没依据就编”，没有取消核对。Agent 还应把检索做成工具，让循环决定要不要再查，而不是每次都塞同一堆文档。

### 9. 你了解 ReAct 框架吗？请描述一下它的“思考-行动-观察”循环是如何工作的。

**参考答案**

**结论：** ReAct 把推理和行动交错进行。每行动一次，就把环境返回写回上下文，再决定下一步，而不是先写完一整段推理再作答。

一轮循环是：

1. **思考**：看目标和已有观察，判断现在该查、该算，还是可以回答。
2. **行动**：给出工具名和参数。运行时执行工具，模型不能自己编写执行结果。
3. **观察**：成功结果或错误写回上下文，成为下一轮的输入。

然后重复，直到模型给出结束，或触发步数、超时、人工确认。和只写思维链相比，它能用外部结果纠正中间判断。

现在的函数调用就是行动这一步的工程形式，思考可以是显式字段，也可以留在模型内部。不必为了贴论文，去解析一段 `Thought:` 自由文本。

代价是步数多、延迟高，还可能反复调用同一工具。步数上限是必需的。工具失败也是观察，应让模型改参数或换工具。

### 10. Agent 的“记忆”能力通常如何实现？短期记忆和长期记忆在设计中有什么区别？

**参考答案**

**结论：** 短期记忆放在这一次请求的上下文里，长期记忆放在外部存储里，用到时再取回来。

短期记忆就是当前消息、工作状态和最近的工具观察。窗口不够时，丢掉最早的原文，或压成摘要，但用户明确说过的约束要单独留着。它随着这次任务结束而失效，内容相对完整。

长期记忆要先决定写什么：用户偏好、已经确认的事实、做过的任务，而不是每一句都向量化。常见是结构化字段加工具检索，带上时间和来源。读的时候，稳定偏好可以常驻，其余按当前问题召回。新事实要能覆盖旧事实，用户也要能删。

区别在寿命、存放位置和写入是否经过挑选。进行中的中间结果是工作记忆，放在任务状态里，不要和用户偏好混进同一个向量池。记忆同样会错，不能因为“曾经记住”就不再核对。

### 11. 在多轮对话中，如何让 Agent 保持对话的一致性和连贯性？会遇到哪些挑战？

**参考答案**

**结论：** 连贯性靠一份显式对话状态，不靠模型自己记得前面说过的话。

状态里至少有：当前目标、已确认的事实和约束、待澄清的问题、已经执行且不能撤销的动作。每一轮把这份状态和最近几轮原话一起给模型。用户改口时，覆盖对应字段，不要让摘要里新旧说法并存。调用工具前先做指代消解，“它”“刚才那个”要变成具体对象。

挑战主要是：

- 话题切换后，旧目标还占着状态。
- 摘要把用户强调的限制压掉了。
- 窗口截断后，早期约定消失。
- 话说回去了，但工具副作用已经发生。
- 一轮里有多件事，只完成了其中一件。
- 风格或立场跟着最近一条消息漂走。

回答前用钉住的约束做一次核对。长期偏好从记忆里读，不要从偶然的一句闲聊里推断。

### 12. 手写算法：实现一个简单的文本相似度计算函数（例如，使用 Jaccard 相似度或余弦相似度）。

**参考答案**

**结论：** Jaccard 看两个集合重叠的比例，余弦看两个向量的方向是否一致。字面相似可以用字片或词袋；语义相似要先做嵌入，再算余弦。

Jaccard 定义为 \(|A \cap B| / |A \cup B|\)。它不管出现次数和顺序。余弦是点积除以两个范数的乘积，一般向量落在 -1 到 1；词袋计数非负，所以词袋余弦落在 0 到 1。任一侧范数为 0 时方向无定义，函数返回 0。两个空文本视为相同，返回 1。

下面用字符二元组，中英文都不依赖分词器。比较前去掉空白，并忽略 ASCII 大小写。长度不足 2 的文本用自身当唯一 token。已经有分词时，把 token 换掉，公式不变。

```python
import math
from collections import Counter


def tokens(text: str) -> list[str]:
    text = "".join(text.lower().split())
    if len(text) < 2:
        return [text] if text else []
    return [text[i : i + 2] for i in range(len(text) - 1)]


def jaccard_similarity(a: str, b: str) -> float:
    sa, sb = set(tokens(a)), set(tokens(b))
    if not sa and not sb:
        return 1.0
    return len(sa & sb) / len(sa | sb)


def cosine_similarity(x: list[float], y: list[float]) -> float:
    if len(x) != len(y):
        raise ValueError("向量维度必须相同")
    dot = sum(a * b for a, b in zip(x, y))
    nx = math.sqrt(sum(a * a for a in x))
    ny = math.sqrt(sum(b * b for b in y))
    if nx == 0.0 or ny == 0.0:
        return 0.0
    return dot / (nx * ny)


def bow_cosine(a: str, b: str) -> float:
    ca, cb = Counter(tokens(a)), Counter(tokens(b))
    if not ca and not cb:
        return 1.0
    vocab = list(ca.keys() | cb.keys())
    return cosine_similarity([ca[t] for t in vocab], [cb[t] for t in vocab])
```

建集合或词袋是 \(O(n+m)\)，Jaccard 的交并也是哈希集合上的线性时间，空间 \(O(n+m)\)。\(n\)、\(m\) 是 token 数。

容易漏：词袋余弦仍是字面重合，和嵌入余弦不是一回事。Jaccard 丢掉词频，词袋余弦保留词频但丢掉顺序。“北京”和“京北”的二元组可以分开，单字集合则分不开。

### 2. 请详细介绍一个你参与的 AI Agent 相关项目，你在其中的角色和解决的核心问题。

**答题思路**

用“任务 → 架构 → 你的决策 → 失败 → 结果”讲，不要讲成框架教程：

1. **任务**：用户是谁，怎样算完成。说明为什么固定流程不够，才用了 Agent。
2. **链路**：入口、状态、模型、工具、检索、停止条件。用四五句讲清数据怎么流。
3. **你的边界**：点名你写过或拍过板的模块，其余明确说是同事的。
4. **核心问题**：只展开一个，例如检索命中但回答不忠实、工具死循环、延迟过高。按“现象 → 怎么定位 → 试过什么 → 留下什么”讲。
5. **结果和复盘**：指标用真实的。最后说如果重做，哪一个设计会换掉。

预备追问：为什么不用更简单的方案、坏例从哪来、你怎么知道是变好了。

### 3. 在项目中，你们是如何进行技术选型的（比如选择特定的框架、模型或向量数据库）？权衡了哪些因素？

**答题思路**

按“约束 → 候选 → 用什么标准淘汰 → 放弃了什么”讲。没有测过的不要说成测过。

建议覆盖三个真正做过的选择：

1. **模型**：数据能不能出域，决定 API 还是自建推理。再比工具调用是否稳定、延迟、费用、失败时有没有备用模型。
2. **编排**：流程如果只是“检索然后回答”，链式调用就够。有分支、暂停、断点续跑，再考虑 LangGraph 或自研状态机。讲清团队是否养得起这个框架的升级和排障。
3. **向量库**：看数据量、元数据过滤、要不要混合关键词、谁来运维。小数据用现有数据库的向量扩展就够，不要为了选型而单独再养一个组件。

比较标准用你们自己的离线题集：任务成功、关键字段是否忠实、p95 延迟、单次费用。结论里一定要有一个被放弃的方案，以及它输在哪条标准上。

### 4. 针对你提到的项目，如果 RAG 的检索效果不理想（比如召回率低或精度差），你会从哪些方面进行排查和优化？

**参考答案**

**结论：** 先分开看召回和精度。召回低是正确材料没进候选，精度差是候选里噪音太多。两件事的改法不同。

先拿一批有标准证据的问题，记下原始问题、改写后的问题、召回 id 和分数。正确段落一次都没出现，就是召回问题；出现了但排得很后，或答案段落根本不该被切成这样，再谈精度。

召回低时按这个顺序查：问题和文档是不是同一个嵌入模型，查询侧的指令前缀有没有漏；建库和查询的度量、归一化是否一致；切块是否把答案切开，标题和表格是否丢失；权限、时间等过滤是否太严；型号、错误码这类词是否缺了关键词一路；“它多少钱”这种指代有没有先改写；索引是不是旧的。

精度差时看块是不是太大、主题混在一起，有没有只按向量分截断、有没有把过期文档和现行文档一起召回。重排只能整理已经召回到的候选，补不回没召回的文档。

优化时一次只改一件，回到同一批题上看召回率和最终回答是否忠实。先改查询改写、切块和混合检索，再加重排。换嵌入模型放在能量化之后。不要同时改五处，否则不知道是哪一处生效。

### 5. 在项目中，Agent 的决策逻辑是如何设计的？是否应用了 ReAct 或类似框架？遇到了什么困难？

**答题思路**

这题要讲你的真实控制流，名字对得上即可。按下面的顺序：

1. 请求进来后，状态里有什么：目标、已确认事实、可用工具、剩余预算。
2. 谁决定下一步。模型可以在工具集里选，也可以是状态机规定这一步只准调用某一类工具，模型只填参数。
3. 如果用了 ReAct：行动是不是函数调用，观察写回哪里，结束条件是什么。如果没用：说明流程固定，状态机更可控，不要硬套论文名字。
4. 困难只讲一个你真遇到的：死循环、选错工具、观察太长把约束挤出窗口、同一输入结果飘忽。讲你怎么从轨迹里发现它。
5. 限制怎么落地：步数和超时、相同失败不重试、参数校验、写操作要人确认。说你留下的那条机制，不说“后来优化了提示词”。

预备追问：工具抛错时模型能不能改参数再试；两个工具都像能用时听谁的；进程中断后从哪一步继续。

### 6. 如何评估一个 AI Agent 的好坏？你们项目采用了哪些评估指标或方法？

**参考答案**

**结论：** 先定义任务成功，再拆过程。最终那句话碰巧对了，不能说明 Agent 是好的。

建议同时看这几类：

- **结果**：任务是否完成，有多少比例转给人工。
- **过程**：工具名和关键参数是否正确，有没有多余步骤，工具失败后能不能恢复。
- **忠实**：结论能否被这次的观察或原文支持。检索系统再单独看召回率、精确率，不要只看最终回答。
- **运行**：延迟、单次任务的 token 和费用、失败率。
- **安全**：注入、越权和该拒绝的请求有没有挡住。

方法上，保留一套固定回归题，改提示词或改检索都重放。同一题要多跑几次，因为采样会晃。模型打分可以帮忙分级，但评分标准要先和人标过的样本对齐，不能只信另一个大模型。

线上看重试、放弃、人工接手和费用，不只看点赞。讲项目时只举你真实接入过的两三项目，以及题集是怎么来的。没有轨迹评测，就不要说自己做了 Agent 评测。

容易漏：正确率要能切开检索错、工具错和生成错。只看最终答案，会把“没调工具但蒙对”算成成功。

### 7. 在工程化部署一个 Agent 时，你考虑过哪些问题？（如性能、并发、稳定性、成本）

**参考答案**

**结论：** 一次用户请求会变成多轮模型调用和工具调用。限流、超时和费用都要按这一整段循环算，不能只按 HTTP QPS 算。

- **性能**：回复尽早流式输出。分类和路由可以用更小的模型，难步骤再用强模型。彼此无关的只读工具并行。相同的检索和幂等读可以缓存。
- **并发**：运行进程不留会话，状态放在外部。限制单个租户同时跑的循环数。长任务进队列，接口负责提交和订阅，不把工作线程一直占着。
- **稳定性**：每一步有超时，整段有最大步数。工具失败写回观察，让循环决定重试或停止，不要把整个请求打成未捕获异常。只有幂等读能自动重试；写操作要有幂等键。模型供应商要有熔断和备用。
- **成本**：每个任务有 token 预算。能用规则或数据库确定的事实，不要交给模型。上下文只留结论和证据编号。

轨迹用同一个请求 id 串起来，否则线上无法复盘。进程挂了之后，从检查点继续时不能把已经生效的写操作再做一遍。

### 8. 如果让你设计一个支持多智能体协作的系统，你会如何规划它们之间的通信和任务分配？

**参考答案**

**结论：** 默认仍是一个 Agent 加一组工具。只有权限、技能或可以并行的子任务明显不同，才拆成多个 Agent。

通信用结构化消息：发送者、任务 id、输入、状态和结果。不把两个模型的自由对话当接口。已经确认的结果放进共享状态，谁都能读；每个字段只有一个写入者。工作者不改彼此的草稿。

任务分配由编排者维护一张有依赖的任务图。每个子任务有负责人、输入、验收方式和步数上限。没有依赖的并行，有依赖的等结果。失败把错误交回编排者，由它重派或停止，避免两个 Agent 重试同一次写操作。

权限按角色收窄，不要每个 Agent 都拿全部工具。所有消息和工具调用进同一条轨迹，否则转述之后无法查是谁先错的。

代价要主动讲：轮数、费用和延迟会涨，错误也会在转述里被放大。如果一个工具调用就能完成，就不要再包装成一个“专家 Agent”。

### 9. 在开发面向用户的 Agent 时，如何考虑安全性和伦理问题（如防止被恶意引导、数据隐私）？

**参考答案**

**结论：** 用户输入、检索内容和工具返回都是不可信数据。权限做在运行时，不做到提示词里。

恶意引导包括用户直接要求越权，也包括网页、文档、工具结果里夹带的指令。系统规则放在独立通道，外部文本不能改工具权限，也不能让模型“忽略之前的要求”。工具按白名单暴露，参数做 schema 校验。

会发消息、付款、删数据、驱动真实设备的工具，默认要人确认。确认和急停放在工具闸门。模型答应“我会小心”不算保护。

隐私上只采集完成任务需要的数据，按用户隔离记忆和索引，日志脱敏，规定保留期限。不要把密钥放进提示词。能不出域的数据就留在自己的推理环境。

伦理上要让用户知道对方是 AI。高影响决定留给人。该拒绝的请求给出拒绝，不提供绕过步骤。输出过滤只能做补充，不能当成主防线。

### 10. 谈谈你对“Harness”或“Agent 框架”的理解。一个优秀的框架应该解决哪些核心问题？

**参考答案**

**结论：** Harness 是模型外面的运行时。它把一次“想一下”变成可停止、可恢复、可审计的循环。模型不负责这些。

一个够用的框架要解决：

1. **控制流**：何时调模型、何时调工具、何时因为步数、超时或完成信号停下来。
2. **状态**：计划、观察和检查点要能持久化，进程挂了从某一步继续，而且不重复副作用。
3. **上下文装配**：在窗口预算内放入系统规则、状态、检索和最近观察。
4. **工具契约**：参数校验、超时、错误变成统一的观察。
5. **人在回路**：危险步骤可以暂停，等人决定后再继续。
6. **追踪**：每一步能按请求回放，评测能直接吃这条轨迹。

LangGraph 这类图运行时解决的是状态、分支和持久化，不是检索质量，也不是业务工具好不好。步骤是一条直线时，不必先引入图。框架也不是效果来源。

### 11. 当 Agent 需要调用外部工具或 API 时，如何保证调用的安全性和稳定性？

**参考答案**

**结论：** 把工具当成一组权限受控的远程调用。模型只提出调用，运行时决定能不能执行。

安全：

- 工具和参数都走白名单与 schema，多余字段丢掉。
- 使用用户自己的权限，不给 Agent 一把管理员凭证。
- 能访问 URL 的工具要限制域名和协议，避免被模型带去访问内网。
- 代码执行放进沙箱，限制网络、文件系统和时间。
- 工具返回限长，并当作不可信数据，防止结果里的指令反过来指挥模型。

稳定：

- 每次调用有超时、限流和熔断。
- 只有幂等的读可以自动重试。写操作带幂等键，超时后先查询是否已经生效。
- 错误分类后写回观察：参数错就让模型改，服务挂了就停止或降级。
- 调用参数和结果进审计日志，但要脱敏。

容易漏：重试一个付款或发命令接口，会把动作做两次。稳定性不是“失败了就再调一次”。

### 12. 手写算法：实现一个简单的基于前缀树的敏感词过滤功能。

**参考答案**

**结论：** 把敏感词建成前缀树，扫描文本时沿树往下走，走到词尾就命中。它解决的是大量词的精确多模式匹配。

每个字一条边，词结束的节点打标记。ASCII 字符入库和查询都转成小写，这样索引和原文仍一一对应。从每个下标出发向下走，才能命中重叠词。例如词表里同时有“ab”和“bc”时，匹配到“ab”就跳到词尾，会漏掉“bc”。

构建时间、空间都和词表总字数成正比。文本长度为 \(n\)、最长词为 \(L\) 时，朴素扫描是 \(O(nL)\)。词表很大且要求线性扫描时，再给节点加失败指针，升级成 AC 自动机。

```python
class _Node:
    def __init__(self) -> None:
        self.children: dict[str, "_Node"] = {}
        self.end = False


def _key(ch: str) -> str:
    return ch.lower() if ch.isascii() else ch


class SensitiveFilter:
    def __init__(self, words: list[str]) -> None:
        self.root = _Node()
        for word in words:
            node = self.root
            normalized = "".join(_key(ch) for ch in word.strip())
            if not normalized:
                continue
            for ch in normalized:
                node = node.children.setdefault(ch, _Node())
            node.end = True

    def mask(self, text: str, repl: str = "*") -> str:
        chars = list(text)
        hit = [False] * len(chars)
        for i in range(len(chars)):
            node = self.root
            j = i
            while j < len(chars) and _key(chars[j]) in node.children:
                node = node.children[_key(chars[j])]
                j += 1
                if node.end:
                    for k in range(i, j):
                        hit[k] = True
        return "".join(repl if flag else ch for flag, ch in zip(hit, chars))
```

前缀树不做归一化以外的模糊匹配。全角半角、插入干扰符号、谐音，都要在入树前处理，或者另做检测。空词不能插入，否则根节点会变成结束节点。过滤可以替换，也可以拿到命中区间后整句拒绝。

### 1. 自我介绍

**答题思路**

三面看的是取舍，不是技术栈清单。一分钟内讲完：

1. 你负责过的系统边界：用户量或任务复杂度用真实量级，不夸大。
2. 一个你拍过板的取舍：例如自研循环还是用现成框架，强模型还是分级模型，以及你用什么标准做的决定。
3. 一次线上或评测里的失败，你如何把责任收回到可验证的改动上。
4. 结尾说明你想做的是可扩展的 Agent 运行时或机器人任务闭环，不是再讲一遍项目功能。

### 2. 请从架构师的角度，描述一个高性能、可扩展的 AI Agent 服务系统设计，需要考虑哪些核心模块？

**参考答案**

**结论：** 按接入、运行时、模型、工具、知识、状态、观测拆开。运行进程无状态，状态和长任务放到外部，模型和工具分别扩容。

1. **接入层**：鉴权、按租户限流、流式输出。
2. **运行时**：决策循环、步数和超时、检查点。这是 Harness 所在的位置。
3. **模型网关**：路由、备用模型、失败切换、token 计量。业务代码不直接绑死一家供应商。
4. **工具层**：注册、schema、沙箱、权限、超时和幂等键。
5. **检索层**：查询改写、混合召回、重排、引用。
6. **状态和记忆**：会话状态与长期记忆分开，按用户隔离。
7. **队列**：长任务异步执行，接口返回任务 id。
8. **观测和评测**：轨迹、费用、延迟，以及一套固定回归题。

扩展时先看瓶颈在模型、工具还是检索，不要把整个服务复制一遍。性能上，无关的只读工具并行，重复读走缓存。

难点是副作用和恢复：节点挂了可以从检查点继续，但已经生效的写操作不能重放。所以写操作要能用幂等键查询“是否做过”。

### 3. RAG 中的“重排序”是什么？它在提升最终答案质量中起到什么作用？有哪些常见的重排序策略？

**参考答案**

**结论：** 重排序是召回之后的精排。第一阶段从大库里快速找候选，第二阶段把问题和候选放在一起再打分，决定谁进入提示词。

双编码器把问题和文档分别变成向量，快，但两边没有细粒度交互，相近主题容易挤在前面。重排模型看到的是这一对的原文，精度更高，计算也更贵，所以只处理召回的前一小段。具体条数看延迟预算，没有统一默认值。

它的作用是提高最终上下文的精度，减少无关段落占窗口、把回答带偏。它不能找回第一阶段就没进候选的文档。召回是 0 时，重排没有输入。

常见策略：

- **交叉编码器**：质量和成本比较均衡，是最常用的语义重排。
- **晚交互**：比双编码器细，又不必每对都完整做一次交叉编码。
- **大模型打分**：可以逐条打，也可以一小批一起排。候选已经很少时才划算。
- **业务特征**：时间、来源、权限和语义分一起用，避免只拿语义分把过期文档排上去。

多路召回可以先按名次融合，再送给重排。融合不是重排的替代品。

### 4. 对比微调大模型和使用 RAG + 提示词工程这两种方案来提升 Agent 能力，各自的优缺点和适用场景是什么？

**参考答案**

**结论：** 微调改的是行为习惯，RAG 和提示词提供的是这次任务的外部依据。事实会变，优先改资料；稳定的格式和动作习惯怎么提示都守不住，再考虑微调。

| | 微调 | RAG + 提示词 |
| --- | --- | --- |
| 改什么 | 模型权重 | 外部资料和指令 |
| 适合 | 输出格式、语气、工具调用习惯，或把这些习惯收进更小的模型 | 会变化的事实、私有文档、必须给出来源的回答 |
| 优点 | 少占上下文，同类任务上行为更稳 | 更新资料不用重新训练，回答可以引用 |
| 缺点 | 数据贵，事实过时，难给出处，窄数据可能损伤原有能力 | 检索错就会跟着错，上下文和延迟上升，教不会一项新的稳定技能 |

两者经常一起用：微调管“怎么做”，RAG 管“根据什么说”。顺序上先把提示词、工具描述和检索做对，再收集真实失败样本去微调。否则是在拟合一套有问题的流程。

参数高效微调（如 LoRA）只说明训练成本可以降低，不说明它适合当知识库。上周才改的制度，应该进索引，而不是再训练一次。秩这类超参数看任务和显存，没有通用默认值。

### 5. 如果业务要求 Agent 在复杂任务中必须保证极低的幻觉率，甚至需要可验证的推理过程，你会如何设计解决方案？

**参考答案**

**结论：** 不能靠模型承诺“我不胡编”。每个会对外生效的结论，都要有独立于生成过程的证据或程序校验；没有证据就拒绝。

1. 能用数据库、检索、计算或代码确定的事实，不允许模型直接说。
2. 输出用固定结构，每条事实带证据 id。没有证据的字段只能是未知。
3. 校验器和生成器分开。规则、SQL 或测试可以直接执行。需要模型参加时，它只判断“这些证据是否支持这条结论”，不能沿用生成时的思维链。思维链可以和真实工具调用不一致，所以它不是证明。
4. 校验失败就改参数重试、换工具，或明确告诉用户缺什么。同一个模型自我反思，不能单独作为通过条件。
5. 不可逆动作和真实世界动作在工具层等人确认。
6. 计划、参数、观察和证据全部留在轨迹里，事后能重放。

延迟会增加。只对会生效、难撤销或高风险的步骤做全套校验，闲聊和草稿从简。所谓可验证，是外部检查能够复算，不是模型把理由写得更长。

### 6. 在多模态 Agent 成为趋势的背景下，你认为现有的技术栈会遇到哪些新的挑战？需要做哪些准备？

**参考答案**

**结论：** 现有栈默认上下文是字符串。图像、音频、视频进来之后，表示、费用、检索、评测和安全都要改，不能把原始媒体整段留在窗口里。

挑战：

- 视觉和音频 token 多，延迟和费用远高于文本。长视频不能逐帧进模型。
- 要保留时间戳和来源，否则工具结果对不上那一帧。
- 检索可以走多模态嵌入，也可以先转写再进文本索引。转写会丢掉只存在于画面里的信息。
- 模型会肯定地描述图里没有的东西，需要检测工具或可引用的区域。
- 纯文本回归题不够用。
- 感知错了再去调用动作工具，错误会进到物理世界。机器人场景里这是主风险。

准备：消息改成文本加媒体引用，原件进对象存储；上下文里只留引用、时间戳和短描述；关键视觉判断走专门工具；建立带媒体和标准答案的回归集；给媒体单独的预算、权限和保留期。图片或页面里夹带的指令，同样按不可信内容处理。

### 7. 你最近关注或学习哪些 AI Agent 领域的新技术、新论文或新开源项目？它解决了什么痛点？

**答题思路**

只讲一个你真正读过或跑过的东西。讲五个名字等于都没讲。

结构固定为：

1. 当时什么做不到，这是痛点。
2. 它的机制，用三句讲完，不要背摘要。
3. 你会用在哪一层，或者为什么先不引进。
4. 它明确解决不了什么。

下面只是备选，没看过就不要讲：

- **MCP**：把工具和上下文的接入收成统一协议，少为每个框架写一套适配器。它不提高规划能力。
- **带来检查点的图运行时**（如 LangGraph）：长任务中断后能从某一步继续。它不解决检索准不准。
- **GraphRAG**：先把文档建成图并做社区摘要，用来回答跨全文的问题。纯向量检索容易只打中局部片段。代价是建图和更新更重。
- **推理模型和测试时计算**：难步骤上多花推理。延迟和费用上升，没有外部证据时，只是更长的胡编。

最后加一句你自己的判断：我们的主痛点是哪一个，所以这个技术值不值得进下一个迭代。

### 8. 当你和团队成员在技术方案（例如，选择自研框架还是使用开源框架）上产生分歧时，你会如何处理？

**答题思路**

把分歧收成一次有期限的技术决定，不要收成谁更懂。

1. 先对齐目标：这次争的是交付时间、效果、可控性，还是以后的维护成本。
2. 写下通过标准。例如两周内能否跑通现有轨迹、能否接上现有鉴权和追踪、许可证是否允许。标准在做原型之前写。
3. 默认分工可以说清楚：开源框架承担通用循环和状态，业务工具、权限和评测自己掌握。只有循环本身成为瓶颈，或许可证不行，才值得自研。
4. 用最小原型打这条标准。拿轨迹和题集说话。
5. 由负责这条链路的人拍板，写上复查时间。拍板后按决定执行，复查点再到数据上翻案。

讲一次你真实经历过的分歧。没有框架之争，就讲别的技术分歧，重点是标准和结果，不是你最后说服了谁。

### 9. 你如何带领或影响团队，保持对 AI 领域快速发展的技术敏感度和学习能力？

**答题思路**

学习要挂在线上问题上，否则会变成转发链接。可以讲你能推动的机制：

1. 这个月哪类失败最多，就只挖那一块。你自己先做一次短分享。
2. 分享模板固定：问题、做法、代价、我们用不用。不收读书笔记。
3. 给有期限的 spike。结果必须是一条可回放轨迹，或回归集上的对比。
4. 新框架先在旁路跑，不直接替换生产主链路。
5. 一个人深入后带回来，避免每个人都浅浅看一遍。

如果你还没有带人，就讲你如何影响同事：把一篇方法和一次失败案例绑在一起，让别人能用你的评测脚本复现。不要承诺“我会组织每日论文打卡”。

### 10. 对于 AI Agent 技术的未来商业化落地，你最看好哪个方向？为什么？

**答题思路**

选一个你能讲清“谁付费、成功怎么判定、难在哪里”的方向。面试宇树，最顺的立场是机器人上的任务型 Agent，但前提是你真愿意做物理世界的可靠性，而不是借公司名义谈风口。

可以这样组织：

3. **为什么能形成生意**：机器人的价值在于把一件事做完。巡检、导览、搬运这类任务有明确成败，才有人持续付费。
4. **主动讲难点**：物理世界的长尾、感知错误会被动作放大、评测难、演示和量产的差距。
5. 如果你更熟的是软件流程或编程 Agent，就讲那个，并说明它和机器人技能编排哪里相通。不要报市场规模。

### 11. 手写算法：模拟一个简单的 Agent 决策循环，给定一组工具和任务描述，输出执行计划（伪代码或关键步骤即可）。

**参考答案**

**结论：** 执行计划是循环跑出来的轨迹，不是一次生成的待办清单。每一步都是：读状态、决定、执行或结束、把观察写回。

关键步骤：

1. 初始状态只有任务、可用工具和空的观察。
2. 决策函数返回两种结果之一：调用某个工具，或给出最终答案。生产里这是一次带工具 schema 的模型调用，下面用规则代替，只为把循环跑通。
3. 工具必须在白名单里。参数错误或执行失败都变成观察，不把异常抛出循环。
4. 达到最大步数仍未结束，就停止并标明原因。
5. 若要求先给人看计划再执行，把真正的工具调用换成“待确认动作”，在这一步暂停。

步数上限是 \(S\)。循环本身 \(O(S)\)，时间和费用由模型和工具决定。空间是整条轨迹，观察很长时要先裁剪再写入下一步。

```python
def run_agent(task, tools, decide, max_steps=6):
    messages = [{"role": "user", "content": task}]
    plan = []
    for step in range(1, max_steps + 1):
        decision = decide(messages, list(tools))
        action = decision.get("action")
        if decision.get("final") is not None and not action:
            plan.append(
                {"step": step, "thought": decision["thought"], "final": decision["final"]}
            )
            return plan
        if not action or action.get("name") not in tools:
            plan.append({"step": step, "stopped": "没有可执行的合法工具"})
            return plan
        name = action["name"]
        args = action.get("args") or {}
        try:
            obs = tools[name](**args)
        except Exception as exc:
            obs = f"工具失败: {exc}"
        plan.append(
            {
                "step": step,
                "thought": decision["thought"],
                "action": name,
                "args": args,
                "observation": obs,
            }
        )
        messages.append({"role": "assistant", "action": action})
        messages.append({"role": "tool", "name": name, "content": str(obs)})
    plan.append({"stopped": "达到最大步数"})
    return plan


def decide(messages, tool_names):
    """规则替身。生产环境换成返回函数调用的模型。"""
    seen = [item for item in messages if item["role"] == "tool"]
    if "get_weather" in tool_names and not seen:
        return {
            "thought": "还没有天气，先查询",
            "action": {"name": "get_weather", "args": {"city": "北京"}},
        }
    weather = seen[-1]["content"] if seen else ""
    answer = "北京有雨，建议带伞" if "雨" in weather else "北京暂无降雨，可以不带伞"
    return {"thought": "已经有观察，可以回答", "final": answer}


tools = {"get_weather": lambda city: f"{city}今天小雨"}
execution_plan = run_agent("查北京天气，并决定要不要带伞", tools, decide)
```

这段规则只认识示例任务。模型版要把工具名称、参数 schema 和历史观察一起传入，并拒绝白名单之外的调用。相同失败连续出现时，也应提前停止，不能等到步数耗尽。

### 1. 请做一个简单的自我介绍（非技术角度）。

**答题思路**

45 到 60 秒，少用框架名：

1. 你现在做什么事，服务的是谁，结果用业务语言说。
2. 你怎么和产品、测试或硬件同事合作，举一个你推动过决定的例子。
3. 为什么这次看机会，用你的真实动机，落到你想做的产品形态上。避免“学习氛围好”这种空话。
4. 收在你希望承担的责任上：把一件事从方案做到线上可维护。

技术名词最多留一个，防止把 HR 面讲成项目复盘。

### 2. 为什么选择宇树科技？对我们公司或 AI Agent 业务有什么了解？

**答题思路**

把个人原因和公开事实接起来，不要只说“贵司发展很好”。

公开信息够用的部分：宇树做高性能四足和人形机器人，业务在往具身智能走。Agent 在这里不是一个聊天窗口，而是把任务落到感知、技能和安全约束上的那一层。

可以按这个顺序：

1. 你为什么离开纯软件问答，想做会作用到真实世界的系统。用你的真实动机。
2. 你了解到的公司业务，只讲你查证过的产品形态，不背参数和市场份额。
3. 你的哪段经历接得上：工具调用的可靠性、评测、或和硬件/业务同学一起把闭环做完。
4. 你也知道难在哪里：动作一旦执行，错误比答错一句话更贵。说明你是来解决这个的。

避免空话，例如“改变人类”或“我很有热情”。

### 3. 你对自己未来 3 年的职业规划是怎样的？

**答题思路**

规划要能落到这条 Agent 链路，不写死职级和薪资：

1. **近一年**：独立负责一块，并对此线上负责。运行时、机器人技能编排、检索或评测，选你真正想做的一块。
2. **第二年**：能做方案取舍，带一两个人把一个场景做成可评测的闭环。
3. **第三年**：负责一个小方向，对质量和事故有担当，而不是只追新框架。
4. 最后反问：这个岗位近一年最重要的交付是什么，看和你的规划是否一致。

不要说“先积累再看机会”，也不要把三年计划讲成跳槽时间表。

### 4. 在以往的项目或工作中，遇到最大的挑战是什么？你是怎么克服的？

**答题思路**

选一次真实的冲突，优先选目标互相打架的情况，例如交付时间和安全、效果和成本。不要选“我加班把它做完了”。

1. 处境：约束是什么，你的责任到哪里。
2. 卡点：信息缺、意见不合，还是方案本身不成立。
3. 你的判断：你放弃了哪条路，依据是什么。
4. 结果：用真实后果说明，好的坏的都可以。坏的要讲你怎么收场。
5. 留下的习惯：例如先写失败标准，或危险动作必须有闸门。

技术细节点到为止。如果和二面是同一个项目，就讲协作或取舍这一面，不要把架构再讲一遍。

### 5. 你如何评价自己的优点和缺点？

**答题思路**

各讲一个，都要有别人能核对的事。

优点选和这个岗位有关的：能把模糊任务收成可测的闭环，或在意见不一致时先写标准再做原型。讲完事情本身，不要自己下“我学习能力强”这种结论。

缺点讲一个真的，并且已经有改法。例如前半段容易连续加方案，评测落后。改法是没有失败标准和停的条件，就不扩大范围。

不要说“我太追求完美”，也不要把粗心、不看安全边界这种岗位上的硬伤说成小小的缺点，除非你能证明已经改掉。缺点不要包装成优点。

### 6. 你期望的团队氛围和工作方式是怎样的？

**答题思路**

讲你能配合的方式，并给一个你自己的行为：

1. 分歧摊在问题和数据上，决定写下来，会后按决定执行。

3. 新想法先有小范围对比，再进主链路。
4. 你需要的反馈是具体的，例如哪条轨迹不合格，而不是“再智能一点”。

结尾可以问对方：一个需求从讨论到上线现在怎么走，出了事故谁来复盘。不要回答“我都能适应”。

### 7. 目前薪资状况如何？对薪资的期望是多少？

**答题思路**

数字只用你自己的真实包，面试前先算清楚。

1. 当前总包拆开：底薪、奖金、股票或期权、签字费，以及明年是否还有一次性部分。

不评价前公司给得低，也不在这一题里重新讲技术。
