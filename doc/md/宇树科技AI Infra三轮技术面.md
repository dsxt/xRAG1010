### 3. 解释数据并行、模型并行、流水线并行的区别和适用场景

**参考答案**

**结论**：三者切分的对象不同——数据并行切数据，张量并行切层内算子，流水线并行切层。

- **数据并行（DP）**：每卡一份完整模型，各自处理不同 batch，反向后对梯度做 AllReduce。实现简单、扩展性好，但每卡要放得下完整模型（可搭配 ZeRO/FSDP 切分状态）。适用于模型能放进单卡或配合 ZeRO 能放下的场景。
- **张量并行（TP，模型并行的一种）**：把单层的矩阵乘按行或列切到多卡，每层前向、反向都要集合通信（Megatron 的 MLP 和 Attention 每层前向 2 次 AllReduce）。通信频繁、延迟敏感，所以一般限制在单机 NVLink 内（常见 TP=2/4/8）。
- **流水线并行（PP）**：把连续的层分成多个 stage，放在不同卡上，用 micro-batch 填充流水线。只在 stage 边界传激活，通信量小、可以跨机，但有气泡（bubble 占比约 \((P-1)/(M+P-1)\)，P 是 stage 数，M 是 micro-batch 数），还要处理 stage 负载均衡。

实际大模型训练是组合：机内 TP，跨机 PP，外层 DP（再加 ZeRO-1），MoE 还会加 EP，长序列加 CP。

### 4. ZeRO 的三个阶段分别是什么，显存节省原理

**参考答案**

**结论**：ZeRO 消除数据并行中各卡冗余保存的模型状态，三个阶段依次切分优化器状态、梯度、参数。

以混合精度 + Adam 为例，参数量 \(\Psi\)：FP16 参数 \(2\Psi\)，FP16 梯度 \(2\Psi\)，优化器状态（FP32 主权重 + 动量 + 方差）\(12\Psi\)，合计 \(16\Psi\) 字节。设 DP 度为 \(N\)：

| 阶段 | 切分内容 | 每卡模型状态显存 |
| --- | --- | --- |
| ZeRO-1 | 优化器状态 | \(2\Psi + 2\Psi + 12\Psi/N\) |
| ZeRO-2 | + 梯度 | \(2\Psi + (2\Psi + 12\Psi)/N\) |
| ZeRO-3 | + 参数 | \(16\Psi/N\) |

通信方面：ZeRO-1/2 的通信量和普通 DP 相同（约 \(2\Psi\)，梯度 reduce-scatter + 参数 all-gather）；ZeRO-3 前向和反向都要先 all-gather 参数，通信量约 \(3\Psi\)，是 DP 的 1.5 倍，需要靠预取和重叠来掩盖。注意 ZeRO 只切模型状态，不切激活，激活要靠重计算等手段。

### 5. 设计一个支持千亿参数模型的分布式训练系统，需要考虑哪些方面

**参考答案**

**结论**：核心是在显存、通信、算力利用率和稳定性之间做联合设计，先估算再选并行策略。

1. **容量估算**：千亿参数混合精度 Adam 约 \(16\Psi\) ≈ 1.6TB 模型状态，加激活，必须多机多卡切分。
2. **并行策略**：机内 TP（NVLink），跨机 PP，外层 DP + ZeRO-1，MoE 用 EP，长序列用 SP/CP。让 TP 通信走高带宽链路，PP 尽量按拓扑切。
3. **显存优化**：BF16、选择性重计算、FlashAttention、融合算子、必要时 offload。
4. **通信优化**：梯度分桶重叠、PP 的 1F1B / interleaved、TP 通信重叠、拓扑感知的 rank 映射。
5. **数据**：预分词、顺序读、分片、可确定性恢复的 dataloader。
6. **容错**：健康检查、故障检测、自动重启、异步 / 分层 Checkpoint、备用节点。
7. **可观测性**：MFU、吞吐、各 rank 耗时、梯度范数、loss、硬件指标。
8. **工程**：配置可复现、并行度可调、Checkpoint 支持跨并行度重切分。

难点在于各维度互相牵制（比如加大 PP 减少显存但增加气泡），要用小规模实验和性能模型验证。

### 6. 如何诊断和优化低 MFU（Model FLOPs Utilization）问题

**参考答案**

**结论**：MFU = 模型实际有效 FLOPs / 硬件峰值 FLOPs，先用 profiler 把时间拆开，再针对性优化。

对 Transformer，每 token 训练约 \(6N\) FLOPs（N 为参数量，不含重计算，注意力项另算），用实测吞吐可算出 MFU。

**诊断**：用 PyTorch Profiler / Nsight Systems 看一个 step 的时间线，拆成：计算、暴露的通信、气泡、数据等待、CPU launch 空洞、同步点。同时对比各 rank 耗时，找 straggler。

**常见原因与对策**：
- 通信暴露：增加梯度分桶重叠、预取、调整 TP/PP/DP 布局，让通信走高速链路。
- 流水线气泡：增大 micro-batch 数、interleaved 1F1B。
- 小算子多、访存受限：算子融合、`torch.compile`、FlashAttention、融合 LayerNorm / 优化器。
- 矩阵太小：增大 micro batch 或 hidden 对齐到 8/64 的倍数，使用 Tensor Core。
- CPU 瓶颈：CUDA Graph、减少 Python 开销、避免频繁 `.item()` 同步。
- 数据加载：增加 worker、预取、预分词。
- 重计算过多：改为选择性重计算。
- 掉队节点：隔离慢卡或慢网卡。

### 7. NCCL 通信底层有哪些算法，Ring AllReduce 的优势是什么

**参考答案**

**结论**：NCCL 主要有 Ring、Tree（double binary tree）等算法，并按消息大小和拓扑自动选择；Ring 的优势是带宽最优。

- **算法**：Ring、Tree（跨机时使用双二叉树）、CollNet（利用交换机 SHARP 做网络内规约）、NVLS（NVLink SHARP，Hopper 机内）。**协议**有 Simple、LL、LL128，用于权衡延迟和带宽。
- **Ring AllReduce**：分成 reduce-scatter 和 all-gather 两阶段，各 \(N-1\) 步，每卡总发送量约 \(2\frac{N-1}{N}D\)，几乎与卡数无关，所有链路同时被利用，带宽最优，也没有中心节点瓶颈。
- **劣势**：延迟随 \(N\) 线性增长（\(2(N-1)\) 步），大规模、小消息场景下，Tree 的 \(O(\log N)\) 延迟更优。所以 NCCL 小消息或大规模时倾向 Tree，大消息倾向 Ring。

### 8. 训练中出现 Loss Spike 如何处理

**参考答案**

**结论**：先止损（回滚 + 跳过问题数据），再定位原因（数据、学习率、数值、硬件），最后加稳定性措施。

**应急处理**：
- 回滚到 spike 之前的 Checkpoint，并跳过 spike 附近的数据 batch（PaLM 报告用过这种做法），或适当降低学习率后继续。

**定位方向**：
- 数据：脏数据、重复数据、异常长序列。
- 优化器：学习率过大、warmup 太短、Adam 的 β2 太大导致更新滞后（大模型常用 β2=0.95）。
- 数值：FP16 溢出（改用 BF16）、注意力 logits 过大、softmax 或 LayerNorm 精度不足。
- 硬件：静默数据错误（SDC）、某张卡异常，可用跨 rank 梯度或 loss 对比排查。

**预防**：梯度裁剪、QK-Norm、z-loss、合理的 warmup 和 LR 衰减、监控梯度范数和参数范数、保留高频 Checkpoint 以便回滚。

### 9. 混合精度训练的原理和实现细节

**参考答案**

**结论**：前向和反向用低精度（FP16/BF16）提速并省显存，同时保留 FP32 主权重和关键算子精度，保证收敛。

**实现细节**：
1. 维护一份 FP32 主权重（master weights）和优化器状态，更新在 FP32 上进行，然后拷回低精度权重用于前向和反向。
2. 前向和反向在低精度进行，矩阵乘走 Tensor Core。
3. 精度敏感算子（softmax、LayerNorm、loss、归约）保持 FP32，`torch.autocast` 会自动管理。
4. **FP16** 动态范围小，梯度可能下溢，需要 **loss scaling**：loss 乘一个缩放因子，反向后再反缩放；遇到 inf/NaN 就跳过这步并降低缩放因子，连续若干步正常则增大。
5. **BF16** 指数位和 FP32 一样（8 位），动态范围够大，一般不需要 loss scaling，但尾数少，所以更需要 FP32 主权重。
6. 更新时注意梯度裁剪应在反缩放之后做。

FP8 训练在此基础上需要逐张量的缩放因子（scaling），属于更进一步的做法。

### 10. 梯度检查点技术如何工作，权衡是什么

**参考答案**

**结论**：梯度检查点（激活重计算）用额外的前向计算换取激活显存。

**原理**：前向时只保存部分层（checkpoint 点）的输入，丢弃中间激活；反向时，从最近的检查点重新做一遍前向，恢复该段激活再计算梯度。

**权衡**：
- 显存：激活显存从与层数成正比，降到约 \(O(\sqrt{L})\)（按均匀分段）。实际中常按 Transformer block 为单位做。
- 计算：多了约一次前向，全量重计算时总计算量约增加 30% 左右（前向 1 + 反向 2 变成 4，即 4/3）。
- **选择性重计算**：只重算占显存大但计算便宜的部分（如注意力的 softmax 和 dropout 等），Megatron 给出的方案可以几乎消除激活显存压力而额外计算很少。
- 注意点：被重计算的区域需要保证随机性一致（dropout 要保存 RNG 状态），且不能含有有副作用的操作。

### 11. 大模型训练中显存占用主要由哪些部分组成

**参考答案**

**结论**：主要是模型状态（参数、梯度、优化器状态）、激活，以及临时缓冲和碎片。

1. **参数**：BF16/FP16 下 \(2\Psi\) 字节。
2. **梯度**：\(2\Psi\)（有些实现用 FP32 梯度累积则是 \(4\Psi\)）。
3. **优化器状态**：Adam 的 FP32 主权重 + 动量 + 方差共 \(12\Psi\)。以上合计常说的 \(16\Psi\)。
4. **激活**：与 batch、序列长度、hidden、层数相关。Transformer 每层激活粗略与 \(s\cdot b\cdot h\) 成正比，注意力分数部分与 \(s^2\) 成正比（不用 FlashAttention 时），往往是长序列下最大的开销。
5. **临时缓冲**：通信 bucket、算子 workspace、CUDA 上下文。
6. **碎片**：缓存分配器碎片，可通过 `expandable_segments` 等配置缓解。

对应手段：ZeRO/FSDP 切模型状态，重计算和 SP 减激活，FlashAttention 去掉 \(s^2\) 的中间量。

### 12. 如何优化数据加载器效率，缩短数据到达模型训练的耗时

**参考答案**

**结论**：目标是让数据准备与 GPU 计算完全重叠，GPU 不等数据。

- **预处理离线化**：提前分词、打包成二进制或 mmap 格式，训练时只做顺序读取，避免海量小文件。
- **并行与预取**：DataLoader 多 worker、`prefetch_factor`、`persistent_workers`，用 `pin_memory=True` 加 `non_blocking=True` 异步拷贝到 GPU。
- **序列打包（packing）**：把多条短样本拼到固定长度，减少 padding 浪费。
- **存储**：数据分片，热数据放本地 NVMe 缓存，减少对网络存储的压力；多机各读不同分片。
- **GPU 侧预处理**：图像或视频解码、增强用 DALI 等放到 GPU。
- **可恢复**：记录数据读取位置，故障后能确定性恢复，避免重复或遗漏。
- **定位**：用 profiler 看 step 开头是否有 GPU 空闲等待，再决定优化 CPU、IO 还是网络。

### 13. AI 模型在嵌入式硬件上的优化部署有哪些技术

**参考答案**

**结论**：从模型压缩、编译优化、运行时三个层面降低延迟、显存和功耗。

1. **模型压缩**：量化（INT8、INT4，PTQ 或 QAT）、剪枝（结构化剪枝更利于硬件加速）、知识蒸馏、轻量网络设计。
2. **推理引擎与编译**：TensorRT、ONNX Runtime、TVM、厂商 NPU SDK，做算子融合、常量折叠、内存规划、自动选择 kernel。
3. **运行时优化**：固定输入形状、batch=1 低延迟、CUDA Graph 降低 launch 开销、零拷贝与内存复用、流水线化前后处理。
4. **精度与硬件匹配**：根据芯片支持的数据类型（FP16 / INT8 等）选择格式，并用校准集评估精度损失。
5. **系统层面**：线程亲和性、功耗和温度管理（限频）、模型分级（简单场景用小模型）。

部署前后要对比精度、延迟分位数（P99）和功耗，不能只看平均值。

### 14. 手写算法：实现一个简单的 Ring AllReduce 伪代码

**参考答案**

**思路**：把每个 rank 的数据切成 \(N\) 块。先做 \(N-1\) 步 reduce-scatter：每步每个 rank 把一块发给右邻居并累加收到的块，结束后 rank \(r\) 持有完整规约后的第 \((r+1)\bmod N\) 块。再做 \(N-1\) 步 all-gather，把这些完整的块传遍所有 rank。每卡通信量 \(2\frac{N-1}{N}D\)，步数 \(2(N-1)\)，空间额外 \(O(D/N)\) 缓冲。

下面用单进程模拟（每一步所有 rank "同时"发送，所以先收集再应用）：

```python
def ring_allreduce(data):
    """data[r][c]: rank r 的第 c 块（数值或 numpy 数组），原地修改为规约结果"""
    n = len(data)

    # 阶段一：reduce-scatter
    for step in range(n - 1):
        sends = []
        for r in range(n):
            c = (r - step) % n                 # 本步 rank r 发送的块
            sends.append(((r + 1) % n, c, data[r][c]))
        for dst, c, val in sends:
            data[dst][c] = data[dst][c] + val  # 累加
    # 此时 rank r 拥有完整规约的块 (r + 1) % n

    # 阶段二：all-gather
    for step in range(n - 1):
        sends = []
        for r in range(n):
            c = (r + 1 - step) % n
            sends.append(((r + 1) % n, c, data[r][c]))
        for dst, c, val in sends:
            data[dst][c] = val                 # 直接覆盖
    return data


# 简单验证：3 个 rank，每个 3 块
if __name__ == "__main__":
    d = [[1, 2, 3], [10, 20, 30], [100, 200, 300]]
    print(ring_allreduce(d))  # 每个 rank 都是 [111, 222, 333]
```

真实实现中，发送和接收用异步通信（如 `isend/irecv`）同时进行，并把大块再切成更小的 chunk 做流水，以隐藏延迟。

### 3. FSDP 的核心原理是什么，与 ZeRO-3 的区别

**参考答案**

**结论**：FSDP 是 PyTorch 原生实现的参数、梯度、优化器状态全分片的数据并行，思想与 ZeRO-3 一致，区别主要在实现和生态。

**原理**：
1. 每个 FSDP 单元（通常是一个 Transformer block）的参数分片存放在各 rank。
2. 前向前对该单元 all-gather 出完整参数，计算后立即释放。
3. 反向时再次 all-gather，计算出梯度后 reduce-scatter，每个 rank 只保留自己那份梯度，再用本地分片更新优化器状态。
4. 通过预取下一单元参数，把通信与计算重叠。

**与 ZeRO-3 的区别**：
- **来源与集成**：FSDP 是 PyTorch 原生，与 `torch.compile`、DTensor、分布式 Checkpoint 等集成；ZeRO-3 在 DeepSpeed 里，配置驱动，功能更丰富。
- **功能**：DeepSpeed 的 ZeRO-Infinity 支持 CPU 和 NVMe offload；FSDP 也支持 CPU offload，但 NVMe 不是其主要卖点。
- **分片策略**：FSDP 提供 `FULL_SHARD`（相当于 ZeRO-3）、`SHARD_GRAD_OP`（相当于 ZeRO-2）、`HYBRID_SHARD`（机内分片、机间复制，减少跨机通信）等。
- **实现细节**：FSDP1 用 FlatParameter 打平；FSDP2 改为基于 DTensor 的按参数分片，更灵活。

### 4. 如何实现通信与计算的重叠优化

**参考答案**

**结论**：把通信放在独立的 CUDA stream 上异步执行，并通过切分、预取、调度让通信和相互独立的计算同时进行。

- **DP 梯度**：DDP 把梯度分桶（bucket），某一桶梯度就绪就立刻异步 AllReduce，同时继续反向计算前面的层；ZeRO/FSDP 同理对 reduce-scatter 做重叠。
- **ZeRO-3 / FSDP 参数**：预取下一层的 all-gather，与当前层计算重叠（需要限制预取量，避免显存峰值）。
- **TP**：把矩阵乘切成多块，一块计算时另一块通信（分块流水），或使用 Megatron 的 TP overlap 方案。
- **PP**：1F1B 和 interleaved 调度，使 P2P 通信与其他 micro-batch 的计算重叠。
- **MoE**：all-to-all 与专家计算按 micro-batch 流水重叠。
- **注意点**：通信 kernel 也占 SM，会和计算抢资源；要避免不必要的 `cuda.synchronize`；Megatron 里常设置 `CUDA_DEVICE_MAX_CONNECTIONS=1` 以保证 kernel 排队顺序有利于重叠。
- 验证用 Nsight Systems 看时间线，确认通信确实被计算覆盖。

### 5. 万卡集群训练中故障恢复机制如何设计

**参考答案**

**结论**：规模越大故障越频繁，机制要做到"快速发现、快速隔离、快速恢复、少丢进度"。

1. **故障检测**：NCCL 超时 watchdog、心跳、GPU XID/ECC 错误、网卡和链路监控、慢节点检测。分清是硬故障、通信 hang 还是掉队（straggler）。
2. **隔离与替换**：定位故障节点后摘除，用备用节点（热备或 spare pool）替换，避免重新排队。
3. **快速重启**：调度器自动拉起任务，预先做节点健康检查（如跑小规模 NCCL 测试）再加入。
4. **状态恢复**：从最近 Checkpoint 恢复，Checkpoint 要异步、分片、多级（内存 → 本地盘 → 远端存储），减少保存开销和丢失进度。
5. **数据一致性**：dataloader 状态和 RNG 状态随 Checkpoint 保存，保证恢复后数据不重复不遗漏。
6. **静默错误**：对 loss 或梯度异常做检查，定期校验，发现后回滚。
7. **度量**：关注有效训练时间占比和平均恢复时间（MTTR）。

### 6. Checkpoint 间隔如何选择，异步保存如何实现

**参考答案**

**结论**：间隔在"保存开销"与"故障后丢失的计算"之间折中，异步保存把写盘移出训练关键路径。

**间隔选择**：设单次保存阻塞时间 \(C\)，平均无故障时间 \(M\)，经典的 Young 近似给出最优间隔约 \(\sqrt{2CM}\)。集群越大，\(M\) 越小，间隔就要越短；\(C\) 越小，越能频繁保存。实际还要考虑存储容量、保留份数和恢复耗时。

**异步保存实现**：
1. 训练暂停很短时间，把 GPU 上的状态拷贝到 CPU 的 pinned memory（快照）。
2. 训练立即继续，后台线程或进程把快照写到存储。
3. 各 rank 并行写自己的分片，避免汇总到 rank 0 造成瓶颈。
4. 先写临时文件，完整后原子重命名或写完成标记，防止出现损坏的 Checkpoint；同时只允许有限个未完成的保存，避免内存堆积。
5. 进一步优化：多级存储（先落内存或本地 NVMe，再异步上传）、Checkpoint 记录并行配置元数据以便跨并行度重切分。

### 7. MoE 模型在分布式训练中有哪些挑战

**参考答案**

**结论**：主要挑战是 all-to-all 通信开销、专家负载不均、显存与并行策略复杂、训练稳定性。

1. **通信**：专家并行（EP）下，token 需要 all-to-all 分发和回收，每层两次，跨机时成为瓶颈，需要重叠和拓扑感知。
2. **负载不均**：路由可能使某些专家过载，导致掉队、token 被丢弃（capacity factor）。常用辅助负载均衡损失、无辅助损失的偏置调整等方式缓解。
3. **显存**：总参数量大，但每 token 只激活少数专家，计算量小而参数显存大，需要 EP 与 TP/DP/ZeRO 组合。
4. **计算效率**：每个专家分到的 token 少，矩阵乘小，需要 grouped GEMM 提高利用率。
5. **稳定性**：路由抖动、logits 过大，常用 router z-loss、路由用 FP32 等。
6. **工程**：Checkpoint 需要支持专家分片的重切分，评估和推理也需要对应并行。

### 8. 序列并行和上下文并行的区别

**参考答案**

**结论**：序列并行（Megatron-SP）是配合 TP 的显存优化，只切非 TP 区域的激活；上下文并行（CP）是沿序列维度切分整个模型输入，包括注意力，用于超长序列。

- **序列并行（SP）**：在 TP 组内，LayerNorm、Dropout 等 TP 中本来被复制的部分，沿序列维度切分，各卡只保存一部分激活。通信上把 TP 的 AllReduce 拆成 reduce-scatter + all-gather，总通信量不变，但激活显存下降。它不增加可处理的序列长度上限（注意力部分仍是完整序列）。
- **上下文并行（CP）**：把序列切到多张卡，所有层都只处理一段序列，注意力需要跨卡交换 K/V，典型做法是 Ring Attention（环形传 KV，与计算重叠）和 DeepSpeed-Ulysses（all-to-all 在序列和注意力头之间转置，受头数限制）。它让单卡显存不再随序列长度线性增长，用于长上下文训练。
- 区别总结：SP 是 TP 的附属优化，作用域是 TP 组；CP 是独立的并行维度，可与 TP/PP/DP 组合，针对注意力的长序列。

### 9. FlashAttention 如何减少显存占用和加速训练

**参考答案**

**结论**：FlashAttention 通过分块和在线 softmax，不物化 \(N\times N\) 注意力矩阵，减少 HBM 读写，是 IO 感知的精确注意力。

- **显存**：标准注意力要存 \(S=QK^T\) 和 softmax 结果，显存 \(O(N^2)\)；FlashAttention 分块把 Q、K、V 载入片上 SRAM，用在线 softmax（维护行最大值和归一化因子）逐块累积输出，显存降到 \(O(N)\)。反向时不保存注意力矩阵，只保存输出和 softmax 统计量（logsumexp），通过重计算得到所需的块。
- **速度**：注意力是访存受限，瓶颈在 HBM 带宽而非 FLOPs。融合成一个 kernel，把中间结果留在 SRAM，大幅减少 HBM 读写，所以更快。
- **注意**：它是精确注意力，不是近似；FLOPs 并没有减少（反向还多了重计算），收益来自 IO。FlashAttention-2 改进并行和分工，FlashAttention-3 针对 Hopper 做了异步和低精度优化。

### 10. 如何设计一个低延迟的机器人实时控制推理流水线

**参考答案**

**结论**：先定延迟预算，把高频控制与低频大模型推理解耦，再从模型、运行时、系统三层压缩延迟，并保证有兜底。

1. **分层架构**：底层高频控制（如运动控制、平衡）用轻量模型或传统控制器，在固定周期内确定性执行；高层感知、规划或 VLA/大模型以较低频率运行，输出目标或动作序列，两者异步通信。
2. **延迟预算**：端到端拆成采集、预处理、推理、后处理、下发，各环节度量 P99 而非平均值。
3. **模型**：量化（FP16 / INT8）、蒸馏、剪枝、静态形状；大模型可输出动作块（action chunk），由低层插值执行，掩盖推理延迟。
4. **运行时**：TensorRT 等引擎、CUDA Graph、零拷贝和 pinned memory、前后处理放 GPU、流水线化（采集与推理并行）。
5. **系统**：传感器时间戳对齐，实时调度（绑核、优先级、避免 GC 和动态内存分配），预分配内存。
6. **安全兜底**：推理超时或异常时，沿用上一个动作或切换到安全策略，并有看门狗。
7. **监控**：线上记录延迟分位数和丢帧情况。

### 11. 模型量化在训练和推理中的应用区别

**参考答案**

**结论**：推理量化主要是压缩模型、加速推理；训练中的低精度主要是提升吞吐和省显存，且必须保证梯度和更新稳定。

**推理侧**：
- **PTQ**（训练后量化）：用少量校准数据确定缩放因子，把权重（和激活）转成 INT8 / INT4 等，如 GPTQ、AWQ、SmoothQuant。简单快速，低比特时可能掉精度。
- 对 LLM 常做权重量化（如 W4A16）降低显存占用和访存，KV Cache 也可量化。

**训练侧**：
- **混合精度**（BF16/FP16，进一步 FP8）：前向反向用低精度，主权重和优化器状态保持高精度。
- **QAT**：训练时插入伪量化节点，前向模拟量化误差，反向用直通估计器（STE），让模型适应量化，精度通常优于 PTQ。
- 训练对数值范围和梯度精度更敏感，不能简单把所有东西压到 INT8；需要缩放因子管理。

**核心差别**：推理是静态的、只需前向；训练要反向，需要保持梯度和累积的精度。

### 12. 如何平衡显存优化和训练速度的 trade-off

**参考答案**

**结论**：按"收益大、代价小"的顺序逐步叠加，每加一项都用实测吞吐和显存验证，直到刚好放下。

建议顺序：
1. 几乎无代价：BF16、FlashAttention、融合算子、合理的 micro-batch。
2. 代价较小：ZeRO-1/2（通信量与 DP 相同）、选择性重计算、序列并行。
3. 代价中等：ZeRO-3 / FSDP（通信翻倍多，需靠重叠掩盖）、PP / TP 增大（引入气泡或通信）。
4. 代价较大：全量激活重计算（约增加 1/3 计算）、CPU / NVMe offload（受 PCIe 带宽限制）。

原则：
- 目标是在显存刚好够的前提下，用尽可能大的 micro-batch 提升算力利用率；显存富余时，减少重计算和切分。
- 用 MFU 和 tokens/s 作为最终指标，不只看显存。
- 有空闲显存时，可用来换速度（关闭重计算、增大 batch）。

### 13. 在跨 2000+ GPU 的集群上，如何设计参数分区和梯度同步策略

**参考答案**

**结论**：按网络拓扑分层设计并行：高带宽域用 TP，跨机用 PP，最外层 DP + ZeRO，并让梯度同步分层、重叠。

1. **并行布局**（示意，以 2048 卡为例）：TP=8（单机 NVLink）× PP=16 × DP=16。再根据模型调整，MoE 加 EP，长序列加 CP。rank 映射要拓扑感知，让通信量大的组落在带宽高的链路上。
2. **参数分区**：模型层按 PP 切 stage，层内 TP 切分；DP 维度使用 ZeRO-1 或 HSDP（组内分片，组间复制），避免 ZeRO-3 在上千卡上做全局 all-gather 的开销。
3. **梯度同步**：
   - 梯度分桶，与反向计算重叠。
   - 分层通信：先机内 reduce，再跨机，再机内广播，减少跨机流量。
   - 大规模下 Ring 延迟随规模增长，NCCL 会使用 Tree 等算法。
   - 梯度累积减少同步频率，必要时调大 global batch。
4. **稳定性**：规模越大 global batch 越大，需要相应调整学习率和 warmup。
5. **工程**：慢节点检测、通信超时和容错、Checkpoint 分片并行写。

### 14. 手写算法：实现一个简单的梯度裁剪函数

**参考答案**

**思路**：按全局范数裁剪：计算所有参数梯度的全局 L2 范数 \(\|g\|\)，若超过阈值 `max_norm`，则所有梯度乘以 `max_norm / (‖g‖ + eps)`。时间 \(O(P)\)，P 为参数量，额外空间 \(O(1)\)。

```python
import torch

def clip_grad_norm_(parameters, max_norm, eps=1e-6):
    grads = [p.grad for p in parameters if p.grad is not None]
    if not grads:
        return torch.tensor(0.0)

    # 用 float32 计算范数，避免低精度溢出
    total_norm = torch.sqrt(
        sum(g.detach().float().pow(2).sum() for g in grads)
    )

    clip_coef = max_norm / (total_norm + eps)
    clip_coef = torch.clamp(clip_coef, max=1.0)  # 范数没超限就不缩放

    for g in grads:
        g.mul_(clip_coef.to(g.dtype))
    return total_norm
```

分布式要点（容易说漏）：
- 参数被 ZeRO/FSDP/TP 切分时，每个 rank 只有部分梯度，要先算本地平方和，再 `all_reduce(SUM)` 得到全局平方和，再开方。
- TP 中被复制的参数不能重复统计。
- 使用 loss scaling 时，应先反缩放再裁剪。
- 若范数是 NaN 或 inf，一般跳过该步更新。

### 5. 从单卡跑不动 7B 模型到多卡训练 70B 模型，完整的显存优化方案

**参考答案**

**结论**：先算清显存账，再从低代价手段到高代价手段逐层叠加；7B 靠单机方案，70B 必须引入模型状态切分和多机并行。

**显存账**：混合精度 + Adam 约 \(16\Psi\) 字节。7B 约 112GB，已超过 80GB 单卡；70B 约 1.1TB，8 张 80GB 卡共 640GB 也放不下，还要留激活空间。

**7B 单卡 / 单机**：
1. BF16 + FlashAttention + 融合算子。
2. 激活重计算，减小 micro-batch 配合梯度累积。
3. 8-bit 优化器或 CPU offload（优化器状态）。
4. 单机多卡用 ZeRO-2/3 或 FSDP 即可放下。
5. 若只是微调，可用 LoRA / QLoRA，只训练少量参数。

**70B 多卡**：
1. 机内 TP（如 8）+ 跨机 PP + DP，或用 ZeRO-3 / FSDP（HSDP）切模型状态。例如 ZeRO-3 在 32 卡上每卡模型状态约 35GB，再留给激活和缓冲。
2. 选择性或全量重计算，序列并行减少激活。
3. 长序列加 CP。
4. 必要时 offload 兜底，通信与计算重叠、拓扑感知放置。
5. 每一步用 profiler 实测显存和 MFU 验证。

### 6. DeepSpeed、Megatron-LM、FSDP 这三个框架的优缺点和适用场景

**参考答案**

**结论**：FSDP 易用、原生；DeepSpeed 显存优化和 offload 功能丰富；Megatron-LM 在超大规模下性能最强，但改造成本高。

| 框架 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| DeepSpeed | ZeRO 1/2/3、offload（CPU/NVMe）、配置驱动，与 HuggingFace 生态集成好，显存省 | 超大规模下 TP/PP 的性能和灵活性不如 Megatron，配置项多，调试复杂 | 中等规模训练、微调、显存受限、快速上手 |
| Megatron-LM | TP/PP/SP/CP/EP 完整，kernel 和通信优化成熟，MFU 高 | 模型需按其接口实现，代码侵入性强，上手和维护成本高，Checkpoint 转换麻烦 | 千亿级或更大、追求极致吞吐的预训练 |
| FSDP | PyTorch 原生，API 简洁，与 `torch.compile`、DTensor 兼容，调试方便 | 单靠 FSDP 在超大规模下通信压力大，需要组合 TP/PP（可结合 DTensor / 2D 并行） | 百亿到几百亿参数、PyTorch 生态、需要灵活修改模型 |

选择依据：模型规模、团队熟悉度、是否需要自定义模型结构、对 MFU 的要求。实践中也有组合用法（如 Megatron + DeepSpeed 的 ZeRO-1）。

### 7. 如何设计一个支持弹性伸缩的训练调度系统

**参考答案**

**结论**：关键是调度层能动态调整资源，训练层能在资源变化时从状态重建并保持训练语义一致。

1. **调度层**：基于 Kubernetes + 批调度器（Volcano、Kueue 等），支持 gang scheduling（要么全拿到，要么都不启动）、优先级和抢占、队列配额、碎片整理。
2. **弹性训练**：使用 torchrun elastic / rendezvous，检测节点增减后重新组网并重启训练进程。
3. **状态保存与重切分**：Checkpoint 保存时附带并行配置，恢复时按新的并行度重新分片（纯 DP 伸缩较容易，TP/PP 变化则需要重新切分参数）。
4. **保持训练语义**：全局 batch size 保持不变，用调整梯度累积步数补偿；必要时调整学习率；dataloader 位置和随机种子可恢复，保证数据不重复不丢失。
5. **健康与容错**：节点健康检查、失败自动替换，与故障恢复机制统一。
6. **策略**：缩容和扩容的触发条件（队列压力、抢占、故障），避免频繁抖动，设置最小间隔。
7. **可观测**：记录伸缩事件、重启耗时、对收敛的影响。

难点：重启开销大、并行度变化带来的 Checkpoint 兼容以及数值一致性，所以通常限定在 DP 维度上伸缩。

### 8. 训练监控系统应该包含哪些关键指标

**参考答案**

**结论**：覆盖训练质量、性能效率、系统资源和稳定性四类指标。

1. **训练质量**：loss（总体和分数据源）、学习率、梯度范数、参数范数、梯度中的 NaN / inf 数量、loss scale、评测指标、MoE 的专家负载。
2. **性能效率**：tokens/s、step time、MFU、各阶段耗时（前向、反向、通信、优化器、数据等待）、各 rank 的 step 时间（找 straggler）、流水线气泡。
3. **通信**：NCCL 通信耗时、带宽、网络错误和重传、InfiniBand / RoCE 计数器。
4. **硬件资源**：GPU 利用率、显存使用和峰值、温度、功耗、时钟频率降频、ECC / XID 错误，CPU、内存、磁盘 IO。
5. **数据**：数据加载等待时间、读取吞吐、数据位置。
6. **稳定性**：故障次数、重启次数、MTTR、有效训练时间占比、Checkpoint 耗时和成功率。
7. **告警**：loss 突增、梯度异常、某卡变慢、Checkpoint 失败等设置阈值和自动告警。

### 9. 如何评估一个新分布式训练框架的引入风险

**参考答案**

**结论**：从正确性、性能、稳定性、成本、可退出性五个维度，用小步验证逐步放量。

1. **正确性**：同一模型、数据、种子下，与现有基线对比 loss 曲线和评测指标；检查数值一致性、Checkpoint 能否转换和恢复。
2. **性能**：在目标规模下实测吞吐、MFU、显存，注意小规模的好结果不一定能扩展到大规模。
3. **稳定性**：长时间运行测试、故障注入（杀节点、断网）、恢复是否正确；社区活跃度、issue 质量、版本迭代节奏。
4. **兼容性与生态**：与现有模型、硬件、驱动、CUDA / PyTorch 版本、监控系统和调度系统的兼容。
5. **团队成本**：学习曲线、调试难度、可维护性、文档，团队是否有人能读懂并修复源码。
6. **可退出性**：保持与旧方案的接口，能快速回退；避免被绑死到特定格式。
7. **推进方式**：POC → 小规模灰度 → 非核心任务 → 核心任务，每阶段有明确的通过标准。

### 13. 如何设计一个支持多模态大模型训练的 Infra 架构

**参考答案**

**结论**：多模态训练的特点是模型结构异构（视觉编码器 + LLM）、数据重且长度不一，所以要在数据管线、并行策略和负载均衡上专门设计。

1. **数据管线**：图像或视频解码和增强是 CPU 重负载，容易成为瓶颈；采用预处理缓存、分布式数据加载、GPU 解码（如 DALI）、特征预提取（如果编码器冻结）。样本长度差异大，用 packing 或按长度分桶、动态 batch。
2. **模型并行**：视觉编码器参数量通常较小，LLM 较大。可以让编码器用 DP，LLM 用 TP/PP；也可以把编码器放入流水线的第一段，要注意 stage 切分时计算量不均衡。
3. **负载均衡**：不同样本的图像数量、token 数差别很大，造成各 DP rank 耗时不同，需要按计算量而不是样本数做均衡分配。
4. **长序列**：视频产生大量 token，需要 CP / SP 和重计算。
5. **显存**：视觉编码器激活大，需要重计算和 FlashAttention。
6. **训练策略**：支持多阶段训练（先对齐、后全量微调）、冻结与解冻不同模块、不同模块使用不同学习率，Infra 要支持灵活的参数分组。
7. **其他**：多模态数据的 Checkpoint 和 dataloader 状态恢复，评测与监控按模态拆分指标。

### 14. 手写算法：设计一个简单的模型并行调度器

**参考答案**

**思路**：以流水线并行为例，实现 1F1B 调度。设 P 个 stage、M 个 micro-batch。对第 `s` 个 stage：先做 `warmup = min(P - s - 1, M)` 次前向填充流水线；稳态下每做一次前向就做一次反向（1F1B），这样每个 stage 最多只持有 `P - s` 个 micro-batch 的激活；最后做 `warmup` 次反向收尾。气泡占比为 \((P-1)/(M+P-1)\)，与 GPipe 相同，但激活显存更小。时间复杂度 \(O(M)\)。

```python
def one_f_one_b(stage, num_stages, num_microbatches):
    """返回某个 stage 的执行序列：[('F', mb), ('B', mb), ...]"""
    warmup = min(num_stages - stage - 1, num_microbatches)
    ops = []
    f = b = 0

    # 1) warmup：只做前向，填充流水线
    for _ in range(warmup):
        ops.append(("F", f)); f += 1

    # 2) 稳态：一次前向，一次反向
    for _ in range(num_microbatches - warmup):
        ops.append(("F", f)); f += 1
        ops.append(("B", b)); b += 1

    # 3) cooldown：把剩余的反向做完
    for _ in range(warmup):
        ops.append(("B", b)); b += 1
    return ops


if __name__ == "__main__":
    P, M = 4, 8
    for s in range(P):
        print(s, one_f_one_b(s, P, M))
```

实际调度器中还需要：
- 前向后把激活发给下一 stage（`send` / `recv`），反向时把梯度发给上一 stage。
- 每个 stage 的 forward / backward 对应的 micro-batch 要保存其输入，用于反向。
- 用异步 P2P 通信与计算重叠，并保证相邻 stage 的发送和接收顺序一致，避免死锁。
- 进阶：interleaved 1F1B 让每个设备持有多个不连续的模型块，进一步减小气泡，但通信量增加。
