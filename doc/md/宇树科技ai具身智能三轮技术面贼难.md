### 3. 讲一下你对具身智能（Embodied AI）和 VLA（Vision-Language-Action）模型的理解

**参考答案**

具身智能是让有身体的智能体在真实环境里感知并行动。动作会改变物理世界，所以延迟、传感和安全都在闭环里：看一眼，动一下，再根据新观测继续。聊天模型把一段文本生成完就结束，没有这个闭环。

VLA 是其中一类模型。输入是图像和自然语言，输出是动作，可以是离散 token，也可以是一小段连续控制量。RT-2 的做法是把动作编成 token，在视觉语言模型上用机器人演示继续训练。它学的是「看到什么、指令是什么，就做什么」，演示数据才是关键，只靠互联网图文训练不出来。

模型输出仍然只是提议。下发前要过关节限位、碰撞检查和急停；长任务按新观测重规划。面试里要补上这一层：动作有物理后果，不能把模型输出直接当成电机指令。

### 4. Java 中 ThreadLocal 的原理，为什么会出现内存泄漏，如何避免

**参考答案**

ThreadLocal 给每个线程一份独立的值，用来传递上下文，不负责线程之间通信。每个 `Thread` 持有一张 `ThreadLocalMap`，key 是 `ThreadLocal` 实例，value 是存进去的数据。`get` 和 `set` 都先取当前线程，再查这张表。

Entry 的 key 是弱引用。外部已经没有强引用的 `ThreadLocal` 可以被回收，value 仍被 Entry 强引用。线程池里的线程长期不销毁，这块 value 就一直留着。之后的 `get`、`set`、`remove` 才会顺手清掉 key 已经空了的条目；线程闲置、不再碰 `ThreadLocal` 时不会清。

静态 `ThreadLocal` 的 key 通常不会被回收，不调用 `remove` 同样有问题：value 占着内存，下一个任务复用这条线程时还会读到上一个请求的数据。

使用时放在 `finally` 里 `remove`。池化任务的上下文优先显式传参。`InheritableThreadLocal` 只在创建子线程时复制，线程池不会为每个任务重新复制。

### 5. JVM 垃圾回收算法有哪些，G1 和 CMS 的区别及适用场景

**参考答案**

HotSpot 用可达性分析判断垃圾：从 GC Roots 出发标出活对象。清理方式有三类。标记-清除会留下碎片；标记-复制把活对象拷到空区，新生代常用；标记-整理把活对象挤到一端，老年代常用。分代收集是把这些策略配在不同代上。引用计数处理不了循环引用，不用作主方案。

CMS 面向老年代，用并发标记清除缩短停顿。初始标记和重新标记要停住应用线程，并发标记和并发清除与应用并行。代价是碎片、占用 CPU，以及并发期间产生的浮动垃圾。老年代在回收完成前被占满，会退化成停顿更长的整堆回收。JDK 8 的默认收集器是 Parallel，CMS 要显式打开。它在 JDK 9 被标记废弃，JDK 14 移除。

G1 把堆分成等大的 Region，优先回收垃圾比例高的部分，并可以设置停顿目标。Region 之间通过复制回收，碎片比 CMS 可控。JDK 9 起它是默认收集器。堆较大、希望停顿可预期时用 G1；堆不大、更看重吞吐时，Parallel 仍然合适。G1 在复制空间不足时也会退化为 Full GC。

### 6. Spring Boot 自动配置原理是怎样实现的

**参考答案**

自动配置的入口是 `@SpringBootApplication` 里的 `@EnableAutoConfiguration`。它 `@Import` 了 `AutoConfigurationImportSelector`，启动时读取一份自动配置清单，选出一批配置类，再按条件决定是否生效。Boot 2 的清单在 `spring.factories` 的 `EnableAutoConfiguration` 键下；Boot 2.7 起改为 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，Boot 3 使用这份新清单。

条件注解决定装配结果。`@ConditionalOnClass` 表示 classpath 里有相应类才装配，所以引入某个 starter 才会出现对应 Bean。`@ConditionalOnMissingBean` 让用户自己声明的 Bean 保留下来。`@ConditionalOnProperty` 用配置开关控制。自动配置排在普通组件扫描之后，所以上面的「缺失才装配」能够看到用户 Bean。顺序由 `@AutoConfigureBefore`、`@AutoConfigureAfter` 控制。

`spring-boot-starter` 负责把依赖打成一组，真正创建 Bean 的是 autoconfigure 里的配置类。配置值来自环境，并用 `@ConfigurationProperties` 绑定。组件扫描只覆盖启动类所在包及其子包；自动配置类来自那份清单，可以用 `exclude` 排除。

### 7. Redis 常用的五种数据类型及典型使用场景

**参考答案**

五种基础类型要连场景一起说。

- String 适合缓存对象、计数和限流占位。`INCR`、带过期时间的 `SET` 都是原子操作。
- List 适合最新若干条记录和简单队列。阻塞弹出可以用 `BRPOP`，消费确认和堆积监控都弱，正式业务队列应交给消息中间件。
- Hash 适合一个对象的多个字段，可以局部更新，避免整份 JSON 反复序列化。
- Set 适合去重、标签和交集并集。成员不重复。
- ZSet 适合排行榜和按时间触发的延迟任务。member 唯一，score 决定顺序。

Redis 5 之后还有 Stream，适合要消费位点的消息。Bitmap 建立在字符串上，GEO 建立在有序集合上，讲的时候和五种基础类型分开。选型时说明访问方式：要范围顺序用 ZSet，要按字段更新用 Hash，只存整份值用 String。

### 8. Redis 分布式锁的实现思路及可能的问题

**参考答案**

加锁用 `SET key token NX PX ttl`：键不存在才写入，并带上过期时间，避免进程挂死后锁永远不释放。token 用随机值。释放时先比较 token 再删除，而且比较和删除必须是一次原子操作，通常用 Lua 完成。否则可能删掉刚被别人拿到的锁。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

仍有几类问题。过期时间短于业务时间时，锁会提前失效，业务还在跑；可以续期，但持有进程停掉后续期也必须停。Redis 主从是异步复制，锁写到主节点后主节点宕机，从节点提升上来可能没有这把锁，另一个客户端会再次加锁。因此它适合允许极小概率互斥失败的场景。不能失败的互斥，用数据库唯一约束，或 etcd、ZooKeeper 这类有明确共识边界的系统。

可重入要自己记录持有者和计数。没有 token 校验的 `DEL`、不设 TTL 的锁，都是错误实现。

### 9. MySQL 事务的四大特性 ACID，InnoDB 默认隔离级别是什么，解决了哪些问题

**参考答案**

原子性指事务里的修改全部提交或全部回滚，InnoDB 用 undo log 回滚。持久性指提交成功后崩溃也能恢复，靠 redo log 先记录再应答。隔离性规定并发事务彼此可见到什么程度。一致性是约束和业务不变量仍然成立，它由前面三条加上主键、唯一约束和应用逻辑共同保证。

InnoDB 默认隔离级别是可重复读（REPEATABLE READ）。普通 `SELECT` 走 MVCC，事务第一次一致性读时确定视图，之后两次普通读看到的已提交数据一致，从而避免脏读和不可重复读。`SELECT ... FOR UPDATE` 和 `UPDATE` 这类当前读会加锁；间隙锁和下一个键锁挡住范围内的插入，用来压制幻读。

读已提交也能避免脏读，但每次普通读都看最新已提交版本，所以还有不可重复读和幻读。读未提交连脏读都挡不住。串行化最强，并发最差。可重复读下间隙锁更容易造成死锁。另一个容易漏的点：两个事务都先普通读再写回，可重复读不会挡住丢失更新，需要原子更新语句或 `SELECT ... FOR UPDATE`。

### 10. RAG（检索增强生成）的基本流程是什么，如何减少大模型的幻觉

**参考答案**

RAG 在生成前先从外部资料取出依据，再把依据和问题一起交给模型。资料变了就更新索引，不必为每篇新文档重训模型。

流程是：清洗后按段落或固定窗口切块，块之间可以重叠一段，避免把一个事实切断；块向量写入向量索引，同时建关键词索引。查询时补全代词和省略，做向量与关键词两路召回，按权限和时效过滤，对一小批候选重排，再放进上下文。生成时要求结论能对上片段，片段里没有就说明无法确认。

幻觉是回答通顺，但和资料、工具结果或事实对不上。把空检索也写进上下文，模型才有依据拒绝编造；温度调低只减少随机。召回和生成要分开看：片段本身错了，复述得再忠实也是错的。机器人是否执行成功以设备回执为准，不能靠检索文档证明。

### 11. 如果让 Agent 调用后端接口下发机器人控制指令，你会怎么设计 Tool Calling 接口并保证超时和重试安全

**参考答案**

工具对模型只暴露意图和参数，例如 `submit_motion(device_id, action, params, idempotency_key)`。schema 里写清枚举、单位和取值范围。模型只能提议调用；鉴权、范围校验和真正下发都在服务端，工具背后不要直接暴露电机协议。

超时分成两段：调用方等到业务服务，业务服务再到机器人。动作一旦发出，超时表示结果未知，调用方应去查询回执，而不是立刻再发一次。

重试靠幂等。`idempotency_key` 由调用方生成，服务端用唯一约束记下已接受、执行中、成功、失败、未知。相同 key 返回同一份回执，不再下发。只有明确没有送到设备时才重发；已经开始执行的动作不自动重放。

查询用单独的只读工具。急停走更高优先级的通道，不排在普通重试队列后面。日志保留模型原始参数、校验后的参数和设备回执。面试里要说清：超时后的盲重试会把一次动作变成两次。

### 12. Kafka 和 RocketMQ 的区别，什么场景下选哪个

**参考答案**

两者都按分区或队列保存日志，消费者组内一条分区只给一个消费者，顺序也都只在这一条分区内成立。差别在保留策略和业务语义。

Kafka 按时间和大小保留消息，消费完不会立刻删掉，吞吐高，适合日志、埋点和流处理，和 Flink 这类计算衔接紧。幂等生产者加事务，解决的是写入 Kafka 再被消费时的不重复，不是数据库和机器人之间的分布式事务。延时投递需要自己做延迟主题或调度。

RocketMQ 把业务语义放得更靠前：同步和异步发送、顺序消息、按 tag 过滤、事务消息。事务消息是半消息加本地事务再加回查，用来让「本地事务」和「消息发出去」一致。4.x 的延时是固定等级，5.x 可以按指定时间投递，回答时按用过的版本说。

日志、流式计算、已经有 Kafka 集群时选 Kafka。订单、支付这类需要事务消息、延时和 tag 的 Java 业务，选 RocketMQ。机器人实时指令要回执和幂等，消息队列适合做审计和解耦，不适合当作唯一控制通道。

### 13. 手撕：二叉树的层序遍历（LeetCode 102）

**参考答案**

用队列做广度优先。根入队后，每一层开始时先记下当前队列长度 `levelSize`，然后连续弹出这么多个节点，它们就是一层。弹出时把非空的左、右孩子依次入队，留给下一层。队列空了结束。空树直接返回空列表。

每个节点入队、出队各一次，时间 O(n)。队列最宽时等于最宽那一层的节点数，空间最坏 O(n)。

```java
public List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> ans = new ArrayList<>();
    if (root == null) {
        return ans;
    }
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int levelSize = queue.size();
        List<Integer> level = new ArrayList<>(levelSize);
        for (int i = 0; i < levelSize; i++) {
            TreeNode node = queue.poll();
            level.add(node.val);
            if (node.left != null) {
                queue.offer(node.left);
            }
            if (node.right != null) {
                queue.offer(node.right);
            }
        }
        ans.add(level);
    }
    return ans;
}
```

循环条件里要先固定 `levelSize`。如果边弹出边读 `queue.size()`，下一层会混进当前层。

### 4. 如何设计一个 Multi-Agent 系统让感知 Agent、规划 Agent 和执行 Agent 协作完成机器人任务，各 Agent 间怎么通信

**参考答案**

三个角色按控制环分工，不要做成三个互相转发自然语言的聊天机器人。感知多数时候是检测、跟踪和定位，输出带时间戳的结构化状态：位姿、障碍、目标。任务规划读取目标和这份状态，产出有限步计划，可以用模型，也可以用行为树。运动规划再把其中一步变成满足关节和碰撞约束的轨迹。执行是控制器，按周期跟踪轨迹，并把成功、失败、超时写回。

通信用共享状态和消息。机器人侧常用发布订阅传递连续状态，用带反馈和取消的动作接口执行一步（ROS 2 里分别是 topic 和 action）。每份状态带任务 id 和时间戳，规划只消费明确的一个版本，避免拿过期障碍做计划。云端若参与，只下发任务目标，不直接发关节级指令。

执行失败先写回执，由任务规划决定重试、改计划或交给人。每一帧新感知不要打断已经发出的短周期控制。急停不经过这些 Agent，直接进入安全回路。运动接口只给执行链路。

### 5. ES 中倒排索引的原理

**参考答案**

倒排索引存的是「词 → 出现过这个词的文档」，不是「文档 → 词」。写入时先分析：分词、规范化、去掉停用词，得到 term，再把文档 id 追加到这个 term 的 postings。链上还记词频和位置，词频供打分，位置供短语查询。

查询「机器人 急停」时，分别取出两个 term 的链，按与、或做集合运算，相关性在现代 Elasticsearch 里默认用 BM25。过滤、聚合和精确匹配走 keyword；全文走 text。两边的分析器要一致，查询词和写入时用同一套规则。中文需要支持中文的分析器，默认分析器按西文和单字规则处理，词召回会偏。

倒排索引解决词项查找。任意子串、没有词边界的模糊匹配，要 n-gram 或扫描，不是倒排的主场。更换分析器后要重建索引，旧 postings 不会自动重切。

### 6. 什么情况下 LIKE '%xx%' 无法命中索引，如何优化全文检索

**参考答案**

普通 B+ 树索引按列值排序，查找要从一个确定的前缀开始。`LIKE 'xx%'` 有前缀，可能走索引。`LIKE '%xx'` 和 `LIKE '%xx%'` 的起点不确定，优化器无法在树上定位，只能扫描；索引建了也用不上这个前缀。

优化要看查询到底是词匹配还是子串匹配。按词检索时，用 MySQL 的 `FULLTEXT`，或把文档放进 Elasticsearch，用倒排索引按 term 命中。必须做子串匹配时，可对片段建 n-gram；只要求「以某串结尾」时，把字段反转后做成前缀查询。先用租户、时间等条件把候选缩小，再在小范围内 `LIKE`。

前缀不确定时，执行计划通常是扫描。表很小，或优化器认为扫描更便宜时，即使是 `LIKE 'xx%'` 也可能不用索引，要以 `EXPLAIN` 为准。已经分好词的 text 字段按 term 检索，不会按 `LIKE '%xx%'` 做子串匹配。

### 7. Redis 缓存穿透、缓存击穿、缓存雪崩分别是什么，各有哪些应对方案

**参考答案**

三者都是请求落到了数据库上，原因不同。

缓存穿透：这个 key 在缓存和数据库里都不存在，随机 id 会让每次都打到库。先做参数校验；确认不存在的 key 缓存短 TTL 的空值；再用布隆过滤器挡住「一定不存在」的 key。标准布隆过滤器可能把不存在误判成可能存在，这时仍要查库。新数据写入时要把 key 加入过滤器，否则新键会被误拒。

缓存击穿：一个热点 key 过期的瞬间，大量并发同时未命中、一起回源。可以用互斥锁让一个请求重建，其他请求短暂等待；也可以逻辑过期，key 不删除，值里带过期时间，由单个线程刷新，其余线程先用旧值。刷新任务本身挂了，数据就会停在旧版本。

缓存雪崩：大批 key 同一时刻过期，或 Redis 本身不可用。TTL 加随机抖动，启动时预热热点；Redis 做主从或集群；数据库前加限流，缓存不可用时返回兜底。穿透是「从来没有」，击穿是「一个热点刚好过期」，雪崩是「一大片一起没有」。

### 8. MySQL 索引的最左匹配原则，什么情况下索引会失效，联合索引设计时要注意什么

**参考答案**

联合索引 `(a, b, c)` 在 B+ 树上按 a、b、c 依次排序。最左匹配指条件要从左边形成连续前缀，才能用这棵索引定位。`a = ? AND b = ?` 能用到 `(a, b)`；只有 `b = ?` 时，一般无法从这棵索引起跳。`a = ? AND c = ?` 通常只用到 a，中间的 b 断了。`a > ? AND b = ?` 里，b 往往不能再用来缩小查找范围。

MySQL 8.0 的 Index Skip Scan 在最左列区分度很低时，可能跳过它去使用右边的等值条件，设计时仍按前缀来排，不要把跳扫当成常规能力。右边的列即使不能定位，也可能通过索引条件下推做过滤，所以 `EXPLAIN` 里用了索引，不代表每一列都参与了查找。

对列套函数或发生隐式类型转换（字符串列和数字比较），普通索引对不上；MySQL 8 可以给表达式单独建索引。`LIKE` 以 `%` 开头无法做前缀定位。`OR` 两边各自有索引时，可能走 index merge，不是一律失效。不等于、`NOT IN` 是否走索引，由优化器按成本决定，以 `EXPLAIN` 为准。

设计时把经常等值、区分度又够用的列放左边，范围条件放右边。列顺序服从真实的 `WHERE`、`JOIN` 和 `ORDER BY`。查询列都能包含在索引里时，可以避免回表。单列索引已经选得很准时，不必再堆很长的联合索引，每多一条索引都增加写入成本。

### 9. 线程池核心参数及拒绝策略，如果 AI 推理接口耗时较长，你会怎么设计异步回调或 CompletableFuture 处理

**参考答案**

`ThreadPoolExecutor` 要按提交顺序理解。工作线程少于 `corePoolSize` 时，来任务就建线程。达到核心数后，任务先进入 `workQueue`。队列满了且线程数还没到 `maximumPoolSize`，才继续建线程。线程数也到上限，才执行拒绝策略。`keepAliveTime` 影响的是超出核心数的空闲线程。线程名由 `threadFactory` 设置，否则日志里分不清是哪个池。

四个自带策略：`AbortPolicy` 抛异常，这是默认；`CallerRunsPolicy` 让提交者自己执行，形成反压；`DiscardPolicy` 直接丢弃；`DiscardOldestPolicy` 丢掉队列里最老的任务。推理任务不能丢，用有界队列加 `AbortPolicy`，调用方再降级或写入任务表。无界队列会让 `maximumPoolSize` 失去作用，内存先被打满。

推理是慢调用，不占 Web 容器线程。接口只做校验并落任务，返回任务 id。推理放在独立有界池，池大小按下游允许的并发估计，不按 CPU 核数来设。`supplyAsync` 必须传入这个池，默认的公共池不适合卡住。Java 9 及以上用 `orTimeout` 把超时写成明确状态；Java 8 用调度线程在到点后 `completeExceptionally`。`whenComplete` 里记录成功、失败或超时，回调里不再做重活，也不要在 HTTP 线程上 `get()` 死等。

超时只说明调用方不再等，下游任务可能仍在跑。取消要传给下游。

### 10. Docker 基础：镜像和容器的区别，docker-compose 在你项目中怎么用的

**参考答案**

镜像是只读模板，由分层文件系统和默认启动命令组成。容器是镜像的一个运行实例：在只读层上加一层可写层，并拥有自己的进程、网络命名空间和资源限制。同一个镜像可以起多个容器。删掉容器后可写层就没了，需要保留的数据放卷。

Compose 用一份 YAML 描述一组服务、网络、卷和环境变量，适合在本地或测试环境把应用和 MySQL、Redis 一起拉起来。它不是多机生产调度器。`depends_on` 默认只保证启动顺序，不等待数据库已经可以连接；要等就绪，需要健康检查和对应的 `condition`。

**答题思路**

问到项目里怎么用时，按仓库里的事实说。

1. 先说明 Compose 用在本地、测试还是线上。很多团队只用它起依赖。
2. 点名你维护的服务，以及它依赖哪些组件。别人写的编排不要全部算成自己的。
3. 讲一个真实问题：环境变量连错库、卷把旧数据留下来，或端口冲突。
4. 项目里没有 Compose，就说实际的部署方式，不要编一份微服务 YAML。

### 11. 具身智能场景中机器人指令下发要求低延迟高可靠，后端系统如果从 HTTP 改为 WebSocket 或 gRPC 有什么利弊

**参考答案**

先分清这条链路传什么。关节级实时控制留在机载控制器上，后端改用 WebSocket 或 gRPC，也替代不了机载控制周期。后端负责任务、监督和回执。可靠来自幂等、回执和重连，不来自协议名字。

HTTP 的请求响应简单，网关、鉴权和日志都成熟，适合低频的一次性任务。它不方便由服务端主动推送进度；短连接每次还有握手成本。响应超时之后，调用方不知道动作执行到了哪一步。

WebSocket 是双向长连接，适合推送姿态、进度和取消。心跳、重连、消息编号，以及多实例时连接落在哪一台，都要自己做。它不规定 schema，也不规定幂等。

gRPC 走 HTTP/2，用 protobuf 约束字段，一元调用适合服务间指令，双向流适合遥测。deadline 可以沿调用链传递。浏览器不能直接使用原生 gRPC，外网控制台通常还要一层网关。一条长连接会让按请求轮询的负载均衡失效。

管理端可以继续用 HTTP 提交任务；设备在线通道再用 WebSocket 或 gRPC 流。重连之后先查询状态，再决定要不要发下一条。三种协议都可能超时和重复。

### 12. 手撕：岛屿数量（LeetCode 200，DFS/BFS 均可）

**参考答案**

把上下左右相连的 `'1'` 看成一座岛，斜角不算相连。扫描每个格子，遇到还没访问过的陆地就让计数加一，再用 DFS 或 BFS 把整座岛标记掉，避免重复计数。

每个格子最多处理一次，时间 O(m × n)。DFS 的递归栈或 BFS 的队列最坏也是 O(m × n)。题目允许改网格时，把访问过的陆地改成 `'0'`；不允许改时，另用同样大小的访问数组。

```java
public int numIslands(char[][] grid) {
    if (grid == null || grid.length == 0 || grid[0].length == 0) {
        return 0;
    }
    int count = 0;
    for (int r = 0; r < grid.length; r++) {
        for (int c = 0; c < grid[0].length; c++) {
            if (grid[r][c] == '1') {
                count++;
                dfs(grid, r, c);
            }
        }
    }
    return count;
}

private void dfs(char[][] grid, int r, int c) {
    if (r < 0 || c < 0 || r >= grid.length || c >= grid[0].length) {
        return;
    }
    if (grid[r][c] != '1') {
        return;
    }
    grid[r][c] = '0';
    dfs(grid, r - 1, c);
    dfs(grid, r + 1, c);
    dfs(grid, r, c - 1);
    dfs(grid, r, c + 1);
}
```

先标记再递归，避免走回头路。网格很大时，深递归可能撑爆栈，可以改成显式栈或队列。BFS 的计数方式和这里相同，只是用队列把四邻域放进去。

### 3. 如果让你设计宇树机器人 AI 后台管理系统（设备管理 + 指令下发 + 日志追踪 + 大模型问答），简单说下整体微服务拆分和选型

**参考答案**

按变化原因拆开，而不是按页面拆。设备服务管注册、型号、权限和在线视图，在线状态以设备上报为准。指令服务接受人和模型的动作请求，做参数校验、幂等和状态机，只有它能向网关发运动指令。设备网关维持与机器人的连接，负责下发、回执和断线。轨迹服务异步记下指令、模型上下文和设备回执，大日志不写进指令库。问答服务只做检索和工具提议，真正下发必须再进指令服务，模型不直连网关。

服务可以用 Spring Boot。指令和设备主数据放 MySQL，用唯一约束做幂等。在线会话放 Redis。审计事件用 Kafka 或 RocketMQ。配置和注册用 Nacos，安全阈值要能推到进程。文档放对象存储，检索另建索引。

问答可以失败，指令状态机不能丢。推理耗时长，要和网关线程隔开。急停不经过模型，也不只靠消息队列投递。可以先做成模块化单体，但模型、指令、网关这三个运行时尽早分成独立进程。

### 4. 具身 Agent 下发运动指令时如何做安全校验和熔断，防止大模型幻觉导致危险动作（提示词约束 / 参数范围校验 / 硬件拦截三层思路）

**参考答案**

三层都要有，能够挡住危险动作的是后两层。

提示词写清允许的动作、速度上限和禁止项，并要求模型通过结构化工具提交。这一层降低胡乱生成的比例，模型仍可能给出越界参数。

指令服务做硬校验。动作必须在枚举内；速度、幅度、时长落在该型号的档案范围内；充电、急停未复位、工作空间不允许时直接拒绝。单位时间指令过多，或连续失败达到阈值，就熔断，熔断期间只保留查询和急停。拒绝原因返回给调用方，避免模型换个说法再试一次。

第三层在网关和本体：关节限位、碰撞检测、看门狗和急停回路。服务端无响应时，机器人进入安全停止，而不是继续执行最后一条。高风险动作要有服务端记录的人工确认，确认状态不放在模型回复里。

熔断要分成两件独立的事：拒绝后续新指令，以及打断正在执行的危险动作。后者要能在超时后主动停车。日志保留原始参数和拒绝原因，便于区分是模型越界还是阈值配错。

### 5. 你们团队代码 Review 重点关注什么，遇到同事写出有明显性能问题的代码你怎么沟通

### 7. ZooKeeper 或 Nacos 做注册中心和配置中心的大致原理，与 Consul 有何区别

**参考答案**

注册中心回答实例在哪、是否健康；配置中心把运行参数发到进程并在变更后生效。两者可以是同一套系统，也可以分开。

ZooKeeper 用 Zab 在多数派之间维护一棵小树，写入走一致性优先的路径。临时节点绑在会话上，会话断了节点消失，因此可以做注册和选主；配置放在持久节点上，客户端用 watch 接收变更。watch 触发一次后要重新注册。它适合协调，不适合存大块配置，也没有现成的 HTTP 健康检查。

Nacos 同时提供注册和配置。临时实例靠客户端心跳维持，偏向可用；持久实例走一致性协议。配置按 dataId 和 group 管理，变更后推给客户端。2.x 起注册和配置主要走 gRPC 长连接，早期配置用长轮询。它和 Spring Cloud 的接入比较直接。

Consul 的服务目录由 Server 用 Raft 达成一致，节点之间用 gossip 做成员和故障检测。健康检查是一等能力，可以用 HTTP、TCP 或 TTL。它自带 DNS 发现，多数据中心是设计目标。和 ZooKeeper 比，它更像服务注册中心，而不是通用协调组件；和 Nacos 比，一致性路径更单一，Java 业务里的现成集成少一些。

配置推下去之后，允许短暂的新旧并存，调用双方要能兼容。

### 8. 你最近在学什么新技术，怎么判断一门技术值不值得深入学，举个你自学并落地到项目里的例子

**答题思路**

要一个真的学习对象，不要临时挑热词。按「学什么 → 为什么值得 → 落到了哪」讲。

1. 先说最近在学的一件事，范围要小：一个你读过源码或写过试用代码的库、协议或排障方法。
2. 判断值不值得深入，用四条：半年内项目用不用得上；它解决的是机制问题，还是只换了一层 API；文档和社区够不够让你独立排障；能不能用一个小功能验证，而不是只看完教程。
3. 落地例子按这个顺序：原来的痛点、你做的最小试验、进生产前看了什么、最后留在系统里的是哪一小块。
4. 学了但没落地也要诚实，说明卡在数据、权限还是收益不够。不要编一个已经上线的改造。
5. 收尾说你接下来补的缺口。和岗位相关更好，例如设备指令的超时语义、检索评测，选你确实在看的那个。

### 9. 如果公司要在 LangChain / 自研 Agent 框架之间二选一用于生产，你的取舍依据是什么

**参考答案**

选型看状态机要不要握在自己手里，以及这条链路变化有多快。

步骤里有分支、人工确认和断点续跑，团队又还没有自己的编排运行时，用 LangGraph 这类框架可以少写一批基础设施，模型、向量库和工具的接入也更快。业务状态、权限和审计仍放在自己的库里，图只负责步骤怎么跳。框架版本锁死，升级单独做回归。

主路径其实固定，模型只是填参数或在少数工具里选择，就自研一个循环：一张工具表、一套超时和一套轨迹。幂等、权限和审计写在自己的状态机里，排障不必穿过多层包装。自研指的是这条业务链路，不是去写一个通用平台。

设备控制应使用自己的指令状态机。动作有副作用，提示词链不适合当控制核心。问答和检索可以留在框架里；运动指令离开框架之后，进入独立的指令服务。

一条实用的判断：脱开框架之后，要说得清状态存在哪、失败如何重放。说不清，就说明复杂度被框架藏起来了，应把框架限制在很薄的一层，或不要让它碰有副作用的链路。

### 10. 手撕：LRU 缓存实现（LeetCode 146）

**参考答案**

LRU 要在 O(1) 内完成按 key 读取、写入，以及淘汰最久未使用的项。`HashMap` 负责 key 到节点的定位；双向链表维护使用顺序，靠近头部的是刚用过的，靠近尾部的是最久未用的。`get` 命中后把节点挪到头部。`put` 已存在则更新值并挪到头部；不存在就插到头部，超过容量时删除尾部节点，并同步删掉哈希表里的 key。

容量为 n 时，每次操作时间 O(1)，空间 O(n)。只用 `LinkedHashMap` 也可以：构造时打开访问顺序，重写 `removeEldestEntry`。要求手写结构时，把头尾哨兵画出来，空链表就不必单独分支。

```java
public class LRUCache {
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node eldest = tail.prev;
            remove(eldest);
            map.remove(eldest.key);
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }
}
```

`get` 不存在时按题目返回 -1。更新已有 key 也算一次使用，要挪到最新。容量为 1 时，插入第二个 key 应淘汰第一个，用这个例子自测。
