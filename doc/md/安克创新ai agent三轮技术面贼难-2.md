# 安克创新ai agent三轮技术面贼难

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这面真不水，不是背八股能混过去的。安克这边明显不是在问 Agent 是什么，而是在问线上烂了怎么办、bad case 怎么收口、评测怎么才不会自己骗自己。RAG、多 Agent、harness、意图识别全被拉到落地上，问得痛快。没有算法题，但一点不轻松，反而更累，因为每句话都在确认过往项目里是不是真干过。没做过 Agent 平台就别装，一问闭环、成本、灰度就会露馅。整体偏难，但专业，喜欢这种不聊虚的。

## 一面

### 1. 自我介绍

**答题思路**

控制在一分半到两分钟，按「身份 → 一段经历 → 和岗位的关系」讲。

1. 年限和语言栈一句话说完，点明你做的是编排、工具、检索还是评测，不要把框架名词铺开。
2. 只留一个 Agent 项目：用户要办成什么事，你负责哪一层。结果只用你自己看过的延迟、成功或成本；没有数字就讲取舍。
3. 收在这个岗位会追问的点上，例如工具失败、bad case 或评测，方便对方顺着往下挖。
4. 没上过线就说做到了哪一步。不要把 Demo 说成平台。

### 2. 最近做的 AI Agent 项目介绍

**答题思路**

和自我介绍错开，用三到四分钟讲一条真实链路。

1. 业务目标：用户的哪句话要变成查询、办理，还是一段说明。为什么固定表单或固定流程不够。
2. 主路径：鉴权、会话、意图、检索、工具、人工确认、回复各在哪一层。状态放在进程外面还是只放在提示词里，要讲清。
3. 你的边界：只讲自己写过、改过或扛过故障的部分。模型、业务政策、客户端谁负责，不要包揽。
4. 一个线上或联调故障：现象、落在哪一层、改了什么、用什么确认没有复发。
5. 收尾讲你仍不让模型直接做的事，例如未确认就退款。没做的层直接说没做。

### 3. 你们 Agent 的意图识别是怎么做的，规则、模型还是混合

**参考答案**

线上可用的做法是混合，而不是只靠规则或只靠一次大模型调用。规则负责高精确、可枚举的说法，例如「退款」「查物流」和带订单号的指令；分类模型或句向量加阈值负责已经稳定的意图；大模型只处理低置信、多意图和要填槽的长尾。三者都输出同一种结构：意图、槽位、置信度、是否拒识。低于阈值就澄清，不进入有副作用的工具。

写操作上，规则和模型冲突时规则优先，模型不能把一条明确的退款说法改写成别的意图。阈值要用验证集标定，不要拍一个固定小数。意图集合里要有「其他」，否则长尾会被硬塞进天气、售后这类大类。

### 4. 意图识别错了之后，怎么发现、怎么兜底

**参考答案**

发现靠行为和抽样，不能等用户投诉。显式信号是用户马上纠正或换一种说法；隐式信号是同一轮里重新描述、放弃、转人工。系统侧还能看：置信度低、工具领域和关键词规则矛盾（退款说法却去调天气）、写操作被拦截。这些分歧要连同 trace 进 bad case，而不是只记一条错误日志。

兜底分三档。低置信只做澄清，不调工具。命中退款、改地址这类写操作时，高精确规则可以推翻模型，并在执行前向用户确认对象。仍然含糊就转人工。不要在意图已经错了的情况下，让模型「再试一次工具」把错误执行掉。

### 5. RAG 在你们项目里接在哪里，检索结果怎么进 Agent 上下文

**参考答案**

售后这类问题里，RAG 应接在实体已经认出来之后，而不是对用户原话无条件先搜一遍。型号、订单往往来自绑定关系或订单工具；先拿到型号，再用它做元数据过滤，检索才不会把别的产品说明书混进来。路径固定的说明类问题可以做成工作流上的一个节点；故障排查则把检索做成工具，让模型在看到设备信息后再写查询。

进上下文的是重排后的少数片段，带文档名、版本和定位，不是整库，也不是只塞一段无出处的文字。提示里写明：没有依据就说查不到，不要用参数补洞。同一轮已经查过的片段不要每个步骤都重复塞进提示。订单状态、退款资格走结构化接口，不要放进向量库冒充知识。

### 6. RAG 召回质量差时，你会先查召回、重排、切片还是 prompt

**参考答案**

先查召回，而且用固定坏例把四件事拆开，不要按名字依次盲调。看标准答案所在的片段在不在召回列表里。不在，问题在语料、查询、过滤或切片，这时改重排和 prompt 都看不到那段文字。已经进了召回、却没进送给模型的那几条，再查重排。上下文里已有依据仍然说错，才查 prompt。

切片不是和召回并列的第四步，它是召回失败的常见原因：步骤被切断，或一块里混了多个型号。改 prompt 最便宜，也最容易把「上下文里根本没有答案」掩盖成文案问题。四个旋钮不要同时动，否则不知道是哪一个修好的。

### 7. 多 Agent 场景下，子 Agent 之间怎么通信，任务怎么拆分

**参考答案**

用一个编排者对用户目标负责，子 Agent 不互相自由聊天。编排者拆出的每个子任务要有负责人、输入、输出结构和完成条件；子 Agent 只拿任务说明和必要上下文，返回结构化结果，不把整段对话转给下一个。传递介质是共享任务状态或一次明确的交接，不是群聊。

拆分按权限和上下文边界，不按句子。查说明书和发起退款分成两个能力，是因为工具权限不同；互相依赖的步骤串行，互不依赖的只读查询才并行。子 Agent 默认不能再去调用另一个子 Agent。容易漏的是：每多一次交接就多一轮模型调用，延迟、成本和甩锅都会上去，能用一个 Agent 加裁剪后的工具列表解决的，不要拆。

### 8. Agent 调工具失败、超时、返回脏数据，怎么处理

**参考答案**

先把失败分成超时、参数错误、下游 5xx、空结果和结构不合法，再决定能不能重试。每次调用都有超时，超时就取消，不要让模型干等。只有瞬时故障才按有限次数退避重试。退款这类写操作必须带幂等键；超时后先查业务单是否已经生效，状态不明就停下来告诉用户，禁止换个说法再扣一次。

返回值在送回模型前做 schema 校验。脏数据、缺字段、明显串了别人的订单，都当成工具失败写进观察结果，让模型换参数或停止，不要把异常栈直接生成给用户。超过重试次数就降级：查询类说明哪项暂时查不了，写操作转人工。工具列表里也不要在同一步并发打两个有副作用的接口。

### 9. Python 里怎么设计一个可观测的 Agent 调用链

**参考答案**

一轮用户请求一个 trace，意图、每次模型调用、每次检索、每次工具各是一个 span。用 `contextvars` 携带 trace。`asyncio.create_task` 会复制当前上下文；断链更多出在线程池和自己起的线程上，提交给 executor 时要用 `copy_context()` 包一层。Span 上记模型名、prompt 版本、索引版本、token、工具名、状态、文档 id 和意图。提示词正文、手机号、地址默认不落日志，坏例再按策略采样全文。

日志和指标都带同一个 trace id，这样看板能还原：当时判成什么意图、哪几段文档进了提示、工具参数和返回是什么。没有 prompt 版本和索引版本，线上对不上某一次发布。按 OpenTelemetry 导出即可，不把链路绑死在某一个观测产品上。

### 10. Java 侧如果做 Agent 编排服务，线程模型和异步调用怎么设计

**参考答案**

入口若还是平台线程，就只负责收消息并把等待交出去，不要堵在模型或工具上；等待放到 Java 21 的虚拟线程里，或交给带超时的异步客户端。服务如果已经用虚拟线程接请求，就可以在这根虚拟线程上发阻塞式 HTTP，不要再套一层无界池。无论哪种，模型调用都单独用信号量按供应商配额限并发，也不要和数据库、本地计算共用一个池。线程多不代表上游扛得住。

整轮有截止时间，超时就取消还没返回的调用并走降级。trace id 跨线程后要继续传递，不要只留在入口线程的 MDC 里。JDK 21 上，虚拟线程长时间停在 `synchronized` 或本地方法里会钉住载体线程，阻塞调用尽量避开这些区段。写操作不要并发重试；只读查询的 fan-out 也要有上限。

### 11. AI 工作流和纯 Agent 自主规划有什么区别，什么时候不用 Agent

**参考答案**

区别在控制权。工作流的步骤和分支是人预先定好的，模型通常只做其中一个节点，例如分类、抽槽或生成一句说明，给定状态后下一步是确定的。纯 Agent 由模型在循环里决定调用哪个工具、何时停止，路径不固定；外层的 harness 只提供工具、步数限制和停止条件。

路径已知就不用 Agent。退款资格就是查订单、对政策、向用户确认、再执行，延迟和审计都要求每一步可复现，模型最多认意图和槽位。动作不可逆、团队还没有评测、一轮对话的时间预算只够一次模型调用，同样不要放开规划。Agent 适合下一步取决于中间观察、工具组合事先写不全的排查。实用做法是外层工作流，只在不确定的那个节点里放一个有步数上限的 Agent。

### 12. Bad case 来了，你从用户原话、意图、检索、工具、模型输出怎么逐层定位

**参考答案**

按 trace 从外往里，一次只怀疑一层。先看用户原话本身是否缺了订单或型号，缺了却还去执行，是槽位和澄清的问题。原话清楚，就对意图：预测标签和期望是否一致，低置信有没有被放行。意图对了，再看检索：正确片段在不在召回里、有没有进上下文、过滤条件是不是另一个型号。

检索没问题就看工具：工具选得对不对、参数对不对、返回是否校验通过、写操作有没有在确认前发生。上下文和工具结果都对，回答仍然编造或违反政策，才归到模型输出或 prompt。定位时不要同时改 prompt 和索引。每一层留下证据：标签、文档 id、工具参数、模型原文。没有 trace 就先补链路，不要凭聊天记录猜。

### 13. 你们怎么定义 Agent 答得“对”，评测集谁建、标签谁标

**参考答案**

「对」按任务结果定义，不按像不像客服。至少拆开：意图对不对，订单和商品认没认对，该查的订单或说明书查了没有，有没有执行不该执行的写操作，说法是否被工具或检索支撑。流畅但退错单，算错。

评测集从线上真实说法抽，不是只靠人编。业务定政策和期望动作，工程定工具轨迹和检索是否命中；有争议的双人标，第三人裁定。模型侧不能自己宣布自己对。集合要有版本，调 prompt 用的题和对外报告的题分开。只标最终一句话、不标应该调用的工具，写操作类题目会把「说得对、做没做」混在一个分数里。

### 14. 如果一个 Agent 线上大面积答非所问，你的第一反应和排查顺序是什么

**参考答案**

先止血，再定位。看错误曲线是否贴着某一次发布，发布物包括模型版本、prompt、索引、工具 schema 和路由配置。时间对得上就回滚这一组版本，而不是只把模型名改回去、留下新 prompt。没有发布，就查依赖是不是全体异常：模型接口错误率、检索服务、某个工具开始返回脏数据。

然后按意图、入口、版本、租户切开，确认是全站还是一条路由。抽十几条 trace 看意图和第一个工具，不要只看汇总准确率。回滚不够就降级到转人工或固定流程。这个阶段不要先谈微调。大面积答非所问，常见的是路由或索引被整体换错，不是模型突然「变笨」。

### 15. 场景题：用户问“帮我退昨天买的充电宝”，Agent 却去查天气，你怎么修

**参考答案**

这是路由错误，不是天气工具要再调优。先从 trace 看三件事：意图被判成了什么、这一步暴露了哪些工具、天气工具的描述是不是宽到「查询信息」都能匹配。若退款场景仍能看见天气工具，优先按意图裁剪工具列表，而不是在 prompt 里加一句「不要查天气」。

同时给退款、退货加高精确规则，命中后进入固定流程：用「昨天」和「充电宝」去匹配订单，多笔就让用户确认，核对政策后再带幂等键执行。模型不能在确认前直接调退款。这条原话写进回归集，期望是售后意图加上订单工具，不能出现天气。若意图已经对、只是工具选错，改的是工具描述和可见范围，不要重标一整套意图数据。

## 二面

### 1. 自我介绍

**答题思路**

这一轮控制在一分钟内，给架构题让路。

1. 用一句重复身份即可，不要把一面的项目故事再说一遍。
2. 点名接下来要画的那个系统，并用一句话带过层次：接入、会话、路由、编排、工具和检索、评测。
3. 说明你能讲透的是哪两层，邀请对方从那一层往下问。
4. 数字仍然只用自己的。没有就不要补。

### 2. 讲一个你最熟的 Agent 项目，整体架构画出来你能讲清哪几层

**答题思路**

按一次请求从上往下画，只展开你真能讲的层。

1. 接入：渠道、登录、限流，用户身份在这里定下来。
2. 会话：当前意图、槽位、阶段放在 Redis 或数据库，不只留在提示词里。
3. 路由：规则、模型和澄清，决定进入哪条工作流。
4. 编排：固定步骤走工作流；只有不确定的节点才进有步数上限的循环。
5. 能力：订单和退款是业务接口，说明书是按型号过滤的检索。两边权限不同。
6. 策略和人审：写操作前的确认、超过额度或低置信时暂停。
7. 观测和评测：trace、版本号、回归集。画完主动说哪一层不是你做的。

### 3. 智能体评测怎么做，离线评测和线上评测分别看什么指标

**参考答案**

离线评测跑在冻结集合上，用来比较版本，不代表全体用户。看的是任务有没有办成、意图和工具轨迹对不对、检索有没有把依据带进上下文、说法是否被依据支撑、输出结构是否合法，同时记录这套集合上的延迟和 token，作为发布约束。唯一答案才用字符串精确匹配；退款类要看「做没做对」，不是看措辞像不像标准答案。

线上看的是真实分布里的结果：未转人工就办成的比例、转人工率、重复进线、工具失败、投诉、时延和单次会话成本。离线准确率上升而转人工和投诉没动，不能算这个版本更好。两边的分母都要先定义，否则「准确率」无法比较。

### 4. 自动评测和人工评测怎么配合，评分标准怎么防主观

**参考答案**

能判定的部分不要交给人或裁判模型。工具是否调用、参数是否符合 schema、有没有引用到给定文档、是否违反写死的政策，用规则做回归。开放式的表达质量才用裁判模型，而且要先在一批人工标过的题上看出一致率，裁判提示词也要版本化。生成答案的模型不要当唯一裁判，它会偏向自己的写法，也会偏向更长的回答。

人工用在新意图、政策边界和每周抽样。防主观靠写死的量表和正反例、双人标注、分歧裁定，并隐藏是哪个版本。只给一个「1 到 5 分，看是否专业」而不给锚点，分差会大到不能用来卡发布。

### 5. Bad case 闭环系统怎么设计，从采集、归类、复盘到回归

**参考答案**

采集要有触发，而不是等人想起截图：点踩、转人工、工具异常、规则拦截、低置信，再加上少量随机抽样。存 trace 指针和版本号，不存一张看不清参数的图。归类控制在少数几层：意图、检索、工具、政策、生成、需求本身不支持。相似说法再聚类，避免同一问题被拆成几十张单。

复盘给每条指定负责人和改动类型。改动落地时必须带回一条回归用例。发布前跑回归，旧坏例失败就不再放量。闭环的完成标准是这一类问题的复发下降，不是工单被关掉。只有采集、没有回归门禁，系统会变成另一个收件箱。

### 6. 相似 bad case 反复出现，你怎么判断是数据、prompt、检索还是模型问题

**参考答案**

先聚类，再一次只换一个部件。同一批说法上做对照：把上下文换成已知正确的片段后问题消失，就是检索或语料，包括文档过期、缺页、切碎和过滤错型号。上下文正确、工具结果也正确，换 prompt 才消失，并且在没调过的题上仍成立，才归 prompt。同一上下文、同一工具、只有某个模型版本失败，才归模型。

标签互相打架，或业务政策已经变了知识库还是旧的，那是数据问题，换模型和改 prompt 都会反复打回。表面都是「答错退款规则」的一簇坏例，里面可以同时有过期文档和提示词歧义，不能用一个改动覆盖整簇。没有对照就说「模型不行」，结论无效。

### 7. 多 Agent 协作里，怎么避免两个 Agent 互相甩锅式调用

**参考答案**

不要给双方一个「问问另一个 Agent」的工具。用户目标只由编排者持有，子 Agent 之间默认没有调用边；需要对方的结果时，回到编排者，由它决定要不要开下一个任务。每次交接带输入、输出结构和完成条件，子 Agent 不能因为自己做不了就把原话原样退回。

再加硬限制：最大交接次数、重复任务检测（同一目标、同一输入第二次出现就停）、写操作只有一个拥有者。最终回复也只由编排者发出，避免两个 Agent 各说各的。若两个角色经常对抛，说明拆分本身是错的，应该合成一个 Agent，用工具权限区分能力，而不是用对话互相推诿。

### 8. Agent 循环调用、死循环、无限工具调用怎么防

**参考答案**

停止条件要写在模型外面。一轮对话同时限制步数、工具次数、token 和墙钟时间，先到先停。再对「工具名 + 规范化参数」计数，同一调用反复出现就停；任务状态的摘要若连续几步不变，也视为没有进展。图上的环要有访问记录，没有新的观察结果不能再走回去。写操作的次数更紧，没有新的幂等键就不能再打。

停下来之后给用户明确结果或转人工，并记下是哪一条限制触发的，不要静默再开一轮。这些上限是 harness 的职责，写进 prompt 里的「不要循环」挡不住已经陷入循环的模型。

```python
def should_stop(state, call, limits, now):
    # signature 在写入本次工具结果之后计算
    state.steps += 1
    if state.steps > limits.max_steps or now > state.deadline:
        return True
    key = (call.name, canonical(call.args))
    state.repeats[key] = state.repeats.get(key, 0) + 1
    if state.repeats[key] > limits.max_same_call:
        return True
    if state.previous_signature is None:
        state.previous_signature = state.signature
        return False
    stalled = state.signature == state.previous_signature
    state.previous_signature = state.signature
    return stalled
```

### 9. 意图识别在长对话里漂移了，怎么用状态或记忆拉回来

**参考答案**

每轮都用整段历史重新分类，短回复就会漂。「对」「就这个」在退款确认阶段是确认，不是新意图。把当前意图、已填槽位和阶段（收集、确认、执行）存到会话存储里，模型只能提议更新，不能靠提示词里的摘要充当状态。旧轮次可以摘要，最近一轮和这份状态保持原样；摘要会丢掉「还没确认」这类约束。

每一轮先判断是在补槽、纠正，还是换了话题。事务进行中要换话题，先确认放弃当前退款，再切走。用户的纠正要写回状态，而不是只追加一句对话。记忆负责找回型号和订单，不负责推翻已经确认的阶段。

### 10. RAG 里 chunk size、overlap、embedding 模型、rerank 怎么调，优先级怎么说

**参考答案**

四个旋钮不要一起拧。chunk 优先按标题、型号、步骤这些结构切，让一个答案跨度落在同一块里；太大噪声高，太小步骤断，没有普遍最优的 token 数。overlap 只用来避免句子卡在边界，加多了会重复占上下文。型号和错误码不能只靠向量，要和关键词检索混用；确认现有向量确实把同类问题分开不了，再换 embedding，并且整库重刷。rerank 用在召回已经把相关块放进几十条候选之后，负责把送进模型的几条排准。

优先级是：先让正确块出现在召回里，这包括语料、过滤、查询和切片；召回里有、上下文里没有，再调 rerank；换 embedding 成本高，放在后面；上下文里已经有答案仍说错，最后才改 prompt。召回集合里没有的内容，rerank 和 prompt 都补不出来。

### 11. AI 工作流里人工审核节点怎么嵌，什么场景必须人审

**参考答案**

人审是工作流里的一个暂停状态，不是指望模型自己停。命中条件后把 checkpoint、已查到的订单和政策依据放进审核队列，审核结论作为恢复执行的输入。超时不能默认通过，只能拒绝或继续排队。审核人看到的应是结构化事实，而不是再去问一遍模型；模型也不能覆盖审核结论。

必须人审的是：退款和打款、改地址或账号、超出成文政策的例外、低置信但要产生副作用的动作。查说明书、查物流不必人审。节点要有队列时延的预期，否则审核会变成所有请求的同步阻塞。哪些金额或哪些政策词触发人审，放在配置里，不要写死在提示词里。

### 12. Java 服务要承载 Agent 编排和工具网关，你怎么设计接口和降级

**参考答案**

接口分成会话入口和工具网关。入口接收一轮消息，返回流式输出或任务号；网关按工具名做参数校验、鉴权、超时、限流和审计。工具契约要版本化，对不上 schema 就拒绝调用，不要把脏 JSON 塞回模型。查询和写操作分成两类接口，写操作强制幂等键。

降级按依赖隔离。模型超时就取消，改走已经画好的固定流程或转人工。检索不可用就明确说查不到这份说明，不要改用参数补全。查询类工具可以有限重试；退款失败要先按幂等键核对业务单，状态不明就停。一个推荐位或天气类工具熔断，不应取消整次会话。总的截止时间要分给意图、检索和工具，避免只在最外层设一个很长的超时。

### 13. Python Agent 服务和 Java 业务系统之间，协议、鉴权、埋点怎么打通

**参考答案**

短调用用 HTTP 或 gRPC 的同步接口，长任务用任务号加回调，流式输出用 SSE 或双向流。请求里带 W3C `traceparent`，两边才能合成一条链路。契约用版本化的 JSON schema，字段不稳定就不发布。

鉴权分成两层：服务之间用 mTLS 或内部 JWT 证明调用方是 Agent 服务；用户身份用范围受限的令牌继续往后传。退款必须在 Java 里按这个用户重新做权限检查，Python 不能持有一把能改任意订单的密钥。订单真源在 Java，Python 只提议调用。埋点上，Python 记模型、检索和工具意图，Java 记业务结果，标签里都有 trace id。不要为了方便让 Python 直写订单库。

### 14. 场景题：老板说“Agent 准确率一周从80%干到95%”，你信不信，怎么拆

**参考答案**

不按这句话承诺。80% 到 95% 是把错误从 20% 打到 5%，等于一周消掉四分之三的错误。只有错误高度集中在一两个可修原因上，例如索引指向了错误环境、某个工具整体坏了，才可能出现这种跳跃。均匀分布在几十个意图上的 15 个点，一周做不到。

先问清这个百分比的分子分母、是离线题还是线上、覆盖哪些意图、80% 是不是在即将拿来调优的同一批题上算的。然后把错误拆桶，只承诺修最大的那一两桶，并在没参与调优的题和一批新的线上样本上复测。复测之前不报 95%。指标本身若把「话术像」和「退款做对」算成一个数，应先把指标拆开，而不是加紧改 prompt。

### 15. 场景题：评测集只有200条，但线上有几十万用户，你怎么说评测结论

**参考答案**

200 条只能说明这批题上的表现，不能说全体用户的准确率。即便把它当成随机样本，比例的波动也很宽：按二项分布，200 条里 80% 对，标准误差大约是 2.8 个百分点，95% 区间大概在正负 5 到 6 个点。意图再拆开，每一类可能只剩一二十条，区间大到不能排序。

更重要的是，手挑的 200 条通常不是线上分布的随机样本，长尾根本不在里面，上面的区间还是偏乐观的。结论要同时说三件事：这 200 条覆盖了哪些意图、哪类线上说法没覆盖、所以它只适合做已知坏例的回归。线上结论用转人工、投诉和按意图抽样，不把 200 条上的一个百分比外推到几十万用户。

## 三面

### 1. 自我介绍

**答题思路**

三面把时间留给范围、协同和取舍，自我介绍控制在半分钟到四十五秒。

1. 一句身份，加上你在 Agent 这件事里的职责边界：需求、排期、工程还是评测。
2. 只给一个和判断力有关的结果，例如你怎么砍过范围、怎么卡住一次不该放量的发布。不讲架构细节。
3. 说完就停。对方要项目，再展开，不要抢着把三轮准备过的故事都讲完。

### 2. 你带过 Agent 相关项目么，需求、排期、模型同学和工程同学怎么协同

**答题思路**

没带过整组就说清你负责的那一段怎么对齐，不编头衔和人数。

1. 需求写成任务成功标准：哪些意图进范围，哪些动作必须人确认。不写「做一个智能客服」。
2. 排期按依赖：先打通工具、状态和鉴权，再做一个意图的闭环，然后才是评测和灰度。不要按「先把框架搭完」排。
3. 分工：业务定政策，工程定工具契约、幂等、鉴权和 trace，做模型的人负责路由或提示以及误差里真正属于模型的那一层。每周看同一批 trace。
4. 效果和工期冲突时，砍意图，不砍鉴权和回归。
5. 准备一个你真正拍过的取舍。没有就讲你提议过、最后谁拍的板。

### 3. 智能体评测体系如果从 0 到 1 搭，你先搭数据、指标、平台还是看板

**参考答案**

先做种子数据和写下来的成功标准，平台和看板都往后放。没有「怎样算对」，数据只是一堆对话；没有真实说法，指标只是一页空定义。所以第一周就从线上抽几十到一百条，覆盖办成的和办砸的，并给主任务写清判定：工具轨迹、是否越权、说法是否有依据。用一个脚本把当前版本跑完、把差异打出来，这就够比较下一次改动。

多人、多版本都要卡同一道发布门时，再把脚本收成平台。看板只是把回归结果和线上切片显示出来，不能代替集合和判定。先做看板，会得到一张没有分母的大盘。

### 4. Bad case 闭环要不要做成产品化系统，投入产出比怎么跟老板讲

**参考答案**

不要第一天就做产品。坏例还数得过来、只有一个人在跟时，表格加上回归集就够。该做成系统的信号是：多个入口都在产生坏例、发布必须卡回归、同类问题因为没进集合而反复出现、单子已经对不上 trace。

跟老板讲时间和复发，不讲平台。算两笔账：定位一条没有 trace 的问题要多久，同一个退款错误重复发生一次的客诉和人工成本是多少；对比做一个薄切片要多久。薄切片只做三件事：把 trace 收进来、归到固定的层、一键变成回归用例。队列、权限和报表以后再加。没有人每周看这些单子，产品化的投入就是负的。

### 5. 多 Agent 平台化时，工具权限、沙箱、审计、成本控制怎么管

**参考答案**

平台管的是边界，不是替业务写提示词。每个 Agent 有自己的工具白名单，再乘上当前用户的权限和环境；读和写分开。退款这类接口不因为「这是内部 Agent」就跳过用户级鉴权。会执行代码或跑不可信插件的，放进沙箱：限制 CPU、时间和出网，只允许访问名单里的下游，生产凭证不进提示词，也不要让它碰云上的元数据地址。

审计日志不可改：谁、代表哪个用户、调了哪个工具、参数摘要、结果码、有没有人审通过。成本按租户做硬预算，限制每日 token、步数和工具次数，到线就停并告警，而不是只在月底看账单。还要有按 Agent、按工具的开关，出问题能单独关掉一个能力。

### 6. RAG + 多 Agent + 工作流，技术选型时你怎么平衡效果、延迟、成本

**参考答案**

默认骨架用工作流，RAG 和 Agent 按意图加，而不是三种一起上。说明类问题在认出型号之后检索一次即可。退款走固定步骤，模型只填槽。只有故障排查这种下一步取决于观察的，才在一个节点里放 Agent，并限制步数。多 Agent 仅在权限或知识必须隔开时使用，因为每增加一个规划者就多一次长上下文的模型调用，时延和费用近乎按次数涨。

选型前先定三个数：任务做成率、端到端 P95、每次办成要花的 token 和工具次数。效果不够，优先补语料、裁剪工具和改路由，而不是再加一个 Agent。延迟或成本先爆，就合并 Agent、减少每轮检索、让简单意图走小模型。三个目标同时抬到最好，通常是不成立的。

### 7. 新模型周周出，你们怎么快速灰度、回滚、防止评测被刷分

**参考答案**

模型名钉死版本，不用浮动的 latest。每次候选比较的是一整组：模型、prompt、工具 schema、索引。顺序是先影子流量，只对比不展示，再按流量小比例放量。回滚是把这一组切回去，不是只改模型、留下配套的新 prompt。放量期间看工具失败、转人工和投诉，不只看离线分；越线就自动停。

防刷分靠题集隔离。调优用过的题不再拿来当成绩；报告集不写进 few-shot，也不每天对着同一批评测改到满分。自动分之外，留一批新抽的线上样本给人看。工具轨迹对不对，比「最终一句像不像标准答案」难背。裁判模型的提示词改了，旧分数不能和今天的分数直接比。

### 8. 意图识别和路由层如果做成平台能力，怎么给不同业务方复用

**参考答案**

平台提供稳定的能力和契约，业务方提供意图包。意图包里是名称、说明、示例说法、槽位、阈值、拒识时做什么、绑定哪条工作流和哪些工具，并且可以独立发版。平台负责规范化、规则和模型的混合识别、多意图、澄清、超域拒绝，以及统一的 trace。业务策略，例如能不能退款，留在业务的工作流里，不写进平台代码。

复用的前提是输出结构统一：意图、槽位、置信度、版本号。不同业务的阈值和工具不能共用一份默认配置。平台升级分类器时，用每个业务自己的回归集做影子对比，不能因为一个业务涨点就全量切换。意图包要能回滚，否则平台一发布，所有业务一起漂。

### 9. Agent 线上成本炸了，token、工具调用、检索次数都高，你先砍哪块

**参考答案**

先看账单拆在哪，再动手；三件事同时高，通常是因为循环步数把它们一起乘大了。所以第一刀是步数、重复工具调用和无进展的检索，而不是先把模型换成最便宜的。每一步都会重新送入变长的历史，步数才是乘数。

第二刀是不要每轮无条件检索：认不出型号就不搜，同一型号在这一轮已经查过就复用。第三刀是上下文：历史改摘要，工具原文不要原样累积，减少 top-k。路由类的简单轮次再改走小模型。输出长度通常不是大头，先砍它几乎不改变账单。也不要为了省钱关掉退款核对这类必要工具，留下一个更长的重试循环。

### 10. 高级场景题：安克这种硬件加 App 加电商售后场景，Agent 要同时懂产品、订单、退款、说明书，你怎么分层

**参考答案**

按事实来源分层，不要做一个什么都知道的提示词。身份层从 App 绑定和账号拿到用户、设备序列号和型号，这是结构化数据。路由层只做分流：说明书、故障排查、订单、退款，或超出范围。知识层用 RAG，但按产品线和文档类型分库，并用型号过滤；退款规则这种会改的政策，优先用结构化配置，不靠一份可能过期的 PDF 片段。

交易层是工作流：匹配订单、核对政策、用户确认、再带幂等键调电商接口。模型不单独计算能不能退。权限跟着层走，能读说明书的能力没有退款工具，退款流程里也看不到无关工具。只有排查步骤依赖中间结果时，才在故障这一支放一个有步数上限的 Agent。订单状态永远走交易接口，不写进向量库。

### 11. 你怎么判断一个团队适不适合做 Agent，招人你看工程能力还是模型感

**参考答案**

适合的团队有四个条件：任务窄且成功标准说得清，关键动作已经有接口，写操作有权限和人审，有人每周看 trace。缺少其中一条，Agent 会变成聊天窗口。不适合的信号是：想一周替换整条客服、没有评测、不能接受转人工、把效果问题都交给「再换一个模型」。

招人两边都要，落地时更缺的是工程：会话状态、工具幂等、鉴权、超时和可观测。模型感指的是能判断失败在哪一层、知道什么时候不该用 Agent，不是会从头训练基座。只会 CRUD 的人做不出可回收的循环，只会讲论文的人过不了退款的权限和一致性。面试里让候选人把一个坏例拆成可改的项，比让他背 Agent 名词有用。

### 12. 你最近在学什么，Agent 评测、harness、observability 里哪个最上头

**答题思路**

三个都说「都在看」等于没答。选一个你能连续讲五分钟的，并说明它怎么带动另外两个。

1. 选评测：讲你最近在补的是任务成功怎么定义、离线题和线上分布差在哪。评测没有 trace 就是空的，所以会碰到可观测性；回归要卡住的是循环和工具，所以会碰到 harness。
2. 选 harness：讲你最近在看的停止条件、工具契约、状态放在哪。没有这些，评测跑出来的轨迹无法复现。
3. 选可观测性：讲一条请求要能还原意图、文档、工具和版本号。没有这条链路，评测和 harness 都是黑的。
4. 用你真正读过或写过的一个点收尾。没有就说正在补的缺口，不要编一个研究课题。
5. 可以反问对方线上最痛的是哪一块，把话题交回去。

### 13. 怎么带人把 bad case 分析从“模型不行”写成可落地的改进项

**参考答案**

不接受「模型不行」作为结论。复盘模板固定成六栏：用户原话、期望、实际、trace 里哪一层的证据、改动项、回归用例。改动项只能落在规则、语料、切片、prompt 版本、工具契约或模型版本之一，并写上负责人。说是模型问题的，必须拿出对照：同一上下文、同一工具，只有模型不同才失败。

周会看聚类后的重复问题，不看零散截图。完成不是「已经改了 prompt」，而是回归用例通过，并且写明线上看哪个切片。带人时先改自己的评审标准：没有证据的结论就退回，做几次之后分类会变成习惯。产品本身不支持的需求要单独标出来，不要塞进模型问题。

### 14. 如果面试官说“你们这 Agent 就是 prompt 堆出来的”，你怎么回

**答题思路**

不要反驳「prompt 不重要」，也不要空讲「我们很复杂」。

1. 先承认 prompt 是系统的一部分，它决定模型在给定证据下怎么说、怎么选工具。
2. 再拿一条真实 trace 指给对方看，这些不是 prompt 能自证的：意图和阶段存在模型外面；工具列表按场景裁剪；退款在业务系统里重新鉴权并要求幂等；循环有步数和重复调用上限；发布要过回归集。
3. 把边界说清楚：prompt 约束的是生成，网关约束的是能不能真的退款。模型忽略提示时，拦截要发生在工具层。
4. 请对方指定怀疑的那一层，用一个坏例对一下。没有 trace 就承认那一层当时确实说不清，不要用名词补上。
