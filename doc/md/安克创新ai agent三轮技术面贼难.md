### 3. Python 的 GIL 锁原理及对多线程 CPU 密集型任务的影响

**参考答案**

CPython 传统构建里的 GIL 是解释器级互斥锁，同一进程同一时刻只有一个线程执行 Python 字节码，所以多线程不能把纯 Python 的 CPU 密集任务摊到多核上。

GIL 保护的是引用计数这一类非线程安全的内存管理。线程按时间片让出锁，`sys.getswitchinterval()` 的默认值是 5 毫秒。阻塞 I/O，以及显式释放 GIL 的 C 扩展在执行期间，别的线程可以运行。

因此纯 Python 计算开多线程几乎没有加速，还要付切换成本。等待 LLM 接口和工具返回属于 I/O 密集，线程或 asyncio 都合适，等待时不会一直占着锁。CPU 密集的热点应放到多进程（每个进程一把锁），或放到会释放 GIL 的原生代码里。3.13 起官方另有 free-threaded 构建，运行时是否关掉 GIL 以实际部署的解释器为准，不能假设线上已经无锁。

多进程之间传递大对象会走序列化；会话状态要放在进程外的 Redis 或数据库里，而不是放在某根线程的内存里。

### 4. Java 的 JVM 内存模型及垃圾回收器 G1/ZGC 在长连接流式服务中的表现差异

**参考答案**

这里要答的是运行时内存区域和两种收集器的停顿差异。堆分成新生代（Eden、两块 Survivor）和老年代，类元数据在元空间，每个线程有自己的栈，JIT 代码在代码缓存，Netty 一类框架还会用堆外直接内存。

G1 把堆划成 Region，年轻代回收和混合回收的复制阶段是 STW。停顿跟存活对象量和回收范围有关，暂停目标 `MaxGCPauseMillis` 默认 200 毫秒。它的吞吐通常更好。超过半个 Region 的对象会进 Humongous 区，流式场景里的大缓冲容易踩中。

ZGC 用染色指针和读屏障，标记、整理与业务线程并发进行，停顿主要花在根扫描，通常是亚毫秒到数毫秒，不随堆变大而线性变长。JDK 21 提供分代 ZGC，JDK 23 起分代是 ZGC 的默认模式。代价是读屏障和更多内存余量。

长连接流式输出会持续分配短命的 token、缓冲区，连接和会话又是长寿对象。G1 的 Young GC 一停，所有连接在安全点一起停，表现是 token 间隔抖动、心跳超时和重连。这条链路更适合分代 ZGC。对 P99 不敏感的离线任务用 G1 更划算。

直接内存有单独上限，泄漏不会出现在堆的 GC 日志里。输出要按块写，避免一块缓冲大到被 G1 当成 Humongous。

### 5. Redis 在 Agent 系统中存储 Session 和工具缓存时的大 Key 拆分策略

**参考答案**

会话和工具缓存都不要写成一个巨大的 String 或 Hash。按元数据、单条消息、单次工具结果拆开，让每条命令都短；大结果在 Redis 里只留指针。

大 Key 的读写、删除和过期会长时间占用 Redis 主线程，集群迁移单个槽也会被拖住。会话拆成三层：一个小 Hash 放状态、摘要和已用 token；消息按条存储，列表或 Stream 里只留 id，并用长度上限保住热窗口；完整历史放 MySQL。工具缓存的键要带工具名、版本、参数哈希和租户，结果到了百 KB 以上就改放对象存储。

需要同一条 Lua 一起改的键，用 `{sessionId}` 哈希标签放到同一个槽。互相独立的缓存不要绑在一起，否则一个热会话仍会打满单个节点。读取用 pipeline，扫描用 HSCAN，删除用 UNLINK。工具缓存加 TTL 抖动，同一个 key 并发未命中时做单飞。

用户相关的工具结果不能放进全局键，否则会串数据。拆完之后如果逐条同步读，RTT 会把收益吃掉。

### 6. 场景题：设计一个高并发场景下的意图识别模块，如何兼顾准确率和 RT

**参考答案**

用「精确缓存 → 规则 → 小模型 → 大模型」逐级短路。高置信度请求不要进大模型，把大模型的延迟只花在歧义和长尾上。

请求先做规范化，再查精确缓存。语义缓存只接受很高的相似度，错意图的代价比未命中大。规则负责命令前缀和固定说法。剩下的交给 fastText 或小 BERT，批量推理，输出意图和置信度；高于阈值就返回。低置信度、多意图和集合外的说法再调 LLM 做路由和槽位，并设置超时，超时就退回小模型的结果。

准确率依赖标签里的「其他」类、验证集上标定的阈值，以及线上抽样回流。一句话里既有查询又有操作时要拆成多个意图，不能硬选一个。阈值调高，误判下降，RT 和成本上升。

分类服务单独扩容，不和 Agent 主循环共用一个会阻塞的线程池。缓存键带上意图体系的版本，发版后旧标签不会继续命中。尾部延迟经常来自排队和下游，而不只是模型前向本身。

### 7. RAG 中文档切分（Chunking）的策略及如何处理长文档的上下文丢失问题

**参考答案**

按文档结构切，并用长度上限兜底。标题、段落、列表和代码块先分开，超长再按句子递归切开。固定窗口实现简单，容易把一句话或一张表从中间切断。块太小会丢语境，太大则向量被无关内容稀释。起点通常是几百 token，重叠取块长的一成到两成，最终用召回评测来定。

长文档的上下文丢失要分开处理：

1. 块内指代不清（「上述配置」）：每块带上标题路径，或在入库前给块补一句它在原文中的位置说明，再拿去嵌入。
2. 答案跨过切分边界：重叠、检索后扩展相邻块，或小块检索、父块送进模型。
3. 问题针对整篇文档：除叶子块外再做章节摘要，先召回章节再召回叶子。
4. 召回很多但模型只用到中间：重排后限制送入的块数。

表格和代码单独成块。重叠过大会让同一段反复召回，返回前按文档 id 合并。

### 8. LangChain 中 Expression Language(LCEL)的核心优势及链式调用的底层实现

**参考答案**

LCEL 把提示、模型、解析器和检索器都收成 `Runnable`，用 `|` 组成声明式管道。流式、异步、批处理、并行、重试和追踪走同一套接口，这是它相对旧 Chain 类的核心优势。旧类继承层次深，每个类自己定义调用方式，流式和并行往往要单独补。

`a | b` 会把两边收成 `RunnableSequence`。`invoke` 按顺序执行，上一步的输出就是下一步的输入。`stream` 把迭代器往下传；末尾是模型时可以逐 token 输出，中间的提示模板一般会先完整执行。字典形式的 `RunnableParallel` 在线程池或事件循环里并发跑各分支，汇合后再交给下一步。`with_retry`、`with_fallbacks` 包在某个 Runnable 外面，失败时按策略重试或换备用。

```python
chain = prompt | model | parser
result = chain.invoke({"question": question})
```

LCEL 描述的是无环数据流，循环、共享状态和暂停不在它的模型里。解析器要等完整 JSON 才能产出对象，这时前面的 token 流会在这一步被攒住。

### 9. 向量检索(Vector Search)与关键词检索(BM25)融合时的分数对齐与 RRF 算法

**参考答案**

两路分数不能直接相加。BM25 没有固定上界，和词频、逆文档频率、字段长度有关；向量这边可能是余弦相似度、内积或距离，距离还是越小越好。量纲不同，加权和会被其中一路主导。

倒数排名融合（RRF）只用名次：

\[
\operatorname{RRF}(d)=\sum_i \frac{1}{k+\operatorname{rank}_i(d)}
\]

\(\operatorname{rank}_i\) 从 1 起算，某一路没有召回该文档就记 0。平滑常数 \(k\) 在原始论文和 Elasticsearch 里常用 60。先让 BM25 和向量各取 top-N，按 RRF 排序，必要时再交 cross-encoder 重排。

按查询做 min-max 或 z-score 再加权，也能对齐分数，但候选集一小就会受极端值影响，权重还要单独调。RRF 丢掉了「第一名领先第二名多少」这层信息，换来的是不用关心分数分布。\(k\) 越大，名次之间的差距越被抹平。

### 10. Agent 的 ReAct 范式执行流程及如何防止陷入死循环(MaxIterations 设置)

**参考答案**

ReAct 把一步推理和一次行动绑在一起循环：模型根据当前轨迹给出思考和工具调用，运行时执行工具，把观察结果追加进上下文，再让模型决定继续还是输出最终答案。

只靠提示词说「不要循环」不够。运行时要有硬上限：经典 `AgentExecutor` 的 `max_iterations` 默认是 15。默认的 `early_stopping_method` 是 `force`，到顶后直接返回已停止，不再调用模型；只有改成 `generate` 才会再要一次最终回答。LangGraph 的 `recursion_limit` 默认 25，而一轮「模型 → 工具」往往占两个 super-step，不能把 25 理解成 25 次工具调用。同时加墙钟超时和 token 预算。

上限防不住两种工具来回跳。要把工具名加参数的签名记下来，连续重复或出现短周期就停。观察结果和上一步相比没有新信息，也应当停止。停掉之后把已获得的观察和「未完成」一起返回，并记下轨迹，而不是一直转到接口超时。

工具侧的失败要返回结构化错误，避免模型用同一组参数无限重试。

### 11. 场景题：用户问了一个知识库外的恶意问题，RAG 系统如何做幻觉拦截与兜底回复

**参考答案**

先把「有害请求」和「库里没有答案」分成两条闸门，最后都落到固定兜底，而不是再自由生成一段看起来很有把握的话。

有害、越权和提示注入在检索之前拦截，用策略分类加规则，直接返回拒绝话术。这类请求即使模型参数里「知道答案」，也不能答。检索阶段给召回分数设门槛，门槛用验证集标定。最高分不够或结果为空，就认定知识库没有依据，跳过「根据资料回答」的生成。

进了生成，也要求回答带引用，并做依据检查：引用必须真的出现在召回文本里，可用蕴含模型或一次专门的核对。核对失败就丢弃草稿，改成兜底。兜底分两种固定模板：拒绝回答，以及「资料里没有这个问题的依据」。模板不要再交回同一个不受约束的模型去润色。

文档本身也可能带恶意指令，检索结果按不可信内容拼接，不能抬到系统提示的位置。拦截、空召回和兜底都要记进追踪，方便改门槛。

### 12. Elasticsearch 作为向量库与 Milvus/Pinecone 的选型对比及 HNSW 索引原理

**参考答案**

已有 Elasticsearch、又要关键词、向量和复杂过滤一起做，优先 ES。向量规模和 QPS 上去之后，专用库更合适：自建选 Milvus，想少运维、能接受托管则选 Pinecone。

ES 的优势是 BM25、过滤、聚合和权限模型都成熟，混合检索可以用 RRF。向量索引建在 Lucene 的每个 segment 上，小 segment 多时一次查询要扇出再合并，只读索引可以通过合并 segment 改善，频繁更新的索引不适合反复 force merge。Milvus 面向大规模 ANN，索引种类多，也能做标量过滤；全文能力后来有补充，运维组件比 ES 插件更重。Pinecone 把索引和扩容托管掉，用元数据过滤，代价是费用、地域和索引细节不可控。

HNSW 是多层可导航小世界图。每个点都在最底层，并以几何分布随机进入更高层，所以高层更稀疏。查询从最高层的入口贪心走向更近的邻居，走到局部最优就下降一层，到底层用 `efSearch` 控制的候选集做精细搜索。`M` 控制每个点的连接数，`efConstruction` 控制建图质量。它不用单独训练，召回和延迟都好，内存里要同时放向量和图；删除通常是墓碑，图会慢慢变差，需要重建。过滤很严时，邻居可能都不满足条件，召回会掉，要使用过滤感知的搜索或加大候选集。

### 13. 手撕算法：LeetCode 200 岛屿数量（用 Python 或 Java 实现，并分析 DFS/BFS 复杂度）

**参考答案**

从每个还没看过的陆地 `'1'` 出发，岛屿数加一，然后把与它四连通的陆地全部标记掉。可以直接把格子改成 `'0'`。

时间是 \(O(mn)\)，每个格子进出搜索一次。递归 DFS 的栈深最坏是 \(O(mn)\)，Python 默认递归上限有限，大网格会爆栈。BFS 若在入队时就标记，每个格子最多入队一次，队列上界 \(O(mn)\)；整片矩形陆地从一角漫延时，波前一般是 \(O(\min(m,n))\)。不允许改原网格时，另开 visited，额外空间 \(O(mn)\)。

```python
def numIslands(grid: list[list[str]]) -> int:
    if not grid or not grid[0]:
        return 0
    m, n = len(grid), len(grid[0])

    def dfs(i: int, j: int) -> None:
        if i < 0 or i >= m or j < 0 or j >= n or grid[i][j] != "1":
            return
        grid[i][j] = "0"
        dfs(i + 1, j)
        dfs(i - 1, j)
        dfs(i, j + 1)
        dfs(i, j - 1)

    count = 0
    for i in range(m):
        for j in range(n):
            if grid[i][j] == "1":
                count += 1
                dfs(i, j)
    return count
```

面试里如果网格可能很大，把 DFS 改成显式栈，标记时机仍放在入栈时，避免重复入栈。动态往海里加陆地、多次询问数量的变体，才用并查集。

### 3. LangGraph 的 StateGraph 状态管理机制，如何实现多 Agent 的共享状态与 Checkpoint

**参考答案**

StateGraph 把共享数据定义成一组通道。节点接收当前状态，只返回自己这一步要改的增量；带 reducer 的字段会把旧值和新值合并，没有 reducer 的字段由本次写入覆盖。同一步里两个节点写同一个无 reducer 的字段会报错。

消息列表用 `add_messages`，按消息 id 追加或更新。并行 Agent 各自往字典里写结果时，用命名函数做合并，并且按 Agent 分键，避免同一个键互相覆盖。reducer 保持纯函数，合并结果不要依赖节点谁先跑完。

多个 Agent 在同一张图里时，天然共享这份状态：Supervisor 和 Worker 都读同一份消息和产物，Worker 只写自己的增量。需要草稿隔离时，把 Worker 做成子图，私有字段留在子图，只把结论映射回父状态；子图使用父图的 checkpointer，这样仍落在同一个 `thread_id` 下。

```python
def merge_dict(old: dict | None, new: dict | None) -> dict:
    return {**(old or {}), **(new or {})}
```

`compile` 时传入检查点实现，开发用内存，生产用 PostgreSQL。每个 super-step 结束按 `thread_id` 保存通道值、版本和尚未完成的写入。进程挂了或遇到人工 `interrupt`，用同一个 `thread_id` 恢复；检查点历史也可以回溯。它保存的是这条线程的执行状态，会持续增长，要按份数或时间清理。跨会话的长期记忆放到单独的 Store，不要塞进检查点。

### 4. LangGraph 与 LangChain 的核心区别，为什么生产环境复杂编排选 LangGraph 不选 Chain

**参考答案**

LangChain 的 Chain / LCEL 表达一条无环的数据流：检索、提示、模型、解析器依次执行，一次调用结束状态就在这次返回值里。LangGraph 表达带状态的图，条件边可以回到前面的节点，形成工具循环，并且能在步与步之间把状态存下来。

复杂编排需要三件事：根据观察决定下一步、失败或人工确认后从中间恢复、多个分支把结果并回同一份状态。这些都是图的基本能力。经典 AgentExecutor 虽然外面套了循环，分支、并行和暂停都不好改，生产里会变成一个外部谁也看不见的 while。

线性的「检索然后生成」仍然适合放在图里的一个节点上，用 LCEL 写完即可。选 LangGraph 是因为控制流会回头、要持久化和人工闸门。单次调用的耗时主要在模型，不在这两个框架的函数调用开销。

图一旦能形成环，终止条件就是设计的一部分：最大步数、重复调用检测和预算要写在条件边上，和业务节点一起评审。

### 5. 多 Agent 协作的常见架构（Supervisor-Worker / Hierarchical / Decentralized）及适用场景

**参考答案**

路径固定时用流水线；需要动态点名时用 Supervisor-Worker；领域多到一个协调者装不下，再用层级；对等交接只适合边界清楚、并且外面有终止条件的场景。

Supervisor-Worker 由一个协调者选择下一个 Worker，Worker 做完把结果交还。查询、知识库、设备控制这类职责清晰的分工适合它，权限和审计也好集中。协调者的规划质量决定全局，它自己的延迟和 token 是单点。

Hierarchical 让某个 Worker 再管理一组子 Agent，按领域分成团队。路由规则已经塞不进一个提示词时再用。每加一层都要多一次模型调用，排障要跨多层轨迹。

Decentralized 里 Agent 直接把任务交给同伴，没有唯一调度者。探索性问题比较合适。终止、责任和冲突都不明显，容易循环调用。生产里即使采用交接，也要有共享的步数和预算，冲突用结构化状态和业务规则裁决，而不是让两个模型继续对话。

角色只有两三个、步骤又能写死时，一个 Agent 加工具就够了，先不要上多 Agent。

### 6. Harness 工程中如何做 Agent 的运行时管控（预算控制、Max Steps、权限审批、失败回滚）

**参考答案**

Harness 是模型循环外面的运行时。预算、步数、权限和回滚由它强制执行，提示词只负责把约束再说一遍。

预算按请求和按会话累计 token、费用和时间，每次模型调用前检查。接近上限时，改为根据已有观察给出目前能确定的结论；到达硬上限就停止。Max Steps 记在状态里，条件边走到结束。同一工具、同一参数连续出现，要单独计数，两种工具交替抖动时，总步数可能还没到顶。

工具按风险分级：只读自动执行；写入、支付和外部可见的副作用必须过策略或人工确认。确认放在副作用之前，用检查点把图暂停住。参数做路径、金额和环境的白名单校验，不把生产凭证放进提示词。

失败时，图状态回到上一个成功的检查点；工作区文件回到任务开始时的快照。已经发生的外部副作用走补偿，调用带幂等键，补偿本身也可重复执行。步数限制管不住已经写出去的副作用。审批通过后、提交前崩溃，恢复时要先查下游状态，再决定是否重新提交。

### 7. 意图识别模块的细粒度设计：如何区分闲聊、知识查询、工具调用和操作指令

**参考答案**

这四类的差别是「要不要外部世界」以及「会不会改状态」，不是四句不同的话术。

闲聊不查库、不调工具，直接回复。知识查询的答案在相对稳定的文档里，走 RAG。工具调用读取会变化或属于某个用户的数据，例如订单和设备状态。操作指令会改变状态或触发外部副作用，例如打开开关、退款、下发配置，必须更高的置信度，并在执行前确认。

实现上输出结构化结果：意图列表、槽位、风险等级。规则先接住明确命令；小分类模型处理常见说法；置信度低、或者一句话里有多个意图时，再交给 LLM。实时性和用户私有数据走工具，静态说明走知识库，两者可以同时出现，拆开执行而不是合并成一个标签。

闲聊不要强行去检索，否则既慢又容易把无关文档编进回答。操作类即使分类对了，缺槽位也要追问，不能用空参数去调工具。评测看混淆矩阵，重点看「知识查询被当成工具」和「操作被当成查询」。

### 8. MCP(Model Context Protocol)与 Function Calling 的区别及在工具治理层的落地方式

**参考答案**

Function Calling 是模型的调用约定：应用把工具的 JSON Schema 放进请求，模型返回工具名和参数，应用自己执行并把结果塞回对话。它没有发现、传输和鉴权的标准。

MCP 是应用和工具进程之间的协议，基于 JSON-RPC。Server 暴露 Tools、Resources 和 Prompts，传输用本地 stdio 或远程 Streamable HTTP。模型仍然通过 Function Calling 表达「我要调某个工具」；Host 再把这次调用变成 MCP 的 `tools/call`。两者是上下层，不是二选一。

治理层落在 Host：

1. 连接受控的 MCP Server，把 `tools/list` 同步进内部目录，标上负责人、风险等级和所需权限。
2. 每次请求按用户和任务过滤，只把允许的工具转成模型的 Schema。工具太多时按任务检索，不要全量塞进上下文。
3. 模型给出调用后，先做参数校验和鉴权，再发 MCP 请求。远程 Server 走 OAuth 一类短期凭证，凭证由 Host 注入，不进提示词。
4. 记录调用方、参数摘要、结果和延迟。本地 stdio 进程继承的是宿主机权限，不能把不受信任的 Server 和用户凭证放在一起跑。

协议保证不了模型选对工具。选错要靠目录、校验和确认来挡。

### 9. Kafka/RocketMQ 在异步化 Agent 任务中的事务消息与幂等性保证

**参考答案**

异步任务队列提供的是至少一次投递。事务消息解决的是「本地状态和消息发送」怎么一起成功，幂等解决的是消费端可能收到两次。

RocketMQ 的事务消息是半消息加回查：先发对消费者不可见的半消息，再执行本地事务，然后提交或回滚；Broker 长时间没收到结果就回查本地事务状态。这样不会出现「库里写了任务、消息丢了」或「消息发出去了、本地事务回滚了」。

Kafka 事务保证的是 Kafka 内部跨分区读写的原子性，包含把消费位移和产出消息放在同一个事务里。它不能和 MySQL 事务组成一个原子操作。要用发件箱：任务行和待发送消息放在同一个数据库事务里，再由独立进程投到 Kafka。

消费端两边一样做。以 `task_id` 建唯一约束，状态分为处理中、成功、失败。已经成功的重复消息直接返回上次结果；处理中的消息不要再开一次副作用；失败且可重试的，在租约超时后再试。同一会话用同一个消息键，保证进同一分区。异步处理时不要在副作用完成前提交位移，否则失败的任务会丢。

### 10. 场景题：多 Agent 并行执行部分失败，如何设计补偿机制（整体失败 vs 部分成功降级）

**参考答案**

先给每个子任务标清是否关键、有没有副作用，再决定整单回滚还是带着失败说明返回。补偿按 saga 逆序执行，并且可以重复调用。

编排器看到的是 DAG。没有依赖的 Agent 并行，有依赖的等上游成功。每个 Agent 返回状态、结果和补偿所需的句柄，不只有一段自然语言。

只读步骤失败就在预算内重试。它若是关键路径，重试耗尽则整单失败；若只是附加信息，主结果照常返回，并写明少了哪一块。有副作用的步骤一旦失败，已经成功的副作用按相反顺序补偿，例如先退款再释放库存。补偿失败进入人工队列，对外不能说已经恢复原状。

付款和发货这类有一致性要求的步骤必须同成同败。回答用户和顺便推荐配件可以部分成功。超时先按幂等键查询下游的真实状态，再决定补偿还是重试。用户已经收到失败之后，还在跑的分支要用统一的截止时间取消，避免后台继续下单。

### 11. Java 的 CompletableFuture 如何编排多个异步工具调用的串并行与异常聚合

**参考答案**

互相独立的工具用 `supplyAsync` 并行，后一个依赖前一个结果时用 `thenCompose` 串起来。`thenApply` 只做映射，如果它返回的又是一个 `CompletableFuture`，会得到嵌套，串行工具调用应使用 `thenCompose`。

`thenCombine` 和 `allOf` 在任意一路异常时会失败，而且你直接 `join` 往往只能看到其中一个，包装在 `CompletionException` 里。要聚合，就先对每一路 `handle`，把成功值和异常都收成普通对象，再合并。业务异常一般在 `CompletionException.getCause()` 里，回流给模型前把包装剥掉。

阻塞型工具不要放进 `ForkJoinPool.commonPool()`，单独配线程池。`orTimeout` 只会让 Future 以超时结束，底层任务还在跑，需要任务自己响应中断，或在超时时配合可取消的调用。允许部分成功时，把失败工具的列表交给汇总步骤，保留已经成功的结果。

```java
record ToolOutcome(String name, String value, Throwable error) {}

CompletableFuture<ToolOutcome> guard(CompletableFuture<String> call, String name) {
    return call.handle((value, error) -> new ToolOutcome(name, value, unwrap(error)));
}

static Throwable unwrap(Throwable error) {
    Throwable current = error;
    while (current instanceof CompletionException && current.getCause() != null) {
        current = current.getCause();
    }
    return current;
}
```

独立的两路先各自 `guard`，再 `thenCombine`。需要用到这两路结果的生成步骤放在 `thenCompose` 里。这样一条工具失败不会把另一条的结果弄丢。

### 12. Agent 的可观测性设计：如何做全链路 Trace (Input/Output/Tool Call/Latency/Token)及 LangSmith/LangFuse 集成

**参考答案**

一次用户请求对应一条 Trace，下面按阶段挂 Span：意图、每次模型调用、每次检索、每次工具调用、汇总。模型 Span 上记录模型名、输入和输出 token、首 token 时间、总延迟和是否成功；工具 Span 上记录工具名、参数摘要、结果摘要、延迟和错误类型。按 OpenTelemetry 的 GenAI 语义约定落这些字段，后面换后端才不用改埋点。

不要为每个 token 建一个 Span。输入输出可能含凭证和个人信息，入库前打码，完整正文按保留期单独存。异步任务和远程 MCP 调用把 `traceparent` 放进消息头或 HTTP 头，否则队列两边会断成两段无关联的 Trace。

LangChain 和 LangGraph 打开 LangSmith 的追踪开关后，节点和模型调用会自动上报，项目用环境变量区分。自定义步骤用它的 traceable 或回调补进同一条 Trace。数据不能出内网时用 LangFuse：可以用它的 LangChain 回调，也可以走 OpenTelemetry。LangFuse 同时用来挂评测分数和会话 id。

指标侧用直方图看延迟和 token，不要只看平均值。告警看工具失败率、单次任务 token 和循环步数。采样可以降正文采样率，错误请求和超预算请求保持全量。

### 13. 场景题：上下文窗口（Context Window）即将溢出，你的截断、压缩与长期记忆检索策略是什么

**参考答案**

先区分两份数据：检查点里的状态可以完整保存，送进模型的上下文只放这一步要用的。调用前用该模型的 tokenizer 计数，到达窗口的七到八成就压缩，不等接口返回超长错误。

截断时钉住系统提示、用户的硬约束和当前目标，从最早的闲聊和过期工具结果开始删。只留头尾会丢掉中段里已经做出的决定。

压缩把即将删掉的历史收成滚动摘要，替换原文；最近几轮保持原文。摘要里保留实体、决定、未完成事项和仍有效的工具结果。工具返回是最常见的爆窗来源，旧结果改成带 id 的占位，需要时再读；大对象放工作区或对象存储。

稳定事实写入可检索的长期记忆，下一轮按当前问题召回，不回放全部历史。摘要可能丢掉「不要退款」这类否定约束，所以约束做成结构化字段，不参与覆盖。压缩本身也是一次模型调用，算进预算。摘要和结构化状态冲突时，以结构化状态为准。

### 14. 手撕算法：LeetCode 139 单词拆分(考察 DP 或记忆化搜索，关联文本分词场景)

**参考答案**

`dp[i]` 表示前 `i` 个字符能否被词典拼出来，`dp[0] = True`。枚举结尾 `i` 和起点 `j`，只有 `dp[j]` 为真且 `s[j:i]` 在词典里，才把 `dp[i]` 标真。词典放进集合，并限制窗口不超过最长词。

设串长 \(n\)、最长词长 \(L\)。窗口枚举是 \(O(nL)\)，Python 里切片和哈希还要 \(O(L)\)，总时间约 \(O(nL^2)\)，空间 \(O(n)\) 再加词典。记忆化搜索是同一递推的另一种写法。纯回溯在歧义多时会指数膨胀。

这和检索前的词典分词是同一类问题：139 只判断能不能拼上，不处理一词多切。生产里要的是一种切分，通常在这个 DP 上再加词频或最大匹配，并为未登录词留策略。

```python
def word_break(s: str, word_dict: list[str]) -> bool:
    words = set(word_dict)
    max_len = max((len(w) for w in words), default=0)
    n = len(s)
    dp = [False] * (n + 1)
    dp[0] = True
    for i in range(1, n + 1):
        for j in range(max(0, i - max_len), i):
            if dp[j] and s[j:i] in words:
                dp[i] = True
                break
    return dp[n]
```

空窗口不会参与匹配，因为 `j < i`。找到一种拼法就 `break`，后面的起点不用再试。

### 1. 自我介绍

**答题思路**

三面关注判断和责任边界，一分钟到一分半：

1. 用一两句说明你做过的系统规模和你在里面的角色，是模块负责人还是能拍板选型的人，按真实情况说。

3. 补一句跨角色协作，例如和算法、后端或业务怎么对齐评测标准。
4. 结尾落到你来这个岗位想继续负责的范围：编排、稳定性或工程规范。

### 2. 项目介绍及你在其中承担的架构职责与技术选型决策

**答题思路**

这题要的是决策，不是把二面的流程再讲一遍：

1. 用三十秒重述业务目标和你的职责边界。
2. 选两个真实决策展开，例如编排用图还是用固定流水线、会话状态放 Redis 还是放数据库、检索用现有搜索引擎还是单独的向量库。
3. 每个决策讲清约束：数据规模、延迟、团队熟悉度、能不能自运维。然后讲放弃的方案差在哪里。
4. 讲这个决策上线后的信号：事故、成本或效果。如果后来推翻过，说明是什么证据让你改的。
5. 主动区分「我建议并落地的」和「别人定好我执行的」。

### 3. 如何管理跨语言的 Agent 工程团队(Python 算法侧与 Java 后端侧)，怎么定协作规范

**答题思路**

用你真实团队的分工来讲，规范可以按下面五条组织：

1. 契约先于实现。工具用 JSON Schema，Java 服务用 OpenAPI，追踪字段两边同一份定义。Schema 进仓库，CI 做兼容检查。
2. 边界写清楚：Python 侧负责图编排、提示、检索和评测；Java 侧负责网关、鉴权、会话和工具后端的并发与一致性。生产路径上，算法进程通过服务改数据，不直接写业务库。
3. 一个需求的完成标准同时包含 Schema、超时、幂等、Trace 字段和评测样例。
4. 评审按契约走。有分歧就写 ADR，记录放弃了什么。
5. 值班按链路排，一次故障两边对着同一条 Trace 看，不按语言分成两个群各自猜。

模型能力变了，这条边界要定期重定，把重定的条件也说出来。

### 4. 当算法同学坚持用新模型导致成本飙升但效果微增，后端同学反对接入，你怎么沟通拍板

**答题思路**

讲一次你真实经历过的取舍；没有同款经历，就按这个决策顺序回答，数字用自己项目里的：

1. 先把双方拉到同一张表：离线提升、线上任务成功率、单次成功的成本、P95 延迟、容量和故障域。效果用同一套评测集，不拿演示对话做依据。
2. 提升若落在噪声里，或成本和延迟的上升明显大于成功率的上升，默认不进主流量。
3. 折中方案是按请求路由：只有低置信度或高价值的子集走新模型，其余保持原模型。后端的反对落实成配额、熔断和失败时退回旧模型。
4. 写出拍板人和回看日期。到期用同一张表决定留下还是撤掉。
5. 表述时把算法同学的效果目标和后端同学的稳定性目标都复述准确，再给出结论。

**参考答案**

进度按可演示的垂直切片来切，每片都有评测样本。模型波动和慢工具从工程关键路径里隔开，开发和回归使用录制好的响应。

LLM 接口不稳定时，调用本身有超时、有限次重试和备用模型。只重试超时和 5xx，参数错误不要重试。CI 回放固定的模型响应和工具桩，提示词实验和功能开发分开排期。线上对供应商做熔断，一个接口抖动不能挡住其他需求联调。

工具耗时不可控时，DAG 上能并行的并行，每步有自己的预算，慢工具不放进所有请求的必经之路。对外承诺看 P95。需要长时间跑的步骤进队列，接口先返回任务 id。

评测集和工具契约没冻结之前，不承诺效果数字。每周看 badcase 和里程碑，达不到就减场景，而不是在月底第一次把整条链路串起来。

### 6. 生产级 Multi-Agent 系统的评估体系：除了答案正确率，还看哪些指标(步数效率、Tool Call 正确率、Token 成本、轨迹合理性)

**参考答案**

最终答案对，只说明这次碰巧答对。生产评估要同时看过程能不能稳定复现。

答案正确率：有标准答案就做字段级比对；开放回答用评分量表，并抽查人和 LLM 裁判的一致性。步数效率看实际步数相对参考轨迹的比例，另计重复工具调用。Tool Call 正确率拆成工具名和参数，参数先过 Schema，再比关键字段；只看名字会放过「工具对了、参数是错的」。Token 成本按成功任务计总费用，失败和重试算进去。轨迹合理性先用规则查死循环、越权工具和跳过确认，再用评分看每一步是否在服务目标。

同一任务要重复跑。`pass@k` 表示 k 次里有一次成功，`pass^k` 表示 k 次都成功。线上更接近后者。延迟、拒答是否正确、工具失败后能否恢复，作为同一张报表上的伴随指标。

评测集按意图分层，否则闲聊的高分会盖住操作类的失败。轨迹和标准答案一起存，模型或提示词变了就回放。

### 7. Harness 工程中 Environment 隔离与 Workspace 管理的设计，如何防止 Agent 越权修改关键数据

**参考答案**

每个任务使用独立工作区，跑完即销毁。代码和命令放在容器或更强的隔离里，CPU、内存、磁盘和时间有上限。仓库以只读方式挂进去，写入只落在这个工作区；需要保留的补丁由运行时导出，而不是让 Agent 直接推主干。

凭证不进提示词，也不进工作区文件。工具调用由经纪进程注入短期、最小范围的令牌。网络走白名单。数据库不把生产写账号交给模型，改数据必须经过带鉴权的工具，参数里的环境由服务端填，不由模型填。

工作区开始时做文件快照，任务失败就回到快照。每一次命令、文件变更和工具调用留下审计。高风险写操作在隔离环境里先执行，人工确认后再对生产重放，重放带幂等键。

提示词里的「不要访问某目录」不是边界。路径校验、系统用户权限和网络策略才是边界。检索到的文档和网页按不可信输入处理，避免其中的指令把工具调用带去改关键数据。

### 8. 技术选型：自研 Agent 编排框架 vs LangGraph/CrewAI/AutoGen，考量维度有哪些（可控性、可维护性、生态、性能）

**参考答案**

编排层要的是看得见的状态转移；沙箱、权限、预算这些 Harness 能力没有标准产品，通常自己做。两边不要用三套框架套在一起。

可控性：LangGraph 的状态、边、暂停和检查点是显式的，分支可以单测。自研一个循环也可以同样显式，但恢复、合并和回溯都要自己补。CrewAI 以角色和流程为主，AutoGen 以多 Agent 对话为主，下一步经常藏在一次模型回复里，闸门和精确恢复都更绕。

可维护性：自研初期代码少，人员一流动就剩下没人敢改的循环。LangGraph 有学习成本，图本身可以被别人读懂。CrewAI、AutoGen 适合维护对话式原型，版本变化也快，锁定版本之前不要写成生产承诺。

生态：LangGraph 和 LangChain 的检查点、追踪、工具绑定最完整。另外两者更轻，周边要自己接。

性能：框架函数调用相对模型延迟可以忽略。真正的差别是抽象会不会诱使你多调几次模型。对话式群聊最容易把 token 打满。循环很简单、团队也不想跟框架发布节奏时，自研薄循环更合适；一旦需要暂停、回溯和多分支合并，就用 LangGraph 这一类显式图。

### 9. Redis 的多级缓存设计在 RAG 热点知识召回中的应用及缓存穿透（用户问不存在问题）的处理

**参考答案**

热点问答分三级。进程内用短 TTL 的 LRU 放最热的一小撮结果；Redis 放规范化问题到文档 id 或稳定答案的映射；向量库和原文是源头。键里带上知识库版本，文档更新后旧键靠 TTL 淘汰，不用在线上扫 Key。个性化答案不进全局缓存。

缓存穿透是每次都查一个根本没有的数据，缓存和源头都不会命中，请求全部打到向量检索。这和热点键过期（击穿）、大量键同时过期（雪崩）不同。用户随口问的不存在问题就是穿透：问题空间没有上界，布隆过滤器只能用来判断有限的已知 FAQ 键，盖不住开放问句。

处理方式是：对规范化之后的查询缓存「空结果」，TTL 短，并且同样带知识库版本，避免新文档入库后仍被空结果挡住。相同查询并发未命中时单飞，只放一个请求去检索。对高基数、低重复的客户端做限流。明显的垃圾输入和安全拦截放在嵌入之前。空结果不要用很长的 TTL，否则索引刚更新也会继续被当成没有资料。

### 10. MySQL 在存储 Agent 会话、任务状态、评估数据时如何做分库分表与读写分离

**参考答案**

会话和任务按用户路由，评估数据按时间拆开，并且不要和在线事务库混在一张表里。

在线查询几乎都带 `user_id` 或 `session_id`。分片键用 `user_id`，一个用户的会话和消息落在同一分片，历史列表不用跨库。任务状态和所属会话放在一起，状态迁移就不必做跨库事务。回调若只带 `task_id`，路由信息要编进 id，或在 Redis 里留 `task_id` 到 `user_id` 的映射。超大会话再按 `session_id` 拆消息，通过用户分片上的映射找到它。主键用全局发号，分片之后没有跨库外键。

消息正文过大时，库里只留摘要和对象存储的地址。索引围绕 `(user_id, updated_at)` 和 `(session_id, created_at)`。

写和立刻要读到的状态走主库，包括任务状态机。从库有复制延迟，读从库会把刚写的步骤读丢。历史列表和运营查询走从库。评估数据按月分区或直接进分析库，聚合查询不打在线主库。扩容用双写或按分片搬迁，应用侧只依赖路由，不写死库的台数。

### 11. 你最近在学什么 AI 新技术或论文，怎么快速验证一个新框架（如 LangGraph 新特性）是否值得引入生产

**答题思路**

只讲你真的读过或用过的一个点，按「问题 → 机制 → 和当前系统的关系 → 你还没确认的地方」来说。例如你最近看的是 MCP、上下文压缩或某次 LangGraph 发布，就讲那个，不临时换一个更时髦的名字。

验证一个新特性值不值得进生产，按这个顺序做：

1. 先写判定标准：它要去掉的是哪一个现有痛点，成功看任务成功率、恢复是否正确、延迟和 token。标准写在试验之前。
2. 在分支里做一个垂直切片，读迁移说明，确认要锁的版本。
3. 用录制的线上轨迹回放新旧实现，比较成功率和成本，不用几次手工对话下结论。
4. 做故障注入：步与步之间把进程杀掉，看检查点能否续跑；同一工具回调两次，看会不会重复副作用。
5. 给几天时间。指标没有更好，就维持原样。要上线也用开关控制，并保留回退版本。

具体 API 以你核对过的版本文档为准，没看过的行为不要讲成已经验证。

### 12. 你怎么构建自己的技术判断力，在 AI 工程化这么卷的领域怎么持续学习并反哺团队

**答题思路**

用你的真实习惯回答，下面是一条说得完整的线：

1. 判断从现有瓶颈出发。当前是循环停不下来、检索不准，还是成本太高，就只深挖解决这个瓶颈的材料。新模型和新框架先过「它改变的是不是我们的评测指标」。

4. 学习节奏绑到迭代：每个周期留固定时间处理 badcase，坏案例比时间线更能决定下一周学什么。
5. 团队里把「试过并放弃」公开出来，避免别人再花一周验证同一个特性。

### 13. 手撕算法：LeetCode 146 LRU 缓存(手写双向链表+HashMap或用 Java LinkedHashMap，关联上下文缓存淘汰策略)

**参考答案**

哈希表按 key 找到节点，双向链表维护使用顺序：最近使用的放在头哨兵后面，最久未使用的在尾哨兵前面。`get` 命中就把节点挪到头部；`put` 已存在则更新并挪到头部，不存在就插入头部，超过容量时删掉尾部节点，并删掉哈希表里的 key。操作都是 \(O(1)\)，空间 \(O(\text{capacity})\)。

```python
class Node:
    def __init__(self, key: int = 0, val: int = 0):
        self.key, self.val = key, val
        self.prev = self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map: dict[int, Node] = {}
        self.head, self.tail = Node(), Node()
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node: Node) -> None:
        node.prev.next, node.next.prev = node.next, node.prev

    def _add_front(self, node: Node) -> None:
        node.next, node.prev = self.head.next, self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.map:
            return -1
        node = self.map[key]
        self._remove(node)
        self._add_front(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            node = self.map[key]
            node.val = value
            self._remove(node)
            self._add_front(node)
            return
        if len(self.map) == self.cap:
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]
        node = Node(key, value)
        self.map[key] = node
        self._add_front(node)
```

Java 可以用 `LinkedHashMap`，第三个构造参数 `accessOrder` 必须为 `true`，否则是插入顺序，不是最近使用顺序。在 `removeEldestEntry` 里用 `size() > capacity` 淘汰。构造函数里的 capacity 只是初始容量，不是最大条数。`accessOrder` 模式下 `get` 也会改链表，迭代时再 `get` 会触发 `ConcurrentModificationException`；它也不是线程安全的。

上下文缓存若直接套 LRU，有两个缺口。窗口限制的是 token 不是条数，淘汰时要按 LRU 顺序累计 token，直到回到预算。系统提示和硬约束要钉住，不能跟普通轮次抢同一个容量。工具结果又大又只在当步有用，应比普通消息更早被逐出。RAG 热点缓存还要加 TTL 或版本，否则知识更新后，热键会一直留在 LRU 里。

### 7. 职业规划是往技术专家还是技术管理走，为什么
