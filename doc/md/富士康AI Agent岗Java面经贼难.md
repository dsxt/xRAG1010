## 一面

### 1. 自我介绍

**答题思路**

控制在 1～2 分钟，按「身份 → 技术栈 → 一个项目 → 为什么匹配」讲：

1. 一句话说明 Java 后端年限，以及最近是在做 LLM 应用，还是仍以业务后端为主、刚开始接模型。
2. 技术栈按这个岗位排：Java、Spring、MySQL、Redis、消息队列，然后是模型调用、RAG、工具调用。名词点到为止。
3. 只展开一个最熟的项目：谁在用、你负责哪一段、线上你守过什么。有真实指标就用自己的，没有就讲一类故障和改法。
4. 收在匹配点：能把模型放进已有的 Java 服务里，把超时、权限和失败收住。

简历上的框架名不要铺开，把时间留给追问。

### 2. 简单介绍你做过的 AI 相关项目或最熟悉的 Java 后端项目

**答题思路**

有 AI 项目就讲 AI，没有就讲最熟的 Java 系统，并说明模型能接在哪一段。不要临时编一个 Demo。按「问题 → 链路 → 你的部分 → 结果」讲，3 分钟内：

1. **问题**：谁在用，原来靠人、规则还是检索。痛在找不到、答错，还是动作执行错。一句话说清怎样算成功。
2. **链路**：请求从入口到回复经过哪些步。哪些步是确定代码（鉴权、查库、下单），哪些步交给模型（理解说法、组织语言、选择工具）。
3. **你的部分**：点名你写的模块，例如会话状态、检索、工具封装、幂等或评测。团队做的和自己做的分开。
4. **结果**：用真实现象，例如人工接手变少、一次具体的召回错误怎么修的。没有数字就不要编。
5. **边界**：如果重做，哪类写操作会从模型手里拿回到服务端。

面试官要听到你见过失败，不是听一遍框架介绍。

### 3. Spring AI 是什么，和 LangChain 相比它的优势和定位是什么

**参考答案**

Spring AI 是 Spring 团队的 AI 应用框架：用统一的 `ChatModel`、`EmbeddingModel`、`VectorStore` 屏蔽供应商差异，再嵌进 Boot 的配置、注入和可观测性。它要解决的是 Java 服务怎么稳定地调用模型，不是再做一个研究向的链式实验场。

LangChain 起源于 Python，把提示、检索、工具和 Agent 拼成可组合的链；状态更复杂的流程现在多用 LangGraph。生态大、迭代快，和数据脚本贴得近。Java 里接近的名字是 LangChain4j，不是把 Python 库直接搬进 Spring 容器。

对已有 Spring Boot 系统，Spring AI 的优势是工程对齐：`ChatClient` 的用法接近 `RestClient`，换模型多半改配置；Advisor 把记忆、RAG、日志做成可插拔横切；工具就是 Java 方法，能走原来的事务、鉴权和审计。代价也明确：复杂状态图和社区工具数量不如 LangGraph。工具循环和 RAG 用 Spring AI 更贴这个岗位；长流程要断点、分支、人工暂停时，不必为了「统一技术栈」否掉专门的编排引擎。

容易漏的是定位：Spring AI 管的是应用集成。模型效果、切片质量和工具是否幂等，仍然是你的设计，不是引入 starter 就自动具备。

### 4. Spring AI 中 ChatClient、PromptTemplate、Advisor 分别起什么作用

**参考答案**

三者是三层，不要混成一个「调用大模型的对象」。

`ChatClient` 是面向模型的流式客户端，底下仍是 `ChatModel`。你用它拼系统提示、用户消息、Advisor 和工具，再选择同步 `call()` 或流式 `stream()`。真正发请求发生在 `content()`、`chatResponse()` 这类取值时，不是调用 `call()` 的那一下就已经执行完。

`PromptTemplate` 负责把带占位符的文案和运行时变量渲染成最终提示。`ChatClient` 的 `.user(u -> u.text("用{lang}解释{topic}").param(...))` 内部就在用它。默认渲染器是基于 StringTemplate 的 `StTemplateRenderer`，占位符是 `{变量}`。提示词里如果有 JSON 示例，花括号要转义或换成不会冲突的渲染器，否则运行时直接渲染失败。

Advisor 是包住这一次模型调用的拦截链，类似 Filter：调用前改写 Prompt，调用后改写响应，多个按顺序嵌套。常见的是 `MessageChatMemoryAdvisor` 补历史，`QuestionAnswerAdvisor` 或 `RetrievalAugmentationAdvisor` 做检索增强，`SimpleLoggerAdvisor` 打调试日志。记忆要排在检索前面，检索才看得到补全后的问题。较新版本还会自动加入 `ToolCallingAdvisor` 执行工具循环。工具是模型可调用的能力，Advisor 是框架的横切，二者不是一回事。

### 5. 什么是 RAG，完整链路分哪几步，结合 Spring AI 说下各阶段用的组件

**参考答案**

RAG 是先从外部资料检索出证据，再让模型基于证据生成，用来补上模型参数里没有或已经过期的事实。链路分入库和问答两段。

入库：`DocumentReader`（PDF、Tika、Markdown、纯文本）读成 `Document`，`TokenTextSplitter` 或按标题切的 `TextSplitter` 做分块，`EmbeddingModel` 向量化，写入 `VectorStore`。原文和版本、租户、权限放元数据，不要只存一个向量。

问答：多轮对话先用 `CompressionQueryTransformer` 把历史收成独立问题，必要时再用 `RewriteQueryTransformer` 改写。`VectorStoreDocumentRetriever` 按向量检索，并加上租户、文档版本这类过滤。可选重排后，由 `ContextualQueryAugmenter` 把片段拼进提示，`ChatClient` 调用 `ChatModel` 生成。这条流水线可以收成 `RetrievalAugmentationAdvisor`；只做「检索然后拼到用户问题后面」时，`QuestionAnswerAdvisor` 就够。

默认的 `ContextualQueryAugmenter` 在上下文为空时会改写提示，让模型不要回答。这仍是提示词约束。价格、库存、是否允许回答，应用代码里还要再拦一次。

容易漏：入库和查询必须用同一个嵌入模型、同一种归一化。换模型而不重建索引，相似度没有意义。

### 6. 文档切分 ChunkSize 和 Overlap 怎么选，过大过小分别有什么问题

**参考答案**

ChunkSize 是一块的长度，Overlap 是相邻块故意重复的部分，用来保住被切点切开的句子。没有普遍正确的默认值。先按文档结构切：标题、条款、表格、代码块尽量整块保留，固定窗口只做兜底。长度用嵌入模型自己的 tokenizer 算，中文不要按字符数估算。问答场景常见起步是几百 token，重叠大约一成到两成，然后用一批真实问题看召回再调。

过大时，一块里混着多个主题，向量变成平均语义，精确问题打不中；送进模型的噪声多，引用也对不齐某一句，token 更贵。过小时，限定条件和结论被拆开，块本身看不懂；块数量上升，嵌入和检索成本都上去。

Overlap 过大，相邻块高度重复，检索结果挤占上下文，存储也浪费。Overlap 为 0，边界上的那句话两边都不完整，两块分数都不高。表格和列表不要为了凑重叠从中间截断。

容易漏：召回的是小块，生成时却需要它所在的整节。可以检索小块、回表带回父级段落，而不是把 ChunkSize 一味加大。

### 7. 向量数据库选型——Milvus、PgVector、Redis Vector 各自适合什么场景

**参考答案**

三者都能做近似最近邻，差别在数据规模、过滤方式和你愿不愿意多养一个系统。

PgVector 适合语料中等、过滤条件又多的业务库。向量和订单、文档、租户在同一个 PostgreSQL 里，过滤就是 SQL，事务和备份不用另做。索引常用 HNSW 或 IVFFlat。数据大到索引构建和延迟明显吃紧时，它就不是专用检索引擎。

Milvus 适合作为独立的检索服务：集合大、QPS 高、要分区和多副本。索引可以按场景选 HNSW、IVF，数据放不进内存时再考虑 DiskANN。代价是单独的集群、监控和容量规划。

Redis Vector（RediSearch 的向量字段，HNSW 或 FLAT）适合已经在用 Redis、集合不大、又要低延迟的热索引，例如会话级检索或缓存后的热门文档。向量常驻内存，维度高、条数多时成本会明显高于前两者，而且淘汰策略开着就不能把它当知识库的唯一副本。

选型可以收成一句：强过滤、中等规模、想少一个组件，用 PgVector；检索本身就是平台服务，用 Milvus；低延迟热数据，用 Redis，冷数据仍落在持久库。

### 8. Embedding 模型中文场景下怎么选，语义相似度用余弦还是点积，为什么

**参考答案**

中文场景先看检索效果、上下文长度、维度、延迟，以及能不能私有化部署，不要只认一个名字。比较时用中文检索集（常见参照是 C-MTEB）加上你们自己的业务问题。bge-m3 这类模型同时覆盖中文和多语言，还带稀疏向量，适合要混合检索的私有化；通义、Qwen 的嵌入接口适合不想自建 GPU 的时候。选定之后，入库和查询必须是同一个模型和同一套归一化，换模型就要重建索引。

语义相似度比的是方向，不是向量有多长。余弦看的是夹角；点积把夹角和长度乘在一起。模型如果按对比学习做了 L2 归一化（bge 一类通常如此），长度被固定，余弦和点积的排序相同，这时用点积多半只是索引实现更直接。没做归一化就用点积，长文档会因为向量更长而压过真正相近的短文档。模型卡写余弦就用余弦，写内积就用内积。

PgVector 里 `<=>` 是余弦距离，`<#>` 是负的内积，排序方向相反，写反了就会召回最不像的。Milvus 的 COSINE 和 IP 也一样，索引度量和查询度量必须同一套。

### 9. RAG 召回质量差怎么优化（Hybrid Search、Rerank、Query 改写等）

**参考答案**

先确认差在召回还是生成。证据根本没进前 K，改提示词没用。优化按漏掉的原因分层，并用固定问题集看 Recall@K，不要凭几次聊天判断。

Query 改写解决「问法不对」。多轮里的「它呢」要先压成独立问题；一个问题里的两个实体可以拆开各查一次再合并。改写会跑偏，改写后的查询要和原问题一起留在日志里。

Hybrid Search 解决「语义近但关键词丢了」。向量一路召回改写过的说法，BM25 一路召回错误码、型号、专有名词。两路分数不能相加，尺度不同。按名次做倒数排名融合即可，Elasticsearch 的 RRF 里常数 k 常用 60。融合前先按租户、版本、权限过滤。

Rerank 解决「前几十条里有答案，但没排到最前」。用交叉编码器把大约几十条压到三五条再送给模型。多一次模型调用，延迟上去，所以只重排融合后的候选，不重排全库。中文语料要用中文重排模型。

另外两件容易漏：切片把条件和结论切开时，要回表取父文档；空结果和低相关结果要拒答。召回没变好之前，不要先加大模型。

### 10. 什么是 AI Agent，ReAct 范式中 Reason→Act→Observe 各步含义

**参考答案**

AI Agent 是围绕一个目标反复决定下一步的系统：模型可以调用工具，看到结果后再继续，直到完成或被停下来。一次「提问然后回答」不是 Agent。工具、停止条件和状态都在服务端，不在模型的自我描述里。

ReAct 把这个循环写成推理、行动、观察交替进行。

- Reason：对照目标和已经拿到的观察，判断还缺什么、该用哪个工具、参数从哪来。论文里的 Thought 就是这一步。生产里不一定把思考过程展示给用户。
- Act：真正发出工具调用。没有执行，就只是链式思考，外部事实不会变。
- Observe：工具的成功或失败写回上下文。下一步必须基于这条观察，不能对错误视而不见再编一个结果。

循环在模型给出最终答案时结束，也在步数、超时或重复调用到上限时结束。工具报错要作为 Observe 交回去，同时限制同一种错误的重试，避免空转把 token 打光。

容易漏：Agent 的权限是工具白名单决定的。模型说自己「可以退款」不算数，没注册的工具就不能出现在这次请求里。

### 11. Spring AI 中 Function Calling / Tool Calling 怎么定义和注册，Java 方法参数是如何映射的

**参考答案**

模型返回的是调用意图，不是工具结果。Spring AI 把 Java 方法收成 JSON Schema 交给模型；模型给出工具名和一份 JSON 参数；框架绑定到方法上执行，再把返回值送回模型，直到不再出现工具调用。`ChatClient` 会通过工具调用 Advisor 把这个循环跑完，也可以关掉自动执行，自己处理 `ToolCall`。

定义用 `@Tool` 写清何时该调用。参数默认都是必填，用 `@ToolParam` 补充描述，不确定的信息标 `required = false`。必填又无法从用户话里得到的字段，模型会编一个值。

```java
class OrderTools {
    @Tool(description = "按订单号查询订单状态，不要用来创建订单")
    public OrderView query(
            @ToolParam(description = "业务订单号") String orderId) {
        return orderService.find(orderId);
    }
}

String answer = chatClient.prompt()
        .user(question)
        .tools(orderTools)
        .call()
        .content();
```

每个请求用 `.tools(...)`，所有请求共用就放在 `ChatClient.builder(...).defaultTools(...)`。需要运行时决定 schema 时，用 `MethodToolCallback` 或 `FunctionToolCallback` 做成 `ToolCallback`。

参数映射是：`JsonSchemaGenerator` 按形参生成对象 schema，属性名来自参数名，嵌套的是 record 或 POJO 的字段；模型返回的 JSON 再绑定回这些形参，返回值默认用 Jackson 转成字符串。编译必须打开 `-parameters`，否则属性名会变成 `arg0`，模型和 Java 对不上。`ToolContext` 不进 schema，租户和用户 id 从这里拿，不能让模型填。`Optional`、`Flux` 这类参数没有可用的 schema，不要出现在工具方法上。

### 12. MCP（Model Context Protocol）是什么，解决什么问题，和直接在代码里硬编码工具调用比有什么好处

**参考答案**

MCP 是一套开放协议，规定 AI 应用（Host/Client）如何发现并调用外部能力。传输用 JSON-RPC，本地进程走 stdio，远程走原先的 HTTP+SSE，新版本用 Streamable HTTP。服务器对外提供的主要是工具、资源和提示模板：客户端先 `tools/list`，再 `tools/call`。

它要解决的是每个应用各写一套工具接入。没有协议时，工具的 schema、鉴权、生命周期都绑在某个 Agent 的代码里，换一个客户端就得再接一次。MCP 把「有哪些工具、参数是什么、怎么调用」标准化，同一个 Server 可以被多个 Host 复用。

和在进程里直接注册 Java 工具比，好处是部署和权限可以切开：工具用别的语言写、单独发布，挂了不影响模型进程；新工具通过发现出现，不必重新编译 Agent；能力边界在 Server 上，而不是散落在提示词里。代价是多一跳，延迟、超时和版本协商都要管。

只有本服务自己用、又要和本地事务放在一起的工具，直接注册更快，也更好调试。被多个 Agent 共用、需要独立发布或隔离故障时，再做成 MCP。不要把所有函数调用都搬出去。

### 13. Spring AI 如何作为 MCP Client 连接 MCP Server 获取工具能力

**参考答案**

用 MCP Client 的 Boot starter。每个连接会建一个 MCP 客户端，starter 在工具回调开启时（默认开）把各 Server 的工具收成一个 `ToolCallbackProvider`。业务侧把它交给 `ChatClient`，模型就跟调用本地工具一样。

```yaml
spring:
  ai:
    mcp:
      client:
        type: SYNC
        stdio:
          connections:
            local-tools:
              command: java
              args: ["-jar", "/opt/mcp/order-server.jar"]
        sse:
          connections:
            remote-tools:
              url: http://order-mcp:8080
              sse-endpoint: /sse
```

```java
@Bean
ChatClient chatClient(ChatClient.Builder builder, ToolCallbackProvider mcpTools) {
    return builder.defaultTools(mcpTools).build();
}
```

stdio 由客户端拉起进程，JSON-RPC 走标准输入输出。SSE 先连 `/sse` 收服务端消息，再把请求 POST 到消息端点。同步和异步客户端不能混用。远程传输在新版本里还有 Streamable HTTP，配置键以你依赖的文档为准，但接进 `ChatClient` 的方式不变：仍然是 `ToolCallbackProvider`。

调用时客户端发 `tools/call`，结果作为工具消息回到模型。要单独设 `request-timeout`，不要指望模型那次 HTTP 超时顺便罩住工具。多个 Server 的工具名必须唯一，重名会在组装回调时失败或调错对象。

容易漏：远端工具和本地方法有同样的副作用。MCP 只统一了发现和调用，不提供幂等和鉴权，这两件仍要在 Server 和调用方做。

### 14. Agent Skills 在 AI Agent 体系中指什么，如何管理和复用 Skill

**参考答案**

Skill 是一份可复用的做事说明书，不是又一个工具函数。工具解决一次调用；Skill 写清什么时候用、按哪几步做、允许动哪些工具，以及做到什么程度停。现在常见的打包方式是一个目录：`SKILL.md` 里放名称、描述和步骤，旁边可以有参考资料和脚本。运行时先只把各 Skill 的短描述给路由，判断用得上再加载正文。这是渐进式披露，避免把所有流程塞进系统提示。

管理和复用按制品来，不按复制提示词来：

- 技能放在仓库或制品库，带版本和负责人。多个 Agent 引用同一个版本。
- 描述要写适用场景和禁用场景，路由只看描述。
- 技能声明可以调用的工具或 MCP Server，运行时做白名单。正文里说「再调用别的系统」不算授权。
- 每个技能配一小套问题。改步骤要重跑，通过了再发布；破坏性变更升版本。

容易漏：技能附带的脚本一旦能执行，就和写工具一样有副作用，要走同样的权限、审计和幂等。只把它当提示词管理，会漏掉这一层。

### 15. Redis 常用数据结构及你用 Redis 做过哪些场景（缓存 / 分布式锁 / 限流 / 向量检索）

**参考答案**

常用的是 String、Hash、List、Set、ZSet，再加上 Bitmap、HyperLogLog、Stream、Geo 和 Pub/Sub。缓存对象的多个字段用 Hash；要按时间排序或做滑动窗口用 ZSet；一组消费者可靠地分摊消息用 Stream，不要用 List 硬凑；Pub/Sub 不留消息，断线就丢。

缓存用旁路：先读 Redis，没有再读数据库并回填，TTL 加随机抖动。空值也要短缓存，挡住打到不存在的 key。数据以数据库为准，Redis 丢失只影响命中率。

分布式锁用 `SET key token NX PX ttl`。释放时用 Lua 比较 token 再删除，避免把别人刚拿到的锁删掉。锁有过期时间，业务还没做完锁就没了，所以库存、订单这种正确性要靠数据库唯一约束或条件更新，锁只是减少冲突。单主节点上的这把锁，比依赖多实例时钟的 Redlock 更好解释。

限流：固定窗口是 `INCR` 加过期，实现简单，窗口边界会突增。滑动窗口可以把时间戳放进 ZSet，先删窗口外的成员再计数。令牌桶一般放进一段 Lua，保证判断和扣减是原子的。

向量检索用 RediSearch 的向量字段，FLAT 适合小数据精确比，HNSW 适合更大规模的近似搜索。它适合热、中小规模的索引。维度高、数据量大时内存成本会很高，原始文档不要只放在一个开了淘汰的 Redis 里。

### 16. MySQL 事务 ACID 说一下，默认隔离级别是什么，会出现什么并发问题

**参考答案**

ACID 是事务的四条保证。原子性：未提交的修改可以经 undo 全部撤销。一致性：事务前后都满足约束和业务不变量；主键、外键数据库能守，跨表规则要写进事务里。隔离性：并发事务能看见什么，由隔离级别、MVCC 和锁一起决定。持久性：提交成功后宕机还在，InnoDB 靠 redo；`innodb_flush_log_at_trx_commit` 默认是 1，提交时刷日志，改成 0 或 2 会在崩溃时丢掉最近的提交。

InnoDB 默认隔离级别是可重复读（REPEATABLE READ）。脏读不会出现。普通 `SELECT` 在事务里第一次一致性读时建立 Read View，之后重复读同一快照，所以不可重复读和幻读在这种读法里基本看不见。`UPDATE`、`DELETE` 和 `SELECT ... FOR UPDATE` 是当前读，靠 Next-Key Lock（记录锁加间隙锁）挡住别的事务往间隙里插入。

因此不要背「RR 一定还有幻读」。InnoDB 的 RR 仍会有这些问题：两个事务都读出库存再分别写回，后写的覆盖先写的，这是丢更新，要用条件更新或 `FOR UPDATE`；两个事务各改各的行，联合起来破坏「至少有一人值班」这种约束，这是写偏斜；间隙锁还会带来死锁。这些要靠锁、唯一约束和业务条件，不是把隔离级别留在默认就结束。

### 1. 自我介绍

**答题思路**

### 2. 详细介绍你做的 AI Agent 或 RAG 项目，遇到了哪些难点怎么解决的

**答题思路**

按一次真实请求讲，再收成两三个你亲自处理的难点。没有 AI 项目就讲最熟的 Java 系统里「如果接上模型，哪一段会先坏」，不要编造成功上线的 Agent。

1. **场景**：谁用，系统只回答，还是会查、改、发消息。读写先说死。
2. **主路径**：鉴权、会话、检索或工具、生成、落日志。每一步点出状态存在哪。
3. **难点挑两个讲透**，从这些里选你真遇到过的：召回不到、模型编数字、工具超时后重复执行、多轮把指代理解错、上下文超长。每个都按「现象 → 原因 → 你改了哪层 → 怎么确认变好」讲。
4. **验证**：离线问题集、日志里的一类错误，或用户重复提问变少。只用自己能解释的数字。
5. **边界**：团队做的部分点明。最后说如果重做，哪一段会从提示词改成代码强制。

面试官在听你有没有把模型关进工程约束里。框架名一带而过。

### 3. Agentic RAG 和多轮普通 RAG 区别在哪，什么场景需要用 Agentic RAG

**参考答案**

多轮普通 RAG 的路径是固定的。每一轮把历史收成一个查询，检索一次，生成一次。拼上「上一轮说了什么」也仍然是这条管道，模型不决定要不要再搜、搜哪个库。

Agentic RAG 把检索变成工具。模型看到结果后可以判断不够、换一种问法、换一个知识库，或者改去调结构化接口，然后再生成。循环在服务端，有步数、费用和超时上限。

需要它的场景是一跳检索回答不了的问题：要先查到一个人，再查他所在部门的制度；问题要在多个库之间路由；第一次召回明显不相关，系统应该换查询而不是硬答。制度问答、FAQ、问法稳定的单跳问题不需要。固定管道更好评测，延迟和费用也稳定。

容易漏：多轮对话不等于 Agentic。还有，Agent 循环没有「证据不足就停」的判断时，只会多烧几次检索，答案不会更可靠。

### 4. 多 Agent 协作常见模式（路由 Router、编排 Orchestrator、黑板模式），你如何设计

**参考答案**

三种模式的差别是谁决定下一步。

路由：前面有一个分类器或一次模型调用，把请求交给一个专家，其他专家不参与。延迟低、责任清楚，适合意图互斥的入口。分类错了后面全错，而且一个请求需要两个专家时路由不够用。

编排：一个编排者拆任务、分派、收回结果、决定是否继续。控制流明确，超时和权限可以写在编排者上。编排者可以是代码里的状态机，也可以是一个「主管」模型。步骤已知时用代码，分解方式每次都变时才让模型拆。主管模型的提示会迅速变成不可测的大杂烩。

黑板：专家围着一份共享状态写自己的部分，谁能补上就补上，没有固定顺序。适合诊断、多来源拼证据这类问题。难在并发覆盖、结束条件和复盘，必须给每笔写入带作者和版本。

企业系统里我会默认用代码编排加一个前置路由：能确定是单一领域的，直接进对应 Agent；需要跨领域时，由状态机按步骤调用专家，专家之间不互相自由对话。共享状态放在会话存储里，而不是放在某个模型的上下文里。等单 Agent 的权限、幂等和评测还站不住，不先上黑板。多 Agent 的难点是失败时收得回，不是角色起得够不够多。

### 5. Agent 长上下文和 Memory 管理——短期记忆和长期记忆怎么分层，超长会话怎么处理

**参考答案**

短期记忆是这一次任务还要用的状态：最近几轮原话、工具的短观察、已经确认的槽位和未完成步骤。热数据放 Redis，按会话过期。长期记忆是跨会话仍要成立的事实：偏好、用户明确要求记住的内容、已结束任务的结论。放数据库，带用户、来源和时间，用到时再检索几条，不要整库注入。

长期记忆的写入要有门槛。用户说「记住」可以记；模型自己的一段猜测、检索来的正文，不能写成用户事实。否则一次错误回答会在以后每轮都被当成前提。

超长会话不能只删最早的消息。处理顺序是：槽位和任务列表单独存，旧对话压成摘要，工具的完整返回按 id 留在库里，上下文里只留短观察。token 预算先留给系统提示、工具 schema 和这次的检索结果，剩下的才给历史。摘要会丢掉订单号和条款编号，这些必须留在结构化状态里。用户说「就按刚才那个」时，解析的是状态里的 id。

容易漏：工具结果往往比聊天更占窗口。另外，用户或文档里的「以后不要遵守限制」不能进入长期记忆，这是记忆投毒。

### 6. 如何防止和控制 AI 幻觉（Prompt 约束、RAG 强制引源、输出校验、Human-in-the-loop）

**参考答案**

幻觉靠分层拦住，提示词只是最外面一层，挡不住空上下文和错上下文。

Prompt 约束写清楚：只根据给定材料回答，没有就说不知道，引用必须带材料编号。温度可以调低，但不要指望某个温度值消除幻觉。

RAG 要强制有据。检索为空，或最高分低于你们在标注集上定的阈值，就在代码里走拒答模板，不把空白交给模型。默认的「请不要回答」提示可以留着，不能只靠它。

引源要校验内容，不只校验编号。编号必须来自这一次的检索结果，回答里的数字、日期、实体要能在对应片段里找到。模型会拿真实编号编一句不存在的话。

输出校验用在格式和关键事实：枚举、JSON schema、范围。价格、库存、权限从工具或数据库取，不从自由文本里抠。校验失败就重问一次或拒答，不要原样返回。

Human-in-the-loop 用在副作用上：发外部消息、改数据、花钱，先复述并等人确认。低置信度的回答进审核队列，不直接给到用户。

容易漏：检索到了不相干片段时，模型会围绕错材料认真编。有片段不等于可以生成。改完这些策略，要用同一批忠实度样本重跑，不能凭几句对话感觉变好了。

### 7. Tool 调用幂等性怎么保证，LLM 同轮重复调同一 Tool 如何处理

**参考答案**

读工具可以重入。写工具的幂等键由服务端在执行前生成，模型只提议业务参数，不负责「只调用一次」。

用户确认一次写操作，就生成一个意图号，先落「执行中」记录，唯一键是这个号，然后再调用。超时只说明结果未知：先按号查询，查到就复用上次的结果，确认没有才用同一个号重试。换一个新号再调，才会重复下单或重复发消息。

同一轮里相同工具、相同参数又出现一次：运行时按工具名加规范化后的参数去重，把上一次的观察直接交回模型，不再执行。规范化要去掉空白、统一数字和字段顺序，否则模型换个空格就绕过去了。参数不同是合法的，例如查两个订单，不能当成重复删掉。

同一组参数连续出现，或者工具循环没有带来新信息，就停止并返回可控错误。Spring AI 的工具管理器可以按工具、按一轮总次数封顶；写操作不要依赖框架宽松的默认上限，自己收到几次以内。

容易漏：幂等键如果让模型自己填，它每轮都会换，去重失效。键要来自用户确认动作或服务端状态，而不是来自模型自由发挥。

### 8. MCP Server 在 Java 中怎么暴露业务能力（注解、Transport 类型 SSE / stdio）

**参考答案**

业务方法仍是普通 Java 方法。一种写法是方法标 `@Tool`，再提供 `ToolCallbackProvider` bean，MCP Server starter 会把它注册成工具。较新版本可以直接在 Spring bean 上标 `@McpTool`，由自动配置扫描。参数说明用 `@ToolParam` 或 `@McpToolParam`，生成的 JSON Schema 就是客户端看到的入参。

```java
@Service
public class OrderService {
    @Tool(description = "按订单号查询状态")
    public OrderView getOrder(@ToolParam(description = "订单号") String orderId) {
        return repository.find(orderId);
    }
}

@Bean
ToolCallbackProvider orderTools(OrderService orderService) {
    return MethodToolCallbackProvider.builder().toolObjects(orderService).build();
}
```

stdio 用 `spring-ai-starter-mcp-server`，打开 `spring.ai.mcp.server.stdio=true`。进程的标准输入输出就是协议，日志和启动 banner 必须离开 stdout，否则客户端解析 JSON-RPC 会失败。它适合被本机 Host 拉起，不监听端口。

SSE 用 WebMVC 或 WebFlux 的 server starter。服务端在 SSE 连接上推消息，客户端把 JSON-RPC POST 到消息端点，文档里的示例端点是 `/mcp/messages`，可以改。2.0 起 SSE 被标为过时，新的远程传输是 Streamable HTTP：同一个 HTTP 端点接收 POST，需要回多条消息时再用 SSE。面试里两种都要讲清，新系统优先 Streamable HTTP。

HTTP 传输默认没有鉴权，谁能访问端点谁就能列出并调用全部工具。放到局域网以外之前要加认证和授权。stdio 没有这个问题，因为它不进网络。资源、提示和工具是三种能力，只想暴露查询就不要把写操作注册上去。

### 9. Spring AI 的流式输出（SSE / Flux）怎么实现，前端怎么消费

**参考答案**

模型侧用 `ChatClient` 的 `stream()`，`content()` 得到逐段文本的 `Flux<String>`，需要结束原因和 token 用量时用 `chatResponse()`。HTTP 侧把这个 `Flux` 以 `text/event-stream` 返回，Spring 按 SSE 帧写出。

```java
@PostMapping(path = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> chat(@RequestBody ChatRequest request) {
    return chatClient.prompt().user(request.message()).stream().content();
}
```

反向代理默认会缓冲响应。Nginx 要关 `proxy_buffering`，响应带上 `X-Accel-Buffering: no`，否则前端还是等全部生成完才看到字。服务端和网关的超时要大于一次生成的墙钟时间，只设连接超时不够。

前端聊天一般是 POST，还要带登录头，不能用只能 GET 的 `EventSource`。`EventSource` 还会自动重连，等于把同一次生成再打一遍。用 `fetch` 读 `response.body`，按空行切 SSE 帧，再取 `data:` 行。不要按网络包当 token，一个包可能是半帧。

带工具的流式要分开处理：工具参数在服务端拼完整再执行，工具调用的 JSON 不能当成答案推到屏幕上。客户端断开时取消上游模型订阅，避免人走了还在计费。已经推出去的半截回复标成未完成，重试时不要再接一段新的在后面。

### 10. ES（Elasticsearch）倒排索引原理，在 RAG 或知识库检索中有没有用过多路召回

**参考答案**

倒排索引按词找文档。文本先经分词器变成词项，每个词项对应一条倒排表，记下文档 id、词频和位置。查询时取出这些倒排表，再用 BM25 打分，分数取决于词频、这个词有多稀有，以及字段有多长。所以错误码、型号、专有名词这类精确说法，关键词检索很稳。向量检索擅长「说法不同但意思接近」，也容易把这些精确词抹平。

中文要在索引和查询使用同一套分词。IK 里用 `ik_max_word` 建索引、`ik_smart` 做查询是常见搭配，但两路召回看到的文本要一致，否则关键词命中的片段和向量命中的片段对不齐。

知识库里的多路召回通常是：元数据先过滤租户和版本，BM25 一路，向量一路，再按名次做 RRF，最后用重排模型把几十条收到三五条。BM25 分和余弦分尺度不同，不能加权硬加。Elasticsearch 可以在同一个索引里做 `dense_vector` 和 BM25，省一个组件；向量规模很大时，向量仍可以放到 Milvus，ES 只留关键词这一路。

第二路不是免费的。口语化、没有精确词的小语料，向量一路就够。值得加 BM25 的信号是评测集里那些带编号、人名、条款号的问题，单路向量的 Recall@K 明显更差。没有这个差距就不要为了「多路」多维护一路索引。

### 11. Kafka 在 Agent 系统中可以用来做什么（异步 Tool 执行、审计日志、事件驱动）

**参考答案**

Kafka 适合已经离开用户这一次 HTTP 连接的事情。三个用途都能成立，但都要接受至少一次投递。

异步工具：模型决定调用一个慢工具后，服务端把命令写进主题并挂起这一轮，Worker 执行完再把结果写回。会话状态要落库，不能停在等待的线程上。消息带上会话 id、工具调用 id 和幂等键，结果回来按调用 id 对上。用户还在线等的短工具不要绕 Kafka，多一跳只增加尾延迟。

审计日志：提示版本、检索到的文档 id、工具名、参数摘要、是否人工确认，按发生顺序追加。这是合规回放，不是调试日志。正文过大时主题里放对象存储的指针。隐私字段要有保留期限，不能把原始对话无限期堆在日志里。

事件驱动：文档入库后的解析、切分、嵌入，以及用户反馈、人工审核结果，都可以做成事件，让索引和评测各自消费。一个会话内需要顺序时，用 sessionId 做消息键，顺序只在分区内有效。

消费者必须幂等。重复投递一次写工具，如果没有第 7 题的意图号，就会重复执行。主题堆积时要有积压告警，否则异步工具会静默地越来越慢。

### 12. 遇到 LLM 接口超时或限流，系统怎么降级和兜底

**参考答案**

超时和 429 都不要立刻用同一请求打满，更不要在失败时编一段看起来完整的答案。

超时拆成连接、首 token、流式空闲和整次截止。只有还没产生副作用、也还没拿到有效结果的生成请求才重试。已经推到前端的半截答案，不能再默默接一段。429 要看 `Retry-After`，指数退避加抖动，次数封顶。网关用信号量限制在途调用，一个租户打满不能占掉全部许可。错误率持续高就熔断，直接走兜底，不要每次都等满超时。

降级按能力往下走：先换备用模型，它的上下文和工具集可能更小，提示要能减负；问题允许陈旧答案时再查缓存；再退回关键词检索或固定说明；最后明确告诉用户服务繁忙。工具已经执行成功、只是总结这一步超时，就复用工具结果重新总结，不要把写工具再跑一遍。

容易漏：备用模型的窗口更短，原样送原提示会直接失败。还有，语义缓存可能把别的租户或旧版本制度答给当前用户，缓存键里要有租户和知识库版本。

### 13. 你们怎么做 AI 应用的可观测性（Trace / Metrics / 日志），Spring AI 有没有 Obs 支持

**参考答案**

一次用户请求一条 Trace。子 Span 至少包括检索、每一次模型调用和每一次工具调用，带上文档 id、模型名、finish reason、工具名和业务错误码。MCP、Kafka 出进程时把 W3C `traceparent` 带上，否则链在边界处断开。

Metrics 看流量、错误率、延迟、首 token 时间、输入输出 token、工具成功率和空检索比例，再加 Agent 的步数。标签用模型、路由、租户这一级就够，不要把问题原文做成标签，基数会爆。

日志和 Trace 用同一个 traceId。决策信息（选了哪个工具、为什么拒答）打在 info。完整提示词只在调试采样里出现，并且脱敏。审计日志单独留，不和调试日志混在一个保留策略里。

Spring AI 有这层支持。它用 Micrometer Observation 给 `ChatClient`、Advisor、`ChatModel`、`EmbeddingModel`、`VectorStore` 记指标和链路，工具执行也有对应观测点。接上 Actuator 和 `micrometer-tracing-bridge-otel` 就能导出到 OpenTelemetry。模型调用上能看到 `gen_ai.client.operation` 和 token 用量，向量库操作在 `db.vector.client.operation`。框架不会替你统计「答案是否忠实」，空检索率、人工接手率、用户重问率要自己打点。

容易漏：只采集到了模型耗时，没有检索分数和工具错误码。线上回答变差时，就分不清是召回空了还是模型编了。

### 14. 最近学了什么新技术或框架，怎么学的，举一个你主动研究并落地的小例子

**答题思路**

选一个你真写过代码的东西，最好和这个岗位相关，例如 MCP、混合检索或流式工具调用。没落地过就讲你做过的最小切片，不要编一个已经上生产的平台。按这个顺序讲，两分钟：

1. **为什么学**：工作里哪类问题把它逼出来的，例如工具每次都要改 Agent 代码，或关键词检索总漏编号。
2. **怎么学**：先看官方文档和一两个最小示例，再对着源码或调试日志确认调用顺序。不要背一串博客标题。
3. **小例子**：输入是什么，你改了哪一个模块，怎样算跑通。例如接了一个本地 MCP Server，只暴露一个查询工具，并把超时和工具名冲突处理掉。
4. **还没做什么**：主动说边界，例如还没有鉴权、没有评测集。面试官接着问时，你不会被自己的完整度绊住。

学习过程比名词重要。讲得出你踩过的一个错误配置，比再报一个框架名有用。

### 15. 如果让你从零设计一个企业级 AI Agent 平台，你会怎么划分模块和技术选型，说下理由

**参考答案**

先做一条能上线的单 Agent 运行时。模型、工具、知识库都走平台网关，业务方注册工具和技能，不各自写一套循环。多 Agent 等权限和评测站得住再加。

模块按边界拆：

1. 接入层负责登录、租户、限流和 SSE。人和 Agent 的身份分开。
2. 运行时负责会话、提示词组装、工具循环、步数、超时和取消。这是平台核心。
3. 模型网关负责多供应商、重试、降级和 token 记账。业务代码禁止直连厂商，否则成本和切换都做不到。
4. 工具平面同时接进程内工具和 MCP。注册表写清 schema、负责人、风险级别和是否写操作。写操作必须有幂等键。
5. 知识库负责解析、切分、向量加关键词，检索时按租户过滤。原文放对象存储。
6. 记忆把热会话放 Redis，跨会话事实放数据库并带来源，不把每句话都写成长期记忆。
7. 安全层对高风险工具做人审，空检索直接拒答。
8. 观测和评测把检索、模型、工具串成一条 Trace。提示词和技能有版本，离线集不过不能发布。

Java 团队用 Spring Boot 和 Spring AI 做运行时。PostgreSQL 存会话元数据和审计，语料中等用 PgVector，检索变成独立大服务再拆 Milvus。Redis 放热状态、锁和限流。关键词这一路用 Elasticsearch。入库、异步工具和审计走 Kafka。

难点不在模型接口，而在写工具的权限和幂等、检索的租户隔离，以及没有评测集就改提示词。长流程要断点续跑时再引入工作流引擎，不在第一天把平台做成一张谁都能改的大图。

## HR面

### 1. 简单自我介绍

**答题思路**

HR 这一轮用 1 分钟，少讲框架，多讲你是谁、最近在做什么、为什么坐在这里：

1. 姓名、年限、现在的方向：Java 后端，最近在做 AI 应用落地。
2. 用一句大白话讲项目：帮谁把哪类事从人工变成可查询或可办理，你在里面负责什么。
3. 补一个协作信息：和产品、算法或业务怎么配合。不展开技术细节。
4. 收在这次机会：想把 Agent 做到真实业务系统里。

对方若是非技术面试官，被追问再展开。不要背一面的项目架构。

### 2. 为什么想来富士康 / 选择我们这个岗位

**答题思路**

把「为什么是这个行业」和「为什么是这个岗位」分开，各一两句，都落到你的真实经历上，不要空说平台大。

1. **行业**：富士康的系统贴着制造和供应链。Agent 如果只停留在通用聊天，价值有限；接上已有的 Java 业务系统，才有查询、办理和审计。你想做的是这种落地，而不是再做一个演示机器人。
2. **岗位**：岗位要的是 Java 工程加上 RAG、工具调用。对应你已经做过的一段，点明即可，不编造没做过的工业项目。
3. **你要的**：可以说想把模型放进权限、超时和失败都收得住的生产链路。具体团队业务以你调研到的为准，不确定就不要讲内部产品名字。

避免只谈城市、标题或「贵司是大厂」。也避免贬低现在的公司来衬托。

### 3. 你对 AI Agent 方向怎么看，自己有什么职业规划

**答题思路**

观点先说判断，规划再说你准备怎么长，不说空的「成为专家」。

1. **看法**：Agent 有用的部分是接上真实工具和数据，难点在幻觉、权限、幂等和评测，不在角色起名。会调用模型的人会变多，能把模型嵌进业务系统并守住失败的人仍然少。这个判断用你自己的项目体会支撑一句。
2. **近一年**：把一条链路做扎实，例如检索质量、工具治理或可观测性里的一块，能量化就讲你的衡量方式。
3. **再往后**：从单点功能走到平台能力，能定工具和发布的规范。带人如果不是你的真实意愿，就不要主动许诺管理岗。
4. **和公司的关系**：希望规划长在工业场景的系统里，而不是每半年换一个概念。

不编职级年限和薪资目标，那些留给薪资那一题。

### 4. 你期望的工作氛围和团队风格是怎样的

**答题思路**

说你能配合的协作方式，并带一个你实际喜欢这样工作的原因。挑三件真正在意的：

1. 需求有书面的验收标准，变更时改的是范围和时间，不是口头加任务。
2. 技术分歧看复现和数据，设计文档可以不同意，但决定了就按决定执行。
3. 线上问题有人负责到底，复盘对事。你也说清自己会怎么做：主动同步风险，不把问题留到上线当天。

不要把答案说成「扁平、开放、有挑战」这种放在哪家都对的话。也不要当面规定加班、远程或管理风格，除非对方先问约束；那些可以作为反问，不作为要求抛出去。

### 5. 如果遇到需求频繁变更或有分歧，你怎么处理，举个例子

**答题思路**

用一件真实的事，按「背景 → 分歧 → 你做了什么 → 结果」讲。公司名、金额、别人的原话不要编。记不清细节就讲行为，不要补戏。

1. **背景**：一句话说明业务目标，例如上线日期已经定了，中间又加了一种问法或一个操作。
2. **分歧是什么**：先分清是目标变了，还是做法不同。目标变了就重排范围；做法不同就比较风险和工时，不争谁对。
3. **你怎么处理**：把新需求写成可验收的一条，标出它影响的接口、数据和上线日。能拆到下一期的，说明白推迟的代价，让产品或业务选，而不是你私下做完。
4. **结果**：一期交了什么，推迟了什么。如果当时处理得不好，补一句后来改了什么，例如改成变更必须带验收例子。

重点是你让变更变得可见。强调「我都能接受」或「我坚决不做」都太满。

### 6. 你目前薪资范围和期望是多少

**答题思路**

用真实数字，给出区间和构成，不报一个没算过的整数。

1. 现在的包按同样口径说：月薪、年终、补贴，说明哪些是固定的。不报虚高的总包。
2. 期望给一个区间，下限是你能接受的，上限是同级别市场里你有依据的位置。依据来自你了解的同类岗位，不说来源八卦。
3. 先把区间给完整，再问对方的带宽和结构，例如固定和浮动怎么分、试用期是否不同。
4. 对方追问底线时，重复你的可接受区间，不在现场层层后退。还没了解业务强度时，可以说需要结合职责再定，但不能拒绝给出范围。

不把股票、加班费和口头承诺算进已经到手的收入。

### 7. 还有什么想问我们的

**答题思路**

准备三个以内，按「岗位怎么算做成 → 团队怎么协作 → 你进来先碰到什么」问。薪资上一题已经谈过，这里不重复。

1. 这个 Agent 岗位前半年，怎样算做得好：是接上一条业务链路，还是先把平台能力补齐。
2. 模型和工具现在是业务系统自己调，还是已经有统一网关、评测和发布流程。
3. 需求从哪来，变更通常谁拍板；上线后的问题和值班怎么分工。

根据对方的回答接一句你的理解再结束，不要连珠炮。不在 HR 这里追问机密架构，也不用「没有问题」收尾。
