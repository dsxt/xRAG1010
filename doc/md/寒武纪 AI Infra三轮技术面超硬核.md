### 2. 讲一个你做过的 AI Infra / 模型部署 / 训练平台项目，别讲业务，讲系统边界和瓶颈在哪

**答题思路**

面试官要的是系统视角，不是业务故事。建议按以下顺序组织：

1. **一句话定位**：这个系统服务谁、规模多大（卡数、模型规模、QPS 或任务量）。
2. **系统边界**：画出分层：接入层 → 调度层 → 运行时或引擎 → 框架 → 驱动与硬件，说明哪些是你负责的，哪些是依赖的。
3. **瓶颈在哪**：用数据说话，先说怎么发现的（profiler、指标、trace），再说瓶颈属于哪类：算力、显存、访存带宽、通信、数据加载、调度排队或 CPU 开销。
4. **你的方案和取舍**：为什么选这个方案，放弃了什么，改完前后指标变化。
5. **遗留问题和复盘**：还有什么没解决，下次会怎么做。

不要编造数字，没有把握的指标宁可讲趋势和方法。

### 3. PyTorch 模型从 CUDA 迁到寒武纪 MLU，大致要走哪些步骤，哪些地方最容易翻车

**参考答案**

结论：迁移的主线是"环境对齐 → 设备切换 → 跑通 → 对精度 → 调性能"，最容易翻车的是算子覆盖、精度差异和 CUDA 专属依赖。

步骤：

1. **环境**：安装与 PyTorch 版本匹配的 `torch_mlu`、驱动和 Neuware 工具链，版本必须配套。
2. **设备切换**：把写死的 `cuda` 字符串、`.cuda()`、`torch.cuda.*` 改成设备无关写法（`torch.device("mlu")`）；AMP、随机种子、显存统计也要换成 MLU 对应接口。
3. **分布式**：通信后端从 `nccl` 换成 `cncl`。
4. **跑通**：先单卡小 batch 跑前向，再反向，再多卡。
5. **精度对齐**：固定种子和输入，逐层对比输出，再对比 loss 曲线。
6. **性能调优**：profiler 找热点，处理 CPU 回退、融合、布局、通信重叠。

易翻车点：

- 自定义 CUDA 算子、Triton kernel 以及 `flash-attn`、`apex`、`bitsandbytes` 等 CUDA 专属第三方库，需要找替代实现或用 BANG C 重写。
- 不支持的算子悄悄回退到 CPU，功能正确但性能崩掉。
- fp16 / bf16 / int 类型支持度和累加顺序不同，导致数值漂移。
- CUDA Graph、pinned memory、stream 语义假设不成立。
- 动态 shape 触发重复编译或性能下降。

### 4. 寒武纪 NeuWare 里 CNNL、CNRT、CNCL、MagicMind、BANG C 各自干什么，别背定义，说清楚调用链

**参考答案**

结论：它们大致对应 CUDA 生态里的 cuDNN/cuBLAS、CUDA Runtime、NCCL、TensorRT 和 CUDA C，分属"算子库、运行时、通信、推理引擎、算子开发语言"五层。

调用链：

- **训练或推理框架**（`torch_mlu` 等）把模型里的算子映射到 **CNNL**（神经网络算子库，提供卷积、矩阵乘、归一化等高性能算子）。
- CNNL 以及用户自定义 kernel 的启动、显存申请、队列（类似 stream）、同步、事件，都通过 **CNRT**（运行时）下发到驱动和 MLU 设备。
- **BANG C** 是写 MLU kernel 的编程语言，用寒武纪编译器编译后，同样经由 CNRT 启动；CNNL 里没有的算子才需要自己写。
- **CNCL** 是集合通信库（AllReduce、AllGather、AllToAll 等），框架分布式后端调用它，底层走 MLU-Link、PCIe 或网络。
- **MagicMind** 是推理引擎：解析模型（ONNX 等）、做图优化和代码生成，产出可序列化的引擎，运行时调用 CNNL、生成的 kernel 和 CNRT 执行。

一句话总结：训练走"框架 → CNNL → CNRT"，多卡加 CNCL，推理走"MagicMind 引擎 → CNRT"，缺算子时用 BANG C 补。

### 5. MagicMind 做推理部署时，模型解析、图优化、后端代码生成这一步到底在干啥

**参考答案**

结论：这一步就是把"通用的模型描述"编译成"针对某型号 MLU 的最优可执行引擎"，思路与 TensorRT 的 build 阶段类似。

- **模型解析**：把 ONNX、PyTorch 等模型转成内部 IR，得到算子、张量形状、数据类型和连接关系。
- **图优化**：常量折叠、消除冗余算子、算子融合（如 Conv + BN + Act、Attention 内部的小算子）、布局转换、精度选择与量化节点插入，目标是减少访存和 kernel 启动次数。
- **后端代码生成**：为每个算子或融合子图选择 CNNL 实现，或生成针对该硬件的 kernel；同时做显存规划（张量生命周期复用）和调度，最终序列化成引擎文件。

要点：

- build 耗时较长，应离线完成，线上只加载引擎。
- 引擎与硬件型号、软件版本、输入 shape 范围绑定，动态 shape 要在构建时给出范围，换环境要重建。
- 精度和性能问题常出在优化阶段，排查时可对比关闭某些优化或逐层输出。

### 6. 推理服务里 KV Cache 为什么是大头，PagedAttention / 连续 batching 解决了什么问题

**参考答案**

结论：KV Cache 随"并发请求数 × 序列长度"线性增长，往往超过权重之外的所有显存占用；PagedAttention 解决显存碎片和浪费，连续 batching 解决 GPU 空转和长尾等待。

- **为什么是大头**：每个 token 要为每一层保存 K 和 V，大小约为 `2 × 层数 × KV 头数 × head_dim × 字节数`。序列越长、并发越高，占用越大；decode 阶段每步都要读取全部历史 KV，也是访存瓶颈。
- **PagedAttention**：借鉴操作系统分页，把 KV Cache 切成固定大小的块，用块表映射逻辑位置到物理块。避免按最大长度预留造成的内部碎片和外部碎片，显存利用率大幅提升；还能让相同前缀的请求共享块（写时复制），支持 prefix cache 和并行采样。
- **连续 batching**（iteration-level 调度）：每生成一个 token 就重新调度，完成的请求立刻退出、新请求立刻加入，不用等整个 batch 最慢的请求，吞吐显著高于静态 batching。

容易漏的点：两者配合才能发挥作用，连续 batching 让请求动态进出，需要分页式 KV 管理来支撑；显存不足时还要有抢占、换出或重算策略。

### 7. INT8 量化里校准集怎么选，激活和权重分别量化有啥区别，Attention 相关层为什么不能无脑量化

**参考答案**

结论：校准集要代表线上分布；权重静态、易量化，激活动态、有离群值、更难；Attention 相关层对精度敏感，应做敏感度分析后混合精度。

- **校准集**：选真实业务分布的样本，通常几百到几千条，覆盖不同长度、类别和场景，不能用训练集里过于单一的数据，也不要包含异常样本。再配合 min-max、百分位截断、KL 散度或 MSE 等方法选量化范围，最后以验证集指标为准。
- **权重 vs 激活**：权重在部署时固定，范围已知，通常按通道（per-channel）量化，误差小；激活取决于输入，范围需要校准（静态量化）或运行时统计（动态量化），常用按张量或按 token 量化，且大模型激活存在少数通道的极端离群值，直接量化会损失精度（SmoothQuant 等方法通过把难度迁移到权重缓解）。
- **Attention 为什么敏感**：softmax 输出分布极不均匀，小概率值被截断会影响注意力分配；`QK^T` 的数值范围大，对误差放大明显；KV Cache 的误差会随生成长度累积。常见做法是 softmax、归一化层保持高精度，首尾层或敏感层跳过量化，KV Cache 的量化单独评估。

### 8. MLU 和 GPU 在推理部署上的差异，除了换设备名，还有哪些底层适配点

**参考答案**

结论：差异集中在软件栈、算子与精度支持、编译与 shape 处理、显存与互联、工具链五个方面。

- **软件栈**：驱动、运行时、算子库、推理引擎分别是 Neuware、CNRT、CNNL、MagicMind，不是 CUDA、cuDNN、TensorRT。
- **算子与数据类型**：支持的算子集合、融合能力、fp16 / bf16 / int8 / int4 的支持程度和累加精度不同，需要建立算子覆盖清单。
- **编译与 shape**：MagicMind 需要预先构建引擎，动态 shape 需要给定范围，换 shape 可能重新编译；与 TensorRT 的 profile 类似，但行为细节不同。
- **自定义算子与高性能库**：FlashAttention、vLLM 等需要有 MLU 适配版本，缺失的要用 BANG C 实现；BANG C 的存储层次（GDRAM、SRAM、NRAM、WRAM）和任务划分与 CUDA 的 shared memory、warp 模型不同，不能直接翻译。
- **显存与互联**：容量、带宽、MLU-Link 与 PCIe 拓扑影响并行策略和 KV Cache 规划。
- **工具链**：监控用 `cnmon`，性能分析用寒武纪自己的 profiler，而不是 `nvidia-smi` 和 Nsight。

建议建立"迁移验收清单"：功能、精度、性能、稳定性、长稳压测各自的通过标准。

### 9. 一个模型在 A100 上跑得动，迁到寒武纪后跑不动或性能不达标，怎么排查

**参考答案**

结论：先分清是"跑不起来"、"结果不对"还是"跑得慢"，再按层定位，不要一上来就调优。

1. **跑不起来**：
   - 看报错：算子不支持、数据类型不支持、shape 越界、显存 OOM、驱动或版本不匹配。
   - OOM 要看权重、激活、KV Cache 各占多少，MLU 显存容量与 A100 不同，需重新做显存预算：量化、降 batch、并行切分。
2. **结果不对**：固定输入，逐层比对与 GPU 的输出，找到第一个误差明显偏大的层；区分是 dtype 精度问题、算子实现差异还是预处理不一致。
3. **跑得慢**：
   - 用 profiler 看热点，确认是否有算子回退 CPU、频繁 host-device 拷贝、同步点过多。
   - 看是否利用了图优化和融合（MagicMind 构建）。
   - 看 batch、数据布局、动态 shape 是否触发重编译。
   - 看单卡算力和访存是否已逼近上限，再决定是否要改并行方式。
4. **兜底**：个别算子拆图绕路、用 BANG C 自定义，或反馈给官方；仍达不到目标要与业务沟通降低预期或更换方案。

### 10. 算子不支持时，你是等官方、写 BANG C 自定义算子、还是拆图绕路，怎么决策

**参考答案**

结论：按"影响范围、紧急程度、实现成本、长期维护"做决策，通常顺序是：先看能否用已有算子组合或拆图绕路，其次是向官方提需求，热点算子且性能关键时才自研。

决策因子：

- **是否在关键路径**：算子在热点路径，回退 CPU 或组合实现会严重拖慢性能，则值得自研；偶尔调用的预处理、后处理算子可以放到 CPU 或用已有算子组合。
- **能否等待**：问官方的修复周期，如果业务上线节点早于排期，就先用临时方案，同时提需求。
- **实现成本与风险**：用现有算子组合实现最便宜，但可能多次访存；BANG C 能得到最好性能，但需要熟悉存储层次、切分和精度处理，还要做正确性和性能测试。
- **长期维护**：自研算子要跟着版本升级维护；官方后续支持后要能无缝切换，所以接口要封装在一层，便于替换。

流程：确认确实缺失（版本、参数、dtype 条件）→ 评估绕路方案 → 评估热点程度 → 决定自研或等待 → 做精度和性能验证并写回归测试。

### 11. Redis 在推理平台里能用在哪，模型元数据、路由、限流、缓存结果分别适不适合放进去

**参考答案**

结论：Redis 适合做热点读缓存、限流计数和临时状态，不适合作为模型元数据的唯一真相来源，也不适合缓存大块张量。

- **模型元数据**：适合当缓存。权威数据放在 MySQL 或 etcd 等有持久化和事务保证的存储中，Redis 做加速，更新时要处理缓存一致性（删除或过期，加上版本号）。
- **路由**：热点路由表、实例列表可以放，读多写少；但强一致的服务发现与选主更适合 etcd 或注册中心，因为 Redis 主从复制是异步的，故障切换时可能丢写。
- **限流**：很适合。固定窗口用 `INCR` + `EXPIRE`，滑动窗口用有序集合，令牌桶用 Lua 脚本保证原子性。集群下注意 key 要落在同一个槽。按租户限制 token 数比限制请求数更合理。
- **缓存结果**：只适合确定性场景：温度为 0 或固定种子，key 要包含模型版本、提示词哈希和全部采样参数，设置 TTL；还要注意用户隔离和敏感数据。语义缓存可以另做，但要有相似度阈值和误命中的评估。

不适合放：KV Cache 张量、大文件（大 value 会阻塞单线程命令处理）、需要强事务的计费数据。

### 12. Kafka 在训练数据流水线里适合干什么，不适合干什么

**参考答案**

结论：Kafka 适合做"持续产生的数据流的缓冲、解耦和分发"，不适合做"需要随机访问和多轮重复读取的训练样本存储"。

适合：

- 线上日志、用户反馈、埋点等增量数据的收集，生产者和消费者解耦，削峰填谷。
- 多个下游（清洗、标注、特征、统计）并行消费同一数据流，靠消费组和 offset 独立推进。
- 顺序写入、高吞吐，支持按 offset 回放，适合在线或增量学习的数据链路。

不适合：

- **随机读和全局 shuffle**：Kafka 按分区顺序读，训练要的全局打乱需要另外落地。
- **多 epoch 重复读取**：需要很长的保留期，成本和管理都不划算。
- **大对象**：图片、视频、长序列样本受消息大小限制（默认约 1MB），应把数据存在对象存储，消息里只传元数据和路径。
- **精确的断点续训语义**：需要自己保证 offset 和训练 step 对齐，Exactly-once 实现较复杂。

通常做法：Kafka 负责实时汇集，清洗后落到对象存储或分布式文件系统（Parquet、WebDataset 等），训练从中读取。

### 13. Linux 上怎么看 MLU 卡占用、显存、PCIe 带宽、进程卡死，不用 nvidia-smi 你用什么

**参考答案**

结论：用寒武纪的 `cnmon` 作为 `nvidia-smi` 的对应工具，配合系统工具和 profiler。具体子命令和输出字段以所用版本的文档为准。

- **占用与显存**：`cnmon` 可以看到各卡的利用率、显存使用、温度、功耗和占用进程，加上 `watch` 或者采集到 Prometheus 做长期监控。
- **PCIe 链路**：`lspci -vv` 的 `LnkSta` 看协商后的速率和位宽，确认没有降速（比如 x16 变成 x8）；带宽实测用厂商带宽测试工具或写简单的 host-device 拷贝压测；`dmesg` 里留意 AER 等 PCIe 错误。
- **互联与多卡**：用厂商的拓扑查询工具确认 MLU-Link 连接关系，通信性能用 CNCL 的测试程序评估。
- **进程卡死**：
  1. `ps` 看进程状态，D 状态通常表示卡在驱动或 IO。
  2. `lsof` 或 `fuser` 查看谁占着设备节点。
  3. Python 进程用 `py-spy dump` 看调用栈，原生栈用 `gdb -p` 或 `strace`。
  4. 看 `dmesg` 和驱动日志有无硬件或驱动报错。
  5. 多卡训练的 hang 要结合各 rank 的栈判断是否卡在某个集合通信上。
  6. 无法恢复时才 kill，必要时按厂商建议重置设备。

### 14. AI 推理服务突然 p99 延迟飙高，但 CPU、显存、网卡都没满，你怎么定位

**参考答案**

结论：资源没满不代表没瓶颈，要把一次请求的耗时拆成"排队、预处理、prefill、decode、网络"各段，找到变长的那一段，再找原因。

1. **确认范围**：是所有请求还是特定模型、租户、长度？什么时间点开始？同时有没有发布、扩缩容、流量变化或定时任务。
2. **分段看耗时**：排队时间、首 token 延迟（TTFT）、每 token 间隔（TPOT）、网络时间分别对比基线。
3. **按段排查**：
   - **排队变长**：batch 组成变了（长请求挤占、prefill 阻塞 decode），可看 chunked prefill 配置、max batch 限制。
   - **KV Cache 压力**：块池耗尽导致请求被抢占、换出或重算，会造成长尾。
   - **设备侧**：降频（温度、功耗限制）、ECC 或链路错误、驱动日志；看卡的实际频率和利用率曲线。
   - **动态 shape**：出现新 shape 触发引擎重编译或缓存未命中。
   - **主机侧**：Python GIL 和 GC、分词、日志、锁竞争、NUMA 跨节点访问、CPU 被限流（cgroup throttle，总体使用率不高也会发生）。
   - **同步点和拷贝**：频繁 host-device 同步、小包拷贝。
   - **上游或下游**：负载均衡不均、重试风暴、下游依赖变慢。
4. **工具**：分布式 trace、各阶段直方图、profiler 时间线，对比"正常实例和异常实例"。

要点：不要只看平均值或资源使用率，一定要看分位数和队列长度。

### 15. 手撕算法：给定一个浮点 tensor 和 scale / zero_point，实现 INT8 对称量化的 encode 和 dequantize 伪代码，并处理越界截断

**参考答案**

思路：对称量化时 `zero_point = 0`，量化为 `q = clamp(round(x / scale), qmin, qmax)`，反量化为 `x' = q * scale`。越界值要截断到 INT8 范围；对称量化常用范围是 `[-127, 127]`，使正负对称（也可以用 `[-128, 127]`）。非对称量化则是 `q = clamp(round(x / scale) + zp, qmin, qmax)`，`x' = (q - zp) * scale`。时间复杂度 O(n)，空间 O(n)（输出）。

```python
import numpy as np

QMIN, QMAX = -127, 127  # 对称量化常用范围


def quantize(x: np.ndarray, scale: float, zero_point: int = 0) -> np.ndarray:
    """float -> int8，zero_point=0 即对称量化。"""
    assert scale > 0
    # np.rint 为四舍五入到最近偶数，与多数硬件实现一致
    q = np.rint(x / scale) + zero_point
    q = np.clip(q, QMIN, QMAX)  # 越界截断
    return q.astype(np.int8)


def dequantize(q: np.ndarray, scale: float, zero_point: int = 0) -> np.ndarray:
    # 先转 int32/float 再减，避免 int8 溢出
    return (q.astype(np.float32) - zero_point) * scale


def calc_symmetric_scale(x: np.ndarray) -> float:
    max_abs = float(np.max(np.abs(x)))
    return max_abs / QMAX if max_abs > 0 else 1.0
```

容易漏的点：

- 对称量化 `zero_point` 必须是 0，激活有明显偏移时才用非对称。
- 先 clip 再转 int8；直接转型会发生回绕。
- 反量化前要先转宽类型再减去零点。
- 量化后误差上限约为 `scale / 2`（未截断部分），被截断的值误差更大，因此 scale 的选取（min-max、百分位、KL）很关键。

### 2. 讲你做过最复杂的一个训推系统，训练侧和推理侧分别踩过什么坑

- **推理侧**：训练到部署的精度不一致、量化掉点、动态 shape 性能、KV Cache 显存规划、长尾延迟、模型热更新、算子缺失。

### 3. 数据并行、张量并行、流水线并行在寒武纪 MLU-Link / PCIe 拓扑下怎么选

**参考答案**

结论：通信越频繁、数据量越大的并行方式，越要放在带宽高的链路内。通常是张量并行放在卡间高速互联域（MLU-Link）内，流水线并行跨节点，数据并行放最外层。

- **张量并行（TP）**：每层前向、反向都有集合通信，频率最高，对带宽和延迟最敏感，应限制在 MLU-Link 互联的卡之间，通常不超过一个互联域大小。
- **流水线并行（PP）**：只在相邻 stage 之间传激活，通信量较小，适合跨节点；代价是流水线气泡，用 micro-batch 和交错调度减少。
- **数据并行（DP）**：每步梯度同步，用分桶和计算通信重叠隐藏；配合 ZeRO 可以节省显存。

决策顺序：

1. 模型单卡放得下：纯 DP（或 DP + ZeRO）。
2. 放不下：先 TP 到单个互联域，再用 PP 跨节点，剩余规模用 DP。
3. 如果只有 PCIe 互联，没有高速互联，TP 开销很大，倾向于小 TP 或不用 TP，改用 PP + ZeRO。
4. 必须先确认实际拓扑（哪些卡直连、是否跨 CPU 插槽、NUMA 亲和），再用通信基准测试验证，而不是凭经验。

另外注意：并行度要能整除头数、层数；长序列可再加序列并行或上下文并行；MoE 还有专家并行。

### 4. 千卡训练时 AllReduce / AllToAll 成为瓶颈，你会看哪些指标，CNCL 和 NCCL 思路上有什么异同

**参考答案**

结论：先区分"通信本身慢"和"通信没被计算掩盖"，再看是带宽、延迟、拓扑还是落后节点导致的。

看的指标：

- **总线带宽 vs 理论带宽**：不同消息大小下的实测值（类似 nccl-tests 的方法），小消息看延迟，大消息看带宽。
- **暴露的通信时间**：step 时间中没有被计算重叠的通信占比。
- **各 rank 的步时间和等待时间**：找落后者（straggler），集合通信的速度取决于最慢的 rank。
- **链路和网络指标**：链路利用率、拥塞、重传、丢包、RDMA 的错误计数。
- **消息大小分布和调用次数**：太碎说明梯度分桶不合理。
- **AllToAll**：各 rank 收发量是否均衡（MoE 专家负载不均会直接放大它）。
- **CPU 发射抖动**：集合通信是否被主机侧延迟。

优化手段：梯度分桶和重叠、层次化通信（节点内先聚合再跨节点）、调整并行布局使大流量落在高速域内、通信压缩、专家放置优化。

**CNCL 与 NCCL**：

- **相同点**：都是面向各自硬件的集合通信库，提供 AllReduce、AllGather、ReduceScatter、AllToAll、Broadcast 等原语；都做拓扑感知，选用 ring、tree 等算法，通信在设备队列（stream）上异步执行，并作为 PyTorch 分布式后端接入。
- **不同点**：底层互联不同（MLU-Link 对应 NVLink / NVSwitch），算法调优、协议和默认参数针对各自的硬件；生态成熟度、调试工具、社区经验差异明显，CNCL 遇到问题更依赖厂商支持和自己做基准测试，不能直接套用 NCCL 的环境变量和经验。

### 5. DeepSpeed ZeRO、Megatron 3D 并行、PyTorch DDP，各自适合什么规模的国产卡集群

**参考答案**

结论：模型越大、卡数越多，越需要更复杂的并行；但同时要考虑国产卡上框架适配的成熟度。以下规模只是经验性的划分，实际要看模型大小、显存和互联。

- **PyTorch DDP**：每卡保存完整模型副本，只同步梯度。适合单卡能放下模型的中小模型，从单机到几十、上百卡都可以，实现最简单、最稳，通信只有梯度 AllReduce。
- **DeepSpeed ZeRO**：把优化器状态（ZeRO-1）、梯度（ZeRO-2）、参数（ZeRO-3）分片到 DP 各卡。单卡放不下优化器状态或模型，但又不想引入复杂并行时使用。ZeRO-1/2 通信开销小；ZeRO-3 会增加参数 AllGather，对网络要求高，在带宽较弱的集群上要谨慎。适合中等规模、中大型模型的训练和微调。
- **Megatron 3D 并行**（TP + PP + DP，常配合序列并行、专家并行）：适合超大模型和上千卡规模，通信按拓扑分层，扩展性最好，但需要手动调并行配置、对拓扑敏感、改造成本高。

国产卡上的现实考虑：要确认对应的框架版本是否有成熟的适配（算子、通信后端 CNCL、混合精度、重计算、checkpoint 格式），以及互联拓扑是否支持 TP 所需的带宽。通常从 DDP 或 ZeRO 起步验证精度，再在规模上去逐步引入 TP 和 PP。

### 6. 大模型训练利用率只有 30%，从数据加载、通信、算子、显存、框架调度几个层面怎么拆

**参考答案**

结论：先测量再优化。用 profiler 把一个 step 的时间线拆开，算出 MFU（实际 FLOPs ÷ 理论峰值），再看设备在哪里空闲。

1. **数据加载**：step 开头设备空闲，说明数据没准备好。检查 DataLoader 的 worker 数量和预取、存储吞吐、在线分词开销、样本打包（packing）是否做好。
2. **通信**：时间线上有大段没被计算重叠的通信。检查梯度分桶、通信重叠、并行布局是否合理、是否存在落后 rank、网络和拓扑。
3. **算子**：单个算子效率低，常见情况是没有融合的小算子、注意力没有用高效实现、不支持的算子回退 CPU、数据类型没有用到低精度、矩阵形状没对齐。
4. **显存**：显存紧张导致只能用很小的 micro-batch，算力吃不满；激活重计算增加额外计算量；显存碎片。可以通过 ZeRO、更合理的并行切分、选择性重计算来缓解。
5. **框架调度**：kernel 启动开销大、Python 开销、频繁 host-device 同步（如 `.item()`、打印 loss）、流水线气泡、各 rank 负载不均。

优化顺序：先处理最大的空闲段，一般是"数据 → 通信重叠 → 算子融合 → batch 和显存 → 调度细节"。每次只改一项并回归验证，保证精度不变。

### 7. FlashAttention 为什么能省显存和带宽，放到国产 AI 芯片上移植时最怕什么

**参考答案**

结论：FlashAttention 是精确注意力，通过分块计算和在线 softmax，不把 N×N 的注意力矩阵写回显存，从而把显存占用从 O(N²) 降到 O(N)，并大幅减少对高带宽显存的读写。

- **机制**：标准实现会把 `QK^T` 得到的 N×N 矩阵、softmax 结果都写入 HBM 再读出，访存是瓶颈。FlashAttention 把 Q、K、V 切成块加载到片上高速存储，在片上完成"打分、在线 softmax（维护行最大值和归一化因子）、乘 V"，只写最终输出。反向传播不保存注意力矩阵，而是保存 logsumexp 并重新计算。
- **效果**：降低显存占用，减少 HBM 读写，因注意力是访存受限的，所以更快。

移植到国产芯片时最怕：

- **片上存储差异**：MLU 的存储层次（NRAM、WRAM、SRAM 和全局内存）容量、对齐和搬运方式与 GPU 的共享内存、寄存器不同，分块大小要重新设计。
- **矩阵计算单元和数据布局要求**：需要贴合硬件指令的形状和对齐。
- **数值问题**：在线 softmax 需要用 fp32 累加，低精度累加顺序不同会导致结果与 GPU 有差异。
- **功能覆盖**：因果 mask、变长序列、GQA/MQA、dropout、反向传播的实现复杂度。
- **性能**：数据搬运和计算的流水重叠依赖编译器和硬件能力，写不好就达不到预期收益。

### 8. MoE 模型在推理和训练里，专家负载不均怎么发现、怎么缓解，drop token 和辅助 loss 的代价是什么

**参考答案**

结论：负载不均会导致热点专家成为瓶颈、其他卡空转、AllToAll 变慢。先用指标发现，再用路由约束和部署策略缓解，两种常用手段各有代价。

**怎么发现**：

- 统计每个专家分到的 token 数，看最大值与平均值之比、变异系数、直方图，以及随训练或时间的变化。
- 看各 EP rank 的步时间差异和 AllToAll 耗时。
- 训练中看 token 被丢弃的比例、路由熵。

**怎么缓解**：

- **训练**：
  - 辅助负载均衡 loss（鼓励路由概率和分配比例均匀）。
  - 设置容量因子限制每个专家处理的 token 数。
  - 路由时加噪声；也有无辅助 loss 的方案，通过动态调整专家偏置来均衡。
- **推理**：
  - 不丢 token，对热点专家做副本复制或重新放置。
  - 按在线统计动态调整专家的放置。
  - 合并请求，增大 batch 使负载更平滑。

**代价**：

- **drop token**：超出容量的 token 不经过专家（只走残差），造成质量损失；训练和推理行为不一致时更明显，所以推理一般不丢弃，但热点专家的延迟会变成尾延迟。
- **辅助 loss**：系数过大，会干扰主任务梯度，让路由趋向均匀而损害专家分化，需要仔细调参；系数太小又起不到作用。

### 9. 推理引擎要做 continuous batching，底层调度状态和普通网关请求调度有什么本质区别

**参考答案**

结论：网关调度的是"无状态的短请求"，决策一次、各请求互不影响；推理引擎调度的是"有状态的长生命周期请求"，每个迭代都要重新决策，且请求之间共享显存和算力。

区别：

- **状态**：网关请求基本无状态，路由后即可忘掉；引擎里每个请求有 KV Cache、已生成 token、采样状态，请求的生命周期跨越几十到几千个迭代。
- **调度粒度**：网关按请求调度；引擎按迭代（每生成一个 token）调度，每步决定谁进入 batch。
- **资源耦合**：引擎里 KV Cache 块是共享的稀缺资源，接纳新请求会影响已有请求，显存不足时要抢占、换出到主机内存或丢弃重算。
- **阶段差异**：prefill 是计算密集，decode 是访存密集，混合在一个 batch 里会互相干扰，需要 chunked prefill、token 预算等策略。
- **请求状态机**：waiting、running、swapped、finished，以及块表、前缀缓存的管理。
- **代价模型**：网关切换请求的代价很小；引擎抢占的代价是重算或换页，必须纳入调度考量。

因此引擎调度更像一个"操作系统调度器 + 内存管理器"。

### 10. 多模型多租户推理平台里，怎么隔离显存、算力、队列，别只说 Kubernetes resource limit

**参考答案**

结论：隔离要分层做：硬件或进程层隔离显存和算力，引擎层隔离 KV Cache 和队列，网关层做配额与公平调度。K8s 的 resource limit 只能管 CPU 和内存，管不了设备内部的竞争。

- **显存**：
  - 强隔离：独占整卡，或使用硬件虚拟化 / 设备切分（取决于所用卡是否支持），每个实例有固定显存配额。
  - 同卡多模型：每个进程设置显存上限，并预先划分权重池和 KV Cache 池；避免动态抢占造成 OOM 连锁。
  - 引擎内部：按租户给 KV Cache 块设置配额。
- **算力**：
  - 独占卡或按切分比例分配；
  - 共享时用时间片，但延迟抖动大，核心业务不建议共享；
  - 重负载的大模型和低延迟的小模型放在不同资源池。
- **队列**：
  - 每个租户或模型独立队列，用加权公平队列调度，避免大客户占满队列。
  - 限流按 token 数而不是请求数，因为请求的大小差异巨大。
  - 准入控制：队列过长时拒绝或降级，别让请求无限排队拖垮所有人。
  - 优先级和抢占，规定高优先级业务可以抢占低优先级。
- **安全隔离**：不同租户使用独立进程，前缀缓存不跨租户共享，防止泄露和侧信道。
- **可观测与计费**：按租户统计 token、显存和时长，便于发现噪声邻居。

### 11. 模型热更新怎么做，不能停服务、不能掉精度、不能让在跑请求崩，方案怎么设计

**参考答案**

结论：不要原地替换权重，而是"新实例加载预热 → 灰度切流 → 老实例排空 → 保留回滚"的蓝绿或滚动发布，并配合精度门禁。

流程：

1. **版本化**：模型注册表保存版本、权重、校验和、量化配置、评估结果，部署只引用不可变版本。
2. **精度门禁**：发布前跑固定的黄金集或回归集，比对关键指标，不达标则不允许上线；量化模型要用线上分布重新校准并验证。
3. **新实例准备**：从共享存储或本地缓存加载权重，完成引擎构建、预热（覆盖常用 shape，触发编译和缓存），健康检查通过后才注册到网关。
4. **灰度切流**：先影子流量对比输出，再小比例放量，监控错误率、延迟、质量指标，异常自动回滚。
5. **老实例排空**：不再接收新请求，等在跑请求（包括流式输出）完成，设置超时上限；超时后再终止。
6. **回滚**：老版本保留一段时间，一键切回。

显存和资源问题：单卡放不下两个版本时，用滚动方式逐个替换副本，或预留备用实例，不要在同一张卡上同时加载。

特殊情况：LoRA 等适配器可以在引擎内热加载；同一会话或多轮对话是否需要固定在同一版本，也要考虑。

### 12. 训练任务异常退出，checkpoint 丢了半小时进度，老板让你把恢复时间压到分钟级，你怎么改架构

**参考答案**

结论：恢复时间 = 故障发现 + 重新调度 + 初始化 + 加载 checkpoint + 丢失的训练步。要压到分钟级，需要同时缩短这几项，核心是高频、异步、分层的 checkpoint 和自动恢复。

1. **高频异步 checkpoint**：先把状态快速拷到主机内存（秒级），再由后台线程写入存储，训练不阻塞。这样可以把间隔缩短到几分钟，最多只丢几分钟。
2. **分片并行写入**：每个 rank 只写自己那份（分布式 checkpoint），写入带宽随机器数线性扩展，并支持换并行度后重新切分加载。
3. **多级存储**：本地内存或 NVMe → 同伴节点内存副本 → 远端共享存储。多数故障只需要从近处恢复，慢的远端存储做低频兜底。
4. **快速发现故障**：心跳、watchdog、通信超时、step 时间监控，避免 hang 住半小时才被发现。
5. **自动恢复**：调度器自动剔除坏节点，用备用节点补位，重启作业，而不是人工重新排队；提前预热镜像、预留备用机器池。
6. **数据和随机状态可恢复**：记录 dataloader 样本位置和随机数状态，保证续训后数据不重复、不遗漏。
7. **完整性保障**：先写临时文件再原子提交，带校验和和清单，保留最近 N 个版本，避免恢复时读到损坏的 checkpoint。

容易漏的点：只提高保存频率而不做异步，会拖慢训练；恢复还要测加载耗时，并定期做恢复演练。

### 13. MySQL 在这里适合存什么，模型版本、任务状态、计费、日志分别该放哪

**参考答案**

结论：MySQL 适合存"结构化、需要事务和一致性、体量可控"的数据，不适合存大文件和海量日志。

- **模型版本**：适合。存元数据（名称、版本、路径、校验和、量化方式、评估结果、状态、创建人），权重本体放对象存储，库里只存路径。
- **任务状态**：适合存任务定义和状态流转（状态机），更新时用乐观锁或带条件的 UPDATE，避免并发覆盖。高频变化的心跳、进度放 Redis 或 etcd，定期落库。
- **计费**：适合存账单、账户余额、流水，需要事务和幂等（流水号唯一索引）。原始的用量事件量很大，先进入 Kafka，用 ClickHouse 等做聚合，再把汇总结果写入 MySQL。
- **日志**：不适合。训练日志、推理日志放日志系统（Elasticsearch、Loki）或对象存储，结构化分析用 ClickHouse，MySQL 只存必要的索引信息。

补充：MySQL 表要考虑分表归档和索引设计；大 JSON 字段谨慎使用；读多的元数据可以加缓存。

### 14. Elasticsearch 在 AI 平台里适合搜什么，模型元信息、训练日志、推理 trace 该不该都进 ES

**参考答案**

结论：ES 适合做"全文检索和多维过滤聚合"，但不应该成为所有数据的归宿，要按价值和成本取舍。

- **训练日志**：适合。按关键字检索报错信息、按任务、节点、时间过滤，排障效率高。注意控制索引的字段数量、设置生命周期管理（热温冷、过期删除）。
- **推理 trace**：适合做按 trace_id、租户、模型、状态码、耗时的检索，但全量保留成本很高，应该采样（错误和慢请求全量保留，正常请求抽样），或用专门的 trace 后端。提示词和输出可能含敏感信息，要脱敏或不入库。
- **模型元信息**：可以做搜索入口（按名称、标签、描述模糊查找），但权威数据放 MySQL，ES 只是同步出来的检索副本，因为 ES 不保证事务和强一致。
- **不适合**：指标时序数据（用 Prometheus 等时序库）、需要事务的数据（MySQL）、大规模离线分析（ClickHouse 或数仓）。

结论：不要全进 ES。按"能否检索、保存多久、成本多少"分层：ES 放近期、需要搜索的数据，长期归档放对象存储。

### 15. 手撕算法：给定一个任务列表，每个任务有 GPU 卡数、预计时长、优先级，实现简化版 Gang Scheduling：只有所需卡全部就绪才启动，否则等待，输出启动顺序和时间线

**参考答案**

思路：Gang Scheduling 要求"全有或全无"，任务要么一次拿到所需的全部卡，要么不启动，避免部分占卡造成死锁。用事件驱动模拟：

1. 等待队列按优先级从高到低、同优先级按提交顺序排序。
2. 每个时刻，依次检查队首任务，空闲卡数够就启动。队首放不下时，默认阻塞后面的任务（严格优先级，避免大任务被饿死），也可以开启 backfill 让后面能放下的小任务先跑。
3. 启动后把结束时间放入最小堆；时间推进到最早结束的任务，释放它的卡，再重复检查。

复杂度：排序 O(n log n)，每次启动或结束堆操作 O(log n)，整体约 O(n²) 最坏（每次扫描等待队列），n 不大时足够。

```python
import heapq


def gang_schedule(tasks, total_gpus, backfill=False):
    """
    tasks: [{"id": str, "gpus": int, "duration": int, "priority": int}, ...]
    返回按启动先后排列的 (task_id, start, end) 时间线。
    """
    for t in tasks:
        if t["gpus"] > total_gpus:
            raise ValueError(f"任务 {t['id']} 需要的卡数超过集群总量")

    # 优先级高的在前；同优先级按输入顺序（sorted 稳定）
    pending = sorted(tasks, key=lambda t: -t["priority"])
    running = []          # 小根堆: (结束时间, 序号, 占用卡数)
    free, now, seq = total_gpus, 0, 0
    timeline = []

    while pending or running:
        # 尝试启动：所需卡数全部满足才启动
        for t in list(pending):
            if t["gpus"] <= free:
                free -= t["gpus"]
                end = now + t["duration"]
                heapq.heappush(running, (end, seq, t["gpus"]))
                seq += 1
                timeline.append((t["id"], now, end))
                pending.remove(t)
            elif not backfill:
                break  # 严格优先级：队首放不下就等待

        if not running:
            break  # 理论上不会发生，因为已检查单任务不超过总量
        # 时间推进到最早结束的任务，并释放同一时刻结束的全部任务
        now = running[0][0]
        while running and running[0][0] == now:
            _, _, g = heapq.heappop(running)
            free += g

    return timeline
```

补充：真实系统里还要考虑抢占、拓扑感知（同一互联域内的卡）、配额公平，以及超时放弃、防止大任务饿死。

### 2. 你主导过哪个 AI Infra 项目，从 0 到 1 还是从 1 到 100，你拍板了哪些技术选型

**答题思路**

先明确阶段，再讲决策。建议结构：

1. **背景与目标**：要解决什么问题，成功标准是什么（稳定性、成本、性能、交付时间）。
2. **阶段判断**：0 到 1 重在选型、验证可行性、快速上线；1 到 100 重在规模化、稳定性、成本、多团队接入。
3. **关键选型**（挑 2 到 3 个讲透）：每个选型都说"备选方案 → 评估维度 → 为什么选它 → 放弃了什么 → 事后复盘"。例如推理引擎、调度系统、并行方案、存储与元数据、监控体系。
4. **你拍板的方式**：做了哪些 POC、基准测试，怎么平衡团队能力和长期维护。
5. **结果与反思**：哪些选型对了，哪些后来调整了。

注意：只讲真实经历，不编造项目名称和数字；诚实地讲出踩过的坑更有说服力。

### 3. 寒武纪、昇腾、英伟达三套生态同时接，平台层怎么抽象，不能每个芯片写一套代码吧

**参考答案**

结论：在"资源、引擎、通信、可观测"四个层面做抽象，并让厂商差异下沉到插件和适配层。抽象的粒度放在"推理或训练引擎"层，而不是算子层。

- **资源层**：通过 Kubernetes 设备插件管理各家的卡（资源名称不同），平台上统一成"加速卡类型 + 数量 + 显存 + 拓扑"的资源模型，调度时按标签和能力匹配。
- **引擎层**：定义统一的服务接口（加载模型、推理、流式输出、健康检查、指标），后端分别接入英伟达侧的 vLLM 或 TensorRT-LLM、昇腾侧的 MindIE 等、寒武纪侧的 MagicMind 或 vLLM 的 MLU 适配版本。上层的网关、路由、计费、限流不感知芯片。
- **模型与精度**：以统一的模型格式（HF 权重、ONNX 等）作为输入，每个后端有自己的转换与量化流程，产出带"芯片 + 版本"标签的制品。
- **训练与通信**：通过 PyTorch 分布式的后端切换（nccl、hccl、cncl），框架代码尽量设备无关。
- **可观测**：用各自的 exporter（英伟达的 DCGM、昇腾和寒武纪的设备监控）采集，统一成同一套指标名。
- **能力矩阵与回归**：维护"芯片 × 模型 × 精度 × 特性"的支持矩阵，每次升级跑精度和性能回归。
- **避免过度抽象**：保留厂商专属的调优参数入口，抽象太厚会影响性能，也会引起芯片团队的抵触。

### 4. 国产芯片软件栈不成熟，算子缺失、精度漂移、通信库抽风，你怎么决定是自研、适配还是劝业务方别上

**参考答案**

结论：用"目标 + 数据 + 成本"做决策，设立明确的准入门槛，而不是凭感觉。

1. **先定义目标**：业务要的吞吐、延迟、精度下限、上线时间，以及为什么要用国产卡（信创要求、成本、供货）。
2. **做 POC 并量化**：在目标模型上测算子覆盖率、精度（与基线对比）、性能、长时间稳定性（通信、掉卡）。
3. **按问题类型决策**：
   - **算子缺失**：次要路径用组合或拆图；热点算子且团队有能力就自研；同时向厂商提需求。
   - **精度漂移**：先定位到层，确认是 dtype、算子实现还是预处理问题，多数可通过调整精度策略、关键层高精度来解决；无法在阈值内则不能上线。
   - **通信不稳定**：影响训练的稳定性，需要厂商给出修复计划，平台侧做超时检测、快速重启、自动隔离坏节点。
4. **选择**：
   - **适配**：差距小、有明确收益；
   - **自研**：只在高频、高价值、团队可维护的地方；
   - **劝业务别上**：关键算子缺失且无解、精度达不到、稳定性不满足 SLA、上线时间等不及厂商修复周期。劝退时拿数据说话，同时给出替代方案（先用英伟达，或分阶段迁移，仅迁移适合的模型）。
5. **机制**：建立与厂商的问题升级通道、版本准入测试、问题清单和修复时间表。

### 5. 大模型推理成本太高，老板要降本 50%，你会从芯片、批处理、量化、缓存、路由、模型小型化里怎么排优先级

**参考答案**

结论：先拆解成本、找出利用率低的地方，按"风险低、见效快的先做，影响大、周期长的后做"排序。降 50% 通常要多项叠加，而不是靠单一手段。

先做测量：定义单位成本（每百万 token 的成本），看当前卡利用率、batch 大小、缓存命中率、请求长度分布和流量峰谷。

优先级：

1. **批处理与调度**（最先）：连续 batching、chunked prefill、合理的 batch 上限和排队策略、提高卡利用率。无需改模型，风险低，常能显著提升单卡吞吐；配合弹性伸缩，利用潮汐降低空闲成本。
2. **缓存**：前缀缓存（系统提示词和多轮对话共享）、确定性请求的结果缓存。命中率取决于业务，成本低。
3. **路由**：简单请求路由到小模型，复杂请求才走大模型；按优先级和 SLA 分流。收益大，但需要质量评估和兜底。
4. **量化**：权重量化（INT8、INT4）、KV Cache 量化，降低显存和带宽，提升吞吐；需要精度回归，风险中等。
5. **模型小型化**：蒸馏、剪枝、投机解码等，收益大但周期长、需要算法团队配合。
6. **芯片选择**（最后，也可以并行规划）：换更高性价比的硬件或国产卡，需要适配和验证，周期长、迁移风险大，但对长期成本影响最大。

约束：每一项都要设置质量门禁（离线评估和线上 A/B），不能为了降本伤害效果；每项做完都要复测成本。

### 6. 万卡集群里故障是常态，你怎么设计健康探测、任务重调度、坏卡隔离、训练续跑和告警闭环

**参考答案**

结论：把故障当作常态来设计，目标是"快发现、自动隔离、自动重调度、快速续跑、可追溯"，人只处理自动化解决不了的部分。

1. **健康探测**（分层）：
   - **硬件层**：设备监控采集 ECC 错误、温度、功耗、链路错误、驱动日志。
   - **节点层**：内核、磁盘、网卡、PCIe 状态。
   - **集合通信探测**：任务启动前和空闲时跑小规模 AllReduce 与带宽测试，提前找出慢卡或坏链路。
   - **作业层**：心跳、step 时间落后检测、loss NaN、通信超时 watchdog、hang 时自动抓栈。
   - **静默错误**：监控梯度范数和 loss 突刺，必要时做重复计算校验。
2. **坏卡隔离**：自动标记节点或卡为不可调度（cordon、taint），进入维修流程，修好后先做压测再放回；对"反复故障"的节点设置熔断。
3. **任务重调度**：调度器用备用节点补位，保持拓扑要求（整组重新调度，Gang 语义），限制重启频率，避免故障风暴。
4. **训练续跑**：异步分层 checkpoint、数据位置和随机状态恢复，必要时用弹性训练；目标是把恢复时间压到分钟级。
5. **告警闭环**：
   - 故障分类（硬件、网络、软件、用户代码）；
   - 告警聚合去重，分级通知；
   - 自动处置结果回写，工单跟踪，复盘和根因归档；
   - 统计 MTBF、自动恢复率、有效训练时间占比，持续改进。

### 7. AI 平台要卖进金融 / 政务私有化环境，信创、隔离、审计、离线部署、模型加密这些怎么落地

**参考答案**

结论：私有化交付要做成"可离线安装、可审计、可隔离、合规可验证"的产品，而不是把公有云方案打包搬过去。

- **信创**：建立适配清单，涵盖国产 CPU（如鲲鹏、飞腾等）、操作系统（麒麟、统信等）、数据库、中间件，以及国产加速卡；每个组合做兼容性与性能测试，镜像按架构构建。国密算法（SM2、SM3、SM4）用于传输和存储加密。
- **隔离**：网络分区（内外网、管理面与业务面隔离），多租户使用独立命名空间、资源池和存储，关键客户可以做物理隔离；不依赖任何公网服务。
- **审计**：记录所有登录、管理操作、模型访问、调用日志，日志防篡改、集中保存并满足留存期限；涉及用户数据的内容要脱敏，并区分哪些内容可以入日志。
- **离线部署**：整套离线安装包（镜像仓库如 Harbor、依赖、驱动、模型），带版本清单和签名校验；升级用离线补丁包，支持回滚；许可证校验不依赖联网；监控、日志、告警都在本地闭环。
- **模型加密**：权重加密存储（信封加密，密钥由 KMS 或硬件密码设备管理），加载时在内存中解密，密钥不落盘；模型文件做签名防篡改；访问需要授权。要诚实说明：若客户完全控制硬件，无法 100% 防止被提取，需要配合合同、审计和部署环境的管控。
- **合规**：对照等保要求，提供安全加固基线、漏洞扫描和渗透测试报告。

### 8. 推理平台 SLA 写 99.9%，但底层芯片驱动半夜崩，你怎么跟客户、业务、硬件团队扯清楚责任

**参考答案**

结论：对客户，SLA 是平台整体的承诺，驱动崩溃属于"可预期的组件故障"，应该通过冗余和自愈来吸收，而不能把责任推给硬件；对内，通过拆分 SLO、错误预算和证据链来明确各方责任。

先算账：99.9% 的月可用性意味着每月（按 30 天）约 43 分钟的不可用预算，单卡驱动崩溃若会导致服务中断，说明架构冗余设计不足。

**对客户**：

### 13. 手撕算法：给定一个模型服务队列，请求有 arrival_time、tokens、priority，实现简化版优先级抢占调度，要求说明抢占正在生成中的请求会有什么副作用

**参考答案**

思路：模拟一个单工作单元，每个时间步生成一个 token（迭代级调度）。用优先级队列保存所有"已到达且未完成"的请求，排序键为（优先级高在前，到达时间早在前，序号）。每一步取队首运行一个 token；如果队首与上一步运行的请求不同，并且上一个请求没完成，就发生了一次抢占。

复杂度：每个 token 一次堆操作，总复杂度 O(T log n)，T 为总 token 数，n 为请求数。

```python
import heapq


def preemptive_schedule(requests):
    """
    requests: [{"id": str, "arrival_time": int, "tokens": int, "priority": int}, ...]
    priority 越大越优先；每个时间步生成 1 个 token。
    返回 (finish_time 字典, 抢占次数, 运行记录列表)。
    """
    reqs = sorted(requests, key=lambda r: r["arrival_time"])
    remaining = {r["id"]: r["tokens"] for r in reqs}
    arrival = {r["id"]: r["arrival_time"] for r in reqs}
    prio = {r["id"]: r["priority"] for r in reqs}

    heap, i, n, now = [], 0, len(reqs), 0
    last, preempts = None, 0
    finish, trace = {}, []

    while i < n or heap:
        if not heap:  # 空闲，时间跳到下一个到达时刻
            now = max(now, reqs[i]["arrival_time"])
            last = None
        while i < n and reqs[i]["arrival_time"] <= now:
            rid = reqs[i]["id"]
            heapq.heappush(heap, (-prio[rid], arrival[rid], i, rid))
            i += 1

        key = heapq.heappop(heap)
        rid = key[3]
        # 上一个请求还没生成完就被换下来：发生抢占
        if last is not None and last != rid and remaining[last] > 0:
            preempts += 1

        remaining[rid] -= 1      # 生成一个 token
        trace.append((now, rid))
        now += 1
        if remaining[rid] > 0:
            heapq.heappush(heap, key)
        else:
            finish[rid] = now
        last = rid

    return finish, preempts, trace
```

说明：这里的 `tokens` 是要生成的 token 数；同优先级时到达早的请求排在前面，所以不会互相抢占；低优先级请求可能被持续抢占而饿死，实际系统需要老化（aging）机制。

**抢占正在生成中的请求会有什么副作用**：

- **KV Cache 的处理代价**：被抢占请求的 KV Cache 要么继续占着显存（降低并发、可能引发 OOM），要么换出到主机内存（占用 PCIe 带宽，恢复时再换入），要么直接丢弃，恢复时重新 prefill 重算（浪费算力、增加延迟）。
- **延迟与流式体验**：被抢占请求的输出会停顿，TPOT 和尾延迟变大，用户看到的流式输出会卡住；还可能触发客户端超时和重试，放大负载。
- **饥饿和不公平**：低优先级请求可能长时间得不到服务，需要老化机制或配额。
- **抖动和效率损失**：频繁抢占（thrashing）会使换入换出和重算的开销超过收益，需要最小运行时间片、抢占阈值或滞回策略。
- **状态一致性**：采样状态（随机种子）、已生成 token、停止条件、结构化生成的状态机必须保存完整，否则恢复后输出不一致。
- **资源统计与计费**：重算的 token 要不要计费、如何统计，需要明确定义。
