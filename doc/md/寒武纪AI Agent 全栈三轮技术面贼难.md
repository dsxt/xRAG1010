### 3. Python 异步编程在 Agent 服务里哪些地方必须用 asyncio，举具体场景

**参考答案**

凡是"等待外部 IO"且需要高并发或流式输出的地方都应使用 asyncio，因为 Agent 服务的耗时几乎全在等 LLM 和工具响应，而不是 CPU 计算。

典型场景：

- **LLM 调用与流式输出**：用异步客户端（如 `AsyncOpenAI`）`async for` 消费 token，配合 FastAPI 的 SSE 推给前端，一个事件循环可同时挂住大量连接。
- **并行工具调用**：模型一次返回多个互不依赖的 tool call，用 `asyncio.gather` 并发执行，总耗时取最慢者。
- **多路召回并发**：向量、BM25、SQL、图谱几路检索并行发起，再融合。
- **超时与取消**：`asyncio.wait_for` / `asyncio.timeout` 给每次工具调用设超时，客户端断开时取消任务，避免继续消耗 token。
- **异步数据库/缓存/MQ 客户端**：asyncpg、redis.asyncio、aiokafka 等。

容易漏的点：

- 在 `async def` 里调用阻塞库（同步 requests、同步 SDK、重 CPU 计算）会卡死整个事件循环，必须用 `asyncio.to_thread` / 线程池 / 进程池隔离。
- 并发要限流（`Semaphore`），避免打爆下游和触发模型限流。
- `gather` 要考虑 `return_exceptions=True`，防止单个工具失败拖垮整批。

### 4. FastAPI 怎么接 SSE 把 Agent 的思考、工具调用、最终结果流式推给前端

**参考答案**

用 `StreamingResponse`（`media_type="text/event-stream"`）或 `sse-starlette` 的 `EventSourceResponse`，把 Agent 执行过程包装成异步生成器，按事件类型逐条推送。

做法：

1. 定义事件协议：`event` 区分 `thinking`、`tool_call`、`tool_result`、`token`、`final`、`error`、`done`，`data` 放 JSON，每条带递增 `seq` 和 `id`。
2. Agent 侧用 `astream` / `astream_events`（LangGraph/LangChain）或自己的回调，把中间步骤放入 `asyncio.Queue`，生成器从队列取出后格式化为 `event: xxx\ndata: {...}\n\n`。
3. 响应头设置 `Cache-Control: no-cache`、`Connection: keep-alive`；若有 Nginx，要关闭代理缓冲（`X-Accel-Buffering: no` 或 `proxy_buffering off`），否则流会被攒着一起吐。
4. 定期发心跳注释行（`: ping`）防止中间件断连。
5. 检测 `await request.is_disconnected()`，客户端断开时取消 Agent 任务。

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
import json, asyncio

app = FastAPI()

def sse(event: str, data: dict, seq: int) -> str:
    return f"id: {seq}\nevent: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

@app.post("/chat")
async def chat(req: Request):
    queue: asyncio.Queue = asyncio.Queue()
    task = asyncio.create_task(run_agent(queue))  # Agent 往 queue 放 (event, data)

    async def gen():
        seq = 0
        try:
            while True:
                if await req.is_disconnected():
                    task.cancel()
                    break
                try:
                    event, data = await asyncio.wait_for(queue.get(), timeout=15)
                except asyncio.TimeoutError:
                    yield ": ping\n\n"
                    continue
                seq += 1
                yield sse(event, data, seq)
                if event in ("done", "error"):
                    break
        finally:
            task.cancel()

    return StreamingResponse(gen(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

关于"乱序"：单个 SSE 连接基于 TCP，本身是有序的；乱序通常来自并行工具回调在多个任务里各自写出、或重连后重放。解决办法是所有事件统一经过同一个队列/序号发生器，前端按 `seq` 去重排序，并支持 `Last-Event-ID` 断线续传。

### 5. 意图识别在你项目里是怎么做的，规则、小模型分类还是 LLM 路由，各自边界

**参考答案**

通常采用分层漏斗：规则兜前面、小模型/分类器做主力、LLM 路由处理长尾，按"成本低、确定性高的优先"。

- **规则（关键词、正则、命令前缀、按钮入口）**：延迟近乎为零、完全可控，适合固定入口、指令式、强格式输入和安全拦截；缺点是泛化差，维护成本随规则数上升。
- **小模型分类（BERT 类、嵌入 + 分类头、微调小 LLM）**：延迟几十毫秒、成本低、输出稳定，适合类别固定、标注数据足够、QPS 高的场景；缺点是新增意图要重新标注训练，对复杂多意图和上下文依赖弱。
- **LLM 路由（Prompt 或 Function Calling 让大模型选意图/工具）**：零样本可扩展，能理解多轮上下文和组合意图，适合长尾和新意图冷启动；缺点是延迟与成本高、输出有波动。

落地要点：输出结构化（意图 + 置信度），低置信度时降级为反问或兜底通用问答；LLM 路由的结果沉淀为标注数据，反哺小模型，逐步把流量从 LLM 迁到小模型；意图分类必须有评测集，监控分错率。

### 6. ReAct 和单轮 ChatCompletion 最本质区别，什么任务不适合用 ReAct

**参考答案**

本质区别：单轮 ChatCompletion 是一次"输入 → 输出"，模型只靠自身参数知识回答；ReAct 把推理（Reason）和行动（Act）交替成循环：思考 → 调用工具 → 观察结果 → 再思考，直到给出最终答案，所以模型能通过观察外部环境反馈动态调整下一步，是"带反馈的闭环"。

不适合用 ReAct 的任务：

- **流程固定、步骤确定**的任务（如固定的 ETL、审批流），用工作流/图硬编码更稳、更快、更便宜。
- **延迟敏感、一次能答完**的简单问答、分类、改写，多轮循环徒增延迟和 token。
- **高风险、不可逆操作**，需要确定性和审批，不应由模型自由决定下一步。
- **步骤很长、容易陷入循环或错误累积**的任务，需要规划拆解、最大步数限制、或 Plan-and-Execute。

要点：ReAct 的代价是不确定性、成本和延迟，必须配最大迭代次数、重复调用检测和超时兜底。

### 7. Function Calling 底层怎么把工具 schema 喂给模型，模型输出非法 JSON 你在代码里怎么兜底

**参考答案**

Function Calling 的做法是：请求里带上 `tools` 列表，每个工具包含 `name`、`description` 和用 JSON Schema 描述的 `parameters`。服务端把这些 schema 按模型特定的模板渲染进上下文（系统提示或专门的特殊 token 区域），模型经过针对工具调用的微调，在需要时输出结构化的调用（工具名 + 参数 JSON）而非普通文本；应用代码解析后真正执行，再把结果以 `tool` 角色消息回填，进入下一轮。模型本身不执行任何函数。

非法 JSON 的兜底（模型输出不保证一定合法）：

1. **解析层**：`json.loads` 失败时先做轻量修复（去掉 markdown 代码围栏、补全括号、`json_repair` 之类的库）。
2. **校验层**：用 Pydantic / JSON Schema 校验字段类型、必填项、枚举值，不通过视为非法。
3. **重试层**：把错误信息（具体哪个字段不合法）作为 tool 结果或用户消息回给模型，让它自行修正，限制 1 到 2 次重试。
4. **约束解码**：服务端支持时启用 strict 模式 / structured outputs / 受限解码（guided decoding），从源头保证符合 schema。
5. **降级**：超过重试次数则降级为不使用工具的直接回答或走固定流程，并记录 badcase。

```python
from pydantic import BaseModel, ValidationError
import json

class SearchArgs(BaseModel):
    query: str
    top_k: int = 5

def parse_args(raw: str) -> SearchArgs:
    raw = raw.strip().removeprefix("```json").removesuffix("```").strip()
    return SearchArgs(**json.loads(raw))  # 失败抛 JSONDecodeError/ValidationError，由调用方回灌错误并重试
```

容易漏的点：参数合法不代表安全，工具执行前还要做权限与业务校验；幻觉出不存在的工具名也要处理。

### 8. LangChain 和 LangGraph 在你眼里分别解决什么问题，什么情况用 LangChain 就够，什么情况必须上图

**参考答案**

LangChain 解决的是"组件抽象和组合"：统一模型、Prompt、检索器、工具、输出解析等接口，用 LCEL 把它们链式串起来，适合线性或简单分支的流程。LangGraph 解决的是"有状态、可循环、可控的编排"：把流程建模成由节点和边组成的图，共享显式 State，支持条件边、循环、并行、持久化 checkpoint、中断恢复。

LangChain 就够用的情况：线性流水线（检索 → 拼 Prompt → 生成）、单次工具调用、没有复杂状态与回环、不需要中断恢复的简单 RAG/问答。

必须上图的情况：

- 需要**循环**（ReAct 循环、反思重试、检索自省后再检索）。
- **多 Agent 协作**，需要显式共享和隔离状态。
- 需要**持久化与断点续跑**（长任务、失败恢复）。
- 需要 **Human-in-the-loop**（审批、人工改状态）。
- 需要对流程**精细控制与可观测**（每个节点的输入输出、分支条件可追踪）。

补充：新版 LangChain 的 Agent 实现底层本身就基于 LangGraph，所以两者不是对立关系，而是不同抽象层。

### 9. RAG 全流程讲一遍，文档切片为什么要有 overlap，chunk 太大太小各有什么坑

**参考答案**

RAG 分离线和在线两段：

- **离线**：文档解析（PDF/表格/图片/OCR）→ 清洗 → 切片 → 向量化（Embedding）+ 建关键词索引 → 写入向量库并保存元数据。
- **在线**：用户问题（可先改写/拆分）→ 召回（向量 + 关键词等多路）→ 融合 → 重排 → 组装 Prompt（带引用来源）→ LLM 生成 → 后处理（引用校验、安全审核）。

overlap 的原因：切片边界可能把一个完整语义（一句话、一段推理、一个表格说明）切断，导致任何一个 chunk 都不完整；让相邻 chunk 有一小段重叠，能保留边界处的上下文连续性，降低关键信息被切断而召回不到的概率。代价是索引变大、可能召回重复内容，需要去重。通常按结构（标题、段落）优先切分，再用 overlap 补充。

chunk 大小的坑：

- **太大**：一个 chunk 混入多个主题，向量被"平均化"，检索精度下降；塞进 Prompt 占用大量 token，噪声多，还可能触发"中间丢失"（lost in the middle）。
- **太小**：语义不完整、缺少上下文，召回的片段无法独立回答问题；chunk 数量多，索引和检索成本上升。

常见改进：按语义/结构切分、父子 chunk（小块检索、返回父块）、为 chunk 附加标题路径等上下文。

### 10. 多路召回你做过哪几路(向量、BM25、SQL、图谱、重排)，各路结果怎么融合打分

**参考答案**

常见几路：

- **向量召回**：语义相似，解决同义改写。
- **BM25/关键词召回**：精确匹配专有名词、型号、代码、编号。
- **SQL/结构化召回**：问题可转成查询时（text-to-SQL），适合指标、统计类。
- **知识图谱召回**：多跳关系、实体关联。
- **重排（Rerank）**：严格说不是召回路，而是融合后的精排阶段。

融合方式：

1. **RRF（Reciprocal Rank Fusion）**：只用排名，不依赖各路分数尺度，`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60，简单稳健，是首选的起点。
2. **加权分数融合**：各路分数先归一化（min-max、z-score）再按权重相加；因为向量余弦和 BM25 分数分布完全不同，不归一化直接相加是错的。
3. **学习式融合**：用点击/采纳数据训练 LTR 模型或调权重。
4. 融合后取 top-N（如几十条）交给 Cross-Encoder 重排，再截取 top-k 进 Prompt。

```python
def rrf(rank_lists: list[list[str]], k: int = 60, weights: list[float] | None = None):
    weights = weights or [1.0] * len(rank_lists)
    scores: dict[str, float] = {}
    for w, ranks in zip(weights, rank_lists):
        for i, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + w / (k + i)
    return sorted(scores, key=scores.get, reverse=True)
```

### 11. 向量检索和关键词检索各自适合什么语料，为什么生产上大多搞混合检索

**参考答案**

- **向量检索**适合自然语言描述、同义/改写多、用户表达与文档用词不一致的语料（FAQ、说明文档、对话）。它按语义匹配，但对精确字符串、罕见专有名词、型号、数字、代码标识不敏感，也受 Embedding 模型领域适配程度影响。
- **关键词检索（BM25 等倒排）**适合术语固定、需要精确命中的语料（产品型号、法规条文号、API 名、日志、代码）。它可解释、速度快、不依赖模型，但无法处理同义词和语义改写，用词不同就召不回。

生产上用混合检索，是因为两者的失败模式互补：向量补语义泛化，BM25 补精确匹配，单一方式总会有一类问题召不回。混合后召回率明显更稳，再通过 RRF 或加权融合 + 重排获得最终结果。同时还需要元数据过滤（权限、时间、类型）作为召回前置条件。

### 12. Reranker 加在哪一层，不加直接把向量 top-k 喂模型会有什么问题

**参考答案**

Reranker 加在**召回（含多路融合）之后、Prompt 组装之前**，是两阶段检索的第二阶段：召回阶段追求高召回，用快速的双塔/倒排取几十到上百条候选；重排阶段追求高精度，用 Cross-Encoder 把问题和每个候选拼在一起联合打分，再取 top 少量（如 5 到 10 条）送入模型。

不加重排直接用向量 top-k 的问题：

- 双塔向量把问题和文档分别编码，只比较向量相似度，交互浅，排在前面的不一定最相关，相关片段可能排在后面被截断丢掉。
- 为保证召回，k 不得不开大，Prompt 里混入大量噪声，token 成本和延迟上升，模型还容易被干扰、出现"中间丢失"，导致答非所问或幻觉。
- 多路融合后分数不可比，缺少统一的相关性判断。

代价与权衡：Cross-Encoder 要对每个候选做一次前向计算，延迟随候选数线性增加，因此候选数要控制，可以做批处理、缓存，或选用轻量重排模型。

### 13. Java 侧你用 SpringBoot 怎么包一层 Agent 调用接口，线程池和异步回调怎么处理

**参考答案**

Java 侧通常作为业务网关/BFF，通过 HTTP（或 gRPC）调用 Python 的 Agent 服务，并把结果流式或异步返回给前端。

做法：

1. **同步接口**：简单场景用 `WebClient`/`RestClient`，配置连接、读取超时，调用失败重试需要幂等。
2. **流式接口**：用 `SseEmitter` 或 WebFlux 的 `Flux<ServerSentEvent>`，把 Python 的 SSE 转发给前端；注意设置 emitter 超时，并在 `onCompletion/onTimeout/onError` 中清理资源。
3. **长任务异步化**：提交任务后立即返回 `taskId`，后台执行，前端轮询、WebSocket 或回调获取结果；失败可用 MQ 重试。
4. **线程池**：为 Agent 调用单独配置有界的 `ThreadPoolTaskExecutor`（核心数、最大数、有界队列、拒绝策略），与普通业务线程池隔离，避免长耗时调用拖垮主线程池；`@Async` 要指定线程池 bean 名。Java 21 可考虑虚拟线程处理阻塞 IO。
5. **异步回调**：用 `CompletableFuture` 组合，设置 `orTimeout`/`completeOnTimeout`，异常通过 `exceptionally/handle` 兜底；回调里要传递链路 ID（MDC 在线程切换时要手动传递）。
6. **保护措施**：限流、熔断（Resilience4j）、超时、降级，并保证请求幂等（请求 ID）。

容易漏的点：无界队列导致 OOM、`@Async` 使用默认线程池、SSE 连接泄漏、线程切换丢失 MDC 和安全上下文。

### 14. Redis 在 Agent 系统里你拿它存过什么(会话、token 限额、checkpoint、限流)，用哪种结构

**参考答案**

Redis 适合存"热数据、需要过期、需要原子计数"的内容：

- **会话上下文/短期记忆**：`List` 或 `Stream` 存近期消息，也可用 `String` 存序列化后的摘要；设 TTL。需要结构化字段时用 `Hash`。
- **Token/调用额度**：`String` + `INCRBY`（原子计数），按用户/日期做 key 并设过期；需要多条件原子判断时用 Lua 脚本。
- **限流**：固定窗口用 `INCR + EXPIRE`；滑动窗口用 `ZSET`（时间戳为 score）；令牌桶用 Lua 脚本实现原子操作。
- **Checkpoint**：LangGraph 有 Redis checkpointer；通常用 `String/JSON/Hash` 存序列化状态，要注意持久化配置和数据体积，重要状态更常放在 PostgreSQL。
- **分布式锁/幂等**：`SET key value NX PX`，防止同一会话并发执行 Agent，用幂等 key 防重复提交。
- **缓存**：Embedding、检索结果、工具调用结果缓存，用 `String` + TTL。
- **异步任务/事件**：`Stream` 支持消费组，可做轻量消息队列。

要点：Redis 默认不保证强持久化，不适合作为唯一的审计或关键状态存储；大 value 要避免，key 要设计过期策略。

### 15. Agent Harness 你怎么定义，没有 harness 层大模型应用会缺哪几块能力(护栏、上下文装配、工具沙箱、trace)

**参考答案**

Harness 可以定义为：包裹在模型外面、让模型能可靠地完成任务的**运行时与控制层**。模型负责"思考和决策"，harness 负责"让这些决策安全、可控、可观测地落地"，公式化理解是 Agent = Model + Harness。

没有 harness 会缺少的能力：

- **上下文装配**：决定每一步给模型看什么——系统提示、历史压缩与摘要、检索结果、工具 schema 的按需裁剪、记忆注入，并控制 token 预算。
- **工具层与沙箱**：统一的工具注册、参数校验、权限控制，危险操作（执行代码、改文件、访问网络）在隔离环境运行，设置超时、资源限额。
- **护栏（Guardrails）**：输入侧的提示注入检测、敏感信息过滤，输出侧的内容审核、格式校验、关键动作的人工审批。
- **循环控制**：最大步数、重复调用检测、预算（token、费用）、失败重试与降级。
- **状态与持久化**：会话、checkpoint、断点续跑。
- **可观测（Trace）**：每步的 Prompt、工具调用、耗时、token、结果可追踪、可回放，支撑排障和评测。
- **评测与回流**：线上 badcase 沉淀成评测集。

没有这一层，模型应用只是"裸调 API"，在稳定性、安全性、成本和可排查性上都无法进入生产。

### 2. 讲你最熟的那个 Agent 项目，画过架构图没，状态放哪、失败怎么回滚

   - 写操作要有幂等 key，失败后用补偿动作（类似 Saga）而不是回滚事务；高风险动作前设人工确认。
   - 状态层面可从最近 checkpoint 回到某个节点重新执行（time travel / 从历史 checkpoint 分叉）。
   - 配合超时、重试、降级兜底路径，以及失败后的告警和 badcase 沉淀。

### 3. LangGraph 的 State 怎么设计，channel 和 reducer 在你项目里怎么用

**参考答案**

State 是图中所有节点共享的数据结构，通常用 `TypedDict` 或 Pydantic 定义。每个字段对应一个 **channel**，节点返回的是对该字段的"更新"而不是整个状态；**reducer** 决定新旧值如何合并：没指定 reducer 则默认覆盖，指定后按规则合并。

设计原则：

- 只放需要在节点间传递或需要持久化的数据，字段保持精简、可序列化（避免放连接、客户端对象）。
- 区分输入、输出和内部状态；大对象（文档全文）放外部存储，State 里只放引用。
- 需要累积的字段必须配 reducer：消息列表用 `add_messages`（按 ID 合并或追加），列表追加用 `operator.add`，也可自定义函数（如去重合并、取最大值）。
- 并行节点同时写同一字段时必须有 reducer，否则会触发并发更新错误。
- 加字段给默认值，为以后迁移兼容留余地，可加 `schema_version`。

```python
from typing import Annotated, TypedDict
from operator import add
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # 消息追加/按 id 更新
    docs: Annotated[list[str], add]           # 并行召回结果累加
    intent: str                               # 覆盖
    step_count: int
    schema_version: int
```

### 4. Checkpoint 用 MemorySaver 还是 PostgresSaver，thread_id 怎么和用户会话映射，中断后怎么续跑

**参考答案**

- **MemorySaver（新版称 InMemorySaver）**：数据存在进程内存，重启即丢，也无法多实例共享，只适合本地开发和测试。
- **PostgresSaver**：生产选择，状态持久化、可多实例共享，需要首次调用 `setup()` 建表；也要注意连接池和 checkpoint 的数据增长，需要清理历史。

`thread_id` 通过 `config={"configurable": {"thread_id": ...}}` 传入，它标识一条状态链。映射方式：一个用户会话对应一个 `thread_id`，通常用会话 ID 直接作为它，或使用 `用户ID:会话ID` 的组合，保证不同用户隔离；同一会话的后续请求使用相同 `thread_id`，就能自动加载上次状态。要在业务层做权限校验，防止用户猜测他人的 thread_id。

中断后续跑：

- 进程崩溃或异常中断后，使用相同的 `thread_id` 以 `graph.invoke(None, config)` 调用，会从最近一个成功的 checkpoint 继续（未完成的那个节点会重新执行，因此节点要幂等）。
- 使用 `interrupt()` 暂停的情况，用 `Command(resume=值)` 恢复。
- 可以通过 `get_state_history` 查看历史 checkpoint，并从某个历史点重放或分叉。

### 5. Human-in-the-loop 在图里怎么落地，什么节点允许人工改 state，改完怎么回到原图

**参考答案**

落地依赖 checkpointer：暂停时状态被持久化，进程可以释放，人工处理后再恢复。

方式：

1. **动态中断**：节点内调用 `interrupt(payload)`，图暂停并把 payload 返回给调用方（展示给审批人）；之后用 `Command(resume=人工输入)` 恢复，`interrupt()` 调用处会返回这个值。
2. **静态断点**：编译时指定 `interrupt_before=[节点]` 或 `interrupt_after=[节点]`，在固定位置暂停。
3. **人工改 state**：用 `graph.update_state(config, 新值, as_node="某节点")`，更新被当成指定节点的输出写入，经过 reducer 合并，之后继续执行就会沿着该节点后面的边往下走。

适合允许人工介入的节点：

- 高风险动作之前（转账、删除、发邮件、改配置）审批或修改参数。
- 计划生成之后，让人确认或编辑计划。
- 模型不确定、置信度低、需要补充信息时。
- 检索结果或草稿需要人工校对时。

容易漏的点：恢复时包含 `interrupt()` 的节点会从头重新执行，所以 `interrupt()` 之前的副作用（写库、发请求）必须幂等或放到中断之后；改 state 要校验字段合法性，并记录审计日志；设置审批超时和过期策略。

### 6. 多 Agent 协作你用的是什么通信模型，A2A 走 HTTP 还是消息队列，鉴权超时幂等怎么处理

**参考答案**

常见通信模型：

- **同进程共享状态（图内多节点/子图）**：Supervisor 模式、Handoff（交接）、Swarm；简单、延迟低，通过共享 State 通信。
- **跨服务通信**：Agent 作为独立服务，通过协议交互。

A2A（Agent2Agent）是 Google 提出的开放协议，基于 HTTP，用 JSON-RPC 2.0 通信，支持 SSE 流式和异步任务，Agent 通过 Agent Card 暴露自身能力、认证方式等信息。因此 A2A 协议本身走 HTTP；但在自建系统里，长耗时、需要削峰和可靠投递的场景也可以走消息队列，二者按场景选择：短交互、需要流式反馈用 HTTP/SSE，长任务、可异步、需要重试和解耦用 MQ。

工程处理：

- **鉴权**：服务间使用 OAuth2/JWT 或 mTLS，按 Agent 身份授权最小权限；调用链中传递用户身份，避免越权（confused deputy）。
- **超时**：每次调用设超时和整体 deadline，并向下游传递剩余时间；超时后取消并降级。
- **幂等**：每个请求/任务带唯一 ID（task ID / idempotency key），接收方去重，重试不会重复执行副作用；结果可按 ID 查询。
- **其他**：重试用指数退避加抖动、熔断、限制调用深度防止 Agent 之间循环调用、链路追踪 ID 贯穿全链路。

### 7. 意图识别和多 Agent 路由怎么配合，意图分错时下游 Agent 怎么拒绝或反问

**参考答案**

意图识别是路由的输入：先识别意图（和置信度、抽取的槽位），再由路由器把请求分发给对应的专家 Agent 或工作流。路由可以是规则映射，也可以由 Supervisor（LLM）在意图基础上做二次决策。

意图分错的防御要做成多层：

1. **路由层看置信度**：低于阈值或 top1/top2 差距小时，不直接分发，转为反问澄清或交给通用 Agent。
2. **下游 Agent 自检**：每个 Agent 在入口根据自己的能力边界（职责描述、必需槽位）判断请求是否属于自己；不属于时返回结构化的拒绝结果（如 `{"status": "out_of_scope", "reason": ...}`），而不是硬答。
3. **重路由**：图里设置条件边，收到拒绝后回到路由节点，排除已尝试的 Agent 重新选择，并限制重路由次数避免循环。
4. **信息不足时反问**：缺少必需槽位时，用 `interrupt` 或直接返回追问，让用户补充。
5. **兜底与回流**：最终兜底为通用回答或转人工；分错的样本进入标注和评测集，持续优化路由。

### 8. Agentic RAG 和传统 RAG 区别，你项目里检索子问题改写、召回自省、矛盾过滤是怎么串的

**参考答案**

传统 RAG 是固定的线性流程：检索一次、生成一次，检索由流水线触发，模型没有决策权。Agentic RAG 把检索变成 Agent 可调用的工具，由模型决定是否检索、检索什么、检索几次、结果不够好时是否改写重搜，是"带决策与反馈的循环"，更适合复杂、多跳、需要综合多源的问题，但延迟和成本更高。

一种典型的串联（可按项目实际情况调整）：

1. **子问题改写/拆解**：把复杂问题拆成多个可独立检索的子问题，并做指代消解、关键词补全。
2. **并行检索**：对每个子问题走多路召回 + 重排。
3. **召回自省（评估）**：让模型或评分器判断召回内容是否足以回答（相关性、完整性）；不足则改写查询、换检索路径或扩大范围后重新检索，限制最大轮数。
4. **矛盾过滤**：比较不同来源的片段，按来源可信度、时间新旧、版本过滤冲突证据；无法裁决的冲突在答案中如实说明，不要硬合并。
5. **生成与引用校验**：基于保留的证据生成，要求引用来源，并校验答案是否被证据支持（防幻觉）。

用 LangGraph 实现时，这些步骤对应节点，"自省不足 → 回到改写"是条件边形成的循环。

### 9. 多路召回里文本向量、表格向量、图片向量权重怎么定，有没有用线上点击或采纳数据回灌调权

**参考答案**

权重不能拍脑袋，通常分阶段确定：

1. **冷启动**：先用 RRF（不依赖分数尺度）或等权，再在一个人工标注的离线评测集上做网格搜索或贝叶斯优化，按 Recall@k、MRR、nDCG 选权重。
2. **按查询类型动态调权**：先用意图/查询分类判断问题偏文本、数值表格还是图像（例如问"某指标是多少"偏表格，问"外观"偏图片），不同类型使用不同权重，比全局固定权重更有效。
3. **注意分数不可比**：不同模态的向量来自不同 Embedding 模型，分数分布不同，需先归一化（或只用排名）再加权。
4. **线上数据回灌**：采集点击、采纳、复制、点赞/点踩、追问（纠正）等信号，构造偏好数据，用来重新调权或训练融合/重排模型（Learning to Rank）。

回灌要注意的偏差：位置偏差（排前面的更容易被点）、采纳不等于正确（用户可能没发现答案错），需要用去偏方法或采样人工校验；调权后要通过离线评测 + 灰度 A/B 验证，再全量上线。

### 10. RAG 答非所问时你的排查顺序，从召回集、chunk、prompt 到生成分别怎么定位

**参考答案**

原则：先判断"证据有没有、对不对"，再判断"模型有没有用好"，从上游往下游查，每一步都用 trace 看实际中间产物。

1. **先看问题本身**：是否有指代不清、多轮上下文缺失，需要改写；意图是否分错。
2. **召回集**：看 top-k 里是否包含正确答案片段。若没有，则为召回问题——检查 Embedding 是否适配领域、是否缺少关键词路、元数据过滤是否误杀、索引是否包含该文档。用评测集的 Recall@k 量化。
3. **chunk**：答案在库里但召不回，检查切片——是否被切断、chunk 太大稀释语义、表格或图片解析丢失、缺少标题上下文。
4. **重排与截断**：召回里有但没进最终 Prompt，说明重排或 top-k 截断有问题。
5. **Prompt 组装**：正确证据已在 Prompt 中，检查顺序（中间丢失）、长度是否被截断、指令是否冲突、是否要求"仅依据资料回答"。
6. **生成**：证据和 Prompt 都没问题仍答错，才是模型问题——温度、模型能力、是否需要换更强模型、是否需要引用校验和拒答策略。

每一步要把问题归类到召回、排序、上下文、生成，再对应优化，避免盲目改 Prompt。

### 11. 工具太多怎么管，工具路由分几层，schema 全发会出什么问题，怎么按意图动态裁剪

**参考答案**

工具太多时，全部 schema 发给模型会带来：占用大量上下文（token 成本和延迟上升）、模型选择困难导致选错工具或参数幻觉、相似工具互相干扰、也扩大了安全暴露面。

管理做法：

- **统一注册中心**：每个工具有名称、清晰的描述、参数 schema、分类标签、权限、超时和成本等元信息，版本化管理。
- **分层路由**：
  1. 第一层：按意图/领域选择工具组或专家 Agent（如查询类、操作类）；
  2. 第二层：在组内，通过向量检索工具描述（工具检索）或规则筛选出 top-N 候选；
  3. 第三层：由模型在少量候选中做最终选择并生成参数。
- **动态裁剪**：根据意图、用户权限、当前上下文、前置条件，只下发相关的工具 schema；也可以先提供精简的工具目录，选中后再加载完整 schema（按需加载）。
- **工具设计本身**：合并相近工具、描述写清适用边界和互斥关系、参数尽量简化。
- **评测**：用工具选择准确率评测裁剪策略，避免裁剪过度导致漏掉需要的工具。

### 12. Tool 执行失败分哪几类（网络、参数、业务、超时），每类在 LangGraph 里走哪条边

**参考答案**

按失败类型采取不同策略，核心是区分"可重试"与"需要模型修正"与"应该终止"。

- **网络类错误**（连接失败、5xx、限流）：瞬时可恢复，节点内或条件边走**重试**（指数退避加抖动，限制次数）；重试耗尽则走降级或备用工具边。LangGraph 节点可配置 `RetryPolicy`。
- **参数类错误**（schema 校验失败、参数不合法）：重试没用，需要模型修正。把具体错误作为 tool 消息回写，边回到 **Agent/LLM 节点**让其重新生成参数，限制修正次数。
- **业务类错误**（余额不足、无权限、资源不存在）：属于确定性结果，不应重试。把结果回传给模型，由它向用户解释或换方案；涉及权限则走拒绝边，必要时进入人工处理（interrupt）。
- **超时类错误**：区分只读与写操作——只读可以重试一次；写操作先查询状态确认是否已执行（幂等 key），避免重复副作用；仍失败则走降级或异步查询边。

通用设计：工具节点返回统一的结构化结果（`ok`、`error_type`、`retryable`、`message`），由条件边读取 `error_type` 做路由；全局设置最大步数和重试预算，避免死循环；所有失败写入 trace。

### 13. MCP、Function Calling、Skill、Tool 四者关系，你们项目里 Skill 化收敛了哪些链路

**参考答案**

- **Tool（工具）**：概念层，指 Agent 可以调用的一个能力（查询、执行、检索等）。
- **Function Calling**：模型层的机制，模型以结构化格式表达"我要调用某个工具及参数"，是模型调用 Tool 的方式。
- **MCP（Model Context Protocol）**：Anthropic 提出的开放协议，用 JSON-RPC 标准化 Agent 应用与外部工具/资源/提示模板服务之间的连接，传输方式有 stdio 和 Streamable HTTP。它解决的是"工具怎么被统一发现、接入和调用"，工具通过 MCP Server 暴露，应用侧转成 Function Calling 的 schema 给模型。
- **Skill**：Anthropic 提出的 Agent Skills，一个包含 `SKILL.md`（说明与流程）以及可选脚本、资源的文件夹，采用渐进式披露：平时只加载名称和描述，任务相关时再加载完整指令。它封装的是"某类任务的做法和领域知识"，而不仅是单个接口。

关系：Skill 封装流程知识（可内部调用多个工具），MCP 是接入工具的标准协议，Function Calling 是模型发起调用的机制，Tool 是被调用的对象。

"项目里 Skill 化收敛了哪些链路"属于个人经历，回答时可以讲：把重复出现、步骤固定、依赖领域规范的流程（如某类报告生成、数据查询加整理、标准化排障）从长 Prompt 和散落的工具调用中抽出，沉淀为 Skill，好处是复用、可版本化、按需加载降低上下文占用、行为更稳定；只讲你真实做过的链路。

### 14. AI 编程场景下 harness 怎么约束模型不漂移到项目规范，Cursor/Claude Code 的 hooks 你接没接

**参考答案**

AI 编程中模型"漂移"指的是越写越偏离项目约定。Harness 靠"软约束 + 硬约束 + 反馈闭环"来管：

- **软约束（告诉模型）**：项目规范文件，如 `CLAUDE.md`、`AGENTS.md`、Cursor 的 `.cursor/rules`，写明目录结构、命名、技术栈、禁止事项、测试方式；按路径作用域加载，保持精简。
- **硬约束（拦截与校验）**：用 hooks 在关键事件执行确定性脚本。Claude Code 的 hooks 有 `PreToolUse`、`PostToolUse`、`UserPromptSubmit`、`Stop` 等事件，在 `settings.json` 中配置，可以在调用前拦截危险命令（脚本返回特定退出码即可阻止并把原因反馈给模型），在编辑后自动运行格式化、lint、类型检查，在结束前强制跑测试。Cursor 也提供 hooks（`hooks.json`）用于在 agent 事件前后运行脚本。
- **权限与沙箱**：限制可读写的路径、可执行的命令白名单。
- **反馈闭环**：把 lint、类型检查、测试结果回传给模型自动修复，作为"完成"的客观标准，而不是靠模型自述。
- **上下文管理**：任务拆小、使用计划模式、必要时新开会话避免上下文污染。

是否接过 hooks 属于个人经历，如实回答；没接过可以讲清设计思路，例如"编辑后自动 lint + 提交前跑测试"这类最小落地方案，不要编造。

### 15. MySQL 存 Agent 审计日志和会话元数据，表怎么设计，热点会话怎么避免行锁

**参考答案**

表设计思路：

- **会话表 `session`**：`id`（主键）、`user_id`、`title`、`status`、`created_at`、`updated_at`、`ext`（JSON）；索引 `(user_id, updated_at)` 用于列表查询。
- **消息/步骤表 `message`**（或 `agent_step`）：`id`、`session_id`、`seq`（会话内序号）、`role`、`content`、`tool_name`、`token_in/out`、`latency_ms`、`trace_id`、`created_at`；索引 `(session_id, seq)`。
- **审计表 `audit_log`**：`id`、`trace_id`、`user_id`、`action`、`resource`、`request/response 摘要`、`result`、`created_at`；按时间分区。

设计原则：审计日志**只追加、不更新**；大文本（完整 Prompt、响应）放对象存储或日志系统，表里存摘要和引用；敏感信息脱敏；按时间分区或分表，冷数据归档；主键用趋势递增的 ID（雪花或自增）避免页分裂。

热点会话行锁问题：同一会话并发更新同一行（如每条消息都更新 `session.updated_at`、消息计数）会造成行锁排队。避免办法：

- 用追加写入代替更新：消息只做 INSERT，不去更新会话行。
- 计数、最后活跃时间放 Redis，定期批量落库，或只在会话状态变化时更新。
- 同一会话的请求在应用层串行化（按 session 加分布式锁或使用队列分区），也避免了状态竞争。
- 需要更新时用短事务，尽量走主键或索引更新，避免长事务和不走索引的更新锁范围扩大；会话内序号用 Redis `INCR` 或在事务里一次获取，不要在大事务里持锁。
- 乐观锁（版本号）处理少量冲突。

### 16. Kafka 或 RocketMQ 在 Agent 系统里你拿它解耦过什么（异步工具执行、评测回流、badcase 入库）

**参考答案**

MQ 适合"不需要同步返回、需要削峰、需要可靠投递、多个消费者"的场景，在 Agent 系统里常见：

- **异步工具执行**：耗时长的工具（生成报告、批量任务、代码执行）投递到队列，Worker 消费执行，完成后通过回调、状态表或推送通知结果，主链路不阻塞。需要幂等消费、重试和死信队列。
- **评测回流**：线上对话的 trace、用户反馈（点赞/点踩/纠正）异步写入队列，下游消费者落入数据湖、触发自动评测打分，不影响主链路延迟。
- **badcase 入库**：低评分、触发护栏、工具失败、用户纠正的样本发消息，由消费者去重、打标签并写入标注库，再进入评测集或训练数据。
- **审计与日志**：审计日志异步落库，避免主链路被日志写入拖慢，同时满足不丢。
- **限流削峰与多 Agent 解耦**：请求高峰时排队，Agent 之间通过事件通信。
- **索引更新**：文档变更事件触发切片、向量化、写入索引的异步流水线。

关键点：消息要带唯一 ID 做幂等消费（至少一次投递会重复）；失败重试加死信队列；同一会话的消息需要保序时用会话 ID 做分区 key（Kafka）或顺序消息（RocketMQ）；注意积压监控和消息体大小。

### 2. 你带过 Agent 方向的小组没，怎么把一个 Demo 项目推到生产，里程碑怎么拆

**答题思路**

先如实说明自己的角色（带小组、技术负责人、或虽没带但牵头过模块），不要虚构团队规模。再给出一个可复用的里程碑框架：

1. **明确目标与验收标准**：业务价值、成功指标（准确率、采纳率、延迟、成本），先建立一个小型评测集，这是后续一切迭代的基准。
2. **Demo 验证（可行性）**：用最小链路证明场景可行，同时暴露主要风险（幻觉、工具误调、延迟）。
3. **工程化补齐**：流式输出、状态与会话持久化、鉴权与权限、超时重试降级、限流、成本配额。
4. **质量与安全**：评测体系（离线集 + 回归）、护栏（注入检测、输出审核）、工具沙箱、人工审批高风险操作。
5. **可观测与运维**：trace、指标、告警、日志脱敏、版本与回滚（Prompt、模型、工具均版本化）。
6. **灰度上线**：小流量或内部用户 → 扩量，对比 A/B 指标，设置一键降级（关闭 Agent 回到固定流程）。
7. **持续运营**：badcase 回流、周期性复盘、成本优化。

带团队的部分：拆分模块和接口约定、统一规范（代码、Prompt、评测）、code review、明确算法与工程分工、定期同步风险。

### 3. 当算法同学坚持上更大模型、你作为工程侧担心成本和延迟，怎么拍板选型

**参考答案**

原则：用数据决策而不是立场，把争论变成"在约束下选最优"的问题。

做法：

1. **对齐目标与约束**：先明确业务的质量底线、延迟预算（如首字延迟、总时长）、单次成本上限和并发量，这些约束是共同前提。
2. **同一评测集对比**：在有代表性的评测集上，对比大模型与小模型（或优化后的小模型）的质量、延迟、单次成本，分场景拆开看，而不是整体一刀切。
3. **先优化再升级**：评估能否通过 Prompt 优化、更好的检索、微调、蒸馏、结构化输出等手段让小模型达标；如果瓶颈在检索或工具，换大模型也解决不了。
4. **分层路由**：简单请求走小模型，复杂请求或小模型低置信度时升级到大模型（级联/路由），兼顾成本和效果；结合缓存、投机解码、量化等降低成本。
5. **算账**：用"质量提升带来的业务收益"与"增加的成本和延迟"对比，计算每次请求的边际收益。
6. **小范围验证与可回退**：灰度上线，监控线上指标，保留切换和回退能力，模型版本通过配置化管理。

拍板时的态度：尊重算法对效果的判断，工程侧提供成本延迟的数据与可行路径，达成"可度量、可回退、可演进"的共识。

### 4. Agent 线上出问题（无限循环、工具误调、答错但用户已采纳）你怎么定级和复盘

**参考答案**

**定级**：按"影响面 × 严重度 × 是否有不可逆后果"来分级，例如：

- **高级（P0/P1）**：有不可逆副作用或安全/合规后果（工具误调导致误删、误转账、泄露数据），或大面积服务不可用。需要立即止血（关闭对应工具或 Agent、降级为固定流程）、通知相关方。
- **中级**：无限循环造成成本飙升或超时、局部用户受影响，需要限流或熔断并尽快修复。
- **低级/质量问题**：答错但无实际损失，进入 badcase 流程。
- "答错但用户已采纳"要特别重视：用户没有发现错误，说明采纳率这个指标会掩盖问题，要根据业务风险评定，涉及决策、资金、合规的按高级处理，并考虑回溯通知受影响用户。

**止血**：开关降级、限流、回滚版本（Prompt/模型/工具版本）、拦截问题工具。

**复盘流程**：

1. 用 trace 还原完整链路（每步 Prompt、工具调用、参数、结果）。
2. 根因分类：
   - 无限循环：缺少最大步数、重复调用检测，或工具错误信息不明确导致模型反复重试；
   - 工具误调：工具描述有歧义、工具过多、参数缺少校验、缺少权限或确认；
   - 答错被采纳：检索证据缺失或错误、未提示不确定性、缺少引用与拒答机制。
3. 改进措施：循环加步数、预算与重复检测；高风险工具加人工确认和幂等；答案强制引用来源与置信度提示；补强护栏。
4. 把案例加入评测集做回归，上线前验证，必要时增加监控指标和告警。
5. 复盘文档只谈机制不追责，明确负责人和跟进事项。

### 5. 多 Agent 系统怎么评测，离线集怎么造，沙箱跑工具怎么隔离，线上看哪些指标（步数、重试率、纠正率、token 成本）

**参考答案**

**评测分层**：

- **端到端**：任务完成率、答案正确率（LLM-as-judge + 人工抽检校准）。
- **组件级**：路由/意图准确率、工具选择与参数正确率、检索 Recall/MRR、各 Agent 的子任务成功率。
- **轨迹级**：步骤是否合理、有没有冗余调用、是否越权，多 Agent 还要看交接是否正确、有无循环。

**离线集怎么造**：

1. 来源：真实线上日志（脱敏）、人工设计的典型场景、边界与对抗样本（注入、缺失信息、矛盾资料、无答案）。
2. 用 LLM 合成扩充，但要人工审核，避免偏差。
3. 标注：期望的最终答案或检查点、期望的工具调用序列（允许多条合法路径）。
4. badcase 持续回流，形成回归集；版本化管理，每次改动（Prompt、模型、工具）都跑回归。
5. 有副作用的任务用确定性的环境或 mock 来保证可复现。

**沙箱隔离**：工具（尤其代码执行）在容器/gVisor/Firecracker 等隔离环境中运行；限制 CPU、内存、执行时间；网络默认关闭或白名单；文件系统只读或临时目录；使用最小权限凭证，不暴露真实密钥；每次任务环境独立、用后销毁；评测使用的数据与生产隔离。

**线上指标**：

- 效率：平均步数、P95 步数、端到端延迟、首字延迟。
- 稳定性：工具失败率、重试率、超时率、触发最大步数/循环的比例。
- 质量：用户纠正率（追问、改写、重新生成）、点赞/点踩、采纳率、转人工率，以及抽样评测得分。
- 成本：每任务 token 用量与费用、工具调用次数。
- 安全：护栏触发率、拒答率。

要把这些指标按版本、场景、Agent 拆开看，并设置告警。

### 6. LangGraph 状态升级改了字段，老 checkpoint 反序列化失败你怎么迁移

**参考答案**

先预防，再迁移。

**预防**：

- State 里只存简单可序列化的数据（基础类型、dict），避免直接存自定义类实例，因为类路径或字段变化会导致反序列化失败。
- 新增字段给默认值或可选；尽量"新增而不是改名或改类型"（向后兼容）；State 中加 `schema_version`。
- 变更先做兼容：新代码同时能读旧字段，再逐步淘汰。

**迁移方案**：

1. **读时兼容（惰性迁移）**：在图入口加一个迁移节点，检查 `schema_version`，对旧版本状态做转换（字段改名、补默认值、类型转换），写回新版本；这样老 thread 在下次续跑时自然升级。
2. **离线批量迁移**：写脚本遍历活跃 thread，用 `get_state` 取出旧状态，转换后通过 `update_state` 写入新 checkpoint；如果旧数据已无法被新代码反序列化，则直接在数据库层（如 PostgreSQL 表里的序列化内容）读取原始数据转换，或用保留的旧版本代码读取后再导出。
3. **新旧并行（蓝绿）**：新版本使用新的 `thread_id` 命名空间，老 thread 继续由旧版本代码处理直到结束，不再接收新会话；适合状态变化大的升级。
4. **放弃长任务状态**：对已完成或价值低的会话，只保留消息历史（单独存储在业务库），新会话从历史重建状态，而不迁移 checkpoint。

**保障**：迁移前备份 checkpoint 表；先用生产数据副本做演练；灰度升级；保留回滚路径；清理过期 checkpoint，减少迁移量。

### 7. 寒武纪 MLU 上部署推理和你之前用的 NVIDIA 栈差异在哪，Agent 调用推理服务时怎么屏蔽底层硬件差异

**参考答案**

我对 MLU 的了解有限，下面讲通行的对应关系，具体版本和细节以官方文档为准。

**差异（概念对照）**：

- **软件栈**：NVIDIA 是 CUDA（编程模型）、cuDNN/cuBLAS、NCCL、TensorRT；寒武纪是 Neuware 软件栈，包括运行时 CNRT、算子库 CNNL、通信库 CNCL、推理引擎 MagicMind，编程语言是 BANG C，对应 CUDA C。
- **框架适配**：PyTorch 在 NVIDIA 上原生支持 `cuda` 设备；在 MLU 上通过 `torch_mlu` 插件，使用 `mlu` 设备；推理框架（如 vLLM）需要对应的适配版本。
- **算子覆盖与精度**：MLU 的算子库覆盖度、自定义算子（需要用 BANG 重写或适配）、混合精度和量化支持情况与 CUDA 生态不同，迁移时要验证算子是否缺失、数值精度是否一致、性能是否达标。
- **生态与工具**：监控、调试、profile 工具不同（如 `cnmon` 对应 `nvidia-smi`），社区资料和第三方库适配相对少，容易遇到版本匹配问题（驱动、Neuware、框架版本强耦合）。
- **模型迁移工作**：通常需要模型转换/编译、校验精度、调优 batch 和并行策略（多卡通信走 CNCL）。

**Agent 侧屏蔽硬件差异**：

1. **推理服务抽象成统一接口**：对外暴露 OpenAI 兼容的 HTTP API（chat/completions、embeddings、流式、工具调用），Agent 只依赖这个协议，不感知底下是 MLU 还是 GPU。
2. **适配层/网关**：在推理服务前放一层网关，负责模型路由、负载均衡、限流、重试和多后端切换（MLU 集群、GPU 集群、云端 API 可互为备份）。
3. **配置驱动**：模型名、后端地址、能力（是否支持工具调用、上下文长度）放在配置中心，不写死在 Agent 代码里。
4. **能力差异显式化**：不同后端对结构化输出、工具调用格式、最大上下文的支持可能不同，用能力声明和适配器处理，并通过统一的一致性测试集验证（相同 Prompt 下的输出质量、延迟、吞吐）。
5. **容器化与镜像**：把驱动、运行时、框架依赖打包在镜像里，部署用 K8s 的设备插件调度。

### 8. Harness 工程化你做到哪一层了：上下文装配、工具沙箱、注入检测、输出审核、成本配额分别怎么落

**答题思路**

这是个人经历题，先如实说明自己落地到哪一层，再用下面的通行做法展开，没做过的部分讲设计思路并明确说明，不要夸大：

1. **上下文装配**：系统提示 + 历史（超长时滚动摘要或裁剪）+ 检索结果 + 按意图裁剪后的工具 schema + 记忆；有 token 预算分配，优先级明确，关键指令放在不易被截断的位置。
2. **工具沙箱**：工具统一注册和权限分级；代码执行等高风险工具跑在容器级隔离环境，限制资源、网络和文件系统，使用最小权限凭证；写操作要幂等、高风险要人工确认。
3. **注入检测**：区分可信指令与不可信内容（用户输入、检索文档、网页、工具返回）；对不可信内容做分隔标记，不赋予指令权限；规则 + 分类模型检测；关键原则是"即使被注入，也无权做危险动作"，所以靠权限最小化和确认机制兜底，不能只靠检测。
4. **输出审核**：格式校验（schema）、敏感信息与合规过滤、引用/事实性校验、敏感操作的二次确认；不通过时重试、改写或拒答。
5. **成本配额**：按用户、租户、会话设置 token 与调用次数额度（Redis 原子计数），单任务设最大步数和 token 预算，超限降级到小模型或终止；用量可观测、告警，并有账单归集。
6. **贯穿所有层**：trace 与评测回流，让每一层的拦截情况可度量、可优化。

讲述顺序建议：先说自己做到的层数和一个真实的落地案例，再补充认知，体现"知道完整图景、做过关键部分"。

### 9. 最近半年你跟过哪些 Agent 方向的新东西（LangGraph 新版、MCP、Agent2Agent、Claude Code 类 harness），哪个你真跑过

**答题思路**

重点是诚实，并体现判断力，不要为了显得全面而编造"跑过"：

1. 先分清三类：真正动手跑过的、读过文档或源码但没落地的、只了解概念的。明确说出哪个是哪一类。
2. 对真正跑过的，用"为什么试 → 怎么用 → 效果与坑 → 是否引入"讲。例如：
   - LangGraph：新版里的 `interrupt` / `Command`、持久化、子图、流式模式，对比旧写法的改进。
   - MCP：自己写过或接过 MCP Server，感受它对工具接入标准化的价值，以及鉴权、安全、工具数量膨胀的问题。
   - A2A：理解它与 MCP 的定位区别（MCP 连工具，A2A 连 Agent），是否做过 demo。
   - Claude Code 类 harness：如何用规范文件、hooks、子 Agent、权限控制来约束编程 Agent。
3. 对没跑过的，说清了解到什么程度、打算怎么验证，比假装更可信。
4. 最后落到"这些东西对我们场景的价值与风险"，体现你不是追热点。

### 10. 如果让你从零搭一套寒武纪内部的 AI Agent 全栈开发框架，分层怎么划，哪些自研哪些接开源

**参考答案**

建议分层（自下而上）：

1. **模型与推理层**：统一的推理网关（OpenAI 兼容接口），后端可接 MLU 集群、GPU、外部 API；做路由、限流、降级、缓存；Embedding 和重排模型同样通过网关提供。
2. **工具与连接层**：工具注册中心（元信息、权限、版本）、MCP 客户端/服务端适配、代码沙箱、内部系统连接器；统一的错误结构。
3. **知识与记忆层**：文档解析、切片、多路索引（向量库 + 全文检索）、检索融合与重排、短期/长期记忆存储。
4. **编排与运行时层（Harness 核心）**：基于图的编排、状态与 checkpoint、人工介入、多 Agent 协作、上下文装配、循环与预算控制。
5. **治理层**：护栏（注入检测、输出审核）、权限与审计、成本配额、Prompt/模型/工具的版本管理与灰度。
6. **可观测与评测层**：trace、指标、日志；离线评测集、回归、线上评测、badcase 回流。
7. **应用与开发体验层**：SDK/CLI、模板脚手架、可视化调试、各业务 Agent。

**自研与开源的取舍原则**：

- **接开源**（成熟、变化快、非差异化）：编排运行时（LangGraph 等）、向量库（Milvus 等）、MCP 协议、基础的 trace 工具（OpenTelemetry + Langfuse 类）、Embedding/重排基础模型、推理引擎（vLLM 等，在 MLU 上使用适配版本）。
- **自研**（与公司特有环境强绑定、关乎安全与差异化）：推理网关与 MLU 适配、工具注册与权限体系、沙箱与安全治理、内部系统连接器、评测集与评测平台、成本配额与审计、对开源组件的统一抽象层（防止被某个框架锁定）。

关键原则：核心接口（模型、工具、状态存储）自己定义标准，下面可替换实现；先用开源跑通闭环，再按痛点替换；优先投入治理和评测，这决定能否进入生产。

### 11. 你怎么判断一个新技术是值得引入还是过度设计，举一个你劝退过自己的例子

**答题思路**

先给判断框架，再用一个真实例子佐证（不要编造，没有现成例子就选一个你真实评估过的）：

1. **判断框架**：
   - 它解决的是不是我们**当下真实存在的痛点**？有没有度量（成本、延迟、错误率、效率）？
   - 现有方案做不到，还是只是不够优雅？
   - 引入成本：学习、运维、调试、依赖风险、团队接手难度。
   - 成熟度与可退出性：社区、版本稳定性、出了问题能否回退。
   - 先做最小验证（PoC），用同一评测集对比收益，没有明显收益就不引入。
2. **例子结构**（"我劝退自己"）：当时看到什么新东西 → 想解决什么问题 → 做了什么验证 → 发现收益有限或成本过高 → 最终决定用简单方案，以及后来是否被证明正确。
3. 可参考的方向（只在你真实遇到过时才用）：问题本可以用固定工作流解决却想上多 Agent；检索效果差先优化切片和重排，而不是上图谱；简单场景用不到复杂的编排框架。
4. 收尾体现态度：技术服务于问题，保持"先简单、有数据再升级"。

### 12. 学习一个新框架你第一步看源码还是跑官方样例，怎么判断它生产可用

**答题思路**

建议的回答顺序：先跑样例，再带着问题读源码。

1. **第一步跑官方样例**：快速建立整体认知，确认能跑通、API 风格合不合适；同时读文档里的核心概念和设计理念。
2. **带着问题看源码**：不是通读，而是围绕关键问题——状态怎么存、并发和异步怎么处理、错误和重试怎么做、扩展点在哪、序列化格式是什么、有没有隐藏的全局状态。
3. **用自己的真实场景做 PoC**：不要只看官方样例，要在自己的数据和约束下试。
4. **判断生产可用的维度**：
   - 稳定性：版本迭代是否频繁破坏兼容、有没有明确的版本与升级策略、issue 响应情况。
   - 可观测：是否支持 trace、日志、指标。
   - 可靠性：超时、重试、取消、持久化、故障恢复。
   - 性能与资源：压测并发、延迟、内存。
   - 安全：依赖风险、权限、数据处理。
   - 可替换性：核心逻辑是否被框架深度绑定，能否抽象一层隔离。
   - 社区、文档和团队的维护能力。
5. 结论方式：给出"可用 / 有条件可用 / 不推荐"，并写清风险和回退方案。

## HR 面

### 1. 自我介绍

**答题思路**

HR 面的自我介绍更关注稳定性和匹配度，时间 1 到 2 分钟：

1. 基本信息：学历背景、工作年限、当前或上一份工作的职责，简洁带过。
2. 经历主线：技术成长路径，做过的项目和你的贡献，不要过于技术细节化。
3. 与岗位的契合：为什么这个岗位适合你（Agent 全栈、Python + Java 的结合）。
4. 个人特质：沟通协作、学习能力、责任心，用一两个具体事例体现。
5. 收尾表达对这个机会的兴趣。

### 2. 为什么看寒武纪这个 AI Agent 全栈岗，对芯片公司做应用层怎么看

**答题思路**

回答要体现"有思考而不是随便投"，避免空泛夸赞或编造对公司的具体了解：

1. **岗位匹配**：自己的经历（Agent、RAG、全栈工程化）和岗位要求对得上，想把能力用在更深入的场景。
2. **对芯片公司做应用层的看法**：
   - 应用层是芯片价值落地的出口，能验证算力在真实业务中的效果。
   - 内部做 Agent 应用既能提升研发和运营效率，又能反向暴露推理栈的问题（性能、兼容性、易用性），形成"软硬件协同"的闭环。
   - 国产算力生态需要有人把上层应用跑通、降低迁移门槛，这是有价值也有挑战的事。
3. **个人发展**：希望接触从应用到推理服务、底层硬件适配的完整链路，拓宽视野。
4. 只说你确实了解到的公司信息，不确定的可以表示"希望入职后进一步了解"。

### 3. 你觉得自己最不能被替代的是哪一块，Python 工程、Java 后端还是 Agent 编排

**答题思路**

不要三个都说"最强"，选一个主轴并给出证据：

1. **先选一个**：根据自己的真实优势选择，例如"Agent 编排 + 工程化落地"，因为这是岗位的核心。
2. **给证据**：用具体的做过的事说明——解决过什么难题、带来什么结果（只讲真实数据）。
3. **解释为什么难被替代**：不是会用框架，而是能做取舍，例如状态设计、失败处理、评测和成本控制，这些需要工程经验和对业务的理解。
4. **把另外两项当作加成**：Python 和 Java 的能力让你可以跨前后端和服务边界推进落地，减少沟通成本。
5. **保持谦逊**：说明自己仍在补强的方面，以及如何持续学习（AI 工具会替代重复性编码，而判断和系统设计更重要）。

### 4. 过去项目里和最难搞的同事或算法怎么掰扯下来的

**答题思路**

用 STAR 结构，选一个真实、不涉及人身攻击的分歧：

1. **情境**：分歧是什么（如模型选型、排期、技术方案），各方的出发点是什么——强调双方都有合理立场。
2. **行动**：
   - 先倾听，弄清对方真正关心的点。
   - 把争论转成可验证的问题：用数据、评测或小范围实验说话。
   - 找到共同目标，提出折中方案（分阶段、灰度、可回退）。
   - 必要时拉上相关负责人对齐，而不是私下对抗。
3. **结果**：问题如何解决，后续合作关系如何，团队从中得到什么。
4. **反思**：从中学到什么，比如更早对齐目标、用数据沟通。

避免：抱怨对方、把自己说成永远正确、编造戏剧性故事。

### 5. 薪资预期和目前手头流程

**答题思路**

薪资预期：

1. 先说明你更看重岗位成长和匹配度，薪资希望在合理范围内沟通。
2. 给出基于市场行情、自身经验和当前薪资的区间，而不是一个死数字；也可以先询问岗位的薪资范围再回应。
3. 说明总包的考虑（固定薪资、奖金、期权、福利等）。
4. 保持灵活，表达如果其他方面匹配，薪资可以协商。
5. 不要说谎，也不要虚报当前薪资，有些公司会做背调。

手头流程：

1. 如实说明处于什么阶段（有的在面试中、有的已有进展），不需要透露具体公司和细节。
2. 表达这家公司在你的优先级里的位置，以及你的决策时间节点。
3. 不要夸大"多个 offer"来施压，诚实但保持一定的谈判空间。

### 6. base 接受深圳还是北京，出差和加班怎么看

**答题思路**

1. **base**：根据自己的真实情况回答，明确选择或可接受的范围；说明理由（家庭、生活成本、团队所在地、职业发展），如果两地都能接受就清楚地说出来，如果有顾虑（如搬家时间）可以提前说明，但不要含糊其辞。
2. **出差**：说明可以接受必要的出差（如与硬件、客户、团队的协作），关心频率和形式即可，可以礼貌地询问大致安排。
3. **加班**：表达的态度是"项目关键期愿意投入、为结果负责"，同时重视效率和可持续性；不要说"完全不加班"，也不要显得盲目答应一切，可以说明自己倾向于通过提前规划和提高效率来减少无谓加班。
4. 态度坦诚、不卑不亢，有硬性限制就如实说明。

### 7. 如果这轮过了你最关心入职后前三个月干什么

**答题思路**

按"学习 → 融入 → 产出"的节奏回答，体现主动性和对岗位的理解：

1. **第一个月：熟悉与对齐**：了解团队目标、业务场景、现有架构和代码、开发流程；跟相关同事（算法、推理、业务方）建立联系，搞清楚当前最大的痛点和成功标准。
2. **第二个月：小范围产出**：承担一个范围清晰的任务，尽快交付并验证，例如补齐评测、可观测或某个模块的优化，通过实际交付了解团队标准。
3. **第三个月：独立负责与改进**：独立负责一个模块或链路，提出基于数据的改进建议（如评测体系、成本优化、推理适配的可用性），形成可复用的沉淀。
4. 同时关注对 MLU 推理栈等公司特有技术的学习。
5. 最后可以反问：团队当前最希望新人三个月内解决的问题是什么，体现你对目标对齐的重视。
