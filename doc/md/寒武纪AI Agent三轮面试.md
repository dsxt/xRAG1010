# 寒武纪 AI Agent 三轮面试

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

三面技术面没有一轮是靠背八股能过的。二面的 LangGraph 状态版本化和 HITL 恢复，答浅了会被继续往下压。寒武纪的面试官不是表演式协作：懂就往深里聊，不懂就换方向，不 PUA，也不让你装懂。当时最不爽的是 AI 工作流和 Harness 边界那题，问得很抠字眼；事后看，这题确实能筛掉只会调 Chain 的人。整体偏硬，重点是在国产算力受限的前提下把 Agent 约束住，不让它疯跑，而不是比谁报的框架名字多。

## 一面

### 1. 自我介绍

**答题思路**

控制在一分半到两分钟，按「我是谁 → 做过什么 → 为什么匹配」讲：

1. 一句话交代年限和主线（后端 / Python / Agent 工程），不要从教育经历讲起。
2. 只留一个已经上线的 Agent 项目：谁在用、你负责的链路、结果用你真实有的指标，不报编出来的提升百分比。
3. 点出和岗位重合的能力：意图分流、RAG、状态图编排、工具权限、评测和熔断。
4. 最后一句落到寒武纪：希望在算力受限的前提下把 Agent 做成可控的生产系统。

准备两个追问钩子，例如「低置信度不执行写操作」和「checkpoint 放在 CPU 侧」，把后面的题引到自己写过的部分。

### 2. 讲一个你落过的 AI Agent 项目，重点说清链路而不是堆名词

**答题思路**

「落过」指进过生产，不要讲笔记本 demo。先用一句讲业务约束（谁用、错了的代价、延迟预算），再按一次请求的真实走向讲，名词只在它出现的那一跳里带过：

1. 接入：会话 ID、鉴权、限流，输出是流式还是一次性。
2. 意图：规则、轻量模型、大模型各接哪一段，低置信度是澄清、拒答还是转人工。
3. 编排：状态里有什么，哪条边会循环，哪一步必须人工点头。
4. 工具：只读和写入怎么分开，超时和脏结果怎么回到状态里。
5. 知识：文档怎么切、怎么召回，回答是否强制带引用。
6. 收尾：trace 里能看到哪几样东西，你亲自修过的一次线上失败是什么。

每一跳都讲「输入是什么、输出是什么、失败到哪」。没做的模块直接说没有，不要把框架名连成一条假链路。

### 3. 意图识别在产线里为什么不能只靠大模型分类，轻量模型+规则怎么混用

**参考答案**

产线意图分类要稳定、可审计、便宜。大模型每次分类的延迟和费用都高，输出还会被用户话术带偏，难以给路由签固定时延，也难以解释「为什么这次进了退款」。高频和有副作用的意图必须先被确定性模块接住。

混用按成本从低到高：

1. 规则先处理安全红线和精确口令（退订、停机、确认支付）。命中即生效，不再交给模型改判。
2. 未命中走轻量分类器（fastText 或小 BERT）。它吃标注日志，延迟在毫秒级，并给出置信度。
3. 置信度不够、一句话多意图、或分类器词表里没有的长尾，才调用大模型。输出必须是枚举标签加槽位，由代码校验，不接受自由发挥的类别名。

大模型判过的样本回流成轻量模型的训练集。规则与模型冲突时，写操作以规则为准。置信度要用校准后的分数，裸 softmax 不能直接当概率。

### 4. 意图歧义或低置信度时怎么兜底，举一个真实 bad case

**参考答案**

低置信度的默认动作是不执行，尤其是写入类工具。兜底分三档：槽位补得上就用会话里已确认的值；补不上就只追问一个缺失项；连意图都不清楚就走只读检索或转人工。阈值定在「误执行写操作的代价」上，不追求把每句话都分出去。

典型坏例：用户说「帮我把那个停掉」。会话里同时有一条测试任务和一条生产告警，「停掉」指向不明，分类器的最高分只略高于另一类。若系统仍按最高分调用 `stop_production_alert`，就会误停生产。正确行为是置信度不够或指代槽位为空时，禁止该写工具，反问「停测试任务还是生产告警」。

面试时把坏例换成自己线上的那次，按「原话、错误动作、损失、补上的规则」四句讲完。容易漏的是：追问本身也要限次数，避免澄清循环；用户拒答就结束，不要再猜。

### 5. RAG 切分策略：chunk大小、重叠、按语义还是按结构切，你怎么选

**参考答案**

按文档形态选，不设一个全局字符数。

有标题、列表、代码、表格的文档按结构切，标题路径写进块的元数据，避免召回后不知道这段属于哪一节。结构块仍超长时，再按段落递归下切，并用 token 设上限，上限小于 embedding 模型的最大输入。很多切分器默认按字符计数，中文场景要单独核对。

重叠只覆盖切点上的那句话，常见起点是块长的一成到两成。重叠过大会让同一句重复召回、索引变胖。没有结构标记的长叙述，才用相邻句的向量相似度做语义切分。表格和代码单独成块，不跟正文混切。

用真实问句看命中率来选定稿。小块负责召回、把命中块的父节送进模型，通常比继续调重叠更有效。

### 6. 检索召回粗排后为什么还要cross-encoder重排，重排候选数怎么定

**参考答案**

粗排的双塔模型把查询和文档分开编码，相关度只是两个向量的点积，查询词和文档词之间没有细粒度交互，排在前面的经常只是「主题接近」。Cross-encoder 把查询和段落拼在一起做完整注意力，能区分真正回答了问题的段落和仅仅话题相似的段落。它的代价是每条候选一次前向，向量不能预计算，所以只能放在粗排之后的小集合上。

候选数由延迟预算和评测一起定。粗召回先留下比最终上下文大一个数量级的集合，常见起点是几十条；重排耗时随条数线性增加。交互系统把窗口收到「再加十条，评测集上的命中提升已经盖不住超时」的位置，最后送给生成模型的一般是个位数。不要背固定的 top-K。算力紧时先缩小这个窗口，而不是拿掉重排去省一次调用。

### 7. Agentic RAG 和传统 RAG 的区别，Agent怎么决定查几次、怎么改写 query

**参考答案**

传统 RAG 是固定流水线：检索一次，拼进提示词，生成一次。查哪一路、查几次，在上线前就写死了。

Agentic RAG 把「证据够不够、要不要改写后再查」放进循环。模型看到当前段落支撑不了回答，就产生下一次查询；代码侧的相关性检查通过、达到最大跳数、或 token 预算用尽，循环就停。停止条件写在路由里，不交给模型自己感觉「可以了」。

改写做三件具体的事：用会话状态补上代词所指；把多跳问题拆成当前这一跳的查询；给关键词检索补上编号、报错码这类必须精确命中的词。后一跳可以使用上一跳观察到的实体，但工具原文和网页只能当数据，不能当新的系统指令。

多跳能提高复杂问题的召回，也成倍增加时延。能一次检索回答的问题不要进这个循环。

### 8. LangChain Chain 和 LangGraph 状态机本质区别，为什么复杂 Agent 不用纯 Chain

**参考答案**

Chain 的调用顺序在编写时就定好，上一步的输出当下一步的输入。LangGraph 把一次任务看成状态机：状态是共享数据，节点返回对状态的局部更新，条件边根据状态选择下一个节点，因此可以回到上游。

复杂 Agent 需要四件 Chain 没有的东西：根据工具结果决定要不要再查、失败后换工具、执行前等人审批、进程中断后从中间继续。纯 Chain 没有一等公民的循环和持久化状态，这些只能在链外面再套 `while`，步数、恢复和追踪会散落在业务代码里。

状态图把循环留在图内，出口由代码控制。路径完全固定的任务继续用 Chain 或普通 DAG，不必为了用框架而上状态机。

### 9. LangGraph里State、Node、Conditional Edge 怎么配合做循环决策

**参考答案**

State 是整张图共享的数据。消息列表用 reducer 追加，节点只返回自己改动的字段，框架按字段合并。Node 是普通函数：读状态，返回局部更新。Conditional Edge 是路由函数：读状态，返回下一个节点的名字。

循环的接法是：`agent` 节点写出工具调用；路由看到还有工具调用，就进入 `tools`；`tools` 把观察写回消息，再固定连回 `agent`；`agent` 不再调用工具，或 `steps` 达到上限，路由进入结束。步数只能由节点写进状态，路由只负责读。提示词里的「不要超过 5 步」不是终止条件。

```python
def route(state):
    if state["steps"] >= state["max_steps"]:
        return "end"
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return "end"

# tools 执行完必须回到 agent，循环才闭合
graph.add_edge("tools", "agent")
graph.add_conditional_edges("agent", route, {"tools": "tools", "end": END})
```

`max_steps` 要算进每次工具往返。只限制模型输出的句子数，工具循环仍会停不下来。

### 10. Checkpoint 机制怎么做断点恢复，国产算力受限下状态存哪里

**参考答案**

Checkpoint 在每个超步之后把状态快照存下来，键是 `thread_id` 加上检查点 ID。进程重启或人工暂停后，用同一个 `thread_id` 读回状态，从未执行的节点继续，而不是把整段对话重放一遍。恢复时图要知道下一个节点是谁，所以快照里除了渠道值，还有待执行节点。

状态放在 CPU 侧。持久副本用 Postgres，单机调试可以用 SQLite。Redis 只放当前会话的热数据和锁。工具返回的大对象放对象存储，状态里留引用。MLU 显存留给权重和当前步的 KV cache，不留对话状态。

算力紧时更要存：已用步数、已调用工具、token 预算。否则一恢复就从头再跑，省下的设备时间会在重放里耗掉。写入在编排进程里完成，不把状态张量留在设备上。

### 11. AI Coding 场景里怎么把仓库上下文喂给模型，全量塞还是分层检索

**参考答案**

用分层检索，不把仓库全量塞进窗口。全量既容易超窗口，也会把真正相关的代码淹没在中间，费用还随仓库体积上涨。

每次都带的只有短上下文：仓库约定、当前文件光标附近、编译或测试报错。其外是一层不含函数体的结构图，也就是目录和符号签名。再往外按符号引用、路径和关键词检索，只读命中的文件片段，并沿 import 或调用关系向外扩一层。扩完仍按 token 预算截断。

模型还缺文件时，通过工具分页去读，而不是预取整个库。测试失败和类型报错通常比多检索十个相似文件更有用，应优先放进上下文。生成补丁时只带目标文件的相关区域和它的直接依赖，避免模型改到没被读入、因而也无法核对的文件。

### 12. Claude Code / Codex 类 harness 思路了解多少，agent.md或 skills 怎么用

**参考答案**

这类编程 Agent 里，模型只提出下一步；Harness 负责组装上下文、在沙箱里执行工具、按权限拦截、再把结果送回去。模型不持有仓库的写权限。

题干里的 agent.md，对应仓库根上长期生效的 `AGENTS.md` 或 `CLAUDE.md`。它每次会话都会进入上下文，只写稳定约定：怎么构建、怎么跑测试、哪些目录不能改。文件要短，不把内部 wiki 整份贴进去。

Skills 是按需加载的操作规程，例如一次数据库迁移的步骤和检查项。平时不占窗口，任务匹配时再读入。一直生效的约定放 agent.md，偶尔才用的步骤放 skill。

两边都不写密钥。改完用一条真实任务核对模型是否遵守，而不是只确认文件存在。

### 13. 手撕算法：给一段非结构化日志流，提取出其中的意图标签序列并去重保序(LeetCode 316类似变形，去重保序)

**参考答案**

先按约定格式抽出标签，再求字典序最小的无重复子序列：每个标签保留一次，结果仍是原序列的子序列。这是 LeetCode 316 的做法。若面试官改口说「按第一次出现的顺序」，就改成有序去重，不要用下面的栈。

用单调栈。记录每个标签最后一次出现的位置；当前标签更小，且栈顶之后还会再出现时，弹出栈顶。每个标签最多入栈、出栈一次。设日志长度为 n、标签长度为 L，抽取加去重的时间是 O(n·L)，空间 O(n)。

```python
import re

_TAG = re.compile(
    r"(?:intent\s*[=:]\s*|\[INTENT\s*:\s*)([^\s\]|,;]+)",
    re.IGNORECASE,
)

def extract_intent_tags(log: str) -> list[str]:
    """标签紧跟 intent= / intent: / [INTENT: ，遇到空白、]、逗号或分号结束。"""
    return [m.group(1) for m in _TAG.finditer(log)]

def dedup_preserve_order(tags: list[str]) -> list[str]:
    last = {tag: i for i, tag in enumerate(tags)}
    stack: list[str] = []
    seen: set[str] = set()
    for i, tag in enumerate(tags):
        if tag in seen:
            continue
        while stack and stack[-1] > tag and last[stack[-1]] > i:
            seen.remove(stack.pop())
        stack.append(tag)
        seen.add(tag)
    return stack

def intent_tag_sequence(log: str) -> list[str]:
    return dedup_preserve_order(extract_intent_tags(log))
```

例如标签序列 `pay, ask, pay, cancel`，首次出现顺序是 `pay, ask, cancel`，本算法的结果是 `ask, pay, cancel`。面试时先把这个差别说出来，避免和面试官做的不是同一题。

### 14. Redis 在Agent 系统里存什么，对话历史怎么控长，不把全量历史喂模型怎么设计

**参考答案**

Redis 存热状态，不存审计档案。适合放当前会话的最近几轮、滚动摘要、限流计数、工具幂等键和分布式锁。可回放的全量历史放数据库，大的工具结果放对象存储，Redis 里只留键。

控长按 token，不按消息条数。送给模型的是四段：系统约束、钉住不能被摘要丢掉的事实（身份、尚未完成的写操作）、旧对话的摘要、最近几轮原文。旧的工具回包改成一句话结果。超过预算才触发一次摘要，不要每轮都摘要，否则摘要会慢慢漂掉约束。

热数据用列表或 Stream，并设置 TTL。Redis 重启后允许热窗口丢失，再从数据库装载最近一轮窗口。摘要键和原文键分开，避免一次 `GET` 把全量历史读进提示词。

### 15. 模型调用失败、工具超时、返回脏数据，Agent 循环怎么熔断

**参考答案**

三类失败都写成结构化观察，不能当成事实喂回模型。处理方式分开：

- 模型调用只对超时和 5xx 做有限次退避。输出不符合 schema 时，最多再约束解码一次，然后失败。
- 工具超时就取消调用。读操作可以重试，写操作不自动重试，避免重复下单、重复发送。
- 脏数据通不过 schema 就丢弃正文，观察里只留校验错误；原文进 trace，不进提示词。

循环的熔断写在代码里：最大步数、token 预算、墙钟时间，以及同一工具加同一参数的重复次数。某个依赖连续失败后打开熔断，后续请求直接得到「工具不可用」，由图走到拒答或只读备用路径；半开时只放一个探测。停机时返回已经拿到的部分结果，并写明停在哪一步。

## 二面

### 1. 自我介绍

**答题思路**

二面已经听过项目名字，这次把时间让给架构判断。一两分钟，结构仍是「背景 → 一个上线项目 → 你做过的取舍」：

1. 背景一句带过，不重复一面的流水账。
2. 项目只讲一条主链路，主动点出你做的两处取舍：什么放进状态图、什么保持固定流程；状态存在哪里、怎么恢复。
3. 补一句线上约束：步数、工具权限、评测怎么卡住这条链路。
4. 结尾落到今天能展开的图：分层架构或 HITL，方便面试官往下压。

不要在自我介绍里把 LangGraph、MCP、A2A 的定义背一遍。

### 2. 画一个企业级研发助手 Agent 分层架构：接入层、编排层、工具层、存储层、可观测层

**参考答案**

五层按「谁可以做决定」来分。

- **接入层**：鉴权、租户、限流、`thread_id`、流式输出。这里不规划、不调工具。
- **编排层**：状态图、计划、条件路由、步数和 token 预算、人工中断。下一步只能在这一层决定。
- **工具层**：注册表、参数 schema、MCP 适配、沙箱、超时和幂等。模型不直接碰命令和网络，只提出调用。
- **存储层**：Postgres 放 checkpoint，Redis 放热状态，另外是文档、向量和对象存储。存储不参与路由。
- **可观测层**：用同一个 `trace_id` 串起上面四层的 span、指标和日志，并采样进评测集。

层间契约：编排层只接收工具的结构化结果，不把模型输出拼进 shell；大结果以引用进入状态。可观测层要在第一条请求时就接入。没有 trace，后面的熔断阈值和评测集都没有数据来源。

### 3. Planner 和 Critic 分工，Critic 怎么判断模型幻觉或工具结果不可信

**参考答案**

Planner 把目标变成下一步，并给出工具名和参数。Critic 在动作执行前、以及工具结果回来后，判断这一步能不能信。它只有否决权，不能自己去调工具。

不可信优先用确定性检查：工具状态是不是成功，返回是否通过 schema；回答里的单号、路径、数字能不能在工具原文里找到；写操作有没有超出这次请求的权限。对不上就向状态写入结构化失败，Planner 重试或停止，并限制批评轮数，避免两个模型互相否定。

语义层面的「这段话有没有被原文支持」才用另一次模型调用，而且使用独立提示，不把刚才生成答案的上下文原样送回去自证。同一段生成的自我肯定几乎抓不到幻觉。Critic 自己也会编，所以否决必须落到「引用对不上」或「schema 失败」这种可复核的理由上。

### 4. LangGraph状态序列化版本兼容怎么做，图定义改了老会话怎么迁移

**参考答案**

在途会话钉在它开始时的图版本上；新会话才用新图。不在进程里改一张正在恢复的图。

状态里放 `schema_version`，checkpoint 的元数据里放 `graph_version`。兼容只做三件事：新字段带默认值；字段改了含义就升版本，加载时按版本链跑纯函数迁移；未知的旧字段忽略，缺失的新字段补默认。迁移函数必须幂等，因为同一次恢复可能重复加载。

图的拓扑变了以后，旧快照里的「下一个节点名」可能已经不存在。能映射的做旧名到新名的表；映射不了的线程不要硬恢复，用摘要出的状态在新图上新开一个 `thread_id`。库升级和 schema 升级都在 CI 里用一份真实的旧 checkpoint 做恢复测试。只做序列化兼容、不测「中断在人工节点上的旧会话」，上线后才会发现恢复失败。

### 5. Human-in-the-loop 在 LangGraph 里怎么实现，人多久不响应怎么超时降级

**参考答案**

有两种暂停，恢复语义不同。

`interrupt()` 写在节点内部。执行到这里就把提案写入 checkpoint 并暂停；恢复时使用 `Command(resume=决定)`，该节点会从头再执行，`interrupt()` 这时返回人的决定。因此节点里、`interrupt()` 之前不能有写操作，否则恢复时会执行两次。写工具放到审批通过后的下一个节点。

`interrupt_before=["tools"]` 是在进入该节点之前暂停，恢复后该节点只执行一次，上一个节点不会重跑。适合「参数已经落在状态里，只差执行」的场景。

两种暂停都没有给人计时的时钟。审批写入带截止时间的表，调度器扫描到期的 `thread_id`，用 `Command(resume={"approved": false, "reason": "timeout"})` 恢复。条件边上写死降级：写操作超时一律拒绝；只读查询可以继续，并标明未经人工确认。迟到的同意靠幂等键丢掉，避免超时拒绝之后又执行一次。

### 6. 多 Agent 主流拓扑：Supervisor、群聊、流水线、层级，各自适合什么

**参考答案**

按控制流选拓扑，不按角色名字选。

- **Supervisor**：一个编排者把子任务分给专家，专家之间不直接闲聊。职责清楚、便于限权，适合企业里检索、改代码、跑测试这种边界明确的分工。瓶颈是编排者的上下文会变大。
- **群聊**：共享消息，由选择器决定下一个发言者。适合发散讨论。副作用工具不适合放进来，停机条件弱，出了坏结果也难追到某一次调用。
- **流水线**：固定的专家顺序，例如检索、起草、核对。时延和费用可预期，适合步骤已知的研发流程。中间结果不符合预期时，它不会自己改道。
- **层级**：编排者下面还有编排者。领域很多、需要隔离权限时用。每多一层，延迟和传话失真都增加。

一条系统里可以混用：主路径用 Supervisor 或流水线，只有开放式子问题才短暂进入群聊，并且群聊没有写权限。

### 7. 多 Agent 上下文爆炸怎么治，Agent 间传全量还是传结论

**参考答案**

传结论，不传全量对话。每个 Agent 保持自己的工作记忆；交回父节点的是结构化结果：结论、依据的引用 ID、未完成的约束、失败原因。父节点不把子 Agent 的工具原文再贴进自己的提示词。

共享的只有一块小黑板：任务目标、权限边界、已经确认的事实。子 Agent 按名字读取自己需要的字段。需要追细节时，用引用 ID 回存储层取原文，这是按需展开，不是默认展开。

在每个交接处截断，并给父节点单独设预算。子 Agent 的循环步数不占用父节点的生成窗口，但占用同一笔任务费用，所以子循环也要有步数上限。全量转发看起来信息无损，实际会把无关工具日志、以及工具里夹带的间接指令，一起送进下一个模型。

### 8. A2A和MCP区别，为什么一套系统两个都要

**参考答案**

MCP 解决的是一个 Agent 怎么调用工具和读取数据。工具带 JSON schema，调用是一次请求配一次结果，权限和超时可以卡在这个边界上。

A2A 解决的是一个 Agent 怎么把任务交给另一个 Agent。对方有自己的工具、记忆和权限，用 Agent Card 声明能力，任务有提交、执行中、等待输入、完成、失败这些状态，还可以跨比较长的时间。

只留 MCP：远端 Agent 会被压成一个同步函数，任务状态、中途补输入和长时间运行都无处安放。只留 A2A：每个函数调用都变成一次 Agent 协商，schema 校验、短超时和沙箱会被绕开。

因此工具和数据走 MCP，跨 Agent 的任务委托走 A2A。远端 Agent 的回复仍是不可信文本，回到本系统时要重新经过拦截，不能因为它来自「另一个 Agent」就当系统指令。

### 9. Tool Calling 参数校验和命令注入怎么防，SSRF 在 Agent 里怎么暴露

**参考答案**

参数校验做在执行之前。工具名只能来自注册表，参数按 JSON schema 校验：类型、枚举、长度、`additionalProperties: false`。校验失败就把错误当观察返回，函数不会被调用。

命令注入来自把模型给的字符串拼进 shell。执行使用参数数组，并且 `shell=False`；可执行文件走白名单；工作目录限制在任务目录。模型不提供整行命令，只提供白名单里的子命令和已经校验过的参数。

SSRF 出现在模型能填 URL 的工具上，例如抓取网页、webhook、按链接读文档。工具跑在服务端，能访问用户自己访问不到的地址。攻击话术会写在用户输入或检索到的网页里，让模型去请求 `127.0.0.1`、内网网段或云元数据地址 `169.254.169.254`。

防护是解析 DNS 之后拒绝回环、内网和链路本地地址，每次重定向都重新检查，只允许明确需要的 https 主机，内网能力改成不接受任意 URL 的具名工具。

### 10. 提示注入攻击真实场景，Guardrail在输入输出端分别拦什么

**参考答案**

真实场景分直接和间接。直接注入是用户要求忽略原有规则、导出密钥或调用写工具。间接注入藏在检索到的文档、网页和工具结果里，例如一段隐藏文字要求把上下文发到外部邮箱，或要求改调删除工具。模型分不清数据和新指令，就可能照做。

输入端要拦：用户的越狱和明确禁止的请求；把检索文本、网页、工具结果标成不可信数据，禁止升格成系统指令；超长输入和不该进入日志的密钥。

输出端要拦：复述出的系统提示词、其他租户的数据和密钥；本该拒答却给出的、没有引用支撑的事实；违反输出策略的内容。

只过滤输入输出的文本，拦不住已经发出的工具调用。执行前还要有独立的一层：schema、权限和 SSRF 检查。副作用工具以这层的结论为准，不以模型的「用户同意了」为准。

### 11. Harness 工程三件套 Eval / Trace /Guardrail 分别解决什么，不能只靠 Prompt的原因

**参考答案**

Eval 回答改动之后任务成功率是升还是降。提示词、模型或工具一变，就在固定评测集上重跑。没有这套回归，只能靠抽样感觉。

Trace 回答这一次具体哪一步做了什么：每次模型调用和工具调用的输入输出、耗时、token、错误码。线上的坏例靠它才能变成下一条评测样本。

Guardrail 回答哪些约束模型说了也不算：权限、步数、schema、敏感操作审批。它由代码执行。

提示词三者都替代不了。它不是强制执行，注入可以盖过它；它也不产生可回归的分数，也不留下可回放的步骤。三件套还互相依赖：没有 trace 就做不出真实评测集，没有 eval 就不知道拦截是否误伤，没有 guardrail 则分数再高也挡不住一次越权调用。

### 12. LLM-as-a-Judge做自动化评测的位置偏见和长度偏见怎么消

**参考答案**

位置偏见是指同一对答案，放在前面的那个更容易被判赢。对调位置各评一次，两次赢家一致才采纳；不一致就记平局，或换一个评判再评。只评一种顺序，分数会跟着选项顺序走。

长度偏见是指更长的答案更容易被判更好。把量表改成核对项：事实是否在材料里、是否完成了用户的要求，并写明长度不加分。对比前可以把两条答案截到相近的长度。再用一批人工标好的样本看评判结果是否仍和长度相关，相关就把这个评判下线，而不是继续用它做回归。

只在提示词里写「不要偏好更长的答案」基本消不掉长度偏见，要改的是评分任务。生成模型和评判模型用同一个时，还会偏好自己的文风，抽查时要有人工样本。

### 13. AI工作流和 Agent的边界在哪，什么时候该用固定DAG 什么时候必须上状态图

**参考答案**

边界在控制流握在谁手里。步骤和分支上线前就能枚举，模型只做节点内部的文本变换，这是工作流，用固定 DAG。下一步要等工具结果出来才知道，或者中途要回到前面的节点、停下来等人，这才需要带循环的状态图。

固定 DAG 适合解析、分类、按类别走已有模板、发送通知。有限次重试也是写死的边，不是开放式探索。

必须用状态图的情况是：循环检索或循环调工具、人工审批后从原节点继续、中断后按原状态恢复、步数预算要写进状态。只是 A 到 B 到 C，用 DAG 即可。

用了 LangGraph 不等于这是 Agent。路由全部由代码写死时，它仍是工作流。`while` 加一次工具调用已经是 Agent，只是没有持久化。状态图解决循环、中断和恢复。Harness 的评测、追踪和拦截套在两者外面，不负责选择下一个节点。

### 14. 手撕算法：实现一个最简ReAct循环模拟器，输入思考-动作-观察序列，输出去环后的最终答案(LeetCode 202 类似环检测思路)

**参考答案**

把一步的状态定义成「动作 + 参数 + 规范化后的观察」。沿序列走，状态重复就是进入了环，和 LeetCode 202 里「数值重复即无幸福数」同一思路。输入已经是完整序列，用哈希集合记录见过的状态即可，时间 O(n)，空间 O(n)。Floyd 判圈适用于只给 `next()`、还想要 O(1) 额外空间的情形，这里不需要。

走到 `finish` 且之前没有重复状态，`action_input` 就是答案，模拟到此结束。状态一旦重复就停止，环上以及环后的步骤都不再执行。这时还没有 `finish`，答案就取进入环之前最后一步的 `observation`，并把状态标成环。序列走完仍没有 `finish`、也没有环，则标成未完成，同样保留最后一步观察。观察里的时间戳、请求 ID 要先剥掉，否则每一步都像新状态，环会检测不到。同一动作参数重复出现、只是观察在抖动时，另加次数上限，避免集合检测被噪声绕过去。

```python
import json

def _normalize(value) -> str:
    if isinstance(value, str):
        return value.strip()
    return json.dumps(value, ensure_ascii=False, sort_keys=True)

def simulate_react(steps: list[dict]) -> dict:
    seen: dict[str, int] = {}
    answer = None
    for i, step in enumerate(steps):
        sig = "\0".join(
            [
                _normalize(step.get("action", "")),
                _normalize(step.get("action_input", "")),
                _normalize(step.get("observation", "")),
            ]
        )
        if sig in seen:
            return {
                "status": "loop",
                "answer": answer,
                "cycle_from": seen[sig],
                "cycle_at": i,
            }
        seen[sig] = i
        if step.get("action") == "finish":
            return {
                "status": "ok",
                "answer": step.get("action_input", ""),
                "cycle_at": None,
            }
        answer = step.get("observation", "")
    return {"status": "incomplete", "answer": answer, "cycle_at": None}
```

`finish` 放在重复状态之后时不会被采纳，因为环上的「最终答案」是循环造出来的。

### 15. 国产 MLU 上跑 Agent 推理和英伟达CUDA 栈差异，MagicMind 动态 shape 对你编排层有什么反压

**参考答案**

CUDA 侧默认能用到成熟的运行时、集合通信、以及 vLLM 这一类服务：连续批处理、prefix cache、按页管理的 KV cache 比较完整。MLU 侧走寒武纪软件栈（运行时、CNNL、CNCL，推理编译常用 MagicMind），算子覆盖和第三方库都更窄，很多库默认假设 CUDA。Agent 编排不能把「模型调用」写成一个无限拉长的黑盒。

MagicMind 的动态维要在编译期给出范围。运行时的 batch 和序列长度必须落在这个范围里，超出就不能像普通动态图那样临时变长，要么截断，要么换一个按更大上限编译的 engine。上限订得高，KV cache 就按上限占显存，短请求也浪费。

反压到编排层就是四条硬约束：工具结果先摘要再进提示词；上下文长度有硬上限，超限走摘要而不是追加；并发按桶对齐，不按「来多少 token 就塞多少」；不能默认 MLU 服务已经具备和 CUDA 上 vLLM 同级的连续批处理。缺这些能力时，多步 Agent 的预填充成本会直接打满设备。编排层把步数和长度预算写进状态，推理客户端只接受已经裁剪过的输入。

### 1. 自我介绍

**答题思路**

三面看判断和边界，不看框架名单。一分钟到一分半：

1. 一句背景后，直接讲自己在 Agent 项目里实际拍过的板：例如额外的模型调用加不加、写工具开不开。
2. 用一个真实约束说明你怎么算账：准确率、失败率、费用、时延，你当时保了哪一个。
3. 结尾留一个能展开的决策题，例如「线上步数爆炸时先关哪三个开关」。

没带过团队就讲自己负责的那一段怎么和其他人划清职责，不编管理幅度。

### 2. 你带过 Agent 项目么，怎么拆子 Agent 职责，和开发扯不清边界时怎么定

**答题思路**

先回答带没带过，没带过就说自己是工程负责人，负责边界和上线，不把职称说大。拆分按数据所有权和副作用，不按人头：

1. 每个子 Agent 写清输入、输出、能读的数据、能写的工具、失败交给谁。
2. 判断类步骤可以并行有多个；真正写入的动作只留一个执行者。
3. 和业务开发扯不清时用三条规则定案：谁持有数据，谁做最终写入；有副作用的工具只挂在一个 Agent 上；另一个需要这项能力时调用对方的接口，不复制一套工具。
4. 边界落成工具白名单和评测责任人，不落成会议纪要。

准备一个你真实遇到的重叠点，讲清最后白名单怎么划。没有这种经历就不要编一组子 Agent 的名字。

### 3. 当算法同学说加一步LLM调用更准，你作为工程侧怎么算成本和失败率账

**参考答案**

先把「更准」落到固定评测集上的任务成功率，再算这一步带进来的费用、时延和整条链路的失败率。口头准确率不进账。

串行步骤的成功率是各步成功率的乘积，不是 1 减去失败率之和。新的一步会引入超时、schema 失败和注入面，单步看起来更准，整单任务可能更常失败。费用按这一步的输入加输出 token 计，旧上下文很长时，输入费用是大头。时延看端到端 p95，串行就是各步相加，不看单步平均值。

四项一起看：评测集上的成功率差值、单次任务费用差值、端到端 p95、任务失败率。只有成功率的提升盖得住失败率上升，并且 p95 仍在预算内，才允许加。上线先做影子流量，结果不返回用户；同时给这一步单独的预算开关，以便线上可以关掉。能用规则或轻量模型覆盖的样本，不要为了统一流程都多打一次大模型。

### 4. Agent线上疯跑、步数爆炸、烧钱，你从哪三个开关先摁住

**参考答案**

按「先停正在烧的，再停副作用，再停新流量」摁三个开关。

1. **编排熔断**：对在途会话立刻生效最大步数、token 预算和墙钟时间。到点就停，返回已有的部分结果。只降 QPS 而不砍在途循环，旧会话会继续烧。
2. **工具闸门**：关掉写操作和外发 HTTP，必要时只留只读。步数停了，已经发出的副作用仍会闯祸，所以闸门紧跟熔断。
3. **入口预算**：按租户限制新的长任务和多 Agent 扇出，把默认模型切到更小的模型，或直接拒绝新的循环任务。

三个开关都要能在配置里马上改，不依赖重新发版。事后用 trace 看是哪一个工具在重复、是哪一个节点没有终止条件，再把缺失的终止条件补进图里。先加提示词让模型「节省一点」，停不住已经在跑的循环。

### 5. RAG知识库过期、向量召回top5全错，Agent 还硬编答案怎么治

**参考答案**

召回失败时禁止自由生成。过期文档和「五条都不相关」是两道独立的闸。

入库时写入更新时间和失效时间，检索时按时间和版本过滤；更新是替换旧块，不是只追加新块。召回后再看相关性：五条分数都低于门槛，就视为没有召回。这个分支走固定拒答或转人工，不再调用一次自由生成，否则模型会用参数记忆把错段落圆成一段流畅答案。

已经生成的答案还要做引用核对：实体和数字必须能对上被引用的片段，对不上就改成「知识库里没有」。线上用固定问句回放，专门盯「top-K 全不相关但仍回答」的比例。容易漏的是只清洗向量、不改生成策略，索引修好之前模型仍会硬编。

### 6. 多 Agent 协作里责任追溯怎么做，一条坏答案能定位到哪个节点哪次工具调用么

**参考答案**

能定位，前提是每次模型调用和工具调用都是父子 span，而不是只有最终答案一条日志。

一次用户请求一个 `trace_id`。每个 Agent 节点一个 span，记下节点名、图版本、提示词版本、模型名、token 和耗时。每次工具调用是它的子 span，记下工具名、参数哈希、结果哈希、错误码；大结果进对象存储，span 里留指针。最终答案的 span 沿 parent 往回走，就能到具体节点和具体那一次调用，并取出当时看到的原文。

只存节点名、不存工具原文指针时，只能知道「谁做的」，不能知道「它当时看见了什么」。模型版本和索引版本要一起记，否则复盘时对不上。这个结构用 OpenTelemetry 一类的追踪实现即可，关键是父子关系和原文指针，不是绑定某一家观测产品。

### 7. LangGraph 子图复用和动态子 Agent 注册，热更新图定义不重启服务怎么搞

**参考答案**

子图编译一次，作为父图的节点挂上，让父图的 checkpointer 一起持久化子图状态。不要在节点函数里另起一次不带配置的 `invoke`，那样子图的中断恢复会丢。父子状态用输入输出投影隔开，只把子图该看的字段传进去，避免子图的消息列表写进父图。

动态子 Agent 不要做成「来一个就给进程重新编译一张大图」。图里留一个分发节点，每次从注册表读取当前 Agent 的端点或可调用对象。新 Agent 以独立进程提供服务，注册表增加一条记录即可，图进程不用重启。

拓扑本身要改时，在后台编译新图，用原子替换把新请求切过去；在途 `thread_id` 仍走旧图对象，键是 `graph_version`。旧图上的会话要么跑完，要么按二面的迁移规则新开线程。正在恢复的那张图不做原地替换，否则快照里的下一个节点名会对不上。

### 8. AI Coding 工程化：单测生成、补丁应用、沙箱执行、回滚，哪一步最易出生产事故

**参考答案**

最容易变成生产事故的是沙箱执行。这一步会真的跑命令。单测生成错了，通常还停在红灯；回滚要出事，多半是前面已经产生了不可逆的副作用。

- **单测生成**可能写出迎合错误实现的测试，或漏掉数据迁移。它本身还不改生产。
- **补丁应用**会打到错误仓库、错误分支，或应用半截补丁。一旦自动合并，这就是事故出口。
- **沙箱执行**最危险。沙箱若带着生产凭证、能访问内网、或挂着宿主机的容器控制接口，生成的命令会直接打到生产。名字叫沙箱，不代表已经隔离。
- **回滚**解决不了已经执行的迁移、已经发出的消息和已经调用的外部 API。

沙箱若确实没有凭证、没有内网，下一个出口就是自动应用补丁。控制顺序是：补丁只进临时分支；测试和策略都过了才合并；有副作用的命令单独审批；回滚方案写明数据怎么补偿，而不是只做 `git revert`。

### 9. 技术选型：LangGraph+Harness 自研 vs套 AutoGen vs 直接上 CrewAI，你拍板逻辑

**参考答案**

按控制流能不能握在自己手里来拍板，不按仓库热度。

LangGraph 加自研 Harness：循环、状态、中断和 checkpoint 是显式的，Eval、Trace、Guardrail 自己补。适合要审计、要恢复、要限预算的主链路。推理客户端是图里的一个节点，换成 MLU 上的服务不用改控制流。

AutoGen 的多 Agent 对话原型快。经典的群聊停机条件容易散在对话里；后来的事件驱动运行时把这点收紧了，选型时仍要检查预算、中断和恢复是不是一等能力，而不是只看群聊 demo 能跑通。

CrewAI 用角色和任务就能搭一条分工，演示快。角色抽象会挡住细粒度的工具权限、单步评测和 checkpoint，生产链路很快会顶到天花板。

主链路用 LangGraph，Harness 自研。AutoGen 或 CrewAI 只做一次性原型。一个框架进生产之前，先要能说明：状态怎么恢复、工具谁能调、坏了怎么停。说不清这三件，就还停在原型。

### 10. 最近半年你主动啃的最难一篇论文或源码是什么，讲清你卡在哪、怎么爬出来

**答题思路**

选你真读过、而且能指出具体机制的那一篇，不选标题最大的。按四句讲：

1. 它要解决的问题，一句话。
2. 你卡住的具体点：哪一段证明、哪一个状态字段、哪一次调用顺序，你原先理解成了什么。
3. 你怎么爬出来：写了一个最小复现、对上了哪一段源码、或用一个反例推翻了自己的理解。
4. 这点后来用在了你的系统的哪个位置。

粒度示例（不要当成自己的经历来背）：读 ReAct 时，卡住的不是提示词格式，而是循环没有可执行的停止条件；你写了一个会重复同一工具的例子，才确定终止必须在代码里检测重复状态。讲完准备接受追问「把那一段伪代码写一下」。没读过就不要现编论文名。

### 11. 你是怎么建立对新框架的判断力的，不会用之前靠什么信号决定要不要押

**答题思路**

按「先看它藏不藏控制流，再用一条真任务去撞」来回答，不要回答成看星标和博客。

还不会用之前，只看这几个信号：

1. 状态、步数上限、人工中断、失败后的恢复，是框架里的正式能力，还是要自己在外面套循环。
2. 工具权限和沙箱留没留接口，还是默认什么都能调。
3. 升级时旧会话怎么办，有没有 checkpoint 或等价的持久化。
4. 许可证、和现有推理服务的耦合、团队能不能看懂生成的调用栈。

然后用两天做一次钉死的试探：选一条你们真实的多步任务，故意制造工具超时和一次人工暂停。试完写三行：控制不了什么、恢复丢了什么、评测能不能单步重放。三行都说得清，才允许进原型；说不清就停。判断力是这张清单用得多了，不是对框架名字的熟悉程度。

### 12. 手撕算法：给定一个工具调用依赖图(DAG)，求最长关键路径并输出执行顺序(LeetCode 207+拓扑变形)

**参考答案**

边 `u → v` 表示 v 必须等 u 完成。先做 Kahn 拓扑排序：入度为 0 的节点入队，每访问一个节点就把它指向的后继入度减一。访问完的节点数小于节点总数，说明有环，这就是课程表那道题的判定，此时没有合法执行顺序。

无环时，按拓扑序做动态规划。`finish[v]` 是 v 完成的最早时刻，等于 v 的耗时加上所有前驱完成时刻的最大值。默认每个工具耗时为 1。全图 `finish` 的最大值就是关键路径长度，它是允许并行时的工期下界；沿前驱指针回溯得到这条路径。队列弹出的顺序是一份合法的串行执行顺序，没有依赖的工具在真实运行时可以并行。

时间 O(V+E)，空间 O(V+E)。

```python
from collections import defaultdict, deque

def plan_tools(nodes: list[str], edges: list[tuple[str, str]], duration: dict | None = None) -> dict:
    duration = duration or {}
    names = list(dict.fromkeys([*nodes, *[x for edge in edges for x in edge]]))
    if not names:
        return {"ok": True, "order": [], "critical_path": [], "length": 0}
    dur = {name: duration.get(name, 1) for name in names}
    graph = defaultdict(list)
    indeg = {name: 0 for name in names}
    seen_edges: set[tuple[str, str]] = set()
    for src, dst in edges:
        if (src, dst) in seen_edges:
            continue
        seen_edges.add((src, dst))
        graph[src].append(dst)
        indeg[dst] += 1

    queue = deque([name for name in names if indeg[name] == 0])
    order: list[str] = []
    finish = dict(dur)
    pred = {name: None for name in names}
    while queue:
        src = queue.popleft()
        order.append(src)
        for dst in graph[src]:
            cand = finish[src] + dur[dst]
            if cand > finish[dst]:
                finish[dst] = cand
                pred[dst] = src
            indeg[dst] -= 1
            if indeg[dst] == 0:
                queue.append(dst)

    if len(order) != len(names):
        return {"ok": False, "error": "cycle"}

    end = max(names, key=lambda name: finish[name])
    path: list[str] = []
    cur = end
    while cur is not None:
        path.append(cur)
        cur = pred[cur]
    path.reverse()
    return {"ok": True, "order": order, "critical_path": path, "length": finish[end]}
```

长度是路径上的耗时之和。若运行时完全串行，墙钟时间是全部节点耗时之和，关键路径仍然指出哪一条依赖链无法靠并行缩短。

### 13. 你看过的最硬的一份Agent系统源码或开源项目是哪份，骂一句它最烂的地方

**答题思路**

点名一份你真读过源码的项目，骂一个机制，不要骂作者或文档「写得烂」。四句就够：

1. 你读的是哪一块（调度、工具执行、checkpoint，具体到模块）。
2. 它最烂的行为是什么，用一次失败路径描述。
3. 这个行为在生产上会怎么伤人。
4. 你会怎么补，或你已经在自己的系统里怎么避开。

粒度示例（不要当成自己的经历来背）：读到某个框架的群聊实现时，最烂的是停止条件只写在提示词里，选择器可以一直点下一个发言者，工具错误也被当成普通消息继续聊。伤人的地方是费用和副作用都没有硬上限。自己的系统里把停止条件做成路由，工具错误做成结构化观察。讲完要能指出你看的那个函数大概在判断什么。

### 14. 如果寒武纪这边算力只有对标A100六成，你会砍 Agent 哪层保主链路

**参考答案**

保住「一次检索加一次生成，加上代码侧校验」这条主链路，先砍额外的模型往返。

对标 A100 只有六成时，显存和时延的余量都薄。多 Agent 扇出、Critic 再打一次大模型、Agentic RAG 的额外跳、很长的思维链，都会把预填充成倍放大。这些先砍掉，路由改回规则或轻量分类器。

第二刀砍上下文：减少送进模型的块数和重排候选，工具结果只留摘要。KV cache 随长度增长，长度往往比参数量更早把设备打满。

主生成留一次。在 MagicMind 支持的精度里做量化，用精度换吞吐，但不把这唯一一次生成换成无依据的模板。鉴权、步数熔断、trace、引用校验都在 CPU 上，不占用这六成，不能砍。砍掉它们，省下的设备时间会耗在疯跑和无法复盘上。

## HR面

### 1. 自我介绍

**答题思路**

HR 面用业务语言，四五句，不超过一分钟：

1. 做什么方向、做了多少年。
2. 一个已经上线的 Agent 解决了什么问题，你负责哪一段。
3. 你习惯怎么和算法、业务同事合作：用评测和预算说话。
4. 为什么这次看的是要把 Agent 做进生产、并且要面对国产算力约束的岗位。

不讲框架清单，不讲薪资，不评价上一任面试官。

### 2. 为什么看寒武纪 AI Agent 岗，不去了字节阿里大模型组是图啥

**答题思路**

先承认大厂模型组在训练数据和通用模型上的条件，再讲自己要的工作形态，避免贬低任何一家。

建议按这个顺序：

1. 你想做的是把 Agent 收成可上线的系统：编排、工具权限、评测、在有限算力上稳住主链路。
2. 寒武纪这个岗位的约束（推理栈、算力预算、生产可用性）和这件事重合。大厂模型组更偏模型和数据时，接口两侧不是你要深做的部分。
3. 用你真实的经历举一个例子：你已经在工程侧卡过步数、费用或恢复，所以这次是顺着这件事找岗位。
4. 收在「看重这条链路的所有权」，不说「那边卷」或「这边风口」。

没拿过字节或阿里的机会，就直接说当前选择，不要编造一个拒掉的 offer。

### 3. 你觉得自己做 Agent 工程最被低估的一项能力是什么

**答题思路**

只选一项，而且要是别人容易当成「调提示词」的工程能力。建议主线是：给循环写停止条件，并把工具的失败变成可判定的结果。

按这个顺序讲：

1. 先说这项能力是什么：超时算失败、脏 JSON 不能当事实、步数到了必须停，这三件都写在代码里。
2. 再讲别人为什么低估它：演示时模型看起来会自己停，一上线就重复调工具或把错误当事实继续编。
3. 用你自己的一次经历填进去：哪类请求在疯跑或胡说，你加了哪一条硬条件，之后怎么确认它生效。
4. 不要再并列沟通能力、学习能力，选了就讲透一项。

没有对应经历就换一项你真做过的，例如把一条坏答案追到某次工具调用。不要为了贴合岗位现编事故。

### 4. 和算法岗同学合作最吵的一次架因为啥，最后谁听谁的

**答题思路**

选一次技术分歧，优先是「准确率对延迟、费用、失败率」，不选人事冲突。

1. 各用一句话讲清双方主张，不描写情绪。
2. 讲停战用的证据：同一评测集、同一费用和时延预算下的对比。没有数据时，先补实验再决定，而不是当场分输赢。
3. 谁听谁的：听实验结果；结果打平，听对线上可用性负责的那一方。不要回答成「最后我说服了他」或「我听领导的」。
4. 结尾讲结论写进了哪条评测门槛或开关，同一种架没有再吵第二次。

记不清原话就讲决策规则，不要编一段争吵台词。

### 5. 国产算力叙事你信几分，真干起来最烦哪块

**答题思路**

把「芯片能不能跑」和「软件栈有没有 CUDA 那么全」分开说，两边都给明确态度。

建议口径：

1. 信的部分：MLU 可以承担推理，岗位要做的是在这个前提下把主链路保住。
2. 不信满的部分：算子覆盖、服务化能力和周边库不会因为叙事自动对齐 CUDA。面试里不要把这个说成芯片没用，也不要说成短期全面替代。
3. 真干时最烦的是软件栈：动态 shape 的范围、不成熟的批处理和缓存、默认只发布 CUDA 轮子的第三方库、以及定位一次推理失败时的工具链。
4. 收在这些麻烦正是工程要补的：编排层限制长度和步数，不把生态缺口留给线上的无限重试。

用你真实碰过的一个库或一次编译约束当例子。没碰过就说这是你预期要面对的，不要编一次 MLU 故障。

### 6. 当前薪资和预期，接受降总包换股票么

**答题思路**

先把口径问清楚，再谈自己的数。不在没有想清楚之前报一个整数。

1. 问对方的总包包含什么：月薪、年终、签字费、股票是上市后的限制性股票还是期权、归属几年、按什么价格折进总包。
2. 自己的当前薪资按同样的口径报，现金和股权分开，不把未归属的部分说成已经到手。
3. 预期给一个区间，锚在你真实的当前总包和这个岗位的职责，不报一个没有依据的跳涨。
4. 降现金换股票：先保证日常生活的现金不被归属周期卡住。寒武纪是上市公司，股票有流动性，价格也会波动，不能按「一定涨」来换。可以接受结构变化，前提是现金底线和归属规则都写得清。

具体数字只用你自己的，不参考别人的面经。

### 7. 入职后前三个月你最想打通哪条链路

**答题思路**

只承诺一条主链路，不承诺三个月重写框架或追平 CUDA 生态。按月讲可检查的结果：

1. 第一个月：把一条真实请求从接入打到模型再打回用户，加上步数、token、超时三个硬开关，确认它不会无限循环。
2. 第二个月：补上 trace，一条坏答案能找到节点和那次工具调用；同时记下 MLU 侧的长度和并发限制，让编排层在调用前完成裁剪。
3. 第三个月：用一份固定问句看这条链路的成功率和单次费用，把多余的模型往返关掉，留下可回归的评测。

结尾问面试官：现在线上最痛的是疯跑、召回，还是恢复。把第三个月的评测集换成他们已经在痛的那一件。
