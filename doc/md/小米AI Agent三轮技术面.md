## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「我是谁 → 做过什么 → 为什么匹配」讲。

1. 一句话定位：年限，Java 业务服务和 Agent 编排各自做过什么。
2. 只展开一个最复杂的 Agent 项目：用户的哪句话要变成哪个结果，你负责哪一层。结果只用你自己的数字。
3. 点出和这个岗位的交点：模型循环要接进已有的 Java 后端，工具有副作用，要能限流、恢复和追查。
4. 收在你最熟的那段链路上，方便面试官接着问项目。

### 2. 介绍你做过的最复杂的 AI Agent 或相关项目

**答题思路**

用真实项目往下套。没做的层直接说没做。

1. 业务目标：用户的一句话最终要查询、办理，还是只生成一段文字。
2. 你的边界：编排、工具、检索、评测，你写哪一层，谁评审。
3. 按时间讲一条请求：鉴权与限流 → 会话上下文 → 意图和槽位 → 规划 → 工具（校验、超时、幂等）→ 回复。只读和写操作分开。
4. 状态放在哪里，进程重启后还在不在。
5. 一个你亲手处理过的故障：现象、落在哪一层、改了什么、用什么确认修好。没有的指标不要编。

准备三个追问：为什么这样拆、哪一步最容易造成重复写、怎么发现的。

### 3. Java 中线程池的 corePoolSize、maximumPoolSize、keepAliveTime、workQueue 各自作用，提交 10 个任务时完整执行流程是怎样的

**参考答案**

结论：任务先占满核心线程，核心线程满了进队列，队列满了才把线程扩到 maximumPoolSize，再满就拒绝。`keepAliveTime` 不参与这次准入，只决定多余空闲线程何时回收。

四个参数：

- `corePoolSize`：常规保留的线程数。运行中的线程少于此值时，新任务会新建线程来执行，即使队列是空的。
- `maximumPoolSize`：线程数上限。只有队列也放不下时才会继续建线程，直到这个上限。
- `keepAliveTime`：超过核心线程数的空闲线程，空闲超过这段时间就退出。调用 `allowCoreThreadTimeOut(true)` 后，核心线程也可以按同一规则回收，此时这个时间必须大于 0。
- `workQueue`：还没开始执行的任务在这里等。`ArrayBlockingQueue` 有界；默认的 `LinkedBlockingQueue` 容量极大，队列几乎放不满，`maximumPoolSize` 就没有机会生效；`SynchronousQueue` 不存任务，核心线程一满就会直接扩容。

下面用饱和情形把 10 个任务走完。线程池是 `corePoolSize=2`、`maximumPoolSize=5`、`keepAliveTime=60` 秒、队列容量 3、默认 `AbortPolicy`，并且这些任务都还没跑完：

```java
new ThreadPoolExecutor(
    2, 5, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(3),
    new ThreadPoolExecutor.AbortPolicy());
```

1. 任务 1、2：线程数小于核心数，新建 2 个核心线程执行。
2. 任务 3、4、5：核心线程已满，进入队列。
3. 任务 6、7、8：队列已满，线程数还没到 5，再建 3 个非核心线程。这三个任务作为新线程的首个任务立刻执行，所以会比还排在队列里的 3、4、5 更早开始。
4. 任务 9、10：线程数和队列都满了，走拒绝策略。默认 `AbortPolicy` 把 `RejectedExecutionException` 抛给提交方，不会藏进 `Future`。
5. 某个线程忙完后，从队列头部取任务 3。非核心线程空闲满 60 秒后回收，核心线程默认保留。

判断发生在每次 `execute` 的当下，不是事先给 10 个任务排好位置。任务如果很快结束，后面的任务会复用已有线程，队列和拒绝都可能不出现。生产上的工具池用有界队列；拒绝时要有明确的降级，而不是让调用方无界堆积。

### 4. Redis 常用的数据结构及典型使用场景，如何用 Redis 做分布式锁，如何解决锁过期但任务未执行完的问题

**参考答案**

结论：常用结构按「值、字段、顺序、集合、排序」来选。分布式锁用带唯一令牌和过期时间的 `SET NX`，解锁必须核对令牌；任务还没做完就续期，真正防住锁丢了还有人去写，要靠幂等和 fencing token。

结构和场景：

- String：缓存、`INCR` 计数、登录令牌、下面的锁。
- Hash：一个对象里分别更新的字段，避免整段 JSON 反复写。
- List：简单队列、最近 N 条记录。
- Set：去重、标签、交集。
- ZSet：排行榜；用时间戳做 score 可以做延迟队列。
- 其余按场景：Bitmap 做签到，HyperLogLog 做 UV 估算，Stream 带消费组做轻量日志，Geo 做附近的点。

加锁用一条原子命令，令牌用每次加锁单独生成的 UUID，不要用 `SETNX` 再另发一条 `EXPIRE`：

```text
SET lock_key unique_token NX PX 30000
```

解锁用 Lua：值等于自己的令牌才 `DEL`。不核对就删，会把别人刚拿到的锁删掉。

任务超过租期还没做完时，由持锁方在到期前把租期延长，并且只有令牌还是自己的才延长。Redisson 在不传入租期时会启用看门狗，默认租约大约 30 秒，并在到期前续期；一旦调用时显式传入了租期，看门狗不会启动，到期就释放。

续期盖不住进程停顿超过租期的情况：锁已经到了另一个工作者手上，原来的工作者恢复后仍可能去写。Redis 自己不阻止这次写。做法是加锁时拿一个单调递增的 fencing token，业务库只接受比已记录值更新的 token。写操作再按业务键做幂等。主从切换时锁也可能丢，多实例 Redlock 方案本身有争议，不能拿它代替幂等和 token 校验。

### 5. MySQL InnoDB 的 MVCC 原理，RR 隔离级别下如何避免幻读

**参考答案**

结论：普通 `SELECT` 读的是事务开始一致性读时生成的 Read View，沿着 undo 找对这个快照可见的版本。RR 下这个 Read View 在事务里复用，所以快照读看不到别的事务后来插入的行。`UPDATE`、`DELETE`、`SELECT FOR UPDATE` 这类当前读要靠临键锁挡住间隙里的新插入，单靠 MVCC 不够。

行上有隐藏的事务 ID 和指向 undo 的回滚指针，旧版本串成一条链。Read View 里需要记住三组信息：创建快照时还活跃的事务 ID、其中最小的那个，以及当时还没分配出去的下一个事务 ID。判断某一版是否可见时：

- 改动就是本事务写的，可见。
- 事务 ID 小于当时活跃事务的最小值，说明快照前已经提交，可见。
- 事务 ID 大于等于快照后的分配水位，或者落在当时的活跃列表里，不可见，顺着 undo 看更旧的版本。
- 其余情况是快照前已提交，可见。

RC 每个一致性读语句各建一个 Read View。RR 在本事务第一次一致性读时建立，之后复用。`BEGIN` 本身不会建立快照，除非使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`；别的事务若在你第一条 `SELECT` 之前提交，这条 `SELECT` 看得到。

幻读指同一个条件后来多出了行。RR 下普通 `SELECT` 不加锁，新插入的行因为不在旧 Read View 里而不可见。当前读看的是最新已提交版本，并在 RR 下对扫描到的索引加临键锁：记录锁加上记录前面的间隙锁，别的事务不能往这些间隙插入。临键锁是左开右闭的区间。唯一索引等值命中已有记录时退化为记录锁；要插入的值还不存在时，锁住它将落入的间隙。RC 的当前读通常不加间隙锁，外键和重复键检查是例外。

间隙锁要留到事务结束，范围越大越容易和别的事务死锁。还有一个边界：本事务的当前读如果修改了别的事务刚提交的新行，后面的快照读能看见自己改过的这些行。RR 保证的是别的事务的提交不会改变你的快照，不是任意读都绝对不变。

### 6. 什么是 AI Agent，ReAct 范式（Thought-Action-Observation）的完整执行流程请描述

**参考答案**

结论：AI Agent 用模型围绕一个目标多步决策，每步可以调用工具或环境，再根据观察决定继续还是停止。ReAct 把推理和动作交错写进同一条轨迹，而不是先写完一段思路再盲猜结果。

和一个补全接口的差别在于：Agent 有工具、有停止条件、有跨步状态。模型本身不保存上次的工具结果，轨迹靠外部运行时拼回去。

ReAct 的一轮循环：

1. 输入是用户目标、工具说明，以及已经发生的 Thought、Action、Observation。
2. Thought：根据当前轨迹判断还缺什么。
3. Action：选择一个工具和参数，或者给出 Final Answer。
4. 运行时真正执行工具，拿到 Observation。工具失败也写成观察，不要让异常直接把循环打崩。
5. 把这三步追加到轨迹里，再调用模型。
6. 出现 Final Answer、步数用尽或超时就停。

只写思路、不接触环境的链式推理，会把工具结果编出来。ReAct 用观察把这一步拉回来。自由文本的 `Action:` 不好解析，生产里经常保留 Thought，把 Action 做成模型供应商的 tool call，由运行时执行后再把结果按调用 ID 填回去。Thought 不要直接播给用户。

### 7. 意图识别在 Agent 系统中怎么做？用规则 / NLU 分类器和用 LLM Few-Shot 分类各有什么优劣，如何防意图漂移

**参考答案**

结论：高频、高风险意图用规则或小分类器先定，长尾和多意图交给大模型，但标签必须是闭集。意图一旦确认，就写进结构化状态，后续短句默认继承，不能每轮把整段历史重新自由分类。

规则和关键词延迟低、结果稳定、说得清为什么命中，覆盖不住说法变化，规则一多就互相打架。NLU 分类器（小模型）便宜、延迟稳定、标签固定，需要标注，新意图要重新训练，槽位和多意图要另做。LLM Few-Shot 扛得住改写、省略和一次说两件事，但更慢、更贵，可能输出标签集合外面的词，同一句话重复调用结果也可能变。

线上按这个顺序：规则命中高风险或高频说法就直接采用；否则走分类器；置信度低、出现多个意图或分类器没有的说法，再调用大模型。大模型必须输出枚举和槽位，温度用低的，服务端再校验一次。

意图漂移有两层。会话内漂移，是用户只说了「明天」或「好的」，模型却因为上文越来越长改判了意图。把已确认的意图和槽位放在状态里，本轮只做继承、填槽或显式切换；「算了，我要查另一单」这种话才允许换意图。跨版本漂移，是上线后两类意图互相串。留下多轮回归集，按意图看混淆，曲线是悬崖就先对发布，是慢变就查输入分布和标签定义。

### 8. LangChain 的核心组件（Model / Prompt / Chain / Memory / Tool / Agent）分别解决什么问题

**参考答案**

结论：这六个名字对应六件不同的事。模型和提示词解决「调用谁、输入长什么样」，Chain 把固定步骤接起来，Memory 管跨轮历史，Tool 把外部能力暴露给模型，Agent 才是运行时才决定下一步的循环。

- Model：屏蔽不同供应商的对话接口，统一普通调用和流式输出。换模型不应该换掉工具和流程。
- Prompt：把系统指令、变量、少样本例子和历史消息拼成一次调用的输入。模板版本要能和评测对应。
- Chain：步骤事先写死，例如检索、拼提示、生成。输入输出类型固定，便于测试和估算延迟。现在通常用可组合的 Runnable 来写，旧的 Chain 类只是同一种想法的早期形式。
- Memory：决定下一轮把哪些历史放进提示。全量缓冲、滑动窗口、摘要是常见三种。它不是数据库里的审计日志。新接口更常见的做法是单独维护消息历史，而不是靠旧的 Memory 类隐式拼接。
- Tool：一项外部能力的名字、说明和参数 schema。模型只提出调用，真正执行在工具实现里。
- Agent：由模型在循环中选择工具、看观察、再选择，直到停止。AgentExecutor 是旧的循环执行器；步骤多、要暂停和恢复时，这个黑盒循环不够用。

记忆解决的是提示词装不下，Chain 解决的是路径已经确定。两件事先分清，后面问到工作流和 Agent 的差别才不会混。

### 9. LangChain 的 AgentExecutor 执行 Tool Calling 的底层流程，max_iterations 设多少合理，如何防止死循环

**参考答案**

结论：AgentExecutor 是一个「调用模型 → 若有 tool call 就执行 → 把观察写回草稿 → 再调用」的循环。步数和墙钟时间由执行器限制，不交给模型自己改。

工具调用这条路径的每一步：

1. 用系统提示、历史和已有的中间步骤组装输入。中间步骤被格式化成带 `tool_calls` 的助手消息，以及按 `tool_call_id` 对上的工具消息。
2. 调用已经绑定工具 schema 的模型。
3. 解析结果。存在工具调用就得到一个或多个动作；没有就结束，文本作为最终回答。
4. 执行每个工具。同一次回复里的多个调用都要执行，观察按调用 ID 对齐。每个工具单独超时。业务异常如果配置了处理，就变成观察文本，让模型看到失败原因。
5. 把动作和观察追加进中间步骤，步数加一，回到第 1 步。
6. 达到 `max_iterations` 或 `max_execution_time` 就停止。`early_stopping_method` 为 `force` 时直接返回停止；为 `generate` 时再让模型在不能调用工具的情况下收束一次。

旧版 AgentExecutor 的 `max_iterations` 默认是 15，这只是库的防失控兜底。一次检索再回答，成功路径常常只有几步，上限就放在略高于这个步数的位置。需要反复查证的，先看成功请求的步数分布，上限略高于绝大多数成功样本，再用墙钟时间封顶。太小会把正常多步任务掐死。

死循环靠三层，而不是只靠默认值。步数和超时是硬停止。同一工具加上规范化参数反复出现，就提前停。参数每轮故意变一个无意义字段时，字符串去重抓不住，所以硬停止不能省。工具失败先返回观察并限制修补次数，不要在工具内部再自动无限重试。写操作不因为模型重复给出同一个调用就执行多次，幂等键放在业务侧。

### 10. RAG 的基础流程，Naive RAG 有哪些缺陷，你们怎么做的 Chunk 切分策略和 Overlap 设置

**参考答案**

结论：RAG 是先把文档切块并向量化入库，查询时召回相关块，再让模型只依据这些块回答。朴素 RAG 只做一次向量召回和一次生成，切块、查询理解和纠正都没有。切块要先保住文档结构，重叠只是为了接住被切断的句子，具体比例用召回评测定。

基础流程分两条。入库：解析、清洗、切块、向量化、连同标题路径和权限等元数据写入。查询：必要时改写问句，向量召回 Top-K，可以再融合关键词和重排，把块放进提示，要求回答带上来源。

朴素 RAG 的缺陷集中在这些地方：事实被切块切断，或者块太大、相似度被无关句子稀释；问句和原文说法不同，单次向量召回找不到；型号、错误码这类必须精确匹配的词，向量检索经常排得很后；取回的块重复、互相矛盾，长上下文里靠中间的块还容易被忽略；检索错了也不会再查一次；模型仍可能说出上下文里没有的内容；索引过期或漏了权限过滤。

切分的可用做法是：按标题和段落等结构先切开，表格和代码保持完整；再用段落、句子、字符逐级降级的递归切分，给块长一个上限。检索用较小的块，返回模型时带上父级小节，避免块内没有主语。面试时讲你们真实采用的粒度，以及评测集上改过一次粒度后召回有什么变化。没做过 A/B，就不要说成已经调优。

Overlap 的作用只是让边界上的那句话同时出现在相邻两块里。起步可以用块长的大约一成到两成，再看标注证据能不能被完整召回。重叠越大，索引和重复召回越贵，不能靠加大重叠代替切分。

### 11. RAG 中 Hybrid Search（向量 + 关键词）和 Rerank（重排）模型的作用，如何评估 RAG 回答质量

**参考答案**

结论：混合检索补的是召回，重排补的是已经召回到的集合内部的次序。重排看不到召回阶段没返回的文档。评估先分开「证据有没有召回到」和「回答有没有瞎编」。

向量检索擅长同义改写，不擅长订单号、错误码、型号这类必须原样命中的词。关键词检索（常见是 BM25）相反。两路分数的量纲不同，不能直接加权。常用倒数排名融合：一个文档的分数是各路 `1 / (k + 名次)` 之和，论文和常见实现里 `k` 取 60。文档只要在任一路靠前就能留下来。

重排模型把查询和候选文本放在一起打分，比双塔向量更准，也更贵。只对融合后的一小批候选做，例如几十条，再留下几条进提示。它不能替代召回，也不能直接打全库。

评估分成离线和线上，而且按意图分开看：

- 检索：对标好的证据算 Recall@K 和 MRR。较大的候选集召回就低，问题在切块、过滤或召回；候选集里有、送进提示的前几条里没有，才是排序问题。
- 生成：忠实度看每个断言能不能在引用块里找到；答案相关性看是否解决用户的问题。有标准答案再谈正确性。引用的块和实际使用的证据对不上，单独计。
- 线上：重试、点踩、转人工、任务有没有办成。模型给自己打的分只能当辅助，不能当发布门槛。

RAGAS 一类工具把忠实度、答案相关性、上下文精度和上下文召回做成了现成指标，用来回归可以，门槛仍要按你们的坏例来定。

### 12. 简述 Agent 工作流（Workflow）与自主 Agent 决策的区别，什么场景用写死工作流而非让 LLM 自由规划

**参考答案**

结论：工作流的下一步由代码和状态决定，自主 Agent 的下一步由模型在运行时选择。路径稳定、出错代价高的环节写成工作流，只把抽槽、改写和话术留给模型。

工作流的分支是显式的边。同一种输入会走同一条路径，延迟、费用和回归测试都算得出来。自主决策把工具选择、调用次数和停止时机交给模型，长尾说法更灵活，也更可能选错工具、重复调用或跳过检查。

这些场景用写死的工作流：办理顺序受规则约束，例如先核实身份和订单状态，再决定能不能退款；动作不可逆或涉及钱、权限、对外发送、设备控制；流量大、说法集中，自由规划的额外模型调用换不来成功率；需要稳定的时延和单次费用。查状态、查知识库可以在固定节点里做检索。用户目标开放、工具顺序取决于上一步观察、又列不全分支时，才在那个局部使用自主循环，并加上步数上限。

模型可以提议「该退款了」，不能决定跳过退款前的状态检查。这个检查是图上的节点，不是提示词里的一句希望。

### 13. 手撕算法：LeetCode 146 LRU Cache。设计一个满足 LRU 淘汰策略的缓存，get 和 put 均为 O(1)

**参考答案**

结论：哈希表定位节点，双向链表维护使用顺序。最近使用的放在头哨兵后面，最久未使用的在尾哨兵前面。`get` 和更新已有 key 都把节点移到头部；插入新 key 后如果超过容量，删除尾部节点并同步删哈希表。单次操作 O(1)，额外空间 O(capacity)。

已有 key 的更新不会增加容量，必须先走更新分支，不能先淘汰。淘汰时链表和哈希表一起改。使用头尾哨兵，插入和删除就不必再写空链表分支。

```python
class Node:
    def __init__(self, key=0, val=0):
        self.key = key
        self.val = val
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}
        self.head, self.tail = Node(), Node()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_front(self, node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        node = self.map.get(key)
        if node is None:
            return -1
        self._remove(node)
        self._add_front(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            node = self.map[key]
            node.val = value
            self._remove(node)
            self._add_front(node)
            return
        node = Node(key, value)
        self.map[key] = node
        self._add_front(node)
        if len(self.map) > self.cap:
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]
```

Java 里可以用 `LinkedHashMap`，构造时把 `accessOrder` 设为 `true`，并在 `removeEldestEntry` 里判断 `size() > capacity`。读路径调用 `get`，命中后才会把节点挪到最新。`getOrDefault` 和 `containsKey` 走的是不会更新访问顺序的查找，不能拿来当 LRU 的读。访问顺序下的 `get` 会改链表，迭代时再 `get` 会触发并发修改异常；多线程访问要另加锁，或换成熟缓存。题目不要求并发。

### 3. LangGraph 相比 LangChain AgentExecutor 的优势，为什么说 LangGraph 更适合复杂多步 Agent

**参考答案**

结论：AgentExecutor 把整个决策收成一个循环和一个草稿列表。LangGraph 把步骤做成节点和边，状态是显式结构，每一步都能留下 checkpoint。步骤一多、中间要停、或者要并行，图比单个循环可控。

AgentExecutor 适合「模型选工具、看结果、再选」这种单一循环。分支、人工确认、多个专职步骤都塞在同一份草稿里，失败后很难从某一拍重来，也很难让两个步骤同时进行。

LangGraph 的差别在四处：

- 控制流是图。确定的顺序用普通边，是否调用工具、是否结束用条件边。循环停下来靠条件边和递归上限，不靠模型自觉。
- 状态按字段更新。每个节点返回自己的那一部分，消息历史和检索结果不会被后一个节点整份覆盖。
- checkpoint 按 `thread_id` 存在进程外。崩溃后续跑、人工确认和回放都依赖它。
- 同一步可以并行多个节点，再用 reducer 合并。子图可以把一个专职 Agent 包起来。

复杂多步难在恢复和边界，不在于多调用几次模型。图让「哪一步已经成功、下一步必须走到哪」变成数据。简单的单工具问答不必上图；路径已经稳定的部分用图上的固定边，只在不确定的节点里调用模型。

### 4. LangGraph 中 StateGraph 的 State 如何定义，Reducer 的作用是什么，多个节点并发写同一 State 字段怎么处理

**参考答案**

结论：State 是这一次运行的共享结构，节点只返回要改的字段。Reducer 定义「新值和旧值怎么合成」。同一个 superstep 里两个节点写同一个没有 reducer 的字段，会直接报错，不会以后写为准。

字段用类型标出来。需要合并的字段加上 reducer；没有 reducer 的字段，跨步骤时被新返回值整份覆盖。

```python
from typing import Annotated, TypedDict
import operator
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]
    docs: Annotated[list, operator.add]
    answer: str
```

`add_messages` 会追加消息，并按消息 id 更新已有的那条，避免同一条工具调用重复堆两遍。`operator.add` 把列表或数字拼起来。节点若返回整份 `docs` 而不是新增的那一截，列表会被越拼越长。

同一个 superstep 里的节点读到的是同一次输入，彼此看不见对方刚写的值，这和 Pregel 的一步语义一致。这一步结束时，某个字段若收到多于一个更新：

- 有 reducer：按收到的更新依次折叠。并发结果不要依赖折叠顺序，需要次序就拆成不同字段，下一节点再合并。
- 没有 reducer：抛出 `InvalidUpdateError`，含义是这个 key 一步只能接收一个值。

所以并发检索各自写 `docs` 的增量，并给 `docs` 配列表拼接；两个节点都写 `answer` 时，改成 `answer_a`、`answer_b`，汇总节点再决定最终答案。

### 5. LangGraph Checkpointer（checkpoint）持久化到 Redis 或 DB 的实现方式，中断后如何从指定节点恢复

**参考答案**

结论：checkpoint 按 `thread_id` 把每一步的状态存到进程外面。生产上用 Postgres 做可恢复的记录；Redis 可以做热数据，但不要给唯一副本设短过期。恢复的是图的状态，不是外部副作用。

实现的是 checkpointer 的四类能力：按配置读取最近的 checkpoint，枚举历史，在 superstep 边界写入新的 checkpoint，以及把同一步里已经完成的节点写入单独落下。后一项让恢复时可以复用已完成节点的结果。进程内的 `InMemorySaver`（旧名 `MemorySaver`）重启即丢，多个 worker 也互相看不见。异步服务使用成对的异步实现。

Postgres 里一条记录要能表达 `thread_id`、子图用的命名空间、`checkpoint_id`、父 checkpoint、通道里的状态和元数据；大的通道值分开存。`thread_id` 用短且稳定的任务 id。Redis 则按 `thread_id` 保留 checkpoint id 的顺序，每个 id 对应一份内容和 blob。它适合短期热状态；要审计、回放和跨故障保留时，以数据库为准。两个 worker 恢复同一个 `thread_id` 之前先加锁。

中断之后有三种继续方式，不要混用：

- 崩溃后续跑：同一个 `thread_id`，`invoke(None, config)`，不带新的用户输入。已落下的节点不重跑，没写完的节点再执行。
- 回到某个历史快照：从 `get_state_history` 里选 `checkpoint_id`，调用时带上它。图从那份快照记录的下一步继续。
- 指定从哪个节点往后走：`update_state(config, values, as_node="那个节点")`。这个更新被当成该节点刚刚写出的，下一步调度的是它的出边。

`thread_id` 必须和登录用户绑定，不能只信客户端传来的 id。工具若已经调用成功、写入还没落下，恢复时会再执行，所以写工具按 `thread_id`、步骤和业务键做幂等。第一份 checkpoint 都没写出来就崩溃时，这条线程和「从未启动」分不开，受理记录要先落在业务库里。

### 6. 多 Agent 协作常见模式（Supervisor-SubAgent / Pipeline / Parallel / Debate），你们项目用了哪种，为什么

**参考答案**

结论：四种模式差在「下一步由谁决定」。有副作用和权限边界时用 Supervisor；顺序固定就用 Pipeline；子任务互不依赖再 Parallel。Debate 贵，而且会把同一个偏见重复几遍，业务办理里很少需要。

- Supervisor-SubAgent：主管负责分流、停止和汇总，子 Agent 只拿自己的工具和最小上下文。适合订单、设备、知识库这类权限不同的领域。代价是多一次路由，路由错了全局都错，所以路由结果要能被规则或 schema 核对。
- Pipeline：A 到 B 到 C 的顺序写死。适合「抽取 → 检索 → 生成 → 校验」这种已经稳定的链。最容易测试，也最不灵活。
- Parallel：同时做互不依赖的子任务，再汇合。时延取决于最慢的一支，不是相加。必须有超时和部分结果策略，否则一支卡住，整轮都在等。
- Debate：多个 Agent 分头作答再互相反驳，最后由裁判取舍。适合高风险推理，不适合查订单。费用和时延都成倍增加，参与者共享同一个模型偏见时，辩论不会把事实辩出来。

讲自己的项目时，按真实接线说一种。步骤当时就是固定的，就说 Pipeline，并说明为什么没有让模型自由转派。领域和工具权限不同，才说 Supervisor。只有一个 Agent，就直接说没有多 Agent，不要临时编一种没跑过的模式。选择标准是：写操作要有一个责任点，上下文不要在每个 Agent 上复制一份，交接用结构化字段。

### 7. Supervisor 模式下子 Agent 结果如何汇总合并（Reducer / Merge 策略），如何处理子 Agent 超时或返回异常

**参考答案**

结论：子 Agent 交结构化结果，主管按字段合并；互相不覆盖的字段用确定性规则，冲突才交给模型或用户。超时和异常是结果的一种状态，不能让一支失败把已经成功的支丢掉。

每个子 Agent 返回同一类信封：谁返回的、成功还是失败、结构化载荷、错误类型。主管不要先把所有人的自然语言压成一段再抽取。订单号、金额、设备状态这类字段按来源填进各自的位置。两个子 Agent 对同一字段给出不同值时，按事先的优先级、票数，或者改问用户，不要让汇总模型挑一个看起来顺的。若这些子 Agent 是图里同一步的并行节点，这个信封列表就用 State 上的 reducer 拼接。

超时和异常：

- 每个子 Agent 有自己的截止时间，到点取消，避免它继续消耗 token。
- 记录 `{agent, status: timeout 或 error}`。策略允许部分结果时，主管根据已经拿到的字段回答，并说明缺了哪一项。
- 只对只读子 Agent、并且本轮预算还够时重试一次。写操作先按幂等键查询有没有执行成功，取消并不等于没执行。
- 某一类错误连续出现就熔断这个子 Agent，主管走降级话术，而不是再路由回去。
- 成功支的结果已经在 checkpoint 或信封里，重试失败支时不要把成功支再跑一遍。

整轮还有一个总预算。子 Agent 各自重试会把时延加穿，总预算到了就用手头结果收束。

### 8. Agent Harness 工程层是什么，和直接用 LangGraph 比有哪些额外职责（限流 / 审计 / 降级 / 全链路 Trace）

**参考答案**

结论：LangGraph 提供图、状态和 checkpoint。Harness 是包在图外面的生产运行时，决定这次请求能不能进、模型能看见什么、工具能不能真执行、失败了怎么收、事后能不能查。

直接跑一张图，通常还没有这些职责：

- 限流和预算：按用户、按工具、按模型供应商限制并发和 token。一个会话的死循环不能打穿账户。图自己的递归上限只是最后一道保险丝。
- 身份和权限：工具目录按用户和租户过滤。模型提出的调用，还要再过一次授权，高风险工具进人工确认。
- 审计：记下提示词版本、工具名、参数、结果、操作者和审批决定。秘密和隐私要脱敏。审计是业务记录，不是把整段提示打进调试日志。
- 降级：模型或工具超时、熔断时，只读改走缓存或明确的失败说明，写操作不能报成功。可以换较小的模型做分类，不能换一条路径去跳过写前检查。
- 全链路 Trace：从入口到每个节点、每次模型调用和每个工具共用一个 trace id。跨度上有时延、状态、token、提示词版本。没有 trace，checkpoint 只告诉你状态在哪，不告诉你为什么走了那条边。

此外还有密钥管理、代码工具的沙箱、幂等键、灰度时的图版本，以及把坏例送回评测集。评测用的 Eval Harness 复用工具的假实现跑用例，和线上这层运行时不是同一个东西。模型和图可以替换，上述职责还在。

### 9. Function Calling / Tool Use 的 JSON Schema 如何做参数校验，工具执行失败如何设计重试和降级策略

**参考答案**

结论：schema 既提示模型，也是服务端的准入合同。模型返回之后、任何副作用之前，再用 schema 和业务规则各校验一次。失败要分类：参数错让模型有限次修补，瞬时故障才重试，写操作失败不能编造成功。

schema 用闭集约束：`additionalProperties` 设为 `false`，`required`、`enum`、格式和范围写清楚。供应商的 strict 或结构化输出能减少格式错误，不能代替校验。

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["order_id"],
  "properties": {
    "order_id": { "type": "string", "pattern": "^[0-9]{6,20}$" },
    "reason": { "type": "string", "enum": ["late", "wrong_item"] }
  }
}
```

校验分三层。第一层是 JSON Schema。第二层是业务规则：订单属于当前用户、金额在允许范围内、枚举值在当前状态下合法。第三层是幂等键，写操作必带。任何一层失败都不执行。

重试按错误类型：

- schema 或参数不合法：把校验错误作为工具观察还给模型，最多修补一到两次，然后向用户问清楚。这不是 HTTP 重试。
- 429、503、网络超时：指数退避加抖动，次数有上限，沿用同一个幂等键。
- 权限不足、资源不存在、业务冲突：不重试，把原因返回给模型和用户。

降级也按读写分。读工具失败，有新鲜缓存就说明这是缓存结果，没有就明确说查不到。写工具失败，回复「未受理」或「处理中」，不能说「已经办好」。连续失败后熔断这个工具，循环结束，用固定话术收束。

### 10. Agent 长会话上下文超限怎么处理：摘要压缩、滑动窗口、向量记忆各自的适用场景

**参考答案**

结论：三种办法保留的东西不同。滑动窗口留最近原文，摘要留早期决策的压缩版，向量记忆留跨会话还能检索的事实。触发时机是组装提示时还没触顶，要给生成和工具结果留余量。

滑动窗口只保留最近若干轮。实现简单，适合闲聊和短任务。它会丢掉会话开头的约束，例如「不要用短信通知」。系统指令和当前目标不要算进这个窗口里一起被裁掉。

摘要压缩在历史超过阈值时，把更早的轮次收成一段滚动摘要，最近几轮仍保留原文。适合长任务里早期决定仍然有效、但原话不必逐字保留的情况。摘要要增量更新，不要每轮把全部历史重新摘要一次。订单号、已确认的意图、已经执行的写操作放在结构化字段里，不进散文摘要，否则数字和承诺会被写丢。

向量记忆把过去的事实或轮次嵌入，本轮按查询召回几条，并按用户和时间过滤。适合长期偏好和很大的历史里只有一小段相关的情况。当前这句话和记忆冲突时，以当前这句话为准。工具返回的大段原文不进向量库，只留结论和业务单号。召回可能错过，也可能把过期事实塞回来，所以这是补充，不是会话主记录。

三种可以同时存在：提示里是系统指令、结构化事实、滚动摘要、最近原文，再加上本轮召回的记忆。审计日志另存数据库，不靠提示词当记录。到硬限制才被接口拒绝，这一轮的工具结果已经没地方放了。

### 11. 如何设计 Human-in-the-Loop（人工审核节点），哪些工具调用必须走审批，如何在 LangGraph 中实现 interrupt

**参考答案**

结论：该不该审批由工具的风险标记决定，由 Harness 执行，不由模型决定。钱、删除、权限、对外发送、生产变更、有安全影响的设备控制、批量导出隐私，必须先停。查询和草稿不必每次打断用户。

审批节点要让人看到工具名和最终参数，允许同意、拒绝或改参数。记录操作者、时间和原始参数。审批单有超时，超时就按拒绝结束，不能停在「可能已经付款」。模型不能通过说「用户已经同意」绕过这个节点。

LangGraph 里要有 checkpointer，否则暂停无法落到进程外面。现在的写法是在副作用之前调用 `interrupt`，恢复时用同一个 `thread_id` 传入 `Command(resume=...)`：

```python
from langgraph.types import Command, interrupt

def refund(state):
    decision = interrupt({
        "tool": "refund",
        "args": state["args"],
    })
    if not decision.get("approved"):
        return {"result": "rejected"}
    args = decision.get("args", state["args"])
    return {"result": do_refund(args)}
```

恢复时这个节点会从头再执行，`interrupt` 直接返回上次提交的决定，不会再次暂停。写在 `interrupt` 前面的副作用会再跑一遍，所以退款必须放在它返回之后。也可以在编译时使用 `interrupt_before=["refund"]`，节点还没开始就暂停，人看完状态后 `invoke(None, config)` 继续；要改参数就先 `update_state`。

低风险读工具不要套这层，否则审核会堆满，真正的高风险操作没人看。

### 12. 手撕算法：LeetCode 394 Decode String。字符串解码，规则是 `k[编码串]` 表示把括号内容重复 k 次，例如 `3[a2[c]]` 解码为 `accaccacc`

**参考答案**

结论：用两个栈，一个记左括号外已经解码的前缀，一个记这个括号要重复的次数。碰到 `]` 就弹出前缀和次数，拼成「前缀 + 括号内容 × 次数」。时间是 O(输出长度 × 嵌套深度)，空间是 O(输出长度 + 嵌套深度)。

数字要累加成整数，`10[a]` 的次数是 10，不是 1 和 0 两次。字母直接追加到当前缓冲。题目保证输入合法、次数是正整数，括号匹配。`3[a2[c]]` 的过程是：内层 `2[c]` 得到 `cc`，和前面的 `a` 拼成 `acc`，再重复 3 次得到 `accaccacc`。把它算成 `accc` 是漏了外层重复。

嵌套时，内层已经展开的字符会在每一层外层重复时被再复制一次，所以不是严格的 O(输出长度)。最终至少要写出全部输出，这是下限。

```python
def decode_string(s: str) -> str:
    prefixes = []
    repeats = []
    cur = []
    k = 0
    for ch in s:
        if ch.isdigit():
            k = k * 10 + int(ch)
        elif ch == "[":
            repeats.append(k)
            prefixes.append(cur)
            k = 0
            cur = []
        elif ch == "]":
            prev = prefixes.pop()
            times = repeats.pop()
            prev.extend(cur * times)
            cur = prev
        else:
            cur.append(ch)
    return "".join(cur)
```

边界：多位数字、括号后还有普通字母（`2[abc]3[cd]ef`）、没有括号的原样返回、多层嵌套。栈空时碰到 `]` 说明输入非法；面试按题目的合法输入讲即可。

### 2. 项目中你们遇到最难解决的 Agent Bad Case 是什么，怎么定位、归因并最终修复的

**答题思路**

讲一件真事。按「现象 → 定位 → 归因 → 修复 → 回归」五步，不要先报结论「模型不行」。

1. 现象用用户能感知的话描述：重复下单、答非所问、停不下来、不该查的资料被查了。带上发生的范围和大概频率，数字用你自己的。
2. 定位靠 trace：意图、检索到的文档 id、模型决定的工具和参数、工具的真实返回、最终回复。先分清是没调用、调用错、调用对了但回复改了，还是根本没进索引。
3. 归因只落一个主层：意图串了、槽位幻觉、检索缺证据、规划跳过检查、工具超时被当成成功、上下文把早期约束裁掉、提示词或模型版本刚改过。
4. 修复对着该层：闭集 schema、写前校验、幂等、步数上限、切块或混合检索、把事实从摘要里挪到结构化字段。不要用加长提示词包住所有层。
5. 把这条例子放进回归集，固定工具的假返回再跑。修不好的判据也说清楚。

没有戏剧性故障，就讲一条你反复看到、最后用评测堵住的坏例。没复现过的案例不要借来讲。

### 3. 如果让你带 2～3 人做 Agent 模块，你怎么拆分任务、定里程碑和 Code Review 标准

**答题思路**

按运行时、工具、质量竖着切。没带过就说这是你会怎么分，不要编成已经带过。

人可以这样分：一个人负责图、状态和 checkpoint；一个人负责工具网关，包括 schema、权限、超时和幂等；第三个人负责评测集、trace 和坏例回流。只有两个人时，运行时和工具合并，质量不能没人管。不要三个人一起改提示词，那样没有人负责重复写。

里程碑按能上线的切片，而不是按「框架搭完」：

1. 先定成功标准和不能出错的写操作，准备一小批真实对话。
2. 一条竖切走通：一个只读意图，从入口到回复，trace 上每一步都在。
3. 补失败路径：超时、参数错误、人工确认、重启后续跑。
4. 评测进持续集成，再灰度。没有回归集不扩大意图。

Code Review 看这些，不看提示词好不好听：写工具有没有幂等键和权限；节点返回的是增量还是整份状态；并发字段有没有 reducer；失败是不是写成了观察而不是未捕获异常；提示词或 schema 变更有没有带评测差异；日志有没有秘密和隐私。写接口作者不单独合并。

### 4. 当产品经理要求 Agent 支持一个模糊的新能力而工期很紧，你如何评估风险和给出技术方案

**答题思路**

先把「模糊的新能力」收成用户的一个动作，以及这个动作最不能接受的失败。收不拢就不要承诺自治。

1. 问清三条：用户说完希望系统做什么；错误办理和慢，哪一个更不能接受；有没有现成的业务接口。接口没有，模型规划再完整也做不了。
2. 风险按四类写：需求还能理解成多种流程；写操作不可逆；没有评测样本；外部接口的时延和失败率未知。每类对应你会砍掉的范围。
3. 方案给两档。档 A 是固定工作流加上抽槽，只覆盖最高频的一种说法，写操作沿用已有审批。档 B 才是多步自主调用，并说明它依赖的样本、时延和人工兜底。两档都写清不做什么。
4. 用一到两天做一条竖切，事先写好停止条件：样本上的关键参数对不上，或者写接口还没有幂等，就不进入全量。
5. 工期不够时，先上只读或草稿，把办理留在原系统。不要用「先上线再看」代替写操作的检查。

### 5. 你们项目中对 Agent 的观测性（Observability）怎么做的：Trace / Token 统计 / 工具成功率 / Bad Case 回流

**答题思路**

按这四项讲你真实埋过的点。没做的说没做。口径用下面的定义，避免把 HTTP 200 说成工具成功。

1. Trace：一轮用户请求一个 trace，意图、每个节点、每次模型调用、每个工具是跨度，全程同一个 trace id。跨度上有图和提示词版本、工具名、时延、状态。提示和参数里的秘密、隐私要脱敏后再留。
2. Token：按每次模型调用记输入、输出，供应商若返回缓存命中也分开记。汇总到一轮和一次会话，看中位数和高分位。死循环会把平均值拉高，只报平均费用会失真。重试、摘要和重排的 token 都算进这一轮。
3. 工具成功率：按工具分开，至少拆成成功、参数不合法、超时、业务拒绝。HTTP 200 里返回业务错误，仍然是失败。写工具的误调用单独看，不和查询合成一个百分比。
4. Bad Case 回流：点踩、重试、转人工、显式失败，保存输入、文档 id、工具轨迹和版本，固定周期归因，再放进回归集。修提示词或切块之后，这批例子要能再跑。没有这条闭环，前面的 trace 只是日志。

发布时把这四项和版本对齐。曲线在发布点下跌，就先回放旧版本，而不是先改提示词。

### 6. RAG 召回率低时你的排查和优化思路（Query Rewrite / HyDE / Multi-Query / 扩大 Top-K / Rerank）

**参考答案**

结论：先看标好的原文在不在库里、在不在候选集里。重排和扩大送给模型的条数，都救不回从未被召回的片段。HyDE 和 Multi-Query 是召回手段，重排是排序手段。

按坏例把原文对上位置：

1. 原文没进库，或被切碎、切串：先改解析和切块。后面的查询技巧都看不到这段文字。过滤条件用错了型号或权限，表现也像召回低，先核对过滤。
2. 原文在库里，问句有指代、省略，或者和文档不是一种说法：做 Query Rewrite，把指代补全、把约束写进问句。改写可能改丢约束，所以保留原问句，两路一起召回。
3. 问句很短、文档很长，向量对不上：HyDE 先让模型写一段假设性答案，用这段的向量去检索。假设答案若编错，邻居也会偏，所以要和原问句、关键词检索一起用，不能单用假文档。
4. 一种问法覆盖不全：Multi-Query 生成几个改写，各自召回再取并集、去重。召回会上去，噪声也上去，后面必须接重排，并限制改写数量。
5. 原文已经在较大的候选集里，只是名次靠后：这时才扩大进入下一阶段的 K，或者上重排。K 扩大会把无关块送进提示，要和重排或截断一起做。重排只改变候选内部的顺序。

用两个数决定动手的层：大候选集的召回低，查切块、过滤、改写、混合检索和向量；大候选集召回高、前几名召回低，查排序。整库更换 embedding 最贵，放在向量确实对不上同义说法、而且小样本对比有效之后。

### 7. Self-RAG 或 Corrective RAG 的思路，如何让 Agent 自主判断检索结果是否相关并决定重检索

**参考答案**

结论：两者都是「先评估检索得对不对，再决定用、重查还是放弃」。Self-RAG 把这个判断训练进模型的反思标记；CRAG 用一个检索评估器把文档分成正确、不正确、含糊，不正确时改走别的知识源。工程上没有这两个专门模型时，用独立的评估步骤加有限次重查，不能让生成模型无限制地自己判自己。

Self-RAG 的标记大致覆盖四件事：要不要检索、这段文字和问题相不相关、生成的句子有没有被段落支撑、这段生成有没有用。推理时可以按这些标记丢掉无关段落、换一条生成，或再检索。它不是一段「请判断是否相关」的提示词就能等价替换的，标记是训练出来的。

CRAG 在检索之后做评估。判为正确，就把文档拆成更小的知识条，丢掉无关条再生成。判为不正确，就丢弃并改用其他检索，论文里的出路是网页搜索。判为含糊，就把内部知识和外部知识结合起来。企业环境常常不允许把查询发到公网，这一档要换成重写查询后再查内部库，或者直接说没有证据。

工程回路可以做成图上的固定边：

1. 召回 Top-K。
2. 用单独的评估步骤给每块一个相关或不相关，输出用闭集。评估不要和最终回答混在同一次自由生成里。
3. 有相关块：只把相关块送去生成。都不相关：重写查询再检索。
4. 生成后再做一次支撑检查。未被支撑就再检索，或明确回答不知道。
5. 重检索最多两次，次数写在图上。评估器自己也会错，没有上限就会死循环。

相关与否的阈值用那批标了证据的坏例来调。滤得太狠，召回会反而下降。

### 8. MCP（Model Context Protocol）了解吗，它与传统 Tool Calling 封装的本质区别

**参考答案**

结论：Tool Calling 是模型在一次补全里提出函数调用的格式。MCP 是宿主应用和外部能力进程之间的协议，负责发现和执行这些能力。两者是上下层，不是二选一。

传统封装里，工具的 schema 和实现都写在 Agent 应用进程中。换一个宿主，就要再接一遍。模型供应商只看到你提交的函数声明，并返回 `tool_calls`；它并不知道你的函数是怎么实现的。

MCP 把能力放到独立的 server。宿主里的 client 通过 JSON-RPC 连接 server。本地进程常用 stdio，远程连接用可流式的 HTTP（早期远程传输是 SSE）。server 对外提供三类东西：tools 是可执行动作，resources 是可供读取的数据，prompts 是可复用的提示模板。宿主用 `tools/list` 发现工具，再转换成当前模型供应商的 tool schema；模型返回工具调用后，宿主用 `tools/call` 执行，并把结果送回模型。

本质区别是工具从「编译进这个应用」变成「按统一协议发现、授权和调用的外部能力」。一个 MCP server 可以被多个宿主复用。MCP 不替你做权限、沙箱和参数校验，也不让模型供应商直接访问你的 server。调用仍然经过宿主。把 MCP 说成一种新的模型，或说成多 Agent 之间的对话协议，都偏了。

### 9. 说一个你近期自学的 AI 相关新技术（如新模型 / 新框架 / 新论文方向），你怎么快速判断是否值得引入项目

**答题思路**

只讲你真读过、最好动手跑过的一个。按「它解决什么 → 我验证了什么 → 我为什么进或不进项目」讲。

判断就看这几条，能用你的材料回答即可：

1. 它针对的是不是你现在的损失：召回、重复办理、时延、恢复，还是只是演示里的能力。对不上当前损失，就停止。
2. 用你已有的坏例做小范围对比。看任务有没有变好，也看时延、费用和失败时长什么样。没有这批例子，就先不引入。
3. 运行负担：要不要新的状态、新的进程、新的密钥，崩溃后能不能恢复，和现在的图能不能共存。
4. 锁定程度：换掉它要改多少工具 schema 和 checkpoint。越难拆，越不适合在工期紧时进主干。
5. 给出结论：不引入、只放在旁路，或限定一个意图试运行。顺便说什么证据会让你改主意。

论文名和框架版本要真，没跑过的数字不要背。

**答题思路**

渠道按你真实在用的说，三四项就够：

### 11. 如果公司要求你把单体 Agent 服务改造成支持千级 QPS 的生产级服务，你会关注哪些点（并发 / 状态隔离 / 熔断 / 灰度）

**参考答案**

结论：先把「千级 QPS」落成用户请求的准入，而不是模型调用的 QPS。一轮 Agent 会放大成多次模型和工具调用，容量看的是在途请求、下游配额和尾延迟。状态必须离开进程，熔断按依赖拆开，灰度按图和提示词版本切。

并发：请求线程不要一直堵到模型返回。可以用异步客户端，或在较新的 Java 里用虚拟线程，再配有界的在途上限。模型供应商、慢工具和普通查询分成不同的舱壁，各自有并发上限。超过上限时尽快拒绝或排队，队列长度要有上限。自动扩容看在途数和队列堆积，不看 CPU，因为这种服务大部分时间在等网络。

状态隔离：会话状态、checkpoint 放在进程外的存储里，按 `thread_id` 读写。`thread_id` 和登录用户绑定。进程内不放会跨请求复用的对话对象，也就不需要把同一用户粘到同一台机器。写工具的幂等键放在业务库。提示前缀缓存可以共用，带副作用的工具结果不能按用户串缓存。

熔断：模型、检索和每个关键工具单独统计超时和错误。熔断打开后，读走明确的降级，写保持未受理。半开时只放少量探测。一个工具熔断不能把健康检查和别的工具一起打死。

灰度：按用户或请求头选择图版本和提示词版本。旧 checkpoint 要能在旧版本上跑完，或者先排空再改状态结构。回滚是切版本，不只是重新部署。上线前用带工具延迟的压测看尾延迟和拒绝率，不拿平均成功的演示当容量证明。

### 12. 手撕算法：LeetCode 200 Number of Islands。给你一个由 `'1'`（陆地）和 `'0'`（水）组成的二维网格，求岛屿个数。岛屿由上下左右相连的陆地组成，对角线不算

**参考答案**

结论：遍历网格，每遇到一块未访问的陆地就让岛屿数加一，然后把与它上下左右相连的整片陆地标记掉。每个格子只进入一次，时间 O(mn)，额外空间最坏 O(mn)，来自递归栈或访问标记。

标记可以直接把 `'1'` 改成 `'0'`，这样会修改输入。面试官不允许改输入时，另开一个同样大小的访问数组，复杂度不变。对角线上的 `'1'` 不算相连。比较的是字符 `'1'`，不是整数 `1`。

```python
def num_islands(grid):
    if not grid or not grid[0]:
        return 0
    m, n = len(grid), len(grid[0])

    def sink(r, c):
        if r < 0 or c < 0 or r >= m or c >= n or grid[r][c] != "1":
            return
        grid[r][c] = "0"
        sink(r + 1, c)
        sink(r - 1, c)
        sink(r, c + 1)
        sink(r, c - 1)

    count = 0
    for r in range(m):
        for c in range(n):
            if grid[r][c] == "1":
                count += 1
                sink(r, c)
    return count
```

空网格、全水返回 0；单个 `'1'` 返回 1。格子很大时，递归深度可能达到陆地格子数，Python 和 JVM 的调用栈都可能溢出，这时改成显式栈或队列，复杂度仍然是 O(mn)。并查集也可以做：每块陆地先看成一座岛，再和上方、左方的陆地合并，最后数根节点。面试主路径把遍历讲清楚即可。

## HR面

### 1. 自我介绍

**答题思路**

一分钟，几乎不讲框架。HR 要听的是你是谁、为什么坐在这里、能不能和人合作。

1. 年限和现在做的事，用业务结果说，不用组件名堆。
2. 为什么转向 AI Agent：你做过的系统已经需要把一句话接到真实动作。
3. 一个协作事实：和产品或后端怎么把一个有风险的动作收住。用真事，不编团队规模。
4. 收在想来做设备和服务都能落地的 Agent，把话留给后面的动机问题。

### 2. 为什么想来小米做 AI Agent 方向，对小爱同学或小米 AI 生态有什么了解

**答题思路**

把动机锚在「一句话要安全地作用到设备和服务上」，不要背参数，也不要只说想进大公司。

可以覆盖这些公开且稳定的事实，面试前用你真实用过的功能核对一遍：

1. 小爱同学是手机、音箱、电视、汽车和 IoT 设备上的语音入口，不只是手机里的聊天窗口。
2. 澎湃 OS 把设备连在一起。小米公开讲的是人、车、家这套生态：手机、米家设备、汽车能接在同一个助手上。
3. 这个方向难在工具有副作用：控家、查信息、跨设备执行，错了会影响真实设备，所以需要权限、确认和可恢复，不是再包一个对话界面。

然后讲一件你自己用小爱做过的事：它当时停在哪一步，如果按你的工程经验会补上哪一层。没使用过就先用，再来面试。你的 Java 服务和 Agent 编排经验，对应的是工具网关和运行时，不要把岗位理解成模型训练。

### 3. 你期望的薪资范围，以及你基于什么考量提这个数

**答题思路**

给一个区间，并说明区间是怎么来的。笔记里不写具体数字，面试时用你自己的包。

1. 先对齐口径：月薪、年薪、奖金和股票是不是算在同一个数里，工作城市和职级是否已经说清。
2. 区间的下沿来自你现在的总包和你能接受的调动成本，上沿来自这个职级在该城市的公开带宽，以及岗位是否同时要 Java 后端和 Agent 工程。两边都用你查过的真实信息。
3. 说明什么时候可以往下沿走：职责就是你想深入的运行时，职级和评估方式说得清。什么时候不会：职责缩成纯提示词，或口径里把不确定的奖金算成保证收入。
4. 让对方先给带宽也可以。你再把区间放进去，避免在职级还不清楚时报一个无法解释的单点。

### 4. 你最不能接受的团队管理方式或工作环境是什么

**答题思路**

说一到两条你做事需要的条件，配一件真实经历。不要抱怨前公司，也不要排成一份缺点清单。

比较站得住的两条：

1. 没有责任边界。线上出了重复办理或误触发，只找人背锅，不留下可回放的 trace 和下次的检查。你需要的是谁对写操作拍板、事后按记录复盘。
2. 风险被工期直接压掉。涉及钱、权限、设备控制的动作，没有幂等和确认也要当天上。你可以用缩小范围来保工期，不能接受先造成伤害再补。

讲完补一句你怎么合作：范围和检查可以谈，记录和责任人不能省。避免把「加班」或「开会」说成唯一不能接受的事，除非你能讲清它如何让线上责任无法落实。

### 5. 过去项目中跟同事或 PM 发生过意见分歧吗，怎么处理的

**答题思路**

用一件真事，按这个顺序，不要站在「我是对的」上讲。

1. 双方要的结果：产品要的是用户能办成，你守的是哪一个不能错的动作。
2. 你复述对方的目标，把分歧收成一个可验证的问题，例如误办理有多少、确认会多打断多少。
3. 给一个同时满足两边的方案：只读先自动，写操作先确认；或者先在影子流量里跑，不真正写。
4. 当时谁拍板。若你没被采纳，说你如何把决定和风险写下来并执行，而不是私下抵制。
5. 事后用哪条记录判断这个决定对不对。没有事后验证，就不要把故事讲成你赢了。

没有激烈争吵，就讲一次评审里规则不同、最后写进检查清单的事。不要编造冲突。

### 6. 未来 3 年你的职业规划，倾向深耕 AI 工程还是往架构 / TL 方向发展

**答题思路**

先讲未来一年能独立负责的范围，再讲分叉，不要报一个职级时间表。

1. 一年内：独立负责一条 Agent 链路的上线质量，包括工具边界、坏例回归和故障时的恢复。这是后面无论做哪边都要有的基础。
2. 之后两条路都接受，选择看你在哪边贡献更大。深耕工程，就继续把运行时、评测和多步可靠性做深，成为别人会来问边界的人。走架构或 TL，是因为团队需要有人把权限、发布和评审标准定下来，并且你已经证明能带一两个同事把模块交出去。
3. TL 不是离开代码。如果还没带过人，就说当前倾向先把模块负责完整，带人要等有真实的分工需求。
4. 和这个岗位对齐：设备侧的 Agent 需要长期的工程判断，两条路都放在这个领域里，而不是把这里当跳板。

### 7. 你还有什么想问我们的（团队规模 / 模型迭代频率 / Agent 落地场景等）

**答题思路**

问两件面试里还没讲清、而且会影响你是否加入的事。薪资已经谈过就不要再问。下面选两件：

1. 团队里工程、算法、产品大概怎么分，你入职后前半年拥有的是工具网关、编排，还是某个具体场景。
2. 小爱或设备生态里，哪些 Agent 场景已经在线上，哪些还是试验。写操作今天由谁确认。
3. 模型、提示词和图多久改一次，有没有评测或坏例门槛挡住发布。
4. 线上出了误触发，trace 和复盘是不是同一套记录，谁有权让一个工具下线。

每个问题听完可以追问一句「那我这项工作的完成标准是什么」。不要问八卦，也不要把加班当成第一个问题；真要确认协作节奏，就问发布和故障时谁在场。
