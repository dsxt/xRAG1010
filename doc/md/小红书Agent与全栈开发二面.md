## 二面

### 1. 自我介绍

**答题思路**

一两分钟，讲完就把话题留在项目上。

1. 方向只说你实际做的那一段：编排、检索、工具、接口或前端流式。年限一带而过，职级和薪资不用报。
2. 只准备一个 Agent 项目，用一句话带过「用户输入到结果展示」，点明你负责的那一段。
3. 对齐这个岗位：模型循环和面向页面的接口或流式展示，你两边都碰过。
4. 停住，让对方决定先问链路、状态还是检索。

### 2. 深度讲一个 Agent 项目：从用户输入到工具调用、模型推理、结果落库与前端展示的完整链路

**答题思路**

按一次真实请求从输入讲到界面。用你自己的项目，每步只展开你写过的部分。

1. 一句话说明谁在用、这一轮要完成什么。不要换成更大的业务。
2. 入口：哪个服务做鉴权、会话和回合 id，用户消息写到哪里，流式连接从这里打开。刷新之后消息还在，说明它已经落库。
3. 模型之前：状态从哪读。最近原文、摘要、检索证据各放了什么，哪类内容故意没放。
4. 工具：模型给出调用后，谁校验参数和权限，超时多久，结果写回何处，然后是再叫模型还是结束。有副作用的调用，讲你怎么保证这一回合只生效一次。
5. 落库：最终答案、工具轨迹、检查点各在哪。连接断了以后靠哪一份恢复。
6. 展示：前端收到哪些事件，例如工具开始、工具结束、文本增量、结束。断线之后怎样接上同一次回合。
7. 收在一个你确实处理过的失败上，例如超时或工具返回了不能用的数据。没有监控数字就讲这次失败怎么发现、用户看到什么，不编耗时和成功率。

第一遍把这条链路讲完。状态机和评测等对方追问再展开。

### 3. 项目里 LangGraph 的状态机怎么设计，并发会话下 State 如何持久化与恢复

**参考答案**

结论：一轮对话是一张图，状态按通道合并；会话之间用 `thread_id` 隔离，同一个会话同时只允许一次运行。恢复靠进程外的检查点，未完成的节点会重跑，所以写操作要幂等。

通道分开设计。消息用追加合并，相同消息 id 覆盖旧内容，节点不用整表替换历史。步数、证据、待确认项用覆盖语义。节点一般是组装上下文、调用模型、执行工具、落库。模型节点之后看有没有工具调用，有就进工具节点，没有就结束。步数和预算在图上判断，到点进入结束节点。

每个 super-step 结束时，把通道的值、版本和接下来要跑的节点写入检查点。`thread_id` 标识这条会话，`checkpoint_id` 标识某一步。`MemorySaver` 在进程内，重启就没了。线上用 Postgres 这类外部存储，并且每步都写。只在整轮结束时写一次，进程被杀会退回更早的状态。

不同会话各有各的 `thread_id`，互不覆盖。同一个 `thread_id` 的检查点是读改写，两个实例一起 `invoke` 会分叉。对这个 id 加租约或排队，后来的回合等上一轮结束。续跑用同一个 `thread_id`，不要把同一条用户消息再追加进 messages。停在 `interrupt` 上的节点，恢复时会从头再执行，副作用放到暂停之后，或按 `tool_call_id` 记过结果。图的结构变了，旧检查点不要直接接到新图上。

容易漏的是：检查点是执行进度，界面上的消息流水要另存，两边用同一个回合 id 对齐。热缓存可以丢，权威进度以检查点为准。

### 4. 多轮长上下文膨胀时，摘要压缩、滑动窗口、向量召回三种策略怎么选，代价分别是什么

**参考答案**

结论：三种按信息类型叠在一起用。最近几轮留原文，更早的过程用摘要，很早且被点名的事实再用向量召回。

滑动窗口保留最近若干轮或最近一段 token 的原文。指代和刚发生的工具结果还在，开销就是这段原文本身。窗口左边的约束、编号和已经做过的决定会被切掉。工具调用和它的结果必须成对留下，从中间切开，下一次模型请求是不合法的。

摘要压缩把旧对话压成一段，最近几轮仍留原文。稳定的决定能留下来，但数字、否定和精确 id 容易被改掉，这个误差会随轮次累积。每轮还要为摘要多付一次生成，以及之后反复带上它的 token。不能改写的内容放在摘要外面：用户的硬约束，以及工具返回的结构化结果。

向量召回按当前问题去历史里取相关片段，适合距离很远、摘要里留不住的稀疏事实。代价是嵌入和检索的延迟，刚说过的话可能召不回，召回片段也没有对话顺序，索引还会比对话慢一拍。

容易漏的是：摘要里的数字不能拿来代替工具结果。最近一轮原文无论用不用向量都要钉在上下文里，否则「刚才那个」会丢。

### 5. RAG 效果不好怎么排查：区分检索、排序、Prompt、模型本身问题，怎么建评测集

**参考答案**

结论：先看证据停在哪一层，再改那一层。一个端到端的对错分不出该改索引还是该改提示。

按这个顺序看同一条坏例。语料里没有能回答的原文，就是知识库缺口。原文在，召回的前 k 条里没有，问题在切块、查询、过滤或嵌入，看召回率。金证据还在粗排结果里，但没进入送给模型的那几条，问题在排序或多路融合。证据已经写进提示，答案却没用上或用反了，就把上下文固定住，只改提示做对照；引用和证据对不上也算这一层。上下文和提示都站得住，换一个模型才变好，才归到模型。换了仍然错，多半是多跳、计算或否定本身超出了这段证据。

评测集从真实提问里抽，另外补上库里没有答案的题、要精确编号的题、要跨段落的题。每条记下问题、金证据的位置、可接受的答案；不该回答的题标成拒答。指标拆开：证据在不在库里、召回有没有命中、进入上下文的那几条有没有命中、答案是否被证据支持、最终对错。调提示用过的集合，不要再拿来当最后的效果结论。

容易漏的是：上下文里已经有证据还答错，继续改索引没有用。评测集里如果全是有答案的题，系统靠编造也能看起来分数很高。

### 6. 工具调用超时、重复执行或返回脏数据，系统怎么重试、熔断和兜底

**参考答案**

结论：重试只覆盖可以再执行的失败；熔断按工具打开；脏数据在进入模型和业务库之前挡住。

单次工具的时限短于整轮预算。网络超时、429、503 可以重试，参数错误和业务拒绝不重试。次数要有上限，间隔用退避加抖动。写操作超时之后，先按幂等键查询有没有已经成功，确认没有再决定要不要重发。

模型打出两次相同调用，或者节点重跑，都按 `tool_call_id` 只执行一次。也可以用回合 id、工具名和规范化参数做键。第一次记成进行中，后来的调用等待，或直接拿走已有结果。没有幂等键的副作用，不要自动重试。

返回先过出参结构。空包、半截 JSON、错误页都算失败，写成结构化错误交回模型，让它改参数或停止。这段文本不进业务库，也不进长期记忆。

熔断按工具或下游统计。关闭时按上面的规则重试；打开后立刻失败，不再重试；半开放少量探测。开的是这一个依赖，同一次对话仍可以走其他只读工具。读工具失败时，说明不可用，或返回标了时间的旧快照。写工具失败就记失败。

容易漏的是：熔断已经打开，重试循环还在打这个工具，熔断就没有生效。写已经成功、响应超时，再执行一次会造成重复。

### 7. MCP 和 Function Calling 区别，接几十个工具时怎么做路由、描述裁剪和权限隔离

**参考答案**

结论：Function Calling 是模型在这一次请求里声明工具名和参数；MCP 是宿主去发现并调用进程外的工具服务。几十个工具先筛选，再把少数几个放进这一轮请求。

Function Calling 由应用把 JSON Schema 放进本次模型请求，模型返回要调用的名字和参数，应用负责执行。它不管这些工具住在哪个进程里。MCP 由工具服务公布自己的工具，宿主列出清单再发起调用。模型不直接看到 MCP。宿主要把选中的工具转成这一次请求里的 function 定义。连接、生命周期和鉴权在宿主和工具服务上。

路由分两级。先按领域选中某个工具服务，再按描述检索，只留和当前回合相关的几个。模型如果点了没有下发的名字，执行层直接拒绝。

描述分成目录和详情。目录里是名字和一句话，写清什么情况下不要用。完整参数 schema 只展开给选中的那几个。名字、说明和 schema 都占上下文，一次放进几十个，选错会变多。

下发给模型的列表，已经是这个用户、这个租户、以及读或写范围的交集。执行时再鉴权一次，并核对参数里的资源属于这个用户。连到 MCP 的服务身份不能代替终端用户，用户身份要传到工具服务。读和写分成不同权限。

容易漏的是：提示里少放几个工具，执行层却接受任意名字，模型仍能调用没展示的工具。提示词里的约定不是权限边界。

### 8. 单 Agent 什么时候该拆多 Agent，主从和流水线模式怎么通信、怎么仲裁冲突

**参考答案**

结论：工具、权限或失败域已经分成稳定的几块，再拆开。主从用来改派，流水线用来走固定步骤。冲突由规则和唯一的写入者解决。

一个提示里工具多到经常选错，某几步的权限、模型或超时需要隔开，并且步骤之间能交接一份结构化结果，这三种情况适合拆。紧耦合的「看一步、调一个工具」留在单个循环里。拆开会丢掉草稿，并多出交接的延迟。

主从里，主管选择下一个专家并汇总。专家之间不直接通话，来回传递的是任务和结构化结果。两个专家矛盾时，主管按写好的优先级取舍：工具观察优先于模型的表述，用户新的约束优先于旧的。最大跳数放在图上，由代码执行。

流水线里，上一段的输出 schema 就是下一段的输入。后一段拒绝时，带上原因退回前一段，并限制修改次数。控制流不随模型临时增加阶段。

权威状态只有一个写入者。写操作走条件更新，版本对不上就失败，后一个 Agent 不能覆盖前一个的写入。

容易漏的是：主管自己拿着全部写工具，专家拆开了也没有隔离。把上一段的自由文本原样转发，错误会被下一段当成事实。

### 9. BFF 与 Agent 服务边界怎么划，流式 SSE 怎么做断线重连与消息去重

**参考答案**

结论：BFF 负责登录态、页面协议和这条 SSE 连接；Agent 负责一轮运行。断线后续传已有运行的事件，连接重连不新开一轮模型。

BFF 把页面请求收成一条运行命令，做限流，再把事件写成浏览器能读的 SSE。Agent 跑状态图、模型和工具，写出带序号的事件和检查点。界面字段变了改 BFF；提示和工具变了改 Agent。事件日志放在两边都能读到的存储里，BFF 换实例之后仍能续。

创建运行和订阅流分开。创建用 POST，带上客户端在第一次发送前生成的幂等键。订阅带上上次已经应用的事件 id。使用 `EventSource` 时，这个 id 要写在 SSE 的 `id` 字段里，浏览器重连才会带上 `Last-Event-ID`。用 `fetch` 读流时，客户端自己保存 id，重连时显式传回来。服务端回放比它大的事件，再接上实时尾部。运行已经结束就回放完关闭；还在跑就挂到同一次运行上。空闲时发心跳注释，避免代理把连接掐掉。

同一个幂等键只创建一次运行，重复的 POST 返回原来的运行 id。客户端丢掉 id 小于等于已应用 id 的事件。文本增量按事件 id 的顺序追加。

容易漏的是：把重新订阅当成一条新的用户消息，会并行跑两轮，检查点互相覆盖。id 如果只放在 JSON 正文里，`EventSource` 重连时不会替你带上。

### 10. 热点笔记或热点会话 Key 打散，本地缓存、Redis、MySQL 三层怎么保证一致

**参考答案**

结论：MySQL 是权威数据。热点读先用本地缓存挡住；写提交之后删除 Redis，并通知各节点丢掉本地副本。会话检查点保持单键，不用拆 key 的方式打散。

热点笔记是读多写少。每台机器的本地缓存先吸收重复读。Redis 上如果仍是单键，就把只读副本做成 `noteId:0` 到 `noteId:n-1`，读的时候随机选一个。这些键不要用同一个哈希标签，否则还会落在同一个槽。更新时删除全部分片，再广播本地失效。

会话检查点要保留一次状态更新的顺序，拆成多键之后无法一次写完。同一会话的读用单飞合并，本机可以放一份可丢的快照；写仍然进入同一个键。

读的顺序是本地缓存、Redis、MySQL。回填时带上版本号和 TTL，本地 TTL 短于 Redis。写的顺序是先提交 MySQL，再删 Redis，再广播各节点删除本地缓存。两个写请求如果都去改缓存，后完成的旧值会留在缓存里，所以写路径删除缓存，让下一次读回源。慢读可能在删除之后把旧值写回去：回填时版本落后就放弃。也可以在提交后再延迟删除一次，延迟要盖住那次回填；这是兜底，精确的是比对版本。失效广播可能丢失，短 TTL 让本地缓存最终会自己掉下去。

容易漏的是：只删了 Redis，各进程里的本地缓存还在，三层会继续不一致。会话的权威进度放在检查点里，本地快照可以过期。

### 11. MySQL 联合索引最左匹配，Order By、范围查询、回表场景怎么分析

**参考答案**

结论：联合索引按定义顺序排列。等值条件从左连续用到，遇到范围就停；`ORDER BY` 要和这个顺序一致才不用额外排序；选出索引里没有的列就要回表。

以 `(user_id, status, created_at)` 为例。`WHERE` 里等值条件的书写顺序不影响使用，优化器会调整，所以 `status` 和 `user_id` 都等值时，仍然用得上左侧两列。只有 `status` 等值、没有 `user_id` 时，不能按这个索引查找。被跳过的列取值非常少时，优化器偶尔会跳跃扫描，这是特殊路径，分析时仍按最左前缀判断。

范围列右边的列不能继续收窄查找，也不能单独提供顺序。`user_id` 等值且 `status` 等值，再 `ORDER BY created_at`，顺序和索引一致，不需要额外排序。`status` 变成范围之后，`created_at` 在不同 `status` 之间并不是全局有序，`ORDER BY created_at` 要额外排序。`user_id` 等值后 `ORDER BY status, created_at` 可以直接沿索引走。`user_id` 本身是范围时，`ORDER BY user_id, status, created_at` 与扫描顺序一致；只按 `status` 排序则不行。排序方向整体一致时可以逆序扫描；同一条 `ORDER BY` 里升降序混用，现有索引对不上就要额外排序。

二级索引的叶子上有索引列和主键。查询列都在里面是覆盖索引，`Extra` 里会有 `Using index`，不再回表。`SELECT *` 或其他不在索引中的列，要用主键去聚簇索引取行。范围很大时，优化器可能改走全表扫描，因为大量随机回表比顺序扫描更贵。

看 `EXPLAIN` 时，`key_len` 表示查找用了左侧几列，不表示排序用了几列。`Extra` 里的 `Using filesort` 表示另外做了排序，不一定真的写了磁盘文件。`Using index condition` 是在索引上过滤，过滤通过的行该回表仍然回表。

容易漏的是：范围条件写在中间列上，右边的列既不能用来查找，也不能用来消除排序。覆盖索引看的是查询涉及的列，不只是 `WHERE` 里的列。

### 12. Redis 缓存击穿、穿透、雪崩解决方案，Lua 扣减库存如何保证原子性

**参考答案**

结论：三种都是请求打到了数据库，原因不同。Lua 保证的是单个 Redis 实例上「判断库存和扣减」不会被别的命令插进来，订单是否成功还要和数据库对上。

穿透是查的数据在缓存和数据库里都不存在，每次都会穿过缓存。入口先挡住明显非法的参数。确定不存在的 key 用布隆过滤器拦截；过滤器可能把不存在误判成可能存在，所以数据库确认没有的结果再用短 TTL 缓存空值。空值缓存要限住规模，避免被随机 key 撑满。

击穿是一个热点 key 过期的瞬间，大量请求同时回源。同一个 key 只放一个请求去加载，其余等待后再读缓存。也可以在值里写逻辑过期时间，先返回旧值，由一个请求异步刷新。极热的 key 可以不设硬 TTL，由后台更新。

雪崩是大批 key 在同一时刻过期，或者缓存实例整体不可用。TTL 加上随机抖动，缓存做主从或集群。缓存挂了要限流和降级，数据库连接也要有上限。

库存扣减要在脚本里分支。`MULTI` 会把命令排队，执行完才看得到 `GET` 的结果，没法在事务中间按库存决定扣不扣。`WATCH` 是乐观锁，冲突后要在客户端重试。下面的脚本在 Redis 里一次做完判断和扣减：

```lua
local qty = tonumber(ARGV[1])
local stock = tonumber(redis.call('GET', KEYS[1]))
if qty == nil or qty <= 0 or stock == nil or stock < qty then
  return -1
end
return redis.call('DECRBY', KEYS[1], qty)
```

返回 `-1` 表示没扣。调用方必须看返回值。脚本只含这一个 key 时，集群槽位没有问题；脚本里再写第二个 key，两个 key 要落在同一个槽。扣减成功之后再写订单，订单失败要把库存加回去，两边用同一个业务单号。Redis 里的原子性不包括这张订单。

容易漏的是：先 `GET` 再在客户端 `DECRBY`，中间会被别的请求插队。脚本太长会堵住这个实例，库存判断以外的逻辑不要放进脚本。

### 13. Kafka 怎么保证消息不丢、不重、有序，事务消息和本地消息表怎么落地

**参考答案**

结论：不丢靠副本确认和处理成功后再提交位点；重复靠业务键去掉；顺序只承诺到分区。数据库和 Kafka 一起成功用本地消息表；Kafka 事务包住的是分区写入和消费位点。

不丢要生产、Broker、消费三段一起做。生产者等待全部同步副本确认，`acks` 用 `all`，`min.insync.replicas` 至少设为 2，并开启重试和幂等。不要让一个没追上的副本被选成首领。消费者关掉自动提交，业务处理成功之后再提交位点。

幂等生产者用序号去掉自己重试造成的重复，范围是同一个生产者会话、同一个分区。消费者仍可能至少收到一次。业务侧用消息 id 或业务单号做唯一约束。消费后再生产到 Kafka，并且不写外部库时，可以用 Kafka 事务：固定 `transactional.id`，一次事务里发送消息并提交位点，消费者使用 `read_committed`。新实例会把旧的事务生产者围栏掉。

顺序以分区为单位。同一个业务键进同一个分区。开启幂等后，在途请求处于允许范围内时，重试仍按序号写入。未开启幂等时，在途请求大于 1 又发生重试，分区内会乱序。消费端对一个分区要按顺序处理；拿到消息后如果并发执行，顺序会在应用里被打乱。

业务库和发消息要用本地消息表。同一个数据库事务里写业务数据和一条待发送记录。补偿任务把记录发到 Kafka，收到确认后再标成已发送。进程在确认前停掉，记录还在，可以再投。消费者按消息 id 去重。Kafka 事务不包含这张业务表的提交。

容易漏的是：`acks=all` 而 `min.insync.replicas` 仍是 1 时，首领在复制前宕掉仍会丢。处理前就提交位点也会丢。幂等生产者不去掉消费端的重复。

### 14. 线程池参数与执行流程，异步调用 LLM 时怎么控制并发、背压和超时

**参考答案**

结论：`ThreadPoolExecutor` 先补核心线程，再入队，队列满了才扩到最大线程数，再失败才拒绝。调用大模型用单独的有界池，并发按下游在途上限收住，超时要取消已经发出的 HTTP。

七个参数是核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。工作线程数小于核心线程数时就新建核心线程，这时即使已有核心线程空闲也会建。达到核心数之后任务入队。队列满了才继续建线程，直到最大线程数。再提交就走拒绝策略，默认是抛出 `RejectedExecutionException`。超过核心数的线程空闲够久会回收；核心线程默认不回收，除非打开 `allowCoreThreadTimeOut`。队列没有上界时队列不会满，最大线程数和拒绝策略都不会生效。

模型和工具是长时间的 IO，和页面请求的线程分开。这个池的核心数等于最大数，再加一个短的有界队列，并发上限用信号量按供应商能承受的在途数来定，不按 CPU 核数放大。同一会话同时只放一轮，避免两轮一起改检查点。队列满了就拒绝，BFF 告诉客户端现在忙。`CallerRuns` 会退回到请求线程上，交互链路里不合适。供应商返回 429 时先冷却，不在池里紧循环重试。

超时分成三层，外层长于内层：HTTP 读超时、这次任务的等待、页面上的 SSE 时限。到点要取消底层 HTTP 并归还信号量。只让 `Future` 超时的话，线程和供应商侧的请求都还在。池里的任务不要再阻塞等待同一个池提交的任务。阻塞等待如果改用虚拟线程承载，在途数仍由信号量限制。

容易漏的是：无界队列看起来不会拒绝，积压会变成内存里的提示词。超时如果没有取消 HTTP，池会慢慢被占满。

### 15. 接口幂等设计：AI 任务创建、支付回调、消息消费如何防重复

**参考答案**

结论：幂等键在第一次请求发出之前就定下来。创建用唯一约束，状态变化用条件更新，消息用同一事务里的去重记录。重复到达时返回和第一次相同的业务结果。

AI 任务的键由客户端生成，超时重试用同一个键。服务端把用户和这个键的唯一约束，与任务插入放在同一个事务里。冲突时查出已有任务返回。任务还在跑，后来的重试挂到同一次运行，不再发起一次模型调用。工具的副作用带上这个任务 id，沿用同一条去重记录。

支付回调先校验签名。渠道流水号做唯一键，再用条件更新，例如只把「待支付」改成「已支付」。影响行数是 1，才做履约。影响行数是 0，说明已经处理过，仍然向渠道返回成功，让它停止重试。改状态和履约放在同一个事务里；履约在库外完成时，写进待发送记录，由补偿任务执行。状态已经是已支付、履约却没做，之后的回调不会再触发履约。

消息消费把消息 id 的插入和业务写入放在同一个数据库事务里。重复插入就是已经处理过，提交位点并跳过。数据库短暂失败时不提交位点，让消息再投。位点放在业务事务提交之后。

容易漏的是：键如果由服务端在插入成功之后才生成，客户端超时后无法复用。只在 Redis 里用 `SETNX` 占位，Redis 丢了之后窗口会重新打开。支付重复回调如果返回失败，渠道会一直重试。

### 16. 手撕算法：手写 LRU Cache，要求 get 和 put 均为 O(1)

**参考答案**

结论：哈希表按 key 找到节点，双向链表把头当作最近使用、把尾当作最久未使用。`get` 和 `put` 都是 O(1)，空间是 O(容量)。

`get` 未命中返回 `-1`。命中时把节点移到表头再返回值。`put` 遇到已有 key，只更新值并移到表头，个数不变。没有这个 key 时，在表头插入；超过容量就摘掉表尾，并同时从哈希表删除。只从链表删除的话，后来的 `get` 还会找到已经被淘汰的节点。

链表必须自己保存前驱和后继。按值在一条链表里查找再删除是 O(n)。表头和表尾放哨兵节点，插入和摘除不用处理空表。

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    private static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    public LRUCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node removed = removeTail();
            map.remove(removed.key);
        }
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void moveToHead(Node node) {
        unlink(node);
        addAfterHead(node);
    }

    private Node removeTail() {
        Node node = tail.prev;
        unlink(node);
        return node;
    }
}
```

标准库里把 `LinkedHashMap` 的 `accessOrder` 设为 true，再在超过容量时去掉最老的条目，结构就是这张表。手写要表现出来的是节点自己带着前驱和后继。

容易漏的是：`get` 也要刷新成最近使用，只在 `put` 时移动会把热点提前淘汰。更新已有 key 不能再走一遍「插入然后淘汰」。
