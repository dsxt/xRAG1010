# 小鹏 AI Agent三轮技术面：LangGraph+Codex+Harness 全拷打，贼难

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这个岗位不是普通 CRUD 岗，面试官明显不想听你背 LangChain 文档。一面就要求画全链路，画不出来基本就凉了。二面 LangGraph checkpoint 和 harness 状态管理是分水岭，没有真正在生产里跑过多步中断恢复的，三句话就会被问住。三面 Codex 沙箱那题很刁，只会说调 API 不行，得真做过把编译错误喂回模型这类脏活。Java 和 Python 两边都要硬，只会一端不行。整体偏难但公平，座舱场景给出的约束（端侧算力、语音歧义、安全降级）比纯互联网 Agent 有意思，值得一试。

## 一面

### 1. 请做一个自我介绍

**答题思路**

控制在 1 到 2 分钟，按"我是谁 → 做过什么 → 为什么匹配这个岗位"组织：

1. 一句话定位：年限、技术栈（Java / Python 双栈、Agent 方向）。
2. 挑 1 到 2 个最相关的项目：讲业务目标、你负责的模块、用到的关键技术（LangGraph、RAG、工具编排、消息队列等），最好带一个可验证的结果（只讲你真实有的指标）。
3. 点出与座舱 Agent 的契合点：低延迟语音交互、多工具编排、状态恢复与安全降级。
4. 结尾回到岗位，表达想继续深入 Agent 工程化的意愿，把话题引到你最熟的项目上，方便面试官接着深挖。

### 2. 讲一个你落过的 AI Agent 项目，从用户一句话进来到最终调工具出结果，全链路画一遍

**答题思路**

不要编造项目，用你真实的项目套下面的骨架，边讲边画图。以座舱语音为例，一条请求的完整链路：

1. **入口**：语音 → ASR 转文本 → 文本规整（口语纠错、指代消解）→ 网关鉴权、限流。
2. **上下文装配**：按 session_id 取短期对话历史、用户画像、车辆状态（位置、电量、车速等）。
3. **意图与槽位**：规则 / 小模型快速判断，命中高频指令直接走快路径；低置信度交给 LLM。
4. **规划与路由**：Planner（LLM 或固定流程）决定调哪些工具、是否需要检索（RAG）、是否需要澄清。
5. **工具执行**：参数校验（JSON Schema）→ 权限与安全检查 → 带超时、重试、熔断的执行池 → 结果标准化。涉及下单、车控等副作用的步骤加人工确认和幂等键。
6. **结果整合**：把工具结果回填给模型，判断是否继续下一轮（Agent loop），设最大步数。
7. **输出**：流式生成 → 按句切分 → TTS 播报；失败时走降级话术。
8. **横切能力**：checkpoint 持久化、全链路 trace（每步耗时、token、工具入参出参）、日志与评测回流。

准备好回答三个追问：为什么这样拆、哪一步最容易出问题、你怎么发现并解决的。

### 3. Python 里 asyncio 和多线程怎么选，Agent 并发调 LLM 和工具时用哪种模型

**参考答案**

结论：Agent 的主要负载是网络 IO（调 LLM、调工具 API），首选 asyncio；遇到无法异步化的阻塞库，用线程池兜底；CPU 密集的任务用多进程。

- **asyncio**：单线程事件循环，协程切换开销小，适合成百上千个并发等待的 IO 请求，且没有线程间的数据竞争问题。
- **多线程**：受 GIL 限制，CPU 密集型任务得不到并行加速，但在 IO 阻塞时 GIL 会释放，所以对阻塞型 SDK 仍有用。可以通过 `asyncio.to_thread` 或 `loop.run_in_executor` 接入事件循环。
- **多进程**：CPU 密集的场景，如本地 embedding、重排、大量文本解析。
- **工程要点**：
  - 用 `asyncio.Semaphore` 限制对 LLM 供应商的并发，防止触发限流。
  - 所有外部调用用 `asyncio.timeout`（3.11+）或 `wait_for` 设超时；并行任务用 `TaskGroup` 或 `gather(return_exceptions=True)`，避免一个失败拖垮全部。
  - 绝不能在协程里直接调用同步阻塞函数，否则会卡住整个事件循环。
  - 处理好取消（用户打断语音时取消在途请求）。

### 4. Java 里线程池参数怎么配，如果 Agent 后端用 Java 起一个工具执行池，corePoolSize 和 maxPoolSize 怎么定

**参考答案**

结论：先区分任务是 CPU 密集还是 IO 密集，再用压测校准；工具调用基本是 IO 密集，且必须使用有界队列。

`ThreadPoolExecutor` 的提交规则是：线程数小于 core 就新建线程；core 满了先入队列；队列满了才扩到 max；max 也满了触发拒绝策略。因此：

- **无界队列**（如默认 `LinkedBlockingQueue`）会让 maxPoolSize 失效，任务堆积还可能导致 OOM，工具池应避免。
- **估算公式**：CPU 密集型约 `N_cpu + 1`；IO 密集型可参考 `N_cpu × (1 + 等待时间/计算时间)`，只是起点，最终要靠压测和监控调整。
- **工具执行池的做法**：
  - core 设为日常稳定并发量，max 设为突发上限，队列容量有界。
  - 按工具类型隔离线程池（舱壁模式），例如慢的第三方接口和快的内部接口分池，避免一个慢工具拖垮全部。
  - 拒绝策略根据业务选：`CallerRunsPolicy` 形成背压，或自定义拒绝后返回"系统繁忙"降级。
  - 使用自定义 `ThreadFactory` 给线程命名，方便排查；监控活跃线程数、队列长度、拒绝次数。
  - 每个任务自带超时（`Future.get(timeout)` 或下游客户端超时），防止线程被永久占用。

### 5. 意图识别你怎么做，规则 + 分类模型 + LLM 三套方案说下取舍，座舱场景下误触怎么办

**参考答案**

结论：生产里通常分层使用，规则兜住高频和高风险指令，小分类模型处理常规意图，LLM 处理长尾和复杂表达。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 规则 / 关键词 / 正则 | 延迟极低、完全可控、可解释 | 覆盖面窄，维护成本随规则增长 |
| 分类模型（小型 BERT 类） | 延迟低、成本低、可本地部署 | 依赖标注数据，标签集固定，新意图要重训 |
| LLM | 泛化最强，支持复杂、多意图、上下文依赖 | 延迟和成本高，可能输出不稳定或幻觉 |

**分层流程**：规则命中且置信度高 → 直接执行；否则交给分类模型；分类模型置信度低或检测到多意图 → 交给 LLM 并要求结构化输出（JSON Schema）。

**座舱误触的处理**：

1. **拒识**：先判断这句话是不是对车机说的（背景对话、乘客聊天），训练拒识类别，结合声源位置、唤醒词、VAD 结果。
2. **置信度阈值**：低置信度时不执行，转为澄清或直接忽略。
3. **按风险分级**：查询类直接执行；车控、下单、导航变更等有副作用的动作加确认；行车中涉及安全的操作按白名单限制。
4. **可撤销**：执行后支持"取消 / 撤回"。
5. **确认要克制**：全部确认会让体验变差，需要用数据平衡误触率和打扰率。

### 6. LangChain 的 Chain 和 Agent 本质区别，为什么生产里不全用 Agent

**参考答案**

结论：Chain 的执行路径由代码预先写死，Agent 的下一步由 LLM 在运行时决定。

- **Chain**：步骤固定（如 检索 → 拼 prompt → 生成），确定性强，易测试、易估算延迟和成本。
- **Agent**：LLM 在循环中选择工具、观察结果、再决策，灵活但路径不可预测。

生产里不全用 Agent 的原因：

1. **可控性**：路径不固定，难以保证行为一致，出问题难复现。
2. **延迟与成本**：每一轮循环都是一次 LLM 调用，步数不确定。
3. **可靠性**：可能陷入死循环、选错工具、参数幻觉，需要加最大步数和校验。
4. **可测试性**：固定流程更容易写回归测试和评测。

实践原则：能用确定性工作流解决的部分用 workflow，只在确实需要动态决策的环节用 Agent，两者混合（workflow 里嵌 Agent 节点）。

### 7. LCEL 为什么比老 Chain 类好，流式输出在座舱语音场景怎么接

**参考答案**

结论：LCEL 用统一的 `Runnable` 接口和管道符 `|` 做声明式组合，让流式、异步、批处理、并行、重试和追踪成为默认能力。

**相比老 Chain 类的优势**：

- 接口统一：`invoke / stream / batch / ainvoke / astream`，组件可任意拼接。
- 自动支持流式和异步，不用为每个 Chain 类单独实现。
- `RunnableParallel` 并行分支、`with_retry`、`with_fallbacks` 内置容错。
- 与 LangSmith 等追踪集成，输入输出类型更清晰。
- 老 Chain 类继承层次复杂，各类接口不一致，定制困难。

**座舱语音接流式**：LLM 的 token 流 → 按标点或语义切句 → 一旦凑成一句立刻送 TTS 流式合成播放，目标是缩短首包延迟。注意：

1. 不要把工具调用的 JSON 或中间推理朗读出来，只播报面向用户的内容。
2. 支持打断（barge-in）：用户插话时取消 LLM 生成和 TTS，释放资源。
3. 句子切分要避开数字、小数点、缩写等误判。
4. 工具执行较慢时先播报"正在查询"一类过渡语，避免沉默。

### 8. RAG 切块策略，长文档切 Chunk 用固定长度还是语义切，重叠区设多少，为什么

**参考答案**

结论：没有统一最优，推荐"按文档结构 + 递归切分，并限制长度"，在此基础上留少量重叠，用评测集调参。

- **固定长度**：实现简单、长度均匀，但可能把句子或表格从中间截断，破坏语义。
- **语义 / 结构切分**：按标题、段落、句子、列表甚至用 embedding 相似度找边界，块内语义完整，检索质量通常更好，代价是实现复杂、块长度不均。
- **常见折中**：递归字符切分（按段落 → 句子 → 字符依次降级），再加长度上限；技术文档、手册则优先按标题层级切，并在每块里带上标题路径作为上下文。
- **块大小**：常见起点是几百 token，太小丢上下文，太大则噪声多且稀释向量表示。
- **重叠区**：常见做法是块大小的 10% 到 20%，目的是避免边界处信息被切断。重叠过大则冗余、增加索引成本和重复召回。具体数值要用自己的检索评测（召回率、答案准确率）来定。
- 进阶：小块检索、大块返回（parent-child），表格和代码块单独处理。

### 9. 向量数据库选 Milvus 还是 PgVector，ANN 索引 HNSW 和 IVF 差在哪，座舱本地端用哪个

**参考答案**

结论：数据量和并发大、需要专门的分布式向量能力选 Milvus；数据量中小、已经在用 PostgreSQL、想与业务数据一起做事务和过滤，选 PgVector。

**Milvus vs PgVector**：

- Milvus：为向量检索专门设计，支持分布式扩展、多种索引、较大规模数据，但运维组件多。
- PgVector：作为 PostgreSQL 扩展，部署简单，可与关系数据同库做 SQL 过滤和事务，规模很大时扩展性和性能不如专用库。

**HNSW vs IVF**：

- **HNSW**：多层小世界图，从上层稀疏图逐层向下贪心搜索。召回和速度都很好，支持增量插入，无需训练；缺点是内存占用大，构建较慢。参数如 `M`、`efConstruction`、`efSearch`。
- **IVF**：先用 k-means 把向量聚成 `nlist` 个簇，查询时只扫最近的 `nprobe` 个簇。需要训练聚类，内存相对小，常与 PQ 量化组合（IVF-PQ）进一步压缩；召回依赖 `nprobe`，增量数据多了聚类会漂移。

**座舱本地端**：端侧算力和内存有限、数据量小（用户手册、个人偏好），不适合部署完整的 Milvus 集群。常见选择是嵌入式或轻量方案，如 FAISS、SQLite 向量扩展、Milvus Lite 等，索引上数据量小可以直接用 Flat 暴力检索；稍大时用 HNSW，或 IVF + 量化来省内存。云端负责大规模知识库，端侧做小规模缓存和离线兜底。

### 10. 混合检索 BM25 + 稠密向量怎么做融合，RRF 公式说一下

**参考答案**

结论：BM25 擅长关键词精确匹配，稠密向量擅长语义匹配，两者的分数量纲不同，常用 RRF（倒数排名融合）按排名而不是按分数融合。

**RRF 公式**：

\[
\text{RRF}(d)=\sum_{i}\frac{1}{k+\text{rank}_i(d)}
\]

其中 \(\text{rank}_i(d)\) 是文档 \(d\) 在第 \(i\) 路检索结果中的名次（从 1 开始），\(k\) 是平滑常数，实践中常用 60。没出现在某一路中的文档，该路贡献记为 0。

**做法**：

1. BM25 和向量检索各自召回 top-N。
2. 对每个文档累加各路的 \(1/(k+\text{rank})\)，按总分排序。
3. 取前若干条，可再接 cross-encoder 重排。

**其他方式**：加权线性融合需要先把分数归一化（min-max 或 z-score），并调权重。RRF 优点是不用关心分数分布，实现简单、鲁棒；缺点是丢掉了分数的绝对差距信息。

### 11. Redis 在 Agent 系统里放什么，checkpoint、session、限流分别怎么用

**参考答案**

结论：Redis 适合放热数据和需要高并发读写、可过期的状态，但不要把它当唯一的持久存储。

- **session（会话）**：用 Hash 或 String（JSON）存近期对话窗口、用户上下文、车辆状态快照，设 TTL 自动过期；多实例部署时让任意节点都能恢复会话。
- **checkpoint**：热 checkpoint 可以放 Redis（LangGraph 有 Redis 版 checkpointer），读写快，适合短时间内恢复；但要开启 AOF 或 RDB 并做好持久化与主从，对必须长期保留或可审计的状态，应落到 PostgreSQL / MySQL 等持久库。
- **限流**：
  - 固定窗口：`INCR` + `EXPIRE`，简单但有边界突刺。
  - 滑动窗口：用 ZSet 存时间戳。
  - 令牌桶 / 漏桶：用 Lua 脚本保证检查和扣减的原子性。
  - 维度可以是用户、设备、租户、LLM 供应商，用来保护下游 LLM 和工具的配额。
- **其他**：分布式锁（同一会话串行处理，避免并发写状态）、工具结果缓存、幂等键去重（`SET NX EX`）。

### 12. MySQL 存 Agent 对话记录和工具调用日志，表怎么设计，慢查询怎么排查

**参考答案**

结论：按"会话 → 消息 → 工具调用"拆表，围绕最常用的查询路径建联合索引，大字段与热数据分离，数据量大后按时间分区或归档。

**表设计示例**：

- `conversation`：`id`、`user_id`、`device_id`、`status`、`created_at`、`updated_at`。
- `message`：`id`、`conversation_id`、`role`、`content`（长文本）、`token_count`、`created_at`。索引 `(conversation_id, created_at)`。
- `tool_call_log`：`id`、`conversation_id`、`message_id`、`tool_name`、`args`（JSON）、`result`（JSON 或存对象存储的引用）、`status`、`latency_ms`、`error`、`idempotency_key`（唯一索引）、`created_at`。

**设计要点**：

- 超长内容（完整 prompt、大型工具返回）放单独表或对象存储，主表只存摘要，避免行过大。
- 字符集用 `utf8mb4`。
- 日志类数据按时间做分区或定期归档，避免单表无限增长。
- 分页用游标（`WHERE id < ? ORDER BY id DESC LIMIT n`），不要深分页 `OFFSET`。

**慢查询排查**：

1. 开启慢查询日志（`slow_query_log`、`long_query_time`），用 `pt-query-digest` 等工具汇总。
2. 对具体 SQL 用 `EXPLAIN`（必要时 `EXPLAIN ANALYZE`），看是否走索引、扫描行数、是否出现 filesort 或临时表。
3. 常见原因：缺索引或联合索引顺序不对、索引列上做函数或隐式类型转换、`SELECT *` 读大字段、深分页、大事务锁等待。
4. 通过 `SHOW PROCESSLIST` 或 performance_schema 排查锁等待。
5. 修复后对比执行计划和耗时。

### 13. 场景题：座舱里用户说"帮我找附近充电站顺便订咖啡"，意图歧义 + 多工具编排你怎么拆

**参考答案**

结论：先把一句话拆成两个有依赖关系的子任务，规划成 DAG；只对影响执行的关键歧义才澄清，有副作用的"订咖啡"必须确认。

**1. 意图与槽位拆解**

- 子任务 A：找附近充电站。槽位：当前位置（取自车辆定位）、电量、接口类型、偏好（快充、空闲、距离）。
- 子任务 B：订咖啡。槽位：品牌 / 门店、品类、取餐时间。
- 依赖：咖啡门店最好选在所选充电站附近，取餐时间要对齐到达时间或充电时长，所以 B 依赖 A 的结果。

**2. 歧义处理**

- "附近"默认用车辆当前位置或导航前方路线；"咖啡"如果有用户偏好就直接用，没有则给出最多两三个选项让用户选。
- 行车中尽量少问、问短问题，能用默认值就不追问。

**3. 工具编排**

1. 查充电站（地图 / 充电服务）→ 按距离、可用桩数、功率排序。
2. 用户确认站点（或自动选最优并播报）。
3. 在该站点周边查咖啡店。
4. 预估到达时间 → 生成订单草稿 → 语音确认 → 提交订单（带幂等键）。

**4. 可靠性与安全**

- 下单是非幂等操作，要有确认和幂等键。
- 部分失败要有降级：咖啡下单失败不影响导航到充电站，并告知用户。
- 驾驶安全：播报精简，避免需要看屏幕才能完成的交互。

### 14. 手撕算法：LeetCode 139 单词拆分（给你一个字符串和字典，判断能否拆成字典里的词）

**参考答案**

思路：动态规划。`dp[i]` 表示前 `i` 个字符能否被拆分；`dp[0] = True`。对每个 `i`，枚举分割点 `j`，若 `dp[j]` 为真且 `s[j:i]` 在字典中，则 `dp[i] = True`。用集合存字典以实现 O(1) 平均查询，并只枚举长度不超过最长单词的 `j` 来剪枝。

复杂度：设串长 `n`，最长单词长 `L`，时间约 \(O(n \cdot L^2)\)（枚举 \(O(nL)\) 次，每次切片并哈希 \(O(L)\)），空间 \(O(n + \text{字典大小})\)。

```python
from typing import List

def wordBreak(s: str, wordDict: List[str]) -> bool:
    words = set(wordDict)
    max_len = max((len(w) for w in words), default=0)
    n = len(s)
    dp = [False] * (n + 1)
    dp[0] = True
    for i in range(1, n + 1):
        for j in range(max(0, i - max_len), i):
            if dp[j] and s[j:i] in words:
                dp[i] = True
                break
    return dp[n]
```

易漏点：DFS 加记忆化也可以，但纯暴力回溯会指数级超时；剪枝用最长单词长度。

### 2. 你那个 Agent 项目里 LangGraph 的 State、Node、Edge 怎么设计的，reducer 怎么写

**答题思路**

这是项目深挖，用真实项目回答，下面是可以直接用的组织框架和技术点：

1. **State**：用 `TypedDict` 或 Pydantic 定义，只放决策与恢复所需的最小状态，例如 `messages`、`intent`、`slots`、`plan`、`tool_results`、`step_count`、`error_count`。大对象（长文档）只存引用。
2. **Node**：每个节点只做一件事（意图识别、规划、检索、工具执行、生成回复、人工确认），接收 state，返回要更新的字段（局部更新）。
3. **Edge**：普通边表示固定流转；条件边（`add_conditional_edges`）根据 state 决定下一步，例如"有工具调用 → 工具节点，否则 → 结束"；并设置最大步数的兜底终止。
4. **Reducer**：当多个节点或并行分支更新同一字段时，需要合并规则。用 `Annotated[类型, reducer函数]` 声明：
   - 消息列表用内置 `add_messages`（按 id 追加或更新）。
   - 列表追加用 `operator.add`。
   - 自定义 reducer 示例：

```python
from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

def merge_tool_results(old: dict, new: dict) -> dict:
    return {**(old or {}), **(new or {})}

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    tool_results: Annotated[dict, merge_tool_results]
    step_count: int
```

没有 reducer 的字段是"后写覆盖"；并行节点写同一个无 reducer 的字段会报错。reducer 应当是纯函数，且满足结合性，避免并行分支顺序影响结果。

### 3. LangGraph checkpoint 用 MemorySaver 还是 PostgresSaver，thread_id 怎么和座舱用户会话绑定

**参考答案**

结论：开发和测试用内存型（`MemorySaver`，新版本也叫 `InMemorySaver`），生产用持久化的 `PostgresSaver`，因为内存型进程重启或多实例之间会丢状态。

**两者差异**：

- `MemorySaver`：状态存在进程内存，重启即丢，无法跨实例共享，只适合本地调试。
- `PostgresSaver`（`langgraph-checkpoint-postgres`）：每个 super-step 结束后把状态写入数据库，支持进程崩溃后恢复、跨实例恢复、中断后长时间等待再恢复、查看历史做回溯。首次使用需调用 `setup()` 建表；异步场景用 `AsyncPostgresSaver`。使用连接时注意其文档要求（如 autocommit、`dict_row`）。

**thread_id 绑定**：checkpoint 以 `config["configurable"]["thread_id"]` 作为会话键。

- 一个"座舱会话"对应一个 thread_id，可以设计为 `user_id:vehicle_id:session_id` 的稳定组合，或生成 UUID 后在业务库里维护映射。
- 同一个 thread_id 的请求要串行处理（用 Redis 锁或按 key 路由），避免并发写同一个线程的状态。
- 用户再次唤醒时，若在会话有效期内（比如未超过 TTL）就沿用 thread_id，否则开新线程。
- 跨会话的长期记忆不要放在 checkpoint 里，应使用 LangGraph Store 或外部记忆库。
- 注意清理策略：checkpoint 会不断增长，需要按 TTL 或保留最近 N 个归档清理。

### 4. 中断恢复怎么做，人机确认节点落在图的哪，非幂等工具（比如真下单）怎么防重放

**参考答案**

结论：用 checkpoint 持久化图状态，在副作用节点之前设置中断点等待用户确认，恢复时用确认结果继续；非幂等工具靠幂等键 + 先草稿后提交来防重放。

**中断与恢复**：

- 在节点中调用 `interrupt(payload)` 暂停图并把 payload 返回给调用方；也可以用编译时的 `interrupt_before` 指定节点前中断。必须配置 checkpointer 才能中断。
- 恢复时用同一个 `thread_id` 调用，并传入 `Command(resume=用户的确认结果)`。
- **关键细节**：恢复后包含 `interrupt()` 的节点会从头重新执行，所以在 `interrupt()` 之前不能有非幂等的副作用，应把副作用放在中断之后，或拆成独立节点。

**确认节点位置**：放在"规划完成、真正执行有副作用的工具之前"，即：`规划 → 生成订单草稿 → [人工确认] → 提交订单`。确认的内容应包含订单关键信息（商品、金额、地点），让用户知道确认的是什么。

**防重放（非幂等工具）**：

1. **幂等键**：由 `thread_id + 业务步骤 / tool_call_id` 生成稳定的 key，随请求传给下游订单服务，下游以该 key 做唯一约束去重，重复请求返回第一次的结果。
2. **两阶段**：先"创建待确认订单（草稿）"，确认后再"提交"，提交接口按订单号幂等。
3. **本地记录**：在调用前把"将要调用"写入日志表（唯一键），调用后更新结果，重放时先查表。
4. **超时处理**：下游超时时不要盲目重试，先按幂等键查询订单状态，再决定是否重提。
5. LangGraph 在节点失败后可能重跑该节点，所以所有带副作用的节点都必须按"至少一次执行"来设计。

### 5. 多 Agent 协作你用主从还是流水线，Orchestrator 怎么把子任务分给 Worker，结果冲突怎么仲裁

**参考答案**

结论：任务路径固定时用流水线，需要动态拆解和分派时用主从（Orchestrator-Worker），实际常混合使用；多 Agent 不是越多越好，先确认单 Agent 加工具是否已经够用。

- **流水线**：步骤固定、前后依赖明确（如 意图 → 检索 → 生成 → 校验）。简单、可预测、易测试。
- **主从**：Orchestrator 根据用户目标动态规划子任务，分派给专门的 Worker（地图、充电、订餐、车控），再汇总。灵活，适合开放任务，但 Orchestrator 本身是瓶颈和单点，规划质量决定全局。

**分派方式**：

1. Orchestrator 用结构化输出生成任务列表：每个子任务含目标、所需输入、依赖关系、预期输出格式。
2. 无依赖的子任务并行执行，有依赖的按 DAG 顺序执行。
3. Worker 只持有各自需要的工具和最小上下文，减少 token 和误用工具。
4. 每个 Worker 有超时和重试，失败时上报给 Orchestrator 决定改派或降级。

**冲突仲裁**：

- 规则优先：按预设优先级仲裁，安全相关（车控、行车安全）优先于娱乐类。
- 置信度或证据：优先采用有来源、有引用的结果。
- 校验者（Verifier / Critic）：让独立的 Agent 或确定性程序检查结果的一致性。
- 多数投票：对可多次采样的判断类任务。
- 仍无法判定时，回到用户确认或降级到保守方案。

### 6. Harness 层你理解是什么，Agent loop 里状态、记忆、工具、观测四件事分别放哪

**参考答案**

结论：Agent = 模型 + Harness。Harness 是包在模型外面的运行时，负责循环控制、上下文管理、工具调度、权限与沙箱、状态持久化和观测，模型只负责决策。

**Agent loop 基本流程**：组装上下文 → 调用模型 → 若返回工具调用，则校验、执行并把结果追加回上下文 → 重复，直到模型给出最终回答或触发停止条件（最大步数、预算、超时）。

**四件事的位置**：

- **状态**：属于 harness，放在模型之外的持久存储（checkpoint）。包括当前步数、计划、待执行的工具调用、中断点。模型本身是无状态的，崩溃恢复靠 harness 的状态。
- **记忆**：短期记忆是当前对话和工具结果，由 harness 负责窗口裁剪、摘要压缩；长期记忆放在外部存储（向量库、图库、KV），在需要时检索后注入上下文，而不是把所有历史都塞进 prompt。
- **工具**：harness 维护工具注册表（名称、JSON Schema、权限级别），负责参数校验、权限检查、沙箱隔离、超时、重试和结果截断后再回填给模型。
- **观测**：贯穿整个循环，记录每一步的 prompt、模型输出、工具入参出参、耗时、token、错误，形成 trace，用于调试、回放和评测（如 OpenTelemetry 或 LangSmith 类工具）。

### 7. Codex / Claude Code 类 harness 你实战过没，fork 过 deep-agent 没，upstream 冲突怎么处理

**答题思路**

先诚实说明你的实际经验，不要夸大没做过的事：

1. **用过的部分**：说清楚你用这类工具做了什么，例如让它改代码、跑测试、配置权限，以及你观察到的 harness 设计（工具集、上下文压缩、子 Agent、权限确认、沙箱）。
2. **没有 fork 过也可以如实说**，然后展示你对原理的理解：这类 harness 的核心是 loop + 文件和 shell 工具 + 规划（todo）+ 子 Agent + 上下文管理。
3. **upstream 冲突的处理思路**（技术点，可直接用）：
   - fork 时尽量不改核心代码，通过插件、配置、继承或扩展点（自定义工具、中间件）实现定制，保持 patch 面积小。
   - 记录并隔离自己的改动，保持小而独立的提交，便于变基。
   - 定期把 upstream 合并或 rebase 到本地分支，而不是长期不同步；固定上游版本并用升级流程验证。
   - 冲突发生时先理解上游改动意图，再决定保留、适配还是回馈上游（提 PR）。
   - 为定制部分写回归测试，升级后用测试发现行为变化。

### 8. 意图识别模型线上漂移了怎么发现，badcase 怎么回流，用不用在线蒸馏

**参考答案**

结论：用指标监控发现漂移，用"日志 → 挖掘 → 标注 → 训练集 + 回归集 → 灰度发布"的闭环回流 badcase；蒸馏通常采用定期离线蒸馏，而不是严格意义的在线实时蒸馏。

**发现漂移**：

- 监控输入和输出分布：意图类别占比、置信度分布、拒识率、兜底到 LLM 的比例，用 PSI、KL 散度等衡量与基线的偏差。
- 业务侧信号：用户重复说、改口、取消、投诉、转人工的比例。
- 定期人工抽检标注，计算线上真实准确率。
- 监控新词、新表达（OOV）和新功能上线带来的新意图。

**badcase 回流**：

1. 线上记录输入、预测结果、置信度、用户后续行为。
2. 低置信度、被用户纠正、与 LLM 判断不一致的样本进入候选池，聚类去重。
3. 人工或 LLM 辅助标注，质检后入训练集；同时加入固定的回归评测集。
4. 重训后离线评测，与线上版本对比，通过后灰度发布，可回滚。

**蒸馏**：把大模型（LLM）的判断作为教师标签，训练小模型以降低延迟和成本。常见做法是周期性地用线上日志经 LLM 打标，离线蒸馏、评测后发布。真正的在线蒸馏风险较大（教师标签噪声、分布反馈环路、没有评测闸门），要谨慎。

### 9. RAG 幻觉怎么防，未检索到时拒答策略，强制引用怎么在 prompt 和解析层双管齐下

**参考答案**

结论：防幻觉要在检索、生成、校验三层都做控制：检索不足就拒答，生成时强制引用，解析时校验引用真实有效。

**1. 检索层**：混合检索 + 重排；设相关性阈值，若最高分低于阈值或结果为空，不让模型自由发挥，直接走拒答或澄清。

**2. 拒答策略**：

- 在 prompt 中明确"只依据给定资料回答，资料不足时回答'未找到相关信息'"。
- 代码层做硬判断：检索结果为空或分数过低时，不调用生成，直接返回固定话术或转人工、转搜索。
- 降低 temperature，减少随机发挥。

**3. 强制引用（双管齐下）**：

- **Prompt 层**：给每个片段编号（如 `[1]`、`[2]`），要求每条结论后标注引用编号，并要求使用 JSON 等结构化输出（如 `answer`、`citations` 字段）。
- **解析层**：
  - 校验输出格式，不合法则重试或降级。
  - 检查引用编号确实存在于本次检索结果中，剔除伪造引用。
  - 可进一步检查引用的片段是否真的支持该结论（文本重合度、NLI / 蕴含模型或 LLM 判定）。
  - 没有有效引用的结论删除或降级为"无依据"，必要时整条拒答。

**4. 持续评测**：用忠实度（faithfulness）、引用准确率等指标回归。

### 10. Embedding 模型选 BGE 还是自训，维度多少，微调时负样本怎么采

**参考答案**

结论：先用开源的 BGE 系列做基线，通过自建评测集衡量；只有当领域术语多、基线召回明显不足时，才在 BGE 基础上微调，而不是从零自训。

**选型**：BGE 中文效果成熟，有不同规模（small、base、large，以及支持多语言、长文本和多种检索方式的 bge-m3）。从零自训需要大量数据和算力，性价比低。

**维度**：由模型决定，常见的是 bge-small 为 384 维，bge-base 为 768 维，bge-large 和 bge-m3 为 1024 维。维度越大表达能力越强，但存储和检索成本越高；端侧可选小模型，也可以对向量做量化或降维。具体以所用模型的实际配置为准。

**微调与负样本**：通常采用对比学习（如 InfoNCE 损失），训练数据是 `(query, 正例, 负例)`。

1. **批内负样本（in-batch negatives）**：同一个 batch 中其他 query 的正例天然是负例，几乎零成本，batch 越大效果越好。
2. **难负样本（hard negatives）**：用基线模型或 BM25 检索 query 的 top-k，排除真正的正例后，取排名靠前但不相关的文档，这类样本最能提升区分能力。
3. **注意假负例**：top-k 里可能混有其实相关但未标注的文档，常见做法是跳过最靠前的若干名，或用重排模型过滤。
4. 微调后要在独立评测集上看召回率和 MRR 等指标，并确认通用能力没有明显退化。

### 11. 图数据库（Neo4j）在 Agent 里能干什么，车辆知识图谱 + 意图推理怎么接 RAG

**参考答案**

结论：图数据库擅长表达实体及其关系，适合多跳推理和结构化知识；与向量 RAG 互补，向量负责语义召回，图负责关系推理。

**能做的事**：

- 存储实体与关系，如 车型 → 配置 → 功能 → 故障码 → 解决方案。
- 多跳查询：例如"这辆车的某个功能依赖哪些前提条件"，用向量检索很难一次找全。
- 实体消歧和关系校验、做 Agent 的长期记忆（用户偏好、历史事件的关联）。

**车辆知识图谱接 RAG（GraphRAG 思路）**：

1. 意图识别 / 实体抽取：从用户问话中识别车型、功能、故障现象等实体，链接到图谱节点。
2. 双路召回：向量检索得到文本片段；图检索以实体为起点取 1 到 2 跳邻居子图。
3. 融合：把子图（三元组或其文本化描述）和文本片段一起放进 prompt，并保留来源便于引用。
4. 意图推理：用图中的约束（某车型是否有该功能、版本是否支持）校验意图的可执行性，例如用户要求的功能该车型不支持就直接告知。

**注意**：让 LLM 生成 Cypher 时要限制只读、基于 schema 和模板、做语法与权限校验，避免注入和写操作；复杂场景优先用参数化的查询模板。

### 12. Kafka 在 Agent 系统里承担什么角色，工具回调异步化怎么保证顺序和幂等

**参考答案**

结论：Kafka 在 Agent 系统里主要用于解耦和异步化：长耗时工具的异步回调、事件流（trace、审计、日志）、评测数据回流和削峰。

**顺序性**：Kafka 只保证单个分区内有序。把需要保序的消息用同一个 key（如 `session_id` 或 `order_id`）发送，同 key 落在同一分区；同一分区在同一消费组内只有一个消费者处理。并行度靠分区数扩展。

**幂等**（重点是端到端）：

- **生产端**：开启 `enable.idempotence=true`（配合 `acks=all`），防止重试造成分区内重复。
- **消费端**：默认至少一次投递，可能重复消费，所以业务处理必须幂等：
  - 以事件唯一 ID 或业务幂等键做去重（数据库唯一索引、Redis `SET NX`）。
  - 业务写入使用 upsert 或带状态机的更新（如订单状态只能前进）。
  - 处理成功后再提交 offset（手动提交），或把"处理结果与 offset/去重记录"放在同一事务里。
- **失败处理**：设置重试 topic 和死信队列（DLQ），避免一条坏消息阻塞整个分区。
- **回调关联**：回调消息携带 `tool_call_id` 和 `thread_id`，用来恢复对应的 LangGraph 线程；对过期或乱序回调按版本号或状态检查丢弃。

### 13. 场景题：Agent 连续 5 步调工具都失败，第 6 步该继续还是降级，降级路径怎么设计

**参考答案**

结论：不应该盲目继续，应当触发降级。连续失败说明当前策略大概率无效，继续只会浪费时间、token，还可能造成副作用。

**判断机制**：

- 区分错误类型：瞬时错误（超时、5xx、限流）可以有限次指数退避重试；确定性错误（参数错误、权限不足、资源不存在）重试没用，应让模型修正参数或换策略。
- 设置失败预算：连续失败次数、总步数、总耗时、token 预算，任何一个超限就停止当前路径。
- 对下游工具加熔断器（断路器），故障时直接快速失败，不再调用。
- 检测重复：连续用相同参数调同一个工具，视为死循环。

**降级路径（逐级）**：

1. **替代工具或备用服务**：切换备用数据源。
2. **缓存或静态数据**：使用最近一次成功的结果，并告知用户数据可能不是最新。
3. **规则兜底或简化能力**：只完成能完成的部分（部分成功）。
4. **向用户澄清或求助**：说明遇到什么问题，询问是否换种方式。
5. **转人工或明确的失败话术**：给出清晰、简短的反馈，不要沉默。

**其他要点**：已产生副作用的步骤需要补偿或回滚（Saga 思想）；座舱场景下降级话术要简短并保证驾驶安全；所有失败写入 trace，用于后续分析。

### 14. 手撕算法：LeetCode 200 岛屿数量（DFS / BFS 都行，顺带问下并查集解法）

**参考答案**

思路：遍历网格，遇到未访问的陆地 `'1'` 就计数加一，并用 DFS / BFS 把与它相连的陆地全部标记为已访问（可以直接改成 `'0'`，若不允许改原数据则用 visited）。

复杂度：时间 \(O(mn)\)，空间：BFS / 迭代 DFS 最坏 \(O(mn)\)（队列或栈）；递归 DFS 最坏递归深度 \(O(mn)\)，Python 默认递归深度有限，大网格建议用迭代写法。

BFS 解法：

```python
from collections import deque
from typing import List

def numIslands(grid: List[List[str]]) -> int:
    if not grid:
        return 0
    m, n = len(grid), len(grid[0])
    count = 0
    for i in range(m):
        for j in range(n):
            if grid[i][j] == '1':
                count += 1
                grid[i][j] = '0'
                q = deque([(i, j)])
                while q:
                    x, y = q.popleft()
                    for dx, dy in ((1, 0), (-1, 0), (0, 1), (0, -1)):
                        nx, ny = x + dx, y + dy
                        if 0 <= nx < m and 0 <= ny < n and grid[nx][ny] == '1':
                            grid[nx][ny] = '0'
                            q.append((nx, ny))
    return count
```

**并查集解法**：把每个陆地格子当作一个节点，对相邻的陆地做 `union`。初始岛屿数等于陆地格子数，每次成功合并（两个不同的根）岛屿数减一，最终剩下的就是答案。使用路径压缩和按大小（或秩）合并，近似 \(O(mn \cdot \alpha(mn))\)。

```python
def numIslands_uf(grid):
    if not grid:
        return 0
    m, n = len(grid), len(grid[0])
    parent = list(range(m * n))
    size = [1] * (m * n)
    count = sum(grid[i][j] == '1' for i in range(m) for j in range(n))

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x

    def union(a, b):
        nonlocal count
        ra, rb = find(a), find(b)
        if ra == rb:
            return
        if size[ra] < size[rb]:
            ra, rb = rb, ra
        parent[rb] = ra
        size[ra] += size[rb]
        count -= 1

    for i in range(m):
        for j in range(n):
            if grid[i][j] == '1':
                if i + 1 < m and grid[i + 1][j] == '1':
                    union(i * n + j, (i + 1) * n + j)
                if j + 1 < n and grid[i][j + 1] == '1':
                    union(i * n + j, i * n + j + 1)
    return count
```

并查集的优势是适合动态加点的变体（LeetCode 305 岛屿数量 II）。

### 2. 项目里最难的 Agent 故障是哪次，状态错乱还是工具超时，怎么定位的

**答题思路**

用你真实经历回答，不要编造细节。推荐 STAR 结构，并突出排查方法：

1. **现象**：用户或监控看到了什么（循环不结束、答非所问、重复下单、响应变慢），影响范围多大。
2. **定位过程**（这是重点）：
   - 先看 trace：每一步的 prompt、模型输出、工具入参出参、耗时。
   - 缩小范围：是特定用户、特定工具、特定版本，还是特定流量时段。
   - 区分两类问题：状态错乱常见原因有并发写同一会话、checkpoint 没有 reducer 合并导致覆盖、中断恢复节点重放；工具超时常见原因有下游慢、线程池被占满、没有设超时、重试风暴。
   - 复现：用 checkpoint 回放该线程的状态，或用日志构造最小复现。
3. **根因与修复**：给出具体措施，例如会话级串行锁、幂等键、超时与熔断、线程池隔离、加最大步数。
4. **预防**：加监控告警、回归用例、混沌或故障注入测试。
5. **复盘**：你从中学到了什么。

### 3. 你们 Agent 评测集怎么建，任务完成率、工具准确率、幻觉率分别怎么量化

**参考答案**

结论：评测集要来自真实线上流量并覆盖长尾，指标分层定义，自动评测加人工抽检，并纳入发布前的回归闸门。

**评测集构建**：

- 来源：脱敏后的线上真实请求、人工构造的边界用例、历史 badcase、对抗样本。
- 每条样本包含：输入（含上下文）、期望意图、期望工具及参数、期望结果或判分标准。
- 按场景分层（导航、充电、车控、知识问答）和难度分层，保持版本固定以便对比，并持续增补。

**指标量化**：

- **任务完成率**：完成的任务数 / 总任务数。"完成"必须明确定义：最终状态是否达成（如订单状态、导航目的地正确），优先用环境状态做程序化判定，难以程序化的再用 LLM 评审加人工抽检。同时看平均步数、耗时。
- **工具准确率**：分层统计 —— 工具选择是否正确、参数是否正确（可按字段逐一匹配）、调用顺序是否合理、是否有多余调用。可以统计 精确率 / 召回率 / F1。
- **幻觉率**：存在不被上下文或工具结果支持的结论的回答占比。对 RAG 看忠实度（claim 是否被检索片段支持）和引用准确率；对 Agent 还看"编造工具结果""声称已完成但实际未执行"。可以用 LLM-as-judge 拆分 claim 逐条核查，并用人工样本校准评审模型的可靠性。

**注意**：LLM 评审自身有偏差，要做一致性校验；LLM 输出随机，需多次运行取均值；线上线下指标要对应。

### 4. 多 Agent 成本怎么控，token 预算超限时先砍记忆还是砍检索还是砍规划

**参考答案**

结论：没有固定顺序，原则是"先砍对结果贡献最小、可压缩的部分"，规划和安全约束最后动。一个常见的次序是：先压缩历史和工具输出，再收紧检索，最后才简化规划。

**预算管理**：给每个请求、每个 Agent 设 token、步数、耗时预算，记录实际消耗，超限前触发降级，而不是超限后才中断。

**超限时的取舍**：

1. **记忆 / 历史**：把旧对话做摘要，截断冗长的工具返回（只保留关键字段），去掉与当前任务无关的内容，一般收益最大、质量损失最小。
2. **检索**：减少 top-k、缩小 chunk、先重排后只保留最相关的几条；对简单问题跳过检索。
3. **规划**：规划决定任务是否能成功，所以尽量保留；可以改为模板化计划，或用小模型规划，而不是直接砍掉。

**其他降本手段**：

- 模型分级路由：简单任务用小模型，复杂任务才用大模型。
- 提示词缓存（prompt caching）：固定的 system prompt 和工具定义放在前缀。
- 缓存工具结果和 embedding 结果。
- 限制多 Agent 之间的传递内容，传摘要或引用而不是全文。
- 能用单 Agent 完成的不拆多 Agent，因为每增加一个 Agent 都有重复上下文的成本。

### 5. 技术选型：LangGraph vs 自研 while-loop harness，什么体量下后者更合适

**参考答案**

结论：流程简单、工具少、单 Agent 的场景，自研 while-loop 更轻、更透明；一旦需要持久化恢复、人工介入、分支并行、多 Agent，用 LangGraph 这类框架更划算。

**自研 while-loop 更合适**：

- 单 Agent，工具数量有限，流程基本是"调模型 → 调工具 → 循环"。
- 团队希望完全掌控提示词、上下文管理和错误处理，减少框架抽象和版本升级带来的风险。
- 对依赖体积、启动时间、调试透明度有要求。
- 但需要自己补上：最大步数与预算、超时重试、工具校验、trace，否则循环容易失控。

**LangGraph 更合适**：

- 需要 checkpoint 持久化、断点恢复、长时间等待用户确认（human-in-the-loop）。
- 有条件分支、并行节点、子图、多 Agent 协作。
- 需要时间回溯、状态查看和可视化调试。

**权衡**：框架节省了状态机、持久化、中断等基础设施的开发，代价是学习成本、抽象泄漏和升级兼容性；自研初期快，但随着功能增加会逐步重造一个简陋的框架。可以先自研简单版，把状态、工具、观测接口设计清晰，需求复杂化时再迁移。

### 6. Codex 实战题：让 Agent 改一个 Java Spring 接口并跑通单元测试，harness 怎么隔离沙箱、怎么把编译错误喂回模型

**参考答案**

结论：在隔离的沙箱里改代码并运行构建，harness 负责执行命令、解析结构化的错误、截断后喂回模型，并限制重试次数和修改范围。

**1. 沙箱隔离**

- 容器（Docker）、更强隔离的 gVisor 或 Firecracker 微虚拟机；用独立工作副本（git worktree 或复制仓库），不污染主分支。
- 限制资源：CPU、内存、进程数、执行超时；非 root 用户运行；不注入生产密钥。
- 网络默认关闭，只放行依赖仓库镜像（Maven 镜像）；挂载只读的依赖缓存（如 `~/.m2`）加速构建。
- 文件系统只开放项目目录写权限，危险命令走权限审批或黑名单。

**2. 执行与反馈循环**

1. 模型以补丁（diff）或文件编辑工具修改代码。
2. harness 运行 `mvn -q test -Dtest=XxxTest` 或 `./gradlew test`，先编译再跑测试。
3. 解析输出：
   - 编译错误：提取 `javac` 的 `文件:行号: error: 信息`，并附上错误位置前后的源码片段。
   - 测试失败：读取 Surefire 报告（`target/surefire-reports`）中的失败用例、断言信息和堆栈关键行。
4. **裁剪**：只保留关键的错误信息，去掉下载依赖和无关日志，避免淹没上下文。
5. 作为工具结果回填给模型，让它继续修改。
6. **终止条件**：最大重试轮数；同一错误重复出现则换策略或停止并上报；通过后再跑相关模块的完整测试。

**3. 防作弊与质量保证**

- 禁止模型为了通过测试而修改或删除测试（保护测试文件，或检测测试文件 diff）。
- 最终产出 diff 供人工评审，并检查接口兼容性（是否破坏已有调用方）。
- 记录整个过程的 trace，方便复盘。

### 7. 图数据库和向量库怎么配合做 Agent 长期记忆，Neo4j + Milvus 双写一致性怎么保

**参考答案**

结论：向量库负责按语义召回相似记忆，图库负责记忆之间的实体关系与多跳推理；一致性上不要追求跨库分布式事务，而是用"单一事实源 + 异步最终一致 + 幂等 + 对账"。

**配合方式**：

- 一条记忆（如"用户喜欢少糖拿铁"）有唯一的 `memory_id`，文本向量存 Milvus，实体和关系（用户 → 偏好 → 咖啡类型）存 Neo4j。
- 读取时：先用向量检索召回相关记忆，再通过实体在图中扩展关联信息，合并后注入上下文。

**双写一致性**：

1. **确定单一事实源**：例如先写入主库（MySQL）或 Neo4j，作为权威数据。
2. **异步同步**：采用事务发件箱（outbox）或 CDC，把变更事件通过消息队列投递给下游同步到另一个库，由消费者完成写入。
3. **幂等写入**：两边都使用同一个 `memory_id` 作主键，用 upsert；带版本号，旧版本事件丢弃。
4. **删除用墓碑（软删除）**：先标记删除再异步清理，避免删除事件乱序导致数据复活。
5. **对账修复**：定时任务比较两边的 ID 和版本，补写缺失、清理多余。
6. **读时校验**：向量召回出 ID 后，回源校验该记忆是否仍有效，容忍短暂不一致。
7. 失败处理：重试 + 死信队列 + 告警。

为什么不用分布式事务（2PC）：两种库都不原生支持统一的分布式事务，实现复杂且影响性能；记忆类数据通常能接受最终一致。

### 8. RocketMQ 和 Kafka 在你这套系统里分工，事务消息用哪套

**参考答案**

结论：Kafka 适合高吞吐的事件流和日志类数据；RocketMQ 内置事务消息、延迟消息和顺序消息，更适合有强业务语义的订单类消息。事务消息的场景优先使用 RocketMQ。

**分工**：

- **Kafka**：Agent 的 trace、审计日志、用户行为和评测数据回流、工具调用事件流，特点是吞吐大、可回溯重放、易于接入流式计算。
- **RocketMQ**：业务消息，如下单、支付状态变更、需要延迟的超时处理（订单超时关闭）、需要保证本地事务与消息发送一致的场景。

**事务消息**：

- RocketMQ 的事务消息采用"半消息（half message）+ 本地事务 + 回查"机制：先发半消息（对消费者不可见）→ 执行本地事务 → 提交或回滚半消息；若长时间没有结果，Broker 回查生产者的本地事务状态。可以保证本地数据库事务与消息发送的最终一致。
- Kafka 的事务主要保证在 Kafka 内部"读 - 处理 - 写"跨分区、跨 topic 的原子性（Exactly-Once），并不能让本地数据库事务和消息发送原子。若用 Kafka，需要配合**本地消息表 / 发件箱（outbox）模式**：业务数据和消息在同一个数据库事务内落库，再由独立进程投递到 Kafka。

无论哪套，消费端都要做幂等。

### 9. 你最近在学什么，LangGraph 新版本 checkpoint 改动、MCP 协议、OpenAI Agents SDK 随便挑一个讲

**答题思路**

选你真正研究过的一个来讲，不要为了显得新而硬凑。结构建议：这个东西解决什么问题 → 核心机制 → 与我们项目的结合点 → 我踩过的坑或还没解决的问题。以 MCP 为例，可以包含的要点：

1. **解决的问题**：此前每个模型 / 应用与每个工具都要单独对接，是 M×N 的集成。MCP（Model Context Protocol）定义了统一的协议，让 AI 应用（Client）与工具和数据源（Server）标准化对接。
2. **机制**：基于 JSON-RPC 2.0；Server 向外暴露 Tools（可执行工具）、Resources（可读数据）、Prompts（提示模板）；传输方式有本地的 stdio 和基于 HTTP 的 Streamable HTTP（取代早期的 HTTP + SSE）；有能力协商和初始化流程。
3. **结合点**：把座舱里的车控、地图、充电、订餐封装成 MCP Server，让 Agent 动态发现工具，而不是在代码里硬编码。
4. **要注意的问题**：工具描述本身可能成为提示注入的入口，需要权限、鉴权、用户确认和最小权限原则；工具数量多时会占用上下文，要做按需加载或检索；远程 Server 的延迟与可用性。

如果选 LangGraph 的 checkpoint 或 OpenAI Agents SDK，具体版本变化请以官方发布说明为准，只讲你确认过的内容，避免凭印象说错。

### 10. 怎么带人推 Agent 项目，算法同学和后端同学对 Agent 边界认知不一致怎么掰

**答题思路**

不要编造具体的团队规模和成果，用方法论加你真实的经历组织：

1. **先对齐目标，不对齐立场**：用业务指标（任务完成率、延迟、成本）作为共同语言，而不是争论谁的模块更重要。
2. **划清职责边界**（可以用接口契约讲）：
   - 算法侧：模型、提示词、检索与召回质量、评测方法。
   - 后端侧：工具服务、状态与持久化、稳定性、幂等、限流、可观测。
   - 双方共同的接口：工具的 Schema、trace 格式、评测集。
3. **用数据和评测说话**：当分歧是"这个应该由模型解决还是由代码规则解决"，用评测集跑 A/B，用结果决定。
4. **机制保障**：定期的 badcase review、统一的 trace 平台、灰度发布与回滚流程、文档化的设计决策（ADR）。
5. **带人方面**：先拆小目标，让每个人拿到可交付、可验证的任务；关键设计做评审；关注新人成长，并公开分享复盘。
6. 强调：边界会随着模型能力变化，需要定期复盘调整，而不是一次定死。

### 11. 业务方要 2 周上线一个座舱 Agent demo，但 RAG 知识库没齐，你怎么排优先级和画甘特

**参考答案**

结论：2 周的 demo 目标是"跑通关键场景、可演示、可迭代"，而不是完整。先砍范围，锁定 1 到 3 个高价值场景，知识库不齐就用有限子集 + 明确的兜底，并把风险提前讲清楚。

**优先级原则**：

1. 与业务方对齐"demo 的成功标准"和必须展示的场景，其余放到后续迭代。
2. 主链路优先（语音输入 → 意图 → 工具调用 → 语音输出），RAG 放在其后，因为没有知识库时仍可以用少量高频问答或 mock 数据展示。
3. 风险高的先做（外部接口联调、延迟、语音链路）。

**RAG 知识库不齐的做法**：

- 只导入演示场景相关的核心文档（如常见功能说明 FAQ），先用 20% 的高频内容覆盖大部分演示。
- 没检索到时有明确的拒答话术，不让模型编造。
- 同时并行推进知识库的补全（让业务方指定负责人和交付时间），后续增量入库。

**两周排期示例（甘特思路）**：

| 时间 | 工作 |
| --- | --- |
| 第 1 到 2 天 | 需求冻结、场景与验收标准、接口和数据清单 |
| 第 2 到 5 天 | 主链路开发：语音接入、意图识别、工具编排，工具先用 mock |
| 第 4 到 8 天 | 接入真实工具接口；并行：知识库清洗、切块、入库 |
| 第 8 到 10 天 | RAG 接入与拒答策略、安全与降级 |
| 第 10 到 12 天 | 评测集测试、badcase 修复、延迟优化 |
| 第 13 到 14 天 | 演示彩排、兜底方案、文档 |

**风险管理**：把依赖项（知识库交付、接口权限）作为关键路径，设检查点，延期就缩范围而不是压测试；保留演示失败时的备用方案（录屏或固定脚本）。

### 12. 手撕算法：LeetCode 146 LRU 缓存（要求 O(1) 读写，顺便问下用 Java LinkedHashMap 和 Python OrderedDict 的坑）

**参考答案**

思路：哈希表 + 双向链表。哈希表按 key 找到链表节点（O(1)），双向链表维护使用顺序：最近使用的放头部，最久未使用的在尾部。`get` 命中时把节点移到头部；`put` 时若 key 存在则更新并移到头部，不存在则插入头部，超过容量就删除尾部节点（并同步删哈希表）。用哨兵头尾节点简化边界处理。所有操作均为 \(O(1)\)，空间 \(O(\text{capacity})\)。

```python
class Node:
    def __init__(self, key=0, val=0):
        self.key = key
        self.val = val
        self.prev = None
        self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}
        self.head, self.tail = Node(), Node()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_front(self, node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.map:
            return -1
        node = self.map[key]
        self._remove(node)
        self._add_front(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            node = self.map[key]
            node.val = value
            self._remove(node)
            self._add_front(node)
            return
        if len(self.map) == self.cap:
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]
        node = Node(key, value)
        self.map[key] = node
        self._add_front(node)
```

**Java 的 LinkedHashMap 写法**（第三个构造参数 `true` 表示按访问顺序）：

```java
import java.util.LinkedHashMap;
import java.util.Map;

class LRUCache {
    private final int capacity;
    private final Map<Integer, Integer> map;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.map = new LinkedHashMap<Integer, Integer>(capacity, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
                return size() > LRUCache.this.capacity;
            }
        };
    }

    public int get(int key) {
        return map.getOrDefault(key, -1);
    }

    public void put(int key, int value) {
        map.put(key, value);
    }
}
```

**Java LinkedHashMap 的坑**：

- 默认是插入顺序，必须用三参数构造函数并把 `accessOrder` 设为 `true` 才是 LRU。
- 访问顺序模式下 `get` 也会修改链表结构，所以**读操作也不是线程安全的**；多线程需要加锁（`synchronized` 或 `Collections.synchronizedMap`），或者使用 Caffeine 等成熟缓存。
- 迭代过程中调用 `get` 会触发 `ConcurrentModificationException`。
- `removeEldestEntry` 在插入新元素后被调用，返回 `true` 则删除最老元素；容量判断写 `size() > capacity`。

**Python OrderedDict 的坑与写法**：

```python
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.d = OrderedDict()

    def get(self, key: int) -> int:
        if key not in self.d:
            return -1
        self.d.move_to_end(key)
        return self.d[key]

    def put(self, key: int, value: int) -> None:
        if key in self.d:
            self.d.move_to_end(key)
        self.d[key] = value
        if len(self.d) > self.cap:
            self.d.popitem(last=False)
```

- 普通的读取（`d[key]`）**不会**更新顺序，必须显式调用 `move_to_end`。
- 淘汰最老元素用 `popitem(last=False)`，默认的 `popitem()` 弹出的是最新的（`last=True`）。
- 更新已存在 key 的值不会改变其位置，需要自己 `move_to_end`。
- 两个 `OrderedDict` 比较相等时会考虑顺序，而与普通 dict 比较时不考虑顺序。
- 多线程同样需要自己加锁，复合操作（先查后改）不是原子的。
- 如果是业务代码而不是面试，可以直接用 `functools.lru_cache`（适用于函数缓存）。

### 2. 为什么看小鹏 AI Agent 岗，座舱和互联网 Agent 场景差异你怎么看

**答题思路**

分"为什么选"和"差异理解"两部分，不要空泛夸公司，也不要编造内部信息：

1. **动机**：对智能座舱这类软硬结合场景的兴趣；Agent 在真实物理环境中落地比纯线上更有挑战；个人能力（Java + Python、Agent 工程化）与岗位的匹配点。
2. **差异（体现你的理解）**：
   - **算力与延迟**：端侧算力有限，对首包延迟敏感，需要端云协同和流式输出。
   - **输入**：语音有噪声、口语化、歧义多，可能存在误唤醒和误触。
   - **安全**：行车场景下操作要有安全边界，车控类操作需要确认和白名单，故障要可降级。
   - **环境状态**：车速、位置、电量等车辆上下文是 Agent 的重要输入。
   - **网络**：弱网和离线场景需要本地兜底。
   - 相比之下，互联网 Agent 更关注内容与功能广度，对安全与实时性的约束相对松。
3. 收尾：说明你想在这样约束更强的环境里积累工程经验。

### 3. 上家离职原因，跟主管闹过矛盾没，怎么处理的

### 4. 期望薪资，拿没拿其他 offer，小鹏给不到怎么选
