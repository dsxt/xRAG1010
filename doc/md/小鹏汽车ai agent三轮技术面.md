### 2. 介绍你做过的最复杂的 AI Agent 或 LLM 应用项目，说清你在里面的角色和技术选型

**答题思路**

4. 按时间讲一条请求：鉴权 → 会话上下文 → 意图和槽位 → 规划 → 工具（校验、超时、幂等）→ 回复。

### 3. 用户说「我想查一下我上周订的车现在到哪了」，你们怎么做意图识别？有哪些方案（规则路由 / 语义相似度 / 小模型分类 / LLM Router），各有什么优缺点？

**参考答案**

这句话的意图是查询订单履约状态，槽位至少有时间「上周」和对象「我订的车」。识别结束后还没有订单号，「订」也可能是购车或预约试驾；槽位对不上唯一订单时先澄清，再查物流。

四种方案：

- 规则路由：关键词、正则或意图树。延迟低、行为稳定、命中原因可解释。说法一变（「车子走到哪儿了」）就漏，规则会随话术膨胀。
- 语义相似度：把用户话和各意图的示例做成向量，取最近意图。换说法时比较稳，不用训练。相邻意图（查订单、改订单）容易贴在一起，阈值要靠混淆对来调，槽位仍要另抽。
- 小模型分类：对封闭意图做分类，槽位用序列标注或另一次抽取。延迟和成本都低于大模型往返，精确率和召回可以离线看。新意图要补标注再训练，多意图和域外话术要单独有类，否则会被塞进最接近的类。
- LLM Router：把意图清单和参数 schema 交给模型，输出结构化意图、槽位和是否需要澄清。新意图靠说明就能接，复合句也能拆。一次调用的延迟、费用和输出波动都更高，结果仍要做 schema 校验。

线上按成本往下漏：规则吃掉明确指令，小模型或向量路由处理高频，置信度低、域外或多意图再交给 LLM。置信度不够就澄清。路由错了会调错工具，所以评测看易混意图的混淆矩阵，看整体准确率不够。

### 4. LangChain 中 Agent、Chain、Tool、PromptTemplate 各自职责是什么？一个典型的 AgentExecutor 执行流程是怎样的？

**参考答案**

四个对象分工不同。Agent 根据当前状态决定下一步是调用工具还是结束，它发出动作，执行在外部。Chain（LCEL）把提示、模型、解析器等步骤串成输入输出确定的管道。Tool 是一项外部能力，带名称、描述、参数 schema 和实现；名称和描述会进入模型上下文。PromptTemplate 负责把变量填进发给模型的消息。

新代码里的 Agent 运行时多用 LangGraph。AgentExecutor 是经典循环，一轮是这样走的：

1. 用系统说明、工具 schema、用户输入和已有的中间步骤拼出提示。
2. 调模型，把输出解析成工具动作（名称 + 参数）或结束。
3. 动作的名称必须在注册表里。找到工具后校验参数、执行，得到观察；名称不存在就记下错误观察。
4. 把动作和观察追加进中间步骤，回到第 2 步。
5. 模型给出结束、达到最大步数或最大时长时停止。到步数上限时，基于已有观察返回明确的停止结果。
6. 解析失败时，把解析错误当作观察喂回模型，并占用一步重试预算。

Tool 的描述是给模型的契约。步数、超时和工具白名单由 Executor 管，写在提示里的「请勿过多调用」替代不了这个循环。

### 5. LangChain 和 LangGraph 的核心区别？为什么说 LangChain 适合线性 Chain，LangGraph 适合复杂多步工作流？

**参考答案**

Chain / LCEL 表达的是往前流动的计算：检索、填提示、生成、解析，步骤事先定好。中间值在这次调用的过程里，进程停了就整段重来。AgentExecutor 内部有循环，但循环是执行器的专门逻辑，检查点和人工插入点要另外接。

LangGraph 把应用建成有状态的图。节点读一份共享 State 并返回局部更新，字段用 reducer 合并，消息列表常用追加语义。普通边表示做完一定去哪；条件边读结构化状态，返回下一个节点名，也可以回到前面的节点。`compile` 时传入 checkpointer，每个 super-step 保存状态。

所以直线、失败了可以整段重跑的流程用 Chain。会出现分支、循环、失败后换边、等人审或进程重启后继续的流程，用带检查点的图。现在不少 LangChain Agent 的底层运行时就是 LangGraph，包名本身说明不了控制流。权限、预算和审计仍然放在图外的运行时里。

### 6. RAG 基础流程是什么？文档切分（Chunking）有哪些策略，按固定长度切和按语义切各有什么坑？

**参考答案**

基础流程是：解析文档并保留标题、来源和版本；切成块；用同一套块建向量索引和关键词索引；在线时把查询嵌入，带过滤条件召回，必要时重排，再把块和出处交给模型生成。文档更新按文档 id 替换旧块，评测跟着索引版本走。

按固定 token 长度切，实现稳定，也容易切在句子、步骤或表格中间，召回只剩半句。重叠太大时，近重复块占满 Top-K；块太长带进噪声，块太短会丢掉主语。

按标题、段落或相邻句相似度变化来切，边界跟主题走。长度会差很多，超长段还是要再截断；阈值一变，渐变主题会切得过碎或过粗。一个结构完整的章节里往往有多个可单独提问的事实，语义完整不等于适合检索。

实务上先按文档结构切，超长块再按窗口滑。检索用小块，送给模型时带上父块和元数据。

### 7. Hybrid Search（向量检索 + BM25 / 关键词）是什么？为什么只用向量检索不够？Rerank（重排序）解决什么问题？

**参考答案**

Hybrid Search 对同一批块走两路召回：向量一路找语义相近的文本，BM25 或关键词一路找词项重合高的文本，再用倒数排名融合（RRF）等不依赖原始分数尺度的方法合成候选。余弦相似度和 BM25 分数不能直接相加。

只用向量时，订单号、故障码、零件号和必须原样匹配的短语容易被近义句压过去；领域词在嵌入空间里也可能挤在一起。只用关键词时，「还能开多远」对不上「续航」。两路必须索引同一批块，过滤要在各自召回时生效，避免先取 Top-K 再过滤把结果滤空。

Rerank 用交叉编码器等模型对「查询，候选块」成对打分，把已经召回的前几十条重新排序，再取少数几条进上下文。它修正的是候选内部的次序。相关文档若没进候选集，重排找不回来，所以召回和重排要分开评。中文查询要用能处理中文的重排模型。

### 8. Agent 的短期记忆（Short-term Memory）和长期记忆（Long-term Memory）怎么设计？多轮对话历史太长怎么压缩或截断？

**参考答案**

短期记忆是这一次会话要送进模型的工作记忆：最近的用户和助手消息、当前轮的工具观察、已确认槽位。按会话 id 存在缓存或数据库里，跟随编排图的检查点走。它受上下文窗口限制，进程重启后还要能读到。

长期记忆是跨会话仍有用的事实：稳定偏好、车辆配置、已确认且会复用的结论。按用户 id 存结构化记录或可检索片段，带时间、来源和适用范围。写入前过滤掉一次性物流状态和工具原文。取用时按相关性和时效检索少量条目，整库塞进提示会污染回答。

历史超长时按 token 预算处理：保留系统约束、最近几轮和尚未消费的工具结果；更早的工具原文先删，结论留下。再早的对话压成滚动摘要，摘要单独版本化。用户明确说过的约束（地址不能改、只查这一单）写成槽位，摘要丢了也能从槽位恢复。预算仍不够时，只检索与当前问题相关的旧轮。

### 9. Function Calling / Tool Use 的基本原理是什么？怎么防止 LLM 生成非法参数或幻觉调用不存在的工具？

**参考答案**

应用把允许调用的工具名称、描述和 JSON Schema 随对话发给模型。模型只返回结构化调用（名称和参数），代码在运行时执行，再把结果作为工具消息追加回去，模型据此继续调用或给出最终回答。一次响应可以包含多个调用；有副作用的调用由运行时串行执行，并带幂等键。

工具名称只从本次注册表解析，按表分发到函数。返回的名称不在表里就记一条错误观察，占用重试步数，到上限后停止。支持对工具名做约束解码时仍要做这层检查。

参数先过 schema：类型、必填、枚举、范围，并拒绝未声明字段。schema 通过后做业务校验，例如订单是否属于当前用户、金额上限、只读还是可写。校验失败把结构化错误交回模型修改，重试次数固定。缺必填参数时生成澄清问题。订单号这类值要能对上用户输入或前序工具结果，schema 只约束形状。

### 10. 什么是 ReAct 范式（Reasoning + Acting）？Agent Loop 的 Think → Act → Observe 循环你怎么控制最大步数和终止条件？

**参考答案**

ReAct 把推理和行动交错进行：每一步先决定下一步动作，执行后把环境返回的观察写回上下文，再决定继续还是结束。使用原生 Function Calling 时，动作就是工具调用，观察就是工具结果，推理文字可以不展示给用户，循环仍由运行时维护。

Think 读取目标、历史和上一次观察，产出工具调用或结束。Act 只执行注册表中的工具。Observe 把成功结果或错误写回状态。然后进入下一次 Think。

运行时在每次决策前检查预算：最大决策次数、墙钟时间和 token 或费用上限，任一耗尽就停止，并用已有观察生成说明进度和缺口的回复。模型明确结束、业务状态已经完成、需要用户补充参数，也是终止条件。

循环检测看结构化指纹：主体、工具名和规范化参数（去掉请求号、时间戳这类每次都会变的字段）。同一指纹再次出现就停止或改走澄清。轮询类工具单独给轮询次数和间隔。超时记为失败观察并计入步数。

### 11. 你们用没用向量数据库（Milvus / Chroma / Weaviate / Qdrant）？简单说下选型理由和使用方式

**答题思路**

先说自己线上用的哪一个，以及数据是否能出域。没用过就直接说，再用下面的标准讲选型，临时编一个集群规模会被追问穿。

1. 规模和过滤：过滤条件要在召回时生效。百万级以内、要和业务数据一起事务更新，先考虑 pgvector。更大规模、按租户和车型过滤，再看独立向量库。
2. 四个库各有侧重：Chroma 适合单机原型和评测脚本。Qdrant 部署相对轻，payload 过滤和检索做在一起。Milvus 面向更大规模的分区和索引，运维组件更重。Weaviate 把对象和向量放在一起，混合检索是常规路径。
3. 使用方式按真实链路讲：用稳定的 chunk id upsert，payload 放文档 id、版本、租户和标题；文档更新先按文档 id 删旧块再写；查询向量和入库使用同一模型、同一距离和同一套归一化。换模型就新建集合全量重写。
4. 准备两个追问：更新时旧向量怎么删，过滤之后候选变空怎么发现。

### 12. 简单说下 Embedding 模型选型要考虑什么？中文场景需要注意什么？

**参考答案**

先用自己的查询—文档集评测，中文检索榜只作参考，英文榜的名次说明不了手册和故障码好不好用。查询和文档必须用同一个模型和同一套预处理；模型一换，整个集合重新嵌入，新旧向量放在一起比距离没有意义。

维度影响内存和延迟，只有模型支持分层维度时才做截断，并在自己的召回指标上重测。切块长度要落在模型最大长度里，超出的 token 不会进入向量。距离度量按模型要求选，需要归一化就在入库和查询两侧都做。手册不能出域时，模型要能私有化部署。文档向量离线批处理，查询向量在在线路径上，延迟分开看。

中文场景里，中英混排、零件号、单位（公里和 kWh）和口语（「没电了」对「动力电池 SOC 低」）要单独做评测切片。有的模型要求查询侧加固定指令、文档侧用另一套处理，两侧按说明来。专有名词的精确匹配交给关键词索引，嵌入模型负责语义相近的说法。生成模型的隐藏状态拿来当向量，检索指标通常站不住。

### 13. 手写算法：LeetCode 139 单词拆分。给定一个字符串 s 和字典 wordDict，判断 s 是否可由字典中的单词拼接而成

**参考答案**

判断 s 能不能被字典单词首尾相接、正好覆盖。单词可以重复使用，不能剩字符，也不能用字典外的片段。

用 `dp[i]` 表示前 i 个字符能否拆成。`dp[0] = true`。枚举结尾 i，只回看最长单词以内的切点 j；前 j 个字符已经能拆开，且 `s[j:i]` 在字典里，则 `dp[i] = true`。字典放进哈希集合。朴素深搜会在「aaaaaaa / aaaa、aaa」这类重叠子问题上重复计算，所以用 DP。

设串长 n、最长词长 L。每个位置最多看 L 个切点，切片并哈希的代价与词长有关，时间约 O(n · L²)，空间 O(n + 字典)。把一次字典查找看成常数时，常写成 O(n²)。

```python
def word_break(s: str, word_dict: list[str]) -> bool:
    words = set(word_dict)
    max_len = max((len(w) for w in words), default=0)
    n = len(s)
    dp = [False] * (n + 1)
    dp[0] = True
    for i in range(1, n + 1):
        start = max(0, i - max_len)
        for j in range(start, i):
            if dp[j] and s[j:i] in words:
                dp[i] = True
                break
    return dp[n]
```

### 2. 结合你项目，说一个最复杂的多步骤 Agent 工作流——怎么拆任务、怎么处理分支/失败重试/人工介入

**答题思路**

用真实链路讲。下面是骨架，项目名和指标用你自己的。

1. 拆任务：一个节点做一件事，输入输出写在 state 里。按副作用边界拆，查询节点和会改数据的节点分开。
2. 分支：条件边只读结构化字段，例如意图、校验结果、工具状态码。用一两个真实分支说明为什么走那边。
3. 重试：超时、429、5xx 才重试，次数少、带退避和抖动。400、403 和业务拒绝直接停止。写操作有幂等键；失败后先查下游状态，确认对方没收到再决定是否重放。
4. 人工介入：高风险动作、低置信或事实冲突时挂起，持久化 thread id 和待审状态，人处理后从该点继续。等待期间释放模型连接。
5. 收在一次真实故障：停在哪个节点、恢复后那个有副作用的工具有没有执行第二次、你怎么证明没有。

### 3. LangGraph 中 StateGraph 的 Node、Edge、State 分别是什么？conditional_edge 怎么用？checkpointer 做断点续跑怎么实现？

**参考答案**

State 是一份可序列化的共享数据，节点返回局部更新，由 reducer 合并。消息字段通常追加或按 id 覆盖，普通字段默认覆盖。数据库连接留在节点外面，State 里只放检查点存得下的数据。

Node 是一步计算：读 State，调用模型、工具或检索，返回部分更新。Edge 是固定后继。条件边在节点之后执行路由函数，返回下一个节点名：

```python
def route(state: State) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return "end"

graph.add_conditional_edges("agent", route, {"tools": "tools", "end": END})
```

路由函数只读结构化字段，分支就可以单测。

checkpointer 在每个 super-step 边界保存状态。开发可用内存实现，进程一退就没了；生产用 Postgres 等持久实现。同一 super-step 里已经成功的节点会留下 pending writes，恢复时重跑失败的那个节点。需要崩溃后续跑时，用会在下一步开始前把检查点写完的耐久模式；只在整次运行退出时落盘，中间崩溃就没有步骤可恢复。

`thread_id` 用来找到这条状态，调用方式决定怎么继续：

```python
config = {"configurable": {"thread_id": thread_id}}
graph.invoke({"messages": [user_msg]}, config)  # 合并状态后从入口执行
graph.invoke(None, config)                       # 继续未完成的步骤
graph.invoke(Command(resume={"approved": True}), config)  # 应答 interrupt()
```

`interrupt()` 恢复时，该节点从头再执行，`interrupt()` 的返回值才是人的答复。有副作用的代码放在 `interrupt()` 之后，或做成幂等，或放到独立节点。静态 `interrupt_before` 停在节点之前，用 `invoke(None, config)` 继续。最新检查点若没有未完成工作，传入 `None` 会直接返回已保存结果。

### 4. 多 Agent 系统常见协作模式有哪些（Orchestrator-SubAgent / Pipeline / Debate / Swarm）？什么场景用哪种？

**参考答案**

看三件事：控制流是否固定、谁对最终结果负责、工具有没有副作用。

- Orchestrator-SubAgent：协调者拆任务、派给职责单一的子 Agent，再汇总。适合子任务边界清楚、权限要统一把关的办理流，例如查订单和查库存分开，最后由协调者答复。协调者要转述上下文，会多一次信息损失。
- Pipeline：上一步的输出是下一步的输入，例如检索、起草、合规审查。适合步骤稳定、每步模型和提示不同的流程。前一步的错误会原样流到后面。
- Debate：多个 Agent 对同一问题分别给出结论，再由裁判取舍。适合需要把分歧摊开的分析。会触发真实副作用的工具不进辩论，避免两边都去执行。
- Swarm：对等交接，当前 Agent 认为问题不属于自己时，把对话转给另一个专职 Agent。适合按领域转接。交接条件要写成明确规则，并记录已经访问过的 Agent。

有副作用的动作用单一编排者串行审批。多个 Agent 同时改同一份状态时，先规定每个字段的唯一写入者。

### 5. 多 Agent 协作时怎么避免无限循环（死循环）、信息冗余、目标冲突？你们怎么设置 max_iteration 和循环检测？

**参考答案**

死循环常见于同一工具被原样调用，或两个 Agent 来回交接。运行时设全局最大决策次数，每次决策前检查；提示里的「不要重复」替代不了这层计数。另对（Agent，工具名，规范化参数）做指纹，去掉请求号和时间戳，同一指纹再次出现就停止或改为向用户澄清。轮询状态的工具单独计数。交接路径记录经过的 Agent，回到已访问节点就交回编排者。

信息冗余来自把整段历史在 Agent 之间原样复制。子 Agent 的返回约定为结论、证据 id 和未完成项。工具原文落库，提示里放摘要和引用。

目标冲突来自几个 Agent 各持一套目标去写同一字段。每个子 Agent 只接收本子任务的目标和约束；State 里每个字段规定唯一写入者，或用明确的 reducer。两份资料不一致时写成待裁决项，停在编排者或人工，避免各自把其中一份当成已确认事实继续执行。

### 6. Agentic RAG 和 Naive RAG 区别？Agent 怎么判断「需要查知识库」还是「可以直接回答」？查回来冲突文档怎么处理？

**参考答案**

Naive RAG 每次都按固定链路召回 Top-K 再生成，查哪个库、查几次都是事先定的。和文档无关的问题也会被塞进片段。Agentic RAG 把检索当成工具：Agent 决定查不查、用什么查询、查哪个库、结果够不够；不够就改写查询再查。检索次数和 token 预算要设上限。

判断依据分成三层。对话状态或前序工具里已经有的事实直接用。价格、政策、手册、库存、物流这类会变的事实走检索，模型参数里的记忆不作为依据。规则可以先把带车型、故障码的问句送去检索；其余由模型输出结构化决定 `retrieve` 或 `answer`。低置信度走检索。每次决定记入 trace，事后才能统计该查没查和空查。

冲突时先用元数据消解：版本更新的、适用车型匹配的、官方资料优先。仍然冲突就把差异和来源一起返回，或拒绝合成一个折中结论。生成结果要求每句对应到块 id，对不上的句子不展示。

### 7. GraphRAG 是什么？相比传统向量 RAG 解决什么问题？增量更新知识图谱有什么难点？

**参考答案**

GraphRAG 用模型从文档抽取实体和关系，建成图，再按社区生成层次摘要。查询时沿实体、关系和社区摘要取证，并回到原文块核对细节。它和「把向量存在图数据库里」是两回事。

向量 RAG 擅长找表述相近的局部段落。跨多篇文档的汇总、多跳关系（某供应商涉及哪些车型、哪些故障）和图上的全局主题，单段相似度经常拼不齐。图先把同一实体的不同说法对齐，再沿边扩展，用社区摘要回答全局问题。建图和查询都更贵，实体级事实仍要回原文核对，所以它通常和向量检索一起用。

增量更新难在抽取和社区都有全局影响。同一零件的别名可能并进旧节点，也可能错误新建；合并一变，依赖它的社区和摘要都要重算。社区划分是全局算法，插入少量边就可能改变边界。关系还有时效，旧文档删除时要去掉只由它支撑的边。同一段重跑抽取，三元组可能不同，所以要有稳定的实体 id 和可审计的合并规则。

### 8. 意图识别模块如果误分类会带来什么后果？你们怎么做意图识别的评测（Precision / Recall / F1 / badcase 分析）？

**参考答案**

误分类会把请求送进错误的工具。只读被送去写操作，会改订单或触发车控；本该人工确认的高风险意图被当成闲聊，确认会被跳过；槽位安在错误意图上，会查到另一笔订单。后面的 Agent 越能执行，路由错误的破坏越大，所以要在工具执行前拦住。

评测集按意图分层，易混对、多意图、口语、语音识别错字和域外说法都要有。每个意图单独算：精确率是预测为该类的样本里有多少真是该类，低了就会误触发工具；召回是该类样本里有多少被找回来，低了就会漏执行。F1 综合这两个数。类的样本量差很大时看宏平均，也保留每个类自己的数。整体准确率会被大类盖住。

混淆矩阵用来找成对错误，badcase 再分成缺槽、多意图、指代、域外。域外要有自己的类或拒识，否则会被分进最近的业务意图。线上把离线分数和「该意图的工具成功率、人工回标」一起看，分布不一致时先改评测集。

### 9. LLM 产生幻觉的常见原因？工程中你用过哪些手段抑制幻觉（约束 Prompt / 事实校验节点 / 拒答策略 / Citation 溯源）？

**参考答案**

模型按上下文续写，材料不足时仍会补出一个像样的答案。检索没命中或不相关、工具结果和模型既有说法冲突、温度高、提示要求必须给结论，都会提高编造率。多步 Agent 里，早一步的错误观察会被后面当成事实。

约束提示写明：只根据给定材料和工具结果回答，不足就说明缺什么。这是底线，挡不住流利的编造。

事实校验做成独立节点：从草稿抽出声称，逐条对证据或再查一次工具。校验看的是声称和证据，沿用起草时那一整段上下文容易自己证明自己。

拒答写成明确策略：无命中、权限不够或置信度不够时，返回固定结构（不能回答、原因、缺什么）。读接口失败时同样走这套结构，避免用通顺的话补一个物流位置。

Citation 做到句级，绑到块 id 或工具返回字段。展示前检查引用片段是否支持该句，阻止编造编号。抑制幻觉会提高拒答率，评测同时看忠实度和任务是否真的完成。

### 10. Agent Harness 工程层是什么？和 LangChain 框架是什么关系？Harness 一般要管哪些事（调度 / 异常捕获 / 日志 Trace / 成本统计）？

**参考答案**

Harness 是模型外面的运行时：何时调模型、工具以谁的身份执行、如何记录、如何停。模型只给出下一步建议。LangChain 提供提示、工具、链这些组件，LangGraph 提供带检查点的图。它们可以用来实现 Harness 的一部分。生产还要补的权限、租户隔离、预算和审计，框架默认执行器没有全部覆盖。自研循环直接调模型 API 也可以，只要这层运行时在。

调度包括队列、并发、步数、超时，以及人审挂起后用 thread id 恢复。异常在边界上变成结构化观察，分出可重试和不可重试，栈信息留在日志里。

Trace 给一次 run 一个 trace id，模型调用、节点和工具各是 span，记下模型名、提示版本、入参出参和 token。成本按调用方累计供应商返回的 usage，超预算就停止。工具按用户身份和注册表执行，模型输出的字符串只作为参数，不作为要反射执行的代码。

### 11. Agent 调用外部 API 工具失败（超时 / 500 / 返回格式异常），你的重试、降级、Fallback 策略怎么设计？

**参考答案**

先分错误，再决定是否自动再打一次。超时、连接重置、429、502、503、504 可以重试：次数少、指数退避加抖动，429 遵守 `Retry-After`。重试限于幂等请求；创建、下单、改状态要带 `Idempotency-Key`，没有键就停止。400、403、404 和业务拒绝不重试。401 刷新凭证后再试一次。

返回体先过 schema。校验失败可以把错误交回模型或再请求一次下游，仍失败就当工具失败，原始脏数据不进下一步。

读接口降级为缓存中带时间戳的结果，或明确的「暂时未知」。写接口失败后记下请求号和对端是否可能已执行，停在待确认，换一个参数或换一个写接口再执行会制造第二笔变更。备用模型或备用供应商只承接契约相同的只读能力；没有等价写能力时，Fallback 是转人工。

连续失败后按依赖熔断，窗口内直接走降级。错误码、是否可重试和已试次数写进 State，由条件边选择重试、澄清或结束。

### 12. 流式输出（Streaming / SSE）怎么从 Agent 服务返回给前端？怎么保证思考过程和工具调用结果不乱序展示？

**参考答案**

一次 run 先落成有序事件日志，再由 HTTP 响应按 SSE（`text/event-stream`）写出。每条事件有单调 id、trace id 和类型：`assistant.delta`、`reasoning.delta`、`tool.start`、`tool.end`、`run.end`、`error`。工具参数在该次调用完整后再发 `tool.end`。思考和正文分属不同事件，前端分块渲染。长工具调用期间发送注释心跳，代理用 `X-Accel-Buffering: no` 并关闭响应缓冲。

服务端只有一个写者按发生顺序写这条流。模型 token 和工具结果先进入同一队列，再写出。前端按事件 id 去重，用 `tool_call_id` 把工具卡片钉在对应调用上。

请求体需要 POST 时，用 fetch 读取 SSE 帧；浏览器自带的 EventSource 只发 GET。客户端断开后，进行中的 run 继续写日志，重连带上最后的事件 id，服务端从日志补发。为了补画面再启动一次 run，有副作用的工具会再执行一遍。

### 13. 手写算法：LeetCode 200 岛屿数量。给定一个二维网格，`'1'` 是陆地、`'0'` 是水，返回岛屿个数

**参考答案**

四连通才算同一座岛，斜角相邻不算。扫描网格，遇到一块没统计过的陆地就把计数加一，并用 DFS 或 BFS 把与它相连的整片陆地标记完。标记可以改网格，也可以用 visited；改输入前要确认调用方还要用原网格。

每个格子进队或递归一次，时间 O(mn)，空间最坏 O(mn)。Python 递归深度可能达到格子数，格子大时用显式栈或 BFS。

```python
def num_islands(grid: list[list[str]]) -> int:
    if not grid or not grid[0]:
        return 0
    m, n = len(grid), len(grid[0])

    def dfs(i: int, j: int) -> None:
        if i < 0 or i >= m or j < 0 or j >= n or grid[i][j] != "1":
            return
        grid[i][j] = "0"
        dfs(i + 1, j)
        dfs(i - 1, j)
        dfs(i, j + 1)
        dfs(i, j - 1)

    count = 0
    for i in range(m):
        for j in range(n):
            if grid[i][j] == "1":
                count += 1
                dfs(i, j)
    return count
```

### 1. 自我介绍

**答题思路**

三面看你是否真的主导过一块。1 到 2 分钟，顺序不变。

### 2. 项目介绍，重点说你主导或深度参与的部分，遇到最难的技术问题是什么、怎么解决的

**答题思路**

1. 用 30 秒说明业务目标和你的边界。参与的部分说清楚评审和上线时你在哪。
2. 架构只保留和这个难点有关的路径。
3. 难点按这个顺序：线上现象 → 你靠哪条 trace、日志或评测定位 → 候选方案和取舍 → 改了哪一层 → 用什么对照确认有效。指标只用真实有的。
4. 主动说还留着的风险。若最难的事是提示词，就讲清评测集如何证明其他意图没有回退；讲不清就换一个你能讲到根因的问题。

### 3. 如果要从小模型意图路由升级到多 Agent 架构，你怎么评估是否值得引入多 Agent？过度设计有哪些信号？

**参考答案**

用同一套线上抽样的评测集，对比「小模型路由 + 单 Agent 或一张状态图」和「多 Agent」。看任务成功率、有害动作率、P95 延迟、单次成本和人工介入率。没有这组对照，就还不到引入的时候。

值得加 Agent 的情况通常同时出现：工具变多后选错工具的比例明显上升，拆开并单独评测后下降；各段的权限、模型或时限本来就不同，例如检索可以快模型，下单必须校验加确认；不同领域要各自发版，上下文需要隔离。

流程只是长，用一张有分支的图就够。几个 Agent 看同一份上下文、做同一类决定，只是多了一次转述。

过度设计的信号：说不清每个 Agent 唯一的输入输出；交接次数上去了，延迟和 token 上去了，成功率没有上去；失败时指不出是哪个 Agent 的哪次决定；封闭的查询办理被做成辩论或群体同时执行；一个分支的单测要拉起全部 Agent。

### 4. 生产环境 Agent 平台需要哪些可观测性（Tracing / Logging / Metrics）？怎么埋点追踪一次完整 Agent Run 的 Token 消耗、工具耗时、失败率？

**参考答案**

三类分开。Logging 保留排障事件，手机号、位置、车架号脱敏。Metrics 是可聚合的速率和分布，用来告警。Tracing 是一次 run 里的因果链。

入口生成 trace id，贯穿网关、每个节点、每次模型调用和每次工具调用，用同一套 span 语义串起来。模型 span 记模型名、提示版本、供应商返回的 input/output token、首 token 时间和结束原因。工具 span 记工具名、状态码、耗时、第几次尝试。run 上记终止原因（完成、步数上限、人工、错误）、总 token 和总耗时。结算和配额以 usage 为准；字符数估算只用于调用前的预算预占。

失败率按「工具名 + 错误类」和「run 终止原因」聚合。解析失败、校验失败和下游 5xx 分开，否则模型输出不合法会淹没在成功率里。成功请求可以采样，失败请求保留完整 trace。订单号和用户原文放进 span 或日志，不放进指标标签，避免时序库被高基数打满。

### 5. 你们怎么做 Agent / RAG 的效果评测？Golden Dataset + LLM-as-Judge 怎么构造和防偏见？在线 A/B 实验怎么设计？

**参考答案**

Golden set 从线上脱敏样本加人工补的长尾组成。每条包含对话、当时可用的工具和索引版本，期望行为写成该调哪个工具、必须出现的事实、必须拒绝的情况，只有一篇参考答案评不了 Agent。双人标注，分歧仲裁。按意图和难度分层，集合版本和提示、索引绑在一起。固定集之外再留滚动集，避免只对一套题优化。

LLM-as-Judge 按维度拆开：忠实度、该不该检索、工具参数、有没有越权。裁判先引用证据再打分。交换材料顺序各评一次，降低位置偏好；生成答案的模型不担任唯一裁判；量表写明长度和文采不加分；不向裁判提供模型名和提示版本。裁判和人工金标对齐，报告一致率。一致率不够时，裁判只做初筛，上线看人工分。

在线实验按用户或会话分流，同一会话走同一版本。主指标是任务成功和有害动作率，护栏是时延、成本、投诉和人工升级。事先写明样本量和停止规则。有副作用的工具在实验组同样走确认。

### 6. MCP（Model Context Protocol）是什么？和 Function Calling 的关系？什么场景适合引入 MCP Server？

**参考答案**

MCP 是 Host/Client 与外部 Server 之间的协议。Server 发布三类能力：模型可发起的 tools、应用按 URI 读取的 resources、用户显式选用的 prompts。本地进程常用 stdio，远程服务走 HTTP。Client 用 `tools/list` 发现工具，用 `tools/call` 执行。远程 Server 的用户授权按协议里的 OAuth 流程处理。

Function Calling 是模型 API 的机制：这次请求附带工具 schema，模型返回名称和参数，应用负责执行。它规定的是模型如何表达一次调用。MCP 规定工具从哪里发现、在哪个进程执行、凭证如何给到 Server。常见接法是把 MCP 列出的 tools 转成这次模型调用的 function schema，模型返回后再由 Client 按 MCP 执行。只有一处私有函数时，直接注册进 Function Calling 即可。

适合引入的情况：多个 Agent、IDE 或内部平台要共用同一组工具；工具由别的团队独立发布；希望统一发现和授权，少写一套适配器。调用涉及事务、幂等和审批时，这些策略仍在 Server 或 Harness 里实现，协议本身不提供。

### 7. 你们怎么管理 Prompt 版本？Prompt 改坏了对线上影响怎么快速回滚？有无 Prompt 注册中心或 A/B 测试机制？

**参考答案**

提示按不可变版本存放，每次变更有作者、说明和对应的评测结果。线上节点引用版本号。注册中心（或带版本的配置制品）按 Agent 和节点名解析当前指针；代码里保留变量和渲染，正文不散落在分支字符串里。还没有注册中心时，模板进版本库，上线物带版本号，trace 里记下实际用到的版本。

回滚是把指针拨回上一份评测通过且在线上跑过的版本。拨回前核对变量契约：新版本多了必填变量时，旧模板和新代码的组合要一起能渲染。回滚后看该版本的错误率。提示依赖的索引和工具 schema 也在同一条变更里时，一起回退，只拨提示指针仍可能是坏的。

A/B 在同一节点挂两个版本，按会话分流，兜底版本写在配置里。指标用任务成功、有害动作、延迟和成本。实验结束把胜出版设为指针，输出版保留，以便再拨回去。

### 8. 模型网关（LiteLLM / 自研）为什么需要？限流、熔断、多模型 Fallback、成本分摊怎么实现？

**参考答案**

业务服务若各自持有供应商 SDK、密钥和重试，模型名、配额和审计就散了。网关提供统一鉴权、兼容协议、模型路由和调用记录。LiteLLM 这类组件把多家供应商收成一个 OpenAI 兼容入口；要接内网模型、数据不出域和内部计费时，通常在同一位置自研或包一层。

限流按租户、应用和模型限制每分钟请求数和 token 数，在网关处拒绝超额调用，并把结果标成可重试的配额错误。Agent 收到后停止或排队。每个模型单独计额度。

熔断按模型和区域统计错误率与超时。打开后在窗口内直接失败或走备用，半开时放少量探测。一个模型熔断不影响网关上的其他模型。

Fallback 只用于超时、5xx 和熔断，且备用模型满足同一输出契约（结构化输出、上下文长度）。内容审核拒绝和上下文超长，换模型仍然会失败。实际命中的模型写进 trace。

成本用供应商 usage 乘以按账单周期维护的单价表，记到调用方的应用、租户和 Agent 上。流式调用在结束帧补记 usage。

### 9. 如果业务方要求 Agent 输出必须严格遵从某个 JSON Schema 且不能胡编字段，你有哪些工程手段保证（Structured Output / Pydantic / 后置校验 / 重试）？

**参考答案**

形状和取值分开保。形状靠生成约束和校验，取值靠和本轮证据对齐。

支持约束解码的接口，用 schema 限制可采样的结构，并关闭未声明字段。严格模式通常要求字段都出现在 schema 里，可选语义用 null 联合类型表达。提示里贴一份 schema，没有这层约束时仍然可能输出说明文字或多余字段。网关 Fallback 到不支持该模式的模型时，保证就消失了，路由要排除这类模型。

服务端再用 Pydantic 或等价类型校验一遍，`extra` 设为禁止。这里加上字段间约束，以及「id 必须来自本轮工具结果或白名单」。能走结构化接口时校验其返回对象；纯文本模式先按 JSON 解析，解析失败视为校验失败。

失败后把校验错误交回模型，重试次数固定。仍失败就拒答或转人工，半合法对象不写下游。提示示例里的 id 使用明显的占位形式，避免模型照抄一个看起来合法的假 id。

```python
from typing import Literal

from pydantic import BaseModel, ConfigDict


class LogisticsReply(BaseModel):
    model_config = ConfigDict(extra="forbid")
    status: Literal["in_transit", "delivered", "unknown"]
    order_id: str
    summary: str
```

### 12. 如果团队对是否引入 LangGraph vs 自研 Harness 有分歧，你怎么推动决策并说服不同意见？

**答题思路**

目标是把分歧收成可检验的问题，并执行写下来的边界。

1. 先记下双方要避免的失败：控制流复杂后改不动、断点续跑不可靠、框架升级锁定、自研以后没人能讲清状态存在哪。
2. 用一条真实链路做对照，至少包含分支、工具失败、进程重启后续跑、人工确认。记录恢复后是否重复执行了有副作用的工具、代码落点和时延。
3. 把边界写进结论：选用 LangGraph 时，权限、幂等、预算和审计仍由自己的 Harness 管。选自研时，检查点、循环和 thread id 的语义要有明确实现。
4. 决策记录包含否掉的方案和重开条件，例如恢复语义不符合这条链路，或图的分支已经无法复现故障。不同意见针对记录里的证据，会议外再改用同一条链路复测。

### 13. 手写算法：LeetCode 146 LRU 缓存。实现 get 和 put，O(1) 均摊时间复杂度

**参考答案**

用哈希表定位节点，用双向链表维护使用顺序。链表头部是最近使用，尾部是最久未使用。`get` 命中后把节点移到头部，未命中返回 -1。`put` 遇到已有键就更新值并移到头部，容量不变；新键插入头部，超过容量时删除尾节点，并从表里去掉。只删链表节点、忘了删哈希表，旧键还会被 `get` 到。

哈希表的期望查找是 O(1)，改四个指针也是 O(1)，所以单次操作均摊 O(1)。空间 O(capacity)。

```python
class Node:
    def __init__(self, key: int = 0, value: int = 0) -> None:
        self.key = key
        self.value = value
        self.prev = self
        self.next = self


class LRUCache:
    def __init__(self, capacity: int) -> None:
        self.cap = capacity
        self.map: dict[int, Node] = {}
        self.head = Node()
        self.tail = Node()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node: Node) -> None:
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_to_head(self, node: Node) -> None:
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        node = self.map.get(key)
        if node is None:
            return -1
        self._remove(node)
        self._add_to_head(node)
        return node.value

    def put(self, key: int, value: int) -> None:
        node = self.map.get(key)
        if node is not None:
            node.value = value
            self._remove(node)
            self._add_to_head(node)
            return
        node = Node(key, value)
        self.map[key] = node
        self._add_to_head(node)
        if len(self.map) > self.cap:
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]
```
