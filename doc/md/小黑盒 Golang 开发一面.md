## 一面

### 1. 请说一下 SSE 协议和 WebSocket 协议的区别。

**参考答案**

结论：SSE 是服务器顺着一条普通 HTTP 响应往下推文本；WebSocket 是先借用 HTTP 握手，升级后变成双向帧协议。

SSE 的响应类型是 `text/event-stream`，浏览器 `EventSource` 只收不发。事件由 `data:`、`event:`、`id:` 这几行组成，二进制要自己编码。断线后浏览器用上次的 `id` 放进 `Last-Event-ID` 再请求。客户端要发数据，只能另开一条 HTTP 请求。

WebSocket 由客户端带 `Upgrade: websocket` 发起握手，服务端返回 `101 Switching Protocols` 后，同一条 TCP 连接改走 WebSocket 帧，文本和二进制都能传，两端可以同时写。心跳是协议里的 ping/pong。断线重连、补消息要应用自己做，浏览器不会像 SSE 那样自动带位点。

代理侧也不同。SSE 仍是 HTTP，主要防的是中间层把响应缓冲住；WebSocket 要求代理正确转发 `Upgrade` 和 `Connection`，空闲超时要大于心跳间隔。通知、行情、模型逐字输出用 SSE 就够；聊天、对战、双方都要主动发帧时用 WebSocket。

### 2. WebSocket 的端口和 HTTP 的端口是一样的吗？为什么？

**参考答案**

结论：默认一样。`ws` 用 80，`wss` 用 443，和 HTTP、HTTPS 相同；协议也允许写别的端口。

握手本身就是发到这个端口上的 HTTP 请求，服务端用已经在监听的 HTTP 套接字接受它。升级成功后并不新开连接，TCP 四元组不变，端口自然不变。放在 80 和 443 上，防火墙、证书和现有反向代理都可以沿用，不必为 WebSocket 再开一个口。

如果监听在别的端口，只要握手和后续帧走那一个端口即可，协议没有第二套端口号。负载均衡要配的是同一条连接上的升级转发，不是再分配一个「WebSocket 专用端口」。

### 3. 端口这个概念是由哪一层提供的？

**参考答案**

结论：传输层。端口是 TCP、UDP 用来在一台主机上区分套接字的 16 位编号。

网络层的 IP 地址定位的是主机，一份 IP 报文到了机器之后，还要靠传输层头部里的源端口和目的端口，交给对应的进程。应用层的 HTTP、WebSocket 只是约定 80、443 这些众所周知端口，并不定义端口这个字段。

所以「端口冲突」发生在同一协议、同一本地地址上的两个套接字，而不是发生在 IP 层。ICMP 这类网络层报文没有端口。

### 4. 发送一个 HTTP 请求，从发送到接收中间发生了哪些过程？

**参考答案**

结论：新的 HTTPS 请求要先有地址、连接和加密，然后才是请求和响应；连接被复用时，前面几步会省掉。

1. 解析 URL，做 DNS 查询。浏览器、操作系统和递归解析器的缓存都可能直接命中。
2. 没有可复用连接时，TCP 三次握手。HTTPS 接着做 TLS 握手，并用 ALPN 选定 HTTP/1.1 或 HTTP/2。HTTP/3 则走 UDP 上的 QUIC，传输和加密一起握手。
3. 报文可能经过 NAT、防火墙、负载均衡。对端地址经常是反向代理，不是业务进程。
4. 发送请求行、头部和正文。HTTP/2 把它们拆成帧，复用在已有连接的流上。
5. 服务器路由到处理函数，读缓存或数据库，写回响应。
6. 客户端按 `Content-Length`、分块结束或流结束判断收完。Keep-Alive 的连接放回复用，否则 TCP 四次挥手。

证书校验发生在应用数据发出之前。把「每个请求都三次握手」说成固定步骤，会和连接池、HTTP/2 对不上。

### 5. 什么是反向代理？正向代理和反向代理有什么区别？

**参考答案**

结论：正向代理替客户端向外访问，反向代理替服务端接收访问。差别在代理站在谁那边、对外隐藏哪一侧。

正向代理由客户端显式配置。请求先到代理，代理再连接目标服务器，目标看到的是代理地址。它用来做访问控制、审计或跨网。

反向代理部署在服务端前面。客户端把代理的地址当作站点本身，不知道后面有几台实例。代理按域名、路径或负载把请求转到内网，还可以终结 TLS、做缓存和限流。Nginx 和 API 网关都是这个角色。

两边都可以代理 HTTP。方向不是协议差出来的，而是谁发起配置、隐藏的是客户端身份还是服务端拓扑。

### 6. 你的项目中使用 Nginx 了吗？用到了哪些功能？

**答题思路**

先回答用过还是没用过。用过就沿着真实请求路径讲，只讲配置里真正开过的能力。

1. 它站在哪：本机反代，还是统一入口。前面是 TLS，还是后面还有一层网关。
2. 对上号再展开：按路径转发、上游负载均衡、静态文件、gzip、限流、缓存。没配过的模块不要顺口带上。
3. 如果流量里有 WebSocket，说明 `Upgrade` 和 `Connection` 如何交给上游，读超时是否大于心跳。SSE 则说明有没有关掉代理缓冲，否则事件会攒一批才到达。
4. 没用过就直接说没有，补一句它该放在哪：多个 Go 进程前面做反向代理和 TLS，而不是在业务进程里自己解析证书。

### 7. WebSocket 是否支持 HTTP/2 或 HTTP/3？

**参考答案**

结论：最初的握手只定义在 HTTP/1.1 上；HTTP/2 和 HTTP/3 后来用扩展的 CONNECT 把 WebSocket 引导到一条流上，双方和中间代理都支持才能通。

RFC 6455 的做法是 HTTP/1.1 的 `Upgrade`。HTTP/2 没有这条连接级升级，所以不能把旧握手原样放进 HTTP/2。RFC 8441 增加了扩展 CONNECT：一条 HTTP/2 流带上 `:protocol = websocket`，WebSocket 帧跑在这条流里，别的请求仍可复用同一条连接。HTTP/3 由 RFC 9220 用同样的扩展 CONNECT 跑在 QUIC 流上。

规范有了，不表示这条链路已经开了。浏览器一般要在 HTTP/2 的 SETTINGS 里看到扩展 CONNECT 被打开，才会把 WebSocket 放上 HTTP/2；否则仍走 HTTP/1.1 升级。Go 服务、Nginx 或云负载均衡只要有一段不认扩展 CONNECT，HTTP/2 或 HTTP/3 上的 WebSocket 就建不起来。面试里先分开「经典握手是 1.1」和「扩展 CONNECT 才覆盖 2 和 3」，现网要逐段确认。开了 HTTP/2 不会自动拥有 WebSocket。

### 8. SSE 是基于 HTTP/1.1 的吗？

**参考答案**

结论：SSE 是一条不主动结束的 HTTP 响应，不绑定 HTTP/1.1。HTTP/1.1 只是最常见的载体。

格式由 `Content-Type: text/event-stream` 和正文里的事件帧决定。HTTP/1.1 上这条正文常用分块传输，连接被这一个响应占住。HTTP/2 和 HTTP/3 没有分块传输这一层，同一段文本放在一条流的数据帧里，其他请求还能并行。语义不变。

所以「必须是 HTTP/1.1」不准确。实务上的差别是：HTTP/1.1 会吃掉浏览器对单主机很少的并行连接配额；HTTP/2 及以后，这条长响应只占一个流。无论哪一版，中间代理都可能缓冲正文，服务端要关掉缓冲并尽快刷出事件。

### 9. 你的社区项目用了 HTTP/2 吗？

**答题思路**

按简历上的社区项目给是否启用的结论。确认方式只用你真正看过的证据：浏览器里该连接的协议列、服务端监听配置，或抓包里的 ALPN。

启用了就说原因，例如页面并发请求多，想在一条连接上多路复用。没启用就说当时的网关或对端只开了 HTTP/1.1。如果实时通道走 WebSocket，把握手版本和页面接口的 HTTP 版本分开说。

不要因为服务端库「能开 HTTP/2」就说项目已经在用。库的能力和线上协商结果是两件事。

### 10. 讲一下 IO 多路复用。

**参考答案**

结论：一个线程向内核登记很多文件描述符，阻塞到其中至少一个可读、可写或出错，再只处理就绪的那些。

没有多路复用时，要么一个连接占一个线程阻塞读写，要么用户态不断对每个套接字做非阻塞试探。前者内存和切换随连接数上涨，后者空转占 CPU。多路复用把「谁就绪了」交给内核。

三种常见接口的差别在于每次调用要付出的扫描成本：

- `select` 使用固定长度的 fd 集合，Linux 上常见编译上限是 1024。每次调用都把集合拷进内核，内核再线性扫一遍。
- `poll` 改用数组，没有那个固定上限，但拷贝和扫描仍然随登记的 fd 数增长。
- `epoll` 在 Linux 上把登记和等待拆开。`epoll_ctl` 增删关注的 fd，`epoll_wait` 只返回这次就绪的 fd。BSD 上的对应物是 `kqueue`，Windows 上是 IOCP，思想相同，接口不同。

默认水平触发表示条件还在就继续通知；边缘触发只在状态变化时通知，应用必须读到不能再读。多路复用解决的是等待，不解决回调里做慢操作：事件循环里一次长时间计算，其他已就绪的连接都会被拖住。

### 11. 详细讲一下 epoll 的实现原理。

**参考答案**

结论：epoll 不是更快地扫描全部 fd。每个被监视的文件在等待队列上挂着回调，就绪时回调把这一项放进就绪链表，`epoll_wait` 只消费这条链表。

`epoll_create` 分配一个内核对象，里面有一棵以 fd 为键的红黑树（兴趣列表）、一条就绪链表，以及供 `epoll_wait` 睡眠的等待队列。这个对象本身也占一个 fd。

`epoll_ctl` 的添加在红黑树里按 fd 查找。没有就插入一项，并在目标文件的等待队列上登记回调。注册时如果已经可读或可写，该项立刻进入就绪链表。修改和删除同样先在树上定位。

套接字缓冲区发生变化时，内核唤醒的是这个文件自己的等待队列。回调拿到的已经是对应项的指针：它不在就绪链表里，就链上去，并唤醒睡在 epoll 上的进程。其他 fd 不会被查看。

`epoll_wait` 看到就绪链表为空就睡到超时或被回调唤醒，然后把事件拷贝到用户空间。拷贝期间新来的事件先挂在一旁，拷完再接回就绪链表，避免边遍历边改链表。

水平触发下，这次没读完、条件仍成立，该项会回到就绪链表。边缘触发只在新的状态变化时再通知，用户态要一直读到 `EAGAIN`。兴趣树只服务登记和去重；把 epoll 理解成「select 的优化扫描」会对不上这个结构。

### 12. 多路复用相对于非多路复用的优势是什么？

**参考答案**

结论：连接数上去之后，等待的成本不再按连接数线性占住线程和 CPU，只在有就绪事件时醒来。

非多路复用的典型做法是一个连接一个阻塞线程，或者单线程轮流阻塞在当前连接上。前者每条连接都要栈和调度实体，空闲连接同样占着；后者一次只能推进一个连接。用户态忙轮询则是连接空闲时也在耗 CPU。

多路复用之后，少量线程可以挂住大量连接。内核只交出已经可读、可写或出错的 fd，用户态不用遍历全部连接。内存主要跟连接上的应用缓冲有关，而不是跟线程栈有关。

代价在编程模型。读写可能只完成一半，要保留每个连接自己的状态。事件回调里不能做磁盘上的慢操作或长时间计算，否则所有连接共享的这条循环会被堵住。连接很少、处理又很重时，多路复用的优势不明显。

### 13. epoll 底层为什么用红黑树而不是哈希表？

**参考答案**

结论：红黑树保存的是「哪些 fd 被监视」，事件到来时并不查它。热路径拿着已有指针把项挂进就绪链表。

`epoll_ctl` 需要按 fd 查找、插入、删除和拒绝重复登记，最坏 O(log n) 的红黑树够用。树节点嵌在每个监视项里，不必另维护一块会扩容的桶数组。

哈希表平均查找是常数时间，但并不因此更适合这张表。登记远少于事件通知；fd 多到百万量级，对数也比较也只是二十次这个量级，相对系统调用可以忽略。哈希要处理冲突链和扩容，扩容时整表重哈希，会让一次 `epoll_ctl` 的延迟突然变长。fd 编号又稀疏，不适合按编号做连续数组。

因此原因不是「红黑树比哈希更快」，而是这张表要稳定的最坏时间、可嵌入的节点，并且它不在热路径上。真正要短的是就绪链表的插入，以及 `epoll_wait` 把就绪事件交回用户态。

### 14. 你在数据库项目中实现的死锁环路检测是怎么设计的？

**答题思路**

按你真实写过的锁管理器讲，顺序固定，没做的检测不要补成已实现。

1. 图里有什么。事务是点。T1 等待 T2 持有的锁，就有一条 T1 指向 T2 的边。如果内部先记成「事务等待某把锁、锁被某事务持有」，检测前折成事务等待图。
2. 边何时增删。申请不到锁、进入等待队列时加边；拿到锁、等待超时、提交或回滚时删边。事务结束不删边，后面会报出假环。
3. 何时检测。常见是每次加边后，从当前事务做一次深度优先搜索，沿等待边走回自己就是环。后台周期扫也可以，但要说明最坏会晚多久才发现。
4. 图和数据锁怎么配合。更新等待图时用图自己的互斥；不要握着这把元数据锁去等待行锁，也不要在回滚的磁盘操作期间一直占着它。否则检测线程和业务线程会再死锁一次。
5. 发现环之后只收集环上的事务，交给牺牲者选择。回滚环外的事务拆不掉这个环。

锁竞争高时，说清楚检测扫描的是从当前边可达的那一小块，不是每次遍历全库事务。

### 15. 如何选择回滚的事务？为什么不是任选一个？

**参考答案**

结论：在环上选一个回滚即可拆环，但应选择代价最小、且不会每次都被选中的那个。任意挑选会撤掉已经做了很多事的事务，也可能把同一个事务反复打死。

选择范围只包括这个环上的事务。环外的事务即使更便宜，回滚它也不会拆掉当前的等待环。常见政策是给环上每个事务一个代价，选最小者；代价相同再用事务号打破平局。

不能任选，主要是三个后果。已修改的数据量不同，回滚成本不同。总是回滚最年轻或总是回滚刚刚等待的那一个，它重试后可能立刻再次入环，形成活锁。业务上有的事务不该给统计类事务让路，任选表达不了这个优先级。

InnoDB 的具体政策可作为例子：优先回滚插入、更新、删除行数更少的事务，让撤销更短。这是一种代价定义，不是唯一合法标准。被选中的事务收到死锁错误，由调用方决定是否重试，锁管理器不要在原地无限重做。

### 16. 如果让你设计一个选择代价最小的事务回滚，你会怎么决定代价？

**参考答案**

结论：代价是环上事务之间可比较的一个数，要能在等锁路径上便宜地算出来，不追求和真实工时完全一致。

只在环内取最小。每个事务平时累计几个单调的计数，检测到环时做加权和，例如：

- 已修改的行数，或已经写下的 undo / redo 字节数，代表撤销要做多少工作
- 当前持有的锁数量，代表这次回滚能解开多少等待
- 已经执行的语句数或经过的时间
- 业务权重：支付、扣库存高于日志、统计
- 近期已经作为牺牲者的次数，次数越高代价越大，避免活锁

权重按业务定死并写进代码，不要在答案里编一套假装最优的系数。几个事务代价接近时，回滚最年轻的那个，它重做的工作通常更少。

这个函数必须稳定：同样的环每次算出同一个牺牲者，否则线上死锁行为无法解释。回滚只保证释放它持有的锁并撤销它的修改；已经发出的外部消息不属于这个代价能免费收回的部分，那种事务应在权重里就比纯内存事务更贵。

### 17. 除了资源数量，还有其他评估代价的方式吗？

**参考答案**

结论：资源数量只反映数据库内部的撤销成本。事务已经碰过的外部副作用、优先级和被牺牲次数，都会改变「谁更便宜」。

除了锁个数和修改行数，还可以看这些信号：

- 已写入的日志字节数，比「锁的把数」更接近回滚时的磁盘工作
- 事务类型和租户优先级。交互式请求用户还在等，批任务通常可以稍后重试
- 是否已经产生数据库外面的动作，例如消息已经投递、支付已经发起。这种事务按行数看可能很小，按业务看最贵
- 近期被选为牺牲者的次数。只按资源选，短事务会反复中签
- 它在环里是否刚开始等待。刚等待的事务往往改动更少，但这只是启发式

不适合在检测路径上现算的，是「这个事务还要多久才能自己结束」。那个预测既不稳定，也会把死锁检测拖慢。面试里说明代价只用已经记下的计数，检测本身不做额外查询。

### 18. B+ 树是如何支持并发操作的？

**参考答案**

结论：页的物理结构用短时间的闩锁保护，键的隔离用事务锁保护。查找从上往下耦合闩锁，分裂用右链接或沿路径加独占闩锁，避免锁住整棵树。

闩锁和事务锁不是一层。事务锁按两阶段锁持有，可能一直到提交；页闩锁只包住这一次读页、插入或分裂，用完就放。读沿着根到叶加共享闩锁，拿到子节点后再放父节点，根就不会在整个查找期间被占住。写请求加独占闩锁。叶子还有空间就地插入；满了才分裂。

如果每次分裂都要把祖先重新独占住，父节点会成为热点。B-link 树给节点加右兄弟指针和高键：查找发现分隔键已经变化时向右走，分裂就不必一直抓着整条路径。

隔离级别需要的记录锁、间隙锁加在叶子的键上，用来处理写写冲突和幻读，和页闩锁分开。采用 MVCC 时，读请求走快照，不必给键加共享事务锁；写请求仍然要短闩锁，以及写写之间的事务锁。

页闩锁的获取顺序要固定，否则两个分裂会在父子节点上互相等待。这和事务死锁是两套机制，检测等待图解决不了闩锁死锁。

### 19. 写操作导致节点分裂时，如何保证并发安全？

**参考答案**

结论：被搬走的键在任何时刻都能被查找到达。先在独占闩锁下把新节点写完并挂上兄弟指针，再把分隔键插入父节点，然后才释放闩锁。

具体可以按 B-link 的顺序做：

1. 给将要分裂的叶子加独占闩锁。
2. 分配新页，把后半段键移进去，新页写完整后再对其他事务可见。更新原叶子的高键，把它的右指针指向新页。这时父节点即使还是旧的分隔键，查找进到原叶子后也能沿右指针进入新页。
3. 再把分隔键插入父节点。父节点也满了就同样分裂，可能一直到根。根分裂要分配新根并让树变高，这一小段要挡住并发读，避免同时看见两个根。
4. 有 WAL 时，页修改前先把对应日志写入日志缓冲，页上记下日志号。日志必须先于这个数据页写回磁盘。释放闩锁之前不必强行 fsync，提交时才要求提交记录落盘。
5. 闩锁要么自上而下获取，要么自下而上时用尝试锁，失败就放开并重试。这样不会出现一个写请求抓着叶子等父亲、另一个抓着父亲等叶子。

另一种做法是自上而下的闩锁耦合：子节点可能分裂就不释放父节点的独占闩锁。它也能不丢键，但分裂期间父节点争用更大。两种不要在同一次分裂里各做一半。并发读要么等独占闩锁结束，读到分裂前或分裂后的完整节点，要么按右指针走，不会读到一半旧一半新的键范围。

### 20. 你对 B+ 树做过单元测试或集成测试吗？压测过吗？

**答题思路**

按你实际跑过的测试说。没压过就说没压过，不要临时编吞吐数字。

1. 单元测试覆盖空树插入、查找命中和未命中、重复键、删除、叶子分裂、内部节点分裂和根变高。断言用性质：分裂前后键的并集不变，中序遍历有序，查找结果等于已插入集合。
2. 并发测试让多线程同时查和插入，专门撞上「插入时正好分裂」。结束后再做一次全量查找。
3. 如果树和 WAL 是一起做的，集成测试在写了一半时杀掉进程再打开，已提交的键还在，未提交的不在。
4. 压测只报告你记录过的数据量、读写比例和是否走缓存。没有记录就说明当时只验证了正确性。

只断言「没有抛异常」挡不住丢键。把这个检查说出来。

### 21. 严格两阶段锁和两阶段锁的区别？

**参考答案**

结论：两阶段锁约束加锁和放锁的阶段，保证冲突可串行化；严格两阶段锁进一步要求排他锁持有到事务结束，用来避免脏读和级联回滚。两者都不是两阶段提交。

两阶段锁把事务分成增长阶段和缩减阶段。增长阶段可以加锁，不能放锁；一旦放过任何一把锁，就进入缩减阶段，只能放、不能再加。这样得到的调度是冲突可串行化的。它允许在提交前进入缩减阶段。若此时放开排他锁，别的事务就能读到尚未提交的修改；原事务再中止，读者也必须跟着中止。

严格两阶段锁把排他锁的释放推迟到提交或中止，增长阶段的规则不变。其他事务读不到未提交的写，也就不会级联回滚。还有一种强严格两阶段锁，共享锁也持有到事务结束。数据库口头说的严格两阶段锁，经常实际是这一种。

两阶段锁不负责死锁。它允许「两个事务各持一把、又等对方」的等待，所以才需要环检测。它也对幻读没有单独的保证：只锁已经存在的行，挡不住另一事务插入新行，需要间隙锁或下一键锁补上。

### 22. 你的 WAL 日志是怎么实现的？

**答题思路**

按日志从产生到落盘的路径讲你的代码，没做的部分直接说没有。

1. 一条记录里有什么：递增的日志号，以及物理页的修改或逻辑操作（插入某个键）。说明你选的是哪一种。
2. 写入顺序：修改数据页之前，先把对应记录放进日志缓冲；事务提交时，至少把直到提交记录的日志刷到磁盘，然后再响应客户端。数据页可以晚一点写。
3. 刷盘方式：每次提交都 fsync，还是多个事务组合成一次 fsync。组提交要讲并发提交如何排队并成一次刷盘。
4. 文件如何切分：固定大小的段，按日志号命名。页上保存已经应用到的日志号，恢复时用来跳过已经在页上的修改。
5. 校验和、检查点有没有做。没有检查点，就说明崩溃后要从哪一段开始扫描，以及这个扫描为什么仍然正确。

不要把「写了日志文件」说成已经满足 WAL。关键是提交成功之前提交记录已经落盘，且日志先于对应数据页写回磁盘。

### 23. 如果数据库崩溃，如何用 WAL 恢复数据？

**参考答案**

结论：崩溃后以日志为准。已经提交但数据页没写回的，重做；没有提交记录的，按你的写回策略丢掉或撤销。重做必须幂等。

正常运行时守住 WAL：描述修改的日志先进入日志缓冲，数据页可以晚写；向客户端确认提交之前，这条事务的提交记录已经 fsync。页上记录应用到的日志号。

恢复时：

1. 找到最近一次完成的检查点。检查点表示在此之前的数据页已经写回，或者它记下了当时仍脏着的页以及需要从哪个日志号重放。没有检查点，就从仍保留的日志开头扫。
2. 向后重做。日志号不大于页上日志号的记录跳过，因为页已经包含这次修改。这样恢复做到一半再次崩溃，重做第二遍也不会把同一修改施加两次。
3. 处理没有提交记录的事务。若实现保证未提交的脏页绝不写回，丢掉尾部未完成的日志即可。若脏页可能已经写回，就要按补偿记录撤销这些事务，再写下中止记录。

检查点若只记一个时间、却不保证此前脏页已经落盘，恢复会从错误的位置开始，已提交的修改补不回来。副本如果也在拉同一段日志，截断日志之前要看它应用到哪里。

### 24. WAL 日志不断增长，有清理机制吗？

**参考答案**

结论：有。检查点推进可截断的位置，比这个位置更早、且没有使用方还需要的日志段可以删掉或循环复用。

一次有效检查点之后，重做不再需要检查点之前、并且已经反映到数据页上的日志。实际能删的终点还要取更严格的下限：最老的活跃事务开始位置、仍未写回的脏页所需的最早日志号、从库已经应用的位置。任何一个还停在旧日志上，对应的段都不能回收。

实现上通常把日志切成固定大小的段，按日志号命名，旧段删除或改名复用。需要按时间点恢复时，旧段先归档再从在线目录拿走，而不是直接删。

没有检查点就没有安全的截断点，只能一直追加。长事务会把截断点拖住，这是清理「失效」时首先要查的原因，而不是磁盘本身不会删文件。

### 25. 你在项目中的双层缓存设计（本地缓存 + Redis）具体是怎样的？

**答题思路**

按真实读路径和写路径讲。容量、过期时间只用你配置过的值。

1. 读：进程内缓存，未命中再查 Redis，仍未命中再查数据库，然后回填。本地结构要有容量上限和淘汰，不能是无界 map。
2. 写：先写数据库，成功后再删除或更新 Redis，并删掉本机缓存。不要先改本地、再异步写数据库。讲清两层失效的顺序。
3. 键是什么，两层的过期时间谁更短。本地更短，用来挡同一进程里的热点重复读。
4. 一致性口径：允许旧值存在多久。不能接受旧值的数据不要放进本地层。
5. 热点键过期时谁去回源。同一进程里用单飞，避免缓存击穿时每个请求都打到数据库。
6. 多实例时各进程的本地缓存互不相同。如果面试官接着问重连和回调，先说明那是不是这条缓存链路，还是另一条长连接。

### 26. 为什么用两层缓存？分别缓存了什么？

**答题思路**

先讲两层各自挡住的成本，再列你真正放过的数据。没分过类型就不要现场分一套。

本地缓存省的是到 Redis 的网络往返和 Redis 的重复 QPS，适合极热、体积小、丢失后能重建的数据。Redis 省的是数据库压力，并且多个进程能看到同一份，适合需要跨实例共享、可以比数据库稍旧的数据。

只有 Redis 时，同一台机器上的热键仍然每次都出网。只有本地缓存时，发布或扩容会把缓存同时清空，实例之间也不能共享。两层是把这两种成本分开，不是「层数越多越快」。

体积大、访问冷、或者必须读到最新值的数据，不应放进进程内存。你项目里如果有这种区分，用一个键说明本地有、Redis 有、只在数据库有的各是什么。

### 27. 如果连接异常断开再重连，会有问题吗？

**参考答案**

结论：会。重连成功只说明新连接能用，不说明断开期间的会话、未确认消息或订阅还在。

按面试当时聊的那条连接回答。长连接（WebSocket、SSE 或自建 TCP）常见有四类问题：

- 半开连接。对端已经消失，本端仍登记在 epoll 里。只靠下一次写失败才发现会拖很久，需要心跳和读超时把旧连接清掉。
- 消息缺口。断开到重连完成之间的推送没有接收方。客户端要带位点补拉，或者服务端按会话暂存，不能假设「连接还在所以没丢」。
- 双连接。新连接已经登记，旧连接的清理才到，同一用户在两台机器上各有一条。下线事件必须带连接代际，旧代际不能删掉新登记。
- 重连风暴。进程一重启，客户端同时连上来。要有退避和抖动，并限制同时握手的数量。

如果当时说的是 Redis 客户端：在途命令会失败，订阅会掉，重连后要重新订阅；连接池要限制重连速度。本地缓存里的旧值不会因为 Redis 重连成功而变新。无论哪一种，重试的请求都要能安全地做第二次。

### 28. 你的设计支持分布式吗？如果支持多个实例，如何保证回调能连接到正确的机器？

**答题思路**

先说你的实现是单机还是多实例。单机就明说回调只打到这一台，再讲如果扩成多实例会选哪一种；多实例就把你用的那一种讲完。

连接有归属时，回调必须找到持有这条连接的进程。三条可讲的做法：

1. 注册表。连接建立时把用户到实例地址写进 Redis，带租约，心跳续约。回调先查表，再调用那台机器。重连覆盖记录。机器宕机靠租约过期，过期前的消息要能暂存或让客户端补拉。旧连接的下线晚到时，用代际挡住误删。
2. 一致性哈希。对用户标识取哈希，接入和回调使用同一个环，落到同一实例。扩缩容只影响相邻一段用户。实例宕了，这一段要重连到后继，哈希本身不保存断开期间的消息。
3. 发布订阅。回调不查机器，发给所有实例，只有握着这条连接的实例真正下发。实例少时简单，实例多时浪费明显。

用源地址在负载均衡上粘住会话，要主动说明局限：客户端网络一变就粘错，实例下线时连接仍被分到旧机器。回调找到机器之后，处理函数本身还要按消息号去重。

### 29. 了解一致性哈希吗？请讲一下。

**参考答案**

结论：把节点和键都哈希到同一个环上，键沿固定方向找到第一个节点。节点增减时，只需要搬迁相邻那一段键，而不是几乎全部重哈希。

普通的 `hash(key) % N` 在 N 变化时，绝大多数键都会换节点。一致性哈希先给每个节点一个环上的位置，键顺时针（或固定的某一方向）归属于第一个遇到的节点。新增节点只接管它与前一个节点之间的键；下线节点只把它名下的键交给后继。

真实节点往往很少，环上位置会不均。给每个物理节点放很多虚拟节点，再映射回物理节点，分布会平一些。虚拟节点数量是平衡和内存的取舍，没有通用的「正确个数」。

它解决的是成员变化时的搬迁比例。它不解决热键：一个键再热也只落在一个节点上。它也不自动完成数据迁移，存储系统仍要把受影响的那段数据拷到新节点。客户端和所有服务必须使用同一套哈希和同一份环，否则同一个用户会被送到不同机器。

### 30. Redis 是如何保证一致性的？

**参考答案**

结论：Redis 默认不保证主从强一致。单机靠单线程把一条命令做成原子；主从是异步复制，主库可以在从库收到写之前就回复客户端。

在一台实例上，命令由单个事件循环执行，一条命令不会被另一条插在中间。`MULTI`/`EXEC` 或一段 Lua 能让一组命令连续执行。这只说明这台进程里的并发顺序，不说明从库、重启后的磁盘和它一致。

复制是异步的。主库改完内存就可以返回成功，再把命令放进复制积压发给从库。从库滞后时，读从库得到旧值；主库在复制完成前宕机，已确认的写可能不在被提升的从库上。`WAIT` 可以让客户端等到指定数量的从库确认收到，超时后的行为仍要业务处理。它是「多等一等复制」，不是多数派共识。

AOF 或 RDB 只影响这一台机器重启后还剩多少数据。常见的每秒刷盘仍可能丢掉最近大约一秒的写，并且和从库是否跟上无关。

Cluster 里一个槽同一时刻由一个主节点负责写，这个主节点上的写有顺序；跨槽没有原子性。故障转移若提升了落后的从库，同样会丢掉主库已确认的写。集群成员和槽位视图靠 Gossip 传播，是最终一致。

如果问的是缓存和数据库谁为准，那不由 Redis 保证，要在更新数据库和删除缓存的顺序里单独设计。把「单线程」说成「Redis 是强一致」会把单机原子性和副本一致性混在一起。

### 31. Redis 的选举是怎么做的？用了什么算法？

**参考答案**

结论：开源 Redis 不用 Raft 复制每一条写。Sentinel 用改造过的 Raft 选举「谁来执行故障转移」；Cluster 用配置 epoch 和多数主节点投票，选出一个分片的新主。

Sentinel 模式里，任一 Sentinel 可以先把主库标为主观下线，再询问其他 Sentinel。同意的数量达到配置的 quorum，才是客观下线。真正去提升从库之前，还要在 Sentinel 之间选出一个执行者：使用任期、每个任期一票、多数 Sentinel 同意。这部分是按 Raft 的领导者选举改的，不复制数据日志。quorum 只决定「主库是否被判定下线」，领导者要另外拿到 Sentinel 的多数票，两个数字不是同一个配置。当选的 Sentinel 按优先级、复制偏移和运行标识挑选从库，把它提升为新主，再让其余从库改指向。

Cluster 没有 Sentinel 这一层。从库通过 Gossip 发现自己的主库被标为失败后发起选举。复制进度更靠前的从库会更早开始。它增大自己的 epoch，向负责槽位的主节点拉票。每个主节点在一个 epoch 里只投一票，并且只投给它认为原主已经失败、epoch 更新的从库。从库拿到配置里超过半数主节点的票，才宣告成为新主并广播。票数按主节点总数计算；挂掉的主节点不投票，所以半数以上的主节点同时不可用时，自动提升会停住，用来避免两边同时当主。

两套投票都不把客户端的写命令送进共识日志。数据仍是主库异步复制到从库。另有独立的 RedisRaft 模块做过日志复制，那不是 Sentinel 和 Cluster 的默认路径。

### 32. Redis Cluster 为什么是无中心的？既然用了 Raft 算法？

**参考答案**

结论：Cluster 没有用 Raft 选出一个全局领导者，所以没有中心。题目里「既然用了 Raft」这个前提不成立。

每个槽位有自己的主节点，客户端对这个槽的写直接发给它，再由它异步复制给自己的从库。写路径上不存在一条全集群共用的 Raft 日志，也没有一个节点代理所有槽。

故障转移时的投票只产出这个分片的新主。其他槽的主节点照常服务，它们投出的票不使自己变成全集群的领导者。成员变化和槽位表靠节点之间的 Gossip 传播，任何一个节点都可以告诉客户端「这个槽现在在哪」。客户端收到重定向后自己改道。

Sentinel 那套更接近 Raft 的选举属于另一种部署，而且也只决定谁来执行切换，不位于 Cluster 的数据路径上。因此「局部多数票」和「无中心」不矛盾：投票决定的是某个槽的主从身份，不是所有请求的入口。

### 33. 你有用过 Redis 的自动切换机制吗？

**答题思路**

先区分三种情况：用过 Sentinel、用过 Cluster、只部署过主从而没有自动切换。第三种不要说成用过故障转移。

用过就按一次真实切换的顺序讲：

1. 谁发现主库不可用，谁执行提升。Sentinel 和 Cluster 的发现者不同，不要混成一个组件。
2. 客户端如何知道新地址：向 Sentinel 查询，或处理 Cluster 的重定向，或前面有代理替你改。连接池要丢掉指向旧主的连接。
3. 切换窗口里你看到过什么：超时、只读错误，还是一段已确认写入消失。业务重试是否能安全执行第二次。
4. 没在生产遇过切换，就说机制是配过还是只在文档和演练里看过，把观察和推断分开。

### 34. 你在实习中做的向量召回，是用 ES 做的吗？

**答题思路**

直接回答是或不是，不要顺着问句改口。

是 Elasticsearch 时，说明向量字段怎么存、近似最近邻用的是哪种索引，以及关键词查询是在同一次检索里做还是两路各自召回再合并。版本和参数只用你配置过的。

不是 ES 时，说出实际引擎，例如 Faiss、Milvus，或数据库里的向量索引。然后只展开你碰过的那一层：写入向量、建索引、查询，或把两路结果合在一起。评测脚本和在线检索不要说成同一件工作。

### 35. 如果同时命中关键词和向量，如何融合排序？

**参考答案**

结论：两路分数不要直接相加。召回层用倒数排名融合，把名次合成一个序；需要更准的相关性时，再对前几十条做重排。

关键词一路给出 BM25 的名次，向量一路给出近邻的名次。文档取并集，而不是只留下两路都出现的那些，否则只被向量找回来的相关文档会被丢掉。融合分是：

```text
score(d) = Σ 1 / (k + rank_i(d))
```

名次从 1 开始。某一路没有召回到的文档，那一路不加项。k 用来减弱头部名次的压倒性，论文和常见实现把 60 当作起点，不是已经调好的最优值。某一路更可信时，可以乘上这一路的权重，变成 `w_i / (k + rank_i)`。

不用原始分数，是因为 BM25 和余弦相似度的尺度、分布都不同，线性加权前必须归一化，而且不同查询之间的分数不好比。倒数排名只看名次。

这一步只解决两路召回怎么合成一个候选序。前排还要业务特征或交叉编码器时，融合结果作为重排的输入，不替代重排。

### 36. 你对 RRF 公式做过调优吗？

**答题思路**

没调过就说使用当时的 k，并说明原因：两路原始分不可比，先用名次把链路跑通。调过就按实验讲，不编提升比例。

1. 动过什么：k、某一路的权重，还是两路各自保留的条数。
2. 用什么查询集评价，指标是 Recall@K 还是 nDCG，K 是否和线上展示的条数一致。
3. 怎么避免只在看过的查询上变好：留出没参与挑选参数的查询。
4. k 变大时名次差异被抹平，融合更接近「被任一路径召回即可」；k 变小时，两路头部文档的权重大。最终取值落在你的评测结果上。

没有标注集时，不要把某一次人工感觉说成调优结论。

### 37. 你在实习中参与向量召回的具体哪部分工作？

**答题思路**

把链路拆开，只认领你写过或改过的段。

1. 数据：文档如何变成向量，模型是谁提供的，你是否做了切分和字段选择。
2. 索引：新增、更新、删除时索引如何一起变化，全量重建有没有你参与。

4. 评测：离线集、坏例，或你改过的那一版用什么指标和前一版对比。

### 38. 算法题：深度比较两个 Object（可能是 Map、List、String），用 Java 实现。

**参考答案**

结论：按运行时类型递归。List 比长度和顺序，Map 比大小和键值、与键的顺序无关，String 和其他叶子用 `equals`。路径上记下正在比较的对象对，遇到环就按「这对已经假定相等」处理，避免无限递归。

无环时，JDK 的 `List.equals` 和 `Map.equals` 本身就是这种深比较。手写是为了把规则显式固定下来，并在循环引用时不爆栈。键按 Map 自己的 `equals` 查找，适合字符串键；键本身若又是带环的 Map，查找键时仍可能递归过深，这题的输入按字符串键处理。数组不是 List，不在题目给出的三种类型里。

时间与节点数、边数成正比，每个节点在一次比较中进出路径各一次。额外空间正比于嵌套深度，最坏是整棵结构。

```java
import java.util.IdentityHashMap;
import java.util.List;
import java.util.Map;

public final class DeepEquals {
    private DeepEquals() {}

    public static boolean deepEquals(Object left, Object right) {
        return deepEquals(left, right, new IdentityHashMap<Object, Object>());
    }

    private static boolean deepEquals(Object left, Object right,
                                      IdentityHashMap<Object, Object> visiting) {
        if (left == right) {
            return true;
        }
        if (left == null || right == null) {
            return false;
        }
        if (left instanceof Map && right instanceof Map) {
            return mapEquals((Map<?, ?>) left, (Map<?, ?>) right, visiting);
        }
        if (left instanceof List && right instanceof List) {
            return listEquals((List<?>) left, (List<?>) right, visiting);
        }
        return left.equals(right);
    }

    private static boolean mapEquals(Map<?, ?> left, Map<?, ?> right,
                                     IdentityHashMap<Object, Object> visiting) {
        if (left.size() != right.size()) {
            return false;
        }
        if (visiting.containsKey(left)) {
            return visiting.get(left) == right;
        }
        visiting.put(left, right);
        try {
            for (Map.Entry<?, ?> entry : left.entrySet()) {
                Object key = entry.getKey();
                if (!right.containsKey(key)) {
                    return false;
                }
                if (!deepEquals(entry.getValue(), right.get(key), visiting)) {
                    return false;
                }
            }
            return true;
        } finally {
            visiting.remove(left);
        }
    }

    private static boolean listEquals(List<?> left, List<?> right,
                                      IdentityHashMap<Object, Object> visiting) {
        if (left.size() != right.size()) {
            return false;
        }
        if (visiting.containsKey(left)) {
            return visiting.get(left) == right;
        }
        visiting.put(left, right);
        try {
            for (int i = 0; i < left.size(); i++) {
                if (!deepEquals(left.get(i), right.get(i), visiting)) {
                    return false;
                }
            }
            return true;
        } finally {
            visiting.remove(left);
        }
    }
}
```

`IdentityHashMap` 用引用区分对象，这样两个内容正在比较中的 Map 不会被 `equals` 当成同一个键。比较结束要摘掉路径上的记录，同一对象在无环的有向无环图里被多处引用时才能再比一次。Map 用 `containsKey` 区分「没有这个键」和「值是 null」。

### 39. 实习中有没有遇到过与导师意见不合的情况？怎么处理？

**答题思路**

用一次真实分歧，没有就说没有具体的一次，不要编项目。控制在一两分钟。

1. 用一句话说明分歧是哪一个技术取舍，并复述导师要守住的目标，例如工期、稳定性或实现复杂度。
2. 你补充的是事实：多出来的状态、失败时怎么回滚、你用多长时间能做一个最小验证。验证拿去对齐，而不是在会上争赢。
3. 决定权在导师时，按确定的方案做。把你担心的前提写进任务里：出现什么现象就改回另一种做法。
4. 如果已经有结果，只说那个担心后来是否发生。没有结果就说到如何对齐为止。

面试官看的是信息不全时能不能把分歧收成一个可执行的决定。

### 40. 如果发现 bug 需要其他组协调，对方不承认，怎么办？

**答题思路**

按证据、契约、临时防护、升级这四步说，不编一次没发生过的事故，可以用「我会这样处理」。

1. 把现象收成能复现的材料：请求标识、时间、入参、出参。只有「你们的服务有问题」时，对方无法确认。
2. 对照双方都承认的接口约定，看是调用方传错，还是被调方违反了约定的返回。不用猜测对方内部实现。
3. 对方不承认时，把复现缩到最小，约一次一起看同一条日志。业务已经受损，就先熔断、降级或把这类响应当失败。防护是为了止血，不是替对方改口。
4. 仍然对不齐，把证据和影响交给两边的负责人，请他们定归属和修复人。目标是修好，不是拿到一份认错说明。

### 41. 你使用过 AI 编程工具吗？优缺点？

**答题思路**

先说用过的类型：补全、对话，或能改仓库的编程代理。没用过就说没用过。

优点只举你真实省过时间的环节，例如样板代码、不熟悉的库怎么读、补测试、把报错和调用栈对照起来。

缺点讲你自己碰到过的情况：

1. 会写出看起来合理、实际不存在的接口或参数。没有对过文档和编译的代码不能提交。
2. 一次改动铺得太大，错误处理和项目里的写法不一致。你要自己读 diff。
3. 仓库或配置里的密钥、线上日志不能贴进对话。说明你如何避免把生产配置交给工具。
4. 并发、事务和协议的解释要能独立验证。这场面试里的机制题，不能用工具的说法代替自己的理解。

收尾说明分工：工具起草，提交前你阅读改动并运行测试。不要给一个无法解释的效率倍数。
