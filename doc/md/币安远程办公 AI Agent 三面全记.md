# 币安远程办公 AI Agent 三面全记

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

币安这种远程 AI 岗考的是生产系统，不是八股。面试官想看你能不能把 LLM、Java、图数据库、RAG 和工作流拼成能上线的链路。意图识别要讲清路由和降级；记忆要讲写入、读取、过期和冲突；图库要讲 Cypher 安全和多跳成本；LangGraph 要讲 checkpoint、reducer 和多 Agent 的状态隔离。碰到特别难的题，可以反问对方的召回评估集、线上幻觉率和多 Agent 成本，把话题拉回可验证的事实。不会的点直接说生产里怎么降级、怎么交给人工，不要编。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1.5 到 2 分钟，按「我是谁 → 做过什么 → 为什么能做这个岗」来讲。

1. 一句话定位：年限、主语言（Java 为主或 Java/Python 双栈）、最近在做的方向是 Agent 工程落地。
2. 后端底子：只讲你真正负责过的稳定性、并发、数据一致性，这些是 Agent 上生产的基础。
3. AI 项目：用两三句说清业务目标、你负责的模块（路由、检索、记忆、工具、评测里你真正做过的）和结果。调用量、延迟、成本只用你能解释的数字。
4. 和岗位的关系：远程协作怎么推进（文档、异步同步、对线上问题的响应），以及你做过的系统里权限、幂等、可观测是怎么落的。
5. 收尾：把话口留给你最熟的那个 Agent 项目，方便面试官往下挖。

### 2. 讲一个你做过的 AI Agent 项目，整体链路、调用量、延迟、成本和踩坑各说一遍

**答题思路**

用你真实做过的项目，按下面的顺序讲 3 到 4 分钟。项目名、调用量和金额只用你自己的数，讲不出就说数量级和口径，不要临时编。

1. **目标和边界**：谁在用，解决什么问题，哪些动作允许模型做，哪些必须人确认。先说明为什么这里需要 Agent，哪些步骤其实是固定流程。
2. **链路**：接入鉴权 → 意图路由 → 检索或工具 → 编排和步数预算 → 生成与校验 → 返回。旁边补记忆、trace、评测回流。
3. **你的职责**：点明哪些是你设计和上线的，哪些是同事的。
4. **四个量化口径**：
   - 调用量：日请求或日会话，峰值大概在什么时段。
   - 延迟：端到端 P95，最好能拆成路由、检索、模型、工具。
   - 成本：单次成功任务的 token 或金额，以及缓存、小模型分流省在哪里。
   - 质量：任务完成率、人工接管率、工具失败率，口径要和评测集对得上。
5. **踩坑**：准备两个你真处理过的，按「现象 → 原因 → 改法 → 怎么防止再发」讲。常见类型可以对号入座：权限过滤漏了、工具重复执行、摘要改坏关键数字、检索命中过期文档。
6. 收尾留一个你愿意展开的难点，不要把所有优化点平铺完。

### 3. 意图识别怎么落地：规则、分类模型、LLM 路由三者怎么配合，如何避免误判导致错误进工具或错误进 RAG

**参考答案**

三者是逐级升级，前一级能确定就不要往后走。

规则处理确定输入：固定指令、菜单、订单号和交易对正则、安全黑白名单。它可解释、延迟极低，也适合在进模型之前做拦截。分类模型覆盖边界清楚的高频意图，输出各类概率；top1 足够高，而且和 top2 拉开差距，才采纳。LLM 路由只接低置信、多意图、强依赖上下文的长尾，并用 JSON Schema 把意图限制在枚举里，同时抽出槽位、标出要不要澄清。

误判进工具或 RAG，要靠路由约束卡住：

- 置信度或分差不够时改为澄清或安全兜底，既不调工具，也不检索。
- 意图到能力是显式白名单。工具意图才能进工具，知识意图才进 RAG，未知意图两边都不进。
- 缺必填槽位先追问。提现、下单这类写操作，即使意图判对了，也要二次确认，不能由分类结果直接执行。

意图集和阈值要版本化，并用回归集看新意图有没有把旧意图带偏。

### 4. 三层记忆怎么设计：会话级、工作/实体级、长期向量级分别存什么，什么时候写、什么时候读、怎么防记忆污染

**参考答案**

三层按生命周期拆开，热状态可以放 Redis，需要审计和删除的记录以 MySQL 为准，向量库只放长期记忆的语义索引。

| 层 | 存什么 | 何时写 | 何时读 | 何时失效 |
| --- | --- | --- | --- | --- |
| 会话级 | 当前会话最近若干轮原文 | 每轮追加 | 每轮组装上下文 | 滑动窗口加会话 TTL |
| 工作/实体级 | 本任务已确认的槽位、实体、计划、工具结果引用 | 槽位确认或工具返回后 | 规划和填参时 | 任务结束或空闲超时 |
| 长期向量级 | 跨会话仍有效的偏好和稳定事实，结构化行加 embedding | 会话结束后异步抽取，过阈值才写 | 会话开始，或当前问题需要个性化时 | 按类型 TTL、用户删除、版本覆盖 |

防污染要靠写入门槛，而不是靠模型「记住该记的」：

- 每条记忆带主体、属性、值、时间、来源和置信度。用户口述和工具核验的事实分开，冲突时核验事实优先；偏好以用户最新的明确表态为准，旧值留版本。
- 用实体键去重，低置信和疑似注入的内容先隔离，不写进长期层。
- 读出来的记忆只当数据，不当系统指令。检索要带用户和租户条件。
- 原始长对话不要整段塞进向量库。面试里容易漏的是：记忆库本身也要能按用户删除，并且删到向量、缓存和数据库每一份副本。

### 5. 上下文超长怎么处理：滑动窗口、摘要压缩、关键信息抽取、向量检索历史，分别适用什么场景，怎么组合

**参考答案**

四件事解决的丢失方式不一样，要一起用，而不是四选一。

- **滑动窗口**：保留最近几轮原文。适合闲聊和刚说过的指代，早期约束会被挤掉。
- **摘要压缩**：把滑出窗口的内容滚成摘要，每次只摘要新滑出的部分。适合长对话要保留脉络的场景。摘要会丢数字、改条件，不能单独作为依据。
- **关键信息抽取**：订单号、交易对、金额、时间范围、用户已确认的决定，写成结构化槽位，每轮固定注入。适合丢了就会调错工具的信息。
- **向量检索历史**：按当前问题召回旧轮次。适合话题跳转、「上次那个问题」这种指代。它不保证按时间顺序，也经常召不回刚刚那一句，所以替代不了窗口。

组合方式是给上下文分预算：系统说明和安全规则、已确认槽位、最近原文、滚动摘要、按需召回的历史，各有上限。占用接近预算上限时再压缩，不要每轮都摘要。工具的大结果只在上下文里留摘要和结果 ID，全文放存储。压缩前后要用同一批评测看任务有没有变差。

### 6. RAG 多路召回怎么搭：向量、BM25、知识图谱、元数据过滤各自负责什么，合并去重后怎么进 rerank

**参考答案**

四路职责不同，元数据过滤是硬条件，要加在每一路召回上，不能等生成后再滤。

- **向量**：语义改写、口语化问法。对错误码、交易对、精确专名不敏感。
- **BM25**：字面命中，适合错误码、币对、产品名、规章制度里的原词。
- **知识图谱**：实体之间的关系和多跳，例如某条规则约束哪些产品。质量取决于抽取和消歧。
- **元数据过滤**：租户、权限、语言、文档版本、有效期、业务线。它缩小范围，也防止串数据。

合并时各路原始分不能拿来相加。每路先按自己的名次排序，再用 RRF 或路内归一化后的加权融合。去重键用 chunk 的稳定 ID；完全相同的正文用哈希去掉；近似重复保留更新、权限匹配的那条，多路同时命中可以作为加分。融合后取几十条进 cross-encoder，再留数条带引用的片段进提示词。rerank 超时就退回融合顺序。权限过滤要由服务端附上，不能让模型改写查询时把它拿掉。

### 7. Reranker 为什么不能直接全库跑，cross-encoder 和 bi-encoder 的取舍，没有 GPU 怎么用 RRF 做轻量融合

**参考答案**

cross-encoder 把问题和文档拼在一起打分，精度高，但每条候选都要过一遍模型，延迟随候选数线性涨，全库跑不完。bi-encoder 把问题和文档分别编码，文档向量可以预先建索引，靠近似搜索从全库捞一个短名单，快，但问题和文档之间没有交叉注意力，精细排序弱于 cross-encoder。

生产形态是 bi-encoder、BM25 或图谱先召回几十到一两百条，cross-encoder 只重排这个短名单，再取数条进上下文。短名单过大，重排自己就会变成 P95 的大头。

没有 GPU 时，不做全库重排，也不要把 cross-encoder 当成必经步骤。各路召回只用名次做 RRF：文档在某一路的名次是 r，这一路权重是 w，贡献 `w / (k + r)`，常用的 k 是 60，再用评测集调整。同一路里同一文档只留最好名次。融合后直接取 Top-K。如果 CPU 上的小重排模型还能扛住，只对融合后的很少条目跑，并设超时，超时退回 RRF 顺序。RRF 绕开的是分数不可比，它补不回 cross-encoder 的精度，所以要用 Recall@K 和坏例看融合有没有把对的文档压下去。

### 8. LangChain 和 LangGraph 区别，什么场景链够用、什么场景必须上状态图

**参考答案**

LangChain 的链（含 LCEL）是用代码把检索、提示词、模型、解析器接成一条有向无环的调用，一次 `invoke` 走完预先写好的路径。LangGraph 是带共享 State 的状态图：节点、条件边、循环都显式存在，走到哪一步由状态和图上的边决定，并且可以把状态持久化。

链够用的场景：分类、抽取、单次 RAG、步骤固定且不需要中途停下来等人的流水线。路径稳定，延迟和成本好估，测试也好写。

必须上状态图的场景：思考—调用工具—观察的循环、按结果分支再汇合、人审中断、进程挂了还要从断点续跑、多个 Agent 要共享一份可恢复的任务状态。这些需求若硬塞进链，循环和恢复会散落在业务代码里。

可以在图的节点里调用一条链。固定步骤留在链或普通工作流里，只有真正要循环、暂停和恢复的部分进图。面试里容易把「用了 Agent」说成必须上 LangGraph；步骤若是确定的，链更清楚。

### 9. LangGraph 的 State、Reducer、Checkpointer 怎么配合做断点恢复和多轮会话

**参考答案**

State 是一张有 schema 的共享数据，节点只返回自己改动的字段。Reducer 决定这些改动怎么并进旧状态：没有 reducer 的字段会被整段覆盖；消息列表要用追加型 reducer（如 `add_messages`），按消息 ID 去重，避免后一个节点把历史对话覆盖掉。计数器、集合也可以有自己的合并函数。

Checkpointer 在每个 super-step 之后，按 `thread_id` 把状态快照存下来。生产里常用 PostgreSQL。进程在节点完成并写完 checkpoint 之前挂掉，恢复时会重跑那个节点，所以有副作用的工具要用幂等键，不能假设节点只执行一次。人审用中断把图停住，checkpoint 保留现场；同一个 `thread_id` 带上人的决定再恢复。

多轮会话复用同一个 `thread_id`：新的用户消息追加进 State，图从上次的状态继续，而不是每次新开一个空白线程。`thread_id` 必须和登录用户绑定，不能凭客户端传来的 ID 读取别人的 checkpoint。

容易漏的两点：checkpoint 里不要塞工具原文大包，改存引用，否则库会迅速膨胀；reducer 配错时，多轮看起来像「模型失忆」，其实是状态被覆盖。

### 10. 图数据库选 Neo4j 还是其他，实体、关系、属性怎么建模，多跳查询和向量召回怎么结合

**参考答案**

知识图谱和交易流水不是同一张图。Agent 用的图是抽过的实体和关系，规模通常远小于全量成交。这种策展过的图，团队又需要 Cypher、事务和可解释路径时，Neo4j 是常见选择。写入量和跳数都非常大、必须水平拆开时，再看 NebulaGraph、JanusGraph 这类分布式图，代价是查询语言和运维都变了。跳数固定而且很少时，关系表也能做，不必先上图数据库。

建模保持克制：

- 节点按类型分标签，例如产品、规则、账户概念、文档。属性放稳定 ID、名称、别名、租户、来源、置信度、更新时间。
- 关系有类型和方向，边上带 `source_chunk_id` 和置信度，方便回到原文。
- 长文本不放在节点上。正文和向量留在检索库，两边用 chunk ID、实体 ID 关联。

查询先做租户和权限过滤，再用向量或 BM25 找到种子实体，然后做有上限的多跳。跳数、扇出和返回条数都要封顶，并设查询超时。高度数的超级节点不要盲目展开。图没有命中就退回向量片段，并在回答里保留路径和原文引用。多跳很慢时，优先怀疑超级节点和跳数，而不是先加机器。

### 11. Agent 调工具怎么做 schema 校验、参数修正、失败重试、限流和降级，举远程高并发例子

**参考答案**

工具调用按「模型提议 → 校验 → 执行 → 结构化观察」走，模型没有越过校验直接打外部系统的路径。

- **Schema 校验**：每个工具一份 JSON Schema，检查必填、类型、枚举、范围和多余字段。不合法就把错误回给模型。
- **参数修正**：只做确定性修正，例如交易对大小写和别名。修正失败再让模型看错误重试一次；仍然不合法就向用户澄清，停止调用。
- **重试**：读接口可以重试，写接口必须带幂等键。参数错误不重试。退避加抖动，次数少，并遵守上游的 `Retry-After`。
- **限流**：用户级和上游级分开。进程内信号量限制在途数，Redis 限制单位时间配额。
- **降级**：超时或熔断时，读接口返回带时间戳的缓存或明确的「暂时查不到」；写接口失败要关断，不能自动换一条路径硬做。

远程高并发可以举只读的规则或公告查询：很多人同时问某个交易对的当前规则。Schema 把交易对收成枚举，别名表做一次修正；上游 429 时按 `Retry-After` 退避，在途数对齐供应商配额；命中短缓存就直接返回并带上缓存时间；缓存也没有就告诉用户暂时查不到，并给出人工入口。下单、提现不走这条路径，默认不开放给 Agent，开放也要人确认。

### 12. Spring Boot 接 LLM 服务，线程池、异步、背压、超时、429/5xx 重试怎么设计

**参考答案**

Tomcat 的请求线程只做接入和写出。模型调用放到带超时的异步 HTTP 客户端上，和数据库、普通业务线程隔离开。

线程池或并发舱用有界队列。池大小按供应商允许的并发和压测来定，瓶颈在配额和延迟，不是 CPU 核数公式。队列满了就拒绝：在线对话返回繁忙或降级，长任务改成入库再异步执行。不要把长时间的模型调用退回 Tomcat 线程，否则容器线程会被慢慢占满。

背压用信号量对准目标并发，排队时间算进端到端预算。剩余时间已经不够一次模型调用时，就不要再发出去。

超时拆开：连接超时、首包超时、整段超时。整段超时要小于网关超时，避免上游还在跑、网关已经把连接断了。客户端断开时取消上游，免得继续烧 token。

429 和 5xx 只在「还没向用户输出内容、重放是安全的」时重试。用带抖动的指数退避，尊重 `Retry-After`，次数很少，并加熔断，避免故障时重试把上游打得更满。参数类 4xx 不重试。重试会重复计费，所以要有重试预算。LLM、工具和数据库分舱，一个慢依赖不要占满全部资源。

### 13. Redis 在 Agent 里用在哪里：会话状态、分布式锁、限流、缓存召回结果，分别怎么落地

**参考答案**

Redis 放热数据和协调，不作为对话和记忆的唯一账本。需要追责、删除和长期保存的内容以 MySQL 为准。

- **会话状态**：按会话 ID 存热状态和最近轮次，用 Hash 或 JSON，设置 TTL，并在活跃时续期。关键对话同时落库。缓存键里带用户和租户。
- **分布式锁**：`SET key token NX PX`，token 用唯一值，释放时用 Lua 比较再删除，避免把别人的锁删掉。锁只包住「状态从待执行改成执行中」这种短临界区。不要在整个模型调用期间占着锁。超时续期要和持有者身份绑在一起。任务到底有没有执行，仍以数据库的唯一约束和状态机为准。
- **限流**：按用户、工具、模型供应商做令牌桶或滑动窗口，用 Lua 保证读取和扣减原子。固定窗口计数会在窗口边界叠出两倍流量，配额紧的时候要用滑动窗口或令牌桶。
- **缓存召回**：键里包含归一化问题、过滤条件、索引版本和 embedding 版本，TTL 短，知识一更新就能对上版本。权限相关的结果把主体放进键里。热点键用单飞，避免缓存击穿时把检索打满。个性化答案和写操作结果不进这个缓存。

### 14. MySQL 存对话、记忆、任务状态，分表怎么分，热点用户长会话怎么避免单表膨胀

**参考答案**

三类数据分表，不要塞进一张宽表。

- **对话**：一行一条消息，字段包含用户、会话、递增序号、角色、内容或对象存储指针、创建时间。唯一键用（会话 ID，序号）。
- **记忆**：一行一个事实版本，带用户、记忆键、版本、过期时间、来源和置信度。当前值是版本折叠的结果，旧版本留作审计。
- **任务**：一行一个任务，状态机字段、幂等键、租约和结果引用。更新频繁，和只追加的消息分开，避免互相抢锁。

分片键用用户 ID，让一个用户的会话和记忆落在同一分片，在线读写不用跨片。会话 ID 若要单独查询，加一张会话到用户的映射。全局分析走数仓，不扫在线分片。

按用户哈希解决不了「一个用户本身太大」。消息再按时间做范围分区，过期分区归档到冷存储，在线表只留近期原文和摘要。超长工具结果存对象存储，数据库留指针。读历史先走 Redis 里的近期页，不把整段会话 `SELECT` 出来。对超高活跃用户要有写入限流和单会话长度上限。归档任务按分区卸载，而不是在一张无限增长的表上删几百万行。

### 15. AI 工作流里 Workflow、Graph、Loop 的区别，Agent Loop 怎么防死循环、防无限工具调用

**参考答案**

三者的控制权不在同一个地方。

- **Workflow**：步骤和依赖事先定义好，引擎按 DAG 推进。适合审批、入库、固定的检索再生成。路径可预测。
- **Graph**：拓扑是工程师设计的状态图，可以分支、汇合和有限循环，节点里才调用模型。适合需要中断、恢复和明确状态的流程。
- **Loop**：模型自己决定下一步调用什么工具，直到它给出结束。灵活，步数和费用都不固定。

Agent Loop 要有硬预算，不能只在提示词里写「不要循环」：

- 限制最大步数、最大工具次数、token 和墙钟时间，任何一个用完就停止并给出兜底。
- 对（工具名，参数哈希）计数，同样的调用重复出现就停止。
- 状态哈希没有变化也视为没有进展，停止。
- 工具白名单和每个工具自己的次数分开计。工具内部重试也要计入全局次数，避免里外两层重试叠成无限调用。
- 结束必须落到明确的终态：成功回答、澄清或失败。有副作用的动作不要放在无监督循环里自动执行。

### 16. 手撕算法：给定意图标签集合和训练语料，实现朴素多分类特征词频统计，并用新 query 输出 Top-K 意图及置信度，要求可扩展同义词词典

**参考答案**

用多项式朴素贝叶斯把「类别条件下的词频」变成后验概率。朴素假设是词在给定类别后条件独立，所以后验正比于先验乘每个词的条件概率。用加一平滑避免没见过的词把整条概率变成 0：

`P(t|c) = (tf(t,c) + α) / (N_c + α × |V|)`

在对数域把各类的 `log P(c) + Σ log P(t|c)` 做 softmax，得到的就是后验。这里的置信度是全部类别上的后验，Top-K 的置信度之和通常小于 1。它没有用验证集校准，不能直接当成线上阈值。

同义词在统计前折叠成规范词，所以词典扩展只改分词，不改模型结构。新别名指向已经统计过的规范词时，不用重算词频；若规范词本身变了，要重跑统计。查询里没出现在词表中的词直接跳过，避免未登录词偏向语料更短的类别。中文按词典最长匹配，匹配不上的字作为单字特征；生产里可以把这一步换成分词器。

训练时间复杂度是语料 token 总数，预测是类别数乘查询 token 数，空间是类别数乘词表大小。

```python
import math
import re
from collections import defaultdict


class IntentClassifier:
    def __init__(self, labels, synonyms=None, alpha=1.0):
        if alpha <= 0:
            raise ValueError("alpha 必须为正")
        self.labels = list(dict.fromkeys(labels))
        if not self.labels:
            raise ValueError("意图标签不能为空")
        self.alpha = float(alpha)
        self.alias = {}
        self.max_cjk = 1
        for canon, aliases in (synonyms or {}).items():
            self.add_synonym(canon, canon)
            for alias in aliases:
                self.add_synonym(canon, alias)
        self.tf = {c: defaultdict(int) for c in self.labels}
        self.token_total = {c: 0 for c in self.labels}
        self.doc_count = {c: 0 for c in self.labels}
        self.vocab = set()
        self.n_docs = 0

    def add_synonym(self, canonical, alias):
        canon = canonical.strip().lower()
        ali = alias.strip().lower()
        if not canon or not ali:
            raise ValueError("同义词不能为空")
        self.alias[canon] = canon
        self.alias[ali] = canon
        if re.fullmatch(r"[\u4e00-\u9fff]+", ali):
            self.max_cjk = max(self.max_cjk, len(ali))

    def fit(self, samples):
        for text, label in samples:
            if label not in self.tf:
                raise ValueError(f"未知意图: {label}")
            tokens = self._tokenize(text)
            self.doc_count[label] += 1
            self.n_docs += 1
            for token in tokens:
                self.tf[label][token] += 1
                self.token_total[label] += 1
                self.vocab.add(token)
        return self

    def predict(self, query, top_k=3):
        if top_k < 1:
            raise ValueError("top_k 必须 >= 1")
        if self.n_docs == 0 or not self.vocab:
            conf = 1.0 / len(self.labels)
            ranked = [{"intent": c, "confidence": conf} for c in self.labels]
            return ranked[:top_k]

        tokens = [t for t in self._tokenize(query) if t in self.vocab]
        c_count = len(self.labels)
        v_size = len(self.vocab)
        log_scores = {}
        for label in self.labels:
            log_prior = math.log(self.doc_count[label] + self.alpha) - math.log(
                self.n_docs + self.alpha * c_count
            )
            denom = self.token_total[label] + self.alpha * v_size
            score = log_prior
            for token in tokens:
                score += math.log(self.tf[label][token] + self.alpha) - math.log(denom)
            log_scores[label] = score

        peak = max(log_scores.values())
        weights = {c: math.exp(s - peak) for c, s in log_scores.items()}
        total = sum(weights.values())
        ranked = sorted(
            ({"intent": c, "confidence": weights[c] / total} for c in self.labels),
            key=lambda item: (-item["confidence"], item["intent"]),
        )
        return ranked[:top_k]

    def _tokenize(self, text):
        parts = re.findall(r"[a-z0-9_]+|[\u4e00-\u9fff]", text.lower())
        out = []
        cjk = []

        def flush():
            if cjk:
                out.extend(self._segment_cjk("".join(cjk)))
                cjk.clear()

        for part in parts:
            if len(part) == 1 and "\u4e00" <= part <= "\u9fff":
                cjk.append(part)
            else:
                flush()
                out.append(self.alias.get(part, part))
        flush()
        return out

    def _segment_cjk(self, text):
        out = []
        i, n = 0, len(text)
        while i < n:
            hit, hit_len = None, 0
            for length in range(min(self.max_cjk, n - i), 1, -1):
                frag = text[i : i + length]
                if frag in self.alias:
                    hit, hit_len = self.alias[frag], length
                    break
            if hit is None:
                ch = text[i]
                out.append(self.alias.get(ch, ch))
                i += 1
            else:
                out.append(hit)
                i += hit_len
        return out


if __name__ == "__main__":
    clf = IntentClassifier(
        ["查价格", "提现"],
        synonyms={
            "比特币": ["btc", "比特币"],
            "价格": ["行情", "价格"],
            "提现": ["出金", "提现"],
        },
    )
    clf.fit(
        [
            ("btc 行情怎么样", "查价格"),
            ("比特币价格", "查价格"),
            ("出金多久到账", "提现"),
            ("我要提现", "提现"),
        ]
    )
    top = clf.predict("帮我看下 BTC 行情", top_k=2)
    assert top[0]["intent"] == "查价格"
    assert abs(sum(item["confidence"] for item in top) - 1) < 1e-9
    clf.add_synonym("价格", "现价")
    assert clf.predict("比特币现价", top_k=1)[0]["intent"] == "查价格"
    assert clf.predict("我要出金", top_k=1)[0]["intent"] == "提现"
```

### 1. 自我介绍

**答题思路**

二面宜短，45 到 90 秒把身份说完，马上进入生产项目。

1. 年限、技术栈、现在负责的 Agent 系统一句话讲清。
2. 只留一个和生产相关的结果：稳定性、评测或成本，数字用你能展开的。
3. 主动把话口交到「模型怎么选、工具怎么控、线上怎么看」上，这是这一轮通常要深挖的地方。
4. 远程协作只用一句：你怎么写设计、怎么同步风险、线上问题你怎么接。不要在自我介绍里把项目细节讲完。

### 2. 深讲一个 Agent 生产项目：需求、模型选型、框架、工具集、评测集、线上监控各说清楚

**答题思路**

选一个你真正上线过的项目，按面试官点名的六段讲，每段都准备被追问「为什么不是另一种做法」。

1. **需求**：用户、成功标准、允许模型犯的错、明确不做什么。资金或写操作若没开放，直接说边界。
2. **模型选型**：按任务拆，不要一个模型打全部。路由和抽取可以用小模型或便宜模型，最终回答再用主模型。讲你比较过的维度：工具调用是否稳定、结构化输出、延迟、单价、数据能否出域。结论用你当时的评测，不要背参数表。
3. **框架**：固定步骤用工作流或链，需要循环、暂停、恢复再用状态图。说明你把状态放在哪里。
4. **工具集**：每个工具的读写属性、Schema、鉴权和幂等。强调写工具默认关闭或必须人确认。
5. **评测集**：从哪来的真实对话，多少条可以不说死，但要说清标签是什么、覆盖了哪些意图、坏例怎么进来、上线前卡哪些指标。
6. **线上监控**：意图、召回文档 ID、工具、token、延迟、失败类型。出现幻觉时你怎么把原因分到检索、工具或生成。
7. 收在一个你做过的取舍上，例如为了 P95 砍掉一次重排，以及你怎么证明质量还能接受。

### 3. 复杂问题路由设计：什么时候直接 LLM 回答，什么时候走 RAG，什么时候走图数据库，什么时候派多个子 Agent

**参考答案**

路由先过安全和槽位，再决定知识从哪来。可以按固定顺序判断。

直接用 LLM：寒暄、写作、对当前上下文里已经有的结果做归纳，而且不需要引用外部依据。一旦涉及会过期的规则、产品说明或用户数据，就不要靠参数记忆回答。

走 RAG：答案在非结构化文档里，需要引用，例如公告、帮助文档、规则正文。检索分数过低就澄清或明确说没有依据，不要改口直接生成。

走图数据库：问题的核心是实体关系或多跳，而且实体能链上。例如某条规则覆盖哪些产品。图空结果再退回向量，两条证据矛盾就放弃断言，把两边的来源留下来。

派多个子 Agent：任务能拆成权限不同或可以并行的子目标，而且单 Agent 的评测已经显示工具集过大、上下文互相干扰或步骤超预算。每个子 Agent 只拿自己的工具和一份任务说明，回来交结构化结果。只为了「看起来高级」拆 Agent，会增加合并错误和费用。

路由结果做成枚举：直接回答、RAG、图、单工具、多 Agent、澄清。枚举之外的输出一律澄清。高风险写操作即使路由对了，也不进入自动执行。

### 4. 三层记忆在长周期任务里怎么演化的：新事实写入、旧事实过期、冲突偏好合并、跨会话用户画像重建

**参考答案**

长周期任务把记忆当成追加的事实日志，当前画像是日志折叠出来的视图，而不是一块会被改写的散文。

新事实在任务节点确认后写入：主体、属性、值、事件时间、来源、置信度、作用域（这次任务还是跨会话）。工具核验过的事实和用户口述分开存。写入前按记忆键找现行版本，内容相同就只刷新时间。

过期靠类型策略，不靠一个全局 TTL。会话内临时槽位随任务结束失效；稳定偏好用更长的有效期；过期后读路径不可见，记录仍保留到留存期结束，方便审计。用户删除是另一条立即生效的路径。

冲突按键合并。同一个（主体，属性）上，用户最新的明确偏好覆盖旧偏好；客观事实以核验来源为准，用户口说不能覆盖已核验的状态。两种来源都没把握时，保留冲突并在下次使用前问一句，不要静默选边。旧版本留着，合并本身也记一条事件。

跨会话画像用离线或会话结束时的任务重算：从仍然有效的事实折叠出结构化画像，再更新 embedding。不要把历史对话拼成一篇越来越长的摘要当画像。重建失败就继续用上一版，并在监控里看见折叠延迟。

### 5. GraphRAG 全链路设计：文档实体抽取、Neo4j 写入、Cypher 生成、多跳查询、空结果降级、向量补召回、结果交叉校验

**参考答案**

链路分入库和查询两段，查询不要在线现抽实体。

入库：文档切块并保留租户、版本、有效期。按限定的类型表抽取实体和关系，每条关系带上 `source_chunk_id` 和置信度。实体先做消歧，再以租户、类型、规范名做幂等 `MERGE`。正文向量另存，和图节点用同一套 ID 关联。抽取失败的文档仍可被向量检索到，只是暂时没有边。

查询：能用意图对应的 Cypher 模板就用模板，模型只填参数。必须自由生成 Cypher 时，先过只读和语法约束，再执行。多跳把跳数、扇出、返回条数和超时写死，超级节点不展开。

空结果按顺序降级：放宽可放宽的过滤条件，仍为空就用向量召回相关块；再为空就说没有依据。不要为了有答案改用模型记忆。

交叉校验：准备写进回答的每条关系，都要能回到来源块；来源文本对不上的边丢掉。图结果和向量结果冲突时，不合成一个折中答案，改为说明冲突或放弃断言。全局性的「总结全部文档」可以另做社区摘要，但不能替代这条带来源的路径。

### 6. Cypher 安全治理：只读账号、白名单、参数化、注入拦截、返回条数和跳数限制，怎么在 LangGraph 节点里落地

**参考答案**

生成和执行必须分成两个节点，中间有一个守卫节点。守卫不通过就走条件边去向量降级，执行节点根本不会跑。

- **只读账号**：图查询使用只有匹配和读取权限的数据库用户，写操作账号不发给 Agent。应用侧再用只读事务执行。
- **白名单**：常见问题用模板 ID，模型填参数，不填语句结构。自由 Cypher 只作为长尾，并且默认关闭。
- **参数化**：条件值全部走参数绑定。用字符串拼接用户输入或模型输出，等于让外部文本变成查询的一部分。
- **注入拦截**：解析语句，只允许匹配、过滤、投影、排序、跳过和限制这类只读子句。拒绝多语句、写子句、装载外部数据和运维过程。解析失败就拒绝。
- **条数和跳数**：没有上限的语句直接拒绝，或由守卫替它加上上限。变长路径限制在业务允许的小范围，并加查询超时。

这些检查放在 LangGraph 的守卫节点里，用代码做，不要放在提示词里。日志记录模板 ID、参数哈希和拒绝原因，不记录可复用的密钥。`thread_id` 和租户条件由服务端写入，模型改不掉。

### 7. 多路召回评估：Recall@K、MRR、NDCG、Faithfulness、Answer Relevancy 怎么定义，bad case 怎么回流重新调切分和 rerank

**参考答案**

前三个看检索排得对不对，后两个看回答本身。不要用一个总分代替。

- **Recall@K**：前 K 条里找回的相关文档数，除以全部相关文档数。RAG 里若一题只有一个金标片段，就退化成这题的金标在不在前 K，再对题目取平均。
- **MRR**：每题取第一个相关文档名次的倒数，再对题目平均。它只关心第一篇对的文档有多靠前。
- **NDCG@K**：按位置折扣累计相关度。常用 `DCG = Σ (2^rel_i - 1) / log2(i + 1)`，再除以理想排序的 DCG。二值相关时 rel 取 0 或 1。它能体现「相关但不是最相关」的文档被排到前面。
- **Faithfulness**：回答里的断言有多少能被这次检索到的上下文支持。它发现的是「说了上下文里没有的话」，不是检索漏了。
- **Answer Relevancy**：回答是否在答所问。答非所问、只答了一半，都会低。它不证明事实正确。

坏例先标失败阶段，再改系统。金标片段不在索引里，查切分、重叠和元数据；在索引里但进不了前 K，查查询改写、过滤是不是太严、某路召回缺失；进了前 K 却被 rerank 打下去，用它做困难负例调重排或 RRF 权重；上下文是对的但回答是错的，查生成约束和引用，不要去调切分。每修一类，先把该例放进回归集再改参数，避免只把这一题调绿。

### 8. LangGraph 多 Agent 编排：Supervisor、子图、条件边、人工介入、状态共享，子 Agent 之间如何避免上下文互相污染

**参考答案**

面向用户的生产流程用 Supervisor：父图根据状态决定下一个子 Agent，而不是让多个 Agent 自由互相聊天。

子图把每个 Agent 编成自己的图，父图用输入映射只传任务说明、权限和必要的实体，子图返回结构化结果。条件边是普通函数，读状态返回下一个节点名，分支要有默认兜底，不能出现没有出边的状态。人工介入用中断停在指定节点，checkpoint 记下现场，恢复时把人的决定写回状态。

状态共享只共享任务 ID、用户权限、最终产物引用。每个子 Agent 用自己的消息通道。并行扇出时给每个分支一份独立输入，不要共用一份可写的草稿列表。

污染通常来自把所有 Agent 的思维过程和工具原文追加进同一条消息列表。父图的上下文里只保留各子 Agent 的结果对象。子图内部的来回调用留在子图 checkpoint 里，需要排查时用 trace 看，不送回父模型。权限也按子 Agent 收窄，研究 Agent 拿不到写工具。

### 9. 多 Agent 任务不重不漏：任务 ID、状态机、幂等、重试、超时重新派发、结果合并，用 Java 服务怎么实现

**参考答案**

以数据库为事实来源，消息队列只负责投递。至少一次投递加上幂等消费，效果上才是一次成功执行。

每个子任务有全局 ID、父任务 ID 和幂等键。幂等键由父任务和子任务规格算出，并加唯一索引。重复创建捕获到唯一键冲突后，返回已有任务。状态只允许：待派发、执行中、成功、失败、取消。用带版本号或下面这种租约更新做迁移，非法迁移影响行数为 0。

超时重新派发靠租约，不靠「再发一条试试」。执行者要在租约到期前续租；到期后调度器把任务改派，并把 fencing token 加一。旧执行者回来提交时 token 对不上，更新失败，结果丢弃。重试次数和退避写在任务行上，超过上限进入失败，并由父任务决定是否整体失败。

结果合并：每个子任务只写自己的结果引用。父任务在事务里锁住自己的行，确认所有必需子任务都成功后，按任务 ID 排序做一次确定性合并。重复的成功回调因为状态已经是成功，更新行数为 0。

派发走发件箱：业务库和「待发送」记录同一事务提交，再投到队列，避免「库里有任务但消息丢了」或「消息有了但库里没有」。

```java
public boolean claim(long taskId, String worker, Instant leaseUntil) {
    // 第一次领取不消耗重试。失败或租约过期后再次领取才增加 retry_count。
    // retry_count 放在 status 之前赋值：MySQL 的 SET 从左到右求值，避免读到刚写上的新状态。
    int updated = jdbc.update(
        """
        UPDATE agent_task
           SET retry_count = CASE
                   WHEN status = 'PENDING' THEN retry_count
                   ELSE retry_count + 1
               END,
               status = 'RUNNING',
               worker = ?,
               fence = fence + 1,
               lease_until = ?
         WHERE id = ?
           AND (
                status = 'PENDING'
                OR (status = 'FAILED' AND retry_count < max_retries)
                OR (
                    status = 'RUNNING'
                    AND lease_until < CURRENT_TIMESTAMP
                    AND retry_count < max_retries
                )
           )
        """,
        worker, Timestamp.from(leaseUntil), taskId);
    return updated == 1;
}

public void succeed(long taskId, long fence, String resultRef) {
    int updated = jdbc.update(
        """
        UPDATE agent_task
           SET status = 'SUCCEEDED', result_ref = ?, lease_until = NULL
         WHERE id = ? AND fence = ? AND status = 'RUNNING'
        """,
        resultRef, taskId, fence);
    if (updated != 1) {
        throw new StaleWorkerException(taskId);
    }
}
```

父任务完成前用 `SELECT ... FOR UPDATE` 看子任务，避免两个回调同时把父任务完成两次。租约已过期且重试次数用尽的行，由扫描改成失败，避免一直停在执行中。锁和队列都不是正确性的唯一依据，唯一索引和 fencing token 才是。

### 10. Harness 工程六层思路：任务管理、上下文供给、工具反馈、验证、错误恢复、审计，哪些放模型内、哪些放模型外

**参考答案**

Harness 是模型外面的控制层。原则是：模型就算错了也必须仍然成立的事情，放在模型外。

| 层 | 放哪里 | 原因 |
| --- | --- | --- |
| 任务管理 | 模型外 | 队列、状态机、取消、优先级不能由模型自己宣布完成 |
| 上下文供给 | 模型外组装，模型只消费 | 检索、记忆挑选、token 预算和权限过滤要可复现 |
| 工具反馈 | 模型选工具，模型外执行并回填观察 | 参数校验、真实调用和错误规范化都不交给模型 |
| 验证 | 模型可以自检，但不能当唯一裁判 | Schema、引用检查、策略和关键操作的人审在外部 |
| 错误恢复 | 策略在模型外，模型只能在预算内重试 | 步数、超时、熔断、降级和转人工由代码控制 |
| 审计 | 完全在模型外 | 轨迹、审批和配置版本不可被模型改写 |

模型内适合做的是：在给定上下文里规划下一步、生成草稿、对模糊文本做抽取。这些输出都要经过外层的校验才能生效。换更强的模型可以减少格式错误，不能因此拆掉外部验证。面试里容易把 Harness 讲成又一个 Agent 框架；它管的是边界和证据，不是再包一层提示词。

### 11. 工具调用沙箱：远程执行命令、文件读写、外部 API、数据库写操作，权限最小化和回滚怎么做

**参考答案**

默认拒绝。远程办公的 Agent 不在生产宿主机上开 shell，也不使用带有生产库账号的工作目录。

命令执行若业务确实需要，放在一次性的隔离环境里：非特权用户、只读根文件系统、默认无外网、没有密钥、有 CPU 和墙钟上限。允许的命令用白名单。任务结束环境销毁。

文件读写限制在该任务的工作区。路径先规范化，拒绝逃出工作区，限制大小和文件类型。写入落在临时卷，确认后再发布；密钥和配置目录不挂进去。

外部 API 由网关代持凭证，模型只看到工具名和业务参数，看不到密钥。出口域名白名单，令牌的权限收到该用户、该操作。

数据库写操作不接受模型生成的自由 SQL。写入走已经存在的领域接口，参数化，并用业务事务。破坏性操作先做人审。回滚优先用同一请求里的事务；已经提交的，用事先写好的补偿动作和幂等键，而不是指望在沙箱里执行反向 shell。每次写记录操作者、参数哈希和审批 ID。

权限按意图发放，会话结束即失效。一个工具被提示词说服去读别的租户或写别的表，应在沙箱和接口两层都被拒绝，并记入审计。

### 12. Kafka 或 RocketMQ 在 Agent 异步任务里怎么用：请求削峰、长任务回调、子 Agent 解耦、失败死信

**参考答案**

在线请求只负责鉴权、落任务、发消息，然后返回任务 ID。模型调用和多步工具都在消费端跑，这样峰值不会打满 Web 线程。

长任务不要占着 HTTP 连接等结果。消费者完成后，把结果引用发到结果主题，或回调业务方；客户端用任务 ID 查状态，也可以走推送。消息体里放任务 ID 和参数引用，大段工具输出放对象存储。

子 Agent 按类型分主题或消费组，Supervisor 只生产子任务消息。需要保持同一会话顺序时，用会话 ID 或父任务 ID 做消息键；可以并行的子任务不要强行塞进同一分区。

失败和死信：消费要幂等，处理过的任务 ID 唯一。可重试的错误按次数退避。RocketMQ 可以用延迟消息做退避；Kafka 没有同样的内建延迟级别，常用重试主题或由调度器到点再投递。超过次数进入死信，带上错误类型，告警后人工或补偿任务处理，不要在原主题里无限重试。

数据库和消息的一致性用发件箱，避免任务状态和消息各写各的。消费端用前面的租约和 fencing token 认领任务，防止两条消息把同一子任务做两次。

### 13. Elasticsearch 做 BM25 召回和元数据过滤，索引字段、分词、权限过滤、与向量库结果融合的实践问题

**参考答案**

索引把「用来匹配的文本」和「用来过滤的字段」分开。正文和标题做文本字段，标题可以在查询时提高权重；租户、权限标签、语言、文档 ID、chunk ID、版本、有效期做成 keyword 或数值，不参与分词。交易对、错误码这类不能被拆开的词，另外保留一个不分词字段。

中文用适合中文的分析器，索引和查询使用同一套分词。同义词要区分索引时展开还是查询时展开，改了词典要知道哪些旧文档不会自动变。只靠默认的西文分析器，中文召回会成片失效。

权限放在过滤上下文里，由服务端按当前用户附上，模型生成的关键词只能进查询子句。过滤不参与打分，也能被缓存。召回之后再滤权限，会把名额浪费在用户不能看的文档上，也有漏滤的风险。

和向量库融合时，两路都先套上同一组权限和时间条件，再按名次做 RRF。BM25 分和余弦相似度不是一个量纲。实践里经常出问题的是：过滤过严导致零结果、分词不一致、chunk 太长使 BM25 失真、近重复占满前排、刷新延迟让新文档暂时搜不到。零结果要能区分「没有文档」和「权限把文档滤光了」，后者不能提示模型换一个更宽的条件。

### 14. 高并发调大模型：信号量限并发、队列异步化、缓存高频答案、降级到小模型或人工，怎么保 P95

**参考答案**

P95 变差多半是排队，不只是模型本身变慢。在途数接近供应商上限时，后面的请求会堆进长尾，所以并发上限按配额设置，而不是按线程池最大值。

交互请求和批处理分队列。交互队列短，等待时间算进截止时间，来不及就不要再调用模型。批处理走异步主题，不跟在线 P95 抢同一批在途名额。信号量限制的是真正打到供应商的请求数。

高频、答案稳定、不涉及用户隐私的问题，可以用归一化问句加知识库版本做精确缓存，回复里带上版本或时间。语义缓存要很高的命中阈值，并先用评测看误命中；金融相关问题上，错缓存比慢更严重。用户私有数据和写操作不缓存。

降级按顺序做：队列将要突破延迟目标时，低优先级改走更小的模型或直接返回「已转人工」；熔断打开后停止重试。重试会在故障时放大在途数，压力高时要收紧重试预算。流式输出能改善首字时间，整段答完的 P95 仍由排队和生成长度决定。

看的延迟是用户侧的端到端，包含排队。只看供应商返回时间，会把队里等着的时间漏掉。

### 15. 可观测性：LangSmith/Langfuse/自建 trace，怎么记录意图、召回、工具、token、延迟、失败率并定位幻觉

**参考答案**

一条用户请求一个 trace，下面按跨度挂意图、检索、重排、模型、工具和校验。LangSmith、Langfuse 或基于 OpenTelemetry 的自建都可以，关键是字段一致、能按版本回放。账号、证件、密钥和完整凭证在导出前脱敏。涉及用户资产数据时，优先自建或放在已批准的环境里，不要为了方便把原文送到未批准的第三方。

每个跨度至少留下：trace ID、会话、租户、意图和置信度、路由结果、检索查询、文档 ID 和分数、重排后的顺序、工具名、参数哈希、工具状态、模型名、提示词版本、输入输出 token、各段延迟、错误类型。失败率按意图和工具拆开，不要只有一个全局错误率。

幻觉要先定位阶段，再决定改哪里。引用检查失败时看上下文里到底有没有依据：没有，是检索或过滤问题；有但回答没用，是生成问题。工具结果和最终回答矛盾，标到生成。意图和用户后来的纠正不一致，标到路由。空检索仍给出肯定答案，标成「无依据仍回答」。把提示词版本、知识库版本和这条轨迹留到留存期结束，才能复现，而不是只留一条「模型胡说」。

线上再用抽检或评判模型看 Faithfulness，但评判模型要定期拿人工标注校准。告警看兜底率、工具失败率、越权拒绝次数和单次费用的突变。

### 16. 手撕算法：实现多路召回结果融合，输入多组 docId 与排名，输出 RRF 分数排序 Top-K，并要求支持按来源权重和去重

**参考答案**

RRF 只使用名次。文档 d 的分数是各来源贡献之和：来源权重为 w、名次为 r（从 1 开始）时，贡献 `w / (k + r)`。k 常用 60，用来减弱第一名和第二名的绝对差距，实际上线要用评测集再定。

同一来源里同一 `docId` 只保留最小名次，避免同一路重复计数。不同来源的贡献相加，这就是多路增强。权重表示这条召回路的可信程度，0 到正无穷都不合适，这里要求权重大于 0。排序按分数降序，分数相同再按 `docId` 字典序，保证结果稳定。

时间复杂度是总命中数加上唯一文档数的排序，空间是唯一文档数。这个算法不读取向量分或 BM25 原始分；调用方如果只有分数、没有名次，要先在路内排好名次再传入。

```python
from collections import defaultdict


def rrf(groups, k=60, weights=None, top_k=10):
    """融合多路召回。

    groups 支持两种输入：
    - [{"weight": 1.0, "hits": [{"doc_id": "a", "rank": 1}, ...]}, ...]
    - [["a", "b"], ["b", "c"]]，名次就是列表顺序，从 1 开始
    """
    if k < 0:
        raise ValueError("k 不能为负")
    if top_k < 1:
        raise ValueError("top_k 必须 >= 1")

    scores = defaultdict(float)
    for index, group in enumerate(groups):
        weight, hits = _parse_group(group, index, weights)
        best_rank = {}
        for doc_id, rank in hits:
            if rank < 1:
                raise ValueError("rank 从 1 开始")
            previous = best_rank.get(doc_id)
            if previous is None or rank < previous:
                best_rank[doc_id] = rank
        for doc_id, rank in best_rank.items():
            scores[doc_id] += weight / (k + rank)

    ordered = sorted(scores.items(), key=lambda item: (-item[1], str(item[0])))
    return ordered[:top_k]


def _parse_group(group, index, weights):
    if isinstance(group, dict):
        weight = float(group.get("weight", 1.0))
        raw_hits = group.get("hits", [])
        hits = []
        for fallback_rank, hit in enumerate(raw_hits, start=1):
            if isinstance(hit, dict):
                hits.append((hit["doc_id"], int(hit["rank"])))
            else:
                hits.append((hit[0], int(hit[1]) if len(hit) > 1 else fallback_rank))
    else:
        weight = 1.0 if weights is None else float(weights[index])
        hits = [(doc_id, rank) for rank, doc_id in enumerate(group, start=1)]
    if weight <= 0:
        raise ValueError("来源权重必须为正")
    return weight, hits


if __name__ == "__main__":
    fused = rrf(
        [
            {
                "weight": 1,
                "hits": [
                    {"doc_id": "a", "rank": 1},
                    {"doc_id": "b", "rank": 2},
                    {"doc_id": "a", "rank": 5},
                ],
            },
            {"weight": 1, "hits": [{"doc_id": "b", "rank": 1}, {"doc_id": "a", "rank": 3}]},
        ],
        k=60,
        top_k=2,
    )
    assert [doc_id for doc_id, _ in fused] == ["b", "a"]
    weighted = rrf([["a"], ["b"]], weights=[10, 1], k=60, top_k=1)
    assert weighted[0][0] == "a"
```

### 2. 讲你最难的 Agent 项目，重点说为什么单 Agent 不行、为什么上多 Agent、如果重做会怎么简化

**答题思路**

用真实项目。面试官要听的是判断，不是架构名词。按「约束 → 单 Agent 的具体失败 → 为什么拆分能对上这个失败 → 重做时删掉什么」来讲。

单 Agent 不够，要举评测或线上证据里的一种，不要只说「任务很复杂」：

- 工具太多，选错率和参数错误明显上升。
- 一个上下文里又检索、又算、又做合规检查，后面的步骤被前面的原文带偏。
- 几段工作可以并行，串在一个循环里把延迟和费用都拉高。
- 只读研究和有副作用的动作混在同一个权限里，没法单独收紧。

上多 Agent 时说明拆分原则：按权限和失败域拆，不按「一个角色一个 Agent」拆。每个子 Agent 有自己的工具、自己的上下文和结构化输出；父流程负责任务状态和合并。补上你怎么证明拆完之后任务完成率、越权率和费用是一起变好的，而不是只变好了其中一个。

重做时主动删：没有评测证据的子 Agent 并回父流程；固定步骤改成工作流；共享草稿改成结果引用。如果这个项目其实用单 Agent 加工作流就够，直接说当时拆早了，以及你靠什么信号判断拆早了。数字和项目名只用你自己的。

### 3. 远程团队协作下，Agent 平台怎么支持多环境、多租户、模型供应商切换、配置灰度和国密/数据合规

**参考答案**

平台把「运行面」和「控制面」分开。运行面处理请求，控制面管配置、密钥、评测和发布。远程团队以配置和设计文档为事实来源，变更走评审，不靠口头同步。

多环境至少分开开发、预发和生产的配置、密钥、索引、图谱和 checkpoint。生产数据不进开发环境。提示词和工具开关用同一套版本化配置，靠环境参数选择端点。

多租户在每条会话、消息、记忆、向量、图节点、缓存键和 checkpoint 上带租户 ID。检索过滤由服务端写入。配额、模型和留存策略按租户配置。任何查询都不信任模型自己声明的租户。

模型供应商放在网关后面。业务代码依赖能力（工具调用、结构化输出、上下文长度），不依赖某一家的 SDK。每个供应商有契约测试和数据等级：敏感上下文只能到已批准的区域和供应商。切换时先影子流量，再按租户灰度，保留即时退回上一版本的路径。

配置灰度包括提示词版本、模型名、检索参数和工具开关，按租户白名单或稳定哈希放量。改索引、重嵌文档这类不能瞬间回滚的变更单独发布，并让在线请求带上知识库版本。

国密和数据合规是工程约束，具体期限和适用法律要按法务结论配置，不写死在代码里。需要国密时，传输和存储使用符合要求的 SM2、SM3、SM4 模块和密钥管理系统，算法和密钥都不进仓库。数据先分级，再决定存哪、能否进模型、保存多久。删除要覆盖数据库、向量、图谱、缓存和 checkpoint，并用审计记录删除动作。密钥销毁可以作为无法解密的最后手段。跨境和跨租户默认不通。

### 4. AI 工作流引擎设计：DAG 任务、依赖解析、并行分支、断点恢复、人工审批、版本回滚，用 Java 怎么落地

**参考答案**

流程定义和某一次运行分开。定义包含节点、依赖和版本，发布后不可改；运行实例钉住它开始时的定义版本。

发布时用 Kahn 算法做依赖解析：统计入度，入度为 0 的节点进队列，弹一个就把它后继的入度减一。最后若还有节点入度不为 0，说明有环，拒绝发布。运行时同样从入度为 0 的节点开始，一个节点成功后才释放后继，所以互不依赖的分支会同时变成就绪，由工作线程或消息消费者并行执行。

每个节点成功后把状态、输入引用和输出引用写进数据库，这就是断点。进程挂了，调度器只重新领取「执行中且租约过期」的节点，已成功的节点不重跑。节点里的外部副作用用幂等键，因为租约过期后可能真的执行过两次。

人工审批是一种节点：进入该节点时状态改为等待，流程停住；审批回调把决定写回，再释放后继。拒绝则走定义好的失败边，而不是让线程在那里睡住。

版本回滚指新的运行用旧定义。已经在跑的实例继续用自己钉住的版本，不中途换定义。若必须迁移，单独写迁移并重新校验依赖。

Java 里用一张运行表加一张节点表即可起步。节点状态用条件更新，就绪节点由线程池或队列消费。下面只示范「依赖释放」这一步，执行器拿到的是已经就绪的节点。

```java
@Transactional
public List<Long> completeAndRelease(long nodeId, long fence, String outputRef) {
    int updated = jdbc.update(
        """
        UPDATE wf_node
           SET status = 'SUCCEEDED', output_ref = ?
         WHERE id = ? AND fence = ? AND status = 'RUNNING'
        """,
        outputRef, nodeId, fence);
    if (updated != 1) {
        return List.of();
    }
    List<Long> children = jdbc.queryForList(
        "SELECT child_id FROM wf_edge WHERE parent_id = ?", Long.class, nodeId);
    List<Long> ready = new ArrayList<>();
    for (Long child : children) {
        // 行锁把多个父节点的释放串行化，只有减到 0 的那次把后继标成就绪
        List<Integer> locked = jdbc.query(
            """
            SELECT indegree FROM wf_node
             WHERE id = ? AND status = 'PENDING'
             FOR UPDATE
            """,
            (rs, rowNum) -> rs.getInt(1),
            child);
        if (locked.isEmpty() || locked.get(0) <= 0) {
            continue;
        }
        int now = locked.get(0) - 1;
        jdbc.update(
            """
            UPDATE wf_node
               SET indegree = ?,
                   status = CASE WHEN ? = 0 THEN 'READY' ELSE status END
             WHERE id = ? AND status = 'PENDING'
            """,
            now, now, child);
        if (now == 0) {
            ready.add(child);
        }
    }
    return ready;
}
```

同一父节点的重复回调因为状态已不是 `RUNNING`，影响行数为 0，后继不会被减两次。并行分支的正确性来自入度，不来自线程数。返回的就绪节点要再用条件更新从 `READY` 改成 `RUNNING`，扫描器就算同时看到，也只有一方领取成功。

### 5. 意图识别持续迭代：标注数据不足、意图漂移、新业务接入、线上误分类如何用反馈闭环自动优化

**参考答案**

闭环可以自动收集和自动回归，不能自动把线上反馈直接写进生产模型。

标注不够时，用规则和高置信的模型预测做预标注，人只审低置信、两类分数接近、以及和规则不一致的样本。主动学习每次抽最不确定的，比随机抽更省标注。

意图漂移靠分布看，不靠感觉。按周看各意图占比、未知类占比、置信度分布，以及查询向量的偏移。某一类突然变多，先确认是业务变了还是模型坏了。

新业务接入时，新意图先放在影子路由里：线上仍走旧决定，同时记录新模型会怎么判。回归集必须包含旧意图。影子指标没有掉点，再按租户灰度。不要把新样本和旧样本混在一起训完就全量替换。

线上误分类来自用户改口、差评和人工坐席的纠正。这些进标注队列，并带来源。进入训练集前要去重、去掉提示注入和明显的对抗样本。自动优化指的是：样本累积到阈值后触发训练，离线对比旧模型，通过才允许影子发布。阈值本身也用新的验证集重算。任何一步回归失败，都停在当前版本。

优化目标同时看准确率和「不该进工具的流量有没有增加」。只把分类准确率做高，可能把更多请求放进错误的工具。

### 6. 三层记忆与个性化冲突：不同地区用户、不同监管要求的记忆留存与删除，怎么设计留存策略和审计

**参考答案**

个性化是留存策略允许之后才有的功能。地区和监管要求冲突时，按更严格且已经生效的策略执行，不把「更好的推荐」放在删除权前面。

留存策略按数据级别和地区配置：原始对话、抽取后的事实、向量、图谱里的个人实体、checkpoint，各自有能否保存、存在哪个区域、保存多久。期限来自合规结论，代码只读取策略，不写死一个全球统一的天数。某些地区或某些用户可以选择关闭长期记忆，这时只有会话级状态，会话结束即失效。

读取时带上用户所在区域。区域 A 的记忆不参与区域 B 的检索，缓存键里也有区域。模型供应商若不能接收该级别的数据，上下文组装阶段就不要把记忆放进去。

删除由用户请求或到期任务触发，生成一个删除清单：关系库、向量、图、Redis、checkpoint 和对象存储。每一处删除都有回执，失败会重试。备份用密钥销毁或按备份周期覆盖，不承诺备份介质上的即时物理清除，这一点要在策略里写明。删除之后的个性化请求只能看到剩余的合法数据。

审计记录谁在什么时候因为什么读取或删除了哪一类记忆，不把记忆正文再复制进审计日志。审计日志自己的留存也受策略约束。面试里容易漏的是 checkpoint 和向量索引里的副本：只删了 MySQL，画像其实还在。

### 7. 图数据库性能与成本：Neo4j 大图多跳慢、写入滞后、实体消歧不准，怎么用分层图谱、缓存和异步构建解决

**参考答案**

先缩小「大图」里真正要在线查询的部分。交易流水那种高写入图不应当成 Agent 的在线知识图谱。在线的是抽过的实体和关系；原始文档仍走检索库。

多跳慢，常见原因是跳数过大或碰上超级节点。在线查询把跳数、每层展开的边数和总返回条数封顶，超级节点只返回摘要，不继续扩散。再把图分成两层：概念和规则是稳定的小图，具体实例是大图。能在概念层回答的问题不要去扫实例。对热点查询，用「模板 ID + 参数 + 图版本」做缓存，图版本变了键就失效。

写入滞后就让写入异步：抽取和消歧走队列，查询读已经提交的图版本。新文档在图里还没有边时，用向量召回兜底，并在结果里标出图谱尚未覆盖。不要让用户请求同步等待整篇文档的抽取。

消歧不准时，合并要比漏链更谨慎。自动合并只处理高置信；低置信进复核队列。每次合并保留来源 ID，方便拆开。错误的合并会把多跳答案成片带偏，所以在线阶段宁可少一条边。

成本上，Neo4j 里只放需要关系遍历的节点。把所有 chunk 都建成节点，内存和写入都会贵，而且查询更慢。贵在查询延迟时先限跳和加缓存，贵在写入时先异步和削峰，不要先把集群规格加倍。

### 8. LangGraph 生产部署：FastAPI/Spring 网关、PostgreSQL 检查点、水平扩容、长任务状态恢复、限流与多模型路由

**参考答案**

网关用 Spring 或 FastAPI 都可以，职责是鉴权、租户、限流、流式输出和取消，不在网关里写业务图。LangGraph 的 worker 放在网关后面，本身尽量无本地状态。

检查点用 PostgreSQL。每个 super-step 按 `thread_id` 写入状态、通道数据和尚未提交的写操作。恢复时取该线程最新的检查点。大字段放外部存储，库里留引用，并按线程裁剪旧检查点，只保留恢复需要的版本和仍在等待人工的版本。连接池按 worker 数配置，避免每个请求新开连接。

水平扩容的前提是 worker 不保存会话。任何一台机器都能用 `thread_id` 把状态读出来继续跑。热点是同一线程的连续写入，不是把所有用户都粘到同一台机器。扩容前先看数据库连接和单线程写放大。

长任务接口先返回任务号和 `thread_id`。客户端断开后用同一线程再连，从最新检查点继续。节点在写完检查点前失败会被重跑，所以工具调用要带幂等键。`thread_id` 和登录用户绑定，防止串会话。

限流放在网关上，按租户和按模型供应商各一份信号量，排队时间计入预算。多模型路由也在网关：按任务选择主模型，429 或超时再切到已批准的备用模型，并把实际使用的模型写进 trace。备用模型的工具调用格式要用契约测试覆盖，不能假设和主模型一样。

### 9. 多 Agent 评测体系：任务完成率、工具准确率、步骤数、token 成本、幻觉率、越权率，如何做回归和对比实验

**参考答案**

六个指标分开报，不合成一个排行榜分数。

- **任务完成率**：终态是否满足该题的成功标准。能用规则判定的不用模型裁判；必须裁判的，定期用人工标注校准。
- **工具准确率**：该调用的工具有没有调用，参数是否正确。多调用、少调用分开计。
- **步骤数**：完成任务的节点或工具次数，用来看多 Agent 有没有越做越绕。
- **token 成本**：按一次任务的输入和输出计，包含失败重试。
- **幻觉率**：无依据断言占断言的比例，分母要固定，否则不可比。
- **越权率**：超出该用户、该 Agent 权限的工具调用或数据访问。这一项是硬门槛，变差就不能发布。

回归用冻结的评测集，按意图和难度切片，集合本身也有版本。每次只改一个因素：提示词、模型、拓扑或检索。和当前生产版本比，完成率至少持平，费用和步骤数要一起看，越权率不允许变差。离线通过后按租户做影子流量，再小流量对比。线上对比看的是同一套指标，不是只看好评。

多 Agent 的对比要包含协调失败：子任务漏了、重复了、合并错了。只看最终回答，会把这些成本藏起来。

### 10. Harness 与模型升级关系：换更强模型后，原有意图阈值、工具校验、记忆压缩、retry 策略哪些要重新验证

**参考答案**

模型升级之后，Harness 的代码可以留着，里面的阈值和策略要重新验证。更强不代表原来的保护仍然落在正确的位置。

意图阈值要重测。新模型的置信度分布会变，旧阈值可能把太多流量放进工具，也可能让澄清变多。用同一套标注集看准确率，以及「错误进入工具」的比例。

工具校验要保留，同时重看重试提示。新模型更遵守 Schema 时，为旧模型写的多次格式重试会变成浪费；它也可能更积极地调用新工具，校验和白名单要用评测看有没有多调用。

记忆压缩要重测事实保留率。旧的压缩提示可能让新模型压得太狠，或写出更长的摘要把预算吃掉。用固定对话比较压缩前后，关键槽位是否还在。

重试策略要重算次数和退避。格式错误变少就降低这类重试；若新模型更慢或更贵，原来的超时和重试预算会直接推高 P95 和费用。有副作用的重试仍由幂等键保护，这一点不因模型变强而放松。

验证方法是冻结评测集加一段影子流量，对比轨迹而不只对比一个总分。通过之前，生产路由仍指向旧模型。

### 11. 技术选型打架时怎么定：LangChain、LangGraph、CrewAI、AutoGen、自研工作流，分别适合什么、什么时候不碰多 Agent

**参考答案**

先写清流程里哪些步骤允许模型临时决定。这一步比框架名字更重要。

LangChain 适合集成多、路径固定的链：检索、抽取、单次生成。它能把一个节点里的模型调用写清楚。用它承载长时间的循环、人审和崩溃恢复，状态会散落在业务代码里。

LangGraph 适合路径里真有循环、分支、人审和断点恢复，并且希望状态结构可见。团队要能看懂检查点和 reducer。只有一条直线流程时，它比普通工作流重。

CrewAI 适合用角色快速做多 Agent 原型。生产上若需要严格的状态机、租户隔离和可重复的失败恢复，要看这些控制点能不能落到你自己的服务里，不能只停留在角色提示词。

AutoGen 适合研究、编程助手这类以对话推动的多 Agent 试验。面向用户、又带权限和副作用的流程，自由对话很难给出步数和权限上限，不适合当主控制面。

自研工作流适合步骤大多确定、团队主栈是 Java、审计和状态机必须进现有服务的情况。模型只作为一个节点。代价是图的可视化和持久化要自己做。

不碰多 Agent 的情况：单一意图、单一工具、步骤固定、延迟和费用预算紧、还没有评测能指出协调错误。这时用一个工作流加上必要的单 Agent 节点。等多 Agent 的评测证明单 Agent 在权限、并行或上下文上确实失败，再拆。选型用同一评测集比较一条固定流程和候选框架，不同时改三个变量。

### 12. 学习能力与新技术判断：最近半年你跟了哪些 Agent/LLM 新东西，怎么从论文、源码、benchmark 到生产验证

**答题思路**

只讲你真正读过、跑过或在项目里验证过的东西。名字、论文和结论都要能展开，没跟过的方向不要凑。

可以按这个顺序准备每件事，讲两件就够：

1. **问题**：它准备解决的是延迟、工具可靠性、评测、上下文长度还是数据出域。先说你当时的生产问题。
2. **材料**：你读的是论文、官方说明还是源码。挑一个你看过的实现细节，例如状态怎么持久化、工具结果怎么回填。
3. **基准**：公开 benchmark 说明了什么，又没覆盖你的场景什么。点明口径，例如只有英文、没有权限、没有副作用。
4. **自己的验证**：用一小批真实轨迹做对比，看质量、P95、费用和失败类型。结论是采纳、限定场景采纳，或明确不采纳。
5. **生产门槛**：要补上哪些 Harness 才敢用，例如校验、审计、回滚和评测集。没有这一步，就说明它还停在原型。

如果面试官追问最近的方向，只从你真跟过的里面选，例如工具调用协议、上下文压缩、Agent 评测、长上下文的实际收益、沙箱边界。每个都要能说出你看到的一个限制，而不只是名称。

### 13. 如果让你从零搭币安级别远程 AI Agent 中台，列架构、团队分工、里程碑、风险点和第一年 KPI

**参考答案**

第一年的目标是一个可审计、可回滚的只读中台，把写操作和多 Agent 留到评测证明需要之后。下面是架构方案，不是已经存在的项目。

架构按数据流分七块。接入网关负责鉴权、租户、限流和区域。编排层用工作流引擎，只有需要循环和恢复的节点用状态图。模型网关统一供应商、配额和降级。知识层按租户和区域放检索、向量和一张小的知识图谱。工具层全部走 Schema、沙箱和领域接口。记忆层按地区策略保存，并支持删除。旁路是评测、trace、审计和配置中心。在线请求和长任务用队列隔开。

团队按职责分，不按人头报一个虚数：平台负责网关、编排、配置和多租户；知识负责文档管道和检索；场景按业务接 Agent，不各自再写一套编排；安全合规负责权限、留存、沙箱和审计；评测和值班负责评测集、线上质量和跨时区响应。远程协作的产出是设计文档、可回滚的配置和值班记录。

里程碑可以排成五步。第一步，一个只读场景跑通鉴权、检索、引用、trace 和人工兜底，并冻结评测集。第二步，加上工具校验和会话记忆，写工具默认关闭。第三步，做配置灰度和模型切换，看清单次任务费用。第四步，只对评测里确实需要多跳的问题加图谱。第五步，补齐分区部署和删除权。多 Agent 不在前三步里。

风险集中在五处：模型直接做资金相关写操作；检索或记忆串租户；供应商和跨境传输超出数据等级；多 Agent 先于评测上线；远程环境的配置漂移。每条都要有对应的开关和告警。

第一年 KPI 用基线对比，不预设一个全球统一的百分比。看冻结评测集上的任务完成率、人工接管率、端到端 P95、单次成功任务的费用、无依据回答的比例，以及越权调用。越权按安全事件处理，门槛由风控和合规定。上线前先把评测集和口径冻结，否则这些 KPI 无法比较。

### 14. 手撕算法：给定一个工具调用依赖图，部分节点需 LLM 产出参数、部分节点可并行，输出合法执行顺序并求最小完成时间，考虑重试和故障节点重调度

**参考答案**

这是带依赖的调度。先检查环：有环就不存在合法顺序。再处理已知会失败的节点。`fail_times` 是工具执行会失败的次数，`max_retries` 是允许的额外重试次数；失败次数超过重试上限时，该节点和所有后继都不可执行，其他分支继续。这样才是故障后的重调度，而不是整张图直接放弃。

可以执行的节点里，LLM 产出参数的耗时只计一次，参数成功后缓存；工具失败则按退避重跑工具，重试串行累加。节点耗时为：

`llm_duration + (fail_times + 1) * duration + fail_times * backoff`

无限并行时，最短完成时间就是关键路径：节点的最早开始时间等于所有前驱最早结束时间的最大值。有限 worker 时，带依赖的最短完成时间是 NP-hard 的，关键路径只是下界。下面的代码用列表调度给一个可行解：每次从已就绪节点里选「最早能开始」的那个，放到当前最早空闲的 worker 上。输出的启动顺序是一个合法拓扑序。并行节点的区间可以重叠。

时间复杂度是节点数加边数，再加上有限 worker 时每次选择就绪节点的开销，整体约 `O(N² + E)`。空间是节点数和边数。

```python
import heapq
from collections import defaultdict


def schedule(nodes, workers=None):
    if not nodes:
        return _result(True, [], 0, [], [], 0)
    children, indeg = _graph(nodes)
    _ensure_acyclic(nodes, children, indeg)

    blocked = _blocked(nodes, children)
    runnable = {i: nodes[i] for i in nodes if i not in blocked}
    if not runnable:
        return _result(False, [], 0, [], sorted(blocked, key=str), 0)

    cost, attempts = _costs(runnable)
    lower = _critical_path(runnable, cost)
    order, plan, makespan = _list_schedule(runnable, cost, attempts, workers)
    return _result(not blocked, order, makespan, plan, sorted(blocked, key=str), lower)


def _graph(nodes):
    children, indeg = defaultdict(list), {}
    for name, node in nodes.items():
        deps = list(node.get("deps", []))
        indeg[name] = len(deps)
        for dep in deps:
            if dep not in nodes:
                raise KeyError(f"未知依赖: {dep}")
            children[dep].append(name)
    return children, indeg


def _ensure_acyclic(nodes, children, indeg):
    pending = dict(indeg)
    stack = [name for name, degree in pending.items() if degree == 0]
    seen = 0
    while stack:
        current = stack.pop()
        seen += 1
        for child in children[current]:
            pending[child] -= 1
            if pending[child] == 0:
                stack.append(child)
    if seen != len(nodes):
        raise ValueError("依赖图有环，不存在合法执行顺序")


def _blocked(nodes, children):
    dead = set()
    for name, node in nodes.items():
        if int(node.get("fail_times", 0)) > int(node.get("max_retries", 0)):
            dead.add(name)
    blocked = set(dead)
    changed = True
    while changed:
        changed = False
        for name, node in nodes.items():
            if name in blocked:
                continue
            if any(dep in blocked for dep in node.get("deps", [])):
                blocked.add(name)
                changed = True
    return blocked


def _costs(nodes):
    cost, attempts = {}, {}
    for name, node in nodes.items():
        fails = int(node.get("fail_times", 0))
        retries = int(node.get("max_retries", 0))
        llm = int(node.get("llm_duration", 0))
        duration = int(node["duration"])
        backoff = int(node.get("backoff", 0))
        if min(fails, retries, llm, duration, backoff) < 0:
            raise ValueError("耗时和次数不能为负")
        attempts[name] = fails + 1
        cost[name] = llm + attempts[name] * duration + fails * backoff
    return cost, attempts


def _critical_path(nodes, cost):
    children, indeg = defaultdict(list), {name: 0 for name in nodes}
    for name, node in nodes.items():
        for dep in node.get("deps", []):
            indeg[name] += 1
            children[dep].append(name)
    ready = sorted(name for name, degree in indeg.items() if degree == 0)
    order = []
    while ready:
        current = ready.pop(0)
        order.append(current)
        for child in children[current]:
            indeg[child] -= 1
            if indeg[child] == 0:
                ready.append(child)
        ready.sort()
    finish = {}
    for name in order:
        start = 0
        for dep in nodes[name].get("deps", []):
            start = max(start, finish[dep])
        finish[name] = start + cost[name]
    return max(finish.values(), default=0)


def _list_schedule(nodes, cost, attempts, workers):
    children, indeg = defaultdict(list), {}
    for name, node in nodes.items():
        deps = [dep for dep in node.get("deps", []) if dep in nodes]
        indeg[name] = len(deps)
        for dep in deps:
            children[dep].append(name)

    worker_count = len(nodes) if workers is None else int(workers)
    if worker_count <= 0:
        raise ValueError("workers 必须为正")
    free = [0] * worker_count
    heapq.heapify(free)
    ready = [(0, name) for name, degree in indeg.items() if degree == 0]
    running = []
    plan, done = [], 0

    while done < len(nodes):
        if ready and free:
            earliest = free[0]
            best = None
            for ready_at, name in ready:
                start = max(ready_at, earliest)
                key = (start, str(name))
                if best is None or key < best[0]:
                    best = (key, ready_at, name, start)
            _, ready_at, name, start = best
            ready.remove((ready_at, name))
            heapq.heappop(free)
            end = start + cost[name]
            heapq.heappush(running, (end, len(plan), name))
            plan.append({
                "id": name,
                "start": start,
                "end": end,
                "attempts": attempts[name],
            })
            continue
        if not running:
            raise RuntimeError("无法继续调度")
        end, _, name = heapq.heappop(running)
        heapq.heappush(free, end)
        done += 1
        for child in children[name]:
            indeg[child] -= 1
            if indeg[child] == 0:
                ready.append((end, child))
    makespan = max(item["end"] for item in plan)
    return [item["id"] for item in plan], plan, makespan


def _result(ok, order, makespan, plan, blocked, lower_bound):
    return {
        "ok": ok,
        "order": order,
        "makespan": makespan,
        "schedule": plan,
        "blocked": blocked,
        "lower_bound": lower_bound,
    }


if __name__ == "__main__":
    graph = {
        "A": {"duration": 1, "deps": []},
        "B": {"duration": 10, "deps": ["A"]},
        "C": {"duration": 1, "deps": ["A"]},
        "D": {"duration": 1, "deps": ["B", "C"]},
    }
    unlimited = schedule(graph)
    assert unlimited["makespan"] == 12
    assert unlimited["lower_bound"] == 12
    assert unlimited["order"] == ["A", "B", "C", "D"]
    limited = schedule(graph, workers=1)
    assert limited["makespan"] == 13
    assert limited["lower_bound"] == 12

    retried = schedule({
        "A": {
            "duration": 3,
            "llm_duration": 2,
            "fail_times": 1,
            "max_retries": 1,
            "backoff": 1,
            "deps": [],
        },
        "B": {"duration": 1, "deps": ["A"]},
    })
    assert retried["schedule"][0]["attempts"] == 2
    assert retried["makespan"] == 10

    failed = schedule({
        "A": {"duration": 1, "fail_times": 2, "max_retries": 0, "deps": []},
        "B": {"duration": 4, "deps": ["A"]},
        "C": {"duration": 3, "deps": []},
    })
    assert failed["ok"] is False
    assert failed["blocked"] == ["A", "B"]
    assert failed["order"] == ["C"]
    assert failed["makespan"] == 3

    try:
        schedule({
            "A": {"duration": 1, "deps": ["B"]},
            "B": {"duration": 1, "deps": ["A"]},
        })
    except ValueError:
        pass
    else:
        raise AssertionError("有环时应当失败")
```
