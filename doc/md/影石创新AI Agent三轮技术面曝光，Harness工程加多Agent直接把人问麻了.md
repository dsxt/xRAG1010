### 3. Python的GIL是什么，在AI Agent高并发场景下有哪些影响及规避方案

**参考答案**

GIL（全局解释器锁）是 CPython 的一把互斥锁，同一时刻只允许一个线程执行 Python 字节码，用来保护解释器内部（如引用计数）的线程安全。

影响：

- **CPU 密集型**：多线程不能并行，反而有切换开销。
- **I/O 密集型**：线程在等待网络 / 磁盘时会释放 GIL，所以多线程和 asyncio 仍然有效。

Agent 服务的主要耗时是调用 LLM、向量库、工具接口，属于 I/O 密集，所以通常影响有限。真正会被卡住的是 CPU 密集环节：本地 Embedding / Rerank 推理、大文档解析与切分、JSON 大对象序列化、正则和文本清洗。

规避方案：

1. I/O 并发用 `asyncio` + 异步客户端（`httpx`、异步 DB / Redis 驱动），避免在事件循环里调用阻塞函数，必要时用 `run_in_executor`。
2. CPU 密集任务交给多进程（`ProcessPoolExecutor` / 多 worker 部署，如 gunicorn + uvicorn workers）。
3. 重计算拆成独立服务（模型推理服务、解析服务），Python 只做编排。
4. 使用会释放 GIL 的 C/C++ 扩展（NumPy、PyTorch 等）。
5. Python 3.13 起提供实验性的 free-threaded 构建（PEP 703），但生态兼容性仍需评估，生产上不应作为默认方案。

容易漏的点：GIL 不保证业务层线程安全，`x += 1` 这类复合操作仍要加锁；多进程之间状态不共享，会话状态要放 Redis 等外部存储。

### 4. Java的JVM内存模型及垃圾回收器在长时间运行Agent服务中的调优经验

**参考答案**

JVM 运行时数据区：

- **堆**：分新生代（Eden + 两个 Survivor）和老年代，对象主要在此分配。
- **元空间（Metaspace）**：类元数据，使用本地内存。
- **虚拟机栈 / 本地方法栈 / 程序计数器**：线程私有。
- **直接内存**：NIO / Netty 使用的堆外内存，不受 `-Xmx` 限制，受 `-XX:MaxDirectMemorySize` 约束。

（注意区分：JMM 指 Java 内存模型，是并发可见性、有序性规范；“JVM 内存模型”通常指运行时数据区。）

垃圾回收器选择：

- **G1**：JDK 9 之后默认，按 Region 回收，可通过 `-XX:MaxGCPauseMillis` 设置目标停顿，适合大多数服务。
- **ZGC / Shenandoah**：低停顿，适合大堆、对延迟敏感的场景；JDK 21 提供分代 ZGC。
- **Parallel**：吞吐优先，适合批处理。

Agent 服务的特点：会话上下文、Prompt、流式响应（SSE / WebSocket）长连接多，大字符串和临时对象多，容易出现内存缓慢上涨。

调优思路（按步骤，不拍脑袋改参数）：

1. 先监控：GC 日志、堆使用、GC 停顿、元空间、直接内存、线程数。
2. 常见配置：`-Xms` 与 `-Xmx` 设为相同避免动态扩缩，容器内要让 JVM 感知容器内存限制并预留堆外空间。
3. 排查泄漏：堆转储分析；常见原因是会话缓存无上限 / 无 TTL、`ThreadLocal` 未清理、流式连接未关闭、监听器未注销。
4. 缓存必须有上限与过期，大对象（长上下文）避免长期驻留堆内。
5. 压测验证后再换回收器或调整参数。

具体效果要以自己项目的真实数据为准。

### 5. 意图识别的常见实现方案，规则匹配、小模型分类与LLM路由在实际落地中的取舍

**参考答案**

三种方案各有定位，生产里通常**分层组合**而不是单选。

- **规则匹配（关键词 / 正则 / 词典）**：延迟近乎为零、成本低、结果可解释、可快速热修；缺点是泛化差、维护量随规则增长。适合边界清晰、高频、必须稳定的指令（如“转人工”“查订单”）。
- **小模型分类（TextCNN / BERT 类，或 Embedding + 分类器 / 向量相似度）**：延迟低（毫秒到几十毫秒）、可私有部署、成本可控，但需要标注数据和持续迭代，新增意图要重训或补样本。适合意图集合相对稳定、流量大的场景。
- **LLM 路由（Prompt + 结构化输出 / Function Calling）**：泛化强、冷启动快、能处理多意图和复杂语义；缺点是延迟高、成本高、输出有非确定性，需要 schema 校验。适合长尾、复杂、意图经常变化的场景。

落地建议：

1. 分层漏斗：规则命中直接返回 → 小模型置信度高则返回 → 低置信度或 `unknown` 才走 LLM 兜底。
2. 设置置信度阈值，并设置兜底意图与澄清追问。
3. 用线上 LLM 路由结果回流为小模型训练数据，逐步降本。
4. 离线评估集覆盖主要意图与易混淆意图，监控准确率、拒识率和各层命中占比。

### 6. RAG的基础链路拆解，离线入库与在线检索各阶段的关键节点

**参考答案**

RAG 分离线构建和在线问答两条链路。

**离线入库**：

1. 数据接入与解析：PDF / Word / HTML / 表格等，保留标题、页码、表格结构，这一步质量决定上限。
2. 清洗：去页眉页脚、去重、脱敏。
3. 切分（Chunking）：按语义结构切，并保留元数据（来源、标题层级、更新时间、权限标签）。
4. 向量化：用 Embedding 模型生成向量，并可同时建立倒排索引（BM25）。
5. 写入索引：向量库 / ES，并维护文档版本以支持增量更新。

**在线检索与生成**：

1. Query 理解：多轮指代消解、改写、扩展、拆分子问题。
2. 召回：向量检索 + 关键词检索（混合检索），带权限和元数据过滤。
3. 融合与重排：RRF 融合，再用 Cross-Encoder 类 Rerank 精排取 Top-K。
4. 上下文组装：去重、排序、控制 Token 预算、附带出处。
5. 生成：Prompt 约束“仅依据资料回答、不知道就说不知道”，并要求引用。
6. 后处理：引用校验、拒答、日志与反馈。

容易漏的点：评估要分开做，检索（召回率）和生成（忠实度）分别度量，才能定位问题出在哪一段。

### 7. Chunk切分策略及Overlap设置对检索召回率的影响，如何做语义边界保护

**参考答案**

切分太大，一个块里混入多个主题，向量被稀释，噪声多，占用上下文；切分太小，语义不完整、上下文丢失，检索到的片段不足以回答问题。Overlap 的作用是减少边界处信息被切断，提高召回，但会增加存储、重复召回，也可能让 Top-K 被相邻重复块占满。

常见策略：

- 固定长度 + Overlap：简单，但容易切断语义。
- 递归字符切分：按段落 → 句子 → 词的优先级切。
- 结构化切分：按 Markdown 标题、章节、代码块、表格切。
- 语义切分：相邻句向量相似度突降处作为边界。
- 父子块（Parent-Child）：小块用来检索，命中后返回所属的大块给 LLM。

Overlap 设置：没有通用值，常见做法是取块大小的 10% 到 20% 左右作为起点，再用自己的评测集调参，以召回率、答案质量和成本为依据。

语义边界保护：

1. 优先在标题、段落、句号处断开，不在句子中间切。
2. 表格、代码块、列表保持整体，必要时在块头补上表头 / 标题路径。
3. 给每个块前缀拼接“文档名 > 章节标题”，减少歧义。
4. 召回后合并相邻块，或用父子块扩展上下文。
5. 对重复内容去重。

### 8. 混合检索中向量检索与BM25的结合方式，RRF融合排序的原理

**参考答案**

向量检索擅长语义相近、同义改写；BM25 擅长精确关键词、专有名词、编号、型号。两者互补，所以做混合检索。

结合方式：

1. **分数加权融合**：`score = α·vec + (1-α)·bm25`。问题是两种分数量纲和分布不同，必须先归一化，且权重难调。
2. **RRF（Reciprocal Rank Fusion）**：只用排名，不用分数。

RRF 公式：

```text
RRF(d) = Σ_i  1 / (k + rank_i(d))
```

- `rank_i(d)` 是文档 d 在第 i 路检索结果中的排名（未出现则不计入）。
- `k` 是平滑常数，常用 60，作用是降低头部排名的绝对优势。
- 在多路都靠前的文档得分最高。

优点：不需要分数归一化，对不同检索器的分布差异不敏感，实现简单、效果稳健。缺点：丢掉了分数的“置信度”信息，无法体现某一路得分明显更高的情况。

实践里常见流程：两路各召回 Top-N → RRF 融合 → Rerank 模型精排 → 取 Top-K。

### 9. 项目中用Redis做了哪些事，缓存Embedding、会话短期记忆还是限流降级

**答题思路**

这是项目深挖题，只讲你项目里真实用到的，其余可以作为“还可以这样做”补充。建议按场景逐个讲“存什么 → 数据结构 → key 设计 → 过期策略 → 一致性”：

1. **Embedding 缓存**：key 用“模型名 + 版本 + 文本哈希”，value 存向量（二进制更省空间），避免重复调用 Embedding 接口；换模型时要换 key 前缀。
2. **会话短期记忆**：List / Stream / Hash 存最近 N 轮对话，设置 TTL，超出窗口截断或摘要。
3. **限流**：用户 / 租户维度的令牌桶或滑动窗口，用 Lua 脚本保证原子性；还可以限制并发 LLM 调用数。
4. **降级与熔断状态**：保存失败计数、熔断开关。
5. **其他**：分布式锁（防重复任务）、幂等 key、语义缓存、任务进度。

要点：说清缓存失效、Redis 故障时的降级策略（如退化为无记忆或直接调用），以及大 key、热 key 的处理。

### 10. MySQL在存储Agent会话轨迹与评估结果时的表结构设计，如何兼顾查询与扩展

**参考答案**

原则：高频查询的字段拆成独立列并建索引，变化多、结构不固定的内容放 JSON，超大文本放对象存储，只存引用。

核心表设计（示例）：

- `session`：`session_id`（主键）、`user_id`、`tenant_id`、`status`、`created_at`、`updated_at`。
- `message`（轮次）：`id`、`session_id`、`seq`、`role`、`content`、`created_at`，索引 `(session_id, seq)`。
- `trace_run`（一次执行）：`run_id`、`session_id`、`agent_version`、`status`、`total_tokens`、`latency_ms`、`started_at`。
- `trace_span`（每一步）：`span_id`、`run_id`、`parent_span_id`、`type`（llm / tool / retrieval）、`name`、`input_ref / output_ref`、`token_in / token_out`、`error_code`、`latency_ms`。
- `eval_run` 与 `eval_result`：评估批次（数据集版本、模型 / Prompt 版本）与逐题结果（指标分数、judge 理由）。

兼顾查询与扩展：

1. 高频过滤和聚合字段（状态、耗时、token、版本号、时间）做成列。
2. 工具参数、模型原始响应、扩展指标放 JSON 列，不用频繁改表。
3. 大文本（完整 Prompt、检索全文）放对象存储，表里存 URL / key。
4. 按时间分区或定期归档冷数据，避免单表无限膨胀。
5. 评估结果必须关联 Prompt / 模型 / 数据集版本，否则无法对比与回归。
6. 海量轨迹分析可同步到 ClickHouse / ES，MySQL 只存在线查询所需。

### 11. Elasticsearch在知识库检索中的索引映射设计，text与dense_vector字段的配合

**参考答案**

一个知识库块（chunk）对应一个 ES 文档，通常包含：

- `content`：`text` 类型，用于 BM25；中文要指定分词器（如 IK 分词插件），索引和查询分词策略要考虑一致性。
- `embedding`：`dense_vector` 类型，指定 `dims`（必须与 Embedding 模型维度一致），`index: true`，`similarity`（`cosine` / `dot_product` / `l2_norm`），ANN 使用 HNSW，可配置 `m`、`ef_construction`（具体可用选项随版本不同）。
- 过滤和元数据字段：`doc_id`、`chunk_id` 用 `keyword`；`tenant_id`、权限标签、来源用 `keyword`；`updated_at` 用 `date`；`title` 可单独建 `text`。

示例映射：

```json
{
  "mappings": {
    "properties": {
      "doc_id":   { "type": "keyword" },
      "chunk_id": { "type": "keyword" },
      "title":    { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "content":  { "type": "text", "analyzer": "ik_max_word", "search_analyzer": "ik_smart" },
      "tenant_id":{ "type": "keyword" },
      "updated_at": { "type": "date" },
      "embedding": {
        "type": "dense_vector",
        "dims": 1024,
        "index": true,
        "similarity": "cosine"
      }
    }
  }
}
```

配合方式：

1. 同一次请求里 `query`（BM25）与 `knn`（向量）并行召回，再融合（RRF 或加权）。是否在 ES 内置融合取决于版本与许可，也可以在应用层融合。
2. `knn` 带 filter（租户、权限），做到“先过滤再近邻”，避免召回无权限内容。
3. 更换 Embedding 模型会改变维度和语义空间，需要新建索引并重建，再通过别名（alias）切换。
4. `_source` 里不一定需要返回向量，减少网络开销。

### 12. Kafka在Agent工作流里用来解耦哪些环节，生产者消费者模型怎么保障不丢消息

**参考答案**

Kafka 在 Agent 工作流里的解耦点：

1. **文档入库流水线**：解析 → 切分 → 向量化 → 写索引，各阶段独立扩缩容，削峰。
2. **长耗时 Agent 任务**：API 立即返回 task_id，worker 异步消费执行，结果通过回调 / 轮询 / 推送返回。
3. **事件与审计**：轨迹日志、评估、计费、监控异步落库。
4. **跨服务通知**：工具执行结果、人工审批结果回流。

保障不丢消息要三端一起做：

- **生产端**：`acks=all`，开启幂等 `enable.idempotence=true`，配置重试，并处理发送回调失败（落库重发，或用事务消息 / Outbox 模式保证业务与消息一致）。
- **Broker**：`replication.factor>=3`，`min.insync.replicas>=2`，关闭 unclean leader election。
- **消费端**：关闭自动提交，**业务处理成功后再手动提交位点**；失败重试，多次失败进死信队列（DLQ）。

这样得到的是**至少一次**语义，可能重复，因此消费端必须做幂等（业务唯一 ID 去重、数据库唯一键、状态机判断）。Kafka 的 exactly-once 事务主要适用于 Kafka 内部的读—处理—写，不能直接保证外部系统（数据库、LLM 调用）只执行一次。

### 13. AI工作流里的非确定性问题是怎样处理的，超时、工具调用失败的重试与熔断策略

**参考答案**

非确定性来自 LLM 输出波动、工具与网络不稳定。思路是“约束输出、可重试、可降级、可观测”。

**降低 LLM 输出不确定性**：

- 降低 temperature，使用结构化输出（JSON Schema / Function Calling），输出后做 schema 校验，不合法时带上错误信息让模型重新生成，并限制重试次数。
- 关键决策尽量由确定性代码完成，让 LLM 只做它擅长的部分。

**超时**：每次调用设置超时，并设置整条工作流的总超时（deadline），超时后取消下游调用。

**重试**：

- 只对可重试错误（网络错误、429、5xx）重试，参数错误、鉴权错误不重试。
- 指数退避 + 随机抖动，限制最大次数。
- 有副作用的工具（下单、写库）必须带幂等 key 才能重试。

**熔断**：对下游连续失败率超阈值时熔断（Closed → Open → Half-Open 探测），熔断期间直接走降级，避免雪崩。

**降级与兜底**：备用模型、缓存结果、简化流程、转人工。

**其他**：并发调用设置限流和隔离（舱壁），保存 checkpoint 以便失败后从断点恢复，并记录完整 trace 用于复盘。

### 14. 手撕算法：实现一个简单的意图分类器骨架，输入用户query列表，输出对应的意图标签列表，可用Python任意写法

**参考答案**

思路：分层漏斗。先用规则匹配（快、确定），未命中的交给可插拔的模型分类器（小模型或 LLM），置信度低于阈值则返回 `unknown`。接口支持批量输入，保持输出顺序与输入一致。

时间复杂度：规则层为 O(n·R·L)（n 条 query，R 条规则，L 为文本长度）；模型层取决于具体模型。

```python
import re
from typing import Callable, List, Optional, Tuple

# (意图标签, 正则) 按优先级排列
RULES: List[Tuple[str, re.Pattern]] = [
    ("transfer_human", re.compile(r"转人工|人工客服")),
    ("refund",         re.compile(r"退款|退货|退钱")),
    ("order_query",    re.compile(r"订单|物流|快递")),
]

# 模型分类器接口: 输入 query，返回 (标签, 置信度)
Model = Callable[[str], Tuple[str, float]]


class IntentClassifier:
    def __init__(self, rules=RULES, model: Optional[Model] = None,
                 threshold: float = 0.7, default: str = "unknown"):
        self.rules = rules
        self.model = model
        self.threshold = threshold
        self.default = default

    def _by_rules(self, query: str) -> Optional[str]:
        for label, pattern in self.rules:
            if pattern.search(query):
                return label
        return None

    def predict_one(self, query: str) -> str:
        query = query.strip()
        if not query:
            return self.default
        label = self._by_rules(query)
        if label:
            return label
        if self.model is not None:
            label, score = self.model(query)
            if score >= self.threshold:
                return label
        return self.default

    def predict(self, queries: List[str]) -> List[str]:
        return [self.predict_one(q) for q in queries]


if __name__ == "__main__":
    clf = IntentClassifier()
    print(clf.predict(["我要退款", "帮我查下物流", "转人工", "今天天气怎么样"]))
    # ['refund', 'order_query', 'transfer_human', 'unknown']
```

扩展点：模型层可以换成 Embedding 与各意图原型向量的相似度，也可以换成 LLM 结构化输出；批量场景下模型层应合并成批请求以提高吞吐。

### 3. LangChain的Chain与LangGraph的Graph核心区别，为什么生产级多步编排会选LangGraph

**参考答案**

核心区别：Chain（LCEL）是**无环的线性 / 有向无环的数据流管道**，LangGraph 是**带共享状态的有向图（支持环）的状态机**。

| 维度 | Chain | LangGraph |
| --- | --- | --- |
| 拓扑 | 线性 / DAG，不支持循环 | 支持条件边、循环 |
| 状态 | 靠参数在步骤间传递 | 显式共享 State，节点返回增量更新 |
| 持久化 | 无内置 | Checkpointer 保存每步状态，支持恢复、时间回溯 |
| 人工介入 | 不便 | 支持 `interrupt` 暂停与恢复 |
| 流式 / 观测 | 基础 | 支持按节点、按 token 流式，与 LangSmith 集成 |

为什么生产级多步编排选 LangGraph：

1. Agent 本质是“思考 → 行动 → 观察”的循环，需要环和条件路由。
2. 长流程需要断点恢复、重试、容错，Checkpointer 提供了基础。
3. 需要人工审批、可回放调试。
4. 状态显式，流程可视化，容易测试和治理（步数上限、超时）。

取舍：简单的单次调用（Prompt → 模型 → 解析）用 Chain 即可，没必要引入图。

### 4. LangGraph里State的设计原则，TypedDict共享状态在多线程并发下怎么避免脏写

**参考答案**

**State 设计原则**：

1. 最小化：只放节点间必须共享的数据，大对象（文档全文）放外部存储，State 里只放引用。
2. 可序列化：因为要被 Checkpointer 持久化，不要放连接、锁、函数等不可序列化对象。
3. 字段职责清晰：输入、中间结果、输出分开，必要的版本字段便于迁移。
4. 节点只返回**部分更新**，不原地修改 State。
5. 对会累积的字段（如消息列表）明确声明 **reducer**，如 `Annotated[list, add_messages]` 或 `operator.add`。

**避免脏写**：

1. LangGraph 按超步（superstep）执行，同一步里并行节点读取的是步开始时的状态快照，各节点返回更新，由框架统一合并后才进入下一步，节点不直接共享可变对象。
2. 并行节点写同一个字段时，该字段必须定义 reducer，否则会报并发更新错误；reducer 应尽量满足交换律、结合律，不依赖执行顺序。
3. 不要原地修改传入的 list / dict，应返回新对象。
4. 并行分支尽量写**不同的 key**。
5. 并发请求之间用不同的 `thread_id` 隔离状态；同一个 `thread_id` 的并发调用会互相覆盖历史，需要在上层串行化（队列或分布式锁）。

```python
from typing import Annotated, TypedDict
import operator

class State(TypedDict):
    question: str
    docs: Annotated[list[str], operator.add]  # 并行检索节点各自追加，由 reducer 合并
    answer: str
```

### 5. 多Agent协作常见模式，Supervisor、Hierarchical与Swarm分别适合什么业务场景

**参考答案**

- **Supervisor（中心调度）**：一个主管 Agent 负责拆解任务、决定调用哪个子 Agent，并汇总结果。优点是流程可控、容易观测和治理；缺点是主管是瓶颈和单点，上下文容易膨胀。适合任务边界清晰、需要统一质量控制的场景，如客服分流、报告生成、数据分析流水线。
- **Hierarchical（层级式）**：多层 Supervisor，上层管理子团队的 Supervisor，每个子团队再管理执行 Agent。适合业务域多、任务复杂的大型系统，通过分层降低单个主管的上下文和决策复杂度，但链路更长、延迟与成本更高、调试难。例如研发助手里分为检索团队、代码团队、测试团队。
- **Swarm（去中心 / 交接式）**：没有中心，Agent 之间根据上下文自行 handoff（交接），当前活跃的 Agent 直接与用户对话。适合对话式、阶段性明显的场景，如售前 → 售后 → 技术支持的转接。灵活、延迟低；缺点是全局流程难控制，容易互相踢皮球形成循环，需要限制交接次数。

选型建议：先用单 Agent 加工具；确实需要职责隔离或上下文隔离时再用 Supervisor；规模变大再分层；强调对话交接才考虑 Swarm。多 Agent 不是越多越好，通信和 Token 成本会显著增加。

### 6. 多Agent陷入无限循环或意见不一致怎么破解，超时、最大步数、仲裁者怎么设计

**参考答案**

原则：任何循环都必须有**确定性的终止条件**，不能依赖 LLM 自己“觉得结束了”。

**防止无限循环**：

1. **最大步数**：设置图的执行步数上限（LangGraph 的 `recursion_limit`，建议显式配置），超限时进入兜底节点输出当前最佳结果或转人工，而不是直接抛异常给用户。
2. **超时**：单步调用超时 + 整个任务总时限（deadline）。
3. **预算**：Token / 费用 / 工具调用次数上限。
4. **重复检测**：记录最近的（动作 + 参数）或状态哈希，连续重复则强制跳出或换策略。
5. **交接次数限制**：同一对 Agent 之间来回 handoff 超过 N 次就终止。

**意见不一致**：

1. **仲裁者（Judge）**：独立的 Arbiter Agent 或规则，依据明确的评分标准（事实依据、引用、一致性）裁决。仲裁者最好使用不同于参与方的模型或加上结构化评分，减少自我偏好。
2. **投票 / 多数表决**：多个 Agent 独立作答后投票，适合有明确答案的任务。
3. **限定辩论轮数**：最多 N 轮，超过后由仲裁者直接裁决。
4. **分歧升级**：低置信度或高风险场景转人工审核。

设计要点：终止原因要作为状态字段记录（`terminated_by`），并在 trace 中可见，便于统计哪种终止最常发生，反推 Prompt 或流程缺陷。

### 7. Agent Harness工程的核心组成，为什么说是Model加Harness才等于生产级Agent

**参考答案**

Harness 指围绕模型的整套**运行时工程框架**：模型只负责推理和决策，Harness 负责让它在真实环境里可靠、可控、可观测地工作。通俗地说：Agent = Model + Harness。

核心组成：

1. **循环与编排**：Agent 主循环、状态机、终止条件、子 Agent 调度。
2. **工具系统**：工具注册、schema、参数校验、权限、沙箱、超时与重试。
3. **上下文管理**：Prompt 组装、历史压缩与摘要、检索注入、Token 预算。
4. **记忆**：短期（会话）与长期（向量 / 知识）。
5. **安全与护栏**：输入输出校验、权限与审批（Human-in-the-loop）、Prompt 注入防护、敏感信息脱敏。
6. **可观测与评估**：Trace、日志、指标、回归评测集、线上反馈回流。
7. **容错与恢复**：Checkpoint、重试、降级、熔断、幂等。
8. **成本与路由控制**：模型路由、缓存、预算。

为什么是 Model + Harness：模型本身不会重试、不会持久化状态、不会自己限权、不会记录日志，也无法保证输出格式稳定。相同的模型放进不同的 Harness，表现可以差很多。生产级可用性（稳定、安全、成本、可维护）主要来自 Harness，而不是只靠换更强的模型。

### 8. Harness里怎么做全链路观测与Trace，每步的输入输出、工具结果、Token消耗怎么采集

**参考答案**

做法是把一次请求建模为一棵 **Trace → Span 树**，并在 Harness 的统一入口（模型调用层、工具调用层、检索层、节点执行层）埋点，而不是散落在业务代码里。

**数据模型**：

- `trace_id`（一次请求 / 任务）、`span_id`、`parent_span_id`，`session_id`、`user_id`、`agent_version`、`prompt_version`。
- Span 类型：`llm`、`tool`、`retrieval`、`node`、`agent`。
- 每个 Span 记录：开始 / 结束时间与耗时、输入、输出、状态与错误码、重试次数。

**采集方式**：

1. 用装饰器 / 中间件 / 回调（LangChain Callback、LangGraph 与 LangSmith 集成）统一包装。也可以使用 OpenTelemetry 作为标准，并对接 Langfuse、LangSmith 等后端。
2. **Token 消耗**：优先读取模型 API 响应里的 `usage`（输入、输出、缓存命中）；流式输出需要打开返回 usage 的选项，没有时用 tokenizer 估算并标记为估算值。再乘以单价得到成本，按 Trace 汇总。
3. **工具结果**：记录参数、返回、耗时、异常；大内容截断或存对象存储，Span 里只存引用。
4. **传播**：跨异步任务、跨服务（Kafka 消息头）传递 `trace_id`。

**注意点**：

- 脱敏：手机号、密钥等在写入前处理。
- 高流量下按比例采样，但出错和慢请求全量保留。
- 异步批量上报，不能阻塞主链路。
- 要能回放：保存足够信息以复现某一步。

### 9. 工具调用失败后的降级与兜底方案，Reflection改写参数、换工具还是切人审

**参考答案**

先**分类错误**，再选择对应策略，而不是一律重试：

1. **瞬时错误**（超时、网络、429、5xx）：指数退避重试，配合熔断；有副作用的操作必须带幂等 key。
2. **参数错误 / 校验失败**（模型生成的参数不合法）：**Reflection**，把错误信息和 schema 回给模型，让它修正参数后重试，限制 1 到 2 次，避免死循环。
3. **工具本身不可用 / 能力不足**：**换工具**，如备用 API、不同数据源，或降级到缓存、历史数据，并向用户说明结果可能不是最新。
4. **权限不足 / 高风险操作 / 多次修复仍失败 / 低置信度**：**切人审**（Human-in-the-loop），保存当前状态等待人工处理或审批。
5. **最终兜底**：诚实告知失败，给出部分结果或下一步建议，不要编造工具结果。

要点：

- 把错误信息结构化（错误码、是否可重试）返回给 Agent，而不是整段堆栈。
- 每种策略都要有次数和时间上限。
- 写操作失败后的状态要可回滚或补偿。
- 全部决策记录进 Trace，方便统计失败原因。

### 10. RAG出现幻觉的三层原因与对应解法，没召回到、召回错了、模型乱答分别怎么治

**参考答案**

**第一层：没召回到**（知识库里有但没找到，或本来就没有）

- 原因：切分不合理、Query 与文档表述不一致、Embedding 对专业术语不敏感、知识库缺内容。
- 解法：优化解析与切分；Query 改写、扩展、拆分；混合检索（向量 + BM25）；增大召回候选数再 Rerank；元数据过滤；补充知识库。知识库确实没有时，要让模型**拒答**而不是硬答。

**第二层：召回错了**（召回了不相关或过期的内容）

- 原因：语义相似但答案不相关、多版本文档冲突、噪声过多。
- 解法：Cross-Encoder Rerank；相关性阈值过滤；版本与时间过滤；去重；检索结果经 LLM 相关性判断再保留；父子块保证上下文完整。

**第三层：模型乱答**（给了正确资料仍然编造）

- 原因：Prompt 没有约束、资料太长被淹没、模型倾向使用参数记忆。
- 解法：Prompt 明确“仅依据资料回答，资料不足就说不知道”；要求引用出处；控制上下文长度与顺序；降低 temperature；生成后做**忠实度校验**（把答案拆成断言，逐条检查是否被资料支撑），不通过则重写或拒答；换更强模型或微调。

核心方法：先分层**定位**再治理——分别评估检索指标（召回率、相关性）和生成指标（忠实度），否则只会盲目调 Prompt。

### 11. 检索效果评估指标，检索相关性、忠实度、回答相关性怎么用LLM-as-a-Judge做无参考评估

**参考答案**

“无参考”指不需要人工标注的标准答案。常用 RAG 三元组：

1. **检索相关性（Context Relevance）**：召回的内容与问题是否相关。做法：让 Judge 对每个召回块打分（或二分类 relevant / irrelevant），再统计相关块比例，或在有排序时算类似 Precision@K 的指标。
2. **忠实度（Faithfulness / Groundedness）**：答案中的内容是否都有召回资料支撑。做法：先让 LLM 把答案拆成多个原子断言，再逐条判断是否能由上下文推出，忠实度 = 被支持断言数 / 总断言数。
3. **回答相关性（Answer Relevance）**：答案是否切题。做法：让 Judge 直接按量表打分；或像 RAGAS 那样，由答案反向生成若干问题，再计算与原问题的 Embedding 相似度。

Judge 的工程要点：

- Prompt 给出明确的评分标准（rubric）和输出 JSON（分数 + 理由），temperature 设为 0。
- 注意偏差：位置偏差、长度偏好、自我偏好，可以用不同于被评模型的 Judge，或多次评估取均值。
- 用一小批人工标注样本**校准** Judge，计算与人工的一致率，不能直接信任。
- 有标注时，再补充传统指标：Recall@K、MRR、nDCG。
- 线上抽样评估 + 离线回归集，并记录 Judge 的模型与 Prompt 版本。

### 12. Redis用在Agent记忆管理的细分设计，短期滑动窗口、长期向量记忆与TTL淘汰策略

**参考答案**

**短期记忆（会话级）**：

- 用 List 或 Stream 存最近消息，key 如 `mem:short:{session_id}`。写入后 `LTRIM` 保留最近 N 轮，或按 Token 数裁剪（比条数更准确）。
- 超出窗口的旧内容不直接丢弃，而是用 LLM 压缩成摘要，存入 `summary` 字段，下次拼接“摘要 + 最近 N 轮”。
- 设置 TTL（如会话空闲后过期），每次访问时续期。

**长期记忆（跨会话）**：

- 存用户偏好、事实等，转成向量，使用 Redis 的向量检索能力（Redis Stack / RediSearch 的向量索引）或使用专门的向量库；元数据（user_id、类型、时间、重要度）用于过滤。
- 写入前做**记忆提炼与去重**，避免把每句话都存下来。
- 检索时按相似度、时间衰减、重要度综合排序，取 Top-K 注入 Prompt。

**TTL 与淘汰**：

- TTL 是按时间过期；Redis 的 `maxmemory-policy`（如 `allkeys-lru`、`volatile-lru`、`volatile-ttl`）是内存满时的淘汰。要明确：重要记忆不要依赖 LRU 被动淘汰，需要持久化到 MySQL 等，Redis 作为缓存层。
- 不同类型记忆设置不同 TTL（会话级短、用户画像长）。
- 避免大 key（超长对话不要放在一个巨大的 value 里）。
- 多实例并发写同一个会话时，注意顺序与原子性（Lua 脚本或 Stream）。
- 涉及隐私的数据支持按用户删除。

### 13. Kafka在Agent异步任务与回调通知中的拓扑设计，怎么保证顺序消费与时间对齐

**参考答案**

**拓扑设计**：

1. `agent.task.request`：API 把任务发入，worker 消费者组执行 Agent。
2. `agent.task.event`：执行过程事件（开始、步骤、完成、失败）。
3. `agent.task.callback`：回调通知服务消费后，通过 Webhook / 推送通知调用方，失败重试，多次失败进 `*.dlq`。
4. 重试用独立的 retry topic（带延迟分级），避免阻塞主 topic。

**保证顺序**：

- Kafka 只保证**同一分区内有序**。用 `task_id` 或 `session_id` 作为消息 key，同一 key 进入同一分区，由同一个消费者顺序处理。
- 同一个 key 并发度要受控：单个消费者对同一 key 串行处理；生产者开启幂等并限制 `max.in.flight.requests.per.connection` 以避免重试导致乱序（开启幂等时 Kafka 在合理范围内保证顺序）。
- 调整分区数会改变 key 到分区的映射，需要谨慎。
- 重试 topic 会破坏顺序，对有严格顺序要求的流，要么原地阻塞重试，要么消费端按序号重排。

**时间对齐**：

- 不要依赖消息到达时间。消息体中带**事件时间戳**和**单调递增的序号（seq）**，消费端按 `seq` 校验，发现乱序或缺口时缓冲等待或丢弃旧版本。
- 多服务时钟可能不一致，业务判断先后用序号 / 版本号，时间戳用于展示和监控。
- 回调通知需要幂等（`event_id` 去重），因为至少一次投递可能重复。

### 14. AI工作流里的成本与控制面设计，模型路由、小模型前置分流、Token预算怎么落地

**参考答案**

“控制面”是把成本、路由、限额这些策略从业务代码中抽出来集中管理，调用方只声明意图，由控制面决定怎么执行。

**模型路由**：

- 按任务类型（分类、抽取、生成、复杂推理）、复杂度、用户等级、延迟要求选择模型。
- 由统一的 LLM Gateway 实现：路由规则可配置、热更新，支持主备切换和故障降级。

**小模型前置分流**：

- 先用规则或小模型判断难度和意图：简单问答、分类、改写走小模型；复杂推理、长文本才升级大模型。
- 小模型置信度不足时再升级（级联）。
- 以线上抽样评估质量，确认分流后效果不下降。

**Token 预算**：

- 请求级：限制输入上下文和最大输出 token（`max_tokens`）；上下文超出预算时按优先级裁剪（摘要旧历史、减少召回数）。
- 任务级：整个 Agent 任务的 Token、工具调用次数、费用上限，超过则终止或降级。
- 租户 / 用户级：配额与限流，用 Redis 计数。
- 预算在每一步调用前检查，剩余不足时走降级路径。

**其他降本手段**：语义缓存与精确缓存；利用供应商的前缀 / Prompt 缓存（稳定的系统提示放前面）；Embedding 缓存；批处理离线任务。

**配套**：按租户、业务、模型维度统计成本，设置告警；评估集联动，避免只看成本不看质量。

### 15. 手撕算法：用Python写一个基于条件边的LangGraph风格最简循环伪代码，包含状态定义、节点函数与条件路由逻辑

**参考答案**

思路：用 `TypedDict` 定义状态；节点函数接收状态，返回**部分更新**；条件边是一个函数，根据状态返回下一个节点名；执行引擎循环“执行节点 → 合并更新 → 路由”，直到到达 `END` 或超过最大步数。

场景：生成答案 → 评审 → 不合格则带着反馈重写，最多重试 3 次。时间复杂度 O(步数 × 节点耗时)。

```python
from typing import Callable, Dict, TypedDict

END = "__end__"


class State(TypedDict):
    question: str
    draft: str
    feedback: str
    attempts: int
    approved: bool


# ---------- 节点：接收状态，返回增量更新 ----------
def generate(state: State) -> dict:
    # 实际中这里调用 LLM，把 feedback 作为改进提示
    draft = f"answer({state['question']}, fb={state['feedback']})"
    return {"draft": draft, "attempts": state["attempts"] + 1}


def review(state: State) -> dict:
    # 实际中这里调用 LLM 或规则评审；此处假设第 2 次起合格
    ok = state["attempts"] >= 2
    return {"approved": ok, "feedback": "" if ok else "请补充依据"}


# ---------- 条件边：根据状态决定下一个节点 ----------
def route_after_review(state: State) -> str:
    if state["approved"]:
        return END
    if state["attempts"] >= 3:      # 终止条件：重试上限
        return END
    return "generate"               # 回到生成节点，形成循环


class Graph:
    def __init__(self):
        self.nodes: Dict[str, Callable[[State], dict]] = {}
        self.edges: Dict[str, str] = {}
        self.cond_edges: Dict[str, Callable[[State], str]] = {}
        self.entry = ""

    def add_node(self, name, fn):
        self.nodes[name] = fn

    def add_edge(self, src, dst):
        self.edges[src] = dst

    def add_conditional_edges(self, src, router):
        self.cond_edges[src] = router

    def set_entry(self, name):
        self.entry = name

    def run(self, state: State, max_steps: int = 20) -> State:
        current = self.entry
        for _ in range(max_steps):          # 兜底：防止无限循环
            update = self.nodes[current](state)
            state = {**state, **update}     # 不原地修改，合并增量
            if current in self.cond_edges:
                current = self.cond_edges[current](state)
            else:
                current = self.edges.get(current, END)
            if current == END:
                return state
        raise RuntimeError("exceeded max_steps")


g = Graph()
g.add_node("generate", generate)
g.add_node("review", review)
g.set_entry("generate")
g.add_edge("generate", "review")
g.add_conditional_edges("review", route_after_review)

init: State = {"question": "什么是RRF", "draft": "", "feedback": "", "attempts": 0, "approved": False}
print(g.run(init))
```

对应真实 LangGraph 写法：`StateGraph(State)`、`add_node`、`add_edge`、`add_conditional_edges("review", route_after_review)`，并用 `recursion_limit` 配置步数上限。

### 16. 如果让你从零搭一套支持多Agent的Harness，第一个版本你优先保哪三个能力，砍掉哪几个

**参考答案**

MVP 的取舍原则：先保证“可控、可见、可恢复”，再追求“聪明”和“功能多”。

**优先保的三个能力**：

1. **可控的执行循环**：统一的状态定义、明确的终止条件（最大步数、总超时、Token / 费用预算）、工具调用的 schema 校验与超时重试。没有它，多 Agent 一旦循环就会烧钱且无法停止。
2. **全链路 Trace 与日志**：每步输入输出、工具结果、耗时、Token 都可查可回放。没有观测，后面的优化和评估都无从做起，线上问题也无法定位。
3. **状态持久化与失败恢复 / 人工介入点**：Checkpoint 保存状态，能从断点恢复，高风险动作可以暂停等待审批。这决定了能否在生产环境放心使用。

**第一版砍掉**：

- 复杂的多层 Hierarchical 与动态创建 Agent，先用单个 Supervisor + 少量固定子 Agent。
- 自动化评估平台与在线 A/B，先保留小规模离线回归集和手工评测。
- 复杂的长期记忆与自动记忆提炼，先只做会话短期记忆。
- 精细的成本路由与语义缓存，先只做硬预算上限。
- 可视化编排界面与插件市场。

接口层面保持可扩展（工具、模型、存储用接口抽象），这样砍掉的能力后续可以平滑补上。

**答题思路**

按“边界 → 契约 → 节奏 → 兜底”回答，并结合你的真实经历（没带过人就讲对接与推动协作的经验）：

### 3. 当算法同学坚持用新模型但工程侧担心延迟与稳定性，你怎么沟通并拍板技术方案

**答题思路**

这是考察决策与沟通的行为题，思路是“用数据对齐而不是争论立场”：

1. **先确认双方关心的目标**：算法关心效果上限，工程关心延迟、稳定性、成本，承认双方都有道理。
2. **定义可量化的验收标准**：效果指标（评测集提升）、延迟（P95）、错误率、成本，由双方共同认可，不凭感觉。
3. **做对比实验**：同一评测集和同样负载下测试，量化收益与代价。
4. **降低风险的折中方案**：
   - 灰度放量或只对复杂请求使用新模型（模型路由）；
   - 老模型作为兜底，超时或失败自动降级；
   - 流式输出、缓存、并发优化缓解延迟。
5. **拍板方式**：以数据为依据，设定回滚条件和观察周期，明确决策人与时间点，结论同步所有人。
6. **复盘**：结果出来后回看决策，建立后续评估新模型的固定流程。

不要编造不存在的案例或数字，没有类似经历时讲清你会如何处理。

### 4. 怎么保障多Agent复杂工作流的按期交付，里程碑、回滚点与灰度开关怎么设计

**参考答案**

核心思路：把大工作流拆成可独立验证、可独立上线、可独立回退的小步。

**里程碑设计**：

1. 先打通**最小闭环**（单链路端到端，哪怕能力简单），再逐步加 Agent、工具与分支。
2. 每个里程碑有明确的验收标准：评测集通过率、延迟、成本、错误率，不能只是“功能做完”。
3. 提前暴露高风险项（模型效果、外部接口、性能），优先做技术验证，避免临近交付才发现问题。
4. 预留联调、压测、评测的时间。

**回滚点**：

- 代码层：版本化发布；Prompt、模型、工具配置、工作流定义都做版本管理，能独立回滚。
- 运行层：Checkpoint 允许任务从最近的稳定节点恢复；长任务按阶段保存产物。
- 数据层：索引和 Schema 变更采用双写与别名切换，保留旧版本一段时间。

**灰度开关**：

- 配置中心 / Feature Flag，按用户、租户、比例、请求类型放量。
- 新旧工作流并存，影子流量（Shadow）先只对比不生效。
- 自动熔断：关键指标（错误率、延迟、成本、评测得分）超过阈值自动回退到旧版本。
- 逐步放量，如小比例观察后再扩大，并有明确的观察窗口。

**配套**：全链路 Trace 与大盘，让灰度期间能快速判断是否回滚；降级路径提前演练。

### 5. RAG大规模文档实时更新问题，增量Upsert、双写索引与事件驱动流水线怎么选

**参考答案**

三者不是互斥关系，通常**组合使用**：事件驱动流水线负责“感知变化与处理”，增量 Upsert 是写入方式，双写索引用于**重建索引 / 模型升级时的平滑迁移**。

**增量 Upsert**：

- 文档有稳定的 `doc_id`，块用 `doc_id + chunk 序号 / 内容哈希` 作为 ID。
- 更新时对比内容哈希，只重新处理变化的文档或块；删除要同步处理（删除旧版本的块，避免残留“幽灵块”）。
- 带版本号，保证旧消息不会覆盖新数据。

**事件驱动流水线**：

- 源系统变更 → CDC / 消息（Kafka）→ 解析 → 切分 → Embedding → 写索引，各阶段异步、可独立扩缩容，用 `doc_id` 作 key 保证同一文档的更新顺序。
- 失败重试 + 死信队列，处理需幂等；Embedding 调用做限流和批处理。

**双写索引**：

- 适用于更换 Embedding 模型、调整切分策略、改 Schema 这类**全量重建**场景：新索引在后台构建，同时新增变更双写到新旧两个索引，验证后用别名切换，再下线旧索引。
- 日常的小更新不需要双写，成本高且增加一致性问题。

**选择建议**：日常更新用事件驱动 + 增量 Upsert；模型 / 结构大变更用双写加别名切换；对实时性要求高的场景保证“写入后几秒可见”（如 ES 的 refresh 间隔），并定期做对账校验。

### 6. 多Agent系统中的上下文膨胀怎么治理，分层记忆、摘要压缩与上下文配额怎么配合

**参考答案**

上下文膨胀会带来成本高、延迟大、模型“迷失”（关键信息被淹没）以及超出窗口的问题。治理的核心是：**不要把所有历史都传给所有 Agent**。

三种手段配合：

1. **分层记忆**：
   - 工作记忆：当前任务需要的最近几轮、当前步骤的中间结果，直接放进 Prompt。
   - 短期记忆：会话历史，存在 Redis / 数据库，按需取。
   - 长期记忆：用户信息、知识沉淀，存向量库，按相似度检索 Top-K 注入。
2. **摘要压缩**：历史超过阈值时，把旧内容压缩为摘要（保留决策、结论、待办、关键事实、引用），原文落库可回查；工具返回的大结果先做裁剪或摘要，只把需要的部分放入上下文。注意摘要会丢失信息，关键事实应结构化保存到状态里，不要只依赖自由文本摘要。
3. **上下文配额**：为每个 Agent、每个部分（系统提示、历史、检索资料、工具结果）分配 Token 预算，超出按优先级裁剪（先裁旧历史、低相关资料），系统提示与当前任务优先保留。

**多 Agent 场景的额外做法**：

- 子 Agent 使用**独立的上下文**，只接收任务描述和必要的输入，完成后只返回**精简的结果**给 Supervisor，而不是返回完整的思考过程。
- Agent 之间通过共享状态里的结构化字段交换信息，而非互相转发完整对话。
- 大对象放外部存储，传递引用。

监控每步 Token 使用，把上下文长度作为告警指标。

### 7. LangGraph的Checkpointer与Human-in-the-loop机制在生产里的落地难点

**参考答案**

**机制**：Checkpointer 在每个超步结束时把图状态保存为 checkpoint，以 `thread_id` 区分会话；有了持久化，才能做暂停、恢复、时间回溯、故障恢复。Human-in-the-loop 通过 `interrupt()`（或编译时设置中断点）暂停图的执行，等人工处理后再用 `Command(resume=...)` 恢复。`interrupt` 依赖 Checkpointer。

**生产落地难点**：

1. **持久化选型**：`InMemorySaver` 只适合开发，生产要用 Postgres 等持久化实现，并考虑连接池、写入延迟、并发。
2. **恢复时节点会重新执行**：恢复后被中断的节点是从头重新运行，而不是从中断那一行继续，所以中断前的副作用（发邮件、扣款）必须幂等，或者把副作用放到中断之后、单独节点中。
3. **状态序列化与演进**：State 必须可序列化；State 结构升级后，旧 checkpoint 的兼容与迁移比较棘手，需要版本字段和迁移策略。
4. **状态膨胀与清理**：每步都会写 checkpoint，历史多时存储增长，需要 TTL、归档、裁剪；State 里不要放大对象。
5. **并发与一致性**：同一 `thread_id` 并发调用要串行化。
6. **审批流程工程化**：待审批任务的通知、超时（审批人一直不响应怎么办）、转交、权限校验、审计记录；前端要能展示待审批内容并支持编辑后恢复。
7. **跨服务 / 进程恢复**：恢复可能发生在另一个实例，因此不能依赖进程内状态、本地文件、内存连接。
8. **可观测**：中断、恢复要体现在 Trace 中，便于排查“卡住”的任务。

### 8. Elasticsearch与向量库双写一致性问题，写入失败、版本冲突与查询侧最终一致性怎么处理

**参考答案**

**首先考虑是否需要双写**：ES 本身支持 `dense_vector`，能用单一存储（ES 或专用向量库）就尽量只维护一份索引，一致性问题自然消失。必须双写时，要明确**数据源（Source of Truth）**，通常是 MySQL / 对象存储，ES 和向量库都只是派生的索引。

**写入失败**：

- 不要在业务代码里“先写 A 再写 B”，失败后无法补偿。用 **Outbox / CDC**：源库变更与事件写入同一个事务，再由异步消费者分别写入 ES 和向量库，这样两边相互独立、可各自重试。
- 失败重试 + 死信队列，写入操作必须幂等（固定的文档 ID，Upsert 语义）。
- 定时**对账**任务，对比源库与两个索引的文档版本或数量，发现缺失就补写。

**版本冲突**：

- 给文档设置单调递增的版本号（源库的更新版本或更新时间）。ES 可使用外部版本（`version_type=external`，更新版本较新才写入），向量库侧在写入时自行比较版本；旧事件迟到时不会覆盖新数据。
- 同一文档的变更按 `doc_id` 作为 Kafka key，保证顺序。
- 删除用带版本的“墓碑”处理，避免旧的写入事件把已删除的文档重新写回。

**查询侧最终一致性**：

- 接受短暂不一致：ES 的刷新间隔本来就是近实时的，两个索引也会有时间差。
- 混合检索融合后，用 `doc_id` 回源或校验版本，剔除已删除、过期的结果，对只在一路出现的文档按需要再确认。
- 敏感场景（权限变更、删除合规）必须保证强一致或在查询时做实时权限校验，而不是只依赖索引里的过滤字段。
- 监控两个索引之间的数据延迟，作为告警指标。

### 9. Kafka在Agent流式输出与多轮交互里的消息语义与幂等消费设计

**参考答案**

先说明定位：面向用户的逐 token 流式输出，通常用 SSE / WebSocket 直连，不会每个 token 都经过 Kafka，否则延迟和开销过高。Kafka 适合在**多服务间传递事件**（如 Agent worker 把流式分片推给网关服务，由网关推送给用户），或做异步落库与审计。如果经过 Kafka，需要考虑如下设计：

**消息语义**：

- 默认是**至少一次**投递，会出现重复，所以**消费端必须幂等**。Kafka 事务的 exactly-once 只覆盖 Kafka 内部的读—处理—写，不覆盖外部系统。
- 同一次回答的所有分片使用同一个 key（`session_id` 或 `message_id`），进入同一分区，保证分片有序。

**消息结构**：

```json
{
  "event_id": "唯一ID",
  "session_id": "s1",
  "message_id": "m1",
  "seq": 17,
  "type": "delta | tool_call | done | error",
  "payload": "...",
  "ts": 1700000000000
}
```

**幂等消费**：

- 以 `(message_id, seq)` 去重：Redis `SET NX` 或数据库唯一键；也可以记录每个消息已处理的最大 `seq`，小于等于的直接丢弃。
- 网关按 `seq` 顺序组装，出现缺口时短暂缓冲等待，超时则以 `done` 事件终止或请求重放。
- `done` / `error` 作为结束标记，保证状态收敛。
- 多轮交互里，用户的新消息要带上 `turn_id`；用户打断时发取消事件，生产者和消费者据此丢弃该 turn 剩余分片。

**其他**：分片合并发送（按时间窗口或字数聚合）降低消息量；设置合理的保留时间；消费位点在处理完成后再提交；消费失败的分片进入死信队列，不阻塞整条流。

### 10. 技术选型时，自研Orchestrator、LangGraph、CrewAI或AutoGen在高阶需求下的权衡依据

**参考答案**

权衡维度：**控制力、成熟度与生态、团队能力、可观测与运维、锁定风险、需求稳定性**。

- **LangGraph**：以图和状态机为核心，显式状态、条件边、循环、Checkpoint、Human-in-the-loop、流式，与 LangSmith 配套，控制粒度细，适合需要强可控的生产级复杂流程。代价是抽象有学习成本，版本迭代较快，需要关注兼容。
- **CrewAI**：以“角色 + 任务 + 团队”为抽象，上手快，适合快速原型和角色分工明确的流程；对流程细粒度控制、复杂状态与恢复的能力相对有限，高阶需求下可能受限。
- **AutoGen**：以多 Agent 对话协作为核心，适合研究与探索式的多 Agent 交互；对话驱动的流程不确定性较高，生产环境需要自己补充约束、观测、预算等控制。框架版本演进较大，选型时要确认当前版本和维护状态。
- **自研 Orchestrator**：完全掌控状态模型、调度、持久化、观测，贴合公司基础设施（鉴权、审计、多租户、成本控制）；代价是开发和长期维护成本高，需要重复造轮子。适合编排需求稳定且清晰、框架约束成为主要瓶颈、团队有足够工程能力的情况。

决策建议：

1. 需求不清晰或需要验证业务时，用成熟框架快速上线，把业务逻辑与框架层隔离（自己封装一层接口）。
2. 对可控性、恢复、审批有强需求，首选 LangGraph 类的状态机方案。
3. 当框架无法满足核心需求并且需求已稳定，再考虑自研核心部分，而不是一开始就全自研。
4. 评估社区活跃度、版本稳定性、可迁移性，避免被单一框架绑定。

### 15. 手撕算法：设计一个简单的Semantic Cache结构，用Python字典加向量相似度伪代码实现查询与写入，包含相似度阈值判断

**参考答案**

思路：把“问题向量 → 答案”存起来；查询时对新问题计算向量，在同一命名空间内找最相似的已缓存问题，相似度不低于阈值才命中，否则未命中（调用 LLM 后再写入缓存）。向量提前归一化，这样点积就等于余弦相似度。

复杂度：查询线性扫描 O(N·d)，N 为缓存条数，d 为向量维度；写入 O(d)。生产中应换成 ANN（HNSW）向量索引，或使用 Redis / 向量库。

```python
import math
import time
from typing import Callable, Dict, List, Optional


def normalize(vec: List[float]) -> List[float]:
    norm = math.sqrt(sum(x * x for x in vec))
    return [x / norm for x in vec] if norm else vec


def dot(a: List[float], b: List[float]) -> float:
    return sum(x * y for x, y in zip(a, b))


class SemanticCache:
    def __init__(self, embed: Callable[[str], List[float]],
                 threshold: float = 0.92, ttl: float = 3600,
                 max_size: int = 10000):
        self.embed = embed
        self.threshold = threshold      # 相似度阈值，需用评测集调参
        self.ttl = ttl
        self.max_size = max_size
        self.store: Dict[int, dict] = {}  # id -> {ns, vec, query, answer, ts}
        self._next_id = 0

    def get(self, query: str, namespace: str = "default") -> Optional[str]:
        q = normalize(self.embed(query))
        now = time.time()
        best_id, best_score = None, -1.0
        for cid, item in list(self.store.items()):
            if now - item["ts"] > self.ttl:      # 过期则惰性删除
                del self.store[cid]
                continue
            if item["ns"] != namespace:          # 租户 / 模型 / Prompt 版本隔离
                continue
            score = dot(q, item["vec"])
            if score > best_score:
                best_id, best_score = cid, score
        if best_id is not None and best_score >= self.threshold:
            return self.store[best_id]["answer"]
        return None

    def put(self, query: str, answer: str, namespace: str = "default") -> None:
        if len(self.store) >= self.max_size:     # 简单淘汰：最早写入的
            oldest = min(self.store, key=lambda k: self.store[k]["ts"])
            del self.store[oldest]
        self.store[self._next_id] = {
            "ns": namespace,
            "vec": normalize(self.embed(query)),
            "query": query,
            "answer": answer,
            "ts": time.time(),
        }
        self._next_id += 1


def answer_with_cache(cache: SemanticCache, query: str, llm: Callable[[str], str]) -> str:
    hit = cache.get(query)
    if hit is not None:
        return hit
    result = llm(query)
    cache.put(query, result)
    return result
```

容易说漏的点：

1. 阈值太低会返回“相似但答案不同”的错误缓存，太高则命中率低，需要用真实数据调参，宁可保守。
2. 缓存必须按租户、权限、模型和 Prompt 版本隔离，避免数据串用。
3. 与时间、个人数据、实时状态相关的问题不应缓存（或设很短的 TTL）。
4. 多轮对话需要先做指代消解，用改写后的完整问题做 key，否则“它多少钱”会误命中。

诚实、有反思，避免过度自夸或否定自己：

1. 选一个确实偏难的点，如多 Agent 的循环治理、Harness 工程体系、RAG 幻觉分层定位等，说明难在哪里（例如“落地经验与理论需要结合”）。
2. 复盘自己当时的回答：哪些讲清楚了，哪些还不够深入，面试后你是怎么补充学习的（查资料、动手验证）。
3. 体现成长性：这次面试帮助你发现了哪些薄弱点，以及你的改进计划。
4. 总体评价保持平衡，如“整体发挥比较稳定，个别细节还可以更深入”，并表达对结果的开放态度。

### 4. 期望的薪资范围与当前薪资结构，期权或股票方面有预期么

**答题思路**

不要编造数字，下面是组织回答的框架：

1. **先表达重点**：更看重岗位成长、业务与团队，薪资希望匹配市场水平与个人能力。
2. **当前薪资结构**：如实说明构成（固定、绩效、奖金、补贴等），不夸大、不隐瞒；也可以说明过往薪资涉及保密约定，主要讲构成和你的期望。
3. **期望范围**：事先查询该岗位、城市、级别的市场行情，给出**一个合理区间**并有弹性，说明依据（能力、经验、市场水平）。
4. **期权 / 股票**：如果有，表示愿意了解公司的方案（授予方式、归属期、行权条件）；如果没有强烈偏好，可以说“更关注整体包的构成，期待进一步沟通”。
5. 保持开放：愿意根据职级、整体薪酬结构沟通，而不是只盯着单个数字。

### 5. 如果让你来深圳长期做Agent Harness这块，职业上最看重的三点是什么

**答题思路**

给出三点并用理由和自己的经历支撑，要与你前面表达的动机一致，真诚一些：

1. **技术成长与挑战**：能否持续做有深度的工程问题（编排、评估、可观测、成本控制），并有机会参与核心架构设计与标准建设。
2. **业务价值与落地**：Agent 在真实场景中被使用、有数据反馈闭环，而不是停留在 Demo。
3. **团队与环境**：技术氛围、协作方式、能得到的资源与带教，以及长期发展路径（晋升与职责成长）。

补充：关于“来深圳长期工作”，如果涉及城市迁移，要诚实说明你对工作地的考虑（生活安排、家庭情况、到岗时间）并表达长期意愿。不要为了迎合而做出自己无法兑现的承诺。

### 6. 之前离职的主要原因，下一份工作最不能接受的点有哪些

**答题思路**

原则：**客观、积极、不贬低前公司**，原因与新岗位的选择逻辑一致。

1. **离职原因**：从个人发展角度讲，如业务阶段或方向变化、希望接触更有挑战的 Agent 工程化问题、希望在更大的平台上成长。避免抱怨领导、同事、薪资，也不要编造原因。
2. 说明你在离职前的责任与交接（体现职业素养）。
3. **不能接受的点**：保持克制，只讲 1 到 2 个原则性问题，如“没有清晰的目标与反馈机制”“长期缺乏技术成长空间”“不尊重工程质量”，不要列出一长串，也不要说得过于苛刻。
4. 把话题回到你对这个机会的期待，让两部分形成呼应。

### 7. 手里有其他Offer吗，决策时影石的权重目前在哪个位置

**答题思路**

诚实但留有余地，不透露具体细节，也不制造虚假的竞争：

1. **如实回答**：有就说“有在沟通 / 已有进展”，没有就说“目前处于面试阶段”。不要编造 Offer 来抬价。
2. **表达对本机会的重视**：说明为什么影石排在比较靠前的位置，如业务方向与你的 Agent / Harness 经验匹配、团队技术挑战、成长空间（要与前面的动机一致）。
3. **决策依据**：说明你主要看岗位内容、团队、成长与整体薪酬，而不是单一因素。
4. **时间安排**：如果有其他流程的时间节点，可以坦诚说明，请 HR 告知本流程的进度，方便双方安排。
5. 避免说“影石只是备选”，也避免承诺“一定来”，保持真诚、专业的态度。

### 8. 反问环节，对团队节奏、业务落地阶段与晋升机制有什么想了解的

**答题思路**

反问体现你的关注点与思考深度，提前准备 3 到 4 个问题，按重要性提问，避免问官网能查到的信息，也不要一开始就只问薪资福利：

1. **团队与节奏**：团队规模与分工、Agent 方向目前的研发与迭代节奏、跨部门协作方式。
2. **业务落地阶段**：Agent 与 Harness 相关项目目前处于哪个阶段（探索、试点、规模化），主要的落地场景和面临的挑战，如何衡量成功。
3. **技术建设**：评估、观测、成本控制等基础设施的现状，是否有统一的 Harness 标准组件。
4. **成长与晋升**：晋升机制与评估周期、对该岗位的期望，以及入职后前三到六个月的目标。
5. **流程**：后续流程与时间安排。

提问时用开放式问题，并结合刚才面试中听到的信息追问，显示你在认真倾听。
