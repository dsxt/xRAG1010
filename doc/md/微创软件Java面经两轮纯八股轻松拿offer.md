### 3. Java 中 synchronized 和 ReentrantLock 的区别

**参考答案**

两者都可重入，也都是互斥锁。`synchronized` 是监视器锁，进入同步方法或代码块就获取，正常退出和抛异常都会释放。实例方法锁的是 `this`，静态方法锁的是 `Class` 对象。`ReentrantLock` 基于 AQS，必须在 `finally` 里 `unlock`，漏了这把锁会一直被占着。

Lock 能做的更多：`tryLock`、带超时的尝试、`lockInterruptibly`、公平锁，以及同一把锁上的多个 `Condition`。`synchronized` 只有该对象上的一个等待集，阻塞在进锁时不能被中断。`lock()` 也要等到拿到锁才响应中断；可中断的是 `lockInterruptibly`。`new ReentrantLock()` 默认非公平，公平要传入 `true`。公平锁按队列获取，吞吐通常更差。无参 `tryLock()` 即使锁是公平的也会插队；公平锁上带超时的 `tryLock` 才遵守排队。

无竞争时 `synchronized` 用轻量级锁，竞争激烈再膨胀成重量级。偏向锁从 JDK 15 起默认关闭，JDK 18 移除，不要再按「偏向、轻量、重量」三步当现状讲。虚拟机还能对监视器做锁消除和锁粗化。简单临界区用 `synchronized`；需要超时、可中断或多条件队列时用 Lock。两边在没有竞争时速度接近。

### 4. JVM 内存区域划分，哪些是线程共享的

**参考答案**

这里问的是运行时数据区。JMM 讲的是可见性和有序性，被追问再单独说。

线程私有的是程序计数器、虚拟机栈、本地方法栈。程序计数器记下一条字节码地址，执行本地方法时为空，这块不会 OOM。虚拟机栈按方法存栈帧，里面是局部变量表、操作数栈、动态链接和返回地址；栈深了是 `StackOverflowError`，线程太多、栈扩不开是 OOM。规范里的本地方法栈也是线程私有；HotSpot 把 Java 栈和本地方法栈合成一个栈实现。

堆和方法区线程共享。堆放对象和数组，是垃圾回收的主战场，装不下会堆 OOM。每个线程可以有自己的 TLAB，那只是堆里预先划出的分配缓冲区，用来减少分配竞争，不是另一块区域。方法区在 HotSpot JDK 8 及以后由元空间实现，放类元数据和运行时常量池，占本地内存，动态类太多会 `Metaspace` OOM。字符串常量池从 JDK 7 起在堆里。直接内存不属于上述分区，NIO 堆外泄漏时机器一样会满。

### 5. 垃圾回收算法有哪些，G1 垃圾回收器的特点

**参考答案**

基础算法三种。标记-清除会留碎片。标记-复制把活对象拷到空区域，年轻代常用，代价是留出空闲空间。标记-整理把活对象挪到一端，整理时要停顿。分代收集是组合策略：大多数对象死得快，年轻代用复制，老年代少收、收得更完整。

G1 把堆切成等大的 Region，大小随堆而定，通常是 1MB 到 32MB 的 2 的幂。年轻代和老年代都是一组 Region，物理上不要求各占一整块。年轻代回收是停顿的，把活对象复制走，被收掉的 Region 得到整理。老年代先做并发标记，写屏障用 SATB 记住标记开始时还活着的引用；标记完成后的 Mixed GC 再挑垃圾比例高的 Region，连同年轻代一起复制回收。`-XX:MaxGCPauseMillis` 是期望停顿，用来挑选收集集合，不是硬上限。

超过 Region 一半的对象进 Humongous 区，独占一个或多个连续 Region，回收不及时会直接把堆顶满。跨 Region 的引用记在记忆集里，收集时不用扫整堆，记忆集本身占额外内存。JDK 9 起默认收集器是 G1。并发标记跟不上分配，或者疏散失败，会退化成整堆 Full GC，停顿明显变长。G1 的并发部分是标记，疏散仍然停顿。

### 6. Spring Bean 的生命周期

**参考答案**

单例 bean 从创建到销毁的主线如下。

先实例化，再填充属性、注入依赖。接着回调 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。随后进入 `BeanPostProcessor.postProcessBeforeInitialization`：其中 `ApplicationContextAwareProcessor` 回调 `ApplicationContextAware` 等环境相关接口，`CommonAnnotationBeanPostProcessor` 调用 `@PostConstruct`。然后才是 `InitializingBean.afterPropertiesSet` 和自定义 `init-method`。最后 `postProcessAfterInitialization` 里，AOP 通常把目标包成代理。代理生成前，初始化回调已经在目标对象上执行过。

容器关闭时销毁单例：`@PreDestroy`，再 `DisposableBean.destroy`，再自定义 `destroy-method`。原型 bean 容器不负责销毁。`BeanFactoryPostProcessor` 改的是 `BeanDefinition`，发生在实例化之前，不属于这一个 bean 的生命周期。

单例的设值注入遇到循环依赖，靠三级缓存提前暴露解决；构造器循环依赖解决不了。Spring Boot 2.6 起默认不允许循环依赖。懒加载单例不会在启动时创建。

### 7. Spring 事务的传播机制

**参考答案**

传播行为决定这段方法加入已有事务，还是另起一个。默认 `REQUIRED`：有就加入，没有就新建。

`REQUIRES_NEW` 把外层挂起，自己新开事务并独立提交。外层之后回滚，不会撤销内层已经提交的结果。内层的运行时异常如果冒泡到外层且没被抓住，外层也会回滚；抓住了，外层还可以提交。它会占用第二条数据库连接，池子太小可能把外层卡住。

`NESTED` 在已有事务里建 JDBC 保存点。内层失败只滚到保存点，外层还能继续；外层最终回滚会把保存点里的工作一并撤销。它不是另开一个物理事务。没有外层时行为同 `REQUIRED`。JTA 下通常没有保存点。

`SUPPORTS` 是有事务就加入，没有就非事务执行。`NOT_SUPPORTED` 先把已有事务挂起，自己非事务执行。`MANDATORY` 必须已经在事务里，`NEVER` 必须不在事务里，否则抛 `IllegalTransactionStateException`。

同一类里自己调自己不经过代理，传播不会生效。默认只拦截 public 方法。未捕获的 `RuntimeException` 和 `Error` 才回滚，受检异常要写 `rollbackFor`。内层同为 `REQUIRED` 时，异常即使被外层抓住，事务也可能已被标成只能回滚，外层提交会得到 `UnexpectedRollbackException`。

### 8. MySQL 索引底层数据结构，B+ 树的特点

**参考答案**

InnoDB 的索引是 B+ 树。主键索引是聚簇索引，叶子放整行，整张表按主键有序。二级索引的叶子放索引列和主键，要整行时再按主键回表。查询列都在这棵二级索引里就是覆盖索引，不必回表。回表查的是聚簇索引，不是一条文件偏移。

非叶子节点只存键和子页指针，一页能挂很多分支，树矮，磁盘 IO 少。数据都在叶子上，查找代价稳定。叶子之间用双向链表相连，范围扫描沿链表走。页默认 16KB。高度通常只有三四层。

复合索引按列从左到右有序，能用上的是左边连续的等值，再到紧接着的一列范围。哈希只适合等值，做不了范围和排序。InnoDB 不能把普通二级索引建成哈希；自适应哈希只是热点页上的内存加速。主键若完全随机，叶子会频繁分裂；趋势递增的主键更贴着 B+ 树的插入方式。

### 9. Redis 持久化方式 RDB 和 AOF 的区别

**参考答案**

RDB 是某一时刻的二进制快照。正常路径是 `BGSAVE`：fork 出子进程写文件，父进程继续服务，靠写时复制。文件小、恢复快，适合备份和主从第一次全量同步。两次快照之间宕机会丢掉这一段。内存大时 fork 可能把实例卡住，写时复制也会把内存顶高。

AOF 把写命令追加到日志。`appendfsync` 常见是每秒一次，崩溃时通常最多丢大约一秒；每次写都刷最稳，吞吐也最差。磁盘卡住时，每秒刷一次的主线程仍可能被拖住。文件变大后后台重写，压成能重建当前数据的最小命令集。重写同样要 fork。Redis 4.0 起重写文件可以先放 RDB 内容，后面再追加增量。两边同时打开时，重启优先用 AOF 恢复，因为它更完整。

RDB 适合冷备和快速拉起，AOF 适合把丢失窗口收小。两者保的是这台机器重启后还在的数据，替代不了主从切换时的高可用。

### 10. Kafka 如何保证消息不丢失

**参考答案**

不丢要生产、Broker、消费三段一起成立。

生产端把 `acks` 显式设为 `all`，当前 ISR 里的副本都写入才算成功。不同客户端版本的默认值不一样，不要靠默认。`send` 返回只说明进了缓冲区，失败要在回调里重试或把错误交给上游。打开幂等生产者，重试不会在同一分区留下重复；它要求 `acks=all`，并且同一连接的在途请求不超过 5。副本至少 3 个，`min.insync.replicas` 至少 2。后者默认是 1，这时只剩 leader 也会确认，leader 再宕就丢了已确认的消息。不要允许 ISR 之外的副本成为 leader，否则已确认的日志会被截短。

消费端处理成功再提交位移，不要用按时间自动提交，否则处理到一半崩溃，这段业务等于丢了。这是至少一次，会重放，所以消费按业务键幂等。Kafka 事务只能原子地提交 Kafka 自己的写和位移，写到数据库的副作用仍要幂等或发件箱。保留时间到了消息会被删，那是保留策略。

### 11. 什么是 CAP 定理，在分布式系统中的应用

**参考答案**

CAP 说的是：发生网络分区时，一个分布式系统不能同时保证线性一致和可用性。C 是读到最新写入，A 是未故障的节点在有限时间内给出响应，P 是节点之间的消息可以丢失或延迟。真实网络必须容忍分区，所以分区发生时只能在 C 和 A 之间取舍。没有分区时，两者可以同时满足。

偏 CP 的系统在凑不齐多数派时拒绝服务，以免读到分叉的数据。etcd 的线性读写、ZooKeeper 的写都是这样。ZooKeeper 的跟随者本地读仍可能稍旧，要线性一致需要先 `sync` 或读 leader。偏 AP 的系统分区期间继续应答，允许暂时读到旧数据，之后再收敛。Eureka 的注册表、Cassandra 使用 `ONE` 时属于这一侧。Cassandra 改成 `QUORUM` 时，凑不齐法定副本的那一侧会拒绝这次请求，所以 CAP 要落到具体操作上，不能给整个产品贴死一个标签。

单机数据库谈不上这个三选二。主从异步复制在切换时可能丢最近的提交，把它叫成 CA 不准确。没有分区时，要最新数据通常得多等一次跨节点确认，这是 PACELC 里延迟和一致性的取舍。

### 12. 微服务架构的优势和挑战

**参考答案**

优势是按服务独立发布和扩容，一个服务的故障可以限制在自己的进程里，团队也能按业务边界并行。各服务可以选择合适的存储和技术栈。这些好处要有清晰的职责边界才成立。

挑战主要在分布以后。调用会超时、重复、乱序，核心写操作要幂等。跨服务不要包一个大事务，用本地事务加可靠消息做最终一致，长流程再补补偿。每个服务拥有自己的数据，不要跨服务连库做联表。排障要有贯穿调用链的追踪标识，日志、指标和链路放在一起看。接口一旦被别人依赖，就得保留兼容或显式版本。

同步链路太长、所有服务共用一个库，只是把单体拆成了分布式单体，延迟和故障面都变大。超时、熔断、限流和有界线程池要配上，否则一个慢下游会把调用方的线程耗尽。团队和领域还没复杂到需要分开部署时，模块化单体更合适；等发布节奏或容量已经互相拖累，再按业务边界拆。

### 13. 了解 AI 在软件开发中的应用吗？举例说明

**参考答案**

AI 现在主要嵌在开发和业务两条线上，都要有人审、有退路。

开发侧，编辑器里的补全能补样板和重复修改，能改仓库的代理可以按失败的测试去改代码、起草单测和变更说明。评审时可以用模型先看 diff、堆栈和日志，给出可疑点；结论要回到代码和监控核对。内部文档和接口说明可以做检索增强，用来回答「这个字段谁在写」。检索不到就该承认没有证据，不能让模型编一个调用方。

业务侧，常见的是客服草稿、单据和合同抽取、搜索排序。模型放在独立的推理服务里，业务系统负责特征、超时和降级，训练和发版解开。流水线里可以用模型标出危险改动，合入仍走原来的构建和测试。

模型会编造 API 和规则，也可能把密钥带进提示。代理如果有提交和改配置的权限，必须有评审和 CI，不能凭一句「已完成」就进主干。

### 14. 如何保证代码质量

**参考答案**

质量靠提交前的自动检查、合入前看行为、发布后能发现并撤回。口头规范挡不住回归。

改动保持小，验收条件写清楚。构建里跑格式化、编译警告和静态检查，新增问题让构建失败，历史债分开治理。测试分层：核心分支用单测，事务、SQL 和消息用集成测试，对外接口用契约测试。覆盖率只是参考，金额、权限和并发必须有对应的失败用例。评审把时间放在事务边界、幂等、空值、失败路径和索引上，格式交给工具。

发布要能回滚，关键路径有日志和指标，线上问题能对上某次变更。依赖漏洞和密钥扫描放进流水线。回答这题时只展开仓库里真有的几项；没有的检查不要说成已经接入，可以说成下一步要补的。

### 15. 最近在学习什么新技术

**答题思路**

只讲一件最近真的在看的。这场会问到 AI：你确实在用编码助手或看过模型接口，就讲这个；没有就讲业务栈里的一项，例如一次故障之后补的 MySQL 或 Kafka。

1. 为什么现在学：它对应你哪段做不顺的工作。
2. 学到哪一步：读了哪份文档、跑了什么、哪一点还不确定。
3. 和你现在的做法差在哪，多出来的运维成本是什么。
4. 准备好被追问机制。讲不下去就承认边界。

不要报一串名词，也别把只看过标题的东西说成已经会用。

### 2. 项目介绍，遇到的最大挑战是什么

**答题思路**

项目按一次请求的路径讲，大约 3 分钟；挑战只讲一件你亲手处理过的事。后面会问隔离级别、锁和高并发，挑战优先落在你真做过的一致性或性能问题上。

项目部分：

1. 入口在哪，鉴权和限流放在网关还是服务里。
2. 服务怎么拆。哪些调用是同步的，哪些已经改成消息。
3. 数据：哪份库是准的，缓存放什么、失效后以谁为准，每个主题谁生产、谁消费。
4. 你的边界：哪些接口和表是你的。上下游只讲契约。
5. 留一个你真做过的权衡。没参与的部分不要讲成自己的设计。

挑战部分：

1. 先说约束：不能停写、不能丢，还是不能算错。
2. 证据：慢在 SQL、锁、远程调用、GC 还是消息堆积。讲你当时看到的现象。
3. 对比两个方案，说清放弃其中一个的原因。
4. 上线后现象有没有消失，有没有副作用。数字只用记得住的。
5. 补一句今天会怎么做。当时没有监控或没有灰度，就直接说。

### 3. 数据库事务的隔离级别，如何解决幻读

**参考答案**

SQL 标准四级，从低到高是读未提交、读已提交、可重复读、可串行化。读未提交会脏读。读已提交每次读到已提交的最新值，同一行两次读可能不同。标准里的可重复读仍可能幻读：同一个范围查询又看到别的事务新插入的行。可串行化避免这些异常，代价是冲突更多。

InnoDB 默认可重复读，实现比标准更进一步。普通 `SELECT` 是快照读，事务里第一次一致读建立起 Read View，之后别的事务新提交的行不会出现在这个快照里，所以经典幻读在快照读上看不到。`UPDATE`、`DELETE` 和 `SELECT ... FOR UPDATE` 是当前读，读最新已提交版本并加锁。可重复读下范围条件加的是临键锁，也就是记录锁加间隙锁，别的事务插不进这个范围。

当前读仍可能改到快照里本来看不见、但已经提交的行；这些行一旦被本事务改过，后面的快照读就能看见。要按范围先查再改，查的时候就用 `FOR UPDATE`，不要只用普通 `SELECT`。唯一索引还能从数据侧挡住重复插入。读已提交每次语句新建快照，搜索和扫描一般不加间隙锁，幻读和非重复读都在，间隙锁导致的死锁会少一些；外键和唯一键检查仍可能加间隙锁。可串行化在关闭自动提交时，把普通 `SELECT` 变成加共享锁的当前读，范围扫描会堵住间隙里的插入。

### 4. 什么是 MVCC，在 MySQL 中如何实现

**参考答案**

MVCC 让一致读不阻塞写，写也不阻塞一致读。每个事务看到的是一个快照，而不是加锁把整张表停住。

InnoDB 在聚簇索引行上维护 `DB_TRX_ID` 和 `DB_ROLL_PTR`。更新时把旧版本写进 undo，行上留下新版本和回滚指针。既没有主键、也没有非空唯一索引时，还会生成隐藏的 `DB_ROW_ID` 充当聚簇索引。一致读创建 Read View，记下创建时还没结束的事务，以及当时的事务号边界。行上的事务号属于快照前已提交的范围就可见；属于当时还活跃的事务，或者比快照更晚，就不可见，顺着 undo 找上一版再判断。本事务自己写的行可见。

可重复读在第一次一致读时建立 Read View 并一直复用。`START TRANSACTION WITH CONSISTENT SNAPSHOT` 会在开始时就建立。读已提交则每条一致读语句新建一个。存储结构相同，差别在快照何时创建。`SELECT ... FOR UPDATE` 和 `UPDATE` 走当前读，读最新版本并加锁，不靠旧快照挡住写。

二级索引记录上没有事务号。页上有 `PAGE_MAX_TRX_ID`，整页都比快照旧时，覆盖索引可以不回表；否则仍要回聚簇索引判断可见性。purge 线程删掉没有任何 Read View 需要的 undo。长事务会把 undo 留住，历史版本堆积，磁盘和查询都会变差。MVCC 不代替写锁，两笔写同一行仍然互斥。

### 5. Spring Cloud 和 Dubbo 的区别

**参考答案**

Dubbo 是以接口为契约的 RPC 和治理框架。Spring Cloud 是一组分布式系统模式，通信多半是 HTTP，注册、配置、网关、熔断由不同组件拼起来。两者不是同一层的互相替代。Java 服务之间调用量大、契约稳定，偏 Dubbo；对外或多语言的 HTTP 接口，偏 Spring Cloud 这条路。注册中心可以都用 Nacos，也可以一起用。

Dubbo 用代理暴露接口，超时、负载均衡、分组和版本可以落到方法上。传统是私有的二进制 TCP 协议；Dubbo 3 的 Triple 基于 HTTP/2，能兼容 gRPC。集群容错默认会重试，写接口如果不是幂等的要把重试关掉。应用级服务发现注册的是实例，减轻注册中心按接口展开的压力。

Spring Cloud 侧，入口常用 Gateway，服务间用 OpenFeign 或带负载均衡的 HTTP 客户端，配置有独立的配置中心。早期的 Eureka、Ribbon、Hystrix、Zuul 已经不是新项目的默认组合；现在常见的是 Spring Cloud LoadBalancer、Gateway，熔断用 Sentinel 或 Resilience4j，发现用 Nacos、Consul 或 Kubernetes。HTTP 更好抓包、更好跨语言，序列化和连接开销通常比二进制 RPC 大。不要把「Dubbo 等于 ZooKeeper、Spring Cloud 等于 Eureka」当成定义，那是旧组合。

### 6. Redis 集群模式有哪些，如何保证高可用

**参考答案**

常见是四层：单机、主从、哨兵、Cluster。单机没有高可用。RDB 和 AOF 只保证这台机器重启后数据还在。

主从是异步复制。从库可以分担读，读到的可能是旧的。主库挂了不会自己切换。

哨兵是一组独立进程监视主库。足够多的哨兵认定客观下线后，再选举出一个哨兵去把从库升为主库，并通知客户端。它解决的是一份数据的自动切换，不分片。哨兵至少 3 个、用奇数，不要和数据节点挤在同一台机器。判定下线的 quorum，和执行切换所需的多数票，是两个条件。切换过程中还没同步到从库的写会丢。

Cluster 把数据分成 16384 个槽，每个主库负责一段，各自可以带从库。客户端按键算槽，槽不在当前节点就按 `MOVED` 重定向；迁移过程中个别键会临时 `ASK`。主库故障时，它的从库向多数主节点拉票后接管这些槽。某一侧如果联系不上多数主节点，这一侧会停止服务，避免两个分区同时写入。Cluster 不用哨兵。多键操作要落在同一个槽里，用 hash tag。

高可用还要客户端能刷新拓扑并在切换时重试，从库跨机器部署。想缩小丢数据的窗口，就同时开持久化，并可以要求写至少到达若干从库，这会降低可用性。异步复制做不到切换时零丢失。

### 7. 消息队列如何保证消息顺序性

**参考答案**

先界定顺序：绝大多数业务要的是同一业务键有序，例如同一订单号，不是全系统一条总队列。全局有序只能单分区、单线程消费，吞吐会一起掉下来。

Kafka 只保证分区内的追加顺序。同一个键用默认分区器会进同一个分区。消费组里一个分区同时只分给一个消费者，在这个分区的处理线程上按拉取顺序做完再提交。把消息丢进线程池并发执行，分区顺序就没了。生产端如果关闭幂等、又允许重试和多个在途请求，失败重试会把同一分区写乱。幂等生产者在在途请求不超过 5 时能保住分区内顺序。位移不要提交到还没处理成功的消息之后，否则重试和后续消息会交错。

RabbitMQ 要顺序就得单队列、单消费者，预取设为 1。多个消费者竞争同一个队列就会乱。RocketMQ 把同一分流键送进同一队列，并用顺序监听器锁住这条队列来消费；并发监听器不保证顺序。

无论哪种队列，再投递都会发生，消费端仍要按业务键幂等。用户又提交了一次是另一次业务请求，队列的分区顺序挡不住。

### 8. 分布式锁的实现方式，Redis 和 ZooKeeper 哪种更好

**参考答案**

没有绝对更好的一个。锁的 QPS 高、临界区短、数据侧还有唯一约束或版本号兜底，用 Redis。互斥错一次代价很大、锁操作又不多，用 ZooKeeper 或 etcd 这种共识加租约的锁。数据库唯一键或 `SELECT ... FOR UPDATE` 也能做，频率高了会占住连接。

Redis 的做法是 `SET key 唯一值 NX PX 过期时间`。解锁必须是一段 Lua：值等于自己的标识才删除，避免删掉别人刚拿到的锁。过期时间要盖住临界区，或者由客户端在存活期间续期；进程停了就不再续，锁到期释放。Redisson 把续期和可重入封装好了。风险有两个：主从异步复制时，锁还没到从库主库就挂了，新主库会再发一把锁；持有者发生长时间停顿，锁过期后别人进来，停顿结束的旧持有者仍去写。Redlock 是多台独立主库的多数派投票，它不是 Redis Cluster 的锁，在进程暂停和时钟上的争议很大，关键正确性不要押在上面。

ZooKeeper 用临时顺序节点：序号最小的拿到锁，其余只监听前一个节点，避免惊群。会话断了，临时节点被删，下一顺位被叫醒。写要经过多数派，少数派分区不会再发出一把锁。顺序号可以直接当作 fencing token，交给存储去拒绝过期的持有者。延迟比 Redis 高，不适合特别高的加锁 QPS，也不要和注册中心抢同一套已经很忙的集群。Curator 的 `InterProcessMutex` 在这个配方上补了同一线程的可重入；原生配方本身不管线程重入。

Redis 的锁值如果只用来解锁，挡不住过期后的旧持有者。数据侧要用单调令牌或版本号拒绝旧写。两边都替代不了业务幂等。锁里不要包远程调用。

### 9. 如何设计一个高并发系统

**参考答案**

先分清读多还是写多、能不能接受旧数据、用户是在等结果还是可以稍后完成。然后把应用做成无状态，读走缓存，写路径缩短，非核心步骤异步，数据库守住正确性，入口能拒绝超出的流量。

应用不在本地放会话，多实例水平扩展，任何一台挂了由负载均衡摘掉。读多的数据用缓存：未命中再查库并回填，同一个键失效时只放一个请求回源，TTL 加抖动，不存在的键缓存短时间的空值。特别热的键再加一层本地缓存。更新数据库之后删除缓存，并接受一个旧值被回填的短窗口；关键数据以库为准，可以用 binlog 再删一次。金额和库存不要把缓存当唯一账本。

写仍进主库。先把索引和事务做短，用 `UPDATE ... WHERE` 的条件更新或唯一约束处理并发，看影响行数。单机锁只在一个进程里有效。单库写入到顶，再按一定会出现在主查询里的键分片。读可以走从库，调用方要接受复制延迟。

通知、统计、日志放进消息队列削峰，消费者按业务键幂等。用户正在等的结果不要整段改成异步。队列有界，堆积要有告警。

入口限流，超限快速失败。下游设置超时，慢依赖用单独的线程池隔开。重试要有上限和退避，只重试幂等请求。上线前按峰值压一遍，看 P99、连接池、慢 SQL、GC 和队列积压。缓存和异步换来的是吞吐，付出的是短暂的旧读或延迟；分库和拆服务等指标证明单点不够再做。

### 10. 了解 AI 编程助手吗？它们如何影响开发效率

**参考答案**

编程助手是接在编辑器或命令行上的模型，能补全、按说明改多文件、解释报错、起草测试。它们缩短的是写出第一版和读懂陌生代码的时间。正确性仍然靠编译、测试和评审。

边界清楚的重复工作收益最大：样板代码、同一模式的批量修改、单测草稿、不熟悉的 API 写法、把一段报错翻译成可能的原因。人先定接口和失败时的行为，让助手填实现，再用测试把结果钉住，来回会少很多。

并发、事务、权限和金额这类不变量，助手容易写出能编译但规则是错的代码。一次接受很大的 diff，又没有测试，后面返工会比自己写更慢。密钥、生产数据和未公开的凭证不要进提示。它的改动按初级同事的补丁来看：事务边界、幂等、资源释放和越权。

效率取决于任务是否说得清，以及审的人能不能看懂。没有基线就不要报一个提升百分比。助手可以解释代码、列举边界，不能替代你对线上行为的判断。

### 11. 如何做技术选型，考虑哪些因素

**参考答案**

先写清约束，再在两个能解决这个问题的候选里，选团队运维得了的那个，并用自己的负载验证一次。

看问题和数据是否匹配：读写比例、一致性、数据量、延迟、查询是否总带着某个键。现有的数据库或队列能解决，就不要为了简历再引入一个组件。接着看失败时的行为：是丢数据、继续读到旧值，还是拒绝写入。这个行为比宣传的峰值吞吐重要。

再看落地：团队能不能值班，Java 客户端和监控齐不齐，备份、升级和迁移有没有路径，许可和机器成本多少，以后换掉要动多少代码。用接近生产的数据量做一次小范围验证，记下因此放弃了什么。纸面上的 QPS 不能直接当成你的系统能达到的数字。

过程留在文档里：约束、比较过的方案、结论、什么条件下重开。选型是为当前约束负责，不是为最新的组件负责。

### 12. 团队协作中如何解决技术分歧

**答题思路**

把分歧收成一个能验证的选择。用你真参加过的一次讨论套这个顺序，不要编一场没开过的评审。

1. 先对齐约束：延迟、一致性、工期、谁来运维。双方往往不是在答同一道题。
2. 方案收成可比较的几项：失败时会怎样、要改多少、能不能回滚。资历和感觉不作为依据。
3. 差在事实上，就用最小原型或一次压测取数，并限时结束。
4. 由负责上线的人拍板。记下选了哪条、没选哪条、为什么。
5. 定了就按这个做。约定哪条假设被线上打脸，就重新打开。

风格问题如果格式化工具已经统一，就停在工具上，不要反复争。

### 13. 如何保持技术敏锐度，平时如何学习

**答题思路**

讲一个你真的维持得住的节奏。这场前半段都是原理题，敏锐度要落到「我能把一个机制讲清楚」，不是名词列表。

1. 工作里刚踩过的坑是第一来源。故障之后把机制补到能讲给别人听，写下一页自己的笔记。
2. 同时只深挖一条和岗位相关的线，例如 MySQL、并发或模型应用，再加一条相邻的。
3. 材料以官方文档和发行说明为先，然后做一个最小实验。博客用来找线索。
4. 固定一小段时间，而不是收藏一堆不看。你负责的组件出了新版本，看默认行为和兼容性。
5. 面试时只展开一件正在学的，以及你纠正过的一个错误理解。没写过的不要说成已经会。

### 14. 职业规划是什么

**答题思路**

用 1 分钟讲近处和远处，接上这场面试里听到的工作，不要报职级和薪资。

1. 近一两年：把一块业务从设计做到线上问题自己能收口，包括数据对不对、故障能不能定位。
2. 再往后：沿团队真实在用的方向做深，例如高并发、数据，或把模型用进现有业务，并能为一小块功能的技术方案负责。
3. 为什么是这边：用面试中已经听到的业务，说你哪段经验对得上。不要背一套通用的平台愿景。
4. 如果被问到带人，就说先把交付做稳，再承担评审和分工。

不要把「很快转管理」或「马上去做另一套完全不同的技术」说成已经定好的计划。

### 15. 有什么问题想问

**答题思路**

准备两个会影响到你判断这次机会的问题。技术面先问工作和责任，薪资等对方开了再谈。

可以问的方向：

1. 这个位置前几个月负责哪段链路，和谁交接。
2. 线上出了问题怎么值班，团队最近真正痛的是性能、正确性还是交付。
3. 方案怎么评审，发布出了问题怎么撤回。
4. 这个名额是新业务还是补人。

对方已经介绍过的技术栈不要再问一遍。不要用反问去挑衅对方的架构。没有问题时，至少问清试用期前会交给你的第一件具体事情。
