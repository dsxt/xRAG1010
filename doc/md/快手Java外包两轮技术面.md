### 3. HashMap 的底层实现原理是什么？在 JDK 1.8 中有什么变化？

**参考答案**

JDK 8 的 HashMap 是数组加链表，单个桶过长时再转成红黑树。平均查找仍是常数时间，过长的桶从线性降到对数。

下标用 `(n - 1) & hash` 计算。`hash` 把 `hashCode` 的高 16 位和低 16 位异或，避免高位在取下标时被丢掉。默认容量 16，负载因子 0.75，元素数超过容量乘以负载因子就扩成 2 倍。

相对 JDK 7 有三处变化。链表上已经有 8 个结点、再插入时，若数组长度不小于 64，该桶转为红黑树，否则只扩容。新结点改为尾插；JDK 7 头插，并发扩容时可能把链表拧成环。哈希扰动从多次移位异或收成一次高低位异或。

HashMap 不保证线程安全，并发写用 ConcurrentHashMap。

### 4. 请描述 HashMap 的 put 操作流程，包括何时触发扩容，以及 1.7 和 1.8 版本在扩容时有何区别？

**参考答案**

JDK 8 的 `put` 先算 hash。表还没建就先扩到初始容量。`key` 为 null 时 hash 为 0，放进 0 号桶。桶为空就直接放入；是红黑树就按树插入；是链表就沿链比较，`==` 或 `equals` 相等则只覆盖 value。只有新增结点才让 `size` 加一，超过阈值才扩容，覆盖旧值不会扩容。链表新增发生在尾部。

JDK 7 在 `addEntry` 里先看要不要扩容，再把头插进桶。桶为空时，即使已经达到阈值也可能先不扩。JDK 8 是先把结点放进去，`++size > threshold` 再扩。

扩容都是容量翻倍。JDK 7 按新容量重新算下标，并用头插，多线程下可能成环。JDK 8 按 `hash & oldCap` 把一条链拆成低位链和高位链：该位为 0 留在原下标，为 1 移到原下标加旧容量，相对顺序保留。拆开后的树如果结点不多，会退回链表。

树化还有前提：数组长度小于 64 时只扩容。只记「超过 8 就变树」不完整。

### 5. HashMap 为什么将链表转为红黑树的阈值是 8，而将红黑树退化为链表的阈值是 6？

**参考答案**

8 来自泊松分布，不是拍脑袋。理想哈希、负载因子 0.75 时，JDK 注释给出的桶长分布里，长度达到 8 的概率大约是一亿分之六，再长则小于千万分之一。树结点大约是普通结点的两倍，这么低的概率才值得付出空间和旋转。真出现超长链表，多半是哈希很差，树化把最坏查找压到 O(log n)，也能减轻故意构造的哈希碰撞。

源码常量 `TREEIFY_THRESHOLD` 是 8：桶里已经有 8 个结点、再插入时调用 `treeifyBin`。数组长度小于 64 则这次只扩容，因为桶少时更像是容量不够。

退化阈值是 6。若 8 变树、7 又变回链表，临界点一插一删就会来回转换。降到 6 留出缓冲。扩容把树拆开后，某一侧结点不超过 6，就退回普通链表。

### 6. HashMap 的容量为什么总是 2 的幂次方？如何实现的？

**参考答案**

容量保持 2 的幂，是为了用位与代替取模。`n` 为 2 的幂时，`hash % n` 等价于 `hash & (n - 1)`，而 `n - 1` 的低位全是 1，哈希的低位都能参与下标。若 `n` 不是 2 的幂，`n - 1` 某些位是 0，对应的哈希位永远不影响下标，冲突会变多。

传入的 `initialCapacity` 会经 `tableSizeFor` 向上取整。先减 1，再把最高位以下的位全部填成 1，最后加 1。先减 1 是为了容量本身已是 2 的幂时不再放大。扩容只左移一位，结果仍是 2 的幂。容量上限是 `1 << 30`，到顶后不再翻倍。

```java
static int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;
    return (n < 0) ? 1 : (n >= (1 << 30) ? (1 << 30) : n + 1);
}
```

### 7. Object 类中有哪些方法？分别有什么作用？

**参考答案**

Object 是所有类的根。和面试相关的方法分三组。

比较和展示：`equals` 默认比较是不是同一个引用；`hashCode` 默认按对象身份计算；`toString` 默认是「类名@身份哈希」。按字段判断相等时，前两个要成对重写。`getClass` 返回运行时的类，是 final，不能重写。

复制：`clone` 是受保护的浅拷贝入口。类实现 `Cloneable` 才能调，否则抛 `CloneNotSupportedException`。业务代码更常用拷贝构造。

线程协作：`wait`（三个重载）、`notify`、`notifyAll`。每个对象都能当锁，所以它们定义在 Object 上。调用时当前线程必须持有该对象的监视器，配合 `synchronized` 做等待和唤醒。

`finalize` 曾约定在回收前执行，已经废弃。释放资源用 `close` 或 try-with-resources。

### 8. equals() 和 hashCode() 方法的关系是什么？为什么重写 equals() 通常也要重写 hashCode()？

**参考答案**

约定是：`equals` 相等的两个对象，`hashCode` 必须相等；`hashCode` 相等，只说明可能进同一个桶，不要求 `equals` 也相等。

HashMap 和 HashSet 先用 `hashCode` 定位桶，再用 `equals` 在桶里比对。只重写 `equals` 时，两个内容相同的对象仍可能算出不同的身份哈希，被放进不同桶。`contains`、`get` 会找不到已经放入的对象。

默认实现都按引用。一旦 `equals` 改成比字段，`hashCode` 就要用同一组字段计算。参与比较的字段和参与哈希的字段必须一致。

### 9. HashSet 的底层实现原理是什么？它是如何保证元素唯一性的？

**参考答案**

HashSet 内部是一个 HashMap。元素放在 key 上，value 是同一个静态占位对象。`add` 实际是 `map.put(e, PRESENT)`，返回 null 才表示之前没有这个 key、插入成功。

唯一性就是 HashMap 对 key 的规则：`hashCode` 决定桶，`equals` 判断是不是已存在。已存在则 `add` 返回 false。因此元素类要正确实现这两个方法。放进去之后再改参与哈希或比较的字段，元素还在集合里也会查不到。

HashSet 允许一个 null，因为 HashMap 允许一个 null key。它不保证顺序，也不是线程安全的。

### 10. 如果一个类重写了 equals()，但只使用了部分字段参与比较，而 hashCode() 使用了所有字段计算，会有什么问题？举例说明。

**参考答案**

这会打破「equals 相等则 hashCode 必须相等」。

用户对象的 `equals` 只比 `id`，`hashCode` 却用 `id` 和 `name`。`User(1, "a")` 和 `User(1, "b")` 被 `equals` 判为相等，哈希却不同。把前者放进 HashSet，再用后者去 `contains`，会进另一个桶，结果是相等的对象在集合里找不到。当作 HashMap 的 key 时，`get` 同样失败。

两边必须使用同一组字段。放入集合之后，这些字段也不能再改。

### 11. 请解释 Java 内存模型（JMM），核心是解决什么问题？

**参考答案**

JMM 规定多线程下共享变量的读写何时对其他线程可见、指令可以怎样重排。它解决的是：一个线程的写入，另一个线程在什么条件下一定能看到。

编译器和 CPU 会缓存、重排序。没有同步时，线程 A 的写入可能还留在寄存器或写缓冲里，线程 B 读到旧值，观察到的顺序也会和源码不一致。

JMM 用 happens-before 给出保证：同一线程里前面的操作先于后面；对同一把锁，解锁先于随后的加锁；volatile 写先于后面的读；`start` 先于新线程里的动作，线程结束先于 `join` 返回之后的读。落在这些关系上的修改一定可见。`synchronized`、`volatile`，以及构造结束后的 `final` 字段，都是在建立这种关系。

堆、方法区、虚拟机栈是运行时数据区，和 JMM 是两套概念。

### 12. Redis 有哪几种持久化方式？分别描述其原理和优缺点。

**参考答案**

Redis 有 RDB 和 AOF，可以同时开。重启时若开了 AOF，优先用 AOF 恢复，因为它通常比最近一次快照更新。

RDB 把某一时刻的全量数据写成紧凑快照。线上用 `BGSAVE`：fork 子进程写文件，父进程继续处理命令。文件小、恢复快，也适合做备份和主从全量同步。两次快照之间的写入会丢。写得多时，写时复制会让内存短时间升高。常见触发条件是一段时间内写入达到次数，例如 60 秒 10000 次、300 秒 100 次、3600 秒 1 次。

AOF 把写命令追加到日志。`appendfsync` 为 `always` 时每条命令都刷盘，最稳也最慢；`everysec` 大约每秒刷一次，是常见默认，宕机大约丢一秒；`no` 交给操作系统，丢得可能更多。文件会变大，靠重写压成重建当前数据的最短命令。恢复比 RDB 慢，丢失窗口更小。

Redis 4.0 起可以混合持久化：重写文件用 RDB 做头，后面接增量 AOF，兼顾体积和恢复速度。

### 13. 简述 Redis 哨兵（Sentinel）和集群（Cluster）模式的主要区别。

**参考答案**

哨兵解决的是一份数据的自动故障转移，数据仍然只在一台主节点上。若干哨兵监视主从，主节点客观下线后，由哨兵选出一台从节点升级，并通知客户端改连新主。它提供高可用，不做分片，容量和写吞吐还是单机。实践上用奇数个、至少三个哨兵，避免哨兵自己成为单点。

Cluster 把数据分成 16384 个槽。键用 CRC16 对 16384 取模决定槽，每个主节点负责一段槽，从节点复制对应的主。容量和写可以横向扩展，主节点故障时由它的从节点接过这些槽，不依赖哨兵。16384 个比特是 2KB，可以放进节点间心跳。相关的键要用 hash tag 固定到同一槽，否则跨槽的多键操作会失败。

要单机容量内的主从切换用哨兵；要分片用 Cluster。

### 14. 什么是稳定的排序算法？哪些是稳定的？哪些是不稳定的？

**参考答案**

稳定排序指相等元素排序后仍保持原来的相对顺序。两条记录排序键相同，排序前 A 在 B 前面，稳定排序后 A 仍然在 B 前面。多关键字排序会依赖这一点：先排次关键字，再用稳定算法排主关键字。

常见稳定算法：冒泡、插入、归并。JDK 对对象排序用的 TimSort 也稳定。

常见不稳定算法：选择、希尔、快速排序、堆排序。划分或交换时，相等元素的原顺序会被打乱。

`Arrays.sort` 对对象走 TimSort，稳定；对基本类型走双轴快排这一类，不稳定。需要稳定时排对象，或自己写归并。

### 15. 简述快速排序的思想。

**参考答案**

快速排序是分治。在区间里选一个基准，把小于基准的放到左边、大于基准的放到右边，基准落到最终位置，再递归排左右两边。两边都有序后，整个区间就有序。

平均时间 O(n log n)，递归栈平均 O(log n)。每次都分成很偏的两边时，会退化成 O(n²)，栈也可能到 O(n)。随机选基准，或取首、中、尾的中值，用来降低这种概率。

它不稳定：相等元素在交换中可能互换相对顺序。它原地划分，不需要和数组一样大的辅助空间。

### 16. 手写算法：实现一个函数，判断给定的链表是否为回文链表（空间复杂度要求 O(1)）。

**参考答案**

用快慢指针找到中点，把后半段原地反转，再和前半段逐个比较。比较完把后半段反转回来，避免改掉入参。时间 O(n)，额外空间 O(1)。用栈保存前半段要 O(n) 空间，不符合要求。递归反转也会占 O(n) 栈，所以反转用迭代。下面的 `ListNode` 含 `int val` 和 `ListNode next`。

偶数长度时，慢指针停在后半段起点；奇数长度时停在中点。从这里反转再比较即可，中点会和自己比一次。

```java
public boolean isPalindrome(ListNode head) {
    if (head == null || head.next == null) {
        return true;
    }
    ListNode slow = head;
    ListNode fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    ListNode second = reverse(slow);
    boolean ok = true;
    for (ListNode p = head, q = second; q != null; p = p.next, q = q.next) {
        if (p.val != q.val) {
            ok = false;
            break;
        }
    }
    reverse(second);
    return ok;
}

private ListNode reverse(ListNode head) {
    ListNode prev = null;
    while (head != null) {
        ListNode next = head.next;
        head.next = prev;
        prev = head;
        head = next;
    }
    return prev;
}
```

### 3. 在项目中，你是如何设计和处理分布式缓存与数据库的数据一致性问题的？

**参考答案**

对着自己项目的读路径和写路径讲。缓存和数据库做不到每次同时成功，常见目标是最终一致，并说清业务能接受多久的旧数据。

写路径用 Cache Aside：数据库事务提交成功后再删缓存。删缓存而不是更新缓存，是因为两个写并发时，后写入缓存的可能是旧值。删缓存失败要能补，用本地消息或重试再删，再加一个不长的 TTL 兜住漏删。要求更稳时，订阅 binlog，由独立消费者按主键删缓存。

仍有一个窄窗口：读请求发现未命中，还没回填时，另一次写已经提交并删了缓存，这个读随后把旧值写回缓存。窗口小，TTL 和 binlog 再删一次都能收口。有人在更新前后各删一次并故意睡眠，睡眠时间不好定。

读路径是未命中再查库并回填。热点 key 用单飞或逻辑过期，避免同时失效把数据库打满。资金、库存这类不能接受旧值的读，直接读数据库。

### 4. 数据库事务的 ACID 属性分别指什么？重点解释一下“隔离性”和“一致性”。

**参考答案**

原子性：事务中的修改全部提交，或全部撤销。InnoDB 用 undo log 回滚已做的修改。

持久性：提交成功的修改在宕机后还在。InnoDB 先把 redo log 落到磁盘，恢复时重放。

一致性：事务把数据库从一个满足约束的状态带到另一个。主键、唯一键、外键、余额不为负，以及业务上的不变式，提交之后仍然成立。它是目标。写对事务边界、加上数据库约束，再靠原子性、隔离性和持久性把它守住。这里说的是单库约束，不是副本之间的数据同步。

隔离性：并发事务互相能看见多少。完全不隔离时会读到别人未提交的修改，同一行或同一范围两次读结果也会变。隔离级别越高，越接近串行执行，越容易守住一致性，并发也越差。实现上靠锁和 MVCC，不是把一致性再解释一遍。

### 5. MySQL 的四个隔离级别分别是什么？分别解决了哪些并发问题？

**参考答案**

先对齐三种现象。脏读是读到其他事务未提交的修改。不可重复读是同一事务里两次读同一行，中间别人提交了更新，值不同。幻读是同一范围两次读，已提交的插入或删除让行数变了。

读未提交：三种都可能发生。

读已提交：只读已提交的数据，解决脏读。同一事务里两次读仍可能看到别人刚提交的更新，所以还有不可重复读和幻读。

可重复读：同一事务的多次快照读看到同一版本，解决脏读和不可重复读。SQL 标准到串行化才要求解决幻读；MySQL InnoDB 默认就是这一级，并用 MVCC 加间隙锁把大多数幻读也挡住。

串行化：读写都加锁，三种现象都避免，冲突最多，吞吐最低。

### 6. “可重复读”隔离级别是如何通过 MVCC 和间隙锁来解决幻读问题的？

**参考答案**

InnoDB 的可重复读要分两种读，机制不同。

普通 `select` 是快照读。该事务第一次快照读时建立 Read View，之后都沿 undo 找这个视图可见的版本：自己的修改可见，视图建立之后才提交的修改不可见。后来插入并提交的行不会出现在这次事务的普通查询里，所以快照读看不到幻读。

`select ... for update`、`update`、`delete` 是当前读，读最新已提交版本，只靠 MVCC 挡不住别人往范围里插入。当前读会给扫描经过的记录加 next-key lock，也就是这条记录上的锁，加上它前面的间隙；范围条件还会锁到第一条不满足条件的记录，于是这段间隙不能插入。唯一索引等值命中已有行时，可以只留记录锁。

因此快照读靠 MVCC，当前读靠间隙锁。读已提交会为每条语句新建 Read View，范围加锁读通常也不再加间隙锁，所以那一级仍有幻读。

### 7. 线程池（ThreadPoolExecutor）有哪些核心参数？请解释每个参数的含义。

**参考答案**

完整构造方法有 7 个参数。

`corePoolSize` 是保留的核心线程数。工作线程数还没到它时，新任务会直接再建线程，哪怕已有线程正空闲。`maximumPoolSize` 是线程数上限，只在队列放不下时才继续往这个数建。`keepAliveTime` 和 `unit` 是多余空闲线程的回收时间，默认只回收超过核心数的线程；核心线程超时回收要另外打开。

`workQueue` 是等待队列。核心线程数已满时，新任务先放这里。有界队列才会把线程撑到最大线程数；无界队列放得下所有任务，`maximumPoolSize` 不会生效。`SynchronousQueue` 不存元素，提交时没有线程来取就算失败。

`threadFactory` 负责建线程，用来设名字和未捕获异常，方便对 jstack。`handler` 是拒绝策略，线程数和队列都到顶时调用。

### 8. 当向一个核心线程数已满、工作队列也已满的线程池提交新任务时，具体的执行流程是怎样的？拒绝策略有哪些？

**参考答案**

`execute` 的顺序是固定的，题目这个状态落在后两步。

1. 工作线程数小于核心线程数：新建线程执行这个任务，即使已有线程空闲。
2. 否则尝试入队。
3. 队列已满、入队失败：工作线程数还小于最大线程数，就再新建非核心线程执行。
4. 已经达到最大线程数，走拒绝策略。

这里的「已满」比的是线程个数，不是每个线程都正忙。无界队列不会走到第 3 步，`Executors.newFixedThreadPool` 就是这种队列。

JDK 自带四种策略。`AbortPolicy` 是默认策略，抛 `RejectedExecutionException`。`CallerRunsPolicy` 让提交任务的线程自己跑，提交速度被拖慢，形成反压；线程池已经关闭时，这个任务会丢掉。`DiscardPolicy` 静默丢掉新任务。`DiscardOldestPolicy` 丢掉队列里最老的一个，再尝试放入新任务。也可以自己实现 `RejectedExecutionHandler`，把丢掉的任务记日志或送进兜底队列。有界队列必须先定好拒绝之后的业务语义。

### 9. Java NIO 与传统的 BIO 主要区别是什么？NIO 的核心组件有哪些？

**参考答案**

BIO 按流读写。数据没到，调用线程就停在读或写上。连接一多，通常是一个连接占一个线程，线程和切换会先成为瓶颈。

NIO 面向通道和缓冲区，用 Selector 在少量线程里同时盯很多连接。通道把读、写、接受、连接这些兴趣注册给 Selector，线程只处理已经就绪的通道，不必为每个连接空等。就绪之后仍由线程自己把数据读进 Buffer，所以它是同步非阻塞。AIO 才是内核完成后回调。

核心组件是 Channel、Buffer、Selector。`ServerSocketChannel` 接受连接，`SocketChannel` 传输数据，Selector 做多路复用。Buffer 用 position、limit、capacity 描述区间：写入之后 flip 再读，读完 clear 或 compact。

连接少、单次处理又重时，BIO 更直接。大量连接且多数时间空闲，多路复用才划算。

### 10. Spring AOP 是如何实现的？有哪些实现方式（比如 JDK 动态代理和 CGLIB）？它们的区别和原理是什么？

**参考答案**

Spring AOP 在运行时给 Bean 生成代理，调用时走拦截器链，把通知插到方法前后。容器创建 Bean 之后，由自动代理创建器包这一层。默认是代理，不是 AspectJ 那种编译期改字节码；要用编译期或加载期织入，得另外配置。

有接口时可以用 JDK 动态代理：`Proxy.newProxyInstance` 生成接口的实现类，调用进到 `InvocationHandler`，先走切面，再反射调用目标。CGLIB 生成目标类的子类并重写方法，在子类里进入拦截器，再调父类方法。类或方法是 final、方法是 private 时，子类覆盖不了，切面不会生效。

Spring Boot 2 起默认按类代理（`proxy-target-class=true`），即使有接口也常用 CGLIB。两种代理都只包住从外部进来、能被重写的方法。同一个类里方法 A 直接调方法 B，不经过代理，B 上的事务或日志不会执行。

### 11. 在项目中，你是如何使用 Spring AOP 来解决实际问题的？比如日志、事务、权限控制等，请举例说明。

**参考答案**

优先讲自己真正加过的那一个切面，另外两个把机制说清即可。切面只放横切逻辑。

日志适合环绕通知。进入时记 traceId 和方法，抛异常时记栈，返回时记耗时。参数里的手机号、令牌要脱敏，序列化也要有长度限制，避免每个请求都在切面里变慢。

事务就是 `@Transactional` 这条代理。调用前开启事务，正常返回则提交，默认只在运行时异常和 Error 时回滚。事务要加在会进入代理的 public 边界上。同类自调用、private 方法，以及把异常 catch 掉再正常返回，都会让回滚没有发生。

权限可以用自定义注解加前置通知：进方法前取出当前用户和注解要求的权限，不满足就抛业务异常。校验放在业务修改之前。

### 12. Linux 中，如何实时查看一个 Java 进程的 CPU 和内存使用情况？

**参考答案**

先用 `jps -l` 或 `ps -ef | grep java` 找到 PID。

进程级用 `top -p <pid>`，它会周期性刷新。`%CPU` 按单核计算，多核上可以超过 100。内存看 RES，这是实际物理内存，包含堆、元空间、线程栈、直接内存和代码缓存，不能把它当成堆里已用的大小。要一次快照可以用 `ps -p <pid> -o pid,pcpu,rss,vsz,cmd`。

堆用 `jstat -gcutil <pid> 1000`，每秒看各区占用和 GC 次数、耗时。

CPU 高要落到线程：`top -H -p <pid>` 找到忙的线程号，`printf '%x\n' <tid>` 转成十六进制，再在 `jstack <pid>` 里搜这个 nid。只看进程总计，分不清是业务线程还是 GC。

### 13. 如果线上服务器的 CPU 使用率（load average）持续很高，你的排查思路和步骤是什么？会用到哪些命令？

**参考答案**

load average 和 CPU 使用率是两个数。负载是一段时间内可运行加上不可中断睡眠的任务平均数，要和核数比；`%CPU` 才是核被占用的比例。负载高而 CPU 空闲，经常是在等磁盘。先分开，再按状态查。

1. `uptime` 看 1、5、15 分钟负载是否在爬升，`nproc` 看核数。`top` 看 us、sy、id、wa。
2. us 高：`top` 找进程。是 Java 就 `top -H -p <pid>` 找线程，nid 转十六进制后对 `jstack <pid>`。连续打两三份，看线程是停住还是在跑。同时 `jstat -gcutil <pid> 1000` 看是不是 GC 在吃 CPU。常见是死循环、正则回溯、频繁 Full GC、大量序列化。
3. wa 高，或很多 D 状态：`iostat -x 1`、`pidstat -d 1` 看谁在写盘，例如日志、dump、磁盘打满。
4. sy 高：`vmstat 1` 看上下文切换和中断。切换很多时，线程栈里常能看到大量 BLOCKED，或连接数过多。

先留下 jstack 和这段监控，再决定要不要重启。

### 14. 在微服务架构中，服务间调用的超时、重试、熔断和降级是如何设计和实现的？

**参考答案**

这四层是为了下游变慢或不可用时，调用方还能在确定的时间内返回，并且不把故障放大。

超时放在每一次调用上。连接超时和读取超时分开。读取超时按下游正常耗时留出余量，远程调用都要有上限。没有超时，后面的重试和熔断都不知道何时算失败。

重试只给幂等的读，或带幂等键的写。次数少，间隔用指数退避加随机抖动，避免所有调用方在同一秒重试。下单、支付这种会重复生效的写，失败就返回不确定，由对账或查询收口。

熔断统计一段窗口里的失败和超时。比例超过阈值就打开，短时间内直接失败，不再访问下游；隔一小段时间放少量探测，成功再关上。它同时保护下游和调用方自己的线程。

降级是打开、超时或失败之后返回什么。读可以退回缓存、默认值或少一块内容；写要明确是快速失败，还是记下一笔以后补偿。隔离再用单独的线程池或信号量，一个慢依赖占不满整个进程的线程。

超时一般设在 HTTP 或 RPC 客户端上。熔断和降级可以用 Sentinel 或 Resilience4j，重试用 Resilience4j 或 Spring Retry。面试讲清每次调用都有超时、重试有次数预算、熔断打开后走降级，以及降级后的业务语义。

### 15. 手写算法：给定一个整数数组 nums 和一个目标值 target，请你在该数组中找出和为目标值的那两个整数，并返回它们的数组下标（力扣 1. 两数之和）。

**参考答案**

用哈希表记已经看过的值和下标，扫一遍。对当前数 `x` 先查 `target - x` 在不在表里，在就返回那两个下标；不在再把 `x` 放进去。先查再放，同一个下标不会被用两次。时间 O(n)，空间 O(n)。

两层循环也能做，时间 O(n²)、额外空间 O(1)。先排序再双指针是 O(n log n)，还得另外保存原下标。这题要的是下标，哈希更合适。力扣这题保证恰好有一组答案。

```java
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> index = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = index.get(target - nums[i]);
        if (j != null) {
            return new int[]{j, i};
        }
        index.put(nums[i], i);
    }
    return new int[0];
}
```
