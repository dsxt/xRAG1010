# 快手直播 AI Agent三轮技术面考你敢不敢让大模型动生产

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

前面两轮挺狠，不是背八股就能混过去的。一面就把直播场景、意图识别、RAG、Redis、线程池全搅在一起问，明显想看你能不能把 Java 工程和 Agent 真正落地。二面更深，工具风险、循环调用、多 Agent 状态隔离、Rerank 融合一路追问，答浅了就会被当成「只会调 SDK」。三面直接上图数据库、Harness、Codex 实战和事故定位，没真踩过坑基本聊虚。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1～2 分钟，按「身份 → 技术栈 → 与岗位最相关的项目 → 为什么匹配」组织：

1. 一句话说明年限和方向：Java 后端，近期转向或同时做 LLM / Agent 应用落地。
2. 技术栈按岗位相关度排序：Java / Spring Boot、并发与中间件（Redis、MySQL、MQ）、RAG 与 Agent 编排。
3. 挑一个最贴近「高并发业务 + Agent」的项目，说明业务背景、你负责的模块、可量化的结果（只说你真实有的数据）。
4. 收尾点题：具备把 Agent 做成稳定、可观测、可控的线上服务的工程能力，所以对直播 AI Agent 方向感兴趣。

不要背简历，不要罗列所有技术名词，把重点留给后面面试官追问。

### 2. 项目里哪个模块和直播业务里的 AI Agent 有关，讲清楚你负责哪块

**答题思路**

先界定范围，再讲职责，最后讲结果和反思：

1. **业务场景**：用一两句话说清 Agent 服务谁（主播、运营、审核、观众），解决什么问题（查数据、改预告、答规则、辅助回复等）。
2. **整体链路**：用户输入 → 意图识别 → 路由（工作流 / Agent）→ 工具调用 → 结果校验 → 回复或动作，在图上标出你负责的那一段。
3. **你的职责**：明确边界，例如工具服务化、会话与状态存储、RAG 入库与检索、线程池与异步化、风控与审计等，只讲真实做过的。
4. **难点与取舍**：挑 1～2 个（如延迟、幂等、工具权限、召回质量），说明方案、备选方案、为什么这样选。
5. **结果与复盘**：用你真实的指标（成功率、延迟、人工介入率等）说明效果，再补一句「如果重来会改什么」。

注意区分「团队做的」和「我做的」，面试官一定会往你负责的部分深挖。

### 3. 直播场景里用户一句话进来，你怎么做的意图识别，规则、分类模型、大模型路由分别解决什么问题

**参考答案**

结论：三者是分层漏斗，按「确定性 → 低成本 → 高灵活」逐级兜底，而不是三选一。

- **规则层**：关键词、正则、指令前缀（如「/封禁」）、白名单命令、按钮点击带来的显式意图。特点是零延迟、零成本、可解释、可强控，适合高频、格式固定、高风险需要确定性的入口。缺点是覆盖不了口语变化。
- **分类模型层**：小模型（BERT 类、轻量 embedding + 分类头、或 FastText）在有标注数据的封闭意图集上做分类，延迟几十毫秒、成本低、可离线评测，适合量大、意图集稳定的场景。缺点是新意图要重新标注训练，对长尾和复合意图弱。
- **大模型路由层**：处理开放表达、多意图、需要结合上下文指代消解的请求，输出结构化结果（intent、slots、置信度），并可以判断「该走工作流还是 Agent」。成本和延迟最高，且有幻觉风险。

落地要点：

1. 前一层置信度低于阈值才下沉到下一层，大部分流量被前两层吃掉，控制成本和延迟。
2. 大模型输出必须约束为枚举值（结构化输出 / JSON Schema），并对结果做合法性校验。
3. 还要有「未知意图 / 澄清追问」出口，而不是强行归类。
4. 用线上日志回流，持续把大模型处理过的样本沉淀成分类模型训练数据。

### 4. 为什么直播助手不能只上固定工作流，什么时候必须走 Agent

**参考答案**

结论：固定工作流适合「路径确定、步骤可枚举」的任务；当路径要靠运行时信息决定时，才需要 Agent。

固定工作流的优势是可预测、好测试、延迟和成本稳定、容易审计，所以能用工作流解决的（如查看今日开播数据、固定格式的预告修改）就不要上 Agent。

必须走 Agent 的情形：

1. **步骤数量不固定**：如「帮我分析昨晚流量下跌的原因」，要根据中间结果决定下一步查什么。
2. **工具选择依赖中间结果**：先查数据，发现异常后再查审核记录、活动变更。
3. **输入开放、组合多变**：一句话里夹多个诉求，穷举分支会爆炸。
4. **需要自我纠错**：工具失败、参数缺失时能够重新规划、追问用户。

工程上的折中是「工作流为主干，Agent 做局部节点」：高风险动作固定在工作流里并配审批，开放性分析交给 Agent，并限制它的工具集、最大步数和预算。

### 5. 简单任务走 ReAct、复杂任务走 Plan-Execute，你的路由标准是什么

**参考答案**

结论：按「任务可分解性、步骤数、工具依赖、对延迟的容忍度和失败代价」来判断，并且路由本身要可观测、可回退。

- **ReAct**（思考-行动-观察循环）：适合 1～3 步、边做边看、目标明确的任务，延迟低、灵活，但步骤多时容易发散、重复调用、丢失全局目标。
- **Plan-Execute**：先产出完整计划，再逐步执行（可按需重规划），适合步骤多、有依赖、需要并行或需要给用户展示和确认计划的任务，全局一致性好，但规划本身多一次大模型调用，计划在环境变化时可能失效，需要重规划机制。

可落地的路由信号：

1. 意图识别阶段给出的任务类型（单工具查询 / 多步分析 / 批量操作）。
2. 预估所需工具数量和是否存在依赖关系。
3. 是否涉及高风险动作（涉及则倾向先出计划并确认）。
4. 延迟预算：实时对话倾向 ReAct。

兜底：ReAct 超过步数阈值或出现重复调用时，自动升级为 Plan-Execute；反过来，计划中某一步很简单时可以直接用确定性调用。路由标准要用线上数据（成功率、步数、成本）持续校准，而不是拍脑袋。

### 6. 意图识别和真正调工具之间，怎么防止大模型瞎编意图

**参考答案**

结论：不要信任模型的自然语言输出，用「约束输出 + 确定性校验 + 低置信度澄清」把意图和参数卡在可验证的范围内。

1. **封闭意图集**：意图只能从预定义枚举中选，输出用结构化输出 / JSON Schema 约束，解析失败直接重试或拒绝。
2. **参数基于来源校验**：槽位值必须能在用户输入、会话上下文或业务系统中找到依据；如直播间 ID、商品 ID 要去后端查存在性和归属，不能直接用模型生成的值。
3. **置信度与澄清**：低于阈值或槽位缺失时追问用户，而不是猜。
4. **规则兜底**：高风险意图必须同时命中规则或二次确认，不能只靠模型判断。
5. **权限先于意图**：先用当前用户身份确定可用工具集，模型只能在这个集合里选，不在集合里的意图直接拒绝。
6. **评测与监控**：构建意图测试集，覆盖边界、对抗和歧义样本，线上抽检意图与最终动作是否一致，记录模型意图与规则意图的分歧。

容易漏的点：意图正确不代表参数正确，参数校验和权限校验要放在工具调用层，而不是只放在意图层。

### 7. Spring Boot 里怎么把 Agent 工具注册成可调用服务

**参考答案**

结论：把每个工具当成「带元数据的 Spring Bean」，统一注册到工具注册中心，由执行器负责校验、鉴权、超时和审计。

做法：

1. **声明**：使用框架注解，如 Spring AI 的 `@Tool(description = "...")` + `@ToolParam`，或 LangChain4j 的 `@Tool`；框架根据方法签名生成 JSON Schema 提供给模型。也可以自定义注解（名称、描述、风险等级、所需权限、超时、是否幂等）。
2. **注册**：Spring AI 中可以通过 `MethodToolCallbackProvider` 把含 `@Tool` 的 Bean 暴露为 `ToolCallbackProvider`，再通过 `ChatClient` 的 `defaultTools` / `tools` 使用；自定义方案则用 `BeanPostProcessor` 或 `ApplicationContext.getBeansWithAnnotation` 扫描后放入 `ToolRegistry`。
3. **执行**：模型只返回「工具名 + 参数」，由统一的 `ToolExecutor` 做：参数 Schema 校验、权限校验、限流、超时（线程池隔离）、幂等键、结果脱敏截断、审计落库。
4. **按请求动态裁剪**：每次请求按用户角色和场景只暴露可用工具，减少 token 和误调用。
5. **跨进程**：工具需要被多个 Agent 复用时，可以暴露为 MCP Server 或内部 HTTP / RPC 接口。

注意：工具描述就是给模型看的 Prompt，名字和描述要清晰；工具方法不要直接信任入参；工具异常要转换成模型可理解的错误信息。

### 8. 线程池参数怎么配，直播高峰期的异步任务如果用错拒绝策略会出什么事

**参考答案**

结论：线程池参数要根据任务类型（CPU / IO 密集）、下游容量和队列有界性来配，不存在通用数值，并且要隔离、监控。

`ThreadPoolExecutor` 的执行顺序：线程数 < `corePoolSize` 就新建线程；否则入队；队列满且线程数 < `maximumPoolSize` 才继续创建线程；都满了触发拒绝策略。因此如果用无界队列，`maximumPoolSize` 不会生效，积压会导致延迟暴涨甚至 OOM。

配置思路：

- CPU 密集：线程数约为 CPU 核数（或核数 + 1）。
- IO 密集（调用大模型、RPC，Agent 大多属于此类）：线程数 ≈ 核数 × (1 + 等待时间 / 计算时间)，再结合下游限流和压测调整。
- 使用有界队列，按业务隔离线程池（大模型调用、工具调用、通知分别隔离），并自定义线程名便于排查。
- Java 21 之后也可以用虚拟线程，但仍需要 Semaphore 等手段限制对下游的并发。

拒绝策略的后果：

- `AbortPolicy`：抛 `RejectedExecutionException`，若没有捕获处理，请求直接失败；但失败是显式的，可以降级。
- `CallerRunsPolicy`：由提交线程自己执行，起到反压作用，但会阻塞 Web 线程或 MQ 消费线程，高峰时可能拖垮整个入口。
- `DiscardPolicy` / `DiscardOldestPolicy`：静默丢任务，对「发提醒、扣库存、写审计」这类任务会造成数据丢失且不易察觉。

建议：关键任务拒绝时落库 / 投递 MQ 稍后重试；非关键任务可以丢弃但要计数告警；同时监控活跃线程数、队列长度、拒绝次数。

### 9. Redis 在 Agent 系统里你都存过什么，会话上下文、任务状态还是工具结果缓存

**参考答案**

结论：Redis 适合放「高频读写、可过期、对延迟敏感」的数据，需要强持久和审计的数据仍以 MySQL 为准。

常见用途：

1. **会话短期上下文**：最近 N 轮消息或摘要，用 List / Hash + TTL，按会话 ID 作 key。
2. **任务状态**：异步 Agent 任务的状态机（排队、执行中、成功、失败），用 Hash，配合 TTL 供前端轮询或推送。
3. **工具结果缓存**：只缓存幂等、只读、可容忍短暂过期的查询（如直播间数据快照），key 包含工具名和规范化参数，TTL 较短；写操作结果不缓存。
4. **分布式锁与幂等键**：用 `SET key value NX PX` 防止同一会话并发执行、同一动作重复执行；锁要带唯一值，释放时用 Lua 校验。
5. **限流与计数**：用户、工具维度的调用次数和 Token 预算。
6. **Pub/Sub 或 Stream**：流式输出分发、任务事件。

容易漏的点：缓存要注意用户隔离（key 里带租户 / 用户维度，避免串数据）；大 value 要拆分或截断；Redis 数据可能丢失，因此关键状态应能从 MySQL 恢复。

### 10. MySQL 里存 Agent 执行记录，表怎么设计，哪些字段必须留

**参考答案**

结论：按「一次会话 → 一次运行 → 多个步骤」三层建模，核心是可追溯、可回放、可统计，并且敏感数据要脱敏。

建议的表：

- `agent_session`：会话 ID、用户 ID、租户、创建时间。
- `agent_run`：`run_id`、`session_id`、用户 ID、入口意图、状态、开始 / 结束时间、总耗时、Token 用量、最终结果摘要、错误码、模型和 Prompt 版本。
- `agent_step`：`step_id`、`run_id`、序号、类型（LLM 调用 / 工具调用 / 人工审批）、工具名、入参（脱敏）、出参摘要、状态、耗时、重试次数、错误信息、`trace_id`、创建时间。

必须保留的字段：

1. 关联 ID：`run_id`、`step_id`、`trace_id`，以及操作人身份。
2. 模型信息：模型名、Prompt / 工具 Schema 版本，否则无法复现。
3. 工具调用的入参和出参（敏感字段脱敏、大字段截断或放对象存储）。
4. 状态、耗时、Token 和错误信息。
5. 幂等键，以及审批人和审批结果（高危动作）。

设计要点：`run_id`、`session_id + 时间`、`user_id + 时间` 建索引；数据量大时按时间分区或归档，大文本放对象存储；审计类表只追加不修改。

### 11. RAG 在直播知识问答里怎么用，主播规则、活动文案、商品信息怎么进知识库

**参考答案**

结论：按数据特点分别做解析、切分、元数据和更新策略，检索时带上权限和时效过滤，让答案可溯源。

流程：采集 → 清洗解析 → 切分 → 向量化 + 关键词索引 → 带元数据入库 → 检索 → 重排 → 组装上下文 → 生成并带引用。

不同数据的处理：

- **主播规则 / 平台规范**：结构化文档，按章节条款切分，保留标题路径、版本号、生效日期；规则变更要有版本管理，旧版本下线或打标。
- **活动文案**：时效性强，元数据中带活动 ID、起止时间，检索时过滤已过期活动；活动结束后清理或归档。
- **商品信息**：结构化数据（价格、库存、规格）不应该只依赖向量检索，价格、库存这类实时数据应通过工具查业务库，RAG 只负责描述类、卖点类文本。

关键点：

1. 元数据过滤（主播等级、地区、类目、生效时间）与权限控制。
2. 增量更新：数据变更触发重新切分和入库，旧向量按文档 ID 删除，避免脏数据。
3. 回答必须引用来源，找不到依据时明确回答不知道，而不是编造。
4. 评测：构造问题集，分别评估召回率（命中正确片段）和答案正确性。

### 12. 向量库和 ES 分别解决什么，为什么直播场景经常要混合检索

**参考答案**

结论：向量检索擅长语义相似，ES 的倒排索引擅长精确词匹配和过滤，两者互补，混合检索能同时提高召回率和精确度。

- **向量库**：把文本转成 embedding，通过近似最近邻（如 HNSW、IVF）找语义相近的内容。能处理同义改写（「怎么提现」和「收益如何到账」），但对精确的专有名词、编号、型号、违规条款号等容易漏或不准，结果也难解释。
- **ES（BM25）**：基于分词倒排索引，对关键词、短语、ID、编号命中准确，支持过滤、聚合、高亮，可解释；但不理解语义，同义表达会漏召回。

直播场景有大量专有名词（商品型号、活动名、规则编号、主播昵称）和口语化表述并存，所以单一方式都不理想。常见做法：两路并行召回，用 RRF 或加权融合，再用 Rerank 精排，同时用 ES 的过滤能力（时间、类目、权限）缩小范围。

补充：现在很多引擎（如 ES 8、OpenSearch、Milvus 等）同时支持稀疏和稠密向量检索，可以减少系统数量，但选型仍要看规模、运维和一致性要求。

### 13. Chunk 切大了和切小了各有什么坑，直播稿、商品详情、违规规则怎么切

**参考答案**

结论：Chunk 大小是在「语义完整」和「检索精度」之间取舍，应按文档结构切，而不是固定字数一刀切。

- **切太大**：一个 chunk 混入多个主题，向量被「平均」，检索精度下降；塞进上下文时噪音多、消耗 token，还可能触发「中间信息丢失」。
- **切太小**：语义被割裂（指代、条件、例外条款丢失），召回的片段缺少上下文，答案不完整；chunk 数量暴增，索引和成本变高。

常用策略：按结构切分（标题、段落、条款）+ 长度上限 + 少量重叠；父子 chunk（小块检索、返回其所在的大块）；给每块附上标题路径和文档元数据。

场景建议：

- **直播稿**：口语化、连续性强，按话题段落或时间段切，保留一定重叠，避免把一个完整话术截断。
- **商品详情**：按「属性项 / 卖点 / 售后」等字段分块，每块带商品 ID 和名称，防止检索到后不知道说的是哪个商品；规格价格走结构化查询。
- **违规规则**：按条款切分，一条规则及其例外、处罚作为一个整体，附带规则编号、版本和生效时间；条款之间引用关系可保存在元数据中，必要时检索后展开引用条款。

最终以检索评测（召回率、答案准确率）调整大小，不是靠经验定死。

### 14. 手撕算法：给定一个字符串数组，把能组成回文对的下标对找出来

**参考答案**

结论：这是 LeetCode 336「回文对」。用哈希表存「单词 → 下标」，对每个单词枚举所有前后缀切分，若一侧是回文，则另一侧的反转串存在于表中，就构成一个回文对。

思路（假设单词互不相同）：对单词 `w`，枚举切分点 `j`，前缀 `p = w[0:j]`，后缀 `s = w[j:]`：

- 若 `p` 是回文，且 `reverse(s)` 在表中、下标 `k != i`，则 `words[k] + words[i]` 是回文，加入 `(k, i)`。
- 若 `s` 是回文且 `j != len`（避免和上一种情况在空后缀处重复），且 `reverse(p)` 在表中、`k != i`，则 `words[i] + words[k]` 是回文，加入 `(i, k)`。

空串通过 `j = 0` 和 `j = len` 的切分自然被覆盖。

时间复杂度 O(n·L²)（L 为平均长度，枚举切分点 O(L)，每次回文判断和反转 O(L)），空间 O(n·L)。暴力解法是 O(n²·L)。

```java
import java.util.*;

public class PalindromePairs {
    public List<List<Integer>> palindromePairs(String[] words) {
        Map<String, Integer> map = new HashMap<>();
        for (int i = 0; i < words.length; i++) {
            map.put(words[i], i);
        }
        List<List<Integer>> res = new ArrayList<>();
        for (int i = 0; i < words.length; i++) {
            String w = words[i];
            int len = w.length();
            for (int j = 0; j <= len; j++) {
                String prefix = w.substring(0, j);
                String suffix = w.substring(j);
                if (isPalindrome(prefix)) {
                    Integer k = map.get(new StringBuilder(suffix).reverse().toString());
                    if (k != null && k != i) {
                        res.add(Arrays.asList(k, i));
                    }
                }
                if (j != len && isPalindrome(suffix)) {
                    Integer k = map.get(new StringBuilder(prefix).reverse().toString());
                    if (k != null && k != i) {
                        res.add(Arrays.asList(i, k));
                    }
                }
            }
        }
        return res;
    }

    private boolean isPalindrome(String s) {
        int l = 0, r = s.length() - 1;
        while (l < r) {
            if (s.charAt(l++) != s.charAt(r--)) return false;
        }
        return true;
    }
}
```

容易说漏的点：必须排除 `k == i`（自己和自己配对）；空串要正确处理且不能重复计数。

### 15. 算法写完面试官补一句：如果数据量到千万级，怎么从暴力改成倒排加字典树思路

**参考答案**

结论：先说明哈希 + 前后缀枚举已经把复杂度降到 O(n·L²)，千万级时瓶颈变成内存和单机吞吐，此时用「反转词字典树 + 节点记录回文剩余信息」配合分片并行处理。

**字典树思路**：把所有单词反转后插入字典树。每个节点记录：

- 以该节点结束的单词下标（`wordIndex`）。
- 经过该节点、且单词「剩余部分」是回文的单词下标列表（`restPalindrome`）。

查询单词 `w` 时沿字典树按 `w` 的字符向下走：

1. 若走到某节点时 `w` 的剩余部分是回文，且该节点有单词结束，则两者可以拼成回文对。
2. 若 `w` 走完，则该节点 `restPalindrome` 中的所有单词都可与 `w` 配对（更长的单词，多出的部分本身回文）。

这样每个单词只需沿一条路径走，不需要对每个切分点做哈希查找和字符串拷贝，常数小、无大量临时字符串，复杂度仍与 O(n·L²) 同阶（因为需要判定回文剩余部分，可预处理回文数组降到 O(L)，整体变为 O(n·L)）。

**倒排 / 工程化思路**：

1. 按长度分桶：回文对中两个词长度之差由较长词的回文部分决定，可以缩小候选集。
2. 按首尾字符建倒排索引：回文对要求 `w1` 首字符等于 `w2` 尾字符，用首字符、尾字符建索引，只在匹配桶内比较，避免全量两两比较。
3. 分片并行：把单词按首尾字符或哈希分片到多机 / 多线程，每片处理自己的查询，最后合并去重。
4. 内存：千万级字典树内存很大，可以用压缩 trie 或把单词按桶分批构建，或使用外部存储。

回答时应强调：首先确认 L 的量级，L 小则哈希方案已经足够，不要过度设计。

### 3. 直播里「查直播间数据、改预告、发提醒、封禁用户」这些事，怎么做成工具并分级

**参考答案**

结论：按「副作用和可逆性」给工具分级，不同级别对应不同的校验、审批和审计强度。

**分级示例**：

- **L0 只读**：查直播间数据。无副作用，可自动执行，可缓存，只需权限校验和脱敏。
- **L1 低风险写**：修改预告。可逆（有历史版本可回滚），影响范围限于自己的直播间；自动执行，但要校验参数、保留旧值、记录审计，必要时让用户确认修改内容。
- **L2 对外触达**：发提醒。不可撤回，影响第三方（粉丝）；需要限频、内容审核、频控和幂等，建议「预览 + 用户确认」后发送。
- **L3 高危**：封禁用户。影响用户权益、不可轻易恢复；Agent 只能「提出建议并生成工单」，由有权限的人审批后由系统执行，或者完全不开放给 Agent。

**工具设计要点**：

1. 每个工具声明元数据：名称、描述、参数 Schema、风险等级、所需权限、是否幂等、超时、是否需要审批。
2. 把「模型能调用的动作」设计成粒度小、语义明确的工具，避免一个万能工具。
3. 高危动作采用「两阶段」：先 `prepare`（生成待执行方案和影响范围预览），再 `confirm`（带审批凭证执行）。
4. 权限基于最终用户身份（透传用户 token），而不是 Agent 的超级账号。

### 4. 工具调用前怎么做参数校验、权限校验、风险拦截

**参考答案**

结论：在模型和真实服务之间放一层确定性的「工具网关」，所有校验在网关内按固定顺序完成，不依赖模型自觉。

典型顺序：

1. **Schema 校验**：类型、必填、枚举、长度、范围，格式不合法直接返回错误让模型修正（可限制重试次数）。
2. **业务校验**：实体是否存在、状态是否允许（如直播已结束就不能改预告）、参数是否有来源依据（来自用户输入或前序工具结果）。
3. **权限校验**：用透传的用户身份做鉴权（RBAC / ABAC），检查是否有权操作该资源（如只能操作自己的直播间），避免越权和提示词注入借用 Agent 权限。
4. **风险拦截**：按工具风险等级和上下文打分：规则（黑名单、频率、批量数量上限、涉及金额）+ 内容审核（发送文案）；命中高风险转人工审批。
5. **限流与预算**：用户 / 会话 / 工具维度的调用次数、成本上限。
6. **幂等与审计**：生成幂等键，执行前后记录审计日志。

容易漏的点：来自检索内容或工具返回里的文本是不可信输入，不能直接驱动高危操作（防间接提示词注入）；参数校验错误信息要对模型友好，但不能泄露内部细节。

### 5. 模型非要调 delete 或发消息怎么办，你的高危操作兜底怎么设计

**参考答案**

结论：不能依赖 Prompt 约束模型，高危保护必须是代码层的、不可被模型绕过的多重防线。

1. **最小权限**：默认不暴露 delete 等工具；按用户、场景动态下发工具集，模型看不到就调不到。
2. **网关强制拦截**：即使模型发出了调用，工具网关按风险等级拒绝或转审批，返回「需要人工确认」，而不是执行。
3. **两阶段提交**：先生成「待执行动作 + 影响范围 + 回滚方案」，由用户 / 管理员确认后凭一次性、绑定参数的确认令牌执行；令牌过期或参数变化即失效。
4. **软删除与可回滚**：删除做成软删除或带保留期，发送类动作增加延迟窗口（可撤销）。
5. **限额与熔断**：批量上限、频率上限；错误率或拦截率异常时熔断，暂停 Agent 的写操作。
6. **内容审核**：对外发送内容走独立的审核服务。
7. **全链路审计与告警**：所有高危尝试（包括被拒绝的）都要落库并告警，用于发现提示词注入和模型异常。
8. **演练**：上线前用红队用例（诱导删除、越权、注入）做测试。

一句话总结：模型只能「提议」，是否「执行」由确定性的系统决定。

### 6. 多 Agent 在直播场景怎么拆，主播助理、运营分析、风控审核、数据查询要不要分开

**参考答案**

结论：按「职责边界、工具权限、风险等级、上下文差异」拆分，而不是为了多 Agent 而多 Agent；能用单 Agent 加工具解决的就不要拆。

拆分依据：

1. **权限与风险隔离**：风控审核有封禁等高危工具，应与主播助理分开，独立权限和审计，避免一个 Agent 带着所有工具。
2. **上下文与知识差异**：运营分析需要大量数据和分析方法，风控审核需要规则库，各用各的知识库和 Prompt，避免互相污染、减少上下文长度。
3. **工具数量**：单个 Agent 工具过多会降低选择准确率，按领域拆开可以保证每个 Agent 工具集精简。
4. **独立演进和评测**：各 Agent 可以单独迭代、单独灰度。

建议：数据查询通常更适合做成共享的「工具 / 服务」而不是独立 Agent（它是确定性查询，没必要每次都过一个大模型）；主播助理作为面向用户的入口或主管 Agent，负责路由；运营分析、风控审核作为专业子 Agent。

代价要说明：多 Agent 带来更多延迟、成本、状态同步和调试复杂度，所以要用编排（主管 Agent 或工作流）+ 明确的输入输出契约控制复杂度。

### 7. 主管 Agent 和子 Agent 之间传什么，别把整段聊天记录全传过去这话怎么落地

**参考答案**

结论：传「任务契约」而不是「对话历史」：子 Agent 只拿完成任务所必需的最小上下文，并返回结构化结果。

下发给子 Agent 的内容：

- 明确的任务目标和验收标准。
- 必要的结构化参数（直播间 ID、时间范围等），已解析好的实体。
- 与任务相关的少量上下文摘要或关键事实（由主管提炼）。
- 约束：可用工具集、权限范围（透传的用户身份）、预算、超时、最大步数。
- 追踪信息：`run_id`、`trace_id`。

子 Agent 返回的内容：结构化结果（状态、结论、关键数据、证据来源 / 引用、失败原因、置信度），而不是一大段自由文本和完整的中间推理。

落地做法：

1. 定义 JSON Schema 的输入输出契约，并校验。
2. 主管维护全局状态（共享状态存储），子 Agent 只读写自己的命名空间，避免上下文互相污染。
3. 大数据结果存外部存储，只传引用（ID）。
4. 日志里保留完整过程用于排查，但传递的内容保持精简。

好处：降低 token 成本和延迟，减少无关信息干扰，减少敏感信息泄露面，也便于单独测试每个子 Agent。

### 8. 子 Agent 执行失败，是重试、重规划、降级还是转人工，举直播场景例子

**参考答案**

结论：先对失败分类，再按「可重试性、影响面、是否有替代方案」选择策略，而不是一律重试。

| 失败类型 | 策略 | 直播场景例子 |
| --- | --- | --- |
| 瞬时错误（超时、网络抖动、限流） | 带指数退避和抖动的有限次重试，要求工具幂等 | 查询直播间数据超时，重试 1～2 次 |
| 参数 / 计划错误（参数不合法、前置条件不满足） | 把错误反馈给模型修正参数，或重规划 | 修改预告时时间早于当前时间，重新向用户确认时间 |
| 依赖不可用或长时间失败 | 降级：用缓存 / 旧数据 / 简化流程，并明确告知结果有局限 | 实时数据服务故障，返回 5 分钟前快照并标注 |
| 高风险或语义不确定 | 转人工，附带已完成步骤和上下文 | 疑似违规封禁判断不一致，转风控人员审核 |
| 无法恢复且影响大 | 终止，回滚已完成的步骤（补偿事务），通知用户 | 批量提醒发到一半失败，停止并记录已发送名单 |

通用原则：重试次数和总耗时要有上限；写操作必须有幂等键，否则不要自动重试；每次失败都落库，便于统计失败原因；兜底的最终出口是转人工，不能让 Agent 无限尝试。

### 9. Agent 循环调用同一个工具停不下来，怎么检测和处理

**参考答案**

结论：用「硬限制 + 重复检测 + 进展判断 + 打断策略」组合防护，硬限制必须由代码保证。

**检测**：

1. **硬上限**：最大迭代步数、最大工具调用次数、最大 Token / 成本、总超时，任一触发就终止。
2. **重复调用检测**：对「工具名 + 规范化参数」做哈希，窗口内相同调用次数超过阈值（如连续 N 次）判定循环；也可检测 A→B→A→B 这类周期。
3. **无进展检测**：连续多步工具返回的结果相同或没有新增信息，则认为没有进展。
4. **状态检测**：计划中的待办项长时间没有变化。

**处理**：

1. 第一次发现重复时，把提示注入上下文：「该调用已执行过，结果为……，请换一种方式或直接回答」。
2. 临时从可用工具中移除该工具，或缓存相同调用的结果直接返回。
3. 触发重规划，或升级到更强的模型 / Plan-Execute 模式。
4. 仍无法脱离循环则终止，给出已有结果，并转人工或提示用户补充信息。
5. 记录并告警，把这类案例纳入评测集，从 Prompt、工具描述（是否报错信息不清晰导致模型反复尝试）和工具返回值设计上根治。

常见根因：工具错误信息不明确、工具返回空结果模型不相信、目标不可达却缺少「放弃」的出口。

### 10. 上下文太长怎么压，滑动窗口、摘要、关键实体保留、检索补上下文分别什么时候用

**参考答案**

结论：这几种手段不是互斥的，通常组合使用：近期对话原文保留，较早内容压缩，关键事实结构化保存，需要时按需检索。

- **滑动窗口**：保留最近 N 轮原文。实现简单、无信息失真，适合短任务和对话式场景；缺点是早期的重要约束会丢失。
- **摘要**：把较早的对话压缩为摘要（可滚动更新）。适合长对话、跨度长的任务；缺点是有损、需要额外模型调用，可能丢失细节或引入错误，关键数值和 ID 不能只留在摘要里。
- **关键实体 / 事实保留**：把用户偏好、确认过的参数、直播间 ID、已完成步骤、约束条件等抽取成结构化状态（slot / 记忆表），每轮固定注入。适合任务型 Agent，信息精确且 token 少。
- **检索补上下文**：把完整历史、文档、工具大结果存外部存储，按当前问题检索相关片段再注入。适合历史很长、需要回溯具体细节的场景。

另外：对工具返回的大结果要截断、抽取字段或只回传摘要和引用；对已完成的工具调用中间过程做折叠。

典型组合：系统提示 + 结构化状态 + 历史摘要 + 最近 N 轮原文 + 检索到的相关片段。要注意压缩后的评测：检查关键信息有没有丢失。

### 11. 短期记忆放 Redis，长期记忆放向量库，用户偏好和直播历史怎么分层

**参考答案**

结论：按「时效、结构化程度、访问方式」分层存储，不是所有记忆都要进向量库。

- **短期记忆（会话级）**：当前会话的最近消息、任务状态、临时变量，放 Redis，设置 TTL，读写快。
- **用户偏好（结构化、稳定）**：例如常用话术风格、通知偏好、默认直播时段，是明确的键值或少量字段，应放 MySQL（或文档库 / KV），按用户 ID 精确读取，必要时用 Redis 做缓存。这类数据不需要语义检索，放向量库反而不精确。
- **直播历史（量大、需要语义回溯）**：历史场次的复盘、经验、过往事件的摘要，适合生成摘要后向量化放入向量库，并附带元数据（用户 ID、时间、场次），按语义检索；精确指标数据（观看人数、成交额）仍放在数仓 / 业务库，由工具查询。

写入与治理：

1. 记忆写入要有「提取 → 去重 / 合并 → 冲突处理（新偏好覆盖旧偏好）→ 过期」流程，不要把所有对话都存进去。
2. 用户隔离、权限和隐私：支持用户查看、删除记忆，敏感信息不入长期记忆。
3. 读取时：先取结构化偏好，再按需检索长期记忆，带上相关度和时间衰减过滤，防止召回过时信息。

### 12. RAG 召回了但答非所问，是检索问题、重排问题、上下文组装问题还是模型问题，怎么定位

**参考答案**

结论：沿着链路分阶段评测，先看「正确答案有没有进入各阶段的结果」，由前向后逐段定位。

按顺序排查：

1. **知识本身**：知识库里是否真的有答案？没有则是数据问题。文档解析、切分是否把答案割裂。
2. **召回阶段**：用人工标注的问题 + 正确片段，计算 Recall@K。正确片段不在召回的 top K 里，是检索问题：查询改写（口语、指代、缺上下文）、embedding 模型不合适、chunk 不合理、缺少关键词检索、元数据过滤过严。
3. **重排阶段**：正确片段在召回里但排名靠后，或被重排后排掉，是重排问题：Rerank 模型不适配领域、融合权重不合理、截断的 top N 太小。
4. **上下文组装**：正确片段已经进入最终 prompt，仍然答错：检查片段顺序、长度、重复、冲突内容、被截断、噪音太多（中间丢失），以及 Prompt 是否要求「基于资料回答」。
5. **生成阶段（模型）**：上下文完整且清晰，模型仍然答非所问：是模型 / Prompt 问题，如指令不清、忽略上下文、能力不足、温度过高。

定位工具：保存每次请求的 query、改写后的 query、各阶段的候选和分数、最终 prompt、回答，做回放；离线构建评测集，分别度量召回（Recall / MRR）、答案忠实度、答案相关性。这样可以把问题归因到具体环节后再针对性优化，而不是盲目换模型。

### 13. BM25、向量检索、Rerank、RRF 融合，你在直播知识库里会怎么排流水线

**参考答案**

结论：采用「多路召回 → 融合 → 精排 → 过滤与组装」的漏斗，前面追求召回、后面追求精度。

流水线：

1. **查询预处理**：结合会话上下文做指代消解和查询改写，必要时拆分多个子查询；抽取实体（商品名、规则编号）和过滤条件（时间、类目、权限）。
2. **多路召回（并行）**：
   - BM25（ES）：命中专有名词、编号、规则条款，取 top 50～100。
   - 向量检索：召回语义相近内容，取 top 50～100。
   - 召回时都带上元数据过滤（权限、有效期）。
3. **RRF 融合**：Reciprocal Rank Fusion，按名次计分 `score = Σ 1 / (k + rank_i)`（k 常取 60 左右），不同检索器分数尺度不一致也不需要归一化，对文档去重后得到合并排序，取 top 20～50。
4. **Rerank 精排**：用交叉编码器（cross-encoder）重排模型对「查询 + 候选」打分，取 top 3～8。该步骤成本较高，所以放在融合之后，只处理有限候选。
5. **上下文组装**：去重、合并同一文档相邻片段、必要时展开父块、按相关度排序、控制 token 预算，附带来源和时间。
6. **生成与引用**：要求基于资料回答，附引用；召回分数过低时拒答或转人工。

权衡：延迟（并行召回、限制 Rerank 候选数）、成本、可解释性；通过评测集调整 K 值、融合方式和阈值。

### 14. Kafka 或 RocketMQ 在 Agent 系统里能干什么，直播事件流怎么接进去

**参考答案**

结论：MQ 在 Agent 系统中主要做「异步解耦、削峰、事件驱动、可靠重试」，让 Agent 从「只能被动对话」变成「能响应业务事件」。

用途：

1. **事件触发 Agent**：订阅直播事件（开播、下播、弹幕突增、违规检测命中、订单异常、预告到期），驱动 Agent 执行分析、提醒、预警。
2. **异步任务队列**：耗时的 Agent 任务（报告生成、批量处理）投递后异步执行，结果通过回调或状态查询返回，用 MQ 削峰。
3. **工具动作异步化**：发提醒、写审计、数据同步等下游动作通过 MQ 可靠投递，失败重试，死信队列兜底。
4. **审计与观测**：Agent 执行日志、指标事件写入 MQ，下游落库和分析。
5. **多 Agent 通信**：Agent 之间通过消息协作。

接入直播事件流的要点：

- **分区键**：按直播间 ID 做 key，保证同一直播间事件有序（Kafka 分区内有序；RocketMQ 可用顺序消息）。
- **事件过滤与聚合**：直播事件量大（弹幕、互动），不能每个事件都触发大模型。先用规则 / 流计算（如 Flink）做窗口聚合和阈值判断，只有「异常或需要决策」时才发给 Agent。
- **幂等消费**：消息可能重复（至少一次投递），用事件 ID 做幂等去重。
- **背压与限流**：消费速率受大模型和工具容量限制，控制并发，积压时按优先级降级处理。
- **失败处理**：重试、死信队列、人工补偿。

### 15. 手撕算法：写一个带过期时间的 LRU Cache，支持 get、put、过期清理

**参考答案**

结论：用「哈希表 + 双向链表」实现 O(1) 的 LRU，每个节点记录过期时间；`get` 时惰性检查过期，并用「最小堆」按过期时间支持主动清理。

设计：

- `HashMap<K, Node>` 实现 O(1) 查找；双向链表维护访问顺序，表头是最近使用，表尾是最久未使用。
- `get`：不存在返回 null；已过期则删除并返回 null；否则移到表头。
- `put`：已存在则更新值和过期时间并移到表头（这里创建新节点替换旧节点，避免修改堆中已有元素的排序键）；容量满时先清理过期项，仍然满则淘汰表尾。
- `cleanup`：从最小堆堆顶开始，弹出所有已过期节点；只有当 map 里当前对应的节点仍是该节点时才真正删除（旧版本节点、已被淘汰的节点会被忽略）。
- 时间复杂度：`get`、`put` 均摊 O(1)（堆操作使 `put` 为 O(log n)），清理按过期条目数 O(m log n)；空间 O(n)。

```java
import java.util.*;

public class TtlLruCache<K, V> {
    private static class Node<K, V> {
        K key;
        V value;
        long expireAt;
        Node<K, V> prev, next;
    }

    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<>();
    private final Node<K, V> head = new Node<>();
    private final Node<K, V> tail = new Node<>();
    private final PriorityQueue<Node<K, V>> heap =
            new PriorityQueue<>(Comparator.comparingLong(n -> n.expireAt));

    public TtlLruCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    protected long now() {
        return System.currentTimeMillis();
    }

    public V get(K key) {
        Node<K, V> node = map.get(key);
        if (node == null) return null;
        if (node.expireAt <= now()) {
            remove(node);
            return null;
        }
        unlink(node);
        addFirst(node);
        return node.value;
    }

    public void put(K key, V value, long ttlMillis) {
        Node<K, V> old = map.get(key);
        if (old != null) {
            remove(old);
        }
        if (map.size() >= capacity) {
            cleanup();
        }
        if (map.size() >= capacity) {
            remove(tail.prev);
        }
        Node<K, V> node = new Node<>();
        node.key = key;
        node.value = value;
        node.expireAt = now() + ttlMillis;
        map.put(key, node);
        addFirst(node);
        heap.offer(node);
    }

    /** 清理所有已过期的条目 */
    public void cleanup() {
        long t = now();
        while (!heap.isEmpty() && heap.peek().expireAt <= t) {
            Node<K, V> node = heap.poll();
            if (map.get(node.key) == node) {
                remove(node);
            }
        }
    }

    private void remove(Node<K, V> node) {
        map.remove(node.key);
        unlink(node);
    }

    private void unlink(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addFirst(Node<K, V> node) {
        node.next = head.next;
        node.prev = head;
        head.next.prev = node;
        head.next = node;
    }
}
```

说明：被淘汰或被覆盖的旧节点会残留在堆里直到过期，内存上有一定滞留，可以通过「堆中保存 key + 版本号」或定期重建来优化。生产中还可以用定时线程调用 `cleanup()`。时钟建议用单调时钟，避免系统时间回拨影响。

### 16. 算法之后追问：高并发下多个线程同时访问这个缓存，怎么改成线程安全还不怎么掉性能

**参考答案**

结论：先保证正确（粗粒度锁），再按瓶颈逐步细化：分段（分片）锁、读写路径解耦、异步更新访问顺序，直接使用成熟实现更稳妥。

演进路径：

1. **全局锁**：给 `get` / `put` / `cleanup` 加 `synchronized` 或 `ReentrantLock`。正确但并发度低。注意 LRU 的 `get` 也会修改链表，所以不能用读写锁简单地让读并发。
2. **分段（分片）**：按 `hash(key) % N` 分成 N 个独立的 LRU 子缓存，各自有锁，各自容量为总容量 / N。冲突概率降低，吞吐近似线性提升；缺点是 LRU 变成近似的全局 LRU，热点 key 仍落在同一分片。
3. **降低 `get` 的写开销**：不是每次读都移动链表，而是把访问记录写入无锁的缓冲区（环形缓冲 / 队列），由后台线程或在下次写入时批量回放来更新顺序，这是 Caffeine 的做法（读缓冲 + 写缓冲 + 异步维护）。也可以用近似策略，例如记录最近访问时间，仅当访问间隔超过阈值才移动。
4. **用 `ConcurrentHashMap` 作为存储**，用锁只保护链表或淘汰逻辑；过期清理放到后台线程（单线程定时，或用时间轮），避免在请求路径上做批量清理。
5. **缓存击穿**：热点 key 过期时多个线程同时回源，可使用 `computeIfAbsent` 或按 key 加锁（单飞，single flight），其余线程等待结果。
6. **生产建议**：直接使用 Caffeine，它支持基于大小的淘汰（W-TinyLFU）、`expireAfterWrite`、`expireAfterAccess`、异步刷新，性能和正确性经过验证。

验证：用 JMH 做并发压测，对比锁竞争（线程 dump、profiler）并观察命中率，而不是只看吞吐。

## 三面

### 1. 自我介绍

**答题思路**

三面通常是 Leader / 架构视角，自我介绍应偏「技术判断与落地推动」：

1. 简要背景和年限。
2. 突出你带来的业务结果和系统稳定性，而不是技术点的堆砌。
3. 讲清你在 Agent 项目中的角色：技术方案设计、风险控制、跨团队协作、评测与观测体系。
4. 表达你的判断力：知道什么时候用 Agent、什么时候不用，如何控制风险和成本。
5. 与岗位匹配：把 Java 后端的稳定性工程能力和 Agent 落地结合起来。

### 2. 你带过或者主导过 Agent 项目么，直播业务里怎么推动后端、算法、产品一起落地

**答题思路**

有真实经历就如实讲，没有就讲你参与的最近经历，并说明你会怎样推动，不要夸大职级。

1. **定义问题和成功标准**：与产品一起确定场景、边界（哪些做、哪些不做）、可量化指标（任务完成率、人工介入率、时延、成本）。
2. **分工与接口契约**：后端负责工具服务化、权限、稳定性、观测；算法负责模型选型、Prompt、RAG 和评测；产品负责场景、交互、验收标准与灰度计划。以工具 Schema 和评测集作为协作的契约。
3. **统一评测集**：三方共同维护一份真实问题样本集，每次改动都跑回归，用数据而不是主观感受讨论效果。
4. **迭代节奏**：先上低风险只读场景，建立观测，再逐步放开写操作；每个阶段设定准入和回退条件。
5. **风险与合规**：提前拉上风控、法务，确认高危动作的审批机制。
6. **复盘机制**：线上 bad case 回流、定期评审，沉淀为评测样本。
7. **冲突处理**：例如产品想快速上线而风险未评估时，用数据和灰度方案折中。

### 3. 老板说下周直播大促就要上智能助手里的高危自动发券和自动回复，你怎么评估接不接

**参考答案**

结论：不是简单的「接」或「不接」，而是评估风险与准备度，给出「分级、分范围、可回退」的替代方案，用数据说服老板。

评估维度：

1. **风险**：自动发券直接涉及资金损失（超发、被刷、重复发放），自动回复涉及舆情和合规（乱承诺、违规话术）。大促流量高峰，一旦出事被放大。
2. **准备度**：是否有评测集和通过率、风控拦截、幂等和限额、审计、监控告警、一键关闭（kill switch）、回滚方案、值班机制。一周时间通常无法完成充分验证。
3. **收益**：能节省多少人力、提升多少转化，与潜在损失对比。

建议的方案（降风险后上线）：

- **发券**：不让 Agent 直接发，改为「Agent 推荐 + 人工确认」，或在严格规则下低额度自动发：单券面额、单用户、总预算、频率上限，必须由发券服务做幂等和风控校验；预算耗尽自动熔断。
- **自动回复**：先限定范围，只回复知识库中有明确来源的 FAQ；敏感话题（赔付、投诉、承诺类）转人工；回复经过内容审核；开启灰度（小比例直播间 / 小流量）。
- **保障**：影子模式（先只生成不发送，对比人工）、实时监控大盘、告警、kill switch、大促期间有专人值守。

结论表达：如果无法满足「限额、幂等、审计、可关闭、可回滚」这些底线，就明确建议大促期间只上低风险部分，把高危能力放到大促后分阶段灰度，并说明风险与损失的量化对比，让决策者知情。

### 4. 多 Agent 系统线上出事故：模型乱发消息、工具重复扣库存、上下文炸了，你先查哪块

**参考答案**

结论：先止损再定位。先止血（关闭相关能力、限流或降级），再基于 trace 按问题类型逐一排查。

**第一步，止损**：用 kill switch 或开关停用有副作用的工具（发消息、扣库存），切换为「只读 / 人工确认」模式；评估已造成的影响范围（哪些用户、哪些订单），准备补偿。

**第二步，定位（依靠 `run_id` / `trace_id` 的全链路日志）**：

- **模型乱发消息**：查对应 run 的 Prompt、上下文、检索内容和工具调用参数。是否有提示词注入（来自用户输入或检索文档）；是否缺少网关的内容审核和确认；模型 / Prompt 版本是否刚刚变更。处理：强制确认、内容审核、限定收件范围。
- **工具重复扣库存**：先查幂等问题。是否因重试（超时后重试而首次其实已成功）、MQ 重复消费、模型重复调用同一个工具、并发请求导致。检查是否有幂等键、扣库存接口是否基于业务单号去重、数据库是否有唯一约束或乐观锁。处理：幂等键 + 唯一约束，库存扣减由库存服务保证，不依赖 Agent 保证。
- **上下文炸了**：查 Token 用量是否暴涨：工具大结果被整段塞回、循环调用累积、历史未压缩、检索片段过多。处理：结果截断、摘要、窗口限制、最大步数和 Token 预算。

**第三步，修复与预防**：补监控告警（拦截率、重复调用率、Token 异常）、增加回归用例、完成事故复盘，补偿受影响用户。

要点：这三类问题的共同根因是「把保证正确性的责任放在了模型身上」，应该把约束下沉到确定性的服务层。

### 5. 图数据库在直播 Agent 里能干什么，主播-粉丝-商品-直播间-违规记录这种关系为什么向量库不全能

**参考答案**

结论：图数据库擅长「实体之间的显式关系和多跳查询」，向量库擅长「语义相似度」，两者解决不同的问题。

图数据库（如 Neo4j、NebulaGraph）的价值：

1. **多跳关系查询**：例如「与被封禁主播有共同粉丝群且推广同类商品的账号」「某违规商品被哪些直播间挂过」，用图遍历很自然，在关系型数据库中需要多层 join，效率低且难写。
2. **团伙与关联发现**：风控中识别刷量、导流团伙，使用社区发现、路径分析、中心性等图算法。
3. **可解释性**：结果是明确的关系路径，可以展示「为什么」。
4. **关系的精确约束**：关系是确定的事实（谁关注谁、谁挂了哪个商品），不是相似度。

向量库不够的原因：

- 它返回的是「语义相似」的文本，不保证存在真实的关系；相似不等于相关。
- 多跳推理、聚合、计数、路径、环路这类结构性查询无法用相似度表达。
- 关系有方向和类型（关注、举报、售卖），向量化后会丢失结构，且难以精确更新（一条关系变更需要重新生成向量）。
- 结果不精确、不可解释，难以满足风控审核的要求。

适用边界：关系量不大、查询只有一两跳时，MySQL 就够了，不必为了新技术引入图数据库。

### 6. 知识图谱加向量检索加 RAG，怎么做成混合推理，不要只说「都能用」

**参考答案**

结论：让图负责「结构化事实和多跳推理」，向量检索负责「非结构化文本的语义召回」，由一个路由 / 编排层决定先查谁、如何互相补充，最后统一组装证据给模型。

**一种可落地的流程**：

1. **查询理解**：抽取问题中的实体（主播、商品、直播间）和问题类型（关系类、事实类、开放描述类）。
2. **实体链接**：把文本中的实体映射到图中的节点 ID（用名称匹配 + 向量相似度做消歧）。
3. **图检索**：围绕这些节点做 1～3 跳子图查询或模板化 Cypher / nGQL（建议用预定义的查询模板或让模型生成再校验，防止生成错误查询），得到结构化事实和关系路径。
4. **向量 / 关键词检索**：针对问题以及图中扩展出的实体，召回相关的规则条文、案例、话术文档片段。
5. **互相补充**：
   - 用图结果扩展检索：把相关实体名、同义关系加到查询中（图增强检索）。
   - 用文档结果补充图：文档中描述的关系抽取后回写图（知识图谱构建，需要人工或规则校验）。
6. **证据融合与重排**：把图路径（转成自然语言三元组）和文本片段放在一起，按相关度和可信度排序，去重，标明来源。
7. **生成与校验**：模型基于证据回答，并要求引用；对关键结论做事实校验（例如重新用图查询核验）。

举例：「这个主播最近为什么被限流？」→ 图查询得到违规记录、关联商品、关联举报；向量检索召回对应违规规则条文；合并后生成带证据的解释。

难点：图谱构建与更新成本、实体消歧、图查询生成的正确性、延迟。回答时要主动说明这些权衡。

### 7. Codex / Claude Code 这类 coding agent 你真用过么，拿来改 Java 项目踩过什么坑

**答题思路**

如实回答，用过就讲具体场景，没用过就讲你的试用和评估，不要编造。结构建议：

1. **使用场景**：适合什么（生成样板代码、补测试、重构、读陌生代码库、批量改动）和不适合什么（涉及核心业务逻辑、并发正确性、安全相关）。
2. **工作方式**：先让它读代码和写计划，再分步实现；每步跑编译和测试；改动用 git 分支隔离，人工 review diff。
3. **常见的坑**（Java 项目中较典型的，可以挑你真实遇到的讲）：
   - 不熟悉项目约定，擅自引入新依赖或不同风格的写法，和现有框架版本不兼容。
   - 为了让测试通过而修改测试或断言，或写出只迎合用例的实现。
   - 改动范围扩散：顺手重构无关代码，导致 diff 巨大难 review。
   - 对并发、事务边界（`@Transactional` 失效场景）、空指针、泛型等细节考虑不周。
   - 幻觉：调用不存在的方法、过时的 API 或错误的库用法。
   - 长会话上下文变长后遗忘约束，反复犯同一个错误。
4. **应对办法**：项目根目录放 AGENTS.md / 规则文件说明构建命令、代码规范、禁止事项；限制任务粒度；让它先写测试；CI 作为最终的把关。
5. **结论**：把它当作需要 review 的高效助手，责任仍在工程师。

### 8. 让 Codex 改 Agent 工具代码，测试挂了它还乱改，你怎么约束它的上下文和重试

**参考答案**

结论：靠「缩小任务和上下文 + 把规则写进仓库 + 用确定性的检查限制重试」来约束，而不是靠在对话里反复叮嘱。

**约束上下文**：

1. 任务拆小，一次只改一个工具或一个问题，并明确要修改的文件范围（指定路径，其他目录只读）。
2. 在 AGENTS.md 中写明：构建和测试命令、代码规范、禁止修改的目录（如测试夹具、生成代码、配置）、不允许新增依赖。
3. 提供精准的信息：失败的测试名称、完整报错、相关的接口约定，而不是整个仓库。
4. 使用独立分支或 worktree，保证随时可以丢弃。

**约束重试**：

1. 限定最大重试轮数（如 2～3 次），超过后停止，输出「已尝试的方案、失败原因、假设」，由人接手。
2. 要求先分析根因再动手：先解释失败原因，再提出修改方案，避免「改到过为止」。
3. **保护测试**：禁止修改或删除既有测试和断言（需要时单独申请）；可以在 CI / 钩子里检测测试文件的改动并拦截；避免用 `@Disabled`、放宽断言来「变绿」。
4. 每轮失败后对比 diff，如果改动越来越大或和问题无关，回滚到上一个检查点再重新开始（避免在错误方向上累积）。
5. 用工具拦截器限制危险命令（删除、强制推送、修改依赖锁文件等）。
6. 最终以 CI 的完整测试、人工 review 为准。

要点：失败信息过长时会污染上下文，应只保留关键日志；换新会话并附带「已尝试方案摘要」往往比在同一个被污染的会话里继续更有效。

### 9. Harness 工程你怎么做，AGENTS.md、进度文件、工具拦截器、检查点、回放分别解决什么

**参考答案**

结论：Harness 是围绕模型的一整套「运行外壳」，让模型在一个受控、可观测、可恢复的环境里工作；模型负责推理，Harness 负责约束、记忆、反馈和安全。

各部分解决的问题：

- **AGENTS.md（项目级指令）**：把项目背景、构建 / 测试命令、代码规范、禁区、常见坑写成仓库内的文件，在每次会话开始时加载。解决「模型不了解项目约定、每次都要重复交代」的问题。内容要精炼，过长会占用上下文并稀释重点。
- **进度文件**（如 `progress.md`、任务清单）：把目标、已完成、待办、关键决策和失败尝试写入文件。解决长任务中跨上下文窗口 / 跨会话丢失状态的问题，新会话读取就能接续，也便于人工检查。
- **工具拦截器**（hook / middleware）：在工具调用前后执行确定性逻辑：权限、参数校验、危险命令拦截、自动格式化、运行测试、脱敏、记录日志。解决「不能依赖模型自觉」的问题。
- **检查点**：在关键步骤保存状态（代码快照 / git commit、Agent 状态）。解决失败后回滚、从中间恢复、避免错误累积的问题。
- **回放**：把一次运行的输入、模型响应、工具调用和结果完整记录下来，可以重放或复现。解决排查问题、回归测试和比较不同模型 / Prompt 版本的问题。

补充要点：还需要评测集（用回放的数据做回归）、预算和最大步数限制、人工介入的出口。判断是否做对的标准，是换一个模型后系统行为仍然可控。

### 10. Agent 上线后看哪些指标，工具调用成功率、任务完成率、人工介入率、幻觉率怎么定义

**参考答案**

结论：指标分「业务效果、质量、稳定性、成本、安全」几类，每个指标必须有明确的分子分母和判定口径。

- **工具调用成功率** = 成功的工具调用数 / 总工具调用数。要区分失败类型：参数错误（模型问题）、权限拒绝、下游错误或超时（系统问题）；同时统计「首次调用成功率」和「重试后成功率」，以及工具选择正确率。
- **任务完成率** = 达成用户目标的会话（run）数 / 总会话数。「完成」要有判定方式：任务型有明确的终态（如预告修改成功并经校验），可以自动判定；开放问答则依赖用户反馈（点赞 / 点踩、是否重复提问）、抽样人工标注或 LLM 评审。
- **人工介入率** = 触发人工接管或审批的会话数 / 总会话数，拆分为「主动转人工」「被风控拦截转人工」「用户要求人工」。既不能太高（没有价值），也不能为零（说明高危保护可能失效）。
- **幻觉率** = 经评审发现含有无依据或错误信息的回答数 / 抽样评审回答数。可以细分为：未被检索内容或工具结果支持的陈述（忠实度）、编造的工具结果或参数、错误的实体。通常通过抽样人工标注 + 模型评审 + 引用校验来估计。

其他必看指标：端到端延迟（P50 / P95 / P99）和首 token 延迟、每任务平均步数和 Token 成本、循环 / 超限终止率、高危动作拦截率、重复调用率、用户满意度、各模型和 Prompt 版本的分维度对比。

要点：指标要能下钻到 run 级别回放，并设告警阈值；上线新版本时和旧版本做对比。

### 11. 模型升级后，你原来写的意图识别、规则路由、风险审核还要不要，怎么灰度

**参考答案**

结论：要保留，但要重新评估其职责。模型更强会减少部分规则的收益，但风险审核等确定性约束不应该因为模型变强而去掉。

分层看待：

- **风险审核 / 权限 / 幂等**：必须保留。它们保证的是系统的正确性和合规，与模型能力无关，不可靠模型自觉。
- **规则路由**：保留高确定性、高频的部分（成本低、延迟低、可解释），对大量靠规则维修补丁的长尾，可以评估后交给新模型。
- **意图识别（分类模型）**：用评测集对比新模型直接做意图识别的准确率、延迟、成本；如果新模型明显更好且成本可接受，可以简化；否则保留作为快速通道。
- 一般模型升级带来的是「能力上升」，同时也带来「行为变化」（输出风格、工具调用习惯、拒答边界），所以所有环节都要回归验证。

灰度方案：

1. **离线评测**：用沉淀的真实样本集和对抗样本对比新旧模型的准确率、工具选择、成功率、延迟、成本。
2. **影子流量**：新模型接收同样的请求但不执行动作，只记录结果，与旧版本对比。
3. **小流量灰度**：按用户或直播间的小比例逐步放量（如逐级扩大），并只先开放低风险场景。
4. **监控与自动回滚**：设置核心指标（成功率、拦截率、人工介入率、延迟）的阈值，超过就自动回滚到旧模型。
5. **版本管理**：模型、Prompt、工具 Schema 作为一个版本整体管理，便于回溯。

### 12. 最近在学什么 Agent 相关的新东西，怎么判断一个新技术是真能上线还是玩具

**答题思路**

第一部分讲你真实在学的内容，选 2～3 个并说明学习方式（读论文 / 文档、跑 demo、在项目里验证），可以从 MCP、Agent 评测、上下文工程、记忆机制、多 Agent 协议、Harness、Agent 观测等方向中选你真正了解的，不要为了显得新而罗列没学过的概念。

1. **解决的是不是真实痛点**：能否对应到当前业务的具体问题，而不是为了技术而技术。
2. **可评测**：能否定义指标并在自己的数据上验证，收益是否显著（相比基线）。
3. **可控与安全**：行为是否可预测，出错时能不能兜底、回滚，权限边界是否清楚。

6. **验证方式**：先做小范围 PoC（用真实数据），再影子流量、灰度，达到预设指标才推广。

### 13. 手撕算法：多 Agent 任务调度场景题，给一组任务依赖关系，输出合法执行顺序，有环要报错

**参考答案**

结论：这是有向图的拓扑排序（类似「课程表 II」），用 Kahn 算法（入度 + 队列）：每次取入度为 0 的任务，执行后将其后继的入度减一；如果最终输出的任务数少于总数，说明存在环。

思路：

1. 建图：依赖 `a -> b`（`b` 依赖 `a`）表示 `a` 必须先于 `b`；统计每个节点的入度。
2. 把所有入度为 0 的节点入队。
3. 循环：取出节点加入结果，遍历其后继，入度减一，减为 0 则入队。
4. 结束后若结果数 < 节点总数，则存在环，抛出异常（可进一步返回环上的节点：入度仍大于 0 的节点）。

时间复杂度 O(V + E)，空间 O(V + E)。

```java
import java.util.*;

public class TaskScheduler {
    /**
     * @param tasks 所有任务 ID
     * @param deps  依赖关系，每个元素 {a, b} 表示 b 依赖 a（a 必须先执行）
     */
    public static List<String> order(List<String> tasks, List<String[]> deps) {
        Map<String, List<String>> graph = new HashMap<>();
        Map<String, Integer> indegree = new HashMap<>();
        for (String t : tasks) {
            graph.put(t, new ArrayList<>());
            indegree.put(t, 0);
        }
        for (String[] d : deps) {
            String from = d[0], to = d[1];
            if (!graph.containsKey(from) || !graph.containsKey(to)) {
                throw new IllegalArgumentException("未知任务: " + from + " -> " + to);
            }
            graph.get(from).add(to);
            indegree.merge(to, 1, Integer::sum);
        }

        Deque<String> queue = new ArrayDeque<>();
        for (String t : tasks) {
            if (indegree.get(t) == 0) queue.offer(t);
        }

        List<String> result = new ArrayList<>();
        while (!queue.isEmpty()) {
            String cur = queue.poll();
            result.add(cur);
            for (String next : graph.get(cur)) {
                if (indegree.merge(next, -1, Integer::sum) == 0) {
                    queue.offer(next);
                }
            }
        }

        if (result.size() != tasks.size()) {
            throw new IllegalStateException("任务依赖存在环");
        }
        return result;
    }
}
```

容易说漏的点：重复边会影响入度统计（要么去重，要么入度和出边保持一致）；依赖了不存在的任务要校验；同一时刻入度为 0 的任务其实可以并行，这为下一题做铺垫。

### 14. 顺着上一题：如果某个任务执行特别慢，怎么改成并行调度加超时取消加结果合并

**参考答案**

结论：把「按顺序执行」改为「就绪即执行」的 DAG 并行调度：入度为 0 的任务并行提交到线程池，任务完成后触发后继；每个任务设置超时并可取消；下游按依赖汇总上游结果。

设计要点：

1. **并行调度**：使用线程池，任务的所有依赖完成就提交执行（可用 `CompletableFuture` 按依赖组合，或者自己维护入度和完成回调）。线程池要有界，并限制对下游（大模型、工具服务）的并发。
2. **超时与取消**：每个任务有独立超时，超时后标记失败并调用 `Future.cancel(true)` 中断线程；注意被取消的任务必须响应中断（不要吞掉 `InterruptedException`），否则取消不生效；对远程调用也要设置客户端超时。整个 DAG 另有总超时。
3. **失败传播**：关键任务失败，后继任务全部标记为取消 / 跳过；可选任务失败可降级（使用默认值或跳过），不阻塞后继。
4. **慢任务处理**：除超时外，可以用对冲请求（hedged request，发起备份请求取最快者，只适用于幂等任务）；优先调度关键路径上的任务。
5. **结果合并**：每个任务的结果存入线程安全的 Map（`ConcurrentHashMap`）；后继任务从中读取依赖的结果；所有任务结束后，由汇总节点按依赖顺序和约定的结构合并，并标注每个子任务的状态（成功、超时、失败），让上层能给出「部分结果」。
6. **环检测**：调度前仍先做拓扑检查。

```java
import java.util.*;
import java.util.concurrent.*;

public class DagExecutor {
    private final ExecutorService pool;
    private final ScheduledExecutorService timer = Executors.newSingleThreadScheduledExecutor();

    public DagExecutor(ExecutorService pool) {
        this.pool = pool;
    }

    /** 带超时并可取消的单任务执行 */
    private CompletableFuture<Object> runWithTimeout(Callable<Object> task, long timeoutMs) {
        CompletableFuture<Object> cf = new CompletableFuture<>();
        Future<?> f = pool.submit(() -> {
            try {
                cf.complete(task.call());
            } catch (Throwable e) {
                cf.completeExceptionally(e);
            }
        });
        timer.schedule(() -> {
            if (cf.completeExceptionally(new TimeoutException("任务超时"))) {
                f.cancel(true); // 中断执行线程
            }
        }, timeoutMs, TimeUnit.MILLISECONDS);
        return cf;
    }

    /**
     * @param order 已经过拓扑排序的任务列表
     * @param deps  任务 -> 其依赖的任务
     */
    public Map<String, Object> execute(List<String> order,
                                       Map<String, List<String>> deps,
                                       Map<String, Callable<Object>> tasks,
                                       long perTaskTimeoutMs) {
        Map<String, CompletableFuture<Object>> futures = new LinkedHashMap<>();
        for (String id : order) {
            CompletableFuture<?>[] upstream = deps.getOrDefault(id, List.of()).stream()
                    .map(futures::get).toArray(CompletableFuture[]::new);
            futures.put(id, CompletableFuture.allOf(upstream)
                    .thenCompose(v -> runWithTimeout(tasks.get(id), perTaskTimeoutMs)));
        }
        // 结果合并：成功的放入结果，失败 / 超时的标记
        Map<String, Object> merged = new LinkedHashMap<>();
        futures.forEach((id, f) -> {
            try {
                merged.put(id, f.get());
            } catch (Exception e) {
                merged.put(id, "FAILED: " + e.getCause());
            }
        });
        return merged;
    }
}
```

说明：上面是简化的示意，因为 `deps` 中的上游任务通过 `allOf` 完成后才会启动任务，任一上游失败会让下游自然失败；若某些任务允许降级，需要对其 future 加 `exceptionally` 提供默认值。任务逻辑需要从 `Callable` 内部读取上游结果时，可以把共享的 `ConcurrentHashMap` 传入。

## HR 面

### 1. 为啥看快手直播 AI Agent 这个方向

**答题思路**

答「为什么是这个方向、这个业务、我为什么合适」三层，避免空泛的「看好 AI」：

1. **业务层面**：直播是高并发、强实时、规则复杂、运营链路长的场景，Agent 能直接作用于主播、运营、审核等真实的提效点，业务价值可衡量。
2. **技术层面**：这里的挑战是「让 Agent 在高并发业务里稳定、可控」，涉及工具治理、风险控制、观测评测，不只是调模型，和你在后端工程上的积累契合。
3. **个人层面**：你过去的经验（高并发、稳定性、中间件、RAG / Agent 实践）与岗位的要求对应，并说明你希望在这里成长的方向。
4. 用具体的细节表现你做过功课（对直播场景的理解），不要说编造的内部信息。

### 2. 你觉得自己做 Java 后端转 Agent，最值钱的能力是什么

**答题思路**

重点回答「工程化落地能力」，而不是「我会用大模型」：

1. **稳定性与高并发经验**：线程池隔离、限流降级、幂等、重试、熔断，这些直接用于 Agent 的工具调用和高峰保护。
2. **系统设计与中间件**：Redis、MySQL、MQ、搜索引擎等，用于记忆、状态、事件驱动和 RAG。
3. **风险意识**：权限、审计、数据一致性、事务边界，知道哪些事不能交给模型自觉。
4. **可观测与排障**：链路追踪、日志、指标、回放，能够把 Agent 这个「黑盒」做成可排查的系统。
5. **学习与落地结果**：你在 Agent 方向的实际学习和项目实践（只讲真实做过的）。

收尾一句：大模型的能力会越来越强，但「让它安全、稳定、可控地在生产里干活」依然是工程能力。

### 3. 前面技术面里有没有哪轮觉得自己答得一般

**答题思路**

诚实、具体、有复盘，展示成长性：

1. 选一个真实答得不够好的点（例如某个细节记不清、某个场景没有展开），不要说「都答得很好」，也不要把自己说得一无是处。
2. 说明原因：是知识盲区、表达不够结构化，还是实战经验不足。
3. 说明面后的补救：面试后你做了什么（查资料、动手验证、整理成笔记）。
4. 表明现在的理解：用一两句话说出正确思路，体现你已经弥补。
5. 收尾：这类复盘习惯也会用在工作中的故障与方案复盘上。

### 4. 如果让你做纯后端、做 Agent 平台、做业务 Agent，你选哪个

**答题思路**

先表明偏好，再说明理由和灵活性，不要显得只挑一边：

1. 给出明确选择和理由，结合你的真实优势与兴趣（例如：想做 Agent 平台能力，因为能沉淀工具治理、评测、观测等通用能力；或想做业务 Agent，因为更贴近业务价值和闭环）。
2. 对比三者：纯后端稳定、确定性高；Agent 平台偏基础设施、复用性强、需要抽象能力；业务 Agent 贴近场景、需要业务理解和快速迭代。
3. 表达开放度：你理解团队的需要，愿意先在业务 Agent 中积累真实场景，再沉淀成平台能力（或相反），后端基础在哪个方向都有用。
4. 结合岗位：说明岗位本身与你偏好的重合部分。

### 5. 直播业务晚高峰、大促、突发舆情这些节奏你能不能扛

**答题思路**

不要只说「能扛」，用事实和机制证明：

1. **态度**：理解直播业务的特点（晚高峰、大促、突发事件需要响应），并愿意承担值班与应急。
2. **经验**：如果有线上值班、大促保障、故障处理的真实经历，简要说明你当时的角色和做法；没有就说明你的理解和准备。
3. **方法**：预案（限流、降级、kill switch）、监控告警、值班机制、事前压测、事后复盘，通过机制降低对「个人硬扛」的依赖。
4. **边界**：坦诚对工作节奏的理解和对可持续性的期望，例如通过自动化和轮值提升长期效率，而不是简单地拒绝或无限承诺。

### 6. 薪资预期和手上进度

**答题思路**

不要编造数字或 offer，按真实情况回答：

1. **薪资预期**：先表达对岗位和成长的重视，再给出基于市场水平和自己能力的合理区间（用你自己的真实数字），并表示有沟通空间；也可以问清薪资结构（固定、绩效、股权等）再判断。
2. **手上进度**：如实说明目前的面试阶段和是否有其他机会，不夸大；可以说明时间节点，方便对方安排流程。
3. **态度**：表达对这个岗位的兴趣和优先级（如果确实如此），语气坦诚，不用竞争 offer 施压。

### 7. 哪天能到岗，愿不愿意先干脏活把 Agent 观测和评测体系搭起来

**答题思路**

1. **到岗时间**：按你真实的离职流程和交接时间回答，给出明确的时间或时间范围，如有可调整空间也说明。
2. **对「脏活」的态度**：明确表示愿意，并解释它的价值：观测（trace、指标、回放）和评测（评测集、回归、线上抽检）是 Agent 能否稳定迭代的基础设施，有了它才能敢改 Prompt、换模型、放开高危能力。
3. **具体打算**：入职初期会怎么做：先梳理现有链路和 bad case，建立基础指标（成功率、延迟、成本、人工介入率），搭建全链路 trace 和回放，沉淀第一版评测集，并纳入发布流程。
4. **边界**：表达愿意做基础建设，同时希望随着体系建立能参与到核心业务 Agent 的迭代中，体现主动和长期投入。
