### 3. 你们系统里 Redis 主要用在哪些场景？缓存穿透、击穿、雪崩怎么处理？

**参考答案**

场景用你线上真实的 key 来讲。这类系统里 Redis 常见四类用途：热点查询缓存、限流计数、短时占位（单飞或幂等键）、会话或验证码。每类说清过期时间和谁是数据源头。

穿透、击穿、雪崩差在失效范围。穿透是这个 key 在数据库里也不存在，请求每次穿过缓存。击穿是一个热点 key 过期的瞬间，大量请求同时回源。雪崩是很多 key 一起过期，或者 Redis 本身不可用，流量成片落到数据库。

穿透先做参数校验，再用布隆过滤器挡住一定不存在的 key。布隆会把不存在误判成可能存在，所以确认没有的结果仍写一个短 TTL 的空值。击穿对同一个 key 做单飞，只放一个请求回源；热点也可以把过期时间放进 value，过期后先返回旧值，再异步刷新。雪崩给 TTL 加随机偏移，热点由后台预热。Redis 不可用时入口限流，并准备可以拒绝的降级。

空值缓存也要过期，否则无效 key 会把内存占满。布隆只能证明「一定不存在」，「可能存在」里仍有误判。删除数据后要重建，或者改用支持删除的结构。

### 4. MySQL 事务 ACID 简单说下，你们项目里遇到过脏写或幻读吗，怎么规避？

**参考答案**

原子性靠 undo log，未提交的修改可以回滚。一致性指事务前后约束仍然成立，靠主键、唯一键、外键，以及应用把相关修改放进同一个事务。隔离性靠 MVCC 和锁，InnoDB 默认是可重复读。持久性靠 redo log 预写；`innodb_flush_log_at_trx_commit=1` 时每次提交都会刷 redo。binlog 和 redo 用内部两阶段提交对齐，`sync_binlog=1` 时已提交事务才能随复制保住。

脏写是一个事务覆盖另一个事务还没提交的写入。InnoDB 在各个隔离级别下都会把行排他锁保持到事务结束，所以不会出现这种脏写。项目里更常见的是丢失更新：应用先 `SELECT` 到内存，改完再把整行写回去，后提交的覆盖先提交的。纯 SQL 的 `UPDATE ... SET col = col + 1` 是当前读，会锁行，本身不会丢。规避应用层的丢失更新，用版本号：`UPDATE ... WHERE id = ? AND version = ?`，失败就重读重试；或者 `SELECT ... FOR UPDATE`。

幻读是同一事务里两次范围查询看到了别的事务新插入的行。可重复读下，普通 `SELECT` 走快照读，事务内复用 Read View，看不到之后才提交的新行。`SELECT FOR UPDATE` 和 `UPDATE` 走当前读，用临键锁（记录锁加间隙锁）挡住间隙插入。仍要防的是：快照读认为不存在，然后插入，中间又没有唯一索引，两个事务会各插入一行。这种用唯一索引，或先做当前读。

有真实事故就按「现象、原因、约束或锁、怎么验证」讲。没有就直接讲上面的预防。读已提交下普通更新基本不加间隙锁，唯一键冲突检查时仍可能加。

### 5. 线程池核心参数说说，你们项目中 IO 密集型和计算密集型任务分别是怎么配置线程数的？

**参考答案**

`ThreadPoolExecutor` 的参数是 corePoolSize、maximumPoolSize、keepAliveTime、时间单位、workQueue、threadFactory、RejectedExecutionHandler。

`execute` 的顺序是：工作线程数小于核心线程数，就新建核心线程；核心线程已满，任务入队；队列满了，才把线程扩到 maximum；再失败就走拒绝策略。任务入队后如果发现线程池已关闭，会把任务摘下来再拒绝。队列里有任务但一个工作线程都没有，会补一个非核心线程。因此核心线程数是 0、最大线程数大于 0 时，任务入队后仍会被执行。默认拒绝策略是 AbortPolicy，抛 `RejectedExecutionException`。另外三种是调用方自己跑、直接丢弃、丢掉队列里最老的任务。

无界队列不会满，maximumPoolSize 和拒绝策略都不会生效。`Executors.newFixedThreadPool` 用的就是无界队列，堆积时会把内存吃满。业务池用有界队列，线程工厂给线程起名。

计算密集型的线程数接近可用核数，突发用队列吸收。线程再加多，主要增加上下文切换。IO 密集型线程会堵在网络或磁盘上，初值可以用 `核数 × (1 + 等待时间 / 计算时间)`，等待时间取这条调用自己的监控，再用排队长度、超时和拒绝率校正。两种任务分池。阻塞调用很多时，可以用虚拟线程承载等待，计算仍留在小的平台线程池里。Java 21 上，虚拟线程长时间停在 `synchronized` 里会占住载体线程；这个行为从 JDK 24 起解除。

线上数字报你压测或监控之后的值，并说明队列长度和拒绝时的降级。

### 6. 场景题：一个高频查询接口，数据库扛不住，要求你设计一套带缓存、布隆过滤器、本地缓存的二级缓存方案，说下数据一致性如何保证

**参考答案**

读路径按固定顺序走：参数校验，布隆过滤器，进程内的 Caffeine，Redis，最后才是数据库。本地缓存挡热点，Redis 在实例之间共享，数据库是源头。布隆放在两级缓存之前，挡住一定不存在的 key。它会误放行，后面仍对空结果写短 TTL。标准布隆不能删除，数据删掉后定期重建；重建之前多放行的请求由空值缓存接住。

写路径用 Cache Aside，以数据库提交为准。先提交数据库，再删 Redis，再发一条缓存失效消息。各实例收到后删自己的本地 key。失效消息用可靠队列；Redis Pub/Sub 不落盘，实例重启会漏消息，只能当加速，短 TTL 才是兜底。本地缓存容量封顶，TTL 用秒级。

并发下的旧值回填靠版本：缓存 value 带上数据库的版本或更新时间，回填时发现已有更新的版本就放弃这次写入。同一个 key 用单飞，只允许一个请求回源，避免击穿。删除缓存失败就重试，并留下可补偿的记录。

这是最终一致，过期窗口是本地 TTL 加上失效延迟。余额、支付状态、风控结论不进本地缓存。写完立刻要读到自己写入的接口，绕过本地缓存，直接读 Redis 或数据库。

### 7. 你了解或使用过 AI Agent / LLM 应用开发吗？说说你对 Agent 和单纯调用 Chat API 的区别理解

**参考答案**

调用 Chat API 时，应用把提示词和历史交给模型，模型返回一段文本。要不要查库、调用哪个接口、失败了怎么办，都写在你的代码里。多轮聊天只是把上一轮文本再传进去，控制流仍在应用。

Agent 把「下一步做什么」交给模型。常见做法是 ReAct 循环：模型看到当前对话和工具清单，选出一个工具并给出参数，应用执行后把结果送回去，模型再决定继续调用还是给出最终回答，直到结束或步数用尽。它多出来的是工具集合、循环和停止条件。

副作用也不同。聊天接口答错了，用户看到的是一句错话。Agent 选错工具，可能真的去退款或改数据。所以写操作要收窄，循环要有上限，金额和状态以工具结果为准。步骤固定、规则清楚的流程用工作流编排更合适，模型负责理解自然语言和组织回复。

做过就按你的真实链路讲：工具有哪些、循环在哪一层停、写操作谁确认。没上过生产就说清楚你设计到了哪一步。

### 8. 如果让你用 Java + Spring AI / LangChain4j 封装一个内部工具调用（Tool Calling）给大模型用，你会怎么设计 Tool 注册和执行链路？

**参考答案**

每个工具是一个带契约的方法：稳定的名字、给模型看的描述、JSON Schema 参数、读写标记、超时时间。描述写成「什么时候用、参数是什么」，模型靠这段文字选工具。

注册放在启动阶段。Spring AI 用 `@Tool` 标在 Spring Bean 的方法上，`ToolCallbacks.from(...)` 扫出回调；LangChain4j 用 `@Tool` 和 `@P`，由 `AiServices` 或 `ToolProvider` 暴露。扫到的结果放进注册表，名字冲突就让启动失败。按用户权限和当前场景过滤之后，才把子集放进这一次模型请求。几十个工具全塞进去，选错的概率和 token 都会上去。内部系统如果已经用 MCP 暴露工具，可以用 Spring AI 或 LangChain4j 的 MCP Client 同步清单，再转成同一套回调。

执行链路是一个有上限的循环。模型返回工具名和参数后，注册表查找，做 JSON Schema 校验，再用当前登录用户的身份调用，忽略模型自己填的用户 id。调用有超时、熔断和审计。成功或失败都变成工具消息送回模型，直到模型给出最终文本，或达到最大步数。ChatClient、`AiServices` 可以自己跑这个循环；写操作、人工确认和步数限制需要包在工具入口或你自己的循环里。

同一轮里多个只读工具可以并行。有副作用的工具串行，并带幂等键。工具抛错要变成结构化结果给模型，避免整个请求失败之后，模型仍对用户说已经办成。

### 9. 手撕算法：两数之和（LeetCode 1）

**参考答案**

题目要求在数组里找两个下标，使对应元素之和等于 target，同一个下标不能用两次。约定恰好有一组解。

用哈希表记下已经看过的值和下标。扫到 `nums[i]` 时先查 `target - nums[i]` 是否出现过，出现过就返回那两个下标，否则再把当前值放进表。先查再放，元素就不会和自己配对。时间 `O(n)`，空间 `O(n)`。

先排序再双指针是 `O(n log n)`，而且排序会打乱下标，要额外记住原下标。这道题要的是下标，哈希一次遍历就是常规解法。

```java
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> indexByValue = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer other = indexByValue.get(target - nums[i]);
        if (other != null) {
            return new int[] {other, i};
        }
        indexByValue.put(nums[i], i);
    }
    return new int[0];
}
```

### 3. 项目里如果有消息队列（Kafka/RocketMQ），为什么引入 MQ，怎么保证消息不丢失、不重复消费？

**参考答案**

引入消息队列，是为了把主链路和耗时、可延迟的副作用拆开，例如通知、积分、对账，同时让突发流量变成可堆积的消费。代价是异步和最终一致，所以要有堆积告警，主流程不能依赖「消息马上被消费完」。没有用过就直接说没有，再讲你会怎么设计。

不丢要三段一起做。生产端：Kafka 使用 `acks=all`、重试和幂等生产者，同一连接上未确认的批次不超过 5，并把 `min.insync.replicas` 设到至少 2。ISR 里如果只剩一个副本，领导副本宕机后已确认的消息仍可能丢。同时关闭 unclean leader election，避免落后副本当选后截断已确认的消息。RocketMQ 的关键消息用同步发送、同步刷盘和同步复制。业务库和发消息要同一结果时，用本地消息表或 RocketMQ 事务消息：先发半消息，本地事务成功后再提交，失败则回滚，状态不明则由 Broker 回查。消费端关闭自动提交，处理成功后再提交 offset 或返回成功。

处理完成但位点还没提交时进程崩溃，消息会再投递一次，所以消费一定要幂等。用业务唯一键做数据库唯一索引，或用状态机：只有「待处理」才能推进。Kafka 的事务能保证 Kafka 内部的读写精确一次，写到 MySQL 的副作用仍然要靠这层幂等。失败多次就进死信，避免一条坏消息堵住分区。

### 4. 场景题：银行某业务需要对外提供 OpenAPI，要求限流、鉴权、防重放攻击，请设计网关层方案

**参考答案**

合作方只访问网关，业务服务不暴露公网。网关按这个顺序处理：按来源做粗限流，验签，防重放，按应用和接口做细限流，检查 scope，再路由到内部服务。防重放放在验签之后，避免无效请求往 Redis 里灌 nonce。

鉴权分两层。传输层用 TLS，合作方使用双向证书。应用层对方法、路径、时间戳、nonce 和报文体摘要签名，算法用双方约定的 HMAC 或 SM2。密钥放在密钥管理系统里，日志只留 keyId。验签通过后，按 appId 的 scope 判断能不能调用这个 API。网关再换成内部身份转发，下游不信任来自公网的原始报头。

防重放靠时间窗加 nonce。时间戳超出窗口就拒绝，窗口按时钟误差留出几分钟量级的余量。nonce 用 `SET key value NX EX`，过期时间等于窗口；设置成功才放行。签名必须覆盖时间戳和 nonce，否则这两项可以被拆掉。比较签名时用常量时间比较。

限流用令牌桶，维度至少有 appId 加接口，写接口的配额单独更紧。计数放在 Redis，用 Lua 保证扣减原子。超限返回 429，并给出可重试的等待时间。验签本身按 IP 或 appId 做粗限流，防止 CPU 被打满。业务上的合法重试另给 Idempotency-Key，和防重放的 nonce 分开：nonce 挡的是同一份报文被再次提交。

审计记录 appId、接口、traceId、结果码和耗时。报文按脱敏要求留存，密钥和完整敏感字段不进普通日志。

### 5. 场景题：设计一个「智能工单助手 Agent」，用户可以自然语言查订单、判断能否退款、调内部系统创建退款单，说整体架构、Tool 定义、多轮对话记忆管理方案

**参考答案**

链路是：渠道接入和登录鉴权，加载会话，模型在允许的工具里选择下一步，工具网关执行，结果写回会话，模型再组织回复。退款能不能办，由规则服务决定；模型负责理解说法、补齐参数和解释结果。

工具只留三个，名字和职责固定。`queryOrder` 按订单号查询，并校验订单属于当前用户。`checkRefund` 只读，返回是否可退、原因和金额，金额由服务端计算。`createRefund` 只接收订单号和已经确认过的预览号，再次调用规则服务，用幂等键创建退款单。模型传来的金额不作为入账依据。没查过单、没有确认，就不允许调用创建。

记忆分成三块。当前窗口保留最近若干轮的用户消息、模型回复和工具结果，按 sessionId 放在 Redis 或数据库。槽位单独存：订单号、规则结论、待确认的预览。较早的工具原文压成一句摘要，摘要里保留订单号和结论。缺订单号就追问，不猜测。用户换一个订单号时覆盖槽位，并让上一张退款预览失效。

写操作先给用户展示服务端生成的预览，用户确认的是这份快照。循环有最大步数。查询失败就告诉用户失败原因，不让模型编一笔退款。

### 6. RAG 了解吗？端到端流程说一下，文档切分策略、检索不准怎么优化（混合检索/重排）？

**参考答案**

RAG 是先检索证据，再把证据和问题一起交给模型生成。制度、条款和产品规则以检索到的原文为准。

离线流程：解析文档，去掉页眉、目录和过期版本，按章节、条款或一问一答切分，给每块记下出处、版本和权限，同时建向量索引和关键词索引。在线流程：多轮问题先改写成独立问句，做混合召回，合并之后重排，取少量片段放进提示词，并要求回答能对应到片段。没有够格的证据就拒答。

切分按语义边界。固定字数硬切会把条件和结论拆开。块太小会丢上下文，块太大时相似度被无关句子稀释。实操上可以检索较小的块，送给模型时带回它所在的父级段落。表格和制度条款尽量整块保留。

检索不准时先看候选集里有没有正确文档。专有名词、制度编号用关键词，说法不同但意思接近的用向量。权限和生效版本放进召回条件，两边的名次用 RRF 这类方法融合，再用交叉编码器对前几十条重排。用一组真实问题和应命中的文档来看召回，再看回答是否只使用了这些证据。

重排只能重排已经召回到的内容。正确段落没进候选集时，先改切分、索引和查询，再加大重排模型。

### 7. Agent 执行 Tool 时怎么防止 LLM 幻觉导致误操作（如错误退款）？你会在代码层做哪些防护（参数校验/幂等/人工确认节点）？

**参考答案**

模型可以建议调用哪个工具，不能充当授权人。退款是否允许、金额是多少，在工具里面重新计算。

参数校验放在执行前。名字必须在注册表里，参数必须符合 JSON Schema，订单号要属于当前登录用户。创建退款只接受上一跳 `checkRefund` 产生的预览号，拒绝模型现编的订单号和金额。工具用会话里的用户身份访问下游，忽略参数里的 userId。

幂等键用用户、订单和动作组成，落唯一索引。重复调用返回同一张退款单，超时重试也走这个键。状态机只允许从「可退」进入「退款中」。

人工确认绑的是服务端预览快照：订单号、金额、原因都展示给用户。用户同意之后，执行这份快照。确认之后模型再次改金额，网关仍按快照执行。超过金额阈值或规则返回边界结果时，转人工，不自动创建。

另外加上工具白名单、最大步数和审计。工具失败时，返回给用户的是失败，模型不能把错误结果说成已经退款。只读工具和写工具分开授权，默认只把只读工具放进自动循环。

### 8. MCP（Model Context Protocol）是什么，和传统 Function Calling / Tool Calling 比有什么优势？

**参考答案**

MCP 是宿主和外部能力之间的开放协议，基于 JSON-RPC。一个 MCP Server 用 `tools/list`、`tools/call` 暴露工具，也可以提供只读资源和提示词模板。Agent 或 IDE 作为 Host，通过 Client 连接。传输常用标准输入输出，或可流式的 HTTP。工具跑在独立进程里，换一个支持 MCP 的宿主还能复用。

Function Calling / Tool Calling 是模型接口：这次请求里带上函数名和 JSON Schema，模型返回要调用的名字和参数，由应用在自己的进程里执行。它规定了模型怎么表达一次调用，没有规定工具怎么发现、怎么部署、怎么换宿主。

MCP 的优势在发现和边界。工具清单可以动态拉取，发布和权限跟某个业务进程拆开，一个订单查询可以同时给内部 Copilot 和别的宿主用。资源适合放制度文档这类只读上下文，不必把所有东西都包成函数。

模型仍然要通过 Function Calling 或同类机制决定调用哪一个工具。Host 的工作是把 MCP 工具转成该模型能读的函数定义，再跑调用循环。接入时审核工具来源和描述，执行时继续做鉴权、幂等和审计。

### 9. 手撕算法：二叉树的最大深度（LeetCode 104）

**参考答案**

最大深度是从根到最远叶子的节点个数。空树是 0，只有根是 1。

递归的定义就是答案：空节点深度为 0，非空节点是 1 加上左右子树深度的较大值。每个节点访问一次，时间 `O(n)`。递归栈的空间是树高，平衡树 `O(log n)`，退化为链表时 `O(n)`。树很高、担心栈溢出时，改成显式栈，或者用层序遍历逐层计数，层序的额外空间是最宽那一层的节点数。

```java
public int maxDepth(TreeNode root) {
    if (root == null) {
        return 0;
    }
    int left = maxDepth(root.left);
    int right = maxDepth(root.right);
    return Math.max(left, right) + 1;
}
```

### 4. 分布式锁在你们项目里的使用场景，Redis 实现分布式锁要注意哪些点（续期/误删/集群下红锁）？

**参考答案**

能用数据库唯一键或状态机挡住的重复，就不必再加锁。Redis 锁适合用来减少并发重复，例如多实例定时任务、缓存重建单飞。资金扣减这类不能双成功的操作，以数据库唯一约束或条件更新为准，Redis 锁只减少并发重叠。场景讲你真实用过的那一个；没用过就讲你会放在哪类任务上。

加锁用 `SET key value NX PX ttl`。value 是持有者唯一标识，过期时间必须设置。解锁用 Lua：先比较 value，相同再删除。分成 `GET` 再 `DEL` 两步时，锁可能已经过期并被别人拿到，你的删除会把别人的锁删掉。

续期只在业务还没做完、并且 value 仍是自己时延长 TTL。客户端停了，续期也要停，锁靠过期释放。看门狗和业务线程一起退出。长时间 GC 如果超过 TTL，另一个客户端会拿到锁，原来的线程恢复后会以为自己还持有。所以任务本身要幂等，关键资源侧再校验一个单调递增的 fencing 令牌，旧持有者的写入会被拒绝。

Redis Cluster 里一个 key 只落在一个主节点，主从复制是异步的，主宕机切换时这把锁可能丢。红锁要向多套互相独立的 Redis 主节点加锁：多数节点加锁成功，并且扣掉耗时和时钟误差后剩余有效期仍够用，才算持有；没拿到多数就释放已经加到的锁。进程长时间暂停或时钟跳动时，两方仍可能同时认为自己持有锁。把锁放进一个 Redis Cluster，key 仍然只在一个主节点上，构不成红锁。不能双执行的互斥，用数据库条件更新，或 etcd 的租约加单调版本号。

### 5. 场景题：假设要做一个企业级 AI Copilot，接入公司几十个内部系统的 API 作为 Tool，你怎么设计 Tool 注册中心、权限隔离、审计日志和调用限流？

### 9. 手撕算法：反转链表（LeetCode 206）

**参考答案**

用三个指针原地反转。`prev` 开始是空，`curr` 从头节点往后走。每次先记下 `curr.next`，再把 `curr.next` 指回 `prev`，然后两个指针一起前进。循环结束时 `curr` 是空，新的头是 `prev`。

空链表和只有一个节点时，循环不会改错：空链表直接返回空，单节点的 next 被置空后返回它自己。时间 `O(n)`，额外空间 `O(1)`。递归写法更短，栈空间是 `O(n)`，链表很长时用迭代。

```java
public ListNode reverseList(ListNode head) {
    ListNode prev = null;
    ListNode curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

4. 提前看你投的部门公开信息。没查清就问面试官这个组负责什么，不要猜内部组织架构。

### 3. 你觉得自己最大的优势和不足分别是什么？

**答题思路**

优势和不足各一个，都要有事实。优势对齐这个岗位在乎的稳定和协作。

1. 优势用一件事证明。例如线上问题你能追到可复现的请求，方案里会写失败和回滚，或者跨角色时你先把口径对齐。
2. 讲完优势停住。学习能力强、能抗压这类说法，后面没有事实就不要用。
3. 不足选一个正在改、而且不伤及资金和数据正确性的点。例如以前容易先写实现，现在会先写一页取舍、风险和回滚再动手。
4. 补上你已经采取的动作，让不足变成改进中的习惯。粗心、不熟悉 Java 不要当答案。

### 4. 项目中遇到过和同事或产品经理意见不合吗，怎么处理的？

**答题思路**

选一次已经结束的分歧，用 STAR 讲，两分钟以内。不要贬低产品或同事。

1. 背景：分歧是范围、排期、规则，还是技术方案。先用你的话复述对方要保的目标。
2. 你的立场：技术约束是什么，例如一致性、权限、回归成本。用用户影响或风险说明，不用「我更专业」。
3. 动作：你补充了什么证据，做了什么折中，谁拍板。拍板的人如果不是你，说明你怎么执行的。
4. 结果：最后交付了什么，关系有没有继续合作。若你后来发现自己判断错了，可以说你怎么调整的。

### 5. 你能接受的工作强度是怎样的，对加班怎么看？

**答题思路**

态度落到具体场景。招银看重稳定，回答体现你能长期持续。

1. 上线、故障和明确的版本节点你可以投入，也接受说好的值班。用你真实有过的一次经历，没有就不要编时长。
2. 日常问题你倾向用发布窗口、回滚、限流和值班交接来消化，而不是靠同一个人一直在线。
3. 问清这个组的发布频率和值班方式，再说明你的接受范围。
4. 避免两个极端：完全不加班，或者任何时候都可以在线。

### 6. 你的职业规划是什么（3～5 年）？

**答题思路**

给出近三年和五年的范围，并和银行科技岗位的稳定性对齐。

1. 三年内：独立负责一个业务域的正确性和稳定性，能对故障、回滚和一次变更负责。技术深度落在你真实的方向上，例如 Java 主链路、消息和一致性，或带权限的工具调用。
2. 五年：能做选型并带新人完成一个小模块，关键代码仍然自己写。管理以你已经能对一条链路负责为前提。
3. 说明你希望在一个业务域里做深。跳槽频率、创业、把这份工作当过渡，都不要讲。
4. 问这个组更需要独立负责模块的人，还是带小团队的人，把你的规划和岗位对齐。

### 7. 目前有其他 offer 吗，倾向怎么选？

**答题思路**

有没有 offer 都按真实情况说。不编公司、职级和薪资数字。

1. 还在流程中就说在流程中。没有其他 offer 也直接说。已经拿到的，只讲你愿意讲的程度，不贬低其他家。
2. 选择标准按这个顺序：事情和业务是否匹配、你能不能对一块系统负责、团队协作方式、总包。总包等对方给出正式口径再比较。
3. 如果招银是你的重点，说明重点在这里的原因，接上你对稳定性和业务复杂度的看重。
4. 被追问期望薪资时，用你自己的现有总包和市场判断给区间。对方没问，就不要在这题里主动报价。

### 8. 你还有什么想问我们的？

**答题思路**

准备三个问题，按面试里还没听清楚的信息选两个问。问业务和协作，薪资等对方开口。

1. 这个岗位前几个月最重要的交付是什么，成功看起来是什么样。
2. 团队负责的业务、发布窗口和值班怎么排。
3. 岗位如果包含 AI：现在有没有已经在线上的工具调用，权限和审计归哪个角色。
4. 新人怎么熟悉业务规则和变更流程。

第一问不要问加班多不多。对方已经介绍过的内容不要再问一遍。
