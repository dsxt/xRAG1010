## 面试感受

拼多多这个岗位确实偏难，尤其二面、三面会一直往深处追问：LangGraph 状态图的细节、多 Agent 协调的坑、RAG 召回率从 60% 怎么拉到 85%，答不出来就会继续追。面试官水平不错，但不要被他带节奏。遇到概念性问题先给结论再展开，不要一上来就背书。遇到压力题要稳住，承认不知道也比瞎编强，面试官看的是思路是否清晰、表达是否明确。要自信一点，你是去做 Agent 开发的，不是去考博士。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按"我是谁 → 做过什么 → 为什么匹配"组织：

1. 一句话说明背景：学历或工作年限，以及当前方向（大模型应用 / Agent 开发）。
2. 挑 1 到 2 个与 Agent、RAG 最相关的项目，说明你的角色、技术栈和可量化的结果（如召回率、延迟、完成率的变化），数字必须真实。
3. 补充工程能力：评测、线上排障、性能优化，以及你对 LangGraph、MCP 等技术的了解。
4. 最后一句落到岗位：说明你想做 Agent 落地，以及你的经历如何支撑这个岗位。

### 2. 介绍一下你做过的 AI Agent 或大模型应用项目，你在其中负责哪些模块

**答题思路**

用"背景 → 架构 → 我的模块 → 难点与结果"四步讲，不要编造数据：

1. **业务背景**：解决什么问题，用户是谁，为什么需要 Agent 而不是固定流程。
2. **整体架构**：一句话概括，例如"意图路由 + RAG + 工具调用 + 生成"，必要时配一张图。
3. **你负责的模块**：明确到具体模块，如检索链路、工具层、编排、评测或提示词，并说明设计取舍（为什么选这个框架、这个向量库、这种切分）。
4. **难点与结果**：挑一个最有说服力的问题，讲清"现象 → 定位 → 方案 → 指标变化"。
5. 提前准备好深挖点：为什么这样设计、有没有对比方案、上线后怎么监控。

### 3. AI Agent 和普通的 LLM Chatbot 本质区别是什么，Agent 的核心组成模块有哪些

**参考答案**

本质区别：Chatbot 是"一问一答的文本生成"，Agent 是"以目标为导向、能自主决策并通过工具作用于外部环境的闭环系统"。

- Chatbot 只靠模型参数和上下文生成回复，没有行动能力，也不会自己拆解任务。
- Agent 会在"感知 → 规划 → 行动 → 观察 → 反思"的循环中推进，直到目标完成或触发终止条件。

核心模块：

1. **LLM（大脑）**：负责理解、推理和决策。
2. **规划（Planning）**：任务拆解，以及 ReAct、Plan-and-Execute、反思等策略。
3. **记忆（Memory）**：短期记忆（上下文）和长期记忆（向量库或 KV 存储）。
4. **工具（Tools）**：API、数据库、代码执行器、检索等，通过 Function Calling 或 MCP 接入。
5. **执行与控制**：循环控制、状态管理、错误处理、人工介入、安全护栏。

容易漏的点：Agent 比 Chatbot 更难评测，也更不可控，所以迭代上限、权限控制和可观测性是工程重点。

### 4. 意图识别在对话系统中怎么做，如何用 LLM 做意图分类，少样本和零样本怎么做

**参考答案**

结论：意图识别可以用规则、传统分类模型、Embedding 相似度或 LLM 来做，生产中常见做法是分层组合：简单高频意图走轻量模型，长尾和复杂意图走 LLM。

**用 LLM 做分类**

- 在提示词里定义意图集合，并为每个意图写清定义和边界。
- 要求输出结构化结果（JSON 或枚举），用 Structured Output 或约束解码保证格式，`temperature` 设为 0。
- 必须设置"其他 / 未知"类，低置信度时反问澄清，避免强行归类。

**零样本（Zero-shot）**：只给意图定义和输出格式，不给示例。成本低、上手快，但边界模糊的意图容易混淆。

**少样本（Few-shot）**：每类给 3 到 5 个示例，重点放易混淆的边界样例和反例。示例较多时，用 Embedding 按当前问题动态检索最相似的示例（动态 Few-shot），比固定示例更准、更省 Token。

**其他要点**

- 多轮对话要结合历史做指代消解后再分类。
- 一句话可能含多个意图，需要支持多标签或拆分。
- 延迟敏感时，可以用 LLM 标注数据，再蒸馏出小模型或 Embedding + 分类器上线。
- 用标注集评估准确率、召回率和混淆矩阵，持续迭代。

### 5. RAG 的完整流程是什么，离线和在线分别做什么

**参考答案**

RAG 的作用是在生成前检索外部知识注入上下文，缓解模型知识过时和幻觉。

**离线阶段（建库）**

1. 文档加载与解析（PDF、Word、网页、表格，必要时做 OCR 和版面分析）。
2. 清洗和结构化，保留标题层级、页码等元数据。
3. 切分（Chunking）。
4. Embedding 向量化。
5. 写入向量库，同时可建 BM25 倒排索引，并存储元数据。

**在线阶段（查询）**

1. 查询理解：指代消解、Query 改写、意图判断。
2. 检索：向量检索，或向量 + BM25 的混合检索，可带元数据过滤。
3. 重排（Rerank）：用交叉编码器精排，取 Top-K。
4. 组装 Prompt：拼接上下文，写明"依据资料回答，资料不足则说明"。
5. LLM 生成，附带引用和溯源。
6. 后处理：幻觉校验、拒答和日志记录，用于评测和迭代。

容易漏的点：RAG 效果取决于整条链路，应分别评估检索（召回率、精确率）和生成（忠实度、相关性），不能只看最终答案。

### 6. 文档切分策略有哪些，RecursiveCharacterTextSplitter 原理及中文场景注意事项

**参考答案**

**常见切分策略**

- 固定长度切分，可设置重叠（overlap）。
- 按分隔符 / 递归字符切分。
- 按文档结构切分（Markdown 标题、HTML 标签、PDF 版面段落）。
- 语义切分：按句子 Embedding 相似度的突变点断开。
- 父子块（Parent-Child）：小块用于检索，命中后返回所在的大块给模型。
- 针对表格和代码的专门切分。

**RecursiveCharacterTextSplitter 原理**

按优先级依次尝试一组分隔符，默认是 `["\n\n", "\n", " ", ""]`。

1. 先用最高优先级的分隔符切开文本。
2. 把相邻小片段合并到不超过 `chunk_size`，相邻块保留 `chunk_overlap`。
3. 如果某个片段仍然超长，就用下一级分隔符递归切分。

这样可以尽量保持段落、句子的完整，只有迫不得已才会按字符硬切。

**中文场景注意**

- 中文词之间没有空格，默认的空格分隔符几乎无效，应加入中文标点：`["\n\n", "\n", "。", "！", "？", "；", "，", ""]`。
- `chunk_size` 默认按字符数计，而模型限制按 Token 计，中文字符与 Token 的比例与英文不同，需要用 token 计数函数（如基于 tokenizer 的 length_function）。
- Embedding 模型有最大输入长度，块不能超过。
- 块过小会丢失上下文，过大会稀释语义，要通过检索评测来调参。

### 7. 向量检索召回率低怎么优化，混合检索（Hybrid Search）、Query 改写、Rerank 的做法

**参考答案**

结论：先建立带标注的评测集（如 Recall@K），再按"文档解析 → 切分 → Embedding → 检索 → 重排"逐层定位，避免凭感觉调参。

1. **索引侧**：改善解析质量，调整切分粒度，并给块加标题或摘要等上下文；选择更适合领域和中文的 Embedding 模型，必要时微调；采用父子块。
2. **混合检索**：向量检索擅长语义，BM25 擅长关键词、专有名词和编号，两者互补。两路各取 Top-N 后融合，常用 RRF，即 score = Σ 1/(k + rank)，k 常取 60；也可以加权融合。
3. **Query 改写**：多轮对话先做指代消解和补全；Multi-Query 生成多个同义问法；HyDE 先生成假设答案再检索；复杂问题拆分为子问题；Step-back 先抽象出更通用的问题。
4. **Rerank**：先粗召回较多候选（如几十条），再用交叉编码器（如 bge-reranker 一类）精排，取 Top 5 到 10 送给 LLM。
5. **检索参数**：调整 `top_k`、相似度阈值、HNSW 的 `ef_search` 等；利用元数据过滤缩小范围。

容易漏的点：召回率低有时是文档根本没入库或解析错误，而不是向量模型的问题，所以要先排查数据。

### 8. LangChain 的核心组件有哪些，LCEL 是什么，相比旧版 Chain 有什么优势

**参考答案**

**核心组件**：Model（LLM / ChatModel / Embedding）、Prompt 模板、Output Parser、Retriever 和向量库、Document Loader 与 Text Splitter、Tool、Memory 或状态管理、Agent、Callback 和追踪（LangSmith）。

**LCEL（LangChain Expression Language）**：用统一的 `Runnable` 接口，通过管道符 `|` 把组件声明式地组合起来，例如 `prompt | model | parser`。

**相比旧版 Chain（如 `LLMChain`、`SequentialChain`）的优势**

- 统一接口：所有组件都支持 `invoke`、`stream`、`batch` 及对应异步方法。
- 原生流式输出，并可流式输出中间步骤。
- 自动并行：`RunnableParallel` 可并发执行多个分支。
- 内置重试和 fallback 等容错能力。
- 与 LangSmith 集成，每一步可追踪。
- 组合更灵活，并可通过 `RunnableLambda`、`RunnablePassthrough` 接入自定义逻辑。

补充：LCEL 适合线性或简单分支的流程；带循环、状态和条件分支的复杂 Agent 更适合 LangGraph，新版本里 LangChain 的 Agent 也建立在 LangGraph 之上。

### 9. Function Calling / Tool Calling 原理是什么，模型怎么决定调哪个工具、传什么参数

**参考答案**

结论：模型本身不执行工具，它只是在看到工具的 JSON Schema 后，输出"要调用哪个工具、参数是什么"的结构化文本，由应用代码实际执行并把结果回传。

**流程**

1. 请求时把工具列表（名称、描述、参数 JSON Schema）一起传给模型。
2. 模型根据用户问题和工具描述，决定直接回答，还是返回一个或多个 `tool_call`（工具名 + JSON 参数）。
3. 应用解析并校验参数，执行真实函数或 API。
4. 把结果以 tool 角色消息追加到对话中，再次调用模型。
5. 模型据此继续调用工具，或生成最终回答。

**模型如何决策**：模型经过专门的工具调用数据微调，基于工具名称、描述、参数说明与当前上下文做语义匹配，并按 Schema 生成参数。所以工具描述写得越清晰（用途、适用与不适用场景、参数含义和示例），选择越准。

**工程要点**

- `tool_choice` 可设为自动、必须调用或指定某个工具。
- 部分模型支持并行工具调用，也支持严格模式（strict）来保证参数符合 Schema。
- 参数必须在服务端校验，不能直接信任模型输出。
- 对有副作用的工具要做权限控制和人工确认。

### 10. Prompt 工程的基本原则，Few-shot、CoT、系统提示词怎么写能减少幻觉

**参考答案**

**基本原则**：指令清晰具体；给出角色、任务、约束和输出格式；提供必要的上下文；复杂任务拆成步骤；用结构化输出；迭代并用评测集验证，而不是只凭几条样例判断好坏。

**减少幻觉的做法**

- **系统提示词**：明确"仅依据提供的资料回答；资料中没有就回答不知道，不要猜测"；要求给出引用来源；限定能力边界和拒答场景；把规则放在前面并保持稳定。
- **Few-shot**：给出正确示例，同时包含"资料不足时拒答"的示例，让模型学到边界；示例要与真实分布一致且格式统一。
- **CoT**：让模型先分步推理再给结论，适合计算和多步推理；生产中可以让推理放在内部字段，只向用户输出结论。注意 CoT 并不保证推理忠实，仍需验证。
- **其他手段**：降低 `temperature`；用 RAG 提供事实依据；要求引用原文再作答；用第二次校验或结构化输出约束。

容易漏的点：提示词只能缓解幻觉，不能根除，还需要检索质量、校验和评测配合。

### 11. Agent 出现死循环或无限调工具怎么防范，最大迭代次数、循环检测怎么设计

**参考答案**

结论：用"硬上限 + 重复检测 + 进展检测 + 预算"多层兜底，并在触发后优雅降级。

1. **最大迭代次数**：限制总步数或工具调用数，如 LangGraph 的 `recursion_limit`；同时设置单次任务的超时、Token 预算和费用预算。
2. **循环检测**：记录最近 N 次（工具名 + 规范化参数）的哈希，相同调用连续或高频重复时中断；也可检测状态没有变化，或输出高度相似。
3. **进展检测**：判断每一步是否获得新信息、子目标是否推进，长期无进展就终止。
4. **提示层**：把已执行的步骤和失败原因放进上下文，提示"不要重复同样调用，换思路或直接回答"。
5. **工具层**：失败要返回明确的错误信息，而不是空结果，否则模型会反复重试；限制重试次数。
6. **触发后的处理**：优雅降级，输出已有信息、说明未完成原因，或转人工，并记录日志用于分析。

### 12. 简述 ReAct 范式（Thought-Action-Observation）的执行流程

**参考答案**

ReAct 是 Reasoning + Acting 的结合：让模型在"思考 → 行动 → 观察"的循环中推进，每一步的推理都基于环境反馈。

**流程**

1. **Thought**：模型根据问题和已有信息，分析下一步该做什么。
2. **Action**：选择工具并给出参数，如搜索、查询、计算。
3. **Observation**：工具执行后，把结果作为观察返回给模型。
4. 重复以上步骤，直到模型判断信息足够，输出 **Final Answer**。

**价值**：推理让行动更有针对性，观察让推理有事实依据，因此可以减少纯推理产生的幻觉，轨迹也可解释。

**局限**：步数多导致延迟和成本高；推理可能出错并累积；可能陷入循环，所以需要迭代上限和循环检测；工具结果过长会撑满上下文。现在常见实现是用 Function Calling 来承载 Action。

### 13. 手撕算法：合并区间（LeetCode 56）

**参考答案**

思路：按区间起点排序，遍历时如果当前区间的起点不大于结果中最后一个区间的终点，说明重叠，更新终点为二者最大值；否则作为新区间加入结果。

时间复杂度 O(n log n)（排序主导），空间复杂度 O(log n) 到 O(n)（取决于排序实现，不含结果）。

```python
def merge(intervals):
    intervals.sort(key=lambda x: x[0])
    res = []
    for start, end in intervals:
        if res and start <= res[-1][1]:
            res[-1][1] = max(res[-1][1], end)
        else:
            res.append([start, end])
    return res
```

注意点：终点要取 `max`，因为后一个区间可能被前一个完全包含；`[1,4]` 与 `[4,5]` 边界相接也算重叠，需要合并。

### 2. 讲一下你们项目中 Agent 的整体架构，规划、记忆、工具、执行各层怎么设计的

**答题思路**

4. **工具层**：工具如何注册和描述，参数怎么校验，权限和幂等如何控制，是否通过 MCP 接入。
5. **执行层**：用什么框架编排（如 LangGraph）；超时、重试、降级、人工介入如何设计。
6. **横切关注点**：日志追踪、评测、安全护栏、成本和延迟。
7. 准备一个"如果重做会改什么"的反思，体现判断力。不要编造项目里没有的细节。

### 3. LangGraph 和 LangChain AgentExecutor 的区别，为什么复杂 Agent 要用 LangGraph

**参考答案**

结论：`AgentExecutor` 是封装好的固定循环（模型 → 工具 → 模型），灵活度低；LangGraph 把流程显式建模为带状态的图，能表达循环、分支、并行和持久化，更适合复杂 Agent。

| 维度 | AgentExecutor | LangGraph |
| --- | --- | --- |
| 控制流 | 内置黑盒循环 | 节点、边、条件边显式定义 |
| 状态 | 隐式 | 显式共享 State，可自定义 reducer |
| 循环与分支 | 难以自定义 | 原生支持 |
| 持久化 | 无内置 | Checkpointer，支持恢复和时间回溯 |
| 人工介入 | 较难 | 原生中断（interrupt）与恢复 |
| 多 Agent | 不方便 | 可用子图和多节点实现 |
| 流式与调试 | 有限 | 细粒度流式、可视化、可追踪 |

复杂 Agent 需要的正是这些能力：可控的流程、可恢复的状态、人工审批、多 Agent 协作，以及对每一步的可观测。补充：`AgentExecutor` 已被视为旧接口，新版本推荐基于 LangGraph 的 Agent 实现。

### 4. LangGraph StateGraph 怎么定义节点、边和条件分支，checkpointer 的作用是什么

**参考答案**

**定义方式**

1. 定义 State（常用 `TypedDict` 或 Pydantic），可用 `Annotated[list, add_messages]` 这类 reducer 指定字段如何合并更新。
2. 用 `add_node` 添加节点，节点是接收 State、返回部分更新的函数。
3. 用 `add_edge` 添加普通边，用 `START`、`END` 标记起止。
4. 用 `add_conditional_edges` 添加条件分支：路由函数根据 State 返回下一个节点名。
5. `compile()` 得到可执行的图。

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]

def route(state: State):
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

builder = StateGraph(State)
builder.add_node("agent", agent_node)
builder.add_node("tools", tool_node)
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", route, {"tools": "tools", END: END})
builder.add_edge("tools", "agent")

graph = builder.compile(checkpointer=MemorySaver())
graph.invoke({"messages": [("user", "hi")]},
             config={"configurable": {"thread_id": "t1"}})
```

**checkpointer 的作用**：在每个执行步骤后保存 State 快照，按 `thread_id` 区分会话。它可以带来：

- 多轮对话的会话记忆（短期记忆）。
- 故障后从断点恢复。
- 人工介入：在 `interrupt` 处暂停，等待审批后继续。
- 时间回溯（time travel）：回到历史状态重新执行或分叉，便于调试。

生产环境应使用持久化实现（如 SQLite、Postgres），而不是内存版。跨会话的长期记忆则要用 Store，而不是 checkpointer。

### 5. 多 Agent 协作的常见模式（Orchestrator-SubAgent、Pipeline、Debate、Swarm），分别适合什么场景

**参考答案**

结论：模式选择取决于任务是否可拆分、步骤是否固定、是否需要交叉验证，以及对可控性和成本的要求。

- **Orchestrator-SubAgent（主管 - 子 Agent）**：主 Agent 负责拆解和分派，子 Agent 专注各自领域，再汇总结果。适合任务可拆分、需要统一控制的场景，如客服路由、研究助手。优点是可控、职责清晰；缺点是主管容易成为瓶颈和单点。
- **Pipeline（流水线）**：Agent 按固定顺序串联，每一步输出是下一步输入。适合流程固定的内容生产和数据处理，如检索 → 分析 → 撰写 → 审核。优点是简单、可预测；缺点是缺乏灵活性，前面出错会向后传递。
- **Debate（辩论 / 评审）**：多个 Agent 提出方案并互相质疑，或由评审 Agent 打分。适合需要提高准确性或降低偏见的场景，如代码评审、决策和事实核查。成本高，需要设置终止条件。
- **Swarm（群体 / 去中心化交接）**：Agent 之间根据上下文自行交接（handoff），没有固定中心。适合开放式、动态路由的对话场景。灵活，但行为难预测，调试难。

共同的坑：上下文在 Agent 间传递会丢失或膨胀，需要定义清晰的共享状态；要设置终止条件，避免互相循环；Token 成本和延迟随 Agent 数量增长。不要为了"多 Agent"而多 Agent，单 Agent 加工具能解决的就不要拆。

### 6. 工具过多时模型选错工具怎么优化，工具路由、动态加载、工具描述精调的做法

**参考答案**

结论：核心是减少模型一次需要判断的候选数量，并让每个工具的描述足够有区分度。

1. **工具路由 / 检索**：把工具的名称和描述做 Embedding，根据用户问题先检索 Top-K 相关工具，再交给模型选择；也可以先做意图分类，再选对应的工具组。
2. **分层选择**：先选类别（订单、物流、售后），再在类别内选具体工具。
3. **动态加载**：按对话阶段或状态只暴露相关工具，比如在 LangGraph 的不同节点绑定不同工具集；通过 MCP 按需加载，避免一次性塞入全部 Schema 撑大上下文。
4. **描述精调**：写清"何时用、何时不用"，名称体现动作和对象，参数含义和取值范围明确，必要时给调用示例；合并功能重叠的工具，减少歧义。
5. **参数约束**：用枚举和必填项限制参数空间，降低误填。
6. **兜底**：对高风险工具做二次确认；用评测集统计工具选择准确率，针对混淆的工具对重点优化；必要时微调模型。

### 7. Agent Memory 分哪几类（短期/长期/情节记忆），超长对话如何压缩上下文，摘要和向量召回怎么做

**参考答案**

**记忆分类**

- **短期记忆**：当前会话的上下文和状态，存在 Prompt 中或 checkpoint 里。
- **长期记忆**：跨会话保留的信息，如用户偏好、画像、事实，存在向量库或 KV 中。
- **情节记忆（Episodic）**：过去具体经历和交互轨迹，可用于参考成功或失败的案例。
- 还常见语义记忆（事实知识）和程序性记忆（技能、规则、系统提示词的演化）的划分。

**超长对话压缩**

1. **滑动窗口**：保留最近 N 轮原文。
2. **摘要**：对较早历史做滚动摘要。可在 Token 超过阈值时触发，把"旧摘要 + 被淘汰的消息"合并成新摘要，同时保留最近几轮原文，并明确保留关键事实和未完成事项。
3. **向量召回**：把历史片段或抽取出的记忆条目 Embedding 后存入向量库，每轮用当前问题检索 Top-K，可结合相关性、时间新近度和重要性打分。
4. **结构化抽取**：把事实抽成键值或三元组，写入长期记忆，并支持更新和去重。
5. **工具结果裁剪**：对体积大的工具返回做截断或摘要。

注意点：摘要会丢失细节，所以关键信息（订单号、用户约束）要单独保存；长期记忆要处理冲突、过期和隐私合规。

### 8. RAG 中如何处理表格、图片等多模态内容，如何做 Citation/溯源

**参考答案**

**表格**

- 用版面解析工具提取为 Markdown 或 HTML，保留表头和行列结构，避免被当作普通文本打散。
- 小表整体作为一个块；大表按行或行组切分，并在每个块里重复表头。
- 额外生成表格摘要或自然语言描述用于检索，命中后再返回原表给模型。
- 精确数值类问题可以转为 Text-to-SQL 或代码计算，而不是让模型直接读表。

**图片**

- OCR 提取文字；用多模态模型生成图片描述（caption）并向量化。
- 或使用多模态 Embedding（如 CLIP 类）做图文统一检索，也有直接对页面图像做检索的方案。
- 回答时可以把原图交给多模态模型。

**Citation / 溯源**

1. 每个块保存元数据：文档 ID、标题、页码、位置（偏移或 bbox）、版本。
2. Prompt 中给每个资料片段编号，要求模型在对应句子后标注 `[n]`。
3. 生成后校验：引用编号必须存在，且最好用 NLI 或模型判断引用内容是否真的支持该句。
4. 前端展示来源，并支持跳转和高亮原文位置。
5. 没有依据的内容不要硬标引用，应按"资料不足"处理。

### 9. 幻觉产生的原因及缓解手段，RAG 加持下仍有幻觉怎么排查

**参考答案**

**产生原因**

- 模型本质是概率生成，目标是"看起来合理"，而非保证事实。
- 训练数据存在缺失、过时或错误，参数知识有截止时间。
- 提示词有歧义，或要求超出模型能力。
- 上下文中缺乏依据，或依据质量差。
- 解码随机性较高，以及模型倾向于迎合用户。

**缓解手段**：引入 RAG 提供依据；提示词约束"不知道就说不知道"；要求引用来源；低 `temperature`；结构化输出；生成后做事实校验或自一致性检查；高风险场景引入人工审核；对模型做针对性微调或偏好优化。

**RAG 下仍有幻觉，按链路逐层排查**

1. **检索**：相关文档有没有被召回？看召回率。没有则排查解析、切分、Embedding 和 Query 改写。
2. **排序与截断**：相关片段是否排到前面、是否被截断？注意上下文过长时中间内容容易被忽略（lost in the middle）。
3. **资料本身**：内容是否过期、冲突或有错误？
4. **生成忠实度**：资料明明有，模型却没有遵循？检查提示词和模型能力，可用忠实度指标（如 RAGAS 的 faithfulness）衡量。
5. **范围问题**：问题超出知识库范围，却没有设置拒答。

做法是对 badcase 标注归因到具体环节，再针对性修复并加入回归集。

### 10. Prompt Injection 攻击是什么，生产环境怎么防御

**参考答案**

Prompt Injection 是攻击者通过输入内容，让模型忽略原有指令、执行攻击者意图。分为**直接注入**（用户直接输入恶意指令）和**间接注入**（恶意指令藏在网页、文档、邮件、工具返回结果中，被 Agent 读取后执行）。Agent 能调用工具，所以危害更大，可能导致数据泄露或越权操作。

**防御（多层纵深，没有单一手段能彻底解决）**

1. **最小权限**：工具只给必要权限，敏感信息不放进上下文，不要把密钥写进提示词。
2. **隔离指令与数据**：用明确分隔符标记外部内容，并说明它只是数据，不是指令；但这只能降低风险，不能依赖它。
3. **输入输出检测**：用规则或分类模型检测注入特征，输出前检测敏感信息泄露。
4. **高风险操作人工确认**：转账、删除、发送邮件等必须二次确认。
5. **工具调用校验**：参数白名单、权限校验在服务端完成，而不是由模型自己决定；对工具返回结果视为不可信。
6. **架构层隔离**：处理不可信内容的模型不拥有敏感工具权限（如双 LLM 模式）；沙箱执行代码。
7. **监控与红队**：记录审计日志，定期做红队测试并持续更新防护。

### 11. Agent 调用外部 API 超时或返回异常怎么重试、降级、兜底

**参考答案**

结论：先对错误分类，再决定重试、降级还是终止，并保证写操作的幂等。

1. **超时设置**：为每次调用设置连接和读取超时，并设置整个任务的总超时。
2. **错误分类**：网络超时、5xx、限流（429）属于可重试；4xx 参数错误、鉴权失败不应重试，应修正参数或终止。
3. **重试策略**：指数退避加随机抖动，限制最大次数；遵守 `Retry-After`；重试要有预算，避免放大故障。
4. **幂等**：只自动重试幂等操作；写操作使用幂等键，避免重复下单或扣款。
5. **熔断与限流**：下游持续失败时熔断，快速失败，防止拖垮整个 Agent；隔离不同依赖的资源池。
6. **降级**：切换备用服务，使用缓存或旧数据，返回部分结果并说明；对非关键工具可以跳过。
7. **兜底**：向用户明确说明失败原因和已完成部分；转人工或提供稍后重试入口。
8. **让模型感知**：把结构化的错误信息返回给模型，使其可以换工具或调整参数，同时限制循环次数。
9. 记录日志和告警，并监控成功率与延迟。

### 12. 手撕算法：二叉树的锯齿形层序遍历（LeetCode 103）

**参考答案**

思路：BFS 逐层遍历，用一个标志位记录当前层方向，偶数层从左到右，奇数层从右到左。本层遍历完后，需要反向时把该层结果反转即可。

时间复杂度 O(n)，空间复杂度 O(n)。

```python
from collections import deque

def zigzagLevelOrder(root):
    if not root:
        return []
    res, queue, left_to_right = [], deque([root]), True
    while queue:
        level = []
        for _ in range(len(queue)):
            node = queue.popleft()
            level.append(node.val)
            if node.left:
                queue.append(node.left)
            if node.right:
                queue.append(node.right)
        res.append(level if left_to_right else level[::-1])
        left_to_right = not left_to_right
    return res
```

注意点：入队顺序始终是先左后右，只在存结果时反转，不要改变入队顺序，否则会影响下一层。

### 2. 结合项目讲一个最难解决的 Agent 线上问题（幻觉/工具误调/性能），怎么定位怎么解

**答题思路**

这是项目深挖题，必须用真实经历，按 STAR 加"定位方法"组织：

1. **现象与影响**：什么问题、影响范围、如何发现（用户反馈、监控、评测）。
2. **定位过程**：这是重点。讲你如何通过 Trace 日志复现和分段拆解，例如检索、规划、工具、生成各环节，用数据缩小范围，以及排除了哪些假设。
3. **根因**：说明真正的原因，如工具描述有歧义、检索没召回、上下文被截断、下游超时。
4. **解决方案**：做了什么改动、为什么选这个方案、考虑过哪些替代方案及取舍。
5. **验证与沉淀**：用评测集或灰度验证效果，用指标说明改善幅度（必须真实），把 badcase 加入回归集，并补充监控和告警。
6. **复盘**：如果重做会怎样，如何避免同类问题。

### 3. 设计一个电商客服多 Agent 系统：意图路由 → 查知识库/RAG → 查订单/物流工具 → 生成回复，画出架构并说清各组件选型

**参考答案**

结论：采用"路由 + 专业子 Agent / 固定子流程"的 Orchestrator 架构，确定性强的环节用固定流程，只在需要开放推理的地方放开自主性。

**架构（数据流）**

```text
用户 → 网关(鉴权/限流/敏感词) → 会话管理(状态/记忆)
     → 意图路由(小模型/分类器)
        ├─ 咨询类 → RAG Agent(混合检索 + Rerank + 引用)
        ├─ 订单/物流类 → 订单 Agent(调用订单、物流 API)
        ├─ 售后类 → 售后 Agent(规则校验 + 工单 + 人工审批)
        └─ 低置信度/投诉/情绪激烈 → 转人工
     → 生成与校验(话术模板 + 事实校验 + 安全过滤)
     → 流式返回 + 日志追踪 + 评测回流
```

**组件选型与要点**

1. **编排**：LangGraph，用状态图表达路由、循环和人工介入，用 checkpointer 持久化会话。
2. **意图路由**：小模型或 Embedding + 分类器，低延迟低成本；置信度低时反问或转人工。
3. **RAG**：知识库做混合检索（向量 + BM25）加 Rerank，带元数据过滤（品类、时效）；回答附来源，资料不足时拒答。
4. **工具层**：订单、物流通过 Function Calling 或 MCP 接入；参数在服务端校验，用户身份来自会话而不是模型生成，防止越权查询他人订单；只读与写操作分离，写操作需幂等和确认。
5. **生成**：按场景用不同模型（简单问答用小模型，复杂问题用大模型）；用话术模板约束语气和合规。
6. **记忆**：短期保存会话和当前订单上下文；长期保存用户偏好，注意隐私。
7. **安全与护栏**：防 Prompt Injection，对敏感操作（退款）人工审批，输出过滤。
8. **稳定性**：超时、重试、熔断、降级（工具失败时给出兜底话术或转人工）。
9. **可观测与评测**：全链路 Trace，指标包括问题解决率、转人工率、工具调用准确率；badcase 回流到评测集。

关键权衡：多 Agent 会增加延迟和成本，所以路由要快，能走固定流程的就不要让模型自由规划。

### 4. 假设 Agent 响应 P95 延迟要求 2s 但现在 5s，从并发、缓存（Prompt Cache / Semantic Cache）、模型分层调度角度说优化思路

**参考答案**

结论：先用 Trace 拆解各环节耗时找到瓶颈，再按"减少串行步骤、减少调用、降低单次耗时"依次优化，不要盲目调参。

1. **先度量**：按环节统计检索、各次 LLM 调用、工具调用的 P50 和 P95，找出最大耗时和长尾来源。
2. **并发**：没有依赖关系的步骤并行执行，如多路检索、多个独立工具调用、并行工具调用；预取可能用到的数据；用异步 IO。
3. **减少 LLM 往返**：合并步骤，把多轮规划变为一次；确定性环节改为固定流程。
4. **缓存**：
   - **Prompt Cache**：利用模型服务商的前缀缓存（KV Cache 复用），把系统提示词、工具定义等稳定内容放在最前面，把变化内容放后面，可降低首 Token 延迟和成本。
   - **Semantic Cache**：按问题 Embedding 相似度命中历史答案，适合高频重复问题，要设置较高阈值，并注意时效性和个性化数据（不能缓存与用户相关的订单结果）。
   - 工具结果缓存和检索结果缓存。
5. **模型分层调度**：路由、分类、改写等用小模型；复杂推理再用大模型；也可先用小模型尝试，置信度低再升级。
6. **缩短输入输出**：精简 Prompt 和上下文，限制输出长度，减少 Token 数。
7. **体验与长尾**：流式输出降低感知延迟（但不改变整体完成时间的 P95）；对慢调用设置超时、对冲请求（hedged request）或降级，控制长尾。
8. **其他**：Rerank 候选数控制，向量索引参数优化，推理侧使用更快的部署方案。

### 5. MCP（Model Context Protocol）是什么，和直接写 Tool 有什么区别，优劣势

**参考答案**

MCP 是 Anthropic 推出的开放协议，用于标准化 LLM 应用（Host / Client）与外部工具、数据源（Server）之间的连接，可以类比为"AI 应用的 USB-C 接口"。基于 JSON-RPC 2.0，传输方式有 stdio 和 Streamable HTTP。

**Server 能力**：Tools（可调用工具）、Resources（数据资源）、Prompts（提示词模板）；Client 侧还有 Sampling、Roots 等能力。

**与直接写 Tool 的区别**

- 直接写 Tool 是在应用内部定义函数和 Schema，与具体框架和模型接口绑定。
- MCP 把工具封装为独立的服务，通过统一协议暴露，任何兼容的客户端都能接入，并支持动态发现工具。

**优势**：标准化和复用（从 M×N 的适配变成 M+N）；生态丰富；工具与应用解耦，可独立部署和升级；可动态发现。

**劣势 / 风险**：多一层进程或网络通信，增加延迟和运维复杂度；安全风险，如恶意或被投毒的工具描述、权限过大、鉴权和多租户隔离问题；工具太多会撑大上下文；协议仍在演进；对于简单的内部工具，直接写 Tool 更轻量。

选择建议：内部少量强耦合工具直接写 Tool；需要跨应用复用、接入第三方生态时用 MCP。

### 6. 如何评测 Agent 效果——任务完成率、工具调用准确率、答案正确性，Badcase 怎么回流

**参考答案**

结论：评测要覆盖"结果 + 过程"两个层面，并形成"离线评测 → 线上监控 → badcase 回流 → 回归"的闭环。

**指标**

- **任务完成率**：任务是否真正达成目标，可通过规则或状态检查、人工标注、LLM-as-Judge 判定。
- **工具调用准确率**：是否选对工具、参数是否正确、调用顺序和次数是否合理，可与标注的标准轨迹对比。
- **答案正确性**：与标准答案对比；RAG 场景加上检索召回、忠实度、相关性（如 RAGAS 一类指标）。
- **效率与成本**：步数、延迟、Token 消耗；稳定性：多次运行的一致性。
- **安全指标**：越权、注入、违规输出的比例。

**方法**

- 构建覆盖典型和边界场景的评测集，来源于真实线上日志，持续扩充。
- LLM-as-Judge 需要用人工标注校准，避免评分偏差。
- 离线评测接入 CI，每次改 Prompt、模型、工具都跑回归；线上通过灰度或 A/B 验证。

**Badcase 回流**

1. 收集：用户反馈（点踩、转人工）、监控告警、抽样审查。
2. 归因：按环节分类（意图、检索、规划、工具、生成）。
3. 修复：针对根因修改提示词、工具描述、检索或数据，必要时微调。
4. 沉淀：把 badcase 加入评测集作为回归样例。
5. 验证和灰度发布，并观察指标。

### 7. 你跟进新技术（LangGraph / AutoGen / CrewAI 等）的方式，最近看过哪些值得关注的论文或开源项目

**答题思路**

这是个人经历类问题，要用你真实接触过的内容回答，不要为了显得全面而罗列没读过的东西：

1. **信息渠道**：官方文档和更新日志、GitHub 仓库、arXiv 和技术博客、技术社区，并说明筛选方法（如只跟踪和自己工作相关的方向）。

### 8. 如果遇到业务方坚持要上一个你评估风险很高的 AI 功能，你怎么沟通和处理

**答题思路**

重点体现"风险意识 + 沟通能力 + 解决问题"，不要简单顶回去，也不要无底线妥协：

1. **先理解诉求**：弄清业务目标和时间压力，以及他最担心什么。
2. **把风险具体化**：用数据和案例说明风险，如评测中的错误率、可能的损失、合规和品牌风险，区分"概率"和"影响程度"。
3. **提供替代方案**：缩小范围上线、灰度放量、先内部或低风险场景试点；加人工审核或确认环节；设置兜底和拒答；加护栏和监控；明确回滚机制。
4. **对齐决策和责任**：把风险和缓解措施以书面形式同步给相关方，由有权限的人做知情决策；若涉及合规或安全底线，要升级汇报，而不是自己硬扛。
5. **落地与复盘**：按约定的指标和阈值上线，出现问题立即回滚；事后复盘，并积累评测依据，减少下次的分歧。

### 9. 最近半年自学的新技术或方向，怎么判断是否值得投入生产

2. **产出**：做出了什么小项目或验证结果，有什么发现和踩坑。
3. **判断是否值得上生产的维度**：
   - **业务价值**：是否解决实际痛点，收益是否大于成本。
   - **成熟度**：社区活跃度、版本稳定性、文档和维护情况。
   - **效果验证**：用自己的评测集对比现有方案。
   - **成本与复杂度**：学习成本、运维成本、推理成本、团队接手难度。
   - **风险**：安全、合规、可回滚性、供应商锁定。
4. **推进方式**：小范围试点、灰度、设置退出条件，而不是一次性全面替换。

### 10. 手撕算法：LRU 缓存（LeetCode 146）

**参考答案**

思路：用哈希表加双向链表。哈希表按 key 在 O(1) 找到节点，双向链表维护使用顺序，头部是最近使用，尾部是最久未使用。`get` 命中后移到头部；`put` 时已存在则更新并移到头部，不存在则插入头部，超出容量时删除尾部节点并同步删除哈希表中的 key。使用哨兵头尾节点可以避免边界判断。

`get` 和 `put` 的时间复杂度均为 O(1)，空间复杂度 O(capacity)。

```python
class Node:
    def __init__(self, key=0, val=0):
        self.key, self.val = key, val
        self.prev = self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}
        self.head, self.tail = Node(), Node()
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_front(self, node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.map:
            return -1
        node = self.map[key]
        self._remove(node)
        self._add_front(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            node = self.map[key]
            node.val = value
            self._remove(node)
            self._add_front(node)
            return
        if len(self.map) == self.cap:
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]
        node = Node(key, value)
        self.map[key] = node
        self._add_front(node)
```

注意点：节点里必须保存 key，淘汰尾节点时才能删除哈希表中的对应项；也可以用 Python 的 `OrderedDict`（`move_to_end` 与 `popitem(last=False)`）或 Java 的 `LinkedHashMap` 简化实现，但面试通常要求手写链表版。

## HR面

### 1. 简单自我介绍

**答题思路**

HR 面的自我介绍要简洁、有亲和力，约 1 分钟：

1. 基本信息：教育背景或工作年限，当前所做方向。
2. 一到两个最能代表你的经历和成果（真实可核实）。
3. 个人特质：学习能力、责任心、协作方式，用一个小例子支撑。
4. 求职动机：为什么对这个岗位和公司感兴趣。
5. 避免过度技术细节，语速平稳，不要背稿。

### 2. 为什么想来拼多多，对加班和高压节奏怎么看

**答题思路**

结论是"动机真实、态度坦诚、不卑不亢"，不要编造对公司的了解：

1. **为什么来**：结合公开信息说明对公司业务规模、技术挑战和 AI 落地场景的兴趣，以及岗位与你的能力和职业方向的匹配，要具体，不要只说"平台大"。
2. **对加班和节奏**：表达你能适应高强度和紧迫节奏，愿意在关键节点（上线、攻坚）投入；同时强调看重效率和产出，而不是单纯拼时长。
3. **体现依据**：用过去赶项目或应对高压的真实例子说明你能承受并保持质量。
4. 不要表现出抗拒，也不要夸张表态，诚实说明你会通过提升效率和合理安排来保持可持续的状态。

### 3. 你觉得自己最大的优势是什么，用具体例子说明

**答题思路**

选一个与岗位相关、有证据支撑的优势，用 STAR 说明：

1. **优势**：一句话点明，如"能把 Agent 从 Demo 推到线上并用数据闭环迭代"或"排查复杂问题的系统性"。
2. **情境和任务**：当时遇到什么问题或目标。
3. **行动**：你具体怎么做，体现这个优势如何发挥作用。
4. **结果**：用真实的结果收尾，有可量化指标最好，但不要编造。
5. **与岗位关联**：说明这个优势如何帮助你在新岗位创造价值。优势不要罗列多个，一个讲透比多个泛泛更好。

### 4. 遇到和 leader 或同事意见严重分歧时怎么处理

**答题思路**

核心是"对事不对人，用数据和目标说话，最终以团队目标为先"：

1. **先倾听和理解**：弄清对方的出发点和顾虑，确认分歧点是目标、方案还是事实。
2. **用事实和数据沟通**：用实验、评测结果、成本分析来对比，而不是争论观点；必要时做小范围验证。
3. **私下沟通**：先一对一沟通，避免公开对立。
4. **寻找折中或升级**：能折中就折中；无法达成一致时，向共同的上级或相关负责人说明各方案的利弊，由决策者拍板。
5. **决定后执行**：一旦决策，即使与自己想法不同也要全力执行，并保留意见和复盘机制。
6. 可以补充一个真实的小例子，但不要贬低对方。

### 5. 讲一个你搞砸的事，怎么复盘

**答题思路**

选一件真实的、影响不致命但有学习价值的事，重点在复盘而不是失误本身：

1. **事件**：简要说明背景、你的角色和出了什么问题，不推卸责任。
2. **原因**：诚实分析根因，既有个人原因（如评估不足、没做回归、沟通不到位），也有流程原因。
3. **补救**：当时如何止损和修复，如何同步相关方。
4. **复盘改进**：具体做了哪些机制上的改变，如加评测、灰度、监控、Checklist、评审流程。
5. **结果**：之后同类问题是否避免，你的成长是什么。
6. 避免选与岗位核心能力直接冲突的重大失误，也不要说"没有搞砸过"。

### 6. 你的职业规划是什么，三年内想达到什么状态

**答题思路**

规划要与岗位方向一致，既有目标也有路径，不夸大：

1. **短期（0 到 1 年）**：快速熟悉业务和技术栈，独立负责模块并稳定交付，在 Agent 或 RAG 的核心环节做出可见的成果。
2. **中期（1 到 3 年）**：成为该方向的技术骨干，能负责端到端的系统设计，在评测、性能、稳定性上形成方法论，并能带动或指导新人。
3. **能力方向**：深度（Agent 架构、检索与推理优化、评测体系）加广度（业务理解、工程化）。
4. 强调与公司发展的结合，即你的成长是通过解决公司的实际问题实现的。
5. 不要说"三年做到某个具体职级"这类脱离实际的目标，也不要说"还没想过"。

### 7. 期望薪资是多少，其他 offer 情况

**答题思路**

不要编造具体数字或其他公司，按自己真实情况回答：

1. **期望薪资**：先表达你更看重岗位成长和匹配度；再根据市场行情、岗位级别和自己当前的薪资，给出一个合理区间，并说明愿意根据整体方案（职级、总包构成）沟通。不要报过低，也不要过高脱离市场。
2. **其他 offer**：如实说明进展，不夸大也不隐瞒，可以说"在同步推进几个机会，但这个岗位的方向与我最匹配，是优先选项"，并给出你能确定的时间点（如需要在何时前给答复）。
3. 保持尊重和坦诚，不要用虚假的 offer 施压。

### 8. 还有什么想问我的

**答题思路**

反问体现你对岗位的思考，提 2 到 3 个高质量问题，不要问官网能查到的信息或只关心薪资福利：

1. **业务和团队**：这个岗位目前主要负责哪些业务场景？团队的规模和分工是怎样的？

5. 避免问负面或敏感问题（如"加班是不是很严重"），措辞保持积极、聚焦工作本身。
