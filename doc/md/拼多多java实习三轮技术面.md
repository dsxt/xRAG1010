### 3. 假设你负责拼多多商品详情页的展示，QPS很高，需要设计一个本地缓存来存储热点商品数据，你会怎么设计？需要考虑哪些问题？（比如淘汰策略、过期时间、内存控制）

**参考答案**

本地缓存用 Caffeine 的 LoadingCache，挡在 Redis 或数据库前面，只缓存详情摘要。静态信息和价格、库存分开存，价格的过期更短。它是进程内的，各实例之间允许短暂不一致。

淘汰用 Caffeine 默认的 Window TinyLFU，扫描大量冷商品时比纯 LRU 更能留下热点。过期用 `expireAfterWrite` 控制价格能旧多久；热点用 `refreshAfterWrite` 异步刷新，刷新间隔要短于过期时间，读请求在刷新完成前仍拿旧值。同一个 key 的并发回源由 LoadingCache 合并成一次。

内存用 `maximumWeight` 加 Weigher，按这条缓存能占用的堆设上限，值里不要放详情长文和图片。无界的 `ConcurrentHashMap` 会把堆吃满；用软引用躲淘汰，会把 Full GC 拖长。

变更后发失效消息，各实例删掉自己的 key。消息可能丢，过期时间是兜底。支付、可售库存这类必须准确的判断不读这份本地缓存。

```java
LoadingCache<Long, ProductBrief> cache = Caffeine.newBuilder()
    .maximumWeight(maxBytes)
    .weigher((Long id, ProductBrief value) -> value.estimatedBytes())
    .expireAfterWrite(Duration.ofSeconds(expireSeconds))
    .refreshAfterWrite(Duration.ofSeconds(refreshSeconds))
    .build(this::loadFromRedisOrDb);
```

### 4. 你项目中用到了MySQL，现在有一个订单表，数据量达到千万级别，查询某个用户的未支付订单列表变得很慢，你会怎么优化？从SQL、索引、分库分表等角度阐述。

**参考答案**

先确认慢在扫描行数还是锁等待。千万行的未支付列表，通常是索引和行宽的问题，不必先分库分表。

SQL 只查列表要的列，并写成等值和有限条数：

```sql
SELECT id, order_no, amount, create_time
FROM orders
WHERE user_id = ? AND status = 0
ORDER BY create_time DESC
LIMIT 20;
```

索引用 `(user_id, status, create_time)`。等值列在前，排序列在最后，未支付行在这个用户下面是连在一起的。`EXPLAIN` 里应看到它走这个索引。商品快照一类大字段拆出去，列表不回表去读它们。列很少时可以做覆盖索引，索引变宽会拖慢写入，所以只覆盖列表真正要的列。

未支付是小集合。可以单独一张未支付表，下单时和订单表放在同一个事务里写，支付成功时再在同一个事务里删掉。在线查询就不必在全量历史订单里过滤。

单表加索引仍放得下时不分片。已经按订单号分片的话，按用户查会散到所有分片；按用户号分片，或在用户所在分片维护「用户到订单号」的映射，这条查询才落在一个分片。跨分片再做排序分页，代价会更高。

### 5. 场景题：双十一大促期间，秒杀活动开始瞬间，大量请求涌入下单接口，如何防止库存超卖？请给出至少两种方案并对比优缺点。

**参考答案**

超卖来自「先读库存，再在应用里扣减」：两个请求读到同一份剩余。扣减必须在同一次原子操作里完成。

方案一，数据库条件更新：

```sql
UPDATE stock
SET remain = remain - 1
WHERE sku_id = ? AND remain >= 1;
```

影响行数是 1 才算扣到。InnoDB 对这一行的更新串行执行，条件在引擎里判断。优点是库存以数据库为准，实现短。缺点是热点行的锁和日志会打满数据库，连接在大促时堆积。

方案二，Redis 用 Lua 预扣，再异步落库。脚本利用 Redis 单线程，把判断和扣减合成一次：

```lua
local left = redis.call('DECR', KEYS[1])
if left < 0 then
  redis.call('INCR', KEYS[1])
  return -1
end
return left
```

活动前用真实库存写入这个 key，过期时间要盖住整场活动。key 不存在时脚本会把它收成 0 并拒绝下单，避免把缺失库存当成无限。预扣成功才创建订单，数据库仍执行 `remain >= 1` 的更新。数据库失败要把 Redis 加回去，并有对账。用户和活动的唯一约束负责一人一单。优点是售罄流量在 Redis 被挡住。缺点是主从切换、消息丢失、回补失败都会让两边不一致，Redis 不能单独当账本。

流量还没把单行打爆时用方案一。瞬时流量远超单行能力时用方案二，数据库条件更新仍是最后一道闸。入口排队只能减少到达扣减的请求，本身不保证不超卖。

### 7. 场景题：假设你负责的一个微服务A调用另一个微服务B的接口，B服务偶尔响应缓慢甚至超时，导致A服务的线程被阻塞，最终拖垮整个系统。你会怎么设计和处理这种情况？

**参考答案**

同步接口里，处理请求的线程会一直占到 B 返回或超时。保护 A，就是让多数请求不必干等，并且同时卡住的调用有上限。

每条出站调用都设置连接超时和读取超时，总预算短于 A 对上游的承诺，并留下降级时间。有的 HTTP 客户端默认不限制读取时间，这个值必须显式写上。调用 B 再用有界的信号量或有界线程池限制并发，额度用完立即拒绝。熔断器在慢调用和失败比例超过阈值后直接失败，半开时只放少量请求探测。降级返回缓存、明确失败或关掉非核心功能，降级路径里不能再同步调用 B。

重试只给幂等的读，次数算进总预算。B 已经慢时，重试会把请求放大。B 自己也要有超时和限流，否则 A 只是少送了一些仍然会卡住的请求。只加大线程池，等待会从 B 转移到 A 的线程和内存上。

### 8. 手撕算法：给定一个字符串数组，请找出所有“变位词”分组。例如输入 ["eat","tea","tan","ate","nat","bat"]，输出 [["bat"],["nat","tan"],["ate","eat","tea"]]。

**参考答案**

变位词的字母次数相同。题目给出的是小写英文字母。对每个字符串数 26 个字母的出现次数，用 `次数#次数#...` 当哈希表的键，相同的键放进同一组。键中间要有分隔符，避免不同次数拼成同一个字符串。组与组、组内的顺序可以不同。

扫描总长度记为所有字符串长度之和，时间是 O(总长度)，空间是 O(总长度)，主要花在结果和键上。把字符串排序后再当键也可以，时间是 O(总长度 × 单词长度的对数)，字符集不限小写字母时更合适。

```java
public List<List<String>> groupAnagrams(String[] strs) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String s : strs) {
        int[] count = new int[26];
        for (int i = 0; i < s.length(); i++) {
            count[s.charAt(i) - 'a']++;
        }
        StringBuilder key = new StringBuilder();
        for (int c : count) {
            key.append(c).append('#');
        }
        groups.computeIfAbsent(key.toString(), k -> new ArrayList<>()).add(s);
    }
    return new ArrayList<>(groups.values());
}
```

### 2. 深挖项目：你说你用到了Redis做分布式锁，能具体讲讲你们是怎么实现的吗？遇到过哪些坑？比如锁超时、锁误删、可重入性等问题是怎么解决的？

**答题思路**

按你仓库里的真实代码讲。下面几件事面试官会逐个追问，讲到哪一步就对到哪一段代码。

1. 先说锁住的资源、key 的粒度、临界区里做什么、通常持有多久。锁只包住必须互斥的那几步。
2. 加锁是一条命令：`SET key 唯一值 NX PX 租约`。唯一值用这次持有者的标识。`SETNX` 和 `EXPIRE` 分成两条命令时，中间宕机会留下没有过期时间的锁。
3. 解锁用 Lua：比较唯一值，相同才 `DEL`。先 `GET` 再 `DEL` 仍有空隙，会删掉别人刚拿到的锁。
4. 锁超时：业务没做完锁过期，第二个请求进得来。对照你的实现说清楚，租约是固定的，还是由持有者续期。使用 Redisson 且调用不带租约的 `lock()` 时，看门狗会续期；传入租约则不会续期。续期线程停了，锁应能到期释放。
5. 可重入：同一线程再次进入不能把自己堵死。用 Hash 记下线程和次数，或在进程内计数并使用同一个唯一值。次数减到 0 才真正删除。
6. 主从切换时，旧主库上的锁可能没有复制到新主库，两个客户端会同时持有。库存、余额最后用数据库条件更新或版本号拦住。锁过期后，原来的持有者仍可能继续写，写路径也要能拒绝过期的写入。

没拿到锁是立即失败还是等待，等待时间要短于接口超时。没有用过分布式锁，就说没有，不要把这套机制说成自己项目里的实现。

### 3. 场景题：拼多多首页推荐Feed流需要根据用户行为实时更新，数据量大且延迟要求高。如果让你设计这个系统的数据存储架构，你会选择哪些技术组件？为什么？（可以从MySQL、Redis、Elasticsearch、Kafka等角度谈）

**参考答案**

首页读路径只走内存和进程内缓存。行为日志进 Kafka，在线特征放 Redis，MySQL 保存商品和订单真值，Elasticsearch 负责可筛选的商品检索。推荐允许秒级延迟，价格和是否可售不从这条链路读。

用户点击、曝光先进 Kafka，用来削峰和回放。流任务消费后再写 Redis 里的近期兴趣、曝光去重和热点商品，不在网关线程里同步更新 Redis。首页接口读这些结构和商品摘要，在服务里召回、过滤、排序。单个爆款再加一层本地缓存，避免打热 Redis 分片。

MySQL 放商品主数据和交易。详情变更通过提交后的可靠通知刷新 Redis，在线接口不对商品表做连接查询。Elasticsearch 适合类目、关键词这类筛选，刷新有延迟，不拿它当每个用户的实时时间线。

难点是曝光去重的内存、特征更新的频率，以及 Redis 与数据库短暂不一致。写放大时先在流任务里聚合，再更新特征。Kafka 是日志，不是首页查询的存储。

```text
行为日志 -> Kafka -> 流任务 -> Redis(兴趣、曝光、热点)
商品主数据 -> MySQL -> 变更通知 -> Redis / Elasticsearch
首页接口 -> 本地缓存 -> Redis 召回排序
```

### 4. 你项目里用了Kafka，如果某条消息消费失败，你们是怎么处理的？如果一直失败怎么办？会不会导致消息积压？如何监控和告警？

**参考答案**

先关掉自动提交，业务成功后再提交位移，这样进程在提交前宕机只会重放，不会默默丢消息。处理按业务主键幂等，因为至少一次投递和重试都会产生重复。

偶发失败在消费线程里有限次退避重试。一条消息始终失败，就是毒消息：继续占着这个分区，后面的消息都过不去，消费滞后会一直涨。超过次数后写入死信主题，再提交这条消息的位移，分区才能前进。同一批拉取里，提交的位移只能覆盖已经成功或已经进死信的消息。死信要带上原始主题、分区、位移和错误原因。

下游整体不可用时不要立刻把积压全部打进死信。停下对应消费或拉长退避，等下游恢复后再消费；滞后会上升，消息还在 Kafka 的保留期内。全部消息都失败时，先修消费者或下游，再从停住的位移回放。

告警看消费滞后的时间和条数、死信增长速度、处理失败率，以及是否频繁再均衡。消费线程堵在一条消息上时，`max.poll.interval.ms` 到期也会触发再均衡，表现为滞后突然上涨。扩容时，同一组里的消费者数超过分区数后，多出来的消费者是空闲的。

主题、失败原因和幂等键用你项目里的真实消费代码来讲。没有用过 Kafka，就不要把这套说成线上方案。

### 5. 场景题：现在有一个需求，需要统计过去24小时内，每分钟的独立访客数(UV)，数据源是一个实时的用户访问日志流。你会如何设计这个实时计算方案？请画出简要的数据流图并说明关键点。

**参考答案**

口径先定为：最近 24 小时的每一个自然分钟各有多少独立用户，共 1440 个点，用日志里的 userId 去重。这是每分钟的 UV，不是把这些数加起来当成 24 小时 UV。

```text
访问日志 -> Kafka -> Flink(事件时间, 先按 userId 再按分钟去重)
        -> Redis(每分钟一个计数值, 过期略长于 24 小时) -> 查询接口
```

Flink 用日志时间做事件时间，允许一小段乱序。先按 userId 把同一分钟收成一条，再按分钟计数，避免所有日志挤在一个 key 上。窗口结果用覆盖写进 Redis，恢复重放时不会把同一次访问累加两次。Redis 只存计数和过期时间，用户集合留在这一分钟的计算状态里。迟到日志让该分钟重新计算并覆盖；窗口已经丢掉的，走补数，不在查询时临时扫原始日志。

业务能接受误差时，每个分钟一个 HyperLogLog 更省内存。同一个用户重复 `PFADD` 不会使估计值变大，回放是幂等的，Redis 默认实现的标准误差大约 0.81%。它仍然不能把 1440 个分钟估计值相加当作 24 小时去重。若要每一分钟向前滚动 24 小时的精确 UV，保存每分钟的用户 bitmap，查询时做并集。

### 6. MySQL的InnoDB引擎中，间隙锁和临键锁的作用是什么？在什么情况下会产生死锁？请举例说明。

**参考答案**

可重复读下，InnoDB 用这些锁挡住当前读的幻读。记录锁锁住已经存在的索引记录。间隙锁锁住索引记录之间的空隙，阻止别的事务往空隙里插入；两个间隙锁可以同时加在同一段空隙上。临键锁是记录锁加上这条记录前面的间隙，区间前开后闭。范围更新、非唯一索引的等值当前读，会使用临键锁。唯一索引等值命中已有行时，临键锁退化为记录锁，不再锁两侧间隙。读已提交下，锁定读、更新和删除基本只加记录锁，一致性读不加锁。外键检查和唯一键冲突检查仍可能加间隙锁。

死锁的一个典型来源是：间隙锁互不冲突，插入却要等待对方的间隙锁。表里已有主键 5 和 15：

```sql
-- 事务 A、B 都执行：10 不存在，各自锁住 (5, 15)
SELECT * FROM t WHERE id = 10 FOR UPDATE;
-- A、B 再都执行，互相等待
INSERT INTO t (id) VALUES (10);
```

InnoDB 会回滚其中一个事务。应用应重试整个事务。两条已有记录按相反顺序更新，只用记录锁也会死锁。缩短事务、以相同顺序访问记录，能减少这类等待；死锁后的重试要有次数上限。

### 7. 手撕算法：给定一个整数数组 nums和一个目标值target，请你在该数组中找出和为目标值的两个整数，并返回它们的数组下标。要求时间复杂度O(n)。(LeetCode 1. 两数之和)

**参考答案**

用哈希表记录已经看过的值和下标。扫到 `nums[i]` 时先查 `target - nums[i]` 是否出现过，出现过就返回那两个下标，否则再放入当前值。先查再放，同一个下标不会被用两次。时间和空间都是 O(n)。

排序后双指针是 O(n log n)，而且会打乱原来的下标，不满足这道题的时间要求。题目约定恰好有一组解。

```java
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = seen.get(target - nums[i]);
        if (j != null) {
            return new int[] {j, i};
        }
        seen.put(nums[i], i);
    }
    return new int[0];
}
```

### 2. 聊聊你在实习或项目过程中，遇到的最棘手的技术难题是什么？你是如何一步步分析并最终解决的？请详细描述你的排查思路和解决方案。

### 4. 场景题：假设你是这个实习项目的技术负责人，需要引入一个新的技术框架（比如从Spring Boot迁移到Spring Cloud Alibaba），但团队成员对其不熟悉，有抵触情绪。你会如何推动这件事？需要考虑哪些风险和收益？

**参考答案**

先写清现在的问题：地址写死、配置只能发版、调用没有超时和限流，还是仅仅想把项目写成微服务。问题不成立，或仍是一个可部署单元，就继续用 Spring Boot。抵触在这时是合理的。

收益只在这些问题已经出现时成立：服务发现、配置外置、限流熔断有现成组件，多个服务可以分开发布。风险是新增强依赖、调用链变长、团队不会排查，以及 Nacos 不可用或一次错误的配置推到全部实例。分布式事务不放进第一期，它会改掉原来的事务模型。版本按官方对照表选择，Spring Boot 2 和 3 不混用。

### 5. 谈谈你对AI大模型的了解，你觉得它在后端开发领域（比如代码生成、自动化测试、智能运维等）会有哪些应用前景？你是否有实际用过相关的工具或API？

**参考答案**

大模型适合生成草稿和做归纳，输出不稳定，不能单独作为正确性来源。进仓库、改生产数据之前，仍走原来的评审、测试和权限。
