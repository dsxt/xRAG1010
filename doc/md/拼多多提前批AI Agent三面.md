# 拼多多提前批 AI Agent 三面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

一面不算温柔，意图识别那块直接往工程延迟上拽，不是背定义就能混过去的。二面基本在确认 LangGraph 是不是真用过，checkpoint 和恢复说不清就会凉半截。死锁和熔断不问概念，问你大促怎么扛，挺拼多多。三面开始聊人，但聊人里还夹着 harness 的版本和灰度，属于典型的技术管理者视角。整体很硬，问的都在生产链路上，不像有些厂只背八股。Java 侧不考 HashMap 算良心，但线程池和 Redis 照样抠。LangGraph 如果只看过 quickstart，别去送，问到 thread_id 映射那层会当场露馅。

## 一面

### 1. 自我介绍

**答题思路**

控制在一分半到两分钟，按「我是谁 → 一条上过线的 Agent 链路 → 我守的那一层」讲完就停。

1. 年限和主语言。这岗听的是 Java 后端里的 Agent，先说你写过的服务，再说模型应用。没上过线的 demo 不要当主项目。
2. 只展开一个项目：谁在用、能做的动作、你负责编排、工具、检索还是运行时。QPS 和延迟留到下一问，这里点到即可。
3. 收在一个你准备被追问的点上，例如意图延迟、工具权限或会话状态。不要把中间件名单念完。

### 2. 讲一个你落过的 AI Agent 项目，你在里面负责哪一层，QPS 和延迟是多少

**答题思路**

用真实项目，按「任务 → 链路 → 我的层 → 数字口径」讲，大约三分钟。项目名用真的，没有的指标不要编。

1. 用户要完成的事，以及哪些步骤是固定流程，哪些才交给模型选工具。先把动作边界说死。
2. 沿一次请求讲：接入、意图和槽位、检索或工具、校验、回复。你负责的那一层说清输入、输出和失败时怎么停。
3. 数字先报口径再报值。QPS 要说明是入口还是模型调用；延迟要说明是首 token 还是整轮结束，是 P50 还是 P99，包不包括排队和工具。只记得压测峰值就说是压测，不要说成线上均值。
4. 没有全链路数字时，拆你负责那一段的耗时：检索、模型、工具各占多少，以及你为了控延迟砍过什么。
5. 收在一个线上问题：现象、怎么定位、改了什么、用哪份日志或评测验证。主动把话口留给意图、状态或工具。

### 3. 意图识别和传统 NLU 分类器的区别，大模型做意图识别时怎么控延迟和控成本

**参考答案**

结论：传统 NLU 是封闭标签上的判别分类，延迟和成本稳定；大模型能结合上下文收长尾说法，但大部分流量应在规则或小模型处结束。

分类器输出标签概率，标签集在训练时确定，分布外的说法只能硬分或拒识，推理通常是毫秒级。大模型能利用多轮把开放说法收成意图和槽位，但首包延迟和 token 费用都高，还可能输出标签集里没有的名字。

控制靠四件事。高置信的规则或小模型直接命中，只有低置信、多意图、要消歧的才进大模型。大模型限制生成长度，能约束到标签集就不要让它写解释。意图缓存的键用归一化说法、会话摘要和标签集版本，上下文相关的说法不要只按原句哈希。分类单独设超时，超时就澄清或走兜底。大促可以关掉大模型这一层。

延迟要看端到端 P99，包括排队，不是只看模型自身耗时。

### 4. 用户说「帮我看看那个东西」，多轮上下文下你怎么消歧，强意图弱意图怎么定

**参考答案**

结论：消歧靠会话里已经落地的实体，不靠模型再猜一个；强意图可以直接执行，弱意图先澄清，有副作用时不猜测。

维护结构化状态：最近的商品、订单、售后单，带来源和轮次。用户原话和工具返回分开记。「那个东西」只绑定类型匹配、且最近唯一的实体。候选接近就列出让用户选。

强意图是动作和对象都明确，或上文只有一个对象且动作在白名单里，例如「退这单」。弱意图是缺对象、多个对象冲突，或只有「看看」没有动作。只读且对象唯一时，可以先按该对象做预览，并说清理解成什么。退款、投诉这类写操作，对象不唯一就不派发。

置信度由规则和分类一起定：唯一实体加白名单动作算强；缺槽或实体冲突算弱。模型自己说「很确定」不算数。澄清要有次数上限，用完转人工。

### 5. ReAct 和 Plan-and-Execute 在 Java 后端里怎么落地，循环终止条件放哪

**参考答案**

结论：ReAct 是走一步看一步，适合分支依赖上一步结果的短任务；Plan-and-Execute 先产出计划再执行，适合步骤相对稳定、要审计的流程。终止条件放在 Java 运行时，不放在模型自己宣布结束。

ReAct 的循环是：调模型，解析出工具调用或结束，网关执行工具，把观察结果追加进状态。Plan-and-Execute 先得到带工具名和成功条件的步骤，执行器逐步跑；失败再重规划，重规划有次数上限。两种都是模型提议、Java 执行。

终止由编排器强制执行：最大步数、最大模型调用次数、墙钟超时、相同工具加相同参数重复出现、结束信号通过结构校验、用户取消、预算用尽。计数器由代码递增。模型把计数写回去，或者输出一句 Final Answer，都不算停。

有副作用的工具成功后记下幂等键。循环停了，已经做成的写操作要照实告诉用户。

### 6. LangChain 的 Chain 和 LangGraph 的 StateGraph 本质差异，什么场景别上 LangGraph

**参考答案**

结论：Chain 是写代码时就定好的调用顺序；StateGraph 是带共享状态、条件边和循环的状态机。没有分支、循环、中断和恢复时，不要上 LangGraph。

Chain 把步骤串起来，输入输出类型顺着流下去，控制流事先可见，延迟好估计。RunnableBranch 能做一点分流，但没有持久化的线程状态，也没有一等的循环和人工中断。

StateGraph 的节点读写同一份 state，边可以按状态跳转、回到前面的节点，并在 checkpoint 上暂停。适合多步工具、要恢复、要等人确认的 Agent。代价是你得设计状态和 reducer，每一步有存储开销，循环可能失控，图的版本和 thread_id 要自己管。它不负责权限和终止，这两件事仍在图外面的运行时里。

单次检索后生成、固定的「检索、重排、生成」、无状态分类、一次工具调用后直接回答，用一个方法或一条 Chain 更清楚。

### 7. RAG 切 chunk 的策略，电商长文本（商品详情、规则页）和短 QA 怎么分开处理

**参考答案**

结论：长详情和规则页按结构切，并保留上级标题；短问答以一问一答为整块，不再切碎。两类用文档类型分开过滤。

详情和规则先按标题、条款号、表格切开。块上带文档编号、上级标题和版本。表格、价格和规格整块保留，拆开后会答错条件。段落仍超长时再按窗口切，并留少量重叠。检索可以用小块命中、把父块送进上下文，避免块太小把条件丢掉。

短 QA 的问题和答案放在同一个块里，元数据标类目、渠道和生效时间。滑动窗口会把问题和答案拆散。

两类至少用 `doc_type` 过滤，问题类型明确时分开查。每个块要能回到原文档和版本，后面增量删除才删得干净。价格和活动日期跟生效时间一起存，过期块在查询时滤掉。

### 8. 向量检索召回不准时，你的排查路径是啥（embedding、切分、metadata filter、rerank）

**参考答案**

结论：先确认正确文档在不在库、在不在过滤后的候选里，再看向量空间和重排。重排救不回根本没进候选集的文档。

拿一条坏例，查期望文档是否入库。不在库，查切分和写入。在库却不在候选里，先去掉 metadata filter 看裸召回：过滤太严会把真文档丢掉，太松会让别的类目和过期活动占满名额。

裸召回也不对，再查 embedding。查询和文档必须是同一模型、同一版本；有的模型要求两侧加不同前缀，要按该模型的约定加。换过模型却没整库重刷，或两侧归一化不一致，相似度没有可比性。然后对照原文看切分：证据被切断、标题丢失、表格拆开，都会召回错块。

最后比 rerank 前后的顺序。对的块若从未进入送给重排的集合，调重排没有用。评测集和知识版本固定，否则看不出是哪一层变了。过期文档被召回，是版本和过滤问题，不是相似度问题。

### 9. Agent 调工具返回脏数据或被提示注入，怎么在 harness 层拦截

**参考答案**

结论：harness 是模型外面的运行时。工具返回先过模式校验，再当作不可信数据送进上下文；能不能执行下一步由网关决定，不由这段文本决定。

脏数据在进模型前处理。校验状态码和结构，类型不对、半截 JSON、把错误页当成成功，都收成一条短的工具错误，不把原文塞进上下文。限制长度，去掉异常字符，工具意外带回的密钥打码。缺价格、部分成功，用明确的错误码表示，避免模型补一个看起来合理的数字。

提示注入靠通道隔离。观察结果放在独立字段里，不能改写系统提示、工具清单和角色。规则可以丢掉明显的「忽略以上、改调某工具」，这只是降噪。安全边界是：下一轮即使跟着脏文本走，网关仍检查工具白名单、参数结构和资源归属。命中可疑观察后，后续有副作用的工具直接禁止，转人工。

写入记忆时保留来源。工具原文不能进系统指令槽，摘要同样可能被带偏。

### 10. Java 线程池参数在项目里怎么配，Agent 并发跑工具时怎么隔离上下文

**参考答案**

结论：模型调用、工具 IO 和接入线程分池；池的大小对齐下游允许的在途数。会话上下文随请求显式传递，不靠线程池里残留的 ThreadLocal。

工具调用是 IO，不要按 CPU 核数去套公式。`ThreadPoolExecutor` 的核心线程数、最大线程数、队列、拒绝策略是一组：队列无界时，最大线程数不会生效，任务堆在内存里。Agent 更怕尾延迟，队列用有界的，打满就拒绝，把失败交回编排，让这一步失败或降级。每个下游再加自己的信号量，避免一个慢工具占满公共池。不要用 `ForkJoinPool.commonPool()` 跑阻塞 IO，也不要用无界的 `newCachedThreadPool()` 做工具扇出。

并行工具各自拿到父状态的快照，写回时按 `tool_call_id` 合并，不并发改同一份 Map。用户、租户和 thread 放在任务对象里传下去。必须用 ThreadLocal 或 MDC 时，提交时拷贝，`finally` 里清除；池线程会复用，不清就会串会话。取消任务时同时取消下游 HTTP，中断线程不等于关闭了 socket。

### 11. Redis 在 Agent 系统里存什么（session、state、semantic cache），击穿和雪崩怎么防

**参考答案**

结论：Redis 放短生命周期的会话、图的热状态和可失效的语义缓存。要能恢复的状态另有权威存储。击穿防的是一个热点同时打穿，雪崩防的是大面积同时失效。

session 存槽位和最近实体，键带用户和会话，设 TTL，并在对话继续时续期。state 可以缓存当前 checkpoint，权威副本在持久化存储；Redis 被逐出后要能从那份副本恢复。语义缓存的键要带租户、已解析的实体、模型和知识版本。订单状态、价格、库存不进语义缓存，或只给极短 TTL。

击穿是热点键过期，并发请求一起回源到模型或数据库。用带过期时间的互斥锁放行一个请求回源，其余等结果或返回旧值；值里也可以带逻辑过期时间，物理 TTL 更长，过期后先返回旧值再异步刷新。

雪崩是大量键同时过期，或 Redis 本身不可用。TTL 加随机抖动；Redis 故障时停用语义缓存，并限制打到模型的并发，而不是全部穿透。穿透是另一个问题：查一定不存在的数据，每次都不命中，做法是缓存空值或用布隆过滤器。三个词不要说串。

### 12. MySQL 存对话记录和工具调用日志，分库分表按什么维度拆

**参考答案**

结论：在线库按用户拆，保证一个用户的会话落在同一分片。不要先按时间拆，否则打开一次会话就要扫所有表。

主查询是用户拉取自己的会话和某个会话的消息，分片键用 `user_id`。`session_id` 加消息序号做分片内索引。工具日志用同一个 `user_id`，排查时消息和调用记录一起取到。客服只拿着会话号来查时，先查 `session_id` 到 `user_id` 的映射，再进分片，不做全库扇出。

按天的全量审计同步到数仓，不在在线库按时间分表。消息是追加写，避免跨分片事务。全局自增改成雪花或号段。完整提示词和工具原文通常很大，在线表留摘要和对象存储指针。

热点用户会把一个分片打满。加盐能打散写入，但用户查询会变成扇出，所以先按用户拆，真出现热点再单独处理。删旧数据按分片归档，保留期跟租户走。

### 13. 手撕算法：给一个字符串，里面包含括号和字母，判断是否是合法括号序列并提取最外层平衡括号内容（LeetCode 1021 变种）

**参考答案**

结论：用深度计数一次扫描。深度不为负且结束时为 0 就是合法；每个原语去掉最外层那一对括号，字母和内层括号原样保留，拼成结果。非法就不提取。

契约按 1021 的变种定：只把 `(` 和 `)` 计入平衡，其余字符原样保留。深度从 0 变为 1 的左括号、以及回到 0 的右括号是最外层，不写入结果。纯括号串 `(()())(())` 得到 `()()()`；`a(b(c)d)e(f)` 得到 `ab(c)def`；`())` 和 `(()` 非法。没有括号的字符串视为平衡，结果就是它本身。字母不需要入栈，计数器够用。

时间 O(n)，空间 O(n)，主要是输出。

```java
final class BracketExtract {
    static final class Result {
        final boolean valid;
        final String content;

        Result(boolean valid, String content) {
            this.valid = valid;
            this.content = content;
        }
    }

    static Result parse(String text) {
        StringBuilder out = new StringBuilder();
        int depth = 0;
        for (int i = 0; i < text.length(); i++) {
            char ch = text.charAt(i);
            if (ch == '(') {
                if (depth > 0) {
                    out.append(ch);
                }
                depth++;
            } else if (ch == ')') {
                depth--;
                if (depth < 0) {
                    return new Result(false, "");
                }
                if (depth > 0) {
                    out.append(ch);
                }
            } else {
                out.append(ch);
            }
        }
        if (depth != 0) {
            return new Result(false, "");
        }
        return new Result(true, out.toString());
    }
}
```

## 二面

### 1. 自我介绍

**答题思路**

二面会沿一面的项目往下拆，压缩到一分钟，把时间留给状态和编排。

1. 一句话交代年限、Java 主栈，以及你做过的那条 Agent 链路。
2. 直接说清四层里你负责的层，并点出线上约束：恢复、取消或工具权限，三选一，选你真做过的。
3. 停在 checkpoint 或路由上，等面试官选一个往下挖。不要把一面讲过的业务背景再讲一遍。

### 2. 把你一面说的项目拆开：编排层、state 层、tool 层、observability 层各自怎么画

**答题思路**

按一次请求从进到出画，不要按简历上的组件清单画。每层讲清输入、输出和你写过的那一段，名称用你的真实系统。

1. 编排层：意图之后谁在循环。说明是固定管线还是图，下一步由谁选择，循环在哪停，人在哪一步能打断。
2. state 层：槽位、证据和工具结果放在哪一份状态里，会话怎么对应到 thread，进程重启后从哪读。热缓存和权威存储分开说。
3. tool 层：模型只提议。讲白名单、参数校验、订单归属、超时和幂等键。举一个你真实拒绝过或重试过的调用。
4. observability 层：一条 trace 里有没有图版本、每步工具名、拒绝原因和结束原因。讲你用它排过的一次错。

最后停在你负责的层上。延迟和失败率的口径跟这一层对齐，数字要能对上日志。

### 3. LangGraph 的 checkpoint 怎么存，thread_id 和租户怎么映射，服务重启后任务怎么续跑

**参考答案**

结论：checkpoint 按 thread_id 保存每一步的图状态。调用方不能直接指定 thread_id，必须先过租户映射和鉴权。重启后续跑靠进程外的 checkpointer；未完成节点会重放，写操作要幂等。

LangGraph 在每个 superstep 结束时写入通道状态、版本和接下来要跑的节点。thread_id 标识这条对话，checkpoint_id 标识某一步快照，先后靠 parent 和 step；子图用 checkpoint_ns 与父图隔开。MemorySaver 在进程内，重启就没了。生产用 Postgres 这类外部存储，并且每一步同步落库；只在运行结束时写一次，进程被杀会退回更早的状态。

映射单独一张表：租户、用户、会话对应一个随机 thread_id，并记下图版本。客户端只传会话号。每次读取或继续执行，先查表确认归属。官方 saver 按 thread_id 和 checkpoint_ns 读取，没有租户字段。

续跑分两种。停在 `interrupt` 上等用户时，用 `Command(resume=回复)` 继续；该节点会从头再执行，副作用不要放在 `interrupt` 之前。死在普通节点上时，用同一个 thread_id 接着跑未完成步骤，不要把上一条用户消息再追加一次，带追加语义的 messages 会重复。同一 thread 加租约，避免两个实例一起续。schema 或图版本不兼容时，旧 checkpoint 不要硬接到新图上。

### 4. 多 Agent 编排：supervisor-worker 和 pipeline 模式在电商售前售后场景怎么选

**参考答案**

结论：控制流上线前就知道的用 pipeline；要在多个专家之间改派的用 supervisor。售前多数是前者，售后的分支和改口更适合后者。写操作都不放在主管节点里。

pipeline 把「路由、查商品或查单、生成」排成固定顺序，失败退路明确，延迟好估计。用户一句话里又问物流又改地址时，它不适合临时换专家。supervisor 只负责选择下一个 worker 和汇总，worker 不互相直接调用，也不同步回调一个正在等自己的主管。最大跳数和预算写在图上，由代码执行。

售前的商品问答、活动说明用 pipeline 即可。需要同时查商品、活动和库存时，可以在管线里加可选的只读节点，仍不必做成自由互调。售后常要先查单，再判断规则，再决定退、换或转投诉，中间用户会改口，用 supervisor 派给专职 worker。退款和投诉的执行权在带策略的工具网关，主管只派任务。

worker 的结果先收成结构化结果再交回主管。把每个 worker 的自由文本原样转发，上下文会膨胀，错误也会被当成事实传下去。

### 5. 意图路由层怎么设计，4 个业务 Agent（查商品、查订单、退换货、投诉）「帮我看看」怎么分发

**参考答案**

结论：路由看会话槽位和置信度。「帮我看看」是弱意图，上文有唯一实体就继承，没有就澄清，不向四个 Agent 一起扇出。

路由放在 worker 之前。输入是当前这句话、已解析的商品或订单、进行中的售后单，以及四个意图的分数。高置信且槽位齐全时，只派一个 Agent，并把实体一并传过去，不让 worker 再猜。

「帮我看看」若上文只有一个订单，派查订单；只有一个商品，派查商品。两个都有或都没有，就问用户看的是哪一个。明确的退、换、投诉压过「看看」。退换货和投诉即使分数高，对象不明确也不进入，因为后面有副作用。

四个 Agent 都跑一遍，既贵又会给出互相冲突的答案。澄清有次数上限，用完转人工。路由标签和 Agent 注册表一起发布，下线一个 Agent 时同时下线路由。每次分发写入 state，后面才能算选错率。

### 6. Tool Schema 怎么写能让 LLM 少选错，参数合法但业务非法（查了别人的订单）怎么拦

**参考答案**

结论：schema 让模型少选错工具、少填错类型；订单是不是这个人的，由网关按登录身份判断。JSON Schema 通过只说明类型合法。

工具名和描述写清做什么、不做什么。查物流和查退款进度这种近邻工具，把边界写进描述。参数尽量少，状态和动作用枚举，避免一个万能字符串。当前用户由服务端注入，不作为模型可填的字段；模型传了 `user_id` 也忽略。返回字段的含义写清楚，减少模型误用。

执行前，网关用会话里的登录用户查订单归属。`order_id` 格式正确但不属于该用户，就拒绝。返回给模型的是固定的无权错误，不带对方的订单详情，也不说明该订单属于谁。客服代查使用单独的委托范围，不要把工具改成无主查询。同一检查放在工具执行前，提示词里的「不要查别人」不是权限。

### 7. Agentic RAG 和被动 RAG 区别，检索结果和工具返回冲突时以谁为准

**参考答案**

结论：被动 RAG 检索一次就生成；Agentic RAG 可以改写查询、换条件、多轮再查，也可以先调工具再检索。冲突时，交易事实以实时工具为准，知识库片段只作说明。

被动链路短，适合不依赖实时状态的规则说明，查不到也不会自己再查。Agentic 由策略或模型决定查哪一类、查几轮，适合先拿到订单号再去匹配售后规则。它必须有轮次和预算上限，否则检索本身会循环。

权威顺序写死，不交给模型斟酌：订单状态、价格、库存以交易系统的工具返回为准，因为索引必然滞后；条款说明以带生效时间的知识版本为准；两边都没有的数字不输出。两边矛盾时，回答说明以实时系统为准，并丢掉过期文档。工具和检索片段都要带编号，没有来源的具体数字不进最终回复。

### 8. 多 Agent 幻觉放大怎么治，critic 节点和 citation 约束怎么接进图

**参考答案**

结论：幻觉会在转发时被写成事实。共享状态里只追加带来源的证据；critic 和引用检查是图上的关卡，不能再变成一个什么都能调的 Agent。

worker 只把证据写进 state：文本、来源编号、工具名。主管汇总时只能引用这些编号，不把工人的自由发挥复制给下一个工人。摘要优先用模板拼。

citation 由生成节点给主张标证据编号，后面接一个代码节点：编号必须存在，价格、订单号这类片段必须真的出现在证据里。对不上就回到生成，次数有限，用完就只回复已经查到的记录或转人工。

critic 节点只读，不挂有副作用的工具。它接收草稿和证据，输出缺证据、越权建议或答非所问这类结构化问题，由条件边决定回到生成还是结束。能用确定性规则判断的，不要先交给 critic 模型；它自己也会编。

### 9. 大促脉冲流量下，Agent 集群任务死锁、算力抢占怎么解，限流熔断降级放哪一层

**参考答案**

结论：死锁来自循环等待和锁顺序不一致；算力抢占来自在线推理与离线任务共用额度。限流在入口，熔断在每个下游客户端，降级在编排层换成更短的路径。

多 Agent 由主管单向派发，worker 不同步回调一个正在等它的主管。图的依赖不要成环。订单和库存的锁规定全局顺序，并设超时，步数超时必须放锁。线程池使用有界队列；任务不要在池里再等待同一池中的任务，否则所有线程都在等，新任务也进不来。

在线用户和评测、重建索引分开配额。大促时把离线回放降到零。入口限制新建 run 和在途数，超限就排队或直接走降级，而不是无限进入模型。

熔断按模型网关、检索、订单服务分别统计超时和错误，打开后不再发新调用。编排层看到模型熔断，只读查询走模板或缓存，写操作直接拒绝。只限流、不取消已经在跑的图，在途任务仍会打满模型。

### 10. Java 侧 SSE 断线重连、用户点停止后怎么真取消推理而不是假装停

**参考答案**

结论：关掉 SSE 写出流，上游还会继续生成。停止必须变成服务端的取消信号，并传到模型那条 HTTP 连接。重连按事件编号补流，不重新开跑。

用户点停止时调用取消接口。浏览器断开、写出超时也走同一条取消路径，不能只把 `SseEmitter` 结束掉。这次 run 记下取消标记，编排循环在每一步和每个工具前检查。对模型的调用保存可取消的句柄：取消 `HttpClient` 的 future、OkHttp 的 call，或 WebClient 的订阅。线程中断不会自动打断一个不响应中断的阻塞 socket。LangChain4j 的流式回调停了，也不代表供应商已经停，所以要取消底层连接；Python 工人如果在另一端，还要有取消接口，单靠掐断连接不够。

已经提交的写操作不能假装没发生。状态写成已取消，并记下最后一次已知的工具调用。发出去但结果不明的，按幂等键对账，不盲目重试。

SSE 事件使用单调编号并按 run 缓冲。重连带着 `Last-Event-ID`，从该编号之后回放；run 还在进行就继续推新事件，已结束就回放完关掉。心跳避免中间设备因为静默而断开。容器的异步超时要单独配置，不要把它当成推理的业务超时。

### 11. Kafka 在 Agent 系统里跑什么（异步工具回调、审计、评测埋点），消息重复消费怎么幂等

**参考答案**

结论：Kafka 传递已经发生的事实：工具回调、审计和评测埋点。它不承担同步推理。消费者是至少一次，副作用靠业务幂等键挡住。

支付结果、工单状态用回调推进图的下一步。每次工具调用的审计异步落库。轨迹、选错的工具、人工接管作为评测事件给离线消费。同一会话用 `session_id` 做分区键，固定到一个分区，并由该分区单线程消费，才谈得上顺序。不要在消费线程里同步跑完整个 Agent，一条慢消息会堵住分区；消费只负责把任务交到有界执行器。

生产者重试和消费者再均衡都会让消息再来一次。生产者幂等只覆盖同一次生产会话里的重复写入，覆盖不了消费侧重放。每条消息带幂等键，例如 `run_id` 加 `tool_call_id`，或业务单号加事件类型加版本。本地状态和这枚键放进同一个事务：插入成功才改状态，提交之后再提交 offset。自动提交可能在处理失败前就把 offset 过掉。

退款这类外部调用不在数据库事务里，外部接口也要认同一枚键。本地记下已发起还是已成功；重试看到已发起时，先查询外部结果。推进图状态还要看当前步骤，更旧的事件不能把状态打回去。

### 12. RocketMQ 延迟消息做 Agent 定时兜底任务，和 Redis 过期回调比有什么坑

**参考答案**

结论：必须执行的兜底用 RocketMQ 延迟消息。Redis 过期适合缓存失效，不适合作为任务队列。

延迟消息到点后进入消费队列，有持久化、重试和死信。消费者当时不在，消息还在。适合「一段时间没有回调就对账」或「无人处理的会话转人工」。

坑有四个。消息发出后不好删除，任务提前完成时，消费端要先查状态，完成了就丢弃。4.x 常见是固定延迟级别，5.x 可以指定投递时间，两种都要在消费时核对是否已经到点、是否已被取消。投递会重复，转人工和补查询必须幂等。精度是秒级，不适合当作毫秒级调度。

Redis 键过期是惰性删除加定期删除，到期时刻不稳定。键空间通知走发布订阅，不落盘，到期可能延迟；订阅方不在线或故障切换期间，通知会丢。多个订阅者还可能各执行一次。它没有消费组、重试和死信。可以用 Redis 做短缓存和租约，兜底任务的可靠投递仍交给消息队列。

### 13. 手撕算法：实现一个简易意图路由——输入字符串列表，用 Trie 匹配最长前缀意图，返回意图名和剩余槽位串

**参考答案**

结论：词典短语放进 Trie，终止节点记下意图名。对每条输入尽量往下走，沿途记住最后一个终止节点，这就是最长前缀；剩下的子串去掉前导空白后是槽位。没有终止节点则未命中，槽位串为原文。

例如词典里「退」是 `return_query`、「退货」是 `return_goods`，输入「退货进度」命中 `return_goods`，槽位是「进度」，不会停在更短的「退」。这是前缀契约，句中才出现的意图不在这题范围内。同一短语后写入的意图覆盖先前的。空短语不能插入，否则会匹配所有句子。

建树时间与空间都是词典总长度。单条查询时间是句子长度。中文和英文在基本多文种平面内，按 Java 的 `char` 走即可。

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

final class IntentRouter {
    static final class Hit {
        final String intent;
        final String slot;

        Hit(String intent, String slot) {
            this.intent = intent;
            this.slot = slot;
        }
    }

    private static final class Node {
        final Map<Character, Node> next = new HashMap<>();
        String intent;
    }

    private final Node root = new Node();

    void add(String phrase, String intent) {
        if (phrase == null || phrase.isEmpty()) {
            throw new IllegalArgumentException("empty phrase");
        }
        Node cur = root;
        for (int i = 0; i < phrase.length(); i++) {
            char ch = phrase.charAt(i);
            cur = cur.next.computeIfAbsent(ch, key -> new Node());
        }
        cur.intent = intent;
    }

    Hit route(String text) {
        Node cur = root;
        int best = -1;
        String intent = null;
        for (int i = 0; i < text.length() && cur != null; i++) {
            cur = cur.next.get(text.charAt(i));
            if (cur != null && cur.intent != null) {
                best = i + 1;
                intent = cur.intent;
            }
        }
        if (intent == null) {
            return new Hit(null, text);
        }
        String rest = text.substring(best);
        int i = 0;
        while (i < rest.length() && Character.isWhitespace(rest.charAt(i))) {
            i++;
        }
        return new Hit(intent, rest.substring(i));
    }

    List<Hit> routeAll(List<String> texts) {
        List<Hit> hits = new ArrayList<>();
        for (String text : texts) {
            hits.add(route(text));
        }
        return hits;
    }
}
```

### 2. 你那个 Agent 项目如果交给 3 个人做半年，你怎么拆模块和排期

**答题思路**

按真实系统的模块说，不要临时造一个平台名。半年按六个月，每个月末都有一条用户能走完的路径。

1. 先定三个人共用的契约：state schema、工具协议、trace 字段、thread 和会话的对应关系。这三样不定，后面各写各的。
2. 分工按职责而不是按人头平均拆文件：一个人负责编排和状态，一个人负责工具网关和业务权限，一个人负责检索、评测和观测。每段有一个能拍板的人。
3. 排期按风险递增。第一个月只做一条只读意图，日志要能排障。第二、三个月补多意图、槽位和越权拦截。第四个月才做有副作用的工具，带确认、取消和幂等。第五个月补评测、知识库更新和灰度。第六个月做压测、降级和故障演练。
4. 主动说依赖：写操作不要早于权限和幂等；灰度不要早于评测集。前四个月各写框架、最后两个月才联调，是这个排期要避开的走法。

### 3. 算法同学想换大模型、后端想稳 Spring 栈、产品要快上线，三方扯皮你咋拍板

**答题思路**

把三方的话翻译成同一个上线标准，再当场写下不做什么。

1. 先对齐第一期的用户任务、错误代价和延迟预算。没有这条，换模型和保栈都无法比较。
2. 「快」收成一条低风险闭环，例如只读查询。退款、投诉这类写操作不进第一期，写进排除项。
3. 入口、鉴权和工具网关继续用现有 Spring 服务。模型调用收口在网关后面，业务代码不绑定某一个供应商。
4. 换模型必须用固定评测集给出对照，赢了再按会话灰度，并保留切回的办法。会上不拿公开榜单当结论。
5. 写下负责人、验证指标和复盘时间。三个人都同意的空话不要当成决定。

### 4. LangChain4j 和 Python LangGraph 混部时，Java 侧 harness 怎么兜住 Python 服务挂掉

**参考答案**

结论：Java 是面向用户的控制面，Python 上的图是可替换的执行面。Python 挂了，请求要在 Java 里超时、熔断和降级，不能挂在一条没有时限的 RPC 上。

会话、鉴权、限流和最终回复放在 Java。Python 只接收这一次已授权的运行：租户、thread_id、输入和图版本。图状态的权威副本放在外部 checkpoint，不放在 Python 进程内存里。给用户看的消息可以在 Java 落库，续跑仍以 checkpoint 为准，两边用同一个 run 编号对账。LangChain4j 不要再保存一份会分叉的图状态。

调用使用有读超时的 HTTP 或 gRPC，并设置整次运行的截止时间。连接失败和 5xx 计入熔断。熔断打开后，只读问题走 Java 侧的模板或缓存；改订单直接告诉用户暂时做不了，不在熔断期间盲重试。

Python 恢复后，由持有租约的一个工人按原 thread_id 续跑。没有租约时，两个 Java 实例会把同一步执行两遍。节点按至少一次设计，工具带幂等键。就绪探针失败就把该实例从负载均衡摘掉。

### 5. harness 工程化：Agent 的 prompt、tool、state schema 怎么做版本管理和灰度

**参考答案**

结论：prompt、工具目录和 state schema 是同一份发布清单里的版本，一次运行从开始到结束绑定这一套。灰度按会话粘住，不在同一次运行中途换 schema。

每次发布记下 prompt 的哈希、工具 schema 版本、state schema 版本和图的代码版本。checkpoint 里保存写下它的那套版本。删字段、改字段含义、改 reducer 算不兼容变更：旧 checkpoint 不在新图上硬恢复，要么做迁移，要么让旧会话继续跑旧版本直到结束。

灰度按用户、租户或会话做稳定分桶。thread 在创建时粘到一个版本，避免前半段状态后半段读不懂。新旧工具可以并存，但一次运行只把对应版本的工具目录给模型。下线工具前，先看还有没有未完成的 thread 会调用它。

日志和评测都带这套版本号，否则灰度期间的成功率混在一起，无法判断是提示词、工具还是状态定义造成的。只灰 prompt、不灰工具 schema，模型会按新提示调用旧参数。

### 6. 多 Agent 系统评测集怎么建，任务成功率、工具选错率、人工接管率怎么埋

**参考答案**

结论：评测集是带期望的任务，不是闲聊样本。三个率从同一次运行的结构化轨迹里算，分母事先定义。

从真实会话抽样并脱敏，按意图分层：查商品、查订单、退换、投诉、弱意图、越权订单。每条包含输入和必要的上文、工具桩的返回、期望的关键事实，以及允许的工具集合。有副作用的用例打桩，不打生产。知识库用例绑知识版本。固定一份回归集，另加近期坏例。

任务成功指事先写好的条件成立，例如订单状态正确且没有错误的写操作。离线用规则或抽检过的评判；线上用用户确认、工单关闭且没有立刻重开做近似，并注明是近似。不要只用模型给自己打分。

工具选错率的分母是应该调用工具的任务。分子是调用了允许集合之外的工具，或对象错了，例如查错单。可以再拆成选错工具和参数错。人工接管率的分母是进入 Agent 的会话，分子要分开用户主动转人工，以及低置信、越权、超时导致的系统转人工。

每条轨迹至少埋 run 编号、租户、图版本、意图、每步工具名、是否被策略拒绝、结束原因。

### 7. RAG 知识库每天变（价格、库存、活动），增量更新和向量一致性怎么保证不召回旧文档

**参考答案**

结论：查询只能看见同一已发布版本的文档和向量。新版本全部写完并校验后，再原子切换指针；价格和库存优先走交易工具，不靠向量库的实时覆盖。

文档带 `doc_id`、版本和生效时间。向量的身份是文档、版本加块编号，并记录嵌入模型版本。更新时把新版本的块全部写入，核对块数和模型版本，再把「当前版本」切过去。切换用元数据里的指针，或搜索侧的别名。然后异步删除旧版本。先删后写会有空窗；按 `doc_id` 原地覆盖时，新版本块数变少，多出来的旧块仍会被召回。过滤条件要带当前已发布版本，删除不及时也能挡住旧块。

查询只能和同一嵌入模型写出的向量比相似度。换模型就整库重刷，版本一起变，新旧向量不要混进同一次检索。活动过期用生效时间过滤。价格、库存以交易系统为准，知识库只放说明；如果业务坚持要进向量库，TTL 必须短，并接受它仍可能落后于下单页。

### 8. MCP 和 Function Calling 在你系统里边界在哪，为什么不直接全上 MCP

**参考答案**

结论：Function Calling 是模型这一轮要调用哪个函数、参数是什么；MCP 是工具如何跨进程发现和执行。核心交易留在 Java 网关的函数调用里，跨团队复用的只读能力再挂 MCP。

函数调用的 schema 随这次请求交给模型，执行发生在同一套鉴权和审计里，少一跳，用户身份也在进程内。MCP 把列工具和调用工具标准化，适合多个 Agent 复用同一批外部能力。模型侧通常仍是函数调用，只是真正执行时转到 MCP 的 `tools/call`。

不全上 MCP，是因为退款和改订单要跟事务、幂等、订单归属绑在一起，多一跳动态发现没有收益，服务器的可用性还会变成核心链路的可用性。服务器返回的工具不能全塞给模型，必须再过允许清单。用户能不能查这张订单，协议不会自动知道，仍要在服务端用委托身份判断。

只读搜索可以放在 MCP 后面。无论哪边进来，审计和拒绝策略只有一套。

### 9. Claude Code 和内部 Agent 中台都有了，为什么还要自研薄编排层，自研部分只留什么

**参考答案**

结论：现成 Agent 和内部中台提供通用执行环境。自研只留电商链路特有的控制面，不再做一套模型网关、沙箱或向量库。

通用部分交给中台：模型接入和重试、代码或文件一类的沙箱、标准的调用轨迹。Claude Code 这类产品解决的是编程任务，不知道订单归属和售后规则，不能把它的循环直接当成客服运行时。

自研留下的是中台无法替你决定的部分。意图、槽位到查商品、查订单、退换货、投诉的路由，「帮我看看」如何绑定上文实体。退款限额、订单归属和人工确认。thread 与租户、会话的映射，以及 checkpoint 的生命周期。prompt、工具和 schema 的版本与灰度。评测集和业务上的成功率、选错率、接管率。模型不可用时，查单仍能走的模板降级。

薄的含义是一张小图或一个循环，节点调用自己的工具网关。图的续跑只能有一个权威状态，不要在中台和自研层各存一份。

### 10. 最近半年你啃过的最硬的一份源码或一篇论文是什么，哪块没看懂

**答题思路**

只讲你完整读过、并且和这条链路有关的一份。没读过的不要临场换一篇摘要。

1. 用一句话说明它要解决的问题。
2. 讲你顺着哪条路径读：入口函数和数据结构，或论文的方法部分。不要从简介念到结论。
3. 说当时没看懂的那一处，具体到一个分支、一个状态字段或一个公式。停在「还需要深入学习」等于没读。
4. 说明你后来怎么确认自己懂了：最小复现、断点，或对上一次线上行为。

如果这份材料是 LangGraph 的持久化实现，对方通常会追 thread_id 和 checkpoint_id 谁用来定位、失败的节点会不会重放、`interrupt` 之后副作用放在哪。只展开你真的读到的那几段。

### 11. 你是怎么判断一个新技术（比如新 embedding 模型）值不值得进生产链路的

**参考答案**

结论：用生产里的失败样本比过当前模型，再看重刷成本、延迟和能不能切回。公开榜单只作为候选名单。

评测集从线上坏例抽，按类目、长短文本和否定句分层，并固定知识版本。同时看召回位置、重排后的命中，以及最终回答是否答对，不只看向量相似度涨了多少。列出新模型修好的和改坏的。价格、库存数字、规则里的否定句不能退步。

维度会改变索引内存和查询延迟，端到端 P99 要放进原来的预算。换模型必须整库重刷，切换期间双索引的资源和时间要算进去。语义缓存会全部失效，这个成本一并算。新旧向量不能混在一个索引里比较。

上线时一小部分查询走新索引，会话粘住，保留一键切回旧索引的办法。高风险类目退步、重刷成本盖不住收益，或许可证说不清，就停在离线对照，不进生产。

### 12. 手撕算法：多 Agent 任务依赖成 DAG，给节点和边，输出拓扑排序；若存在环要检测出环路径

**参考答案**

结论：边 `u → v` 表示 u 完成后才能做 v。用深度优先的三色标记：白是未访问，灰是正在访问，黑是已完成。碰到灰节点就是环；无环时，把完成顺序反转，得到拓扑序。

Kahn 算法能发现剩余入度不为零的点，但环上的具体路径还要再搜。三色标记在回边处就能从递归栈取出路径。发现环就返回这一条，起点再重复一次作为结尾，同时不返回拓扑序，因为整个图的拓扑序不存在。自环会得到两个相同节点。节点按名称排序后再遍历，结果稳定，任何合法拓扑序都对。

时间 O(V+E)，空间 O(V+E)。

```java
import java.util.ArrayList;
import java.util.Collections;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

final class AgentDag {
    static final class Result {
        final List<String> order;
        final List<String> cycle;

        Result(List<String> order, List<String> cycle) {
            this.order = order;
            this.cycle = cycle;
        }
    }

    static Result sort(List<String> nodes, List<String[]> edges) {
        Map<String, List<String>> adj = new HashMap<>();
        for (String node : nodes) {
            adj.put(node, new ArrayList<>());
        }
        for (String[] edge : edges) {
            adj.computeIfAbsent(edge[0], key -> new ArrayList<>()).add(edge[1]);
            adj.computeIfAbsent(edge[1], key -> new ArrayList<>());
        }
        for (List<String> next : adj.values()) {
            Collections.sort(next);
        }
        List<String> names = new ArrayList<>(adj.keySet());
        Collections.sort(names);

        Map<String, Integer> color = new HashMap<>();
        List<String> stack = new ArrayList<>();
        List<String> post = new ArrayList<>();
        for (String name : names) {
            if (color.getOrDefault(name, 0) == 0) {
                List<String> cycle = dfs(name, adj, color, stack, post);
                if (cycle != null) {
                    return new Result(null, cycle);
                }
            }
        }
        Collections.reverse(post);
        return new Result(post, null);
    }

    /** 0 白，1 灰，2 黑。发现环时返回路径，否则返回 null。 */
    private static List<String> dfs(
            String node,
            Map<String, List<String>> adj,
            Map<String, Integer> color,
            List<String> stack,
            List<String> post) {
        color.put(node, 1);
        stack.add(node);
        for (String next : adj.getOrDefault(node, Collections.emptyList())) {
            int state = color.getOrDefault(next, 0);
            if (state == 1) {
                int from = stack.lastIndexOf(next);
                List<String> cycle = new ArrayList<>(stack.subList(from, stack.size()));
                cycle.add(next);
                return cycle;
            }
            if (state == 0) {
                List<String> cycle = dfs(next, adj, color, stack, post);
                if (cycle != null) {
                    return cycle;
                }
            }
        }
        stack.remove(stack.size() - 1);
        color.put(node, 2);
        post.add(node);
        return null;
    }
}
```
