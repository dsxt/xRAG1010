## 一面

### 1. 自我介绍

**答题思路**

控制在一分半到两分钟，按「我是谁、做过什么、为什么匹配」讲，停在一个能往下挖的项目上。

1. 年限、主语言和系统类型。Java 后端转 AI 应用，就直接说清现在写的是在线服务，还是离线实验。
2. 只讲一个真上过线的 Agent 项目：用户是谁，解决什么问题，你负责的是工具接入、检索、循环还是稳定性。
3. 补一个你能展开的取舍或结果。有真实数字再说数字，没有就讲当时放弃了哪条方案。
4. 收到旅行场景：查询、政策和交易在一条链路里，你想做的是能扛超时和改口的服务。

不要在开场把后面的技术题都答一遍。

### 2. 讲一个你落过的 AI Agent 项目，从用户提问到最终回答完整链路说一遍

**答题思路**

面试官在确认你真的跑通过。用自己的项目填下面这条链，每一步说清输入、输出和你写的代码落在哪。

1. 请求进入：鉴权、会话 id、用户时区和渠道。登录态沿用原业务，不在提示词里传证件号。
2. 理解：意图和槽位。缺日期、城市、场馆这类关键槽位时先追问，有副作用的工具先不调。
3. 分流：高频、步骤固定的走工作流；需要临时决定的才进模型循环。
4. 检索：政策类问题先查知识库，片段带条款 id 和知识库版本。
5. 工具：模型只能提出调用。代码做 schema 和业务校验，再调原有机票、酒店、订单接口。
6. 观察：工具结果写回状态。超时记为未知，不记为成功或空结果。
7. 结束：信息够了就汇总。出站前核对回答里的航班号、价格、订单状态都能在工具结果里找到。
8. 留下：检查点、trace、token 和工具状态，供回放和排错。

准备一个你真实修过的断点，按「现象、定位、改法、怎么验证」讲。没做过的层直接说了解原理、没有落地。

### 3. Java 线程池参数怎么配，IO 密集和 CPU 密集在 Agent 服务里怎么取数

**参考答案**

结论：IO 和 CPU 分池。IO 池按在途请求数估算，再被下游配额截断；CPU 池按核数配。卡住模型供应商的是信号量，不是把线程数开得很大。

LLM 和工具 HTTP 几乎一直在等网络。教科书公式是线程数约等于核数乘（1 + 等待时间 / CPU 时间），它假设你要喂满 CPU。模型调用的等待占比很高，算出来会远大于供应商允许的并发，也会撑大平台线程的内存。实际取数按在途并发 ≈ QPS × 平均耗时估算。例如目标 10 QPS、下游耗时 2 秒，在途大约 20，池子要容得下这 20 个等待，队列保持很短，满了就拒绝并返回明确的忙提示。调用方若是 Web 容器线程，拒绝后由容器线程立刻返回，避免容器线程被拖进去一起等。

Java 21 及以上可以用虚拟线程承载这种阻塞 IO，同时用信号量把打到模型和各下游的并发限制在配额内。虚拟线程减少的是线程占用，不提高供应商的限额。

本地嵌入、重排、大 JSON 解析吃 CPU，池大小靠近核数，和 IO 池分开，避免重排占住等待模型的线程，也避免 IO 排队把 CPU 任务饿死。线程池提交任务时要带上 trace 和日志上下文。核心线程数以压测修正，脱离耗时和配额没有通用值。

### 4. Spring Boot 里你是怎么把 Agent 能力嵌进已有微服务的，不走重造轮子思路

**参考答案**

结论：原有机票、酒店、订单服务继续做领域真相和事务，Agent 只加一层自然语言入口，把已有客户端包成工具。

做法是在现有 Spring Boot 应用里加一个模块，或者加一个独立的 BFF，而不是重写订单状态机。对话端点接收会话并流式返回；原来的下单、退款接口协议不动。Spring AI 的 `ChatClient` 负责模型协议，工具用 `ToolCallback` 调用已经在用的 Feign 或 Dubbo 客户端。验价、库存、退改费仍由原服务计算，提示词只描述参数和结果含义。

用户身份从网关登录态放进工具上下文，工具内做资源校验，例如只能查本人的订单。模型看不到下游的内部地址。灰度用配置开关按用户放量，旧入口保留。会话、trace 和工具权限走统一网关，新业务以后也从这里接。

这样嵌入的边界是：模型收集参数、选择已注册的工具、组织说明；提交、幂等和状态迁移留在原服务。把订单状态机搬进提示词，才是重造轮子。

### 5. 意图识别在你项目里是模型做的还是分类器做的，为什么这么选

**参考答案**

结论：生产上用混合。高频、槽位固定的意图走分类器或规则，开放说法和组合意图走模型，由置信度和槽位是否齐全决定能不能直接执行。

全用模型能覆盖改写，但头部查询量大，延迟、成本和结果波动都不合适，标签空间也不如分类器好回归。全用分类器延迟稳、可以对着枚举做评测，可是旅游说法变化大，互斥的单标签会把后半句丢掉，「退改宽松的上午航班，再加海边的酒店」会被收成其中一个类。

做法是分类器先出 top 意图和置信度。置信度高且槽位齐，进入对应工作流。置信度低、命中多个领域，或句子里明显有两件要办的事，交给模型按 schema 输出意图列表和槽位。路由只接受代码里登记过的意图，模型不能发明一个没有工具的类别。阈值放在留出集上调，写操作宁可不放行也先追问。

### 6. 意图歧义或漏识别时怎么兜底，举例说一个旅游场景的组合意图

**参考答案**

结论：歧义就追问关键槽位，漏识别就保留原话进入开放检索或人工，不把低置信结果强行映射到最近的类，更不据此调用写操作。

组合意图的例子：「国庆带父母从北京去三亚，要直飞，酒店看海，老人机票退改要松。」这里同时有机票、酒店和政策三类需求。日期只给了「国庆」，机场有首都和大兴，退改「松」也不是可执行参数。兜底顺序是：抽出已确定的城市和人员，向用户确认出发日期范围和机场；机票查询可以先并行直飞约束；「看海」作为酒店过滤条件；「退改要松」必须等舱位候选出来后去查对应规则，由检索结果解释什么叫松，模型不直接承诺手续费。

漏识别时，原话和已填槽位都留在状态里。开放问题走知识检索；仍然对不上已注册意图，就说明没理解并给出可选项，或者转人工。分类器只返回了一个「查机票」时，代码仍要看原话里有没有酒店、政策这些残留需求，避免后半句被丢掉。

### 7. RAG 里 Chunk 切大切小各有什么坑，你实际怎么切业务文档

**参考答案**

结论：业务规则按条款边界切。检索用小块，送给模型用完整条款；切多大由「单独拿出来会不会答错」决定，不先写死一个长度。

切太大时，一块里有多个主题，向量被稀释，检索既不容易命中，又把无关条款送进上下文，模型会引用错条款。切太小时，「起飞前 2 小时」和「手续费 20%」分属两块，只召回任意一块都会答错。固定重叠只能接住被拦腰截断的句子，补不回条款之间的条件关系。

退改签、行李、酒店取消这类文档，按标题、条款号和表格切。例外、表格和费用阶梯整段保留。子块用来检索，父块或整条条款用来生成，子块上带着标题路径和条款 id。查询侧可以用同一套结构先定位条款，再展开。长度从几百 token 的子块试起，用带正确条款 id 的评测集看引用是否命中，而不是看向量分数高不高。

### 8. 混合检索怎么融 BM25 和向量，RRF 还是别的，为什么

**参考答案**

结论：没有点击标注时，用 RRF 融合两边的名次，再把融合后的前若干条交给重排。航班号、机场三字码、条款编号靠 BM25，口语改写靠向量。

BM25 分数和余弦相似度的量纲不同，直接加权要先归一化，权重大小还跟着查询类型变，航班号查询和自然语言查询不是同一套权重。RRF 只使用名次：一条文档的分数是各路排名里 `1 / (k + rank)` 的和，某一侧没有召回到它，那一侧就不加分。论文里常用的 k 是 60，上线以自己的评测为准。

两边各自取一段候选，取并集后做 RRF，再截断给交叉编码器。有点击或人工标注之后，可以在这些特征上再学一个融合器；没有标注时，RRF 比手调权重稳。融合解决的是候选集合，精确顺序交给重排，端到端对不对还是要看生成是否引用了正确条款。

### 9. ReRank 模型上线后和没上之前，召回质量怎么量化

**参考答案**

结论：固定候选的生成方式和后面的生成模型，只比较「真正送进模型的那 K 条」以及据此做出的回答。

离线用同一批标注查询，看 Recall@K、MRR 或 nDCG。K 取生成窗口里的条数，不取向量库内部的一个更大的数。相关文档按条款 id 标，退改签可以按条款相关程度打分级，这时 nDCG 比只看命中更合适。生成模型和提示词保持不变，再看回答是否引用了正确条款，避免检索分上升、答案反而变差。

线上用影子流量或会话级分流，记录空召回、重排耗时、引用命中和人工抽检。抽样时把「没召回到」和「召回到了但生成改了」分开。重排模型会把正确条款挤出窗口：前排看起来更干净，任务完成率可能下降，所以两个方向都要看。

### 10. Function Calling 的 JSON Schema 你是怎么定义的，参数写错模型会怎样

**参考答案**

结论：schema 写清字段、类型、必填和枚举，执行前用 schema 和主数据各校验一次。结构错或业务不合法都不调用下游，把错误作为工具结果交回模型，并限制重试次数。

```json
{
  "name": "search_flights",
  "description": "按出发地、目的地和日期查询航班。只读，不会下单或占座。",
  "parameters": {
    "type": "object",
    "additionalProperties": false,
    "required": ["origin", "destination", "date"],
    "properties": {
      "origin": { "type": "string", "description": "出发城市或机场三字码" },
      "destination": { "type": "string", "description": "到达城市或机场三字码" },
      "date": { "type": "string", "description": "出发日期，YYYY-MM-DD，按用户时区" },
      "sort": { "type": "string", "enum": ["departure_asc", "price_asc"] }
    }
  }
}
```

Spring 里用 `ToolCallback` 从参数对象生成 schema，描述里写明只读还是会改状态。缺字段、类型不对、枚举越界，在调用前被 schema 拦住。机场不存在、日期早于今天，schema 可以通过，要由代码对主数据再查一次。「明天」由代码按用户时区和注入的时钟换算，不靠模型自己算。供应商若支持严格的工具调用格式，可以减少非法 JSON，但减不掉语义错误。

模型收到错误后仍可能改错，所以重试有上限，用尽就向用户追问。退款、下单即使 schema 通过，也要再过权限和状态机。

### 11. Agent Loop 里一次模型调用前你会做哪些事，上下文压缩放在哪一步

**参考答案**

结论：压缩放在发起这次模型调用之前，工具的超长结果则在写入状态时先裁剪。模型调用前先装上下文、收工具、卡预算，再发请求。

一次调用前的顺序是：

1. 读取已提交的会话、槽位和计划版本，丢掉旧版本晚到的结果。
2. 装入系统约束、当前目标、未完成步骤和最近对话，并按本轮角色过滤工具 schema。
3. 这一步需要知识，就先检索，片段带条款 id 和知识库版本。
4. 估算 token。超过预算时压缩：完成掉的工具原文收成短结论，保留系统约束、当前用户目标和还没被消化的最新观察。
5. 检查步数、墙钟、费用和相同参数的重复调用。超限就停止，返回已经确认的部分。
6. 然后才调用模型。返回后只解析工具调用或最终回答，执行在代码里。

压缩若放到模型内部，窗口已经超了，请求发不出去。只在对话很长时才摘要，会漏掉单次工具结果就把窗口撑满的情况，所以观察写入和调用前各做一次。

### 12. Redis 在 Agent 系统里你拿它存什么，会话状态还是工具结果缓存

**参考答案**

结论：两类都放，键、TTL 和耐久性分开。会话的准以可恢复存储为准，Redis 放热数据和租约；工具缓存只放可重算的读结果。

会话热数据包括槽位、计划版本、近期消息指针和分布式租约。租约用 `SET key token NX PX`，续跑时核对 token，避免两个进程一起往下执行。Redis 淘汰或主从切换会丢热数据，所以每步提交仍写数据库检查点，Redis 用来加速读取和互斥。

工具缓存的键是工具名、规范化参数，以及会影响结果的版本（知识库版本或库存口径），TTL 按数据变化速度定。航班查询是分钟级，不按天缓存。下单、占座、退款不进结果缓存。缓存击穿时对同一个键做单飞，避免超时风暴把下游打满。

两边如果混在同一个会按内存淘汰任意键的实例里，工具缓存的流量可能把会话热键挤掉。会话仍然要能从检查点恢复。trace 和完整工具原文进可持续存储，不放在 Redis 里当唯一副本。

### 13. 场景题：用户说「帮我看明天上海飞北京最早的航班，再推个离会场近的酒店」，怎么拆任务、调哪些工具、怎么汇总结论

**参考答案**

结论：拆成约束加上两个只读查询。会场未知就先查航班并追问，酒店不猜坐标；汇总只使用工具返回的字段。

槽位里可以确定出发城市上海、到达城市北京、日期是明天、航班按最早起飞。酒店依赖会场位置，句子里没有，这是缺失槽位。人数和舱位未知时，航班查询可以标明按经济舱、1 位成人这些默认值，酒店不能编一个地标。

工具是城市到机场、航班查询、会场地理解析、按坐标或地标查酒店，全部只读。机场码解析完才能查航班；会场坐标有了才能按距离查酒店。两个查询彼此独立，会场已知时并行。上海有浦东和虹桥，北京有首都和大兴，城市对城市的「最早」要把多个机场纳入，否则会漏掉真正最早的一班。

会场未知时只发航班查询，同时追问会场，不调用酒店工具。代码按起飞时间排序，回答保留航班号、时刻、机场和价格。酒店按距离取前几条，并说明入住离店的默认日期。模型组织语言。出站核对航班号和时间必须出现在工具 JSON 里。红眼航班和落地机场要在回答里说出来。

### 14. 场景题：模型返回「退款已成功」但后端实际调用支付网关超时，怎么防这个幻觉

**参考答案**

结论：退款是否成功只由支付网关的明确确认决定。超时是未知，对外说处理中，模型和文案都不能把它说成成功。

写操作先落一条带幂等键的处理中记录，再调网关。超时或连接断开时，工具返回未知，不返回成功，也不返回失败。恢复时用同一幂等键向网关查询：查到成功才是成功，查到失败才是失败，仍然查不到就保持未知，进入对账。下游支持幂等时，重放使用同一键；不支持时不自动再退一次。

给用户的状态句由这条状态生成。出站核对发现「已成功」，就必须有状态为成功且带网关单号的工具结果，否则改写成已提交、结果未确认。模型没有调用退款工具就声称成功，同样拦住。

超时不等于失败。对用户说退款失败、请再试一次，可能造成重复退款。未知状态的口径是处理中，等待确认。

### 15. 最近在看什么 AI 工程化东西，Spring AI 还是 LangGraph，说一个你不喜欢的点

**答题思路**

先说你真的在写的那个，再说一个你碰到过的具体限制，以及你因此把哪件事收回到自己的代码里。下面两个点按实际经历选一个，不要两个都展开。

Spring AI 适合把模型和工具嵌进现有 Spring Boot：`ChatClient`、`ToolCallback`、Advisor、向量库和 MCP 都顺着 Spring 的自动配置走。可以说的限制是，它把一次模型调用和工具循环包装得比较好，分支、人工确认和可恢复的步骤状态仍要自己写。订票这种有状态迁移的流程，框架替你做协议，状态机还是在业务代码里。

LangGraph 把状态图、检查点和人工插入做成了一等能力，长任务更好看。可以说的限制是，图恢复和下游副作用不是同一件事。占座、支付在图的检查点之外还有网关那一侧的未知状态，只把图重放一遍不能代替幂等键和对账。图变大以后，分支条件散落在边上，比一张显式的业务状态表难查。

收尾讲你怎么补：图或 Advisor 负责推进，写操作的合法性留在工具网关。

### 1. 自我介绍

**答题思路**

一分钟以内，不重复一面的项目编年，把钩子放到编排。

1. 一两句交代身份和栈。
2. 点明你做过的多步任务：计划从哪来，哪些步骤是固定流程，哪些交给模型。

### 2. 你们 Agent 编排是 ReAct 还是 Plan-and-Execute，长任务为什么最后选了后者或混合

**参考答案**

结论：长的订票订酒店任务用混合。全局是 Plan-and-Execute，步骤内部才用有界的 ReAct 处理局部失败。

ReAct 把推理和一次工具调用交替进行，适合短、探索性强、下一步取决于上一次观察的任务。任务一长，它没有可持久化的全局计划，容易漂移，也难在重启后说明做到了哪一步。Plan-and-Execute 先产出步骤，再逐步执行，计划本身可以检查、保存和局部重做。它的问题是计划会过期，用户改口或库存变化后要重规划。

旅行场景的步骤大体知道：解析城市、查航班、查酒店、解释规则、确认后再写订单。这些适合先落到一份结构化计划上，执行器按步骤调用工具，失败时只重做该步。纯计划执行不会在工具报「日期不合法」时改参数，所以步骤内部允许模型根据这次错误做有限次修正。修正不能改变已经确认的槽位，也不能跳过验价直接占座。

选择混合，是因为长任务要能审计和续跑，而局部错误又需要模型看过观察再决定。全局循环若也是 ReAct，副作用的顺序守不住。

### 3. 多 Agent 怎么分工，Router / Planner / Worker / Reviewer 各自边界在哪

**参考答案**

结论：四个角色按「能不能执行工具、能不能改计划」切开。Router 和 Reviewer 不执行写操作，Planner 不直接改外部世界，Worker 只完成分给它的一步。

Router 判断进入哪条业务或是否该追问，输出登记过的意图。它不拆详细步骤，也不订票。Planner 读槽位和检索到的约束，产出结构化计划或 DAG，不调用占座、支付。Worker 拿到单步输入和这一步允许的工具，返回结构化观察，不改别的步骤，也不替用户放宽条件。Reviewer 对照计划、工具结果和草稿，检查字段有没有编造、约束有没有丢，可以打回。它不能为了「补全答案」自己去调写工具。

边界写在各自可见的工具列表和输出 schema 上。四个角色共用一个大提示词、同一套工具，分工只是名字不同，线上分不清是谁做的决定。

### 4. 多 Agent 共享工具注册表但限制某些角色不能调工具，怎么在工程和提示词两层同时卡住

**参考答案**

结论：提示词里只出现该角色允许的工具；网关在执行前按角色再查一次注册表。两层都做，能不能执行以代码为准。

注册表每一项带允许的角色、读写类型、超时和风险等级。组装某轮请求时按角色过滤，模型拿到的 schema 里就没有退款或占座。提示词写明这个角色的职责和可用工具，用来减少无效调用。

模型仍可能输出一个没给过的工具名，注入的文本也可能诱导它这么做。网关按注册表拒绝，把拒绝结果交回模型，并记审计。下游服务保留自己的鉴权，不因为调用来自 Agent 进程就信任。Reviewer、Router 的服务身份本身没有写权限。

只在提示词里写「不要调用退款」，模型看见 schema 就仍能调用。只做网关、仍把全部 schema 放进上下文，无效调用和提示注入会多很多。过滤可见工具和拒绝执行一起做，才同时减少诱惑和堵住绕过。

### 5. Agent 间传递上下文是传全量还是传结论，上下文爆炸怎么压

**参考答案**

结论：交接传结构化结论和引用，不传全部推理和工具原文。全文在会话存储里，需要时按 id 再取。

一份交接包含用户目标、已确认槽位、计划版本、这一步的输入、上一步的短结论和未决问题。Worker 要核对航班时刻时，按引用拉取那次工具结果，而不是把所有 Worker 的输出堆进 Planner 的下一轮。

每个交接有 token 上限。已完成步骤只留结论和状态。槽位和工具 id 是事实来源，散文摘要可以重写。最新的用户改口，以及当前步骤还没消化的工具结果，保留可用的原文。思考过程不交给下一个角色。

爆炸通常来自每跳都复制全量历史。压的办法是共享一份状态，各角色只看自己的视图。摘要如果把航班号和来源 id 压没了，Reviewer 就无法核对，所以结论里留关键字段和引用。

### 6. DAG 工作流和自主 Agent 在携程这种订票订酒店场景里怎么共存

**参考答案**

结论：交易路径用 DAG 固定，Agent 把自然语言变成 DAG 的输入，并只在已经存在的分支上处理歧义和改口。

查航班、验价、占座、支付有顺序和副作用，做成工作流节点。节点能不能进入由代码判断，例如没有同一次验价成功就不能占座。机票和酒店可以是两个并行子图，在汇总节点会合；「落地后再入住」写在依赖边上。

Agent 负责意图、槽位、政策解释，以及在无库存、用户改排序这类节点上选择下一条已有的边。它不能新造一条绕过确认或支付的边。自主循环包在节点内部，例如退改规则没召回到时改写查询，步数有上限。

两套引擎要读写同一份会话状态和计划版本。工作流和模型各记各的进度，改口时就会一边作废、另一边仍把旧结果汇总进去。

### 7. RAG 知识库版本变了（比如退改签规则更新），线上怎么热更不闪断

**参考答案**

结论：新规则写入新版本索引，评测和预热之后原子切换读指针。进行中的请求粘住进入时的版本。退改签按票适用的生效区间过滤，不只按「当前最新」。

新文档按条款切分，带上版本、生效时间和适用条件，用与线上相同的嵌入模型和维度写入新集合。用固定评测集看召回，通过后先预热新索引，再切换别名或读指针。不在旧集合上原地覆盖，避免读到写了一半的数据。

请求开始时记下知识库版本，这一轮的检索、缓存键和回答都用它，避免前半段旧规则、后半段新规则。缓存键带版本，切换后旧缓存不会被新请求命中。旧版本保留一段时间，回滚就是把指针切回去。

已出票订单的退改咨询，要命中购票时适用的规则版本。只把「现在对客政策」热更成唯一答案，历史订单会答错。切换的是读指针，不是重启应用，所以没有版本闪断。

### 8. Embedding 模型要和召回场景对齐，你怎么做领域微调或替换选型

**参考答案**

结论：用领域检索评测集选型。查询和文档必须同一模型、同一归一化和同一套查询指令。换模型或微调后整库重嵌，新旧向量不能混在一个索引里查。

评测集用真实问法，标注应命中的条款，看与线上窗口一致的 Recall@K 和 nDCG。通用榜单只适合初筛。先确认切分、元数据和 BM25 没有明显问题；缺口确实是领域说法对不上，再换模型或做对比学习。微调的样本是查询、正例条款和硬负例，硬负例取现在召回错的近邻。

换维度、换相似度或换模型，都新建索引，按知识库热更的方式切换。模型要求查询侧指令前缀时，评测和线上使用同一前缀。重排已经能把正确条款放到窗口里时，优先调重排，因为嵌入一变就要重嵌全库，回滚成本更大。

只重嵌一部分文档，或微调后查询仍用旧模型，相似度不再可比，这是选型时最常见的对齐失败。

### 9. MCP 和你现在用的 Tool Callback 是什么关系，接 MCP 后老工具怎么迁移

**参考答案**

结论：Tool Callback 是进程内的执行接口，MCP 是跨进程发现和调用工具的协议。接上之后，模型看见的仍是工具名和 schema，变化在适配器和传输。

Agent 循环只依赖工具描述和一次调用的结果。本地 `ToolCallback` 直接进 Java 方法。MCP 客户端用发现接口拿到远端工具，用调用接口执行，再适配成同一个 `ToolCallback`，注册进同一张表。循环不用为远端单独写一套。

迁移时保持工具名和参数 schema 不变，用契约测试对比旧回调和 MCP 公布的 schema。只读工具先灰度，下单和退款仍走本地回调，直到幂等键、超时、错误码和权限在 MCP 路径上一致。远端单独鉴权，不把网络可达当成授权。业务错误映射成原来的工具错误结构，模型侧的重试不用分叉。追踪上下文放进 MCP 的元数据，远端 span 才能接上同一次请求。

### 10. Harness 层你理解该管什么：loop 控制、状态恢复、trace、预算熔断讲讲

**参考答案**

结论：Harness 是模型外面的运行时，管循环能不能停、状态能不能恢复、一次执行能不能被追踪、时间和费用有没有熔断。这些不交给模型自律。

循环控制包括步数上限、停止条件、工具调用解析、相同参数的重复调用检测，以及失败后重试还是把错误交回模型。工具由网关执行。

状态恢复要求每步提交后写检查点：槽位、计划版本、幂等键和已确认结果。进程重启从最后一次提交继续，不从内存里的半截推理继续。

Trace 里，一次用户请求是一条 trace，每次模型调用、检索和工具调用是子 span，带会话 id、模型名、提示词版本、token 和工具状态。

预算在发请求前扣：token、工具次数、墙钟和费用估算。超限就返回已确认的部分，并标明哪一步没做完。下游错误率升高时熔断写操作，只读查询或转人工可以保留。

熔断若只写在提示词里请模型节约 token，请求已经发出去就停不住。预算必须是发调用前的代码判断。

### 11. Agent 执行到一半进程重启，session 怎么续跑，工具半成功状态怎么清理

**参考答案**

结论：从最后一次已提交的检查点续跑。写工具在调用前就落幂等键；重启后先查询下游，确认不了就进入对账，不盲目再执行一次。

会话状态在数据库里，Redis 只做热缓存和租约。每完成一步提交槽位、计划版本和工具结果。重启的工作者要拿到租约，并用 fencing token 写入，旧进程迟到的写入因 token 不符被拒绝，避免两个进程把同一次订票往下做。

读工具没有副作用，未完成就重试。写工具的记录在调用前是处理中。恢复时用同一幂等键查询：下游已成功，就把结果补进检查点；下游已失败，按失败处理；下游也是未知，保持未知并交给对账或清扫任务。补偿，例如释放占座，是明确的逆向工具，同样走幂等键。

模型上下文可以重放，下游的半成功不能靠把提示词再跑一遍来清理。

### 12. 场景题：机票查询工具返回空，是重试、换参数、还是直接告诉用户没票，决策权给模型还是代码

**参考答案**

结论：传输失败才按同一参数重试。合法查询返回空列表是业务结果。能不能改参数由代码里的放宽阶梯决定，模型负责说明和追问。

先分清返回。超时和 5xx 用有限次、带退避的重试，读请求本身可重复。参数已经通过机场和日期校验、结果是空列表时，再用同样的参数打一次没有新信息。

放宽写成策略，例如可以提议次日或同一城市的另一个机场，不能静默改成另一个城市。代码执行放宽，并在状态里记下用户原话是明天、当前结果是后天。阶梯之外的改写直接拒绝。默认回答是这条查询没有航班，并询问是否看下一个允许的选项。

合法性、重试和放宽阶梯在代码。话术，以及在阶梯内部选哪一个建议，可以交给模型。空结果和调用失败若走同一个分支，就会对真的没票反复重试，或者把超时说成没票。

### 13. 场景题：三个 Worker 并行查航班、酒店、签证政策，其中一个超时，最终结果怎么聚合

**参考答案**

结论：按每个分支自己的截止时间汇合，结果带上成功、超时或失败。必选分支没有数据，最终答案就写明缺了这一块，不让模型补。

航班、酒店、签证各自计时，互不相等到把整次请求拖死。超时的分支取消在途调用。聚合器只读结构化结果。必选和可选按产品定：用户要订机票时，航班是必选，签证政策可以是可选。必选超时，先做一次有限重试或读缓存；仍然没有，回答里写航班这次没查到，酒店和签证按实际状态附上。可选取超时，就返回另外两项，并写明签证政策本次没有查到。

生成只使用状态为成功的数据。出站检查回答里没有描述那个超时分支。把三份文本交给模型自由合并，超时很容易被写成「签证一般没问题」。

### 14. 场景题：用户在中途改口「不要最早了要最便宜」，原 Plan 怎么作废重规划

**参考答案**

结论：把排序从最早起飞改成最低价，当成约束变更。只作废依赖它的步骤，计划版本加一，旧版本晚到的结果丢弃。

槽位更新后，依赖所选航班的步骤过期：航班列表、已选航班，以及按到达时间推算的入住安排。只跟会场有关、且不依赖具体航班的酒店条件可以保留。城市、日期、会场这些没被改口否定的槽位继续用。

旧计划若已经占座或锁价，先用幂等键释放，再展示新方案。还在飞行中的旧查询允许返回，但不写入新版本。重规划从变更点往后生成步骤。回答说明保留了什么、重查了什么。

只在提示词里说「按最便宜重新来」、不升版本，最早那班的结果晚到后仍会进汇总。作废的是依赖链和版本，不是把整个会话删掉重开。

### 15. Java 侧怎么把 LLM 调用、工具调用、MySQL 写入放在同一个分布式链路追踪里

**参考答案**

结论：一次用户请求一条 trace。模型调用、工具调用和 MySQL 写入是子 span。跨线程和跨进程时把同一份追踪上下文传下去。

入口用 OpenTelemetry 建 span，属性里放会话 id。循环中每次 LLM 调用、每次工具调用各开子 span，记录模型名、提示词版本、token、工具名和状态。写检查点的 SQL 落在同一条 trace 下。生成式调用的模型名和 token 按 OpenTelemetry 的 GenAI 语义约定记，换采集后端时不用改埋点含义。

断点常在业务线程池。提交任务时用当前上下文包装 runnable，日志 MDC 一起传，否则工具和 SQL 会变成没有父 span 的新 trace。HTTP 客户端自动注入 `traceparent`。MCP 或自研 RPC 没有自动注入时，把追踪上下文放进元数据。

提示词正文和证件号不进追踪系统。需要回放时，正文在受控的会话存储里，trace 上留哈希和引用。只有网关一条访问日志时，循环里的第二次模型调用和事务提交对不上。

**答题思路**

这一轮看判断。一分半，少讲接口细节。

1. 身份和角色按事实说：负责人、核心开发，还是某个模块的 owner。

### 2. 你带过 Agent 项目么，几个人，怎么拆 Harness 和模型实验的边界

**答题思路**

人数和头衔用真实的。没带过就说清自己拥有的模块，不编团队规模。

带过的话按这个顺序：

1. 几个人，工程、算法、业务各多少，都用真实数字。
2. 工程拥有运行时：工具网关、状态、权限、trace、预算和发布。模型实验拥有提示词、模型选择和检索参数的候选。
3. 两边共用工具 schema、会话状态和同一套评测集。实验走影子或灰度，写操作仍过工程网关，不另开一条能直接打生产的链。
4. 指标过线才进生产配置，配置可以回滚。你守的是这道门。

### 3. 算法同学想调 prompt，工程同学想稳链路，冲突了你怎么拍板

**答题思路**

把冲突写成一次可比较的发布，不站队。

1. 复述两边：一边要回答质量，一边要错误率和延迟不退步。
2. 先宣布这条业务的顺序。旅行交易里，写操作正确、不编造结果，优先于文案变好；然后是任务完成率；然后是延迟预算；成本在前面几项守住之后再优化。
3. 提示词和代码走同一道门：离线评测、小流量、可回滚。先在只读场景放量。订票和退款保持原路径，直到工具顺序和幻觉指标没有回退。
4. 给出决定、看哪些指标、什么时候重新讨论。质量升了但出现越权或乱序工具调用，这次不发布，让提示词在工具集合已被代码限制的环境里再改。
5. 你的角色是守指标，不是替任何一边改方案。

### 4. Agent 效果评测集怎么建，golden dataset 从哪来，回归怎么跑

**参考答案**

结论：评测集标的是意图、关键参数、工具顺序和必须遵守的事实，不只标一段标准答案。调参和留出分开，提示词、模型、索引和 Harness 的改动都跑同一套回归。

来源有五类：脱敏后的线上对话，由人标意图、槽位、应调用的工具和必须出现的字段；业务专家写的政策题，附正确条款 id；用模板铺开日期、城市、排序的组合，再人工筛掉不自然的句子；事故和投诉回放；对抗样本，包括诱导模型谎称退款成功。

每条用例包含输入状态、允许的工具、关键参数、顺序约束，以及回答里必须出现和不能出现的内容。用词可以变，所以不断言整段文案，而断言航班号、状态和条款这些结构化结果。

回归在 CI 里用工具回放跑，保证确定性。留出集不拿来改提示词。另有一小批夜间用例走沙箱里的真实工具。写操作或退款的关键用例失败就挡住发布；其余指标事先定好允许的波动。数据集本身有版本，否则无法解释分数变化来自评测集还是来自系统。

### 5. 任务完成率、工具调用准确率、幻觉率、P99 延迟、单轮 Token 成本这几个指标打架时先保哪个

**参考答案**

结论：先保不做错事，也就是写操作的工具准确率和副作用上的幻觉；再保任务真的完成；延迟守在产品时限内；单轮 token 成本在前三项站住之后优化。

任务完成率会被「回答很顺、其实没订成」抬高，所以它不能单独当第一指标。工具调用准确率，尤其是占座、支付、退款的工具名、关键参数和顺序，以及「退款已成功」这类断言必须有工具证据，是完成率的前提。这两项退步时，完成率上升也不发布。

P99 超了，正确结果也送不到用户面前。用并行只读查询、缩短上下文、把非关键步骤换到更小的模型里去追时限，而不是放宽工具校验。成本用路由和缓存降，前提是幻觉和工具顺序的护栏还在。

只读问答可以把完成率和延迟放得更靠前。一到会改订单的路径，顺序就回到：不产生错误副作用，再谈完成、时限和成本。

### 6. 多 Agent 系统线上出问题，trace 里只有最后答错，怎么定位是 Planner 拆错还是 Worker 调错工具

**参考答案**

结论：先看有没有计划产物和每次工具的请求。计划已经违反用户约束，就是 Planner；计划对、工具名或关键参数偏离计划，就是 Worker；工具结果对、最终文本对不上，就是汇总阶段的幻觉。

只有最后一句答错，说明检查点没留下计划，span 也没留下工具参数，归因做不满。能补的旁路是工具网关的审计日志和会话里的计划版本。有完整 trace 时按这个顺序看：

1. Planner 的输出是否丢掉或改写了约束。用户要最早，计划却按价格查，或漏了酒店，责任在 Planner。
2. 计划正确，Worker 调用的工具或关键参数和该步不一致，责任在 Worker，或在发给它的工具列表。
3. 参数正确、工具结果正确，最终回答对不上结果，责任在汇总或 Reviewer，不是拆解错误。
4. 工具把超时映射成了空结果或成功，责任在工具适配和状态映射。

下次固定记下计划、每次工具参数和结果引用。没有这些，只能重放输入碰运气，不能稳定区分 Planner 和 Worker。

### 7. Harness 工程化里 Tool Mock 和 Trajectory Replay 你怎么搭，失败样本怎么复现

**参考答案**

结论：Mock 装在工具网关里，返回和生产相同的结构。轨迹回放分两种：冻住模型和工具，用来测 Harness；冻住工具、放开模型，用来测新的提示词或模型。失败样本从 trace 一键变成用例。

Mock 的键是工具名加规范化参数。模式有回放录制好的结果、注入超时、空列表和 5xx，以及转到沙箱。录制时脱敏。网关是唯一注入点，模型和应用代码不用为测试写分支。

一条轨迹保存每步的输入、模型原始输出、工具调用、工具结果和提交后的状态。回归 Harness 时固定模型和工具输出，断言重试、拒绝和熔断。比较新模型时固定工具结果、温度设为 0 并钉住模型版本；输出仍可能不完全确定，所以断言工具名、关键参数和状态，不断言整段话。

线上失败保存会话快照、模型版本、提示词版本、知识库版本和工具结果。回放这条 trace 复现。证件号等字段脱敏。用例进评测集时标上事故来源，避免下次回归漏掉。

### 8. RAG 检索层和生成层分别怎么 AB，实验流量怎么隔离

**参考答案**

结论：一次实验只动一层。测检索时固定模型和提示词；测生成时固定送进模型的条款。分流按用户或会话粘滞，缓存键带上实验臂和知识库版本。

检索实验可以先走影子：两套检索都算，用户仍看对照臂，离线比 Recall 和引用。需要用户反馈时再做小流量在线实验。生成实验若同时换了检索，分数变化无法归因，所以使用已记录的条款 id，让两边看见同一份证据。

粘滞是为了同一次行程不要混用两套政策或两种话术。只读问答可以进在线实验；订票、退款默认不进，或者只影子。事先定护栏：超时、空召回、投诉和写操作错误，护栏被打穿就停。实验臂写进 trace。

索引热更若和实验叠在一起，要把知识库版本钉在请求上，否则检索实验的差异其实来自规则更新。

### 9. 场景题：要让一个新业务线（比如门票 + 租车）接入你现有 Agent 平台，接入口子有哪些，最小改动是什么

**参考答案**

结论：新业务线复用 Harness、网关、会话、trace 和写操作协议，只增加意图、工具适配、槽位、工作流片段、知识库分区和评测用例。

接入口有六处。意图注册门票、租车，以及和机票组合的说法。工具清单写 schema、角色、超时、读写和幂等，适配器调用原有门票和租车接口。状态对象增加景点、取还车地点、驾驶人约束等槽位。工作流增加子图，例如「航班落地后再取车」要写成边，不能靠模型临时记得。知识库按业务过滤，取消规则走原来的版本化索引。上线前补黄金用例，覆盖查到、查空、超时和改口。

最小改动是先接只读查询：注册工具和意图，加上评测，走现有循环。支付和订单号沿用平台已有的写路径，不给租车单独做一套退款。先不要为这个业务线新拆一组 Agent 角色。

容易漏的是跨业务依赖。只把两个工具丢进注册表，模型会在航班还没确定时许诺取车时间。依赖要写在工作流边上。

### 10. 场景题：模型升级后整体答对率涨了，但工具调用乱序了，怎么在不回滚模型的前提下修复

**参考答案**

结论：保留新模型，把工具顺序从「模型输出的调用顺序」改成「状态机允许的下一跳」。网关拒绝还不满足前置条件的调用。

先在评测里单列顺序：查询或验价成功之后才能占座，占座成功之后才能支付，关键 id 必须对得上。新模型答对率上升、顺序违规上升，就确认问题在轨迹，不在最终文案。

修复放在网关，而不是把模型退回去：

```java
boolean allowed(ToolCall call, State state) {
    if (call.name().equals("hold_seat")) {
        return state.hasSuccessful("quote")
            && state.quoteId().equals(call.arg("quoteId"));
    }
    if (call.name().equals("pay")) {
        return state.hasSuccessful("hold_seat")
            && state.holdId().equals(call.arg("holdId"));
    }
    return state.toolVisible(call.name());
}
```

非法调用不执行，把「还缺哪一步」作为工具结果交回模型一次。同一违规重复出现，只读的下一步可以由代码按依赖补上；占座、支付仍停住并向用户确认，不再跟着模型的顺序执行写操作。前置条件不满足时，可以把还不能用的工具从当轮 schema 里拿掉，减少新模型乱点的机会。提示词里的顺序说明只作辅助。

乱序有时是并行查询没有声明依赖，晚返回的结果先被汇总。只读查询可以并行，有依赖的写操作仍走上面的准入。灰度时同时看答对率和顺序违规率，后者回到原水位再放量。

### 11. 你是怎么学 Harness / Context Engineering 这种没多少中文资料的东西的

**答题思路**

讲你的学习闭环，少报文章名单。

1. 一手来源是你正在用的框架文档和源码：循环在哪停、状态写到哪、工具错误怎么喂回去。中文转述只用来找术语。
2. 把概念收成一句能实现的话。Context Engineering 就是决定这次调用放进窗口的内容、顺序和丢掉什么；Harness 就是循环、状态、追踪和预算这些模型外面的机制。
3. 在一条真实只读工具上做最小闭环，故意制造超时、参数错误和进程中断，看哪一种你还没处理。
4. 面试时讲一个你因此改过的机制，例如观察太长所以在写入时裁剪，或重启后先查幂等键。讲改动和验证，不讲收藏了多少资料。

### 12. 最近半年哪篇 Agent 工程文章你觉得在吹牛，哪篇真能落地

**答题思路**

用你真读过的文章。临时编标题一问细节就会穿。判断标准可以这样说：

能落地的文章会写清状态放哪、工具失败怎么办、用哪个指标判断变好，并且你能在自己的链路上做出同样的机制。例如把已知交易收成工作流，模型只做意图、缺参和政策解释，副作用以工具返回为准。这种结论可以直接改架构。

当吹牛处理的是这类断言：多个 Agent 互相评审就能稳定提高正确率，或者换一个框架就等于有了生产级 Agent。评审可以抓到一部分草稿错误，但工具顺序、幂等和权限仍要由代码保证；角色一多，成本、延迟和归因都会变差。对话录展示的是单次成功，没有失败样本和回归。

回答时点名一篇你读过的：它缺了状态、评测或副作用里的哪一块，或者你照着做进系统的是哪一块。说不出文章名字，就说这个判断标准，不要凑一篇。

### 13. 如果给你两个月搭一套携程级别的 Agent 底座，你先写哪一层，最后补哪一层

**参考答案**

结论：先写工具网关、会话检查点和 trace，让查航班这条只读链路跑通，并同时建最小评测。最后补多 Agent 角色拆分和自动实验平台。两个月做的是一条能运营的垂直链路，不是所有旅行业务。

第一层是 Harness 内核。工具有 schema、超时、权限和幂等键；每步有检查点；一次请求能把模型、工具和数据库写串成一条 trace；发调用前有步数和预算限制。查航班从原话到引用工具结果的回答在这条内核上跑通。没有它，后面的提示词无法安全迭代。

评测和回放夹具跟第一条链路一起建，至少覆盖查到、查空、超时和参数错误。政策检索做成带版本的知识库，接在只读回答上。验价、占座、支付用 DAG 接上，写操作带确认和对账。这些都还是同一套网关和状态。

最后补多 Agent。在网关和评测还没有的时候拆 Router、Planner、Worker，只是把一次错误调用变成多次，并且更难定位。跨业务线的平台化也放在一条业务的顺序和回放已经稳定之后。
