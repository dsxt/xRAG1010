### 2. 讲一个你真正落过的 Agent 项目，别说 Demo，说清楚业务链路和你在哪一层

**答题思路**

面试官要判断的是"是否真上过线"，所以按下面顺序讲：

1. **业务背景**：解决什么问题，用户是谁，为什么需要 Agent 而不是固定流程。
2. **整体链路**：用户输入 → 意图识别/路由 → 规划与编排 → 工具调用/检索 → 结果校验 → 流式输出。画出链路并标出每一层的输入输出。
3. **你负责的层**：明确是编排层、RAG、工具网关、评测还是稳定性，不要说"都是我做的"。
4. **踩过的坑与取舍**：至少准备 3 个，例如 chunk 策略调整、工具超时与重复调用、bad case 回流、降级方案，每个按"现象 → 定位 → 方案 → 效果"讲。
5. **上线后的数据**：成功率、耗时、成本、人工接管率等，只说真实有的。

不要编造项目细节，没做过的部分明确说"了解原理，没有落地"。

### 3. Agent 和普通 LLM 对话到底差在哪，什么时候其实不该上 Agent

**参考答案**

结论：普通 LLM 对话是"一问一答、只靠参数知识生成文本"，Agent 是"以 LLM 为决策核心，能规划、调用工具、观察结果并循环迭代直到完成目标"的系统。

差异：

- **能力边界**：Agent 能通过工具访问实时数据、执行动作（查库存、下单），LLM 对话只能输出文本。
- **控制流**：LLM 对话是单次推理，Agent 有多步循环（规划 → 行动 → 观察 → 修正）。
- **状态与记忆**：Agent 需要管理任务状态、中间结果和长短期记忆。
- **风险面**：Agent 会产生副作用，需要权限、幂等、审计。

不该上 Agent 的场景：

- 流程固定、步骤可枚举，用 Workflow 或规则更稳定、更便宜；
- 对延迟、成本、确定性要求高，Agent 多轮调用带来延迟放大和结果不稳定；
- 强合规、容错极低的操作（资金），应由确定性代码控制，模型只负责理解意图；
- 单次问答或纯知识问答，RAG 或直接 LLM 即可。

原则：能用确定性代码解决的就不用 Agent，Agent 只负责真正需要"动态决策"的那一段。

### 4. ReAct 循环完整执行流程，Thought、Action、Observation 各自怎么流转

**参考答案**

结论：ReAct 是"推理 + 行动"交替的循环：模型先思考（Thought），决定调用哪个工具（Action），拿到工具返回（Observation），把三者追加进上下文后再次推理，直到输出最终答案。

流程：

1. 输入用户问题、工具描述和格式约束，进入上下文。
2. **Thought**：模型分析当前信息是否足够，下一步该做什么。
3. **Action**：模型输出要调用的工具名和参数。早期靠文本格式解析，现在多用 Function Calling 的结构化 tool_calls。
4. 框架**不让模型自己执行**，由后端校验参数后执行工具。
5. **Observation**：工具结果作为一条 tool 消息追加回上下文。
6. 回到第 2 步，模型基于新观察继续推理；信息足够时输出 Final Answer，循环结束。

工程上要注意的点：必须有**最大步数、总耗时、token 预算**作为终止条件；工具报错也要作为 Observation 回给模型让它修正；对重复调用做检测；Thought 过长会吃上下文，需要裁剪历史 Observation。

### 5. LangChain 和 LangGraph 本质区别，为什么生产级 Agent 更偏向图编排

**参考答案**

结论：LangChain 偏"组件和链式调用的工具箱"，LangGraph 是"以状态图为核心的有状态编排运行时"。

区别：

- **LangChain**：提供模型、Prompt、检索器、工具等抽象，链（LCEL）本质是有向无环的线性或简单分支流水线，循环和复杂分支表达不便。
- **LangGraph**：把流程建模为图，节点是处理步骤，边是流转逻辑（可条件分支、可成环），共享一个显式的 State；内置 Checkpointer（持久化）、中断恢复、人工介入（interrupt）、流式输出。

生产级偏向图编排的原因：

1. **可控**：路径显式，哪些步骤可以走、什么条件跳转都由开发者定义，而不是完全交给模型自由发挥。
2. **可恢复**：每一步状态可持久化，崩溃后可从断点继续。
3. **可观测、可测试**：节点是独立单元，可以单测，可追踪每步状态。
4. **支持人工确认、并行、循环、子图**。

补充：LangChain 的 Agent 能力现在也建立在 LangGraph 之上，二者不是对立关系。

### 6. Function Calling 底层原理，模型返回的工具参数不可信时后端怎么兜底

**参考答案**

结论：Function Calling 是模型经过专门训练，在给定工具的 JSON Schema 后，能输出"要调用哪个函数、参数是什么"的结构化结果；**模型本身不执行函数**，由后端执行并把结果回传。

原理：请求里带上 tools 定义（名称、描述、参数 Schema）→ 模型判断是否需要调用，返回 tool_calls（函数名 + JSON 参数）→ 后端执行 → 以 tool 角色消息把结果追加到对话 → 再次请求模型生成最终回答。

参数不可信，因为模型可能产生：缺字段、类型错、枚举越界、幻觉出的 ID、被 Prompt Injection 诱导的参数。兜底：

1. **Schema 校验**：按 JSON Schema 校验必填、类型、枚举、范围、长度，失败不执行。
2. **工具白名单**：只允许调用已注册且当前用户有权限的工具。
3. **身份不信任模型**：用户 ID、租户 ID 等由后端从登录态注入，不从模型参数取。
4. **业务校验**：对象归属校验（订单是否属于该用户）、金额上限等。
5. **校验失败回灌**：把具体错误信息作为 Observation 让模型重试，限制重试次数。
6. **严格模式 / 约束解码**：能用的话启用 strict 结构化输出以降低格式错误。
7. **高风险操作**走人工确认，写操作使用幂等键。

### 7. RAG 完整链路讲一遍，Query Rewrite、混合检索、Rerank 分别在解决什么问题

**参考答案**

结论：RAG 是"先检索相关资料，再把资料作为上下文交给模型生成答案"，以此降低幻觉并引入私有、实时知识。

完整链路：

- **离线**：文档解析 → 清洗 → 切分（chunk）→ Embedding → 写入向量库/倒排索引，并保留元数据（来源、时间、权限）。
- **在线**：用户问题 → Query 改写 → 召回 → 重排 → 拼装 Prompt（带引用）→ 生成 → 校验/引用溯源。

三个环节分别解决：

- **Query Rewrite**：解决用户问题口语化、省略、指代不清（多轮"它多少钱"）、过于笼统的问题，做指代消解、补全、多查询扩展或拆分子问题，提升召回。
- **混合检索**：向量检索擅长语义相似但对专有名词、编号、型号不敏感；BM25 擅长精确关键词匹配。两路结果用 RRF 或加权融合，互补以提高召回率。
- **Rerank**：召回阶段追求"别漏"，返回候选较多且排序粗糙。用 cross-encoder 对 query 和候选做精细打分，取 Top-N 送入模型，提高精度并减少噪声和 token。

容易说漏：元数据过滤和权限过滤要在检索层做；还要有评测（Recall@K、MRR、答案忠实度）才能证明每个环节有效。

### 8. Chunk 切分策略怎么定，父子文档、overlap、召回率和延迟怎么权衡

**参考答案**

结论：没有通用最优值，应按文档结构和问题类型选择，再用离线评测集（Recall@K、答案正确率）调参。

策略：

- **优先按语义结构切**：标题/章节、段落、表格、代码块分别处理，其次再按 token 长度兜底。避免把一条完整规则、一张表切断。
- **chunk 大小**：太小语义不完整、召回碎片化；太大向量被稀释、噪声多、占上下文。常见起点是几百 token，再按评测调整。
- **overlap**：用来缓解边界处信息被切断，常见取 10% 到 20% 左右。过大会造成冗余、索引膨胀和重复召回。
- **父子文档（Parent-Child）**：用小的子块做检索（精准匹配），命中后返回所属的大父块或相邻上下文给模型（信息完整）。代价是索引结构更复杂、送入模型的 token 更多。

权衡：

- 召回率与精度：小块精准但可能缺上下文，父子文档可以兼顾；
- 延迟：块越多、Top-K 越大、Rerank 候选越多，延迟越高，可通过限制候选数、缓存、ANN 参数调节；
- 元数据（标题路径、文档名）拼进 chunk 或作为过滤字段，常常比调大小更有效。

### 9. Redis 在 Agent 系统里能扛什么：会话、限流、工具结果缓存、分布式锁

**参考答案**

结论：Redis 适合承载 Agent 系统里"高频、短生命周期、需要共享"的数据。

- **会话**：用 Hash/List/String 存会话上下文、最近若干轮消息、任务临时状态，设置 TTL；完整历史仍落 MySQL。多实例部署时会话共享依赖它。
- **限流**：按用户/租户/工具/模型维度。固定窗口用 INCR + EXPIRE，更平滑的用 ZSET 滑动窗口或令牌桶，建议用 Lua 保证原子性。可以对 token 消耗限流，而不仅仅是请求数。
- **工具结果缓存**：只缓存只读、幂等且时效可接受的结果（如城市信息），key 由工具名 + 规范化参数哈希 + 租户组成，设置合理 TTL；价格、库存等强实时数据谨慎缓存或用极短 TTL。
- **分布式锁**：`SET key value NX PX` 加唯一值，释放用 Lua 校验 value 再删除；长任务需要看门狗续期（如 Redisson）。典型用途是同一会话串行化请求、防重复下单。

注意：Redis 锁在主从切换下并非绝对安全，涉及资金等强一致场景要配合数据库唯一约束或 fencing token 做兜底；缓存要处理穿透、击穿、雪崩。

### 10. Kafka 在 Agent 异步任务里怎么解耦，重复消费和幂等怎么保证

**参考答案**

结论：Kafka 用来把"提交任务"和"执行任务"解耦、削峰填谷；Kafka 通常是至少一次投递，**幂等必须在消费端实现**。

解耦做法：接入层只创建任务记录（状态 PENDING）并发送消息，立即返回 taskId；Worker 消费后执行 Agent 流程并更新状态；结果通过 SSE/WebSocket 推送或前端轮询。以 sessionId 作 key，保证同一会话的消息落在同一分区、顺序消费。

重复消费原因：消费者处理完但提交 offset 前宕机、再均衡（rebalance）、生产者重试。

幂等方案：

1. 每个任务有业务唯一键（taskId + stepId），消费前后用 MySQL 唯一索引或 Redis SETNX 去重。
2. 任务用**状态机**（PENDING → RUNNING → SUCCESS/FAILED），用条件更新（`WHERE status='PENDING'`）抢占，已完成的直接跳过。
3. 对外部副作用（下单、扣款）带幂等键，由下游保证。
4. **先处理后提交 offset**，宁可重复不丢失。

其他要点：长任务要注意 `max.poll.interval.ms`，避免被判定失活；失败走重试 topic，超过次数进死信队列并告警；Kafka 事务的精确一次只覆盖 Kafka 内部读写，覆盖不到外部系统副作用。

### 11. MySQL 怎么存对话、任务状态、工具调用 trace，索引怎么建

**参考答案**

结论：按"会话、消息、任务、调用链"拆表，围绕主要查询路径建联合索引，大字段与冷数据分离。

表设计示例：

- `conversation`：id、user_id、tenant_id、状态、创建/更新时间。索引：`(user_id, updated_at)`。
- `message`：id、conversation_id、role、content、token 数、创建时间。索引：`(conversation_id, id)`，按主键递增顺序取最近 N 条。
- `agent_task`：task_id（唯一）、conversation_id、状态、当前 step、重试次数、下次重试时间、版本号。索引：`uk(task_id)`、`(status, next_retry_time)` 用于扫描补偿任务。
- `tool_call_trace`：id、task_id、trace_id、step_no、tool_name、入参、出参摘要、状态、耗时、错误码、时间。索引：`(task_id, step_no)`、`(trace_id)`，必要时 `(tool_name, created_at)` 做统计。

要点：

- 入参出参可能很大，存摘要，全文放对象存储或 ES，并做脱敏；
- 联合索引遵循最左前缀，按查询条件和排序组合设计；
- trace 数据量增长快，按时间分区或分表、定期归档，复杂分析和检索放 ES/ClickHouse；
- 状态更新使用乐观锁或条件更新，避免并发覆盖；
- 消息表以追加写为主，避免频繁更新大字段。

### 12. Agent 跑着跑着开始重复调同一个工具停不下来，怎么检测、拦截、降级

**参考答案**

结论：这是典型的"循环无进展"，要用多重硬性保护检测，拦截后给模型明确反馈，仍不行则降级收敛。

检测：

- 步数上限、总耗时上限、token 预算（硬阈值）；
- 对"工具名 + 规范化参数"取哈希，在窗口内计数，同一调用出现 N 次视为重复；
- 无进展检测：连续几步状态、关键槽位、检索结果集没有变化；
- 出现 A→B→A→B 的循环模式。

拦截：

- 命中重复时不再真实执行，直接把**之前的结果**返回，并附一句"该调用已执行过，请基于已有结果继续或换策略"；
- 对失败的工具设置单任务调用次数上限，超出后将该工具临时屏蔽（从可用工具列表移除）。

降级：

- 去掉工具、强制模型基于现有信息给出最终回答（并说明不确定处）；
- 转到固定 Workflow 或兜底话术；
- 转人工；
- 记录 trace，进入 bad case 回流。

根因治理：检查工具描述是否模糊、返回信息是否让模型无法判断完成、错误信息是否可操作。

### 13. 上下文窗口有限，多轮对话怎么压缩，摘要、滑窗、向量召回怎么选

**参考答案**

结论：三种方法互补，通常组合使用：**最近几轮原文（滑窗）+ 历史摘要 + 按需召回的相关历史 + 结构化关键状态**。

- **滑窗**：保留最近 N 轮原文。实现简单、无信息损失，但会丢失早期信息，适合短对话。
- **摘要**：把较早的对话压缩为摘要，滚动更新。节省 token，但摘要可能丢细节或失真，更新摘要还有额外的模型调用成本。
- **向量召回**：把历史片段向量化存储，按当前问题检索相关片段。适合长周期、话题跳跃的对话，但可能召回不准，需要结合时间和元数据。
- **结构化状态**：把目的地、日期、预算等关键槽位单独维护，每轮固定注入，比摘要更可靠。

选择依据：对话长度、是否需要精确引用早期细节、延迟成本预算。

补充点：系统提示和关键约束必须固定保留；工具返回的大结果应先裁剪或摘要再进入上下文；压缩要有评测，对比压缩前后的任务成功率。

### 14. Prompt Injection 怎么防，Agent 调高危工具时怎么鉴权和人工确认

**参考答案**

结论：Prompt Injection 无法靠一句"忽略恶意指令"根治，要做**纵深防御**，核心是即使模型被诱导，也做不了越权的事。

防护：

1. **隔离不可信内容**：把网页、文档、工具返回等外部内容标记为"数据而非指令"，用清晰分隔，并在系统提示里说明。
2. **最小权限**：处理不可信内容的环节只给只读工具；按任务动态收敛可用工具。
3. **输入/输出检测**：规则或分类模型检测注入特征、敏感信息泄露。
4. **参数与行为校验**：工具参数走 Schema 和业务校验，身份信息由后端注入。
5. **不在 Prompt 里放密钥**，输出做脱敏。

高危工具鉴权与确认：

- **鉴权在工具执行层完成**，使用登录态身份做 RBAC/ABAC 和资源归属校验，而不是让模型决定"我有权限"；
- 对高危操作先生成**待确认操作**，向用户展示完整参数（对象、金额），用户明确确认后才执行；
- 确认令牌与具体参数绑定、一次性、有过期时间，防止被篡改或重放；
- 额度、频率限制，必要时二次验证或人工审核；
- 全程审计日志。

### 15. 手撕算法：实现一个简化版 Agent 工具调度器，支持注册工具、超时中断、失败重试、调用记录

**参考答案**

思路：用注册表保存工具及其策略（超时、重试次数、退避）；执行时提交到线程池，用 `Future.get(timeout)` 实现超时，超时后 `cancel(true)` 中断；失败按指数退避重试；每次调用写入记录。

复杂度：注册和查找 O(1)，一次调用的耗时由工具本身、重试次数决定，记录为追加写，空间 O(调用数)。

```java
import java.util.*;
import java.util.concurrent.*;

public class ToolScheduler {
    public interface Tool {
        String call(Map<String, Object> args) throws Exception;
    }

    public record ToolSpec(String name, Tool tool, long timeoutMs, int maxRetries, long backoffMs) {}

    public record CallRecord(String tool, Map<String, Object> args, boolean success,
                             int attempts, long costMs, String result, String error, long timestamp) {}

    private final Map<String, ToolSpec> registry = new ConcurrentHashMap<>();
    private final Queue<CallRecord> records = new ConcurrentLinkedQueue<>();
    private final ExecutorService pool = new ThreadPoolExecutor(
            8, 16, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(100), new ThreadPoolExecutor.AbortPolicy());

    public void register(ToolSpec spec) {
        if (registry.putIfAbsent(spec.name(), spec) != null) {
            throw new IllegalStateException("tool already registered: " + spec.name());
        }
    }

    public String invoke(String name, Map<String, Object> args) throws Exception {
        ToolSpec spec = registry.get(name);
        if (spec == null) throw new IllegalArgumentException("unknown tool: " + name);

        long start = System.currentTimeMillis();
        Throwable last = null;
        int attempts = 0;
        for (int i = 0; i <= spec.maxRetries(); i++) {
            attempts++;
            Future<String> f = pool.submit(() -> spec.tool().call(args));
            try {
                String result = f.get(spec.timeoutMs(), TimeUnit.MILLISECONDS);
                records.add(new CallRecord(name, args, true, attempts,
                        System.currentTimeMillis() - start, result, null, start));
                return result;
            } catch (TimeoutException e) {
                f.cancel(true);           // 中断工作线程，工具需响应中断
                last = e;
            } catch (ExecutionException e) {
                last = e.getCause();
            }
            if (i < spec.maxRetries()) {
                Thread.sleep(spec.backoffMs() * (1L << i));  // 指数退避
            }
        }
        records.add(new CallRecord(name, args, false, attempts,
                System.currentTimeMillis() - start, null, String.valueOf(last), start));
        throw new Exception("tool failed after " + attempts + " attempts: " + name, last);
    }

    public List<CallRecord> getRecords() {
        return new ArrayList<>(records);
    }
}
```

容易说漏的点：

- `cancel(true)` 只是发出中断信号，工具内部阻塞调用必须响应中断或自己设置网络超时，否则线程仍被占用；
- **只对幂等工具重试**，写操作需要幂等键，否则重试会重复执行；
- 重试应加随机抖动，并限制总重试预算；
- 可区分可重试错误（超时、5xx）和不可重试错误（参数错误）。

### 2. 深抠你简历里那个 Agent 项目：从用户一句话到最终执行接口，全链路怎么走

5. **工具执行**：超时、重试、幂等键、限流熔断、结果裁剪。

### 3. LangGraph 里 State、Node、Edge、Checkpointer 分别解决什么，并发会话怎么持久化恢复

**参考答案**

结论：State 管"数据"，Node 管"处理"，Edge 管"流转"，Checkpointer 管"持久化与恢复"。

- **State**：图的共享状态（如消息列表、槽位、中间结果），通常用带 reducer 的结构定义，reducer 决定多个节点写同一字段时如何合并（如消息追加）。
- **Node**：一个处理函数，读取 State，返回对 State 的更新（调用模型、执行工具、校验）。
- **Edge**：节点间的连接，分普通边和**条件边**（根据 State 动态决定下一节点，可形成循环）。
- **Checkpointer**：在每个执行步骤后保存 State 快照，使得可以中断恢复、人工介入、回溯。

并发会话：

- 以 `thread_id` 标识会话，不同 thread 的状态相互隔离，天然可并发；
- 生产环境使用持久化后端（如 Postgres、Redis），内存版只适合开发测试；
- **同一 thread 的并发请求要串行化**（会话级锁或队列），否则状态会互相覆盖；
- 恢复时用同一 thread_id 重新调用，从最近的检查点继续。

容易说漏：崩溃时正在执行的节点可能在恢复后**被重新执行**，因此节点内的有副作用操作必须幂等；还有检查点的存储体积和清理策略。

### 4. 多 Agent 怎么拆，Supervisor 和 Handoff 模式区别，子 Agent 之间怎么通信和仲裁

**参考答案**

结论：多 Agent 要按职责、权限和上下文隔离来拆，不是越多越好；Supervisor 是中心化调度，Handoff 是控制权的点对点移交。

怎么拆：按领域能力（机票、酒店、行程、客服）、按权限/风险（只读与写操作分开）、按上下文规模（避免单个 Agent 工具过多、提示过长）。如果单 Agent 加工具就能解决，不必拆。

两种模式：

- **Supervisor**：一个主管 Agent 负责理解任务、分发给子 Agent、汇总结果，子 Agent 完成后回到主管。优点是全局可控、易追踪、易插入审核；缺点是主管成为瓶颈和单点，多一次模型调用，延迟与成本更高。
- **Handoff**：当前 Agent 判断该由谁处理时，把对话和控制权移交给另一个 Agent，由后者直接与用户交互。链路短、更灵活，但流转更难控制，容易出现来回踢皮球或死循环，需要设定转交次数上限。

通信：共享 State 或黑板（blackboard）、结构化消息传递（固定 Schema）；只传必要的信息，避免全量上下文。

仲裁：由 Supervisor 或规则引擎裁决；按优先级、置信度；冲突时用独立的校验/裁判 Agent 或确定性规则；仍无法决定则请求用户澄清或转人工。同时要有最大步数和转交次数限制。

### 5. RAG 召回率低怎么定位，是切分问题、向量问题、检索问题还是 Rerank 问题

**参考答案**

结论：先建立带标注的评测集（问题 → 应命中的文档/片段），然后**分阶段度量**，逐环节定位，而不是凭感觉调参。

排查顺序：

1. **数据层**：标准答案所在的文档是否进入了索引？解析是否丢失表格、图片、格式？权限或元数据过滤是否误过滤？
2. **切分**：答案是否被切断、分散在多个 chunk？chunk 是否缺少标题等上下文？
3. **Query**：用户问题是否需要改写、指代消解？
4. **检索**：分别测向量检索、BM25 和混合检索的 Recall@K。仅向量低而 BM25 高，说明 Embedding 对专有名词不敏感；检查 Embedding 模型是否适合领域、ANN 参数（如 ef_search、nprobe）是否过小。
5. **Rerank**：对比 Rerank 前后黄金片段的排名。召回阶段包含但 Rerank 后丢失，是 Rerank 问题；召回就没有，则是前几步的问题。
6. **生成阶段**：召回其实正确但答案错，属于 Prompt 或模型问题，不能算召回率。

结论的判断依据是各阶段 Recall@K、MRR 的数据，改一个变量对比一次，并把修复的 case 加入回归集。

### 6. 评测体系怎么搭，good case 和 bad case 怎么回流，怎么量化 Agent 输出好坏

**参考答案**

结论：评测体系由"离线评测集 + 在线监控 + 回流闭环"组成，指标要同时覆盖结果、过程和成本。

量化指标：

- **结果**：任务成功率、答案正确性、引用忠实度（是否有依据）、业务约束满足率；
- **过程**：工具选择准确率、参数正确率、调用步数、重复调用率；
- **RAG**：Recall@K、MRR、上下文相关性；
- **体验与成本**：延迟、token 成本、人工接管率、用户点踩/重试率、转化。

评测方式：有标准答案的用规则/精确匹配；开放式输出用 LLM-as-Judge，需用人工标注样本校准评审模型，且设置明确的评分标准（rubric）；关键场景保留人工评审。

回流：

1. 线上全链路 trace 采集，并根据点踩、重试、接管、异常等信号筛选候选 case；
2. 标注归因（意图、检索、规划、工具、模型、数据）；
3. bad case 修复后加入回归集，good case 作为基线与 few-shot 候选；
4. 版本发布时跑回归，设置准入阈值，退化则阻断；
5. 定期更新评测集，避免过拟合。

### 7. 工具注册中心怎么设计：Schema、权限、超时、幂等、审计、版本管理

**参考答案**

结论：工具注册中心是 Agent 访问外部能力的统一入口，每个工具用一份"元数据 + 执行策略"描述，调用经过统一网关。

元数据设计：

- **Schema**：名称、描述（会直接影响模型选择，要写清用途和边界）、入参/出参 JSON Schema、示例；
- **权限**：风险等级（只读/写/资金）、所需 scope、可用租户和角色，调用时校验的是**用户身份**，而不是模型；
- **超时与重试**：每个工具独立的超时、重试策略、并发上限、熔断阈值；
- **幂等**：标明是否幂等，写操作要求传入幂等键，网关对幂等键去重；
- **审计**：每次调用记录谁、何时、什么参数、结果、耗时、traceId，脱敏后存储；
- **版本管理**：语义化版本，Schema 变更要兼容；新版本灰度发布，可回滚，旧版本设置下线期限；
- 另外：owner、限流配额、健康检查、动态上下线。

执行流程：模型选择工具 → 网关校验 Schema 和权限 → 限流熔断 → 执行 → 结果裁剪与脱敏 → 记录审计。

### 8. ES 和向量库怎么配合，倒排加稠密检索的融合排序怎么做

**参考答案**

结论：ES 的倒排索引（BM25）负责关键词精确匹配和过滤，向量库负责语义相似，两路并行召回后融合，再 Rerank。

配合方式：

- 文档用同一个 doc/chunk ID 在两边保持一致，元数据（权限、租户、时间）同步，并保证更新、删除一致；
- 也可以直接用 ES 自带的向量检索（dense_vector + kNN）在一个系统内同时做两路，降低运维成本；
- 元数据过滤要在检索时应用（前置过滤），避免召回后再过滤导致结果不足。

融合排序：

- **RRF（Reciprocal Rank Fusion）**：对每路结果按名次计分，`score = Σ 1/(k + rank)`（k 常取 60），累加后排序。只用排名，不受两路分数量纲不同的影响，实现简单、稳健。
- **加权分数融合**：先将两路分数归一化（min-max、z-score），再按权重线性加权，权重通过评测调参。缺点是对分数分布敏感。
- 融合后取 Top-N 候选做 cross-encoder Rerank，再送入模型。

调优：用评测集比较不同融合方式的 Recall@K、MRR；可以对包含编号、型号的 query 调高 BM25 权重。

### 9. Agent 调用链突然 RT 升高、线程池打满，怎么止损和排查

**参考答案**

结论：先止损，再定位，最后根治。

止损：

1. 限流，保护核心流量，拒绝低优先级请求；
2. 对慢下游**熔断/降级**：关闭相关工具、切换备用模型、返回兜底回答；
3. 若与最近发布相关，立即回滚或关闭灰度开关；
4. 必要时扩容，但前提是瓶颈不是下游本身，否则只会加重压力。

排查：

1. 看监控：哪类请求、哪个接口、哪个下游 RT 升高，开始时间与发布/流量变化是否吻合；
2. 看链路追踪：慢在哪个 span（模型调用、检索、某个工具）；
3. `jstack` 或线程 dump：线程是否大量阻塞在网络 IO、锁、连接池等待；
4. 检查连接池（HTTP、DB、Redis）是否耗尽、有无超时设置缺失；
5. 检查 LLM 供应商延迟、限速（429）、流式长输出；
6. 检查 GC、CPU、内存，是否有重试风暴、Agent 循环调用放大请求量；
7. 队列堆积情况。

根治：所有外部调用必须有超时；按下游做**线程池隔离（舱壁）**，避免一个慢下游拖垮全部；队列有界；重试加退避和预算；增加告警和压测；Agent 增加步数与耗时上限。

### 10. 模型失败、工具超时、服务重启，任务状态怎么恢复，断点续跑怎么做

**参考答案**

结论：任务必须建模为**持久化状态机**，每一步完成后落盘 checkpoint，恢复时从最后一个已确认的步骤继续，副作用步骤用幂等保证。

做法：

1. **状态持久化**：任务表记录状态、当前 step、已完成步骤的输出、重试次数；每个步骤执行前后更新（条件更新）。
2. **模型失败**：带退避重试，仍失败切换备用模型或降级；
3. **工具超时**：按策略重试；写操作结果不确定时，先用**业务幂等键查询下游真实状态**，再决定重试或补偿，不能盲目重发。
4. **服务重启**：Worker 持有任务租约（lease）并心跳续约；宕机后租约过期，由恢复扫描任务（`status=RUNNING` 且租约过期）重新拉起，从最近 checkpoint 继续。
5. **断点续跑**：已成功步骤的结果直接复用，不再重复调用；使用 LangGraph 一类框架时，即为 Checkpointer + 同一 thread_id 恢复。
6. **超过重试上限**：进入失败状态，通知用户或人工处理，必要时执行补偿（取消订单、释放库存）。

注意：被中断的步骤恢复后可能重新执行，所以每个有副作用的步骤都要幂等；还要设置任务整体超时，防止僵尸任务。

### 11. 敏感操作（查订单、动资金、发消息）怎么防越权，Guardrail 怎么做

**参考答案**

结论：防越权靠**确定性的权限控制**，不是靠提示词；Guardrail 是围绕输入、工具调用、输出的多层检查。

防越权：

1. **身份来自后端**：用户身份从登录态注入工具调用上下文，不信任模型给出的 userId。
2. **工具级权限**：RBAC/ABAC，按角色、租户、风险等级控制可用工具。
3. **资源级校验**：查询订单必须校验订单属于当前用户，防止横向越权（IDOR）。
4. **分级策略**：查询类直接执行；发消息类展示内容并确认；资金类需用户明确确认，设置金额上限、频率限制，必要时二次验证（短信、支付密码）；
5. 确认令牌绑定具体参数，一次性、有过期时间。
6. 全程审计。

Guardrail：

- **输入侧**：Prompt Injection 检测、敏感词、违规内容、PII 识别；
- **工具调用侧**：参数 Schema 校验、策略引擎（规则判定允许/拒绝/需确认）、异常行为检测（短时间大量调用）；
- **输出侧**：敏感信息脱敏、合规检查、事实依据校验（价格必须来自工具返回）；
- 实现方式为规则 + 分类模型组合，规则保证确定性，模型覆盖语义；拒绝时给出明确原因并记录。

### 12. 流式输出 SSE 怎么做，断线重连、消息去重、生成中断取消怎么处理

**参考答案**

结论：SSE 基于 HTTP 的 `text/event-stream` 单向推送；可靠性需要靠"事件序号 + 服务端缓冲 + 取消机制"补全。

基本做法：服务端设置 `Content-Type: text/event-stream`，按事件格式输出 `id`、`event`、`data`；关闭代理缓冲（如 Nginx `proxy_buffering off`）；定期发送心跳注释行防止连接被中间设备断开。

- **断线重连**：给每个事件分配单调递增的序号作为 `id`；浏览器 EventSource 重连时会带 `Last-Event-ID`，服务端据此从缓冲中补发。生成内容需要按消息 ID 暂存（如 Redis Stream/List，设置 TTL），生成过程与连接解耦。注意原生 EventSource 只支持 GET，需要 POST 时用 fetch 流式读取实现。
- **消息去重**：客户端按 `(messageId, seq)` 去重，序号小于等于已处理的丢弃，补发可能带来重复。
- **生成中断取消**：客户端主动关闭连接或调用取消接口；服务端检测连接关闭或收到取消标记，**取消对上游模型的请求**（关闭流，避免继续消耗 token），终止未执行的工具步骤，保存已生成的部分内容并标记状态为已取消。
- 多实例部署时，取消标记和缓冲要放在共享存储，重连请求才能被任一实例处理。

### 13. 成本怎么控，大模型小模型怎么分级路由，语义缓存怎么设计

**参考答案**

结论：成本控制的思路是"少调用、小模型优先、少 token、能复用就复用"，同时用评测保证质量不降。

成本控制手段：

- **分级路由**：简单任务（意图分类、改写、抽取、格式化）用小模型；复杂推理、规划用大模型。路由依据可以是规则、轻量分类器或小模型先答并依据置信度/校验结果升级到大模型；
- **减少 token**：裁剪上下文、压缩历史、限制检索片段数量、精简工具返回；
- **Prompt 前缀缓存**：把固定的系统提示放在前面，利用模型服务商的前缀缓存；
- **预算与限额**：单任务 token 预算、步数上限、租户配额，并做成本监控与告警；
- 并行、批量、异步处理非实时任务。

语义缓存设计：

1. 对问题做 Embedding，在向量库中找相似历史问题，相似度超过阈值才命中；
2. **缓存键必须包含上下文维度**：租户、权限、语言、相关版本，避免串数据；
3. 设置 TTL，知识更新时失效相关缓存；
4. **不缓存**个性化、强实时（价格、库存）、有副作用的请求；
5. 阈值要用评测集调，宁可保守；命中后可再经轻量校验；
6. 监控命中率、误命中率。

### 14. Spring 里工具执行器怎么注册和生命周期管理，AOP 怎么埋点统计耗时和成功率

**参考答案**

结论：把每个工具实现为 Spring Bean，由注册中心在容器启动时自动收集；用 AOP 切面统一做耗时和成功率埋点。

注册：

- 定义 `Tool` 接口，每个实现标注 `@Component`；注册中心通过构造器注入 `List<Tool>` 或 `Map<String, Tool>` 自动收集，也可以用自定义注解配合 `BeanPostProcessor` 在 Bean 初始化后注册元数据（名称、Schema、权限）。Spring AI 也提供 `@Tool` 注解的方式。
- 启动时校验名称重复、Schema 是否合法。

生命周期：

- 初始化用 `@PostConstruct` 或 `InitializingBean`，预热连接、加载配置；
- 销毁用 `@PreDestroy`，关闭线程池、连接；
- 需要有序启动或优雅停机时用 `SmartLifecycle`：停机时先停止接收新任务，等待执行中的任务完成；
- 工具的动态上下线可由注册中心维护启用状态，配合配置中心。

AOP 埋点：

- 写 `@Aspect` 切面，用 `@Around` 环绕执行工具方法：记录开始时间，`try` 正常返回记成功，捕获异常记失败并继续抛出，`finally` 中记录耗时；
- 指标用 Micrometer 的 Timer 和 Counter，tag 包括工具名、结果状态、错误类型，对接 Prometheus；同时记录 traceId 和日志；
- 切点可以拦截 `Tool` 接口实现或带自定义注解的方法。

注意：Spring AOP 基于代理，**同类内部方法自调用不会触发切面**；注意 tag 基数不要过高（不要把用户 ID 放进 tag）。

### 15. Java 线程池在并发调工具场景怎么配，异步编排和拒绝策略怎么定

**参考答案**

结论：工具调用主要是 IO 密集，线程池要有界、按下游隔离，参数通过压测和监控确定，而不是拍脑袋。

配置：

- **核心线程数**：IO 密集型可参考 `N × (1 + 等待时间/计算时间)` 估算，之后用压测调整，不是越大越好，线程多会造成上下文切换并压垮下游；
- **队列**：使用**有界队列**，避免无界队列堆积导致内存溢出和延迟不可控；
- **最大线程数**：队列满后才会扩到最大线程数（执行顺序：核心线程 → 队列 → 非核心线程 → 拒绝）；
- **线程命名**，并暴露活跃线程数、队列长度、拒绝次数监控；
- **按下游隔离（舱壁）**：不同工具/下游使用不同线程池，防止一个慢下游占满所有线程。
- Java 21 可使用虚拟线程处理阻塞 IO，但仍需用信号量等方式限制对下游的并发数。

异步编排：用 `CompletableFuture` 并行调用互不依赖的工具，`allOf` 汇总；每个任务设置超时（`orTimeout` 或 `completeOnTimeout`，Java 9+）；对失败做 `exceptionally`/`handle` 降级，返回部分结果而不是整体失败；依赖链用 `thenCompose`。注意要指定自定义线程池，不要使用默认的 `ForkJoinPool.commonPool()`。

拒绝策略：

- `AbortPolicy`：抛异常，由上层捕获后降级或返回"系统繁忙"；
- `CallerRunsPolicy`：由调用线程自己执行，起到反压作用，但可能阻塞请求线程；
- 通常更推荐"拒绝 + 降级 + 告警"，核心任务可以先落库再异步重试，而不是直接丢弃。

### 16. 手撕算法：手写带过期时间的 LRU Cache，要求 get、put 均摊 O(1)

**参考答案**

思路：`HashMap` 做 O(1) 查找，双向链表维护使用顺序（头部最新、尾部最旧）。每个节点保存过期时间。采用**惰性过期**：`get` 时发现已过期就删除并返回空；容量满时淘汰链表尾部。

复杂度：`get`、`put` 均为 O(1)，空间 O(capacity)。

```java
import java.util.HashMap;
import java.util.Map;

public class TtlLRUCache<K, V> {
    private static class Node<K, V> {
        K key;
        V value;
        long expireAt;
        Node<K, V> prev, next;
    }

    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<>();
    private final Node<K, V> head = new Node<>();  // 哨兵：最近使用
    private final Node<K, V> tail = new Node<>();  // 哨兵：最久未使用

    public TtlLRUCache(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public synchronized V get(K key) {
        Node<K, V> node = map.get(key);
        if (node == null) return null;
        if (node.expireAt <= now()) {      // 惰性过期
            removeNode(node);
            map.remove(key);
            return null;
        }
        moveToHead(node);
        return node.value;
    }

    public synchronized void put(K key, V value, long ttlMs) {
        long expireAt = now() + ttlMs;
        Node<K, V> node = map.get(key);
        if (node != null) {
            node.value = value;
            node.expireAt = expireAt;
            moveToHead(node);
            return;
        }
        if (map.size() >= capacity) {
            Node<K, V> last = tail.prev;   // 淘汰最久未使用
            removeNode(last);
            map.remove(last.key);
        }
        node = new Node<>();
        node.key = key;
        node.value = value;
        node.expireAt = expireAt;
        map.put(key, node);
        addToHead(node);
    }

    private long now() {
        return System.currentTimeMillis();
    }

    private void addToHead(Node<K, V> node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void removeNode(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void moveToHead(Node<K, V> node) {
        removeNode(node);
        addToHead(node);
    }
}
```

容易说漏的点：

- 过期条目可能处于链表任意位置，惰性删除会让已过期的数据暂时占用容量。需要主动清理时，可增加最小堆（按过期时间）或后台定时扫描，但堆的操作是 O(log n)，不再严格 O(1)；
- 对已存在 key 的 `put` 要更新值和过期时间并移到头部；
- 过期时间使用 `System.nanoTime()` 更不受系统时钟调整影响，面试时可以说明；
- 并发场景用 `synchronized` 或分段锁，`get` 也会修改链表，所以读也需要加锁。

### 2. 假设你从零设计携程旅行 Agent，整体架构怎么分层，哪些模块必须自研哪些可以接开源

**参考答案**

结论：按"接入 → 编排 → 能力 → 知识与记忆 → 模型网关 → 基础设施"分层，与业务强相关、决定核心竞争力和风险的自研，通用基础设施接开源。

分层：

1. **接入层**：网关、鉴权、限流、会话管理、SSE 流式输出。
2. **编排层（Agent Runtime）**：意图识别与路由、规划、状态图编排、多 Agent 协作、人工确认、断点恢复。
3. **能力层（工具网关）**：机票、酒店、门票、天气、地图、订单等业务服务封装为工具，统一 Schema、权限、超时、幂等、审计。
4. **知识与记忆层**：RAG（攻略、政策、商品知识）、用户记忆与画像。
5. **模型网关**：多模型接入、路由、灰度、降级、成本统计。
6. **治理层**：评测、可观测、安全 Guardrail、配置与灰度、成本管理。

**必须自研**：与业务绑定的编排逻辑和状态机、工具网关与权限风控（涉及资金和用户数据）、行程规划与约束校验、评测集与回流体系、模型网关的路由与兜底策略、业务知识的数据治理。

**可接开源/商用**：向量库与 ES、LangGraph 等编排框架（可基于其扩展）、OpenTelemetry/Langfuse 类可观测组件、推理服务框架、基础模型、消息队列和缓存。

原则：核心链路自己能掌控、可替换；避免被某一框架或供应商锁定。

### 3. 多城市多约束动态行程规划，怎么把 LLM 和运筹算法融合，不只是让模型瞎生成

**参考答案**

结论：让 LLM 负责"理解和表达"，让算法负责"求解和验证"，二者通过**结构化约束**连接。

做法：

1. **需求结构化**：LLM 把自然语言抽取为约束 JSON（城市、日期、预算、人数、偏好、必去景点、时间窗），缺失信息主动追问。
2. **候选生成**：从真实数据（POI、航班、酒店、营业时间、交通耗时）检索候选，并用偏好打分，避免模型编造不存在的地点。
3. **算法求解**：把行程建模为带时间窗的路径规划问题（类似带时间窗的 TSP/VRP、定向越野问题），目标是最大化偏好收益，约束包括营业时间、交通耗时、每日时长、预算、跨城顺序。这类问题是 NP-hard，实际使用 OR-Tools（CP-SAT/路由求解器）、启发式（贪心 + 局部搜索）或分层求解（先分城市天数，再做每日路线）。
4. **校验**：规则引擎检查所有硬约束，不通过则回到求解或修复。
5. **LLM 润色与解释**：将结构化结果转成自然语言，说明取舍。
6. **动态调整**：用户修改（换景点、预算变动）或外部变化（库存、天气）时，LLM 把变更转成约束修改，算法做**局部重规划**，保持稳定性，减少大幅变动。

关键难点：约束的软硬划分、求解时间要满足交互延迟、数据实时性、方案可解释性。

### 4. Agent 的规划能力不稳定，怎么用反射、自我校验、外部规则约束把准确率拉起来

**参考答案**

结论：不要只依赖模型自省，应当"生成 → 外部验证 → 带反馈修正"形成闭环，并尽可能把确定性部分交给代码。

手段：

1. **结构化输出**：计划以固定 Schema 输出，先校验格式再执行。
2. **外部规则校验（最可靠）**：用代码校验计划是否满足硬约束，如日期合法、营业时间、交通耗时、预算、库存；校验失败的具体原因作为反馈传回模型。
3. **反思（Reflection）/自我校验**：让模型对照检查清单审查自己的计划，或由独立的"评审 Agent"打分。注意同一模型自我纠错能力有限，且可能错判，所以优先用外部验证，自我反思作为补充。
4. **修正循环**：限制最大轮数，每轮把错误信息和上一版计划带上，轮次用完仍失败则降级（使用模板方案、转人工或明确告知不确定）。
5. **任务拆解**：Plan-and-Execute，先出粗计划再逐步细化，每一步单独校验；复杂计算（时间、金额）交给工具或代码，不让模型心算。
6. **Few-shot 与提示优化**：使用线上 bad case 构造示例。
7. **评测驱动**：用回归集量化每种方法带来的准确率提升及额外成本和延迟。

### 5. 系统稳定性设计：限流、熔断、降级、重试、幂等、可观测，六件套怎么落到一个 Agent 平台

**参考答案**

结论：六件套要分别落在接入层、工具网关、模型网关和编排层，由统一的策略配置管理。

- **限流**：接入层按用户/租户限流，模型网关按模型 RPM/TPM 限流，工具网关按下游容量限流；采用令牌桶，配额分级，保证核心业务优先。
- **熔断**：对每个下游（模型供应商、工具服务）设置熔断（如基于 Resilience4j、Sentinel），错误率或慢调用比例超过阈值后快速失败，半开状态探测恢复。
- **降级**：备用模型、缓存结果、关闭非核心工具、固定模板回复、转人工；降级策略预先配置并演练。
- **重试**：仅对幂等且可重试的错误重试（超时、5xx、429），指数退避加抖动，设置重试预算，避免放大雪崩；多层重试要避免叠加。
- **幂等**：写操作使用幂等键；消息消费用唯一键去重；任务状态机条件更新；重试和恢复场景尤其依赖它。
- **可观测**：全链路 traceId，把每次模型调用、检索、工具调用作为 span；指标包括成功率、延迟分位、token 与成本、工具错误率、重复调用率；结构化日志脱敏；告警与大盘；采样保存完整对话供复盘。

落地方式：把这些能力沉淀成平台的网关和中间件，业务工具接入时默认获得，而不是每个团队重复实现。

### 6. 记忆系统怎么设计，短期上下文、长期偏好、用户画像、事实记忆分别存哪、怎么检索

**参考答案**

结论：按时效和性质分层存储，不同类型的记忆用不同的存储和检索方式。

- **短期上下文**：当前会话的最近消息、槽位和任务状态。存 Redis（设置 TTL），完整历史落 MySQL；检索方式是直接读取，必要时窗口截断加摘要。
- **长期偏好**（如喜欢住靠近地铁的酒店）：结构化键值存 MySQL/文档库；由 LLM 从对话中异步抽取，经置信度或用户确认后写入，每条保存来源与时间。使用时在会话开始或相关场景按 key 读取并注入提示。
- **用户画像**：基于订单、浏览等行为数据由离线或实时数据链路生成标签，存在特征库或画像服务，通过 userId 查询，不让模型自己编造。
- **事实记忆**（如"上次去日本是 3 月"）：存向量库，带元数据（用户、时间、类型、置信度），按当前问题 Embedding 检索，结合元数据过滤和时间衰减排序；订单等权威事实应直接从业务库取，不依赖记忆。

设计要点：

1. 写入有策略：什么该记（稳定偏好）、什么不该记（一次性信息、敏感信息）；
2. 冲突与更新：新偏好覆盖旧偏好，保留版本；
3. 隐私合规：用户可查看、修改、删除，敏感信息脱敏和加密；
4. 检索注入时控制 token 量，并标明来源；
5. 评测记忆是否真的提升了效果，避免错误记忆污染回答。

### 7. 多租户场景下，知识隔离、工具隔离、权限隔离、成本控制分别怎么做

**参考答案**

结论：隔离必须由系统在**数据和执行层强制实现**，不能依赖提示词；每个租户的上下文由网关注入。

- **知识隔离**：每条数据带 `tenant_id`，检索层强制附加租户过滤条件，调用方无法绕过。强隔离要求高的租户用独立索引或 collection，甚至独立实例；缓存、语义缓存的 key 同样包含租户。
- **工具隔离**：每个租户有独立的工具白名单和配置；调用外部系统使用该租户自己的凭证（保存在密钥管理系统），工具网关按租户执行；高风险租户可使用独立执行环境或资源池。
- **权限隔离**：租户身份来自鉴权令牌，在租户内再做 RBAC/ABAC 和资源级校验；日志、trace、审计都带租户标识，并保证跨租户不可查。
- **成本控制**：租户级 token 和调用配额、限流、预算告警与超额处理（限速或降级到小模型）；按租户计量统计成本，支持计费；用独立线程池或优先级队列避免"吵闹邻居"影响他人。

验证：增加跨租户越权的自动化测试，定期审计。

### 8. 线上出现幻觉报价、库存不一致、重复下单，事故定责和复盘流程怎么设计

**参考答案**

结论：先止损和补偿用户，再用 trace 还原事实，**按系统原因归因而非追究个人**，最后用可验证的改进措施闭环。

流程：

1. **止损**：关闭或降级相关功能（如禁用自动下单，只允许跳转人工确认），拦截问题请求，补偿受影响用户；
2. **还原事实**：根据 traceId 重建完整链路：用户输入、检索内容、模型输出、工具调用参数与返回、下游响应，确定问题发生在哪一层；
3. **分层归因**：
   - 幻觉报价：价格是否来自工具返回？模型是否自己生成了价格？缺少校验；
   - 库存不一致：是否使用了缓存数据、下单前是否实时校验、是否存在并发超卖；
   - 重复下单：重试或消息重复消费、缺少幂等键、用户重复点击；
4. **定责**：对应到模块归属（模型/提示、检索、工具网关、下游业务、产品流程），采用无责复盘原则，关注"哪个防线缺失"；
5. **改进措施**：价格、库存只能由权威接口给出，输出前做一致性校验；下单环节必须带幂等键并在下单前实时校验；加入 Guardrail、监控告警，把案例加入回归集；
6. **复盘输出**：时间线、影响范围、根因、改进项（负责人和截止时间）、跟踪验证；
7. 事故分级和响应 SLA，定期演练。

### 9. 模型供应商故障或某模型效果突变，网关层怎么路由、灰度、回滚和兜底

**参考答案**

结论：模型网关是 Agent 平台对模型供应商的统一抽象层，要具备路由、健康检查、灰度、回滚和多级兜底能力。

- **统一接入**：屏蔽不同供应商的 API、tool-call 格式差异，对外统一接口，同时做限流、鉴权、计量。
- **路由**：按场景、租户、成本、模型能力配置规则，支持权重；优先级链路：主模型 → 备用模型 → 小模型 → 兜底。
- **故障检测与切换**：健康检查和实时指标（错误率、超时率、429、延迟），熔断异常节点后自动切换到备用，并探测恢复；重试需注意幂等和超时预算。
- **灰度**：按流量比例、用户哈希、租户逐步放量新模型或新 Prompt 版本，对比在线指标（成功率、点踩、成本、延迟），影子流量可在不影响用户的情况下评测。
- **效果突变**：固定模型版本快照，避免供应商静默升级；建立线上质量监控，用固定评测集定时回归，一旦指标下降告警并切换。
- **回滚**：模型、Prompt、路由配置均版本化，通过配置中心一键回滚。
- **兜底**：缓存答案、规则/模板回复、仅提供检索结果、转人工，并明确告知用户。

备用模型上线前要提前评测，因为模型间提示和工具调用表现不同。

### 10. Agent 的可测试性怎么做，图结构怎么写回归用例，效果退化怎么提前报警

**参考答案**

结论：把不确定的部分隔离出来，确定性部分用传统单测，非确定性部分用评测集和阈值。

分层测试：

1. **工具单测**：纯确定性，覆盖参数校验、异常、超时、幂等。
2. **节点测试**：对单个节点输入给定 State，Mock 模型（返回预设输出或录制回放），断言输出的状态更新。
3. **图结构/路径回归**：用脚本化的假模型（按预设返回 tool_calls）驱动整个图，断言**执行轨迹**：经过哪些节点、调用哪些工具、参数是否正确、最终状态，而不是断言自然语言的完全一致。条件边的每个分支都要有用例；还要覆盖异常路径（工具超时、重复调用、中断恢复）。
4. **端到端评测**：用真实模型运行黄金集，指标包括任务成功率、工具选择准确率；文本质量用 LLM-as-Judge 加规则；设置准入阈值，接入 CI。

效果退化预警：

- 发布前跑回归，不达标则阻断；
- 线上持续监控任务成功率、工具错误率、重复调用率、token 消耗、点踩率、人工接管率，与基线对比，偏离则告警；
- 定时用固定评测集探测模型是否发生漂移；
- 灰度发布和影子流量比对；
- bad case 持续进入回归集。

### 11. 技术选型冲突：新技术很香但没踩过坑，旧技术稳但笨重，你怎么拍板

**答题思路**

面试官看的是决策方法，而不是站队。建议这样组织：

1. **先明确目标与约束**：业务要解决什么、上线时间、团队能力、稳定性要求、可接受风险。
2. **列出评估维度**：成熟度与社区、团队熟悉度、运维成本、性能与功能满足度、可回退性、长期维护成本、合规安全。
3. **用数据代替争论**：做小规模 PoC 或压测，基于真实场景测量，而不是靠印象。
4. **控制风险**：新技术先在非核心链路灰度试点，设计抽象层或适配层使其可替换，准备回滚方案，设置明确的评估指标和止损点。
5. **拍板与沟通**：核心链路优先稳定，非核心可以尝试；记录决策依据（ADR），拍板后统一推进，并在试点后复盘。
6. 结尾可以结合自己的真实案例，说明当时怎么选、结果如何、有什么反思。

### 12. 你怎么看 AI Agent 接下来一两年的工程化演进，RAG、Agent、Workflow 边界会不会重排

**参考答案**

结论：边界会变得模糊，趋势是"确定性 Workflow 做骨架，Agent 在局部节点里做决策，RAG 作为 Agent 的一种能力"，工程重点从"能跑"转向"可控、可评测、可运营"。

判断：

- **Workflow 与 Agent 融合**：流程稳定、需要强可控的部分用 Workflow/状态图，需要开放式决策的节点由 Agent 完成。生产系统会更偏混合架构，而不是纯自主 Agent。
- **RAG 变成工具**：从固定的"检索再生成"流程演进到 Agentic RAG，由模型决定是否检索、检索几次、如何改写。但长上下文并不会取代 RAG，因为成本、时效、权限和可追溯性依旧需要检索。
- **工具协议标准化**：MCP 等协议让工具接入更统一，随之而来的是工具治理、权限、安全的需求。
- **工程化重点**：评测体系、可观测、成本治理、安全与 Guardrail、模型网关、记忆管理、断点恢复，这些会成为平台化的核心能力。
- **模型能力提升**会减少部分"编排补丁"，但不会消除对权限、幂等、审计等确定性工程的需要。

观点要保持有依据，并说明哪些是判断而不是定论。

### 13. 最近在学什么新技术，怎么把一个完全陌生的方向啃到能上线

**答题思路**

先说**真实**在学的内容（如 MCP、LangGraph、评测方法、推理优化），不要罗列没碰过的热词。然后展示方法论：

1. **定目标**：为什么学，解决什么业务问题，先定义"能上线"的标准。
2. **建框架**：读官方文档和经典论文/文章，了解核心概念、适用边界和局限。
3. **小步验证**：写最小 Demo，在真实数据上验证关键假设，找到坑。
4. **对比与取舍**：和现有方案比较，评估收益与成本。
5. **工程化**：补齐稳定性、监控、测试、回滚、文档，灰度上线。
6. **复盘沉淀**：写文档或分享，把踩坑变成团队资产。

最好用一个自己的真实例子，讲清楚从陌生到落地的过程和遇到的问题。

### 14. 你怎么做技术判断，信息源是什么，怎么区分真需求和跟风需求

**答题思路**

分两部分回答：

1. **信息源与过滤**：一手来源（官方文档、论文、源码、Release Note）、业界工程实践文章和技术大会、团队内部事故和数据。强调"优先看一手信息，对二手观点要验证"，并说明会自己动手复现。
2. **区分真假需求的方法**：
   - 追问"解决了谁的什么问题"，没有明确用户和问题的是跟风；
   - 看是否有可衡量的收益指标（效率、成本、转化），能否小成本验证；
   - 看当前方案的痛点是否真实存在（有数据支撑）；
   - 替代方案对比：是否有更简单的办法；
   - 用 PoC 或灰度快速验证，再决定投入；
   - 考虑长期维护成本和团队能力匹配度。
3. 可以举一个"拒绝了跟风需求"或"验证后确认是真需求"的真实例子。

### 15. 如果你带人做这个 Agent 项目，需求分歧时怎么推动，进度风险怎么控

**答题思路**

分"需求分歧"和"进度风险"两块：

**需求分歧**

1. 先把分歧具体化：各方的目标、约束、依据；
2. 回到业务目标和用户价值，用数据或小实验验证，而不是争论观点；
3. 明确优先级框架（价值、成本、风险），把需求拆成 MVP 与后续迭代；
4. 无法达成一致时，由明确的决策人拍板，并记录决策理由，保证执行时对齐；
5. 保持透明沟通，同步各方。

**进度风险**

1. 拆分里程碑和可交付物，识别关键路径与技术风险（如模型效果、外部接口依赖），提前做 PoC；
2. 定期同步（站会、周报）并暴露风险，设置预警线；
3. 预留缓冲，必要时砍范围而不是压质量；
4. 并行推进评测集建设、灰度、监控，避免临近上线才补；
5. 风险出现时及时升级并给出方案选项；
6. 项目复盘。

回答时可结合自己带人或牵头的真实经历。

## HR 面

> 以下题目在原 JSON 中位于三面末尾，实际为 HR 面。

### 1. 自我介绍

**答题思路**

HR 面的自我介绍要更贴近"人"和"稳定性"：

1. 基本背景（学历、年限、主要技术方向），简明；
2. 职业经历的主线和每一段的成长，不堆技术细节；
3. 1 到 2 个代表性成果，突出你的角色和贡献；
4. 你的特点（协作、责任心、学习能力）和求职动机；
5. 控制在 1 到 2 分钟，语速平稳，与简历一致。

### 2. 为什么看携程，为什么想做 AI Agent 方向

**答题思路**

1. **为什么携程**：行业定位（在线旅游头部平台）、业务场景丰富（机票酒店行程订单，约束多、链路长，适合 Agent 落地）、数据与业务规模、对技术的重视。结合你研究过的公开信息，不要空泛夸奖。
2. **为什么 Agent 方向**：对 Agent 作为新一代应用形态的判断；自己已有的积累与兴趣（做过的相关项目、学习经历）；觉得这个方向的难点（稳定性、评测、与真实业务结合）正好是自己想深耕的。
3. **匹配点**：你的能力如何与岗位对应，入职后希望解决的问题。
4. 避免只讲"行业热门"或"薪资"。

### 3. 你觉得自己做 Agent 最不可替代的能力是什么

**答题思路**

避免空泛的"学习能力强"，选一个能被事实支撑的能力，按"能力 → 证据 → 价值"回答：

1. 选择 1 到 2 个：例如"把 Agent 从 Demo 做到能扛线上的工程化能力"（稳定性、幂等、降级、可观测）、"用评测和 bad case 回流持续提升效果的闭环能力"、"把业务约束与 LLM 结合的能力"。
2. **证据**：用你项目中的具体案例说明（遇到什么问题、怎么解决、结果如何），只用真实数据。
3. **价值**：这个能力对团队和业务的帮助。
4. 谦虚收尾：承认还需要在哪些方面持续学习，不贬低他人，也不夸大"不可替代"。

### 4. 项目里最挫败的一次，怎么处理的

**答题思路**

用 STAR 结构，选一个真实且有成长性的事件，不要选与你岗位核心能力相冲突的致命失误：

1. **情境与任务**：简要说明项目背景和你的责任；
2. **挫败点**：具体发生了什么（如效果始终达不到预期、线上故障、需求反复变化），当时的感受要坦诚但克制；
3. **行动**：怎么分析原因（数据、日志、复盘）、怎么调整方案、如何沟通求助、如何控制影响；
4. **结果**：问题如何解决，数据或结果如何，即使没有完美结果也要说清收获；
5. **反思**：形成了什么机制或习惯（如上线前评测、灰度、告警、复盘），后续如何避免。

重点体现抗压、负责、复盘和成长，不要抱怨同事或公司。

### 5. 接受加班和值班吗，对线上稳定性的心态是什么

**答题思路**

1. **态度明确**：理解线上系统有值班和应急的需要，愿意承担责任，不回避；同时表达追求通过工程手段（监控、告警、预案、自动化）减少救火，让加班是例外而不是常态。
2. **对稳定性的心态**：敬畏线上，发布有灰度和回滚，故障先止损后定位，事后复盘并改进；Agent 面对外部不确定性，更要提前设计超时、降级、幂等。
3. **边界**：可以表达愿意在必要时投入，也关注效率与可持续，但不要把话说成抗拒。
4. 若有真实的值班或处理故障经历，简要举例。

### 6. 薪资预期和底线，手上其他机会情况

**答题思路**

不要编造具体数字，以自己的真实情况为准。

1. **薪资**：先说明你更看重岗位成长和匹配度；提前调研该岗位的市场行情和自己当前待遇，给出合理区间并说明依据（能力、经验、市场水平）；可以表达有协商空间，总包的构成（薪资、奖金、期权）综合考虑。
2. **底线**：说得有弹性，例如"希望不低于目前的水平并结合整体机会判断"，不要一口咬死也不要完全不设限。
3. **其他机会**：如实但不过度透露细节，表明正在接触其他机会，同时对本岗位有明确的优先意向和理由；不要夸大 offer 来施压，也不要说"没有别的机会"而显得被动。
4. 保持诚信，信息和后续行为一致。

### 7. 未来三年你想成为什么样的技术人

**答题思路**

1. **方向清晰**：例如成为在 AI 应用工程化方面有深度的技术骨干，能独立负责一个 Agent 平台或核心模块，从"会用"到"能设计、能治理、能扛线上"。
2. **分阶段**：第一年快速融入、熟悉业务并把负责的模块做稳；第二年在架构设计、评测和稳定性体系上形成方法论；第三年能带动团队，输出可复用的平台能力或影响团队技术决策。
3. **与公司结合**：说明这个目标如何与公司业务发展相互促进，而不是脱离岗位的空想。
4. **学习方式**：保持对新技术的判断力，注重实战落地和复盘沉淀。
5. 避免说"想转岗"或"三年后创业"等容易引起稳定性顾虑的内容。

### 8. 你有什么想问我的，别问加班多不多这种废话

**答题思路**

提问要体现你对业务和团队的思考，准备 3 到 4 个：

1. **业务与目标**：这个 Agent 团队当前最核心的业务目标是什么？一两年的重点是提升转化、降低客服成本还是新产品形态？
2. **技术现状与挑战**：目前 Agent 平台在评测、稳定性、成本方面最大的挑战是什么？线上效果现在主要靠什么衡量？
3. **团队与成长**：团队的分工和协作方式，新人入职后前三个月的期望和典型的成长路径。
4. **岗位期望**：您认为这个岗位最需要补强的能力是什么？我入职后最先需要解决什么问题？
5. 适当向面试官了解其本人的经历和团队文化。

不要问薪资福利细节（留给 HR 流程）、可以通过公开信息查到的内容，或带有负面倾向的问题。
