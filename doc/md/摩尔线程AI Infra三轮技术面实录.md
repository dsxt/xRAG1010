# 摩尔线程 AI Infra 三轮技术面实录

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

整体偏硬核，没有手撕，反而有点不习惯。问的都是集群、通信、调度里的实际问题，不是背八股就能过。有些中间件题往 AI 场景上靠，结合得比较牵强，但能看出面试官在考察迁移能力。摩尔线程相关的 MUSA、MCCL 问得比较细，没真正排过障，后面很容易被追问住。准备时要多补实际排障案例，不要只讲原理。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「身份 → 一件最相关的事 → 技术栈 → 为什么匹配」讲。这一轮的面试官没听过你的项目，不要一上来堆组件名。

1. 一句话说明年限和方向，例如分布式训练、推理系统或集群平台。
2. 只展开一段你真实做过的事：规模、你负责的边界、瓶颈是算力、显存、通信还是调度。数字用自己的，没有把握的指标不说。
3. 点出你亲手写过或排过障的栈。有 MUSA、MCCL 或国产卡迁移经历就放在这里；没有就讲 CUDA 侧的并行和通信，不要把文档里的名词说成线上经验。
4. 收尾落到想解决的问题，把话头交给下一题的项目。

### 2. 项目介绍

**答题思路**

面试官要听系统和取舍，不是业务故事。用这个顺序：

1. 背景：模型或集群规模，当时慢在显存、吞吐、故障恢复，还是数据加载。
2. 边界：你负责调度、训练框架、通信还是平台，上下游是谁。
3. 方案：并行和存储为什么这样选，放弃过什么。
4. 定位：profiler、日志、哪条指标证明瓶颈在计算、通信、数据或排队。
5. 结果：只报真实的前后对比。
6. 复盘：如果重做，会改哪一个决定。

提前准备三个追问：通信量怎么估、显存大头是参数还是激活、挂了从哪一份 checkpoint 恢复。

### 3. Redis 介绍及其在 AI 训练任务元数据缓存中的适用场景

**参考答案**

**结论**：Redis 适合放训练控制面里读多、可过期、丢了能重建的元数据，不适合当任务状态和资源预留的唯一事实来源。

它是内存键值库，命令在主线程执行，延迟低，适合字符串、哈希、流和带 TTL 的键。训练里可以缓存作业展示状态、节点心跳、数据集分片索引，以及读多写少的配置。心跳设过期时间，进程死后自动消失。

任务有没有提交成功、配额扣没扣、checkpoint 清单以谁为准，要用 MySQL 或 etcd。Redis 只做旁路缓存：先更新数据库，再删缓存。调度选主用 Kubernetes Lease 或 etcd，不要用 Redis 锁硬扛。队列里也不要塞完整样本，载荷放对象存储，Redis 只留任务 ID。

容易漏的是持久化。AOF 每秒刷盘仍可能丢大约一秒的写入，不能靠它防止配额超卖。

### 4. MySQL 的隔离级别及在分布式训练任务状态管理中的一致性保障

**参考答案**

**结论**：InnoDB 默认是可重复读。任务状态靠短事务和条件更新保证不重复调度，隔离级别代替不了幂等。

读未提交会脏读。读已提交避免脏读，同一事务里两次普通读仍可能不同。可重复读用 MVCC 固定快照，加锁读再配合 next-key 锁抑制幻读。串行化把普通读也变成加锁读，调度器吞吐会很差。

状态迁移写成条件更新：影响行数是 1，才算抢到这单。

```sql
UPDATE train_job
SET status = 'Running', version = version + 1
WHERE id = ? AND status = 'Pending' AND version = ?;
```

扣配额用 `remaining >= ?` 的条件更新，和状态变更放进同一个短事务。拉镜像、建通信域不要放在事务里。重试靠任务 ID 的唯一约束，而不是“再读一次还是 Pending”。跨进程的最终一致还要发件箱或事务消息，单机隔离级别覆盖不到。

### 5. Elasticsearch 在 AI 集群日志检索与异常定位中的使用经验

**答题思路**

这题讲你怎么用日志定位故障，不是背倒排索引。按这个顺序：

1. 场景：作业变慢、通信超时或某个 rank 失败时，用作业、节点、rank 和时间窗过滤，而不是在全库搜一段报错。
2. 索引里留什么：时间、集群、节点、作业、rank、级别、错误码。原始长日志可以不建索引，避免动态映射把字段撑爆。
3. 你怎么查：先缩到失败 rank 的前后几分钟，再和 GPU、网络指标对齐时间。
4. 只讲你踩过的坑，例如刷新太密、对高基数字段做聚合、把监控指标也灌进 ES。
5. 结果落到哪一类原因：单节点、通信或数据。没有的数字不要编。

原理点到即可：过滤字段用 keyword，按天建索引，用生命周期删旧日志。段合并留给专门的原理题。

### 6. Kafka 在 AI 训练流水线中解耦数据预处理与训练节点的场景题

**参考答案**

**结论**：用 Kafka 吸收预处理和训练的速度差。消息里放样本指针，不要把样本本体塞进 Kafka。

预处理把分词、过滤、打包后的样本写到对象存储或并行文件系统，再发送样本 ID、路径和长度。训练进程按分区消费，把指针交给 DataLoader 去顺序读。两边可以独立扩容，预处理失败也不会直接打死 GPU 进程，积压量就是反压信号。

分区只保证分区内有序。shuffle 和断点续训以样本 ID、采样器状态为准，并把已消费位点写进 checkpoint，否则重启会大段重放或跳过样本。投递按至少一次加幂等 ID 来做。

大消息会拉高延迟，图片和长序列不适合进 Kafka。训练进程被踢出消费组时，step 会卡住。分区键也不要打在极少数键上。Kafka 是缓冲，一个 epoch 的全量数据仍然应该落在文件系统上。

### 7. RocketMQ 事务消息原理及如何保证训练任务下发与资源预留的最终一致性

**参考答案**

**结论**：事务消息把“本地已经预留资源”和“任务对消费者可见”收成最终一致。崩溃窗口靠回查和对账，不是两阶段提交。

生产者先发半消息，这时训练节点看不到它。接着在数据库里用条件更新预留 GPU，并写下预留记录。成功就提交消息，失败就回滚。只有提交之后，消费者才能拉到下发指令。生产者若在确认前崩溃，Broker 会回查；有预留记录就提交，没有就回滚。

消费者按任务 ID 幂等建作业。预留要有超时，对账任务把“留了资源但长期没跑起来”的配额还回去。本地事务提交之后，再单独向 Broker 发送提交或回滚，不要把这次 RPC 包进数据库事务。

半消息的确认和数据库提交不是同一次原子写入。隔离级别填不上这个窗口。

### 8. 模型参数量过大单卡显存不足时，TP、PP、DP 并行的区别与选型考量

**参考答案**

**结论**：数据并行切批次，张量并行切层内矩阵，流水线并行切层。通信范围决定并行度放在哪。

数据并行是每卡一份模型、不同的 micro-batch，反向再同步梯度。模型状态放不下时，再配 ZeRO 或 FSDP。它实现简单，但解决不了“一层的权重或激活本身超过一张卡”。

张量并行把同一层矩阵按行或列切开。每个 Transformer 层前向大约两次 AllReduce，反向再两次。通信次数多，要放在节点内的 MTLink 或 NVLink 上，度数一般等于机内卡数。

流水线并行按层切 stage，只在边界传激活，可以跨机。气泡大约占 \((P-1)/(M+P-1)\)，\(P\) 是 stage 数，\(M\) 是 micro-batch 数。1F1B 主要降低激活显存，气泡比例还在；交错流水线才能再把气泡压下去。

常见摆法是机内 TP、跨机 PP、最外层 DP。先算参数、梯度和优化器状态能不能进显存，再看机间带宽够不够频繁做集合通信。激活大时，优先重计算和减小 micro-batch，而不是无脑加大 TP。

### 9. DeepSpeed ZeRO 各阶段的显存优化原理及通信开销分析

**参考答案**

**结论**：ZeRO 去掉数据并行里每卡各存一份模型状态的冗余。阶段 1 和 2 的通信量可以做到与普通数据并行同级，阶段 3 大约是 1.5 倍。

混合精度 Adam 下，每个参数约 16 字节：半精度参数和梯度各 2 字节，FP32 主权重、动量、方差共 12 字节。设数据并行度为 \(N\)：

- ZeRO-1 切优化器状态，每卡约 \(4\Psi + 12\Psi/N\)。
- ZeRO-2 再切梯度，每卡约 \(2\Psi + 14\Psi/N\)。
- ZeRO-3 再切参数，每卡约 \(16\Psi/N\)。

高效实现把梯度 AllReduce 拆成 reduce-scatter，更新本分片后再 all-gather 参数，所以前两个阶段仍是一次 AllReduce 的量级。阶段 3 在前向和反向都要 all-gather 参数，用完释放，总量约 1.5 倍，靠按层预取和计算重叠盖住。PyTorch FSDP 的 `SHARD_GRAD_OP` 对应阶段 2，`FULL_SHARD` 对应阶段 3。

ZeRO 不切激活。all-gather 的临时缓冲会让峰值高于公式。若先做完整 AllReduce、再额外同步参数，阶段 1 就会比朴素数据并行更贵。机间带宽差时，阶段 3 更容易把 step 打满在通信上。

### 10. Megatron-LM 的 Column Parallel 与 Row Parallel 矩阵划分策略

**参考答案**

**结论**：列并行按输出维切权重，行并行按输入维切权重。两层线性这样配对，中间的逐元素激活不用通信。

MLP 是 \(Y=\mathrm{GeLU}(XA)B\)。\(A\) 做列并行：每卡拿完整输入和一部分列，算出自己那一段，GeLU 在本地做。\(B\) 做行并行：输入的切分和 \(B\) 的行切分对齐，每卡只得到部分乘积，再 AllReduce 成完整输出。注意力里 QKV 投影用列并行，按头切开，头内注意力没有通信；输出投影用行并行，再做一次 AllReduce。

因此每个 Transformer 层前向两次 AllReduce，反向再两次。列并行的反向要汇总输入梯度，行并行的前向要汇总输出。行并行的偏置只能在汇总之后加一次，不能每张卡各加一次。

2019 年的切法仍会在每卡保存沿序列展开的激活。后来的序列并行把 LayerNorm 和 Dropout 也沿序列切开，列并行前 all-gather，行并行后 reduce-scatter，用通信量换激活显存。只讲行列切分、不说激活还在不在每张卡上，容易被追问。

### 11. NCCL/MCCL 集合通信中 Ring AllReduce 与 Tree AllReduce 的带宽与延迟差异

**参考答案**

**结论**：Ring 的带宽好，步数随卡数线性增加。Tree 的步数是对数，小消息和大规模时延迟更合适。

Ring 分成 reduce-scatter 和 all-gather，各 \(N-1\) 步，每步大约传 \(D/N\)。每卡总发送量约 \(2(N-1)/N\cdot D\)，卡数变大时接近 \(2D\)，所以能把链路打满。代价是启动 \(2(N-1)\) 次。消息小，或者规模到了千卡以上，延迟会盖过带宽优势。

二叉树向上归约、再向下广播，步数是 \(O(\log N)\)，但单树的链路利用差。NCCL 用两棵互补的二叉树，让延迟保持对数，带宽接近 Ring。大块梯度常用 Ring，或者节点内先走 NVLink、MTLink，节点间再走网。小消息更偏 Tree。

MCCL 同样按拓扑和消息大小选算法，没有一个通用的切换字节数。以 `MCCL_DEBUG` 的日志和 `all_reduce_perf` 为准。分层做错时，机内高速互联会被绕开。

### 12. RDMA 在 AI 集群中的优势，RoCE 与 InfiniBand 的选型对比及丢包影响

**参考答案**

**结论**：RDMA 让网卡绕过内核直接读写内存，集合通信才有机会接近线速。InfiniBand 默认按无损织物工作；RoCE v2 跑在以太网上，丢包会把同步集合通信拖垮。

训练里一次 AllReduce 是所有卡一起等，一条流变慢，整个 step 都变慢。GPU 与网卡直通还能省掉主机内存里的一次拷贝，摩尔线程侧要确认当前驱动和网卡确实走了这条路径，不能默认已经打开。

InfiniBand 用信用流控，正常时不靠丢包表达拥塞，适合紧耦合训练，代价是独立组网。RoCE v2 把 RDMA 封在可路由的 UDP/IP 里，通常靠 PFC 避免丢包，再用 ECN 和 DCQCN 控制拥塞。PFC 配错会出现暂停帧风暴，甚至死锁。

RoCE 上少量丢包就会引起网卡重传。集合通信看的是尾延迟，表现是总线带宽远低于线速、step 时间抖动。IB 上丢包少见，真出现了，多半是链路、光模块或拥塞配置故障。选型要看集群有没有无损以太网的运维能力，不要只比网卡标称速率。

### 13. GPU 拓扑感知调度（NVLink/PCIe）在 K8s 中的实现难点及缓存亲和性场景题

**参考答案**

**结论**：Kubernetes 默认只按 GPU 个数调度，不知道卡之间怎么连，也不知道数据缓存在哪。张量并行必须落在同一高速互联域里。

device plugin 往往到了 kubelet 才真正挑卡，调度器早先只看到“这台机器有 8 张卡”。PCIe 机器上的 8 张卡并不等价，跨 NUMA 或跨根复合体会把 P2P 打到慢路径。整机 NVSwitch 或全连接 MTLink 时，机内相对均匀，问题转移到 GPU 和网卡是不是同一个 NUMA。实现上要用拓扑管理、节点标签和调度插件，把一个互联域当成分配单位，必要时整机独占。只写 Preferred 亲和，资源一紧就会被打散。

缓存亲和是另一件事。数据集或镜像已经在节点本地盘时，优先把作业分过去，避免千卡同时打到共享存储。它只能加偏好分，不能做成硬约束，否则和 Gang、配额冲突：热节点被撑死，冷节点空着。未命中要能回退到远程读。

### 14. 混合精度训练中 FP16 与 BF16 的数值稳定性差异及 Loss Scale 原理

**参考答案**

**结论**：FP16 指数位少，小梯度会下溢，所以要做损失缩放。BF16 的指数范围和 FP32 相同，通常不用损失缩放，但尾数更短。

FP16 是 1 个符号位、5 个指数位、10 个尾数位，可表示的最大值约 65504，稍大的激活或梯度就会溢出。BF16 是 8 个指数位、7 个尾数位，动态范围和 FP32 同级，舍入误差更大。两种格式的优化器状态和主权重都应留在 FP32，Softmax 和 LayerNorm 的归约也用 FP32 累加。

损失缩放是给 FP16 用的。反向前把 loss 乘上缩放因子，让梯度落进可表示范围，更新前再除掉。动态缩放发现 inf 或 NaN 就丢掉这一步并减小因子，连续若干步正常再增大。BF16 再套损失缩放没有这个收益，因子过大时反而会溢出。

对齐时看 loss 曲线和梯度范数，不要追求逐 bit 相同。这张卡有没有对应的半精度计算单元，以该型号的文档和实测为准。

### 15. 算子融合（Operator Fusion）在推理优化中的作用及访存瓶颈分析

**参考答案**

**结论**：算子融合减少内核启动，更重要的是让中间结果留在片上，少做几次显存往返。推理的 decode 往往先碰到带宽，而不是峰值算力。

GEMM、加偏置、激活分开执行时，每个算子都把中间张量写出显存再读回来。算术强度低，运行点落在屋顶线的带宽一侧。融合后只读一次输入和权重、写一次最终结果，偏置和激活留在寄存器或片上存储里完成。注意力不物化 \(N\times N\) 的分数矩阵，也是在省这一类流量。

decode 的 batch 很小时，权重本身就要整份流过显存。融合消得掉后处理流量，消不掉权重流量。权重仍是大头时，要靠量化、批处理和 KV Cache，而不是只融合 epilogue。

融合会抬高寄存器压力，占用下降后可能变慢。动态形状还会让编译缓存失效。数值顺序变了，要用同一批输入对比融合前后的输出。

## 二面

### 1. 自我介绍

**答题思路**

这一轮通常换了面试官，自我介绍要重讲，但把时间让给规模和故障。控制在 1 分钟出头。

1. 一句话报方向和年限。
2. 直接进入最大规模的训练或推理系统：多少卡、你负责哪一层、一次真实故障你怎么处理。没做过千卡，就说你做过的最大规模，不要往上编。
3. 只留一个技术关键词作为钩子，例如 Gang 调度、异步 checkpoint 或 MCCL 带宽，让面试官顺着问。
4. 不要重复一面里已经展开的业务背景。

### 2. 详细描述你参与过的千卡级或大规模 AI 训练/推理基础设施建设项目

**答题思路**

按系统边界讲，不要编一个没做过的千卡项目。如果规模没到千卡，先说明真实规模，再讲哪些设计是为了继续扩大。

1. 目标：吞吐、交付时间，还是作业成功率。谁使用这套平台。
2. 结构：队列和调度、训练或推理运行时、通信、存储、监控各自由谁负责，你在哪一层。
3. 并行和放置：TP 是否限制在机内互联域，作业是否整组调度，节点按什么芯片和驱动分池。
4. 稳定性：checkpoint 写在哪，单节点失败后怎么重排队，坏节点会不会被再次分进去。
5. 你亲自排过的一个瓶颈，包括当时看的指标和放弃的方案。
6. 结果只报真实数据。准备被追问：MFU 的分子分母、恢复时间、存储有没有被 checkpoint 打满。

### 3. 在 K8s 上部署大模型训练时遇到 Pod 调度死锁或资源碎片，如何用 Gang Scheduling 解决

**参考答案**

**结论**：Gang 调度让分布式作业要么整组拿到资源，要么继续排队，避免每个 Pod 先占住一部分 GPU，然后互相等待。

默认调度器按 Pod 绑定。一个 64 卡作业先启动 40 个 Pod，就会把卡占住，剩下的 Pod 继续 Pending；另一个作业反过来占着它需要的卡，这就是持有并等待。碎片则是空闲卡的总数够，但凑不齐同一作业要求的整组，再加上同机拓扑之后更明显。

做法是给作业一个组，声明最少成员数。调度时先看有没有足够的 GPU 和拓扑域，够才一次性绑定，不够就不占。高优先级作业可以抢占出一整组，被抢占的一方要有时间写 checkpoint。Volcano 的 PodGroup、调度器里的 coscheduling 插件，以及 Kueue 在准入时按整组计算配额，都是这个语义。

超时还没凑齐，必须整组释放，否则 Gang 自己也会卡住。弹性作业要把最小副本和最大副本分开，不能要求最大值同时就绪。

### 4. Volcano 与 Kueue 调度器在 AI 负载排队与抢占策略上的区别及适用场景

**参考答案**

**结论**：Volcano 自己做排队和落点，适合单集群里的整组调度、装箱和拓扑。Kueue 先做配额准入，Pod 仍交给 Kubernetes 调度器放置，适合多租户借用和多集群。

Volcano 用队列和 PodGroup 描述批作业，在一个调度周期里完成入队、分配、抢占和回收，并能按装箱或主导资源公平来打分。GPU 拓扑和整组放置可以做成调度插件。它在绑定的关键路径上，能力集中，集群也要按主调度器来运维。

Kueue 放在 Job、JobSet、RayJob 之上。ClusterQueue 的配额不够就排队，够了才允许创建 Pod。同一组队列可以借用空闲配额，不够时按优先级回收整份低优先级 Workload。它也能把作业派到另一个集群。准入通过只说明配额够，卡仍可能因为碎片放不下去；卡级装箱要靠后面的调度器。

一个集群不要让两边各排一次队。已经用 Volcano 做 GPU 装箱时，就不要再叠一层互不相通的准入，除非配额和放置的边界划清楚。

### 5. 训练过程中因节点故障触发 Checkpoint 恢复，如何设计异步 Checkpoint 降低存储 IO 对训练的阻塞

**参考答案**

**结论**：异步 checkpoint 先把这一步的状态拷出 GPU，训练继续，再在后台做成持久副本。进程崩溃时，只能回到最后一次写完的清单。

优化器步进之后、下一步改写参数之前，状态是稳定的。每个 rank 先把自己的分片拷到独立缓冲，例如主机固定内存或本地 NVMe。这块显存在拷贝完成前不能被下一步改写。拷贝用单独的流，上传再和后续计算重叠。分片都写完之后，最后原子提交清单，读者不会打开半份 checkpoint。旧的一份在新的一份上传完成前不能覆盖。

节点盘会跟着节点一起坏，所以本地副本只减小抖动，持久副本必须离开这台机器。上传要限速，并避开集合通信用的网卡，否则 checkpoint 把 MCCL 的带宽吃掉。

采样器位置、随机数和数据消费位点都要进快照，只存权重会对不齐续训。后台失败必须让作业失败或告警，不能出现训练还在跑、实际上没有可恢复点。

### 6. 多机多卡通信带宽不及预期时，从网卡绑定、NUMA、QP 数量、MCCL_DEBUG 排查的思路

**参考答案**

**结论**：先分清慢在机内还是机间、慢在哪一对，再改网卡、NUMA 和 QP。`MCCL_DEBUG` 用来核对库实际走了哪条路。

用 `all_reduce_perf` 先跑单机，再跑两机，再放到作业同规模。AllReduce 的总线带宽约等于算法带宽乘 \(2(N-1)/N\)，拿它和 MTLink 或网卡线速比。卡数不同的节点不要直接比绝对值。

计算网口、存储网和管理网要分开。官方排障用 `MCCL_SOCKET_IFNAME` 指定控制面网口，用 `MCCL_TOPO_DUMP_FILE` 把拓扑打出来，再对照 `mthreads-gmi` 看 GPU 和网卡有没有跨 NUMA。进程和中断绑到同一侧，避免跨插座走 PCIe。

QP 太少打不满多轨网卡，太多会让网卡上的连接缓存抖动。变量名以这一版 MCCL 文档为准，不要把 NCCL 的环境变量照抄进启动脚本。

`MCCL_DEBUG=INFO` 看算法、通道，以及有没有退回 socket。单机失败先查 P2P、MTLink 或 PCIe、共享内存和容器设备挂载。单机正常、跨机失败，再查 RDMA、GID、防火墙和丢包。需要关 ACS 或改交换机时，先留证据，交给管理员。

### 7. 推理框架 vLLM 中 PagedAttention 的核心思想及如何优化 KV Cache 内存碎片

**参考答案**

**结论**：PagedAttention 按固定块管理 KV Cache，用块表把逻辑块映射到物理块，避免按最大长度预留造成的碎片。

每个请求若按最大序列长度分配连续显存，短请求内部有空洞，请求结束后又留下外部碎片，显存还有剩余也开不了新请求。分页后，KV 切成固定块，常见实现里一块装十几个 token。生成时按需领块，结束就归还。内部碎片主要剩最后一块没填满的部分，外部碎片接近消失。

物理块不连续，注意力内核必须按块表读取 K、V。若先拷回一大段连续内存，省下的显存会再花到拷贝上。相同前缀可以共享块，多条采样分支用写时复制，所以它也是前缀缓存的基础。

连续批处理让请求随时进出，靠的就是不必搬动一整块连续缓存。块太大，碎片回来；块太小，块表和访存都变差。块大小要按真实序列长度分布选。

### 8. LLM 量化技术 INT8、W4A16 流程，若数据分布极不均匀（最小值 -10000，其余在 [-1, 1]）应选何种量化策略

**参考答案**

**结论**：这种分布不能用全局 min-max。把离群值分开，用更高精度计算，其余数据再用紧的 scale 做 INT8 或 4 比特权重量化。

INT8 把权重或激活映射到 8 位整数，按张量、通道或组配 scale。权重量化常用 per-channel。激活范围依赖输入，要用校准集做静态 scale，或运行时按 token 统计。W4A16 只把权重压到 4 位，激活留在 FP16 或 BF16，计算时反量化。它省的是解码阶段的权重访存。组越小，scale 越能跟上局部范围，额外存储也越多。

最小值是 -10000、其余落在 \([-1,1]\) 时，无论对称还是非对称，整张量的 scale 都被这一个端点拉开，正常值在整数里几乎没有分辨率。离群值若集中在少数通道，per-channel 或 per-group 可以保住其他通道；一个组里只要混进这个点，该组仍然无效。

更稳的是 LLM.int8() 那种分解：离群通道用 FP16 做矩阵乘，其余用 INT8，再把结果相加。激活上的系统性离群可以用 SmoothQuant 挪到权重上，但单点极端值更适合隔离。确认它是噪声后才可以截断。W4A16 不量化激活，所以激活离群还能保留；权重离群仍然要靠分组或混精。用任务指标验收，不要只看量化误差。

### 9. Speculative Decoding 原理及与量化技术结合时的工程挑战

**参考答案**

**结论**：投机解码让小模型先猜若干 token，大模型一次前向验证。接受率够高，才能少跑大模型的解码步。和量化叠在一起时，分布和显存预算都会变。

草稿模型自回归提出 \(K\) 个 token，目标模型并行验证这条候选。拒绝采样以 \(\min(1,p/q)\) 的概率接受；拒绝后，从修正过的分布重采样。这样对齐的是目标模型的分布。加速比取决于接受率，也取决于草稿自己的成本。Medusa、EAGLE 用小草稿头代替第二个完整模型，验证方式不同，但都要能回滚没被接受的 token。

量化会改变 logits。草稿按 FP16 目标对齐，线上却验证 INT4 或 W4A16 模型，\(p\) 和 \(q\) 就不是同一个分布，接受率下降，输出也不再等于要上线的模型。验证路径必须使用和线上相同的量化内核。被拒绝的 KV 要按块释放，不能只把序列长度减回去、块仍占着。

草稿模型占用的显存，可能吃掉量化省出来的空间，并发下降后吞吐反而不如只做量化。温度和 top-p 也必须与验证路径一致。

### 10. 存储层面对象存储 + Ceph 与并行文件系统 Lustre/GPFS 在训练数据加载中的取舍与缓存加速方案

**参考答案**

**结论**：训练加载要高带宽顺序读，checkpoint 要扛突发写。并行文件系统适合这条热路径；对象存储适合容量、多租户和跨集群归档，中间通常要本地缓存。

Lustre 和 GPFS 把文件条带化到多个存储目标，POSIX 访问直接，单客户端的顺序带宽高，也适合希望尽快读回的 checkpoint。代价是独立集群，元数据怕海量小文件，跨地域基本不现实。

对象存储加上 Ceph 这种后端，容量和多租户更容易扩展，适合数据集和 checkpoint 归档。小文件延迟、目录列举都差。训练如果还在对海量小文件做 open 和 seek，GPU 会等数据。CephFS 虽是 POSIX，大规模同时写 checkpoint 时，元数据和锁仍可能成为瓶颈。

落地时把样本收成大分片，节点本地 NVMe 做预取，未命中再回源。checkpoint 先写本地，再异步上传，清单最后提交。缓存盘不要和 checkpoint 盘混用。选哪边，先用真实作业测顺序读带宽、小文件比例和恢复时间。

### 11. Redis 大 Key 与热 Key 问题在 AI 任务队列中的表现及拆分、本地缓存、Proxy 层限流等解决方案

**参考答案**

**结论**：大 key 是一条命令堵住实例，热 key 是所有客户端打在同一个槽上。加 Redis 节点不会自动把这两类问题拆开。

大 key 常见是一个 List 里堆满带特征的任务，或一个 Hash 存着全部作业状态。删除和遍历都在主线程上执行，其他命令一起排队，复制也会落后。载荷应放到对象存储，Redis 只留 ID；队列按槽位拆开；删除用 UNLINK。不要对这种 key 做全量遍历。

热 key 常见是所有 worker 对同一个 List 做阻塞弹出，或一起轮询同一份配置。读副本解决不了写热点。队列拆成多条，客户端随机选；读多写少的配置可以在进程内做短 TTL 缓存，并用 singleflight 合并同时回源。代理限流用来挡住打爆 Redis 的重试，同时要给生产者反压。

租约、锁和任务所有权不能进本地缓存。真正要重放的日志型队列更适合 Kafka，Redis 留给出队延迟敏感的小元数据。

### 12. Kafka 消息积压在特征流转场景下的成因，如何从分区扩容、消费并发、下游算力排查

**参考答案**

**结论**：先看积压是各分区一起涨，还是集中在少数分区，再决定扩分区、加消费者，还是查下游算力。

消费并行度的上限是分区数。所有分区的 lag 都在涨，消费线程又不忙，才是分区不够或单条处理太慢。只有一个分区涨，就是键打歪了；给已有主题加分区，不会把这个旧热点拆开，要改分区键。

不要在 poll 线程里做重特征计算。按批拉取，交给有界队列；下游慢时停止拉取，而不是在内存里无限堆积。处理时间超过 `max.poll.interval` 会触发重平衡，积压时越重平衡越慢。

下游是特征库或 GPU 推理时，消费者再多也只是把压力往后推。分区 lag、消费 CPU 和下游延迟要一起看。下游饱和就扩算力或降级，而不是先扩 broker。回补历史数据应使用单独主题，避免和线上写入打满同一批分区。

### 13. Elasticsearch 倒排索引在海量训练日志聚合分析中的性能瓶颈及 Segment 合并调优

**参考答案**

**结论**：倒排索引适合按作业、节点和错误码过滤日志。海量训练日志慢，通常是因为段太多、合并抢 IO，以及高基数聚合，不是倒排这个结构本身慢。

每个段有自己的词典和倒排表。刷新越频繁，小段越多，一次查询要打开的段也越多。合并能减少段数，但会占用 CPU 和磁盘，和写入、查询抢资源。日志按时间切索引，加大 refresh interval，过期就整索引删除。不要在还在写的热索引上 force merge，也不要用按查询删除来清理大量日志。

动态映射会让每种 JSON 字段都进映射，集群状态跟着膨胀。只把要过滤的字段建成 keyword，原文不索引或采样保存。对 pod、rank 做全量 terms 聚合会占用大量堆。利用率和丢包这类指标进 Prometheus，ES 只留需要检索的事件。

合并线程、每层段数和段大小可以调，但先分清是写入被合并拖死，还是查询打开了过多小段。这两个方向的调法相反。

### 14. 国产 GPU（摩尔线程等）与 NVIDIA 架构在 MUSA/CUDA 算子移植、通信库适配中的差异与坑点

**参考答案**

**结论**：MUSA 沿 CUDA 的编程模型设计，源码转换或编译期映射能搬过大量调用。算子覆盖、数值和拓扑仍要逐项验收。通信换成 MCCL，不是改一个字符串就结束。

运行时、流和设备内存走 MUSA，深度算子走 MUDNN 这一层，集合通信走 MCCL。`torch_musa` 把设备从 cuda 换成 musa，分布式后端从 nccl 换成 mccl。官方提供 musify 和编译期 CUDA 映射。自定义 kernel、FlashAttention 一类实现，以及绑定特定硬件指令的扩展，不在自动替换范围内。缺算子会直接失败，或者退回 CPU，功能还在，性能已经没了。

核函数不能假设 warp 宽度、共享内存和矩阵指令与 NVIDIA 相同，块大小和占用要重调。随机数、归约顺序不同，loss 按容差对齐；对不齐时先关 dropout、固定输入，再逐层比。驱动、MUSA、MCCL 和框架插件必须按配套版本安装。

MCCL 能走 MTLink、PCIe 和节点间 RDMA，集合通信也能进 MUSA Graph。图捕获期间不能照搬 CUDA Graph 的缓冲区注册调优，多通信器从同一线程启动图也观察到过死锁。先用 `all_reduce_perf` 确认机内走了 MTLink，再跑作业。只替换库名、不看拓扑，多半仍走在慢链路上。

### 15. AI Infra 中监控 GPU 利用率、显存、IB 网络丢包、PCIe 抖动的关键指标及 Prometheus + DCGM 落地

**参考答案**

**结论**：利用率、显存、网卡丢包和 PCIe 链路要分开采集。DCGM 只覆盖 NVIDIA。摩尔线程节点用自己的导出器，Prometheus 负责汇到一起。

GPU 看核心利用率、显存占用、温度、功耗和降频原因。利用率低，可能是在等数据或通信，也可能是时钟被降下来，要和 step 时间一起看。驱动看到的显存占用，和框架分配器保留的显存不是同一个数，碎片化时前者已经很高。节点上用 `mthreads-gmi`，集群里由 GPU Operator 的导出器刮进 Prometheus。在 MTT 节点上部署 DCGM，读不到这张卡。

IB 或 RoCE 看端口速率、错包、重传和 PFC 暂停帧。集合通信抖动时，这些计数要能对到同一台机器上的 MCCL 超时。PCIe 看链路宽度和代数有没有下降，以及重放计数。PCIe 抖动指的是 step 时间的方差跟着链路重放或降速出现，不是再做一个利用率面板。

训练侧另记 MFU、step 时间、计算和通信各占多少。标签留到作业、节点和 GPU 序号。告警用“作业在跑但利用率为零”“链路宽度低于预期”“出现不可纠正或互连类错误”。阈值取这套集群的基线，不抄一张与硬件无关的表。

### 2. 项目架构设计经验，如何主导设计一个支持多租户的千卡 AI 训练平台

**参考答案**

**结论**：按控制面、调度、运行时、数据和网络拆开。千卡多租户难在隔离和恢复，不是把 Job 包一层 API。

用户代码直接跑在 GPU 节点上，不能靠“都是内部用户”。限制特权容器、主机目录和网络，只挂这个作业该看到的设备。抢占前留出写 checkpoint 的时间。计量和日志从第一版就有，否则无法追责，也做不了配额。

第一版先保证单集群能排队、能跑完、能从最近一份完整 checkpoint 拉起。弹性跨集群不要和第一版绑在一起。

### 3. 怎么管理 AI Infra 团队成员及技术路线规划，如何权衡自研调度器与开源方案的债务

**答题思路**

先讲约束，再讲路线，最后讲人。没有管理职级，就讲你怎么推动过一次技术决策。

1. 优先级只看稳定性、交付时间和现有人力，不看技术喜好。
2. 路线按季度拆：现在必须交付的、可以跟随上游的、必须自己写的。每项写清退出条件，什么指标没达到就停。
3. 自研调度器的债，具体到三件事：和 Kubernetes、Volcano 或 Kueue 的行为差谁来补；集群升级要改多少补丁；on-call 是不是始终同一两个人。
4. 开源已经覆盖整组调度、配额和优先级时，只补拓扑和国产设备插件。全量自研只在上游改不动、而且有人长期维护时成立。
5. 分工按链路，而不是按“前端后端”：调度、通信、存储各有负责人。周会看故障复盘。意见不一致时用同一份作业的实验，不靠资历压过去。
6. 不要编团队规模、汇报线和绩效制度。

### 4. 当团队成员对分布式存储选型（如 JuiceFS vs Alluxio vs Lustre）意见不一致时如何沟通并说服

**答题思路**

先把产品名收成同一组指标，再用一段真实作业比较。不要用“业界都在用”压人。

1. 约定要测的东西：每卡顺序读带宽、checkpoint 突发写、小文件比例、要不要跨集群、谁值班。
2. 三种东西不在一层，讨论前先说清楚。Lustre 是并行文件系统，适合训练热路径。JuiceFS 把 POSIX 建在对象存储上，元数据在独立引擎里，客户端带本地缓存，适合已经有对象存储、又不想再运维一套专有存储的情况。Alluxio 是缓存层，不是数据的归属地，多个计算集群反复读同一份远程数据时才有意义。
3. 用同一份作业、限定时间和成功标准做对比，例如 GPU 等数据的比例、恢复时间。比完只留一条热路径。
4. 公开数据和失败情况。给反对意见留回退：热数据走 Lustre 或 JuiceFS 的本地缓存，冷数据进对象存储。只有命中率被证明不够，再加 Alluxio。
5. 决定写成一页：选了什么、不选什么、什么信号出现就重新打开。避免三套同时进生产。

### 5. 怎么保证大规模 AI 集群的 SLA 与稳定性，灰度发布、熔断及故障演练机制

**参考答案**

**结论**：千卡作业碰到单机故障是常态。SLA 要承诺的是恢复时间，不是零失败。

指标先定清楚：排队时延、作业失败率、真正产出 step 的 GPU 时、checkpoint 成功率和恢复时间。不同租户可以有不同的排队和抢占策略，不要所有人共用一个脱离硬件规模的可用性数字。

灰度对象是驱动、MCCL 和训练镜像。先放进一小部分节点，跑通带宽测试和一小段 loss 对齐，再扩大。超时变多或 loss 偏离，就停止继续发布；已经跑起来的作业留在旧节点上直到结束。

熔断打在依赖上。并行文件系统的错误率或延迟越过基线，就暂停新的、会密集写 checkpoint 的作业，避免把存储打到不可恢复。同一节点连续出现互连或 XID 类错误，就把它隔离出队列。熔断停的是新入口，不是把正在写的 checkpoint 掐断。

演练要真做：停掉一个 rank、让计算网失效、写满本地盘，然后看整组资源有没有释放、作业能不能从最后一份完整清单拉起、告警有没有到人。第一次不要放在全集群唯一的生产队列上，并事先写好回退时间。

### 6. 多集群管理方案，跨地域 AI 训练面临的带宽时延与数据同步一致性问题

**参考答案**

**结论**：一次同步训练必须留在同一套低延迟网络里。跨地域搬的是数据、镜像和已经提交的 checkpoint，不是 AllReduce。

跨地域时延是毫秒到几十毫秒，带宽也不是机内互联。张量并行和频繁的梯度同步过广域网，step 会被通信占满。流水线理论上可以跨地域传激活，气泡和故障域都会差到不值得做。

数据集用版本号。作业启动前，清单和校验和必须到齐，否则继续排队，不边同步边训练。训练过程中的 checkpoint 以作业所在地域为事实来源，写完再复制到另一地域做灾备。两个集群不要同时写同一步。

控制面保证一个作业只被一个集群认领，另一地域是故障转移，不是双活计算同一步。调度看数据在哪、哪种卡在哪。数据量大过广域网能在可接受时间内搬完的量，就把作业派到数据那边。

摩尔线程和 NVIDIA 是不同的资源池。不能为了有空闲卡，把 MUSA 作业派到只有 CUDA 软件栈的集群。

### 7. Kubernetes Operator 开发经验，如何设计 CRD 管理训练任务生命周期与弹性伸缩

**参考答案**

**结论**：CRD 表达作业的期望状态，Operator 把 Pod、服务和 checkpoint 收敛到这个状态。弹性伸缩难在进程组和分片能不能对上，不在修改 replicas。

规格里写角色、副本数、镜像、资源、最小可用数、重试和 checkpoint 策略。status 只放阶段、条件和各角色是否就绪。日志和大列表不要写进 status。控制器发现差异后创建 Headless Service、作业和 PodGroup，异常记成事件，用 finalizer 回收通信组和临时卷。

状态保持短：等待、运行、重启、成功、失败。一次调和只做当前状态该做的事，靠重新入队推进，不要在一次调用里跑完训练。`observedGeneration` 用来区分用户改了规格，还是控制器自己更新了状态。

多数同步训练不能在一步中间改变世界大小。成员变化要落在步边界：通知工人、等 checkpoint 完成、按新并行度重新加载，并做分片重切。框架不支持时，Operator 不能假装热加入一张卡。Pod 中断预算、抢占和故障隔离会互相挡住，该摘除的坏节点不要被预算永久留住。

### 8. 国产 AI 芯片在集群部署中的显存隔离（MIG/cGPU 类）、驱动兼容性及生态适配难点

**参考答案**

**结论**：MIG 是 NVIDIA 在部分数据中心卡上的硬件分区。摩尔线程要看 vGPU 或 sGPU 的驱动隔离能力，不能把 MIG 的隔离强度直接套过来。

MIG 把一张卡分成带独立计算和显存的实例，互相干扰小，但档位固定，消费级卡没有。MPS、cGPU 一类多是软件限额，能限制显存配额，缓存和显存带宽仍然共用，一个进程异常也可能影响同卡的其他人。

摩尔线程的云原生方案用 vGPU、sGPU 做显存和算力隔离，整卡则由设备插件按卡上报。训练默认整卡或整机，共享切分更适合小推理。隔离行为跟驱动和调度器绑定，升级驱动可能改变切分结果，所以要放进测试过的版本矩阵。

驱动、内核、容器运行时和 MUSA 必须配套。容器里要挂上设备节点和库；缺运行时钩子时，Pod 能启动但看不到卡。不同型号分节点池，不在还有作业的节点上原地换驱动。

生态上的坑是算子和通信都要在真卡上回归。默认脚本仍是 CUDA 时，平台要提供设备选择和后端切换，而不是让每个业务自己改一遍。

### 9. 技术选型时面对 MUSA 新特性与稳定 CUDA 生态的取舍，考虑的维度有哪些

**参考答案**

**结论**：按正确性、性能、稳定性、生态和能不能退回来选。不用“新”或“成熟”一句话做决定。

第一看当前模型的算子、精度和通信是不是已经覆盖，而不是路线图上有。第二用目标模型测吞吐、时延或 MFU，不看标称算力。第三看驱动和 MCCL 的已知故障、连续运行时间，以及出问题后能不能定位。第四看框架、内核、监控和人员是不是都绑在 CUDA 上，换到 MUSA 要改多少。第五看同一份作业规格能不能回到 CUDA 池，供应或软件出问题时有没有退路。

决策做成小范围双跑：精度容差、相对 CUDA 的性能、连续稳定运行，三条有一条不过就停。先迁推理或离线批处理，再迁长时间训练。即使目标就是把负载迁到自己的软件栈上，也按这个顺序写进路线图，而不是口头鼓励尝试。

### 10. 最近在学的 AI Infra 相关新技术（如 Serverless 推理、异构调度、FP8 训练）

**答题思路**

只讲一个你真的读过实现或跑过实验的方向，按“它解决什么、你验证了什么、还没搞清什么”说。下面三个是素材，不要一次背完。

无服务器推理按请求扩容，空闲时可以缩到零。冷启动的大头是加载权重和初始化设备上下文，所以要有模型缓存和预热。长解码不适合频繁缩到零，突发的短请求更合适。隔离和按 token 计量要一起讲。

异构调度按显存、精度支持和互联能力区分资源，不按“有几张卡”调度。不同速度的卡不要放进同一个张量并行组，最慢的那张决定 step。

FP8 训练常见的做法，是前向用指数位较少的 E4M3、反向用范围更大的 E5M2，再用张量或分块缩放避免溢出。它省带宽，也加速大矩阵乘；首尾层经常仍用 BF16。这张卡有没有 FP8 硬件，以型号为准。没有就不要把它当成已经打开的加速开关。

收尾留一个你还没验证的点。没有动手过的方向，直接说还没做，不要讲成线上方案。

### 11. 你是怎么去接触一门新技术的，以 MUSA 开发或 RDMA 调优为例讲讲学习路径

**答题思路**

挑一条你真的走过的路径。没碰过 MUSA，就讲 RDMA，两条都没做过就不要拼经历。顺序是：

1. 先写成一个可验证的问题，例如集合通信带宽达不到线速，而不是“把 RDMA 学完”。MUSA 则收成“这个模型迁过去之后，loss 和单机带宽是否达标”。
2. 读原始材料。RDMA 看无损、PFC、ECN 各自管什么；MUSA 看官方运行时、musify 和 MCCL 说明。博客只用来找术语。
3. 做最小实验：两机 `all_reduce_perf`，或 musify 之后的一个小模型。记下版本、拓扑和命令。
4. 故意做一次对照，例如绑错网口，或确认没有走 MTLink。你能讲清指标怎么变，排障题就有例子。
5. 最后才看生产配置。把现象、证据、修改和回退写成一页。
6. 没跑过的步骤说成“我准备这样验证”，不要说成已经在集群里做过。

### 12. 会看哪些书或论文，如何筛选高质量的技术资料避免信息噪音

**答题思路**

报一个短名单，每篇都能讲出问题和结论。没读过的论文直接说没读，不要讲错。

1. 分布式训练可以讲 Megatron 的张量并行、ZeRO，以及 GPipe 或 1F1B。推理可以讲 FlashAttention 和 PagedAttention。只选你能推导通信量或显存的那几篇。
2. 系统侧用数据密集型应用里存储和一致性的相关章节。通信以 NCCL 或 MCCL 的官方说明为准，不用二手文章代替。
3. 硬件只补你要排障的部分，例如 PCIe 和 NUMA，不从体系结构课本第一页开始背。
4. 筛选时先看来源是不是论文、官方文档或代码，再看实验用的硬件代际还对不对。博客用来找关键词，结论回到原文。
5. 同一主题先吃透一篇，能自己写出公式，再看下一篇。没有实验设置、没有版本、把不同芯片的数字拼在一起的材料，不拿来当依据。

### 13. 如果让你给团队做一场关于摩尔线程 GPU 通信库 MCCL 优化的分享，你会怎么准备内容

**答题思路**

目标是让同事能按步骤查完一次带宽问题，不是介绍 MCCL 的定义。

1. 用你自己一周内跑过的实验，钉死驱动、MCCL 和节点型号。用 `all_reduce_perf` 给出单机和两机基线，写清总线带宽怎么从算法带宽换算。
2. 画这套集群的拓扑：MTLink、PCIe、哪几块是计算网卡。图用 `MCCL_TOPO_DUMP_FILE` 和 `mthreads-gmi` 的输出，不用 NVIDIA 的拓扑图代替。
3. 只讲一个完整案例：现象、`MCCL_DEBUG=INFO` 里看到的路径、根因、修改、前后带宽。数字只用这次实验的。
4. 留一张检查表：网口、NUMA、机内有没有走 MTLink、有没有退回 socket、容器有没有把 RDMA 设备挂进去。环境变量以现场这一版文档为准。
5. 留出大约三分之一的时间讨论。不要在唯一的生产队列上现场改配置。
6. 材料里写回退命令，以及什么时候停下来找管理员，例如要关 ACS 或改交换机。
