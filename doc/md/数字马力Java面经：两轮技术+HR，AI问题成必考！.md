### 3. ArrayList 和 LinkedList 有什么区别？ArrayList 的扩容机制是怎样的

**参考答案**

ArrayList 是连续数组，按下标访问是 O(1)；LinkedList 是双向链表，要先走到那个位置才能改。扩容只发生在 ArrayList。

ArrayList 的中间插入和删除要搬运后面的元素，是 O(n)，但内存连续，对 CPU 缓存友好。LinkedList 每个节点单独分配，带前驱和后继；已经拿到节点时改指针是 O(1)，可是 `get(i)` 和 `add(i)` 都要先遍历，平均 O(n)，实际往往比数组搬运更慢。它同时实现了双端队列，适合在头尾进出。两者都不是线程安全的。

无参构造时内部是空数组，第一次 `add` 才分配容量 10。之后空间不够，新容量按 `old + (old >> 1)` 计算，大约是 1.5 倍。一次 `addAll` 需要的长度比 1.5 倍还大，就直接扩到这次所需的长度。新容量超过 `Integer.MAX_VALUE - 8` 时会尝试分配到 `Integer.MAX_VALUE`；长度计算溢出才抛出 `OutOfMemoryError`。过程是申请新数组再拷贝。构造时如果显式传入初始容量 0，第一次只会扩到 1，不会跳到 10。

面试里容易把「LinkedList 插入一定更快」说死。通过下标插入时，先遍历到该位置的成本经常更高。扩容倍数也不要和 HashMap 的负载因子混在一起。

### 4. HashMap 的底层原理，扩容机制，key 有什么要求

**参考答案**

JDK 8 的 HashMap 是数组加链表，单个桶的链表过长才变成红黑树。它不是线程安全的。

第一次 `put` 才建表，默认容量 16，负载因子 0.75。桶下标是 `(n - 1) & hash`，容量保持 2 的幂，这样取模可以用位与。`hash` 会把 `hashCode` 的高 16 位异或进低位，避免只使用低位时都挤在少数桶里。

同一个桶里已经有 8 个节点、再插入时会尝试树化；表长度还不到 64 则先扩容，不树化。删除或扩容拆分后，树节点降到 6 会变回链表。允许一个 `null` key，哈希按 0 处理；value 可以有多个 `null`。JDK 8 用尾插，避免了 JDK 7 头插在并发扩容时形成环，但并发 `put` 仍然会丢数据。

元素个数超过「容量 × 负载因子」就扩容，容量翻倍。节点在新表里要么留在原下标，要么移到「原下标 + 旧容量」，看 hash 里对应旧容量的那一位。构造时传入的容量会向上取到 2 的幂。

key 必须满足：`equals` 相等则 `hashCode` 相等；参与哈希的字段插入后不能改，否则 `get` 找不到。key 最好不可变。不强制实现 `Comparable`，树化时没有比较顺序会退回到类型和身份哈希，只是这个顺序没有业务含义。

### 5. Java 的 I/O 流分为几种？各自的应用场景

**参考答案**

按数据单位分是字节流和字符流，按方向分是输入和输出，所以有四个抽象基类：`InputStream`、`OutputStream`、`Reader`、`Writer`。

按职责还可以分成节点流和处理流。节点流直接接触数据源，例如 `FileInputStream`、`ByteArrayInputStream`。处理流包装另一条流，补上缓冲、编码转换或对象编码，例如 `BufferedInputStream`、`InputStreamReader`、`ObjectInputStream`。

图片、音视频和网络上的原始字节用字节流。文本用字符流，并明确字符集。把字节流解释成文本用 `InputStreamReader`，读文件和解析网络协议时最常见。读写很频繁时再套缓冲流，减少系统调用。要把 Java 对象写出再读回，用对象流，并保证序列化兼容。

关闭最外层处理流时，它包装的节点流会一起关掉，所以用 try-with-resources。题目问的是 `java.io` 的流；NIO 的 Channel 不是流，被追问再讲非阻塞和 `Selector`。

### 6. 了解 Java 的双亲委派机制吗？类加载过程是怎样的

**参考答案**

类加载把字节码变成可用的 `Class`；双亲委派规定加载请求先交给上层类加载器，用来保住核心类不被替换，也避免同一个类被加载出两份。

过程分三步。加载：找到字节码，生成 `Class` 对象。链接：验证字节码；准备阶段给静态变量分配空间并置成 0 或 `null`，还不会执行 `static int a = 1` 这种赋值；解析把符号引用变成直接引用。初始化：执行 `<clinit>`，也就是静态赋值和静态代码块，父类先于子类。触发初始化的是主动使用，例如 `new`、调用静态方法、读写非常量静态字段、反射、初始化子类、启动 main 类。

`static final` 的基本类型或字符串常量会进常量池，使用它不一定导致类初始化。类加载器把字节码载入内存，也不等于已经执行了静态初始化。

委派顺序是应用类加载器交给平台类加载器，再交给启动类加载器。JDK 8 及以前，中间这一层叫扩展类加载器。上层加载不了，下层才自己加载，所以应用不能用自己的 jar 替换 `java.lang.String`。

JDBC 会打破这个顺序：接口由上层加载，驱动实现在应用 classpath 里，上层看不见，于是通过线程上下文类加载器去加载驱动。Tomcat 的 Web 应用类加载器会优先加载应用自己的类，避免和容器互相污染。只重写 `findClass` 仍然走委派；要改变顺序，需要重写 `loadClass`。

### 7. Spring 注入 Bean 的方式有几种？分别怎么使用

**参考答案**

日常依赖注入是三种：构造器注入、Setter 注入、字段注入。需要的依赖优先用构造器。

构造器注入在创建对象时就把依赖传入，字段可以是 `final`，缺依赖会在启动时失败。Spring 4.3 起，类只有一个构造器时可以不写 `@Autowired`。

```java
@Service
public class OrderService {
    private final PayClient payClient;

    public OrderService(PayClient payClient) {
        this.payClient = payClient;
    }
}
```

Setter 注入适合可选依赖，配合 `@Autowired(required = false)`。字段注入写起来短，但依赖不直观，单测也不好自己 new。`@Bean` 方法的参数同样是创建时注入。XML 里对应 `constructor-arg` 和 `property`，新代码用注解或 Java 配置即可。

`@Autowired` 默认按类型匹配；同一类型有多个 Bean 时，用 `@Qualifier` 或 `@Primary`，参数名也可以匹配同名 Bean。`@Resource` 先按名字再按类型。`ApplicationContextAware` 这类回调是容器把上下文交给你，不是业务依赖的常规注入方式。

### 8. MySQL 事务的隔离级别有哪些？分别解决什么问题

**参考答案**

标准隔离级别有四个，用来限制并发事务之间能看见多少中间状态。InnoDB 默认是可重复读。

三种现象先分开：脏读是读到别的事务还没提交、后来可能回滚的修改；不可重复读是同一事务里两次读同一行，已提交的值变了；幻读是同一范围两次查询，行集合变了，通常是别的事务插入或删除了行。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 READ UNCOMMITTED | 会发生 | 会发生 | 会发生 |
| 读已提交 READ COMMITTED | 避免 | 会发生 | 会发生 |
| 可重复读 REPEATABLE READ | 避免 | 避免 | InnoDB 下基本避免 |
| 串行化 SERIALIZABLE | 避免 | 避免 | 避免 |

InnoDB 的普通 `SELECT` 走 MVCC。读已提交每次语句新建一个读视图；可重复读在事务里第一次一致性读时建立读视图，之后复用，所以同一行和同一范围的快照结果保持不变。当前读（`SELECT ... FOR UPDATE`、`UPDATE`）读最新已提交版本并加锁。可重复读下用临键锁，也就是记录锁加间隙锁，挡住别人往这个范围插入，从而避免当前读的幻读。读已提交一般不加间隙锁，所以还有幻读。

串行化会把普通查询变成共享的加锁读，冲突最高。面试里要补上「标准 SQL 里可重复读并不承诺解决幻读，InnoDB 是靠 MVCC 和临键锁做到的」，不要说成所有数据库的可重复读都没有幻读。

### 9. Redis 的数据类型有哪些？在实际项目中你用过哪些

**参考答案**

常用的是 String、Hash、List、Set、ZSet。后来还有 Bitmap、HyperLogLog、Geospatial 和 Stream。

- String 可以是文本、数字或序列化后的对象，用来做缓存、计数，以及 `SET NX` 这样的原子占位。
- Hash 存一个对象的多个字段，适合局部更新，避免整段 JSON 反复读写。
- List 是双向链表，适合最新记录、头尾进出，不适合当成可靠消息队列。
- Set 做去重、标签和集合运算。
- ZSet 按分数排序，适合排行榜；分数存到期时间时也可以做延迟队列。
- Bitmap 适合按位记签到或是否活跃。HyperLogLog 用固定很小的内存估算基数，允许误差才用。GEO 是地理位置。Stream 带消费组，适合日志和简易的消费位点，可靠性要求高的主链路仍更常用 Kafka 一类消息队列。

被问到项目里用过哪些时，只讲两三个你真的设计过的：key 怎么组成、过期时间、缓存和数据库谁为准、更新失败怎么办。没用过的类型不要说成用过。上面的对应关系用来对照你的项目，不是一份可以照背的经历。

### 10. 场景题：假设有一个用户量级达上千万的系统，举办营销活动让用户抢同一个产品，如何保证该产品只能被一个人抢到

**参考答案**

名额只有 1，正确性靠一次原子占位，再加上数据库唯一约束把胜者留住。上千万用户不能都打到数据库上。

活动页静态化，开抢前按钮不可用。网关校验登录和活动时间，并按用户限流。占位使用 `SET claim:{productId} {userId} NX`：只有一个客户端能设置成功。失败后再读出 value，是自己就按幂等返回成功，是别人就返回已抢完。题面是抢到即确定，这个 key 不要设过期，否则过期后第二个人又能抢走。

胜出的请求再写数据库，`product_id` 建唯一索引，插入成功才算最终结果。Redis 成功但进程在写库前挂了，用对账按 Redis 里的 userId 补插入。Redis 重启后，重新放流量之前先用数据库里的胜者把 key 填回去。售罄结果可以放到本地内存，后续请求直接失败。

只靠数据库唯一索引也正确，但开抢瞬间的插入会把库打满。Redis 负责挡住并发，数据库负责留下不可变结果。所有请求进一条单消费者队列也能保证只有一个胜者，顺序好解释，但多一次排队，消费者一停活动就停。这里一次 `SET NX` 已经原子完成占位，再包一层分布式锁只会让所有人堵在同一把锁上。

如果业务后来改成「超时未支付就释放」，value 里要带持有者，释放时用 Lua 比较 userId 再删，避免删掉下一个人的占位。题面没有这个规则，就按抢到即确定来设计，最后说明这个差别。

### 11. 你在项目中使用过 AI 相关技术吗？比如 RAG 或 Agent

**答题思路**

先明确说用过还是没有，不要含糊。两种回答都要接得住追问。

没有上过生产：直接说没有，不要编一个智能客服或知识库项目。接着讲你自己跑过的最小例子：数据从哪来、怎么检索或怎么调工具、你怎么判断结果对不对。最后主动说一个还没处理的问题，例如权限、评测或答非所问。

用过：按这个顺序讲。

1. 业务问题是什么，为什么规则或直接提问解决不了。
2. 你负责的部分，和同事的边界。
3. 链路按下面的概念讲准确。
4. 效果怎么判断，出过什么错，你改了哪一环。

概念要说准。RAG 是先检索再生成：文档切块、向量化后写入索引，提问时取出相关片段放进提示词，让模型依据这些材料回答。它不更新模型参数。效果主要看切块是否合适、有没有检索到、回答是否扣住材料。Agent 是模型在循环里选择工具，运行时执行工具，再把结果交回模型，直到给出最终答案或达到步数上限。要能说出工具列表、停止条件和调用错了怎么处理。只写一段很长的提示词，还不能称为 Agent。

没做过的那个就不要说做过。两个里讲清一个即可。

### 12. 如果让你用 AI 辅助开发，你会怎么设计提示词让 AI 更好地理解需求

**参考答案**

提示词要写成给新同事的任务单：上下文、边界和验收都在，而不是只写「帮我实现这个需求」。

1. 背景写技术栈、要改的模块，以及相关的类、接口或表。贴关键代码，不要把整个仓库无差别地丢进去。
2. 目标和边界分开：要做成什么；不改对外协议、不加新中间件、不动无关文件。
3. 给例子：一条正常输入、一条边界输入，以及期望的返回或数据变化。
4. 把一致性写进约束：是否要幂等、事务包住哪些写操作、失败时返回什么。
5. 验收写清要补的测试，以及怎样算做完。
6. 先让模型复述理解和准备修改的文件，确认后再写代码。需求大就拆开，先定接口和测试，再写实现。

真实用户数据和密钥不能贴进外部模型。模型答偏时，把错的地方指回具体文件和期望行为，不要只说「不对，重写」。

### 13. 手写算法：反转链表

**参考答案**

用三个指针迭代：`prev` 一开始为空，`curr` 从头节点开始。每次先记下 `curr.next`，再把 `curr.next` 指向 `prev`，然后两个指针一起后移。循环结束时 `prev` 就是新的头节点。

空链表和只有一个节点时，循环不会改错，直接返回 `prev`。时间 O(n)，额外空间 O(1)。递归也能做，先走到尾部再逐层把 `next` 指回来，时间同样 O(n)，但栈深 O(n)。面试默认写迭代。

容易写错的是先改 `next`、把后面的节点弄丢，以及最后返回了原来的 `head`。

```java
class ListNode {
    int val;
    ListNode next;
    ListNode(int val) { this.val = val; }
}

class Solution {
    public ListNode reverseList(ListNode head) {
        ListNode prev = null;
        ListNode curr = head;
        while (curr != null) {
            ListNode next = curr.next;
            curr.next = prev;
            prev = curr;
            curr = next;
        }
        return prev;
    }
}
```

### 3. 项目中用到过哪些设计模式？单例模式初始化的时机是什么时候

**参考答案**

第一问只讲你仓库里真实有的 1 到 2 个。按「变化点是什么、模式固定了什么、代码在哪」来说。多种分支算法可以用策略，固定流程骨架可以用模板方法，一串前置校验可以用责任链，Spring 的事务和日志用的是代理。不要把「用了 Spring」直接说成「用了工厂模式」。没把握的模式不要讲；讲了单例，就准备好下面的时机问题。

单例对象何时被 `new` 出来，取决于写法。类被载入内存，不等于实例已经创建。

1. 饿汉式写成 `private static final Instance INSTANCE = new Instance();`，在类初始化时创建。类初始化由主动使用触发，例如第一次调用它的静态方法。线程安全来自 JVM 的类初始化锁。
2. 静态内部类：外部类初始化不会创建实例。第一次 `getInstance` 访问内部类的静态字段时，内部类才初始化。同样由类初始化锁保证只创建一次，所以它既是懒加载也是线程安全的。
3. 双重检查锁：第一个抢到锁的线程在 `getInstance` 里创建。引用要声明为 `volatile`，否则另一个线程可能读到还没构造完的对象。
4. 枚举：枚举类初始化时创建唯一实例，反射和序列化也不会再得到一个新对象。

懒加载省下的是「用不到就不创建」。实例很轻、而且这个类一旦用到就一定要实例时，饿汉式更直接。

### 4. MySQL 的 undo log 和 redo log 了解吗？它们的作用和区别

**参考答案**

redo 保证已提交的修改在崩溃后还在；undo 用来回滚未提交的事务，并给一致性读提供旧版本。两者一起才有持久性和原子性。

InnoDB 修改的是缓冲池里的页，同时生成 redo，记录这一页上的物理修改。脏页可以稍后刷盘；刷出去之前，覆盖这次修改的 redo 必须已经落盘，这就是预写日志。崩溃后重放已提交事务的 redo，页就能恢复。redo 循环使用，检查点推进之后，更早的日志才能丢。它不能用来把一次事务撤销掉。

undo 保存行的旧版本。事务回滚时按它把修改退回去。别的事务做一致性读时，如果当前行版本太新，就沿着 undo 找到自己的读视图能看见的版本。insert 产生的 undo 在事务提交后可以丢；update 产生的 undo 要等到没有读视图再需要它，由 purge 清理。undo 页也在缓冲池里，它的落盘同样靠 redo，不是提交时单独 fsync 一份回滚日志。

binlog 是 Server 层的日志，记录语句或行变更，用于复制和按时间点恢复，不要和 redo 当成同一个文件。崩溃恢复的顺序是：先用 redo 把页恢复到崩溃前，再用 undo 滚掉当时没有提交的事务。

### 5. MySQL 写日志是同步的还是异步的？具体流程是怎样的

**参考答案**

不能把 MySQL 的日志概括成「天生异步」或「天生同步」。事务进行中，redo 先写在内存里的 log buffer；提交时是否 fsync，由参数决定。

要保证已经返回成功的事务不丢，使用 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1`。现行主流版本这就是默认组合：每次提交都把 redo 和 binlog 刷到磁盘。代价是提交要等 fsync。

`innodb_flush_log_at_trx_commit=0` 时，提交不刷 redo，大约每秒由后台写一次，崩溃可能丢掉这一秒内已提交的事务。设为 2 时，提交只写到操作系统缓存，大约每秒才 fsync；进程崩溃一般还在，操作系统崩溃可能丢。`sync_binlog` 为 0 或大于 1 时，binlog 也不是每次提交都落盘。这是用一小段数据风险换吞吐。

开了 binlog 时，一次提交按这个顺序走：

1. 事务执行中改缓冲池里的页，undo 记下旧版本，redo 追加到 log buffer。脏页先留在内存。
2. 提交时 InnoDB 先写 prepare，并按上面的参数决定 redo 是否 fsync。
3. 写 binlog，并按 `sync_binlog` 决定是否 fsync。多个事务可以组提交，把多次 fsync 合成一次。
4. InnoDB 再在 redo 里记 commit。如果 binlog 已经落盘，而进程在这一步之前崩溃，恢复时会提交这个准备好的事务，因为 binlog 里已经有它。

数据页由后台线程另走一条异步刷盘路径，不在提交时写入。提交成功表示日志已经按参数落到了相应位置，不表示数据页当时已经在磁盘上。

### 6. Kafka 的使用场景是什么？有没有遇到过消息积压的情况

**参考答案**

Kafka 适合异步解耦、削峰和事件流：下单成功后通知积分、短信，主链路不用等；秒杀请求先进入队列，下游按自己的能力消费；用户行为和数据管道也可以按日志来接。它不适合替代需要立刻返回结果的查询。

积压指消费位移持续落后于日志末端。处理时先看是哪个分区的 lag 在涨、消费耗时花在哪里，不要先扩容。常见原因是慢 SQL、同步调用外部系统、消费者挂了、分区热点，或流量突然变大。

消费者数量超过分区数后，同一个消费组的并行度不会再提高。增加分区主要影响新消息的分布，已经写在旧分区里的消息不会因此被拆开。能优化消费逻辑或把非关键步骤再异步出去时，优先这么做。入口也可以限流，让生产速度降下来。业务允许时，过期消息可以降级。积压恢复后仍会有重复投递，消费逻辑必须按业务键幂等。

有没有遇到过，只讲真实经历：当时 lag 大概到什么量级、原因是什么、你做了哪一步、之后 lag 怎么下来。没遇到就直接说没有，再把上面的判断顺序讲出来，不要编一条故障。

### 7. Redis 缓存击穿、缓存穿透、缓存雪崩分别是什么？如何解决

**参考答案**

三个词对应三种不同的打法，解法不能互换。

缓存穿透：查询的数据本来就不存在，缓存永远不命中，请求一次次打到数据库。随机 id 刷接口就是这种。入口先校验 id。布隆过滤器能挡住「一定不存在」的 key；它可能把存在误判成存在，所以放行之后仍要查库，而且标准布隆过滤器不好删除。确认没有的结果可以缓存一个短 TTL 的空值，同时要限制空值数量，避免随机 key 把内存打满。

缓存击穿：热点 key 正好过期，大量请求同时回源。可以用互斥锁只放一个请求回源，其他请求等待或重试，锁必须有超时。也可以逻辑过期：缓存不设硬 TTL，值里带过期时间，发现过期就异步刷新，当前请求先返回旧值，代价是短暂的旧数据。特别热的 key 可以不设过期，由任务主动更新。

缓存雪崩：大批 key 在同一时刻过期，或者 Redis 整体不可用，数据库被大面积打到。写入时给 TTL 加随机偏移。Redis 用哨兵或集群，避免单机宕掉后全部没有缓存。缓存或数据库异常时要限流、降级，返回兜底结果，而不是让所有请求无限重试打到数据库。

互斥锁只解决热点 key 过期。它挡不住根本不存在的穿透，也挡不住 Redis 进程挂掉。

### 8. 设计一个秒杀系统，需要考虑哪些问题，会用哪些技术栈

**参考答案**

秒杀要同时处理瞬时流量、超卖、重复下单，以及库存扣了但订单没创建。链路是：静态页放到 CDN，网关做鉴权和限流，秒杀接口用 Redis 预减库存，成功的请求进入消息队列，订单服务按自己的速度消费并写数据库，用户轮询结果。

库存预减放在一段 Lua 里：库存小于等于 0 就失败，否则 `DECR` 并返回成功。Redis 执行 Lua 时不会插入别的命令。数据库再执行 `update stock set stock = stock - 1 where sku_id = ? and stock >= 1`，影响行数为 0 就失败，并按这条失败把 Redis 补回去。用户和活动做唯一约束，Redis 里也用 `SET NX` 挡住连点。

预减成功但消息丢了，会出现库存被占、订单不存在。消息用事务消息或本地消息表，再加对账把预减记录和订单对齐。超时未支付要归还库存，归还必须带订单号做幂等。售罄标记放到应用本地内存，后面的请求直接拒绝。验证码、开抢令牌、账号和设备限频用来打散黄牛流量。

技术栈按这条链路选择：CDN、网关限流、Redis、Kafka 或 RocketMQ、MySQL。单个商品的库存行是热点，分库分表解决不了这一行的争用；先用预减和队列把写数据库的速度削平。直接每次都扣数据库更一致，但扛不住开抢瞬间的流量。

### 9. 如果现在参与到一个新项目，分到任务后你会先做哪些事情

**参考答案**

先确认完成标准和这段逻辑在系统里的位置，再改代码。

### 10. 接口文档的目的是什么？你觉得好的接口文档应该包含什么

**参考答案**

### 12. 你觉得用 AI 写前端代码和用 AI 写后端代码有什么区别

**参考答案**

前端生成结果可以在页面上立刻看出来；后端生成结果经常能编译、原有测试也能过，但事务、并发和数据仍然可能是错的。

前端模型容易拼出看起来像样的界面，薄弱的是状态切换、空数据、异常提示、权限按钮、不同宽度下的布局，以及和现有组件库是否一致。验收要把主路径和这些状态在页面里点一遍，一张静态截图说明不了交互是对的。提示词里要给界面状态和组件约定。

后端模型容易给出能跑的增删改查，但可能把事务范围划错、漏掉幂等、写出不走索引的 SQL、把异常吃掉，或者只在页面上做了鉴权。验收要先有不变量，例如库存不能为负、同一个请求重复提交只生效一次，再用测试和 diff 核对。改表时还要看执行计划，以及迁移失败能不能收回。提示词里要给表现有结构、接口约定、一致性要求和失败时的行为。

两边都不能把「能跑起来」当成「做对了」。

### 13. 如何校验 AI 生成结果的准确性？在项目中如何应用

**参考答案**

准确性靠事先写好的验收和事后核对，不靠模型自己说已经完成。

生成代码时：

1. 先写不变量、输入输出例子，以及这次不允许改的部分。
2. 编译和原有测试只是底线。针对这次改动补空值、重复提交、并发和无权限。
3. 读 diff，重点看事务边界、幂等键、SQL 条件、异常有没有被吞、有没有改到无关模块。
4. 外部 API 以项目锁定的库版本为准。方法不存在或编译不过，就按幻觉处理。
5. 项目里小步提交，CI 必须通过。评审标准不因为代码是 AI 写的就放宽。密钥和真实用户数据不放进外部模型。

生成的是回答或业务结论时，另外准备一组标准问题和要点，检查结论能不能在检索到的材料里找到依据，并留下请求和引用来源。人工抽检。模型给自己打的分不能当成准确率。

### 14. 手写算法：括号生成（Generate Parentheses）

**参考答案**

给定 n，生成全部由 n 对括号组成的合法字符串。例如 n = 2，结果是 `(())` 和 `()()`。合法的含义是：任意前缀里右括号不多于左括号，并且最终两种括号数量都是 n。

用回溯。路径上左括号数量小于 n 时可以放 `(`；右括号数量小于左括号数量时可以放 `)`。长度达到 `2n` 就收集一个结果。放完要撤销最后一个字符，才能尝试另一种选择。这个剪枝直接避免了先生成全部排列再过滤。

结果个数是第 n 个卡特兰数，时间复杂度约为 O(4^n / √n)。递归深度 O(n)。所有结果字符串还要单独占用空间。n 一般很小，因为组合数涨得很快；常见约束是 1 ≤ n ≤ 8。

```java
import java.util.ArrayList;
import java.util.List;

public class GenerateParenthesis {
    public List<String> generateParenthesis(int n) {
        List<String> result = new ArrayList<>();
        backtrack(n, 0, 0, new StringBuilder(), result);
        return result;
    }

    private void backtrack(int n, int open, int close, StringBuilder path, List<String> result) {
        if (path.length() == n * 2) {
            result.add(path.toString());
            return;
        }
        if (open < n) {
            path.append('(');
            backtrack(n, open + 1, close, path, result);
            path.deleteCharAt(path.length() - 1);
        }
        if (close < open) {
            path.append(')');
            backtrack(n, open, close + 1, path, result);
            path.deleteCharAt(path.length() - 1);
        }
    }
}
```

**答题思路**

面试前自己算清两件事：现在的总包，以及你能接受的下限。现场给一个区间，并说明这个区间指的是税前月薪还是年包。问清固定工资、绩效和城市补贴怎么构成。

这里不代你填任何数字。对方要求先报价时，说你算过的那个区间，不要当场改口抬高或砍半。对方的级别和你假设的不一致时，先问级别，再调整区间。

不要用「按公司规定就行」结束，也不要说出同事或上家同事的具体包。

### 7. 你还有什么问题想问我的

**答题思路**

准备两个具体问题，不要问「公司氛围怎么样」。

1. 这个岗位前三个月最主要的交付是什么，做的是固定业务还是支援多个项目。
2. 需求从评审到上线的节奏，线上问题由谁值班。
3. 团队现在最希望这次招聘补上的能力是什么。
4. 后面还有几轮，大概什么时候有结果。

上一题如果没问清薪资构成，可以在最后补一句。不要打听面试官个人收入，也不要问自己这一面有没有通过。
