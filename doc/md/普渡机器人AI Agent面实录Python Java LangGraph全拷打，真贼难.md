### 3. Python中GIL的原理是什么，对CPU密集型和IO密集型任务分别有什么影响

**参考答案**

GIL（全局解释器锁）是 CPython 解释器里的一把互斥锁，保证同一时刻只有一个线程在执行 Python 字节码。

- **为什么需要**：CPython 的内存管理靠引用计数，引用计数的增减不是线程安全的，用一把全局锁比给每个对象加锁简单且单线程更快。
- **切换机制**：持有 GIL 的线程在执行一定时间（默认切换间隔 5ms，可用 `sys.setswitchinterval` 调整）后会被请求释放；遇到阻塞 IO（读写文件、网络、`time.sleep`）时主动释放 GIL。
- **CPU 密集型**：多线程无法并行利用多核，甚至因为线程切换和锁竞争比单线程更慢。解决：`multiprocessing` / `ProcessPoolExecutor`、把热点放到会释放 GIL 的 C 扩展（NumPy 等）、用 Cython / Rust 扩展。
- **IO 密集型**：线程等待 IO 时会释放 GIL，多线程或 `asyncio` 都能有效提升吞吐。

容易漏掉的点：GIL 只保护解释器内部状态，不保证用户代码原子性，`count += 1` 这类复合操作仍需 `threading.Lock`；Python 3.13 起提供实验性的 free-threaded（无 GIL）构建（PEP 703），但不是默认。

### 4. Java的JVM内存模型及垃圾回收器G1的工作流程

**参考答案**

先澄清概念：这里说的“JVM 内存模型”通常指**运行时数据区**；另有 **JMM（Java 内存模型）**，是关于可见性、有序性的 happens-before 规范，两者不要混淆，答题时可以都点一下。

**运行时数据区**：
- 线程共享：**堆**（对象实例，分新生代 Eden / Survivor 与老年代）、**方法区**（JDK 8+ 由元空间 Metaspace 实现，使用本地内存）。
- 线程私有：**虚拟机栈**（栈帧：局部变量表、操作数栈等）、**本地方法栈**、**程序计数器**。
- 另有直接内存（NIO 的 DirectByteBuffer）。

**G1（Garbage-First，JDK 9 起为默认收集器）**：
- 把堆划分为大小相等的多个 Region，每个 Region 动态扮演 Eden / Survivor / Old / Humongous（大对象，大小超过 Region 一半）角色。
- **Young GC**：Eden 满触发，STW，采用复制算法，把存活对象复制到 Survivor 或晋升到 Old。
- **并发标记周期**（堆占用达到 IHOP 阈值触发）：初始标记（STW，借 Young GC 完成）→ 根区域扫描 → 并发标记 → 最终标记（STW，处理 SATB 记录的变更）→ 清理（统计各 Region 存活情况，回收完全空闲的 Region）。
- **Mixed GC**：根据标记结果，优先选择垃圾最多（回收收益最高）的 Old Region，连同 Young Region 一起回收，在 `MaxGCPauseMillis`（默认 200ms，是目标不是保证）内尽量多收。
- 若回收速度跟不上分配速度，会退化为 Full GC。

### 5. 场景题：在普渡机器人场景下，用户语音输入存在噪音且语义模糊，如何设计意图识别流程来做多层兜底与澄清

**参考答案**

结论：用“**前端降噪 → 多级识别 → 置信度分流 → 澄清 / 兜底**”的分层流程，不把所有压力交给一次 LLM 调用。

1. **语音与文本预处理**：设备端降噪、VAD 断句、麦克风阵列定向；ASR 输出保留置信度和 N-best 候选，对热词（点位名、菜品名）做增强，用拼音相似度修正同音错字。
2. **第一层：规则与热词快速路径**：高频明确指令（“带我去 3 号桌”“停止”）用关键词 / 正则 / 槽位匹配直接命中，低延迟、可预期。
3. **第二层：小模型或向量分类**：意图分类器 / Embedding 相似度，输出意图和置信度。
4. **第三层：LLM 理解与槽位抽取**：处理复杂、口语化、多意图输入，结合对话历史、机器人当前状态（位置、任务、电量）做消歧，输出结构化 JSON。
5. **置信度分流**：
   - 高置信：直接执行（涉及移动、开门等物理动作的意图，必要时做一次轻确认）。
   - 中置信：澄清确认，如“您是想去 3 号桌吗？”。
   - 低置信：给出选项式提问或引导；连续 2～3 轮仍不清楚，转人工或走 FAQ 兜底。
6. **兜底与安全**：高风险动作必须确认；有明确的“听不清请再说一次”话术；澄清轮数设上限，避免死循环。
7. **闭环**：记录误识别、澄清触发和转人工样本，回流到词表、规则和评测集。

### 6. LangChain中Agent与Chain的核心区别，为什么复杂工作流要用Agent

**参考答案**

**核心区别：控制流由谁决定。**

- **Chain**：步骤和顺序由开发者预先写死（Prompt → LLM → Parser，或固定的检索 → 生成），执行路径确定、可预测、延迟和成本稳定。
- **Agent**：由 LLM 在运行时根据当前观察决定下一步——调用哪个工具、传什么参数、是否继续或结束，形成“思考 → 行动 → 观察”的循环（ReAct / tool calling）。

**复杂工作流为什么用 Agent**：步骤数和路径事先不确定（要不要检索、调哪个工具、失败后换方案）、需要根据中间结果动态分支、需要多工具组合、需要自我纠错。

**要补充的取舍**：Agent 带来非确定性、更高延迟与 token 成本、更难测试。工程上的做法是：确定的部分仍用 Chain / 固定节点，不确定的部分才交给 Agent；复杂场景用 LangGraph 这类图编排，把循环、分支、状态、人工介入和最大步数显式化，而不是完全放任 LLM 自由循环。

### 7. RAG系统中文档切分Chunk大小如何选择，切太大和切太小分别会引发什么问题

**参考答案**

**结论：没有通用最优值，要结合文档类型、Embedding 模型的最大输入长度和问题类型，在评测集上调。** 常见起点是几百 token（约 300～800）、10%～20% 重叠，再用 Recall@k、答案准确率验证。

- **切太大**：一个 chunk 里混入多个主题，向量表示被稀释，检索精度下降；召回后塞入大量无关内容，浪费上下文、增加成本和延迟，还可能触发“中间信息被忽略”；可能超过 Embedding 模型长度限制被截断。
- **切太小**：语义被拆碎，丢失上下文（指代、前提条件、表格表头）；答案跨多个 chunk，需要多召回才能拼全；chunk 数量暴涨，索引和检索成本上升。

**优化做法**：按文档结构切分（标题、段落、表格、代码块）而不是机械按字数；加适度重叠；父子块策略（小块检索、返回所在大块 / 父块）；给 chunk 附加标题路径、文档名等元数据；不同类型文档用不同策略。

### 8. 使用Elasticsearch做向量检索时，HNSW算法的原理及参数ef_search、m对性能和精度的权衡

**参考答案**

**HNSW（Hierarchical Navigable Small World）** 是分层的近邻图索引，近似于“跳表 + 小世界图”。

- **结构**：多层图，越往上节点越稀疏（节点层数按指数衰减的概率随机分配），最底层包含全部向量。
- **查询**：从顶层入口点开始贪心找到离查询最近的节点，下沉到下一层继续；到最底层时用大小为 `ef` 的候选队列做 beam search，返回最近的 k 个。
- **插入**：随机确定节点层数，逐层搜索近邻，并与其中最近的若干个建立连接（受 `m` 限制）。

**参数权衡**：
- **m**（每个节点的最大连接数，ES 中为索引映射参数 `m`，默认 16）：越大图越稠密，召回率越高，但内存占用更大、构建更慢、查询每跳要算的距离更多。
- **ef_construction**（建索引时的候选队列大小，ES 默认 100）：越大图质量越好、构建越慢。
- **ef_search**（查询时候选队列大小）：越大召回越高、延迟越高，且必须不小于 k。

**要点出的细节**：ES 的 kNN 查询里没有叫 `ef_search` 的参数，对应作用的是查询参数 `num_candidates`（每个分片的候选数量）；`ef_search` 是 FAISS、OpenSearch 等的叫法。另外，ES 的 HNSW 图是按 Lucene segment 构建的，查询要搜索每个 segment 的图再合并，segment 合并会带来额外开销；新版本支持向量量化以降低内存。

### 9. Redis在AI工作流中一般用来存什么，如何用Redis实现Agent的短期对话记忆

**参考答案**

**常见用途**：
- 会话短期记忆（最近 N 轮对话、会话摘要）。
- LLM 响应缓存、语义缓存、Embedding 缓存。
- 限流与配额（按用户 / 租户的令牌或调用次数）。
- 分布式锁、幂等键（防止同一任务被重复执行）。
- 任务队列 / Stream、状态检查点、流式输出的 Pub/Sub。

**短期对话记忆的实现**：
1. 每个会话一个 key，如 `chat:{session_id}`，用 **List** 保存消息 JSON：`RPUSH` 追加，`LTRIM` 保留最近 N 条。
2. 设置 TTL（`EXPIRE`），每次访问续期，会话结束自动清理。
3. 读取时 `LRANGE` 取出，再按 token 预算做截断；超出窗口的旧消息用摘要替换，摘要存另一个 key（如 Hash 字段）。
4. 追加 + 裁剪 + 续期用 Pipeline 或 Lua 脚本，保证原子性。
5. 需要消息级元数据（角色、时间、tool 调用）时可用 Stream。

```python
import json, redis

r = redis.Redis()

def append_message(session_id: str, role: str, content: str, max_len: int = 20, ttl: int = 3600):
    key = f"chat:{session_id}"
    pipe = r.pipeline()
    pipe.rpush(key, json.dumps({"role": role, "content": content}, ensure_ascii=False))
    pipe.ltrim(key, -max_len, -1)
    pipe.expire(key, ttl)
    pipe.execute()

def load_messages(session_id: str):
    return [json.loads(x) for x in r.lrange(f"chat:{session_id}", 0, -1)]
```

注意：Redis 是内存存储，只放短期热数据；需要长期保留或审计的对话要异步落库。

### 10. 场景题：Agent调用外部工具超时或返回异常JSON，如何在工程层面做重试、熔断与降级

**参考答案**

**结论：超时控制 + 有限重试 + 输出校验 + 熔断隔离 + 分级降级，各层各管一件事。**

1. **超时**：设置连接超时、读取超时和整体 deadline，避免 Agent 被一个慢工具拖死；整条链路的总预算要大于各步之和。
2. **重试**：只对幂等或可安全重试的调用重试（查询类）；使用指数退避加抖动，限制最大次数，并设置重试预算，防止放大下游压力。写操作必须带幂等键，否则不能盲目重试。
3. **异常 JSON 处理**：用 Schema（Pydantic / JSON Schema）校验返回；校验失败先尝试轻量修复（去掉多余文本、补全括号），再把错误信息反馈给 LLM 让其修正，限定次数；返回格式不稳定的工具在适配层统一转换。
4. **熔断**：对每个工具按失败率或慢调用比例统计，达到阈值进入 Open 状态直接快速失败，一段时间后半开探测恢复（Resilience4j、pybreaker 等）；配合舱壁隔离（每个工具独立线程池或并发上限）。
5. **降级**：返回缓存结果；切换备用工具或备用数据源；让 LLM 在明确说明限制的前提下基于已有信息回答；告知用户稍后重试或转人工。
6. **可观测**：记录每次调用的耗时、错误类型、重试次数、熔断状态，并设置告警。

### 11. MySQL在存储Agent执行轨迹时，如何设计表结构及索引来支撑高频写入与按session查询

**参考答案**

**结论：会话表 + 追加写入的步骤表，用自增主键保持顺序写入，以 `(session_id, step_no)` 联合索引支撑按会话查询，大字段拆出或外置。**

```sql
CREATE TABLE agent_session (
  session_id   VARCHAR(64) PRIMARY KEY,
  user_id      VARCHAR(64) NOT NULL,
  status       TINYINT NOT NULL,
  created_at   DATETIME(3) NOT NULL,
  KEY idx_user_time (user_id, created_at)
);

CREATE TABLE agent_step (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  session_id   VARCHAR(64) NOT NULL,
  step_no      INT NOT NULL,
  step_type    VARCHAR(32) NOT NULL,   -- llm / tool / retrieval ...
  node_name    VARCHAR(64),
  status       TINYINT NOT NULL,
  latency_ms   INT,
  token_in     INT,
  token_out    INT,
  payload_id   BIGINT,                 -- 指向大字段表，或存对象存储地址
  created_at   DATETIME(3) NOT NULL,
  UNIQUE KEY uk_session_step (session_id, step_no)
);
```

要点：
- **自增主键**：InnoDB 聚簇索引顺序追加，避免随机主键（如 UUID）导致页分裂。
- **索引精简**：写入量大时索引越多越慢，只保留 `(session_id, step_no)` 和必要的时间索引；按会话查询走联合索引，已按 `step_no` 有序，无需 filesort。
- **大字段**：prompt、响应、工具入出参体积大，拆到单独表（或对象存储 / ES），热表只放元数据和摘要。
- **写入优化**：应用端批量插入，或经消息队列异步批量落库；视可靠性要求调整 `innodb_flush_log_at_trx_commit` 与 `sync_binlog`。
- **容量治理**：按时间分区或分表，冷数据归档，设置保留期。

### 12. 手撕算法：用Python实现一个带优先级的最近最少使用缓存LRUCache，支持get和put，时间复杂度O(1)

**参考答案**

**思路**：题意需要先确认。常见定义是：淘汰时优先淘汰**优先级最低**的元素，同优先级内淘汰**最近最少使用**的。

- 一个 `dict` 记录 `key → priority`。
- 每个优先级一个 `OrderedDict`（底层是哈希加双向链表），`move_to_end` 与 `popitem(last=False)` 都是 O(1)。
- 假设优先级是有限的几个等级（K 个，K 为常数）：淘汰时从低到高找第一个非空桶，复杂度 O(K)，即 O(1)。如果优先级是任意整数，则需额外用最小堆维护非空优先级，淘汰为 O(log P)，应在面试时说明这一点。

复杂度：`get`、`put` 均为 O(1)，空间 O(capacity)。

```python
from collections import OrderedDict


class PriorityLRUCache:
    def __init__(self, capacity: int, levels: int = 3):
        self.cap = capacity
        self.buckets = [OrderedDict() for _ in range(levels)]  # 下标越小优先级越低
        self.prio = {}  # key -> priority

    def get(self, key):
        if key not in self.prio:
            return -1
        bucket = self.buckets[self.prio[key]]
        bucket.move_to_end(key)          # 标记为最近使用
        return bucket[key]

    def put(self, key, value, priority: int = 0) -> None:
        if self.cap <= 0:
            return
        if key in self.prio:             # 更新：先从旧桶移除（优先级可能变化）
            del self.buckets[self.prio[key]][key]
        elif len(self.prio) >= self.cap:
            self._evict()
        self.buckets[priority][key] = value
        self.prio[key] = priority

    def _evict(self) -> None:
        for bucket in self.buckets:      # 从最低优先级开始
            if bucket:
                k, _ = bucket.popitem(last=False)   # 桶内最久未使用
                del self.prio[k]
                return
```

   - Supervisor、Swarm 等多 Agent 模式的封装，以及对 MCP 的集成。
3. **落点**：说明哪些你已经用在项目里、哪些评估后没引入以及原因，体现你的判断而非追新。

### 14. 让谈一下对Harness工程的理解，Agent等于Model加Harness这句话你怎么看

**参考答案**

**结论：Harness 是模型之外所有让 Agent 可靠、可控、可用的工程基础设施；“Agent = Model + Harness”基本成立，模型提供智能，Harness 决定这份智能能否稳定落地。**

**Harness 包含什么**：
- 循环与编排：Agent loop、状态管理、终止条件。
- 工具层：工具定义、调用、权限、结果处理。
- 上下文工程：Prompt 组装、记忆、压缩、检索。
- 安全与约束：沙箱、权限、输入输出校验、护栏。
- 可靠性：重试、超时、熔断、人工介入。
- 观测与评测：Trace、日志、自动评测、BadCase 回流。
- 成本与限流管控。

**怎么看这句话**：
- 同一个模型，换不同的 Harness，表现差异可以很大，因此工程决定 Agent 的可靠性下限，模型决定能力上限。
- 但不应理解成“模型不重要”，模型能力不足时 Harness 无法弥补。
- 随着模型变强，Harness 里补偿模型缺陷的部分（过度的提示约束、过细的流程）应随之精简，而安全、权限、观测、评测这类部分始终需要。
- 它与 Prompt 工程、上下文工程是包含关系：后两者是 Harness 的一部分。

### 15. 场景题：现在一个AI工作流需要串联RAG检索、工具调用、LLM生成三步，如何用Python异步编程提升端到端吞吐

**参考答案**

**结论：先分析依赖关系，让无依赖的 IO 并发起来；全链路使用异步客户端；别阻塞事件循环；对并发度和超时做限制；生成阶段流式输出。**

1. **拆依赖**：三步有数据依赖时只能串行，但步骤内部和无依赖的部分可以并发，如“向量检索 + 关键词检索 + 用户画像查询”并行，多个互不依赖的工具调用并行；LLM 生成必须等前置结果。
2. **异步 IO**：使用 `httpx.AsyncClient`、异步的 ES / Redis / 数据库客户端，复用连接池；用 `asyncio.gather` 或 `TaskGroup`（3.11+）并发。
3. **不阻塞事件循环**：同步库或 CPU 密集操作用 `asyncio.to_thread` / `run_in_executor` 或进程池；CPU 密集的部分（如 Embedding 本地推理）靠多进程或独立服务。
4. **限流与超时**：`asyncio.Semaphore` 限制对下游的并发；每一步 `asyncio.wait_for` 设超时；单个子任务失败时有降级，不拖垮整体。
5. **吞吐优化**：LLM 流式返回降低首字延迟；检索结果、Embedding、工具结果加缓存；批量请求合并；多 worker 部署以利用多核。

```python
import asyncio

async def handle(query: str):
    async with asyncio.timeout(30):   # Python 3.11+
        async with asyncio.TaskGroup() as tg:
            t_vec = tg.create_task(vector_search(query))
            t_kw = tg.create_task(keyword_search(query))
            t_tool = tg.create_task(call_tool(query))
        docs = merge(t_vec.result(), t_kw.result())
        async for token in llm_stream(query, docs, t_tool.result()):
            yield token
```

### 3. LangGraph中StateGraph的状态管理机制，Node、Edge、ConditionalEdge在生产级多Agent编排中怎么设计循环与分支

**参考答案**

**结论：LangGraph 把工作流建模成“共享状态 + 节点函数 + 边”的图，节点返回对状态的增量更新，由 reducer 合并；循环与分支通过条件边回指实现，并用限步和检查点保证生产可控。**

- **State**：用 `TypedDict` 或 Pydantic 定义 schema；每个字段可指定 reducer（如 `Annotated[list, add_messages]` 追加消息，没有 reducer 则覆盖）。
- **Node**：接收当前 state，返回部分更新，不直接改状态；可以是 LLM 调用、工具、子图。
- **Edge**：固定的下一跳。**ConditionalEdge**：路由函数读取 state 返回下一个节点名，用于分支。
- **执行模型**：基于 Pregel 式的 super-step，同一步内可并行的节点并发执行，再统一合并状态。
- **持久化**：编译时挂 Checkpointer（SQLite / Postgres 等），按 `thread_id` 保存每步状态，支持断点恢复、人工介入（`interrupt`）、时间回溯。

**生产设计要点**：
- **循环**：如“Agent → 工具 → Agent”，条件边判断是否还有 tool call，没有则结束；状态里记录步数、重试次数，并设置 `recursion_limit`（默认 25）和业务级最大步数，防止死循环。
- **分支**：路由依据 state 里的结构化字段（意图、置信度、错误计数），而不是让 LLM 自由输出节点名；加兜底分支。
- **状态瘦身**：只放必要字段，大对象存外部引用。
- **节点幂等**：恢复重放时副作用不能重复。
- **多 Agent**：每个 Agent 做成子图，用清晰的输入输出 schema 隔离状态；独立并行任务用 `Send` 做动态扇出。

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]
    steps: int

def route(state: State) -> str:
    last = state["messages"][-1]
    if state["steps"] >= 8:
        return "finish"
    return "tools" if getattr(last, "tool_calls", None) else "finish"

g = StateGraph(State)
g.add_node("agent", agent_node)
g.add_node("tools", tool_node)
g.set_entry_point("agent")
g.add_conditional_edges("agent", route, {"tools": "tools", "finish": END})
g.add_edge("tools", "agent")      # 回到 agent，形成循环
app = g.compile(checkpointer=checkpointer)
```

### 4. 多Agent系统里Supervisor模式和PeerToPeer模式各适合什么场景，Agent之间出现结果冲突怎么仲裁

**参考答案**

**Supervisor（中心调度）**：一个主管 Agent 负责拆解任务、分派给专业 Agent、汇总结果。
- 适合：任务可明确拆分、需要统一控制流程、审计与权限管理的场景，如客服分流、报告生成。
- 优点：流程可控、便于观测与限步；缺点：主管成为瓶颈与单点，多一层 LLM 调用，增加延迟与 token 成本。

**Peer-to-Peer（对等 / 交接 handoff / Swarm）**：Agent 之间直接移交控制权，没有中心。
- 适合：对话流程灵活、由当前专家决定下一个接手者（如转接售后、技术支持），或需要多角色讨论的开放式任务。
- 缺点：全局状态难掌控，容易互相踢皮球或循环，调试困难，需要明确的交接协议和限制。

实践中常用**层级式**混合：顶层 Supervisor，下层小组内允许直接 handoff。

**冲突仲裁**：
1. **以权威来源裁决**：事实类结论以数据库、工具、知识库等可验证的数据为准，而非 Agent 的自信。
2. **结构化输出**：要求每个 Agent 输出结论 + 证据 + 置信度，便于比较。
3. **规则 / 优先级**：按领域权威设定优先级（如政策 Agent 在条款问题上优先）。
4. **投票或交叉验证**：独立多个 Agent 结果多数一致才采用（注意它们可能共享同样的偏差）。
5. **Judge / Critic Agent**：基于证据裁决，并保留判定理由。
6. **升级人工**：高风险或无法裁决时转人工，同时记录以回流评测集。

### 5. 意图识别路由层如何设计可扩展架构，支持动态注册新Agent且不改核心分发逻辑，弱意图和多意图怎么处理

**参考答案**

**结论：把“有哪些 Agent”做成数据（注册中心），路由逻辑只依赖统一接口和元数据，用“召回 + 精选”两阶段做选择。**

**可扩展架构**：
1. **Agent 注册中心**：每个 Agent 声明元数据——名称、能力描述、示例话术、输入输出 Schema、优先级、版本、状态；存配置中心 / 数据库，支持热加载与灰度开关。
2. **统一接口**：所有 Agent 实现同一协议（如 `handle(request) -> response`），核心分发器只做“选择 + 调用”，不含 `if/else` 业务判断。
3. **两阶段路由**：先用规则 / Embedding 对 Agent 描述与示例做召回（top-k），再由分类器或 LLM 在候选中精选。Agent 增多时不会让 Prompt 无限膨胀。
4. **新 Agent 上线**：注册元数据 → 为它补充示例与评测集 → 灰度 → 观察误路由率。

```python
class AgentRegistry:
    def __init__(self):
        self._agents = {}

    def register(self, name, desc, examples, handler, priority=0):
        self._agents[name] = {"desc": desc, "examples": examples,
                              "handler": handler, "priority": priority}

    def candidates(self, query, top_k=3):
        # 基于 Embedding 召回候选，具体实现略
        ...

    def dispatch(self, query):
        cands = self.candidates(query)
        name, conf = select(query, cands)       # 分类器或 LLM 精选
        return self._agents[name]["handler"](query) if conf >= 0.6 else None
```

**弱意图**：置信度低时不硬路由，先结合上下文补全；仍不确定则向用户澄清（给选项），或走通用对话 / FAQ 兜底，并记录样本用于补充示例。

**多意图**：先做意图拆分，识别子意图及依赖关系；无依赖的并行执行，有依赖的按序执行；最后统一汇总回复。子意图中有不确定的，只对该部分澄清。

### 6. RAG高级优化：Hybrid Search混合检索、Rerank重排序、Query改写在你的项目里是怎么落地的，效果提升多少

**参考答案**

**结论：混合检索提升召回，重排提升精度，Query 改写解决“问法”问题；效果必须用同一评测集做消融来量化，具体提升幅度以自己项目的实测为准，不要编造数字。**

1. **Hybrid Search**：向量检索擅长语义匹配，BM25 擅长精确词（型号、条款号、专有名词）。两路并行召回后融合：
   - **RRF**（Reciprocal Rank Fusion）：得分 = Σ 1 / (k + rank)，k 常取 60，免去不同分数尺度的归一化。
   - 或分数归一化后加权。
   ES 可同时承担 BM25 与向量检索。
2. **Rerank**：先召回较多候选（如几十条），用 Cross-Encoder 重排模型（如 bge-reranker 系列）对 query 与文档联合打分，取 top 几条进 Prompt。精度更高，但增加延迟，要控制候选数，必要时做缓存或异步。
3. **Query 改写**：
   - 多轮对话中做指代消解与补全，生成独立查询。
   - 多查询扩展（同义改写）、HyDE（先生成假设答案再检索）。
   - 复杂问题拆成子问题分别检索。
   - 关键词 / 实体抽取用于过滤和 BM25。
4. **评估怎么讲**：准备带标注的评测集；指标用 Recall@k、MRR、nDCG、答案忠实度；逐项开关做消融，对比基线（纯向量）与各项叠加后的变化，同时记录延迟与成本的代价。

### 7. 场景题：普渡机器人客服Agent在回答用户关于售后政策时产生幻觉瞎编条款，从Harness工程角度怎么加校验、审计与兜底

**参考答案**

**结论：政策类回答必须“有据可依”——检索溯源 + 生成约束 + 事后校验 + 审计留痕 + 失败兜底，把风险从 Prompt 转移到工程机制上。**

1. **溯源（Grounding）**：政策问题强制走权威政策库检索，回答只能基于检索到的条款；检索不到或相关度低时不回答，直接转人工或使用标准话术。
2. **生成约束**：要求结构化输出（结论、引用条款编号、原文片段）；低温度；Prompt 明确“无依据不得回答”。
3. **后置校验**：
   - 引用的条款编号与原文片段必须真实存在于检索结果中（字符串或语义匹配）。
   - 金额、天数、比例等关键数值与政策库逐一比对，必要时直接由数据库取值、模板拼装，不让模型自由生成。
   - 用 NLI 或 LLM Judge 判断回答是否被引文蕴含。
   - 校验失败：重试一次（把失败原因反馈给模型），仍失败则兜底。
4. **审计**：记录 trace_id、用户问题、检索到的文档及版本、Prompt 版本、模型输出、校验结果、最终回复，支持事后回溯与客诉举证；政策库带生效时间与版本管理。
5. **兜底**：低置信度走固定话术或转人工；高风险话题（赔付、法律责任）一律不由模型自由发挥。
6. **闭环**：把出错的案例加入评测集与回归测试，上线前跑幻觉专项评测，线上抽样复核并监控“无依据回答率”。

### 8. Java后端如何通过gRPC或HTTP与Python的LangGraph服务通信，SSE流式响应在Java里怎么转发给前端

**参考答案**

**通信方式**：
- **HTTP（FastAPI 等）**：简单通用、易调试，流式用 SSE 或分块传输，适合对外和多数内部场景。
- **gRPC**：基于 HTTP/2 + Protobuf，强类型接口、双向 / 服务端流式、内置 deadline 与拦截器，性能更好，适合内部高频调用；缺点是浏览器不能直接调用，调试成本稍高。

**SSE 转发**：Python 服务以 `text/event-stream` 输出，Java 作为网关消费上游流并转发给前端。
- Spring WebFlux：用 `WebClient` 读取上游 SSE，返回 `Flux<ServerSentEvent>`，天然支持背压。
- Spring MVC：用 `SseEmitter`，在独立线程池中读取上游并 `send`，避免占用 Tomcat 请求线程。

```java
@GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> chat(@RequestParam String q) {
    return webClient.post().uri("/agent/stream")
        .bodyValue(Map.of("query", q))
        .accept(MediaType.TEXT_EVENT_STREAM)
        .retrieve()
        .bodyToFlux(new ParameterizedTypeReference<ServerSentEvent<String>>() {})
        .timeout(Duration.ofSeconds(120));
}
```

**容易漏的细节**：
- **取消传播**：前端断开时要取消上游请求，让 Python 端停止生成，否则浪费 token 和算力。
- 反向代理（Nginx）关闭缓冲（`proxy_buffering off`），设置较长读取超时。
- 心跳（注释行或 ping 事件）防止中间设备断连。
- 错误以专门的事件下发，并有明确的结束事件。
- 事件带 id 便于断线续传；透传 trace_id 和鉴权信息。

### 9. Kafka在AI工作流中用来解耦哪些环节，Agent执行日志、观测数据Trace怎么采集和回溯

**参考答案**

**解耦的环节**：
- 耗时的异步任务（长时间 Agent 任务、批量处理），请求方只投递任务，结果通过回调或查询获取。
- 文档入库流水线：解析 → 切分 → Embedding → 写索引，各阶段独立扩缩容、失败可重试。
- Agent 执行日志、Trace、指标的采集。
- 用户反馈与评测事件、审计日志、通知。
- 数据同步（MySQL → ES）。

注意：同步交互的主链路（用户等待回答）不适合用 Kafka 做请求响应。

**Trace 采集与回溯**：
1. 每个步骤（LLM 调用、检索、工具调用、节点执行）生成一个 span：`trace_id`、`span_id`、`parent_span_id`、`session_id`、Agent / 节点名、输入输出摘要、耗时、token 用量、状态、错误信息。可使用 OpenTelemetry 规范，或接入 Langfuse、LangSmith 等。
2. 应用异步发送到 Kafka，不阻塞主流程；用 `session_id` 作消息 key，保证同一会话在同一分区内有序。
3. 消费者落地：ES（检索与排查）、ClickHouse 或 MySQL（统计分析）、对象存储（大体积原文）。
4. **回溯**：按 `trace_id` / `session_id` 查询完整调用树，重放；还可以依托 Kafka 保留期和 offset 重新消费，重建索引或回填数据。
5. 注意：消息至少一次投递，消费端用 `(trace_id, span_id)` 幂等去重；敏感数据脱敏；高流量时采样；大 payload 存外部，只在消息中放引用。

### 10. 场景题:一个多Agent协作任务跑了十多步上下文窗口快爆了，有哪些策略做上下文压缩、摘要与长期记忆迁移

**参考答案**

**结论：不是简单截断，而是分层管理——保留关键、压缩冗余、外置存储、按需取回。**

1. **滑动窗口**：保留最近 N 轮原文，系统提示和任务目标固定保留。
2. **滚动摘要**：上下文达到阈值（如窗口的 70%～80%）时，把较早的历史摘要为一段，之后继续迭代更新。摘要里要原样保留 ID、数值、决策与约束，避免细节失真。
3. **工具结果瘦身**：大体积的工具返回（网页、日志、表格）只保留相关字段或摘要，原文存外部存储，上下文里只留引用，需要时再读取。
4. **结构化状态 / 草稿板**：把已确认的事实、已完成步骤、待办放进 state，让后续 Agent 读结构化状态，而不是回读全部对话。
5. **选择性检索历史**：历史消息向量化，按当前子任务召回相关片段。
6. **子 Agent 上下文隔离**：子 Agent 在独立上下文里完成任务，只把结论和必要证据返回给主 Agent。
7. **长期记忆迁移**：把用户偏好、已确认事实、经验教训抽取为结构化记忆，写入向量库 / KV（如 LangGraph Store、Mem0），去重并带时间戳与过期策略，下次按需检索注入。
8. **成本侧**：保持前缀稳定以利用 Prompt Cache。

**风险**：摘要会丢信息，压缩错误会累积，需要评测压缩前后的任务成功率；关键约束放在固定区域，不参与压缩。

### 11. Redis用作分布式锁在Agent并发调度里要注意哪些问题，如何用Redisson实现看门狗自动续期

**参考答案**

**基本做法**：`SET key value NX PX ttl` 原子加锁，value 为唯一标识（客户端 ID + 线程 ID）。

**注意问题**：
1. **释放安全**：解锁必须校验 value 是自己的，再删除，用 Lua 保证原子，防止误删别人的锁。
2. **过期与业务时长**：TTL 太短，业务未结束锁就过期，会导致并发执行；TTL 太长，宕机后长时间无法获取。Agent 任务耗时不确定，应该用自动续期。
3. **可重入**：同一线程重复获取要支持（Redisson 用 Hash 记录持有者与重入次数）。
4. **主从与故障转移**：主节点异步复制，宕机切换时锁可能丢失。需要更强保证时使用 fencing token（单调递增令牌，资源侧校验）、数据库乐观锁，或 ZooKeeper / etcd；RedLock 的安全性存在争议，不要当作绝对保证。
5. **等待策略**：设置获取超时（`tryLock`），避免无限阻塞；避免自旋空转。
6. **锁粒度与范围**：锁的粒度尽量细（如按任务 ID）；不要把长时间 LLM 调用放进持锁的临界区，能用幂等设计就不用锁。

**Redisson 看门狗**：调用 `lock()` 或 `tryLock(waitTime, unit)`，**不指定 leaseTime** 时启用看门狗：默认锁过期时间 30 秒（`lockWatchdogTimeout`），只要持有锁的客户端存活，每隔 lockWatchdogTimeout / 3（约 10 秒）自动续期；`unlock` 后停止续期；客户端宕机则续期停止，锁到期自动释放。一旦显式指定 leaseTime，则不会自动续期。

```java
RLock lock = redisson.getLock("agent:task:" + taskId);
if (lock.tryLock(3, TimeUnit.SECONDS)) {   // 不传 leaseTime，启用看门狗
    try {
        runAgentTask();
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

### 12. Elasticsearch索引在RAG知识库频繁更新时如何做平滑重建与别名切换，避免检索中断

**参考答案**

**结论：应用只访问别名，不直接访问物理索引；新建索引、全量构建、补增量、校验后用别名原子切换，旧索引保留用于回滚。**

步骤：
1. 创建新索引 `kb_v2`（新 mapping / 新分词器 / 新向量维度）。
2. 全量构建：用 `_reindex` 从旧索引复制，或从源数据（MySQL、对象存储）重新处理；若更换 Embedding 模型需重新计算向量。构建期间可临时设置 `refresh_interval: -1`、`number_of_replicas: 0` 加速，完成后恢复。
3. **补增量**：重建期间的更新要同步到新索引——双写，或记录起始时间点后从消息队列 / 变更日志回放。
4. 校验：文档数、抽样检索结果、评测集召回率对比。
5. **原子切换**：一次 `_aliases` 请求同时移除旧、添加新，切换瞬间完成，没有检索中断。
6. 观察一段时间，确认无问题再删除旧索引；有问题则把别名切回。

```json
POST /_aliases
{
  "actions": [
    { "remove": { "index": "kb_v1", "alias": "kb_read" } },
    { "add":    { "index": "kb_v2", "alias": "kb_read" } }
  ]
}
```

补充：读写别名分开（写别名使用 `is_write_index` 指定写入目标）；平时的小更新直接 upsert，用文档 ID 保证幂等，不需要重建。

### 13. 手撕算法：给定一个有向图表示Agent节点依赖关系，实现拓扑排序，如果存在环返回空列表

**参考答案**

**思路**：Kahn 算法。统计每个节点入度，把入度为 0 的节点入队；每次出队一个节点加入结果，并把它的后继入度减 1，减到 0 就入队。若最终结果数小于节点数，说明有环，返回空列表。

时间复杂度 O(V + E)，空间 O(V + E)。约定边 `(u, v)` 表示 u 必须先于 v。

```python
from collections import defaultdict, deque


def topo_sort(nodes: list[str], edges: list[tuple[str, str]]) -> list[str]:
    graph = defaultdict(list)
    indegree = {n: 0 for n in nodes}
    for u, v in edges:
        graph[u].append(v)
        indegree[v] += 1

    queue = deque(n for n in nodes if indegree[n] == 0)
    order = []
    while queue:
        cur = queue.popleft()
        order.append(cur)
        for nxt in graph[cur]:
            indegree[nxt] -= 1
            if indegree[nxt] == 0:
                queue.append(nxt)

    return order if len(order) == len(nodes) else []
```

### 14. 项目里怎么衡量Agent工作流的好坏，除了人工评估外，自动评测指标和BadCase回流机制怎么建

**参考答案**

**结论：离线评测集 + 线上指标 + 自动评审三者结合，再用 BadCase 回流形成闭环。**

**自动评测指标**：
- **结果层**：任务成功率、答案正确率、忠实度（有无幻觉）、相关性。
- **过程层**：工具选择与参数正确率、步骤数 / 轨迹效率、重复调用率、循环触发率。
- **RAG 层**：Recall@k、MRR、nDCG、上下文相关度。
- **路由层**：意图 / 路由准确率。
- **系统层**：P50 / P95 延迟、首字延迟、token 成本、错误率。
- **LLM-as-Judge**：按评分细则打分，需用人工标注抽样校准，并注意位置偏好、自我偏好等偏差。
- 把评测接入 CI，每次修改 Prompt、模型、工具或编排都跑回归，设阈值，不达标不发布。

**线上指标**：用户点赞 / 点踩、重复提问或改写率、转人工率、问题解决率；新版本做灰度或 A/B。

**BadCase 回流**：
1. **发现**：用户负反馈、Judge 低分、校验失败、异常（超时、循环）、转人工记录、告警。
2. **沉淀**：脱敏后进入问题池，保留完整 Trace。
3. **归因**：分类为检索问题、意图路由问题、工具问题、Prompt / 模型问题、数据缺失。
4. **修复并验证**：修复后加入评测集作为回归用例，确认修复且不影响其他。
5. **复用**：必要时作为微调或示例数据；定期统计 BadCase 类型分布，指导优先级。

### 15. 当产品经理要求把单Agent改成三个专业Agent分工，但延迟涨了一倍，你怎么在技术成本和体验间取舍

**参考答案**

**结论：用数据决策——先确认多 Agent 带来的收益是否值得延迟的代价，再想办法把延迟压下来，而不是简单同意或拒绝。**

1. **量化**：对比单 Agent 与三 Agent 在评测集上的正确率、完成率，以及延迟（P50 / P95、首字延迟）、成本。如果质量提升有限，不应为分工而分工；如果提升明显，再优化延迟。
2. **定位延迟来源**：Trace 里看是串行 LLM 调用、上下文传递过长，还是路由层额外开销。
3. **降延迟手段**：
   - 无依赖的专业 Agent 并行执行。
   - 路由与简单任务使用小模型 / 更快的模型。
   - 简单问题仍走单 Agent，复杂问题才走多 Agent（分级路由）。
   - 缩短 Agent 间传递的上下文，只传结论。
   - 流式输出，先让用户看到进展，降低体感延迟。
   - 缓存、预取。
   - 也可考虑“单 Agent + 多工具 / 多技能（动态提示）”，保留专业性但不增加调用跳数。
4. **与产品对齐**：设定体验目标（如首字延迟与整体 P95 的 SLO）和质量目标，把方案、收益与代价摆在一起，用灰度实验验证后再全量。
5. **结论示例**：质量提升明显且延迟能压到可接受范围就上；否则保留单 Agent，对特别复杂的场景才启用多 Agent。

### 4. 多Agent系统上线后线上出现偶发死循环或无限调用工具，怎么设计观测、报警与人工介入HumanInTheLoop机制

**参考答案**

**结论：事前限制、事中检测、事后告警、人工兜底，四层都要有。**

1. **预防（硬限制）**：最大步数（LangGraph 的 `recursion_limit` + 业务级上限）、单会话最大工具调用次数、token / 成本预算、整体超时；重复调用检测（相同工具 + 相同参数的哈希连续出现 N 次即中断）；循环检测（状态重复）。
2. **观测**：
   - 每个步骤记录 Trace：Agent、工具、参数摘要、耗时、token。
   - 指标：会话步数分布（P95 / P99）、工具调用频率、重复调用率、单会话成本、触发限制的次数。
   - 按 `session_id` 可以回放完整调用链。
3. **报警**：步数或成本超过阈值、触发限制的比例突增、单会话异常高耗时，分级通知（普通告警 / 紧急）；配套开关，可一键降级、禁用某个工具或 Agent，支持版本回滚。
4. **人工介入（HITL）**：
   - 触发条件：检测到循环、置信度低、高风险动作（付款、下发控制指令等）、多次重试失败。
   - 实现：LangGraph 的 `interrupt` 暂停并持久化状态，推送到工单 / 运营后台；人工可以批准、修改参数或状态、拒绝或接管，然后从检查点 `resume`。
   - 设置超时：人工长时间未处理，则走兜底话术，避免用户一直等待。
5. **复盘**：异常会话进入评测集，修复根因（工具描述、停止条件、Prompt），并验证。

### 6. 从Harness工程角度，Agent从Demo到生产有哪些鸿沟，重试、沙箱、输出校验、成本管控、熵管理你各自怎么落地

**参考答案**

**结论：Demo 只验证“能跑通一次”，生产要求“稳定、安全、可控、可观测、可负担”，鸿沟就是把各类失败模式用工程手段兜住。**

- **重试**：区分可重试错误（超时、限流、5xx）和不可重试错误（参数错误、权限）；指数退避加抖动，设最大次数和重试预算；写操作带幂等键；把错误信息反馈给模型让其修正，限定次数；重试不能无限放大成本。
- **沙箱**：执行代码或高权限工具时放在隔离环境（容器 / gVisor / 微虚机），限制 CPU、内存、时长，文件系统最小权限、只读挂载、临时目录，网络默认禁止或白名单出站，用后销毁；敏感动作要审批。
- **输出校验**：结构化输出用 Schema 校验；业务规则校验（数值范围、枚举、权限）；事实类内容做溯源校验；安全过滤；校验失败触发修复重试，再失败则兜底。
- **成本管控**：token 与步数预算；按任务难度做模型路由（简单任务用小模型）；缓存（结果缓存、Prompt Cache）；上下文压缩；租户 / 用户配额与限流；成本监控与告警。
- **熵管理**：这里指系统随运行时间累积的混乱——上下文膨胀、记忆陈旧或相互矛盾、Prompt 与工具描述漂移、状态与知识库不一致。做法：上下文压缩与摘要、记忆去重与过期、Prompt 和工具版本化、定期清理与一致性校验、回归评测、收窄 Agent 的动作空间。
- **其他鸿沟**：观测与追踪、评测与回归、权限与审计、人工介入、灰度与回滚。

### 7. 场景题：普渡机器人要接入几十个内部微服务工具，工具Schema变动频繁，怎么设计统一适配层与版本兼容策略

**参考答案**

**结论：在 LLM 与微服务之间建一层“工具网关 / 适配层”（防腐层），向模型暴露稳定的工具契约，把后端的变化吸收在适配层内。**

1. **统一工具描述**：每个工具登记名称、版本、描述、入参 / 出参 JSON Schema、超时、是否幂等、鉴权、负责人、所属领域。可由 OpenAPI / Protobuf 自动生成，也可按 MCP 协议封装。
2. **适配层**：模型看到的是稳定的“逻辑 Schema”，适配层负责转换成各微服务的真实请求，并把响应归一化为统一的结构与错误码；后端字段变化只改映射，不动 Prompt。
3. **版本兼容**：
   - 语义化版本；优先向后兼容的变更（新增可选字段）；破坏性变更发新版本，新旧并行一段时间，设置弃用期。
   - 注册中心保存多版本，路由按版本 / 灰度选择。
   - CI 中加入契约测试，Schema 变更自动触发并校验兼容性，不兼容的阻断发布。
   - 变更事件通知，适配层与工具描述自动更新。
4. **工具数量多的问题**：几十个工具不要全部塞进 Prompt。按领域分组，分层路由（先选领域 Agent，再选工具），或对工具描述做检索，只暴露 top-k 相关工具。
5. **治理**：统一超时、重试、熔断、限流、权限、审计；监控每个工具的调用成功率和 Schema 校验失败率，作为发现不兼容的信号。

### 8. Java在高并发调用Python推理服务时，线程池与连接池参数怎么配，如何防止下游慢导致上游雪崩

**参考答案**

**结论：参数要依据“并发量 = QPS × 响应时间”（Little 定律）和压测结果配置，核心是有界、隔离、有超时、可快速失败。**

**线程池**：
- 调用推理服务是 IO 等待型，线程数可用估算公式：核心线程数 ≈ CPU 核数 × (1 + 等待时间 / 计算时间)，再以压测校准；也可用 QPS × 平均耗时估算所需并发。
- 使用**有界队列**，不要无界（会堆积内存并拉长等待）；拒绝策略用快速失败或 CallerRuns，并有降级返回。
- 给该下游使用独立线程池（舱壁隔离），避免拖垮其他业务。
- JDK 21 可使用虚拟线程降低阻塞成本，但仍需用信号量限制对下游的并发。

**连接池（HttpClient / OkHttp / gRPC）**：
- 最大连接数、单路由最大连接数与目标并发匹配；连接获取超时要短，拿不到连接快速失败。
- 连接超时较短，读取超时依据下游 P99 设置；配置空闲连接清理与存活时间，避免使用已被服务端关闭的连接。
- gRPC 基于 HTTP/2 多路复用，少量 Channel 即可，注意最大并发流设置，每次调用设置 deadline。

**防雪崩**：
1. 各层超时，且上游超时 > 下游，并向下传递 deadline。
2. **熔断**（Resilience4j）：失败率或慢调用比例超阈值，直接快速失败。
3. **限流与并发限制**（信号量舱壁）、负载削峰、请求优先级。
4. 重试要克制：有重试预算，避免重试风暴；只重试幂等请求。
5. **降级**：缓存、兜底话术、排队提示。
6. 推理服务端也要限流和排队，并提供健康检查，配合网关摘除异常实例；监控线程池队列长度、活跃线程数、连接池等待数、下游 P99，及时报警。

### 9. MySQL与Elasticsearch在数据一致性上怎么处理，Agent产生的执行记录写MySQL成功后ES同步失败了怎么补偿

**参考答案**

**结论：以 MySQL 为唯一事实源，ES 作为派生索引，接受最终一致，通过可靠的异步同步 + 重试 + 对账补偿保证收敛，不使用跨库分布式事务。**

**同步方案**：
1. **本地消息表（Outbox）**：业务写入和“待同步事件”在同一个 MySQL 事务中提交，保证二者要么都成功要么都失败；独立的投递任务读取事件发到 MQ 或直接写 ES。
2. **CDC**：通过 Canal / Debezium 订阅 binlog，写入 Kafka，再由消费者写 ES。对业务无侵入。
3. 不推荐业务里“先写 MySQL 再同步调用写 ES”的双写：中间失败会造成不一致。

**幂等与乱序**：ES 文档 ID 使用 MySQL 主键，用 upsert 写入；利用 `version_type=external` 并以更新时间或版本号作为外部版本，避免旧消息覆盖新数据。

**ES 同步失败的补偿**：
- 消费端重试（指数退避），多次失败进入死信队列并告警，人工或定时任务重新处理。
- Outbox 表保留状态字段，投递任务定时扫描未成功的记录重试。
- **对账**：定期比较 MySQL 与 ES 的数量、最大更新时间或抽样校验，发现差异时修复。
- **全量重建**：必要时用新索引加别名切换整体重建。

业务上要明确：ES 查询存在短暂延迟，需要强一致读取的场景直接查 MySQL。

### 12. 手撕算法：实现一个简易的Agent工作流调度器，输入是任务列表与依赖关系，模拟并发执行并打印完成顺序

**参考答案**

**思路**：基于拓扑排序（入度）的并发调度。入度为 0 的任务立刻启动；任务完成后，把后继的入度减 1，入度变 0 就启动；用 `asyncio` 模拟耗时，用 `Semaphore` 限制最大并发；按完成时间打印完成顺序。若还有任务未完成但没有任何在运行的任务，说明有环（死锁），抛出异常。

复杂度：调度本身 O(V + E)，总耗时取决于关键路径与并发度。

```python
import asyncio
from collections import defaultdict


async def run_workflow(durations: dict[str, float],
                       deps: list[tuple[str, str]],
                       max_concurrency: int = 3) -> list[str]:
    """durations: 任务名 -> 模拟耗时（秒）；deps 中 (a, b) 表示 a 先于 b"""
    graph = defaultdict(list)
    indegree = {t: 0 for t in durations}
    for a, b in deps:
        graph[a].append(b)
        indegree[b] += 1

    sem = asyncio.Semaphore(max_concurrency)
    done_queue: asyncio.Queue[str] = asyncio.Queue()
    order: list[str] = []
    background: set[asyncio.Task] = set()

    async def run(name: str) -> None:
        async with sem:
            await asyncio.sleep(durations[name])    # 模拟任务执行
        await done_queue.put(name)

    def launch(name: str) -> None:
        task = asyncio.create_task(run(name))
        background.add(task)                        # 持有引用，避免被回收
        task.add_done_callback(background.discard)

    running = 0
    for t, d in indegree.items():
        if d == 0:
            launch(t)
            running += 1

    while len(order) < len(durations):
        if running == 0:
            raise ValueError("任务依赖存在环")
        name = await done_queue.get()
        running -= 1
        order.append(name)
        print(f"完成: {name}")
        for nxt in graph[name]:
            indegree[nxt] -= 1
            if indegree[nxt] == 0:
                launch(nxt)
                running += 1
    return order


if __name__ == "__main__":
    asyncio.run(run_workflow(
        {"retrieve": 0.3, "tool": 0.2, "rerank": 0.1, "generate": 0.4},
        [("retrieve", "rerank"), ("rerank", "generate"), ("tool", "generate")],
    ))
```

说明：示例没有处理任务失败。生产实现里需要捕获异常、记录失败状态，并决定是中断整个工作流、跳过下游还是重试，否则失败任务会让主循环一直等待。

### 14. 如果公司要求半年内把AI Agent覆盖三条业务线，但人力只有你现在的一半，你怎么拆优先级和保交付

**答题思路**

6. **沟通与止损**：尽早向上同步人力与目标的差距，提出可选方案（缩范围、延期、增援），而不是到最后才暴露。

### 7. 如果这轮技术面评价你AI理论稍弱但工程很强，你怎么看待这个短板并打算怎么补

**答题思路**

2. **说明工程优势的价值**：Agent 落地中工程能力（稳定性、评测、可观测、成本）很关键，但理论理解能帮助更好地判断模型行为与方案取舍，二者互补。
3. **补强计划**（具体可执行）：
   - 系统学习 Transformer、训练与推理基础、RAG 与 Agent 的核心论文。

### 8. 手里有其他Offer吗，大概是什么方向，为什么还在看普渡的机会
