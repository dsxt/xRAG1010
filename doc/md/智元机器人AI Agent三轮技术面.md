> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

面了三轮，整体感觉还行。一面问得比较基础，都是概念性的东西，答起来没什么压力。二面开始深挖项目，问得挺细，不过都在射程范围内，毕竟是自己做的东西。三面聊架构和规划，面试官水平可以，问的问题有深度，聊得还挺投机。就是手写算法那部分，KMP 确实有点老套，现在很少再手写这个，不过能写出来就行。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「定位 → 一件做过的事 → 和岗位的连接」讲。

1. 一句话说明年限和方向。技术栈只报真正写过的，例如 Python、Java、检索、工具调用、Redis、MySQL。
2. 只展开一个 Agent 项目：用户要完成什么、你负责的那段链路、结果用你能复述的现象说明。没有统计就不要报百分比。
3. 留下一个可追问的点，例如检索怎么进上下文、写操作如何确认、失败轨迹怎么看。
4. 收束到岗位：能把模型放进有状态、有工具边界的系统里，一面的概念题也能落到这条链路上。

### 2. 项目介绍

**答题思路**

用 2 到 3 分钟讲清一条真实链路，按下面的顺序，名称用自己项目里的叫法。

1. 背景：谁在用，原来卡在哪一步，Agent 介入之后人还保留哪一步。
2. 你的职责：编排、检索、工具、评测里具体哪几块是你做的。
3. 请求怎么走：会话从哪来，哪些步骤是固定流程，哪一段才让模型选工具。
4. 知识从哪来：业务库、文档，还是两者都有。文档检索和订单状态不要混成一个来源。
5. 一个失败怎么处理：工具超时、资料不足、用户中途改口，分别看到什么。
6. 怎么知道它工作：离线任务集、线上轨迹，或人工抽检。只讲你真的看过的信号。

讲完停住，等面试官选点往下挖。

### 3. 什么是 AI Agent？它的核心组件有哪些？

**参考答案**

AI Agent 是以大模型为决策核心、围绕目标循环行动的系统：每一步根据当前状态选择动作，读到外部结果后再决定下一步。

核心组件有四块，再加一层运行约束。

- 模型负责理解目标和生成下一步。
- 规划把目标拆开，并在观察结果不符合预期时改计划。
- 记忆包括本轮上下文里的工作记忆，以及放在外部、跨轮还能取回的长期记忆。
- 工具是查询、检索和写业务系统的通道。事实和副作用都经过工具，模型只提议调用。

运行时负责步数、超时、权限和日志，把循环限制在可停止的范围内。角色设定只是提示词里的策略，算不上独立子系统。

路径完全可以事先写死时，用工作流让模型填槽即可。下一步取决于观察结果时，才需要这段自主循环。

### 4. 解释一下什么是幻觉问题（Hallucination）？在 AI Agent 中如何缓解？

**参考答案**

幻觉是模型给出了流畅、但和事实、给定资料或真实工具结果对不上的内容。Agent 里常见三类：编造资料里没有的事实或引用，声称做了并没有发生的操作，以及工具参数形式合法、对象却是错的。

根子是模型按概率续写，本身没有对外部世界的一致性承诺。上下文里缺少证据时，它会用参数记忆把缺口补上。

缓解按类型做。事实问题把可引用的资料放进上下文，并要求结论能对上片段；资料不足就明确说无法确认。动作问题以运行时记下的工具回执为准，回答里只能转述回执。参数问题除了 schema，还要查对象是否属于当前用户、是否真实存在。高风险事实把温度压低，并把坏例放进固定评测。

检索和工具只能减少没有依据的生成。证据本身错了，或模型忽视证据，幻觉仍会发生。

### 5. 提示词（Prompt）工程有哪些最佳实践？

**参考答案**

提示词要写成可测试的任务说明，迭代时一次只改一条。

1. 把角色、任务、约束、输出格式分开。用户输入和检索片段用明确边界包住，避免和系统指令糊成一段。
2. 写清成功标准。事实类回答只能依据工具结果或检索片段；依据不足时说明缺什么。
3. 工具说明写清何时该调、参数含义，以及失败后应该停下来还是换一条路径。
4. 硬约束放在提示的前部和结尾。长上下文的中部更容易被忽略。
5. 格式不稳时用结构化输出。示例只覆盖容易错的边界，同类例子不必堆很多。
6. 提示词和代码一样版本化。用同一批坏例比较改动，口头感觉不能当作结论。

「尽量专业、详细、友好」这类空话几乎不会改变行为。约束要具体到可以判断对错。

### 6. 上下文（Context）在对话系统中的重要性是什么？

**参考答案**

这一轮模型能用的信息，就是当前上下文里的那些 token：系统约束、对话状态、最近原话、工具回执和检索片段。没放进去的订单号、偏好和上一步结果，对这次调用等于不存在。

它决定三件事。代词和省略能否接上上一句；已经确认的槽位和权限会不会丢；回答有没有依据。所以多轮系统不能假设模型「记得」服务端没发给它的内容。

上下文越长越贵，延迟越高，无关内容也会把关键事实挤掉。重要性体现在挑选和排列：结构化状态单独放一块，最近几轮保留原文，旧对话用摘要，证据放在模型容易用到的位置。把全部历史原样塞进窗口，并没有利用好上下文。

### 7. 向量数据库在 AI Agent 中的作用是什么？

**参考答案**

向量数据库提供按语义近邻取回文本的能力。文档块和可复用的记忆被编成向量，查询时用同一套嵌入模型把问句变成向量，再做近似最近邻搜索，把相关片段放进有限的上下文。精确词面，例如型号、错误码，通常还要配关键词检索，两路结果再融合。

元数据过滤和向量搜索一起用，才能按租户、文档版本、时间裁剪候选。没有过滤时，语义相近但属于别人或已经过期的内容也会被取回。

它存的是检索索引。订单状态、库存、权限以业务库为准。近邻只说明「像」，不能把检索分数当成事实已经成立。换嵌入模型必须整库重编，查询侧和入库侧要用同一个模型。

### 8. 介绍 RAG（Retrieval-Augmented Generation）的基本原理。

**参考答案**

RAG 把「可更新的外部资料」和「模型生成」分开。回答之前先从资料库取出相关片段，再把片段和问题一起交给模型，让结论有处可查。资料变了，更新索引即可，不必为了新文档去重训模型。

基本链路是：文档按结构切块并嵌入入库；查询时可以先补全指代；用关键词和向量两路召回；必要时对一小撮候选重排；把排好的片段放进上下文再生成。生成侧要求紧扣片段，片段里没有答案时允许拒答。

原理解决的是知识从哪里来，以及怎么随业务更新。它不保证每一句都对：库里没有证据、切块把事实切断、或模型绕过片段自由发挥，都会答错。所以检索命中和生成是否忠于片段要分开看。

### 9. 手写算法：实现一个简单的字符串匹配算法（如 KMP）

**参考答案**

KMP 先把模式串预处理成 LPS（最长真前后缀表）：`lps[i]` 是 `pattern[0..i]` 的最长真前缀，同时它也是这段的后缀。匹配时文本下标只前进；失配时模式下标退到 `lps[j - 1]`，已经比对过的前缀不必在文本里重扫。

模式串 `ABABC` 的 LPS 是 `[0, 0, 1, 2, 0]`。在文本 `ABABABC` 里，对齐到模式最后一个字符失配时，模式指针回到 2，最终命中下标 2。

时间是 O(n + m)：文本下标只增，模式下标回退的总量不超过成功比较的次数。额外空间是 LPS 的 O(m)。朴素匹配最坏要 O((n − m + 1) · m)。

```python
def build_lps(pattern: str) -> list[int]:
    lps = [0] * len(pattern)
    length = 0
    i = 1
    while i < len(pattern):
        if pattern[i] == pattern[length]:
            length += 1
            lps[i] = length
            i += 1
        elif length:
            length = lps[length - 1]
        else:
            lps[i] = 0
            i += 1
    return lps


def kmp_search(text: str, pattern: str) -> list[int]:
    if not pattern:
        return []
    lps = build_lps(pattern)
    hits = []
    i = j = 0
    while i < len(text):
        if text[i] == pattern[j]:
            i += 1
            j += 1
            if j == len(pattern):
                hits.append(i - j)
                j = lps[j - 1]
        elif j:
            j = lps[j - 1]
        else:
            i += 1
    return hits
```

这里按字符比较，中文同样适用。若业务要按词或按字节匹配，先定义序列元素再套同一张表。空模式串这里定义为没有命中。

### 10. 什么是 ReAct 框架？它如何帮助 AI Agent 推理？

**参考答案**

ReAct 把推理和行动交错执行。每一轮模型先写出当前判断（Thought），再给出一个工具名和参数（Action）；运行时真正调用工具，把回执写成 Observation 送回下一轮，直到可以回答或达到步数上限。

和只写一段思维链相比，它的中间结论能被外部结果纠正。和只调工具、不留判断相比，轨迹上能看出是计划错了还是工具错了。帮助推理的方式，就是把原先藏在一次生成里的中间决定显式化，并用观察结果约束下一步，减少凭空补齐订单号、政策或计算结果。

落地时有三个条件。动作按 schema 解析，解析失败就把错误退回模型。Observation 只能由运行时写入，模型无权伪造回执。循环有最大步数和超时。写操作即使出现在 Thought 里，也要等确认后再执行。

### 11. 多轮对话中如何维护对话状态？

**参考答案**

每轮在服务端保存结构化状态：当前目标、已确认槽位、还缺的槽位、待确认动作，以及最近一次工具回执。模型看到的是「状态摘要 + 最近几轮原话」，更早的原文压成摘要。会话键把这些内容和用户绑在一起。

状态转移放在代码里。槽位由模型提议、由代码校验后写入；槽位齐了才进入确认；用户确认后才执行写操作。模型不能直接把阶段改成已完成。

这样换话题或压缩历史时，已经确认的事实还在。只拼接全部历史，槽位会散落在原文里，既占窗口，也容易在摘要时丢掉。工具回执过期后要重新查询，状态里的旧回执不能一直当成当前事实。

### 12. 记忆（Memory）在 AI Agent 中有哪些类型？

**参考答案**

按内容可以分成四类。

- 工作记忆：这一轮决策要用的信息，放在当前上下文里，包括最近对话、槽位和本轮工具结果。
- 情节记忆：发生过的事，例如某次对话解决了什么问题，通常带时间。
- 语义记忆：相对稳定的事实和偏好，例如称呼、常用地址、设备型号。
- 程序记忆：怎么做某类事，表现为工具代码、技能说明和版本化的提示词。

短期和长期说的是保存多久、放在哪。短期对应工作记忆，随会话过期。长期把情节和语义放到外部存储，需要时再取回。程序记忆放在仓库里按任务加载，不必把所有历史再嵌入一次。

对话缓冲、摘要缓冲是实现手段，不是记忆类型。面试里把类型和存储方式分开讲。

### 13. 如何评估 AI Agent 的性能？

**参考答案**

性能要同时看任务有没有完成，以及完成一次要多少时间和费用。流畅度不能代替这两项。

离线用固定任务集，记录：任务是否达到终态、工具名和参数是否正确、有没有调用禁止的工具、答案里的事实能否对上回执或检索片段、走了多少步。同一任务要重复跑，看稳定成功率。多条路径都合法时，用终态和禁调工具来判，不必死扣唯一轨迹。

线上看延迟分位、token 和费用、工具错误率、人工接管率、用户是否立刻重试。模型当裁判只适合开放式表述，而且要先用人工标注校准。退款是否生成、设备指令是否下发，以业务状态为准。

一个总分会把检索错误、工具错误和生成错误混在一起。至少按意图和这三层拆开看。

### 14. 了解哪些开源 AI Agent 框架？

**参考答案**

选型先看缺的是状态、检索还是多角色编排，框架替代不了工具权限和评测。

- LangGraph 用图描述有状态流程，支持检查点和人工确认，适合步骤必须可控的业务。
- LlamaIndex 侧重文档接入、索引和检索，适合 RAG 资料链路。
- AutoGen 侧重多个 Agent 对话协作。
- Semantic Kernel 把模型和插件嵌进现有应用。
- CrewAI 用角色快速搭原型。
- Dify 一类平台用可视化把检索和工具串成应用，适合交付完整应用；已有后端要深度定制运行时时，通常仍然自己掌握编排。

这些项目迭代很快，面试里说明白各自管哪一层即可。真正要讲的是：状态存在哪、工具谁能调、失败后从哪一步继续。

### 15. 在开发 AI Agent 时遇到的最大挑战是什么？

**答题思路**

讲一件自己项目里的事，按「哪一类问题 → 当时的后果 → 你把约束放在哪 → 怎么确认有改善」的顺序。百分比没有依据就不要编。

可以选的真实类型通常是下面之一：

1. 事实不可靠：模型补齐了资料里没有的政策或状态。
2. 副作用难测：写操作重试会造成重复提交。
3. 上下文取舍：窗口里堆了历史，确认过的槽位反而丢了。
4. 评测缺失：演示能过，换一种说法就失败，而且说不清失败在检索、工具还是生成。

讲完补一句共性：循环能跑通之后，难点是失败时仍然停得住、查得到。若面试官问的是行业共性而不是你的项目，就用这四类说明你如何取舍，仍然落到你做过的那一类上。

## 二面

### 1. 自我介绍

**答题思路**

二面会顺着项目往下挖，自我介绍控制在 1 分钟内，把钩子放在即将深挖的那条链路上。

1. 年限、方向、你在项目里的角色。
2. 用三句话圈定项目：用户任务、系统形态（工作流里嵌了一段 Agent，或完整的工具循环）、你负责的模块。
3. 主动点出最硬的一处，例如幻觉怎么被资料和回执约束、对话状态谁来改、评测看终态还是看文案。后面的题就从这里展开。
4. 不要在开场把所有框架名词报一遍。

### 2. 详细描述一个你参与的 AI Agent 项目

**答题思路**

按一次请求的时间顺序讲 4 分钟左右，名字和数字只用你能展开的。

1. 任务边界：Agent 起草、查询，还是在人确认后执行。哪些动作明确不让它做。
2. 入口：身份、会话 id、限流，结果是一次性返回还是流式。
3. 状态：服务端保存哪些槽位和阶段。模型每轮拿到的是状态摘要加最近原话。
4. 决策：哪几步是固定流程，从哪一步起模型才选择工具。循环的步数上限是多少量级，按你们的真实设置说。
5. 只读路径：检索有哪些过滤（权限、版本、产品线）；工具参数如何校验。
6. 写路径：确认点在哪，幂等键谁生成，失败回执回来之后状态怎么变。
7. 观测：一次失败的轨迹里能看到意图、参数、回执和引用片段。
8. 收在一个你修过的坏例上：现象、改动放在提示词里还是代码里、用什么信号确认好转。

准备三个追问：最容易错的一段、如何从轨迹定位、用户在失败时看到什么。

### 3. 在项目中如何解决幻觉问题？

**答题思路**

先把项目里的幻觉说成一种具体失败，再讲你放在模型外面的约束。不要说「我们用了 RAG，所以没有幻觉」。

1. 定性：是编造政策或文档、编造工具结果，还是参数指向了错误对象。最好举一条你还记得的用户说法。
2. 证据从哪来：可变事实走业务接口；文档事实走检索，回答要能对上片段 id。两条都没有时，产品文案是「无法确认」，同时说明缺哪一项。
3. 代码守住什么：工具白名单、对象归属校验、确认前不调用写接口。运行时写入的回执覆盖模型自己说的「已经办好」。
4. 怎么防止退步：这条坏例进了固定集，改提示词或换模型时要重放。
5. 若被追问效果：讲坏例是否不再复现、人工抽检看什么。没有统计就讲抽检方式。

### 4. 如何使用 Harness 进行 AI Agent 的测试和评估？

**参考答案**

Harness 是模型外面的运行外壳：组装上下文、提供工具、限制步数、记录轨迹、校验动作。评测使用同一个外壳，把外部工具换成夹具，才能比较两次改动。

一套可回归的任务包含：用户输入、初始状态、脚本化的工具回执、终态判定。判定优先写在业务状态上，例如「只创建了一笔退款、金额来自工具回执」。轨迹断言补充：必须调用过的只读工具、禁止调用的写工具、步数上限。开放式措辞才用裁判模型，并且先对照人工标注。

模型有随机性时，把采样收到接口允许的最低随机度，并对同一任务重复执行，看每次都成功的比例。单次通过只能说明存在一条走通的路径。

失败时看轨迹差异：从哪一步的回执开始偏离，是检索为空、参数被拒，还是生成无视回执。发布前跑一小套冒烟，较大的集合夜间跑。没有结构化回执和显式状态，Harness 就只剩下一轮对话，评测无法落到动作上。

### 5. 如何设计提示词以改善 AI Agent 的响应质量？

**参考答案**

先定义质量，再改提示词。Agent 场景里质量通常是：忠实于回执和资料、该做的步骤做完、格式能被下游解析、没有越权承诺。

实用结构就五段：一句话任务；当前允许的工具和调用条件；事实约束（只使用工具结果与检索片段，不足就说明缺什么）；输出字段（结论、依据、未完成项）；一条反例，例如用户催促也不能把未确认写成已办理。检索片段和用户原文放在数据区，不写进系统规则区。

改进回路是：从真实失败里归类，一次只改一条指令，在 Harness 里重放这一类以及相邻的类。这一类上升、其他类不下降，才保留。提示词版本和工具 schema 版本一起记在轨迹里，否则线上好了也说不清是哪次改动。

示例用来固定容易错的格式和拒答，不要用例子暗示模型可以跳过工具自己编状态。

### 6. 上下文长度限制下，如何优化信息检索？

**参考答案**

窗口有限时，优化目标是把能支撑答案的那几段放进去，而不是提高召回的名义条数。

查询侧先用会话状态补全指代，原句和改写句都去召回，再按名次融合，避免改写改错时丢掉原句。入库侧用元数据把租户、过期文档和错误产品线排除在候选之外。关键词负责型号和错误码，向量负责说法不同的同一问题，交叉编码器只重排前几十个候选。

进窗口之前做提取式压缩：只留与问题有关的句子，近重复的块去掉。小块用来命中，若小块的事实不完整（例如表头被切开），再补回所属的父块，并仍然卡在 token 预算里。证据和硬约束放在上下文两端，减轻长上下文中部被忽略的问题。

第一轮上下文里已经有依据就停止。多跳检索只在依据不足时再生成下一个查询，并限制跳数，因为每一跳都是一次模型调用。历史对话和检索证据分预算，不能让旧聊天记录占满窗口。

### 7. 向量数据库的选择和优化策略有哪些？

**参考答案**

先定规模、过滤方式、更新频率和延迟，再选引擎。嵌入模型和切分对效果的影响，往往大于换一个向量库。

资料和元数据已经在 PostgreSQL、规模与 QPS 还没把近似搜索打满时，pgvector 能和事务、权限过滤放在一起，运维简单。过滤很重、数据量大、或需要独立扩容检索时，再看 Milvus、Qdrant、Vespa、Weaviate、OpenSearch 这类专用引擎。FAISS 是近邻索引库，可以用 ID 选择器做过滤，但文档存储、元数据更新和在线服务要自己补，它本身不是向量数据库。

优化按这条顺序：查询和入库使用同一个嵌入模型，换模型就整库重编；用稳定的块 id 做幂等更新，并删除旧版本；过滤尽量下推到搜索里。过滤很严时，若只在全库近邻里事后过滤，名额会被无关向量占满。HNSW 一类近似索引的搜索宽度要在自己的召回–延迟曲线上选，别人的默认值只是起点。做量化节省内存时，用同一评测集看召回掉了多少再决定。

精确编号不要只靠向量。混合检索加上按租户分索引或强制租户过滤，避免只在提示词里要求模型「不要看别人的文档」。

### 8. RAG 中如何平衡检索质量和生成质量？

**参考答案**

两条质量分开测，再看端到端。检索质量看标准证据有没有进最终上下文（上下文召回），以及混进来多少无关片段。生成质量看结论是否被这些片段支持、有没有漏掉要点、格式是否可用。

张力在于：多送几段能提高证据在场的概率，也会带来干扰，模型可能抓住错误的那段，或在长上下文中部漏掉正确的那段。做法是先固定 token 预算，把重排后的条数调到「标准证据进得来、无关片段尽量少」，然后再改排列和生成指令。

上下文召回高、回答仍不受支持，就改排列、压缩和「紧扣片段、否则拒答」的指令。上下文召回低，继续改生成提示词没有意义。更强的模型会掩盖一部分检索漏洞，所以换模型之后仍然要看检索指标。

高风险问题上，没有证据就拒答。用参数记忆把缺口说圆，生成看起来完整，任务其实是错的。

### 9. ReAct 框架在实际项目中的应用案例？

**参考答案**

一个典型案例是售后资格判断。用户说「上周买的耳机右耳没声音，能退吗」。模型不能直接答应。

1. Thought：需要订单和退货规则，两者都还没有。
2. Action：按当前用户和商品线索查订单。
3. Observation：运行时返回订单 123，五天前签收。这一段由工具写入。
4. Thought：签收时间已有，还要看该 SKU 的规则。
5. Action：查询退货规则。
6. Observation：签收七天内的质量问题可以退。
7. Thought：条件满足，但退款是写操作，生成确认内容，等待用户点头。

最终回复只转述这两次回执，并请用户确认。确认前的工具列表里没有退款接口；确认后由状态机带着幂等键调用。

这个案例里 ReAct 的价值是：每一步缺什么是显式的，观察结果会改写下一步。需要防的是死循环查同一个订单、模型自己编写 Observation，以及在 Thought 里就把「已退款」说出去。步数上限到了仍缺规则时，回复改为无法确认，并转人工。

自己的项目换成真实的只读查询和写操作即可，节拍保持「先取证，再承诺」。

### 10. 多轮对话中如何处理话题切换和上下文丢失？

**参考答案**

每个未完成任务是一帧：意图、槽位、阶段、待确认动作。用户明确换话题，或新句子的意图已经对不上当前帧时，把当前帧压栈，为新话题新建一帧。槽位跟帧走，不能把上一单的订单号继承到新问题里。用户说「接着刚才那个」，再弹回栈顶。栈要有深度上限。

代词只在当前帧的实体里绑定。绑定不上就追问，不能由模型挑一个看起来最近的 id。

上下文丢失多数出在压缩。摘要只压缩原文；已确认槽位、权限和未完成的确认单放在结构化字段里，摘要步骤不许改它们。话题切走后，上一题的工具原文从窗口里拿掉，需要时重新调用，避免旧回执被当成这题的事实。

检测可以用意图结果的变化，加上当前句和活动帧实体是否对得上。只靠向量距离判断「是不是新话题」容易误伤补充条件的句子，补充槽位应先尝试写入当前帧。

### 11. 长期记忆和短期记忆在 AI Agent 中的实现方式？

**参考答案**

短期记忆就是会话工作集。会话存储（常见是 Redis，并设过期时间）里分开放：最近 N 轮原文、滚动摘要、结构化槽位和阶段。每次模型调用由代码装配，窗口不够时只把更早的原文压进摘要，槽位保持原字段。

长期记忆分成两条写路径。稳定事实用表：`user_id`、键、值、来源、更新时间。用户明确说了偏好或更正时才 upsert，同一键以最新的明确说法为准，用户也可以删除。情节用向量索引保存对话摘要，带时间和主题；检索时必须带 `user_id` 过滤，再按相似度和时间一起选，并限制注入的 token。

程序记忆不进这张向量表。技能说明和工具代码放在仓库里，按任务类型加载，和用户隐私分开。

容易漏的是写入门槛和隔离。每句话都嵌入，记忆会被寒暄污染；不带用户过滤的相似度搜索会串记忆。密钥和完整证件号不进记忆。矛盾时表里的新值优先，向量里的旧摘要不能覆盖它。

### 12. 如何保证 AI Agent 的安全性和可控性？

**参考答案**

安全按层做，核心是限制模型的权力。身份和租户在网关确定，工具按当前阶段给白名单：咨询阶段的 schema 里就没有退款和设备控制。写操作默认停在「待确认」，确认后由代码带幂等键、金额和对象归属校验再发出。模型生成的 SQL、Shell 或任意 URL 不直接执行，查询走有白名单的接口。

用户原文、网页和检索片段都是不可信数据，可以要求模型做某件事。它们不写入系统指令区，也不能借此扩大工具列表。这是 Agent 场景里常见的间接注入。

输出侧脱敏，轨迹审计，工具可以按配置立刻停用。步数、费用和墙钟时间有预算，用户断开时取消尚未结束的模型调用。评测集里要有越权工具、注入和「编造已执行」这几类。

可控指的是转移由状态机决定，同一输入的轨迹能回放。若工具会驱动物理设备，参数必须落在设备侧允许的范围内，急停不经过模型。对话状态机取消不了已经提交的外部副作用，那种情况要查回执再用补偿接口。

### 13. 了解哪些 AI Agent 部署和监控工具？

**参考答案**

部署和监控看的是一次任务能不能追踪，进程活着只是前提。

部署上，编排服务无状态、多副本，会话和检查点放在外部存储。模型用托管 API，或用 vLLM 一类的推理服务自己托管。提示词版本、工具白名单和模型名作为可回滚配置发布。多供应商时可以用 LiteLLM 这类网关统一做鉴权、超时和切换。

监控上用 OpenTelemetry 把入口、模型、检索和工具串成一条 trace。轨迹产品常见的是 Langfuse、LangSmith、Arize Phoenix，选一个能按会话看步骤的即可。指标包括任务成功率、工具失败率、步数、token、费用和延迟分位。告警要能跳到某一次 trace。

发布前用固定任务集重放，工具可以是 promptfoo、RAGAS（看检索与忠实度）或自写的状态断言。HTTP 200 只能说明服务返回了，任务仍可能是错的。日志里的证件号、密钥和完整工具回执要脱敏。

### 14. 在团队中如何协调 AI 模型工程师和软件工程师的工作？

**答题思路**

用契约把两边的工作接上，避免「这是模型问题」和「这是工程问题」来回传。

1. 先写清接口：工具的输入输出 schema、错误码、延迟预算、谁可以调用，以及终态由哪个字段表示成功。
2. 分工：模型工程师对检索命中、工具选择和回答是否忠于证据负责；软件工程师对鉴权、幂等、超时、状态转移、发布和回滚负责。提示词变更走和代码一样的评审。
3. 共用一套轨迹和坏例评审。每周看失败步骤，而不是各看各的离线分数。
4. 联调用录制好的工具回执，不把生产写接口当调试环境。
5. 模型升级或提示词改动，必须重跑同一评测集再生效。没有这条约，协调会变成上线后对事故。

如果团队没有这么拆角色，就按「谁改提示词、谁改工具网关、谁对线上任务成功率负责」来讲你实际的配合方式。

### 15. 手写算法：实现一个简单的对话状态管理器

**参考答案**

用一个确定性状态机管理阶段，模型只产生事件。阶段是 `idle → collecting → confirming → executing → done`。槽位只接受白名单字段。槽位第一次凑齐时生成幂等键；用户改了槽位就换新键；执行失败退回 `confirming`，键不变，重试不会变成另一次提交。`execute` 在用户确认后才非空，真正的写操作由调用方去做。

`executing` 期间不再接受修改。此时取消也不能把状态直接清空，因为工具可能已经发出，要等回执再补偿。每步时间 O(槽位数)，空间 O(槽位数)。

```python
import uuid

REQUIRED = ("order_id", "reason")


class DialogManager:
    """阶段和槽位由代码维护。确认前不会产生可执行动作。"""

    def __init__(self):
        self.stage = "idle"
        self.intent = None
        self.slots = {}
        self.idempotency_key = None

    def on_event(self, event: str, data: dict | None = None) -> dict:
        data = data or {}
        if event == "cancel":
            if self.stage == "executing":
                return self._view("执行已经提交，请等待回执", None)
            self._clear()
            return self._view("已取消", None)

        if event == "start":
            if self.stage not in ("idle", "done"):
                return self._view("当前事项未结束，请先确认或取消", None)
            self._clear()
            intent = (data.get("intent") or "").strip()
            self.intent = intent or None
            self._merge(data.get("slots"))
            self.stage = "collecting"
            return self._collect_or_confirm()

        if event == "inform" and self.stage in ("collecting", "confirming"):
            self._merge(data.get("slots"))
            self.stage = "collecting"
            return self._collect_or_confirm()

        if event == "confirm" and self.stage == "confirming":
            self.stage = "executing"
            action = {
                "intent": self.intent,
                "slots": dict(self.slots),
                "idempotency_key": self.idempotency_key,
            }
            return self._view("已确认，等待执行结果", action)

        if event == "tool_result" and self.stage == "executing":
            if data.get("ok"):
                self.stage = "done"
                return self._view("已完成", None)
            self.stage = "confirming"
            return self._view("执行失败，可以重试", None)

        return self._view("当前状态不接受该操作", None)

    def _merge(self, incoming: dict | None) -> None:
        changed = False
        for key, value in (incoming or {}).items():
            if key in REQUIRED and value and self.slots.get(key) != value:
                self.slots[key] = value
                changed = True
        if changed:
            self.idempotency_key = None

    def _collect_or_confirm(self) -> dict:
        if not self.intent:
            self.stage = "collecting"
            return self._view("还需要确认要办理的事项", None)
        missing = [key for key in REQUIRED if not self.slots.get(key)]
        if missing:
            self.stage = "collecting"
            return self._view("还需要：" + "、".join(missing), None)
        if self.idempotency_key is None:
            self.idempotency_key = uuid.uuid4().hex
        self.stage = "confirming"
        return self._view("请确认是否提交", None)

    def _clear(self) -> None:
        self.stage = "idle"
        self.intent = None
        self.slots = {}
        self.idempotency_key = None

    def _view(self, reply: str, execute: dict | None) -> dict:
        return {
            "reply": reply,
            "stage": self.stage,
            "intent": self.intent,
            "slots": dict(self.slots),
            "execute": execute,
        }
```

白名单之外的字段，例如模型顺手写上的金额，不会进 `slots`。金额应由工具回执决定。

### 1. 自我介绍

**答题思路**

三面时间会花在架构和取舍上，开场控制在半分钟到 1 分钟。

1. 角色和年限，强调你负责过的系统边界，而不是框架名单。
2. 一个项目用两句说完：什么任务、你做的架构决定是什么。例如状态外置、写操作确认、检索独立成服务。
3. 补一个取舍：当时没有把系统拆成多个自由 Agent 的原因，或已经拆开的那条边界。
4. 结尾留一个规划问题：如果流量或任务种类上去，你先扩哪一层。

### 2. 项目介绍（侧重架构设计）

**答题思路**

让面试官能画出图。按层次讲，少讲提示词原文。

1. 接入层：鉴权、限流、流式输出、请求 id。
2. 编排层：状态机、步数预算、检查点。工作者进程里不留会话。
3. 模型层：哪类步骤用便宜模型，哪类才用强模型。
4. 工具与知识层：读接口、写接口、检索各自如何扩容，写接口的幂等键从哪来。
5. 失败域：模型超时、工具失败、检索为空，用户分别看到什么，会不会重试写操作。
6. 同步和异步：多长的任务还占着连接，更长的任务如何改成任务 id 加进度。
7. 若重做，只改一个你确实觉得别扭的接口，并说明当时为什么那样切。

### 3. 如何设计可扩展的 AI Agent 系统架构？

**参考答案**

按「无状态编排 + 外部状态 + 独立的工具面」来扩。加机器和加工具，而不是把一个无限循环的进程垂直堆大。

请求经网关做鉴权、限流和 trace。编排服务把每一步的意图、槽位、待确认动作和工具回执写入会话存储，工作者失败后从最近的检查点继续。模型调用单独走路由：分类和抽槽用便宜模型，规划和开放式生成才用强模型，并设并发上限。读工具可以并行、可以重试；写工具必须带幂等键，并且只能从确认状态发出。检索和记忆独立成服务，编排侧只接收预算内的片段。

长任务返回任务 id，用队列和进度通知，避免一个 HTTP 连接挂住编排副本。动作若作用到物理设备，Agent 只调用有边界的技能接口，速度、力度和急停由设备侧保证，模型不直接下发底层控制量。

难点是状态一致性和扇出。多 Agent 会放大 token 和失败面，只有权限和职责确实不同才拆。可以先在一个代码库里把编排、工具网关、状态三个接口划清，等检索或某个工具的容量曲线和主链路分开再独立扩。检查点和幂等没做之前，水平扩展会把同一次写操作打出多份。

### 4. 在技术选型时，如何评估新技术与稳定的旧技术？

**参考答案**

用同一套任务集比较，不以官方演示为据。看五件事：坏例是否真的变少、尾延迟和费用、失败能不能在轨迹里解释、能不能用开关退回旧路径、团队能不能排障。还要看数据格式和接口会不会被单家实现锁死。

新技术先接一条低风险的只读任务，影子跑或按很小比例切流。旧路径继续承担写操作和高风险动作，直到新路径在评测和值班负担上都过线。回滚不能留下一半已写入的业务数据，所以写操作的幂等和状态版本要在切换前就存在。

没有评测差异，就保持旧实现。能回滚的实验可以快一点；嵌进主状态机、拿不出来的依赖要慢。模型或框架的「新」本身不是收益，只是一个待验证的假设。

### 5. 最近关注哪些 AI Agent 领域的新技术或论文？

**答题思路**

选两条你真能讲 3 分钟的，每条按「问题 → 机制 → 你会怎么用、不会怎么用」说。没读过的论文不要说读过。下面是适合准备的真实方向，挑你能展开的。

1. 工具接口标准化。Model Context Protocol 把工具、资源和提示词变成可替换的接口，Agent 不必绑死在某一个框架的插件上。采用时仍然要在自己的网关里做权限和幂等，协议不会替你完成这两件事。
2. 结果导向的评测。SWE-bench 用真实代码仓库的测试看问题有没有修好，GAIA 用需要推理和工具的题目看最终答案。它们说明评测正从「像不像人」转到「任务完成没有」。准备时要能说出指标的盲区，例如测试通过仍可能改坏无关行为。
3. 可恢复的运行时，以及经典论文里的边界。ReAct 是推理和行动交错的基线。Reflexion 把环境反馈写进后续尝试，只在成功信号可靠时有用，否则会把错误反思越积越多。Tree of Thoughts 在思路上搜索，调用次数高，适合有检查器的规划题，不适合每条客服消息。MemGPT 这一类工作把上下文当虚拟内存来分页，落地时仍然要有结构化槽位，不能只靠摘要。

面试官要的是判断。每条收在「我不会在生产里无限制使用它」。

### 6. 如何学习一门新技术？你的学习方法论是什么？

**答题思路**

用一个小而真的任务当轴，避免先收集一堆框架对比。

1. 写下成功标准。例如「一条带工具的链路，工具失败时状态是对的，并且有三条回归用例」。
2. 只读够用的材料：官方文档、接口说明，必要时加论文的方法节。先不看第二手的全景解读。
3. 做垂直切片：状态、一次工具调用、一次失败、一条评测。故意让工具超时一次，看自己能不能从轨迹里发现。
4. 把不变式写下来。例如确认前不写、回执才能出现在回答里。这些句子比框架名词更值得留下。
5. 能向别人讲清失败模式，才算这门技术学完了这一轮。

若举例，就举你最近真实学过的一项，按这五步讲，不要改成一份通用书单。

### 7. 在 AI Agent 开发中，如何平衡创新和工程稳定性？

**参考答案**

把系统分成稳定核和创新层。稳定核是鉴权、会话状态、工具网关、确认、审计，变更要慢，发布要能回滚。创新层是提示词、检索策略、模型路由和新的规划方式，用开关包住。

新路径先影子运行：执行并记录，用户仍走旧路径。影子结果在同一评测集上不差于旧路径，再按比例切读流量。写操作留在稳定核上，即使规划已经换成实验模型，确认和幂等仍然走旧代码。

实验要有截止日期和砍掉条件，例如两周内任务成功率或尾延迟没有收益就删除分支。长期并存两套循环，故障时无法判断该修哪一条。模型变强会减少格式错误，不会减少越权和重复提交，所以稳定核不会因为换了模型就拆掉。

### 8. 如何带领团队进行 AI Agent 项目开发？

**答题思路**

按「风险边界 → 完成定义 → 节奏」讲，不必编团队人数。

1. 开头写明目标和非目标，并把动作分成只读、需确认、禁止三类。禁止类不要留到联调再争。
2. 完成的定义是：评测集达到约定的任务成功率，轨迹能定位失败，写操作有确认和幂等。演示能跑不算完成。
3. 平台负责 Harness、工具网关和评测；业务任务复用这套运行时，各自复制一套循环会让权限和日志分叉。
4. 节奏上固定看失败轨迹，而不是只看成功演示。排期里留出坏例、观测和灰度，不要按普通 CRUD 估 Agent。
5. 你自己要能读一条轨迹并指出责任层。带队的可信度来自这个动作，不来自术语。

### 9. 如何制定 AI Agent 项目的技术路线图？

**参考答案**

路线图是一串可停止的赌注，每项都有指标、负责人和砍掉条件。

先用坏例和线上信号给失败分类：检索、工具、状态、生成、延迟费用。最大的那一类决定近期只做一条高价值链路，把它做到可灰度，而不是同时铺开十个场景。安全相关的能力，权限、确认、审计、评测，排在体验优化前面。中期让新任务复用同一 Harness 和工具网关。远期才考虑新模态、更深的自主性或多 Agent；前提是评测和回滚已经存在。

每一期写清不做清单。模型能力会改变「自己做还是调用」，所以按季度用同一任务集复核，过期的阶段目标要删。做和物理设备相关的 Agent 时，技能库和安全联锁是独立阶段，语言规划不能绕过它们单独上线。

路线图上的日期是假设。没有停止条件的「研究多 Agent」不算路线图上的一项。

### 10. 在跨部门合作中，如何推动 AI Agent 项目落地？

**答题思路**

落地靠一个真实流程的负责人，而不是靠一份模型能力介绍。

1. 一起圈定一步：Agent 起草或查询，哪一步必须由人点头。先辅助模式，再谈自动执行。
2. 用对方已经在看的指标，例如处理时长、一次解决、差错。模型分数只作为内部诊断。
3. 开发前谈妥数据权限、审计和失败时谁负责。这两件事后补，项目会停在演示环境。
4. 用他们的坏例做每周演示，保留一键退回人工的路径。
5. 范围被要求扩大时，回到路线图的不做清单，用评测和值班成本说明下一期再做。

讲的时候用你真实合作过的角色，例如业务、合规、设备或后端。没有跨部门经历就说明你准备如何和工具提供方定 schema，不要编一个协作项目。

### 11. 如何看待 AI Agent 的未来发展趋势？

**参考答案**

趋势是从一轮对话走向可恢复的长任务：检查点、人工确认节点、可靠的工具回执。提示词仍会变，可复用的部分会落在工具接口和评测上。Model Context Protocol 这类协议让工具不再绑死某一个框架，权限和幂等仍要留在业务网关。

模型侧会继续分工。硬规划和难判断使用更多的推理时计算，分类、抽槽和路由使用更便宜的模型。把强模型用在每一步上，成本和延迟都不划算。

多 Agent 会留在职责和权限真的不同的地方，例如一个只读调查、一个在确认后执行。为了看起来像一个团队而互相聊天，通常只增加 token 和故障点。

记忆会更结构化，并且让用户能看、能删。计算机操作一类的界面 Agent 会增加，但在高风险动作上仍然要受工具白名单约束。和机器人结合时，语言层负责规划，技能库负责执行，安全联锁独立于模型。模型变强会挪动这几层的边界，不会取消确认、审计和急停。

### 12. 手写算法：设计一个简单的 RAG 检索系统（伪代码即可）

**参考答案**

系统分成离线索引和在线检索。索引按文档结构切块，避免从句子或表格行中间切断；块 id 稳定，便于幂等更新，并删掉该文档不再保留的旧块。查询和入库共用一个嵌入函数。

在线侧对原句和改写句分别做关键词检索和向量检索，再用 RRF 按名次融合。RRF 的平滑常数在原论文里通常取 60，用来避免两路原始分数直接相加。融合后的前 20 个才交给重排，重排不能扫全库。问句若做了指代补全，重排用补全后的问句；候选仍包含原句召回的结果，避免改写改错时池子里只剩错误问句。没有候选就拒答。相似度阈值如果要加，必须在标注集上校准，不同查询的原始分数不能横比，所以下面的伪代码不以某个魔法阈值拒答。

离线成本主要是每块一次嵌入。在线是常数次查询嵌入、两次带过滤的 top-N 召回，以及对固定小候选集的重排。额外空间是候选集。

```python
def reciprocal_rank_fusion(rankings: list[list[str]], k: int = 60) -> list[str]:
    """按名次融合。k 是 RRF 的平滑常数，常见取 60。"""
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=lambda doc_id: (-scores[doc_id], doc_id))


def index_document(doc, store, embed) -> None:
    chunks = split_by_structure(doc)
    fresh_ids = []
    for i, chunk in enumerate(chunks):
        chunk_id = f"{doc.id}:{doc.version}:{i}"
        fresh_ids.append(chunk_id)
        store.upsert(
            chunk_id=chunk_id,
            text=chunk.text,
            embedding=embed(chunk.text),
            metadata={
                "doc_id": doc.id,
                "version": doc.version,
                "title_path": chunk.path,
            },
        )
    store.retain_only(doc_id=doc.id, chunk_ids=fresh_ids)


def retrieve(query, store, embed, tenant_id: str, k: int = 5) -> dict:
    rewritten = rewrite_query(query)
    queries = [query]
    if rewritten and rewritten != query:
        queries.append(rewritten)

    filters = {"tenant_id": tenant_id, "active": True}
    rankings = []
    by_id = {}
    for q in queries:
        lexical = store.bm25(q, top_n=50, filters=filters)
        dense = store.vector(embed(q), top_n=50, filters=filters)
        for chunk in lexical + dense:
            by_id[chunk.id] = chunk
        rankings.append([chunk.id for chunk in lexical])
        rankings.append([chunk.id for chunk in dense])

    fused_ids = reciprocal_rank_fusion(rankings)[:20]
    candidates = [by_id[doc_id] for doc_id in fused_ids if doc_id in by_id]
    focus = rewritten or query
    top = store.rerank(focus, candidates)[:k]
    if not top:
        return {"context": "", "citations": [], "abstain": True}

    context = "\n\n".join(f"[{item.id}] {item.text}" for item in top)
    return {
        "context": context,
        "citations": [item.id for item in top],
        "abstain": False,
    }
```

`split_by_structure`、`rewrite_query` 和 `store.rerank` 是边界。生成放在检索之后单独调用，这样上下文召回可以不经过模型就测量。引用 id 出现在回答里，仍然要核对句子是否被该片段支持。

### 13. 在资源有限的情况下，如何优化 AI Agent 的性能？

**参考答案**

先量时间花在模型、检索还是工具上，再动最贵的那一段。

能用规则或一次检索直接回答的请求不要进 Agent 循环。必须进循环时，用便宜模型做分类和抽槽，只有低置信或需要多步规划时才调用强模型。步数和 token 设预算，超预算就降级到固定流程或人工，而不是再加一轮反思。

上下文只留状态摘要、最近几轮和压缩后的证据。稳定的系统提示放在前缀里，便于推理服务做前缀缓存。只读且与具体用户无关的问答可以缓存，键里必须包含权限范围和知识版本，避免把别的租户或旧文档的答案返回去。彼此独立的只读工具并行；写工具不并行。语料嵌入放在离线做。

流式输出降低的是体感等待，不降低总计算量。资源紧的时候，减少步数和缩短上下文，通常比再调一个更大的模型更有效。

### 14. 如何建立 AI Agent 的评估体系和指标？

**参考答案**

体系按层设门禁，共用从真实轨迹里抽出来的任务集。任务按意图和风险分层，并保留失败样本，不要只留演示里的顺利句子。

检索层在不调用生成模型时看上下文召回，以及标准片段的排名。工具层看工具选择、参数是否通过 schema 和业务校验、禁止工具是否被调用。任务层看终态：钱是否退对、查询是否答对、该转人工时有没有转。忠实度看回答中的事实能否对上引用片段或工具回执。运行层看延迟分位、单次成功任务的 token 和费用、工具错误率、步数。安全层单列注入、越权和编造已执行。

离线门禁用夹具工具，发布前必须过。裁判模型只评开放式表述，先抽样和人工标注对齐。线上用同一套切片看接管率、重试率和抽检轨迹，灰度期间旧路径还在，便于比较。

一个准确率会掩盖「检索没找到」「工具参数错了」和「找到了却说错」。仪表盘至少能按意图切到检索、工具和生成这三层。任务集也要版本化，否则换一批题之后的升降无法解释。
