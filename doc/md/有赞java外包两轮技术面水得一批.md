## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「做什么的、做成过什么、为什么能接手」讲。

1. 一句话：年限、Java 后端、订单或库存这条链路。教育经历不用展开。
2. 只留一个你最熟的电商项目：用户是谁、你负责哪一段。量级用记得住的数量级，记不清的百分比不要编。
3. 主动埋两个后面会被挖的点，例如库存扣减、超时关单、重复下单。这场面试大概率顺着这两处问。
4. 收尾对准外包：能独立把一条写链路讲清楚，也能在出问题时定位。

框架名词扫一遍即可，不要换成技术栈清单。

### 2. 项目介绍

**答题思路**

用 3 分钟讲清楚一个真实系统。重点放在你做过的技术决策上。

1. 业务：系统解决什么问题，上游是谁，下游是支付、库存还是履约。
2. 架构：入口、核心服务、MySQL、Redis、消息队列，用四五句话画出来。订单和库存是不是同一个库，这里就说清。
3. 你的角色：挑一个难点，讲约束、你的做法、另一个做法为什么没选。库存预占、消息补偿、慢 SQL 都可以。
4. 结果：超卖、超时、错误率停在什么程度。没有监控数字就说现象是否还在，不编精确百分比。

介绍结束时刻意留口：状态怎么迁、失败了谁重试、怎么确认没有写两笔。没做过的细节直接说边界。

### 3. 说说你们电商系统的订单流转流程，从下单到支付到发货

**答题思路**

按时间顺序讲一条订单的状态，用你们系统里的真实状态名。先说你负责下单、支付还是履约，没做过的那段讲到交接为止。

1. 下单：校验用户、地址、商品可售。价格在服务端按活动重算，写入订单快照，不使用页面传来的金额。订单和明细放在同一个本地事务，生成订单号，状态到待支付，并投一条延迟消息做超时关单。库存是下单预占还是直接扣减，用你真实的那种讲。
2. 支付：向渠道下预支付单。回调先验签，再核对订单号和金额。更新条件是「状态仍为待支付」，成功后改为已支付。同一笔回调来多次，返回第一次的成功结果。支付渠道在外部，这段不要包进跨服务大事务。
3. 发货：已支付后把履约消息交给仓库或商家。写下物流单号，状态改为已发货。用户确认或超时后变为完成。积分、搜索、短信跟着消息走，不堵在下单接口里。
4. 分支：用户取消和超时未支付要释放预占，释放按订单号幂等。关单任务和支付成功回调会碰到一起，关单前以渠道查询为准；已经支付成功的单走退款，不关成取消。
5. 收尾留三个可追问的点：幂等键放在哪、库存扣在下单还是支付、回调失败靠谁补偿。

### 4. 库存扣减怎么设计的？超卖怎么处理?

**参考答案**

超卖来自「先读库存再扣减」不是原子操作，两个请求会同时看见最后一件。

普通商品以数据库条件更新为最终依据：

```sql
UPDATE sku_stock
SET available = available - ?
WHERE sku_id = ?
  AND available >= ?;
```

影响行数为 0 就是库存不足。InnoDB 会锁住这一行，同一 SKU 的更新串行执行。再写一条扣减流水，对 `(sku_id, order_id)` 做唯一约束，重试不会扣第二次。

秒杀和热点 SKU 在数据库前面加一层 Redis。用 Lua 在一次执行里判断库存并 `DECRBY`，失败立刻返回。预扣成功才创建订单；数据库更新失败要把 Redis 加回去，加回同样带着订单号，避免加两次。未支付超时和用户取消走同一条幂等释放。

热点行会把锁等集中到一行。可以把库存分成多段，每段独立原子扣减，下单时选一段；某一段空了再试另一段。所有请求共用一把分布式锁能避免超卖，但锁本身会变成排队点。

已经超卖时，先停售，再拿订单和库存对账。优先取消未支付订单，已支付的走退款，并留下告警。

### 5. Redis在电商里怎么用的？缓存穿透、击穿、雪崩怎么解决?

**参考答案**

电商里 Redis 承担两类事：读多写少的加速，以及短临界区的计数。商品详情、类目、会话、购物车适合缓存。库存预扣、限流、幂等键、分布式锁用的是它的原子操作。订单状态和支付结果以数据库为准，Redis 只做加速或预扣。

三个故障指的不是同一件事。

穿透是在查一个本来就不存在的数据，缓存永远不会命中，请求每次打到数据库。先校验入参。对确定没有的 key 缓存一个短 TTL 的空值，新数据写进来时删掉这个空值。布隆过滤器适合 key 空间很大的时候：它说没有就可以直接返回；它说可能有，仍然要查缓存和数据库。

击穿是热点 key 到期的那一下，大量请求同时回源。峰值上的热点用逻辑过期：值先返回，只放一个请求去刷新。普通 key 可以用互斥锁，让一个请求查库，其他请求短暂等待。

雪崩是大量 key 在同一时刻失效，或者 Redis 不可用，流量一起打到数据库。同一批写入的 key 把 TTL 打散。另外准备本地缓存、限流和降级，Redis 故障时保住下单，先关掉推荐这类非必要读。热点数据在大促前预热，避免开场全部未命中。

### 6. MySQL分库分表做过吗？分片键怎么选的？

**参考答案**

做过就按真实查询讲你选的键。没做过就讲选型，不要编一个已经上线的分片方案。

字段过多、更新互相打架，先做垂直拆分。单表行数让索引、备份、变更都难做时，再水平分片。分片键要同时满足三件事：大多数查询都带得上它，数据分布均匀，下单这种事务不要跨分片。

面向买家的「我的订单」用买家 id。面向商家的后台用店铺 id。两条都是主路径时，交易表按主路径分片，另一条用异构表或搜索，不在交易库上跨分片扫描。按创建时间分片，写入会集中在最新的一片。

订单和明细使用同一个分片键，创建订单才是单分片本地事务。订单号里带上分片基因，例如买家 id 取模后的固定几位。这样按订单号也能算出落在哪一片，不必先查一张全局映射。主键在应用侧用号段或雪花算法生成。

扩容时，分片数取 2 的幂，按取模划分，翻倍时数据只迁到新增的一半。跨分片的管理端分页和统计放到异构索引里做。

### 7. 消息队列用的啥？Kafka还是RocketMQ?怎么保证消息不丢失?

**参考答案**

订单超时、支付后通知履约，用 RocketMQ 更贴业务：它有延迟消息和事务消息。开源 4.x 的延迟是固定档位，不能答应任意延迟，除非集群版本支持定时消息。日志、埋点和大流量流水更常见 Kafka。讲你实际上用的那一个。

不丢要生产、Broker、消费三段一起做，得到的是至少一次，重复要靠业务键消化。

生产侧同步发送并确认结果。Kafka 使用 `acks=all`，主题至少两个同步副本，这样只剩 leader 时生产会失败而不是假装成功；开启生产者幂等，避免重试在分区里写出重复记录。RocketMQ 同步发送成功表示 Master 已接受。要扛 Master 宕机还要同步复制，要扛掉电还要同步刷盘，吞吐会下降。

数据库和消息之间还有一个洞：订单已提交、消息还没发出，进程退出，消息就没了。用 RocketMQ 事务消息，或同一本地事务里写本地消息表：先发半消息或先记下待发送记录，再提交本地事务，结果未知时按数据库状态反查。

消费侧处理成功再确认。Kafka 不要把消息丢进线程池后就继续 `poll`，否则位点已经提交、库还没写上。RocketMQ 业务失败就稍后重试，多次失败进死信。消费者按订单号做幂等。对账负责把死信和极端丢盘补回来。

### 8. 分布式事务怎么搞的？TCC还是Seata?

**参考答案**

订单主链路多数不用一个全局事务包住所有服务。支付渠道在外部，XA 包不住。每个服务用本地事务保证自己的库正确，跨服务用可靠消息做到最终一致，再用对账补洞。

TCC 是模式，Seata 是框架。Seata 里有 AT、TCC、Saga 和 XA。问二选一时，先把模式和框架分开。

TCC 把动作拆成 Try、Confirm、Cancel。库存场景里 Try 冻结，Confirm 把冻结转成实扣，Cancel 释放冻结。三个接口都按业务单号幂等。Cancel 可能比 Try 先到，这时空回滚也要成功，并记下标记，拦住随后才到的 Try。TCC 适合必须先占住库存或余额的场景，业务代码要写三套。

AT 由 Seata 解析 SQL，在业务库记前后镜像和 `undo_log`，全局提交后删除日志，回滚时按镜像补偿，并用全局锁挡住脏写。业务表要有主键，接入时代码改动少。全局事务提交前，其他事务可能已经读到这次写入；需要按已提交来读时，用 `SELECT FOR UPDATE` 去拿全局锁。行冲突高的热点库存不适合靠 AT 锁住大量行。

没上过 Seata，就讲本地消息表和幂等消费。不要把框架说成已经在生产使用。

### 9. JVM内存结构说一下，线上OOM怎么排查？

**参考答案**

JDK 8 及以后，按线程私有和进程共享来记。

私有的是程序计数器、Java 虚拟机栈、本地方法栈。虚拟机栈里是栈帧、局部变量和操作数栈。栈帧太深抛的是 `StackOverflowError`。每个线程都占一块栈，线程过多会把内存吃掉。

共享的是堆和元空间。对象实例在堆上；分代收集器里通常有 Eden、两块 Survivor 和老年代。JDK 8 默认 Parallel GC，JDK 9 起默认 G1，这块划分还在。类元数据在元空间，使用本地内存，替代了 8 之前的永久代。直接内存不占堆，NIO 和 Netty 用它；不单独设置上限时，通常和堆上限同一量级。

排查先看报错类型，再决定看哪块内存。

1. `Java heap space` 或 `GC overhead limit exceeded`：打开 OOM 时自动 heap dump，并保留 GC 日志。GC 之后占用还持续上涨，按泄漏查，用支配树找到被静态集合、缓存或 `ThreadLocal` 拽住的对象。GC 能回收、只是峰值不够，那是流量或单次查询太大。
2. `Metaspace`：看类加载器数量和动态生成的类，常见于热部署或代理类泄漏。
3. `Direct buffer memory`：看直接内存计数和网络框架的分配器。
4. `unable to create new native thread`：看线程数、`-Xss` 和容器的进程数上限。
5. 容器把进程杀掉时，退出码常常是 137，Java 日志里可能没有 OOM。堆、元空间、直接内存和线程栈的总和要小于容器限制。

### 10. 线程池核心参数，你们业务里怎么配的?

**参考答案**

`ThreadPoolExecutor` 有七个参数：核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。

执行顺序是：线程数小于核心线程数就建线程；达到核心线程数后任务入队；队列满了并且还没到最大线程数，再建线程；仍然放不下就拒绝。最大线程是队列满了之后才用的。队列没有上界时，最大线程数不会生效。`Executors.newFixedThreadPool` 就是这种队列；`newCachedThreadPool` 使用不存放任务的同步队列，线程数会一直往上长。

超过存活时间会被回收的，是核心线程数以上的空闲线程。核心线程默认保留，除非打开 `allowCoreThreadTimeOut`。

拒绝策略里，Abort 抛出 `RejectedExecutionException`；CallerRuns 退回调用线程执行；Discard 丢掉新任务；DiscardOldest 丢掉队列里等得最久的任务，正在跑的任务还在。订单类任务使用有界队列加 Abort 或自定义拒绝，让接口明确失败。CallerRuns 若发生在 Web 线程上，慢任务会占住请求线程。

业务上按任务分开建池，下单、通知、对账不共用。IO 型线程数可以大于核数，但不要超过下游连接池撑得住的并发，否则线程都堵在借连接上。CPU 型接近核数。`线程数 ≈ 核数 × (1 + 等待时间 / 计算时间)` 只是估算起点，再看队列长度、拒绝次数和耗时调整。线程名字带上业务。记不清线上那个具体数字，就讲这套取舍。

### 11. Spring Cloud微服务之间调用，Feign超时怎么处理?

**参考答案**

每个下游单独设置连接超时和读取超时。连接超时表示没有连上；读取超时表示请求已经发出，响应没有在时限内回来，服务端可能仍在处理。创建订单这种接口在读取超时后不能直接再打一次，除非原来的请求有幂等键。

超时要嵌套：被调方短于调用方，调用方短于网关。调用方先放弃、被调方还在写，再叠加重试，就会出现重复订单和线程堆积。

Spring Cloud OpenFeign 默认不再次重试。使用 Ribbon 或 Hystrix 的老版本里，这两层自己的超时常常只有 1 秒，会先于 Feign 把调用掐断。底层换成 Apache HttpClient 或 OkHttp 之后，核对真正发请求的客户端用的是不是另一套超时。

处理上，读超时把失败返回给上游或走明确的降级，并把线程还回去。连续超时触发熔断，避免把下游打得更慢。核心下单失败就告诉用户失败。日志里留下目标服务、接口和耗时，方便和下游的慢调用对齐。查询类接口可以有限次换实例重试；写接口只在幂等之后重试。

### 12. 接口幂等性怎么保证?重复下单怎么防?

**参考答案**

幂等是指同一个业务请求执行一次和多次，留下来的业务状态相同。重复下单来自连点、超时重试，以及异步创建时的消息再投。

幂等键必须稳定。用「用户 + 客户端令牌」，或者预下单时发给页面的 token。同一次下单的所有重试共用这个键，每次点击都换新键就防不住。

数据库做最终裁决。幂等记录和订单放在同一个事务里，对幂等键建唯一索引。键冲突时查出已经创建的订单，把原来的订单号返回去。先查再插仍有并发窗口，两次请求会同时看见「还没有」。Redis `SETNX` 只能挡住键还在的那一段，过期或故障之后仍然靠唯一索引。

状态迁移写成条件更新，例如只有待支付才能改成已支付，重复执行不会再推进一步。前端禁用按钮可以减少连点，不能代替这套约束。

异步下单时，消费者也按同一个订单号或幂等键去重。重复请求要返回第一次的成功结果，返回「请勿重复提交」会让客户端继续重试。

### 13. 手写算法：反转链表

**参考答案**

用三个指针原地反转。`prev` 一开始为空，`curr` 从头结点走。每次先记下 `curr.next`，再把 `curr.next` 指向 `prev`，然后两个指针一起前进一步。循环结束时 `prev` 是新的头结点。

空链表和只有一个结点时，循环不改指针或只走一步，结果仍然对。先保存 `next`，否则原链表会断。时间 O(n)，空间 O(1)。递归也能反转，递归栈是 O(n) 空间。

```java
public ListNode reverseList(ListNode head) {
    ListNode prev = null;
    ListNode curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

### 2. 深挖项目，你们秒杀系统怎么设计的？流量怎么削峰？

**答题思路**

讲你真实做过的秒杀，按「请求从哪进来、在哪被扔掉、库存在哪扣、订单在哪创建」说。没做过分层里的某一层就跳过，不要把方案补成自己的上线经历。

1. 先界定场景：固定开售时间、少量 SKU、读远多于写、峰值很短。和普通下单分开讲。
2. 进服务之前：商品页静态化；开售时间以服务端为准；资格或预约把人打散；网关按用户和活动限流。
3. 削峰：只放进与库存和下单能力相称的请求。预约令牌或队列把峰值拉平，消费者按数据库撑得住的速度创建订单。其余请求马上返回售罄或排队中。队列要有上限，否则峰值只是从数据库搬到了内存。
4. 扣库存：Redis Lua 判断并扣减。售罄后在应用里留下短时标记，挡住后续请求。扣减成功再投递下单消息。数据库条件更新再校验一次，失败就把 Redis 加回去。
5. 一人一单：用户加活动做唯一约束。重复消息按订单号当成功。
6. 准备四个追问：Redis 成功但数据库失败、少卖、队列积压了怎么扩、为什么不用一把大锁把所有人串起来。锁会把热点请求排成一条队，原子扣减加有界队列才对得上这个峰值。

### 3. 热点数据怎么处理？比如双十一爆款商品频繁查询

**参考答案**

爆款查询打满的是某一个缓存分片，不是整座集群。Redis 集群里一个 key 只落在一个分片，读再多也在那个分片的主线程上。

1. 开售前按活动名单把详情写入 Redis，并预热到各实例的本地缓存。开场如果全部未命中，数据库会先被打满。
2. 应用内用短 TTL 的本地缓存吃掉大部分读。本地缓存和 Redis 可以差几秒。能不能卖，以下单时的扣减结果为准。
3. 仍打到 Redis 的读，把详情复制成多份 key，请求散列到不同分片。份数够让单个分片离开打满即可。库存不能复制成多份各自乱写；库存要分段，每段单独扣。
4. 热点 key 不在峰值整点用硬过期。值里放逻辑过期时间，过期后仍返回旧值，只允许一个请求回源。同一时刻对同一个 key 的回源合并成一次。
5. 标题、主图能静态化的放到 CDN。价格和库存在下单接口再查，不拿详情页缓存去扣减。

### 4. ES在电商里用在哪？商品搜索怎么做分词和排序的？

**参考答案**

商品搜索、运营后台的多条件订单查询、搜索联想，适合放 Elasticsearch。它是近实时索引，默认大约一秒刷新一次，不能当作库存和支付的事实来源。

中文分词要用插件，常见的是 IK。内置的 cjk 只是按两个字切开。索引用细粒度，搜索用粗粒度：文档里的词尽量齐，查询不要被切得太碎，否则不相干的商品也会被召回。品牌、类目、SKU、上下架状态用 keyword 做过滤和聚合，不参与分词。同义词和拼音可以加，但要收着同义词表，避免一个词打中两个类目时没有类目条件。

相关性默认按 BM25 打分。电商排序不会只靠文本分。匹配放在 query 里算分，类目、价格区间、上下架放在 filter 里，过滤不参与评分。再用 function_score 叠上销量、上架时间、是否有货、店铺权重。有货可以直接过滤，也可以只降权，这是产品取舍。深分页不用很大的 from，默认窗口也就一万条，翻页用 search_after。

### 5. MySQL索引失效场景有哪些?联合索引最左匹配原则举例

**参考答案**

先分开两件事：优化器根本不能用这棵索引，以及它能用但判断全表扫描更便宜。用 `EXPLAIN` 看 `type` 和 `possible_keys`，用 `SHOW WARNINGS` 看语句有没有被改写。

索引用不上的常见情况：

1. 索引列上套函数或做计算，例如对时间列取日期再比较。
2. 字符串列和数字比较。优化器会转换这一列，列上的索引用不上。数字列和纯数字字符串比较，一般仍能用索引。
3. `LIKE '%关键字'` 这种前导模糊匹配。
4. 联合索引没有从最左列开始连续使用。
5. 关联两边的字符集或排序规则不同，条件被改写成转换。
6. `OR` 的一侧没有可用索引。

表很小、选择性很差、统计信息过期时，优化器会放弃索引，即使 `possible_keys` 里有它。`!=` 和 `NOT IN` 是否走索引取决于行数估计。InnoDB 的二级索引包含 NULL，`IS NULL` 可以用索引。

最左匹配看的是索引定义的顺序，不是 SQL 里条件的书写顺序。索引 `(a, b, c)` 时，`WHERE b = 2 AND a = 1` 仍然用到 `a` 和 `b`。

```sql
-- 用到 a, b, c
WHERE a = 1 AND b = 2 AND c = 3

-- 用到 a, b
WHERE a = 1 AND b = 2

-- 只用 a 收窄范围；c 不能跳过 b，但扫描索引时可以顺带过滤 c
WHERE a = 1 AND c = 3

-- 经典规则下不能用 (a, b, c) 做查找
WHERE b = 2

-- a 已经是范围，b 不能再收窄查找起点
WHERE a > 1 AND b = 2
```

`WHERE a = 1 AND b = 2 ORDER BY c` 可以靠这棵索引避免排序。`b` 一旦变成范围，后面的 `c` 就不再有序。MySQL 8.0.13 起有跳跃扫描：前导列取值很少、条件里又没写它时，优化器仍可能使用这棵索引。这是例外，最左原则本身还在。

### 6. 分布式锁用Redis还是Zookeeper?各自优缺点

**参考答案**

短临界区、后面还有数据库唯一约束，用 Redis。选主、配置变更、不能同时有两个写入方，用 ZooKeeper 或 etcd。库存正确性靠原子扣减，不靠这把锁。

Redis 加锁用 `SET key requestId NX PX ttl`，value 是这次请求的唯一标识。释放时用 Lua 比较标识再删除，避免删掉别人刚拿到的锁。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

过期时间要盖住临界区，执行时间长就续期。进程停在长时间 GC 里，续期也不会发生，锁过期后第二个请求能进来。主从如果是异步复制，Master 宕机后新 Master 上可能没有这把锁。多节点 Redlock 也处理不了长时间停顿。怕两个写入都成功时，数据库用版本号或唯一键拒绝后到的那个持有者。

ZooKeeper 用临时顺序节点。客户端只监听序号比自己小的前一个节点，会话断开后节点消失，写入经过共识才算成功，主从切换时不容易出现两把锁。代价是延迟更高，依赖 ZK 集群；会话超时之前，旧持有者可能还在执行。所有客户端都去监听父节点，会在释放时惊群。

Redis 快，极端情况下会放进两个客户端。ZooKeeper 更稳，也更重，适合低频协调，不适合每个下单请求都去抢一次。

### 7. CAP理论说下，你们系统更倾向AP还是CP?

**参考答案**

CAP 讨论的是网络分区已经发生时的选择：不能同时让每个请求都拿到强一致的数据，又让所有分区都继续提供服务。分区在分布式系统里会发生，所以要决定的是分区期间保一致性还是保可用性。没有分区时，系统可以又一致又可用。

ZooKeeper、etcd 这类系统分区时让少数派停止写入，保住一致，偏 CP。缓存和一些注册中心分区时继续读写，可能读到旧值，之后再收敛，偏 AP。

电商不是整站一个字母。商品详情和搜索差几秒可以接受，分区时页面仍要打开，这条读路径偏 AP。扣库存、支付结果、订单状态不能在不确定时返回成功；分区时宁可下单失败，也不超卖、也不出现付了款没有订单。写路径偏 CP，或者做成有事实来源的最终一致，事实来源是支付渠道的账单和自己的订单表。

回答时把浏览和交易分开说，并指明哪一个存储是事实来源。

### 8. AI相关：有没有用过LLM辅助开发？比如写代码或者做数据分析

**答题思路**

按真实经历回答用过或没用过。用过就讲一个你真用过的工具和一次具体任务；没用过就说你打算怎么用。不要编一段日常工作流。

1. 任务：样板代码、单测草稿、解释一段报错、根据表结构写 SQL 草稿。数据分析先给字段含义和脱敏后的小样本。
2. 验收：自己读 diff，跑编译和测试。金额、库存、权限、事务边界逐行看。SQL 先在小范围对结果，再放到真实环境。
3. 边界：生产数据、密钥、用户隐私不贴进对话框。方案你自己定，模型负责起草。
4. 追问例子时，重点讲你改掉了它哪一处，而不是它生成了多少行。

### 9. 你们团队Code Review怎么做的？遇到代码冲突怎么解决?

**答题思路**

按团队里真实发生的流程讲。没有成文规范，就讲仓库里实际怎么合并，不要编一套没人执行的制度。

1. 合并请求尽量小，说明意图、影响面和怎么验证。一次改动只做一件事。
2. 评审看正确性、事务和幂等、SQL 和索引、失败以后怎么办、测试有没有覆盖这次改动。格式交给格式化工具。
3. 找熟悉这块代码的人看。核心链路至少一个人通过，CI 通过再合。意见写到哪一行、什么输入会错。
4. 请求不要挂很多天。

代码冲突分开处理：

1. 先把主干合进来。冲突是两边改了同一处文本，逐段看意图，合完编译并跑相关测试。
2. 锁文件和生成代码重新生成，不手改一半。
3. 两边改的是同一条业务规则时，先和作者对齐再决定留哪边。能编译只说明语法通过。
4. 分支拉得越久越容易冲突。小步合并能减少这种事。

### 10. 系统性能瓶颈怎么定位？从哪几个维度分析？

**参考答案**

先确认是哪一个接口、从什么时候变慢，再把时间拆开，最后看哪一个资源先饱和。

1. 症状。看 QPS、P50、P99、错误率，以及有没有发布或配置变更。P50 和 P99 一起变坏，主路径上的必经依赖很可能变了。只有 P99 变坏，优先看锁、队列、GC 和重试。
2. 时间拆分。有链路追踪就按 span 排序。没有就看访问日志里的分段耗时，和同一分钟的慢 SQL、Redis 慢日志对齐。
3. 饱和。应用看线程池队列、GC 停顿和锁等待；数据库看连接池等待、行锁和慢查询；Redis 看单个分片的 CPU 和大 key；消息看积压；机器看 CPU 节流、磁盘和网络。整机 CPU 不高，不代表 Redis 那个核或者数据库连接池还有空。
4. 常见根因按证据对上再改：缺索引、热点行锁、连接池和下游不匹配、缓存失效后回源、超时重试把一次慢调用乘成多次、同步刷盘的日志。
5. 一次只改一个点，用同一组图确认。扩容放在已经确认是容量之后。

### 11. 最近在看什么技术书？怎么保持学习的?

**答题思路**

只讲最近真的在看、并能说出一个章节的材料。官方文档、一次故障后的笔记也算。不要临时报一本没翻过的经典。

1. 书或文档的名字，为什么最近看它。最好和你做的订单、库存、MySQL 或 Redis 有关。
2. 一个你记住的点，以及它对照过哪段真实代码或哪次线上问题。用不上就老实说还在看，不编应用经历。
3. 保持学习的方式说一个你真的在做的：故障之后补记录、跟一个版本的变更、把一个机制用小实验跑一遍。频率按真实情况说。
4. 如果对方追问计划，就说下一本和当前项目缺口相关的，而不是列一份书单。

### 12. 手写算法：判断链表是否有环

**参考答案**

用快慢指针。两个指针都从头结点出发，慢指针每次一步，快指针每次两步。快指针走到空，说明没有环。二者相遇，说明有环。

有环时，快指针在环里相对慢指针每步靠近一格，一定会相遇。无环时快指针先到结尾。时间 O(n)，空间 O(1)。也可以用哈希集合记录出现过的结点引用，空间是 O(n)；按结点的值去重会把不同结点当成同一个。

如果继续问环的入口：相遇后把其中一个指针放回头结点，两个都每次走一步，再次相遇的位置就是入口。时间仍是 O(n)，空间 O(1)。

```java
public boolean hasCycle(ListNode head) {
    ListNode slow = head;
    ListNode fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {
            return true;
        }
    }
    return false;
}
```

## HR面

### 1. 自我介绍

**答题思路**

HR 听的是业务和稳定性，控制在 1 分钟以内。

1. 做什么方向、做了几年、最近一段在电商交易里负责什么。公司名点到即可，不展开架构。
2. 一件你独立完成的事，用业务结果说，例如订单、库存、大促支持。不报记不清的数字。
3. 为什么看这个机会：业务和你做过的相近，你能比较快接手。
4. 技术栈一笔带过。职业规划和薪资等对方问到再说。

### 2. 为什么离开上一家公司？

**答题思路**

用一个真实原因，一句说完，后面讲你要什么。

1. 原因保持中性：业务调整、合同结束、想做更完整的交易系统、现有工作技术面太窄。组织调整就说组织调整，不展开人事矛盾，不评价上级。
2. 补一句你已经能独立做的事，不点名前公司的内部项目代号。
3. 接到这个岗位：电商链路和你的经验对得上。
4. 外包面试会关心你能待多久。把到岗时间和你能负责的范围按真实情况说清楚。

### 3. 对加班怎么看？

**答题思路**

把平时和峰值分开，用一次真实经历说明，不表态「来者不拒」，也不把加班说成原则问题。

1. 平时把需求放在工作时间里完成。有值班就按轮换来。
2. 大促、故障和发布窗口可以加班，最好事先知道原因和大概时长。你有过值守，就讲那一次在做什么、结束后怎么恢复。
3. 如果加班变成常态，你会先看是发布节奏还是线上不稳，再和负责人对齐，而不是只答应时长。
4. 可以问他们大促怎么排班、加班如何记录。这题后面经常接着问到岗时间。

### 4. 期望薪资多少?

**答题思路**

现场的数字只来自你自己的收入和这个岗位的职责。不报别人面经里的数，也不报一个没算过的整数。

1. 面试前先统一口径：月薪还是总包，年终、加班费、社保公积金各占多少。外包还要确认合同主体、社保城市和项目周期。
2. 给出一个区间。下限是你能接受的数，上限对应当前这个职责。区间太宽等于没说，一口价又没有交谈余地。
3. 级别和结构还不清楚时，先问级别、固定与浮动的比例，再给区间。
4. 对方往下压时，用独立负责的范围讨论。没有别的 offer，就不要借一个不存在的数。

### 5. 职业规划是什么？

**答题思路**

分两段，都落到这份工作能提供的事情上。不编职级，不说一个没有路径的管理岗位。

1. 近一到两年：独立负责电商里的一条链路，能改方案、能排障、能把订单和库存对上。
2. 再往后：在交易和高并发上做深，能参与方案评审，而不只接单点需求。
3. 和外包的项目周期对齐：先把当前这段做稳。规划如果听起来马上要换方向，会和岗位冲突。
4. 对方问得比较虚时，用你准备深入的一个技术问题收尾，例如库存一致性或链路排查。

### 6. 你觉得自己的优势在哪里？

**答题思路**

准备两个，每个都落到你做过的事。

1. 方向和岗位相关：能把下单、库存、支付的状态讲完；写接口会先处理重复请求和失败补偿；线上问题按监控和日志缩小范围。选你真有例子的两个。
2. 讲法固定：优势一句，一次真实的事，这件事之后现象有没有好转。百分比记不清就不说。
3. 学习能力、沟通能力这种词，要换成一次具体协作，例如和前端约定幂等键、和测试补过某一类重试。
4. 如果接着问缺点，说一个真实的、不直接打掉这个岗位的点，并说明你现在怎么补。

### 7. 还有什么想问我的？

**答题思路**

准备三个，现场问一到两个。问你还不知道、并且影响判断的事。已经讲过的不重复。

1. 小组负责哪块业务，进去之后前几个月接手哪一段，方案是自己设计还是按现成需求改。
2. 大促和值班怎么排，外包同学的发布权限到哪一层。
3. 合同主体、项目周期、薪资结构，如果前面没讲清，可以问。技术栈和代码评审是谁拍板，也可以问。
4. 下一轮见谁、大概什么时候有结果。

不问「我这次过了吗」。
