### 3. Java 中 String 的 intern() 方法了解吗？它有什么作用？

**参考答案**

结论：`intern()` 返回字符串常量池里与当前内容相等的那份引用，让相同内容可以共享同一个 `String` 对象。

字面量在类加载时就会进池。`new String("ab")` 还会在堆上再有一个对象。JDK 7 起常量池在堆中：调用 `intern()` 时，池里已有相等字符串就返回池中引用；没有就把这个堆对象的引用放进池，不再像 JDK 6 那样拷贝进永久代。因此运行时拼出来、池里还没有的字符串，返回的就是原对象；字面量已经在池里时，返回的是池中旧对象，不一定是你 `new` 出来的那个。

它用来节省重复字符串的内存，池化之后也可以用 `==` 比较内容。入池要在全局字符串表上同步。订单号、用户 ID 这类大量不重复的字符串不适合 `intern`，表和堆都会被撑大。

JDK 6 的池在永久代，`intern` 会拷贝一份，这个差异要单独说清楚。

### 4. volatile 关键字的原理是什么？它能保证原子性吗？

**参考答案**

结论：`volatile` 保证可见性和有序性。单个变量的一次读或一次写是原子的，包含 `long` 和 `double`；`i++` 这种读改写不是原子的。

JMM 里，对一个 `volatile` 变量的写 happens-before 之后任意线程对它的读。读者能看到这次写入，也能看到写之前那些已经完成的普通写。编译器不能把 `volatile` 写之前的写挪到它后面，也不能把 `volatile` 读之后的读挪到它前面。HotSpot 在 x86 上，`volatile` 写会落成带 `lock` 前缀的指令，起到 StoreLoad 屏障的作用。

`i++` 仍是读、加、写三步，两个线程会互相覆盖。计数用 `AtomicInteger` 或锁。`volatile` 也不互斥，两段临界区仍可能同时执行。状态标志、双重检查锁里的实例引用适合用它：没有 `volatile` 时，别的线程可能看见非空引用，对象却还没构造完。

按 happens-before 讲即可。不要把它说成「每次读写都锁住总线」。

### 5. 谈谈 Java 中的线程池，核心参数有哪些？如果任务队列满了，会发生什么？

**参考答案**

结论：`ThreadPoolExecutor` 先补满核心线程，再入队，队列满了才把线程扩到最大；最大线程也满了就拒绝。无界队列几乎不会走到这一步。

构造参数有七个：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、时间单位、工作队列、线程工厂、拒绝策略。超过核心数量的线程空闲超过 `keepAliveTime` 会退出；`allowCoreThreadTimeOut` 打开后，核心线程也会退出。

队列满了之后分两种：

1. 当前线程数还小于最大线程数：新建非核心线程执行，不再入队。
2. 已经达到最大线程数：执行拒绝策略。默认 `AbortPolicy` 抛 `RejectedExecutionException`。`CallerRunsPolicy` 让提交者自己跑，形成反压。`DiscardPolicy` 丢掉新任务。`DiscardOldestPolicy` 丢掉队列头再尝试提交一次。线程池已经关闭时，提交同样走拒绝策略。

`Executors.newFixedThreadPool` 用的是无界 `LinkedBlockingQueue`，`maximumPoolSize` 基本不会生效，任务会一直堆到内存出问题。`newCachedThreadPool` 用 `SynchronousQueue`，等价于没有容量，线程会一直扩。生产里用有界队列，并自己规定拒绝后是快速失败还是退回调用方。

`execute` 的异常会抛给工作线程的未捕获处理器；`submit` 把异常放进 `Future`，不调用 `get` 就看不见。拒绝发生在提交时，两种都会被拒绝策略处理。

### 6. JVM 中你知道哪些垃圾收集器？简单描述一下 G1 收集器的工作流程。

**参考答案**

结论：按停顿和吞吐来记。小堆、单线程用 Serial；追求吞吐用 Parallel；G1 从 JDK 9 起是默认，兼顾停顿；ZGC、Shenandoah 面向更低停顿。CMS 已经在 JDK 14 移除。

G1 把堆切成大小相等的 Region，逻辑上仍有 Eden、Survivor、Old。超过半个 Region 的对象进 Humongous，单独占连续 Region。

日常是年轻代回收：停顿，把 Eden 和 Survivor 里的存活对象复制走。老年代占用升到阈值后启动并发标记：初始标记借一次年轻代停顿完成；并发标记和业务线程一起跑，用 SATB 写屏障记住标记开始时的引用；再标记停顿处理这段时间的变化；清理阶段回收完全空白的 Region，并统计每个 Region 的垃圾比例。

之后是混合回收：一次停顿里既收年轻代，也按垃圾比例挑选一部分老年代 Region 复制。挑选多少受 `MaxGCPauseMillis` 约束，默认目标 200 毫秒，这是目标，不是保证。跨 Region 引用记在记忆集里，写屏障有额外开销。复制时没有空闲 Region，会退化为整堆 Full GC；从 JDK 10 起，这次 Full GC 是并行的。

### 7. JVM 的类加载过程是怎样的？双亲委派模型有什么好处？

**参考答案**

结论：类要经过加载、链接、初始化才能使用。双亲委派让核心类由父加载器先加载，避免被应用里的同名类替换，也避免核心类重复加载。

加载把字节流变成方法区数据和一个 `Class` 对象。链接分三步：验证字节码；准备阶段给静态变量赋零值；解析把符号引用变成直接引用，可以推迟到第一次使用。`static int x = 1` 在准备阶段是 0，到初始化执行 `<clinit>` 才变成 1。编译期常量（`static final` 的基本类型或字符串常量）在准备阶段就是最终值，引用它也不会触发类初始化。初始化时父类先于子类。`new`、调用静态方法、读写非常量静态字段、反射、初始化子类，都会触发初始化。

所谓双亲委派，是每个加载器先交给自己的 parent：启动类加载器、平台类加载器（JDK 9 起，原来的扩展类加载器）、应用类加载器，再到自定义加载器。每个加载器只有一个 parent。好处是 `java.lang.String` 这类核心类由启动类加载器加载，应用 classpath 上的同名类不会被用上；类的身份是「全限定名 + 加载器」，核心类只加载一次。

两个应用之间的隔离来自不同的类加载器，不是来自双亲委派。这套顺序是类加载器的实现约定。JDBC 用线程上下文类加载器，让启动类能找到应用里的驱动；Tomcat 的 Web 应用类加载器则先加载自己的类，再交给父加载器。

### 8. Spring Bean 的生命周期是怎样的？

**参考答案**

结论：正常 Bean 的路径是实例化、填充依赖、初始化、使用、销毁。AOP 代理包在初始化之后。

1. 实例化，调用构造器或工厂方法。
2. 填充属性。`@Autowired` 在这一步注入，早于 `@PostConstruct`。
3. 回调 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。
4. `BeanPostProcessor` 的前置处理：先注入 `ApplicationContext`，再执行 `@PostConstruct`。
5. `InitializingBean.afterPropertiesSet()`，然后是自定义 `init-method`。
6. `BeanPostProcessor` 的后置处理。声明式事务和 AOP 的代理通常在这里包上去。
7. 放入容器，可以对外使用。
8. 容器关闭时销毁：`@PreDestroy`、`DisposableBean.destroy()`、自定义 `destroy-method`。

`ApplicationContextAware` 不在第 3 步，它走的是 BeanPostProcessor。`@PostConstruct` 里的 `this` 还不是代理，同类自调用不会进切面。`InstantiationAwareBeanPostProcessor` 如果在实例化前就返回了对象，后面的填充和初始化会跳过，那是短路路径。

### 9. Spring 的事务传播行为有哪些？REQUIRES_NEW 和 NESTED 有什么区别？

**参考答案**

结论：传播行为决定这次调用加入现有事务、另起事务，还是不许有事务。`REQUIRES_NEW` 是另一条物理事务；`NESTED` 是同一条事务上的保存点。

七种：

- `REQUIRED`：默认。有事务就加入，没有就新建。
- `REQUIRES_NEW`：挂起当前事务，新建一条独立事务。
- `NESTED`：当前有事务就建保存点；没有就和 `REQUIRED` 一样新建。
- `SUPPORTS`：有就加入，没有就以非事务执行。
- `NOT_SUPPORTED`：挂起当前事务，自己以非事务执行。
- `MANDATORY`：必须已经在事务里，否则抛异常。
- `NEVER`：必须没有事务，否则抛异常。

`REQUIRES_NEW` 会另取一条连接。内层提交后，外层再回滚也撤不掉；内层回滚不会把外层标记成只能回滚。外层捕获内层异常后，外层仍可以提交。

`NESTED` 依赖 JDBC 保存点，内层「提交」只是释放保存点，真正提交要等外层。内层失败只回到保存点；外层自己捕获异常后可以提交，保存点之后的修改不会留下。外层若回滚，内层做过的修改一起没了。事务管理器不支持保存点时，创建嵌套事务会失败。

默认只有 `RuntimeException` 和 `Error` 会回滚，受检异常会提交，传播行为不改变这条规则。同类自调用不经过代理，传播设置不会生效。`REQUIRES_NEW` 在连接池很小的时候还可能把连接占满。

### 10. Redis 常用的数据结构有哪些？如果要实现一个文章点赞排行榜，你会用哪种结构？

**参考答案**

结论：常用的是 String、Hash、List、Set、ZSet，另外有 Bitmap、HyperLogLog、GEO、Stream。点赞排行榜用 ZSet：member 是文章 ID，score 是点赞数。

`ZINCRBY` 加一，`ZREVRANGE` 取前 N 名，`ZREVRANK` 查某一篇文章的名次。相关命令的复杂度是对数级，适合按分数排序。

ZSet 去不了重。同一用户连点两次，要先用 Set 记录「文章 + 用户」，插入成功才加分；取消赞再减分，并且不要减成负数。用户 ID 又长又稀疏时不要用 Bitmap，位图只适合连续、稠密的编号。

分数相同的 member 按字典序排，不是按点赞时间。若要「先达到的排前面」，得把时间编进 score，同时注意 score 是双精度浮点，编码空间有限。文章很多时按天或板块拆 key，总榜再合并，避免一个 ZSet 无限变大。

### 11. 在项目中用过消息队列吗？Kafka 的消费者组（Consumer Group）机制了解吗？

**答题思路**

用过就讲一条真实链路：什么事件、谁生产、谁消费、重复或丢失会怎样。没用过就直接说没用过，不要临时编一个订单系统。机制按下面的参考答案讲。

**参考答案**

结论：同一个消费者组里，一个分区同一时刻只分给一个消费者，用来分摊流量；不同的组各自消费全量，用来广播。

组由 broker 上的 Group Coordinator 管理，组内一个成员做 leader，负责分配分区。常见分配策略有 Range、RoundRobin、Sticky、CooperativeSticky。Range 按主题各自切分，消费者订了多个主题时容易不均；Sticky 尽量少搬家；协作式再均衡只收回必须移动的分区，避免全组停下来。

消费者加入、退出、心跳超时，或两次 `poll` 间隔太长，都会再均衡。收回分区前提交已经处理完的位移，在 `onPartitionsRevoked` 里做；新分区从已提交位移接着读。位移在内部主题 `__consumer_offsets`。

自动提交跟的是 `poll` 推进后的位点，不是业务处理成功。处理还没做完就再次 `poll`，位点可能已经提交，失败后不会重投。要至少一次，就关掉自动提交，处理成功后再提交，消费端再按业务键做幂等。

并行度的上限是分区数。消费者比分区多时，多出来的会空闲。给重启的实例配置 `group.instance.id`，在会话超时内回来可以不做一次全量再均衡。

### 12. 你了解的 AI Agent 开发框架或工具链有哪些？（例如 LangChain）

**参考答案**

结论：框架负责把模型、提示词、工具和状态接起来。Java 服务优先 Spring AI 或 LangChain4j；流程里有循环、人工确认和断点续跑时，再用状态图。效果、幂等和评测不在框架里。

LangChain 是 Python（也有 JavaScript）里的组件库，把模型、提示、检索和工具拼成链，生态最大，迭代也快。LangGraph 在它旁边用状态图描述循环和分支，可以暂停等人确认，再从检查点继续。LlamaIndex 更偏数据接入和检索。Semantic Kernel 用插件和规划器，覆盖 Java、Python 和 C#。CrewAI、AutoGen 这类偏多代理协作。Dify、Coze 用来快速搭流程，适合验证，不适合当成唯一的生产运行时。

Java 侧，Spring AI 贴着 Spring Boot：`ChatClient`、Advisor、工具方法，能走原来的配置、鉴权和监控。LangChain4j 提供 AI Service、工具、记忆和检索，接口更偏「声明一个代理」。MCP 是接入工具和资源的协议，不是又一个编排框架。

简单工具调用不必上图。状态要持久、失败要从中间恢复时，再引入图引擎。选型时问三件事：进程重启后任务还在不在、工具超时谁来取消、换模型要不要改业务代码。

### 13. 在构建 AI Agent 时，如何设计一个高效、可靠的提示词（Prompt）管理方案？

**参考答案**

结论：提示词按场景和版本管理，运行时只做渲染和校验，不在业务代码里拼接长字符串。

每个模板有场景键、版本和适用的模型。系统约束、任务说明、少量示例、输出格式分开存，示例可以单独替换。变量用占位符，渲染前检查缺参。用户原文放进明确的数据区，并写明这段是资料。不要把用户输入直接接在指令后面。

输出用 JSON Schema 或供应商的结构化接口约束。校验失败把错误原因交回模型重试，限制次数，仍然失败就走兜底文案或转人工。改模板先跑固定评测集，看任务成功率和格式合法率，再灰度。日志打上模板版本，出了问题能回滚到上一版。

模型一换，旧模板的格式遵循就会变，所以模板要绑定模型版本，升级模型就重跑评测。密钥和个人信息不要进模板仓库。小团队用 Git 管模板和评测集；多团队同时改，再放到配置中心，版本和回滚仍然要留着。

### 14. 如果让你用 Java 设计一个简单的 Agent 服务，调用大模型 API 并处理返回，你会考虑哪些关键模块？

**参考答案**

结论：最小可用的服务是一条有上限的循环：组装上下文、调模型、校验并执行工具、把观察结果喂回去，直到模型给出最终回答或步数用尽。

1. 接入层：鉴权、请求号、限流。调用方只传场景和用户输入，不传供应商密钥。
2. 模型网关：屏蔽供应商差异，统一超时、重试、流式输出和错误码。密钥和配额放在这里。
3. 提示词组装：按场景取模板版本，塞进历史和检索结果，并卡死 token 预算。
4. 编排：固定最大步数。模型返回工具调用时，先解析再执行，不能把一段文本直接当成功。
5. 工具注册表：名字、JSON Schema、超时、是否有副作用。未知工具和非法参数不执行，把错误交回模型。写操作带幂等键。
6. 记忆：当前会话的消息列表，超长就裁剪或摘要。
7. 观测：记录模板版本、模型、工具入参摘要、耗时、token 和错误。敏感字段脱敏。

关键难点是取消和超时要能传到模型和工具，不能只在入口掐断、下游还在跑。返回给调用方的是业务结果和可展示的失败原因，不是模型的原始堆栈。

### 15. 手写算法：反转一个单链表。

**参考答案**

结论：用三个引用把每个节点的 `next` 指向上一个节点。时间 O(n)，额外空间 O(1)。

`prev` 是已经反转的前缀，`curr` 是还没处理的头。先记下 `curr.next`，再把 `curr.next` 指向 `prev`，然后两个引用一起前移。循环结束时 `prev` 是新头。空链表和只有一个节点时，循环不跑或只跑一次，返回值仍然正确。

```java
class ListNode {
    int val;
    ListNode next;
    ListNode(int val) { this.val = val; }
}

ListNode reverse(ListNode head) {
    ListNode prev = null;
    ListNode curr = head;
    while (curr != null) {
        ListNode next = curr.next;
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

递归也能做：先反转 `head.next` 之后的链表，再让后继指向自己，自己的 `next` 置空。时间同样 O(n)，栈深度也是 O(n)，链表很长会栈溢出。迭代是面试里应先写出来的版本。返回的是 `prev`，继续返回原来的 `head` 会得到只有一个节点的链。

### 3. 在 Agent 开发中，如何保证调用外部工具（Tool / Function Calling）的稳定性和错误处理？

**参考答案**

结论：模型只负责选出工具和参数。执行前校验、超时、鉴权和幂等都在服务端，不把一段合法 JSON 当成业务成功。

工具以白名单注册，每个工具有 JSON Schema、超时和是否有副作用。模型返回的名字不在白名单里，或者参数解析失败、类型不对，就不执行，把可理解的错误作为观察结果交回模型，并限制重试次数。同一工具、同一参数连续出现多次，视为死循环，停止并返回失败。

读操作可以有限次重试，并加退避。写操作必须带业务幂等键；超时后先查上次是否已经生效，再决定要不要重试。权限用用户自己的身份去校验，模型不能通过换一个工具名扩大权限。不可逆动作在执行前由服务端或人工确认。

并行工具时，成功和失败都要收回来，不能因为一个失败丢掉其他结果。熔断按工具打开，下游持续失败就直接返回，不再打满线程。交回模型的是错误类别和可行动的说明，不是完整堆栈。日志里留下请求号、工具名、参数摘要、耗时和结果码，敏感字段脱敏。

整轮还有最大步数。模型不再请求工具，才把内容返回给用户。

### 4. Java 中的 AQS（AbstractQueuedSynchronizer）了解吗？说说它的原理。

**参考答案**

结论：AQS 用一个 `volatile int state` 和一条 FIFO 等待队列，把阻塞、唤醒和排队做成模板。`ReentrantLock`、`Semaphore`、`CountDownLatch`、读写锁都是在它上面定义 `state` 的含义。

获取时先走子类的 `tryAcquire` 或 `tryAcquireShared`。成功就改 `state` 返回；失败就把当前线程包装成节点排到队尾，前驱是头节点时再试一次，仍失败就 `park`。释放时 `tryRelease` 成功，就 `unpark` 后继。`park` 可能被虚假唤醒，所以获取必须放在循环里。

独占模式一次唤醒一个后继，`ReentrantLock` 的 `state` 表示重入次数，持有者线程另记。共享模式在释放时会向后传播，信号量的 `state` 是剩余许可，倒计时门闩的 `state` 是剩余计数。公平锁在尝试获取前先看队列里有没有前驱；非公平锁会先 CAS 抢一次，失败再入队。队列是 CLH 锁的变体：双向链表，取消的节点会被后继跳过。

`Condition.await` 会释放锁，把节点放进条件队列；`signal` 再把节点搬回同步队列。AQS 自己不规定什么叫「拿到锁」，那是子类的 `tryXxx` 决定的。

### 5. ConcurrentHashMap 在 JDK 1.7 和 1.8 中有什么不同？为什么这么改？

**参考答案**

结论：JDK 7 是分段锁加链表；JDK 8 取消 `Segment`，改成桶头上的 `synchronized` 加 CAS，链表过长再转红黑树，扩容也可以由多个线程一起做。

JDK 7 默认 16 个 `Segment`，每个段是一把锁，段内是 `HashEntry` 链表。`put` 锁整段，`get` 基本无锁，靠 `volatile` 的 value。并发度受段数限制，扩容也是锁住一段再迁移。

JDK 8 的数组节点是链表或树。空桶用 CAS 放入头节点；有冲突就锁住头节点，锁内再确认这个桶的头没有变，变了就重试。向一个已经有至少 8 个节点的桶再插入时尝试树化，但数组长度小于 64 会先扩容。迁移或收缩后，一侧节点数不超过 6 就退回链表。两个阈值差开，是为了避免在边界上来回转换。桶上如果是转发节点，说明这个桶正在迁移，当前线程去帮忙。`sizeCtl` 用来协调初始化和这次扩容。计数分散在 `baseCount` 和 `CounterCell` 里，并发下 `size` 是近似值。

这样改，是因为段数把并发度封死了，段对象也占内存。锁收窄到一个桶以后，临界区很短，`synchronized` 足够，不必再为每段配一把 `ReentrantLock`。树把严重哈希冲突时的查找从线性降到对数。多线程帮忙迁移，扩容不再由一个线程扛完。

不要用 HashMap 在 JDK 7 的死循环来解释这里的改动。JDK 7 的 `ConcurrentHashMap` 在段锁里操作链表，没有那个问题。

### 6. JVM 调优你一般关注哪些参数？有没有实际解决过 OOM 问题的经验？

**参考答案**

结论：先分清内存用在堆、元空间、堆外还是线程栈，再谈参数。线上优先留下 GC 日志和 OOM 时的堆转储，而不是先背一串开关。

堆的 `-Xms` 和 `-Xmx` 设成一样，避免运行中反复扩缩。收集器一般保持 G1，停顿不合适再调 `MaxGCPauseMillis`，不要一上来改新生代比例。类卸载不掉时给元空间一个上限 `MaxMetaspaceSize`，让问题暴露成 Metaspace OOM，而不是把本地内存吃光。用了 Netty 或大量直接内存，再看 `MaxDirectMemorySize`。`-Xss` 只在线程数量把本地内存打满时才动，调小会更容易 `StackOverflowError`。

排错开关比「优化开关」重要：`-XX:+HeapDumpOnOutOfMemoryError` 指定转储路径，JDK 9 以后用 `-Xlog:gc*` 留 GC 日志。`Java heap space` 和 `GC overhead limit exceeded` 看堆转储里的支配树。`Metaspace` 看类加载器是否泄漏。`Direct buffer memory` 时堆转储往往是正常的，要看堆外。`unable to create native thread` 是线程数或系统限制，加堆没有用。

**答题思路**

有真实案例就按「报错原文 → 现场 → 定位 → 修改 → 怎么确认不再涨」讲。报错要能对上上面的某一种。现场是当时的 GC 日志、堆转储或监控时间点。定位讲你沿着哪条引用链看到缓存、类加载器或堆外缓冲。没有处理过线上 OOM 就直接说没有，再讲你会提前打开转储，以及本地怎样把堆打满来验证判断。不要编一次「某服务内存泄漏」。

### 7. Redis 的持久化机制 RDB 和 AOF 各有什么优缺点？生产环境如何选择？

**参考答案**

结论：RDB 是某一时刻的快照，文件紧凑、恢复快，两次快照之间的写入会丢。AOF 按写命令记日志，丢失窗口更小，文件更大，重放更慢。持久化不是高可用。

RDB 用 `BGSAVE` 在子进程里写，靠写时复制。优点是适合备份和做从节点的全量基础。缺点是 fork 大实例时会有明显抖动，而且上次快照之后的数据没有。`SAVE` 会堵住主线程，线上不用。

AOF 常见是每秒刷盘，进程崩溃时通常最多丢一秒左右的写入；磁盘卡住时窗口会更大。每条命令都刷盘最稳，写入延迟会明显变差；交给操作系统刷盘则可能丢更多。日志变大后要重写。Redis 4.0 起可以混合持久化：文件头是 RDB，后面接增量命令，加载比纯 AOF 快。Redis 7 起 AOF 拆成基础文件和增量文件，重写时生成新的基础文件，并去掉已经写进基础文件的增量。AOF 开着时，重启优先用 AOF，因为它比上一份 RDB 更完整。

缓存能从数据库重建时，可以只留 RDB 做预热，甚至不持久化。不能多丢数据时，用每秒刷盘的 AOF，再加副本，不要靠单机刷盘扛主机磁盘损坏。两种一起开是常见做法，但副本延迟和磁盘写满仍然会丢数据。

### 8. MySQL 的 InnoDB 索引结构（B+ 树）了解吗？为什么用 B+ 树而不用哈希表或 B 树？

**参考答案**

结论：InnoDB 的索引是 B+ 树。主键索引的叶子就是整行，按主键有序；二级索引的叶子是主键，拿完整行还要回表。选 B+ 树是为了范围查询和高扇出，不是为了单次等值更快。

哈希只能等值。范围、排序、`ORDER BY`、最左前缀都做不了，冲突时也不稳定。InnoDB 可以在缓冲池里对热点页建自适应哈希，那是内存中的加速，替代不了磁盘上的有序索引。

B 树的非叶子节点也存数据，同样一页能放下的键更少，树更高，磁盘 IO 更多，范围扫描还要在树里上下跳。B+ 树的非叶子只有键和子页指针，扇出大，树通常很矮。叶子之间有链表，范围扫描顺着叶子走。查询都落到叶子，代价稳定。InnoDB 一页默认 16KB，这个页大小和缓冲池配合，才是 B+ 树扇出大的前提。

覆盖索引可以避免回表，那是怎么用索引，不是改用哈希或 B 树的理由。

### 9. 一个 SQL 执行很慢，你通常会从哪些方面入手排查和优化？

**参考答案**

结论：先分清是执行慢、等锁，还是结果集太大把网络打满，再决定加索引还是改 SQL。

1. 确认慢在哪。看慢查询日志和应用里的 trace。MySQL 8.0 可以用 `EXPLAIN ANALYZE` 看实际耗时，不只看估计行数。
2. 看 `EXPLAIN`：有没有用到预期索引，访问类型是范围还是全表，估计行数是否离谱，`Extra` 里有没有 `Using filesort`、`Using temporary`。
3. 索引没用上时，检查是否对列做了函数或隐式转换、前导模糊匹配、不符合最左前缀、区分度太差，或者统计信息过期。
4. 看 SQL 形状：`SELECT *`、大偏移量分页、一次 JOIN 把行数乘上去、超大 `IN`。深分页改成按主键往后扫。
5. 执行本身不慢、时间耗在排队时，看长事务和锁等待。加索引解决不了锁。
6. 再看实例：Buffer Pool 命中、磁盘、连接数。读的是从库时，把复制延迟和慢 SQL 分开。

改完用同一批数据比较执行时间和扫描行数。索引不是越多越好，写放大和优化器选错索引都会出现。

### 10. 在微服务架构下，如何设计一个 Agent 服务，使其能够优雅地处理高并发、低延迟的模型调用请求？

**参考答案**

结论：把模型调用当成慢 IO。给它独立的在途上限、贯穿全链路的超时预算和明确的降级，不要和普通业务线程共用一个无界池。

每个请求带截止时间，剩余预算传给模型和工具。入口按用户和全局限流。模型客户端用连接池，在途数用信号量卡在供应商的配额以内。实现上可以用虚拟线程，也可以用异步 HTTP。虚拟线程避免阻塞占满平台线程，替代不了配额限制。

队列必须有界。满了就拒绝、换小模型或返回已有检索结果，不无限排队。能流式输出就把首 token 尽快推给调用方。彼此无关的只读工具并行；有副作用的工具串行，并带幂等键。检索结果和只读工具可以缓存。供应商若支持提示词前缀缓存，就把稳定的系统提示放在前面。

重试只给读，次数少，并加退避，避免故障时把流量放大。供应商连续失败就熔断，切到备用模型或直接失败。网关、模型和工具三层超时要满足同一条预算：内层先超时，外层才有机会返回可控错误。

观测上看排队时间、首 token、总延迟、在途数、拒绝数和 token。尾延迟和账单是主要难点。多试一次、换大模型，体验更好，容量和费用更差，这个取舍要按场景写进降级策略，而不是每次临时决定。

### 11. 你如何理解 Agent 的“记忆”（Memory）能力？在你的项目中是如何实现或规划长期/短期记忆的？

**参考答案**

结论：记忆分三层。短期是这段对话还留在上下文里的内容，长期是跨会话存下来、用到时再取回的事实，工作记忆是这一轮任务的中间状态。

短期就是消息列表加 token 预算。超了就丢掉最早的轮次，或压成一段摘要放回去。工具返回的大段原文要截断，否则几步就把窗口占满。

长期不要把聊天记录原样灌进向量库。抽取还会再用的事实，带上时间和来源存下来；回答前按当前问题取少数几条，注入时标明这是资料。用户新的明确说法覆盖旧记录。删账号时这些记录要能删掉。

工作记忆是当前计划、已调用的工具和结果，放在编排状态里，不和聊天记录混在一起。否则模型会把中间 JSON 当成给用户的回复。

检索到的记忆可能过期，也可能被人投毒。写入放在主回复之外异步做，失败不能卡住这次回答。

**答题思路**

按你项目里真实有的层来讲，没有的层直接说没有。

1. 短期：历史存在哪，按条数裁还是按 token 裁，摘要是谁生成的。
2. 长期：如果做了，讲存什么、谁触发写入、检索条件、新旧冲突听谁的。如果没做，说当时没有跨会话需求，不要把「以后可以加向量库」说成已经上线。
3. 工作记忆：多步工具的中间结果存在会话状态里，还是每次把全文重新塞进提示词。
4. 讲一个取舍：全量历史最简单，费用和干扰最大；只检索事实更稳，抽取错了会把错误记很久。

### 12. 有没有尝试过对大模型进行微调（Fine-tuning）或使用 LoRA 等技术？了解其大致流程吗？

**参考答案**

结论：微调改变的是模型的默认行为。LoRA 冻结基座，只训练插在线性层上的低秩矩阵；事实会变、需要出处的内容优先检索，格式、语气和工具调用习惯更适合微调。

低秩矩阵的形状和原线性层一致：一边把维度降到一个很小的秩，另一边再投回去，加到原权重的输出上。训练开始时这份增量是 0，所以一开始和基座相同。秩越大，能拟合的变化越大，也越容易过拟合，没有通用的默认秩。QLoRA 是在 4-bit 基座上训练这些矩阵，用来省显存，它本身不是另一种任务。

流程：

1. 先定目标。要的是格式和说话方式，还是把新知识写进权重。后者先做检索。
2. 准备指令和期望输出，去重、去掉敏感信息，划出验证集。脏数据会被稳定地学进去。
3. 选基座，确认许可证和上下文长度。
4. 冻结基座，在注意力或前馈的线性层加 LoRA。显存不够再用 QLoRA。
5. 训练时看验证集损失，不要只看训练损失。
6. 用任务集对比基座：格式是否遵守、原有事实有没有退步、工具调用有没有变差。
7. 通过后再部署。可以合并进基座，也可以按场景挂适配器。数据和模板版本一起留档。

微调消不了幻觉，只是让某些输出更稳定。评测不过就不要替换线上模型。

**答题思路**

做过就按你的数据、秩的选择和评测结果讲，没做过就说没做过，再把上面的流程和「什么时候不该微调」讲完。不要编一个训练集大小或某个开源模型的微调经历。

### 13. 如何评估一个 AI Agent 的表现好坏？你会设计哪些指标（除了准确率）？

**参考答案**

结论：Agent 要看任务有没有办成、办的过程有没有副作用，不能只看最终一句话像不像标准答案。

离线准备一批带期望结果的用例，工具用桩，能重复跑。线上从轨迹里抽样人工看。模型或提示词一变就重跑同一批用例。

除了最终答案是否正确，还看这些：

- 端到端任务成功率：该写的写对了，不该写的没有写。
- 工具选择是否正确、参数是否合法、有没有重复调用。
- 步数、首 token 时间、总延迟、token 费用。
- 忠实度：结论能不能被这次的工具结果或检索内容支持。
- 稳定性：同一输入跑多次，结果差多少。
- 安全：提示注入有没有让它越权调用工具。
- 人工接手率：多少对话是人接过去才完成的。

最终答案碰巧正确、写接口却调用了两次，准确率看不出来。所以轨迹要和最终结果一起留。

### 15. 手写算法：给定一个包含 n 个整数的数组 nums，判断 nums 中是否存在三个元素 a，b，c，使得 a + b + c = 0？找出所有满足条件且不重复的三元组。

**参考答案**

结论：先排序，固定一个数，剩下两个数用相向双指针找。时间 O(n²)。除结果外，额外空间是排序的 O(log n) 栈。

排序后相同的数挨在一起，才能跳过重复三元组。枚举下标 `i`，左指针从 `i + 1` 开始，右指针从末尾开始。三者之和小于 0 就左指针右移，大于 0 就右指针左移，等于 0 就记下这一组，然后左右都跳过刚用过的值。只跳一边，仍然会留下重复三元组。因为已经排序，`nums[i] > 0` 时后面都是正数，可以直接结束。三个 `int` 相加可能溢出，求和用 `long`。

哈希表同样是 O(n²)，去重更麻烦。面试里写排序加双指针。

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

List<List<Integer>> threeSum(int[] nums) {
    List<List<Integer>> ans = new ArrayList<>();
    if (nums == null || nums.length < 3) {
        return ans;
    }
    Arrays.sort(nums);
    for (int i = 0; i < nums.length - 2; i++) {
        if (nums[i] > 0) {
            break;
        }
        if (i > 0 && nums[i] == nums[i - 1]) {
            continue;
        }
        int l = i + 1;
        int r = nums.length - 1;
        while (l < r) {
            long sum = (long) nums[i] + nums[l] + nums[r];
            if (sum == 0) {
                ans.add(Arrays.asList(nums[i], nums[l], nums[r]));
                int left = nums[l];
                int right = nums[r];
                while (l < r && nums[l] == left) {
                    l++;
                }
                while (l < r && nums[r] == right) {
                    r--;
                }
            } else if (sum < 0) {
                l++;
            } else {
                r--;
            }
        }
    }
    return ans;
}
```
