### 3. Java 中 synchronized 和 ReentrantLock 的区别

**参考答案**

两者都可重入，互斥语义接近。差别在谁负责释放，以及锁能不能中断、试锁和按条件等待。

`synchronized` 是关键字，进入和退出由编译器与 JVM 配对，方法抛异常也会释放。正在等这把锁的线程不能被中断，也不能限时尝试。它配合同一个对象的 `wait` 和 `notify`，做不到多条条件队列。实例方法锁的是 `this`，静态方法锁的是 Class 对象。

`ReentrantLock` 基于 AQS，必须在 `finally` 里 `unlock`，否则异常路径会把锁留住。它提供 `tryLock`、带超时的获取、`lockInterruptibly`、可选的公平锁，以及多个 `Condition`。公平锁让等待最久的线程先拿到，吞吐通常更低，默认是非公平。普通互斥用 `synchronized` 更不容易写错；需要试锁、中断或分开唤醒时再用 `ReentrantLock`。JDK 15 起偏向锁默认关闭，后来的版本把这块实现也去掉了，不要再说 `synchronized` 一定更慢。两把锁都不跨进程。

### 4. 讲一下 Java 内存模型，volatile 关键字的作用

**参考答案**

这里要的是多线程下的可见性和重排序。堆、虚拟机栈、方法区是运行时数据区，被追问再分开讲。线程之间靠 happens-before：前一个动作的结果，对后一个动作可见。

`volatile` 写先于之后任意线程对同一变量的读，所以一个线程改完标志，别的线程能读到新值。它也约束重排：普通写不能挪到这次 volatile 写之后，普通读不能挪到这次 volatile 读之前。双重检查锁里的实例引用因此必须是 volatile，否则另一线程可能拿到还没构造完的对象。

它不保证 `i++` 这种读改写的原子性，计数要用原子类或锁。它适合状态标志和安全发布，保护不了一段必须互斥的复合逻辑。

### 5. Spring Bean 的生命周期

**参考答案**

单例从构造走到可用，代理出现在初始化之后；销毁要等容器关闭。

顺序是：构造，注入依赖，再回调 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。随后进入 `BeanPostProcessor` 的前置处理，`ApplicationContextAware` 和 `@PostConstruct` 发生在这一步。然后执行 `InitializingBean.afterPropertiesSet` 和自定义 init-method。后置处理里通常才生成 AOP 代理，这之后 bean 才算成品。

容器关闭时的销毁顺序是 `@PreDestroy`、`DisposableBean.destroy`、自定义 destroy-method。原型 bean 容器默认不跟踪，也就不会替你调销毁。单例的设值循环依赖靠提前暴露半成品对象；构造器互相依赖会创建失败。`@PostConstruct` 里拿到的还是原始对象，这里面的自调用走不到代理，事务和切面不会生效。

### 6. Spring 事务的传播机制和隔离级别

**参考答案**

传播决定这次调用要不要进入已有事务，隔离决定并发事务之间能看见什么。

`REQUIRED` 是默认：有就加入，没有就新建。`REQUIRES_NEW` 挂起外层并单独提交，外层回滚带不走已经提交的内层。`NESTED` 在已有事务上打保存点，失败可以只滚到保存点；没有外层时相当于新建，而且依赖 JDBC 保存点，不是每个事务管理器都支持。`SUPPORTS` 有则加入，没有就非事务执行。`NOT_SUPPORTED` 先挂起外层再裸跑。`MANDATORY` 没有事务就抛错，`NEVER` 有事务就抛错。

隔离五档里，`DEFAULT` 跟随数据库，InnoDB 默认是可重复读；另外四档是读未提交、读已提交、可重复读和串行化。InnoDB 的普通一致性读靠 MVCC 保持快照，当前读还要临键锁才挡得住幻读。加入外层事务时，连接上的隔离级别沿用外层，内层注解写的另一档通常不会再生效。

同一类内部自调用不经过代理，注解不会生效。默认只在运行时异常和 `Error` 时回滚，受检异常要写 `rollbackFor`。异常在方法内部被吃掉，事务同样不会回滚。

### 7. MySQL 索引底层数据结构，B+ 树的特点

**参考答案**

InnoDB 的索引是 B+ 树。主键索引是聚簇索引，叶子放整行。二级索引的叶子放的是主键，要整行时再按主键回表。查询列都在这棵二级索引里，就是覆盖索引，不必回表。

非叶子节点只放键和子页指针，一页能挂更多分支，树更矮，磁盘 IO 更少。记录都在叶子上，单点查找的代价稳定。叶子之间用双向链表相连，范围扫描沿链表走。页的默认大小是 16KB，配合这种扇出，高度常见是三四层。

联合索引从左到右有序。用得上的是左边连续的等值，再加上紧挨着的那一列范围。单独拿右边的列来查，这棵索引用不上。哈希做不了范围和排序。InnoDB 不能把普通二级索引建成哈希索引，自适应哈希只是热点页上的内存加速。

### 8. Redis 持久化方式 RDB 和 AOF 的区别

**参考答案**

RDB 是某一时刻的数据快照，AOF 是把写命令追加到日志。两者可以同时开。

`BGSAVE` 会 fork 出子进程写 RDB，父进程继续服务，靠写时复制。文件小、恢复快，适合备份，也适合主从第一次全量同步。两次快照之间宕机会丢掉这一段。内存大时，fork 复制页表可能把实例卡住，写时复制还会把内存顶高。

AOF 常见是每秒刷一次盘，进程崩溃时通常最多丢掉大约一秒的写；每条命令都刷最稳，吞吐也最差。文件变大后会在后台重写，压成能重建当前数据的最小命令集。重写结果可以在文件头放一段 RDB 格式的全量，后面再追加增量，加载比纯命令回放快。

它们保住的是这台机器重启后还在的数据。异步复制的从库同样可能缺最近几条写，替代不了本机持久化。

### 9. 如何保证缓存与数据库的双写一致性

**参考答案**

以数据库为准，用旁路缓存：读的时候命中直接返回，未命中再查库，并带过期时间回填。写的时候先提交数据库，成功后再删缓存，下一次读再把新值填进去。

先改缓存再改库，进程若死在两次写之间，缓存已是新值，库还是旧值。先删缓存再更新库，删除和提交之间的读会把旧值填回去，这份旧值能一直留到过期。并发下还有一种少见交错：读请求已经拿到旧值，写请求提交并删完缓存之后，这个读又把旧值写回。过期时间是兜底，删缓存失败要另记一条待重试记录，或订阅数据库的提交日志再删一次。同一个键回填时加短锁，避免缓存同时失效时一群请求打到库上。

调用方要立刻读到自己刚写的内容，这次读走主库或绕过缓存。库存、余额这类不能忍受旧值的数据，按键把读写串行起来，或者这段数据不进缓存。

### 10. 什么是 CAP 定理，在分布式系统中的应用

**参考答案**

CAP 说的是网络一旦分区，一致性、可用性和分区容忍不能同时满足。跨机器通信会分区，所以分区期间只能在「拒绝写入以保住一致」和「继续应答但可能读到旧数据」之间取舍。它描述的是分区期间的行为，不是给整个产品贴一个永久标签。

etcd、ZooKeeper 这类要法定人数才提交的系统，少数派一侧会拒绝写入，已经确认的写入仍然保持一致。Cassandra 这类系统的一致性级别可以调低，分区后仍用本地副本应答，读到的可能是旧值；把级别调到法定人数时，丢了法定人数它也会不可用。同一系统可以分接口：扣减库存偏一致，信息流允许短暂旧读。

没有分区时，CAP 并不帮你选。这时仍要在延迟和一致之间权衡。单机数据库不是这个定理里的分布式系统；主从之间的复制延迟，才进入这个讨论。

### 11. 了解大模型吗？说说 GPT 的基本原理

**参考答案**

GPT 这类模型是只含解码器的 Transformer，训练目标是根据前文预测下一个 token，生成时就按这个分布逐个往外接。温度越高，抽样越发散。

文本先切成 token。每一层做因果自注意力，一个位置只能看见自己和前面的位置，再经过前馈网络，层与层之间有残差和归一化。位置信息要单独编码：公开的早期 GPT 用绝对位置，如今开源的主流解码器模型多用旋转位置编码。推理时把已经算过的键和值放进 KV cache，避免每生成一个 token 都重算整段前文。标准自注意力的计算量会随长度明显上升，上下文也有长度上限。

对话能力主要来自预训练之后的指令微调，以及用偏好数据做的对齐，具体算法各家不同。模型参数里没有一份可更新的业务事实库，所以说得通的句子不一定是事实。业务数据要靠检索或工具现查。

### 12. 在 Java 中如何调用大模型 API？有哪些注意事项

**参考答案**

业务代码调用自己的门面。门面里用 Spring AI 的 `ChatClient`，框架还没封装的厂商参数再用 WebClient 调 HTTP。密钥来自环境变量或密钥服务，不写进源码和镜像。

超时按模型单独设。连接超时保持短，读超时要盖住首 token 和整段生成；沿用普通 REST 的短读超时，生成还没结束就会被断开。429 和 5xx 按响应里的等待时间做有限次退避。已经触发了业务写操作的，不要因为模型超时就盲目再执行一遍。这种调用远长于普通查询，放在有界线程池或虚拟线程上，避免占光 Web 容器线程；响应式接口则直接把流交回去。

同时限制最大输出 token，并按用户做配额。返回值先校验，再交给下游。模型正文当不可信输入，不拼进 SQL 或系统命令。提示词和回答里的个人信息不进普通日志。

### 13. Spring AI 是什么？它提供了哪些核心功能

**参考答案**

Spring AI 是嵌在 Spring 里的模型应用框架，用来以统一接口接聊天、嵌入、向量检索和工具调用。训练和微调不在它的职责里。

底层是 `ChatModel`，业务更常使用 `ChatClient`：同步走 `call`，流式走 `stream`。提示词可以用模板填参数。Advisor 在一次调用前后插入逻辑，会话记忆、检索和日志都放在这里。工具调用把 Spring Bean 上的方法暴露给模型，框架执行方法后再把结果送回模型。`EmbeddingModel` 和 `VectorStore` 负责把文本变成向量并检索，文档读取和切分负责把资料灌进向量库。需要固定字段时，用结构化输出把文本转成 Java 对象。这些调用接到 Micrometer 上，能看耗时、错误和 token。

换一家提供了对应 starter 的厂商，业务侧的 `ChatClient` 调用可以少改。刚发布的厂商私有参数、密钥轮换、权限和效果评测，仍然要自己做。

### 14. 用 Spring AI 实现一个简单的聊天应用，需要考虑哪些方面

**参考答案**

先定会话边界，再定上下文怎么裁、失败怎么返回。界面能打字只是其中一小节。

每个用户的每个会话用自己的 ID，记忆按这个 ID 隔离。历史保留窗口，或把更早的轮次收成摘要，避免每次把全部记录塞进上下文。系统提示写清角色、允许使用的资料，以及资料里没有时怎么回答，并且带版本号。用户原文和系统指令分开放。`ChatClient` 挂上记忆 Advisor；窗口记忆的默认实现在进程内存里，重启即失，多实例也不共享，要保留就换 Redis 或数据库。

回复用 `stream`，让用户先看到文字。客户端断开要取消上游请求。容器的异步超时按生成时长加长。模型超时或 5xx 时返回明确失败，并保留原来的非模型路径。按用户做限流和费用上限。查订单、改数据仍然走原有业务方法，模型只组织话术。同一会话上的并发消息要串行或带版本，避免两段记忆互相覆盖。日志记会话 ID、模型、耗时和 token，正文按隐私要求另存。

### 15. 如果大模型响应慢，如何优化调用性能

**参考答案**

先分清慢在首 token 还是整段生成。聊天优先流式输出，总耗时还在，用户不必等全文才看见第一个字。

每次请求把上下文变短：历史用摘要加最近几轮，检索只放相关片段，输出 token 设上限。稳定的系统提示和工具定义放在前缀里；厂商若支持提示缓存，重复前缀可以少算，命中情况以监控为准，不凭感觉报比例。简单意图路由到更小的模型，答不好再换更强的模型。不含个人信息、结果又稳定的请求可以做短缓存。

HTTP 连接复用，避免每次重新握手。连接超时和读超时间隔开。慢调用放进隔离的有界线程池，或使用虚拟线程，不让它占满普通 Web 线程。已经慢成功的请求不要立刻重试，否则费用和排队一起加倍。模型调用不要包在数据库事务里。彼此没有依赖的工具调用可以并行，有先后关系的保持顺序。

### 3. 在项目中如何设计提示词（Prompt）以获得更好的模型输出

**参考答案**

把任务、边界和输出格式写清楚，把资料、用户原文和系统指令分开。单靠「请不要胡说」稳不住输出。

系统提示放稳定规则：角色、只能依据哪些资料、资料不足时说不知道、禁止哪些动作。检索片段和用户原文放进用户消息，并用明确分隔包起来，降低用户句子被当成新指令的概率。程序要消费的结果走结构化输出，约定字段和类型，少从自由文本里抠。格式很难稳定时，再加一两个不含真实隐私的例子。

抽取和分类把温度调低，减少抽样晃动。提示词放进模板文件并写版本，改一版就用同一批样本回归。检索为空时由程序直接拒答，不把「不知道」只写在提示词里。提示词改善的是表述和格式，业务事实仍要来自检索或工具。

### 4. 如何评估大模型应用的效果和性能

**参考答案**

效果看任务有没有做对，性能看快慢、失败和花费。两边分开统计，不能用一个平均分盖过去。

离线准备固定样本：任务是否完成，字段是否符合结构，关键事实能不能在检索片段或工具结果里找到，该拒答的是否拒了，工具名和关键参数是否正确。开放闲聊不要只用字面重合度。用另一个模型打分可以做辅助，先拿一部分人工标注校准，不能单独当作发布标准。

线上按接口看错误率、首 token 时间、整段耗时、输入和输出 token、超时次数，以及用户是否立刻重试。费用用账单上的单价去乘 token，不凭记忆写一个价格。提示词、模型或索引只要变更，就重跑同一套样本，关键样本退步就不发布。线上再抽样人工看，把错误归到检索、提示词或工具，改对应的那一层。

### 5. Spring AI 中如何集成不同的模型提供商（如 OpenAI、Azure OpenAI）

**参考答案**

业务依赖 `ChatModel` 和 `ChatClient`，厂商差异留在 starter 和配置里。OpenAI 与 Azure OpenAI 各引入自己的 starter。OpenAI 配的是模型名和可选的 base-url；Azure 配的是资源端点和部署名，部署名不等于公开的模型系列名。密钥只出现在环境配置中。

classpath 上只有一个聊天 starter 时，自动配置会提供 `ChatModel`，再用它建立 `ChatClient`。两家同时存在时都会尝试注册 `ChatModel`，注入会冲突。这时用 `spring.ai.model.chat` 指定当前实现，或者按具体类型各自声明 `ChatClient`，调用方注入需要的那一个。

切换前核对三件事：这家模型是否支持工具调用、是否支持你用的结构化输出、上下文长度是否够。私有化服务若提供 OpenAI 兼容接口，可以改 base-url 沿用同一套客户端。只属于某一家的字段留在那一家的配置里，不塞进公共调用代码。

### 6. Spring AI 的 PromptTemplate 怎么用，有什么优势

**参考答案**

`PromptTemplate` 把带 `{name}` 占位符的文本和参数渲染成最终提示。参数用 Map 传入，也可以在 `ChatClient` 的 system、user 回调里 `param`。模板既能写在代码里，也能放在 classpath 的文件中，措辞可以随资源发版。

这样做的好处是同一段规则多处复用，变量和指令分开，换措辞不用改拼接代码。用户输入只作为参数填入，不把用户原文拼成模板语法。它默认按 StringTemplate 渲染，字面量的大括号要转义；JSON 示例直接贴进去时，括号会被当成占位符，这是最常见的运行错误。

模板保证的是生成过程可重复，不保证内容正确。渲染结果仍要跟普通提示词一样做回归。

```java
PromptTemplate template = new PromptTemplate("""
        只根据资料回答。资料里没有就说不知道。
        资料：{context}
        问题：{question}
        """);
String text = template.render(Map.of("context", context, "question", question));
```

### 7. 如何实现大模型输出的流式响应（Streaming Response）

**参考答案**

用 `ChatClient.stream()` 拿到内容片段的 `Flux`，每来一段就往客户端推，不要等全文生成完再返回。WebFlux 可以把这个 `Flux` 以 `text/event-stream` 直接作为响应体。只有 Servlet 栈时，订阅同一个 `Flux`，写入 `SseEmitter`，在完成、失败和客户端断开时结束或取消。

```java
@GetMapping(value = "/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<String> chat(@RequestParam String message) {
    return chatClient.prompt().user(message).stream().content();
}
```

上面的返回值在 WebFlux 里可以直接用。读超时要盖住两个片段之间的间隔，容器的异步超时也要按整段生成加长，否则流会在中途被掐断。用量信息常常到最后一个片段才有，中途断开时要能记下已经推出的内容。取消订阅要传到上游 HTTP 请求，避免用户离开后仍在生成和计费。反向代理按流式转发，不能先攒成一整包。

### 8. 在大模型应用开发中，如何管理 API 密钥和配置

**参考答案**

密钥放在环境变量、部署平台的 Secret 或专门的密钥服务里。仓库、镜像和日志里都不出现明文。Spring 配置只写 `${OPENAI_API_KEY}` 这种引用，`api-key`、端点、模型名或 Azure 部署名按环境切换。

一个服务使用一把密钥，便于单独轮换和停用。轮换前先确认客户端是每次请求再取密钥，还是启动时复制进了 HTTP 客户端。后者必须重建客户端或滚动实例，否则进程里继续用旧值。访问日志去掉 `Authorization` 头，异常信息里也不要带密钥。

提示词版本、温度、最大 token 可以进配置中心，和密钥的读取权限分开。同事之间不共享长期个人密钥，测试和生产也不共用一把。

### 9. 有没有遇到过模型输出不稳定或幻觉问题，如何缓解

**参考答案**

输出晃动和事实编造要分开处理。晃动靠低温度、钉死模型快照和结构化字段来收。编造靠检索或工具提供事实，模型只组织语言。项目里如果只做过闲聊、没有事实问答，就说明当时没有这层约束，再讲你会怎么加。

检索结果为空时，程序直接回答不知道，不再让模型自由发挥。提示词要求结论能对上给定资料；订单号、金额这类字段由程序对照工具返回值校验，对不上就当失败。温度调低只能减少抽样差异，不能证明内容为真。厂商提供的 seed 也只是尽量复现同一次抽样，不是逻辑保证。浮动的模型别名会被上游更新，稳定性要求高时钉死带日期的快照，升级走评测。

改数据、给结论这种高风险动作仍走原来的业务接口，并由用户确认。已经出现过的编造案例放进回归样本。这些手段用来降低比例，对外不要承诺没有幻觉。

### 10. 如何将大模型能力嵌入到现有 Spring Boot 应用中

**参考答案**

加一个应用服务包住 `ChatClient`，现有控制器调用这个服务。不要在各个接口里各自 new 一套 HTTP 客户端。引入对应 starter，密钥走原来的环境配置。用户身份和权限仍在进入模型之前，沿用现有登录态，不让模型自己声明自己是谁。

模型等待时间远长于 SQL。数据库事务里不要等模型返回，否则连接会被占住。给这路调用单独的超时和有界线程池，失败时走原来的非模型逻辑，并用开关把这项能力关掉。模型返回先校验，再写入业务表。

先接一个读多、写少的场景，例如问答或草稿。需要改数据的工具，调用现有服务方法，沿用原来的事务和鉴权，不让模型直接访问数据库。

### 11. 微服务架构下，如何设计大模型服务模块

**参考答案**

厂商接入和业务决策分开。模型网关集中管密钥、配额、路由、重试、审计和流式转发。领域服务管提示词、检索、工具和业务规则，调用网关时传模板编号和变量，不把某一家的请求体复制到每个服务。

这样换厂商或轮换密钥只改网关。代价是多一跳，网关故障会变成全局故障，所以它要有限流、熔断和明确的超时预算。流式路径上的代理按块转发，不能缓冲成完整响应。只有一个小队、一种模型时，可以先做成库嵌进现有服务，等密钥和配额需要统一再拆出去。

长任务放进队列，调用方拿任务号查结果。同步链路上，模型超时算进用户请求的总预算，到点就失败或走备用逻辑。传给模型的业务数据按这次任务的最小字段裁剪，能不能查、能不能改仍由领域服务判断。

### 12. 如何监控和日志记录大模型调用情况

**参考答案**

Spring AI 把模型调用接在 Micrometer Observation 上，可以拿到耗时、错误、模型名以及输入和输出 token。按接口和模型聚合调用量、错误率、首 token 时间、总耗时和 token。告警看错误率、超时和 token 突增。费用用当期账单的单价去乘，不在代码里写死一个过期价格。指标的具体名字以当前版本文档为准，升级后对一下仪表盘。

日志记录关联 ID、会话 ID、模型、提示词版本、耗时、token、结束原因和厂商错误码，用来对上一次用户请求。提示词正文和完整回答可能含个人信息，不写进普通信息日志；需要审计时单独存储、脱敏，并规定保留期限。密钥和 `Authorization` 头不记录。网关和领域服务沿用原来的 trace，避免模型调用在链路上断成一段没人认领的耗时。

### 13. 如果模型 API 版本升级，如何平滑迁移

**参考答案**

业务代码停留在自己的门面和 `ChatClient` 上。模型名、Azure 部署名、端点和厂商 API 版本放在配置里，不散落在各个调用点。

升级先用同一套样本对比：任务是否仍成功、该拒的是否仍拒、工具参数有没有变、延迟和 token 有没有明显变坏。关键样本退步就停止放量。可以先打到影子流量或一小部分用户，追踪里记下模型版本和提示词版本，出问题能对上是哪一次变更。

厂商改字段或改路径时，只改适配层。结构化输出要兼容新旧字段，解析失败按错误处理，不把半截文本写进业务表。Azure 可以保持部署名不变、在后面更换模型版本，行为仍可能变，一样要跑样本。浮动别名随时会被厂商更新，稳定环境钉死快照。配置里保留上一版，开关能够马上切回去。

### 14. 除了 Spring AI，还了解哪些 Java 大模型开发框架

**参考答案**

Java 里常见的还有 LangChain4j、微软的 Semantic Kernel，以及接通义等阿里云模型的 Spring AI Alibaba。进程内推理是另一类库，例如 DJL，它负责加载和运行模型，不负责提示词、记忆和工具循环。

LangChain4j 把聊天、工具、记忆和嵌入库收成一个 AI Service 接口，Java 里把检索和工具先跑起来时资料比较多。Semantic Kernel 用 Kernel 把业务函数注册成插件，和 Azure 一起用时文档比较集中。Spring AI Alibaba 的调用方式贴近 Spring AI，已经在 Spring 上的团队少引入一套全新抽象。

现有系统是 Spring Boot、目标是接进现有配置和监控时，优先 Spring AI。某一家刚发布、starter 还没有的参数，再直接用 HTTP。服务已经用 LangChain4j 写完工具循环时，不必为了统一再包一层 Spring AI。两套框架各自维护调用循环，会话状态会分成两份。这些框架都不负责训练。

### 15. 未来在大模型应用开发领域，你关注哪些技术

**答题思路**

选一两件你真的读过或写过的，按「碰到的问题、看到的做法、边界在哪」讲。不要把趋势名词排成清单。

1. 从你接入时已经遇到的问题起：延迟、费用、输出不稳，或工具调用不可靠。
2. 只展开你能讲清限制的那一个方向。Agent 的工具循环、检索评测、模型网关、提示词和微调怎么选，挑你打开过文档或写过代码的。
3. 微调要能说出数据从哪来、谁标注、用什么标准判断它比提示词加检索更好。没做过就说判断标准还停在哪，不要编一个微调项目。
4. 收在你准备在现有 Java 服务里试的一小步。论文和框架只出你读过的那篇、用过的那一个。
