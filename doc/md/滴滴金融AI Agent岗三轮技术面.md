### 3. Java 中 volatile 关键字的作用及底层可见性实现原理

**参考答案**

volatile 用来发布状态：一个线程写完，其他线程能读到这次写入，并且读到新值时也能看到这次写之前的修改。`i++` 这种读改写仍然要靠锁或原子类。

JMM 规定，对同一个变量的 volatile 写 happens-before 之后的 volatile 读。编译器不能把写之前的普通写排到这次写后面，也不能把读之后的操作排到这次读前面。

HotSpot 在 x86 上，volatile 写会生成带 `lock` 前缀的指令，作为 StoreLoad 屏障，让此前的写对其他核可见；缓存一致性协议会把其他核上的旧缓存行置为失效。x86 本身是 TSO，volatile 读主要靠编译器不再重排，CPU 侧通常不再加单独的读屏障。写入仍然进缓存，随后由一致性协议传播。

适合放 volatile 的是停止标志、状态枚举这类单次写。双重检查锁里被发布的引用也要是 volatile，否则另一个线程可能拿到还未构造完的对象。计数和扣减用 `Atomic*` 或锁。

### 4. Java 线程池核心参数，以及任务提交后的完整执行流程

**参考答案**

`ThreadPoolExecutor` 的七个构造参数是 corePoolSize、maximumPoolSize、keepAliveTime、时间单位、workQueue、threadFactory、RejectedExecutionHandler。

`execute` 的顺序是：当前工作线程数小于 core，就新建核心线程执行；否则把任务放入队列；队列满了，才新建线程直到 maximum；再失败就走拒绝策略。入队之后如果发现线程池已经关闭，会把任务摘下来再拒绝；如果一个工作线程都没有，会补一个线程去跑队列里的任务，所以 core 设为 0 时任务也不会永远躺在队列里。

默认拒绝策略是 AbortPolicy，抛 `RejectedExecutionException`。另外三种是调用方自己跑、直接丢弃、丢掉队列里最老的任务再提交。非核心线程空闲超过 keepAliveTime 会回收；核心线程默认保留，除非打开 `allowCoreThreadTimeOut`。

无界队列不会满，maximumPoolSize 和拒绝策略都不会走到。Agent 的工具池要用有界队列，并按工具拆池，避免一个慢接口占满公共线程。

### 5. Spring Boot 中自定义 Starter 是如何被自动加载的

**参考答案**

自动配置不靠启动类的组件扫描。Starter 一般是一个依赖聚合，真正的配置类在自动配置包里，随依赖出现在 classpath 上。

`@SpringBootApplication` 带有 `@EnableAutoConfiguration`。`AutoConfigurationImportSelector` 读取清单：Spring Boot 2.7 起使用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，更早的版本写在 `META-INF/spring.factories` 的 `EnableAutoConfiguration` 项下。Boot 3 只认前面的 imports 文件。

清单里的类用 `@AutoConfiguration` 或 `@Configuration`，再加 `@ConditionalOnClass`、`@ConditionalOnProperty`、`@ConditionalOnMissingBean`。条件不满足就不会注册。`@ConditionalOnMissingBean` 让业务自己声明的 Bean 留下，自动配置的默认实现退开。配置项用 `@EnableConfigurationProperties` 绑定到 `@ConfigurationProperties`。多个自动配置之间用 `@AutoConfigureBefore` / `@AutoConfigureAfter` 排顺序。

加载失败时先看依赖有没有进来、imports 路径是否写对、条件注解是否把配置类排除了。

### 6. Redis 常用数据结构，你在项目中用 Redis 做过哪些事

**参考答案**

常用的是五种基础结构和 Stream。String 适合缓存、计数和 `SET key value NX PX` 这种带过期的占位。Hash 用来存一个对象的多个字段。List 用来保留最近 N 条或做简单队列。Set 用来去重和做交并差。ZSet 按分数排序，适合排行榜和延迟任务。Stream 带消费组，适合组内各自确认的消息。

底层编码会随长度变化：短 List、Hash、ZSet 常用 listpack，变长后 List 变成 quicklist，ZSet 变成跳表加哈希。面试里讲清用途即可，编码作为被追问时的补充。

项目部分只讲你真实用过的两件。每件说清 key 怎么设计、TTL 放在哪、和数据库谁是准的。缓存就讲更新时先改数据库还是先删缓存，以及失败怎么补偿。计数限流就讲 key 的粒度和过期窗口。会话就讲登录态和对话槽位为什么要分开过期。锁如果被追问，再讲删除时必须校验持有者，避免删掉别人的锁。

### 7. Redis 缓存击穿、穿透、雪崩的区别及应对方案

**参考答案**

三者差在「失效的是什么」。穿透是这个 key 在数据库里也不存在，请求每次都穿过缓存。击穿是一个热点 key 过期的瞬间，大量请求同时打到数据库。雪崩是很多 key 同时过期，或者 Redis 本身不可用，流量成片落到数据库。

穿透先做参数校验，再用布隆过滤器挡掉明显不存在的 key。布隆会把不存在误判成可能存在，所以挡完之后，对确认没有的结果仍写一个短 TTL 的空值。击穿用互斥重建：只放一个请求回源，其余等待或先返回旧值；也可以不设硬过期，在 value 里放逻辑过期时间，过期后仍返回旧值并异步刷新。雪崩给 TTL 加随机抖动，热点改为后台刷新；Redis 侧用主从或集群。Redis 整体不可用时，入口要限流，并准备可以拒绝的降级，不能把全部请求放进数据库。

### 8. MySQL 联合索引最左匹配原则，哪些写法会用不到索引

**参考答案**

联合索引 `(a, b, c)` 先按 a 排序，a 相同再按 b，然后按 c。查找必须从最左列开始连续使用，所以 `a`、`a+b`、`a+b+c` 的等值条件都能用来定位。等值条件书写顺序可以颠倒，优化器会调整，`where b = ? and a = ?` 仍能用 `(a, b)`。

用不全或用不上的常见写法：

- 跳过 a，只写 `b`、`c`。MySQL 8.0 的索引跳跃扫描只在前导列区分度很低时偶尔用上，不能当成常规计划。
- a 已经是范围条件，后面的 b、c 不能再用于定位。`a = ? and b > ?` 之后的 c 同样不能用于定位，最多作为索引条件下推做过滤。
- 对索引列做函数或计算，发生隐式类型转换（字符串列和数字比较），`like '%xx'` 这种前导模糊。
- `<>`、`NOT IN` 这类否定条件经常无法做有序定位。`OR` 一侧用不上这个索引时，整句常常改走别的计划。

优化器还可能因为回表成本判断全表扫描更便宜。用 `EXPLAIN` 看 `key` 和 `key_len`，确认实际用了几列。

### 9. 什么是 RAG（检索增强生成），简要说明离线与在线流程

**参考答案**

RAG 是先从外部知识里检索证据，再把证据和问题一起交给模型生成。金额、条款、产品规则以检索结果为准，用来减少模型凭参数记忆编造。

离线把知识准备好：解析文档、去掉页眉目录和过期版本，按标题或段落切块并限制长度，必要时保留块之间的重叠。每块带上来源、生效时间和权限，做 embedding 后写入向量索引，专有名词和单号同时进关键词索引。

在线处理一次提问：多轮场景先把问题改写成独立问句，再做向量召回，并与关键词召回合并。按权限和生效时间过滤，精排后取少量证据拼进提示词，要求回答引用依据。生成后做忠实度检查，数字应能在证据或接口结果里找到。

检索质量和生成质量要分开评。检索没命中时，模型答得再流畅也是错的。

### 10. 做意图识别时，如果用户 query 很短且有歧义，你一般怎么处理

**参考答案**

短句缺少槽位，分类分数又经常挤在一起，这时硬选一个意图容易把查询做成办理。先判断信息够不够，再决定执行、澄清还是拒掉。

具体做四件事：

1. 用上下文补全。上一轮意图、已确认槽位、当前页面都能消掉「这个呢」这类说法。补全后再分类。
2. 看置信度和分差。最高分低于阈值，或前两名差距很小，就判定为不确定。短 query 的阈值要比完整句子更严。
3. 不确定时只问一个区分度最高的问题，例如「看昨天的支出，还是看还款日」。澄清有轮次上限，避免反复追问。
4. 按风险分路。查账单可以给出最可能结果并说明假设；转账、还款、解约在歧义未消除时不调用写接口。

澄清后的说法和最终意图要记回坏例集，用来补规则、同义词或训练样本。

### 11. LangChain 中 Chain 和 Agent 的区别是什么

**参考答案**

Chain 的下一步由代码写死，Agent 的下一步由模型在运行时选择。

Chain 把提示词、模型和解析器串成固定管道，例如检索、拼提示、生成。输入输出类型明确，延迟和成本可以估算，回归测试也好写。LangChain 里对应 LCEL 的 `Runnable` 组合。

Agent 则进入循环：模型决定调用哪个工具、框架执行后把观察结果放回上下文，再让模型决定继续还是结束。路径能随问题变化，也因此会出现选错工具、参数编造和步数失控。生产里必须有最大步数、总超时、工具白名单和参数校验。

能写成固定步骤的用 Chain 或工作流；只有工具组合事先定不下来的那一段交给 Agent。金融里的查账、下单应由确定性代码调用接口，模型负责理解意图和组织语言。

### 12. 如果让你设计一个 AI Workflow Harness（统一入口、超时、重试、降级），你会考虑哪些点

**参考答案**

Harness 是所有模型调用和工具调用的统一入口，业务代码不直接依赖某一家模型 SDK。一次请求在这里带上 traceId、用户、场景和提示词版本。

超时拆开设：排队超时、首 token 超时、整次请求超时。超时后要取消下游流式生成，只在本地停止等待，费用和连接仍会占着。

重试只覆盖连接失败、429 和 503，并且加上限次数、指数退避和抖动。参数错误不重试。会改状态的工具默认不自动重试，要重试必须带同一个幂等键。

降级按主模型、小模型、模板拒答逐级进行，用错误率和慢调用比例熔断，单次失败只进入重试。查余额、利率、账单时，小模型只能组织语言，数字必须来自接口；接口失败就模板拒答。内容安全拒绝要直接结束，不再换一个模型试。

入口同时做按用户和按场景的 QPS 与 token 预算，并把模型、token、耗时、重试次数和是否降级打进同一条 trace。降级结果单独标记，避免可用性指标把质量下降盖住。

### 13. 你们用的向量数据库是什么，embedding 模型怎么选的，维度多少

**答题思路**

先报你真实使用的库、模型和维度，再说选择理由。维度以该模型的官方说明为准，查询和入库必须是同一个模型、同一种归一化。很多模型要求先做 L2 归一化，之后用内积，效果与余弦相同。常见中文 embedding 的维度在 768 或 1024 这一档，回答时报你线上的数字。

选型理由按这几个点准备：

1. 数据量和写入方式。要独立扩展、海量向量，用 Milvus 这类专门的库；数据量中等、还要和业务条件一起过滤，用 pgvector；已经有 Elasticsearch，就用它的 dense_vector 和 BM25 做混合检索。
2. 模型是否覆盖中文、金融专有名词，以及是否要同时出稠密向量和稀疏向量。换模型必须重建索引，两个模型的向量不能放进同一个索引比距离。
3. 准备被追问的三个细节：chunk 怎么切、召回 topK 之后有没有精排、权限和生效时间是在检索时过滤还是事后过滤。

没做过向量检索就直接说没有落地，再讲你会怎么选，不把方案说成线上架构。

### 14. 手撕：给一个字符串数组，找出所有能组成 target 的两个字符串（字符可重排），返回下标

**参考答案**

定义先说清：`words[i]` 和 `words[j]`（`i < j`）的字符计数相加，正好等于 `target` 的字符计数。拼接顺序不影响结果。例如 `["ab","ba","abc"]` 和 `target = "abab"` 只返回 `[0,1]`，`abc` 多出来的 `c` 不能参与。

对每个字符串统计字符频率。它的计数有任何一项超过 target，就不可能是一对中的一个。否则 target 减去它，得到「还缺的那一半」的频率。用频率做 key，前面已经见过的下标放进哈希表。处理当前下标时先查这个补集，命中就组成一对，再把自己放进表，这样同一个下标不会和自己配对，一对也只会出现一次。

下面按小写英文字母来写。字符集更大时，把长度 26 的数组换成有序的字符计数映射，key 的做法不变。时间是 `O(总字符数 + 26n)`，空间 `O(n)`。命中对特别多时，输出本身可能到 `O(n²)`。

```java
public List<int[]> findPairs(String[] words, String target) {
    int[] need = count(target);
    Map<String, List<Integer>> seen = new HashMap<String, List<Integer>>();
    List<int[]> ans = new ArrayList<int[]>();
    if (need == null) {
        return ans;
    }
    for (int i = 0; i < words.length; i++) {
        int[] cur = count(words[i]);
        if (cur == null || !within(cur, need)) {
            continue;
        }
        List<Integer> hit = seen.get(key(diff(need, cur)));
        if (hit != null) {
            for (int j : hit) {
                ans.add(new int[]{j, i});
            }
        }
        String self = key(cur);
        List<Integer> bucket = seen.get(self);
        if (bucket == null) {
            bucket = new ArrayList<Integer>();
            seen.put(self, bucket);
        }
        bucket.add(i);
    }
    return ans;
}

private int[] count(String s) {
    int[] c = new int[26];
    for (int i = 0; i < s.length(); i++) {
        char ch = s.charAt(i);
        if (ch < 'a' || ch > 'z') {
            return null;
        }
        c[ch - 'a']++;
    }
    return c;
}

private boolean within(int[] cur, int[] need) {
    for (int i = 0; i < 26; i++) {
        if (cur[i] > need[i]) {
            return false;
        }
    }
    return true;
}

private int[] diff(int[] need, int[] cur) {
    int[] d = new int[26];
    for (int i = 0; i < 26; i++) {
        d[i] = need[i] - cur[i];
    }
    return d;
}

private String key(int[] c) {
    StringBuilder sb = new StringBuilder();
    for (int i = 0; i < c.length; i++) {
        if (i > 0) {
            sb.append('#');
        }
        sb.append(c[i]);
    }
    return sb.toString();
}
```

### 2. 详细讲你参与过的 AI Agent 或多轮对话系统，把整体架构口述出来

**答题思路**

用你自己的系统讲，按数据往下走，每个框只说输入、输出和失败时去哪。

1. 入口：文本或语音。语音先转写，低置信度先确认文本。网关做鉴权、限流，并从登录态取用户，不从话术里取身份。
2. 会话状态：意图、已确认槽位、最近几轮原文、更早的摘要。状态要能按会话 id 读出来。
3. 理解：意图分类和槽位填充。缺关键槽位就澄清，写操作比查询多一轮确认。
4. 知识：需要条款、产品说明时走 RAG；需要余额、账单时走金融接口。两条路的结果都当成证据，不让模型改数字。
5. 工具执行：参数校验、超时、幂等键、独立的连接池。失败返回明确错误码。
6. 生成：模型只组织语言，并带上口径，例如统计的是哪一天、含不含退款。
7. 横切：trace 里能看到每一步的耗时、模型版本、工具入参和是否降级；坏例能回放。

讲完主动留三个追问位：状态存在哪、进程重启后能不能继续、写接口超时后怎么查单而不是再提交一次。

### 3. 多轮对话里如何维护上下文窗口，长会话怎么做截断和摘要

**参考答案**

上下文按预算分层保留，预留生成所需的 token，历史只能用剩下的部分。预算用尽时截断旧内容，而不是等模型侧报超长。

优先级从高到低是：系统约束和工具协议、结构化槽位、最近几轮原文、更早对话的摘要。金融字段放进结构化状态，包括账户、时间范围、金额口径、用户刚确认过的选择。用户更正后以新槽位为准。摘要只作为补充，因为摘要会把数字说丢或说错。

滚动摘要的做法是：对话达到阈值时，把旧摘要和即将被挤出的轮次压成新摘要，摘要里保留未完成事项、已否决的选项和关键实体。截断以一整轮为单位，不把一对用户和助手消息从中间切开。工具返回很长时，上下文里只留摘要和可回查的 id。

容易漏掉的是摘要本身也占 token；指代消解要用摘要加最近一轮，单独拿最后一句会把「昨天呢」理解错。

### 4. LangGraph 相比 LangChain 顺序 Chain 的优势是什么，怎么画状态机，怎么处理分支和循环

**参考答案**

顺序 Chain 是一条预先连好的管道，分支和循环都要嵌进代码里。LangGraph 把步骤做成图上的节点，共享一份状态，分支和循环都是显式的边，每个节点的输入输出可以单独追踪，也可以按检查点恢复。

状态用一个 schema 表示，例如消息、意图、槽位、步数、工具结果。节点只返回自己修改的字段，由 reducer 合并；消息列表一般是追加，槽位是覆盖。图编译时挂上 checkpointer，进程中断后能从上次节点继续。

可以画成这些节点：理解、澄清、检索、工具、生成、结束。条件边根据状态选择：

- 缺关键槽位 → 澄清 → 回到理解。
- 槽位齐全且要查数 → 工具；要查条款 → 检索。
- 工具成功 → 生成 → 结束。
- 工具失败且仍有剩余次数 → 回到工具；步数或时间用尽 → 拒答。

循环必须写在条件边上，并检查步数、重复调用和总超时。只在图上连一条回到自己的边，运行时会一直转。

### 5. 多 Agent 协作时，怎么避免 Agent 之间死循环调用或无限递归

**参考答案**

每个 Agent 自己的步数上限挡不住互相委托。要在协作协议上加退出条件。

职责先收成树：路由只负责选择，执行 Agent 只向父节点返回结果，不能再去调路由或其他执行者。必须移交时，返回里带上 `done`、`need_user` 或 `handoff`，以及原因。同一个问题、同一组参数的移交只允许发生一次。

运行时做三道限制。全局最大跳转次数、每个 Agent 的最大步数、墙钟时间和 token 预算，任一到达就带着已有结果退出。把 `(调用方, 被调方, 工具, 参数摘要)` 放进最近的调用序列，连续重复就判定为循环并停止。用户可见的写操作不参与自动移交，停下来问人。

观察上把每次移交打进 trace。只看最终回复，来回调用会表现为变慢和变贵，原因却看不出来。

### 6. 意图识别模块如果线上 bad case 突然增多，你怎么排查（日志、标注、回放）

**参考答案**

先确认是整体掉了，还是某一类掉了。按时间、入口、意图看准确率和混淆矩阵，并和最近的发布对齐：模型版本、阈值、规则、提示词、上游转写是否一起变了。

日志里一条请求要能串起来：原文、上下文、规则是否命中、分类分数、最终意图、有没有澄清、模型和词表版本。缺任何一段，就分不清是识别错了还是下游执行错了。

然后分层抽样标注，头部高频句和长尾各抽。标的是金标意图，以及这句到底该执行、该澄清还是该拒绝。金融场景把「没识别出来」和「识别成了另一个会触发写操作的意图」分开统计，后者优先。

用当时的请求快照回放，固定模型和特征，区分服务故障和用户说法变了。定位之后再改：缺槽位就收紧澄清，新说法就补样本或同义词，分数挤在一起就调阈值。改完把这批坏例放进回归集，再用同一套回放看有没有把原来对的打坏。

### 7. RAG 召回阶段，召回少和召回噪声大分别怎么优化（chunk、rerank、hybrid）

**参考答案**

两件事用不同的旋钮。召回少时放宽召回，噪声大时在精排收紧。用同一个 topK 同时解决两边，通常会左右互踩。

召回少，先查证据有没有进索引、权限过滤是不是太严、topK 是不是太小。切块太大时主题被稀释，太碎时例外条款被切开。按标题切，并限制长度；检索用小块，把父块交给模型。用户用词和文档不一致时做查询改写。单号、产品代码和专有名词同时走关键词检索，和向量召回做 hybrid。embedding 模型与语料不匹配时，换模型并重建索引。

噪声大，先清洗目录、页眉和重复的重叠块，并按生效时间过滤过期制度。召回可以多取一些，再用 cross-encoder 精排后只留少数几条。完全匹配到条款编号时直接加权或走精确过滤。hybrid 的权重用标注集调整。

评测时召回率和答案忠实度分开看。召回率上去之后，如果模型仍把无关段落写进答案，问题已经不在召回。

### 8. Kafka 在你们系统中用在哪，如何保证消息不丢失和幂等消费

**参考答案**

先讲你系统里的真实用途，例如对话日志、审核、知识库增量或账单通知。下面的可靠性配置与具体业务无关，核心是：生产者和 broker 保证已确认的消息还在，消费者做到至少一次，业务侧把重复消费变成一次生效。

生产端使用 `acks=all`，并让 `min.insync.replicas` 至少为 2，这样确认时不只写在 leader 上。关闭 unclean leader election，避免一个落后副本被选成 leader 后截断已确认的数据。打开生产者幂等，重试不会因为换序写出重复；它要求 `acks=all`，且 `max.in.flight.requests.per.connection` 不超过 5。发送失败要进入可恢复的重试或缓冲，不能把异常吃掉。

消费端先处理成功，再提交 offset。自动提交可能在处理前就提交，进程崩溃后这条消息不会再来。由此得到的是至少一次，重复不可避免。

幂等靠业务键。订单号或消息 id 在数据库里建唯一约束，业务写入和「已处理」标记放在同一个事务里。重复投递会撞上唯一约束而跳过。只放在 Redis 里做去重，会出现去重成功但业务写入失败，或相反的窗口。Kafka 事务能保证消费位点与写出到 Kafka 的原子性，外部数据库仍要靠这层唯一约束。

### 9. Elasticsearch 全文检索与向量检索结合时，你怎么做 score 融合

**参考答案**

BM25 的分数和向量相似度不在一个尺度上，原始分直接相加没有意义。两路各自取一批候选，过滤条件（权限、生效时间、租户）在两路都生效，再在候选集上融合。

稳妥的融合是 RRF：每一路按名次贡献 `1 / (k + rank)`，再相加。`k` 常用 60，只用名次，不受两路分数尺度影响。这个常数可以用标注集再调。

另一条路是各自归一化后加权。min-max 受当次候选的最大最小值影响，不同请求之间不稳定，所以只适合作为试验。权重必须用标注集选，产品代码、条款编号这种完全命中应当作硬条件或单独的强加权，不交给向量距离碰运气。

融合后的名单仍是召回结果。最终顺序交给 cross-encoder，或再加上新鲜度等业务特征。ES 版本若自带 RRF retriever，可以把融合下推到引擎；应用层做融合则更容易打日志和回放。

### 10. 用户问「我想查我昨天花了多少钱」，从 ASR/NLU 到意图、槽位填充、调金融接口、生成回复，设计全流程

**参考答案**

这条链路是只读查询。模型负责理解说法，金额只来自账务接口。

1. 语音先转写，并给置信度。置信度低时先跟用户确认文本。文本入口跳过这一步。「花了多少钱」要和转账、还款分开，避免短句进错意图。
2. 意图定为查询支出。分数低或和邻近意图分差很小，就澄清一句：「看昨天的支出总额吗？」写操作的意图不能靠猜测进入。
3. 槽位填三个：时间、指标、账户范围。昨天按用户时区换成左闭右开的绝对区间，从昨日 0 点到今日 0 点。指标是支出总额。账户默认用登录态里该用户的支付账户，并在回复里说明口径。身份只用登录态，不用话术里的姓名。
4. 调用只读接口，参数是用户、时间区间和币种。套上 Harness 的超时和熔断。返回 0 是合法结果；超时和错误要另说「这次没查到」，不能说成没花钱。
5. 生成时把金额、笔数和口径原样写进回复，提示词约束模型不得改写数字。支出口径要事先定义是否包含退款、转账和还款，回复里用同一套定义。可以追问是否看明细。
6. 日志记录意图、槽位、接口返回码和耗时，不记录完整卡号。

关键取舍是：只在时间或口径会影响金额时才澄清，其余用明确口径直接回答。

### 11. 手撕：二叉树层序遍历，按层输出 List<List<Integer>>

**参考答案**

用队列做广度优先。空树返回空列表。根入队后，每一轮先记下队列长度，这个长度就是当前层的节点数；只弹出这么多个节点，并把它们的非空孩子放进队尾，下一轮看到的就是下一层。

时间 `O(n)`，每个节点入队出队一次。队列最宽处与输出列表都是 `O(n)` 空间。分层要靠这一轮的 size，不要在遍历中途用空节点当分隔符，除非先定义空节点怎么放。

```java
public List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> ans = new ArrayList<List<Integer>>();
    if (root == null) {
        return ans;
    }
    Queue<TreeNode> queue = new ArrayDeque<TreeNode>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();
        List<Integer> level = new ArrayList<Integer>(size);
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            level.add(node.val);
            if (node.left != null) {
                queue.offer(node.left);
            }
            if (node.right != null) {
                queue.offer(node.right);
            }
        }
        ans.add(level);
    }
    return ans;
}
```

### 2. 你们的 AI Harness 里，如何做 Token 限流、单个请求超时、模型降级（主模型 → 小模型 → 拒答）

**参考答案**

三件事都放在统一入口，业务拿不到模型客户端。

Token 限流分两层。入口先按用户、应用和模型限制 QPS，挡住突发请求数；再按 token 做预算，因为一次超长上下文的成本远高于一次短请求。调用前用 tokenizer 估算输入并预占，流式过程中累计输出，超过单次上限就截断并取消下游。分布式配额用 Redis 令牌桶，本地先扣一小段，减少每次都打 Redis。预算不够时直接返回明确错误，只给少数高优先级场景排队，排队本身也有超时。

单次超时从入口下发 deadline，拆成排队、首 token 和总时长。时间到了就中止上游生成。超时计入熔断统计。

降级顺序是主模型、小模型、模板拒答。熔断看一段时间的错误率和慢调用比例，而不是一次失败就换模型。小模型只承担解释和澄清。余额、账单、利率没有工具结果时用模板说暂时查不到，不用小模型补数字。内容安全命中后直接结束。降级响应打上标记，监控里和主模型的成功率分开。

### 3. Agent 调用外部工具（HTTP/RPC）时，怎么处理重试、幂等，以及慢调用拖垮主链路

**参考答案**

工具调用和模型调用分开隔离。每个工具有自己的超时、连接池和熔断，超时必须小于用户请求还剩的时间。

重试只针对连接失败、超时、429 和 503，次数少，并加指数退避和抖动。参数错误、无权限不重试。查询接口可以重试。转账、还款这类写接口不自动重试；超时后用业务单号查状态，再告诉用户结果，避免提交两次。

幂等键由用户、工具名、规范化参数和这一次动作的 id 组成，一次动作的多次重试共用它。键里不要放当前时间，否则每次都是新请求。服务端用这个键保证同一动作只生效一次。

慢调用用舱壁隔开：慢的第三方和快的内部接口不用一个池。某个工具的慢调用比例或错误率过高就熔断，对话改为说明暂时办不了。可以异步的动作先回复「已受理」，完成后再通知，回复文案要和「已经办理成功」区分开。重试如果没有熔断，故障恢复时会把下游再打满。

### 4. 如果公司要求你推动团队从裸调 LLM API 迁移到统一 Agent Framework，你怎么做方案评审和灰度

**参考答案**

先摸清现状：哪些服务在直连模型、提示词放在哪、有没有 trace 和评测集。没有基线就先补最小评测，再谈迁移。

评审时把框架边界写死。统一的是模型路由、工具协议、限流、超时、降级和审计；意图和业务规则仍留在业务侧。对着一个真实场景对比自研和开源：缺的能力、许可证、和现有 Java 服务怎么接、状态存在哪、失败能否回到旧链路。用一个低风险的只读场景做样板，拿出延迟、成本、任务成功率和误调用率，不拿演示当结论。

灰度按场景和用户比例切。只读请求可以双跑对比意图、工具参数和答复；有副作用的工具不能双调。不一致的请求进标注。资金相关的误操作作为一票否决。入口留分钟级开关，旧链路在灰度期间保持可运行。顺序是先迁只读，最后迁写操作，写操作保留人工确认。

平台要留逃生口，例如指定模型和跳过可选能力。逃生口如果也没有，业务会绕过框架，统一就失败了。

### 5. 你们在做 RAG 或 Agent 时遇到的最大坑是什么，怎么解决的

**答题思路**

讲一个你真遇到的问题，两分钟，按一条线讲完。没有落地经验就说没有，再分析一个你知道的风险，把两件事分开。

1. 现象落到一个指标：答非所问、金额错误、工具来回调用，或成本突然升高。
2. 只认定一个主因，例如切块把例外条款切开、提示词允许模型复述时改写数字、两个 Agent 互相移交、改提示词没有回归集。
3. 定位过程：哪条 trace、哪批坏例、怎么回放才确定是这个原因。
4. 修复要对应原因：改切块并返回父块、数字只允许从接口字段填入、加移交次数和重复检测、把坏例收进回归集。
5. 结果用前后对比。没有百分比就说明还剩什么问题，以及你怎么继续看。

面试官会追问你怎么防止它再生。结尾落在回归集和发布检查上。

### 6. MySQL 大表加字段你一般怎么做（online DDL、pt-osc），对读写有什么影响

**参考答案**

先确认能不能 `ALGORITHM=INSTANT`。MySQL 8.0.12 起，把列加在表尾多数只改数据字典；8.0.29 起，更多位置的加列、删列也可以 INSTANT，但压缩行格式等场景仍然不行。语句里显式写 `ALGORITHM=INSTANT`，做不到就失败，避免悄悄退回重建整表。INSTANT 对读写几乎没有持续影响，开始和结束仍有很短的元数据锁。从库版本更老时，同一条语句可能在从库上变成重建，复制延迟会拉得很长。

不能 INSTANT 的变更，例如改类型，用 gh-ost 或 pt-osc。两者都是建影子表、分批拷数据、追增量，最后用一次改名切换。切换期间有短锁，整个过程读可以继续，磁盘大约要再留一份数据。pt-osc 靠触发器同步增量，写延迟在拷贝期间都会变高，表上本来就有触发器时不合适。gh-ost 解析 binlog，不靠触发器，要求行格式 binlog 和可用的主键或唯一键。

无论哪种，长事务会占着元数据锁，后面的 DDL 和查询都会排上。执行前先看未提交事务、磁盘和复制延迟，放在低峰，并先在从库验证。

### 7. Redis Cluster 比单机主从好在哪，迁移 slot 时有读到脏数据的风险吗

**参考答案**

主从复制是一份全量数据，写都在同一个 master，容量和写 QPS 受单机限制，优点是多 key 事务和 Lua 都在本地。Cluster 把数据分成 16384 个 slot，按 key 的 CRC16 映射，每个 slot 有自己的主从。容量和写可以随分片扩展，故障也先限制在一个分片里。代价是多 key 操作必须落在同一个 slot 里，通常用 hash tag；客户端要处理重定向。

迁移时，源节点把 slot 标为 MIGRATING，目标标为 IMPORTING。单个 key 由 `MIGRATE` 同步搬到目标再从源删除，单线程执行，读不到写了一半的 value。key 还在源上就由源处理；源上已经没有、slot 仍未交接完时，源返回 ASK，客户端到目标重试这一次，并且不要更新本地槽位表。槽位已经归新节点所有时返回的是 MOVED，客户端才更新路由。

正确处理 ASK 和 MOVED 时，一个 key 只会由当前持有它的主节点服务。风险来自客户端：把 ASK 当成 MOVED，后续请求会提前打到目标；或者把重定向过程中的空结果当成不存在，再回填一份旧值，源和目标就会各有一份。另外，如果去读从节点，异步复制本身会读到旧值，这和是否正在迁 slot 是两件事。大 key 的 `MIGRATE` 会堵住源节点，表现为延迟抖动。

### 8. 你平时怎么跟进 LLM、Agent 新技术，举一个你最近学到并落地或打算落地的点

**答题思路**

用固定的信息源和一次真实验证来回答，少报名单。

1. 信息源控制在一两处：框架的 release note、模型供应商的接口变更、你正在用的那类论文或工程博客。定一个很短的周期看，而不是刷信息流。
2. 筛选标准只留和当前链路有关的：上下文长度、工具调用协议、检索融合、评测、推理成本。和现有系统无关的先记下来。
3. 举一个最近的点，按「当时的问题 → 它解决哪一段 → 你用什么离线集或影子流量验证 → 上线了还是暂缓」来讲。可以是混合检索的名次融合、长对话改成槽位加摘要、给工具循环加步数上限。没上线就说卡在评测、延迟或风险。
4. 收益只用你测到的。没有数字就说明你准备拿哪几个指标做决定。

### 9. 如果组内新人不懂 LangChain 和 RAG，你如何带他上手

**答题思路**

目标是让他独立改一个小场景并知道怎么验证，而不是先看完框架文档。

1. 第一天跑通一条已有请求：从入口到意图、检索、工具、生成，让他改一句话就能看到输出变化。环境问题你先帮他排掉。
2. 阅读顺序是架构图、一条真实 trace、离线怎么切块和建索引、在线怎么召回和过滤，最后再看框架代码。先讲固定管道和带工具循环的差别，再把这个差别对应到 LangChain 的 Chain 和 Agent。
3. 给他一个有标准答案的任务：补一条评测样本，或给某一类问法加澄清。要求写明输入、期望命中的证据、失败时长什么样。
4. 评审时看三件事：有没有把整篇文档塞进提示词、工具有没有超时、提示词改了有没有留下版本。
5. 第一周用很短的每日对齐看他卡在概念还是环境。他能独立解释一条坏 trace 时，再让他碰状态机和多 Agent。

### 10. 当你和 TL 在技术选型（自研 vs 开源框架）上意见不合，你通常怎么沟通

**答题思路**

把分歧从立场改成同一组约束，再约定怎么验证。

1. 先复述 TL 在意的点：交付时间、人力、许可证、供应商锁定、出了问题能否回滚。确认你们在争的是同一件事。
2. 把自己的依据写成可以核对的条目：现成框架已经覆盖什么、还缺什么、缺的部分要改框架还是放在框架外面、自研要维护哪些模块。
3. 提议一个限时对比，用一个真实场景做小样，比稳定性、接入成本和能不能回到旧链路。时间盒定死，避免开放式争论。
4. 能拆开就拆开，例如开源框架负责图编排，审计、权限和降级仍走自己的 Harness。
5. 方案定了就按决定执行，并把风险和回退写进评审记录。涉及资金安全这类你认为不能让的点，把后果说清楚，然后接受 TL 拍板，事后用线上数据复盘。

### 11. 手撕：编辑距离（Levenshtein Distance），可用于意图模糊匹配

**参考答案**

编辑距离是把字符串 `a` 变成 `b` 的最少操作次数，允许插入、删除、替换一个字符，每种代价为 1。`dp[i][j]` 表示 `a` 的前 i 个字符变成 `b` 的前 j 个字符所需的最少次数。

边界是 `dp[i][0] = i`、`dp[0][j] = j`，对应删光或插满。若当前两个字符相同，`dp[i][j] = dp[i-1][j-1]`。否则取删除、插入、替换三者的最小值再加 1。时间 `O(nm)`，二维表空间 `O(nm)`，可以滚成两行，空间降到 `O(min(n,m))`。

意图匹配时，先用关键词或向量召回少量候选，再算距离。阈值用距离相对句长来定。短词差一个字就可能是另一个意图，例如还款和换款，不能只凭距离去调金融接口。中文按字符算；Java 里一个 `char` 对常用汉字够用，生僻字可能占两个 `char`，比较前可以先转成码点。同音不同字的距离可能很大，需要时再加拼音候选。

```java
public int minDistance(String a, String b) {
    int n = a.length();
    int m = b.length();
    int[][] dp = new int[n + 1][m + 1];
    for (int i = 0; i <= n; i++) {
        dp[i][0] = i;
    }
    for (int j = 0; j <= m; j++) {
        dp[0][j] = j;
    }
    for (int i = 1; i <= n; i++) {
        for (int j = 1; j <= m; j++) {
            if (a.charAt(i - 1) == b.charAt(j - 1)) {
                dp[i][j] = dp[i - 1][j - 1];
            } else {
                int replace = dp[i - 1][j - 1];
                int delete = dp[i - 1][j];
                int insert = dp[i][j - 1];
                dp[i][j] = 1 + Math.min(replace, Math.min(delete, insert));
            }
        }
    }
    return dp[n][m];
}
```

## HR面

### 1. 自我介绍

**答题思路**

HR 这一轮用非技术版本，45 秒到 1 分钟。

1. 你是谁：年限、现在的方向、最近在做 AI 应用还是业务后端。
2. 做过什么：一个项目用业务语言讲，用户得到了什么，你在其中的角色是什么。
3. 为什么坐在这里：想在金融业务里把 Agent 做到能上线，强调准确性、权限和可追查，少讲框架名。
4. 结尾停住，把时间留给动机和协作，不展开架构。

### 2. 为什么想换工作，为什么投滴滴金融 AI 岗

**答题思路**

准备一个主因，正向说完，再接到这个岗位。

1. 换工作的原因只留一个：业务方向调整、现有工作接触不到完整的 Agent 链路，或你希望从单点功能走到整条线上系统。事实按你的情况讲。
2. 前公司用「我接下来想获得什么」来表达。不评价前同事和管理。
3. 为什么是这个岗位：金融查询和办理对错一个数字代价很高，Agent 必须和检索、工具、审计做在一起，这和你想深入的方向一致。
4. 补一句你已经做过的相关事，让动机落在经历上，而不是只说感兴趣。
5. 如果被问「还在看哪些机会」，说你重点看能把 Agent 做到生产的团队，标准一致即可。

### 3. 你觉得自己做 AI Agent 方向最大的优势是什么

**答题思路**

只讲一个优势，并且能用一件事证明。

1. 优势落在「能把模型和工程接起来」：你会把意图、检索、工具、超时和评测放进一条链路，而不是停在调通接口。
2. 用一个例子证明：曾经哪类错误会直接影响用户，你加了什么约束，后来怎么确认它不再出现。
3. 承认边界：哪一块你还在补，例如评测体系或多 Agent 协作，用你正在做的动作说明。
4. 避开「学习能力强」「抗压」这类说法，除非后面立刻有事实。

### 4. 工作中遇到最难搞的事是什么，怎么处理的

**答题思路**

选一件已经收尾、而且你本人有动作的事。用 STAR 讲，控制在两分钟。

1. 背景：业务或线上出了什么问题，影响的是用户、进度还是稳定性。
2. 你的责任：你负责哪一段，谁还需要参与。
3. 难在哪里：技术不确定、跨团队意见不合，或缺少评测无法判断改好了没有。只选真正难的那一个。
4. 你的动作：怎么拆开问题、怎么对齐、做了什么取舍。遇到反对时，你补充了什么证据。
5. 结果：问题怎么结束的，你留下了什么机制防止再生。没有数字就讲结果的状态。过程中你的失误也可以讲一点，接着说你后来怎么改的。

### 5. 你期望的技术成长路径是 IC 深入还是将来带方向

**答题思路**

给出明确的近期选择，并说明判断标准。

1. 近期选 IC 做深：把一条 Agent 链路从效果做到稳定性，包括评测、降级、工具治理和线上问题定位。讲你还缺的那一块能力。
2. 带方向的前提说清楚：当你能对一条链路的质量和故障负责，并且已经在带新人做小任务时，再扩大范围。现在如果还没有这个基础，就不要把管理当成下一步。
3. 说明你理解的带方向是定边界、评测和评审，不是离开代码。
4. 问一句这个组当前更需要独立负责模块的人，还是带小团队的人，把你的选择和岗位对齐。

### 6. 对加班、on-call、业务压力的看法

**答题思路**

态度具体到场景，避免表态成永远在线或完全不加班。

1. 上线、故障和关键活动期间你可以投入，也接受轮值 on-call。说一下你做过的类似经历。
2. 你希望排班、交接和事后复盘是清楚的，问题修完会留下手册或告警，而不是靠同一个人记住。
3. 日常压力你用工程手段消化：超时、降级、限流和回滚开关，减少夜里靠人肉撑着。
4. 如果问到强度，先问清这个组 on-call 的频率和最近的故障情况，再给出你的接受范围。

### 7. 期望薪资范围及入职时间

**答题思路**

薪资给区间，入职时间按真实档期说。具体数字只用你自己的现有总包和市场判断，这里不预设。

1. 先确认职级和总包结构：月薪、年终、签字费或其他部分是否分开谈。
2. 区间的下沿放在你能接受的总包，上沿留出谈的空间。说明你更看重职级和事情的匹配，总包可以再谈。
3. 如果对方追问当前收入，按真实口径回答，并区分固定和浮动。
4. 入职时间：在职就按离职通知期加上交接来说；已经离职就说你能到岗的时间。有未完成的上线或交接要主动讲。
5. 对方给出的范围和你的预期差一截时，问清评估依据和复议的时点，再决定是否接受。
