### 3. Python里asyncio并发调LLM或工具时，怎么限流、怎么处理速率限制和超时，CPU密集解析能不能靠asyncio解决

**参考答案**

结论：asyncio 适合 IO 并发，限流、重试、超时要自己显式控制；CPU 密集任务不能靠 asyncio 解决。

1. **限流**：
   - 并发数用 `asyncio.Semaphore` 控制。
   - 速率（RPM/TPM）用令牌桶或漏桶，不能只靠信号量，因为信号量只限同时在途数，不限单位时间请求数。
   - LLM 通常既有请求数限制也有 token 限制，需要按预估 token 扣减额度。
   - 多实例部署时，单进程限流不够，需要用 Redis 做全局限流。
2. **速率限制处理**：收到 429 时优先读 `Retry-After`，没有则指数退避加随机抖动（jitter），设置最大重试次数；只对 429、5xx、网络超时重试，4xx 参数错误不重试。重试要有总预算，防止放大流量；持续失败触发熔断，切备用模型或降级。
3. **超时**：区分连接超时、首 token 超时、总超时。Python 3.11+ 可用 `asyncio.timeout()`，也可用 `asyncio.wait_for`。超时后要取消任务并释放信号量，流式场景还要关闭上游连接。
4. **CPU 密集**：asyncio 是单线程协作式调度，CPU 密集的 PDF 解析、OCR、大规模分词会阻塞事件循环，所有协程都卡住。应该用 `ProcessPoolExecutor` 配合 `loop.run_in_executor`，或独立 worker/队列服务。线程池（`asyncio.to_thread`）只适合阻塞型 IO，因为受 GIL 限制，对纯 Python CPU 计算帮助有限。

```python
sem = asyncio.Semaphore(8)

async def call_llm(req):
    async with sem:
        for attempt in range(4):
            try:
                async with asyncio.timeout(30):
                    return await client.chat(req)
            except RateLimitError as e:
                await asyncio.sleep(min(e.retry_after or 2 ** attempt, 20) + random.random())
            except asyncio.TimeoutError:
                if attempt == 3:
                    raise
        raise RuntimeError("retry exhausted")
```

### 4. Java侧讲一下线程池参数设定思路，以及Agent服务被Java后端通过HTTP/SSE调用时怎么转发流式输出

**参考答案**

**第一问：线程池参数。**

结论：先判断任务是 CPU 密集还是 IO 密集，再用有界队列加明确的拒绝策略，通过压测调整。

- `ThreadPoolExecutor` 的执行顺序是：先到 `corePoolSize`，然后入队列，队列满了才扩到 `maximumPoolSize`，再满就触发拒绝策略。
- CPU 密集型：线程数约 CPU 核数 + 1。IO 密集型：可参考 `核数 × (1 + 等待时间/计算时间)`，这只是起点，要靠压测。
- 队列必须有界，不要用 `Executors.newFixedThreadPool` 这类无界队列的写法，否则任务堆积会 OOM。
- 拒绝策略按业务选：`CallerRunsPolicy` 可形成背压，核心请求可以降级或返回繁忙。
- 不同类型的任务（调用 LLM、查库、发消息）用独立线程池隔离，避免慢调用拖垮所有请求；线程命名、监控队列长度和活跃数。

**第二问：转发 SSE 流式输出。**

- Java 端作为代理，用 `WebClient` 以流的方式订阅 Agent 服务的 SSE，再通过 `SseEmitter`（Spring MVC）或 `Flux<ServerSentEvent>`（WebFlux）逐事件透传，不要把完整响应缓冲后再返回。
- 不要在 Tomcat 请求线程里同步阻塞读流，应使用异步线程或响应式。
- 关键细节：关闭中间层缓冲（Nginx 的 `proxy_buffering off`，或者响应头 `X-Accel-Buffering: no`）；设置心跳事件避免连接被空闲断开；客户端断开时要取消上游订阅，否则 Agent 还在白白消耗 token；设置超时；带事件 id 便于断线续传；错误用单独的 error 事件表示，而不是直接断连接。

### 5. 意图识别在你项目里是怎么落地的，规则、分类模型、LLM路由三者怎么选，怎么处理意图歧义

**答题思路**

先讲三者的定位，再讲你的组合方式：

1. **规则**：关键词、正则、按钮或入口带来的显式意图。零成本、可解释、延迟低，适合高频、边界清晰的场景（如"转人工"）。覆盖率有限。
2. **分类模型**：小模型（BERT 类）或 embedding 加分类头，延迟低、成本低、可离线评估，适合意图固定且有标注数据的场景；新增意图需要重新训练。
3. **LLM 路由**：靠 prompt 加 few-shot 或 function calling，覆盖长尾和新意图，但延迟、成本高，稳定性略差。
4. **常见组合**：规则兜底快速命中，分类模型处理主流意图，置信度低的再交给 LLM；这是分层漏斗，而不是三选一。
5. **歧义处理**：设置置信度阈值；Top-2 意图分差小就主动追问用户（澄清问题）；结合上下文（上一轮意图、设备状态）；允许多意图拆分；对高风险意图（退款、删除）必须二次确认。
6. 用线上数据做混淆矩阵，持续把误判样本回流到训练集和评测集。

结合自己项目说明实际选择和效果，数据按真实情况讲。

### 6. LangChain和LangGraph本质区别，什么情况下LangChain不够用必须上图编排

**参考答案**

结论：LangChain 提供模型、prompt、工具、检索器等组件和链式组合；LangGraph 是有状态的图编排运行时，核心是显式的状态、节点、边，支持循环、分支、持久化。

- LangChain 的 LCEL 链本质上是有向无环的流水线，适合"检索 → 拼 prompt → 生成"这类线性流程。
- LangGraph 引入共享 `State`、节点、条件边，可以有环（循环 ReAct、反思、重试），并提供 checkpoint（持久化、断点恢复）、`interrupt` 人工介入、流式输出、时间旅行调试。
- 注意：新版 LangChain 的 agent 抽象底层也是基于 LangGraph 运行的，所以两者不是对立关系，而是 LangChain 做组件，LangGraph 做编排。

必须上图编排的情况：
1. 有循环和条件分支（工具调用到满足条件为止、验证不通过回到检索）。
2. 需要长流程的状态持久化和中断恢复（审批、等用户补充信息）。
3. 多 Agent 协作，需要显式的共享状态和路由。
4. 需要可观测、可回放的执行轨迹和精细的失败重试。

简单场景用链加一个 agent 就足够，没必要过度设计。

### 7. ReAct循环在你代码里具体怎么跑，Thought/Action/Observation在哪落地，怎么防止死循环

**参考答案**

结论：ReAct 是"推理 → 行动 → 观察"的循环，现在主流用原生 function calling 实现，防死循环靠硬性预算加重复检测。

**落地方式**：
- Thought：模型产出的推理或规划文本（有的模型推理内容单独返回，生产中通常只记录摘要）。
- Action：模型返回结构化 `tool_calls`（工具名加参数），由代码校验 schema 后执行。
- Observation：工具结果以 `tool` 角色消息追加到 messages 中，再次调用模型。
- 模型不再返回 tool_calls 时，循环结束，输出最终答案。在 LangGraph 里就是 `agent` 节点、`tools` 节点以及一条条件边（有 tool_calls 就去 tools，否则结束）。

**防死循环**：
1. 最大步数（`max_steps`）、总 token 预算、总耗时上限，LangGraph 里对应 `recursion_limit`。
2. 重复检测：相同工具加相同参数连续出现就中断，或返回提示让模型换策略。
3. 工具错误以可读方式反馈给模型，同时限制同类错误的重试次数。
4. 达到上限时强制输出"基于当前信息的最佳答案"或转人工，而不是静默失败。
5. Observation 过长要截断或摘要，防止上下文爆炸导致模型跑偏。

```python
for step in range(MAX_STEPS):
    msg = llm.invoke(messages, tools=tools)
    messages.append(msg)
    if not msg.tool_calls:
        return msg.content
    for call in msg.tool_calls:
        key = (call.name, json.dumps(call.args, sort_keys=True))
        if seen[key] >= 2:
            result = "重复调用，请换一种方式或直接回答"
        else:
            seen[key] += 1
            result = run_tool(call)
        messages.append(tool_message(call.id, truncate(result)))
return force_final_answer(messages)
```

### 8. RAG完整链路讲一遍，重点说文档解析到chunk的策略，chunk大小和overlap怎么定

**参考答案**

结论：RAG 分离线索引和在线问答两条链路，文档解析和切块质量决定检索上限。

**离线**：文档采集 → 解析（PDF、Word、HTML、扫描件 OCR，保留标题层级、表格、图片说明）→ 清洗（去页眉页脚、去重）→ 切块 → 生成 embedding → 写入向量库和倒排索引，同时存元数据（文档 id、版本、章节、权限、产品型号）。

**在线**：query 理解/改写 → 多路召回 → 融合 → 精排 → 拼装上下文 → LLM 生成并引用来源 → 校验。

**切块策略**：
- 优先按文档结构切（标题、段落、列表、表格），而不是机械按字数切。
- 表格尽量整体保留，或带表头切分；说明书类要保留章节标题作为每个 chunk 的前缀。
- 可以用父子块（parent-child）：小块用于召回，命中后返回所属大块或前后文给 LLM。
- 大小没有固定标准，常见做法是几百 token 一块，overlap 取块大小的一成到两成左右，需要在自己的评测集上比较 recall 和答案质量后确定。块太小语义不完整，太大则噪声多、占上下文、embedding 被稀释。
- overlap 的作用是缓解边界处语义被截断；按结构切时 overlap 的重要性下降。

容易漏的点：解析质量（表格、多栏）、元数据设计、chunk 带标题上下文、以及用评测集而不是凭感觉定参数。

### 9. 多路召回指哪几路，向量召回、BM25、ES关键词、元数据过滤分别解决什么问题，多路结果怎么合并(RRF之类)

**参考答案**

结论：多路召回是让语义和精确匹配互补，再用融合算法合并，目的是提高 recall。

- **向量召回**：解决语义相近但字面不同的问题（"机器不回充" 对应 "回充失败"），弱点是对型号、错误码、专有名词不敏感。
- **BM25/关键词（ES 倒排）**：解决精确词匹配，如错误码、型号、专有名词、缩写。BM25 本身是 ES 的默认相关性算法，所以 BM25 和 ES 关键词本质上是同一类召回，区别在于是否做了分词、同义词、字段权重等调优。
- **元数据过滤**：不是相关性算法，而是缩小范围：按产品型号、语言、文档版本、用户权限先过滤，避免召回到别的型号说明书，也是权限控制的关键一环。

**合并方法**：
- 各路得分尺度不同（余弦相似度与 BM25 分数不可直接相加），所以常用 **RRF（倒数排名融合）**：`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60，只用排名不用分数，简单稳健。
- 也可以对分数做归一化后加权求和，权重需要靠评测集调。
- 融合后进入精排。

```python
def rrf(rank_lists, k=60):
    scores = {}
    for lst in rank_lists:
        for rank, doc_id in enumerate(lst, 1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

### 10. 为什么多路召回之后还要精排，cross-encoder和bi-encoder分工是什么，Top-K设多少你怎么定

**参考答案**

结论：召回追求"不漏"，精排追求"排准"；bi-encoder 负责大规模快速召回，cross-encoder 负责小范围精确排序。

- **bi-encoder**：query 和文档各自独立编码成向量，文档向量可预先计算并建索引，用 ANN 检索，速度快，但 query 与文档没有 token 级交互，精度有限。
- **cross-encoder**：把 query 和文档拼在一起输入模型，直接输出相关性分数，有充分的交互，精度更高，但每个候选都要完整前向推理，无法预计算，只能用于几十到上百个候选。
- 多路召回合并后候选质量参差、排序依据不统一（分数尺度不同），需要一个统一的精排器。

**Top-K 怎么定**：
- 召回阶段 K 要大（通常几十到上百），看评测集上 recall@K 的曲线拐点。
- 精排后给 LLM 的 K 则取决于上下文预算、答案质量和成本，一般是少量几条到十来条，也要用评测集对比。
- 同时受 rerank 延迟约束：候选数乘以单条推理耗时。可以通过候选截断、批处理、模型蒸馏、GPU 部署来控制。
- 精排后还可以设置分数阈值，低于阈值的丢弃，避免把无关内容塞给 LLM。

### 11. Embedding模型选型看哪些指标，领域不匹配时你怎么做，微调Embedding还是换模型

**参考答案**

结论：选型以自己领域评测集上的效果为准，公开榜单只作参考；领域不匹配时先低成本手段，再考虑微调。

**选型看什么**：
- 在业务评测集上的 recall@K、MRR、NDCG（比 MTEB/C-MTEB 之类公开榜单更重要）。
- 语言支持（中文、中英混合）、最大输入长度、向量维度（影响存储和检索成本）、推理延迟与吞吐、部署方式（API 或自托管）、成本、许可证。

**领域不匹配时的顺序**：
1. 先确认问题出在哪：是解析、切块、query 改写的问题，还是 embedding 本身的问题。
2. 低成本手段：换更合适的现成模型、混合检索（加 BM25 补专有名词）、query 改写、给 chunk 加标题和元数据上下文。
3. 仍不足再微调：用领域内的 query–正文对加 hard negative 做对比学习微调，数据可来自日志、人工标注和 LLM 合成问题；注意过拟合和通用能力下降。
4. 无论换模型还是微调，向量空间都变了，**必须全量重建索引**，并且 query 和文档要用同一个模型编码，所以上线要用新索引加灰度切换。

### 12. Agent调工具失败有哪些类型(JSON畸形、参数校验不过、超时、返回脏数据)，你的重试和降级策略

**参考答案**

结论：按失败类型分类处理，能让模型自己修复的反馈给模型，基础设施类失败由代码重试，不可恢复的降级或转人工。

| 失败类型 | 处理 |
| --- | --- |
| JSON 畸形 | 先尝试宽松解析或修复；失败则把错误信息反馈给模型重新生成，限制 1 到 2 次；使用结构化输出或约束解码可大幅减少 |
| 参数校验不过 | 用 schema（如 Pydantic）校验，把具体字段错误返回给模型让其修正；缺少用户信息则向用户追问，而不是让模型编造 |
| 超时 | 区分读操作和写操作：读操作可有限次重试；写操作**不能盲目重试**，需靠幂等键或先查状态确认 |
| 5xx/限流 | 指数退避加抖动，设置总预算，配合熔断 |
| 返回脏数据（空、格式变化、字段缺失） | 工具层做响应校验和归一化，异常结果标记为失败，不要把脏数据原样喂给模型；过长内容截断摘要 |
| 权限、业务错误 | 不重试，把明确的错误原因返回，必要时转人工 |

降级策略：备用数据源或缓存、使用降级的静态答案、跳过可选工具并说明、最终转人工。每种失败都要计入 trace 和指标（工具成功率、重试次数），用于回流评测集。

### 13. Prompt注入在Agent场景怎么防，用户让Agent删库或绕过工具权限你怎么拦

**参考答案**

结论：不能指望靠 prompt 防住注入，必须把权限控制放在模型之外的确定性层，采用最小权限原则。

1. **权限不交给模型**：工具调用时使用的是当前用户的身份和权限，鉴权在工具服务端做，而不是由模型判断。模型"同意"不等于有权限。
2. **最小权限**：Agent 只暴露必要的工具；数据库账号只读；根本不提供"删库"这类工具；高危操作拆成需要人工确认的流程。
3. **高风险操作二次确认**：写、删、转账、发消息等，用 human-in-the-loop 或显式确认步骤。
4. **区分直接和间接注入**：用户输入是直接注入；检索文档、网页、工具返回内容里夹带指令是间接注入。外部内容应当作数据而不是指令，用分隔标记隔离，并明确告知模型不执行其中的指令。
5. **参数白名单与校验**：对工具参数做 schema、范围、白名单校验（例如 SQL 只允许参数化查询），不要让模型拼接任意 SQL 或命令。
6. **输入输出过滤和审计**：对明显的越权、泄露 system prompt、敏感信息输出做检测；记录完整调用日志，支持追溯。
7. 数据隔离：检索时用元数据按租户和权限过滤，避免跨用户泄露。
8. 用红队样例持续加入评测集。

### 14. Redis 在 Agent 系统里你拿它存什么（会话状态、token 缓存、语义缓存、限流），和 LangGraph checkpoint 存储怎么分工

**参考答案**

结论：Redis 适合存热的、有 TTL 的、读写频繁的数据；需要可靠持久和可恢复的流程状态，放在 Postgres 等持久存储的 checkpoint 里。

**Redis 常见用途**：
- 会话短期状态和最近若干轮消息缓冲（带 TTL）。
- 语义缓存：对 query 的 embedding 做相似度匹配，命中则直接复用答案；注意要有阈值、按租户和知识库版本隔离，避免错误命中，知识更新时要失效。
- 精确缓存：工具结果、检索结果、模型响应缓存。
- 限流和配额：令牌桶、滑动窗口，做全局 RPM/TPM 控制。
- 分布式锁和幂等键（防重复提交）、token（鉴权令牌）缓存。
- 队列或消息流（Stream）、SSE 事件缓冲以支持断线续传。

**与 checkpoint 的分工**：
- checkpoint 保存的是 LangGraph 每一步的完整图状态，用于中断恢复、重放和时间旅行，要求可靠持久、可按 thread 查询历史，通常用 Postgres（或使用 Redis 的 checkpoint 实现，但需要考虑持久化配置）。
- Redis 里的数据偏缓存和加速，丢了可以重建，不是流程正确性的来源。
- 简单说：丢了会让任务无法恢复的数据放 checkpoint，丢了只是变慢的数据放 Redis。

### 1. 请做一个自我介绍

**答题思路**

二面面试官通常已经看过一面的评价，介绍应更偏架构和深度：

1. 简短带过背景，把重点放在你主导的 Agent/RAG 系统：规模、模块划分、你负责的部分。
2. 突出一两个工程化亮点：State 与 checkpoint 设计、评测集和 badcase 回流、trace 与成本控制。
3. 说明你关注的问题（稳定性、可观测、成本），并和石头科技的设备助手场景挂钩。
4. 结尾留一两个钩子，引导面试官去问你最熟的部分（如多路召回和精排、Harness）。

不要夸大，所有数据以真实为准。

### 2. 项目里LangGraph的State怎么设计的，哪些字段放共享state，哪些放node私有

**参考答案**

结论：State 只放"多个节点都要读写、且需要被持久化恢复"的最小数据；大对象放外部存储，只存引用；节点内部的临时变量不进共享 state。

**共享 state（图级）**：
- `messages`（用 `add_messages` 这类 reducer 做追加合并）。
- 用户和会话标识（user_id、session_id）、意图、计划（plan）、当前步骤。
- 检索结果的引用（文档 id 加摘要）、工具结果摘要、验证结论、最终答案、重试计数。

**node 私有**：
- 节点内部的中间变量（临时 prompt、原始大块工具返回、解析中间结果）就用局部变量，不写入 state。
- LangGraph 支持节点使用不同的输入/输出 schema，也可以定义内部使用的私有状态通道，把只在少数节点间传递的数据隔离开，避免污染全局 schema。

**设计要点**：
1. 用 `TypedDict` 或 Pydantic 明确字段，每个字段定义 reducer（覆盖还是追加），并行节点写同一字段时必须有 reducer，否则会冲突。
2. state 会被写入每一个 checkpoint，体积大会拖慢存储和恢复，所以大文本、文件只存引用。
3. state 里不要放不可序列化的对象（连接、客户端），这些通过 config 或依赖注入传入。
4. state schema 变更要考虑旧 checkpoint 的兼容性。

### 3. LangGraph checkpoint存哪(MemorySaver/Redis/Postgres),thread_id怎么和用户信息映射，中断恢复从哪个节点续跑

**参考答案**

结论：开发用内存 saver，生产用 Postgres（或 Redis 实现）；thread_id 由服务端生成并与用户绑定；恢复从最近一次成功保存的 checkpoint 之后继续，但使用 `interrupt` 时要注意被中断的节点会重新执行。

**存储选择**：
- `MemorySaver`（现在也叫 `InMemorySaver`）：进程内存，重启即丢，只用于开发和测试。
- Postgres（`PostgresSaver`）：持久、可查询、事务可靠，适合作为生产默认。
- Redis：读写快，适合对延迟敏感的场景，但要明确持久化（AOF/RDB）和容量策略。

**thread_id 映射**：
- thread_id 通过 `config={"configurable": {"thread_id": ...}}` 传入，标识一条状态链。
- 业务侧维护映射表：`user_id`、`session_id` 到 `thread_id`，一个用户可有多个会话。
- 不要信任客户端直传的 thread_id，服务端校验该 thread 属于当前用户，防止越权读取他人会话；也可以用 `user_id:session_id` 这样的规则生成。
- 跨会话的长期记忆用 LangGraph 的 Store，不是用 thread。

**恢复从哪续跑**：
- checkpoint 在每个 super-step 结束后保存。进程崩溃或中断后，用同一 thread_id 调用，会从最后一个已保存的 checkpoint 状态继续，已完成的节点不会重跑；同一 super-step 内未完成的节点会重新执行。
- 使用 `interrupt()` 做人工介入时，恢复（`Command(resume=...)`）后是**从被中断的那个节点开头重新执行**，`interrupt` 调用处返回恢复值。因此 `interrupt` 之前的副作用代码必须幂等，或者放到 `interrupt` 之后、拆成独立节点。这是常被忽略的坑。

### 4. 多Agent为什么拆，不拆成单Agent带多工具的理由，拆完引入的通信成本和状态冲突你怎么控

**参考答案**

结论：默认先用单 Agent 加工具，只有在工具和指令多到模型选择变差、职责需要隔离时才拆。

**为什么拆**：
- 工具和 prompt 太多，单 Agent 选工具准确率下降、上下文臃肿。
- 不同子任务需要不同的 prompt、模型（大小模型）、权限，拆开可以做权限隔离和成本优化。
- 子任务可并行，可独立测试、评测、迭代。

**为什么不拆**：多 Agent 增加延迟、token 消耗、通信和调试复杂度，且错误会在 Agent 之间传播。任务线性、工具少时，单 Agent 更稳。

**控制成本和冲突**：
1. 通信不传完整历史，只传结构化的任务描述和结果摘要（明确的输入输出 schema）。
2. 共享状态集中放在 State，每个字段有明确的写入者（单一写入原则），并行写入用 reducer 合并。
3. 限制 Agent 间的跳转次数和总步数，防止互相踢皮球。
4. 由编排层或 Supervisor 统一仲裁，避免对等 Agent 各自决策。
5. 对整体链路做 trace 和端到端评测，而不是只测单个 Agent。

### 5. Supervisor模式和群聊模式区别，你项目里Planner、Retriever、Executor、Verifier各自边界，谁有最终决定权

**参考答案**

结论：Supervisor 是中心化调度，群聊是去中心化的自由对话；工程上优先用 Supervisor，因为可控、可追踪。

- **Supervisor 模式**：一个调度 Agent 决定下一步交给哪个子 Agent，子 Agent 返回结果给 Supervisor。流程清晰、易于加护栏、易于调试，但 Supervisor 可能成为瓶颈和单点。
- **群聊模式**：多个 Agent 共享对话上下文，轮流或按规则发言，灵活，适合开放式讨论或创作，但 token 消耗大、容易发散、难以终止和复现。

**角色边界（示例划分）**：
- Planner：只拆解任务、产出步骤计划，不调用外部工具。
- Retriever：只负责检索（知识库、设备信息），返回带来源的证据，不下结论。
- Executor：执行有副作用的动作（查询设备、创建工单），受权限和幂等控制。
- Verifier：检查答案是否有证据支撑、是否满足约束，输出通过、不通过及原因。

**最终决定权**：建议放在编排层的确定性规则加 Verifier 的结论上：Verifier 不通过则回流重试或转人工；对有副作用的动作，最终决定权在权限与策略层（甚至人工确认），而不是任意一个 LLM Agent。要根据自己项目的实际设计来讲。

### 6. Agent之间上下文怎么传，全量历史灌进去会怎样，Resolver和RAG在上下文注入上的分工

**参考答案**

结论：按需、结构化地传上下文，不要全量灌历史；Resolver 负责确定性地解析结构化上下文，RAG 负责按语义检索知识。

**传递方式**：通过共享 State 里的结构化字段传任务、关键结论、证据引用；给每个 Agent 只构造它需要的视图（裁剪后的 messages 加相关字段）。

**全量历史的问题**：
- token 成本和延迟显著增加。
- 上下文过长，模型对中间信息的利用率下降（"lost in the middle"），噪声干扰判断。
- 可能超出窗口，也会把不该给某个 Agent 的敏感信息暴露出去。
- 前面 Agent 的错误推理会污染后面的 Agent。

**Resolver 与 RAG 的分工**（Resolver 在不同团队里叫法不一，这里按"上下文解析/装配层"来理解）：
- Resolver：根据确定的键（user_id、设备 SN、订单号、会话）去查结构化数据，如用户信息、设备型号、当前状态、权限，把指代解析为具体实体（"它" 对应哪台设备），结果准确且来自权威来源。
- RAG：处理非结构化知识（说明书、FAQ、故障排查文档），靠语义检索，结果带相关性但不保证精确。
- 原则：能用确定性查询得到的事实，不要让 RAG 去猜；两者的结果在上下文装配时分区放置并标注来源。

### 7. 长任务跑50轮上下文溢出怎么处理，三层存储（短期缓冲/长期向量/外部KV）怎么配合动态注入

**参考答案**

结论：上下文是预算有限的资源，需要"裁剪、摘要、外置、按需召回"组合处理。

**溢出处理**：
1. 保留最近若干轮原文（滑动窗口），保留 system prompt 和当前任务目标。
2. 更早的内容做滚动摘要，摘要必须保留关键事实、已做决定、未完成事项。
3. 大的工具结果（长文本、表格）外置，上下文里只留摘要和引用，需要时再取。
4. 清理已无用的中间观察结果。
5. 达到阈值前主动压缩，而不是溢出后才报错。

**三层存储配合**：
- **短期缓冲**：最近几轮原文，在内存或 Redis，直接进入 prompt。
- **长期向量**：历史对话片段、经验、知识的 embedding，按当前问题做语义召回，只注入 top-k 相关内容。
- **外部 KV**：结构化的用户画像、设备信息、任务进度、偏好等，按键精确读取。
- **动态注入**：每轮组装上下文时，先放固定指令，再放 KV 里的确定性事实，再放向量召回的相关记忆，再放短期缓冲；总量超过预算时按优先级裁剪。写回时，新的关键事实更新 KV，值得保留的片段写入向量库。

### 8. 意图识别和多Agent路由怎么接，先意图分类再派Agent，还是Agent自己判断，误路由怎么回收

**参考答案**

结论：生产中常用"先意图分类，再路由到子 Agent"的两段式，兼顾可控和灵活；让 Agent 自己判断（Supervisor 用 LLM 决策）适合意图边界模糊的场景。

- **先分类再派发**：延迟低、可评测、可对高风险意图加规则；缺点是意图体系要维护，边界外的问题容易被误分。
- **Agent 自己判断**：灵活，可处理复合需求，但不稳定、成本高，也更难评测。
- **折中**：规则加分类模型处理主流，低置信度交给 LLM Supervisor；复合意图拆成多个子任务。

**误路由回收**：
1. 子 Agent 具备"拒绝或上交"能力：发现超出自身职责时返回特定信号，由编排层重新路由，限制回退次数。
2. Verifier 或置信度检查发现答案不符时回退重派。
3. 兜底到通用 Agent 或转人工。
4. 用户纠正（"不是这个意思"）作为信号触发重新路由。
5. 日志记录路由决策，把误路由样本回流到分类训练集和评测集。

### 9. RAG多路召回具体实现:ES倒排+向量库双写、query改写、同义词扩展、负样本挖掘你做过哪些

**答题思路**

这是项目深挖题，要讲你真实做过的部分，建议按以下结构，没做过的明确说"了解原理，但未落地"：

1. **双写**：同一份 chunk 以 `doc_id + chunk_id + version` 为主键，同时写入 ES（倒排）和向量库。保证一致性可用"先写源数据，再由异步管道（消息队列或 outbox）驱动索引"的方式，失败重试加对账任务；检索时用同一 id 做融合去重。
2. **query 改写**：指代消解（结合历史补全）、口语转检索式、多 query 扩展（生成若干改写并行检索再用 RRF 融合）、HyDE（先生成假想答案再检索）。要说明改写带来的延迟和漂移风险，以及用评测集验证。
3. **同义词扩展**：在 ES 里配置同义词词典（领域词、型号别名、缩写），或查询时扩展；词典要持续从 badcase 和日志里补充，注意过度扩展导致噪声。
4. **负样本挖掘**：从召回结果中取排名靠前但人工或 LLM 判定不相关的作为 hard negative；用于训练 embedding 或精排；注意避免把其实相关的当作负样本（假负例）。
5. 每项改动都对应评测集的指标变化（recall、MRR、答案正确率），只讲真实数据。

### 10. 精排模型离线怎么训，正负样本怎么造，线上rerank延迟超了怎么降级成单路向量召回

**参考答案**

结论：精排通常基于预训练 cross-encoder 在领域数据上微调；样本质量比数量更关键；线上用延迟预算加熔断做降级。

**离线训练**：
- 模型：以预训练的 cross-encoder 或 reranker 为底座，输入 query 加文档拼接，输出相关性分数。
- 损失：pointwise（二分类）、pairwise（正负对比较）、listwise（整个列表排序）都有应用，实践里 pairwise 或 listwise 更贴合排序目标。
- 评估：用 NDCG、MRR、recall@K 在独立的验证集上评估，并与未微调的基线对比。

**正负样本构造**：
- 正样本：人工标注的相关片段、用户点击或采纳的答案对应的 chunk、由文档生成问题得到的"问题到出处块"对（LLM 合成）。
- 负样本：随机负例（便宜但太简单）、**hard negative**（来自多路召回的高排名但不相关的片段，对提升精度最有效）、同文档的相邻块。
- 用 LLM 或人工复核，避免假负例；注意样本分布要与线上 query 一致。

**线上降级**：
1. 给 rerank 设置超时预算（例如占总延迟的一部分），超时则放弃精排。
2. 降级路径：直接用融合后的排序结果（RRF 的结果），或进一步只用向量召回的排序，截取 top-k 返回；同时降级时可减少候选数量。
3. 用熔断器：连续超时或错误率高时，短时间内直接跳过 rerank，再探测恢复。
4. 其他手段：限制候选数、批量推理、GPU 部署、模型蒸馏或量化、缓存热门 query 的结果。
5. 降级事件要记录并告警，评估其对质量的影响。

### 11. 工具调用用Function Calling还是MCP，工具schema怎么写才能让模型少幻觉，非幂等工具（发消息、写单）怎么防重

**参考答案**

结论：二者不是互斥关系。Function Calling 是模型输出结构化调用的能力，MCP 是工具和上下文的标准化协议；MCP 解决的是"工具如何被不同 Agent 或客户端统一发现和接入"。

**如何选择**：
- 工具只给自己的单一应用用、数量少，直接 Function Calling 加本地函数，简单、延迟低。
- 工具需要跨多个 Agent、团队或客户端复用，或要接入第三方生态，用 MCP 做统一封装；MCP 的 server 最终也会被转成模型的 tool 定义来调用。
- 使用 MCP 要注意鉴权、工具来源可信（防工具描述投毒）、权限最小化。

**schema 怎么写减少幻觉**：
1. 名称语义清晰，描述写清楚"何时用、何时不用"，并给出示例。
2. 参数用强类型：枚举、范围、必填项、格式（如日期格式），减少自由文本。
3. 参数少而明确，字段说明里写清来源（例如"从设备列表返回的 device_id，不要自行编造"）。
4. 工具数量不要过多，相近功能合并，必要时先做工具检索或分组。
5. 服务端严格校验，错误信息可读，让模型能自我纠正。
6. 返回结果精简、结构化。

**非幂等工具防重**：
1. 由代码（而非模型）生成**幂等键**（如 `run_id + step + 业务参数哈希`），服务端按幂等键去重，重复请求返回第一次的结果。
2. 超时后不要盲重试：先查询状态确认是否已执行。
3. 数据库用唯一索引或状态机约束。
4. 高风险操作需要人工确认。
5. 与 checkpoint 恢复结合：恢复重放时已执行的副作用要靠幂等键跳过，而不是再次执行。

### 12. Harness层你理解是什么，和单纯Agent脚本比，Harness要解决loop控制、状态、观测、回放哪些事

**参考答案**

结论：Harness 是包在模型和工具外面的运行框架，把"让 Agent 可靠运行"的工程能力从业务逻辑里抽出来；Agent 脚本只管"做什么"，Harness 管"怎么可靠地做"。

**Harness 要解决的事**：
- **Loop 控制**：最大步数、token 与耗时预算、重复检测、终止条件、超时和取消、失败重试和降级。
- **状态**：会话与任务状态的持久化、checkpoint、断点恢复、上下文管理（压缩、裁剪、注入）。
- **工具层**：工具注册、schema 校验、权限与沙箱、幂等和重试、结果截断。
- **观测**：trace、日志、指标（耗时、token、成功率、成本）。
- **回放与评测**：记录每步的模型输入输出和工具结果，支持 replay 复现问题、对比 prompt 或模型变更、接入评测集和回归测试。
- **安全与治理**：人工审批点、权限控制、审计、预算限额。

和单纯脚本相比：脚本能跑通 Demo，但遇到长任务崩溃无法恢复、线上问题无法复现、成本和风险无法控制，这些正是 Harness 的价值。需要注意，Harness 不要过度设计，应该随着实际问题逐步沉淀。

### 13. Trace字段你打哪些：每步token、工具耗时、观察结果摘要、节点名、retry次数，怎么接Langfuse或自研

**参考答案**

结论：trace 的目标是"能复现、能定位、能算账"，字段围绕这三点设计，粒度是一次请求一个 trace，每个节点、模型调用、工具调用是一个 span。

**建议字段**：
- 标识：trace_id、session_id、user_id（注意脱敏）、thread_id、run_id、环境和版本（prompt 版本、模型版本、代码版本）。
- 节点或 span：节点名、父子关系、开始和结束时间、耗时、状态。
- 模型调用：模型名、参数（temperature 等）、输入输出（可采样或脱敏存储）、输入输出 token 数、首 token 延迟、成本、finish_reason。
- 工具调用：工具名、参数、耗时、返回摘要（完整结果存对象存储，trace 里放引用）、错误类型、retry 次数、是否命中缓存。
- 检索：query、改写后的 query、各路召回的 id 和分数、精排后结果、是否降级。
- 路由和决策：意图、置信度、路由结果、验证结论。
- 用户反馈和评测分数。

**接入**：
- Langfuse：用其 SDK、装饰器，或 LangChain/LangGraph 的 callback handler 自动采集，trace、span、generation 的模型与其对应；可以做 prompt 版本管理、评分、数据集。
- 自研：基于 OpenTelemetry 采集 span，落到 ClickHouse、ES 等存储，加上看板和告警。
- 注意采样策略（错误和慢请求全量保留）、敏感信息脱敏、大字段外置，避免 trace 本身成为性能和存储负担。

### 14. 评测集怎么建，成功路径和故意失败路径比例，LLM-as-judge和规则评分怎么结合，badcase怎么回流

**参考答案**

结论：评测集来自真实线上数据加人工构造的边界用例，分层评测，规则打底、LLM 评判补充语义维度，并形成回流闭环。

**怎么建**：
- 来源：线上真实 query（脱敏）、客服工单、人工编写的典型场景、LLM 合成后人工审核、历史 badcase。
- 覆盖：按意图、难度、工具类型分层；包含成功路径和故意设计的失败路径（工具超时、返回脏数据、权限不足、信息缺失需追问、越权或注入攻击、知识库没有答案应拒答）。
- 比例没有固定标准，原则是失败和边界用例要占足够比重，保证对稳定性和安全性有区分度，并保持线上真实分布的代表性，再根据实际 badcase 分布调整。
- 每条用例包含输入、期望的行为（期望调用的工具或参数、关键事实、是否应拒绝）、参考答案。

**评分结合**：
- 规则评分：能确定性判断的优先用规则，如是否调用了正确工具、参数是否正确、格式是否合法、是否包含关键事实、是否触发违规，便宜、稳定、可复现。
- LLM-as-judge：评估相关性、忠实度（答案是否有证据支撑）、完整性等主观维度；要用明确的评分细则，用强模型，评判模型和被测模型分开，用人工抽检标注集校准一致性，并注意位置偏差、长度偏差等已知偏差。
- 分层使用：规则的硬指标当门槛，LLM 评分做趋势比较，关键场景保留人工评审。

**badcase 回流**：线上反馈、低分、转人工、用户纠正和异常 trace 自动入池，人工归因（检索、prompt、工具、模型）后标注，进入评测集和训练集（hard negative、few-shot），修复后跑回归，并接入 CI 或发布前门禁，防止指标回退。

### 15. Agent 成本失控怎么查，是 retrieve 太宽、rewrite 太多次还是模型选贵了，模型路由（大模型/小模型）怎么切

**参考答案**

结论：先用 trace 做成本归因，再针对占比最高的环节优化，不要凭感觉。

**排查**：
1. 按维度聚合 token 和费用：按节点、模型、工具、意图、用户或租户、版本，找到头部。
2. 看是**输入 token 多还是输出多**：输入多通常是上下文太长（retrieve 数量过大、历史全量灌入、工具结果太长、prompt 过长）；输出多则是生成过长或推理过度。
3. 看**调用次数**：每个请求的 LLM 调用数、循环步数、rewrite 或反思重试次数；是否存在死循环或重复调用。
4. 看**模型选择**：简单任务是否也用了最贵的模型。
5. 看缓存命中率、重试造成的重复消耗。

**优化**：减少 Top-K 或加阈值、压缩和摘要上下文、限制步数和重试、利用 prompt 前缀缓存（把固定内容放在 prompt 前部）、语义和精确缓存、限制输出长度。

**模型路由**：
- 按任务难度和风险分层：意图分类、改写、信息抽取等简单任务用小模型；复杂推理、规划、最终答案生成或高风险场景用大模型。
- 切换依据：规则（任务类型）、分类器或置信度判断、级联（先小模型，置信度低或校验不过再升级到大模型）。
- 要用评测集验证小模型在该环节的质量不下降，并监控路由后的质量和成本，设置预算上限和告警。

### 2. 讲你负责过最难的Agent落地问题，哪个故障让你半夜起来修，根因和修复路径

**答题思路**

这是经历类题，必须用你真实遇到的事讲，不要编造。用 STAR 加复盘的结构：

1. **背景和影响**：什么系统、什么现象（例如成功率下降、成本暴涨、响应变慢、答案错误），影响范围和严重度。
2. **定位过程**：先看监控和告警，再看 trace 找到异常节点，缩小范围，是如何排除其他可能的；强调你靠什么数据定位（trace、日志、回放）。
3. **根因**：说清楚技术原因，常见方向如上游模型限流或变更、工具返回格式变化、检索索引不一致、循环失控、上下文溢出、依赖超时。
4. **修复**：止血（降级、回滚、限流）和根治（代码、配置、数据修复）分开讲。
5. **复盘与预防**：补了哪些监控告警、评测用例、熔断和预算限制，推动了什么流程改进。

重点体现排查的方法论和你从中沉淀的机制，而不是单纯讲故事。

### 3. 多Agent出现观点冲突（比如Retriever说有、Verifier说证据不足）怎么仲裁，靠LLM再审还是规则投票

**参考答案**

结论：优先用确定性规则和证据溯源仲裁，规则无法判定的灰色地带再用 LLM 或转人工；不建议简单投票。

1. **先明确冲突性质**：Retriever 说"有"，但 Verifier 说"证据不足"，本质上是证据质量问题。应当让仲裁基于**可核验的证据**，而不是 Agent 的自信程度。
2. **规则优先**：检查证据是否有来源引用、相关性分数是否超过阈值、是否与问题关键实体（型号、版本）匹配、是否有多个独立来源互相印证；Verifier 的判断依据是否可验证。
3. **有限的回流**：证据不足时，让 Retriever 扩大检索（改写 query、放宽过滤、增加召回）重试，限制 1 到 2 轮，而不是无限争论。
4. **LLM 再审**：作为独立的裁判，只看问题、证据和双方理由，输出结论和依据；裁判应使用较强的模型，避免与前面 Agent 共享偏见，并通过评测集验证裁判的准确率。成本和延迟较高，所以只用于规则处理不了的情形。
5. **兜底**：仍无法确定时，选择保守策略：明确告知用户"依据不足"、追问更多信息，或转人工；对有副作用的操作，宁可不执行。
6. **为什么不用简单投票**：多个 Agent 常基于相同的底座模型和同一份上下文，错误高度相关，投票并不独立；而且 Agent 数量少，投票没有统计意义。
7. 所有冲突与仲裁结果记录 trace，作为 badcase 的重要来源。

### 4. Harness工程化里，Replay为什么冻结工具结果而不是重调真实接口，冻结格式怎么和checkpoint区分

**参考答案**

结论：Replay 的目的是**复现与对比**同一次运行，所以必须固定外部世界；重调真实接口既不确定又可能有副作用。

**为什么冻结工具结果**：
1. **确定性**：真实接口的结果会随时间变化（设备状态、库存、检索结果），重调后环境已不是出问题时的环境，无法复现 bug。
2. **避免副作用**：创建工单、发消息等写操作重放会产生真实的重复操作。
3. **成本和速度**：避免重复调用付费或慢的接口，回放可以批量快速执行。
4. **可对比**：冻结工具输出后，只改 prompt、模型或编排逻辑，差异就只来自被改动的部分，适合做回归和 A/B 评测。
5. 模型本身仍有随机性，可以固定 temperature 和 seed（若支持），或者也冻结模型输出以做纯逻辑回放，按回放目的选择。

**冻结格式和 checkpoint 的区别**：

| | checkpoint | replay 记录 |
| --- | --- | --- |
| 目的 | 让运行**继续**（中断恢复、时间旅行） | 让运行**重现**（调试、回归、评测） |
| 内容 | 图的完整状态快照（state、下一个节点、元数据） | 事件日志：每步的模型输入输出、工具名、参数、返回、耗时、错误，以及版本信息 |
| 粒度 | 以 super-step 为单位的状态 | 以调用为单位的输入输出 |
| 使用方式 | 加载状态后接着执行，会真实调用外部 | 按调用顺序或以"工具名加参数哈希"为键匹配并返回冻结结果，不访问外部 |
| 生命周期 | 随会话，可以被裁剪 | 通常归档保留，用于分析 |

设计要点：replay 记录要独立于 checkpoint 存储，带上 run_id、步骤序号、代码和 prompt 版本；当回放时参数与记录不一致（说明逻辑变了），要明确报告"未命中冻结结果"，而不是悄悄调用真实接口。敏感数据要脱敏。

### 5. 如果让你从零设计石头科技扫地机助手 Agent（设备状态查询/售后意图/说明书 RAG/工单创建），整体分层怎么画

**参考答案**

结论：按"接入 → 编排 → 能力 → 数据 → 治理"分层，查询类走低风险快路径，工单这类写操作走带确认和幂等的受控路径。

**分层**：
1. **接入层**：App 或小程序或客服入口，经网关做鉴权、限流、灰度，SSE 流式返回。
2. **理解与路由层**：意图识别（规则加分类加 LLM 兜底）：设备状态、故障咨询、售后、闲聊或其他；低置信度追问；高风险意图加确认。
3. **编排层**（LangGraph 加 Harness）：
   - 状态查询 Agent：调用设备云 API，只读。
   - 说明书 RAG：按设备型号过滤，多路召回加精排，生成带出处的答案。
   - 售后和工单 Agent：收集必要信息（设备 SN、故障描述、购买凭证、联系方式），校验完整后创建工单。
   - 验证节点：答案是否有证据、信息是否齐全。
4. **工具层**：设备状态查询、工单创建、订单和保修查询，每个有严格 schema、用户级鉴权（只能查询自己名下的设备）。工单创建使用幂等键，创建前由用户确认。
5. **数据层**：向量库加 ES（说明书，带型号和语言版本元数据）、会话存储（Redis 加 checkpoint 存 Postgres）、用户和设备主数据。
6. **模型网关**：统一限流、重试、模型路由（小模型做分类和改写，大模型做生成）、成本统计。
7. **观测与评测**：trace、指标、评测集、badcase 回流；人工客服兜底。

**关键点**：设备状态是实时事实，必须走工具而不是 RAG；说明书按型号过滤避免串型号；设备状态结合说明书给出针对性建议（先 Resolver 确定设备型号和当前状态，再检索）；故障现场信息不足时追问；写操作必须幂等并可审计；随时可转人工。

### 6. Java后端存量系统接Python Agent服务，鉴权、灰度、SSE转发、异常熔断、埋点各自放哪层

**参考答案**

结论：Java 后端（或网关）作为统一入口，负责身份、流量、稳定性；Python Agent 服务专注于智能逻辑，信任来自 Java 的身份，但自身也做必要的校验。

| 关注点 | 放置位置 | 做法 |
| --- | --- | --- |
| 鉴权 | 网关或 Java 层 | 用户登录态、权限在此校验；向 Agent 传递可信的用户身份（内部签名 token 或 mTLS），Agent 调用工具时带上该用户身份，由工具服务端再次鉴权；Agent 不信任外部直传 |
| 灰度 | 网关或 Java 层（流量），Agent 层（版本） | 按用户、租户、百分比路由到不同的 Agent 版本；prompt、模型版本也要可灰度、可回滚，并在 trace 里记录版本 |
| SSE 转发 | Java 层 | 异步透传（WebFlux 或 SseEmitter），关闭缓冲，加心跳，客户端断开时取消上游，错误用事件表达 |
| 异常熔断与降级 | Java 层的调用 Agent 处（如 Resilience4j），Agent 内部对模型和工具也要熔断 | 设置超时、并发隔离（舱壁）、熔断，失败时降级到固定话术、传统 FAQ 或转人工 |
| 限流 | 网关做用户级，Agent 内做模型 token 级 | 双层限流 |
| 埋点与 trace | 两层都有 | Java 层记录业务事件（请求量、转化、用户反馈），Agent 层记录推理 trace；通过统一的 trace_id（OpenTelemetry 透传）串联 |
| 会话与状态 | Agent 层的 checkpoint；会话归属映射在 Java 业务库 | thread_id 由服务端生成并绑定用户 |

注意：流式响应的超时设置和普通接口不同（首包超时加空闲超时）；Java 和 Python 之间的接口要有版本约定和契约测试。

### 7. 技术选型题：LangGraph+自研Harness vs直接Claude Code类产品封装，什么情况下后者更划算，什么情况必须自研

**参考答案**

结论：先看需求是"通用的、开放式的代码或文件类任务"还是"强业务、强合规、强定制的流程"；前者优先用现成产品或 SDK，后者倾向自研。

**封装现成产品（如 Claude Code 类 Agent SDK）更划算的情况**：
- 任务本身就是开放式的：代码生成修改、文件处理、调研分析等，现成产品的工具链、上下文管理、权限系统已经成熟。
- 团队规模小、要快速验证价值、Agent 工程经验不足。
- 对延迟、成本、数据出境没有硬性约束。
- 内部工具类，用户可信、风险较低。

**必须或更适合自研的情况**：
- 面向 C 端或高并发业务，对延迟、成本、稳定性有严格 SLO，需要精细的模型路由和缓存。
- 强业务流程（售后、工单、审批），要求确定性的流程控制、状态持久、人工介入和审计。
- 数据合规：数据不能出境、需要私有化或国产模型，或需要接入自有的模型和推理服务。
- 需要深度定制的工具权限、多租户隔离、自有的评测和回放体系。
- 避免供应商锁定，希望可控的升级节奏。

**权衡**：自研的隐性成本是维护、评测、安全治理和人力；封装的风险是黑盒、定制受限、成本不可控。常见的折中做法是：编排和治理自研，底层用成熟的模型、MCP 和开源组件；先用现成方案验证价值，稳定后再把关键路径自研。依据是成本、风险和可控性的量化对比，而不是技术偏好。

### 8. RAG知识库文档更新了，增量更新、双写切换、向量版本号你怎么选，召回到旧chunk怎么避免

**参考答案**

结论：日常更新用**文档级增量**，embedding 模型或切块策略变化时用**蓝绿式双写切换（新索引加别名切换）**；版本号用来保证一致性和可回滚。

**增量更新**：
- 为每个文档记录 `doc_id` 和内容哈希，变更检测只处理有变化的文档。
- 流程：重新解析和切块，按 `doc_id` 写入新版本 chunk，再删除或下线旧版本 chunk；chunk 带 `doc_version`。
- 要同时更新向量库和 ES，使用幂等写入和失败重试，并有对账任务检查两边数量和版本一致。

**双写切换（蓝绿）**：
- 适用于换 embedding 模型、改切块策略、改索引结构，这时新旧向量不兼容，必须全量重建。
- 做法：新建 collection 或 index，离线全量构建，期间新增的更新双写到新旧两边；校验（抽样评测、对比 recall）通过后，用**别名（alias）**原子切换流量，保留旧索引一段时间用于回滚。

**向量版本号**：给每个 chunk 记录 `embedding_model_version` 和 `index_version`；查询时 query 必须用同一模型编码，避免不同版本向量混用。

**避免召回旧 chunk**：
1. 检索时按 `is_active=true` 或最新 `doc_version` 过滤。
2. 更新采用"先写新、再原子切换可见、最后清理旧"的顺序，避免出现空窗期（旧的已删而新的未就绪），也避免新旧并存。
3. 缓存（语义缓存、检索缓存）要与知识库版本关联，更新后失效。
4. 定期清理软删除的数据，对账发现孤儿 chunk。
5. 答案中带出处和文档版本，便于发现过期内容。

### 9. 多Agent系统上线后准确率plateau了，你先动检索、动prompt、动工具还是动评测集，依据是什么

**参考答案**

结论：先动评测集和错误归因，再据此决定改哪一环；在没有诊断前盲目调 prompt 或检索，容易造成"此消彼长"。

**步骤**：
1. **先检查评测集**：是否还能代表线上分布、是否有标注错误、是否已经被过拟合（反复针对它调优）、是否覆盖新出现的问题类型。指标 plateau 有时是评测集饱和而非系统到顶。
2. **做错误归因**：抽样分析失败案例，按阶段分类：意图或路由错、检索没召回到（recall 问题）、召回到但排序靠后或没被用上、工具调用参数或选择错误、生成时幻觉或没遵循指令、验证环节漏判。用 trace 逐步判断每步的对错。
3. **按占比和可修复性决定优先级**：
   - 如果多数失败是"相关证据根本没召回"，先动检索（切块、多路召回、query 改写、embedding、精排）。
   - 如果证据在上下文里但答案错，动 prompt、上下文组织或模型。
   - 如果是工具选择或参数错误，动工具 schema、描述和校验。
   - 如果是路由或编排问题，调整路由和流程。
4. **一次只改一个变量**，用 A/B 或回归集验证，同时看是否有回退。
5. 如果剩余错误是歧义、知识库缺失、标注争议等，继续优化收益很低，需要补知识、改产品交互（追问或转人工）。

依据是数据（错误分布和各阶段指标），而非直觉。

### 10. 最近半年你跟过哪些 Agent/RAG 新东西（LangGraph 更新、MCP、Agent2Agent、语义缓存），哪个你真跑过

**答题思路**

这是诚实度和学习深度的检验，核心原则：**只讲你真正接触过的，分清"跑过"和"了解"**。

1. 选 2 到 3 个主题，按"是什么、解决什么问题、我怎么用或验证、结论和局限"讲：
   - **LangGraph**：持久化、`interrupt` 人工介入、流式、子图、Store 长期记忆等更新对项目的影响。
   - **MCP**：标准化工具接入协议，说清它与 Function Calling 的关系，以及鉴权和工具可信度风险。
   - **Agent2Agent（A2A）**：跨 Agent 的互操作协议，与 MCP 的定位区别（MCP 偏 Agent 到工具和上下文，A2A 偏 Agent 到 Agent）；如果没落地，明确说"了解设计，没有生产实践"。
   - **语义缓存**：命中阈值、误命中风险、与知识库版本的联动、节省的成本。
2. 对真正跑过的那个，讲一个具体的实验或落地经历、遇到的坑和量化结果（真实数据）。
3. 对没跑过的，说清楚你的判断：什么场景会引入、为什么暂时没引入。

不要把没做过的说成做过，面试官很容易追问细节。

### 11. 你怎么判断一个新技术是值得引入还是炫技，给团队推一套Agent规范你会先定哪三条

**答题思路**

这是工程判断和管理题，用"判断标准加例子加规范"的结构：

1. **判断是否值得引入**，可用几个问题：
   - 它解决的是**当前真实存在、可度量**的问题吗（如成本、准确率、延迟、维护性）？
   - 有没有更简单的替代方案？
   - 引入成本：学习成本、维护成本、迁移风险、团队能否接得住？
   - 能否小范围试点、用评测集量化收益，并且可回滚？
   - 技术成熟度、社区和长期维护情况。
   举一个你真实的"引入了"和"果断没引入"的例子。
2. **规范先定哪三条**（给出理由，下面是推荐方向，可按自己经验调整）：
   - **可评测**：任何 Agent 改动（prompt、模型、工具）必须有评测集回归结果，才能上线。
   - **可观测可回放**：统一的 trace 规范和关键指标，线上问题可复现。
   - **权限与副作用控制**：工具最小权限、写操作幂等和确认、关键动作可审计；以及步数和成本预算限制。
3. 强调规范要轻量、可自动化（接入 CI、模板、脚手架），避免变成形式主义。

### 12. 你怎么带人排查Agent线上问题，新手容易卡在哪一环，你怎么做code review里的Agent代码把关

**答题思路**

按"方法论 → 新手常见问题 → review 清单"组织，体现带人和把关能力：

1. **排查方法论**（教给团队的流程）：
   - 先止血（降级、回滚版本、限流），再定位。
   - 用 trace 复现：取得出错请求的 trace_id，逐节点查看输入输出；必要时用 replay 重放。
   - 分段定位：路由、检索、工具、生成、验证，逐段确认是哪里首先出错。
   - 一次只改一个变量，改完用评测集回归，并把问题沉淀为用例。
2. **新手容易卡的环节**：
   - 只看最终答案，不看中间 trace，把检索、工具问题误判为"模型不行"。
   - 一出问题就改 prompt，没有区分根因，导致其他场景回退。
   - 没有可复现的数据，无法验证修复是否有效。
   - 忽略工具返回的脏数据、超时重试、上下文被截断。
   - 忽略非确定性：用一次结果判断好坏，没有多次采样或评测集。
3. **code review 的 Agent 专项把关**：
   - 循环是否有步数、token、时间上限；是否可能死循环。
   - 工具 schema 是否清晰；参数是否有校验；错误是否可读。
   - 写操作是否幂等、权限是否在服务端校验、是否有确认。
   - state 设计：字段 reducer、体积、是否存了不可序列化对象或大对象。
   - 超时、重试、降级是否完整，是否有对用户可见的兜底。
   - prompt 是否版本化，是否有注入风险（外部内容与指令隔离）。
   - 是否有 trace 埋点、是否附带评测用例或回归结果。
   - 密钥和敏感数据是否泄露到日志。

### 13. 学习能力强不强不是嘴说，讲一个你从零啃下陌生模块（比如突然接手向量库调优）的时间线和抓手

**答题思路**

用一个你真实的经历，按时间线加抓手来讲，不要编造具体数据。结构建议：

1. **背景**：为什么突然接手、目标是什么、时间压力、可量化的验收标准（如召回率、延迟）。
2. **时间线**（例如第一阶段、第二阶段、第三阶段，按自己实际情况）：
   - 第一阶段：建立全局认识：读官方文档和源码关键部分，搞清核心概念和原理（以向量库为例：索引类型 HNSW 或 IVF、距离度量、量化、召回与延迟的权衡）。
   - 第二阶段：建立基线：搭评测集和压测脚本，先测现状，找到瓶颈在哪里，而不是直接调参数。
   - 第三阶段：小步实验：一次改一个变量（索引参数、过滤策略、分片、embedding 维度等），记录结果。
   - 第四阶段：落地与沉淀：灰度上线，监控，写文档，同步团队。
3. **抓手**：找内部熟悉的人请教、拆分问题、用评测和数据驱动、做最小可行实验、输出文档倒逼理解。
4. **结果和复盘**：达成了什么、哪些地方走了弯路、之后遇到类似问题怎么更快上手。

## HR面

### 1. 请做一个自我介绍

**答题思路**

HR 面的自我介绍与技术面不同，偏稳定性和匹配度，控制在 1 到 2 分钟：

1. 基本信息：学历背景、工作年限、最近的工作方向。
2. 职业脉络：做过什么、为什么转到或深入 Agent/AI 应用方向（讲清动机，别太功利）。
3. 一到两个代表性成果，用通俗的语言讲价值，而不是堆技术名词。
4. 对岗位和公司的兴趣点，以及未来想怎么发展。
5. 语气真诚、简洁，避免与简历完全重复。

### 2. 为什么看石头科技，AI Agent在家居/硬件助手场景你看好哪条线

**答题思路**

1. **为什么看公司**：从公司真实可查的信息出发，比如在智能家居、扫地机或机器人品类的产品、市场和技术积累，硬件加软件加服务的闭环，数据和场景的优势；以及你的经验与岗位的匹配点。不要说没依据的话，面试前先做功课。
2. **看好的方向**（选一两条并说出理由，可从下面这些切入）：
   - 设备使用和故障的智能客服与售后：问题明确、有说明书和设备状态数据、效果容易量化，落地确定性最高。
   - 设备控制和个性化的家居助手：自然语言控制设备、根据家庭情况推荐清洁方案，体验价值大，但需要解决权限、安全和可靠性。
   - 主动式服务：基于设备日志预测故障、主动提醒，长期价值高。
3. 说明你的判断标准：场景是否有闭环数据、风险是否可控、是否有明确的衡量指标。
4. 结合自己的能力说明你能在其中贡献什么。

### 3. 你觉得自己做Agent应用层最值钱的能力是哪块，最弱的哪块

**答题思路**

1. **最值钱的能力**：选一个你真能举出证据的，而不是泛泛说"都擅长"。可选方向：把 Demo 做成稳定线上系统的工程能力（评测、观测、降级、成本控制）、RAG 检索质量优化、对业务场景的拆解和落地。用一个具体的案例佐证。
2. **最弱的一块**：诚实说一个真实的短板，但要选"不致命、可改进"的，比如底层模型训练和推理优化经验有限、前端或产品侧经验较少、某个新框架实践较少。
3. **关键是补救**：说明你已经做了什么、接下来怎么补（学习计划、通过协作弥补）。
4. 避免说"没有缺点"，也避免说出与岗位核心要求直接冲突的弱点。

### 4. 项目里和算法/前端/产品吵过架么，怎么收尾

**答题思路**

HR 看的是协作方式和情绪成熟度，用真实经历，STAR 结构：

1. **情境**：什么分歧（如需求范围、效果指标、排期、接口设计），双方各自的立场和合理之处。
2. **行动**：先倾听并确认对方真正的诉求；用数据和事实而不是情绪说话（比如拿评测结果、线上 badcase 来对齐认知）；提出折中方案或分阶段方案；必要时找上级或相关方对齐。
3. **结果**：问题如何解决，关系如何，最终的产出。
4. **反思**：你学到了什么，之后如何提前对齐（例如提前定义验收指标）。

避免指责对方、把自己说成永远正确，也不要说"从没有过分歧"（不真实）。

### 5. 接Offer最看重什么，底座模型自由度、算力、还是业务数据

**答题思路**

1. 先表明自己的优先级排序，并给出理由。题目三个选项不必三选一，可以排序：
   - **业务数据和真实场景**：Agent 应用层的核心壁垒往往是场景、数据和闭环反馈，没有数据就无法做评测和 badcase 回流。对应用层岗位通常最关键。
   - **底座模型自由度**：能否根据任务选择和切换模型、做路由和微调，决定效果和成本的上限。
   - **算力**：保障实验和推理的效率，但通常是手段而不是目的。
2. 补充其他你在意的因素：团队和技术氛围、成长空间、业务的长期价值、工作方式。薪资可以提但不宜放第一位。
3. 回答要和你申请的岗位一致，并体现你对 Agent 落地规律的理解。

### 6. 当前薪资和预期，接受降薪试错么

**答题思路**

1. **当前薪资**：如实说，用总包口径（固定、绩效、补贴等）说明，不要虚报，背调和流水可能核实。
2. **预期**：给一个合理的范围，并说明依据（市场行情、岗位要求、自己的能力和成果），表现出可以沟通的弹性，同时看重整体机会而不只是数字；不要在没了解岗位职责和总包结构前报死价。
3. **降薪试错**：表明态度要诚恳但有底线。可以说"更看重岗位的成长和业务匹配，对短期的结构调整是可以沟通的，但希望整体回报与我的能力和贡献相匹配"，不要直接说"完全不接受"或"无所谓"。
4. 可以询问薪酬结构和职级范围，以便更准确地沟通。

注意：这里不写具体数字，请按自己真实情况回答。

### 7. 如果让你从Java后端切到AI Agent为主，前半年最不适应的会是什么

**答题思路**

结合自己的实际背景，真诚地讲，并展示你的应对计划：

1. **思维上的不适应**：Java 后端追求确定性，输入决定输出；Agent 的输出是概率性的，需要用评测集、概率指标和多次采样来衡量质量，不能只用单测通过与否判断。
2. **技术栈**：Python 生态和异步编程、模型和框架更新快、Prompt 和评测相关的方法论是新的，需要快速补齐。
3. **问题的边界模糊**：效果问题常常不是 bug，而是数据、检索、prompt 的综合结果，定位需要依赖 trace 和评测。
4. **你的优势**：Java 后端的工程经验在 Agent 落地里很值钱，包括高并发、线程池、稳定性、熔断降级、幂等、权限、存量系统集成、监控；这些恰恰是 Demo 到生产的关键。
5. **前半年的计划**：先接手一个小而明确的场景，建立评测基线，在实践中补齐 Python 与 Agent 框架，积极向算法同事请教。

### 8. 反问

**答题思路**

反问展示你对岗位和业务的思考，选 2 到 3 个问，避免问薪资福利等可以在 offer 阶段谈的问题，也不要问官网能查到的信息。可参考：

1. **业务和目标**：这个岗位当前最需要解决的问题是什么？Agent 项目现阶段在业务中的位置和半年内的目标是什么？
2. **技术和工程**：目前 Agent 落地用的是什么技术栈？有没有评测集和 badcase 回流机制？线上最大的挑战是准确率、成本还是稳定性？
3. **团队和成长**：团队的构成和分工、新人入职后的预期产出和培养方式。
4. **评价标准**：试用期或前半年，对这个岗位的期望成果是什么？
5. 对 HR 可以问：流程后续节奏、团队的情况和岗位的汇报关系。

提问时语气自然，最好顺着面试中聊到的内容追问，会比背好的问题更加分。
