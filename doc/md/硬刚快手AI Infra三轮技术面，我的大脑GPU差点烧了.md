### 3. 在 AI 训练场景下，如何设计和实现一个高性能的参数服务器（Parameter Server）？需要考虑哪些关键点？

**参考答案**

**结论**：参数服务器把参数和优化器状态按分片放在一组 server 上，worker 只 pull 参数、push 梯度；它适合稀疏更新，稠密大模型更常见的做法是集合通信。

分片按 key 或张量区间切到多台 server，用带虚拟节点的一致性哈希，扩容时只搬走一部分 key。特别热的 id 要复制或加盐拆开，避免打爆一台 server。推荐场景里一个 batch 只碰到少量 embedding 行：worker 先把重复 id 的梯度加总，再只传输这些行。Server 收到后在本地更新，优化器状态跟分片走，不要在每个 worker 上再复制一份。

一致性有三档。BSP 等齐所有 worker 再更新，等价于同步 SGD，好复现，慢节点会拖住全局。ASP 来一条梯度用一条，吞吐高，梯度可能基于很旧的参数。SSP 允许最快的 worker 最多领先最慢的 s 步，用有界陈旧换吞吐。

性能上把多次 push/pull 打成批量 RPC，和下一轮计算重叠；server 侧可以走 RDMA。Server 太少时网卡先满，太多则请求变碎。容错上每个 server 对自己的分片和优化器状态做完整快照，worker 失败后重新 pull。稠密梯度几乎全是非零，流量会聚到 server 网卡上，这种形状用 AllReduce 把带宽铺开更合适。容易漏的一点：异步看起来 step 更快，比较时要看达到目标指标的时间，不能只比 step time。

### 4. 谈谈对 CUDA 编程和 GPU 显存管理的理解，如何避免显存溢出（OOM）和优化 kernel 性能？

**参考答案**

**结论**：CUDA 用 grid、block、thread 把计算铺到 SM 上；显存是分层的，OOM 看的是分配峰值和碎片，kernel 慢多半是访存和占用率。

线程私有的是寄存器。寄存器溢出会落到 local memory，它虽然叫 local，实际在显存上，带宽很差。Block 内用 shared memory 复用数据，要避开 bank conflict。Warp 内分支发散会把两条路径串行执行。全局内存要合并访问，让一个 warp 的连续线程落到连续地址上。

训练显存的大头通常是参数状态、激活和算子临时缓冲。PyTorch 的缓存分配器会把释放的块留在池里，所以「逻辑上 free 了」进程仍占着显存；碎片还会让保留量明显高于正在用的量。先用 memory snapshot 分清是峰值、缓存还是碎片。降低峰值靠减小 micro-batch、激活重计算，以及不要把还连着计算图的 loss 一直攒在列表里。`empty_cache` 只是把缓存还给驱动，一次前向本身的峰值并不会因此下降。

Kernel 先分清吃算力还是吃带宽。带宽型就减少读写和 kernel 启动，把逐元素算子融合掉；算力型再看 Tensor Core 有没有吃到，形状要对齐，具体倍数随架构和精度变化。用 Nsight Compute 核对占用率、显存吞吐和是否在发生寄存器溢出。容易漏的一点：shared memory 用得越多，能同时驻留的 block 越少，占用率会掉下来。

### 5. 在分布式深度学习训练中，数据并行、模型并行、流水线并行的区别是什么？各自适用于什么场景？

**参考答案**

**结论**：数据并行切 batch，张量并行切层内矩阵，流水线并行按层切 stage。口语里的「模型并行」要先说明切的是算子还是层。

数据并行每卡一份完整模型、不同的 mini-batch，反向后对梯度做 AllReduce，再各自用相同的优化器步进。实现直接，通信主要是每步一次梯度同步。模型状态要放得进单卡，放不下就配合 ZeRO 或 FSDP 把优化器状态、梯度、参数切开。

张量并行把一次 GEMM 按行或列切到多卡。Megatron 风格的 Transformer 每层前向大约两次 AllReduce（注意力输出和 MLP 输出），反向再两次。通信步数多、延迟敏感，一般留在机内 NVLink，常见的并行度是 2、4、8。

流水线并行把连续的层分成 P 个 stage，stage 之间只传激活，可以跨机。空转来自填满和排空：每个 batch 有 M 个 micro-batch 时，空转大约占整次迭代的 \((P-1)/(M+P-1)\)。M 要明显大于 P，并用 1F1B 控制同时在飞的激活。各 stage 的计算量要均衡。

大模型通常组合使用：机内张量并行，跨机流水线，外层数据并行。容易漏的一点：流水线省的是每卡层数和激活，气泡不会因为卡数增加自动消失。

### 6. 场景题：假设训练任务出现通信瓶颈（如 AllReduce 耗时过长），你会从哪些维度进行排查和优化？

**参考答案**

**结论**：先确认变长的是链路本身，还是有 rank 晚到、把整次集合通信拖住了，再决定动网络、分桶还是并行切分。

排查按这个顺序：

1. 用 PyTorch Profiler 或 Nsight Systems 看 AllReduce 有没有露在计算外面。已经和反向重叠的时间，优化它收益很小。
2. 对齐各 rank 进入通信的时刻。最慢的那张卡算得慢、数据晚到，集合通信都会等它。这看起来像网络变慢。
3. 用单机和跨机的集合通信测试对比总线带宽，看掉没掉到 PCIe，或者某一跳有重传、拥塞。
4. 看消息大小。小桶是启动和延迟占主导，大块才是带宽占主导。同时看拓扑：张量并行的组有没有跨出 NVLink 域。

优化也按杠杆从低到高。先把梯度分桶，让算完的桶先通信。跨机流量仍然打满时，机内先归约、机间只对一份数据做 AllReduce，再在机内散回去；或者把频繁通信留在机内，跨机改走流水线。梯度累积能减少同步次数，代价是单步更大、交互更慢。8-bit 一类压缩要单独看精度。容易漏的一点：NCCL 超时很多时候是某个 rank 没有参加同一次集合通信，调用次数不一致，链路本身是通的。

### 7. 如何实现一个高效的分布式训练任务调度和资源管理系统？与传统的批处理调度（如 YARN、K8s）有何不同？

**参考答案**

**结论**：训练作业要么整组卡同时到位，要么就不要占着；调度器要懂 gang、GPU 拓扑和「失败就整组换卡续训」。

落地时常见的底座仍是 Kubernetes，上面加 Volcano、Kueue 这类批调度，而不是从零写一个资源管理器。作业提交时声明卡数、型号、显存和预计时长。调度器按队列和配额挑选后，必须一次分配齐全部 Pod：少一张卡，同步训练的 step 也进行不下去，已经占上的卡要整组让出来。放置时优先整机、同一 NVLink 域、同一叶交换机。抢占之前先看有没有可用的 checkpoint，否则抢到的只是一段白算的时间。

和传统批处理的差别在作业语义。YARN 擅长按 CPU、内存和数据本地性切很多短任务，单个任务失败可以单独重试。K8s 默认调度器按 Pod 逐个放置，一个 64 卡作业可能先占住 60 卡再无限等剩下的 4 卡。训练任务通常要跑几天，重试单位是整组进程加上最近一次完整快照，还要重新 rendezvous。资源视图里 GPU 也不是一个简单计数，型号、互联和健康状态都会影响能不能排到一起。

难点是碎片和公平。大作业要整机，小作业会把节点拆碎。可以用回填、整机预留和配额限制抖动。容易漏的一点：弹性扩缩容如果改变了张量并行或流水线的切分，checkpoint 要能按新的并行度重切，否则调度层扩了、训练层接不住。

### 8. 了解主流深度学习框架（PyTorch/TensorFlow）的分布式训练通信后端（如 NCCL、Gloo）吗？它们的优劣是什么？

**参考答案**

**结论**：GPU 上的大块梯度用 NCCL；Gloo 适合 CPU 张量和控制消息。两者经常在同一个作业里各干一层，不是二选一。

NCCL 提供 AllReduce、AllGather、ReduceScatter、AllToAll 和点对点，能按 NVLink、PCIe、InfiniBand/RoCE 组环或组树，并支持 GPU 之间 RDMA 直达显存。大消息偏 Ring，每卡发送量大约是 \(2\frac{N-1}{N}\) 倍数据，接近带宽最优，步数随卡数线性增加；小消息偏 Tree，步数是对数级。它跟 NVIDIA GPU 和 CUDA 绑定，不管分桶、优化器和容错。非 NVIDIA 卡要用各自的集合通信库。

Gloo 的 CPU 集合通信是完整的，PyTorch 里 CPU 张量的归约、一些进程组的小消息会走它。它也有 GPU 路径，但没有 NCCL 那套拓扑和带宽优化，GPU 上的大块梯度仍交给 NCCL。TensorFlow 的多机同步训练同样把 GPU 集合通信交给 NCCL 一类后端；参数服务器策略走的是另一条 RPC 路径。

MPI 常用来拉起进程，也能做 CPU 集合通信，GPU 上的大数据面仍交给 NCCL。容易漏的一点：比较「NCCL 和 Gloo 谁更快」之前先看张量在 CPU 还是 GPU。框架默认值一般是 CUDA 用 NCCL、CPU 用 Gloo。

### 9. AI 训练中 Checkpoint 的保存与恢复如何设计，以保证训练容错和高可用？

**参考答案**

**结论**：续训要保存的是「还能把同一步优化器接着算下去」的状态，并且只有写完整的那一份才能被恢复逻辑看见。

至少包括模型参数、优化器状态、学习率调度、全局步、各层随机数状态，以及 dataloader 的 epoch 和消费位置。混合精度 Adam 的动量、方差和 FP32 主权重比 FP16 参数大得多，只存推理用的权重可以导出模型，不能无损续训。ZeRO/FSDP 下这些状态是分片的，保存时要带上切分方式，恢复到另一种并行度时才能重切。

写的路径是：各 rank 写自己的分片，先落节点本地盘，训练继续往前走，后台再上传到耐久存储。上传完成之前，上一份已经发布的快照仍是恢复点。发布用清单文件，里面是分片列表和校验，清单原子改名之后才算这份可用。按时间和步数保留最近若干份。频率是在「丢得起多少步」和存储带宽之间取的，没有统一默认值。

高可用指的是：节点或机架挂了，作业能在别的健康机器上从最近一份完整快照拉起。本地盘只是缓冲。存储本身要有冗余，控制面不要只有一个调度器实例。训练进程是同步的一整组，挂了是重拉，不是热备接着算同一步。容易漏的一点：样本顺序没和步数一起恢复，续训会重复或跳过数据；上线前要实际做一次恢复演练，不能只看文件写成功。

### 10. 如何对训练任务进行性能 Profiling？通常会关注哪些指标（如 GPU 利用率、TFLOPS）？

**参考答案**

**结论**：先把一个 step 拆成计算、暴露的通信、数据等待和流水线空转，再用硬件计数器看这些时间有没有变成有效算力。

工具按层次选。PyTorch Profiler 看算子和 CPU 与 GPU 是否重叠；Nsight Systems 看 kernel、集合通信和拷贝的时间线；Nsight Compute 钻进单个 kernel 的访存和占用率；DCGM 看整卡的利用率、显存、功耗、时钟和错误。

GPU 利用率是 SM 在忙的比例，小 kernel 频繁启动也会把它打高。TFLOPS 是实际达到的算力，和标称峰值比的时候，峰值要和当前精度一致：FP32、TF32、FP16/BF16、FP8 不是同一个峰值。训练侧更常用 MFU，也就是模型有效 FLOPs 除以硬件峰值。Transformer 线性层部分常见按每 token 约 \(6N\) 估算（N 为参数量），注意力的二次项另计。重计算会多做一次前向，把这部分算进硬件 FLOPs 得到的利用率会高于 MFU。

同时还要看显存峰值、各 rank 的 step 时间差、tokens/s，以及 loss 和梯度范数是否正常。容易漏的一点：利用率、TFLOPS、MFU 回答的是三件不同的事，只报其中一个会把「很忙但在搬数据」说成训练很快。

### 11. 谈谈对 AI 编译栈（如 XLA、TVM）的理解，它们是如何优化计算图的？

**参考答案**

**结论**：编译栈把计算图 lowering 成目标硬件上的 kernel，主要收益是融合、布局和少写中间结果，数学上仍是同一个模型。

XLA 用 HLO 做中间表示。图上会做代数简化、常量折叠、死代码消除，以及把逐元素和规约融成更少的 kernel，再做布局选择和缓冲区复用。JAX、TensorFlow 的 jit，以及 PyTorch/XLA 都走这条链路。动态 shape 会触发重新编译，所以要么稳住形状，要么把编译结果缓存起来。

TVM 先在 Relay 或更新的 Relax 上做图级融合和折叠，再在张量级选择 tile、线程绑定和 shared memory。AutoTVM、Ansor、MetaSchedule 用搜索找调度，编译产物缓存成可加载的模块。它解决的是「同一套算子描述落到不同硬件」，热点 GEMM 仍常常打不过厂商手写库。

两边的共同点是减少 kernel 启动和 HBM 往返。PyTorch 里的 `torch.compile` 是同一类思路的另一条实现：Dynamo 抓图，Inductor 生成 Triton 或 C++。容易漏的一点：编译器不保证比 cuDNN、cuBLAS 或手写的 FlashAttention 更快；它更适合长尾算子和跨硬件，注意力这种热点经常仍要手写 kernel。

### 12. 如何监控和管理大规模 GPU 集群的健康状态与故障？

**参考答案**

**结论**：把故障分成卡、链路、节点、作业四层持续探测，坏设备先隔离，作业从最近一次完整 checkpoint 换一组健康卡续上。

卡上看温度、功耗、SM 时钟、显存 ECC 和 XID。降频会让一张卡变成同步训练里的慢节点。链路上看 NVLink 错误、PCIe 是否降速、网卡端口、重传和拥塞。节点上看磁盘、内存、内核日志，以及驱动、CUDA、通信库版本是否和集群基线一致。作业上看 step 超时、集合通信超时、loss 出现 NaN，以及各 rank 的耗时差。

只有 up/down 不够。空闲卡定期跑短的 GEMM 和集合通信，性能掉过阈值就打污点，调度器不再把作业分上去。作业侧用 watchdog 把 hang 收成失败，替换节点后重新组网，从最近一份完整快照恢复。同一交换机上的多个作业同时超时，要按机架聚合，这通常是网络而不是某一份用户代码。

容易漏的一点：慢卡比死卡更常见，也更难从「进程还在」看出来。健康检查要带性能阈值，集合通信的耗时也要能对上是哪一张卡晚到。

### 13. 手写算法：实现一个线程安全的 LRU 缓存

**参考答案**

**结论**：哈希表负责 O(1) 找到节点，双向链表维护使用顺序；get 和 put 都会改链表，所以两次操作都放在同一把互斥锁里。

命中时把节点挪到表头（最近使用）。插入新 key 时放在表头，超过容量就删掉表尾。更新已有 key 只改值并挪到表头，不改变个数。未命中返回 null，因此缓存值本身不用 null。容量小于等于 0 直接拒绝。

单次 get/put 在锁内是 O(1)，空间 O(capacity)。锁使这些操作串行。get 会改顺序，不能配读锁。锁保护的是表和链表；值对象如果可变，调用方还要自己保证值的并发安全。锁内不要做 IO 或回调。

`LinkedHashMap` 用 `accessOrder=true` 再覆盖 `removeEldestEntry` 能表达同样的淘汰语义，它本身不是并发容器。单次 `get`/`put` 可以外套一把锁；先 `containsKey` 再 `get` 这种复合动作仍要合成一次临界区。

```java
import java.util.HashMap;
import java.util.Map;

public class ThreadSafeLru<K, V> {
    private static final class Node<K, V> {
        final K key;
        V value;
        Node<K, V> prev;
        Node<K, V> next;

        Node(K key, V value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<K, Node<K, V>>();
    private final Node<K, V> head = new Node<K, V>(null, null);
    private final Node<K, V> tail = new Node<K, V>(null, null);
    private final Object lock = new Object();

    public ThreadSafeLru(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public V get(K key) {
        synchronized (lock) {
            Node<K, V> node = map.get(key);
            if (node == null) {
                return null;
            }
            moveToFront(node);
            return node.value;
        }
    }

    public void put(K key, V value) {
        if (key == null) {
            throw new NullPointerException("key");
        }
        synchronized (lock) {
            Node<K, V> node = map.get(key);
            if (node != null) {
                node.value = value;
                moveToFront(node);
                return;
            }
            node = new Node<K, V>(key, value);
            map.put(key, node);
            addFront(node);
            if (map.size() > capacity) {
                Node<K, V> lru = tail.prev;
                unlink(lru);
                map.remove(lru.key);
            }
        }
    }

    public int size() {
        synchronized (lock) {
            return map.size();
        }
    }

    private void moveToFront(Node<K, V> node) {
        unlink(node);
        addFront(node);
    }

    private void unlink(Node<K, V> node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addFront(Node<K, V> node) {
        Node<K, V> first = head.next;
        node.prev = head;
        node.next = first;
        head.next = node;
        first.prev = node;
    }
}
```

### 3. 项目深究：在模型推理服务（Serving）中，如何实现高吞吐、低延迟？有哪些模型优化（如量化、剪枝、编译优化）和工程优化手段？

**参考答案**

**结论**：延迟看单请求的首 token 和后续 token 间隔，吞吐看 GPU 有没有被连续的 batch 打满；模型侧减少每 token 的读写，工程侧避免静态 batch 的队头阻塞。

模型侧：权重量化（常见是 W8A16 或 W8A8）主要省带宽，激活量化才把矩阵乘放上低精度 Tensor Core，要用贴近线上的数据做校准。剪枝里，非结构化稀疏往往跑不满 GPU；NVIDIA 上能变成实际加速的，通常是硬件支持的 2:4 这类结构化稀疏。蒸馏换成小模型，编译用算子融合、FlashAttention、TensorRT-LLM 或 `torch.compile`。解码阶段 KV Cache 避免重复投影历史 token，GQA 减少 KV 体积，分页管理避免按最大长度预留。投机解码用小模型起草，再用大模型一次验证多步。

工程侧：continuous batching 每个 step 插入新请求、移除已经结束的请求。Prefill 偏计算，decode 偏带宽，两边分开调度，互相少抢。Decode 的 launch 开销用 CUDA Graph 吃掉。相同前缀复用 KV。副本按模型扩，限流和超时放在入口。

Batch 越大吞吐越高，排队越久，尾延迟越差，所以同时设最大 batch 和最长等待。容易漏的一点：decode 每步只算一个 token，却要读入全部权重，只加卡、不改调度，利用率上不来，成本先上去。

### 4. 设计一个支持多模型、多版本、动态更新的在线推理服务平台，需要考虑哪些架构模块？如何做流量调度和灰度发布？

**参考答案**

**结论**：平台按「不可变的模型版本 → 按硬件编译的运行时 → 带灰度的入口」拆开，回滚单位是版本，不是线上临时改权重。

模块有这些：

1. 仓库：权重、tokenizer、配置、依赖版本打成一个不可变版本。
2. 构建：量化、编译按 GPU 型号产出引擎。A10 和 A100 的引擎不能混用。
3. 部署：每个版本是一组副本，声明显存、并发和卡型。小模型可以用 MIG/MPS 共享卡，大模型独占。按模型分队列，避免一个长请求堵住其他模型。
4. 网关：按模型名和版本路由，做鉴权、限流、超时。
5. 观测：按版本拆开 QPS、首 token 时延、token 间隔、队列长度、显存和错误率。

动态更新先拉起新副本，健康检查通过再切流量，旧副本留到回滚窗口结束。灰度按用户或请求哈希放量，影子流量只对比结果、不返回给用户。错误率、延迟或业务指标越过事先定的线，就切回上一版本。Tokenizer、KV 布局变了要当成新模型，不能在有在途请求时原地覆盖。

灰度期间两套权重同时占资源，容量按重叠阶段预算。容易漏的一点：有状态的解码如果 KV 留在本地，切版本会丢掉这段缓存；粘性路由只能保证打到同一副本，不能代替版本兼容。

### 5. 如何保证分布式训练任务在数千张 GPU 卡上的稳定性和可扩展性？当训练任务频繁失败时，如何快速定位根因？

**参考答案**

**结论**：千卡上单卡故障会变成整组作业失败，稳定性靠快速隔离和续训；可扩展性靠通信仍走在合适的互联上，并且不要有 rank0 汇聚。

稳定性：启动前做健康检查，慢卡和坏卡不进作业。运行时对 step、集合通信和 NaN 设超时，把 hang 收成可重试的失败。Checkpoint 异步写、滚动保留，备用节点尽量预热，失败后替换并重新 rendezvous。卡数增加后，单卡的故障间隔没变，整作业碰到故障会更密，所以恢复时间要单独当成指标。

可扩展性：张量并行留在 NVLink 域内，跨机用流水线或数据并行；机内先归约，减少出机次数。日志、梯度和快照都不要汇到一个 rank。数据按 rank 分片读取，避免所有节点打同一个存储前缀。

频繁失败时按这个顺序收窄：

1. 先分类：起不来、中途 hang、数值坏了，还是被抢占。
2. 看空间是否扎堆：同一节点、机架或交换机反复出现，优先查硬件和网络。
3. 看时间是否扎堆：一次代码发布或一次数据切换之后才开始，优先查变更。
4. Hang 看各 rank 的集合通信次数是否一致，以及谁没有进入同一次调用。
5. 数值问题看梯度范数从哪一层开始异常，再用固定种子把卡数缩小复现。

容易漏的一点：千卡上很多「偶发 hang」是某个分支让个别 rank 少了一次 AllReduce，缩到两张卡、把那个分支喂到，才容易复现。

### 6. 在异构计算集群（包含多种型号的 GPU、AI 加速卡）环境下，如何设计资源调度策略以实现最优的资源利用率和任务性能？

**参考答案**

**结论**：先给设备建能力画像，再让任务声明硬需求；同步训练作业尽量同构放置，异构的价值是不同作业用不同的卡。

画像包括型号、显存、互联域、是否支持目标精度，以及软件栈。显存放不下、缺少算子或驱动不匹配的机器直接排除。一个同步作业里混进慢卡，整步会等最慢的那张，平均利用率看起来高，作业时间反而变长。所以默认把同一作业放进同一型号、同一 NVLink 域。

集群里同时有训练和推理时，用队列把它们分开：推理按延迟占住一小部分确定的容量，训练吃剩余的整机。大显存卡优先给放得下模型的作业，入口卡给小模型和低延迟服务。碎片用回填处理，小作业填进大作业暂时用不上的空档，但不要把整机拆得下一单大作业永远排不上。

必须混卡时，按实测的 step 时间配比切 batch 或调整流水线 stage，不按标称 TFLOPS 直接比例切。标称算力在不同 kernel 上的达成率不一样。切换和迁移以有 checkpoint 为前提，并设置冷却时间，避免作业在机型之间来回搬家。

目标函数是：延迟类作业先满足 SLO，然后再提高分配率。容易漏的一点：利用率最优和单作业最快经常不是同一个放置，调度策略要把作业类型写进目标，而不是全集群只留一个利用率数字。

### 7. 谈谈对大规模稀疏模型训练（如推荐系统）中 Embedding 层存储和通信优化的理解

**参考答案**

**结论**：推荐模型的 embedding 表往往比稠密网络大几个数量级，而每个 batch 只碰到其中很少的行，所以按行分片存储，通信只搬这些行。

存储上按 id 把行切到多台参数服务器或 GPU。热行留在内存甚至卡上，冷行放到 SSD，按访问再换入。Worker 对重复 id 做本地缓存，减少反复 pull。表的大小要用频次过滤或哈希分桶卡住，否则低频 id 会让表一直涨。优化器用稀疏 Adam 或 Adagrad，只给存在的行存状态，不要按稠密 Adam 给整张表留动量。

通信上，每个 step 只 pull 本 batch 的行、push 这些行的梯度。Worker 先把同一个 id 的梯度加总，流量正比于去重后的 id 数，和表的总行数分开算。热 key 会打满单个分片，需要拆分或多副本：读可以打到副本，写要能合并。

AllReduce 适合几乎全稠密的梯度。对这种极稀疏的更新，把整张表同步一遍会把大量零也发出去。这也是参数服务器还留在推荐训练里的原因。容易漏的一点：去重前后的 id 数可以差很多，容量估算要用去重后的数字；异步更新还要看热门 id 的写冲突会不会让线上指标抖动。

### 8. 中间件：在 AI Infra 中，消息队列（如 Kafka、Pulsar）可以用于哪些场景？与训练、推理流水线如何结合？

**参考答案**

**结论**：消息队列用来解开「不断产生的数据」和「按自己的节奏消费的训练或推理」，不拿来做梯度同步。

常见场景有四类。一是样本：曝光、点击日志进入队列，近线拼成样本，训练按消费组读取，并可以按位点重放。二是特征：同一条实时流既更新在线存储，也留给训练做回放，减轻训练和线上特征不一致。三是可延迟的推理：尖峰先堆在队列里，推理服务按自己的 batch 节奏拉，同步低延迟接口仍然直连服务。四是平台事件：checkpoint 完成、模型版本发布、评估结果，用来驱动下游部署。

和训练结合时，把消费位点写进同一次 checkpoint。只提交位点、快照还没写完，恢复会跳过一段样本；只写快照、位点已经往后走得很远，恢复会重复一大段。队列侧通常是至少一次，样本 id 要能去重。Pulsar 的分层存储适合要把日志留很久的场景，Kafka 的吞吐和生态更常见；已有哪一套就沿用哪一套，不要为了训练再平行引进一套。

容易漏的一点：队列不提供全局 batch 和严格一次的训练语义，乱序和重复是正常的。梯度 AllReduce 仍走 NCCL，不要为了「全链路都用消息队列」把同步训练的热路径绕进去。

### 9. 中间件：如何为 AI 场景设计和优化存储系统？例如，用于海量训练数据、特征、模型参数的存储，与传统对象存储有何不同？

**参考答案**

**结论**：AI 存储按访问形状拆开：训练样本是大文件顺序读，特征是按 key 随机读，checkpoint 是大对象写一次、读多次。对象存储适合当容量层，不适合当所有访问的热路径。

样本要先打包。大量图片如果一个文件一个对象，元数据会先于带宽打满。用 WebDataset、Parquet 这类分片做顺序读，客户端并行预取。对象存储前面加节点本地 NVMe 或并行文件系统，把重复扫描吃掉。所有 GPU 同时读同一个前缀时，要做预热或打散。

特征和 embedding 是低延迟随机读，放在 KV 或参数服务器的内存里，冷数据再落到 SSD。对象存储的请求延迟和按 key 更新都对不上这个路径。

Checkpoint 和模型版本适合对象存储的耐久和容量，但要分片并行写，并用清单文件做「写完才可见」。它不提供训练需要的文件锁和部分更新。写入带宽要和样本读取隔开或限速，否则 step 时间会跟着存盘抖动。

和传统对象存储相比，差在目标：对象存储优化的是耐久、成本和 HTTP 接口；训练优化的是每节点可持续的顺序带宽和可恢复的位点。容易漏的一点：把 POSIX 共享盘直接当千卡训练的唯一数据源，元数据服务器会先成为瓶颈。

### 10. 有没有关注过最新的 AI 硬件趋势（如 NVLink、CXL、存算一体）？它们会对 AI Infra 架构产生什么影响？

**参考答案**

**结论**：这几条趋势都在改变「数据离算力有多远」。调度和并行要读互联域、内存层级，不能再假设机器之间只有一种网络。

NVLink 配合 NVSwitch，把多张 GPU 收成一个高带宽域。张量并行、专家并行这种步数多的通信尽量留在域内。域从单机扩到机柜时，调度的分配单位要跟着变成整个域，张量并行才可以跨出单机机箱，同时仍然不跨进更慢的网络。

CXL 把额外内存接到系统上，容量变大，延迟高于本地 DRAM、通常低于跨机访问。它适合冷的 embedding、KV Cache 卸载和优化器状态卸载。软件要显式区分热层和这一层；把 CXL 内存当成无限的本地内存，热张量会落到慢层上。

存算一体是在数据旁边做固定计算，例如 embedding 的查找和部分聚合，减少把整张表搬来搬去。编程模型比较专用，适合推荐里的查表，不能当成通用训练后端去替换 GPU。

对架构的影响是：资源模型里同时有计算设备、互联域和内存层级；并行策略、卸载和 checkpoint 都读这张拓扑。容易漏的一点：带宽上去之后，小消息的延迟和 kernel 启动会变成新的瓶颈，集合通信的策略也要跟着改。

### 11. 当团队在技术方案（例如，选择自研还是基于开源方案进行二次开发）上产生重大分歧时，你通常如何决策和推进？

把立场换成可以比较的成本和一个有期限的对照。

### 12. 手写算法：给定一个计算图（DAG）的节点依赖关系，输出所有可能的拓扑排序序列

**参考答案**

**结论**：这是在枚举全部合法顺序，用 Kahn 的回溯：每一层把当前所有入度为 0 的节点各试一次，选中后把后继入度减一，回溯时恢复。

边 `u → v` 表示 u 必须排在 v 前面。入度用计数，邻接表存后继。递归走到节点全部入列，就收集一条序列。某一层没有任何未使用且入度为 0 的节点，说明剩下的子图里有环，这条路失败；整个图有环时，结果是空列表。节点按输入列表的顺序尝试，输出顺序是稳定的。

无边的 n 个节点有 \(n!\) 条合法序列，时间与「序列数 × 每层扫描的节点数」成正比，最坏大约 \(O(n \cdot n!)\)，没法按多项式时间输出全部结果。除结果之外的栈空间是 \(O(n)\)。只要任意一种顺序时，普通 Kahn 是 \(O(V+E)\)，和这题的要求不同。面试时先确认节点规模；图大就改成输出一种，或只计数。

例如 A、B 都指向 C，合法序列只有 A-B-C 和 B-A-C。

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

public class AllTopoOrders {
    public static List<List<String>> allOrders(List<String> nodes, List<String[]> edges) {
        List<List<String>> orders = new ArrayList<List<String>>();
        if (nodes == null) {
            return orders;
        }
        if (new HashSet<String>(nodes).size() != nodes.size()) {
            throw new IllegalArgumentException("duplicate node");
        }
        Map<String, List<String>> graph = new HashMap<String, List<String>>();
        Map<String, Integer> indeg = new HashMap<String, Integer>();
        for (String n : nodes) {
            graph.put(n, new ArrayList<String>());
            indeg.put(n, 0);
        }
        if (edges != null) {
            for (String[] e : edges) {
                if (!indeg.containsKey(e[0]) || !indeg.containsKey(e[1])) {
                    throw new IllegalArgumentException("edge node missing");
                }
                graph.get(e[0]).add(e[1]);
                indeg.put(e[1], indeg.get(e[1]) + 1);
            }
        }
        dfs(nodes, graph, indeg, new ArrayList<String>(), new HashSet<String>(), orders);
        return orders;
    }

    private static void dfs(List<String> nodes, Map<String, List<String>> graph,
                            Map<String, Integer> indeg, List<String> path,
                            Set<String> used, List<List<String>> orders) {
        if (path.size() == nodes.size()) {
            orders.add(new ArrayList<String>(path));
            return;
        }
        for (String n : nodes) {
            if (used.contains(n) || indeg.get(n) != 0) {
                continue;
            }
            used.add(n);
            path.add(n);
            for (String nxt : graph.get(n)) {
                indeg.put(nxt, indeg.get(nxt) - 1);
            }
            dfs(nodes, graph, indeg, path, used, orders);
            for (String nxt : graph.get(n)) {
                indeg.put(nxt, indeg.get(nxt) + 1);
            }
            path.remove(path.size() - 1);
            used.remove(n);
        }
    }
}
```

### 2. 从你的经验看，一个优秀的 AI Infra 团队应该具备哪些技术栈和能力？如何规划其技术演进路线？

技术栈对应五块：训练运行时（PyTorch、并行、集合通信）、推理运行时（批处理、KV、模型版本）、集群（调度、GPU 健康、网络）、数据与存储（样本、特征、checkpoint）、平台（实验记录、权限配额、发布和观测）。能力上要有人能把一个慢作业追到通信、显存或调度，而不是只会改配置；还要有人守住和算法之间的接口，包括指标、特征和回滚。

### 3. 如果由你从零开始搭建快手的 AI 基础设施平台，你会如何划分阶段和设定各阶段的里程碑目标？

### 4. 在 AI Infra 领域，如何建立有效的技术评估体系来衡量一个系统或组件的优劣（例如，对比两种参数同步策略）？

### 13. 手写算法：设计一个支持动态扩容缩容的分布式一致性哈希算法

**参考答案**

**结论**：把哈希空间围成环，key 顺时针找到第一个节点；增减节点只搬动相邻弧上的 key。虚拟节点用来把一台物理机拆成许多小弧，避免负载歪向某一台。

每个物理节点放 K 个虚拟节点。K 太少会倾斜，太多会让成员信息变大，具体个数看压测时的负载倾斜，常见会放到上百。哈希输入带上节点名和编号，所有进程用同一个函数、同一个 K，否则定位结果不一致。Java 的 `String.hashCode` 只有 32 位，相似节点名容易挤在一起，这里用摘要的高位做环上坐标。

定位是二分找到第一个大于等于 key 的虚拟节点，再顺时针收集 R 个不同的物理节点，作为副本列表。TreeMap 的插入是 \(O(\log V)\)，增删一台机器是 \(O(K \log V)\)，V 是环上虚拟节点总数。定位找到起点是 \(O(\log V)\)，凑齐副本最坏再扫一圈 \(O(V)\)。空间 \(O(V)\)。从 n 台扩到 n+1 台，期望大约搬走 \(1/(n+1)\) 的 key，其余 key 的归属不变。一台机器下线时，它的多段弧会散到不同的后继，不会都堆到同一台。

成员变更和数据搬迁分开。搬哪些 key 用一份影子环算：影子环里先加上或摘掉这台机器，和线上环比对，只有归属变了的 key 才拷贝。扩容时这些 key 在切换前双写，拷完再对线上环 `addNode`，旧主确认没有读之后再删。缩容时节点仍对外服务，先把数据推到影子环里的新主，到齐后再 `removeNode`。先摘成员、后拷数据，读会打到还没有数据的节点。

下面的类只回答「key 现在落到谁」。控制面在拷贝完成之后才调用 `addNode` 或 `removeNode` 切换路由。

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.ArrayList;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.NavigableMap;
import java.util.Set;
import java.util.TreeMap;

public class ConsistentHashRing {
    private final int virtualNodes;
    private final NavigableMap<Long, String> ring = new TreeMap<Long, String>();
    private final Map<String, List<Long>> owned = new java.util.HashMap<String, List<Long>>();

    public ConsistentHashRing(int virtualNodes) {
        if (virtualNodes <= 0) {
            throw new IllegalArgumentException("virtualNodes");
        }
        this.virtualNodes = virtualNodes;
    }

    public synchronized void addNode(String node) {
        if (node == null || owned.containsKey(node)) {
            return;
        }
        List<Long> hashes = new ArrayList<Long>();
        int i = 0;
        while (hashes.size() < virtualNodes) {
            if (i > virtualNodes * 8) {
                throw new IllegalStateException("too many hash collisions");
            }
            long h = hash(node + "#" + i);
            i++;
            if (ring.containsKey(h)) {
                continue;
            }
            ring.put(h, node);
            hashes.add(h);
        }
        owned.put(node, hashes);
    }

    public synchronized void removeNode(String node) {
        List<Long> hashes = owned.remove(node);
        if (hashes == null) {
            return;
        }
        for (Long h : hashes) {
            ring.remove(h);
        }
    }

    public synchronized List<String> locate(String key, int replicas) {
        List<String> result = new ArrayList<String>();
        if (ring.isEmpty() || replicas <= 0) {
            return result;
        }
        long h = hash(key);
        Map.Entry<Long, String> first = ring.ceilingEntry(h);
        if (first == null) {
            first = ring.firstEntry();
        }
        Set<String> seen = new LinkedHashSet<String>();
        for (Map.Entry<Long, String> e : ring.tailMap(first.getKey(), true).entrySet()) {
            seen.add(e.getValue());
            if (seen.size() == replicas || seen.size() == owned.size()) {
                break;
            }
        }
        if (seen.size() < replicas && seen.size() < owned.size()) {
            for (Map.Entry<Long, String> e : ring.headMap(first.getKey(), false).entrySet()) {
                seen.add(e.getValue());
                if (seen.size() == replicas || seen.size() == owned.size()) {
                    break;
                }
            }
        }
        result.addAll(seen);
        return result;
    }

    private static long hash(String text) {
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            byte[] digest = md.digest(text.getBytes(StandardCharsets.UTF_8));
            long value = 0L;
            for (int i = 0; i < 8; i++) {
                value = (value << 8) | (digest[i] & 0xffL);
            }
            return value & Long.MAX_VALUE;
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

**答题思路**

一两分钟，少讲技术细节，多讲你是谁、做过什么、为什么来。

1. 年限、方向，以及现在最主要的工作是训练、推理还是平台。
2. 用两句话概括一段经历和你在里面的角色，不展开架构。
3. 补一个和岗位相关的做事方式，例如把故障复盘写成记录、推一个有回滚的改造。
4. 收尾说明为什么看 AI Infra 的机会。
5. 职级和薪资留到后面的问题，这里不报。

### 2. 为什么选择快手，以及为什么对这个 AI Infra 岗位感兴趣？

**答题思路**

理由落在负载和自己能贡献什么，不落在名气上。

1. 短视频、直播和推荐带来的是持续的大规模训练与在线推理；生成式内容还会加上长时延的训练和很高的推理成本。这两类负载都需要基础设施，而不是只需要一个模型接口。
2. 岗位和自己做过的那一层匹配：调度、训练稳定性或推理服务。说清你能马上接手什么。
3. 这个方向还有多长时间的技术问题，例如千卡恢复、异构资源、推理成本，和你的规划一致。
4. 面试里听到的问题如果确实专业，可以作为感受提到，不编造团队内部情况。
5. 薪资和品牌可以是考虑因素之一，不作为唯一理由。

### 3. 回顾你的职业生涯，你认为自己最大的成就是什么？过程中遇到的最大困难是什么？

**答题思路**

成就和困难讲同一件事，让人看见你的角色，而不是团队的总成绩。

1. 选一件你真正拍过板或扛过的事。背景用两句说完。
2. 困难写具体：技术上到了哪个瓶颈，或者协作上谁的目标不一致。
3. 你做了什么：怎么取舍、怎么验证、怎么推到上线。
4. 结果用自己的真实数字。没有数字就讲行为变化，例如恢复从人工变成自动。
5. 补一句事后会改的地方。不把同事的工作说成自己的。

### 4. 你未来的职业发展规划是怎样的？希望在未来 3-5 年达到什么目标？

**答题思路**

按 1 年、3 年、5 年说，和 AI Infra 的岗位绑在一起。

1. 1 年内：摸清现有的训练或推理链路，独立负责一块能度量的系统，例如恢复时间、排队或线上延迟。
2. 3 年左右：能主导一条子系统的方案，包括自研还是基于开源、怎么灰度、怎么回滚。
3. 5 年：成为这一块的技术负责人，能做跨训练、推理和集群的取舍，并对稳定性负责。
4. 达成方式是持续做有对照的改进，并把排障方法留给团队。
5. 管理意愿如实说。如果目标是技术专家，就直接说，不把「带团队」当成唯一正确的答案。

### 5. 你通常如何应对工作压力或项目中的高挑战时刻？

**答题思路**

讲一次真实的高压场景，重点放在你怎么排优先级和同步风险。

1. 先说明压力来自哪里：故障、工期或一次没把握的上线。
2. 把问题拆开，分出现在会扩大损失的事和可以第二天再做的事。
3. 尽早同步风险和需要的支持，而不是自己扛到截止时间。
4. 事后写复盘，把临时动作变成检查项或自动化。
5. 表达你接受关键节点的投入，同时用平时的准备减少手忙脚乱。用自己的例子，不夸大成习惯性通宵。

### 6. 你期望在一个什么样的团队和文化中工作？

**答题思路**

谈做事方式，不谈抽象的形容词。

1. 讨论方案时能把问题追到通信、显存、调度或数据，决定写得下对照指标和回滚条件。
2. 值班、复盘和设计记录是常态，下一个人能顺着记录定位同类问题。
3. 职责边界清楚：训练、推理、集群各自有人负责，交叉的接口有人守。
4. 允许在小流量和可回滚的前提下试新方案，主路径有稳定性要求。
5. 反问一句对方团队实际怎么评审、怎么值班，把期望落到可核对的做法上。

### 7. 你如何看待工作与生活的平衡？

**答题思路**

承认关键节点要投入，也说明你怎么让这种投入不变成日常状态。

1. 上线、故障和有明确截止日期的窗口，你会跟着把问题解决完。
2. 平时用自动化、检查清单和提前暴露风险，减少反复的临时加班。
3. 长期排障需要可持续的节奏，连续透支之后定位质量会下降。用一次你主动提前沟通工期的例子说明。
4. 如果对方问具体加班强度，如实说出自己的边界，并问清这个岗位的值班方式。

### 8. 你目前的薪资构成和期望薪资是多少？

**答题思路**

用自己的真实数字，面试材料里不写示例金额。

1. 先说明现金、奖金和股票或期权分别是什么结构，不把总包说成月薪。
2. 期望给出一个区间，依据是当前收入、这个岗位的范围和自己负责的工作。区间之外表示可以谈。
3. 也可以先问对方这个级别的带宽，再把自己的区间放进去。
4. 同时看值班、成长空间和总包里长期部分的条件，不在条件没问清时只争一个月薪数字。
5. 语气直接，不贬低现在的团队。
