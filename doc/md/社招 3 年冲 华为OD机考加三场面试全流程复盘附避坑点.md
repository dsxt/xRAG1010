### 1. 第一题（100 分，模拟/字符串）：输入一串日志，每行格式为时间戳、日志级别和内容，要求按时间戳排序后，输出错误级别日志的去重结果

**参考答案**

题面没有给完整样例。下面按这个约定实现：每行是 `时间戳 级别 内容`，时间戳是整数，内容可以含空格；只保留级别 `ERROR`（不区分大小写）；内容相同只留时间戳最早的一条，时间戳相同则留先出现的一条；结果按时间戳从小到大输出。

先过滤再排序，去重键用内容。如果用整行去重，时间戳不同就去不掉。时间戳按数值排序，不按字符串排序，否则 `"9"` 会排在 `"10"` 后面。

时间 O(n log n)，空间 O(n)，瓶颈在排序。

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

public class ErrorLogDedup {
    static class Item {
        final long ts;
        final String content;
        final int order;

        Item(long ts, String content, int order) {
            this.ts = ts;
            this.content = content;
            this.order = order;
        }
    }

    public List<String> collect(String raw) {
        List<Item> items = new ArrayList<>();
        String[] lines = raw == null ? new String[0] : raw.split("\\R");
        for (int i = 0; i < lines.length; i++) {
            String line = lines[i].trim();
            if (line.isEmpty()) {
                continue;
            }
            String[] parts = line.split("\\s+", 3);
            if (parts.length < 3 || !"ERROR".equalsIgnoreCase(parts[1])) {
                continue;
            }
            long ts;
            try {
                ts = Long.parseLong(parts[0]);
            } catch (NumberFormatException ex) {
                continue;
            }
            items.add(new Item(ts, parts[2], i));
        }
        items.sort(Comparator.comparingLong((Item it) -> it.ts).thenComparingInt(it -> it.order));
        List<String> ans = new ArrayList<>();
        Set<String> seen = new HashSet<>();
        for (Item it : items) {
            if (seen.add(it.content)) {
                ans.add(it.ts + " ERROR " + it.content);
            }
        }
        return ans;
    }
}
```

例如输入四行：`100 INFO ok`、`200 ERROR disk full`、`150 ERROR disk full`、`180 ERROR timeout`。输出是 `150 ERROR disk full` 和 `180 ERROR timeout`。若题面规定整行完全相同才算重复，把去重键改成整行即可。

### 2. 第二题（100 分，滑动窗口）：给定一个数组和窗口大小 k，求每个窗口内第二大的数，输出整个结果序列

**参考答案**

这里的「第二大」指窗口里严格小于最大值的那个最大值。`[1,3,3]` 的第二大是 `1`，`[4,2,3]` 的第二大是 `3`。窗口里只有一种取值时没有第二大，下面用 `-1` 占位；如果数据里真有 `-1`，换成题面给定的缺省值。若题面把相同值算成两个名次，最大值出现两次时答案就是最大值本身，查询条件要跟着改。

每个完整窗口输出一个数，结果长度是 `n - k + 1`。用平衡树维护窗口里每个值的个数：进入窗口加一，滑出时减一，减到 0 就删键。最大值是最大键，第二大是比它小的下一个键。单次插入删除 O(log k)，总时间 O(n log k)，空间 O(k)。

单调队列只能稳定维护最大值。后进入的相等最大值会把前一个最大值从队列里挤掉，第二大不一定还在队列中，所以不能取队列里的第二个元素。

手写一次扫描时也容易错：相等的最大值不能写成第二大；第二大的初值如果用 `Integer.MIN_VALUE`，数组里真有这个值会判错。

```java
import java.util.TreeMap;

public class SecondMaxWindow {
    public int[] secondMax(int[] nums, int k) {
        if (nums == null || k <= 0 || nums.length < k) {
            return new int[0];
        }
        int[] ans = new int[nums.length - k + 1];
        TreeMap<Integer, Integer> window = new TreeMap<>();
        for (int i = 0; i < nums.length; i++) {
            window.merge(nums[i], 1, Integer::sum);
            if (i >= k) {
                int left = nums[i - k];
                int count = window.get(left) - 1;
                if (count == 0) {
                    window.remove(left);
                } else {
                    window.put(left, count);
                }
            }
            if (i >= k - 1) {
                Integer max = window.lastKey();
                Integer second = window.lowerKey(max);
                ans[i - k + 1] = second == null ? -1 : second;
            }
        }
        return ans;
    }
}
```

`[4,2,3,1]`、`k = 3` 的结果是 `[3,2]`。`[5,5,5]`、`k = 3` 的结果是 `[-1]`。

### 3. 第三题（200 分，图论/DFS）：给定若干个机房之间的网络连接关系，判断去掉任意一个机房后剩余网络是否还连通，输出所有这样的关键机房

**参考答案**

关键机房是无向图的割点：删掉它之后，连通块数量增加。下面按机房编号 1 到 n 的无向边来写。链 `1-2-3` 的关键机房是 `2`；三角形没有；星型的关键机房是中心。孤立点和叶子都不是。度为 2 的点仍可能是割点，不能只看度数。原图可以不连通，判断标准仍是连通块是否变多。

数据量小可以暴力：叶子不用试，对其余每个点，把它从所属连通块里拿掉，再搜索一次，看其余点是否还能互相到达。复杂度 O(n(n + m))。下面用 Tarjan 一次 DFS，时间 O(n + m)，空间 O(n + m)。

记 `dfn[u]` 为首次访问时间，`low[u]` 为从 `u` 出发能回到的最小访问时间。非根节点只要有一个孩子 `v` 满足 `low[v] >= dfn[u]`，`u` 就是割点。根节点要有至少两个 DFS 孩子。回边更新 `low` 时用对方的 `dfn`，用 `low` 会把结果传错。

建图时去掉自环和重复边，遍历时才能按父节点编号跳过。父边有多条时，只能跳过一条，不能把回到父节点的其他边全部忽略。输出按编号从小到大。链很长时递归深度等于节点数，需要加大线程栈或改成显式栈。

```java
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

public class CriticalRooms {
    public List<Integer> find(int n, int[][] edges) {
        List<List<Integer>> graph = new ArrayList<>();
        for (int i = 0; i <= n; i++) {
            graph.add(new ArrayList<>());
        }
        Set<String> seen = new HashSet<>();
        for (int[] edge : edges) {
            int u = edge[0];
            int v = edge[1];
            if (u == v || u < 1 || v < 1 || u > n || v > n) {
                continue;
            }
            int a = Math.min(u, v);
            int b = Math.max(u, v);
            if (!seen.add(a + "#" + b)) {
                continue;
            }
            graph.get(u).add(v);
            graph.get(v).add(u);
        }
        int[] dfn = new int[n + 1];
        int[] low = new int[n + 1];
        boolean[] cut = new boolean[n + 1];
        int[] timer = new int[1];
        for (int i = 1; i <= n; i++) {
            if (dfn[i] == 0) {
                dfs(i, -1, graph, dfn, low, cut, timer);
            }
        }
        List<Integer> ans = new ArrayList<>();
        for (int i = 1; i <= n; i++) {
            if (cut[i]) {
                ans.add(i);
            }
        }
        return ans;
    }

    private void dfs(int u, int parent, List<List<Integer>> graph,
                     int[] dfn, int[] low, boolean[] cut, int[] timer) {
        dfn[u] = low[u] = ++timer[0];
        int children = 0;
        for (int v : graph.get(u)) {
            if (v == parent) {
                continue;
            }
            if (dfn[v] == 0) {
                children++;
                dfs(v, u, graph, dfn, low, cut, timer);
                low[u] = Math.min(low[u], low[v]);
                if (parent != -1 && low[v] >= dfn[u]) {
                    cut[u] = true;
                }
            } else {
                low[u] = Math.min(low[u], dfn[v]);
            }
        }
        if (parent == -1 && children >= 2) {
            cut[u] = true;
        }
    }
}
```

### 3. String、StringBuilder、StringBuffer 的区别，分别用在什么场景

**参考答案**

String 不可变，适合常量、Map 的键和少量拼接；单线程拼接用 StringBuilder；多个线程共用同一个缓冲才用 StringBuffer。

String 的修改会生成新对象，字面量会进入字符串常量池。StringBuilder 和 StringBuffer 都在内部数组上追加，空间不够再扩容。StringBuffer 的单次修改方法带 `synchronized`，锁的是这个缓冲对象。一次 `append` 是安全的，先判断长度再追加这种复合操作，仍然要在外面加锁。

Java 8 里，一条表达式中连续的 `+` 通常编译成一个 StringBuilder。Java 9 之后多数改成 `StringConcatFactory`。循环里的 `+=` 每次生成新字符串，拼接很多次时自己用 StringBuilder。每个线程各拼各的，最后再汇总，一般不需要 StringBuffer。

### 4. Integer 的缓存机制，两个 127 和两个 128 用 == 比较分别是什么结果

**参考答案**

自动装箱的两个 127 用 `==` 比较是 `true`，两个 128 是 `false`。

`Integer a = 127` 会调用 `Integer.valueOf`。`-128` 到 `127` 的值返回缓存里的同一批对象，所以引用相同。128 超出默认上界，每次装箱是新对象，`==` 比的是引用。比较数值用 `equals`，或者拆成 `int` 再比。

`new Integer(127)` 不走缓存，两个 `new` 出来的对象用 `==` 一定是 `false`。`-XX:AutoBoxCacheMax` 只能调高上界，下界仍是 `-128`，业务代码不能依赖这个参数。一边是 `Integer`、一边是 `int` 时，`==` 会先拆箱再比数值，128 也会是 `true`。题目说的是两个包装类。

### 5. 重载和重写的区别，方法签名由什么决定

**参考答案**

重载是方法名相同、参数列表不同，编译期按实参的声明类型选定。重写是子类重新实现父类的实例方法，运行期按对象的实际类型调用。

方法签名由方法名和参数类型序列决定，泛型按擦除后的类型计算。返回值、访问修饰符和异常列表都不属于签名，所以只改返回值不能构成重载。

重写要求参数一致，返回类型可以是原类型的子类，访问权限不能更严，受检异常不能比父类更宽。`private`、`final` 和 `static` 都不能重写；子类里同名的 `static` 方法是隐藏，调用看引用的声明类型。`@Override` 能让编译器确认这是重写。重载没有多态，父类引用指向子类对象时，选哪个重载方法在编译期就定了。

### 6. volatile 的语义，能保证原子性么，典型使用场景是什么

**参考答案**

`volatile` 保证可见性，并通过内存屏障约束这个变量读写前后的重排序。它不保证 `i++` 这种读改写的原子性。

对 `volatile` 的写 happens-before 后续对它的读，所以一个线程写完，另一个线程再读能看到这次写入，以及写之前的其他写入。引用和 `int` 的单次读写本来就是原子的；`volatile` 让 `long` 和 `double` 的单次读写也不会被拆开。`count++` 仍是读、加、写三步，并发下会丢更新，计数要用 `AtomicInteger` 或加锁。

典型场景有两类。一类是停止标志：一个线程把 `boolean` 设为 true，工作线程周期性地读它。另一类是双重检查锁里的实例字段，避免别的线程看到还没构造完的对象。只发布一个不再修改的对象时，也可以用它做安全发布。它不能替代锁去保护复合状态。

### 7. synchronized 修饰静态方法和实例方法的区别，锁的是什么对象

**参考答案**

修饰实例方法锁的是 `this`，修饰静态方法锁的是这个类的 `Class` 对象。两把锁互不排斥。

同一实例上的同步实例方法会互斥，不同实例不会。所有线程调用该类的静态同步方法，抢的都是同一把 `Class` 锁。同步代码块锁的是括号里的那个对象；要和静态同步方法互斥，代码块就要锁同一个 `Class` 对象。

锁是可重入的，锁的是对象的监视器，不是锁住一段源码。子类的静态同步方法锁的是子类的 `Class`，和父类的静态同步方法不互斥。实例方法里的 `this` 是实际实例，子类对象调用继承来的同步方法，锁的是这个子类对象。

### 8. 线程池的核心参数，工作队列满了之后执行流程是什么样的

**参考答案**

`ThreadPoolExecutor` 的参数是核心线程数、最大线程数、空闲存活时间及其单位、工作队列、线程工厂、拒绝策略。存活时间默认只回收非核心线程，`allowCoreThreadTimeOut` 打开后核心线程也会回收。

执行顺序是：当前线程数小于核心线程数时创建核心线程；核心已满就把任务入队；队列也满了，并且线程数还小于最大线程数，才创建非核心线程；线程数已经到最大，执行拒绝策略。队列满了以后不会立刻拒绝。

默认拒绝策略是 `AbortPolicy`，抛 `RejectedExecutionException`。`CallerRunsPolicy` 让提交任务的线程自己执行，形成反压。`DiscardPolicy` 直接丢掉。`DiscardOldestPolicy` 丢掉队列头部再尝试提交。无界队列不会满，最大线程数基本不起作用，任务会一直堆积。`SynchronousQueue` 不保存任务，提交时更容易直接走到扩容。

### 9. JVM 运行时内存结构，哪些区域线程共享，哪些私有

**参考答案**

线程共享的是堆和方法区。线程私有的是程序计数器、虚拟机栈、本地方法栈。

堆上放对象和数组，也是垃圾回收的主要区域。JDK 7 起字符串常量池在堆里。方法区在 HotSpot Java 8 及以后的实现是元空间，使用本地内存，里面有类的元数据和运行时常量池，不在堆上，受 `MaxMetaspaceSize` 限制。

虚拟机栈保存栈帧，包括局部变量表、操作数栈、动态链接和返回地址。每个线程一份。程序计数器记录当前字节码位置；执行本地方法时它的值无效。规范里它是唯一不会因为空间不足抛出 `OutOfMemoryError` 的区域，栈太深抛的是 `StackOverflowError`。

直接内存用于堆外缓冲区，不属于上述运行时数据区，分配过多同样会 OOM。容易说漏的是：元空间不在堆里，字符串常量池也不在元空间里。

### 10. 常见的垃圾回收器有哪些，你们线上用的哪个，为什么

**参考答案**

常见的有 Serial、Parallel、CMS、G1 和 ZGC。JDK 8 在服务端机器上默认是 Parallel，JDK 9 及以后默认是 G1。CMS 在 JDK 9 标记废弃，JDK 14 移除。线上用哪个以启动参数为准，用 `-XX:+PrintCommandLineFlags` 看实际标志，不按 JDK 版本猜测。

Parallel 用多线程回收，适合堆不大、更在意吞吐量的服务。G1 按区域回收，可以设置停顿目标，堆到数 GB、希望停顿可控时常用它。ZGC 面向更低的停顿，JDK 21 提供分代 ZGC；延迟要求很高、堆很大时再考虑，并用 GC 日志核对停顿。

回答「你们用哪个」时，说你环境里的收集器、堆大小和当时看重吞吐还是停顿。没有看过启动参数，就讲选型依据，不编一个没运行过的收集器。

### 11. MySQL 的 B+ 树索引为什么适合数据库，和二叉树比优势在哪

**参考答案**

B+ 树矮、按页存放、叶子串成链表，能把磁盘随机 IO 压到很少几次，所以适合作为数据库索引。

二叉树一个节点只有一个键，千万级数据高度大约二十多层，每一层都可能是一次随机 IO。B+ 树一个节点对应一页，InnoDB 默认 16KB，内部节点只放键和子指针，扇出可以到几百，高度通常 3 到 4 层。

范围查询沿着叶子链表向右扫，相邻叶子在逻辑上有序。二叉树做范围要中序来回跳，指针在磁盘上不连续。InnoDB 的主键索引叶子放整行，二级索引叶子放主键，查二级索引后再按主键回表。和二叉树比，优势是高度和范围扫描，不是「有序」这一件事。

### 12. 事务的隔离级别，默认级别是什么，解决了什么问题

**参考答案**

四个级别是读未提交、读已提交、可重复读、串行化。MySQL InnoDB 默认是可重复读。回答时说明是 MySQL，有的数据库默认是读已提交。

读已提交保证读到的是已经提交的版本，解决脏读；同一事务里两次读同一行仍可能不同。可重复读让同一事务里的快照读看到稳定的行内容。串行化下普通查询也会加锁，脏读、不可重复读和幻读都压住，并发最差。InnoDB 的读未提交在普通查询上和读已提交接近，不能靠它获得可重复读。

InnoDB 在可重复读下，事务里第一次一致性读建立 Read View，之后都用这个视图。别的事务新插入的行不会出现在这个快照里。`select ... for update` 这类当前读还会加临键锁，挡住间隙里的插入。所以讲幻读时要分开说快照读和当前读，不能笼统说这一级完全没有幻读。

### 13. Redis 为什么快，单线程为什么还能扛住高并发

**参考答案**

快来自内存操作、IO 多路复用和很短的命令执行，不是因为「单线程」这三个字本身。

数据放在内存里，常用结构针对小对象做了编码。一个线程用 epoll 盯住大量连接，命令在读缓冲里顺序执行，没有锁竞争。单次简单命令是微秒级内存操作，所以一个核可以轮流服务很多连接。Redis 6 起可以用 IO 线程并行做网络读写和解析，执行命令仍然在主线程。持久化、关闭文件和懒释放在其他线程，整个进程不是只有一个线程。

单线程的约束同样明显：`KEYS`、对大 key 的删除、以及跑很久的 Lua，会堵住后面所有命令。高并发成立的前提是命令短、key 小。批量场景用 pipeline 减少往返，而不是开更多执行命令的线程。

### 14. 场景题：接口偶发超时，从收到请求到返回的链路上你会怎么一步步排查

**参考答案**

先确认超时发生在哪一段，再对同一时刻的证据，不先改索引或加机器。

1. 划定范围。看是单个接口还是全局，是一台机器还是全部实例。分清超时时间配在客户端、网关还是服务端。偶发要按时间对齐发布、GC、定时任务和流量尖峰。
2. 看入口。网关日志区分排队时间和上游处理时间。只有单机变慢，先看那台的 CPU、负载和连接数，必要时摘掉流量。
3. 看进程内。用链路追踪看时间花在业务代码、等锁还是等下游。线程池队列上升说明请求堵住了。同一时刻 GC 停顿变长，会表现为一批请求一起超时。
4. 看下游。数据库看慢查询和行锁等待，Redis 看慢日志和大 key，RPC 看超时与重试。一次偶发变慢经过重试会变成大面积超时。
5. 先止血。对齐超时时间、限制重试、对下游做隔离，再修慢 SQL 或热点。客户端先放弃而服务端还在执行时，重试会造成重复请求。

### 15. 手撕算法：实现一个 LRU 缓存，支持 get 和 put 操作，要求时间复杂度 O(1)

**参考答案**

用哈希表定位节点，用双向链表维护使用顺序。链表头部是最近使用，尾部是最久未使用。`get` 命中后把节点移到头部；`put` 已存在则改值并移到头部，不存在则插到头部，超过容量就删掉尾部。哈希表保证查找 O(1)，链表的插入和删除在已知节点时也是 O(1)。空间 O(capacity)。

更新已有 key 也算一次使用，要移动位置。容量只在插入新 key 且超过上限时检查。双向链表加头尾哑节点，删除时不用分空表和删头两种写法。Java 的 `LinkedHashMap` 在 `accessOrder = true` 时可以重写 `removeEldestEntry` 完成同样的事；要求手写时用下面这种结构。

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node oldest = tail.prev;
            unlink(oldest);
            map.remove(oldest.key);
        }
    }

    private void moveToHead(Node node) {
        unlink(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}
```

### 4. MySQL 慢查询怎么排查，explain 里你重点看哪些字段

**参考答案**

先从慢日志或 `performance_schema` 里找出贡献时间最多的 SQL，再对这条语句做 `explain`，最后改索引或改写，并用同样的流量确认耗时下降。

慢日志看执行时间超过阈值的语句，阈值按线上要求开。应用日志要能对上具体接口。在空表上做 `explain`，`rows` 没有参考价值，要用接近线上的数据量。

重点看四个字段。`type` 是访问方式，`const`、`eq_ref`、`ref` 比较好，`range` 通常可接受，`index` 是扫整棵索引，`ALL` 是全表扫描。`key` 是实际用上的索引，`possible_keys` 里有但 `key` 为空，就是没选上。`rows` 是估算的扫描行数。`Extra` 里的 `Using filesort`、`Using temporary` 表示排序或临时表；`Using index` 表示覆盖索引，没有回表。

`key_len` 能看出联合索引用了左边的几列，可空列会多占标记长度，要对照建表语句看。`type = index` 只是全索引扫描，不等于这条 SQL 已经够快。MySQL 8 可以用 `EXPLAIN ANALYZE` 看实际耗时，估计行数和真实行数差很多时，以它为准。

### 5. 索引失效的常见场景，平时写 SQL 怎么避免

**参考答案**

常见情况是索引列被计算或转换、联合索引没有从最左列用起、以及优化器认为全表扫描更便宜。

对列套函数、做运算，普通索引无法按原值查找，例如 `where date(create_time) = ...`。MySQL 8 可以给表达式单独建索引，那是另一棵索引。字符串列和数字比较时，列会被转换成数字，索引同样用不上。`like '%abc'` 不能走 B+ 树的前缀查找，`abc%` 可以。

联合索引 `(a, b, c)` 的查找从 `a` 开始。跳过 `a`，或者 `a` 已经是范围条件，后面的列就不能再用于定位。MySQL 8 在前导列区分度很低时可能走 Index Skip Scan，写 SQL 仍按最左前缀来。`or` 两边不是都能用索引时，经常退成全表扫描；两边都可以时，可能是 `index_merge`。

`<>` 和 `not in` 不是语法上禁止用索引，选择性差时优化器会选全表扫描。查出大部分行时也一样，这是代价选择，要用 `explain` 确认。

写法上让索引列以原样出现在条件里，等值列放在联合索引前面，范围列放后面。写完看 `type`、`key` 和 `key_len`，不用口诀代替执行计划。

### 6. Redis 的持久化方式，RDB 和 AOF 怎么选，线上怎么配的

**参考答案**

RDB 是某个时点的内存快照，恢复快、文件紧凑，两次快照之间的写入会丢。AOF 追加写命令，`appendfsync` 为 `always` 时每次写入都刷盘，`everysec` 大约丢一秒附近的数据，`no` 则交给操作系统。AOF 文件变大后要重写，生成一份更短的命令集。

能接受丢掉几分钟、希望尽快拉起时用 RDB。希望少丢数据时用 AOF 的 `everysec`。可以同时打开，并使用混合持久化：AOF 文件前半是 RDB，后半是增量命令，重启时重放更短。纯缓存、丢了可以从数据库回源，可以不持久化。`bgsave` 和 AOF 重写都会 `fork`，写多的实例要留出一份写时复制的内存余量。

线上怎么配，按自己环境说：开了哪种、`fsync` 策略、快照间隔、宕机后能不能接受那段丢失。主从复制不能代替持久化，主机宕机时从库可能还没收到最后的写。

### 7. 缓存穿透、击穿、雪崩分别怎么防

**参考答案**

穿透是查根本不存在的数据，缓存和数据库都没有，请求每次都打到数据库。先做参数校验。布隆过滤器可以挡住「一定不存在」的 key；它会放行少量实际上不存在的 key，所以还要用短 TTL 缓存空值，并限流。数据写入后要更新布隆过滤器，否则新 key 会被当成不存在。空值缓存要能在数据插入时删掉。

击穿是一个热点 key 过期的瞬间，大量请求同时回源。可以用互斥锁只放一个请求去查数据库，其他请求等待或短暂返回旧值。更稳的是热点不做硬过期，后台刷新；或者逻辑过期，读到旧值后异步更新。

雪崩是大批 key 同时过期，或者 Redis 本身不可用，流量一起落到数据库。TTL 加随机偏移，避免同一秒失效。缓存做主从或集群。数据库前面有限流和熔断，核心数据可以再加本地缓存。Redis 不可用时要有降级结果，不能让每个请求同步打数据库。

三个词对应三件不同的事：数据不存在、单个热点刚好失效、一批缓存一起没了。

### 8. Kafka 怎么保证消息不丢，从生产者到消费者分别说一遍

**参考答案**

生产者、Broker、消费者三段都要管。这样做得到的是至少一次，不是恰好一次，消费端要用业务幂等消化重复。

生产者显式设置 `acks=all`，等 ISR 里的副本确认，并处理发送回调里的失败。只发出去不等结果，失败就是丢。打开幂等生产者，重试时不会因为重复发送把同一批消息写多次。幂等要求 `acks=all`，在途请求数也要留在它允许的范围内。

Broker 侧副本数至少 3，`min.insync.replicas` 至少设为 2。这个值如果还是 1，ISR 里只剩首领时，`acks=all` 仍然会在首领写完后返回成功。关闭非 ISR 副本选举，避免一个落后副本当首领后把已确认的消息截掉。

消费者先处理业务，再提交 offset。自动提交可能业务失败了 offset 已经前进。处理完宕机、offset 没提交，会再投递一次，这是重复，要用唯一业务键挡住。

### 9. RocketMQ 的延迟消息和事务消息，分别在什么业务里用过

**参考答案**

延迟消息让消息到了指定时间才被消费。4.x 默认是从 1 秒到 2 小时的固定档，只能选档，不能选任意秒数；档位可以改 Broker 配置，但仍然是档。5.x 支持按指定时间投递。它适合超时关闭、超时提醒、失败后按间隔重试。到点的消费者要再查业务状态，因为人可能已经提前处理。重试时沿用原来的截止时间，不能从当前时间再顺延一个周期。

事务消息解决本地事务和发消息的一致。先发一条消费者不可见的 half 消息，再执行本地事务，然后提交或回滚。Broker 迟迟收不到结果会回查。回查只查本地事务的结果，提交、回滚或未知都要幂等。它适合「数据库里的状态变了，下游必须收到；本地回滚了，下游不能收到」，例如扣减成功才通知下游发货。

讲自己的经历时换成真实业务，按「消息承担哪一步、延迟或回查怎么判断、失败后怎么查」来讲。没有用过事务消息，就把回查和本地事务状态的对应关系讲清楚，不编一个没上线的场景。

### 10. 分布式锁用 Redis 怎么实现，过期时间续期怎么处理

**参考答案**

加锁用一条 `SET key token NX PX ttl`。`NX` 保证只有一个客户端成功，`token` 用每次加锁唯一的值。释放时用 Lua 比较 `token` 再删除，避免把别人刚拿到的锁删掉。`SETNX` 和 `EXPIRE` 分成两条命令时，进程可能死在中间，锁就没有过期时间。

业务时间可能超过 TTL。持有锁的进程要周期性续期：Lua 先确认 `token` 还是自己，再延长过期时间。Redisson 无参加锁的常见参数是租约 30 秒、大约每 10 秒续一次，直到主动解锁或进程停掉。加锁时如果自己传入了过期时间，看门狗不会启动，到期就释放。续期失败就停止业务或重新抢锁，不能继续改数据。把 TTL 设得很大可以少续期，进程崩溃后锁也会长时间不释放。

Redis 主从异步复制时，锁写在旧主、还没复制到新主，另一个客户端可能再次加锁。能接受这个窗口才用 Redis 锁。要求更强的互斥时，用数据库唯一约束、etcd 或 ZooKeeper。

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### 11. 场景题：公司内部审批流系统，审批节点超时要自动流转，怎么设计

**参考答案**

超时流转是审批状态机上的一次转移。节点实例上保存截止时间、当前审批人和状态。无论用定时扫描还是延迟消息，真正流转时都用条件更新：`where id = ? and status = '待审批' and deadline <= ?`。更新行数为 0，说明人已经批过或节点已撤回，任务直接结束。

扫描适合单量不大的内部系统。给 `(status, deadline)` 建索引，每分钟分批捞到期节点，多实例靠条件更新抢同一行。延迟消息适合要更准时的场景：进入节点时发一条到期消息，消费时再读数据库。RocketMQ 4.x 只有固定档位，任意超时可以用 5.x 的定时消息，或者仍以数据库扫描兜底。消息重复、提前投递都以数据库状态为准。

截止时间在进入节点时算好，重试不能从当前时间重新加一个超时。只计算工作时间时，用工作日历算截止点，不能简单加 24 小时。流转要写审批记录，并保证同一次转移不会发出两次通知。

人和定时器会同时点同一单，条件更新就是用来收口这件事的。扫描简单、好补偿；延迟消息更准时，仍然留扫描兜底。

### 12. 场景题：报表导出几十万条数据会超时，你怎么改造

**参考答案**

超时是因为一次请求里查出全部数据，内存、数据库连接和网关等待都扛不住。改成异步任务。

接口只创建任务并返回任务号，页面轮询或用消息通知下载。任务状态分为排队、执行、成功、失败。同一个用户重复点击时返回已有任务。同时执行的导出数量要限制。

查询按主键向后扫，`where id > ? order by id limit 1000`，不用大偏移量的 `limit`。每批只查需要的列，写完就释放连接。文件用 CSV 或流式 xlsx 往外写，不把几十万行放进一个列表。生成后上传对象存储，返回有时效的下载地址。xlsx 单表大约 104 万行，再大就用 CSV。

整个导出不要包在一个长事务里，否则 undo 会一直保留。每批独立提交，页面写明导出时间点，接受导出开始后的新写入不一定都在文件里。查询打在只读副本上，避免拖住主库。失败可以按任务重试，已生成的文件到期删除。

**参考答案**

AI 适合补样板、起草测试、解释陌生报错。质量靠约束和验证，不靠多生成几遍。

提问时给相关类、接口约定和报错原文，并写明不能改哪些模块。任务拆到一个函数、一条 SQL 或一组测试。一次生成整段架构，接口和事务边界很容易漂。

审查时重点看空值、事务、幂等、并发，以及它调用的 API 在项目里是否真的存在。测试要断言业务行为，不接受只为了能跑过而写的断言。合入前走编译、单测和原有的静态检查。密钥、生产数据和未公开的漏洞细节不贴进外部工具。

面试里讲一次自己真实用过的事，例如补了一个失败分支的测试，或者根据堆栈把调用链对上。说明你改了哪里、怎么验证。不说生成完没看就上线。

### 14. 手撕算法：二叉树的锯齿形层序遍历

**参考答案**

按层做 BFS。队列里先记下本层节点数 `size`，这一轮只处理这么多个，新入队的孩子属于下一层。第 0 层从左到右，第 1 层从右到左，之后交替。孩子始终按左、右入队，方向只影响这一层结果的书写顺序：先按从左到右收集，奇数层再反转。

时间 O(n)，空间 O(n)，主要是队列和结果。空树返回空列表。反转和双端队列头插都是 O(n)，反转更不容易写错下标。

根为 3、左 9、右 20，20 的左右是 15 和 7 时，结果是 `[[3],[20,9],[15,7]]`。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Queue;

public class ZigzagLevelOrder {
    static class TreeNode {
        int val;
        TreeNode left;
        TreeNode right;

        TreeNode(int val) {
            this.val = val;
        }
    }

    public List<List<Integer>> zigzagLevelOrder(TreeNode root) {
        List<List<Integer>> ans = new ArrayList<>();
        if (root == null) {
            return ans;
        }
        Queue<TreeNode> queue = new ArrayDeque<>();
        queue.offer(root);
        boolean leftToRight = true;
        while (!queue.isEmpty()) {
            int size = queue.size();
            List<Integer> level = new ArrayList<>(size);
            for (int i = 0; i < size; i++) {
                TreeNode node = queue.poll();
                level.add(node.val);
                if (node.left != null) {
                    queue.offer(node.left);
                }
                if (node.right != null) {
                    queue.offer(node.right);
                }
            }
            if (!leftToRight) {
                Collections.reverse(level);
            }
            ans.add(level);
            leftToRight = !leftToRight;
        }
        return ans;
    }
}
```

## 主管面

### 1. 自我介绍

**答题思路**

主管面听的是你能不能进组。一分钟，少讲框架名词。

1. 几年经验、做什么业务。
2. 你负责的那块系统解决了什么问题，结果用数量级。
3. 协作方式：需求从哪来，你怎么和测试、前端或对方团队对齐。
4. 为什么看这次 OD：方向匹配，并且你知道这是项目制用工。

讲完停住。和一面同一篇稿，会像没有针对这一轮准备。

### 2. 为什么考虑 OD，对 OD 和正编的差异了解么，怎么看待这个机制

**答题思路**

先讲清楚差异，再说你为什么仍然考虑。

1. OD 一般和供应商签合同，在华为项目里工作，不是华为正式编制。合同和社保主体、薪酬福利、项目结束后的去留，都和正编不同。有没有转正式编制的通道，以当时的招聘说明为准，不把「一定能转正」说成自己的判断。
2. 你仍然考虑的原因要具体：技术栈或业务匹配，机考按分数定级，规则直接，希望在规范的大项目里把一块系统做深。
3. 你的看法：按项目周期、技术含量、加班和出差能不能接受来评估，不把它说成和正编同一套待遇。

态度平稳，差异和接受度都说清楚。

### 3. 项目里遇到的最大挫折是什么，怎么走出来的

**答题思路**

选一次和你有关的事：上线故障、项目延期或方案被推翻。按情境、责任、行动、改变来讲。

1. 当时的目标、期限和你的角色。
2. 哪一个判断错了，影响是什么。讲事实，不讲成委屈。
3. 你怎么补救，优先保住了什么，找了谁一起处理。
4. 事情怎么收场，之后多了哪条机制，例如灰度、提前联调或复盘清单。

责任放在自己能改的部分。不选「我太追求完美」这种没有动作的例子。

### 4. 和同事意见冲突时你怎么处理，举个例子

**答题思路**

选一次排期或方案上的分歧，不选人际恩怨。

1. 先说明对方在保什么，例如工期、体验或稳定性。
2. 给出你的依据：数据、风险、工作量。同时给两个能执行的方案。
3. 当场能定就定。涉及排期和职责时，拉上负责人，把结论写下来。
4. 最后用了哪个方案，后面还能否继续合作。

如果后来证明是你错了，也可以讲，重点是你怎么改。不点名指责同事。例子用自己真实发生过的事，不现编一个圆满结局。

### 5. OD 项目组可能有驻场和出差，你能接受么，频率上有什么底线

**答题思路**

给出一条你做得到的频率。当场答应、入职后反悔，后面更难收场。

1. 能接受的部分说具体：上线、联调、故障时可以短期驻场或出差。范围按你的真实安排填，例如单次多久、一个季度大概几次。
2. 做不到的部分直接说：长期异地，或者和家庭安排冲突的频率。
3. 反问一句这个项目实际的驻场和出差频率，用对方的答案核对你的底线。

能接受就明确接受。接受不了就说边界，不说「看情况」。

### 6. 华为节奏比较快，加班强度你能接受到什么程度

**答题思路**

把接受度说成程度，不空喊能吃苦。

1. 版本发布、故障和截止日期前可以加班，事后把原因收掉，例如补自动化或提前联调。
2. 说出你的真实限度：工作日晚上到几点，周末能不能值班，连续加班几周还能不能保证质量。
3. 长期没有目标的熬夜、没有轮换的通宵，如果接受不了，就在这里说清楚。

高峰可以顶上，日常仍靠排期把活做完。这条底线和你实际能做到的一致。

### 7. 你的职业规划是什么，三年后想做到什么位置

**答题思路**

规划落在能力上，不报一个没有依据的职级。

1. 近一年：独立负责一个子系统，能把设计、上线和故障处理讲清楚。
2. 三年：在同一类业务上能判断优先级，带小范围的方案，而不是只接单点需求。
3. 和 OD 对齐：当前项目周期内把这块业务做深。后续发展看项目评价和当时的政策。

不说空泛的「成为技术专家」。也不把这段经历只说成短期跳板；可以说你希望之后能独立负责更完整的系统。

### 8. 薪资期望多少，目前手里有其他 offer 么

**答题思路**

OD 的薪级和机考分数相关，期望跟这个档对齐，不报一个没有依据的数。

1. 先核对口径：对应城市、税前月薪还是含补贴、一年发多少薪。分数对应的区间以沟通结果为准。
2. 给一个区间。下限是你能接受的数，上限略高于目标。区间来自你已经了解的行情和沟通，不在现场编。
3. 其他 offer 按实情说阶段：已经拿到、还在面试，或者目前没有。不拿不存在的 offer 抬价。
4. 必须当场给数时，连同税前和薪数一起说，并说明可以按机考定级再核对。

### 9. 你觉得自己相比其他候选人，最大的优势是什么

**答题思路**

只讲一条主优势，再补一条能被前面面试验证的辅优势。

1. 主优势：一块业务能独立闭环。用二面那个模块，一句话说明难点和结果。
2. 辅优势：基础和编码已经在机考、手撕里见过；或者联调时能把问题收口。
3. 收在岗位上：进组后能接手一块后端，不需要长时间带着看代码。

「学习能力强」「能抗压」换成谁都能说。只有配得上刚才那个模块时再提。

### 10. 你有什么想问我的

**答题思路**

问两三件影响你是否入职的事，优先问面试官本人知道的。

1. 项目现在到哪一阶段，入组后前三个月负责什么。
2. 团队的技术栈、协作方式，驻场或出差的实际频率。
3. 入项之后怎么评估，试用期看什么。

后续发展和转编制放在最后，请对方按现行政策讲。薪资已经谈过就不再问。加班刚才已经表过态，可以改成问版本发布的节奏。
