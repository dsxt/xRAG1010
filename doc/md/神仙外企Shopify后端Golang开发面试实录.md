## 一面

### 1. Goroutine 和线程的区别？

**参考答案**

goroutine 是 Go 运行时调度的用户态协程，线程是操作系统内核线程。goroutine 的创建和切换都轻得多。

goroutine 的栈最小约 2KB，不够就翻倍扩容，空闲时再收缩；Go 1.19 起还会按最近扫描到的栈使用量调整新 goroutine 的起始大小。线程栈一般是数 MB，而且创建要走内核。一个进程里可以有几十万个 goroutine，线程通常只能到几千。goroutine 切换主要是保存少量寄存器，不必进出内核。

跑 Go 代码的线程数接近 `GOMAXPROCS`。网络阻塞会把 goroutine 挂到 netpoller，线程继续跑别的任务；只有进入阻塞系统调用时，才会暂时多占一个线程。从 Go 1.14 起，长时间不主动让出的 goroutine 也会被信号异步抢占。

goroutine 之间常用 channel 传值。线程更常见的做法是共享内存再加锁。goroutine 泄漏会占着栈，栈还是 GC 的根，所以 goroutine 数量本身就要监控。

### 2. Go 的 GMP 调度模型？

**参考答案**

G 是 goroutine，M 是操作系统线程，P 是逻辑处理器。M 必须绑到一个 P 上才能执行 Go 代码。P 的数量就是 `GOMAXPROCS`。Go 1.25 起，Linux 上的默认值会取「可用逻辑 CPU」和「cgroup CPU limit」里较小的那个，看的是 limit，不是 Kubernetes 的 request；手动设置 `GOMAXPROCS` 则以设置为准。

每个 P 有长度 256 的本地运行队列，外加一个 `runnext` 槽，用来让刚被唤醒的 G 紧接着运行。本地队列满了，会把大约一半挪到全局队列。调度时先看 `runnext` 和本地队列；大约每 61 次调度从全局队列拿一个，避免全局队列里的 G 饿死；本地也没有，就去别的 P 偷一半。

G 阻塞在网络上时只占用一个 G，M 不退出。G 进入阻塞系统调用时，M 和 P 分离，P 可以交给别的 M，所以系统调用不会把逻辑处理器卡死。sysmon 会把运行超过约 10ms 的 G 抢占，也会把卡在系统调用里的 P 抢走。

容易说漏的是：P 的数量决定并行度，G 的数量可以远大于 P。把 `GOMAXPROCS` 调得比容器 CPU limit 还高，只会增加抢占和上下文切换。

### 3. Channel 的底层实现？有缓冲和无缓冲的区别？

**参考答案**

channel 在运行时是一个带锁的 `hchan`：环形缓冲区、发送下标、接收下标、发送等待队列、接收等待队列，再加上关闭标志。等待者用 sudog 挂在队列上。

无缓冲 channel 没有队列，发送和接收必须碰上。两边都准备好时，数据从发送方栈直接拷到接收方栈。

有缓冲 channel 把数据放进环形缓冲区。缓冲区没满，发送不阻塞；没空，接收不阻塞。缓冲区满了发送才阻塞，空了接收才阻塞。已经有接收者在等时，缓冲区一定是空的，这次发送会直接交给接收者。缓冲区满了且有发送者在等时，接收方拿走的是缓冲区里最老的元素，等待发送者的值补进缓冲区，这样顺序仍然是先进先出。

关闭规则：只能由发送方关闭；关闭 nil channel、重复关闭、向已关闭 channel 发送，都会 panic。对已关闭 channel 接收会立刻得到零值和 `false`。向 nil channel 发送或接收会永远阻塞。select 里把某个 case 的 channel 设成 nil，等于关掉这个分支。

### 4. select 的用法？底层实现？

**参考答案**

`select` 用来同时等待多个 channel 操作。哪个 case 先就绪就走哪个；几个同时就绪，就均匀随机挑一个，源码里的先后顺序不代表优先级。写了 `default`，所有 case 都没就绪就走 `default`，不会阻塞。空的 `select{}` 永远阻塞。某个 case 的 channel 是 nil 时，这个 case 永远不会被选中。

编译器把 `select` 交给 `runtime.selectgo`。每个 case 变成一条描述发送或接收的记录。运行时先按 channel 地址排序再加锁，避免两个 goroutine 以相反顺序锁同一组 channel 而死锁；选择时再用另一套随机排列，保证公平。有就绪的 case 就执行它。都没就绪又没有 `default`，就把当前 goroutine 挂到涉及的每个 channel 的等待队列上；其中一个唤醒它之后，再把自己从其余队列摘掉。

`time.After` 能做超时，但高 QPS 下每次都会分配一个定时器。循环里更合适的是 `context` 的截止时间，或者复用 `time.Timer`。

### 5. sync.Map 什么时候用？普通 map 呢？

**参考答案**

普通 `map` 并发读写会直接把进程打崩（`concurrent map read and map write`）。只有「大家一起读、没有人写」才是安全的。单 goroutine 使用，或者外面用 `sync.Mutex` / `sync.RWMutex` 包住整次读写，就用普通 map。临界区要短，不要在锁里做远程调用。需要一次遍历看到稳定视图时，互斥锁也比 `sync.Map` 好解释。

`sync.Map` 从 Go 1.24 起内部换成哈希字典树，Go 1.26 删除了旧的 read/dirty 实现。读路径无锁；写只锁目标 key 所在的节点，并用新叶子替换旧叶子。不同 key 落在不同节点时不容易互相堵住，也不再需要把 key「预热」进只读层。适合多个 goroutine 共用一张表、key 比较分散的缓存或连接表。key 和 value 都是 `any`，要类型安全就自己包一层。零值可以直接用，复制会出问题。

`Range` 不保证对应某一个完整快照，遍历过程中别的 goroutine 仍可能增删。旧说法「sync.Map 只适合读多写少」描述的是 1.24 之前的实现，现在写多一些也能用，但 map 很小、逻辑又简单时，一把锁往往更清楚。

### 6. Go 的 GC 原理？三色标记法？

**参考答案**

Go 的 GC 是并发、不分代、不整理内存的三色标记清除，用低停顿换吞吐和实现复杂度。

白色是还没访问到的对象，灰色是已经可达、子指针还没扫完的对象，黑色是子指针已经扫完的对象。从根（全局变量、goroutine 栈）出发，灰色对象被扫描后变黑，扫到的白色对象变灰。一轮标记结束后仍是白色的对象不可达，交给并发清扫回收。标记期间新分配的对象直接标成黑色，这一轮不会被收掉。

Go 1.8 起使用混合写屏障：覆盖一个指针时，总是把旧目标标灰；当前栈还是灰色时，新写入的目标也标灰。栈扫过一次就变成黑色，标记结束前不用再把所有栈重新扫一遍，所以 STW 只留在标记开始和标记终止这两个很短的窗口。清扫是懒的，分配内存时顺手扫一点。

`GOGC` 默认 100，大致是存活堆和根涨到原来的一倍左右再触发。后台标记的目标大约占用四分之一的 `GOMAXPROCS`。分配太快、标记跟不上时，业务 goroutine 会被拉去协助标记，延迟就会抖。Go 1.19 起可以用 `GOMEMLIMIT` 设软内存上限。

因为不移动对象，碎片靠按尺寸分档的分配器缓解。指针越少、堆上短命对象越少，GC 越轻。

### 7. context 包的作用？

**参考答案**

`context` 在一次调用链里传递取消信号、截止时间和少量请求范围的数据。

入口用 `WithTimeout` 或 `WithDeadline` 限定整次请求，用 `WithCancel` 表达主动取消。派生函数返回的 `cancel` 必须调用，否则定时器要等到父上下文结束才释放。父上下文取消，子上下文一起取消；子上下文取消不影响父上下文和兄弟。`Done` 返回的 channel 只读，取消时被关闭。

`WithValue` 只放 trace id 这类真正属于这一次请求的数据。key 用本包未导出的类型，避免和别的包撞在同一个 key 上。`context` 作为每个函数的第一个参数往下传，不要塞进一个活得很久的结构体。

取消要传到真正会阻塞的地方：数据库驱动、HTTP 客户端、等锁的地方都要看这个 ctx。只在自己的函数里听 `Done`，下游照样会把调用跑完。`context.Canceled` 和 `DeadlineExceeded` 要原样往上返回，业务重试要把它们排除掉。

### 8. defer 的执行顺序？

**参考答案**

一个函数里后注册的 `defer` 先执行，和栈一样。`defer` 后面的参数在注册这一行就求值，不是等函数返回时才算。

返回顺序是：先把返回值写好，再按相反顺序执行 defer，最后真正回到调用方。具名返回值因此可以被 defer 改掉。

```go
func f() (n int) {
    defer func() { n++ }()
    return 1 // 先把 n 设为 1，再执行 defer，调用方得到 2
}

func g() {
    i := 0
    defer fmt.Println(i) // 注册时记下 0，后面改 i 不会影响它
    i = 1
}
```

发生 panic 时，已经注册的 defer 仍按相反顺序执行。`recover` 只有直接写在 defer 调用的函数里才接得住 panic。`os.Exit` 和进程被杀掉都不会跑 defer。

循环里的 defer 要等外层函数返回才执行，次数多了会堆在一起。Go 1.22 起，每次循环的循环变量是新的；1.22 之前，defer 闭包会共享同一个循环变量，最后看到的都是最后一次的值。

### 9. 错误处理最佳实践？

**参考答案**

把 `error` 当作普通返回值，在出错的那一层处理一次。需要补充上下文时用 `fmt.Errorf("读订单: %w", err)` 包装，上层用 `errors.Is` 和 `errors.As` 判断，不用字符串比较。

调用后立刻检查错误。同一条错误在中间层只包装、不打日志，到请求入口或消费者再记，避免一条失败在日志里出现好几次。可预期的业务失败用哨兵错误或自定义类型；只有程序不该继续的状态才 `panic`。

`context` 取消和超时原样向上传，重试逻辑要把它们排除。多个独立失败可以用 `errors.Join` 合在一起。故意忽略错误时写成 `_ = do()`，并让读者看得出原因。错误字符串按 Go 的习惯小写开头、不加句号。

库的边界把底层错误包成自己的类型，调用方就不用依赖数据库驱动的具体错误。

### 10. 泛型用过了吗？有什么坑？

**参考答案**

Go 1.18 起，类型和函数可以有类型参数。约束是接口，用 `~` 表示底层类型，用 `|` 表示类型并集。只有约束允许的操作才能用在类型参数上，所以 `int | string` 上不能做加法。

Go 1.27 起，具体类型的方法也可以声明自己的类型参数，例如 `func (l List[E]) Map[R any](f func(E) R) List[R]`。接口方法仍然不能带类型参数，泛型方法也不能用来实现接口。想多态时，继续用普通方法或包级泛型函数。

编译器按内存形状实例化，指针类型会共用代码，方法通过字典查找，热路径上不一定比手写具体类型更快。类型推断推不出来时要显式写成 `F[int](...)`。`comparable` 不包括切片、map 和函数。类型参数的零值写成 `var zero T`。

只在同一套算法确实要服务多种类型时用泛型。约束写得太宽，函数里就什么都做不了；写得太窄，调用方又推不出类型。

## 二面

### 1. 设计一个高并发的计数器

**参考答案**

先分清要精确值，还是允许秒级误差。精确且并发高时，不能让所有请求去加同一个内存地址或同一行数据库。

单机用 `atomic` 加 `int64`。一个地址被打满、CPU 缓存行来回失效时，改成分片：每个分片填充到独立的缓存行，加法落到不同分片，读取时再求和。这和 Java 的 `LongAdder` 是同一思路。

多实例看精度：

- 浏览量、点赞这类允许丢最后一小段的计数，每个实例先在内存累加，按时间或条数批量 `INCRBY` 到 Redis。刷出去的间隔越长，Redis 压力越小，进程崩溃丢掉的也越多。
- 金额、库存这类必须精确的计数，把增量写成流水再异步汇总。单 key 的 `INCR` 在 Redis 里仍是单线程热点，QPS 极高时按 id 拆成多个 key，展示时求和。
- 读多的汇总值可以缓存极短时间。

分片和批量刷写换来吞吐，代价是读到的值稍旧，以及崩溃时还没刷出的那一截。金额不要做成一行余额让所有请求去更新。

### 2. 分布式 ID 生成方案？雪花算法？时间回拨怎么办？

**参考答案**

64 位数字、要按时间大致有序、又要能在多台机器上独立生成时，用雪花算法。Twitter 的布局是 1 位符号、41 位毫秒时间戳、10 位机器号、12 位序列号：每台机器每毫秒 4096 个号，自定义纪元大约能用 69 年。机器号必须全局唯一，重复的机器号比时钟回拨更容易撞号。

生成时记下上次的时间戳。同一毫秒内递增序列号，序列号用完就等到下一毫秒。时间戳比上次还小，就是时钟回拨：

- 回拨只有几毫秒，就自旋或睡眠，直到时钟追上上次的时间戳。
- 回拨很大，就停止发号并告警，或者切到预先留出来的备用机器号。继续用旧时间戳把序列号从 0 再发一遍，会和回拨前的 ID 冲突。
- 主机用 chrony 这类服务把时间调慢的方式修正，避免时间一下子往回跳。

不依赖时钟的做法是号段：从数据库一次取出一段 ID，在内存里发完再取。没有回拨问题，但依赖数据库，多台机器之间也不是严格按时间排好的。UUID v7 把毫秒时间放在高位，后面是随机位，128 位，回拨时靠随机位降低冲突概率，适合能接受更长 ID 的存储。

### 3. Redis 集群怎么部署？槽迁移？主从同步？

**参考答案**

Redis Cluster 把键空间分成 16384 个槽，`CRC16(key) % 16384` 决定槽位。生产上至少 3 个主节点，集群故障转移需要主节点的多数派。每个主配一个从，从和主分机部署。同一批要一起操作的 key 用 `{tag}` 放进同一个槽。客户端使用支持集群的库，收到 `MOVED` 后更新本地槽缓存。这和 Sentinel 不同：Sentinel 只给一份数据做高可用，不负责分片。

迁槽时，目标节点把该槽标成 `IMPORTING`，源节点标成 `MIGRATING`，再用 `CLUSTER GETKEYSINSLOT` 找出 key，逐个 `MIGRATE`。key 还在源上就由源处理；已经迁走的 key，源返回 `ASK`。客户端对这一次请求先发 `ASKING`，再访问目标，并且不要把槽的归属改掉。槽里的 key 迁完，再向集群广播 `SETSLOT NODE`，之后别的节点用 `MOVED` 告诉客户端新的归属。迁移中途崩溃可能让一个 key 在两边短暂同时存在，迁完要核对槽位和 key 数量。

主从复制默认异步。从节点带复制偏移量做 `PSYNC`，偏移量还在积压缓冲里就部分同步；否则主节点 `BGSAVE` 做一次全量。复制保证的是从节点收到了数据，不是已经可以线性一致地读。`WAIT` 可以等若干个从节点确认，它仍然不是共识协议。主节点被判定失败后，从节点向多数主节点拉票，偏移量更新的从节点优先上位。

### 4. MySQL 主从同步原理？延迟怎么处理？

**参考答案**

主库把提交写进 binlog，dump 线程发给从库。从库的 IO 线程把事件写入 relay log，SQL 线程再应用。现在一般用行格式 binlog，用 GTID 标识事务，故障转移时不用对文件位点。

MySQL 5.7 可以按组提交的逻辑时钟并行回放，8.0 还可以按 writeset 并行：同一库里只要改的行不冲突，就能同时应用。并行复制是缩小延迟的主要手段。

延迟的常见来源是大事务、从库硬件更弱、从库上还有分析查询、DDL。`Seconds_Behind_Source` 只是「正在执行的事件时间戳和从库当前时间的差」，中间没事件时会显示成 0。用心跳或比较主从 GTID 集合更可靠。

处理延迟分两层。复制本身：拆掉大事务，打开并行复制，从库不要和重查询抢资源。业务读：刚写完必须看见自己的写入时，这段读走主库，或者用 `WAIT_FOR_EXECUTED_GTID_SET` 等到从库执行过这条 GTID。可以接受旧数据的列表页继续读从库。

半同步（`AFTER_SYNC`）是主库在向客户端确认之前，先等至少一个从库收到 binlog。它不保证从库已经应用，所以从库读仍然会延迟。等待超时后还会退回异步，不能把它说成「数据一定不丢」。

### 5. 怎么做接口限流？滑动窗口和固定窗口？

**参考答案**

限流放在网关或接口入口，按用户、IP 或接口计数，超限返回 429，并带上 `Retry-After`。多个实例的限额必须放在共享存储里，用 Lua 把「判断」和「加一」做成一次原子操作。只在进程内计数，扩容会把总限额乘以实例数。

固定窗口给每一分钟（或每一秒）一个计数，实现就是 `INCR` 加过期时间。窗口交界处会叠在一起：上一窗口最后一秒和下一窗口第一秒各自打满，实际突发接近两倍限额。

滑动窗口统计的是最近一段时间。精确做法把每个请求的时间戳放进 Redis ZSET，丢掉窗口外的记录再计数，内存随请求量增长。近似做法只留当前窗口和上一个窗口的计数：`当前计数 + 上一窗口计数 × 窗口内还没过去的比例`。内存是常数，交界处比固定窗口平滑，结果不是精确值。

令牌桶按固定速率补令牌，允许一下子用掉桶里的余量。漏桶把出去的速率抹平。窗口算法回答的是「这一段时间里来了多少」，桶算法回答的是「能不能接受这一小段突发」。

### 6. 设计一个延迟任务系统？消息队列怎么选型？

**参考答案**

把「到点」和「执行」拆开。任务表是事实来源，字段至少有 id、执行时间、状态和 payload。时间索引可以用数据库的 `execute_at`，也可以用 Redis ZSET，score 存时间戳。

量不大、延迟又长，工作者用 `SELECT ... FOR UPDATE SKIP LOCKED` 拉取到期任务就够。秒级、QPS 高，用时间轮放在内存里，任务本身落库；进程重启时，把即将到期的任务从数据库装回时间轮。

扫描器抢任务时，用条件更新把状态从 pending 改成 running，更新成功才算抢到。然后交给工作者执行。工作者按业务单号做幂等，失败按退避重试，超过次数进死信。取消只改状态，执行前再读一次状态。

消息队列负责运送已经到期的任务，不负责记住很远的未来：

- 延迟是基本能力，还要事务消息：RocketMQ。4.x 是若干固定延迟级别，5.x 可以指定任意时间。
- 路由复杂、量中等：RabbitMQ 用消息 TTL 加死信，或者延迟消息插件。
- 高吞吐、按 key 有序的事件流：Kafka。Kafka 没有原生延迟消息，要延迟就得自己按时间分 topic 再投递，不适合当调度器。

多个扫描器、时钟不一致、执行不幂等、到期任务一下子堆积，是这套系统真正要处理的问题。

### 7. Kafka 的顺序消息怎么保证？

**参考答案**

Kafka 只保证同一个分区内部有序，不保证整个 topic 有序。

需要保持顺序的消息使用同一个 key，默认分区器会把相同 key 送到同一个分区。一个分区在同一个消费组里只分给一个消费者。生产者开启幂等：Kafka 3.0 起这是默认行为，`acks` 也默认是 `all`。幂等生产者按分区分配序列号，重试不会把后写的消息排到先写的前面。没有幂等时，要把 `max.in.flight.requests.per.connection` 设为 1，否则多个在途请求一重试就会乱序。

消费者关掉自动提交，这条消息处理完再提交它的 offset。拿到一个分区后再开多线程，必须按 key 串行；前面的消息失败了，后面的 offset 不能先提交。

两个生产者同时写同一个 key，它们之间没有顺序。消费失败后如果另起一个 retry topic 又没有按原来的 key 回到同一条分区，顺序也到此为止。幂等只覆盖生产者同一次会话里的重试，业务自己再发一次同样的消息，Kafka 不会帮你去重。

### 8. 微服务架构下怎么做监控？链路追踪怎么做？

**参考答案**

指标、日志、链路放在一起做，用同一个 trace id 串起来。

指标用 Prometheus 抓 QPS、延迟直方图、错误率和饱和度。在线服务看速率、错误、耗时，机器和池子看利用率、饱和度、错误。告警对着 SLO 和错误预算，而不是单机 CPU 抖一下就响。

日志用结构化字段，每条带上 trace id。排查时先从链路找到慢的那一跳，再下钻到日志。

链路用 OpenTelemetry。入口生成或继续传递 W3C 的 `traceparent`，HTTP、gRPC 和消息头都要接着传。Go 服务在 http、grpc 的中间件里建 span，数据库和 Redis 调用单独成 span。后端可以用 Jaeger 或 Tempo。生产消息时把 trace context 写进 header，消费时再取出来，否则链路在队列处断开。

正常流量可以降采样，错误和慢请求保留。span 里记操作名和耗时，不记完整 SQL 参数、令牌和用户隐私。只有链路、没有业务指标，仍然不知道该不该告警。

### 9. 设计一个抢红包系统？并发扣减怎么实现？

**参考答案**

金额用「分」做整数。发红包时把总额拆开，抢的路径在 Redis 里一次做完，数据库负责记账，不参加热路径。

拆分用二倍均值：还剩 `remain` 分、`n` 个人时，最后一人拿走全部剩余；否则在 `1` 和 `remain/n*2` 之间取值，并且不超过 `remain-(n-1)`，保证后面每人至少还有 1 分。这样总和等于总额，也不会出现 0 分。拆好的金额放进 Redis List。特别大的红包按片拆成多个 list，抢的时候随机挑一片。

抢的 Lua 脚本按这个顺序做：先 `LPOP` 一份金额，没有就返回已抢完；再写入「这个用户已经抢过」的标记，标记如果已经存在，就把金额推回去并返回已抢过。整个脚本在一个节点上原子执行，所以不会超发，也不会让同一个人抢两次。标记如果写在弹出之前，列表空了就会把用户记成已经抢过。

抢到以后发消息，异步写入领取流水，唯一键是红包 id 加用户 id。Redis 打开持久化。对账任务比较单据、已弹出的金额和流水，把没落库的领取补上。过期用延迟消息退回剩余金额，退回按红包 id 做幂等。

不要用数据库里的一行余额加锁来扛抢红包。热点在 Redis 的那个 list 上，用分片和 Lua 把单 key 的压力散开。

### 10. 热点数据怎么发现和处理？

**参考答案**

热点 key 是访问集中在极少数键上。大 key 是值本身太大。两件事经常一起出现，处理方式不同。

发现靠三处。业务预先知道秒杀商品、大账号，直接加白名单。网关或应用对 key 做本地计数，上报 top N。Redis 使用 LFU 淘汰时，可以用 `OBJECT FREQ` 看频率；`redis-cli --hotkeys` 会扫键，大实例上不能当常规手段。表现通常是某一个分片的 CPU 或延迟突然升高。

读热点：应用内做一层 TTL 很短的本地缓存，并用 `singleflight` 把同一个 key 的并发回源并成一次。还不够，就把值复制到 `key#0` 到 `key#n`，读的时候随机挑一个。写热点：按用户或时间片拆开，先在内存或队列里聚合，再批量落地，避免所有写打到一个 key。

值特别大时，拆字段或把详情放到对象存储，缓存里只留索引。本地缓存要有上限和过期，否则热点过去之后内存还占着，多实例之间的数据也会长时间不一致。

### 11. 缓存和数据库的一致性怎么保证？

**参考答案**

常规做法是 Cache Aside：读先看缓存，没有再读数据库并回填，回填带 TTL。数据库里不存在的 key 也缓存一个很短的空值，避免穿透。写的时候先更新数据库，成功后再删除缓存。删除失败就投递重试，或者订阅 binlog，由变更日志来删。

写路径删除缓存，而不是更新缓存。两个请求同时把新值写进缓存时，后到达的可能是较旧的一次更新，缓存会倒退。删掉之后，下一次读会按数据库的当前值回填。

先删缓存再改数据库，中间的读会把旧值填回去，窗口更大。

还有一种竞态：请求 A 已经读到旧的数据库值，还没回填；请求 B 更新了数据库并删了缓存；A 再把旧值写进缓存。窗口很小。要求更高时，缓存值带上版本，回填发现版本更旧就放弃；或者让 binlog 消费者再删一次。TTL 是最后的兜底。

用户刚写完就要看见自己的更新时，这一次读走主库，或者沿用本次请求里已经拿到的新值。需要强一致的余额、库存确认，不要走这层缓存。

### 12. 布隆过滤器了解吗？适用场景？

**参考答案**

布隆过滤器回答「这个元素一定不在集合里」。它可能把不存在误判成存在，标准实现不会把已经插入的元素误判成不存在。

底层是一个位数组和 k 个哈希函数。插入时把 k 个位置设成 1。查询时只要有一位仍是 0，就一定不存在；全是 1，只表示可能存在。位可以被多次插入共用，所以标准布隆不能删除。要删除就用每一位改成计数器的计数布隆，或者整体重建。

缓存穿透是典型场景：把数据库里已有的 key 放进布隆，查询时布隆说没有就直接返回。误判的代价只是多查一次数据库。爬虫 URL 去重、推荐里的「已经看过」、LSM 树跳过不可能包含这个 key 的文件，也是同一类判断。

位数组大小和哈希个数由预期元素个数、可接受的误判率决定。元素远超预期，误判率会明显上升。新增的 key 必须同步进布隆，漏加就会出现「过滤器说没有、数据库里其实有」。删除了数据库记录却不重建，只会让误判变多，不会把还存在的 key 挡掉。

## 三面

### 1. 项目中最有成就感的事情？具体讲讲？

**答题思路**

准备一个两分钟能讲完的故事，按这个顺序：

1. 当时的目标和约束：流量、正确性、期限，哪一个最紧。
2. 你负责的那一块，以及你做过的取舍。讲一个你否掉的方案，说明为什么。
3. 结果用你记得住的真实数量级：延迟、错误率、成本或人肉操作少了多少。记不清就说数量级。
4. 收在你会复用的做法上，例如幂等、限流或对账。

选你能接受连续追问的那件事。表结构、失败重试、监控告警都要讲得下去。英语面试先写一版 8 到 10 句的英文稿，按「背景、行动、结果」背熟。

### 2. 线上出过的最大故障？怎么解决的？

**答题思路**

按时间线讲，突出你自己的动作：

1. 现象和影响：哪些用户、持续多久、有没有错账或错单。
2. 怎么发现的：告警、用户反馈，还是你自己看到指标。
3. 止血：降级、限流、切只读、回滚，先让损失停止。
4. 根因：一条因果链，停在「改了什么就会再发生」。
5. 防再发：监控补了什么、发布或演练改了什么。

没有特别大的事故，就讲一个真实的中等事故，把复盘讲完整。责任写在机制上：缺告警、缺演练、变更没有灰度。准备好面试官追问「如果再来一次，你第一步做什么」。

### 3. 技术选型的原则？有没有选错的时候？

**答题思路**

原则按这个顺序说：

1. 问题是否匹配：吞吐、延迟、一致性、运维人数，哪一项是硬约束。
2. 团队能不能把它运行下去：值班、升级、排障，有没有人熟。
3. 失败时长什么样，数据能不能迁出来。
4. 用一次小范围验证代替口号。新，本身不是理由。

选错过就讲一次真实的选择：当时看重了什么，上线后哪项指标不符合预期，怎么止损，怎么迁出，之后选型清单多了哪一条。还没有明显选错，就讲一次你在两个方案里放弃更热闹的那个，以及放弃的理由。

### 4. 为什么选择 Shopify？对电商领域有兴趣吗？

**答题思路**

把动机落到平台型电商和你的经历上，按四句来说：

1. 你做过的系统和交易、库存、订单或支付里的哪一段有关。
2. Shopify 是多商家平台，复杂处在租户隔离、结账正确性和全球商家，而不只是一个商城首页。
3. 岗位是 Golang 后端，和你想深入的并发、存储、分布式问题一致。
4. 你对产品的一个具体观察：结账、店铺后台或应用生态。观察来自你真的用过或研究过的部分。

英文可以收在：I want to work on multi-tenant commerce, where correctness of checkout and inventory matters as much as throughput。文化、福利放在后面一句带过。

### 5. 对海外工作的看法？能接受远程吗？

**答题思路**

先给态度，再给协作方式：

1. 能接受远程，也能接受和团队核心时段重叠。说出你能稳定在线的时区范围。
2. 跨时区靠书面结论：设计、评审意见和事故记录写下来，而不是靠随叫随到。
3. 你已经用英文写过设计或处理过工单的话，举一个真实例子。
4. 出差或偶尔进办公室，说清频率和城市限制。

帖子里的氛围是远程可以协商。回答表达灵活性，同时把你的硬约束说在前面，例如时差最大能接受到几点。

### 6. 英语能不能正常交流？英语面试没问题吧？

**答题思路**

按真实水平说，并给出补救方式。技术讨论能进行，就直接说：

I can handle technical discussions. If I miss a word, I will ask you to rephrase, then repeat my understanding.

准备三样东西：一分钟自我介绍、一个项目、一次故障，各写一版口语稿，大声讲到顺。听不清时先复述你听到的部分，再问对方是不是这个意思。关键设计在会后用文字补一遍，说明你习惯把结论写下来。

不要把「能读文档」说成「会议里没有障碍」。面试官这一轮就是在取样。

### 7. 你的技术成长路径是什么样的？

**答题思路**

按阶段讲，每阶段只留一个标志：

1. 早期把一块做深：一条服务的性能、正确性或数据模型，能独立交付。
2. 中期能对一条链路负责：从接口到存储、失败和监控，能讲清取舍。
3. 后面开始影响别人的方案：评审、排障、把一次事故变成团队的默认做法。

每一段配一个真实例子。学习闭环是：线上问题，读文档或源码，写成可以复用的做法，再在下一次评审里用上。下一步对准这个岗位：把 Go 服务的并发和数据一致性做到能带人评审。职级名词少说，用责任范围说明。

### 8. 最近在学习什么新技术？

**答题思路**

只讲一个你能写得出实验或读过源码的题目。结构是：

1. 为什么学：工作里的哪类问题让你想弄清它。
2. 你做了什么：一个小实验、一次对比，或读了哪一部分实现。
3. 你还没搞清的一点。主动把边界说出来。

题目可以是你最近真的在看的 Go 运行时、Kafka 投递语义或 OpenTelemetry。面试官会顺着问原理，答不上的名词会伤这一轮。学了还没用到生产，就说明它解决什么问题，以及你还没把它放进生产的原因。

### 9. 如果让你做一个电商系统，你会怎么架构？

**参考答案**

按交易链路拆开。展示可以稍旧，库存扣减和订单状态必须有明确的状态机。

入口用 CDN 放静态资源和商品图，网关做鉴权、限流和 trace。服务按商品、库存、购物车、订单、支付、促销、履约拆开。商品详情和搜索走缓存和独立索引。

下单链路保持很短。请求带幂等键。先预扣库存：Redis Lua 或数据库条件更新 `available >= ?`。然后在订单库的本地事务里写下「待支付」订单，并用 outbox 记下后续动作。支付成功的消息把订单推进到已支付，再确认扣库存。超时用延迟消息取消订单、释放预扣。订单库和库存库之间不用分布式事务，靠预留、确认、取消和唯一约束。

订单按用户 id 分库。热点商品的库存分段。大促流量和日常下单隔离开，超额请求直接失败，而不是把数据库打满。

如果是多商家平台，所有表、缓存键和消息都带店铺 id，查询条件里始终带上它，避免一个店铺读到另一个店铺的数据。支付回调以渠道账单为准做对账，回调处理本身要幂等。

### 10. 怎么处理团队内部的技术争议？

**答题思路**

按这个顺序处理，英文面试也按这个顺序说：

1. 先写清分歧影响的指标：延迟、成本、交付时间、正确性。先对齐问题，再比方案。
2. 用一次有时间盒的验证或现有数据做判断。讨论设一个截止时间。
3. 明确谁拍板。拍板之后按决定执行，并把异议和理由记在设计文档里。
4. 涉及错账、数据泄露或不可逆迁移时，把风险升级，不因为要尽快结束讨论就放过去。

例子用一次真实的分歧：双方原来坚持什么，最后用哪条证据决定，决定之后你做了什么。可以这样说：We agreed on the constraint first, ran a small test, and the owner made the call. I followed it and wrote down the disagreement.

### 11. 你理想的工作环境是什么样的？

**答题思路**

讲协作方式，不讲福利清单：

1. 服务有明确的负责人，代码评审看正确性和失败路径。
2. 线上问题有复盘，结论会变成检查项或告警。
3. 设计结论写下来。跨时区的团队尤其要这样。
4. 工程师能接触生产指标和值班，而不是只交功能。

对应 Shopify 这种远程、英语环境，补一句你能接受异步沟通，也会保证核心时段在线。你不适应的点说一个具体的，例如没有评审就直接上线、或者只有口头决定。说完你怎么应对，面试官才能判断你和团队是否合得来。

## HR 面

### 1. 期望薪资？有没有 bonus？

**答题思路**

先谈总包，再谈结构。问清对方的组成：月薪、目标奖金、股票或 RSU、签约奖金，以及发放周期。

自己的数字用真实的当前总包和市场区间。报一个范围，说明区间对应的是总包，底薪和奖金可以再拆。对方问 bonus 预期时，反问他们的奖金是目标值还是保底、和绩效怎么挂钩。

还没了解到级别对应的带宽，就先问这个岗位的范围，再把你的区间放进去。对方坚持让你先开口，就用「当前总包，加上你认为合理的涨幅」这一种说法，涨幅和底数都用你自己的数。

### 2. 现在手上有没有其他 offer？

**答题思路**

按实际情况说。

- 有书面 offer：说明还在有效期内，不贬低那家公司，也不报一个没有的数字。时间线说清即可。
- 只有在进行的面试：说明在流程中，表达你对这一家的兴趣和大致决策时间。
- 没有其他机会：直接说目前在专注这条流程。

用真实进度换取对方的反馈时间，例如你希望什么时候知道下一轮。不要编造竞争 offer。

### 3. 什么时候能入职？

**答题思路**

用「通知期 + 交接」算出一个日期，当场就说这个日期。通知期按合同里的真实周数，交接留出你真的需要的时间，包括在途项目和值班移交。

如果有已经答应的发布时间，说明最早能走的日期，以及提前的条件。给一个确定的日子，比「看情况，大概一个月」更容易往下排。

### 4. 对工作地点有什么要求？远程还是办公室？

**答题思路**

直接给偏好和约束：

1. 能接受远程。说出你能和团队重叠的工作时区。
2. 如果团队需要办公室，说清你能去的城市，以及每周能到的天数。
3. 签证、搬迁或家庭对城市的限制，在这一轮说清楚。

帖子里远程可以协商。回答里保留这个灵活性，同时把不能接受的点说具体，例如完全没有重叠时段，或者必须全周在某个城市坐班。
