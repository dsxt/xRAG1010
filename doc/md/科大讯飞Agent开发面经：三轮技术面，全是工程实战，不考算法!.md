## 面试感受

面完感觉挺爽的，全程没问那些死记硬背的八股文，全是实打实的工程问题。面试官明显是做过大项目的，问的点都在刀刃上，比如 RAG 的分块策略、Agent 的死循环熔断、高并发下的流式输出。虽然没考算法，但手写 Agent 执行器和向量检索反而更能看出代码功底。整体下来，感觉科大讯飞对 Agent 开发的要求就是：“既要懂 AI，又要懂工程”。

## 一面

### 1. 自我介绍

**答题思路**

控制在一分半到两分钟，按「我是谁、做过什么、为什么匹配」讲，停在一个能往下挖的项目上。

1. 年限和主语言。说清你写的是在线编排、检索建库，还是工具接入。
2. 只讲一个真正上过线或完整跑通过的 Agent：用户是谁，系统是在回答、查询还是办理。你负责哪一段。
3. 补一个你能展开的取舍，例如分块、熔断或流式。有监控里的真实数字再说数字，并说清口径；没有就讲当时放弃了哪条方案。
4. 收到这个岗位：知识要能回到原文，工具要能超时和取消，循环要有步数上限。

技术细节留到追问，开场停在项目钩子上。

### 2. 项目介绍：讲一下你做的 Agent 项目，重点说清楚数据流和架构图

**答题思路**

按一次请求怎么流过系统来讲，让面试官能在纸上画出图。用自己的项目填空，没做的框不要画进去。

1. 入口：页面、开放接口还是坐席。用户发出的是问题、文件还是一个要执行的动作。
2. 同步路径：网关、编排、检索、工具、模型、流式返回。每一步标清进程和存储，模型厂商和向量库用真实组件名。
3. 异步路径：上传、解析、分块、向量化。这条线和用户正在等的回答分开，说明任务状态存在哪。
4. 在图上圈出你写的部分，以及你依赖别人的部分。
5. 用一个具体问题走一遍：证据来自哪份文档，工具失败时停在哪一框，结果从哪条连接回给用户。
6. 最后留一个钩子，分块、死循环熔断、流式输出里选你真正做过的那个。

### 3. RAG 全流程：请描述一个完整的 RAG 系统从文档上传到最终回答的端到端流程

**参考答案**

结论：上传只负责收下原文并排队；回答必须先检索到证据再生成，生成结果要能回到具体分块。

文件流式进对象存储，接口返回文档 id 和「处理中」。解析、分块、向量化在队列里做。解析保留标题、页码、表格和图片图注，页眉页脚丢掉。分块按标题切，超长再按句子切开，每块带文档 id、分块 id、标题路径和权限。向量索引和关键词索引用同一套 id。文档更新时写新版本，写完再切换，避免读到建了一半的索引。

提问时先按权限过滤，再走向量和关键词两路召回、融合、重排。命中的块和问题一起送给模型，并要求引用分块 id。检索为空就拒答。返回前核对引用是不是这次召回的，对不上就改成资料不足。日志留下召回 id、提示词版本和模型版本，方便回放。

容易漏的是：上传成功只说明文件在库里，不说明已经能搜。过滤要下推到召回阶段，后过滤会把名额占满。

### 4. 向量化选型：为什么选择这个 Embedding 模型？对比过哪些模型？如何解决中文长文本的语义漂移问题？

**参考答案**

结论：模型用业务问答集上的召回和延迟来选。长文本的语义漂移靠分块和标题上下文解决，整篇压成一个向量会把后半段冲掉。

对比至少放这几类：中文通用向量模型（如 bge 系列，其中 bge-m3 还能同时出稠密和稀疏表示）、多语言向量模型（如 e5 一类）、云厂商的 embedding 接口。看中文召回、最大长度、维度、能否私有化、接口延迟和许可证。换模型就要用同一模型重算全库，不同模型的向量不能放在一个索引里比余弦。

一个向量是整段的平均方向，一段里换了主题，后半段就几乎看不见。做法是按章节和句子边界切块，块首带上标题路径；检索用小块，送给模型用父块。超过模型最大长度会被截断，截掉的尾巴不会进入向量。查询侧可以把长问题改写成短查询，多一次生成就要单独算成本和跑偏的风险。

容易漏的是：入库和查询必须同一套归一化和度量。库用内积时，先做 L2 归一化，余弦才等于点积。

### 5. 分块策略：文档分块时，你是如何确定 Chunk Size 和 Overlap 的？遇到过哪些坑？

**参考答案**

结论：块的大小由「这一块能否独立回答一个问题」和嵌入模型的有效长度一起决定。重叠只补切口上的句子。

先按标题、段落、表格这些结构切，再按 token 上限兜底。制度、FAQ 常常几百 token 就够；合同和手册按条款切。中文一个 token 通常对应一到两个汉字，512 token 不是 512 个字。重叠的常见起点是块长的一成到两成，并且对齐句号或换行，再用同一套问答集看 Recall，不把这个比例当成最优解。

常见的坑：固定字数从表格中间切开；重叠太大，同一句占满 top-k；切得太小，代词失去所指；切得太大，一块里几个主题，相似度被稀释，也挤占生成窗口；块上没有标题路径，命中了也不知道属于哪一章；原文更新了，旧向量还留在库里。

容易漏的是：评测要固定 top-k 和生成模型。否则分块的变化和模型波动混在一起。

### 6. 检索优化：除了向量检索，你还用了哪些检索手段（如关键词、BM25）？如何做加权融合？

**参考答案**

结论：向量负责语义相近，BM25 和精确关键词负责专名、错误码、条款号。两路原始分数尺度不同，用倒数排名融合，或先归一化再加权。

关键词可以是倒排上的 BM25，也可以是编号、产品名的精确命中。元数据过滤（权限、时间、文档类型）在召回时下推。两路各自取一批候选。

倒数排名融合不看原始分数：一条文档的分数是各路 `1 / (k + 名次)` 之和，某路没召回到它就不加这一项。k 的常用起点是论文里的 60，上线用自己的评测集调，它不是相似度阈值。若做线性加权，先在本次候选集里把两路分数归一化；查询里有编号或专名时提高词法一路的权重。融合后再用交叉编码器重排前几十条。

容易漏的是：候选集内做 min-max，弱列表的第一名也会变成 1。排名融合没有这个问题。无权文档要在融合前剔除。

### 7. Prompt 工程：在 RAG 中，你是如何设计 Prompt 来减少模型幻觉的？

**参考答案**

结论：幻觉靠证据约束、拒答和返回后校验。只写「不要幻觉」约束不住模型。

提示分成三段：系统指令、带编号的资料、用户问题。资料段声明为数据，里面的文字不能改写系统指令。指令写明只根据资料回答，资料没有就说不知道，数字和日期要能在引用块里找到，两段资料冲突时点出冲突。事实问答把采样温度调低。

检索为空就不要调用生成。返回后检查引用 id 属于本次召回，关键数字能在对应原文里对上；对不上就改成资料不足。用户在问题里要求忽略资料时，仍按系统指令拒答或只依据资料。

容易漏的是：温度和提示都对了，把过多无关块送进窗口，模型仍会从噪声里补全。控制送入的块数是提示设计的一部分。

### 8. 工程架构：为什么选择 LangChain/LlamaIndex？如果不用框架，你会怎么设计底层的 Agent 执行器？

**参考答案**

结论：框架用来加快检索和工具接入。超时、幂等、取消和停止条件要落在自己能看懂的一层里。

LangChain 的工具、链、回调和模型适配比较全，适合把已有组件拼起来。它的抽象变得快，默认重试、记忆和最大步数藏在执行器里，上线前要逐项核对。LlamaIndex 的索引、检索器和查询引擎更完整，主路径是 RAG 时更短。Agent 循环只是它的一部分。主要矛盾在检索就偏向 LlamaIndex，主要矛盾在多工具编排就先看 LangChain 能不能把行为说清。

不用框架时，执行器保持一个有预算的循环。注册表记录工具名、参数 schema、超时和是否有副作用。每步把状态渲染成消息，调用模型，得到最终回答或一次工具调用。调用前做 schema 校验和鉴权，执行时带超时，结果以观察写回。停止条件包括最终回答、步数上限、相同参数重复、token 预算和用户取消。每步先落盘再执行写操作，进程重启后先核对结果，再决定要不要重试。

容易漏的是：自研指的是控制流，模型 SDK 和向量库客户端用现成的。把 HTTP 客户端也重写一遍，没有解决执行器的问题。

### 9. 并发处理：如果用户同时上传多个大文件，系统如何保证不卡死？

**参考答案**

结论：上传请求只把文件写入对象存储并入队。解析和向量化用有界的工作池，池满了就拒绝新任务，而不是堵住服务线程。

接口按流写文件，内存里只留当前缓冲。返回已接受和文档 id，状态是处理中。解析队列有全局容量，也有单用户容量，避免一个人的一批大文件占满工人。队列满时返回稍后重试。解析并发、向量化批大小、数据库连接和向量库写入分开限流。同一内容哈希已建过索引就复用，任务失败要落到失败状态并可重试，不能永远停在处理中。

容量看队列深度、解析耗时和向量化在途数。这些指标上涨时先减入口，再扩工人。

容易漏的是：同步在上传请求里做嵌入，几个大 PDF 就能把服务线程占满。进程还活着，新的问答也会一起卡住。

### 10. 线上问题：如果线上发现 Agent 回答质量突然下降，你的排查思路是什么？

**参考答案**

结论：先把检索、提示词、模型和服务故障拆开。用同一批问题回放，看是哪一层变了。

先看范围和起始时间：全站还是一个知识库，是否赶上发布、索引重建、提示词变更、模型版本变化。再看空检索率、引用对得上的比例、点踩、工具错误率和尾延迟。延迟没变而引用变差，多半是内容或提示；超时后走了兜底，会同时出现变慢和答非所问。

回放做对照：旧索引配旧模型、新索引配旧模型、旧索引配新模型。哪一组掉了，问题就在那一层。抽坏例时看召回块里有没有答案。没有就是分块、过滤或索引；有而答错，就是提示、截断或模型。还要查新文档解析失败、权限过滤变严、向量模型版本和库不一致、缓存了旧回答，以及模型别名在上游被换成了另一个版本。

止血时切回上一版索引或上一版提示，再查根因。

容易漏的是：只看模型日志，不看当时送进提示的分块。模型没看见证据，换模型也补不回来。

### 11. 手写代码：手写一个简单的 Agent 执行器，实现 ReAct（Reasoning + Acting）循环

**参考答案**

结论：ReAct 是「决定、行动、观察」的循环。模型负责下一步，执行器负责校验、调用工具、写回观察，并在步数或重复调用处停住。

经典格式是 Thought、Action、Observation。工程里 Thought 可以留在模型侧，Action 用结构化 JSON，循环不变。下面的实现最多走 `max_steps` 步。解析失败也占用步数。相同工具名和相同参数在执行前熔断，避免写操作被原样打第二次。读操作的瞬时失败在工具内部有限重试。

时间上最多 S 次模型调用和 S 次工具调用，S 为步数上限。空间是整段轨迹，随步数线性增长。模型和工具的耗时另计。交替调用两个不同工具也会空转，所以除了相同参数去重，还要有步数和 token 预算。用户取消和超时要传到工具和模型请求。

```python
import json
from collections.abc import Callable

def react(llm, tools: dict[str, Callable[[dict], str]], question: str, max_steps: int = 6) -> str:
    messages = [
        {
            "role": "system",
            "content": (
                "需要工具时只输出 JSON："
                '{"type":"action","name":"工具名","args":{}}。'
                "可以回答时只输出："
                '{"type":"final","answer":"..."}。'
                "不要编造观察。可用工具：" + "、".join(tools)
            ),
        },
        {"role": "user", "content": question},
    ]
    seen: set[str] = set()
    for _ in range(max_steps):
        raw = llm(messages)
        try:
            decision = json.loads(raw)
        except json.JSONDecodeError:
            messages.append({"role": "user", "content": "请只输出约定的 JSON。"})
            continue
        if not isinstance(decision, dict):
            messages.append({"role": "user", "content": "根节点必须是对象。"})
            continue
        if decision.get("type") == "final":
            return str(decision.get("answer", ""))
        if decision.get("type") != "action":
            messages.append({"role": "user", "content": "type 只能是 action 或 final。"})
            continue
        name, args = decision.get("name"), decision.get("args") or {}
        if not isinstance(name, str) or not isinstance(args, dict):
            messages.append({"role": "user", "content": "name 必须是字符串，args 必须是对象。"})
            continue
        signature = json.dumps({"name": name, "args": args}, sort_keys=True, ensure_ascii=False)
        if signature in seen:
            return "相同工具和参数被重复调用，已停止。"
        seen.add(signature)
        fn = tools.get(name)
        if fn is None:
            observation = "没有这个工具。可用：" + "、".join(tools)
        else:
            try:
                observation = str(fn(args))
            except Exception as exc:
                observation = "工具执行失败：" + type(exc).__name__
        messages.append({"role": "assistant", "content": raw})
        messages.append({"role": "user", "content": "Observation: " + observation})
    return "已达到最大步数，停止执行。"
```

容易漏的是：线上优先使用模型接口的结构化 tool call。从自然语言里抠 JSON 只适合作为兜底，正式执行前还要过参数 schema 和权限。

## 二面

### 1. 自我介绍

**答题思路**

二面多半已经听过项目。压到一分钟内，把时间留给并发、状态和流式。

1. 一句背景：年限、语言、系统是在线对话还是离线建库。
2. 只讲运行特征：有没有流式、会话存在哪、工具有没有写操作。
3. 数字只用自己监控或压测里见过的，并说明是同时在线会话、每秒请求，还是打到模型的并发。没统计过就说没统计，不编峰值。
4. 抛一个你处理过的稳定性问题，现象和改法各一句，然后停下来等对方选点。

### 2. 项目深挖：你项目里 Agent 的并发量是多少？如何保证高并发下的稳定性？

**答题思路**

先定义并发，再讲稳定性。两个数不要混在一个词里。

1. 并发量说明口径：同时进行的会话、每秒新请求、打到模型供应商的并发，是三个数。只记得其中一个就只报那一个，并说明统计窗口。没上线就标明是压测或估算。
2. 顺着链路讲你真做过的保护：入口限流、队列容量、模型并发上限、工具超时、用户取消能不能传到上游。
3. 写操作单独说：幂等键，以及超时后不确定是否成功时，先查询再决定要不要重试。
4. 补死循环的步数上限和熔断后用户看到什么。没做的直接说没做，以及你会加在哪一层。
5. 用一次真实压测或故障收尾：先坏的是哪一段，你怎么确认原因在容量上，而不是模型本身变了。

### 3. 流式输出：WebSocket 和 SSE（Server-Sent Events）在 Agent 场景下的区别？为什么选它？

**参考答案**

结论：普通对话是服务器单向推 token，用 POST 响应体里的 SSE。生成过程中还要持续上行语音、打断或协同编辑，再用 WebSocket。

SSE 基于 HTTP，内容类型是 `text/event-stream`，服务器往下推事件。浏览器自带的 EventSource 只能发 GET，还会自动重连并带上上次的事件 id。Agent 的提示通常在 POST 正文里，所以用支持流式读正文的客户端，自己记录事件 id。断线后用这个 id 把已经生成的后半段补上。反向代理要关掉这段响应的缓冲，并放宽读超时。

WebSocket 是全双工，能传二进制，适合边说边出字、中途打断。心跳、重连、鉴权和「连接在哪台机器」要自己做。生成若发生在另一台机器，还要有一条把 token 送到持有连接的节点的通道。

选择就按上行需求说。只把回答流式打出来，SSE 沿用现有的 HTTP 网关。选了任何一种，用户取消都要传到上游模型请求，停止继续生成。半段回答不能当成完整回答落库。

容易漏的是：SSE 一样会断。没有事件 id，重连要么从头重复，要么丢掉后半段。

### 4. 状态管理：Agent 多轮对话中，如何管理对话状态？如何防止 Token 窗口爆炸？

**参考答案**

结论：状态是结构化会话，包含摘要、最近几轮、槽位和未完成的工具调用。窗口用预算管理，旧内容先摘要，工具原文按 id 去取。

热状态按会话 id 放 Redis，有新消息就续期，空闲再过期。完整消息落库，Redis 丢了可以用摘要和最近消息重建。同一会话的写入串行，避免两轮交错改槽位。写操作发出前，先把「准备调用什么」落盘；重启后先查下游结果，再决定是否重试。

防爆窗先用所用模型的分词器算预算，给生成留出位置。系统约束、未完成的工具结果保留原文。更早的对话收成滚动摘要，摘要只保留已有的决定、数字和承诺。工具返回存原文，上下文里留摘要和 id。丢弃顺序是旧的工具原文，然后才是更早的对话。

容易漏的是：关键约束若只存在摘要里，可能被压掉。退款上限、已经确认的单号这类槽位单独存放。

### 5. 消息队列：为什么要在 Agent 系统中引入 Kafka？它解决了什么问题？

**参考答案**

结论：Kafka 把用户正在等待的对话，和可以稍后完成的建库、审计、离线评测拆开，用来削峰和重放。

文档解析和向量化耗时长。上传接口把任务按文档 id 投递出去，工人按能力消费，对话服务的线程就不会被大文件拖住。审计日志和评测样本用各自的消费组，互不影响。消费滞后能直接解释「刚上传的文档还搜不到」。同一文档的更新落在同一分区，顺序才有意义；消费端用版本号，旧消息不能覆盖新索引。投递至少一次，效果上的去重靠这个版本号。

用户还在等待的那一轮工具调用，用带超时的直接调用。放进 Kafka 会把等待变成队列延迟，重复消费还可能把写操作执行两遍。

容易漏的是：分区保证的是分区内有序。扩分区之后，同一个 key 的新消息可能进新分区，旧分区里的旧消息仍可能晚到，版本号仍然要比较。

### 6. 缓存设计：Agent 的上下文缓存用 Redis 还是 MySQL？为什么？如何设计缓存失效策略？

**参考答案**

结论：热上下文用 Redis，需要追溯的消息和审计用 MySQL。Redis 负责按会话读写和过期，MySQL 负责历史。

一轮对话要整包读出摘要、最近轮次和槽位，还要在空闲后消失。这个访问形态用 Redis 的一个会话 key。MySQL 按会话存消息，适合翻历史和追责；每轮热路径不去扫这张表。Redis 未命中时，用库里的摘要和最近消息重建。

失效分三类。会话空闲超过产品定义的时间就过期，有新消息续期；用户清空、退出或权限变更时主动删除。检索缓存的 key 带上知识库版本、过滤条件和向量模型名，版本一变就读不到旧条目，再加一个 TTL 做兜底。事实型最终回答缓存很短，或者只缓存检索结果，知识更新后继续返回旧答案会直接表现为质量下降。热点会话用单飞，避免缓存同时失效时把数据库打满。

容易漏的是：上下文里有手机号和证件时，缓存和缓存日志都要按字段脱敏，并限制谁能查看。

### 7. 文件上传：大文件上传的流程是怎样的？如何做断点续传？

**参考答案**

结论：大文件按固定分片上传，服务端记住已收到的分片序号。中断后只补缺片，齐了再校验、合并、投递解析。

先申请上传，提交文件名、大小、整体哈希和分片大小，服务端发 upload id。哈希已经存在就复用原文件。客户端按序号上传分片，重复上传同一个序号直接返回成功。进度接口返回已收到的序号，续传只补缺的。完成时检查分片齐全且整体哈希一致，合并成正式对象，再进入解析队列。超时没完成的上传清掉临时分片。

分片大小按网关超时和存储规则定。对象存储的分片上传对非最后一片通常有最小尺寸。upload id 要绑到用户，避免猜到 id 就能往别人的文件上写。

这里的断点续传是上传续传。HTTP Range 是下载续传，解决不了「第 7 片没传完」。

容易漏的是：合并前不校验整体哈希，缺一片或错一片会做出一份坏文档，后面的索引也会跟着错。

### 8. 性能瓶颈：Agent 系统的性能瓶颈通常在哪里？如何做性能调优？

**参考答案**

结论：先看分段耗时。多数 Agent 的时间花在模型等待和检索上，应用自己的 CPU 很少是第一处。

首 token 慢，常见是模型排队、提示过长、连接池太小。检索慢，常见是过滤没下推、top-k 过大、把上百块都送进模型。工具慢，常见是彼此独立的只读工具被串行调用，或者超时设得比网关还长。建库慢，是因为嵌入还做在上传请求里。供应商一抖，没有预算的重试会把在途请求放大。

调优对着测量结果做：回答改为流式；每次只把路由出来的少数工具说明放进提示；重排只处理前几十条；只读工具并行，写工具串行；重复检索按知识库版本缓存；简单问题走小模型；入口按用户和全局限流。重试要有次数、退避和抖动，并且受这一轮剩余时间约束。

容易漏的是：平均延迟正常时，尾延迟已经把线程占满。容量看尾部和在途数。

### 9. 容错机制：当 Agent 调用外部工具失败时，系统如何降级处理？

**参考答案**

结论：先给失败分类。可重试的只限幂等读操作；写操作超时后先查询状态，再决定是否重试。

超时、429 和 5xx，对幂等读做有限次重试，指数退避加抖动。参数错误把简短原因写回观察，让模型改参数或向用户说明，同一组参数不再打。某个工具错误率过高就熔断一段时间，熔断期间走降级。降级顺序可以是：带时间标记的上次成功结果、改成只回答知识库、转人工。这一轮剩余时间不够就停止，不再接一个更慢的工具。

写操作使用幂等键。超时只说明响应丢了，下游可能已经执行。先用查询对账，向用户说明当前不确定的是哪一步。

观察里放失败类型和可否重试。原始异常栈留在服务端日志。

容易漏的是：把异常原文塞给模型后，模型会顺着错误信息编一段「已经办理成功」。

### 10. 架构演进：如果用户量从 100 万增长到 1000 万，你的架构需要做哪些调整？

**参考答案**

结论：用户数扩大十倍，先按峰值在线和每人每轮的模型调用估容量。先打满的通常是模型配额、检索和会话，扩容时还要保住租户隔离。

入口做按用户、按租户和全局的限额。在线对话、建库、离线评测分集群，建库任务不能占满检索。会话热状态用 Redis 集群；历史消息按用户或时间分表。WebSocket 要有把 token 送到持有连接的节点的通道；SSE 只要把已生成的事件按会话缓冲好，重连可以落到任意节点。

向量库按知识库或租户分片，热库加副本，索引构建离开查询路径。模型前面加一层网关，统一排队、超时、配额和备用模型。Kafka 的分区和 key 在扩容前定好，同一文档的顺序和版本号继续有效。提示词和索引都保留版本，能切回上一版。

成本随 token 增长，涨幅可以明显高于用户数，因为上下文变长、重度用户比例变高。配额和缓存要一起做。

容易漏的是：只加机器，不隔离大租户。一个租户的全量重建会把在线检索拖慢。

### 11. 手写代码：手写一个简单的向量检索函数（如计算余弦相似度）

**参考答案**

结论：余弦相似度是两个向量夹角的余弦，等于点积除以两个模长的乘积，范围在 -1 到 1。任一向量是零向量时没有方向，结果无定义。

文本向量经常落在正区间，计算时仍按 -1 到 1 处理。向量若已经 L2 归一化，余弦等于点积，很多近似索引因此用内积。查询和入库必须使用同一种归一化和同一种度量。

精确扫描 n 条、维度 d 的时间是 O(nd)，排序再加 O(n log n)，额外空间 O(n)。这只说明定义。线上召回用 HNSW、IVF 这类近似索引，再对候选算精确分。

```python
import math

def cosine_similarity(a: list[float], b: list[float]) -> float:
    if len(a) != len(b) or not a:
        raise ValueError("向量必须非空且维度相同")
    dot = norm_a = norm_b = 0.0
    for x, y in zip(a, b):
        dot += x * y
        norm_a += x * x
        norm_b += y * y
    if norm_a == 0.0 or norm_b == 0.0:
        raise ValueError("零向量没有方向，余弦相似度无定义")
    return dot / (math.sqrt(norm_a) * math.sqrt(norm_b))

def search(query: list[float], docs: list[tuple[str, list[float]]], k: int) -> list[tuple[str, float]]:
    scored: list[tuple[str, float]] = []
    for doc_id, vector in docs:
        try:
            score = cosine_similarity(query, vector)
        except ValueError:
            continue
        scored.append((doc_id, score))
    scored.sort(key=lambda item: item[1], reverse=True)
    return scored[: max(k, 0)]
```

容易漏的是：维度不同要直接报错。悄悄截断或补零会算出一个看起来正常、语义已经错了的分数。查询向量本身为零时，调用方应视为请求错误。

### 1. 自我介绍

**答题思路**

三面看判断。架构图不要再讲一遍，一分钟内把一个取舍讲清楚。

1. 一句说明系统和用户任务，点明你负责的层。
2. 讲一个你做过的选择：框架还是自己掌握循环、工作流还是多 Agent、缓存回答还是每次重检索。说清被放弃的方案差在哪。
3. 讲一个重做时会改的点，依据来自故障、评测或成本。没有数据就不要编百分比。
4. 收在岗位要求上：回答要能追溯，工具要能停，坏版本要能切回去。

### 2. 项目复盘：如果让你重做一遍这个项目，你会改进哪些地方？

**答题思路**

选两三个真能落地的改进。全盘否定和「没什么可改」都站不住。

1. 先用一句话重述用户和成功标准，后面的改进都对着这个标准。
2. 从数据、控制、成本里挑有证据的点：坏例有没有评测集，索引能不能回滚，引用能不能回到原文；工具有没有幂等和取消；大模型是不是用在了每一步，送进窗口的块是不是太多。
3. 每个点按「当时为什么这样、后来看到了什么、重做放在哪一层、怎么知道变好」讲。没有的数字不要补。
4. 没做的能力直接说没做，不要把框架的默认功能说成自己的设计。
5. 最后说哪一块会保持不动，以及它已经满足了哪条成功标准。

### 3. 架构权衡：在 Agent 开发中，你更倾向于使用框架（如 LangChain）还是自研底层？为什么？

**参考答案**

结论：执行循环、权限和副作用自己掌握；模型 SDK、向量库客户端和成熟的检索组件继续用库。

框架赢在起步。工具少、场景还在验证时，用 LangChain 一类框架把检索和工具先串起来，同时把超时、幂等和评测写在自己的代码里。工具多、存在写操作、还要审计时，一个默认的 Agent 类会把重试、停止和记忆藏起来，坏回答对不上步骤。

自研的范围是注册表、循环、会话状态和鉴权，这个循环本身并不大。成本在工具治理和评测，不在重写 HTTP 客户端。升级框架前要能说清：默认最大步数、解析失败是否重试、记忆把什么放进了提示。

判断标准很具体。出现坏回答时，能不能指出是检索、提示、工具还是模型，并且能不能单独关掉一个工具。做不到，控制流就还在默认行为里。

容易漏的是：把「自研」说成拒绝一切依赖。面试官要听的是控制流在谁手里。

### 4. 多 Agent 协作：如何设计一个多 Agent 协作系统？如何解决 Agent 之间的通信和冲突？

**参考答案**

结论：按职责拆成少量角色，由一个协调者负责任务边界。通信用结构化消息，冲突靠写入权解决。

协调者拆任务、收结果、决定是否结束。专家只做一类事，例如检索、办理或审核。审核角色不执行写操作。步骤固定的流程用工作流，不必为了每个函数起一个 Agent。

消息带任务 id、发送方、接收方、类型、内容和证据 id。一个请求内可以用内存队列；任务比连接活得久，就落任务表。专家拿到的是自含的子任务，拿到的上下文是证据 id。协调者转发结果，避免每个角色都保存完整聊天。

同一份状态只有协调者能写，专家返回的是提议。两条结果矛盾时，工具观察优先于自由生成；两条工具结果也矛盾，就把两边证据交给审核或用户。跳数、总步数和总 token 有上限。A 把同一任务送回 B、B 再送回 A，按任务和双方去重后停止。

容易漏的是：多角色会增加延迟，也会把一个角色的错误写进另一个角色的上下文。它不自动提高事实正确率。

### 5. 记忆系统：Agent 的长期记忆和短期记忆分别如何实现？如何做记忆的压缩和检索？

**参考答案**

结论：短期记忆是这一次会话的工作集，长期记忆是跨会话、带来源、可删除的事实。压缩只缩短原文，不产生新事实。

短期记忆放当前消息、槽位、未完成计划和滚动摘要，热数据在 Redis，按会话过期。窗口接近预算时，把更早的对话收进摘要，槽位和系统约束保留原文，工具原文改成 id。摘要提示要求只保留已经出现的决定、数字和承诺。

长期记忆写成条目：主体、关系、客体、时间、来源、范围和是否经用户或工具确认。模型推测和已确认事实分开存。检索先按用户和有效期过滤，再按关键词或向量取少数几条，注入前再看它是否仍适用。用户删除、过期、被新事实替代，都要让旧条目退出检索。

容易漏的是：把整段历史对话向量化当长期记忆，检索会召回一句随口的话。写入长期记忆要有确认来源。

### 6. 工具调用：当 Agent 需要调用上百个工具时，如何设计路由和权限控制？

**参考答案**

结论：每轮只把少数候选工具送给模型，而且模型看见它们之前，权限过滤已经完成。

每个工具有名称、描述、参数 schema、风险级别和允许的角色。先按意图或工具描述检索出一小批候选，再去掉当前用户不能用的。高风险工具不进开放检索，只能从固定意图进入。提示里只放这几个 schema。模型返回的名字必须在这批候选里。

服务端再查一次参数。订单号、用户 id 这类资源以登录身份为准，模型声称「这是用户自己的」不算鉴权。写操作、扣费、对外发送走确认或策略引擎。密钥放在适配器里，由服务端发出请求。审计记录谁、调用了什么、参数摘要和结果码。

容易漏的是：路由检索会被一句话带向危险工具。所以危险工具的入口是固定意图，描述检索只覆盖低风险工具。

### 7. 安全合规：Agent 在调用外部 API 时，如何防止敏感信息泄露？

**参考答案**

结论：模型只看见完成任务必需的字段。密钥、内部地址和未授权数据留在服务端，出网前再检查一次。

API 密钥和内部域名由适配器注入。模型可以填业务字段，不能指定任意 URL，主机名必须在白名单里，避免服务端请求伪造。下游只查询单状态时，身份证号和完整手机号不进提示，也不进普通日志。工具返回进上下文之前先挑字段，避免下游多给的敏感字段被写进后续轮次。

检索内容和工具结果都当数据。模型写给外部接口的自由文本，先做敏感检测，再允许发送。日志、链路和排障里的提示按权限查看，手机号、证件和 token 默认打码。缓存 key 和检索过滤都带租户，避免串数据。

容易漏的是：接口本身收得很紧，完整提示却打到了人人能搜的日志里。泄露面往往在排障副本。

### 8. 监控体系：如何设计 Agent 系统的可观测性（Observability）？需要监控哪些关键指标？

**参考答案**

结论：一次回答要能串起检索、每次模型调用和每次工具调用。指标负责发现异常，追踪负责复现模型当时看见了什么。

每次请求一个 trace id，检索、重排、模型、工具各是一段，日志都带这个 id。保存当时的召回 id、提示词版本和模型版本，才能回放。

指标按这几组看。流量看请求量、并发会话和队列深度。延迟看首 token、总时长、检索、模型和工具的尾部。质量看空检索率、拒答率、引用能对上召回的比例、点踩和转人工。稳定看工具错误率、熔断、重试、步数用尽和死循环熔断。成本按租户看 token。建库看解析失败和从上传到可搜的延迟。

告警打在尾延迟、错误率、空检索突增和成本突增上。阈值按这个系统的常态来定。

容易漏的是：只有 CPU 和总 QPS 时，质量变差而服务仍「健康」。质量代理指标要和延迟放在一起看。

### 9. 技术选型：面对一个新技术和一个稳定的旧技术，你会如何做技术选型？

**参考答案**

结论：旧技术已经满足约束就继续用。新技术只替换一个能量化的痛点，并且保留退回旧路径的办法。

先写下延迟、正确率、成本、能否私有化、许可证和团队能不能维护。差距可以接受就不动。要换时，写出旧技术哪一个指标不够，用自己的坏例集做对照，小流量看质量、尾延迟和失败时怎么降级。Agent 框架还要看接口稳不稳定，升级后默认重试和记忆有没有变。

数据格式避免绑死在新系统的私有能力上。索引版本、提示词版本和模型版本都能切回上一版。对照跑不过，就停在旧路径上。

容易漏的是：用演示里的效果做决定，没有把自己的坏例放进同一套评测。

### 10. 业务理解：你认为 Agent 技术在科大讯飞的业务中最大的应用场景是什么？

**参考答案**

结论：最大的场景是教育里的个性化辅导和口语陪练。任务多轮、有标准、能用学习结果闭环。

讯飞公开的业务里，教育和学习机、课堂、口语评测连在一起，办公有转写和纪要，医疗有辅诊，汽车有座舱语音，开放平台提供语音和星火一类模型。教育同时具备入口、语音和学习过程。辅导要出题、批改、讲解、按错题再练，这些是工具调用；讲解又要落到教材和知识点，这是带引用的检索。做题结果和口语评测能用来看效果。

这个场景的约束是内容安全、未成年人和「模型发挥不能当成标准答案」。答的时候把这三条一起说。

医疗辅诊的价值高，结论要留给医生，责任边界更重。办公里的纪要、待办和企业知识库问答确定性强，适合做，多轮决策和学习过程相比通常更浅。所以把教育作为主答案，医疗和办公作为边界。

容易漏的是：只答「智能客服」或「聊天机器人」。客服没有用上讯飞已经有的学习数据和评测闭环。

### 11. 手写代码：手写一个简单的工具调用解析器（解析 LLM 返回的 JSON 并执行对应函数）

**参考答案**

结论：只执行注册表里的函数。先取出第一个完整 JSON 对象，校验名字和参数，通过后再调用。模型输出当数据，不能当代码。

模型经常在 JSON 前后加解释，参数字段有时又是一层 JSON 字符串。解析器接受这两种形式。尾逗号、注释和单引号都不是合法 JSON，失败就把错误类型交回模型修改。一次返回多个调用时，有副作用的按顺序执行，只读的可以并行，全部观察写回后再进入下一步。下面的代码处理单个对象。

扫描和解析相对文本长度 n 是 O(n)，空间 O(n)。函数本身的耗时另计。

```python
import json
from collections.abc import Callable
from typing import Any

class ToolCallError(Exception):
    pass

def first_json_object(text: str) -> str:
    start = text.find("{")
    if start < 0:
        raise ToolCallError("找不到 JSON 对象")
    depth = 0
    in_string = False
    escaped = False
    for index in range(start, len(text)):
        char = text[index]
        if in_string:
            if escaped:
                escaped = False
            elif char == "\\":
                escaped = True
            elif char == '"':
                in_string = False
            continue
        if char == '"':
            in_string = True
        elif char == "{":
            depth += 1
        elif char == "}":
            depth -= 1
            if depth == 0:
                return text[start : index + 1]
    raise ToolCallError("JSON 对象不完整")

def run_tool(raw: str, tools: dict[str, Callable[[dict], Any]]) -> Any:
    try:
        data = json.loads(first_json_object(raw))
    except json.JSONDecodeError as exc:
        raise ToolCallError("JSON 无法解析") from exc
    if not isinstance(data, dict):
        raise ToolCallError("工具调用必须是对象")
    name = data.get("name")
    if not isinstance(name, str) or name not in tools:
        raise ToolCallError("工具未注册")
    arguments = data.get("arguments", {})
    if isinstance(arguments, str):
        try:
            arguments = json.loads(arguments)
        except json.JSONDecodeError as exc:
            raise ToolCallError("arguments 不是合法 JSON") from exc
    if not isinstance(arguments, dict):
        raise ToolCallError("arguments 必须是对象")
    return tools[name](arguments)
```

容易漏的是：解析成功还不等于可以执行。必填字段、类型、权限和超时都在调用前处理。用 `eval` 执行模型输出，等于把代码执行权交了出去。
