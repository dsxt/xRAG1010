# 美团 AI Agent 三轮技术面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

面完了，来唠两句。美团这面试官水平还是在线的，问得挺深，全往实际场景和系统设计上怼。一面基础打得牢，RAG、记忆、ReAct 这些核心概念掰开揉碎了问。二面那个旅游规划 Agent 的场景题有点意思，得把工具调用链和逻辑理得特别清楚。三面直接让你设计平台级框架，格局打开了，考察的是顶层设计和解决复杂问题的思路，没点真实实战经验还真容易懵。整体感觉他们对候选人的工程落地能力和技术视野要求挺高的，不是光会调 API 就行。手撕算法倒是常规操作，LFU 和字符串拼接那题都算经典。HR 面就比较常规，看看你的动机和软实力。面下来感觉不错，是个能搞事情的地方。

## 一面

### 1. 请简单做一下自我介绍

**答题思路**

控制在 1 到 2 分钟，按「我是谁 → 做过什么 → 为什么和这个岗位有关」讲完就停。

1. 一句话交代年限和方向，点出你真实写过的检索、工具调用或对话链路。
2. 只展开一个最相关的项目：用户要完成什么事、你负责哪一段、结果用你拿得出来的证据。没有数字就讲评测集或坏例，不要临时编指标。
3. 收到这个岗位上：外卖、到店这类场景会真下单，工具要有超时、幂等和确认。把话停在你准备被追问的那个项目上。

### 2. 介绍一下你简历上最有挑战的、与智能体相关的项目

**答题思路**

面试官要区分「做过一条能完成任务的链路」和「只调过聊天接口」。用真实项目套这个顺序：

1. 一句话说明用户是谁、任务是什么、为什么单次问答不够。
2. 按请求路径讲：入口、意图和槽位、检索或工具、校验、回复。每一步说清输入和输出。
3. 划清你写的部分。团队项目里说明你负责的是编排、检索、工具网关还是评测。
4. 准备一个难点，按「现象 → 怎么定位 → 改了什么 → 怎么验证」讲。常见的真问题有：检索命中了但生成改写了事实、工具超时被重复执行、多轮把槽位盖错。
5. 主动留下三个追问的口子：状态存在哪、失败时用户看到什么、金额或订单号从哪个接口来。

简历里没有智能体项目时，讲最接近的检索、规则或工作流，并说明它还缺规划、工具观察和任务是否完成的判定。

### 3. 什么是 AI Agent？它与传统 ChatBot/对话系统的主要区别是什么？

**参考答案**

AI Agent 围绕目标持续决策：维护任务状态，选择工具，根据观察决定下一步，直到任务完成或明确失败。传统 ChatBot 优化的是下一句回复。

差别在控制流和状态。Agent 按思考、行动、观察循环，检索为空或接口报错时可以改计划；槽位、计划和工具结果单独保存。它还有完成条件、步数上限，下单这类动作要经过确认。ChatBot 即使接了检索，通常也是一次生成。

Function Calling 接上状态、真实观察和终止条件，才形成 Agent。

### 4. 在构建一个任务导向型 AI Agent 时，核心模块通常包括哪些？请简述其工作流程

**参考答案**

核心模块是输入理解、规划、记忆、工具执行、策略确认和回复生成。记忆里既有当前任务的槽位，也有跨会话的用户事实。

流程是：抽出目标和约束，读记忆补全上下文，规划下一步，按契约校验参数并执行工具，把观察写回状态，再判断完成、失败或向用户澄清，最后生成回复。有副作用的步骤先进入确认，确认后才执行。

关键路径可以把循环收成显式状态机，模型负责抽槽和选分支。步数、超时和重复调用要有上限。

### 5. RAG 的原理是什么？它如何解决大模型幻觉和知识更新问题？

**参考答案**

RAG 在生成前从外部知识库检索相关片段，把证据放进上下文，再让模型据此回答。

对幻觉：回答被约束在可引用的证据上；检索不到就拒答或澄清，不靠参数记忆编造价格、规则和订单事实。对知识更新：改文档并重建索引即可，不必为了菜单或政策变化重训模型。索引有延迟，权限和版本要随文档一起变。

检索错了、片段被截断或证据互相矛盾时，模型仍可能编。RAG 降低的是无依据回答，要配合引用和拒答。

### 6. 详细描述一下 RAG 的完整流程，从查询理解、检索到生成

**参考答案**

多轮对话先做指代消解和查询改写，把「它」「上次那家」补成可以独立检索的问句，并判断走知识问答、工具还是闲聊。

检索用向量加关键词做混合召回，同时按业务线、权限和时效过滤。候选交给交叉编码器重排，取少量片段，同一文档的相邻块合并、按来源去重。上下文里保留出处，并控制长度。

生成时只依据这些证据回答；证据冲突就说明冲突，没有证据就拒答。回答附上来源。菜名、订单号这类精确词要留在检索词里，不能只靠改写后的语义查询。

### 7. 在 RAG 中，如何对文档进行高效的索引和检索？（可涉及向量数据库、检索器选型、chunk 策略等）

**参考答案**

离线按标题等结构切块，块间留少量重叠，避免步骤被切断。检索可以用小块保证命中，生成时带回所属段落。表格和 FAQ 单独切。每块带上文档编号、权限、更新时间，用同一套嵌入模型写入向量库，并另建关键词倒排。换嵌入模型就要重建索引。

在线检索分成两路：向量侧用 HNSW 一类近似最近邻，关键词侧用 BM25，两路名次用倒数排名融合合并。权限和时间过滤放进检索条件，被排除的文档就不会占满召回名额。文档下线时同步删除向量。

向量负责改写过的说法，关键词负责菜名、门店名和错误码。两边都要有。

### 8. 什么是「意图识别」？在 Agent 系统中，它通常位于什么环节？实现意图识别有哪些常见方法？

**参考答案**

意图识别判断用户要办的事，例如查订单、退款、点餐或闲聊，并带出槽位。它位于输入理解之后、规划和工具选择之前，用来路由；也可以作为规划的第一步，直接输出意图和槽位。

常见做法有规则、分类模型、大模型，以及混合路由：意图集合稳定且置信度高时走小模型，说不清时再升级或向用户澄清。多件事要输出意图列表。「再加两碗米饭」多半仍是点餐里的槽位；「草莓不甜，牛奶盒也瘪了」才是两个售后意图。

### 9. Agent 中的「记忆」（Memory）通常分为哪些类型（如短期记忆、长期记忆）？它们是如何被存储、管理和调用的？

**参考答案**

短期记忆是当前会话的原文、计划、工具结果和槽位，放在按会话编号读取的会话存储里，超长就滚动摘要。长期记忆是跨会话仍有用的事实：偏好、默认地址等结构化字段放画像表，带时间、来源和置信度；不好结构化的再写入向量库，并且按用户过滤。

每轮先读画像，再用当前问题检索少量相关事实。写入前去重，设置过期，并允许用户删除。冲突时以更新的明确说法为准，旧值留审计。用户当次说的话和系统推断要分开存。

对话状态管这一单的槽位，长期记忆不替代它。工具返回的原文默认不写入长期记忆。

### 10. 解释一下 ReAct（Reasoning and Acting）框架的思想。它如何让 Agent 具备更强的推理和工具调用能力？

**参考答案**

ReAct 把推理和行动交错进行。模型每步先写出为什么这样做，再给出工具名和参数；环境执行后返回观察，模型据此决定继续、改计划或给出最终答案。

相对一次把计划全生成出来，它用的是工具的真实返回：检索为空就换查询，参数报错就修改后再调用。工具能力来自三件事：上下文里有工具说明和参数契约，动作能被解析，观察会写回上下文。步数和连续失败要有上限。

内部轨迹和给用户的回复要分开。流式输出时不要把未校验的思考过程直接甩给用户，也不要把没执行的工具当成已经成功。

### 11. 在实现一个支持多轮复杂对话的 Agent 时，如何设计和维护对话状态（Dialog State）？

**参考答案**

对话状态用结构化对象，不靠把历史消息重写一遍来代替。字段包括意图列表、带来源的槽位、待澄清问题、已调用工具及结果引用、当前阶段和版本号。

每轮只根据新证据做增量更新。用户改口就覆盖对应槽位，并记下是用户说的还是系统推断的。指代先消解，再写入状态。换话题时把当前任务挂起，而不是清掉。同一会话用版本号或锁，避免并发消息互相覆盖。

下单、赔付这类阶段必须先把槽位回显给用户。模型可以提议状态变更，真正落库的是校验后的结构。

### 12. 如何评估一个 AI Agent 的性能好坏？有哪些可量化的指标？

**参考答案**

看任务是否做成，也看过程和代价。可量化的有任务完成率、工具选择和参数准确率、非法调用率、检索命中和回答是否被证据支持、步数、端到端时延、token 和单次成本，以及转人工率、确认后的撤销或投诉。

评测用固定集合，覆盖缺槽、多意图和工具失败。有副作用的任务断言最终状态和关键工具有没有被调用。线上再抽样人工看，并把坏例补进集合。

「已完成」要由订单或工单状态判定。模型自己说完成，不能算完成。

### 13. 场景题：设计一个美团外卖的订餐助手 Agent，用户说「帮我点一份上次那家还不错的水煮鱼，再加两碗米饭」，这个 Agent 应该如何拆解任务、调用工具并完成交互？

**参考答案**

这是一次复购点餐，有两个商品槽位：水煮鱼一份、米饭两碗。下单有副作用，确认前不能提交。

默认地址查询和历史订单查询可以并行。历史里找含这道菜、且评价较好或无差评的最近订单，得到门店和商品；命中多家就问用户，不让模型挑一家。再查营业和可售，确认辣度等规格，以及米饭是不是该店在售商品。然后做价格和配送预览。

回复回显店名、菜品、数量、地址、价格和预计送达，用户确认后再提交，请求带幂等键。门店打烊、商品下架或地址有多个时，只追问缺的那一项。

「还不错」用历史评价或复购来落地。模型记住的店名不能当作订单依据。

## 二面

### 1. 请再次进行自我介绍，并深入介绍一个能体现你 Agent 系统设计能力的项目

**答题思路**

身份用半分钟带过，把时间留给系统设计。仍用真实项目，重点换成「为什么这样拆」。

1. 用约束开场：任务有没有副作用、能不能失败重试、用户等待上限大概在什么量级。数字只用你知道的。
2. 讲一次请求经过哪些模块，每个模块拥有什么数据。说明规划是自由循环，还是被状态机卡住。
3. 讲一个你做过的取舍，例如写操作为什么不让模型直接调用、检索为什么要关键词和向量一起用。
4. 说明你负责的边界，以及上线后用什么信号判断这套设计成立：任务完成、错误率、时延或人工抽检。
5. 收在一个你希望面试官追问的点上，例如状态存在哪、工具失败如何返回给规划。

### 2. 在刚才提到的项目中，你遇到了最大的技术挑战是什么？是如何解决的？

**答题思路**

只讲一个挑战，按四拍说完：现象、定位、改动、验证。

1. 现象要具体到某类请求，例如事实被改写、写接口被调用两次、多轮之后槽位错了。
2. 定位时说明你看的是轨迹、工具入参还是检索片段，排除了哪一个看起来像、其实不是的原因。
3. 改动讲一个主措施。若还有备选方案，说明你没选它的原因，例如成本、延迟或业务不能接受误下单。
4. 验证用同一批坏例或固定评测集，说明回归看的是状态和工具，不看回复好不好听。

准备被追问：怎么确认没有把另一类请求修坏，失败时用户看到什么。

### 3. 详细描述你设计的 Agent 系统架构。各个服务/模块是如何通信和协作的？

**答题思路**

按你的真实系统讲，名字用项目里的名字。下面这些通信关系要能对上，没有的模块就明确说当时没拆。

1. 画出一条请求：接入层到 Agent 运行时，再到模型网关、工具网关和业务接口。检索是运行时同步调用的独立能力。
2. 模型和当前步骤依赖的工具走同步调用，因为下一步要等观察。互不依赖的只读工具由运行时并行发出。流式只用于最终回复或需要尽早展示的文本。
3. 会话状态放在带版本的存储里，同一会话加锁或用版本校验，避免两轮消息互盖。轨迹异步落日志，不堵主链路。
4. 写操作带幂等键，经过确认才发出。出票、退款结果这类慢通知走消息，运行时持久化等待点，回来再恢复。
5. 最后说你故意不拆的部分。步骤少的时候，把规划和状态放在一个运行时里，比拆一堆自由 Agent 更容易排障。

### 4. 在 RAG 系统中，如果检索返回的相关文档片段（chunk）过多或质量参差不齐，如何对它们进行重排序（Re-rank）或信息融合，以提高最终回答质量？

**参考答案**

召回可以多取一些，重排只处理这几十个候选。用交叉编码器对「查询，片段」打分，取得分最高的少量片段。它比双编码器慢，所以不拿去扫全库。

融合时合并同一文档的相邻块，按文档去重。片段互相矛盾时保留双方并带上时间或来源，交给生成阶段说明冲突，不在排序时悄悄丢掉一方。仍然超长，就压成带引用的要点再生成。业务上可对时效做硬过滤，语义次序仍以重排分为主。

重排救不了召回。正确片段不在候选里，后面的融合没有材料。

### 5. 如何让 Agent 具备使用外部工具（API、函数）的能力？请描述完整的工具调用链路，包括工具描述、模型选择、参数提取、结果处理。

**参考答案**

每个工具提供名称、用途、参数的 JSON Schema、只读还是写入、超时和错误码。工具太多时，先按意图召回一个子集再给模型，否则选择变差，上下文也被说明文字占满。

模型在这一步输出工具调用或最终回复。应用先用 Schema 校验类型、必填和枚举；校验失败把错误交回模型改，连续失败再问用户。通过后才由网关执行。网关负责身份、超时和审计。只读且幂等的调用才按策略重试。

结果裁剪后作为观察写回。金额、订单号以工具原文为准，不让模型补未返回的字段。写入类先形成草稿，用户确认后再执行，并带幂等键。

### 6. 在多工具 Agent 场景下，如何让模型自主规划工具调用顺序（Planning）？有哪些技术方案？

**参考答案**

有四种常见做法，按任务风险选用。

ReAct 每步看过观察再决定下一个工具，适合分支多、下一步依赖返回值的任务。先规划再执行会先产出步骤列表，某步失败再局部重规划，适合步骤相对清楚的流程。模型若产出带依赖的步骤，没有依赖的只读工具可以并行。下单、赔付则用显式状态机，模型填槽和选分支，不能自己发明下一步写操作。

无论哪一种，都要有最大步数、重复调用检测和人工接手。咨询可以用更自主的规划，支付和赔付用受约束的规划。

### 7. Agent 的「记忆」如果全部存在向量数据库中，在长对话中可能会遇到效率问题。如何设计记忆的存储、检索和压缩机制？

**参考答案**

每句对话都做向量，长会话会变慢，也会检索到过期句子。记忆分成三层。

工作记忆只留当前槽位、最近几轮原文和未完成步骤，按会话编号直接读取。会话变长再做滚动摘要，但订单号、金额、地址和用户明确改过的槽位留在结构化字段里。摘要按窗口或轮次触发，不必每说一句都调一次摘要模型。

长期记忆只保存以后还用得上的事实。结构化画像按用户主键能直接读；非结构化事实才嵌入，并且必须带用户过滤，限制条数。冲突时以更新的明确说法为准。检索顺序是先画像、后语义。写入去重，并设过期和删除。

### 8. 场景题：设计一个旅游规划 Agent。用户输入「我想下周末去杭州玩两天，预算 5000，喜欢自然风光和美食」。请描述 Agent 需要调用哪些工具（如搜索、日历、预订 API），以及大致的推理和行动步骤。

**参考答案**

工具包括日历、天气、景点搜索、路线、餐厅搜索，以及酒店、交通和门票的价格或库存。预算汇总放在内部，不必假装成一个外部接口。

先用日历把「下周末」落成具体日期，拿不准就确认。人数没说时，方案按一人估算并写明假设。再查天气和自然类景点，按区域排两天，用路线避开来回折返，餐厅跟着区域选。然后查价格，把交通、住宿、餐饮、门票加总；超出 5000 就替换项目，并说明动了哪一项偏好。

库存和预订只在用户确认某一项之后调用。没有真实库存接口时，输出的是可执行清单，不说已经订好。难点是相对日期、总账和多目标取舍，这三处都要展示依据。

### 9. 如何保证 Agent 行为的安全性和可控性？例如防止工具调用越权、生成有害内容等。

**参考答案**

身份以会话为准，模型填进参数的用户编号不能直接用。每个工具在网关上按 Agent、终端用户和资源归属鉴权，例如只能查这个用户自己的订单。提示词不能扩大权限。

赔付、支付、改地址设额度和二次确认。工具结果和用户输入都当不可信数据，其中的指令不能变成新的系统指令。输入输出再做内容过滤，这是补充，权限仍在网关。

每次调用留审计。步数、费用和重复调用设熔断，触发后澄清或转人工。高风险写操作默认不因为「模型判断紧急」就跳过确认。

### 10. Agent 系统的线上监控和运维你会关注哪些核心指标？（如耗时、Token 消耗、工具调用成功率、任务完成率）

**参考答案**

分五组看。效果看任务完成率、转人工率、确认后的撤销和投诉。工具看成功率、超时、业务错误码和重试次数。性能看端到端时延，以及模型、检索、工具各自的时延。成本看 token 和单次任务费用。安全看越权拒绝、确认放弃和循环熔断。

这些指标按 Agent、工具和业务线拆开。轨迹脱敏保存，用来回放失败。告警绑成功率和分阶段时延；请求量只说明流量。任务完成与否由业务状态判定，不由模型的结束语判定。

### 12. 谈谈你对当前 AI Agent 领域技术发展趋势的看法。未来 1-2 年，你认为哪些方向会有突破？

### 13. 你如何看待 AI 编程助手（如 GitHub Copilot、Cursor）对你开发工作的影响？你自己在项目中会使用它们吗，如何有效利用？

可以让它起草评测样本和适配代码，再逐项核对字段是否真的存在于接口里。它编出的调用和漏掉的失败分支，靠测试和评审接住。

### 1. 请做一下自我介绍，并概述你在 AI Agent 或相关领域的技术积累和认知

**答题思路**

1. 用一两句说明你做过单点 Agent、检索还是工具链路，范围用真实项目。

### 2. 假设要你从零开始，为美团设计一个平台级的 AI Agent 开发框架，以支持各业务线（外卖、到店、酒旅等）快速构建自己的智能体。你会如何设计这个框架的核心架构和关键组件？

**参考答案**

框架分成运行时、能力接入和治理，业务线只填差异。

运行时负责会话、状态机、规划循环、人工确认和中断恢复。模型统一走网关，处理路由、超时、降级和配额。工具以版本化契约注册，包括 JSON Schema、读写类型、超时、幂等键和错误码，由网关鉴权并调度。知识和画像按业务线隔离，检索带权限过滤。策略中心卡住赔付、支付等写操作。各业务用自己的任务集做回归，轨迹、时延和成本进同一套观测。

难点是共用和差异的边界。循环、权限、幂等和回放做成框架，外卖和酒旅才能共用工具和评测。提示词、工具组合和流程节点留给业务。把具体对话流程写死，业务会绕开框架。

### 3. 在这个平台框架中，如何实现工具（能力）的标准化接入和统一调度？如何让不同业务方的 Agent 能安全、高效地共享和互调工具？

**参考答案**

工具接入先过契约：名称、描述、JSON Schema、只读或写入、超时、幂等键、资源范围和错误码。契约测试不过不能上线。描述层可以用统一协议，鉴权和审计仍走内部网关。

Agent 不直连业务接口。网关核对调用方、终端用户和资源归属，并做限流、超时、结果裁剪和审计。跨业务共享靠授权订阅，每次调用带上用户委托。服务账号不能绕过用户权限。跨业务的写入默认要用户确认，或者不开放。调用方锁定契约的主版本。

只读且无依赖的工具允许并行。每个工具声明代价，规划器据此避免无界调用。热点读可以短缓存，写不缓存。

### 4. Agent 系统的性能瓶颈可能出现在哪里？（如模型推理延迟、检索延迟、工具调用网络延迟）有哪些系统性的优化思路？

**参考答案**

常见瓶颈有四类。多步模型串行，上下文变长后预填充变慢，工具说明和历史把提示撑大。每一步都检索，或过滤放在召回之后。工具串行往返，超时重试把延迟放大。同一会话并发、没有步数上限，也会把尾延迟打高。

先按阶段打点，再动占比最高的一段。状态机能决定的步骤不调用模型，简单路由用小模型。稳定前缀做缓存，工具结果裁剪后再回填。无依赖的只读工具并行。热门检索和热点读加缓存，过滤条件下推。工具超时和熔断直接失败返回；步数或费用到顶后改为澄清或转人工。改索引前先确认检索时延在总时延里占得住。

### 5. 如何管理和评估平台上众多业务方开发的 Agent 的质量和效果？如何设计一套自动化评测体系？

**参考答案**

每个 Agent 维护自己的任务集，覆盖主路径、缺槽、多意图、工具失败、越权和知识过期。自动跑轨迹时，断言最终业务状态和关键工具是否调用，不只比较回复文本。指标包括任务成功率、工具精确率和召回、回答是否被证据支持、违规率、时延和成本。

提示词、模型、工具版本和知识库变更都触发回归，低于约定阈值就不能发布。线上看抽样人工评、投诉、转人工和撤销，坏轨迹回灌到任务集。

### 6. 场景题：现在有一个「美团买菜智能客服 Agent」，用户反馈「我买的草莓不甜，而且送来的牛奶盒子是瘪的」。这个 Agent 需要处理复杂的多意图投诉（商品质量 + 物流损伤），并且可能需要调用订单查询、售后政策、赔付流程等多个工具。请设计它的处理逻辑和状态机。

### 12. 手写算法：一个字符串数组 ["hello", "world", "hello world", "hello world!"]，请找出其中最长的、可以由数组中其他字符串拼接而成的字符串。如果不存在则返回空字符串。

**参考答案**

要找的是数组里最长的那个字符串，并且它能由数组中的其他字符串至少拼接两段得到。词可以在不同段里重复使用，但不能只拿候选词自身当作唯一一段。不存在则返回 `""`。等长时保留原数组里先出现的一条。

给定的四个字符串里没有答案。`"hello"` 和 `"world"` 无法再拆。「hello」加「world」得到的是 `helloworld`，对不上带空格的 `"hello world"`。`"hello world!"` 用掉 `"hello world"` 之后剩下 `"!"`，数组里没有能接上的词。所以返回空字符串。若数组里还有 `"helloworld"`，它由 `"hello"` 和 `"world"` 组成，应当返回它。

做法是把全部字符串放进集合。对每个比当前答案更长的候选词做单词拆分：`dp[i]` 表示前 `i` 个字符能否拆成集合里的词。枚举切点时跳过「整段等于自身」这一刀，因此至少两段，也避免把重复出现的同一个字符串当成拼接结果。

设词数为 `n`、最大长度为 `L`。切点是 `O(n L^2)`。这段 Python 每次切片和哈希还要扫描字符，实际大约 `O(n L^3)`。若用前缀哈希把判断降到均摊常数时间，就是 `O(n L^2)`。空间是词集合，再加上 `O(L)` 的 `dp`。

```python
def longest_concatenated(words: list[str]) -> str:
    pool = set(words)
    best = ""
    for word in words:
        n = len(word)
        if n <= len(best):
            continue
        dp = [False] * (n + 1)
        dp[0] = True
        for i in range(1, n + 1):
            for j in range(i):
                if not dp[j]:
                    continue
                if j == 0 and i == n:
                    continue
                if word[j:i] in pool:
                    dp[i] = True
                    break
        if dp[n]:
            best = word
    return best
```

2. 你的关键动作只讲一两下，例如把失败链路分阶段、补上确认、做成可回归的检查。
3. 结果用前后对比。没有权威数字，就讲坏例是否消失、排障是否变短、谁开始按这套方式做事。
4. 为什么有成就感：你留下了可重复的做法，而不是一次好运。用一句说清你从中确认了自己想继续做的工作类型。

避免讲团队奖项，却说不出自己的决定。

### 3. 在以往团队合作中，遇到过最大的挑战是什么？你是如何应对和解决的？

**答题思路**

选协作问题，不选纯技术题。技术深挖前面已经问过。

1. 说明目标原本是什么，卡点是信息、优先级还是责任边界。
2. 你做的动作要可见：把分歧写成共同的失败样本、约定决策人、把接口和截止日期说死。
3. 结果说明事情有没有向前，以及关系有没有留下可复用的协作方式。
4. 收在你以后会提前做的一件事上。对同事的评价只描述行为，不贴动机。

没有戏剧性冲突时，讲一次跨角色对齐需求或排期的经历即可。

### 4. 你为什么选择美团？对 AI Agent 在美团业务中的应用有什么期待？

**答题思路**

原因分成业务和你自己两半，业务用公开事实，个人动机用真话。

1. 业务：外卖、到店、买菜、酒旅都有高频、可验证的任务，工具连着库存、订单和售后，做完没有做成能被业务状态证明。
2. 期待讲一个具体问题，例如多业务线共用运行时和工具权限之后，各业务仍能保持自己的流程和评测。不要空说「赋能所有场景」。
3. 个人：这个问题和你上一问留下的方向一致，说明你想在有副作用的 Agent 上做深，而不是只换一家公司。
4. 若你还有真实的使用体验或行业判断，放在最后一句。没有就停在工程问题，不编消费故事。

### 5. 你对自己未来的职业发展有什么规划？希望 3 年后成为什么样的人？

**答题思路**

用能力描述三年后的状态，不报一个你还没拿到的职级，也不把公司名写进规划。

1. 近一年：独立把一条有副作用的 Agent 链路做稳，包括工具契约、失败恢复和评测门禁。
2. 三年：能为一组业务定运行时和评测标准，判断哪些步骤不该交给模型，并带同事把新场景接进来。
3. 说明这个路径为什么和美团的多业务线有关。对方若讲团队实际需要，把你的规划对齐到那个范围，保留你仍想亲手做技术决定。
4. 准备一句你不想变成什么样：只做演示、不看线上失败的人。用你的说法讲。

### 6. 你如何看待工作与生活的平衡？

**答题思路**

直接给出你的真实节奏，再说明交付怎么保证。

1. 承认上线和事故会有峰值，平时你如何区分值班和深度工作。用自己的例子，例如发布周和普通周的差别。
2. 讲一个减少无效加班的做法：固定评测、把失败按阶段打点、把需求范围说清。这是工程手段，不是态度表态。
3. 说明你的底线，例如长期不可预期的加班会降低排障质量。表达时对着事情，不对着某一家前公司。
4. 若面试官描述团队的实际节奏，按真实情况回应你能接受的部分和需要提前知道的部分。

### 7. 你当前的薪资构成和期望薪资是多少？

**答题思路**

复习时不要写死一个数字。面试时只用自己的真实包，并先把口径对齐。

1. 先问职级范围，以及对方说的包里有没有月薪、年终、股票和签字费。确认对方要的是现金还是总包。
2. 当前构成按同样的口径说明。股票说清是总价值还是你自己估计的年化，不确定就标明是估计。
3. 期望给一个区间，并说明它对应总包还是现金。区间的理由是职责和你现有的包，不现场编一个整数。
4. 对方暂时给不了带宽时，约定信息补齐后再收窄区间。不要为了让谈话结束而改口一个没有依据的数。

### 8. 你还有什么问题想问我的吗？

**答题思路**

准备三个问题，按面试官的角色选两个问。问完听回答，再追一句，不要把问题清单念完。

1. 问业务负责人：这个岗位前六个月做成的标志是什么，最先接入的是哪条有副作用的业务。
2. 问技术负责人：Agent 线上出错时谁负责，提示词、模型和工具变更有没有评测门禁。
3. 问 HR：团队现在的节奏、职级对应的责任范围，以及这个机会更缺单点交付还是平台能力。

薪资和假期若上一问还没对齐，可以补问口径。已经谈完就换上面的问题。避免只问远程和加班。
