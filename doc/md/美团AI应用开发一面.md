### 1. 自我介绍

**答题思路**

用一两分钟，按「现在做什么、一件能展开的事、和岗位的关系」讲完。

1. 从最近一段工作说起：Java 后端、业务用一句话带过。年限用真实数字。公司、职级、薪资不在这题里展开。
2. 只留一个你写过、被追问也能画出来的系统：谁在用，你负责接口、数据还是任务，结果交付到哪。
3. 埋一个经得起追问的点，例如一次请求的状态怎么变、失败怎么补。项目名用简历上的原话。
4. 这场后面会问网络、JVM 和 SQL，也会问大模型怎么用。自我介绍里用一句话点出你真正接过或练过的模型调用，细节留给下一题。
5. 停在这个点上。教育经历和离职原因等被问到再答。

### 2. AI 大模型学习与实践

**答题思路**

把「学过」和「做过」分开，按时间顺序讲，只讲你能复述调用过程的那一段。

1. 先说目标：你要解决的是接入一个生成接口、把文档检索进上下文，还是让模型调工具。名词清单不要代替这条目标。
2. 学习路径按你的真实顺序：官方接口说明、自己发通一次请求、再看超时、流式和错误码。没读过的论文不要报。
3. 实践停在你做到的层：本地脚本、业务里的一个接口，或已经给别人用。停在哪一层就说哪一层。
4. 准备三个能画出来的事实：请求里上下文长什么样、返回你怎么解析、失败时是重试、降级还是交给人。
5. 效果只用你有的样例。没有准确率和时延就讲你怎么判断这条答案能不能用，不临时补百分比。

### 3. 能否具体举一个你在项目中使用 AI 大模型的场景？比如它是如何帮助你解决某个具体问题的？

**答题思路**

只讲一个场景。下一句就要能说出输入、输出和失败时怎么办。

1. 用一句话框住：谁在什么步骤卡住，原来靠人翻、靠规则或靠搜索，哪一类情况盖不住。
2. 说明模型坐在链路的哪一格。常见是同步接口：上游把上下文组装好，模型返回文本，你的服务做校验再落库或展示。不要把整个系统说成「就是一个大模型」。
3. 按一次调用讲数据：系统提示和用户内容从哪来，有没有检索片段，结果要不要变成固定字段。上下文是你拼的，还是直接把原始库丢进去，这两件事要分开。
4. 说明你怎么确认它解决了问题：一组固定输入，期望输出长什么样，哪类错例不能上线。超时、输出不是约定格式、内容越界时，分别回到模板、拒绝还是人工。
5. 指标用你能量到的。没有就停在样例和回退。不编调用量和准确率。

### 4. IPv4 和 IPv6 的区别

**参考答案**

IPv6 用 128 位地址，并改了首部、分片和地址解析，用来应对 IPv4 的 32 位地址耗尽。

IPv4 写成点分十进制，公网地址不够时常用 NAT。IPv6 写成八组十六进制，每个接口都有 `fe80::/10` 链路本地地址，站点内部用 ULA（`fc00::/7`）。IPv6 没有广播，通知一批主机用组播，同一地址也可以做任播。

IPv4 首部 20 到 60 字节，带首部校验和，中间路由器可以分片。IPv6 基本首部固定 40 字节，选项放进扩展首部，不再计算首部校验和。只有源主机按路径 MTU 分片；路由器发现报文过大就丢弃，并回 ICMPv6 Packet Too Big。

IPv4 用 ARP 做链路地址解析，地址多由 DHCP 分配。IPv6 用 ICMPv6 邻居发现完成解析、重复地址检测和前缀通告，主机可以按前缀用 SLAAC 生成地址，DNS 仍常靠 DHCPv6 或路由器通告里的 RDNSS。IPv6 上 UDP 校验和是强制的。规范把 IPsec 列为应支持的能力，报文不会因此自动加密。

### 5. IPv4 到 IPv6 的过渡策略有哪些？

**参考答案**

迁移有三条路，能双栈就双栈。

双栈是主干。主机和网络同时跑 IPv4 和 IPv6，应用按 Happy Eyeballs 优先连 IPv6，短时间连不上再回退 IPv4。用户无感。地址规划、路由、防火墙和监控要各维护一套。

隧道用来穿过还没升级的网段。IPv6 孤岛之间可以把 IPv6 封装进 IPv4，例如手工配置的 6in4，或运营商自己发放前缀的 6rd。接入网已经是 IPv6、用户侧还有 IPv4 应用时，可以用 DS-Lite 把 IPv4 封装进 IPv6，送到运营商的 AFTR 解封装，并在那里复用 IPv4 地址。隧道多一层封装，MTU 变小，中继故障要单独告警。

翻译用在一侧短期内不能双栈。边界把一种协议的报文转换成另一种，典型是只剩 IPv4 的服务要给 IPv6 客户端用。翻译会改写地址，排障时要能对照转换前后的地址。它补的是连通，不代替把服务做成双栈。

### 6. 有哪些技术手段可以实现 IPv4 和 IPv6 的互通？

**参考答案**

先看流量从哪一族到哪一族，再选直连、封装、报头翻译或应用层代理。

两端都是双栈时，应用按目标地址族直接连接，中间不改报文。这是最稳的互通。

封装保留内层报文。6in4 和 6rd 把 IPv6 放进 IPv4。DS-Lite、MAP-E 把 IPv4 放进 IPv6，送到运营商侧再解封装。隧道两端要成对，路径 MTU 要减去外层首部。

报头翻译用在不能把另一族原样送到对端的时候。NAT64 配 DNS64：DNS 把 A 记录合成 AAAA，常用前缀是 `64:ff9b::/96`，NAT64 网关再把 IPv6 报文改写成 IPv4。这条路径覆盖的是 IPv6 客户端访问 IPv4 服务。客户端写死 IPv4 字面量、或不走这段 DNS 时，合成记录不会出现。移动网常用 464XLAT，在终端再做一层无状态翻译，让这类应用还能发出去。

业务侧最常落地的是应用层代理。反向代理用一种协议接受连接，再用另一种协议访问源站。HTTP 这样就能通，别的端口不会跟着通。

### 7. Java 垃圾回收机制是什么？

**参考答案**

Java 用可达性分析回收堆上不再被使用的对象。从 GC Roots 沿着引用能走到的对象留下，其余对象可以回收。Roots 包括线程栈上的引用、类的静态引用和 JNI 全局引用。

回收分标记和回收两段。标记找出存活对象。回收可以扫掉垃圾、把存活对象拷到新空间，或在原地整理以去掉碎片。HotSpot 的主流收集器是追踪式的，循环引用也能被回收。

分代利用「多数对象死得快」。新对象进 Eden，熬过若干次年轻代收集再按年龄晋升老年代。年轻代用拷贝，死对象不用逐个清扫；老年代收集次数少，单次代价更高。

线程要停在安全点，收集器才能看到一致的引用关系。Parallel 的主要工作在停顿里完成。G1 可以并发标记，拷贝仍在停顿里。ZGC、Shenandoah 把搬运也尽量放到并发阶段。JDK 8 起类元数据在本地内存的元空间，不跟堆对象一起按年轻代和老年代划分。`finalize` 的时机不确定，资源要用明确的关闭动作释放。

### 8. G1 在设计上如何优化内存分配和回收效率？分区机制如何工作？

**参考答案**

G1 把堆切成许多同样大小的 Region。Region 在运行中充当 Eden、Survivor、老年代、Humongous 或空闲，角色会变，年轻代和老年代不是两块固定的连续内存。单个 Region 的字节数在启动时确定。

普通对象的分配走线程本地分配缓冲：在 Eden Region 里用指针碰撞往后摆，分配路径上不用搜索空闲链表。Young GC 把存活对象拷走之后，原 Region 整块回到空闲链表。大于一个 Region 一半的对象不进这种缓冲，而占用连续的 Humongous Region。

回收不必每次碰整堆。每个 Region 有记忆集，记下堆中其他位置对它的引用，收集器就可以只处理本次的回收集。Young GC 会拷走全部年轻代 Region 里的存活对象，死对象留在原处，不再逐个清除。老年代分批处理：并发标记先算出各 Region 的存活情况，随后的 Mixed GC 在停顿目标内优先拷贝垃圾最多的老年代 Region。标记可以和业务并发进行，拷贝发生在停顿里。

跨 Region 的引用由写屏障记进记忆集。处理某次回收集时，区外的引用靠这张表查找。

### 9. G1 的每个 Region 大小是固定的吗？如果会动态调整，如何调整，对性能有什么影响？

**参考答案**

一个 JVM 进程里，Region 的字节数在启动时确定，之后不变。会变的是 Region 的角色、年轻代占多少个 Region，以及堆扩缩时 Region 的个数。

大小按最大堆估算，目标是大约 2048 个 Region，取 2 的幂。自动选择时通常落在 1MB 到 32MB。也可以用 `-XX:G1HeapRegionSize` 在启动时指定。堆从初始大小涨到最大堆时，增加的是 Region 个数。源码里这个大小只设置一次。

和停顿直接相关的动态部分是年轻代规模。G1 按停顿目标增减 Eden 的 Region 数。年轻代规模默认落在当前堆的 5% 到 60% 之间，停顿目标默认是 200 毫秒。年轻代变大，对象更有机会死在年轻代，晋升变少，但单次要拷贝的存活对象变多，停顿变长。年轻代变小，单次停顿下降，收集更频繁，对象更容易晋升，老年代会更早变满。

启动时把 Region 定得过小，Region 数量变多，记忆集开销变大，普通对象也更容易超过半个 Region 而走 Humongous 分配。定得过大，一次至少以整个 Region 为粒度选择和拷贝，停顿更难掐细。

### 10. SQL 查询优化中常用的方法有哪些？

**参考答案**

先看执行计划和扫描行数，再改索引和写法。下面按 MySQL 来说。

索引对齐访问路径。WHERE、JOIN、ORDER BY 用到的列放进索引。联合索引把等值列放前面，范围列放后面，顺序和排序方向跟查询一致。区分度极低的单列索引帮不上过滤。

谓词要能用上索引。不要在列上套函数，比较双方的类型要一致，避免隐式转换。`LIKE '%关键字'` 用不上普通 B+ 树。少读无用列，避免 `SELECT *`。查询列都在索引里时可以覆盖，不必回表。深分页不要用很大的 OFFSET，改成按主键或排序键接着上一页的范围翻。

连接尽量用小结果集驱动，连接键上有索引。`OR`、`UNION` 去重、临时表和 filesort 会在「已经用了索引」的情况下仍然很慢。统计信息要新，基数明显不对时先 `ANALYZE TABLE`，倾斜列再考虑直方图。

行数很少的表，优化器选全表扫描是正常的。单条语句本来就要扫大量行时，索引没有杠杆，应改成分批、汇总表或按分区裁剪。

### 11. 某个 SQL 即使使用了索引，执行仍然很慢，如何系统性排查？

**参考答案**

先把慢分到锁、扫描行数、回表、排序或缓存未命中上，再改索引。以 MySQL 为例。

1. 记录真实语句和绑定参数。看慢查询里的 `Query_time` 和 `Lock_time`。锁等待长，先查谁持有行锁或间隙锁，执行计划本身可能没问题。
2. 看 `EXPLAIN` 的 `type`、`key`、`rows` 和 `Extra`。估算和体感差很多时，用 `EXPLAIN ANALYZE` 看实际行数和耗时。它会真正执行这条 SELECT，不要拿它去跑写语句。
3. 已经用了索引仍慢，对着结果分：
   - `rows` 很大：区分度低或范围太宽，索引扫描仍然读了表的很大一部分。
   - 没有 `Using index`：二级索引命中后还要按主键回表，行数一多，随机读就贵。
   - `Using filesort` 或 `Using temporary`：这个索引满足不了排序或分组。
   - 同一语句第二次就快很多：更像缓冲池是冷的，先把 I/O 和计划问题分开。
4. 再改联合索引的列顺序、补覆盖列、改写分页和谓词，或更新统计信息。用同一组参数对比扫描行数和耗时。应用层循环里的多次查询要单独看，单次 EXPLAIN 看不出 N 次调用。

### 12. EXPLAIN 显示走了全表扫描而不是索引扫描，如何判断要不要优化？需要的话怎么做？

**参考答案**

全表扫描不一定要改。先看这次要读的行占整表的比例，以及这条语句的耗时和调用频率。

表很小，或者结果本来就要覆盖大部分行时，顺序扫描往往比「走索引再回表」更便宜，优化器选 `type=ALL` 是合理的。

值得改的典型情况是：`possible_keys` 里有索引，`key` 却是空的，同时实际只需要很少的行。常见原因是列上套了函数、发生了隐式类型转换、前导模糊匹配，或统计信息过期，把索引估算得太贵。

处理顺序：

1. 把条件改成对裸列的范围比较，让参数类型和列定义一致。
2. 联合索引按等值列、范围列、排序列排列。若回表仍贵，把 SELECT 的列纳入索引做成覆盖索引。
3. `ANALYZE TABLE` 更新统计信息。列值倾斜时再加直方图，然后重新看计划。
4. 用 `EXPLAIN ANALYZE` 确认实际扫描行数下降。`FORCE INDEX` 只用来验证「换这个索引会不会更快」。验证完把列顺序和统计信息留住，不把 hint 留在线上语句里。

业务就是要扫完整张表时，改单条 SQL 没有杠杆，应限流、分批，或改查汇总结果。

### 13. 设计一个在线音乐播放系统，说明歌曲、专辑、歌单三者的关系，并给出数据库设计

**参考答案**

专辑是发行单位，歌单是用户侧的播放集合，两者不要合成一张表。

一首歌曲通常属于一张专辑，专辑包含多首歌曲，用 `song.album_id` 表示。单曲允许专辑为空。专辑内顺序用 `track_no`。同一首歌要进多张合辑时，再把这个外键升级成带碟号和曲序的关联表，默认设计不必先做成多对多。

歌单和歌曲是多对多。一首歌可以出现在多个歌单，一个歌单包含多首歌曲，成员会变。用中间表 `playlist_song`，默认按 `added_at` 播放。音频文件放对象存储，表里只存访问地址。

```sql
CREATE TABLE album (
  id           BIGINT PRIMARY KEY,
  title        VARCHAR(255) NOT NULL,
  artist_name  VARCHAR(255) NOT NULL,
  release_date DATE,
  cover_url    VARCHAR(512)
);

CREATE TABLE song (
  id          BIGINT PRIMARY KEY,
  album_id    BIGINT NULL,
  title       VARCHAR(255) NOT NULL,
  duration_ms INT NOT NULL,
  track_no    INT NULL,
  audio_url   VARCHAR(512) NOT NULL,
  FOREIGN KEY (album_id) REFERENCES album (id)
);

CREATE TABLE playlist (
  id         BIGINT PRIMARY KEY,
  owner_id   BIGINT NOT NULL,
  title      VARCHAR(255) NOT NULL,
  is_public  TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL
);

CREATE TABLE playlist_song (
  playlist_id BIGINT NOT NULL,
  song_id     BIGINT NOT NULL,
  added_at    DATETIME NOT NULL,
  PRIMARY KEY (playlist_id, song_id),
  KEY idx_song (song_id),
  FOREIGN KEY (playlist_id) REFERENCES playlist (id),
  FOREIGN KEY (song_id) REFERENCES song (id)
);
```

艺人如果只是展示，放在专辑上即可。合作演唱再单独做人和歌的关系，不塞进这三张核心关系里。

### 14. 歌曲和歌单是多对多关系，在关系型数据库里如何实现？

**参考答案**

用中间表保存每一对「歌单、歌曲」，不要把歌曲 id 列表写进歌单的一列。

`playlist_song` 的主键用 `(playlist_id, song_id)`。同一首歌在同一个歌单里只能出现一次，这个约束由主键完成。两列都建外键：`playlist_id` 指向歌单，`song_id` 指向歌曲。按歌单拉歌曲时，主键的左前缀已经能用。反查「这首歌在哪些歌单」需要 `song_id` 上的二级索引。

逗号分隔的 id 字符串或一个 JSON 数组做不到这三件事：外键约束、按歌曲反查、只改其中一首时的局部更新。每次改序或删除都要读出整段再写回。

删除要定清楚。删除歌单时级联删除它的中间行。删除歌曲时，若仍被歌单引用，要么禁止删除，要么按产品要求级联删掉中间行。不要留下指不到歌曲的 `song_id`。

### 15. 如果用户要调整歌单里每首歌的播放顺序，数据库设计如何改？

**参考答案**

顺序是歌单和歌曲这条关系上的属性，在 `playlist_song` 增加 `position`，不要写到 `song` 上。同一首歌在不同歌单里的位置本来就不同。题干里的个性化指的是调整这个歌单的播放顺序；若以后每个收听者各有一套顺序，再把用户 id 放进主键。

表里已有成员时，先加可空列，按 `added_at` 回填成 `1..n`，再改为非空并加上唯一约束。空表可以直接建成最终形态：

```sql
ALTER TABLE playlist_song
  ADD COLUMN position INT NOT NULL,
  ADD UNIQUE KEY uk_playlist_pos (playlist_id, position);
```

查询用 `ORDER BY position`。`added_at` 只能表示加入先后，不能表示用户把一首歌拖到任意位置，所以要单独的序号。

歌单通常只有几十到几百首，可以在事务里锁住歌单行，把该歌单的 `position` 重写成 `1..n`。想少写几行，可以用留空隙的序号，移动时只更新被拖动的那一行；空隙用尽再整理。

MySQL 的唯一索引在语句执行时检查，两条记录直接对调 `position` 会先撞车。事务里可以先把该歌单全部序号加上一个大偏移，再写成最终序号。并发编辑同一歌单时，对歌单行 `SELECT ... FOR UPDATE`，或用版本号拒绝过期写入。

### 16. 设计一个给业务方调用的文本生成 HTTP 接口：请求和返回要有哪些关键字段？如何支持流式返回？

**参考答案**

一次调用要能看清上下文、模型参数、输出、错误和追踪 id。上下文用消息数组，保留角色，不用一整段没有角色的字符串代替多轮对话。

请求：

```json
{
  "model": "model-name",
  "messages": [
    {"role": "system", "content": "你是客服助手"},
    {"role": "user", "content": "帮我改写这段文案"}
  ],
  "parameters": {
    "temperature": 0.3,
    "top_p": 0.9,
    "max_tokens": 512
  },
  "stream": false
}
```

`parameters` 原样约束后传给模型，并在文档里写明本服务的默认值。检索到的资料可以作为额外的消息放进 `messages`，调用方能看出模型看见了什么。

非流式返回：

```json
{
  "id": "018f3b6c-7c2e-7a1b-8d4e-9a0b1c2d3e4f",
  "model": "model-name",
  "output": {
    "role": "assistant",
    "content": "改写后的文案",
    "finish_reason": "stop"
  },
  "usage": {"input_tokens": 120, "output_tokens": 46}
}
```

`finish_reason` 区分正常结束、触达 `max_tokens` 和内容审核拦截。失败时 HTTP 状态和正文一起用：参数错误 400，未认证 401，无权限 403，限流 429 并带重试等待，模型超时 504，模型过载 503，其余服务端故障 500。正文给稳定的 `error.code`、说明和 `retryable`。限流和过载不要返回 200，否则网关和调用方不会重试。

流式用 SSE：`Content-Type: text/event-stream`，关闭代理缓冲，每段 delta 立刻 flush。浏览器的 `EventSource` 只能做 GET，带请求体的生成要用 `fetch` 读响应流。HTTP 状态在首字节发出前就定了，所以流中间的失败改用错误事件，不能再改状态码。调用 id 同时放在响应头和第一条事件里。生成过程中周期性地写注释行作心跳，避免代理把空闲连接掐掉。客户端断开时，服务端停止向上游模型拉后续内容。

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Request-Id: 018f3b6c-7c2e-7a1b-8d4e-9a0b1c2d3e4f

data: {"id":"018f3b6c-7c2e-7a1b-8d4e-9a0b1c2d3e4f","delta":"改写","finish_reason":null}

data: {"id":"018f3b6c-7c2e-7a1b-8d4e-9a0b1c2d3e4f","delta":"后的文案","finish_reason":"stop","usage":{"output_tokens":6}}
```

对浏览器和业务方用 SSE。内网服务之间也可以用支持服务端流的 RPC，事件里的 id、delta 和 `finish_reason` 保持同一套语义。

### 17. 实际实现中，如何生成调用 ID，才能保证唯一和可追踪？

**参考答案**

服务端生成 UUIDv7，并让响应头、首包和日志使用同一个值。

UUIDv7 前 48 位是毫秒时间，后面是随机位。日志按它排序，近似就是发生顺序。随机位让多个节点同时生成也不会撞号，对一次调用的追踪，这个碰撞概率可以忽略。不要用毫秒时间戳本身或很短的随机数当调用 ID，同一毫秒里就会重复。

可追踪靠传播，不靠 ID 的格式。网关写入 `X-Request-Id` 和结构化日志，并放进 W3C `traceparent`。模型网关、下游存储使用同一条 trace。这个 ID 标识这一次生成；下游自己的查询再记各自的 span。只在 JSON 里返回、日志不打，排障时对不上。

客户端可以传入 ID。格式合法就沿用，这样超时重试仍指向同一次调用；格式不合法就拒绝，避免各写各的。它负责把日志串起来。若超时重试必须返回同一次生成结果，还要按这个 ID 保存结果并做幂等，单靠「号不重复」不会把已经生成的内容找回来。

### 18. 多个节点都可能生成调用 ID 时，如何保证分布式环境下绝对唯一？

**参考答案**

绝对唯一指区间在构造上不重叠，而不是碰撞概率很小。各节点只拿本地毫秒时间做不到这一点。发号空间必须拆开：要么由数据库发出互不重叠的号段，要么每个节点拥有独占的 workerId。美团公开的 Leaf 就是这两种。

号段模式在库里按业务键保存 `max_id` 和 `step`。节点在事务里执行 `max_id = max_id + step`，然后在内存中发放这一段。行锁保证两台机器领不到同一段。双缓冲可以在当前段用完前提前领取下一段，避免发号时同步等数据库。号段不看时钟，会有空洞，空洞不影响唯一。数据库不可用时，已领的段还能发，新段要等库恢复。

雪花模式把 64 位拆成时间戳、10 位 workerId 和 12 位毫秒内序列，同一节点同一毫秒最多 4096 个。Leaf 用 ZooKeeper 按实例分配 workerId，避免两台机器用同一个 worker。运行中时钟回拨不超过 5 毫秒会等待后重试，再长就让这次发号失败；启动时还会拿本机时间和 ZK 上上次记录的时间比较，本机落后就拒绝启动。序列用尽就等到下一毫秒。这样唯一性依赖「workerId 不冲突，且同一 worker 的时间不回退」。

调用 ID 若主要用来追踪，UUIDv7 或雪花都能从号里看到时间。雪花还可以解出 worker。号段更适合要单调递增的主键。追踪号不要各节点用短随机数，再把它说成绝对唯一。号唯一之后，仍然要写进同一条 trace，下游日志才连得起来。

### 19. 对于不熟悉的领域或技术，你会如何系统学习和掌握？

**答题思路**

按「先定一件要做成的事，再打通最小闭环，最后补失败」来，不要从名词表第一页读起。

1. 用一句话写目标：例如独立把一个生成接口接到现有服务里，并说清超时和重试。目标以外的词先记下来，不展开。
2. 用官方文档建地图：核心对象、一次正常调用的顺序、哪些配置会改变结果。地图短到能讲给别人听。
3. 做最小可运行例子：自己发请求，看到原始返回，再故意触发一种错误。这一步用一手文档和真实响应，不先看二手总结。
4. 对照一个成熟实现，只看你已经遇到的那段：连接怎么建、错误怎么返回、追踪 id 放在哪。
5. 把失败补齐：超时、重复请求、非法输入、依赖不可用。每一种说清你靠哪条日志或指标看见它。
6. 用自己的话讲一遍，列出仍然讲不清的词，再回到文档。验收标准是能独立完成第 1 步那件事，并说清两种失败。先把闭环做完，再按真正碰到的问题加深。
