# 10.19 美团 Agent Harness 一面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 一面

这一轮大约 75 分钟。

### 1. 自我介绍

**答题思路**

控制在一两分钟，按「方向 → 一个项目 → 和这个岗位的关系」讲完就停。

1. 一句话说明你做 Agent 工程里的哪一段：编排、检索、工具执行或运行时。年限和职级不用凑。
2. 只展开智能运维这一个项目：要完成的是告警后的排查还是操作建议、你负责的链路、结果用你拿得出来的证据。没有数字就讲评测集或坏例，不临时编指标。
3. 收到 Harness 相关岗位上：你关心模型循环外面的上下文、工具约束和失败后怎么恢复。话停在这个项目上，让对方顺着往下问。

### 2. 你当时为什么会想到做这个智能运维 Agent 项目？

**答题思路**

从你当时的痛点讲起，不从名词讲起。原因用你真实负责的系统，不编业务量和团队规模。

1. 先说重复劳动：告警多、手册散、同类故障仍要人工翻日志和文档，新人依赖个人经验。范围只讲你确实接触到的那一类系统。
2. 说明为什么不是一个搜索框或一次问答。排查是多步的，下一步取决于上一步看到的指标、日志或变更，单次检索给不出这个闭环。
3. 你的位置：你当时改的是手册、告警还是执行链路，所以由你来做。只讲职责，不讲头衔。
4. 用边界收住：它给出依据和建议，重启、回滚、改配置仍由人确认。避免被听成「模型直接在生产执行命令」。

### 3. 简单描述一下你是怎样构思这个系统运转流程的，以及中间技术或中间件选型的依据是什么。

**答题思路**

按一次请求的路径讲，每一步只配一个选型理由。中间件只报你用过的，并准备一句「不用它时这一步会怎样」。

1. 入口是告警还是人工提问，目标语句是什么。
2. 规划放在循环里：先出整段计划再执行，还是看一步走一步。这里点到即可。
3. 知识分开：手册和历史故障走检索；当前指标、日志、变更走工具。实时状态不要说成向量库里的文档。
4. 每个工具讲输入、输出和失败时的行为。有副作用的调用先停在确认。
5. 选型按这个顺序取舍：要精确匹配还是语义、数据变不变、失败能否原样重试、延迟能不能接受、这一步有没有轨迹可查。

### 4. 为什么使用 RAG？现在模型的上下文窗口已经很大，为什么不直接把原始文档都交给 Agent，让它自己查询？这两种方式有什么区别？

**参考答案**

窗口变大只说明文本塞得下，不说明相关证据会被用到。RAG 在生成前把证据收成少数片段；把原始文档整包交给 Agent，是让模型在全量文本里自己定位。

RAG 离线切块、嵌入、建索引，线上按问题召回再生成。证据边界清楚，可以要求引用，文档更新改的是索引。失败时是召回漏了，生成阶段根本看不见。

全量放进上下文，或让 Agent 自己翻附件，在语料很小、问题又要跨全文归纳时少一层漏召。文档变多以后，无关内容把相关事实挤到模型不敏感的位置，引用也没有稳定边界，每一轮都要带着整库。

检索要做的是把该看的证据放到模型实际会用的位置。容量和相关性是两件事。

### 5. 如果有十篇甚至更多文档，或者让 AI 阅读信息量更大的代码仓库，比较「用 RAG」与「把文件交给 Agent、让它通过 grep 等操作自行检索」，在不考虑 token 消耗时，两者各有什么优劣？

**参考答案**

不计 token 时，比的是召回方式、读到的是不是最新内容、以及能不能沿着结构多跳。

RAG 能按语义碰到措辞不同的手册和注释，一次检索有全局排序。切块会切断函数、表格和连续步骤；索引会落后于刚改的文件；函数名、错误码、配置键这类精确符号不稳定，因为一个向量代表的是整块，不是某一个标识符。

Agent 用 grep 再打开文件，精确串很稳，可以顺着报错、import 和调用继续读，读到的是当前内容。它的召回取决于模型猜中关键词，没有共享词的段落会直接漏掉；它没有全局排序，只看见自己打开的部分。十篇文档里逐篇看通常更稳。文件一多，搜错目录就会停在错误结论上。

代码仓库里标识符适合 grep，概念说明适合向量，两边补的是不同的漏法。不计费用，步骤数和过早停止仍然存在：grep 方案常见的失败是没再往下翻，不是单次排序算错。

### 6. 从原始文档到最终检索、合成答案，RAG 中间有切块、索引、存储、检索、排序等很多步骤。哪些步骤对你构成了挑战，并会影响最终效果？

**答题思路**

先点你真正调过、而且改完坏例有变化的那一步。不要把每一步都说成自己的难点。被追问时按下面的影响顺序讲，只展开你有坏例的那些。

1. 切块决定证据完不完整。从步骤、表格或函数中间切开，召回块里没有答案。块太大，关键句又被同一块里的其他句子盖住。
2. 查询和文档对不齐时，正确块的距离并不近。短问、多意图、口头语和文档用词不一致，都属于这一步。存储和生成救不回没召回到的事实。
3. 双编码器的顺序很粗，正确块常在前面一截但不在送进模型的那几条里。这里才需要重排或按排名融合。
4. 过期手册、错误服务、权限不对，是过滤和版本问题。向量库的品牌通常不是质量瓶颈。
5. 证据在上下文里，答案仍改了数字或否定词，这是生成约束，不是索引。

用同一批问题把「没召回到」和「召回到了但答案超出证据」分开，才能说明你动的那一步确实影响效果。

### 7. 如果你的 Markdown 文件没有标题，要怎么切分？

**参考答案**

没有标题就按文中还在的结构切，不要按固定字数从句子中间断开。

空行隔开的段落各自成块。围栏代码、列表和表格保持完整，不从代码块或表格行中间切开。块仍然过长时，再按句号、分号往下拆，相邻块留一小段重叠，避免一个步骤分到两边之后都不完整。

全文几乎没有空行时，比较相邻句子的相似度，在话题明显转折的地方切开。等宽滑动窗口会把同一步骤切成两半，只适合作为兜底。

每块带上文件路径，以及该块开头的一两句，否则无标题碎片嵌完之后和其他文件分不开。可以用模型给段落拟标题再切，拟出来的结构要抽查，不能当成文档原有大纲。手册里若能认出现象、原因、处理这类字样，同一组处理步骤尽量留在一块。

### 8. 混合、多路检索中，关键词检索有什么优缺点？向量检索又有什么缺点？

**参考答案**

关键词检索走倒排和 BM25 一类的词项匹配。错误码、配置键、服务名和少见词能命中，结果可以解释，短查询稳定，索引可以按词更新。它没有同义能力，「宕机」对不上「服务不可用」；中文分词错了就会偏；问句里没有文档用过的词，召回就是空的。

向量检索把一块文本压成一个向量，精确符号被稀释，命中原因说不清楚。短查询和长文档不在同一分布上，距离不可靠。近似索引探测太少时，真正接近的块会静默丢掉。嵌入模型没见过领域说法时，语义召回同样失败。改文档要重嵌入，不能像倒排那样改一个词项。

两路一起用，是因为漏法不同：关键词留住精确词，向量留住改写。融合时按排名合并，避免两套分数直接相加。

### 9. chunk 可能有一两百字，但 query 可能只有三到五个字，怎样把短 query 与长 chunk 向量化后比较？你有没有对比过长 query 和两三个字的短 query 在向量召回上的差异？

**参考答案**

两边各压成一个向量再算余弦，比的是一个很窄的意图和一整段的平均。块里往往只有一句相关，其余句子把向量拉向别的话题。三五个字换一个同义词，向量就偏得很远，召回不稳定。一句完整的问更接近嵌入模型训练时的查询，和文档向量可比，同一套双编码器上通常更稳。两三个字时，向量经常不如关键词。

不要把长块硬压到和短查询一样短。用区分查询和段落的嵌入模型，两边加各自的指令前缀。或者把块再拆细，检索命中小块，送给模型时带回相邻句。短查询也可以先扩写成一段假设性答案再嵌入，让两边都是段落；扩写会跑偏，原查询里的关键词要同时参加检索。更细的做法是给块保留 token 级向量，让短查询只对准块里最接近的若干 token。

没分长度测过，就按查询长度分桶看召回。长查询上的结果不能说成短查询也一样。

### 10. 除了压缩以外，对长 query 还会做什么处理？

**参考答案**

压缩去掉的是口语和重复。长查询里更影响召回的是多个意图、约束和指代，这些不能压掉。

一句话里同时有现象、时间和服务时，拆成几条子查询分别召回，再把结果融合。实体、错误码、服务名抽出来走关键词，其余走向量；压缩或改写时这些稀有词留下。环境、时间范围、租户、服务名写成过滤条件，不要只留在嵌入文本里。

多轮里的「它」「刚才那个」先补成可以单独检索的问句，不要把整段对话嵌进去。还可以平行检索一个更抽象的问法，用来补原则性段落。生成一段假设答案再去检索，也是改写，不是把原句缩短。

最后判断这句要不要检索。计算、闲聊或明确的工具操作，送进文档库只会召回无关手册。

### 11. 你怎样确认 RAG 的产出有没有出现幻觉？

**参考答案**

不能证明某次回答完全没有幻觉。能做的是检查每个断言是否被检索到的证据蕴含，对不上就不当成事实输出。

回答带片段编号。没有出处，或出处里没有这句话，就标成未证实。数字、错误码、版本号、命令和是否定再做字符串核对，这些最容易被改写。

检查要看证据是否蕴含断言，而不是让同一遍生成再评价自己。检索分数整体都很低时拒答，避免用参数记忆把空缺补上。

离线用同一批问题分开统计：证据里有没有召回到，答案有没有超出证据。会执行的建议里，命令和阈值要能在手册原文中找到，否则只展示，不执行。没召回到，和证据在但回答改了，修的不是同一个环节。

### 12. 测评只能说明有较高概率答对，人和 AI 都做不到百分之百正确。对于剩余 1% 或 2% 的错误，怎样识别？有没有考虑给模型的最终产出增加检测机制？

**参考答案**

评测集上的正确率不是单次输出可以交付的证明。剩下的错误要在交付前变成「拦住」，而不是指望平均分再高一点。这里的百分数只说明还有尾部，不是某个模型的实测指标。

把最终输出拆成单条断言，逐条对照证据或工具结果。能用确定性规则就不用模型：格式是否合法、命令是否在允许列表里、数值和单位是否与来源一致、否定有没有被说反。和生成模型同一次习惯的「再评一次」会漏掉同一类错误，检查要用独立的提示，规则能覆盖的部分不用模型。

检查不通过、检索没有把握、或工具结果和草稿矛盾时，不给结论，改为重新检索、重新规划或交给人。尾部若集中在重启、回滚、改配置上，总正确率仍然好看，所以要按这类切片看。用户改过的答案和执行失败的步骤记成坏例，测试集里原来没有这些样本。

### 13. 你平时会用 AI 写代码吗？你怎样判断 AI 写的代码对不对？

**参考答案**

会用。判断对错看它有没有实现你指定的行为，不看差异写得像不像，也不看它自己写的测试是否通过。

先按评审读改动：边界、错误处理、并发和资源释放，以及它是不是在解一个更简单的相邻问题。再跑你事先写好的用例，至少覆盖空输入、边界和失败路径。期望若由模型根据自己的实现来写，错误会被写成正确。类型检查和构建只能排除一部分问题。库的函数名和参数顺序要对照真实定义，生成结果会编出不存在的重载。

外部输入、命令拼接和权限判断沿数据流看一遍。一次改动保持在你能解释每一行的规模。说不清某行为什么在，就还没有判断对。

### 14. 一个 Agent 和多个 Agent 协作完成同一件事，你以前实际使用过多 Agent 的协作方式吗？

**答题思路**

先回答用过还是没用过。一个 Agent 循环调多个工具，不要说成多 Agent。

用过就按这个顺序讲真实的那一次：每个角色做什么、能调哪些工具、中间状态放在哪、某个角色失败谁接手、最后谁对结果负责。

没用过就说明项目是一个 Agent 在同一条上下文里调工具，并给出没拆的原因。任务是一条控制回路、下一步依赖上一步的原始观察、工具不多时，一个上下文更不容易丢证据。角色的提示、工具权限或可以并行的子任务确实不同，再拆开，例如查日志、只依据手册起草步骤、检查危险操作分成不同角色。

两种都要能讲代价：证据被拆开，角色互相复述，延迟变长，出错后不知道是哪个决定。收在你实际的默认做法上：一条回路能完成，就保持一个 Agent。

### 15. 你提到使用 Plan-and-Execute；它和 ReAct 相比，你的选择依据是什么？

**参考答案**

依据是路径能不能事先说清，以及整段计划要不要先被人看过。运维手册若大体是固定顺序，适合先给出计划再逐步执行；下一步完全取决于刚读到的日志时，适合 ReAct。

Plan-and-Execute 先列出步骤，再执行，观察推翻计划时要重排。计划和执行可以分开看：人先确认计划，执行某一阶时上下文里主要是这一阶和它的观察。代价是多一次规划，而且计划会过时。没有重排的计划就是一条写死的脚本。

ReAct 每一步根据最近的观察决定下一个工具，假设变了可以马上改。它没有一份可先审的计划，步数不封顶时会重复调用、偏离原来的目标，长轨迹也会把目标淹没。

选择时看三件事：手册是否提供了稳定顺序、危险动作是否必须先看到整段计划、错误的早期步骤代价有多大。实际链路若是「短计划加上按观察执行，只有观察矛盾才重排」，要和纯 ReAct、纯一次性计划区分开讲。

### 16. 你觉得 Agent 和 Harness 分别是什么？二者有什么区别？Harness 做了哪些事情，能让 Agent 更好地执行任务？

**参考答案**

Agent 是围绕目标的决策循环：读当前上下文，决定调用工具或给出结论，再根据观察继续，直到完成、明确失败或到达步数上限。系统提示、规划方式和选工具的策略在这一侧。

Harness 是包住这条循环的运行时。它校验并执行工具调用，处理超时、权限和沙箱，把输出和错误结构化送回；决定这一步哪些内容进入上下文，过长时如何裁剪；限制步数，重复失败时触发重规划，危险操作前要求人工确认，中断后按记录恢复。工作区和每一步轨迹也由它留下。

模型负责决定下一步。参数是否合法、上下文里有什么、何时停止、失败后能否回到现场，决定这个决定能不能做完。只说一个框架的名字，还没有说明这些职责；用来监督的模型只是运行时里的一种可选策略。

### 17. 上下文管理也是 Harness 的职责，比如上下文过长时，哪些内容该送、哪些不该送，哪些该裁剪，以及 System Prompt 中哪些该写。你在项目里是怎么做的？

**答题思路**

按「送什么、不送什么、过长怎么裁、系统提示写什么」讲你项目里的真实做法。没做的机制不要说成已经上线。

1. 送进模型的，保持在这些范围内：稳定的系统提示、工具定义、当前目标、还没做完的计划、最近几步工具结果、本轮检索片段。
2. 不送：密钥和令牌、重复的告警原文、已经结束且有结论的尝试、超长命令输出的全文。截断长输出时留下可以再读的位置。
3. 接近窗口上限时，把更早的工具轨迹收成短状态：试过什么、结论是什么、还开着什么。最近一次观察保持原文。系统和当前计划不要压成一段含糊摘要。
4. 系统提示写角色、何时检索、何时调工具、何时问人、回答要带证据、哪些操作不能直接执行。这次告警、单号和时间放在后面的消息里，系统提示跨轮次保持字节不变，前缀缓存才撞得上。
5. 顺序固定：系统提示和工具在前，对话和本轮检索在后。

当时若只按长度截断，就这样说，并补上你会先加的两件：被截掉的早期步骤有摘要，检索片段带来源编号。

### 18. 你了解模型的 Prompt Cache 吗？

**参考答案**

Prompt Cache 复用的是相同前缀在预填充阶段算出的键值状态。下一次请求的前缀逐 token 一致时，这一段不必重算。它不是对话记忆，也不是向量缓存。

前缀里有一个 token 变化，从这里到末尾的缓存失效。命中之后，这段预填充更便宜，首 token 更快；新增后缀和后面的解码仍要正常计算。缓存有时效，不能假设隔夜还在。不同服务的最小可缓存长度和计费不同，讲清失效方式即可。

要用上它，跨轮不变的部分必须是严格相同的前缀：系统提示、工具定义的文本和顺序都冻结。时间戳、请求编号、本轮检索放在前缀之后。每轮重排工具，或把告警写进系统提示，缓存每次都会失效。

同一轮解码内部的键值缓存是另一次复用，不要和跨请求的前缀缓存混在一起。

### 19. Milvus 和自己手写一套余弦相似度检索相比，有什么区别？

**参考答案**

余弦公式可以相同。手写是对内存里的全部向量做精确扫描；Milvus 是带索引、过滤、持久化和并发查询的向量库。

手写把向量放在数组里，查询时逐个算余弦再取前 k。数据量不大、查询很少时，它精确，也容易调试。进程退出后数据要靠你自己保存；按服务名或时间过滤、删除、并发，都要另外写。单次查询要扫过全部向量。

Milvus 按段存放向量和标量字段，封存后的段建立近似索引，常见的是 HNSW、IVF。查询走索引取候选，再加上标量条件，多段结果归并成前 k。它用少量召回损失换查询不随数据量线性变慢，并处理写入、删除和持久化。需要精确近邻时，可以用不做近似的平坦索引，排序应和手写余弦一致。

向量已经归一化时，内积和余弦的排序相同。一边用余弦、一边用未归一化的内积，结果不同，原因在度量，不在「库把余弦算错了」。

### 20. Milvus 内部的存储、检索等机制是怎么实现的，你看过吗？

**参考答案**

Milvus 2.x 的路径是先写日志，再落成段，封存后建索引，查询时加载这些段。没读过源码，也可以按这条路径讲，不必背默认参数。

写入经代理进入消息队列。消费后先放在内存里的增长段，达到阈值再刷成封存段，文件进入对象存储，元数据放在独立存储里，常见是 etcd。增长段还没有索引；一致性要求看见刚写入的数据时，这段按原始向量比较。

封存段再建索引。HNSW 这类从图的入口走向近邻；IVF 这类先定位若干粗簇，再在簇内算距离。查询节点加载封存段，按需要连同增长段一起查。各段候选举合成前 k，同时套用删除标记。删除先记下来，压缩时才从文件里去掉。

标量条件可以先圈定主键再搜，也可以先搜再滤。条件很严时，先过滤会让近似索引的优势变小。一致性由时间戳区分，决定这次查询看不看得到还在增长段里的写入。

### 21. 如果有三万个协程和三万个线程，在同一颗 8 核 16 线程的 CPU 上运行，它们在调度上有什么区别？

**参考答案**

这颗 CPU 同时真在执行的大约是 16 个硬件线程。三万个内核线程全部交给操作系统排；三万个协程先由运行时排到大约 16 个内核线程上，操作系统只看见这一小批。

内核线程和调度实体一一对应。三万个都可运行时，调度器在远大于硬件的队列里切换，路径经过内核，每个线程还有自己的栈和控制信息。并行度不超过 16，创建和切换的成本先被放大。

以 Go 为例，这三万个是协程，跑在内核线程上。同时执行 Go 代码的线程数默认等于逻辑 CPU 数，这里是 16。协程在信道、锁、网络和调度点让出，运行时把线程交给另一个协程。协程堵在系统调用里时，运行时另找线程继续跑已经就绪的协程。栈按需增长，所以三万个协程可以同时存在。1.14 之后，长时间运算也可以被抢占；进入 cgo 或持有运行时锁时除外。

Java 21 起的虚拟线程是同一形状：大量虚拟线程挂在接近 CPU 数的平台线程上，在能卸载的阻塞点让出平台线程。落在无法卸载的本地调用里时，仍会占住一条平台线程。

计算密集时，协程不会比 16 路并行更快。等待密集时，已经让出的协程不占内核调度名额，阻塞中的内核线程则一直占着。

### 22. 你平时用 AI 写代码，对 Vibe Coding 和 Spec Coding 这两个概念有了解吗？

**参考答案**

Vibe Coding 是用自然语言把想法试出来：描述想要的结果，接受生成的代码，跑起来不对就把现象贴回去再改。它适合一次性脚本、界面试验和边界还没定的探索。代价是实现你说不清，结构会越改越散，错误留在「看起来能跑」里。

Spec Coding 是先写规格再实现。规格里有行为、接口、约束和怎样算做完，检查从这些验收来，而不是从已经生成的实现反推期望。评审先看规格齐不齐，再看代码是否满足它。开始更慢，改动能不能留下有标准。

两种是写法，不是两套产品。探索时可以先把路径跑通；要留在仓库里的改动，收成短规格和你能独立复核的检查。没有规格和反例，就只是在看代码顺不顺。

### 23. 将 K 个升序链表合并为一个升序链表

**参考答案**

每条链表已经升序，合并后仍保持升序。用大小为 K 的最小堆维护每条链表当前的头。堆里每个元素是（节点值，链表下标，节点）。下标必须带上：值相同时，堆无法比较节点对象。

每次弹出当前最小节点，接到结果尾部，并把该节点的后继压回堆。空链表不要入堆。全部弹出后，哑节点的后继就是结果。节点是原链表上的，不新开数据节点。

设节点总数为 N。每个节点入堆、出堆各一次，堆大小不超过 K，时间是 O(N log K)，额外空间是 O(K)。K 为 2 时，双指针归并即可，是同一个问题的特例。一条条顺序归并，后面的链表会反复被扫，最坏到 O(KN)。两两分治合并也是 O(N log K)，额外空间主要是递归深度 O(log K)。

```python
import heapq
from typing import Optional


class ListNode:
    def __init__(self, val: int = 0, next: Optional["ListNode"] = None):
        self.val = val
        self.next = next


def merge_k_lists(lists: list[Optional[ListNode]]) -> Optional[ListNode]:
    heap: list[tuple[int, int, ListNode]] = []
    for i, node in enumerate(lists):
        if node is not None:
            heapq.heappush(heap, (node.val, i, node))
    dummy = ListNode()
    tail = dummy
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node
        tail = node
        if node.next is not None:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next
```

### 24. 最长有效括号

**参考答案**

给一个只含 `(` 和 `)` 的字符串，求最长有效括号子串的长度。有效指括号能够两两匹配，例如 `(()())` 的长度是 6，`()(()` 的最长是 2。

用栈存下标，先压入 `-1` 作为长度计算的基准。遇到 `(` 就压入下标。遇到 `)` 先弹出：栈空了，说明这个右括号没有匹配，把它的下标压进去当新基准；栈不空，当前下标减去新的栈顶，就是以这里结尾的有效长度。全程取最大值。

时间 O(n)，空间 O(n)。容易写错的是空栈后的基准，以及长度要用下标差，不是用栈的深度。

也可以扫两遍、把空间降到 O(1)：从左向右计数，右括号多于左括号就清零，相等时用 `2 * 右括号数` 更新答案；再从右向左扫，处理多余的左括号。动态规划以「在 i 结尾的最长有效长度」为状态，匹配到一对之后还要加上这对前面已经有效的长度，白板上容易漏掉这一段，所以优先写栈。

```python
def longest_valid_parentheses(s: str) -> int:
    stack = [-1]
    best = 0
    for i, ch in enumerate(s):
        if ch == "(":
            stack.append(i)
        else:
            stack.pop()
            if not stack:
                stack.append(i)
            else:
                best = max(best, i - stack[-1])
    return best
```
