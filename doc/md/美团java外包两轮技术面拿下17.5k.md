### 3. 项目里用了哪些技术栈，为什么这么选

**答题思路**

只讲线上真实在用的。每一项两句：它承担什么约束，另一个常见选项为什么不适合这个约束。

1. 要事务、约束和复杂查询的数据放 MySQL。订单状态、余额这一类事实来源不放进 Redis。
2. 读多写少的详情、会话、原子计数才放 Redis。讲清过期和回源，以及它挂了主链路怎么降级。
3. 可以异步、允许短暂延迟的下游通知才放消息队列。点名你用的是哪一个，以及你用到的能力是解耦、削峰还是延迟消息。
4. 框架按调用链说：Web 入口、事务、连接池。没接入的组件就说了解选型，说成已经在跑会被追问配置。

选型对着数据量、一致性要求和团队能维护的复杂度讲。流量没到的拆分，说明当时为什么不拆。

### 4. MySQL 索引为什么用 B+ 树，不用 B 树

**参考答案**

InnoDB 的索引是 B+ 树。等值查找和范围扫描都落在同一层叶子上，树高低，磁盘 IO 少。

非叶子节点只放键和子页指针，不放整行。默认页 16KB，同样一页能放下更多键，扇出大，树高通常只有两三层，定位一行只要几次 IO。所有记录都在叶子，叶子之间有双向链表，范围查询顺着链表顺序扫。

经典 B 树的内节点也存记录。同样页大小下扇出更小，树更高；范围扫描要在内节点和叶子之间来回走。数据库的典型访问是等值和范围，B+ 树对这两类都更合适。

聚簇索引的叶子是整行，二级索引的叶子是索引列加主键。这是「叶子里放什么」，和「为什么用 B+ 树」分开说。

### 5. 聚簇索引和非聚簇索引区别，什么是回表

**参考答案**

InnoDB 里，表就是一棵聚簇索引，一张表只有一棵。叶子放整行，键一般是主键，数据和主键顺序放在一起。

二级索引是非聚簇索引。叶子放索引列和主键，不放整行。查到主键之后，如果还要其他列，再拿主键到聚簇索引取整行，这一步叫回表。

查询列都在这棵二级索引里时，不回表，EXPLAIN 的 Extra 里会出现 Using index。回表次数多、行又宽时，可以加覆盖索引，用写放大换少一次随机查找。

没建主键时，InnoDB 会选第一个全列非空的唯一索引做聚簇；再没有，就生成隐藏的 6 字节行 id。所以聚簇索引就是主键，只在你确实建了主键时成立。

### 6. 事务的 ACID 分别怎么理解

**参考答案**

ACID 是一次提交要保住的四件事，InnoDB 用日志和锁落地。

原子性：事务里的修改要么全部留下，要么全部撤销。未提交的修改记在 undo 里，回滚时顺着 undo 撤销。

一致性：事务前后，约束和业务不变量都成立，例如余额不为负、外键成立。隔离和原子负责机制，库存不为负这一类规则要靠约束和条件更新，引擎不会替你补业务规则。ACID 里的一致性也和 CAP 里的一致性不是一个词。

隔离性：并发事务看不到对方还没提交的中间状态。InnoDB 用锁和 MVCC 实现，级别从低到高是读未提交、读已提交、可重复读、串行化。

持久性：提交返回之后宕机也不丢。redo 按 WAL 先落盘，恢复时重做已提交的修改。undo 负责回滚未提交的，不负责「提交之后还在」。

### 7. MySQL 默认隔离级别，可重复读下 MVCC 怎么实现

**参考答案**

默认隔离级别是可重复读（REPEATABLE READ）。普通 SELECT 是快照读，靠 MVCC；当前读靠锁。

每行有隐藏的事务 id 和指向 undo 的回滚指针，修改会把旧版本串成链。事务第一次快照读时生成 Read View，里面有当时还活跃的事务 id、最小活跃 id，以及下一次将分配的 id。

可见性按行上的事务 id 判断：小于最小活跃 id，说明早已经提交，可见；大于等于高水位，是视图建立之后才开始的，不可见；落在中间的，还在活跃列表里就不可见，顺着 undo 找更老的版本。可重复读里这个 Read View 复用到事务结束，所以同一次事务里的快照读对得上。读已提交则每条语句新建一个 Read View。

Read View 建在第一条快照读，建在 BEGIN 上要写 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。BEGIN 之后、第一次查询之前提交的修改，第一次查询看得到。

`SELECT FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，读最新已提交版本并加锁。可重复读用临键锁（记录锁加间隙锁）挡住别人往间隙里插行。快照读不加间隙锁。

### 8. synchronized 和 ReentrantLock 区别

**参考答案**

两者都是可重入的互斥锁。不需要限时、中断或多个等待队列时，用 synchronized；需要这些能力时用 ReentrantLock。

synchronized 离开同步块一定会释放，包括抛异常。ReentrantLock 要写在 finally 里 unlock，漏了就是死锁。

synchronized 的等待不能中断，也没有超时。ReentrantLock 有 `lockInterruptibly` 和 `tryLock`。它默认非公平，构造参数可以改成公平锁；公平锁按队列来，吞吐通常更差。synchronized 只有一个等待集合，ReentrantLock 可以建多个 Condition，分组等待。

synchronized 的锁状态在对象头里，争用上去才进入 Monitor 队列。ReentrantLock 基于 AQS，用 volatile state 加 CAS 排队。轻度争用下两者接近。偏向锁从 JDK 15 起默认关闭，讲轻量级锁和重量级锁即可。

### 9. 线程池核心参数说一下，IO 密集任务怎么配

**参考答案**

`ThreadPoolExecutor` 有七个参数：核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。

执行顺序是：线程数小于核心就建线程；达到核心后任务入队；队列满了并且还没到最大线程数，再建线程；仍然放不下就拒绝。最大线程是队列满了之后才用的。队列没有上界时，最大线程数不会生效。`Executors.newFixedThreadPool` 就是这种队列，生产上改用有界队列。

超过存活时间会被回收的，是核心线程数以上的空闲线程。核心线程默认留着，除非打开 `allowCoreThreadTimeOut`。默认拒绝策略是抛 `RejectedExecutionException`。

IO 密集可以从 `核数 × (1 + 等待时间 / 计算时间)` 起估，再拿队列长度、拒绝次数和下游连接池校正。等待远大于计算时，线程数可以明显高于核数，但不要超过下游真正能并行的连接数，多出来的线程只是堵在借连接上。CPU 密集接近核数。两种任务分开建池，线程名带上业务。

### 10. Redis 为什么快，常见数据结构用在什么场景

**参考答案**

快，是因为数据在内存里，命令在单线程里执行，网络用 IO 多路复用。内存省掉了普通读路径上的磁盘 IO。单线程执行命令就没有锁竞争；Redis 6 以后可以用 IO 线程做网络读写，命令执行默认仍是单线程。一条慢命令（大 key 删除、`KEYS`）会堵住后面所有命令。

常见结构按用途选：

- String：缓存对象、`INCR` 计数、`SET NX` 做简单锁、会话。
- Hash：一个对象的多个字段。购物车可以用用户 id 做 key，注意字段过多会变成大 key。
- List：最新 N 条、简单队列。它没有消费位点，承担不了业务消息队列。
- Set：去重、标签、交集。抽奖可以用 `SPOP`。
- ZSet：排行榜、按时间戳做延迟队列、滑动窗口限流。分数就是排序键。

Bitmap 适合按天签到这种位标记，HyperLogLog 适合允许误差的 UV。选择前先看 key 会不会大、命令是不是 O(n)。

### 11. 缓存穿透、缓存击穿、缓存雪崩分别是什么，怎么处理

**参考答案**

三件事的流量形态不同。

穿透：查的数据本来就不存在，缓存永远不命中，每次都打到数据库。先校验入参。确定没有的 key 缓存一个短 TTL 的空值，真实数据写进来时删掉这个空值。布隆过滤器说没有就可以直接返回；说可能有，仍然要查缓存和库。它挡的是大量不存在的 key，挡不住一个热点 key 过期。

击穿：热点 key 到期的那一下，大量请求同时回源。互斥锁让一个请求查库，其他请求短暂等待再读缓存。峰值上的热点可以用逻辑过期：先返回旧值，只放一个请求去刷新。

雪崩：大批 key 在同一时刻失效，或者 Redis 自己不可用，流量一起打到数据库。同一批写入的 TTL 打散。另外准备本地缓存、限流和降级，Redis 故障时先保住下单，关掉推荐这类非必要读。热点在峰值前预热。

### 12. Spring Bean 生命周期

**参考答案**

单例 Bean 从创建到可用，按这个顺序走：

1. 实例化，调用构造器。
2. 填充属性，完成依赖注入。
3. 回调 Aware：`BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。
4. `BeanPostProcessor.postProcessBeforeInitialization`。`@PostConstruct` 在这里执行。
5. `InitializingBean.afterPropertiesSet`，然后才是自定义 init-method。
6. `postProcessAfterInitialization`。AOP 代理通常在这一步包上去。
7. 放入单例池，之后被使用。

所以初始化的三个钩子顺序是 `@PostConstruct`、`afterPropertiesSet`、init-method。代理包在初始化之后；如果有循环依赖，提前暴露的时机会更早。

销毁顺序是 `@PreDestroy`、`DisposableBean.destroy`、自定义 destroy-method。原型 Bean 容器不负责销毁。`BeanFactoryPostProcessor` 改的是 Bean 定义，发生在任何 Bean 实例化之前，不要和 `BeanPostProcessor` 混在一起。

### 13. Spring 事务什么时候会失效

**参考答案**

`@Transactional` 靠代理生效。调用没有经过代理，或者异常没有按规则抛出代理，提交照常发生。

1. 同一个类里自己调自己，走的是 `this`，不进代理。要把事务方法拆到另一个 Bean，或者注入自身的代理再调。
2. 方法不是 public。默认的事务属性解析只认 public 方法。
3. 异常在方法内部被 catch 掉，代理看见的是正常返回，会提交。
4. 默认只在 `RuntimeException` 和 `Error` 时回滚。受检异常要写 `rollbackFor`。
5. 对象是自己 new 的，容器里没有代理。
6. 事务绑在线程的 ThreadLocal 上。方法里再开线程，新线程不在这个事务里。`@Async` 同样要单独经过代理才会有自己的事务。
7. 切面开了，但事务管理器绑的是另一个数据源，提交的库和你更新的库不一致。

代理生效之后，回滚的是抛出方法的那一次。内部已经 catch 住的失败，要手动设回滚标记。

### 16. 手撕算法：合并两个有序链表

**参考答案**

两条链表都按值升序。用一个哑结点当新链表的头，尾指针每次接上当前较小的节点，然后那条链表前进一步。一条先空了，把另一条剩下的整段接上，因为剩下的部分已经有序。相等时先接第一条，排序稳定。

空链表、只有一个节点，循环不会接错。时间 O(m+n)，迭代的额外空间 O(1)。递归每次选较小的头，栈深也是 O(m+n)。

```java
public ListNode mergeTwoLists(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0);
    ListNode tail = dummy;
    while (l1 != null && l2 != null) {
        if (l1.val <= l2.val) {
            tail.next = l1;
            l1 = l1.next;
        } else {
            tail.next = l2;
            l2 = l2.next;
        }
        tail = tail.next;
    }
    tail.next = l1 != null ? l1 : l2;
    return dummy.next;
}
```

### 2. 接着一面项目深挖，这个模块 QPS 上来后瓶颈在哪

### 3. 订单/优惠券/库存这类场景，并发扣减怎么保证不超卖

**参考答案**

超卖来自「先读剩余再扣减」不是原子操作。权威扣减放在数据库的条件更新上，Redis 只做热点前面的预扣。

库存用条件更新。影响行数为 0 就是不够。InnoDB 会把同一行的更新串成串行。

```sql
UPDATE sku_stock
SET available = available - ?
WHERE sku_id = ?
  AND available >= ?;
```

每次扣减带业务单号，对 `(sku_id, order_id)` 做唯一约束，重试不会扣第二次。

优惠券的批次剩余用同一条条件更新。每人限领用 `(user_id, batch_id)` 唯一索引挡住并发领取。核销写成 `WHERE status = unused`，重复核销不会再改一次状态。

订单和库存在同一个库时，建单和扣减放在一个本地事务里。不在同一个库时，Redis 预扣成功再投递建单；数据库失败要把预扣加回去，加回带同一个单号。热点 SKU 可以把库存拆成多段，段内仍然原子扣。所有请求共用一把分布式锁能避免超卖，锁本身会变成排队点。

已经超卖时先停售，再拿订单和库存对账。未支付的取消，已支付的走退款。

### 4. Redis 分布式锁怎么实现，过期时间设置和误删问题怎么解决

**参考答案**

加锁用一条带过期时间的原子命令，释放时先核对持有者再删除。过期用来避免死锁，持有者标识用来避免误删。

```text
SET lock:{biz} {requestId} NX PX {ttl}
```

`NX` 保证只有一个客户端能写入，`PX` 和写入在同一条命令里。先 `SETNX` 再 `EXPIRE`，进程死在两条命令之间，锁会没有过期时间。`requestId` 是这一次加锁的唯一值。

过期时间按临界区耗时的上限来定，并留余量。太短，业务还在跑第二个人就进来了。太长，持有者进程挂了，别人要干等。临界区可能超过 TTL 时，持有者还活着就续期；进程已经死了就不能续，让锁过期。

误删发生在锁过期之后：A 醒来执行 `DEL`，删掉的是 B 刚加上的锁。比较和删除放在一条 Lua 里。先 `GET` 再 `DEL` 中间仍然可能换人。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

长时间 GC 时续期线程也停着，Redis 侧的 TTL 照样减少。醒来后核对失败，就不要再改共享数据。库存、券额用数据库条件更新再挡一次「锁过期之后的写入」。主从异步复制时，主节点宕机也可能把锁丢掉，Redis 锁单独不是严格互斥。

### 5. Redisson 分布式锁相比自己写 setnx 有什么优势

**参考答案**

自己写的 `SET NX PX` 做到的是「带过期的互斥」。Redisson 把可重入、续期、原子释放和等待唤醒放进了同一套脚本。

锁在 Redis 里是一个 hash，field 是客户端加线程，value 是重入次数。同一线程再次进入只加次数，解锁减到 0 才删除。字符串锁没有重入，同一线程再申请会把自己卡住。

`lock()` 不传租期时，看门狗会在持有期间续期。Redisson 的默认租约是 30 秒，大约每 10 秒续一次，业务还在跑就不会因为固定 TTL 被抢走。进程停了，续期也停，锁仍会过期。调用时如果传入了租期，看门狗关闭，到点就释放，业务没跑完也会丢锁。

解锁仍然用 Lua 核对持有者，并通过发布订阅叫醒等待方。公平锁、读写锁它也提供。主从切换时锁可能丢，这一点和自己写的锁一样。库存正确性还是靠数据库条件更新，不靠这把锁单独保证。

### 6. MySQL 深度分页怎么优化，limit 100000,10 有什么问题

**参考答案**

`LIMIT 100000, 10` 要先扫过 100010 行，丢掉前 100000 行，再返回 10 行。代价随偏移变大，和本页只要 10 行无关。排序用的是二级索引、查询列又不在索引里时，被丢掉的那些行也会回表。翻页期间有插入和删除，offset 分页还会重复或漏行。

下一页用上一页最后的排序键做范围，代价和偏移无关：

```sql
SELECT * FROM orders WHERE id > #{lastId} ORDER BY id LIMIT 10;
```

排序键要能唯一定位。有相同键时再加上主键，避免翻页漏行。这种写法不能直接跳到第 10000 页。

必须保留偏移时，先用覆盖索引取出这一页的主键，再回表 10 次。索引里仍然要走过那些偏移，但不再把整行读出来：

```sql
SELECT t.*
FROM orders t
JOIN (
    SELECT id FROM orders ORDER BY id LIMIT 100000, 10
) x ON t.id = x.id;
```

产品上可以限制最大页数。任意深页的检索放到搜索引擎，用游标翻页。

### 7. 联合索引最左匹配原则，什么情况下索引会失效

**参考答案**

最左匹配看的是索引列的顺序。索引 `(a, b, c)` 可以从 `a`，或 `a、b`，或 `a、b、c` 开始用。`WHERE b = 2 AND a = 1` 仍然用到 `a` 和 `b`，条件在 SQL 里的书写顺序无所谓。

```sql
-- 索引 (a, b, c)
WHERE a = 1 AND b = 2   -- 用 a、b 定位
WHERE a = 1 AND c = 3   -- 只用 a 定位，c 用来过滤
WHERE b = 2             -- 一般不能用这棵索引定位
WHERE a > 1 AND b = 2   -- a 已是范围，b 不能再收窄扫描起点
```

`a` 变成范围之后，后面的列不能继续用来定位起点，索引条件下推仍可能用它们在回表前过滤。`b = 2` 这种跳过前导列的条件，MySQL 8.0.13 起在前导列取值很少时可能走跳跃扫描，这是例外。

下面这些情况优化器会用不上普通索引：索引列外面套了函数或计算（有对应的函数索引时除外）；字符串列和数字比较，列被转换成数字；`LIKE '%关键字'`。`OR` 的一侧没有索引时，可能整段改成全表扫描；两侧都有索引时可能走 index merge。

区分度很差或统计信息过期时，优化器可能仍选择全表扫描。这时 `possible_keys` 里有这棵索引，它是成本选择，索引本身还能用。用 EXPLAIN 看 `type`、`key` 和 `rows`。

### 8. 消息队列用过没，消费者重复消费怎么处理

**参考答案**

用过就点明中间件和那条链路。没上过生产就直接说，下面是通用做法。

重复来自两处：生产侧重试，以及消费成功之后确认失败、进程重启再次投递。常见语义是至少一次。处理完再确认：先确认再处理，进程挂了消息就丢了；处理完确认失败，就会再来一次。所以消费逻辑要能重复执行。

幂等放在数据库。消费记录和业务写入放在同一个事务里，对消息 id 建唯一索引。主键冲突说明已经处理过，直接返回成功。记录和业务分成两个事务时，可能记下「已消费」但业务没写上。

状态迁移写成条件更新，例如只有待支付才能改成已支付，重复消息不会再推进一步。Redis `SETNX` 可以挡掉键还在的那一段，过期或丢数据之后仍然靠唯一索引。

Kafka 打开生产者幂等，避免的是同一次生产会话里重试写出重复记录，消费侧仍要按业务键去重。RocketMQ 业务失败就稍后重试，多次失败进死信；进了死信也按同一条幂等逻辑补。

### 9. Kafka 和 RocketMQ 使用场景上你怎么选

**参考答案**

日志、埋点、流式计算，吞吐和堆积放在前面，用 Kafka。订单超时、支付后通知、要和本地事务一起成功，用 RocketMQ。

Kafka 分区内有序，消费组可以水平扩展，适合大流量管道。生产者幂等避免同一次会话里的重试写出重复记录。它的事务解决的是跨分区原子写入，不能把本地数据库提交和发消息包成一次提交。延迟和死信要自己用主题或时间索引做。

RocketMQ 面向业务消息。事务消息先写半消息，本地事务提交后再提交消息，状态不明就回查生产者。失败有重试和死信。4.x 的延迟是固定档位，5.x 才比较好做任意时刻。顺序消息按队列有序。日志管道的吞吐仍更适合 Kafka。

这条链路缺延迟、回查和死信，选 RocketMQ。缺的是海量堆积和流处理，选 Kafka。两个都没在线上用过，就按这个约束讲，把选型和「已经接入」分开。

### 10. 接口响应慢，从网关、服务、缓存、数据库、慢 SQL 怎么一层层排查

**参考答案**

先定范围：哪一个接口、从什么时候开始、是单机还是全部、P99 还是整段都慢、错误率有没有一起升。然后按调用链看时间花在哪一层，不先改 SQL。

1. 网关：对访问日志里的总耗时和上游耗时。总耗时长、上游短，时间在网关的鉴权、限流或 body 上。上游也长，就进服务。顺便看有没有超时重试把下游打得更慢。
2. 服务：用链路追踪看各 span。时间在业务方法里，就看锁、循环和序列化。时间在排队上，看 Tomcat 或业务线程池是不是满了。CPU 和 GC 一起高时，先看是不是停顿，再看代码。
3. 缓存：看命中率、Redis 慢日志和连接池等待。大 key、热点 key、`KEYS` 这类命令会让整段变慢。超时要和数据库耗时分开，避免把缓存故障记成慢 SQL。
4. 数据库：看连接池活跃数和等待时间。池是满的，先分清是 SQL 慢还是连接泄漏。再看行锁、元数据锁和主从延迟。
5. 慢 SQL：打开慢日志，对最慢的那条做 EXPLAIN，看 `type`、`rows`、是否回表、是否 `Using filesort`。函数套列、深分页、一次查出过多行，都在这里对上。

改完看同一条链路的分段耗时，确认时间从那一层掉下去。

### 11. 缓存和数据库一致性怎么保证，先删缓存还是先更新库

**参考答案**

旁路缓存的写路径是：先更新数据库，再删除缓存。

读的时候命中就返回；未命中查库，再把结果写入缓存。写的时候去改缓存，两个写并发，后完成的那个旧请求会把缓存写成旧值，库里已经是新值。删除缓存则下一次读会回源。

先删缓存再更新库，中间的读会把旧行装进缓存，库更新之后，缓存会在 TTL 内一直是旧的。先更新库再删除，窗口更窄：一个读已经拿到旧行，写提交并删了缓存，然后这个读把旧行写回去。窗口短，但存在。

删除失败要重试，或者订阅 binlog 再删一次。缓存保留 TTL，这次没删掉，旧值也会过期。写完立刻读从库再回填，会把从库上还没跟上的旧行写进缓存，写后的回源读主库。

延迟双删是更新库之后马上删一次，过一小段再删一次，用来盖住那个回填旧值的窗口。延迟时间不好估，binlog 删除更稳。要读到强一致结果的请求不走这套缓存。

### 12. Spring 如何解决循环依赖，三级缓存分别存什么

**参考答案**

Spring 对单例、并且是属性注入的循环依赖，用三级缓存提前交出一个还没初始化完的引用。构造器里互相依赖解决不了，对象还没构造出来，没有引用可交。原型也不进这三张表。

一级 `singletonObjects` 放已经初始化完成的单例。二级 `earlySingletonObjects` 放已经实例化、还没走完初始化、但是已经被提前取走的对象。三级 `singletonFactories` 放能生产这个早期引用的工厂。

A 依赖 B、B 又依赖 A：A 实例化后把工厂放进三级，注入 B 时转去创建 B。B 再注入 A，容器调用三级工厂，把早期引用放进二级，并去掉工厂。B 完成后进入一级，A 再完成进入一级。

三级放的是工厂，是为了 AOP。提前交给 B 的必须是最终那个代理，否则 B 里是原始对象，容器里是代理。工厂在真正发生循环时才做早期代理；没有循环，代理仍在初始化之后创建。只有两级的话，就得要么总是提前暴露原始对象，要么总是提前做代理。

Spring Boot 2.6 起默认不允许循环依赖，需要时打开 `spring.main.allow-circular-references`。允许之后，上面这套才工作。

### 13. JVM 内存区域说一下，Young GC 和 Full GC 区别

**参考答案**

线程私有的是程序计数器、Java 虚拟机栈、本地方法栈。栈帧里是局部变量和操作数栈，栈太深抛 `StackOverflowError`。每个线程一块栈，线程过多会把内存吃掉。

共享的是堆。分代收集里，年轻代是 Eden 加两块 Survivor，其余是老年代。对象一般在 Eden 分配。JDK 8 起类元数据在元空间，使用本地内存。直接内存也不在堆里。字符串常量池在堆上。

Young GC 在 Eden 放不下新对象时触发。把 Eden 和 From 里还活的对象复制到 To，年龄加一。年龄到阈值（默认 15），或者 Survivor 放不下，就晋升老年代；动态年龄判定会让一批对象更早晋升。停顿短，发生得勤。

Full GC 回收整堆，停顿通常长得多。触发原因包括老年代放不下、元空间要回收、晋升失败，以及显式 `System.gc`。JDK 9 起默认是 G1，正常的老年代回收很多是 Mixed GC，只选一部分老年代 Region。G1 的 Full GC 是整堆压缩的兜底。频繁 Full GC 先当异常查。线上如果是 ZGC，就改看 GC 日志里的暂停和分配速率。

### 14. 线上 CPU 飙高或频繁 Full GC，你的排查思路

**参考答案**

先分开两件事：业务线程在烧 CPU，还是 GC 线程在烧 CPU。

CPU 高时，先确认是这个 Java 进程，再看是用户态高还是等 IO 高。等磁盘就去看 IO。然后 `top -Hp` 找到线程，线程号转成十六进制，到 `jstack` 的 nid 里对上；Arthas 的 `thread -n` 可以少做换算。一个业务线程高，看死循环、正则回溯、热锁空转、大对象序列化。一排 GC 线程高，转到 GC。很多业务线程都高而且 QPS 也高，先确认是不是流量本身上来了。

频繁 Full GC 时，先看 GC 日志里的原因：老年代满、元空间、晋升失败、`System.gc`、G1 疏散失败。`jstat -gcutil` 看每次回收之后老年代掉不掉。掉得下去又很快涨满，是分配太快或晋升太多，查大对象和一次查出的数据量。掉不下去，是存活集太大或泄漏。在扛得住停顿时做 heap dump，用支配树看谁拽着大集合：无上限缓存、静态 Map、没清理的 ThreadLocal、类加载器泄漏。

泄漏改的是引用关系。堆小于存活集时才加大堆，先加大堆会把停顿拖长。直接内存打满不一定表现为堆上的 Full GC，用 native memory 的指标分开看。

### 16. 手撕算法：删除链表的倒数第 N 个节点

**参考答案**

题目保证 `n` 合法。用哑结点接在头前面，这样删头结点和删中间是同一段代码。快慢指针都从头前面出发，快指针先走 `n + 1` 步，中间隔着待删节点。然后一起走，快指针到空时，慢指针停在待删节点的前驱，把 `next` 跳过待删节点。

停在前驱，单链表才能删。只停在待删节点上，尾节点没有后继可以拷贝。一次扫描，时间 O(n)，额外空间 O(1)。先数长度再删是两次扫描，也对。

```java
public ListNode removeNthFromEnd(ListNode head, int n) {
    ListNode dummy = new ListNode(0);
    dummy.next = head;
    ListNode fast = dummy;
    ListNode slow = dummy;
    for (int i = 0; i <= n; i++) {
        fast = fast.next;
    }
    while (fast != null) {
        fast = fast.next;
        slow = slow.next;
    }
    slow.next = slow.next.next;
    return dummy.next;
}
```
