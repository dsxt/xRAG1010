### 3. Java 中线程有哪些状态？状态之间如何转换？

**参考答案**

结论：`Thread.State` 有六种：NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。就绪和正在执行都记为 RUNNABLE。

`start()` 使 NEW 进入 RUNNABLE，每个线程只能启动一次。进入 `synchronized` 时拿不到监视器，或者 `wait` 被唤醒后重新抢这把锁，状态是 BLOCKED，抢到后回到 RUNNABLE。`Object.wait()`、无超时的 `join()`、`LockSupport.park()` 进入 WAITING。`sleep`、`wait(timeout)`、`join(timeout)`、`parkNanos` 进入 TIMED_WAITING。`run` 结束进入 TERMINATED，没调用过 `start()` 的线程不会变成 TERMINATED。

`wait` 会先放开监视器再等待，`sleep` 和 `join` 仍握着已经拿到的锁。`ReentrantLock.lock()` 拿不到锁时走 park，线程显示 WAITING；带超时则是 TIMED_WAITING。BLOCKED 只出现在监视器竞争上。

### 4. synchronized 和 Lock（ReentrantLock）的区别是什么？在什么场景下你会选择使用 Lock？

**参考答案**

结论：两者都可重入、互斥。`synchronized` 由 JVM 在离开同步块时释放；`ReentrantLock` 要在加锁成功后的 `finally` 里按次数解锁，并提供中断、超时、公平策略和多个条件队列。

`synchronized` 锁的是对象监视器。偏向锁从 JDK 15 起默认关闭，现行 HotSpot 走轻量级锁，竞争失败再膨胀成重量级。它不能中断等待，不能限时获取，也没有公平排队；条件等待只有这个对象上的 `wait` / `notify`。同步块里抛异常，监视器仍会释放。

`ReentrantLock` 基于 AQS，默认非公平。构造参数传 `true` 才按队列顺序，公平锁吞吐通常更低。`lock()` 不响应中断，需要响应时用 `lockInterruptibly`。`tryLock(timeout)` 超时返回 false。无超时的 `tryLock()` 在锁空闲时会直接拿到，公平队列也拦不住这次插队。一把锁可以 `newCondition()` 出多组等待，`await` 期间会放开这把锁。

临界区边界清楚、只要互斥时用 `synchronized`。需要限时或可中断地获取，或者同一把锁上有「非空」「非满」这种不同条件时，用 `ReentrantLock`。加锁放在 `try` 外面，避免加锁失败仍去 `unlock`。

### 5. Spring 框架中，Bean 的实例化过程是怎样的？（结合生命周期谈谈）

**参考答案**

结论：实例化只是构造出对象；生命周期还包含依赖填充、初始化，以及容器关闭时的销毁。单例第二次 `getBean` 直接走单例池，不会再实例化。

单例首次创建的顺序是：

1. 按构造器或工厂方法实例化。构造器上的依赖在这一步注入。单例会在填充属性前暴露早期引用，字段和 setter 的循环依赖可以完成，构造器循环依赖不行。发生循环依赖且这个 Bean 需要代理时，提前暴露出去的应是代理，协作者注入到的才是最终对象。
2. 填充属性：`@Autowired` 字段和 setter、`@Value`。
3. 回调 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。
4. 前置处理里先完成 `ApplicationContextAware` 等回调，再执行 `@PostConstruct`。
5. `InitializingBean.afterPropertiesSet()`，然后是自定义 `init-method`。
6. 后置处理。AOP 代理多数在这一步包上，随后放入单例池。

容器关闭时，对已注册销毁回调的单例依次执行 `@PreDestroy`、`DisposableBean.destroy()` 和 `destroy-method`。prototype 每次新建，容器不负责收尾。

### 6. MySQL 的 InnoDB 存储引擎中，事务的 ACID 特性是如何通过日志（如 Redo Log、Undo Log）和锁机制来保证的？

**参考答案**

结论：原子性靠 Undo Log，持久性靠 Redo Log 的预写和刷盘，隔离性靠锁和 MVCC，一致性是约束加上这三件事一起成立后的结果。

事务进行中，页的修改先记进 redo。提交时默认把 redo 刷到磁盘（`innodb_flush_log_at_trx_commit=1`），数据页可以晚些再刷。崩溃后从检查点重放 redo，已提交的修改能找回来。这个值若改成 0 或 2，已提交事务在掉电时可能丢掉。页写到一半会损坏，双写缓冲先留一份页的副本，恢复时才能安全套用 redo。开启 binlog 时，InnoDB 先把事务准备好，binlog 写成功后再在 redo 里记提交；恢复按 binlog 决定提交还是回滚，主库和复制日志才对得上。

Undo Log 记录如何把改动倒回去，事务回滚用它。崩溃恢复在重放 redo 之后，把没有提交记录的事务用 undo 清掉。同一份旧版本也给 MVCC 用：行上有事务 id 和回滚指针，一致性读按 Read View 看该看的版本。RR 在事务第一次一致性读时建立 Read View，RC 则每条语句重建。

普通一致性读不加锁。`UPDATE`、`SELECT ... FOR UPDATE` 这类当前读才加锁。RR 下范围当前读使用 next-key 锁，把记录和前面的间隙一起锁住，避免别的事务往范围内插入。RC 下普通加锁多是记录锁。锁解决的是并发交错，崩溃后的原子恢复仍要靠 undo。

### 7. 在微服务架构中，如何保证服务之间调用的幂等性？请设计一个方案。

**参考答案**

结论：同一次业务请求执行多次，只生效一次，并返回同一份结果。靠业务幂等键和状态，靠调用方重试时沿用这个键。

调用方为每次业务生成稳定的幂等键，重试、超时后再调都带同一个键。服务端用数据库唯一约束占位，建议把键、请求摘要、状态和响应快照放在一张表里，状态分处理中、成功、失败。占位和业务写入放在同一个本地事务：插入成功才继续扣减、建单；唯一键冲突就查出原记录。已经成功则直接返回当时的响应。键相同而请求体不同，按冲突拒绝，避免把两次不同操作当成一次重放。

处理中要带租约时间。租约内的重复请求只告知进行中，不能再开一笔写入。租约过期后，同一个幂等键的重试可以接着做，但要先确认下游是否已经生效。Redis 的 `SET NX` 只能挡住短时间连点，驱逐或主从切换会丢，不能代替唯一约束。

跨服务的后续动作用本地消息表：业务事务里同时写下待发送记录，异步投递，消费者按同一个业务键去重。查询天然可以重复。创建、扣减、发券、发消息才走这套。网关上去重挡不住绕过网关的调用，写数据的那个服务才是边界。

### 8. 你如何理解 AI Agent？它和传统的 API 调用或任务调度程序的核心区别在哪里？

**参考答案**

结论：Agent 把「下一步做什么」交给模型：根据当前目标和工具结果选择动作，运行时执行并再喂回去，直到给出最终结果或碰到预算。API 由调用方指定操作；调度程序按时间或预先写好的 DAG 触发固定任务。

区别在控制流、停止条件和失败形态。同一次用户请求里，模型可能不调工具、调一次，或看完观察再调。路径可以变，所以服务端提供的是一组受约束的工具、步数、时间和费用上限。API 的契约是固定输入输出，一次调用对应一段确定代码。调度任务的分支写在程序里，到点就跑，通常没有「看结果再改计划」这一步。

失败也不一样。API 返回明确的错误码。模型可能选错工具、编造参数，运行时要在执行前校验，并把可理解的失败交回模型或直接结束。状态上，调度任务多是无对话的；Agent 要带着目标、历史和工具观察往下走。

路径事先能画完的流程，用普通工作流更合适。模型能改变控制流，并且系统能拦住越权动作，这套循环才和传统编排分开。

### 9. 在开发 AI Agent 时，你如何处理 LLM（大语言模型）输出的不确定性或幻觉问题？有什么工程实践？

**参考答案**

结论：模型输出当成提案。事实以工具和检索结果为准，格式用程序校验，会改数据的动作经服务端授权后才执行。

事实类问题走数据库或检索，回答带上出处。检索为空时直接说明没有依据，内部知识库的答案只引用这次取回的片段。工具参数按 schema 校验，枚举、范围、必填不对就把错误退回模型，并限制修正次数。金额、权限、删除、对外消息只允许模型提议，规则或人工确认后再落库，写入带幂等键。

输出分成两类处理。格式不稳用结构化输出或 JSON schema，非法就当失败。事实不稳靠证据和拒答，把温度调低只能让采样更集中，约束不了依据。关键不变量用确定性代码再查一遍，例如单号是否存在、日期是否合法。

评测集里单独放「库里没有答案」和「不该调用写工具」的样本。提示词里写「不要编造」没有执行层效力，只能作辅助说明。

### 10. 如果一个 Agent 需要调用多个工具（如搜索、查数据库、调外部 API），你如何设计它的工作流和控制逻辑？

**参考答案**

结论：运行时掌握循环，模型每一步只提案。互不依赖的只读工具可以同一轮并行；后一步依赖前一步结果的必须串行。写入工具单独管控。

每个工具登记名字、参数 schema、是否有副作用、超时和所需权限。循环里模型要么返回工具调用，要么返回最终答案。运行时解析后先校验，通过才执行，再把成功结果或缩短后的错误放回上下文。单步失败把可理解的原因交回模型，堆栈和内部地址留在日志里。

控制放在循环外：最大步数、总时限、token 预算，同一参数的重复调用直接复用上一次观察。搜索、查询这类只读调用可以并行，并给每一路单独超时。下单、扣款、发消息走白名单，执行前对权限和幂等键，必要时人工确认。部分成功要记在任务状态里，搜索已经完成、写库失败时，最终答复按这个状态说，避免报成全部完成。

步骤稳定的链路用固定图，例如先检索再作答。下一步确实依赖观察时，才把选择权交给模型。图和循环都要能从某一步失败处停下来。

### 11. 在 Agent 开发中，你如何实现上下文（Conversation Context）的管理和长期记忆？会用到哪些技术或组件？

**参考答案**

结论：上下文是这一轮窗口里的消息，长期记忆是窗口之外、按需取回的状态。全文记录、热窗口、摘要、结构化事实和向量召回分开存。

会话原文进数据库，作为可回放的来源。Redis 放最近若干轮和当前槽位，设置条数、大小和过期，服务重启后从数据库回填。每次调用按预算组装：系统提示和工具定义、尚未完成的任务槽位、本轮检索、最近原文，最后才是更早对话的摘要。超预算先压缩工具的长输出，再丢掉最早的原文。订单号、已确认的决定写成单独字段，摘要是有损的，不能只活在摘要句子里。

长期记忆只写确认过的事实：用户明确说过的偏好，或从可靠工具结果提取的字段，带上时间和来源，允许覆盖和删除。密码、密钥和一次性验证码不写入。向量库用来按语义找旧对话或旧工单，查询必须带用户和租户过滤，取回的片段当材料，关键事实以结构化表为准。

窗口管理在应用层做。模型进程本身不保留上一次请求的状态。

### 12. 手写算法：合并两个有序链表。

**参考答案**

结论：两条链表都按非降序排好。用双指针比较当前头，把较小的节点接到结果尾部，空的那条整段接上。时间 O(m+n)，迭代只改指针，额外空间 O(1)。

相等时先接第一条，合并是稳定的。两条都为空时返回空。递归写法复杂度同样是 O(m+n)，调用栈 O(m+n)，链表很长时用迭代。

```java
public ListNode mergeTwoLists(ListNode l1, ListNode l2) {
    ListNode dummy = new ListNode(0);
    ListNode tail = dummy;
    while (l1 != null && l2 != null) {
        if (l1.val <= l2.val) {
            tail.next = l1;
            l1 = l1.next;
        } else {
            tail.next = l2;
            l2 = l2.next;
        }
        tail = tail.next;
    }
    tail.next = (l1 != null) ? l1 : l2;
    return dummy.next;
}
```

`ListNode` 含 `val` 和 `next`。这里复用原节点，只重连 `next`。

### 4. 在项目中，你们是如何评估一个 Agent 的“好坏”或“有效性”的？有哪些评价指标？

**答题思路**

先定义这个 Agent 的成功，再讲你真实看过的指标。没用过的指标不要报成已经上线。数字只用你能对上的。

1. 成功标准：问答看依据是否支撑回答，办理看有没有在允许的步骤内做完。两类不要合成一个笼统的准确率。
2. 离线：固定样本看任务是否完成、工具和参数是否选对、该拒答的时候有没有拒答。样本里保留失败案例。
3. 线上：办成率或解决率、转人工、用户是否很快再次进来、首 token 和尾延迟、错误和超时、平均步数、每成功一次的 token 或费用。转人工下降时，要同时看重复请求有没有上升。
4. 安全单独看：不该执行的写操作有没有发生，检索有没有跨过权限。
5. 说清分母是全部会话，还是只统计自动处理的那部分。没有仪表盘，就讲你抽查失败会话的方法和看到的现象。

### 5. 当 Agent 需要访问内部知识库（例如通过向量数据库检索）来回答问题，这个 RAG（检索增强生成）流程你是如何设计和优化的？如何缓解“检索不到”或“检索不准”的问题？

**参考答案**

结论：先检索到可引用的片段，再让模型基于片段回答。检索为空就说明知识库里没有依据。权限过滤做在取近邻时，原文和向量分开存放。

入库时解析文档、去掉页眉页脚，按标题、段落、表格切块。表格带上表头，避免在句子中间硬截。块太大，一块里主题混杂；块太小，条件被切开。常见起步是按段落、几百 token、少量重叠，长度用召回评测调整。更稳的做法是小块负责召回，返回时带上父级段落。向量和文档 id、章节、租户、更新时间一起进索引，正文放数据库或对象存储。更换嵌入模型或距离度量就要全量重建，查询和索引必须用同一套。

查询先把对话里的「这个」还原成具体对象，再按租户和权限过滤并取近邻。错误码、单号、专有名词同时走关键词检索，和向量结果融合后再重排，只把前几段和出处交给模型。文档更新按文档 id 删掉旧块再写入。

检索不到时，先查索引是否过期、过滤是否过严、问法是否太虚，再用关键词和查询改写补召回。把相似度门槛一味放低，会把不相关片段放进提示词。检索不准时，靠元数据缩小范围、重排压掉噪声、父块补足上下文。评测看召回，以及引用是否真支持答案。

### 6. 如果 Agent 服务的 QPS 突然飙升，导致响应变慢甚至超时，你会如何排查和优化？可以从哪些层面考虑？

**参考答案**

结论：先分清是入口请求变多，还是每条请求里的模型步数、工具和重试把调用放大了。止损用限流和降级，再按饱和点优化。

看入口 QPS、进行中的请求、模型 QPS、429、端到端和模型的 p95/p99、线程池排队、连接池等待、检索耗时、错误率。用户量没涨多少而模型调用涨得更多，优先查步数变多、超时后的重试，以及缓存失效。客户端、网关、模型适配层如果同时重试，会把变慢放大成超时。

先保证服务还能拒绝多余流量：按租户限流，模型等待设队列上限，非核心工具关掉，必要时降到更小的模型或固定答复，并在响应里标明降级。有副作用的工具超时后，先按幂等键核对是否已经生效，再决定要不要重试。

优化按层做。相同且不随用户、时间变化的问答可以短缓存。只读工具并行，每路单独超时。缩短提示词和检索片段，记忆写入、摘要移出用户等待的路径。模型调用使用有界连接池，避免占满 Web 线程。无状态的接入和编排可以水平扩展；向量库、数据库和模型配额要单独看，入口扩容会把压力原样打到它们身上。

### 7. Redis 在你的项目中是如何使用的？除了缓存，是否用到了其他数据结构支持业务逻辑？举例说明。

**答题思路**

先说你项目里 Redis 承担的角色，再举两个你真写过的结构。下面只是对得上号才讲的例子，没用过的不要算进项目。

1. 缓存：说清 key 里有什么（租户、用户、问题或工具参数）、TTL、会不会缓存个性化或随时变化的结果。这种结果不适合按问句缓存。
2. 会话热数据：String 或 Hash 存最近消息和槽位，并说明重启后以数据库里的原文为准，Redis 过期只影响热数据。
3. 幂等或去重：`SET key token NX PX` 挡短时间重复提交。讲清数据库唯一约束仍是最终依据。
4. 限流：ZSET 滑动窗口或一段 Lua 令牌桶，强调判断和写入要原子完成。
5. 任务或事件：Stream 加消费组做异步步骤。讲一次至少投递，消费端如何按任务号去重。
6. 若用过分布式锁：锁有过期时间，value 是持有者 token，解锁时用 Lua 核对再删。锁过期而业务还在跑的情况要主动说明。

普通字符串结构不是向量索引。项目如果用了带向量检索的 Redis 模块，再单独讲索引和过滤；没有就不要把 Redis 说成知识库。

### 8. Kafka 或 RocketMQ 在你的系统中扮演什么角色？有没有用于解耦 Agent 执行过程中的某些步骤？

**答题思路**

先说明系统里用的是哪一个，还是这条链路目前是同步的。没有队列就直接说同步，把超时和重试讲清楚。

用过的话，按这四段挑你真实落地的讲：

1. 角色：削峰、解耦、异步任务，还是业务库和下游通知之间的缓冲。
2. 适合甩出在线请求的步骤：文档入库、会话摘要、评测、通知、用户不必守着的长任务。模型正在等待的工具结果仍走同步，否则一轮对话会变成跨多次消息的等待。
3. 顺序和投递：同一会话或同一任务用同一个分区键或消息组。常见语义是至少一次，消费端按业务键去重，失败进死信前要有次数上限。
4. 和本地事务的关系：RocketMQ 若用了事务消息，讲半消息、本地事务、提交或回滚。Kafka 若只是普通投递，就讲发送失败时本地消息表怎么补偿。两者的事务能力不一样，用过哪个讲哪个。

最后补一句怎么观察堆积：哪个消费组、延迟到了什么现象才告警。数字用你看过的。

### 9. 在微服务架构下，多个 Agent 之间如果需要协同完成一个复杂任务，你会如何设计它们之间的通信和协作机制？

**参考答案**

结论：用一个编排服务掌握任务状态、步数和预算。专家 Agent 只做窄步骤，通过结构化任务单协作。用户还在等待、且结果马上要进入下一步时同步调用；慢步骤走消息队列。

任务表记录目标、状态、当前步骤和产物 id。编排者按规则或一次路由决定下一个专家，专家是独立服务，只持有自己的工具。移交的内容是任务号、步骤号、目标、约束、输入引用和剩余预算，对话原文留在会话库里按 id 读取。专家把结果写回任务状态，不把完整聊天记录当作彼此的接口。

同步用 HTTP 或 gRPC，每跳有超时。文档处理、人工确认、批量动作发到 Kafka 或 RocketMQ，按任务号保序，消费者幂等。写数据只经过统一的工具网关，权限和幂等键在网关校验。专家之间不互相开放全部工具，避免成环调用。用最大跳数或一张允许的步骤图停住循环。

某一步超时就标失败，已完成的写操作按幂等记录保留，需要补偿或转人工时显式进入下一步。意图很少时，一个 Agent 加上分组工具就够用。拆成多个专家可以隔离权限、分开扩容，同时会增加延迟，移交时也可能丢掉约束。

### 10. 如何保证 AI Agent 系统的稳定性和可观测性？你做了哪些监控、告警和日志方面的设计？

**参考答案**

结论：一次用户请求一条 trace，模型、检索、工具各是 span。稳定性靠每条依赖的超时、隔离和降级；排障靠延迟、错误、token 和这一步有没有办成。

超时把连接、首 token 和总时限分开。模型、向量库、外部 API 各自用连接池和熔断，一个下游变慢不占满入口线程。循环有最大步数。失败时可以切到备用模型或固定答复，响应里标明降级，因为答案质量已经变了。客户端断开就取消上游生成。写工具只在核对幂等键之后重试。

指标看入口 QPS、进行中请求、端到端和各 span 的 p95/p99、超时、429、工具失败、检索为空的比例、平均步数、输入输出 token 和费用。日志用 traceId、sessionId、工具名和状态串起来。提示词和工具报文采样并脱敏，默认不在普通日志里落全文。

告警按错误率和尾延迟、模型 429、费用突增、工具成功率下降、检索为空比例突变、队列堆积来做，阈值跟自己的 SLO 走。只有进程存活告警，看见不了「还在回复但已经在胡编或烧钱」。抽查失败 trace 时，要能从 span 还原出每一步的工具和结束原因。

### 11. 谈谈你在学习一项新技术（比如年初的某个新 AI 框架或模型）时的路径和方法。如何快速掌握并判断其是否适合引入项目？

**答题思路**

讲你真的做过的一次学习，框架或模型用你读过文档、跑过实验的那个。没有就讲你准备怎么在当前项目里评估，不要编一段使用体验。

1. 从现有链路上一个具体问题开始：延迟、费用、检索不稳定、工具失败不好恢复。先说这个痛，再说新技术声称解决它的哪一段。
2. 路径按这个顺序：官方文档和最小可运行例子，弄清状态放在哪、失败怎么返回、怎么从现有 Java 服务里替换；再拿一组真实失败样本做对照。资讯只用来发现名字，结论回到文档和这次实验。
3. 判断看五件事：效果有没有好于现在的做法，尾延迟和费用怎么变，失败时行为能不能预测，能不能观测和回滚，换掉它要改多少调用方。
4. 实验限时。对上问题再灰度一条路径，旧实现留着可切回。对不上就停，把看到的差距讲出来。
5. 准备一个五分钟能讲完的例子：看了哪份文档，跑了什么样本，最后引进或放弃的理由。

### 12. 手写算法：二叉树层序遍历。

**参考答案**

结论：用队列做广度优先。每轮开始时队列长度就是这一层的节点数，按这个数量出队，并把下一层的孩子入队。时间 O(n)，队列最宽时约是最后一层的节点数，额外空间 O(n)。

根为空返回空列表。必须先记下当前层的个数，边出队边把孩子放进同一个队列；不记下个数，两层会混在一起。按深度递归、放进对应层的列表也可以，时间同样 O(n)，额外栈深是树高。

```java
public List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> ans = new ArrayList<>();
    if (root == null) {
        return ans;
    }
    Queue<TreeNode> queue = new ArrayDeque<>();
    queue.offer(root);
    while (!queue.isEmpty()) {
        int size = queue.size();
        List<Integer> level = new ArrayList<>(size);
        for (int i = 0; i < size; i++) {
            TreeNode node = queue.poll();
            level.add(node.val);
            if (node.left != null) {
                queue.offer(node.left);
            }
            if (node.right != null) {
                queue.offer(node.right);
            }
        }
        ans.add(level);
    }
    return ans;
}
```

`TreeNode` 含 `val`、`left`、`right`。只打印时，把每一层的 `level` 输出即可。
