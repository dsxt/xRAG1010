# 美团小象超市全栈开发偏后端一面面经

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试题

### 1. 自我介绍

**答题思路**

按「现在在做什么、做过哪一件和岗位相关的事、为什么投这个岗位」来说，控制在一分钟到一分半。

1. 开头只留身份和方向：年级或工作年限，主要写后端还是全栈。学校和专业点到即可。
2. 选一段真实经历展开：业务目标、你负责的链路、用过的存储或并发手段、结果。数字只说你记得住的数量级。
3. 收在岗位上：这个岗位偏后端，你准备把接口、数据和线上问题讲清楚。主动留下可追问的点，例如缓存、表结构或消息。
4. 有实习就放在项目前面，用一两句说明你写的是业务代码还是周边工作。

自我介绍里抛出的名词，后面都要能展开。没有做过的经历不要写进来。

### 2. 你现在是在腾讯实习吗？未来 offer 怎么选？

**答题思路**

两问分开答，都按事实说。

第一问用一句话给结论。如果确实在腾讯实习，说清业务方向、你写的模块、实习还剩多久，用做过的事说明，不靠团队名头。如果不是，直接说当前实习在做什么类型的系统；没有实习就说没有，把时间留给项目。

第二问先定比较的尺子，再谈结果。顺序可以是：业务是不是你想做的、后端代码是不是你能亲手写、能不能碰到并发和数据、城市和到岗时间你是否接受。薪资放进比较，但不要报具体数字，也不要编出几个不存在的 offer。还没有别的 offer，就说你现在的排序标准。

如果流程还没结束，告诉对方你的决策时间，并问这个岗位的业务和日常写什么，把选择标准和眼前这场面试接上。

### 3. 为什么你这个专业要找互联网工作？

**答题思路**

先讲专业给你的能力，再对到这个岗位，不要先否定专业。

1. 用一句大白话说这个专业训练你做什么。按你的真实课程说，例如建模、写程序、处理数据，不要临时换成另一个专业。
2. 这些能力和后端的交集：把业务规则做成可靠的数据和接口，出了问题能查。举一个你已经做过的例子，课程作业或项目都行，但必须是真的。
3. 为什么是互联网：系统有真实用户和迭代，你想把功能从需求做到线上。
4. 收束到这场面试：交易、履约这类系统要补的是并发、存储和排障。专业背景用来理解业务。

专业本身就是计算机的话，这题改成为什么做业务后端：你希望数据被真实请求打到，并愿意对正确性和故障负责。

### 4. CSS 匹配缓存怎么设计？

**参考答案**

结论：缓存的是「这个节点匹配到哪些规则」或「算完的样式」，键必须覆盖所有会影响结果的输入，失效宁肯扩大范围，也不能返回过期样式。

选择器匹配通常从右向左。规则先按最右端的 id、class、标签分桶，节点只查自己相关的桶。这是索引，还不是结果缓存。结果缓存再往上做。

键至少要包含：标签、id、class、被选择器读到的属性、内联样式、伪类状态（悬停、聚焦），以及样式表的版本号。样式会继承，所以还要带上父节点计算结果的标识，否则两个 class 相同、父级字体不同的节点会错共用一份样式。值做成不可变对象，相同键的节点共享，避免每个节点存一份拷贝。

失效按变更的影响面来。改 class、id、属性，标脏这个节点；样式表增删，提升全局版本。后代、相邻兄弟、`:nth-child` 这类选择器会波及兄弟和子树，精确集合算不清时就扩大失效。祖先的 class 可以用布隆过滤器快速拒绝「祖先一定没有这个特征」的规则：过滤器只有误报，没有漏报，拒绝不了再做精确匹配。

只按 class 做键、或者样式表改了还不换版本，是最常见的错。同步读计算样式时，失效必须发生在这次读取之前。

### 5. 什么是 Copy-On-Write 操作？

**参考答案**

结论：读者继续使用旧副本，写者先复制再修改，最后用一次发布替换引用。读路径不和写者互相阻塞，写路径要保证两个写者不会各写各的。

`CopyOnWriteArrayList` 把数组放在 volatile 引用里。`get` 不加锁，读到的是当时那份数组。`add`、`set` 先拿锁，复制出新数组，改完再把引用拨过去。volatile 写保证读者能看到完整的新数组。迭代器拿的是创建时的数组，不会抛并发修改异常，也看不到迭代开始之后的写入。`addIfAbsent` 这种封装好的方法在锁里完成；业务自己先 `contains` 再 `add`，中间仍然会插进别的写。

操作系统里 `fork` 是同一件事：子进程先共享页，某一页被写时才复制那一页。Redis 用 `fork` 做后台快照，父进程在这期间写得越多，内存涨得越多。

它适合读多写少、数据量不大的场景。数组一大、写又频繁，每次复制的 CPU 和内存都会成为成本。写者之间的锁还在，Copy-On-Write 去掉的是读者的锁。

### 6. AI 项目高并发怎么做？

**参考答案**

结论：模型调用又慢又贵。高并发要限制同时打到模型上的请求，让等待发生在有界队列里，而不是把服务线程和显存一起堆满。

1. 接入层按用户和接口限流。超过配额快速失败，避免客户端重试把下游再打一遍。
2. 接请求的线程和调用模型的线程分开。容器线程不要同步堵在几秒的推理上。请求进入有界队列，独立的调用池去打模型网关。池的大小对齐模型服务给的并发额度，不对齐入口 QPS。
3. 流式输出会长时间占着连接。连接数可以很多，模型侧的并发仍然要小。两套额度不要混成一个数。
4. 队列满了就拒绝或降级。降级可以是可复用的缓存结果、更小的模型，或明确告诉用户稍后。相同且允许复用的请求才能缓存；带隐私或必须实时的请求不要为了命中率去缓存。
5. 超时、熔断、有限次重试要一起配。超时之后先确认下游是不是还在算，再决定重试。
6. 自建推理可以用连续批处理提高 GPU 利用率。显存接近上限时延迟会陡增，准入控制仍然要有。

限流配额要和供应商或 GPU 的真实并发一致。应用侧线程池开得很大，只是把排队从队列搬到了模型外面。

### 7. 线程池设计需要注意什么？

**参考答案**

结论：线程池同时限制并发和排队。只加大核心线程、队列又不设上限，任务会先把内存堆满。

参数按这个顺序定：有界队列、最大线程数、拒绝策略、线程名字和异常处理。核心线程处理常态流量，队列吸收短尖峰，最大线程应对更长的尖峰，再超出就拒绝。`AbortPolicy` 把失败抛给调用方；`CallerRunsPolicy` 让调用线程自己跑，适合作为反压。调用线程如果也属于这个池，就不能再用调用者执行，否则池满时自己等自己。

`Executors` 里的固定池使用无界队列，最大线程数实际不起作用；缓存池几乎不排队，线程数会随任务涨。生产上这两类默认都不适合直接拿来用。

CPU 计算和等数据库、等模型的任务拆开。慢 IO 占满线程后，计算任务没有线程可用。池的上限还要受下游连接数约束。

另外几件容易漏：提交进池的任务不要再同步等待同一个池的结果。`execute` 抛出的异常进未捕获处理器，`submit` 的异常藏在 `Future` 里，没人调用 `get` 就像成功了。池线程会复用 `ThreadLocal`，用完要在 `finally` 里 `remove`。关闭时先停止接收新任务，再等待已有任务结束。

池的大小没有通用最优值。CPU 密集从核数附近试，IO 密集看下游超时和连接。上线后看队列长度、活跃线程和拒绝次数再调。

### 8. 什么时候用锁？什么时候不用？

**参考答案**

结论：锁保护的是一段必须一起完成的共享可变状态。一个变量上的原子更新用原子类；跨字段的不变式用锁，或者收成一个对象做一次原子替换。

要用锁的情况：先检查再修改，几个字段必须一起变，或者条件不满足时要等待。锁要盖住这些读写。临界区里不要做远程调用，否则占锁时间取决于下游。两把锁的获取顺序要固定。

可以不用锁的情况：状态只活在一个线程里；对象构造完成后不再改，并且已经安全发布；大家只是各自累加一个计数；读的是一份不会再改的快照。`volatile` 保证这个变量的读写可见，不保证自增这种读改写是原子的。

并发容器的单个方法是原子的。「没有这个键才放入」要放进 `compute` 这类一次完成的方法里。两次调用之间，别的线程仍然进得来。

读写锁适合读远多于写、临界区又比较长的场景。临界区很短时，读写锁自己的开销可能盖过收益。公平锁能避免饿死，吞吐通常更差，默认用非公平。

### 9. 原子变量是什么？

**参考答案**

结论：原子变量用 CAS 在一个变量上完成读改写，失败就重试。它保证的是这一个变量的原子性，不是一段业务逻辑的原子性。

`AtomicInteger` 的值是 volatile 的。`incrementAndGet` 在比较并交换上循环，并发自增不会丢更新。对一个 volatile 的 `int` 做 `++`，读和写仍然是分开的，会丢更新。

CAS 有 ABA：值从 A 变成 B 又变回 A，只比较值看不出中间被动过。需要识别这种情况时用带版本号的 `AtomicStampedReference`。高争用的纯计数可以用 `LongAdder`，它把增量拆到多个单元上。并发更新的同时调用 `sum`，得到的不是一个严格的瞬间快照。

两个字段要同时成立时，不要各放一个原子变量分别改。把它们做成一个不可变对象，对引用做一次 CAS，或者直接用锁。原子变量也没有「条件不满足就等待」，那种需求是锁和条件队列。

### 10. 数据库表结构怎么设计？

**参考答案**

结论：先写清谁写入、按什么查询、哪些字段不能错，再定表。没有访问路径，表结构没有对错。

1. 一笔业务事实放主表，当前状态和过程流水分开。不要把每次变更都堆进同一行的大字段。
2. 主键用稳定、不会被业务修改的单号或代理键。会变的字段不要当主键。没有主键时，InnoDB 会自己生成隐藏行号，二级索引也会更长。
3. 金额用整数分或 `DECIMAL`，不用浮点。状态用有限枚举。事件发生时间和入库时间分开。
4. 唯一约束表达业务不变量，例如支付单号不能重复。这是正确性，不是普通二级索引能替代的。
5. 索引跟着 `WHERE`、`JOIN`、`ORDER BY` 建。等值、区分度高的列放在联合索引前面。不要给每一列都建索引。
6. 大文本和列表查询用不到的字段拆出去，避免把大列读进缓冲池。为了少做连接而冗余的字段，要说清由哪次写入维护。

面试时拿一张核心表按写入、查询、不能错的字段讲。范式用来检查更新异常，本身不是目标。

### 11. 如何保证消息顺序？

**参考答案**

结论：消息队列保证的是单个队列内部的追加顺序，不是全局顺序。要保的是同一笔业务的先后，就让这批消息只进一个队列，并且按这个顺序处理。

以 Kafka 为例，相同的业务键哈希到同一个分区，分区内 offset 递增。生产侧如果允许重试，同时在途请求又大于 1，后发的批次可能先写入。打开幂等后，生产者按分区分序列号，在途请求不超过 5 时，同一个生产者实例在这个分区上的顺序能保住。两个实例同时发同一个键，broker 只按到达顺序追加，业务顺序仍然可能乱。

消费侧一个分区在同一个消费者组里只交给一个消费者。处理时不要再把这个分区丢进线程池并行，否则分区有序就没了。要并行，就按业务键拆到不同分区，分区内部仍然串行。某个消息失败时，不要先提交它后面的位点。

只关心同一订单的状态时，消息里带单调版本号，落库条件写成版本更大才更新。旧消息晚到直接丢掉。这比全系统挤进一个分区更常见。RocketMQ 的顺序消息也是同一套：按键选一个队列，这个队列单线程消费。

### 12. 数据量大怎么办？

**参考答案**

结论：先分清大在行数、单行大小还是访问量。顺序是少读、少留在在线库、再拆开。没有一个固定行数到了就必须分库。

1. 查询先看是不是扫得太多。补上匹配条件的索引，列表不要 `SELECT *`。深分页改成记住上一页的主键，再向后扫，避免每次丢掉前 N 行。
2. 在线库只留热数据。历史订单按时间归档。大字段拆到另一张表，详情页才去读。
3. 读多写少时，用从库分担读。复制有延迟。刚写完就要读到的状态，尤其是钱和库存，读主库。
4. 单库的容量或写入确实不够，再按查询里总会带上的键分片，例如用户或门店。跨分片查询和跨分片事务要单独设计，这是分片的主要代价。
5. 缓存只挡住热点读。行数变多这件事，不会因为前面加了 Redis 就消失。

判断依据是慢查询、缓冲池命中和磁盘，不是一个通用的行数门槛。如果对方说的是消息堆积，那是消费速度和分区数的问题，不是先把数据库拆开。

### 13. 索引什么时候会失效？

**参考答案**

结论：多数人口中的失效，是优化器没法用这个索引缩小查找范围，或者估算下来全表扫描更便宜。索引对象还在。用 `EXPLAIN` 看 `type`、`key` 和 `rows`，再判断是写法问题还是统计信息问题。

写法上对不上索引的情况：

1. 索引列上套了函数或运算，例如 `DATE(create_time)`、`id + 1 = 10`。普通 B+ 树不会自动变成表达式索引；要走索引，就改写条件，或给这个表达式单独建索引。
2. 比较时发生在列上的隐式转换。字符串列和数字比较，会先把列转成数字，索引用不上。数字列和字符串常量比较，通常转的是常量，索引还可以用。
3. `LIKE '%abc'` 这种前导模糊。`abc%` 可以用普通索引。
4. 联合索引不满足最左前缀。`(a, b, c)` 上只查 `b`，用不上。`a` 等值、`b` 范围时，`c` 不能再缩小查找范围，只可能作为索引条件下推来过滤。MySQL 8.0 的跳跃扫描只在前导列区分度很低等少数情况下出现，不能当成可以随便跳过第一列。
5. `OR` 两边不是都能用索引时，常常整句改走全表。两边都可以用时，有机会做索引合并。

不等于、`NOT IN` 不必然放弃索引，匹配行太多时优化器会改走全表。`IS NULL` 在 InnoDB 里可以使用索引。统计信息过时时，优化器会选错，需要更新统计信息，不是把索引删了重建当常规手段。

### 14. 为什么用 MQ？

**参考答案**

结论：消息队列用来把「必须现在做完」和「可以稍后做完」拆开。它提供解耦、异步和削峰，不提供请求内的强一致。

下游各自消费，短时不可用不会把主接口拖死，这是解耦。用户要等的路径里只留必须同步完成的事，通知、检索更新、积分放到消息后面，这是异步。入口的尖峰先堆在队列里，消费者按自己的容量处理，这是削峰。队列会涨，要有堆积告警，也要知道消费速度能不能在可接受的时间内追上。

代价是消息会重复、会延迟，顺序默认只在单个队列内成立，链路上多了一套要监控的组件。调用简单、用户必须立刻看到结果时，同步调用更合适。钱和库存的状态以数据库为准，消息负责通知后续动作，不把队列当成账本。

### 15. 如何保证消息不丢？

**参考答案**

结论：发送、存储、消费三段都要确认成功。端到端通常做成至少一次，再用业务幂等去掉重复，而不是默认存在恰好一次。

生产者要等 broker 确认。Kafka 把 `acks` 设为 `all`，并且 `min.insync.replicas` 至少为 2，否则 `all` 可能只代表 leader 自己写下了。副本数通常大于这个最小值，未跟上的副本不要当选 leader，避免确认过的消息在切换后消失。`acks=all` 保证的是副本收到记录，不是每个副本都已经刷到磁盘；所有副本同时掉电，尾部仍可能丢。发送超时要当成结果未知，可能已经写入，所以重试必须带业务幂等键。

业务库和消息要一起成功时，用本地消息表：业务数据和待发送记录放在同一个事务里，后台再投递，失败就重试。这样不会出现「库提交了但消息没发出」或「消息发出去了但事务回滚了」。

消费者处理成功后再提交位点。自动提交可能在处理前就前进，处理失败等于这条消息被跳过。崩溃发生在处理之后、提交之前，消息会再来一次。消费侧用业务唯一键挡住重复。Kafka 事务能覆盖「从 Kafka 读、再写回 Kafka」这条链路，跨到数据库时仍然要本地消息表或幂等。

### 16. MVCC 原理？

**参考答案**

结论：InnoDB 的普通查询读的是事务开始时已经提交的版本，版本存在聚簇索引和 undo 里。它让一致性读不加行锁，写和当前读仍然要加锁。

每一行聚簇记录带最后修改它的事务号和回滚指针。修改时把旧版本写进 undo，指针串成版本链。没有主键时，InnoDB 会用第一个非空唯一索引，再不行就生成隐藏行号。

一致性读会建一个 Read View：创建时还活跃的事务集合、当时的高水位。判断某个版本可不可见的规则是：自己写的可见；快照时已经提交的可见；快照时还没提交、或者快照之后才开始的事务，不可见，就顺着 undo 找更老的版本。读已提交是每条语句一个 Read View，所以别的事务提交后，下一条语句能看见。可重复读是事务里第一次一致性读建立 Read View，之后复用，普通查询不会看见别人后来提交的修改。

`SELECT ... FOR UPDATE`、普通的 `UPDATE` 和 `DELETE` 是当前读，读最新提交版本并加锁，不走这套快照。可重复读下，范围当前读还要加间隙锁，避免别的事务把新行插进这个范围。普通 `SELECT` 看不到幻行，靠的是快照；当前读防幻读，靠的是锁。

长事务会一直握着 Read View，purge 不敢删掉它还需要的 undo，回滚段会涨。MVCC 去掉的是一致性读的行锁，不是写入的锁。

### 17. 手撕代码：LeetCode K 个一组翻转链表

**参考答案**

从前往后每数出 k 个节点就原地反转这一组，接回前一组的尾巴。不足 k 个的尾部保持原顺序。用哑节点承接头节点本身被换掉的情况。

每一组先从当前前驱走 k 步。走不到就结束。走得到，就把这一段的 next 指针反过来，反转时让这段的新尾巴指向下一组的头。然后前驱指向这段的新头，前驱再移到这段的新尾巴，也就是反转前的第一个节点。

每个节点入组、反转各常数次，时间是 O(n)。只用几个指针，额外空间是 O(1)。递归写法每组一层栈，空间是 O(n / k)。

```java
public ListNode reverseKGroup(ListNode head, int k) {
    ListNode dummy = new ListNode(0);
    dummy.next = head;
    ListNode prev = dummy;

    while (true) {
        ListNode end = prev;
        for (int i = 0; i < k && end != null; i++) {
            end = end.next;
        }
        if (end == null) {
            break;
        }

        ListNode start = prev.next;
        ListNode nextGroup = end.next;
        ListNode cur = start;
        ListNode pre = nextGroup;
        while (cur != nextGroup) {
            ListNode nxt = cur.next;
            cur.next = pre;
            pre = cur;
            cur = nxt;
        }

        prev.next = end;
        prev = start;
    }
    return dummy.next;
}
```

`ListNode` 就是通常的 `val`、`next`。k 为 1 时每一组只有一个节点，反转后链表不变。面试时先讲「数满 k 个再反转，不满就停」，再写指针，最后用 4 个节点、k 为 2 走一遍：头会换成原来的第 k 个。

### 18. 是否接受北京/上海？

**答题思路**

先给明确结论，再给一个真实约束。

接受就说接受哪一个，以及你什么时候能到。两个都接受，也说一个优先顺序。不接受就直接说，并说明你能接受的城市。

约束只讲事实：实习什么时候结束、能不能线下、生活上是否已经有安排。没有约束就不要编故事。可以补一句你同时看业务和团队，但能不能到这个城市，答案本身要明确。

### 19. 是否接受写 Java？

**答题思路**

这个岗位偏后端，先说愿不愿意写 Java。

愿意的话，按你的实际情况选一档，不要报高：

1. 已经在写：说明你写过的范围，例如接口、数据库、并发。没写过的部分不要说成熟练。
2. 可以转：说明哪些能力能直接搬过来，例如 HTTP、SQL、事务和基本并发模型，以及你准备先补的 Spring 和 JVM 基础。只说你已经开始做的那一部分。

不愿意就直说，并问这个组的日常语言是不是只有 Java，把预期对齐。

### 20. 对于 AI 焦虑的讨论

**答题思路**

这是交换看法。按「你怎么看、你怎么做、你想听对方怎么做」来说。

1. 看法：模型会写样板代码，线上的正确性、数据和故障仍然要人负责。把焦虑放在自己会不会只会调用工具，而不是放在一个替代时间表上。
2. 做法：说一件你真的在用的方式，例如读代码、补测试、查报错。关键设计、表结构和边界条件要能自己讲出来。没有做过的 Agent 项目不要临时编一个。
3. 把问题递回去：团队现在用在什么环节，哪些代码可以起草，哪些必须人复核。

不要贬低模型，也不要把这个岗位说成很快会被写代码工具吃掉。

## 反问

### 1. 部门业务技术挑战？高并发 + 资金安全

**答题思路**

这题用来听清这个组难在哪。问法可以是：新人进来，前几个月最常碰到的技术问题是什么。原帖记下的回答是高并发和资金安全。对方如果提到这两项，各追问一层；对方没提，就不要替对方假定。

高并发追问峰值在下单、库存还是查询，同步链路有多长，超过容量是排队、限流还是直接失败。资金安全追问哪一类账不能错，重复请求靠什么挡住，账对不上时谁发现、多久能发现。

你要听的是约束和责任边界。回答很虚时，可以再问最近一次线上问题是什么。不要在反问里展开一套自己没做过的架构。

### 2. 有没有着手做 AI 应用？发票识别 / 小助手

**答题思路**

先问有没有已经在用的应用，而不是问公司怎么看大模型。原帖记下的方向是发票识别和小助手，可以据此准备追问；对方没提，就不要假定这两项已经落地。

发票识别追问输入是拍照还是电子发票，识别错了是人工改还是直接入账，模型结果外面有没有校验。小助手追问它是查文档，还是能改订单和库存。能写业务数据的，要问失败和越权由谁兜底。

听完用来判断你是接现成链路，还是从零开始试。你没做过识别，就不要把反问拐成自己的项目介绍。

### 3. 如何看待 AI 时代的学习路径？不用焦虑，跟趋势

**答题思路**

适合问团队希望新人把学习时间花在哪。原帖记下的态度是不用焦虑、跟着趋势。可以顺着要一个具体例子：最近在跟的趋势，是业务系统里的哪项能力，还是模型应用；希望新人先补业务，还是先补模型。

自己的态度用一两句说完：主线是把数据、接口和故障弄懂，工具用来加快阅读和验证。不要报一个编出来的周计划或课程清单。对方如果只停留在口号上，就收住。
