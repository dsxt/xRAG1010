### 3. JavaScript 中，var、let、const 的区别是什么？谈谈你对作用域和暂时性死区的理解。

**参考答案**

`var` 是函数作用域，声明提升后会初始化为 `undefined`，同一作用域可以重复声明。在非模块的浏览器脚本里，顶层 `var` 还会变成全局对象的属性。`let` 和 `const` 是块级作用域，进入块就会留下绑定，但在声明语句执行前处于暂时性死区，读取会抛 `ReferenceError`。它们不能在同一作用域重复声明，也不会挂到全局对象上。`const` 必须在声明时赋值，这个绑定不能再指向别处；对象和数组的内容仍然可以改。

作用域从外到内是全局或模块、函数、块。模块里的顶层 `var` 也只属于模块，不会变成 `globalThis` 的属性。暂时性死区和“变量不存在”不同：未声明的名字做 `typeof` 得到 `"undefined"`，死区里的 `typeof` 会直接抛错。

`for (var i)` 整个循环共用一个绑定，回调读到的是最终值。`for (let i)` 每次迭代一个新绑定。`for (const x of list)` 可以，因为每次迭代是新绑定；`for (const i = 0; i < n; i++)` 不行，因为 `i++` 要改绑定。

### 4. 说说你对闭包的理解，它有哪些应用场景？使用不当可能会导致什么问题？

**参考答案**

闭包是函数记住定义时的词法环境，并在外层调用结束后继续访问其中的绑定。函数被创建时就带有这个环境；只有被内层实际用到的绑定才需要留下来，引擎可以不保留没用到的外层变量。

常见用途：

- 工厂函数把计数、缓存放在外层，只返回操作方法。
- 柯里化和偏应用，把已确定的参数留在外层。
- 防抖、节流把定时器 id 留在闭包里。
- 回调、事件处理拿创建当时需要的状态。

问题出在引用的寿命，不在“函数套函数”本身。定时器、全局变量或 DOM 事件如果一直抓着闭包，闭包里的大对象和 DOM 节点就回收不掉。循环里用 `var`，所有回调共享一个绑定，看到的是最后一次赋值。异步回调还会读到过期值：请求回来时，外层变量已经变成新的了。清理方式是取消订阅、清掉定时器，并避免用一个长寿命回调抓住整棵大对象。

### 5. 浏览器从输入 URL 到页面展示，具体发生了什么？尽可能详细地描述。

**参考答案**

按导航、连接、解析、渲染讲。前进或后退有时会从往返缓存整页恢复，包括 JS 状态，那一次不会重走网络。

地址先判断是 URL 还是搜索。站点在 HSTS 列表里时，HTTP 会升级成 HTTPS。没有 Service Worker 时，先看 HTTP 缓存：`max-age` 未过期可以直接用；`no-cache` 表示可以存，用之前要向服务器验证。带内容哈希的文件再标上 `immutable`，新鲜期内就不再发条件请求；文件名变了就是另一个资源。有 Service Worker 控制该页时，请求先进入它的 `fetch`，由它决定读 Cache、走网络，或两边组合。

要联网就做 DNS：浏览器缓存、操作系统缓存和 hosts，然后才是递归解析。能复用连接池就复用。HTTP/1.1 和 HTTP/2 的新连接走 TCP，HTTPS 再做 TLS。TLS 1.3 的完整握手一般一个往返，有会话票据时可以恢复。HTTP/2 在一条连接上多路复用。HTTP/3 走 QUIC（UDP），传输握手和 TLS 合在一起。请求会按域、路径和 `SameSite` 带上 Cookie。遇到重定向就换目标再请求：307、308 保留原来的方法，302 在浏览器里常常被改成 GET。

HTML 边下边解析，生成 DOM。预加载扫描器会提前发现后面的 CSS、脚本和图片并开始下载；解析被脚本堵住时，扫描器仍能先把后面的资源拉下来。CSS 组成 CSSOM，不阻止解析器继续读 HTML，但渲染要等它。没有 `async` 或 `defer` 的经典脚本会停住解析，下载并执行完再继续；排在样式表后面的这种脚本，还会等 CSS 下来，因为它可能读样式。`defer` 并行下载，文档解析完按顺序执行；`async` 下载完就执行，顺序不定。`type="module"` 默认按推迟执行。

可见节点和 CSSOM 合成渲染树。`display: none` 不进这棵树；`visibility: hidden` 仍占布局。接着布局算几何、绘制记录指令、合成把层交给 GPU。已经独立成层的元素，改 `transform` 和 `opacity` 通常只走合成；改宽高会从布局重来。

`DOMContentLoaded` 在文档解析完、推迟执行的脚本跑完后触发，不等图片，也不等 `async` 脚本。挡住脚本的样式表会让同步脚本和这些推迟脚本一起等待，事件跟着晚。`load` 才等待图片等子资源。LCP 可能落在这两个事件之间。

### 6. 前端性能优化有哪些常见的实践？请从网络请求、资源加载、渲染等不同层面举例。

**参考答案**

先有 LCP、INP、CLS 或接口耗时，再改。没有基线就不知道哪一层在慢。

网络请求：文本用 Brotli 或 gzip；图片给合适的格式和尺寸。互相独立的接口并行发，重复请求合并。带内容哈希的静态资源做长时间强缓存，HTML 入口用短缓存，发布后才能指到新文件。关键域名用 `preconnect`。HTTP/2 已经多路复用，再把资源拆到很多域名，常常只增加连接成本。

资源加载：关键 CSS 尽早到达，脚本用 `defer`，路由和重模块用动态 `import`。首屏 LCP 图不要懒加载，并写上宽高，避免出来时把版面顶下去；折线下的图再用 `loading="lazy"`。用打包分析看体积，大库按需引入，去掉没引用的依赖。

渲染：长列表做虚拟化，只挂可见节点。连续读布局又写样式会强制同步布局，先把读完再写。动画优先改 `transform` 和 `opacity`。大计算拆开或放到 Worker，避免长任务挡住输入。INP 差时，拆开点击之后的长任务；只压首屏体积盖不住输入延迟。

### 7. CSS 中，如何实现一个元素的水平垂直居中？至少说出三种方法。

**参考答案**

父元素要有可分配的高度，否则垂直方向没有剩余空间，看起来会像没有生效。题目是一个元素时，下面几种都能用。

Flex。未知子元素尺寸也可以。单个子项还可以只设 `display: flex`，再给子项 `margin: auto`。

```css
.wrap {
  display: flex;
  justify-content: center;
  align-items: center;
  min-height: 100%;
}
```

Grid。一个子元素时，容器就是一格，`place-items` 同时管两个方向。多个子元素会各自在自己的格子里居中。Flex 在主轴上是把这一组一起摆到中间。

```css
.wrap {
  display: grid;
  place-items: center;
  min-height: 100%;
}
```

绝对定位加位移。子元素不必先有宽高。父元素要是定位包含块。这里的 `transform` 会生成层叠上下文，也会成为固定定位后代的包含块。只是为了居中时，优先用 Flex 或 Grid。

```css
.item {
  position: absolute;
  left: 50%;
  top: 50%;
  transform: translate(-50%, -50%);
}
```

四边拉满再让自动外边距分剩余空间。这条要求子元素有明确的宽和高；宽度不写时，左右为 0 会把元素拉满，水平方向就没有剩余空间。

```css
.item {
  position: absolute;
  inset: 0;
  width: 120px;
  height: 40px;
  margin: auto;
}
```

### 8. Vue/React 中，组件间通信有哪些方式？（根据你简历的技术栈选择其一）

**参考答案**

面试只展开简历上的那一个栈。父子用数据向下、事件向上；跨很多层再考虑注入；远距离、多处读写的客户端状态才进全局 Store。

Vue：

- `props` 向下，`emit` 向上。`v-model` 是这两件事的约定。
- 父组件用模板 ref 调用子组件 `expose` 出来的方法。
- `provide` / `inject` 适合主题、表单这类跨层上下文。提供一个 `ref` 或响应式对象，注入方才能跟着变；提供一个普通数字，之后再改外层局部变量，注入方看不到。
- 插槽和作用域插槽把数据和展示拆开。
- 远距离共享用 Pinia。Vue 3 去掉了实例上的 `$on`，再用事件总线就要自己引入库，订阅关系不直观。
- 页面之间用路由参数。

React：

- `props` 和回调。兄弟组件把状态提到最近的共同父级。
- Context 做跨层数据。`value` 每次都是新对象时，消费者会一起渲染；稳定数据和高频数据分成不同 Context。
- `ref` 加 `useImperativeHandle` 暴露少量命令式方法。
- `children`、render props 或组合组件做扩展点。
- 远距离客户端状态用 Redux 或 MobX。接口数据放请求缓存，不塞进全局 Store。

能用状态提升解决的共享，先不要上全局状态。`provide` / `inject` 和 Context 传递的是数据，不是任意事件通道。

### 9. 谈谈你对前端工程化的理解，你们项目是如何进行构建、部署的？

**参考答案**

工程化是把开发、检查、构建、发布变成仓库里可重复的流程，减少靠人记步骤。

开发侧锁定依赖版本，用环境变量区分环境，业务代码按模块而不是按个人目录堆。质量侧把 ESLint、类型检查和测试放进 CI，提交前的检查只是提前失败。生产构建做压缩和按路由拆包，静态资源文件名带内容哈希。Source map 上传到错误平台，不对公网目录开放。

部署时 CI 把带哈希的资源上传到 CDN，这些文件可以长期缓存。HTML 入口用短缓存，用户下一次才能拿到指向新资源的入口。回滚就是切回上一份入口，并保留对应的旧资源。发布要能灰度，出问题能退回。

讲自己的项目时按「本地一条命令、CI 做什么、产物在哪、怎么回滚」说，工具名只用你用过的。没做过发布就说负责到构建产物，后面的人怎么接，不要补一段没参与的流水线。

### 10. 你了解哪些前端监控方案？一般会关注哪些核心指标？

**参考答案**

线上监控一般同时收错误、性能、接口和资源。只挂一个 `window.onerror` 会漏掉资源失败和未处理的 Promise。

JS 异常听 `window.onerror` 和 `unhandledrejection`。资源失败要在捕获阶段听 `error`，因为图片、脚本的错误不冒泡；这类事件没有 `message`，目标是元素本身。跨域脚本要带 `crossorigin`，响应也要允许跨域，否则只能拿到 `Script error`。Vue 3 的 `app.config.errorHandler` 能接到渲染、侦听器、生命周期和事件处理函数里的异常。React 的 Error Boundary 管子树渲染，事件处理和异步回调还是要自己捕获。白屏要另做：入口脚本没执行时，框架的错误回调不会运行，可以用一个很小的超时检查根节点有没有内容。

性能用 `PerformanceObserver` 或 web-vitals 采 LCP、INP、CLS。实验室里的 Lighthouse 代替不了真实用户；INP 需要真实交互。接口包一层 `fetch` 或 XHR，记状态码和耗时。

上报要采样、去重，并带发布版本，Source map 才能对上。页面进入后台时用 `sendBeacon`。SPA 的路由切换要自己记访问，否则次数里只有首屏。监控本身会占带宽和主线程，所以要有采样。

核心看三类：稳定性是 JS 错误率、接口失败率和白屏；体验是 LCP、INP、CLS；业务是关键路径有没有走完。

### 11. 手写算法：实现一个函数，将数组 [1, [2, [3, 4], 5], 6] 扁平化，并去重排序。

**参考答案**

用显式栈做深度优先展开，避免层级很深时递归把调用栈撑满。数组如果引用了自己，用一个 Set 记住已经展开过的数组。值再用一个 Set 去重，最后按数值排序。示例的结果是 `[1, 2, 3, 4, 5, 6]`。

扁平化本身每个元素进出栈一次，是 O(n)。排序是 O(n log n)，总时间以排序为准，空间 O(n)。默认的 `sort()` 按字符串比较，`10` 会排在 `2` 前面，所以比较函数用减法。`0` 会被保留；去重用的是 `Set`，`NaN` 也只会留一个。环境支持时，`list.flat(Infinity)` 再放进 `Set` 再排序可以得到同样的结果；下面这版把过程和环处理写明。

```javascript
function flattenUniqueSort(list) {
  const values = [];
  const seenValues = new Set();
  const seenArrays = new Set();
  const stack = [list];

  while (stack.length > 0) {
    const current = stack.pop();
    if (Array.isArray(current)) {
      if (seenArrays.has(current)) continue;
      seenArrays.add(current);
      for (let i = current.length - 1; i >= 0; i -= 1) {
        stack.push(current[i]);
      }
    } else if (!seenValues.has(current)) {
      seenValues.add(current);
      values.push(current);
    }
  }

  values.sort((a, b) => a - b);
  return values;
}
```

去重发生在排序之前，最终顺序由比较函数决定，展开顺序不影响结果。题目给的是数字；如果数组里还有对象，Set 只按引用去重，减法比较也不再有意义，要先约定比较规则。

### 12. （场景题）如果用户反馈页面打开非常慢，你的排查思路是什么？

**参考答案**

先把“慢”量化，再决定时间花在网络、资源还是主线程。

1. 复现：哪个页面、第一次打开还是再次打开、什么网络和机型、是不是只有一部分用户。对照监控里的 LCP、INP、接口耗时和错误率，确认是普遍变慢还是个案。
2. 看瀑布：DNS、连接、TTFB、下载体积、请求是否串成链、缓存有没有命中。TTFB 高，先查服务端和地域，压前端包解决不了这一段。
3. 看资源：有没有同步大脚本挡住解析，包里有没有没用到的库。找到 LCP 元素，看它是图还是文字，以及它在等 CSS、等接口还是等自己的文件。
4. 看主线程：Performance 里看长任务、强制布局、一次渲染过多节点。交互慢时看输入到下一次绘制，不只看首屏。
5. 一次只改一个主要因素，用同一指标对比。缓存、拆包、并行请求、虚拟列表，都要能说清对应的是哪一段耗时。

返回该页可能走往返缓存，和冷启动不是同一条路径。用户机器上的扩展也会让同一页面变慢，个案要看环境和现场录制。

### 4. Vue 的响应式原理是如何实现的？（或 React 的 Fiber 架构和 Diff 算法是如何工作的？）

**参考答案**

这题按简历二选一，讲透一个。两套机制不要混在同一次回答里。

Vue 2 用 `Object.defineProperty` 把对象上已有的属性改成 getter 和 setter。读取时把当前 Watcher 记进这个属性的依赖，写入时通知它们。初始化时会递归遍历。新增属性、删除属性，以及通过下标改数组，都不走已经装好的 setter，所以 Vue 2 要 `Vue.set`，并改写 `push`、`splice` 等变异方法。

Vue 3 用 `Proxy` 代理整个对象。`get` 里 `track`，`set` 和 `deleteProperty` 里 `trigger`，因此新增、删除和下标都能收集。依赖关系是「对象 → key → 订阅者」，用 `WeakMap` 挂在对象上，对象回收后依赖可以一起回收。原始值不能被 `Proxy` 代理，用 `ref` 包一层 `.value`。模板里，以及作为响应式对象属性时，ref 会自动解开。`computed` 懒求值并缓存，依赖变了才标脏。组件里的多次修改进入同一个异步队列，在微任务里刷新；`nextTick` 排在这次 DOM 更新之后。

从 `reactive` 对象上解构出来的字段是当时的值，要 `toRefs` 才继续响应。组件里的 `watch` 默认在渲染前执行，回调里还读不到这次更新后的 DOM，要读 DOM 就用 `flush: 'post'` 或 `nextTick`。

React 把每个组件写成一个 Fiber 节点。节点用 `child`、`sibling`、`return` 串起来，并用 `alternate` 指向另一棵树上的对应节点。`current` 是已经提交、正在显示的树，`workInProgress` 是正在计算的树。屏幕上一直是 `current`，算到一半的那棵不会被画出来。

渲染阶段从根向下：处理当前节点，再协调它的子节点，回升时补宿主节点的 DOM 信息。`createRoot` 打开并发渲染后，这一阶段按优先级执行，调度器通过宏任务切时间片，时间用完可以让出主线程，没提交的 `workInProgress` 可以丢掉重来。优先级用 lane 表示，用户输入高于 `transition`。

DOM 变更和 `useLayoutEffect` 在绘制前同步做完。`useEffect` 排到绘制之后。已经进入提交的这一轮会做完。Diff 只比较同一层。类型不同就卸掉旧子树、装上新的；类型相同就复用并更新属性。列表用 key 认身份：两端能按顺序对上的先复用，中间剩下的旧节点放进 key 映射再取。同一层是线性扫描，复杂度 O(n)，移动次数不必是理论最少。会变化的下标不适合当 key，否则节点复用后状态会串。Hooks 按调用顺序存在 Fiber 的状态链表上，条件分支里增减 Hook 会把状态错位。需要在绘制前读布局并改 DOM 时用 `useLayoutEffect`。

### 5. Vue 3 的 Composition API 与 Vue 2 的 Options API 相比，有什么优势和设计上的不同？

**参考答案**

Options API 按 `data`、`methods`、`computed`、`watch` 这些选项类型组织。一个功能的状态和逻辑会散在不同选项里，复用常靠 mixin。mixin 的字段来源不直观，同名还会互相覆盖。`this` 指向组件实例，选项合并也让类型推断更绕。

Composition API 在 `setup` 里按功能写。相关的状态、计算和副作用放在一起，再抽成 composable。`setup` 每个组件实例执行一次，生命周期通过 `onMounted` 这类函数注册，不依赖每次渲染都按同一顺序调用。`<script setup>` 里的 `defineProps` 和 `defineEmits` 是编译宏。类型可以直接从参数推出来。复用是普通函数，依赖写在参数和返回值上。

它主要改善组织、复用和类型。更新性能来自 `Proxy`，以及模板编译的静态提升和补丁标记；Options API 和 Composition API 在 Vue 3 里都能走到这套编译。简单组件用选项写仍然清楚。`setup` 如果堆成一个长函数，就要按功能拆出去。响应式是显式的：解构成普通变量会丢掉响应，副作用要在 `onUnmounted` 里取消。

### 6. 前端状态管理你是怎么做的？在什么情况下你会选择引入 Vuex/Pinia 或 Redux/MobX？

**参考答案**

状态放在离使用它最近的地方。组件自己的输入和开关留在组件里；兄弟要共享，就提到共同父组件。多处远距离读写、并且属于客户端状态时，再引入 Store。

接口数据用请求库做缓存、失效和重试。放进 Vuex 或 Redux 之后，加载、过期和页面局部状态会缠在一起，失效还要再写一套。

- Pinia 是 Vue 3 的常规选择。它没有 Vuex 那种单独的 mutation。action 里可以同步或异步改状态，组件也可以直接改 store 上的字段。可以按业务拆多个 store，类型直接写在 state 上。
- Vuex 是单一状态树，同步走 mutation，异步走 action。已有模块可以继续用，新的 Vue 3 代码更适合 Pinia，不必为了换库重写整棵旧状态树。
- Redux 是单一 store，reducer 是纯函数，副作用放在中间件或 Redux Toolkit 的 `createAsyncThunk`。更新路径清楚，适合要追溯“谁改了状态”的多人项目。`useSelector` 默认按引用比较。选择器每次返回新对象时，一次无关的 store 更新也会让组件重渲染。订阅最小的数据，或自己比较结果。
- MobX 把数据做成可观察对象，渲染时收集用到的字段，改了就通知。代码短，依赖是跑起来才确定的，约定要严，否则难追是谁改的。

Store 解决共享和追溯，不解决组件边界。一个页面里的临时态放进全局之后，这个页面就难拆出去。

### 7. 你如何管理一个大型前端项目的代码结构和团队协作规范？

**参考答案**

目录按业务域切，一个功能的页面、组件、接口和状态放在一起。共享 UI 和工具才进公共目录。依赖只允许页面向功能模块、功能模块向共享层。用 ESLint 的导入限制把反向引用挡在 CI 里。多个应用共享设计系统和工具时再上 monorepo；只有一个应用时，多包管理会先变成发布成本。

协作规范写进仓库：格式化、类型检查、提交说明、PR 需要哪些检查。公共组件要有使用说明和变更记录。接口类型从约定生成，避免手写一份、后端改一份。设计用 token，颜色和间距不散落在业务样式里。

发布公共包时固定版本和变更说明，业务应用显式升级，不在锁文件里飘着一个随时变的最新版。

面试按「目录怎么切、依赖方向怎么挡、一条改动怎么进主干」讲。只讲自己维护过的那一层；没定过规范，就说你在团队规范里怎么落地，例如补过哪类检查。

### 9. 谈谈你对 Serverless 和 SSR 的理解，它们在前端领域带来了哪些变化？

**参考答案**

这两件事不在一层。SSR 是渲染方式：服务端先输出 HTML，浏览器再 hydrate 成可交互页面。Serverless 是部署方式：函数按请求拉起，空闲可以缩到零，按调用计费。SSR 可以跑在常驻 Node 上，也可以跑在函数里。

SSR 让用户更早看到正文，爬虫拿到的也是内容。服务端要跑同一套框架，先把数据取好并注进页面，还要处理 hydrate 时客户端算出来的结果和服务端 HTML 不一致。页面因人而异时，HTML 很难共用缓存，首字节时间会回到服务器。内容不常变的页面，更适合构建时生成，或过期后再生成。

Serverless 让 BFF、渲染函数和轻量接口可以按请求扩缩，不用先申请一台长期机器。冷启动会加进一次请求的延迟。本地磁盘和进程内存不能当成下次请求还在的状态。协同编辑这种长连接需要专门的连接层，不适合放进一次请求就结束的函数。

首屏慢先分清是 TTFB、资源体积还是主线程。SSR 把渲染成本搬到服务器，仍然用 TTFB 和 LCP 看它有没有变好。

### 10. 你如何看待现在各种低代码平台和 AI 编程助手（如 GitHub Copilot）？它们会改变前端开发的工作模式吗？

**参考答案**

低代码把表单、列表、审批这类结构稳定的页面收成配置，适合中后台和活动页。交互一复杂、视觉一偏离组件，配置就会变成另一种难调试的程序。引入前要看三件事：能不能写自定义组件逃出配置、配置怎么做版本和回滚、出了问题能不能定位到一次渲染。

AI 编程助手擅长补全、样板、测试草稿和机械重构。它没有业务约束。生成结果要过类型检查、安全检查和代码评审。用户内容进 HTML、鉴权、重复提交，是最容易被生成代码漏掉的地方。

工作模式会变：重复页面和重复样板变少，方案、接口契约、状态边界和验收变多。团队如果没有统一的目录、组件和请求方式，生成得越快，风格越散。这两类工具都吃掉一部分重复劳动；线上结果仍然由写进仓库、能回滚的那套工程负责。

### 11. 手写算法：实现一个简单的模板引擎函数 render(template, data)，将模板中的 {{name}} 替换为数据对象中对应的值。

**参考答案**

扫一遍模板，用正则找出 `{{name}}`，允许花括号内侧有空白。名字只取数据对象自己的属性，避免读到原型上的 `toString`。缺字段、`null` 和 `undefined` 换成空串；`0` 和 `false` 要保留，不能用真值判断把它们丢掉。替换结果里即使还有 `{{name}}` 也不再展开，避免值把模板再次执行。

时间是模板长度 O(n)，每个占位符取值 O(1)，空间是结果字符串 O(n)。这是文本替换。结果若要插入 HTML，再对 `& < > " '` 做转义；转义不属于这道题的替换本身。更完整的引擎会编译成函数，不可信模板不能交给 `new Function` 或 `eval`。

```javascript
function render(template, data) {
  const source = data == null ? {} : data;
  return template.replace(/\{\{\s*([A-Za-z_$][\w$]*)\s*\}\}/g, (_, key) => {
    if (!Object.prototype.hasOwnProperty.call(source, key)) return '';
    const value = source[key];
    if (value == null) return '';
    return String(value);
  });
}
```

`render('Hello {{ name }}', { name: 'Ada' })` 得到 `Hello Ada`。`render('{{count}}', { count: 0 })` 得到 `0`。如果面试官接着问 `{{user.name}}`，按点拆开逐级取值，中间遇到空引用就停，返回空串。

### 2. 如果让你从零设计一个类似腾讯文档的在线协同编辑应用的前端架构，你会考虑哪些核心问题和关键技术选型？

**参考答案**

核心是并发修改怎么收敛，同时光标、权限和历史还跟得上。文档以操作同步，而不是每次把整篇内容覆盖上传。

纯文本和富文本可以选 OT 或 CRDT。OT 由服务端给出唯一顺序，客户端把并发操作变换到这个顺序上；富文本的变换函数很难写对。CRDT 保证并发操作合并后收敛。基于操作的实现通常仍要按因果顺序送达，不能把任意乱序都当成合法，重连时用 state vector 交换双方缺失的更新。OT 则用服务端版本号补操作。有账号、权限和历史时，服务端仍是权威：非法操作在广播前丢掉。编辑器侧用成熟的 CRDT 或 OT 库，自己写传输、权限和光标映射。

体验上先在本地应用操作，再等确认。远端操作要映射到本地光标，而不是把编辑器内容整体替换掉。光标和选区走单独通道，丢一帧可以接受；文档操作要可靠、有序。撤销是这个用户自己的操作栈，按操作来源过滤，不能把别人刚写的字弹掉。

渲染和协同分开。大文档按块增量更新，长文只挂可见块。服务端存快照加操作日志，用来做打开速度、历史版本和审计。选型上，离线编辑多、结构复杂，优先成熟 CRDT；模型简单且服务端强定序，OT 更直观。工作量在编辑器内核、位置映射、重连和权限，不在从零发明一套变换。

### 3. 前端如何保证应用的安全性？请谈谈你了解的常见攻击（如 XSS、CSRF）和防护手段。

**参考答案**

权限和数据校验以服务端为准。前端要做的是不把攻击面做大，并用浏览器提供的机制补一层。

XSS 是页面把不可信内容当成代码执行。存储型来自已经存下来的内容，反射型来自这次请求被拼进响应，DOM 型来自前端自己把 `location` 之类的输入写进 HTML 或脚本。Vue 和 React 默认按文本转义。风险集中在 `v-html`、`dangerouslySetInnerHTML`、`innerHTML` 和拼接 URL。文本用 `textContent`。必须渲染富文本时，用维护中的消毒库按白名单处理。转义还要看上下文：HTML 正文、属性、URL 和脚本里的规则不同。CSP 限制脚本来源，作为兜底；它替代不了转义。Cookie 加 `HttpOnly`，页面脚本就读不到会话。`postMessage` 要校验来源。

CSRF 利用浏览器自动带上的 Cookie：别的网站可以发起请求，用户的登录态会一起过去。`SameSite=Lax` 时，跨站表单提交和子资源请求不带 Cookie，顶层的 GET 跳转仍会带，所以改数据的接口不能做成 GET。`Strict` 连跨站进来的顶层跳转也不带，从外部点进已登录页面时要重新建立会话体验。需要跨站携带时用 `SameSite=None` 并且 `Secure`。状态变更再校验 CSRF token 或自定义请求头，并核对 `Origin`。自定义头会触发跨域预检，别的源发不出来，除非服务端主动放开。鉴权若只放在 `Authorization` 头里、不放在 Cookie 里，浏览器不会自动带上，经典 CSRF 就不成立；这个头仍然怕 XSS 把它读走。

另外几件要一起做：用 CSP 的 `frame-ancestors` 限制被嵌套，防止点击劫持；跳转目标用白名单，避免开放重定向；密钥和会话签名放在服务端。CORS 放松的是浏览器的同源限制，服务器仍然要鉴权。`Access-Control-Allow-Credentials: true` 时不能把允许源写成 `*`。

### 4. 当项目需要引入一个全新的技术栈（如从 Vue 切换到 React，或引入一个新的图形库）时，你会如何评估和推动落地？

**参考答案**

先写清现有栈挡死了什么：性能、招聘、生态，还是能力做不到。说不清这一条，就继续用现栈。换图形库是加一个依赖；从 Vue 换到 React 是两套运行时，成本不是同一量级。

评估用能验证的项：体积和运行时、要支持的浏览器、类型和测试能不能接上、许可证、维护是否还活跃、和现有构建的配合、团队学会要多久。图形库再加内存、事件模型和可访问性。每个候选用同一个小场景试，比较这些项，不用“生态更好”这种说法结案。

落地先选一条非核心路径，写好成功标准，例如开发耗时、体积和缺陷数。换框架按页面或子应用切开，一块业务只留一个框架。公共视觉收成不依赖框架的样式约定，业务组件允许有两份薄封装。微前端适合独立发布的边界；同一页里嵌两套框架，会同时付样式、路由和体积的成本。

推动时给出试点数据和停损条件：做到哪一步、哪项指标没达到就停。规范放在仓库的例子里。新页面要能把流量切回旧实现。

### 7. （AI 相关问题）现在 AI 能力越来越强，比如可以直接根据设计稿生成前端代码。你认为在未来，前端工程师的核心价值在哪里？会不会被 AI 工具所替代？

**参考答案**

设计稿生成代码，替代的是“已知组件怎么翻译成模板”这一段重复劳动。前端的核心价值是：在不完整的需求里定交互和边界，把性能、权限、异常、可访问性收进可发布的工程，并在线上对结果负责。

模型可以给出一个看起来完整的页面，但不知道它要和哪条接口、哪套权限、哪种空数据放在一起。生成结果要人审查：状态全不全、提交会不会重复、用户内容有没有进入 HTML。这些判断依赖产品和系统上下文。

工作会往上移一层：信息架构和交互、前端架构、设计系统，以及把生成代码约束在同一套目录、组件和请求方式里。纯按稿改样式、补样板会变少。会把工具用起来，并且能把结果收进可回滚工程的人，会接住原来只做翻译的那部分工作。线上出错时，仍然要有人能定位和回滚。

### 8. 你如何看待业务需求和技术追求之间的平衡？举个例子。

**答题思路**

先说原则：期限是约束，技术选择服务于这次交付的风险。现有能力能按期交付，就先交付，并写下还债条件。若要让需求停下来等架构，就要说得清用户侧的损失。

例子按这个形状讲，项目用你自己的：

1. 需求是什么，什么时候用户要能用。
2. 理想方案是什么，它哪一块赶不上这次期限。
3. 你实际做了什么缩小版，守住了哪条底线，例如数据正确、可回滚或基本性能。
4. 什么信号出现就补上，例如数据量、投诉或某项指标。

形状可以是：列表本周要上，完整虚拟化来不及，先分页并限制首屏节点数，把滚动卡顿的阈值写进后续事项。讲的时候换成你真实的取舍。

### 9. 手写算法：给定一个字符串，请你找出其中不含有重复字符的最长子串的长度。

**参考答案**

用滑动窗口。右端逐个纳入字符，窗口 `[left, right]` 始终没有重复字符。用 Map 记每个字符上次出现的下标。右端字符如果在窗口内出现过，就把左端移到上次位置的下一位。左端只前进。上次出现在左端左边时，说明已经出窗，左端不动。

每个下标最多进出一次，时间 O(n)。Map 的大小不超过不同字符数，空间 O(min(n, 字符集))。空串返回 0。`"abcabcbb"` 是 3，`"pwwkew"` 是 3，`"bbbbb"` 是 1。这里按 JS 的 UTF-16 码元滑动，和字符串下标一致。

```javascript
function lengthOfLongestSubstring(s) {
  const last = new Map();
  let left = 0;
  let best = 0;
  for (let right = 0; right < s.length; right += 1) {
    const ch = s[right];
    const prev = last.get(ch);
    if (prev !== undefined && prev >= left) {
      left = prev + 1;
    }
    last.set(ch, right);
    const len = right - left + 1;
    if (len > best) best = len;
  }
  return best;
}
```

`"abba"` 可以检查左端会不会退回去：处理到最后一个 `a` 时，它上次出现在下标 0，已经在窗口外，左端应停在第二个 `b`，长度是 2。若看到重复就把左端设到 `prev + 1` 而不比较 `prev >= left`，左端会退回，窗口里重新纳入重复字符。

## HR面

### 1. 请做一个简单的自我介绍。

**答题思路**

少用术语，一分钟到一分半。

1. 你是谁，做前端多久，最近在做什么类型的产品。
2. 一件具体的事：你的职责、和谁配合、做成了什么。
3. 为什么看机会，和你理解的这个岗位怎么对应。
4. 项目名和数字与简历一致，语气平稳。

### 2. 为什么选择腾讯？对我们部门有了解吗？

**答题思路**

1. 业务：点一个你用过或认真看过的公开产品，说明它和你想做的前端问题哪里重合，例如复杂交互、性能、内容或协同。
2. 部门：面试前看这个部门对外的产品和方向。了解到哪说到哪。没确认的内部情况留到反问，不要背官网介绍。
3. 个人：你哪一段经历能迁过来，例如 C 端性能、中后台或组件建设。
4. 收在你希望负责的工作内容。

城市、业务方向如果是真实原因，可以直接说，再用一条技术原因说明你能贡献什么。

### 3. 你过往经历中，最有成就感的一件事是什么？

**答题思路**

选一件和岗位相关、你本人动作清楚的事。用 STAR，一两分钟。

1. 背景：当时要达成什么。
2. 你的动作：你判断了什么、推动了谁、写了或改了哪一层。
3. 结果：上线范围、故障、耗时或协作方式，用你能对上的事实。
4. 为什么有成就感：难在判断或协调，而不只是加班做完。

团队的结果要说出你那一段。没有的数字不要补。

### 4. 你遇到过最大的挫折或失败是什么？你是怎么应对和走出来的？

**答题思路**

选一件已经结束、你自己有责任、后来行为有变化的事。

1. 当时的目标。
2. 哪一个判断或动作错了，后果是什么。
3. 你怎么补：复盘、改流程、补验证或重新对齐预期。
4. 后来遇到类似情况，你怎么做。

失败要具体到一个决定。还在抱怨某个人、或者把“我太追求完美”当成挫折，都听不出你处理问题的方式。

### 5. 你未来的职业规划是怎样的？

**答题思路**

1. 近一两年：把一类前端问题做深，例如复杂交互、性能或工程化，能独立把一块功能从方案带到线上。
2. 再往后：能负责一个业务的前端结构和质量，让规范落在仓库里，而不只停在分享。
3. 和这个机会的关系：产品有真实用户和复杂界面，适合把上面的能力用在具体业务上。

管理如果要提，放在你先把技术判断和项目交付做好之后。规划里不要把这份工作说成短暂停靠。

### 6. 你如何看待团队合作？如果和同事或上级意见不一致，你会怎么处理？

**答题思路**

1. 先对齐目标和约束，把分歧写成选项：对用户、进度、风险各有什么影响。
2. 事实用数据和复现说话。属于偏好时，就承认是偏好，找一个小范围试。
3. 和上级不一致：把风险讲完，由负责人拍板。决定之后按决定执行。
4. 涉及线上正确性或合规：把风险留在书面记录里，同时给出你能接受的替代。

例子的形状：你认为该先修稳定性，对方要先上功能。你给出影响范围和最小修复时间，约定功能带开关上线，指标一过线就停。换成你自己的事。

### 7. 你目前有其他公司的面试或 Offer 吗？如果都有，你会如何选择？

**答题思路**

如实说进度。没有就说没有。还在流程里，就说哪个阶段，不把面试说成 Offer。

都有 Offer 时，按这个顺序选：业务内容、你能负责的范围、团队协作方式、技术是否匹配，然后是城市和薪酬的整体。薪酬是因素之一；对方没问具体数字，就不要主动报一串比较。

还在等结果时，说出你做决定需要的时间，并问对方的流程节点。不要用还没拿到的 Offer 抬价。

### 8. 你有什么问题想问我的吗？

**答题思路**

准备两个你真的关心、而且前面还没被回答的问题。

- 这个团队接下来半年最想解决的前端问题是什么？
- 新人怎样算度过试用期，预期先负责哪一块？
- 前端和产品、设计、后端怎么定接口和排期？

少问公开渠道已经写明的福利清单。对方反过来问你的选择时，用你已经确认的公开信息接，不要装作了解内部架构。
