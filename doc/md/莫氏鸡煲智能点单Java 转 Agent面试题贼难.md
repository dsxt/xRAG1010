## 一面

### 1. 自我介绍

**答题思路**

控制在 1～2 分钟，按「身份 → 技术栈 → 最相关的项目 → 为什么匹配」说：

1. 一句话说明 Java 后端年限，以及最近在做 LLM 应用或 Agent 落地。
2. 技术栈按岗位相关度排：Java / Spring Boot、MySQL、Redis、消息队列，再是工具调用、RAG、会话状态。
3. 只展开一个最接近「交易链路 + 模型」的项目：业务问题、你负责的模块、你真实有的结果。数字用自己的，没有就讲现象和改法。
4. 收在匹配点：订单、库存、幂等、超时这些后端能力，正好用来把点单 Agent 做稳。

简历上的名词不要铺开，把时间留给追问。

### 2. 讲一个你做过的 AI Agent / RAG / 智能体项目，核心解决了什么业务问题

**答题思路**

按「问题 → 为什么用模型 → 你做了什么 → 结果」讲，核心是业务问题。

1. **问题**：谁在用，原来靠人工还是固定表单，痛在漏单、答错、处理慢，还是知识找不到。一句话说清成功标准。
2. **边界**：哪些步骤是确定流程（查价、创建订单），哪些交给模型（口语理解、缺槽追问）。说明整段都交给模型会在哪里出事。
3. **你的部分**：意图和槽位、工具封装、会话状态、检索、幂等、人工兜底，只讲真正负责的。团队做的和自己做的分开。
4. **结果**：用真实指标，例如自动完成率、人工接手率、错单或投诉的变化。没有数字就讲上线后的一类故障和你怎么修的。
5. **复盘**：如果重做，会把哪类写操作从模型手里拿回到服务端。

### 3. 用户让鸡煲店 AI 助手“帮我订一份莫氏鸡煲，微辣，加鸡翅，半小时后来拿”，Agent 怎么把这句话拆成下单动作

**参考答案**

结论：先把这句话收成结构化草稿，服务端校验并让用户确认之后，再调用创建订单。

槽位可以收成这些：

- 意图是创建到店自取订单。
- 菜品「莫氏鸡煲」要解析成菜单里的 sku，数量按「一份」先记 1。
- 辣度「微辣」必须是这道菜的可选项。
- 加料「鸡翅」解析成加料 sku；份数没说清时先按 1 份放进确认卡，有多种规格就追问。
- 「来拿」是自取。「半小时后」用服务端时钟换算成门店时区的绝对时间，写进确认卡里给用户看。
- 价格、是否在售、库存、门店此时是否接单，全部以菜单和订单服务的返回为准。

编排上拆成两段：先保存草稿并返回缺了哪些必填项；用户确认后才生成这一次的下单意图号，调用创建订单。草稿阶段不长期占库存，确认后的预占要有过期释放。

容易漏的是默认数量、跨天的相对时间，以及模型顺口报出的价格。确认卡上的时间和金额都应该是服务端算好的。

### 4. Agent 调“创建订单工具”时，模型生成的参数缺了手机号，你怎么设计兜底和追问

**参考答案**

结论：手机号是创建订单的必填槽。工具层直接拒绝缺参调用；能从登录态或本会话补上的先补上并请用户确认，补不上就用固定话术追问。

1. 工具 Schema 把手机号标成必填。执行器在打到订单服务之前校验，缺参返回 `MISSING_SLOT: phone`，订单服务看不到这次调用。
2. 槽位状态放在会话里。取值顺序是：本轮用户明确说的，其次是已登录账号绑定的号码，再次是本会话早先说过的号码。后两种要在回复里复述，用户点头再用。
3. 追问用模板，一次只问一件事：「下单需要联系电话，请留一个手机号。」号码格式按业务允许的规则校验，不通过就再问。
4. 追问设上限。到了上限就留下草稿，转人工或结束，避免模型空转。
5. 模型没见过号码时，不允许它编一个填进去。

容易漏：登录用户已经有手机号，仍建议在下单确认卡里露出来。追问次数不封顶的话，缺一个字段就会把 token 打光。

### 5. Tool Calling 返回参数不合法时，是直接重试、让模型改参数，还是走人工兜底？说场景

**参考答案**

结论：按错误类型分流。格式不合法可以让模型改一次；业务拒绝不要用同一组参数再打；涉及钱的操作即使参数格式正确，也要确认或人审。

1. **Schema 不合法**（缺字段、类型错、枚举越界）：把校验错误当作工具结果交回模型，允许它修改后再调用，限制 1～2 次。同一组参数重复出现就停下，原样重试没有新信息。
2. **业务不合法**（下架、库存不足、未营业、金额和菜单不一致）：这是确定的失败。把原因告诉用户，让用户改菜或改时间，不要自动换成别的菜再下单。
3. **高风险写操作**（退款、改价、免单）：参数看起来合法也不自动执行，先复述并等人确认，超过门店策略的直接进人审。
4. 整个工具循环有最大步数。超限后用固定话术或转人工。

超时是另一类问题：结果未知，要按幂等键先查单，不能把它当成参数错误来改一改再调用。

### 6. Redis 在鸡煲点单 Agent 里能干什么？别只说缓存

**参考答案**

结论：Redis 放会话热数据、下单互斥、限流和进度事件。菜单缓存只是其中一项。订单和退款以 MySQL 为准。

- 当前槽位和草稿购物车按会话存放，TTL 盖住这一单的取餐时间，具体时长按门店履约窗口定。
- 下单互斥用 `SET key token NX PX`。释放时先比对 token 再删除，避免删掉别人的锁。锁过期以后，订单表唯一键仍是最终保证。
- 按用户、门店限流，保护模型和订单接口。
- 进度事件放 List 或 Stream，前端断线后按 taskId 补拉。Pub/Sub 只负责唤醒，断线期间的消息它留不住。
- 在售菜单可以短缓存，改价或下架后要能失效。真正计价以菜单服务当时的结果为准。
- 用用户消息 id 做去重，挡住客户端重放。

容易漏：Redis 被淘汰或宕机时，进行中的会话重新确认关键槽位即可。已经创建的订单不能靠 Redis 恢复。

### 7. 对话历史存 Redis 还是 MySQL？鸡煲店这种高频短会话场景你怎么选

**参考答案**

结论：进行中的短会话用 Redis 扛热读写，MySQL 异步留下需要回放和审计的记录。两边各管一段。

点餐往往几分钟、十几轮以内，每轮都要把最近上下文拼进提示词，读写频繁，中间闲聊可以丢。这种数据适合按 sessionId 放在 Redis，并在每轮后续期。TTL 盖住取餐窗口，不把 Redis 当成长期库。

必须进 MySQL 的是：和最终订单绑在一起的会话号、用户确认记录、工具调用审计、投诉回放。这些要能按订单号、用户和时间查询。

写法是：每轮先写 Redis，保证下一轮读得到；再异步把轮次批量写入 MySQL。Redis 丢了，进行中的关键槽位可以再问一遍，已落库的订单不受影响。拼提示词时只取最近几轮加一份摘要，不把全量历史从 MySQL 读出来塞进去。

### 8. 用户问“你们家鸡煲用什么鸡”，知识库里没有答案，Agent 硬编怎么办

**参考答案**

结论：品牌事实没有检索依据就明确说不知道。空结果要在代码里截住，不能只靠提示词要求模型诚实。

1. 检索为空，或最高分低于你们在标注集上定的阈值时，直接走拒答模板，不把空白上下文交给模型自由发挥。还没有标注集时，先把「一条都没召回」定为拒答。
2. 固定话术即可：「菜单资料没写用什么鸡，我帮你转店员确认。」需要的话再开工单，让店员补一条 FAQ。
3. 价格、库存、过敏原走结构化接口，不走开放生成。
4. 把这类问题记成知识缺口。资料补上并入库之后，下次才可以回答。

容易漏：模型会用常识圆场，例如「一般用三黄鸡」。菜单没写，这句就是错的。提示词里的「不许编」只是辅助，门禁要写在检索结果返回之后。

### 9. RAG 检索回来 10 段菜单文本，但用户只问价格和辣度，你怎么裁剪上下文省 token

**参考答案**

结论：价格和辣度优先查菜单服务的字段。已经召回了 10 段原文时，也只把这两项送进模型。

1. 从问题里抽出菜品和属性。能按菜品 id、在售状态、文档版本做元数据过滤，就不要只靠向量相似度。
2. 再用问题和「价格、辣度」做重排，留下最相关的 2～3 段。
3. 从段落里只抽出价格、辣度和规格，整理成几行。这一步用规则或结构化字段，避免再调一次大模型把数字改写错。
4. 给这段上下文一个 token 上限，并把它放在提示词靠前的位置。
5. 菜单改得勤时，正文容易过期。金额以数据库当前价为准，检索文本只补充说明。

容易漏：为了省 token 把含价格的那一行截掉。数字字段宁可不答，也不要答半截。

### 10. Agent 调第三方外卖平台接口超时，怎么重试，重试会不会重复下单

**参考答案**

结论：超时只说明时限内没收到响应，订单可能已经在对方创建成功。先按同一个业务单号查询，查不到才用这个单号重试。

1. 调用前就定好订单意图号，并先在本地插入「创建中」记录，唯一键就是这个号。然后再请求外卖平台。
2. 对方支持幂等键就传这个号；不支持就把它作为外部订单号，并约定对方按这个号去重。
3. 超时、429、502、504 先查单。查到就把本地状态补成已创建，停止重试。查明确没有，再用同一个号重试，指数退避加抖动，次数设上限。
4. 参数错误这类 4xx 不重试，把原因交回用户。返回冲突时也先查单，不要另开一个新号。
5. 查单也超时：本地保持未知，停止创建，交给对账任务。对账最终只收成成功或失败。

重复下单通常来自超时后换了新订单号再请求一次。同一个号的重试不会变成两单，前提是对方按这个号去重，并且本地唯一键挡住并发插入。

### 11. 创建订单工具怎么做幂等，防止模型重试导致下两单鸡煲

**参考答案**

结论：幂等落在订单表的唯一约束上。提示词只能减少多余调用，挡不住重试和并发。

1. 用户确认下单时生成 `order_intent_id`，放进工具参数。模型如果重试，必须原样带回这个号。不要只用「用户 + 菜品」做哈希，否则用户合法地再来一份同样的鸡煲会被挡掉。几秒内的双击去重可以另做一条产品规则，和这次意图号分开。
2. 订单表对意图号建唯一索引，并保存请求体哈希。插入冲突时查出原单：哈希相同就返回第一次的结果；哈希不同就返回冲突，停止并告警，不覆盖原单。
3. Redis 的 `SET NX` 只减少并发打到数据库的次数。锁会过期，主从切换时也可能穿透，所以它不是最终保证。
4. 工具执行器进入模型循环之前先查这个号。已经成功过，就把上次结果交回模型，不再创建。
5. 这个号要保留到对账结束，不能等接口一返回就删。

### 12. 手撕算法：给定订单里的菜品列表和数量，求所有菜品组合里总价最接近预算的那个组合，写出思路并写代码

**参考答案**

先把题意定成：每一行有名称、单价和数量，行金额 = 单价 × 数量，金额用整数分。一行要么整行入选，要么不选。在所有子集里找总价和预算绝对差最小的一个；差相同则优先总价不超过预算。同一总价有多组菜时，还原出其中一组即可。

若面试官允许少选份数，就改成每道菜选 `0..qty` 份的有界背包，内层多一个份数循环，时间从 O(n·S) 变成 O(S·Σqty)。一单菜品很少时，直接枚举子集也行，复杂度 O(2ⁿ·n)。下面的 DP 适合行金额总和 S 不大的情况；S 很大而 n 仍不大时，改用折半枚举。

设 `take[i+1][s]` 表示考虑完前 `i+1` 行后，凑出金额 `s` 时第 `i` 行选没选。从可凑出的金额里选最接近预算的，再倒着还原。时间 O(n·S)，空间 O(n·S)。只需要最接近的金额、不需要菜品时，空间可以压到 O(S)。

例：鸡煲 68 元、鸡翅 8 元 × 2 = 16 元、可乐 5 元，预算 70 元。换成分是 6800、1600、500，预算 7000。只选鸡煲，差 200 分；鸡煲加可乐是 7300，差 300 分。再如金额 10 和 30、预算 20，两边差都是 10，选 10，因为优先不超过预算。

```python
def closest_subset(lines: list[tuple[str, int]], budget: int) -> tuple[int, list[bool]]:
    if budget < 0:
        raise ValueError("budget 不能为负")
    amounts = []
    for _, amount in lines:
        if amount < 0:
            raise ValueError("金额不能为负")
        amounts.append(amount)
    n = len(amounts)
    max_sum = sum(amounts)
    take = [[-1] * (max_sum + 1) for _ in range(n + 1)]
    reachable = [False] * (max_sum + 1)
    reachable[0] = True
    for i, price in enumerate(amounts):
        nxt = [False] * (max_sum + 1)
        for s in range(max_sum + 1):
            if not reachable[s]:
                continue
            if not nxt[s]:
                nxt[s] = True
                take[i + 1][s] = 0
            ns = s + price
            if ns <= max_sum and not nxt[ns]:
                nxt[ns] = True
                take[i + 1][ns] = 1
        reachable = nxt
    best = 0
    best_diff = None
    for s in range(max_sum + 1):
        if n > 0 and take[n][s] < 0:
            continue
        if n == 0 and s != 0:
            continue
        diff = abs(s - budget)
        if best_diff is None or diff < best_diff or (diff == best_diff and s <= budget < best):
            best = s
            best_diff = diff
    chosen = [False] * n
    s = best
    for i in range(n - 1, -1, -1):
        bit = take[i + 1][s]
        if bit < 0:
            raise RuntimeError("无法还原组合")
        chosen[i] = bool(bit)
        if bit:
            s -= amounts[i]
    if s != 0:
        raise RuntimeError("还原金额不一致")
    return best, chosen
```

### 2. 讲你最熟的一个 Agent 项目，从需求、架构、工具、上线讲一遍

**答题思路**

按这四段讲，每段都落到你自己做过的部分。

1. **需求**：谁在用，原来怎么做，为什么不是纯规则。成功标准用你真实看过的指标，例如完成率、错单、人工接手。
2. **架构**：从入口、会话状态、模型、工具、存储到人工，画一条主链路。标出模型能决定什么，以及哪一步必须服务端校验。
3. **工具**：举 3～5 个。每个说清入参、有没有副作用、失败怎么办。指出哪几个是你做的。
4. **上线**：灰度范围、评测集、监控、回滚开关，以及你值守过的一类事故。
5. 最后留一个取舍：如果重做，哪段会从自由工具循环改成固定步骤。

不编项目名、公司名和没把握的数字。面试官会顺着你说的模块往下问。

### 3. 鸡煲店客服 Agent 要同时查订单、查菜单、查会员积分、发起退款，你怎么拆单 Agent 和多工具

**参考答案**

结论：对用户保持一个客服 Agent，把查订单、查菜单、查积分、退款做成四个工具。先不要按话题拆成四个都会说话的 Agent。

- 每个工具是普通服务接口，入参和出参用 Schema 固定，并带上超时、权限和审计。
- 工具描述写清何时调用、必填参数、有没有副作用。退款标成高风险，和查询分开。
- 按当前意图裁剪可见工具。用户只是在问菜单时，不把退款暴露给模型，减少误调用，也省 token。
- 几个互不依赖的查询可以并行。退款必须先得到用户确认过的唯一订单号，再单独执行。
- 售后政策、发布节奏和评测集已经和点单明显分开时，再在前面加一个路由，把售后交给专门的 Agent。即便到了那一步，幂等和权限仍然做在工具层。

容易漏：拆成多个 Agent 解决不了重复退款。重复退款要靠退款单的幂等键和人审。

### 4. 用户说“我刚才下的鸡煲单退了吧”，但没给订单号，Agent 怎么从多轮对话里定位订单

**参考答案**

结论：用会话里已经出现的订单锚点，加上已验证身份和「刚才」对应的短时间窗去查。查到 0 笔或不止 1 笔都要问，不能猜。

1. 本会话如果刚刚创建过订单，就用那张订单，并向用户复述菜品、时间和金额。用户确认后，退款工具才接收这个订单号。
2. 会话里没有订单号时，用登录用户或已验证手机号去查。不能按昵称查，避免退到别人的单。
3. 「刚才」映射成门店配置的短时间窗，只看这个窗口里还能退的订单，不从开业记录一直翻到现在。
4. 查到 1 笔：复述尾号、菜品和金额，等用户说是。查到多笔：列出 2～3 个候选让用户选。查到 0 笔：请用户提供订单号或手机号。
5. 退款入参只能是确认后的订单号。查询工具返回的「最近一笔」不能未经确认就传进去。

### 5. 多轮对话到第 30 轮，用户最开始说的“不要香菜”被忘了，你怎么设计记忆和摘要

**参考答案**

结论：忌口这种硬约束写成结构化字段，每轮单独注入。较早的闲聊可以摘要，这份字段不参与压缩。

1. **结构化约束**：不要香菜、辣度、履约方式存成槽位。用户说出来时写入，并在回复里复述一次。之后每轮用固定块放进提示词，例如「忌口=不要香菜」。
2. **原文窗口**：只保留最近若干轮，轮数由 token 预算决定，不把 30 轮原文都塞进去。中间的旧句子既贵，也容易被模型忽略。
3. **滚动摘要**：更早的对话压成摘要。生成新摘要时对照结构化字段做一次检查，缺了「不要香菜」就回填。摘要模型自己也会丢约束，所以字段才是硬记录。
4. **下单以草稿为准**：购物车备注写入「不要香菜」。创建订单读这个字段，不读模型当时想起来的内容。
5. 会话很长时，提交前再确认一次：「还是不要香菜、微辣，对吗？」

热数据放 Redis；订单落库时，备注随订单进 MySQL。

### 6. Agent 一边查数据库一边调 LLM 一边调消息推送，某一步失败了，整体怎么回滚或补偿

**参考答案**

结论：这三步不是一个数据库事务。查询和生成失败不用回滚业务数据；通知失败只补偿通知。已经创建的订单不因为话术或推送失败被删掉。

1. **查库**：只读。失败就有限次重试，或告诉用户这次没查到。没有写进去的数据需要回滚。
2. **调模型**：失败、超时或输出不合法，这次回复作废。如果前一步工具已经成功，用工具结果拼一条确定模板，例如已经查到的价格、已经创建的订单号。生成本身没有业务事务。
3. **推送**：放在业务提交之后。订单入库和出站消息表放在同一个本地事务里，异步投递到 Kafka 或微信。发送失败就重试，消费者按订单号幂等。补偿的是通知，不是取消订单。
4. 如果链路里还有锁库存，用预占加过期释放。释放接口同样要幂等。

顺序是：先读，再决定，业务库和 outbox 一起提交，最后才是用户看得见的通知。把「回复生成失败」和「订单回滚」绑在一起，会出现钱已收、单却没了。

### 7. Kafka 在 Agent 系统里用来做什么？鸡煲店订单生成、通知、日志异步化怎么接

**参考答案**

结论：Kafka 用来把下单主链路和通知、打印、日志拆开，让对话线程不等待慢下游。它不代替订单库，业务上的去重要消费者自己做。

1. **订单事件**：MySQL 提交订单时，同一事务写入 outbox。中继再发 `order.created`。本地事务成功之后才能告诉用户下单成功，不能只看「往 Kafka 发过一次」。
2. **通知**：独立消费组发微信、短信或店内屏。用 `order_id` 做消息键，保证同一订单在分区内有序；不同消费组互不阻塞。消费端按订单号和通知类型做幂等，手动在处理成功后提交位点。至少一次投递下，重复消息不能变成重复通知风暴，可以用「已发送」标记压住。
3. **日志和评测**：工具调用、模型用量、拒答事件进单独的 topic，异步进分析存储，不堵对话。手机号等字段先脱敏。
4. 生产者对订单事件要等到写入确认；失败留在 outbox 重试。消费者先处理再提交位点，重复消费由幂等接住。

容易漏：Kafka 的生产者幂等覆盖的是写入 Kafka，不覆盖「微信已经发出去」。端到端还是 outbox 加消费端幂等。

### 8. Agent 调工具特别慢，前端要看到“正在查菜单、正在锁库存、正在生成回复”，状态怎么推

**参考答案**

结论：进度由执行器按真实步骤发出，文案用服务端映射，不让模型临时编一句「正在锁库存」。

1. 每个工具开始、成功、失败时写一条事件：`taskId`、步骤、状态、展示文案、时间。`QUERY_MENU` 对应「正在查菜单」，`LOCK_STOCK` 对应「正在锁库存」。没执行到的步骤不发。
2. 事件先写入 Redis List 或 Stream，再推给客户端。浏览器可以用 SSE；微信小程序更稳的是 WebSocket 或按 taskId 短轮询。Pub/Sub 只做唤醒。
3. 断线后用最后一条事件 id 把 Redis 里的进度补齐。进度不能只放在某一台机器的内存里。
4. 最终回复单独一条完成事件。失败要有明确的失败事件，不能停在「正在查」。
5. 工具超时后，把文案改成「菜单服务响应慢，正在重试」或「转人工」，并真正走对应分支。

### 9. MySQL 存 Agent 任务表、步骤表、工具调用日志表，字段和索引怎么设计

**参考答案**

结论：任务表管一次用户目标，步骤表管循环里的每一步，工具日志表按次追加。写操作的唯一约束放在任务或订单上；日志表只追加，不给幂等键加唯一索引，否则失败重试会插不进去。

热表不放完整提示词和工具原文。大文本进对象存储或冷表，热表留哈希、结果码和耗时。手机号脱敏。日志写入高，不建外键，用 `task_id` 关联。状态变更时同时写 `updated_at`。

```sql
CREATE TABLE agent_task (

  UNIQUE KEY uk_idem (idempotency_key),

  KEY idx_user_time (user_id, created_at),

CREATE TABLE tool_call_log (

  task_id          BIGINT NOT NULL,

  idempotency_key  VARCHAR(64) NULL,
```

索引对应的查询是：按会话或用户看最近任务，扫描长时间停在运行中的任务，按任务顺序读步骤，按工具看一段时间的失败，按幂等键查调用记录。`status` 单独索引用处不大，和 `updated_at` 组成复合索引，才能服务「运行中且超时」这种范围条件。InnoDB 二级索引会带上主键，所以日志表按 `task_id` 过滤再按 `id` 排序，不必再把 `id` 写进索引。自增主键让日志顺序追加，避免随机主键把页打散。

同一幂等键、请求哈希不同的冲突判断放在 `agent_task.request_hash`，不放在可重复插入的日志表。

### 10. 鸡煲店晚上高峰期 Agent 并发上来，LLM 接口限流，你怎么降级到规则引擎或人工客服

**参考答案**

结论：模型被限流时，标准点单仍走规则和菜单服务；退款、投诉和没把握的话转人工。降级路径继续用原来的计价和幂等。

1. 入口按门店和用户限流。超限就快速返回排队或转人工，不把线程池堵在模型超时上。
2. 看到 429 或错误率升高，停止调用贵模型。能用小模型做槽位的继续用小模型，小模型也不可用就跳过生成。
3. 高频说法、按钮和明确指令用一组可配置规则识别，直接填槽，再向菜单服务取价、走同一个创建订单。这里的规则引擎是意图和槽位的确定匹配，不必先上很重的规则平台。
4. 纯菜单查询直接读库。退款、投诉、低置信度、连续工具失败转人工，并把已填槽位和草稿带上，用户不用从头说。
5. 降级按门店开关，高峰过去再放开。规则下单也要用户确认，不能因为绕过模型就跳过价格校验。

### 11. RAG 里旧菜单说“微辣免费”，新菜单说“微辣加 3 元”，模型信哪个，怎么让新知识优先

**参考答案**

结论：模型信菜单服务返回的当前价。这道题里的当前事实是微辣加 3 元。检索文本只注入仍在生效的那一份，不让模型在两段文案里投票。

1. 价格调用 `menu_service`，传入门店、菜品和当前时间，返回现在生效的加价。回复只转述这个结果。
2. 文档带上 `version`、`effective_from`、`effective_to`、`status`、`store_id`。检索时过滤在售，并且当前时间落在有效期内，同时限定本店。
3. 新菜单发布时，把旧切片标成失效或从索引删除。只多写一篇新文档，并不能保证向量分数更高。
4. 如果运营忘了下线，两份都还是有效，就按 `effective_from` 只取最新的一份放进提示词，并告警「两份有效文档价格冲突」。这种情况下拒答加价，等数据修好，比让模型挑一句更安全。
5. 提示词里写「请采用最新信息」只能作辅助。相似度不理解「新」，重排模型也不理解时间，除非你把时间做成明确的过滤条件。

评测集里固定放「旧文案免费、新菜单加价」这种样本，发布前跑一遍。

### 12. 手撕算法：解析模型输出的非法 JSON 工具调用串，提取出 tool 名称和参数并兜底，写代码

**参考答案**

思路：先去掉代码围栏和前后闲话，按括号配对截出第一段 JSON，字符串里的括号不算。再做有限修复：整段没有双引号时才把单引号换成双引号；删掉字符串外面的尾逗号；给没加引号的键补上引号。然后用标准 JSON 解析。

兼容三种外形：`tool` / `name` 加 `arguments`，嵌套的 `function.name`，以及 `tool_calls[0].function`。`arguments` 如果是字符串，再解析一次，并且必须得到对象。

兜底：括号不闭合、修完仍不是 JSON、参数不是对象、一次吐出多个调用，都把 `complete` 置为 false，禁止执行。截断的 JSON 不要猜手机号或数量。正则只再尝试抠出英文工具名和参数对象。`complete=true` 只表示结构完整，执行器还要做工具白名单和 JSON Schema；名称不在白名单、必填槽缺失、金额和菜单不一致，都不调用。失败信息可以回给模型重写一次，仍失败就追问用户或转人工。

扫描是 O(n)，n 为这段输出的长度。Java 里最后一步可以换成 Jackson，修复规则仍然要自己写。

```python
import json
import re

FENCE = "`" * 3


class ToolCall:
    def __init__(self, tool, arguments, complete, error=None):
        self.tool = tool
        self.arguments = arguments
        self.complete = complete
        self.error = error


def parse_tool_call(raw: str) -> ToolCall:
    if raw is None or not str(raw).strip():
        return ToolCall(None, {}, False, "empty")
    sliced = _slice_json(_strip_fence(str(raw).strip()))
    if sliced is None:
        return ToolCall(None, {}, False, "no json")
    repaired = _repair(sliced)
    try:
        return _from_value(json.loads(repaired))
    except json.JSONDecodeError:
        return _fallback(repaired)


def _strip_fence(raw: str) -> str:
    fence = raw.find(FENCE)
    if fence < 0:
        return raw
    nl = raw.find("\n", fence)
    start = fence + len(FENCE) if nl < 0 else nl + 1
    end = raw.find(FENCE, start)
    return raw[start:] if end < 0 else raw[start:end]


def _repair(s: str) -> str:
    if '"' not in s and "'" in s:
        s = s.replace("'", '"')
    return _quote_unquoted_keys(_strip_trailing_commas(s))


def _slice_json(s: str):
    start = next((i for i, c in enumerate(s) if c in "{["), -1)
    if start < 0:
        return None
    stack, in_str, esc = [], False, False
    for k in range(start, len(s)):
        c = s[k]
        if in_str:
            if esc:
                esc = False
            elif c == "\\":
                esc = True
            elif c == '"':
                in_str = False
            continue
        if c == '"':
            in_str = True
        elif c in "{[":
            stack.append(c)
        elif c in "}]":
            if not stack:
                return None
            open_ = stack.pop()
            if (open_ == "{" and c != "}") or (open_ == "[" and c != "]"):
                return None
            if not stack:
                return s[start:k + 1]
    return None


def _strip_trailing_commas(s: str) -> str:
    out, in_str, esc, i = [], False, False, 0
    while i < len(s):
        c = s[i]
        if in_str:
            out.append(c)
            if esc:
                esc = False
            elif c == "\\":
                esc = True
            elif c == '"':
                in_str = False
            i += 1
            continue
        if c == '"':
            in_str = True
            out.append(c)
            i += 1
            continue
        if c == ",":
            j = i + 1
            while j < len(s) and s[j].isspace():
                j += 1
            if j < len(s) and s[j] in "}]":
                i += 1
                continue
        out.append(c)
        i += 1
    return "".join(out)


def _quote_unquoted_keys(s: str) -> str:
    out, in_str, esc, i, n = [], False, False, 0, len(s)
    while i < n:
        c = s[i]
        if in_str:
            out.append(c)
            if esc:
                esc = False
            elif c == "\\":
                esc = True
            elif c == '"':
                in_str = False
            i += 1
            continue
        if c == '"':
            in_str = True
            out.append(c)
            i += 1
            continue
        if c.isalpha() or c == "_":
            j = i + 1
            while j < n and (s[j].isalnum() or s[j] in "_-"):
                j += 1
            k = j
            while k < n and s[k].isspace():
                k += 1
            if k < n and s[k] == ":":
                out.append('"' + s[i:j] + '"')
                i = j
                continue
        out.append(c)
        i += 1
    return "".join(out)


def _from_value(value) -> ToolCall:
    if isinstance(value, list):
        if len(value) == 1 and isinstance(value[0], dict):
            return _from_obj(value[0])
        if value and isinstance(value[0], dict):
            call = _from_obj(value[0])
            call.complete = False
            call.error = "multiple tool calls"
            return call
        return ToolCall(None, {}, False, "not object")
    if not isinstance(value, dict):
        return ToolCall(None, {}, False, "not object")
    calls = value.get("tool_calls")
    if isinstance(calls, list) and calls:
        if len(calls) == 1 and isinstance(calls[0], dict):
            inner = calls[0].get("function", calls[0])
            return _from_obj(inner if isinstance(inner, dict) else {})
        if isinstance(calls[0], dict):
            inner = calls[0].get("function", calls[0])
            call = _from_obj(inner if isinstance(inner, dict) else {})
            call.complete = False
            call.error = "multiple tool calls"
            return call
        return ToolCall(None, {}, False, "bad tool_calls")
    if isinstance(value.get("function"), dict) and not any(k in value for k in ("tool", "tool_name")):
        return _from_obj(value["function"])
    return _from_obj(value)


def _from_obj(obj: dict) -> ToolCall:
    tool = next((obj[k].strip() for k in ("tool", "tool_name", "name") if isinstance(obj.get(k), str) and obj[k].strip()), None)
    if not tool:
        return ToolCall(None, {}, False, "missing tool")
    raw, present = None, False
    for key in ("arguments", "parameters", "args"):
        if key in obj:
            raw, present = obj[key], True
            break
    if not present or raw is None:
        return ToolCall(tool, {}, True, None)
    if isinstance(raw, dict):
        return ToolCall(tool, raw, True, None)
    if isinstance(raw, str):
        try:
            parsed = json.loads(_repair(raw))
        except json.JSONDecodeError:
            return ToolCall(tool, {}, False, "bad arguments")
        if isinstance(parsed, dict):
            return ToolCall(tool, parsed, True, None)
    return ToolCall(tool, {}, False, "bad arguments")


def _fallback(text: str) -> ToolCall:
    tool = None
    for key in ("tool", "tool_name", "name"):
        m = re.search(rf'["\']?{key}["\']?\s*:\s*["\']?([A-Za-z_][\w\-]*)["\']?', text)
        if m:
            tool = m.group(1)
            break
    args = None
    for key in ("arguments", "parameters", "args"):
        m = re.search(rf'["\']?{key}["\']?\s*:', text)
        if not m:
            continue
        sliced = _slice_json(text[m.end():])
        if sliced:
            try:
                value = json.loads(_repair(sliced))
                if isinstance(value, dict):
                    args = value
            except json.JSONDecodeError:
                pass
        break
    if not tool:
        return ToolCall(None, {}, False, "unparsed")
    if args is None:
        return ToolCall(tool, {}, False, "arguments not parsed")
    return ToolCall(tool, args, True, None)
```

### 1. 自我介绍

**答题思路**

三面更想听你能不能对结果负责。控制在 30～60 秒。

1. 身份一句带过，不重复简历。
2. 讲一个你拍过板的取舍：哪些动作允许模型做，哪些必须用户确认或人工处理，你用什么现象判断线上有没有做坏。
3. 补一句你和后端、运营或客服怎么配合，例如菜单改价怎么通知到 Agent，投诉怎么回到评测集。
4. 落到这个岗位：点单和售后的关键是资损和稳定性，你想负责这条链路，而不是只接模型 API。

项目架构等对方追问再展开。数字仍然只用你真实有的。

### 2. 如果让你从 0 搭莫氏鸡煲智能点单 + 售后 Agent 平台，整体架构怎么画

**参考答案**

结论：主干用确定的下单步骤，模型用在听懂人话和组织回复上。价格、库存和退款结果都以业务服务为准。

可以分成这几层：

1. **渠道**：微信、电话 ASR、门店屏都收成统一消息，带上门店和用户身份。
2. **接入**：登录、门店路由、限流、这一轮的幂等键。
3. **编排**：会话槽位和任务状态机。标准套餐走固定步骤；说法很散时才叫模型产出工具草案。模型不直接改库。
4. **工具**：菜单、库存、订单、会员、退款、通知。统一 Schema、超时、权限和审计。写操作带幂等键。
5. **知识**：FAQ 走检索。价格、库存、订单状态不走生成。
6. **模型网关**：按任务选模型，失败降到规则。
7. **数据**：MySQL 存订单和任务，Redis 存会话和锁，Kafka 承担通知和日志。
8. **观测**：链路 trace、工具成功率、幻觉抽检、订单对账。

难点是工具超时后的未知结果、用户中途改口，以及三个渠道要共用同一份会话和订单。取舍也很明确：全交给一个自由 Agent 更灵活，但资损和回归测试都差，所以确认前不下单，承诺必须来自已经成功的工具结果。

### 3. 单 Agent 和多 Agent（点单 Agent、售后 Agent、营销 Agent、巡检 Agent）怎么分工通信

**参考答案**

结论：用户只看到一个入口。内部按职责拆开，但一轮对话只有一个负责人回复。共享的是订单和会员这些业务服务，不是一份公共提示词。

- **点单**：菜单、购物车、创建订单。
- **售后**：查单、退款、改单。动钱的默认进人审。
- **营销**：可以推荐和草拟优惠券，不能直接改订单金额。优惠要经用户确认后，由点单链路按菜单价重新计算再应用。
- **巡检**：离线看差评、卡住的订单和库存，只开工单，不插进正在进行的对话。

通信上，路由按意图把这一轮交给一个 owner，避免两个 Agent 同时说话。传给下游的是 `user_id`、`store_id`、`order_id` 和已确认槽位，不广播全部聊天记录。同步查询走内部 RPC，巡检和通知走队列。

MCP 解决的是工具和资源怎么暴露给模型，不决定这四个 Agent 怎么分工。店刚起步时，一个 Agent 加多工具就够用；售后政策需要独立发布和独立评测时再拆。拆早了，路由错误会比工具错误更影响体验。

### 4. Agent 自动给用户发“退差价、送优惠券、改订单”等敏感操作，怎么加审批和人审

**参考答案**

结论：这类写操作默认先生成审批单，审批通过后再由服务端执行冻结好的参数。用户侧在执行成功之前不能说「已经退好了」。

1. 工具元数据标出风险。查询可以自动；退差价、发券、改订单、免单属于写操作。
2. 策略放在工具执行前，不写进提示词。金额阈值、动作类型由门店配置。超过策略就创建审批单，而不是直接调用。
3. 审批单里冻结订单号、金额、命中的规则、模型给出的理由，以及对参数做的哈希。审核人在后台通过或拒绝。通过后，服务端用原幂等键执行这份参数，模型不能在审批后再改金额。
4. 审批前的话术是「已提交店员确认」。工具成功之后，才按工具结果说「已退」或「已改」。
5. 审计留下谁批准、何时执行、前后金额。每个敏感工具都有开关，可以按门店关掉。

容易漏：人看过的是 10 元，执行时模型又改成 100 元。所以批准的是一份不可变参数，不是批准「让模型再去退一次」。

### 5. 鸡煲店老板说“Agent 昨天自动答应客户免单 20 份”，这种幻觉资损怎么防

**参考答案**

结论：模型没有免单权限。回复里的赠送和改价必须对得上一条已经成功的补偿单，对不上就拦截。

1. 免单、改价工具默认不注册给模型；业务上确实要补偿时，也走上一题的审批，不自动执行。提示词里写「不能免单」只是辅助。
2. 发出前做核对：回复里出现免单、免费、不收费、赠送，但没有对应的已批准补偿单，就换成「需要店员确认」。明显词用规则拦，金额和赠送再按结构化结果核对，避免只拦关键词、放过换一种说法。
3. 补偿有门店预算和单笔上限，上限由业务配置，做在工具里。超出直接失败。
4. 每天把对话里的承诺和退款、免单流水对一次。只有口头承诺、没有单据的，告警并回访。
5. 上线前准备对抗样本：用户要求免单、情绪施压、声称自己是老板。过期活动「全场免单」被检索出来，同样会造成资损，所以活动也要有有效期，发布新规则时作废旧文案。

已经发生时：关掉对应工具和话术，联系客户，用 trace 看是模型编的，还是旧活动被检索进去了。

### 6. 怎么评估这个鸡煲 Agent 好不好：任务完成率、工具成功率、幻觉率、客诉率怎么算

**参考答案**

结论：用业务终态衡量，不用模型自己说的「已完成」。四个指标都先写死分子分母，并能按门店和意图下钻。

- **任务完成率**：分母是进入该任务的会话数，意图识别错误另计，避免一个指标同时背两件事。分子是业务系统达到目标的数量。下单看订单创建成功，且不是随后因为助手下错被取消；咨询看答复里的事实能对上菜单或订单。口径和业务事先定好。
- **工具成功率**：分母是实际发出的调用次数，分子是拿到业务成功结果的次数。超时、参数不合法、下游 5xx 都算失败。按工具名分开，否则菜单查询成功会把退款失败稀释掉。模型决定不调用，不进这个分母。
- **幻觉率**：分母是有权威答案的回复，例如价格、菜品、订单状态、政策。分子是和权威数据不一致的回复，包括不该承诺却承诺。价格可以全量比对；开放说法抽样人工看。寒暄没有标准答案，不进分母。免单这类资损单独统计，不和说错配料混成一个率。
- **客诉率**：分子是事后投诉、差评或退款原因被标成助手说错、做错的数量。分母同时看会话数和订单数。它是滞后指标。

同时看转人工率。完成率上升，可能只是难任务都被转走了，所以要一起看自动完成了多少。

### 7. 线上 Bad Case 来了，你怎么归因是 Prompt 问题、检索问题、工具问题还是模型问题

**参考答案**

结论：先拿一条 trace，按链路从前往后看，先修最上游坏掉的那一层。一次发布里不要同时改提示词和模型，否则不知道是哪次生效。

1. trace 里要有用户原话、检索片段和分数、文档版本、工具名和参数、工具返回、模型原始输出、最终回复，以及数据库里的真实订单或价格。
2. **工具问题**：参数和用户说法、库里的数据一致，但返回错误、超时或旧价格。去修工具、超时或数据。改提示词解决不了。
3. **检索问题**：正确文档没进上下文，或过期菜单进来了。看过滤条件、分数和版本，改切片、元数据或索引。
4. **Prompt 或编排问题**：上下文或工具结果里已经有正确答案，模型没用；或者槽位没问全就调用。去改提示词、工具描述，或把这一步收成状态机。
5. **模型问题**：把当时的消息和工具结果冻住重放，模型仍然选错工具或编造。这时再换模型、收紧结构化输出，或在外面加校验器。重放如果变成正确的，就去看温度和那一次的真实入参，不先换模型。

归因之后把这个 case 补进评测集。一层修完再看下一层，因为一次坏案例经常是几层叠在一起。

### 8. Token 成本突然翻倍，你会从哪些环节排查：上下文、检索、重试、模型路由

**参考答案**

结论：先把增量拆成请求量、每任务调用次数、单次输入和输出 token、以及模型单价和流量占比。再按上下文、检索、重试、路由四条线对发布记录。

1. **上下文**：系统提示词、工具 Schema、历史轮次、回灌的工具结果变大。看单次 prompt token 的分位数，和上周比。全量历史没有摘要时，这里最容易涨。
2. **检索**：召回条数和切片长度变大，或重排后又把原文整段拼回去。十段菜单全文进提示词就足够翻倍。菜单问答若做缓存，缓存键要带菜单版本，改价后失效。
3. **重试**：JSON 解析失败、工具失败导致同一轮多次调用模型。看每任务的模型调用次数和重复的工具名。步数要有上限。
4. **模型路由**：流量从便宜模型切到贵模型，或失败后升级重试的比例升高。按模型看 token 和调用占比。也要看输出是不是突然被要求写很长的解释。

先限制最大轮次、裁掉工具原文、把价格改走结构化接口，再决定要不要换模型。曲线拐点和发布时刻对齐，能少猜很多。

### 9. 强模型贵、小模型快，鸡煲点单 / 售后 / 运营分析三类任务你怎么路由模型

**参考答案**

结论：按说错的代价和是否需要多步推理来路由。金额计算始终在业务代码里，强模型也不负责算价。

- **点单**：高频，槽位相对封闭。意图和槽位用规则或小模型。价格和库存读菜单服务。说法很乱、置信度低时再升级到强模型，创建订单前仍要用户确认。
- **售后**：用小模型或规则分辨用户指的是哪一单。能不能退、退多少，走政策引擎和订单状态。向用户解释时，小模型只转述工具结果。投诉、政策冲突再升级强模型，并且常常要人审。
- **运营分析**：离线跑，可以慢，用强模型做原因分析和周报。配额和晚高峰的点单分开，避免分析任务把下单配额吃光。分析结果给店长，不直接改生产数据。

小模型低置信度再升级，并把升级记到成本里。限流时按相反方向退回规则。强模型同样会把退款金额说错，所以数字以工具返回为准。

### 10. 你最近怎么学 Agent 新东西，MCP、LangGraph、Spring AI、RAG 重排这些怎么跟进

**答题思路**

用店里一条真实失败链路当滤镜：用户改口、工具超时、重复下单。一个新名词先回答它补的是这条链路的哪一层，补不上就先不追。

可以按这个顺序讲你的跟进方式：

1. 读这个项目的文档和变更记录，跑通一次最小调用。
2. 列出生产还缺的部分：权限、幂等、人审、评测、失败后怎么恢复。
3. 准备讲清三句话：它解决什么，不解决什么，怎么接到现有 Java 服务。

这四样可以落成这样的说法，用你真实看过的资料填充，不编「我已经用它做了某店」：

- **MCP**：把菜单、订单做成可发现的工具和资源，让不同运行时复用同一套接口。它不负责多轮状态，也不授予免单权限。退款这类工具默认不暴露，接入要有鉴权。
- **LangGraph**：把「澄清 → 确认 → 下单 → 通知」收成有状态的图，检查点落到数据库，人审可以在确认节点暂停，失败后从检查点续跑。订单是否成立仍以订单库为准。
- **Spring AI**：在 Spring Boot 里用 ChatClient 接模型，用工具注解把 Java 方法暴露出去并生成参数 Schema。校验、事务和幂等留在原有服务里。
- **RAG 重排**：向量召回只负责找候选，再用问题和文档一起打分的重排模型留下前几条。微辣加价这种字段仍以菜单库当前版本为准，重排不负责判断哪份文档更新。

节奏上，用每周的 bad case 过滤要跟的发布，不把每个新框架都接进主链路。

### 11. 如果老板要求 Agent 三个月内接电话订餐、微信订餐、门店屏订餐，你怎么排优先级和灰度

**参考答案**

结论：三个月先做通一个渠道的标准自取单，再复用同一套编排接第二个、第三个。排序看错单代价、现有单量、接入成本和现场有没有人兜住。

第一期范围只含标准菜和到店自取。退款和发券仍给店员。三个入口共用编排和订单工具，各自只做渠道适配。

- **微信文字优先**：没有语音识别误差，确认和支付都在对话里，适合先做。若门店几乎没有微信单、但店员一直站在屏幕旁边，也可以把门店屏的影子模式放到前面，因为人能当场改错。
- **门店屏其次**：复用同一接口。界面要防误触，大字展示确认卡。店员在场，适合作为第二家灰度。
- **电话放最后**：语音识别会直接变成错单。创建前必须把菜品、辣度、时间和金额复述一遍。置信度低就转人工。老板如果坚持电话单量最大，也只先做影子模式：Agent 填草稿，人来确认，不无人值守下单。

灰度按门店开关，先一店。第一阶段可以是影子模式，高置信度的标准单再放开自动创建。出问题一键回到原来的人工点单。每周看完成率、错单退款、人工接手和单均 token。三个入口不要在第一周同时无人值守。

### 12. 手撕算法：给定一个用户会话里多个待执行任务及依赖关系，输出合法执行顺序，写拓扑排序代码

**参考答案**

用 Kahn 算法：边是「前置任务 → 当前任务」。当前任务的入度加上前置的个数，重复依赖按一条算。入度为 0 的任务可以执行；每完成一个，就把它指向的后续入度减 1。最后如果排出的个数少于任务个数，说明有环。

有环就拒绝执行，把环交回规划或人工，不要带着环去调退款。多个任务同时入度为 0 时，任意顺序都合法。下面用堆按任务名取，是为了同输入得到稳定结果；线上可以把堆换成业务优先级，例如先做用户正在等的那一步。

时间用堆是 O((V+E) log V)，改成普通队列就是 O(V+E)。空间 O(V+E)。

例如 `lock_stock` 依赖 `check_menu`，`create_order` 依赖 `lock_stock`，`notify` 依赖 `create_order`，一个合法顺序是 `check_menu → lock_stock → create_order → notify`。

```python
import heapq
from collections import defaultdict


def topo(prerequisites: dict[str, list[str]]) -> list[str]:
    outgoing = defaultdict(list)
    indegree = {task: 0 for task in prerequisites}
    for task, pres in prerequisites.items():
        for pre in dict.fromkeys(pres):
            if pre == task:
                raise ValueError("任务依赖存在环，无法执行")
            indegree.setdefault(pre, 0)
            outgoing[pre].append(task)
            indegree[task] += 1
    ready = [task for task, degree in indegree.items() if degree == 0]
    heapq.heapify(ready)
    order = []
    while ready:
        cur = heapq.heappop(ready)
        order.append(cur)
        for nxt in outgoing[cur]:
            indegree[nxt] -= 1
            if indegree[nxt] == 0:
                heapq.heappush(ready, nxt)
    if len(order) != len(indegree):
        raise ValueError("任务依赖存在环，无法执行")
    return order
```

## HR面

### 1. 为什么从普通 Java 后端转 AI Agent 开发

**答题思路**

按「原来的能力 → 为什么现在转 → 为什么是这个场景」说，把 Java 说成优势。

1. 你在事务、幂等、超时、对账上的经验，正好是点单 Agent 容易出事的地方。模型负责听懂话，这些仍然要工程兜住。
2. 转的原因落到业务：你想做的是能下单、能退款、能复盘的系统，而不是只把接口包一层模型。用你真实接触过的一个 LLM 需求当例子，没有就说你补过哪一块基础。
3. 为什么是鸡煲这种场景：订单、库存、会员、外卖都在，练的是落地，不是名词。
4. 不要把原来的 Java 工作说成没有价值，也不要把动机说成单纯追热点。

### 2. 做鸡煲 Agent 这种业务，你觉得苦不苦，愿不愿意沉到场景里

**答题思路**

先承认难在哪，再说明你愿意怎么沉进去。

1. 难的是晚高峰的改口、错单、退款纠纷和每天的 bad case，不是把一个演示调到能聊天。
2. 愿意沉到场景的具体做法：高峰跟一班客服或门店，自己把投诉按「听错、查错、下错、说错」分类，用真实对话改槽位和工具。
3. 判断自己做没做进去的标准：一家店的下单闭环稳不稳，客服是否还在重复回答同一类问题。
4. 如果这和你的真实偏好冲突，就直接说你更能接受哪一类强度，不要空泛说「我吃苦」。

### 3. 如果进来发现团队大部分还是写 Java 接口，只有三成做 Agent，你能不能接受

**答题思路**

可以接受，并把接口工作说成 Agent 的一部分。

1. 菜单、库存、退款接口不可靠时，模型没有用。写这些 Java 接口就是在做 Agent 的工具层。
2. 你希望那三成是一条垂直切片，例如自取下单，自己能碰到工具契约、评测和线上问题，而不是只在旁边看演示。
3. 如果大部分时间在做交易接口，你也可以接受，只要这些接口会被 Agent 真正调用，并且你能看到线上结果。
4. 可以反问：这三成具体负责编排、工具，还是只负责接模型。对方的回答也帮你判断岗位。

### 4. 上家公司为什么走

**答题思路**

只讲一个真实原因，不评价前领导和同事。

1. 先说你在上一家已经做成的事，例如交易链路、稳定性或你负责的系统。
2. 再说现在缺的那一块：你希望下一份工作能把这些能力用到可上线的 Agent 上，上一家的范围给不到。原因按事实讲，组织调整、业务收缩、技术方向不一致都可以，用你自己的那一个。
3. 如果主要是薪资或通勤，用一句话说清楚，不要铺成抱怨。薪资数字留到下一题。
4. 避免「领导不行」「加班太多」这种没有事实的评价。对方问得细，就补事实，不补情绪。

### 5. 薪资预期和底线

**答题思路**

先把结构问清，再给区间。复习稿里不写死数字，用你自己的总包和市场区间填。

1. 先了解职级、底薪、绩效、补贴和试用期怎么算，确认双方说的是同一口径的总包。
2. 给出一个期望区间。区间基于你现在的总包和你了解到的市场，不报一个没有依据的单点。
3. 底线是低于它这次变动就不划算的那个总包，把通勤、强度和你要的成长算进去。对方追问再给底线，开口不先抛底线。
4. 说明区间可以谈。如果岗位能让你负责从理解到下单的完整链路，你看重的不只是固定月薪。

不编一个具体的「期望多少、底线多少」背进去。数字必须是你自己核对过的。

### 6. 未来三年想做 Agent 架构师、业务负责人，还是继续啃大模型工程

**答题思路**

给出方向，同时把前两年的交付说具体，避免只报一个头衔。

1. 第一年：把一个渠道的下单和售后做稳，自己跟 bad case 和晚高峰。
2. 第二年：补评测、成本和多渠道，能把工具契约和失败标准讲给别人听。
3. 第三年更想做贴着门店结果的 Agent 架构：工具权限、人审、评测、降级。业务负责人如果意味着对客诉和资损负责，这条路径是通的，因为它和架构看的是同一套结果。
4. 大模型工程会继续学，但是为这条业务服务。模型榜上的新名字，要能解释它怎么减少错单或成本，才值得引进。

如果团队更需要你先守住一条业务线，你也可以先做负责人要的那部分，前提是仍然能碰到系统和线上问题。

### 7. 入职后第一个月你准备怎么快速摸清鸡煲业务和现有系统

**答题思路**

按四周说，产出是一张业务链路和一小组你亲手看过的问题，不是一份新框架方案。

1. **第一周**：跟着一笔真实订单走读代码和表，覆盖下单、支付、退款。自己下一单，把状态变化记下来。
2. **第二周**：高峰时段跟客服或门店，记录用户实际怎么说，尤其是改口、催单、退款。
3. **第三周**：读最近的 trace 和投诉，按听错、查错、下错、说错归类，列出出现最多的几类。
4. **第四周**：修一个小闭环，例如一个缺槽追问或一处错误价的展示。给带教人一页笔记：业务对象、现有系统、当前风险。

第一个月不提重写编排。先证明你能在现有订单链路上改对一个问题。

### 8. 有没有不能接受的管理方式或协作方式

**答题思路**

只讲一两条和协作有关的边界，并说你自己会怎么做。

1. 不能接受的一种：动到钱的改动没有评审、没有回滚，出了资损再补日志。你的做法是把验收和资损边界写进需求，上线前对一下监控和开关。
2. 不能接受的另一种：出了问题先定责任，不让看 trace。你希望复盘对事，先把订单、工具返回和回复对齐。
3. 可以接受的：进度紧、优先级变化。只要风险是明示的，你可以先做小范围灰度。
4. 不评价前一家的具体管理者，不把个人偏好列成清单。对方如果问「那你怎么和意见不同的人合作」，就回到事实和书面结论：争议点、可选方案、最后谁对结果负责。
