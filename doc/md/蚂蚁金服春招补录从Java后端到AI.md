### 3. Java 并发编程中，如何实现一个线程安全的高效缓存？请阐述你的设计思路。

**参考答案**

结论：进程内用并发哈希表存放不可变条目，同一个 key 的回源合并成一次；容量和过期单独限制。要跨进程共享的状态放到 Redis。

`ConcurrentHashMap` 的 `get` 本身能并发读。条目一旦放入就不再改字段，读方不用再加整表锁。未命中时，在另一张 in-flight 表里登记 `CompletableFuture`：第一个请求负责加载，同 key 的后来者等待这一次。加载放在哈希表外面，成功后再写入；失败只摘掉自己放进去的那次登记，下次才能重试。

回源不要写进 `computeIfAbsent` 的映射函数。函数执行时占着桶锁，里面做阻塞 IO 会拖住同桶的其他 key；函数里再改这张表，还可能和另一次嵌套更新死锁。

过期时间加一点抖动，避免一批 key 同时失效。容量设上限。读多、又夹杂一次性扫描时，Caffeine 用的 W-TinyLFU 准入比纯 LRU 更能留下热点。为了挡住穿透而缓存空结果时，只保留很短时间。懒过期删除要用「仅当仍是这一条才删除」，避免删掉别的线程刚写入的新值。

本地缓存每个实例各有一份，适合可重建的数据。会话和余额要全局一致，不放在这层。

### 4. 在微服务架构下，如何设计一个保证最终一致性的分布式事务方案？可以结合具体业务场景（如积分兑换）说明。

**参考答案**

结论：积分兑换用「本地兑换单 + 发件箱 + 积分冻结」做最终一致。可用余额在冻结时就减掉，发券结果确定后再实扣或解冻。

兑换服务在一个本地事务里写兑换单（状态为处理中，业务单号唯一）和发件箱。投递失败只重试发件箱，不会出现单已提交但消息丢失。

积分库用同一个本地事务写冻结流水和余额：业务单号唯一，`balance` 足够才扣减并增加 `frozen`。余额不足则整笔回滚，不留半笔冻结。重复请求读到已有流水就返回上次结果，不能把扣减再执行一遍。条件更新保证两笔并发兑换不会把同一份余额都花掉。

冻结成功后再发券，发券同样按业务单号幂等。券已发出，冻结转为实扣；确认没发出，再解冻。超时先查券的结果，查清之前不做反向操作。冻结流水走状态机：已确认和已取消都是终态，后到的另一次操作直接忽略。

停在处理中太久的单，由定时任务按积分流水和发券记录补偿，用户最终只看到成功或失败。两阶段提交在准备成功之后，仍要把两边的锁留到全局提交或回滚；发券一慢，积分账户就一直被占着。这条链路接受短暂的处理中，用幂等和对账收口。

### 5. 什么是 AI 智能体（AI Agent）？你认为它与传统的编程模型或规则引擎有何本质区别？

**参考答案**

结论：智能体是模型在循环里，根据目标和工具结果决定下一步。传统程序和规则引擎的分支，在发布前就写死了。

只调用一次模型、得到一段话，还不算智能体。它要有目标、一组允许使用的工具，以及工具返回的观察，然后重复「决定、执行、再看」，直到完成或达到步数上限。

普通代码把条件、循环和状态机写明，同样的输入走同一条路径。规则引擎把条件放进规则表，命中就执行预定动作，优先级也是人定的。智能体的下一步来自模型对当前上下文的判断，发布时穷举不了所有说法。

改账户、下订单仍由普通接口执行，模型只产出结构化决定。决定没有被穷举，就会选错工具或打转，所以循环要有步数和超时。

### 6. 如果要为我们的一个金融产品（比如智能投顾、反欺诈风控）引入智能体能力，你认为在技术架构上需要考虑哪些核心组件？

**参考答案**

结论：智能体放在编排层。账户、行情和风控策略仍由现有系统负责，模型不充当账本。

一次请求经过这些组件：接入层做鉴权、会话和 traceId，先确定用户和适当性；编排层限制步数、工具白名单和超时；模型层用小模型做意图和抽槽，用大模型做解释，输出先落到结构化字段；工具网关接入持仓、产品、行情和案例库，每个工具带权限和是否允许副作用；知识库保存说明书、费率和合规话术，带出处和生效时间；短期槽位放会话存储，风险等级仍以客户系统为准。

模型后面还要有一道护栏，拦截承诺收益和越权建议。金额大或置信度低就转人工。问题、工具参数、证据 id 和最终话术按 trace 留档。

投顾和反欺诈共用这套骨架，处置权不同。投顾可以生成解释，调仓要人确认。反欺诈的分数和拦截由策略引擎给出，智能体负责归纳证据和补问，不单独决定冻结账户。

### 7. 智能体在决策过程中可能需要调用多个外部工具或 API，如何设计一个可靠且高效的「工具调用」层？

**参考答案**

结论：工具调用层是网关。模型只提交工具名和参数，网关校验、限流、执行，再把裁剪后的结果交回去。

注册表里每个工具有 JSON Schema、超时、是否幂等、是否有副作用、所需权限和下游依赖。未注册的名字直接拒绝。参数对不上 schema，把错误交回模型，并限制重试次数。

彼此无关的读工具可以并行。响应只留模型要用的字段，纯读结果按参数短缓存。写工具默认不自动重试；要重试必须带业务幂等号。下单、调仓收成待确认指令，不进自动调用。

每个下游用自己的线程池或信号量，一个慢接口占不满全部工作者。连续失败就熔断该依赖，短时间内直接返回不可用。超时和错误码变成结构化结果，原始页面不进上下文。

用户原文和工具返回都当不可信数据，不能改白名单和系统指令。每次调用记下调用方、参数摘要、结果码和耗时。

### 8. 场景题：假设我们要开发一个智能客服助手，它需要理解用户意图、查询知识库并生成回复。如果回复速度慢，请从系统设计角度分析可能的原因及优化方向。

**参考答案**

结论：先按段计时，分清时间在排队、检索、业务工具还是等模型。能并行的并行，不必等全文的改成流式，每段超时都有退路。

常见卡点有四类。意图、改写、检索、重排串成一条，历史对话又整段塞进提示词。工单或账户接口慢，还和模型调用抢同一批线程。模型并发打满后，请求在队列里等。网关把流式响应缓冲成一整包，用户仍要等结束才看到字。

意图走规则或小模型，开放问题才进大模型。检索带上产品、渠道等过滤条件，热门问法命中 FAQ 就直接返回。检索和用户资料并行取，上下文只留摘要和命中片段。对用户使用流式输出，反向代理不缓冲这段响应。

模型、检索和业务工具分成独立的并发额度。某一段超过截止时间，就退回固定话术或转人工。上线后同时看首 token 和端到端，按 trace 找到变慢的那一段。

### 9. Redis 在智能体系统中可能扮演什么角色？（如记忆管理、会话缓存、向量检索等）

**参考答案**

结论：Redis 放热会话、互斥和短期记忆。它不是唯一账本。向量能力适合中小规模、过滤简单的集合。

槽位和最近几轮对话放 Redis，键里带 userId 和 sessionId，并设置 TTL。重要轨迹同时落数据库，缓存丢了可以按会话回放。同一会话的并发轮次用 `SET key value NX PX` 互斥，释放时用唯一令牌校验，避免一路删掉另一路刚加上的锁。

纯读工具的结果可以按参数短缓存。模型和单用户的频率也可以用 Redis 计数。

Redis 的向量索引支持 FLAT 和 HNSW，能做会话级或中等语料的相似度召回。语料大、又要按权限和生效时间过滤时，用带过滤的检索引擎更合适。向量是派生数据，原文下线要能删掉对应向量。

长期画像设容量和淘汰，不在内存里无上限堆积。

### 10. 如何评估一个 AI 智能体的效果？除了准确率，还会关注哪些指标？

**参考答案**

结论：先定义这件任务怎样算做成，再看有没有依据、走了多少步、慢不慢、贵不贵、有没有越线。开放生成上的单一准确率覆盖不了这些。

任务成功率看多步是否办完，例如查到正确产品并给出有依据的说明。忠实度看陈述能否对上检索片段或工具字段。工具侧看有没有选对、参数合不合法、是否无效调用和打转。

体验看首 token、端到端和平均步数。成本看 token 和工具次数。合规用红线集，承诺收益、越权、泄露和提示注入被拦住才能上线。人工侧看接管率、改写率和重复来访。

同一批输入多跑几次，看结论会不会乱跳。离线用固定评测集，线上抽样复查。用模型当裁判时，只核对照证据是否支持陈述。

### 11. 手写算法：实现一个 LRU（最近最少使用）缓存。

**参考答案**

用哈希表定位节点，用双向链表维护使用顺序。链表靠近头的是最近使用，靠近尾的是最久未使用。`get` 未命中返回 -1，命中则把节点移到头部。`put` 已存在就改值并移到头部；不存在就插入头部，尺寸超过容量时删掉尾部。查找、移动、删除在已知节点时都是 O(1)，总时间 O(1)，空间 O(capacity)。

更新已有 key 也算一次使用，但不会因为更新而淘汰。只有插入新 key 且 `size` 超过容量才删除。头尾哑节点让删头、删尾不用分情况。这是单线程结构。并发缓存要另加分段锁或用并发哈希表，不能假设这里的链表能被多线程同时改。

JDK 里可以用 `LinkedHashMap`：构造参数 `accessOrder = true`，再在 `removeEldestEntry` 里于 `size() > capacity` 时丢掉最久未访问的条目。这里的初始容量只是哈希表大小，淘汰上限靠 `removeEldestEntry`。读取要走会更新访问顺序的 `get`。它同样不是线程安全的。

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    static class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node oldest = tail.prev;
            unlink(oldest);
            map.remove(oldest.key);
        }
    }

    private void moveToHead(Node node) {
        unlink(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}
```

### 2. 请详细阐述你经历中最有挑战性的一个项目，你在其中的角色、技术架构、以及遇到的最大技术难点是什么？

### 3. 在智能体系统的开发中，如何管理提示词（Prompt）的版本和效果？如何做 A/B 测试？

**参考答案**

结论：提示词按配置发布，每次请求记下版本；效果先过离线评测，再按用户或会话分流做对照，并保留一键回滚。

模板放进版本库，带 id、版本号、适用模型和变更说明。运行时按版本加载。日志里同时记下提示词版本、模型名和工具 schema 的版本，否则线上一条坏回答无法复现。用户内容放在明确边界里，和系统指令分开。发布顺序是评测、小流量、全量，任一档都可以退回上一版。

对照实验的分流单位用 userId 或 sessionId 的哈希，使同一个人在实验期间走同一版本。一次只改一个因素，例如一句指令或一个模型。先看合规拦截和失败率有没有变坏，再比较任务成功率、人工改写率、延迟和 token。流量还很小的时候，不下「已经更好」的结论。

工具描述和输出 schema 要跟提示词一起版本化。只改了措辞、却换了工具列表，对照的就不是同一条链路。

### 4. 场景题：一个智能营销推荐系统，需要实时根据用户行为调整推荐策略。如果使用智能体，如何设计它的「记忆」和「学习」机制，使其能进行个性化推荐？

**参考答案**

结论：个性化来自可追溯的记忆和近线更新的策略。在线只读特征和白名单活动，不在对话里改生产模型的权重。

记忆分三层。这次会话里的点击、关闭和拒绝放 Redis，并设 TTL。偏好、已购、某活动已曝光次数、是否授权，落在数据库或特征库，模型不能直接改主数据。曝光、点击、转化和投诉作为事件进入消息队列，供后面的作业消费。

学习也分层。在线时，智能体读取特征和候选活动，在白名单里组织文案或选择触达时机；排序分由推荐策略给出。用户当次说不感兴趣，立刻写入负反馈，本轮后面的推荐就要避开。近线作业更新疲劳度和兴趣标签。活动之间的权重可以按转化做小步调整。模型权重的训练放在离线，按批次生效。

利率、额度和优惠只引用活动配置。频控和退订在发送前检查。小流量探索新活动，不把未验证文案推给全部用户。用户注销时，这三层记忆都要能删。

### 5. 如何保证 AI 智能体输出的稳定性和可控性？特别是在金融领域，如何避免「幻觉」或产生不合规的内容？

**参考答案**

结论：事实从工具和检索来，话术在模型之后再过一道规则。提示词里写「不要编造」挡不住幻觉。

余额、费率、收益率有接口字段就填字段，不让模型心算后当成官方数字。输出先落成结构化结果：结论、证据 id、风险提示。schema 不合法就有限次重试，仍失败就转人工或返回固定话术。检索不到就说明不知道，并给出下一步，例如查公告或转人工。

知识库里的文档带生效时间，过期材料不能被召回。生成之后再用合规策略扫一遍，承诺收益、绝对化用语和未披露风险替换成固定口径。温度调低只能减少随机，不能代替证据。

下单和调仓由人确认。用户原文和检索片段都不能改工具白名单。每次回答留下证据和版本，投诉时能回放。上线前用一组红线输入做回归：诱导违规、提示注入、过期产品。

### 6. 如果智能体的决策依赖一个响应较慢的大模型，如何设计异步调用和回调机制，避免阻塞主业务线程？

**参考答案**

结论：主链路只受理并落下状态，模型调用交给独立工作者。完成后再按业务单号写回结果。进程内的等待扛不过重启，也占着连接和配额。

接口立即返回受理号，状态为处理中。请求写入数据库并投递消息，工作者拉取后调用模型。工作者使用单独的并发上限，HTTP 客户端分开设置连接超时、首包超时和整次截止时间。虚拟线程可以减少平台线程被阻塞占满的问题，但配额、截止时间和落库仍然要做。

供应商若只提供同步接口，就由工作者等待，不由接入线程等待。供应商若支持回调，回调要验签、拒绝过期时间戳，并以任务 id 幂等。重复回调靠唯一约束只生效一次，处理回调的线程只做校验和入账，重活再丢回队列。

用户还连着就用已有的流式通道推送；连接已断就写站内消息，查询接口读数据库。用户取消或会话过期后，晚到的结果标记作废，不写进新会话。超过任务截止时间就标失败，读请求可以安全重试，写请求转人工或等待对账。

### 7. Kafka/RocketMQ 在智能体事件驱动架构中可以如何应用？比如用于分发用户请求、记录智能体行为日志等。

**参考答案**

结论：命令和日志分成两类主题。命令驱动会改状态的动作，日志用于审计、评测和回放。回放日志不能再次扣款或发券。

用户请求可以先落库再投递，工作者按分区水平扩展，入口不被模型耗时拖住。分区键用 userId 或 sessionId，使同一会话在单分区内有序；该分区上的处理不要再并发打乱顺序。行为日志记录规划步骤、工具调用和最终回复，供回放和抽样评测。对话结束后的摘要、标签更新也通过事件交给近线作业。

两边常见都是至少一次，消费方按业务单号幂等。消息体只放引用和摘要，大段上下文放数据库或对象存储。

Kafka 适合高吞吐日志，可以用消费位点重放一段历史。RocketMQ 适合和本地事务绑在一起的业务事件，也适合延迟消息：半消息在本地事务成功后提交，不确定时回查；超时关单可以用延迟消息触发。金融业务事件更常需要事务消息和定时补偿，行为日志更看重吞吐和回放。二者按这个边界并用，不互相替代。

### 8. 描述一下你在项目中如何进行性能调优的？请结合 JVM、数据库或缓存举例。

**答题思路**

先讲目标和证据，再讲你改了什么。选 JVM、数据库、缓存里你真做过的一类展开，另外两类知道定位顺序即可。

1. 说清变慢的是哪条接口、哪个时间段，看的是延迟、错误率、CPU、GC、慢查询还是命中率。先有优化前的曲线。
2. 分段：网关排队、应用内部、数据库、缓存、下游。同时间窗的线程栈、GC 日志、执行计划和慢日志放在一起看。
3. 一次只改一个因素，用同一指标对比。没有数字，就说明观察了哪段时间、哪条曲线。

可以讲的真实例子，按你做过的选：

- JVM：暂停变长或老年代持续上涨时，先看线程是在跑业务、等锁，还是停在 GC。无界缓存和一次性读入的大响应会把对象留到老年代。先限制集合大小和生命周期，再谈堆。JDK 17、21 的默认收集器是 G1，先分清是普通回收还是整堆回收，再考虑更换收集器。
- 数据库：看执行计划里过滤有没有走到索引，有没有回表、文件排序或临时表。列上套函数、类型对不上，会让该索引用不上。深分页改成按主键向后扫。连接池等待变多，先查是不是慢语句占着连接不还。
- 缓存：同时看命中率、热 key 和大 key。更新数据库成功后删除缓存，删除失败要重试；并发写入时直接改缓存，可能把旧值写回去。热 key 回源用单飞，同一批过期用 TTL 抖动。

收在你如何确认没有把错误率或资源占用换到别的地方。

### 9. Elasticsearch 除了全文检索，在智能体相关业务中还有哪些应用场景？（例如：向量相似度搜索用于召回、行为日志分析）

**参考答案**

结论：智能体里 Elasticsearch 主要做「带过滤的混合召回」和「对话轨迹的检索分析」。它近实时，不承担余额和订单这种账。

知识库可以用 BM25 和 `dense_vector` 的 kNN 一起召回。专有名词、产品代码靠全文，换一种说法靠向量，两路结果可以按倒数排名融合。权限、产品线和生效时间放进同一次查询的过滤条件。过滤很严时，近似近邻可能召不齐，小集合上要能退回精确计算。向量维度必须和嵌入模型一致，换模型就重建索引。

行为日志按 trace 查一次对话的全部步骤，并聚合工具失败率、某意图的延迟。索引按时间做冷热分层，避免无限膨胀。日志可以晚一点可见；命令通道仍用消息队列，不把 Elasticsearch 当队列。

默认大约一秒刷新一次，写入后不能立刻当成刚刚发生的交易去查。召回阶段就做权限过滤，不把无权片段交给模型再指望它不说出来。

### 10. 如果由你来主导一个从零开始的 AI 智能体项目，你的技术选型思路和团队协作规划是怎样的？

**参考答案**

### 11. 手写算法：二叉树的锯齿形（Z 字形）层序遍历。

**参考答案**

按层做 BFS。每一轮先记下队列长度 `size`，只处理这么多个节点，新入队的孩子属于下一层。第 0 层从左到右，之后奇偶交替。孩子始终先左后右入队，方向只影响这一层结果的书写：先按从左到右收集，奇数层再反转。

时间 O(n)，空间 O(n)，主要是队列和结果。空树返回空列表。用双端队列按头插收集，总体仍是 O(n)；若对 `ArrayList` 每次插到下标 0，一层很宽时会退化成 O(n²)。先按从左到右收集再反转这一层，总体 O(n)，也不容易把下一层的入队顺序写反。

根为 3，左 9，右 20，20 的左右是 15 和 7 时，结果是 `[[3],[20,9],[15,7]]`。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Queue;

public class ZigzagLevelOrder {
    static class TreeNode {
        int val;
        TreeNode left;
        TreeNode right;

        TreeNode(int val) {
            this.val = val;
        }
    }

    public List<List<Integer>> zigzagLevelOrder(TreeNode root) {
        List<List<Integer>> ans = new ArrayList<>();
        if (root == null) {
            return ans;
        }
        Queue<TreeNode> queue = new ArrayDeque<>();
        queue.offer(root);
        boolean leftToRight = true;
        while (!queue.isEmpty()) {
            int size = queue.size();
            List<Integer> level = new ArrayList<>(size);
            for (int i = 0; i < size; i++) {
                TreeNode node = queue.poll();
                level.add(node.val);
                if (node.left != null) {
                    queue.offer(node.left);
                }
                if (node.right != null) {
                    queue.offer(node.right);
                }
            }
            if (!leftToRight) {
                Collections.reverse(level);
            }
            ans.add(level);
            leftToRight = !leftToRight;
        }
        return ans;
    }
}
```

### 2. 谈谈你对行业大模型（如 GPT、通义千问等）和领域/企业专属小模型结合应用的看法。在落地时如何抉择？

### 3. 智能体系统与现有中台（业务中台、数据中台）该如何融合？会带来哪些新的架构挑战？

**参考答案**

结论：业务中台继续拥有交易、账户、产品和权限。数据中台提供有口径、有时效的特征和指标。智能体是上面的编排和解释层，通过工具调用中台，不复制一套账。

融合时先包一层稳定的工具 API，把幂等、错误码、权限和返回字段说清楚，模型不直接打中台内部接口。用户身份随调用传到下游，不能用一个超级账号替所有人查询。

新的挑战主要在契约和时效。中台接口原来写给后端程序，返回往往太大，也缺少「能否重试」的说明。标签如果是 T+1，回答里就要带上数据时间，不能说成刚刚发生。接口升级会让工具 schema 失效，所以要有契约测试。一次对话会横切多个领域，需要场景负责人把接口冻结下来。链路追踪要从智能体的 trace 跟到中台的调用。

智能体运行时自己要补的是会话、提示词版本、工具网关和审计。这些状态不属于任一业务中台，但权限和交易结果以中台为准。

### 4. 场景题：假设我们要设计一个供应链金融的风险评估智能体，它需要整合企业多维度数据（经营、舆情、交易链），并给出动态风险评分。请勾勒核心系统模块和数据流转图。

2. 动机落到一个具体缺口：项目里一次失败、实习里一段讲不清的链路，或你发现 Java 服务要接模型时缺了哪块。
3. 方法按顺序讲：一条主线材料，一个小到能跑的实现，一组你自己造的坏例，再把取舍写下来。学会的标准是能独立讲清失败时状态停在哪，而不是看完目录。
4. 收在这个岗位上：你准备把这套方法用到工具调用、评测或一致性的哪一层。

材料名称和页码不重要，能讲出你做过的那个小系统和一组反例就够了。

### 8. 在团队管理或跨团队协作中，你认为最重要的原则是什么？

**答题思路**

校招没有带人经验，就讲协作，不要编管理幅度。原则只留一条，讲透。建议用：目标、接口和责任写清楚，分歧可以追溯。

1. 先说原则。跨团队容易坏在各自假设不同，信息和决策留得下来，后面才改得动。
2. 你怎么做：开始时对齐怎样算完成；接口写明谁负责哪一段、失败返回什么；阻塞时带上可选方案和时间影响再升级；答应的时间有变化就提前说。
3. 用一个真实的小组作业、实习或项目协作举例，不编团队和职级。讲你当时对齐了什么、哪里曾经假设错、后来记在了哪里。
4. 扣到这个岗位：智能体项目会碰到业务、风控、合规和中台，先对齐红线和接口，再谈模型效果。

原则背成「沟通、责任、双赢」三条，等于没有原则。

### 9. 手写算法：接雨水问题。

**参考答案**

每个位置能接的水，等于它左边最高柱和右边最高柱的较矮者，减去自身高度；小于 0 就是 0。从两边向中间走，可以用 O(n) 时间和 O(1) 额外空间算完。

维护 `leftMax` 和 `rightMax`，表示两端已经见过的最高值。每一步先把当前左右柱子纳进去。哪一侧的 max 更小，哪一侧就是短板，因为另一侧已经出现过不低于它的柱子。该位置的水量是这一侧的 max 减去当前高度，然后这一侧向中间移动。左右指针相遇时结束。

单调栈也可以：栈里放递减的下标，当前柱更高时弹出栈顶作为槽底，新栈顶和当前下标是左右边界，按宽度累加。时间同样 O(n)，栈需要 O(n) 空间。下面用双指针。

`[0,1,0,2,1,0,1,3,2,1,2,1]` 的结果是 6。少于三根柱子接不住水。

```java
public class TrappingRainWater {
    public int trap(int[] height) {
        if (height == null || height.length < 3) {
            return 0;
        }
        int left = 0;
        int right = height.length - 1;
        int leftMax = 0;
        int rightMax = 0;
        int water = 0;
        while (left < right) {
            leftMax = Math.max(leftMax, height[left]);
            rightMax = Math.max(rightMax, height[right]);
            if (leftMax < rightMax) {
                water += leftMax - height[left];
                left++;
            } else {
                water += rightMax - height[right];
                right--;
            }
        }
        return water;
    }
}
```

## HR面

### 1. 请做一个简单的自我介绍。

**答题思路**

HR 听得懂的版本，一分钟。技术名词最多留一个。

1. 学校、专业，以及你主要做 Java 后端还是已经做过模型应用。
2. 一件最能代表你的事：项目、实习或竞赛里你负责的部分和结果。用事实，不用「学习能力强」开头。
3. 为什么看蚂蚁的补录：想把工程做进金融业务，而不是只做演示。
4. 一个具体习惯，例如先把失败状态写下来再改代码、评审时把反对意见记进记录。

讲完停住。不要把三面的架构再讲一遍。

### 2. 为什么选择蚂蚁金服？对我们有什么了解？

**答题思路**

把「业务约束」和「你的方向」接上，用公开信息，不编内部团队和数字。

1. 你了解的公开业务选一到两个，用自己的话说：支付、理财、信用或信贷。点出它们同时要求正确、合规和体验。
2. 为什么是现在：春招补录这个时间点，你的方向已经从 Java 服务走到想把模型放进真实链路。
3. 匹配：你在意的是工具调用、一致性和审计这类工程问题，和金融场景对得上。
4. 了解停在公开产品和岗位要求。不知道的内部项目直接说还想在入职后了解。

避免只说平台大、机会多。薪资放到对方询问时再谈，不在这里报价。

### 3. 你过往经历中遇到的最大挫折是什么，如何克服的？

**答题思路**

选学业、项目或实习里一次真实没做成或一度失控的事。按「当时的结果 → 你的责任 → 你改了什么 → 现在会提前做什么」讲。

1. 情境一句就够，把时间放在你的判断上。
2. 责任讲具体：准备不足、边界没对齐、关键路径没有提前验证。不把原因推给同学或环境。
3. 行动要有顺序：你先确认了哪件事，改了哪一个做法，最后结果怎样。结果仍然不理想，就说明你如何收场。
4. 收在可迁移的习惯：提前写出失败状态、中途同步风险、留下可以复查的记录。

不要用「我太追求完美」或「我压力太大但都克服了」这种没有事件的回答。

### 4. 你的职业规划是什么？未来 3 年希望成为什么样的人？

**答题思路**

按校招的三年讲，和补录岗位对齐，留出业务变化的余地。

1. 第一年：把金融后端的正确性做扎实，能独立负责一条小链路，包括超时、幂等和日志。若团队在做智能体，你希望先守住工具调用和评测，而不是先追求模型规模。
2. 第二年到第三年：能负责一个场景从方案到上线，在一致性、检索或风控协作里有自己的判断，并能带一个新人看懂这条链路。
3. 说明你愿意随业务调整具体技术，不把三年规划写成某个框架的名单。

不说三年做管理，也不说先来看看再决定。管理如果出现，是把事情和接口担起来，不是职级目标。

### 5. 你一般如何应对工作压力？

**答题思路**

承认压力会有，讲你怎么区分和怎么同步。用一次考试、项目截止或实习高峰当例子。

1. 先分清是日期明确的交付，还是线上故障。前者拆成可检查的小步，后者先保住数据和合规，再修体验。
2. 做法：写下优先级，先做会阻塞别人的那件；发现可能延期，在还来得及调整时说出来，并带上你建议砍掉或延后的部分。
3. 恢复方式只讲一个你真实在用的，例如固定睡眠、运动或把问题写下来后离开屏幕。
4. 例子里说清压力从哪来、你改了哪一个做法、结果如何。

不要说自己没有压力，也不要把连续熬夜说成常态。

### 6. 你期望的团队氛围是怎样的？

**答题思路**

说具体行为，不说「像家一样」。

1. 目标写得清楚，评审对事，新人可以问到听懂为止，代码和方案有人看，线上问题有复盘。
2. 你怎么配合：按时说清进度，接口和失败情况写明白，愿意补测试和记录。
3. 用实验室、课程项目或实习里一段有效的协作说明你为什么在意这些，不贬低以前的环境。
4. 补一句：金融业务有明确标准，氛围好指的是问题能摆到桌上，不是没有要求。

### 7. 目前有其他公司的面试或 Offer 吗？

**答题思路**

如实说。用选择标准回答，不用别家来加压。

1. 有在进行的流程，就说到哪个阶段，公司可以讲公开的那一层。薪资数字不主动比较。
2. 选择标准按这个岗位：能否做进真实金融业务、工程要求是否严格、你前三年能不能独立负责一条链路。
3. 还没有结果，就直接说没有，并说明蚂蚁是你想继续走的原因。
4. 对方问时间，就给出你真实的节点；没有节点就说可以按对方流程走。

不虚构 Offer，也不把「只有你们」说成策略。
