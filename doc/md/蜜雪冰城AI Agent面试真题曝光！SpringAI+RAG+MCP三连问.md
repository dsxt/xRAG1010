## 一面

### 1. 自我介绍

**答题思路**

一两分钟，按「现在做什么、一个真实项目、和岗位的关系」讲完就停。

1. 年限和方向只说你实际写的那一层：模型接入、检索、工具编排或业务系统。
2. 只展开一个你真正做过的系统：谁在用，一次请求最后交付什么，你负责哪一段。
3. 主动落到这次会问的点：ChatClient 你用过哪部分、知识从哪来、工具有没有副作用。
4. 数字只用自己能量出来的。停在联调或内测，就说停在哪一层。
5. 收在一个可追问的点上，例如记忆存在哪、检索怎么验收。

### 2. 项目介绍

**答题思路**

用真实项目，按一次请求把链路讲完。后面的追问会拿这段话逐项拆。

1. 先讲问题和边界：用户是谁，Agent 允许做什么，哪一类请求明确不做。只读查询和会改数据的动作分开。
2. 再讲模块：入口和会话、编排、模型、工具、检索、记忆、校验。每个模块用一句话说输入和输出，点名你写的部分。
3. 准备一个取舍：事实为什么走检索，工具为什么留在进程内或拆成独立服务。
4. 准备一个故障：现象、你怎么判断是检索、提示词、工具还是模型，改了什么，用哪组案例确认。
5. 结果用你有的事实：上线了没有、谁在用。没有指标就停在事实，不补时延和准确率。

### 3. Spring AI 是什么？它的核心架构是怎样的？

**参考答案**

Spring AI 是把大模型接进 Spring 应用的框架，用同一套 API 挡住各家供应商的差异。

调用从 ChatClient 进入，写法接近 RestClient，真正发请求的是 ChatModel。文本向量化走 EmbeddingModel，相似检索走 VectorStore。一次调用外面是 Advisor 链，记忆、检索增强和工具循环都插在这里。工具用 `@Tool` 方法或 ToolCallback 交给模型。文档侧是 Reader、Transformer、Writer：读原文、切块、嵌入、写入向量库。

换模型供应商时，主要换 starter 和配置。ChatModel 只做单次补全；多轮工具由谁执行，是 ChatClient 和 Advisor 的职责。

### 4. Spring AI 2.0 相比 1.x 有哪些关键变化？

**参考答案**

2.0 换的是运行基线和工具编排。2.0.0 对齐 Spring Boot 4.1，序列化跟着 Boot 4 使用 Jackson 3。

1.x 的 ChatModel 会在内部执行工具并再次调用模型。2.0 删掉了这条循环，`call` 只返回模型的原始响应；自动执行改由 ChatClient 上的 ToolCallingAdvisor 完成。`internalToolExecutionEnabled` 已删除。旧的 FunctionCallback API 也删除了，统一为 ToolCallback，函数式工具用 FunctionToolCallback 构建。要自己控制循环，就直接调用 ChatModel，再用 ToolCallingManager 执行。

会话必须每次传入 conversationId，原来的默认会话没了。PromptChatMemoryAdvisor 删除，用 MessageChatMemoryAdvisor 把历史按消息放进提示。ChatClient 的选项改为传 Builder，选项对象不可变。框架不再默认把 temperature 设为 0.7，没配置就用供应商自己的默认值。

MCP Java SDK 升到 2.0，注解进入 `org.springframework.ai.mcp.annotation`，服务端默认按 JSON Schema 校验工具入参。工具很多时，可以用 ToolSearchToolCallingAdvisor，只把相关工具定义发给模型。

### 5. 什么是 RAG？它解决了大模型的哪些痛点问题？

**参考答案**

RAG 是检索增强生成：先从外部知识里找出相关片段，再连同问题交给模型生成，权重保持不动。

它补的是参数记忆的缺口。训练有截止日期，新制度和内部文档不在权重里；私有知识不能靠反复训练来更新；整库放不进上下文，硬塞既贵又会被截断；只靠参数生成时，错了也没有出处。检索把「知道什么」放到可更新的索引里，答案可以带回片段来源。

检索失败或片段互相矛盾时，模型仍可能编造。RAG 解决知识从哪来，生成之后还要单独做忠实度检查。

### 6. RAG 与传统微调的核心区别是什么？

**参考答案**

微调改变权重，RAG 改变这次推理读到的材料。

微调适合稳定的行为：格式、语气、领域说法、工具使用习惯。知识仍在参数里，制度变化后要重新训练，答案默认没有出处。RAG 不改权重，更新索引就能更换知识，成本主要在嵌入、存储和每次检索，适合会变化的事实，也可以要求按片段作答。

行为用微调或提示词约束，事实用检索，两者可以同时存在。微调提高的是说话方式和任务格式，代替不了一份能追溯到来源的知识库。

### 7. 完整的 RAG 系统包含哪些核心步骤？

**参考答案**

分成入库和请求两条链路。

入库时解析正文，去掉页眉页脚，按章节或步骤切块。每块带上来源、标题路径和生效时间，用固定的嵌入模型向量化，连同原文和元数据写入向量库。更换嵌入模型后要整库重建，两种模型的向量不能混在同一次检索里。

请求时按需要改写查询，先按权限和元数据过滤，再做向量召回。专有名词同时走关键词，两路结果融合后重排。重排只处理已经召回的候选。然后把片段、出处和问题装进提示，要求模型依据这些材料回答。检索为空或片段冲突时，回答不确定。

文档变更要能重建索引，坏答案要能追到切分、召回或生成中的一层。

### 8. 向量数据库在 RAG 系统中承担什么作用？

**参考答案**

向量库是语义检索的索引，保存块向量、对应文本和元数据。查询被嵌到同一向量空间后，用 HNSW、IVF 这类近似近邻结构取 top-k。元数据用来限定租户、版本和权限。

关键词检索、重排和生成都在向量库外面。近似搜索要单独测召回率；先过滤还是先搜索，会同时影响延迟和结果。原文、权限和任务状态以数据库或对象存储为准。换嵌入模型后，旧向量和新查询向量不能比较，必须用同一个模型重建。

### 9. 什么是 MCP？它的核心价值是什么？

**参考答案**

MCP（Model Context Protocol）是模型和外部能力之间的开放协议。能力放在 MCP Server，宿主里的客户端负责发现和调用。一次会话里主要有三类：工具是模型可调用的函数，资源是可读的数据，提示词模板是可复用的提示。本地进程常用 stdio，远程常用 Streamable HTTP。

价值在于把每个应用各自对接工具，收成一套可复用协议。同一个 Server 可以被不同 Agent 宿主使用；工具列表由服务端声明，客户端运行时拉取。密钥和业务校验留在 Server，模型只看见允许暴露的能力。

模型会不会选对工具，仍取决于描述、上下文和宿主里的调用循环。

### 10. MCP 与传统工具调用方案有何区别？

**参考答案**

工具调用是模型按 schema 输出函数名和参数的能力。MCP 是这些函数如何被发现、鉴权和执行的协议。在 Spring AI 里，MCP 工具最终会适配成 ToolCallback，进入同一个工具循环。

进程内工具和这次请求的 schema 一起发给模型，执行也在同一份代码里，延迟低，适合跟业务同生共死的小工具。每个宿主都要再接一遍，密钥也容易和模型进程放在一起。

MCP 把工具放到独立 Server，客户端用 tools/list 发现，再用 tools/call 执行，中间是 JSON-RPC。同一 Server 可以给多个宿主共用，除函数外还能提供资源和提示词模板。代价是多一跳进程或网络，超时、会话和协议版本要单独处理。需要跨团队复用，或把密钥隔离出去时，再做成 MCP。

### 11. Spring AI 中如何集成 MCP？

**参考答案**

调用别人的能力时做客户端，把自己的接口暴露给 Agent 时做服务器。

客户端引入 `spring-ai-starter-mcp-client`，在 `spring.ai.mcp.client.streamable-http.connections` 下按名字配置 url，端点默认是 `/mcp`。本地进程则配置 stdio 的启动命令。启动器为每个连接建立一个客户端，把 tools/list 的结果适配成 ToolCallbackProvider，交给 ChatClient 的 `tools`。后续选择和多轮执行仍由 ToolCallingAdvisor 负责。自动配置的客户端是应用级单例，一条连接共用一个协议会话。tools/list 在连接建立时拉一次；服务端若按身份过滤工具，后来的用户会看到第一次发现的列表。需要按用户隔离会话时，要自己创建和关闭客户端。

服务器用 `spring-ai-starter-mcp-server-webmvc` 或 WebFlux，`spring.ai.mcp.server.protocol` 设为 `STREAMABLE`。Bean 方法上使用 `@McpTool` 和 `@McpToolParam`，2.0 的包名是 `org.springframework.ai.mcp.annotation`。服务端默认按生成的 JSON Schema 校验入参。租户、幂等和密钥放在 Server 方法里，多个 Server 的工具名用前缀或过滤器避免冲突。

### 12. 什么是 Agent Skills？在 Spring AI 中如何实现？

**参考答案**

Agent Skills 用目录描述一项能力：文件夹里必须有 SKILL.md，YAML 头写 name 和 description，正文写步骤，旁边可以放参考文档和脚本。技能告诉模型怎么做，它自己不执行代码。

省上下文的办法是渐进披露。启动时只把名字和描述放进工具说明；模型判断相关后，再调用技能工具读入全文；要读文件或跑脚本时，再走文件系统、Shell 或 MCP 工具。描述写错，技能就不会被选中。

Spring AI 核心没有单独的 Skill 模型 API。实现就是一组 ToolCallback：Skill 工具按名字返回 SKILL.md 和目录，真正的副作用交给受限制的 Read、Shell 或 MCP。社区项目 spring-ai-agent-utils 的 SkillsTool 就是这个做法。脚本和路径用白名单限制。技能负责说明，MCP 负责可调用的标准接口，说明里点名的动作仍然要有真实工具去执行。

### 13. Redis 在 AI Agent 系统中可以用于哪些场景？

**参考答案**

Redis 放的是要共享、要快、生命周期短的状态。知识原文仍以文档库为准。

会话记忆可以按 conversationId 存在 Redis 里，Spring AI 的 ChatMemory 能接这种仓库，多实例就能接着同一段对话。相同请求的模型结果可以做缓存，知识或权限变化后必须失效。有副作用的工具用 SET NX 或锁加幂等键，避免模型重试造成重复执行。按用户累计调用次数或 token，用来限流和卡住预算。多步任务的进度可以放在 Redis，进程重启后能查到停在哪一步；要审计和可靠投递时，把权威状态放到数据库或消息中间件。

带向量检索模块的 Redis 也能做中小规模的块检索。会话消息、缓存和任务进度使用不同的 key，工具调用的中间消息不要无筛选地写进长期会话。

### 14. 如何设计一个高可用的 RAG 系统？

**参考答案**

模型不可用、检索不可用、索引过期，是三种要分开处理的故障。

嵌入服务和向量库做多副本，查询设置超时。向量库不可用时，降级到关键词检索，或明确告诉用户暂时查不了；这时不要改用模型的参数记忆回答业务事实。生成侧准备可切换的供应商，只对超时和 5xx 做有限次重试，重试带上幂等，避免流式响应重复计费。

索引管道和查询分开部署。解析、切块、嵌入、写入做成可重放的异步步骤，写入带版本号。新索引先用同一批问句影子运行，召回和引用没有退步再切换，并保留旧版本以便回滚。查询只读已发布版本。

权限过滤放在检索前。缓存键带上租户和文档版本。分别告警依赖健康、检索为空的比例、引用率和生成超时。嵌入和重排通常比向量查询更早打满，这两处要能水平扩展。

### 15. 在实际项目中，你如何评估 RAG 系统的效果？

**参考答案**

准备一套带标准依据的问句，离线和线上分开看。分数只报你真正测过的那一组。

离线把链路拆开。召回看标准片段在不在 top-k，用来暴露切分和嵌入的问题。生成看答案是否被这些片段支持、有没有引用、该拒答时有没有拒答。忠实度看结论能不能在片段里找到出处。另外准备「库里没有」的问题，模型编造了就算失败。问句按真实分布覆盖专有名词、跨片段问题、过期文档和权限外的请求。改切分、嵌入或提示词时，用同一套问句比较差异。

线上看用户是否追问、是否打开引用、抽检的错误类型，以及检索为空的比例。时延和 token 单独记录。还没有标注集时，先从线上坏案例整理几十条，再谈分数。

## 二面

### 1. 自我介绍

**答题思路**

二面改成「我负责的系统」，仍然一两分钟。

1. 用一句话交代方向，不再重复一面的完整履历。
2. 进入你最近那个 Agent：业务目标、你的边界、请求经过哪些模块。
3. 点出准备被追问的三处：工具副作用、记忆放在哪、检索怎么验收。
4. 公司、职级和薪资不在这段里讲。没有的指标不说。

### 2. 详细介绍一下你最近做的 AI Agent 项目

**答题思路**

讲你真实做过的项目。这段是后面所有项目题的提纲。

1. 场景：谁在什么情况下发起，成功时交付的是一句话、一条记录，还是一个已经执行的动作。
2. 边界：只读查询和会写库、会调用外部系统的工具分开。说出一类你明确拒绝自动化的请求。
3. 按时间讲链路：会话、是否规划、检索或工具、参数校验、执行、把观察写回上下文、最终答复。多步任务说明停止条件。
4. 你的角色：编排、检索、工具、评测里哪些是你写的，哪些是现成组件。
5. 留下三个可追问的口：记忆的存储、一次工具失败怎么处理、你怎么知道它答对了。

### 3. 在项目中如何设计 Agent 的架构？有哪些核心模块？

**答题思路**

只讲项目里真实存在的模块。建议按下面的顺序，没有的模块直接说没有。

1. 入口：同步接口还是异步任务。用户身份和租户在这里确定，后面的检索和工具都带上。
2. 编排：谁决定下一步。步骤固定的流程用代码推进；需要模型选择工具时，说明循环的最大步数。
3. 模型访问：只负责补全和结构化输出，不直接碰数据库。
4. 工具：每个工具的入参校验、有没有副作用、超时和幂等。只读和写入分成两组权限。
5. 知识：文档怎么进来、怎么切、查询时怎么过滤。知识和记忆分开存放。
6. 记忆：这一轮的草稿、跨轮会话、可以长期检索的事实，分三种存储。
7. 护栏和观测：什么情况拒绝执行，一次 trace 里能不能看到每次模型输出和工具入参。

工具结果以外部系统为准，模型生成的文字不是业务状态。

### 4. 项目中如何实现工具调用？遇到了哪些挑战？

**答题思路**

先讲机制，再讲你真实遇到的一个问题。没有线上事故，就讲设计时防住的那一个。

1. 定义工具名、参数 schema 和给模型看的描述。描述写清何时调用、何时不调用。进程内用 `@Tool` 或 ToolCallback；跨进程用 MCP，再适配进同一次工具循环。
2. 模型返回 tool call 后，由应用执行，把结果作为工具消息送回，直到最终答复或到达步数上限。Spring AI 2.0 里这个循环在 ToolCallingAdvisor。
3. 从你的项目里选两个讲透：参数格式合法但业务不成立；有副作用的工具被重复调用；超时后不知道外部系统是否已经生效；工具太多，无关 schema 占满上下文。
4. 对应做法：写入前用业务代码校验；副作用使用幂等键；超时先查询状态；只暴露当前任务需要的工具。
5. 准备一组真实参数：模型当时填了什么，校验在哪一步拒绝。

### 5. 如何管理 Agent 的记忆？使用了什么技术方案？

**答题思路**

先分成三种记忆，再对上你项目里的存储。没用到的不说用了。

1. 工作记忆是这一次任务的工具结果和中间结论，只活在本次循环里。工具消息不必全部写入长期会话。
2. 会话记忆是跨轮还需要的目标和关键事实。用 ChatMemory 按 conversationId 隔离，仓库可以是内存、数据库或 Redis。Spring AI 2.0 每次请求都要显式带会话编号。说明你保留最近若干轮，还是先做摘要。
3. 长期记忆是跨会话仍要想起的偏好或业务事实，放在数据库或向量库，并且能删除。整段聊天不要无筛选地嵌入。

摘要会丢掉数字和否定，订单号、时间这类字段结构化保存。用户要求删除时，会话和长期记忆一起删。

### 6. 项目中 RAG 部分是如何实现的？文档分块策略是什么？

**答题思路**

按你的语料讲，顺序固定，方便追问。

1. 语料是手册、制度、表格还是问答，谁来更新，更新后索引怎么重建。
2. 解析保留了标题、表格和步骤里的哪些信息。
3. 分块说明原因。制度按章节；操作步骤把前提、警告和动作放在同一块；问答可以一问一块。固定长度只作为超长章节的兜底，并留一小段重叠。每块带文档编号、标题路径和版本。
4. 检索先做元数据过滤，再做向量召回。专有名词有没有关键词一路，有没有重排。
5. 生成时是否要求只根据片段回答，引用怎么回到原文。
6. 准备一个反例：哪类问题曾经被切散或召不回，块边界后来怎么改。没有评测就说明当时靠坏案例检查。

### 7. 如何解决 RAG 中的幻觉问题？

**参考答案**

先分开两种情况：片段没检索到，以及检索到了但回答没有照着说。提示词只能约束第二种。

检索上保持一块里的事实完整，查询先过滤权限和版本，专有名词同时走关键词，再用重排提高真正会被阅读的片段。召回为空就拒答，把空上下文交给模型会让它用参数记忆填空。

生成上要求每条关键事实对应给定片段，片段里没有的就说不知道。互相矛盾的片段一起给出，并允许回答不确定。结构化输出只能约束格式，约束不了事实真假。

上线后抽查答案里的数字和否定是否出现在引用片段中。新事实写入新的索引版本，而不是追加在系统提示词里。

### 8. 项目中是否使用了 MCP？如何设计和实现 MCP Server？

**答题思路**

先说用了还是没用。没用就说明工具留在进程内的原因，以及哪一个工具值得以后拆出去。

用了的话按这个顺序讲：

1. 独立进程是为了给多个宿主复用，还是为了把密钥和业务校验隔开。
2. 一个 Server 暴露哪些工具、资源和提示词。粒度按业务动作划分。
3. 实现用 MCP Server starter，方法上加 `@McpTool`，参数用 `@McpToolParam` 写明含义和是否必填。远程用 Streamable HTTP，只给本机 Agent 用时才用 stdio。
4. schema 校验通过后再做业务校验。身份由调用方传入，模型填写的用户编号不能当作鉴权结果。有副作用的工具要幂等。
5. 超时和下游 5xx 作为工具错误返回，写清原因。准备一个模型填错过的参数，以及服务端拦住它的那一步。

### 9. Agent Skills 在项目中是如何应用的？

**答题思路**

先说项目里有没有技能目录。没有就讲固定步骤现在放在流程代码或系统提示词里，以及如果改成技能会怎么切。

用过则按这几点讲：

1. 一个技能对应一类稳定流程。SKILL.md 写步骤和停止条件，description 写清何时启用，因为模型先靠描述决定要不要加载。
2. 启动时只放名字和描述，命中后再读全文。
3. 技能里的脚本和外部动作必须经过允许的工具或 MCP。写进 Markdown 不会自己执行。
4. 举一个你改过的技能：改的是说明还是工具，用哪组固定问句确认行为变了。
5. 这个技能允许哪些工具。高风险动作要有业务校验或人工确认。

### 10. 如何保证 AI Agent 系统的安全性？

**参考答案**

权限放在应用代码里。用户内容可以要求模型忽略系统提示，所以提示词不能当作安全边界。

身份在请求入口确定，放进工具上下文，由业务代码检查。工具按最小权限分组，只读和会下单、退款、改数据的分开，高风险动作要二次确认或人工审批。检索在取片段之前过滤租户和权限；片段已经进了上下文，提示词里的保密要求挡不住。

网页、文档和工具返回都当作不可信数据，不能当成新的系统指令。工具参数同时做 schema 校验和业务范围校验。密钥只放在服务端，MCP Server 只暴露业务动作。

循环限制步数、超时和重复的副作用调用。每次工具的参数和结果写入可审计的 trace。输出对个人信息做脱敏。准备一类用例：用户要求说出系统提示或其他人的数据，系统应拒绝，并且检索结果里本来就没有那些数据。

### 11. 项目中如何监控和观测 AI Agent 的性能？

**答题思路**

讲你真实打过的点。没有链路追踪，就说当时日志里看了哪几项。

1. 一次请求对应一条 trace，下面是模型调用、检索和每一次工具。能对上会话编号；完整提示词不要无控制地进入公共日志。
2. 模型看时延、超时、输入输出 token 和工具调用次数。
3. 检索看是否为空、返回条数和文档版本。检索为空但回答很具体，要单独能发现。
4. 工具看成功率、超时、业务拒绝和重复调用。有副作用的工具分开看。
5. 质量用抽检或用户追问，不和时延合成一个分数。
6. 准备一次真实排查：最后定位到模型慢、检索为空，还是某个工具超时。

### 12. 遇到 Agent 执行异常时，如何进行调试和排查？

**参考答案**

先把这一次的现场串起来：会话编号、每一步模型输出、工具名、参数、工具结果和最终答复。再判断停在哪一层。

模型没有调用该调用的工具，先看工具有没有注册进这次请求，以及描述和上下文够不够。调用了但参数非法，看 schema 和业务校验返回了什么，下一轮模型有没有读到这段错误。工具超时或结果含糊，先查下游是否已经生效，再决定能不能重试。检索为空却回答得很具体，回到召回和拒答。步数耗尽时，区分是重复同一调用，还是任务本身超长。

一次只改一层，用触发故障的原话重放。能固定下来的案例放进评测集。

### 13. 如何设计 Agent 的容错机制？

**参考答案**

失败要可见，副作用不重复，用户得到确定的下一步。

循环设置最大步数、单步超时和总超时。同一工具用相同参数连续失败就停止，并把错误告诉用户。只读工具可以有限次重试。会写数据的工具先用幂等键查询是否已经成功。超时当成结果未知，先查询再决定是否重做。

模型输出解析失败时，把校验错误送回模型一次；再次失败就结束。检索失败和供应商失败分开降级：可以切换备用模型来生成，检索不可用时不改用参数记忆回答事实题。

长任务把已确认的步骤落到存储里，重启后从该步骤继续，已经执行过的写入不再执行一遍。人工接管使用明确状态：挂起、等待确认、已取消。补偿做成独立工具，记在同一条 trace 上。

### 14. 在团队中如何协调 AI 模型工程师和后端开发工程师的工作？

**答题思路**

按一次需求从定义到上线讲协作接口。

1. 先写共同的完成标准：哪类问题必须答对，哪类必须拒答，时延上限，能不能产生副作用。
2. 模型侧负责提示词、嵌入、重排和离线问句集；后端负责会话、权限、工具、索引管道和线上追踪。坏案例两边一起补。
3. 契约放在工具 schema 和检索返回的字段上。模型侧不直接改生产库，后端不在无人评测的情况下改提示词。
4. 索引版本、提示词或技能、工具接口可以独立回滚。改了一层，就用同一批问句看是召回变了还是生成变了。
5. 举一个你真实遇到的分歧，例如上下文变长和超时之间怎么取舍。没有这种经历，就说你会先拿延迟和坏案例对齐。
