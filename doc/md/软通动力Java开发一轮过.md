### 2. Spring Bean 的生命周期

**参考答案**

单例 Bean 的主路径是：实例化、填充依赖、初始化回调、后置处理；容器关闭时再销毁。

1. 实例化。容器根据 BeanDefinition 调用构造器或工厂方法。构造器注入在这一步完成。
2. 填充属性。`@Autowired`、`@Value` 和 setter 注入发生在这里，早于任何初始化回调，所以 `@PostConstruct` 里可以使用已经注入的依赖。
3. Aware 回调。先执行 `BeanNameAware`、`BeanClassLoaderAware`、`BeanFactoryAware`。`ApplicationContextAware` 以及环境、事件发布器这类和容器相关的 Aware，是在 BeanPostProcessor 的前置处理里回调的。
4. 初始化。`@PostConstruct` 在前置处理阶段执行，接着是 `InitializingBean.afterPropertiesSet()`，然后是自定义 `init-method`。
5. BeanPostProcessor 后置处理。AOP 代理通常在这里生成，容器里最终拿到的是代理对象。初始化方法内部的 `this` 调用仍然打在原对象上。
6. 销毁。单例随容器关闭而销毁，顺序是 `@PreDestroy`、`DisposableBean.destroy()`、自定义 `destroy-method`。原型 Bean 交给调用方之后，容器不再管它的销毁。

循环依赖只发生在单例、并且依赖能通过提前暴露的引用来接上的时候：对象刚创建出来、初始化还没完成，会放进三级缓存。构造器之间互相依赖无法提前暴露。对方如果需要的是代理，这个代理要在提前暴露时就创建出来。

### 3. Spring 事务传播机制有哪些

**参考答案**

Spring 的传播行为定义在 `Propagation` 中，一共 7 种，默认是 `REQUIRED`。

1. `REQUIRED`：当前有事务就加入，没有就新建。内外层是同一个事务，外层回滚会带上内层已做的修改。内层抛出运行时异常后，事务被标记为只能回滚；外层吃掉异常再提交时，会抛出 `UnexpectedRollbackException`。
2. `REQUIRES_NEW`：挂起当前事务，用另一条数据库连接新建事务。内层提交之后，结果已经独立落库，外层回滚只作用于外层自己的事务。内层读不到外层尚未提交的修改。两边更新同一行时，两套连接会各自持有锁。
3. `NESTED`：当前已有事务时，在这个事务上建立保存点。内层失败只回滚到保存点，外层可以继续。外层最后若回滚，保存点前后的修改都属于这一个事务，会一起撤销。当前没有事务时，行为与 `REQUIRED` 相同。它依赖事务管理器支持保存点，`DataSourceTransactionManager` 可以，JTA 场景通常不行。
4. `SUPPORTS`：当前有事务就加入，没有就以非事务方式执行。
5. `NOT_SUPPORTED`：挂起当前事务，本方法以非事务方式执行。
6. `MANDATORY`：调用时必须已经处在事务中，否则抛 `IllegalTransactionStateException`。
7. `NEVER`：调用时必须没有事务，否则抛 `IllegalTransactionStateException`。

传播在调用经过 Spring 代理时才会按声明执行。同一个类内部直接调用方法，栈上没有代理，被调方法上的 `@Transactional` 不会另起或加入事务。默认只在 `RuntimeException` 和 `Error` 时回滚，受检异常要指定 `rollbackFor`。事务拦截器识别的是外部可调用的 public 方法。

### 4. MyBatis 和 JPA 你们怎么选

**参考答案**

按 SQL 是否要握在自己手里来选。复杂查询多、需要 `EXPLAIN`、SQL 要给别人评审，用 MyBatis。表结构稳定、以单表增删改为主、希望少写 SQL，用 JPA（常见是 Spring Data JPA 加 Hibernate）。

MyBatis 的 SQL 写在 XML 或注解里，执行计划可以直接看。动态条件用 `<if>`、`<foreach>` 拼出来。一级缓存属于当前 `SqlSession`：同一次会话里相同查询会命中，一旦执行更新语句就会清空。Spring 托管时，这个缓存跟着一次会话或一个事务走，不会跨请求共享。二级缓存要在 Mapper 上配置 `<cache>` 才生效；全局 `cacheEnabled` 默认是开的，但没有这段配置的命名空间不会缓存。多实例下二级缓存容易读到旧数据，业务项目里经常不启用。MyBatis 没有脏检查，改了字段就要自己写 `UPDATE`。

JPA 用持久化上下文做一级缓存。事务中修改托管实体的字段，flush 时按脏检查生成 `UPDATE`。关联默认懒加载，Session 关闭后再访问会抛 `LazyInitializationException`。Spring Boot 的 `spring.jpa.open-in-view` 默认是 `true`，会把 Session 延长到整个 HTTP 请求，懒加载因此还能触发，数据库连接也会被占用更久，线上常常关掉它。列表里逐条点关联会变成 N+1，用 fetch join 或 `@EntityGraph` 一次查出来。

同一张核心表只用一套持久化方案去写，避免一边脏检查、一边手写 SQL，更新和缓存对不齐。面试时把项目里实际用的那套讲透，另一套用来说明取舍。

### 5. MySQL 优化做过哪些

**参考答案**

先定位慢语句，再用 `EXPLAIN` 和索引改写法。从慢查询日志或监控里找出耗时长、扫描行数多的 SQL，确认访问路径之后再加索引或改语句。缓存和读写分离放在语句已经合理之后。

`EXPLAIN` 看 `type`、`key`、`rows` 和 `Extra`。访问类型从快到慢大致是 `const`（最多一行）、`eq_ref`（唯一索引联表）、`ref`（非唯一索引）、`range`（范围）、`index`（扫整棵索引）、`ALL`（扫表）。`rows` 是优化器的估算。`Extra` 里的 `Using index` 表示覆盖索引，查询列都在索引中；`Using index condition` 表示索引下推，过滤后再回表。`Using filesort` 和 `Using temporary` 说明排序或分组没有被索引接住。

索引建在 `WHERE`、`JOIN`、`ORDER BY` 真正用来过滤和排序的列上。联合索引遵守最左前缀：等值且区分度高的列放前面，范围条件放后面。需要回表的列很多时，把查询列收进索引做成覆盖索引。索引列外套函数、做运算，或者发生隐式转换（字符串列和数字比较），优化器就无法按这列做索引查找。`like '%xx'` 也用不上该列的普通前缀索引。统计信息过期，或者表很小，优化器仍可能选择扫表。

深分页把 `LIMIT` 很大的偏移改成按唯一有序键向后翻：

```sql
SELECT id, user_id, status
FROM orders
WHERE id > #{lastId}
ORDER BY id
LIMIT 20;
```

写入频繁的表要控制二级索引数量，每多一棵索引，插入和更新都要维护它。面试时拿自己真正改过的语句，对比改前改后的 `type` 和 `key`。

### 6. Redis 缓存穿透、击穿、雪崩怎么解决

**参考答案**

三种都会把压力打到数据库上，成因不同，要分开处理。

缓存穿透是要查的数据在缓存和数据库里都不存在，缓存永远建立不起来。先做参数校验，挡掉明显非法的 id。对确认不存在的 key 可以缓存一个空值，TTL 设短一些；这条数据后来写入成功时，把空值删掉。也可以在前面加布隆过滤器：判定不存在就直接返回，判定存在再查缓存和数据库，所以会有少量「看起来存在」的误判。标准布隆过滤器支持添加和查询，key 大量删除时要重建，或换用支持删除的结构。新 key 入库时同步放进过滤器，否则合法数据会被挡在外面。

缓存击穿是一个热点 key 过期的瞬间，很多请求同时发现缓存没有，一起回源。互斥重建可以让一个请求加载数据库：用唯一 token 作为锁的值，过期时间盖住本次回源；其他请求稍后重新读缓存。释放锁时先比对 token，避免删掉下一个持有者刚拿到的锁。

```redis
SET lock:item:1001 <token> NX EX 10
```

上面的 10 秒要按回源耗时调整。另一种做法是逻辑过期：key 不设 Redis 的 TTL，值里面放逻辑过期时间；发现过期后只允许一个线程重建，其余请求继续返回旧值。热点数据也可以不设过期，改由任务主动刷新。互斥会让没拿到锁的请求等待；逻辑过期会在重建完成前返回旧值。

缓存雪崩是大量 key 同一时刻过期，或者 Redis 本身不可用，流量一起落到数据库。写入时给 TTL 加一段随机偏移，把过期时间错开。实例故障用哨兵或集群做转移；RDB 和 AOF 负责把数据恢复出来，多副本才负责继续提供服务。应用侧对数据库限流，缓存不可用时返回降级结果，必要的话用本地缓存再挡一层。随机 TTL 解决的是同时过期，实例宕机要靠高可用、限流和降级。

### 7. 说下你项目里的微服务架构

**答题思路**

用大约 2 分钟把真实项目的边界和一条链路讲清。服务名、框架和一致性方案都用自己项目里的，没用过的组件不要临时加进去。

1. 边界：按业务能力拆成哪几块，每块的数据归谁。如果几个服务共用一个库，直接说出来，后面的事务边界才对得上。
2. 入口和同步调用：请求从网关进来之后，服务之间用 HTTP 或 OpenFeign 的，超时和重试怎么设。会重试的写接口要能对上幂等键。
3. 异步：哪些步骤放到消息队列，消费失败怎么重试，重复投递时怎么识别已经处理过。
4. 一致性：能放在一个本地事务里的写操作留在一个服务里。跨服务如果用了本地消息表、事务消息或 Saga，就讲实际用的那一种；没有做分布式事务，就讲现在如何靠最终一致和补偿把状态对齐。
5. 落到你写的那一段：从一个接口讲到表、缓存和失败后的处理。这是面试官追问的入口。
6. 排查：配置在配置中心还是打在包里，日志里有没有把同一次请求串起来的 traceId。

对方如果只想听调用关系，前四步收短，把时间留给自己负责的那段。

### 8. Docker 和 K8s 用过吗

**答题思路**

先说自己用到哪一层，再按「Docker 负责把应用打成镜像，Kubernetes 负责把容器跑起来并保持期望状态」补充。只用过其中一层，就把边界说清楚。

Docker 可以讲这些事实，并配一件自己做过的事：

1. 镜像是分层的只读模板，容器是在镜像上加一层可写层之后跑起来的进程。
2. 容器与宿主机共用内核，用命名空间做隔离，用 cgroup 限制 CPU 和内存。
3. Dockerfile 把依赖层和业务代码层分开，改代码时不必重做依赖层。配置用环境变量或挂载文件，构建时再确定环境。
4. 容器里的主进程在前台运行，日志写到标准输出，方便收集。

Kubernetes 按对象讲：

1. Pod 是调度单位。同一个 Pod 里的容器共享网络，通过 localhost 互相访问；Pod 重建后 IP 会变。
2. Deployment 维持副本数，滚动发布时用新 Pod 替换旧 Pod。
3. Service 提供稳定的访问入口，把流量转到当前就绪的 Pod。
4. 存活探针失败会重启容器；就绪探针失败会把这个 Pod 从 Service 的后端拿掉。启动慢的应用可以再加启动探针。
5. 配置放 ConfigMap，密钥放 Secret。
6. 集群里常见的容器运行时是 containerd。Docker 多用于本机或 CI 构建镜像。

没有独立运维过集群，就说明自己做到了写 Dockerfile、看容器日志或按现成清单发布，再把上面几个对象各自的职责讲准确。

### 9. 说一个你解决过的线上问题

**答题思路**

选自己真正处理过的一次，用 STAR 讲，控制在 3 分钟左右。公司、系统名和影响范围用记得住的事实，数量级说不清就讲现象。

1. 场景：什么业务，用户看到的是超时、报错还是数据错了，从什么时候开始，影响持续了多久。
2. 定位：先用监控把范围收到应用、数据库、缓存或下游，再用日志、链路或慢查询落到具体语句和代码。说明当时依据哪几个信号排除了其他层。
3. 原因：用一句话停在查到的那一层。
4. 处理分成两步：先止血，例如限流、回滚、扩容或降级；再改根因，例如补索引、加超时、做幂等或修正发出去的配置。
5. 结果：用什么现象确认已经恢复，之后留下了哪条告警或哪段防护。

准备一个追问：这次修复会不会把同一条数据再改错。没处理过的故障类型不要安到自己身上。

### 10. 能接受驻场吗

**答题思路**

按真实意愿直接表态，再把地点和周期问清楚。原帖的处理是可以接受，同时看项目情况，可以沿这个结构组织。

1. 能接受就明确说可以驻场，并问城市、预计周期、是全程驻场还是项目某个阶段驻场。
2. 通勤、家庭安排或另一个在谈的机会如果有硬约束，在这一问就说出来，说明什么条件下可以去。
3. 顺带确认汇报关系是外包公司还是甲方、差旅和加班怎么计算。这些会影响下一题的薪资口径。
4. 条件还不清楚时，表态「地点和周期合适就可以」，等对方补充项目信息后再确认。

### 11. 期望薪资

**答题思路**

报一个区间，数字用自己当前收入和目标城市的真实预期，这里不代填具体薪资。

1. 先对齐口径：税前月薪、一年发多少个月、有没有绩效、驻场或加班是否另算。外包报价和正式编制的结构不同，确认再报。
2. 区间的下限放自己能接受的数，上限放希望谈到的数。对方说会反馈时，把区间留下即可，当场不必再往下改。
3. 如果驻场城市、强度和上一题了解到的不一致，说明预期要随这些条件调整。
4. 被问到当前收入时，按真实总包说，包含每个月的固定部分和能算进年包的奖金。
