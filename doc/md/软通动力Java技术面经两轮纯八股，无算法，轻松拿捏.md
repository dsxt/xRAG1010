### 3. Java 中 final 关键字的作用

**参考答案**

`final` 表示这份定义或这个引用不再改，对象里面的状态仍可以变。

修饰类则不能被继承，修饰方法则不能被重写。修饰字段、局部变量或参数时只能赋值一次。空白 final 的实例字段在构造器里赋完，静态字段在静态初始化里赋完。引用被 `final` 固定后不能改指向，对象的字段仍然能改；要不可变，得字段本身也不可变。

构造过程中 `this` 没有逸出时，其他线程之后能看见 `final` 字段的初始化结果。它不保护之后的修改，也不能代替同步。lambda 和匿名类捕获的局部变量要是 final 或事实上的 final。`static final` 的基本类型和字符串，还得用常量表达式初始化，才会在编译期被折叠。

### 4. JVM 内存模型，各个区域的作用

**参考答案**

题目要的是运行时数据区各自干什么。JMM 管的是可见性和有序性，被追问再单独讲。

线程私有三块。程序计数器记下一条字节码地址，执行本地方法时为空，这块不会 OOM。Java 虚拟机栈按方法存栈帧，里面是局部变量表、操作数栈、动态链接和返回地址；栈深了是 `StackOverflowError`，栈扩不开是 OOM。本地方法栈给 native 方法用。

堆和方法区线程共享。堆放对象和数组，是垃圾回收的主战场，装不下抛出堆空间 OOM。方法区在 HotSpot JDK 8 及以后由元空间实现，放类元数据和运行时常量池，占的是本地内存，类太多会 `Metaspace` OOM。直接内存不属于上述分区，NIO 堆外泄漏时机器一样会满。字符串常量池从 JDK 7 起在堆里，不要把它说成还在永久代。

### 5. 垃圾回收算法，CMS 和 G1 的区别

**参考答案**

基础算法三种。标记-清除会留碎片。标记-复制把活对象拷到空区域，年轻代常用，代价是留出空间。标记-整理把活对象挪到一端，适合老年代，整理时要停顿。

CMS 只回收老年代，目标是短停顿。初始标记和重新标记会停顿，并发标记和并发清除与业务并行。它不整理，碎片多；并发期间产生的垃圾要等下一轮。老年代在回收完成前被填满，会退化成整堆压缩，停顿很长。重新标记也可能拖很久。JDK 9 废弃，JDK 14 移除。

G1 把堆切成等大的 Region，年轻代和老年代都由 Region 组成，优先收集垃圾比例高的那些。回收用复制，被收走的 Region 得到整理，并按期望停顿挑选收集集合。这个时间是目标，不是硬上限。JDK 9 起默认收集器是 G1。超过 Region 一半的对象进 Humongous 区，跨 Region 引用靠记忆集，记忆集会占额外内存。

两者都有并发标记，也都有停顿。新系统用 G1。CMS 只出现在还没升级的旧系统里。

### 6. 线程池的核心参数及其含义

**参考答案**

`ThreadPoolExecutor` 有七个构造参数：`corePoolSize` 是核心线程数，`maximumPoolSize` 是最大线程数，`keepAliveTime` 和 `unit` 是超出核心的线程空闲多久回收，`workQueue` 是等待队列，`threadFactory` 决定线程名，`handler` 是拒绝策略。核心线程默认一直留着，除非打开 `allowCoreThreadTimeOut`。

JDK 的提交顺序是：工作线程少于核心数时，即使已有线程空闲，也会新建核心线程；达到核心数后先入队；队列满了才把线程扩到最大；再满才拒绝。无界队列时 `maximumPoolSize` 不会生效。`SynchronousQueue` 不保存任务，没有线程正在取的时候放不进去，提交就会去扩线程，直到最大数。

默认拒绝策略是 `AbortPolicy`，抛 `RejectedExecutionException`。其余三种是调用方自己执行、丢掉当前任务、丢掉队列头再试一次。调用方执行能形成反压，但会占住上游线程。线程要有业务名字，否则 dump 对不上是哪个池。

### 7. Spring 的 IoC 容器启动过程

**参考答案**

日常用的是 `ApplicationContext`，启动主线在 `refresh`。

先准备环境并建好 `BeanFactory`，配置被加载成 `BeanDefinition`，这时还没有业务对象。接着跑 `BeanFactoryPostProcessor`：`ConfigurationClassPostProcessor` 解析 `@Configuration`、组件扫描、`@Import` 和 `@Bean`，定义可以在这里被改掉。然后注册 `BeanPostProcessor`，准备好事件广播。

`finishBeanFactoryInitialization` 预实例化非懒加载单例：构造、注入依赖、初始化。初始化里回调 Aware，`BeanPostProcessor` 包住初始化方法。AOP 代理一般在初始化之后生成。最后 `finishRefresh` 发出容器已刷新事件。

`BeanFactoryPostProcessor` 改的是定义，`BeanPostProcessor` 改的是对象。单例的设值循环依赖靠提前暴露解决，构造器循环依赖解决不了。Spring Boot 2.6 起默认不允许循环依赖。懒加载单例不会在启动时创建。

### 8. Spring AOP 的实现原理

**参考答案**

Spring AOP 默认是运行时代理，不是编译期织入。`AnnotationAwareAspectJAutoProxyCreator` 作为 `BeanPostProcessor`，在 bean 初始化之后按切点决定要不要包一层代理。

目标实现了接口时用 JDK 动态代理，否则用 CGLIB 生成子类。Spring Boot 默认打开按类代理，有接口也常用 CGLIB。调用时把命中的通知排成链，沿 `proceed` 前进。Around 包住整次调用，Before 在业务之前，After 无论成败都执行，AfterReturning 和 AfterThrowing 看结果。多个切面用 `@Order`，数值小的包在外层。

对象内部自己调自己的方法不经过代理，切面不会生效。要生效就把调用改到注入进来的代理上，或打开 `exposeProxy` 再取当前代理。`final` 类和 `final` 方法无法被 CGLIB 覆盖。`new` 出来的对象也不在容器的代理里。

### 9. MySQL 的索引结构，B+ 树的特点

**参考答案**

InnoDB 的索引是 B+ 树。主键索引是聚簇索引，叶子放整行。二级索引的叶子放主键，要整行时再按主键回表。查询列都在这棵二级索引里，就是覆盖索引，不必回表。回表查的是聚簇索引，不是一条磁盘偏移。

非叶子只存键和子页指针，一页能挂更多分支，树更矮，磁盘 IO 更少。数据都在叶子上，查找代价稳定。叶子之间用双向链表相连，范围扫描沿链表走。页默认 16KB，和这种高扇出配合，高度通常只有三四层。

复合索引按列从左到右有序，能用上的是左边连续的等值，再到紧接着的一列范围。哈希只适合等值，做不了范围和排序。InnoDB 不能把哈希建成普通二级索引，自适应哈希只是热点页上的内存加速。

### 10. Redis 的持久化机制，RDB 和 AOF 的优缺点

**参考答案**

RDB 是某一时刻的二进制快照。`BGSAVE` 会 fork 出子进程写文件，父进程继续服务，靠写时复制。文件小、恢复快，适合备份和主从第一次同步。两次快照之间宕机会丢掉这一段。内存大时 fork 可能把实例卡住，写时复制也会把内存顶高。

AOF 把写命令追加到日志。刷盘常见是每秒一次，崩溃时通常最多丢大约一秒；每次写都刷最稳，吞吐也最差。文件会变大，后台重写压成能重建当前数据的最小命令集。重写文件可以在头上放 RDB 内容，后面再追加增量，加载比纯命令回放快。AOF 更不容易丢数据，文件更大，恢复也比重放快照慢。

两边可以同时开：RDB 做冷备，AOF 保住最近的写。它们保的是这台机器重启后还在的数据。异步复制的从库同样可能缺最近几条写，替代不了本机持久化。

### 11. 场景题：如何设计一个短链接生成服务

**参考答案**

短链读多写少。生成必须全局唯一，跳转只做查找和 302，点击统计不要堵在跳转上。

短码用发号器的全局 ID 做 Base62，不要把连续自增原样暴露，否则会被人把库扫完。号段或雪花都可以发号。雪花转出来偏长；产品要更短的码，就用打乱后的号段，或随机码加唯一索引，冲突再重试。同一个长链要不要永远对应同一个短码，看要不要分开统计。

库表以短码为主键，行里放长链、过期时间、状态和创建人。过期和禁用改状态。跳转先查本地缓存和 Redis，未命中再查库并回填；同一个短码失效时只放一个请求回源。不存在的短码缓存一个短 TTL 的空值。用 302，浏览器才不会把跳转目标记死，改目标和计点击才仍然经过服务端。

点击异步累加。创建接口按用户限流，并拒绝内网地址和非常规协议。多实例共享同一套发号和短码唯一约束。容量上去之后按短码分片，热点在缓存，不在跳转计算。

### 12. 在 Java 项目中如何调用机器学习模型进行预测

**参考答案**

模型放在独立的推理服务里，Java 负责组装特征、超时和失败后的降级。训练留在 Python，导出后再服务。Java 通过 HTTP 或 gRPC 按模型版本调用，GPU 和模型升级都不绑在业务发版上。

只有模型很小、延迟又卡在网络上，才考虑进程内加载，例如 DJL 或 ONNX Runtime。ONNX 是两边都能接的交换格式，比在 Java 里绑定某一家训练框架稳妥。

预处理必须和训练时同一套，否则权重没问题，结果也会错。推理用独立线程池和明确超时，避免拖死业务线程。请求路径上不做训练，也不要每次请求重新读模型文件。日志里留下模型版本、耗时和失败率，输入分布变了要能看出来。远程推理不可用时返回规则结果或明确失败，不要无限重试。

### 14. Java 中 synchronized 和 ReentrantLock 的区别

**参考答案**

两者都可重入，也都是互斥。`synchronized` 由监视器实现，进入代码块就加锁，正常退出和抛异常都会放开。`ReentrantLock` 基于 AQS，必须在 `finally` 里 `unlock`，漏了会一直占着。

锁能做的更多：`tryLock`、带超时的尝试、`lockInterruptibly`、公平锁，以及多个 `Condition`。`synchronized` 只有这一把锁上的 `wait` / `notify`，进锁时不能被中断，也没有公平模式。`ReentrantLock()` 默认非公平，公平要构造时传入 `true`，排队会更严格，吞吐通常更差。

无竞争时 `synchronized` 走轻量级锁，竞争激烈再膨胀成重量级。偏向锁从 JDK 15 起默认关闭，不要再按三步升级当现状讲。虚拟机还能对它做锁消除和锁粗化，普通的 Lock 对象享受不到。简单临界区用 `synchronized`；需要超时、可中断或多条件队列时用 Lock。两边在没有竞争时速度接近，不要说谁永远更快。

### 15. 如何保证微服务之间的数据一致性

**参考答案**

跨服务默认做最终一致：每个服务提交自己的本地事务，再用可靠消息把结果送出去，消费按业务键幂等。不要用一个大事务把多个库包在一起。

发件箱最常用。业务更新和待发送记录在同一个本地事务里提交，后台再投递。投递是至少一次，消费者用业务键去重。流程长、每步都能补偿时用 Saga，失败按相反方向补偿，补偿也要幂等。余额、库存这种需要先占住资源的，用 TCC，每个参与方都要实现尝试、确认和取消。

XA 能做强一致，协调者和锁会拖住吞吐，只适合参与方少、可以同步等待的内部场景。Seata AT 靠 undo log 回滚，对 SQL 和隔离有要求，不是所有写都能自动套上。

要读到自己刚写的结果，就读负责写入的那个服务。消息会重复，也会乱序，对账扫未投递的发件箱和未完成的补偿。

### 4. Kafka 如何保证消息不丢失和顺序性

**参考答案**

不丢要生产、Broker、消费三段一起看。

生产端显式使用 `acks=all`，失败在回调里重试或返回给上游，不能把已经调用 send 当成成功。打开幂等，避免重试在同一分区写出重复。幂等会要求 `acks=all`，也就是当前 ISR 里的副本都确认，并且同一连接的在途请求不超过 5。副本至少 3 个，`min.insync.replicas` 至少 2。这个值若保持默认的 1，`acks=all` 在只剩 leader 时也会确认，leader 再挂就丢。不要让 ISR 之外的副本当选 leader，否则已确认的日志会被截短。

消费端关掉自动提交，处理成功再提交位移。这是至少一次，崩溃会重放，所以消费按业务键幂等。Kafka 事务只能包住 Kafka 自己的读写，写到外部数据库仍要幂等或发件箱。保留时间到了消息仍会被删，那是保留策略，不是发送没确认。

顺序只在分区内有效。同一业务键进同一分区。没有幂等时，重试加上多个在途请求会打乱分区内顺序。消费端在处理这个分区的线程上按拉取顺序做完再提交；拿去线程池并发执行，顺序就没了。全局有序只能单分区，吞吐一起掉下来。用户重复提交是另一次业务请求，幂等生产者挡不住。

### 5. MySQL 分库分表的常见方案及适用场景

**参考答案**

先确认是单表太大，还是单库写不过来。索引、SQL 和归档还能解决问题时不要分片。

垂直拆分按业务把库切开，或把大字段拆出热行。边界清楚、互相查询少时最合适。水平拆分按分片键把同一张表散到多套库表。哈希写入均匀，范围查询和跨片分页会难；按时间范围方便归档，最新的一片容易成为热点。分片键要出现在大多数查询里，否则每条 SQL 都扫全部片。

两张表总按同一键关联，就用同一规则拆，关联留在单片里。小的字典表可以每片放一份。跨片不要做大事务。主键用雪花或号段。深分页改成记住上次主键接着翻，检索类查询交给搜索引擎。

落地可以在应用里路由，也可以走独立代理。预先拆足够多的逻辑表，映射到较少的物理库，扩容时只搬一部分逻辑表。对分片数取模再硬扩，要搬的数据会很多。

### 6. 微服务架构下如何实现服务发现和负载均衡

**参考答案**

服务发现回答有哪些实例，负载均衡回答这一次打哪一个。

客户端发现时，实例启动向注册中心登记并续约，下线主动摘掉。调用方把列表缓存在本地，注册中心短时间不可用还能用旧列表。Nacos、Eureka、Consul 都是这条路。服务端发现时，调用方只认一个稳定地址，由 Kubernetes Service、网关或 Sidecar 转到后端，实例变化对业务代码不可见。

Spring 里带负载均衡的 HTTP 客户端或 OpenFeign，从本地列表里挑实例。机器一样用轮询，规格不同用权重，要粘住同一用户用一致性哈希。列表里只放健康实例。失败后换实例重试，并且只重试幂等请求。

列表长期不刷新，会继续把流量打到已经没了的机器上。注册中心的心跳和本地缓存要一起看，不能只讲一个轮询算法。

### 7. Elasticsearch 的倒排索引原理及其优势

**参考答案**

倒排是词项到文档。写入时分析器把文本切成词项，每个词项对应一组 postings：文档 ID、词频，做短语时还有位置。查询先查词典，再取 postings 做交集，用 BM25 按词频和文档长度打分，不必扫全表。词典压在内存里，postings 顺序放在磁盘上。

Lucene 的段不可变。新文档先进入内存缓冲，refresh 之后成为可搜索的新段，所以是近实时。refresh 的默认间隔是 1 秒。refresh 只让新段可搜，flush 才把数据落到提交点。删除是标记，更新等于删除再添加。段太多时后台合并。

优势是关键词、短语和相关性都不必全表扫描。分析器在索引和查询两侧必须一致，否则同一句话切出来对不上。聚合和排序走列式的 doc values，那不是倒排。它不适合当事务库，深分页用 search_after，不要把 offset 拉得很大。

### 8. 在 Java 中如何集成并调用 TensorFlow 或 PyTorch 模型

**参考答案**

在 Python 里导出模型，Java 只做推理。不要在 Java 里重写训练。

TensorFlow 导出 SavedModel，交给 TensorFlow Serving，Java 走 gRPC。PyTorch 导出 TorchScript，交给 TorchServe；两边也都可以转成 ONNX，用 ONNX Runtime。在线服务负责批处理、版本和 GPU。Java 传入已经对齐的特征，并设置超时。

要进进程时，用 DJL 加载对应引擎，或直接用 ONNX Runtime 的 Java API。DJL 的 Predictor 不能多线程共用，要放进池里；ONNX 的 Session 可以多线程执行 `run`。预处理和训练用同一套归一化，输入的名字、类型和形状按导出的签名来。

上线前固定为评估状态：关掉 dropout，BatchNorm 用训练期的统计量。模型在启动时加载并预热，不要在请求里现读文件。进程内加载失败就退回远程推理，不要在业务机器上临时装一套 Python。

### 9. 项目中的代码规范和质量保障措施

**答题思路**

讲你仓库里真实在跑的几道关。没有的不要说成有。

1. 规范落在工具上：格式化和静态检查进构建。新增问题要挡住，历史债分开说。
2. 分支和评审：主干保护，合并要有人看。说你评审时看什么，例如事务边界、幂等和 SQL。
3. 测试分层：单测守核心分支，集成测试守数据库和消息。讲能拦住哪类缺陷，不背一个覆盖率。
4. 发布：流水线里构建、检查、测试，出问题要能回滚。有灰度就讲看哪些指标。
5. 线上关键路径有日志和告警，能对上某次发布。最后补一条你觉得还缺的，例如缺压测或缺回归。

### 10. 团队技术方案出现分歧时，如何推动达成一致

**答题思路**

把分歧收成一个能验证的选择。用你真参加过的一次讨论套这个顺序，不要编一场没开过的评审。

1. 先对齐约束：延迟、一致性、工期、谁来运维。各方往往不是在答同一道题。
2. 方案收成可比较的几项：失败时会怎样、改多少、能不能回滚。感觉和资历不作为依据。
3. 差在事实上，就用最小原型或一次压测取数，并限时结束。
4. 由负责上线的人拍板。记下选了哪条、没选哪条、为什么。
5. 定了就按这个做。约定哪条假设被线上打脸，就重新打开。

### 11. 最近在关注或学习哪些新技术，为什么

### 12. RocketMQ 和 Kafka 在选型时的考量因素

**参考答案**

两者都能做高吞吐的发布订阅。先看消息是业务事件还是日志流，不要只比一个峰值吞吐数字。

Kafka 强在分区日志：吞吐高、按位移重放、可以保留很久，后面接流处理很自然。顺序在分区内。延迟消息、和本地事务绑在一起的回查、按级别重试，都要自己用主题和调度补。运维要管分区、副本和消费位移。

RocketMQ 更贴近业务消息。延迟和定时、事务消息（半消息、本地事务、提交或回滚、Broker 回查）、失败重试和死信都是内建的。4.x 的延迟是固定档位，5.x 可以指定延迟时间。Tag 能在一个主题里做过滤。顺序消费有单独的队列模型。Java 技术栈里通常更好接。

订单、支付、超时关闭，优先看 RocketMQ 的事务和延迟。埋点、日志、需要反复重放的管道，优先看 Kafka。团队已经会运维哪一个，往往比纸面特性更决定选型。无论选谁，不丢、分区顺序和消费幂等都要在应用里设计。

### 13. 场景题：设计一个支持千万级用户的活动抽奖系统

**参考答案**

千万是注册用户数，不是每秒请求。压力在开场那几秒，同一活动的资格和库存会被打爆，数据库里一行 `stock-1` 扛不住。

资格和结果放在 Redis。用 Lua 一次做完：这个用户有没有抽过、按权重和剩余库存决定中哪一档、扣减、写下结果。未中奖也要写下，否则超时重试会再摇一次。幂等键里存的是这一次的结果，重试返回同一次，而不是只拒绝第二次。权重计算和扣减必须在同一个脚本里。

也可以事先按奖品数量铺好池子再弹出，池子空了就是未中奖。单 key 太热时把库存分成多桶，脚本换桶再试，总数以各桶之和为准。

接口马上返回结果。发券和记账走消息，消费者按抽奖单号幂等写库。Redis 是开场时的现场，数据库是事后的账，定时对账。活动配置放本地缓存。超限直接返回繁忙，客户端用同一个幂等键来查。发放失败保持「发放中」，补偿任务重试。

全员走一个数据库事务更直观，开场会被连接和行锁打挂。这里用最终一致的账本，换开场能返回。

### 14. 如何监控和预警线上系统的性能瓶颈

**参考答案**

先看用户是否已经变慢或失败，再看哪一层快满了。服务看速率、错误率、延迟和饱和度。

应用上收集 QPS、P99、错误率、线程池队列和拒绝次数、GC 停顿、连接池等待。链路把一次请求在各服务上的耗时串起来，先找到慢的那一跳。数据库看慢查询和锁等待，Redis 看延迟和命中率，消息看消费滞后。CPU 不高也可以有瓶颈：池子等满、Full GC 变长、滞后变大，都会先于 CPU 打满出现。

告警打在症状上：成功率、P99、消费滞后。阈值对照近期基线，用连续窗口减少抖动误报。池子使用率、磁盘、Full GC 作为提前量。每条告警要能跳到仪表盘和一条 trace。

定位时沿最慢的一段往下，分清是远程调用、SQL、锁还是本地计算。热点用飞行记录或抽样剖析确认，不要只看一张 CPU 图就改代码。下单成功率、发奖延迟这类业务指标也要有。机器很闲时，业务可能已经错了。
