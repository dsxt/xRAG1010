# 追觅 AI Agent 三轮技术面

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

这面问得挺邪乎，不是常规八股，全是生产里才会踩的坑。前面还以为聊 Agent 架构，后面直接按在 bad case、Harness、多 Agent 死循环、设备控制幂等上摩擦。没有算法题，但比写红黑树还累，因为每道题都在问线上出事怎么办。答得出来就是真干过，答不出来马上露馅。追觅这个岗位明显不是招只会调 Prompt 的人，而是招能把 Agent 当系统工程扛起来的人。如果只背过 ReAct、只跑过 PDF 问答，三面都撑不到。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按“我是谁 → 做过什么 → 为什么匹配”讲：

1. 一句话定位：年限、方向（后端 / AI 应用 / Agent 工程），技术栈只报真正用过的，例如 Python、Java、RAG、工具调用、Redis、MySQL。
2. 挑 1 个最完整的 Agent 项目：业务问题、你负责的链路、结果。结果只讲你能展开的事实，没有数字就讲定性变化。
3. 埋一个可深挖的点：意图分流、工具参数校验、取消或 trace，方便面试官顺着问。
4. 收尾到岗位：能把 Agent 做成可观测、可取消、写操作可校验的系统，而不是只调 Prompt。

### 2. 讲一个你做过的最完整的 AI Agent 项目，从用户请求进来到最终返回结果，全链路怎么跑

**答题思路**

用你真实的项目套下面的骨架，按时间顺序讲一条请求，不要跳到框架名词。

1. 入口：鉴权、限流、会话 id，流式输出用 SSE。
2. 装配上下文：近期对话、已确认的槽位、未完成的确认单。长期原文不要整段塞进 Prompt。
3. 意图：规则 → 分类模型 → 低置信度才走 LLM。多意图先拆开，写入动作先不执行。
4. 路由：路径固定的走工作流；只有下一步不确定时才进 Agent loop，并设最大步数。
5. 检索或工具：检索带型号、权限、文档版本过滤。工具先过 schema，再过业务校验（订单属于谁、型号在不在）。
6. 写操作：人工确认、幂等键、回执核对。回执失败就不能生成“已办理”。
7. 输出：流式返回；用户断开要取消模型和未完成工具。
8. 横切：trace 里能看到意图、工具参数、回执、引用文档和 token。

准备三个追问：哪一段最容易错、你怎么从 trace 定位、失败时用户看到什么。

### 3. 意图识别你们是怎么做的，规则、分类模型、LLM 路由分别用在什么阶段

**参考答案**

三层叠成漏斗，各管一段流量。规则放最前，专门接必须稳定的指令：转人工、明确的订单号、高危词。它延迟极低，出了问题可以热修，但说法一变就失效。分类模型接意图集合已经稳定、量又大的请求，置信度够就直接路由，不够就拒识，延迟通常在毫秒到几十毫秒。LLM 路由只接长尾、多意图、还要同时抽槽位的句子，输出必须符合 schema。

线上把 LLM 处理过、事后确认无误的样本回流去训分类模型，让更多流量停在便宜的层。每一层都要能产出 unknown：未知句子去澄清或转人工，不能为了“有个意图”硬落到退款或设备控制。

### 4. 一句话里同时包含咨询、下单、售后三种意图，Agent 怎么分流，会不会串行处理

**参考答案**

先一次拆成意图列表和槽位，再由代码决定哪些能跑、哪些只挂起。模型负责拆，不负责擅自把三个意图都执行完。

咨询是只读，可以马上检索并回答。下单和售后是写操作，先补全并核对槽位，生成确认单，用户确认前不打写接口。两者若指向同一件商品还可能冲突，冲突时先问清，不要并行下一单又一单退掉。没有依赖的只读查询（知识库、订单只读详情）可以并行；有依赖的步骤才串行，例如先查到订单才能判断能不能退。

回复里三件事都要提到，避免用户觉得后半句被丢掉。容易漏的是：串行指的是依赖和确认顺序，不是把三个写接口无确认地排成一条流水线。

### 5. AI 工作流和 Agent 的边界在哪里，什么场景不该上 Agent

**参考答案**

工作流的下一步由预先配好的图决定，模型只在节点里做抽取、分类或生成，路径可枚举，时延和成本有上界。Agent 的下一步由模型在循环里选工具和参数，路径要跑起来才知道。

边界就在“下一步能不能事先写死”。高频 FAQ、按清单核验的退款、恢复出厂，都该走工作流，模型只填槽。步骤事先不确定、工具很多、失败后要改计划时，才在图里嵌一段 Agent，并加上步数、时间和费用上限。

不该上自由 Agent 的情况：没有轨迹日志和评测、动作不可逆、或者时延预算不允许多轮推理。先有工作流骨架，只把开放决策点交给模型。

### 6. RAG 里 Chunk 怎么切，长文档、表格、接口文档分别怎么处理

**参考答案**

切分目标是检索时能命中完整事实，同时别把上下文撑爆。没有统一的最优长度，用评测集在召回率和 token 之间定；叙述性文本可以留大约一成到两成的重叠作为起点，结构化内容不要靠重叠硬粘。

长文档按标题层级切，块上带“文档名 > 章节”路径。小块用来检索，命中后回带所属的父块给模型。表格保持表头：小表整表一块，大表按行转成“列名：值”，再加一块表级摘要；行不要从中间截断，型号和数值同时进关键词索引。接口文档按一个 operation 一块，方法、路径、参数、示例、错误码放在一起，版本和是否废弃放进元数据，检索时滤掉废弃版本。

### 7. 向量召回不准时你的排查路径是什么，BM25、向量、重排各自负责什么

**参考答案**

先看 trace 里的原始问句、改写、过滤条件和各路命中的文档，不要先改 Prompt。标准文档不在库里或被型号、权限、过期滤掉，调排序没有用；文档在库里但答案被切断，先改切分。

三路职责不同。BM25 负责精确词：型号、故障码、SKU、订单号，不理解改写。向量负责语义相近，弱项是精确编号和否定。重排（常见是 Cross-Encoder）只对前几十到一两百个候选重新打分，负责最后放进 Prompt 的精度；正确块根本没进候选集时，重排找不回来。

对照评测集看每一层的召回：候选集里没有，问题在入库、过滤、改写或召回；候选里有、送进模型的 top 里没有，问题在融合或重排；上下文里已经有却答错，问题在生成。两路分数不要直接加权，量纲不同，名次融合更稳。

### 8. Agent 调工具时参数合法但业务语义错误，比如日期写错、设备型号不存在，怎么拦

**参考答案**

schema 只保证类型、必填和格式，保证不了“这是不是该用户的订单、这个型号存不存在”。写工具前面加一层业务校验，校验失败就返回结构化错误，循环停在这一步，不能生成成功话术。

日期由代码用业务时区解析。“明天”不要让模型自己换算；解析后再检查退货窗口、预约是否早于现在。型号、订单号、设备 id 必须来自本轮工具返回的候选，或能在主数据里查到；对不上就拒绝，必要时把候选退回给模型重选。只允许纠正成规范 id，不允许模型悄悄换成另一个型号。

相对日期的基准时刻、时区，以及“候选闭集”这三件事要放在代码里。校验拒绝（型号不存在）是业务结果，不要记成下游故障去熔断整个设备服务。

### 9. Python 里 asyncio 调多个工具，其中一个失败，其余结果怎么处理

**参考答案**

只读工具要部分结果：一个失败不能把已经成功的查询丢掉。`gather(..., return_exceptions=True)` 会把子任务里的异常收进结果列表，其他协程继续跑完。每个调用自己带超时，否则最慢的一个会拖住整批。

```python
async def run_read_tools(coros: list):
    results = await asyncio.gather(*coros, return_exceptions=True)
    ok, failed = [], []
    for i, item in enumerate(results):
        if isinstance(item, Exception):
            failed.append((i, type(item).__name__, str(item)))
        else:
            ok.append((i, item))
    return ok, failed
```

墙钟时间取决于最慢的调用。失败列表和成功结果一起交回模型，让它基于事实继续，而不是假定全部成功。

有副作用的工具不要放进这个并行函数。若一组调用必须全成功才有意义，用 `asyncio.TaskGroup`：其中一个抛错，同组未完成任务会被取消，并抛出 `ExceptionGroup`。取消只是不再等待，已经提交的退款或设备指令不会自动回滚，那种调用要靠幂等键事后核对。外层任务被取消时，不要用 `except Exception` 把 `CancelledError` 吞掉。

### 10. Java 侧如果 Agent 服务要接现有后台系统，线程池、超时、熔断怎么设计

**参考答案**

按下游拆舱壁：订单、设备、用户系统各自独立的并发上限。一个慢接口打满池子时，其他系统还能调用。阻塞 IO 可以用有界线程池，也可以用 Java 21 的虚拟线程；虚拟线程仍然要按下游加信号量，否则只是把无界并发转移到数据库和设备网关。

线程池用有界队列。队列无界时最大线程数不会生效，任务堆在内存里。队列和线程都满了就拒绝，并返回可识别的错误，不要让拒绝策略把设备调用退回 Web 容器线程。

超时写在 HTTP 客户端的连接和读取上，这才能释放连接。`Future.get` 超时之后要 cancel，并真正关掉那次调用。跨服务传绝对截止时间，下游用剩余时间，不要每跳都重新给满额。设备控制若超时，结果是未知，不是可以立刻重试的失败。

熔断按下游分开，只统计超时、连接失败和 5xx。业务校验失败不参与熔断。熔断打开后快速失败，把结构化错误交给 Agent 降级，避免请求继续占满线程。

### 11. SSE 流式返回时用户中途退出，后端怎么真正取消大模型推理和工具调用

**参考答案**

停止往 SSE 写只解决了出口，模型和工具还会继续跑。连接断开要变成这次 run 的取消信号：Spring 的 `SseEmitter` 在完成、超时、写失败时回调；WebFlux 在订阅取消时触发；Python 流式生成里检查客户端已断开。循环每一步开始前看这个标记，通过后不再发起下一轮模型或工具。

取消必须传到出站请求上。正在读的模型流要关闭连接，让对端停止生成；只停读不关连接，自建推理的 GPU 仍会把这段算完。已经发出的工具调用标成未知，用幂等键查询实际结果，不盲重试，也不在话术里说成已取消成功。还没发出的工具不再发。

`CancelledError` 不要被宽泛的异常捕获吃掉。写操作若已经过了提交点，取消改变不了业务结果，只能把回执记进状态，下次会话接着解释。

### 12. 场景题：用户说“扫地机一直撞墙，还把我刚买的耗材订单退了”，Agent 先处理哪个，为什么

**参考答案**

先处理撞墙，退款在同一轮只做只读核对，不提交。撞墙表示设备可能还在异常运动，拖得越久越容易损坏或卡住；退款的时效是天，而且打错一笔就是资金事故。

回复里两件事都要承认，否则用户会觉得后半句被忽略。设备侧优先停止或给出明确的急停指引，再查故障；订单侧可并行查询“刚买的耗材”是否存在、是否在退货窗口内，然后给出待确认的退款单。用户确认前不调用退款接口。

若停止指令本身超时，结果按未知处理，先查设备状态，不要连续再发运动类指令。两件事的 trace 要分开，避免故障查询的结果被写进退款参数。

### 13. bad case 初步定义：什么叫 Agent 答得“像对的但其实是错的”

**参考答案**

指格式、语气和部分关键词都像正确答案，但关键事实、作用对象或动作结果是错的。用户和只看通顺度的评测都不容易发现。

典型有四类：保修期、价格说得很完整，依据却是过期政策或另一个型号；退款工具返回失败，回复写成已受理；召回了相近型号的说明书；该转人工时给了一段无法执行的操作建议。这和胡言乱语不同，置信的错话更危险。

评测要核对证据和工具回执：话术里的“已退款”必须能对上成功状态码，推荐的耗材必须能对上该型号。只给一个流畅度分数，会把这类 bad case 放进线上。

### 14. 你怎么做 Agent 的埋点和 trace，一次失败运行你最先看哪一段

**参考答案**

一次用户请求一个 trace。意图、检索（含过滤条件和文档 id）、模型调用、每一次工具的参数和回执、确认单、取消，都是独立 span，并带上 session、run、step。跨 Python 和 Java 用同一条 trace 传递，只打本地日志对不齐。

失败时不要从最终话术开始改 Prompt。先看失败类型：超时、工具错误、用户差评还是接管。用户说“办错了”或“说办成了但没有”时，第一眼看对应写工具的状态码和参数，核对有没有绑错订单或型号；回执是失败而话术是成功，问题在结果使用。回执没问题再往上游看意图拆分和检索证据，找到第一条偏离正确动作的 span。

没有回执的步骤不要补记成成功。业务校验拒绝和下游 5xx 用不同错误码，否则后面的熔断和归因都会歪。

### 15. 场景题：评测集里有一条 case，人工觉得对，模型评分低；另一条模型评分高，人工觉得废话多，你信谁

**参考答案**

两条都先进入分歧样本，不直接采信任一方。人工看的是业务是否真的完成、用户还要不要再问；模型裁判容易偏爱写得长、位置靠前、和自己同系列的答案，也会因为缺一句套话而压低一个正确短答案。

第一条先复核评分量表和参考答案。人是对的，就保留人工标签，改裁判：量表里写明“事实对即可，不要求固定话术”。第二条把分数拆开，事实正确和是否啰嗦分开打。产品上要的是办成且说完能执行，废话多算体验失败，即使忠实度分数高也不算通过。

安全相关的退款、设备案例用规则或人工做发布门禁。裁判和人工的一致率稳定之前，不用裁判一票放行。两边都可能错，分歧样本用第二个人再标。

## 二面

### 1. 自我介绍

**答题思路**

仍控制在 1 到 2 分钟，侧重点改到生产和评测，避免把一面原话再背一遍。

1. 身份和栈一句话带过。
2. 项目只保留和评测、bad case、多 Agent、状态恢复有关的那一段：你怎么发现线上错、怎么收进回归集。
3. 主动埋点：指标冲突时你保过哪条底线，或者一次死循环、重复退款是怎么停住的。
4. 收尾说明这轮可以展开 Harness 和轨迹，而不是再讲一遍产品功能。

### 2. 你们智能体评测体系是怎么搭的，离线评测和线上评测分别看什么指标

**参考答案**

离线用固定集合做发布门禁，线上用真实流量做灰度门禁，两边指标不要混成一个分。

离线看过程也看结果：任务有没有按标注完成、工具选得对不对、参数是否指向正确订单和设备、检索 recall、回答是否被证据支持、是否出现禁止动作。同一批回放同时记录步数、token 和时延，防止靠多烧调用把正确率做高。集合里单列退款、设备控制这类必须通过的案例。

线上没有干净标签，用代理指标：解决后是否短时间重复进线、人工接管率、工具失败率、不安全动作数、时延分位和单次解决成本。点赞率不能代替任务成功率。代理指标要定期抽人工校准。发布先过离线回归，再用小流量看线上有没有切片恶化。

### 3. 任务成功率、工具选择准确率、幻觉率、人工接管率、成本、时延，这些指标冲突时怎么取舍

**参考答案**

先定不能交换的约束，再在预算里提高成功率。资金和设备控制上的错误动作、越权、以及“回执失败却说成功”，不拿来换成功率或时延。幻觉率在保修、价格、已办理结果上同样是约束。

任务成功率是约束之内要拉高的目标。工具选择准确率只是过程指标：工具选对但订单号错，任务仍然失败，不能单独报喜。

人工接管率不是越低越好。该转人工时没有转，投诉和错误退款会上去，这是故障。只有在错误动作不升的前提下，接管率下降才算变好。

成本和时延是分意图的预算。查询可以走小模型、少检索；退款和设备控制保留校验，允许更慢、更贵。对外报切片，不报一个把六项加权后的总分。

### 4. bad case 闭环怎么建：发现、标注、归因、修复、回归，每一步谁来做

**参考答案**

发现靠工具失败、接管、差评、抽检和告警，由值班把 trace 收进来。没有 run id 的口头反馈先补再现，补不了就单独搁置。

标注要写下预期行为和实际行为，并标严重级别。业务预期由熟悉政策的人定，工程师负责把订单号、工具回执贴上。不能让同一个模型给自己的回答打“是否正确”就入库。

归因用固定原因码：意图、检索、参数、下游故障、状态丢失、策略缺失。工程师根据 trace 归到一个主因。能变成校验或规则的，先改代码；提示词用来处理剩下的开放说法。模块负责人改，高危案例另有人复核。

回归在修复同时进行：这条 case 带上预期答案进评测集，发布时必须通过。作者不能自己宣布修好。评测负责人守门，线上再看同一类错误率有没有下降。

### 5. 同一条 bad case 反复出现，但修复后又把另一条本来正常的 case 打挂，怎么处理

**参考答案**

这是回归，不是“再加一句提示词”。变更已经影响正常流量时先回滚。两条 case 都留在集合里，下一次修改必须同时通过，还要带上同一意图、不同槽位的邻近案例。

对照 trace 找分界条件：型号、是否已发货、文档版本、用户有没有明确拒绝。分界写进规则或工作流条件。两条业务期望本身矛盾时，交给产品定哪条为准，不要让模型折中出第三种说法。

合并前看切片：目标 case 变好，受保护切片跌破约定范围就拒绝发布。用影子流量先跑，确认正常 case 的工具调用没有变。

### 6. RAG 评测里怎么判断是检索错了、重排出错了、还是生成错了

**参考答案**

评测样本要有三个标注：问句、应命中的文档或段落、必须包含或不得包含的事实。然后按层看日志，不要只看最终答案对错。

应命中段落不在召回候选里，是检索问题。再拆开看：关键词路能命中、向量路不能，多半是改写丢了型号或错误码；两路都没有，查入库、切分和过滤。候选里有，送进模型的 top 里没有，是融合或重排问题。段落已经在 Prompt 里，回答仍矛盾、编造或漏掉限制条件，是生成问题。

一个直接的判别实验：只把标注段落塞给模型。这样仍答错，就是生成或指令问题；这样能答对，就是检索或重排没把证据送进去。改写也要单独留痕，避免把改写丢词误判成向量模型不行。

### 7. 多 Agent 架构里，规划 Agent、检索 Agent、执行 Agent、校验 Agent 各自边界是什么

**参考答案**

规划 Agent 只产出步骤、依赖和完成条件，不调用退款、设备控制这类写工具，也不直接给用户最终承诺。检索 Agent 只按给定查询返回带文档 id 和版本的证据，不改写政策，不发起动作。

执行 Agent 按已通过的步骤调用工具。参数必须经过 schema 和业务校验；它不能因为工具报错就自己改目标，例如把退 A 单改成退 B 单。每一步使用调用方传入的幂等键。

校验 Agent 只读。它核对计划有没有越权、证据能不能支持说法、工具回执是不是成功。校验失败就退回规划或转人工。校验 Agent 不能为了“修好”再去调用写工具，否则它会变成第二个执行者，两个执行者会互调打转。

写权限只留在执行侧，且高风险步骤要等确认或策略通过。Agent 之间传结构化消息，不传一段互相理解的自由文本当状态。

### 8. 多 Agent 之间用共享上下文、消息队列、还是中心状态机，为什么

**参考答案**

面向用户的这一轮对话，用中心状态机做唯一事实来源。状态包括当前步骤、已确认槽位、已完成动作和幂等键。规划、检索、执行、校验都由编排器调用，结果写回状态机。这样顺序是确定的，崩溃后能从最后一次提交恢复，也便于限制谁能写。

共享黑板适合存放派生出来的证据和摘要，方便各 Agent 读取，但不能有多个写者同时改“当前目标”。否则后写的覆盖先写的，审计也看不出哪次修改算数。

消息队列用来接超出本轮请求的异步任务，例如退款审核回调、耗时的设备任务。队列要带 run id 和幂等键，消费者按状态机推进，而不是 Agent 之间自由订阅、互相发下一跳。自由消息很容易形成呼叫环，延时也更难放进一次 SSE 响应里。

### 9. 多 Agent 互调形成死循环，你从工程上怎么预防，最大步数、超时、看门狗怎么落地

**参考答案**

步数、截止时间和重复检测都写在 Harness 里，放在状态存储中，模型改不了这些计数。提示词里写“不要循环”不算控制。

每进入下一步，编排器增加持久化的步数，超过上限就停。整次 run 有墙钟截止时间，单次模型和工具调用还有更短的超时，超时后进入取消或未知结果流程。调用指纹用 Agent、工具名和规范化参数计算，同一指纹重复达到小的次数就停。Agent 调用栈里出现环也停。另外用有向白名单限制谁可以调用谁，规划不能直接调写工具，校验不能调执行。

看门狗是另一个定时任务，不和推理循环挤在同一条协程里。它检查 run 的心跳和步数是否还在推进；进程卡死时，循环内的判断不会再执行，要靠看门狗把 run 标失败、取消在途请求，并告警。停掉之后从可用工具列表里拿掉继续互调的能力，给用户固定的降级说明和 trace id。

```python
def stop_reason(state, step) -> str | None:
    if step.count >= step.max_steps:
        return "max_steps"
    if time.monotonic() >= step.deadline:
        return "deadline"
    sig = (step.agent, step.tool, canonical(step.args))
    state.repeats[sig] = state.repeats.get(sig, 0) + 1
    if state.repeats[sig] >= 3:
        return "same_call"
    if step.agent in step.stack:
        return "cycle"
    return None
```

计数要和 run 一起落库。进程重启后本地变量清空，同一逻辑步骤会重新从 0 开始。

### 10. Harness 工程你是怎么理解的，它和 Agent 本身、Prompt、框架分别差在哪

**参考答案**

Harness 是包在模型外面的运行时，负责那些不能靠模型自觉遵守的约束：循环步数、超时、工具权限、参数和业务校验、确认门禁、幂等、取消、轨迹和费用。模型提出动作，Harness 决定这个动作能不能执行、执行到什么时候必须停。

Agent 本身是策略：模型、工具定义和规划方式，决定它想调用什么。Prompt 是输入给策略的说明和示例，可以引导行为，但用户一句话就能和系统说明冲突，不能当作权限和上限。框架（例如用来画图和存 checkpoint 的库）提供表达能力和状态原语。用了框架，只说明能把步骤串起来；上限、权限和回执核对仍要自己做到 Harness 里。

面试里容易把四者说成同一层。能换模型而不改权限代码，能换框架而步数和幂等还在，这两点说清楚，层次就分开了。

### 11. Agent loop 跑久了上下文膨胀，压缩策略、摘要策略、关键状态保留怎么做

**参考答案**

把会丢不起的状态从对话原文里拆出来，单独全量放进每次请求：目标、用户明确拒绝过的动作、已确认槽位、已执行动作的 id 和状态、未完成的确认、最近的工具错误码。摘要不能代替这份状态。

原文只保留最近几轮。更早的对话压成短摘要，摘要只负责语气和未写入状态的背景。大段工具结果存到库里，上下文里留结果码和引用 id。触发条件用 token 估计，不要每一步都摘要；摘要后把系统和结构化状态放回上下文头部。

摘要模型会丢掉否定句和“已经退过了”。所以能不能再退、设备指令有没有发过，只查状态机。状态里没有的成功记录，即使摘要里写了也不要再相信；状态里有的成功记录，摘要没提也不能再执行一次。

### 12. 任务中断后重启，执行到一半的工单、退款、设备控制类动作怎么恢复，幂等怎么保证

**参考答案**

每个写步骤在调用前生成幂等键并落库，状态从“计划”到“已发出”，收到确定回执后改为“成功”或“失败”。重启时先读这个状态，不从模型的记忆恢复。

已经成功的步骤直接沿用回执，不再发送。状态停在“已发出”或超时未知的，用同一个幂等键向下游查询：下游没收到就重放同一键，收到了就把本地改成成功。下游对同一键和同一参数返回原来的结果；同一键换了参数要拒绝。设备控制也一样，恢复出厂这类指令重复发送新的命令 id 会再执行一次，恢复时必须复用原来的命令 id。

人工确认的结果一并存在步骤上，恢复后不重复打扰，也不跳过没确认的步骤。补偿只在查清“已经生效且必须撤销”之后做。查询类步骤可以重跑。

### 13. Java/Python 混合栈里，Agent 核心用 Python，业务系统用 Java，两边状态、日志、trace 怎么对齐

**参考答案**

入口生成一个 run id，并用 W3C `traceparent` 传递。Python 调 Java、Java 再调下游时都带上这个头；队列消息除了头里带，正文里也放一份，避免某段中间件把头丢掉。Java 入口如果看见已有的 `traceparent`，必须接着这条 trace，不能新建。

业务状态只有一处主记录，用 run id 关联。Python 写步骤和工具回执，Java 写订单、退款、设备命令，两边都存同一个幂等键和 run id。日志用 JSON，字段名统一。跨进程对顺序以 span 的父子关系为准，不要靠两台机器的本地时钟拼接。

线程池和异步任务里要显式传递上下文。只在本进程的日志上下文里放 trace id，RPC 没带头，Java 侧就会断链。Java 的业务错误码原样回到 Python 工具结果里，不要只返回一段堆栈让模型改写。

### 14. 场景题：生产环境 Agent 连续 3 次调用设备控制工具失败，第 4 次用户已经骂人，系统该怎么降级

**参考答案**

同一设备、同一类控制连续失败到阈值后，熔断这一条工具，第 4 次不再发。失败若是超时或连接中断，结果是未知，降级前先按命令 id 查询设备现在的状态，避免命令其实已经生效还告诉用户没执行。

熔断之后把该工具从模型可调用列表去掉，或在网关直接拒绝。降级话术用固定模板：承认连续失败、说明不会再下发这条指令、给出机身或 App 上的手动路径，并转人工。工单里带设备 id、三次错误码和 trace id。

若失败发生在碰撞、停机这类安全相关命令上，不再补发移动类指令；停机命令若同样失败，就停止自动控设备。容易漏的是降级回合如果仍走原来的 Agent loop，模型还会再选一次这个工具。工具列表和网关拒绝要先生效，再生成回复。

### 15. 场景题：RAG 里旧文档删了，但缓存和向量库还没清，用户问出来过时答案，责任算检索、缓存还是流程

**参考答案**

责任在知识下线流程：源文档删除时，没有把派生的向量和缓存一起失效。检索是按当前索引工作的，索引里还有旧段落，它就会命中；这不是检索模型临时编了一份旧政策。

要分成两个面看。向量库仍能查到已删除文档，说明删除事件没有更新索引，也没有用“生效状态、文档版本”在查询时过滤。缓存若只用问句做键、不带语料版本，索引后来修好了，缓存仍会返回旧答案。所以修复点是同一条下线事件：删除或标记失效、更新向量、抬高语料版本。缓存键带上这个版本，旧条目自然不会再被命中。

线上先把该文档从索引删除并清对应缓存，再复测这条问句。不要用提示词要求模型“不要用旧知识”来代替失效。

### 16. 你做 AI 工作流时，怎么把“人工审批、条件分支、重试、回滚”做成可配置而不是硬编码

**参考答案**

把流程做成版本化的数据：节点和边存在配置里，引擎只负责解释。节点类型控制在小集合里，例如工具、条件、人工确认、补偿。条件用受限表达式比较结构化字段（金额、意图、风险等级），不要把模型输出当脚本执行。

人工确认是一个会挂起状态机的节点，等回调再往下走；确认结果和操作者写在该步骤上。重试只配置在可重试的错误码上，并写明次数和退避；超时未知的设备控制和退款不走普通重试，走幂等查询。回滚配置成失败边上的补偿节点，补偿自己也有幂等键。

发布前做静态检查：写节点必须有幂等键，要么有补偿，要么明确声明不能自动补偿。业务规则变化时发新版本配置，不改引擎。Agent 只出现在配置允许的开放节点里，不能跳过确认节点。

## 三面

### 1. 自我介绍

**答题思路**

1 到 2 分钟，重点放在把系统送进生产时的取舍。

1. 身份一句话。
2. 讲一次从试用到真实用户的经历：上线前你卡住了哪类风险，上线后你看哪几个数。
3. 点出你做过的范围控制，例如先上只读、写操作留确认，方便后面接“两周上线怎么排”。
4. 如果带过人，补一句你怎么分工；没带过就讲你如何和评测、业务一起定“什么叫答对”。不要编团队规模。

### 2. 你最近一次把 Agent 项目从 demo 推到生产，最难的一段是什么

**答题思路**

选你真实遇到过、能量化或能复盘的一段。优先讲 demo 里不会出现的问题：写操作重复执行、用户断开后任务还在跑、评测分高但人工觉得没用、旧知识删不干净。

按这个顺序讲：

1. 线上现象：用户看到什么，和 demo 差在哪。
2. 你先看的证据：哪一段 trace、哪一个回执。
3. 改动落在哪一层：校验、状态机、门禁或流程，不只是提示词。
4. 怎么确认修好：回归样本和线上切片。没有数字就讲判断标准，不要临时编指标。
5. 如果重来，上线前会先补上的那一块。

把“提示词改了很多版”当作最难的一段时，要能说出对应的失败类型，否则经不起追问。

### 3. 如果老板要求两周上线智能体客服，但评测集还没建完，你怎么排优先级

**参考答案**

两周内把范围收到能说清对错的流程上：高频咨询用检索和工作流，长尾直接转人工。自动退款、恢复出厂、多 Agent 互调、更换 Embedding 都不放进这次上线。

评测集可以小，但不能没有。从真实工单里抽覆盖顶部意图的案例，并单列错退款、错型号、不该控设备的案例，作为必须通过的门禁。集合没覆盖到的写操作保持关闭。

上线前先完成超时、最大步数、参数和业务校验、确认、幂等、trace、转人工。这些缺一个，模型回答再好也不放开写接口。已知路径用配置好的工作流，模型只做意图和槽位。

上线时小流量，每天把接管和差评补进评测集。容易漏的是用“先上线再补评测”把资金和设备控制也放出去；只读可以在小集合下灰度，写操作要等对应案例进了门禁。

### 4. 多 Agent 系统上线后效果下滑，老板说是模型问题，你觉得可能是工程问题，怎么用数据说服他

**参考答案**

把下滑对齐到发布时间线：模型版本、提示词、工具 schema、索引、Harness 限额、流量构成，哪些没变、哪些变了。模型版本和参数没变，下滑就不是“模型突然变差”能解释的。

再看漏斗，而不是一个总分：意图是否分对、工具是否选对、工具回执是否失败、证据是否还在召回里、最终话术是否和回执一致。掉在工具失败率或召回上，就是工程或数据。

用同一批历史请求回放：模型不动，只换上线前后的编排、索引或工具。回放结果跟着工程变更走，就能说明原因。必要时在小流量把工程变更退回，模型保持不动，看指标是否恢复。报告里给这条时间线和漏斗，不跟老板争论感觉。

### 5. 智能体评测要不要自动化回归，LLM-as-judge 的偏差你怎么处理

**参考答案**

要自动化，但先自动化能够判定对错的部分：工具名、参数是否指向正确对象、是否调用了禁止工具、回执和话术是否一致、该命中的文档在不在、退款金额和保修期这类有标准答案的字段。这些不需要裁判模型。

LLM-as-judge 只评开放说法，并且给它量表、证据和参考要点，不给它模型名字。偏差要单独处理：交换两个答案的位置，避免位置偏向；事实和简洁分项打分，避免写得长就分高；裁判不要用被评模型的同一系列，减轻自评偏好。

裁判先在人工标过的集合上看一致率。一致率不够时，它只作抽检辅助，发布门禁仍用规则和人工，尤其是资金和设备。定期抽查裁判通过的样本。量表改了也要重新看一致率。

### 6. bad case 库积累到几千条后，怎么变成训练集、评测集、规则集，而不是变成垃圾堆

**参考答案**

先清洗再分流。每条至少要有输入、预期行为、实际行为、原因码和能否复现。缺预期、对不上 trace、重复的先隔离，不进任何集合。按意图、工具和原因聚类，近重复只留代表，其余计数，避免一套集合被同一句话占满。

分流保持互斥。能写成确定判断的，变成规则或业务校验，例如型号必须在候选集中；这些案例留在评测里检验规则还在，不放进提示词，也不当训练样本。属于模型该学会的说法，才在人工改好目标输出后进入训练或 few-shot。评测集按意图和风险分层抽样，版本冻结，不参与训练。

退款、设备类案例标成必须通过，不因为聚类被合并掉。修过的案例保留，用来防止打挂邻近 case。没有这套字段和互斥分流，几千条就只是搜索日志。

### 7. 意图识别模型要迭代，但线上又在跑，灰度、回滚、流量切片怎么设计

**参考答案**

新模型先影子运行：线上仍由旧模型或规则做决定，新模型只记录判断。按意图对比，尤其看会导向退款和设备控制的标签有没有变多。

灰度按用户或会话做稳定分桶，不要同一会话一会儿新一会儿旧。从很小的比例开始，看分意图的后续结果：工具是否成功、未知意图比例、接管率、有没有把查询误判成写操作。整体准确率会掩盖某一个危险意图的退步。

规则层继续挡转人工和高危词，未知标签只进澄清或人工。回滚用配置切回上一版模型制品，不靠临时重新发布。模型和提示词、标签集合不要在同一次灰度里一起改。标签改名时做显式映射，避免旧的“退款”对新的“售后查询”对不上。

### 8. RAG 要换 Embedding 模型，召回率波动怎么评估，旧向量怎么迁移，冷启动怎么扛

**参考答案**

新旧向量不在同一空间，不能混在一个索引里互相近邻搜索，旧的相似度阈值也不能沿用。查询向量和文档向量必须来自同一个模型。

用同一套标注问句比较两个索引：看应命中段落的 recall，再看最终回答是否被证据支持。只看平均相似度没有意义。评估期间线上仍查旧索引。

迁移是离线把仍有效的文档全部用新模型重嵌入，写到新索引。某个分区（例如一个产品线）的有效文档都完成后，才把该分区的查询切到新模型和它的索引。切之前双读对比，不把新查询向量打到旧索引上。回滚就是查询路由切回旧模型和旧索引，所以旧索引保留到新索引稳定之后。

冷启动主要是文档还没嵌完，以及阈值还没在验证集上重标定。查询侧的向量缓存要带模型版本；文档侧用批任务补齐，不要在用户请求里临时嵌整库。语义缓存同样按模型和语料版本失效。

### 9. 多 Agent 系统成本失控，token、工具调用、重试、人工接管都在烧钱，你先砍哪块

**参考答案**

先按 run 拆开账单：输入 token、输出 token、工具调用、重试、人工。没有占比就不要凭感觉砍模型。Agent 循环里输入 token 经常最大，因为历史和工具结果反复送进模型。

最先砍的是没有推进任务的消耗：互调死循环、同一参数的重复工具、不可重试错误上的重试、塞进上下文的完整工具原文。这些去掉不会减少该有的退款校验。同时把大结果改成引用，摘要只压对话，不压结构化状态。

然后才是按意图换模型：稳定查询走小模型或工作流，规划和有争议的售后留在强模型。人工接管是高风险动作的安全阀，不作为第一刀；要降的是本可以自助、却因为重复错误而转人工的那一部分，用 bad case 修，而不是把接管按钮拿掉。高风险步骤上的校验留着。

### 10. Harness 层如果要抽成公司级底座，核心模块有哪些，哪些不该抽象进底座

**参考答案**

底座放所有业务线都要重复实现、而且必须在模型之外生效的机制：运行循环和步数、时间、费用上限；工具注册、schema、业务校验钩子、权限和沙箱；状态、checkpoint 和幂等；取消；人工确认门禁；trace 和成本；评测回放要用的事件记录。业务线通过这些接口接入工具和策略。

不放进底座的是会按产品周更的内容：某一品类的保修话术、具体提示词、某个 Agent 的分工、页面。工具的业务协议留在适配器里。退款规则、耗材和型号的对应关系做成配置或独立服务，不要编译进底座。

只服务一条业务线的流程不要为了“通用”抽进平台。底座保证任何接入方都绕不过上限、权限和回执核对；至于规划用一个 Agent 还是四个，由业务场景决定。

### 11. 场景题：追觅这种硬件加电商加售后场景，Agent 要同时懂设备状态、订单、耗材、保修规则，你怎么做知识边界和工具权限

**参考答案**

按来源拆开，不要合成一个什么都答的库。设备在线、电量、故障码来自 IoT 的实时状态，说明书来自按型号过滤的文档，订单来自订单系统，耗材适配优先用型号到 SKU 的结构化数据，保修和退换以带生效日期的政策服务为准。冲突时以实时状态、该用户的订单和现行政策为准，说明书不覆盖政策。检索条件里带产品线、型号、文档类型和有效期；内部维修文档不能召回给普通用户。

工具按风险分开：查状态、暂停或回充、恢复出厂和配网、退款，不是一个“处理售后”的大工具。凭证用该用户、该设备的短时授权，后台不要拿一把能操作所有设备的钥匙给模型。调用前核对设备已绑定、订单属于当前用户。恢复出厂、配网和退款要确认、幂等和审计。模型可以组织语言，不能自己决定价格和保修结论。

### 12. 场景题：用户让 Agent“把扫地机恢复出厂设置再重新配网，顺便把上周误购的滤芯退掉”，这一步里哪些动作必须人工确认

**参考答案**

恢复出厂和退款必须确认；重新配网也要确认用户在机器旁边。用户用“顺便”把三件事放在一句里，只说明他有这个意向，还不等于看过后果。

恢复出厂会清掉地图、预约和已配网络，不可自动撤销。退款要先只读查出上周的滤芯订单，把订单行和金额回显，确认退的是这一笔。配网通常要按机身键，人在旁边才能完成；恢复出厂之后设备会离线，配网失败就会留下一台尚未联网的机器。

只读查询（设备是否在线、哪一笔订单、是否在退货窗口）可以先做，用来生成确认内容。确认前不调用写接口。设备侧顺序必须是先恢复出厂、再配网，反过来会把刚配好的网络清掉。退款和设备是两个系统，都确认后可以分别执行，但恢复出厂失败不能重发一个新的命令 id。三个动作的确认结果分别记在步骤上。

### 13. 你是怎么学 Harness、多 Agent、评测这些新东西的，看源码、跑实验还是只看文章

**答题思路**

按“先复现，再读源码，文章只用来找入口”讲，准备一个你真的跑过的小实验。

1. 实验：例如两个 Agent 互相移交，不设上限就会打转；加上步数和调用指纹后能停住，并留下 trace。或者拿几十条人工标过的答案看裁判在哪一类上偏长、偏短。
2. 源码：对着实验去读你用过的检查点、取消传播或 trace 是怎么串的，讲出你看过的模块和你改过的行为。
3. 文章和文档：用来知道概念和该读哪一段，结论用实验核对。
4. 收尾：这个学法对应到工作里的哪次故障。没做过的部分直接说还没动手，不要把读过的文章说成线上经验。

### 14. 过去半年你主动推翻过自己之前的技术方案么，举一个最痛的

**答题思路**

讲一次你自己拍板、后来又撤回的方案。没有就讲真实的那次，不要临时编项目名和收益数字。

和这个岗位贴近的类型可以作为选择标准：把任务拆成多个自由互调的 Agent，后来收成一个状态机加工作流；或者原来靠提示词禁止错误退款，后来改成回执和权限校验。你没有同类经历时，不要套这个例子。

顺序：

1. 当初的方案和它要解决的问题。
2. 线上或评测里出现的反例。
3. 你依据哪份 trace 或回归结果决定撤回。
4. 新方案改了哪一层，邻近的正常 case 怎么保住。
5. 痛在哪：排期、返工，或你公开改口的成本。最后补一句你提前设了什么信号，避免下次拖这么久。

### 15. 如果让你带 3 个人做智能体平台，你会先定架构、先定评测、还是先定业务场景，为什么

**参考答案**

先定一个业务场景，再定这个场景的评测，最后只做该场景强迫你做的那截架构。三个人同时开平台、评测和多个业务，每一边都做不完。

场景要窄到能说清用户、成功和不能做错的事，例如“已绑定设备的耗材咨询，加查询能不能退”。没有这一步，评测不知道什么叫对，架构会做成一套谁都能接、谁的退款都保不住的编排器。

评测紧跟场景：从真实工单抽小集合，写上必须通过的错退款、错型号案例，并规定上线看接管和重复进线。架构只实现这条链路需要的入口、检索或订单只读工具、确认和幂等、trace。多 Agent、公司级底座和更换 Embedding 等第二条业务线真的出现再加。

先做架构会把时间耗在抽象上；先做一套脱离场景的通用评测，分数和保修、设备控制对不上。场景定完，评测和架构的范围就都被卡住了。
