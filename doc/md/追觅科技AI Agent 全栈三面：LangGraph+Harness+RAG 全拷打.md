### 3. Python 的 GIL 是什么，异步编程里 asyncio 的事件循环怎么理解，FastAPI 为什么适合写 Agent 服务

**参考答案**

结论：Agent 服务的时间主要耗在等模型和等工具，用 asyncio 承接这些 IO。GIL 限制的是同一进程里的字节码，多核靠多进程，不靠在协程里堆线程。

GIL 是 CPython 默认构建的解释器锁，同一时刻只允许一个线程执行 Python 字节码。网络 IO 和一部分 C 扩展在等待时会放开锁，所以多线程可以并发等待，加速不了纯 Python 计算。Python 3.14 起无 GIL 构建已经官方支持，但是可选项；常规解释器仍然带 GIL。生产 Agent 服务按有 GIL 来设计。

事件循环跑在一个线程上。协程执行到 `await` 就把控制权交还循环，循环用多路复用等 socket，就绪后再唤醒对应协程。多个只读工具用 `TaskGroup` 或 `gather` 并发。`requests`、`time.sleep` 以及同步 SDK 写进协程会堵住整条循环，这种调用放进 `asyncio.to_thread`。对模型供应商用 `Semaphore` 限制并发，每次外部调用单独设超时，并处理取消。

FastAPI 建在 Starlette 上。`async def` 路由跑在事件循环里，等待上游时不占工作线程；Pydantic 校验入参；SSE 可以把 token 推给客户端。同步 `def` 路由会进线程池，不要在异步路由里调用阻塞 SDK。进程内的 `BackgroundTasks` 随进程消失，多步 Agent 交给队列。多核用多个 worker 进程，每个进程一个循环。

### 4. Java 侧你怎么把一个现有 Spring Boot 服务对接到大模型 Agent，用哪种调用方式，同步还是异步

**参考答案**

结论：短的单次补全可以同步；会调工具、尾延迟不稳定的 Agent 用异步任务或流式。一次 HTTP 请求不要挂住整段多步推理。

Java 服务继续负责登录态和业务 API。Agent 可以是独立的 Python 服务，团队以 Java 为主时也可以用 Spring AI 的 ChatClient，把本进程的方法注册成工具。调用方式分三档：

- 同步：分类、改写、超时上限很短的补全。用 WebClient 设置连接和读超时。Java 21 的虚拟线程可以避免这种阻塞占满平台线程。调用带幂等键，防止客户端超时后重试打出两次副作用。
- 流式：闲聊用 SSE 把 token 转发给客户端，用户取消时把取消传到上游，停掉模型和工具。
- 异步：查订单、催办这类多步任务，接口返回受理号，任务进队列，worker 执行，客户端轮询或订阅进度。写工具的幂等和人工确认放在 worker 里。

模型调用和普通业务接口做舱壁隔离，模型变慢时下单、查询接口还能活。网关的读超时通常盖不住一次完整 Agent，同步接口在开发环境能跑通，上线后会被网关掐断，客户端再重试就会碰到重复副作用。

### 5. Redis 在 Agent 系统里能干什么，举例说明用 Redis 存会话上下文和限流怎么设计

**参考答案**

结论：Redis 放热数据和需要原子判断的计数；对话审计和订单幂等以数据库为准，Redis 丢了或过期了，业务事实还在。

会话上下文按 `session_id` 存热状态。一个 List 保留最近若干轮的短记录（角色、裁剪后的文本、时间），每次写入后截断尾部并刷新 TTL，空闲会话自己过期。滚动摘要另放一个 key。工具原文不进 List，只留工具名、状态和业务单号。同一会话的并发消息用 `SET key NX PX` 串行化，或者让队列按会话 key 进同一分区。提示词用的是这里的窗口，合规日志写 MySQL。

限流按用户和按工具分开，催办比闲聊紧得多。用一段 Lua 做令牌桶：读剩余令牌和时间戳、按经过的时间补充、够就扣减、写回并设置过期，整段在 Redis 里原子执行。固定窗口的 `INCR` 会在窗口交界放进大约两倍流量；`INCR` 和 `EXPIRE` 若分成两次调用，进程死在中间会留下没有 TTL 的 key。超限返回明确错误，写工具不交给模型自己重试。模型 token 的预算单独计数，避免一个会话死循环打穿账户。

Redis 还可以放分布式锁、取消信号和幂等结果缓存。幂等的最终依据仍是订单库的唯一约束，缓存淘汰不能变成允许再下一单。

### 6. MySQL 里有一张对话日志表，量大了查询慢，你会怎么建索引，哪些字段不适合建

**参考答案**

结论：先看慢在哪条 SQL，再为「等值条件 + 排序」建组合索引。这张表以追加写入为主，索引少而准，正文不进普通索引。

拉一个会话的历史，条件是 `session_id`，排序是 `created_at`、`id`，索引就是 `(session_id, created_at, id)`。查某个用户最近的会话，用 `(user_id, created_at)`。按 `trace_id` 精确回放时，给 `trace_id` 单独的索引。组合索引遵守最左前缀，`created_at` 放在 `session_id` 后面才能同时满足过滤和排序。列表查询不要 `SELECT *`，避开大字段，才有机会走覆盖索引。深分页改成按上一页的 `(created_at, id)` 做 keyset，`OFFSET` 很大时索引救不了。

不适合建普通索引的列：

- `content`、原始请求、原始响应这类大文本。要搜正文，走搜索引擎。
- 单独的 `role`、几乎总是同一值的标志位。基数太低，优化器用不上，还拖慢插入。
- 只出现在 SELECT 里、从不进 WHERE、JOIN、ORDER BY 的列。
- 会被频繁更新的列。日志表尽量只追加，状态变化放到更窄的表，避免整段历史的二级索引跟着改。

对 `created_at` 做函数计算后再过滤，索引用不上，时间条件写成范围。索引只解决选择性高的查找；按月归档或分区解决的是表本身太大。建完用 `EXPLAIN` 看是否仍是全表扫描，再决定要不要加第二条。

### 7. 意图识别你做过么，是完全丢给大模型做分类，还是规则加模型混合，各自利弊

**参考答案**

结论：生产用规则、小分类模型、大模型三层，按置信度往下漏。全量丢给大模型能覆盖长尾，但成本、延迟和回归都差。

规则接措辞固定的高频说法，也接催办、退款这类必须稳的意图。延迟低、结果可解释，覆盖面窄，说法一变就要改规则。小分类模型接常规说法，便宜、稳定、可以用固定测试集评估；新意图要补标注再训练，标签体系一改就要重训。大模型接长尾、一句话里有多个意图、还要顺便抽槽位的句子。表达能力最好，输出会漂，更贵，也不适合作为唯一的回归手段。

落地顺序：规则以高置信度先出；否则走小模型，置信度够就采用；剩下的给大模型，输出仍要过 schema。三条路的利弊就在「覆盖」和「可控」之间。资损类意图即使分得很准，也只表示用户想做这件事，能不能执行由后面的策略节点决定。

### 8. LangChain 里 Chain 和 Agent 的区别，为什么复杂场景不能直接用简单 Chain

**参考答案**

结论：Chain 的下一步是代码写死的，Agent 的下一步是模型看过当前观察后临时选的。路径会随中间结果变化时，一条直线 Chain 表达不了。

Chain 是固定流水线：检索的输出必然进入生成，分支如果存在，也写在代码里。它便宜、延迟稳定、容易做回归，适合「已知路径的检索然后回答」。Agent 把工具清单交给模型，由模型决定叫哪个工具、要不要再来一轮，直到给出最终答复或触到步数上限。它适合事先列不全路径、下一步依赖工具返回的任务。

复杂场景不能靠一条简单 Chain，是因为中间结果会改掉后续步骤。先发现话里没有订单号，就应该反问或去拉该用户的售后单，而不是继续查物流。把这些分支写进代码，得到的是一张图，已经不是一条简单 Chain。路径固定的查进度也不必为了看起来像 Agent 而上循环，循环更慢，也更容易重复调工具。

### 9. RAG 基础流程讲一下，文档切片大小怎么定，切片大了小了分别有什么问题

**参考答案**

结论：先把「一块里只有一个主题」做对，再用带标准答案的问句集看召回，没有普适的切片字数。

流程是：解析文档并保留标题层级，按语义边界切片，向量化后连同型号、版本、更新时间入库；查询时先按元数据过滤，再取候选，需要时做混合检索和重排；生成时只依据命中片段，并带上出处。过滤条件经常比微调块大小更能减少串型号。

块的大小跟着文档形态走。FAQ 一问一答一块，表格按完整的一行或一张表，长文按标题和段落，再落到几百 token 这一量级。边界留一小段重叠，避免一句话被切成两半。重叠补的是边界，补不了一块里混了两个产品。

切得太大：一块里有多件不相干的事，向量被平均掉，命中之后也把噪声带进上下文。切得太小：事实和它的条件拆开，每一块单独看都像对的，拼起来才是完整答案；块数变多，召回更碎。

### 10. 向量库你用过哪个，Milvus 和 Chroma 选型上怎么考虑

**参考答案**

结论：看规模、过滤条件和谁来运维。原型和小数据用 Chroma 这类嵌入式库，要在线扩容、按租户过滤、稳定扛 QPS 时用 Milvus。

Chroma 跑在进程里，API 直接，支持本地持久化和元数据过滤，适合演示、离线脚本和数据量还小的内部工具。它不负责分片、副本和多机扩容。Milvus 独立部署，有集合、分区、多种索引和标量过滤，可以按副本扩展查询。代价是集群本身要有人管。

选型就三件事：向量规模和查询 QPS，要不要按机型、租户、文档版本过滤，团队能不能把集群纳入现有运维。量小且和业务同进程，Chroma 或数据库里的向量类型就够。需要隔离、扩容和稳定的过滤检索，用 Milvus。原型阶段先上 Milvus 集群，运维成本会先于检索质量成为问题。已经用过的那一个，讲清楚数据量、过滤字段和你踩过的索引或过滤问题。

### 11. Tool Calling 里怎么约束大模型传参，Pydantic 模型校验够不够，还要做什么兜底

**参考答案**

结论：Pydantic 或 JSON Schema 挡住类型和形状错误，挡不住「形状合法但业务为假」的参数。执行前要回查，写操作还要另过策略。

把工具定义成 Pydantic 模型，框架据此生成 schema：类型、必填、枚举、数值范围都写进去，能枚举的字段不要让模型自由填字符串。模型返回后、真正调用前，用同一模型再校验一遍。校验失败就把结构化错误回给模型，最多允许修正一次，再失败就停。

这仍然不够。通过校验的订单号可以是幻觉，也可以是别人的订单，状态也可能不允许催办。兜底做在服务端：单号真实存在、属于当前登录用户、状态机允许这个动作。用户身份取自登录态，忽略模型参数里自报的用户 id。写操作在校验通过之后还要有幂等键和策略节点，不能在校验成功的瞬间直接下单。异常信息回给模型时只留可行动的错误码，不回堆栈和内部地址。

### 12. Agent 调外部工具超时或返回脏数据，怎么重试，重试怎么避免重复下单这种副作用

**参考答案**

结论：只读可以退避重试；写操作超时先按幂等键查询，确认没有成功再重试。幂等键来自业务身份，并且落在订单库的唯一约束上。

工具先分成只读和有副作用。只读超时用指数退避加抖动，次数有上限。返回对不上 schema 的脏数据，视为失败，把错误回给模型一次，不拿同一参数连续盲打。

写操作更严格。幂等键在第一次调用前就生成，用用户、售后单、动作和逻辑步骤拼出来。每次重试复用这把键。若每次重试换一把随机 UUID，唯一约束对不上，重复下单照样发生。键存在订单或售后库里。Redis 只能缓存查询结果，键被淘汰不能当成「可以再下一单」。

超时说明请求可能已经到达。先按这把键查询受理结果：成功就返回第一次的结果，进行中就等待或返回进行中，确认没有记录再重试。重试策略放在工具网关。模型若再次发起同样的催办，网关用同一业务键接住。

### 13. 手撕算法：手写一个带过期时间的 LRU Cache（Python 或 Java 均可，要求 get/put O(1)，支持 TTL）

**参考答案**

结论：哈希表加双向链表保证 get/put 均摊 O(1)；TTL 在访问和腾位置时惰性删除。既要严格 O(1)，又要按过期时间立刻回收任意位置的条目，做不到，那需要额外的时间索引，写入变成 O(log n)。

链表头部是最久未使用，尾部是刚用过。`get` 命中后先看是否过期，过期就摘掉并返回未命中，未过期则移到尾部。`put` 更新已有 key 时刷新值和过期时间，并移到尾部，此时不挤掉别人。插入新 key 时，先从头部连续摘掉已经过期的条目，容量仍满再摘掉头部那个仍有效的 LRU。

每个节点最多被摘一次，所以从头部连续清理过期项是均摊 O(1)。刚访问过、但 TTL 更短的 key 会停在尾部，容量满时可能先挤掉一个仍有效的 LRU。这是 O(1) 的代价，面试里要主动说。时钟用 `time.monotonic`，避免系统时间回拨把 TTL 算乱。容量小于等于 0 直接拒绝。TTL 小于等于 0 表示删除这个 key。并发不是这题的要求；真要上线，在这层外面加锁，锁的粒度不要破坏接口复杂度的说明。

```python
import time


class _Node:
    def __init__(self, key, value, expire_at):
        self.key = key
        self.value = value
        self.expire_at = expire_at
        self.prev = None
        self.next = None


class LRUCacheTTL:
    def __init__(self, capacity, clock=None):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        self._clock = clock or time.monotonic
        self.map = {}
        self.head = _Node(None, None, 0.0)
        self.tail = _Node(None, None, 0.0)
        self.head.next = self.tail
        self.tail.prev = self.head

    def _expired(self, node):
        return node.expire_at <= self._clock()

    def _unlink(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _push_mru(self, node):
        last = self.tail.prev
        last.next = node
        node.prev = last
        node.next = self.tail
        self.tail.prev = node

    def _drop(self, node):
        self._unlink(node)
        del self.map[node.key]

    def _drop_expired_head(self):
        node = self.head.next
        while node is not self.tail and self._expired(node):
            nxt = node.next
            self._drop(node)
            node = nxt

    def get(self, key):
        node = self.map.get(key)
        if node is None:
            return None
        if self._expired(node):
            self._drop(node)
            return None
        self._unlink(node)
        self._push_mru(node)
        return node.value

    def put(self, key, value, ttl):
        if ttl <= 0:
            node = self.map.get(key)
            if node is not None:
                self._drop(node)
            return
        node = self.map.get(key)
        if node is not None:
            node.value = value
            node.expire_at = self._clock() + ttl
            self._unlink(node)
            self._push_mru(node)
            return
        self._drop_expired_head()
        if len(self.map) >= self.capacity:
            self._drop(self.head.next)
        node = _Node(key, value, self._clock() + ttl)
        self.map[key] = node
        self._push_mru(node)
```

边界：容量为 1 时第二次 `put` 挤掉前一个；更新已有 key 只刷新它自己；`get` 到过期 key 返回未命中并删除；存进的值可以是 `None` 以外的任何对象，未命中用 `None` 表示，所以不要用 `-1` 兼做「没有」和合法值。Java 同样是 `HashMap` 加双向链表，过期判断放在 `get`/`put` 里。

## 二面

### 3. LangGraph 的 State、Node、Edge 分别解决什么问题，Checkpointer 在生产环境怎么用

**参考答案**

结论：State 是这一次运行的共享数据，Node 是一步计算，Edge 决定下一步去哪。Checkpointer 按 `thread_id` 把每一步的状态存到进程外面，线上用 Postgres，不用进程内实现。

State 一般是带类型的结构。节点返回局部更新。带 reducer 的通道会把新消息追加进去；没有 reducer 的字段会被这次返回整个覆盖。消息历史要用追加，避免某个节点把前面的对话盖掉。

Node 读状态，做一件事，例如调模型、执行工具或组织回复，再返回局部更新。Edge 里，普通边把步骤按固定顺序接上；条件边看状态决定下一节点，例如有工具调用就去工具节点，没有就结束。循环能停，靠的是条件边，再加上步数上限。

Checkpointer 在每个 super-step 边界保存整份状态；同一步里已经跑完的节点，还会把各自的写入单独落下。官方的进程内实现是 `InMemorySaver`，重启即丢，多个 worker 也互相看不见。生产用 `PostgresSaver`，异步服务配对 `AsyncPostgresSaver`。`thread_id` 是这条 checkpoint 序列的主键，Postgres 实现里它有长度上限，官方说明要控制在 255 以内，用短的任务 id。

已经把写入落到 checkpointer 的节点，恢复时不会重跑；工具调用已经发出、写入还没落下的节点会再执行。人工确认若使用 `interrupt()`，恢复时该节点从头再跑。写接口要么放在确认结果已经拿到之后，要么自己幂等。

### 4. 多 Agent 架构你踩过什么坑，Supervisor-Worker 和 Peer-to-Peer 通信怎么选

**参考答案**

结论：有写操作、要审计、角色还会变，用 Supervisor-Worker。只在接力关系固定时使用收紧的 handoff。任意点对点聊天不适合带副作用的客服。

讲坑时用你自己的一次故障，把角色和现象说具体。这类架构里最值得讲的是下面几类：

- 每个 Agent 都带上全量历史，token 被复制好几份。
- 工人用一大段自然语言交接，上游把失败读成成功。
- 两个 Agent 都握有写工具，同一张售后单被催办两次。
- 互相委托形成环，没有统一的步数和预算。
- Supervisor 选错工人之后，没有第二个检查点。

Supervisor-Worker 里，supervisor 负责分流和汇总，工人只拿自己的只读工具和最小上下文，写操作回到 supervisor 或独立的工具网关。这样预算、审计和停止条件有一个落点。代价是多一次路由，路由错了全局都错，所以路由结果要能被规则或 schema 核对。

Peer-to-Peer 只在接力已经固定时使用，例如分诊到专员。每跳只有一个接收方，交接用结构化字段，不开放「谁都可以叫谁」。完全对等的通信容易成环，也很难回答「这个写操作到底谁有权发」。

### 5. Agent 长任务跑到一半崩了，怎么从断点恢复，thread_id 和 checkpoint 怎么配合

**参考答案**

结论：一个长任务绑定一个稳定的 `thread_id`。崩溃后续跑用同一个 id、且不带新输入；用户的下一句话虽然也用这个 id，但是另一种调用，会从图的入口重新走。

`thread_id` 是 checkpoint 序列的主键。调用时放进 `configurable`。恢复前先用数据库或 Redis 给这个 id 加租约，避免两个 worker 同时把它拉起来。

三种调用不要混：

- 崩溃后续跑：`invoke(None, config)`，不带 `checkpoint_id`。运行时加载最近的 checkpoint，已经写下的节点复用结果，没写完的节点再执行。
- 回答人工确认：`invoke(Command(resume=确认结果), config)`。被中断的节点从头再执行，写接口要放在拿到确认结果之后。
- 用户新的一句：`invoke(新输入, config)`。新输入按 reducer 并进已有状态，然后从入口节点再跑。这是接着聊天，不是把崩掉的那一步续上。

第一份 checkpoint 还没写成功就崩溃时，这条 thread 和「从未启动」分不开，`invoke(None)` 会失败。任务受理要先写到自己的发件箱，再启动图。工具侧按 `thread_id`、步骤和业务键做幂等，盖住「下游已经成功、本地写入还没落下」的窗口。

### 6. 意图识别模块线上准确率掉了怎么排查，是样本漂移、提示词问题还是模型版本问题

**参考答案**

结论：先对齐「掉下去的时刻」和「发布的时刻」，用同一批输入回放旧版本。对不上发布，再查输入分布和标签定义。先不要重训。

1. 确认指标本身没变：分母、标签集合、抽样方式若同时改了，曲线下降可能是口径变化。
2. 把曲线和模型版本、提示词版本、规则版本、上游接口的发布时间叠在一起。掉点是一条悬崖，优先怀疑发布；是慢慢下滑，再怀疑分布。
3. 拿掉点之后的请求，用旧模型或旧提示词回放。准确率恢复，就是版本问题。再拆是提示词 diff、schema 变化，还是模型版本。提示词问题常常表现为某两个意图互相串，模型版本问题更常表现为一批意图一起掉。
4. 版本回放救不回来，再看样本漂移：句长、渠道、新型号、活动词、语音识别噪声，和上线前的分布比。同时看标注标准有没有变，标签漂移会被误当成模型变差。
5. 按意图、渠道、型号切片，看是全线下降还是局部下降。局部下降去查那一类的规则和样本，全线下降去查共用的预处理。

业务侧的重复提问、改口和转人工，用来发现「离线集还是绿的、线上已经坏了」。

### 7. RAG 检索召回不准，你从分块、embedding、混合检索、rerank 哪一层先动手，为什么

**参考答案**

结论：先看标准片段在不在候选集里，再决定动哪一层。重排只能调整已经召回到的顺序，救不回没进候选集的片段。整库重做 embedding 最贵，放在最后。

抽一批坏例，标出应该被命中的原文，看它落在哪一档。

- 原文没进库，或被切碎、切串了主题：先改解析和分块。模型、混合检索和重排都看不到不存在的文本。
- 原文在库里，但查询带有型号、错误码、订单规则这类必须精确命中的词，向量检索经常把它排得很后：先加混合检索，让关键词检索和向量检索一起出候选。
- 原文在库里，查询是换种说法，关键词也帮不上，混合检索之后仍然不在候选里：再考虑换 embedding，并用同一批问句比较新旧向量。不要先全库重刷。
- 原文已经在较大的候选集里，只是没进送给模型的前几名：这一档才上 rerank。

可以用两个数把这四层分开：较大候选集的召回很低，问题在分块、过滤或召回；较大候选集召回高、前几名召回低，问题在排序，重排才有用。元数据过滤用错型号，表现也像「召回不准」，先核对过滤条件，再改模型。

### 8. Agent 出现死循环一直调工具，工程上怎么掐断，最大步数、token 预算、反思节点怎么配合

**参考答案**

结论：最大步数是硬保险丝，token 预算是费用保险丝，重复调用检测用来提前停。反思节点只跑一次，并且不能再发写操作。

三道闸从外向里配：

- 最大步数或图的递归上限到了就停，返回已经拿到的工具事实和「未完成」状态。这个上限不交给模型自己改。
- token 或费用预算按会话累计，包含重试和反思。到阈值就收束，避免死循环把均值成本打穿。
- 同一工具加上规范化之后的参数连续出现，视为循环。读工具直接停止再调；写工具根本不进自动重试。

反思节点放在触到硬上限之前，只调用一次。它只能在「向用户澄清」和「根据已有观察给出现有答复」之间选，不能再调用刚才失败的写工具，否则反思自己又成了第二层循环。LangGraph 里除了应用层计数，还要设运行时的递归上限，防止条件边写错时停不下来。

### 9. Kafka 在 Agent 系统里用来干什么，任务队列和事件总线的用法区别

**参考答案**

结论：Kafka 在这里既可以当任务队列，也可以当事件总线。两种用法的主题、消费者组和失败语义分开，写操作只允许执行组消费。

长任务用队列把请求线程放开：一条消息是一件待执行的工作，例如继续跑某个会话的工具步骤。同一个消费者组里竞争消费，成功后再提交位移，失败进重试或死信。用 `session_id` 或订单号做 key，同一会话在分区内有序。

事件总线传的是已经发生的事实，例如「催办已受理」。分析、评测采样、通知各自一个消费者组，按保留时间回放，互不影响。消费者要自己幂等，因为投递是至少一次。

区别在于再加一个消费者组会发生什么。队列主题上若再挂一个也会执行催办的组，同一件写操作会再做一遍。总线主题上的新组只是多一个观察者。所以 Agent 的执行用队列，轨迹和评测用总线，写接口只挂在那个唯一的执行组后面。

### 10. RocketMQ 和 Kafka 在 Agent 工具异步执行场景里怎么选

**参考答案**

结论：工具执行选 RocketMQ，事件流和评测回放选 Kafka。团队如果只能稳定运维其中一种，运维能力可以盖过功能差，缺的延迟重试和幂等要在应用里补上。

异步执行一张催办或查询任务，需要的是：失败后过一会儿再试、多次失败进死信、同一订单号严格有序、以及「库里的受理记录」和「发出去的消息」一起成功或一起取消。RocketMQ 把延迟消息、消费失败重试、死信、按 sharding key 有序、事务消息做成了消息模型里的能力，事务消息用来对接本地事务。

Kafka 是可回放的日志，强项是吞吐和多组独立消费。单条消息的延迟重试、死信和本地事务要自己用重试主题或发件箱做。它适合对话事件、trace 和评测样本的回放。

因此执行通道用 RocketMQ，事实通道用 Kafka。没有压测过就不要报吞吐数字。无论选哪一个，写工具的幂等键都在业务库里，不依赖消息会恰好投递一次。

### 11. AI 编程你平时用哪些工具，Cursor、Copilot、Claude Code 怎么介入你日常开发，会不会带来代码质量风险

**答题思路**

只讲你真用过的，没碰过的不要凑数。按三类说它进了你哪一步：

1. 编辑器里的补全，帮你写重复代码和测试骨架。
2. 对话里改一块指定代码，你负责圈定范围和看 diff。
3. 终端里的编码代理，让它改文件、跑测试。说清你给它的权限：能不能联网、能不能直接提交。

主动把质量风险讲完，这是这题的得分点：

- 没跑测试、没人看 diff 就进主干。
- 生成出不存在的 API 或错误的调用方式，编译能过、语义是错的。
- 把内部仓库、日志和密钥贴进未经允许的服务。
- 大段代码没有人能解释，后续只有继续让模型改。

收法按你的真实习惯讲：小步 diff、关键路径人工审、测试和类型检查挡住合并、只用公司允许的工具、密钥和生产数据不进提示。最后补一句你怎么发现模型改错了的例子，用真事。

### 12. Harness 工程你理解是什么，Agent = Model + Harness 这句话你怎么展开讲

**参考答案**

结论：模型在给定上下文里选择下一步；Harness 是模型外面的运行时，决定模型能看见什么、能调用什么、循环何时停、状态留在哪里、结果算不算数。

可以按一次请求展开：

- 上下文组装：系统指令、裁剪后的历史、检索片段、工具 schema。模型无状态，这些都是 Harness 塞进去的。
- 工具运行时：参数校验、登录态鉴权、超时、沙箱或权限。模型只能提出调用，发不发由这一层决定。
- 循环控制：最大步数、token 预算、重复调用检测、停止条件。
- 状态：`thread_id` 和 checkpoint，崩溃和人工确认都靠它。
- 验收和观测：每一步的入参、出参、token、耗时，以及回归集。工具结果没有被引用，这次答复就不算完成。

模型可以换成另一家，Harness 还在。只有模型、没有这层运行时，就只是一次补全调用，撑不住超时、重复下单和进程重启。评测用的 Eval Harness 是另一套东西，它复用工具的假实现来跑用例，不要和线上运行时混成一个词。

### 13. 给一个场景：追觅的智能客服 Agent 要接订单、物流、售后三个系统，让用户一句话查退款进度并触发催办，画出架构并说清每步谁决策

**参考答案**

结论：查进度和催办走一张固定的图。模型负责抽槽和组织话术；能不能催，由策略节点根据售后状态决定。

1. 接入层核对登录态并限流，会话键使用用户和会话。身份只来自这里。决策者是网关。
2. 抽槽拿出订单号，以及用户是不是在要求催办。没有订单号，就调订单系统查该用户未完成的售后单：只有一笔时按规则选定，有多笔就反问。决策者是模型抽槽，歧义由规则停下来问用户，不让模型猜一笔。
3. 只读查询售后状态和物流节点。回复里的进度、时间只能来自工具 JSON。决策者是售后和物流系统，模型负责转述。
4. 催办前由策略节点检查：当前状态允许催、距离上次催办已经超过间隔、幂等键（用户、售后单、催办）还没用过。通过才调用售后的写接口。决策者是策略节点。模型不能因为用户话术强烈就跳过它。
5. 生成回复，说明进度和催办是否受理，不补充工具里没有的承诺。决策者是模型，但字段范围由模板约束。

催办超时后，按同一幂等键查询受理记录，再决定要不要重试。三个系统都挂在工具网关上，图里的节点不直接握有数据库账号。

### 14. 手撕算法：合并 K 个有序链表（优先队列实现，顺带说复杂度）

**参考答案**

结论：用小根堆保存 K 条链表当前的头节点，每次弹出最小的那个，再把它的后继推进堆。总节点数为 N 时，时间 O(N log K)，堆的额外空间 O(K)。

默认每条链表是非降序。堆里同一时刻每条链表最多一个节点，所以堆大小不超过 K。每个节点进出堆各一次，单次操作 O(log K)，合计 O(N log K)。输出复用原节点，不另开一条新链表。Python 的 `heapq` 在比较元组时，值相等会继续比较后面的元素；节点对象不能比较，所以元组里加上链表下标。下标在堆里是唯一的，比较不会落到节点上。

空链表直接跳过。全部为空时返回空。只有一条链表时，算法仍然正确，复杂度退化为 O(N log 1)。值全部相等时，下标只用来避免比较节点，不要求稳定排序。

```python
import heapq


class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next


def merge_k_lists(lists):
    dummy = ListNode()
    tail = dummy
    heap = []
    for i, node in enumerate(lists):
        if node is not None:
            heapq.heappush(heap, (node.val, i, node))
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node
        tail = node
        if node.next is not None:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next
```

边界：`lists` 为空；其中夹着空链表；K 等于 1；多条链表的头结点值相同。分治两两合并也是 O(N log K)，这题要求的是优先队列，就把堆的实现讲清楚。

### 2. 你带过 Agent 项目么，几个人，怎么拆任务，模型调用层和业务工具层谁写谁审

**答题思路**

人数、你是不是负责人，都用实话。没带过，就讲你作为核心开发和负责人怎么分。

1. 先说人数和你拍板的范围：只对自己的模块负责，还是对整条链路的上线负责。
2. 任务按运行时、工具网关、评测、业务场景竖着切。不要按「大家都改提示词」横切，那样没有人负责幂等和权限。
3. 模型调用层：超时、重试、日志、供应商适配，由工程来写。算法审效果、提示词和评测集，不直接改调用栈里的重试。
4. 业务工具层：懂订单、物流、售后的人写适配。另一个人审权限、幂等、错误码和超时，作者不单独合并写接口。
5. 评审分开：工具 schema 和权限走代码评审；提示词变更必须跑回归集，只看线下感觉不算过。

### 3. 当算法同学认为应该全自治 Agent，你作为工程侧坚持加人工确认节点，意见不合怎么推

**答题思路**

不要站在「工程对、算法错」上争。把动作按后果分级，用一批真实请求给双方看。

1. 先对齐目标：全自治要省掉人工，你要挡住的是不可逆和资损，不是所有自动化。
2. 把动作分成三档。只读查询可以自动。可逆、金额和影响面都小的动作，可以在有幂等和限额之后自动。退款执行、催办、改地址、设备控制，先人工确认。
3. 用影子流量说话：同一批请求让全自治方案跑在旁边，不真正写。看它会发多少次写操作、有多少次参数是错的。用这个结果讨论，不凭感觉。
4. 给出退场条件：确认节点在连续一段时间里若总是原样通过，并且误触发低于你们约定的线，就把这一档放开。条件写下来，避免确认节点永久堆在那里。
5. 你让步的部分也说清楚：只读和低风险档交给算法做自治，换取写操作留在策略节点。

例子必须是你自己的分歧。没有吵过架，就讲一次意见不同、最后定下规则的评审。

### 4. Agent 上线后老板问效果怎么量化，你建哪些指标：任务成功率、工具准确率、人工接管率、成本 per session

**参考答案**

结论：四个指标都按「会话或任务」计算，并且按意图分开。再加两条红线：写操作的重复执行次数，以及端到端 P95 时延。四个指标都好看、催办却发重了，不能算上线成功。

- 任务成功率：达到已核实终态的任务会话，除以有明确任务的会话。核实指回复和工具返回一致，或业务单到达目标状态。用户中途离开单独计数。闲聊成功率和退款成功率不要合成一个平均数。不用模型给自己打的分。
- 工具准确率：该调的时候，工具名和关键参数都对，才算对。另外单记「不该调却调了」。只看工具名会漏掉订单号幻觉。写工具的误调用单独作为严重问题，不和查询混在同一个百分比里。
- 人工接管率：转人工的会话除以全部会话。它下降时，要同时看投诉和重复进线，防止智能体把难的请求硬扛下来。接管之后是否真的解决，另看一条。
- 成本 per session：该会话里全部模型调用的费用，包含路由、重试、摘要、重排和最终回复，再加上按次计费的检索。报中位数和 P95。平均数会被死循环拉高，也不能代表大多数会话。

这四条按意图、按是否包含写操作切片。没有分母定义之前，先不要给老板一个总百分比。

### 5. Eval Harness 你怎么搭，离线用例集怎么来，bad case 怎么回流成回归集

**参考答案**

结论：Eval Harness 是一套可重复运行的用例和判分，不是线上那个 Agent 运行时。工具一律走假实现，写操作不能打到真实售后。

每条用例固定四样东西：用户输入、当时的上下文或设备状态、工具的假返回、期望。期望尽量是工具名、关键参数和是否允许写操作，这种可以用规则判分。话术只在需要时用评审模型，并且抽一部分人工核对。提示词既是被测对象，又当唯一裁判，结果会自己给自己放行。

用例从四处来：每个意图按规格写的主干和边界；线上脱敏后的真实说法；提示注入和不属于该用户的订单号；每次修过的故障。第一版可以小，但写操作和越权必须在里面。

回流做成固定动作：线上的工具报错、用户改口、转人工、重复催办，进入待看队列。标上原因后，若是智能体的行为问题，就脱敏，把当时的输入、工具返回和正确行为收成一条回归用例。改提示词、模型或工具 schema 之前先跑旧集。旧集变差，或新收进来的这条不过，就不要发。数据集和提示词一样要有版本。

### 6. 多 Agent 协作里某个子 Agent 一直产出低质量结果，是换 prompt、换模型、还是拆角色，依据是什么

**参考答案**

结论：先抽样归类，一次只改一个因素，用同一批用例对比。三件事一起改，就不知道是哪一下起了作用。

抽几十条低质量结果，分成四类：

- 缺了关键上下文，或工具结果没被用上：补状态和工具。换模型和改提示词都补不进根本没给它的字段。
- 信息够，错在格式、步骤或漏字段：改 prompt、schema 和例子。
- 信息够、格式也对，复杂判断仍然错：只把这个角色换成更强的模型，其他角色不动。
- 一个角色同时检索、做决定、还调用写接口：拆角色。写操作挪到策略节点，这个角色只留下它能做好的那一件。

依据是错误类型，加上同一批评测集上的前后对比，不是「感觉这个模型更强」。若四类里面上下文缺失占了大多数，先修上下文，不会先换模型。

### 7. MCP 协议和 Function Calling 的关系，为什么 2026 年大家开始聊 MCP，它解决了什么痛点

**参考答案**

结论：Function Calling 是模型选出工具并给出参数的方式；MCP 是应用和工具服务之间的协议。两者叠在一起用，MCP 不取代模型的工具调用。

Function Calling 里，应用把工具名、说明和 JSON Schema 交给某一家模型，模型返回要调用的名字和参数，真正执行的是应用自己的代码。各家厂商的 schema 格式并不相同，工具就写死在那个应用里。

MCP 是一套 JSON-RPC 协议。工具服务用 `tools/list` 公布能力，宿主用 `tools/call` 执行，还可以提供只读资源和提示词模板。本机进程常用 stdio，远程服务用 HTTP。宿主把 MCP 的工具列表转成当前模型要求的 function schema；模型仍然以 function call 做选择；宿主再把这次选择转发到 MCP server。

协议在 2026 年之前就已经发布。这一阶段被追着问，是因为订单、物流、售后不能再各写进每个 Agent 仓库。痛点是 M 个智能体乘以 N 个系统的适配，以及工具权限跟着某个框架走、换个运行时就要重接一遍。MCP 把售后做成独立服务，客服 Agent 和内部工具可以复用。谁有权催办，仍然由宿主的登录态和策略节点决定，协议本身不负责放行。

### 8. ReAct 和 Plan-and-Execute 在你项目里怎么取舍，什么任务你绝对不用 ReAct

**参考答案**

结论：下一步依赖上一次观察、并且工具只读时，可以用 ReAct。步骤大体已知，或其中有写操作时，用 Plan-and-Execute 或一张固定的图。退款、催办、下单、改地址、设备控制不用 ReAct。

ReAct 把「想一步、做一个工具、看观察、再想下一步」放在同一个循环里。排查故障、深度事先不知道、工具只读时，它能跟着观察改方向。代价是容易跑偏、重复调用，也没有一份可以先审的计划。

Plan-and-Execute 先产出步骤，执行器按步做；某一步的观察推翻了计划，再触发重规划。计划可以给人看，也可以在真正写之前交给策略节点。代价是计划会过时，所以要有明确的重规划条件，避免每一步都重新计划一遍。

查一个已知订单的进度，路径是固定的，用图即可，不必上 ReAct。绝对不用 ReAct 的是会改业务状态的动作：下一步由模型临时决定，确认点插不进去，失败后又容易再调一次。这些动作必须先被规则允许，再调用写接口。

### 9. Agent 安全你怎么做，提示注入、越权调工具、敏感信息回显分别怎么防

**参考答案**

结论：用户原文、检索片段和工具返回都当数据；身份只来自登录态；回复和日志只出允许的字段。提示词里的「请忽略以上指令」不能当安全边界。

提示注入：系统指令和外部文本分通道进入模型，检索结果和工具返回包在明确的数据区里。写工具不因为工具返回或网页里的一句话而放行，放行只看策略节点。这一轮若吃进了不可信检索，写工具默认不可用，或者必须再过一次独立策略。防御放在网关和策略上，提示词只是辅助。

越权调工具：按意图给工具白名单。`user_id` 只取登录态，模型参数里自报的用户 id 丢掉。每个工具在服务端检查资源归属，例如订单属于当前用户、售后单处于可催状态。写操作留下审计：谁的会话、哪个工具、哪把幂等键、策略是否通过。

敏感信息回显：回复使用字段白名单，手机号、地址、证件号在进入模型前和写入日志前脱敏。检索按租户或用户过滤，避免把别人的售后单取进上下文。密钥和内部地址不进提示词，也不随错误信息返回给用户。

### 10. 模型路由你做过么，简单意图用便宜小模型，复杂任务路由大模型，路由本身不准怎么办

**参考答案**

结论：路由错把难任务交给小模型，伤害大于多花一次大模型的钱。置信度不够、以及退款催办这类写操作，直接走大模型或规则。

路由器用规则加快小分类器，单独用标注集看它自己的准确率。它不应该是一次和目标模型差不多贵的大模型调用，否则省不下钱，也很难做回归。

不准时按这个顺序补：

- 置信度低于阈值，升级到大模型。阈值按小模型那一路的任务成功率来调，不按省下的金额来调。
- 投诉、退款、催办、改地址钉死在规则或大模型上，不进便宜模型。
- 小模型的工具参数两次校验失败，或用户把原话又说了一遍，升级一次，避免来回跳。
- 线上按路由切片看任务成功率和被升级的比例，并抽检留在小模型上的回答，计算「本该升级却没升级」的比例。

路由器和执行模型一起换，出了问题就分不清是谁变差。先固定一个，再改另一个。

### 11. 最近半年你学的新东西是什么，LangGraph 源码、某个 embedding 模型、还是 harness 模式，怎么学的

**答题思路**

三个里只选一个你真能展开的。面试官会追问细节，另两个没读过就不要并列。

1. 为什么学：线上的一个具体问题，例如崩溃后续跑、召回串了型号、循环停不下来。
2. 怎么学：沿着一条调用链读。例如从 `invoke` 到 checkpointer 的写入，或者从一篇模型说明到你自己的一小批评测。再做一个最小复现，把现象跑出来。
3. 学完能讲清的一个机制：checkpoint 在哪一步落下、这个 embedding 适合什么文本、Harness 里停止条件放在哪。只讲你能在白板上画出来的那个。
4. 你因此改了什么，或者明确决定先不改什么。没有落地改动，就讲你排除掉的一个错误做法。

### 12. 如果让你从零搭一套追觅内部的 Agent 开发框架，你会先写哪三层，为什么

**参考答案**

结论：按上线依赖的顺序写三层：工具网关、编排和状态、评测和追踪。模型供应商先做一个薄封装，多 Agent 市场和可视化编排先不做。

1. 工具网关。订单、物流、售后都从这里出去。统一 schema、登录态鉴权、超时、幂等键和审计。模型以后会换，写接口的安全边界先定死，否则每个业务组都会自己直接调售后。
2. 编排和状态。图、checkpoint、步数和 token 预算、人工确认。业务组只填节点，不再各自写一个 while 去调模型。供应商适配先嵌在这层里，等确实有成本问题再拆路由。
3. 评测和追踪。每一步留下 trace，再加上一套虽小但包含写操作和越权的回归集。没有这层，改提示词无法判断催办有没有被改坏。

这三层能把「一句话查退款并催办」送到线上。先不做的是：多 Agent 市场、拖拽编排、通用记忆中台。主路径还没跑稳，这些会把框架变成第二个业务系统。

### 13. 手撕算法：给定一个 DAG 表示 Agent 任务依赖，手写拓扑排序并输出一种合法执行顺序，顺便处理环检测

**参考答案**

结论：用 Kahn 算法。入度为 0 的任务可以执行，执行完就减少后继的入度。全部任务都能进入结果，就得到一种合法顺序；剩下入度降不到 0 的任务处在环上，或只能穿过环才能到达，不存在包含它们的合法顺序。

时间 O(V+E)，空间 O(V+E)。V 是任务数，E 是依赖边数。入度为 0 的若干任务可以并行，队列给出的是其中一种串行化结果。队列按任务输入顺序放入，结果是稳定的。若业务要优先级，把队列换成堆，复杂度变成 O((V+E) log V)。

输入约定：依赖对是 `(前置, 后置)`，前置必须先做完。若调用方给的是「A 依赖 B」（B 先做），建图时反过来。重边只计一次，否则入度会被加多。自环让该任务入度永远降不到 0，从而被环检测抓住。任务 id 重复直接拒绝。

有环时，函数仍返回已经能执行的前缀，同时返回无法执行的任务列表。前缀里的任务，它们的前置也都在前缀里，可以先跑；无法执行的那些要人工拆环，不能假装有一个完整顺序。

```python
from collections import defaultdict, deque


def agent_execution_order(tasks, deps):
    """返回 (可执行顺序, 因环而无法执行的任务)。依赖对为 (前置, 后置)。"""
    if len(set(tasks)) != len(tasks):
        raise ValueError("duplicate task id")
    indeg = {task: 0 for task in tasks}
    graph = defaultdict(list)
    seen = set()
    for pre, post in deps:
        if pre not in indeg or post not in indeg:
            raise KeyError("unknown task: %s -> %s" % (pre, post))
        if (pre, post) in seen:
            continue
        seen.add((pre, post))
        graph[pre].append(post)
        indeg[post] += 1
    ready = deque(task for task in tasks if indeg[task] == 0)
    order = []
    while ready:
        cur = ready.popleft()
        order.append(cur)
        for nxt in graph[cur]:
            indeg[nxt] -= 1
            if indeg[nxt] == 0:
                ready.append(nxt)
    done = set(order)
    blocked = [task for task in tasks if task not in done]
    return order, blocked
```

边界：没有边，顺序就是输入顺序；图分成互不依赖的几块，仍然能排出完整顺序；自环、重边、A→B→A 都要让环上的任务出现在第二个返回值里；依赖到了未声明的任务，直接报错，不悄悄加进图里。深度优先的三色标记可以找出一条具体的回边，Kahn 更直接对应「现在能跑哪些任务」。

## HR面

### 1. 自我介绍

**答题思路**

一分钟，少堆模型名词。

1. 你是做什么的：年限，最近在做能调用业务系统的 Agent，还是业务后端。
2. 一件你负责过的事：问题是什么，你推动了哪个决定，结果用真实情况，没有数字就不要编。
3. 为什么坐在这里：想把这件事做到设备售后这种有真实工单的场景里。
4. 停住，让面试官接「为什么看追觅」。

### 2. 为什么看追觅，家电硬件公司做 AI Agent 你觉得机会在哪

**答题思路**

按「场景 → 岗位匹配 → 为什么是现在」讲，不要空泛地说行业有前景。

1. 场景：设备在用户家里，故障、耗材、保修、物流、售后都是可查询、可执行的系统。Agent 的价值是把一句话落到这些系统上，查询进度、发起催办，而不是再做一个通用聊天窗口。
2. 岗位匹配：这个位子要的是能把 Agent 接进现有业务并扛住线上的人。对应你已经做过的编排、工具和评测，挑你真实做过的那一层说。
3. 为什么是现在：你想继续做生产落地。硬件公司有稳定的业务流程和明确的副作用，适合把人工确认、幂等和指标做实。
4. 收一句你想先做深的环节，例如售后查询和催办，表示你看过业务，而不是只看公司名。

### 3. 你现在薪资多少，期望多少，base 还是总包口径

**答题思路**

先把口径对齐，再报一个你算得过来的区间。文档里不写具体数字，面试时用你自己的真实包。

1. 问清对方说的是月薪 base、年度总包，还是含奖金和股票。你也按这两个口径分开说现在的数。
2. 期望给一个区间，下限是你能接受的总包，上限是你希望谈到的位置。区间来自你现在的收入和这次岗位的职责差，不报一个没拆过的整数。
3. 说明区间里你最看重的一项：base、奖金月数，还是股票及归属。主动问清奖金月数、发放条件和深圳的缴纳基数。
4. 若对方追问底线，重复你的下限，并表示可以在总包结构上商量。不在口径还没对齐时就把底线降下去。

### 4. 前三轮技术面下来你觉得哪轮最吃力，自己哪块最虚

**答题思路**

选一轮你确实卡过的，一分钟讲完。不要说「都还行」，也不要评价面试官。

1. 点名一轮。对照这场的内容，常见的卡点是：二面的 checkpoint 和长任务恢复，或三面让你拍板砍掉什么。选你自己那一轮。
2. 说清卡在哪一个追问，例如分不清「同一 thread 续跑」和「新输入重新从入口走」，或指标说得出名字但说不清分母。
3. 面试之后你补了什么：读了哪一段机制，或自己把边界情况写出来跑了一遍。
4. 收在这块和岗位的关系上：上线一定会遇到，所以你愿意先把这层做实。

### 5. 你做 Agent 项目时和算法、产品吵过架么，举一个真例子

**答题思路**

要一个真实的分歧，不需要戏剧化。没有当众争吵，就讲一次评审里的不同意见。

1. 场景：上线前的哪个动作要不要全自动。用你项目里的真实动作，不要临时编一个退款故事。
2. 双方在争什么：算法或产品希望少一步人工，你担心的是不可逆、重复执行或权限。
3. 你怎么处理：按后果把动作分级，拿一批影子请求给大家看，而不是比谁声音大。
4. 结果：最后定下的规则是什么，你让了哪一档，对方让了哪一档。有真实数字就说，没有就停在规则本身。
5. 一句反思：后来你会更早把分级标准写出来，避免吵到上线前一夜。

### 6. 未来三年你想成为 Agent 架构师还是往管理走

**答题思路**

选一条主线。两条都想要，听起来是没想过。下面按架构师来组织；若你确实要走管理，把第 4 点换成带人，但仍然要说你先对哪条系统负责。

1. 表明选择：未来三年以 Agent 架构师为主，手不离开关键链路。
2. 第一年：独立负责一条业务链路，从工具网关、状态恢复到线上指标和故障处理都跟着。
3. 第二到三年：把这条链路里可复用的部分收成内部框架，评审别人的工具权限和评测，而不是去管一个越来越大的提示词仓库。
4. 管理只作为需要时的责任：若小组需要有人排任务，你可以做，但判断标准仍是系统有没有在线上稳住。
5. 为什么不是现在就转管理：这个岗位要先有人把 Agent 做进订单和售后。你想先成为那个能拍板技术取舍的人。

### 7. 入职后能接受加班和线下协作节奏么，深圳 base 没问题吧

**答题思路**

两件事先分开答，都按你的真实约束说。

1. 深圳：能去就明确说能去，以及到岗时间。若需要搬迁，说出你需要的时间，不把困难留到 offer 之后。
2. 线下协作：说明你可以接受的节奏，例如关键评审和故障处理在现场，日常开发可以按团队既有方式。问清团队现在是全员坐班还是部分远程。
3. 加班：接受版本节点和线上故障时的投入。问清这是阶段性的，还是每周固定的长工时，有没有调休。你的接受范围用一句实话说完。
4. 不要主动承诺一个你做不到的工时。面试官要的是预期对齐，不是一句「都可以」。
