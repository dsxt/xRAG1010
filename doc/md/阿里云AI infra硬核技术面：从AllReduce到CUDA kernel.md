### 3. 解释一下 AllReduce 的工作原理，Ring AllReduce 和 Tree AllReduce 的区别

**参考答案**

**结论**：AllReduce 让每个 rank 都得到全体同形状张量的规约结果；训练里通常是求和，再除以进程数得到平均梯度。Ring 带宽好、延迟随规模变差，Tree 延迟是对数级。

Ring 分两段，每段 \(N-1\) 步。reduce-scatter 之后，每卡只持有 \(1/N\) 的完整和；all-gather 再把这块结果拼回全量。每卡发送量约 \(2\frac{N-1}{N}D\)，规模变大时接近 \(2D\)，和卡数几乎无关，所以带宽接近最优。代价是步数 \(2(N-1)\)，小消息或万卡时，延迟项会盖过带宽优势。

Tree 沿树向上 Reduce、再向下 Broadcast。单棵二叉树很多链路空着；NCCL 常用的 double binary tree 用两棵互补的树把带宽补上，步数仍是 \(O(\log N)\)。因此小消息、大规模更适合 Tree，大块梯度更适合 Ring。

NCCL 还会按拓扑使用多 channel、机内 NVLink SHARP，以及交换机上的 SHARP 做网内规约。应用侧一般按消息大小交给 NCCL 选算法。容易漏的一点：Ring 优化的是带宽，通信步数仍然随 \(N\) 线性增加。

### 4. NCCL 和 Horovod 在分布式训练中的优劣对比

**参考答案**

**结论**：二者不在一层。NCCL 是集合通信库，Horovod 是训练框架；GPU 上 Horovod 的后端通常就是 NCCL。新项目优先 PyTorch DDP/FSDP 或 Megatron 直接调 NCCL。

NCCL 提供 AllReduce、AllGather、ReduceScatter、AllToAll 和点对点，能按 NVLink、PCIe、InfiniBand/RoCE 的拓扑选算法，并支持 GPUDirect RDMA。它随 GPU 代际更新，张量并行和流水线并行需要的 AllToAll、Send/Recv 都靠它。它不管分桶、优化器和容错，换到非 NVIDIA 卡也要换对应的通信库。

Horovod 用统一 API 包住 TensorFlow、PyTorch 等的梯度同步，早期卖点是梯度融合、分层 AllReduce 和 MPI 启动。这些收益现在大多被 DDP 的 bucket 重叠和 NCCL 的拓扑感知覆盖。它对张量并行、流水线并行、FSDP 不是一等公民，多一跳抽象也不利于排通信死锁。

仍然适合 Horovod 的情况，是存量多框架代码，或者现场已经用 MPI 管理作业。容易漏的一点：把「Horovod 比 NCCL 快」当成同层对比会偏掉，该比的是 Horovod 和 PyTorch Distributed 谁来组织梯度，底层大消息性能都看 NCCL。

### 5. PyTorch DistributedDataParallel 的原理，数据并行和模型并行的区别

**参考答案**

**结论**：DDP 是多进程数据并行。每卡一份完整模型、不同的 mini-batch，反向时把梯度 AllReduce 成一致更新；模型并行切的是参数，二者切分对象不同。

DDP 启动时从 rank 0 广播参数。反向按 bucket 收集已经算完的梯度，在通信流上 AllReduce，和后续反向重叠。同步后的梯度会除以 world size，各卡用相同优化器步进，参数保持一致。梯度累积时用 `no_sync()` 跳过中间 micro-batch 的通信，只在最后一步同步，损失自己再按累积步数缩放。

数据并行复制模型、切分 batch，通信主要是每步一次梯度同步，模型必须放得进单卡，或配合 ZeRO/FSDP 把状态切开。模型并行切模型本身：张量并行把层内矩阵按行或列切开，Megatron 风格下每个 Transformer 层前向大约两次 AllReduce、反向再两次，延迟敏感，一般留在机内 NVLink；流水线并行按层分段，只在 stage 边界传激活，可以跨机，但要靠 micro-batch 填气泡。

单进程的 `DataParallel` 会把梯度收到一张卡上，还受 GIL 影响，和 DDP 不是一条路径。动态图如果有的参数某步没有梯度，要打开 `find_unused_parameters`，否则对应 bucket 会一直等。

### 6. 大模型训练中常见的显存瓶颈有哪些，如何优化

**参考答案**

**结论**：显存大头是模型状态、激活和算子临时缓冲，三块的优化手段不同。

混合精度 Adam 下，每个参数大约 16 字节：FP16 参数和梯度各 2 字节，FP32 主权重、动量、方差合计 12 字节。这部分随参数量走，和 batch、序列长度无关。激活随 batch、序列长度和层数增长，长上下文时经常超过参数。注意力若物化 \(N \times N\) 的分数矩阵，以及 GEMM 的 workspace，会再占一块临时显存。分配器碎片还会让「保留显存」明显高于「正在用的显存」。

对应做法：

- 模型状态：BF16/FP16、ZeRO 或 FSDP；显存仍不够再考虑 8-bit 优化器。CPU/NVMe offload 用速度换容量，万卡训练里通常是后手。
- 激活：减小 micro-batch、选择性重计算、FlashAttention、用张量并行/流水线并行/上下文并行把激活摊开。完整重计算大约多一次前向。
- 临时缓冲：融合算子，避免把中间张量写回 HBM。

梯度累积增大的是有效 batch，单步激活峰值仍由 micro-batch 决定。优化前先看 allocator 的分段统计，确认大头是参数、激活还是碎片。

### 7. ZeRO 优化器的三个阶段分别解决了什么问题

**参考答案**

**结论**：数据并行会在每张卡上各存一份模型状态。ZeRO 按阶段去掉优化器状态、梯度、参数的重复，换来的是参数 all-gather 的组织成本。

仍按混合精度 Adam 的 \(16\Psi\) 估算，\(N_d\) 是数据并行度：

| 阶段 | 解决的重复 | 每卡模型状态 |
| --- | --- | --- |
| ZeRO-1 | 优化器状态，大约 \(12\Psi\)，是最大的一块 | \(4\Psi + 12\Psi/N_d\) |
| ZeRO-2 | 再加上梯度 | \(2\Psi + 14\Psi/N_d\) |
| ZeRO-3 | 再加上参数，单卡放不下完整权重时才放得下 | \(16\Psi/N_d\)，另加临时缓冲 |

ZeRO-1/2 的通信量可以和普通数据并行相同：reduce-scatter 把梯度送到持有该分片的 rank，本地更新后 all-gather 参数，总量约 \(2\Psi\)。若实现成「先 AllReduce 完整梯度，再 AllGather 参数」，阶段 1 会多出一次参数通信。ZeRO-2 不在每张卡保留完整梯度。ZeRO-3 前向和反向用到参数前都要 all-gather，用完可丢，总通信量约 \(3\Psi\)，是数据并行的 1.5 倍，要靠预取和计算重叠盖住。

PyTorch FSDP 的 `SHARD_GRAD_OP` 对应阶段 2，`FULL_SHARD` 对应阶段 3。ZeRO 不切激活，激活仍靠重计算或模型并行。峰值还要算上 all-gather 缓冲，公式是驻留量，是下限。

### 8. KV Cache 的原理是什么，如何影响推理性能

**参考答案**

**结论**：自回归解码里，历史 token 的 K、V 每次都要参与注意力。KV Cache 把它们存下来，用显存和带宽换掉重复的投影计算。

没有缓存时，生成到第 \(t\) 个 token 要把前缀再投影一遍，解码总成本随长度明显变陡。有缓存后，每个新 token 只做一次 QKV 投影，注意力改成读取已有的 K、V。Prefill 一次并行处理提示词并写入缓存，通常更偏计算；decode 每步只算一个 token，却要读入全部权重和整段缓存，很快变成带宽瓶颈。

单请求缓存大约是 \(2 \times \text{层数} \times \text{KV 头数} \times \text{head dim} \times \text{序列长度} \times \text{字节数}\)，batch 再线性放大。它经常比权重更大，直接决定能并发多少条请求，从而决定吞吐。GQA/MQA 减少的是 KV 头数，量化减少的是每个元素的字节数。

容易漏的两点：计算量的大头往往仍是每步读取权重做 GEMM，缓存是随序列变长的额外流量；若按最大长度预留连续缓存，碎片和内部空洞会先于理论容量把请求打满，分页管理解决的是这块浪费。

### 9. 解释一下模型量化的基本原理，INT8 量化如何实现

**参考答案**

**结论**：量化用低比特整数保存张量，减少访存，并在硬件支持时走 INT8 算力；误差控制靠缩放因子和少数敏感层的高精度保留。

对称量化最常用：\(\text{scale} = \max|x| / 127\)，\(q = \mathrm{clip}(\mathrm{round}(x / \text{scale}), -127, 127)\)，反量化是 \(q \times \text{scale}\)。零点固定为 0，方便 INT8 Tensor Core。非对称量化再加 zero-point，能贴合偏在一侧的分布，运行时开销更大。

INT8 线性层一般这样落地：

1. 权重量化离线完成，scale 按输出通道统计，比整层一个 scale 更抗通道间差异。
2. 激活可以用校准集做静态 per-tensor scale，也可以 decode 时按 token 动态取 scale。
3. 整数矩阵乘用 INT32 累加，再乘上激活 scale 和权重 scale 回到浮点。按通道、按 token 时，输出 \((m,n)\) 的系数是 \(\text{scale}_x[m] \times \text{scale}_w[n]\)。
4. bias、LayerNorm、softmax 通常留在高精度，最后再加回去。

大模型激活有个别通道特别大。W8A16 只压缩权重，解码读权重的带宽下来，计算仍是 FP16。W8A8 才使用 INT8 乘加，常配合 SmoothQuant 把激活的量化难度按通道挪到权重上，或把离群通道留在 FP16。校准集要接近线上分布；min-max 对离群点敏感，可以用分位数或误差最小化来定范围。

### 10. AI 编译框架（如 TVM、MLIR）在推理优化中的作用

**参考答案**

**结论**：它们把模型图变成目标硬件上的内核，主要收益是融合、布局和少写长尾算子。TVM 是端到端编译器，MLIR 是多层中间表示，很多编译器在 MLIR 上做逐步 lowering。

TVM 一类的栈会先把计算图变成自己的 IR（Relay/Relax），做算子融合、常量折叠和 layout 变换，再在张量级选择 tile、线程绑定和共享内存，并用 AutoTVM/Ansor 这类搜索找调度。编译结果缓存成可执行模块，线上加载，而不是每个请求重编。

MLIR 用 dialect 把同一条 lowering 管道拆开：高层算子、结构化线性代数、循环、GPU/LLVM 可以分别做 pass。框架前端和不同芯片后端因此能复用同一套基础设施。它本身不保证某个模型比手写库更快。

在推理里，融合减少 kernel 启动和中间结果写回，量化算子也要在这里落到整数内核。动态 shape 会触发重新编译，所以上线要用形状范围和编译缓存。注意力这种热点，手写的 FlashAttention 往往仍然更快；编译器更适合长尾算子和跨硬件移植。

### 11. RDMA 通信相比传统 TCP/IP 的优势在哪里

**参考答案**

**结论**：RDMA 让网卡把数据从一块用户态缓冲直接搬到对端用户态缓冲，CPU 不跑协议栈，也不做多次拷贝。

TCP 发送通常要经过用户缓冲、内核 socket 缓冲和网卡描述符，接收再抄回来，还伴随中断和协议处理。GPU 训练若走这条路，梯度还要先落到主机内存，再进网卡。RDMA（InfiniBand，或 RoCE）用队列对注册好的内存，网卡 DMA 完成读写，延迟和抖动都更低，CPU 可以继续跑计算。配合 GPUDirect RDMA 时，网卡直接访问 GPU 显存，集合通信少一次主机中转。

代价也集中在网络本身。InfiniBand 有基于信用的流控；RoCE 需要 PFC、ECN 或 DCQCN 这类拥塞控制，否则丢包后性能会掉到不可用。编程接口是 verbs，连接和内存注册都比 socket 重，适合长连接、大块的训练通信，不适合拿来替代一般的请求 API。

### 12. Kubernetes 中如何调度 AI 训练任务，资源请求和限制如何设置

**参考答案**

**结论**：训练任务要整组同时启动、按拓扑占住 GPU，CPU 和内存用 Guaranteed，避免运行中被驱逐把 NCCL 集体打断。

GPU 由 device plugin 暴露为 `nvidia.com/gpu` 这类扩展资源。扩展资源的 request 和 limit 必须相等，不能像 CPU 那样超卖。CPU、内存也同样写成 request 等于 limit，QoS 成为 Guaranteed，节点内存紧张时不会优先杀掉训练进程。卡数按整机申请更常见，例如 8 卡机器申请 8 卡并独占节点，避免和别人分 NVLink、PCIe 和网卡。具体核数和内存按节点可分配容量留出系统占用，没有统一的「标准 GiB」。

默认调度器按 Pod 逐个放置。两个都要 8 卡的任务可能各拿到 4 卡然后一起死等，所以要用 Kueue、Volcano 或 coscheduling 做 gang。作业 API 可以用 PyTorchJob、JobSet 一类，由它们起 worker，再交给 gang 层准入。

还要处理训练运行时的周边资源：`/dev/shm` 用内存型 emptyDir 加大，Docker 默认的 64MB 会让 DataLoader 或 NCCL 共享内存失败；RDMA 用 SR-IOV 或明确的主机网络方案，并打开 `IPC_LOCK`；GPU 节点加污点，rank 映射尽量对齐 NVLink 域和网卡 rail。

### 13. 设计一个简单的参数服务器架构，描述数据流

**参考答案**

**结论**：Worker 算梯度，Server 按分片保存参数并执行优化器。稠密大模型的全量同步后来更多改用 AllReduce；参数服务器仍适合稀疏嵌入。

组件可以很简单。若干 Worker 各读一块数据；若干 Server 按参数下标或哈希持有分片；需要严格同步时加一个屏障。Server 上放着该分片的参数和优化器状态。

数据流：

1. Worker 向相关 Server pull 当前参数。
2. 用本地 batch 做前向和反向。
3. 把梯度 push 回 Server，由 Server 对分片做更新。
4. 进入下一步。BSP 在屏障处等全体 Worker；ASP 不等，下一轮可能读到略旧的参数；SSP 给陈旧度一个上限。

Server 之间不需要彼此交换稠密梯度，但每个 Server 的网卡会成为热点，分片不均时尤其明显。异步吞吐更高，复现和收敛要靠陈旧度约束。

稠密参数每步都全量更新时，AllReduce 没有中心瓶颈，带宽也更好，所以成为大模型数据并行的主干。嵌入表只有命中的行发生变化，push/pull 那些行更省，这是参数服务器还留在推荐和稀疏模型里的原因。

### 14. 手撕算法：实现一个简单的 MLP 前向传播和反向传播

**参考答案**

**结论**：先固定形状和损失函数，再写两次线性层。下面用一层隐藏层、ReLU 和全体元素平均的 MSE，反向和这个定义对齐。

记 \(X\) 为 \((B, D_{in})\)，\(W_1\) 为 \((D_{in}, H)\)，\(W_2\) 为 \((H, D_{out})\)。前向是 \(Z_1 = XW_1 + b_1\)，\(A_1 = \mathrm{ReLU}(Z_1)\)，\(Z_2 = A_1 W_2 + b_2\)。损失 \(\frac{1}{BD_{out}}\sum (Z_2 - Y)^2\) 对 \(Z_2\) 的梯度是 \(2(Z_2-Y)/(BD_{out})\)。线性层 \(Y=XW+b\) 的局部反向是 \(dW = X^\top dY\)，\(dX = dY\, W^\top\)，\(db\) 为 \(dY\) 沿 batch 求和。ReLU 的掩码用 \(Z_1 > 0\)，0 处取 0。

时间是 \(\Theta(B D_{in} H + B H D_{out})\) 量级的矩阵乘，反向大约再做输入梯度和权重梯度两侧，常数大约是前向的两倍。除参数外要保存 \(A_1\) 和 ReLU 掩码，空间随 \(B \times H\) 增长。

```python
import numpy as np

def mlp_forward(x, W1, b1, W2, b2):
    # x: (B, Din), W1: (Din, H), b1: (H,), W2: (H, Dout), b2: (Dout,)
    z1 = x @ W1 + b1
    a1 = np.maximum(z1, 0.0)
    z2 = a1 @ W2 + b2
    return z1, a1, z2

def mlp_backward(x, y, z1, a1, z2, W1, W2):
    # loss = mean((z2 - y) ** 2)，分母是 B * Dout
    batch, dout = z2.shape
    dz2 = 2.0 * (z2 - y) / (batch * dout)
    dW2 = a1.T @ dz2
    db2 = dz2.sum(axis=0)
    da1 = dz2 @ W2.T
    dz1 = da1 * (z1 > 0)
    dW1 = x.T @ dz1
    db1 = dz1.sum(axis=0)
    dx = dz1 @ W1.T
    return dx, dW1, db1, dW2, db2
```

若输出层改成按 batch 平均的交叉熵，\(dz_2\) 换成 \((\mathrm{softmax}(Z_2) - Y) / B\)，前面的线性层反向不变。面试时先把四个维度写在纸上，再写公式。

### 4. 如何设计一个支持万卡级分布式训练的系统架构

**参考答案**

**结论**：万卡先按网络拓扑放置并行策略，再保证任意节点挂掉后能从同一步恢复。单步能算完、作业能重启，之后才谈 MFU。

并行上，张量并行留在机内 NVLink，常见就是单机的 8 卡域；流水线按层跨机，用 1F1B 和足够的 micro-batch 压气泡；数据并行放在最外层。优化器状态用 ZeRO-1 或节点组内的 FSDP 即可，模型已经被 TP/PP 切开时，ZeRO-3 多出来的约 1.5 倍通信往往不划算。超长序列再加上下文并行，MoE 再加专家并行。精度用 BF16，注意力用 FlashAttention，激活用选择性重计算。CPU offload 会把计算卡在主机带宽上，只作为放不下时的后手。

网络上，跨机走 RDMA 和 GPUDirect，梯度不要绕主机内存。rank 按「机器内 GPU 编号 ↔ 网卡 ↔ 同一层接入交换机」对齐，让跨机集合通信尽量留在 rail 内。NCCL 用多 channel，由拓扑选择 Ring 或 Tree。

数据预先切成分片顺序读。检查点按 rank 分片异步写，清单里记录 global step、文件和校验和，只有清单提交成功才算可恢复；内容要包含优化器、学习率、RNG 和 dataloader 位置。调度用 gang 和节点独占，并留热备。任一 rank 失败就整组从上一个已提交 step 重启。

观测至少有 step time、MFU、暴露出来的通信时间、流水线气泡、慢 rank、loss、梯度范数和 GPU Xid。MFU 可以用每 token 约 \(6N\) 次线性层浮点除以硬件峰值来估算，注意力和重计算另算。TP 出了 NVLink 域、PP 的 stage 过多、检查点过勤，都会直接打到这几条曲线上。

### 5. 训练过程中出现节点故障，如何保证训练不中断

**参考答案**

**结论**：同步集合通信里，一台节点失败，这次 NCCL 通信就不能原地继续。能做的是尽快发现、丢掉未完成的 step，从上一份一致检查点整组重启。

检测要覆盖进程退出、NCCL 超时、step 时间看门狗，以及 GPU Xid 和网卡链路错误。挂死比崩溃更常见，所以不能只靠进程退出码。发现后由调度器把节点隔离，停掉还堵在通信里的其余 rank，拉起热备，按原拓扑重建进程组。

检查点必须是同一个 global step 的全体分片。异步写盘时，只有清单原子提交之后才对训练可见，写到一半的目录不能读。状态里除了参数和优化器，还要有学习率调度、Python/NumPy/Torch/CUDA 的 RNG，以及 dataloader 的 epoch 和偏移，否则恢复后的样本序列会对不上。失败那一步的更新整步作废。

频率是吞吐和回滚损失的交换：太密，日常 IO 吃掉 MFU；太疏，万卡初始化加加载的时间会放大每一分钟丢失的计算。弹性改 world size 需要重分片，实现复杂，生产里更常见的是原规模整组重启。

### 6. 模型推理服务的延迟和吞吐如何平衡，具体优化手段

**参考答案**

**结论**：吞吐靠批量把读权重的成本摊开，延迟靠少排队和缩短单步。二者在 batch 大小上对着干，所以按 TTFT 和 token 间隔的 SLO 去卡吞吐，而不是把 batch 拉到显存上限。

Decode 每步都要读完整权重，batch 越大，同样的权重流量服务的 token 越多，GPU 越划算；同时排队变长，单步变慢，KV Cache 也会先顶满。Prefill 更偏计算，一条长提示词可能把正在解码的请求堵住。

可用的手段：

- 连续批处理，按迭代组 batch，结束的请求马上离开。
- 把长 prefill 切成块，和 decode 交错，避免首 token 把 token 间隔打穿。
- Prefill 和 decode 分池扩容，两边的瓶颈一个偏计算、一个偏带宽。
- 量化、FlashAttention、解码步用 CUDA Graph 去掉启动开销。
- 投机解码用小模型或多头先猜几个 token，再由大模型一次验证；接受率不够时吞吐会变差。
- 前缀缓存复用相同提示词的 KV。交互请求和离线请求分队列。

张量并行能降单请求延迟，复制多副本能抬吞吐。扩容单位要和并行度对齐。GPU 利用率高不代表延迟合格，调度看的是排队时间和 TPOT。

### 7. 批处理（batching）对推理性能的影响，动态批处理如何实现

**参考答案**

**结论**：batch 提高权重读取和 GEMM 的利用率，也带来等待、padding 和长尾。大模型解码要在经典动态批处理之上做成按 token 迭代的连续批处理。

经典动态批处理把请求放进队列，凑满最大 batch 或到达等待时间就执行一次。GPU 因此少做很多只含一条请求的小内核。代价是短请求等长请求，变长序列要 pad 到本批最长，等待时间直接进延迟。

大模型如果沿用「凑一批然后各自生成到底」，先完成的请求会一直占着 batch 位置。连续批处理改成每轮只前进一步：请求有等待、prefill、decode、完成四种状态；每一轮在 KV 空闲块和 token 预算内挑选请求；用变长注意力，不把整个 batch pad 到最大长度；遇到停止符就归还缓存块，并把新请求插进来。Prefill 一次可能吃掉很多 token 预算，所以要单独限制它，给 decode 留步时。

公平性靠每租户的 token 预算、最长等待和必要时的抢占。抢占要么把 KV 换出，要么丢掉缓存稍后重算。这和「时间窗加最大 batch」不是同一个调度循环。

### 8. Redis 在 AI 基础设施中的典型应用

**参考答案**

**结论**：Redis 适合小 value、高 QPS 的控制和缓存，不适合训练样本、检查点和 GPU KV Cache。

常见用途有五类。在线特征存在推荐或排序的推理路径上，用模型版本和主键组 key。完全相同的请求可以做结果缓存，必须带模型版本和采样参数，并设置 TTL。限流、配额和调度锁用计数、字符串或有序集合，防止多副本同时把同一份模型加载进同一张卡。任务状态、心跳和配置热缓存用来挡住 MySQL。配置变更可以用 Pub/Sub 通知，但 Pub/Sub 不落盘，真相仍放在数据库。

值要小，热点 key 要拆开。只当缓存时可以不要持久化；若保存调度状态，再开 AOF/RDB 并明确丢失窗口。大块样本和 checkpoint 放对象存储或并行文件系统。KV Cache 由推理引擎在显存里分页管理，远程缓存即使存在，也是专门的层级存储，不是把张量放进 Redis。

### 9. MySQL 如何存储和管理模型元数据，索引设计考虑

**参考答案**

**结论**：MySQL 存可事务更新的元数据，权重文件放对象存储，表里只留 URI 和校验和。索引按真实的点查和列表查询来建。

核心是「模型名 + 版本」唯一。发布时在一个事务里插入不可变的版本行，再把 `model_head` 指到新的 `version_id`，读请求就只看到完整版本。回滚是把指针指回去。并发发布可以用版本列做乐观锁。

```sql
CREATE TABLE model_version (
  id BIGINT PRIMARY KEY,
  model_name VARCHAR(128) NOT NULL,
  version VARCHAR(64) NOT NULL,
  artifact_uri VARCHAR(512) NOT NULL,
  checksum CHAR(64) NOT NULL,
  status VARCHAR(32) NOT NULL,
  created_at DATETIME(3) NOT NULL,
  UNIQUE KEY uk_name_ver (model_name, version),
  KEY idx_status_time (status, created_at)
);

CREATE TABLE model_head (
  model_name VARCHAR(128) PRIMARY KEY,
  version_id BIGINT NOT NULL
);
```

`uk_name_ver` 服务按名字取某个版本。`idx_status_time` 服务「列出某状态、按时间倒序」的运维查询，组合索引跟着 WHERE 和 ORDER BY 走。URI、大段超参 JSON 不建索引；真要按某个超参过滤，把那个字段拆成普通列。注册表写入很少，索引不必堆很多，但每一条都要对应已知查询。在线延迟和 token 统计是流水数据，放时序库或检索系统，不放这张表。

### 10. Kafka 在训练数据流水线中的作用，如何保证数据顺序性

**参考答案**

**结论**：Kafka 用来切开生产、清洗和训练集生成，抗突发并支持按 offset 回放。顺序只存在于分区内部，训练样本的全局顺序通常还要主动打散。

生产者把日志、抓取结果或标注事件写入主题，训练前的清洗、质检和分片生成用不同 consumer group 各自消费。某个下游失败时从已提交的 offset 重放，不必让上游重跑。流量突增先堆在分区里，用消费滞后观察，而不是打满训练任务。

需要顺序的是「同一文档的分片」或「同一用户的事件」这种局部约束：用该 id 做 key，默认分区器会把同一个 key 送进同一分区。开启幂等生产者，重试不会打乱分区内顺序。消费者按 offset 顺序处理该分区，结果落稳后再提交。至少一次加上按样本 id 去重，比在整条训练链路里做跨系统的恰好一次更常见。

扩分区会改变 key 的落点，不能假设映射永远不变。全局有序也不该靠「只建一个分区」来实现，那会把吞吐打没。训练要的是可复现的数据集版本：消费到约定的时间或 offset 水位，落成文件，再打散成分片。SGD 本身希望样本打散，Kafka 的分区顺序不等于训练顺序。

### 11. Elasticsearch 如何用于模型服务日志的检索和分析

**参考答案**

**结论**：用 ES 检索和聚合近期的请求日志，按时间和租户、模型版本过滤，再看延迟分位和错误分布。原文长期归档放对象存储。

日志至少带时间、request id、trace id、租户、模型版本、状态码、错误类型、TTFT、token 间隔、输入和输出 token 数。模型版本、租户、状态、错误码、trace id 用 keyword；延迟和 token 数用数值；时间用 date。提示词默认不进索引，需要排查时再采样或截断，避免高基数文本把堆打满。

写入用按时间滚动的 data stream，ILM 做热、温和删除。查询走 filter context：时间范围加模型版本加租户，然后再做 date histogram、延迟分位和错误码 terms。分位是近似结构算出来的，用来看趋势和告警。request id 可以精确查一条，不对它做大范围 terms 聚合。

日志场景把 refresh 调长，换写入吞吐。mapping 尽量固定，避免字段爆炸。ES 承担检索窗口内的排障，按月的全量回放和分析更适合列式存储。每条日志上的模型版本是后面做 A/B 对照的前提。

### 12. 系统设计题：设计一个支持多租户的模型服务平台

**参考答案**

**结论**：控制面按租户管配额和发布，数据面按隔离等级决定独占 GPU 还是共享推理进程。共享才能提高利用率，公平性要落在每一轮的 token 和 KV 预算上。

网关做认证、租户鉴权和限流，按模型名与版本把请求转到后端。控制面保存模型制品、部署、配额和计费。调度面对每个租户使用队列，GPU 池支持独占和共享两类放置；需要多卡的副本按整组申请。数据面是推理引擎，连续批处理之外再加一层租户记账：每一轮限制该租户能占用的 token 和 KV 块，长请求不能把共享缓存吃光。

隔离分三档。合规或噪声明显的租户用独立节点池和独立副本。普通租户共享集群，但用命名空间、网络策略和制品 ACL 分开。大量小模型或小改动用同一底座加 LoRA，避免每个租户各加载一份完整权重。不可信的自定义模型放进沙箱池，不和托管模型混部。

计费和排障都按租户、模型版本记录 token、错误和 GPU 时间。独占最稳也最贵；共享必须处理冷启动、KV 碎片和邻居干扰。平台要能对单个租户降配额或摘流，而不重启整个服务。

### 13. 手撕算法：优化矩阵乘法，考虑缓存友好性和并行化

**参考答案**

**结论**：\(C = AB\) 的算术量仍是 \(\Theta(MNK)\)。优化靠循环顺序和分块让 B、C 的当前工作集留在缓存里，并行只切互不重叠的 C 块，K 维在块内串行累加。

行主序下，最内层沿着 N 走：\(A_{ik}\) 留在寄存器，\(B_{k,\*}\) 和 \(C_{i,\*}\) 连续读取，硬件预取有效。若整行比缓存大，就按 `tile` 把 i、j、k 都切开。对固定的 C 小块，把 K 方向扫完再换下一块，这块 C 在缓存里被反复累加。`tile` 让当前 A 面板、B 面板和 C 块能放进 L2，常见从几十试到几百，没有脱离缓存容量的万能值。

并行放在 i 的分块上，每个线程写不同的行，没有归约竞争。OpenMP 的线程在本地代码里才有多核；纯 Python 线程受 GIL 限制，盖不住这种计算。N 很小时，相邻行可能落在同一缓存行上，把 N 补齐到缓存行的倍数。规模大时下标用 64 位，避免 \(M \times K\) 溢出。生产 BLAS 还会把 A、B 打包成连续面板再进 SIMD 微内核，减少跨步和 TLB 抖动。GPU 上同一思想是 shared memory 分块加 Tensor Core，K 仍在块内累加。

时间 \(\Theta(MNK)\)，除 C 外额外空间 \(O(1)\)；若打包，额外空间与面板大小成正比。加速比最后会碰到内存带宽。

```c
#include <stddef.h>

/* 编译加 -fopenmp。A 是 M*K，B 是 K*N，C 是 M*N，均为行主序。 */
void matmul_tiled(const float *A, const float *B, float *C,
                  int M, int N, int K, int tile) {
    for (size_t n = 0; n < (size_t)M * (size_t)N; ++n) C[n] = 0.f;

    #pragma omp parallel for schedule(static)
    for (int i0 = 0; i0 < M; i0 += tile) {
        int i_max = (i0 + tile < M) ? i0 + tile : M;
        for (int j0 = 0; j0 < N; j0 += tile) {
            int j_max = (j0 + tile < N) ? j0 + tile : N;
            for (int k0 = 0; k0 < K; k0 += tile) {
                int k_max = (k0 + tile < K) ? k0 + tile : K;
                for (int i = i0; i < i_max; ++i) {
                    for (int k = k0; k < k_max; ++k) {
                        float aik = A[(size_t)i * (size_t)K + (size_t)k];
                        float *c_row = C + (size_t)i * (size_t)N;
                        const float *b_row = B + (size_t)k * (size_t)N;
                        for (int j = j0; j < j_max; ++j)
                            c_row[j] += aik * b_row[j];
                    }
                }
            }
        }
    }
}
```

### 4. 如何评估一个新技术的引入风险，比如从 TensorFlow 迁移到 PyTorch

**参考答案**

**结论**：按正确性、性能、生态和回滚四项评估，用同一份数据和双跑结果决策。社区热度不是迁移理由。

正确性看 loss 曲线、梯度范数和关键层输出，种子和数据要对齐，只保证 API 能跑不够。性能看 step time、显存、MFU 和扩展效率。TensorFlow 的图与 XLA，和 PyTorch eager 或 `torch.compile`，不会自动得到同样的速度。生态看自定义算子有没有对应实现、checkpoint 能不能转换、导出是 SavedModel 还是现有推理引擎能吃的格式。人的风险是团队是否真能排 PyTorch 分布式的死锁和显存问题。

推法是一个模型先影子双跑，模块逐步替换，旧栈留到指标过线。事先写好回滚线：正确性偏差、吞吐回退或故障率超阈值就停。分布式语义、BatchNorm/Dropout 的同步，以及优化器状态，往往比模型代码本身难迁。

现有栈已经稳定、收益只体现在招聘宣传上，就不必迁。新的并行策略、硬件支持和人手都被旧栈卡住时，再付迁移成本。

### 5. AI 基础设施领域最近有哪些重要技术突破，你关注哪些

**参考答案**

**结论**：这几年真正改变系统做法的，是注意力的 IO、推理调度、MoE 通信，以及 FP8 和更大的 NVLink 域。回答时挑两个自己能讲清瓶颈和代价的，不要报名字。

- FlashAttention 把精确注意力从「把 \(N \times N\) 矩阵写入 HBM」变成片上分块。FA2/FA3 主要改进并行度和 Hopper/Blackwell 指令，数学仍是精确注意力。
- Orca 的连续批处理和 vLLM 的 PagedAttention 改变了服务形态：按 token 调度，KV 按页分配，静态 batch 和按最大长度预留不再是默认架构。
- MoE 把总参数和每 token 计算分开。系统问题变成 AllToAll、专家负载和仍然巨大的优化器状态。MLA 则是从结构上压缩 KV。
- FP8 训练、投机解码、prefill/decode 分离、上下文并行，分别打在训练数值、解码步数、两类请求的干扰和长序列通信上。
- 硬件侧，GPUDirect RDMA 和更大的机内/机柜级 NVLink 域，决定了张量并行还能不能留在域内。

和训练岗位就重点准备通信与并行；和推理岗位就准备调度、KV 和伸缩。每个点都要能说出它没解决什么。

### 6. 解释一下 Flash Attention 的原理和优势

**参考答案**

**结论**：FlashAttention 是精确注意力的 IO 感知实现。它按块在片上 SRAM 做 softmax，避免把 \(N \times N\) 的分数和概率写回 HBM。

标准实现先物化 \(QK^\top\)，再 softmax，再乘 V，中间矩阵随序列长度平方增长，长上下文时既占显存也占带宽。FlashAttention 把 Q、K、V 切成能放进 SRAM 的块，用在线 softmax 维护当前行的最大值 \(m\) 和指数和 \(\ell\)。记新块的行最大值为 \(m_b\)、指数和为 \(\ell_b\)，则

\[
m_{\text{new}}=\max(m,m_b),\quad
\ell \leftarrow e^{m-m_{\text{new}}}\ell+\ell_b
\]

输出累加器先乘 \(e^{m-m_{\text{new}}}\)，再加上这块对 V 的贡献，然后把 \(m\) 更新为 \(m_{\text{new}}\)。全部块扫完后除以 \(\ell\)。这样不需要整行分数同时存在。因果掩码下，整块都在对角线上方的 tile 直接跳过。

优势是显存回到输出、Q、K、V 这一级，HBM 流量下降，长序列能跑、往往也更快。它减少的是访存，浮点次数并不更少。反向不保存注意力矩阵，而是用 Q、K、V 按同样的分块重算，再用计算换显存。浮点舍入顺序和朴素实现可能不同，但算法不是稀疏或线性注意力那种近似。

### 7. MoE（Mixture of Experts）模型在分布式训练中的挑战

**参考答案**

**结论**：MoE 省的是每个 token 的 FFN 计算，不是优化器显存，也不是通信次数。专家并行之后，主要难点是负载不均和大小不固定的 AllToAll。

每一层通常仍有稠密注意力，只有前馈被换成多个专家，每个 token 走 top-k。专家并行把不同专家放到不同 rank：本卡先算路由，再 AllToAll 把 token 派到专家所在的卡，算完再 AllToAll 回来组合。消息大小取决于路由结果，不像 AllReduce 那样规整，也不好和计算重叠。

负载会集中到少数专家，造成掉队，严重时部分卡激活爆显存、其余卡空转。常见约束是容量因子：每个专家每步只接收额定 token，溢出的丢掉或改道，丢弃会伤害质量。均衡手段包括辅助损失、router z-loss，以及按负载更新路由偏置、不再强依赖辅助损失的做法。专家内部用 grouped GEMM 处理变长 token 数。

全部专家的参数和优化器状态都要保存，总显存随专家数上涨。路由权重很小，一般复制；专家组和张量并行、流水线的进程组要单独规划，AllToAll 域太大时跨机成本会吃掉 MoE 的计算收益。推理时专家冷热会随流量变化，批处理更碎，KV Cache 却仍然按 token 保留。

### 8. 如何设计一个弹性伸缩的推理服务，应对流量波动

**参考答案**

**结论**：秒级波动用排队和连续批处理吸收，分钟级趋势才扩缩副本。伸缩信号用排队时延、在途请求和 KV 占用，单独看 GPU 利用率会误判。

一个副本若是张量并行组，扩容单位就是这一组卡，不是一张卡。缩容先摘流，等在途请求完成或迁移失败后重算，再释放 GPU，并设置冷却时间，避免副本来回创建。

冷启动的大头是加载权重。镜像预热、权重放在节点本地缓存、最小副本数保持温热，比收到流量再拉镜像有效。有明显的日周期时，按历史曲线提前扩，再由实时排队做修正。短尖峰若靠扩容，权重还没加载完，高峰已经过去。

Prefill 和 decode 分开之后，哪一边先破 SLO 就扩哪一边。多 LoRA 的租户波动优先调整适配器容量，不必每来一个租户加载一份底座。配额和集群碎片仍会让「指标到了却起不来」，调度要能看到整组卡是否同时空闲。

### 9. 模型版本管理和 A/B 测试在基础设施层面如何支持

**参考答案**

**结论**：版本是不可变制品加一个可切换的发布指针。A/B 在网关做粘性分流，指标和日志都带版本号，回滚就是把指针指回上一版。

注册表记录版本、制品 URI、校验和、代码、数据快照、配置和离线指标。tokenizer、最大长度和对话模板跟模型一起版本化，避免同权重不同预处理。发布流程从候选到影子，再到小流量，再到全量；每一步都有错误率、延迟和质量的停止线。

A/B 按用户 id 哈希分流，同一个用户固定落在一个版本上，否则前后两句会打到不同模型。影子流量复制请求、丢弃响应，用来比输出，同时计入配额，防止把 GPU 打满。金丝雀只放一小部分真实流量。两个完整大模型双份常驻很贵；差异只是适配器时，用多 LoRA 共享底座。架构不同就只能分副本。

质量对照需要在线指标，延迟变好不代表回答更好。蓝绿部署时，新副本健康并把指针切过去之前，旧副本保持可服务。

### 13. 手撕算法：实现一个简单的 CUDA kernel 进行向量加法

**参考答案**

**结论**：每个线程算一个元素 \(c_i = a_i + b_i\)。这个核没有数据复用，瓶颈是全局内存带宽，不是算力。

线程编号 `blockIdx.x * blockDim.x + threadIdx.x` 对应连续地址，一个 warp 的 32 个线程访问 32 个连续 float，也就是 128 字节，可以合并访问。block 大小取 256，保持 warp 对齐。`n` 不是 block 的整数倍时，用 `i < n` 挡住越界线程。数据已在显存里就不要为这个核再做一次主机拷贝。

每个加法对应两次读和一次写，共 12 字节，算术强度很低，占用率堆得再高也先碰到带宽。向量加法没有复用，放进 shared memory 只是多搬一次。下一步才是 `float4` 向量化加载，减少指令数，并要求 16 字节对齐、单独处理尾部；元素特别多时用网格跨步，让有限的 grid 覆盖全部 n。每次 CUDA API 和 kernel 启动都要检查错误，`cudaFree(nullptr)` 是安全的，所以失败路径上可以统一释放。

时间 \(\Theta(n)\)，每线程额外空间 \(O(1)\)，设备上三块数组共 \(12n\) 字节。主机到设备的三次传输若存在，往往会比核本身更显眼。

```cuda
#include <cuda_runtime.h>

__global__ void vectorAdd(const float* __restrict__ a,
                          const float* __restrict__ b,
                          float* __restrict__ c,
                          int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

int vectorAddCuda(const float* h_a, const float* h_b, float* h_c, int n) {
    if (n <= 0) return 0;
    float *d_a = nullptr, *d_b = nullptr, *d_c = nullptr;
    size_t bytes = (size_t)n * sizeof(float);
    cudaError_t err = cudaMalloc(&d_a, bytes);
    if (err == cudaSuccess) err = cudaMalloc(&d_b, bytes);
    if (err == cudaSuccess) err = cudaMalloc(&d_c, bytes);
    if (err == cudaSuccess)
        err = cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice);
    if (err == cudaSuccess)
        err = cudaMemcpy(d_b, h_b, bytes, cudaMemcpyHostToDevice);
    if (err == cudaSuccess) {
        int threads = 256;
        int blocks = (n + threads - 1) / threads;
        vectorAdd<<<blocks, threads>>>(d_a, d_b, d_c, n);
        err = cudaGetLastError();
    }
    if (err == cudaSuccess)
        err = cudaMemcpy(h_c, d_c, bytes, cudaMemcpyDeviceToHost);
    cudaFree(d_a);
    cudaFree(d_b);
    cudaFree(d_c);
    return err == cudaSuccess ? 0 : 1;
}
```
