### 2. 介绍你做过的 AI Agent 或 RAG 相关项目，说清楚你在里面的角色和核心难点

**答题思路**

### 3. JVM 内存模型，G1 与 ZGC 在长连接流式 Agent 服务中的表现差异

**参考答案**

这里和 GC 直接相关的是运行时内存：业务对象在堆上，类元数据在元空间，Netty 的 DirectBuffer 在堆外。流式连接还会长期留着会话和缓冲。如果对方改问并发可见性，再讲 JMM：对 volatile 的写 happens-before 之后对它的读。那是另一件事。

G1 按 Region 管理堆。年轻代回收要 Stop-The-World，停顿取决于要复制的存活对象；`MaxGCPauseMillis` 默认目标是 200ms，不是上限。超过 Region 一半的数组进入 Humongous 区，通常要等标记周期才回收，一次拼出来的大响应很容易踩中。安全点会停住所有 Java 线程，于是所有正在吐 token 的连接一起卡。

ZGC 用染色指针和读屏障，标记和整理大部分与业务并发，停顿主要来自根扫描，通常是亚毫秒，且不随堆大小成比例上升。JDK 21 引入了分代 ZGC，JDK 23 起分代是 ZGC 的默认模式。每个 token 都在制造短命对象：非分代 ZGC 要整堆回收，分配跟不上就会分配停顿；分代 ZGC 可以高频收年轻代。它要给并发整理留堆空间，堆顶满时尾延迟仍会抖。

会话活得久，老年代更胀；token 则是年轻代高分配。延迟敏感用分代 ZGC，缓冲池化，不要把整段回复合成一个大数组。堆外打满两种收集器都不管，要单独看直接内存和缓冲泄漏。

### 4. ThreadPoolExecutor 核心参数，Agent 并发调多个外部工具时如何设置线程池和拒绝策略

**参考答案**

七个构造参数是 corePoolSize、maximumPoolSize、keepAliveTime、时间单位、workQueue、threadFactory、RejectedExecutionHandler。

`execute` 的顺序是：工作线程少于 core 就建核心线程；否则入队；队列满了才把线程加到 max；再失败就拒绝。无界队列不会满，max 和拒绝策略都走不到。core 为 0 时，任务会先入队，再视情况补一个线程去跑队列。

工具调用是阻塞 IO，不要放进 `ForkJoinPool.commonPool()`，也不要用无界的 `newCachedThreadPool()`。按下游拆池，订单、物流、模型互不占用。线程数从「并发 ≈ QPS × 下游耗时」起估，上限是下游配额，不是 CPU 核数。队列用有界且要短，超载尽快变成工具错误，而不是排到用户超时。JDK 21 的虚拟线程能扛住大量阻塞调用，但每个下游仍要有信号量，否则慢接口照样堆积。

交互请求不要用 CallerRunsPolicy，它会占住 Tomcat/Netty 线程；调用方如果就是这个池的线程，还可能死锁。Discard 会把失败藏掉。自定义拒绝策略把这次调用收成明确的「工具忙」，交给编排降级。每次调用另设客户端超时；`Future` 超时不会自动打断正在跑的 HTTP，客户端自己的超时才放得开线程。线程要有名字，任务要带上 trace。

### 5. CompletableFuture 如何实现多个工具调用的并行与串行编排

**参考答案**

有依赖用 `thenCompose`，它会把返回的 Future 摊平。`thenApply` 只做同步映射，里面再返回 Future 就会套一层。彼此独立用 `thenCombine` 或 `allOf`。线程池用上一题的工具池，`supplyAsync` 不传池会掉进 commonPool。

```java
CompletableFuture<Order> order = CompletableFuture.supplyAsync(
        () -> queryOrder(orderId), toolPool);
CompletableFuture<String> answer = order.thenCompose(o -> {
    CompletableFuture<Logistics> logistics = CompletableFuture.supplyAsync(
            () -> queryLogistics(o), toolPool);
    CompletableFuture<Coupon> coupon = CompletableFuture.supplyAsync(
            () -> queryCoupon(o), toolPool);
    return logistics.thenCombine(coupon, (l, c) -> assemble(o, l, c));
});
```

`allOf` 在任一分支异常时，组合结果会异常完成，其他分支仍会继续跑，除非你自己 cancel。工具场景通常把每个调用收成「成功或带错误码的结果」，这样物流失败仍能返回订单。`orTimeout` 只让 Future 超时，不中断底层线程，HTTP 客户端要有自己的超时。不要在很小的池里对同一个池 `join()`，池被占满时会自己等自己。

### 6. ReAct（Reasoning + Acting）模式的执行流程，Agent 如何防止陷入无限循环

**参考答案**

ReAct 是一轮轮交替推理和行动。系统提示里给出工具清单；模型产出下一步，要么是某个工具和参数，要么是最终回答；运行时校验并执行工具，把观察结果追加进上下文，再调模型。工具是运行时执行的，不是模型自己执行的。

停的条件要写在运行时里，不能指望模型自觉收尾：

- 最大步数、墙钟时间和 token 预算。
- 同一工具加同一组参数重复出现就停。
- 观察结果没有新信息也停。
- 工具名必须在白名单里，参数过不了 schema 就不执行。
- 触顶后用已有观察做降级回答，或反问用户，不再调模型。

图里用状态中的步数做条件边，超过上限就到结束节点。高风险动作再加人审，不放进自动循环。

### 7. 意图识别在 Agent 系统中的实现方式，什么情况下用 LLM Router，什么情况下用规则分类

**参考答案**

常见是三条路叠在一起。规则用关键词、正则和槽位词典，命中就出固定意图。标注够多、集合稳定时，用小分类器。开放说法用 LLM Router：给定封闭的意图列表，要求输出 JSON 的意图、槽位和置信度。

规则用在集合小、延迟和成本紧、错了要审计的地方，例如退款确认、明确的订单指令。LLM Router 用在说法长尾、一句里有多个意图、意图还在变的地方。线上一般是规则先接高置信的流量，剩下的才进 Router。置信度不够就澄清，不要猜一个意图去调工具。多意图返回列表，由编排拆开，不要压成一个标签。

Router 的输出仍要过白名单和 schema。它只负责路由，不直接拿到比对话状态更多的工具权限。

### 8. LangChain4j 的 Chain 与 LangGraph4j 的 StateGraph 区别，什么场景必须用 LangGraph

**参考答案**

Chain 把步骤串成管道：上一步的输出就是下一步的输入。分支要自己写在 Java 里。LangChain4j 的 AiServices 也能做工具循环，但循环状态关在服务内部，不方便在任意一步停住、换机器接着跑，或让多个 Agent 改同一份状态。

StateGraph 把步骤做成节点，转移做成条件边，共享一份 State。节点只返回局部更新，字段怎么合并由 reducer 决定：消息列表要追加，没有 reducer 的字段会被整段覆盖。循环是正常结构，ReAct 就是「模型 → 工具 → 模型」。

固定的检索再生成不必上图。必须用图的是：控制流本身是循环或看累积状态分支、要在副作用前暂停等人、进程挂了要按 threadId 恢复、多个 Agent 写同一份状态。图能跑起来不等于能恢复，恢复要另接 Checkpointer。

### 9. RAG 全流程讲一下，文档切分 Chunking 策略怎么设计，如何做混合检索和 Re-rank

**参考答案**

离线把文档解析干净，去掉页眉目录和过期版本，按标题、段落、表格和代码的结构切开，再给每块打上来源、版本、生效时间和权限，写入向量索引和关键词索引。

切分没有统一长度。正文按几百 token 这个量级用召回评测来定；太长会掺进无关句，太短会丢掉条件。先按结构切，超长再打包到上限，块之间留重叠，避免一句话被切断。表格、代码、一组问答不要从中间劈开。也可以检索小块、回填它所在的小节，让模型看到完整上下文。纯按向量相似度切分更贵，结构清楚的文档不必先用它。

在线先把多轮问题改写成独立问句，再同时做向量召回和 BM25。两边的分数量纲不同，用 RRF 融合，常用常数 k 为 60，不要把余弦和 BM25 直接相加。权限和生效时间在精排前滤掉。交叉编码器只对召回后的几十条打分，留下数条放进提示词，并带上出处。精排贵，所以不能拿去扫全库。

生成要求只依据这些片段。检索没命中就明确说不知道。评测把召回和忠实度分开，答案通顺不能代替检索命中。

### 10. Redis 在 Agent 系统中一般存什么，对话历史大 Key 如何拆分

**参考答案**

Redis 适合放会话窗口、滚动摘要、槽位、工具幂等结果、限流计数、分布式锁，以及带知识库版本号的检索缓存。全文和向量索引放搜索引擎或向量库。一个会话不要收成一个大 String：单线程执行命令，大 value 的读取和删除会占住主线程，活跃用户还会无限变长。

按会话拆开。`{sid}` 作为 hash tag，元数据、摘要、历史落在同一个槽。历史用 List，一轮一个元素，`LPUSH` 配合 `LTRIM` 只留最近 N 轮；需要独立消费位点再用 Stream。滑出窗口的旧轮由任务折进摘要，请求路径只读摘要加最近窗口。单轮工具结果很大时，Redis 只留指针，正文放数据库或对象存储。幂等键用 `SET key result NX EX`。

会话要有 TTL，访问时续期；只续期不截断，活跃会话仍会涨。曾经落下的大 key 用 `UNLINK` 释放，不要用 `KEYS` 去扫。

### 11. 用户问了一个需要先后调用订单查询、物流查询、优惠计算三个工具的问题，Agent 工作流怎么编排，数据怎么拼装给 LLM

**参考答案**

物流和优惠都依赖订单，它们彼此不依赖。所以先查订单，成功后再并行查物流和优惠，最后拼装。用户身份从登录态取，覆盖模型自己填的 userId。订单号缺失就追问，不拿模型猜的单号去查。订单失败就停，不再调用后两个。

这是固定的有向无环图，边写在工作流里。模型负责补槽和最后的表述，不负责每次重新发现调用顺序。物流超时仍返回订单和优惠，并在结构里写明物流失败。读接口可以带同一个幂等键重试。

给模型的是裁过字段的 JSON，不是三份原始报文。金额用字符串或「分」的整数。查失败的字段用 null 加重错误码，不要省掉。提示词要求只根据这份 JSON 回答，金额原样引用，不要重算；标了错误的项就说暂时查不到。数字如果必须稳定，金额和状态用模板填，模型只写解释句。

```json
{
  "order": {"id": "1001", "status": "已发货", "amount": "89.00"},
  "logistics": {"state": "运输中"},
  "coupon": null,
  "errors": {"coupon": "TIMEOUT"}
}
```

### 12. 手撕算法：手写 LRU 缓存（支持 get 和 put）

**参考答案**

用哈希表定位节点，用双向链表维护使用顺序。靠近头的是刚用过的，靠近尾的是最久未用的。`get` 命中后把节点移到头；`put` 已有 key 时只改值并移到头；新 key 超过容量时删掉尾节点。头尾使用哨兵，插入删除不用分空链表。单次操作时间 O(1)，空间 O(capacity)。下面这份不是线程安全的；线上缓存用锁或 Caffeine。JDK 里也可以用 `accessOrder` 为 true 的 `LinkedHashMap`，在 `removeEldestEntry` 里淘汰。

```java
public class LRUCache {
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity");
        }
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        insertAfterHead(created);
        if (map.size() > capacity) {
            Node lru = tail.prev;
            unlink(lru);
            map.remove(lru.key);
        }
    }

    private void moveToHead(Node node) {
        unlink(node);
        insertAfterHead(node);
    }

    private void insertAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void unlink(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private static final class Node {
        final int key;
        int value;
        Node prev, next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }
}
```

### 1. 自我介绍

**答题思路**

二面时间用在架构上。身份一句带过，然后只讲一个系统：入口、编排、检索、工具、模型分别在哪，你负责哪一段。主动把一个你能解释清楚的取舍放在结尾，例如为什么工具是固定图而不是自由循环，或为什么先压检索而不是先换模型。指标只讲你真有的，并说清是首 token 还是整段结束。讲完停住，等对方选一个环节往下钻。

### 2. 深入讲你 Agent 项目的架构，QPS、P99 延迟、GPU 推理成本怎么控制和监控

**答题思路**

按「架构 → 三个指标怎么定义 → 怎么拆开 → 你动过哪一个旋钮 → 怎么监控」讲。数字必须是你能回溯的。

1. 架构用一条请求串起来：网关、编排、检索、工具网关、模型路由、会话存储。说清同步等待和异步任务的分界。
2. QPS 要说明是哪一个接口。用户请求 QPS 小于模型调用和工具调用，因为一次对话会扇出。
3. P99 先定义口径。首 token 看排队和 prefill，整段完成还要加上解码和工具。把预算分给检索、每个工具和模型，不要只用一个总超时。
4. 成本按「成功完成一次任务的输入输出 token，或 GPU 时间」讲。控制手段用你真做过的：路由用小模型、限制输出长度、检索结果缓存、不要把全量历史塞进每次请求。
5. 监控要有贯穿工具的 trace、token、排队时间、GPU 利用率和降级比例。告警看尾延迟和成本，不只看 QPS。
6. 被追问某一跳时，讲你怎么从 trace 里把它拆出来，以及改完用哪份评测或哪条曲线验收。

### 3. MySQL 大表按什么分库分表，跨分片聚合查询怎么处理

**参考答案**

先确认单表已经过了归档、索引和读写分离仍然扛不住，再分片。分片键要高基数、绝大多数查询都带、而且以后不改。查用户订单用 userId；按订单号点查用 orderId。只按状态这种低基数字段切，会把热点打进一个分片。

哈希分片均匀，但范围扫描要扇出。按时间范围分片方便归档，最新一片会热。订单号如果还要能路由，可以把分片基因编进单号。全局唯一键用发号器，不能靠各库自增。分片键相同、又经常一起查的表做成绑定表，连接留在片内。

跨分片聚合不要放在下单主路径上。必须做时，把过滤和部分聚合下推，各片并行，再在协调层合并。`ORDER BY ... LIMIT` 的第一页可以每片取 limit 条再归并；深分页不能各片都套一个大 offset，要么改游标，要么限制深度。没有分片键的查询走预先建好的检索索引，而不是每次广播全部分片。分析型的大汇总进汇总表或 OLAP，不在交易库上扇出。

### 4. RocketMQ 事务消息保证不丢且幂等的实现思路，Agent 异步长任务用 MQ 怎么设计

**参考答案**

事务消息解决的是「本地事务和消息一起成功」。先发半消息，消费者看不见；再执行本地事务；然后 commit 或 rollback。生产者在 commit 前崩溃的话，Broker 会回查，回查可能落到组内另一台机器，所以只能查共享数据库里的任务行，不能查本机内存。查到已提交就 commit，未提交就 rollback，暂时不确定就等下一次回查。

这仍是至少一次。同步刷盘避免进程崩溃丢掉还在页缓存里的消息，同步复制再覆盖单机故障，发送延迟会上去；默认异步刷盘没有这个保证。消费成功再返回成功，失败则稍后重投，次数耗尽进入该消费组的死信队列。幂等靠业务键：任务表对 taskId 做唯一约束，状态只允许 PENDING 到 RUNNING 再到终态，重复消息看到终态就直接成功返回。

长任务的接口先落任务行并发送事务消息，消息体只带 taskId，立刻把 taskId 返回给用户。不要靠一直不确认消息来占住一条长推理，消费超时是有限的。消费者用条件更新拿走租约，执行中续期；实例挂了，租约过期后由扫描或重投接手。已经成功的投递直接返回。工具副作用用 taskId 加步骤号做幂等键。结果写入任务表，用户轮询，或完成时再推送。不可重试的业务错误进死信并告警，不要无限重试。

### 5. 多级缓存（本地 Caffeine + Redis）在高频 RAG 知识查询中的设计，缓存击穿/穿透在问答场景如何防

**参考答案**

缓存检索结果，不缓存模型自由生成的答案，避免一次幻觉变成热点。Key 包含规范化后的问题、知识库版本、租户和权限维度，重建索引只需要换版本。本地 TTL 短于 Redis。读路径是 Caffeine，然后 Redis，然后检索；回填两级。

Caffeine 的 LoadingCache 能合并同一 JVM 里同一个 key 的并发加载，`refreshAfterWrite` 在刷新时仍返回旧值。这挡不住多台机器同时过期。击穿要在 Redis 上用 `SET NX` 做一把短租约，只有一个请求回源，其余等一下或先返回旧值。

穿透是问题在库里本来就没有，每次都打到向量库。问答是开放文本，布隆过滤器不好用。对确认无结果的查询写一条短 TTL 的空值，并限制异常长的 query。空值 TTL 太长会在刚入库时继续误判没有，所以宁短。个性化答案不能放进跨用户的本地缓存。

### 6. Sentinel 对 LLM API 做限流与降级，GPU 推理服务挂了如何 fallback 到小模型或规则引擎

**参考答案**

LLM 一次调用会占住 GPU 数秒，限流看并发槽位比看 QPS 更贴切。Sentinel 的线程数模式只是在数入口并发，不是隔离出一套线程池；调用如果没有自己的超时，槽位会一直被占。熔断用异常比例，或用高于正常生成耗时的慢调用阈值。阈值若按普通接口的几百毫秒来设，健康的长回答会把熔断器打开。

GPU 刚挂时抛的是连接异常，走 fallback；熔断打开后抛的是 BlockException，走 blockHandler。两条都要进同一套降级，只写一边的话，开头那批失败仍是 500。

降级在出第一个 token 之前决定，顺序是：没有副作用的请求，有限次换一个副本；封闭意图且检索命中，用规则模板填，不再调模型；低风险生成改走仍存活的小模型；其余明确告诉用户暂时办不了。已经开始吐字就发错误事件并关掉流，不要把另一个模型的后文接上来。熔断半开时放探测请求。trace 里记下实际模型，避免评测把降级结果算成主模型。

### 7. LangGraph 中 State 如何定义和管理，Checkpointer 做状态持久化和 Human-in-the-loop 怎么实现

**参考答案**

State 是一份有 schema 的共享数据，例如消息、意图、工具结果、步数、是否已批准。节点返回局部更新。消息用追加语义合并，普通字段用新值覆盖。大段工具输出只放引用，避免每个检查点都复制一份正文。

Checkpointer 在每个 super-step 之后按 threadId 存快照。同一个 threadId 才能接着跑。进程内实现换机器就没了，多实例要用 Redis 或数据库。schema 变了要能识别旧快照，不能默默反序列化错。

人工确认放在有副作用的节点之前：模型可以先决定调用哪个工具，图在真正执行前暂停，快照落盘，接口把待确认动作交给用户。同意之后用同一个 threadId 恢复；拒绝就把决定写进状态并走到修改或结束。`interrupt()` 这种写在节点内部的暂停，恢复时节点会从头再执行，所以副作用必须放在暂停之后，并且调用本身幂等。待确认状态要有超时。批准请求重复提交也要幂等。

### 8. 多 Agent 协作的 Orchestrator-Worker 模式，Agent 间如何做幂等和超时重试（Saga 补偿思路）

**参考答案**

编排者拆计划、保存步骤日志、决定下一步。Worker 只做一件事并返回结构化结果，不互相私自调用，否则超时和补偿就没有一份总账。每个 Worker 只看到它需要的那一段状态。

步骤键用 taskId 加 stepId。Worker 先按这个键查结果，做过就原样返回。读操作可以重试；写操作只有带同一个幂等键才能重试。超时先查这一步到底是成功、失败还是仍在跑。查不到结果就保持未知，不要立刻再执行，也不要立刻补偿。

Saga 的每一步有正向动作和补偿动作，补偿按成功步骤的反序执行，并且也要幂等。这不是两阶段提交，中间状态别人看得见。涉及钱和库存时，收成一个本身具备事务的业务接口，让 Agent 只调用它，而不是几个 Agent 分头改余额。整个流程有总超时，卡在补偿中的任务进入人工队列。

### 9. Agent 幻觉的常见原因，工程上怎么通过 RAG 约束、Self-Reflection、工具结果校验来缓解

**参考答案**

常见原因是上下文里没有依据，模型用参数记忆补上；检索到了错误或过期片段仍照着说；工具结果被忽略或被重新计算；长上下文中间的证据被丢掉；以及「尽量给个答案」的倾向。检索文档里的注入文本也会带偏后面的工具调用。

RAG 约束是：没有命中或分数不够就说不知道；片段带编号；提示词要求只使用这些片段。更稳的是抽查回答里的数字和单号是否真的出现在证据里，对不上就不展示。只在提示词里写「不要编造」挡不住。

Self-Reflection 是另一次调用，对照证据做清单：有没有证据外的数字、实体和原因。校验器要看到证据，输出结构化结论，由运行时决定放弃还是重写一次。它自己也会编，所以最多再来一轮，而且只用在高风险意图上。

工具结果先过 schema、枚举和范围。回答里的订单状态、金额必须等于工具字段。校验失败就重试工具或放弃，不能让模型改一个更像真的数字。三层里，schema 和工具核对便宜，应当默认开；反思贵，放在最后。

### 10. Function Calling / Tool Use 的参数校验与失败重试策略，工具执行异常时 Agent 如何选择 fallback

**参考答案**

运行时按这个顺序处理，不把选择权全交给模型。工具名必须在白名单里，不按相似名字模糊匹配。参数先过 JSON Schema，再做业务范围检查。userId、租户这些身份字段用会话里的值覆盖。解析失败或 schema 失败，把错误退回模型改一次到两次，仍失败就向用户要缺失的槽位，停止执行。

执行异常要分类。读操作的超时和 5xx 可以有限次退避重试；4xx 和无权限不重试。写操作没有幂等键就不要自动重试，先按幂等键查询结果。同一种非法参数反复出现，直接打断循环。

fallback 用一张事先允许的策略表：读失败可以换一个只读工具或返回缓存；写失败就停，不能改调一个权限更高的工具。模型可以建议下一步，但运行时拒绝表外的工具。最终回答在工具失败时只能说办不到，不能把错误文本润色成成功结果。

### 11. SSE / WebSocket 实现 Agent 流式输出接入 Java 后端的关键点和背压处理

**参考答案**

SSE 是服务端单向推送，`Content-Type` 为 `text/event-stream`，浏览器能按 Last-Event-ID 重连，适合吐 token。模型生成通常没有可重放的事件日志，重连更现实的做法是接上已保存的半成品，或重新发起并去掉重复前缀。WebSocket 是双向的，取消、补充输入和人工批准走同一条连接时用它，负载均衡要处理升级和粘性，多实例时用发布订阅把 token 送到持有连接的那台机器。

反向代理和压缩会把流式缓冲成一整段，需要关掉代理缓冲。工具调用期间没有 token，要发心跳，否则代理或容器会断开。`SseEmitter` 的超时要大于一次生成。不要用容器的请求线程同步堵到生成结束；用 WebFlux，或异步写出加单独的生产线程。同一个连接上的写出要串行，`SseEmitter.send` 并发调用会把帧打乱。

背压是有界队列加上减慢上游。模型读得比客户端快时，队列满了就暂停继续读模型，不要把 token 堆在无界队列里。客户端断开或长时间不读，就取消上游生成，否则 GPU 还在为没人看的输出花钱。丢弃中间 token 会把句子切坏，只能整段取消。

### 12. 手撕算法：给定一个字符串，手写按固定长度 + 语义重叠（overlap）做文本 Chunk 切分

**参考答案**

先按句读符切成语义单元，标点留在单元末尾。小数点两边都是数字时不当成句号。单元不超过 `size` 就直接用；超长的没有句读可依，按固定窗口硬切，相邻窗口重叠 `overlap` 个字符。再按顺序装箱，每箱长度不超过 `size`。下一箱从上一箱尾部回退若干个完整单元，回退总长不超过 `overlap`，并且至少丢掉一个已经输出的单元，避免死循环。一个单元比 `overlap` 还长时，不把半句硬塞进重叠。时间在块长视为常数时是 O(n)，空间 O(n)。这里按 UTF-16 code unit 计长度，生产环境应按码点或 token，避免把增补字符切开。

```java
public final class TextChunker {
    public static List<String> chunk(String text, int size, int overlap) {
        if (text == null || text.isBlank()) {
            return List.of();
        }
        if (size <= 0 || overlap < 0 || overlap >= size) {
            throw new IllegalArgumentException("require size > overlap >= 0");
        }
        List<String> units = splitUnits(text, size, overlap);
        List<String> chunks = new ArrayList<>();
        int i = 0;
        while (i < units.size()) {
            int length = 0;
            int j = i;
            while (j < units.size() && length + units.get(j).length() <= size) {
                length += units.get(j).length();
                j++;
            }
            String piece = String.join("", units.subList(i, j)).strip();
            if (!piece.isEmpty()) {
                chunks.add(piece);
            }
            if (j >= units.size()) {
                break;
            }
            int taken = 0;
            int k = j;
            while (k - 1 > i && taken + units.get(k - 1).length() <= overlap) {
                k--;
                taken += units.get(k).length();
            }
            i = Math.max(k, i + 1);
        }
        return chunks;
    }

    private static List<String> splitUnits(String text, int size, int overlap) {
        List<String> units = new ArrayList<>();
        int start = 0;
        for (int i = 0; i < text.length(); i++) {
            if (!isBoundary(text, i)) {
                continue;
            }
            addSegment(units, text.substring(start, i + 1), size, overlap);
            start = i + 1;
        }
        if (start < text.length()) {
            addSegment(units, text.substring(start), size, overlap);
        }
        return units;
    }

    private static void addSegment(List<String> units, String segment, int size, int overlap) {
        if (segment.isBlank()) {
            return;
        }
        if (segment.length() <= size) {
            units.add(segment);
            return;
        }
        int from = 0;
        while (from < segment.length()) {
            int to = Math.min(from + size, segment.length());
            units.add(segment.substring(from, to));
            if (to >= segment.length()) {
                break;
            }
            int next = to - overlap;
            from = next <= from ? from + 1 : next;
        }
    }

    private static boolean isBoundary(String text, int index) {
        char ch = text.charAt(index);
        if (ch == '\n' || ch == '\r' || "。！？!?；;".indexOf(ch) >= 0) {
            return true;
        }
        if (ch != '.') {
            return false;
        }
        boolean prevDigit = index > 0 && Character.isDigit(text.charAt(index - 1));
        boolean nextDigit = index + 1 < text.length()
                && Character.isDigit(text.charAt(index + 1));
        return !(prevDigit && nextDigit);
    }
}
```

## 三面

### 1. 自我介绍

**答题思路**

三面看判断力。用不到一分钟说明你做过能上线的 Agent 或 RAG，然后把话引到一个你负责到底的技术决定上：边界怎么划的、出过什么问题、你怎么验收。不要再讲一遍完整项目史。结尾留出你在三面准备展开的那个难点。

### 2. 项目介绍，遇到最难的技术问题是什么，怎么排查和解决

**答题思路**

项目用四五句重建上下文，时间留给一个真实问题。不要把「调通了接口」当成难点。

1. 现象要可观察：错答、重复下单、尾延迟、任务恢复后状态丢了，选你真查过的一种。
2. 排查按链路缩小范围。先看 trace 里时间花在模型、检索还是工具，再看那一跳的输入输出。保留当时的 prompt 版本、检索片段和工具原文，否则无法复现。
3. 改动只讲你做的那一处，以及没选另一个方案的原因。例如先做结果校验而不是先微调，因为坏例来自错误检索。
4. 验证用固定坏例加一份回归集，说明上线后看哪条曲线。
5. 最后补一句你会提前加上的护栏：超时、幂等或评测。承认边界，比把故事讲成一次根治更可信。

### 3. 为什么选 ReAct 而不是传统规则工作流，高确定性业务场景 Agent 自主性边界怎么定

**参考答案**

ReAct 用在下一步取决于上一步观察、路径事先枚举不完的任务，例如开放排查、多轮补槽。规则工作流用在步骤稳定、错了代价高、必须审计的流程。两者不是互斥的：语言理解用模型，合法转移用状态机。

高确定性业务里，模型可以做意图、槽位、在白名单里选一个读工具、起草回复。它不能跳过校验、编造单号，也不能自己增加工具。支付、退款、改权限这些副作用走固定节点，或先人工确认。每个状态有自己的工具白名单、步数上限、时间和 token 预算。身份从会话取。图的边就是自主性边界，写在提示词里的「请谨慎」不是边界。

流程图能画完、分支也不多的业务，就做成工作流，只在需要理解句子的节点上用模型。把这种流程放成自由 ReAct，延迟、成本和错路都会上去，还不好解释为什么调了那个工具。

### 4. Agent 响应 P99 过高，从模型推理、网络、工具超时、序列化几个维度说排查思路

**参考答案**

先定义是首 token 还是整段结束。前者看排队和 prefill，后者还包含解码和工具。拿慢请求的 trace，把时间拆成排队、检索、每个工具、模型首 token、解码和序列化。

模型侧看输入 token 是否过长、GPU 是否在排队、输出是否特别长、有没有冷启动。首 token 慢，查 prefill 和排队；token 间隔整体变大，查解码速度或安全点。为了填满 batch 而等待，会抬高尾延迟。

网络侧看跨可用区、TLS 和连接池。池耗尽时，等连接的时间会伪装成模型变慢。重试会把多次耗时叠进客户端看到的 P99，服务端单次日志却可能正常。代理把流缓冲掉时，客户端会在结束时一次性拿到全部内容。

工具侧看直方图有没有堆在超时值上。堆在那里说明请求撞上了 deadline。彼此独立的工具并行。连接超时和读超时分开，单个工具的超时要小于用户总预算。

序列化侧看历史是不是整份复制、图片是不是 base64、图状态是不是每步深拷贝，以及热路径有没有同步打印完整 prompt。`ObjectMapper` 复用。只有客户端耗时时，把 GC 日志对上，停顿会看起来像网络抖动。

### 5. Agent Hallucination 产生违规或虚假内容怎么拦截（敏感词 + 规则引擎 + 二次校验）

**参考答案**

三层都要有，而且用在出口，不只用在入口。敏感词和分类器扫输出。流式不能每个 token 立刻下发，要留一个短窗口，否则一个词被切在两个片段里就绕过了。命中后停掉后续生成，换成安全回复。高风险意图可以先缓冲整段再展示；低风险才边生成边发。

规则引擎管有标准答案的字段。价格、订单状态、库存必须等于工具或检索里的值，对不上就拦截。这类意图可以直接用模板填字段，不让模型写数字。

二次校验用一个看得到证据的检查器，判断声明是否被证据支持。它有超时。合规和交易场景超时就失败关闭，不把没查完的草稿发出去。检查失败可以按更严的提示重写一次，再失败就拒绝。被拦住的原文只进审计。

敏感词挡不住拆字和谐音。事实错误靠规则比对和二次校验，不靠把词表加长。

### 6. 用户点赞点踩数据如何回收用于模型微调或 Prompt 优化，数据标注闭环怎么设计

**参考答案**

点踩不能直接拿去训练。先把当时的完整上下文存下来：对话和轮次、prompt 版本、模型版本、检索到的文档、工具输入输出、点赞或点踩、可选原因。缺任何一段版本信息，后面都无法复现。手机号、地址等与这条坏例无关的内容去掉，并规定保留期限。

先分错类型。检索错了去改索引，工具错了去改接口，给定正确证据仍说错了才是生成问题。把检索失败混进微调，会让模型学会照着坏上下文回答。

更快的闭环是改 prompt 和检索，不是先训练。按错误类型抽样人工标注，优先标低置信和点踩，而不是全量。改动放到固定评测集和一份回归集上比，再按版本灰度。点赞率有偏差，生气的用户更愿意点，所以验收看评测，不看点赞率本身。

微调要等前两步还解决不了、并且有干净样本。监督微调用改写后的标准回答；偏好优化要成对的 chosen 和 rejected，单独一次点踩不是一对。保留不参与训练的测试集。每次发布记下评测差，并能用 prompt 版本把之后的点踩对回去。

### 7. 如果业务要求 Agent 支持图片输入做向量化检索（多模态），后端架构要改哪些地方

**参考答案**

图片放对象存储，数据库只留 id、归属、权限、哈希和大小。上传要限制类型和大小，并做安全检查。

文本向量和图像向量往往维度不同、空间也不同，不能写进同一个字段碰运气。文本问图片，需要两边在同一套多模态向量空间里，例如图文对比学习得到的编码器。做不到就另走一条旁路：用多模态模型生成说明文字，再进现有文本索引。说明文字可能编，只能当派生物，并保留图片 id。图里的文字用 OCR 进 BM25，视觉相似用图像向量，两条都留。

查询分两种。用户上传图片时，对图片做向量，召回相似图和关联文本，同时把图片本身交给多模态生成模型；只有向量、生成模型却是纯文本的，就回答不了「图里有什么」。用户用文字问时，只有空间对齐才能既搜文本也搜图，否则搜 OCR、说明文字和文本块。精排也要能看图，文本交叉编码器不能给图片打分。

索引按租户和权限过滤。缓存 key 带上图片哈希和模型版本。送进提示词的是降过分辨率的图，控制图像 token。评测集里要有图片问题，不能只用原来的文本集。

### 8. 最近在学什么 AI 新技术（新模型、新框架、新协议如 MCP/A2A），怎么快速上手一门新框架

**答题思路**

只讲一个你真的跑过的东西，用 20 分钟讲完。不要把名词表当成学习经历。

1. 它解决你现有链路里的哪一个问题：工具接入、Agent 之间委托，或评测。
2. 你怎么上手：先画对象模型，跑官方最小例子，再把你已经有的一个工具或一条工作流套进去。
3. 对照你现在的网关，写出例子里没有、上线必须有的部分：鉴权、超时、重试、幂等、trace。
4. 如果学的是 MCP：Host 管对话和权限，Client 连接 Server，Server 提供 tools、resources、prompts。模型不直接访问 Server。它和现有的 function calling 网关是同一层问题。
5. 如果学的是 A2A：Agent 用 Agent Card 声明能力，委托是一个有状态的任务，中间可以停下来等人输入。它解决的是 Agent 和 Agent 之间的发现与委托，不取代 MCP 那种对工具的协议。
6. 没进生产就明确说停在本地切片。把对照清单讲清楚，比声称已经替换了线上网关更可信。

### 9. 看你平时怎么跟进前沿论文或开源项目，举一个你从开源学到并应用到项目的例子

**答题思路**

讲来源和过滤器，再讲一个你真实改过的点。没有就不要编论文标题和项目名。

1. 来源收窄：你在用的框架的发布说明、少数论文和源码，而不是每天扫一遍预印本。
2. 过滤器只有一条：它是否改变延迟、评测或工具调用。不改变的先记下，不引进。
3. 例子按这个骨架：你在哪里看到它，对应你线上的哪类失败，你改了哪一段，用哪份坏例和回归集验收，论文或项目里你故意没抄的部分是什么。
4. 适合讲的真改动通常很小，例如父子切块、用 RRF 融合两路召回、给工具结果加 schema。把评测差讲出来。
5. 以「我读完了」结尾会站不住。以「没采纳的原因」结尾，能说明你有取舍。

### 10. 假如让你带两个新人做 Agent Harness 工程（SDK、评测、可观测性），你怎么做 Code Review 和技术分享

**答题思路**

Harness 是模型外面的运行时：工具 SDK、评测、可观测性。带人先给一条写下来的标准，再让他们沿着一条失败请求改代码。

1. 第一周结对完成「加一个工具」：schema、超时、幂等键、错误码、一条必须失败的评测、一条能串起来的 trace。
2. Review 先看失败路径。工具名和参数有白名单；身份字段不来自模型；超时能放开线程；重复请求不会做两次副作用；日志里没有密钥和完整证件号；取消能传到上游模型。
3. 评测不是演示用例。至少有一条「检索错了就必须失败」的用例，以及一份不能变差的回归集。数据和 prompt 要有版本。
4. 可观测性要求同一个 trace 穿过模型和每个工具，带上 token、prompt 版本和实际使用的模型。看一条失败 trace 就能重建输入。
5. 分享不要讲名词。拿一条真实的失败 trace，指出运行时本应在哪一步停下，再让新人改那一步并补评测。第二次分享只读一份评测报告：哪条变好，哪条被带坏。
6. PR 保持小。标准先写成一页清单，Review 时对着清单，而不是临时口味。

### 11. 手撕算法：实现一个简易版余弦相似度，计算两个 Embedding 向量的函数

**参考答案**

余弦相似度是点积除以两个向量的欧氏范数，实数向量的结果在 -1 到 1 之间。维度不同、空向量和零向量都没有定义，直接拒绝；零向量若业务上要当成不相关，可以改成返回 0，但不要把它算成相似。累加用 double，避免 float 连乘丢精度。浮点误差可能让结果略超出区间，需要严格落在区间内时再夹紧。不少嵌入接口返回的已经是单位向量，这时余弦等于点积；这个函数不假设已经归一化。时间 O(d)，额外空间 O(1)。

```java
public static double cosine(float[] a, float[] b) {
    if (a == null || b == null || a.length == 0 || a.length != b.length) {
        throw new IllegalArgumentException("vectors must be non-empty and same length");
    }
    double dot = 0.0;
    double na = 0.0;
    double nb = 0.0;
    for (int i = 0; i < a.length; i++) {
        double x = a[i];
        double y = b[i];
        dot += x * y;
        na += x * x;
        nb += y * y;
    }
    if (na == 0.0 || nb == 0.0) {
        throw new IllegalArgumentException("zero vector");
    }
    return dot / (Math.sqrt(na) * Math.sqrt(nb));
}
```

## HR面

### 1. 自我介绍

**答题思路**

HR 面用一两分钟讲清楚人，不讲架构细节。顺序是：你做什么方向、一个你负责到底的结果、你怎么和产品或算法配合、你为什么看这个机会。结果用你能解释的事实。最后落到你想继续做的 Agent 工程问题，把话交给对方。

### 2. 讲一个你最有成就感的项目或技术难点

**答题思路**

选一个你能讲清「你的决定改变了结果」的事。可以和技术面是同一个项目，但这面少讲组件，多讲结果和协作。

1. 当时的业务问题是什么，卡在哪里。
2. 你具体推动了什么，团队里别人负责什么，避免听成整个团队的成绩都是你的。
3. 难在取舍，不在加班。例如先保证金额不被编造，再谈回答好不好听。
4. 结果用你有的证据：坏例下降、事故不再复现、评测通过。没有数字就讲验收方式。
5. 补一句留下的风险，说明你知道它还没结束。

### 3. 团队协作中跟产品或算法同学意见不合怎么处理，举例

**答题思路**

用一件真事，按「分歧是什么 → 共同的判断标准 → 你做了什么 → 怎么收场」讲。

1. 把分歧说成一个可验证的问题。产品要覆盖更多问法，算法要先上更大的模型，你担心的是错误回答或延迟。不要讲成性格冲突。
2. 先约定标准：哪份评测、哪类用户伤害不能接受、延迟预算是多少。标准没对齐之前不争实现。
3. 拿一小份坏例或一条 trace 给双方看。能用样例结束的争论，不要用立场结束。
4. 你让步的部分和你坚持的部分分开说。例如可以先覆盖长尾问法，但金额必须来自接口。
5. 收场要有决定和负责人。如果最后采用了对方的方案，讲你怎么把它做成可回滚的，以及事后哪条证据说明当时的判断。

### 4. 为什么想来阿里千问 / 淘天做 AI Agent 方向

**答题思路**

讲你要解决的工程问题，不讲平台大、模型强这类空话。

1. 你想做的是能进交易或高并发对话的 Agent：工具、评测、失败可解释，而不是演示机器人。
2. 这个方向同时有模型和真实业务约束。千问这边是模型和协议，淘天这边是订单、优惠、物流这种不能编的事实。你把两边哪一边当成主线，按你真实的偏好说。
3. 接上你已经做过的一层，例如检索、工具网关或运行时，说明你能接手什么，还想补什么。
4. 不要假装了解他们的内部系统和编制。把你想确认的留给反问：上线门禁和业务边界。

### 5. 你未来 3 年的职业规划是走技术专家还是技术管理

**答题思路**

先选一个主线，用你现在怎么花时间来证明，不要两个都要。

1. 专家路线：三年内把 Agent 运行时做深，范围是工具可靠性、评测和故障定位，能对一条线上链路负责。带人是为了把标准传下去，头衔不是目标。
2. 管理路线：只有当你已经在带人、做排期和做取舍，并且愿意把写核心代码的时间让出来时才选。讲你准备先带小范围，自己仍保持能 Review 运行时。
3. 没想清楚就说实话：未来一年先把 Harness 这一层做扎实，再根据团队需要决定更偏专家还是带一个小组。三年内不把「转管理」当成离开技术问题的方式。
4. 无论哪条，都补一句你不会放下的判断力：什么改动可以上线，用哪份评测说话。

### 6. 能接受的工作强度和入职时间

**答题思路**

按真实情况说，现场不要改口编一个日期或节奏。

1. 入职时间用你真实的通知期和已经承诺的交接。还没和现团队确认，就说确认后的最早时间，不说「随时」。
2. 强度讲你能长期维持的节奏，以及你怎么保证发布质量。问清对方的发布频率、值班和故障响应，再判断是否匹配。
3. 可以接受阶段性冲刺，同时说清你依赖的条件：需求有边界、值班有轮换、上线有评测门禁。
4. 不把「能接受高强度」说成不需要睡眠和周末。HR 要的是稳定到岗和预期一致。

### 7. 还有什么想问我们的

**答题思路**

问三件你真的会用来做决定的事，问完听回答，不要连珠炮。

1. Agent 的上线门禁是什么：评测、人工抽检、还是只看离线分数。谁能拦住一次发布。
2. 自主性边界画在哪：模型能调用哪些写操作，支付和退款是否必须走人审或固定流程。
3. 平台和业务怎么分工：运行时、评测、工具接入分别由哪个团队负责，新人前半年最可能接手哪一段。

时间还够，再问值班和故障怎么升级。薪资和职级等对方进入这个话题再问，不要当成唯一的反问。
