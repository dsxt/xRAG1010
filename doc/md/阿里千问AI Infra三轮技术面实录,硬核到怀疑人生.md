### 2. 项目介绍，重点描述在 AI 基础设施领域的贡献

**答题思路**

用 STAR，把时间花在系统和取舍上，少讲业务故事。

1. 背景：模型规模、卡数、当时的瓶颈是显存、吞吐、故障恢复还是资源利用率。
2. 边界：自己负责哪一层，上下游是谁。调度、通信、数据、训练运行时、推理服务，只讲真正拥有的那层。
3. 方案：为什么选这个并行策略、存储或调度方式，放弃过什么。
4. 定位：profiler、trace、哪条指标证明瓶颈在计算、通信、数据或调度。
5. 结果：只报真实的前后对比。
6. 复盘：如果重做会改哪一个决定。

提前准备三个追问：通信量怎么估、显存大头在参数还是激活、挂了从哪一步恢复。

### 3. 请解释 CAP 定理，在 AI 训练场景中如何权衡一致性、可用性和分区容错性

**参考答案**

**结论**：分区发生时，训练步的参数更新要一致性；平台控制面可以偏向可用。整个 AI 平台不能只贴一个 CP 或 AP。

CAP 讨论的是网络分区下，线性一致和可用不能同时保证。分区没发生时两者可以同时有，分区恢复后还要能会合。训练通信按强一致处理：一次 AllReduce 少了一个 rank，就不能把剩下的梯度当成全局梯度，否则各卡更新会分叉。这一步应当失败，停在上一个已提交的检查点，牺牲的是这一步的可用。

控制面相反。提交作业、查询状态在分区时可以暂时读到旧状态，只要不把失败作业标成成功。检查点「哪一步已经提交」必须一致，否则恢复会读到写了一半的快照。样本缓存和日志可以最终一致。

没有分区时，同步 AllReduce 仍用延迟换一致，这是 PACELC 里的取舍，和 CAP 不是同一件事。弹性扩缩容也要先组成新的一致通信组，再继续下一步。

### 4. 请描述分布式训练中参数服务器架构与 AllReduce 架构的异同及适用场景

**参考答案**

**结论**：参数服务器适合稀疏、异构、需要弹性的更新；稠密大模型的同步训练更适合 AllReduce。

参数服务器把参数分片放在一组 server 上，worker 算完梯度再 push，然后 pull 新参数。异步方式允许旧梯度，worker 之间不用互相等，机器不齐时利用率更高，但陈旧梯度会影响收敛。同步方式要等最慢的 worker。每个 worker 都要发送完整梯度并拉回参数，server 的网卡和聚合能力是瓶颈，流量随 worker 数上涨。它增减 worker 相对容易，也适合只更新一部分 key 的稀疏嵌入。

AllReduce 没有中心参数节点。每个 rank 持有一份模型（或 ZeRO/FSDP 的一份分片），集体通信后大家都得到规约结果。Ring AllReduce 在规模变大时，每卡通信量接近两倍梯度，不随卡数线性涨。它天然是同步屏障，适合同构 GPU 上的稠密 Transformer。增减成员要重建通信组。

千亿参数的稠密预训练几乎都走集合通信。巨大的稀疏嵌入、机器异构、或需要随时增减 worker 时，才更适合参数服务器，或稠密部分 AllReduce、稀疏部分参数服务器的混合。容易漏的一点：同步参数服务器和 AllReduce 都要等慢节点，真正能容忍掉队的是异步参数服务器，代价在收敛。

### 5. 请解释 RDMA 的工作原理及其在分布式 AI 训练中的优势

**参考答案**

**结论**：RDMA 让网卡直接读写对端已注册内存，数据路径不进远端 CPU 和内核协议栈。分布式训练用它扛梯度交换的带宽和时延。

应用先把内存注册并钉住，拿到本地和远端的 key。发送队列上提交 SEND/RECV、READ、WRITE 或原子操作，网卡用 DMA 搬数据，完成后写入完成队列，应用轮询即可，不必每次中断。可靠连接（RC）提供有序可靠传输。常见承载是 InfiniBand，以及跑在以太网上的 RoCEv2。

训练里的优势是时延低、带宽高、CPU 占用小。NCCL 的跨机通信走 RDMA；GPUDirect RDMA 还能让网卡直接访问 GPU 显存，省掉 GPU 到 CPU 再到网卡的拷贝。大梯度、MoE 的 AllToAll、跨机张量并行都依赖这条路径。网卡要和对应 GPU 在同一 NUMA / 同一条 PCIe 路径上，否则 GPUDirect 会退回绕行。

RoCEv2 没有 InfiniBand 那种原生逐跳信誉流控，需要 PFC、ECN 和拥塞控制，配不好会出现暂停帧风暴。RDMA 也替代不了通信算法：消息很小时，跳数和时延仍然主导。容易漏的一点：内存注册有成本，通信缓冲应复用，不要每步重新注册。

### 6. 请描述 Kubernetes 调度器的工作原理，如何为 AI 训练任务定制调度策略

**参考答案**

**结论**：默认调度器按单个 Pod 过滤、打分、绑定；训练任务要改成整组同时启动，并按 GPU 拓扑装箱。

调度框架里，调度周期对一个 Pod 做 Filter 和 Score，再 Reserve 资源。绑定周期经过 Permit、PreBind、Bind。Filter 看资源、污点、亲和、卷；Score 默认倾向把 Pod 打散到比较空的节点。失败会 Unreserve，Pod 进入退避队列。调度器默认只认识 `nvidia.com/gpu` 的个数，不认识 NVLink 和网卡拓扑。

训练定制通常做四件事：

1. **Gang**：在 Permit 阶段等同一作业的 Pod 都预留成功再放行。超时没齐必须全部释放，否则会占着几张卡永久等待。
2. **装箱**：一台 8 卡机器要填满，让张量并行留在 NVLink 域内。默认的打散策略会拆散这组卡。
3. **拓扑**：同一作业优先同机，其次同一叶交换机；GPU 和 RDMA 网卡按 rail 对齐。节点上要有拓扑信息，调度插件才能打分。
4. **队列**：按租户配额、优先级调度。抢占必须整组考虑，只抢走一个 Pod 会让作业更死锁。

实现上可以用调度框架插件，或 Volcano、Koordinator、YuniKorn 这类已有 Gang 和队列的调度器。设备侧由 device plugin 或 DRA 上报 GPU。容易漏的一点：只加「需要 8 张 GPU」的资源请求，解决不了拓扑和整组原子性。

### 7. 请解释 GPU 虚拟化技术（如 MIG、vGPU）的原理及其在 AI 基础设施中的价值

**参考答案**

**结论**：MIG 是硬件分区，隔离强；vGPU 是虚拟机里的时间片，灵活但有抖动。两者用来填满小任务，不适合需要整段 NVLink 的大模型训练。

MIG 在 A100、H100 这类数据中心 GPU 上，把一张卡切成最多约 7 个实例。每个实例有自己的 SM 分区、显存分区和对应的内存控制器，算力和显存带宽按 profile 分开。一个实例上的核函数不会和另一个实例抢同一组 SM，一个实例把显存打满也不会直接占掉别人的那份显存。代价是实例之间不能再当成一张完整卡做 NVLink 集合通信，profile 也要在卡空闲时配置。它适合推理、开发和放不下一整卡的小任务。

vGPU 由宿主机驱动把物理 GPU 按时间片分给多个虚拟机，显存按 profile 划给虚机，算力是轮转共享。隔离弱于 MIG，延迟有时间片抖动，还依赖虚拟化许可。它适合必须进虚机的轻量推理和桌面，不适合步调一致的多卡训练。

还有两种弱一些的共享：MPS 让多个进程同时往一张卡提交核函数，空间上共享 SM，但没有硬件显存分区，一个进程出错可能波及 MPS 服务；Kubernetes 的时间片插件只是轮转，隔离更弱。平台上的价值是把 GPU 从「整卡」变成可配额的小单位，提高空闲卡的利用率。大训练仍应按整卡和整机分配。

### 8. 请描述模型并行与数据并行的区别，各自在千亿参数模型训练中的挑战

**参考答案**

**结论**：数据并行切批次，模型并行切参数。千亿参数两者都要，单用数据并行放不下状态，单用模型并行也会被通信或气泡拖住。

数据并行每卡一份模型、不同的 micro-batch，反向后对梯度做 AllReduce。混合精度 Adam 的模型状态大约按每参数 16 字节约：低精度参数和梯度，加上 FP32 主权重、动量和方差。千亿参数就是约 1.6TB，80GB 卡只放状态也要二十张以上，激活和碎片还要再加。ZeRO/FSDP 能把这份状态切开，但不切激活；长序列的激活仍可能先 OOM。纯数据并行还要把百 GB 量级的梯度同步出去，通信很难被计算盖住。全局批次过大之后，收敛也不再随批次线性变好。

模型并行里，张量并行把一层内的矩阵按行或列切开。Megatron 风格下，每个 Transformer 层前向大约两次 AllReduce，反向再两次，延迟敏感，一般限制在机内 NVLink，常见 2、4、8。跨机做张量并行，链路时延会直接打进每一层。流水线并行按层分段，只在 stage 边界传激活，可以跨机，但有气泡，比例大约 \((P-1)/M\)（\(P\) 是 stage 数，\(M\) 是 micro-batch 数）。首尾 stage 还有嵌入和损失，容易不均衡；全局批次必须够大，才有足够的 micro-batch 把气泡摊薄。

实际是机内张量并行、跨机流水线、外层数据并行，MoE 再加专家并行。检查点要能按并行度重新切分，否则一改规模就无法恢复。

### 9. 请解释梯度累积的原理及其在大批次训练中的作用

**参考答案**

**结论**：梯度累积用多次小批次反向，凑出一次大的有效批次，从而在显存放不下大 batch 时仍按目标批次更新。

每个 micro-batch 单独前向和反向，梯度加到同一块缓冲里，中间不清零。攒够 \(K\) 步再做一次优化器更新。有效批次约是 micro-batch × 累积步数 × 数据并行度。它降低的是激活峰值，优化器状态一点都不会变小。大批次能减小梯度方差，也减少优化器和通信的频率；通信只有最后一步需要同步。

缩放要对齐。每个 micro-batch 的损失如果已经是批内平均，累积 \(K\) 次相当于求和，更新前要再除以 \(K\)，否则梯度放大 \(K\) 倍。DDP 在最后一次反向做 AllReduce 时还会除以 world size，这和除以 \(K\) 是两回事，都要留。中间 \(K-1\) 步用 `no_sync()` 跳过通信，只在最后一步同步。

梯度裁剪要放在累积完成、并且混合精度已经 unscale 之后，对平均后的梯度裁。FP16 累积要用 FP32 梯度缓冲，并配合动态 loss scale；某一步溢出则整次累积作废。LayerNorm 不受批大小影响，BatchNorm 的统计量仍按 micro-batch 计算，累积不会合成一个大批次的均值和方差。

### 10. 请描述检查点（Checkpoint）机制在分布式训练中的实现难点

**参考答案**

**结论**：难点不是 `torch.save`，而是多 rank 在同一步留下一份可恢复、可换并行度、并且别把训练拖死的快照。

要保存的不只是权重。优化器里的 FP32 主权重、动量、方差、学习率调度、loss scale、各卡的 RNG，以及数据读到哪里，都决定能不能从这一步接着训。三维并行下每个 rank 只有一块分片，缺任何一块，这一步就废了。

写的时候各 rank 先写到临时位置，全部成功并 fsync 之后，再原子发布一份元数据：步数、世界大小、并行配置、分片清单。恢复只认这份元数据。进程死在写入中途时，旧的已发布版本必须仍然完整。

体积是 TB 级时，同步写盘会占掉整段训练。常见做法是先在计算流之外拷到主机内存或本地 NVMe，再后台上传。拷贝期间新旧缓冲同时在，显存和内存峰值会上去，要单独留余量。存储侧要避免成千上万个小文件打爆并行文件系统的元数据。

分片格式如果绑死在「rank 3 的本地 blob」，换卡数或换张量并行度就读不回来。应按全局张量保存分片映射，恢复时再重切。ZeRO 的优化器分片同样要有完整映射。

流水线里正在飞的 micro-batch 一般不落盘，恢复后从最后一次提交的迭代重算。容易漏的一点：只存了模型、没存优化器和数据位置，损失能接着打印，但已经不是原来那条训练轨迹。

### 11. 请解释阿里云 PAI 平台在弹性训练方面的技术实现

**参考答案**

**结论**：按阿里云公开资料，PAI 的弹性训练落在 PAI-DLC 上，是「Kubernetes 作业 + 精度无损的 EasyScale + AIMaster 容错 + EasyCkpt」几块配在一起，不是把 worker 数改掉就继续 AllReduce。

作业跑在 ACK 上，用 CRD 和 Operator（公开架构里的 KubeDL）管理 PyTorchJob、TFJob、MPIJob。资源可以被抢占或归还。公开分享把抢占分成温和抢占和暴力抢占：长任务被直接杀掉，几天的进度就没了。

朴素弹性会改变 world size，全局批次和学习率跟着变，精度会漂。EasyScale 在 PyTorch 上把逻辑训练线程和物理 GPU 拆开。缩容时在剩余卡上用多个 EasyScale 线程分时复用，把被拿走的那份计算留在逻辑线程里，使并行度、批次和学习率保持不变；扩容时再把逻辑线程迁回新卡。异构卡则按卡型调整计算量，避免慢卡直接破坏原来的超参。代价是缩容后一张卡要干多份逻辑 rank 的活，吞吐下降，换来的是不用重新调参。

真正出事时，AIMaster 作为额外的作业级实例做监控、容错判定和资源控制。同步任务在可重试错误上通常整作业重启，并限制重启次数；也能做 hang 检测。EasyCkpt 用异步分层检查点，先到内存、后台落盘，并利用三维并行或 ZeRO 的副本来缩短回退。开跑前还有健康检查，把坏节点隔离掉。

脚本侧不能把物理卡数写死成算法超参，检查点里要有优化器和步数。容易漏的一点：保持逻辑批次不变的 EasyScale，和 TorchElastic 那种直接改 world size 再热启动，是两条路线。

### 12. 请描述 Kafka 在 AI 训练日志收集与实时监控中的应用架构

**参考答案**

**结论**：Kafka 适合承接训练日志和作业事件，不适合替代监控系统去存每秒的 GPU 指标，更不能挡在训练的关键路径上。

每台机器上的采集进程读容器标准输出和结构化事件，异步发给 Kafka。训练进程只写本地，采集慢了就在节点上有界地落盘，磁盘到上限就丢日志或丢弃低优先级事件，不能把训练步堵住。Topic 按用途拆开：平台事件、训练日志、告警事件。用 `job_id` 做消息 key，保证同一个作业在一个分区内有序；跨 rank 的顺序本来就不存在，事件里要自己带 step、rank 和时间戳。

下游至少两类消费者：一类写入可检索的日志存储，一类做规则告警，例如出现 OOM、NCCL 错误、Xid，或者一个运行中的作业连续一段时间没有步日志。消费延迟本身就是监控信号。Schema 用 `job_id`、`rank`、`step`、`level`、`event_type`、截断后的消息，字段变更要能兼容旧消费者。

GPU 利用率、显存、网卡计数是高频数值，走节点上的指标采集和时序库更合适。若把万卡、一秒一次的原始指标全灌进 Kafka，分区数、存储和消费者都会被打满。日志也要采样，不要每步打印张量。

容易漏的一点：Kafka 不可用时训练必须继续；日志可以缺，梯度同步不能等 broker。

### 13. 请解释 Redis 在模型服务化（Model Serving）中可能扮演的角色

**参考答案**

**结论**：Redis 适合放小而热的路由、限流和精确缓存；不适合放权重、KV Cache，也不适合当唯一的元数据源头。

适合的角色有四类。一是模型路由缓存：模型名到版本、再到就绪实例，值很小，读多写少。二是限流和配额，用带过期时间的计数或令牌桶，拦截单租户打满。三是精确结果缓存，例如温度和参数都固定时的短结果、嵌入缓存。key 必须包含模型版本和规范化后的请求，并设置容量上限。四是短生命周期的会话状态。

发布通知可以把 Pub/Sub 当成「去刷新」的提示，但不能只靠它。Pub/Sub 不保存消息，订阅方当时不在就丢了。版本指针应放在可持续读到的 key 或数据库里，订阅只是加速。

不适合的也明确：解码用的 KV Cache 在 GPU 上，容量和时延都不是 Redis 能接的；权重用对象存储和节点本地盘；需要审计的计费、正式的模型元数据以数据库为准，Redis 只是缓存，丢了可以重建。在线解码队列也放在推理引擎进程内，再绕一跳 Redis 只会增加尾延迟。语义相似缓存需要向量检索，普通 GET 做不到。

Redis 故障时，缓存和限流应降级，推理本身继续；限流若必须失败即拒绝，要在设计里单独写明。分布式锁只适合做预热去重这类最好努力的协调。

### 14. 手撕算法：实现一个支持动态扩容的环形缓冲区（Circular Buffer），要求线程安全

**参考答案**

**思路**：用一块数组加 `head` 和下标计数表示环形队列。空和满都靠 `size` 区分，不浪费一个空槽。写满时持有同一把锁，分配两倍容量，把有效元素按逻辑顺序拷到新数组开头，再写入新元素。多生产者多消费者共用一把锁和一个条件变量：`push` 扩容后 `notify`，`pop` 在空队列上等待。锁要覆盖扩容的全过程，读线程不能看到拷贝到一半的数组。

动态扩容后，锁外不能再持有内部槽位的引用，弹出时把元素所有权交给调用方。缩容可以不做，避免来回抖动。只靠头尾指针做无锁 CAS，解决不了「旧数组何时能释放」；真要无锁扩容，需要 epoch 或 hazard pointer。面试里用互斥锁是正确实现。

**复杂度**：平摊后 `push`、`pop` 都是 \(O(1)\)，扩容那一次是 \(O(n)\)。空间 \(O(n)\)，扩容瞬间新旧数组并存，峰值大约再多一倍。扩容期间其他线程会停在这把锁上。

```python
import threading
import time


class DynamicRingBuffer:
    def __init__(self, capacity=8):
        if capacity < 1:
            raise ValueError("capacity must be >= 1")
        self._buf = [None] * capacity
        self._head = 0
        self._size = 0
        self._cv = threading.Condition()

    def push(self, item):
        with self._cv:
            if self._size == len(self._buf):
                self._grow()
            tail = (self._head + self._size) % len(self._buf)
            self._buf[tail] = item
            self._size += 1
            self._cv.notify()

    def pop(self, timeout=None):
        with self._cv:
            if timeout is None:
                while self._size == 0:
                    self._cv.wait()
            else:
                deadline = time.monotonic() + timeout
                while self._size == 0:
                    remaining = deadline - time.monotonic()
                    if remaining <= 0:
                        raise TimeoutError("pop timeout")
                    self._cv.wait(remaining)
            item = self._buf[self._head]
            self._buf[self._head] = None
            self._head = (self._head + 1) % len(self._buf)
            self._size -= 1
            return item

    def _grow(self):
        old_cap = len(self._buf)
        new_buf = [None] * (old_cap * 2)
        for i in range(self._size):
            new_buf[i] = self._buf[(self._head + i) % old_cap]
        self._buf = new_buf
        self._head = 0

    def __len__(self):
        with self._cv:
            return self._size


if __name__ == "__main__":
    buf = DynamicRingBuffer(2)
    buf.push(1)
    buf.push(2)
    buf.push(3)  # 触发扩容，顺序仍是 1, 2, 3
    assert [buf.pop(timeout=0) for _ in range(3)] == [1, 2, 3]

    shared = DynamicRingBuffer(1)
    out = []

    def produce(start):
        for i in range(start, start + 100):
            shared.push(i)

    def consume():
        for _ in range(200):
            out.append(shared.pop())

    threads = [
        threading.Thread(target=produce, args=(0,)),
        threading.Thread(target=produce, args=(100,)),
        threading.Thread(target=consume),
    ]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    assert sorted(out) == list(range(200))
```

### 3. 请描述你在项目中如何实现训练任务的故障恢复与自动重试机制

**参考答案**

**结论**：同步训练丢一个 rank，旧的通信组就不能继续。恢复的主路径是检出故障、隔离坏节点、用备用资源拉起整组，再从最后一次一致的检查点续跑。

故障要分开处理。进程崩溃、机器被抢占、链路抖动，通常可重试。梯度 NaN、数据损坏、配置错误，重试只会循环失败。GPU 的 Xid、ECC、NVLink 错误要把节点隔离，不能立刻调度回同一台机器。

检测靠三层：进程退出码、集合通信的有限超时，以及作业外的心跳。NCCL 卡死时进程往往不会自己退出，必须由外部控制器发现「步日志或心跳停了」再杀掉整组，否则会一直占着卡。超时设得太短会误杀正常的长尾 step，太长又浪费卡时，应按正常步时的分布留余量，而不是抄一个固定秒数。

重试要有预算和退避，并按退出原因做黑名单。同一作业反复撞上同一台机器，应摘掉机器而不是无限重启。开跑前做健康检查，镜像提前拉好，资源池里留少量备用节点，能把「等调度」从主要恢复时间里拿掉。

续跑点只能是已经原子发布的检查点。未完成的 step 重算。数据读取要么能按步数确定性回放，要么明确接受最后一小段样本重放。指标上报和文件发布要能容忍重复执行。

PAI-DLC 公开的做法是这个结构的一个实例：AIMaster 做作业级监控和重启判定，同步作业整组重启并限制次数，EasyCkpt 缩短回退距离。容易漏的一点：只给进程套一个 `restartPolicy`，解决不了 hang，也保证不了各 rank 从同一步恢复。

### 4. 请解释你如何监控分布式训练中的性能瓶颈（如 GPU 利用率、网络带宽、存储 IO）

**参考答案**

**结论**：先把一步拆成数据、前向、反向、通信、优化器和存盘，再决定看 GPU、网络还是存储。利用率高不等于算得有效。

GPU 看两层。`nvidia-smi` 的利用率只说明核函数在跑，MFU 才说明有效算力。利用率高但 MFU 低，常见是访存瓶颈或核函数太碎。用 PyTorch Profiler 或 Nsight Systems 看一次正常 step 和一次慢 step：时间线里大段空白，多半是 CPU、数据或同步；核函数本身长，再看是算力还是带宽。

通信看每步 AllReduce / AllToAll 的耗时，以及它有没有和计算重叠。网卡收发字节可以和名义带宽比，但要同时看重传、RoCE 的暂停帧。各 rank 的 step 时间放在一起，最慢的那个就是掉队者，再下钻它的数据、温度、ECC 和链路。所有卡都是 100% 或都是 0%，同时步数不涨，优先怀疑集合通信卡死，而不是「GPU 很忙所以没瓶颈」。

存储看数据队列是否被抽空。队列经常空，GPU 就在等数据。区分带宽和元数据：大分片读不满，是吞吐；海量小文件时，延迟在元数据操作。主机侧看 IO 利用率和并行文件系统的延迟，不要只看 GPU。

容易漏的一点：只在 rank 0 打点会漏掉掉队者。每个 rank 的分项耗时都要能对上同一步。

### 5. 请描述你如何优化跨可用区的训练任务通信延迟

**参考答案**

**结论**：先别让频繁集合通信跨可用区。调度把一个作业收进同一个可用区；实在放不下，也只让少量、消息较大的边界跨区。

可用区之间的往返通常是毫秒级，机柜内互联是微秒级，带宽还常常被共享和限速。张量并行每一层都要通信，跨区会把时延打进每一层，应留在机内。数据并行的梯度有参数那么大，跨区带宽项通常也吃不消。

分层 AllReduce 的价值要说准确：区内先做 reduce-scatter，再在区之间同步分片，能减少跨区流的数量和慢链路上的步数，但每个区仍然要把约一整份梯度送出去。它不按区内卡数把跨区流量除掉。真正能少跨区字节的，是把跨区切在流水线边界上，传的是一块激活，而不是每层的张量并行或整份梯度。局部 SGD、梯度压缩能减流量，但会改变收敛，预训练里不是默认项。

跨区消息要攒大，让带宽盖过往返时延；桶太小会被 RTT 主导。链路用训练专网，不要绕 NAT。上线前先测区间往返和实际 GB/s，再用这个数决定能不能拆作业。

调度上，同区是硬约束；只有用户明确允许，才降级成跨区，并且同时改并行计划。容易漏的一点：把普通 VPC 的连通当成训练带宽。能 ping 通不代表能喂饱集合通信。

### 6. 请解释你如何设计一个支持多租户的 AI 训练平台，包括资源隔离与配额管理

**参考答案**

**结论**：配额按 GPU 型号记账，调度按整组作业扣减；隔离至少做到节点、网络、存储和故障域，而不是只加一个 namespace。

每个租户有独立身份和队列。配额分成保证额度和可借用的空闲额度，维度包括 GPU 型号、卡数、并发作业数、最长运行时间和存储。H100 和 A100 不能折成同一个「GPU 个数」。原生 ResourceQuota 能限制扩展资源的数量，但不理解整组原子性：作业拿到 7 张还差 1 张时，不应把这 7 张从别人的额度里长期扣死。

调度用队列做公平或按主导资源公平。借用部分可以抢占，抢占前给出检查点窗口；保证额度内的长任务不作为默认牺牲品。小开发任务可以用 MIG，正式训练按整卡，并尽量独占节点。同机的其他卡仍共享 CPU、内存和网卡，嘈杂的大作业应进独立节点池。

RDMA 很难像 CPU 那样软限流。训练租户用独立的网卡或速率隔离，避免一个作业的暂停帧影响整网。存储按目录做容量和 IOPS 配额，密钥按租户分开。Pod 默认不给特权，不挂别人的 hostPath，网络策略默认拒绝跨租户访问。

控制面也要隔离：按租户限制 API 速率，避免一个用户的查询拖住调度器。计量按作业出账。容易漏的一点：GPU 上的侧信道和故障扩散，MIG 也不能完全消掉，强隔离仍靠节点池。

### 7. 请描述你如何实现训练模型的版本管理与部署流水线

**参考答案**

**结论**：一个版本是不可变的一组产物，外加评测记录；部署只切换指针，不覆盖旧文件。

产物至少包括权重、分词器、配置、训练代码版本、数据快照 ID 和评测报告。大文件放对象存储，用内容哈希寻址；数据库存版本号、阶段（开发、预发、生产）和别名。分布式优化器的分片要先合并成服务能读的格式，或显式带上分片说明。分片不全，流水线应直接失败。

流水线按关卡走：训练产出检查点，导出成推理格式，跑质量、安全和时延评测，通过后才允许把别名指向新版本。发布用金丝雀，先切一小部分流量，看错误率和质量再加大。旧版本在观察期内保持可加载，回滚就是把指针指回去。

服务侧同时加载两个版本会占两份显存，计划里要写多余容量从哪来，不能假设一张卡放得下两份权重。请求路由带上版本，进行中的请求不要被热更新打断。

容易漏的一点：权重文件相同，不代表行为相同。预处理、分词器和依赖版本都要锁进这个版本，否则线上无法复现评测结果。

### 8. 请解释你如何利用 Elasticsearch 实现训练日志的实时检索与异常检测

**参考答案**

**结论**：Elasticsearch 用来按作业检索日志和做聚合告警。它是近实时，不是指标库，也不能挡住训练。

日志从节点采集进 Kafka，再由消费者写入 ES。Kafka 负责削峰，ES 慢或宕机时训练继续。索引按时间或 data stream 切分，并设生命周期：热数据短保留，过期删除。`job_id`、`rank`、`event_type` 用 keyword，`step` 用数值，消息正文用 text 并截断。不要对原始报文字段做无限制的动态映射，高基数聚会把映射打爆。

检索先限定 `job_id` 和时间范围，再搜 OOM、NCCL、Xid 这类关键词。默认刷新间隔大约 1 秒，所以「实时」是秒级可见。

异常检测优先用能解释的规则：某个运行中作业每分钟错误数、NaN 的比例、或者长时间没有步日志。ES 自带的无监督异常检测可以当线索，阈值和误报要另说清楚，结论用时序指标再确认。不要在 ES 里做逐 token 的检测。

集群规模按写入量和保留期估，训练日志和在线业务检索分开，避免互相拖垮。容易漏的一点：日志在背压下会丢，ES 不适合当唯一审计账本。

### 9. 请描述你如何保证训练数据的安全性与隐私保护

**参考答案**

**结论**：按数据分级做权限、加密和审计；默认假设日志、本地盘和检查点都会把训练数据带出去。

数据先分级：公开、内部、个人数据、客户数据。个人数据进 GPU 集群前完成脱敏或审批，训练作业绑定到不可变的数据快照，并用校验和防篡改。Pod 使用短时凭证，只能读该快照的前缀，凭证不写进镜像。

静态加密覆盖数据集和检查点，传输用 TLS。RDMA 默认不提供这层加密，威胁模型若要求链路上的机密性，不能假装 RoCE 已经加密，而要靠专网隔离或额外方案，并接受成本。节点本地 NVMe 会缓存样本，作业结束后要清除；core dump 同样会留下数据。

权限上，生产集群和办公网络分开，默认禁止把原始数据下载到个人环境。租户之间网络隔离，不能挂到别人的数据目录。日志里关掉原始样本打印。检查点继承数据的密级，不能因为「只是权重」就放到公开桶。

防的另一类问题是记住训练集和数据投毒。去重、来源追踪是基本项。差分隐私训练能约束记忆，但会伤效用和速度，只在威胁模型需要时使用，不作为默认加速手段。

容易漏的一点：只给对象存储加了权限，忽略了节点缓存、日志和崩溃转储这三条旁路。

### 10. 请解释你如何评估与选择存储系统（如 Ceph、Alluxio）用于大规模训练数据

**参考答案**

**结论**：Ceph 一类系统做持久的数据源，Alluxio 一类系统做靠近计算的缓存。检查点的唯一副本不能只放在缓存里。

训练的读法是大量顺序读、多 rank 各读各的分片、同一个热数据可能被反复读，启动时还会有元数据尖峰。数据应先整理成大分片，而不是千万个小文件。

Ceph 是存储系统本身，对象、块、文件都能提供，多副本或纠删码保证耐久，适合当数据集和检查点的源头。CephFS 的元数据服务怕海量小文件；纠删码有读放大和重建成本，热数据更常用副本。它的聚合带宽取决于集群规模和网络，一个小 Ceph 喂不了几千张 GPU。

Alluxio 坐在对象存储或 Ceph 前面，把热数据缓存在内存或本地 SSD。它能减少远端延迟、挡住重复的 epoch 读取，但容量小于数据湖，源文件变了就要失效。训练应钉住一个不可变快照。FUSE 还有额外开销。缓存未命中如果同时发生，仍会打垮后端，所以热数据集要预热。

选型时实测四件事：聚合 GB/s 是否喂得饱 GPU、元数据操作每秒多少、首个 batch 要多久、命中率以及重启后的行为。检查点是大块顺序写，必须等持久层确认；缓存节点宕机会丢写回数据。常见组合是对象存储或 Ceph 当源头，Alluxio 或节点 NVMe 当读缓存。

### 11. 请描述你如何优化 PCIe/NVLink 拓扑结构以提升多 GPU 训练效率

**参考答案**

**结论**：让每层都要通信的张量并行留在 NVLink 域里，并让 GPU 和它用的网卡走同一段 PCIe，不要跨 CPU 插槽绕路。

NVLink / NVSwitch 是机内 GPU 之间的高带宽互联。名义带宽量级上，A100 大约 600GB/s，H100 大约 900GB/s。PCIe Gen4 x16 单向大约 32GB/s，Gen5 x16 大约 64GB/s。这是名义值，实际以拓扑和 NCCL 测得的 busbw 为准。Ring AllReduce 的速度由环上最慢的一段决定，一对 GPU 从 NVLink 掉到 PCIe，整环都跟着掉。

做法是：

1. 用 `nvidia-smi topo -m` 看 GPU 之间是 NVLink 还是跨 PCIe / 跨插槽，rank 的相邻关系按这个表排，而不是按卡号想当然。
2. 张量并行不超过一个 NVLink 域，常见就是单机 8 卡以内。没有 NVLink 的 PCIe 卡，缩小张量并行或改成数据并行。
3. 网卡和 GPU 同 NUMA、同根复合体，打开 GPUDirect，避免每次通信经 CPU 内存。ACS / IOMMU 有时会禁止对等访问，需要用带宽测试确认没有退回 CPU。
4. Hopper 及之后如果有 NVSwitch 上的规约（NVLS），AllReduce 可以少在某张 GPU 上折返。
5. 数据加载线程绑在同一插槽，避免跨插槽喂数据。

容易漏的一点：平均带宽好看没有用。先看最慢链路和实际集合通信带宽，再改框架配置。

### 12. 请解释你如何处理训练中的内存溢出（OOM）问题，有哪些调试工具与方法

**参考答案**

**结论**：先分清是 GPU 还是主机、哪一个 rank、从第几步开始，再把峰值拆成参数、梯度、优化器、激活和工作区。`empty_cache` 不降低峰值。

GPU OOM 是分配器申请失败；主机 OOM 常常是进程被系统杀掉，pinned memory 和过多 DataLoader worker 也会把主机打满。第 0 步就失败，多半是并行配置或形状过大。每步上涨，更像泄漏，例如把带图的损失攒进列表。某一 rank 单独失败，对比各 rank 的形状，流水线的嵌入层、最后一层和大词表经常更重，MoE 还会因 token 不均倾斜。

PyTorch 的 `memory_summary` 和 memory snapshot 能看分配块；`memory_stats` 区分 allocated 和 reserved。`nvidia-smi` 的占用包含缓存和其他进程，它远大于 PyTorch allocated 时，先怀疑碎片或别的进程，而不是模型突然变大。碎片导致「当前已用放得下，但一块连续申请失败」时，可试 `expandable_segments`。Profiler 的内存时间线用来定位是哪一个算子冲到峰值。

对上原因再改：激活大就减 micro-batch、做选择性重计算或 FlashAttention；状态大就上 ZeRO/FSDP；工作区大就换融合算子。`empty_cache` 只是把缓存还给驱动，下一步仍会按峰值再申请。`CUDA_LAUNCH_BLOCKING` 用来定位异步报错的算子，不解决占用。

容易漏的一点：只看 rank 0 的显存。OOM 往往发生在最重的那个 stage。

### 13. 请描述你如何设计一个支持混合精度训练的自动精度调整策略

**参考答案**

**结论**：能用 BF16 就用 BF16；只有 FP16 才做动态 loss scale。调精度的决定必须在 step 开始前对所有 rank 一致。

Ampere 及更新的 GPU 上，BF16 指数范围和 FP32 相同，通常不需要 loss scale。FP16 范围小，要用动态缩放：把损失放大后再反向，梯度里出现 inf/NaN 就丢掉这一步并缩小 scale，连续若干步稳定再放大。PyTorch `GradScaler` 长期默认大约是初始 scale \(2^{16}\)、放大倍数 2、缩小倍数 0.5、每 2000 个成功步尝试放大。这只是默认值，策略要看实际溢出率，而不是假设它适合所有模型。

无论哪种低精度，优化器主权重、动量和最后的归约都留在 FP32。自动混合精度按算子白名单把矩阵乘放到低精度，softmax、LayerNorm 这类归约留在 FP32，而不是把所有张量强转。

自动调整可以做成很简单的状态机：

1. 硬件支持 BF16 就从 BF16 开始，否则 FP16 加 `GradScaler`。
2. 每个优化器 step 只 unscale 一次、裁剪一次、`step` 一次。累积梯度时，每个 micro-batch 都缩放后再反向，不要每个 micro-batch 都更新 scale。
3. 记录溢出比例和梯度范数。某一类算子反复溢出，就把该类提升到 FP32。scale 已经缩到训练几乎不前进时，整步降回更高精度，而不是继续空跳。
4. 决定由 rank 0 按规则做出后广播，或者用完全确定的规则。各 rank 各判各的，模型会分叉。
5. 参数的 dtype 和它的优化器状态一起转换，不要在 step 中间改一半。

和短程 FP32 或稳定 BF16 的损失曲线对比，再看吞吐。只看快了多少，看不出精度已经漂了。

### 14. 手撕算法：实现一个分布式键值存储的简单一致性哈希（Consistent Hashing）算法

**参考答案**

**思路**：把哈希空间看成一个环。每个物理节点放 \(R\) 个虚拟节点，用稳定哈希落到环上；key 顺时针找到第一个虚拟节点，它的物理节点就是主副本。增删节点只影响该节点到前驱之间的那段 key。查找再往下走，跳过重复的物理节点，得到后续副本。

哈希要用进程间稳定的函数。Python 内置 `hash()` 每次启动盐值不同，不能用。MD5 这里只负责分布，不承担安全。虚拟节点数是均匀性和内存的折中，常见几十到几百，没有普适最优。有序数组上的查找是二分；插入要搬移元素。生产上可以把环换成平衡树，把单次增删降到 \(O(R \log V)\)。

这个实现只回答「key 在哪」。真正搬数据时，只有落在变更弧上的 key 需要迁移，飞行中的写要有交接协议。虚拟节点仍可能有局部不均，负载上限更严时要用带负载约束的一致性哈希。

**复杂度**：设虚拟节点总数 \(V = NR\)。查找 \(O(\log V)\)，空间 \(O(V)\)。下面的有序数组每插入一个虚拟节点要 \(O(V)\)，一个物理节点是 \(O(RV)\)。

```python
import bisect
import hashlib


class ConsistentHash:
    def __init__(self, replicas=128):
        if replicas < 1:
            raise ValueError("replicas must be >= 1")
        self.replicas = replicas
        self._ring = []  # 升序 (hash, node)
        self._nodes = set()

    @staticmethod
    def _hash(text):
        digest = hashlib.md5(text.encode("utf-8")).digest()
        return int.from_bytes(digest, "big")

    def add(self, node):
        if not node or node in self._nodes:
            return
        self._nodes.add(node)
        for i in range(self.replicas):
            point = (self._hash("%s#%d" % (node, i)), node)
            bisect.insort(self._ring, point)

    def remove(self, node):
        if node not in self._nodes:
            return
        self._nodes.remove(node)
        self._ring = [item for item in self._ring if item[1] != node]

    def get(self, key):
        if not self._ring:
            raise RuntimeError("no nodes")
        idx = bisect.bisect_left(self._ring, (self._hash(key), ""))
        if idx == len(self._ring):
            idx = 0
        return self._ring[idx][1]

    def get_n(self, key, n):
        if n < 1:
            raise ValueError("n must be >= 1")
        if len(self._nodes) < n:
            raise RuntimeError("not enough nodes")
        start = bisect.bisect_left(self._ring, (self._hash(key), ""))
        found = []
        seen = set()
        for step in range(len(self._ring)):
            node = self._ring[(start + step) % len(self._ring)][1]
            if node in seen:
                continue
            seen.add(node)
            found.append(node)
            if len(found) == n:
                return found
        return found


if __name__ == "__main__":
    ring = ConsistentHash(replicas=32)
    for node in ("A", "B", "C"):
        ring.add(node)
    keys = ["user-%d" % i for i in range(200)]
    owners = {key: ring.get(key) for key in keys}
    ring.add("D")
    for key, old in owners.items():
        now = ring.get(key)
        # 新增节点只接管原本落在它弧上的 key
        assert now == old or now == "D"
    assert any(ring.get(key) == "D" for key in keys)
    assert ring.get("user-0") == ring.get("user-0")
    replicas = ring.get_n("u1", 3)
    assert replicas[0] == ring.get("u1")
    assert len(set(replicas)) == 3
```

### 5. 请描述你如何设计一个可扩展的 AI 推理服务框架，支持动态批处理与模型热更新

**参考答案**

**结论**：服务层负责路由、配额和版本指针，引擎层按迭代组 batch，并按 KV 容量准入。热更新用新副本引流，不在一次解码中途换权重。

动态批处理是迭代级的，不是等满 N 个请求再一起跑。每个解码步，调度器把已经完成预填充的请求并进正在跑的集合，结束的请求拿走。预算用 token 数而不是请求个数，因为解码成本大致随当前 KV 增长，预填充则重得多。长提示拆成 chunked prefill，和短解码交错，避免一个长提示把整批解码卡住。不同模型不进同一个 batch。KV 用分页缓存；空闲块不够时请求排队或拒绝，而不是启动后 OOM。

横向扩展时，网关无状态，副本持有 KV。为了前缀缓存可以把同一会话粘在一个副本上，粘性太强又会打斜，路由按在途 token 和缓存命中权衡。自动扩缩看队列延迟和 token 吞吐。GPU 扩容要先拉权重、再预热、再捕获 CUDA Graph，比 Web 服务慢得多，所以要有有界队列，不能只靠扩容。

热更新把新版本做成另一组副本或另一份已加载权重。就绪检查包含一次预热请求。流量按比例切过去，已经开始的解码留在旧版本直到结束。旧版本停止接新请求后排空，再卸载。一张卡往往放不下两份完整权重，滚动计划要么有备用卡，要么接受切换期间并发下降。回滚是把指针指回仍在加载的旧版本。

容易漏的一点：重试只适用于还没开始生成的幂等请求。已经在解码的请求被网关再发一次，客户端会看到两段输出。

### 7. 请描述你如何设计一个面向大模型训练的异构计算资源调度系统

**参考答案**

**结论**：异构放在集群和队列层。进入同一个集合通信组的 GPU 保持同型号、同互联，不要把不同卡混成一组再指望同步训练。

节点按型号、显存、是否有 NVLink、是否有 RDMA、驱动分支打标签。作业申请的是一份拓扑模板，例如「8 卡 H100 且机内 NVLink」，不是一个叫 GPU 的整数。调度整组装箱：16 张卡应落在两台完整机器上，而不是十六个 1 卡碎片。张量并行的模板如果要求 NVLink，PCIe 机器在过滤阶段就排除。

CPU 预处理、数据打包不占 GPU 节点。驱动和大版本 CUDA 不兼容的机器分池，容器封不住宿主机驱动。公平调度在「型号」这个维度上做，同时允许可抢占作业借用空闲整机，回收前留检查点时间。

难点是碎片和公平的冲突：为了拓扑要把整机留住，利用率看起来会低；为了填满碎片又会拆散 NVLink。策略上，大训练只接受整机，小任务去 MIG 或 PCIe 池。系统要能量化一个计划的步时：算力、显存上限、互联带宽，不满足就拒绝，而不是调度成功后再发现训不动。

### 10. 请解释你如何从零开始学习一门新的基础设施技术（如 DPU、可编程交换机）

**答题思路**

选一条和现有集群故障有关的窄路径，用实验验证，不从采购一整套设备开始。

1. 先写明它在你的系统里解决什么：DPU 可能卸掉节点上的网络或存储开销，可编程交换机可能提供拥塞和路径上的可见性。对不上现有瓶颈就先不学完整栈。
2. 只选一个闭环：例如读懂一种拥塞控制在丢包时的行为，或在模拟器里跑通一段转发逻辑。材料用厂商的架构说明加一篇相关论文就够开始。
3. 用你已经有的指标验收，例如 GPU 节点的 CPU 占用、暂停帧、尾延迟。没有指标变化，就说明还没学到能用的程度。
4. 边界一起学：可编程数据面会增加谁来排障、版本怎么发布、出错时是否旁路回固定转发。
5. 讲给面试官的结构是「问题 → 最小实验 → 指标 → 我不打算把它用在哪」。DPU 和交换机都这样讲，不要展开成产品介绍。

### 11. 请描述你如何设计一个 AI 训练工作流的编排系统，支持条件分支与循环

**参考答案**

**结论**：条件分支和循环放在可恢复的编排器里；训练本身是带心跳的长任务。循环必须有上限，每轮产物用独立前缀。

控制面用能把进度落盘的系统，例如 Argo Workflows 或 Temporal 这一类。Airflow 更适合数据侧的调度，GPU 长任务通常只是它拉起的一个外部作业。编排器重启后要能从历史里知道循环进行到第几轮，而不是靠某个进程的内存。

每个步骤的输入输出是产物 URI 和一份小的结构化结果，不靠解析日志来决定下一步。评测分数低于阈值就走继续训练的分支，缺少这份结果就失败，不要默认当成通过。进入生产前可以加一个人工审批步骤。

循环要写最大次数、总时限和停止条件。第 \(i\) 轮的检查点写到带轮次和尝试次数的前缀，结束后再发布一个「当前有效」指针。这样重试不会和上一轮的写入互相覆盖。训练步骤和普通容器不同：它占一整组 GPU、时间按小时计。失败后应从检查点续跑，而不是无条件从头再交一次。编排器要接收心跳，心跳丢失才判定挂死。

并行搜索会打出很多分支，必须有并发上限和配额，否则一个循环就能占满集群。发布、删除旧检查点这类副作用要能重复执行。容易漏的一点：分支条件若放在训练脚本里用 `if` 自己调下一轮，控制器一旦重启就不知道跑到哪了。

### 12. 请解释你如何保证 AI 平台在高并发场景下的服务可用性与性能

**参考答案**

**结论**：控制面和 GPU 数据面拆开，过载变成有界队列里的积压；队列满了就拒绝，而不是把所有层一起拖死。

可用性上，接入层无状态、多副本。存活探针只说明进程还在，就绪探针失败才从负载均衡摘掉；不要因为下游变慢就把 Pod 全部重启。请求先落进有界队列再确认，尖峰变成积压。超过预算返回 429，并给出可重试的等待时间。重试只针对幂等调用，带抖动，下游已经超时或熔断时停止重试，否则重试会把局部故障放大成全站故障。

推理、训练提交、日志检索不要共用一个线程池或同一套数据库连接。检索和缓存可以降级，检查点写入和正在进行的推理尽量保持。训练作业的整组调度仍按可用区收拢；无状态的 API 可以跨可用区。发布用滚动或蓝绿，就绪之前包含预热。

性能上，推理走动态批处理和 KV 复用，日志不要同步写在请求路径里。控制面的列表和调度做增量，不要每个周期扫描全部历史作业。数据库按租户和状态建索引，队列用 `SKIP LOCKED` 或分区，避免所有工作者抢同一行。GPU 副本扩容要加载权重，水平扩容来不及接突发流量，所以准入和队列是性能设计的一部分。容量按到达率和延迟估计并发，延迟上去就先限流。

压测要包含依赖变慢，不只测全部成功的路径。容易漏的一点：把平均延迟当成容量。高并发先坏在尾延迟和队列锁上。

### 13. 请描述你如何看待 AI 基础设施未来的技术趋势（如 Serverless AI、AI Native Infrastructure）

**参考答案**

**结论**：Serverless 适合把推理的机器管理交出去；AI Native 是让调度、运行时和观测按模型负载来设计。大模型训练不会在一个 step 中间缩成零。

Serverless AI 让用户按请求或作业使用容量，空闲时缩到零，不必管节点。推理的突发流量适合这种形态。冷启动的大头是拉取权重和捕获 CUDA Graph，不是把容器拉起来。能做的是预热池、节点上的权重缓存，以及热模型不参与缩容。训练作业时间长，还要求一组 GPU 同时在场、状态在检查点里。平台可以做到用户不登录机器，这是免运维；它不能在通信进行到一半时把卡收走。公开的弹性训练也是先迁状态或先保住检查点，再改变资源。

AI Native 指基础设施从一开始就按模型来建：调度看拓扑和显存，不只看 CPU 核数；观测看 MFU、token 和恢复时间；故障是控制循环的正常输入，不是例外。编译、运行时和并行计划要知道注意力、MoE 和序列长度，而不是把模型当成不透明容器。

两者会在同一个控制面相遇：统一的配额、模型版本和观测，下面分出弹性推理和整组训练两条数据面。相关的具体方向还有预填充与解码分离、按 KV 缓存路由。容易漏的一点：把 Serverless 理解成所有 AI 负载的默认运行方式。训练要的是稳定的一组卡，推理要的是按 token 伸缩，目标函数不一样。

### 14. 手撕算法：实现一个简单的分布式事务两阶段提交（2PC）协议

**参考答案**

**思路**：协调者先问所有参与者能不能提交（prepare），全部同意才提交，任一拒绝或超时就中止。投票 YES 之前，参与者要把「已准备」写进日志；协调者把 commit 或 abort 写进日志之后，才能把决定发给别人。日志写在发送之前，崩溃后才知道该重放哪一种决定。

参与者处于 PREPARED 时不能自己改主意。协调者没恢复、决定未知，它就继续阻塞。这是 2PC 的固有问题。协调者重启后：日志里有 commit 就只重发 commit，有 abort 就重发 abort；只有 start、还没有决定，就按 abort 处理。超时只在还没做出决定时当成 NO。决定已经是 commit 之后，超时只能重发，不能改成 abort。

3PC 试图减少协调者崩溃时的阻塞，但分区下仍不正确，工程里很少用。跨服务更常见的是单库事务，或用补偿的 saga。Paxos/Raft 的多数派提交也不是 2PC。训练梯度同步走的是集合通信，不是两阶段提交；2PC 会出现在模型注册表和制品库这类必须一起成功的元数据上。

**复杂度**：正常路径两轮消息，加上两次落盘。下面用内存列表代表预写日志，真实系统在 `write` 返回前要 fsync，消息处理要能重复执行。

```python
class WAL:
    def __init__(self):
        self.records = []

    def write(self, record):
        # 真实系统在这里 fsync，返回后才算持久化
        self.records.append(record)


class Participant:
    def __init__(self, name, fail_prepare=False):
        self.name = name
        self.fail_prepare = fail_prepare
        self.log = WAL()
        self.state = {}

    def load(self):
        self.state = {}
        for kind, tx in self.log.records:
            if kind == "prepare" and self.state.get(tx) not in ("COMMITTED", "ABORTED"):
                self.state[tx] = "PREPARED"
            elif kind == "commit":
                self.state[tx] = "COMMITTED"
            elif kind == "abort":
                self.state[tx] = "ABORTED"

    def prepare(self, tx):
        if self.state.get(tx) == "ABORTED" or self.fail_prepare:
            self.abort(tx)
            return "NO"
        if self.state.get(tx) != "PREPARED":
            self.log.write(("prepare", tx))
            self.state[tx] = "PREPARED"
        return "YES"

    def commit(self, tx):
        if self.state.get(tx) == "ABORTED":
            raise RuntimeError("cannot commit an aborted tx")
        if self.state.get(tx) == "COMMITTED":
            return
        self.log.write(("commit", tx))
        self.state[tx] = "COMMITTED"

    def abort(self, tx):
        if self.state.get(tx) == "COMMITTED":
            raise RuntimeError("cannot abort a committed tx")
        if self.state.get(tx) == "ABORTED":
            return
        self.log.write(("abort", tx))
        self.state[tx] = "ABORTED"


class Coordinator:
    def __init__(self, participants):
        self.participants = list(participants)
        self.log = WAL()
        self.decision = {}

    def decision_of(self, tx):
        return self.decision.get(tx)

    def run(self, tx):
        self.log.write(("start", tx))
        votes = []
        for p in self.participants:
            try:
                votes.append(p.prepare(tx))
            except Exception:
                votes.append("NO")
        if self.participants and all(v == "YES" for v in votes):
            self.log.write(("commit", tx))  # 先落盘，再通知
            self.decision[tx] = "commit"
            for p in self.participants:
                p.commit(tx)
            return "commit"
        self.log.write(("abort", tx))
        self.decision[tx] = "abort"
        for p in self.participants:
            p.abort(tx)
        return "abort"

    def recover(self):
        decided = {}
        started = set()
        for kind, tx in self.log.records:
            if kind == "start":
                started.add(tx)
            elif kind in ("commit", "abort"):
                decided[tx] = kind
        for tx, kind in decided.items():
            self._drive(tx, kind)
        for tx in started - set(decided):
            self.log.write(("abort", tx))
            self._drive(tx, "abort")

    def _drive(self, tx, kind):
        self.decision[tx] = kind
        for p in self.participants:
            if kind == "commit":
                p.commit(tx)
            else:
                p.abort(tx)


if __name__ == "__main__":
    ok = [Participant("a"), Participant("b")]
    assert Coordinator(ok).run("tx1") == "commit"
    assert all(p.state["tx1"] == "COMMITTED" for p in ok)

    mixed = [Participant("a"), Participant("b", fail_prepare=True)]
    assert Coordinator(mixed).run("tx2") == "abort"
    assert all(p.state["tx2"] == "ABORTED" for p in mixed)

    # 协调者在写出 commit 前崩溃：恢复后按 abort，已准备的参与者解除阻塞
    prepared = [Participant("a"), Participant("b")]
    coord = Coordinator(prepared)
    coord.log.write(("start", "tx3"))
    for p in prepared:
        assert p.prepare("tx3") == "YES"
    assert coord.decision_of("tx3") is None  # 决定未知，参与者必须等待
    coord.recover()
    assert all(p.state["tx3"] == "ABORTED" for p in prepared)

    # commit 已落盘但通知丢失：恢复只能重发 commit
    again = [Participant("a"), Participant("b")]
    coord = Coordinator(again)
    coord.log.write(("start", "tx4"))
    coord.log.write(("commit", "tx4"))
    for p in again:
        p.prepare("tx4")
    coord.recover()
    assert all(p.state["tx4"] == "COMMITTED" for p in again)
```
