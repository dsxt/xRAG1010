# 阿里巴巴Java + AI Agent外包岗两轮技术面轻松拿下18k

> 根据面试截图整理。题干来自原帖，参考答案用于复习，不是候选人当时的口述。

## 面试感受

一面偏「你到底做没做过 AI 项目」，别拿 Demo 吹生产。RAG、Function Calling、Redis 存上下文这些要是只能背概念，面试官一追「召回不准怎么查」就露馅。

二面就不跟你玩八股了，直接看你能不能把 Agent 当系统做：多 Agent、工具治理、消息队列、成本控制、评估体系，全是落地坑。外包岗也不是纯 CRUD，阿里这边问得很实，答成「大模型加几个工具」会被嫌浅。

别怂，项目是真的就往深了讲；假项目就少吹，多聊工程兜底和边界处理，反而像老手。

## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「现在做什么 → 技术栈 → 一个项目钩子 → 和岗位的关系」讲。不要报期望薪资，也不要编年限和职级。

1. 第一句只说自己做 Java 后端多久、现在维护的是什么类型的系统。年限用自己的。
2. 技术栈按这个岗位排：Spring、MySQL、Redis、消息队列，然后才是你真写过的模型调用、检索或工具。只调通过聊天接口，就说调用；不要把本地 Demo 说成线上 Agent。
3. 项目只留一个钩子：谁在用、请求进来后你负责哪一段。难点留给下一问。
4. 收在匹配点：能把模型放进已有 Java 服务，并把超时、权限和失败收住。

讲完停住。框架名词不要在自我介绍里铺开。

### 2. 讲一个你做过的 Java 后端项目，重点说你负责哪块

**答题思路**

用自己真正写过的系统，两分钟内讲清楚边界。没有模型就讲 Java，不要为了岗位把 CRUD 改口成 Agent。

1. 背景两句：谁在用，核心对象是订单、工单还是内容。你的模块和同事的模块分开。
2. 按一条请求讲你负责的那段：入口、落哪张表、缓存或消息、失败怎么处理。只讲你能对上代码的部分。
3. 一个难点就够：一致性、并发、慢查询或超时。说明你怎么确认是这一层，改了什么，用什么现象验证。没有监控数字就讲现象，不要编 QPS。
4. 收在一个可追问的点：一张你最熟的表、一个缓存 key，或一段失败重试。面试官往下挖时不要换项目。

### 3. 项目里怎么接大模型 / AI Agent 的，用 Spring AI、LangChain4j 还是自己封装

**答题思路**

先承认实际用的那一种。三种都说「都用过」会在重试、流式和工具回传上露馅。没有接入过就说没有，再讲你准备接在哪一层，不要临时编一条链路。

1. 用一次真实请求串起来：入口在哪个服务、谁组装消息、谁执行工具、结果写回哪里。你写的和框架代劳的分开。
2. 选型理由绑团队现状，不要背官网。被追问三种接法时，按下面的差别讲。
3. Spring AI 适合已经是 Spring Boot 的服务：`ChatClient` 统一模型，Advisor 链插入记忆、检索和日志，`@Tool` / `ToolCallback` 注册工具，嵌入和向量库也有抽象。模型厂商可以换，但工具循环的步数、审计和鉴权仍是你的代码。
4. LangChain4j 适合想少写样板：`AiServices` 把 Java 接口代理成对话，`@Tool` 挂方法，`ChatMemory`、`EmbeddingStore`、`ContentRetriever` 比较全。要能讲出代理背后消息怎么拼、工具结果怎么回到下一次调用。
5. 自己封装就是用 HTTP 客户端打厂商的对话加工具接口，自己写循环、schema 校验和追踪。协议最透明，记忆、检索和重试都得自己做。工具网关本身是核心，或不想绑框架时，这条更合适。
6. 可以混用：对话循环用框架，工具执行走自己的网关。无论哪条，都要讲清三件事：流式输出时工具参数是一段一段到的，拼完再解析；框架自带记忆多半在进程内，重启就丢，生产要落到 Redis 或数据库；模型只提出调用，超时、权限和幂等在应用侧。

### 4. Agent、Workflow、Tool 这三个东西你是怎么理解的

**参考答案**

结论：Agent 自己决定下一步，Workflow 按预定分支执行，Tool 是两者都能调用的一项带契约的能力。

Agent 把模型放在循环里：看目标和当前观察，决定直接回答还是调用工具，再把结果写回上下文。路径不固定，适合意图多变的对话，也因此难测、难审计。Workflow 的分支写在代码或状态图里，模型只是其中的节点，超时、重试和回滚可以按步骤做。Tool 是契约：名字、用途、参数 schema，真正执行的是业务代码，不是模型。

生产里常用 Workflow 做外层，只把无法事先写死的那段交给 Agent，并由外层裁剪可用工具。三个词不要答成「Agent 就是自动工作流」。漏掉的一点是：Tool 没有权限和幂等时，Agent 的自由就是误调用。

### 5. Function Calling 完整流程是什么，模型怎么把自然语言变成结构化参数

**参考答案**

结论：模型只根据工具 schema 生成调用参数，不执行工具；应用校验并执行后，把结果放回对话，模型再决定是否继续。

1. 注册工具：名字、用途说明、参数的 JSON Schema。说明要写清何时该调用、每个字段是什么，模型靠这些决定填什么，不是另有一个实体抽取服务。
2. 请求带上历史消息和工具列表。有的接口还可以指定必须调用、禁止调用或自动决定。
3. 模型输出一个或多个 `tool_call`：调用 id、工具名、`arguments`。参数一般是一段 JSON 文本，由模型在 schema 约束下直接生成。应用负责反序列化。
4. 应用做 schema 校验、权限和业务规则。不合法就把错误退回模型，并限制修正次数。
5. 执行工具。超时、下游错误都变成结构化结果，不要变成空字符串。
6. 按 `tool_call_id` 把结果以 tool 消息追加回去。并行调用时，每一个都要有对应结果。
7. 模型继续生成，直到给出最终文本，或达到步数上限。

`arguments` 经常不是合法 JSON，枚举也会编。相同参数的重复调用要靠幂等键挡住。工具原文没有长度限制地塞回上下文，下一轮就会超窗。

### 6. RAG 全流程讲一下，文档切片、向量化、检索、重排、生成分别怎么做

**参考答案**

结论：先把文档切成可引用的片段并向量化，检索时先宽召回再重排，生成时只能依据拿回来的片段。

- 切片：按标题、段落等结构切，片段之间留重叠，避免一句话被切断。太长会掺进无关句，太短会把完整事实拆散。长度用评测调，没有放之四海的默认值。
- 向量化：文档和查询必须用同一个嵌入模型，并使用相同的归一化方式。向量和原文、文档 id、权限等元数据一起入库。
- 检索：查询可以先改写再嵌入，按近邻取回一批，并用元数据滤掉无权文档。专有名词再补一路关键词检索。这一步要的是把正确片段召回，不追求顺序已经完美。
- 重排：对这一批候选用交叉编码器或重排模型再排序，只留前面几条进提示词。
- 生成：提示词带上片段和来源 id，依据不足就拒答。回答里的引用必须来自这几条，不能来自模型补写。

索引模型和查询模型不一致时，后面每一步都在错的集合上优化。评测如果只看最终回答，就无法知道是哪一层丢的。

### 7. MySQL 索引为什么用 B+ 树，联合索引最左匹配怎么理解

**参考答案**

结论：InnoDB 的索引是 B+ 树，为了用很少的磁盘读做等值和范围扫描；联合索引只能从左起连续使用等值前缀。

非叶子节点只放键和指针，扇出大，树通常只有几层。聚簇索引的叶子存整行，叶子之间有链表，范围扫描沿着叶子走。二级索引的叶子存主键，查完整行还要再回表。`SHOW INDEX` 的类型写着 `BTREE`，实现仍是 B+ 树，不是非叶子也存整行的 B 树。二叉查找树太高，随机 IO 多。哈希只能等值，不能做范围和排序；InnoDB 的自适应哈希是内存里的热点加速，不是磁盘索引。

联合索引 `(a, b, c)` 按 a、b、c 依次排序。`a`、`a AND b`、`a AND b AND c` 都能用来定位。等值条件在 SQL 里的书写顺序无所谓，优化器会重排。范围条件后面的列不能再用来缩小扫描区间，例如 `a > 1 AND b = 1` 只能用 a 划范围。`b = 1` 单独用不上这个索引；MySQL 8.0 的索引跳跃扫描只在前导列取值很少时才可能被选中，不能当成一般规则。缺了中间列时，后面的列最多做索引条件下推，在回表前过滤，不能当成已经用了整棵联合索引。字符串前缀 `LIKE 'ab%'` 可以用，`LIKE '%ab'` 不行。

### 8. Redis 用来做 Agent 会话上下文存储时，key 怎么设计，过期策略怎么定

**参考答案**

结论：Redis 只放当前会话的热窗口，按会话拆 key，用滑动过期；要审计的原文另落数据库或日志。

同一会话拆开，避免一个大字符串无法裁剪：

- `agent:sess:{sid}:meta`，Hash，放用户、槽位、摘要版本。
- `agent:sess:{sid}:msgs`，List，只留最近若干轮。
- `agent:sess:{sid}:sum`，String，放滚动摘要。

`{sid}` 是集群的 hash tag，需要用脚本同时改这几个 key 时才放在一起。工具返回的大原文不要进 List，只留 id 和短观察。

过期用滑动 TTL：用户每次发消息就续期，时长按一次咨询允许多久不说话来定，不要背一个固定分钟数。再加一个绝对最长寿命，避免永久续命。到期前把摘要和必须保留的工具结果写出去。内存淘汰只作为保护，用 `volatile-lru` 这类只清理带过期时间的 key。会话寿命靠 TTL，不要靠 `allkeys-lru` 碰运气；缓存丢了最多从摘要恢复，不能把 Redis 当账本。

### 9. 线程池核心参数说一下，Agent 并发调模型时线程池怎么配

**参考答案**

结论：七个参数决定「先铺核心线程，再入队，队列满了才扩到最大，再满就拒绝」。调模型是慢 IO，池子大小对齐供应商的在途配额，而不是 CPU 核数。

`ThreadPoolExecutor` 的参数是核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。核心线程默认不因为空闲退出，超过核心数的线程空闲超过存活时间才退出。提交时，工作线程还不到核心数就新建线程；否则入队；队列满了且还没到最大线程数就再新建；否则拒绝。默认 `AbortPolicy` 抛异常。`CallerRunsPolicy` 让提交方自己跑，形成反压，但可能占满 Web 容器线程。无界队列时最大线程数基本不会生效，任务会一直堆到内存出问题。

模型调用每次要数秒，还受厂商并发和每分钟 token 限制。队列必须有界且短，最大在途数用信号量卡在配额上；线程开得比配额多，只是在本地排队。模型调用、工具 HTTP、Kafka 消费分开限流，避免慢工具占住模型许可。超时放在 HTTP 客户端上，到点就取消这次调用。Java 21 可以用虚拟线程承担阻塞 IO，但仍要用信号量限制在途请求，否则会把厂商打满。拒绝要变成可感知的降级或限流，不要静默丢掉用户请求。追踪 id 要传到工作线程里。

### 10. Kafka 在 Agent 系统里能干什么，工具调用日志、审计、异步任务怎么落地

**参考答案**

结论：用户正在等的短工具同步调用；Kafka 负责审计、可回放的日志，以及索引、摘要这类可以晚一点的任务。

不要把 Kafka 放进同步工具循环里当 RPC。一旦消费滞后，用户侧的延迟和失败都不可控。适合的是：每次工具调用发一条审计事件，长任务和文档索引异步执行，评测、摘要跟在线请求拆开。

落地时按用途分主题，例如审计一条、异步任务一条。消息键用 `sessionId`，保证同一会话有序。消息体带 traceId、幂等键、工具名、状态、耗时，大结果放对象存储，消息里只留引用；个人信息先脱敏。消费端按至少一次来设计，靠幂等键去重，处理失败进死信，不能卡死分区。在线请求把审计发送和工具执行分开，发送失败要有补偿，但不能因为审计写不进去就假装工具没调用过。

### 11. 缓存和数据库一致性怎么保证，写 DB 后删缓存失败怎么办

**参考答案**

结论：缓存旁路读是最终一致，不是强一致。常规是先提交数据库，再删缓存；删除失败要有可靠补删，并用短 TTL 收口。

读的时候先读缓存，没有再读库并回填。写的时候改数据库，成功后删除缓存，而不是顺便把缓存更新成新值。并发更新时，后写进缓存的可能是旧值，删除让下一次读重新装载，窗口更小。先删缓存再改库，中间的读会把旧值又写回去，窗口更大。

删缓存失败时，库已是新的、缓存仍是旧的。业务更新和一条待删记录要放在同一个事务里提交，不能等删除失败后再补进已经结束的事务。提交之后做有限次删除，仍失败就由发件箱异步重试并告警。binlog 订阅可以再失效一次，应用进程挂了也能做。TTL 只负责兜住没补到的窗口。

还有一个竞态：线程 A 读到旧行，线程 B 提交新行并删掉缓存，线程 A 再把旧行写回已经空了的缓存。空 key 上比较版本挡不住这次写入。读路径回填要和这次加载互斥，或者不在读路径回填，只让写路径和 binlog 按版本写缓存。延迟双删能清掉刚写回的旧值，但睡眠时间不好定，只作辅助。要读己之写，就绕开缓存读主库，不要宣称删缓存等于强一致。

### 12. 场景题：AI 客服查订单，用户说「我昨天买的那个东西到哪了」，系统怎么从多轮对话里抽出用户身份、订单时间和意图

**参考答案**

结论：身份以登录态为准，时间按对话发生时的时区解析成区间，意图用槽位补齐；「那个东西」不够就先查候选订单，只用工具结果回答。

1. 意图定为查订单物流。用一次结构化输出填槽，不要从闲聊句子里用正则硬抠，也不要让模型直接写一句「已经到了」。
2. 身份取已认证的用户 id。模型不能自己编用户。未登录就先核验订单号或手机号，核验前不调订单工具。
3. 「昨天」按用户时区换成左闭右开的日期区间，并保留原话。下一轮不能只剩模型改写过的句子，否则相对时间会漂。
4. 「那个东西」是缺失槽。用用户 id 加时间范围查订单：一条就复述商品名请用户确认，多条列出候选，没有就扩大时间或追问订单号。
5. 槽位放在会话里：用户、时间范围、商品线索、订单号、意图、还缺什么。每轮合并，不把整段历史重新猜一遍。代词默认指向上一轮已经确认的订单。
6. 槽齐了再调物流工具。回复只转述返回的状态和单号。工具没有的单号不能补。别人的订单号即使被抽出来，工具层也要按当前用户拒绝。

### 13. 场景题：Agent 调外部工具超时、返回格式不对、重复调用，你怎么兜底

**参考答案**

结论：这三件事都在工具网关处理。模型只看见结构化的成功或失败，不能自己重试有副作用的调用。

超时要把连接和读取分开。只对幂等、且错误是超时、429 或 5xx 的调用做有限次退避。下单、退款、发消息先用幂等键查上次的状态，不盲目重放。连续失败就熔断这条依赖。对用户说明这项查不到，不要把超时当成空结果交回去，模型会补一个看起来合理的答案。整次 Agent 另有总时限，避免每一步都把超时叠满。

格式方面，调用前校验参数 schema，失败把原因退回模型，并限制修正次数。工具输出也要校验和截断，非法输出当失败，不能当事实写进上下文。

重复调用用幂等键挡住：会话、步骤、工具名和规范化参数。短时间内命中就返回上次结果。循环里发现参数完全相同的调用，停止并复用上一次观察。有副作用的工具还要人工确认，步数有上限。重试如果放在模型自己的循环里，非幂等副作用会被放大。

### 14. 你平时用哪些 AI 编程工具，Cursor、通义灵码、Copilot 之类，别光说好用，说清楚帮你提效在哪

**答题思路**

只讲你每天真开着的一个，题目里这几个不必都报。没怎么用就说主要靠自己读代码，不要编一段使用体验。

1. 用一件具体的事讲，不要说「写代码更快」。例如读一个陌生模块、补失败路径的测试、顺着调用链改一个接口。
2. 按「你给了什么上下文 → 它生成了什么 → 你怎么验证」讲。验证是编译、单测和自己读 diff。没有验证的生成不算提效。
3. 主动说错在哪：业务约束、并发、权限、幂等经常错。你是改提示重新生成，还是直接自己写。能举一个你拒绝过的补丁最好。
4. 收在边界：IDE 里生成的工具 schema 或样板，不能代替线上的超时、鉴权和审计。

### 15. 手撕算法：给你一个字符串，找出最长不含有重复字符的子串长度

**参考答案**

结论：滑动窗口。右指针逐个纳入字符，左指针跳到重复字符的下一位。时间 O(n)，额外空间 O(min(n, 字符集大小))。

用哈希表记录每个字符上次出现的下标。右指针扫到 `c` 时，如果它上次出现的位置落在当前窗口里，左边界就改到那个位置的右边。然后更新 `c` 的位置，并用 `right - left + 1` 刷新答案。每个下标最多进出窗口一次。

`abcabcbb` 的最长段是 `abc`，长度为 3。空串是 0，全相同字符是 1。窗口外的旧下标不能把左边界往回拉，所以要判断「上次位置是否还在窗口内」。字符集有限时可以把表换成数组。Java 的 `char` 是 UTF-16 码元，一个 emoji 可能占两个 `char`；题目若要求按码点计，要用 `codePointAt` 移动窗口。

```java
public int lengthOfLongestSubstring(String s) {
    if (s == null || s.isEmpty()) {
        return 0;
    }
    java.util.Map<Character, Integer> last = new java.util.HashMap<>();
    int left = 0;
    int best = 0;
    for (int right = 0; right < s.length(); right++) {
        char c = s.charAt(right);
        Integer prev = last.get(c);
        if (prev != null && prev >= left) {
            left = prev + 1;
        }
        last.put(c, right);
        best = Math.max(best, right - left + 1);
    }
    return best;
}
```

### 2. 挑一个最像生产项目的 AI Agent 项目，从需求、架构、上线、踩坑讲一遍

**答题思路**

2. 架构按请求路径四段：接入和鉴权、编排、模型、工具或检索。每段只点一个你写过的组件，以及失败时返回什么。
3. 上线讲灰度、回滚，以及日志里能不能对上一次工具调用。这些还没有，就说还在试运行，并说明你准备补哪一条。

### 3. 多 Agent 怎么编排，Router Agent、检索 Agent、执行 Agent 之间怎么传上下文

**参考答案**

结论：外层用固定编排管预算和停止条件。Router 只分流，检索只交证据，执行 Agent 只拿本意图的工具。上下文传结构化字段，不传整段聊天。

Router 根据意图把请求交给一个专家，而不是每个 Agent 都看见全部工具。分类可以用规则或小模型。检索 Agent 返回片段和来源 id，不生成对用户的最终答复，避免下一跳把来源说丢。执行 Agent 拿到的工具表在下发前已经按权限裁过。

移交的信封里放：用户目标、已确认槽位、权限、检索证据、当前步骤、工具观察、剩余步数。对话原文留在会话存储里，用 id 引用。后一个 Agent 只读自己需要的字段。父级 trace 下面每个 Agent 一个 span，费用记在父任务上。

难点是传话失真和互相踢皮球。移交次数和总步数要有上限，超了就停，并把已有依据返回。意图很少时，一个 Agent 加严格的工具名单就够，拆三个只会增加延迟和不一致。

### 4. Agent 记忆怎么设计，短期记忆、长期记忆、会话摘要、向量召回分别放哪

**参考答案**

结论：短期记忆放 Redis 的热窗口，长期事实放数据库，摘要用来压缩旧对话，向量库只召回相关的历史片段。四者不要合成一个「把所有聊天记录都塞进提示词」。

短期记忆是这一轮还要用的原文和槽位，放 Redis，设条数、字节和滑动过期，直接进当前提示词。会话摘要在原文超出预算时，把较早的轮次压成一段，替换进提示词，同时仍保留最后几轮原文。订单号、已确认的决定这类槽位单独存结构化字段，不能只活在摘要句子里，摘要是有损的。

长期记忆是跨会话还要用的偏好和资料，放 MySQL，带来源和时间。写入要有规则：用户确认过的，或从可靠工具结果提取的，才写入。用户随口说的、以及密码和密钥，不写入。新事实覆盖旧事实时保留时间，并允许用户删除。

向量召回放的是过去工单、对话片段这类要按语义找的内容，必须带 `userId` 过滤，不能和公司知识库混在一个无过滤的集合里。召回结果当「可能相关的材料」，不直接当已经核实的事实。热窗口、摘要、档案、向量各走各的存储，合规要留的全量原文进冷存储，不进 Redis。

### 5. ReAct 和 Plan-and-Execute 区别，什么任务不适合让 Agent 自由发挥

**参考答案**

结论：ReAct 每一步都根据观察重新决定；Plan-and-Execute 先出计划再执行，失败才重规划。步骤清楚、代价高或不可逆的任务不要让模型自由发挥。

ReAct 把推理和行动穿插起来：思考、调用、看结果、再决定。下一步取决于工具返回时适合用它。代价是模型调用多，容易循环，路径不稳定，也难事先审。

Plan-and-Execute 由规划器先产生步骤，执行器按步调用，某步失败再局部重排。计划稳定时调用更少，也便于把计划给人看、按步骤做权限检查。环境变化快时计划会过时，所以要规定什么情况必须重规划，不能死走完。

不适合自由发挥的包括：退款、改数据、对外发消息，这些走固定流程加人工确认；金额和库存用代码算；合规话术用检索加模板；高并发的简单问答不必进循环。模型可以提议动作，提交由服务端按白名单执行。如果计划的每一步仍是一个不受限制的 ReAct，计划层就没有约束。

### 6. MCP 和 Function Calling 是什么关系，为什么生产里不能只靠 Function Calling

**参考答案**

结论：Function Calling 是模型的进出协议，MCP 是工具服务的接入协议。生产里模型仍然通过 Function Calling 提出调用，但工具的发现、权限和发布不能只靠把 schema 塞进提示词。

Function Calling（各家叫 tool use 也一样）做的是：请求里带上工具 schema，模型返回工具名和参数，应用执行后再把结果送回。工具实现和这次请求写在同一个应用里。

MCP 用 JSON-RPC 把工具从应用进程里拆出去。独立的服务声明自己有哪些工具、资源和可复用提示，宿主通过本地标准输入输出或远程 HTTP 去发现和调用。宿主把 MCP 的工具列表转成模型的 tools 参数，再把模型返回的调用映射成 MCP 的 `tools/call`。MCP 不会替模型生成参数，也不等于已经鉴权。

只靠 Function Calling 时，工具名单和发版绑在应用上，提示词会随着工具变长，也没有统一的权限、限流、审计和网络隔离。每个接入方都要重写一遍对接。生产需要一层工具网关：按用户裁剪可见工具，校验参数，记录调用。MCP 适合把这层做成可复用的服务；即便不用 MCP，也不能让模型看见什么就调用什么。

### 7. RAG 召回不准导致幻觉，你怎么定位是切片问题、Embedding 问题、检索问题还是重排问题

**参考答案**

结论：准备带期望文档 id 的坏例，从切片到生成逐层看金标还在不在。一次只改一层。

1. 切片：原文里答案是完整的，但没有任何一个片段同时包含这个事实，或句子在边界被切断。去看相邻片段。改结构切分、重叠，或用小片段召回、把父片段送给模型。
2. Embedding：片段是完整的，关键词能命中，向量近邻却是别的主题；或者查询和文档不是同一个模型、归一化不一致。先核对模型和归一化，再考虑领域嵌入或混合检索。这时候调重排没有用，因为正确片段根本不在近邻里。
3. 检索：向量其实很近，但被权限过滤、top-k 太小或近似索引的探测宽度挡住，也可能是问句和文档用词差太远。查过滤条件、HNSW 一类索引的探测参数，以及查询改写。关键词有、过滤后没有，就是检索条件问题。
4. 重排：金标还在召回的那一批里，重排后掉出了送给模型的几条。问题在重排模型和特征，不在库。
5. 证据已经在最终提示词里，模型仍然编造，那是生成约束问题。再改索引对不上。

每一层留下查询、改写、文档 id 和分数。没有这些日志，就只能凭感觉改提示词。

### 8. Agent 工具调用怎么做成统一注册、统一入参校验、统一权限控制和统一埋点

**参考答案**

结论：所有工具经过同一个网关。注册表是唯一事实来源，模型手里的 schema、校验、权限和埋点都从这里来。

注册项包括名字、版本、用途、参数 schema、超时、是否幂等、副作用级别、所需权限和负责人。启动时从代码或 MCP 的工具列表装入。每个意图只能拿到策略过滤后的子集，不能把内部工具一并放进提示词再指望模型不去点。

调用前在网关做 JSON Schema 校验，拒绝多余字段和非法枚举。订单是否属于当前用户，要在工具实现里再查一次，schema 看不出来。敏感操作另要确认，不因为模型填对了参数就执行。

埋点和审计放在同一层拦截器：traceId、工具名、版本、耗时、状态、参数哈希。原文按合规要求脱敏后另存。成功率、超时率和延迟都从这里出，不要每个工具自己打一套日志。

发给模型的 schema 必须和注册表同一版本。两边漂移时，模型会按旧参数调用，校验全失败，看起来像模型变笨了。

### 9. Redis 热点 key、大 key、上下文堆积怎么处理

**参考答案**

结论：先分清是单个 key 太热、单个 value 太大，还是会话只增不减。用户会话天然按 id 分散；热点和大 key 多半来自全局配置和无限追加的上下文。

热点 key 在集群里只属于一个主分片，默认读写都打到这个主节点。从节点可以分担读，但写和复制仍在主节点，要求强一致的读也绕不开它。系统提示、模型配置、全局计数器如果打成一个 key，就会热在这一分片上。读多写少的放进程内短缓存，Redis 仍是源。必须共享的计数拆成多个 key 再汇总。不要把所有人的上下文写进同一个 List。

大 key 是一个字符串过大，或集合元素过多。危害是慢查询、删除阻塞、迁移和内存不均。`UNLINK` 只能缓解删除，不解决读取。会话 List 要截断到固定窗口，大的工具结果存对象存储，只留 id。按天拆 key 可以控制体积。上线前扫描大 key，请求路径上禁止 `KEYS` 和一次取出整个大集合。

上下文堆积是 Agent 把每轮工具原文都追加进去。写入前就限制条数和字节，旧轮次换成摘要，并设置过期。等 key 已经变大再删，慢请求已经发生了。监控单会话的内存，而不是只看实例总内存。

### 10. MySQL 订单/会话表数据量大了，怎么分库分表，Agent 历史消息查询怎么不把主库打满

**参考答案**

结论：按线上真正的查询路径选分片键。Agent 的在线对话只读热数据，历史查询离开事务主库。

订单如果总是按买家查，就按买家 id 分片。只拿订单号来查时，把分片键编进订单号，或维护一张订单号到分片的路由，避免扫全库。会话消息按 `sessionId` 分片，在分片内按时间追加。用户维度的「这个人所有会话」另建按用户 id 分片的索引表，不在消息大表上做跨分片查询。不要按状态分片，热点会集中。分页用时间和 id 续页，不用大偏移。

在线 Agent 只读 Redis 里的最近若干轮。更早的记录走从库，或异步同步到专门的历史库、搜索引擎，工具默认带条数上限。主库保留会话状态即可，全文检索和导出不要打到事务库。给历史查询单独的覆盖索引，并限制这个工具的并发。没有上限的「把整个会话 SELECT 出来交给模型」，分库分表也挡不住。

### 11. RocketMQ 或 Kafka 消息积压了，Agent 异步任务怎么快速恢复，怎么保证工具调用幂等

**参考答案**

结论：先找到积压是消费慢、下游超时还是生产突增。恢复时优先保住用户正在等的任务，并且默认回放会重复，工具必须认幂等键。

下游模型配额已经打满时，加消费者只会放大失败。摘要、评测和在途任务分成不同主题或优先级，先把低优先级停掉或降并发。Kafka 的并行度受分区数限制；一条慢消息会堵住整个分区，处理要有超时，失败进死信再提交位点。RocketMQ 可以在集群消费下加机器和消费线程，超过重试次数的消息进死信，先恢复主流，再单独回放死信。重置消费位点只在确认下游能重放时做。

幂等键用会话、步骤、工具和参数哈希，或直接用消息 id。执行前写入带唯一约束的记录，状态从处理中到成功，并保存结果。重复投递读到已成功就返回上次结果。记录停在处理中又超时的，先按这把钥匙向工具查询，不能直接再执行。创建类工具自己也要认这把钥匙，只在消费者里去重不够。没有查询接口的非幂等操作，失败后交给人工，不自动重试。Kafka 的事务不能让外部 HTTP 工具只执行一次。

### 12. 场景题：100 个用户并发问 Agent，每个问题都要调模型 + 查数据库 + 调 3 个工具，怎么设计限流、熔断、降级和 Token 成本控制

**参考答案**

结论：100 个在途会话的上限是模型和工具的配额，不是线程池能开多大。限流、熔断、降级和预算都按依赖拆开。

入口用信号量限制在途 Agent 数，对齐模型允许的并发。超过的短队列或直接限流，不放进无界线程池。再拆三层配额：全局、单用户、单工具。一个用户不能占满全部额度。100 个会话如果同时打模型和 3 个工具，下游就是数百个在途调用；工具能并行时峰值更高，所以每个依赖有自己的超时和舱壁，数据库变慢不能占住模型许可。

熔断按模型和每个工具分开，看失败率和慢调用。可选工具熔断后跳过并说明；必选工具熔断就整单降级，把明确的失败交给用户，不要喂给模型一个空结果。

降级顺序事先写好：路由改规则或小模型，重复的问答走缓存，重排超时就用向量顺序，摘要这类非关键任务直接丢弃。对用户说哪一项查不到。

成本按单次步数、单次 token 和用户日预算卡死。稳定的系统提示走上下文缓存，工具 schema 只带本意图需要的。重试单独算预算，因为每一次重试都在计费。日志按阶段记 token，才能看出是循环、重排还是最终生成在烧钱。

### 13. 场景题：甲方要求 Agent 回答必须可溯源、可审计、不能乱编，你怎么做护栏和人工兜底

**参考答案**

结论：事实只来自这次的工具结果和检索证据，回答层不能新增事实。审计留下依据，对不上就转人工。

生成前把证据整理成带 id 的材料，提示词规定没有材料就拒答。模型输出分成事实字段和话术。事实字段用程序核对：单号、状态、金额必须出现在工具返回里，引用的文档 id 必须在本次检索结果里。核对失败就改口为查不到，不用第二次自由生成去圆。

输入侧处理越权和提示注入，包括用户输入和检索内容里的指令。工具名单按意图收窄，订单参数在网关绑当前用户。高风险动作不进自动执行。

审计记录请求、模型版本、提示词哈希、每次工具的参数和原始结果、最终输出、引用和拦截原因，写入追加式日志。事后要能重放依据，而不是只剩一句话。只审计最终回答，对不上工具原文。

人工兜底的触发写清楚：检索分数过低、涉及退款投诉和承诺、用户要求人工、事实核对失败。转接时把证据包交给人工队列，转接期间模型不再补答案。

### 14. 你怎么做 Agent 效果评估，任务完成率、工具调用成功率、首响延迟、Bad Case 回流怎么搞

**参考答案**

结论：用任务有没有办成来评估，不要用回答像不像。线下回归和线上按意图切片是两套数。

任务完成率建在标注集上：订单号对不对、该调的工具调了没有、该拒答的是否拒了。话术流畅但办错，算失败。

工具调用成功率要拆开：选错工具、参数不合法、下游 5xx、超时。合成一个百分比就无法改。重复调用有副作用的，即使最后结果碰巧对，也算坏轨迹。

首响延迟是用户看到第一句有效内容的时间，含排队，不只是模型内部耗时。同时看端到端。只报平均会掩盖排队。

Bad Case 来自点踩、转人工、核对失败和检索分数过低。进复核队列，标上是切片、工具、提示词还是模型的问题，放进回归集。改任何一层之前先跑这批。指标按意图拆，总完成率高不代表物流或退款这一类是好的。

另一个大模型可以辅助抽检，不能当唯一裁判，它会把说得顺判成成功。关键字段用规则和工具返回比对。

### 15. 最近在学什么 AI 相关东西，LangGraph、MCP、RAG 重排、向量库、模型微调这些有没有真动手

**答题思路**

只声称你能演示的一项。名单里其余的用一句话讲边界。没训过模型就直接说没训过，不要把读过文档说成动手做过。

1. 先讲你做成的那个可运行的东西：输入是什么、跑到了哪一步、你怎么判断它是好是坏。
2. 再讲一个具体失败：例如状态没保存导致重跑、工具没有鉴权、重排把金标挤掉、过滤条件写错召回为 0。没有失败细节，面试官会认为只是看过名词。
3. 被追问到某一项时，讲到这个深度就停：
   - LangGraph：状态图里有哪些节点，检查点能不能恢复，人工打断停在哪。没跑过就不要讲持久化实现。
   - MCP：你是否把一个工具放到独立进程，宿主如何发现并调用，谁做鉴权。
   - 重排：同一批坏例上，金标文档在重排前和重排后还在不在。
   - 向量库：元数据过滤和召回检查。不要只报一个产品名。
   - 微调：数据从哪来、基座是什么、和只做 RAG 比过没有。没训过就说为什么先用检索。
4. 收在你还补不上的一个缺口，和这个岗位相关即可。不要顺势报一个学习清单。

### 16. 手撕算法：用 Java 写一个 LRU Cache，要求 get 和 put 都是 O(1)

**参考答案**

结论：哈希表定位节点，双向链表维护使用顺序，最近使用的放在表头，淘汰表尾。`get` 和 `put` 都是 O(1)，空间 O(capacity)。

哈希表的值是链表节点，做到按 key 直接找到节点。链表用哑头和哑尾，避免空指针。`get` 命中后把节点移到表头。`put` 已存在就改值并移到表头，不增加容量；不存在就插入表头，超过容量时删掉表尾，并同时从哈希表移除。只删一边会留下悬空节点，下一次淘汰就错。

这个结构不是线程安全的。并发场景不要自己加一把大锁了事，可以用现成的缓存组件。JDK 里 `LinkedHashMap` 把 `accessOrder` 设为 true，并在 `removeEldestEntry` 里按 `size() > capacity` 淘汰，复杂度相同。`accessOrder` 为 false 时，`get` 不会更新顺序，那不是 LRU。面试里手写链表，是为了把「更新顺序」和「淘汰」显式写出来。

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);
    private final Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node node = map.get(key);
        if (node == null) {
            return -1;
        }
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        Node node = map.get(key);
        if (node != null) {
            node.value = value;
            moveToHead(node);
            return;
        }
        Node created = new Node(key, value);
        map.put(key, created);
        addAfterHead(created);
        if (map.size() > capacity) {
            Node lru = tail.prev;
            remove(lru);
            map.remove(lru.key);
        }
    }

    private void moveToHead(Node node) {
        remove(node);
        addAfterHead(node);
    }

    private void addAfterHead(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private static final class Node {
        private final int key;
        private int value;
        private Node prev;
        private Node next;

        private Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }
}
```
