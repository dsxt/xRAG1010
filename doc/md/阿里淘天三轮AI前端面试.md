## 一面

### 1. 自我介绍

**答题思路**

控制在 1 到 2 分钟，按「我是谁 → 做过什么 → 为什么匹配」讲。

1. 一句话定位：年限、前端技术栈，以及有没有做过模型对接、流式对话或 Agent 界面。
2. 只展开一个和 AI 相关的项目：用户看到什么，你负责页面、协议还是结果渲染。结果只用自己的数字。
3. 点出和这个岗位的交点：流式输出、页面性能，或可组合的模块化页面。
4. 收在你最熟的一段实现上，方便面试官接着问 SSE、状态或性能。

### 2. 项目介绍

**答题思路**

挑一个你真正负责过的项目，按业务目标、你的边界、一条请求的链路来讲。没做的层直接说没做。

1. 业务目标：用户要完成对话、搭一个页面，还是看一段生成结果。
2. 你的边界：页面、流式协议、状态、模块协议，谁提供模型接口。
3. 按时间讲一条请求：输入 → 请求 → 流式渲染 → 中断或结束 → 异常。做过流式输出时，把取消和半截内容怎么留在界面上放进这条链路。
4. 一个你处理过的问题：现象、原因、改了什么、怎么确认好了。没有的指标不要编。
5. 准备追问：为什么用这种传输、状态放在哪、模块或列表变多时怎么保持流畅。

### 3. 前端如何与大模型对接？有哪些方式?

**参考答案**

页面不持有厂商密钥，只请求自己的后端。后端做鉴权、限流和提示词组装，再去调模型。

对接方式按返回形态分：

- 非流式 HTTP：等完整 JSON，适合分类、抽取这类短结果。
- SSE：服务端持续下发增量文本，适合对话。标准 `EventSource` 只能 GET，也不能带自定义请求头；要 POST 消息体和鉴权时，用 `fetch` 读 `ReadableStream`，自己解析 `text/event-stream`。
- WebSocket 或 WebRTC：连接是双向的。文本对话通常上行很少；实时语音这种两边同时在传数据时再用。
- 端侧推理：用 WebGPU 和 WASM 在浏览器里跑小模型，数据留在设备上，模型大小受显存限制。

工具调用和检索放在后端。前端负责带 `AbortSignal` 取消、按增量渲染，并把模型输出当不可信内容显示。

### 4. SSE和WebSocket的区别是什么？为什么AI对话场景多采用SSE?

**参考答案**

SSE 是跑在 HTTP 上的服务端到客户端的文本推送。WebSocket 是协议升级之后的全双工长连接。对话生成的形态是一次请求后面跟着持续的 token，SSE 和这个形态一致。

SSE 沿用 HTTP 的代理、负载均衡和鉴权。标准 `EventSource` 会自动重连；服务端下发过事件 id 时，重连请求带上 `Last-Event-ID`。自己用 `fetch` 读流时，重连要自己写。它传文本，客户端的下一句话是另一次 HTTP 请求。

WebSocket 可以双向传输文本和二进制，适合协作编辑、游戏和实时音频。连接状态、心跳和重连都要自己维护，服务端要为每条连接保留资源。

文本对话里用户发言稀疏，生成方向是单向的，主流对话接口也按 SSE 来推增量。用户要停，取消这次 HTTP 请求即可，后端在发现断开后停止上游生成。上行同样密集时，再改用 WebSocket 或 WebRTC。

### 5. 前端实现AI流式输出（打字机效果）的具体实现方案是什么？

**参考答案**

网络层按 SSE 事件取出增量，渲染层每帧合并成一次更新。模型本身已经一个字一个字到达时，直接把增量画出来；只有产品要求匀速时，才把字放进队列，每帧取固定个数，队列积压过多就一次刷完。

解析时用 `TextDecoder` 的 `stream: true`，避免汉字被截在两个 chunk 中间。缓冲按空行切事件，分隔符是 `\n\n` 或 `\r\n\r\n`，切不齐的留在缓冲里。流结束再 `decode()` 一次，并把最后一段按同一规则解析。`data:` 行拼成载荷；`[DONE]` 只是部分厂商的结束标记。`event: error` 走错误分支。调用方按厂商字段取文本，不认识的事件跳过。

React 里增量先写入 ref，`requestAnimationFrame` 每帧把全文 `setState` 一次。每个 token 都更新状态，会让 Markdown 整树反复渲染。只有用户已经贴在底部时才自动滚动。没闭合的代码围栏先当纯文本。Markdown 按结构渲染，原始 HTML 不进 DOM。

```javascript
async function consumeSSE(response, onData) {
  if (!response.ok || !response.body) throw new Error(`HTTP ${response.status}`);
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buf = '';
  const delim = /\r?\n\r?\n/;
  const take = (block) => {
    let event = 'message';
    const data = [];
    for (const line of block.split(/\r?\n/)) {
      if (!line || line.startsWith(':')) continue;
      if (line.startsWith('event:')) event = line.slice(6).trim();
      else if (line.startsWith('data:')) data.push(line.slice(5).replace(/^ /, ''));
    }
    const payload = data.join('\n');
    if (!payload) return 'skip';
    if (payload === '[DONE]') return 'done';
    if (event === 'error') throw new Error(payload);
    onData(JSON.parse(payload));
    return 'ok';
  };
  try {
    for (;;) {
      const { done, value } = await reader.read();
      if (done) break;
      buf += decoder.decode(value, { stream: true });
      let matched;
      while ((matched = delim.exec(buf))) {
        const block = buf.slice(0, matched.index);
        buf = buf.slice(matched.index + matched[0].length);
        if (take(block) === 'done') return;
      }
    }
    buf += decoder.decode();
    if (buf.trim()) take(buf);
  } finally {
    reader.releaseLock();
  }
}
```

### 6. 流式输出过程中如何实现中断响应？前端怎么处理?

**参考答案**

用 `AbortController` 取消这次 `fetch`。已经显示的半段留下，这条消息标成已停止。浏览器里的取消要传到模型，得靠后端发现连接断开后中止上游请求，否则 token 还会继续产生。

`fetch` 因取消失败时，错误名是 `AbortError`，不要弹成普通失败。用户主动停止后不要自动重试。发起新的一轮之前，先把上一条标成已停止，再 abort 它的控制器。旧请求晚到的回调带有自己的序号，序号已经前进就不再写入界面。

`EventSource` 用 `close()`。WebSocket 和单次生成没有绑定关系，要另发取消消息，并在这轮结束前丢掉该轮后续帧。

```javascript
async function sendAndMaybeStop(url, payload) {
  const ctrl = new AbortController();
  stopButton.onclick = () => ctrl.abort();
  try {
    await consumeSSE(await fetch(url, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(payload),
      signal: ctrl.signal,
    }), appendDelta);
  } catch (err) {
    if (err.name === 'AbortError') markStopped();
    else showError(err);
  }
}
```

### 7. React中状态管理库的理解，不用状态管理库怎么做组件间通信？

**参考答案**

状态库要解决的是跨层级共享，以及一次更新通知谁。服务端列表和缓存用 React Query 或 SWR；按钮展开这类客户端状态才进 store。两者塞进同一个大对象，失效策略会缠在一起。

组件内部用 `useState` 或 `useReducer`。Context 适合主题、登录态这类低频数据。某个 Context 的 value 变化，读它的组件都会重新渲染；value 每次渲染都换成新对象时也会如此，所以要稳住引用，或按变化频率拆开。Redux 配合 Toolkit，用单一状态树、纯函数和中间件，适合步骤多、要回溯的流程。Zustand 的 store 在 React 外面，组件按选择器订阅。Jotai 一类按原子订阅。

没有库时：父子走 props 和回调；隔层就把状态提到最近的公共父组件；再远用 Context 加 `useReducer`。需要分享的筛选放进 URL。父组件调用子组件的播放、聚焦，用 `useImperativeHandle`。手写发布订阅能通信，订阅必须在卸载时去掉；主状态仍走 React 的数据流。

### 8. useMemo、useCallback、useRef的区别是什么？

**参考答案**

`useMemo` 缓存计算结果，`useCallback` 缓存函数，计算发生在渲染期间。`useRef` 是跨渲染保留的可变容器，改 `.current` 不会让组件重新渲染。

`useCallback(fn, deps)` 等价于 `useMemo(() => fn, deps)`。依赖按 `Object.is` 比较。漏写依赖，函数里看到的是旧状态；依赖每次都是新引用，缓存就不起作用。它们用来稳住传给子组件的引用、避开昂贵计算。正确性不要押在「这次一定命中缓存」上。已经用 `memo` 包住的子组件，如果收到的仍是新的内联函数，还是会更新。项目开了 React Compiler 的话，手写记忆化的收益要重新量。

`useRef` 用来放 DOM 节点、定时器、`AbortController`，以及只在事件里读、不需要刷新界面的最新值。界面要跟着变，用 state。`useRef(new AbortController())` 每次渲染都会执行构造函数，只是第一次之后丢掉返回值；昂贵对象在 `current` 为空时再创建。

### 9. 原型链、类和继承的关系，class语法跟prototype是什么关系?

**参考答案**

属性查找沿着内部槽 `[[Prototype]]` 委托给原型。`class` 把「构造函数 + 原型对象」写成声明，继承的是这条委托链，实例方法不会复制到每个对象上。

读 `obj.x` 时先看自身，再沿原型走到 `null`。普通对象的链末端是 `Object.prototype`。`instanceof` 看的是构造函数的 `prototype` 是否出现在这条链上。

`class Foo extends Bar` 会接两条链：`Foo.prototype` 委托 `Bar.prototype`，实例方法走这里；`Foo` 委托 `Bar`，静态方法走这里。子类构造函数要先 `super()` 才能用 `this`。类体里的方法在原型上，并且不可枚举。公有实例字段装在实例自身，子类要等 `super()` 返回之后才装，每个实例一份。写成箭头函数的字段也在实例上，不共享。

类声明在初始化完成前处于暂时性死区，声明之前不能访问。类体运行在严格模式，构造函数必须用 `new` 调用。手写的对应物就是把子类原型委托给父类原型，再把子类构造函数委托给父类构造函数。

### 10. 事件循环机制，如果微任务一直没执行完会怎样?

**参考答案**

浏览器处理完一个宏任务，会把微任务队列清空，然后才轮到渲染和下一个宏任务。清空这一步如果结束不了，点击、定时器和绘制都会停住。

宏任务包括脚本、`setTimeout`、I/O 回调和用户事件。微任务包括 `Promise.then`、`queueMicrotask` 和 `MutationObserver`。微任务执行时又排入的微任务，仍在同一次清空里跑完。`new Promise` 的执行器是同步的，`.then` 才进微任务队列。`requestAnimationFrame` 属于后面的渲染步骤，和微任务队列是两条路径。

有两种「执行不完」。单个微任务函数里死循环，调用栈不返回，排在它后面的微任务也跑不到。微任务不断再把自己排进队列，当前函数会返回，但检查点不结束，效果同样是页面不再响应，浏览器可能提示页面无响应。

```javascript
function spin() {
  queueMicrotask(spin);
}
spin();
setTimeout(() => console.log('macro'), 0);
```

Node 里 `process.nextTick` 是另一条队列，会在 Promise 微任务之前被清空，和浏览器的划分不一样。

### 11. 线上页面性能不好，有没有系统的定位和优化方法?

**参考答案**

先用线上数据确认差的是哪一个指标，再拆成网络、主线程和渲染。一次只改一类，用同一个分位对比。

现场按页面和版本看 TTFB、LCP、INP、CLS，以及接口成功率。实验室用 Performance 面板看长任务、请求瀑布和强制同步布局，用覆盖率和打包结果看体积落在哪个模块。

TTFB 高，查服务端和缓存。资源大，就压缩，图片按尺寸用现代格式，首屏脚本拆开；入口 HTML 短缓存，带指纹的静态资源长缓存。主线程上的长任务拆开，把一段工作让出去再继续；长列表做虚拟化，收掉无关的重新渲染。布局抖动来自读写几何信息交替进行；动画用 transform 和 opacity，屏外区块可以用 `content-visibility`。内存一直涨，就查监听器、定时器和已经脱离文档的节点。

INP 差，多半是输入之后的处理太长。没有基线时先打点，再谈优化。本机一次实验分数不能代替线上分位。

### 12. 如果要跟客户端一起做性能优化，哪些可以是客户端帮忙做的？

**参考答案**

混合容器里，客户端适合提前消化启动、网络和重资源。页面仍然负责业务渲染。离线资源和预取数据要能对上版本。

客户端可以做这些事：

- 预热 WebView，把冷启动提前付掉。
- 用离线包和资源拦截命中 HTML、JS、CSS。包要带版本；坏包必须能绕过，直接走网络。
- 原生提前请求首屏接口，页面打开时直接拿结果。
- 大图走原生缓存和解码，避免在 WebView 里解码。
- 原生先画出骨架。登录态、字体和公共桥由容器复用。
- 白屏和加载耗时由容器打点，比页面里的 `performance` 更接近打开瞬间。

页面侧让非核心模块晚到也不挡住主内容，并把频繁的桥调用合并。版本对不齐时，旧离线包配新接口是最常见的故障。

### 13. 设计一个动态加载的渲染系统，系统里有很多模块，随意组合成一个页面，怎么设计？怎么处理模块动态渲染的逻辑？

**参考答案**

页面保存一份模块协议，渲染器按类型到注册表里取组件。每个模块单独加载、单独失败。同一仓库里用动态 `import`；多个团队各自发布，再用模块联邦这类方案，并保证 React 只有一份。

协议写楼层顺序、模块类型、版本和数据源，不写死打包路径。注册表把类型映射到懒加载函数。未知类型显示占位。每个楼层外包错误边界，一个模块抛错，页面其余部分还在。首屏模块先加载，其余空闲再拉。样式用模块化方案或约定前缀，避免楼层互相覆盖。

模块声明数据依赖，由页面级 loader 合并请求，而不是每个楼层各打各的。模块之间不互相引用，跨楼层用页面级的类型化事件。第三方模块不要跑在主文档的全局环境里。

难在版本一起灰度：协议、模块包和接口字段必须匹配。服务端渲染时，服务端和浏览器要解析到同一个模块版本，否则注水会对不齐。

### 14. AI在实习部门或项目中有什么应用场景?

**答题思路**

只讲部门里真实用过的场景。没上线的说了解，不要说成自己做的。

1. 场景：谁在用，要完成对话、生成文案、总结、审核，还是辅助写代码。
2. 你的前端职责：输入、流式展示、引用、中断、结果编辑，还是只嵌了一个对话窗。
3. 数据从哪来：用户输入、商品信息、文档检索，还是订单接口。哪些字段不能放进提示词。
4. 失败时长什么样：超时、没有依据时的拒答、转人工。你做了哪一种。
5. 有多个场景时先讲透一个，再用一两句带过其余的。

可对照的方向包括客服问答、商品卖点、搜索摘要、审核辅助、运营文案。只选你做过的。

### 15. AI带来了哪些前端新挑战?

**参考答案**

模型的输出又慢、又不完整，还可能是错的。前端要处理流、取消、不可信内容和能回溯的反馈。

半截 Markdown 会让代码块和表格闪坏，闭合之前要有降级显示。停止生成要同时停界面和上游。旧请求晚到，不能覆盖新的回复。模型输出里的 HTML 不能直接进 DOM，链接协议也要限制。

上下文变长之后，不能每轮把整页 DOM 和全部历史原样回传。没有检索或接口依据时，界面要明确说没有查到，而不是把句子写得像结论。改数据的动作等人确认后再发。

散文不适合做快照测试。协议解析、参数校验、有没有引用，这些可以做成稳定断言。流式区域用 `aria-live="polite"`，避免每个 token 都打断读屏。

### 2. 详细介绍一下你做过的最复杂的AI相关项目

**答题思路**

用真实项目往下套。没做的层直接说没做。

1. 目标：最后交付的是一段文字、页面上的结构化卡片，还是会改数据的操作。

### 3. 什么是AI智能体？它的核心组成部分有哪些?

**参考答案**

智能体用模型面向一个目标做多步决策：可以选择工具，看到真实结果后再决定继续还是停止。一次文本补全只生成一段话，还不是智能体。

核心部分有五块。模型根据当前上下文选择下一步。工具带名字、说明、参数结构和副作用级别，说明写清楚，它才不会选错。运行时负责组装上下文、调用模型、校验并执行工具、把观察写回、判断停止；模型自己不记得上一次工具返回了什么。记忆分成当前任务的短期状态，和跨会话仍有效的长期事实。约束包括步数、超时、费用，以及写操作的确认和权限。

循环直到模型给出最终答案、步数用尽或人停掉。轨迹里没有那次工具调用，就不能把「模型说已经办好了」展示成成功。

### 4. ReAct机制是什么？与CoT、ToT有什么区别?

**参考答案**

CoT 在一次生成里把中间推理写出来。ReAct 让推理和外部动作交替进行，用观察修正下一步。ToT 同时展开多条思路，评估后再搜索。

CoT 不接触环境。零样本里要求逐步推理，或给出少量示例，模型都会先写过程再给答案。过程错了，后面会跟着错，没有检索或接口可以纠正。

ReAct（Yao 等人，2022）每步产生思考和动作。动作调用搜索、接口或代码，环境把观察追加进轨迹，模型再决定继续或结束。它能用外部事实，往返也更多。没有步数上限时，会反复调用同一个工具。函数调用只是模型输出结构化动作的接口；ReAct 还要求运行时真的执行，并把观察写回后再生成下一步。参数执行前要用 schema 校验。

ToT 把中间想法展开成树，用模型或规则给部分解打分，按宽度或深度搜索，可以回退。它适合有明确对错的搜索题，token 和时间都明显高于一条链。

生产里的工具循环多按这个节奏走：执行动作、写回观察、再决定下一步，并加上步数上限。模型不一定把思考过程展示给用户。完整的树搜索很少直接上生产。某一步的思考里可以用 CoT，树的某个节点也可以是一段 ReAct。

### 5. 在前端实现一个Agent循环时，如何管理工具调用的异步执行、超时处理与结果合并?

**参考答案**

循环放在渲染外面的控制器里。只读工具并行，写工具串行。每条结果用 `tool_call_id` 对回去。超时变成模型读得懂的失败观察，而不是把整个循环打崩。

厂商经常把参数做成 JSON 字符串，要先解析，再用 schema 校验。未知工具名和校验失败都不执行，把原因按 id 写回。只读调用共用父级 `AbortSignal`，每个工具再套自己的超时。每个调用自己捕获错误，这样某一条失败不会让整组 `Promise.all` 丢掉其余结果。用户停止时父级信号取消，这一轮不再请求模型。调用前信号已经处于取消状态时，`abort` 事件不会再响一次，所以要先判断再进入 handler。

写回顺序跟当初的 `tool_calls` 一致，按 id 匹配，不按完成先后。创建工单、提交订单这类写操作串行执行，并带幂等键。超时只说明响应没到，服务端可能已经执行，不能直接再发一次。

界面只订阅轨迹，工具状态分 pending、success、error。步数和总时长单独封顶。React 渲染期间不要推进循环。

```javascript
async function runToolCall(call, registry, parent) {
  const tool = registry.get(call.name);
  if (!tool) return { tool_call_id: call.id, ok: false, error: 'unknown tool' };
  if (parent.aborted) return { tool_call_id: call.id, ok: false, error: 'aborted' };
  const signal = AbortSignal.any([parent, AbortSignal.timeout(tool.timeoutMs)]);
  try {
    const args = typeof call.arguments === 'string'
      ? JSON.parse(call.arguments)
      : call.arguments;
    const output = await tool.handler(args, { signal });
    return { tool_call_id: call.id, ok: true, output };
  } catch (err) {
    const error = parent.aborted ? 'aborted'
      : err.name === 'TimeoutError' ? 'timeout'
      : err.message;
    return { tool_call_id: call.id, ok: false, error };
  }
}
```

旧浏览器没有 `AbortSignal.any` 和 `AbortSignal.timeout` 时，用 `AbortController` 加定时器组合同一个信号。

### 6. 前端Agent常用的工具有哪些？如何封装这些工具?

**参考答案**

前端只暴露当前页面和本域接口需要的动作。工具是一份带模式的清单：执行前校验，给模型的观察和给界面的载荷分开。

常用的有：读取路由、选中文本和表单草稿；在页内滚动、高亮；按注册表挂上预先做好的结果卡片；调用本域接口做搜索、查订单、查帮助文档；读写用户明确保存过的偏好；向用户要一次确认。任意 URL、任意脚本，以及未经确认的写接口，不放进清单。检索在后端时，前端只传查询，不在浏览器里编一份「命中文档」。

注册表的每一项包含 `name`、`description`、JSON Schema、`handler`、超时、副作用是读还是写、是否必须确认。发给模型的工具列表由注册表生成。`handler` 收到的参数先校验。返回给模型的是截断后的结构化观察；卡片用另一份 UI 数据，整页 DOM 不进上下文。描述里写上什么情况下不要用它。前后端共用同一份 schema，避免字段各写各的。

### 7. Agent开发中最常见的失败场景是什么？你怎么解决？

**参考答案**

最常见的是循环不收敛：同一个调用反复出现，或者工具还没执行，回复里已经说办完了。紧接着的问题是，超时后把写操作又发了一次。

给最大步数。工具名加参数算一个摘要，连续相同的调用就停，改为基于已有观察回答，或向用户问清楚。未知工具和 schema 不通过的参数不要执行，把校验错误当作观察返回。轨迹里没有对应调用时，界面不能展示成已提交。

写操作超时后，先按幂等键查询结果，再决定要不要再发。没有幂等键就停下来问人。读操作才按有限次数重试。

工具返回的网页或文档里可能夹着新的指令。观察用固定分隔标成数据，权限不随这段文字升高。旧观察把上下文塞满，是另一类失败，处理办法是裁剪和摘要，而不是把轨迹无限接长。

### 8. 工具调用上下文污染怎么解决？

**参考答案**

污染指过期的工具输出、错误堆栈，以及观察正文里的指令占满了上下文。后面的步骤会跟着旧结果走，或者跟着外部文本里的要求走。

消息分成用户目标、模型决定和工具观察。观察用固定分隔包起来，并标明这是数据。每条输出有长度上限。原文按 id 放在上下文外面，需要细节时再按 id 取一页。失败尝试只留一行原因，堆栈不进入下一轮。

阶段变了，例如检索结束、开始起草，就去掉没有被引用的命中片段。较早的工具结果压成短的事实列表：实体、已做决定、未决问题。用户明确说过的预算、时间、不能改的条件单独保留。系统提示、当前目标和最近几步始终留在窗口里。

其他用户的数据、整页 HTML，以及已经否掉的计划，不再拼进下一轮提示词。

### 9. 前端Agent的记忆存储怎么设计？本地存储与RAG如何结合？

**参考答案**

当前对话放会话存储。稳定偏好做成结构化字段。文档和说不清结构的旧对话走检索。浏览器里的存储是这台设备上的缓存；换设备以服务端为准。

这一线程的消息和工具轨迹先放内存。刷新后还要看，就进 IndexedDB。`localStorage` 是同步 API，容量只有数 MB，只放主题这类小配置，不放对话和密钥。尺码、常用地址这类长期偏好带上时间和来源，写入前让用户确认。模型每一轮的推断不要自动写进长期记忆。

帮助文档和历史对话的检索，企业场景放在后端，按租户和权限过滤，前端提交查询并展示引用。确实要留在端上时，用同一套嵌入模型写入本地库；换嵌入模型就要重建索引。

组装请求时先放结构化偏好，再放这次检索到的少量片段，并带来源 id。用户删除记忆时，本地和远端一起删。两条偏好冲突时，以更新的明确说法为当前值，旧值留记录。订单和工单的事实来自业务接口，不来自本地库。

### 10. 如何控制Agent的上下文长度，避免Token溢出?

**参考答案**

调用前按该模型的上下文上限做预算，先给输出和系统提示留位置，再分配历史和检索。快到上限就压缩，不等接口返回长度错误。

用和模型匹配的分词器计数。按字符数除以 4 只适合粗算英文，中文会明显低估。不同模型上限不同，数字放配置。

预算先扣掉输出预留、系统提示和本轮真正会用到的工具定义。剩下的分给最近几轮原文和检索片段。超出时按这个顺序减：旧的工具原文、没被引用的检索块、已经写进摘要的早期闲聊。摘要里留下约束和未决问题。压缩触发在上限之前，留出余量。

系统提示和工具定义保持稳定，放在前缀；变化的历史放在后缀，这样服务商的前缀缓存才有机会命中。图片先缩小再上传。前端裁剪改善的是费用和失败率；服务端用同一规则再裁一次，因为请求可以不经过你的页面。

### 11. 前端如何安全使用AI？有哪些安全措施?

**参考答案**

密钥和权限放在后端。前端把模型输出当不可信内容来渲染，写操作单独让用户确认。只做在浏览器里的检查，关了脚本就没了。

请求走自己的 BFF，会话鉴权、限流和审计都在这里。厂商密钥和系统提示由 BFF 持有，不打进前端包。送进模型的内容先去掉证件号、令牌、整页 DOM 和其他用户的数据。

Markdown 渲染不插入原始 HTML。业务必须展示 HTML 时，先净化，并禁止 `javascript:` 链接和内联事件。代码块只展示，不自动执行。

付款、删除、提交工单在界面上单独确认后再发。观察文本里要求升高权限或调用某个工具时，运行时不照做。工具白名单和数据分隔由服务端执行。内部异常和密钥不回显到气泡里。

### 12. 在AI产品中，前端可以通过哪些技术手段帮助降低Token成本?

**参考答案**

费用取决于输入多少、输出多少、用的哪一档模型。前端能决定的是少发、少生成、少调用，并让可缓存的前缀保持稳定。

少发：上传选中文本或当前模块，不上传整页；历史和工具输出按预算裁；检索减少条数和每条长度；这一轮用不到的工具定义不带。系统提示和工具列表放在提示词前部，内容保持稳定，方便前缀缓存。

少生成：按功能设置输出上限。用户一点停止就中止上游。意图不清楚时先追问，不直接生成长文。

少调用：输入防抖，提交后再请求对话。不含个人信息、答案又稳定的说明，可以短时缓存。规则或小模型能分类的，就不要先打大模型。补全和正式回答可以走不同模型。具体单价以厂商当时的计费为准。

### 13. 如何处理AI生成内容的质量评估?前端可在交互层面提供哪些反馈机制？

**参考答案**

前端负责把信号系到一次具体生成上：哪一段不好、当时的模型、提示词版本和实验桶。质量结论来自这些信号和离线评测。界面自己不给内容打一个总分。

显式反馈包括赞踩、原因标签（事实错误、不完整、格式错、有害）、重新生成，以及用户改完再接受。点踩时记下选中的范围，不只存整段。隐式信号包括复制、追问里的纠正、放弃、引用是否被点开、工具是否真的成功。隐式信号有偏差，用来辅助。

浏览器里能做确定检查的先做：JSON 能否解析，链接是否出现在检索结果里，必填字段是否齐全。检查不通过，就不要把结果展示成已核实。

每条反馈带 trace id、模型名、提示词版本和实验桶，否则无法回溯。交互上一次点击就能完成，详细理由可选，不挡住用户原来要办的事。

### 14. 在处理AI幻觉时，前端可以设计哪些实时提示与用户教育交互？

**参考答案**

界面把「有检索或接口依据」和「模型组织的语句」分开。没有可靠信号时，不显示一个编出来的置信度百分比。

有出处，就把引用放在对应句子旁边，点开能看到片段和文档版本。检索为空，或者价格、库存不是接口返回的，就直接写没有查到，并给出商品页、工单或人工入口。金额、库存、时效、规则用接口卡片展示，模型只组织语言。

说明放在结果旁边的一句短文案，例如价格和库存以商品页为准。首次使用可以有一条可关闭的说明，不必每轮弹出长段声明。用户点「这不对」时，把原句带进下一轮输入。

退款金额、规则承诺这类问题，依据不足就转人工。流式输出时依据还没到齐，可以先显示正在核对来源，对上了再收成引用。

### 15. 如何实现前端本地的敏感词过滤与内容安全审核?

**参考答案**

本地词表负责输入前提示、输出时遮盖。能不能发送、能不能落库，由服务端用同一套策略再判定。本地逻辑关脚本就能绕过。

词表建成 Trie。词量大时用 Aho-Corasick，扫描时间和文本长度成线性关系。扫描前做 NFKC、全角转半角，并去掉零宽字符。中文按子串做最长匹配，减轻短词误伤。归一化挡不住故意拆字，所以不能只靠这一层。

流式输出时，已确定不是任何词前缀的部分才上屏。末尾留下「最长词长度减 1」个码点，和下一块拼起来再扫，避免敏感词被 chunk 切开后前半段已经画出去。电话和证件号用单独模式。词表按版本从服务端下发，缓存在 IndexedDB。误伤要允许改写后继续。

```javascript
function buildTrie(words) {
  const root = { next: new Map(), end: false };
  for (const word of words) {
    let node = root;
    for (const ch of word) {
      if (!node.next.has(ch)) node.next.set(ch, { next: new Map(), end: false });
      node = node.next.get(ch);
    }
    node.end = true;
  }
  return root;
}

function maskHits(root, text) {
  const chars = [...text];
  const cover = Array(chars.length).fill(false);
  for (let i = 0; i < chars.length; i++) {
    let node = root;
    let j = i;
    let end = -1;
    while (j < chars.length && node.next.has(chars[j])) {
      node = node.next.get(chars[j]);
      j += 1;
      if (node.end) end = j;
    }
    for (let k = i; k < end; k++) cover[k] = true;
  }
  return chars.map((ch, i) => (cover[i] ? '*' : ch)).join('');
}
```

### 1. 自我介绍

**答题思路**

三面压缩履历，突出取舍。半分钟说明年限和方向，然后只讲一个系统。

1. 这个系统的硬约束：有没有写操作、能不能接受厂商绑定、用户愿意等多久。
2. 你怎么分层，每一层谁拥有状态。
3. 你放弃过的一条路，以及当时为什么放弃。
4. 收在权限或稳定性上，例如写操作为什么不由模型直接提交。

### 2. 项目介绍，重点讲技术选型和架构设计

**答题思路**

按「约束 → 比较过的选项 → 选择 → 上线后怎么核对」讲。功能点不要按时间线念完。

1. 约束：要不要流式，有没有写操作，首屏时延，发布频率，能不能被一家模型厂商绑住。
2. 讲两条你真的比较过的路，例如自己写循环还是用编排框架，传输用 SSE 还是 WebSocket。带上当时团队熟不熟、能不能回滚。
3. 一次请求经过接入、编排、模型、工具和知识、安全。每层谁保存状态。
4. 一个选型事后怎么验证：完成率、时延、错误率或人工抽检。数字只用真实的。
5. 留下一个你希望被追问的点，例如灰度时模块版本怎么对齐，或工具权限怎么收。

### 3. 设计一个面向企业客户的智能客服Agent系统，要求能回答产品问题、处理售后、对接工单系统，你怎么设计？

**参考答案**

按租户隔离。路由把产品问答、售后和人工拆开。价格、订单和退款金额只来自业务接口，模型负责理解问题、组织语言。创建工单要人确认，并带幂等键。

接入层处理企业账号、租户和限流。编排层根据意图选择路径。问答路径的工具清单里不出现售后写接口。产品问答只检索审核过的文档，回答带上文档版本；检索为空就说明没有依据。售后先查订单和规则，缺槽位就追问。确认之后，由工单适配器提交，模型不直接写库。

检索分低、连续失败，或用户要求人工时，把同一条 trace 交给人工队列。前端用流式气泡显示「正在查订单」，用卡片展示订单和引用，停止按钮始终可用。生成失败时，提交工单仍然可用。

租户之间的知识库不能互查，这个过滤做在检索条件里，不写在提示词里。超时之后工单可能已经创建，再次提交前先按幂等键查询。

### 4. Agent系统的架构分层应该怎么设计？各层职责是什么？

**参考答案**

竖向四层：接入、编排、模型适配、能力。安全、评测和观测横切每一层。工具不反向去驱动编排，界面不保存密钥和系统提示。

接入层负责渠道、会话、流式推送和渲染，把用户输入变成内部请求。编排层是运行时：步数、超时、重试、停止条件、人工确认和轨迹，不绑定某一家模型。模型适配层组装提示词和工具 schema，做 token 预算，抹平厂商差异。能力层是订单、工单、检索和记忆的适配器，每个工具标明读还是写。知识进入模型之前，先按租户和权限过滤。

治理层做输入输出策略、密钥、审计、trace 和评测集。增加一个渠道时，复用编排和治理，审核逻辑不写死在某一个页面里。

写操作的幂等和确认放在编排和工具契约里。检索时就被权限排除的文档，不会占满召回名额，也不会进提示词。

### 5. 多Agent系统有了解吗？多个智能体如何分工合作?

**参考答案**

多个智能体用来拆开权限和提示词。它们靠一份写清楚的交接状态协作。一个智能体加上分路径的工具白名单已经够用时，就先不拆。

三种常见分工：路由把请求分给专科，专科之间不互相聊天；主管拆任务、收结果，专科只有自己的工具；固定流水线按检索、起草、检查的顺序执行。交接的内容是目标、已确认事实、约束和未完成项，不是把全部原始轨迹倒给下一位。

有副作用的工具只交给一个执行者。对外始终由一个角色说话，内部步骤用进度展示。每个智能体有自己的步数上限，主管可以终止整次任务。

多一个角色，轮次和 token 会上去，两个角色还可能互相等待。提示词和权限已经互相干扰时，再把专科拆开。

### 6. 如何设计一个AI前端项目的标准化目录结构，兼顾业务功能、共享组件、工具函数与类型定义?

**参考答案**

按业务功能分目录。共享组件、纯工具函数和协议类型各自守住边界。流式解析做成纯函数，方便用截断的 chunk 做单测。密钥和系统提示不放进前端目录。

```text
src/
  features/chat/     会话界面、消息类型、流式状态
  features/agent/    循环控制器、工具注册表、结果卡片
  components/        与业务无关的共享组件
  services/          BFF 客户端、SSE 解析
  hooks/
  types/             跨功能共用的协议类型
  utils/             无业务含义的纯函数
```

一个功能自己的组件、请求和类型放在该功能目录里，外面只引用它的入口。`components` 不发请求，也不认识工具协议。只被一个功能使用的函数留在功能目录，不进 `utils`。消息、工具调用和流事件用可辨识联合类型描述。

工具定义和系统提示归后端。前端保留渲染卡片需要的结果类型，两边从同一份 schema 生成，避免手写两套对不上的字段。

### 7. 如何用WebComponents封装可复用的AI自定义元素，实现跨框架使用？

**参考答案**

把对话或消息做成自定义元素。契约只有 attribute、property、方法和 `CustomEvent`。React、Vue 或原生页面外面各写一层很薄的适配。

`customElements.define` 注册元素。字符串配置用 attribute。工具列表这类对象用 property，不把 JSON 塞进属性字符串。向外通知用 `CustomEvent`，`bubbles` 和 `composed` 都设为 true，事件才能穿过 Shadow DOM。宿主用 `addEventListener` 订阅。样式放在 Shadow DOM 里，宿主通过 CSS 变量换肤，需要被外部选中的节点用 `part` 暴露。

`connectedCallback` 里再做会发起网络的工作。`disconnectedCallback` 里中止请求和监听。节点被移动时会先断开再连上，中止逻辑用代次区分销毁和移动，避免误停正在进行的生成。影子树内部补上焦点顺序，对话记录用 `role="log"` 和 `aria-live="polite"`。

元素本身用原生自定义元素或 Lit 这类轻运行时。把一整份 React 打进组件可以运行，体积和多份 React 会变成跨应用的负担。服务端渲染提供降级内容，元素升级发生在客户端。

### 8. 如何设计一个前端实验平台，支持对AI模型参数、Prompt模板、UI布局进行A/B测试?

**参考答案**

按用户稳定分桶。布局变体可以在前端生效。模型和提示词由服务端按桶里的配置解析，调用方不能自己改温度或系统提示。主指标和护栏指标事先定好，真正曝光之后才计数。

一条实验有标识、变体、流量和状态。哈希输入同时包含用户标识和实验标识，同一个人在这个实验里始终落在同一个变体，不同实验也不会绑死在同一个桶号。分配结果由服务端注入，避免首屏在两个布局之间闪动。按请求随机会让同一个人交替看到两套界面。

布局、提示词版本、模型参数分成三条配置。提示词变更走评审和小流量，并能一键退回。实验台提供布局预览，以及调试时可见的变体标识。

主指标可以是解决率或人工接手率。时延、token、错误率和安全拦截率作为护栏，一起看。流量从小比例开始。反馈和链路日志都带实验标识和变体，否则结果无法归因。

### 9. 在AI多轮对话中，如何设计上下文窗口的管理策略?

**参考答案**

每一轮按预算重新组装，而不是把历史原样累加。始终保留系统约束、当前目标、最近原文，以及一份会更新的摘要。用户明确说过的限制，不因为窗口滑动被删掉。

预算等于模型上限减去输出预留和余量，用该模型的分词器计数。超预算时，先去掉旧的工具原文和未引用的检索，再去掉已经写进摘要的早期闲聊。

摘要异步生成，不挡住当前这轮回复。结构固定为：已做决定、实体、未决问题、约束。预算、不能退换这类原话单独成列表。用户换了一个任务时，旧任务归档，新任务用新的工作上下文。用户钉住的消息不参与裁剪。

重新生成时，使用当时那一轮组装好的同一份上下文。服务端保存实际送进模型的内容。界面把早期气泡折叠之后，模型看到的是摘要，这两件事在界面上要对得上。

### 10. 如何实现AI生成结果的一键格式化？

**参考答案**

格式化作用在副本上，模型原始输出保留。认得出的结构才动，认不出就保持原文并提示。

先判断是围栏代码、JSON、Markdown 还是表格。代码按声明的语言，放在 Worker 里格式化，避免卡住输入；语言未知就不动。JSON 先解析再缩进，解析失败不改原文。Markdown 用解析后再打印，统一标题和列表的空白。展示路径仍然做净化，格式化不因此打开原始 HTML。

流还没结束时，按钮不可用，或者只处理已经闭合的围栏。连续格式化两次，结果应保持稳定。存储同时留下 raw 和 formatted，撤销就是切回 raw。复制和导出要标明是 Markdown、纯文本还是富文本。

### 11. 如何设计一个AI辅助编程的IDE插件，提供代码补全、注释生成、错误解释、重构建议等功能?

**参考答案**

插件负责编辑器集成和上下文裁剪。补全能取消。注释、解释和重构都先给预览，用户接受后才改缓冲区。凭据文件不进提示词。

补全使用 FIM：把光标前缀、后缀、当前诊断和少量相关导入放进预算，不上传整个仓库。用户继续输入，就用编辑器的取消令牌停掉上一次请求。语言服务已经给出精确符号时，优先用那个结果，模型结果作为幽灵文本。评估看采纳率，以及采纳后短时间内有没有被删掉。

注释、错误解释和重构由用户显式触发。解释带上诊断信息和周围代码。重构返回工作区编辑，用 diff 预览。聊天面板可以流式输出；行内幽灵文本按一次结果替换，避免逐字闪动。

索引放在本地或企业网关后面，按仓库增量更新。排除 `.env` 和凭据路径。仓库里的文字只当作代码数据，即使其中夹着指令，也不改变插件权限。补全的时延预算要短；重构可以慢，因为人在等一份 diff。

### 12. 最近在学什么新技术？怎么去接触一门新技术?

**答题思路**

说一个你正在学、并且已经写过代码的技术。方向可以贴近岗位，例如流式协议、智能体运行时或编辑器插件，但必须是真的。

1. 用官方文档或规范把最小路径跑通，先得到一个能运行的切片。
2. 只加一个真实约束，例如取消、超时或一段截断输入，看它在哪一层破。
3. 对照一个成熟实现里的对应模块，看状态放在哪、失败怎么返回。从一个模块看起，不从框架全貌抄起。
4. 用自己的话写一页：输入输出、失败时的行为、你仍然不清楚的点。
5. 能把这段讲清楚，或接到自己的小项目里，再放到回答里。主动说出还没学完的部分，追问会落在你的边界上。

### 13. 会看哪些书？怎么选择要看的书？

**答题思路**

报 2 到 3 本你读完或正在读的，并说它解决了你当时的哪个问题。

1. 按当前的卡点选：协议、渲染、语言机制，或系统设计。先有问题，再找材料。
2. 变化快的接口看现行文档和原始论文，例如模型厂商的流式说明、ReAct 论文。语言机制、浏览器工作方式这些稳定部分，再用书把体系补上。
3. 看版本和日期。接口类材料过时就换文档。基础书要还描述得了你正在用的行为。
4. 读一个机制，就在自己的切片里验证一次。
5. 一本书只取这一阶段要用的章节。说不出它改变了你哪段代码，就不要放进回答。

### 14. 技术选型时，一个新技术和一个稳定的旧技术，你会怎么选择？选择的考虑有哪些?

**答题思路**

先看失败了会怎样，再看收益能不能衡量。

1. 浏览、加购、下单这类主路径，用团队已经能排障的技术。新能力放在可以摘掉的边缘，例如旁边的智能客服，用接口和主路径隔开。
2. 写清收益：时延、体积、开发速度，或旧技术做不到的一种能力。说不出怎么衡量，就保持现状。
3. 看回滚：开关和旧实现能不能在一次发布里切回去。切不回去的选型，验证要更充分。
4. 看生产证据和人力：谁在用、出了问题谁能修、团队里有没有人写过。
5. 用有期限的试验验证，试验前写好放弃条件。模型接口变化快，业务代码依赖自己的网关；界面技术栈保持团队熟悉的那一套。

### 15. 前端在电商大促中的稳定性保障思路是什么？

**参考答案**

保住浏览、加购和下单。推荐、营销动画和智能客服超时就摘掉。大模型不放进提交订单的链路。

大促前：入口 HTML 短缓存，静态资源带指纹并长缓存，回滚时切入口。变更冻结，灰度可以退回。配置服务失败时用内置默认：核心交易继续可用，营销和 AI 模块关闭。离线包按版本验收，并保留绕过本地包走网络的通道。开关提前演练一次。

核心接口有超时和明确的失败界面。非核心接口超时更短，失败用占位，不挡住首屏。重试有次数上限，避免把下游错误放大成重试风暴。下单按钮在请求期间禁用，提交带幂等键；超时后先查询这单有没有生成，再提示用户。

按页面看脚本错误、白屏、核心接口成功率和下单结果，相对平时基线报警。限流和拥挤时的提示文案提前准备好。
