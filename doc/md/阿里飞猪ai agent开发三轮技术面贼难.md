### 1. 自我介绍

**答题思路**

1. 基本信息：学历或工作年限、技术方向（Agent / 大模型应用 / 后端）。

### 2. 项目介绍

**答题思路**

用 STAR 加技术深度的结构：

1. 背景和目标：项目解决什么业务问题，用户是谁，为什么要用 Agent。
2. 整体架构：一句话说清链路（用户输入 → 意图识别/规划 → 检索与工具调用 → 生成 → 校验 → 输出），最好能口头画出架构图。
3. 你的职责：自己负责的模块和决策点，明确区分"我做的"和"团队做的"。
4. 难点与取舍：幻觉、延迟、上下文过长、工具调用失败等，各说一个你实际遇到的问题、你的方案和效果。

提前准备好每个环节的"为什么这么选"，因为这是后面深挖的入口。不要编造没做过的模块。

### 3. Python 和 Java 在 agent 开发中的各自优势是什么？

**参考答案**

Python 胜在 AI 生态和迭代速度，Java 胜在企业级工程和稳定性，实际中常常混用。

- **Python**：LangChain、LlamaIndex、LangGraph、AutoGen、vLLM、Transformers 等都以 Python 为一等公民；做原型、Prompt 调试、评测脚本、数据处理很快；异步靠 `asyncio`，适合 IO 密集的工具调用。短板是 GIL 限制 CPU 并行、类型约束弱、大型项目维护成本较高。
- **Java**：成熟的微服务体系（Spring Boot/Cloud）、线程模型和并发能力强、JVM 性能与可观测性工具完善，易接入公司既有的订单、支付、权限等系统；近年有 Spring AI、LangChain4j 补齐 Agent 能力。短板是 AI 生态更新慢，实验迭代成本高。
- **实践方案**：模型相关的推理、RAG、Agent 编排用 Python 服务，业务网关、权限、交易链路用 Java，两者通过 HTTP/gRPC 或 MCP 对接。

容易漏的点：说清选型依据是团队技术栈、现有系统集成和上线稳定性，不是语言优劣之争。

### 4. 解释一下 RAG（检索增强生成）的基本原理

**参考答案**

RAG 是在生成前先从外部知识库检索相关内容，把它和问题一起放进 Prompt，让模型基于证据回答，用来缓解知识过时和幻觉。

流程分两段：

1. **离线索引**：文档解析 → 清洗 → 切分（chunk，通常带少量重叠）→ Embedding → 写入向量库，同时可建立 BM25 倒排索引和元数据。
2. **在线问答**：Query（可先改写或扩展）→ 向量检索，或向量加关键词的混合检索 → 重排序（Reranker）→ 取 Top-K 拼接上下文 → LLM 生成，并要求引用来源。

优点：知识可更新、不用重新训练、答案可溯源、可做权限控制。

容易漏的点：效果瓶颈多在检索而不是生成，切分策略、混合检索、重排、召回评估（Recall@K）比换模型更关键；知识库没有答案时要让模型拒答。

### 5. 什么是三层记忆？在 agent 中如何实现？

**参考答案**

三层记忆常见的划分是短期记忆、中期（会话/情景）记忆和长期记忆，对应"当前上下文 → 会话摘要 → 持久知识"。业界说法不完全统一，面试时先说清自己的划分。

- **短期记忆（工作记忆）**：当前对话最近若干轮，直接放在上下文窗口里，用滑动窗口或 token 预算控制长度。
- **中期记忆（会话/情景记忆）**：会话较长时，把早期对话压缩成摘要，或抽取关键事实、任务状态，存在 Redis 或数据库里，按会话 ID 读取。
- **长期记忆**：跨会话保存用户画像、偏好（例如喜欢的出行方式）、历史事件，通常存向量库加结构化库，用时按语义检索再注入 Prompt。

实现要点：写入时判断什么值得记（抽取、去重、冲突更新）；读取时按相关性、时间衰减和重要性打分；注入时占用 token 预算，并做隐私与删除处理。

### 6. BERT 小模型相比大模型有哪些优缺点？

**参考答案**

BERT 这类小模型在特定判别任务上成本低、速度快、可控；大模型通用性和生成能力强，但推理成本高。

- **优点**：参数量小（BERT-base 约 1.1 亿），推理延迟低、可用 CPU 或小 GPU 部署；在分类、NER、语义匹配、Embedding、重排等任务上，有标注数据时微调效果好；可私有部署，输出稳定可控，调用成本低。
- **缺点**：BERT 是 Encoder-only，不擅长开放式文本生成；零样本和少样本能力弱，换任务就要重新标注和训练；原始最大输入长度通常是 512 token；世界知识和复杂推理弱。

在 Agent 里典型用法：意图识别、槽位抽取、检索的 Embedding 与 Reranker、安全过滤这类高频低成本环节用小模型，复杂规划和生成交给大模型。

### 7. 模型调优通常有哪些步骤？

**参考答案**

调优按"先定义问题，再用最便宜的手段，逐级加码"进行。

1. **明确目标和指标**：确定任务、评测集和上线标准，先跑一个基线。
2. **数据准备**：收集、清洗、去重、标注、划分训练/验证/测试集，保证分布贴近线上，避免数据泄漏。
3. **选方案**：优先 Prompt 工程和 RAG；不够再做微调（全参、LoRA/QLoRA 等参数高效微调）；需要对齐偏好时再做 DPO/RLHF 类训练。
4. **训练与超参搜索**：学习率、batch size、epoch、warmup、正则等，用验证集做早停。
5. **评估与错误分析**：看指标，更要抽样看 bad case，分类归因后回到数据或方案迭代。
6. **部署与监控**：量化、蒸馏或加速推理，灰度上线，监控效果漂移，持续回流数据。

容易漏的点：微调不是第一选择，知识类问题通常 RAG 更合适；微调要防止灾难性遗忘。

### 8. 提示词工程的关键技巧有哪些？

**参考答案**

提示词的核心是让任务、约束、输出格式足够明确，并用示例和结构降低歧义。

- **角色与任务**：明确身份、目标和边界，指令具体、可执行。
- **提供上下文**：给必要背景和检索证据，并限定"只能依据给定资料回答，没有则说不知道"。
- **Few-shot**：给 2 到 3 个典型输入输出示例，覆盖边界情况。
- **结构化输出**：指定 JSON Schema 或固定格式，配合结构化输出/函数调用，下游解析更稳。
- **分步推理**：复杂任务要求先拆步骤再作答（CoT），或使用规划加执行的结构，需要时让模型自检。
- **分隔与排版**：用标签或分隔符隔开指令、资料、用户输入，减少 Prompt 注入风险。
- **迭代与版本管理**：Prompt 当成代码管理，配评测集回归。

容易漏的点：模型能力和版本变化会改变 Prompt 效果，要有评测集；用户输入属于不可信内容，不能直接和系统指令混在一起。

### 9. 上下文工程在对话系统中的作用是什么？

**参考答案**

上下文工程是决定每一步给模型看什么信息：在有限窗口里，把正确的信息按正确的方式放进去，它是 Agent 效果和成本的关键。

- **作用**：
    1. 提升准确性：让模型拿到完成任务所需的指令、历史、检索证据、工具结果，减少幻觉。
    2. 控制成本和延迟：上下文越长越贵越慢，需要裁剪、压缩。
    3. 避免上下文腐烂：无关、重复、冲突的信息会干扰模型，长上下文中间的信息也容易被忽略。
- **组成**：系统提示、工具定义、对话历史、记忆、RAG 检索结果、当前任务状态。
- **常用手段**：滑动窗口、历史摘要、检索式按需加载、工具结果裁剪、重要信息放在开头或结尾、子 Agent 隔离上下文、将中间产物写到外部存储只保留引用。

它比单纯的提示词工程范围更大，包含动态组装的整个流程。

### 10. Harness 工程是什么？在 agent 开发中如何应用？

**参考答案**

Harness（脚手架/运行外壳）指围绕模型搭建的所有非模型部分，常见说法是 Agent = Model + Harness。这个词在评测里还有"测试 Harness"的含义，面试时可先确认指哪个，也可以两个都答。

- **运行 Harness**：Agent 循环（思考 → 调工具 → 观察）、工具注册与调用、权限和沙箱、上下文管理与压缩、记忆、重试与超时、错误恢复、人工确认、日志追踪。
- **评测 Harness**：加载用例，驱动 Agent 执行，Mock 外部工具和接口保证可复现，记录轨迹，自动打分（规则、LLM Judge），产出报告并用于回归。

应用场景：模型换版本或改 Prompt 时跑固定用例集做回归；用 Mock 的酒店/机票接口测试工具调用链路；线上失败轨迹回流成新用例。

容易漏的点：同一个模型在不同 Harness 下表现差异很大，Agent 效果很大程度由 Harness 决定。

### 11. 手写算法：实现一个简单的文本相似度计算函数（如余弦相似度）

**参考答案**

思路：把文本分词，转成词频向量，用余弦公式 `cos = (A·B) / (|A||B|)` 计算，范围 0 到 1（词频非负）。时间复杂度 O(n + m)，空间 O(n + m)，n、m 为两段文本的词数。

```python
import math
import re
from collections import Counter


def tokenize(text: str) -> list[str]:
    # 英文按单词切，中文按字切；生产环境中文可换成 jieba 分词
    return re.findall(r"[a-zA-Z0-9]+|[\u4e00-\u9fa5]", text.lower())


def cosine_similarity(text1: str, text2: str) -> float:
    v1, v2 = Counter(tokenize(text1)), Counter(tokenize(text2))
    if not v1 or not v2:
        return 0.0
    # 只遍历较小的字典求点积
    if len(v1) > len(v2):
        v1, v2 = v2, v1
    dot = sum(cnt * v2[w] for w, cnt in v1.items() if w in v2)
    norm1 = math.sqrt(sum(c * c for c in v1.values()))
    norm2 = math.sqrt(sum(c * c for c in v2.values()))
    return dot / (norm1 * norm2)


if __name__ == "__main__":
    print(cosine_similarity("我想去三亚旅游", "三亚旅游推荐"))
```

容易漏的点：处理空文本，避免分母为 0；词频向量不考虑语义，可换 TF-IDF 或 Embedding 向量，公式不变。

### 12. 场景题：设计一个旅游推荐 agent，需要考虑哪些模块？

**参考答案**

旅游推荐 Agent 的关键是"理解需求 → 取到真实数据 → 规划 → 可信输出"，主要模块如下。

1. **入口与对话管理**：多轮对话、会话状态、意图识别（推荐、改行程、问答、下单）。
2. **需求理解与槽位**：目的地、日期、人数、预算、偏好；缺失信息主动追问。
3. **记忆与用户画像**：短期上下文、历史偏好、出行人信息，注意隐私授权。
4. **知识与检索（RAG）**：攻略、景点、政策文档，加向量与关键词混合检索。
5. **工具层**：机票、酒店、天气、地图/路线、票价库存等实时接口，统一 Schema，带超时、重试、降级。
6. **规划与推荐**：行程规划、约束求解（时间、预算、距离），结合召回与排序，多方案对比。
7. **生成与校验**：结构化输出，对价格、库存、时间等关键事实基于工具结果生成，并做一致性校验和敏感内容过滤。
8. **交易衔接**：下单等有副作用的操作需用户确认，保证幂等和权限。
9. **评测与监控**：离线评测集、线上埋点、反馈闭环、Trace 与成本监控。

权衡：实时性强的数据（价格、库存）必须走工具而不能靠模型记忆；延迟要通过并行调用工具、缓存和流式输出来控制。

### 13. 如何评估一个 agent 的性能？

**参考答案**

要同时评结果和过程，离线与线上结合。

- **任务成功率**：按任务是否达成目标判定，是最核心指标，可用规则、人工或 LLM-as-Judge 判断。
- **过程指标**：工具选择和参数正确率、步骤数、是否陷入循环、失败恢复能力。
- **答案质量**：准确性、完整性、幻觉率、引用是否正确；RAG 部分单独看召回（Recall@K、MRR）和答案忠实度。
- **效率与成本**：端到端延迟（含首 Token 延迟）、Token 消耗、工具调用次数。
- **安全与稳定**：越权、Prompt 注入、敏感内容、结果一致性。
- **线上指标**：用户满意度、点赞点踩、转化率、人工接管率。

做法：构建覆盖典型和边界场景的评测集，固定环境（Mock 工具）保证可复现，每次改 Prompt、模型或工具都做回归；LLM Judge 要用人工标注样本校准，避免评分偏差。

### 14. 了解过哪些开源 agent 框架？

**参考答案**

按定位介绍几个主流框架，并说明选型思路：

- **LangChain / LangGraph**：LangChain 提供模型、工具、检索等组件；LangGraph 用图和状态机表达有状态、可循环的 Agent 流程，支持持久化和人工介入，适合复杂工作流。
- **LlamaIndex**：以数据接入和 RAG 见长。
- **AutoGen**：偏多 Agent 对话协作。
- **CrewAI**：以角色和任务编排多 Agent。
- **OpenAI Agents SDK**：轻量，提供 Agent、Handoff、Guardrails、Tracing 等基础抽象。
- **Dify、Coze**：低代码平台，适合快速搭建。
- **Java 生态**：Spring AI、LangChain4j。
- **协议**：MCP 用于标准化工具和数据源接入。

选型看三点：流程是否需要精确控制、团队技术栈、可观测和可维护性。框架更新很快，要说明自己真正用过哪些，避免泛泛罗列。

### 15. 在 agent 开发中，如何处理多轮对话的上下文管理？

**参考答案**

多轮对话管理的目标是在有限窗口内保留对完成任务有用的信息。

1. **会话存储**：按会话 ID 保存消息和结构化状态（槽位、任务进度），放 Redis 或数据库。
2. **窗口策略**：保留最近 N 轮原文，或按 token 预算裁剪。
3. **摘要压缩**：早期对话滚动摘要，保留事实、决定、未完成事项，不保留寒暄。
4. **关键信息抽取**：把用户偏好、约束抽成结构化状态独立存放，每轮注入，避免被摘要稀释。
5. **按需检索**：长期记忆用向量检索，只取与当前问题相关的部分。
6. **指代和改写**：把"那里"、"便宜点的"这类省略表达结合历史改写成完整查询，再检索或调用工具。
7. **工具结果处理**：大体量工具结果裁剪或只保留摘要和引用。

容易漏的点：摘要会丢信息，所以关键约束要结构化保存；上下文要考虑隔离，避免串话；提示词和工具定义放在稳定位置，有利于缓存命中。

## 二面

### 1. 自我介绍

**答题思路**

二面面对的往往是技术负责人，自我介绍要比一面更偏技术深度：

1. 一句话定位：方向和年限。
2. 重点讲一个 Agent 相关项目，突出你的独立决策，例如检索方案、记忆设计、评测体系。
3. 点出 1 到 2 个解决过的难题，用"问题 → 方案 → 结果"。
4. 说明对岗位的匹配点，以及愿意深入的方向。

与一面保持一致，不要前后矛盾；时间控制在 1.5 分钟左右。

### 2. 详细介绍一下你之前做过的 agent 项目

**答题思路**

按下面顺序讲，每个环节准备好追问：

1. **业务与目标**：解决什么问题，用户规模和约束（延迟、准确率要求）。
2. **架构**：Agent 主循环、规划方式（ReAct、Plan-and-Execute 或工作流）、工具列表、检索与记忆、模型选型。
3. **你的职责**：具体负责的模块和关键决策，说明为什么这样选。
4. **关键难点**：例如工具调用不稳定、幻觉、长上下文、延迟，各给出方案和验证方式。
5. **评测与效果**：评测集、指标、线上监控，只讲真实数据。
6. **复盘**：做得不好的地方、如果重做会怎么改。

不要编造项目或指标，没做过的部分就说"了解原理，没有落地"。

### 3. 在项目中，你是如何实现 RAG 的？用了哪些工具或库？

**答题思路**

按离线、在线两条链路讲，工具要说你真正用过的：

1. **文档处理**：数据来源、解析（PDF、网页、表格）、清洗、切分策略（按语义或结构切、chunk 大小、overlap）和选择理由。
2. **向量化与存储**：Embedding 模型、向量库（常见有 Milvus、Faiss、Elasticsearch/OpenSearch、pgvector）、元数据过滤。
3. **检索**：向量加 BM25 混合检索、Query 改写、Top-K、重排序（Cross-Encoder Reranker）。
4. **生成**：Prompt 模板、引用来源、无答案时拒答。
5. **框架**：LangChain、LlamaIndex，或自己封装。
6. **评估与优化**：召回率、答案忠实度，遇到的问题（切分过碎、召回不准）和修正。

### 4. 三层记忆的具体实现方案是什么？有什么挑战？

**参考答案**

一个常见方案如下：

- **短期**：最近 N 轮消息放在上下文，按 token 预算裁剪。
- **中期**：会话摘要加结构化状态（槽位、任务进度）存 Redis，设 TTL；会话结束或超过阈值时触发摘要。
- **长期**：用户偏好和事实经抽取后写入向量库加关系库，带用户 ID、时间、来源、置信度；检索时按语义相似度、时间衰减、重要性综合打分取 Top-K 注入。

**主要挑战**：

1. **写什么**：抽取质量，避免把闲聊或错误信息写进长期记忆。
2. **冲突与更新**：新旧偏好冲突时要覆盖或标注，不能同时注入。
3. **召回准确**：召回无关记忆会干扰回答，需要阈值和重排。
4. **成本和延迟**：摘要与抽取需要额外的模型调用，可异步执行。
5. **隐私合规**：用户可查看、删除，敏感信息脱敏。
6. **摘要失真**：关键约束用结构化字段保存，不依赖摘要。

### 5. BERT 小模型你是如何训练和调优的？

### 7. 上下文工程中，如何避免上下文溢出或信息丢失？

**参考答案**

核心是在不丢关键信息的前提下控制 token：预算管理、分层存储、按需加载。

**避免溢出**：

1. 设置 token 预算，按系统提示、工具、历史、检索结果分配额度，超出时按优先级裁剪。
2. 滑动窗口加滚动摘要，压缩历史。
3. 工具结果截断或摘要，大文件只返回片段和引用。
4. 检索按需加载，限制 Top-K，做重排和去重。
5. 拆分任务给子 Agent，各自使用独立上下文，只回传结论。

**避免信息丢失**：

1. 关键约束和用户偏好抽成结构化状态，每轮显式注入。
2. 摘要里保留事实、决定和待办，并对摘要做质量校验。
3. 原始内容落外部存储，需要时可检索回读。
4. 重要指令放在上下文开头或结尾，避免被"中间遗忘"。
5. 压缩触发要留余量，在逼近上限前进行。

6. **反馈闭环**：收集用户纠错，沉淀到评测集和知识库，定期回归。

### 11. 手写算法：实现一个简单的检索算法（如 BM25）

**参考答案**

BM25 用词频、逆文档频率和文档长度归一化给文档打分：

`score(q, d) = Σ IDF(t) · tf · (k1 + 1) / (tf + k1 · (1 - b + b · |d| / avgdl))`

其中 `IDF(t) = ln((N - n_t + 0.5) / (n_t + 0.5) + 1)`，常用 `k1 = 1.5`、`b = 0.75`（常见取值，可调）。

建索引时间 O(总词数)；单次查询是对每个文档累加查询词得分，复杂度 O(文档数 × 查询词数)。工业实现用倒排索引，只遍历包含查询词的文档。

```python
import math
import re
from collections import Counter


def tokenize(text: str) -> list[str]:
    # 中文生产环境建议用 jieba；这里按单词和单字切分
    return re.findall(r"[a-zA-Z0-9]+|[\u4e00-\u9fa5]", text.lower())


class BM25:
    def __init__(self, docs: list[str], k1: float = 1.5, b: float = 0.75):
        self.k1, self.b = k1, b
        self.docs = [tokenize(d) for d in docs]
        self.N = len(self.docs)
        self.doc_len = [len(d) for d in self.docs]
        self.avgdl = sum(self.doc_len) / self.N if self.N else 0.0
        self.tf = [Counter(d) for d in self.docs]
        df = Counter()
        for d in self.docs:
            df.update(set(d))
        self.idf = {
            t: math.log((self.N - n + 0.5) / (n + 0.5) + 1) for t, n in df.items()
        }

    def score(self, query: str, idx: int) -> float:
        score = 0.0
        tf, dl = self.tf[idx], self.doc_len[idx]
        for t in tokenize(query):
            if t not in tf:
                continue
            f = tf[t]
            denom = f + self.k1 * (1 - self.b + self.b * dl / self.avgdl)
            score += self.idf[t] * f * (self.k1 + 1) / denom
        return score

    def search(self, query: str, top_k: int = 3) -> list[tuple[int, float]]:
        scores = [(i, self.score(query, i)) for i in range(self.N)]
        scores.sort(key=lambda x: x[1], reverse=True)
        return scores[:top_k]


if __name__ == "__main__":
    corpus = ["三亚五天四晚亲子游攻略", "北京故宫门票预约指南", "三亚酒店推荐"]
    bm25 = BM25(corpus)
    print(bm25.search("三亚 酒店", 2))
```

容易漏的点：IDF 要保证非负（上面用 `+1` 的形式）；文档长度归一化由 `b` 控制；BM25 是词法匹配，常和向量检索做混合召回。

### 12. 场景题：如果 agent 在旅游推荐中给出了错误信息，如何设计反馈机制？

**参考答案**

目标是形成"发现 → 止损 → 归因 → 修复 → 回归"的闭环。

1. **收集反馈**：界面提供点踩、纠错入口并让用户选择错误类型（价格错、地点不存在、时间冲突等）；同时用隐式信号（用户重复提问、放弃下单、转人工）；加上自动检测（价格与接口不一致、实体不存在）。
2. **记录证据**：保存完整 Trace，包括用户输入、上下文、检索内容、工具调用与返回、最终回答、模型和 Prompt 版本，便于复现。
3. **即时止损**：对严重错误（价格、库存、安全信息）可对相关知识或工具结果打标，临时屏蔽或降级为"请以页面为准"，必要时转人工。
4. **归因分类**：知识库过期、检索没召回、工具返回错误、Prompt 不清、模型幻觉，对应不同修复方案。
5. **修复**：更新知识库、修正切分或检索、增加校验规则、调整 Prompt、必要时微调。
6. **回归**：把案例加入评测集，每次变更自动回归；对修复效果做灰度观察。
7. **治理**：设定告警阈值、定期复盘高频错误，防止反馈被恶意刷。

关键点：错误信息涉及交易时要用工具结果做强校验，不能只依赖事后反馈。

### 13. 在 RAG 中，你使用过 Elasticsearch 或类似搜索引擎吗？有什么优化经验？

**参考答案**

Elasticsearch 同时支持倒排索引（BM25）和向量检索（dense_vector），适合做混合检索。优化经验可以从下面几点说，只讲真正用过的：

1. **分词**：中文使用 IK 等分词器，建立自定义词典（景点、酒店等专有名词），索引和查询分词要匹配，否则召回差。
2. **混合检索**：BM25 与向量召回分别取 Top-N，再用 RRF（倒数排名融合）或加权融合，再接 Reranker 精排。
3. **字段设计**：标题、正文分字段并设置不同权重（boost），元数据（城市、类别、时间）用于过滤，缩小检索范围。
4. **Chunk 设计**：控制 chunk 大小，带标题等上下文信息，提升召回的可读性。
5. **索引与性能**：合理分片和副本数量，避免分片过多过小；向量索引用 HNSW，权衡召回率与延迟（`num_candidates`、`m` 等参数）；写入用批量（bulk）；热点查询加缓存。
6. **评估**：用标注 query 集合评估 Recall@K、MRR，调参前后做对比。

容易漏的点：优化先看召回评估，而不是凭感觉；数据更新要考虑增量同步与索引别名切换。

### 14. 如何监控和日志记录 agent 的运行状态？

### 4. RAG 中，你是如何选择检索模型的？为什么？

**参考答案**

选型的依据是评测结果，而不是排行榜名次。检索通常分两级：

1. **召回（Embedding / Bi-Encoder）**：把 query 和文档分别编码成向量，做近似最近邻搜索，速度快。选择时看：语言（中文还是多语言）、领域匹配、向量维度（影响存储和延迟）、最大输入长度、是否可私有部署和成本。常见可参考 BGE、GTE、E5 等开源系列，或商用 API。
2. **精排（Cross-Encoder Reranker）**：把 query 与候选文档拼接后打分，精度高但慢，只对召回的 Top-N 做，提升排序质量。
3. **混合检索**：向量加 BM25，弥补向量对专有名词、编号的不足。

**决策方法**：用自己业务的标注集（query-相关文档）评估 Recall@K、MRR、NDCG，对比几个候选模型的效果和延迟；效果不够再考虑用领域数据微调 Embedding 模型。

### 5. 三层记忆的设计中，如何平衡记忆的存储和检索效率？

核心是"存得精、取得准、分层放"，把高频低成本的放前面，低频大体量的放后面。

**存储侧**：

1. **选择性写入**：只写有长期价值的信息（偏好、事实、决策），闲聊不写；写入前去重、合并相似记忆。
2. **压缩**：对话摘要、事实抽取，用结构化条目取代原文。
3. **分层存储**：短期放内存或 Redis，中期放 Redis 或数据库并设 TTL，长期放向量库加关系库。
4. **遗忘策略**：按时间衰减、访问频次、重要性淘汰或归档。

**检索侧**：

1. 先按用户 ID、类型等元数据过滤缩小范围，再做向量检索，用 ANN 索引（如 HNSW）。
2. 综合相似度、时间和重要性打分，设阈值，只注入少量 Top-K。
3. 缓存热点记忆，检索和注入可异步或并行。
4. 写入异步化（摘要、抽取放后台），避免拖慢主请求。

取舍：记得越多召回噪声越大、成本越高，要用评测确认记忆是否真的提升回答质量。

### 6. BERT 小模型的训练数据是如何准备的？有什么注意事项？

**参考答案**

小模型的效果主要由数据质量决定，流程和注意事项如下。

**准备流程**：

1. **定义任务和标签体系**：标签互斥、边界清晰，写标注规范和示例。
2. **数据来源**：线上日志、人工构造、公开数据集，以及用大模型辅助生成或预标注（需人工抽检）。
3. **清洗**：去重、去噪、脱敏，过滤无效样本。
4. **标注**：多人标注，计算一致性（如 Kappa），分歧样本由专人仲裁。
5. **划分**：训练、验证、测试集，测试集要固定并贴近线上分布。

**注意事项**：

1. **防止数据泄漏**：相似或重复样本不能同时落在训练集和测试集。
2. **类别不平衡**：采样、加权损失、补充少数类数据。
3. **覆盖难例和边界**：包括口语、错别字、否定和多意图等。
4. **分布一致**：训练数据要贴近线上真实输入，而不是只有"干净"的样本。
5. **合规**：敏感信息脱敏。
6. **持续迭代**：线上错例回流，定期补充和重新评估。

### 7. 模型调优中，你是如何选择超参数的？

**参考答案**

原则是先用经验默认值跑通，再在验证集上有重点地搜索。

1. **先定基线**：采用社区常用配置，比如 BERT 类微调的学习率常在 `1e-5` 到 `5e-5` 量级，epoch 2 到 5 轮，再按任务调整。
2. **重点调敏感参数**：学习率最敏感，其次是 batch size、warmup 比例、weight decay、训练轮数；LoRA 微调还有 rank、alpha、目标模块。
3. **搜索方式**：先手动粗调，再用随机搜索或贝叶斯优化（如 Optuna），一般优于网格搜索；每次只变少量因素。
4. **评估依据**：用验证集指标选参数，用早停控制轮数，最终在独立测试集上报告结果，避免对测试集过拟合。
5. **资源约束**：先用小数据或小模型快速试验，再放大；多个随机种子验证稳定性。
6. **记录**：用实验管理工具（如 W&B、MLflow）记录参数与指标，便于复现。

学习率和 batch size 通常要联动调整；效果不好时先检查数据，不要一味调参。

### 8. 提示词工程中，如何评估提示词的好坏？

**参考答案**

提示词要用评测集和指标衡量，而不是凭几个例子的主观感觉。

1. **构建评测集**：覆盖典型、边界和历史失败样本，并给出期望输出或评分标准。
2. **定义指标**：
    - 正确性或任务成功率。
    - 格式合规率（JSON 能否解析、字段是否齐全）。
    - 幻觉率与忠实度。
    - 稳定性（同一输入多次采样的一致性）。
    - 成本与延迟（Token 数）。
3. **评分方式**：规则或脚本自动判断；LLM-as-Judge 做开放式评价，并用人工标注样本校准其可靠性；关键场景人工评估。
4. **对比实验**：A/B 对比新旧版本，一次只改一处，样本量要足够，观察差异是否显著。
5. **线上验证**：灰度发布，观察用户反馈和业务指标，并关注回归。
6. **版本管理**：Prompt 版本与评测结果绑定，模型升级后重新评测。

### 9. 上下文工程中，如何处理长文本的摘要和关键信息提取？

**参考答案**

长文本超出窗口或信息密度低时，需要"分块处理 + 层级汇总 + 结构化抽取"。

**摘要**：

1. **Map-Reduce**：切块后各自摘要，再汇总成总摘要，可并行，层数多时合并多轮。
2. **Refine（迭代）**：逐块把新内容并入已有摘要，保序但串行、慢。
3. **分层摘要**：保留章节级摘要作为索引，需要细节时再按需检索原文。
4. **查询导向**：按用户问题只摘要相关部分，比通用摘要更省。

**关键信息提取**：

1. 用结构化 Schema（JSON）抽取实体、数字、日期、结论等，并保留原文位置以便溯源。
2. 先用规则或小模型粗筛，再用大模型精抽，降低成本。
3. 对抽取结果做校验，比如数字是否在原文中出现。

**注意**：摘要会丢信息，关键事实要独立保存；切块时尽量按语义或章节边界；长上下文中重要信息放开头或结尾；摘要质量要用样本评估。

### 10. Harness 工程中，如何设计可扩展的测试框架？

**参考答案**

可扩展的关键是"用例、执行、评分、报告"解耦，用配置而不是代码扩展。

1. **用例层**：用例用统一的数据格式（YAML/JSON）描述，包含输入、初始状态、期望结果或评分标准、标签（场景、优先级）；可从线上日志自动沉淀。
2. **执行层**：统一的 Agent 适配接口，不同 Agent 或模型版本只需实现适配器；支持并发运行、超时和重试。
3. **环境层**：外部工具（机票、酒店等）用 Mock 或录制回放（record/replay）保证可复现，隔离网络波动和数据变化。
4. **评分层**：插件化的评估器，包含规则断言、工具调用轨迹检查、LLM Judge，新增指标只需注册一个评估器。
5. **报告层**：记录完整轨迹、各指标、与基线对比，支持失败用例回放，输出到看板。
6. **CI 集成**：Prompt、模型或工具变更自动触发回归，设置通过门槛。
7. **不确定性处理**：LLM 输出有随机性，需多次采样取统计结果，设合理阈值，而不是单次对比。

### 11. 手写算法：实现一个简单的对话状态跟踪器

**参考答案**

对话状态跟踪（DST）要维护当前意图和各个槽位的值，随着每轮用户输入更新，并判断是否还缺必要槽位。简单实现用规则抽取，生产中通常用模型或大模型做槽位抽取，状态更新逻辑相同。

思路：

1. 定义槽位和必填项。
2. 每轮从用户输入里抽取意图和槽位（本例用正则示意）。
3. 合并到状态：新值覆盖旧值，没提到的槽位保持不变，支持用户修改和取消。
4. 返回缺失槽位，用于追问。
5. 保存历史，便于回溯。

每轮更新时间复杂度与规则数量和文本长度成正比，状态空间为 O(槽位数 + 历史轮数)。

```python
import re
from dataclasses import dataclass, field


@dataclass
class DialogState:
    intent: str | None = None
    slots: dict[str, str] = field(default_factory=dict)
    history: list[dict] = field(default_factory=list)


class DialogStateTracker:
    REQUIRED = {"book_trip": ["destination", "date", "people"]}

    def __init__(self):
        self.state = DialogState()

    def _extract(self, text: str) -> tuple[str | None, dict[str, str]]:
        intent = "book_trip" if re.search(r"订|预订|订票|订酒店|想去|旅游", text) else None
        slots = {}
        m = re.search(r"去([\u4e00-\u9fa5]{2,4}?)(?:玩|旅游|出差|$|，|,|,|\s)", text)
        if m:
            slots["destination"] = m.group(1)
        m = re.search(r"(\d{1,2}月\d{1,2}[日号]|明天|后天|下周[一二三四五六日天]?)", text)
        if m:
            slots["date"] = m.group(1)
        m = re.search(r"(\d+)\s*(?:个)?人", text)
        if m:
            slots["people"] = m.group(1)
        return intent, slots

    def update(self, user_text: str) -> DialogState:
        intent, slots = self._extract(user_text)
        if intent:
            self.state.intent = intent
        self.state.slots.update(slots)  # 新值覆盖旧值，未提及的保持不变
        self.state.history.append({"user": user_text, "slots": dict(self.state.slots)})
        return self.state

    def missing_slots(self) -> list[str]:
        required = self.REQUIRED.get(self.state.intent or "", [])
        return [s for s in required if s not in self.state.slots]

    def reset(self):
        self.state = DialogState()


if __name__ == "__main__":
    t = DialogStateTracker()
    t.update("我想去三亚旅游")
    print(t.state.slots, t.missing_slots())  # 缺 date、people
    t.update("明天出发，2个人")
    print(t.state.slots, t.missing_slots())  # 槽位已齐
```

容易漏的点：要处理用户修改槽位和切换话题（重置状态）；正则只是示意，真实场景用 NLU 模型或 LLM 结构化抽取；状态要持久化以支持多轮。
