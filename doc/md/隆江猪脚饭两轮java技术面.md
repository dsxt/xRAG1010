### 3. Java 中有哪些方式可以创建一个线程

**参考答案**

让线程真正跑起来的是 `start`。直接调用 `run` 只是在当前线程里执行一个方法。

常见有四种写法。继承 `Thread` 重写 `run`，或者实现 `Runnable` 再交给 `Thread`，两者都没有返回值，异常要在任务里自己处理。`Callable` 配 `FutureTask` 再交给 `Thread`，可以拿到返回值，异常包在 `ExecutionException` 里。把任务提交给线程池，由 `ThreadFactory` 创建线程并复用，这是业务代码该用的方式。线程池并没有另一套造线程的机制。

Java 21 起还可以 `Thread.ofVirtual().start(...)` 创建虚拟线程，大量阻塞等待时不必按请求堆平台线程。按请求 `new Thread` 不可控，生产上用有界的 `ThreadPoolExecutor`。

### 4. 谈谈对 Java 并发包中 ThreadPoolExecutor 的理解，核心参数有哪些

**参考答案**

`ThreadPoolExecutor` 把线程数量和等待队列封死，避免业务自己无界地造线程。构造参数是七个：`corePoolSize` 核心线程数，`maximumPoolSize` 最大线程数，`keepAliveTime` 和 `unit` 控制超出核心的空闲线程何时回收，`workQueue` 是等待队列，`threadFactory` 决定线程名字，`handler` 是拒绝策略。核心线程默认一直保留，除非打开 `allowCoreThreadTimeOut`。

接纳顺序容易说反：工作线程少于核心数时，即使已有线程空闲，也会新建核心线程来接这个任务；达到核心数后先入队；队列满了才把线程扩到最大；再满才拒绝。无界队列时 `maximumPoolSize` 不会生效。`Executors.newFixedThreadPool` 的队列无界，`newCachedThreadPool` 的最大线程数是 `Integer.MAX_VALUE`，线上用构造函数把队列容量和最大线程数写明确，并给线程起业务名字。

### 5. 假设一个核心线程数为 5，最大线程数为 10 的线程池，队列长度为 100。瞬间提交 200 个任务，线程池会如何工作？拒绝策略有哪些

**参考答案**

按任务在提交期间执行不完、队列容量 100、使用默认 `AbortPolicy` 来看。前 5 个任务建起 5 个核心线程，接着 100 个进入队列，队列满后再创建 5 个非核心线程，各自直接带走 1 个任务。一共接纳 110 个：10 个在执行，100 个在排队，剩下 90 个在 `execute` 或 `submit` 时抛出 `RejectedExecutionException`。`submit` 不会把拒绝吞进 Future。空闲超过 `keepAliveTime` 后，多出来的线程回收，池子回到 5 个核心线程。

四种策略：`AbortPolicy` 抛异常，是默认；`CallerRunsPolicy` 由提交方线程自己执行，能形成反压，但会占住上游线程，池内仍然最多 10 个线程；`DiscardPolicy` 丢掉当前任务；`DiscardOldestPolicy` 丢掉队列头再尝试入队，池已关闭时仍会拒绝。也可以自己实现 `RejectedExecutionHandler`。

### 6. 什么是 ThreadLocal？使用场景是什么？用完后需要注意什么

**参考答案**

`ThreadLocal` 把变量绑在线程上，各线程读写自己的那一份，用来避免把上下文逐层当参数传递。实现上每个 `Thread` 持有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 的弱引用，value 是强引用。

典型场景是请求内的用户标识、traceId，以及 `SimpleDateFormat` 这种不宜共享的对象。Spring 的事务同步管理器也是这个思路。它不适合当隐式全局变量到处写。

线程池里线程会复用，用完必须在 `finally` 里 `remove`。否则下一个任务会读到上一次的值，大对象也会一直被线程引用。key 是弱引用，`ThreadLocal` 对象如果已经没有强引用，key 会变成 null，value 仍要等后续操作才清得掉；池化线程几乎不退出，不能指望 GC。`InheritableThreadLocal` 只在创建子线程时复制，池里的线程早于任务存在，传上下文要用任务参数，或用能包装任务的传递工具。

### 7. 在 Spring 中，Bean 的常见作用域有哪些？@Autowired 和 @Resource 注解的区别是什么

**参考答案**

`singleton` 是默认，一个容器一份。`prototype` 每次取用都新建。Web 里还有 `request`、`session`、`application`。单例里 `@Autowired` 一个原型 Bean，容器启动时只注入一次；每次都要新实例，用 `ObjectProvider` 或 `@Lookup`。把 request、session 作用域注进单例时，需要作用域代理。

`@Autowired` 是 Spring 的注解，默认按类型，多个候选时用 `@Qualifier` 或 `@Primary`，`required` 默认 true，可以用在构造器上。`@Resource` 来自 JSR-250（Boot 3 对应 Jakarta），默认按名字，名字来自 `name` 或字段名；没写 `name` 且按字段名找不到时，才退回按类型。写了 `name` 就只按名字找。它不能用在构造器上，按名字匹配时也不看 `@Primary`。构造器注入能把依赖做成 final，优先用 `@Autowired`，单个构造器时 Spring 4.3 起可以不写这个注解。

### 8. 谈谈 Spring Boot 的自动装配原理

**参考答案**

`@SpringBootApplication` 包含 `@EnableAutoConfiguration`。它通过 `AutoConfigurationImportSelector` 延迟导入自动配置类，因此用户自己的 `@Bean` 会先注册，`@ConditionalOnMissingBean` 才能让用户 Bean 压过自动配置。

候选类早期写在 `META-INF/spring.factories` 的 `EnableAutoConfiguration` 里。Boot 2.7 起主路径改为 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。导入前按 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等条件过滤，再用 `@AutoConfigureBefore`、`@AutoConfigureAfter` 排序。starter 本身多半只是依赖集合，真正创建 Bean 的是 autoconfigure 里的配置类。

排除用 `@SpringBootApplication(exclude = ...)` 或 `spring.autoconfigure.exclude`。条件是否生效可以看启动时的 conditions 报告。自己写 starter 时，条件要放在自动配置类上。

### 9. MySQL 的 InnoDB 存储引擎中，事务的默认隔离级别是什么？它解决了哪些并发问题

**参考答案**

InnoDB 默认是可重复读（REPEATABLE READ）。SQL 标准的默认是读已提交，MySQL 这里不一样。

可重复读消除脏读和不可重复读。普通 `SELECT` 是一致性读：事务里第一次建立快照之后，重复读取同一范围，看到的仍是那一版，别的事务新插入并提交的行不会出现在这次快照里。`UPDATE`、`DELETE` 和 `SELECT ... FOR UPDATE` 这类当前读会加临键锁，锁住命中的记录以及两边的间隙，锁释放前其他事务插不进这个间隙。所以在 InnoDB 里，幻读是在当前读这条路径上被临键锁挡住的。面试里把快照读和当前读分开讲。更新丢失要靠当前读的锁或版本号，隔离级别单独补不上。

### 10. 解释一下 MVCC（多版本并发控制）是如何工作的

**参考答案**

InnoDB 的普通查询不阻塞写入，靠的是行的历史版本。聚簇索引记录上有事务 ID 和回滚指针，更新时把旧版本串进 undo，形成版本链。

一致性读会拿一个 Read View：创建那一刻还活跃的事务 ID、其中最小的活跃 ID，以及下一个将要分配的事务 ID。某个版本对当前事务可见，有三种情况：事务 ID 是自己的；小于最小活跃 ID；或者大于等于最小活跃 ID、又小于下一个将分配的 ID，并且不在活跃列表里。这三种以外的版本在快照创建时都还没提交，不可见，顺着 undo 找更老的版本。

可重复读在事务第一次一致性读时生成 Read View 并一直复用。读已提交每条语句生成新的 Read View，所以能看见语句间隙里提交的修改。当前读不走这套旧版本，它读最新行并加锁。没有事务再需要的 undo 才会被清理，长事务会把版本链拖住。

### 11. user 表在 (city, age) 上建了联合索引，下面的 SQL 会用到索引吗？为什么？

表字段为 id（主键）、name、age、city。

```sql
SELECT * FROM user WHERE city = '北京' AND age = 25;
```

**参考答案**

会用到。联合索引 `(city, age)` 按 city 再按 age 排序，这条语句两列都是等值，能从最左列一直查到 age。

`age = 25 AND city = '北京'` 也一样：都是等值，优化器会调整列顺序，SQL 里的书写顺序不影响。只写 `age = 25` 则用不上这个索引的前缀查找，优化器一般全表扫描。MySQL 8.0 的 Index Skip Scan 只在左前缀区分度很低、优化器判断划算时才可能出现，不能当成默认会走索引。只写 `city = '北京'` 能用左前缀。左前缀一旦变成范围，它右边的列就不能再参与查找。`city > '北京' AND age = 25` 只能用 city 的范围，用不上 age。`city = '北京' AND age > 25` 则两列都能用。

这条是 `SELECT *`。二级索引叶子上有 city、age 和主键 id，没有 name，即便走到索引也要回表。若问覆盖索引，需要把 name 放进索引，或不要 `SELECT *`。

### 12. Redis 的持久化机制 RDB 和 AOF 的优缺点分别是什么？在生产环境中如何选择或搭配使用

**参考答案**

RDB 按时间点把内存打成紧凑快照，文件小、重启加载快，也适合做冷备。代价是两次快照之间的写入会丢，内存大时 `fork` 要复制页表，主线程可能短暂卡住。

AOF 把写命令追加到日志里。`appendfsync` 设为 always 最不易丢、也最慢；everysec 是常用折中，大约丢一秒；交给操作系统刷盘则可能丢得更多。文件更大，重放更慢。重写可以压缩体积，重写时同样要 `fork`。Redis 4.0 起重写可以前半段用 RDB、后半段接增量命令。Redis 7 进一步把 AOF 拆成基础文件和增量文件。AOF 开着时，重启优先用 AOF 恢复。

缓存丢了能回源，可以只开 RDB，甚至不持久化。不能接受长窗口丢数，就开 AOF everysec，并用混合格式缩短重启时间，再定期把 RDB 拷走做备份。两者不互相替代。

### 13. 什么是缓存穿透、缓存击穿、缓存雪崩？各自的解决方案是什么

**参考答案**

三者都是请求打到数据库，原因不同。穿透是查的数据缓存和数据库都没有，每次都穿过缓存。击穿是一个热点 key 过期，同一时刻大量请求一起回源。雪崩是大批 key 同时过期，或者缓存实例整体不可用。

穿透：入口校验非法参数。布隆过滤器把确定不存在的 key 挡住；它可能把不存在误判成存在，所以库里确认没有的结果仍要用短 TTL 缓存空值。

击穿：同一个 key 只允许一个请求回源，其余等待；或者逻辑过期，先返回旧值再异步刷新；极热的 key 可以不设 TTL，由后台更新。

雪崩：TTL 加上随机抖动；缓存做主从或集群；应用侧限流、降级，数据库侧也要有连接上限。缓存挂了要能快速失败，而不是把全部流量同步压到数据库。

### 14. Kafka 作为消息队列，它的高吞吐量主要依赖于哪些设计

**参考答案**

吞吐来自顺序 IO、批量、少拷贝和分区并行，不是把消息堆在 JVM 堆里。

分区日志只追加，落在页缓存上，消费者跟得上时读的往往是内存里的页。偏移索引是稀疏的，不必为每条消息做随机查找。Broker 把日志发给消费者时用 `sendfile` 一类的零拷贝，数据不必再拷进用户态。

生产者把多条消息攒成批再发送，可以压缩，减少请求次数和磁盘占用。消费者是拉取，用批量拉取自己控制节奏。一个主题的多个分区分到不同 Broker，消费组里的成员并行处理。

分区不是越多越快。分区过多会增加文件句柄、恢复时间和端到端延迟，数量按目标吞吐和消费者数来定。`acks` 越严格，可靠性越高，单生产者吞吐越低，这是取舍，不是默认一律最强。

### 15. 实现一个函数，判断给定的字符串是否是有效的括号序列。()、()[]{} 是有效的，([)] 是无效的

**参考答案**

用栈保存「下一个期望出现的右括号」。遇到左括号，把对应的右括号压栈；遇到右括号，栈顶必须正好是它。扫完栈要为空。空串有效。奇数长度一定无效；偶数仍要走栈，`)(` 长度是偶数但无效。时间 O(n)，空间最坏 O(n)。

```java
public boolean isValid(String s) {
    if (s == null || (s.length() & 1) == 1) {
        return false;
    }
    Deque<Character> expected = new ArrayDeque<>();
    for (int i = 0; i < s.length(); i++) {
        char c = s.charAt(i);
        switch (c) {
            case '(':
                expected.push(')');
                break;
            case '[':
                expected.push(']');
                break;
            case '{':
                expected.push('}');
                break;
            default:
                if (expected.isEmpty() || expected.pop() != c) {
                    return false;
                }
        }
    }
    return expected.isEmpty();
}
```

### 4. 在微服务架构下，如何保证分布式事务的最终一致性？了解哪些常见的解决方案

**参考答案**

跨服务写入会有一段不一致的窗口。窗口靠消费端幂等、有限重试和对账收口。

本地消息表和发件箱是同一次本地事务写下业务和待投递记录，再异步发送。RocketMQ 事务消息先写半消息，本地事务成功后再提交，结果不明由 Broker 回查。流程长就用 Saga，每步配可重入的补偿；它默认没有隔离，中间状态可能被读到。通知类用最大努力通知，并留下查询接口供对账。

TCC 和 Seata AT 代价更高。TCC 把业务拆成 Try、Confirm、Cancel。AT 在一阶段把业务更新和 undo log 放进同一个本地事务提交，并用全局锁挡住别的全局事务改同一行，直到二阶段结束；失败时用 undo log 把数据改回去，那时本地事务已经提交。状态机、幂等键和对账仍然要有。

### 5. 谈谈你对 CAP 理论的理解。在服务注册中心（如 Eureka，Nacos）的设计中，是如何权衡 CP 和 AP 的

**参考答案**

网络分区不可避免时，系统只能在「返回可能过期的数据」和「拒绝服务以保住一致」之间选。P 不是可选项。CA 只存在于不考虑分区的单机设想里。平时可以既可用又一致，CAP 说的是分区发生时的选择，不是给整个产品永久贴一个标签。

Eureka 选 AP。实例心跳注册，客户端缓存注册表。分区时各侧继续返回自己认识的实例，可能含已下线的节点。短时间大量心跳丢失会进入自我保护，暂停按心跳剔除，避免网络抖动把注册表掏空。这是宁可注册表暂时不准，也让调用方还能拿到名单。

Nacos 按数据分开选。临时实例走 Distro，偏向 AP，适合会心跳的服务发现。持久实例和配置走 Raft，偏向 CP，避免配置写进两个脑裂的值。所以不能把 Nacos 整体说成 CP 或 AP。客户端本地缓存进一步保证「注册中心短暂不可用时，已有调用还能继续」。

### 6. 如何设计一个高性能的本地缓存？需要考虑哪些方面（如过期策略、内存淘汰、并发安全）

**参考答案**

先限住容量和过期，再谈命中率。生产优先用 Caffeine 这类实现；只用 `ConcurrentHashMap` 时，过期和淘汰很容易做错。

容量按条目数或按字节权重封顶。纯 LRU 会被一次性扫描冲掉热点，访问不均时用会保护高频项的策略（Caffeine 的 W-TinyLFU 就是这个思路）。过期分写后过期和访问后过期：读时惰性删除，再用时间轮清理，不要定时扫全部 key。热点可以用异步 refresh，过期瞬间不要让所有请求一起回源。

同一个 key 未命中时只放一个加载，其余等待这次结果，加载下游时不要握着整个 map 的锁。value 用强引用。软引用的回收时机由 GC 决定，命中率和停顿都不可控。

补三样观测：命中率、加载耗时、淘汰次数。旁边还有 Redis 时，本地 TTL 更短，数据变更用消息删掉各节点上的 key。

### 7. 在 Java 应用中，如果遇到 CPU 使用率突然飙升，你的排查思路是什么？会用到哪些命令或工具

**参考答案**

先确认是不是这台机器上的 Java 进程，以及高在用户态还是内核态、是一条线程还是铺满所有核。

`top -Hp <pid>` 找出 CPU 高的线程，线程号转成十六进制，用 `jcmd <pid> Thread.print` 或 `jstack` 对上 `nid`，看是不是 RUNNABLE 以及栈停在哪。连续打两到三次，排除瞬时抖动。栈若停在 GC 线程上，就改看 GC 日志和堆，业务栈解释不了这种飙升。

要看热点方法，用 async-profiler 或 Arthas 的 `thread -n`、`profiler`。现场常见的是死循环、正则回溯、序列化、锁自旋和日志风暴。先留线程栈和一段 profiler，再决定重启。没有栈就重启，下次还是不知道原因。

### 8. JVM 的垃圾回收器中，G1 相比 CMS 有哪些改进？它是如何工作的

**参考答案**

CMS 只回收老年代，流程是初始标记、并发标记、重新标记、并发清除。初始标记和重新标记会停顿。它不整理，碎片多；并发周期没结束老年代就满了，会退化成整堆压缩，停顿很长。JDK 9 废弃，JDK 14 移除。

G1 把堆划成等大的 Region，年轻代和老年代都由 Region 组成。回收用复制，清掉的 Region 得到整理，并优先收垃圾比例高的那些。年轻代用疏散停顿；老年代占用升高后做并发标记，再以混合回收把一部分老 Region 和年轻代一起收。`MaxGCPauseMillis` 是停顿目标，不是上限。跨 Region 引用靠记忆集，写屏障和记忆集会多占内存。超过 Region 一半的对象进 Humongous 区。JDK 9 起默认收集器是 G1。疏散失败时仍会整堆回收，只是不再走 CMS 那种碎片导致的失败方式。

### 9. 线上一个接口突然变慢，你的排查链路是怎样的？从哪些维度去定位问题（数据库、缓存、代码、网络等）

**参考答案**

先划范围：只有这一个接口，还是整机、整条下游都慢；从哪个时间点开始，中间有没有发布、配置或流量变化。

看 RT、错误率、CPU、GC、线程池队列和连接池等待。有链路就找最慢的那一跳，没有链路就看这层的日志耗时打在数据库、缓存还是远程调用。

数据库看慢查询、锁等待、行数是否突然变大。应用线程堵在取连接上时，接口会慢，SQL 本身未必慢。缓存看命中率、大 key、慢查询和超时。代码看是不是新提交引入了循环调用、锁或同步阻塞。网络看超时是否成片、有没有重试风暴、DNS 或丢包。

先沿时间线对齐变更，再沿最慢的一跳往下钻。下游变慢时无上限重试会把本机线程打满，限流和超时要一起看。

### 10. 你如何看待当前 AIGC（如 ChatGPT、代码助手）对开发工作的影响？你在工作中会使用它们吗，主要解决什么问题

**答题思路**

表明会用，并把它放在「草稿和检索」，不要说成已经验证过的实现。

1. 适合交给它的：样板代码、补测试的草稿、解释一段陌生栈、整理报错和日志、SQL 草稿、列出方案对照。
2. 必须自己收口的：事务边界、并发、权限、金额和线上配置。说不出为什么对的 diff 不提交。
3. 习惯按这个顺序：先写清输入输出和约束，再看生成结果，跑过你关心的测试，最后自己对关键路径负责。
4. 对工作的影响可以收到一句：重复代码变少，读代码、划边界和排障更重要。
不要编「用 AI 独立完成了某个上线项目」。

### 11. 有没有阅读过一些知名开源框架（如 Spring，MyBatis，Netty）的源码？分享一下你的收获

**答题思路**

只讲一条你真的跟过的调用链，从入口方法到一个关键设计，三分钟内。没读过整库就说读过哪一段。类名背得很全但讲不清顺序，不如讲透一个分支。

1. 先说你原来的理解，再说源码里实际怎么做，最后落到使用时会多检查的一件事。
2. Spring 若跟过容器：讲 `refresh` 里单例怎么创建，三级缓存只解决单例的 setter 或字段循环依赖，构造器循环依赖解决不了；循环里还要代理时，提前暴露的对象可能还不是最终代理。
3. MyBatis 若跟过执行器：Mapper 接口是 JDK 动态代理；一级缓存在 `SqlSession` 上，二级缓存在 namespace 上，提交之后才对其他会话可见。
4. Netty 若跟过事件循环：一个 Channel 绑在一个 EventLoop 上，IO 线程里不能做阻塞调用；写数据是出站，从 pipeline 的尾走到头。

### 12. 如果让你设计一个短链接生成系统，你会考虑哪些关键点（如发号策略、存储、跳转、高并发）

**参考答案**

短链读多写少：生成要全局唯一，跳转是一次键查找。

发号用号段或雪花算法取唯一整数，再 base62 编码。7 位时空间大约是 62 的 7 次方，约 3.5 万亿，一般够用。不要把数据库自增原样当短码，否则可以被顺序扫完。同一长链要始终对应同一短码时，给长链哈希加唯一索引再查重。只截断哈希、不处理碰撞，不同长链会串到一起。

存储一张表即可：短码唯一索引指向长链。跳转先查 Redis，库是准的来源；极热的码再加本地缓存。

跳转返回 302。301 会被浏览器长期记住，点击统计和更换目标都会失真。点击计数丢进队列，不要堵在跳转上。生成接口单独限流。服务端只做重定向，不去请求那条长链；长链仍要限制为 http 或 https。

### 13. 如何保证你负责的系统在高并发场景下的稳定性？有哪些常用的技术手段（限流、降级、熔断等）

**参考答案**

稳定性是事先把容量和失败方式定好，而不是打满了再加机器。

限流放在网关和应用内，按接口、调用方区分。令牌桶允许短突发，超过就立刻失败，把线程和连接留给还能做完的请求。阈值来自压测出来的容量。

熔断看的是下游：错误率和慢调用超过门槛就打开，一段时间内直接失败，再到半开放少量探测。没有半开，下游恢复后流量也回不来。

降级是产品决定：压力上来时关掉非核心依赖，返回缓存、默认值或明确的提示。核心写链路要事先写明能降什么、不能降什么。

三者都依赖超时和有界资源：线程池、连接池、队列都要有上限。重试要有次数，并且只打在幂等操作上，否则重试会把限流和熔断一起打穿。舱壁用不同线程池隔开核心和旁路。工具可以用 Sentinel 或 Resilience4j，关键是阈值、半开和幂等，不是引了依赖就算接上了。

### 14. 在技术选型时，面对一个充满潜力但社区尚新的技术，和一个稳定但略显陈旧的技术，你会如何做决策？考虑因素有哪些

**答题思路**

先分这条链路错了能不能隔离、能不能回滚。核心链路偏向已经有人在相近规模下运维过的技术；新的只放在拆得开的模块里试点。

1. 对比时写清：正确性有没有人踩过坑、出故障时团队能不能自己改、观测和运维、招人难度、换掉它要动多少数据、许可证和安全补丁还在不在。
2. 「陈旧」先看是不是还在维护、问题域是不是已经熟。熟并且补丁还在，核心链路就用它。
3. 新项目要写明它补上的具体缺口，以及旧技术做不到的证据。潜力本身不是理由。
4. 试点要有退出方案：数据怎么迁回、流量怎么切走。先用一小部分真实流量验证，再扩大。
5. 性能数字只写自己测过的。决定写成一页对比，避免会上只剩谁更熟谁的名字。

### 15. 给定一个整数数组 nums 和一个整数目标值 target，找出和为目标值的两个整数，返回它们的下标。每种输入对应一个答案，不能重复使用同一个元素

**参考答案**

一遍扫描，用哈希表记下已经见过的值和下标。看 `target - 当前值` 是否出现过，出现过就返回那一下标和当前下标。先查再放入，这样不会用到自己，也能处理两个相同的值，例如 `[3,3]`、目标 `6`。平均时间 O(n)，空间 O(n)。暴力是 O(n²)。排序加双指针是 O(n log n)，还得额外保存原下标。题目保证有解。

```java
public int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> indexByValue = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = indexByValue.get(target - nums[i]);
        if (j != null) {
            return new int[] {j, i};
        }
        indexByValue.put(nums[i], i);
    }
    throw new IllegalArgumentException("no two sum");
}
```
