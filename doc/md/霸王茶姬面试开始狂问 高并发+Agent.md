### 3. 你们做奶茶点单系统，郑钦文夺冠后买一送一，早高峰小程序直接崩，第一眼你会怀疑哪几层先挂了

**参考答案**

结论：先看是不是只有小程序这条入口挂了，再沿「接入连接 → 应用线程和连接池 → 下游超时」往下找。现象在入口，根因经常在更慢的一跳把线程占死。

按这个顺序看：

1. **入口**：CDN、登录、网关的 5xx 和耗时。只有小程序超时、门店自取仍正常，就先拆入口，不要当成全站宕机。
2. **连接和线程**：网关到上游的连接、Tomcat 或 Netty 线程、HTTP 客户端连接池、数据库连接池。瞬时流量进来后，慢请求不返回，池子先满，后面的请求全部排队。
3. **热点缓存**：爆火门店的菜单、库存打在同一个分片上，这一分片延迟抖动，读接口跟着超时。
4. **数据库**：订单插入、库存和券的行锁。连接池等待出现在拿连接或等锁上。
5. **下游**：券、库存、门店接单如果同步调用且没有熔断，会把上面每一层的线程都拖死。看超时堆栈停在哪一跳。

容易漏：小程序「崩」有时只是静态资源或登录态，核心下单服务还活着。先用一条门店通道的成功请求把范围圈小。

### 4. 网关层怎么防瞬时流量把连接池打满，令牌桶和漏桶你选哪个，为什么

**参考答案**

结论：入口用令牌桶限平均速率，并单独限制最大在途数；超限直接拒绝。漏桶放在只允许匀速写入的内部通道上，例如给出餐系统喂单。

连接池被打满，看的是同时挂着的请求和它们占住连接的时间。网关如果把突发收进内存队列，连接在排队期间已经占上了。所以入口限流要快速失败，返回 429，而不是在网关里堆长队列。下游超时要短，避免慢调用一直占着连接。

令牌桶以固定速率补令牌，桶容量就是允许的突发上限。早高峰本身有短抖动，这样正常突发能过去，长期平均速率仍受控。Spring Cloud Gateway 的 Redis 限流器就是令牌桶，配置项是补充速率和桶容量。Nginx 的 `limit_req` 是漏桶思路，`limit_conn` 才是在限连接数。

漏桶的出口速率恒定，适合下游只能匀速消化的写。用在小程序入口上，正常的短突发也会被抹平，用户感觉全部变慢。Sentinel 默认流控是时间窗口里的 QPS 直接拒绝；匀速排队才接近漏桶。它和令牌桶不是同一个东西。

容易漏：只限 QPS、不限并发，少量超慢请求照样能把池子占满。速率、在途数、超时要一起设，并且从网关到数据库逐跳变短。

### 5. Redis 在奶茶点单里存门店状态、菜单、优惠券，热点门店 Key 怎么设计才不会倾斜

**参考答案**

结论：菜单和门店状态拆成小 key，读走本地缓存；不要给同一家店的所有 key 加同一个 hash tag。库存扣减做不到完全没有热点，因为一次原子扣减必须落在一个 key 上。

可以这样拆：

- 门店状态：`store:{storeId}:status`，值很小，本地缓存秒级。
- 菜单：`menu:{storeId}:ver` 只存当前版本，正文放 `menu:{storeId}:v:{version}`。正文发布后不变，本地按版本缓存。
- 券模板：`coupon:tpl:{templateId}`。用户的券按 `coupon:user:{userId}` 走，天然随用户散开。
- 库存：`stock:{storeId}:{skuId}`，只给扣减用。展示库存读本地或单独的展示缓存，不拿本地缓存里的数字去扣。

Redis Cluster 里，key 不加同一个 hash tag，菜单和库存会落到不同 slot，读菜单不会和扣库存抢同一分片。只有一条 Lua 必须同时改的几个 key 才共用 tag。把一家店的全部 key 都标成 `{storeId}`，热点门店会更斜。

库存这个 key 仍然会热。前面用限流把写压下来；展示读不要打到它。库存很大、单分片写不过来时，再拆成多段，每段自己原子扣，扣完一段再试下一段。段里的余量要能回收。100 杯这种小库存不适合先拆段，尾数会卡在某一段里。

容易漏：hash tag 解决的是同槽，不是热点。本地缓存可以挡读，不能拿来做扣减。

### 6. 缓存穿透、缓存击穿、缓存雪崩在“查某个爆火门店库存”这个场景里分别怎么发生，怎么防

**参考答案**

结论：穿透是在查不存在的门店或 SKU，击穿是这一家爆火门店的 key 刚好失效，雪崩是一批 key 一起没了或 Redis 整体不可用。三件事先分开，再谈怎么防。

查库存如果是「缓存没有就回源 MySQL」：

- **穿透**：活动脚本拿不存在的 id 来刷，缓存永远不命中，请求全到数据库。先校验 id 是否在已知门店和 SKU 集合里。布隆过滤器说「没有」就可以直接拒绝；它说「可能有」仍要查后面，挡不住全部穿透。也可以缓存空值，TTL 要短，新店开业时删掉这个空值。
- **击穿**：这家店的 key 在高峰过期，大量请求同时回源，打爆这一行。热点展示 key 用逻辑过期：值里带失效时间，过期后先返回旧值，只放一个请求去刷新。没拿到刷新权的请求不要堵在锁上，否则线程池会被等锁打满。扣减不用这种会过期的缓存当账。
- **雪崩**：各门店库存 key 设了相同 TTL，一起过期；或者 Redis 宕机，查询全部落到 MySQL。TTL 加随机抖动，热点提前预热。缓存整体不可用时，库存查询限流，扣减停在条件更新上，不为了展示把数据库打穿。

容易漏：爆火门店一直被访问，更常见的是击穿和热 key。把单个热 key 过期说成雪崩，口径就错了。

### 7. MySQL 订单表如果按门店号分表，用户查“我的全部订单”怎么查，跨分片分页怎么处理

**参考答案**

结论：按门店分表服务的是店内履约。用户查自己的订单，要另有一张按用户分片的索引，不能每次把所有门店分片扫一遍再合并。

下单时，订单主表按 `storeId` 落库。同时记一条用户索引：`userId`、`orderId`、`storeId`、下单时间、状态、金额，表按 `userId` 分片。两张表不在一个库里，不能塞进同一个本地事务，用可靠消息补索引。用户刚下完的那一笔，用下单接口的返回插在列表前面，不靠异步索引来做读己之写。

列表只查这一张索引，详情再用 `orderId` 加上索引里的 `storeId` 回主表。订单号里如果没有门店号，索引里必须带 `storeId`，否则拿到单号仍不知道去哪张表。状态变更也走消息更新索引。列表可以短暂落后，详情以主表为准。

分页在用户这一个分片里做 seek：`user_id = ? AND (created_at, order_id) < (?, ?) ORDER BY created_at DESC, order_id DESC LIMIT ?`。不要用很大的 `OFFSET`。

如果暂时没有用户索引、只能跨门店分片：每一页带上「每个分片自己的游标」，各分片从游标再取一小批，内存归并。页码越深也不能改成各分片同一个 offset。分片一多，每一页都要打全部库，只能当过渡。搜索引擎有近实时延迟，刚写完的订单不一定立刻能查到，订单列表仍以用户索引为准。

### 8. RocketMQ 和 Kafka 在订单异步化、门店出餐通知里怎么选，为什么要消息队列而不是直接同步写

**参考答案**

结论：下单主链路只同步做订单落库和库存预扣。门店接单、打印、积分、通知放到消息后面。订单、券、超时关单用 RocketMQ；纯进度流水如果已经有 Kafka，可以走 Kafka。一个团队没有两套设施时，RocketMQ 够覆盖这个场景。

同步把这些全写完，任一跳变慢，用户侧的下单就超时。消息队列把「单已经成立」和「门店稍后接到」拆开：门店系统短时不可用，消息堆着，恢复后续上，而不是让用户下单失败。早高峰的写入也被拉平。

RocketMQ 对这条链路更直接：半消息用来对齐本地事务，延迟消息做超时关单和解冻券，按 `orderId` 选择队列可以保证同一订单有序，失败有重试和死信，标签能把出餐、退款分开。茶饮订单的量级用它足够。

Kafka 吞吐更高，保留和回放适合销量流水、大屏聚合。它的事务解决的是「消息和消费位点」一起成功，不是「订单库事务和发消息」这件业务事。延迟消息和死信要自己做。出餐进度如果只是通知和指标，按 `storeId` 分区可以；丢一条或重复一条都要业务幂等。

容易漏：消息队列不提高下单接口里那几步同步调用的速度。主链路没减负，后面加队列只是把超时挪了个地方。

### 9. AI Agent 场景：让用户用自然语言说“帮我给公司楼下霸王茶姬点两杯伯牙绝弦，用买一送一券”，后端要不要让大模型直接扣库存，边界在哪

**参考答案**

结论：不能让大模型直接扣库存。模型只负责把这句话收成草稿，库存、券和价格由服务端在用户确认后原子执行。

这句话里要收的是：哪一家店、SKU、两杯、规格、要用买一送一券。模型可以调只读工具查附近门店、当前菜单、这张券是否可用。查到的价格和规则只是展示，口播的金额不算数。

边界划在写操作上：

- 扣库存、核销券、创建订单不暴露成模型可以随便调的工具。
- 服务端按菜单重新计价，按促销规则重新判断券能不能用、两杯是否都满足。模型说「可以用」没有效力。
- 确认卡上的门店、杯数、金额来自服务端草稿。用户确认后，才用这一份草稿的幂等键调订单服务。
- 订单服务里用 Lua 或数据库条件更新扣库存。这一步没有模型参数。

模型会编出门店、用错券、同一句话调用两次。库存和券是账，要能审计、幂等、回补。只读可以交给模型，写必须交给订单领域服务。

### 10. Agent 调门店查询 API、优惠券核销 API、下单 API 时，模型乱填参数怎么办，怎么校验和兜底

**参考答案**

结论：工具层不信任模型填的参数。格式不对直接拒绝；门店、SKU、券必须能在服务端候选集里对上。核销和下单不要拆成两次由模型自由编排的副作用。

1. 工具定义写成 schema，缺字段、类型错、枚举越界，请求发不出去。把校验错误交回模型，允许它改，限制 1～2 次。同一组参数再出现就停下，改问用户。
2. 门店 id 只能来自上一跳「附近门店」写进会话的候选。SKU 必须属于该店当前菜单，券必须属于这个用户且状态可用。用户 id 从登录态取，不从模型参数取。
3. 业务拒绝（打烊、售罄、券互斥）是确定失败。把原因告诉用户，不要让模型换一家店或换一张券再自动下单。
4. 写操作收成一个「提交已确认草稿」。幂等键用 `userId + draftId`。核销和建单在服务端一个流程里完成。超时先按这个键查结果，查到就返回原单，查不到才允许重试。
5. 必填项补不上，用固定话术一次问一件：哪家店、几杯、甜度。步数或追问次数到上限，就留草稿或转人工。

容易漏：校验不只有类型。模型没见过的 id，不允许它编一个填进去。

### 11. Spring Boot 里接口限流、降级、超时一般怎么落地，Resilience4j 和 Sentinel 你更熟哪个

**参考答案**

结论：超时以 HTTP 和数据库客户端自己的超时为准；限流放在入口和少数写接口上；熔断必须带降级逻辑。应用内嵌入用 Resilience4j 更直接，要控制台动态改规则、网关统一限流，用 Sentinel。面试时讲自己项目里真正用过的那个。

落地时三件事分开：

- **超时**：连接超时和读超时设在 RestTemplate、WebClient 或 Feign，以及数据库连接池上。从网关到下游逐跳变短。Resilience4j 的 TimeLimiter 只负责计时，阻塞 IO 不放进独立线程池并取消，调用线程还是占着。
- **限流**：网关令牌桶挡总入口。下单、核销再按用户限更小的配额，超了快速失败。Resilience4j 的 RateLimiter 是令牌桶。Sentinel 默认按窗口统计 QPS 后拒绝，匀速排队才把通过速率抹平。排队窗口要很小，否则线程还是堆在队列里。
- **熔断和隔离**：下游错误率或慢调用比例上去，熔断打开，菜单走本地缓存，券服务挂了就隐藏券，而不是让整单卡住。查询线程池和下单线程池分开。半开只放少量探测。

Resilience4j 以装饰器或注解嵌在 Spring Boot 里，指标进 Micrometer，规则多在配置里。Sentinel 有控制台和网关适配，热点参数限流更完整；规则在内存里，不接到配置中心，重启就没了。

容易漏：熔断以后如果没有降级，只是失败得更快。库存扣减不能降级成「先让下单成功」。

### 12. 项目里最有价值的一个技术决策是什么，为什么不是加机器

**答题思路**

讲一个你真实做过的决策。下面是组织方式，项目名和数字用你自己的。

1. **决策**：用一句话说清你改了哪条边界。例如把券核销移出下单同步链路、给库存做了预扣和回补、或把某个热查询从数据库前移到缓存。不要同时讲三件。
2. **当时的约束**：峰值在哪、哪一段已经超时、一致性要强到什么程度、能改动的时间有多少。
3. **为什么不是加机器**：先说瓶颈在不在 CPU。热 key、单行锁、同步调用被下游拖死、没有幂等，加实例只会把同一把锁或同一个 key 打得更重。机器解决的是无状态计算不够，解决不了错误的调用边界。
4. **你怎么验证**：压测看的是连接池等待和锁等待，不只是 QPS；上线后看对账差和超时比例。用你真实看过的现象。
5. **代价**：最终一致的空窗、回补任务、排查变复杂。说明你当时接受了哪一个。

如果这个项目里最有价值的确实是扩容，就讲清你先去掉了什么同步依赖，扩容才生效。不要为了这道题硬编一个架构故事。

### 13. 手写算法：给定一个订单列表，按门店分组后每个门店取金额前 K 大，写出来

**参考答案**

每个门店维持一个大小为 K 的堆，堆顶是当前「最不该留下」的订单：金额更小，金额相同则订单号更大。扫到一笔单，先入堆，大小超过 K 就弹出堆顶。这样每个门店只留下金额最高的 K 笔，金额相同保留订单号更小的。

全部分组后再按金额从高到低排序，金额相同按订单号从小到大。直接对每个门店排序是 O(n log n)。堆的做法是 O(n log K)，额外空间 O(门店数 × K)。金额用分，类型用 long。订单号相同才视为同一笔；比较器不要把两笔不同的单比成相等。

K 不大于 0 或列表为空，返回空。某家店不足 K 笔，有多少留多少。

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.PriorityQueue;

public class TopOrders {
    public static final class Order {
        public final String storeId;
        public final String orderId;
        public final long amount;

        public Order(String storeId, String orderId, long amount) {
            this.storeId = storeId;
            this.orderId = orderId;
            this.amount = amount;
        }
    }

    public static Map<String, List<Order>> topKByStore(List<Order> orders, int k) {
        if (k <= 0 || orders == null || orders.isEmpty()) {
            return Map.of();
        }
        Comparator<Order> dropFirst = Comparator.comparingLong((Order o) -> o.amount)
                .thenComparing(o -> o.orderId, Comparator.reverseOrder());
        Map<String, PriorityQueue<Order>> heaps = new HashMap<>();
        for (Order order : orders) {
            PriorityQueue<Order> heap = heaps.computeIfAbsent(
                    order.storeId, id -> new PriorityQueue<>(dropFirst));
            heap.offer(order);
            if (heap.size() > k) {
                heap.poll();
            }
        }
        Comparator<Order> showOrder = Comparator.comparingLong((Order o) -> o.amount)
                .reversed()
                .thenComparing(o -> o.orderId);
        Map<String, List<Order>> result = new HashMap<>();
        for (Map.Entry<String, PriorityQueue<Order>> entry : heaps.entrySet()) {
            List<Order> top = new ArrayList<>(entry.getValue());
            top.sort(showOrder);
            result.put(entry.getKey(), top);
        }
        return result;
    }
}
```

### 2. 郑钦文夺冠活动里，小程序崩了但门店自取还能进，外卖入口卡死，你会怎么拆流量入口和核心链路

**参考答案**

结论：小程序和外卖是入口故障，门店自取还能进，说明订单服务没有整体死掉。按入口隔离，再把核心链路收成「下单 + 库存或券 + 已接订单的出餐」。

入口拆开：

- 小程序、门店自取、外卖三条路，用不同的网关路由、限流配额和线程池。外卖把连接占满时，自取仍能进。
- 静态资源、登录、菜单、提交下单也拆开。菜单可以走缓存；提交失败要明确返回，不要转圈。
- 外卖卡死，常见原因是同步询价、询配送把线程拖住。外卖频道单独限流；询价失败就提示改自取，不再占用自取的线程。

链路拆开：

- 核心只保留创建订单、库存预扣、支付或到店接单、出餐状态。这些依赖尽量少。
- 配送费、推荐、积分、点单助手都是非核心。超时就关掉，不回压到下单。
- 活动开关要能单独关买一送一展示、关助手、关外卖。门店自取和新单是否继续接，看门店产能，不跟小程序是否恢复绑在一起。

先保住已经接单的出餐状态，再决定还接不接新单。容易漏：把三个入口的线程池配成共用，隔离在配置上等于没做。

### 3. 买一送一券核销和订单创建要保证最终一致，不用强分布式事务，你会用 RocketMQ 怎么串起来

**参考答案**

结论：券先按幂等键冻结，订单服务用事务消息保证「订单落库」和「核销消息」一起成立。券服务把冻结改成已核销。不用 XA。

用户确认用券时，如果完全异步核销，会出现单在、券没用上，或者券没了、单没有。所以提交前先同步冻结，冻结键用 `userId + couponId + clientToken`，并带过期时间。超时就按这个键查询，不盲重试成两次冻结。冻结失败就不创建订单。

订单服务侧：

1. 发半消息，对消费者不可见。消息体带 `orderId`、`couponId`、`userId`，key 用 `orderId`。
2. 执行本地事务：插入订单，券状态记为已冻结。成功就 commit 消息，失败就 rollback，并尽力解冻。
3. broker 没收到二次确认就回查库。订单在且仍待核销，提交消息；订单不存在，丢弃消息；本地事务还没结束，返回未知，稍后再查。回查读的是库，不是本机内存。

券服务按 `orderId + couponId` 幂等消费，把冻结改为已核销。券已失效就走补偿：取消订单或改成原价，由订单状态机决定，不是无限重试。超时未支付用延迟消息关单并解冻，解冻同样幂等。

对账扫「订单已在、券长时间停在冻结」的记录。消费者仍可能收到两次，幂等要单独做，半消息保证不了消费只发生一次。

### 4. 事务消息半消息、本地消息表、最大努力通知，这个奶茶下单场景你选哪个，为什么

**参考答案**

结论：券核销选半消息。本地消息表能做到同等的「库和消息」一致，扫描和抢占要自己写。最大努力通知只用于出餐提醒、积分这类丢了可以再补、且不影响券和库存的通知。

半消息是先发一条不可见的消息，再做订单本地事务，然后提交或回滚。提交请求丢了，靠回查订单决定这条消息的命运。实时性比扫表好，也少维护一张消息表。代价是绑在 RocketMQ 的事务消息上，回查接口要幂等，并且要能区分「事务还没做完」和「事务已经回滚」。

本地消息表是订单和一条待发送记录写在同一个本地事务里，后台任务再投递。存储自己掌握，不挑消息队列品牌，排查时能直接看表。代价是扫描延迟、任务要抢占，订单库高峰时还要避免扫表把库扫热。RocketMQ 回查不稳定，或团队不能用事务消息时，用这一种。

最大努力通知是业务做完后再尽力推给对方，对方幂等，丢了靠查询补。支付渠道回调常常这样，因为有主动查单。券如果只是「尽量通知」，消息丢了就会长期不一致，用户已经享受了优惠。这个保证不够。

容易漏：半消息提交成功，消费者仍会重复。三种方案都替代不了消费端幂等。

### 5. 库存只有 100 杯，10 万人抢“买一送一资格”，怎么防止超发，Redis 预扣减失败后怎么回补

**参考答案**

结论：10 万个请求挡在限流和 Redis 原子预扣之外，只有按杯数扣减成功的请求才写订单库。预扣动作本身失败是售罄，不能加回库存。预扣成功但订单没立住，才回补，而且只回补一次。

防超发：

- 用一段 Lua 判断剩余杯数并扣减，同时写下 `hold:{token}`。不要在 Java 里先 GET 再 SET。
- 一人一单的资格 key 按用户散开。Cluster 里资格 key 和库存 key 不在一个 slot，一条 Lua 跨不了 slot。两步之间失败，靠 token 和对账补，不要假设集群里一条脚本能同时原子地做完这两件事。单机 Redis 上可以放在同一个脚本里。
- 同一个请求号重复提交，命中已有 token，不能再扣一次。
- 100 杯不要拆给每个应用实例预分，尾数会卡在某个实例上。单 key 前面加上入口限流即可。库存很大、单分片写满时才考虑分段。

回补：

- Lua 返回库存不足：直接售罄，禁止 INCR。
- 预扣成功后写订单。写库失败，执行回补脚本：只有 hold 还在才把杯数加回并删掉 hold。
- 调用超时先按请求号查订单。查到单就确认 hold，不能回补，否则这杯会再卖给下一个人。查不到单再回补。
- 进程在预扣之后、写订单之前崩溃：定时任务扫过期 hold，先问订单库，没有订单才回补。不要只靠 Redis 过期通知，通知会丢。
- 账本放在数据库条件更新：`remain >= 扣减量` 才更新。Redis 是漏斗。两边不一致时，以已经成立的订单重放扣减。

### 6. 分布式锁用 Redis 实现，主节点挂了从节点没同步锁，怎么解，Redlock 你信不信

**参考答案**

结论：主从异步复制的锁会丢。库存和券的正确性不要押在这把锁上，用原子扣减或数据库条件更新。Redlock 我不会当成资金链路的依据。

`SET key token NX PX` 写在主节点上。主节点宕机时，这个 key 可能还没复制到被提升的从节点，另一个请求会再次拿到锁。`WAIT` 只能多等几个副本确认，故障切换仍可能提升一个没收到这次写的节点，它不是共识。

锁还有第二个洞：持有者 GC 停顿或网络超过 TTL，锁过期，两方都以为自己持有。所以即使用单机 Redis，锁也只是减少冲突，不是账。

可以这样做：

- 超卖问题用上一题的 Lua 或 `UPDATE ... WHERE remain >= ?`，不把 10 万人串在一把锁后面。
- 还需要锁时，例如同一订单的状态迁移，锁值用单调递增的 fencing token。写数据库时带上这个 token，库拒绝更小的 token。旧持有者在锁过期后继续写，会被拒绝。
- 释放锁用 Lua 比较 token 再删，不能直接 DEL。
- 需要租约本身可靠时，用 etcd 或 ZooKeeper 这类多数派确认后再发租约的系统。

Redlock 是向多个独立主节点加锁，超过半数且耗时小于 TTL 才算成功。它依赖时钟和「进程不会停太久」这些假设；主节点重启丢数据时也会坏。Redis 作者认为在工程故障模型下可用，Martin Kleppmann 认为它做不成一个可靠的分布式锁。争议先讲清楚，然后给出生产选择：锁可以减少并发冲突，正确性看 fencing token 和数据库约束。

### 7. 门店出餐慢、订单积压 700 杯，消费者组堆积了，怎么保证订单状态和门店大屏最终对齐

**参考答案**

结论：订单表是状态真相，大屏是投影。700 杯是产能积压，消费者 lag 是同步变慢，两件事分开处理。大屏允许延迟，不能把旧状态覆盖新状态。

状态只在订单服务里按状态机修改，然后发消息。消费端更新大屏时带单调版本号：`WHERE order_id = ? AND version < ?`。更新行数为 0，说明是旧消息，直接丢掉。不要用机器本地时间比先后。

消费用并发，靠版本号挡住乱序。同一门店如果上了严格顺序消费，一条坏消息会堵住这家店后面的投影。失败记下来再补，不要让整条队列停住。

处理堆积时先看消费时间花在哪。如果是同步等咖啡师做完，就把消费改成只更新大屏和通知。多加消费者只能加快投影，不能加快出杯。队列超过门店产能，就停止接新单或改成预约取餐，把预计等待写回用户侧。

对齐靠两条：

- 按 `orderId + 目标状态` 幂等，重复消息不会把大屏打乱。
- 定时按门店拉取未完成订单的快照，覆盖本地投影。700 笔的全量对账成本可以接受。死信单独处理，不能让一笔单永远停在「制作中」。

容易漏：大屏自己维护一套可以被任意消息覆盖的状态，后到的「制作中」会把「已完成」盖掉。

### 8. ES 在“附近门店+饮品名模糊搜+销量排序”里怎么建索引，分词和地理查询怎么配合

**参考答案**

结论：一篇文档表示「某店在售的一杯饮品」，冗余门店坐标。地理和在售放在 filter 里，饮品名参与匹配，排序用销量。价格和真实库存仍以菜单服务为准，不读索引里的旧数字。

```json
{
  "mappings": {
    "properties": {
      "storeId": { "type": "keyword" },
      "location": { "type": "geo_point" },
      "drinkName": {
        "type": "text",
        "analyzer": "ik_max_word",
        "search_analyzer": "ik_smart",
        "fields": { "raw": { "type": "keyword" } }
      },
      "sales": { "type": "long" },
      "onSale": { "type": "boolean" }
    }
  }
}
```

索引用 `ik_max_word`，搜索用 `ik_smart`，需要 IK 插件。「伯牙绝弦」这类品牌名放进词典，同时保留 keyword 子字段做整词匹配，整词命中的权重更高。不要用前置通配做模糊搜。

查询时，`onSale` 和 `geo_distance` 放在 filter 里，不参与评分，距离按产品给的范围填。`match` 饮品名，按 `sales` 降序。`storeId` 用 collapse，避免同一家店因多款相近饮品重复出现。要展示命中的那一杯，再取 inner hits。text 字段不能用来排序。

分页用 `search_after`，不用很深的 from/size。销量按一批订单回写，不在每杯完成时同步改 ES。门店搬迁要更新这家店全部饮品文档的坐标。上下架要能马上改 `onSale`，查询把下架滤掉。

### 9. AI Agent 做智能点单助手，RAG 知识库里放门店菜单、活动规则、过敏提示，文档更新后旧内容还被召回怎么处理

**参考答案**

结论：更新不是再插入一份。每份知识有 docId、版本和生效区间，检索只拿当前版本。菜单价格、是否在售、库存不走 RAG。

入库时先写好新版本的切片和向量，metadata 带上版本、`effectiveAt`、`expireAt`。然后把「当前版本指针」拨到新版本，检索条件带上这个版本，再异步删旧切片。先删后插会有一段空窗，新旧同时留着又会把过期活动召回。

查询过滤 `effectiveAt <= now` 且未过期。活动文案过期必须滤掉，不能只比相似度。检索缓存按 docId 失效，避免模型上下文里还钉着旧段落。

过敏原没有命中当前版本文档，就说以门店公示为准，不拿旧文生成。即便召回了旧活动说明，下单前仍由促销引擎否决。知识库负责解释，不负责成交。

容易漏：只换模型或加大 topK，旧切片还在索引里，该召回的还会回来。

### 10. 大模型回答“这杯买一送一券能和会员折扣叠加”是瞎编的，这种幻觉在交易系统里怎么拦

**参考答案**

结论：能不能叠加、金额是多少，只认促销引擎。模型可以转述引擎的原因码，不能自己生成这句承诺。说错了的那一次也不能进核销。

涉及券、价格、互斥的问题，先调 `checkPromotion`，入参是门店、SKU、券、会员。返回能不能叠加和原因码。服务端用模板把原因码填成用户能看的句子。本轮没有成功的计价结果，回复里却出现「可以叠加」「已减免」，就换成固定话术。

下单和核销再判一次券模板上的互斥组。确认卡上的金额来自报价单。模型文本不参与记账。

知识库里的活动说明只能当解释。文档和引擎冲突时以引擎为准。上线前把「叠加、互斥、过期券」做成固定用例，答错就阻断发布。线上留下工具轨迹，方便对是哪一次没调引擎。

容易漏：只在系统提示里写「不要编造」。提示挡不住已经生成的承诺，挡得住的是工具结果和核销前的再次校验。

### 11. Agent 多轮对话里用户改地址、改杯数、改甜度，上下文和订单草稿怎么存才不会串单

**参考答案**

结论：会话、草稿、订单三套 id 分开。聊天记录不是订单。改甜度、改杯数只改当前这份草稿，已提交的草稿冻住。

- `sessionId` 是对话通道。Redis 里存最近几轮和当前 `draftId`，key 带登录态里的 `userId`。
- `draftId` 是一份未提交意图：门店、履约方式、地址 id、行项目（SKU、杯数、甜度、冰量）、券、版本号。
- `orderId` 在提交成功后才有。之后再说「改甜度」，是新草稿或走改单接口，不改已经支付的那一笔。

用户 id 从登录态取。地址用地址簿里的 `addressId`，改的时候重新校验配送范围。服务端以草稿里最后一次确认的地址为准，不让模型从历史句子里挑一个旧地址。

同一份草稿的工具调用串行执行，更新带版本号，版本冲突就重读再改。两个并行工具会互相覆盖杯数和甜度。每轮注入的是服务端渲染的当前草稿，不把别的会话拼进来。

提交的幂等键是 `userId + draftId`。成功后草稿变为已提交。草稿过期就释放预占。多端同时点可以有多份草稿，一个会话只指向其中一份。

### 12. 你们项目里最复杂的一个异步链路讲讲，排查过消息重复消费吗，幂等键怎么设计

**答题思路**

讲一条你真实跟过的链路。没有排查过重复消费，就不要编「我们做过」；把下面的键设计当成你会怎么做，并说清楚这是方案。

1. **链路**：按顺序列出同步和异步。例如订单本地事务、发消息、券或库存、门店投影、通知。标出哪一跳会至少投递一次。
2. **重复从哪来**：消费成功但应答丢了，同一条消息会再来。生产方超时后重发，是另一条消息，消息 id 变了，业务动作没变。只按消息 id 去重，第二类挡不住。
3. **键**：用业务主键加动作，例如 `orderId + 目标状态`，或 `orderId + couponId + REDEEM`。一人一张的券用 `userId + campaignId`；一单一张用 `orderId + 券模板`。先把粒度说清楚。
4. **怎么落**：幂等记录和业务写入放在同一个本地事务里。外部 HTTP 则先把键置为处理中，对方也按这个键幂等，超时先查询。状态机用 `WHERE status = 旧状态`，更新行数为 0 就当重复。
5. **你怎么查到的**：唯一键冲突、对账差、用户侧重复通知。讲你真实看过的那一种，以及死信和对账怎么补洞。

最复杂不要选成「发一条短信」。面试官要的是有分支、有重试、有账的那条。

### 13. 手写算法：模拟虚拟排队，给定用户到达时间和门店每秒出杯数，算每个用户开始制作的时间

**参考答案**

先把口径定下来：每个用户一杯，门店一条制作线，每秒做 `rate` 杯，所以一杯占用 `1/rate` 秒。用户还没到，机器空着等他；用户到了但上一杯还占着机器，就要排队。开始时间是到达时间和机器空闲时间的较大值。

同一时刻按输入顺序排，保证结果稳定。时间用整数刻度，1 个刻度等于 `1/rate` 秒，避免用 double 比大小。返回值除以 `rate` 才是秒。时间 O(n log n)，空间 O(n)。`rate <= 0` 直接拒绝。

例如到达 `[0, 0, 0]`、每秒 2 杯，开始时间是 0 秒、0.5 秒、1 秒。到达 `[5, 1, 1]`、每秒 1 杯，按原下标的开始时间是 5 秒、1 秒、2 秒。

如果「每秒出杯数」指的是并行工位数、每个工位每秒一杯，就改成小根堆维护各工位的空闲时间。两种模型在同一秒到达的人身上结果不同，写代码前先跟面试官确认。一人多杯时，把占用从 1 个刻度改成杯数。

```java
import java.util.Arrays;
import java.util.Comparator;

public class CupQueue {
    /** 返回值单位是 1/rate 秒。实际秒数 = scaled / (double) rate。 */
    public static long[] startScaled(long[] arrivalSeconds, int rate) {
        if (rate <= 0) {
            throw new IllegalArgumentException("每秒出杯数必须大于 0");
        }
        if (arrivalSeconds == null || arrivalSeconds.length == 0) {
            return new long[0];
        }
        int n = arrivalSeconds.length;
        Integer[] order = new Integer[n];
        for (int i = 0; i < n; i++) {
            order[i] = i;
        }
        Arrays.sort(order, Comparator.comparingLong((Integer i) -> arrivalSeconds[i])
                .thenComparingInt(i -> i));
        long[] start = new long[n];
        long nextFree = 0;
        for (int index : order) {
            long arrival = Math.multiplyExact(arrivalSeconds[index], (long) rate);
            long begin = Math.max(arrival, nextFree);
            start[index] = begin;
            nextFree = begin + 1;
        }
        return start;
    }
}
```

### 4. 小程序崩了之后，门店还在爆单，这时候该先保下单、保出餐、还是保退款，依据是什么

**参考答案**

结论：先保出餐。已经收了钱或已经接了的单继续做；新下单按门店产能收紧；退款的账和幂等不能停，到账可以变慢。

依据是损失和瓶颈：

- 付了钱没拿到货，比暂时下不了新单、比退款晚几分钟更严重。
- 瓶颈是门店的人和出餐设备。继续放新单，队列更长，超时取消会再变成退款。
- 退款如果占着和小票、出餐状态同一个线程池，会把正在做的单拖住。退款走单独的池子，异步处理。

所以出餐状态、打印、门店大屏继续。新下单降级成排队、预约或暂停接单。支付回调和退款幂等照常跑，避免账乱；批量到账可以靠后。退款的时效能降，正确性不能降。

这是故障已经发生、店里还有一堆未完成杯数时的顺序。活动前要保的则是「新单不要超卖」和「出餐链路可用」，两件事不矛盾，时刻不同。

### 5. AI Agent 要自动发“门店太忙建议改自提/延后取餐”的提示，这种主动动作能不能直接替用户取消订单，权限边界怎么定

**参考答案**

结论：可以主动提示，不能自己取消订单。改自提或延后取餐要用户确认。取消和退款默认不在助手的工具里。

提示是通知。等待杯数和预计时间来自队列服务，文案用模板填，不让模型现编一个等待时间。

改履约方式会改取餐时间和费用，属于改单。助手只能生成建议。用户在卡片上确认后，服务端发一个一次性的 `confirmToken`，绑住用户、订单号、动作和过期时间。改单接口没有这个令牌就拒绝。

取消涉及退款。即使用户口头说取消，也要复述订单号和金额，再点一次确认。已经在制作的订单能不能取消，由订单状态机决定，不由模型决定。超过门店允许的范围，转人工。

工具分成查询、发建议、执行三类。对话只拿前两类。执行器核对令牌和当前状态。没有确认的取消，接口层直接拒绝。

### 6. 多 Agent 架构里，一个管优惠、一个管门店运力、一个管用户对话，三个 Agent 吵起来了谁拍板

**参考答案**

结论：三个 Agent 都没有拍板权。优惠和运力最好是规则和队列服务，对话只负责问清楚和说人话。决定由一个确定性的订单编排器按固定优先级做出。

优先级写成代码：

1. 门店是否接单、最早取餐时间。数据来自队列，不来自模型估计。做不了的店，券也不能硬派过去。
2. 促销引擎给出的价格和互斥。对话里承诺过的叠加，引擎拒绝就不算数。
3. 用户明确选过的门店、杯数、甜度。
4. 推荐话术。前三条都满足时，才把推荐写进确认卡。

冲突时把约束告诉用户，例如这家店要等很久、券只能在另一家用，让用户选。不要让三个模型互相说服，那个过程不可复现，也没法对账。

如果系统里已经是三个自由规划的 Agent，也仍然用编排器收口：它们只输出结构化意见，谁也调不了核销和建单。意见不一致就返回冲突，不投票。

### 7. Agent 调用发券接口重复发了两次买一送一，怎么止损、溯源、补单、复盘

**参考答案**

结论：先停发券并冻住多出来的那张，再按幂等键把影响面圈出来。未使用的作废；已经做成饮品的记为资损。补的是「仍然一张都没有的人」，不是再发一张。

复盘：看发现用了多久、影响多少人、资损多少。改动落在唯一索引、助手写工具必须带稳定键、超时先查询、以及对账任务。用一次「超时后重试」的演练验证不会再多发。

### 11. 手写算法：给一组活动开始前后系统 QPS 曲线，找出最长连续超载区间，并返回最大积压订单数

**参考答案**

先定口径。`qps[i]` 是第 i 秒到达的订单数，系统每秒最多处理 `capacity` 单。某一秒 `qps[i] > capacity` 才算超载，等于只是打满，不算超载。最长连续超载区间是最长的一段下标；长度相同取起点更早的那一段。

积压按队列模拟：`backlog = max(0, backlog + qps[i] - capacity)`，全程峰值才是最大积压订单数。只把超载区间里的超出量相加，会漏掉这段之前已经排着的单，也会漏掉中间低谷没消化完、后面又堆上去的峰值。区间内净增是另一个数：这段里每秒都处理不完，净增等于超出量之和。两个数分开返回。

例如 `qps = [3, 8, 9, 2, 7, 7]`，`capacity = 5`。超载段是下标 `[1, 2]` 和 `[4, 5]`，都是长度 2，取 `[1, 2]`，净增 `(8-5)+(9-5) = 7`。队列是 0、3、7、4、6、8，峰值是 8。峰值大于这段净增，因为第 3 秒只消化了一部分。

一次扫描找区间，一次扫描算峰值，时间 O(n)，空间 O(1)。`capacity` 为负或出现负的到达量直接拒绝。没有任何一秒超载时，区间记为不存在，峰值仍按全程计算。

```java
public class Overload {
    public static final class Result {
        public final int start;
        public final int end;
        public final long peakBacklog;
        public final long intervalOverflow;

        public Result(int start, int end, long peakBacklog, long intervalOverflow) {
            this.start = start;
            this.end = end;
            this.peakBacklog = peakBacklog;
            this.intervalOverflow = intervalOverflow;
        }
    }

    public static Result analyze(int[] qps, int capacity) {
        if (qps == null || qps.length == 0 || capacity < 0) {
            throw new IllegalArgumentException("qps 不能为空，capacity 不能为负");
        }
        int bestStart = -1;
        int bestEnd = -1;
        int bestLen = 0;
        int i = 0;
        while (i < qps.length) {
            if (qps[i] < 0) {
                throw new IllegalArgumentException("到达量不能为负");
            }
            if (qps[i] <= capacity) {
                i++;
                continue;
            }
            int j = i;
            while (j < qps.length && qps[j] > capacity) {
                if (qps[j] < 0) {
                    throw new IllegalArgumentException("到达量不能为负");
                }
                j++;
            }
            if (j - i > bestLen) {
                bestLen = j - i;
                bestStart = i;
                bestEnd = j - 1;
            }
            i = j;
        }
        long backlog = 0;
        long peak = 0;
        for (int t = 0; t < qps.length; t++) {
            if (qps[t] < 0) {
                throw new IllegalArgumentException("到达量不能为负");
            }
            backlog = Math.max(0L, backlog + qps[t] - (long) capacity);
            if (backlog > peak) {
                peak = backlog;
            }
        }
        long overflow = 0;
        for (int t = bestStart; t <= bestEnd && bestStart >= 0; t++) {
            overflow += qps[t] - (long) capacity;
        }
        return new Result(bestStart, bestEnd, peak, overflow);
    }
}
```

### 2. 为什么看霸王茶姬这种业务+AI Agent结合的岗位

**答题思路**

动机落在「你已经会的」和「这个岗位天天在做的」重合，不说追热点，也不说喜欢奶茶。

1. 你过去做的是下单、库存、券或消息这一类链路，讲一个真实场景即可。
2. 这个岗位的差别是：活动流量会突然上来，同时有人想用自然语言下单。模型负责听懂，库存和券仍要工程兜住。这正好用得上你已有的能力。
3. 你想补的是助手上线后的那一块：确认、权限、评测、坏例。没有接触过就说你在补哪一部分基础，不编一个已经上线的助手项目。
4. 为什么是现在：上一家的范围给不到这条链路，或者你希望工作对象从纯接口变成能看到门店和用户结果的系统。原因用你自己的那一个。

避免「贵司发展好」「我很认可品牌」。对方追问时，能说出一条你关心的链路：券不能发重、助手不能自己取消订单。

### 3. 上家公司最烦的一种协作方是谁，怎么处理的

**答题思路**

讲一种角色，不讲一个真人，也不给前同事贴标签。

1. 选一种和这行工作有关的摩擦。例如活动规则当天改口径、出了问题又对不齐当初怎么说的。用你真实遇到过的那一种。
2. 你做了什么：把规则写成书面结论，分清谁有权改、技术侧哪里有硬上限；临时变更只接书面的，并说明来不及就降级哪一段。
3. 结果讲过程：规则有没有冻结、事故后能不能对上口径。没有漂亮数据就不要编「投诉下降了多少」。
4. 收在你从中学到的协作方式：对事、留痕、提前说清保哪条链路。

不说「业务都不懂技术」。对方如果追问具体的人，把话题拉回事实和书面结论。

### 4. 活动型业务经常半夜应急，你能不能接受临时顶系统

**答题思路**

接受轮值，不接受没有轮换的随叫随到。把重点放在你怎么让半夜变少。

1. 直接回答：活动窗口内可以值守，重大故障可以起来处理。长期没有排班、每次都找同一个人，你不接受。
2. 补你真实做过的事：预案、开关、告警、跑手册。目的是大多数夜晚只看告警，而不是人人守在电脑前。
3. 说清你值守时先做什么：看影响的是下单、出餐还是通知，先按已经写好的开关降级，再查根因。
4. 如果家庭或身体情况让你没法频繁夜班，直接说你能接受的频率，例如重大活动可以、每周固定夜班不行。不要先答应再在入职后翻脸。

这道题看的是边界清不清楚，不是表态有多满。

### 5. 你觉得自己做 Java 后端和做 AI Agent 后端，最大能力迁移点是什么

**答题思路**

迁移点选「写操作的边界」，不要选「我会调 HTTP，所以会做 Agent」。

按这个顺序说：

1. 你从 Java 带过来的是超时、幂等、状态机、对账、限流。助手触发的发券和下单，一样会超时、会重试、会重复。
2. 举一个你真实处理过的重复请求或消息重复，说明这套方法怎么用到工具调用上：稳定的幂等键、先查询再重试、状态用条件更新。
3. 说清带不过去的部分：模型不是确定的下游，同样的话两次结果可能不同。所以要有确认、权限和评测，不能只靠代码评审。
4. 收一句：最大的迁移不是会接模型，而是知道哪些动作永远不能交给模型直接做。

没做过助手，就说你准备先守住工具层，不说自己已经是 Agent 负责人。

### 6. 薪资预期，别绕

**答题思路**

直接给区间，不先讲梦想。复习稿里不写死数字，用你自己核对过的总包和市场填写。

1. 先用一句话确认口径：对方说的是月薪还是年总包，是否含绩效、补贴、年终。口径不一致，数字没法比。
2. 给出期望的税前总包区间。下限是你这次跳槽值得动的数，上限是你了解到的市场。区间基于现在的收入和市场，不报一个没有依据的单点。
3. 对方追问底线，再给那个低于它就不谈的总包。开口不先抛底线。
4. 说明构成你更看重哪一块，例如固定月薪和年终的比例。岗位能负责完整的下单和助手链路时，你愿意在区间里谈，不把一个整数说成完全不能动。

不说「看公司所定」「都可以」。也不要在没问到时主动把底线压到最低。

### 7. 如果业务方说“先上线再补预案”，你跟不跟

**答题思路**

分动作回答，不说「看情况」，也不说「业务说了算」。

1. 只读、可回滚、影响面是一家店的展示，可以先小流量上，同时写明关掉以后回到什么。
2. 发券、扣库存、自动取消、退款，没有下面四样就不上：能关掉的开关、入口限流、幂等、出了问题谁按开关。预案可以薄，不能空。
3. 你跟业务方怎么说：先上的范围收成哪一步，哪一步这次不做；上线后多久补哪条对账。把这个写成双方都看得到的结论。
4. 如果对方坚持裸上写操作，你不跟。理由是一次重复发券或超卖，比晚一天上线的损失更大。语气放在账上，不放在「我不同意」。

这道题和三面的预案是同一套判断，HR 面前用业务语言说。

### 8. 未来三年想做成“能扛大促的 Java 架构”，还是“懂业务的 AI 工程负责人”

**答题思路**

选「懂业务的 AI 工程负责人」。底子是能扛住活动流量的 Java 工程，不是两条路各走一半。

1. 先选择，再解释。说「都行」等于没想过。你选这个方向，是因为助手如果不管库存、券和门店产能，就只是一个聊天入口。
2. 近一年：把一条真实链路做稳，例如下单、券和高峰开关。用你实际能负责的范围说，不报一个职级。
3. 再往后：补评测、工具权限、坏例和成本，让助手的写操作和订单状态机接在一起。能向门店和业务解释为什么不能自动取消、为什么不能叠加。
4. 大促架构能力继续用，它是这个方向的基础。模型侧的新东西，要能说清它怎么减少错单或资损，才值得引进。

如果团队更需要你先守活动稳定性，你也接受先做那一段，只要结果仍和门店、订单有关，而不是只看演示。
