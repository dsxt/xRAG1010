### 3. 大模型基础：解释一下 Transformer 架构中的注意力机制，以及 MiniMax 的 Lightning Attention 相比传统注意力有什么优势？

**参考答案**

结论：softmax 注意力对序列两两打分，代价随长度平方增长；Lightning Attention 是线性注意力的分块实现，MiniMax-01 用它把长上下文的成本降下来，并且每隔几层仍放回 softmax。

传统注意力计算 softmax(QKᵀ)V。相关矩阵的时间和显存都是 O(n²)，解码时还要留下随历史变长的 KV。线性注意力把历史收进一个与长度无关的状态，当前查询只和这个状态相乘；序列长度上是线性的，状态维度固定时大约是 O(n d²)。Lightning Attention 沿分块思路做 I/O：块内在片上直接算，块间用递归状态传递，避免把巨大的中间矩阵写回显存。

MiniMax-01 的正文模型是混合结构：每 7 个 Lightning Attention 层后面接 1 个 softmax 层，一共 80 层。纯线性注意力语言建模接近 softmax，精确检索明显弱，所以要插回 softmax。公开报告里，这套结构把训练上下文做到约 100 万 token，推理外推到约 400 万 token。优势是多数层不再按平方付费，这些层的推理状态也不随历史 token 数增长。

容易漏的是两条产品线。混合结构在更大规模上暴露过复杂多跳推理的缺口；M2 的预训练说明又改回了全注意力，原因包括评测跟不上、线性注意力对低精度更敏感，以及前缀缓存和推测解码这套推理设施还不成熟。M2.5 的速度和价格要沿全注意力这条线讲。序列极长时，混合模型里剩下的 softmax 层仍会占掉主要延迟。

### 4. 智能体架构：AI Agent 通常包含哪些核心组件？请简述 ReAct（Reasoning and Acting）框架的工作流程

**参考答案**

结论：可运行的 Agent 至少有模型、工具、记忆和掌管循环的运行时。ReAct 是这个循环里的策略：想一步、做一个动作、读回真实结果，再继续。

模型根据当前上下文决定下一步。工具是带参数模式的外部动作，用来读数据或改状态。记忆分成这一次的工作上下文，以及可以跨会话保留的存储。运行时负责拼上下文、校验并执行工具、写入观察、判断停止。规划可以是单独一步，也可以摊在每一步的决策里。

ReAct 的一轮是：模型先给出简短推理（Thought），再给出动作（Action，通常是工具名和参数）；运行时执行后，把真实返回写成观察（Observation）追加进上下文；然后重复，直到动作是结束，或步数用尽，再产生给用户的答案。它和只写思维链的差别是，每一步都要经过外部环境，事实不能只在推理句子里编完。

容易漏的是：Thought 只是痕迹，Observation 由运行时写入。生产里还要有步数上限、工具白名单和重复调用检测，否则推理会把循环拖死。

### 5. 工具调用：在智能体开发中，如何设计一个可靠的 Function Calling 机制来避免模型幻觉？

**参考答案**

结论：幻觉靠协议堵住。模型只能在白名单里选工具，参数先过模式校验，工具返回值只由运行时写入。

每个工具带名字、说明和 JSON Schema，必填、枚举和类型写死，解码时做约束采样，让非法 JSON 出不来。服务端再验一遍范围、权限和资源是否存在。校验失败或超时，把结构化错误当作观察还给模型，并限制重试次数。订单号、路径、用户 id 必须能在先前的检索或工具结果里找到，对不上就拒绝执行。有副作用的工具带幂等键，同一参数重复调用不会做成两遍。

常见幻觉有三种：调用不存在的工具、编造参数、自己写下「工具返回成功」。前两种用白名单和校验挡住。第三种靠消息角色：观察不是模型生成的内容，给用户的事实以工具日志为准。

容易漏的是：把温度调低代替不了模式约束。检索为空仍让模型按常识回答，等于主动放行幻觉。步数和完全相同的重复调用也要设上限。

### 6. 系统设计：如果让你设计一个支持多轮对话的智能体服务，如何保证长上下文（如 100K+ tokens）的稳定性和效率？

**参考答案**

结论：稳定性来自预算外有明确的退化方式，效率来自默认不要把 10 万 token 都送给模型。

历史不要放在进程内存里。每轮先算 token 预算：系统说明和最近几轮原样保留，更早的对话压成结构化摘要（已定结论、未决事项、关键实体），再按当前问题检索补充。摘要和检索结果落库，换机器也能续。能对上的前缀走提示词缓存，避免每轮把同一长前缀重新预填。超出预算时，保留用户刚说的话，改为摘要加检索，并在日志里记下裁掉了什么。

预填成本随提示变长明显上升，首字延迟会先坏。默认走检索；问题确实要通读、材料也放得进窗口时，才用长上下文。工具返回先裁剪再进入上下文。生成用流式。模型窗口很大，也仍然按 token 计费和排队。

全文窗口漏检少，但更慢、更贵，关键句也更容易淹在中间。检索相反。按问题类型路由，比选死一种更稳。负载均衡和网关的空闲超时要大于两个 token 的间隔，否则长生成会被连接掐断。摘要会丢条件，日志里要能回到原文。

### 7. 算法题：手写代码，实现一个简单的 RAG（Retrieval-Augmented Generation）流程中的相似度匹配，例如 BM25 或向量余弦相似度

**参考答案**

结论：向量召回用余弦，专名和错误码用 BM25。两路原始分数尺度不同，各自取候选后按名次融合。

余弦比的是方向：点积除以两个 L2 范数。入库时已经做过 L2 归一化的话，余弦等于点积，索引可以用内积。零向量没有方向，下面约定相似度为 0。一对向量是 O(d)，n 篇文档暴力扫描是 O(nd)；只留 top-k 用大小为 k 的堆，时间 O(n log k)，额外空间 O(k)。这是讲原理的实现。线上用近似最近邻索引，并且查询和库必须是同一个嵌入模型、同一种归一化。

BM25 按词频和逆文档频率打分。每个查询词贡献

IDF(t) · tf(k₁+1) / (tf + k₁(1 - b + b·|d| / avgdl))

这里的 IDF 用 log(1 + (N - df + 0.5) / (df + 0.5))，避免出现负值。k₁=1.5、b=0.75 只是常用起点，要用业务问答集再调。空文档集要把平均长度护住，避免除零。

```python
import math
import heapq
from collections import Counter


def cosine(a, b):
    if len(a) != len(b) or not a:
        raise ValueError("vectors must be non-empty and the same length")
    dot = norm_a = norm_b = 0.0
    for x, y in zip(a, b):
        dot += x * y
        norm_a += x * x
        norm_b += y * y
    if norm_a == 0.0 or norm_b == 0.0:
        return 0.0
    return dot / (math.sqrt(norm_a) * math.sqrt(norm_b))


def top_k_cosine(query, docs, k):
    """docs: [(doc_id, vector), ...]，返回分数从高到低的 k 个。"""
    if k <= 0:
        return []
    heap = []
    for doc_id, vec in docs:
        score = cosine(query, vec)
        item = (score, doc_id)
        if len(heap) < k:
            heapq.heappush(heap, item)
        elif score > heap[0][0]:
            heapq.heapreplace(heap, item)
    return sorted(heap, reverse=True)


def bm25(query, docs, k1=1.5, b=0.75):
    """query 是 token 列表，docs 是每篇文档的 token 列表。分数越大越相关。"""
    n = len(docs)
    if n == 0:
        return []
    lengths = [len(doc) for doc in docs]
    avgdl = sum(lengths) / n
    if avgdl == 0:
        return [0.0] * n
    df = Counter()
    for doc in docs:
        df.update(set(doc))
    scores = []
    for doc, dl in zip(docs, lengths):
        tf = Counter(doc)
        score = 0.0
        for term in query:
            freq = tf.get(term, 0)
            if freq == 0:
                continue
            n_q = df[term]
            idf = math.log(1.0 + (n - n_q + 0.5) / (n_q + 0.5))
            denom = freq + k1 * (1.0 - b + b * dl / avgdl)
            score += idf * (freq * (k1 + 1.0)) / denom
        scores.append(score)
    return scores
```

容易漏的是：余弦和 BM25 都是越大越好，但不能把两个原始分直接相加。融合用倒数排名这一类按名次的方法。查询里的重复词会按出现次数累加，这是 BM25 里的查询词频。

### 8. 算法题：LeetCode 470. 用 Rand7() 实现 Rand10()（考察概率与拒绝采样优化）

**参考答案**

结论：一次 Rand7 只有 7 种结果，不能均分成 10 份。用两次拼出 49 种等概率结果，只接受其中 40 种并映射到 1–10，其余重试。

`(rand7()-1)*7 + rand7()` 得到 1 到 49，每种概率都是 1/49。1 到 40 里，每个余数恰好出现 4 次，所以 `(x-1)%10+1` 在 1 到 10 上均匀。41 到 49 丢掉。每次尝试固定调用 2 次，成功概率 40/49，期望调用次数是 2×49/40 = 2.45。空间 O(1)，最坏次数没有上界。

优化是把丢掉的值接着用：9 种残留配上一次 Rand7 得到 63 种，留下 60 种；再剩 3 种就再拼一次，21 种里留下 20 种。期望调用次数会低于 2.45。严格均匀时，调用次数不能有一个到点就一定返回的硬上限：有限深度的调用树上，每个叶子的概率都是 7 的负整数次幂，要凑成 1/10，公分母 7^D 必须能被 10 整除，但 7 和 10 互素，做不到。

```python
def rand10():
    """rand7() 已给出，独立均匀返回 1..7。"""
    while True:
        x = (rand7() - 1) * 7 + rand7()  # 1..49，均匀
        if x <= 40:
            return (x - 1) % 10 + 1
        x = (x - 41) * 7 + rand7()  # 用掉 9 种残留，得到 1..63
        if x <= 60:
            return (x - 1) % 10 + 1
        x = (x - 61) * 7 + rand7()  # 用掉 3 种残留，得到 1..21
        if x <= 20:
            return (x - 1) % 10 + 1
```

容易漏的是：Rand7 含 7，且各次独立。`rand7() % 10`，或拒绝区间不按 10 的倍数截断，都会偏。基础版先写对，再讲怎么吃掉残留。

### 9. 工程实践：Linux 下如何批量处理大量文件（如重命名、内容提取），并考虑并行化处理？

**参考答案**

结论：用 `find -print0` 产出路径，交给 `xargs -0 -P` 分给多个进程。并行度看磁盘和单文件成本，不按核数拉满。

路径里会有空格和换行，所以用 NUL 分隔，不用 `for f in $(ls)`。进程启动不便宜，小文件用 `-n` 把几十到上百个路径交给同一次处理。每个输入写自己的输出，写完再改名；多进程不要追加同一个结果文件。重命名先写到临时名，再 `mv` 到目标名，中断后可以重跑。

文本解析这类 CPU 活，并行度可以接近核数，并用进程。拷贝和改名是磁盘活，并行太大 iowait 升高，整体更慢，从较小的并发试起。打开文件数不够就调 `ulimit -n`。失败路径单独记日志，处理程序用非零退出码表示失败。GNU `xargs -P` 不是所有 POSIX 都有；需要补跑记录时可以用 GNU parallel 的 `--joblog`。

```bash
set -o pipefail
find /data/docs -type f -name '*.txt' -print0 \
  | xargs -0 -n 100 -P 4 python3 extract.py
```

`extract.py` 从参数读取路径，把结果写到独立文件。管道要打开 `pipefail`，前面的 `find` 失败才能传出去。网络盘上先用小并发试跑。

### 3. MiniMax 技术栈：了解 MiniMax 自研的 Forge 框架吗？请谈谈你对“Agent 原生”模型（如 M2.5）的理解，以及它在成本控制上的优势

**参考答案**

结论：Forge 是训练 Agent 的强化学习框架；M2.5 的成本优势来自接口标价、缓存和更短的任务轨迹。它和 MiniMax-01 的 Lightning Attention 不是同一套结构。

Forge 在训练引擎和 Agent 之间加了一层，Agent 只负责产出轨迹，训练和推理引擎可以换。这样模型学的是跨脚手架、跨工具协议的行为，而不是某一种框架的提示词。采样和训练之间用数据池隔开，异步调度要在吞吐和「样本相对当前策略有多旧」之间取平衡。同一批采样轨迹里，共享前缀按树合并，去掉重复预填；官方把这项合并带来的训练加速说成大约 40 倍，并保持损失计算和原来等价。算法上他们继续用 CISPO 稳定 MoE 的大规模训练，并用过程奖励处理长轨迹的信用分配。

Agent 原生在这里指：模型在大量真实环境里用强化学习学过多步工具使用，上线时还能按场景装上可复用的技能，而不是聊天模型外面套一层提示词。官方发布了能力相同、吞吐不同的两档：约 100 token/s 的一档，输入约 0.3 美元/百万 token、输出约 2.4 美元/百万 token；约 50 token/s 的一档价格减半。两档都支持缓存。按输出速率折算，100 token/s 连续生成一小时约 1 美元，50 token/s 约 0.3 美元。

容易漏的是：这一美元是输出 token 的小时价，不含预填、工具费用和失败重试。一次任务的总价还取决于轨迹有多长。M2 系列使用全注意力，不要把这个价格解释成线性注意力省下来的。

### 4. 强化学习：在智能体训练中，PPO（Proximal Policy Optimization）和 DPO（Direct Preference Optimization）有什么区别？DPO 为什么在微调中更受欢迎？

**参考答案**

结论：PPO 是在线强化学习，要采样、奖励信号和价值基线；DPO 把带 KL 约束的偏好优化写成对离线偏好对的分类损失。微调更常见 DPO，是因为它的工程栈短。有环境奖励的 Agent 训练仍然要在线采样。

PPO 限制新旧策略的概率比，裁剪过大的更新。用在语言模型上时，通常要有奖励（奖励模型或环境分数）、从当前策略采出的样本，以及一个估计优势的 critic，并常用相对参考模型的 KL 防止漂太远。算力高，对奖励模型和采样是否及时都敏感，也会出现奖励投机。

DPO 从「奖励最大化加相对参考策略的 KL 约束」推出：最优奖励可以写成策略与参考模型的对数概率差。再放进 Bradley-Terry 偏好模型，损失就是让胜出答案相对落败答案的这个差值变大：

`-log σ( β (log πθ(y₊|x)/πref(y₊|x) - log πθ(y₋|x)/πref(y₋|x)) )`

没有单独的奖励模型，也不在训练步里向环境采样，形态接近监督学习。β 控制离参考模型多远。参考模型一般是监督微调之后的那个模型。

DPO 更受欢迎，是因为偏好对可以离线准备，少训一个奖励模型，也少一套在线采样。它的边界同样明确：学的是数据里已经出现的对比，数据外面的行为探索不到；偏好如果偏向长答案，模型会变啰嗦。测试是否通过、页面状态对不对这类可验证奖励，仍然要在线强化学习。Forge 走的是后面这条路。

容易漏的是：DPO 把奖励吸收进策略和参考模型的对数比里，并不是「没有奖励」。β 和参考模型选错，更新会直接失真。

### 5. 微调技术：解释一下 LoRA（Low-Rank Adaptation）的原理，以及它在智能体微调中的应用场景

**参考答案**

结论：LoRA 冻结原权重，只训练一对低秩矩阵去近似权重增量，用来改工具调用的格式和策略，同时不必全参微调。

前向是 h = Wx + (α/r) BAx。W 冻结，A、B 可训练，秩 r 远小于维度。它依赖一个经验前提：适配阶段需要的更新，落在一个低秩子空间里。推理时可以把 BA 合并进 W，也可以不合并，按任务换适配器。原论文的缩放是 α/r，α 固定、调 r 时实际步长会变。

Agent 里常见的用法，是用成功的工具轨迹做监督微调或偏好微调，只更新注意力投影（常见起点是 Q、V，也可以加上输出投影和 MLP）。多块技能可以是多个适配器，基座共用。显存紧时再把基座量化。它改变不了「基座根本不会这个任务」：秩太小会欠拟合长程策略，多个适配器直接相加也会互相干扰。需要探索和可验证奖励时，仍然要在轨迹上做强化学习，LoRA 只是让策略更新更省参数。

容易漏的是：评测看工具参数是否合法、任务是否做完，语言损失下降说明不了 Agent 变好。α/r 才是实际步长。

### 6. 系统设计：设计一个支持高并发请求的智能体服务架构，如何做负载均衡和容错处理？

**参考答案**

结论：接入无状态，状态外置，模型和工具分池。负载均衡看在途请求，容错的单位是一步工具调用。

接入层做认证、限流和请求号。对话状态和每一步的检查点放在外部存储，API 进程不留会话，才能水平扩展。在线对话和长任务分开队列：前者保首字时间，后者用任务号查询进度。模型服务单独成池，做连续批处理，按队列深度扩容。工具服务再单独成池，慢工具有自己的并发上限，避免占满 API 的线程。

对 GPU 少用纯轮询。单次解码时长差很多，用最少在途请求，并把截止时间从入口传到工具。流式连接的空闲超时要大于 token 间隔。

读工具在幂等的前提下可以重试。写工具带幂等键，超时后先查状态，再决定要不要重做。每一步把参数和观察写入检查点，进程挂了从最后一步继续。模型池配熔断和备用模型；备用模型只接读请求，写操作失败就停下来交给人。限流按用户和按工具两级做。

容易漏的是：整段对话重放会把已经生效的副作用再做一遍。没有检查点和幂等键，重试就会重复下单或重复改文件。

### 7. 性能优化：当智能体处理超长文本（如整本代码库）时，除了分块，还有哪些技术手段可以提升推理速度？

**参考答案**

结论：超长文本慢，主要慢在预填。先减少送进模型的 token，并让没变的前缀命中缓存。分块已经假定做过，下面是另外的手段。

用目录、符号和检索决定这次要打开的文件，模型只看和问题有关的几段。稳定的系统提示和仓库摘要放在前缀里，用提示词缓存或推理引擎的前缀 KV 复用，多轮只为新增的后缀付预填。读文件的工具并行发，避免一轮只打开一个文件。

要覆盖整个库时用地图-归约：模块摘要并行算，再用摘要做综合。延迟取决于最慢的一支加上最后一轮，而不是一整库的一次预填。历史轮次做结构化压缩，压缩结果要能回到原文。

引擎侧再用连续批处理、量化和推测解码。推测解码加快的是生成，不解决 10 万 token 的预填。量化省显存、换吞吐，不提高找对文件的概率。

容易漏的是：缓存命中要求前缀逐字节一致，中间插一个时间戳，整段前缀都会失效。窗口更大不等于更快。

### 8. 评估指标：如何评估一个 AI Agent 的好坏？除了准确率，还会关注哪些指标（如推理速度、成本、幻觉率）？

**参考答案**

结论：先看任务有没有在环境里做完，再看花了多少步、多少钱、有多少事实对不上证据。单独一个准确率盖不住这些。

任务成功率用可核对的结果：测试是否通过、页面或文件是否变成目标状态。可以看 pass@k，但 k 次的成本要一起报。过程指标分开看：非法参数、调错工具、重复同一调用、该停不停。幻觉率定义为最终回答里有多少事实在工具观察或检索证据中找不到。

效率看完成一次任务的 token、费用，以及首字和端到端延迟的 p95。失败和超时留在分母里，只在成功样本上统计时间会把问题藏掉。写操作另看误触发率。改提示词或换模型时跑同一套固定任务。

容易漏的是：分母要说明是全部任务，还是模型自己认为会做的题。另一个模型打分只能用来抽检，环境结果才是主指标。

### 9. 算法题：手写代码，实现一个简单的 KV 缓存机制（类似 Redis 的简易版），支持 TTL 过期和 LRU 淘汰策略

**参考答案**

结论：这是应用层的键值缓存。过期键不能被读到；容量满了先丢掉已过期的键，还不够再淘汰最久未使用的键。

`get` 平均 O(1)，`set` 在需要腾位置时最坏 O(n)（要扫一遍过期键），空间 O(容量)。生产实现会用哈希表加双向链表做 LRU，再用按过期时间组织的堆做主动清理，堆里用懒删除处理已经更新过的旧记录，从而把淘汰降到 O(log n)。下面这个版本把正确性写清楚。过期采用惰性删除：访问时发现过期就移除；插入且容量已满时，优先删一个已过期的键。

它和模型推理时保存历史 token 键值的那份缓存是两回事。后者没有 TTL，也不是按 LRU 丢掉任意 token，题目要求的是 Redis 这一类语义。单机字典不加锁，多线程要用同一把锁罩住读写。

```python
import time
from collections import OrderedDict


class KVCache:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        # key -> (value, expire_at)。expire_at 为 None 表示不过期。
        # 顺序从最久未使用到最近使用。
        self._store = OrderedDict()

    def get(self, key):
        item = self._store.get(key)
        if item is None:
            return None
        value, expire_at = item
        if expire_at is not None and expire_at <= time.monotonic():
            del self._store[key]
            return None
        self._store.move_to_end(key)
        return value

    def set(self, key, value, ttl=None):
        if ttl is not None and ttl <= 0:
            self._store.pop(key, None)
            return
        expire_at = None if ttl is None else time.monotonic() + ttl
        if key in self._store:
            self._store[key] = (value, expire_at)
            self._store.move_to_end(key)
            return
        if len(self._store) >= self.capacity:
            self._make_room()
        self._store[key] = (value, expire_at)

    def _make_room(self):
        now = time.monotonic()
        expired_key = None
        for key, (_, exp) in self._store.items():
            if exp is not None and exp <= now:
                expired_key = key
                break
        if expired_key is not None:
            del self._store[expired_key]
            return
        self._store.popitem(last=False)
```

容易漏的是：更新已有键只刷新值和过期时间，不应该因此淘汰别的键。刚过期但仍在最近位置的键会占着容量，所以插入时要先找过期键，不能只看最久未使用的那一个。`ttl <= 0` 这里直接删除，避免塞进一个永远读不出来的键。

### 2. 技术视野：对比一下当前主流的智能体开发框架（如 LangChain、CrewAI、MiniMax Forge），你更倾向于哪种？为什么？

**参考答案**

结论：三样不在一层。LangChain 加上 LangGraph 是应用编排，CrewAI 是多角色协作的上层框架，Forge 是 MiniMax 训模型的强化学习系统。有副作用的线上 Agent，我用状态写明的图或更薄的自研循环。

LangChain 的价值是模型、工具和检索的接头多。LangGraph 把步骤做成有检查点的状态图，适合人确认、失败恢复和循环。抽象比较厚，出问题要能看到实际提示词和工具参数。CrewAI 用角色、任务和流程把多个 Agent 编在一起，原型快，停止条件、权限和重试容易落在框架默认值里。Forge 解决的是训练时如何接入不同脚手架并规模化采样。产品运行时用不上它；值得拿走的是，模型应对工具协议保持稳定，不绑死某一种框架的提示词。

我倾向 LangGraph 这种显式状态机，或一个只保留「拼上下文、校验工具、写检查点、判断停止」的自研循环。Agent 的事故大多是工具参数、超时和做了一半的副作用，这些要在步骤上看见。多个角色只在分工确实不同、而且各自有评测时才加。

容易漏的是：框架不提供效果。无论选哪个，模式校验、步数上限和任务级评测都要自己有。和面试官讨论时把 Forge 放回训练系统，应用框架在另外两家里选。

### 3. 业务理解：你认为 AI Agent 在哪些垂直领域（如编程、办公、游戏）最容易实现商业化落地？为什么？

**参考答案**

结论：这三样里编程最容易先收到钱，办公次之，面向玩家的游戏 Agent 最难。能落地要同时有：反复出现的任务、做对做错能核对、单次成本低于人工，以及预算已经在某个部门里。

编程四条都占。测试、类型检查和代码审查就是环境结果，工程团队本来就在为工具付费。能卖的是带检查和人工合并的助手。仓库权限，以及长任务做到一半改错分支，是它的主要风险。

办公的频次和市场更大，但写得好不好经常没有自动核对，模板和口径一变就翻车。比较稳的方式是嵌进已有文档流程，按文件类型收紧技能，关键结果由人确认。一个什么都能写的办公 Agent，容易停在演示。

游戏里，玩家能看见的自由 NPC 对延迟、人设一致和重复感都很苛刻，失败会被直接感知，收入却往往只是间接的留存。更接近付钱的是工作室内部的剧本草稿、数值和自动化测试，验收的人是制作组。

容易漏的是：演示效果好不等于能收费。没有核对手段时，成本会花在人工返工上。
