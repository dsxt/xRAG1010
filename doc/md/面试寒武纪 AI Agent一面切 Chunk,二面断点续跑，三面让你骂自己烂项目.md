## 一面

### 1. 自我介绍

**答题思路**

控制在 1.5 到 2 分钟，按"身份 → 经历 → 亮点 → 匹配"组织：

1. 一句话说明年限和方向，例如做后端或 AI 应用工程，近期聚焦 Agent / RAG 落地。
2. 挑 1 到 2 个最相关的项目，说清楚业务目标、你负责的层（检索、编排、工具、评测或工程化）、最终效果。效果用真实数据，没有就讲可验证的变化。
3. 突出和岗位相关的能力：RAG 链路调优、Agent 可控性、线上稳定性、评测体系。
4. 收尾说明为什么想做国产算力上的 Agent，把话题引向你准备得最充分的项目。

不要背简历，也不要罗列技术名词，每个亮点都要留一个让面试官追问的钩子。

### 2. 讲一个你做过的最复杂的 AI Agent 或 RAG 项目，你在里面负责哪一层

**答题思路**

选一个链路完整、有取舍的项目，按下面顺序讲：

1. **背景与目标**：解决什么业务问题，用户是谁，成功指标是什么。
2. **整体架构**：用一句话画出链路，例如"接入 → 意图识别 → 检索 / 工具 → 生成 → 校验 → 回写"，再说明你负责哪一层，边界在哪。
3. **最难的问题**：选 1 到 2 个，例如召回不准、工具参数出错、长任务中断、成本过高，按"现象 → 定位方法 → 方案 → 结果"讲。
4. **取舍**：为什么用工作流而不是全自主 Agent，为什么这样切分 chunk，放弃了什么。
5. **结果与复盘**：用评测集或线上指标证明，再说下一步改进。

准备好面试官会追问的点：评测方式、失败案例、成本、可控性。不要夸大自己没做过的层。

### 3. 意图识别在你项目里是怎么落地的，规则、分类模型、还是 LLM 路由，各自优缺点

**参考答案**

三种方式各有适用场景，生产上通常做成"规则 → 小模型 → LLM 兜底"的级联。

- **规则（关键词、正则、状态判断）**：延迟极低、成本几乎为零、结果确定、可解释。缺点是覆盖度差，维护成本随规则数量上升，对口语化和同义表达很脆弱。适合高频、边界清晰的指令，如"转人工""查订单号"。
- **分类模型（BERT 类小模型或 embedding + 分类头）**：延迟低、成本低、稳定，可以输出置信度。缺点是意图集合封闭，新增意图要重新标注和训练，对长尾和组合意图表现差。
- **LLM 路由（Prompt 或函数调用）**：零样本和少样本就能用，能处理开放表达、多意图和槽位抽取，新增意图只改 Prompt。缺点是延迟高、成本高、输出有随机性，需要用结构化输出和枚举约束。

落地要点：给每层设置置信度阈值，低于阈值才升级到下一层；LLM 输出必须限定在意图枚举内，并做 schema 校验；线上日志回流，把 LLM 的判定结果沉淀为训练数据，逐步把流量转给小模型；用混淆矩阵监控易混淆的意图。

### 4. 用户一句话多意图（比如查库存顺便发邮件）你怎么拆，怎么保证不漏不重

**参考答案**

结论：先把一句话拆成结构化的子任务清单，再按清单执行并逐项核销，副作用操作加幂等键。

1. **拆分**：用 LLM 结构化输出（或规则加分句）得到 `[{intent, slots, depends_on}]`。例如"查库存"和"发邮件"，其中邮件正文依赖库存结果，所以 `depends_on` 指向前者。
2. **依赖编排**：把子任务构成 DAG，无依赖的并行，有依赖的串行，缺失的槽位（收件人等）先向用户追问。
3. **不漏**：为每个子任务维护状态（pending、running、done、failed）。结束前做完整性检查，对照原始请求确认所有子任务都已完成，否则继续执行或向用户说明。必要时让模型再做一次"是否有遗漏意图"的复核。
4. **不重**：对 `(intent, 归一化槽位)` 做去重。有副作用的工具（发邮件、下单）使用幂等键，例如 `run_id + 子任务序号`，重试时只会生效一次。
5. **部分失败**：已完成的结果不回滚，向用户明确说明哪一步失败。

容易说漏的点：多意图之间的依赖关系，以及重试导致邮件被发送两次的问题。

### 5. LangChain 的 Chain 和 Agent 本质区别，什么场景你坚决不用 Agent

**参考答案**

本质区别是**控制流由谁决定**。Chain 的步骤顺序由代码写死，LLM 只是其中的一个组件；Agent 由 LLM 在循环里决定下一步调用哪个工具或是否结束，控制流在运行时动态生成。

Chain 可预测、延迟和成本稳定、容易测试；Agent 灵活，能处理步骤数不确定的开放任务，但存在不可控、循环、成本和延迟波动的风险。

坚决不用 Agent 的场景：

- 流程确定、步骤已知（如"检索 → 生成"的问答），用 Chain 或工作流更好。
- 对延迟和成本有严格 SLA 的高频场景。
- 涉及资金、权限、合规的强确定性流程，或不可逆的操作。
- 需要强审计和可复现结果的场景。
- 小模型或工具调用能力弱的环境，Agent 容易出错。

即使使用 Agent，也要限定工具白名单、最大步数和预算，并在关键步骤加人工确认。

### 6. LangChain 里 Retriever、DocumentCompressor、RunnablePassthrough 在工程里分别解决什么问题

**参考答案**

- **Retriever**：统一的"查询 → 文档列表"接口，屏蔽底层来源，可以是向量库、BM25、多查询改写、Ensemble 融合等。这样上层链路不用关心数据来自哪里，可以在不改链路的情况下替换或组合检索策略。
- **DocumentCompressor**：对已召回的文档做后处理，包括重排序、过滤无关片段、抽取与问题相关的句子、压缩文本。通常配合 `ContextualCompressionRetriever` 使用，目的是减少进入 Prompt 的噪声和 token，提高答案质量。
- **RunnablePassthrough**：LCEL 里"原样透传输入"的组件，常与 `RunnableParallel` 或 `.assign()` 一起用。典型场景是让原始问题与检索到的 context 同时进入 Prompt，即 `{"context": retriever, "question": RunnablePassthrough()}`。

三者对应 RAG 链路里的"取数据 → 精炼数据 → 把数据和问题拼起来"。

### 7. RAG 里 Chunk 大小怎么定，重叠窗口设多少，为什么不能无脑按字数切

**参考答案**

没有通用的最优值，要通过评测集（recall@k、答案正确率）调参。常见起点是每块 256 到 1024 token，重叠 10% 到 20%，同时不能超过 embedding 模型的最大输入长度。

- 块太小：语义不完整，召回的上下文碎片化，需要更大的 top-k。
- 块太大：一个向量混杂多个主题，检索精度下降，还会占用更多上下文窗口。

不能无脑按字数切的原因：固定字数会把句子、段落、表格、代码块、列表切断，破坏语义；标题层级的上下文会丢失，导致片段脱离语境，检索时命中但无法回答。

更好的做法：

- 按文档结构切（标题、段落、表格、代码块），再用长度做兜底。
- 在每个 chunk 前附加标题路径等上下文。
- 采用父子块或 small-to-big：用小块检索，返回其所在的大块。
- 重叠只用于缓解边界切断，不能当成弥补不合理切分的手段，重叠过大会造成重复召回。
- 表格、代码等特殊内容单独处理。

### 8. Hybrid Search（向量+BM25）你怎么融合打分，Rerank 模型放哪一层

**参考答案**

向量相似度和 BM25 分数量纲不同，不能直接相加。常见融合方式有两种：

1. **RRF（Reciprocal Rank Fusion）**：只用排名，`score = Σ 1 / (k + rank_i)`，k 常取 60。不需要归一化，鲁棒，工程上最常用。
2. **加权求和**：先对各路分数做归一化（min-max 或 z-score），再用权重 `α·向量 + (1-α)·BM25`，权重通过评测集调参。

Rerank 放在融合之后、送入 LLM 之前。流程是：多路召回（向量加 BM25，各取 top 50 到 100）→ 融合去重 → 用 cross-encoder 对 query 和候选文档做精排 → 取 top 5 到 10 进入 Prompt。cross-encoder 精度高但延迟大，所以只处理候选集，不处理全库。

注意：重排的候选数量要在延迟预算和召回率之间权衡；元数据过滤（租户、权限、时间）应尽量在召回阶段完成，而不是留到重排后。

### 9. Embedding 模型选型的踩坑：领域词、同义词、中英混排怎么处理

**参考答案**

选型先在自己的评测集上比较，不要只看公开榜单。

- **领域词**：通用模型对行业术语和缩写表示不好。可以选用在领域数据上微调过的模型，或用领域语料和难负例对 embedding 做微调；同时配合 BM25 并加载自定义分词词典，让精确术语靠词法检索命中。
- **同义词**：建立同义词和缩写词典做 query 改写与扩展，或用 LLM 做多查询改写；文档入库时也可以补充别名。
- **中英混排**：选用多语言模型（如 bge-m3 一类），不要用单语模型；预处理统一大小写和全角半角，保持术语原样不翻译；词法检索端使用支持中英文的分词器。

其他踩坑：查询和文档要按模型要求加指令前缀；超出最大长度会被截断；更换模型必须全量重建索引，不同模型的向量不能混用；记录 embedding 版本号。

### 10. Agent 调工具时参数生成非法怎么办，怎么让 LLM 自我修复而不是崩

**参考答案**

原则是把错误当成可恢复的观测结果反馈给模型，同时有上限和降级。

1. **预防**：用 JSON Schema 或 Pydantic 精确定义参数，使用函数调用或结构化输出的 strict 模式，提供枚举和示例，在工具描述中写清约束。
2. **校验**：执行工具前先在代码里校验参数，副作用操作一定要在校验通过之后才执行。
3. **修复循环**：校验失败时，不抛异常，而是把字段级的错误信息（哪个字段、期望什么、实际是什么）作为工具返回的观测结果交给 LLM，让它重新生成。限制重试次数（通常 2 到 3 次）。
4. **轻量修复**：对明显的格式问题（多余的 markdown 围栏、尾逗号）可以做确定性修复；类型和单位可以做安全的转换，但不要猜测业务含义。
5. **降级**：重试仍失败时，向用户追问缺失信息、切换备用工具或转人工，并记录日志用于优化 Prompt 和 schema。
6. **防护**：工具实现具备幂等性，避免重试造成重复的副作用。

### 11. 手撕算法：给一段对话文本，提取用户意图标签并做多标签分类（写核心逻辑/状态机即可，不调包）

**参考答案**

思路：将文本切分成子句，对每个子句用关键词规则给各意图打分，处理否定，再按阈值输出多个标签。流程是一个简单的状态机：切分 → 逐句匹配 → 否定过滤 → 聚合 → 阈值判定。

时间复杂度 \(O(L \cdot K)\)，L 是文本长度，K 是关键词总数；空间 \(O(C)\)，C 是意图数。

```python
import re
from collections import defaultdict

RULES = {
    "query_stock": ["库存", "有货", "缺货", "还剩"],
    "send_email": ["发邮件", "邮件", "email", "抄送"],
    "refund": ["退款", "退货", "退钱"],
    "complaint": ["投诉", "举报", "太差"],
}
NEGATIONS = ["不用", "不要", "别", "无需"]
SPLIT_RE = re.compile(r"[，,。；;！!？?]|顺便|然后|并且|而且|另外")


def extract_intents(dialog, threshold=1.0):
    """dialog: [(role, text), ...]，只统计用户发言，返回多标签列表"""
    scores = defaultdict(float)
    for role, text in dialog:
        if role != "user":
            continue
        for clause in (c.strip() for c in SPLIT_RE.split(text)):
            if not clause:
                continue
            for label, kws in RULES.items():
                for kw in kws:
                    pos = clause.find(kw)
                    if pos < 0:
                        continue
                    # 否定：关键词前 4 个字符内出现否定词，则忽略
                    if any(n in clause[max(0, pos - 4):pos] for n in NEGATIONS):
                        continue
                    scores[label] += 1.0  # 每个子句对每个标签只计一次
                    break
    ranked = sorted(scores.items(), key=lambda x: -x[1])
    return [label for label, s in ranked if s >= threshold]
```

例如输入"帮我查下库存，顺便给张三发邮件"，输出 `["query_stock", "send_email"]`。

面试时要补充：规则法覆盖有限，实际会用分类模型或 LLM 做兜底；多标签阈值需要通过标注数据调整。

### 12. Redis 在 Agent 系统里你拿它存什么，会话上下文、锁、还是向量缓存，过期策略怎么设

**参考答案**

Redis 适合存放需要低延迟、可过期的临时数据，不适合作为唯一的持久存储。

- **会话上下文**：用 List 或 Hash 保存最近若干轮对话与短期记忆，设置 TTL，每次访问续期（滑动过期）。完整历史落到 MySQL 或对象存储。
- **分布式锁**：保证同一会话或任务同时只有一个 Agent 实例在执行。用 `SET key value NX PX ttl`，释放时用 Lua 校验 value，长任务需要续期（看门狗，如 Redisson）。
- **缓存**：embedding 缓存、检索结果缓存、语义缓存（Redis Stack 支持向量检索）。缓存键要包含知识库版本和租户。
- **其他**：限流计数器、幂等键、任务状态与进度。

过期策略：会话类用滑动 TTL（按业务设置，如数小时到数天）；缓存类用固定 TTL 并加随机抖动，避免同时失效造成雪崩；锁的 TTL 要略大于任务的预期时间并支持续期；设置 `maxmemory` 和淘汰策略（缓存使用 `allkeys-lru` 类，会话数据则避免被淘汰）。

注意 Redis 默认不保证持久性，关键数据（执行轨迹、审计）要落库。

### 13. MySQL 存 Agent 执行轨迹怎么建表，量大了之后读写瓶颈怎么破

**参考答案**

建议拆为"运行表 + 步骤表"。

```sql
CREATE TABLE agent_run (
  run_id      BIGINT PRIMARY KEY,
  tenant_id   BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,
  status      TINYINT NOT NULL,       -- 运行中/成功/失败/超时
  total_tokens INT, cost_cents INT,
  started_at  DATETIME(3), ended_at DATETIME(3),
  KEY idx_tenant_time (tenant_id, started_at)
);

CREATE TABLE agent_step (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  run_id      BIGINT NOT NULL,
  step_no     INT NOT NULL,
  step_type   TINYINT NOT NULL,       -- LLM / 工具 / 检索
  name        VARCHAR(128),           -- 模型名或工具名
  input_ref   VARCHAR(256),           -- 大文本放对象存储，这里存引用或摘要
  output_ref  VARCHAR(256),
  status      TINYINT, error_msg VARCHAR(512),
  latency_ms  INT, tokens INT,
  created_at  DATETIME(3),
  UNIQUE KEY uk_run_step (run_id, step_no)
);
```

量大后的优化：

1. **减小行体积**：Prompt 和输出等大文本放对象存储或 ES，MySQL 只保留摘要和引用。
2. **异步批量写**：通过队列（Kafka 等）削峰，消费者批量插入，不要在 Agent 主链路里同步写。
3. **分区与归档**：按时间做 RANGE 分区，旧分区直接 DROP 或归档到冷存储，避免大批量 DELETE。
4. **分库分表**：按 `tenant_id` 或 `run_id` 切分。
5. **读写分离与分析下沉**：查询和统计分析交给从库，或同步到 ClickHouse、ES 等分析型存储。
6. **索引克制**：只建必要的索引，减少写放大。

### 14. Linux 上排查 Agent 服务 CPU 飙高和内存泄漏的前三步命令

**参考答案**

**CPU 飙高：**

1. `top` 或 `top -Hp <pid>`：定位占用最高的进程，再按线程查看哪个线程最耗 CPU。
2. 把线程 ID 转成 16 进制（`printf '%x\n' <tid>`），用 `jstack <pid>` 在栈里找到对应的 `nid`（Java）；Python 服务用 `py-spy dump --pid <pid>` 或 `py-spy top`，直接看热点调用栈。
3. 结合 `pidstat -u -t 1`、`vmstat 1` 判断是用户态、系统态还是 IO 等待，并检查是否是死循环、频繁 GC、正则回溯或工具调用重试风暴。

**内存泄漏：**

1. `free -h`、`ps -o pid,rss,vsz -p <pid>`：确认内存是否持续增长，用 `dmesg | grep -i oom` 查看是否被 OOM Killer 终止。
2. `pmap -x <pid>` 或 `/proc/<pid>/smaps`：区分堆内存和 native 内存。
3. 看堆内对象：Java 用 `jmap -histo:live <pid>` 或导出 heap dump 后用 MAT 分析；Python 用 `tracemalloc`、`objgraph` 或 `memray`。

Agent 服务常见的泄漏点：会话上下文无限累积、缓存无上限、未关闭的 HTTP 连接和流式响应、全局列表持续追加。

### 15. 最近测过哪个国产大模型或推理框架，在寒武纪这类国产算力上跑 Agent 你觉得最卡的点在哪

**答题思路**

- **算子与框架适配**：自定义算子（FlashAttention、PagedAttention 类）、新模型结构的支持程度和版本匹配。

结尾说明你会如何验证：用真实的 Agent 轨迹做压测，并量化每个卡点。

### 3. LangGraph 的 State 为什么必须可序列化，不可序列化的东西（数据库连接、socket）你怎么处理

**参考答案**

结论：因为 LangGraph 的持久化依赖在每个超步（superstep）后把 State 写入 checkpointer，需要时再读出来恢复。State 不可序列化，就无法做 checkpoint，也就无法实现断点续跑、HITL 中断恢复、time travel 和跨进程、跨机器恢复。

数据库连接、socket、线程锁、文件句柄等只属于当前进程，序列化后也无法在另一个进程里恢复。处理方式：

- **不放进 State**：State 里只存可序列化的数据（字符串、数字、列表、字典、Pydantic 模型、消息），以及资源的标识，如 ID、路径、URL。
- **运行时注入**：连接和客户端通过节点函数的闭包、依赖注入，或通过 `config["configurable"]`（新版本里也可用 runtime context）传入，节点执行时获取，每次恢复时重新创建。
- **连接池与工厂**：在进程级别用全局连接池，节点按需获取连接，用完归还。
- **大对象外置**：大文件和二进制数据存对象存储，State 里只放引用。

另外，State 里的自定义类型需要序列化器支持，否则恢复时会得到错误的类型。

### 4. LangGraph 条件边和普通边在 Agent 循环里分别管什么，checkpoint 断了怎么恢复

**参考答案**

**边的作用：**

- **普通边**（`add_edge`）：固定的流转，A 执行完一定到 B。例如工具节点执行完后固定回到 Agent 节点。
- **条件边**（`add_conditional_edges`）：路由函数读取当前 State，返回下一个节点名，实现分支和循环的退出判断。典型的 ReAct 循环是：`agent` 节点之后用条件边判断最后一条消息是否带 `tool_calls`，有则去 `tools` 节点，无则到 `END`；`tools` 通过普通边回到 `agent`。循环的终止由条件边和 `recursion_limit` 共同保证。

**checkpoint 恢复：**

1. 编译图时配置持久化的 checkpointer（Postgres、Redis、SQLite 等，不要用内存版的 `MemorySaver` 做生产），每次调用都带上固定的 `thread_id`。
2. 进程崩溃后，用相同的 `thread_id` 再次调用（输入传 `None`），图会从最近一个成功的 checkpoint 继续执行。同一个超步里已经成功完成的节点，其写入会作为 pending writes 保存，不会重复执行。
3. 需要回滚时，用 `get_state_history` 找到某个历史 checkpoint，指定 `checkpoint_id` 从该点重放，或用 `update_state` 修改状态后继续。

注意：失败的节点会被重新执行，所以节点里的副作用必须幂等。

### 5. 多 Agent 模式里 Supervisor、Hierarchical、Peer-to-Peer 你分别什么时候用

**参考答案**

- **Supervisor（中心调度）**：一个主管 Agent 负责分配任务、汇总结果，Worker 只做自己的专业工作。适合任务可以清晰拆解、需要统一控制、审计和限制权限的场景，是多数业务的首选。缺点是主管成为瓶颈和单点，上下文会随 Worker 数增加而膨胀。
- **Hierarchical（层级）**：多层主管，每个主管管理一个领域团队。适合 Agent 数量多、领域边界清楚、单个主管的上下文和工具列表放不下的大型系统。缺点是层级多，延迟和成本更高，调试更复杂。
- **Peer-to-Peer（对等或 Swarm）**：Agent 之间直接移交（handoff），没有中心。适合角色少、对话式的交接场景，比如客服里从导购转到售后。缺点是控制流难以追踪，容易出现互相踢皮球的循环，需要明确的移交规则和步数上限。

选型原则是**从最简单的开始**：能单 Agent 就不多 Agent，需要多个时先用 Supervisor，只有规模或领域增长后才升级为层级。

### 6. 多 Agent 互喷（两个 Agent 结论矛盾）怎么仲裁，投票/置信度/升级人工你选哪个，为什么

**参考答案**

不会只选一种，而是按**可验证性和风险**分层选择：

1. **能用工具验证的，先验证**：矛盾若涉及事实、计算、代码，就让它们给出证据（引用来源、执行代码、查询数据库），由确定性的程序或验证器裁决，这是最可靠的。
2. **低风险、结论是离散选项的，用投票**：使用 3 个及以上相互独立的 Agent（最好是不同模型或不同 Prompt）做多数投票。注意同源模型的错误是相关的，投票的收益有限。
3. **置信度只作辅助**：LLM 自述的置信度没有校准，不能直接作为裁决依据。只有经过校准的分数（如验证器分数、检索证据覆盖度）才可信。
4. **高风险、不可逆、分歧大的，升级人工**：涉及资金、权限、合规，或者各方都缺乏证据时，交给人工并附上双方的论据。

另外可以引入一个独立的"裁判 Agent"来比较论据，但它也会犯错，所以仍要有证据约束。同时要限制辩论的轮数，避免无限互喷。

### 7. Agentic RAG 和普通 RAG 的边界，什么时候该让 Agent 决定再检一次，而不是硬编循环

**参考答案**

普通 RAG 是固定的"检索一次 → 生成"，或者带固定轮数的硬编码流程。Agentic RAG 把检索当成工具，由 Agent 决定：要不要检索、检索什么（改写 query）、查哪个数据源、检索结果够不够、是否需要再检一次。

应该让 Agent 决定的场景：

- 多跳问题，第二次的查询依赖第一次的结果。
- 多数据源（文档库、数据库、网页），需要路由选择。
- 问题模糊或需要拆解，检索质量不稳定，需要评估结果后改写重试。
- 某些问题根本不需要检索，不检索可以节省成本。

仍然应该硬编码的场景：单跳的 FAQ 类问题、延迟和成本要求严格、行为需要完全可预测。

要点：Agentic 带来更多的 LLM 调用和不确定性，所以要设置最大检索轮数、"信息是否充分"的判定标准，以及每轮的成本预算；可以采用折中方案，主流程固定，只在"检索结果评分低"时进入 Agent 决策的补充检索。

### 8. 长上下文 Agent 怎么防 context blowup，summary buffer 和 external scratchpad 你怎么切

**参考答案**

目标是让上下文只保留当前推理所需的内容。常用手段：

- **Summary buffer**：保留最近若干轮的原文，把更早的历史压缩成摘要，在 token 达到阈值（如窗口的六七成）时触发压缩。摘要要保留结构化的关键事实，如用户目标、已做的决定、约束条件。
- **External scratchpad**：把体量大、需要精确保存、之后可按需读取的内容放到上下文之外（文件、数据库或 State 的外部存储），上下文里只留一段简短摘要和引用，Agent 通过工具按需读回。

怎么切：

| 内容 | 放哪里 |
| --- | --- |
| 用户目标、约束、对话要点、已决定的结论 | summary buffer |
| 工具的大体量输出、文档、代码、表格、中间结果 | scratchpad |
| 计划和待办清单 | scratchpad，并在上下文里保留最新状态 |
| ID、金额等精确数据 | 不能只存在有损的摘要里，需要同时落到 scratchpad |

其他措施：限制每个工具的输出长度并做截断；清理已经用完的旧工具结果；子任务交给子 Agent，只返回精简的结果；对检索使用 top-k 限制。

### 9. Human-in-the-loop 在 LangGraph 里 interrupt_before 和 checkpoint 的配合细节，人工超时怎么兜底

**参考答案**

**配合机制：**`interrupt_before=["node"]`（编译时指定）或节点内部调用 `interrupt()`，会在执行指定节点之前暂停图。暂停的前提是配置了 checkpointer：图暂停时把当前 State 持久化，调用立即返回，进程可以释放资源。恢复时用同一个 `thread_id` 继续：旧写法是 `invoke(None, config)`，使用 `interrupt()` 时则用 `Command(resume=人工输入)`。人工若要修改内容，先用 `update_state` 改写 State 再继续。因为依赖持久化，生产环境必须使用 Postgres、Redis 等持久化的 checkpointer，而不是内存版。

注意：使用 `interrupt()` 恢复时，被中断的节点会从头重新执行，所以中断点之前的副作用必须幂等，或者把中断单独放在一个节点里。

**人工超时兜底：** LangGraph 本身不提供超时机制，需要在外部实现：

1. 记录"等待审批"的 thread 和过期时间，由定时任务或延迟队列扫描。
2. 超时后按风险选择策略：低风险的可以采用安全默认值或自动拒绝；高风险的先提醒，再升级到上级或其他审批人；无人处理就取消任务并通知用户。
3. 超时处理同样通过 `Command(resume=...)` 或 `update_state` 回到图中，并把状态标记为已过期。
4. 不要对不可逆的操作自动批准。

### 10. AI 工作流里 DAG 编排和 Agent 自主循环你怎么共存，哪部分写死哪部分放权

**参考答案**

原则是**外层工作流写死，内层 Agent 在受限范围内放权**，即"确定的骨架加有边界的自主"。

**写死的部分（DAG）：**

- 业务主流程和步骤顺序、必须执行的校验。
- 涉及副作用、权限、资金的操作，以及人工审批点。
- 合规和审计节点。
- 输入输出的 schema 校验。

**放权给 Agent 的部分：**

- 步骤数不确定的开放任务，如调研、排查、多轮检索和信息整合。
- 工具选择与参数组合。

实现方式：在 DAG（或 LangGraph 的主图）里把某个节点实现为 Agent 子图，并给它加约束：工具白名单、最大步数、token 与时间预算、输出必须符合 schema，超限则降级或转人工。Agent 的产出回到 DAG 后，由确定性节点做校验再继续。

这样既保留了可预测性和可测试性，又在需要灵活性的局部使用自主能力。如果某个 Agent 节点的行为在线上趋于稳定，也可以逐步固化为确定性的步骤。

### 11. Kafka 或 RocketMQ 在 Agent 系统里你拿来做啥，任务队列、事件总线还是审计流，消息重复消费怎么防

**参考答案**

**用途：**

- **任务队列**：长耗时 Agent 任务异步执行，削峰填谷，并按租户或优先级分队列。
- **事件总线**：传递 Agent 的运行事件、工具结果、状态变更，解耦各个服务。
- **审计与轨迹流**：追加写入的日志流，可回放，用于落库、分析和评测。

**防重复消费：** 消息队列通常是至少一次投递，必须在消费端做幂等。

1. 使用业务唯一键（如 `run_id + step_no`，或消息 ID）。在 DB 里用唯一约束，或用 Redis `SETNX` 做去重表。
2. 有副作用的下游调用带幂等键，由对方去重。
3. 处理成功后再手动提交 offset，不要自动提交。
4. Kafka 的幂等生产者和事务只保证 Kafka 内部的精确一次，不能覆盖外部的副作用。

Agent 场景的特别注意：任务执行时间长，如果超过 Kafka 的 `max.poll.interval.ms`，消费者会被踢出组并触发 rebalance，导致同一条消息被重复消费。应该把耗时处理放到独立线程并继续调用 poll（必要时暂停分区），或者只在队列里放任务 ID，由 worker 异步执行并回写状态。需要保证顺序的用 `run_id` 作为分区键。

### 12. Elasticsearch 存 RAG 元数据还是正文，和向量库怎么分工

**参考答案**

通常正文和元数据都可以放在 ES，和向量库按职责分工：

- **ES**：存 chunk 的正文，用于 BM25 关键词检索，同时存元数据（文档 ID、租户、权限、版本、时间、来源、标题路径等），用于过滤和聚合。ES 在全文检索、过滤和聚合上成熟。
- **向量库**：存 embedding 向量以及必要的过滤字段，负责语义召回。
- 两边通过 `chunk_id` 关联。检索时两路分别召回，用 RRF 等方式融合，再回表获取正文。
- **原始文档**放在对象存储或数据库，它们才是数据的权威来源，ES 和向量库都是可重建的索引。

也可以简化：ES 8 及以上版本支持 `dense_vector` 和 kNN，规模不大时一套 ES 就能完成混合检索，减少运维成本。如果向量规模很大，或对向量检索性能要求高，再使用专用向量库。

关键点是**一致性**：文档更新和删除要同时作用于两边（以文档版本和 `doc_id` 为准），否则会召回已被删除的内容。权限过滤要在检索阶段完成，不能依赖生成阶段。

### 13. 手撕算法：实现一个简易意图路由状态机，输入多轮对话列表，输出当前应跳转的 Agent 名称和理由（伪代码或 Python 均可）

**参考答案**

思路：路由状态由"当前 Agent"和最近几轮用户消息决定。先判断显式的强制规则（如"转人工"），再对每个目标 Agent 按关键词计分，越近的消息权重越大；为避免来回切换，加入滞回（hysteresis），只有新 Agent 的得分明显高于当前 Agent 才切换；没有命中就保持当前 Agent 或进入兜底。

时间复杂度 \(O(W \cdot K)\)，W 是窗口内的消息数，K 是关键词总数；空间 \(O(A)\)，A 是 Agent 数。

```python
ROUTES = {
    "refund_agent": ["退款", "退货", "退钱"],
    "order_agent": ["订单", "物流", "快递", "发货"],
    "tech_agent": ["报错", "bug", "崩溃", "打不开"],
}
FORCE_HUMAN = ["转人工", "人工客服"]


def route(dialog, current=None, window=3, switch_ratio=1.5):
    """dialog: [{"role": "user"/"assistant", "content": str}, ...]
    返回 (agent_name, reason)"""
    user_msgs = [m["content"] for m in dialog if m["role"] == "user"][-window:]
    if not user_msgs:
        return current or "general_agent", "没有用户消息，保持当前状态"

    # 1. 强制规则优先，只看最新一条
    if any(k in user_msgs[-1] for k in FORCE_HUMAN):
        return "human_agent", "用户明确要求转人工"

    # 2. 近期消息权重更大
    scores = {}
    for age, text in enumerate(reversed(user_msgs)):  # age=0 是最新一条
        weight = 1.0 / (1 + age)
        for agent, kws in ROUTES.items():
            hits = sum(1 for k in kws if k in text)
            if hits:
                scores[agent] = scores.get(agent, 0.0) + weight * hits

    if not scores:
        return current or "general_agent", "没有命中任何意图，保持当前 Agent"

    best = max(scores, key=scores.get)

    # 3. 滞回：避免在两个 Agent 之间来回抖动
    if current in scores and best != current:
        if scores[best] < scores[current] * switch_ratio:
            return current, f"{best} 得分未明显高于当前 Agent，继续由 {current} 处理"

    return best, f"最近 {len(user_msgs)} 轮命中 {best} 的关键词，得分 {scores[best]:.2f}"
```

可以补充：实际工程里关键词打分可以换成分类模型或 LLM 路由，低置信度时追问用户；每次路由结果要记录日志，便于评估和回放。

### 14. Agent 生产环境上线前你要测哪些非功能指标：尾延迟、工具失败率、循环次数分布、成本/千次调用

**参考答案**

上线前要用接近真实的流量轨迹做压测和回归，主要看以下几类：

- **延迟**：P50、P95、P99 的端到端耗时，首 token 时间（TTFT），以及各环节（检索、LLM、工具）的耗时拆分。Agent 的尾延迟往往来自循环次数多和工具超时。
- **可靠性**：任务成功率，工具调用失败率与超时率，重试率，降级和兜底的触发率，模型接口限流和报错下的表现。
- **循环与步数**：每个任务的 LLM 调用次数和工具调用次数的分布，特别关注长尾、触达最大步数的比例、死循环检出率。
- **成本**：每千次调用的 token 消耗与费用，按场景拆分，以及长尾任务的成本占比。
- **容量**：最大并发、吞吐、队列堆积、显存或 KV Cache 占用，各类限流是否生效。
- **稳定性**：长时间浸泡测试（内存泄漏）、故障注入（工具宕机、模型超时、网络抖动）、断点续跑验证。
- **质量与安全**：端到端评测集通过率，Prompt 注入、越权调用等安全用例。

做法是为每项指标设置明确的门禁阈值，由业务基线决定，不达标不上线。上线后通过灰度发布和线上监控持续观察，指标变化要能够告警。

### 15. 如果让你在寒武纪芯片上部署这套 Agent，推理框架选 vLLM 还是 SGLang 还是自研适配层，理由是什么

**参考答案**

我的选择是：以**寒武纪官方已适配的开源引擎（优先 vLLM）为基线**，在其之上做**薄的适配和网关层**，不自研推理引擎。最终要用真实数据做选型，不要凭印象判断。

理由：

- **vLLM**：生态最成熟，具备连续批处理（continuous batching）、PagedAttention、前缀缓存、OpenAI 兼容接口，并且有硬件平台抽象，社区和硬件厂商的适配最多。是否能用、性能如何，取决于寒武纪侧的适配版本和算子覆盖度，以官方提供的版本为准。
- **SGLang**：RadixAttention 的前缀复用和结构化输出（约束解码）对多轮 Agent、共享 system prompt 和工具 schema 的场景很有优势，但在国产硬件上的适配成熟度要先验证。
- **自研适配层**：成本高、维护压力大，难以追上社区的优化速度。只在现有引擎无法覆盖关键算子或模型时才考虑，并且应仅限于后端算子和接口层。

决策方法：用真实的 Agent 轨迹做基准测试，比较 TTFT、吞吐、前缀缓存命中率、结构化输出和工具调用的支持度、长上下文表现、稳定性，以及版本维护成本。上层用统一的网关抽象模型接口，这样后续可以替换引擎而不影响 Agent 业务。

## 三面

### 1. 自我介绍

**答题思路**

三面通常是技术负责人或交叉面试，自我介绍应更强调"带人、决策和落地"：

1. 开场一句话说明经验和方向。
2. 讲一个体现技术判断和工程可控性的项目：为什么这样设计，遇到什么问题，怎么解决。
3. 补充协作和推动能力：与算法、产品的配合，任务拆分，推动落地。
4. 说明你关心的问题，如 Agent 的可控性、评测、成本，以及对国产算力场景的理解。

时间控制在 1 分钟左右，不重复前两面的细节，并主动暴露一两个可以被深挖的话题。

### 2. 你带人做过 Agent 项目吗，几个人，怎么拆工时和模块

**答题思路**

如实回答你的角色：带过就讲团队规模和分工；没有正式带过，就讲你作为模块负责人或技术主导如何协调。不要编造人数和职级。

可以按以下顺序讲：

1. **团队构成**：几个人，各自角色（算法、后端、前端、测试等）。
2. **模块拆分**：按稳定的接口边界拆，如接入层、意图与路由、检索（RAG）、工具与适配层、编排（Agent 逻辑）、评测与观测、基础设施。先定好模块间的接口和数据契约，各模块才能并行开发。
3. **工时拆分**：先做最小闭环（MVP），再逐步增强；风险高的部分（如模型效果、国产算力适配）尽早验证；留出评测集建设和联调的时间，这部分常被低估。
4. **管理动作**：每日同步、里程碑评审、代码评审、用评测集作为验收标准。
5. **复盘**：做得好的和下次会改进的地方，比如更早建立评测集。

### 3. 当算法同学坚持上自主 Agent，你作为工程侧担心可控性和成本，怎么说服对方加工作流约束

**答题思路**

核心是**用数据而不是立场沟通**，把"约束"表述成"让 Agent 更容易上线"的手段，而不是对抗。

1. **先认可对方的价值**：自主 Agent 在开放问题上的上限更高，承认这一点，建立共同目标，也就是"可上线、可持续迭代"。
2. **用数据说话**：做一次小规模对比实验，用同一份评测集比较自主 Agent 和带工作流约束的方案，看成功率、步数分布、尾延迟、每千次调用的成本和失败案例。
3. **提出折中方案，而不是二选一**：主流程用工作流写死，在局部使用自主 Agent，并加上工具白名单、最大步数、预算上限、关键步骤人工确认。
4. **说明风险在业务上的代价**：不可控的行为会导致线上事故、成本失控，也不利于排查和复现。
5. **给出演进路径**：先约束后放开，有了评测和观测，再根据数据逐步放权。

结束时约定验收指标和复盘时间，用结果决定下一步。

### 4. Agent 项目需求中途大改（比如老板要加多模态），你怎么保进度又不让链路重构炸锅

**答题思路**

按"评估 → 隔离 → 分步交付 → 回归保障"的顺序回答：

1. **先澄清需求**：确认多模态的真实目标（图片问答、OCR、语音？），哪些是核心场景，哪些是后续，把范围压缩成最小可交付版本。
2. **评估影响面**：梳理会影响的环节，输入解析、embedding 和检索、模型选择、Prompt 与工具、评测集、成本和延迟，给出工期和风险，让老板知道取舍。
3. **隔离变化，不重构主链路**：把多模态当作"新增的输入处理节点和新增的工具或模型路由"，通过已有的抽象（模型网关、工具接口、State schema 的可选字段）接入；用特性开关（feature flag）灰度，没有开启时旧链路完全不受影响。
4. **分阶段交付**：先做能用的版本（如先用 OCR 或图像描述转成文本，复用现有文本链路），再逐步升级成原生多模态。
5. **回归保障**：保持现有评测集作为回归门禁，新增多模态用例，确保旧功能不受影响。
6. **事后复盘**：沉淀可扩展的抽象，避免下次再出现同类问题。

### 5. Harness 工程你理解成哪一层，和 Orchestration、Scheduler 的边界划清

**参考答案**

Harness 是包裹在模型外面的**运行时执行环境**，负责让 Agent 的每一次运行可靠、可控、可观测。它不决定"下一步做什么"，而是保证"每一步能被稳定、安全地执行"。典型职责包括：上下文构建与注入、工具执行与沙箱、错误隔离与重试、状态持久化、权限与预算守卫、可观测性。

三者的边界：

| 层 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| Orchestration（编排） | 控制流：下一步执行哪个节点或 Agent | 图、DAG、条件路由、多 Agent 协作逻辑 |
| Harness（运行时） | 单次运行怎样被可靠地执行 | 上下文注入、工具调用与隔离、checkpoint、追踪、预算限制 |
| Scheduler（调度） | 资源和时间：任务何时、在哪个 worker 或算力上运行 | 队列、优先级、配额、并发控制、重试调度 |

可以这样类比：编排是"业务流程图"，Harness 是"每个流程实例的运行容器和保险装置"，Scheduler 是"决定容器何时在哪台机器上起来的调度员"。

三者有重叠，比如重试既可能在 Harness（单步重试），也可能在 Scheduler（任务级重新调度）。答题时要说明你的划分标准：与控制流相关的归编排，与单次运行可靠性相关的归 Harness，与资源分配相关的归调度。

### 6. Harness 四大件（上下文注入、错误隔离、状态持久化、可观测）你项目里最弱的是哪个，怎么补

**答题思路**

选一个你真实存在的短板来回答，并不是回避，面试官看重的是自我认知和改进能力。结构是：**现状 → 影响 → 补法 → 验证**。下面给出每一项常见的短板和补法，供你选取：

- **上下文注入**：问题是上下文堆积、无关信息多、关键信息被挤出。补法：分层构建 Prompt（系统指令、任务状态、检索内容、历史），设置 token 预算和裁剪策略，使用摘要和外置 scratchpad。
- **错误隔离**：问题是单个工具失败会拖垮整个任务。补法：为每个工具设置超时、重试和熔断，把错误转成结构化观测反馈给模型，给不可信的工具加沙箱，限制最大步数和预算，降级路径明确。
- **状态持久化**：问题是长任务中断后要从头开始。补法：每步做 checkpoint，使用持久化存储，节点设计成幂等，加入恢复演练。
- **可观测**：问题是出了问题无法复盘。补法：给每次运行分配 trace ID，记录每一步的输入输出、耗时、token 和错误，接入 OpenTelemetry 类的链路追踪，做指标看板和告警，并支持回放。

回答时要结合一个真实的事故或案例说明为什么它最弱，补上之后用什么指标证明变好了。

### 7. Agent 跑长任务挂了，怎么做到断点续跑且不让用户感知，幂等怎么设计

**参考答案**

**断点续跑：**

1. **持久化每一步**：每个步骤完成后，把状态（已完成的步骤、中间结果、工具输出）写入 checkpoint 存储（如 LangGraph 的持久化 checkpointer，或 Temporal 这类持久化执行引擎），不依赖进程内存。
2. **故障检测与接管**：worker 通过心跳或租约（lease）上报存活，租约过期后，任务被重新投递给其他 worker，从最近的 checkpoint 继续执行。
3. **已完成的步骤不重复执行**：已完成的 LLM 调用和工具结果被记录下来，恢复时直接回放，不重新调用，这样可以避免成本重复，也避免结果不一致，因为 LLM 的输出是非确定性的。

**让用户无感：**任务异步化，用户拿到任务 ID，前端通过 SSE 或 WebSocket 获取进度；进度和已输出的内容存在服务端，连接断开后可以按事件 ID（如 `Last-Event-ID`）续传；故障切换在后台完成，前端只会看到"处理中"。

**幂等设计：**

- 每个步骤使用稳定的幂等键，例如 `run_id + step_no`，重试时键不变。
- 有副作用的操作采用"先记录意图，后执行，再记录结果"的方式，执行前先查看是否已有结果。
- 对外部服务使用其提供的幂等键；没有的，先查询再执行。
- 数据库使用唯一约束，保证重复写入不会产生副作用。

难点是"已执行但结果未记录"的窗口：恢复时要先通过查询外部系统确认状态，再决定是否重试。

### 8. 多租户下 Agent 的上下文隔离和配额限流怎么做，寒武纪算力紧张时怎么排队

**参考答案**

**上下文隔离：**

- 所有数据都带 `tenant_id`：Redis key 前缀、数据库字段、向量库的 namespace 或过滤条件、`thread_id` 中包含租户。
- 检索阶段强制注入租户和权限过滤条件，不依赖 Prompt 来约束。
- 缓存（包括语义缓存、前缀缓存）要按租户隔离，防止跨租户的数据泄露。
- 工具执行使用租户级的凭据和沙箱，日志和轨迹按租户隔离。

**配额限流：**

- 多层限流：QPS（令牌桶）、并发数、token 用量（按分钟和按天）、成本预算，按租户和套餐分级。
- 超限返回 429 并附带 `Retry-After`，同时在 Agent 内部限制最大步数，防止单个任务耗尽配额。

**算力紧张时的排队：**

- **准入控制**：队列满时拒绝或降级，避免无限堆积。
- **优先级与公平性**：按套餐设置多级队列，使用加权公平队列，防止大租户占满资源，也避免小租户饿死。
- **任务分类**：交互式请求优先，离线、批量任务放入低优先级队列，在空闲时运行。
- **降级**：高峰时切换到更小的模型，缩短最大输出，或关闭可选的功能。
- **容量估算**：按预估 token 数（输入加 `max_tokens`）做资源预留，结合推理引擎的并发上限调度。
- 向用户提供排队位置和预计等待时间，并支持取消。

### 9. RAG 知识库每天变，增量 Embedding 和缓存失效策略你怎么设计，避免答出昨天删掉的旧政策

**参考答案**

**增量 Embedding：**

1. 为文档和 chunk 保存内容哈希和版本号。每次同步时比较哈希，只对新增和变化的 chunk 重新做 embedding。
2. 文档更新时，先删除该文档的旧 chunk，再写入新 chunk（以 `doc_id` 和版本为准），向量库、ES 同步操作。
3. 变更通过 CDC 或消息队列驱动，处理失败可重试，保证幂等。
4. 记录 embedding 模型版本，更换模型时必须全量重建，不能混用。

**避免答出旧政策：**

- **删除要真实生效**：使用 `doc_id` 删除向量和索引，并在元数据中保留 `is_deleted`、`effective_date`、`expire_date`，检索时过滤。
- **回表校验**：向量库和 ES 是最终一致的，召回后用 chunk_id 去权威库检查是否仍然有效，再送入 LLM。
- **缓存失效**：答案缓存和语义缓存的 key 带上知识库版本号，或建立"doc_id → 缓存 key"的反向索引，文档变化时精准失效；同时设置较短的 TTL 作为兜底。检索结果缓存同理。
- **回答可追溯**：答案附带来源和文档版本、更新时间，高风险领域（政策、合规）要求必须有引用。
- **监控与验证**：定期用"已删除文档的问题"做回归测试，监控索引的同步延迟。

### 10. 评估 Agent 你不能只跑准确率，说一套你用过的端到端评估体系（检索/生成/工具/成本四个维度）

**参考答案**

准确率只是结果指标，不能解释失败的原因，也无法反映成本和稳定性。完整的体系按四个维度拆分，并加上端到端的任务成功率。

1. **检索**：recall@k、MRR、nDCG，context precision 和 recall（召回的内容是否相关、是否覆盖了答案所需的信息）。需要有标注了相关文档的评测集。
2. **生成**：忠实度（答案是否有依据，没有幻觉）、答案相关性、与参考答案的正确性对比。可以用 LLM-as-judge，但要用人工抽样做校准，避免评审模型的偏差。
3. **工具**：工具选择是否正确、参数是否正确、调用成功率、冗余调用次数、轨迹效率（和最优步数比较）、错误恢复能力。
4. **成本与性能**：每个任务的 token 消耗、步数、延迟（P95、P99）、每千次调用的成本。
5. **端到端**：任务成功率，以真实业务指标定义。

工程做法：

- 建立分层的评测集（黄金集、边界案例、历史线上失败案例），每次改动 Prompt、模型或策略都跑回归，作为 CI 门禁。
- 对失败样本做归因，分到检索、生成、工具、规划哪一类。
- 线上做抽样评估、用户反馈和监控，和离线指标对照。
- 可以借助 RAGAS、LangSmith 等工具，但指标定义和评测数据要贴合自己的业务。

### 11. 最近半年你自学的 AI 新技术里，哪个是你从源码层面啃的，LangGraph checkpoint 还是 Reranker 训练

**答题思路**

只讲你真正读过、做过的，不要假装读过源码，面试官很容易追问细节。如果确实读过，按"为什么读 → 读到什么 → 怎样用到项目里"来讲。

如果选择 LangGraph checkpoint，可以围绕这些点：

- State 通过 reducer 合并，每个超步结束后由 checkpointer 保存（序列化器、thread_id、checkpoint_id）。
- pending writes 机制：同一超步里成功节点的写入会被保存，恢复时不重复执行。
- `interrupt` 和 `Command(resume=...)` 如何基于 checkpoint 实现中断恢复。
- 持久化后端（Postgres、SQLite 等）的存储结构，以及 time travel 的实现。

如果选择 Reranker 训练，可以围绕：cross-encoder 的结构、训练数据构造（正例、难负例挖掘）、损失函数（pairwise 或 listwise）、评估指标（nDCG、MRR），以及蒸馏和延迟优化。

回答要体现：读源码解决了什么实际问题（如排查恢复后状态不一致），以及你对设计取舍的理解。如果没有读过源码，就诚实说明你通过哪种方式学习，并展示你的学习方法。

### 12. 你怎么判断一个新技术（比如某国产 Agent 框架）值不值得在产线替掉 LangChain

**参考答案**

结论：不要因为"新"而替换，只有当它能解决明确的现有痛点，并且迁移成本和风险可控时才替换。可以用下面的维度评估：

1. **痛点和收益**：现有方案的问题是什么（性能、可控性、国产算力适配、可观测、维护成本），新框架能否带来可量化的改善。
2. **用评测数据验证**：用自己的业务数据和评测集做对比（成功率、延迟、成本、稳定性），不要只看官方 demo。
3. **成熟度与生态**：版本稳定性、社区活跃度、文档、维护团队的持续性、License、安全更新、与现有模型和工具的兼容性。
4. **可控性与可观测**：是否支持 checkpoint、人机协同、追踪，能否接入现有的监控。
5. **迁移成本与锁定风险**：重写量、团队学习成本、是否有抽象层可以降低耦合、能否回滚。
6. **渐进策略**：先在非核心的新场景试点，灰度对比，达到预设的验收标准后再扩大；业务代码通过自己的适配层隔离框架，降低未来替换的成本。

同时也要认识到：LangChain 的缺点（抽象过重、版本变动快）可以通过只使用其中稳定的部分（如 LangGraph 做编排）缓解，并不一定需要替换。

### 13. 手撕算法：给定一个工具调用序列和观测结果序列，检测 Agent 是否进入死循环，并返回首次重复子路径起点（LeetCode 风格）

**参考答案**

问题定义：把每一步抽象成 `(工具名及归一化参数, 观测结果)`，若序列中某个位置 `i` 开始，长度为 `L` 的一段子路径紧接着又完整重复了一次（`steps[i:i+L] == steps[i+L:i+2L]`），就认为进入了循环。返回满足条件的**最小起点 `i`**（同一起点取最短的 `L`），没有则返回 `-1`。

思路：令 `lcp[i][j]` 为从 `i` 和 `j` 开始的最长公共前缀长度，则有 `steps[i]==steps[j]` 时 `lcp[i][j] = lcp[i+1][j+1] + 1`。位置 `i` 处存在周期为 `L` 的连续重复，当且仅当 `lcp[i][i+L] >= L`。从小到大枚举 `i` 和 `L`，第一个满足的就是答案。

时间复杂度 \(O(n^2)\)，空间 \(O(n^2)\)（可以用滚动数组优化为 \(O(n)\)）。Agent 的步数通常不大，足够使用。

```python
def find_loop_start(calls, observations):
    """返回 (起点下标, 循环长度)，没有循环返回 (-1, 0)"""
    steps = list(zip(calls, observations))
    n = len(steps)
    # lcp[i][j]：从 i 和 j 开始的最长公共前缀长度，j > i
    lcp = [[0] * (n + 1) for _ in range(n + 1)]
    for i in range(n - 1, -1, -1):
        for j in range(n - 1, i, -1):
            if steps[i] == steps[j]:
                lcp[i][j] = lcp[i + 1][j + 1] + 1

    for i in range(n):
        for L in range(1, (n - i) // 2 + 1):
            if lcp[i][i + L] >= L:
                return i, L
    return -1, 0


# 示例：A B C B C -> 从下标 1 开始，长度为 2 的 "B C" 重复
print(find_loop_start(["A", "B", "C", "B", "C"], ["1", "2", "3", "2", "3"]))  # (1, 2)
```

工程上的补充：

- 工具参数要先归一化（排序键、去掉时间戳等无关字段），观测结果可以取哈希，否则同样的循环会因为微小差异而漏检。
- 如果只关心"相同的调用且结果没有变化"，可以只比较 `(调用, 观测)` 的组合，这是比只比较调用更可靠的判定，因为合理的重试可能得到不同的结果。
- 线上可以增量检测：每次追加一步，只检查以末尾结束的重复，同时配合最大步数和重复次数阈值（如重复 3 次）来终止。

### 14. 如果你来定寒武纪 AI Agent 平台的技术基线，框架栈、模型路由、评测门禁你分别卡什么标准

**参考答案**

基线的原则是：**可控、可观测、可替换、可验收**。具体的数值阈值应该由业务和实测数据确定，下面给出卡点的维度。

**框架栈：**

- 编排层使用支持状态持久化、条件路由和人机协同的图式框架（如 LangGraph 一类），要求可以做 checkpoint 和断点恢复。
- 版本锁定，核心依赖有升级和回归流程；业务代码通过自己的适配层隔离框架，降低替换成本。
- 要求链路追踪（接入 OpenTelemetry 类标准）、结构化日志，以及工具的 schema 约束和超时、重试、幂等规范。
- 推理引擎：优先选择与寒武纪官方适配的开源引擎，通过统一的 OpenAI 兼容网关对上层暴露。

**模型路由：**

- 分层使用：分类、改写等简单任务用小模型，复杂规划用大模型。
- 每条路由配置降级和兜底路径，有熔断和限流，按租户设置配额。
- 模型版本固定，切换要经过评测，支持灰度和回滚。
- 路由策略要考虑国产算力的容量，高峰时可以降级。

**评测门禁：**

- 变更（Prompt、模型、框架版本）上线前，必须通过黄金评测集的回归，覆盖检索、生成、工具、成本四个维度。
- 关键指标（任务成功率、工具调用准确率、忠实度）不得低于当前基线，成本和 P95 延迟不得恶化超过约定的幅度。
- 安全用例（注入、越权、敏感数据）必须通过。
- 灰度发布加线上监控，不达标可自动回滚。

### 15. 聊一个你做砸了的 Agent 场景，根因是模型、工程还是产品定义，重来一次你怎么改

**答题思路**

选一个真实的失败案例，不要编造；选择"有教训、你能掌控一部分原因"的案例，比选完全是外部原因的更加可信。

结构：

1. **场景和目标**：当时要解决什么问题，预期是什么，实际结果怎样（用事实描述，如上线后被回滚、用户使用率低、成本超支）。
2. **根因分析**：不要把原因简单归到某一类，而是用证据拆解。
   - 模型：能力不够、幻觉、工具调用不稳定。
   - 工程：缺少评测、没有限制步数和预算、没有可观测、没有兜底。
   - 产品定义：场景本身不适合 Agent，成功标准模糊，用户预期过高。
   通常是多个因素叠加，你需要说明哪个是主因，以及你是如何判断的。
3. **当时的处理**：怎么止损，怎么沟通。
4. **重来一次的改法**：先定义清晰的成功标准和评测集；从受限的工作流起步，再逐渐放权；先做小范围试点；加上可观测和人工兜底；必要时果断缩小范围或放弃。
5. **反思**：你从中形成的方法，例如"上线前先有评测集"。

态度上要承担责任，不推卸，也不要过度自责。

## HR 面

### 1. 自我介绍

**答题思路**

HR 面的重点是稳定性、动机和沟通，技术细节可以减少。控制在 1 分钟，结构是：

4. 对这个岗位的兴趣和匹配点，如对国产算力和 Agent 平台的关注。

语气自然，避免大段技术名词，不要回避离职的变动，如果有的话，用积极的角度解释。

### 2. 为什么看寒武纪，芯片厂做 Agent 和你之前做纯应用有啥不同预期

**答题思路**

分成两部分来回答：

1. **为什么选寒武纪**：结合真实的动机，例如对国产算力和软硬件协同的兴趣，希望接触推理和底层优化与上层应用结合的场景，看重公司的技术方向和平台价值。避免只说"大厂、稳定"或者只谈待遇。
2. **预期的不同**：表达你对差异的理解，并保持开放：
   - 约束不同：算力和生态有限，需要在性能、成本、可控性上做更多取舍。
   - 工作重心不同：除了应用逻辑，还要关注推理框架适配、性能优化、与硬件团队协作。
   - 价值不同：可能更偏平台和基础能力，服务内部和生态客户，而不是单一的业务指标。
   - 节奏不同：适配和稳定性的工作更长线。

最后表达你做好的准备，例如愿意学习硬件和推理栈的知识。不要贬低以前的工作。

### 3. 你觉得自己做 Agent 工程最不可替代的一点是什么

**答题思路**

回答要具体、可验证，而不是空泛的"学习能力强"。建议选一个你真正擅长的点，用"能力 + 证据 + 价值"来表达：

- 例如：把 Agent 从 demo 做到可上线的能力，包括评测体系、可控性约束（步数、预算、工作流加自主的边界）、故障恢复和可观测。
- 证据：用一个具体的案例说明，你做了什么，指标有什么变化（只说真实的）。
- 价值：这个能力对寒武纪的平台意味着什么，如在算力受限时，如何用工程手段控制成本和稳定性。

避免夸大，不要说"别人都做不到"，用"我的特点是…"这种表述。

### 4. 项目里和算法/产品吵得最凶的一次，怎么收场的

**答题思路**

选择一个真实的、"对事不对人"的分歧，按 STAR 结构讲：

1. **背景**：什么分歧，例如要不要上自主 Agent、需求范围、上线时间、成本。
2. **立场**：双方的出发点和诉求都说清楚，展示你理解对方的合理性。
3. **行动**：你如何推动解决：用数据和实验代替争论，拆解成可验证的假设，找到折中方案，必要时升级给共同的上级，并明确决策人。
4. **结果**：最终采取了什么方案，关系和项目有什么变化，用事实说明。
5. **反思**：之后你会更早对齐目标和验收标准。

注意：不要把对方说成"不懂"，不要显得好胜，也不要说"从不吵架"。

### 5. 当前薪资和预期，不接受降薪的前提下底线是多少
