### 2. 讲一下你最近做过的 Java 大模型应用项目，整体链路是什么

**答题思路**

用自己真正做过的系统。没有上线项目就讲你完整跑通过的练习，并说明还没进生产。按一次请求的生命周期讲，不要按组件名单背。

1. 场景一句：谁在问，成功是答对知识，还是办成一件事。同步对话还是异步任务。
2. 入口：鉴权、会话号、限流放在模型调用之前。
3. 编排：哪些请求只检索后回答，哪些会进工具循环。下一步是固定流程，还是模型选工具。
4. 模型接入：ChatClient 包在哪一层，流式还是一次性返回，超时和降级落在哪。
5. 状态：短会话放哪，工具调用记录落哪。只讲你做过的存储。
6. 你的职责和同事的职责分开。最后留一个联调或线上真实出过的问题，方便对方往下挖。

没有把握的 QPS 和费用不要报数字。

### 3. Spring AI 里 ChatClient 和 ChatModel 是什么关系，为什么有了 ChatModel 还要封装 ChatClient

**参考答案**

结论：`ChatModel` 是模型端口，`ChatClient` 是给业务用的调用门面。门面持有一个 `ChatModel`，真正发请求时仍落到它的 `call` / `stream`。

`ChatModel` 的核心是 `call(Prompt) → ChatResponse`，流式再提供 `stream(Prompt)`。OpenAI、Ollama、通义这些实现都走这个接口，用来换供应商。它不管会话、检索和工具循环。

`ChatClient` 在 Builder 上绑默认 system、Advisor 和工具，调用处写成 `prompt().user(...).call().content()`。框架把这次请求装成 `ChatClientRequest` 走进 Advisor 链；同步链的最后一环是 `ChatModelCallAdvisor`，流式则是 `ChatModelStreamAdvisor`，由它们调用 `ChatModel`。同一个模型可以建多个 `ChatClient`，客服和内部审核用不同的默认提示词和工具集。

只留 `ChatModel` 的话，拼 Prompt、插记忆、接检索、跑工具、把结果转成对象，都要在每个调用点重写。`ChatClient` 把这些收成一条链。

换模型换的是 `ChatModel` 这个 Bean，不是改业务调用。`ChatClient` 也不是另一套模型协议。

### 4. Spring AI 的 Advisor 链是什么，和 Spring AOP 的 Advisor 有什么区别，举两个自定义 Advisor

**参考答案**

结论：Advisor 链是围着这一次模型调用的拦截链，类似过滤器。它不是 Spring AOP，也不会织到任意 Bean 方法上。

同步走 `CallAdvisor.adviseCall`，流式走 `StreamAdvisor.adviseStream`。每个顾问可以改请求，再调用 `chain.nextCall`；返回时逆序改响应。`getOrder()` 越小，越先处理请求、越后处理响应。链尾由框架放上调用模型的顾问。顾问之间用请求上的 context 传参。

和 AOP 的区别：AOP 的 Advisor 是切点加通知，靠代理拦 Bean 方法。Spring AI 的 Advisor 只拦 ChatClient 这一次模型请求，注册在 `defaultAdvisors` 或单次 `advisors()` 上，没有切点表达式。同名只是借用。

顺序上，先让记忆进入提示词，再检索。指代要先解开：「那单」得先还原成运单号，再拿这个短查询去向量化，不要把整段历史拿去嵌入。

两个自定义例子：

1. 脱敏顾问：调用前掩码手机号和地址，调用后检查回答没有把原文回显出来。
2. 上下文预算顾问：按 token 估算丢掉更早的历史，保留系统规则和本轮问题。审计适合放在返回之后，异步记模型名、token 和耗时，原文不落日志。

顾问里不要做退款这类写操作。写操作交给带幂等键的工具。

### 5. 用 Spring AI 做 Tool Calling 时，@Tool 注解和 ToolCallback 怎么选，工具描述写不好会有什么问题

**参考答案**

结论：`@Tool` 是声明方式，`ToolCallback` 是运行时的工具接口。注解方法会被适配成 `ToolCallback`，再交给 ChatClient。

工具需要注入 Repository、走现有 Spring Bean 时，用 `@Tool` 和 `@ToolParam`，通过 `tools(bean)` 或 `ToolCallbacks.from(...)` 注册。Bean 也可以交给 `MethodToolCallbackProvider`，由自动配置收进 ChatClient。工具要到手写 schema、用 lambda，或把 MCP 工具适配进来时，直接建 `FunctionToolCallback`，或自己实现 `ToolCallback`。选的是谁来生成这个回调，不是两套互斥能力。

描述要写清何时调用、何时不要调用、参数格式和有没有副作用。写不好会出现：该查轨迹时不调用；两个工具描述重叠，模型来回换工具，看起来像死循环；参数缺少格式，运单号被编造，校验失败后又重试；把退款写成查询，没拿到单号就发起写操作；返回值又长又含糊，模型读不懂就再调一次。工具名用稳定的动词短语。失败信息要能让模型改参数，而不是一段栈。循环次数要有上限。

模型只负责选出工具和参数。权限和幂等必须在 Java 里再查一遍。

### 6. RAG 在你们项目里是怎么落地的，文档切分用的什么策略，为什么不用固定字数切

**答题思路**

按你真实的知识库讲。没有做过 RAG，就说清楚边界，不要把 Demo 说成生产。

1. 语料是什么：制度、FAQ、操作说明，还是表格。谁在问，答案能不能公开。
2. 流水线按顺序：解析、切分、向量化、带元数据入库、召回、是否重排、拼进提示词。只展开你做过的环节。
3. 切分这样讲：先按标题、条款、问答对切开；超长的小节再按段落和句号递归切，并留少量重叠。检索用较短片段，送进模型的是它所属的整节。每个片段带上文档号、标题路径、版本和业务线。
4. 固定字数会切在句子、表格和条款中间，片段自己读不通，标题也丢了。重叠只能减轻断句，补不回结构。字数相等也不等于都是一个可回答的单位。固定窗口只适合某一节已经按结构切开、但仍然超长时的兜底。
5. 当时如果用的就是固定字数，直接说，并补你后来在哪类文档上看到了切断。不要改口编一套更高级的方案。

### 7. Embedding 模型怎么选的，中文场景用 bge 还是 m3e，相似度用余弦还是内积，为什么

**参考答案**

结论：中文物流知识库优先在 BGE 里选，常见是 `bge-m3` 或 `bge-large-zh-v1.5`。m3e 适合已经跑通、语料短、只想少折腾的场景。排序用余弦；向量做了 L2 归一化之后，内积和余弦的排序相同。

m3e 是较早的中文检索模型，短文本 FAQ 够用，一般不用查询指令。`bge-large-zh-v1.5` 查询侧通常要加「为这个句子生成表示以用于检索相关文章：」，文档侧不加。`bge-m3` 能处理更长文本，稠密向量之外还可以出稀疏向量，默认检索可以不加指令。最终用自己的问题集看 Recall@k。运单黑话、改址、时效不一定跟公开榜单一致。索引和查询必须是同一个模型、同一种预处理，换模型就要整库重嵌。

BGE 按余弦来用。归一化之后改用内积，是为了让 Milvus、pgvector 少算一次模长，结果应和余弦一致。没归一化就用内积，向量长度会参与排序，长文档可能占便宜。pgvector 的 `<#>` 是负内积，越相似值越小，要按升序取；`<=>` 才是余弦距离。评测用余弦、线上用没说明的内积，排序会对不上。

### 8. 向量库用的什么，PGVector 和 Milvus 在 Java 项目里怎么选型，顺丰这种物流知识库场景你选哪个

**参考答案**

结论：制度、网点和异常说明这类知识库，数据量还没到专门向量库的规模，又要按业务线、组织和版本过滤时，选 PGVector。已经有高并发、上千万片段，或运维上已经在用 Milvus，再选 Milvus。

PGVector 跟业务数据在同一个 PostgreSQL 里，过滤就是 SQL，片段可以和文档版本、生效时间一起更新，备份也只有一套。Spring AI 有 `PgVectorStore`，索引常用 HNSW。代价是向量检索和业务查询抢同一台库的内存和 IO。规模上去之后要单独拆库，它也不是为超大 ANN 设计的。

Milvus 能分片，能把索引和查询水平扩出去，标量过滤也有。元数据和业务表不在一个事务里，删除、改版本要自己对齐。Java 用官方 SDK 或 Spring AI 的 Milvus 存储。组件比多装一个 Postgres 扩展重。

物流知识库更常见的难点是「这份制度过期了没有、这个组织能不能看」，不是裸向量 QPS。默认用 PGVector，原文和版本放在库里，查询带上版本和权限。测出 Postgres 的 ANN 成为瓶颈，再把向量拆到 Milvus，原文和权限仍以关系数据库为准。不要两套库同时当权威。

### 9. RAG 召回不准怎么排查，是 chunk 问题、embedding 问题还是 rerank 问题，分别怎么验证

**参考答案**

结论：先准备一批「问题 → 应该命中的片段」，分层看这段文字还在不在候选集里。一次只改一层。上下文里已经有答案，只是模型没用，那就不是这三层的问题。

1. chunk：库里根本没有一块完整包含答案。打开命中的片段，看句子、表格、条款是不是被切断，标题在不在。关键词能在原文里找到、在片段表里找不到，就是切分或入库漏了。只重切这一类文档。
2. embedding：片段是完整的，关键词或 BM25 能把它打进前排，向量的前 20 到 50 名里却没有。直接算问题向量和这块黄金片段的相似度，核对查询指令、是否归一化、索引模型和查询模型是否同一个。对得上就是向量召回不行，再考虑换模型、查询改写或加词法检索，然后按新模型重嵌。
3. rerank：融合后的候选里已经有黄金片段，过完重排或卡完阈值就没了。对比重排前后的 Recall@k。常见原因是重排模型不吃这类中文、片段被截断、标题没传给重排器、阈值太狠。

权限和版本条件写错，会把黄金片段提前滤掉。先拿掉过滤再看一遍，避免误判成模型问题。

### 10. Agent 的 ReAct 循环讲一下，和普通工作流（Workflow）本质区别是什么

**参考答案**

结论：ReAct 是模型每一步自己决定调哪个工具；工作流是程序里写好下一步去哪。差别在于控制流在代码里，还是交给模型临时决定。

一轮 ReAct：模型根据当前消息产出工具调用，应用执行工具，把观察结果塞回消息，再调用模型，直到它给出最终回答或步数到顶。下一步取决于上一次观察，路径不固定。适合「先查轨迹，不够再查网点，再决定要不要引用改址规则」这种事先列不全的问题。代价是慢、费 token、不稳定，工具描述一重叠就可能来回调。

工作流把分类、检索、生成、校验写成固定节点和条件边。模型只在某个节点里填内容，不负责调度。超时、重试和审计按节点加。路径一多，图会变成条件迷宫。

生产上常用工作流包住外壳：能确定的步骤不交给模型；只有其中某个节点允许短循环，并限制工具白名单和最大步数。写操作不要放进没有上限的 ReAct。

ReAct 不是另一个模型，只是调用方式。没有步数上限、工具又不能安全重试，循环会直接打满配额。

### 11. Spring AI Alibaba 的 Graph 框架干嘛的，单 Agent 和多 Agent 在你项目里怎么取舍

**参考答案**

结论：Graph 是把 Agent 编排成状态图的运行时。节点读同一份状态、写回自己的结果，条件边决定下一跳；编译之后可以停住，把状态存下来再恢复。

它解决的是多步调用不能只靠一个 while 硬写：检索、模型、工具、人工审批可以是不同节点；状态里有消息、工具出参和业务字段；在某个节点前暂停，配合 checkpoint，进程重启后按线程号接着跑。路由、监督者、移交这些多 Agent 模式也是画在这张图上，不是另一套产品。

单 Agent 是一个提示词、一组工具、一个循环。工具少、职责不打架、又在意延迟时用它，轨迹最好读。查轨迹再答制度，经常一个 Agent 就够。

多 Agent 用在工具多到描述分不清、对外话术和内部规章互相干扰、退款权限不能跟闲聊放在同一个工具集里的时候。拆开要付路由错误、重复上下文和交接丢字段的成本。

先用图把固定阶段定下来，图里仍然可以只有一个 Agent 节点。单提示词装不下规则，或工具选错明显变多，再拆开。结合自己的系统时，只拿真实的工具数量和有没有写操作来对号；没拆过就不要说已经上了多 Agent。

### 12. MCP 和 Function Calling 区别，为什么 2025 年后大家都在聊 MCP

**参考答案**

结论：Function Calling 是模型侧的调用协议，MCP 是应用和外部工具服务之间的发现与调用协议。MCP 没有取代 Function Calling，两者叠在一起用。

Function Calling 把工具的名字、说明和 JSON Schema 放进这次模型请求；模型返回要调用的名字和参数；应用执行后把结果再送回模型。工具多半就在你的进程里。各家厂商报文字段不同，Spring AI 的 `ToolCallback` 把这个差异挡住。

MCP（Model Context Protocol）规定独立的工具服务怎么被发现：客户端用 stdio 或 HTTP 连上服务器，拉工具列表、执行工具，也可以读资源和提示词模板。Spring AI 的 MCP 客户端把这些工具转成 `ToolCallback`，模型最后仍通过 Function Calling 决定叫哪一个。

2025 年后它被频繁提到，是因为以前每个 Agent 框架各写一套插件，工具数和应用数要相乘。一个运单 MCP 服务可以被桌面助手、IDE 和 Java 应用共用，工具的权限和发布留在业务团队。它同时覆盖工具、资源和提示词，不只是一次 RPC。

模型并不「说 MCP」。模型只会产出工具调用；MCP 是这个调用出进程之后怎么到达对方。

### 13. Redis 在你们 AI 项目里用在哪里，对话上下文存 Redis 要注意什么（过期、序列化、多端隔离）

**参考答案**

结论：Redis 放热数据和短会话，不放审计真相。对话上下文可以放，但要有过期、长度上限，并且按会话隔离。

常见用途是最近几轮消息、限流计数、幂等键、检索缓存。语义缓存只适合稳定、且不涉及个人运单的问答，键里要带知识库版本。轨迹查询和写操作的结果不要当普通问答去缓存。回答「你们用在哪」时只讲真实用过的；会话不在 Redis，就直接说不在。

上下文本身有三件事：

1. 过期按会话，不按永久键。有新消息再续期，会话结束就失效。幂等键的保留时间和会话分开，不要共用一个 TTL。不设过期，历史会一直堆，隔天的旧轨迹也会被当成当前事实。
2. 序列化用 JSON 文本，带 schema 版本，字段包括角色、内容和必要的工具摘要。不要用 JDK 序列化。写入前按条数或 token 截断，单键保持很小。用了 Spring AI 的 Redis Chat Memory，键前缀和序列化要跟应用约定一致。
3. 键至少包含用户和应用自己的会话号，按租户、用户、会话分开。同一个人的小程序和电话要不要共一份记忆，由产品决定，不能默认混用，也不能只按用户号存。Builder 上写死一个 conversationId，所有人会共用一份历史。

Redis 里的记忆不是权限边界。工具执行前仍要在服务端鉴权。

### 14. MySQL 侧怎么存 Agent 的执行轨迹和工具调用日志，表怎么设计

**参考答案**

结论：一次用户请求一行运行记录，循环里的每一步和每一次工具调用分开存。MySQL 是审计依据，Redis 只缓存会话。

`agent_run` 记运行号、会话号、用户、traceId、状态、模型名、提示词版本、token 用量、起止时间和错误码。状态至少要能表达运行中、等待人工、成功、失败、超时、不确定。最终回答可以只存摘要。嵌套 Agent 用 parent_run_id。

`agent_step` 记 run_id、步骤序号、类型（模型、工具、人工）、状态、耗时和这一步的 token。思考文本可空，很多模型并不单独给出 thought。

`tool_call_log` 记 step_id、模型给出的 tool_call_id、工具名、掩码后的参数和结果、是否成功、业务幂等键、起止时间。tool_call_id 用来关联这一次模型调用；幂等要看业务键，因为模型重试会换一个新的 call id。结果很大时，库里只留对象存储地址和截断摘要。

索引做会话号加时间、traceId、工具名加时间。手机号和地址入库前掩码。「调用已发出、结果未知」必须能落下来，方便进程挂了以后对账。轨迹表不替代下游业务单据。退款是否发生，以支付单上的幂等键为准。

### 15. 大模型接口慢，QPS 上不去，你在 Java 侧做了哪些兜底（线程池、CompletableFuture、SSE、限流、降级）

**参考答案**

结论：慢的根子多半是供应商的时延和配额。Java 要做的是隔离、超时、背压和少调用，不是把线程池调大。

模型调用用单独的有界线程池，和查运单的业务池分开。队列有界，拒绝时快速失败或降级。调用方如果是 Tomcat 线程，不要用 `CallerRunsPolicy`，否则提交处就把容器线程堵死。池大小按供应商允许的并发来，不按 CPU 核数。

并行的检索可以用 `CompletableFuture` 合并，每次调用带超时，超时就走兜底。非幂等工具超时后不能直接再提交一次。

同步接口会把容器线程占满。面向用户的回答用 SSE：WebFlux 返回 `Flux`，或 MVC 用 `SseEmitter` 订阅流。网关关掉响应缓冲；工具执行的空档发心跳；浏览器一断开就取消上游模型请求。`ChatClient.stream().content()` 吐的是文本增量。

限流按用户、按密钥、按全局做，同时卡请求数和 token。超限就明确拒绝，不要在池里排队到超时。熔断看错误率和超时率，打开后走降级：稳定 FAQ 读缓存，或换更短的上下文、更小的模型，或直接说明暂时查不了。没有缓存的运单状态不要编一条。

Agent 循环会把一次用户请求放大成多次模型调用。步数上限本身就是 QPS 措施。

### 2. 接着一面项目往下挖，你们 Agent 调用工具失败或超时，状态怎么回滚，怎么保证幂等

**答题思路**

挑一个你系统里真实的写操作讲。没有写操作就讲查询工具，并说明查询失败不存在业务回滚，只是重试和告知用户。按时间顺序讲。

1. 先分工具：只读可以重试。短信、退款、拦截一旦发出去，把 Agent 的内存滚回去，外部世界不会跟着回去。
2. 调用前先把步骤写成待执行。幂等键用运行号、工具名和业务单号组成，传给下游，下游用唯一约束接住重复请求。不要只用模型的 tool_call_id：模型一重试就会换新 id，下游会当成另一次退款。tool_call_id 只做日志关联。
3. 成功就把下游结果写回这一步，循环继续。失败且下游明确没受理，才允许用同一把键重试，并有次数上限。
4. 超时或进程挂了，不先假设没执行。用同一把键向下游查询：已有单据就记成功并继续；确认没有就重试；查不清就停在不确定，交给对账或人工。禁止模型再发明一次退款。
5. 补偿只在业务确有逆向接口、且正向已经确认成功时才做。由服务端按状态机触发，不由模型看着聊天记录决定。
6. 恢复时从最后一条已落库的步骤接着走，不要把整段 ReAct 从头再跑。

没做过的环节直接说没有，不要编一张没上过的状态机。

### 3. Agent 多轮对话记忆怎么设计，短期记忆放哪，长期记忆放哪，上下文超长怎么压缩

**参考答案**

结论：短期记忆是这次会话的最近消息，长期记忆是跨会话仍有用的结构化事实。超长时先删工具原文，再摘要旧回合，最近几轮保持原话。

短期放 Redis 或 `MessageWindowChatMemory`，键是会话号，只留窗口内的用户、助手和必要的工具摘要，并设滑动过期。它解决的是「刚才那个运单号还算数吗」。

长期放数据库：用户偏好、未关闭的工单、已经核实过的身份结论。用用户号精确查，必要时再按当前问题检索一小段。不要把历史会话全文嵌进向量后整段灌回提示词。写入要经过规则或人工，模型随口一句不能变成永久事实。

压缩按这个顺序：

1. 旧的工具入参和返回先收成一句结果。运单号、状态、时间单独留结构化字段，不放进散文摘要。
2. 更早的回合收成滚动摘要：来意、已做决定、还没解决的问题。每轮增量更新，不要每次把全历史重新摘要一遍。
3. 系统规则、本轮问题和最近若干轮保持原文。摘要模型也会丢单号，所以槽位优先于摘要。
4. 预算按本次模型的上下文，给出回答和工具 schema 留余量，不要顶满。

记忆不是权限。换了会话号，不应自动继承上一通的手机号和地址，除非身份核验还有效。

### 4. Human-in-the-loop 场景（比如 Agent 要发起退款）怎么在 Spring AI 里插审批 checkpoint

**参考答案**

结论：审批点要落在服务端状态上。模型口头说「用户已同意」不算数。Spring AI 核心没有持久化断点；断点要么做在工具状态机上，要么做在 Spring AI Alibaba Graph 的暂停和 checkpoint 上。

工具状态机更直白。退款工具不调用支付，只把待审批写入 `agent_run`：工具名、掩码参数、幂等键、当前节点。工具结果返回「已提交审批」，循环在这里结束，并告诉用户等待人工。审批通过后，由后台用同一把幂等键真正调用支付，再把结果写回这趟运行。拒绝就只通知，不调用支付。过期未批要有超时状态。

Graph 的做法是把提议和执行拆成两个节点，在审批节点前暂停。编译时带上 checkpoint，演示可以用内存，生产用 Redis 或数据库；恢复必须用同一个 threadId。审批人、通过与否写回状态再继续跑。进程重启靠的是这份状态，不是模型重新读聊天记录。Builder 的方法名在 1.0 到 1.1 有过调整，讲清暂停点、状态内容和恢复键即可。

两种做法都要满足：副作用发生在恢复之后，且只有一次；审批人的权限在 Java 里校验；金额以落库快照为准，不从后来的模型输出里重新解析。

### 5. RAG 知识库增量更新怎么做，文档改了一句话是全量重建还是局部更新，向量怎么删旧留新

**参考答案**

结论：改一句话不做全库重建。按文档做差异：没变的片段不重嵌，变了的片段删旧向量、写入新向量。线上查询只看见当前版本。

文档和每个片段都保存内容哈希。切分键尽量稳定，用标题路径加条款，而不是全局第 N 个固定窗口。固定窗口改一个字，后面的窗口会全部错位。解析后对比哈希：新增的嵌入并插入，消失的删除，相同的跳过。

PGVector 可以在同一事务里删除该文档的旧片段再插入新片段，查询不会看见半截版本。Milvus 没有这个事务，就让查询条件带上当前版本号；新版本可搜索之后，再按文档号删掉旧版本。删失败只多占空间，不影响正确性。先删后嵌、又没有版本条件，中间会空窗。

同一模型、同一文本的嵌入应可重复，哈希没变就不要再请求一次嵌入。换了嵌入模型或改了切分算法，才对该文档或全库重嵌。原文和版本以关系数据库为准，向量库只是索引。权限和生效时间写在元数据里，旧版本不能再被过滤条件命中。

### 6. 混合检索（向量 + BM25）在 Java 里怎么拼，权重怎么融合，rerank 模型接在哪个环节

**参考答案**

结论：两路各自取回一截候选，用名次融合。不要把 BM25 原始分和余弦直接相加。重排接在融合之后、送进提示词之前。

Java 里并行查。向量走 PGVector 或 Milvus；BM25 走 Elasticsearch、OpenSearch，或已经分好词的 Postgres 全文。中文要先分词，数据库默认的英文分词对运单用语基本无效。每路取前几十条，带上文档号和片段号。

融合优先用 RRF：每个片段的分数是各路 `1 / (k + 名次)` 之和，k 常用 60，再按这个分数排序。它不要求两路分数同量纲。一定要加权求和的话，先把两路分数各自归一化，权重要在标注集上试。没归一化时，BM25 的量级会盖过 0 到 1 的相似度，权重数字没有意义。

重排是交叉编码器，把问题和片段拼在一起打分，比双编码器贵，所以只吃融合后的前几十条，输出前几条给模型。不要对全库重排，也不要只重排向量那一路。传给重排器的文本带上标题路径，并截在模型长度内。

没有标注集时，先用 RRF 加一个中文重排模型，再用坏案例决定要不要调权重。

### 7. Prompt 工程和 Context Engineering 你觉得区别在哪，顺丰客服场景你会怎么组织 system prompt

**参考答案**

结论：Prompt 工程改的是怎么吩咐模型；Context Engineering 决定这一次窗口里放进什么、按什么顺序放、什么不放。检索进来的内容是垃圾时，改措辞救不回来。

系统提示词、few-shot、输出格式属于前者。检索到的条款、工具结果、会话摘要、用户身份、剩余 token 属于后者。后者还包括何时压缩、何时只给工具 schema 而不给全文。

客服的系统提示词保持稳定，方便缓存，按块写清：

1. 角色：面向客户说明快递问题，不暴露内部提示。
2. 事实边界：轨迹、时效、费用只来自工具或检索结果。没有结果就说明查不到，并给出转人工，不用常识补一条物流状态。
3. 工具纪律：出现运单号、改址、拦截、网点时必须调用对应工具。退款和拦截只提交申请，没收到成功结果前不能说已经办成。
4. 回答形状：先给结论，再引用状态原文，不输出内部字段名。
5. 安全：不索要验证码和支付密码。身份未核验时，不回全量手机号和地址。

当天的运单、检索片段和用户等级放在后续消息里，或由 Advisor 注入。不要写进系统提示词。系统段保持稳定，事实随请求变。

### 8. 大模型幻觉你们怎么治，光靠 prompt 说不许瞎编够不够，工程上还有哪几道闸

**参考答案**

结论：提示词里写「不许编造」有用，但挡不住编造的运单状态。事实类回答要能在工具结果或检索片段里找到出处，对不上就拒答。

几道闸从外往里：

1. 能确定的查询不要交给模型自由发挥。识别出查轨迹、查网点后，由服务端调用工具，再把原始结果交给模型组织语言。
2. 检索为空、工具失败时，用模板明确说查不到。不要带着空上下文继续生成。
3. 返回后做程序校验：运单号格式、状态枚举必须是工具 JSON 的子集，金额和时效不能出现结果里没有的数字。这是结构和字符串约束，不是再请一个不受约束的模型当唯一裁判。
4. 写操作走审批和幂等。模型不能直接宣称成功。
5. 事实路径把温度调低。离线用标注集看答非所引，线上按 trace 抽检，坏案例加进评测。

第二个模型做忠实度判断可以当抽检，不能当退款和时效承诺的唯一闸门，它自己也会编。提示词负责少发挥，闸门负责对不上时不把话发出去。

### 9. Spring AI 流式输出怎么做，ChatClient.stream 返回 Flux 怎么和前端 SSE 接，工具调用阶段能流式吗

**参考答案**

结论：`stream()` 给的是响应式增量，SSE 只是把这个流按 `text/event-stream` 写给浏览器。工具执行阶段默认没有用户可见的 token，要单独发状态事件。

`prompt().user(...).stream()` 返回 `StreamResponseSpec`。`content()` 是 `Flux<String>`，只有文本增量；`chatResponse()` 才带上元数据和工具调用片段。WebFlux 把这个 `Flux` 标成 `TEXT_EVENT_STREAM` 即可。MVC 则订阅它，逐段 `SseEmitter.send`，结束时 complete，出错时 completeWithError。客户端断开要 dispose 订阅，让访问模型的 HTTP 请求一并取消。

网关和 Nginx 关掉这段响应的缓冲，读超时要大于生成时间。工具还在跑、暂时没有 token 时发注释心跳，避免中间设备把连接掐掉。

工具阶段，框架会把流式的工具参数拼完整，执行 Java 方法，再发起下一轮模型流。`content()` 在这段时间是空档，参数片段不应直接推给客户。可以另开一种 SSE 事件告诉前端正在查运单。多轮工具就是多次空档。`returnDirect` 的工具不会再回到模型生成第二段文本。

流式降低的是首字等待，不降低总 token 时间。限流和超时仍然要算完整次调用。

### 10. 生产级 AI 应用的可观测性怎么做，trace 里要埋哪些点（token、tool、retrieval、cost）

**参考答案**

结论：一次用户请求一条 trace。检索、每一次模型调用、每一次工具调用各是一个 span。费用和排障靠这些字段，不靠事后翻聊天记录。

Spring AI 的 ChatClient 已有 Micrometer observation。trace 上下文要传进工具和线程池，异步执行器用包过 trace 的那种，避免断链。`agent_run` 的 traceId 和日志用同一个号。

模型 span 记模型名、提示词版本、结束原因、耗时、首 token 时间，以及 usage 里的 prompt 和 completion token。费用用自己维护的单价表乘 token。单价会变，不要写死在代码里当制度。检索 span 记走了向量还是 BM25、过滤条件、top-k、命中文档号和分数、是否空结果。重排单独记前后名次。工具 span 记工具名、成功或失败、错误码、幂等键和耗时，不记完整手机号和地址。

指标看 QPS、首 token 和总时延、工具失败率、检索为空的比例、单次 token。质量反馈用同一个 traceId 回链。

提示词原文默认不进日志。需要回放时加密或抽样，并规定保留期限。没有 token 和工具名，成本告警和「这单为什么说错状态」都无从查起。

### 11. Kafka 在你们大模型项目里用在哪里，比如异步灌库、Agent 任务队列、日志回流分别怎么用

**参考答案**

结论：Kafka 适合文档灌库和轨迹回流这种可延迟、可重放的流水。用户正等着的那一轮对话，不要放进 Kafka 再等消费。

异步灌库：文档变更发一条消息，键用文档号，保证同一文档按顺序处理。消费者解析、切分、嵌入，按片段哈希幂等写入。失败重试后进死信，不要在 Web 请求里嵌文档。写入成功之后再提交位点。

Agent 任务队列只放用户不必同步等待的长任务。Kafka 至少投递一次，又没有可见性超时，所以任务先落库，消息只做唤醒，消费者按任务号抢占。处理中崩溃后可以再次被唤醒，业务靠幂等键，不靠「只消费一次」。聊天里的工具调用仍在请求线程或自己的工作池里完成。用 Kafka 模拟延迟审批会很难看，超时更适合任务表或专门的延迟机制。

日志回流是把工具和 trace 事件再发一个主题，给离线评测和成本汇总。这是扇出，事务真相仍在 MySQL。主题上的数据可以迟到和重复，消费者按事件号去重。不要从回流主题反查这笔退款有没有发生。

三条链路分开主题和消费组。灌库积压不应堵住审计消费。

### 12. 如果让你从零搭一个 Java + Spring AI 的企业知识库问答，技术选型（模型网关、向量库、缓存、限流）你怎么定

**参考答案**

结论：应用只依赖 Spring AI 的 `ChatModel` 和向量存储接口。供应商、向量库和限流都放在接口后面，业务代码不绑死一家。

模型网关用一个 OpenAI 兼容入口，后面接内网模型或云厂商。密钥、超时、默认模型和备用模型放在网关或配置里。敏感制度走内网模型。应用侧仍然是 ChatClient。

向量库沿用前面的标准：要和文档版本、组织权限一起过滤，就先 PGVector，原文和权限以关系数据库为准。测出 ANN 成为瓶颈再拆 Milvus。入库走异步流水，不在问答请求里嵌。

缓存分成三层，不要混：会话上下文用 Redis，并设置过期；嵌入结果可以按文本哈希缓存；语义缓存只缓存与人无关、与单号无关的稳定 FAQ，键里带知识库版本，文档一更新就失效。运单和个性化答案不进语义缓存。

限流在网关卡供应商的请求数和 token 数，应用里按租户再限一次。超过就拒绝，并说明可以稍后重试。线程池按配额隔离。检索必须带权限条件，不能先召回、再指望提示词不说出来。

可观测性、重排和评测集从第一天留位置。没有评测集，选型时的数字都只是猜测。

### 13. 你怎么看 Spring AI 和 LangChain4j 的差异，团队已有 Spring 全家桶你会选哪个，为什么

**参考答案**

结论：团队已经是 Spring Boot，就用 Spring AI 作为调用和装配的主路径。LangChain4j 会在同一个系统里做出第二套编程模型。

Spring AI 的核心是 `ChatModel` 加 `ChatClient`。交叉关注点走 Advisor，工具走 `ToolCallback`，模型、向量库和 MCP 以 Boot Starter 提供，观测走 Micrometer，和现有的 Security、WebFlux、JDBC 配在一起。1.0 之后比 0.8 时代稳定，小版本仍要锁定。

LangChain4j 的习惯是声明一个接口，用 `AiServices` 生成实现。工具、记忆和 RAG 组件很全，示例里的 Agent 味道更重，Quarkus 和 Spring 都能接。它不是 Spring 的官方抽象，自动配置、观测和事务边界要自己再包一层。

选 Spring AI，是为了配置、链路追踪和人员接手保持一致，不是因为它的检索算法更强。检索质量取决于切分、模型和评测，两个框架都不会替你做。只有某块必须用的能力 Spring AI 还没有、LangChain4j 已经有，才在那一块局部引入，并且不要两套同时当核心调用路径。

### 14. 最近在看什么 AI 方向的东西，Spring AI Alibaba 1.1 的 Agent Skills 你了解多少，有没有自己跑过 Demo

**答题思路**

这题看你是不是真的在跟，不看名词数量。没跑过 Demo 就直接说没跑过。

1. 只讲一个你最近真在看的方向，并说明它补的是哪块短板：检索评测、工具幂等、MCP，或上下文怎么装。先给结论，再说你看的文档或代码，最后说一个你自己对上的细节。不要编阅读量和指标。
2. 还没看过 Agent Skills，就按下面这个范围讲，并声明还没动手。它是 Spring AI Alibaba 在 1.1 这一代加到 ReactAgent 上的，不是 Spring AI 核心里的类。一个技能一个目录，入口是 `SKILL.md`，里面有名称、描述和操作步骤，还可以带 references、scripts。`ClasspathSkillRegistry` 或 `FileSystemSkillRegistry` 负责加载，`SkillsAgentHook` 挂到 ReactAgent 上。
3. 重点是渐进式披露：系统提示里先只放技能的名称和描述；模型判断用得上，再通过 `read_skill` 读取正文，然后才去看附件或调用该技能允许的工具。目的是不要把所有规程一股脑塞进系统提示词。
4. 和相邻概念分开。一个 Tool 是一次函数调用。一个 Skill 是按需加载的操作说明，里面可以再要求调用工具。MCP 是远程工具和资源的协议，Skills 是打进上下文的规程包，两边可以同时存在。
5. 跑过的话，只讲你的目录结构、哪句提问触发了 `read_skill`、轨迹里有没有把全文提前塞进去。没跑过，就说下一步会用一个只含 `SKILL.md` 的技能，验证不触发时上下文里没有正文。不要编你没见过的延迟或准确率。
